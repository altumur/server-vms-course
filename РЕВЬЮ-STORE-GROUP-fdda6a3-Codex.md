## 1. P2 — ответы admin@ проходят без полной формы

`runner/store_group.py:318–324`: после сравнения TSV полная схема вызывается только для `store@` / `@as`, причём только для объекта или массива. Ветвь `admin@` её полностью обходит.

Проба с буквальными запросом и ожиданием сц. 07 шага 6: ответ `409 {"kind":"refused"}` без обязательного `error` даёт **GREEN**. Отдельный контроль сц. 17 шага 10: `403` с пустым телом тоже даёт **GREEN**. Неизменённый общий проверяющий схемы на тех же ответах обнаруживает соответственно `body.error: missing` и отсутствие `kind/error`.

Это не допустимое сравнение по подмножеству: общий README, «Ожидание», строка `<код>` оставляет проверку полной формы даже без JSON в TSV; README P/01.3, «Полная форма и воспроизводимость» требует её поверх подмножества. В `01-store.api.openapi.yaml` `/v1/join` с 409 использует `Refused`, с 403 — `ForbiddenFault`, оба требуют `kind/error`.

Нужно проверять схему служебных ответов той же двери P/01, в том числе при пустом/не-JSON теле. До фикса неправильная реализация служебных ответов получает ложный зачёт новых сценариев.

## 2. P2 — SIGKILL уборки засчитывается как успешный sigterm

`runner/store_group.py:92–104`: `stop()` ждёт только оболочку `Popen(..., shell=True)`, затем вызывает `finish_process()`. При уже вышедшей оболочке общий `c_process.finish()` убивает оставшихся потомков SIGKILL; отсутствие ошибок уборки превращается в `ok` проверяемой директивы.

Нативная проба: оболочка запускает принадлежащий ей дочерний процесс, который игнорирует SIGTERM, и ждёт его. SIGTERM группе завершает оболочку (`-15`), дочерний процесс остаётся жив; `finish_process` посылает ему SIGKILL (`9`), а `Group.stop()` возвращает **пустой список причин / успех**. Перехват только наблюдает сигналы общего cleanup, поведение `stop` и ОС не заменено.

Следствие для сц. 17/18: проверяемая остановка и принудительная уборка смешаны. Сломанная остановка демона может получить зачёт, а последующий restart/recover начнётся после принудительного убийства, хотя шаг объявлен успешным SIGTERM.

Нужно сначала подтвердить выход всей принадлежащей команды от заданного сигнала, как это уже делает `c_process.signal_and_wait`; принудительную уборку оставить отдельно и не превращать её успех в успех шага. Норма: общий README, «Стенд группы», `@sigterm store@<id>` / `@sigkill store@<id>`; правило ожидания выхода процесса, а не только оболочки, уже закреплено общим кодом стендов.

## 3. P2 — срок двери короче разрешённой пересылки

`runner/store_group.py:210`: для всех обычных запросов группы поставлен `HttpDoor(..., timeout=2)`. P/01.3 Н1.3 `door` даёт пересылке попытку **2 с и запас 1 с**. Поэтому внешний клиент, обрывающийся ровно через 2 с, не покрывает даже это разрешённое окно; отдельного двухсекундного ограничения для `store@` договор стенда не вводит.

Нативный сокет роли `console` принимает запрос и возвращает обычный HTTP 200 через 2,25 с — в пределах 3 с. `Group.request()` вместо получения ответа обрывается через **2,005 с** с транспортной ошибкой. Запросы без `@until`, в том числе запись через `store@d1` сц. 07 шага 10, получат ложный отказ стенда; повторять такую запись нельзя.

Нужно выбрать ограниченный срок внешнего запроса, покрывающий нормативные сроки реализации/пересылки, с учётом бюджета сценария. Транспортный обрыв более раннего клиента не является доказательством нарушения норм реализацией.
