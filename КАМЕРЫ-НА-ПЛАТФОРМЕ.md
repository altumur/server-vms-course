# Камеры на нашей платформе: где живут Variables — с серверами и без

Мы — вендор: делаем камеры и софт для онпрем-инсталляций, и код в камере — та же платформа, что на серверах. Два сценария: **с серверами** — камеры и кластер серверов в одном домене — и крайний случай, **только камеры**: ни одного сервера, ни NAS, записи на SD-картах. В обоих каждая камера — отдельный кластер из одного и свою строку пишет всегда сама; сценарии отличаются тем, где размещён домен и кто пишет запись. Отдельно — камера сама по себе, вне домена, и переход из одного сценария в другой.

Ссылки вида `vmsworker/w2cplatform/contract.go` — на продукт (`vmssubsystem/vmsworker`), проверены против рабочей копии на 25 сентября 2026; если код с тех пор уехал, верьте коду. Записка начиналась как проектирование; что из неё сделано и где — в разделе «Что решено» и в ссылках на уроки по ходу текста: камеры как члены домена — М12, уроки 9–17; резервный архив и дозапись из него — в продукте и в курсе (М10B, уроки 16 и 26).

## Что решено (26–28 сентября 2026)

Записку сверили с курсом, и бо́льшая часть её механизмов оказалась **доменом М12 под другими именами**. Решили строить на М12: камеры — отдельные кластеры, серверы — ещё один кластер, домен объединяет их в одну систему. Это вторая часть М12, уроки 10–17 (все написаны, с кодом и тестами; решения — в [`М12_DomainVMS/module-design.md`](М12_DomainVMS/module-design.md), раздел «Вторая часть»). Урок 9 про правку выключенной камеры закрывает первую часть: он нужен любому домену, где кластеры часто недоступны, — например, филиалам на слабой связи.

**Как устроен домен.** Как mesh-сеть роутеров, только наоборот. Один член — **держатель домена** (кластер или камера, где запущены службы домена: подписывающий, размещение, консоль домена), как контроллер mesh-сети; ретрансляторы — те же, что в mesh; держателя ставят туда, куда дозваниваются все, часто в облако. Отличий два: данные собираются с камер, а не раздаются клиентам, и настройки члены забирают сами — держатель никому не звонит, иначе камера за NAT их не получила бы. Держатель — роль, а не вид: «облачный кластер — держатель домена» значит, что службы домена запущены в облаке, а не что там пишется видео. Раньше эта роль называлась «доменный кластер», «кластер домена» или «хост домена»; переименована 29 сентября (запись в [`GLOSSARY.md`](GLOSSARY.md)).

| Решение | Что выбрано | Почему |
|---|---|---|
| Что такое камера | **Отдельный кластер — кластер из одного** | У набора камер нет того, что делает кластер кластером в М11: ни raft, ни оркестратора, ни юнита, который может переехать на другую камеру. Если все камеры считать одним кластером, им понадобится одно согласованное хранилище, то есть Raft между камерами, от которого записка отказывается. Если каждую камеру считать своим кластером, её хранилище согласовано бесплатно (флеш, один писатель), а правило М12 «ни один raft не охватывает кластеры» — это и есть «без консенсуса» из записки. |
| Что их объединяет | **Домен М12** | Вступление — М12 урок 6. Одна консоль, правящая любую камеру, — сохранённая правка урока 9: домен её хранит, агент камеры уносит домой. Недоступная камера — неполный ответ урока 1. Доверие без связи — урок 7. «Домен может пропасть, и камеры не заметят» — тезис М12, и это ровно «главная выключена, запись идёт» из этой записки. |
| Кто пишет строку камеры | **Сама камера, всегда** | Первый вариант записки переносил строку на серверный кластер при привязке (режим adopted), и для этого требовались маршрутизирующее хранилище, поток изменений и запись камеры в хранилище серверов. От него отказались: если владелец не меняется, ничего из этого не нужно. |
| Номер камеры | **Локальный id остаётся целым, серийник — в `ref`** | Домен М12 уже отвечает по `ref`. Сделать серийник id значит пройтись по всем целым номерам камер ниже — в индексе событий `cam INTEGER` — без выгоды. |
| Строка устройства | **`vms/devices/<устройство>` — по устройству, не по id камеры** | В курсе «устройство» уже значит прибор за каналами (`device_of`, `group_by: device`): регистратор на 16 каналов — одно устройство и 16 строк камер. Если ключевать по камере, сведения о регистраторе повторятся 16 раз. |
| Главная камера | **Держатель домена, размещённый на камере** | В М12 уже есть один назначенный кластер со всеми доменными службами, и при его падении переносить их некуда. На камере это держатель домена на одном узле: перенос домена становится обычной операцией, а старый держатель, который вернулся, — обычным событием. Для этого нужен **срок** (урок 15). |
| Кто открывает соединение | **Камера, всегда** (урок 10, шаг 7) | Камера может быть никогда недоступна домену — NAT, изолированный сегмент, сотовый канал, — а домен иногда доступен камере. Её агент на своём проходе уносит строки домой и оставляет **отчёт** в хранилище держателя домена; домен читает только своё хранилище. Молчание камеры — возраст её отчёта по часам домена. |
| Поток камеры, до которой не дотягивается и серверная | **Камера толкает один поток на приёмник кластера записи — и для записи, и для живого видео** (урок 16) | Раздача переезжает с камеры в кластер записи. Куда и по какому праву — книга основных и ключ потока от подписывающего домена; когда — по долгому опросу; диапазон с карты — ответ на заявку. Туннель не нужен. |
| Объекты, ретрансляторы и центр | **Каждый уровень звонит на уровень выше и достижим только снизу** (урок 17) | Ретранслятор — роль кластера посередине, а не тип (в примере заказчика — офис). Камера, которой виден только её ретранслятор, ходит к домену через ретранслятор в обе стороны: ретранслятор несёт ей вниз всё, что оставил домен, и несёт наверх её отчёт в сводном объекте. Медиа — урок 16 на каждом переходе. Для облака и мобильных операторов — «звезда». |
| Сценарии между камерами | **Запрос со сроком — через долгий опрос цели** (урок 16, шаг 8; урок 17, шаг 7) | Правка ждёт выключенную камеру, а запрос «сейчас» ждать не должен. Через агента он шёл бы полминуты. Приёмник, который цель уже опрашивает, будит её за секунду. Право — токен, выданный под сценарий, с названным действием. |
| Кто члены домена | **Запись `domain/members`: пишет регистратор, читает каждый проход** (урок 6) | Раньше список был конфигурацией процессов домена, и принятая камера оставалась неизвестной до правки окружения и перезапуска. Теперь вступление добавляет, уход убирает, и домен следует записи без перезапуска. Первая запись переносит членов из конфигурации; кто отчитывается, а в списке его нет, — «стучится», и администратор может его принять. |
| Забор или толкание | **Решает домен, не человек** (урок 16) | Факт о сети: общая сеть у кластера записи и камеры — регистратор забирает поток, общей нет — камера толкает. Регистратор, который не смог забрать (межсетевой экран), говорит это сам, и домен переводит камеру на толкание и помнит это. Камера может сказать «толкаю всегда». |
| Два сервера без места для свидетеля | **Два кластера из одного, резервы `edge` и `backup`, один поток** (М11 урок 1, урок 16) | Raft из двух голосов хуже одного сервера. Отказоустойчивость даёт запись, а не планировщик: карта и резервный том второго сервера пишут, когда основная не пишет, и узнают об этом из самого потока — домен в переключении не участвует. |
| Видимость | **Что кластер видит — говорит он сам; кто через кого ходит — одна запись оператора** (урок 17, шаг 8) | Сети — наблюдаемый факт, его сообщает агент кластера (`domain/reaches`). Центр, «звезда» и дорога через ретранслятор — политика, её задаёт оператор записью `domain/topology` по CAS, с проверкой при записи. Метки для этого не годятся. |
| Дверь камеры | **Только для площадки** | Регистратор серверной, сводный журнал событий, страница камеры. Домен дверью не пользуется никогда — ни для чтения, ни для правок, ни для запросов, и в варианте «только камеры» тоже. Дверь необязательна: у камеры за NAT она закрыта. |
| Правка выключенной камеры | **Сохраняется по полям и применяется, когда камера вернётся** (урок 9, написан) | `503` честен, но для члена домена, который часто недоступен — филиал на слабой связи или камера, — бесполезен. Правка лежит рядом с правами (`domain/pending/<кластер>`), агент камеры забирает её домой, консоль камеры применяет её от имени оператора и проверяет права в момент применения. По каждому полю: применено / уже на месте / конфликт. Результат сверяется по номеру версии, а не по часам. Владелец не меняется. |

**Что отпадает.** ACL на юнит: токен камеры действует только в её собственном кластере, и в чужие хранилища она ничего не пишет. Перенос строки на серверы, маршрутизирующее `Variables`, поток изменений для строк. Федеративное хранилище объектов как отдельная сущность: его роль играет каталог и вид для чтения М12 по отчётам камер. Туннель к камере: медиа камера толкает сама, а управление ходит проходом агента и долгим опросом. Список членов и топология в окружении процессов домена: и то и другое — записи у держателя домена.

**Что осталось новым** — уроки 10–17: кластер из одного; домен на сотнях мелких членов (край заявленного предела М12, проверен замером); общие настройки без базы у домена; регистратор сервера, пишущий камеру из чужого кластера; тревоги со всех камер одним списком, с молчанием камеры как тревогой; держатель домена на одном узле со сроком; камера, до которой не дотягивается никто, толкает поток сама; цепочка «объект — ретранслятор — центр»; сценарии между камерами за секунду — и внутри ретранслятора, и между ретрансляторами; топология одной записью оператора и список членов, который пишет вступление; забор или толкание, решённые по сетям; офис из двух серверов без оркестратора.

## Что это такое в трёх абзацах

В камере vmsworker работает **на месте**: видео берёт не через DriverPack, а прямо с сенсора, и переехать никуда не может. Оркестратор решает вопрос «на каком сервере работает юнит» — в камере на него ответило железо, поэтому оркестратор ей не нужен. Variables нужны для другого: хранить своё, получать общее сверху и отдавать своё состояние тем, кто спросит.

У платформы уже есть свойство, которое делает это дешёвым: **у каждого семейства ключей ровно один писатель** по ACL. Значит, копии можно сводить односторонним копированием — без консенсуса и без конфликтов. Консенсус понадобился бы только ключу с двумя писателями, а платформа их не допускает.

Ключи раскладываются на три кучки. **Своё** камеры — её строка, устройство, эпоха, события — живёт в ней самой и только в ней; строку пишет её собственная консоль, а правку из консоли домена домен сохраняет, и агент камеры уносит её домой. **Общее** — настройки по умолчанию, дерево папок, сценарии между камерами — публикует домен одним подписанным объектом, и агент приносит копию в каждую камеру; два держателя домена сразу разводит номер срока — так же, как эпоха разводит два экземпляра воркера. **Публикуемое** — heartbeat, срез snapshot, страницы тревог — агент камеры кладёт в отчёт домену, а записи и события остаются у неё; домен к камере не ходит. Всё, что домен хочет сказать камере, он кладёт в свои **книги**, а агент камеры уносит их домой. Где пишут камеру, куда толкать поток, кого она может спросить — это книги. Сценарий между камерами — запрос со сроком. Он доходит тем же долгим опросом, которым камере говорят толкать поток. Два варианта развёртывания отличаются только тем, где размещён домен: на серверах или на одной из камер.

## Три кучки ключей

| | Примеры | Писатель | Где живёт |
|---|---|---|---|
| **своё** камеры | её строка `vms/cameras/<id>` (`ref` — серийник), `vms/devices/<устройство>`, `vms/epoch/<id>`, `vms/requests/*` к ней, события | строку — консоль камеры, в том числе по сохранённой правке из консоли домена, которую принёс агент; остальное — сама камера | в камере, и только в ней |
| **общее** на систему | настройки по умолчанию (retention и пр.), дерево папок, сценарии между камерами | домен: подписывающий публикует документ, держатель домена хранит указатель | объект за указателем у держателя домена; подписанная копия в каждой камере, на карте (М12 урок 12) |
| **доверие** | ключи подписывающего, список отзыва, права на эту камеру (`domain/keys`, `domain/grants`); книги домена — основных, опроса, запросов (`domain/primaries`, `domain/poll`, `domain/asks`) | домен; в камеру пишет только её агент | в камере, под `domain/*` (М12 уроки 4, 13, 16) |
| **публикуемое** | heartbeat (с признаком `polls`), срез snapshot, что камера видит (`domain/reaches`), `rec/<cam>/…`, корзины событий | своя камера | в своей камере (heartbeat и срез — в RAM); heartbeat, срез, сети и страницы тревог уходят домену в отчёте агента |

Пользователи в камеру не попадают вовсе: они у подписывающего домена, а камера держит только его публичный ключ, отзыв и права, — так же, как любой кластер М12.

У камеры два имени. **`ref` — её серийный номер**: по нему её знает домен, он выдан на заводе и остаётся, если камеру вывели из домена и ввели снова. **Локальный id** в её кластере из одного — целый, как в любом кластере; `next_id` для него не нужен, строка одна.

**Строка камеры делится на две**, потому что у неё два писателя и внутри одной камеры. `vms/cameras/<id>` — то, что решает оператор: имя, папки, метки, включена ли, retention, live; пишет консоль. `vms/devices/<устройство>` — то, что знает только устройство: модель, прошивка, возможности сенсора, адрес; пишет воркер. В курсе строка уже есть (урок 25 М10B, шаг 4а): какие события поднимают юниты устройства и что оно умеет — `events`, `rays`, `relays`, `ptz`, `presets`. Воркер пишет её, только когда ответ изменился, и кладёт то же описание в heartbeat как `can` у камеры, чтобы его видел домен. По ней проверяются сценарии. Пока это одна строка, у неё два писателя; разделённые — каждая с одним писателем, как везде в платформе.

## Своё: камера — кластер из одного

Каждая камера работает так, как сегодня работает `vmsdev` на одной коробке, минус контроллер (М12 урок 10):

- **Строка.** Её создаёт собственная консоль камеры при первой загрузке, с `ref: <серийник>`.
- **Закреплённый юнит.** В спеке — `place: device`: юнит и есть устройство. Размещать его некому и незачем: слотов и аренд нет, назначение неизменно, ключей, которые писал бы размещающий, просто нет. Контроллер в камере не работает.
- **Эпоху** воркер берёт сам — он её единственный писатель — и пишет на флеш раз за загрузку. Она нужна не для переезда, а для путей архива `rec/<cam>/e<epoch>/` и для отсечения событий по эпохам: после перезагрузки, в том числе аварийной, номер должен вырасти.
- **Хранилище** — обычный `FileVariables`: интерфейс `Get/Put/List/Delete` с CAS (`w2cplatform/variables.go:80`), код воркера не меняется.
- **Флеш.** Heartbeat и срез snapshot живут в RAM и отдаются по запросу, а не пишутся на флеш; аренд у камеры нет. На флеш уходят только конфигурация, эпоха и то, что приносит агент, — единицы записей в сутки.
- **Отчёт — после первой публикации.** Камера, отчитавшаяся раньше, сказала бы «камер нет» — а это *полный* ответ, которому домен обязан поверить. Поэтому до первой публикации она не отчитывается вовсе, и домен говорит «ещё ни разу не отчитывался». То же правило держит и её дверь для площадки.
- **Связь вверх** — агент домена, как в любом кластере: уносит `domain/*` домой и оставляет отчёт у держателя домена под `domain/members/<камера>/` — heartbeat и срез, исходы правок, копию указателя общих настроек, запись о держателе, эпоху, страницы тревог, сети, которые камера видит. (Это префикс объектов с отчётами; список членов — отдельная запись `domain/members` в Variables.) Переписывается только изменившееся.
- **Правку, пришедшую от домена, применяет агент камеры у себя** — не через её дверь: у камеры, до которой никто не дотягивается, двери для чужих нет.

### Хранилище камеры — без маршрутизации

Раз строку всегда пишет камера, её хранилище — обычное хранилище кластера из одного. Куда идёт каждый ключ:

| Ключ | Get | Put |
|---|---|---|
| своё, пишет воркер камеры | локальный файл | локальный файл |
| своя строка | локальный файл | локальный файл — консоль камеры, в том числе по сохранённой правке, принесённой агентом |
| общее и доверие | локальная копия, принесённая агентом | только агент; правка общего — в консоль домена |
| heartbeat, срез snapshot | RAM | RAM |

## Камера одна и камера в домене

**Одна** — камера из коробки: её веб-страница и есть консоль, строку пишет она. Общего нет, точнее, оно тоже своё: политика и пользователи одной камеры.

**В домене** — камера вступила в домен (М12 урок 6). Строку по-прежнему пишет она сама; меняется только то, откуда приходят общее и доверие: их приносит агент домена. Домен знает её по её отчётам, как любого своего члена, и отвечает по её `ref`.

### Вступление в домен

1. **Заявка.** Оператор в консоли домена выбирает найденную камеру (WS-Discovery / mDNS) или вводит серийник. Камера должна доказать, что она физически у этого заказчика: одноразовый код с наклейки или QR, либо пароль администратора камеры; с ваучером производителя — без участия человека. Без доказательства в домен можно было бы ввести чужую камеру из той же сети.
2. **Выдача.** Подписывающий домена выдаёт камере LDevID на её серийник. Токенов на чужие ключи камера не получает: писать ей есть куда только в собственном кластере.
3. **Строка никуда не едет.** Регистратор записывает камеру в список членов домена (`domain/members`), и со следующего прохода домен читает её по отчётам, которые оставляет её агент; конфигурацию домена никто не правит и ничего не перезапускает. Её строка остаётся её строкой. Камера, которая отчитывается, а в списке её нет, названа в консоли домена как «стучится», и администратор может её принять.
4. **Агент.** Агент камеры начинает приносить `domain/*`: ключи подписывающего, отзыв, права, общие настройки, сохранённые правки.

### Правка

На странице камеры оператор правит её строку сам, в любой момент, — это консоль её кластера. Из консоли домена правка для камеры **сохраняется** по полям (урок 9): агент уносит её на следующем проходе, камера применяет от имени оператора с проверкой права, и исход уходит вверх в отчёте того же прохода. Ответ оператору — «принято, применится, когда камера выйдет на связь». Мгновенной пересылки в дверь камеры нет — домен к камере не ходит. Настройки самого устройства — адрес, NTP, параметры сенсора — лежат в `vms/devices/<устройство>` или в собственных ключах камеры и правятся на ней.

### Выход из домена

- **Плановый.** Домен убирает её из списка членов — со следующего прохода он её не читает, какой бы отчёт она ни оставила, — и отзывает LDevID. Переносить нечего: строка у камеры и так своя, общие настройки остаются на карте последней копией.
- **Домена больше нет.** Камера продолжает работать по своей строке и последним общим настройкам; сброс к заводским — по желанию оператора, с паролем администратора.
- **Чужой домен.** Пока камера в домене A, заявка домена B отклоняется. Сначала выход или сброс.

## Сценарий с серверами

Серверы — ещё один кластер того же домена, обычная платформа с оркестратором; держатель домена, как правило, на них. Камеры в кластер серверов не входят: каждая — свой кластер, и контроллер серверов о них не знает — их строк в его хранилище нет.

### Что остаётся оркестратору

Всё, что может переезжать:

- **Регистраторы.** Регистратор сервера пишет камеру из чужого кластера: находит её не в heartbeat'ах своего кластера, а в **книге источников** — `domain/sources/<кластер>`, которую домен публикует для кластера записи, а агент кластера приносит домой (М12 урок 13). Одну камеру пишет один кластер — это решение домена, хранится как размещение; перенести запись в другой кластер — отдельная просьба, и книги следуют за ней. Запись продолжается и при выключенном домене: регистратор разрешает `ref:` по копии книги в своём кластере.
- **Live-шлюзы и автоматизация** — без изменений.
- **Контроллер** серверов размещает регистраторы и остальное своё, как всегда; камер он не размещает и срезов snapshot за них не пишет — каждая камера публикует свой.

### Что ходит между камерой и доменом

| Направление | Что | Кто пишет | Как доходит |
|---|---|---|---|
| вниз | `domain/keys`, отзыв, `domain/grants`, общие настройки, `domain/pending`; книги: основных (кто пишет камеру и куда толкать), опроса, запросов | домен; книги строит один проход домена в процессе подписывающего, потому что в них его токены | агент камеры забирает сам |
| вверх | отчёт: heartbeat и срез snapshot, исходы правок, копия указателя общих настроек, запись о держателе, эпоха, страницы тревог, сети (`domain/reaches`) | агент камеры, под `domain/members/<камера>/` | агент кладёт в хранилище держателя домена тем же проходом |
| на месте | события, записи на SD | камера | читаются у источника теми, кто на площадке до камеры достаёт; домен видит тревоги по страницам в отчёте, записи с карты приходят выгрузкой по заявке (урок 16) |

У каждого ключа один писатель, поэтому никакого слияния нет: агент применяет документ с большим `(term, rev)`, подпись которого сходится с ключами, которые у камеры уже есть.

**Соединение открывает камера, всегда** (М12, урок 10, шаг 7). Камера может быть никогда недоступна домену — NAT, изолированный сегмент, сотовый канал, — а домен иногда доступен камере. Поэтому домен не ходит к камерам вовсе: он читает только хранилище своего кластера, куда агент каждой камеры оставляет отчёт. Молчание камеры — возраст её последнего отчёта по часам домена; время внутри отчёта домен переводит на свои часы. Правка из консоли домена для такой камеры всегда сохраняется и уходит домой с агентом (урок 9). Дверь камеры остаётся для площадки: регистратор серверной забирает RTSP и читает карту, сводный журнал событий серверов забирает события, соседи — закрытые корзины тревог, оператор на месте открывает страницу камеры. Домен дверью не пользуется никогда.

### Камера, до которой не дотягивается и серверная

Всё выше предполагает, что регистратор серверной достаёт до камеры: тянет её поток и читает её карту. Если нет — камера за NAT, серверная в другом здании, облачный кластер записи, — поток открывает камера (М12, урок 16).

**Что из двух — решает домен, по трём признакам, от сильного к слабому** (толкать может только камера-член; камеру без платформы забирают всегда): камера сказала `push` — толкает всегда (сотовый канал); регистратор, которого послали забирать, сказал, что не может (`source_unreachable`, межсетевой экран), — толкает, и домен помнит это в `domain/roads`, пока не изменятся сети любой из сторон или кластер записи; иначе сети, которые сообщают сами кластер записи и камера: общая есть — забор, нет — толкание. Не названы сети — как раньше, слово камеры. Причину книга источников несёт в `road`.

Камера толкает **один поток** на приёмник кластера записи — и для записи, и для живого видео; адрес приёмника и ключ потока (токен подписывающего домена) приходят в книге основных. Туннель не нужен, страница камеры остаётся для оператора на площадке.

**Приёмник** — процесс на каждом сервере кластера записи со стабильным адресом (`rec/ingest`). Он принимает поток камеры и раздаёт его внутри кластера регистратору и шлюзу. Он держит долгий опрос камеры и отвечает на него, как только меняется ответ. Он проверяет токены по ключам, которые уже лежат в его кластере. Все три канала камеры открывает сама камера:

| Канал | Куда | Что несёт | Скорость |
|---|---|---|---|
| проход агента | к держателю домена (или в свой ретранслятор) | вниз — книги, права, правки; вверх — отчёт | полминуты |
| долгий опрос | в приёмник | «толкай поток», «выгрузи диапазон с карты», запросы других камер | около секунды |
| поток | в приёмник | живое видео, запись, выгрузки с карты | непрерывно |


- **Когда толкать.** Пока поток нужен: регистратору с постоянной записью — всегда, записи по событию — на окно, зрителю — пока смотрит и ещё 10 секунд. Узнаёт по долгому опросу к приёмнику: первый опрос отвечается сразу, удержанный будит уход зрителя.
- **Время кадра — съёмки, по часам камеры.** Приёмник переводит его на часы кластера по разнице, которую камера называет в каждом запросе, а заявку на диапазон — обратно. Иначе шов записи с дозаписью разошёлся бы на расхождение часов.
- **Кольцо предзаписи — на камере.** Пока поток не нужен, камера держит последние секунды; первая отправка после «толкай» начинается с них — начало события не теряется. Регистратор получает кольцо, зритель — живой край.
- **Карта — по заявке.** Дозапись и просмотр карты — выгрузка диапазона ответом на заявку по её номеру, кадрами со своими временами: регистратор просит минуту и получает эту минуту. Просмотр карты перестаёт быть мгновенным.
- **Несколько приёмников кластера** передают поток друг другу: камера толкает на любой, а запись может держать регистратор другого сервера. Приёмник, к которому толкает камера, толкает дальше соседу с подписчиком; сосед отстал — хвост режется целиком до ключевого кадра, а не теряется кадрами посреди GOP.
- **Опрос держит каждая камера-член**, дверь у неё открыта или нет, и говорит об этом в heartbeat'е (`polls`). Камеру, которую серверная пишет, забирая поток сама, толкать не просят: регистратор на приёмнике не подписывается. Зато её можно спросить (раздел «Сценарии между камерами»).
- **Камера, которую никто не пишет**, — например поворотная, которую держат только для живого просмотра, — всё равно опрашивает приёмник: адрес ей даёт **книга опроса**, отдельная от книги основных. Толкать ей не велят, пока никто не смотрит, а запросы других камер она получает. Отдельная книга нужна потому, что книгу основных читает резервная запись на карте, и опрос без записи не должен выглядеть для неё основной записью.
- **Резервная на карте знает, пишется ли основная,** прежде всего от своей камеры: камера сама знает, отдала ли она поток основной, и это решение местное, без домена. Когда камера сказать не может — по книге основных: должна ли серверная писать камеру, пишет ли, и только ли запускается запись. Остановку карта подменяет сразу, запуск — через 20 секунд; книгу, которую агент давно не подтверждал, считает незнанием и пишет сама.

### Объекты, ретрансляторы и центр

**Ретранслятор** — роль кластера посередине, а не тип: в примере заказчика это офис, но им может быть и серверная на объекте, и региональный узел, и облачный кластер. Камеры на объектах, регистраторы в офисах, один мониторинговый центр, и все за NAT, кроме центра (М12, урок 17). Правило одно: каждый уровень звонит на уровень выше и достижим только снизу.

- **Управление плоское, где можно.** Кто дотягивается до центра, отчитывается домену напрямую.
- **Камера, которой виден только ретранслятор, — через него в обе стороны.** Вниз ретранслятор несёт ей всё, что оставил домен; вверх — её отчёт в сводном объекте. Свежесть её книг — по последнему разговору ретранслятора с доменом: ретранслятор сообщает возраст по своим часам, камера отсчитывает его на своих. Цена: лёг ретранслятор — его камеры молчат вместе с ним, другой дороги нет.
- **Запись описывает дорогу, а не запрещает другую.** Камеру, поставленную за ретранслятор, домен читает и из сводного отчёта, и из её прямого отчёта: среди дорог, живых по часам домена, — более новый по часам камеры. Камера, которая на самом деле дотягивается до домена или чьи часы шагнули назад, из-за записи не замолкает.
- **Медиа — урок 16 на каждом переходе.** Камера толкает в ретранслятор, ретранслятор отдаёт в центр то, что центр хочет, и желание центра доходит до камеры. От камеры поток получает один кластер — её ретранслятор. Для облака и мобильных операторов, где до ретранслятора не дозвониться, — «звезда»: камера толкает в центр, ретранслятор забирает свои потоки оттуда.
- **Опрос и запросы.** Камера за ретранслятором, которую никто не пишет, опрашивает приёмник своего ретранслятора: центр и держатель домена ей недоступны. Центр доходит до неё через передатчик ретранслятора — и запросом, и желанием зрителя. Сценарий между объектами двух ретрансляторов идёт вверх через свой ретранслятор (раздел «Сценарии между камерами»).
- **Топология — одна запись оператора** `domain/topology`: кто через какой ретранслятор ходит, где центр, какие ретрансляторы — «звезда». По CAS, с проверкой при записи (через держателя домена не ходит никто), и каждый проход читает её оттуда без перезапуска. **Какие сети видит кластер или камера, они сообщают сами** (`domain/reaches`): сети площадки из `REACHES`, а сети интерфейсов — только запасным источником, без туннелей VPN (урок 17, шаг 8).

### События не копируются, записи дозаписываются

> **В силе**, и уже есть в курсе: архив устройства и дозапись из края — М10B урок 16; запись на карте нашей камеры как резервный архив и копирование из неё сэмплами, а не перезаписью, — М10B урок 26. Новое одно: регистратор сервера находит камеру через каталог домена, а не в heartbeat'ах своего кластера — М12 урок 13.

Камера публикует heartbeat ресурса, и `MergedIndex` на серверах (`w2cplatform/eventdatabase.go:519`) находит её среди источников и забирает `GET <url>/events` прямо у неё — если серверная на той же площадке до неё достаёт. Недоступная камера честно видна как `unreachable`, а не как пустое окно; её тревоги доходят до домена страницами в её отчёте (М12 урок 14).

Живую запись ведёт регистратор на сервере, как сейчас: тянет RTSP с камеры и пишет в свой том ObjectStorage. Карта камеры — **резервный архив** этой записи: том вида `edge`, который пишет регистратор в самой камере. Закрытие дыр основной записи из него — **дозапись**, урок 16 М10B. Это сделано в продукте (26 сентября) и проверено на коробке; ниже — как. В курсе то же самое — урок 26 М10B: резервный том с сервером и без, `register_admit` и `register_near_rank` вместо `Admit` и `NearRank`, `when: offline` с 20 секундами на старт, кольцом предзаписи на 30 секунд и минутой перекрытия; и пункт 4 списка «Дозапись» ниже — шаг 9 урока 16. Отличия курса: происхождение — в строке манифеста, а не в имени потока (у файлового архива манифест есть), и имена по времени съёмки — только у конвейера с кольцом.

**Два вида резервного тома, один механизм.** Критичная камера пишется в два архива, и основная запись закрывает из резервной любую дыру — обрыв связи с площадкой или те секунды, что её регистратор переезжает на другой сервер. Резервный том — **`edge`**, карта в камере, или **`backup`**, диск другого сервера (с `server`) или адрес, который может обслужить любой ящик (без `server`). Внутри кластера у них одни правила; имена разные, потому что между кластерами разное поведение: `edge` пишет камера сама со своего сенсора, сеть ей не нужна, а на `backup` другого сервера камера шлёт свой единственный поток, только когда основная его не берёт.

- **Место.** Резервный том принимает только записи, сделанные для него, и запись резервного тома никуда с него не уходит (`vms.GuardBackups` поверх общего шва `SpecController.Admit`). Для обычного тома `home` — предпочтение; для резервного — фильтр в обе стороны: основная запись, переложенная на резервный том, оставила бы одну копию там, где их должно быть две.
- **Воркер камеры — рядом с резервной записью.** `near: {sub: rec, of: cam}` при двух записях камеры выбирает резервную (`vms.PreferBackups` поверх `SpecController.NearRank`). Тогда сервер основной записи может упасть, не унося с собой поток: воркер и резервная запись на другом сервере его не замечают, а основная потом дозаписывает свой переезд из резервной.
- **Покрытие.** Регистратор резервной записи публикует в heartbeat сводку `coverage` (начало, конец, число фрагментов) и дверь `url` — то, что урок 15 кладёт в heartbeat держателя.

**Когда пишет резервная — `when` в строке записи.** `always`: каждую секунду, и основная закрывает из неё любую дыру. `offline`: только пока основная запись **включена, но никто её не пишет** — её регистратор молчит (связь потеряна, сервер лёг), не сообщает запись идущей или она никуда не размещена.

- **Сбой, а не решение.** Основная выключена, событие детектора закончилось (`until` прошёл), основной нет вовсе — резервная ждёт. Иначе запись по событиям превратилась бы в постоянную. Только что созданной или ещё не размещённой основной — так начинается каждая запись по событию — даётся 20 секунд на запуск.
- **Предзапись.** Пропажу основной замечают с опозданием — сторожевой таймер регистратора и heartbeat, 15–25 секунд. Поэтому конвейер резервной записи внутри кластера работает всегда, **на удержании** (резерв на другом сервере, который забирает поток сам, — холодный: там начало закрывает карта): `recworkersink` держит в памяти последние 30 секунд (`prebuffer-ms`, от ключевого кадра) и ничего не пишет. Пропажу заметили — удержание снимается, кольцо ложится в архив первым, дальше без шва идёт живой поток. На коробке запись резервного архива началась за 28,5 секунды до снятия удержания.
- **Метки по времени съёмки.** Чтобы кольцо легло своим временем, `recworkersink` ставит кадру метку по часам конвейера — когда кадр снят, а не когда дошёл (`timestamps=capture`, по умолчанию; привязка по приходу осталась запасной).
- **Перекрытие.** Основная вернулась — резервная пишет ещё минуту: архивы перекрываются, и дозапись находит шов с обеих сторон.

**Дозапись.** Регистратор основной записи сверяет своё покрытие с покрытием резервной; дыры — со склейкой швов, бюджет диапазонов, окно по местному времени, пауза при нехватке места, перекрытие с живой записью проверяется дважды (урок 16). Четыре отличия от урока, все из-за того, что том ObjectStorage — не каталог с манифестом:

1. **Своё покрытие** — таймлайн тома по всем потокам записи, а не манифест.
2. **Диапазон копируется сэмплами** из тома в том с исходными метками (`/samples` у двери регистратора → запись в уже открытый писатель тома), а не записывается заново через конвейер — быстрее реального времени и без разбора потока.
3. **Отдельный поток** `<rec>/e<n>/backfill`: дозапись в поток живой записи перемешала бы старые сэмплы с новыми, и движок резал бы последовательность на каждом переключении. Происхождение живёт в имени потока — в томе нет ни манифеста, ни починки по пути.
4. **Только дыры внутри записанного.** Плановая дозапись берёт дыры между первой и последней видимой секундой основной записи — до своей первой секунды запись не шла (создана позже или детектором для одного события), и заливать это из резервной значило бы превратить запись по событиям в постоянную. Верхняя граница — конец видимого покрытия: хвост идущей записи ещё не виден, и это не дыра. Закрепить любой интервал оператор может кнопкой «Закрепить» — заявкой через `rec/requests`, вне бюджета и окна.

Камера при этом ничего не знает о серверах: она пишет и показывает свой архив, а инициатива у того, кому не хватает — то же правило, что записано в `vms/space.go:119`: эвакуация толкает, дозапись тянет.

**Чужие камеры.** Для камеры с картой, но без нашей платформы, архив устройства читается через DriverPack. Продукт сделал это 28 сентября (обратная связь, AU): вызовы хранилища в шиме (`ipint_storage_*`), дверь `GET /device/samples/<камера>` у воркера, который держит устройство, и карта камеры — ещё один источник дозаписи после наших резервов. Дозапись не изменилась ни строкой, как и обещала эта записка.

### Два сервера в офисе: два кластера из одного

Третьего голоса raft негде поставить, а Nomad из двух голосов хуже одного сервера (М11, урок 1). Поэтому два сервера — два кластера из одного под `systemd`, домен над ними — на любом из серверов (М12, урок 16, шаг 9).

- **Основная запись** камеры — на сервере А. **Резервов два**, оба `when: offline`: `edge` — карта в камере, `backup` — резервный том сервера Б. Резервную запись на Б оператор заводит как обычно (`cam: ref:<серийник>`); домен находит её в срезе Б и кладёт книги на обе стороны: камере — вторую дорогу, Б — факты об основной, А — покрытие и дверь резерва на Б.
- **Поток по сети один.** Камера толкает на Б, только когда А не берёт: не отвечает ни один приёмник А или приёмник сам говорит «я должен тебя писать, и никто здесь не берёт» — это он говорит только о камере, которая толкает к нему; о той, что А забирает по RTSP, молчит, и решает книга. Кадры, которых не взял никто, — в кольце камеры, уходят первыми.
- **Когда писать, резервы узнают из потока, а не от домена:** карта — от своей камеры, резерв на Б — потому что камера пришла к нему. Домен мог умереть вместе с А; книга основных — лишь запасной признак.
- **Камеру, которую Б забирает сам** (RTSP), резерв держит **холодной**, без сессии, и открывает её, только когда А не пишет: нашу камеру спрашивает саму — она говорит, кто забирает её поток; у чужой смотрит регистратор А по сети офиса, что требует, чтобы серверы видели друг друга. Сверху вниз ничего нового: забор возможен там же, где обычная запись забором.
- **А вернулся — забирает всё себе:** поток снова на А, дыру А закрывает сначала с Б по локальной сети, остаток — с карты.
- **Живое видео** — там, куда идёт поток: шлюз любого сервера выбирает дорогу по тому же правилу, что и камера.
- **Чего нет:** переезда остальной работы — шлюзы, автоматизация, аналитика держатся каждый на своём сервере. Для чужих камер сервер Б должен знать собственный адрес камеры, а не раздачу А, — пока это не сделано. Появился третий сервер — кластер Nomad из трёх, домен остаётся над ним.

### Когда серверов не видно

Камеру это почти не касается: её строка — её, общие настройки лежат у неё на карте, реконсайлер работает от сохранённого желаемого состояния. Она пишет на SD, события лежат у неё, правка на её странице работает как всегда. Не работает то, что живёт на серверах: консоль домена, если домен на них, и основная запись. Когда связь вернулась, регистраторы дозаписывают пропуск из её резервного архива (урок 16), а правки, которые домен сохранил для неё, агент приносит домой.

### Отказы

| Отказ | Что происходит |
|---|---|
| упал один сервер | оркестратор переносит регистраторы, которые там были; камеру это не касается — она не в кластере серверов |
| недоступны все серверы | камера живёт как жила и пишет на SD; её строку можно править на её странице; консоль домена, если домен на серверах, недоступна |
| недоступна камера | домен показывает её `unreachable`, а не «камеры нет»; правка из консоли домена сохраняется и применяется при её возвращении (урок 9); запрос сценария к ней умирает в своём сроке |
| перезапустился приёмник | запросы, которые в нём лежали, пропадают: через срок плюс 5 с камера-триггер получает «потерян», а не ждёт вечно; поток камера снова толкает после ближайшего опроса |
| ретранслятор потерял центр | его камеры молчат для домена; запрос в чужой ретранслятор ждёт у своего ретранслятора и умирает в сроке; сценарии внутри ретранслятора работают — они центр не проходят |
| два сервера — умер А | камера сразу толкает на Б; карта и резерв на Б пишут по слову потока, не ожидая домена; А вернулся — забирает дыру с Б и с карты |
| два сервера — умер сервер с доменом | переключение записи идёт без него; домен переносят на выживший (урок 15) |
| регистратор не может забрать камеру | говорит `source_unreachable`; домен переводит камеру на толкание и помнит это, пока не изменятся сети |

## Сценарии между камерами

«Машина у ворот — камеру двора на пресет 3». Сценарий лежит в общем документе: `{"when": {"camera", "kind"}, "then": {"camera", "action", …, "within"}}`. Выполняет его камера, чьё событие его запускает. Действие на ней самой — её собственная автоматизация (М10B урок 25). Действие на другой камере — **запрос** к той камере (М12 урок 12). Узкое право `RequestsACL` (`w2cplatform/contract.go:119`) задумано ровно для этого.

**Срок, а не хранение.** В отличие от правки, запрос не ждёт выключенную цель: «пресет 3 сейчас» через час никому не нужен. Срок — свойство запроса: истёкшие выметает любое обращение к приёмнику, даже если цель не опросит больше никогда. Считается он от времени события, а не от момента, когда событие стало видно; сводка окна подавления сценарий не запускает. Срок задаёт `within`, по умолчанию 30 с — как `valid_until` заявки в продукте. Истёкший запрос умирает с исходом `expired`, а цель, вернувшись, его не получает.

**Дорога — долгий опрос цели.** Домен к камере не ходит, а проход агента занимает полминуты. Поэтому запрос кладётся туда, где цель уже держит открытый опрос, — на приёмник, и будит её за секунду (М12 урок 16, шаг 8):

| Цель | Где она опрашивает | Дорога запроса |
|---|---|---|
| её пишет кластер записи | приёмник этого кластера | прямо туда |
| её никто не пишет | книга опроса: приёмник центра или держателя домена | туда |
| за ретранслятором, её никто не пишет | приёмник своего ретранслятора | туда |
| в чужом ретрансляторе, а камере-триггеру виден только свой | приёмник чужого ретранслятора | вверх через свой ретранслятор → центр → чужой ретранслятор (урок 17, шаг 7) |

**Кого можно спросить — любую камеру-член.** Опрос держит каждая камера-член, с открытой дверью или закрытой. Открытая дверь — дорога для площадки, а не для запроса: домен к члену не ходит ни с дверью, ни без. Типичная цель — поворотная в одной сети с сервером, который её пишет забором. Правило «только толкающие» оставило бы сценарии одним камерам за NAT. Спросить нельзя только не-члена: камеру серверного кластера без платформы или незнакомый серийник. Триггером она быть может: её события разбирает автоматика её кластера, и книга запросов уходит в этот кластер. Такой сценарий отвергается при записи с 409 и причиной, а если камера ушла потом — называется на каждом проходе книг.

**Право — книга запросов.** Для каждого сценария домен кладёт камере-триггеру дороги к цели. На каждой дороге токен: `ask: <цель>`, `by: <триггер>`, `acts: <действия сценария>`. Нет сценария — нет и токена. Другое действие приёмник отвергает раньше, чем цель о нём услышит. Ключ потока правом спросить не является, и наоборот. Убранный сценарий опустошает книгу, а уже унесённый токен доживает свои сутки или отзывается по `jti`.

**Кто что делает.** Книги строит один проход домена в процессе подписывающего: источники, основные, опрос, вышестоящие, запросы. По событию камера читает свою проверенную копию документа, находит свои сценарии и оставляет запросы. Цель получает запрос в ответе на опрос, выполняет и отвечает `performed` или `refused: <почему>`. Камера-триггер читает исход, заново перебирая дороги своей книги.

**Под нагрузкой.**
- **Потолок сценария** — `rate_per_minute`, по умолчанию 6, как в продукте. Счётчик живёт в памяти камеры.
- **Схлопывание.** Запрос, равный живому, приёмник схлопывает в тот же номер.
- **Потолок на камеру.** Одна камера держит на одном приёмнике не больше 16 живых запросов.
- **Память, а не журнал.** Запросы и исходы живут в памяти приёмника, исход хранится 15 минут. Двадцать срабатываний за минуту от листвы — шесть запросов, а пока цель между опросами, её ждёт один.

**Между ретрансляторами — по событию.** Путь: камера-триггер → свой ретранслятор → центр → чужой ретранслятор → цель. У своего ретранслятора для этой пары есть собственный токен к центру; `by` в нём — исходная камера, `acts` те же. Каждый переход будит следующий:
- приёмник будит свой передатчик;
- опросы у центра действительно удерживаются и отвечаются при любом изменении;
- исход передатчик ждёт у центра так же.

Весь путь туда и обратно в курсе занял 21 мс при таймерах в секунду — это дорога от крючка на событии. Сценарий, читающий сводный журнал событий, как в продукте, прибавляет интервал хвоста журнала: на ящике от события до запроса 1–4 с, от запроса до заявки на цели 2 мс. По сети это четыре перехода в каждую сторону по уже открытым соединениям. Внутри ретранслятора ничего не меняется: дорога прямая, и центр о запросе не слышит.

**Только камеры — у камеры-держателя.** Без серверов книга опроса ведёт к держателю домена, то есть на камеру-держатель. На ней работает лёгкий приёмник: только опросы и запросы, без потоков. Камеры забирают запросы у неё так же, как забирают у неё всё остальное. Если держатель выключен, запросы между камерами стоят вместе с правкой общего и консолью домена, пока держатель не вернут или домен не перенесут; своя автоматизация каждой камеры при этом работает. После переноса новый держатель в первом же проходе строит книги со своим приёмником, и камеры переходят на него со следующим проходом агента. Запрос соседу прямо в его дверь сознательно не делаем: к камере снова звонили бы, и появилась бы вторая дорога со своими правами и отказами — только на то время, пока нет держателя. Тест урока 16 проходит это целиком: запрос через камеру-держатель, её смерть, перенос домена на другую камеру и тот же сценарий через нового держателя. По дороге он нашёл дыру в переносе домена: указатель на общий документ восстанавливался, а сам документ оставался в хранилище умершего держателя, и книга запросов опустела бы. Теперь новый держатель берёт документ из копии члена по контрольной сумме указателя (урок 15, шаг 3).

## Сценарий «только камеры»: домен на одной из камер

Серверов нет, и домен размещён на камере, назначенной оператором, — это держатель домена на одном узле (М12 урок 15). Его по привычке можно звать главной камерой, но это не особый режим: это те же доменные службы — подписывающий, каталог, вид для чтения, консоль домена, — только держатель у них камера.

### Кто пишет общее

Общее пишет домен и только он. Правка общего со страницы любой камеры уходит в консоль домена на держателе; два оператора одновременно разводятся CAS по ревизии документа.

### Что он публикует

Всё общее целиком, одним документом, подписанным ключом подписывающего (М12 урок 12):

```
{ term, rev, …настройки…, kid, sig }
```

Документ — объект; у держателя домена на него смотрит указатель-Variable, записанный по CAS после объекта. Объём — даже для 500 камер десятки килобайт, больше потолка Variable в 64 КиБ, поэтому объект. Копия у соседа — это данные, которым камера верит по подписи и своему набору ключей, а не по тому, от кого их получила.

### Как документ доходит до всех

1. **Агент забирает.** Агент каждой камеры сравнивает `(term, rev)` указателя со своей копией и, если отстал, забирает документ; назад — никогда: копию новее он не отдаёт за старую.
2. **Проверка.** Подпись проверяется по ключам, которые у камеры уже есть под `domain/keys`; не сходится — документ отвергнут, остаётся прежний.
3. **Хранение.** Документ ложится на карту, а не в RAM: настройки должны пережить перезагрузку при выключенном домене. Значения по умолчанию применяются при чтении и в строки не пишутся.
4. **Доставка видна.** Консоль показывает «rev 7 на 47 из 50; не отвечают: …», пока не станет 50 из 50.

Каждая камера держит последний документ у себя — поэтому смерть держателя не теряет общего: оно уже лежит на всех.

## Только камеры: смена держателя домена, срок как эпоха

Срок полномочий — у держателя домена (М12 урок 15). Он растёт при каждом переносе домена и старше ревизии: документ нового срока побеждает, даже если восстановлен из копии на несколько ревизий позади.

- **Плановая.** Оператор выбирает «перенести домен на камеру X». Держатель замораживает запись состояния домена на секунды переноса, делает последнюю копию прямо на X, X восстанавливается из неё со сроком `term+1`, старый держатель видит больший срок и уступает. Если X копию не взяла — перенос отменяется, держатель остаётся держателем, ничего не потеряно.
- **Аварийная.** Держатель молчит. Оператор нажимает ту же кнопку на X; X восстанавливает домен из ключа подписывающего и самой свежей проверенной копии состояния домена, которую держат другие камеры, и публикует его со сроком `term+1`.
- **Старый держатель вернулся.** Он видит больший срок и понижает себя до обычного члена. То, что успел сделать только он и что не попало в копию, **не пропадает молча и не применяется само**: консоль показывает это списком «не вошло в срок N+1 — применить заново?».

**Кто кому звонит и здесь.** Держатель читает остальные камеры только по отчётам в своём хранилище; плановая передача видит, что новая камера взяла последнюю копию, в её отчёте. Двери соседей открывает только камера, действующая как камера: загрузившаяся ищет держателя, вернувшийся старый держатель проверяет, держатель ли он ещё, а аварийный перенос читает соседей за самой свежей копией — единственное исключение, потому что отчёты лежали у держателя, которого нет. Общий документ возвращается вместе с доменом из копии члена по контрольной сумме указателя (урок 15, шаг 3).

Это единственное место, где возможны два держателя сразу, и оно разрешается как везде в платформе: побеждает больший номер, а проигравший узнаёт об этом при первом чтении.

**Автоматический выбор** («живая камера с наименьшим серийником») возможен, но без кворума разрыв сети даёт два держателя **с одним и тем же сроком**: их придётся разводить по серийнику и показывать проигравшие правки как конфликт. Для конфигурации, которая меняется раз в неделю, это терпимо; по умолчанию — вручную. Это открытый вопрос и в М12: выбирать держателя домена автоматически или это решение человека сознательно.

**Если автоматика обязательна** — кворум: Raft на трёх–пяти назначенных камерах, остальные — читатели копии. По размеру влезает (`hashicorp/raft` — единицы мегабайт), но камеры теряют питание чаще серверов, а голосующая камера пишет журнал на флеш при каждой правке. Это для заказчиков, которым недопустимо «общее заморожено, пока оператор не перенесёт домен», — не первый шаг.

## Только камеры: картина системы без общего хранилища

Общего хранилища объектов нет, и отдельный федеративный `ObjectStore` не нужен: картину системы собирают каталог и вид для чтения домена, которые и так читают каждый кластер — здесь каждую камеру, по отчёту, который оставил её агент. Окупается старое решение платформы: **имя писателя — последний сегмент ключа** (`HeartbeatsDir`, `w2cplatform/contract.go:322`: `<sub>/heartbeats/<worker>`, а не `<sub>/<worker>/heartbeat`), поэтому по ключу видно, у какой камеры спросить.

**Предел.** Проверен замером (М12 урок 11) на 300 камерах, 30 выключены. Когда домен читал камеры сам, проход шёл 82 с по очереди, 5 с в 16 полос, 1,4 с с отсрочкой для молчащих. По отчётам проход читает только хранилище домена — 1,1 с, выключенная камера ничего не стоит, — а цена переезжает в записи: три на камеру за отчёт, 810 записей и 162 КБ за раунд. «Где камера» отвечается из памяти вида для чтения, а не обходом всех камер. Около тысячи камер записей у держателя домена становится много: реже и только изменившееся, или сводный отчёт через ретранслятор, где он есть (урок 17 — одна запись на ретранслятор вместо трёх на камеру).

**Тревоги со всех камер** — один список, по странице на камеру, с честно названными недоступными (М12 урок 14). Тревога уходит с камеры сразу: карта будит агента. О погасшей камере отвечает её последний отчёт, а её молчание само становится тревогой; приёмник, которого камера опрашивает, — свидетель, живая ли она. Неделю истории хранит держатель домена. Копий тревог на соседних камерах нет: они копировали только закрытые корзины и последнюю тревогу не спасали (убраны 29 сентября).

**Записи** — только SD-карты, каждая камера — свой том. **Retention** не нужен как служба: каждая камера чистит только своё дерево — у каталога один писатель.

**Автоматизация между камерами** — как в варианте с серверами (раздел «Сценарии между камерами»), с оговоркой про держателя домена там же.

## Что появляется только без серверов и NAS

1. **Состав системы.** Кто в неё входит, решает **вступление в домен** (М12 урок 6), и решение записано в список членов `domain/members` на держателе. Находить кандидатов — WS-Discovery / mDNS в своём сегменте; между подсетями — список начальных адресов.
2. **Ключ подписывающего.** LDevID камер, взаимный TLS между ними и подпись общего документа — всё от ключа подписывающего домена. Его **нельзя держать только на держателе**: с его смертью домен нельзя будет ни восстановить, ни расширять. Резервная копия ключа лежит за пределами держателя — файлом восстановления у оператора или зашифрованной на нескольких камерах (М12, «Два куска состояния»). Проблемы прав на NAS нет вовсе: каждая камера пишет только себя.
   **Обратная сторона — кража.** Сейчас оба ключа (корень CA и ключ токенов) лежат на флеше держателя открытым текстом. Унесённая камера — это корень доверия домена у вора: сертификаты и токены с любыми ролями, а в сети площадки — и захват домена записью с большим сроком. Перенос по файлу восстановления не помогает: в нём те же ключи. Процедура «держатель украден», критерии монтажника (в помещении, на бесперебойном питании, хранители копии на другом коммутаторе, заранее названный преемник) — М12 урок 15, шаг 8. Закрывает дыру разделение корня и рабочего ключа — следующее изменение курса.
3. **Время.** Слияние событий и таймлайнов требует синхронных часов. Источник NTP — держатель домена или внешний, если есть.
4. **Предел масштаба.** Проверенный замером — сотни камер (М12 урок 11): проход домена по отчётам — 1,1 с на трёхстах, цена — записи у держателя домена. Они ложатся на его SD-карту, а не на флеш: около 470 МБ в сутки на трёхстах камерах против 43 ГБ собственного видео, так что износ не главное. **Проверить в продукте:** около 27 мелких записей в секунду поверх записи видео — не мешают ли они записи на той карте, что ставят в камеры. Дальше — сервер или ретрансляторы со сводным отчётом, и это уже другой вариант развёртывания.

## Переход между сценариями

Система растёт: сначала десять камер без серверов, потом заказчик ставит сервер. Или наоборот, сервер выводят. Переход — это перенос домена, и делается он той же механикой, что смена держателя; строки камер не трогает вовсе.

**Только камеры → с серверами.**
1. Серверы разворачиваются как новый кластер и вступают в домен (М12 урок 6).
2. Домен плановой передачей переносится с камеры на серверный кластер (М12 урок 15): срок `term+1`, последняя копия — прямо на нового держателя. Ключ подписывающего переезжает вместе с доменом, поэтому перевыпускать сертификаты камер не нужно.
3. Агенты камер видят больший срок и дальше следуют за новым держателем. Ни одна камера ничего не переписывает.
4. Если оператор хочет, чтобы серверы писали камеры, домен назначает камерам кластер записи, и регистраторы находят их через книгу источников (урок 13).

**С серверами → только камеры.** Обратно: домен плановой передачей переносится на назначенную камеру, серверный кластер выходит из домена. Записи, которые жили только на серверах, остаются на серверах; это решение оператора, а не платформы.

## Чего не хватает в платформе

Исходный список из девяти пунктов строился на переносе строки камеры на серверы. На домене М12 он сжался; ниже — что осталось и где это сделано.

Что **отпало**:

- ~~ACL на юнит~~ — токен камеры действует только в её кластере из одного, в чужие хранилища она не пишет;
- ~~маршрутизирующее `Variables`~~ — строку всегда пишет камера;
- ~~поток изменений для строк~~ — строка не течёт вниз;
- ~~федеративный `ObjectStore`~~ — картину собирают каталог и вид для чтения М12 по отчётам камер;
- ~~туннель к камере~~ — медиа камера толкает сама, управление — проход агента и долгий опрос;
- ~~Raft~~ — как и было: только если заказчику нужна автоматическая смена держателя домена.

Что **осталось** — вторая часть М12, всё написано:

1. **Правка выключенной камеры** — М12 урок 9, конец первой части: `domain/pending.py`, 9 тестов.
2. **Кластер из одного**: закреплённый юнит `place: device`, без оркестратора, эпоху камера берёт сама, доменный агент — её единственная связь вверх — урок 10: `domain/device.py`, 7 тестов. Новое по сути: флеш (heartbeat — в RAM) и порядок загрузки (ни двери, ни отчёта до первой публикации, иначе домен получит ложный полный ответ «камеры нет»). **Соединение открывает камера** — отчёт вверх, домен читает только своё хранилище, молчание по часам домена: `domain/uplink.py`, 9 тестов.
3. **Сотни мелких членов домена**: М12 заявлен до «низких сотен кластеров», это край; проверено замером — урок 11: `domain/scale.py`, 8 тестов. 300 камер, 30 выключены: когда домен читал камеры сам, проход шёл 82 с по очереди, 5 с в 16 дорожек, 1,4 с с отсрочкой для молчащих; по отчётам — 1,1 с, выключенная камера ничего не стоит, цена — три записи на камеру за отчёт.
4. **Общие настройки без базы**: политика по умолчанию, дерево папок, сценарии между камерами — опубликованы один раз, подписаны, донесены агентами — урок 12: `domain/shared.py`, 7 тестов. Значения по умолчанию разрешаются при чтении и в строки не пишутся.
5. **Поток из чужого кластера**: регистратор сервера пишет и дозаписывает камеру из её кластера, находя её через книгу источников, которую агент приносит в его кластер, — урок 13: `domain/crossing.py`, 8 тестов. Одну камеру пишет один кластер — решение домена; перенос записи в другой кластер переписывает решение, и книги следуют (кластер, которому нечего сказать, получает пустую книгу). Книга основных говорит карте камеры, пишет ли серверная её основную.
6. **Тревоги со всех камер**: один список, по странице на камеру; тревога уходит сразу; погасшая камера — из последнего отчёта, её молчание — тревога со свидетелем-приёмником; неделя истории у держателя домена — урок 14: `domain/alarms.py`, 7 тестов.
7. **Держатель домена на одном узле**: только камеры; срок; подписанная копия состояния домена у других членов; перенос домена как обычная операция, вместе с общим документом; старый держатель уступает и показывает, что было только у него; плановая передача с живого держателя (заморозка, последняя копия на новую камеру — видна в её отчёте, перенос) ничего не теряет, а если новая камера копию не взяла или замолчала — отменяется; держатель читает остальных по отчётам — урок 15: `domain/term.py`, 9 тестов.
8. **Камера, до которой никто не дотягивается**: один поток на приёмник кластера записи для записи и живого видео, ключ потока, долгий опрос (удержанный по-настоящему и разбуженный сроком желания), время съёмки по часам камеры, кольцо на камере, выгрузка карты ответом на заявку, приёмники кластера толкают поток соседу с отсечением до ключевого кадра — урок 16: `domain/ingest.py`; в уроке 26 тестов, из них 14 — сценарии (пункт 10).
9. **Цепочка «объект — ретранслятор — центр»**: передатчик ретранслятора, желание вниз и поток вверх, «звезда», ретранслятор как дорога к домену для камеры, которой виден только он (ретрансляция вниз, сводный отчёт вверх, свежесть — возрастом) — урок 17: `domain/chain.py`; в уроке 11 тестов, из них 5 — сценарии.
10. **Сценарии между камерами**:
    - запрос со сроком тем же долгим опросом;
    - книга запросов с токеном под сценарий и названным действием;
    - книга опроса для камер, которых никто не пишет, в том числе за ретранслятором;
    - проход домена по всем книгам в процессе подписывающего;
    - на камере — от события к запросу;
    - потолки, схлопывание, «потерян» после перезапуска приёмника;
    - между ретрансляторами — вверх через свой ретранслятор, передатчики по событию;
    - кого можно спросить: любую камеру-член; триггером может быть и камера серверного кластера без платформы.

    Урок 16, шаг 8, и урок 17, шаг 7: `domain/ingest.py` (`Asker`, `publish_asks`), `domain/scenario.py`, `domain/books.py`, `domain/chain.py` (`lift`, `serve`). Тестов 19: 14 в уроке 16 и 5 в уроке 17.
11. **Видимость и топология**: что кластер видит — сообщает он сам (`domain/reaches`; его читают размещение и выбор «забор или толкание»); топология — одна запись оператора (`domain/topology`), консоль правит её по HTTP; камера за ретранслятором читается по живой и более новой из двух дорог; свежесть за ретранслятором — возраст по часам ретранслятора; регистратор, который не смог забрать камеру, переводит её на толкание — урок 17, шаг 8, и урок 16: `domain/topology.py`, `domain/federation.py`, `domain/uplink.py` (`NewerRoad`), `domain/chain.py` (`say_seen`), `domain/crossing.py` (`_road`), 11 тестов (`test_topology.py`).
12. **Список членов домена**: вступление пишет, уход убирает, каждый проход следует записи; первая запись переносит конфигурацию; держатель домена не принимается и не выводится; кто стучится — назван, администратор принимает; уход из консоли — только администратору — уроки 6 и 10: `domain/members.py`, 7 тестов (`test_members.py`).
13. **Два сервера — два кластера из одного**: резерв на втором сервере находится сам; книги на обе стороны; один поток — на резерв, только когда основная не берёт, по слову её приёмника; резервы пишут по слову потока, без домена; холодный резерв для камер, которые сервер забирает сам; возврат дыры с резерва и с карты; живое видео на той дороге, где поток — урок 1 М11, урок 16 М12, шаг 9, урок 26 М10B: `domain/crossing.py`, `domain/ingest.py`, 9 тестов (`test_two_servers.py`); в `vmsserver` — вид тома `edge`, резерв по `ref:`, `stream_says`, `note_source_unreachable` (`tests/test_backup_archive.py`).
14. **Что камера поднимает и умеет**: держатель описывает устройство в `vms/devices/<устройство>` и в heartbeat (`can`). Сценарий проверяется по этому описанию при записи — и в кластере (урок 25 М10B, `Catalog`), и между камерами (урок 16, шаг 8, `scenario.refusals`): вид события, которого триггер не поднимает, пресет или реле, которых у цели нет, — отказ с подсказкой. Камера, которая ещё не сказала о себе, называется на каждом проходе (`unchecked`), переставшая подходить — тоже (`unfit`, `refused`). Цель отвергает запрос той же функцией. Форма строится из каталога: `GET /auto/catalog` в кластере, `GET /api/catalog` у домена.

**Основы, которых в продукте ещё нет, — и временные замены на их месте**

- **Пользователи и права (урок 4 М12).** Их нет, поэтому правка топологии и списка членов открыта (AM, AN) — договорились, что до появления пользователей это допустимо; потом — право `admin` держателя домена.
- **Регистратор и вступление с доказательством владения (урок 6).** Членов в список добавляет оператор через дверь домена или кнопкой «Принять» у стучащегося (AN). Удостоверение у двери домена (Z, пункт 7 записки о связи) ждёт того же урока.
- **Общий подписанный документ (урок 12).** Сценарии между камерами пока хранит домен в `domain/scenarios`, а ключ запроса — общий секрет, а не токен подписывающего с `ask`/`by`/`acts` (AK, AL, AQ). Со вторым меняется и первое: право спросить станет токеном, выданным под сценарий из документа.
- **Домен на камере — вариант «только камеры» (урок 15).** Не начинался (AQ).

**Сценарии и автоматизация**

- **Реле (`output`) на цели.** Исполнитель выполняет пресет, а выход отвергает: для `IIODevice` в шиме нет обработчика (AQ).
- **Что камера поднимает и умеет — новое в курсе, 28 сентября** (пункт 14 выше; урок 25 М10B, шаг 4а; урок 16, шаг 8):
  - держатель пишет описание устройства в `vms/devices/<устройство>`, только при изменении; в heartbeat — `can` у камеры; в токен воркера — `vms/devices/*`;
  - сценарий в кластере и между камерами проверяется по нему при записи: 409 с подсказкой;
  - `unchecked` и `unfit` — на каждом проходе;
  - цель отвергает запрос той же функцией;
  - форма страницы строится из каталога (`/auto/catalog`, `/api/catalog`).

  Для продукта это продолжение AQ: шим уже умеет телеметрию, а описание — `IDevice` и части `.rep` (`ioDevice`: `rayCount`, `relayCount`; `telemetry`), то есть то, что держатель и так узнаёт, открывая устройство. Форма сценариев на странице домена сейчас строится из свободного ввода.

**Поток камеры**

- **Несколько приёмников одного кластера (AG, AJ)** сделаны и покрыты тестами, но на ящике не проверены: там у кластера один приёмник.

**Тревоги**

- **Зеркала тревог у соседних камер курс убрал (29 сентября).** Копировались только закрытые корзины, поэтому последнюю тревогу перед гибелью камеры они не спасали; работали только между камерами с открытыми дверями в одной сети; стоили плана, книги `domain/mirrors` и флеша соседей. Взамен в уроке 14 четыре вещи, которые стоит перенести:
  - **тревога уходит сразу**: карта будит агента (`Card.on_alarm` → `DomainAgent.wake`), срочный отчёт — не чаще раза в секунду;
  - **о погасшей камере — её последний отчёт** (это уже было по AR);
  - **молчание — тревога**, строка класса `alarm` в списке, и **свидетель — приёмник**: он публикует, когда каждая камера его последний раз опрашивала (`rec/polled`), и домен различает `silent` (камеры нет) и `not_reporting` (жива, но не отчитывается);
  - **неделя истории у держателя домена** (`AlarmHistory`): страница — только сутки, а карта может умереть.
  Продукт зеркала уже перенёс (AR). Их можно выключить и не развивать; четыре пункта выше закрывают то, ради чего они были, и шире — для всех камер, включая камеры за NAT.

**Чужие камеры**

- **Карта чужой камеры — источник дозаписи, сделано (AU).** Осталось два пункта:
  - **Время карты.** Драйвер Virtual читает время из имени папки как местное. Курс просит, чтобы держатель переводил метки карты в UTC до двери и говорил смещение в статусе камеры, а дозапись с карты, чьё смещение неизвестно, не шла. Иначе отрезок молча встанет на часовой пояс не туда.
  - **Камера другого кластера (`ref:`).** Домен не кладёт её карту в книгу пишущего кластера. Для площадки, где такую камеру держит и пишет один серверный кластер, это не нужно.

Вне темы камер: патч движка хранилища не собран (Y) — на macOS нет среды сборки: нужны Boost ≤ 1.86, utfcpp и NGP SDK, их загрузка ждёт разрешения. Движок хранилища открывает тома по одному, и брошенное открытие задерживает следующий том (T, AQ).

## Как это ложится на то, что уже есть

Почти ничего здесь не новое — старое под другими именами:

| Здесь | В платформе |
|---|---|
| камера | кластер из одного: воркер с закреплённым юнитом и без контроллера |
| вступление в домен | регистрация М12: доказательство владения, LDevID от подписывающего |
| строка камеры | строка кластера, у неё один писатель — консоль этого кластера |
| правка из консоли домена | сохранённая правка (урок 9): агент уносит, камера применяет, исход — в отчёте |
| отчёт камеры | копия члена у держателя домена (`member_copy`), читается как хранилище самого члена |
| список членов домена | запись у держателя домена, которую пишет регистратор и читает каждый проход, — как книги |
| топология | одна запись по CAS с проверкой при записи — как общие настройки, только без подписи и не уносится камерам |
| что камера видит | публикуемое (`domain/reaches`), уходит в отчёте, как heartbeat |
| поток камеры | приёмник кластера записи — раздача, переехавшая с воркера (М10B урок 9) в кластер |
| камера за ретранслятором | ретрансляция вниз и сводный отчёт вверх — агент ретранслятора, как агент любого кластера |
| книги домена | строка домена под `domain/<вид>/<член>`, которую агент уносит домой, — как права с урока 4 |
| запрос другой камеры | заявка со сроком (`valid_until`, М10B урок 25), доставленная долгим опросом приёмника |
| запись на SD и закрытие дыр | резервный архив (`edge` на карте, `backup` на другом сервере; обобщение архива устройства М10B урока 15) и дозапись из него (урок 16) |
| два сервера без свидетеля | два кластера из одного: основная на одном, `backup` на другом, `edge` на карте, один поток (М11 урок 1) |
| главная камера | держатель домена, размещённый на камере |
| номер срока | его эпоха |
| общий документ | публикация-и-указатель, как набор идентичностей у подписывающего; объект за указателем по CAS |
| «наибольший целый документ» | `(term, rev)` и подпись, никогда назад |
| события со всех камер | `MergedIndex` как есть |
| молчание камеры | тревога, как потеря связи с объектом у пульта охраны |
| «одно семейство — один писатель» | ACL, как с урока 1 |

Новое по существу — немного, и всё про размер и характер членов домена, а не про механизмы. Камера — член домена, который часто выключен, мал, пишет на флеш, может сам оказаться держателем домена и может быть недостижим вовсе; отсюда порядок загрузки, RAM для heartbeat'а, правка, которая ждёт, запрос, который не ждёт, замер на сотнях членов, перенос домена как обычная операция и соединения, которые всегда открывает камера.
