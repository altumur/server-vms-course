# Камеры на нашей платформе: где живут Variables — с серверами и без

Мы — вендор: делаем камеры и софт для онпрем-инсталляций, и код в камере — та же платформа, что на серверах. Два сценария: **с серверами** — камеры и кластер серверов в одном домене — и крайний случай, **только камеры**: ни одного сервера, ни NAS, записи на SD-картах. В обоих каждая камера — отдельный кластер из одного и свою строку пишет всегда сама; сценарии отличаются тем, где размещён домен и кто пишет запись. Отдельно — камера сама по себе, вне домена, и переход из одного сценария в другой.

Ссылки вида `vmsworker/w2cplatform/contract.go` — на продукт (`vmssubsystem/vmsworker`), проверены против рабочей копии на 25 сентября 2026; если код с тех пор уехал, верьте коду. Записка начиналась как проектирование; что из неё сделано и где — в разделе «Что решено» и в ссылках на уроки по ходу текста: камеры как члены домена — М12, уроки 9–17; резервный архив и дозапись из него — в продукте и в курсе (М10B, уроки 16 и 26).

## Что решено (26–27 сентября 2026)

Записку сверили с курсом, и бо́льшая часть её механизмов оказалась **доменом М12 под другими именами**. Решили строить на М12: камеры — отдельные кластеры, серверы — ещё один кластер, домен объединяет их в одну систему. Это вторая часть М12, уроки 10–17 (все написаны, с кодом и тестами; решения — в [`М12_DomainVMS/module-design.md`](М12_DomainVMS/module-design.md), раздел «Вторая часть»). Урок 9 про правку выключенной камеры закрывает первую часть: он нужен любому домену, где кластеры часто недоступны, — например, филиалам на слабой связи.

| Решение | Что выбрано | Почему |
|---|---|---|
| Что такое камера | **Отдельный кластер — кластер из одного** | У набора камер нет того, что делает кластер кластером в М11: ни raft, ни оркестратора, ни юнита, который может переехать на другую камеру. Если все камеры считать одним кластером, им понадобится одно согласованное хранилище, то есть Raft между камерами, от которого записка отказывается. Если каждую камеру считать своим кластером, её хранилище согласовано бесплатно (флеш, один писатель), а правило М12 «ни один raft не охватывает кластеры» — это и есть «без консенсуса» из записки. |
| Что их объединяет | **Домен М12** | Вступление — М12 урок 6. Одна консоль, правящая любую камеру, — пересылка правки кластеру-владельцу из урока 3. Недоступная камера — неполный ответ урока 1. Доверие без связи — урок 7. «Домен может пропасть, и камеры не заметят» — тезис М12, и это ровно «главная выключена, запись идёт» из этой записки. |
| Кто пишет строку камеры | **Сама камера, всегда** | Первый вариант записки переносил строку на серверный кластер при привязке (режим adopted), и для этого требовались маршрутизирующее хранилище, поток изменений и запись камеры в хранилище серверов. От него отказались: если владелец не меняется, ничего из этого не нужно. |
| Номер камеры | **Локальный id остаётся целым, серийник — в `ref`** | Домен М12 уже отвечает по `ref`. Сделать серийник id значит пройтись по всем целым номерам камер ниже — в индексе событий `cam INTEGER` — без выгоды. |
| Строка устройства | **`vms/devices/<устройство>` — по устройству, не по id камеры** | В курсе «устройство» уже значит прибор за каналами (`device_of`, `group_by: device`): регистратор на 16 каналов — одно устройство и 16 строк камер. Если ключевать по камере, сведения о регистраторе повторятся 16 раз. |
| Главная камера | **Доменный кластер, размещённый на камере** | В М12 уже есть один назначенный кластер со всеми доменными службами, и при его падении переносить их некуда. На камере это доменный кластер из одного узла: перенос домена становится обычной операцией, а старый хост, который вернулся, — обычным событием. Для этого нужен **срок** (урок 15). |
| Кто открывает соединение | **Камера, всегда** (урок 10, шаг 7) | Камера может быть никогда недоступна домену — NAT, изолированный сегмент, сотовый канал, — а домен иногда доступен камере. Её агент на своём проходе уносит строки домой и оставляет **отчёт** в хранилище доменного кластера; домен читает только своё хранилище. Молчание камеры — возраст её отчёта по часам домена. |
| Поток камеры, до которой не дотягивается и серверная | **Камера толкает один поток на приёмник кластера записи — и для записи, и для живого видео** (урок 16) | Раздача переезжает с камеры в кластер записи. Куда и по какому праву — книга основных и ключ потока от подписывающего домена; когда — по долгому опросу; диапазон с карты — ответ на заявку. Туннель не нужен. |
| Объекты, офисы и центр | **Каждый уровень звонит на уровень выше и достижим только снизу** (урок 17) | Камера, которой виден только её офис, ходит к домену через офис в обе стороны: офис ретранслирует ей вниз всё, что оставил домен, и несёт наверх её отчёт в сводном объекте. Медиа — урок 16 на каждом переходе. Для облака и мобильных операторов — «звезда». |
| Сценарии между камерами | **Запрос со сроком — через долгий опрос цели** (урок 16, шаг 8; урок 17, шаг 7) | Правка ждёт выключенную камеру, а запрос «сейчас» ждать не должен. Через агента он шёл бы полминуты. Приёмник, который цель уже опрашивает, будит её за секунду. Право — токен, выданный под сценарий, с названным действием. |
| Правка выключенной камеры | **Сохраняется по полям и применяется, когда камера вернётся** (урок 9, написан) | `503` честен, но для члена домена, который часто недоступен — филиал на слабой связи или камера, — бесполезен. Правка лежит рядом с правами (`domain/pending/<кластер>`), агент камеры забирает её домой, консоль камеры применяет её от имени оператора и проверяет права в момент применения. По каждому полю: применено / уже на месте / конфликт. Результат сверяется по номеру версии, а не по часам. Владелец не меняется. |

**Что отпадает.** ACL на юнит: токен камеры действует только в её собственном кластере, и в чужие хранилища она ничего не пишет. Перенос строки на серверы, маршрутизирующее `Variables`, поток изменений для строк. Федеративное хранилище объектов как отдельная сущность: его роль играет каталог и вид для чтения М12 по отчётам камер. Туннель к камере: медиа камера толкает сама, а управление ходит проходом агента и долгим опросом.

**Что осталось новым** — уроки 10–17: кластер из одного; домен на сотнях мелких членов (край заявленного предела М12, проверен замером); общие настройки без базы у домена; регистратор сервера, пишущий камеру из чужого кластера; тревоги со всех камер одним списком и их зеркала у соседей; доменный кластер из одного узла со сроком; камера, до которой не дотягивается никто, толкает поток сама; цепочка «объект — офис — центр»; сценарии между камерами за секунду — и внутри офиса, и между офисами.

## Что это такое в трёх абзацах

В камере vmsworker работает **на месте**: видео берёт не через DriverPack, а прямо с сенсора, и переехать никуда не может. Оркестратор решает вопрос «на каком сервере работает юнит» — в камере на него ответило железо, поэтому оркестратор ей не нужен. Variables нужны для другого: хранить своё, получать общее сверху и отдавать своё состояние тем, кто спросит.

У платформы уже есть свойство, которое делает это дешёвым: **у каждого семейства ключей ровно один писатель** по ACL. Значит, копии можно сводить односторонним копированием — без консенсуса и без конфликтов. Консенсус понадобился бы только ключу с двумя писателями, а платформа их не допускает.

Ключи раскладываются на три кучки. **Своё** камеры — её строка, устройство, эпоха, события — живёт в ней самой и только в ней; строку пишет её собственная консоль, а правка из консоли домена пересылается камере. **Общее** — настройки по умолчанию, дерево папок, сценарии между камерами — публикует домен одним подписанным объектом, и агент приносит копию в каждую камеру; два хоста домена сразу разводит номер срока — так же, как эпоха разводит два экземпляра воркера. **Публикуемое** — heartbeat, срез snapshot, страницы тревог — агент камеры кладёт в отчёт домену, а записи и события остаются у неё; домен к камере не ходит. Всё, что домен хочет сказать камере, он кладёт в свои **книги**, а агент камеры уносит их домой. Где пишут камеру, куда толкать поток, кого она может спросить — это книги. Сценарий между камерами — запрос со сроком. Он доходит тем же долгим опросом, которым камере говорят толкать поток. Два варианта развёртывания отличаются только тем, где размещён домен: на серверах или на одной из камер.

## Три кучки ключей

| | Примеры | Писатель | Где живёт |
|---|---|---|---|
| **своё** камеры | её строка `vms/cameras/<id>` (`ref` — серийник), `vms/devices/<устройство>`, `vms/epoch/<id>`, `vms/requests/*` к ней, события | строку — консоль камеры, в том числе по пересланной правке из консоли домена; остальное — сама камера | в камере, и только в ней |
| **общее** на систему | настройки по умолчанию (retention и пр.), дерево папок, сценарии между камерами | домен: подписывающий публикует документ, доменный кластер держит указатель | объект за указателем в доменном кластере; подписанная копия в каждой камере, на карте (М12 урок 12) |
| **доверие** | ключи подписывающего, список отзыва, права на эту камеру (`domain/keys`, `domain/grants`); книги домена — основных, опроса, запросов (`domain/primaries`, `domain/poll`, `domain/asks`) | домен; в камеру пишет только её агент | в камере, под `domain/*` (М12 уроки 4, 13, 16) |
| **публикуемое** | heartbeat, срез snapshot, `rec/<cam>/…`, корзины событий | своя камера | в своей камере (heartbeat и срез — в RAM); heartbeat, срез и страницы тревог уходят домену в отчёте агента |

Пользователи в камеру не попадают вовсе: они у подписывающего домена, а камера держит только его публичный ключ, отзыв и права, — так же, как любой кластер М12.

У камеры два имени. **`ref` — её серийный номер**: по нему её знает домен, он выдан на заводе и остаётся, если камеру вывели из домена и ввели снова. **Локальный id** в её кластере из одного — целый, как в любом кластере; `next_id` для него не нужен, строка одна.

**Строка камеры делится на две**, потому что у неё два писателя и внутри одной камеры. `vms/cameras/<id>` — то, что решает оператор: имя, папки, метки, включена ли, retention, live; пишет консоль. `vms/devices/<устройство>` — то, что знает только устройство: модель, прошивка, возможности сенсора, адрес; пишет воркер. Пока это одна строка, у неё два писателя; разделённые — каждая с одним писателем, как везде в платформе.

## Своё: камера — кластер из одного

Каждая камера работает так, как сегодня работает `vmsdev` на одной коробке, минус контроллер (М12 урок 10):

- **Строка.** Её создаёт собственная консоль камеры при первой загрузке, с `ref: <серийник>`.
- **Закреплённый юнит.** В спеке — `place: device`: юнит и есть устройство. Размещать его некому и незачем: слотов и аренд нет, назначение неизменно, ключей, которые писал бы размещающий, просто нет. Контроллер в камере не работает.
- **Эпоху** воркер берёт сам — он её единственный писатель — и пишет на флеш раз за загрузку. Она нужна не для переезда, а для путей архива `rec/<cam>/e<epoch>/` и для отсечения событий по эпохам: после перезагрузки, в том числе аварийной, номер должен вырасти.
- **Хранилище** — обычный `FileVariables`: интерфейс `Get/Put/List/Delete` с CAS (`w2cplatform/variables.go:80`), код воркера не меняется.
- **Флеш.** Heartbeat и срез snapshot живут в RAM и отдаются по запросу, а не пишутся на флеш; аренд у камеры нет. На флеш уходят только конфигурация, эпоха и то, что приносит агент, — единицы записей в сутки.
- **Отчёт — после первой публикации.** Камера, отчитавшаяся раньше, сказала бы «камер нет» — а это *полный* ответ, которому домен обязан поверить. Поэтому до первой публикации она не отчитывается вовсе, и домен говорит «ещё ни разу не отчитывался». То же правило держит и её дверь для площадки.
- **Связь вверх** — агент домена, как в любом кластере: уносит `domain/*` домой и оставляет отчёт в доменном кластере под `domain/members/<камера>/` — heartbeat и срез, исходы правок, копию указателя общих настроек, запись о хосте, эпоху, страницы тревог. Переписывается только изменившееся.
- **Правку, пришедшую от домена, применяет агент камеры у себя** — не через её дверь: у камеры, до которой никто не дотягивается, двери для чужих нет.

### Хранилище камеры — без маршрутизации

Раз строку всегда пишет камера, её хранилище — обычное хранилище кластера из одного. Куда идёт каждый ключ:

| Ключ | Get | Put |
|---|---|---|
| своё, пишет воркер камеры | локальный файл | локальный файл |
| своя строка | локальный файл | локальный файл — консоль камеры, в том числе по пересланной правке |
| общее и доверие | локальная копия, принесённая агентом | только агент; правка общего — в консоль домена |
| heartbeat, срез snapshot | RAM | RAM |

## Камера одна и камера в домене

**Одна** — камера из коробки: её веб-страница и есть консоль, строку пишет она. Общего нет, точнее, оно тоже своё: политика и пользователи одной камеры.

**В домене** — камера вступила в домен (М12 урок 6). Строку по-прежнему пишет она сама; меняется только то, откуда приходят общее и доверие: их приносит агент домена. Домен знает её по её отчётам, как любого своего члена, и отвечает по её `ref`.

### Вступление в домен

1. **Заявка.** Оператор в консоли домена выбирает найденную камеру (WS-Discovery / mDNS) или вводит серийник. Камера должна доказать, что она физически у этого заказчика: одноразовый код с наклейки или QR, либо пароль администратора камеры; с ваучером производителя — без участия человека. Без доказательства в домен можно было бы ввести чужую камеру из той же сети.
2. **Выдача.** Подписывающий домена выдаёт камере LDevID на её серийник. Токенов на чужие ключи камера не получает: писать ей есть куда только в собственном кластере.
3. **Строка никуда не едет.** Домен добавляет камеру как ещё один кластер и читает её по отчётам, которые оставляет её агент; её строка остаётся её строкой.
4. **Агент.** Агент камеры начинает приносить `domain/*`: ключи подписывающего, отзыв, права, общие настройки, сохранённые правки.

### Правка

На странице камеры оператор правит её строку сам, в любой момент, — это консоль её кластера. Из консоли домена правка для камеры **сохраняется** по полям (урок 9): агент уносит её на следующем проходе, камера применяет от имени оператора с проверкой права, и исход уходит вверх в отчёте того же прохода. Ответ оператору — «принято, применится, когда камера выйдет на связь». Мгновенной пересылки в дверь камеры нет — домен к камере не ходит. Настройки самого устройства — адрес, NTP, параметры сенсора — лежат в `vms/devices/<устройство>` или в собственных ключах камеры и правятся на ней.

### Выход из домена

- **Плановый.** Домен забывает кластер и отзывает LDevID. Переносить нечего: строка у камеры и так своя, общие настройки остаются на карте последней копией.
- **Домена больше нет.** Камера продолжает работать по своей строке и последним общим настройкам; сброс к заводским — по желанию оператора, с паролем администратора.
- **Чужой домен.** Пока камера в домене A, заявка домена B отклоняется. Сначала выход или сброс.

## Сценарий с серверами

Серверы — ещё один кластер того же домена, обычная платформа с оркестратором; доменный кластер, как правило, на них. Камеры в кластер серверов не входят: каждая — свой кластер, и контроллер серверов о них не знает — их строк в его хранилище нет.

### Что остаётся оркестратору

Всё, что может переезжать:

- **Регистраторы.** Регистратор сервера пишет камеру из чужого кластера: находит её не в heartbeat'ах своего кластера, а в **книге источников** — `domain/sources/<кластер>`, которую домен публикует для кластера записи, а агент кластера приносит домой (М12 урок 13). Одну камеру пишет один кластер — это решение домена, хранится как размещение. Запись продолжается и при выключенном домене: регистратор разрешает `ref:` по копии книги в своём кластере.
- **Live-шлюзы и автоматизация** — без изменений.
- **Контроллер** серверов размещает регистраторы и остальное своё, как всегда; камер он не размещает и срезов snapshot за них не пишет — каждая камера публикует свой.

### Что ходит между камерой и доменом

| Направление | Что | Кто пишет | Как доходит |
|---|---|---|---|
| вниз | `domain/keys`, отзыв, `domain/grants`, общие настройки, `domain/pending`; книги: основных (кто пишет камеру и куда толкать), опроса, запросов | домен; книги строит один проход домена в процессе подписывающего, потому что в них его токены | агент камеры забирает сам |
| вверх | отчёт: heartbeat и срез snapshot, исходы правок, копия указателя общих настроек, запись о хосте, эпоха, страницы тревог | агент камеры, под `domain/members/<камера>/` | агент кладёт в хранилище доменного кластера тем же проходом |
| на месте | события, записи на SD | камера | читаются у источника теми, кто на площадке до камеры достаёт; домен видит тревоги по страницам в отчёте, записи с карты приходят выгрузкой по заявке (урок 16) |

У каждого ключа один писатель, поэтому никакого слияния нет: агент применяет документ с большим `(term, rev)`, подпись которого сходится с ключами, которые у камеры уже есть.

**Соединение открывает камера, всегда** (М12, урок 10, шаг 7). Камера может быть никогда недоступна домену — NAT, изолированный сегмент, сотовый канал, — а домен иногда доступен камере. Поэтому домен не ходит к камерам вовсе: он читает только хранилище своего кластера, куда агент каждой камеры оставляет отчёт. Молчание камеры — возраст её последнего отчёта по часам домена; время внутри отчёта домен переводит на свои часы. Правка из консоли домена для такой камеры всегда сохраняется и уходит домой с агентом (урок 9). Дверь камеры остаётся для площадки: регистратор серверной, соседи с зеркалами тревог.

### Камера, до которой не дотягивается и серверная

Всё выше предполагает, что регистратор серверной достаёт до камеры: тянет её поток и читает её карту. Если нет — камера за NAT, серверная в другом здании, облачный кластер записи, — поток открывает камера (М12, урок 16). Она толкает **один поток** на приёмник кластера записи — и для записи, и для живого видео; адрес приёмника и ключ потока (токен подписывающего домена) приходят в книге основных. Туннель не нужен, страница камеры остаётся для оператора на площадке.

**Приёмник** — процесс на каждом сервере кластера записи со стабильным адресом (`rec/ingest`). Он принимает поток камеры и раздаёт его внутри кластера регистратору и шлюзу. Он держит долгий опрос камеры и отвечает на него, как только меняется ответ. Он проверяет токены по ключам, которые уже лежат в его кластере. Все три канала камеры открывает сама камера:

| Канал | Куда | Что несёт | Скорость |
|---|---|---|---|
| проход агента | в кластер домена (или в свой офис) | вниз — книги, права, правки; вверх — отчёт | полминуты |
| долгий опрос | в приёмник | «толкай поток», «выгрузи диапазон с карты», запросы других камер | около секунды |
| поток | в приёмник | живое видео, запись, выгрузки с карты | непрерывно |


- **Когда толкать.** Пока поток нужен: регистратору с постоянной записью — всегда, записи по событию — на окно, зрителю — пока смотрит и ещё 10 секунд. Узнаёт по долгому опросу к приёмнику: первый опрос отвечается сразу, удержанный будит уход зрителя.
- **Время кадра — съёмки, по часам камеры.** Приёмник переводит его на часы кластера по разнице, которую камера называет в каждом запросе, а заявку на диапазон — обратно. Иначе шов записи с дозаписью разошёлся бы на расхождение часов.
- **Кольцо предзаписи — на камере.** Пока поток не нужен, камера держит последние секунды; первая отправка после «толкай» начинается с них — начало события не теряется. Регистратор получает кольцо, зритель — живой край.
- **Карта — по заявке.** Дозапись и просмотр карты — выгрузка диапазона ответом на заявку по её номеру, кадрами со своими временами: регистратор просит минуту и получает эту минуту. Просмотр карты перестаёт быть мгновенным.
- **Несколько приёмников кластера** передают поток друг другу: камера толкает на любой, а запись может держать регистратор другого сервера. Приёмник, к которому толкает камера, толкает дальше соседу с подписчиком; сосед отстал — хвост режется целиком до ключевого кадра, а не теряется кадрами посреди GOP.
- **Опрос держит каждая камера-член**, дверь у неё открыта или нет, и говорит об этом в heartbeat'е (`polls`). Камеру, которую серверная пишет, забирая поток сама, толкать не просят: регистратор на приёмнике не подписывается. Зато её можно спросить (раздел «Сценарии между камерами»).
- **Камера, которую никто не пишет**, — например поворотная, которую держат только для живого просмотра, — всё равно опрашивает приёмник: адрес ей даёт **книга опроса**, отдельная от книги основных. Толкать ей не велят, пока никто не смотрит, а запросы других камер она получает. Отдельная книга нужна потому, что книгу основных читает резервная запись на карте, и опрос без записи не должен выглядеть для неё основной записью.
- **Резервная на карте знает о своей основной** из книги основных: должна ли серверная писать камеру, пишет ли, и только ли запускается запись. Остановку карта подменяет сразу, запуск — через 20 секунд; книгу, которую агент давно не подтверждал, считает незнанием и пишет сама.

### Объекты, офисы и центр

Камеры на объектах, регистраторы в офисах, один мониторинговый центр, и все за NAT, кроме центра (М12, урок 17). Цена камер за офисом: лёг офис — они молчат вместе с ним, другой дороги нет. Правило одно: каждый уровень звонит на уровень выше и достижим только снизу. Кто дотягивается до центра, отчитывается домену напрямую. Камера, которой виден только её офис, ходит к домену через офис в обе стороны: офис ретранслирует ей вниз всё, что оставил домен, и несёт наверх её отчёт в сводном объекте; свежесть её книг — по последнему разговору офиса с доменом, и замолкает она вместе с офисом. Медиа — урок 16 на каждом переходе: камера толкает в офис, офис отдаёт в центр то, что центр хочет, и желание центра доходит до камеры. От камеры поток получает один кластер — её офис. Для облака и мобильных операторов, где до офиса не дозвониться, — «звезда»: камера толкает в центр, офис забирает свои потоки оттуда. Камера за офисом, которую никто не пишет, опрашивает приёмник своего офиса: центр и кластер домена ей недоступны. Центр доходит до неё через передатчик офиса — и запросом, и желанием зрителя. Сценарий между объектами двух офисов идёт вверх через свой офис (раздел «Сценарии между камерами»). Кто через кого ходит, где центр и какие офисы — «звезда», оператор задаёт одной записью домена `domain/topology`, и каждый проход читает её оттуда. Какие сети видит кластер или камера, они сообщают сами (`domain/reaches`), а не оператор в домене (урок 17, шаг 8).

### События не копируются, записи дозаписываются

> **В силе**, и уже есть в курсе: архив устройства и дозапись из края — М10B урок 16; запись на карте нашей камеры как резервный архив и копирование из неё сэмплами, а не перезаписью, — М10B урок 26. Новое одно: регистратор сервера находит камеру через каталог домена, а не в heartbeat'ах своего кластера — М12 урок 13.

Камера публикует heartbeat ресурса, и `MergedIndex` на серверах (`w2cplatform/eventdatabase.go:519`) находит её среди источников и забирает `GET <url>/events` прямо у неё — если серверная на той же площадке до неё достаёт. Недоступная камера честно видна как `unreachable`, а не как пустое окно; её тревоги доходят до домена страницами в её отчёте (М12 урок 14).

Живую запись ведёт регистратор на сервере, как сейчас: тянет RTSP с камеры и пишет в свой том ObjectStorage. Карта камеры — **резервный архив** этой записи: том вида `backup`, который пишет регистратор в самой камере. Закрытие дыр основной записи из него — **дозапись**, урок 16 М10B. Это сделано в продукте (26 сентября) и проверено на коробке; ниже — как. В курсе то же самое — урок 26 М10B: резервный том с сервером и без, `register_admit` и `register_near_rank` вместо `Admit` и `NearRank`, `when: offline` с 20 секундами на старт, кольцом предзаписи на 30 секунд и минутой перекрытия; и пункт 4 списка «Дозапись» ниже — шаг 9 урока 16. Отличия курса: происхождение — в строке манифеста, а не в имени потока (у файлового архива манифест есть), и имена по времени съёмки — только у конвейера с кольцом.

**Резервный архив — не про камеры.** Вид тома назван `backup`, а не по карте, потому что механизм одинаков для карты в камере и для диска другого сервера: критичная камера пишется в два архива, и основная запись закрывает из резервной любую дыру — обрыв связи с площадкой или те секунды, что её регистратор переезжает на другой сервер. С `server` резервный том — диск или карта одной машины, без `server` — адрес, который может обслужить любой ящик.

- **Место.** Резервный том принимает только записи, сделанные для него, и запись резервного тома никуда с него не уходит (`vms.GuardBackups` поверх общего шва `SpecController.Admit`). Для обычного тома `home` — предпочтение; для резервного — фильтр в обе стороны: основная запись, переложенная на резервный том, оставила бы одну копию там, где их должно быть две.
- **Воркер камеры — рядом с резервной записью.** `near: {sub: rec, of: cam}` при двух записях камеры выбирает резервную (`vms.PreferBackups` поверх `SpecController.NearRank`). Тогда сервер основной записи может упасть, не унося с собой поток: воркер и резервная запись на другом сервере его не замечают, а основная потом дозаписывает свой переезд из резервной.
- **Покрытие.** Регистратор резервной записи публикует в heartbeat сводку `coverage` (начало, конец, число фрагментов) и дверь `url` — то, что урок 15 кладёт в heartbeat держателя.

**Когда пишет резервная — `when` в строке записи.** `always`: каждую секунду, и основная закрывает из неё любую дыру. `offline`: только пока основная запись **включена, но никто её не пишет** — её регистратор молчит (связь потеряна, сервер лёг), не сообщает запись идущей или она никуда не размещена.

- **Сбой, а не решение.** Основная выключена, событие детектора закончилось (`until` прошёл), основной нет вовсе — резервная ждёт. Иначе запись по событиям превратилась бы в постоянную. Только что созданной или ещё не размещённой основной — так начинается каждая запись по событию — даётся 20 секунд на запуск.
- **Предзапись.** Пропажу основной замечают с опозданием — сторожевой таймер регистратора и heartbeat, 15–25 секунд. Поэтому конвейер резервной записи работает всегда, **на удержании**: `recworkersink` держит в памяти последние 30 секунд (`prebuffer-ms`, от ключевого кадра) и ничего не пишет. Пропажу заметили — удержание снимается, кольцо ложится в архив первым, дальше без шва идёт живой поток. На коробке запись резервного архива началась за 28,5 секунды до снятия удержания.
- **Метки по времени съёмки.** Чтобы кольцо легло своим временем, `recworkersink` ставит кадру метку по часам конвейера — когда кадр снят, а не когда дошёл (`timestamps=capture`, по умолчанию; привязка по приходу осталась запасной).
- **Перекрытие.** Основная вернулась — резервная пишет ещё минуту: архивы перекрываются, и дозапись находит шов с обеих сторон.

**Дозапись.** Регистратор основной записи сверяет своё покрытие с покрытием резервной; дыры — со склейкой швов, бюджет диапазонов, окно по местному времени, пауза при нехватке места, перекрытие с живой записью проверяется дважды (урок 16). Четыре отличия от урока, все из-за того, что том ObjectStorage — не каталог с манифестом:

1. **Своё покрытие** — таймлайн тома по всем потокам записи, а не манифест.
2. **Диапазон копируется сэмплами** из тома в том с исходными метками (`/samples` у двери регистратора → запись в уже открытый писатель тома), а не записывается заново через конвейер — быстрее реального времени и без разбора потока.
3. **Отдельный поток** `<rec>/e<n>/backfill`: дозапись в поток живой записи перемешала бы старые сэмплы с новыми, и движок резал бы последовательность на каждом переключении. Происхождение живёт в имени потока — в томе нет ни манифеста, ни починки по пути.
4. **Только дыры внутри записанного.** Плановая дозапись берёт дыры между первой и последней видимой секундой основной записи — до своей первой секунды запись не шла (создана позже или детектором для одного события), и заливать это из резервной значило бы превратить запись по событиям в постоянную. Верхняя граница — конец видимого покрытия: хвост идущей записи ещё не виден, и это не дыра. Закрепить любой интервал оператор может кнопкой «Закрепить» — заявкой через `rec/requests`, вне бюджета и окна.

Камера при этом ничего не знает о серверах: она пишет и показывает свой архив, а инициатива у того, кому не хватает — то же правило, что записано в `vms/space.go:119`: эвакуация толкает, дозапись тянет.

**Чужие камеры.** Для камеры с картой, но без нашей платформы, архив устройства читается через DriverPack — а у привязки к DriverPack в продукте нет вызовов хранилища и воспроизведения (`ipint_storage_*`, `ipint_playback_*` в `ipint.h` только зарезервированы). Когда они появятся, карта чужой камеры станет ещё одним источником дозаписи; остальное не изменится.

### Когда серверов не видно

Камеру это почти не касается: её строка — её, общие настройки лежат у неё на карте, реконсайлер работает от сохранённого желаемого состояния. Она пишет на SD, события лежат у неё, правка на её странице работает как всегда. Не работает то, что живёт на серверах: консоль домена, если домен на них, и основная запись. Когда связь вернулась, регистраторы дозаписывают пропуск из её резервного архива (урок 16), а правки, которые домен сохранил для неё, агент приносит домой.

### Отказы

| Отказ | Что происходит |
|---|---|
| упал один сервер | оркестратор переносит регистраторы, которые там были; камеру это не касается — она не в кластере серверов |
| недоступны все серверы | камера живёт как жила и пишет на SD; её строку можно править на её странице; консоль домена, если домен на серверах, недоступна |
| недоступна камера | домен показывает её `unreachable`, а не «камеры нет»; правка из консоли домена сохраняется и применяется при её возвращении (урок 9); запрос сценария к ней умирает в своём сроке |
| перезапустился приёмник | запросы, которые в нём лежали, пропадают: через срок плюс 5 с камера-триггер получает «потерян», а не ждёт вечно; поток камера снова толкает после ближайшего опроса |
| офис потерял центр | его камеры молчат для домена; запрос в чужой офис ждёт у своего офиса и умирает в сроке; сценарии внутри офиса работают — они центр не проходят |

## Сценарии между камерами

«Машина у ворот — камеру двора на пресет 3». Сценарий лежит в общем документе: `{"when": {"camera", "kind"}, "then": {"camera", "action", …, "within"}}`. Выполняет его камера, чьё событие его запускает. Действие на ней самой — её собственная автоматизация (М10B урок 25). Действие на другой камере — **запрос** к той камере (М12 урок 12). Узкое право `RequestsACL` (`w2cplatform/contract.go:119`) задумано ровно для этого.

**Срок, а не хранение.** В отличие от правки, запрос не ждёт выключенную цель: «пресет 3 сейчас» через час никому не нужен. Срок — свойство запроса: истёкшие выметает любое обращение к приёмнику, даже если цель не опросит больше никогда. Считается он от времени события, а не от момента, когда событие стало видно; сводка окна подавления сценарий не запускает. Срок задаёт `within`, по умолчанию 30 с — как `valid_until` заявки в продукте. Истёкший запрос умирает с исходом `expired`, а цель, вернувшись, его не получает.

**Дорога — долгий опрос цели.** Домен к камере не ходит, а проход агента занимает полминуты. Поэтому запрос кладётся туда, где цель уже держит открытый опрос, — на приёмник, и будит её за секунду (М12 урок 16, шаг 8):

| Цель | Где она опрашивает | Дорога запроса |
|---|---|---|
| её пишет кластер записи | приёмник этого кластера | прямо туда |
| её никто не пишет | книга опроса: приёмник центра или кластера домена | туда |
| за офисом, её никто не пишет | приёмник своего офиса | туда |
| в чужом офисе, а камере-триггеру виден только свой | приёмник чужого офиса | вверх через свой офис → центр → чужой офис (урок 17, шаг 7) |

**Кого можно спросить — любую камеру-член.** Опрос держит каждая камера-член, с открытой дверью или закрытой. Открытая дверь — дорога для площадки, а не для запроса: домен к члену не ходит ни с дверью, ни без. Типичная цель — поворотная в одной сети с сервером, который её пишет забором. Правило «только толкающие» оставило бы сценарии одним камерам за NAT. Спросить нельзя только не-члена: камеру серверного кластера без платформы или незнакомый серийник. Такой сценарий отвергается при записи с 409 и причиной, а если камера ушла потом — называется на каждом проходе книг.

**Право — книга запросов.** Для каждого сценария домен кладёт камере-триггеру дороги к цели. На каждой дороге токен: `ask: <цель>`, `by: <триггер>`, `acts: <действия сценария>`. Нет сценария — нет и токена. Другое действие приёмник отвергает раньше, чем цель о нём услышит. Ключ потока правом спросить не является, и наоборот. Убранный сценарий опустошает книгу, а уже унесённый токен доживает свои сутки или отзывается по `jti`.

**Кто что делает.** Книги строит один проход домена в процессе подписывающего: источники, основные, опрос, вышестоящие, запросы. По событию камера читает свою проверенную копию документа, находит свои сценарии и оставляет запросы. Цель получает запрос в ответе на опрос, выполняет и отвечает `performed` или `refused: <почему>`. Камера-триггер читает исход, заново перебирая дороги своей книги.

**Под нагрузкой.**
- **Потолок сценария** — `rate_per_minute`, по умолчанию 6, как в продукте. Счётчик живёт в памяти камеры.
- **Схлопывание.** Запрос, равный живому, приёмник схлопывает в тот же номер.
- **Потолок на камеру.** Одна камера держит на одном приёмнике не больше 16 живых запросов.
- **Память, а не журнал.** Запросы и исходы живут в памяти приёмника, исход хранится 15 минут. Двадцать срабатываний за минуту от листвы — шесть запросов, а пока цель между опросами, её ждёт один.

**Между офисами — по событию.** Путь: камера-триггер → свой офис → центр → чужой офис → цель. У своего офиса для этой пары есть собственный токен к центру; `by` в нём — исходная камера, `acts` те же. Каждый переход будит следующий:
- приёмник будит свой передатчик;
- опросы у центра действительно удерживаются и отвечаются при любом изменении;
- исход передатчик ждёт у центра так же.

Весь путь туда и обратно в курсе занял 21 мс при таймерах в секунду — это дорога от крючка на событии. Сценарий, читающий сводный журнал событий, как в продукте, прибавляет интервал хвоста журнала: на ящике от события до запроса 1–4 с, от запроса до заявки на цели 2 мс. По сети это четыре перехода в каждую сторону по уже открытым соединениям. Внутри офиса ничего не меняется: дорога прямая, и центр о запросе не слышит.

**Только камеры — у доменной камеры.** Без серверов книга опроса ведёт в кластер домена, то есть на камеру-хост. На ней работает лёгкий приёмник: только опросы и запросы, без потоков. Камеры забирают запросы у неё так же, как забирают у неё всё остальное. Если хост выключен, запросы между камерами стоят вместе с правкой общего и консолью домена, пока хост не вернут или домен не перенесут; своя автоматизация каждой камеры при этом работает. После переноса новый хост в первом же проходе строит книги со своим приёмником, и камеры переходят на него со следующим проходом агента. Запрос соседу прямо в его дверь сознательно не делаем: к камере снова звонили бы, и появилась бы вторая дорога со своими правами и отказами — только на то время, пока нет хоста. Тест урока 16 проходит это целиком: запрос через доменную камеру, её смерть, перенос домена на другую камеру и тот же сценарий через новый хост. По дороге он нашёл дыру в переносе домена: указатель на общий документ восстанавливался, а сам документ оставался в хранилище умершего хоста, и книга запросов опустела бы. Теперь новый хост берёт документ из копии члена по контрольной сумме указателя (урок 15, шаг 3).

## Сценарий «только камеры»: домен на одной из камер

Серверов нет, и домен размещён на камере, назначенной оператором, — это доменный кластер из одного узла (М12 урок 15). Его по привычке можно звать главной камерой, но это не особый режим: это те же доменные службы — подписывающий, каталог, вид для чтения, консоль домена, — только хост у них камера.

### Кто пишет общее

Общее пишет домен и только он. Правка общего со страницы любой камеры уходит в консоль домена на хосте; два оператора одновременно разводятся CAS по ревизии документа.

### Что он публикует

Всё общее целиком, одним документом, подписанным ключом подписывающего (М12 урок 12):

```
{ term, rev, …настройки…, kid, sig }
```

Документ — объект; в доменном кластере на него смотрит указатель-Variable, записанный по CAS после объекта. Объём — даже для 500 камер десятки килобайт, больше потолка Variable в 64 КиБ, поэтому объект. Копия у соседа — это данные, которым камера верит по подписи и своему набору ключей, а не по тому, от кого их получила.

### Как документ доходит до всех

1. **Агент забирает.** Агент каждой камеры сравнивает `(term, rev)` указателя со своей копией и, если отстал, забирает документ; назад — никогда: копию новее он не отдаёт за старую.
2. **Проверка.** Подпись проверяется по ключам, которые у камеры уже есть под `domain/keys`; не сходится — документ отвергнут, остаётся прежний.
3. **Хранение.** Документ ложится на карту, а не в RAM: настройки должны пережить перезагрузку при выключенном домене. Значения по умолчанию применяются при чтении и в строки не пишутся.
4. **Доставка видна.** Консоль показывает «rev 7 на 47 из 50; не отвечают: …», пока не станет 50 из 50.

Каждая камера держит последний документ у себя — поэтому смерть хоста не теряет общего: оно уже лежит на всех.

## Только камеры: смена хоста домена, срок как эпоха

Срок полномочий — у доменного кластера (М12 урок 15). Он растёт при каждом переносе домена и старше ревизии: документ нового срока побеждает, даже если восстановлен из копии на несколько ревизий позади.

- **Плановая.** Оператор выбирает «перенести домен на камеру X». Хост замораживает запись состояния домена на секунды переноса, делает последнюю копию прямо на X, X восстанавливается из неё со сроком `term+1`, старый хост видит больший срок и уступает. Если X копию не взяла — перенос отменяется, хост остаётся хостом, ничего не потеряно.
- **Аварийная.** Хост молчит. Оператор нажимает ту же кнопку на X; X восстанавливает домен из ключа подписывающего и самой свежей проверенной копии состояния домена, которую держат другие камеры, и публикует его со сроком `term+1`.
- **Старый хост вернулся.** Он видит больший срок и понижает себя до обычного члена. То, что успел сделать только он и что не попало в копию, **не пропадает молча и не применяется само**: консоль показывает это списком «не вошло в срок N+1 — применить заново?».

Это единственное место, где возможны два хоста сразу, и оно разрешается как везде в платформе: побеждает больший номер, а проигравший узнаёт об этом при первом чтении.

**Автоматический выбор** («живая камера с наименьшим серийником») возможен, но без кворума разрыв сети даёт два хоста **с одним и тем же сроком**: их придётся разводить по серийнику и показывать проигравшие правки как конфликт. Для конфигурации, которая меняется раз в неделю, это терпимо; по умолчанию — вручную. Это открытый вопрос и в М12: выбирать доменный кластер автоматически или это решение человека сознательно.

**Если автоматика обязательна** — кворум: Raft на трёх–пяти назначенных камерах, остальные — читатели копии. По размеру влезает (`hashicorp/raft` — единицы мегабайт), но камеры теряют питание чаще серверов, а голосующая камера пишет журнал на флеш при каждой правке. Это для заказчиков, которым недопустимо «общее заморожено, пока оператор не перенесёт домен», — не первый шаг.

## Только камеры: картина системы без общего хранилища

Общего хранилища объектов нет, и отдельный федеративный `ObjectStore` не нужен: картину системы собирают каталог и вид для чтения домена, которые и так читают каждый кластер — здесь каждую камеру, по отчёту, который оставил её агент. Окупается старое решение платформы: **имя писателя — последний сегмент ключа** (`HeartbeatsDir`, `w2cplatform/contract.go:322`: `<sub>/heartbeats/<worker>`, а не `<sub>/<worker>/heartbeat`), поэтому по ключу видно, у какой камеры спросить.

**Предел.** Проверен замером (М12 урок 11) на 300 камерах, 30 выключены. Когда домен читал камеры сам, проход шёл 82 с по очереди, 5 с в 16 полос, 1,4 с с отсрочкой для молчащих. По отчётам проход читает только хранилище домена — 1,1 с, выключенная камера ничего не стоит, — а цена переезжает в записи: три на камеру за отчёт, 810 записей и 162 КБ за раунд. «Где камера» отвечается из памяти вида для чтения, а не обходом всех камер. Около тысячи камер записей в доменный кластер становится много: реже и только изменившееся, или сводный отчёт через офис, где он есть (урок 17 — одна запись на офис вместо трёх на камеру).

**Тревоги со всех камер** — один список, по странице на камеру, с честно названными недоступными (М12 урок 14). **Зеркала:** соседи держат копии **закрытых корзин тревог**; тянет хранитель, план зеркал выбирает домен и хранит в `domain/mirrors`. Закрытые корзины не меняются, поэтому копирование не требует координации. Всё видео на соседях не уместится; тревоги — да.

**Записи** — только SD-карты, каждая камера — свой том. **Retention** не нужен как служба: каждая камера чистит только своё дерево — у каталога один писатель.

**Автоматизация между камерами** — как в варианте с серверами (раздел «Сценарии между камерами»), с оговоркой про хост домена там же.

## Что появляется только без серверов и NAS

1. **Состав системы.** Кто в неё входит, решает **вступление в домен** (М12 урок 6). Находить кандидатов — WS-Discovery / mDNS в своём сегменте; между подсетями — список начальных адресов.
2. **Ключ подписывающего.** LDevID камер, взаимный TLS между ними и подпись общего документа — всё от ключа подписывающего домена. Его **нельзя держать только на хосте**: с его смертью домен нельзя будет ни восстановить, ни расширять. Резервная копия ключа лежит за пределами хоста — файлом восстановления у оператора или зашифрованной на нескольких камерах (М12, «Два куска состояния»). Проблемы прав на NAS нет вовсе: каждая камера пишет только себя.
3. **Время.** Слияние событий и таймлайнов требует синхронных часов. Источник NTP — хост домена или внешний, если есть.
4. **Предел масштаба.** Проверенный замером — сотни камер (М12 урок 11): проход домена по отчётам — 1,1 с на трёхстах, цена — записи в доменный кластер. Дальше — сервер или офисы со сводным отчётом, и это уже другой вариант развёртывания.

## Переход между сценариями

Система растёт: сначала десять камер без серверов, потом заказчик ставит сервер. Или наоборот, сервер выводят. Переход — это перенос домена, и делается он той же механикой, что смена хоста; строки камер не трогает вовсе.

**Только камеры → с серверами.**
1. Серверы разворачиваются как новый кластер и вступают в домен (М12 урок 6).
2. Домен плановой передачей переносится с камеры на серверный кластер (М12 урок 15): срок `term+1`, последняя копия — прямо на новый хост. Ключ подписывающего переезжает вместе с доменом, поэтому перевыпускать сертификаты камер не нужно.
3. Агенты камер видят больший срок и дальше следуют за новым хостом. Ни одна камера ничего не переписывает.
4. Если оператор хочет, чтобы серверы писали камеры, домен назначает камерам кластер записи, и регистраторы находят их через книгу источников (урок 13).

**С серверами → только камеры.** Обратно: домен плановой передачей переносится на назначенную камеру, серверный кластер выходит из домена. Записи, которые жили только на серверах, остаются на серверах; это решение оператора, а не платформы.

## Чего не хватает в платформе

Исходный список из девяти пунктов строился на переносе строки камеры на серверы. На домене М12 он сжался; ниже — что осталось и где это сделано.

Что **отпало**:

- ~~ACL на юнит~~ — токен камеры действует только в её кластере из одного, в чужие хранилища она не пишет;
- ~~маршрутизирующее `Variables`~~ — строку всегда пишет камера;
- ~~поток изменений для строк~~ — строка не течёт вниз;
- ~~федеративный `ObjectStore`~~ — картину собирают каталог и вид для чтения М12 по отчётам камер;
- ~~туннель к камере~~ — медиа камера толкает сама, управление — проход агента и долгий опрос;
- ~~Raft~~ — как и было: только если заказчику нужна автоматическая смена хоста домена.

Что **осталось** — вторая часть М12, всё написано:

1. **Правка выключенной камеры** — М12 урок 9, конец первой части: `domain/pending.py`, 9 тестов.
2. **Кластер из одного**: закреплённый юнит `place: device`, без оркестратора, эпоху камера берёт сама, доменный агент — её единственная связь вверх — урок 10: `domain/device.py`, 7 тестов. Новое по сути: флеш (heartbeat — в RAM) и порядок загрузки (ни двери, ни отчёта до первой публикации, иначе домен получит ложный полный ответ «камеры нет»). **Соединение открывает камера** — отчёт вверх, домен читает только своё хранилище, молчание по часам домена: `domain/uplink.py`, 9 тестов.
3. **Сотни мелких членов домена**: М12 заявлен до «низких сотен кластеров», это край; проверено замером — урок 11: `domain/scale.py`, 8 тестов. 300 камер, 30 выключены: когда домен читал камеры сам, проход шёл 82 с по очереди, 5 с в 16 дорожек, 1,4 с с отсрочкой для молчащих; по отчётам — 1,1 с, выключенная камера ничего не стоит, цена — три записи на камеру за отчёт.
4. **Общие настройки без базы**: политика по умолчанию, дерево папок, сценарии между камерами — опубликованы один раз, подписаны, донесены агентами — урок 12: `domain/shared.py`, 7 тестов. Значения по умолчанию разрешаются при чтении и в строки не пишутся.
5. **Поток из чужого кластера**: регистратор сервера пишет и дозаписывает камеру из её кластера, находя её через книгу источников, которую агент приносит в его кластер, — урок 13: `domain/crossing.py`, 7 тестов. Одну камеру пишет один кластер — решение домена. Книга основных говорит карте камеры, пишет ли серверная её основную.
6. **Тревоги со всех камер**: один список, по странице на камеру; зеркала закрытых корзин тревог у соседей, тянет хранитель; план зеркал выбирает домен — урок 14: `domain/alarms.py`, 6 тестов.
7. **Доменный кластер из одного узла**: только камеры; срок; подписанная копия состояния домена у других членов; перенос домена как обычная операция; старый хост уступает и показывает, что было только у него; плановая передача с живого хоста (заморозка, последняя копия на новую камеру, перенос) ничего не теряет, а если новая камера копию не взяла — отменяется, — урок 15: `domain/term.py`, 9 тестов.
8. **Камера, до которой никто не дотягивается**: один поток на приёмник кластера записи для записи и живого видео, ключ потока, долгий опрос, время съёмки по часам камеры, кольцо на камере, выгрузка карты ответом на заявку, приёмники кластера передают поток друг другу — урок 16: `domain/ingest.py`, 10 тестов.
9. **Цепочка «объект — офис — центр»**: передатчик офиса, желание вниз и поток вверх, «звезда», офис как дорога к домену для камеры, которой виден только он (ретрансляция вниз, сводный отчёт вверх) — урок 17: `domain/chain.py`, 6 тестов.
10. **Сценарии между камерами**:
    - запрос со сроком тем же долгим опросом;
    - книга запросов с токеном под сценарий и названным действием;
    - книга опроса для камер, которых никто не пишет, в том числе за офисом;
    - проход домена по всем книгам в процессе подписывающего;
    - на камере — от события к запросу;
    - потолки, схлопывание, «потерян» после перезапуска приёмника;
    - между офисами — вверх через свой офис, передатчики по событию.

    Урок 16, шаг 8, и урок 17, шаг 7: `domain/ingest.py` (`Asker`, `publish_asks`), `domain/scenario.py`, `domain/books.py`, `domain/chain.py` (`lift`, `serve`). Тестов 18: 13 в уроке 16 (там всего 25) и 5 в уроке 17 (там всего 11).

Вступление с доказательством владения, сертификат на устройство и сроки жизни — уже есть: М12 уроки 6–7.

## Как это ложится на то, что уже есть

Почти ничего здесь не новое — старое под другими именами:

| Здесь | В платформе |
|---|---|
| камера | кластер из одного: воркер с закреплённым юнитом и без контроллера |
| вступление в домен | регистрация М12: доказательство владения, LDevID от подписывающего |
| строка камеры | строка кластера, у неё один писатель — консоль этого кластера |
| правка из консоли домена | сохранённая правка (урок 9): агент уносит, камера применяет, исход — в отчёте |
| отчёт камеры | копия члена в доменном кластере (`member_copy`), читается как хранилище самого члена |
| поток камеры | приёмник кластера записи — раздача, переехавшая с воркера (М10B урок 9) в кластер |
| камера за офисом | ретрансляция вниз и сводный отчёт вверх — агент офиса, как агент любого кластера |
| книги домена | строка домена под `domain/<вид>/<член>`, которую агент уносит домой, — как права с урока 4 |
| запрос другой камеры | заявка со сроком (`valid_until`, М10B урок 25), доставленная долгим опросом приёмника |
| запись на SD и закрытие дыр | резервный архив (`backup`, обобщение архива устройства М10B урока 15) и дозапись из него (урок 16) |
| главная камера | доменный кластер, размещённый на камере |
| номер срока | его эпоха |
| общий документ | публикация-и-указатель, как набор идентичностей у подписывающего; объект за указателем по CAS |
| «наибольший целый документ» | `(term, rev)` и подпись, никогда назад |
| события со всех камер | `MergedIndex` как есть |
| зеркала тревог | `platform/mirror` как есть |
| «одно семейство — один писатель» | ACL, как с урока 1 |

Новое по существу — немного, и всё про размер и характер членов домена, а не про механизмы. Камера — член домена, который часто выключен, мал, пишет на флеш, может сам оказаться хостом домена и может быть недостижим вовсе; отсюда порядок загрузки, RAM для heartbeat'а, правка, которая ждёт, запрос, который не ждёт, замер на сотнях членов, перенос домена как обычная операция и соединения, которые всегда открывает камера.
