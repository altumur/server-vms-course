# Ревью ServerVMS: четырнадцатый проход

6 октября 2026 · ревью по правилам `.cursor/rules` через скил `platform-review` · первый проход по ADR-0052 «один механизм, два дерева» · прошлое: [`РЕВЬЮ-SERVERVMS-13.md`](./РЕВЬЮ-SERVERVMS-13.md), ответ автора [`РЕВЬЮ-SERVERVMS-13-ОТВЕТ.md`](./РЕВЬЮ-SERVERVMS-13-ОТВЕТ.md)

**Предмет:** шаг «семейство `requests` и базовый воркер», закрытый на обеих сторонах, ведомость «Паритета» по нему пуста. Решения шага: ADR-0012, 0013, 0014, 0029, 0031, 0033, 0054, 0057; правило 11 `СЕССИИ.md`.

**Деревья:**
- курс — `e7443379` (main), проверен полно: `Source/w2cplatform/{requests,worker,reconcile,spec,speckeys}.py`, `Source/vms/autoworker.py`, спеки;
- продукт — `2d46e95` (main; коммиты шага 9dcb00a, 3285a7c, bc647a7, fd15f2a, 9b1b579, a472353, 2d82b1f, 9f39614), проверен по каждой находке: `vmsworker/w2cplatform/{requests,requestserver,requestspec,workerrequests,reconcile,contract,speckeys,yaml}.go`, `vmsworker/vms/autoworker.go`.

У каждой находки две колонки «курс / продукт»; находка без статуса по второму дереву открыта. Пробы лежат в [`РЕВЬЮ-SERVERVMS-14/probes/`](./РЕВЬЮ-SERVERVMS-14/probes/README.md) и повторяются следующим проходом и ночным прогоном.

Аутентификация дверей между процессами отложена до mTLS по решению владельца (ADR-0034) — не находка. Открытое из ответа на 13-е ревью новой находкой не считается; остальные его области ждут своих шагов.

## Итог

**Заявки шага подтверждены в основном.** Из 16 заявок по восьми ADR в обоих деревьях исправлено 10, частично 5, не исправлена 1 (`filings` на `/metrics`). Пробы 13-го ревью `n1`/`n2` (`lost_to_epoch`) на курсе дают «эпоха не забрана». Долги паритета только сокращаются: паритет спек 210 → 140 строк (один файл байт в байт), загрузка курса 27 → 5, загрузка продукта 58 → 44. Тесты границы обоих деревьев зелёные.

**Новых находок 40: 2 blocker, 11 major, 27 minor.** Блокеры — только в продукте:
- взятие строгого места сравнивает чужой `until` со своими часами: при часах второй коробки впереди на 5 с и больше — два писателя в одно кольцо сетевого тома;
- сценарий автоматизации с именем `asks-…` не исполняется никогда и не убирается: держатель и уборщик пропускают префикс учёта.

Major в обоих деревьях: чужая просьба под тем же `rid` на двери получает 202 с чужой строкой; двойное исполнение после переезда оценщика; `filings` нет в метриках; просьба без ответа цели остаётся без итога в метке; дубликат ключа YAML молча принимается; `spread_by` с опечаткой снимает фильтр. Major только в продукте: одно отказанное действие замораживает сценарий; путь жнеца по `ttl` не читает метку (исправление на ветке `console-host`); `ParseYAML` молча отбрасывает конец файла. Major только в курсе: проваленный перезапуск единицы идёт без задержки и без счёта; `placement.group_by` в строковой форме не сверяется с полями.

**Тесты.** Курс `e7443379`: основной набор — 1476 прошли, 0 упали, 4 пропущены (консоль без jsdom); `tests/cluster` — 100 из 100; `tests/domain` — 211 из 211. Продукт `2d46e95`: `go test ./vmsworker/...` — все 32 пакета `ok`.

## Новые блокеры

1. **Продукт: взятие строгого места сравнивает чужой `until` со своими часами — два писателя.** ADR-0013, ADR-0029, `consensus-and-leadership.mdc`.
   - Курс: **ведёт себя верно**. `_hold_stale` (`worker.py:650`–`658`) ждёт `slot_ttl + HOLD_SKEW` неизменной строки по своему монотонному времени — закрыто ещё в 4-м ревью. Проба `b4`: `ANY_TWO_WRITERS False`, B берёт место на +52 с.
   - Продукт: **дефект**. `ClaimHold` (`contract.go:1965`) → `Slot.Claimable(now)` (`:478`): `now > s.Until`, оба по стенным часам разных коробок. Проба `b4`: часы B впереди на 8 с — на +37,5 с B взял `net`, а `A.fresh=true` до +40 с, `TWO_WRITERS=true`.
   - Сценарий: регистратор A держит сетевой том (строка без сервера, место строгое), отрезан от хранилища и пишет до `until − margin`. Часы B впереди на Δ ≥ 5 с (внутри `ClockAhead = 60`). B берёт удержание при `R + 45 − Δ`; оба пишут в одно кольцо `Δ − 5` с. Блокировка движка на S3 не ограждает. `writtenByOthers` (`vms/volumes.go:482`) сужает окно, но не закрывает: пульс раз в 10 с, продление — раз в проход аренды.
   - Предложение: в `ClaimHold` для чужого непустого удержания применять тот же наблюдатель неизменности (`tornStale`/`HoldSkew`, `contract.go:1267`–`1287`), что и курсовый `_hold_stale`; Go-тест с часами, разнесёнными на 8 с.
2. **Продукт: сценарий с именем `asks-…` не исполняется никогда — ни исхода, ни уборки.** ADR-0054, ADR-0013.
   - Курс: **ведёт себя верно** — префикс учёта в держателе и жнеце не обрабатывается особо (`grep asks- worker.py requests.py` пуст), сценарий исполняется.
   - Продукт: **дефект**. `FileRequest` принимает `rid` с `LedgerPrefix` (проверка только на двери, `requests.go:185`); держатель его пропускает (`requestserver.go:212`), уборщик тоже (`requests.go:598`). Проба `TestR14AScenarioNamedAsksIsNeverPerformed`: контроль — `performed=1`; сценарий `asks-door` — `filed=1 performed=0 outcome="" row-stands=true`.
   - Сценарий: оператор называет сценарий `asks-…`; каждая сработка подаётся (`filed` растёт), команда теряется молча, строка висит вечно, `expired`/`unknown` нет.
   - Предложение: отказывать `LedgerPrefix` в `FileRequest` и в `file_request`; лучше вынести учёт людей из семейства `requests`.

## Ответ на 13-е ревью: что проверено в этом проходе

Проверялись только части, относящиеся к шагу.
- Major 20 («жнец в М11 падал на правах») — **исправлено** в обоих деревьях (`cluster/rights.py:96`–`107`; `specrights.go:71`–`73`), консоль пишет метки и не удаляет.
- Minor «Жнец… `vms_requests_unknown_total`» — формулировка неверна: в коде `w2c_requests_unknown_total` (minor 17).
- Заявка «Платформы» о `filings` на `/metrics` не подтверждена (major 3); остальные её заявки (штампы, повтор, конфликт, `PrepareRequest` отдельно) подтверждены.

Остальные области ответа на 13-е (configstore, секреты, часы камеры, поставка, DQ) ждут своих шагов.

## Что сделано хорошо

- **Закрывающий пишет по индексу, ответ держателя — безусловно.** Курс `requests.py:110`–`134`, продукт `requestserver.go:660`–`695`: в гонке на пяти хранилищах ни одного потерянного ответа и ни одной записи поверх итога за 300 попыток. Жнец считает только после удаления строки по CAS — две консоли одну просьбу дважды не посчитают.
- **«Та же просьба» в двух деревьях определена одинаково:** сравнение текстов строки без `filed`, числа в кратчайшей десятичной записи, вложенное — канонический JSON (`worker.py:2086`–`2087`, `workerrequests.go:93`–`114`). Стражи базы одни на всех хранилищах, права выводятся из того же `worker.requests` (`rights.py:121`, `unit.go:1263`).
- **Ключ идемпотентности привязан к человеку и телу**, тело под HMAC или маской секретов (`console.py:1255`–`1310`, `console.go:389`–`420`); `maxLength` считается по тексту, как его хранит строка, по общей таблице `requests_body.tsv`.
- **`lost_to_epoch` — правило самой эпохи в курсе** (`worker.py:935`–`967`): пробы 13-го `n1`/`n2` закрыты. Признак «место этого сервера» перечитывается только по прочитанной строке и только в безопасную сторону в обоих деревьях (`worker.py:786`–`839`, `contract.go:2113`–`2158`).
- **Отказ на своё `of` стоит в самом журнале** (`events.py:323`–`384`, `events.go:324`–`336`): подсистема, открывшая журнал сама, тоже получает отказ. Перезапуск на месте в продукте сделан аккуратно (`reconcile.go:185`–`206`).
- **Закрытое дерево ключей спеки с отказом по полному пути** в обоих деревьях; двусторонняя загрузка спек с долгами, которые только сокращаются, и один файл долга паритета байт в байт. Долг границы продукта 2861 → 648 слов.
