Дата: 2026-10-22. Срез: **`9c8358d1aeed2364ce84aeaa2977f2d8cf7d3c7b`**.

**Вывод: с правками — 2 блокера, 0 существенных, 0 мелких; 2 причины.**

1. Включённые границы `not_after` и `keep` пересекаются при ровно 60 с расхождения часов: удаление

## П. 1 — not_after и keep

### R91.5-01 — блокер. Оба конца временного окна включены; порядок журнала не гарантирован на равенстве

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:51`–52:

> «лидер хранилища принимает запись в журнал, только пока его часы не позже `not_after`».

И строки 55, 67–69:

> «`keep` = `at` + `valid_for` + 120»;
> «никто не удаляет физически раньше `made.keep` по своим часам»;
> «стоит в журнале раньше любого такого удаления».

**Контрпример на разрешённой границе:** время события=1000, valid_for=600, not_after=1660, keep=1720.
Воркер-заказчик и лидер имеют одинаковые часы; контроллер впереди них на ровно 60 с. Предел ADR:61
соблюдён между всеми этими писателями. Часы лидера возвращают один и тот же секундный тик 1660 для
нескольких последовательных операций; требование уникального значения часов на каждую операцию не задано.

Адресат — именная конечная задача с `name: source-e`, отдельным fixed-полем `event: e`, key=`{event}`,
без about. Key однозначен, не ссылается на поле id; случай не зависит от второй находки. Физическая уборка
строки с made разрешена новой поправкой ADR, после подтверждённого завершения и снятия задачи.

1. Первая запись с id операции `aa` исполнена в t=1000. Задача закончилась, её состояние done сохранено.
2. Копия того же вызова была повторно отправлена в t=1001 до получения первого ответа и остаётся в пути.
   После первого ответа логический вызов завершён; нормальный цикл заказчика подтверждает ту же эпоху.
   Страж не меняется. Это не ожидание основного шага воркера без пульсов.
3. После первой записи прошло больше 120 с и применено не меньше 50 000 других записей с id. Хранилище
   законно забыло квитанцию aa. Это разрешённое состояние памяти по P/01.1:311.
4. При часах контроллера **1720** удаление уже разрешено: это не «раньше keep». Лидер с часами **1660**
   ставит в журнал удаление единицы, затем убирается осиротевшее состояние.
5. В том же тике лидера **1660** приходит копия aa с not_after=1660. Условие «не позже» ещё истинно.
   Guard эпохи прежний, строки уже нет, CAS `""` проходит. После удаления в журнал попадает повторное создание.

Получается заново появившаяся задача без результата. Это также возвращает прежнее значение born из
сохранённой команды после физического удаления; одна уникальность born не заменяет барьер этой записи.
Событие проверялось библиотекой до отправки, а новое условие должно было отсечь именно позднее применение.
Идентификатор операции сохранён; правило повтора после ambiguous не нарушается.

**Первичное основание:** собственное обещание ADR:68–69 о порядке журнала и Confirmation:178–180 о
безвредности позднего повтора. P/01.1 Н3 `записать`,
`Platform/01-store/spec/01.1-store.norms.md:255`–266 проверяет в момент операции текущие guard/CAS;
строки 305–311 разрешают CAS отсутствия после удаления и истечение памяти id. Стенной формат времени
P/01.1 Н0:26–36 допускает целые секунды, минимальная точность часов в новом условии не задана.
Увеличение номера журнала не обязано увеличивать показание стенных часов.

**Почему одного запаса 60 с недостаточно на включённых концах:**

```text
удаление разрешено: C >= keep
расхождение:        C - L <= 60
следовательно:      L >= keep - 60 = not_after
приём разрешён:     L <= not_after
пересечение:        L == not_after, C == keep
```

**Вопрос «Архитектору» / рекомендация:** сделать один конец строгим. Например, физическое удаление
только при `now > keep`, оставив приём при `now <= not_after`, либо приём только при `now < not_after`,
оставив удаление с keep. Зафиксировать выбор в общей семантике и проверить равенство/соседние значения
при максимальном разрешённом расхождении часов. Не полагаться на скорость железа или точность часов,
которую профиль не требует.

**Происхождение:** сохранившийся граничный случай R91.4-02 после нового механизма. На `8c6b0b96f` поздняя
запись вообще не несла not_after; пятая редакция закрывает применение при `L > not_after`, но вводит
две включённые границы без доказанного разнесения на равенстве. Наличие дефекта в классе не объявляется
впервые наведённым этим коммитом; конкретные новые условия сравнения добавлены `9c8358d1a`.

**Проба:** `inclusive-expiry-and-delete-boundary` в `probes.py`; журнал модели заканчивается
`delete(unit), delete(state), put(unit)` при одинаковом leader_now=1660, результат put — ok.
Контроль `strict-endpoint-controls` показывает, что каждый из двух вариантов строгого конца запрещает
эту трассу. Сеть и нагрузка 50 000 записей не выполнялись; их расписание и допустимое истечение памяти
заданы как предпосылки конечной модели.

## П. 1 — шаблон key

### R91.5-02 — блокер. Обязательное включение источника id в key создаёт циклическую формулу

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:36`–39:

> «Id создаваемой строки — `<заказчик>-<key>` … `key` — шаблон … по полям строки, называющий
> все `fixed`-поля адресата и поле его `about`».

**Допустимый адресат:**

```yaml
name: sink
unit:
  rows: jobs
  id: name
  fields:
    name: {type: string, required: true, fixed: true}
about: {sub: cameras, field: name}
placement:
  capacity: {default: 1}
  unplaced: {delete_after: 1}
```

И декларация заказчика source по новому ADR:

```yaml
worker.creates:
  - {sub: sink, rows: jobs, key: "{name}", valid_for: 600}
```

`{name}` — допустимый шаблон P/02.1:177; он инъективен по единственному строковому полю.
Он называет все fixed-поля и поле about, адресат не numeric, вложенных префиксов нет. Но P/06.1 Н1.3
определяет named id как **значение поля** unit.id, то есть в этом примере row.id=row.name.
Совместно с новой формулой получается:

```text
row.id = row.name
row.id = "source-" + row.name
len(row.name) = 7 + len(row.name)
```

Ни одной конечной строки, удовлетворяющей обоим правилам, нет. Для name=u новое правило даёт id=source-u,
не равный name. Заполнить name значением source-u — не решение: шаблон по полям **получившейся строки**
теперь даёт id=source-source-u. Нельзя молча поменять значение named id на другое поле: ADR:47 сохраняет
общие правила строки и не выбирает такого исключения.

**Первичное основание:** `Platform/06-console/spec/06.1-console.norms.md:174`–177 — named id и его
неизменность. `Platform/02-installer/spec/02.1-installer.norms.md:201`, 206 разрешает string-источник id
и fixed=true; строки 315–316, 838 разрешают about по этому же fixed-полю. Действующие ограничения
delete_after:805–806 специально допускают fixed у источника id и about по id. Новое требование key
не делает для них исключения. Отказ источнику id только из-за этой рекурсии также пока не назван.

**Последствие:** декларация, удовлетворяющая названным условиям новой редакции, не может создать ни одной
единицы. Проверка инъективности шаблона сама по себе этого не обнаруживает: `{name}` инъективен,
проблема в цикле определения id.

**Вопрос «Архитектору» / рекомендация:** явно отделить вычисляемый источник named id от входов key.
Например, исключить источник unit.id из требования включить fixed/about, заполнять его окончательным
id и запрещать циклический шаблон, который от него зависит. Либо явно исключить соответствующие формы
адресатов из worker.creates. Выбор сужения — решение «Архитектора»; расширять внутренний API не требуется.

**Происхождение:** наведено `9c8358d1a`. В четвёртой редакции key с обязательным включением fixed/about
не было: row.name=source-u и id=source-u не требовали повторного префиксования имени. Новый diff добавляет
именно это обязательное отношение. Это не претензия к сознательному отказу numeric или вложенных префиксов.

**Проба:** файл `id-source-fixed.subsystem.yaml` действительно принят текущим проверяющим Loader навыка,
построенным из трёх файлов формы P/02.1: verdict=ok. Проверен **адресат**, не будущая форма worker.creates.
Отдельно проверены допустимость `{name}` и равенства длин; последнее — алгебраическое противоречие для
любых конечных строк, а не вывод о всей области из нескольких примеров.
