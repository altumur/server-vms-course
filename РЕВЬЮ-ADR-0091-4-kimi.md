## Проверено без находок (закрытие блокеров и существенного)

- **Блокер «порядок уборки» (Codex R91.3-01, Claude Т-2) — закрыт.** Новый порядок — «снять с размещения → удалить строку (CAS, `placement_turn`) → состояние только после подтверждённого удаления» устраняет обе дыры старого порядка: отменённое удаление строки (правка/продление) состояние не трогает (итог действует), обрыв после удаления строки оставляет осиротевшее состояние, которое снимает уборка. Уборка осиротевшего одной операцией (CAS версии состояния + `guard` строки с `index: ""`) отменяется строкой, созданной или изменённой после чтения; действующее состояние уборка не трогает. Confirmation требует оба отрицательных сценария.
- **Блокер «повтор после физической уборки» (Codex R91.3-04, Kimi 1) — закрыт.** Горизонт уборки связан с горизонтом повтора: `made.keep = at + valid_for + 60`, контроллер не удаляет физически строку с `made` раньше `keep` по своим часам — пока повтор возможен, id занят и CAS `""` повтора проваливается. Допуск 60 с назван предпосылкой P/08.2:109 (`clocks`, тот же допуск, что `TOKEN_SKEW`). «При продлении `at` — наибольшее» двигает `keep` корректно; `valid_for` объявляется в `worker.creates[]` — моя мелкая 3 ред. 3 закрыта.
- **Kimi 2 ред. 3 (имена полей состояния) — закрыта.** Действующее состояние — вложенным объектом `state: {<имя>: <поля без born, revision, epoch>}` в представлении консоли и в снимке контроллера, одним правилом действия; поле единицы `state` при объявленном `unit.state` — отказ загрузки; столкновения имён с платформенными полями не возникает.
- **Смена `born` — новая жизнь (Codex R91.3-02).** Держатель останавливает единицу и берёт эпоху заново с новыми привязками `of` (ADR-0013), как у удалённой и созданной (P/03.3 Н5); смена `revision` при том же `born` — перезапуск под прежней эпохой — согласовано с P/03.2 Н1.5 («перезапуск той же единицы тем же держателем по смене revision эпоху не меняет»). «Состояние пишется с `born` и `revision` запуска, не перечитанной строки» — верно: запись перечитанной revision была бы гонкой с правкой.
- **Чтения обратной проверки (Claude Т-1).** Формулировка «цели `ref`/`must_match` самой строки и строки семей каталога, чьё поле с `ref` на таблицу адресата и `must_match`» соответствует P/06.1:200–202 («в обе стороны»: создание/правка цели проверяет ссылающиеся строки). «Удаление ссылок не проверяет» согласовано с правом без удаления.
- **Надгробие (Claude мелкое 3).** «Только для события позже надгробия (`written`), с CAS его версии и теми же `fixed`» — точно правило P/06.1:182 (создание над надгробием с cas по версии надгробия и теми же fixed). Повтор прежнего события (его время старше `written` быть не может) удалённое оператором не возрождает; событие той же личности позже надгробия — заводит. Поле `written` у надгробия есть (P/06.1 Н0).
- **Префикс не выбирается (Claude мелкое 1).** `<заказчик>-` — константа; вложенные префиксы двух заказчиков (`rec-`/`rec-x-`) — отказ загрузчика; право — создание и правка без удаления (удаление — контроллер по сроку и оператор дверью; сценария «заказчик отменяет заказ» у свидетеля нет).
- **Маска ссылкой `mask_from` (Claude Т-3).** `<sub>/<id>@sha256-<hex>` — дайджест зафиксирован в строке задачи; тела нет — задача `failed`, скана без маски нет; наследование — только у строк с `made` (ручные задают маску blob-полем, как прежде).
- **Confirmation** обновлена под все новые нормы: отменённое удаление — итог действует; смена `born` — новая эпоха; повтор после уборки по сроку и над надгробием — без нового эффекта; действующее состояние — в выдаче консоли и в снимке.
- **Таблица разбора** — все 8 строк (включая Kimi 1, 2, 3 ред. 3) отражены в тексте четвёртой редакции.

## Находки

### 1. Мелкая — п. 1: строка с `made` живёт до `keep` даже после `delete_after` — накопление без названного потолка

- **Место:** decisions/0091-….md :59–60, :103–104.
- **Что не так:** законченная задача с `made` удаляется физически не раньше `made.keep` = последнее событие + `valid_for` + 60, даже если `delete_after` меньше. При большом `valid_for` строки заказов копятся в таблице адресата (перечисления, представления консоли) без названного потолка или наблюдаемости (метрика `creates{outcome}` считает создания, не живой остаток).
- **Источник:** п. 1 и п. 3 четвёртой редакции; P/04 (delete_after).
- **Рекомендация:** одна фраза — ожидаемый порядок `valid_for` у заказчиков VMS и/или что остаток строк с `made` виден в пульсе/представлении.
