# Урок 2 — Хранилище становится реплицируемым

**Модуль:** М11 — ClusterVMS: воркеры, которые переживают свой сервер
**Вы напишете:** группу raft из трёх демонов `configstore` — сначала группу из одного, потом вступление двух серверов; разовый перенос строк коробки в группу; разбор API хранилища и его отказов — «конфликт», «нельзя», «не сделано» и «неизвестно»; замер смерти лидера под продлениями аренд и правку цикла воркера, которую этот замер нашёл; список того, что обязан обещать фейк хранилища; и доказательство, что `vms/` смены хранилища не заметил.
**Время:** ~180 минут (75 без стенда).

## Зачем этот урок

Первое утверждение модуля: **в `vms/` ничего не меняется**, когда файлы коробки становятся хранилищем, реплицированным на три сервера. Всё, что будет дальше, стоит на этом утверждении, поэтому его нужно доказать первым делом, а не принять на веру.

Доказательство — не фраза «наше хранилище похоже на каталог файлов». Доказательство — это список запросов, которые процесс кластера отправляет в хранилище, и обещания, которые хранилище по ним даёт: версия, растущая в одном журнале на весь кластер, и запись с `cas`, которая проходит, только если версия не сдвинулась. Если обещания те же, что давали файлы на одной коробке, — код поверх них работает одинаково. Этот урок показывает запросы, обещания и то, как их держит машина состояний, на которой идёт стенд.

У реплицированного хранилища есть то, чего у файлов не было: лидер, который может умереть посреди записи. Поэтому половина урока — о том, что хранилище отвечает, когда не может ответить «да» или «нет», и что происходит с арендами воркеров, пока группа выбирает нового лидера. Замер этого нашёл ошибку не в raft, а в цикле воркера, — и это тоже урок.

> **Что проверяется без железа.** Почти всё. `tests/test_lesson1_stores.py` гоняет базовые классы М10A поверх хранилища стенда — машины состояний демона за дверями по ролям; `tests/test_trace.py` проверяет, что трасса, которую печатают уроки, — это ровно то, что ручка `ConfigstoreVariables` отправляет в настоящий unix-сокет. Сам демон, группа из трёх и смерть лидера — `vmsserver/tests/test_configstore.py` (нужен `pip install pysyncobj cryptography`, без них эти тесты пропускаются), вступление по mTLS, импорт и отказы — `vmsserver/tests/test_configstorevars.py`, машина и права — `vmsserver/tests/test_storemachine.py`. Полные трассы урока — в [`traces/`](traces/), файлы `02-*.txt`. Кластеру нужны три виртуальные машины со стенда М9.

## Что нужно знать заранее

- **Урок 1** — стенд модуля, первый воркер и его heartbeat; группа raft в терминах модуля.
- **М10A, урок 2** — `Variables`: `get`, `put(cas)`, `list`, версия, `Conflict`.
- **М10A, урок 3** — хранилище — это URL; схемы в `open_vars`.
- **М10A, урок 6** — эпоха и аренда: окно записи `lease_ttl − lease_margin`.
- **М9, урок 4** — раздел данных `/data`, который переживает A/B-обновление. На нём живёт журнал raft.

## Чему вы научитесь

1. Собрать группу raft: группа из одного, вступление нового сервера и почему порядок «сначала демон, потом вступление».
2. Перенести строки коробки в группу один раз — и объяснить, зачем группе `-index-base`.
3. Прочитать API хранилища и пять его отказов и сказать, какой из них что значит для вызывающего.
4. Объяснить, почему `403` приходит от демона своего сервера раньше, чем запрос куда-то уйдёт.
5. Сказать, переживают ли аренды выборы лидера, по трём замерам — прототипа курса, демона курса и продукта.
6. Найти в цикле воркера место, где пауза хранилища удваивалась, и показать правку.
7. Сказать, что обязан обещать фейк хранилища, и найти место, где он может соврать.

## Шаг 1 — Группа из одного и вступление

На каждом сервере стоит демон `configstore` — юнит `configstore.service` (урок 3), данные в `/data/platform/configstore`. Его флаги собирает `w2c-run.sh` из файла платформы `/etc/w2c/w2c.env` ([`deploy/w2c-run.sh`](clustervms/deploy/w2c-run.sh)):

```sh
    configstore)
        # The daemon's flags from the platform's file. `-bootstrap` on the first server of a cluster (CONFIGSTORE_JOIN
        # empty), `-join <member>` on every other; both count only the first time — a daemon taken into a group starts
        # from its journal, so systemd restarting it with the same flags just brings it back.
        start="-bootstrap"
        [ -n "${CONFIGSTORE_JOIN:-}" ] && start="-join $CONFIGSTORE_JOIN"
        # shellcheck disable=SC2086
        exec "$PYTHON" -m w2cplatform.configstore -id "${SERVER_NAME:?SERVER_NAME in $W2C_ENV}" \
            -dir "${CONFIGSTORE_DIR:-/data/platform/configstore}" -raft "${CONFIGSTORE_RAFT:?CONFIGSTORE_RAFT in $W2C_ENV}" \
            -api "${CONFIGSTORE_API:?CONFIGSTORE_API in $W2C_ENV}" -sockets "${CONFIGSTORE_SOCKETS:-/run/configstore}" \
            -rights "${CONFIGSTORE_RIGHTS:-/etc/w2c/configstore-rights.json}" -tls "${W2C_TLS:-/etc/w2c/tls}" \
            -tuning "${CONFIGSTORE_TUNING:-lan}" $start "$@" ;;
```

У демона три двери. Сокеты ролей в `/run/configstore/` — для процессов своего сервера (урок 5). `-raft` — порт библиотеки raft, по нему члены группы гоняют журнал. `-api` — дверь для других демонов: вступление, состояние группы. В `w2c.env` первого сервера `CONFIGSTORE_JOIN` пуст, у остальных он называет дверь члена группы:

```sh
CONFIGSTORE_RAFT=10.0.0.1:8301
CONFIGSTORE_API=10.0.0.1:8300
# Empty on the cluster's first server (`-bootstrap`: a group of one); on every other, a member's door:
#CONFIGSTORE_JOIN=srv-a@10.0.0.1:8300
```

**Первый сервер — группа из одного.** `-bootstrap` на пустом каталоге запускает группу, в которой один голос: демон выбирает себя лидером, записывает основание версий (`-index-base`, шаг 2) и строку о себе как о члене группы — и только потом открывает сокеты.

**Каждый следующий — сначала свой демон, потом вступление.** `-join srv-a@10.0.0.1:8300` — демон нового сервера спрашивает члена группы, кто в ней состоит, запускается с ними как с соседями и **после этого** просит добавить себя. Член группы передаёт просьбу библиотеке, а она — лидеру (в `hashicorp/raft` это `AddVoter`). Порядок важен: группа, которая уже считает голосом сервер, ещё не запущенный, потеряла один голос, а у группы из одного это был бы единственный, кроме её собственного. Библиотека проводит одно изменение состава за раз; второе, пока первое не записано, она отклоняет, и демон его повторяет.

Трасса — [`traces/02-a-server-joins.txt`](traces/02-a-server-joins.txt). На стенд из трёх серверов приходит четвёртый, `srv-d`:

```
# configstore on srv-d → srv-a's daemon, srv-a@10.0.0.1:8300 (mutual TLS)
POST /v1/join {"id": "srv-d", "raft": "10.0.0.4:8301", "api": "srv-d@10.0.0.4:8300"}
→ 200 {
```

В ответе — состав группы, уже с `srv-d`. Дверь `-api` — только взаимный TLS: без сертификата кластера с ролью `configstore` вступить нельзя (шаг 11). Дальше в трассе стартуют юниты `srv-d`: ресурс записывает, где он отвечает, и воркер берёт своё имя.

```
# resource on srv-d → /run/configstore/resource.sock
POST /v1/write {"op": "put", "key": "platform/doors/srv-d", "cas": null, "items": {
  "url": "http://srv-d:8090",
  "since": "1757500000.0",
  "at": "1757500000.0"
}}
→ 200 {"index": 1004}
```

```
# vmsworker w-srv-d-1 on srv-d → /run/configstore/vmsworker.sock
POST /v1/write {"op": "put", "key": "vms/slots/w-srv-d-1", "cas": "", "items": {
```

Ни одной строки других серверов `srv-d` не записал. Данные группы новый демон получил от лидера сам — raft присылает журнал или снимок, — и это не шаг, который кто-то пишет. Тест — `test_a_server_that_joins_a_running_group_gets_its_data` (`vmsserver/tests/test_configstore.py`): пятьдесят строк на первом сервере, два сервера вступают — третий через второго, ведомого, — и в **своей** копии у третьего те же ключи и **те же версии**; потом первый сервер останавливают, и двое пишут дальше.

**Два сервера — по-прежнему два кластера из одного** (урок 1). Вступление делает из группы из одного группу из двух, а это хуже одного: смерть любого останавливает запись. Поэтому второй и третий сервер вступают один за другим, в один заход, и между двумя вступлениями — секунды, когда голосов двое. Это окно не мерилось; смерть лидера во время вступления — тоже (открытые вопросы в конце урока).

**Перезапуск — не новое вступление.** Демон, которого группа приняла, кладёт рядом с журналом `member.json`; на следующем старте он поднимается со своего журнала с теми соседями, которых видел последними, а `-bootstrap` и `-join` больше не читает. Поэтому `systemd` перезапускает его с теми же флагами, и он просто возвращается, догоняя пропущенное (`test_a_member_restarted_on_its_journal_comes_back_with_its_rows`).

## Шаг 2 — Коробка становится кластером: импорт один раз

Одиночная коробка и камера остаются на файлах — `FileVariables`, `file://` (решение владельца): ни демона, ни журнала raft, ни лишних записей на флеш. Когда коробка становится кластером, её строки переходят в группу **один раз**, на том перезапуске, который переход и так требует:

```sh
# srv-a: счётчик версий коробки
cat /data/platform/config/index                       # скажем, 4817

# группа из одного, версии которой начнутся выше любого числа, что коробка когда-либо выдала
w2c-run.sh configstore -index-base 5000               # первый запуск — руками; основание ляжет в журнал группы

# строки коробки — в группу, через admin.sock этого сервера
python3 -m w2cplatform.configstore import --from file:///data/platform/config
```

Дальше демон, как обычно, поднимается юнитом с теми же флагами: демон стартует со своего журнала, и основание уже в нём. Значения переносятся как есть: эпохи, поколения и ревизии лежат **внутри** значений. Версии — нет: у каждой строки в группе новая. И вот зачем `-index-base`. Процесс, который читал строку на коробке, может держать в памяти её версию — скажем, 4810 — и через минуту прийти с ней в CAS. Если бы группа считала версии с нуля, 4810 однажды стала бы версией какой-то **другой** строки, и устаревший CAS прошёл бы поверх неё. Группа, начатая с основанием 5000, выдаёт версии `5000 + индекс журнала`: любая из них выше любой версии, что выдала коробка, и CAS со старой версией конфликтует — вызывающий перечитывает.

Импорт отказывается **целиком и до первой записи**, если ему есть, что перепутать (`w2cplatform/configstore.py`):

```python
def _load_fresh(rows: list[tuple[str, dict]], highest: int, dst, what: str) -> dict:
    """Write `rows` into the group behind `dst` (an admin handle), each created with `cas=0`, values untouched.
    Refused whole, before the first write, when a row is heavier than the store takes, when the group's base is below
    `highest`, or when the group holds a row this load did not write — a row that is one of `rows`, the same, is one
    an earlier run of the same load wrote before it stopped, and the load goes on after it (twelfth pass, minor)."""
    heavy = [f"{k} ({items_bytes(v)} bytes)" for k, v in rows if items_bytes(v) > MAX_VALUE]
    if heavy:
        raise ValueError(f"rows heavier than the store takes ({MAX_VALUE} bytes) — move what makes them big into an "
                         f"object first: " + "; ".join(heavy))
    status = dst.status()
    base = int(status.get("index_base", 0))
    if base < highest:
        raise ValueError(f"the group's base is {base} and {what} handed out versions up to {highest}: start the group "
                         f"with -index-base {highest} or more, or a version remembered from {what} could match a new row")
    want = dict(rows)
    held = set(dst.list(""))
    alien = sorted(k for k in held if k not in want or dst.get(k)[0] != want[k])
    if alien:
        raise ValueError(f"the group holds rows this load did not write ({', '.join(alien[:5])}"
                         f"{', …' if len(alien) > 5 else ''}): rows are loaded into a fresh group only")
    for key, items in rows:
        if key not in held:
            dst.put(key, items, cas=0)
    return {"rows": len(rows), "highest_before": highest, "index_base": base, "there_before": len(held)}
```

И ещё раньше — если в файлах коробки есть строка, которая не читается: выброшенная, она читалась бы как отсутствующая, а отсутствующая эпоха начинается снова с 1. Тесты — `test_a_box_imported_into_a_fresh_group_keeps_its_values_and_no_version_it_handed_out_matches` (значения те же, каждая запомненная старая версия даёт `Conflict`, и весь набор тестов контракта `Variables` зелёный после импорта) и `test_an_import_is_refused_whole_into_a_group_it_could_confuse`. Тот же механизм у резервной копии: `configstore backup` пишет строки и самую высокую версию, `configstore restore --from` загружает их в свежую группу, основание которой выше этой версии (`test_a_backup_restores_into_a_fresh_group_above_its_highest_version`).

**Остановившийся импорт продолжается.** Двенадцатое ревью заметило, что импорт, оборванный на середине (оборвалась сессия оператора, упал демон), продолжить было нельзя: в группе уже есть строки, а группу со строками импорт отвергает. Оставалось одно — стереть `-dir` на всех серверах и поднимать группу заново. Теперь тот же `import` или `restore`, запущенный ещё раз, продолжает с того места, где остановился, если каждая строка в группе — одна из тех, что он загружает, и такая же. Строка, которую он не писал, или изменённая с тех пор, по-прежнему отказывает: загружать можно только в группу, куда больше никто не писал. **И строка тяжелее, чем берёт хранилище, отказывает весь импорт до первой записи**: у `FileVariables` потолка нет, у группы есть (`MAX_VALUE`, шаг 3). Тест — `test_an_import_that_stopped_goes_on_and_a_row_heavier_than_the_store_takes_refuses_it_whole`.

Почему не сделать коробку группой из одного с первого дня, чтобы обойтись без импорта? Так предлагала записка, и это работает. Но коробка тогда платит журналом raft за каждую запись — продления аренд, порядка записи в секунду на воркер, на флеш, круглосуточно, — ради перехода, который большинство коробок не сделает никогда. Разовый импорт дешевле.

## Шаг 3 — API и отказы

Процесс разговаривает с демоном своего сервера по HTTP с JSON поверх unix-сокета своей роли. API — продукта, по его именам; в курсе его отвечает одна функция, `storemachine.answer`, и на демоне, и на стенде:

| Метод | Запрос | Ответ |
|---|---|---|
| `get(path)` | `GET /v1/get?key=<path>` | `200 {"items": {…}, "index": N}`; ключа нет — `{"items": null, "index": ""}` |
| `list(prefix)` | `GET /v1/list?prefix=<prefix>` | `200 {"keys": {"<path>": N, …}}` |
| `put(path, items, cas)` | `POST /v1/write {"op": "put", "key", "items", "cas", "id"}` | `200 {"index": N}` |
| `delete(path, cas)` | `POST /v1/write {"op": "delete", "key", "cas", "id"}` | `200 {"index": N}` |

`cas: null` — без условия; `cas: ""` — «только создать»: ключа быть не должно; число — «только если версия ключа сейчас такая». `id` — идентификатор операции, его ручка делает сама, один на операцию (шаг 9).

Отказ — тело `{"kind", "error"}` с одним из шести видов, и каждый вид ручка переводит в то, что код платформы уже понимает (`w2cplatform/configstorevars.py`):

```
#   409 → `Conflict`   403 → `Forbidden`   400 → `ValueError` (not a key, as `safe_path` says it)
#   413 toolarge → `TooLarge` (a row over `storemachine.MAX_VALUE`)
#   503 unavailable → `StoreUnavailable`   503 ambiguous → `StoreAmbiguous`
```

| Код и вид | Что случилось | Что делает вызывающий |
|---|---|---|
| `409 conflict` | версия ключа не та, что в `cas`; тело несёт версию сейчас | перечитать и применить своё поверх (шаг 5) |
| `403 forbidden` | роль этого сокета не может так поступить с этим ключом | ничего: это ошибка кода или чужой процесс (шаг 6) |
| `400 badkey` | ключ, который хранилище не примет (тот же запрет, что у файлов) | ничего: ошибка кода |
| `413 toolarge` | строка тяжелее `MAX_VALUE` (512 КиБ) | ничего: то, что делает строку тяжёлой, место в объекте |
| `503 unavailable` | лидера не нашлось за время ожидания (`-leader-wait`, 5 с): запись **не сделана** | повторить можно; воркер держит то, что держит, и пробует на следующем шаге |
| `503 ambiguous` | запись дошла до лидера, а он умер, не ответив: исход **неизвестен** | повторять — только с тем же `id`; кому важно, сначала перечитать |

Два `503` — новое по сравнению с файлами, и различать их — главное, что здесь надо понять. Оба вида — `OSError` (`StoreUnavailable` — подкласс `OSError`, `StoreAmbiguous` — подкласс `StoreUnavailable`), а каждый вызывающий в платформе уже читает `OSError` как «хранилище не ответило», а не как «нет» (обратная связь BC): воркер не бросает камеру из-за паузы хранилища. И ни один из них — не `Conflict`. `Conflict` на продлении слота **ограждает** воркер (`Worker._renew_slot` возвращает `False`); отдать его за неизвестный исход значило бы оградить живой воркер выборами лидера.

**У строки есть потолок.** Двенадцатое ревью записало значение в 32 МиБ — оно было принято за 0,24 с и легло в журнал raft. Такую запись каждый член группы держит в памяти и пишет в журнал, её шлют отставшему ведомому, и пока одна такая запись идёт по сети, пульс лидера ждёт за ней. Строка весит пару сотен байт, а тяжёлой её делает поле, которому место в объекте. Поэтому строка весит не больше `MAX_VALUE` байт. Считают так же, как любое хранилище (`variables.items_bytes`: ключи и значения в байтах — мера Nomad для Variable). Отказ дважды: дверь отвечает `413 toolarge` до того, как что-то отправлено в журнал, и машина отказывает ту же команду сама — каждый член группы применяет журнал и обязан отказать одинаково (`w2cplatform/storemachine.py`):

```python
MAX_VALUE = 512 << 10      # what a row's items may weigh (`items_bytes`): see the notes above
```

512 КиБ — потолок значения у Consul на том же `hashicorp/raft`, что у продукта (`kv_max_value_size`), и по той же причине. Это тысяча строк и восемь потолков Nomad (64 КиБ), под которые платформа строилась. Ни одна строка, которую пишет код, к нему не подходит. Ручка объявляет этот потолок своим `max_bytes`, поэтому тяжёлая строка — `TooLarge` ещё у вызывающего, как у любого хранилища с потолком. Тест — `test_a_row_heavier_than_the_store_takes_is_refused_at_the_door_and_by_the_machine`.

Откуда демон знает, какой из двух `503` ответить (`RaftBackend._apply`): отказы библиотеки «нет лидера», «очередь полна», «идёт смена состава» значат «команда не добавлена в журнал»; «этот узел не лидер», «лидер сменился», «исход неизвестен» и молчание дольше срока — «могла быть добавлена, а дойдёт ли до фиксации, неизвестно». В пределах своего срока демон повторяет обе с той же командой — и с тем же `id`; когда срок вышел, он отвечает `unavailable`, только если видел одни отказы первого рода.

**Чтение — тоже через журнал.** `get` и `list` — команды raft: ответ — то, что лежало в машине состояний на этой записи у лидера этого срока. Это линеаризуемо — в `pysyncobj` нет ReadIndex и аренды лидера, и другого линеаризуемого чтения она не даёт. Продление аренды в платформе — это **чтение** (`Lease.renew` читает строку эпохи), и локальным оно быть не может: ведомый, отрезанный от группы, продолжал бы подтверждать эпоху, которую остальные уже сдвинули. Следствие для трасс: на демоне чтение тратит индекс журнала, и версии двух соседних записей отличаются не на единицу, а на число чтений между ними. Стенд чтений не считает, чтобы трассы читались, а ни один код в платформе не рассчитывает, что версии идут подряд: их сравнивают только на равенство.

## Шаг 4 — Консоль создаёт камеру

Трасса — [`traces/02-console-creates-a-camera.txt`](traces/02-console-creates-a-camera.txt). Консоль стенда создаёт камеру `north-gate`. Первый запрос — чтение `platform/schema`: консоль сверяет формат хранилища, прежде чем писать (М10A, урок 17); здесь его не разбираем.

Сначала номер. Камерам номера выдаёт счётчик `vms/next_id`, и выдаёт по CAS, как любую другую запись:

```
  "id": "1",
  "revision": "1",
  "name": "north-gate",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": "true",
  "priority": "100",
  "labels": "vlan:cctv-a",
  "folders": "",
  "ref": "",
  "cred_username": "",
  "cred_secret": "",
  "live": "always",
  "kind": "video"
}}
→ 200 {"index": 1005}
```

Все значения — строки: `"enabled": "true"`, `"priority": "100"`, список меток — строка через запятую. Так было у файлов, так у хранилища кластера: строка — словарь строк. Типы восстанавливает спека подсистемы при чтении (`SPEC.row`, М10A урок 9): хранилище хранит текст, смысл знает подсистема.

## Шаг 5 — Два редактора одной строки

Самое важное обещание хранилища видно, только когда пишут двое. Трасса — [`traces/02-two-editors-one-row.txt`](traces/02-two-editors-one-row.txt): консоль на `srv-a` переименовывает камеру 1, консоль на `srv-b` одновременно задаёт ей срок хранения. Обе читают строку с одной версией:

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/cameras/1
→ 200 {
  "items": {
    …
  },
  "index": 1005
}

# console on srv-b → /run/configstore/console.sock
GET /v1/get?key=vms/cameras/1
→ 200 {
  "items": {
    …
  },
  "index": 1005
}
```

Консоль `srv-b` пишет первой — и проходит, потому что версия ещё 1005:

```
# console on srv-b → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/cameras/1", "cas": 1005, "items": {
  "id": "1",
  "revision": "2",
  "name": "north-gate",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": "true",
  "events_retention_days": "30",
  …
}}
→ 200 {"index": 1006}
```

Консоль `srv-a` пишет второй — со старой версией, и получает отказ:

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/cameras/1", "cas": 1005, "items": {
  "id": "1",
  "revision": "1",
  "name": "north-gate-2",
  …
}}
→ 409 {"kind": "conflict", "error": "vms/cameras/1: cas=1005 but the version is 1006", "index": 1006}
```

Посмотрите на тело этой записи. В нём **нет** `events_retention_days`: `srv-a` прочитала строку до того, как `srv-b` задала срок. Без CAS эта запись прошла бы, строка снова осталась бы без срока, и правка `srv-b` исчезла бы молча — камера вернулась бы к наследуемому сроку: никто бы ничего не заметил, пока через месяц не стали бы искать, куда делись события. С CAS `srv-a` получает `409`, читает строку снова и пишет поверх:

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/cameras/1", "cas": 1006, "items": {
  "id": "1",
  "revision": "2",
  "name": "north-gate-2",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": "true",
  "events_retention_days": "30",
  …
}}
→ 200 {"index": 1009}
```

Обе правки на месте. Почему 1009, а не 1007: между ними `srv-b` записала строку срока (`vms/retention/1`, 1007), а отказанная запись `srv-a` тоже потратила индекс журнала — 1008. Команда записи попадает в журнал до того, как машина состояний решит, пройдёт ли её `cas`, и решение принимают все члены группы одинаково, по одному и тому же журналу.

Повтор после `409` делает `Controller.write` из М10A — примитив, которым пользуется каждая правка в платформе (`w2cplatform/contract.py`):

```python
    def write(self, path: str, mutate, retries: int = 10) -> dict:
        """Read-modify-write by CAS: `mutate(items or {}) -> new items`.
        A conflict means another instance wrote; re-read and go again."""
        for attempt in range(retries):
            try:
                items, idx = self.vars.get(path)
            except Garbled as e:                     # a row the store cannot read is written whole: from nothing, under TORN
                items, idx = None, e.index
            new = mutate(dict(items or {}))
            if new is None:
                return dict(items or {})
            try:
                self.vars.put(path, new, cas=idx)
                return new
            except Conflict:
                cas_pause(attempt)                   # a random pause, growing: tried again at once, the same writers meet again
                continue
```

Прочитать, изменить, записать с версией прочитанного; `409` — прочитать заново. Ровно так же работала запись на одной коробке, где версию давал файл под блокировкой. Обещание то же — значит, и код тот же. Это и есть первое утверждение модуля, показанное запросами.

## Шаг 6 — Воркер пишет не туда: `403` до пересылки

Трасса — [`traces/02-a-worker-may-not-write-a-camera.txt`](traces/02-a-worker-may-not-write-a-camera.txt), и она короткая:

```
# vmsworker w-srv-a-1 on srv-a → /run/configstore/vmsworker.sock
POST /v1/write {"op": "put", "key": "vms/cameras/1", "cas": null, "items": {"name": "mine now"}}
→ 403 {"kind": "forbidden", "error": "vmsworker may not write vms/cameras/1"}
```

Сокет воркера разрешает писать его эпохи, его слот, его место — и ничего больше. Строка камеры — не его. Отказ приходит от хранилища, а не из кода воркера: даже воркер с ошибкой, даже воркер, в который кто-то пролез, не может переписать конфигурацию.

**Кто звонит, демон знает по сокету.** Сокет `vmsworker.sock` принадлежит группе `vms-vmsworker`, и открыть его может только процесс, чей юнит в этой группе (урок 5). **И спрашивает права демон того сервера, к которому пришли, до того, как что-то переслать или применить** (`storemachine.answer`):

```python
            key = check_key(body.get("key", ""))
            action = "write" if body["op"] == "put" else "delete"
            if not rights.allows(role, action, key):
                return fault(403, "forbidden", f"{role} may not {action} {key}")
```

Отказ не стоит записи в журнале и не доходит до лидера. Тест — `test_a_role_socket_on_a_follower_refuses_before_anything_is_forwarded` (`vmsserver/tests/test_configstore.py`): воркер на ведомом пишет строку камеры и удаляет эпоху, получает `Forbidden` оба раза, и номер фиксации у лидера не сдвинулся — запрос не покинул ведомого. Какие префиксы разрешены какой роли, откуда это берётся и как проверяется в обе стороны — урок 5. Проверка в самом процессе (`as_writer` у ручки) осталась вторым, клиентским рубежом, как у файлов: процесс, открывший не тот сокет, узнаёт об этом сразу.

## Шаг 7 — Смерть лидера под продлениями

Пока группа выбирает нового лидера, записи не проходят. А воркер каждые несколько секунд продлевает слот и аренду каждой своей камеры, и аренда, не подтверждённая дольше окна `lease_ttl − lease_margin` = 30 − 5 = **25 с**, запрещает ему писать камеру (`may_write` ложен, М10A, урок 6). Переживают ли аренды выборы лидера? Это было первым открытым вопросом записки, и на него ответили три замера.

**Как меряют.** Три демона на одной машине; сначала группа из одного, потом два сервера вступают. Тридцать настоящих `Worker` платформы — не модель — по десять на сервер, у каждого слот и восемь эпох: 240 аренд. Каждый продлевает так, как продлевает цикл воркера: шаг аренд, когда прошло `25 / 3 = 8,33` с, проверка раз в 2 с, — то есть раз в ~10 с; срок одного вызова хранилища — 5 с. На каждом сервере зонд пишет раз в 20 мс. Один заход: найти лидера, убить его `SIGKILL`, мерить, пока зонды двух выживших снова не запишут; поднять убитого на его журнале. Пауза записи — от убийства до первой успешной записи, начатой после него. Аренду можно потерять двумя способами, и замер считает оба: «потеряна» — `renew_leases` её отдал; «вышла за окно» — между двумя подтверждениями прошло больше 25 с, а потом пришло подтверждение с той же эпохой: воркер держит её дальше, но эти секунды запись стояла.

**Прототип курса** ([записка](../_notes-ru/raft-prototype.md), `pysyncobj`, до правки цикла воркера):

| Тайминги | Заходов | Пауза записи, с: мин / медиана / макс | Дольше всех без подтверждения, с (окно 25) | Заходов, где аренда вышла за окно |
|---|---|---|---|---|
| библиотеки по умолчанию, лидер убит | 25 | 1,01 / 1,79 / 3,53 | 12,9 | 0 |
| то же, лидер заморожен (`SIGSTOP`) | 20 | 1,10 / 1,43 / 3,03 | 11,4 | 0 |
| медленные: выборы 2–7 с | 25 | 5,04 / 7,92 / 11,94 | 29,7 | 4 |

**Демон курса** — `configstore` этого урока, с правкой цикла (шаг 8), `vmsserver/tests/configstore_election.py`, 10 убийств лидера на строку:

| Тайминги (`-tuning`) | Пауза записи, с: мин / медиана / p90 / макс | Дольше всех без подтверждения, с (окно 25) | Потеряно аренд | Вышло за окно | Продлений без ответа |
|---|---|---|---|---|---|
| `default` (библиотеки) | 1,19 / 1,35 / 1,64 / 1,72 | 11,28 | 0 | 0 | 0 |
| `lan` | 0,42 / 0,47 / 0,69 / 0,73 | 10,77 | 0 | 0 | 0 |

**Продукт** — `configstore` на `hashicorp/raft`, второй заход замера (три члена на петле, по 5 прогонов на строку; «дольше всех без подтверждения» — со старым циклом воркера → с новым):

| Режим, тайминги | Выборы, p50 / макс, с | Пауза записи, макс, с | Дольше всех без подтверждения, с: старый цикл → новый |
|---|---|---|---|
| `SIGKILL`, по умолчанию | 2,0 / 2,6 | 2,8 | 11,3 → 10,2 |
| `SIGKILL`, для локальной сети | 1,1 / 1,5 | 1,6 | 9,8 → 9,9 |
| `SIGKILL`, медленные (5 / 5 / 2,5 с) | 10,8 / 12,5 | 13,0 | **30,1** → 20,6 |
| остановка на 10 с, по умолчанию | 2,5 / 2,8 | 2,9 | 11,2 → 10,3 |
| остановка, для локальной сети | 1,1 / 1,3 | 1,3 | 10,6 → 10,3 |

Во всех прогонах продукта — ни одной потерянной аренды, ни одной потерянной подтверждённой записи, ни одного `ambiguous`; в каждом прогоне 26–38 повторов записи были отвечены из памяти идентификаторов операций, без единого конфликта.

Что из этого следует. С настройками по умолчанию и для локальной сети аренды выборы переживают с запасом больше чем вдвое: худший выживший воркер оставался без подтверждения 10–13 с из 25. С медленными таймингами — нет, и не из-за raft. Почему — следующий шаг. Для серверов продукт и курс берут настройки для локальной сети (`CONFIGSTORE_TUNING=lan` в `w2c.env`); аренды 30/5 и ожидание лидера 5 с не меняют.

## Шаг 8 — Находка замера: цикл воркера

Прототип убивал лидера с медленными таймингами и видел аренды без подтверждения по 29,7 с — дольше окна, — хотя пауза записи была до 12 с, а шаг аренд — раз в 10 с. Откуда ещё 8 секунд? Из цикла воркера. Вот его шаг аренд, каким он был (`vms/worker.py`, `run`):

```python
            try:
                if self.clock() - last_lease >= lease_every:
                    with self.guarded("lease"):
                        self.lease_pass()
                    last_lease = self.clock()
```

Две ошибки в двух строках. **Следующий шаг отсчитывался от конца предыдущего** (`last_lease = self.clock()` после `lease_pass`): шаг, который 9,6 с ждал хранилище, отодвигал следующий на те же 9,6 с. **И продление, которому хранилище не ответило, ждало целый период**, а не повторялось на следующей проверке. Пауза записи `P`, длиннее срока вызова `D` = 4,5 с, давала без подтверждения `≈ 2T + P`, где `T` ≈ 10 с — период шага, — и окно в 25 с пробивалось уже при паузе около 5 с.

Теперь шаг отсчитывается от **начала** предыдущего, а после шага с неотвеченным продлением следующий идёт на следующей проверке, через `poll` = 2 с:

```python
            try:
                if again or self.clock() - last_lease >= lease_every:
                    unanswered, started = self.unanswered, self.clock()
                    with self.guarded("lease"):
                        self.lease_pass()
                    last_lease, again = started, self.unanswered > unanswered
```

Без подтверждения теперь `≈ T + P + poll`, и окно выдерживает паузу до `25 − 10 − 2 ≈ 13` с при тех же 30/5. То же в цикле автоматизации (`vms/autoworker.py`); регистратор наследует цикл воркера. Тест — `test_the_next_lease_step_counts_from_the_start_of_the_last_and_a_step_unanswered_is_tried_again_at_the_next_look` (`vmsserver/tests/test_lease_step.py`): хранилище-фейк замолкает на 9,6 с ровно тогда, когда начинается шаг аренд, тот же воркер, то же хранилище, разный только цикл:

```
worst unconfirmed with a 9.6 s pause: before 29.6 s, after 21.6 s (window 25)
```

Продукт нашёл ту же ошибку в своём цикле (Go, `vms/worker.go` и `vms/live.go`): худший разрыв был `2 · 8,33 + 5 + 4 = 25,7` с при окне 25; после правки — не больше `8,33 + P + 4`. Это видно в его таблице выше: медленные тайминги, 30,1 → 20,6 и 25,7 → 22,5 с.

Урок отсюда: **срок вызова и период шага — части бюджета аренды, а не мелочи ручки.** Правка помогает не только raft: коробке на файлах, у которой задумался диск, тоже.

## Шаг 9 — Повтор записи применяется один раз

Во время выборов библиотека отвечает «лидер сменился» или «исход неизвестен» на команду, которую старый лидер уже добавил в журнал и которая ещё может пройти. Повторить её как новую запись — значит получить `Conflict` от собственной первой копии: первая копия сдвинула версию, и `cas` повтора уже не тот. А `Conflict` на продлении слота ограждает воркер.

Поэтому каждая запись несёт идентификатор операции — `id`, ручка делает его один раз на операцию (ниже), — демон повторяет команду с тем же `id`, а машина состояний помнит последние 50 000 ответов и на повтор отдаёт первый (клиентские сессии из диссертации Raft, § 6.3; `w2cplatform/storemachine.py`):

```python
    def _write(self, cmd: dict, index: int) -> dict:
        op_id = cmd.get("id")
        if op_id and op_id in self.done:
            return dict(self.done[op_id])
```

Решает машина только по команде и своему состоянию — никаких часов и случайных чисел, — потому что каждый член группы применяет тот же журнал и обязан прийти к тем же строкам; и память идентификаторов у всех забывает одинаково. Тесты — `test_a_write_repeated_with_its_id_is_answered_with_its_first_answer` (машина) и `test_a_write_retried_with_its_id_after_its_first_copy_landed_is_applied_once` (группа из трёх: повтор через другой сервер — тот же индекс, ничего не применено дважды). В замере продукта это и есть «26–38 повторов на прогон, отвеченных из памяти, без конфликта». `hashicorp/raft` этого сам не делает: это слой над библиотекой, и продукт его написал.

**Один `id` на операцию, а не на вызов.** Двенадцатое ревью запустило пробу: два вызова одного и того же `put` после оборванного соединения несли два разных `id`. Ручка делала новый на каждый вызов. А цикл аренд, получив `StoreAmbiguous`, просит ту же запись ещё раз — и если первая копия тем временем прошла, `cas` повтора конфликтовал с ней, то есть ограждал воркер. Теперь ручка помнит `id` записи, исход которой ей неизвестен (`_unknown`, по всему содержимому записи: операция, ключ, значения, `cas`). Та же запись, попрошенная снова, уходит с тем же `id` и отвечается один раз. Определённый ответ — индекс, `Conflict`, `Forbidden`, плохой ключ — `id` забывает; другая запись в тот же ключ — другая операция, со своим `id` (`w2cplatform/configstorevars.py`):

```python
    def _write(self, body: dict) -> dict:
        what = json.dumps(body, sort_keys=True)
        op_id = self._unknown.get(what) or uuid.uuid4().hex
        try:
            got = self._call("POST", "/v1/write", {**body, "id": op_id})
        except StoreUnavailable:
            self._unknown.keep(what, op_id)        # "not done" this time; an earlier copy may still land
            raise
        except BaseException:
            self._unknown.forget(what)
            raise
        self._unknown.forget(what)
        return got
```

Тест — `test_a_write_asked_again_after_its_outcome_was_unknown_carries_its_first_id_and_is_applied_once`: первая копия прошла, соединение оборвалось, тот же `put` ещё раз получает индекс первой копии, а не `Conflict`; проба ревью внутри теста — два оборванных вызова несут один `id`.

## Шаг 10 — Что обязан обещать фейк

Тесты модуля идут не на группе raft, а на стенде: одна машина состояний `StoreMachine` за дверями по ролям, в одном процессе (`tests/conftest.py`). Это тот же код, что применяет демон на каждом члене группы, тот же `storemachine.answer`, та же ручка `ConfigstoreVariables` — у стенда и демона нет двух реализаций, которые могли бы разойтись. А `tests/test_trace.py` прогоняет те же вызовы через настоящую ручку в настоящий unix-сокет маленького демона и сравнивает запросы с трассой.

Но стенду — и любому фейку хранилища — можно верить ровно настолько, насколько он держит **все** обещания настоящего хранилища. Их семь:

1. версия растёт в **одном журнале на весь кластер**, через все сокеты, и никогда не выдаётся дважды — ни после перезапуска, ни после выборов, ни после импорта (основание);
2. запись с числом в `cas` проходит, только если версия ключа сейчас такая, иначе — `409` с версией сейчас;
3. `"cas": ""` создаёт только отсутствующий ключ;
4. запись вне прав роли сокета — `403`, и до того, как что-то применено;
5. повтор записи с тем же `id` получает первый ответ и не применяется второй раз;
6. «не сделано» (`unavailable`), «неизвестно» (`ambiguous`) и «конфликт» — три разных ответа, и первые два — никогда не `Conflict`;
7. обрезанный или нечитаемый ответ демона — «не ответил», а не исключение, которое уронит поток воркера.

Седьмое нашлось на пятнадцатом убийстве лидера в замере прототипа: демон отправил заголовки и умер до тела ответа. `http.client.IncompleteRead` — это `HTTPException`, а не `OSError`; оно вылетело из `renew_slot` и убило поток воркера. Теперь обрезанное тело, тело не в JSON и закрытое соединение — `StoreUnavailable`, а для записи `StoreAmbiguous` (`test_an_answer_cut_off_by_a_dying_daemon_is_not_an_answer`). У `file://` такого класса ошибок нет — у файлов нет сети.

Первое обещание однажды нарушил старый фейк модуля, `FakeVariables` (он остался в `cluster/variables.py` для тестов, которым не нужны двери, и для М12). У него есть `as_writer(writer, allowed)` — тот же фейк, увиденный другим писателем. Сделано это копированием атрибутов объекта. Словарь записей при копировании остаётся общим, а счётчик версий был **числом** — и у каждой копии становился своим. Консоль и воркер писали в один словарь, но нумеровали записи каждый по-своему:

```
консоль:  put vms/cameras/1 → версия 1001
воркер:   put vms/epoch/1   → версия 1001      ← тот же номер
```

Чем это опасно? CAS сравнивает версию, которую процесс прочитал, с версией ключа сейчас. Если два разных изменения могут получить один номер, то процесс с устаревшей версией однажды попадёт на совпадение — и его запись пройдёт поверх чужой, без `409`. Ровно та потерянная правка, от которой защищает шаг 5, — и фейк бы её пропустил, а настоящее хранилище нет. Исправление — счётчик в общем списке, который копия разделяет, а не дублирует:

```python
        # ONE log for the whole cluster, shared by every writer's view of it: `as_writer` copies this object's
        # attributes, and an int copied is a second counter — two views then hand out the same version, and a
        # stale CAS can match a write it never saw. A list is shared by the copy; an int is not.
        self._log = [1000]
```

И тест, который держит это обещание и для стенда, и для фейка, — `test_every_writer_sees_one_log`: консоль, воркер и снова консоль получают три разных растущих версии.

Урок отсюда общий: **фейк проверяют против обещаний настоящего хранилища, а не против того, что тесты проходят.** С этой ошибкой все тесты модуля были зелёными.

## Шаг 11 — Двери между демонами: mTLS и пароль raft

Хранилище, до которого можно дотянуться по сети с трёх серверов, обязано само знать, кто к нему пришёл. В нём ключи домена, и демон, который принял бы `POST /v1/join` от кого угодно, отдал бы кому угодно всё хранилище. Поэтому аутентификация между процессами здесь перестала быть отложенной (урок 5 разбирает её целиком).

**Дверь `-api` — только взаимный TLS.** Одна CA на установку, `deploy/w2c-ca.sh` (в `vmsserver/deploy/`): `init` делает CA и общий секрет порта raft, `issue <сервер>` — сертификат демона сервера, который кладут в `/etc/w2c/tls`. Дверь требует клиентский сертификат этой CA с ролью `configstore` (`tls.require_role`): без сертификата не проходит рукопожатие, с сертификатом другой роли — `403`. Набирающий демон проверяет и сервер, к которому пришёл: сертификат CA, имя того сервера, которого он хотел, роль `configstore`. Без `-tls` демон дверь `-api` не открывает вовсе. Тесты — `test_a_join_is_refused_without_a_daemons_certificate`, `test_the_api_door_refuses_a_join_without_a_certificate_and_with_another_roles_certificate`, `test_a_daemon_dialling_another_checks_the_name_and_the_role_of_the_one_that_answers`, `test_a_daemon_will_not_open_its_doors_unprotected`.

**Демон на двери `-api` меняет группу только за свой сервер и не трогает строк.** Двенадцатое ревью: сертификат роли `configstore` имел все права — удалял слоты, писал схему, добавлял ложных голосующих и снимал членов. Теперь демону можно то, что демонам нужно друг от друга: `/v1/status` и `/v1/join` / `/v1/leave` за тот сервер, который назван в его сертификате (`configstore.StoreDaemon.serve`):

```python
            if role == PEER and node_id != peer:
                return 403, {"kind": "forbidden", "error": f"the daemon of {peer or 'no server'} may change the group "
                                                           f"for its own server, not for {node_id}"}
```

Прав на строки у него нет вовсе (урок 5). Запрос, который демон пересылает за процесс (так делает демон продукта: `hashicorp/raft` команды не носит), отвечается с правами **этого процесса** — его роль пересылающий называет в `X-Configstore-Forwarded`, и это роль из файла прав, никогда не `admin`. И вступление не оставляет голосующего, которого никто не запускал: id, который группа держит на другом адресе raft, или адрес, который держит другой id, — `409` (`RaftBackend.add`; то же для `join` оператора через `admin.sock`). Тесты — `test_another_daemon_changes_the_group_only_for_its_own_server_and_touches_a_row_only_forwarding` и `test_a_daemon_joins_only_as_its_own_server_and_no_join_leaves_a_voter_nobody_runs` (на настоящей группе из двух).

**Порт raft — пароль.** Узлы `pysyncobj` говорят между собой pickle, и открытый порт raft — это исполнение чужого кода для любого, кто до него дотянулся. Демон курса передаёт библиотеке `password=` из `/etc/w2c/tls/raft.secret` — она шифрует и аутентифицирует трафик (для этого нужен модуль `cryptography`). Секрет проверяется: если его могут прочесть другие (не `0600`) или он короче 32 символов, демон откажется стартовать. А соль PBKDF2 у `pysyncobj` одна на все установки мира, поэтому библиотеке отдаётся секрет, ключённый `ca.pem` установки (`tls.raft_secret`).

**Без секрета — только группа из одного на петле, и проверяется сокет, а не текст адреса.** Двенадцатое ревью запустило пробу: член группы, поднятый с `-raft 127.0.0.1:<порт>` без `-tls`, прошёл прежнюю проверку — она сверяла строку адреса со списком петлевых. А слушал он `*:<порт>`: `pysyncobj` без `bindAddress` слушает все интерфейсы, и pickle с сети исполнялся бы от имени хранилища. Теперь библиотеке передаётся адрес, на котором слушать (`bindAddress` — тот же адрес raft, разрешённый один раз). Без секрета этот адрес сначала связывается сокетом до того, как библиотека к нему подойдёт, и демон отказывает, если это не петля; соседи без секрета не допускаются вовсе (`RaftBackend.__init__`):

```python
        ip, port = _bind_address(raft)
        if not password:
            if partners:
                raise ValueError(f"{NO_SECRET}; this member was to start with {', '.join(partners)}")
            # The socket, not the address's text: bound to the address resolved, before the library is let near it.
            probe = socket.socket(socket.AF_INET6 if ":" in ip else socket.AF_INET, socket.SOCK_STREAM)
            try:
                probe.bind((ip, 0))
                bound = probe.getsockname()[0]
            except OSError as e:
                raise ValueError(f"the raft address {raft} is not this box's: {e}") from None
            finally:
                probe.close()
            if not _loopback(bound):
                raise ValueError(f"{NO_SECRET}; {raft} is {bound}")
```

А когда библиотека открыла порт, демон спрашивает уже её собственный слушающий сокет и останавливает её, если тот не на петле (`_open_only_to_this_box`). Такой член группы никого не принимает: `-join` без `-tls`, `join` оператора, старт с журнала, в котором записаны соседи, — отказ. Тесты — `test_a_member_without_the_raft_secret_listens_on_loopback_only_and_takes_nobody` (проба ревью: сокет на `127.0.0.1`, и `lsof` говорит то же), `test_a_raft_port_without_its_secret_is_refused_on_every_interface_but_loopback_before_it_opens` (`0.0.0.0` — отказ, и на порту так никто и не слушал), `test_the_raft_secret_is_refused_readable_by_others_or_short_and_is_keyed_by_the_installation`. Честно об оставшемся: группа из одного на петле без секрета открыта локальным пользователям этой машины — это решение курса для стенда, а не для площадки.

**У каждой двери демона — срок и предел.** Двенадцатое ревью: 200 простаивающих соединений к сокету роли — 203 потока навсегда, а `Content-Length: -1` превращался в `read(-1)` — чтение до конца соединения, которое вызывающий держит открытым. Теперь сокет роли и `admin.sock` обслуживают не больше `ROLE_CONNECTIONS` соединений сразу, а дверь `-api` — не больше `API_CONNECTIONS`, из них `API_PER_ADDRESS` от одного адреса. Следующее соединение получает отказ сразу и непрочитанным: `503 unavailable`, то есть «не сделано», и запись можно повторить; дверь `-api` его просто закрывает, потому что TLS ещё нет и отвечать не в чем. Строка запроса с заголовками должна прийти целиком за `HEADERS_WAIT`, тело — за свой срок с нижней границей темпа. Это `Deadlined` и `read_body` платформы, те же, что у остальных дверей. Длина, которая не неотрицательное число, — `400`, длина больше `MAX_BODY` — `413`, и тело не читается (`w2cplatform/configstore.py`):

```python
ROLE_CONNECTIONS = 64      # connections one socket (a role's, `admin.sock`) serves at once
API_CONNECTIONS = 32       # …the `-api` door: a few daemons, each with a join or a status at a time
API_PER_ADDRESS = 8        # …of which one address holds this many, so a stranger's handshakes do not fill it
HEADERS_WAIT = 5.0         # seconds a request's line and headers may take, whole
DOOR_TIMEOUT = 10.0        # seconds a door's socket waits on a caller that sends or reads nothing
MAX_BODY = 6 * MAX_VALUE + (64 << 10)   # a row at its ceiling, every character escaped (`\u00XX`), and its key
```

Тесты — `test_every_door_lets_an_idle_connection_go_and_serves_so_many_at_once` (сокет роли и `admin.sock`), `test_a_length_that_is_no_byte_count_or_past_the_ceiling_is_refused_unread_at_every_door` (и дверь `-api`), `test_the_api_door_serves_so_many_of_one_address_and_lets_a_stalled_handshake_go`. Порт raft — дверь библиотеки: сколько соединений она держит и сколько ждёт незнакомца, решает `pysyncobj`. Курс закрывает его секретом; в продукте — TLS и транспорт `hashicorp/raft` со своими сроками.

**Очередь сокета у ядра — тоже предел двери.** Тест выше падал примерно в трёх запусках из семи, и падал не на пределе, а раньше него: шестое из шести простаивающих соединений получало `ConnectionRefusedError` на `connect`, хотя дверь ещё ничего не приняла. Дело было в `socketserver`: двери открывались с его очередью по умолчанию, `request_queue_size = 5`, — столько соединений ядро держит, пока поток приёма их не забрал. На macOS unix-сокет с полной очередью отвечает на `connect` отказом сразу (проверено запуском: ядро взяло ровно пять); у TCP полная очередь роняет SYN, и клиент ждёт повтора секунду. Шестой вызывающий, пришедший раньше, чем проснулся поток приёма, дверью не считался и `busy` не получал. Теперь очередь равна пределу двери: сокет роли и `admin.sock` — `ROLE_CONNECTIONS`, дверь `-api` — `API_CONNECTIONS`. `listen` вызывается внутри `__init__` сервера, поэтому предел ставится до него (`w2cplatform/configstore.py`):

```python
    @property
    def request_queue_size(self) -> int:
        return self.limit
```

```python
        def __init__(self, path, handler):
            self.bound(ROLE_CONNECTIONS)             # before `listen`: the queue is as long as the bound
            super().__init__(path, handler)
```

Всплеск больше предела по-прежнему получает отказ ядра — это тоже «не сделано», и обработчик хранилища читает его как `StoreUnavailable`. Того же рода были двери консоли и двери между процессами (`console.Bounded`, М10A, урок 15). Тест: `test_configstorevars.py::test_a_door_queues_as_many_connections_as_it_serves_before_it_accepts_one`. Дверь, которая не принимает ни одного соединения, должна взять в очередь `ROLE_CONNECTIONS` подключений к сокету роли и `API_CONNECTIONS` к двери `-api`. На старой очереди тест падает на шестом подключении. Исходный тест после исправления прошёл 30 запусков из 30, до него — 25 из 30.

Скажем прямо, чего у демона курса нет. **В `hashicorp/raft` продукта на порту raft стоит TLS**, тот же сертификат кластера; в `pysyncobj` TLS нет — только общий пароль. **И у продукта есть `configstore recover`** — группа, пересобранная из журнала одного выжившего, когда большинство потеряно навсегда (`RecoverCluster`, процедура в `deploy/STORE-RECOVERY.md` продукта); у демона курса `recover` нет, и потеря двух серверов из трёх — это восстановление из резервной копии (`configstore restore`). К этому же списку: журнал `pysyncobj` не делает `fsync` перед подтверждением записи (переживает убитый процесс, но не отключение питания большинства), в ней нет пред-голосования и аренды лидера. Для курса библиотеки хватает — контракт зелёный, запись через ведомого ~1 мс, ни одной аренды за окном с таймингами по умолчанию, — а этот список и есть то, что продукт берёт у `hashicorp/raft` с `raft-boltdb`.

## Шаг 12 — Ничего больше не изменилось

Последнее — сами базовые классы М10A поверх хранилища кластера, без единой правки (`tests/test_lesson1_stores.py`):

```python
def test_m10s_base_classes_run_on_the_cluster_stores_unchanged():
    c = Cluster(); sub = Subsystem("thing")
    ctl = Controller(sub, c.vars, c.objects, wall=c.wall)
    w = Worker(sub, None, c.vars, c.objects, clock=c.clock, wall=c.wall, instance="A")
    assert w.claim_slot() == "w-1"
    w.heartbeat([{"id": 1, "phase": "running"}], server="srv-a")
    assert list(ctl.workers_seen()) == ["w-1"] and ctl.workers_seen()["w-1"].extra["server"] == "srv-a"
    ctl.assign("w-1", ["1"]); assert w.assignment().units == ["1"]
    assert w.take_epoch("1") == 1 and w.may_write("1")
```

Имя теста и есть утверждение. А четыре потока через `next_epoch` выдают номера `1..200` без единого повтора (`test_the_epoch_issuer_under_four_threads_on_the_clusters_store`): это и значит CAS по версии, откуда бы версия ни бралась — из блокировки файла или из журнала raft. И ещё строже — весь набор тестов контракта `Variables` (`vmsserver/tests/test_variables_contract.py`) против группы из одного и из трёх (`test_the_variables_contract_holds_on_a_configstore_group_of_one`, `…_of_three`) и через сокет демона.

Хранилище выбирается одной строкой окружения: `PLATFORM_STORE=configstore:///run/configstore/vmsworker.sock` в юните воркера (прежнее имя переменной, `CONFIG_URL`, тоже читается — `variables.store_url`). Схема `configstore` записана в `open_vars` рядом с `file` и `memory`. В `vms/` о хранилище не знает ни одна строка: при переходе на `configstore` в `vms/` поменялось одно место — `vms/__main__.py` теперь читает адрес хранилища через `store_url`. Цикл воркера поменялся тоже, но по находке замера (шаг 8), и эта правка верна и для файлов.

Объекты — heartbeat'ы, срезы снимка, отчёты прохода — в хранилище больше не живут: это файлы на сервере, который их пишет, и читаются они по всему кластеру через ресурсы. Как это устроено — урок 6.

## Результат

- Группа из трёх: `python3 -m w2cplatform.configstore status` на любом сервере показывает трёх членов и одного лидера; журнал на `/data`, сокеты по ролям в `/run/configstore`, дверь `-api` — только по сертификату кластера.
- Строки коробки перенесены в группу один раз, с `-index-base` выше её счётчика.
- `tests/test_lesson1_stores.py` и `tests/test_trace.py` зелёные: базовые классы М10A работают на хранилище кластера, а трассы уроков — это запросы настоящей ручки.
- Свой замер смерти лидера (`configstore_election.py`) и ответ, переживают ли аренды выборы с таймингами вашей сети.
- Трассы этого урока в `traces/`, и вы можете прочитать каждый запрос в них и сказать, какое обещание он проверяет.

## Что может пойти не так

- **Журнал не на `/data`.** После A/B-обновления сервер возвращается без памяти о группе.
- **Вступить вторым сервером и остановиться.** Группа из двух хуже одного сервера. Второй и третий — в один заход.
- **Импорт в группу, начатую без `-index-base`.** Импорт откажется целиком — и правильно: иначе версия, запомненная с коробки, однажды совпала бы с новой строкой.
- **Прочитать один раз и писать много раз с первой версией.** Каждая запись после первой — `409`. Пишите через `Controller.write`: он перечитывает.
- **Писать без `cas`, где он нужен.** Две консоли — одна потерянная правка, без единой ошибки.
- **Принять `503` за «нет».** `unavailable` и `ambiguous` — «хранилище не ответило»; воркер, бросивший камеры из-за выборов лидера, сделал отказ из паузы.
- **Повторить запись после `ambiguous` с новым `id`.** Первая копия могла пройти — повтор получит `Conflict` от неё. Ручка сама повторяет ту же запись с тем же `id`; запись, хоть чем-то другая, — новая операция, и перед ней перечитайте.
- **Медленные тайминги raft «для надёжности».** Каждая секунда выборов — секунда без записи на всех серверах. `lan` для серверов.
- **Открыть порт raft без секрета.** Демон откажется на любом адресе, кроме петли, и в любой группе больше одного — и правильно: pickle на открытом порту — чужой код у вас в процессе. Проверяется сокет, а не текст адреса: `127.0.0.1` в строке не значит, что библиотека слушает только петлю.
- **Положить `raft.secret` с правами `0644`.** Демон не стартует: секрет порта raft — пароль, его читает только владелец.
- **Верить фейку, потому что тесты зелёные.** Проверьте его против семи обещаний — иначе он пропустит ровно ту ошибку, от которой должен защищать.

## Итог

- Кластер — группа raft из трёх демонов `configstore`: первый — группа из одного, остальные вступают, запустив сначала свой демон; перезапуск — со своего журнала.
- Коробка остаётся на файлах; переход в кластер — один импорт в свежую группу, чьё основание выше счётчика коробки.
- API — `get`, `list`, `write` в одном формате; смысл несут `200` с версией, `409`, `403`, `400` и два разных `503`: «не сделано» и «неизвестно».
- Права спрашивает демон того сервера, к которому пришли, по сокету роли, до пересылки; `403` не стоит записи в журнале.
- Аренды выборы лидера переживают — по трём замерам — с настройками по умолчанию и для локальной сети; медленные тайминги пробивали окно из-за цикла воркера, и цикл исправлен: следующий шаг — от начала предыдущего, неотвеченное — на следующей проверке.
- Повтор записи несёт тот же `id` и применяется один раз.
- Фейк хранилища обязан держать все семь обещаний; стенд держит их потому, что это код самого демона.
- mTLS на двери демонов и пароль на порту raft — в курсе; TLS на raft и `recover` — у продукта, на `hashicorp/raft`.
- `vms/` смены хранилища не заметил: хранилище — это URL.

## Открытые вопросы

- **Не измерено:** разделение сети (лидер жив, но отрезан), отключение питания большинства, смерть лидера во время вступления нового сервера и окно 1 → 2 → 3, настоящая сеть вместо петли. Влияние TLS на выборы в продукте тоже не мерилось.
- **Журнал без `fsync`.** `pysyncobj` подтверждает запись, не сбросив журнал на диск: убитый процесс он переживает, отключение питания большинства — нет. У продукта `raft-boltdb` сбрасывает каждую пачку до подтверждения. В курсе это не исправить, не меняя библиотеку; не мерилось.
- **Одно чтение на все эпохи воркера.** Шаг аренд — это `K + 3` запросов подряд, при `CAPACITY=50` — 53 записи журнала на воркер каждые 10 с. Чтение нескольких ключей одной командой сделало бы шаг из трёх запросов. Это расширение контракта `Variables`, не только хранилища, и в этот заход оно не вошло.
