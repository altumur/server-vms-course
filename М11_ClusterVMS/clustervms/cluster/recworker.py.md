# recworker.py — the recorder as an allocation: М10's `RecWorker`, unchanged

**Role in the module.** Lessons 2 and 4. `ClusterRecorder(RecWorker)` is what `worker.py` is for the worker: М10's class by the name the lessons use, with the `env=` calling convention. The runtime hands it `SLOT_INDEX` (→ slot `r-<i>`, claimed by CAS on `rec/slots/*`), `SERVER_NAME` (the server it runs on), `LABELS`, `INSTANCE_ID`, `CAPACITY`. It takes a VOLUME — a declared one it may serve, by CAS on `rec/holds/*`, or its server's own, `$ARCHIVE/volume` — and opens it through the host's `obsd`. It holds no camera: each recording's pipeline subscribes to the worker's tee from the VMS heartbeat — `live_shm` (shared memory under `/run/vms`) when the worker is on the same server, `live_url` (RTSP) otherwise — and writes the stream `<recording>/e<epoch>` into its volume. It serves that volume at its archive door (`ARCHIVE_HOST:ARCHIVE_PORT`), which is where the console finds a camera's footage.

## Notes
- `tests/conftest.py::Cluster.recorder(index, server)` builds one with that server's `archive` and a session on the test run's one `obsd` (М10's fixture, loaded by path); each server's own volume is a directory of its own there.
- The jobspec is `deploy/recworker.nomad.hcl`: the archive constraint, `spread`, `rec/policy {servers: distinct}` by default; the rec controller (`python3 -m cluster reccontroller`) moves its recordings when its server dies — `test_the_power_pull_moves_the_recording_and_leaves_the_footage_where_it_was_written`: the footage written before the move stays in the dead server's volume, named unavailable on the timeline until a recorder holds that volume again; a restarted `r-1` on the same server picks up the writer the dead one left (`reattached`).
