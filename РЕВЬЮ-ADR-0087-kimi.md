## Находки

### A87-01 — существенная: построитель не проверяет пути отношений против формы — опечатка молча выключает норму

- **Место**: `source/DIALECT.md` §6 (требования нет), `source/build_common.py:725–743` (`load_references` разбирает путь, но не сверяет с формой; `node_at` существует — `build_common.py:164` — и используется только для умолчаний), `decisions/0087-…md` Confirmation (пункта нет).
- **Контрпример** (допустимый вход, проба 2, `probes.log`): меняю в `references.tsv` путь `placement.spread_by` на `placement.spred_by` → `python build_py.py` собирает без ошибки (exit 0); спека `placement: {capacity: {default: 1}, spread_by: nosuchfield}` при `unit.id: numeric` принимается `{'verdict': 'ok'}`, хотя обязана быть `refused:reference` (М10/2 Н1.4, строка `placement.spread_by`).
- **Нарушение**: драйвер ADR-0087:28 «форма записывается один раз и не расходится» — одна опечатка в источнике стирает норму без следа; ровно тот дефект, который CEL-записка (§3.5, довод 2) справедливо предъявляет старому references.tsv: «нет пути в документе — строка не применяется». Переименование ключа в форме без правки references.tsv — тот же случай.
- **Последствие**: норма молча перестаёт действовать во всех построенных загрузчиках и в построенном разделе урока; корпус это поймает только для 58 из 111 строк, остальные 53 неконтролируемы.
- **Рекомендация**: построитель обязан отказать источнику, в котором путь строки не находится в форме (как Kubernetes компилирует CEL-правило по схеме); добавить в Confirmation ADR-0087: «check_spec отказывает источник с путём отношения вне формы». Происхождение: свойство пилота C (новый артефакт); унаследовано по смыслу от references.tsv ADR-0085.

### A87-02 — существенная: образец null в scalars.tsv читает пустую строку как null — против Н1.1/Н1.2а

- **Место**: `source/scalars.tsv:4` — `null	null|Null|NULL|~|	…` (образец кончается на `|` — пустая альтернатива); `source/DIALECT.md` §7.
- **Контрпример** (проба 1, `probes.log`): `re.fullmatch('null|Null|NULL|~|', '', re.S)` совпадает; построенный `form.scalar_kind("")` → `'null'`, `resolve_plain("")` → `(None, True)` — «пустой простой скаляр — это null, в пределах».
- **Нарушение**: Н1.1 (`02-…norms.md` на срезе, `scalars null`): «пустое значение (`key:` без значения) — не null, а "сказанный ключ без значения": `refused:value` везде (Н1.2а), в том числе у `default:`». Источник, который ADR-0087 объявляет нормой (0087:44), говорит обратное. В пилоте поведение спасает слой текста (пустые значения идут отдельным каналом `empties`, DIALECT §5.1), но диалект этого не фиксирует: будущий интерпретатор/слой текста, читающий только scalars.tsv, получит норму «пустое — null».
- **Последствие**: расхождение реализаций на каждом `key:` без значения — самом частом отказе корпуса.
- **Рекомендация**: убрать хвостовой `|` из образца null (пустое значение в таблицу не доходит по устройству слоёв); в DIALECT §7 явно: «пустой скаляр таблицей не распознаётся — его видит слой текста». Происхождение: пилот C (новый артефакт).

### A87-03 — мелкая: description `secrets.reads` в источнике устарел относительно нормы (П2)

- **Место**: `source/spec.form.yaml:508` — `reads: {ref: grantList, description: точные имена или префиксы}`.
- **Цитата нормы** (`02-…norms.md` на срезе, Н1.2а): «`secrets.reads` — список `<семья>/<имя>` или префиксов с `/`, как `worker.reads`; голое слово — отказ value (добавлено пилотом варианта C, П2)».
- **Нарушение**: description — «смысл ключей» по ADR-0087 п. 1 (0087:43) и попадает в построенный раздел урока; форма уже исправлена (pattern `.*/.*`), слово — нет. Урок унаследует две разные формулировки одной нормы.
- **Рекомендация**: синхронизировать description (и заодно сверить остальные description с нормами среза одним проходом — после `ad3f1c1f3` это единственное замеченное расхождение, но проход был выборочным). Происхождение: пилот C; наведено запаздыванием источника за правкой норм.

## 7. Дополнительный материал: CEL-записка (оценка по поручению)

Записка `/Users/murat/Downloads/ПРЕДЛОЖЕНИЕ-ССЫЛКИ-И-СКАЛЯРЫ-СТАНДАРТОМ.md` (576 строк) предлагает: отношения — подмножеством CEL в `x-rules` прямо в схеме (как `x-kubernetes-validations`), исполнитель вместо построителя, скаляры — core YAML 1.2 + 3 отклонения, метасхему диалекта через `$vocabulary`. Важно: записка писана против **ADR-0085** (87 строк references.tsv + 46 слов, смысл которых живёт только в `refs.py`). ADR-0087 этот механизм уже заменил: у диалекта пилота C есть спецификация (DIALECT.md §6), ~14 проверок вместо 46 слов и нет `refs.py`. Поэтому сравнивать надо не с тем, что записка критикует, а с диалектом.

**Чем CEL лучше языка отношений пилота C:**

1. **Компиляция правил по схеме.** Обращение к несуществующему полю — ошибка компиляции, а не мёртвая строка. Это закрывает мою A87-01 «из коробки». У диалекта того же можно добиться одной проверкой в построителе — и это дешевле смены языка (см. рекомендацию A87-01).
2. **Правило несёт свой смысл и сообщение отказа** (`message`, `fieldPath`, `reason`). Строка диалекта `prefix_free values(worker.reads[])` короче, но смысл — в DIALECT.md; CEL-правило самодостаточно и снабжено текстом для автора спеки. Реальное улучшение читаемости.
3. **Нет повторов**: правила полей пишутся один раз в `$defs/fields`, у диалекта — 5 строк на unit + 5 на tables + must_match и т.д. (в references.tsv это видно по дублям строк 5–9 / 19–23).
4. **Стандарт со спецификацией и тестами совместимости; агенты его знают** (Kubernetes, protovalidate) — против довода «31 догадка». Довод весомый, но ослаблен: DIALECT.md — 117 строк и заморожен решением владельца; угадывать в нём почти нечего, а пилот показал 0 особых веток и 831/831.
5. **Скаляры через core YAML 1.2 + 3 отклонения** — точное наблюдение: наша таблица отличается от core ровно тремя строками (пустое ≠ null, bool в любом регистре, без 0o/0x). Ссылка на стандарт короче и надёжнее своей таблицы; вопрос про bool в любом регистре (записка §4) законный — это единственное отклонение без видимой причины.

**Чем CEL хуже / риски подмножества CEL:**

1. **Семантика ошибки.** В CEL ошибка вычисления ≠ `false` (записка §7 честно: «проще всего считать ошибку отказом того же класса» — это уже поправка к стандарту). У диалекта ошибочных вычислений нет в принципе: отсутствующий ключ определён всегда (`<=` — ложно, `@путь` — умолчание формы, `exists/absent`). Это строже и проще для чистой комнаты: не надо договариваться, что значит ошибка. Подмножество CEL без ошибок придётся определять самим — и это будет уже не CEL, а «наш диалект на синтаксисе CEL» со своей метасемантикой.
2. **Исполнитель — тот же объём, что интерпретатор диалекта.** Записка оценивает подмножество в ~15 конструкций; разбор языка отношений диалекта — ~260 строк (ADR-0087:68). Работа сопоставима, но у CEL типизация (int/double, динамические списки, `has()`-макросы, comprehension-переменные) заметно тоньше: риск «два исполнителя разошлись в угловом случае» выше, а проверочные тесты CEL покрывают полный язык, не наше подмножество. Библиотека CEL в загрузчик противоречит драйверу ADR-0087:29 («нет чужого кода, решающего вердикт») — значит, всё равно свой исполнитель; эталон `cel-expr-python` в check_spec возвращает проблему незакреплённых версий (моя A85-04) и чужого кода в инструменте.
3. **Длинные правила в корне.** CEL не видит родителя: правило, связывающее ветки, стоит в корне с полными путями (записка §7, признано). У диалекта строка привязана к пути — компактнее и локальнее; таблица references.tsv читается сверху вниз как Н1.4. В схеме правила рассредоточатся по `$defs` и корню — навигация «все отношения одним списком» теряется.
4. **Три слова всё равно не ложатся** (записка §3.3): `schema_depth` (нет рекурсии в CEL), `request_key`/`table_key` (разбор `{имя:int}` — нет извлечения по regexp в ядре). Остаются 2–3 своих слова диалекта — то есть «словарь перестаёт расти» (довод 6 записки) не достигается полностью: расширения будут, просто на стыке CEL и своих слов, который сложнее заморозить.
5. **Списки платформы как переменные CEL** (`PLATFORM_SHOWN`, `OBJECT_FAMILIES`) требуют окружения исполнителя — ещё один канал данных в диалект. Полезное замечание записки §9.3 независимо от CEL: оба списка сейчас зашиты в `refs.py` и их надо перенести в `platform_lists.tsv` при любом исходе (на срезе уже частично сделано: `9777e05c4` перевёл запрещённые имена на `object_families` из platform_lists.tsv).
6. **Метасхема `$vocabulary`** — роль «машинной проверки диалекта» у пилота уже играет построитель (`SourceError: words outside the dialect`, `build_common.py:251`); метасхема добавила бы проверку схемы стандартным инструментом, но своим построителем она достигается уже сейчас.

**Рекомендация по записке:** язык отношений диалекта на CEL не менять — выигрыш (самодостаточные правила, стандарт) не покрывает потерь (семантика ошибки, окружение списков платформы, длинные корневые правила, 2–3 своих слова всё равно остаются, свой исполнитель всё равно нужен), а диалект уже доказан пилотом с нулём особых веток. Перенять два независимых улучшения: (1) компиляционную проверку путей правил против формы — это A87-01, дешёвая и закрывает главный довод записки; (2) скаляры через ссылку на core YAML 1.2.2 §10.3.2 с тремя названными отклонениями вместо своей таблицы в прозе (таблица `scalars.tsv` при этом остаётся машинным видом тех же отклонений — и её образец null чинится по A87-02); заодно пересмотреть отклонение «bool в любом регистре» — если причины нет, норма станет строже и короче. Пилот CEL (объявлен отдельно) даст по этим пунктам фактуру; до него решение не пересматривать.
