### R21-02 — Проверка заполненности пропускает многострочные подстановки собственных шаблонов

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:99–101; S/assets/instructions.md:20–21,25–26,36–38; S/assets/norms.md:12–13; S/references/validation.md:18; S/references/templates.md:39.

Выражение `\{\{[^\n]*?\}\}` ищет только подстановку на одной строке, тогда как собственные шаблоны содержат многострочные заготовки.

Контрпример: в готовой инструкции оставить неизменными строки 20–21 из `assets/instructions.md`:

```text
{{Компоненты или результаты по нормам: процедура, команда, дверь — только если они действительно есть.
Описание выборов реализации и средство выполнения приёмки.}}
```

CLI возвращает **0 / PASS**. Контроль с однострочным `{{TITLE}}` возвращает 1. Следствие: обещанная проверка заполненности не обнаруживает незавершённую часть инструкции или канона после применения своих же шаблонов.

Основание: ADR-0080, дополнение 2026-10-15 (3), и заявленная проверка заполненности в validation.md:18; templates.md:39 требует убрать все `{{...}}` до публикации.

Рекомендация: обнаруживать многострочные незаполненные подстановки и закрепить отрицательную проверку на фрагменте поставляемого шаблона.

### R21-03 — Ссылки через Markdown-метки обходят проверку существования файла

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:102–111; S/references/validation.md:19; decisions/0080-лекции-как-спецификации.md:263–266.

Скрипт извлекает только ссылки вида `[текст](путь)`. Для обычной ссылки с вынесенным адресом он не проверяет путь и не сообщает, что форма не поддерживается.

Контрпример — заменить текст лекции временного комплекта на:

```markdown
# Example
[Нормы][canon]

[canon]: spec/missing.norms.md
```

Файла `missing.norms.md` нет, но CLI возвращает **0 / PASS**. Та же отсутствующая цель в форме `[Нормы](spec/missing.norms.md)` даёт код 1. Следствие: изменение записи ссылки скрывает её обрыв от структурной проверки.

Основание: ADR-0080, дополнение 2026-10-15 (3), прямо запрещает зелёный результат для неподдержанной ссылки; validation.md:19 обещает проверять относительные Markdown-ссылки. Показанная форма является [reference link по CommonMark](https://spec.commonmark.org/0.31.2/#reference-link).

Рекомендация: проверять ссылки с вынесенным адресом либо явно отказывать на неподдерживаемой форме, добавив отрицательную пробу отсутствующей цели.

### R21-04 — Незнакомая таблица приёмки не мешает PASS, если рядом есть знакомая

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:249–267,279–283; S/references/validation.md:27–28; S/scripts/test_check_spec.py:125–129.

Выбор проверок определяется наличием `scenarios.tsv` или `verdicts.tsv`. Неизвестный формат приводит к ошибке лишь тогда, когда обеих знакомых таблиц нет. Дополнительные таблицы не перечисляются и остаются без проверки и предупреждения.

Контрпример: сохранить корректную `scenarios.tsv`, добавить `assertions.tsv` с новым форматом и в README назвать обе таблицы обязательными, сославшись на `[assertions.tsv](assertions.tsv)`. CLI возвращает **0 / PASS**, проверив только знакомую таблицу и существование ссылки. После удаления `scenarios.tsv` тот же незнакомый формат уже даёт код 1 — именно этот более узкий случай покрывает существующий тест.

Последствие: автор может дополнить приёмку новым видом данных, а результат останется зелёным без предусмотренного расширения проверки. Оговорка о ручной проверке семантики не сообщает о полностью пропущенном формате.

Основание: ADR-0080, дополнение 2026-10-15 (3): новые форматы требуют добавления проверок и не дают зелёного результата без поддержки; то же записано в validation.md:27–28.

Рекомендация: обнаруживать неподдерживаемые таблицы и при наличии поддерживаемых, явно останавливать проверку или требовать определённого для них проверяющего правила.

### R21-05 — «Точное множество файлов cases/» проверяется только фильтром имён

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:196–205; S/references/validation.md:23; A02/README.md:9,17.

Множество `actual` строится через `glob("*.subsystem.yaml")`. Прочие файлы не видны, а совпавший с шаблоном каталог считается файлом случая без проверки его вида.

Два контрпримера одного дефекта инвентаризации: (1) к корректным `cases/` и `verdicts.tsv` добавить не названный в таблице файл `cases/unlisted.yaml`; (2) заменить перечисленный файл `cases/valid.subsystem.yaml` пустым каталогом с тем же именем. В обоих случаях CLI возвращает **0 / PASS**. Контроль с лишним файлом `unlisted.subsystem.yaml` даёт код 1.

Последствие: лишний файл с ошибочным суффиксом исключается молча, а вместо входных байтов может оказаться каталог. Это нарушает обещание проверки точного множества файлов до запуска загрузчика; разбирать намеренно неверный YAML для обнаружения ошибки не требуется.

Основание: ADR-0080, дополнение 2026-10-15 (3), и validation.md:23; A02/README.md:17 считает лишний файл несовпадением.

Рекомендация: сверять фактическое содержимое `cases/` с ожидаемыми путями, проверяя, что каждый случай — файл, и не скрывать неизвестные имена фильтром суффикса.

### R21-06 — Поле данных `$ref` принимается за ссылку OpenAPI

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:56–65,127–134; S/references/validation.md:20.

Функция `references()` рекурсивно считает любой ключ `$ref` ссылкой контракта, не различая узел схемы и произвольные данные примера.

Контрпример: в валидный временный OpenAPI добавить `POST /example` с `requestBody.content.application/json`:

```yaml
schema: {type: object}
example: {$ref: "ordinary application data"}
```

У операции также задан обычный ответ 200. `openapi_spec_validator.validate()` принимает полный документ, но CLI завершается кодом **1** с `unresolved/unsupported $ref 'ordinary application data'`. Здесь `$ref` — строковое поле демонстрируемого JSON-запроса, а не внешняя ссылка, которую нужно загружать. Следствие: допустимый пример запроса делает контракт красным и вынуждает автора менять данные ради проверяющего скрипта.

Основание: ADR-0080, дополнение о нотациях и дополнение 2026-10-15 (3), требуют проверки OpenAPI 3.1. Поле `example` содержит значение примера по [OpenAPI 3.1, Media Type Object](https://spec.openapis.org/oas/v3.1.0.html#media-type-object), а не обязательный Reference Object. Находка относится к инструменту и примеру запроса, не к отложенным схемам ответов Н2.

Рекомендация: учитывать положение `$ref` в структуре OpenAPI/JSON Schema, не обходить значения примеров как схемы; сохранить отказ на настоящие неподдерживаемые ссылки и добавить положительную пробу поля `$ref` в данных.
