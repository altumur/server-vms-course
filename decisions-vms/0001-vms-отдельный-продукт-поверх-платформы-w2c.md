# ADR-VMS-0001. VMS — отдельный продукт поверх платформы w2c, работа на маке

## Context and Problem Statement

Класс системы: платформенная система (VMS как набор подсистем поверх платформы w2c).

Слово владельца 2026-11-08: «давай работа на 103 будет только по платформе», затем «собери всё это в первый ADR-VMS-0001 и на маке будем вести работу параллельно как отдельный продукт поверх платформы w2c». Архитектор снял VMS с планов сессий CT 103 (ADR-0083 доп. (146), main `fc187cb62`) и передал всё, что было, представителю владельца: `cammeta-sessions/architect-memory/reports/2026-11-08-vms-handoff-to-owner.md` (копия на CT 103 — `/home/pilot/cammeta-sessions/owner/vms-handoff-20261108.md`) (sha256 `4289e2e1432fdaeebf4aa85a7dc072920195e909d8d771527d25c21113fe2b65`).

Приём долей spec-vms после доп. (146) — у представителя владельца. Доли ADR-0129 `a8a982d24` и `ecb5b9cc4` влиты словом владельца в main `4928fbabb` (полная проверка `check_spec` до и после вливания — тот же набор: 6 ошибок платформы, 62 исключения).

* **Не закончено:** M3 — старый WIP `44f62fca9` (семь RU-файлов); шесть процедур уже вошли в принятый English16, остаётся V11.2. Грязное дерево `wt-vms-english-16` — история (`decisions/history/vms/`, `decisions/journal/vms/`), не кандидат.

* **Решения владельца** (по передаче spec-vms): граница продукта (место канона и будущего кода, пин w2c, состав приёмки, владельцы инструментов); целевой пин consolem — `0fbdd12` или другой; открывать ли работу V11 (английский источник, V11.2, кириллица); ревью VMS — по слову владельца; полные проходы, пробы, Quint и `backend` на камере — нужны входы (DriverPack, экземпляр камеры, пороги).
* **Реестр:** 15 открытых строк VMS (НЕТ НОРМЫ/РАСХОДИТСЯ) в `adr-norms.tsv` — снимок, не доказанные дефекты; часть закрывают сданные доли (`b70`, `9f95`), часть относится к прежнему контракту `/exports`.

Задача: как вести VMS дальше, не отнимая CT 103 у платформы и не теряя связи с платформой, на которой VMS стоит.

## Decision Drivers

* CT 103 и его сессии — только платформа (доп. (146)); VMS не должна ставить работу в их очереди.
* VMS стоит на платформе: читает её только из выгрузки `cammeta-specs` на закреплённом пине (ADR-0090 п. 2), изменения платформы просит файлом во входящих (п. 4).
* Боевая пригодность — приоритет №1 (ADR-0130): VMS получит те же требования, когда до неё дойдёт генерация.
* Ревью VMS — только по слову владельца (ADR-0129 доп. (24)).
* Общий репозиторий курса: реестры `decisions/adr-pipeline.tsv`, `adr-norms.tsv`, `check_spec` общие для Platform и VMS.

## Considered Options

* А. Оставить VMS в общем потоке курса под Архитектором на CT 103.
* Б. VMS — отдельный продукт в том же репозитории: своя серия решений ADR-VMS-NNNN, свой план, работа на маке; платформа — внешняя зависимость по закреплённому API.
* В. VMS — отдельный репозиторий.

## Decision Outcome

Выбран вариант «Б».

1. **Продукт.** VMS — отдельный продукт поверх платформы w2c. Уроки, нормы и формы остаются в `VMS/` этого репозитория; решения о VMS с этого дня — серия ADR-VMS-NNNN в `decisions-vms/`. Действующие ADR курса с долей VMS не переносятся и не переписываются: их VMS-шаги ведутся в плане VMS со ссылкой на ADR курса.
2. **Где и кто.** Работа идёт на маке. Писатель VMS — spec-vms (по белому списку ADR-0090 доп. (1)). Представитель владельца ведёт план VMS, принимает и вливает доли spec-vms (полная проверка `check_spec` без новых ошибок против main), ставит вопросы владельцу. Сессии CT 103 VMS не берут.
3. **Связь с платформой.** VMS читает платформу только из выгрузки на закреплённом пине и судится только по нему (ADR-VMS-0002). Новый пин платформы для VMS выбирает владелец. Нужна правка платформы — запрос файлом во входящие курса (`decisions/inbox/`) и строкой Архитектору; сама правка — работа платформы на CT 103.
4. **Ревью.** Ревью уроков и норм VMS — по слову владельца (доп. (24) в силе); новые ADR-VMS — тремя ревьюверами по правилу курса, когда владелец назначит.
5. **План VMS.** Файл плана VMS ведёт представитель владельца: первые пункты — приём ждущих долей spec-vms, разбор её остатка, ADR-VMS-0002 (API платформы для VMS), затем шаги ADR-0103 «VMS до первой генерации».
6. **Машина.** VMS не занимает CT 103. Если владелец вернёт CT 102 — он для VMS.

### Consequences

* Good, because платформа на CT 103 идёт без очереди VMS, а VMS не стоит, пока платформа занята.
* Good, because у VMS одно место решений и один план; граница с платформой становится явной (API, пин), а не общим деревом.
* Good, because не нужно переносить историю и инструменты: уроки VMS, `check_spec`, хуки границы остаются как есть.
* Bad, because общий репозиторий: правки реестров `adr-pipeline.tsv`/`adr-norms.tsv` с двух сторон дают конфликты вливания (уже были при вливании 0129).
* Bad, because две серии номеров решений (ADR-NNNN и ADR-VMS-NNNN) — нужно не путать при ссылках.
* Bad, because у VMS на маке нет своих судей и раннера на сервере: до появления машины приёмка VMS не исполняется, только проверки формы.

### Confirmation

* В `plan-roadmap.md` и планах сессий CT 103 нет пунктов VMS (Диспетчер, доп. (146)).
* `decisions-vms/` содержит ADR-VMS-0001 и следующие; план VMS ведётся отдельно и ссылается на ADR курса для их VMS-шагов.
* Каждое вливание доли VMS в main — с полной проверкой `check_spec`: набор ошибок не шире, чем в main до вливания.
* Ни одна сессия CT 103 не получает поручений по VMS (видно по окнам и журналу Диспетчера).

## Pros and Cons of the Options

### А. Оставить в общем потоке

* Good, because ничего не меняется в процессах.
* Bad, because противоречит слову владельца (доп. (146)); VMS снова конкурирует с платформой за CT 103 и за Архитектора.

### Б. Отдельный продукт в том же репозитории

* Good, because см. Consequences.
* Neutral, because реестры остаются общими.
* Bad, because конфликты в общих реестрах и две серии номеров.

### В. Отдельный репозиторий

* Good, because полная развязка, свои реестры и проверки.
* Bad, because нужно разделять историю, `check_spec`, хуки границы и выгрузку; VMS читает платформу из выгрузки, но правила и инструменты курса общие — их пришлось бы копировать. Можно вернуться к этому варианту позже, когда API платформы закрепится (ADR-VMS-0002).
