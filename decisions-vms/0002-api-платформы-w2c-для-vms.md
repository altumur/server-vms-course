# ADR-VMS-0002. Что VMS берёт из платформы w2c: вся выгрузка на закреплённом пине, VMS судится только по нему

## Context and Problem Statement

Класс системы: платформенная система.

ADR-VMS-0001 делает VMS отдельным продуктом поверх платформы w2c. Слово владельца: «подумай над ADR-VMS-0002, в котором предложи, что нам нужно взять из w2c в качестве API (не код)»; после разбора — «давай обсудим, нужно ли нам API» и «да» на вариант «пин вместо списка».

Факты (main `3623859ff`, `VMS/` без `ru/`): уроки VMS ссылаются на платформу так — P/03 491, P/06 482, P/02 230, P/08 194, P/04 111, P/01 99, P/09 51, P/05 35, P/07 17, P/10 16 ссылок; плюс общие договоры `Platform/common/contracts`, данные `common/data`, приёмка платформы, векторы, `id-map`, закреплённые версии. Ссылки — по номерам глав `Nk.m`, у P/02 и P/07 нет `req`-якорей (ревью Claude С5).

Главная находка ревью (Claude Б1, Codex С): `check_spec` судит VMS по **живой** платформе в main (451 ссылка с якорями, манифесты по P/02.1, семьи, формы дверей), а не по пину выгрузки, из которой VMS читает платформу (ADR-0090 п. 2). Любая правка платформы на CT 103 может покраснить VMS в main, а сессии CT 103 VMS больше не чинят (ADR-0083 доп. (146)).

Первая редакция предлагала явный список API с проверкой ссылок. Ревью показало: список почти совпадает с P/03, P/06, P/02 целиком, включает внутренние места норм (бюджет воркера, поздний слой) и неполон (нет P/03.1, P/06.6, P/09.2, приёмки платформы, точек расширения); журнал разницы по `req` невозможен.

## Decision Drivers

* VMS не берёт код платформы.
* Правка платформы не должна ломать VMS незаметно и не должна краснить VMS в main без её ведома.
* Кода VMS поверх платформы ещё нет: какое API на деле нужно, станет видно только с реализацией.
* Меньше ручного ведения: список, который надо держать вручную, устаревает.

## Considered Options

* А. API — вся выгрузка платформы на закреплённом пине; VMS судится только по пину; явный список — позже, по реализации.
* Б. Явный список API с проверкой ссылок VMS по нему (первая редакция).
* В. Отдельный пакет API: только OpenAPI, схемы, договоры.

## Decision Outcome

Выбран вариант «А» (слово владельца 2026-11-08).

1. **Что VMS берёт.** Всё опубликованное в выгрузке платформы `cammeta-specs` на закреплённом пине: нормы, формы, OpenAPI, схемы семей, общие договоры, приёмку, векторы, закреплённые версии. Не код: ни пакетов генераторов, ни реализаций платформы.
2. **Чем VMS судится.** Проверки VMS (`check_spec` в части VMS) идут по платформе **пина**, а не по живому main. Живой main — отдельная необязательная проверка «что сломается при следующем перепине», её краснота не блокирует main.
3. **Перепин.** Новый пин платформы для VMS выбирает владелец. Перед перепином — прогон проверок VMS на новом пине; что покраснело — список того, что изменилось в обещанном платформой. Это и есть журнал разницы API.
4. **Явный список API** — позже, когда появится реализация VMS поверх платформы: из того, что она фактически вызывает. Тогда же — вопрос взаимозаменяемости реализаций платформы (ревью Codex: приёмка платформы не проверяет общий двоичный интерфейс SDK).

### Consequences

* Good, because главная находка ревью закрыта: правка платформы больше не краснит VMS в main.
* Good, because никакого ручного списка; изменения видны при перепине прогоном, а не по памяти.
* Good, because платформа не замораживает внутренние места норм ради VMS.
* Bad, because пока пин не меняется, VMS может отставать от платформы; перепин делает расхождение видимым сразу и целиком.
* Bad, because `check_spec` надо научить судить VMS по пину (код инструментов — coord103-tools, по поручению Архитектора).
* Bad, because «любая реализация платформы» не обещается: пока это не проверяется приёмкой платформы.

### Confirmation

* Правка в main одной только платформы не меняет итог `check_spec` в части VMS.
* При перепине есть отчёт прогона VMS на новом пине до решения владельца.
* Ревью тремя ревьюверами; находки первой редакции разобраны (раздел «More Information»).

## Pros and Cons of the Options

### А. Вся выгрузка на пине

* Good, because просто и проверяемо.
* Bad, because граница широкая: VMS может опереться на что угодно в выгрузке; узнаем об этом только при перепине.

### Б. Явный список

* Good, because платформа знает свои обещания.
* Bad, because список почти вся платформа, замораживает внутренние места, неполон; журнал по `req` невозможен — ревью Claude С4/С5, Codex.

### В. Пакет API

* Good, because чистая поверхность.
* Bad, because VMS опирается на нормы поведения воркера и консоли, а не только на двери и схемы.
