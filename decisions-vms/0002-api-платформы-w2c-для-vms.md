# ADR-VMS-0002. Что VMS берёт из платформы w2c: явный список API, не код

## Context and Problem Statement

Класс системы: платформенная система.

ADR-VMS-0001 делает VMS отдельным продуктом поверх платформы w2c. Слово владельца: «подумай над ADR-VMS-0002, в котором предложи, что нам нужно взять из w2c в качестве API (не код)».

Сейчас граница — вся выгрузка: уроки VMS читают платформу из `cammeta-specs` на закреплённом пине (ADR-0090 п. 2) и ссылаются на что угодно в ней. По факту (подсчёт ссылок в `VMS/`, без `ru/`, 2026-11-08):

| P/06 Консоль кластера | 590 | 06.1 «Units door: rows, bodies, tables» (230), 06.4 «Requests and events» (103), 06.5 «Observations» (97), 06.3, 06.2, 06.7–06.9 |

Общие договоры `Platform/common/contracts` (64 ссылки; чаще всего `gate-and-pass`, `row-check`, `env-file`, `role-certificate`, `request-mark`, события, `group-of`), данные `Platform/common/data` (42), а также приёмка, векторы, `id-map`, закреплённые версии.

Проблема: при отдельном продукте любая правка платформы может незаметно сломать VMS, а платформа не знает, что из неё — обещание для VMS, а что — её внутреннее дело.

## Decision Drivers

* VMS не берёт код платформы: реализация VMS должна работать поверх любой реализации платформы, прошедшей её приёмку.
* Граница должна проверяться машиной, а не держаться на памяти сессий.
* Правка платформы, задевающая VMS, должна быть видна до смены пина.
* Боевая пригодность (ADR-0130): поведение под нагрузкой и при сбоях — тоже часть обещания платформы.

## Considered Options

* А. Оставить как есть: API — вся выгрузка платформы.
* Б. Явный список API платформы для VMS: перечень поверхностей с путями и якорями норм, проверка ссылок VMS по нему, журнал изменений API при смене пина.
* В. Отдельный пакет API: только OpenAPI, схемы семей и договоры, без норм реализации.

## Decision Outcome

Предлагается вариант «Б»; «В» — следующий шаг, когда список устоится.

**Что входит в API платформы для VMS** (предложение; уточняет spec-vms по фактическим ссылкам):

1. **Подсистема как единица поставки** — P/02.1 формат манифеста и строгий загрузчик, P/02.5 вывод прав, P/02.4 договор установщика (что VMS даёт установщику и что получает: юниты, развёртывание, обновление), P/02.3 — в части, на которую ссылается VMS.
2. **Договор воркера** — P/03.2–P/03.7: слот, эпоха, аренда, место; цикл согласования; пульс, записи, остановка, бюджет; просьбы и события; поздний слой (книги, воркер домена, токены). Это главная поверхность: подсистемы VMS — воркеры платформы.
3. **Договор контроллера и ресурса** — P/04, P/05 в части, на которую ссылается VMS.
4. **Данные** — P/01.1 словарь операций хранилища (строки, версии, CAS, guard, список) как модель данных, к которой VMS обращается через платформу (`configstore:///`), без прямого доступа к процессу хранилища; семьи данных и их схемы `Platform/common/data`, слои В7 `Platform/common/LAYERS.md`.
5. **Двери консоли и модуль консоли** — P/06.1 (дверь юнитов: строки, тела, таблицы), P/06.2–P/06.5, P/06.7–P/06.9 в части ссылок VMS; P/07 и `КОНСОЛЬ-МОДУЛЬ-ПЛАТФОРМЫ.md` — публичный договор модуля, на котором стоят оболочки подсистем `<sub>.shell.html`.
6. **Домен и агент** — P/08 (книги и индекс имён, назначение и правки, остальные главы по ссылкам), P/09.1 агент участника, P/10 в части ссылок.
7. **Общие договоры** — используемые файлы `Platform/common/contracts/*`, формат каталога отказов, `id-map`, термины норм `NORMATIVE-TERMS.md`, закреплённые версии `common/versions` (то, что обязано совпасть у реализаций).
8. **Боевые свойства** — нормы ADR-0130 тех уроков, что входят в список: пределы, сроки, поведение при сбоях. VMS опирается на них, а не на свойства конкретной реализации.

**Что не входит:** код и пакеты генераторов платформы, внутренние нормы реализации, не названные VMS, приёмка платформы как исполняемое средство (VMS использует её векторы и формы только там, где на них ссылается), русские зеркала.

**Как держится граница:**

* Список — машиночитаемый файл [TODO: место и формат — например, `VMS/common/platform-api.tsv`: урок, глава, якорь нормы или путь, с какого пина]. Его пишет spec-vms, принимает представитель владельца, Архитектор подтверждает, что перечисленное — обещание платформы.
* `check_spec` проверяет: каждая ссылка из `VMS/` на платформу попадает в список; ссылка вне списка — ошибка (сначала — отчёт, с долгом, который только уменьшается, как у теста границы).
* При смене пина платформы для VMS — разница API между пинами (по `req`-якорям и дельтам ADR-0122) в журнал; меняет пин владелец.
* Правка платформы, задевающая элемент списка, помечается в её ADR как изменение API для VMS.

### Consequences

* Good, because граница явная и проверяемая; платформа знает, что обещала VMS.
* Good, because VMS не зависит от кода и может стоять на любой реализации платформы, прошедшей приёмку.
* Good, because смена пина становится осознанной: видно, что поменялось в обещанном.
* Bad, because список большой (по факту — почти весь P/03, P/06, P/02) и его надо вести; первый проход дорогой.
* Bad, because VMS ссылается и на внутренние места норм (например, бюджет воркера, поздний слой): попав в список, они замораживаются для платформы — платформе станет труднее их менять.
* Bad, because `check_spec` придётся научить новой проверке, а до неё граница держится только на ревью.

### Confirmation

* Файл списка API есть и принят; `check_spec` по нему находит 0 ссылок VMS вне списка (или убывающий долг).
* При первой смене пина платформы для VMS журнал разницы API составлен до решения владельца.
* Ревью ADR тремя ревьюверами по правилу курса, когда владелец назначит.

## Pros and Cons of the Options

### А. Вся выгрузка

* Good, because ничего делать не нужно.
* Bad, because любая правка платформы может сломать VMS незаметно; платформа не знает своих обещаний.

### Б. Явный список с проверкой

* Good, because см. Consequences.
* Bad, because ведение списка и заморозка внутренних мест, на которые ссылается VMS.

### В. Отдельный пакет API

* Good, because чистая поверхность: OpenAPI, схемы, договоры — без норм реализации.
* Bad, because сейчас VMS опирается на нормы поведения воркера и консоли, а не только на двери и схемы; без этих норм пакет неполон. Имеет смысл после «Б», когда станет видно, какие нормы реально нужны.
