# ADR-VMS-0002. Что VMS берёт из платформы w2c: вся выгрузка на закреплённом пине, VMS судится только по нему

## Context and Problem Statement

Класс системы: платформенная система.

ADR-VMS-0001 делает VMS отдельным продуктом поверх платформы w2c. Слово владельца: «подумай над ADR-VMS-0002, в котором предложи, что нам нужно взять из w2c в качестве API (не код)»; после разбора — «давай обсудим, нужно ли нам API» и «да» на вариант «пин вместо списка».

Факты (main `3623859ff`; тот же итог на `6fe89fce7` и main `518eecf75`): уроки VMS упоминают главы платформы так — P/03 491, P/06 482, P/02 230, P/08 194, P/04 111, P/01 99, P/09 51, P/05 35, P/07 17, P/10 16 ссылок; плюс общие договоры `Platform/common/contracts`, данные `common/data`, приёмка платформы, векторы, закреплённые версии и `id-map` (он — история курса `decisions/history/platform/`, не часть выгрузки; ревью Claude М4). Подсчёт — текстовые вхождения, не число обязательств: `git grep -ohE 'P/(0[1-9]|10)(\.[0-9]+)?' <коммит> -- VMS ':(exclude,glob)**/ru/**'` (каталоги `ru/` исключены на любом уровне; ревью Kimi М1). Ссылки — по номерам глав `Nk.m`, у P/02 и P/07 нет `req`-якорей (ревью Claude С6).

Главная находка ревью (Claude Б1, Codex С4): `check_spec` судит VMS по **живой** платформе в main (451 markdown-ссылка из `VMS/` в `Platform/`, 71 из них с якорем — тот же подсчёт `git grep` без `ru/`, ревью Kimi М2; манифесты по P/02.1, семьи, формы дверей), а не по пину выгрузки, из которой VMS читает платформу (ADR-0090 п. 2). Любая правка платформы на CT 103 может покраснить VMS в main, а сессии CT 103 VMS больше не чинят (ADR-0083 доп. (146)).

Первая редакция предлагала явный список API с проверкой ссылок. Ревью показало: список почти совпадает с P/03, P/06, P/02 целиком, включает внутренние места норм (бюджет воркера, поздний слой) и неполон (нет P/03.1, P/06.6, P/09.2, приёмки платформы, точек расширения — ревью Claude С5, Codex С1, С3); журнал разницы по `req` невозможен (Claude С6).

## Decision Drivers

* VMS не берёт код платформы.
* Правка платформы не должна ломать VMS незаметно и не должна краснить VMS в main без её ведома.
* Кода VMS поверх платформы ещё нет: какое API на деле нужно, станет видно только с реализацией.
* Меньше ручного ведения: список, который надо держать вручную, устаревает.

## Considered Options

* А. API — вся выгрузка платформы на закреплённом пине; VMS судится только по пину; явный список — позже, по реализации.
* Б. Явный список API с проверкой ссылок VMS по нему (первая редакция).
* В. Отдельный пакет API: только OpenAPI, схемы, договоры.

## Decision Outcome

Выбран вариант «А» (слово владельца 2026-11-08), потому что он закрывает главную находку ревью без ручного списка, который ревью показало неполным и почти равным всей платформе.

1. **Носитель пина.** Файл `VMS/PLATFORM_PIN` — одна строка, полный SHA коммита курса, чья платформа (`Platform/`) обещана VMS; начальное значение `3d8b6a3a74bfa359d362c691bd645fe4c132eaad` (main в момент записи, коммит `30eb9d734`). Это пин коммита курса, а не выгрузки `cammeta-specs`: VMS сверяется с `Platform/` этого коммита. Нет файла или запись неверна — проверка VMS падает ошибкой, без отката на живой main и на `Platform/` рабочего дерева (ревью Kimi С1, Codex С4; Архитектор). Идентичность пина — этот один SHA: выгрузка `cammeta-specs` строится из коммита курса, так что пин коммита задаёт и её `Platform/`; для VMS он заменяет пин выгрузки ADR-0090 п. 2. Упоминания пина выгрузки `7a875c75` в уроках VMS — долг уроков: их приводят к `VMS/PLATFORM_PIN` писатели «Спецификации VMS» при первом перепине.
2. **Что VMS берёт.** Всё опубликованное в `Platform/` на коммите пина: нормы, формы, OpenAPI, схемы семей, общие договоры, приёмку, векторы, закреплённые версии. Не код: ни пакетов генераторов, ни реализаций платформы.
3. **Чем VMS судится.** Проверки VMS (`check_spec` в части VMS) идут по платформе **пина**, а не по живому main. Живой main — отдельная необязательная проверка «что сломается при следующем перепине»: её запускает представитель владельца перед перепином, итог идёт в отчёт перепина; её краснота не блокирует main.
4. **Перепин.** Новый пин платформы для VMS выбирает владелец. Перед перепином представитель владельца прогоняет на маке проверки VMS на новом пине; что покраснело — список того, что изменилось в обещанном платформой. Это и есть журнал разницы API. Сессии CT 103 ради VMS ничего не помечают и не подтверждают (ADR-0083 доп. (146); ревью Claude С7); единственная работа CT 103 по этому ADR — правка `check_spec` (план, шаг 3), точечным исключением ADR-0083 доп. (150).
5. **Явный список API** — позже, когда появится реализация VMS поверх платформы: из того, что она фактически вызывает. Тогда же — вопрос взаимозаменяемости реализаций платформы (ревью Codex С2: приёмка платформы не проверяет общий двоичный интерфейс SDK; тогда же развести совместимость по проводу, смысловой договор SDK и привязку конкретной реализации).

### Consequences

* Good, because главная находка ревью закрыта: правка платформы больше не краснит VMS в main.
* Good, because никакого ручного списка; изменения видны при перепине прогоном, а не по памяти.
* Good, because платформа не замораживает внутренние места норм ради VMS.
* Bad, because пока пин не меняется, VMS может отставать от платформы; перепин делает расхождение видимым сразу и целиком.
* Bad, because `check_spec` надо научить судить VMS по пину: это навык `skills/lesson-spec/scripts`, его правит только «Архитектор» (ADR-0080 доп. 14) — правку он передаёт coord103-tools явной целой задачей (ревью Kimi С2), на CT 103 это точечное исключение ADR-0083 доп. (150).
* Bad, because «любая реализация платформы» не обещается: пока это не проверяется приёмкой платформы; при смене реализации может понадобиться новая привязка и пересборка VMS даже при неизменном смысловом договоре (ревью Codex С2).

### Confirmation

* Правка в main одной только платформы не меняет итог `check_spec` в части VMS — после шага 3 плана; до него `check_spec` судит VMS по живому дереву (ревью Kimi М3).
* При перепине есть отчёт прогона VMS на новом пине (и проверки по живому main) до решения владельца.
* Ревью тремя ревьюверами; находки первой редакции разобраны (раздел «More Information»).

## Pros and Cons of the Options

### А. Вся выгрузка на пине

* Good, because просто и проверяемо.
* Bad, because граница широкая: VMS может опереться на что угодно в выгрузке; узнаем об этом только при перепине.

### Б. Явный список

* Good, because платформа знает свои обещания.
* Bad, because список почти вся платформа, замораживает внутренние места, неполон; журнал по `req` невозможен — ревью Claude С5, С6, Codex С1, С3.

### В. Пакет API

* Good, because чистая поверхность.
* Bad, because VMS опирается на нормы поведения воркера и консоли, а не только на двери и схемы.
