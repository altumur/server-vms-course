## Повтор

Из корня неизменного checkout указанной базы:

```sh
PYTHONDONTWRITEBYTECODE=1 /Users/murat/w2c/vms-nightly/venv/bin/python windows/m10-1-mutation-trial/probe.py
```

Команда повторно создаёт только артефакты этого окна и временные копии `Source` под `/tmp/m10-mut-*`; каждая копия удаляется после своего прогона.
Результат завершения пробы — отсутствие ошибки самого runner. Соответствие реализации приёмке читается из `summary.json` и `baseline/api.json`, **не** из exit кода runner.
Сохранённый `run.exit = 0` означает завершённую пробу с диагностированным красным baseline.
`summarize.py` отдельно пересобирает таблицы из сохранённых свидетельств, тесты не запускает.

## Что именно запускалось

- Общие [scenarios.tsv](../../Platform/01-store/acceptance/1/scenarios.tsv) и [README](../../Platform/common/acceptance/README.md) не изменены. Все 98 шагов, включая `ASSERT`, выполнены; ни одного заблокированного шага или ошибки транспорта.
- Каждую реализацию обслуживает отдельный Python-процесс с настоящим `StoreDaemon`, настоящим unix HTTP и сокетом роли `acceptance`. Права роли: read/write/delete только `acc/*`. Из runner не вызывается `storemachine.answer` или `StoreMachine.apply` напрямую.
- `$a` связывает **фактическое значение любого JSON-типа**. Следующий запрос получает то же значение: числовая версия не превращена принудительно в строку. Проверка Н1 «версия на проводе — строка» хранится отдельным слоем `shape` и не участвует в kill ratio.
- JSON-тело сравнивается целиком; текст `error` игнорируется, если его нет в ожидании. Поэтому лишнее поле `fault` в сц. 17 отмечено отдельным несовпадением точного JSON, а не неправильным HTTP-кодом.
- Unit отдельно запускаются штатным `Source/tests/run.py`: `test_variables_contract test_storemachine test_guard`. Это **46 существующих тестов**, не полный unit курса. `OBSD_BIN` задан; `CONTRACT_URL` и `W2C_PRODUCT_REF` сняты в дочернем процессе.
- Каждому мутанту соответствует ровно одна замена в одном из двух файлов; исходный checkout не меняется. Синтаксис проверен `ast.parse`, импорт и живой daemon API — реальным запуском. Невалидных мутантов: 0.
- Kill API — **новый** провал `(scenario, step, facet)`, которого нет в красном baseline. Уже красный baseline сам по себе не убивает мутанта. Полные новые facets — в `*/result.json`.
- `api-calls.json` фиксирует вызовы функций двух целевых модулей в daemon-процессе: различает исполненный участок и недостижимую реализацию. Это не процент покрытия строк или ветвей.
- Все 13 собственных daemon-процессов завершились `exit 0`; их PID и exit сохранены отдельно. Чужие процессы не останавливались. Временных копий и работающих процессов пробы после завершения нет.

## Артефакты

`inputs.json` — версия Python, база, SHA256 обоих исходников и общего TSV.
`results.json`, `summary.json`, `mutants.tsv`, `baseline-failures.tsv` — результаты и знаменатели.
`baseline/` и каталоги 12 мутантов — `api.json`, вызовы API, PID/exit демона, stderr, исходный unit-лог/exit и результат; у мутанта также `mutation.patch`.
`baseline/non-scoring-delete-witness.json` и `V12-file-delete-version/non-scoring-delete-witness.json` — контроль и отдельная диагностика повторной выдачи версии.

Это фиксированная проба из 12 заранее выбранных ошибок, аналог узкого ручного mutation testing. Она не заменяет полный поиск `mutmut`, проверку эквивалентности всех мутантов, испытание raft, сбоев питания или всех реализаций хранилища.
