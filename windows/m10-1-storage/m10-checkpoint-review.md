## P2: NativeAPI скрывает чужие имена при list

`Source/tests/storage_acceptance.py:251–252` фильтрует backend.list по
read ACL. М10/1:237 и storemachine.answer:385–390 требуют выдавать имена
и версии без прав чтения значений.

Воспроизведение на ОБОИХ backend: admin `put("other/row", {...})`; затем
`NativeAPI(store.as_writer("acceptance", ["acc/*"]))`
`GET /v1/list?prefix=other/` возвращает `200 {keys:{}}`, хотя backend.list
возвращает `["other/row"]` и ожидается `keys:{"other/row":"1001"}`.
Текущая TSV 21.6 не обнаруживает ошибку: чужих строк там не создано.

Рекомендация: убрать фильтр read; добавить отдельный regression с
непустым чужим префиксом, общую acceptance не менять без согласования.
Это ошибка notation executor, не backend ACL.

## P2: NativeAPI может перечислить отсутствующую строку с пустой версией

Те же `storage_acceptance.py:251–252`: names получены отдельно от get.
Детерминированная проба вызывает backend.list, затем удаляет найденные
строки, затем отдаёт список NativeAPI. Оба backend дают результат
`keys:{"acc/row":"", ...}`. По М10/1:239 конкурентная запись допускает
ключ со своей версией либо отсутствие; пустая версия — отсутствующая
строка (Н1), такого элемента в list быть не должно.

Рекомендация: в переводе names→versions включать только get с index!=0.
Полный snapshot и новая форма API для этой слабой согласованности не
требуются. Версию брать только backend, не синтезировать в исполнителе.

## P2: Mem унаследовал файловый предел ключа

`Source/w2cplatform/variables.py:423–427` вызывает общий
storemachine.check_key, ограниченный KEY_BYTES=246 в кодированном имени
файла. `memvariables.py:112` теперь использует этот валидатор, включая
страж. До checkpoint Mem.put использовал safe_path и такого предела не
имел. `MemVariables().put("acc/"+"k"*296,{})` теперь ValueError
`longer than 246 bytes as a file's name`.

М10/1 Н1:73 задаёт 1024 bytes; исключение Н1:110 разрешает ранний отказ
именно реализации на файлах. Mem не хранит строку файлом. Это регрессия
Mem и конкретное расхождение с нормой; TSV проверяет лишь >1100 bytes,
поэтому зелёный прогон её не отличает от разрешённого файлового отказа.

Рекомендация: отделить общий валидатор Н1 от лимита имени файла; File
сохраняет собственный меньший предел, Mem — общий 1024. То же относится
к guard.key. Ключи платформы <200 bytes, поэтому обычные suites могут
оставаться зелёными. Новую wire/disk форму не предлагаю.

## Что проверено без новых находок

Replay выполняется внутри общей блокировки backend. Права текущего
вызывающего на target и чтение guard проверяются перед replay; отдельные
пробы подтвердили Forbidden и для ранее успешного id после отзыва прав,
и для guard, который прочитать нельзя. Повтор после изменения guard
возвращает прежний receipt, различающийся op/body/cas/guard под старым id
не применяется. Результат/входные items копируются. Guard проверяется
раньше target CAS под той же блокировкой. Delete сохраняет CAS/guard,
защиту epoch/domain и возвращает новую версию, включая absent target.

Retention хранит минимум 50000 ответов и не удаляет моложе 120 секунд;
старые не удаляются ради одного времени, пока не превышен минимум.
Срок жизни replay — процесс, без нового disk record, ровно принятое
решение. Разные File handles одного store делят replay, отдельные
процессы — только файл/lock, как явно описано. Порядок locks в reviewed
пути единый, инверсии не обнаружены.

TSV runner читает общий expected отдельно и не хранит id/receipt, не
рассчитывает CAS/guard исход. Он вызывает настоящий backend.write;
again приходит из receipt backend, не из expected. Это независимая
реализация backend от HTTP-machine по факту вызова; read/key grammar
разделяется с production helper как перевод HTTP-нотации. Найденные
list-ошибки показывают, что executor пока не полностью faithful.

Дополнительное наблюдение, НЕ новая регрессия checkpoint: File/Mem
проверяют ACL перед размером строки, поэтому одновременно oversized и
unauthorized put отвечает403, хотя поток М10/1:244–247 показывает
размер перед ACL. Такая последовательность была и на base; если
закрывается полная конформность, стоит явно сверить приоритет с нормой.
