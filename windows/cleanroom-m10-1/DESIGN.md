# Описание реализации М10/1 (Python 3.12, чистая комната)

Хранилище строк на одной коробке: состояние в памяти, долговечность — журнал на файле, дверь Н2 —
HTTP/1.1 на unix-сокете роли. Только стандартная библиотека. Номера пунктов «Решает реализация»
совпадают с `spec/01-storage.norms.md:279-289`; ссылки «журнал № N» — строки `GUESSES.md`.

## Устройство

| Файл | Что делает |
|---|---|
| `m10store/model.py` | Н1 и Н4: проверки ключа, `items`, `cas`, `guard`, `id` (чистые функции), отпечаток повтора, `Fault` закрытого списка, строгий разбор JSON |
| `m10store/store.py` | Н3: `Store.read / list / write` (запись и удаление — `write` с `op`), права, журнал, память повторов |
| `m10store/door.py` | Н2: `Door.dispatch` (маршруты, разбор тела, Fault → код) и `RoleServer` (сокет роли, предел тела до разбора) |
| `server.py` | запуск: каталог данных, сокеты ролей, предел тела, потолок строки |
| `tests/test_store.py` | проверки «чтением»: копии, перезапуск, порча, барьеры, блокировка, память `id`, гонки, края HTTP |

Запуск экземпляра приёмки:

```
python3.12 impl/server.py --data DIR --socket SOCK --role-prefix acc/ --body-limit 1048576 --row-ceiling 524288
```

`--config roles.json` задаёт несколько сокетов с ролями и правами `{prefix, read, write, delete}`.

API в процессе (М10/1-23): `Store(dir).read(rights, key)`, `.list(rights, prefix)`,
`.write(rights, model.parse_cmd(op, key, items, cas, guard, id))`; отказы — `model.Fault` с `kind`,
`status` и полями своей строки Н4, так что отображение на коды двери одно и то же.

## Решает реализация

1. **Неделимость и срок блокировки.** Один процесс на каталог данных (`flock` на `DIR/LOCK`, второй
   процесс не стартует). Внутри — один мьютекс (`threading.Lock`) на всё хранилище: чтение, перечисление
   и все шаги записи после «далее одной операцией» (повтор по `id`, страж, CAS, выдача версии, запись
   журнала, публикация в памяти) идут под ним (`store.py`, `Store.write`). Проверки формы, веса и прав —
   до блокировки, как в псевдокоде Н3. Срок ожидания блокировки — 2 с (`--lock-timeout`), по истечении —
   `503 unavailable`, ничего не записано; так же для чтения и перечисления (журнал № 13, 23). Группы
   серверов нет — урок 11.
2. **Версия.** Десятичный счётчик хранилища, первая версия — `"1"`, каждая сделанная запись и каждое
   удаление получают следующую. Счётчик не хранится отдельно: версия записана в каждой записи журнала
   (и в её рамке, которую можно прочитать даже у испорченной записи), снимок хранит последнюю выданную.
   После перезапуска счётчик продолжается с наибольшей версии, встреченной в журнале. Отказ версию не
   тратит. Вызывающему версия непрозрачна; внутри — число.
3. **Раскладка и барьеры.** `DIR/journal` — записи только дописываются:
   `R <index> <hlen> <blen> <crc32 заголовка> <crc32 тела>\n<заголовок JSON><тело>\n`; заголовок — `op`,
   `key`, `index` и, если был, `id` с отпечатком, временем и порядковым номером; тело — `items` у put.
   Удаление — тоже запись журнала, поэтому переживает потерю питания так же, как запись. Барьер: запись
   журнала → `fsync` (на macOS `F_FULLFSYNC`) → публикация в памяти → ответ. Создание журнала и замена
   его снимком — с `fsync` каталога. Снимок (компакция) — когда журнал больше 64 МиБ (проверяется при старте и после каждой записи):
   `journal.tmp` → `fsync` → `rename` → `fsync` каталога. Без барьеров — только при
   `M10_STORE_NO_FSYNC=1` в окружении, с предупреждением в лог.
   Отказы ввода-вывода: не удалось дописать запись — откат длины файла и `503 ambiguous` (ничего не
   опубликовано; журнал № 14); не удалось откатить — хранилище больше не принимает записей (`ambiguous`).
   Запись легла, но `fsync` отказал — строка публикуется (байты уже в файле и вернутся при перезапуске),
   ответ `503 ambiguous`; повтор с тем же `id` повторяет `fsync`: успех — первый ответ с `again: true`,
   снова отказ — снова `ambiguous` (Н4; журнал № 25).
4. **Предел длины ключа.** Строка не файл, имя файла от ключа не зависит, поэтому меньшего предела нет:
   1024 байта UTF-8 полного ключа, одинаково для целевого ключа и ключа стража (`model.KEY_LIMIT`).
5. **Повреждённая строка.** Порча видна при чтении журнала на старте. Испорчено только тело записи
   (CRC тела не сошёлся) — строка становится нечитаемой: чтение `{items: null, index: <версия из
   заголовка>, unreadable: true}`, перечисление и страж видят эту версию, запись с `cas` по ней заменяет
   строку. В лог (stderr): `journal: row '<key>' index <N> unreadable (body damaged at offset <off>)`.
   Оборванная последняя запись (не дописана до конца) отрезается с записью в лог — её `fsync` не
   завершился, её никто не видел. Испорчен заголовок или рамка записи в середине журнала — хранилище
   не стартует (`CorruptJournal`, в лог — смещение): без заголовка неизвестно, какой строке принадлежала
   запись, а старое значение этой строки выдавать за текущее нельзя. Порча файла во время работы
   замечается только при следующем старте: чтения идут из памяти.
6. **Память повторов.** `id` с отпечатком (sha256 канонического JSON `[op, key, items у put, cas, guard]`;
   отсутствующий и `null` `cas` — одно и то же, порядок полей `items` не важен, лишние поля команды и
   `items` у delete не входят) хранится в памяти и в журнале вместе с самой записью, поэтому переживает
   перезапуск и компакцию. Забывается запись, только когда она **и** старше 10 минут, **и** после неё
   применено больше 50 000 записей с `id` (журнал № 5) — это больше минимума Н3 при любом прочтении.
   Помнится только сделанная запись: отказанная (409, 412, …) с `id` в память не попадает.
7. **«Не добавлено в журнал» и «неизвестно».** Группы нет. На коробке: истёк срок блокировки —
   `unavailable` (до любого шага записи); запись не легла в журнал — `ambiguous` (журнал № 14);
   легла, но барьер отказал — `ambiguous`. Ожидание лидера 5 с — урок 11, здесь не применяется.
8. **Предел чтения HTTP-тела.** Флаг `--body-limit` (байты, по умолчанию 1048576), независим от
   `--row-ceiling` (по умолчанию 524288). Считаются байты тела HTTP до разбора JSON. При
   `Content-Length` больше предела тело не читается в память: остаток (до 64 МиБ) дочитывается и
   выбрасывается, ответ `413 {kind: toolarge, limit: <предел тела>, size: <Content-Length>}`,
   соединение закрывается; при `Expect: 100-continue` ответ уходит сразу, без `100 Continue`. Тело
   `chunked` считается по декодированным байтам; при превышении `size` не выдаётся (полный размер
   неизвестен). Тело не больше предела идёт к разбору JSON и проверкам Н3 (журнал № 24).

## Прочие выборы

- **Права и личность** (урок 6 и М10/6 в каталоге отсутствуют; журнал № 1–4). Роль определяется сокетом;
  права роли — правила `{prefix, read, write, delete}`, префикс сравнивается по байтам UTF-8. Чтение —
  право read на ключ; запись — write; удаление — delete; страж — read на `guard.key`. Перечисление прав
  не проверяет и отдаёт все совпавшие ключи. Проверки личности М10/6 (заголовки пересылки и т. п.) нет.
- **Разбор запроса** (журнал № 7–12, 26, 27). Query — процент-декодирование, `+` буквален; `key` —
  ровно один, UTF-8. JSON — строгий RFC 8259: повтор имени, `NaN`, BOM, неверный UTF-8 — `badrequest`.
  Порядок проверок команды: объект → `op` → `key` → `items` (put) → `cas` → `guard` → `id` → вес →
  права. Строка запроса HTTP длиннее 64 КиБ и любая ошибка разбора HTTP — `400 badrequest`. Любой метод
  и путь вне трёх маршрутов — `404 badrequest`.
- **Ответы.** `Content-Type: application/json`, компактный JSON UTF-8, `keys` перечисления — в порядке
  байтов UTF-8 (сортировка строк Python по кодовым точкам совпадает с порядком байтов UTF-8). Текст
  `error` — постоянный, без присланных данных и без ключа.
