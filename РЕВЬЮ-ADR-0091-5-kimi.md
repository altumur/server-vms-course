## Проверено без находок (закрытие блокеров и существенного)

- **Блокер «удержание без предела доставки» (Codex R91.4-02) — закрыт верно.** `not_after` — условие уровня хранилища (лидер принимает в журнал по своим часам, иначе `expired`), а не срок прикладного уровня: это единственная форма, закрывающая запись, принятую в путь до конца окна. Арифметика сходится: `not_after` = `at` + `valid_for` + 60, `keep` = `at` + `valid_for` + 120; запись, принятая до `not_after`, по журналу раньше любого физического удаления (не раньше `keep`), значит повтор падает на CAS `""`; опоздавшая — `expired`. Зазор в 60 между `not_after` и `keep` покрывает расхождение часов лидера и контроллера (предпосылка ≤ 60 с, P/08.2:109 — названа в тексте). Альтернатива «надгробия навсегда» отвергнута обоснованно (рост без предела, против ADR-0067).
- **Блокер «удаление в обход `keep`» (Codex R91.4-01) — закрыт.** `keep` распространён на любое физическое удаление — контроллер (`delete_after`, `ends`) и `worker.deletes` адресата (проверка в библиотеке); Confirmation требует сценарий «при удалении воркером адресата».
- **Claude Ч-2 (физическое удаление против ADR-0067) — закрыто.** Id `<заказчик>-<key>`, шаблон `key` — существующий механизм P/02.1 Н1.4 (`{поле}` / `{поле:int}`), называет все `fixed` и `about`, однозначен (проверка загрузчиком — названа Т-правкой); «вернувшееся имя — тот же предмет» — точно условие ADR-0067 доп. 2026-10-10. Отказ двери id с префиксом заказчика (400) не даёт оператору занять освобождённое `auto-7` другой камерой. Поправка правил 46–47 P/02.1 (сейчас: `delete_after` только без fixed/about вне id) названа явно.
- **Claude Ч-1 / Codex R91.4-03 (у надгробия нет времени) — закрыто.** `made.gone` ставит дверь по своим часам; запись над надгробием — событием позже `gone` + 60 (тот же допуск часов); сужение «событие в минуте после удаления — прежнее» названо сознательным.
- **Claude Ч-3 (надгробие в п. 3) — закрыто.** Действует состояние только живой строки; надгробие — осиротевшее; `guard.index` — версия надгробия (надгробие — та же строка с `deleted`, версия меняется при создании над ним — уборка отменяется).
- **Claude мелкие 1–4 — закрыты:** уборка — шаг прохода контроллера с чтением `<sub>/state/*` и правом `delete:<sub>/state/*` по P/02.5 при объявленном `unit.state`; `mask_from` не ссылка для уборки тел (P/06.1:618), `worker.reads` — существующий ключ (grantList); «значения не меняются — записи нет»; нечитаемое состояние — единица в шарде без него, счёт в отчёте прохода.
- **Kimi 1 ред. 4 — закрыта:** `valid_for` ≤ 3600 (потолок накопления) и `made_rows` в пульсе (наблюдаемость остатка).
- **Confirmation** пополнена всеми новыми механизмами: `expired`, удаление воркером адресата, надгробие (`gone` + 60), отказ двери id с префиксом, состояние надгробия, состояние в выдаче и снимке.

## Находки

### 1. Существенная — п. 1: судьба ручной строки по сроку у адресата с поправкой правил 46–47 не названа

- **Место:** decisions/0091-….md :73–75 («физически удаляются … только строки с `made` … ручные строки этого адресата физически не удаляются»).
- **Что не так:** поправка делает `delete_after`/`ends` загружаемыми у адресата с `fixed`/`about` не по id (сегодня — отказ загрузчика, правила 46–47 P/02.1). Для строки с `made` физическое удаление теперь безопасно (имя держит шаблон). Но для ручной строки такого адресата по сроку возможны только два исхода: надгробие — а контроллер «строку единицы не пишет никогда (`DeleteOnly`), поэтому надгробие ему не дать» (ADR-0067 доп. 2026-10-10, дословно); или контроллер её не трогает — и тогда `delete_after` молча не действует на ручные строки (P/04:143 обещает удаление любой строки без держателя дольше N с). ADR не называет ни того, ни другого; Confirmation не требует сценария «ручная строка просрочена». Две реализации разойдутся.
- **Контрпример:** оператор вручную завёл задачу `detjob` без срока-на-вечно; `delete_after` прошёл. Реализация А оставляет строку навсегда, реализация Б считает это нарушением `delete_after`. Поведение свидетеля (общий процесс убирал все задачи) не сохраняется ни в одном прочтении.
- **Источник:** ADR-0067 доп. 2026-10-10 (`DeleteOnly`, надгробие контроллеру недоступно); P/04:143; правила 45–47 P/02.1 (:804–806).
- **Рекомендация:** одна норма: «`delete_after`/`ends` к ручным строкам такого адресата не применяются, строка остаётся до удаления дверью» (и сценарий в Confirmation) — либо иной явный исход.

### 2. Мелкая — п. 1: отказ `expired` без HTTP-кода и группы повторяемости

- **Место:** decisions/0091-….md :51–53.
- **Что не так:** P/01.1 держит закрытый список отказов Н4 с нормированными кодом и советом вызывающему (`conflict` — перечитать и повторить; `guard` — не повторять). Для `expired` назван только `kind`; HTTP-код и группа («не повторять», как у `badrequest`) не названы — остаётся на Т-правку, но одна фраза в ADR зафиксировала бы семантику «не повторять с тем же `not_after`».
- **Источник:** P/01.1 Н4 (закрытый список, 01-store.md:150).
- **Рекомендация:** фраза: «`expired` — 4xx, не повторять с прежним `not_after`».
