## Проверено без находок (закрытие блокеров и существенного)

- **Блокер «две нестрогие границы» (Codex R91.5-01, Claude мелкое 4) — закрыт.** Удаление — только при часах строго позже `keep`; приём — при часах лидера ≤ `not_after`. При допуске 60 с: приём в худшем случае в реальном времени ≤ `not_after` − 60 (лидер впереди), удаление в худшем случае в реальном времени > `keep` − 60 = `not_after` (удаляющий позади) — интервалы не касаются, повтор в журнале раньше удаления, CAS `""` проваливается. Граничный случай «часы удаляющего = `keep` — не удаляет» вынесен в Confirmation. Предпосылка часов перенесена в P/01.1 «Время» как кластерная (лидер, контроллер, дверь, воркеры, писатель события) — верное место, ссылки на домен больше нет.
- **Блокер «цикл id» (Codex R91.5-02) — закрыт.** Поле-источник id исключено из требования `key`: библиотека заполняет его готовым id, шаблон, ссылающийся на него, — отказ загрузчика; согласовано с P/06.1 Н1.3 named (id из поля) — цикла нет, поле получает уже вычисленный id.
- **Блокер «неоднозначный `key`» (Claude Д-1) — закрыт конструктивно.** Подстановка кодирует `%`→`%25` и `-`→`%2D`, литерал `-` между подстановками тогда разделяет однозначно (разбор: сплит по `-`, раскодирование); `:int` — только к целым полям. Пример из Confirmation — (`7`, `1-x`) → `7-1%2Dx` против (`7-1`, `x`) → `7%2D1-x` — разные id, сходится.
- **Kimi 1 ред. 5 (ручные строки по сроку) — закрыта полностью.** Записано явно: «срок к ним не применяется молча нигде: `ends` снимает с размещения и не размещает, `delete_after` не удаляет, строка остаётся до удаления оператором дверью», счёт `expired_kept` в отчёте прохода даёт наблюдаемость; отличие от свидетеля (`jobs.forget_finished`) записывается в урок 05; сценарий «ручная строка с прошедшим сроком — снята, не удалена» — в Confirmation. Обхода ADR-0067 (DeleteOnly, надгробие контроллеру недоступно) не требуется — надгробие ручной строке не нужно, она не удаляется вовсе.
- **Kimi 2 ред. 5 (`expired`) — закрыта.** Группа `conflict` названа с уточнением «той же записью не повторяется» — согласуется с дисциплиной P/01.1 (новая попытка после перечитки условия разрешена: у заказчика это новое событие с новым `not_after`); исход `creates{expired}` в пульсе.
- **Claude Д-2 (`retire_when.delete_after`) — закрыт верно.** Срок законченной отсчитывается от снятия по `retire_when`, а не от «времени без держателя» — довод про `unplaced.delete_after` («удалил бы задачу, ждущую ёмкости, не начатой») верен: ожидание места — это время без держателя. Сценарий «задача, ждущая ёмкости, не удаляется» — в Confirmation. С `made.keep` связан («только когда часы строго позже `keep`»).
- **Claude мелкое 1 (сужение имён оператора) — закрыто:** называется в уроках 02, 04 и словами двери; строки с префиксом, созданные до объявления, остаются и заняты.
- **Claude мелкое 2 (поля `key` неизменяемы у строк с `made`) — закрыто:** «как `fixed`», сценарий правки поля `key` — в Confirmation; инвариант «имя держит шаблон» защищён.

## Находки

### 1. Мелкая — п. 1: кодирование `key` покрывает только `%` и `-`; судьба полей со знаками из refused-списка named id не названа

- **Место:** decisions/0091-….md :38–41 (однозначность построением: кодируются `%` и `-`).
- **Что не так:** named id отвергает `/`, `\`, `|`, `"`, `,`, управляющие знаки и пр. (P/06.1 Н1.3 refused). Значение поля `key` с таким знаком пройдёт кодирование без изменений и даст id, который откажет дверь/хранилище при записи заказа — поздно и молча для заказчика. Правило «какие поля допустимы в `key`» (проверка загрузчиком по типу/границам поля или полное кодирование refused-знаков) не названо.
- **Контрпример:** поле `cam` допускает значение `a/b` (тип string без enum); `auto` создаёт `rec/auto-a/b` — отказ `badkey` при записи, заказ потерян без диагностики в манифесте.
- **Источник:** P/06.1 Н1.3 named.refused; P/02.1 Н1.4.
- **Рекомендация:** одна фраза: поля `key` — только те, чьи значения внутри азбуки named id (проверка загрузчиком), либо кодирование расширяется на все refused-знаки.
