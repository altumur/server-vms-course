# P/06.8 — Cluster folders: norms

This English text is the source; the Russian translation `ru/spec/06.8-console.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 6.8 of lesson P/06 «Cluster console» (the cluster console; ADR-0096 with the amendments of ADR-0097 §5–§6, ADR-0099 §3–§4). Lecture (`ru/06-console.md`, for people, not in the export),
[contract](06-console.api.openapi.yaml), [instructions](06-console.README.md), [life cycle](../lifecycle.md),
[acceptance](../acceptance/8/README.md).

A folder is a record of the cluster console: it has an `id`, a name, a parent and an ordered member list. A folder groups units and inherits
nothing. The member list of a folder row and the reverse membership of a unit row are two sides of one link: one batch always writes them both.

The chapter rests on norms introduced earlier: the unit door and the batch — [chapter 6.1](06.1-console.norms.md), request parsing and the common
codes — [chapter 6.5](06.5-console.norms.md), the gate — [the gate and pass contract](../../common/contracts/gate-and-pass.md),
`may` — [the contract](../../common/contracts/may.md), the store batch — [P/01.1](../../01-store/spec/01.1-store.norms.md). A reference
«chapter 6.K» is a chapter of this lesson. Norm ids are `P/06.8-MM`;
the record of new ids is `id-map.tsv` (historical record).

### N1.1 Folder row and membership row

<!-- req: P/06.8-R003 -->

```yaml
platform/folders/<id>:                       # writer — the cluster console
  id:       128 random bits, 32 lowercase hex; one segment of the path and of the key, without parsing or case conversion
  name:     not empty, at most FOLDER_NAME_MAX bytes of UTF-8; no uniqueness among siblings
  parent:   id of the parent or "" — the root of the cluster
  members:  references <sub>/<rows>/<id> in order, without repeats; a unit can stand in several folders
  deleted:  "true" — a tombstone; a live row has no such element
platform/memberof/<sub>/<rows>/<id>:         # writer — the cluster console; the key is the reference to the unit under the prefix platform/memberof/
  folders:  ids of the folders where the unit stands as a member, without repeats, from 1 to FOLDERS_PER_UNIT_MAX; there is no empty list — the row is removed
```

The id is random because the grants `folder:<id>` live at the domain holder longer than the cluster: a counter would give an old grant row someone
else's folder after a reinstallation. Hex is chosen as a form without parsing: the segment needs no encoding either in the path or in the key, and `folder:<id>`
in a grant row does not intersect with `*` and other scopes. The id does not repeat: the console chooses it itself, the caller does not set it.

A reference to a unit is the full key of its row. The membership key is longer than the unit key by the 18 bytes of the prefix `platform/memberof/`.
Therefore a unit whose key `platform/memberof/<ref>` does not pass the key rules of P/01.1 N1 (the limit of 1024 bytes) is never
a member: `400 bad member`. The key cannot be shortened (chapter 6.1 N3 «Full keys and store refusal»).

**Who can be a member.** A unit of `unit.rows` of a subsystem whose manifest declared `display.tree.folders: true`
([P/02.1](../../02-installer/spec/02.1-installer.norms.md) the summary table of keys; [chapter 6.5](06.5-console.norms.md) N1.2 `tree`). Rows of tables
are never members. This way the platform does not know the kinds of subsystems, and a subsystem has one answer to the question of what lies in a folder.

**Link invariant.** `U` stands in `F.members` if and only if `F` stands in `memberof(U).folders`, for any row `F`
without a tombstone. Only the batch holds it: no write of the chapter changes one side without the other, except for two windows: a unit
deleted past the door — the unit's side is already dead; and a non-live folder that the batch removed from `memberof(U)` (N3 «folder rows in a batch» step 6) — the folder is not visible. The reaper removes both links (N3 «folder reaper»).

### N1.2 Nesting and tombstone

<!-- req: P/06.8-R004 -->

- The parent is set only at creation. There is no edit of the parent: `parent` in the body of `PUT` — `400 bad folder`, the field `/parent`.
- A new folder has no descendants, and its parent is older than it and set forever. Therefore a cycle cannot exist.
- Depth is the number of folders in the chain from the folder to the root, the folder included. A root folder has depth 1. Depth is at most
  `FOLDERS_DEPTH_MAX`.
- Deletion writes a tombstone: `{name, parent, members: [], deleted: "true"}`. The row is not removed: the version of its index is needed by the feed
  ([chapter 6.1](06.1-console.norms.md) N2 «Change feed»), and the `id` does not repeat, so there is no one to resurrect the folder or to occupy its key anew.
- **A write over a folder tombstone is a refusal.** The rule of ADR-0094 addendum (3) item 9 on a write over a tombstone does not apply to the family
  `platform/folders`: a resurrected folder would bring back a subtree that is already deleted as seen from outside.
- **Live folder** — a row without a tombstone whose whole chain to the root is without tombstones and without gaps. Only a live folder is given out
  by the read doors. An unreachable row does not exist from outside until the reaper removes it.
- There is no inheritance: neither rights nor fields pass from a folder to its members. The scope `folder:<id>` — [the `may` contract](../../common/contracts/may.md).

### N1.2a Domain member (ADR-0110 addendum (5) item 3, ADR-0111 item 13)

<!-- req: P/06.8-R005 -->

This chapter is about a cluster outside a domain. A cluster in a domain (`domain trace`, P/06.3 N1.8) has shared folders, held by the domain ([P/08.5](../../08-domain/spec/08.5-domain.norms.md) N1.8):

- `platform/folders/<id>`, `platform/memberof/…` — a copy, written by the agent ([P/09.1](../../09-agent/spec/09.1-agent.norms.md) N1.5 `folders`); `members` of a row are only units of this cluster: `GET /folders` shows its own ones, a member has no full member list. The folder reaper does not walk as soon as the copy exists.
- Reading — the former doors over the copy, `may` and `chains` — over the copy: a chain is judged by `memberof` and `parent`, `members` is a display. The agent writes top-down: first the folder rows, then the membership, and removes in reverse order, so `memberof` does not name a folder that does not exist.
- `POST /folders`, `PUT`, `DELETE /folders/<id>` — `409 folders are the domain's` as soon as the copy exists: the object `domain/folders-state`, `rev` not null, the console reads it; the object is confirmed absent or `rev` is null — the doors work as outside a domain; the object does not read or the read is not confirmed — the write is `503 unavailable`, nothing is written: folders and membership are edited by the doors of the domain [P/08.5](../../08-domain/spec/08.5-domain.norms.md) N1.8; no connection — a forwarding refusal, without the domain a folder is not edited.
- Rows of these families in `POST /console/batch` — `400 badkey`; creating a unit in a folder is two steps: the unit, then the membership.
- Deletion of a unit by the door — N3 «unit deletion by the door» as is; if `memberof(U)` existed, the same batch writes the row `platform/memberof-gone/<ref>` `{}`: a new unit with the same `id` does not inherit the folders, the agent's copy does not bring them back, the agent carries the reference in `gone` until confirmation. The key is longer by 5 bytes: the limit of N1.1 is counted by it.

### N1.3 Constants

<!-- req: P/06.8-R006 -->

The constants `FOLDER_NAME_MAX`, `FOLDERS_DEPTH_MAX`, `FOLDERS_PER_UNIT_MAX`, `FOLDERS_MEMBERS_MAX`, `FOLDER_ROW_MAX`, `FOLDERS_REAP_EVERY`, `FOLDERS_TRIES` are declared by [forms/runtime-constants.tsv](../forms/runtime-constants.tsv); the meaning and the dependent bounds remain this section.

`FOLDER_ROW_MAX` is a row-weight bound, not a serialized request-body bound. Every actually mandatory deletion request (target, done and other claim/auxiliary requests, separately) fits the store's actual entity-body ceiling B inclusively: compact JSON, UTF-8, required escaping, every metadata field and delimiter, plus the actual final LF. HTTP framing is excluded. All full keys, CAS/index/id/deadline strings/numbers, membership/gone rows, complete prepared unit/claim rows and guards are counted; auxiliary internal rows have no exemption from this ceiling. An8*64KiB items sum does not prove this obligation.

The accepted sufficient finite profile is checked **statically at installation and process start**, by [P02.3 N3](../../02-installer/spec/02.3-installer.norms.md#internal-finite-deletion-profile-adr-0127-p06-c2). The internal typed form is [`finite-profile.schema.json`](../../02-installer/forms/finite-profile.schema.json). B is actual Status.max_body, V is actual Status.max_value, F is FOLDER_ROW_MAX; no default is substituted. H bounds all encoded metadata after removing put items; each put is assigned once to a proved unit/tombstone, claim, three-field folder or empty-map category. Full finite metadata/multiplicity proofs give, for each packet:

`H + (n_unit+n_claim)*(12*V+7) + n_folder*(6*F+19) + 2*n_empty + LF <= B`.

The12V+7 bound counts worst string escaping and every field,6F+19 uses the folder's three fields; H includes deletes, all guards and framing inside the JSON entity. The8*n_unit folder expansion is not a bound for arbitrary member-list replacements or mixed batches: their permitted consequences need their own complete packet/multiplicity/category proof. Every other nonempty auxiliary family is counted by an explicit proved weight category. Unbounded/missing metadata, a missing packet/proof, or any bound>B refuses the profile before any installation write, `refused:form`; exactly B is admitted. This is not per-mutation admission, a new DELETE refusal or a dynamic bypass. A conservative profile can require a much larger B than the default1MiB; item weights alone cannot make deletion available. Existing caller batch refusals remain refusals of the whole batch, not a substitute for the static deletion obligation.

[`deletion-body-witnesses.json`](../forms/deletion-body-witnesses.json) records codec entities1048575/1048576/1048577, an extra LF and the same payload's ASCII-escaped encoding. The padded boundaries explicitly use V=1048576, not the default524288. Our escaping packet is1380972 bytes, not the reviewer's1380980; its450000-quote unit fits the default row ceiling. These are byte witnesses, not store execution or successful installation of a finite profile. The separate P02 profile witnesses exercise the sufficient bound and reject incomplete proofs; actual full production descriptors remain an implementation duty.

## N2 Doors

<!-- req: P/06.8-R007 -->

The doors are common, like `/console/batch`: they get no subsystem prefix, because a folder belongs to the cluster, not to a subsystem. The segment
`folders` is closed by the loader to the names of subsystems, units and tables ([P/02.1](../../02-installer/spec/02.1-installer.norms.md) N1.2a).
Request parsing — chapter 6.5 N2 «Console request parsing»; there are no deviations of its own. A refusal — the form and the rules of chapter 6.1 N2
«Refusal: `error` and `field`», the words — [`refusal-words.tsv`](../data/refusal-words.tsv), the door `folders`. The contract — [OpenAPI](06-console.api.openapi.yaml),
the paths `/folders`, `/folders/{id}`. Rights — N3 «folder rights», `need` — the gate and pass contract.

| Door | Request body | Success | Norm |
|---|---|---|---|
| `GET /folders` | none; the query `member=<ref>` is optional | 200 `{folders: [Folder…]}`, by `id` in UTF-8 bytes | N3 «read» |
| `GET /folders/<id>` | none | 200 `Folder` | N3 «read» |
| `POST /folders` | `{name, parent?}` | 201 `Folder` with an empty `members` | N3 «create folder» |
| `PUT /folders/<id>` | `{name?, members?}` | 200 `Folder` | N3 «edit folder» |
| `DELETE /folders/<id>` | none | 200 `{deleted: <id>}` | N3 «delete folder» |

`Folder` — `{id, name, parent, members, index}`: `parent` — as in the row, `""` at the root; `index` — the store index of the row, an opaque
string, compared only for equality. References to all members are given to the holder of the grant without a filter by the `view` of the units: otherwise `index`
would change from edits that the reader does not see. An unreadable row is the element `{id, garbled: true}` (the outcomes of the family).

Bodies are closed: another field — `400 bad folder`, `field` is that field. `POST` has no field `members`: the member list is set by `PUT`. The door `HEAD` — like `GET`
without a body (chapter 6.5 N2); another method — `405 method`; a path longer than `/folders/<id>` — `404 no such path`. A segment `<id>` not of 32 lowercase hex —
`404 no such folder`: such a folder cannot exist.

`If-Match` of `PUT` and `DELETE` is optional; the value is an index in double quotes, as `ETag` gave it ([chapter 6.1](06.1-console.norms.md) N2 «Versions»). A folder has no `revision`: a number, like any other value, — `400 If-Match is a unit revision` before
the row is read. The index has diverged — `412 folder moved`, the body `{detail, error, field: "/index", row: Folder}`: `row` — the current row; when there is no row, for a tombstone and without `view`, there is no such field. The answers of `GET /folders/<id>`, `POST`, `PUT` carry `ETag` — the index of the row, `DELETE` — the index of the tombstone.
`Idempotency-Key` of `POST`, `PUT`, `DELETE` is optional: the memory — as at the cluster doors of chapter 6.6, the claim `<CONSOLE_ROOT>/idem/<key>`,
another fingerprint — `422 key reused` (chapter 6.1 N3 «replay memory»). `done` goes as a write of the batch, as at `POST /console/batch`.

`GET /folders?member=<ref>` — the folders where the unit stands as a member, and `member: {index}` — the index of the membership row, `""` — there is no row.
This form is needed by a caller who builds a batch with a membership row himself (N3 «folder rows in a batch»): there is nowhere else for him to take the `cas`.
The reference is the full key of the unit, percent-encoded; not by the form — `400 bad member` without `field`.

### Folder rows in the batch door

<!-- req: P/06.8-R008 -->

`POST /console/batch` ([chapter 6.1](06.1-console.norms.md) N2) accepts the two families of this chapter: the caller writes a unit and its folders in one
operation.

```yaml
writes[]:
  - {op: put, key: platform/folders/<id>, fields: {members: [...]}, cas: <index>}   # only members, the member list whole; name and parent are not written by the batch door
  - {op: put, key: platform/memberof/<sub>/<rows>/<id>, fields: {folders: [...]}, cas: <index> | ""}
  - {op: delete, key: platform/memberof/<sub>/<rows>/<id>, cas: <index>}
guards[]:   the rows of the ancestor chain of each folder into which the batch adds a member; for a folder from which the member is only removed the chain is not guarded: a removal under a dead branch is harmless (ADR-0096 §2); the row of each added member if it is not in writes
```

Any other family `platform/*` — `400 badkey`, as before. `delete` of a folder row — `400 bad batch`: only the folder door deletes a folder. The order of the checks — N3 «folder rows in a batch».

The feed `/changes` covers the folder rows: [chapter 6.1](06.1-console.norms.md) N2 «Change feed». The callback list — the record `folders` ([chapter 6.3](06.3-console.norms.md) N1.9).

## N3 Procedures

<!-- req: P/06.8-R009 -->

A write is a store batch (`op: batch`, P/01.1): all or nothing, one index per batch. This is an internal batch of the console: it is limited by weight, not by
`BATCH_WRITES` (chapter 6.1 N1.4). The chain, the rights, the fingerprint and the claim are read before it; a break before the batch leaves nothing.

### chain(F) → rows from F to the root | refusal

<!-- req: P/06.8-R010 -->

```
1. F := the row platform/folders/<id>; while parent ≠ "": read the parent; a chain longer than FOLDERS_DEPTH_MAX → «unknown»: no door makes such a write
2. the read is not confirmed or the row is unreadable → «unknown»: 503 unavailable, nothing is written
3. there is no row                                → «none»
4. F or an ancestor has a tombstone               → «tombstone»
5. otherwise                                      → a live chain with the indexes of the rows
```

«unknown» is not «none»: an unconfirmed read gives neither a 404 refusal nor a removal by the reaper.

### read

<!-- req: P/06.8-R011 -->

`GET /folders` lists `platform/folders/`, gives out the live folders and reads each chain once from this same listing. A listing failure — `503 unavailable`, not
an empty list. `GET /folders/<id>` reads the chain: «none» and «tombstone» — `404 no such folder`, «unknown» — `503 unavailable`. This way the deletion of a subtree is atomic from outside at any
size: a subfolder of a deleted folder is 404 from the same instant.

`?member=`: a read of the membership row, then the chain of each of its folders; non-live folders are not given out, and `member.index` is the index of the row as is.

### create folder(body, key?) → 201 | refusal

<!-- req: P/06.8-R012 -->

```
1. form: the body is a JSON object → otherwise 400 not_json; fields, name, parent → 400 bad folder, field
   a key is present and not by the form → 400 Idempotency-Key required
2. a key is present: the claim — step 2 «create» of chapter 6.1
3. parent ≠ "": chain(parent):
     none → 404 no such parent; tombstone → 409 parent gone, field /parent; unknown → 503 unavailable
     depth of the chain + 1 > FOLDERS_DEPTH_MAX → 400 too deep, field /parent
4. rights — «folder rights»: create a subfolder in parent, or a root
5. batch: writes: a new row cas "", id — 128 random bits; the done claim with cas of its own version, if a key is present
          guards: each row of the chain of parent by the index read
6. succeeded → journal folder.created {id, parent, user, addr} → 201
   412 guard → 412 parent moved, field /parent, nothing is written
   413 → 413 row too large | batch too large
   unavailable, ambiguous, no answer → 503 store unavailable; its own pending remains, a repeat with the same key converges
```

Step 2 goes before step 3, unlike in the batch door. The reason: the right to a subfolder depends on the chain of the parent. A repeat after a lost answer could see the parent deleted and get
a refusal instead of the saved `201`. Therefore the refusals of steps 3–4 enter the memory, like the other answers `< 500` of the procedure.

### edit folder(id, body, If-Match?, key?) → 200 | refusal

<!-- req: P/06.8-R013 -->

```
1. form: body, fields, members → 400 bad folder, field; parent in the body → 400 bad folder, field /parent; If-Match and key → as in chapter 6.1
2. a key is present: the claim
3. chain(id): none, tombstone → 404 no such folder; unknown → 503 unavailable
4. rights over the folder → 403
5. If-Match is present and ≠ the index of the row → 412 folder moved
6. name and members coincide with the row → 200 with the current row: there is no write, the index does not change (the version promise)
7. member list: a repeated reference → 400 bad member, field /members/<i> of the second occurrence; members > FOLDERS_MEMBERS_MAX → 400 too many members, field /members
   for each added U (in the order of the body):
     U not by the reference form; the subsystem outside the catalogue; <rows> ≠ unit.rows; no display.tree.folders; the membership key not by P/01.1 → 400 bad member, field /members/<i>
     read the row of U: none or deleted → 400 bad member, field /members/<i>; the read is not confirmed → 503 unavailable
     read memberof(U): unreadable or not confirmed → 503 unavailable; already FOLDERS_PER_UNIT_MAX folders → 400 too many folders, field /members/<i>
   for each removed U: read memberof(U) the same way
8. rights to the added and the removed U — «folder rights» → 403; a removed U needs no read of its row if the may input does without it (the may contract)
9. batch: writes: the folder row cas the index of step 3; memberof of each added — put, the new folder at the end of the list, cas (no row — "");
                  memberof of each removed — put without F, and if F was the only one — delete, cas; the done claim with cas of its own version, if a key is present
          guards: the rows of the ancestors of F by the indexes of step 3; the row of each added U by the index of step 7
10. succeeded → journal folder.written {id, name?, added, removed, user, addr} → 200 with the new row
    412 guard on an ancestor → 412 parent moved, without a field; nothing is written
    412 guard on a unit, 409 conflict on memberof → from step 7 anew, at most FOLDERS_TRIES times, then 503 store unavailable; the unit is gone — step 7 answers 400
    409 conflict on the folder row: If-Match is present → 412 folder moved; absent → from step 3, at most FOLDERS_TRIES times
    413 → 413 row too large (the row weight > FOLDER_ROW_MAX or the store ceiling) | batch too large
    unavailable, ambiguous, no answer → 503 store unavailable
```

The row weight `FOLDER_ROW_MAX` is checked before the batch on the prepared row: `413 row too large`. Liveness is checked only for the added members. A dangling member that remains in the member list
gives no refusal: it comes into the body by a read, and a `400` on it would break a `PUT` of the name until the reaper removed the member.

**A new member goes to the end of the folder's list** for the writes of the batch door; in `PUT` the body sets the order.

### delete folder(id, If-Match?, key?) → 200 | refusal

```
1. If-Match and key — the form; a key is present: the claim
2. chain(id): none, tombstone → 404 no such folder; unknown → 503 unavailable
3. rights over the folder; role rows on the subtree → 403 («folder rights»)

          guards: the rows of the ancestors by the indexes of step 2

```

The devices remain: a folder does not own units. The batch does not touch subfolders: from this index they are unreachable, the reaper removes their rows and membership. An unreadable membership row is removed in the batch by `delete` with `cas`: the deletion
of the folder does not lose the unit, and such a row has already broken the link invariant.

### folder rights

<!-- req: P/06.8-R015 -->

A folder as an object of a write is the `may` input `unit = {sub: platform, id: F, labels: [], chains: [[F, ancestors of F]]}`, the `sub` of the check is `platform`. Creating a root — `unit = "*"`. The form of the input is held by
the `may` contract; here is what the door asks.

| Action | What is needed |
|---|---|
| create a subfolder in `P` | `admin` over `P` |
| create a root folder | `admin` on `*` |
| rename `F`, change the order of the members of `F` | `admin` over `F` |
| delete `F` | `admin` over `F`; if the copy of the grants has a role row `folder:` on `F` or its descendant — also `admin` on `*` in each `sub` of such rows; a row without `sub` acts in all subsystems and requires `admin *` without `sub`; a role row not by the form (`unread`) — as a row without `sub`, the right is not proven — 503 |
| add `U` to `F` (`PUT`, a folder row of a batch) | `admin` over `F` and `admin` on `U` in the subsystem of `U` |
| remove `U` from `G` | `admin` over `G` and `admin` on `U` in the subsystem of `U` |
| move `U` from `G` to `F` | `admin` over `G`, `admin` over `F`, `admin` on `U` |
| create a unit directly in `F` (the creation and the folder row in one batch) | `admin` over `F`; the right to create the unit — with the input `chains: [[F, ancestors of F]]` of the new unit |
| remove a member at the deletion of a unit | the right to delete this unit, there is no separate check of the folder and membership rows |
| read folders | `view` without a unit: any effective grant row, the `sub` of the check is empty |

- The right to `U` is judged by the member list **before** the write: `F` and its ancestors do not enter the `may` input for `U`. Otherwise the write would give the right to itself.
- A removal requires the right to `U`, because an exclusion of the role `none` at the folder tier could forbid `U`: the removal would raise the rights. The right is judged in the subsystem of the unit: a row `none` of another `sub` is removed by this same right, this is a policy (the decisions file, the review analysis, item 4). The reason is the same as for adding: a right in one subsystem does not
  become a right in all of them.
- The deletion of a subtree does not walk its members: that is expensive. `admin` on `*` in the `sub` of the role rows covers any member. The subtree is counted by the listing of `platform/folders/` of this request.
- The rights of consequences are a particular rule. It concerns only the rows that the console itself puts into the batch of a unit deletion. The common rule of the batch door «rights per row» does not change.
- Adding to a folder is a person's will, therefore it goes by the right to write the folder, also in a batch with the creation of a unit.
- A batch where the right was decided by a row `folder:` carries guards of the membership rows of the unit and of its `about` — the gate and pass contract «Membership guards».

### unit deletion by the door

<!-- req: P/06.8-R016 -->

An insertion into step 2 «delete» of chapter 6.1 and into `delete` of the procedure «batch» of chapter 6.1. It concerns the subsystems with `display.tree.folders: true`; for the others the writes are as before.

```
a. read memberof(U):
     no row           → into the batch: the guard {memberof(U), ""}: a folder to which U was added after the read refuses the guard
     the read is not confirmed → 503 store unavailable, the row is unchanged
     unreadable       → into the batch: delete memberof(U) cas of the read version; do not touch the folders, the reaper removes the member
     reads            → for each folder of the list read its row:
                          no row or a tombstone → does not enter the batch; a subfolder under a deleted branch is not considered live, but its member is removed by the same batch if the row is live
                          the row is live → put members without U, cas of its index
                        into the batch: delete memberof(U) cas of its index
b. write — the batch: the unit row with cas (and the claim guard, if a key is present), the rows of step a
c. 412 guard, 409 conflict on the rows of step a → from step 1 «delete» anew, at most FOLDERS_TRIES times, then 503 store unavailable, the row is unchanged
d. journal: unit.deleted of chapter 6.1 and folder.written {id, removed: [U], user, addr} for each folder
```

This procedure neither reads nor guards the chain of ancestors: removing a member from a folder under an ancestor being deleted bothers no one, and chain guards would give a unit that lies in someone else's folder
a false refusal. The version of the folder changes together with the member list, because the folder row is written by the same batch. A deletion of a unit past the door (the controller by `ends` and `delete_after`, the worker by `worker.deletes`, P/06.1 N1)
does not do this procedure: the member dangles until the reaper. There is no second writer of the family: the controller does not write rows `platform/*`.

### folder rows in a batch

<!-- req: P/06.8-R017 -->

An insertion between steps 6 and 7 of the procedure «batch» of chapter 6.1. Refusals — the words of N4, the same order: the rows in the order of `writes`.

```
1. folder row: the form of fields — only members → 400 bad batch, field /writes/<n>/fields; repeat, number of members, weight — as «edit folder» step 7, field /writes/<n>/fields/members/<i>
2. the folder row read: none → 404 no such folder, tombstone → 409 folder gone, field /writes/<n>/key
3. the difference of the member list: the added U and the removed U relative to the row read
4. there are added ones: the chain of ancestors: none, tombstone → 404 no such parent, 409 parent gone, field /writes/<n>/key; unknown → 503 store unavailable;
   a guard for each row of the chain is in guards → otherwise 400 no chain, field /writes/<n>/key; the store checks the index
5. only removals: step 4 does not run
6. for each U — one row memberof(U) in writes, and its folders equals the one read without non-live folders (the chain of each; «unknown» → 503 store unavailable), minus all folders of the batch where U is removed, plus all folders of the batch where U is added → otherwise 400 no membership, field /writes/<n>/key
   the caller does not see a non-live folder (`?member=`), therefore it is absent in the result: the reaper removes the link of its row
   this way one batch moves U and sets its folders whole (the folderIds step)
   a memberof row without its folder row → 400 no membership, field of this row; folders in total > FOLDERS_PER_UNIT_MAX → 400 too many folders
7. added U: subsystem, table, declaration, membership key — as «edit folder» step 7
   U is created by this batch → it fits; otherwise it is live and its row is in writes or guards → otherwise 400 no chain, field /writes/<n>/fields/members/<i>
8. rights — «folder rights» by the difference; a memberof row has no check of its own: the folder row judges it
```

The caller reads and places the chain and the guard: the console only checks that the guards are there, because the indexes were read by the caller, not by the console. The row of a unit created by the batch passes the right of creation with the input `chains` from this same batch.

`delete` of a unit in the batch door puts the rows of «unit deletion by the door» into the same batch itself. These rows are not counted in the caller's `BATCH_WRITES` and do not enter the caller's incoming body; they fully count in the serialized entity of the emitted store request and its static profile bound (N1.3). If the caller has named the folder row of the unit himself, the coinciding rows are not duplicated:
the body decides, the console adds only the missing ones.

### folder reaper

<!-- req: P/06.8-R018 -->

A new job of the console reaper ([chapter 6.4](06.4-console.norms.md) N3): every `FOLDERS_REAP_EVERY`, outside the maintenance window. It runs on every console: `cas` does not let two passes write the same thing twice.

```
1. list platform/folders/; not confirmed → the pass is over
2. an unreachable row (no tombstone, the chain «none» or «tombstone»): batch: a tombstone of the row cas of its index; memberof of each member — as «delete folder» step 6
3. a live folder, a member U, a confirmed read: the row of U is absent or is a tombstone:
     batch: the folder row without U cas of its index; memberof(U) without this folder or delete, cas
4. memberof(U) is unreadable at a member of a live folder: rewrite it by the member lists of all listed folders with cas of the read version
5. the chain «unknown», the row unreadable, the read of U not confirmed → leave until the next pass
6. journal: folder.reaped {id, removed} for each changed folder; conflict → the next pass
```

Step 2 need not remove bottom-up: the tombstone of the parent already makes the descendants unreachable in any order. Step 3 is the only write that removes a member without a person's will: the `index` of the folder changes
on the next pass after a deletion past the door. Until the pass a read gives out the member as is.

**Races.**
- An edit of the member list against the deletion of a unit, the unit deleted first: the unit guard in the batch of the edit refuses, step 7 sees the tombstone, `400 bad member`.
- An edit of the member list against the deletion of a unit, the edit first: the deletion batch carries `cas` or a guard of the absence of the membership row. The new membership refuses the batch, the procedure re-reads the row and removes the unit from the new folder too.
- Two edits of different folders with one unit: both write one membership row, `cas` lets one through, the second goes from step 7.
- A folder write against the deletion of an ancestor: the chain guard, `412 parent moved`, nothing is written. The ancestor deleted before the read — `404`.
- Creating a subfolder against the deletion of the parent: the parent's guard. The folder does not appear under a deleted branch.
- The reaper against an edit: `cas`, the loser waits for the next pass.
- The index of the chain also changes from a rename of an ancestor: a `PUT` of the ancestor's name gives a parallel write `412 parent moved`. This is a false refusal on a rare edit; the caller re-reads and repeats with a new key.
- Two instances of `POST` with one key: the claim of chapter 6.1, the second gets `409 in flight` or the saved answer.

## Implementation decides

1. How to list the units in the reaper's pass: one listing of the table per pass or a read per member. The observable behaviour is the same.
2. The order of the rows of `writes` inside a batch: the batch is atomic.
3. Where to take the 128 random bits from: the system source of randomness. A counter, the time and a hash of the name are a violation of N1.1.
