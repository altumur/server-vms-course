## Н1 Форма

**Время.** Поля времени строк и объектов главы — время по [канону Н0 P/01.1](../../01-store/spec/01.1-store.norms.md#время-в-строке): `<sub>/requests/<rid>` — `valid_until`, `at` (штамп); `<sub>/asked/<sha16(имя)>` — `at`; метка `objects/<sub>/commands/<rid>` — `begun.at`, `begun.valid_until`, `ended_at`. Строка события (журнал, отметка) — `t` — [договор журнала событий](../../common/contracts/event-journal.md).

**Данные** ([каталог](../../common/data/catalog.tsv)):
- владеет: `<sub>/requests/<rid>`, `<sub>/asked/<sha16(имя)>`, `objects/<sub>/commands/<rid>`;
- пишет: `<корень событий>/console/<экземпляр>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<корень событий>/audit/<роль>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<sub>/requests/free-<server>-<volume>` (delete), `<корень событий или объектов>/<путь>/%h<sha256>.name` (create);
- читает: `platform/spec/<sub>`, `<sub>/<spec:unit.rows>/<id>`, `<sub>/heartbeats/<имя>`, `<sub>/epoch/<id>`, `platform/doors/<сервер>`, `/etc/w2c/tls/<роль>/server.key`.

Строку ресурса `free-*` без живого хозяина жнец снимает по `ttl` (Н1.5 `ttl`; участник семьи P/05); файл
`%h<sha256>.name` консоль кладёт по договору журнала событий «Имена файлов»; ключ своего комплекта — клиент дверей
ресурса при слиянии (Н1.3) и своя дверь вне петли ([P/02.4 Н1.6](../../02-installer/spec/02.4-installer.norms.md)
`roles`) (разбор ревью стадии B 3–5, № 10).

Строку просьбы консоль создаёт дверью (`cas ""`) и снимает жнецом — обычную по `settle` после подтверждённой метки с
исходом, брошенную — после метки `expired`/`unknown`, дозапись — после подтверждённого `fetched` и `settle`; своя строка
двери при чужой метке снимается по `cas` (409 `spent`, Н3 «подать просьбу» шаг 5). Строки ресурса `free-*` и `elsewhere`
жнец не снимает (кроме строки ресурса без живого хозяина по `ttl` — участник семьи P/05). Учёт `asked` консоль создаёт,
меняет и снимает по `cas`. В метке консоль — участник: жнец пишет `no_begun` `expired` создание-однажды и `unknown` по
индексу поверх чужой `begun`; метку пишет и убирает держатель (глава 3.6). Отметки оператора дописываются в дерево
`console/<экземпляр>`, журнал — в `audit/console` по договору журнала событий (участник `append`, владелец — P/05). Строку
единицы читает дверь просьб (существование единицы, шаг 0), пульсы — жнец (`fetched` дозаписи и подсказка), эпохи и строки
дверей — слияние.

### Н1.2 Событие: что пишет консоль

Форма строки (`line`), бакет (`bucket`), класс (`class`), журнал `audit` (`journal`) и писатели файла (`writer`), id
события, экземпляр писателя и поля платформы — [договор журнала событий](../../common/contracts/event-journal.md); владелец —
[P/05 Н1.2](../../05-resource/spec/05-resource.norms.md), там же строка индекса (`subsystem`, `unit`). Подавление —
[глава 3.6 Н1.2](../../03-worker/spec/03.6-worker.norms.md), только у писателя событий подсистемы: строки консоли и `audit` не
подавляются (договор, «Запись строки» шаг 3; разбор ревью стадии B 6–7, № 34). Своё `of` — только деревья `console` и `audit` (договор, `line.of`).
Здесь — `older_epochs` и `marks`:

```yaml
older_epochs: fenced | earlier-run           # слово для страницы; умолчание fenced
marks:      дерево console/<экземпляр>/e1/…: отметки оператора, kind mark, of = единица, user — имя человека, доказанное
            сторожевой (без домена — operator, глава 6.3 Н1.3) (сверка python и go М10/6–11, E60); строка индекса —
            subsystem: "console", unit: "console/<экземпляр>", of — адресат
```

### Н1.5 Просьба

Строка просьбы `<sub>/requests/<rid>`, действие (`action`), грамматика `rid`, ключи спеки `requests` (`spec`) и метка
`objects/<sub>/commands/<rid>` (`begun`, `answer`, `no_begun`, `outcome`, `ended_by`, `kept`) — [договор просьбы и её метки](../../common/contracts/request-mark.md)
(перенесено туда из этого подраздела вместе с абзацем о векторах; разбор ревью стадии B 3–5, В1); глава — его владелец.
Здесь — учёт человека, `holds` и константы жнеца:

```yaml
ledger:     <sub>/asked/<sha256(имя)[:16]> {rids: [<rid>…], by, at}   # учёт человека: список зарезервированных/неотвеченных rid, cas; писатель и читатель — консоль (ADR-0060)
holds:      раздел спеки (P/02.1 Н1.2), закрытый: {table, unit, since, until, longest, released} — таблица удержаний: строка таблицы
            называет единицу (поле unit) и окно [since, until] (поля), бакеты единицы в окне не убираются по сроку, пока строка
            не помечена полем released или не прошло longest секунд; читает ресурс (P/02.5 Н1.4)
constants:
  PERFORM_TIMEOUT, PERFORM_GRACE, REQUESTS_HOLD, COMMANDS_PER_LOOK — глава 3.6 Н1.5
  CLEAR_EVERY: 2; SWEEP_EVERY: 30; REAP_AFTER: 60
```

### Семьи данных (построены из источника)

Форма строк и объектов, которыми глава владеет по [каталогу](../../common/data/catalog.tsv), — из схем семей на [диалекте](../../common/DIALECT.md) (ADR-0088). Экземпляр строки — `{key, row}`, объекта — `{key, object}`; ключ — грамматика колонки `key` каталога. Поля `row` — значения `items` после [кодека](../../common/data/codec.tsv): писатель пишет строго, читатель читает терпимо (DIALECT § 8). Ключ вне таблицы — отказ `key`, иной отказ — `value`. Нечитаемо — строка не раскодировалась или не прошла схему в режиме читателя; исход — по таблице исходов семьи (DIALECT § 9): путь — префикс пути отказа (пустой — строка целиком), при нескольких путях отказа действует исход с наименьшим приоритетом.

## Н2 Двери

Полный контракт: [OpenAPI урока](06-console.api.openapi.yaml). Схемы ответа `/events`, общие с ресурсом, — контракт
[P/05](../../05-resource/spec/05-resource.api.openapi.yaml). Двери ресурса (`/v1/objects`, `/events` ресурса, `/events/wait`,
`/buckets`, `/events/{path}`, `/mirror`, `/mirrored`), их разбор запроса, допуск, ограничения профиля и отказы —
[P/05 Н2](../../05-resource/spec/05-resource.norms.md). Схемы задают обязательные поля и допустимые расширения; проверки
существования, прав, UTF-8-размера и состояния исполняются отдельно.

| Вход | Успех | Прикладные отказы |
|---|---|---|
| консоль GET /events | 200 ConsoleEvents; `HEAD` — код и заголовки `GET` без тела ([глава 6.5](06.5-console.norms.md) Н2) | 400 TextError (разбор ниже); 503 TextError |
| консоль POST /marks | 200 MarkWritten | 400 TextError |
| консоль POST /{sub}/requests | 202 Queued; 200 Answered | 400 RequestError; 404/409/429/503 TextError |
| консоль DELETE /{sub}/asked/{sha16} | 200 Cleared | 404 TextError |

Эти две двери всегда явно именуют подсистему, в том числе CONSOLE_ROOT. Короткие
/requests и /asked/{sha16} не объявлены: общий неизвестный маршрут консоли —404
по главе 6.5. Зарезервированное имя семьи само по себе не добавляет HTTP-дверь.

TextError — только `{detail: текст, error: текст}`.
RequestError допускает дополнительно `fault:"too_long"` только при превышении длины
поля по requests.schema; остальные причины fault не получают. Применение схемы — до
проверки существования единицы.

**Разбор запроса.** Двери консоли этой главы — [глава 6.5](06.5-console.norms.md) Н2 «Разбор запроса консоли». Дверь ресурса — [P/05 Н2](../../05-resource/spec/05-resource.norms.md)
«Разбор запроса».

Общие отказы консоли по главе 6.5: 400/401/403/404/405/408/413/429/503;
тела TextError (у POST requests 400 — RequestError), у 401/403 error=denied.
Предел тела консоли объявляется развёртыванием и не меньше 1 MiB; chunked/короткое тело
даёт 400, превышение размера — 413, срока чтения — 408. При 429 действует предел входа.
Время чтения должно быть объявлено до запуска, не подбираться под запрос. Отказ TLS до HTTP
не получает выдуманного HTTP-тела. Каждый применимый общий ответ внесён в OpenAPI.
При busy — Retry-After: 1. На неизвестном пути — 404; на неподдержанном методе известного
пути — 405; у консоли TextError. Этого общего правила достаточно:
оно не создаёт отдельный метод OpenAPI для каждой невозможной операции.

`POST /marks`: unit обязателен и имеет форму полной ссылки; отсутствующий note — пустая строка,
переданный note — строка. Проверяется форма ссылки, не наличие живой строки единицы; отсутствие строки не вводит отдельный 404/400 этой двери. Лишние поля принимаются, но не попадают в событие. Дверь требует
грант edit на адресата по [главе 6.3](06.3-console.norms.md) Н1.3. `Idempotency-Key` здесь не обещает памяти повторов.
Для POST requests заголовок обязателен, безопасная форма/размер — как у двери единиц [главы 6.1](06.1-console.norms.md);
отпечаток, rid и память — собственные правила Н1.5/Н3, не копия pending/done единиц.
Поля сервера rid/digest/filed/by/at/group в теле клиента отвергаются; единственное
разрешённое служебное поле — valid_until. Поля тела дополнительно проверяются по
requests.schema и правилам stamp выбранной спеки, существование — после формы.

## Н3 Проход

### слияние (консоль)

```
живые ресурсы — строки дверей platform/doors/<s>, чья версия менялась в последние LOST_AFTER по часам консоли (≤ 45 с,
договор наблюдения `fresh`; первый взгляд — как свежий; пульс ресурса слияние не читает: живость ресурса здесь — только
по строке двери, разбор ревью стадии B 6–7, № 35) → параллельно (8 полос, 3 с); current_epochs — из <sub>/epoch/*; политика — из спек
дубли по id → одна; не ответил / сказал не live → incomplete[сервер]; state: live[; s unreachable][; s from mirror]
ресурс с несвежей строкой двери (silent) не спрашивается: incomplete[s] = silent, state «; s unreachable»; копии его
  бакетов в ответах других ресурсов отдаются, и тогда state ещё «; s from mirror» (сверка python и go М10/6–11, E23)
epoch_is: эпоха строки < current_epochs[unit] → политика спеки (fenced | earlier-run), иначе current; fenced — P/05 Н1.3
с unit: запрос без ограждения, затем разметка по эпохам (`epoch_is`, `fenced`, P/05 Н1.3): строка прежней эпохи отдаётся с
  `fenced: true`, не выбрасывается (сверка python и go М10/6–11, E21)
строка ответа ресурса не по форме EventRow → пропустить, lines_garbled консоли (P/05 Н1.3; E24)
полученные уникальные кандидаты упорядочить по cut P/05 Н1.3 (OpenAPI ресурса GET /events; № 32); оставить первые limit;
truncated = сумма truncated ответивших ресурсов + число кандидатов, не вошедших в общий limit;
дедупликация и отсечение по эпохам сами по себе в этот счётчик не входят; порядок выдачи — тот же, что cut
```

Свежесть строки двери — [договор наблюдения](../../common/contracts/observation.md) «Свежесть: `LOST_AFTER`»: прежняя
запись «`at` менялось `< 45 с`» читается по нему — граница одна, `≤ LOST_AFTER` (разбор ревью стадии A 6–7, № 1; правка
поведения на одном шаге — возраст ровно 45 с: ресурс жив; граница — вектор [`fresh-age`](../../common/vectors/fresh-age/README.md), разбор ревью стадии B 6–7,
№ 20).

**Гонки.** Источники и эпохи могут изменяться между чтениями: общего снимка нет.
Счёт относится к наблюдённым ответам: локальная обрезка может скрыть копии и строки,
которые позже отсекаются по эпохе; результат не обещает глобальный top-k всех файлов.
Ответивший позже таймаута ресурс отмечается в incomplete этого ответа и может ответить
на следующий. Поздний ответ не дописывается в уже отданное тело.

### Состояния исполняемой просьбы и её метки

Таблица состояний подачи, держателя и жнеца, подтверждение исхода, `settle` и класс строки (обычная просьба, дозапись,
строки ресурса, elsewhere) — [договор просьбы и её метки](../../common/contracts/request-mark.md) «Состояния исполняемой просьбы и её метки» (перенесено туда целиком;
разбор ревью стадии B 3–5, В1). Строки «подача …» таблицы исполняет проход «подать просьбу» ниже, «жнец …» и «clear …» —
проход «жнец».

### подать просьбу (консоль, `POST /<sub>/requests`)

Проверка тела, digest/rid, создание строки и лимит человека общие. Шаги чтения
метки2/5 применяются только к обычному профилю таблицы состояний (договор просьбы и её метки; разбор ревью стадии B 3–5, В1). У дозаписи их нет:
совпавшая или созданная строка подтверждает202 queued, метка не требуется,
освобождение учёта — по fetched/правилу исключения, не по отсутствующей метке.

```
0. у спеки нет requests (или подсистема просьб не принимает) → 404 TextError; единицы unit нет (строки нет или deleted) —
   после схемы, шаг 1 → 404 TextError (Н4 «просьба: нет requests / нет единицы»)
1. Idempotency-Key (нет → 400, Н4); тело — объект с unit; схема; digest = sha256(JCS(тело без valid_until — единственного поля сервера, которое клиент вправе прислать)); rid: по requests.key — шаблон {поле} из тела ({поле:int} — целая часть числа, P/02.1 Н1.4; не число → 400; детерминированный: одинаковые
   поля — один rid, создание-однажды); иначе r-<sha16(Idempotency-Key)> — заголовок у двери обязателен, иной ветки нет (случайный rid — у воркера, пишущего строку сам);
   valid_for задан → valid_for ≤ most_valid (проверено загрузчиком), valid_until = now + valid_for; без valid_for строка без срока, действует ttl. valid_until из тела клиента при заданном most_valid —
   не позже now + most_valid, иначе 400 too far, и тогда он и есть срок; valid_until — конечное число JSON: null,
   строка, bool — 400; 0 и прошедшее принимаются и записываются как есть (срок вышел); у спеки без most_valid
   valid_until в теле — 400 «this subsystem takes no deadline» (сверка python и go М10/6–11, E50, E52, E54). Все отказы шага 1
   (форма, срок, шаблон) — раньше отказа «нет единицы» шага 0 (E51); тело не JSON — 400 RequestError без fault (E49);
   Idempotency-Key — форма двери единиц главы 6.1: `.` и `a,b` допустимы (E48); {поле:int} — каноническая десятичная запись:
   −0 → 0 (E53)
2. метка objects/<sub>/commands/<rid> уже есть (строка могла уйти по clear): тот же unit и digest и у метки есть исход (answer или
   no_begun) → 200 answered; тот же unit и digest, но только begun без исхода (исполняется) → 202 {queued: rid}; учёт и строку не трогать;
   иной unit или digest → 409 spent
3. per_person: прочитать учёт: недоступное/неподтверждённое чтение → 503; прочитана повреждённая форма
   (rids не список допустимых rid, неверные by/at) → 429, без изменения; rid уже в rids → учёт не менять и продолжить шагом 4, ответа здесь нет;
   иначе len(rids) ≥ per_person → 429; иначе добавить rid по cas и продолжить шагом 4; конфликт → перечитать учёт
4. записать строку cas ""; подтверждённое создание → шаг 5; уже есть: прочитать строку, тот же unit и digest → шаг 5;
   иной unit или digest → 409 exists (резерв не откатывать); исчезла при чтении → повторить шаг 4.
   Отказ или неизвестный исход записи/чтения → 503, один резерв не подтверждает постановку просьбы
5. перечитать метку: появилась после шага 2 с теми же unit/digest и **с исходом** (держатель исполнил) →
   снять rid из учёта, ответ 200 answered; строку оставить жнецу с соблюдением settle; тот же unit и digest, но только begun без исхода (держатель взял мою строку) →
   ничего не трогать, 202 {queued: rid}; иной unit или digest → удалить только свою строку по cas, резерв оставить, 409 spent
6. journal → строка журнала (дерево audit; of у неё нет — единица просьбы в полях sub и target, ADR-0069, поэтому
   /events?unit= её не выдаёт; разбор ревью стадии B 6–7, № 35); 202 {queued: rid}
Ошибки чтения/записи → 503, не успех по предположению; успешно прочитанный, но повреждённый
учёт — отдельный 429 шага 3. При любом отказе после резерва (включая определённый отказ
создания и 409 exists) резерв не откатывается: его мог использовать параллельный повтор.
Повтор тем же rid заново читает строку и метку; обрыв после резерва до создания лечится
переходом из шага 3 к шагу 4, где отсутствующая строка создаётся. Ответ 202 разрешён только
после подтверждения строки в шаге 4 и проверки метки в шаге 5 либо по begun шага 2. Освобождение — только по подтверждённому
исходу с теми же unit/digest либо по обслуживанию ниже. Это консервативный лимит, не
транзакция учёта, строки, метки и журнала; лишний резерв может временно уменьшить доступность.
```

**Гонки.** Две одинаковые подачи с одним ключом: rid один, создание строки пропускает одну;
вторая получает queued или уже известный answered по Н3. При разном теле сравниваются
unit/digest, чужая версия не заменяется. Разные rid одной единицы — разные просьбы;
этот урок не обещает их глобального порядка. Подача против жнеца проверяет метку повторно
после создания строки; свежесть строки сама по себе не заменяет эту проверку.

### жнец (консоль): каждые 2 с — снять отвеченные; каждые 30 с — закрыть брошенные

```
clear:  обычная просьба: подтверждённая метка с исходом для тех же unit/digest;
        fetched — подсказка перечитать метку, отсутствие/вытеснение rid из пульса не отменяет подтверждённый исход;
        rid в fetched — имя rid или SaidID(rid) среди имён через запятую (P/03.4 Н1.1 `said_id`);
        дозапись ADR-0054: подтверждённый fetched держателя, метку не читать/не создавать;
        дождаться возраста ≥settle по правилу договора просьбы и её метки («Состояния…»; В1), подтвердить текущую строку и основание;
        удалить по cas; rid снять из учёта человека (rids − rid, cas); неизвестность → оставить
sweep:  ветвь меток — только обычный профиль; дозапись, elsewhere и строки ресурса не получают меток этого прохода.
        Обычная строка с valid_until + REAP_AFTER < now или старше ttl (без срока):
          метки нет → метка expired создание-однажды {ended_by: reaper, unit, digest из строки} (договор просьбы и её метки `no_begun`; В1)
          метка begun без исхода → {outcome: unknown, ended_by: reaper, error: "begun and never answered"} по индексу
        удалить строку по cas только после подтверждённой метки с исходом и возраста ≥settle;
        conflict метки → перечитать; неизвестное чтение/запись → оставить строку;
        снять rid из учёта человека по cas; просьбы ресурса (семья ключа requests/free-<server>-<volume>, P/05 Н1.4; разбор ревью стадии B 6–7, № 37) без хозяина — по ttl.
        Дозапись без fetched не закрывать меткой и не снимать по одному возрасту; её завершает обработчик.
asked:  один возраст ttl/settle не разрешает снимать непустой учёт. В фоне снимать отдельный rid через CAS
        только после подтверждённой метки с исходом обычной просьбы либо подтверждения fetched дозаписи
        по правилу исключения; повторный CAS перечитывает весь список,
        не теряя новые rid. Пустую строку учёта можно удалить по CAS после ttl/settle.
        Резерв без доказанного исхода, включая отсутствие строки, автоматически не освобождается: запоздалая
        подача ещё может создать строку. Административный DELETE asked оператор вызывает только в окне, где остановлены
        и завершены все подачи этого человека и его оставшиеся просьбы закрыты. Неподтверждённый покой — оператор
        не вызывает DELETE; это допуск обслуживаемого профиля, автоматическое обнаружение окна не обещано.
```

**Гонки.** Метки против держателей (два держателя, жнец против начавшего, повтор подачи тем же rid) — [договор просьбы и её метки](../../common/contracts/request-mark.md)
«Гонки меток» (перенесено туда; разбор ревью стадии B 3–5, В1).

## Решает реализация

Реализация обязана назвать в своём описании:

1. **пределы просьб**: повторы `cas` учёта; `FETCHED_COUNT`/`FETCHED_BYTES`, `MARK_SWEEP` — [глава 3.6](../../03-worker/spec/03.6-worker.norms.md) «Решает реализация» п. 1;

   наблюдения), не выбор реализации (разбор ревью стадии B 6–7, № 32);
3. **пределы и сроки POST** по владельцу двери — [глава 6.3](06.3-console.norms.md) Н1.3 `body` (предел ≥ 1 MiB, срок чтения — 408); потоки и приём
   зеркала — [P/05](../../05-resource/spec/05-resource.norms.md) «Решает реализация» п. 6.

Число полос слияния (8) и срок (3 с) — норма Н3 «слияние», не выбор (P/05 «Решает реализация» п. 3 ссылается сюда).
