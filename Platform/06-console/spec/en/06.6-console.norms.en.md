### Н1.1 Console rows

The rows written by the console (the doors of Н2); the controller reads them by P/04 Н1.1.

```yaml
<sub>/policy:                             # the writer is the console; the controller reads
  servers:   shared | distinct            # another value or key on read — the manifest default; on write — a refusal
  revision:  <integer ≥ 1>                # Н2.1 «Row version»; the same at platform/servers, platform/drain, platform/schema
platform/servers/<сервер>:                # the writer is the console (ADR-0026)
  labels:    <comma-separated labels>     # "" — none; the row beats the node labels
  revision:  <integer ≥ 1>
platform/drain:                           # the writer is the console; one row per cluster
  server: <сервер>; at: <момент>; revision: <integer ≥ 1>
platform/decommission/<сервер>:           # the writer is the console
  by: <кто>; at: <момент>; why: <слова>; gone: "true"?   # gone — the confirmation «no server» when the resource was never heard
```

The server door row `platform/doors/<сервер>` (the writer is the resource of the server, ADR-0045) has the form of
[P/05 Н1.4](../../../05-resource/spec/05-resource.norms.md) `door_row` (family `doors`); the console reads it for the state of the
resource and the knownness of the server (Н2.1) and deletes it at a decommissioned server (Н3 «decommission_server»).

### Н1.2 Drain

```yaml
platform/drain:  {server: <сервер> | "", at, revision}   # one server at a time; the writer is the console (admin); the controller reads (P/04 Н1.1)
state:
  draining:        <сервер> | ""
  safe:            all subsystems safe
  would_strand:    {<sub>: [id…]}                      # a probe without modelling the placement: all units of the workers of this server
                                                         # and all unplaced ones (Н2.2)
  subsystems:      {<sub>: {draining, subsystem, workers, units, pending_writes, pending_unsaid?, would_strand, safe}}
  safe(sub):       units == 0 ∧ pending_writes == 0 ∧ pending_unsaid empty
  pending_writes:  Σ over the workers of the server of the heartbeat field pending_writes — a JSON integer without a fractional part and an exponent,
                   0 ≤ x ≤ 2^53 − 1 (the form int of [the row check contract](../../../common/contracts/row-check.md) «Preparation of fields»: «An `int` value at the input of the door»): the base worker of the platform (P/03.4 Н1.1) writes
                   0 into the heartbeat itself if the subsystem has not said its own (a subsystem with a buffer on disk says its own number);
                   no field / a word / a fraction, including `0.0`, `1000.0`, `-0.0`, `1e3` / more than 2^53 − 1 / an unreadable or
                   stale heartbeat → pending_unsaid (the drain is not safe) (reconciliation of python and go М10/6–11, T1, T3, T4)
  server_of:       a worker of the server — by the field server of a readable heartbeat; the heartbeat does not read — by server of its slot
                   `<sub>/slots/<имя>` (P/03.2 Н1.4): such a worker goes into pending_unsaid, the units of its assignment
                   `<sub>/workers/<имя>` — into units and would_strand (reconciliation of python and go М10/6–11, T2)
journal:  drain.started {server, user}; drain.ended {server} — there are no other kinds of the drain journal (no `drain.cleared`)
          (reconciliation of python and go М10/6–11, T22)
          # the console journals of this chapter (schema.raised, policy.changed, drain.*, server.decommission_*) — the tree audit/console (the event log contract `journal`,
          # role console); the journals of the unit and table doors (<t>.written/<t>.deleted, unit.changed) — chapter 6.1
```

`GET /drain` returns `DrainState` whole, without a filter by grants: the drain is a state of the whole cluster, the door requires `view` on
`*` ([the gate and pass contract](../../../common/contracts/gate-and-pass.md) `need`), a narrow grant — 403; `safe` is over all
subsystems (C06-DRAIN-VISIBILITY-33-01, the Architect's decision of 2026-10-25; the scenario — the acceptance of chapter 8.4, sc. 01 steps 25–26).

A stale heartbeat is one that is not fresh by [the observation contract](../../../common/contracts/observation.md) «Свежесть»: the version has not
changed within the last LOST_AFTER (review of stage A 6–7, № 2: freshness — in one place).

### Семьи данных (построены из стандартных файлов)

Форма строк и объектов, которыми глава владеет по [каталогу](../../common/data/catalog.tsv), — JSON Schema 2020-12 семьи (ADR-0092). Экземпляр строки — `{key, row}`, объекта — `{key, object}`; ключ — грамматика колонки `key` каталога. Поля `row` — значения `items` после [кодека](../../common/data/codec.tsv): писатель проверяет схему и её `$defs.writer`, читатель — схему (слой 3 — слова `x-*` схемы). Нечитаемо — строка не раскодировалась или не прошла схему в режиме читателя; исход — по таблице исходов семьи: путь — префикс пути отказа (пустой — строка целиком), при нескольких путях отказа действует исход с наименьшим приоритетом.

**Replay memory** (ADR-0094 B3). `PUT /policy`, `POST` and `DELETE /drain`, `PUT` and `DELETE /servers/{server}/labels`, `POST` and `DELETE /servers/{server}/decommission`,
`PUT /schema` read the optional `Idempotency-Key` by the rule of [chapter 6.1](../06.1-console.norms.md) Н3 «память повторов»: the key is `(user, метод, путь, ключ)` (user, method, path, key), the order is
«parsing of the request → claim → pass of the door → write under the claim guard → answer into the claim», an answer `< 500` is remembered, the term is as at `POST`. Another body or another query input
under the same key (`server` at `POST /drain`, `version` at `PUT /schema`) — 422 `key reused`; a foreign pending one younger than 30 s — 409 `in flight`; a key out of form — 400 `Idempotency-Key required`.
The claim of `PUT /policy` is `<sub>/idem/<key>` of the chosen subsystem; at the cluster doors `/drain`, `/servers/{server}/…`, `/schema` it is `<CONSOLE_ROOT>/idem/<key>`
([chapter 6.5](../06.5-console.norms.md) Н1.1): they have no family of their own, the path in the key distinguishes the doors. Without the header the doors are as before.
The doors that write `revision` hold the intended `revision` in the claim before the write, as chapter 6.1 Н3 «edit» step 5а. The one who took over a claim looks at the target before `If-Match`: the row has this `revision` → written by this claim, the answer by step 9;
`DELETE` of the labels: no row → the same. Otherwise the pass anew would raise `revision` a second time and refuse its own write with `412`. The decommission of a server does not write `revision`; its taken-over claim passes the door anew: it converges.

**Row version** (ADR-0094 B4). The snapshots of settings — `<sub>/policy`, `platform/servers/<сервер>`, `platform/drain`, `platform/schema` — carry `revision`: 1 at the creation of the row, +1 for every write. A write goes with `cas` of the read version (no row — `cas ""`):
without it two writes would raise `revision` to the same number. A conflict — re-read and check the condition again, the retry limit exhausted — 503 `unavailable`. A pass without a write (`POST /drain` of the same server, `DELETE /drain` without a drain, `DELETE` of the labels without a row)
does not move `revision`. Removed labels count anew. A row without a readable `revision` reads as 0, the next write writes 1.

`If-Match`, `ETag`, the index and `412 revision moved` are [chapter 6.1](../06.1-console.norms.md) Н2 «Версии», with the same words:

- `ETag` is carried by `GET /policy`, `GET /drain`, `GET /schema`, `GET /servers/{server}/labels` and the success answers of `PUT /policy`, `POST` and `DELETE /drain`, `PUT` of the labels, `PUT /schema`, if the row exists. No row — no `ETag`; `DELETE` of the labels removes the row — no `ETag`.
- `If-Match` is read by `PUT /policy`, `POST` and `DELETE /drain`, `PUT` and `DELETE` of the labels, `PUT /schema`. The decommission of a server does not read it: it is a request, not a snapshot of a setting, and `PUT` does not edit its fields.
- The order: the parsing and the form of `If-Match` → the claim → the read of the row → the condition → the pass of the door → the write. The condition stands before the checks of the door: the client judges the row that it saw.
- No row and `If-Match` present — 412 with `revision: 0`, without `row`: the condition names a version that does not exist. To create a row, the client sends a request without `If-Match`.
- `row` of the refusal 412: `{servers, revision}` at the policy, `{labels, revision}` at the labels, `{server, at, revision}` at the drain, `{version, revision}` at the schema.

In all rows of the table the JSON objects are closed: there are no unlisted fields. A success `{}` contains a JSON object,
not an empty HTTP body. A label is by [the label alphabet](../../../common/contracts/labels.md) (1–64 ASCII characters: the first a letter/digit,
then a letter/digit, `_`, `.`, `:`, `-`). A query list is parsed by commas, without empty elements,
except a wholly empty string; a server in path/query is a server name: a host name of RFC 1123 — labels separated by «.», a label of 1–63
characters `[A-Za-z0-9-]`, not starting and not ending with «-», in total not more than 253 bytes (`..`, `.`, a space, `/` are not a name);
otherwise — 400 before the existence check (reconciliation of python and go 2026-10-18). Into `will_move` and
`would_move` go only the references available to the caller by `view`; the list can be empty.
The label forecast `would_move` / `will_move` is the set of units that **leave** the server s, not that come to it (review
of stage B 6–7, № 33): a unit of a subsystem with `constraint: labels-subset` whose worker of the effective placement
([the observation contract](../../../common/contracts/observation.md) «Reading the decision: intent → placement → intent») is fresh by the same
contract and whose heartbeat names `server: s`, while the labels of the unit (its field `labels`, [P/04 Н1.3](../../../04-controller/spec/04-controller.norms.md)
`constraint`) are not a subset of the checked set: the query `labels` or the body of `PUT`; at `GET` without the query — the current
effective labels of the server (the row `platform/servers/<s>`, otherwise the node labels — P/04 Н1.3). Unplaced units, units
of other servers and units which the set would suit on this server do not enter the forecast. The references `<sub>/<id>` are without
repeats, in ascending order of the UTF-8 bytes of the reference string. The forecast is a read output: a non-answer when reading heartbeats and placements (and their listing) is
`lapse` of the observation contract, the forecast by the memory of the last read versions (C06-PULSE-LAPSE-503-01); a source not read even
once since the start — 503 `unavailable`, at `PUT` — before the write of the row: there is no write without an answer. The write of the label row by `PUT` does not depend
on the heartbeats and is not an admission by observations (C06-PULSE-LAPSE-503-02, the Architect's decision of 2026-10-29).
The subsystem name in the reference `<sub>/<id>`, in the keys of the drain maps and in the field `subsystem` follows P/02.1 Н1.2,
including the whole closed list of reserved names; the grammar of the id itself is [chapter 6.1](../06.1-console.norms.md) Н1.3.
The existence of a server is determined by all subsystems and resources of the console: a server is known if there is at least
one piece of evidence — the heartbeat of the resource of this server, the row `platform/doors/<сервер>`, the field `server` of a worker heartbeat
or of a slot of any subsystem, and for the label operations also the row `platform/servers/<сервер>`. For all three
label operations and both decommission methods an unknown server — 404. A wrong form of the body/labels — 400 before this check.

## Н3 Procedures

### raise_schema(N) — console, admin

```
1. the string N — only ASCII [1-9][0-9]* whole (without a sign, spaces and a leading zero), the value ≥1 (Н2.3)      → otherwise 400 «a version is a whole number from 1»
   If-Match — the form; the condition by the read row — before step 2 (Н2.1 «Row version»)
2. the row platform/schema: not a number → 409 «mend the row first»; have > N → 409 «does not go back»
3. its own SCHEMA < N → 409; live processes (the heartbeats changed before the eyes of the reader within the last LOST_AFTER — the observation contract):
   any with schema < N or an unknown one → 409 «still running: …»; the read of the heartbeats of this pass is not confirmed
   (a non-answer, including of the listing) → 503 unavailable, no write: it does not decide by memory, not an empty membership
4. write {version: N, at, revision: the read one + 1} with cas; journal schema.raised
```

Step 3: «live» — by [the observation contract](../../../common/contracts/observation.md) «Свежесть» (review of stage A 6–7,
№ 1: it was «< 45 с» — a change of behaviour at the boundary step; the boundary — the vector [`fresh-age`](../../../common/vectors/fresh-age/README.md), review
of stage B 6–7, № 20). The raise is a write: it decides only by the reads of its own pass; the observation memory (`lapse`) is no ground for it — by that memory
a heartbeat ages within LOST_AFTER, the process drops out of the «live» ones, and the raise would pass blindly (C06-PULSE-LAPSE-503-01, the Architect's decision of 2026-10-29).

**Admission.** The operator forbids the starts and writes of the former builds for the whole window, including silent servers; updates the whole known membership and leaves one compatible console for the raise. The heartbeats are a check of the observed membership, not a proof of the absence of an old process. Without this admission a concurrent raise is outside the profile of the lesson. After a successful CAS the starts of only the updated builds can be opened. Two admins are still protected by CAS: the loser re-reads the state and does not announce success.

| Phase | Admission/transition | Refusal |
|---|---|---|
| Open installation | The operator closes the starts of old builds, stops their writers | Failed to confirm the stop — do not raise |
| Maintenance | A full read of the schema and of the known processes; N is admitted by its own build | An unknown read — 503; incompatibility — 409 |
| CAS | Fix the version; on a break re-read | Do not take a break for a rollback |
| Done | Return only compatible builds | An old build refuses to start |

### console start — schema check

The common block of all four processes (formerly М10/10 Н3 «старт контроллера, воркера, ресурса или консоли — проверка схемы»);
here — the console side, inside P/06.6-04 (В5 of the plan of the move of lesson 6). The worker side is
[P/03.2](../../../03-worker/spec/03.2-worker.norms.md) Н3 «schema check by the worker», the controller side —
[P/04](../../../04-controller/spec/04-controller.norms.md) Н3 «controller start — schema check», the resource side —
[P/05](../../../05-resource/spec/05-resource.norms.md) Н3 «resource start — schema check».

The processes of the domain start in the same way — `domain`, the agent, the domain console ([P/02.4 Н1.12](../../../02-installer/spec/02.4-installer.norms.md)).

The check at start and its boundary are [the schema contract](../../../common/contracts/schema.md) «Check at start» (moved there without a change of behaviour; layout audit А-02, the Architect's decision of 2026-10-25).

### drain — reading the state

```
for each manifest: the workers of the server (heartbeats; the heartbeat does not read — server of the slot, Н1.2 server_of) → units = Σ of the assignments,
pending = Σ pending_writes (none/a word/a fraction/an unreadable heartbeat → unsaid; reconciliation of python and go М10/6–11, T2),
would_strand = all units of the workers of the server and all unplaced units of the subsystem — without modelling the placement (Н2.2 `DrainState`)
safe = Σ units == 0 ∧ Σ pending == 0 ∧ unsaid empty
```

### drain — start (`POST /drain?server=s`)

```
1. read platform/drain (not confirmed → 503); If-Match present and not equal to the version of the row → 412 revision moved (Н2.1 «Row version»); server of the row = s → 200 {draining: s}, write nothing
2. server of the row — another non-empty one → 409 «<server> is already draining; one server at a time»
3. write {server: s, at, revision: the read one + 1} with cas of the read version (no row — cas ""); conflict → from step 1;
   the retry limit on conflict exhausted → 503 unavailable; success → journal drain.started, 200 {draining: s}
```

**Races.** Two simultaneous `POST /drain` of different servers: `cas` lets one write through; the loser re-reads — sees
another server and answers 409, for its own one — 200 without a write (the Architect's decision of 2026-10-20, review of stage B 6–7; formerly — a question to the Architect, review of stage B 6–7, № 41). The controller reads draining once per pass; what was assigned earlier can arrive later. `safe` is a conclusion from the observed placements and the fresh known heartbeats, not an atomic snapshot and not a lock on new assignments. Before switching off, the operator stops new writes/assignments to the server, waits for the started actions to complete and checks the state again. Failed to confirm quiescence — the switch-off is postponed; one `safe: true` is not enough.
