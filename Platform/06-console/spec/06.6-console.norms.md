# P/06.6 — Control doors: norms

This English text is the source; the Russian translation `ru/spec/06.6-console.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand.

The canon of chapter 6.6 of lesson P/06 «Cluster console» (the cluster console; module «Platform»). Lecture (`ru/06-console.md`, for people, not in the export),
[contract](06-console.api.openapi.yaml), [instructions](06-console.README.md), [life cycle](../lifecycle.md),
[acceptance](../acceptance/6/README.md). The doors through which the operator talks to the controller and the platform: the policy,
the drain, the server labels, the decommission of a server, `/unplaceable`, `/where/{id}`, the schema row and its raise, the schema check at the start
of the console.

«Chapter 6.K» is a chapter of this lesson; «P/0N.K» is a chapter of the module. Norm ids are
`P/06.6-MM`.

The freshness of a heartbeat, the state of a resource and the reading of the decision intent → placement → intent are the common
[observation contract](../../common/contracts/observation.md); the controller rows that the doors read are P/04 N1.1, N1.2,
N1.5.

## N1 Form

<!-- req: P/06.6-R002 -->

**Time.** The time fields of the rows of the chapter are time by [the canon of N0 of P/01.1](../../01-store/spec/01.1-store.norms.md#time-in-a-row): `platform/drain` — `at`; `platform/decommission/<host>` — `at`; `platform/schema` — `at`.

**Data** ([catalogue](../../common/data/catalog.tsv)):
- owns: `<sub>/policy`, `platform/servers/<host>`, `platform/drain`, `platform/decommission/<host>`, `platform/schema`;
- writes: `<sub>/idem/<key>` (create), `platform/doors/<host>` (delete), `<events root>/audit/<role>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append);
- reads: `platform/manifest/<sub>`, `<sub>/heartbeats/<name>`, `<sub>/slots/<name>`, `platform/resources/<server>/heartbeat`, `platform/doors/<host>`, `<sub>/placement/<id>`, `<sub>/workers/<name>`, `<sub>/decommissioned/<host>`, `<sub>/controller/placement_intent`, `<sub>/controller/pass`, `<sub>/<manifest:unit.rows>/<id>`.

The `audit` journal of the chapter has the kinds `schema.raised`, `policy.changed`, `drain.*` and, about the decommission of a server, `server.decommission_requested`,
`server.decommission_withdrawn` (N3 «decommission_server»). The server label doors (`PUT`/`DELETE /servers/{server}/labels`) write no journal;
`server.decommission_refused` and `server.decommissioned` are words of the console module, not kinds of the console of P/06.

The rows «owns» are written by the console with the doors of N2 and with the schema raise (N3 «raise_schema»); the controller reads them by
[P/04 N1.1](../../04-controller/spec/04-controller.norms.md), the other processes — by the catalogue. The door row
`platform/doors/<host>` (its owner is the resource, [P/05 N1.4](../../05-resource/spec/05-resource.norms.md) `door_row`) the console
deletes at a decommissioned server (N3 «decommission_server»). The controller rows (`placement`, `workers`, `placement_intent`, the pass
report) the doors read by [the observation contract](../../common/contracts/observation.md) «Reading the decision» and P/04 N1.2; the heartbeats
and the slots — for the knownness of a server (N2.1), the drain (N1.2) and `/schema` (N2.3).

### N1.1 Console rows

<!-- req: P/06.6-R003 -->

The rows written by the console (the doors of N2); the controller reads them by P/04 N1.1.

```yaml
<sub>/policy:                             # the writer is the console; the controller reads
  servers:   shared | distinct            # another value or key on read — the manifest default; on write — a refusal
  revision:  <integer ≥ 1>                # N2.1 «Row version»; the same at platform/servers, platform/drain, platform/schema
platform/servers/<host>:                # the writer is the console
  labels:    <comma-separated labels>     # "" — none; the row beats the node labels
  revision:  <integer ≥ 1>
platform/drain:                           # the writer is the console; one row per cluster
  server: <server>; at: <moment>; revision: <integer ≥ 1>
platform/decommission/<host>:           # the writer is the console
  by: <who>; at: <moment>; why: <words>; gone: "true"?   # gone — the confirmation «no server» when the resource was never heard
```

The server door row `platform/doors/<host>` (the writer is the resource of the server) has the form of
[P/05 N1.4](../../05-resource/spec/05-resource.norms.md) `door_row` (family `doors`); the console reads it for the state of the
resource and the knownness of the server (N2.1) and deletes it at a decommissioned server (N3 «decommission_server»).

### N1.2 Drain

<!-- req: P/06.6-R005 -->

```yaml
platform/drain:  {server: <server> | "", at, revision}   # one server at a time; the writer is the console (admin); the controller reads (P/04 N1.1)
state:
  draining:        <server> | ""
  safe:            all subsystems safe
  would_strand:    {<sub>: [id…]}                      # a probe without modelling the placement: all units of the workers of this server
                                                         # and all unplaced ones (N2.2)
  subsystems:      {<sub>: {draining, subsystem, workers, units, pending_writes, pending_unsaid?, would_strand, safe}}
  safe(sub):       units == 0 ∧ pending_writes == 0 ∧ pending_unsaid empty
  pending_writes:  Σ over the workers of the server of the heartbeat field pending_writes — a JSON integer without a fractional part and an exponent,
                   0 ≤ x ≤ 2^53 − 1 (the form int of [the row check contract](../../../common/contracts/row-check.md) «Preparation of fields»: «An `int` value at the input of the door»): the base worker of the platform (P/03.4 N1.1) writes
                   0 into the heartbeat itself if the subsystem has not said its own (a subsystem with a buffer on disk says its own number);
                   no field / a word / a fraction, including `0.0`, `1000.0`, `-0.0`, `1e3` / more than 2^53 − 1 / an unreadable or
                   stale heartbeat → pending_unsaid (the drain is not safe)
  server_of:       a worker of the server — by the field server of a readable heartbeat; the heartbeat does not read — by server of its slot
                   `<sub>/slots/<name>` (P/03.2 N1.4): such a worker goes into pending_unsaid, the units of its assignment
                   `<sub>/workers/<name>` — into units and would_strand
journal:  drain.started {server, user}; drain.ended {server} — there are no other kinds of the drain journal (no `drain.cleared`)

          # the console journals of this chapter (schema.raised, policy.changed, drain.*, server.decommission_*) — the tree audit/console (the event log contract `journal`,
          # role console); the journals of the unit and table doors (<t>.written/<t>.deleted, unit.changed) — chapter 6.1
```

`GET /drain` returns `DrainState` whole, without a filter by grants: the drain is a state of the whole cluster, the door requires `view` on
`*` ([the gate and pass contract](../../common/contracts/gate-and-pass.md) `need`), a narrow grant — 403; `safe` is over all
subsystems (the scenario — the acceptance of chapter 8.4, sc. 01 steps 25–26).

A stale heartbeat is one that is not fresh by [the observation contract](../../common/contracts/observation.md) «Freshness»: the version has not
changed within the last LOST_AFTER.

### Data families (built from the standard files)

The form of the rows and objects that the chapter owns by the [catalog](../../common/data/catalog.tsv) is the JSON Schema 2020-12 of the family (ADR-0092). An instance of a row is `{key, row}`, of an object `{key, object}`; the key is the grammar of the column `key` of the catalog. The fields of `row` are the values of `items` after the [codec](../../common/data/codec.tsv): the writer checks the schema and its `$defs.writer`, the reader the schema (layer 3 — the words `x-*` of the schema). Unreadable — the row did not decode or did not pass the schema in the reader's mode; the outcome is by the table of outcomes of the family: the path is a prefix of the path of the refusal (empty — the whole row); with several paths of refusal the outcome of the least priority applies.

## N2 Doors

<!-- req: P/06.6-R006 -->

The console doors through which the operator talks to the controller and the platform. The HTTP forms and the closed sets of codes are
[the lesson contract](06-console.api.openapi.yaml); every `GET` has a `HEAD` — the same code and headers without a body
([chapter 6.5](06.5-console.norms.md) N2). The common console refusals are chapter 6.5 N4; they are `{detail, error, field?}` (chapter 6.1 N2 «Refusal: `error` and `field`»), not a Fault
of the store. The state, the rights and the chosen kind of id are checked after the static form. There are no new doors of moving and
rebalancing.

### N2.1 Inputs

<!-- req: P/06.6-R007 -->

PUT /policy takes closed PolicyInput with servers only (shared or distinct); revision is not an input field. Policy with revision remains the response form.

The parsing of a request is [chapter 6.5](06.5-console.norms.md) N2 «Console request parsing» (P/01.1 N2.1 with the deviations of the console);
the controller doors have no deviations of their own (a repeat of `server` at `POST /drain` — 400 by the common rule).

`/policy`, `/unplaceable` and `/where/{id}` belong to the chosen subsystem; at the root one they are
without a prefix, at a mounted one — with `/<sub>`. `/drain` and `/servers/{server}/…` are located
at the console root and cover all its manifests. A subsystem prefix does not create copies
of the cluster rows. The rights — the role `console` of [P/02.5 N1.4](../../02-installer/spec/02.5-installer.norms.md); the order of the gate — [chapter 6.3](06.3-console.norms.md) N1.3 `identity` and `need`. The standard servers of these three path items
give both full URLs; the common /drain and /servers/{server}/… do not inherit the prefix.
The name sub explicitly chooses a loaded manifest, including CONSOLE_ROOT (chapter 6.5 N2).

| Operation | Input | Success |
|---|---|---|
| GET /policy | no body | 200 Policy: `{servers: shared \| distinct, revision}`, the effective value; `revision` 0 — no row |
| PUT /policy | a required object with only `servers` | 200 Policy after the write; journal policy.changed |
| GET /drain | no body | 200 DrainState, a snapshot of the state by N1.2, with `revision` of the row `platform/drain` |
| POST /drain | a required non-empty query `server`, no body; no `server`, it is empty, repeated or not by the server name grammar — 400 `{detail, error}` by N4 | 200 `{draining: server}`; a repeat of the same server is idempotent, another one during an active drain — 409; the write `{server, at, revision}` — by `cas` of the read version of the row (no row — `cas ""`), conflict → re-read and decide anew, the retry limit exhausted — 503 (N3 «drain — start») |
| DELETE /drain | no body | 200 `{draining: ""}`, also if already removed; the end of the drain is one word: the write `{server: "", at, revision}` by `cas` of the read version (conflict — re-read), do not delete the row; no row or `server: ""` in it — write nothing |

**Replay memory**. `PUT /policy`, `POST` and `DELETE /drain`, `PUT` and `DELETE /servers/{server}/labels`, `POST` and `DELETE /servers/{server}/decommission`,
`PUT /schema` read the optional `Idempotency-Key` by the rule of [chapter 6.1](06.1-console.norms.md) N3 «replay memory»: the key is `(user, method, path, key)` (user, method, path, key), the order is
«parsing of the request → claim → pass of the door → write under the claim guard → answer into the claim», an answer `< 500` is remembered, the term is as at `POST`. Another body or another query input
under the same key (`server` at `POST /drain`, `version` at `PUT /schema`) — 422 `key reused`; a foreign pending one younger than 30 s — 409 `in flight`; a key out of form — 400 `Idempotency-Key required`.
The claim of `PUT /policy` is `<sub>/idem/<key>` of the chosen subsystem; at the cluster doors `/drain`, `/servers/{server}/…`, `/schema` it is `<CONSOLE_ROOT>/idem/<key>`
([chapter 6.5](06.5-console.norms.md) N1.1): they have no family of their own, the path in the key distinguishes the doors. Without the header the doors are as before.
The doors that write `revision` hold the intended `revision` in the claim before the write, as chapter 6.1 N3 «edit» step 5a. The one who took over a claim looks at the target before `If-Match`: the row has this `revision` → written by this claim, the answer by step 9;
`DELETE` of the labels: no row → the same. Otherwise the pass anew would raise `revision` a second time and refuse its own write with `412`. The decommission of a server does not write `revision`; its taken-over claim passes the door anew: it converges.

**Row version**. The snapshots of settings — `<sub>/policy`, `platform/servers/<host>`, `platform/drain`, `platform/schema` — carry `revision`: 1 at the creation of the row, +1 for every write. A write goes with `cas` of the read version (no row — `cas ""`):
without it two writes would raise `revision` to the same number. A conflict — re-read and check the condition again, the retry limit exhausted — 503 `unavailable`. A pass without a write (`POST /drain` of the same server, `DELETE /drain` without a drain, `DELETE` of the labels without a row)
does not move `revision`. Removed labels count anew. A row without a readable `revision` reads as 0, the next write writes 1.

`If-Match`, `ETag`, the index and `412 revision moved` are [chapter 6.1](06.1-console.norms.md) N2 «Versions», with the same words:

- `ETag` is carried by `GET /policy`, `GET /drain`, `GET /schema`, `GET /servers/{server}/labels` and the success answers of `PUT /policy`, `POST` and `DELETE /drain`, `PUT` of the labels, `PUT /schema`, if the row exists. No row — no `ETag`; `DELETE` of the labels removes the row — no `ETag`.
- `If-Match` is read by `PUT /policy`, `POST` and `DELETE /drain`, `PUT` and `DELETE` of the labels, `PUT /schema`. The decommission of a server does not read it: it is a request, not a snapshot of a setting, and `PUT` does not edit its fields.
- The order: the parsing and the form of `If-Match` → the claim → the read of the row → the condition → the pass of the door → the write. The condition stands before the checks of the door: the client judges the row that it saw.
- No row and `If-Match` present — 412 with `revision: 0`, without `row`: the condition names a version that does not exist. To create a row, the client sends a request without `If-Match`.
- `row` of the refusal 412: `{servers, revision}` at the policy, `{labels, revision}` at the labels, `{server, at, revision}` at the drain, `{version, revision}` at the schema.

In all rows of the table the JSON objects are closed: there are no unlisted fields. A success `{}` contains a JSON object,
not an empty HTTP body. A label is by [the label alphabet](../../common/contracts/labels.md) (1–64 ASCII characters: the first a letter/digit,
then a letter/digit, `_`, `.`, `:`, `-`). A query list is parsed by commas, without empty elements,
except a wholly empty string; a server in path/query is a server name: a host name of RFC 1123 — labels separated by «.», a label of 1–63
characters `[A-Za-z0-9-]`, not starting and not ending with «-», in total not more than 253 bytes (`..`, `.`, a space, `/` are not a name);
otherwise — 400 before the existence check. Into `will_move` and
`would_move` go only the references available to the caller by `view`; the list can be empty.
The label forecast `would_move` / `will_move` is the set of units that **leave** the server s, not that come to it: a unit of a subsystem with `constraint: labels-subset` whose worker of the effective placement
([the observation contract](../../common/contracts/observation.md) «Reading the decision: intent → placement → intent») is fresh by the same
contract and whose heartbeat names `server: s`, while the labels of the unit (its field `labels`, [P/04 N1.3](../../04-controller/spec/04-controller.norms.md)
`constraint`) are not a subset of the checked set: the query `labels` or the body of `PUT`; at `GET` without the query — the current
effective labels of the server (the row `platform/servers/<s>`, otherwise the node labels — P/04 N1.3). Unplaced units, units
of other servers and units which the set would suit on this server do not enter the forecast. The references `<sub>/<id>` are without
repeats, in ascending order of the UTF-8 bytes of the reference string. The forecast is a read output: a non-answer when reading heartbeats and placements (and their listing) is
`lapse` of the observation contract, the forecast by the memory of the last read versions; a source not read even
once since the start — 503 `unavailable`, at `PUT` — before the write of the row: there is no write without an answer. The write of the label row by `PUT` does not depend
on the heartbeats and is not an admission by observations.
The subsystem name in the reference `<sub>/<id>`, in the keys of the drain maps and in the field `subsystem` follows P/02.1 N1.2,
including the whole closed list of reserved names; the grammar of the id itself is [chapter 6.1](06.1-console.norms.md) N1.3.
The existence of a server is determined by all subsystems and resources of the console: a server is known if there is at least
one piece of evidence — the heartbeat of the resource of this server, the row `platform/doors/<host>`, the field `server` of a worker heartbeat
or of a slot of any subsystem, and for the label operations also the row `platform/servers/<host>`. For all three
label operations and both decommission methods an unknown server — 404. A wrong form of the body/labels — 400 before this check.

### N2.2 Full read bodies

<!-- req: P/06.6-R008 -->

- **Unplaceable:** `{id, labels, workers_live, why?}`. `id` is a string; `labels` is an array of labels;
  `workers_live` is an integer ≥ 0; `why`, if present, is a non-empty reason from the field `unplaceable` of the last
  pass report ([P/04 N1.2](../../04-controller/spec/04-controller.norms.md)): the controller decides, the console reads. These are the units without a place,
  including at an empty pool, and the units for which the constraints give no candidate.
- **Where:** `{worker, server, reason, directory, scans, door?}` by [chapter 6.5](06.5-console.norms.md) N3 «`/where/<id>`». `worker` is a non-empty
  assignment name by the slot grammar of P/03.2 N1.4; `server` — from the worker heartbeat, otherwise from the field `server` of its slot row,
  otherwise null; `reason` is a
  non-empty reason of the decision; `directory` is the name from the last scan of assignments or null;
  `scans` is the number of completed scans ≥ 0 since the start of the console. The directory cache can lag behind the decision;
  the frequency of the assignment scan is «Implementation decides» item 1. For an unplaced unit, 404 `{reason}` takes the reason
  from the field `unplaceable` of the pass report, and without it — `not placed: no worker holds it`.
  The optional `door` contains `url`, `token` (non-empty strings), `expires` (a number of wall seconds)
  and `routes` (an array of non-empty strings); the conditions of issue (`view` on the unit, the journal `door.issued`) and the term (TTL DOOR_TOKEN_TTL) are chapter 6.5 N3 «`/where/<id>`», not a right that follows from the schema.
- **DrainState:** `{draining, safe, would_strand, subsystems}`. `draining` is a name or `""`;
  `safe` is a boolean; `would_strand` is a map subsystem → array of ids.
  The value `subsystems[sub]`: `{draining, subsystem, workers, units, pending_writes, would_strand, safe, pending_unsaid?}`.
  `draining` is the same name or `""`, `subsystem` equals the key of the map; `workers`, `units`,
  `pending_writes` are integer counters ≥ 0; `would_strand` is an array of ids; `pending_unsaid`, if present,
  is an array of worker names by P/03.2 N1.4 without a readable counter. `safe` is computed by N1.2, not by the emptiness of
  `would_strand` — without modelling the placement: all units of the workers of this server and all unplaced units
  of the subsystem. The units of a worker are the union of its assignment (`<sub>/workers/<name>`) and `status[].id` of its heartbeat: an empty
  `status` with assigned units does not make the server empty; conversely, an empty assignment with a nonempty status does not make it empty. An id occurring in both is counted once per worker; `units` is the sum of these worker union sizes. Without an active drain the server set is empty, the counters are 0, `safe: true`;
  the probe of the unplaced units can still give a non-empty `would_strand`.
  The keys of the two maps coincide and correspond to the visible subsystems; the common `safe` is determined by all
  subsystems, not only by the visible ones, so that hidden units do not allow switching the server off.

If the needed read/write of the store is not confirmed, the operation returns 503 `{detail, error: unavailable}`;
the read outputs (`GET /drain`, `GET /schema`, `GET /unplaceable` — `workers_live`) on a non-answer in the read of observations (heartbeats, door rows, holds, labels, their listing) are
`lapse` of the observation contract, the answer by the memory of the last read version with its age; 503 — only if the source was not
read even once since the start and the answer would assert emptiness or zero; writes and admissions (`PUT /schema` step 3, `POST /drain`, `POST /servers/{server}/decommission`) —
only by the reads of their own pass: a non-answer — 503, no write; required reads that are not observations (the row `platform/schema`,
the rows of units and tables) — 503;
on an unknown outcome of a write the client first re-reads the state or repeats the request with the same `Idempotency-Key`. `busy` and `denied` have separate reasons of chapters 6.3
and 6.5 (N4). The codes and bodies of the common refusals are described at each operation of the lesson contract. The operational 404 differs from
`NoRoute`: at a server — `{detail, error}`, at an unplaced unit — `{reason}`.
The decommission refusal 409 contains `{detail, error: "server answers", server, may_confirm_gone}`;
`may_confirm_gone: true` is allowed only for a never-heard resource and in the absence of fresh
evidence of a worker/slot/resource. With a live server `gone: true` does not bypass the refusal: any fresh evidence —
409 with `may_confirm_gone: false`, and `gone: true` does not change it. The freshness of evidence is «heard within the last LOST_AFTER»
of [the observation contract](../../common/contracts/observation.md) (N3 «decommission_server»).

### raise_schema(N) — console, admin

<!-- req: P/06.6-R011 -->

```
1. the string N — only ASCII [1-9][0-9]* whole (without a sign, spaces and a leading zero), the value ≥1 (N2.3)      → otherwise 400 «a version is a whole number from 1»
   If-Match — the form; the condition by the read row — before step 2 (N2.1 «Row version»)
2. the row platform/schema: not a number → 409 «mend the row first»; have > N → 409 «does not go back»
3. its own SCHEMA < N → 409; live processes (the heartbeats changed before the eyes of the reader within the last LOST_AFTER — the observation contract):
   any with an unknown schema → 409 «still running: …»; the read of the heartbeats of this pass is not confirmed
   (a non-answer, including of the listing) → 503 unavailable, no write: it does not decide by memory, not an empty membership
4. write {version: N, at, revision: the read one + 1} with cas; journal schema.raised
```

Step 3: «live» — by [the observation contract](../../common/contracts/observation.md) «Freshness» (the boundary — the vector [`fresh-age`](../../common/vectors/fresh-age/README.md)). The raise is a write: it decides only by the reads of its own pass; the observation memory (`lapse`) is no ground for it — by that memory
a heartbeat ages within LOST_AFTER, the process drops out of the «live» ones, and the raise would pass blindly.

Two admins are still protected by CAS: the loser re-reads the state and does not announce success.

### drain — reading the state

<!-- req: P/06.6-R013 -->

```
for each manifest: the workers of the server (heartbeats; the heartbeat does not read — server of the slot, N1.2 server_of),
for each such worker w: ids(w) = set(assignment(w)) ∪ set(heartbeat(w).status[].id),
units = Σ |ids(w)|; an id present in both sources counts once for that worker,
pending = Σ pending_writes (none/a word/a fraction/an unreadable heartbeat → unsaid),
would_strand = all units of the workers of the server and all unplaced units of the subsystem — without modelling the placement (N2.2 `DrainState`)
safe = Σ units == 0 ∧ Σ pending == 0 ∧ unsaid empty
```

An unreadable/unconfirmed required source is handled by the existing N1.2 and N2 observation/lapse/unavailable rules, never replaced by an empty set or zero. In particular an unreadable heartbeat still gives unsaid, so an empty assignment cannot make safe true. The answer is an observation; it does not replace the maintenance stop window before powering a server off.

### drain — start (`POST /drain?server=s`)

<!-- req: P/06.6-R014 -->

```
1. read platform/drain (not confirmed → 503); If-Match present and not equal to the version of the row → 412 revision moved (N2.1 «Row version»); server of the row = s → 200 {draining: s}, write nothing
2. server of the row — another non-empty one → 409 «<server> is already draining; one server at a time»
3. write {server: s, at, revision: the read one + 1} with cas of the read version (no row — cas ""); conflict → from step 1;
   the retry limit on conflict exhausted → 503 unavailable; success → journal drain.started, 200 {draining: s}
```

**Races.** Two simultaneous `POST /drain` of different servers: `cas` lets one write through; the loser re-reads — sees
another server and answers 409, for its own one — 200 without a write. The controller reads draining once per pass; what was assigned earlier can arrive later. `safe` is a conclusion from the observed placements and the fresh known heartbeats, not an atomic snapshot and not a lock on new assignments. Before switching off, the operator stops new writes/assignments to the server, waits for the started actions to complete and checks the state again. Failed to confirm quiescence — the switch-off is postponed; one `safe: true` is not enough.
