## Н1 Форма

**Время.** Поля времени строк и объектов главы — время по [канону Н0 P/01.1](../../01-store/spec/01.1-store.norms.md#время-в-строке): `<sub>/sweep` — `at`; штампы строк таблиц — `at`, `made_at`; надгробие `.gone/<ключ>` — `written` ([P/05](../../05-resource/spec/05-resource.norms.md) Н1.1 «Надгробия»). У строки единицы, счётчика `next_id` и заявки `idem` полей времени-строки нет (время заявки — форма реализации, «Решает реализация» п. 3; слот и пол эпох — [P/03.2 Н1](../../03-worker/spec/03.2-worker.norms.md) «Время»).

**Данные** ([каталог](../../common/data/catalog.tsv)):
- владеет: `<sub>/<manifest:unit.rows>/<id>`, `<sub>/next_id`, `<sub>/idem/<key>`, `<sub>/blobs/sha256-<hex>`, `<sub>/sweep`, `<sub>/<manifest:tables>/<имя>`;
- пишет: `.gone/<ключ>` (put), `<корень событий>/audit/<роль>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<корень объектов>/<каталог>/~lock` (create);
- читает: `platform/manifest/<sub>`, `platform/manifest/<sub>/rev`, `<sub>/placement/<id>`, `<sub>/heartbeats/<имя>`, `<sub>/holds/<место>`, `<sub>/state/<имя>/<id>`.

Журнал `audit` главы — виды `unit.*`, `<t>.written`, `<t>.deleted`, `next_id.recovered`; `<sub>/holds/<место>` читается для `held_by`
таблицы мест (разбор ревью стадии B 6–7, № 41). Пакетная дверь (Н2 «Пакетная дверь») пишет те же строки тех же семей.

Строку единицы контроллер удаляет по `placement.unplaced.delete_after`, `placement.retire_when.delete_after` и
`placement.ends` ([P/04](../../04-controller/spec/04-controller.norms.md) Н1.3), воркер — по `worker.deletes` (участники `delete`);
заводит и продлевает её ещё заказчик — воркер другой подсистемы по своему `worker.creates`, только строки своего `made`
([P/03.6](../../03-worker/spec/03.6-worker.norms.md) Н1.6): строка заказа двухписательная — оператор дверью, заказчик
библиотекой (решение ADR-0091 п. 1, исключение из «одного писателя» ниже). Состояние единицы `<sub>/state/<имя>/<id>` пишет
держатель единицы (P/03.6 Н1.7), удаляет контроллер (P/04 Н3); консоль читает его для представления единицы (Н2);
таблицу из `worker.writes` пишет её воркер (участник `cas`, [P/03.4](../../03-worker/spec/03.4-worker.norms.md) Н1.6);
копию тела кладёт и снимает ресурс (участник `put`, `delete`, P/05 Н1.1 «Тела у ресурса»). Надгробие тела `.gone/<ключ>`
— строка-объект ресурса (owner P/05; разбор ревью стадии A 6–7, № 17): консоль его пишет (`put`) на завершении окна
уборки (Н3 «уборка тел»). Пульсы `<sub>/heartbeats/<имя>` консоль читает для `rows` в `GET /{rows}` (Н2; форма —
P/03.4 Н1.1).

### Н1.1 Раскладка ключей подсистемы

`unit`, `unit.rows` и `unit.id` обязательны без умолчаний (P/02.1 Н1.2). `unit.rows` — имя по грамматике и не из перечня запрещённых имён сводной таблицы P/02.1 Н1.2а (служебные семьи
этой раскладки, первые сегменты платформенных дверей, семьи объектов, а также cluster, worker, ts из оболочки
снимка [P/04 Н1.3а](../../04-controller/spec/04-controller.norms.md)). Непредставимое имя — отказ загрузки, не недостижимая дверь.

Все ключи подсистемы начинаются с её имени (P/02.1). У каждой строки один писатель — кроме строки заказа: её пишут оператор дверью и заказчик библиотекой (P/03.6 Н1.6; решение ADR-0091 п. 1); у семьи их может быть несколько, когда урок-владелец делит её по форме строки (просьбы — строка `<sub>/requests/<rid>` [главы 6.4](06.4-console.norms.md) Н1.5, писатели по `worker.requests`; таблицы — `worker.writes` Н1.6); права — роли и образцы P/02.5 Н1.4 (`console`, `<s>controller`, `<s>worker`).

```yaml
rows:                                  # строки хранилища (P/01.1)
  <sub>/<rows>/<id>:        {писатель: консоль; заказчик по worker.creates — строки своего made (P/03.6 Н1.6; ADR-0091 п. 1); удаление — ещё контроллер по placement.unplaced.delete_after, retire_when.delete_after, ends и воркер по worker.deletes (участники delete; разбор ревью стадии B 6–7, № 23)}
  <sub>/state/<имя>/<id>:   {писатель: держатель единицы под стражем эпохи (P/03.6 Н1.7); удаление — контроллер (P/04 Н3, уборка); ADR-0091 п. 3}
  <sub>/next_id:            {писатель: консоль; items: {n}}                                 # n — последний выданный номер (Н1.3; № 38)
  <sub>/idem/<key>:         {писатель: консоль; <key> — Н3 «память повторов»; форма — решает реализация (п. 3); только консоль читает}
  <sub>/policy:             {писатель: консоль; items: {servers: shared | distinct, revision}}  # глава 6.6
  <sub>/slots/<имя>:        {писатель: держатель; контроллер — отдать (P/04 Н3 «судьба», release); форма P/03.2 Н1.4}
  <sub>/holds/<место>:      {писатель: держатель; форма слота без server, плюс by — P/03.2 Н1.3}
  <sub>/epoch/<id>:         {писатель: воркер; items: {epoch}; никогда не удаляется}
  <sub>/placement/<id>:     {писатель: контроллер; items: {worker, reason, at, rev, manifest_rev} — P/04 Н1.1}
  <sub>/workers/<имя>:      {писатель: контроллер; items: {units, rev} — P/04 Н1.1}
  <sub>/controller/placement_turn, <sub>/controller/placement_intent: {писатель: контроллер; строки допуска P/04 Н1.5; не удаляются}
  <sub>/requests/*:         {писатели: консоль (дверь); воркер по worker.requests; ресурс — free_ask своей формы — P/05 Н1.4}
  <sub>/asked/*:            {писатель: консоль; items: {rids, by, at} — учёт человека, глава 6.4 Н1.5 ledger}
  <sub>/<таблица>/*:        {писатель: консоль; таблица из worker.writes — её воркер, консоль только читает — Н1.6; удаление по delete_after — жнец консоли, глава 6.4 Н3 `tables`}
  <sub>/sweep:              {писатель: консоль; items: {at, digests} — Н1.5 sweep}
  <sub>/decommissioned/<сервер>: {писатель: контроллер — P/04 Н1.1, Н3 «вывести_сервер»}
platform rows:
  platform/epoch_floor:     {items: {floor, generation_at}; писатель — операция «восстановить хранилище» P/01.3 Н3 (поднимает пол на поколение); право — только у неё (P/01.2 Н1.3 never)}
objects:                               # объекты, не строки; дверь объектов — P/05 Н1.1
  # heartbeats — P/03.4 Н1.1; contenders — P/03.2 Н1.4а; snapshot — P/04 Н1.3а; controller/pass — P/04 Н1.2;
  # blobs — Н1.5; метка просьбы — строка-объект objects/<sub>/commands/<rid> договора просьбы и её метки (common/contracts/request-mark.md) «Метка» mark (ключ
  # хранилища строк, не дверь объектов; каталог данных)
  <sub>/heartbeats/<имя>, <sub>/contenders/<имя>/<коробка>, <sub>/snapshot/*, <sub>/controller/pass,
  <sub>/blobs/<дайджест>
reserved_table_names:   <rows> и перечень запрещённых имён таблиц P/02.1 Н1.2а
```

`controller` не может быть именем unit.rows или таблицы подсистемы: этот префикс содержит
служебные строки допуска [P/04 Н1.5](../../04-controller/spec/04-controller.norms.md) (`placement_turn`, `placement_intent`). Загрузчик отказывает таким значениям (перечень P/02.1 Н1.2а).

### Н1.2 Строка единицы

Форма строки единицы (`id`, `revision`, `born`, `made`, `deleted`, поля), `values_by_type`, `absent` и `platform_fields` — [договор проверки строки](../../common/contracts/row-check.md)
«Строка единицы» (перенесено без изменения поведения; W03-E07); векторы — [`values-by-type`](../../common/vectors/values-by-type/README.md).
`index` в ответе двери — индекс хранилища строки (Н2 «Версии»), в строке его нет.

Поле bytes остаётся обычным полем единицы только в манифестах без blob: сочетание с любым
blob-полем отвергается загрузчиком по P/02.1, чтобы счётчик `bytes` в ответе двери байтов `PUT /{rows}/{id}/{blob_field}` (Н2 «Двери тел и таблиц») не затирал поле.

Состав клиентских полей при создании и правке (переданное, `inherit`, `default` и `{id}` в нём, пустая форма типа), формы
`list`, `int`, `json` на входе — [договор проверки строки](../../common/contracts/row-check.md) «Подготовка полей».

### Н1.3 Идентификатор

```yaml
id:
  numeric:                                  # unit.id: numeric
    rule:    десятичное целое ≥ 1 из счётчика <sub>/next_id: n — последний выданный номер, следующий — n + 1 (разбор ревью стадии B 6–7,
             № 38); строки нет — recover ниже и создание cas "" с n = выдаваемый номер: без единиц и заявок это 1, при уже
             существующих единицах — наибольший + 1, не 1 (выдать 1 — столкновение с живой единицей; (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7)); первый — 1; номер не используется повторно никогда,
             в пути — десятичная запись без знака, пробелов и ведущих нулей (`01`, `+1` — 400 `badkey`);
             надгробия считаются; номер, выданный отказанной попытке, не возвращается
    recover: только при полном подтверждённом перечне строк/надгробий и живых заявок; утрата истории или ошибка чтения не считается пустотой и не разрешает автоматическое восстановление. Счётчик не читается или строки нет → наибольший номер среди строк <rows>/ (с надгробиями) и номеров в живых заявках + 1 — выдаваемый
             номер; счётчик переписан целиком с n = этот номер (последний выданный, № 38); номера отказанных попыток следов не оставляют и после восстановления МОГУТ выйти снова —
             единственное исключение из «никогда», журнал `next_id.recovered {from, to}`
  named:                                    # unit.id: <поле> — [договор проверки строки](../../common/contracts/row-check.md) «Идентификатор и ограничения полей»
  made_prefix:                              # ADR-0091 п. 1
    rule:    создание дверью (POST) id, который начинается с «<заказчик>-» подсистемы, объявившей worker.creates к этой
             таблице (каталог манифестов, P/02.1 Н3), — 400 «names starting with "<заказчик>-" are made by <заказчик>
             (worker.creates)», и над надгробием: под этим префиксом живут только строки заказчика; строка с таким
             именем, созданная до объявления заказчика, остаётся и занята — без своего made заказчик её не пишет
  made_key:                                 # ADR-0091 п. 1
    rule:    у строки с made поля, которые называет key заказчика (worker.creates[].key, P/03.6 Н1.6), неизменяемы и
             для двери, как fixed: правка иным значением — 400 «<поле> is fixed»; прочие поля оператор правит дверью
# tombstone, unique, canonical_url, ref_and_must_match — [договор проверки строки](../../common/contracts/row-check.md) «Идентификатор и ограничения полей»
```

Профиль восстановления numeric не совместим с физической уборкой: unit.id: numeric вместе с placement.unplaced.delete_after — отказ загрузки P/02.1. Успешные номера представлены сохранёнными строками/надгробиями; очистка done-заявок это не отменяет. Произвольная утрата этих строк не покрыта формулой recover.

Любое имя, которое разрешают грамматика id и слота и предел полного ключа P/01.1, хранит любая реализация: имена файлов
(каталоги бакетов — договор журнала событий «Имена файлов в общих деревьях») реализация кодирует сама, более узкого файлового профиля нет — иначе части разных
реализаций над одними данными несовместимы (сверка python и go М10/3–5, U20).

**Срок done-заявки.** Завершённый сохранённый ответ заявки с HTTP-кодом <500 ДОЛЖЕН сохраняться не менее
86400 секунд с момента его сохранения. Для очистки используется местный монотонный возраст;
после восстановления памяти новый наблюдатель считает её свежей, а не доверяет чужим wall-часам.
Это не распространяет done на 5xx или pending: их судьба остаётся по Н3.

### Н1.4 Потолки

Проверяются у двери до чтения тела, где возможно; отказ — не усечение. Ответ отказа до чтения тела доходит до клиента
по правилу P/01.1 Н2.1 «Ранний отказ».

### Н1.5 Тела

Blob объявляется только в unit.fields; blob в таблице вне профиля и отвергается загрузчиком.
Имя blob-поля — 1–64 ASCII: первый A-Z/a-z/_, остальные A-Z/a-z/0-9/_.
Пустое имя, разделитель пути, точка, процент, пробел, управляющий или не-ASCII символ
не представляют blob-дверь этого урока: отказ загрузки `refused:value` с путём поля.
Прочие поля этим ограничением автоматически не сужаются.

Манифест с любым blob-полем единицы не объявляет unit.fields.bytes: отказ загрузки
`refused:value` по P/02.1. Без blob поле bytes допустимо. Это ограничение сохраняет
полную Unit в ответе загрузки; переименование счётчика или новая оболочка не вводятся.

```yaml
field:    type: blob; в строке — "sha256-<64 hex>"; байты в теле строки → 400 «takes a digest, not the bytes (N of them):
          PUT the bytes to /<rows>/<id>/<поле> and the row gets the digest back»; в snapshot — манифест не грузится
object:   <sub>/blobs/sha256-<hex>; имя — дайджест байтов; читатель сверяет (BlobMismatch — «the object was replaced»)

mirror:   копия тела соседу и её дверь — P/05 Н1.1 «Тела у ресурса» (стадия B; решение по В2 переноса)
delete:   надгробие и схождение копий тел — договор надгробий common/contracts/tombstone.md (владелец P/05; C06-BLOB-GC-33-01)
sweep:    <sub>/sweep {at, digests}  — писатель консоль; раз в 60 с
          # байты строки: at — стенные секунды первой отметки партии, текст по values_by_type Н1.2 (float);
          # digests — список "sha256-<hex>" по правилу list Н1.2 (через запятую); пустая партия — digests: ""
          # или строки нет, at тогда не читается; пример: {at: "1760700000.5", digests: "sha256-ab…,sha256-cd…"}
  mark:   только при пустой прежней партии дайджесты без ссылок из строк (≤ SWEEP_LIMIT 64) → записать с cas; непустую не освежать; ничего не удалять;
          ссылка — поле blob строк своей подсистемы; строка другой подсистемы (её строковое поле с <sub>/blobs/<digest>) тело не держит:
          кому тело нужно дольше, копирует его в своё blob-поле (C06-SWEEP-FOREIGN-REF-01, решение «Архитектора» 2026-10-29, разбор V/04)
  wait:   SWEEP_GRACE 300 с
  sweep:  удаление только в исключительном окне обслуживания Н3; обычный фоновый проход лишь отмечает/ждёт.
          После остановки писателей проверить ссылки снова; список снять с cas (конфликт — ничего не удалять); удалить объекты.
          put_blob снимает digest с cas; эта отмена — помощь отметкам, не защита параллельного удаления
```

Копия тела у ресурса (`mirror`) — [P/05](../../05-resource/spec/05-resource.norms.md) Н1.1 «Тела у ресурса» (стадия B); надгробия (`delete`) — [договор надгробий](../../common/contracts/tombstone.md) (C06-BLOB-GC-33-01).

### Н1.6 Объявленные таблицы

```yaml

  <t>:
    key:      <несекретное поле type string> | <шаблон по P/02.1 Н1.4, requests.key>   # число подстановок не ограничено двумя;
                                                     # пример: "{of}-{from:int}-{to:int}"; итоговое имя по Н2
    fields:   {<поле>: {type, required, enum, default, schema, ref, must_match, bound_to, credentials, secret_in, schemes}}
              # без fixed, inherit, merge, unique (P/02.1)
    schema:   JSON Schema на всю строку
    stamp:    [by, at, made_at]                   # что консоль дописывает при каждой записи POST:
              # by — пользователь записи; at — стенные секунды этой записи; made_at — стенные секунды первой записи
              # строки, перезапись его сохраняет; в строке хранилища — текст по values_by_type Н1.2 (float),
              # в TableRow — by строка, at и made_at числа; пример строки: {by: "admin", at: "1760700000.5",

                                                  # у таблицы мест и таблицы удержаний ключа нет: отказ загрузки (P/02.1 Н1.4, строки 125, 126)

             иначе refused:value при загрузке. Прочие служебные имена единицы (id/worker и т.д.)
             сами по себе полям таблицы не запрещены; значения проверяются по объявлению.
names:      грамматика имени и перечень запрещённых имён таблиц — сводная таблица P/02.1 Н1.2а; не значение unit.rows;
            конфликт с любым именем подсистемы каталога — отказ каталога по P/02.1 Н3, а не разрешённое пересечение root/mount

            консоль только читает (GET с полями), POST → 403 denied «written by its worker»; DELETE оператора → 200 с cas по

            <sub>/holds/<имя> ([договор наблюдения](../../common/contracts/observation.md) «Удержание места»), иначе null;
            чтение удержания или пульса держателя не подтверждено, строка удержания или пульс держателя не читаются — null (не
```

### Семьи данных (построены из стандартных файлов)

Форма строк и объектов, которыми глава владеет по [каталогу](../../common/data/catalog.tsv), — JSON Schema 2020-12 семьи (ADR-0092). Экземпляр строки — `{key, row}`, объекта — `{key, object}`; ключ — грамматика колонки `key` каталога. Поля `row` — значения `items` после [кодека](../../common/data/codec.tsv): писатель проверяет схему и её `$defs.writer`, читатель — схему (слой 3 — слова `x-*` схемы). Нечитаемо — строка не раскодировалась или не прошла схему в режиме читателя; исход — по таблице исходов семьи: путь — префикс пути отказа (пустой — строка целиком), при нескольких путях отказа действует исход с наименьшим приоритетом.

## Н2 Двери

Пути единиц относятся к CONSOLE_ROOT без префикса или к явно названной подсистеме
под /{sub}, включая root. Полный URL в OpenAPI задают стандартные servers + paths
по [главе 6.5](06.5-console.norms.md) Н2; префикс не является частью id.

Дверь единиц — консоль подсистемы (глава 6.5 описывает страницу; здесь — строки). Все тела — JSON-объекты; ответ-отказ — `{detail, error, fault?, field?}` (Н2 «Отказ: `error` и `field`»).
Разбор запроса — глава 6.5 Н2 «Разбор запроса консоли» (P/01.1 Н2.1 с отступлениями консоли); своих отступлений у двери единиц нет.

[Контракт двери единиц](06-console.api.openapi.yaml) — OpenAPI 3.1, пути `/{rows}`, `/{rows}/{id}`.

Значения строки хранилища из Н1.2 и JSON-ответа различаются: в ответе числа и булевы имеют свои JSON-типы,
списки — массивы, `json` — значение JSON, строковые поля — строки; непустой секрет заменён `"***"`,
пустой остаётся пустым (глава 6.2). `id` выдаётся строкой, `revision` — целым числом от 1.
Отсутствующие `inherit` и `json: null` не добавляются в ответ. У поля с `inherit` значение `null` в теле создания или
правки значит «не задано»: элемента в строке нет, значение снова наследуется (`PUT {"step": null}` возвращает `step` к
наследуемому); у прочих полей, кроме json, `null` — 400 по типу. Путь сравнивается байт в байт (глава 6.5 Н3 шаг 5):
`/counters/` — не маршрут, 404. Сегмент id процент-декодируется после выбора маршрута (RFC 3986 §2.1): `/counters/a%20b` —
единица `a b`, `%31` у numeric — `1`; результат не UTF-8 или не по грамматике id Н1.3 — 400 `{detail, error: "badkey"}`, как ключ Н3 (C06-UNIT-ID-BADKEY-01, решение «Архитектора» 2026-10-28). Заголовки, которые
читает дверь (`Idempotency-Key`, `If-Match`): значение без OWS по краям (RFC 9112 §5.5); заголовок дважды — 400, как
повтор параметра; значение `If-Match` — Н2 «Версии». Остальные имена полей определяет манифест;
открытый набор свойств общей схемы не разрешает неизвестные поля.

| Операция | Успешное тело | Норма-владелец |
|---|---|---|
| POST | типизированная строка с `id`, `revision`, `index` и `worker: null`, `ETag`; при повторе — сохранённый ответ целиком | Н1.2, Н3 создать; P/06.1-02, 03, 07 |
| PUT | типизированная строка после правки с `id`, новой `revision` и `index` (у строки заказчика — с `made`), `ETag`; при повторе тем же ключом — сохранённый ответ целиком | Н1.2, Н3 править, «память повторов»; P/06.1-02, 03, 23 |
| DELETE | ровно `{deleted: <id как строка>}`, `ETag` — индекс надгробия; при повторе тем же ключом — сохранённый ответ целиком | Н3 удалить, «память повторов»; P/06.1-10, 23 |
| GET | ровно `{rows: [...], configured: [...]}`; `rows` — единицы пульса с `worker`, `server`, `age`, `worker_state` (правило ниже; пульсов нет — `[]`), `configured` — типизированные живые строки с масками и `index` (надгробий нет; порядок не нормирован), у строки заказчика — `made: {by, at, keep}`, при объявленном `unit.state` — `state: {<имя>: <значение>}` действующих состояний (ниже «Состояние в ответе»); двери `GET /<rows>/<id>` нет | собственный контракт Н2 (UnitList/RunningUnit); фильтрация по `view` — [глава 6.3](06.3-console.norms.md) Н1.3 `need` (GET/HEAD → view на единицу); форма пульса — [P/03.4 Н1.1](../../03-worker/spec/03.4-worker.norms.md) |

Ключ повторов — непустой сегмент без `/`, не равный `..`, не больше 200 UTF-8-байт. `maxLength` в схеме — только верхняя
граница числа символов; проверка байтов отдельная. POST и PUT требуют JSON-объект; набор `unit.fields`,
обязательность и типы проверяются по загруженному манифесту в порядке Н3. Схема не заменяет проверок состояния,
ссылок, прав и размера. При отказе выдаются ровно `detail`, `error` и, только для причин Н4, `fault` и `field`.
У `409 conflict` поле `fault` обязательно; `exists`, `in flight` и `key reused` его не добавляют. Слова `fault` —
закрытый словарь, векторы [`fault`](../../common/vectors/fault/README.md).


`GET /{rows}?deleted=1&about=<значение>` — другая выдача той же двери: надгробия, Н2 «Надгробия по `about`».

`HEAD /{rows}` — как `GET` без тела (глава 6.5 Н2); иной метод у `/{rows}` и `/{rows}/{id}` — `405`, путь длиннее `/{rows}/{id}` — `404` (Н4), кроме двери байтов `/{rows}/{id}/{blob_field}` (Н2 «Двери тел и таблиц»): на ней иной метод, чем `PUT`, — `405`; общие коды консоли (401, 403, 408, 413, 429, 503 busy) — глава 6.5 Н4. Отдельной двери `GET /{rows}/{id}` нет: единицу читают в составе `GET /{rows}` (этот Н2; фильтрация по `view` — глава 6.3 Н1.3 `need`).

Двери слота, эпохи и аренды перенесены в [P/03.2 Н2](../../03-worker/spec/03.2-worker.norms.md) (стадия B).

### Отказ: `error` и `field`

Отказ дверей глав 6.1, 6.2, 6.4, 6.5, 6.6 — `{detail, error, fault?, field?}` (ADR-0094 B5, доп. (13)); второй формы нет. Клиент выбирает действие по слову и
ставит ошибку у поля по `field`, поэтому его код не разбирает текст для человека. Слова главы 6.7 —
её Н4; сторожевая — [договор сторожевой и передачи](../../common/contracts/gate-and-pass.md).

- `error` — слово закрытого перечня [`refusal-words.tsv`](../data/refusal-words.tsv): постоянная строка без имён и значений. Дверь говорит
  только слова своих строк перечня и строк `*` с тем же кодом.
- `detail` — фраза для человека: имена, причина, предел. Точный текст — выбор реализации, кроме слов, которые называет Н4;
  значений секретов в нём нет (глава 6.2).
- `fault` — слово закрытого словаря, правила прежние. У 400 с `fault` слово `error` равно `fault`; у 409 с `fault` — `conflict`.
- Где норма называла фразу с именами, слово — класс строки [договора проверки строки](../../common/contracts/row-check.md) «Отказы»;
  класса нет — `refused`. Фраза остаётся в `detail`. Постоянная фраза нормы (`If-Match is a unit revision`) сама и есть слово.

**Формат `field`** (на него ссылаются P/07 и двери уроков P/08, P/10). `field` — строка JSON Pointer ([RFC 6901](https://www.rfc-editor.org/rfc/rfc6901)):
путь поля от корня JSON-тела запроса, форма `^(/([^~/]|~[01])*)+$`.

- Токены разделены `/`; `~` в имени поля пишется `~0`, `/` — `~1`; элемент списка — номер с нуля: `/start`, `/labels/2`,
  `/feed_secret`, `/config/feed_secret`, `/a~1b`.
- `field` есть только у 400, 409 и 412 и только у строк перечня, где колонка `field` не `-`. Отказ всего тела идёт без `field`, пустого
  указателя нет.
- Значение одно. Отказ называет несколько полей — `field` первое по порядку проверки [договора проверки строки](../../common/contracts/row-check.md),
  у `unknown field` — наименьшее имя по байтам UTF-8; остальные имена — в `detail`. Колонка `field` векторов
  [`row-check`](../../common/vectors/row-check/README.md) — то же поле, по имени.
- Нарушение в заголовке, параметре query или сегменте пути идёт без `field`: указатель адресует тело.
- У `412 revision moved` значение постоянно — `/revision`: поле версии строки, которое разошлось с `If-Match`; в теле запроса его нет.
- `field` несёт только имена и номера, значений поля в нём нет.

**`rows` в `GET /{rows}`.** Каждый элемент `status` последнего пульса каждого воркера подсистемы, любого возраста
([P/03.4 Н1.1](../../03-worker/spec/03.4-worker.norms.md)), дополненный полями: `worker` — имя слота воркера; `server` — поле `server` пульса, а если его нет — `?`;
`age` — секунды, сколько эта консоль видит версию пульса неизменной, по её монотонным часам (первый взгляд — 0),
с одним знаком после точки; `worker_state` — `live` при `age` ≤ 45 с (LOST_AFTER — [договор наблюдения](../../common/contracts/observation.md) «Свежесть»; разбор ревью стадии A 6–7, № 1), иначе `stale`; судят по точному возрасту, не по выданному с одним знаком (вектор `fresh-age`; разбор ревью стадии B 6–7, № 35). Элемент
не по форме пропускается; перечень «не по форме» — один, строка `/status` [исходов семьи пульса](../../03-worker/data/heartbeats.outcomes.tsv) (форма `status.items` — [семья](../../03-worker/data/heartbeats.schema.json); разбор ревью стадии B 6–7, № 15; нецелый `observed_revision` — правка поведения разбора ревью стадии A 6–7, № 13); `worker` — имя слота из ключа
пульса `<sub>/heartbeats/<слот>`, а не поле пульса. Пропуск по элементу — только у этой выдачи; пульс, нечитаемый целиком
(путь `""` [исходов семьи пульса](../../03-worker/data/heartbeats.outcomes.tsv): не по форме вне `status[]`, `worker` ≠
имени в ключе), действует раньше элемента — ни один его элемент в `rows` не входит (разбор ревью стадии B 6–7, № 14). Список упорядочен по id единицы (байты UTF-8), при равных — по имени слота воркера (байты UTF-8). Фильтр `view` — глава 6.3 Н1.3 `need`.
Неответ при чтении пульсов (и их листинга) — `lapse` [договора наблюдения](../../common/contracts/observation.md): `rows` по памяти
последних прочитанных версий с их возрастом; пульсы не читались ни разу с запуска — 503 `unavailable` (не `[]`); строки единиц
(`configured`) — обязательное чтение, неответ — 503 (C06-PULSE-LAPSE-503-01, решение «Архитектора» 2026-10-29).

**Состояние в ответе** (ADR-0091 п. 3). Элемент `configured` строки единицы получает `state` — объект, имя `unit.state` →
значение действующего состояния: строки `<sub>/state/<имя>/<id>`, которая действует по договор проверки строки «Состояние единицы» acts (её `born` и
`revision` равны `born` и `revision` этой живой строки, у `cursor` — только `born`; эпоха не сверяется); значение — `value` строки состояния без
`born`, `revision`, `epoch`. Нет действующего — имени нет; ни одного — `state` нет. Строка состояния, которая не читается
своим типом (не по форме P/03.6 Н1.7 или `value` не по схеме `unit.state.<имя>`), не действует — имени нет. Только
чтение: `state` в теле POST и PUT — платформенное имя, 400 (Н3 шаг 4).

### Версии: `revision`, индекс, `ETag`, `If-Match`

У строки две версии разного смысла (ADR-0094 B4); обе сравниваются только на равенство.

- **`revision`** — счётчик правок: целое, 1 при создании, +1 на правку (Н1.2, Н1.6). `DELETE` единицы его не двигает, снятая строка таблицы считает заново, поэтому прежнее значение может вернуться.
- **Индекс** — версия строки хранилища (P/01.1 `index`): меняется на каждой записи строки, в том числе надгробием и запечатыванием, и не повторяется (P/01.1 Н1). Это условие `cas` и стража
  пакетной двери и единственная версия, которую надгробие не сбрасывает.

Индекс отдают:

| Строка | Где |
|---|---|
| живая строка единицы | поле `index` элемента `configured`, ответа `POST`, `PUT`, двери байтов; строка `row` отказа 412 |
| строка таблицы | поле `index` `TableRow` |
| надгробие единицы | `ETag` ответа `DELETE`; `GET /{rows}?deleted=1&about=<значение>` |
| счётчик `<sub>/next_id` | `GET /{sub}/next_id` |
| строка папки, строка членства | поле `index` `Folder`, `member.index` ([глава 6.8](06.8-console.norms.md) Н2) |

Значения строки и её индекс берутся из одного чтения (P/01.1 Н3 «прочитать»), не из перечисления: иначе пара описывала бы разные версии.

**`ETag`** — индекс в двойных кавычках, сильный тег [RFC 9110 §8.8.3](https://www.rfc-editor.org/rfc/rfc9110#section-8.8.3): `ETag: "17"`. Его несут ответы успеха, которые называют одну строку: `GET` строки таблицы; `POST`, `PUT` единицы и
дверь байтов; `DELETE` единицы — индекс надгробия; `POST` таблицы; двери [главы 6.6](06.6-console.norms.md) Н2.1. Без `ETag`: `GET /{rows}` и `GET /{table}` (строк много), `DELETE` строки таблицы (надгробия нет), пакетная дверь (`{written}`), отказы.
`ETag` входит в сохранённый ответ заявки: повтор отдаёт его как есть.

**`If-Match`** необязателен для любого вызывающего. Его читают `PUT` и `DELETE` единицы, `POST /{rows}` при `unit.id` с именем (Н3 «создать» шаг 5а), `POST` и `DELETE` таблицы, двери записи главы 6.6 Н2.1.
Дверь байтов, пакетная дверь (условие строки — `cas`) и дверь просьб его не читают. У `POST /{rows}` при `unit.id: numeric` заголовка не читают: номер выдаёт консоль, условию не о чем судить.

| Значение | Сравнивается с | Кто шлёт |
|---|---|---|
| `<revision>` — десятичное целое ≥ 1 без знака и ведущих нулей | `revision` строки | агент домена (P/08.6 Н1.4 `base`: домен видел ревизию, индекса у него нет), модуль консоли (P/07 Н1.5 `api`) |
| `"<индекс>"` — индекс в двойных кавычках, как отдал `ETag` | индекс строки, у надгробия — индекс надгробия | кто читал `ETag` или `index`; надёжнее `revision`: прежнее значение не вернётся |

Иное значение — `*`, список, `W/"…"`, пустое — 400 `If-Match is a unit revision` до чтения строки: слово одно на всех дверях. Значение не входит в отпечаток заявки (Н3 «память повторов»). Условие судится после заявки и на каждом
перечитывании прохода.

**`412 revision moved`** — условие не выполнено, ничего не записано: `{detail, error: "revision moved", field: "/revision", revision, row?}`.

- `revision` — нынешняя; 0 — строки нет или её `revision` не читается (Н1.6).
- `row` — текущая строка в форме чтения этой двери: элемент `configured` у единицы, `TableRow` у таблицы, форма главы 6.6 Н2.1 у её дверей. Секреты — маской (глава 6.2). Поля нет, если строки нет, если это надгробие
  (`POST` над надгробием) и если вызывающий не прошёл бы `need` чтения этой строки (договор сторожевой и передачи): отказ не выдаёт значений мимо `view`.
- С ключом ответ запоминается как прочие (Н3 «память повторов»). Done-заявка с `row` тяжелее потолка хранилища — ответ и запись идут без `row`: отказ важнее копии строки, клиент перечитает её сам.

### Надгробия по `about`

`GET /{rows}?deleted=1&about=<значение>` → `200 {deleted: [{id, index}]}` (ADR-0094 доп. (5) п. 1): надгробия семьи `<rows>` манифеста с `about: {sub, field}`, у которых поле `field` равно значению. Надгробие хранит все поля
строки (Н3 «удалить» шаг 2), значит и поле `about`, отдельной строки нет. Так читатель находит индекс снятой части, когда её имени уже нигде нет.

- Только чтение: `index` — индекс надгробия, `id` — строкой; список по возрастанию `id` (байты UTF-8); таких надгробий нет — `{deleted: []}`.
- Право — `view` на единицу `<about.sub>/<значение>` (договор сторожевой и передачи `need`, `scope`); нет — 403 `denied`, ответа без права нет.
- Оба параметра обязательны и идут по одному разу, `deleted` — ровно `1`, `about` непуст; иначе, и у манифеста без `about`, — 400 `refused`, без `field`: параметр не адресуется указателем. Перечень не подтверждён — 503 `store unavailable`.
- Значение сравнивается байт в байт после процент-декодирования; `about` единицы — поле с `fixed: true` (P/02.1), поэтому значение надгробия совпадает со значением живой строки.

Платформа надгробий единиц сама не снимает, кроме объявленных `placement.unplaced.delete_after`, `placement.retire_when.delete_after`, `placement.ends` ([P/04](../../04-controller/spec/04-controller.norms.md) Н1.3). Подсистема, чей читатель опирается на индекс надгробия части, этих ключей у части не
объявляет (ADR-0094 доп. (2) п. 4 (в)): снятое надгробие вернуло бы прежнюю версию.

### Дверь счётчика

`GET /{sub}/next_id` → `200 {n, index}` (ADR-0094 B4; решение «Архитектора» 2026-10-31): чтение счётчика для вызывающего, который сам называет номер новой единицы в пакете (Н2 «Пакетная дверь»). Подсистема названа в пути всегда, и корневая: `/testsub/next_id`.

- `n` — последний выданный номер (Н1.3), следующий — `n + 1`. `index` — индекс строки счётчика.
- Строки нет: `n` — по recover Н1.3, `index` — `""`. Выдаваемый номер recover минус один: наибольший номер среди строк `<rows>/` с надгробиями и номеров живых заявок, ничего нет — 0. `n + 1` остаётся следующим номером, как при строке.
- Строка не читается: `n` так же, `index` — её версия (P/01.1 Н3 «прочитать»): запись пакета с этим `cas` заменяет её.
- recover здесь только считает: перечень не подтверждён — 503 `unavailable` (P/06.5 Н4), как в исходах семьи `<sub>/next_id`. Дверь счётчик не пишет, журнала нет.
- Право — как у создания строк `<s>` (договор сторожевой и передачи `need`). Тела нет, поэтому проверка та, что до чтения тела у `POST /{rows}` (`create_about`).
- `unit.id` не `numeric` — 404 `no such path`. Иной метод — 405; `HEAD` — как `GET`.

### Пакетная дверь

`POST /console/batch` — запись строк единицы и её частей одной операцией хранилища: всё или ничего (ADR-0094 B9, доп. (9), (12)). Дверь
общая, как `/drain`: префикса подсистемы не получает, строки называет полными ключами, строки разных подсистем идут вместе.
`If-Match` дверь не читает: условие каждой строки — её `cas`.

```yaml
тело:
  writes:                    # 1 … BATCH_WRITES (P/01.1 Н1); порядок значим; ключ встречается один раз
    - op:     put | delete
      key:    <s>/<rows>/<id> | <s>/<t>/<имя> | <s>/next_id   # строка единицы, строка объявленной таблицы, счётчик; <s> — подсистема каталога
      fields: {…}            # у put обязателен: у единицы — тело POST или PUT этой строки, у таблицы — тело POST, у счётчика — {n: целое ≥ 1}; у delete поля нет
      cas:    <индекс> | ""  # обязателен: индекс хранилища прочитанной строки (P/01.1 index; откуда — Н2 «Версии»), у надгробия — его индекс; "" — строки нет; без кавычек ETag
  guards:                    # необязателен; 0 … BATCH_GUARDS; порядок значим; ключ один раз и не в writes
    - {key, index}           # строка, прочитанная, но не записываемая; index "" — строки нет; форма — P/01.1 Н1 guard
ответ 200: {written: <число строк writes>}
```

- Тело и элементы закрыты: иного поля нет. `put` по прочитанной строке: строки нет или надгробие — создание (Н3 «создать»), живая строка — правка (Н3 «править»); у таблицы —
  «таблица — записать строку». `delete`: у единицы — надгробие (Н3 «удалить»), у таблицы — снятие строки; счётчик не снимается: `delete` на `<s>/next_id` — 400 `bad batch`.
- Иная семья — `<sub>/policy`, `<sub>/idem/*`, `platform/*` кроме строк папок и членства ([глава 6.8](06.8-console.norms.md) Н2 «Строки папок в пакетной двери»), строки операции кроме итога и счётчиков по билету шага ([глава 6.9](06.9-console.norms.md) Н2 «Пакет шага»), подсистема вне каталога — 400 `badkey`, `field` — `/writes/<номер>/key`. Таблица из `worker.writes`
  дверью не пишется — 403, снять её строку можно, как `DELETE` (Н1.6 `rows`).
- **Строка-якорь** (доп. (12) п. 3). Единица подсистемы с `about: {sub, field}`, у которой значение поля `field` непусто, — часть единицы
  `<sub>/<rows>/<значение>`; у `delete` значение берётся из прочитанной строки. Эта единица ДОЛЖНА быть строкой `writes` того же пакета: иначе 400 `no anchor`,
  `field` — `/writes/<номер>/fields/<field>`. Так два пакета над одной единицей всегда конфликтуют, а новая часть не проходит мимо; `revision` единицы растёт от правки части.
  Правило держит только дверь пакета: часть, созданная одиночным `POST`, якорь не двигает.
- **Счётчик** (ADR-0094 B9, ещё (6)). Номер единицы `unit.id: numeric` в пакете называет сам вызывающий, поэтому её создание и строка `<s>/next_id` идут только вместе: одно без другого — 400 `bad_id`,
  `field` — `/writes/<номер>/key`. `n` — наибольший номер создаваемых строк, и все они больше прочитанного `n` (Н1.3: `n` — последний выданный, номер не используется повторно); иначе 400 `bad_id`, `field` — `/writes/<номер>/fields/n`.
- Пределы — Н1.4. Форма тела и элемента не та — 400 `bad batch`, `field` — путь нарушившего поля; нарушения судятся в порядке тела: `writes` по порядку, затем `guards`, затем повторы ключей.
  Вход строки судится как тело её двери; `field` отказа строки — `/writes/<номер>/fields/<поле>` (номер с нуля).
- `412 row moved {detail, error, field, key, index}`: первая разошедшаяся строка в порядке хранилища — стражи по порядку, затем `cas` по порядку. `field` — `/guards/<номер>/index` или
  `/writes/<номер>/cas`; `key` — её ключ; `index` — её индекс сейчас, `""` — строки нет. Страж без `view` на строку — тот же отказ, что у отсутствующей строки: `index: ""` (доп. (12) п. 12).

### Двери тел и таблиц

Пути таблиц и blob-полей единицы выбирают root либо /{sub} по главе 6.5 Н2.
В OpenAPI это стандартные servers + paths. /schema и /drain остаются общими ([глава 6.6](06.6-console.norms.md)),
/v1/objects — дверь ресурса ([P/05](../../05-resource/spec/05-resource.norms.md) Н2): префикс консоли к ней не добавляется.

HTTP-контракт: [06-console.api.openapi.yaml](06-console.api.openapi.yaml), пути `/{rows}/{id}/{blob_field}`, `/{table}`,
`/{table}/{name}`.

Разбор запроса — глава 6.5 Н2 «Разбор запроса консоли» (P/01.1 Н2.1 с отступлениями консоли). Отступление двери байтов: тело — байты (`application/octet-stream`), JSON не разбирается. Иной метод у таблицы — `405 {detail: "/<t> takes GET, POST and DELETE of one row", error: "method"}` (контракт — `TableMethod`); метод проверяется до прав на запись. Общие отказы консоли, `HEAD` и предел чтения — глава 6.5 и полные формы главы 6.5 Н2 «GET /manifest».

| Дверь | Полное успешное тело / особые отказы |
|---|---|
| PUT `/<rows>/<id>/<blob_field>` | Полная `Unit` (Н2 выше) плюс `bytes` — число принятых байтов; 404 `{detail, error}` для отсутствующей единицы/поля; 409 для CAS; иной метод на этом пути, в том числе GET, POST и DELETE, — 405 (сверка python и go М10/6–11, T9; Н2 выше). `Content-Length` обязателен, иначе 400. `If-Match` и `Idempotency-Key` дверь байтов не читает (сверка python и go М10/6–11, совпало без нормы). Нет единицы — 404 `error` «no such unit», нет blob-поля — 404 `error` «no such blob field» (сверка python и go М10/6–11, T26). Каждый успешный новый вызов, даже с прежними байтами, увеличивает revision. Маршрут: любой PUT `/[<sub>/]<rows>/<id>/<x>` — дверь байтов: предел 32 МиБ и одно из двух мест (Н1.4) берутся до поиска единицы и поля; нет единицы или blob-поля `<x>` — 404 после чтения тела |
| GET `/<table>` | `{<table>: [TableRow…]}`; имя свойства равно имени таблицы. GET одной строки — `TableRow` и `ETag`; 404 `{detail, error}` при её отсутствии |
| POST `/<table>` | 201 `{row: TableRow}` — тот же TableRow, что GET одной строки (у таблицы мест — с `held_by`), и `ETag`; 400 текстовый или структурный `FormRefusal` (Н2 выше); 409 `ReferenceConflict` либо текстовый отказ; 412 `revision moved` (Н2 «Версии»). Это полная замена полей по манифесту, не patch; `Idempotency-Key` необязателен, с ним — Н3 «память повторов» |
| DELETE `/<table>/<name>` | 200 `{deleted: имя}`; 404 при отсутствии, в том числе с `If-Match`; 412 `revision moved`; 409 — исчерпаны повторы CAS. Ссылки на строку удалению не мешают: `ref` не требует существования цели, `must_match` связывает только с живой целью (Н1.3, ADR-0057); `Idempotency-Key` — как у POST |

Дверь копии тела у ресурса `PUT /v1/objects/<sub>/blobs/<digest>` — [P/05](../../05-resource/spec/05-resource.norms.md) Н2 (стадия B).

`TableRow` содержит обязательные `name`, `revision`, `index`, объявленные поля и stamp; `held_by` добавляется только таблице мест, значение — имя воркера или null. Секретные ключи с суффиксом `_secret` исключаются рекурсивно, адреса маскируются по главе 6.2. Только уже прочитанная, но испорченная строка — значение объявленного поля не читается своим типом по values_by_type Н1.2 — представляется `{name, garbled: true, index}`: индекс нужен, чтобы снять или заменить её условно; сбой чтения/перечисления — 503, не пустой список и не garbled. Вход POST — собственная TableInput, не ClientFields единицы. Поле, не переданное в POST и без `default`, в строке и TableRow отсутствует: пустая форма Н1.2 у таблиц не применяется; `default` подставляется (то же — [договор проверки строки](../../common/contracts/row-check.md) «Подготовка полей», «Строка таблицы»). Необъявленные поля POST отвергаются по манифесту; `name` вычисляется по key и может происходить из одноимённого объявленного поля тела. Вычисляемые `held_by`, `garbled`, `revision`, `index` и штампы `by`, `at`, `made_at` клиент не задаёт; переданный штамп — 400 `unknown field`, даже если он не включён в stamp таблицы; `revision` и `index` — так же. Манифест с их объявлением как редактируемых полей таблицы вне профиля этого урока и отвергается при загрузке. Формы `SnapshotUnit`/`SnapshotShard` описывают объект снимка ([P/04 Н1.3а](../../04-controller/spec/04-controller.norms.md)), не новый HTTP-маршрут.

JSON-тела читаются с общим пределом ≥1 МиБ, blob с 32 МиБ, копия ресурса с 64 МиБ (P/05). Заголовок не заменяет счёт фактических байтов. Плохое framing/короткое тело — 400, таймаут — 408, превышение — 413, chunked консоли — 400. Отказы чтения/доверия/запечатывания дают 503 с полной формой `{detail, error}` по владельцу. Успех публикации объекта не доказывает успех следующей записи строки; при неизвестном исходе клиент сначала читает строку или повторяет запрос с тем же `Idempotency-Key` (Н3 «память повторов»); запрос без ключа автоматически не повторяется.

### Команда окна уборки

Исключительное окно уборки (Н3 «уборка тел») оператор открывает командой реализации `sweep` (её имя — «Решает
реализация» п. 9) с флагом `--writers-stopped`: им оператор подтверждает строку «допуск удаления» Н3. Команда
обходит все подсистемы каталога с blob-полем, сама выдерживает SWEEP_GRACE как новый наблюдатель версии списка,
затем выполняет фазы sweep и «завершение» Н3.

| Исход | Код выхода | Что сделано |
|---|---|---|
| окно выполнено, в том числе удалять нечего; в окне удалено хоть что-то, даже если партии других подсистем сняты — снятая партия не сбой: данных не потеряно, следующий mark повторит | 0 | doomed удалены, надгробия записаны; снятые партии — строками вывода «`<sub>`: batch dropped: mark time unknown (`<n>`)» |
| во всём окне ничего не удалено: нет `--writers-stopped`; сбой чтения ссылок или списка; конфликт CAS списка; все непустые партии сняты — `at` нет или не читается (Н3 «уборка тел» sweep); листинг дверей или вывода для `peers` надгробия не подтверждён ([договор надгробий](../../common/contracts/tombstone.md) «Соседи») | 2 | ничего не удалено |

Код окна — по всему окну, не по подсистеме: 2 — только если во всём окне ничего не удалено, иначе 0 (C06-BLOB-CUTOFF-33-01, ответ «Архитектора» 2026-10-25).
| сбой после начала удалений: надгробие или исход удаления не подтверждён | 3 | писателей и копирование не открывать (Н3 «завершение») |

## Н3 Проход

### Полные ключи и отказ хранилища

Во всех операциях ниже правила ключа P/01.1 Н1 применяются после сборки полного пути Н1.1,
включая префикс, семейство и разделители; ключ стража проверяется так же. Грамматика UnitId,
WorkerName и 200-байтный предел компонента Idempotency-Key сохраняются. Схема компонента
не обещает вместимость полного ключа. Ключи не сокращаются и не хешируются при отказе; дайджест в ключе заявки (Н3 «память повторов») — постоянное правило, не ответ на отказ.

Определённый `badkey` при чтении или записи — отказ этой операции, не отсутствие строки,
не CAS-conflict и не неответ. Применимые правила ключа можно проверить до вызова хранилища;
отказ меньшего объявленного предела файловой реализации обрабатывается тем же способом.

- Дверь единиц отвечает `400 {detail, error: "badkey"}`, без fault; detail называет семейство
  ключа и причину без содержимого секретов. У PUT/DELETE строка и revision не меняются.
  POST до получения своей pending отвечает без сохранения; после получения — завершает
  отказ шагом 9. Прежний резерв номера не возвращается. Отказ сохранения самого ответа
  на шаге 9 по-прежнему даёт 503, а не неподтверждённый 400. Правила утраты заявки/guard
  имеют прежний приоритет; чужую заявку не меняют.
- Ветви воркера (выбор слота, захват, продление, запись под стражем, выдача и подтверждение эпохи) перенесены в
  [P/03.2 Н3 «Полные ключи и отказ хранилища»](../../03-worker/spec/03.2-worker.norms.md) (стадия B; разбор ревью стадии A 3–5, № 11).

### Общая проверка строки

Одна для двери и для библиотеки заказчика ([P/03.6](../../03-worker/spec/03.6-worker.norms.md) Н1.6; ADR-0091 п. 1) — [договор проверки строки](../../common/contracts/row-check.md) (перенесено без изменения поведения; догадка стадии C W03-E07, решение «Архитектора» 2026-10-23): у создания —
шаги 4–7 «создать» (П1–П5), у правки — шаги 2, 4–5 «править» (Р1–Р3). Исход отказа у двери — Н4, у библиотеки — исход
`refused` заказчика (P/03.6 Н1.6).

### память повторов — двери записи людей

Память повторов (ADR-0094 B3) — строка заявки `<sub>/idem/<key>`, один механизм на все двери записи людей: шаги 1, 2 и 9 прохода «создать»,
«Владение заявкой» и срок [Н1.3](#н13-идентификатор) «Срок done-заявки». У `POST /{rows}` ключ обязателен. У `PUT` и `DELETE` единицы, `POST` и
`DELETE` таблицы и дверей записи [главы 6.6](06.6-console.norms.md) Н2.1 заголовок `Idempotency-Key` необязателен: нет его — проход двери
прежний и повтор есть новая запись; есть — дверь идёт под заявкой. У `POST /console/batch` — так же (Н3 «пакет»). Дверь байтов и дверь просьб (глава 6.4) памяти повторов не имеют.

```yaml
ключ:       (user, метод, путь, ключ)
<key>:      hex sha256(UTF-8(user) ‖ 0x00 ‖ метод ‖ 0x00 ‖ UTF-8(путь) ‖ 0x00 ‖ UTF-8(ключ)); 64 строчных знака, один сегмент;
            user — доказанное имя вызывающего (глава 6.3 Н1.3); метод — прописными;
            путь — без префикса подсистемы, сегменты процент-декодированы: `/testsub/counters/a%20b` и `/counters/a b` — один путь
отпечаток:  кто, метод, путь, тело как значение JSON (шаг 2 «создать»); вход двери в query — часть тела; тела нет — как `{}`;
            If-Match в отпечаток не входит: повтор после потери ответа несёт прежнее условие, его не судят (порядок ниже)
порядок:    шаг 1 (форма запроса и ключа, тело, кольцо; If-Match — только форма) → заявка шаг 2 → If-Match → проход двери →
            целевая запись под стражем → ответ в заявку шаг 9
иной отпечаток: 422 `key reused` на всех дверях памяти (ADR-0094 доп. (14))
слова:      значение заголовка — Н2 (без OWS, дважды — 400); ключ не по форме — 400 `Idempotency-Key required`; чужая pending моложе 30 с — 409 `in flight`;
            503 — `store unavailable` у единиц, `unavailable` у таблиц и главы 6.6
```

Сторожевая и разбор запроса идут раньше заявки: их отказы в память не входят. Ответ `< 500`, в том числе отказ двери и `412 revision moved`, запоминается и
отдаётся повтору как есть, кодом и телом: решив заново, клиент берёт новый ключ. Повтор из памяти ничего не записывает и журнала не пишет.

**Целевая запись** двери — её прежний `cas` вместе со стражем `{key: <sub>/idem/<key>, index: моя версия заявки}`; дверь записи без `cas` — со стражем.
Подготовленная done-заявка проверяется по весу до записи, как шаг 8: больше потолка хранилища — 413 `row too large`, запись не выполняется, к шагу 9.
Отказ стража — «Владение заявкой». Судьба своей pending на шаге 9 — та же: снять, только если целевая запись достоверно не выполнена.

**Продолжение.** Перехват заявки через 30 с не отменяет записанного прежним исполнителем. Перехвативший сначала смотрит цель, затем идёт проходом двери:

- `PUT` единицы: шаг 5а «править» держит в заявке намеченную `revision`; у строки эта `revision` и `born` намерения → записана этой заявкой, шаг 9 с этой строкой;
- запись строки таблицы: шаг 2а «таблица» держит намеченную `revision`; у строки эта `revision` → записана этой заявкой, шаг 9 с этой строкой. Без этого проход заново поднял бы `revision` второй раз и отказал бы своей же записи `412`;
- `DELETE` единицы: строка уже надгробие → шаг 9 с `{deleted}`; `DELETE` таблицы: строки уже нет → то же;
- заявка без намеченной `revision` — запись ещё не начата, идёт проход заново.

Чужая запись той же `revision` или чужое снятие в те же 30 с неразличимы и принимаются, как у создания (Н3 «создать», «Гонки»). Цель смотрят раньше `If-Match`: условие судит чужие правки, а не свою запись.

**Владение заявкой.** Версия строки заявки — условие каждого изменения: записи/снятия самой заявки
идут с `cas` моей версии, резерв счётчика и создание единицы — со стражем этой версии вместе с `cas`
целевой строки. Проверить заявку отдельным чтением перед безусловной записью недостаточно.
После успешного изменения заявки исполнитель запоминает новую версию; перехват всегда меняет её.
После `412 guard` или конфликта `cas` заявки прежний исполнитель прекращает изменения и перечитывает
заявку, не присваивая себе её новую версию: тот же отпечаток и `done` → сохранённый ответ целиком;
тот же отпечаток и `pending` → `409 in flight`; иной отпечаток → `422 key reused`;
нет заявки или хранилище не ответило → `503 store unavailable`, клиент повторяет с тем же ключом.
Он не сохраняет этот отказ и не снимает чужую заявку. После неизвестного исхода записи он также
не продолжает со старым предположением об успехе: до выяснения сохраняется pending, клиент получает 503.

Отсутствующее после материализации поле веса (например, ненаданное inherit) не подменяет отказ
значения: для расчёта веса такой строки используется placement.weight.default. Присутствующие
0, отрицательное или нечисловое значение не заменяются этим default. Пустая форма int равна 0,
поэтому манифест с полем веса без подходящего default может требовать явного положительного значения
при POST; правила материализации Н1.2 остаются общими.

**Гонки.** Две консоли с одним ключом: заявка с `cas ""` пропускает одну; вторая видит `pending` и отвечает `409 in flight`, потом — прежний ответ. Две консоли с разными ключами и одним именем: запись строки с `cas ""` пропускает одну; вторая получает `409 exists`. Консоль умерла после резерва номера: заявка через 30 с достаётся другой консоли, и та продолжает с шага 4 — проверки формы, обязательных полей и ссылок повторяются — и пишет на шаге 8 номером из заявки (numeric): строка с ним уже есть → тот же create, 201 та же строка; нет → записать её этим номером. Named: строка с этим именем есть, `revision: 1`, а ответа в заявке нет → записана этой заявкой, 201 (одноимённое чужое создание в то же окно 30 с неразличимо и принимается). Консоль умерла между резервом номера (cas счётчика) и записью номера в заявку: заявка без номера — резервировать заново с шага 3, прежний номер сгорел (две строки, две операции — неделимости между ними нет). Номер, записанный в заявку до смерти, не сгорает; сгорает номер отказанной попытки (шаги 5–7 вернули отказ).

Прежняя консоль A может ожить после перехвата консолью B. Если A зарезервировала 1, но не сохранила
его в заявке, её поздний `cas` заявки отказывается; A не доходит до записи единицы 1. B резервирует 2
и создаёт только её. Если номер 1 уже сохранён, B сохраняет его при перехвате: поздняя запись A
под старым стражем отказывается, а B продолжает с номером 1. Если A записала единицу до перехвата,
B находит эту же строку и сохраняет ответ; поздний `cas` ответа A не заменяет результат B.
Та же защита действует на отказ и снятие pending: A не удаляет заявку B. Потеря ответа о создании
не даёт права снять pending — сохранённый номер нужен продолжению. Эти исходы опираются на атомарные
`cas`/`guard` P/01.1, а не на предположение, что прежний исполнитель умер.

Превышение потолка служебной записи до шага 8 также даёт 413 row too large. Если pending ещё
не создана, сохранять ответ негде; если заявка своя — отказ завершается через шаг 9. Зарезервированный
номер не возвращается. Отказ сохранения результата на шаге 9 — 503: если единица уже записана или
исход неизвестен, pending остаётся для восстановления; чужую заявку не изменяют.

### править(id, тело) → 200 строка | отказ

`Idempotency-Key` у PUT необязателен. Без него правка сходится по `cas` прочитанной строки, а повтор PUT — новая правка,
которая снова поднимает `revision`; с ним правка идёт под заявкой, повтор отдаёт сохранённый ответ (Н3 «память повторов»).

**Условие `If-Match`** (P/08.6 Н1.4 `base`: правка домена применяется агентом — урок P/09 — от ревизии, которую видел домен). Значение и отказ 412 — Н2 «Версии». Заголовок не по форме — 400 `{error: "If-Match is a unit revision"}` до чтения строки.
Условие судится после заявки: повтор тем же ключом отвечает из памяти, не `412` своей же правки. Сравнение — на каждом перечитывании прохода (после конфликта `cas` — с шага 3 снова). Заголовка нет — как прежде.

```
1. id по Н1.3; путь — ровно один id                                        → иначе 400 / 404
   тело — JSON-объект; заданное нечитаемое кольцо → 503 SealingUnavailable до правки/проверок полей (глава 6.2 Н3)
   If-Match не по форме → 400; ключ есть и не по форме → 400 Idempotency-Key required
1а. ключ есть: заявка — шаг 2 «создать»; дальше проход под ней, ответ — шагом 9 (Н3 «память повторов»)
2. отказы формы — [договор проверки строки](../../common/contracts/row-check.md) Р1 → 400; секрет пустой или null — сохранить прежний (глава 6.2 Н3 «создать/править», шаг 3; смена поля из bound_to при пустом секрете — 400 «must be given anew»)
3. прочитать строку; нет или deleted                                       → 404 no such unit
   (нет строки и свежий дайджест в теле — 404: строки нет, сравнивать не с чем)
3а. If-Match есть и не равен версии строки своей формы                       → 412 revision moved {revision, row?}
4. [договор проверки строки](../../common/contracts/row-check.md) Р2 по прочитанной строке → 400 (id — id пути); у строки с made меняется поле key заказчика
   (Н1.3 made_key) → 400 «<поле> is fixed»; новый дайджест blob — только дверью байтов `PUT /{rows}/{id}/{blob_field}`, Н2
5. ссылки — [договор проверки строки](../../common/contracts/row-check.md) Р3                                                 → 409 conflict с fault
5а. ключ есть: записать в заявку намеченную revision (прежний + 1) и born строки с cas моей версии; полученная версия — моя
6. записать {…прежние, …новые, revision: прежний + 1} с cas прочитанной версии (born и made — прочитанной строки), с ключом — и со стражем заявки;
   toolarge → 413 row too large, прежняя строка/revision сохранены; conflict → перечитать с шага 3;
   предел повторов при conflict исчерпан → 503 store unavailable, строка и revision прежние (журнал cammeta-go, урок 3 № 2)
```

**Гонки.** Две правки одной строки: `cas` пропускает одну, вторая перечитывает и накладывает свои поля поверх (шаг 6 → 3) — обе отвечают 200, у второй `revision` на два выше — кроме blob-поля: проверка «прежний дайджест строки» идёт на шаге 4 по **перечитанной** строке, и повтор, заставший `mask` снятым (`""`), с тем же дайджестом в теле получает 400, а не восстанавливает ссылку на тело, которое уборка могла уже снять; без `If-Match` клиент версии не присылает (с ним — 412 `revision moved` по условию выше, а `"<индекс>"` отказывает и при правке, вернувшей строку к прежним значениям), 409 — только `exists`/`conflict` ссылок. Правка против удаления: перечитав надгробие — 404.

Неатомарность проверок `ref`/`must_match`/`unique` — [договор проверки строки](../../common/contracts/row-check.md) «Порядок проверок».

```
0. If-Match не по форме                                                     → 400
   ключ есть и не по форме → 400 Idempotency-Key required; ключ есть: заявка — шаг 2 «создать», ответ — шагом 9 (Н3 «память повторов»)
1. прочитать строку; нет или deleted                                       → 404
1а. If-Match есть и не равен версии строки своей формы                       → 412 revision moved {revision, row?}
2. записать {…строка, deleted: "true"} с cas прочитанной версии, с ключом — и со стражем заявки; revision, born и made не меняются, у строки с made —
   made.gone = часы двери (ADR-0091 п. 1: над надгробием заказчик пишет только событие позже gone + 60, договор проверки строки «Строка заказчика: made» tombstone); conflict → с шага 1;

3. второй шаг — контроллер (P/04 Н3 «проход()», шаг 4 «снять удалённые (reason deleted)»): снять с назначения, строка размещения {worker: "", reason: deleted, rev + 1}
```

У подсистемы с `display.tree.folders` шаг 2 пишет пакетом ещё снятие единицы из папок — [глава 6.8](06.8-console.norms.md) Н3 «удаление единицы дверью»; `delete` пакетной двери — так же.

**Гонки.** Удаление против правки: `cas` — проигравший перечитывает и повторяет (удаление — поверх правки, правка — 404 на надгробии); удаление против удаления — второе 404 (надгробие уже стоит); удаление при живом назначении — контроллер снимает единицу следующим проходом ([P/04 Н3 «проход()»](../../04-controller/spec/04-controller.norms.md), шаг 4), воркер — при чтении назначения ([P/03.3 Н3 «цикл()»](../../03-worker/spec/03.3-worker.norms.md), шаг 2: ведомой нет в назначении → stop_unit).

### пакет(тело, ключ?) → 200 {written} | отказ

`Idempotency-Key` необязателен. Заявка — `<CONSOLE_ROOT>/idem/<key>`, как у кластерных дверей главы 6.6; иной отпечаток под тем же ключом — 422 `key reused` (ADR-0094 доп. (14)).

```
1. форма (Н2 «Пакетная дверь»): тело — JSON-объект → иначе 400 not_json; форма → 400 bad batch; ключи строк → 400 badkey; пределы → 413 batch too large;
   ключ есть и не по форме → 400 Idempotency-Key required; кольцо — шаг 1 «создать» по секретам всех строк (глава 6.2)
2. прочитать строки writes по порядку; чтение не подтверждено → 503 store unavailable
3. права по каждой строке (договор сторожевой и передачи need) → отказ одной — 403 denied всего пакета, журнал access.denied;
   ни заявки, ни записи: сторожевая идёт раньше памяти повторов
4. ключ есть: заявка — шаг 2 «создать»; дальше проход под ней
5. сверка по чтению шага 2: стражи по порядку, затем cas по порядку (Н2) → 412 row moved
   без этой сверки проверка шага 7 судила бы строку не той версии и отвечала бы ложным 400
6. якорь и счётчик (Н2) → 400 no anchor, 400 bad_id
6а. строки папок и членства — глава 6.8 Н3 «строки папок в пакете»
7. строки по порядку writes, проверка и подготовка своей двери, первая отказанная даёт ответ всего пакета:
   создание — шаги 4–8 «создать»; правка — шаги 2, 4–5 «править»; delete — шаг 2 «удалить»; таблица — шаги 1–3 «таблица — записать строку»;
   delete отсутствующей строки или надгробия → 404 no such unit, 404 no such row
   ссылки — по состоянию после пакета (договор проверки строки «Порядок проверок», ниже)
8. команда хранилища op: batch: writes — подготовленные строки с их cas; guards — стражи тела; id — новый; ключ есть — ещё одна запись:
   done-заявка с cas моей версии и ответом {written}
   вес done-заявки и строк — потолок хранилища → 413 row too large, к шагу 9 «создать»
9. записать:
   сделано → журнал по каждой строке (unit.created | unit.changed | unit.deleted, <t>.written, <t>.deleted) → 200 {written}
   412 guard, 409 conflict по строке тела → 412 row moved; 413 toolarge строки → 413 row too large; 413 toolarge тела → 413 batch too large: ничего не записано, к шагу 9 «создать»
   409 conflict по строке заявки → «Владение заявкой»
   unavailable, ambiguous, неответ → 503 store unavailable; своя pending остаётся: повтор тем же ключом сходится (ниже)
```

Ответ `< 500` — как у прочих дверей памяти: успех лежит в заявке вместе с самим пакетом, отказ — шагом 9 «создать». Поэтому повтор после потери ответа получает прежний итог, а не ложный `412`
на свою же запись. `done` идёт записью пакета, а не отдельной: иначе обрыв между ними оставил бы записанный пакет с `pending`.

**Продолжение.** Пакет с заявкой ложится только вместе с `done`: `pending` значит, что пакета не было. Перехвативший идёт проходом заново, с шага 5; поздний пакет прежнего исполнителя отказывает `cas` заявки.

Секреты строк — глава 6.2, как у дверей этих строк: запечатаны до записи, отпечаток — не маской. Версия ответа в `{written}` не входит: done-заявка пишется тем же пакетом, версия ещё не выдана.

Заявку пакета консоль пишет правом следствий, без проверки человека (доп. (12) п. 5). Строка служебной таблицы (`service: true`, Н1.6) идёт в пакете строкой таблицы по правилу этой таблицы: память `backend` — таблица `backend/repeats` (ADR-0094 доп. (15)). Строк `<sub>/idem/*` дверь в теле не принимает.

**Гонки.** Два пакета одной единицы: `cas` якоря пропускает один, второй — 412, ничего не записано. Пакет и одиночная правка той же строки: `cas`. Пакет и одиночная правка другой части той же единицы: одиночная якорь не двигает — пакет стережёт её стражем, если вызывающий его поставил. Обратные чтения проверки — как у одиночных дверей, не атомарны (договор проверки строки); атомарна запись. Журнал пишется после записи: обрыв между ними теряет строку журнала, как у одиночных дверей.

### положить_тело(id, поле, байты)

```
1. общий конвейер консоли уже проверил framing, длину и потолок 32 МиБ по заголовку до двери (глава 6.5 Н3):
   нет Content-Length → 400, выше потолка → 413; затем поле blob и единица есть → иначе 404
2. digest = sha256(байты); снять digest со списка <sub>/sweep (cas), если там
3. put_durable(<sub>/blobs/<digest>) → TooLarge → 413 «a blob is what an object store is for»
4. правка строки {<поле>: digest} с cas, revision + 1; журнал unit.changed
5. перечитать объект blobs/<digest>: нет (уборка сняла его между шагами 3 и 4) → put_durable снова
```

**Гонки.** Две загрузки одинаковых байтов дают один digest; повторный put_durable может сохранить прежний индекс объекта. CAS строки защищает только строку. Параллельное удаление исключается допуском уборки ниже; отмена отметки и контрольное чтение не заменяют этот допуск. Неизвестный исход CAS разрешается чтением строки перед новым действием.

### уборка тел — отметки в фоне, удаление в окне обслуживания

| Фаза | Условия и действие | При сбое |
|---|---|---|
| mark | Каждые 60 с полный успешный обход; если текущая партия digests непуста — не переписывать at/версию и не добавлять новые. Если списка нет/пуст — CAS новой партии ≤64 без ссылок с at первой отметки | Неизвестный обход — ничего не отмечать/удалять |
| grace | Ждать 300 с наблюдения неизменной версии списка по местным монотонным часам. Первый взгляд/новая версия начинают с 0; put_blob может снять отметку | Повторить чтение позже |
| допуск удаления | Один оператор закрывает новые записи единиц/таблиц с blob, blob PUT, импорт/restore и входящие зеркальные копии; ждёт начатые операции. Один уборщик | Неизвестный исход писателя или неподтверждённый покой — удаления нет |
| sweep | В этом же окне перечитать все ссылки и список и вычислить `peers` надгробий ([договор надгробий](../../common/contracts/tombstone.md) «Соседи»: листинг дверей или вывода не подтверждён — удаления нет). doomed = отмеченные без ссылок; снять список CAS; только затем get_at и delete_at каждого doomed старше отметки — граница «старше отметки» только по читаемому `at`. `at` нет или не читается при непустой партии — из неё в окне ничего не удалять: партию снять CAS по прочитанной версии, строка вывода «`<sub>`: batch dropped: mark time unknown (`<n>`)», `<n>` — число дайджестов; снятая партия — не сбой: код окна — по всему окну (Н2 «Команда окна уборки»); следующий mark пишет новую партию с `at` (C06-BLOB-CUTOFF-33-01, решение и ответ «Архитектора» 2026-10-25) | Ошибка чтения/конфликт — пропустить удаление, не считать отсутствие доказанным |
| завершение | Прочно записать надгробия удалённым (форма и `peers` — договор надгробий); при частичном сбое сохранить запрет писателей до восстановления надгробий/определения исходов | Не открывать копирование, которое может воскресить удалённое |
| выход | После завершения окна вернуть писателей/копирование | Следующая уборка начинает новый обход |

mark/grace/sweep одного уборщика не пересекаются; в исключительном окне другие уборщики, включая mark, остановлены.

at — диагностическое время первой отметки партии, не скользящий срок. Уменьшение списка не добавляет новый дайджест и начинает новое консервативное окно наблюдения версии; новый наблюдатель всегда ждёт 300 с. Обходы в T0+60…540 не обновляют непустую неизменную партию, поэтому к T0+600 льгота уже выдержана. Новые кандидаты попадут только в следующую партию после опустошения прежней.

В обычном режиме раз в минуту исполняются только mark/grace. Удаление не является автоматическим действием живой установки. `delete_at` и CAS списка предотвращают часть конфликтов, но сами по себе не защищают от новой ссылки после проверки: это обеспечивает только окно без писателей. Полученные до остановки результаты обхода для sweep не используются.

```
порядок отказов — по шагам, первое нарушение даёт ответ (сверка python и go М10/6–11, T18, T19):

1б. прочитать строку; If-Match есть: строки нет → 412 revision moved {revision: 0}; значение не равно версии строки своей формы → 412 revision moved {revision, row?}
2. поля: типы, required, enum, schema на строку, ref/must_match в обе стороны, то же правило, что у единиц (Н1.3) — (а) поля этой строки
   с ref/must_match к их живым целям (Н1.3); (б) живые единицы и строки таблиц каталога, чьё поле с ref на эту
   таблицу и must_match называет эту строку, — их значения равны новым значениям строки; нарушение → 409 conflict,
   fault must_match; цель ссылки или ссылающаяся строка не читается → 409 fault garbled (Н1.3; сверка python и go М10/6–11, T20); секреты:
   пустой — прежний, смена bound_to без нового секрета — 400 «must be given anew» по правилу главы 6.2 Н3 шаг 3,
   POST поверх строки с тем же именем — правка этой строки; stamp: by, at, made_at; revision: прочитанная + 1, строки нет — 1 (Н1.6)
2а. ключ есть: записать в заявку намеченную revision с cas моей версии; полученная версия — моя
3. запечатать; записать полную строку с CAS, с ключом — и со стражем заявки (конфликт → с шага 1б: перечитать, сверить If-Match и снова проверить все зависимости;
   после ограниченного числа конфликтов 409); журнал <t>.written {sub, target, user, addr, fields, changed, was}
   (форма — Н1.6 journal_form); at и made_at первой записи строки — одно и то же значение (сверка python и go М10/6–11, T23)
```

`DELETE /<table>/<name>` с ключом идёт под заявкой так же: заявка до чтения строки, снятие строки с `cas` прочитанной версии и стражем заявки, ответ — шагом 9. Порядок: `If-Match` не по форме → 400; заявка; строки нет → 404; `If-Match` не равен версии строки → 412; снятие.

**Гонки.** Две записи одной строки таблицы: `cas` (Н3 «править»); таблица воркера — один писатель, строкой целиком; консоль её не пишет, только удаляет строку по `cas` (Н1.6; сторона воркера — [P/03.4 Н1.6](../../03-worker/spec/03.4-worker.norms.md), стадия B).

## Решает реализация

Реализация обязана назвать в своём описании:

1. **разбивку семей** на строки и объекты сверх Н1.1, если она иная, и где лежат объекты;
2. **предел тела двери** (`413`); форма `*_secret` в строке — норма главы 6.2 Н1.2 (конверт), не выбор;
3. **форму строки заявки** `<sub>/idem/<key>` (ключ строки и что она помнит — норма Н3 «память повторов»), срок хранения done-заявок (не меньше 86400 с — норма) и способ их очистки;
4. **точный текст** `detail` сверх слов Н4;
5. **периоды**: предел повторов при `conflict` на `next_id`, правке, пометке удаления (исход исчерпания — норма Н3: 503 store unavailable у двери; удаление — разбор ревью стадии B 6–7, № 13);
   шаг продления и повторы захвата и эпохи — [P/03.2](../../03-worker/spec/03.2-worker.norms.md) «Решает реализация» п. 2 (стадия B);
6. **запуск стенда** для приёмки — по разделу «Стенд» общего README приёмки;
7. **предел тела консоли** (≥ 1 МиБ); одновременных тел — ровно два (Н1.4), выбора нет;
8. **хранилище объектов и его потолок** (`OBJECTS` URI, `max_bytes`), где лежат надгробия;
9. **имя команды окна уборки** (её флаг и коды — Н2) и как оператор исключает всех писателей до неё и завершает надгробия после кода 3; состояние сверх `{at, digests}`.

## Чеклист готовности

Реализация соответствует главе, когда выполнена каждая норма; id нормы `P/06.1-MM` — то, на что ссылаются дельты решений, находки и записи окон (ADR-0080 доп. 6). Ссылки — точные шаги приёмки главы или «чтением» с причиной (разбор ревью стадии A 6–7, № 22):

- [ ] **P/06.1-01** раскладка ключей Н1.1: семьи, зарезервированные имена таблиц; у строки один писатель, семья делится по форме строки только по правилу урока-владельца (просьбы — глава 6.4 Н1.5, таблицы — Н1.6) — проверяется чтением: раскладка — форма ключей хранилища, шаги двери её не показывают (права — P/02.5 Н1.4; зарезервированные имена — отказ загрузки P/02.1); представимость обязательного файлового пути до публикации/захвата — чтением Н1.3 и README приёмки («Дополнительные проверки R29»: нужен отдельный экземпляр с пределом ключа)
- [ ] **P/06.1-02** строка единицы: `id`, `revision`, значения по типам — сц. 01 шаг 1, сц. 03 шаги 3–4, сц. 08 шаги 5, 10; обратимый list — сц. 09 шаги 1–2; [] и [""] различимы после чтения, правки и перезапуска — сц. 25 шаги 2–11; заполнение default/пустой формы при создании по Н1.2 — сц. 01 шаг 1 (`labels: []`), сц. 02 шаг 1 (`start: 0`); отсутствие ненаданных `inherit` — сц. 10 шаги 1, 3; `json: null` — чтением (у `testsub` нет json-поля); `null` у поля без `inherit` — 400 — сц. 03 шаг 7; `blob` в правке — только прежний дайджест или `""`, иначе 400 — сц. 15 шаги 9–10; текстовые формы по типам — векторы `values-by-type`
- [ ] **P/06.1-03** `revision`: 1 при создании, +1 на каждую правку — сц. 03 шаги 2–5; удаление не меняет, возврат имени — надгробие + 1 — сц. 07 шаги 1–4, 7; условие `If-Match` у PUT и DELETE — сц. 14 шаги 3–10
