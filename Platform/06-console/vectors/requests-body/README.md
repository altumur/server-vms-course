# Векторы: запись значения тела в строку и канонический JSON

Владелец — глава P/06.4 ([нормы](../../spec/06.4-console.norms.md) Н1.5 `<поля тела>`: «строка — как есть, иное значение —
канонический JSON (JCS, ADR-0072)»; Н2: `fault` двери просьб — только `too_long`). Участники — дверь единиц и таблиц
[главы 6.1](../../spec/06.1-console.norms.md) (поле типа `json`: значение как есть, потолок `JSON_CEILING`, `not_json`) и

текстом). Байты пишет «Спецификация» (ADR-0083, стадия B; правила — «Архитектор», 2026-10-05/06, числа по JCS — стадия A
ADR-0083, 2026-10-18); соответствие продукта — его приёмкой по этой таблице (ADR-0080 доп. 16).

Пакет перенесён из `Source/tests/testdata/requests_body.tsv` (стадия A) вместе с уроком 6 (стадия B, ADR-0083 доп. (1));
байты таблицы — те же, включая заголовок-комментарий (его «М10/3», «М10/8» — прежние адреса норм, ныне глава 6.1 и

[`fault`](../../../common/vectors/fault/README.md) (глава 6.1).

## `requests_body.tsv`

UTF-8, LF, поля через TAB. Строки с `#` и пустые пропускаются; строки заголовка нет. Четыре поля в каждой строке (TAB
стоит и при пустом `fault`). Ячейка читается байт в байт между TAB, ничего не раскрывается: TAB или перевод строки внутри
текста JSON записан так, как JSON пишет их в строке (`\t`, `\n`).

| Поле | Значение |
|---|---|
| `field` | `request` — поле `v` строки просьбы; `json` — поле `doc` типа `json` единицы |
| `body` | значение, как его несёт тело, — текст JSON ровно как отправлен (`5.0` — не `5`) |
| `stored` | текст, который держит строка; `<absent>` — поля в строке нет; `<empty>` — пустая строка |
| `fault` | пусто — принято; `too_long` — длиннее `maxLength` схемы (`request`) или `JSON_CEILING` (`json`); `not_json` — тело не JSON (строки `json`); `<refused>` — 400 двери просьб без `fault` (строки `request`) |

## Стенд

Обе стороны подают через один стенд: семья, чья схема говорит `v: {maxLength: 32}` (строка просьбы: `POST /<sub>/requests
{"unit": <единица>, "v": <body>}`, поле `v` строки читается обратно), и таблица `counters`, чьё поле `doc` — типа `json`
(`POST /counters {"name": …, "doc": <body>}`, поле `doc` единицы читается обратно); отказ — `fault` ответа 400.

Манифест стенда — `Source/tests/testdata/testsub.subsystem.yaml` с двумя изменениями и без прочих (копия во временном
каталоге стенда; исходный файл не меняется):
- `unit.fields.doc: {type: json}`;
- `requests.schema` — `{type: object, required: [unit, v], additionalProperties: false, properties: {unit: {type:
  string}, v: {maxLength: 32}}}` (`v` без `type`: длина — по записанному тексту, правило ниже); `valid_for: 30`,
  `most_valid: 600` — как в `testsub`.

Перед таблицей создаётся единица `c1`; просьбы подаются к ней. Процессы, кроме хранилища и консоли, не запускаются.
Строка читается ролью с правом чтения `testsub/` через дверь хранилища; отказ — 400 с `fault` (или без него) и строки
нет. Повторная подача строки `json` (ниже) — `PUT /counters/<name> {"doc": <прочитанное значение>}` (правка главы 6.1),
затем поле `doc` сравнивается снова. Стенд — один свежий на всю таблицу (разбор чтения коммитов «cammeta-acceptance»
2026-10-20: подготовка — данные пакета, не выбор раннера).

## Правила

Правила записи — заголовок-комментарий таблицы (строка, `true`/`false`, `null` верхнего уровня, число по JCS, длина по
записанному тексту, канонический JSON словаря и списка, значение поля `json` как есть, потолок `JSON_CEILING` 4000 байт
UTF-8, не JSON — отказ без починки). Обратный ход: значение, прочитанное и поданное снова, записывается так же, байт в
байт — обе стороны подают каждую принятую строку `json` второй раз прочитанным значением.

## Прогон

Сторона подаёт `body` по виду `field` через стенд и сравнивает `stored` (или отказ и `fault`) байт в байт. Одна
каноническая функция на сторону — у двери просьб, у двери единиц и у воркера. Кто исполняет — по `field`: `json` — дверь
единиц консоли (`06-console`, глава 6.1); `request` — дверь просьб консоли (`06-console`) и воркер, который пишет просьбу
сам (`03-worker`, глава 3.6 Н1.5; своей функцией записи тела, без стенда консоли) (ACC-VECTORS-CONNECT-02, решение «Архитектора» 2026-10-26).

У воркера (`03-worker`, строки `request`, 52: 46 принятых, 1 `too_long`, 5 `<refused>`) вход единой команды `vectors` —
`cells: {body}`, ячейка как есть; нативный исход — код 0 и `{"stored": <строка>}` у принятой строки (`<empty>` — `""`)
либо `{"fault": "too_long"}` или `{"fault": "<refused>"}` — по колонке `fault`; сравнение по значению. `too_long` у воркера
судит не функция записи, а проверка тела по `requests.schema` до подачи (P/03.6 Н1.5) — по схеме стенда пакета
(`v: {maxLength: 32}`, длина по записанному тексту); отказ по схеме — исход `refused` нормы, в векторе он различается
словом колонки `fault` (ACC-REQUESTS-BODY-WORKER-01, решение «Архитектора» 2026-10-27).
