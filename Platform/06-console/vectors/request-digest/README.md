# Векторы: digest просьбы

Владелец — глава P/06.4 ([нормы](../../spec/06.4-console.norms.md) Н1.5 `digest`, Н3 «подать просьбу» шаг 1). Участники:
- `console` — просьба, поданная дверью;
- `<s>worker` — просьба, которую воркер пишет сам (`worker.requests`).

Байты таблицы пишет «Спецификация» (ADR-0083, стадия A). Соответствие продукта — его приёмкой по этой таблице
(ADR-0080 доп. 16).

Байты таблицы при переносе урока 6 (стадия B, ADR-0083 доп. (1)) не менялись, включая
заголовок-комментарий (его «М10/8 Н1.5», «lesson-owner М10/8» — прежний адрес нормы, ныне [договор просьбы и её метки](../../../common/contracts/request-mark.md) (разбор ревью стадии B 6–7, № 24); копия продукта
сверяется с этими байтами).

## `digest.tsv`

UTF-8, LF, поля через TAB. Строки с `#` и пустые пропускаются, первая непропущенная — заголовок. Пять полей:

| Поле | Значение |
|---|---|
| `sender` | `client` — тело клиента у двери консоли; `worker` — строка, которую пишет воркер |
| `input` | `client` — тело как прислано, текст JSON; `worker` — элементы строки как записаны, объект JSON из строк |
| `canonical` | текст JCS, который хэшируется (нормализованный вход) |
| `sha256` | hex SHA-256 байтов UTF-8 поля `canonical` |
| `note` | зачем строка |

## Правила

**Клиент.** Хэшируется JCS (RFC 8785, ADR-0072) тела после схемы. Из тела убирается только `valid_until` — единственное
поле сервера, которое клиент вправе прислать. `unit` остаётся.

**Воркер.** Хэшируется JCS объекта, собранного из полей тела строки как записаны (текстом). Не входят:
- `unit`;
- `valid_until`;
- штампы `by`, `at`, `group` и поле `about` (у `testsub2` — `of`);
- `filed` — не поле тела: экземпляр подателя, поле строки, которое пишет воркер (договор просьбы и её метки «Просьба» `filed`); «поля тела строки»
  нормы его не включают (ревью стадии A: SA1-27, Gemini 4.4).

**Два вида digest между собой не сравниваются.** Повтор узнаётся по digest своего вида (договор просьбы и её метки «Просьба» `digest`).

## Команда стенда `request-digest`

Ключ `stand` профиля `06-console` (раздел «Раскладка по процессам» [общего README приёмки](../../../common/acceptance/README.md));
шаблон с `{input}` — путь файла с одним объектом JSON `{"sender": "client" | "worker", "input": <исходный текст ячейки input
строкой JSON>}`: текст ячейки экранирован только для внешней строки — лексемы чисел, порядок полей и знаки сохраняются,
раннер ячейку не разбирает и не перевыводит. Ответ — `{"canonical": <текст JCS>, "sha256": <64 строчных hex>}`: `canonical`
сравнивается с колонкой `canonical` байтами UTF-8, `sha256` — с колонкой `sha256`. Вход не по форме: не объект, повтор или
незнакомое поле, `sender` не из двух слов, `input` не строка, её текст не объект JSON, у `worker` значение объекта не строка.
stdout — ровно один JSON-объект и LF: первый байт `{`, после объекта — LF и конец; лишние поля, байты, CRLF, пробелы
вокруг — FAIL строки; форматирование внутри объекта допустимо; служебное — в stderr. Код 0 — вычислено; вход не по
форме — код 2, stdout пуст (догадка стадии C C06-F2-IO-01, решение «Архитектора» 2026-10-23).

## Прогон

Сторона читает каждую строку и проверяет два шага:
1. из `input` по своему виду получает `canonical`, байт в байт;
2. SHA-256 от `canonical` равен `sha256`.
