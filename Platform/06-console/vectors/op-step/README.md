# Векторы: ключ пакета шага и ожидаемая версия шага

Владелец — глава P/06.9 ([нормы](../../spec/06.9-console.norms.md) Н1.4, Н2 «Пакет шага»; ADR-0095). Участники — ведущий консоли (ожидаемая версия в вызове шага) и подсистема (ключ пакета шага). Байты пишет «Спецификация»; значения посчитаны по тексту нормы, не кодом реализаций.
Сухого прогона реализацией нет.

## `key.tsv`

UTF-8, LF, поля через TAB; первая строка — заголовок `case<TAB>id<TAB>i<TAB>expect<TAB>note`.

| Поле | Значение |
|---|---|
| `id` | id операции, строка |
| `i` | номер шага, десятичный |
| `expect` | `step_key(id, i)`: hex SHA-256 от `UTF-8(id) ‖ 0x00 ‖ UTF-8(десятичная запись i)`, 64 строчных знака |

6 строк. Разделитель `0x00` не даёт паре `(id, i)` совпасть с другой парой при склейке.

## `expected.tsv`

UTF-8, LF, поля через TAB; первая строка — заголовок `case<TAB>input<TAB>expect<TAB>note`.

**Вход** — объект JSON:

| Поле | Значение |
|---|---|
| `steps` | шаги операции по порядку: `{root, expected}`, `expected` — как в строке шага |
| `done` | итоги по номеру шага, ключ — десятичная строка: `{state, versions?}` |
| `i` | номер шага, для которого нужно значение |

**Выход** — значение JSON `ожидаемое(i)` Н1.4, в `expect` таблицы — текстом JSON: `versions` итога `ok` с наибольшим номером меньше `i` и тем же `root`, иначе `expected` шага `i`. Сравнение — JSON по значению. 10 строк: без прежних шагов, `ok`, `fail`, `cancel`, `ok → fail → set`, два `ok`, чужой корень, два объекта одного корня, итог после `i`, копия шага `retry-failed`.

## Прогон

Сторона проверяет обе таблицы своей функцией: команда — запись `vectors/06-console/op-step` профиля (раздел «Раскладка по процессам» [общего README приёмки](../../../common/acceptance/README.md)). Нативный исход — код 0 и значение `expect`; вход не по форме — код 2. Форма команды — та же, что у соседних пакетов.
