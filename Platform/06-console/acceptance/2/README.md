## Границы сценариев

Границы сценариев: процессы перезапускаются между сценариями, переменные сбрасываются, а **хранилище сохраняется** внутри файла — сценарии идут по порядку, и сц. 05 читает строки, записанные раньше; файл начинается с пустого хранилища.

В файле 9 сценариев / 50 шагов. Перед полным повтором новый экземпляр получает пустые
прикладные строки и память заявок, затем раннер снова готовит c1. Параллельные прогоны
не разделяют экземпляр. Между сценариями одного файла c1, строки tallies и заявки
сохраняются; кольцо остаётся тем же, ротация и фоновые изменения во время файла запрещены.

Ключи `Idempotency-Key` и `@key(N)` — по словарю, тело берётся из текущего шага. Счастливый повтор сохраняет его, проба key reused меняет только секрет. Перезапуск процесса
не заменяет сброс памяти заявок в хранилище при новом полном запуске. Токен/роль консоли
имеет права на используемые единицы, ограничения входа настроены так, чтобы не мешать сценарию.

Список `configured` проверяется по id, без предположения о порядке строк. Подмножество
полей ожидания не отменяет полную форму ответа по контракту двери единиц (глава 6.1, [`06-console.api.openapi.yaml`](../../spec/06-console.api.openapi.yaml)). Формы ожидания — по словарю. Роль store
по умолчанию задаётся заново для каждого сценария; явный @as действует на последующие
store-запросы этого сценария. ASSERT не выполняет HTTP-запрос.

В сценарии 05 у t4 ожидается `feed_secret: ""`: поле объявлено строковым без default/inherit,
а при создании t4 его не передали. Оно получает пустую форму по главе 6.1 Н1.2. У t1–t3
ожидается маска; отсутствие секретного поля проверяется отдельно у таблицы shelves.

## Проверки вне сценарного файла

- Полные тела отказов секретов: detail/error обязательны; bad_url только для адреса;
  нечитаемое кольцо — 503 SealingUnavailable на POST/PUT. Запросы GET/DELETE не получают
  эту новую причину. Ни одна диагностика не повторяет исходное значение секрета.
- Состояния своей/чужой pending и неизвестного исхода — по главе 6.1 Н3; исход 503 не done,
  чужая заявка не снимается. Эта проверка требует модели/исполнения нужного состояния,
  обычный счастливый повтор сценария 01 её не заменяет.
- Кольцо: не задано, задано и читается, задано и пусто/повреждено/нечитаемо; отдельное
  открытие с чужим kid, неверными строкой/полем и повреждённым конвертом. Пустой файл
  не допускает запись открытого секрета. Не считать проверку префикса проверкой AES-GCM.
- Обслуживание: последовательные состояния таблицы Н3, k1/k9/k10, отказ rotate для
  иных kid, нуля, ведущих нулей, повторов и непредставимого следующего номера.
  Неподтверждённый обход/запись сохраняют старые ключи; зависимая копия не пропускается
  только потому, что текущие строки перезапечатаны. Работа выполняется с остановленными
  обычными записями, конкурентная ротация не заявляется проверенной. Старые ключи в
  профиле главы сохраняются все; status не подтверждает возможность их удаления.
- GET таблицы без секретных полей, вложенные секреты, снимки, журнал, argv и пульс —
  отдельные предметы чтения Н5. Права файлов и открытие воркером подтверждаются стендом.

## Контрпримеры прогона 31 и близкие допустимые случаи

1. Отдельный новый экземпляр без SECRETS_KEY, пустая память заявок, подготовлен c1.
   POST /tallies с ключом x и телом {name:t1, of:c1, feed:https://hub.example/a,
   feed_secret:alpha} — 400 с точным телом отказа Н4, без fault. Заменить только alpha
   на bravo, сохранить x — тот же отказ; ни единицы, ни заявки, ни резерва номера нет.
   Повторить со вложенным секретом в допустимом JSON-поле отдельного манифеста; отсутствие,
   пустая строка и null не являются непустым секретом (остальные проверки формы сохраняются).
   POST без секрета остаётся обычным созданием, его повтор работает по главе 6.1.
2. С кольцом k1: тот же POST с alpha создаёт единицу, точный повтор возвращает прежний
   ответ; замена только секрета на bravo даёт 422 key reused и ничего не меняет.
   Это последний шаг сценария 01. Проверить также прежнюю pending младше/старше 30 с
   по правилам главы 6.1: запрет без кольца не снимает чужую заявку; заданное нечитаемое
   кольцо остаётся 503, не подменяется режимом без ключа.
3. При кольце k1 оставить done-заявку исходного POST, затем PUT сменить секрет единицы.
   Остановить обычные записи, добавить k2, перезапустить держателей, перезапечатать
   строки и получить ноль старых конвертов. k1 остаётся в кольце; точный первоначальный
   POST под прежним ключом возвращает старый ответ, изменённый — 422. Не пересчитывать
   HMAC из текущей единицы и не сравнивать старую заявку только под текущим k2.
4. Разбор кольца: строка #backup + 64 hex — комментарий, кольцо только из неё пусто
   и нечитаемо. # пояснение, пустая строка, затем k1 + 64 hex — корректное кольцо;
   a#b + 64 hex — допустимый импортированный kid для open/seal, но не rotate.
   k1 + 64 hex + #хвост — неверная запись. В диагностике чужого kid показывается
   именно имя конверта (например, k9), без его ключевых байт.

Это спецификация дополнительных проб, не заявление об исполнении реализации.

Пробы прогона 32: заданное нечитаемое кольцо даёт SealingUnavailable на всех POST/PUT единиц, включая тело без secret и с пустым/null/пропущенным secret, до HMAC/заявки; GET/DELETE — обычные исходы. Незаданное кольцо сохраняет отдельный профиль 400 только непустому secret в POST. В secret-in строка с pass%E2%80%8Bword требует явного удаления U+200B из нормализуемого имени по Н1; исходное имя/значение не переписываются до маскирования.

Дополнительная проверка чтением/моделью R36-06: AAD Н1.2 использует полный путь. Различить строки a#b с полем c и a с полем b#c, прямое поле и вложенное, одинаковый *_secret в разных объектах/индексах массива, ключи с /, ~, NUL и Unicode. Для каждого пути проверить однозначное экранирование JSON Pointer и байты UTF-8 без нормализации; открытие не пробует старый AAD. Это проверка формы контекста, не стойкости AES или фактического открытия реализацией. Переход старых запечатанных строк требует отдельного внедрения и доверенного исходника, не проверяется TSV.

## Дополнительная проверка класса ошибок прогона 36 (Kimi)

Чтением проверить порядок POST/PUT: после ограниченного разбора JSON-объекта кольцо раньше формы полей, HMAC и захвата заявки. Нечитаемое кольцо даёт общий 503 по главе 6.1 даже при плохом поле. GET/DELETE этого отказа не приобретают. P/02.5 Н1.3 включает domainworker как платформенную роль; манифесты подсистем её не включают (процесса этой роли нет, P/01.2 Н1.1). Проверка общей таблицы загрузчиком — работа реализации, а не этой приёмки.

Это предмет ручной проверки спецификации и будущей проверки реализации. Подготовленные запросы, чтение и конечные модели автора не являются выполненным стендовым испытанием.

## Проверка класса ошибок R37 (Codex)

Источник публичного id/name/rid с суффиксом _secret отвергается при загрузке, даже если исходное поле маскируется. Проверить одиночный table.key, все подстановки и requests.key. Запрет NUL — условие профиля seal/open договора запечатывания; общий Cmd P/01.1 сам по себе NUL не запрещает. Не приписывать ограничение владельцу, у которого его нет.

Это предмет проверки норм/данных и будущего стенда, не выполненное испытание реализации.
