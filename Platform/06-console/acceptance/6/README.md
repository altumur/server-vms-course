## Сц. 01–07: один экземпляр без воркеров

Сценарии выполняются последовательно на одном экземпляре: 02 использует u1 из 01, 07 — u1 из 01. Между ними состояние не
сбрасывается.

Отдельное хранилище и новая консоль без домена, доступ только с петли по главе 6.3 Н1.3 `open` (ключей нет — только с
петли, имя operator). Загружена актуальная testsub из общих testdata: unit.id = name, rows = counters,
placement.servers имеет эффективное умолчание shared (ключ в testsub не задан). Работает её контроллер и ресурс `srv-a` — первым шагом сц. 01 (`@start resource`: пульсы консоль читает дверью объектов
ресурса своего сервера; C06-PULSE-LAPSE-503-03, решение «Архитектора» 2026-10-29); воркеров, заказанных процессов и фоновых
писателей нет. Серверы srv-b, srv-nobody неизвестны.
Создание дренажа не объявляет сервер известным для операций labels/decommission.

«Пусто» относится к прикладным строкам и объектам, размещениям, назначениям, слотам, policy,
platform/servers, platform/doors, platform/drain, запросам и отметкам decommission,
заявкам повторов POST и памяти id хранилища. Манифест, его метка и необходимые данные конфигурации
установлены подготовкой, а не удаляются словом «пусто». Новый прогон/параллельный прогон получает
своё состояние, без общих каталогов и портов.

Между 01 и 02 контроллер должен завершить хотя бы один проход после создания u1.
Подтверждение — смена отчёта controller/pass, наблюдаемая командой печати отчёта из раздела «Стенд»
общего README приёмки; она не требует добавления новой HTTP-двери. Предел ожидания 15 с. Истечение срока — отказ подготовки,
а не разрешение продолжить. GET /counters без размещения не доказывает завершение прохода:
при пустом пуле строка размещения может вообще не появиться.

Сц. 07 — единицы дренажа. Воркера нет, его подделывают: шаг 1 пишет строку слота `w-1` ролью `testsubworker` (`@as`),
шаг 2 кладёт пульс `inputs/hb-w-1-no-status.json` с `status: []` (`@put object`). Контроллер назначает `d1` и `u1` на
`w-1`. Дренаж `srv-a` считает единицы по назначению ∪ `status[].id`: `units: 2`, `safe: false`, хотя `status` пуст
(Н2.2, сверка python и go М10/3–5, P8).

Сц. 01 — неразмещённая единица и 404 where; 02 — её наличие в unplaceable; 03 — политика;
04 — один активный дренаж; 05 — отказ формы меток раньше проверки сервера и неизвестный сервер;
06 — неизвестный сервер при выводе; 04, шаги 11–13 — имя сервера не по грамматике Н2.1 — 400. Они не проверяют выбор в живом пуле, гонки, safe при pending_writes,
вывод живого/никогда не слышанного ресурса, выдачу door, прогноз смены меток. Успешная смена меток — только в памяти повторов (сц. 05 шаги 7–13).
Память повторов дверей записи (Н2.1) — сц. 03 шаги 8–12, 04 шаги 15–22, 05 шаги 7–13, 08 шаги 7–9, 13 шаги 17–20.
Для этих ветвей использовать таблицу свидетельств Н5. Успех схемы не доказывает права,
изменение состояния, срок или исполнение запроса контроллером.

## Сц. 08–16: свежий стенд на сценарий

Двери консоли `testsub` (root) и `testsub2` (смонтирована, `console2 …` — её двери `/testsub2/…`), контроллер и ресурс
`srv-a` по директивам (`@start controller`, `@start resource`), хранилище (`store …`); без воркеров и домена. Сборка со
схемой 1 (сц. 08 ждёт `understood: 1`, сц. 11 — `understood: 1`, `can_raise_to: 1`); предел тела консоли — 1 МиБ.

Интерфейс запуска — раздел «Стенд» общего README приёмки, без своих команд главы: `@start controller` и
`@start resource` — команды ролей контроллера `testsub` и ресурса сервера `srv-a` (подстановки `{data}`, `{socket}`,
`{manifest}`, у ресурса `{rport}`); ресурс готов, когда слушает `{rport}` и есть строка `platform/doors/srv-a`.
`console …` и `console2 …` — одна консоль на `{port}`, второй — префикс `/testsub2`. `store …` без `@as` — дверь хранилища
`admin.sock` (`{socket}` — дверь с полными правами, [общий README приёмки](../../../common/acceptance/README.md) «Сокеты
ролей»): шаг 14 сц. 04 и шаг 10 сц. 05 читают `platform/drain` и `platform/servers/srv-a` вне префикса подсистемы; `@as <роль>` — сокет роли до конца сценария.

До каждого сценария остановить процессы предыдущего, создать отдельные пустые строковое/объектное хранилища и очистить
переменные/память повторов. Загрузить неизменённые testsub и testsub2; root — testsub, второй доступен под /testsub2;
домена нет, обращения с петли. Фоновые controller/resource/worker до @start не работают. Хранилище свежее и пустое — строки
platform/schema нет, раннер её не пишет (чтение коммитов «cammeta-acceptance» 2026-10-20). Для каждого POST создания единицы раннер выдаёт свежий Idempotency-Key, сохраняемый только для
повторов того же шага.

Сверка python и go М10/6–11 (сц. 08–12 и дописанные шаги):
- Сц. 08 шаг 6 — версия схемы без верхней границы формы: больше своей SCHEMA — 409, не 400.
- Сц. 10 шаги 8–10 — журнал дренажа через `/events` консоли (ресурс — с шага 1, C06-PULSE-LAPSE-503-03): `drain.started`, `drain.ended`,
  иного вида (`drain.cleared`) нет (T22).
- Сц. 09 — дренаж при нечитаемом пульсе (T2): слот `w-1` ролью `testsubworker`, пульс — тем же входом, что сц. 07,
  `inputs/hb-w-1-no-status.json`, затем `@spoil object`; воркер сервера — по слоту.
- Сц. 12 — формы чисел пульса воркера `w-1` без живого воркера: строка слота и пульсы `@put object` из `inputs/`
  (`hb-w-1-pending-0.json` — опора: `safe: true`; `-pending-missing`, `-pending-fraction` (`1000.0`), `-pending-minus-zero`,
  `-pending-2p63` — `pending_unsaid`; `-schema-fraction` (`1.0`) — `schema: null`; `-build-number` (`5`) — `build: null`, не известно, П1; В7 п. 3 строка 14).
  Каждый `@put object` меняет версию пульса — консоль видит его живым (Н1.2: устаревший пульс тоже дал бы
  `pending_unsaid`, поэтому шаги 4 и 21 — опора свежести; свежесть — [договор наблюдения](../../../common/contracts/observation.md))
  (сверка python и go М10/6–11, T1, T3, T4, T27). Перед каждым входом не по форме, кроме первого, — снова
  `-pending-0` и `@until` до `safe: true` (шаги 8–9, 12–13, 16–17): иначе ожидание `pending_unsaid` следующего входа
  совпало бы с прежним состоянием, и консоль, которая видит новый пульс с запозданием, прошла бы шаг по старому пульсу
  (разбор ревью стадии B 6–7, № 21).

Сц. 10 после DELETE снимает только дренаж: d1 остаётся неразмещённой, would_strand.testsub=[d1], счётчики 0 и safe=true;
полный ответ сохраняет одинаковые ключи would_strand/subsystems по Н2.2. Сц. 11 (`/schema` после обновления) —
свидетельство и P/02.4-08: ресурс — под ключом `resource/srv-a` (Н2.3).

Чтением: версия query — только ASCII [1-9][0-9]* целиком; сверить все причины 409 подъёма схемы (Н3 «поднять_схему»,
Н4).

## Отдельные проверки полных ответов

- `POST /drain` с server=srv-a: полный ответ `{draining: "srv-a"}`; `DELETE`: `{draining: ""}`.
  Противоположные тела не проходят схему даже при правильном последующем GET.
- Полные ответы меток и drain проверяются по всей грамматике имени подсистемы
  [P/02.1 Н1.2](../../../02-installer/spec/02.1-installer.norms.md#н12-документ),
  включая весь закрытый список зарезервированных имён. Для каждого слова проверить отказ
  в префиксе UnitRef (would_move и will_move), в ключе каждой из карт would_strand/subsystems
  и в поле subsystem; например, platform/u1, domain/u1, events/u1 и ключ events недопустимы.
  Близкие допустимые имена — platformx и events2 (ссылки platformx/u1 и events2/u1).
  Дополнительные отрицательные случаи имени: bad/name, заглавная первая буква, 33 знака
  и конечный перевод строки. Положительные: testsub и имя длины 32. Это проверка схем
  ответов, не требование загружать запрещённую подсистему или получать такой ответ от процесса.
  Существование и видимость подсистем, совпадение ключей карт и поля subsystem проверяются
  отдельно, одна грамматика этого не доказывает.
- В обоих GET-ответах drain поле `draining` проверяется как имя сервера одного сегмента
  либо `""`: `a/b` и обратный слэш отвергаются схемой, `box-a` и пустая строка допустимы.
  Это не меняет POST (только непустое имя) и DELETE (только пустая строка).
- Where.worker, ненулевой Where.directory и каждый элемент SubsystemDrain.pending_unsaid имеют форму имени слота
  [P/03.2 Н1.4](../../../03-worker/spec/03.2-worker.norms.md).
  Допустимы `w-1`, `w-server-12`, prefix длиной восемь букв и длинный допустимый суффикс;
  не допускаются `""`, `w`, `w-`, `w--1`, `W-1`, `w/1`, `w_1` и конечный перевод строки.
  Схема проверяет общую грамматику; соответствие slot.prefix конкретного манифеста проверяется
  отдельно. directory:null и пустой pending_unsaid допустимы; пустое имя directory или элемент массива — нет.

Это предмет ручной проверки спецификации и будущей проверки реализации. Подготовленные запросы, чтение и конечные модели
автора не являются выполненным стендовым испытанием.

## Сны (`@sleep`, ADR-0080 доп. (17) п. 4)

Сон один: сц. 13 шаг 7, 46 с — время перед действием: версия слота `srv-b` не меняется дольше LOST_AFTER 45 с ([договор наблюдения](../../../common/contracts/observation.md) «Свежесть»), только тогда сервер не «слышен» и `may_confirm_gone` может быть `true` (Н3 «вывести_сервер»). Ожидание события — `@until`: сц. 02 шаг 2 (причина в `/unplaceable` после прохода), 07 шаги 4–5, 09 шаг 6
(назначение по проходу контроллера), 10 шаг 8 (журнал в индексе ресурса), 11 шаг 3 (пульс ресурса в `processes`), 12
шаги 4, 5 и нечётные 7–25 (консоль видит новый пульс; чётные 6–24 — `@put object`; разбор ревью стадии B 6–7, № 21, № 22), 13 шаги 2, 15, 16 (живой ресурс, журнал вывода в индексе ресурса), 16 шаг 3 (`/servers` по строке меток).

## Границы сценариев

Сц. 01–07 — один экземпляр, состояние между ними не сбрасывается. Перед сц. 08–16 раннер останавливает процессы,
сбрасывает хранилище (строки и объекты) и переменные. После последнего шага дождаться остановки всех созданных процессов,
затем удалить состояние.
