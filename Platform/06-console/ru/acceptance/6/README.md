## Сц. 01–07: один экземпляр без воркеров

Сценарии выполняются последовательно на одном экземпляре: 02 использует u1 из 01, 07 — u1 из 01. Между ними состояние не
сбрасывается.

Отдельное хранилище и новая консоль без домена, доступ только с петли по главе 6.3 N1.3 `open` (ключей нет — только с
петли, имя operator). Загружена актуальная testsub из общих testdata: unit.id = name, rows = counters,
placement.servers имеет эффективное умолчание shared (ключ в testsub не задан). Работает её контроллер и ресурс `srv-a` — первым шагом сц. 01 (`@start resource`: пульсы консоль читает дверью объектов
ресурса своего сервера; C06-PULSE-LAPSE-503-03, решение «Архитектора» 2026-10-29); воркеров, заказанных процессов и фоновых
писателей нет. Серверы srv-b, srv-nobody неизвестны.
Создание дренажа не объявляет сервер известным для операций labels/decommission.

«Пусто» относится к прикладным строкам и объектам, размещениям, назначениям, слотам, policy,
platform/servers, platform/doors, platform/drain, запросам и отметкам decommission,
заявкам повторов POST и памяти id хранилища. Манифест, его метка и необходимые данные конфигурации
установлены подготовкой, а не удаляются словом «пусто». Новый прогон/параллельный прогон получает
своё состояние, без общих каталогов и портов.

Между 01 и 02 контроллер должен завершить хотя бы один проход после создания u1.
Подтверждение — смена отчёта controller/pass, наблюдаемая командой печати отчёта из раздела «Стенд»
общего README приёмки; она не требует добавления новой HTTP-двери. Предел ожидания 15 с. Истечение срока — отказ подготовки,
а не разрешение продолжить. GET /counters без размещения не доказывает завершение прохода:
при пустом пуле строка размещения может вообще не появиться.

Для этих ветвей использовать таблицу свидетельств N5. Успех схемы не доказывает права,
изменение состояния, срок или исполнение запроса контроллером.

## Сц. 08–16: свежий стенд на сценарий

Двери консоли `testsub` (root) и `testsub2` (смонтирована, `console2 …` — её двери `/testsub2/…`), контроллер и ресурс
`srv-a` по директивам (`@start controller`, `@start resource`), хранилище (`store …`); без воркеров и домена. Сборка со
схемой 1 (сц. 08 ждёт `understood: 1`, сц. 11 — `understood: 1`, `can_raise_to: 1`); предел тела консоли — 1 МиБ.

Интерфейс запуска — раздел «Стенд» общего README приёмки, без своих команд главы: `@start controller` и
`@start resource` — команды ролей контроллера `testsub` и ресурса сервера `srv-a` (подстановки `{data}`, `{socket}`,
`{manifest}`, у ресурса `{rport}`); ресурс готов, когда слушает `{rport}` и есть строка `platform/doors/srv-a`.
`console …` и `console2 …` — одна консоль на `{port}`, второй — префикс `/testsub2`. `store …` без `@as` — дверь хранилища
`admin.sock` (`{socket}` — дверь с полными правами, [общий README приёмки](../../../../common/ru/acceptance/README.md) «Сокеты
ролей»): шаг 14 сц. 04 и шаг 10 сц. 05 читают `platform/drain` и `platform/servers/srv-a` вне префикса подсистемы; `@as <роль>` — сокет роли до конца сценария.

До каждого сценария остановить процессы предыдущего, создать отдельные пустые строковое/объектное хранилища и очистить
переменные/память повторов. Загрузить неизменённые testsub и testsub2; root — testsub, второй доступен под /testsub2;
домена нет, обращения с петли. Фоновые controller/resource/worker до @start не работают. Хранилище свежее и пустое — строки
platform/schema нет, раннер её не пишет (чтение коммитов «cammeta-acceptance» 2026-10-20). Для каждого POST создания единицы раннер выдаёт свежий Idempotency-Key, сохраняемый только для
повторов того же шага.

Чтением: версия query — только ASCII [1-9][0-9]* целиком; сверить все причины 409 подъёма схемы (N3 «поднять_схему»,
N4).

## Сны (`@sleep`, ADR-0080 доп. (17) п. 4)

Сон один: сц. 13 шаг 7, 46 с — время перед действием: версия слота `srv-b` не меняется дольше LOST_AFTER 45 с ([договор наблюдения](../../../../common/ru/contracts/observation.md) «Свежесть»), только тогда сервер не «слышен» и `may_confirm_gone` может быть `true` (N3 «вывести_сервер»). Ожидание события — `@until`: сц. 02 шаг 2 (причина в `/unplaceable` после прохода), 07 шаги 4–5, 09 шаг 6
(назначение по проходу контроллера), 10 шаг 8 (журнал в индексе ресурса), 11 шаг 3 (пульс ресурса в `processes`), 12
шаги 4, 5 и нечётные 7–25 (консоль видит новый пульс; чётные 6–24 — `@put object`; разбор ревью стадии B 6–7, № 21, № 22), 13 шаги 2, 15, 16 (живой ресурс, журнал вывода в индексе ресурса), 16 шаг 3 (`/servers` по строке меток).

## Границы сценариев

Сц. 01–07 — один экземпляр, состояние между ними не сбрасывается. Перед сц. 08–16 раннер останавливает процессы,
сбрасывает хранилище (строки и объекты) и переменные. После последнего шага дождаться остановки всех созданных процессов,
затем удалить состояние.
