## Подготовка каждого сценария

Сценарии независимы. Перед каждым остановить и дождаться всех процессов прошлого
сценария, создать изолированные каталоги/порты и пустое хранилище: строки, объекты,
память id хранилища, заявки POST консоли, учёт asked и метки commands отсутствуют.
Очистить дерево событий, зеркала и кэш индекса, переменные и ключи повторов раннера.
Установить актуальную testsub из общих testdata с её служебной меткой административными
правами. Единиц и пользовательских строк ещё нет. Подготовка — не перенос состояния
предыдущего сценария и не проверка установщика.

Запустить хранилище, новую консоль testsub и ресурс srv-a по разделу «Стенд» общего README приёмки. Их двери должны быть готовы;
ресурс зарегистрирован и доступен консоли до первого шага. Все процессы этой коробки
используют одну BOX_ID и server=srv-a; каждый новый процесс получает новый instance.
Контроллера и воркеров нет: сценарии их не запускают. Нет сторонних демонов и таймеров, способных запустить держателя в выбранном сценарии.
platform/mirror и platform/space не заданы; запросы освобождения и копии не готовятся.

console — дверь консоли testsub с петли, доступ к операциям и единицам разрешён;
resource — дверь ресурса srv-a с допустимой личностью; store — дверь хранилища с чтением
testsub/ и objects/testsub/. Если развёртывание использует TLS, выдать соответствующие
сертификаты и роли по P/02.4 N1.6 (`w2c-ca.sh issue <server> <роль>`, комплект `kit`) и правилу адреса P/02.4 N1.6;
проверку отказов TLS эти сценарии не заменяют.
Сроки и параметры testsub не ускорять: valid_for=30, most_valid=600; ожидаются обычные
такты держателя и жнеца, settle=60 по умолчанию.

## scenarios.tsv

Формат — [словарь директив и дверей «Стенда» общего README приёмки](../../../../common/ru/acceptance/README.md#словарь-директив-и-дверей): двери `console`, `console2`, `resource`, `store` (с `@as`), `admin`, директивы `@until`, `@sleep`, форма запроса `@header`. Всего 9 сценариев / 120 шагов; все HTTP (с @until и @key).

`Idempotency-Key` и `@key(N)` — по словарю. Тело повтора
совпадает с первоначальным. Наличие заголовка у /marks не создаёт обещания
памяти повторов для отметки.

Раннер не должен завершать весь сценарий раньше суммарного бюджета его шагов. После
последнего шага дождаться остановки всех созданных процессов, затем удалить состояние.

## Сравнение

Формы ожидания — по словарю.
Ожидание одного кода не требует пустого тела.

Повтор переменной внутри expect сравнивает её временное значение.
Директивы не отправляются серверу как HTTP. Полный ответ дополнительно проверяется по контракту его владельца:
хранилище — P/01.1, единицы — глава 6.1, двери ресурса — P/05 N2, остальные двери — N2 главы. В частности, answered
с @any в TSV всё равно обязан быть полной меткой одной из трёх форм AnsweredMark.

## Свидетельства вне TSV

Это задания реализации/стенда, а не уже выполненные проверки. Объекты, события, индекс, wait, потоки, retention/holds и
свободное место — в приёмке P/05; держатель и метка — в
приёмке главы 3.6.

Чтение ветвей и схема подтверждают только соответствующий порядок/форму. Таймеры,
процессы, барьеры файлов, сетевые обрывы и криптографическая личность требуют отдельных
наблюдений.

Граница свежести строки двери у слияния — `≤ LOST_AFTER` ([договор наблюдения](../../../../common/ru/contracts/observation.md)): ресурс, чья строка двери менялась ровно 45 с назад, жив — граница проверяется вектором
[`fresh-age`](../../../../common/ru/vectors/fresh-age/README.md), не шагом (нужны управляемые часы).

## Дополнительные проверки источника

Для обычной подстановки requests.key нужны строки; :int принимает конечное число, bool исключён, усечение к нулю и десятичное написание общие.

Это предмет проверки норм/данных и будущего стенда, не выполненное испытание реализации.

Границы :int по P/02.1: binary64, модуль не больше 2^53−1; bool/null/строка/нечисловое/неfinite/выход за границу — 400, не языковое приведение. Проверить ±0.5, ±7.9, ±(2^53−1), 1e16, 1e21 и канонический десятичный результат без экспоненты.
