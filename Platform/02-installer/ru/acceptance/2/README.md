## Интерфейс профиля

Используется [формат профиля](../../../../common/ru/acceptance/PROFILE.md) `02-installer`. Пакет функции канонизации использует `stand.canonical` с `{input}`: путь называет входной манифест пакета, stdout содержит ровно канонические байты его [формы провода](../../../../common/vectors/wire.tsv). Пробы установки ниже используют `stand.manifest-put` с `{socket}`, `{file}`; своя команда выполняет штатную установку, а не только печатает канонический вид. Параметры запуска хранилища принадлежат выбранному профилю `01-store`. Объявление команд не доказывает полного positive-profile provider, достаточности B/V и исполнения восстановления.

## puts.tsv

Формат `puts.tsv` [главы 2.3](../3/README.md) с четвёртой колонкой `canonical` и директивами между файлами. Установка —
команда `manifest-put {socket} {file}` раздела «Стенд» общего README приёмки; хранилище — экземпляр «Стенда» с потолком строки
524288 байт (общий README, «Parameters of each instance»).

**Форма файла.** UTF-8, строки через LF, поля через TAB. Строки, начинающиеся с `#`, и пустые строки пропускаются. Первая
не пропущенная строка — заголовок `case<TAB>puts<TAB>expect<TAB>canonical`, дальше — по строке на случай; ровно четыре поля.

- `case` — имя случая: `[a-z0-9_]+`, уникально в файле;
- `puts` — через один пробел, по порядку: имена файлов `puts/<имя>.subsystem.yaml` и директивы `@view-delete`,
  `@view-spoil`, `@rev-delete`, `@rev-spoil`; первым и последним — файл;
- `expect` — `<код> <rev>`: `<код>` — код возврата **последней** установки (`0` или `2`), `<rev>` — десятичное `rev` строки
  `platform/manifest/<name>` после неё, где `<name>` — `name` последнего файла; `-` — строки нет;
- `canonical` — имя случая [`vectors/canonical/cases.tsv`](../../../vectors/canonical/cases.tsv), байты `expect/<case>.json`
  которого — ожидаемое поле `manifest` строки вида; `-` — строки вида нет.

**Директивы** (между установками, через `admin.sock` экземпляра — `{socket}` «Стенда», операции P/01.1; `<name>` — `name`
файла перед директивой):
- `@view-delete` — `delete` строки `platform/manifest/<name>/canonical/1`;
- `@view-spoil` — прочитать строку `platform/manifest/<name>/canonical/1` и записать её же с `cas` по прочитанной версии, но с
  полем `manifest`, равным `{}` (иной вид: не проекция манифеста); прочие поля — как были;
- `@rev-delete` — `delete` метки `platform/manifest/<name>/rev`;
- `@rev-spoil` — прочитать метку `platform/manifest/<name>/rev` и записать её же с `cas` по прочитанной версии, но с полем
  `rev`, равным строке `"x"` (метка не по форме N1.5 главы 2.3: `rev` — не десятичное целое); прочие поля — как были.

**Исполнение.** Случаи независимы, порядок строк не важен. Для **каждой строки** раннер берёт новое пустое хранилище
(P/01.1; ни одного манифеста) и исполняет `puts` по порядку: файл — отдельным вызовом установки, директиву — записью хранилища.
Все установки, кроме последней, ДОЛЖНЫ вернуть `0`, каждая директива — пройти: иное — несовпадение случая (подготовка не
удалась). После последней установки раннер сравнивает:

1. код возврата — с `<код>`;
2. при коде `2` — stderr называет файл последней установки и ключ отказавшей строки: если последняя директива перед установкой — `@rev-spoil` — ключ метки `platform/manifest/<name>/rev`, иначе — ключ вида `platform/manifest/<name>/canonical/1` (оба входят в
   текст; вес и потолок в тексте не сравниваются);
3. `rev` строки `platform/manifest/<name>` — с `<rev>`, как в главе 2.3 (дверь хранилища `GET /v1/get?key=…`, поле `rev` в
   `items`; `-` — `items: null`);
4. метку `platform/manifest/<name>/rev`: её `rev` — тот же `<rev>`, `sha256` — `sha256` строки; `-` — метки нет; при коде `2`
   после `@rev-spoil` — метка та, что записала директива (`rev` — `"x"`): отказанная установка её не трогает;
5. строку вида `platform/manifest/<name>/canonical/1` (`items` по кодеку [семьи `canonical-row`](../../../data/canonical-row.schema.json)):
   `form` — `"1"`, `rev` — `<rev>`, `sha256` — `sha256` строки, `manifest` — байты `expect/<canonical>.json` вектора байт в
   байт; лишние поля не сравниваются; `canonical` = `-` — строки вида нет.

Пункты 4–5 сравнивают состояние после установки, не порядок записей во времени: порядок строка — вид — метка и повтор
вида после конфликта `cas` — чтением по N5 главы.

## puts-ceiling.tsv: потолок хранилища не по умолчанию

Потолок вида — `max_value` ответа `GET /v1/status` хранилища, а не число 524288 (решение «Архитектора» по вопросу Go P/02 № 4).
Случаи — отдельный файл `puts-ceiling.tsv` (аудит покрытия P/02, B00; `puts.tsv` своей формы не меняет; форма
проверки — check_spec 0021baa83): форма —
`case<TAB>puts<TAB>expect<TAB>canonical<TAB>ceiling`, первые четыре поля и сравнение — как у `puts.tsv`; `ceiling` — потолок
строки нового экземпляра этой строки (`{row_ceiling}` команды запуска «Стенда»). Раннер до случая сверяет параметр:
`GET /v1/status` → `max_value` = `ceiling`, и поведением — `items` весом ровно `ceiling` записывается, на байт больше — 413
`toolarge` с `limit` = `ceiling`; не сошлось — прогон не выполнен.

Случаи другого потолка и их исходы — в [данных случаев только для судьи](README.cases.md). Установщик проверяет вес с окончательной новой rev до любой записи (глава 2.3 N3 шаг 14a), поэтому отказ приходит до частей, строки и метки. Граница через конфликт `cas` двух установщиков проверяется чтением: таблица ставит последовательно.

## Проверки чтением

Порядок записей во времени (строка — вид — метка), повтор `cas` вида, кластер из одного процесса (P/02.4 N1.10, R15) и
читатель вида (P/02.2-06 — правками читателей) — чтением по N5 главы.

## Аудит покрытия Gemini P/02: метка `/rev` (формы «Архитектора»)

Свойства 13 и 14 отчёта the coverage audit Gemini P02 (for people) (ветка gemini/audit-coverage, c698f3291) — директивы `@rev-delete`,
`@rev-spoil` (решение «Архитектора» по вопросу формы; check_spec dad80a80b), случаи 08 `rev_deleted` и 09 `rev_spoiled`.
