## Интерфейс профиля

Используется [формат профиля](../../../../common/ru/acceptance/PROFILE.md) `02-installer`. `stand.manifest-put` принимает подготовленные административный `{socket}` и кандидат `{file}`, выполняет штатную установку манифеста с прежними правилами каталога, файлов, порядка записи и неизменённого состояния. Нативный исход установки описан ниже; подстановки deployment и строки ожидания команда не получает. Создание хранилища принадлежит выбранному профилю `01-store`. Реализация выбирает обёртку и флаги для существующего договора команды. Явно непривязанное обязательство восстановления ниже остаётся неисполненным.

## puts.tsv

Установка манифеста `manifest put` реализации (N3 «Смена манифеста», имя команды и argv — [`operator-commands.tsv`](../../../forms/operator-commands.tsv)); раннер зовёт её
командой `manifest-put {socket} {file}` раздела «Стенд» общего README приёмки (пилот хранилища, A6).

**Форма файла.** UTF-8, строки через LF, поля через TAB. Строки, начинающиеся с `#`, и пустые строки пропускаются. Первая
не пропущенная строка — заголовок `case<TAB>puts<TAB>expect`, дальше — по строке на случай; ровно три поля.

- `case` — имя случая: `[a-z0-9_]+`, уникально в файле;
- `puts` — имена файлов `puts/<имя>.subsystem.yaml` через один пробел, по порядку установки, и директивы `@rev-max`,
  `@shell-put <имя>`, `@file-fill <путь> <байтов>` между ними; первым и последним — файл; оболочки подсистемы рядом с манифестом нет, пока её не
  положит `@shell-put` (N1.5 `shell`: нет файла — поле не пишется);
- `expect` — `<код> <rev>`: `<код>` — код возврата **последней** установки (`0` или `2`), `<rev>` — десятичное значение поля
  `rev` строки `platform/manifest/<name>` после неё, где `<name>` — `name` последнего файла; `-` — строки нет.

**Директивы** (только эта глава; через `admin.sock` экземпляра — `{socket}` «Стенда»; `<name>` — `name` файла перед директивой):
- `@rev-max` — прочитать строку `platform/manifest/<name>`, метку `platform/manifest/<name>/rev` и вид
  `platform/manifest/<name>/canonical/1` и записать каждую с `cas` по прочитанной версии, где `rev` = `9007199254740991`
  (2^53 − 1), прочие поля — байт в байт прежние: состояние, как после честной установки с такой ревизией (N1.5 `rev`);
- `@shell-put <имя>` — положить рядом с манифестом `<name>` оболочку `<name>.shell.html` с байтами `puts/<имя>.shell.html`
  (прежнюю — заменить); она действует для следующих установок строки; рабочая копия — своя у каждой строки.

**Файлы перечня.** Рядом с рабочей копией манифеста каждой установки раннер кладёт всё содержимое
[`06-console/acceptance/5/inputs/testsub2/`](../../../../06-console/acceptance/5/inputs/testsub2) под теми же путями — те же файлы, что у
`testsub2` на стенде (общий README, «Manifests»); P/02.3 N3 читает их рядом с файлом манифеста. Директивы для них нет: файлы между
установками не меняются. Оболочка рядом с манифестом появляется только по `@shell-put`.

- `@file-fill <путь> <байтов>` — положить рядом с манифестом файл `<путь>` (относительный, без `..`) ровно в `<байтов>` байтов; он
  действует для следующих установок строки; байты любые: предмет — размер (потолки P/02.3 N1.5). Файл создаёт раннер, в `puts/` его нет,
  поэтому потолки в 8 МиБ не добавляют веса данным приёмки.

**Исполнение.** Случаи независимы, порядок строк не важен. Для **каждой строки** раннер берёт новое пустое хранилище
(P/01.1; ни одного манифеста, в том числе `testsub`) и ставит файлы этой строки по порядку в одно и то же хранилище командой
установки, каждый отдельным вызовом. Все установки, кроме последней, ДОЛЖНЫ вернуть `0`: иное — несовпадение случая
(подготовка не удалась). После последней раннер сравнивает:

1. код возврата — с `<код>`;
2. при коде `2` — stderr называет файл последней установки (имя файла входит в текст), как у `verdicts.tsv`; отказ по атрибуту
   `on…=` в оболочке — файл оболочки `<name>.shell.html` (P/02.3 N4: «stderr names the file and attribute»; имя атрибута — чтением);
3. `rev` строки `platform/manifest/<name>` — с `<rev>`: строка читается дверью хранилища (`GET /v1/get?key=platform/manifest/<name>`,
   поле `rev` в `items`) или командой `manifest show` реализации; `-` — `items: null` / строки нет.

Больше ничего не сравнивается: ни метка `/rev`, ни текст отказа сверх имени файла. Проверки каталога (глава 2.1 N3 `load_catalogue`: «A=B», совпадение `metrics.prefix`) при одиночной загрузке такого файла дают `ok`, отказ — только у установки в каталоге. Тот же файл снова — «unchanged»; изменённый файл с тем же именем получает новую ревизию.
Проверки каталога главы 2.1 N3 действуют для `worker.creates`, `worker.uses` и имён ОС (ADR-0091). Адресата или владельца доли в каталоге ещё нет — проверка ждёт его установки; адресат после несовместимого заказчика — отказ у установки адресата.
Виды токена домена (ADR-0091 доп. (14), (17), (18) п. 6): тот же вид у второй подсистемы — отказ; вид маршрута `door.routes[].domain` объявлен другой подсистемой каталога или своей — принят; вида нет — отказ (отсрочки нет).
Статические файлы и объявленная оболочка (ADR-0094 B7): все расширения, вложенные сегменты, `api.js` и `apis/…` рядом с запретом `api/`, пустой файл и файл в две части — принятые имена; указанный в перечне файл, которого нет, — код 2, stderr называет файл манифеста и путь; `console.shell: true`, оболочки нет — код 2; тот же манифест без этого слова при наличии оболочки — новая ревизия с объявлением; файл выше `FILE_MAX` или сумма выше `FILES_TOTAL_MAX` — код 2 до записи, ревизия прежняя; ровно `FILE_MAX` — принят.
Отсрочка `near` (ADR-0091 доп. (26) п. 2): подсистемы `near.sub` нет — клиент принят, проверка полей ждёт; адресат после несовместимого клиента — отказ у установки адресата.

## Проверки чтением

Строка и метка манифеста в хранилище, все причины отказа старта, допустимая отставшая метка, остановка при смене метки и ветвь
`toolarge` установщика — чтением по N5 главы: `puts.tsv` сравнивает только код последней установки, имя файла в stderr и
`rev` строки.
