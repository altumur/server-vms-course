### N1.5 The manifest row in the store

The form of the row and the mark is the section «Data families» below, built from the schemas [`data/manifest-row.schema.json`](../data/manifest-row.schema.json),
[`data/manifest-rev.schema.json`](../data/manifest-rev.schema.json) and the outcomes of an unreadable row `*.outcomes.tsv` next to them (ADR-0088 item 7;
review of stage B 1–2, item 5; the built section replaced the form block, a task of the Architect by 495cc7833). The mark
`platform/manifest/<sub>/rev` is written AFTER the row; a running process reads it. The rules of the writer and the reader (`rules`):

- rev strictly grows; the mark never decreases.
- Identical yaml, shell and files are «unchanged», rev does not grow; shell is compared by bytes, absence equals empty; files — by value, absence equals an empty list.
- The writer of the row and the mark is only the installer (and a cluster of one process with a built-in manifest — itself), with
  the right admin: the box process installs the built-in manifest as the installer (the Architect's decision of 2026-10-18, data catalogue).
- The writer writes exactly the fields `yaml`, `sha256`, `rev`, `shell` (if any), `files` (if any) of the row and `rev`, `sha256` of the mark; the reader does not read extra
  fields and does not refuse on them (the current behaviour recorded by review of stage A 2).
- Next to the row the installer writes the canonical view `platform/manifest/<sub>/canonical/<form>` — [chapter 2.2](02.2-installer.norms.md)
  N1.2; the write order is the row, the view, the mark last (window 2.2, the Architect's decision, item 8).
- **Static files** (`console.files`, P/02.1; ADR-0094 addendum (1)) lie next to the manifest in the store, as rows. The field `files`
  of the manifest row names `{<path>: {sha256, size}}`, the bytes are the parts `platform/manifest/<sub>/files/<sha256>/<n>`, `n` from 0.
  A part is up to `FILE_PART` = 262144 bytes of the file in order, the last one shorter; the field `data` is base64 (RFC 4648 § 4, with padding).
  There are exactly `size / FILE_PART` parts rounded up; an empty file has no parts. Ceilings: `FILE_MAX` = 8 MiB (8388608 bytes) per
  file, `FILES_TOTAL_MAX` = 32 MiB (33554432 bytes) per sum of `size` of the list; the bound is included: the files live in the store log. The part size is constant so that one file
  gives the same keys and bytes at any store ceiling and at any implementation. The key carries the digest, not the path: a file with the same
  bytes in a new revision is not rewritten, and the previous revision reads its own parts until the stop.
- The reason for choosing rows: the files and the shell are read by the console from the same store as the manifest, so they survive the
  installer's server, do not depend on the resource and its object door, and are published by the same mark. A file heavier than the row ceiling is a common case
  (a font, a built JS), therefore a file is cut into parts; the rights do not change: `platform/manifest/*` is read by all roles (chapter 2.5
  N1.4), written by `admin`.
- `manifest put` with an unreadable row or mark of this subsystem (the store did not answer, `rev` is not a decimal integer from 1 to
  2^53 − 1, `sha256` is not by the form, `yaml` does not load; analysis of review of stage A 6–7, B3, B4) refuses, writes nothing, code ≠ 0; the row is fixed by the operator (the current behaviour recorded by
  review of stage A 2; checked by reading — there is no scenario).

### Data families (built from the standard files)

The form of the rows and objects that the chapter owns by the [catalog](../../common/data/catalog.tsv) is the JSON Schema 2020-12 of the family (ADR-0092). An instance of a row is `{key, row}`, of an object `{key, object}`; the key is the grammar of the column `key` of the catalog. The fields of `row` are the values of `items` after the [codec](../../common/data/codec.tsv): the writer checks the schema and its `$defs.writer`, the reader the schema (layer 3 — the words `x-*` of the schema). Unreadable — the row did not decode or did not pass the schema in the reader's mode; the outcome is by the table of outcomes of the family: the path is a prefix of the path of the refusal (empty — the whole row); with several paths of refusal the outcome of the least priority applies.

## N3 Procedures

`load` and `load_catalogue` — chapter 2.1 N3.

### Process start

0. Check the store schema — the schema contract «Check at start» (common/contracts/schema.md; added by М10/10; layout audit `A-02`, the Architect's decision of 2026-10-25): as the first step, before step 1.
1. Read the row `platform/manifest/<sub>` and the mark `/rev` (all of them — for processes that need the whole catalogue;
   any other process checks on step 3 a catalogue of its one own manifest: the intersection of the name with its own rows and tables;
   the checks between manifests were made by the installer on the full catalogue, N3 «Manifest change»).
   If there is no row/mark or their read is not confirmed, do not start (code 2).
2. If the sha256 of the yaml bytes is not equal to the recorded one — or, at a process with a built-in manifest, the built-in bytes are not equal to the row —
   do not start.
3. `load(yaml, "platform/manifest/<sub>")` and `load_catalogue`; on a refusal, do not start.
4. Remember the rev of the row; serve. A mark below the row at start (the installer between the writes) is not a refusal: the process serves by the
   row, and compares the mark with its rev only when the mark has become not lower than it (the first equal one has «caught up», without a restart);
   a worker program started by the runner (`w2c-run.sh worker`, `domainworker`, P/02.4 N1.9) compares `W2C_MANIFEST_REV`
   of the environment with the rev of the read row: if they are not equal — exit 0 without work (the restart executes the program of the new rev; ADR-0091 addendum (4), (5); the Architect's decisions on the repeated review 2026-10-23).

**The worker program from the row.** The runner of the cluster worker and of the worker on the domain takes `worker.exec` from the row
`platform/manifest/<sub>` at every start — from the canonical view of the same rev (JSON, chapter 2.2 N3), not by parsing YAML, — with
the checks of steps 1–2 (the row and the mark are read, `sha256`); it passes to the program `W2C_MANIFEST_REV` — the rev of this row.
A change of `worker.exec` is an ordinary manifest change below: the processes of the subsystem stop on the change and at the restart
execute the new program (ADR-0091 addendum (4), (5); the Architect's decisions on the repeated review 2026-10-23).

«Do not start» means to exit with a non-zero code and a log line naming the source and the path. The process MUST NOT serve without the refused subsystem or with the previous manifest.

**Races.** The installer writes the row, then the mark. A process started between them has read the new row (rev 2) and the previous mark (rev 1): it serves by the row and, while the mark is below its rev, does not count it as a change (step 4). When the installer brings the mark to the same number, there is no restart; a change is a mark with a rev different from the remembered one and **not lower** than it. A process that read the old row before the new one was written restarts after reading the new mark. One period of change detection is counted **from the publication of the new mark**, given a successful read of the store. If the installer died after writing the row but before the mark, old processes still see the previous mark, and new ones may start by the new row. Their work on different revisions is not bounded by this period: the mark is brought up by the next `manifest put`, the term of its call is not set (the races of the change below).

### Manifest change

The installer, `manifest put <file>`:

1. `load(bytes, file)`; on a refusal, the file is not put, exit code 2.
2. If the shell (the file `<sub>.shell.html`) has an attribute `on…=` in any tag, refuse: exit code 2, stderr names the file
   and the attribute; before reading the catalogue (P/06.5 N1.1 page; comparison of python and
   go М10/6–11, C31). A tag is markup by the HTML tokenizer; the attribute is one whose name starts with `on`
   and which has a value with the sign `=` (an empty one too; `onclick` without `=` carries no code and is accepted): the text of `<script>` and `<style>`
   and comments are not tags, `data-on=` is not this attribute (C02-SHELL-TAG-01, the Architect's decision of 2026-11-01, analysis of the VMS pass).
3. If `console.shell: true` and there is no file `<sub>.shell.html` next to the manifest or it is empty, refuse: exit code 2, stderr names the file;
   before reading the catalogue (ADR-0094 addendum (3) item 8).
4. Read each path of `console.files` relative to the directory of the manifest file; compute sha256, size.
   1. If the file does not exist, is not a regular file, a link leads outside the directory, or the read
      failed: refuse, exit code 2, stderr names the file and the path; before reading the catalogue (ADR-0094 addendum (1)).
   2. If a file is larger than `FILE_MAX` or the sum of size is larger than `FILES_TOTAL_MAX`: refuse, exit code
      2, stderr names the manifest file, the path or the sum, and the ceiling; before reading the catalogue.
5. Read the full confirmed catalogue; substitute the candidate by its name and run `load_catalogue`; on a read error/refusal: code 2,
   before the first write of the row and the mark.
6. Read the row ceiling of the store: `GET /v1/status` → `max_value` (P/01.3 N2; 524288 is the default of `-max-value`, not
   a constant of the installer). If it did not answer, is not 200 or is without `max_value`: refuse the installation as a whole,
   nothing is written, code 2 (the Architect's decision on question Go P/02 № 4).
7. Build the view (chapter 2.2 N3) for the new row; on `toolarge` of the view: refuse the installation as a whole, nothing is written, code 2;
   stderr names the file, the view key, the weight and the ceiling (window 2.2, item 8).
8. Build the parts of the files (N1.5); if the row of a part is heavier than `max_value`: refuse the installation as a whole, nothing is
   written, code 2; stderr names the file, the part key, the weight and the ceiling.
9. Read the row, the view of the current form and the mark.
10. If the row exists, with the same yaml, shell and files, and the view of the current form exists, reads and equals the projection:
    «unchanged»; bring the parts up (step 15 below); if there is no mark or it is below the row, bring it up (step 18 below); exit 0.
11. If the row is the same but there is no view or it differs: as «the row exists» below (step 14): a row with rev + 1, the view, the mark (chapter 2.2 N1.2).
12. If there is no row: new rev := 1; the condition cas := "" (create while there is no row).
13. If the row exists and the previous rev = 2^53 − 1 (not «unchanged»): refuse before any write: code 2, stderr names the key of the row and the rev
    (the class «not permitted» of N4; the Architect's decision on the guess of Go, 2026-10-20).
14. If the row exists: new rev := the previous rev + 1; the condition cas := the read version of the row.
15. Bring the parts up: for each part of the files read its row; if it is absent, write it with cas ""; if it is unreadable or its data differs, write it with cas
    by the read version; if it is the same, do not write.
    On a conflict: re-read the part and repeat; the manifest row is not yet
    touched: a break here leaves the previous revision whole.
16. Write the row {yaml, shell (if there are pages), files (if the list is not empty), sha256: sha256(yaml), rev: new rev} with this cas.
    On a conflict: re-read and repeat.
    On `toolarge`: stop the installation, code 2; stderr names the file,
    the key `platform/manifest/<sub>`, the weight of the row and the ceiling;
    this call does not change the row and does not go on to writing the mark.
17. Write the view {form, rev: new rev, sha256, manifest} with cas by the read version of the view or "".
    On a conflict: re-read the row and the view; if the rev of the row is mine, repeat the cas of the view;
    if it is another, run the pass anew from reading the row, the view of the previous rev is not written
    (chapter 2.2 N3; C02-VIEW-CAS-RESTART-01); the mark does not move until
    the view is written.
18. Bring the mark up: if there is no mark, write {rev, sha256} of the row with cas ""; if it exists and the rev of the mark < the rev of the row, write with cas by its version.
    On a conflict: re-read the mark and repeat while it is below the row; if it is not below — nothing.
19. Remove the parts: if the mark was brought up by this call and the rev of the re-read row is mine, list `platform/manifest/<sub>/files/` and delete
    the rows of digests outside its files; if the rev is another, do not remove (that installer removes). A refusal or a break of the removal is not a refusal
    of the installation: code 0, the rest is removed by the next call that moves the mark.

A running process, on every pass and not less often than once in 30 s (ADR-0068):

1. Read the mark.
   - If the rev of the mark is ≥ the remembered one and not equal to it, or there is no mark — as a change: stop with code 0; the supervisor starts it
     again. A mark below the remembered one (the installer has not brought it up yet) is not a change: wait.
   - If the mark is not by the form (N1.5: rev is not a decimal integer from 1 to 2^53 − 1, sha256 is not 64 lowercase hex) — as at start: stop with
     a diagnostic (refused, the row name), code 2; a restart refuses until the operator fixes the mark (an admin write
     of the store by the rev of the row, P/01.3; analysis of review of stage A 6–7, B1).
   - If the read is not
     confirmed (the store did not answer) — not a change, continue (the Architect's decision on gap Go P/02 № 1).

Process start: no row/mark, their read is not confirmed, the sha256 is wrong, the manifest/catalogue is refused, the built-in one did not match (a cluster of one process)
→ no start, code 2, without a restart (ADR-0068).

**File races.** The parts are written before the row, so the row never names parts that do not exist yet. A running console of the previous
revision may, after the removal, not find a removed part: it answers 503 (P/06.5 N2 «Статические файлы») until the stop on the change of the mark,
no longer than the detection period. Two installers of one name at once: the loser of the row `cas` re-reads and either sees
«unchanged» or puts its own revision; the removal looks at the re-read row, and a part removed by the race is brought up by the next
`manifest put`.

**The installation source.** The keys that are baked into the units of each server at installation — `parts` (and
`parts.<part name>.exec`, `parts.<part name>.stop_timeout`), `worker.stop_timeout`, `shares` and `worker.uses` (groups and
`ReadWritePaths`), the order `After=` of the parts (P/02.4 N1.1) — are taken from the manifest file in `MANIFEST_DIR` at installation;
they are changed by reinstalling the subsystem on the servers. `manifest put` does not change them: a new row with other values of these keys
takes effect for the units only after a reinstallation. The part runner does not read the manifest row from the store (ADR-0091 addendum (4), (5); the Architect's decisions on the repeated review 2026-10-23).

**Races.** The installation profile admits a simultaneous change of only one manifest name: different names are changed by one operator in sequence. This is a condition of the window, not an atomicity of several rows; with an unconfirmed read of the catalogue no write is made. Two installers of one name at once: the `cas` on the row lets one pass, the second re-reads and either sees «unchanged» or puts its own revision on top; the first creation with `cas: ""` gives rev 1, each following change raises rev by one. The mark only rises: its write is conditioned by `cas` and by the condition «below the row», so a lagging installer (wrote the row rev 2, was delayed, another one managed to put rev 3 and the mark 3) will not lower the mark — its write does not pass. A mark above the row is impossible: it is written after the row and from it. After the installer's death between the row and the mark, the mark stays behind until the next `manifest put` brings it up (including in the branch «unchanged»); there is no automatic bringing-up by this pass, and there is no term for the next call. `manifest status` only shows the divergence (ADR-0068). The term of change detection by running processes begins after the publication of the mark, not after the write of the main row.

## Implementation decides

The command names and argv are fixed by [`forms/operator-commands.tsv`](../forms/operator-commands.tsv); the ceiling of the manifest row is the store's actual `max_value` (chapter 2.2 N3), with no independent installer ceiling. The implementation is to name in its description:

1. **the form of the log line** around the mandatory words `manifest changed, restart` at the stop on a change of the mark (the period not less often than 30 s and code 0 — a norm of N3, ADR-0068);
2. **the form of the log line** at a start refusal (code 2 — a norm of N3, ADR-0068);
3. **the location of the source file and the internal API** implementing `manifest put`, `manifest status` and rights generation (P/02.5 N2; the public commands follow `operator-commands.tsv`);
4. **the internal handling of the store ceiling**: how the installer obtains and carries `max_value` to the row and view weight checks;
5. **the way of storing the built-in manifest** at a process that does not read the store at start (a cluster of one process), and how it compares it with the row.
6. **links in the list `console.files`**: how the installer establishes that a file does not leave the manifest directory (N3).
