The units of `units` stand on every server; names — the platform `w2c`, a subsystem with its own prefix.

<!-- req: P/02.4-R018 -->

Exit 1 — a read not confirmed during `START_WAIT` (chapter 2.3) — is restarted.

<!-- req: P/02.4-R020 -->
`After=configstore.service`, not `Wants`: the store is not pulled in. A long-lived service starts through the runner (`w2c-run.sh`) with umask 0007.

<!-- req: P/02.4-R022 -->
`configstore.service`: `W2C_ROLE=configstore` is for the order of the runner's environment files; the rights file has no such name; there is no `roles/configstore.env` — skipped. `configstore.service`: the sockets come from the units `configstore-*.socket` (P/01.3 N1.3 sockets).

<!-- req: P/02.4-R024 -->
`configstore-admin.socket`, `configstore-<role>.socket`: one unit for admin and for each role of the rights file; `<role group>` — `users_groups`.

<!-- req: P/02.4-R025 -->
`w2c-resource.service` is the role resource; `RESOURCE_HOST`/`PORT` the unit does not write — the default of the process
127.0.0.1:8090 (lifecycle P/05); a variable from `w2c.env` is an explicit address (N1.6 process).

<!-- req: P/02.4-R026 -->
`w2c-controller@.service`: the role `<sub>controller`, the group `w2c-<sub>controller`. `w2c-controller@.service`: `WatchdogSec=360` (SHOULD).

<!-- req: P/02.4-R028 -->
`w2c-console.service` is the role console; `CONSOLE_HOST`/`PORT` the unit does not set — `w2c.env` (install `w2c_env` N1.7).

<!-- req: P/02.4-R029 -->
`<dep>-<sub>worker@.service`: `w2c-secrets` is in `SupplementaryGroups` for the holders of secrets.

<!-- req: P/02.4-R030 -->
`<dep>-<sub>worker@.service`: the instance `%i` is the slot name `<prefix>-<SERVER_NAME>-<n>`: `<prefix>` —
`slot.prefix` of the manifest (P/03.2 N1.4), default `w`; `SERVER_NAME` — N1.2; `n` — an integer without leading zeros. `<dep>-<sub>worker@.service`: `n` 1 is the base one, the installation enables it; 2…99 — on order, they are started by the script of N1.5. `<dep>-<sub>worker@.service`: the part of `%i` between `<prefix>-` and `-<n>` ≠ `SERVER_NAME` — a start refusal, code 2.

<!-- req: P/02.4-R033 -->
`<dep>-<sub>worker@.service`: `ExecStart=` — `w2c-run.sh worker <sub> %i` (N1.9): the runner reads the environment by N1.2 and executes
`worker.exec` from the manifest row (P/02.3 N3 «Worker program from the row») with the last
argument — the slot name, `W2C_MANIFEST_REV` — the rev of this row. `<dep>-<sub>worker@.service`: the exec line does not get into the unit; on the stand — the command of the implementation profile with the substitution `{name}` (the common acceptance README).

<!-- req: P/02.4-R035 -->
`<dep>-<sub>worker@.service`: an environment variable with the name the unit sets only if
the manifest declared `slot.name_env` — that one, and with the same `%i`.

<!-- req: P/02.4-R036 -->
`<dep>-<sub>worker@.service`: the groups of the shares `worker.uses` — `SupplementaryGroups` += the group of each share
`<A>.<share>` declared in `shares` of the subsystem A of the catalogue (a share of a part — the group of the part's user,
otherwise `<dep>-<A>-<share>`; its own share — only with `part`, the group of the part). `<dep>-<sub>worker@.service`: A is not in the catalogue — there is no group.

<!-- req: P/02.4-R038 -->
`<dep>-<sub>worker@.service`: `ReadWritePaths` — its own state directory `/data/platform/subsystems/<sub>` and

<!-- req: P/02.4-R041 -->
`<dep>-<sub>worker@.service`: for a subsystem with parts — `After=` of the unit of each of its parts, without `Wants` and `Requires`: a restart of the worker

### N1.5 Workers on demand

<!-- req: P/02.4-R103 -->
```yaml
order:        <sub>/want/<host>; want 1…99; <sub>_workers_wanted{server}
extra_unit:   <dep>-<sub>worker@<prefix>-<SERVER_NAME>-<n>, n 2…99
script:       w2c-workers.sh; the timer, once a minute; User=w2c-workers
  polkit:     start, stop; User w2c-workers; <dep>-<sub>worker@<prefix>-<SERVER_NAME>-<n>.service, n [2-9]|[1-9][0-9]
rules:        1–6
stop:         systemctl stop
memory:       CAPACITY, unit_mb, base_mb, WORKER_MEMORY_MB; GOMEMLIMIT
```

<!-- req: P/02.4-R104 -->
`order`: the number of processes of a role on a server is set by the controller — the row `<sub>/want/<host>` (P/04 N1.1). `order`: `want` — the absolute target 1…99, the base `<prefix>-<SERVER_NAME>-1` is included in it.

<!-- req: P/02.4-R106 -->
`order`: the console gives the series `<sub>_workers_wanted{server}` for each order row (P/06.5 N3 «/metrics — text»).

<!-- req: P/02.4-R107 -->
`extra_unit`: an additional worker — an instance of the same role unit `<dep>-<sub>worker@<prefix>-<SERVER_NAME>-<n>`, n 2…99
(N1.1): the same credentials, keys, user and groups; the slot capture is ordinary (P/03.2 N3). `extra_unit`: there is no special unit, file or variable for an additional worker.

<!-- req: P/02.4-R109 -->
`script`: `w2c-workers.sh`, once a minute by the timer, `User=w2c-workers` without groups; one per server — all roles of the server.

<!-- req: P/02.4-R110 -->
`script` `polkit`: only start and stop, only by the user `w2c-workers`, only the full names
`<dep>-<sub>worker@<prefix>-<SERVER_NAME>-<n>.service` of the roles of this server, n — `[2-9]|[1-9][0-9]` without leading
zeros. `script` `polkit`: the base -1, a foreign server, other units and verbs — a refusal.

<!-- req: P/02.4-R113 -->
`rules` 1: the script reads its own series `<sub>_workers_wanted{server=<SERVER_NAME>}` of all roles of the server from `/metrics` of the console, the series of other
servers it does not read, it executes no commands. `rules` 1: the console URL — `own_url` of the role certificate contract (`CONSOLE_HOST`,
`CONSOLE_PORT` of `w2c.env`; https with `ca.pem` in `W2C_TLS_DIR`, otherwise http). `rules` 1: the server check — the client of its own cluster
`own_client` of the same contract, the role console (N1.6 roles).

<!-- req: P/02.4-R115 -->
`rules` 2: there is no series of the role, it is not readable, the console is silent or the series
`<sub>_reconcile_last_success_age_seconds` (P/06.5 N3 «/metrics — text») is greater than 60 or −1 → for this role start nothing
and stop nothing: silence is not a reason. `rules` 2: a series is not readable when its value is not in the form of the metric of P/06.5 N3 — an integer without leading zeros, sign and fraction: `02`,
`2.0`, `+2` — there is no series — or outside 1…99. `rules` 2: a line not in the text format — skipped with
a diagnostic, the other series of the pass are counted (P/01.1 N0 «Stability of output»). `rules` 2: the console is silent — the collection of `/metrics`
failed, the last successful collection is older than a minute by the local monotonic clock of the script.

<!-- req: P/02.4-R119 -->
`rules` 3: the target of the role is exactly the numbers {2…want}: start the missing ones of this set (the smallest first), stop the running ones with a number
greater than want (the greatest first). `rules` 3: a number is compared as an integer, not by the order of lines. `rules` 3: the base -1 the script does not touch.

<!-- req: P/02.4-R126 -->
`rules` 4: before a start — memory: the ceiling = floor(`HOST_MEMORY_MB` / `WORKER_MEMORY_MB`) from `roles/<role>.env` (parsing, not source;
no file — the role is skipped). `rules` 4: both budgets are positive integers, `CAPACITY` is an integer > 0; a value not in form or
a zero divisor → skip the role with a diagnostic. `rules` 4: `unit_mb` and `base_mb` the script does not
read — they are the input of the worker start (`memory` below, P/03.4 N1.2). `rules` 4: the ceiling is the number of processes of the role on the server, each with `WORKER_MEMORY_MB`: the running ones, the base -1 and
the reserved starts are counted. `rules` 4: the common memory ceiling of the server over all roles is not
divided — a limit of the scheme.

<!-- req: P/02.4-R127 -->
`rules` 5: passes are serialised. `rules` 5: a number is reserved until start; an uncertain outcome of start or stop stays occupied until the reconciliation with
systemd. `rules` 5: a second pass with the same target starts no new ones and stops no extra ones.

<!-- req: P/02.4-R130 -->
`rules` 6: exactly one mechanism executes the series on an installation: the timer or the hand; on the stand — the directive `@grow` (the common acceptance README).

<!-- req: P/02.4-R132 -->
`stop`: stopping — `systemctl stop`: the worker gives up the slot regularly (P/03.4 N3 «stop by SIGTERM»); for a worker with a non-empty
assignment this is a move of units, not a loss. `stop`: the controller decreases want after an empty
assignment of the worker being shrunk (P/04 N3 «shrink()») or by removing the order by the deadline `WANT_GRACE` (P/04 N3
«withdraw by deadline»): then the script stops a number above want even with a non-empty assignment —
the units move.

<!-- req: P/02.4-R133 -->
`memory`: the worker does not start if `CAPACITY × unit_mb + base_mb > WORKER_MEMORY_MB`. `memory`: `GOMEMLIMIT = WORKER_MEMORY_MB`.

### N1.7 Upgrade and installation

<!-- req: P/02.4-R178 -->
```yaml

  os:         Linux/systemd: install apply; macOS: the build, unit tests, launchd artefacts

  warn:       RESOURCE_URL; SERVER_NAME; unconfirmed; DOMAIN_SERVER=no; placement.near.sub; name resolution
  refuse:     /etc/w2c, /etc/<sub>; W2C_DEPLOYMENT; CONSOLE_ROOT; DOMAIN_SERVER; TIMEZONE; a cycle; the rights candidate; OS names
  steps:      the code → the runner and the scripts → users and groups → /data and links → manifests → environment and role files

```

<!-- req: P/02.4-R179 -->
`upgrade`: server after server.

<!-- req: P/02.4-R180 -->
`upgrade` 1: `POST /drain?server=<s>`; wait for `GET /drain` `safe: true` (P/06.6 N2.3, N1.2). `upgrade` 1: units without another place (a strict home, a cluster of one) will not give `safe`: the operator accepts the downtime explicitly, by `would_strand`, there is no deadline.

<!-- req: P/02.4-R182 -->
`upgrade` 2: confirm quiescence by P/06.6 N3 «drain — reading the state», stop the server, update, start; `DELETE /drain`;
enough healthy assignments; do not wait for the return home.

<!-- req: P/02.4-R183 -->
`upgrade` 3: the next server.

<!-- req: P/02.4-R184 -->
`upgrade` 3a: all servers are updated — the manifest of the new revision: `w2cctl manifest put`. `upgrade` 3a: not earlier: all see the mark, an unknown key is a start refusal of the old build (P/02.3, P/02.1); the new build works on the former manifest.

<!-- req: P/02.4-R186 -->
`upgrade` 4: last — `PUT /schema?version=N` by P/06.6 N3 «raise_schema»: current request, `SCHEMA`, heartbeat and confirmed-read guards, then CAS; it does not go back.

<!-- req: P/02.4-R187 -->
`upgrade` `rule`: a new build works on the old layout. `upgrade` `rule`: an old build on the new layout does not start (visibly).

<!-- req: P/02.4-R190 -->
`add`: a subsystem on a running cluster, the manifest is not from the deployment package. `add` `why`: the store rights and the console catalogue are taken only at the start of the process (P/01.2 N1.2: a new rights file — a restart of the daemon;
P/06.5 N2: the console serves the catalogue of its start). `add` `why`: therefore adding is done by restarts one server at a time; there is no live
rereading.

<!-- req: P/02.4-R192 -->
`add` 0: before the rollout — `manifest put` of all manifests changed by the step for the sake of which the rollout is made (for VMS — the assembly of V/12.4 N1.3: the new
subsystem, dependents, owners, backend). `add` 0: each put outputs the sha256 of the row — these are the hashes of the rollout. `add` 0: then wait until the console of each server serves the new revisions of the already running manifests of the rollout (backend, dependents,
owners): they are picked up by the mark without a rollout (P/02.3 N3 «Manifest change»), the console barrier of `rollout` checks exactly this. `add` 0: `served` of the new subsystem — usually after the rollout (it is not in the start catalogue of the consoles); by the mark
of a backend whose calls name it — also earlier (N1.9 `rollout` `barrier`).

<!-- req: P/02.4-R196 -->
`add` 1: the rollout — `w2cctl rollout <sub>=<sha256>…` (N1.9) on each server in turn, the server of the leader member — last. `add` 1: code 0 — the step
of the server is done, otherwise the rollout stands: the cluster works on the former rights and catalogue, the new subsystem is not enabled.

<!-- req: P/02.4-R198 -->
`add` 2: after all servers: `install` without `W2C_HOLD` on each — a repeat = an update: the files, rights and rows are the same, the step enable enables
the units of the subsystems of the rollout. `add` 2: until then none of the processes of the subsystems of the rollout starts, so none meets a member without its rights.

<!-- req: P/02.4-R200 -->
`add` `resume`: a repeat of the rollout — the same commands with the same hashes from the first server: `rollout` on a passed server finds the barrier
fulfilled and exits 0 without restarts (N1.9 `rollout` `done`).

<!-- req: P/02.4-R201 -->
`add` `others`: the controllers and workers of other subsystems are not restarted.

<!-- req: P/02.4-R202 -->
`add` `others`: the console of a server is unavailable for the time of its restart, the quorum
is intact because one at a time.

<!-- req: P/02.4-R203 -->
`add` `others`: the workers of the server go to their member — its restart longer than `LOST_AFTER` (45 s) re-places
their units by the common rules (P/04), this is a limit of the rollout.

<!-- req: P/02.4-R204 -->
`add` `others`: while the rollout goes, the processes on the servers not yet passed live with the
old rights — transient refusals of new reads there are a limit.

<!-- req: P/02.4-R205 -->
`add` `others`: a backend with calls of a new plugin earlier than the consoles serve it —
transient 404 and 401 — a limit.

<!-- req: P/02.4-R206 -->
`install`: `install.sh`; a repeat of the installation = an update.

<!-- req: P/02.4-R207 -->
`install` `os`: the release OS: Linux/systemd — install apply is required; macOS — the build, unit tests and launchd artefacts are required
(plist with `ExitTimeOut` and so on, N1.1). `install` `os`: a native application on macOS MAY exist, without it — a refusal with code 2 before
writing. `install` `os`: the system host of the stand is not touched.

<!-- req: P/02.4-R210 -->
`install` `w2c_env`: the installation writes into `w2c.env` `CONSOLE_HOST` and `CONSOLE_PORT` (default 127.0.0.1, 8080) — one console address
that all processes of the box read (the URL of its own console — `own_url` of the role certificate contract). `install` `w2c_env`: the console unit does not set `CONSOLE_HOST` and `CONSOLE_PORT`.

<!-- req: P/02.4-R212 -->
`install` `w2c_env`: `CONSOLE_CALL_PORT` (default 8081) — the port of the callback listener, a value not in form — an installation refusal (`refuse` below).

<!-- req: P/02.4-R213 -->
`install` `w2c_env`: `TIMEZONE` (a value of the installer's environment, default UTC) — a cluster setting that `GET /session` gives (the contract of the environment
file «Environment variables»). `install` `w2c_env`: a `TIMEZONE` value not in form — an installation refusal (`refuse` below), the console start

### N1.9 Operator commands

**Command options**

<!-- req: P/02.4-R271 -->
The normative option table is [`forms/daemon-flags.tsv`](../forms/daemon-flags.tsv); command ids, executable names, fixed argv prefixes and positional arity are [`forms/operator-commands.tsv`](../forms/operator-commands.tsv). Despite the shared file name, P/02 defines operator arguments and has no daemon flags. The table is not repeated here; the procedures below explain effects and their owner norms. A command of `operator-commands.tsv` whose options are out of this form — an option outside the table or of another command, a repeated option, a `bool` with a value, an option without its value, a value out of its `type`, an unmet `required` or a true `bad` — MUST refuse with `command_options` of the [refusal catalogue](../forms/refusals.tsv): code 2, before any effect (nothing is written to the store, no file is created or changed), and its log line on stderr names the option. The command MUST parse its options before every other check: the refusal `command_options` comes before the check of rights and before any access to the store or to files, so a command line with a wrong option and another fault (for example, absent rights) ends with code 2 `command_options`, not with the refusal of that other check.

<!-- req: P/02.4-R273 -->
The delegated command grammars stay with their owners: configstore admin_ops — [P/01.3 N1.3](../../01-store/spec/01.3-store.norms.md), `w2cctl domain move` — [P/08.8 N1.8](../../08-domain/spec/08.8-domain.norms.md); `install.sh` follows N1.7 above.

<!-- req: P/02.4-R274 -->
`w2cctl mirror on|off` changes only `enabled`; `w2cctl space -off` changes only its `enabled` to false. Each command reads its row and writes with CAS of that version (an absent row — CAS ""); on a conflict it re-reads and repeats. All other fields of an existing readable row stay as read, including their absence: a missing `copies` is not replaced by its reading default. If the row is absent, use the defaults of its owner (P/02.4-R277) for the other fields. An unconfirmed read, an unreadable row or an invalid `copies` refuses with code 2 before a write; stderr names the row key and the cause (the catalogue refusal `setting_read_refused`). The rows written by `mirror`, `space` and `retention` have the form of «Data families» below:

<!-- req: P/02.4-R275 -->
```yaml
platform/space:          {enabled: true | false, high: 0.85, low: 0.75}   # fractions; w2cctl space -high -low | -off
platform/mirror:         {enabled, copies}                                 # w2cctl mirror on|off; copies — an integer ≥ 0
<sub>/retention:         {days}                                            # w2cctl retention <sub> -days N
<sub>/alarms_retention:  {days}                                            # w2cctl retention <sub> -alarms N
```

<!-- req: P/02.4-R276 -->
The only writer of the rows `platform/space`, `platform/mirror`, `<sub>/retention`, `<sub>/alarms_retention` is admin, the resource and the console
only read them; the owner of a row is the writer process.

<!-- req: P/02.4-R277 -->
The meaning of these rows and the defaults on reading — [P/05](../../05-resource/spec/05-resource.norms.md) N1.3 `retention`, N1.4
`space`, `mirror`.

#### N1.9 The command `w2cctl manifest get`

<!-- req: P/02.4-R278 -->
Carrying the manifest files over to the other servers — both of the new subsystem and of the changed
manifests of those already standing (backend, dependents, owners): on the server they have the former file from the package (the order `add` of N1.7, the
rollout step `get`).

<!-- req: P/02.4-R279 -->
```yaml
get:       w2cctl manifest get <sub> --sha256 <hash>; admin.sock; platform/manifest/<sub>
write:     MANIFEST_DIR: <sub>.subsystem.yaml, <sub>.shell.html, the files of files
check:     sha256(yaml), sha256 and size of each file; code 2
replace:   files and shell, yaml last; <sub>.shell.html.old
untouched: the files of MANIFEST_DIR that the row does not name
not:       the row, the mark, rights, units
```

<!-- req: P/02.4-R280 -->
`get`: `w2cctl manifest get <sub> --sha256 <hash>` — `admin.sock` of its own server; reads the row `platform/manifest/<sub>` (the form — chapter
2.3 N1.5). `get`: `<hash>` — the one that manifest put of the first server output: a check of the row against itself proves nothing.

<!-- req: P/02.4-R282 -->
`write`: into `MANIFEST_DIR`: `<sub>.subsystem.yaml` — the bytes of `yaml` of the row; `<sub>.shell.html` — the bytes of `shell`, if any (a row without `shell` — the quarantine of the former shell, below). `write`: the files of `files` — each
path from the parts `platform/manifest/<sub>/files/<sha256>/<n>` (the parts by n from 0, glued together), under its own path next to the manifest.

<!-- req: P/02.4-R286 -->
`check`: all files that the row names are written into temporary names next to the target. `check`: sha256(yaml) and the sha256 of the row equal `<hash>`,
sha256 and size of each file — the records of `files`. `check`: a mismatch, no row, an unreadable row or part, a write error — a refusal,
code 2, the temporary ones are removed, the former files are intact.

<!-- req: P/02.4-R287 -->
`replace`: after all checks — the replacement of the former files named by the row, each by its own atomic rename of the temporary one over
the target: first `files` and `shell`, `yaml` last. `replace`: a row without `shell` (no field or empty, chapter 2.3 N1.5): in place of the replacement
of the shell the former `<sub>.shell.html`, if any, is moved by an atomic rename into quarantine — `<sub>.shell.html.old` next to it
(a former `.old` is replaced), a name that manifest put and install do not read: otherwise the next put would read the former shell
and bring the page back into a revision without it (chapter 2.3 N3 «Manifest change» item 3). `replace`: an interruption between the files leaves part of the new ones with the former `yaml`. `replace`: a repeat of get with the
same hash converges: a file already equal to the bytes of the row is not touched, the others are replaced, a former shell left
at a row without `shell` goes into quarantine, `yaml` again last. `replace`: the operator's
hash is the protection: a former file is replaced only by the bytes that the operator named.

<!-- req: P/02.4-R292 -->
`untouched`: the files of `MANIFEST_DIR` that the row does not name, get does not touch, except the former shell above: its name is implicit,
put reads `<sub>.shell.html` without a declaration. `untouched`: on a refusal of get (`check` above) nothing moves, the former shell included. `untouched`: a file of `files` of a former revision that the new one removes
stays in place, is not brought back and means nothing: install and manifest put read only the paths of `files` of their own manifest (N1.7 `files`;
chapter 2.3 N3 «Manifest change»); the operator removes it if he wishes.

<!-- req: P/02.4-R295 -->
`not`: get does not change the row and does not move the mark; rights and units are the business of install.

#### N1.9 The command `w2cctl rollout`

<!-- req: P/02.4-R296 -->
The rollout step of one server (the order `add` of N1.7). The operator runs it on each server in turn.

<!-- req: P/02.4-R297 -->
```yaml
rollout:   w2cctl rollout <sub>=<sha256>… [-allow-downtime] [-last]
mode:      GET /v1/status of admin.sock: Leader | Follower — a voter; Door — a door without a vote
done:      «already done», code 0
pre:       quorum — ⌊voters / 2⌋ + 1; live ≥ quorum + 1; ROLLOUT_WAIT
  leader:  -last
poll:      Platform/02-installer/forms/rollout-poll.machine.yaml
  why:     the rationale
  other_order: another order of reads
  bound:   the bounds of the poll
steps:     1 manifest get; 2 install with W2C_HOLD; 3 rights; 4 the console
barrier:   the store; the console
  limit:   operator limits
  console: CONSOLE_HOST, CONSOLE_PORT; W2C_TOKEN
  wait:    ROLLOUT_WAIT; once per 1 s
ROLLOUT_WAIT: 300 s
failure:   a non-zero code with the name of the step
not:       units, store rows
unproven:  the bounds of the model
```

<!-- req: P/02.4-R298 -->
`rollout`: `w2cctl rollout <sub>=<sha256>… [-allow-downtime] [-last]` — all manifests of the rollout, each with its own hash (N1.7 `add` step 0). `rollout`: `<sub>` by the grammar of P/02.1 name, `<sha256>` — 64 lowercase hex, a repeat of `<sub>` — a refusal, code 2, before any actions.

<!-- req: P/02.4-R300 -->
`mode`: by the own member — `GET /v1/status` of `admin.sock` (P/01.3 N2): state Leader or Follower — a voter; Door — a door without a vote
(P/01.3 N1.3 door); anything else — a refusal, code 2.

<!-- req: P/02.4-R301 -->
`done`: step 1 (get of all manifests of the rollout) and the console check always run, also on a passed server: otherwise a server with an old manifest
file in `MANIFEST_DIR` (a backend whose calls alone changed — the rights are the same) would bring back with the next install the former
bytes. `done`: the barrier (below, of the store and of the console) is judged always, also at «already done». `done`: after get the rights are equal and the barrier is fulfilled —
the output «already done», code 0, neither the member nor the console is restarted. `done`: the rights are equal but the barrier is not fulfilled (the member lags, there is no
leader) — wait for the barrier, as after a restart, code 0 only by it; this way a repeat of the rollout finds the first server not yet passed.

<!-- req: P/02.4-R305 -->
`pre`: a voter — before the actions and once more before the restart of the member: a poll (`poll` below); the pass — the first batch where the live ones are
≥ quorum + 1 (quorum — ⌊voters / 2⌋ + 1). `pre`: no pass by the deadline `ROLLOUT_WAIT` — a refusal, code 2, «not enough live voters», a refusal only by the
deadline: with three voters and one of them dead a restart of one would lose the quorum.

<!-- req: P/02.4-R307 -->
`pre`: at most two voters —
only with `-allow-downtime`, the cluster is unavailable for the time of the member restart (with two the quorum 2 of 2 is lost), and there is no poll. `pre`: two voters without the flag — the refusal by the deadline above, a named bound.

<!-- req: P/02.4-R309 -->
`pre`: the number of voters
and the flag are judged before the choice between `pre` and the `-last` check (`leader` below), also at the leader. `pre`: two voters with `-last` and
without `-allow-downtime` — the count of `pre`, not of `-last`, so the poll never passes: the refusal by the deadline, «not enough live voters».

<!-- req: P/02.4-R311 -->
`pre`: two voters with the flag — no poll, also with `-last`.

<!-- req: P/02.4-R312 -->
`pre`: one voter is judged before the machine (its input has ≥ 2 voters): with
`-allow-downtime` there is no poll; without the flag — a refusal at once, code 2, «not enough live voters», before the actions.

<!-- req: P/02.4-R313 -->
`pre`: with three voters
and more `-allow-downtime` changes nothing.

<!-- req: P/02.4-R314 -->
`pre`: a door is not counted among the voters, its restart does not touch the quorum: a door has no `pre`.

<!-- req: P/02.4-R315 -->
`pre` `leader`: the own member is the leader, there is more than one voter — only with `-last`: the operator confirms that the other servers are passed — the rights
of the other members are not visible from the leader's server, `admin.sock` is not forwarded. `pre` `leader`: what is visible, the command checks itself: with `-last` and ≥ 3 voters both `pre`
are replaced by the `-last` check (before the actions and before the restart of the own member); its pass — the first batch where each other voter is live, not
quorum + 1. `pre` `leader`: no pass of the `-last` check by the deadline `ROLLOUT_WAIT` — a refusal, code 2, «-last: voters not live».

<!-- req: P/02.4-R318 -->
`pre` `leader`: the leadership of the own
member is judged at `mode` and in each batch of each poll, the refusal is at once, not by the deadline.

<!-- req: P/02.4-R319 -->
`pre` `leader`: with `-last` the own member is not
Leader or its `leader_id` is not its own id — code 2, «-last: not the leader».

<!-- req: P/02.4-R320 -->
`pre` `leader`: without `-last` the own member is Leader, more than one voter — code 2, «leader goes last».

<!-- req: P/02.4-R321 -->
`poll`: the norm of the poll is the machine [`rollout-poll.machine.yaml`](../forms/rollout-poll.machine.yaml): the poll
(`pre` before the actions, `pre` before the member restart, the `-last` check — each anew, with its own targets), the status batches
by the clock, the answer of the own member (the leader of the batch by `leader_id`, the membership check by it and by the answer of the leader of the batch — «voters changed», the leadership — «-last: not the leader»,
«leader goes last»), the live answer, the target and its read, the break, the judgement of a batch, the deadline `ROLLOUT_WAIT`, the timers and the order of the events
of one instant (env) — there. `poll`: where the prose and the machine differ,
the machine holds; the prose gives only the rationale (`why`), another order (`other_order`), the bounds (`bound`) and the unproven (`unproven`).

<!-- req: P/02.4-R324 -->
`poll`: the voters — `voters` of the status of the own member at `mode`, the addresses — `members` of the same answer. `poll`: a voter
absent from `members` (no `-api`) is not asked: it gives no answer, the next batch puts its break, as for any read without an answer (`send_status`). `poll`: a live answer
is compared with the answer of the own member by `leader_id`, the address `leader` is needed only for the target read.

<!-- req: P/02.4-R327 -->
`poll`: a repeat of `rollout` starts with
a new `mode` and a new membership, a repeat of the rollout finds the first server not yet passed (`barrier`).

<!-- req: P/02.4-R330 -->
`poll` `why`: an HTTP answer does not mean «in the group»: a member with a closed `-raft` port answers but receives no log — a live answer requires
state Leader or Follower and the same `leader_id`. `poll` `why`: the target is the commit read after the live
answer: a voter that was down at the read would otherwise be counted by the old one. `poll` `why`: without a break the target does not
move: otherwise a healthy cluster under continuous writing would refuse by the deadline. `poll` `why`: a break removes the target: otherwise one that fell in the middle of the poll and rose lagging would be counted by the old one.

<!-- req: P/02.4-R332 -->
`poll` `why`: batches by the clock, the deadline of a read — until the next batch, the target read is separate and does not delay the batch: so two
observations of a voter are no further than 2 s apart. `poll` `why`: the count is by the answers of one batch: a counted one is also
polled, otherwise its break is not seen. `poll` `why`: the membership is checked by every received answer of the own member, also without
leader: otherwise a join or a leave in the middle of the poll would give a restart without a quorum; and the answer of the leader of the batch: the own member as a follower may apply a join later than the leader.

<!-- req: P/02.4-R335 -->
`poll` `other_order`: another order of reads is admissible if the target of each voter is not below the commit read after the first live answer
of the voter after its last break (or after the start of the poll), and without a break the target does not move in the poll. `poll` `other_order`: the order of such
a poll the implementation names explicitly («Implementation decides»).

<!-- req: P/02.4-R337 -->
`poll` `bound`: the bounds of the poll below are named; there is no rule for them. `poll` `bound`: a voter cut off from the group after the last read of its status, or less
than an election timeout before it, shows the former state and `leader_id` — the same as one that fell after the check; a cut-off shorter than 2 s plus the election timeout the poll may not see. `poll` `bound`: the observation bound of a crash —
two observations of one voter (the instants of the answers of neighbouring batches) are separated by no more than 2 s, a crash and rise shorter than 2 s
the poll may not see. `poll` `bound`: a restart of a member by `RestartSec=2` keeps it down for 2 s plus the start time and falls into at least
one batch.

<!-- req: P/02.4-R341 -->
`poll` `bound`: `voters` and `members` of the own member may lag behind the leader until the own member
has applied a membership change, so the answer of the leader of the batch checks the membership too. `poll` `bound`: a change of the membership after the answers of the own member and of the leader in the passing batch.

<!-- req: P/02.4-R343 -->
`steps` 1: `manifest get <sub> --sha256 <hash>` for each (above).

<!-- req: P/02.4-R344 -->
`steps` 2: install with `W2C_HOLD` — the names of all `<sub>` of the rollout whose units on the
server are not enabled (the new subsystems of the rollout; also on a repeat of `rollout`, when the units are already installed disabled: otherwise the repeat
would enable them before the end of the rollout; N1.7 `w2c_env`).

<!-- req: P/02.4-R345 -->
`steps` 3: rights: `GET /v1/rights` of the own member by meaning
equals the file assembled from `MANIFEST_DIR` (the same comparison as `rights --check`, P/02.5 N3 «install») — do not
restart the member. `steps` 3: otherwise `pre` once more and a restart of the member configstore (a restart by `member.json`, not join; N3 «server start» step
1). `steps` 3: in both cases — the store barrier.

<!-- req: P/02.4-R348 -->
`steps` 4: the console: for each `<sub>` of the rollout `/manifest/<sub>/source` answers — the console serves them and will pick up the new revision by the mark
itself (P/02.3 N3 «Manifest change»), wait for the console barrier. `steps` 4: if even one is 404 (the subsystem is not in the start catalogue) — a restart
of the console of this server, then the console barrier. `steps` 4: a plugin switch that changes at the running subsystems only
`door.pass.calls` (P/02.5 N1.5, not the prefixes of the rights file of N1.4) usually ends without restarts.

<!-- req: P/02.4-R351 -->
`barrier`: the store — a voter: `GET /v1/rights` of the own member ≡ the file of the rollout (as step 3), its `leader_id` equals `leader_id` from `GET
/v1/status` of the leader (the address `leader` of its own status), its `applied` ≥ `commit` of the leader read after step 3 (after the restart,
if there was one).

<!-- req: P/02.4-R352 -->
`barrier`: the store — a door: `GET /v1/rights` ≡ the file of the rollout and the read of the mark row `platform/manifest/<sub>/rev` of the first `<sub>` of the rollout through
the role socket console of its own door — 200: forwarding to the group works. `barrier`: `applied` of a door is always 0 and is not compared.

<!-- req: P/02.4-R354 -->
`barrier`: the console — `GET /manifest/<sub>/source` of its own console (P/06.5 N2) for each `<sub>`
of the rollout: `source.sha256` equals the hash of the rollout and `source.served` equals rev of the row `platform/manifest/<sub>` of the store (rollout reads it
through `admin.sock` of its own member). `barrier`: the equality of `served` and `rev` inside one answer of `/source` is not checked — in it they are
always equal (P/06.5 N2 «served = rev»). `barrier`: `served` of a new subsystem can come also before the rollout of this server — by the mark of a backend whose calls name it: admissible,
this does not cancel the console barrier.

<!-- req: P/02.4-R357 -->
`barrier`: the store and the console have no new fields.

<!-- req: P/02.4-R358 -->
`barrier` `limit`: two rollouts at once — on one server or on different ones — an operator limit: the command does not judge it, the order «one at a time»
is held by the operator. `barrier` `limit`: the store membership (join, leave, admit; P/01.3 N1.3) is not changed during rollout — also
an operator limit, the command does not judge it, except the membership check in each batch (`poll`).

<!-- req: P/02.4-R360 -->
`barrier` `console`: a request to its own console — `CONSOLE_HOST` and `CONSOLE_PORT` of `w2c.env` (N1.7 `w2c_env`). `barrier` `console`: a console without a domain is open from the loopback (P/06.3
N1.3 open); with a domain — an administrator token on "*" from the environment value `W2C_TOKEN`.

<!-- req: P/02.4-R362 -->
`barrier` `wait`: the barrier waits no longer than `ROLLOUT_WAIT`, polling once per 1 s. `barrier` `wait`: not reached — code 2, the output names the unfulfilled part of the barrier
(`leader_id`, `applied`, rights, the read through the door, sha256 or served `<sub>`); the rollout stands, the operator does not touch the next server.

<!-- req: P/02.4-R364 -->
`failure`: any step — a non-zero code with the name of the step, without a rollback. `failure`: a repeat with the same command is harmless: get with the same files — 0, install
as a repeat — an update, the restart and the barrier — again.

<!-- req: P/02.4-R366 -->
`not`: rollout does not enable the units of the subsystems of the rollout (N1.7 `add` step 2), writes no store rows.

<!-- req: P/02.4-R367 -->
`unproven`: what the model of the rollout did not prove is accepted as a bound: the barrier «always» is checked only by the simulator, the exhaustive check
does not get through; the target of the poll exhaustively — one configuration and one judge,
the rest — by the simulator; the `-last` part is not checked by the model (its mutant is not caught);
a repeat of the rollout and the second server; a fall of a voter in the middle of the poll and a hanging status read are an external
event, the judge of the target of the poll does not judge it. Not proven either: the safety and the order of the poll in every configuration,
two mutants of the poll are not caught; `-allow-downtime` with one voter; the link of the two `pre` with the barrier;
a hanging `admin.sock` as a separate kind; a write without a quorum by a cut-off leader. `unproven`: the order of the rollout in an implementation is judged by no automatic run: P/02.4-22
«not run by an implementation», sc. 09 of the system acceptance — @manual.

#### N1.9 The commands `w2cctl secrets`

<!-- req: P/02.4-R369 -->
The envelope, the ring and AAD — the [sealing contract](../../common/contracts/sealing.md).

<!-- req: P/02.4-R370 -->
```
w2cctl secrets new [<path>]
w2cctl secrets seal [<prefix>…]
w2cctl secrets rotate [<path>]
w2cctl secrets status [<prefix>…]
```

<!-- req: P/02.4-R371 -->
`new` — create the ring (O_EXCL, 0640); a path inside the store — a refusal.

<!-- req: P/02.4-R372 -->
`seal` — seal/reseal the open and old ones by `cas` (the outcomes of a value — the sealing contract «Reseal a value»); code 1 if something is left.

<!-- req: P/02.4-R373 -->
`rotate` — a new key on top.

<!-- req: P/02.4-R374 -->
`status` — clear / current / older / ?; code 1 if there is an open one while a readable ring exists, or ? > 0. An unset `SECRETS_KEY` is the mode without a key, with the diagnostic reason “key not set”; a set but empty or unreadable ring is not this mode (P/02.4-R402).

<!-- req: P/02.4-R375 -->
The prefixes of `seal` and `status`, their default D and the rows walked — «Walk» below. `status` and `seal` walk `*_secret` at any depth, including inside the value of a json field.

<!-- req: P/02.4-R377 -->
An envelope counts as
`current` or `older` only if it opens with the key of its kid with the AAD of its place (the sealing contract). A known kid that does not
open (the envelope is moved to a foreign place, spoiled) is `?`, like a foreign kid.

<!-- req: P/02.4-R379 -->
`seal` on an envelope that does not open does not break off the walk: it brings it to the end and answers with code 1 — something is left.

<!-- req: P/02.4-R380 -->
An empty value of `*_secret` is not counted. A non-string value of `*_secret` (a number, an object, an array, a bool) is counted as `?`. `status` with `?` > 0
— code 1, like `seal` with remaining `?`; the walk continues, there are no values in the output.

<!-- req: P/02.4-R383 -->
**Walk.** This one rule names the rows that `status` and `seal` walk; the Data list of N1, the command list above and the rows
14–16 of chapter 2.4 in [`refusals.tsv`](../forms/refusals.tsv) refer to it; the families are the `row` families of the
[data catalogue](../../common/data/catalog.tsv):

<!-- req: P/02.4-R384 -->
```yaml
prefixes:  P — argv; D — domain/, identity/, <sub>/<manifest:unit.rows>/<id>, <sub>/<manifest:tables>/<name>
selected:  the rows of the store under P
kept:      domain/<sub>/<manifest:domain.kept>[/…]
walked:    door/signer, domain/signer, domain/signer-pending, domain/book-seal, domain/member-key, domain/users/<name>,
           domain/break-glass/<cluster>, <sub>/<manifest:unit.rows>/<id>, <sub>/<manifest:tables>/<name>
other:     domain/keys, domain/root, door/keys, …
join:      domain/join
unknown:   identity/x, domain/<unknown name>, <sub>/<unknown name>
```

<!-- req: P/02.4-R386 -->
`prefixes`: P — the prefixes given in argv, each a plain prefix of the row key. `prefixes`: none given — the default D: the rows under `domain/`, the
rows under `identity/`, and the rows of the families `<sub>/<manifest:unit.rows>/<id>` and `<sub>/<manifest:tables>/<name>` of
every manifest in the store (`platform/manifest/<sub>`).

<!-- req: P/02.4-R387 -->
`selected`: the rows of the store under P (for D — the rows named in D).

<!-- req: P/02.4-R388 -->
`kept`: a selected row `domain/<sub>/<manifest:domain.kept>[/…]` (the writers `<s>domain` and domain) leaves the selection: it is not
read, not counted, not unknown-row-form and does not affect the code, under D and under a given prefix alike.

<!-- req: P/02.4-R389 -->
`walked`: a selected row of a row family of the data catalogue whose writer is `admin(w2cctl secrets seal …)`: `door/signer`,
`domain/signer`, `domain/signer-pending`, `domain/book-seal`, `domain/member-key`, `domain/users/<name>`,
`domain/break-glass/<cluster>`, the unit rows and the tables of the manifests. `walked`: a walked row is read by the schema of its family, its
values follow «Reseal a value» of the sealing contract; `status` counts only these rows, `seal` writes only these rows. `walked`: `door/signer` is outside D — only a given prefix (`door/`) selects it.

<!-- req: P/02.4-R392 -->
`other`: a selected row of another row family of the data catalogue (`domain/keys`, `domain/root`, `door/keys`, …) is not walked: it is
not counted, not written and does not affect the code.

<!-- req: P/02.4-R393 -->
`join`: `domain/join` carries `seed_secret`, but its writer is only join (create): it is not walked — `seal` does not reseal it,
`status` does not count it; an exception named here, no admin writer.

<!-- req: P/02.4-R394 -->
`unknown`: a selected row that matches no row family of the data catalogue (`identity/x`, `domain/<unknown name>`, under a given
prefix `<sub>/<unknown name>`) is listed, not skipped: unknown-row-form below, code 1 at `status` and at `seal`. An unknown row — do not guess the fields: do not touch the row (byte for byte), a log line «`<object-key>` unknown-row-form» without
the value, the walk continues, the result is code 1, something is left.

<!-- req: P/02.4-R396 -->
A walked row that is not readable (the outcome of its family, `<family>.outcomes.tsv`), at `seal` and `status` — the same: do not
touch the row (byte for byte), a log line «`<object-key>` unreadable» without the value, the walk continues, the result is code 1; this is one
rule for all families that the command walks. The kept rows leave the selection
(«Walk» `kept`). The codes of `seal`/`status` above refer to the named outcomes; the form of their text output is left
to the implementation.

<!-- req: P/02.4-R399 -->
`new`/`rotate`: success — 0, a refusal — a non-zero code and a reason without key material.

<!-- req: P/02.4-R400 -->
A refusal of `new` with an existing file does not change it.

<!-- req: P/02.4-R401 -->
A refusal of the ring check at `rotate` keeps
the former file.

<!-- req: P/02.4-R402 -->
When `SECRETS_KEY` is set to an empty string or its ring is unreadable, `seal`/`status` refuse with code 2 before any write. The diagnostic names the reason “ring unreadable” and the supplied path (including an empty path), without secret values; rows with clear secrets remain unchanged. When the walk is unavailable, `seal`/`status` do not declare a successful completion and do not count unread rows as absent.

<!-- req: P/02.4-R404 -->
The check of `status` does not cover backups:
the output of status is not a permission to delete keys — in the profile of the lesson they are kept,
including the keys of envelopes, copies and fingerprints of live claims. Taking keys out of circulation requires
a separate procedure and is not part of the command `status` (copies — P/08.8 N1.5).

#### N1.9 The command `w2cctl tls status`

<!-- req: P/02.4-R405 -->
```
w2cctl tls status
  reads:  the heartbeats of the resources of the cluster (door: {addr, mode, cert_until}; mode: loopback | mtls); the kits of W2C_TLS_DIR
  output: a line per door — server, role, address, mode, cert_until
  code:   0 | 1 | 2
```

<!-- req: P/02.4-R406 -->
`w2cctl tls status`: no input; the right admin (`admin.sock`), read only: writes nothing.

<!-- req: P/02.4-R407 -->
`reads`: the heartbeats of the resources of the cluster (the field `door` of a process door — `{addr, mode, cert_until}`, the words of `mode` — `loopback | mtls`; written by the resource, P/05 N1.4) and the kits of `W2C_TLS_DIR` of its own server (N1.6 `kit`).

<!-- req: P/02.4-R408 -->
`output`: a line per door — server, role, address, mode, `cert_until`; the form of a line is the implementation's (as at `secrets status`),
normative are the set of lines, the fields and the codes. `output`: a role with a kit on its own server without a live process (no heartbeat) —
there is no door: a line by the kit without an address, with the mode and `cert_until`. `output`: an expired certificate of a kit without a door — code 1
(the role will not come up).

<!-- req: P/02.4-R411 -->
`code`: 0 — there is no `loopback` door with an address off the loopback and no expired `cert_until`; 1 — there is such a door or an expired
`cert_until` of a door or a kit; 2 — the read is not confirmed (the store or a heartbeat did not answer, a kit is not readable).

<!-- req: P/02.4-R417 -->

<!-- req: P/02.4-R418 -->
`controller`: without a shard the agent
does not report (P/09.1 N1.2 ready).

<!-- req: P/02.4-R419 -->

<!-- req: P/02.4-R420 -->

while there is no snapshot shard of each manifest of the catalogue with `domain.ref`, like ready of the agent (P/09.1 N1.2), — answer 503

## N3 Procedures

### server start

<!-- req: P/02.4-R457 -->

<!-- req: P/02.4-R460 -->
2. the resource: a heartbeat at once, the heartbeat stream; restore (P/05 N1.4) in its own attempt; the door row `platform/doors/<s>` with `at` (P/05 N1.4).

<!-- req: P/02.4-R461 -->
3. the controllers of the manifests: the manifest from the store row (chapter 2.3). Step 3: the first 45 s the controllers judge nobody.

<!-- req: P/02.4-R464 -->
4. the console: the manifests from the rows, the shell root, resealing of the secrets (P/06.2 N3), the reaper of requests and the marks of bodies. Step 4: deleting bodies — only in a separate maintenance window of P/06.1 N2.

<!-- req: P/02.4-R465 -->

of the worker unit (N1.1). Step 5: on macOS launchd does not guarantee an order — the worker waits for the share of its part itself, with a pause, until
the first action with it.

<!-- req: P/02.4-R468 -->
6. the workers script by the timer: the series `workers_wanted` from `/metrics` → start/stop of the instances n ≥ 2 within the ceiling (N1.5).

<!-- req: P/02.4-R469 -->
Steps 2–5: the first action of each platform process and worker (not a part) is the schema check (P/06.6 N3 «console start — schema check», the common block), before reading the manifest.

<!-- req: P/02.4-R470 -->
**Races.** `After` sets the start order, but not the readiness of the store, the rights or the manifest. Each process waits for a reliable read before its first action. An erroneous configuration/schema — exit 2 without a restart (`RestartPreventExitStatus=2`, N1.1).

<!-- req: P/02.4-R474 -->

<!-- req: P/02.4-R475 -->

at the leader. revoke: a server without a kit — a door on the loopback.

<!-- req: P/02.4-R481 -->
