### Н1.1 Manifest text

A manifest is a text in the UTF-8 encoding in the syntax of YAML 1.2.2 within the rules below (ADR-0092 items 2–4,
addendum (2)). The text is parsed by a ready-made YAML 1.2 parser of a pinned version; on top of it stands the thin check
of layer 1 ([layers of В7](../../common/LAYERS.md)): the rules `text` below, nothing beyond them. Plain scalars are
recognized by the scalar table of [the section «Form»](#форма-построена-из-стандартных-файлов) by the style of the node —
a norm of this chapter, not the core schema of YAML 1.2 (core reads `0x10` and `0o7` as integers, and bool only as `true`,
`True`, `TRUE`; added by the JSON Schema pilot). The loader MUST accept exactly this text and MUST refuse everything beyond
it (`refused:text`, Н4).

```yaml
text:
  bytes:    UTF-8; no BOM: U+FEFF as the first character of the file — refusal, further on — an ordinary character (`a﻿b` — a word); no C0 except
            TAB, LF and CR, no DEL and C1 (including U+0085 NEL), U+FFFE, U+FFFF, U+2028 and U+2029 — refusal; the same characters in
            a value after escaping (`\x07`, ` `, surrogates) — refusal; a lone CR — refusal, CRLF reads as LF
  tab:      a literal TAB — only in a comment (after `#`); in indentation, after `:` or `-`, inside a plain word, in a
            quoted string, in a block scalar and in a flow `{…}`/`[…]` — refusal (ADR-0092 item 4); `\t` and `\<TAB>` in
            double quotes — an escape, admissible
  document: exactly one document — by bytes, not by the answer of the parser: a leading `---` from column 1 before any content
            is admissible; a second `---`, a `---` not from column 1, `...` and a directive `%` — refusal; the root is a block mapping from
            column 1: a shifted document, a root in flow `{…}`, a list, a scalar, an empty file — refusal
  refused:  an anchor `&`, an alias `*`, a tag `!…`, a merge key `<<`; a mapping key and a list key; a plain key that the
            scalar table reads not as a string (int, float, bool, null, `~`: `1:`, `1.5:`, `true:`, `null:`) — everywhere, including
            inside values of `type: json`; in quotes (`'1'`, `'true'`) — a string, `0x10`, `0o7` — words; a key said
            twice in one mapping (and in a flow `{a: 1, a: 2}`); nesting deeper than 64 (the root is level 1, every
            mapping and list, block and flow alike, is one more level, a scalar adds no level)
  rare:     what YAML libraries read differently — a flow collection over several lines, a quoted string over several
            lines, an explicit indentation indicator (`|2`), a complex key (`? …`) — refusal in words, not «whatever comes out»
  flow:     a key of a flow mapping with `:` and without a value (`{unconfirmed_max:}`) — refusal (ADR-0092 item 4); a lone `-`
            as a plain scalar in a flow (`[-, a]`, `[-]`, `a: [x, -]`, `{k: -}`) — refusal: in YAML 1.2.2 a plain scalar in a flow does
            not start with `-` (yaml-test-suite G5U8, YJV2; V7-FLOW-DASH-01)
  escape:   in double quotes — only `\\` `\"` `\/` `\t` `\<TAB>` `\n` `\r` `\<space>` `\_` (U+00A0) `\xXX` `\uXXXX`
            `\UXXXXXXXX`; the resulting character obeys `bytes`; the result is a Unicode scalar value: a surrogate D800–DFFF
            (`\ud800`, `\U0000d800`, or the pair `\ud83d\ude00` — YAML does not join surrogate pairs) — refusal; a Unicode scalar outside
            the BMP is admissible as a literal `😀` or as `\U0001F600`; `\0` `\a` `\b` `\v` `\f` `\e` `\N` `\L` `\P` and an unknown one (`\q`) — refusal; in single quotes
            there are no escapes except `''`
  comment:  `#` right after a closing quote, `]` or `}` (`"a"# c`, `]# c`) — refusal; `#` after a space —
            a comment, `#` inside a plain word (`a#b`, `counter# c`) — part of the word (YAML 1.2.2)
  block:    after `|` or `>` and an indicator (`-`, `+`) — a space or the end of the line; leading empty lines of a block scalar are not
            deeper than its first non-empty line — otherwise refusal
  parser:   a YAML parser error — refusal (`[ - , a ]`, an implicit key longer than 1024 characters — YAML 1.2.2 § 7.4.2); an empty element
            of a flow at the start or in the middle (`[a,,b]`, `[,a]`, `{a: 1,, b: 2}`) — a parse error; a trailing comma at the end
            of a flow (`[a, b, ]`, `{k: v, }`) — admissible (YAML 1.2.2; decision of the Architect of 2026-10-28 on ADR-0092 addendum (1), yaml-test-suite UDR7)
```

What YAML 1.2.2 reads by itself is read by it: a value on the line below the key (a word, quotes, a flow), a scalar below
a bare `-`, `?x` as a key and as a value, ` # c` in a continuation line of a plain word — a comment; a lone `-` as a value in
a block is the indicator of a list element, not a word (`unit: -` above a key of the same indentation — a parse error), in
a flow `[-, a]` — refusal (`flow`) (ADR-0092 item 3: 11 deviations of the former norm are removed, deviation 12 — the
trailing comma in a flow — by the Architect's decision of 2026-10-28 on ADR-0092 addendum (1), yaml-test-suite UDR7).
Scalars: a plain one — by the scalar table, a quoted one and a block one — always a string; an empty value (`key:` without
a value) is neither a string nor a mapping: where the place needs a value, a form refusal (`refused:form`); an explicit
«no» is written with the word `null` or `~`.

Float numbers in an accepted manifest are finite and in absolute value not greater than the limit of the scalar table
(`float_max`) — after reading in binary64: a notation that rounds to this number (`1.7976931348623158e308`) is accepted; a
notation of a non-zero number that reads as zero (underflow, `1e-400`) is `refused:form` (added by the experience of the
text layer). NaN, both infinities (in any spelling YAML admits) and an overflow of this range are `refused:form` with the
path of the value; they do not turn into a string or null. This rule applies in the whole document, including
default/inherit and nested numbers of JSON and of opaque places. Opacity cancels the check of the names of inner keys, but
not the common requirements on numbers and JSON.

### Н1.2 Document

The root is a mapping with a closed set of sections; the form of each section, whether it is required, its defaults and the
lesson where a key gets its meaning are [the section «Form»](#форма-построена-из-стандартных-файлов). The owner lessons
give the meaning of keys and refer here for the form; when the form diverges, the source is right. An unknown key at any
level is a refusal (Н4). A section absent from the file means the default of its lesson, if one is defined. The absence of
a required one is `refused:form`; null does not replace a mapping or a string. A profile of a subsystem without units is not
part of this chapter; the loader does not choose `unit.rows` and numeric/named for the author. Places with author names (in
the section «Form» — «имена автора») and opaque places («opaque») are places of the schema without a closed set of keys
([layers of В7](../../common/LAYERS.md)): for an opaque place the form (Н3 step 2) does not check the set of keys, but the
references of Н1.4 to its keys and values are checked, and the numbers — by Н1.1. An integer place (the places
`x-integer-place` of the layer table: `capacity.default`, deadlines, a column width and the like) is a number with an
integer value: `4.0`, `4e0`, `1e1` are integers and in the tree become `4`, `4`, `10`; a fractional part (`4.5`) and a value
outside ±(2^53 − 1) are `refused:form` (ADR-0092 item 8; layer 2, the word `x-integer-place` of the layer table). The integer
notion of data families is another layer (the row codec, layer 3) and is not changed by this.

### Н1.2а Summary table of keys

The table of keys is [the section «Form»](#форма-построена-из-стандартных-файлов) (the root and the definitions). A said
key without a value is `refused:form` (and `default:` without a value: an explicit `null` is «no default», an empty value is
not said); the class of a refusal is the layer (Н4); the marks `x-class` of the layer table serve only to reconcile set A
with the former classes (ADR-0092 Confirmation), they are not a norm of the class. An intersection of a table name with the
names of the subsystems of the catalogue is `refused:catalogue` (Н3).

### Н1.3 Field

The grammar of a unit field (`unit.fields.<имя>`, the definition `unitField`) and of a table field (`tables.<т>.fields.<имя>`,
`tableField`) is [the section «Form»](#форма-построена-из-стандартных-файлов). The meaning of a field in a row is
[P/06.1](../../06-console/spec/06.1-console.norms.md) Н1.2 (`<sub>/<rows>/<id>`), in a form —
[P/06.5](../../06-console/spec/06.5-console.norms.md) Н1.2 (`display.form`), in the domain —
[P/08.1](../../08-domain/spec/08.1-domain.norms.md) Н1.4 (the view) and [P/08.6](../../08-domain/spec/08.6-domain.norms.md)
Н1.3 (the edit); here is what the loader checks and in what order:

- a name from `platform_fields` of P/06.1 Н1.2 in `unit.fields` is `refused:form` before the check and the materialization
  of the value, including `default`/`inherit`; the ban does not carry over to table fields; the field `state` with a declared
  `unit.state` is also `refused:form` (the key `state` of a unit is its state, P/06.1 Н1.2; ADR-0091 item 3);
- a blob field — only in `unit.fields`: the digest comes through the byte door `PUT /<rows>/<id>/<blob_field>` after the
  unit is created (P/06.1 Н3 «put_body»), at creation the field is always `""` — a default or an inheritance would
  write a digest into the row past that door; `unit.fields.bytes` next to blob is a refusal: it is a field of the answer
  `BlobWritten` of the byte door (P/06.1 Н1.5);
- a table field `name` — only string with `key: name` (P/06.1 Н1.6); `held_by`, `garbled`, `by`, `at`, `made_at`,
  `revision`, `index` are computed values and stamps, they are never table fields, regardless of `stamp`;
- a field name is only a string key of YAML (Н1.1 keys); conversion of a name into a string is forbidden;
- `{id}` in a default: for a `string` field of a unit with `unit.id: numeric` the `default` MAY contain `{id}` — the door
  substitutes the decimal notation of the issued id at creation ([P/06.1](../../06-console/spec/06.1-console.norms.md)
  Н1.2 step 3), an edit does not recompute the value; `{id}` with `unit.id` equal to a field, not `numeric` (row 122 of
  `relations.json`), `{id}` in a default of a field of another type (row 123) and any other `{`, `}` in a default of a
  `string` field with `unit.id: numeric` (row 124; there is no escaping) are `refused:relations`; for a table field and for
  a unit field when `unit.id` is a field, `{`, `}` without `{id}` in a default are characters as they are (VMS request
  № 1, the Architect's decision of 2026-10-23).

### Н1.4 References between keys

A key that names a field, a table, a metric or a route MUST name what is declared in **this same** manifest; otherwise it
is a refusal at loading, not on the page and not during a pass. The rows of references and of relations between values are
[the section «Form»](#форма-построена-из-стандартных-файлов) («Связи», the source `02.1-installer.relations.json`, row
numbers — the field `no`); they are checked only on a clean form (Н3: form before relations). Beyond the rows:

- the template `requests.key` names the properties of `requests.schema.properties` — the fields of the body of a request
  `POST /<sub>/requests` ([P/06.4](../../06-console/spec/06.4-console.norms.md) Н1.5): `{имя}` — only a string without
  conversion, `{имя:int}` — a finite binary64 number (as in JCS) with absolute value ≤ 2^53−1, truncation towards zero and
  decimal notation without the sign `+` and leading zeros (`7.9` → `7`, `-7.9` → `-7`, `-0.5` → `0`); bool is not a number.
  An absent value, another type or a number outside this bound is 400 on submission, not at loading. Unit fields have
  nothing to do with it. The same template is in `tables.<т>.key`;
- `display.options.<поле>` of a `bool` field: the key is the text of the value in quotes (`'true'`, `'false'`); a plain
  `true:` is `text` by Н1.1 keys; for a pulse word from `display.form[].status[]` — any strings (labels of values);
- `display.fields.<имя>`, `display.field_help.<имя>`, `display.form[].fields[]`, `display.tree.columns[].field` accept, of

- `placement.unplaced.delete_after` no longer requires the absence of `fixed` fields and of `about` by id (rules 46–47 in the former numbering, before ADR-0091, are

- `tables.<т>.delete_after` — the lifetime of the rows of the table in seconds, an integer ≥ 1; anything else is
  `refused:form`. No key — no lifetime: the absence of the key does not turn deletion on. The meaning and the removal —
  [P/06.1](../../06-console/spec/06.1-console.norms.md) Н1.6,
  [P/06.4](../../06-console/spec/06.4-console.norms.md) Н3 `tables`; the right of the console —
  [P/02.5](02.5-installer.norms.md) Н1.4 (ADR-0094 step 3b). A table named by `holds.table` or `placement.places.table`
  has no such key: the key there is a relations refusal (rows 125, 126; the Architect's decision of 2026-10-31): a row of
  such a table is a declared place, and a lifetime would remove it from under an active hold;

## Н2 Doors

The loader has two doors: the loading procedure, which all processes and the installer use, and `GET /manifest` of the
console, by which the console module (lesson P/07) learns the form of a subsystem; the second one is in
[chapter P/06.5](../../06-console/spec/06.5-console.norms.md) Н2 «GET /manifest».

### Loading procedure

Not HTTP: an entry of the implementation that gets bytes and the name of a source and answers with a manifest or a refusal. All paths of reading a manifest — a file, a store row, a built-in manifest — MUST go through it.

```
load(bytes, source) → manifest | refusal(source, key_path, reason)
load_catalogue([manifest…])  → catalogue | refusal(source, key_path, reason)     # checks between manifests
```

---

## Н3 Procedures

### load(bytes, source) → manifest | refusal

1. Text: parse the bytes with the YAML 1.2.2 parser of a pinned version and the thin check of Н1.1 (layer 1); if they do
   not pass, return `refused:text`.
2. Form: check the tree against the schema `02.1-installer.schema.json` (JSON Schema 2020-12) and the words `x-*` of the
   layer table `02.1-installer.layers.tsv`: the name (Н1.2), the closed set of keys of every level, in places of author
   names — any names by their grammar, in opaque places the set of keys is not checked; types, the field grammar (Н1.3),
   enumerations, required keys (`capacity.default`); numbers — by Н1.1, in opaque places too; an integer place — the bounds
   ±(2^53 − 1), a value with an integer value is an integer and is converted to an integer in the tree (`4.0` → `4`;
   layer 2). If the tree does not pass, return `refused:form`.
3. Relations: only on a clean form, check every row of the relations (CEL, `02.1-installer.relations.json`) over the tree
   of the loader; an absent value and `has` take the static default `default` of the form (Н1.4). If a row does not hold,
   return `refused:relations`.
4. Defaults: fill what is absent with the defaults of the owner lessons; no weakening defaults for `lease.unconfirmed_max`,
   `placement.unplaced.delete_after` and `placement.places.server_field` (Н1.2 «Form», the properties of the same names).
5. Return the manifest.

The order of layers is normative (ADR-0092): text → form → relations; relations are checked only on a clean form — a
manifest with a form refusal is refused with the class `form` even if a relation is wrong too (added by the corpus of
chapter 2.1). The order inside the form and inside the relations — the implementation decides; the path and the row of a
refusal are a hint (Н4).

**Races.** None: loading is pure, without state and without the store.

### load_catalogue([manifest…]) → catalogue | refusal

Checks that need more than one manifest: `worker.requests` names a subsystem of the catalogue that accepts requests; `near.of` and `near.prefer` are fields of the subsystem `placement.near.sub`; `metrics.prefix` of two subsystems does not coincide (`GET /manifest`, P/06.5 Н2). While the subsystem `near.sub` is not yet in the catalogue, the check of `near.of` and `near.prefer` waits for its installation, as for `worker.creates` below: the affinity does not act before it (the unit is placed without it, P/04 Н1.3 `near`); installing `near.sub` with incompatible fields is a catalogue refusal; the subsystem is there but the fields are not — a catalogue refusal, as before (ADR-0091 addendum (26) item 2). The deferral of `near` sets no order of installation (P/02.4 Н1.7 `order`; addendum (26) item 1).

`worker.creates[]` of a subsystem C (ADR-0091 item 1; `Г-8` — the Architect's clarification of 2026-10-22):

1. `sub` is a subsystem A, `rows` is its `unit.rows`; `unit.id` of A is not `numeric` (the reserve `next_id` is not given
   to the orderer). While A is not in the catalogue, checks 1–4 wait for its installation: the catalogue is checked whole at
   every installation, and installing A with an incompatible orderer is a catalogue refusal (the orderer and the addressee
   MAY refer to each other — `testsub` orders `testsub2`, `testsub2` asks `testsub`; otherwise they could not be installed
   one by one);
2. every substitution `{f}` in `key` is a field of `unit.fields` of A with `required: true`, of type `string`, `url`, `int`,
   `float` or `bool`, not `*_secret` and not the id-source field of A (`unit.id`: the library fills it with the ready id);
3. `key` names every `fixed` field of A except the id-source field, and the field `about.field` of A if it is not `unit.id`;
4. A has no field `*_secret` with `required: true` or with `default`: the library of the orderer writes no secrets
   (P/03.6 Н1.6), a row without them would not be created;
5. two orderers of one table — names C and D where `C-` is the beginning of `D-` (`rec` and `rec-x`) — are a refusal: the
   prefixes of their ids are nested.

`worker.uses[]` — `<подсистема>.<доля>`: the subsystem, if it is in the catalogue, has declared `shares.<доля>`; while it is
not there — the same deferral as for `worker.creates` (there is no group of the share, the systemd unit of the worker does not
get it — P/02.4 Н1.1). The OS names and paths of all subsystems of the catalogue — users, groups, systemd units, directories
of shares and parts ([P/02.4](02.4-installer.norms.md) Н1.1) — are built all together: any coincidence of two names and a
name longer than 32 characters is a catalogue refusal (ADR-0091 item 5). The catalogue is all manifests of the cluster (all rows `platform/manifest/*`); a refusal of one manifest of the catalogue is a refusal of the catalogue. For any subsystems A and B, including A=B, the name of B does not coincide with unit.rows or with the name of any table of A, list tables included. Otherwise refused:catalogue with the names of both manifests and the conflicting family, before the catalogue is issued / before the first write of the installer; this excludes an intersection of the root door and a mount for any choice of root.

Token kinds of the domain (Н1.2б; ADR-0091 addendum (14) item 1, addendum (17) item 5): the name of a kind of `domain.tokens`
is declared in the catalogue once — the same kind in two subsystems is a catalogue refusal; every kind in
`door.routes[].domain` of a subsystem C is declared in `domain.tokens` of a subsystem of the catalogue (C itself included),
otherwise — a catalogue refusal. A route kind has no deferral like that of `worker.creates`: the subsystem that declares a
kind is installed before the door that names it.

`door.pass.calls[]` of a subsystem C (ADR-0094 B1): an entry `<s>/<имя>` of another subsystem `<s>`, if it is in the catalogue, names its `unit.rows`, a table of the display form, `policy`, `next_id`, a route of `door.routes` or a segment of the first kind of its `door.pass` (ADR-0112 addendum (3) item 2): a segment of the second kind and a segment that is not in its list are a catalogue refusal; `GET <s>/where` — for any subsystem of the catalogue; `GET <s>/heartbeats` and `GET domain/at/<s>/heartbeats` — only for `<s>` with `heartbeat.door`, otherwise a catalogue refusal; `<s>/operations` — only the own subsystem with `door.pass.operations` (relation 133), otherwise — a catalogue refusal. While `<s>` is not there — a deferral, as for `worker.creates`: a subsystem of the list need not stand in every cluster, and then its door simply does not exist.

`domain.kept_read`: every element is a row of `domain.kept` of this manifest by its exact name, not a family with `/`; otherwise a catalogue refusal. An entry `GET domain/<s>/kept/<имя>` in `door.pass.calls[]` names an element of `domain.kept_read` of the subsystem `<s>`, otherwise a catalogue refusal; while `<s>` is not there — a deferral. A table or `unit.rows` named `kept` with `domain.kept_read` is a catalogue refusal: the segment is taken by the door.

A book for all: `domain.books.<книга>.to` equal to `"*"` ([P/08.5](../../08-domain/spec/08.5-domain.norms.md) Н1.3 `to_all`) with `domain.names.<книга>/.grant` is a catalogue refusal: one row for everyone has nothing per recipient (ADR-0113 addendum (9) item 1); with `pick: unique` — too: the row does not keep the losing contribution. The manifest does not name the secret of such an entry: the assembly judges it, `bad_contribution`.

**Races.** The catalogue check gets a ready set of loaded manifests; two checks do not change each other's inputs.
Reading the sources before it does not promise an atomic snapshot of all files or rows. If a file changes during reading,
old, new or mixed bytes may be obtained: an admissible document loads, an inadmissible one gives a refusal by Н1. The pure
procedure over bytes does not detect the fact of the change of a file itself. An unresolved link between accepted manifests
gives a catalogue refusal; with any such refusal no partial catalogue is issued.

The manifest row, the start of a process and the change of a manifest are set by [chapter 2.3](02.3-installer.norms.md) Н3.

## Н4 Refusals

A closed list. The loader has one kind of answer «not a manifest» — a refusal in words that names the source (a file or a store key) and the path of keys; the classes below distinguish the cause for the reader and for acceptance, not the code.

The path of keys and the line of the file in a refusal are a hint, not a norm: the verdict and the exit code are strict
(ADR-0092 item 5); acceptance writes them into the report without a failure (Н5). The hint is as python and go were
reconciled on 2026-10-18 (SHOULD): the path — to the deepest key with a wrong value; a list index in the path is a number;
the line is the line of this key; an absent key — the path with its name and the line of the enclosing mapping; a repeated
key — the path of the repeated key and the line of the second declaration; an encoding error — the line of the byte,
without a path; a refusal of the text layer — the line of the guilty character or construct (a marker, an opening quote, an
unclosed flow, a line without a key), not the next one and not the end of the file (added by the experience of the text
layer). For a rule on two keys the path is the key that the rule forbids next to the other: `merge: union` of a field that is
not `list` — `…fields.<поле>.merge`; `bytes` next to blob — `unit.fields.bytes`; a field `name` of a table out of form —
`tables.<т>.fields.name`; `delete_after` with a `numeric` id — `placement.unplaced.delete_after` (added by the JSON Schema
pilot). For presence rules the path is: «A is forbidden without B» — A itself (`merge` without `inherit`, `must_match`
without `ref`, `login` without `param`, `in` without `regex`); «A requires B» — the missing B (`per_person` and `free: true`
→ `ttl`, `free: false` → `valid_for`, `most_valid`; `from` → `key`, `pick`, `to`) (added by the pilot of variant C, П4). For a reference of Н1.4 that requires another key (`requests.stamp: group` and `rights.reach.group` without `placement.group_by`, `requests.outcome: fetched` without `requests.key`, `placement.home: near` without `placement.near`), the path is the referring key itself (added by the corpus of chapter 2.1). For a rule over a set (`unique`, `prefix_free`, the depth of `schema`) the path is the set itself; for a repetition of a list element — the second occurrence, as for a repetition of a key (added by the corpus of chapter 2.1). The form of the value of a key (`worker.reads[]`, `secrets.reads[]` — `<семья>/<имя>`) is
the class `form`, not a relation of Н1.4 (added by the pilot of variant C, П3). The class of a refusal is the layer where the
refusal is (ADR-0092 item 6): `text`, `form`, `relations`, `catalogue`; the refusal word is `refused:<класс>`; acceptance
checks the class (`classes.tsv`, Н5).

The normative refusal catalogue of this chapter is [`forms/refusals.tsv`](../forms/refusals.tsv) (ADR-0125 addendum (1) item 5). The `chapter` and `row` columns preserve the addresses of the former table; the form contains the codes, fixed words, diagnostic subjects, conditions and caller actions. This text does not repeat that catalogue.

There are no warnings. There is no list «accepted and ignored». There is no partially loaded manifest.

The loader does not judge the size of the files of `console.files`: it sees only the bytes of the manifest. The ceilings
`FILE_MAX`, `FILES_TOTAL_MAX` — [chapter 2.3](02.3-installer.norms.md) Н1.5, Н4.

## Implementation decides

The implementation is to name in its description:

1. **the libraries of the stack** ([the section «Form»](#форма-построена-из-стандартных-файлов)) for steps 1–3 of the procedure: a YAML 1.2 parser, a JSON Schema 2020-12 validator, CEL — pinned versions, and its own layers (`LAYERS.md`); the standard files themselves are a norm, not a choice;
2. **how many form errors one refusal names** (the first one or all) — the path and the line in a refusal are a hint (Н4);
3. **the command that loads one file for acceptance**, by the section «Stand» of the common acceptance README: the runner calls it on every file of `verdicts.tsv`; exit code 0 — a manifest, any other — a refusal, the text of the refusal names the file.
4. **the internal contract of the manifest API**: read the row `platform/manifest/<sub>` into the canonical view
   ([P/02.2](02.2-installer.norms.md)), assemble and check the catalogue, `rev`, the outcomes and the refusals (the words —
   as in P/02, without retelling the norms) — an API of a library, not a move of P/02 into `common/`. The owner of lesson 02
   writes the description in the repository of the implementation before the library; the processes 03–10 read only the
   contract and the API; a mix of languages — through the store: the canonical view of the row is a norm of P/02.2 (the
   stage C guess C04-MANIFEST-SDK-01, ADR-0087 addendum (12) item 7).
