## N0 Vocabulary

<!-- req: P/02.1-R001 -->
Normative keywords follow RFC 2119 and RFC 8174 (MUST, MUST NOT, SHOULD, MAY), as the
[course canon](../../common/NORMATIVE-TERMS.md) maps them; requirements are written in EARS templates (When … / If … then …
/ While … / The …) with the RFC keyword in place of «shall». An unmarked sentence of a normative section reads as MUST.

<!-- req: P/02.1-R003 -->
Markers of this text. «(judge-only: …)» marks a named file, row or scenario outside the model input (M). A case name (`base`, `name_*`, `c8_ref<N>_*`) denotes judge-only data: a case of the verdict table of chapter 2.1 or, where chapter 2.3 is named, an installation row of that chapter. `sc. NN` denotes scenario NN of the named chapter or lesson; scenarios and seams are data supplied only to the judge. The public norms and forms define the implementation obligations; concrete scenarios, fixtures and expected answers are supplied to the judge.

<!-- req: P/02.1-R004 -->
A requirement whose paragraph starts
with the label «**Scope: production.**» (a checklist item — right after its id) belongs only to production qualification
by the [common production obligations](../../common/contracts/production-obligations.md): the verdicts, installation
rows, seams and scenarios of this lesson do not establish it, and a missing executable, context, fault, budget or
capacity binding there is MissingBinding/NOTEXEC, not a pass. A requirement without the label binds every
implementation, also when only reading or a real stand checks it.

<!-- req: P/02.1-R005 -->
Marks of the readiness checklist and of the system checklist. Right after its id (after the label
«**Scope: production.**» when the item has it), a checklist item names in square brackets how it is closed: `test` — by
an execution of the implementation: its own test and/or a case of the verdict table, an installation row, a seam, a
scenario or a vector of acceptance; `reading` — only by reading the code or the description of the implementation, a test
does not close it; `stand` — only by a real stand outside the own tests of the implementation: production acceptance and
the probes of a real host (an item that needs the OS or the host). Several words stand comma-separated,
`[test, reading]`; each word names the part of the item it closes.

### N1.1 Manifest text

<!-- req: P/02.1-R008 -->
A manifest is a text in the UTF-8 encoding in the syntax of YAML 1.2.2 within the rules below. The text is parsed by a ready-made YAML 1.2 parser of a pinned version; on top of it stands the thin check
of layer 1 ([layers of V7](../../common/LAYERS.md)): the rules `text` below, nothing beyond them. Plain scalars are
recognized by the scalar table of [the section «Form»](#form-built-from-the-standard-files) by the style of the node —
a norm of this chapter, not the core schema of YAML 1.2 (core reads `0x10` and `0o7` as integers, and bool only as `true`,
`True`, `TRUE`). The loader MUST accept exactly this text and MUST refuse everything beyond
it (`refused:text`, N4).

<!-- req: P/02.1-R012 -->
```yaml
text:       # the rules of layer 1: each key names its rules, the items below the block
  bytes:    the encoding and the characters
  tab:      a literal TAB
  document: one document and its root
  refused:  forbidden constructs and keys, the depth
  rare:     constructs YAML libraries read differently
  flow:     flow collections
  escape:   escapes in quotes
  comment:  the character `#`
  block:    the header of a block scalar
  parser:   parser errors and flow commas
```

<!-- req: P/02.1-R013 -->
`bytes`: UTF-8. `bytes`: no BOM: U+FEFF as the first character of the file — refusal, further on — an ordinary character (`a﻿b` — a word). `bytes`: no C0 except TAB, LF and CR, no DEL and C1 (including U+0085 NEL), U+FFFE, U+FFFF, U+2028 and U+2029 — refusal. `bytes`: the same characters in a value after escaping (`\x07`, ` `, surrogates) — refusal. `bytes`: a lone CR — refusal, CRLF reads as LF.

<!-- req: P/02.1-R018 -->
`tab`: a literal TAB — only in a comment (after `#`); in indentation, after `:` or `-`, inside a plain word, in a
  quoted string, in a block scalar and in a flow `{…}`/`[…]` — refusal. `tab`: `\t` and `\<TAB>` in double quotes — an escape, admissible.

<!-- req: P/02.1-R020 -->
`document`: exactly one document — by bytes, not by the answer of the parser: a leading `---` from column 1 before any
  content is admissible; a second `---`, a `---` not from column 1, `...` and a directive `%` — refusal. `document`: the root is a block mapping from column 1: a shifted document, a root in flow `{…}`, a list, a scalar, an
  empty file — refusal.

<!-- req: P/02.1-R024 -->
`refused`: an anchor `&`, an alias `*`, a tag `!…`, a merge key `<<`. `refused`: a mapping key and a list key. `refused`: a plain key that the scalar table reads not as a string (int, float, bool, null, `~`: `1:`, `1.5:`, `true:`,
  `null:`) — everywhere, including inside values of `type: json`; in quotes (`'1'`, `'true'`) — a string, `0x10`, `0o7` —
  words. `refused`: a key said twice in one mapping (and in a flow `{a: 1, a: 2}`).

<!-- req: P/02.1-R026 -->
- `refused`: nesting deeper than 64 (the root is level 1, every mapping and list, block and flow alike, is one more level,
  a scalar adds no level).

<!-- req: P/02.1-R027 -->
- `rare`: what YAML libraries read differently — a flow collection over several lines, a quoted string over several
  lines, an explicit indentation indicator (`|2`), a complex key (`? …`) — refusal in words, not «whatever comes out».

<!-- req: P/02.1-R028 -->
`flow`: a key of a flow mapping with `:` and without a value (`{unconfirmed_max:}`) — refusal. `flow`: a lone `-` as a plain scalar in a flow (`[-, a]`, `[-]`, `a: [x, -]`, `{k: -}`) — refusal: in YAML 1.2.2 a plain
  scalar in a flow does not start with `-` (yaml-test-suite G5U8, YJV2).

<!-- req: P/02.1-R030 -->
`escape`: in double quotes — only `\\` `\"` `\/` `\t` `\<TAB>` `\n` `\r` `\<space>` `\_` (U+00A0) `\xXX` `\uXXXX`
  `\UXXXXXXXX`; `\0` `\a` `\b` `\v` `\f` `\e` `\N` `\L` `\P` and an unknown one (`\q`) — refusal. `escape`: the resulting character obeys `bytes`. `escape`: the result is a Unicode scalar value: a surrogate D800–DFFF (`\ud800`, `\U0000d800`, or the pair
  `\ud83d\ude00` — YAML does not join surrogate pairs) — refusal; a Unicode scalar outside the BMP is admissible as a
  literal `😀` or as `\U0001F600`.

<!-- req: P/02.1-R033 -->
- `escape`: in single quotes there are no escapes except `''`.

<!-- req: P/02.1-R034 -->
`comment`: `#` right after a closing quote, `]` or `}` (`"a"# c`, `]# c`) — refusal. `comment`: `#` after a space — a comment, `#` inside a plain word (`a#b`, `counter# c`) — part of the word (YAML 1.2.2).

<!-- req: P/02.1-R036 -->
`block`: after `|` or `>` and an indicator (`-`, `+`) — a space or the end of the line, otherwise refusal. `block`: leading empty lines of a block scalar are not deeper than its first non-empty line — otherwise refusal.

<!-- req: P/02.1-R038 -->
`parser`: a YAML parser error — refusal (`[ - , a ]`, an implicit key longer than 1024 characters — YAML 1.2.2 § 7.4.2). `parser`: an empty element of a flow at the start or in the middle (`[a,,b]`, `[,a]`, `{a: 1,, b: 2}`) — a parse error. `parser`: a trailing comma at the end of a flow (`[a, b, ]`, `{k: v, }`) — admissible (YAML 1.2.2; yaml-test-suite
  UDR7).

<!-- req: P/02.1-R041 -->
What YAML 1.2.2 reads by itself is read by it: a value on the line below the key (a word, quotes, a flow), a scalar below
a bare `-`, `?x` as a key and as a value, ` # c` in a continuation line of a plain word — a comment. A lone `-` as a value in a block is the indicator of a list element, not a word (`unit: -` above a key of the same
indentation — a parse error), in a flow `[-, a]` — refusal (`flow`).

<!-- req: P/02.1-R043 -->
Scalars: a plain one — by the scalar table, a quoted one and a block one — always a string. An empty value (`key:` without a value) is neither a string nor a mapping: where the place needs a value, a form refusal
(`refused:form`); an explicit «no» is written with the word `null` or `~`.

<!-- req: P/02.1-R047 -->
Float numbers in an accepted manifest are finite and in absolute value not greater than the limit of the scalar table
(`float_max`) — after reading in binary64: a notation that rounds to this number (`1.7976931348623158e308`) is accepted. A notation of a non-zero number that reads as zero (underflow, `1e-400`) is `refused:form`. NaN, both infinities (in any spelling YAML admits) and an overflow of this range are `refused:form` with the
path of the value; they do not turn into a string or null.

<!-- req: P/02.1-R048 -->
These rules of numbers apply in the whole document, including
default/inherit and nested numbers of JSON and of opaque places. Opacity cancels the check of the names of inner keys, but
not the common requirements on numbers and JSON.

## N2 Doors

<!-- req: P/02.1-R146 -->
The loader has two doors: the loading procedure, which all processes and the installer use, and `GET /manifest` of the
console, by which the console module (lesson P/07) learns the form of a subsystem; the second one is in
[chapter P/06.5](../../06-console/spec/06.5-console.norms.md) N2 «GET /manifest».

### Loading procedure

<!-- req: P/02.1-R147 -->
Not HTTP: an entry of the implementation that gets bytes and the name of a source and answers with a manifest or a refusal. All paths of reading a manifest — a file, a store row, a built-in manifest — MUST go through it.

<!-- req: P/02.1-R149 -->
```
load(bytes, source) → manifest | refusal(source, key_path, reason)
load_catalogue([manifest…])  → catalogue | refusal(source, key_path, reason)     # checks between manifests
```

## N3 Procedures

### load(bytes, source) → manifest | refusal

<!-- req: P/02.1-R150 -->
1. Text: parse the bytes with the YAML 1.2.2 parser of a pinned version and the thin check of N1.1 (layer 1); if they do
   not pass, return `refused:text`.

<!-- req: P/02.1-R151 -->
2. Form: check the tree against the schema `02.1-installer.schema.json` (JSON Schema 2020-12) and the words `x-*` of the
   layer table `02.1-installer.layers.tsv`: the name (N1.2), the closed set of keys of every level, in places of author
   names — any names by their grammar, in opaque places the set of keys is not checked; types, the field grammar (N1.3),
   enumerations, required keys (`capacity.default`); numbers — by N1.1, in opaque places too; an integer place — the bounds
   ±(2^53 − 1), a value with an integer value is an integer and is converted to an integer in the tree (`4.0` → `4`;
   layer 2). If the tree does not pass, return `refused:form`.

<!-- req: P/02.1-R152 -->
3. Relations: only on a clean form, check every row of the relations (CEL, `02.1-installer.relations.json`) over the tree
   of the loader; an absent value and `has` take the static default `default` of the form (N1.4). If a row does not hold,
   return `refused:relations`.

<!-- req: P/02.1-R153 -->
4. Defaults: fill what is absent with the defaults of the owner lessons; no weakening defaults for `lease.unconfirmed_max`,
   `placement.unplaced.delete_after` and `placement.places.server_field` (N1.2 «Form», the properties of the same names).

<!-- req: P/02.1-R154 -->
5. Return the manifest.

<!-- req: P/02.1-R155 -->
The order of layers is normative: text → form → relations; relations are checked only on a clean form — a
manifest with a form refusal is refused with the class `form` even if a relation is wrong too. The order inside the form and inside the relations — the implementation decides; the path and the row of a
refusal are a hint (N4).

<!-- req: P/02.1-R157 -->
**Races.** None: loading is pure, without state and without the store.

### load_catalogue([manifest…]) → catalogue | refusal

<!-- req: P/02.1-R158 -->
Checks that need more than one manifest: `worker.requests` names a subsystem of the catalogue that accepts requests.

<!-- req: P/02.1-R159 -->
`near.of` and `near.prefer` are fields of the subsystem `placement.near.sub`.

<!-- req: P/02.1-R160 -->
`metrics.prefix` of two subsystems does not coincide (`GET /manifest`, P/06.5 N2).

<!-- req: P/02.1-R161 -->
While the subsystem `near.sub` is not yet in the catalogue, the check of `near.of` and `near.prefer` waits for its installation, as for `worker.creates` below: the affinity does not act before it (the unit is placed without it, P/04 N1.3 `near`). Installing `near.sub` with incompatible fields is a catalogue refusal; the subsystem is there but the fields are not — a catalogue refusal.

<!-- req: P/02.1-R163 -->
The deferral of `near` sets no order of installation (P/02.4 N1.7 `order`).

`worker.creates[]` of a subsystem C:

<!-- req: P/02.1-R164 -->
1. `sub` is a subsystem A, `rows` is its `unit.rows`; `unit.id` of A is not `numeric` (the reserve `next_id` is not given
   to the orderer);

<!-- req: P/02.1-R165 -->
2. every substitution `{f}` in `key` is a field of `unit.fields` of A with `required: true`, of type `string`, `url`, `int`,
   `float` or `bool`, not `*_secret` and not the id-source field of A (`unit.id`: the library fills it with the ready id);

<!-- req: P/02.1-R166 -->
3. `key` names every `fixed` field of A except the id-source field, and the field `about.field` of A if it is not `unit.id`;

<!-- req: P/02.1-R167 -->
4. A has no field `*_secret` with `required: true` or with `default`: the library of the orderer writes no secrets
   (P/03.6 N1.6), a row without them would not be created;

<!-- req: P/02.1-R168 -->
5. two orderers of one table — names C and D where `C-` is the beginning of `D-` (`rec` and `rec-x`) — are a refusal: the
   prefixes of their ids are nested.

<!-- req: P/02.1-R169 -->
While A is not in the catalogue, checks 1–4 of `worker.creates[]` wait for its installation: the catalogue is checked whole
at every installation. Installing A with an incompatible orderer is a catalogue refusal. The orderer and the addressee MAY refer to each other — `testsub` orders `testsub2`, `testsub2` asks `testsub`; otherwise
they could not be installed one by one.

<!-- req: P/02.1-R172 -->
`worker.uses[]` — `<subsystem>.<share>`: the subsystem, if it is in the catalogue, has declared `shares.<share>`. While the subsystem of `worker.uses[]` is not in the catalogue — the same deferral as for `worker.creates` (there is no
group of the share, the systemd unit of the worker does not get it — P/02.4 N1.1).

<!-- req: P/02.1-R174 -->
The OS names and paths of all subsystems of the catalogue — users, groups, systemd units, directories
of shares and parts ([P/02.4](02.4-installer.norms.md) N1.1) — are built all together: any coincidence of two names is a
catalogue refusal. An OS name of the catalogue longer than 32 characters is a catalogue refusal.

<!-- req: P/02.1-R176 -->
The catalogue is all manifests of the cluster (all rows `platform/manifest/*`). A refusal of one manifest of the catalogue is a refusal of the catalogue.

<!-- req: P/02.1-R178 -->
For any subsystems A and B, including A=B, the name of B does not coincide with unit.rows or with the name of any table of A, list tables included. Otherwise refused:catalogue with the names of both manifests and the conflicting family, before the catalogue is issued / before the first write of the installer; this excludes an intersection of the root door and a mount for any choice of root.

<!-- req: P/02.1-R179 -->
Token kinds of the domain (N1.2b): the name of a kind of `domain.tokens`
is declared in the catalogue once — the same kind in two subsystems is a catalogue refusal. Every kind in `door.routes[].domain` of a subsystem C is declared in `domain.tokens` of a subsystem of the catalogue
(C itself included), otherwise — a catalogue refusal. A route kind has no deferral like that of `worker.creates`: the subsystem that declares a
kind is installed before the door that names it.

<!-- req: P/02.1-R182 -->
`door.pass.calls[]` of a subsystem C: an entry `<s>/<name>` of another subsystem `<s>`, if it is in the catalogue, names its `unit.rows`, a table of the display form, `policy`, `next_id`, a route of `door.routes` or a segment of the first kind of its `door.pass`: a segment of the second kind and a segment that is not in its list are a catalogue refusal. `door.pass.calls[]`: `GET <s>/where` and `<s>/requests` — for any subsystem of the catalogue (`<s>/requests` is the submission of P/06.3 N1.9; a subsystem without `requests` answers it 404, P/06.4 «file a request» step 0). `door.pass.calls[]`: `GET <s>/heartbeats` and `GET domain/at/<s>/heartbeats` — only for `<s>` with `heartbeat.door`, otherwise a catalogue refusal. `door.pass.calls[]`: `<s>/operations` — only the own subsystem with `door.pass.operations` (relation 133), otherwise — a catalogue refusal. While `<s>` of `door.pass.calls[]` is not there — a deferral, as for `worker.creates`: a subsystem of the list need not stand in every cluster, and then its door simply does not exist.

<!-- req: P/02.1-R187 -->
`domain.kept_read`: every element is a row of `domain.kept` of this manifest by its exact name, not a family with `/`; otherwise a catalogue refusal. An entry `GET domain/<s>/kept/<name>` in `door.pass.calls[]` names an element of `domain.kept_read` of the subsystem `<s>`, otherwise a catalogue refusal; while `<s>` is not there — a deferral. A table or `unit.rows` named `kept` with `domain.kept_read` is a catalogue refusal: the segment is taken by the door.

<!-- req: P/02.1-R190 -->
A book for all: `domain.books.<book>.to` equal to `"*"` ([P/08.5](../../08-domain/spec/08.5-domain.norms.md) N1.3 `to_all`) with `domain.names.<book>/.grant` is a catalogue refusal: one row for everyone has nothing per recipient. A book for all with `pick: unique` is a catalogue refusal too: the row does not keep the losing contribution. The manifest does not name the secret of such an entry: the assembly judges it, `bad_contribution`.

<!-- req: P/02.1-R193 -->
**Races.** The catalogue check gets a ready set of loaded manifests; two checks do not change each other's inputs. Reading the sources before it does not promise an atomic snapshot of all files or rows. If a file changes during reading,
old, new or mixed bytes may be obtained: an admissible document loads, an inadmissible one gives a refusal by N1. The pure
procedure over bytes does not detect the fact of the change of a file itself.

<!-- req: P/02.1-R196 -->
An unresolved link between accepted manifests
gives a catalogue refusal; with any such refusal no partial catalogue is issued.

## N4 Refusals

<!-- req: P/02.1-R198 -->
A closed list. The loader has one kind of answer «not a manifest» — a refusal in words that names the source (a file or a store key) and the path of keys. The classes below distinguish the cause for the reader and for acceptance, not the code.

<!-- req: P/02.1-R201 -->
The path of keys and the line of the file in a refusal are a hint, not a norm: the verdict and the exit code are strict; acceptance writes them into the report without a failure (N5). The hint (SHOULD): the path — to the deepest key with a wrong value; a list index in the path is a number;
the line is the line of this key. The hint (SHOULD) of an absent key — the path with its name and the line of the enclosing mapping. The hint (SHOULD) of a repeated key — the path of the repeated key and the line of the second declaration.

<!-- req: P/02.1-R205 -->
The hint (SHOULD) of an encoding error — the line of the byte, without a path. The hint (SHOULD) of a refusal of the text layer — the line of the guilty character or construct (a marker, an opening
quote, an unclosed flow, a line without a key), not the next one and not the end of the file.

<!-- req: P/02.1-R206 -->
The hint (SHOULD) of a rule on two keys — the path is the key that the rule forbids next to the other: `merge: union` of a field that is
not `list` — `…fields.<field>.merge`; `bytes` next to blob — `unit.fields.bytes`; a field `name` of a table out of form —
`tables.<t>.fields.name`; `delete_after` with a `numeric` id — `placement.unplaced.delete_after`. The hint (SHOULD) of presence rules «A is forbidden without B» — the path is A itself (`merge` without `inherit`, `must_match`
without `ref`, `login` without `param`, `in` without `regex`). The hint (SHOULD) of presence rules «A requires B» — the path is the missing B (`per_person` and `free: true`
→ `ttl`, `free: false` → `valid_for`, `most_valid`; `from` → `key`, `pick`, `to`). The hint (SHOULD) of a reference of N1.4 that requires another key (`requests.stamp: group` and `rights.reach.group` without `placement.group_by`, `requests.outcome: fetched` without `requests.key`, `placement.home: near` without `placement.near`) — the path is the referring key itself.

<!-- req: P/02.1-R210 -->
The hint (SHOULD) of a rule over a set (`unique`, `prefix_free`, the depth of `schema`) — the path is the set itself. The hint (SHOULD) of a repetition of a list element — the path is the second occurrence, as for a repetition of a key.

<!-- req: P/02.1-R212 -->
The form of the value of a key (`worker.reads[]`, `secrets.reads[]` — `<family>/<name>`) is
the class `form`, not a relation of N1.4.

<!-- req: P/02.1-R213 -->
The class of a refusal is the layer where the
refusal is: `text`, `form`, `relations`, `catalogue`; the refusal word is `refused:<class>`; acceptance
checks the class (`classes.tsv`; judge-only: the class of each case).

<!-- req: P/02.1-R214 -->
The normative refusal catalogue of this chapter is [`forms/refusals.tsv`](../forms/refusals.tsv). The `chapter` and `row` columns are the stable address of a refusal; the form contains the codes, fixed words, diagnostic subjects, conditions and caller actions. This text does not repeat that catalogue.

<!-- req: P/02.1-R215 -->
There are no warnings. There is no list «accepted and ignored». There is no partially loaded manifest.

<!-- req: P/02.1-R218 -->
The loader does not judge the size of the files of `console.files`: it sees only the bytes of the manifest. The ceilings
`FILE_MAX`, `FILES_TOTAL_MAX` — [chapter 2.3](02.3-installer.norms.md) N1.5, N4.

## Implementation decides

The implementation is to name in its description:

1. **the libraries of the stack** ([the section «Form»](#form-built-from-the-standard-files)) for steps 1–3 of the procedure: a YAML 1.2 parser, a JSON Schema 2020-12 validator, CEL — pinned versions, and its own layers (`LAYERS.md`); the standard files themselves are a norm, not a choice; the judge sees only the verdict, the exit code and, for the cases with a class, the layer of the refusal of each file (P/02.1-R221, P/02.1-R222);
2. **how many form errors one refusal names** (the first one or all) — the path and the line in a refusal are a hint (N4); the judge compares the layer of the refusal, not the number of errors it names (P/02.1-R222, P/02.1-R223);
3. **the command that loads one file for acceptance**, by the section «Stand» of the common acceptance README: the runner calls it on every file of `verdicts.tsv` (judge-only: the verdict table of the chapter); exit code 0 — a manifest, any other — a refusal, the text of the refusal names the file.
4. **the internal contract of the manifest API**: read the row `platform/manifest/<sub>` into the canonical view
   ([P/02.2](02.2-installer.norms.md)), assemble and check the catalogue, `rev`, the outcomes and the refusals (the words —
   as in P/02, without retelling the norms) — an API of a library, not a move of P/02 into `common/`. The owner of lesson 02
   writes the description in the repository of the implementation before the library; the processes 03–10 read only the
   contract and the API; a mix of languages — through the store: the canonical view of the row is a norm of P/02.2. The judge does not call this API: it sees the bytes of the canonical view (the vectors `canonical`), the outcomes of `manifest put` (chapter 2.3 N5) and the verdicts of loading (P/02.1-R221).
