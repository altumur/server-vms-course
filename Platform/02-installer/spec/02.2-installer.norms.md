### N1.1 Projection

<!-- req: P/02.2-R005 -->
The canonical view of a manifest is the JCS bytes of the value that
is obtained from the tree of the accepted manifest (the loader of chapter 2.1, verdict `ok`) by the rules below, in order. The view depends only on the bytes of the manifest and the standard files of chapter 2.1 (the schema
`02.1-installer.schema.json`, the layer table `02.1-installer.layers.tsv`).

<!-- req: P/02.2-R007 -->
```yaml
sugar:                       # before defaults
  tables:   "[a, b] → {a: {}, b: {}}"
  bound_to: '"x" → ["x"]'
  in:       '"query" → ["query"]'
defaults:   default          # the annotation of the schema of chapter 2.1
computed:                    # after defaults
  P1 snapshot:            [<unit.fields>, state.<name>]
  P2 tables.<t>.journal:  {written: "<t>.written", deleted: "<t>.deleted"}
  P3 display.form:        [{fields: [<names of unit.fields>]}]
  P4 descriptor default:  null
  P5 decoded:             true
not:        [events.suppress.<kind>.by, display.section, display.general]
ordered:    x-ordered        # the mark of the layer table
scalars:    [integer, string, boolean]
notes:      []
```

<!-- req: P/02.2-R009 -->
`sugar` is a closed list of reductions to one form, applied before defaults. `sugar.tables`: a list of names `[a, b]` becomes `{a: {}, b: {}}`. `sugar.bound_to`: for a unit field and a table field, a single name `"x"` becomes `["x"]`. `sugar.in`: for an element of `secret_in` of the regex kind, a single word `"query"` becomes `["query"]`.

<!-- req: P/02.2-R012 -->
`defaults`: every key with the annotation `default` of the schema of chapter 2.1 is present explicitly — only inside a
  present parent or a parent with its own default. `defaults`: an absent section without default stays absent.

<!-- req: P/02.2-R014 -->
- `computed` is a closed list of the steps of lesson 2, applied after defaults.

<!-- req: P/02.2-R015 -->
- `P1 snapshot`: when there is no key `snapshot`, its value is the names of `unit.fields` in author order without
  `*_secret`, without `type: blob` and without `server`, then `state.<name>` of each `unit.state`, except `cursor`, in
  author order; a stated `[]` stays `[]`.

<!-- req: P/02.2-R016 -->
- `P2 tables.<t>.journal`: when it is absent, it is `{written: "<t>.written", deleted: "<t>.deleted"}`; when one key is
  given, the second is computed likewise.

<!-- req: P/02.2-R017 -->
- `P3 display.form`: when it is absent, it is `[{fields: [...]}]` with the names of `unit.fields` in author order, without `title`.

<!-- req: P/02.2-R018 -->
- `P4 descriptor default`: for a unit field and a table field, the `default` of the descriptor is the value said; when it
  is not said or `inherit` is said, it is `null` (for all types, `blob` included).

<!-- req: P/02.2-R019 -->
- `P5 decoded`: for an element of `secret_in` of the regex kind without `decoded`, `decoded` is `true` (P/06.2 N1.1).

<!-- req: P/02.2-R020 -->
- `not`: not substituted are `events.suppress.<kind>.by`, `display.section`, `display.general` and keys without the
  annotation `default` in the schema.

<!-- req: P/02.2-R021 -->
`ordered`: maps with the mark `x-ordered` of the layer table (`unit.fields`, `tables.<t>.fields`) are an array
  `{"name": <key>, …value}` in author order. `ordered`: other maps are objects; their order is JCS. `ordered`: a reader does not rely on author order outside `ordered`.

<!-- req: P/02.2-R024 -->
- `scalars`: JSON values are by the type of the schema place (integer — a number, an integer place — an integer after
  the reduction of layer 2: `4.0` → `4`; string — a string, boolean — `true`/`false`).

<!-- req: P/02.2-R025 -->
- `notes`: the view has no comments, no source text and no `x-*` marks.

### N1.2 View row

<!-- req: P/02.2-R026 -->
```yaml
platform/manifest/<sub>/canonical/<form>:   # the view row
  form:     decimal integer  # the number of the view form
  rev:      rev              # of the manifest row platform/manifest/<sub>
  sha256:   sha256           # of the manifest row (its field sha256)
  manifest: text             # the bytes of the view (N1.1)
ceiling:    max_value        # of the answer of GET /v1/status
window:     …/canonical/<form + 1>
```

<!-- req: P/02.2-R027 -->
There is one view row per subsystem and view form; the writer is the installer (N3). `form` is the number of the view form, a decimal integer ≥ 1; now 1 (key `…/canonical/1`). `rev` is the rev of the manifest row `platform/manifest/<sub>` from which the view is built (chapter 2.3 N1.5). `sha256` is the sha256 of the manifest row (its field `sha256`). `manifest` is the bytes of the view (N1.1) as text — JCS, UTF-8, without a final newline.

<!-- req: P/02.2-R032 -->
`ceiling`: the ceiling of the view row is the ceiling of a store row of P/01.1 N1 for this key; the sum of the manifest
  row and the view is not limited. `ceiling`: its source is the actual ceiling of the store: `max_value` of the answer of `GET /v1/status` (P/01.3 N2,
  OpenAPI 01 `StatusResponse`); 524288 is only the default of the daemon flag `-max-value`, not a constant of the
  installer; the installer has no ceiling setting of its own.

<!-- req: P/02.2-R034 -->
`window`: a change of the view form is a new form next to it (`…/canonical/<form + 1>`). `window`: during the change window the installer writes both forms.

<!-- req: P/02.2-R036 -->
The form of `manifest` itself is the view schema [`02.2-installer.view.schema.json`](02.2-installer.view.schema.json) (JSON Schema 2020-12;
the marks `x-step` — a projection step, `x-default` — the key is required by a default of the form, `x-unique-by` — the key of the elements of `ordered`;
[layers V7](../../common/LAYERS.md) § 3). The view schema is closed where the form is. In the view schema, keys with `default` are required.

<!-- req: P/02.2-R039 -->
- In the view schema, `ordered` is an array with a unique `name`.

The view form section below and the `canonical` vectors are built by the builder of the skill `lesson-spec`.

<!-- canonical:begin -->
### Form of the canonical view (built from the standard files)

The value `manifest` of the row `platform/manifest/<sub>/canonical/1` is a JSON (JCS, RFC 8785) of this form: the JSON Schema 2020-12 `02.2-installer.view.schema.json`. A map without author names is closed: there is no key outside the table. «Always present» — a key with a default of the form of the manifest (`default` of `02.1-installer.schema.json`) or by a step of the projection; «present if stated in the manifest» — a key without a default, its absence is the value. A map `x-ordered` of the form of the manifest is a list of objects `{name, …}` in the author's order. The rules and relations of the form of the manifest are not here: the installer has checked the accepted manifest.

### Data families (built from the standard files)

The form of the rows and objects that the chapter owns by the [catalog](../../common/data/catalog.tsv) is the JSON Schema 2020-12 of the family. An instance of a row is `{key, row}`, of an object `{key, object}`; the key is the grammar of the column `key` of the catalog. ## N3 Procedures

### build view(manifest bytes) → bytes | refusal

<!-- req: P/02.2-R042 -->
1. Load the bytes by chapter 2.1. If the load refuses, return that refusal of the load (the view is not built).

<!-- req: P/02.2-R043 -->
2. Let bytes be the result of sugar, defaults, computed, ordered, scalars of N1.1, applied in order, encoded by JCS.

<!-- req: P/02.2-R044 -->
3. If the view row {form, rev, sha256, manifest} is heavier than the ceiling of N1.2 (`max_value` read by the caller),
   return `toolarge` of the view (N4). `rev` is the final new rev chosen by the caller (chapter 2.3 N3 step 14a), not an earlier estimate.

<!-- req: P/02.2-R046 -->
4. Return bytes.

### installer `manifest put` — writing the view

<!-- req: P/02.2-R047 -->
The view is built before any write.

<!-- req: P/02.2-R048 -->
The order of the steps is [chapter 2.3](02.3-installer.norms.md) N3 «Manifest change» (the installer):

<!-- req: P/02.2-R050 -->
1. Read the ceiling: `GET /v1/status` → `max_value`. If the store did not answer, answered not 200, or answered without
   `max_value`, refuse the whole installation: nothing is written, exit code 2 (chapter 2.3 N4).

<!-- req: P/02.2-R051 -->
2. Build the view (above) for the new rev. First choose the final new rev (after reading the row, chapter 2.3 N3 steps 9–14a), then
   check the weight of the view row with exactly that rev, then write the parts and the row. On `toolarge` of the view, refuse the whole
   installation: nothing is written, exit code 2; stderr names the file, the view key, the weight and the ceiling. A `cas` conflict that changes the new rev repeats this check before any further write.

<!-- req: P/02.2-R054 -->
3. «Unchanged» means: the row is the same (yaml, shell, files by value) AND the view of the current form is present, readable and equal to
   the projection; otherwise write.

<!-- req: P/02.2-R055 -->
4. The order of writes: the manifest row → the view (`cas` by the version of the view read, or `""`) → the mark last.

<!-- req: P/02.2-R060 -->
5. If the view is not written because of a `cas` conflict, re-read the row and the view: 1. If the rev of the row is mine, repeat the `cas` of the view. 2. If the rev of the row is already another one (another installer wrote a newer one), run the procedure again from
      reading the row (my file — a new rev or «unchanged»; a new rev — with the weight check of item 2 for that rev). The view of the former rev is not written: the view always carries the rev of the current row. 3. If the row is already written, the mark does not move until the view is written.

<!-- req: P/02.2-R061 -->
A cluster of one process with a built-in manifest writes the view by the same rule ([P/02.4](02.4-installer.norms.md) N1.10).

### Reader

<!-- req: P/02.2-R062 -->
A reader of the view is a process that has moved over to the view by its own change of behaviour; it acts as follows:

<!-- req: P/02.2-R064 -->
1. Read the mark, then the view of its own form. 2. If the view is absent, or it is readable and its rev ≠ the rev of the mark, this is the installation window (the view is written with rev N, the mark is still
   N − 1, or the view of a new rev is not written yet): repeat step 1 with a pause of 1 s, within `START_WAIT` of chapter 2.3 N3 «Process start». An unconfirmed read of the mark or of the view (the store did not answer) is repeated the same way. If they still do not match at the end of `START_WAIT`: the refusal «not published» — do not start, exit code 1; the supervisor
   restarts the process (the temporary outcome of chapter 2.3 N3 «Process start»).

<!-- req: P/02.2-R067 -->
3. If the view is not readable (out of the form of its family), or its rev equals the rev of the mark but its sha256 ≠ the sha256 of
   the mark, or manifest does not pass the built schema: the refusal «corruption» — act as for an unreadable manifest (chapter 2.3 N3
   «Process start»): do not start, exit code 2, without a restart.

<!-- req: P/02.2-R068 -->
   For a running process, the refusal «corruption» acts as for a mark not in form.

<!-- req: P/02.2-R069 -->
4. Otherwise the reader's manifest is the value of manifest; the YAML loader is not needed.

<!-- req: P/02.2-R070 -->
The reader decides between «not published» and «corruption» before its doors open. While the reader repeats, it serves nothing.

<!-- req: P/02.2-R072 -->
Until its own change, the reader runs the loader by chapter 2.3 N3; it does not read the view.

<!-- req: P/02.2-R073 -->
**Races.** The view is written after the row and before the mark: running processes see the change by the mark, when the row
and the view are already written.

<!-- req: P/02.2-R074 -->
A starting process, having read the mark, reads the row and the view of the same `rev`
(otherwise it repeats by N3 «Reader» until the mark has the rev of the view).

<!-- req: P/02.2-R075 -->
Two installers of one name: the `cas` of the row (chapter 2.3 «Races»), then
the `cas` of the view; the loser re-reads.

## Implementation decides

1. How to build the view (its own pass over the loader's tree or common code) — the bytes must match the vectors `canonical`.
2. When a reader moves over to the view — its change of behaviour; before it — the loader. What the stand sees does not depend on the moment: the start ends with code 1 (the read is not confirmed or the view is not published within `START_WAIT`) or with code 2 (a refused or corrupt manifest) by P/02.3-R065, P/02.3-R068, P/02.2-R064, P/02.2-R067; the moment of the move itself is checked by reading (P/02.2-06).
