## Подготовка каждого сценария

Тринадцать сценариев независимы. Перед каждым остановить и дождаться всех процессов прошлого
сценария, создать изолированные каталоги/порты и пустое хранилище: строки, объекты,
память id хранилища отсутствуют. Очистить дерево событий, зеркала и кэш индекса, переменные и ключи повторов раннера.
Установить актуальную testsub из общих testdata с её служебной меткой административными
правами. Единиц и пользовательских строк ещё нет. Подготовка — не перенос состояния
предыдущего сценария и не проверка установщика.

Запустить хранилище, новую консоль testsub и ресурс srv-a по разделу «Стенд» общего README приёмки. Их двери должны быть готовы;
ресурс зарегистрирован и доступен консоли до первого шага. Сц. `09-resource-door`, `16-presence-lock` и 17–23 ресурс до первого
шага не запускают: его поднимает шаг 1 (`@start resource`; у сц. 17 и 18 — шаг 2). Все процессы этой коробки
используют одну BOX_ID и server=srv-a; каждый новый процесс получает новый instance.
Контроллера нет; воркеров нет, кроме `w-1` (`testsub`) сц. 16-presence-lock и 19-service-names и `t-srv-a-2`, `t-1`, `t-srv-a-1` (`testsub2`)
сц. 20-door-room, которых запускают их шаги. platform/mirror и platform/space не заданы; запросы освобождения и копии не готовятся.
Сборка — схема 1.

Сц. `20-door-room` и `23-object-ceiling` ставят каталог `testsub` и `testsub2` так же, как `10-body-copy` (порядок — «Стенд»).
Сц. `10-body-copy` (копия тела у ресурса, из М10/10; T10, T11) ставит каталог `testsub` и `testsub2` (порядок — «Стенд»;
`testsub2` объявляет blob-поле, `testsub` — нет), ресурс запускает шагом 1 (`@start resource`); дверь ресурса `resource` с
допустимой личностью соседа; дайджест `sha256-190267417aed…` — байтов `peer-copy`. Консоль и контроллер ему не нужны.

console — дверь консоли testsub с петли, доступ к операциям и единицам разрешён (консоли нужны шаги 02/6, 8, 12–16, 08/14 —
та же дверь у слияния, и 09-resource-door/6–7 — `/servers`, `/metrics`; консоль — [P/06](../../06-console/06-console.md));
resource — дверь ресурса srv-a с допустимой личностью; store — дверь хранилища с чтением
testsub/ и `platform/doors/`; admin — дверь `admin.sock` (строка `platform/schema` сц. 17, её пишет консоль ролью admin, P/06.6 Н1.1а). Если развёртывание использует TLS, выдать соответствующие
сертификаты и роли по P/02.4 Н1.6 (`w2c-ca.sh issue <server> <роль>`, комплект `kit`) и правилу адреса P/02.4 Н1.6;

## Аудит покрытия (сц. 17–23)

Сценарии аудита покрытия P/05 (2026-10-30); каждое ожидание — из нормы:

- сц. 17-schema-refusal — проверка схемы при старте (Н3 «старт ресурса — проверка схемы»; [договор схемы](../../common/contracts/schema.md)
  «Проверка при старте», «Граница»): `platform/schema` с `version` 2 (выше SCHEMA 1) и `x` (не целое) — `@start resource`
  выходит с кодом 2; строки двери `platform/doors/srv-a` нет — проверка схемы идёт до первой записи (lifecycle «Порядок
  старта»); с `version` 1 — ресурс стартует и пишет строку двери. Строку пишет дверь `admin` (писатель — консоль ролью admin,
  P/06.6 Н1.1а); значения строки хранилища — строки (P/01.1);
- сц. 18-schema-read-wait — ошибка чтения `platform/schema` — «ждать доступности, не начиная работы», не код 2 (договор
  схемы): `@cut role resource store` до старта — хранилище молчит ресурсу (соединения сокета роли `resource` висят без
  ответа); `@mend` закрывает висевшие соединения — ресурс получает ошибку чтения и, не выходя, читает снова: строка двери
  появляется без нового `@start` (срок 90 с — повтор чтения нормой не ограничен по шагу). Ресурс, вышедший на ошибке
  чтения, строки двери не напишет;
- сц. 19-service-names — служебные имена (Н1.1 `disk`; [договор журнала событий](../../common/contracts/event-journal.md)
  «Имена файлов в общих деревьях»): запись пульса воркера `w-1` идёт temp + rename под замком каталога
  `objects/testsub/heartbeats/~lock`, файл замка не удаляется; обход дерева пропускает имена с `~` — в листинге ключа
  `testsub/heartbeats/~lock` нет; ключ `~lock` кодируется в `%7elock` — чтение ключа — 404, не файл замка (служебное имя с
  ключом не совпадёт). Пульс `w-1` в листинге — контроль, что каталог тот самый;
- сц. 20-door-room — пульс ресурса (Н1.4 `heartbeat`): поле `door` с `addr` и `mode` (`loopback` без `RESOURCE_TLS`, `mtls`
  с ним — «Стенд» `RESOURCE_TLS` не ставит, ветвь `mtls` — для развёртывания с TLS); строка двери (Н1.4 `door_row`,
  [договор замка присутствия](../../common/contracts/presence-lock.md) «Счёт `room`»): у `testsub2` (`grows: true`, файл роли
  `testsub2worker.env` с `HOST_MEMORY_MB=4096`, `WORKER_MEMORY_MB=256` кладёт раннер — «Стенд») `room` =
  min(16 − живые, 98 − живые с номером n ≥ 2): без воркеров — 16 и `live` ""; `t-srv-a-2` (n = 2) — 15 и "2"; `t-1`
  (имя без сервера — без номера, [договор имени слота](../../common/contracts/slot-name.md) «Имя процесса роли и его номер»)
  — 14, в `live` не входит; `t-srv-a-1` (n = 1, базовый) — 13, в `live` не входит. У `testsub` файла роли нет — элементов
  `room.testsub`, `live.testsub` нет, они не ожидаются;
- сц. 21-events-wait — подсказка (Н1.6): под `want` строк нет — ожидание отвечает по сроку `{changed: false, seq}`; строка
  `testsub/c1` вида `probe.tick` дописана — `since=0` («у клиента нет позиции») отвечает сразу `{changed: true, seq,
  touched}` с ровно этой тройкой; `seq` монотонен (`ASSERT $s1 <= $s2`); курсор `since=seq` без новых строк — снова
  `changed: false`. Исходы `full`, `replaced` и вытеснение требуют параллельных ожиданий — вне TSV;
- сц. 22-torn-tail — порванный хвост (Н1.3 «Нечитаемая строка бакета», Н3 «запрос» шаг 3; договор журнала событий `torn`;
  договор слияния журнала событий `partial`): целая строка отдаётся, `truncated` 0; хвост без LF — даже разбираемый JSON — не
  строка: не в `events` и не в `truncated`, ответ `partial: true`, `lines_garbled` нет (поле — только когда больше 0). Хвост
  пишется последним: следующая дописка склеилась бы с ним;
- сц. 23-object-ceiling — потолок двери ресурса (Н1.1 «Потолки ресурса», Н2 `PUT /v1/objects/<sub>/blobs/<digest>`, Н4):

## Сравнение

Формы ожидания — по словарю. Ожидание одного кода не требует пустого тела.
Повтор переменной внутри expect сравнивает её временное значение. Директивы не отправляются
серверу как HTTP. Полный ответ дополнительно проверяется по контракту его владельца:
хранилище — P/01.1, двери ресурса — Н2 урока, консоль — [P/06](../../06-console/spec/06-console.api.openapi.yaml) (главы 6.4, 6.5).

## Свидетельства вне TSV

Это задания реализации/стенда, а не уже выполненные проверки:

| Область | Контрпример и требуемое наблюдение |
|---|---|
| Объекты | Равный written, один сервер молчит: выбор имени, missing и 404 без ложной полноты; запрещённые ключи и строки-объекты не выданы; GET объекта больше 64 МиБ (положенного мимо двери) — 413 ResourceError до успешных заголовков (копия тела ровно 64 МиБ и +1 байт у двери — сц. 23) |
| События | Два процесса на разных коробках и перезапуск: id различны. Оба класса, of, защищённые поля; fsync подтверждён барьером |
| Индекс | Порванный хвост — сц. 22. Пустой/вытесненный кэш сохраняет ответ при неизменных файлах; границы from/to/limit и приоритет тревог |
| Wait | Исходы `full` и `replaced` (`changed` и срок — сц. 21), неверные/повторные параметры и границы. Два CN с одним client не вытесняют друг друга; после рестарта/full остаётся обычный проход |
| Потоки | JSONL без массива; 200/206/416; обрыв файла. PUT зеркала: плохая сумма, 64 MiB и +1 байт, срок, ошибка публикации: нет частичной копии, прежняя цела |
| Retention/holds | Отсутствие и неизвестное чтение различаются; неверный days/нечитаемые holds не разрешают удалить дерево. Окно удержания (функция удержания — векторы [`holds`](../../common/vectors/holds/README.md)), пол срока отметок и час зеркала |
| Свободное место | После смены free_ask на обычную просьбу с тем же rid удаление CAS конфликтует, просьба цела. freeing не включает уже отражённое измерением освобождение |

Чтение ветвей и схема подтверждают только соответствующий порядок/форму. Таймеры,
процессы, барьеры файлов, сетевые обрывы и криптографическая личность требуют отдельных
наблюдений. Надгробия и схождение копий тел (Н1.1 «Надгробия») и `restore` (Н1.4 «Восстановление бакетов») — стенд
с двумя ресурсами, сценария нет.

Restore: полный пустой перечень, подтверждённое отсутствие копий, 500 каталога и оборванный ответ различаются; два
последних оставляют восстановление неполным и повторяются по Н1.4. INSTANCE_ID новым процессом не переиспользуется.
Дополнительные пробы вне TSV.

Проверить id на коллизии составных имён a-e1-j/node:1:aaaaaa и a/j-e1-node:1:aaaaaa, UTF-8, разные деревья/эпохи/параллельные номера, перезапуск и итог подавления; копии сохраняют исходный id. Для обоих перечней buckets/mirrored: отсутствующий, пустой известный и нечитаемый каталог различаются; ошибка до заголовков — 500 без тела, обрыв не даёт полного ответа. Дополнительные пробы вне TSV.

Дополнительная проверка чтением R36-07: пары server=a-b/volume=c и server=a/volume=b_c имеют разные ключи; volume=b-c вне профиля requests.free и диагностируется без записи. Проверить длины volume 0/1/64/65, разрешённые ASCII и не-ASCII; при чтении существующей строки отсутствие unit недостаточно — server/volume обязаны совпасть. Обновление и удаление используют CAS именно проверенной версии; строка другого владельца не меняется. Текущая TSV эти конфигурации томов не запускает.

Чтением (прогон 36, Kimi): PULSE_LIMIT — объявленный конечный положительный профиль; превышение диагностическое. Листинг объектов имеет оба 403.

Каждый записывающий участник кодирует имена файлов сам (договор журнала событий «Имена файлов в общих деревьях»): любое разрешённое имя представимо, разные ключи — разные пути, включая временные имена и зеркала (R37, Codex).
