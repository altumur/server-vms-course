## Стенд

**Подготовка каждого сценария** (из README приёмки М11/03, «Подготовка каждого сценария 01–09»). Раннер поднимает на
одной машине три кластера — `hold`, `m1`, `m2`: у каждого своё пустое хранилище, свой `{data}`, свои сокеты ролей и
порты консоли и ресурса, своё кольцо (P/06.2 Н1.2), каталог манифестов — только `testsub`; консоль, контроллер и воркер `w-1`
`testsub`, ресурс своего сервера (`srv-hold`, `srv-m1`, `srv-m2`). Единиц нет. Домена нет: его ставят шаги сценария
(`@install domain`, `@start domain`, `@start agent`) или директива `@domain`. Имя домена — `acme`; файл восстановления
установки — `{recovery}` в каталоге экземпляра.

- `store` у `member <кластер>` — дверь хранилища кластера через `admin.sock` (подготовка и наблюдение строк домена).
- `resource` без префикса — дверь ресурса `hold`: через неё читаются объекты держателя `domain/members/<член>/…`.
- Часы не ускорять: LOST_AFTER 45 с, REPORT_EVERY 5 с, MARK_REFRESH 22,5 с; сроки `@until` взяты с запасом.

**Сценарии 15, 16** (из README приёмки М11/04), **21 и 25**: кластеров четыре — `hold`, `m1`, `m2`, `relay`. Агент `relay` всегда
открывает дверь ретранслятора (`RELAY=1`, `{relay_port}`); директивы `@domain <кластеры>`, `@start agent <кластер> via
relay`, `@stop agent`. Топология пуста до шага, который её пишет.

**Сценарии 20–22** (аудит покрытия P/08, audit-kimi 1e9929d51) — поля вида главы 8.1 на стенде:
- сц. 20 — `trust` и `topology` вида ([глава 8.1](../../spec/08.1-domain.norms.md) Н1.2а, Н1.6а): до записи топологии —
  ровно `{rev: 0, star: [], via: {}}`; `trust.rev` — тот же `rev` набора, что `reports.<член>.keys_rev` после `@domain`
  (готовность `@domain` — каждый член держит набор держателя); записанная топология видна в виде следующим проходом
  (`@until`). `m2` в `via` не ретранслятор — отказов Н1.2 нет; прямой отчёт `m1` — вторая дорога (Н1.3а).
- сц. 21 — `relay_refused` (Н1.6а): метка `m1` у держателя испорчена (`@stop domain`, затем `@on hold @spoil object` — писатель
  метки остановлен, — `@start domain`), и каждый пакет `relay` с `m1` получает `refused` «unavailable» (Н3 «держатель на
  POST /api/relay» шаг 2) — запись ретранслятора в виде устойчива; топология без `via` — ретранслятор узнаёт из ответа
  `relay_for: []`, следующий пакет пуст и принят — запись снята. Поле `relay_refused` в форме вида необязательно, поэтому шаг
  11 принимает `{}` или отсутствие поля (`@oneof`); ключа `relay` нет ни в одной ветви.
- сц. 22 — метка `domain/members/m1/reported` с `rev` 2^53 (9007199254740992, на единицу выше `pos53`), положенная мимо
  писателя при остановленном агенте `m1`: член `silent`, вид неполон полем (`complete: false`). Строгое чтение — метка не по
  форме ([исходы семьи](../../data/member-reported.outcomes.tsv): копии нет, член `silent`); нестрогое — поколения
  `reports/9007199254740992` нет и `sha256` чужой (глава 8.1 Н3 шаг 2) — тот же `silent`. `@until 10`: метка `m1`
  моложе `MARK_REFRESH` + `REPORT_EVERY` на момент остановки, и до LOST_AFTER (45 с) молчание по сроку не наступает —
  `silent` даёт только подмена.

**Сценарий 04** (из README приёмки М11/08): агенту `m1` даётся каталог TLS `inputs/kit-m1-one/` (только `ca.pem`
центра A), затем `inputs/kit-m1-two/` (`ca.pem` A и `ca.next.pem` B), затем переменная снимается (`@env m1
W2C_TLS_DIR=…`, `@env m1 W2C_TLS_DIR`; значение `inputs/…` — путь от этого каталога). Двери стенда TLS не говорят: агент
лишь публикует отпечатки и сертификаты центров (Н1.6 `tls_ca`, `tls_ca_certs`). Отпечатки в ожиданиях — sha256 DER этих
файлов: A — `d72f9e5e…68a6`, B — `6fefd57b…e217`. Шаг 4 — строка `domain/members/m1/ca-certs` записана до `Entry.ca` (шаг
3 уже видит отпечаток), шаг 18 — снятие администратором удалило её. Шаги 10–11 проверяют, что правка администратора без
смены центров у члена переписывается его следующим отчётом. Шаги 14–16 — два прохода агента (`REPORT_EVERY` 5 с) без
`tls_ca`: отпечатки не снимаются. Как раннер передаёт окружение и перезапускает консоль и агента кластера с переменной
(`@env`) — словарь «Стенда домена» [общего README приёмки](../../../common/acceptance/README.md), `@env` и «Окружение
пересылки» (разбор ревью стадии B 8–10, № 22: М-16).

**Сценарий 19** — сосед на стенде: дверь `GET /domain/members` консоли домена ([урок P/10](../../../10-domain-console/spec/10-domain-console.norms.md)
Н1.2б, P/10-07; C10-MEMBERS-SOURCE-01, C10-MEMBERS-KNOCKING-ABSENT-01). Процесс `domain` остановлен (шаг 2), чтобы проход
держателя не переписал вид; на его место кладётся вид `inputs/view-member-list-ghost.json`: в `member_list` — `hold` и
посторонний `ghost`, поля `knocking` нет (шаг 3). Шаг 4 показывает, что консоль домена читает этот вид. Шаг 5: `members` —
doc строки `domain/members` (`hold`, `m1`, `m2`, без `ghost`), а не `member_list` вида; поля `knocking` в читаемом виде нет —
`knocking: []`.

**Сценарий 17** (из README приёмки М11/12): агент `m1` держит список — ответ держателя без `members`. Принят `m2` — копия
списка у `m1` с ним (список пришёл один раз), затем ответ снова без `members`. Раннер ходит человеком `root`
(урок P/08, глава 8.4); ожидание `@carry` — `ok <JSON>`, подмножество полей.

## scenarios.tsv

Формат — словарь «Стенда» общего README приёмки и раздел «Стенд домена». `$fp1`, `$fp2` — отпечатки, которые раннер
связывает из `knocking` и подставляет в приём: так стенд повторяет то, что делает человек, сверяя отпечаток с журналом
агента; `$kr` (сц. 20) — `rev` набора из `trust` вида. Всего 18 сценариев / 165 шагов.

Сц. 18 (C08-G06): дверь `signer` шлёт процессу `domain` пакет `POST /api/relay/m9` с `{"relayed": {}}` без подписи — `m9`
не член: 404 раньше проверки подписи и без стука (P/08.3 Н2, порядок строки `POST /api/relay`).

Потерю памяти держателя (409 `rebase`) стенд не вызывает: её проверяют векторы `accept` и чтение договора приёма отчёта.

Мутационная проверка 2026-10-18 (разбор прогона 41, «Мутации»): сценарий 14 — стук незнакомца без верной подписи (часы
агента на 400 с вперёд, вне `MEMBER_WINDOW`) не попадает в `knocking`, с верной — попадает (Н2: подпись ключом из тела,
401 — без стука).

Сц. 03 не зависит от момента резервной копии (глава 8.8: `first`, `BACKUP_EVERY`): член `m1` — хранитель, и
`domain/backup-taken` в его отчёте даёт своё поколение в любой момент прогона. Поэтому шаг 5 ждёт у `m1` сам объект
`testsub/snapshot/w-1` (размещение `c3`), шаги 6–9 — две смены отметки круга отчёта `sent_at`, связанной после снимка
(два прохода агента: одна смена может принадлежать кругу, бывшему в полёте), и только шаг 10 берёт последнее поколение: в
нём снимок есть при любом числе поколений между ними (поколение несёт все объекты члена, Н1.3).

**Сценарии 23–26** (аудит покрытия P/08, второй проход Gemini, черновик G03 `e32df6f8b`, переписан):
- сц. 23 — повтор приёма (Н3 «принять члена» шаг 1, D20): стенд поднимается вручную, как сц. 01; шаг 5 ждёт и `key`
  держателя в списке — дальше список сам не переписывается, и `rev` после приёма (`$r1`) не меняется. Тот же отпечаток —
  200 без записи (тот же `rev`, шаг 9 читает его снова); иной — 409 «… was admitted with another key: have it leave first»;
  `m2` без агента не стучится — 404.
- сц. 24 — `POST /domain/members/<член>/ca` (Н1.6 `admin`): список не по возрастанию записывается по возрастанию; тот же
  список снова — новая запись (`rev` растёт). Комплекта TLS у агента `m1` нет — `on_accept` правку не переписывает.
- сц. 25 — снятие центра и маршрута правкой топологии (Н1.2 `centre`, `put_order`): `centre: ""` и `via: {"m1": ""}`
  снимают центр и маршрут; `centre: null` — тоже.
- сц. 26 — строка `domain/topology` испорчена мимо двери (`doc` не JSON): `PUT` — 503 `unavailable`, строка прежняя (правка
  частичная и против `base_rev`, без чтения её не исполнить; C08-TOPOLOGY-PUT-UNREADABLE-01), `GET` — тоже 503 (P/10 Н1.2в).

Не взяты из черновика G03: 503 шага 0 «принять члена» при нечитаемом `domain/view` — объект вида переписывает проход
держателя раз в `VIEW_EVERY` (3 с), окно порчи стенд не удержит (гонка, чтением; при остановленном `domain` двери нет);
отказ двери агента при нечитаемом `domain/revoked` (C08-CARRY-UNREADABLE-01) —
`@carry` видит только ответ 200, а `silent` через LOST_AFTER не отличает причину (чтением). Ожидание черновика `star: []`
после `centre: ""` без `star` в теле неверно: не указанное поле — прежнее, звезда без центра — 409.

## Сны (`@sleep`, ADR-0080 доп. (17) п. 4)

Ожидание события — `@until`: сц. 03 шаги 6–9 ждут двух кругов отчёта после снимка (`sent_at` сменился дважды; по `rev`
поколение не различить — ревью стадии B 1–2, п. 1); сц. 17 шаги 2 и 8 — списка членов у `m1`; сц. 20 шаг 5, сц. 21
шаги 5, 9, 11, сц. 22 шаг 4 — следующего прохода вида (`VIEW_EVERY` 3 с). Оставшиеся сны:

| Сц./шаг | Сон | Причина |
|---|---|---|
| 03/2 | 20 с | время перед действием: отчёты после `@domain` затихли — `$r1` и шаг 3 читают одно поколение (тишину не наблюдать) |
| 03/14 | 20 с | время перед действием: тишина отчётов перед связыванием `$r3` — шаг 16 ждёт повторной отправки того же поколения; счётчик `c3` заведён с `step: 0` (шаг 4): учебный обработчик пишет `n` в `status` пульса (P/03.4 Н1.1), а сравнение вклада исключает только `ts` (P/09.1 Н1.2 `change`) — тикающий счётчик законно давал бы новое поколение каждый круг (C08-REPORT-STEADY-COUNTER-01) |
| 04/15 | 12 с | отсутствие: без каталога `W2C_TLS_DIR` поле `ca` члена не снимается — два прохода агента (`REPORT_EVERY` 5 с) |
| 05/3 | 60 с | домен полон и отсутствие: часы `m1` на 100 с позади не делают его молчащим за срок (не одно событие — `@until` прошёл бы до первого отчёта с этими часами) |
| 14/5 | 10 с | отсутствие: стук без верной подписи не принят — агент стучится раз в `REPORT_EVERY` 5 с, два прохода |
| 17/3, 17/9 | 10 с | время перед действием, круг не наблюдаем: `@carry` читает ответ того же круга — держатель узнаёт из следующего отчёта `m1`, что список у него свежий (`REPORT_EVERY` 5 с и проход); шаги 2 и 8 ждут списка у `m1` (`@until`) |
