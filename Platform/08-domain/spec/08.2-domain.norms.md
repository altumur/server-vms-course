### N1.2 The key set `domain/keys`

<!-- req: P/08.2-R042 -->
The form of the row and of the set document (`row`, `doc`, `writer_forms`) and the rule «only forward» (`only_forward`) — the [domain key set
contract](../../common/contracts/keys.md) «The set `domain/keys`» (the owner is this chapter). Here — the `rev` of the writer:

<!-- req: P/08.2-R004 -->
```yaml
rev:               max(rev of the set that the signer holds + 1, whole wall-clock seconds of the signer)
  emergency:       max(the greatest known rev + 1, floor(now) + TOKEN_SKEW + 1)
  clocks:          the wall clocks of the holders of the domain differ by at most TOKEN_SKEW
```

`rev` of an ordinary and a planned change (token key, book_seal) — max(rev of the set that the signer holds
+ 1, whole wall-clock seconds of the signer).

<!-- req: P/08.2-R043 -->
In an ordinary and a planned change (token key, book_seal), if rev + 1 is greater than the wall-clock seconds, the change waits until
the clock catches up with it: rev does not overtake the wall clock of the signer.

<!-- req: P/08.2-R044 -->
`rev.emergency`: the `rev` of an emergency change — after theft (N3) and a move without the former holder (chapter 8.8 N1.8) — is max(the greatest known rev + 1, floor(now) + TOKEN_SKEW + 1). The known rev of `rev.emergency` — the sets of the answers of neighbours and its own domain/keys, checked by the root, including one not confirmed by its own term record (chapter 8.8 N1.8 step 5).

<!-- req: P/08.2-R046 -->
`rev.clocks`: premise: the wall clocks of the holders of the domain differ by at most TOKEN_SKEW; under it the emergency set is newer than any set that the former holder issued.

<!-- req: P/08.2-R047 -->
The set is what a member trusts without a connection: the token keys of the holder, the revocations and the book acceptance key. Without the set the member has no domain (the gate [P/06.3](../../06-console/spec/06.3-console.norms.md) N1.3, N1.8).

<!-- req: P/08.2-R049 -->
The field of the view `domain/view.trust` (the set that the holder trusts: `rev`, the fingerprints of `root` and `book_seal` by N1.1) —
[chapter 8.1](08.1-domain.norms.md) N1.2a (P/08.1-11).

<!-- req: P/08.2-R050 -->
**Representability of an emergency revision.** Compute the emergency revision candidate exactly before any publication. The upper bound of the candidate is the existing `common.pos53` bound of the [keys family](../data/keys.schema.json); neither operand may wrap, round or saturate. If the candidate is outside that form, no set, signing key, seed, term or member entry is written. For a candidate outside that form, the signer operation uses its existing nonzero refusal exit; the move uses its existing failed-restoration response, without publishing a partial change.

<!-- req: P/08.2-R054 -->
Equality and `only_forward` checks, signatures and the term guard are unchanged by the representability check.

### N1.7 The offline revocation window

<!-- req: P/08.2-R009 -->
The checker decides by its own set and its own copy of `domain/revoked` by its own wall clock; the check needs no connection
with the holder.

<!-- req: P/08.2-R079 -->
Therefore a revocation does not arrive instantly, and the norm names the limits by number:

| What is revoked | Accepted no longer than | Whose clock |
|---|---|---|
| a token (`jti` in `domain/revoked`) | `min(exp + TOKEN_SKEW, delivery of domain/revoked to the checker)`; offline — `exp + 60`, that is `lifetime + 60` from the issue; in `testsub*` the longest kind is `testsub2` `feed: 600` → 660 s | the wall clock of the checker |
| a former token key after the planned change | until the `until` of its set (`OLD_KEYS` = 3600 s from the change); only for the kinds `keep` — until `keep_until` (`KEEP_OLD`) | the wall clock of the checker |
| a stolen current token key (current has no `until`) | **until the first set accepted by the checker in which this key is absent** (the change after theft, N3): the thief issues new tokens, and an offline member accepts them; this window is not bounded by a term | — |
| a member key (`revoked_members`) | the holder refuses right after its own set (chapter 8.3); an offline member does not revoke itself | — |

<!-- req: P/08.2-R080 -->
The delivery named in the table above, at a member, is with the answer of the holder to the agent (chapter 8.3; the agent applies it — chapter 9.1); at the cluster of the holder — a write into
its own store.

### N1.6a Tokens `keep`: the memory of the domain and revocation

<!-- req: P/08.2-R010 -->
```yaml
domain/issued/<sub>/<kind>/<sha16(ref)>: {ref, jti, exp, member, at}    # at the holder
why:        the domain does not remember issued tokens
jti:        constant for the target
order:      under the shared side of the lock P/08.8 N1.7 step 1
door:       DELETE /domain/issued/<sub>/<kind>/<ref>
loss:       a limit
state:      the family is in the state of the backup
limits:     the reserve of 80 % is shared by all people
limit:      the row domain/revoked — 524288 bytes, a record 28 bytes
```

The row `domain/issued/<sub>/<kind>/<sha16(ref)>` is at the holder; the writer is the process domain at the issue of a kind with keep: true, CAS.

<!-- req: P/08.2-R081 -->
`why`: the domain does not remember issued tokens: the thief holds a token, and there is nothing to revoke it by, POST /domain/revoke accepts only the token itself. The row `domain/issued` is per target, not per issue: it grows with the number of cameras, not with the number of issues.

<!-- req: P/08.2-R083 -->
`jti`: the jti of a kind with keep: true is constant for the target: the issue takes jti from the row. `jti`: if there is no row `domain/issued` or its jti is in domain/revoked — the issue takes a new random one, the row is rewritten.

<!-- req: P/08.2-R085 -->
A request with the word `revoked: <jti>` — the recipient refused this token with revoked, while the holder may not know of the revocation (a copy older than DELETE). If the word revoked equals the jti of the row `domain/issued`: this jti is put with the exp of the row into domain/revoked, in one batch with the new row, a new jti is issued.

<!-- req: P/08.2-R087 -->
If the word revoked is not equal to the jti of the row: the row has already changed, the request is ordinary, the jti of the row is taken: otherwise two executors of the target would extinguish the tokens of each other up to the ceiling of the row. A forgery of an equal word extinguishes only the tokens of the target itself, of an unequal one — nothing, it does not take the token of the thief out from under the revocation.

<!-- req: P/08.2-R089 -->
REVOKED_WORDS: executed words from a member per day, REVOKED_WORDS_CAMERA for class camera, REVOKED_WORDS_SERVER for class server, the count is in the memory of the process domain. Above REVOKED_WORDS the request is ordinary, journal domain.revoked.word_limit.

<!-- req: P/08.2-R091 -->
When the row domain/revoked is 80 % full, the word is not executed at all, the remainder is only for people (DELETE, POST /domain/revoke with a token person): a record lives up to 10 years, and otherwise the word would use up the ceiling. A limit: with the row 80 % full, a copy older than DELETE gives a circle of refusals of one target, the operator removes it with the same DELETE of the target, the journal domain.revoked.word_limit shows this; an ordinary DELETE removes the row, the next issue gets a new jti, the word is not needed.

<!-- req: P/08.2-R093 -->
Nobody relies on the uniqueness of jti: door.pass and tickets are only at the sessions person.

<!-- req: P/08.2-R094 -->
`order`: the freeze check and the CAS of the row — under the shared side of the lock P/08.8 N1.7 step 1: an issue in flight either landed before the copy or gets frozen, otherwise DELETE on the target would not have reached it.

<!-- req: P/08.2-R095 -->
`order`: at the issue of a kind with keep: true, e = now + lifetime is computed once before the CAS, the row — max(former exp, e), the token — e: always not older than the row.

<!-- req: P/08.2-R096 -->
`order`: at the issue of a kind with keep: true, the signature of the token only after a successful CAS of the row, creation or extension. `order`: at the issue of a kind with keep: true, the loser of the CAS of the row re-reads and takes the jti of the winner, a conflict — up to 3 times, as with revocation, then 503 unavailable.

<!-- req: P/08.2-R098 -->
`order`: at the issue of a kind with keep: true, if domain/revoked is not read — 503 unavailable: a row with a possibly revoked jti is not taken.

<!-- req: P/08.2-R099 -->
`order`: the exp of the row `domain/issued` is the greatest of the former and the new, otherwise prune would remove the revocation before the live token.

<!-- req: P/08.2-R100 -->
`order`: two executors of one ref and another member share the jti of a kind with keep: true: a revocation closes both.

<!-- req: P/08.2-R104 -->
`door`: `DELETE /domain/issued/<sub>/<kind>/<ref>` at the domain console: admin of the domain. At DELETE /domain/issued the write of the jti with the greatest exp into domain/revoked and the removal of the row — in one batch; 200 `{revoked: <jti>}`. At DELETE /domain/issued there is no row — 404. At DELETE /domain/issued the row domain/revoked is full (the record does not fit under the ceiling limit) — 409 {error: "too many revocations"}: nothing is written, the row domain/issued stays, the token is not revoked.

<!-- req: P/08.2-R105 -->
A revocation closes all tokens of the target, old and new; the box gets a refusal when the revocations reach the cluster of the write.

<!-- req: P/08.2-R106 -->
`loss`: a copy older than the first issue or than a change of jti (with a live new jti DELETE closes the former one), a move «from nothing» (from nothing), an unreadable row: a new issue gets a new jti, the old token is alive, DELETE does not reach it, and by keep_until it survives the key change; only the change after theft closes it. This is a limit.

<!-- req: P/08.2-R107 -->
An unreadable row domain/issued: the issue rewrites it, journal.

<!-- req: P/08.2-R108 -->
`state`: the family is in the state of the backup (P/08.8 N1.5): after a move the revocation must work. `state`: at restore the exp of the row `domain/issued` is raised to no less than now + lifetime of the kind: a copy can be older than an extension, and DELETE with a low exp would let prune remove the revocation before the live token; the price — the revocation holds longer, up to lifetime.

<!-- req: P/08.2-R110 -->
`limits`: the reserve of 80 % is shared by all people: a person without a grant holds the ceiling with logins and revocations at 19.5 pairs per second, exp 900 s; a record leaves by prune 16 min after the end.

<!-- req: P/08.2-R111 -->
A planned change does not drive out an unnoticeably stolen key for the kinds keep: the thief mints a token with a fresh jti, DELETE does not reach it, the window is 10 years (KEEP_OLD), not 3600 s (OLD_KEYS); the iat signed by the thief cannot be checked, only the change after theft cures it; the token gives the write of a stream, not rights. For the kinds keep the limit of P/08.8 N1.8 lasts up to KEEP_OLD.

<!-- req: P/08.2-R113 -->
`limit`: the row domain/revoked — 524288 bytes, a record 28 bytes: about 18,700 revocations of live tokens per domain, a revocation of a 10-year token takes space for the whole term; above it — 409 too many revocations at DELETE and POST /domain/revoke, journal domain.revoked.full from 80 %: a limit. The path of the operator at a long 409 too many revocations — the change after theft (N3, step 3b): the tokens of former keys do not pass, the row is cleared. A planned change does not lower the row domain/revoked: the key of the kinds keep holds until keep_until, KEEP_OLD; without a change a revocation waits for expiry — a limit.

into the journal without the value (the outcome of the family `keys`).

### planned token key change

<!-- req: P/08.2-R019 -->
1. The root from the recovery file; the new token key — the row domain/signer; it is written by the batch of step 2, before it the key lives in the memory of the operation (the signing key changes with the write of the set).

<!-- req: P/08.2-R126 -->
2. The set: keys = the former keys — the former current (it has no until) and those whose until > now or keep_until > now — plus the new one; current = the new one;
   until[former current] = now + OLD_KEYS, keep_until[former current] = now + KEEP_OLD, until and keep_until of the others — the former ones (the filter is only for keys with until: an expired until is removed only together with keep_until); more than 8 live keep_until — the oldest is removed, journal domain.keys.keep_dropped;
   issuing, revoked_issuing, revoked_members, stolen_issuing, thefts, book_seal — the former ones; rev by N1.2 → domain/keys and domain/signer in one batch op: batch (P/01.1 N3 «write batch»; each row has its own cas, the guard domain/signer-turn).

<!-- req: P/08.2-R127 -->
3. Members take the set with the answer of the holder (chapter 8.3; the agent — chapter 9.1).

<!-- req: P/08.2-R128 -->
Tokens of the new key are refused with `unknown_key` by a member that has not yet taken the set — until the delivery (chapter 8.3).

<!-- req: P/08.2-R129 -->
After the planned token key change the former tokens are valid
until `until` and their `exp`, only for the kinds `keep` — until `keep_until` and their `exp`.

<!-- req: P/08.2-R130 -->
In the planned token key change a break before the batch of step 2 changes nothing: the row and the set are the former ones, the holder signs with the former key;
the operation answers with a refusal (code ≠ 0), its repeat starts from step 1 — one more new key.

### book acceptance key change

<!-- req: P/08.2-R020 -->
1. The root from the recovery file; the new seed — the row domain/book-seal; it is written by the batch of step 2, before it the seed lives in the memory of the operation.

<!-- req: P/08.2-R131 -->
2. The set: everything former, book_seal — the new one; rev by N1.2 → domain/keys and domain/book-seal in one batch op: batch (P/01.1 N3 «write batch»; each row has its own cas, the guard domain/signer-turn): the holder will not get an envelope to a key it cannot open with, and will not be left with a seed outside the set.

<!-- req: P/08.2-R132 -->
3. Envelopes to the former book_seal no longer open: the secret contributions of such members are missing (chapter 8.5) until their report,
   sealed to the new one; accepted bodies are not rewritten.

<!-- req: P/08.2-R133 -->
The planned token key change keeps `book_seal`.

<!-- req: P/08.2-R134 -->
In the book acceptance key change a break before the batch of step 2 changes nothing: the row and the set are the former ones, contributions to the former `book_seal` open;
the operation answers with a refusal (code ≠ 0), its repeat starts from step 1 — one more new seed.

<!-- req: P/08.2-R135 -->
There is no separate change «revocation of a member»: `revoked_members` is extended only by the change after theft (step 3), which also maintains the `revoked_keys` of the entry (step 3a).

<!-- req: P/08.2-R136 -->
`DELETE /domain/members/<member>` does not
change the set ([chapter 8.3](08.3-domain.norms.md)).

### change after theft (the holder keys are with the thief)

<!-- req: P/08.2-R021 -->
1. The operator takes out the recovery file; the move of the holder — chapter 8.8 (POST /domain/move {stolen: true}); before chapter 8.8
   the change after theft is a signer operation over its own set on the same holder (steps 2–3 and 5, the rows of step 2 and the set of step 3 in one batch; the call — «Implementation
   decides» item 2), chapter 8.8 calls the same steps from the move.

<!-- req: P/08.2-R137 -->
2. A new token key, issuing key and book acceptance seed — the rows domain/signer and domain/book-seal of the new holder; they are written by the batch of step 4, before it they live in the memory of the operation.

<!-- req: P/08.2-R138 -->
3. The set: keys = {new} without until (there are no former token keys); current = new; issuing = [new serial]; stolen_issuing = former revoked_issuing ∪ former issuing: nobody knows the moment of theft, a key that left by a move before the discovery would serve the thief as a source; thefts = former + 1 (none — 0; the theft mark for SET_GUARD, the domain key set contract «The follow set»); revoked_issuing = former revoked_issuing ∪ former issuing; revoked_members = former ∪ {the member key of the stolen holder — the Entry.key of the holder in `domain/member-rows/<part>` (chapter 8.3 N1.1), without it — the last one in its revoked_keys (a repeat, step 3a); without that too — a refusal, nothing changes}; book_seal = new; rev — emergency (N1.2 emergency): max(the greatest rev of the set at the reachable members + 1, floor(now) + TOKEN_SKEW + 1) → domain/keys. Before chapter 8.8 (the same holder) the known rev of step 3 is the rev of the set of the holder: the members hold its sets; the formula is the same.

<!-- req: P/08.2-R140 -->
3a. The Entry of the stolen holder in `domain/member-rows/<part>`: key goes to the end of its revoked_keys, there is no field key any more (chapter 8.3 N1.1, limit 4 — chapter 8.10 N1.5);
   the key is stolen together with the machine, so the entry does not hold it, a copy with holder_member_key does not return it (chapter 8.8 N1.2), and a returned machine
   makes a new key and is admitted anew (chapter 8.3 N3 step 1). An Entry already without key — a repeat: the step is skipped; in a move the Entry is written by chapter 8.8 N1.2.

<!-- req: P/08.2-R141 -->
3b. domain/revoked := {jtis: ""} in the same batch of step 4: all revocations are written before the change, and their tokens are signed by the former keys and no longer pass
   the signature step (keys = {new}); otherwise a full row would hold the 409 of revocation for years; members clear their row with the same batch
   with which they write a set with thefts above the former (the domain key set contract «Revocations» merge).

<!-- req: P/08.2-R142 -->
4. The term record — chapter 8.8 N1.1 (the signature of the new issuing key), in one batch with the set of step 3, the row of step 3b and the rows of step 2 (chapter 8.8 N1.8 step 8); the common document is re-signed — chapter 8.9 N1.2 after_move.

<!-- req: P/08.2-R143 -->
5. Members take the set with the answer of the new holder (chapter 8.3; the agent — chapter 9.1).

<!-- req: P/08.2-R144 -->
In the change after theft a break between steps 2 and 4: the operation answers with a refusal (code ≠ 0), its repeat starts from step 2 — new keys and a new seed, `rev` again by N1.2 `emergency`;
the repeat does not spoil the unions of step 3: nobody accepted the keys of the previous attempt, and before the batch of step 4 neither they nor the set are written.

<!-- req: P/08.2-R145 -->
**A member that was offline.** While a member that was offline holds the former set, it accepts the tokens of the stolen key (N1.7) and
seals contributions to the former `book_seal`.

<!-- req: P/08.2-R146 -->
Having returned, the member that was offline takes the new set: the `rev` of the new set is greater than any former one under the
premise N1.2 `clocks` — the former holder did not issue a `rev` greater than its wall-clock seconds, and the emergency one is not less than the
floor(now) + TOKEN_SKEW + 1.

<!-- req: P/08.2-R147 -->
If the clocks of the holders diverged more than TOKEN_SKEW, there is no guarantee: this is a limit, not a norm.

<!-- req: P/08.2-R148 -->
From the moment the returned member takes the new set
the tokens of the former keys are `unknown_key`, the term records of the former issuing key are a refusal (chapter 8.8), and its contributions sealed
to the former `book_seal` are missing until the first report after the new set (chapter 8.5).

<!-- req: P/08.2-R012 -->
**Races.** The set is written by one process (`domain` of the holder); at a member — by one active agent (the queue `domain/agent-turn`,
[P/09.1](../../09-agent/spec/09.1-agent.norms.md) N1.13).

<!-- req: P/08.2-R150 -->
Two sets with one `rev` from different
signers are impossible without the root; «holding» at an equal `rev` does not let a repeat overwrite the set.

<!-- req: P/08.2-R151 -->
A change in the middle of assembling a
book: the holder opens with the seed that it read at the start of the assembly; a contribution to another `book_seal` is missing, not a refusal of the whole book.

## N5 Acceptance

The chapter has no stand scenarios: acceptance is the vectors of the functions of N3 (the packages below; the input keys and the source journal — the [README of the package
`domain-token`](../../common/vectors/domain-token/README.md) (judge-only: test vectors; they check P/08.2-R008, P/08.2-R014, P/08.2-R076, P/08.2-R078 and P/08.2-R079)). The commands
`keys`, `token`, `seal`, `seal-round` of the implementation on the inputs of the vectors — without a store, a network and a stand. The input keys are
test keys, open in the READMEs of the packages. The call is the doors of the vocabulary «Domain stand» of the [common README of acceptance](../../common/acceptance/README.md);
the comparison is a subset of fields. The output of a command is only the JSON of the decision of the form below on stdout (`{result: ok, …}` or
`{result: refused, reason}`, code 0 for both); an input not in the form — code 2. `ok` in an expectation (`ok <JSON>`, `@verify`) is a word of
acceptance: «code 0 and stdout is this JSON» (the common README, «`ok <JSON>` in an expectation»), the command does not print it.
