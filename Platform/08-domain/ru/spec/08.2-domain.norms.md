### N1.1 Корень домена

```yaml
root:          пара Ed25519 домена
recovery_file: форма, place, mode
signs:         [domain/keys, просьба переноса по файлу]
limit:         файл восстановления — всё
needed_for:    [установка, плановая смена ключа токенов, смена ключа приёма книг, смена после кражи, перенос]
not_on:        [держатель, консоль, агент, воркер]
fingerprint:   hex(sha256(<32 байта открытого ключа>)[:8])
pin:           domain/root
```

`root` — пара Ed25519 домена; одна на всю жизнь домена.

`recovery_file`: форма, place и mode файла восстановления — договор основания домена «Корень и файл восстановления».

`signs`: корень подписывает только набор `domain/keys` (N1.2) и просьбу переноса по файлу (глава 8.8 N1.8 by_file).

Записи срока и удостоверение держателя подписывают ключи issuing[] набора (глава 8.8 N1.1).

`limit`: файл восстановления — всё: корень подписывает набор, а ключ резервной копии держателя выводится из зерна корня —
украденный файл открывает и все резервные копии домена (глава 8.8 N1.5); средства, кроме смены корня с новой установкой, нет.

`needed_for`: корень нужен для установки (P/02.4 N3), плановой смены ключа токенов, смены ключа приёма книг, смены после кражи (N3), переноса (глава 8.8 N1.8); иначе никогда.

`not_on`: держатель (`domain/signer`, его резервная копия главы 8.8), консоль, агент, воркер корня не хранят и не читают.

`fingerprint`: hex(sha256(<32 байта открытого ключа>)[:8]) — 16 знаков; так корень и ключи называют люди и журналы.

`pin`: форма строки `domain/root` — семья root (08-domain/data/root.schema.json); not_a_pin, when, never — договор основания
домена «Закрепление корня».

X.509 под корнем домена нет: сертификаты TLS ролей выдаёт центр поставки (P/02.4 N1.6). Заводская личность
устройства и регистратор — M13; приём члена оператором — глава 8.3.

### N1.2 Набор ключей `domain/keys`

Форма строки и документа набора (`row`, `doc`, `writer_forms`) и правило «только вперёд» (`only_forward`) — [договор набора
ключей домена](../../../common/ru/contracts/keys.md) «Набор `domain/keys`» (владелец — эта глава). Здесь — `rev` писателя:

```yaml
rev:               max(rev набора, который держит подписант, + 1, целые стенные секунды подписанта)
  emergency:       max(наибольший известный rev + 1, floor(now) + TOKEN_SKEW + 1)
  clocks:          стенные часы держателей домена расходятся не больше чем на TOKEN_SKEW
```

`rev` обычной и плановой смены (ключ токенов, book_seal) — max(rev набора, который держит
подписант, + 1, целые стенные секунды подписанта).

Если rev + 1 больше стенных секунд, смена ждёт, пока
часы его не догонят: rev не обгоняет стенные часы подписанта.

`rev.emergency`: `rev` аварийной смены — после кражи (N3) и переноса без прежнего держателя (глава 8.8 N1.8) — max(наибольший
известный rev + 1, floor(now) + TOKEN_SKEW + 1).

Известный rev для `rev.emergency` — наборы ответов соседей и своя domain/keys,
проверенная корнем, в том числе неподтверждённая своей записью срока (глава 8.8 N1.8 шаг 5).

`rev.clocks`: предпосылка: стенные часы держателей домена расходятся не больше чем на TOKEN_SKEW; при ней аварийный набор новее любого, который выпустил прежний держатель.

Набор — то, чему член верит без связи: ключи токенов держателя, отзывы и ключ приёма книг.

Без набора у члена нет
домена (сторожевая [P/06.3](../../../06-console/ru/spec/06.3-console.norms.md) N1.3, N1.8).

Поле вида `domain/view.trust` (набор, которому верит держатель: `rev`, отпечатки `root` и `book_seal` по N1.1) —
[глава 8.1](08.1-domain.norms.md) N1.2a (P/08.1-11).

**Представимость аварийной ревизии.** Кандидат аварийной ревизии вычисляется точно до публикации.

Верхний предел кандидата — существующий `common.pos53` [семьи keys](../../data/keys.schema.json); переполнение, округление и насыщение недопустимы.

Кандидат вне формы: набор, ключ подписанта, зерно, срок и запись члена не записываются.

При кандидате вне формы операция подписанта использует прежний ненулевой код отказа; перенос — прежний ответ неудачного восстановления, без частичной публикации.

Равенство, `only_forward`, подписи и страж срока при проверке представимости прежние.

### N1.3 Ключи держателя

```yaml
process:       domain                       # подписант
domain/signer: {kid, token_key_secret, serial, issuing_key_secret, backup_key_secret, backup_key_rev}   # у держателя
  token_key_secret:   hex 32 байт           # зерно Ed25519 ключа токенов (current набора)
  issuing_key_secret: hex 32 байт           # зерно Ed25519 выпускающего
  backup_key_secret:  hex 32 байт           # ключ резервной копии
  backup_key_rev:     целое ≥ 1
  forgotten:          {forgotten: "deposed by term N"}
readers:       domain
domain/signer-pending:  {seed_secret}       # подготовленный ключ X25519 плановой передачи у цели
  seed_secret:  hex 32 случайных байт       # закрытый скаляр X25519
SIGNER_URL:    адрес двери процесса domain держателя
```

`process`: `domain` (подписант) — единственный процесс с ключами домена и единственный писатель строк держателя.

Смены набора по этой главе исполняет операция подписанта ролью `domain` под стражем `domain/signer-turn`.

При смене набора корень берётся только
из файла восстановления на время операции; постоянный процесс его не держит.

Вызов операции подписанта — команда или дверь, «Решает
реализация» п. 2.

`domainconsole` и консоль кластера ключей не держат, подписи не просят и строк держателя не пишут: правку
консоль домена передаёт процессу `domain` (глава 8.0).

`domain/signer` — у держателя; его секреты — конверты кольца (договор запечатывания; P/06.2 N1.2).

Serial выпускающего ключа `domain/signer.issuing_key_secret` — в issuing набора; применение — глава 8.8.

`domain/signer.backup_key_secret` — ключ резервной копии (глава 8.8 N1.5: HMAC-SHA256 от зерна корня), пишет установка (P/02.4 N3) и перенос.

`domain/signer.backup_key_rev` при установке равен 1.

`domain/signer.forgotten`: смещённый держатель заменяет строку `domain/signer` на {forgotten: "deposed by term N"} (глава 8.8 N1.6).

`readers`: читатель `domain/signer` — `domain` (общая таблица читателей секретов P/02.5 N1.3 `platform_readers`).

`domain/signer-pending` — подготовленный ключ X25519 плановой передачи у цели (глава 8.8 N1.7); читатель тот же, что у `domain/signer`.

`domain/signer-pending.seed_secret` — hex 32 случайных байт — закрытый скаляр X25519, конверт кольца (договор запечатывания; P/06.2 N1.2) (одно имя с domain/member-key,
domain/book-seal).

`SIGNER_URL` — адрес двери процесса `domain` держателя; его знают консоль кластера держателя и запись срока (глава 6.7 — пересылка подписанту, OpenAPI урока 6; глава 8.8).

### N1.4 Ключ приёма книг

```yaml
domain/book-seal:  {seed_secret}           # у держателя
  seed_secret:     hex 32 случайных байт   # закрытый скаляр X25519
public:            book_seal набора = X25519(seed_secret, 9)
born:              при установке
travels:           с резервной копией держателя и переносом
```

Строка `domain/book-seal` — у держателя, конверт кольца (договор запечатывания; P/06.2 N1.2), без rev.

Читатель `domain/book-seal` — только `domain`.

`domain/book-seal.seed_secret` — hex 32 случайных байт — закрытый скаляр X25519 как есть (RFC 7748 §5: зажим при умножении).

`public`: book_seal набора = X25519(seed_secret, 9) — открытая половина, hex.

`born`: `domain/book-seal` рождается при установке (P/02.4 N3) раньше набора rev 1.

`domain/book-seal` заменяется только сменой ключа приёма книг и сменой после кражи (N3).

`travels`: `domain/book-seal` ездит с резервной копией держателя и переносом (глава 8.8).

`domain/book-seal` в отчёты, книги и журналы не попадает.

### N1.6 Токены домена и `domain/revoked`

Форма токена (`token`: `header`, `payload`, `sig`) и константа `TOKEN_SKEW` — [договор токена домена](../../../common/ru/contracts/domain-token.md)
«Токен» (глава — владелец договора). Здесь — отзывы и срок прежних ключей:

Строка `domain/revoked` — форма, писатели, порядок, снятие `prune`, читатели — [договор набора ключей домена](../../../common/ru/contracts/keys.md)
«Отзывы `domain/revoked`». Здесь — срок прежних ключей:

```yaml
OLD_KEYS:      forms/runtime-constants.tsv        # с
KEEP_OLD:      forms/runtime-constants.tsv   # с, 10 лет
```

`OLD_KEYS` — until прежнего current при плановой смене ключа токенов (N3); `KEEP_OLD` — keep_until прежнего current при той же смене.

Вид с keep: true и lifetime больше `KEEP_OLD` — не по форме манифеста (связь P/02.1).

Кто проверяет токен и где отказывают вид и `aud` — [договор токена домена](../../../common/ru/contracts/domain-token.md) «Токен».
Векторы функции `token` — [`common/vectors/domain-token`](../../../common/ru/vectors/domain-token/README.md) (только для судьи: тестовые векторы; они проверяют P/08.2-R008, P/08.2-R014, P/08.2-R076, P/08.2-R078 и P/08.2-R079).

### N1.7 Окно отзыва без связи

Проверяющий решает по своему набору и своей копии `domain/revoked` по своим стенным часам; связи с держателем проверка не
требует.

Поэтому отзыв доходит не мгновенно, и норма называет пределы числом:

| Что отозвано | Принимается не дольше | Чьи часы |
|---|---|---|
| токен (`jti` в `domain/revoked`) | `min(exp + TOKEN_SKEW, delivery of domain/revoked to the checker)`; без связи — `exp + 60`, то есть `lifetime + 60` от выдачи; в `testsub*` самый долгий вид — `testsub2` `feed: 600` → 660 с | стенные проверяющего |
| прежний ключ токенов после плановой смены | до `until` своего набора (`OLD_KEYS` = 3600 с от смены); только для видов `keep` — до `keep_until` (`KEEP_OLD`) | стенные проверяющего |
| украденный текущий ключ токенов (у current нет `until`) | **до первого принятого проверяющим набора, где этого ключа нет** (смена после кражи, N3): вор выпускает новые токены, и член без связи их принимает; сроком это окно не ограничено | — |
| ключ члена (`revoked_members`) | держатель отказывает сразу после своего набора (глава 8.3); член без связи сам себя не отзывает | — |

Доставка `domain/revoked` у члена — с ответом держателя агенту (глава 8.3; применяет агент — глава 9.1); у кластера держателя — запись в
его же хранилище.

### N1.6a Токены `keep`: память домена и отзыв

```yaml
domain/issued/<sub>/<вид>/<sha16(ref)>: {ref, jti, exp, member, at}    # у держателя
why:        домен выданных токенов не помнит
jti:        постоянен для цели
порядок:    под общей стороной замка P/08.8 N1.7 шаг 1
door:       DELETE /domain/issued/<sub>/<вид>/<ref>
потеря:     предел
state:      семья в state резервной копии
limits:     запас 80 % делят все люди
limit:      строка domain/revoked — 524288 байт, запись 28 байт
```

Строка `domain/issued/<sub>/<kind>/<sha16(ref)>` — у держателя; писатель — процесс domain при выдаче вида с keep: true, CAS.

`why`: домен выданных токенов не помнит: вор держит токен, а отозвать по нему нечем, POST /domain/revoke принимает только сам токен.

Строка `domain/issued` — на цель, не на выдачу: растёт с числом камер, не с числом выдач.

`jti`: jti вида с keep: true постоянен для цели: выдача берёт jti из строки.

Строки нет или её jti в domain/revoked — выдача берёт новый случайный, строка переписывается.

Просьба со словом `revoked: <jti>` — получатель отказал этому токену revoked, а держатель отзыва может не знать (копия старше DELETE).

Если слово revoked равно jti строки: он с exp строки кладётся в domain/revoked, одним пакетом с новой строкой, выдаётся новый jti.

Если слово revoked не равно jti строки: строка уже сменилась, просьба обычная, берётся jti строки: иначе два исполнителя цели гасили бы токены друг друга до потолка строки.

Подделка равного слова гасит только токены самой цели, неравного — ничего, из-под отзыва токен вора не уводит.

REVOKED_WORDS: исполненных слов от члена за сутки, REVOKED_WORDS_CAMERA для класса camera, REVOKED_WORDS_SERVER для класса server, счёт в памяти процесса domain.

Сверх REVOKED_WORDS просьба обычная, журнал domain.revoked.word_limit.

Когда строка domain/revoked заполнена на 80 %, слово не исполняется вовсе, остаток только людям (DELETE, POST /domain/revoke с токеном person): запись живёт до 10 лет, и слово иначе выбрало бы потолок.

Предел: при заполненной на 80 % строке копия старше DELETE даёт круг отказов одной цели, его снимает оператор тем же DELETE цели, журнал domain.revoked.word_limit это показывает; обычный DELETE снимает строку, следующая выдача получает новый jti, слово не нужно.

На уникальность jti никто не опирается: door.pass и билеты — только у сессий person.

`order`: проверка заморозки и CAS строки — под общей стороной замка P/08.8 N1.7 шаг 1: выдача в полёте либо легла до копии, либо получает frozen, иначе DELETE на цели её не достал бы.

При выдаче e = now + lifetime считается один раз до CAS, строка — max(прежний exp, e), токен — e: всегда не старше строки.

Подпись токена только после удачного CAS строки, создания или продления.

Проигравший CAS строки перечитывает и берёт jti победителя, конфликт — до 3 раз, как у отзыва, затем 503 unavailable.

Если domain/revoked не читается — 503 unavailable: строка с возможно отозванным jti не берётся.

exp строки — наибольший из прежнего и нового, иначе prune снимет отзыв раньше живого токена.

Два исполнителя одного ref и другой член делят jti: отзыв закрывает обоих.

`door`: `DELETE /domain/issued/<sub>/<kind>/<ref>` у консоли домена: admin домена.

У DELETE /domain/issued запись jti с наибольшим exp в domain/revoked и снятие строки — одним пакетом; 200 `{revoked: <jti>}`.

У DELETE /domain/issued строки нет — 404.

У DELETE /domain/issued строка domain/revoked полна (запись не вмещается под потолок limit) — 409 {error: "too many revocations"}: ничего не пишется, строка domain/issued остаётся, токен не отозван.

Отзыв закрывает все токены цели, старые и новые; коробка получит отказ, когда отзывы дойдут до кластера записи.

`loss`: копия старше первой выдачи или смены jti (при живом новом jti DELETE закрывает прежний), перенос «из ничего», нечитаемая строка: новая выдача получает новый jti, старый токен жив, DELETE его не достаёт, а по keep_until он переживает смену ключа; закрывает только смена после кражи. Это предел.

Нечитаемая строка domain/issued: выдача переписывает её, журнал.

`state`: семья в state резервной копии (P/08.8 N1.5): после переноса отзыв должен работать.

При восстановлении exp строки поднимается не ниже now + lifetime вида: копия бывает старше продления, а DELETE с низким exp дал бы prune снять отзыв раньше живого токена; цена — отзыв держится дольше, до lifetime.

`limits`: запас 80 % делят все люди: человек без гранта логином и отзывом держит потолок при 19,5 пары в секунду, exp 900 с; запись уходит prune за 16 мин после конца.

Плановая смена не выгоняет незаметно украденный ключ для видов keep: вор чеканит токен со свежим jti, DELETE его не достаёт, окно — 10 лет (KEEP_OLD), а не 3600 с (OLD_KEYS); подписанное вором iat не сверить, лечит только смена после кражи; токен даёт запись потока, не права.

Для видов keep предел P/08.8 N1.8 длится до KEEP_OLD.

`limit`: строка domain/revoked — 524288 байт, запись 28 байт: около 18 700 отзывов живых токенов на домен, отзыв 10-летнего токена занимает место весь срок; сверх — 409 too many revocations у DELETE и POST /domain/revoke, журнал domain.revoked.full с 80 %: предел.

Путь оператора при долгом 409 too many revocations — смена после кражи (N3, шаг 3b): токены прежних ключей не проходят, строка очищается.

Плановая смена строку domain/revoked не опускает: ключ видов keep держится до keep_until, KEEP_OLD; без смены отзыв ждёт истечения — предел.

### установка домена

Установка домена — в главе позднего слоя [P/02.4](../../../02-installer/ru/spec/02.4-installer.norms.md) N3 «установка домена» (P/02.4-10,
вводит 8.2): шаги 1–8, интерфейс шага 8, прерванная установка. Сторона процесса —
ниже.

### процесс `domain` домена не основывает

Процесс `domain` домена не основывает: без строки `domain/signer` он ждёт её, проверяя раз в VIEW_EVERY, и не берёт
роль держателя и пишет причину в журнал.

Домен основывает установка ([P/02.4](../../../02-installer/ru/spec/02.4-installer.norms.md)
N3 «установка домена»). Холодный старт — N3 «холодный старт».

### холодный старт

```
хранилище каждого кластера поднято (своя установка P/02.4, свой TLS) → установка домена на держателе (P/02.4 N3)
→ процесс domain держателя стартует и читает свои ключи → оператор принимает членов, закрепляя корень (глава 8.3)
→ агенты членов уносят набор и пишут отчёты (главы 8.3, 9.1) → вид домена полнеет (глава 8.1)
```

Между «хранилище поднято» и «набор у члена» каждый кластер работает сам (уроки P/01–P/07); домена у него нет, сторожевая
— по [P/06.3](../../../06-console/ru/spec/06.3-console.norms.md) N1.8.

Ни один шаг холодного старта не зависит от другого кластера: подпись
корнем (установка домена, [P/02.4](../../../02-installer/ru/spec/02.4-installer.norms.md) N3) берёт только своё хранилище и файл
восстановления.

Процесс `domain` файла восстановления и корня не читает (N1.1 `not_on`) — его ключи в своём хранилище,
секреты открывает своё кольцо.

Смены набора ниже (плановая смена ключа токенов, смена ключа приёма книг, смена после кражи) поверх нечитаемой строки
`domain/keys` держателя не пишутся: операция отказывает (код ≠ 0) до шага записи набора, строка не меняется, причина —
в журнал без значения (исход семьи `keys`).

### плановая смена ключа токенов

1. Корень из файла восстановления; новый ключ токенов — строка domain/signer; её пишет пакет шага 2, до него ключ живёт в памяти операции (ключ подписи меняется с записью набора).

2. Набор: keys = прежние ключи — прежний current (у него until нет) и те, чей until > now или keep_until > now, — плюс новый; current = новый;
   until[прежний current] = now + OLD_KEYS, keep_until[прежний current] = now + KEEP_OLD, until и keep_until прочих — прежние (фильтр — только у ключей с until: истёкший until снимается только вместе с keep_until); живых keep_until больше 8 — самый ранний снят, журнал domain.keys.keep_dropped;
   issuing, revoked_issuing, revoked_members, stolen_issuing, thefts, book_seal — прежние; rev по N1.2 → domain/keys и domain/signer одним пакетом op: batch (P/01.1 N3 «записать пакет»; у каждой строки свой cas, страж domain/signer-turn).

3. Члены берут набор с ответом держателя (глава 8.3; агент — глава 9.1).

Токены нового ключа член, ещё не взявший набор, отказывает `unknown_key` — до доставки (глава 8.3).

После плановой смены ключа токенов прежние токены годны
до `until` и своего `exp`, только для видов `keep` — до `keep_until` и своего `exp`.

В плановой смене ключа токенов обрыв до пакета шага 2 не меняет ничего: строка и набор прежние, держатель подписывает прежним ключом;
операция отвечает отказом (код ≠ 0), её повтор начинается с шага 1 — ещё один новый ключ.

### смена ключа приёма книг

1. Корень из файла восстановления; новое зерно — строка domain/book-seal; её пишет пакет шага 2, до него зерно живёт в памяти операции.

2. Набор: всё прежнее, book_seal — новый; rev по N1.2 → domain/keys и domain/book-seal одним пакетом op: batch (P/01.1 N3 «записать пакет»; у каждой строки свой cas, страж domain/signer-turn): держатель не получит конверта к ключу, которым не откроет, и не останется с зерном вне набора.

3. Конверты к прежнему book_seal больше не открываются: секретные вклады таких членов — missing (глава 8.5) до их отчёта,
   запечатанного к новому; принятые тела не переписываются.

Плановая смена ключа токенов `book_seal` сохраняет.

В смене ключа приёма книг обрыв до пакета шага 2 не меняет ничего: строка и набор прежние, вклады к прежнему `book_seal` открываются;
операция отвечает отказом (код ≠ 0), её повтор начинается с шага 1 — ещё одно новое зерно.

Отдельной смены «отзыв члена» нет: `revoked_members` пополняет только смена после кражи (шаг 3), она же ведёт `revoked_keys` записи (шаг 3a).

`DELETE /domain/members/<член>` набор не
меняет ([глава 8.3](08.3-domain.norms.md)).

### смена после кражи (ключи держателя у вора)

1. Оператор достаёт файл восстановления; перенос держателя — глава 8.8 (POST /domain/move {stolen: true}); до главы 8.8
   смена после кражи — операция подписанта над своим набором на том же держателе (шаги 2–3 и 5, строки шага 2 и набор шага 3 одним пакетом; вызов — «Решает
   реализация» п. 2), глава 8.8 вызывает те же шаги из переноса.

2. Новые ключ токенов, выпускающий и зерно приёма книг — строки domain/signer и domain/book-seal нового держателя; их пишет пакет шага 4, до него они живут в памяти операции.

3. Набор: keys = {новый} без until (прежних ключей токенов нет); current = новый; issuing = [новый serial];
   stolen_issuing = прежний revoked_issuing ∪ прежний issuing: момента кражи никто не знает, ключ, ушедший переносом до обнаружения, годился бы источником вору; thefts = прежний + 1 (нет — 0; метка кражи для SET_GUARD, договор набора ключей «Набор следования»);
   revoked_issuing = прежний revoked_issuing ∪ прежний issuing; revoked_members = прежний ∪ {ключ члена украденного
   держателя — Entry.key держателя в domain/member-rows/<раздел> (глава 8.3 N1.1), без него — последний в её revoked_keys (повтор, шаг 3a); нет и его —
   отказ, ничего не меняется}; book_seal = новый; rev — аварийный (N1.2 emergency): max(наибольший rev набора у достижимых членов + 1,
   floor(now) + TOKEN_SKEW + 1) → domain/keys.

   До главы 8.8 (тот же держатель) известный rev шага 3 — rev набора держателя: члены держат его наборы; формула та же.

3a. Entry украденного держателя в domain/member-rows/<раздел>: key уходит в конец её revoked_keys, поля key больше нет (глава 8.3 N1.1, предел 4 — глава 8.10 N1.5);
   ключ украден вместе с машиной, поэтому запись его не держит, копия с holder_member_key его не возвращает (глава 8.8 N1.2), а вернувшаяся машина
   делает новый ключ и принимается заново (глава 8.3 N3 шаг 1). Entry уже без key — повтор: шаг пропущен; в переносе Entry пишется по главе 8.8 N1.2.

3b. domain/revoked := {jtis: ""} тем же пакетом шага 4: все отзывы записаны до смены, а их токены подписаны прежними ключами и шаг подписи
   больше не проходят (keys = {новый}); иначе полная строка держала бы 409 отзыва годами; члены очищают свою строку тем же пакетом,
   которым пишут набор с thefts выше прежнего (договор набора ключей домена «Отзывы» merge).

4. Запись срока — глава 8.8 N1.1 (подпись нового выпускающего), одним пакетом с набором шага 3, строкой шага 3b и строками шага 2 (глава 8.8 N1.8 шаг 8); общий документ переподписывается — глава 8.9 N1.2 after_move.

5. Члены берут набор с ответом нового держателя (глава 8.3; агент — глава 9.1).

В смене после кражи обрыв между шагами 2 и 4: операция отвечает отказом (код ≠ 0), её повтор начинается с шага 2 — новые ключи и зерно, `rev` снова по N1.2 `emergency`;
объединения шага 3 повтор не портит: ключи прошлой попытки никто не принял, до пакета шага 4 не записаны ни они, ни набор.

**Член, который был без связи.** Пока член, который был без связи, держит прежний набор, он принимает токены украденного ключа (N1.7) и
запечатывает вклады к прежнему `book_seal`.

Вернувшись, член берёт новый набор: его `rev` больше любого прежнего при
предпосылке N1.2 `clocks` — прежний держатель не выпускал `rev` больше своих стенных секунд, а аварийный не меньше
floor(now) + TOKEN_SKEW + 1.

Часы держателей разошлись больше — гарантии нет: это предел, а не норма.

С момента, когда вернувшийся член берёт новый набор,
токены прежних ключей — `unknown_key`, записи срока прежнего выпускающего — отказ (глава 8.8), а его вклады, запечатанные
к прежнему `book_seal`, — missing до первого отчёта после нового набора (глава 8.5).

**Гонки.** Набор пишет один процесс (`domain` держателя); у члена — один активный агент (очередь `domain/agent-turn`,
[P/09.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.13).

Два набора с одним `rev` от разных
подписантов невозможны без корня; «держу» при равном `rev` не даёт перезаписать набор повтором.

Смена посреди сборки
книги: держатель открывает тем зерном, что прочёл в начале сборки; вклад к другому `book_seal` — missing, не отказ всей книги.

             # kind списком — непустой, без повторов, без person; audience_claim при нём — отображение с ключами из списка
             # (вид без записи — aud); иное сочетание — вход не по форме, код 2 (договор токена домена «Проверка» expect)
             # audience_claim пустой или не строка — вход не по форме, код 2
             # cluster — обязательный ключ expect; null — только при kind: person; без ключа или null при ином kind —
             # вход не по форме, код 2 (договор токена домена «Проверка» expect)
             вывод {result: ok, payload} | {result: refused, reason: no_revocations | not_a_token | unknown_key | bad_signature |
                   bad_claims | expired | future | revoked | wrong_kind | wrong_audience}
seal:        вход {seed: <hex 32 байт>, envelope: <как пришёл>, member, source_path, item, pointer: <строки>}   # open N3
             вывод {result: ok, plain} | {result: refused, reason: not_v1 | not_an_envelope | does_not_open}
seal-round:  вход {book_seal: <hex 32 байт>, seed: <hex 32 байт>, plain, member, source_path, item, pointer: <строки>}
             вывод {result: ok, envelopes: [<конверт>, <конверт>], opened: [<plain>, <plain>], distinct: true | false}
             # два запечатывания к book_seal и открытие обоих seed; envelopes — по форме N1.5;
             # свой конверт не открылся — {result: refused, reason: <слово открытия N1.5>}
held:        не по форме N1.2 (включая book_seal) — код 2: это набор, которому член уже верит
Pin:         {pub, domain}                     # N1.1; pinned во входе не по этой форме — код 2
output:      закрытые объекты выше; ключи — в любом порядке; payload — объект payload токена как есть
exit:        0 — вычислено (в том числе отказ словом); 2 — вход не по этой форме

## Решает реализация

Реализация обязана назвать в своём описании:

1. **команды `keys`, `token`, `seal`, `seal-round`** для приёмки — шаблоны с `{input}`; их вызов и вывод — двери словаря
   «Стенда домена» [общего README приёмки](../../../common/ru/acceptance/README.md), формы — N5;
2. **вызов двух плановых смен** — ключа токенов и ключа приёма книг (имя, аргументы, где файл восстановления, как команда узнаёт
   каталоги хранилища, объектов и их копий, внутри которых файл запрещён): другого пути к ним нет; смена после кражи с главой 8.8 — перенос со `stolen`, отдельный вызов нужен только реализации без главы 8.8; приёмка их не вызывает (N5); команду установки домена называет
   [P/02.4](../../../02-installer/ru/spec/02.4-installer.norms.md) «Решает реализация» (стенд главы 8.3
   называет её строкой словаря `@install domain`);
3. **генератор случайности** для зёрен, `eph` и `nonce` — криптографический генератор ОС;
4. **порядок полей JSON** в `doc` и выводах — свободен; подпись — над JCS.
