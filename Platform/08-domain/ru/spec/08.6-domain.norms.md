N1.5.

Общее [глав 8.2](08.2-domain.norms.md) и [8.3](08.3-domain.norms.md) N1 действует.

Домен не пишет
строк в члены: правку члена применяет агент члена ([глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.5) через дверь единиц своей
консоли ([P/06.1](../../../06-console/ru/spec/06.1-console.norms.md)).

### N1.1 Назначение у держателя

```yaml
domain/placement/<sub>/<ref>:   строка хранилища держателя; элементы — строки (P/01.1):
  cluster:   член-исполнитель; обязателен
  origin:    член-владелец источника; "" — нет
  copies:    текст JCS массива других исполнителей, по возрастанию, без повторов, без cluster; "[]" — нет
  reason:    слова оператора; "" — нет
  at:        стенные секунды процесса domain записи, десятичным текстом
  rev:       значение счётчика domain/placement этой записи, десятичным текстом
domain/placement:   {rev}
writer:     процесс domain
readers:    процесс domain; воркер на держателе
executors:  {cluster} ∪ copies
ref:        остаток после <sub>/ байт в байт
form:       cluster — непустая строка
class:      cluster — только class server
```

`domain/placement` — счётчик, +1 на каждую запись и удаление назначения.

`writer`: процесс domain по двери N2 консоли домена (глава 8.0 N1.8); агенту запись запрещена (P/02.5 N1.4a domainagent).

`readers`: процесс domain (вид главы 8.1, теневой отчёт главы 8.1 N1.6, ответ агенту — N1.2); воркер на держателе — через
чтение `domain/placed/<sub>/` (P/02.5 N3 шаг 3 даёт и `domain/placement/<sub>/`).

`executors`: исполнители ref — множество {cluster} ∪ copies; поле origin ни добавляет члена в это множество, ни исключает из
него (origin = cluster — исполнитель как cluster).

Член вне множества исполнителей, давший тот же ref, — спор (глава 8.1 N1.4
executors).

Роль исполнителя (основной или резерв) — забота подсистемы.

`ref`: не проверяется на существование: назначение может опередить единицу (теневой отчёт — orphaned через
SHADOW_STALL).

В пути ref — остаток после `<sub>/` байт в байт, процент-формы не декодируются (`a%20b` — ref
«a%20b»).

ref не по грамматике имени P/06.1 N1.3 named (в том числе с `/`: `/domain/placement/testsub/a/b`) — 400.

`form`: cluster — непустая строка: "" — 400, не 409.

`class`: cluster — только class server (Entry; нет поля — server): камера-кластер основным исполнителем не бывает.

copies и origin по class не судятся: камера с картой — законная копия, источник может быть камерой.

### N1.2 Ответ держателя: назначения члена

```yaml
carry.placement:  {rev, records: {"<sub>/<ref>": {cluster, origin, copies: [<член>…], reason, at, rev}}}   # глава 8.3 N1.5
  records:   назначения, которые называют этого члена
  rev:       счётчик domain/placement держателя
  absent:    поля нет
```

`carry.placement.records`: только назначения, которые называют этого члена: он — cluster, origin или в copies (минимум знания;
цена ответа при сотнях членов — глава 8.10 N1.9).

`carry.placement.absent`: поля `carry.placement` нет, пока счётчика нет (rev 0).

Ответ строится под тем же мьютексом, что запись назначения, и после подъёма счётчика при старте и при новом взятии
очереди (N3 «записать назначение»).

Копия у члена (`domain/placed/<sub>/<ref>`, `domain/placed`) — что агент пишет по этому полю, без отката, и
её читатели — [глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.5 `member`,
`readers`.

Держатель копий не пишет: его читатели берут запись (N1.1 readers).

### N1.3 Правка единицы члена доменом

```yaml
doors:      POST /domain/<sub>/<rows> {cluster, <поля>}        — создать единицу на члене cluster
            PUT /domain/<sub>/<rows>/<ref>[?cluster=<член>]   — править поля
            DELETE /domain/<sub>/<rows>/<ref>[?cluster=<член>] — удалить
            POST /domain/<sub>/<таблица> {cluster, <поля>}      — записать строку таблицы domain.edit_tables на члене cluster
            DELETE /domain/<sub>/<таблица>/<имя>?cluster=<член> — снять строку
            POST /domain/edits {cluster, writes}                — связка правок: N1.3b
fields:     только поля domain.edit манифеста
secrets:    *_secret на любой глубине
order:      платформенные поля → секреты → поля вне domain.edit → пустое тело PUT → значения
find:       ref → член и id по виду домена
refusals:   ровно глава 8.1 N4:
  - ?cluster= не член списка                         → 404 {error: "no such member"}
  - ref в contested                                  → 503 {error: "refused", detail: называет членов}
  - ref не найден, кто-то не ok (unseen, silent, never) → 503 {error: "refused", detail: называет молчащих}
  - ref не найден, ответ полный                       → 404 {error: "refused", detail: "<sub> <ref> is in no member of the domain"}
  - POST: cluster не член                             → 404 {error: "no such member"}
  - PUT, DELETE без ?cluster=: ref у двух исполнителей и больше, раннего повтора нет → 409 {error: "executors", detail,
    clusters: [<кластер>…]} по возрастанию байтов, без правки
kept:       202 {kept, cluster, what, note}
view:       domain/ref-claims/<sub>/<sha16 ref>
```

У `DELETE /domain/<sub>/<rows>/<ref>` тело — пустое или {}, иное — 400.

PUT таблицы нет, как у двери члена (P/06.1 N1.6).

Idempotency-Key обязателен у всех шести дверей (иначе 400) и по пределу двери владельца P/06.1 (200 байт UTF-8, один
сегмент — иначе 400).

Idempotency-Key уходит агенту и его консоли как есть (P/09.1 N1.5 apply).

Право у двери домена — договор права common/contracts/may.md
«Суд по цели» `write`, по кластеру цели: `<cluster>` тела или член из find.

`<sub>` не из каталога (манифеста нет или он без domain.ref, глава 8.1 N1.2 no_ref) — 404, до разбора тела, у всех
трёх дверей единицы.

У таблицы domain.ref не нужен: манифест каталога с этим ключом domain.edit_tables.

`<rows>` не unit.rows манифеста и не ключ domain.edit_tables — 404 `{error: "refused", detail: "<sub> <rows> is not a family of the domain"}`, до разбора тела.

Порядок проверок двери: Idempotency-Key → `<sub>` → `<rows>` → тело.

POST: cluster нет, не строка или пустая строка — 400.

У POST поиска нет: из refusals ниже действует
только «cluster не член», новая единица ищет не ref, а место.

`fields`: только поля domain.edit манифеста (P/02.1 N1.2a), у таблицы — `domain.edit_tables.<table>`, секреты — N1.3a.

У единицы платформенные поля (cluster, worker, server, placement, epoch,
observed_revision, phase, revision), у таблицы только table_platform_fields (P/06.1 N4: by, at, made_at, held_by, garbled, revision, index), её поле server — поле автора, и поля вне списка — 400.

Пустое тело PUT — 400.

Значения — по
манифесту (P/06.1 N3 «создать» шаг 4 формы) — 400.

POST дополнительно принимает обязательное поле domain.ref манифеста, даже
если его нет в domain.edit (у testsub edit — [start, labels], ref — name); у PUT исключения нет: ref — в пути.

Граница «значений»: договор проверки строки R1 — проверки значений P2 над переданными полями, без
заполнения умолчаний, у POST и PUT; у POST ещё P3 над полем domain.ref (раздел «Идентификатор»).

P4 (required),
P5 и R2–R3 (fixed, ref, must_match, unique по строкам) домен не проверяет — строк члена у него нет: их
проверяет консоль члена при применении, отказ — исход refused (P/09.1 N1.5).

`secrets`: *_secret на любой глубине, кроме полей domain.edit_secrets (N1.3a), адрес с учётными данными — 400 «a secret is set in the member's own cluster, never
through a kept edit» (P/06.2 N1.4).

domain.edit с секретом — отказ загрузки манифеста (P/02.1 N4); секрет идёт только полем domain.edit_secrets, N1.3a.

Тело отказа по секрету — {error: «a secret is set in the member's own cluster, never through a kept edit»}: текст — в error, не
refused с detail (как строки P/06.2 N4 «Тело»; приёмка 8.6 сц. 02 шаг 8; только для судьи: сц. 02 шаг 8 главы 8.6; он проверяет P/08.6-R059).

`order`: проверки тела идут по порядку: платформенные поля → секреты → поля вне domain.edit → пустое тело PUT → значения.

`find`: ref судится свежей строкой domain/ref-claims (глава 8.1 N1.4b), id — её члена по строке вида.

У таблицы поиска нет: член — ?cluster= или cluster тела, обязателен, нет — 400.

ref → член и id по виду домена (глава 8.1 N1.4); ?cluster= — только этот член.

ref в units у двух исполнителей и
больше (глава 8.1 N1.4 executors) и запрос без ?cluster= — ранний повтор, затем 409 executors (N3 «принять
правку» шаг 2a); с `?cluster=<executor>` — правка у этого члена.

ref у нескольких единиц одного члена (глава 8.1 N1.2 siblings): нужен `?id=<unit id>`, нет — 409 `{error: "siblings", detail, ids: [<id>…]}` по возрастанию байтов, без правки.

С ?id= — эта единица, id вне этого ref — 404 refused.

В связке (N1.3b) — поле id строки writes, то же правило.

id читатель берёт из Unit вида.

`refusals`: отказы поиска — ровно глава 8.1 N4, по списку `refusals`.

Отказ «ref в contested» действует и при
?cluster= одного из спорящих — вид не держит единиц спорного ref; член вне спора — поиск только у него.

`kept`: найденная единица (в том числе у члена silent — по его последней копии) и POST → правка хранится (N1.4) и ответ
202 {kept, cluster, what, note}.

При хранимой правке домен в члены не пишет.

`view`: ref ищется свежим чтением `domain/ref-claims/<sub>/<sha16 ref>` (P/08.1 N1.4b), единица — строкой вида раздела заявившего члена.

Строки заявки нет при complete головы — ref нигде.

Головы или строки вида нет (круг их ещё не собрал), complete ложь — ответ неполон: 503 {error:
"refused", detail: "the domain view is not built yet: ask again in a few seconds"}, не 404.

В поиске по виду не читается — 503
{error: "unavailable"}, ничего не записано (P1; исходы domain/view).

### N1.3a Секрет в правке

```yaml
declare:    domain.edit_secrets: {<rows или таблица>: [<поле *_secret>…]}
seal:       конверт m1 к ключу члена цели
open:       агентом ключом члена
repeat:     поля domain.edit_secrets не участвуют
stranded:   POST /domain/edits/stranded {asked, by?, iat?}
path:       предел
```

`declare`: domain.edit_secrets (P/02.1, связи 148, 149); только верхний уровень тела: вложенный *_secret — 400 N1.3 secrets.

`seal`: процесс domain при приёме заменяет значение конвертом m1 к ключу члена цели (договор конвертов домена «Конверт m1», ключ — Entry.key
`domain/member-rows/<part>`): plain — JSON `{edit: <edit id>, field: <field>, value: <secret>}`, поле в теле правки — текст конверта.

Открытого значения нет ни в domain/pending, ни в asked, ни в журнале, ни в view.pending.

`open`: агент перед применением открывает ключом члена и сверяет edit и field; не открылось или не сошлось — исход refused, error — слово
отказа конверта, дверь не зовётся (P/09.1 N1.5).

`repeat`: поля domain.edit_secrets в сравнении N1.4 repeat не участвуют: конверты одного значения различны.

Предел: иной секрет под тем же ключом — 202 с прежней правкой,
новое значение не применится; новый секрет — новый ключ.

`stranded`: обычная дверь запечатывает любое значение, с приставкой m1: тоже.

Конверт как есть принимает только POST /domain/edits/stranded (глава 8.8 N1.6 apply), дверь admin домена:
тело {asked, by?, iat?}, Idempotency-Key — key; значение не конверт — 400.

Шаг суда у POST /domain/edits/stranded — wide, человек правки сохраняется: by, iat — из тела.

`path`: открытое значение проходит консоль входа и консоль держателя и живёт в памяти процесса domain до шага 4a N3: предел, в строки и журнал оно не попадает.

### N1.3b Связка правок

```yaml
door:       POST /domain/edits {cluster, writes: [{op: put | delete, sub, rows, ref?, id?, name?, create?, new?, fields?}…]}
  rows:     unit.rows или ключ domain.edit_tables манифеста sub
  ref:      единица
  name:     строка таблицы
  id:       адрес единицы
  put:      правило только единицы
  согласие: unit.rows манифеста с domain.ref или с непустым domain.edit
  create:   true — создание единицы с unit.id: name
  new:      true — создание единицы с unit.id: numeric
  fields:   у put обязателен
  отказы:   [bad batch, no anchor]
  суд:      договор права write своей sub
edit:       method POST, path /console/batch
apply:      агент (P/09.1 N1.5)
new_id:     предел
size:       правка лежит дважды, body и asked
```

У POST /domain/edits Idempotency-Key обязателен.

`door`: writes — 1 … BATCH_WRITES (P/01.1 N1), у связки с new — на одну меньше.

Правка одного устройства — один элемент `domain/pending/<member>`, применяется всё или ничего.

`door.rows`: unit.rows или ключ domain.edit_tables манифеста sub; у единицы поля — domain.edit.

`door.ref`: единица, id? — выбор среди единиц одного ref: N1.3 find только у cluster; не найден — 404 refused, как N1.3.

`door.name`: строка таблицы; у delete обязателен, у put — либо он, либо вычислен по `tables.<t>.key` из fields.

`door.id`: адрес единицы: с ref — выбор среди единиц одного ref (N1.3 find); без ref — строка (cluster, id) прямо, поиска по виду нет: так правят единицы без ref и манифесты вне каталога вида; при create — имя новой.

Для `door.id` base — revision строки шарда копии по id, иначе строки снимка таблиц, если rows в domain.view_tables; иначе base нет: предел, такая правка затирает локальную.

contested адрес `door.id` не касается: спор — об имени ref, а (cluster, id) однозначен, домен цель не угадывает.

`door.put`: правило только единицы: без create и new единица правится только по живой строке: агент видит, что строки нет или она надгробие, — исход refused, дверь не зовётся.

Без ref, id, create, new у единицы — 400 bad batch.

Строка таблицы — put по name или `tables.<t>.key`, строки нет — создаётся, как POST таблицы (P/06.1 N1.6): cas "".

`door.consent`: unit.rows манифеста с domain.ref или с непустым domain.edit, иначе 404.

op: delete единицы манифеста без domain.ref — только при domain.edit_delete: true, иначе 404: автор решает, что домен снимает.

`door.create`: true — создание единицы с unit.id: name: поиска нет, id обязателен; в пакете revision 0: живая строка — 412 revision moved, исход conflict; надгробие — создание.

`door.new`: true — создание единицы с unit.id: numeric; не больше одной на связку, номер выдаёт агент, ниже.

Подстрока $id в id, name и строковых значениях fields всех строк связки — этот номер
(`<id>-<volume>` записи — "$id-disk-a"); $id без new — 400 bad batch.

`door.fields`: у put обязателен, {} — можно: строка-якорь (P/06.1 N2) без правки.

Проверки `door.fields` — N1.3 fields, secrets, order, номер строки в detail; секреты — N1.3a, field — `"<number>/<field>"`.

`door.refusals`: ключ дважды — 400 bad batch; часть с about без строки единицы-якоря в writes — 400 no anchor: то, что всё равно откажет у члена, отказывается сразу.

`door.judgement`: каждая строка — договор права write своей sub; отказ одной — 403 всей связки.

`edit`: method POST, path /console/batch, what — ключи строк по возрастанию через «,»; body {writes: [{op, key, fields?, base?}], new?: {sub, rows}}: key — `<sub>/<rows>/<id>` или `<sub>/<table>/<name>`; base — N1.4 base по строке.

`apply`: агент (P/09.1 N1.5) читает строки writes из своего хранилища (право чтения, надгробие — его индекс, чтение не удалось — без исхода, повтор); cas — прочитанный индекс, строки нет — "".

В `apply` revision строки пакета — base, у create и new — 0.

В `apply` агент сам конфликт не судит и всегда зовёт дверь: заявка стоит раньше сверки (P/06.1 N3 «пакет» шаги 4, 5), поэтому повтор после потери ответа
получает прежний ответ, а не ложный конфликт.

В `apply` 412 revision moved — исход conflict; 412 row moved — повтор следующим проходом, cas устарел; иной 4xx — refused.

`new_id`: предел: счётчик сдвинули между вызовами — 400 bad_id, исход refused.

При new агент до первого вызова читает `<sub>/next_id`, берёт n + 1 и пишет его в строку domain/edit-ids элементом `<edit id>` (cas): повтор берёт тот же номер, отпечаток прежний.

В пакет идёт строка `<sub>/next_id` {n: номер}; элемент снимается вместе с исходом (OUTCOME_HOLD).

`size`: правка лежит дважды, body и asked; связка в 64 строки — около 50 КиБ, в строку входит 10 таких: честный отказ row_full.

### N1.4 Хранимая правка

```yaml
domain/pending/<член>:   строка держателя; элемент <id> — текст JSON правки
  edit:     {id, seq, what, method, path, body, key, at, base?, by?, iat?, asked}
    id:     "e-" + первые 12 знаков hex sha256(UTF-8(член) ‖ 0x00 ‖ UTF-8(Idempotency-Key))
    seq:    номер приёма
    what:   имена полей тела по возрастанию через «,»
    keys:   строки, которые правка задевает
    method: POST | PUT | DELETE
    path:   путь двери консоли члена
    body:   объект полей
    by, iat: человек и iat его токена
    key:    Idempotency-Key запроса
    asked:  {method, path, body}
    at:     стенные секунды процесса domain
    base?:  revision единицы в копии члена у держателя в момент приёма
writer:     процесс domain
repeat:     тот же id и тот же asked
cancel:     отмены нет
KEPT_LIMIT: forms/runtime-constants.tsv          # ждущих правок на члена
row_full:   потолок строки 524288 байт
reply:      202 {kept: <id>, cluster: <член>, what, note: "kept; <член> applies it when it next reports"}
carry:      pending: [<edit>…]
```

`domain/pending/<member>` — строка держателя; элемент `<id>` — текст JSON правки; `edit.id` — "e-" + первые 12 знаков hex sha256(UTF-8(член) ‖ 0x00 ‖ UTF-8(Idempotency-Key)).

`edit.seq`: номер приёма — значение элемента seq этой строки после +1 при приёме, под тем же CAS.

seq задаёт порядок ждущих
правок члена: по нему назначается base (ниже) и выдаются правки (carry); at — только время для людей и исходов.

`edit.what`: имена полей тела по возрастанию через «,», у POST — с полем domain.ref, без cluster (DELETE — ""); у связки — N1.3b edit.

`edit.keys`: строки, которые правка задевает: `<sub>/<rows>/<id>`, `<sub>/<table>/<name>` (имя строки POST таблицы — по `tables.<t>.key`), у связки — все key её writes; поля нет, это вывод из path и body.

Правила ниже (base, ждущая DELETE, same_path агента) идут по keys, а не по path: две двери одной строки таблицы и связка видят друг друга.

`edit.method`: POST | PUT | DELETE; `edit.path` — путь двери консоли члена: `/<sub>/<rows>`, `/<sub>/<rows>/<id>`, `/<sub>/<table>`, `/<sub>/<table>/<name>`
или /console/batch (N1.3b) (id — местный id единицы из копии члена); `edit.body` — объект полей (DELETE — {}).

`edit.by`, `edit.iat`: человек и iat его токена, если дверь пропустила его строкой кластера цели, а не domain/grants/domain (договор права `write`).

Консоль члена судит человека `edit.by` по своим грантам при применении (P/09.1 N1.5 apply).

Зрителю домена полей by, iat нет: суд домена окончателен.

`edit.asked`: {method, path, body} — запрос двери домена, как его принял процесс: путь N2 с ref и `?cluster=<member>` у PUT и
DELETE, тело с cluster у POST.

По `edit.asked` правку повторяют у нового держателя (глава 8.8 N1.6 apply).

`edit.asked.path` нормализован: у PUT и DELETE — `/domain/<sub>/<rows>/<ref>?cluster=<member found>`, даже если запрос
?cluster= не нёс, при ?id= — ещё `&id=<id>`; у POST — `/domain/<sub>/<rows>` без query; прочий query запроса в path не входит.

Строка `domain/outcomes/<member>` целиком нечитаема — любой приём у этого члена 503 unavailable: id мог быть
исполнен, нечитаемая строка отсутствия не подтверждает (исходы domain/outcomes).

`edit.at`: стенные секунды процесса domain; если по этому id уже записан исход (строка `domain/outcomes/<member>` держателя,
N1.6) — не меньше следующего за его kept_at
числа (nextafter): новый приём того же ключа отличим от прежнего.

Исход, вытесненный из последних 50, границы `edit.at` не даёт:
приём идёт со стенными секундами, совпасть с прежним kept_at он может только при откате часов, это предел.

В форме писателя (дробь не длиннее трёх знаков) граница `edit.at` — не меньше kept_at, округлённого до тысячных, + 0.001:
следующее за kept_at число округлилось бы обратно в kept_at и совпало с ним.

Граница считается точно в десятичной записи; если binary64 значения round(kept_at) + 0.001 не больше binary64
round(kept_at) (шаг binary64 там крупнее 0.001), at — не меньше наименьшего значения формы писателя (дробь не
длиннее трёх знаков), чьё binary64 больше binary64 round(kept_at): у 4503599627370496 — 4503599627370497.

Такого конечного нет (kept_at — наибольшее конечное binary64) — приём 503 {error: "unavailable"}, ничего не
записано.

Без исхода по id граница не действует: at — стенные секунды в форме писателя, перевод часов в три
знака (отсечение или округление) — реализации.

`edit.base`: revision единицы в копии члена у держателя в момент приёма (PUT, DELETE), у строки таблицы — из объекта `domain/members/<member>/tables`, если таблица в domain.view_tables; у POST единицы нет.

Строки шарда с
revision этой единицы в копии нет — base нет, правка идёт без If-Match.

Есть ждущая запись той же строки по keys
(PUT, POST таблицы, put связки) — base = base последней из них по seq + 1 (так применяется её результат, а не прежнее значение), у
последней base нет — base нет и у новой.

Ждущее снятие той же строки (DELETE, delete связки) —
новая правка этой строки отказывается 409 {error: "unit is being deleted"}.

Ждущая правка не применилась (conflict) — следующие того же path тоже дадут conflict: оператор решает заново.

`writer`: процесс domain — приём (N3, дверь консоли домена — глава 8.0 N1.8) и снятие исполненной (N3 «исход»); CAS строки.

`repeat`: тот же id и тот же asked (метод, путь, тело, без полей N1.3a) — 202 с прежней записью, at прежний; иное — 422 {error: "this Idempotency-Key
was used for another edit"}.

Нечитаемая прежняя запись этого id — 422 (ключ не переиспользуется).

`cancel`: отмены нет: принятая правка применяется или получает исход; откат — новая правка.

`KEPT_LIMIT`: ждущих правок на члена; пятьдесят первая — 409 `{error: "kept_full", detail: "<member> has 50 edits waiting"}`.

`row_full`: строка `domain/pending/<member>` с этой правкой не влезает в потолок строки 524288 байт (P/01.1 N1): строка из seq и одной этой правки в форме записи больше потолка — 413 {error: "too large"}.

Когда строка с этой правкой не влезает, а строка из seq и одной этой правки не больше потолка, — 409 `{error: "kept_full", detail: "<member>'s waiting edits fill the row"}`: ждать, пока член применит.

`carry`: ответ держателя (глава 8.3 N1.5) несёт `pending: [<edit>…]` этого члена по seq; элемент seq строки — счётчик, не правка
(правки — элементы e-…; KEPT_LIMIT считает их).

pending есть всегда, когда строка `domain/pending/<member>` прочитана; строки нет или правок в ней нет — pending: [].

Поля pending нет только при нечитаемой строке (исходы domain/pending): «неизвестно», не «пусто».

### N1.6 Исходы у держателя и вид

Исход — форма агента ([глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.5
`outcome`): `{id, status, result, error?, at, what, kept_at}`.

Копия члена несёт исходы полем `outcomes` публикации
(там же, `publication.outcomes`).

```yaml
domain/outcomes/<член>:  строка держателя; элемент <id> — исход (P/09.1 N1.5)
settle:     исход из копии члена
domain/view.pending:   {<член>: <число ждущих правок>}
domain/view.outcomes:  {<член>: [<исход>…]}
```

`domain/outcomes/<member>` — строка держателя; элемент `<id>` — исход (P/09.1 N1.5); OUTCOMES_LIMIT — последние по (at, id) убывая.

`settle`: поле by исхода держатель берёт из своей правки, не из копии члена.

Исход из копии члена принят, если правка с этим id ждёт, kept_at = at правки (обе стороны округлены до тысячных,
P/09.1 N1.5 kept_at), what совпал.

Запись исхода —
затем снятие правки по CAS, если она не менялась.

Исход, чей ключ в publication.outcomes ≠ его id внутри, не
засчитывается: журнал держателя domain.outcome.ignored {member, key, id}, правка ждёт.

`domain/view.pending`: каждый член списка, 0 — ждущих нет, null — строка его ждущих правок
не читается.

`domain/view.pending` считает проход вида (глава 8.1
N3, раз в VIEW_EVERY), не дверь в момент ответа.

`domain/view.outcomes`: строка `domain/outcomes/<member>` по (at, id) убывая.

## N3 Проход

### записать назначение (процесс domain, PUT и DELETE `/domain/placement/<sub>/<ref>`)

0. Заголовки и память повторов (глава 8.0 N1.9) → 400 / 409 / 422 / прежний ответ.

1. Форма, манифест, имена — по порядку N2 → 400 / 404 / 409.

1a. If-Match не равен версии строки: у PUT строки нет — 412 с revision 0, у DELETE — 404 N2 → 412 revision moved.

2. PUT: то же содержимое, что в строке → 200 без новой rev.

3. r = domain/placement.rev + 1; PUT — записать строку `domain/placement/<sub>/<ref>` с rev = r и at; DELETE — удалить
   строку (её нет — 404).

4. domain/placement := {rev: r} по CAS (конфликт — перечитать и повторить шаги 3–4, до 8 попыток, затем 503).

5. Ответ 200.

С ключом шаги 3–4 — одна целевая запись: строка, счётчик и строка заявки ложатся одним пакетом (глава 8.0 N1.9 `write`), конфликт счётчика — те же 8 попыток с шага 1a. Поэтому повтор не находит своей записи с прежним счётчиком и не получает ложный 412.

С ключом шаг 2 ничего не пишет, поэтому строка заявки несёт `index` прочитанной записи.

Ответ агенту (N1.2) строится тем же процессом под тем же мьютексом, что запись: промежуточного состояния ответ не видит.

Обрыв между шагами 3 и 4 — строка новая, счётчик прежний: процесс `domain` при старте и при каждом новом взятии очереди
`domain/signer-turn` (ждущий стал активным, [глава 8.10](08.10-domain.norms.md) N1.7) — до первого ответа агенту в этом
владении — поднимает счётчик: оборваться мог и другой процесс, владевший очередью.

Процесс `domain` так же поднимает счётчик при взятии срока переносом или передачей.

Подъём: на сроке 1 — `rev + 1`; иначе max(rev + 1, целые стенные секунды + 60), строки нет — rev 0: счётчик пришёл из копии или его нет, члены держат `domain/placed.rev` прежнего держателя, а агент назад не идёт.

Предел срока 1: откат хранилища держателя на этом сроке (`restore`, `import`, `recover`, P/01.3) не лечится: счётчик уходит вместе с прочим состоянием, `rev + 1` остаётся ниже `placed.rev` членов.

Выход из предела срока 1 — передача: срок 2 поднимет счётчик по max. Цена закрытия хода — связанные значения вместо точных `rev` во всей приёмке срока 1; она больше редкости хода.

Предел прочих сроков: подъём старше прежних значений, пока прежний счётчик меньше целых стенных секунд нового держателя + 60.

У счётчика нет инварианта набора «`rev` не обгоняет стенные часы», поэтому запас от первого такого подъёма — 0 с: счётчик идёт на 60 выше стенных часов.

Прошедшая секунда прибавляет к запасу единицу; каждая запись и каждый подъём ветвью `rev + 1` отнимают единицу; отставание часов нового держателя отнимает столько же.

Равенство запаса нулю — уже отказ: агенту нужно строго больше. Запас исчерпан — член не получает правок, пока счётчик не обгонит его `placed.rev`.

После подъёма члены перечитывают записи и сходятся (копии пишутся только при отличии —
[глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.5).

Подъём этого владения не подтверждён — CAS счётчика не прошёл за 8 попыток, запись отвергнута или ответа нет
(неизвестный исход): ответ агенту — без `rev`, как при нечитаемом счётчике (исходы `domain/placement`): поле
`carry.placement` опускается целиком, как N1.2 `absent` (форма `CarryPlacement` требует `rev` и `records`); прежний `rev` не
выдаётся, дверь агента не отвечает 503 — прочие поля carry идут.

Перед каждым следующим ответом агенту в этом владении
неподтверждённый подъём повторяется.

Неизвестный исход подъёма — как барьер [договора очереди писателя](../../../common/ru/contracts/turn.md) «Барьер»
(глава 8.10 N1.7): успехом не считается, процесс перечитывает очередь и счётчик и поднимает его по прочитанной версии.

Подтверждённый CAS счётчика этим владением в записи назначения (шаг 4) — тоже подъём.

Повтор шагов 3–4 после конфликта CAS: строка, которую этот проход уже записал или удалил, — его; DELETE не отвечает 404
из-за своего удаления (404 — только строки нет до первого шага 3), повторяется CAS счётчика по перечитанному `rev`; PUT
переписывает строку с новым r.

Восемь конфликтов — 503, правка остаётся, а счётчик — в долгу подъёма этого владения, как
неподтверждённый подъём выше: ответ агенту без `rev`, пока подъём не подтверждён.

### принять правку (процесс domain, дверь консоли домена — глава 8.0 N1.8)

1. Idempotency-Key отсутствует → 400.

1a. `<sub>` из каталога, `<rows>` — unit.rows его манифеста или ключ domain.edit_tables → 404.

1b. Поля, секреты, значения — N1.3 → 400.

2. PUT, DELETE: найти (N1.3 find, refusals); POST: cluster — член → 404 / 503.

2a. PUT, DELETE без ?cluster=, ref в units у двух исполнителей и больше (ранний повтор):
   для каждого исполнителя — id по N1.4 (id зависит от члена) и строка `domain/pending/<member>`; запись этого id
   есть ровно у одного — repeat (202 / 422) у него; у двух и больше — 409 executors (нужен ?cluster=); ни у кого —
   409 executors → 202 / 422 / 409.

   С ?cluster= — шаги ниже у названного члена, как прежде.

3. id = N1.4; прочитать `domain/pending/<member>`: тот же id — repeat (202 / 422).

3a. Секреты N1.3a → конверты m1; ключа члена нет — 503 {error: "unavailable"}, ничего не записано: дальше меряется уже строка с конвертами.

4. Ждущих 50 → 409 kept_full.

   Строка с этой правкой больше потолка (N1.4 row_full) → 413 too large / 409 kept_full.

   Ждёт DELETE того же path → 409 unit is being deleted.

   Base: копия члена; ждёт PUT того же path — base последней по seq + 1.

5. seq строки + 1; edit {id, seq, what, method, path, body, key, at, base?, by?, iat?, asked} → записать правку и seq одним CAS (конфликт — перечитать с шага 3, до 10 раз,
   затем 409 «the pending edits kept changing; ask again»).

6. Ответ 202.

### исход (процесс domain, в проходе главы 8.1)

```
для каждого члена: исходы его копии (глава 8.3 N3 «прочитать копию», поле outcomes публикации) → settle N1.6:
записать domain/outcomes/<член> (обрезать до 50), затем снять правку из domain/pending/<член> по CAS
```

**Гонки.** Приём и снятие — в одном процессе `domain`, CAS строки `domain/pending/<member>`; снятие одного id — только
неизменённой правки.

Локальная правка единицы на члене между приёмом и применением — `If-Match` даёт 412, исход `conflict`: молча не
перезаписывается.

Агент, получивший правку дважды (повтор ответа), — `Idempotency-Key` двери единиц ([P/06.1](../../../06-console/ru/spec/06.1-console.norms.md)) и правило
`kept_at`.

Назначение и единица — разные строки: удаление назначения единицу не трогает.

Обрыв агента между применением
и записью исхода в `domain/outcomes`: правка ещё ждёт и применяется снова — `POST`, `PUT` и `DELETE` дают прежний ответ по `Idempotency-Key`
([P/06.1](../../../06-console/ru/spec/06.1-console.norms.md) N3 «память повторов»).

Новая правка берёт новый ключ (at — N1.4): дверь члена помнит ключ 86400 с, прежний ключ там даёт прежний ответ, а с иным телом — 422 `key reused` и исход `refused`.

Base новой правки берётся
из копии члена, а шард снимка может отставать от значения, уже применённого прежней правкой, поэтому возможен 412 и исход
`conflict` — допустимо, оператор решает заново. Применение агентом —
[глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.5.
