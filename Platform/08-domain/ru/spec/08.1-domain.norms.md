# P/08.1 — Вид домена и теневой режим: нормы

Канон главы 8.1 урока P/08 «Процесс domain» (модуль «Платформа»). Лекция (`ru/08-domain.md`, для человека, в выгрузку не входит),
[контракт](../../spec/08-domain.api.openapi.yaml), [инструкция](08-domain.README.md), [жизненный цикл](../lifecycle.md),
[приёмка](../acceptance/1/README.md), [векторы `view`](../vectors/view/README.md). Здесь — чего кластер не может знать и
что держатель знает о домене по копиям членов: домен, член, держатель, копия; имя единицы в домене `domain.ref`; свежесть
члена и единицы по часам держателя; вид домена `domain/view`, его полнота и поля других глав; теневой отчёт
`domain/shadow` и условие `may_write`; проход держателя, который их строит.

## N1 Форма

**Время.** Поля времени строк и объектов главы — время по [канону N0](../../../01-store/ru/spec/01.1-store.norms.md#время-в-строке): объект `domain/view` — `as_of`.

**Данные** ([каталог](../../../common/data/catalog.tsv)):
- владеет: `domain/view`, `domain/view-rows/<part>`, `domain/ref-claims/<sub>/<sha16>`, `domain/shadow`, `domain/members/<member>/tables/<sub>/<table>`;
- читает: `domain/members/<member>/reported`, `domain/members/<member>/reports/<rev>`, `domain/placement/<sub>/<ref>`, `domain/member-rows/<part>`, `domain/topology`, `domain/keys`.

Вид и теневой отчёт пишет только процесс `domain` проходом держателя (N3). Объекты процесс пишет по правилу очереди [главы 8.10](08.10-domain.norms.md) N1.7 `objects`. Поля вида других глав (`books`, `pending`, `outcomes`, `term`, `shared`) процесс пишет тем же проходом. Форма и смысл полей вида других глав — в главах-владельцах (шапка главы).

`domain/keys` проход читает для поля `trust` (N1.2a; владелец строки — [глава 8.2](08.2-domain.norms.md)). `domain/topology` проход читает для поля `topology` (N1.6a; владелец — глава 8.3). `domain/member-rows/<part>` проход читает — список членов (владелец — глава 8.3). Копии членов проход читает по метке `reported` и поколению ([P/08.3 N1.3](08.3-domain.norms.md) и N3 «прочитать копию»).

Назначения проход читает для
теневого отчёта (N1.6; владелец — глава 8.6).

### N1.1 Домен, член, держатель

```yaml
domain:      набор кластеров-членов под одним корнем доверия (глава 8.2)
member:      кластер M10 (одно хранилище строк, свой raft, свои процессы), принятый в список членов
holder:      ровно один член, на котором работают службы домена
copy:        копия члена у держателя
```

У `domain` ни один raft не охватывает двух членов: у членов нет общей строки, слота, эпохи или объекта.

Список членов для `member` — `domain/member-rows/<part>` у держателя — глава 8.3 N1.1, `domain/member-list/<part>` у члена — [глава 9.1](../../../09-agent/ru/spec/09.1-agent.norms.md) N1.1.

Имя члена — `CLUSTER` его установки (P/04 N1.3a `cluster`), 1–64 знака [a-z0-9-], не пустое.

Держатель — роль члена, не вид кластера. Какой член держатель — решение развёртывания (глава 8.8), не порядок установки.

Копия члена у держателя — то, что держатель принял от члена последним (глава 8.3 N1.3: отчёт поколением и метка `reported`). Домен читает члена только по его копии, к самому члену не ходит.

**Чего кластер не знает.** Кластер отвечает о своих единицах и только о них.

Три вопроса — уровень домена: где единица,
если этот кластер о ней не слышал («не у меня» ≠ «нигде»); в какой кластер ставить новую единицу (назначение — глава 8.6);
полон ли ответ.

Поиск внутри кластера, размещение на воркер, перенос между воркерами — M10, домен их не повторяет.

Воркер не пересекает границу кластера. Эпоха единицы монотонна в своём кластере ([P/03.2 N1.5](../../../03-worker/ru/spec/03.2-worker.norms.md)); домену выдающий эпох не нужен.

### N1.2 Имя единицы в домене

```yaml
ref:         значение поля `domain.ref` строки единицы (сводная таблица P/02.1 N1.2a; у `testsub` и `testsub2` — `name`)
siblings:
no_ref:      манифест без `domain.ref`
no_value:    строка единицы без значения поля `domain.ref` (поля нет или "")
```

Номер единицы (`id`) принадлежит кластеру и в домене не ищется: у манифеста с `unit.id: numeric` id 1 есть в каждом
члене (векторы N5 — такие); у `testsub` id — имя (P/06.1 N1.3), поиск — всё равно по ref.

`siblings`: у одного члена один ref могут нести несколько единиц: основная и прочие записи камеры. `siblings` — не спор: ref — имя для людей и назначения, строку адресует пара (cluster, id). Какая из `siblings` основная, домен не судит: это слово подсистемы.

Правка выбирает одну из `siblings` явно, глава 8.6 N1.3 find.

`no_ref`: манифест без `domain.ref` в каталоге домена не участвует: его единиц нет в виде. У манифеста без `domain.ref` дверь `/domain/<sub>/<rows>` — 404.

`no_value`: строка единицы без значения поля `domain.ref` (поля нет или "") — не единица домена: в `units` её нет.

Строка единицы без значения поля `domain.ref` заявки теневого отчёта не даёт (ни `unmanaged`, ни `conflict`). Строка единицы без значения поля `domain.ref` полноты вида не отнимает.

`may_write` из-за строки единицы без значения поля `domain.ref` не меняется. Пульс единицы без значения поля `domain.ref` в отчёт члена идёт всё равно.

### N1.3 Свежесть члена и единицы

```yaml
LOST_AFTER:  договор наблюдения «Свежесть» (значение там)
member_state: договор наблюдения «Свежесть члена домена»
unit_state:
  live:
  stale:
  configured:
  silent:
```

LOST_AFTER — тот же срок, что у пульса воркера.

`unit_state` — состояние единицы из копии члена.

`unit_state.live`: единица есть в `status[]` пульса воркера (P/03.4 N1.1), и пульса нет в `stale` метки члена (публикация — P/09.1 N1.2; метка — глава 8.3 N1.3).

`unit_state.stale`: единица есть в пульсе, и пульс — в `stale` метки: агент члена не видел его смены дольше порога подсистемы
(P/09.1 N1.2 stale: heartbeat.stale_after, нет ключа — LOST_AFTER) по монотонным часам члена.

Живость воркера — факт кластера, P/04; домен её наблюдает, а не выводит из прихода копии.

`unit_state.configured`: единица есть только в шарде снимка (P/04 N1.3a), ни один пульс её не ведёт.

`unit_state.silent`: член не `ok` (`unseen`, `silent`): единицы его последней копии остаются в виде с этим словом, не удаляются.

Смена пульса — смена его JCS (глава 8.2 N1): `1` и `1.0` в любом поле — не смена.

`unit_state` live и stale — только у члена ok. Первый взгляд этого процесса на пульс — смена при любом состоянии члена (возраст пульса — с него).

У `unit_state.silent` — phase, worker, server и age по происхождению единицы: из пульса — его фаза и возраст,
из шарда — "unobserved" и возраст метки.

Член `unseen`, `silent` или `never` — «не подтвердился», а не «ничего нет»: ответ, которому он нужен, неполон (N1.5).

**Окно после старта и передачи держателя.** Монотонные часы держателя начинаются заново при каждом старте его процесса. После перезапуска того же держателя метки членов остаются в его хранилище, но первый взгляд на метку — не смена: член с меткой — `unseen`, вид неполон, пока процесс не увидит смену. Живой член обновляет метку не реже LOST_AFTER/2 (глава 8.3 N1.3) и выходит в `ok` не позже этого срока. Член, умерший до перезапуска, через LOST_AFTER становится `silent`. Так он не выглядит живым после перезапуска, и правка главы 8.6 по его единице отвечает 503 «не слышно», а не 404 «нигде».

После передачи держателя (глава 8.8) у нового держателя меток нет: поколения отчётов с передачей не едут (глава 8.8), каждый член — `never` до первого отчёта новому держателю, вид неполон. Нового окна «по старой памяти» нет.

### N1.4 Вид домена

```yaml
domain/view:
  as_of:     <стенные секунды держателя на конце прохода>
  holder:    <имя держателя>
  complete:  true | false
  members:   [{name, state: ok | unseen | silent | never, age, class?, url?, servers?}]
  units:     {<sub>: [Unit]}
  backup_short?: {have, need}
  contested: {<sub>: {<ref>: [<member>…]}}
  <fields of other chapters>:
Unit:        {sub, id, ref, cluster, revision, labels?, about?, worker?, server?, phase, age, state, view?, status?}
  id:        id единицы в её кластере (строкой)
  revision:  версия строки единицы из строки шарда, та, что взята правилом duplicate
  worker, server: из пульса (`worker`, поле `server` пульса) или из строки шарда снимка
  phase:     `status[].phase` пульса (P/03.4 N1.1)
  age:       секунды
  labels, about: поле labels и значение поля about.field манифеста из строки шарда
  view:      поля, названные `domain.view` манифеста (P/02.1 N1.2a), из строки шарда
  status:    поля, названные `domain.view_status` манифеста, из элемента status[] пульса этой единицы
round:       «один знак после точки»
order:       (cluster, id, worker)
duplicate:   id в двух шардах снимка одного члена
no_ref:      элемент пульса, у id которого нет строки в шарде своего члена
executors:   ref, все члены которого — исполнители его назначения
as_of:       у команды view — стенные секунды её процесса на конце прохода входа
```

`domain/view` — форма целого вида: её считает команда view.

Раскладка `domain/view` на объектах — N1.4b, голова раз в VIEW_EVERY с.

`complete` команды view: true ⟺ каждый член `ok` и `contested` пуст.

`complete` прохода — круг, N1.4b complete.

`members[].age` — секунды с последней смены метки, которую видел
этот процесс, без смены — с первого взгляда; один знак после
точки (N1.4 round).

`members[].age` у `never` — null.

Порядок `members` — по name.

`members[].url` — адрес входа члена из объекта domain/servers копии.

Держатель берёт `members[].url`, только если это https с хостом, без учётных данных и фрагмента, иначе поля нет, журнал:
значение идёт в браузер, а коробка стоит на улице.

Нет `members[].url` — член за NAT, ссылка не строится.

`members[].servers` — [{name, online?, labels?, pulse?}] по name в байтах UTF-8: имена из объекта
domain/servers копии, поля server её пульсов и строк шардов.

`members[].servers[].online` — есть пульс
этого сервера: true, если член ok и пульс свеж (N1.3), иначе false.

Пульсов сервера нет —
поля `online` нет: о сервере без воркера неизвестно.

`members[].servers[].labels` — из domain/servers.

`members[].servers[].pulse` — `{<sub>: {<field>: <value>}}`: поля domain.view_pulse манифеста из пульса
воркера этого сервера, из первого по ключу в байтах UTF-8, *_secret срезаны.

`members[].servers[].pulse.<sub>.stale: true` — ключ этого пульса в stale последней публикации члена
(P/09.1 N1.2: не менялся дольше LOST_AFTER по часам агента), по подсистеме; нет — поля нет;
слово сервера, а не единицы.

Нет копии или ни одного имени — поля `members[].servers` нет.

`units` содержит каждый манифест каталога с domain.ref (N1.2), ключ есть и у пустого.

`backup_short` — есть камеры, а взявших копию меньше BACKUP_HOLDERS: have — взявших, need — BACKUP_HOLDERS (глава 8.8 N1.5 new_camera).

`contested` — ref, который заявляют два члена и больше, кроме ref исполнителей (executors
ниже); его единиц нет в units.

Ключ `contested` есть у каждого манифеста с domain.ref, без спорных — {}.

`<fields of other chapters>`: trust — N1.2a; knocking — N1.7; topology, relay_refused — N1.6a;
books — глава 8.5; pending, outcomes — глава 8.6; url — договор пересылки; term — глава 8.8;
shared — глава 8.9; reports — N1.7; role_spread — глава 8.4.

`Unit.ref` — N1.2; `Unit.cluster` — член.

`Unit.revision` непрозрачна для читателя.

У чужой записи `Unit.revision`
— версия для правки.

`Unit.worker`, `Unit.server`: нет — поля нет.

`Unit.worker` пульса
без поля worker — имя из ключа пульса `<sub>/heartbeats/<name>`.

`Unit.phase` у `configured` — "unobserved".

`Unit.age`: у live/stale — с последней смены пульса, у configured — с последней смены метки. `Unit.age` — с одним знаком после точки.

`round`: «один знак после точки» — округление точного десятичного значения секунд (не двоичной дроби) до 0.1,
половина — от нуля: 0.25 → 0.3, 60.05 → 60.1.

`Unit.labels`, `Unit.about`: поля нет в снимке или значение пусто — поля нет. `Unit.labels` и `Unit.about` служат суду по цели (договор права), чтобы вид фильтровался не грубее консоли.

В `Unit.view` секретных полей нет (P/06.2 N1.4). В `Unit.status` ключи *_secret внутри срезаны на любой глубине (P/06.2 N1.4).

У `Unit.status`: элемента нет (`configured`), списка нет или ни одного поля нет — поля status нет. Пульс нечитаем — `Unit.status` как при отсутствии элемента.

`order`: units в каждой подсистеме — по (cluster, id, worker) в порядке байтов UTF-8. Единица в пульсах двух воркеров одного члена — два элемента (её ведут оба; теневой отчёт разбирает, кто из них действует).

`duplicate`: id в двух шардах снимка одного члена — строка с большей revision; при равной — из первого шарда по ключу
в порядке байтов UTF-8.

`no_ref`: элемент пульса, у id которого нет строки в шарде своего члена, в units не входит (у Unit нет ref) и не заявляет;
так же строка шарда без значения domain.ref (N1.2 no_value).

Исполнители ref — {cluster} ∪ copies его назначения (глава 8.6 N1.1); origin члена в это
множество не добавляет и из него не исключает.

`executors`: ref, все члены которого — исполнители его назначения, не contested: единицы всех исполнителей — в units. Роль исполнителя (основной или резерв) — забота подсистемы, вид её не показывает.

Член вне множества исполнителей, давший тот же ref, —
contested.

Назначения прохода не прочитаны (N3 шаг 3a) — исключения `executors` нет: ref у двух членов и больше — contested. При `executors` полнота вида — по N3 шаг 5.

`as_of` команды view: приёмка его не сравнивает.

Исходы семьи пульсов (`heartbeats`, [P/03.4](../../../03-worker/ru/spec/03.4-worker.norms.md)) применяет живой читатель объекта из
хранилища — проход держателя, читающий объекты копии члена: пульс, нечитаемый целиком, в вид не попадает.

Чистая функция
вида (команда `view`, вектор [`view`](../vectors/view/README.md)) получает уже прочитанное: форма её входа — `ViewInput`
(`worker` может прийти из ключа, `instance` не обязателен), не семья.

Заявки теневого отчёта — по строгому `status.items`
(N1.6 `claim`).

### N1.4a Таблицы вида

Чужому кластеру нужны не только единицы с `ref`: консоль видит настройки и тома члена, манифесты без `domain.ref` и единицы без значения `ref`, а правила и права стоят на таблицах. Таблицы в `domain/view` не входят: вид пишется каждые 3 с, а таблицы меняются редко. Спор `ref` (`contested`) строк таблиц не снимает: строка адресована кластером и ключом.

```yaml
domain/members/<member>/tables/<sub>/<table>:
  {cluster, ts, refused?, rows}
manifest:  domain.view_tables: {<table>: [<field>…]}
refused:
stale:
leave:
versions:
move:
```

`domain/members/<member>/tables/<sub>/<table>` — объект держателя; писатель — проход держателя, N3 шаг 3b. Объект `domain/members/<member>/tables/<sub>/<table>` — снимок P/04 N1.3b из копии члена как есть; cluster равен имени члена.

`manifest`: таблица `domain.view_tables` — объявленная таблица, не service: true, не из domain.kept, или unit.rows. Поля таблицы `domain.view_tables` — из её fields или unit.fields, не *_secret, не blob, held_by — только у таблицы мест (P/02.1, связи 137–143). `manifest`: ключ `domain.view_status` манифеста — N1.4 Unit status.

`refused`: таблица не вошла, строк нет. При `refused` читатель показывает, что данных нет, а не что таблица пуста.

`stale`: объект — наблюдение: ts — часы члена. У молчащего члена объект таблицы — прежний объект, живость читатель берёт из members[].state вида.

Для объектов таблиц после смены держателя — так же: член unseen, пока не пришёл отчёт.

`leave`: проход, увидев уход члена (N3 шаг 1), снимает его объекты. Ошибка снятия объектов ушедшего члена — следующий проход.

Вернувшийся член с тем же именем
чужих строк не видит: дверь отвечает по списку членов, объекты сняты раньше приёма.

`versions`: ключа нет у манифеста члена, а у манифеста держателя есть, — объекта нет: дверь 404 not reported yet, то же, что отчёт ещё не пришёл;
различать незачем, данных нет в обоих случаях.

`move`: объекты не входят в резервную копию домена: новый держатель пишет их тем же шагом из принятых копий.

### N1.4b Вид по разделам

Форма полей N1.4 та же, команда `view` считает целый вид; меняется раскладка: вид не пишется одним объектом и цена прохода не растёт с числом членов. Растёт возраст.

```yaml
domain/view:              голова — as_of, holder, url, term, complete, topology, trust, knocking, knocking_count, relay_refused, shared, books, role_spread, counts, parts
domain/view-rows/<part>: {part, as_of, members, units, contested, reports, pending, outcomes}
names:    domain/view.<поле> глав 8.5, 8.6, 8.1 N1.7 о полях на члена
knocking: стуки памяти KNOCKS; knocking_count
reader:   воркер на домене
round:    VIEW_MEMBERS членов в секунду
complete:
contested: domain/ref-claims/<sub>/<sha16 ref>: {<member>: <as_of>}
member_list:
stale:
shadow:
```

Голова `domain/view` — всё, что не на члена.

Голова `domain/view` пишется раз в VIEW_EVERY.

holds и view.url перехода 2 читают только голову `domain/view`.

`domain/view-rows/<part>` — объект P/05 на непустой раздел.

`names`: `domain/view.<field>` глав 8.5, 8.6, 8.1 N1.7 о полях на члена — поле строки раздела этого члена; их читатель читает строку, а не голову.

Строки раздела нет: круг её ещё не построил — ответ неполон, как complete: false.

`knocking`: голова несёт стуки памяти KNOCKS.

`knocking_count` — сколько лежит в domain/knocks/*, сами они — дверь P/10 N1.2b постранично.

`reader`: воркер на домене берёт единицы и члены строками разделов из parts головы, правом worker.reads domain/view-rows/ (V/01.7): голова их не несёт. Строка раздела пишется только при отличии, поэтому воркер на домене читает раздел, сменивший as_of.

`round`: VIEW_MEMBERS членов в секунду, статус измерения: не измерено. Раздел — единица работы, перечень непустых — parts головы, круг = члены / бюджет; строка пишется только при отличии.

`complete`: последний круг закрыт и все его разделы полны. После смены держателя и старта процесса `complete` — ложь, пока круг не закрыт.

`contested`: круг пишет заявку члена в domain/ref-claims и снимает ту, которую член больше не даёт. Строка domain/ref-claims с двумя членами — спор.

Дверь правки судит ref свежим чтением строки domain/ref-claims, не видом;
исполнители — назначение, прочитанное с заявкой.

Предел `contested`: камера переехала — ложный спор до её отчёта; спор виден со сдвигом до круга.

`member_list`: в виде нет: список — строки раздела, дверь P/10 N1.2b.

`stale`: член камеры выходит из unseen после перезапуска держателя по received_at метки, а не по следующему отчёту (N1.3).

`shadow`: теневой отчёт и clean_streak — по закрытому кругу, отсчёт SHADOW_STALL — на проходе раздела пары. domain/shadow пишется раз в круг. При малом домене круг короче VIEW_EVERY и всё как прежде.

### N1.5 Полнота ответа

Ответ домена о единицах — сводка по копиям: частичная и устаревшая на ограниченную величину.

Ответ ДОЛЖЕН нести свою неполноту полем, а не отсутствием: `complete: false`, член `unseen`/`silent`/`never`, `contested`. Короткий список НЕ ДОЛЖЕН выдаваться за полный. «Не найдено» при полном ответе — факт о домене; при неполном — факт о сети: отказ называет, кого не было слышно (N4).

Каждое производное от копий (вид, книги главы 8.5, имена главы 8.5, тревоги урока P/10) — наблюдение, а не власть: оно не даёт права записи в члене. Каждое производное от копий несёт свой список отсутствующих.

### N1.6 Теневой отчёт

```yaml
shadow:
  inputs:    назначения domain/placement/<sub>/<ref> {cluster, copies} (глава 8.6 N1.1); копии членов (N1.3)
  claim:     элемент status[] пульса воркера в копии члена → (sub, ref, id, member, worker, epoch, revision, observed_revision)
  kinds:
    lagging:
    stalled:
    orphaned:
    unmanaged:
    conflict:
    stale_epoch:
    unknown:
  facts:
  grain:
  orphaned_from:
  unread:
  findings_order:
  SHADOW_STALL:  forms/runtime-constants.tsv       # с
  silent_member:
  exit:          may_write
  SHADOW_CLEAN:  forms/runtime-constants.tsv
  report:        {counts: {lagging, stalled, orphaned, unmanaged, conflict, stale_epoch, unknown},
                  findings: [{kind, sub, ref, cluster?, worker?, detail}], clean_streak, may_write, why}
```

`shadow` считает проход держателя вместе с видом, ничего не пишет в члены.

`inputs`: назначения проход читает один раз (N3 шаг 3a).

Исполнители ref — {cluster} ∪ copies; origin множество не меняет (origin = cluster — исполнитель как cluster).

`claim`: ref — по id единицы из шарда снимка этого члена; элемент без ref (нет строки в шарде) — заявки нет. Элемент не по форме P/03.4 N1.1 (epoch, revision, observed_revision — не целые и т. п.) — заявки нет. Элемент phase: sealed (эпоха не взята, P/03.4 N1.1, P/03.5 N3) — заявки нет. Элемент phase: unreadable (эпоха не взята, P/03.3 N3 шаг 2) — заявки нет.

Единица без
значения domain.ref (N1.2 no_value) — заявки нет: ни unmanaged, ни conflict.

Действующая заявка — только из пульса единицы в состоянии live (N1.3): последний пульс умершего воркера
устаревает и заявлять перестаёт сам.

`kinds`: lagging — норма; stalled, orphaned, conflict и stale_epoch — отказы; unmanaged — измерение.

`kinds.lagging`: заявка с revision > observed_revision, отсчёт SHADOW_STALL не вышел.

`kinds.stalled`: заявка с revision > observed_revision, отсчёт SHADOW_STALL вышел.

`kinds.orphaned`: назначение есть, действующей заявки ref от его cluster нет дольше SHADOW_STALL — с появления назначения или с пропажи последней действующей заявки. Пока SHADOW_STALL для `orphaned` не вышел, находки нет (контроллер члена ещё не разместил).

`kinds.unmanaged`: действующая заявка ref без назначения.

`kinds.conflict`: действующие заявки ref у двух членов, не все из которых — исполнители назначения ref; или у двух
воркеров одного члена с равной эпохой по одной единице (тот же id; N1.2 siblings); или у члена, который не исполнитель назначения.

`kinds.stale_epoch`: заявка из живого пульса с эпохой ниже наибольшей эпохи этой единицы (ref и id) среди заявок из живых пульсов того же члена в состоянии ok; такая заявка не действующая. Равная наибольшая эпоха у двух воркеров по одной единице (тот же id) — conflict; разные id одного ref — разные единицы (N1.2 siblings), не спор.

`kinds.unknown`: назначение на члена не ok или на имя вне списка членов (detail называет состояние или «not a member»).

`facts`: назначенный не заявляет (orphaned) и заявляет неназначенный (conflict) — два разных факта: назначение c → m2
при действующей заявке только у m1 даёт обе находки.

`grain`: lagging, stalled, unmanaged, stale_epoch — находка на заявку (cluster, worker); conflict — одна на ref (cluster — лишний член, если он один; у двух воркеров одного члена с равной эпохой — этот член); orphaned, unknown — на назначение (cluster назначения). Находки lagging и stalled — только у действующих заявок.

`orphaned_from`: первый проход без действующей заявки назначенного ref или первый взгляд на назначение. Назначение — тройка (sub, ref, cluster): смена цели и возврат к прежней — новое назначение, отсчёт заново.

Отсчёт `orphaned_from` идёт и при члене не `ok`: находка пока `unknown`, член снова `ok`
без заявки и срок вышел — `orphaned` в том же проходе, заявка вернулась — отсчёт снят.

`unread`: назначения прохода не прочитаны (N3 шаг 3a) — отчёт этого прохода не строится: domain/shadow не переписывается
(остаётся прежний), clean_streak не растёт и не сбрасывается, отсчёты orphaned_from и SHADOW_STALL не начинаются
и не сбрасываются.

`findings_order`: по порядку видов в counts, затем (sub, ref, cluster, worker) в байтах UTF-8.

SHADOW_STALL у class camera — max(60, 3 × every метки) (P/08.3 N1.1a). SHADOW_STALL считается по монотонным часам держателя: время отставания без смены observed_revision этой пары (член, воркер, ref) — от позднейшего из: последней смены observed_revision, начала отставания (проход с revision > observed_revision после прохода, где заявка пары не отставала; единица, долго стоявшая без отставания, с новым revision — lagging, не сразу stalled); и время без действующей заявки назначенного ref. Оба отсчёта SHADOW_STALL — с первого взгляда этого процесса на пару или назначение, при любом состоянии члена. Счёт истёк — время строго больше SHADOW_STALL: при ровно SHADOW_STALL ещё нет (оба счёта).

`silent_member`: заявки члена не `ok` (`unseen`, `silent`, `never`) не действующие. Назначение на члена не `ok` — не orphaned, а неизвестно (`unknown` в findings, в счёт отказов не входит).

`exit`: may_write ⟺ unmanaged == 0 ∧ no failures (stalled, orphaned, conflict, stale_epoch) ∧ clean_streak ≥ SHADOW_CLEAN.

`SHADOW_CLEAN`: проходов подряд без находок; любая находка или неизвестно обнуляет счёт.

`may_write` — условие, при котором домену будет разрешено размещать единицы самому. В модуле домен сам не размещает (назначение пишет оператор, глава 8.6).

Отчёт — измерение модели: каждая
`unmanaged` — единица, которую модель домена не описывает.

## N2 Двери

Своих дверей у главы нет.

Вид и теневой отчёт отдаёт консоль домена дверями `GET /domain`, `GET /domain/<sub>/<rows>`, `GET /domain/shadow` — урок P/10 (P/10-01; [N1.2a](../../../10-domain-console/ru/spec/10-domain-console.norms.md)): объект `domain/view` как есть плюс `age`, единицы подсистемы из вида, отчёт последнего прохода. Содержимое дверей `GET /domain`, `GET /domain/<sub>/<rows>`, `GET /domain/shadow` — N1.4, N1.6 этой главы.

Команда `view` реализации (Решает реализация п. 1): вход — файл проходов (N5), выход — JSON `{view, shadow}` последнего прохода. В выходе команды `view` `shadow` — отчёт последнего прохода, который его строил, N1.6 `unread`; ни один не строил — `null`. Код выхода команды `view`: 0 — вычислено, 2 — вход не по форме N5. Команда `view` — та же функция, что у прохода держателя, без хранилища.

Нативный вход камеры. В `ViewInput` явно переданный `silent_after` выбирает свежесть камеры для этого прохода; без него вход моделирует сервер. Это абстракция команды для `Entry.class` и `received_at` метки, которых её закрытый вход не несёт. При первом взгляде на существующую метку камеры команда задаёт время её приёма монотонным `at` этого прохода: член `ok`, пока метка существует и возраст с этого приёма или последней наблюдённой смены метки не больше `silent_after`, и `silent`, когда больше. Во входе камеры команды ни разу не виденная метка — `never`; исчезнувшая — `silent`, как в N1.3. Во входе команды сервер сохраняет обычное первое `unseen` до наблюдённой смены метки.

Абстракция камеры у команды не меняет работающего держателя: класс берётся из принятой записи участника, время приёма — из настоящей метки, не из времени heartbeat. Ни класс, ни поле приёма не выводятся из объектов копии.

## N3 Проход

### проход держателя — вид и теневой отчёт (голова раз в VIEW_EVERY, разделы кругом N1.4b)

Шаги идут по разделам круга над их членами. Шаг 7 пишет строку раздела при отличии, голову — раз в VIEW_EVERY; шаг 5 — `complete` N1.4b. Шаги 3a, 6 — раз в круг (N1.4b `shadow`).

1. Прочитать список членов (глава 8.3) и метку каждого члена. На шаге 1 член без метки — never, если этот процесс его метки не видел, иначе silent с прежней копией (N1.3). На шаге 1 ушедший из списка — забыть (N1.3 leave). На шаге 1 смена метки на глазах — сброс возраста.

   На шаге 1 первый взгляд процесса на метку — не смена (unseen, N1.3; камера — N1.4b stale).

   На шаге 1 `domain/member-rows/<part>`, `domain/keys` или `domain/topology` есть, но
   не читаются — прохода нет: domain/view и domain/shadow не переписываются, clean_streak и отсчёты — как у `unread` (N1.6),
   журнал без значения: нечитаемое не подменяется пустым списком.

2. Для каждого члена не never: копия — отчёт поколения метки (глава 8.3 N3 «прочитать копию»), у пропавшей метки — прежняя копия процесса. На шаге 2 копия не читается — член silent. На шаге 2 метка читается, поколения нет или sha256 не тот: silent и при первом взгляде процесса, не unseen. На шаге 2 у члена, silent при читаемой метке, reports — поля этой метки, как у любого члена с меткой, N1.7.

3. Для каждого манифеста каталога с domain.ref: units из пульсов и шардов каждой копии (N1.4). На шаге 3 id уже из пульса — шард его не дублирует. На шаге 3 строка без значения domain.ref — не единица (N1.2 no_value).

3b. Для каждого манифеста с domain.view_tables и каждой копии: поколение копии сменилось с прошлого прохода или процесс её ещё не разбирал — для каждой таблицы взять объект `<sub>/snapshot-tables/<table>`. На шаге 3b объект `<sub>/snapshot-tables/<table>`, которого нет в копии, или не по семье, или чей cluster не имя члена, — не трогать, журнал без значения. На шаге 3b для объекта `<sub>/snapshot-tables/<table>`, который есть в копии, по семье и чей cluster — имя члена: если rows или refused отличается от записанного → записать `domain/members/<member>/tables/<sub>/<table>` (глава 8.10 N1.7 objects).

   На шаге 3b ошибка записи или очередь не подтверждена — копия не считается разобранной, следующий проход повторит
   независимо от поколения.

   На шаге 3b вид пишется независимо (N1.4a).

3a. Прочитать назначения `domain/placement/<sub>/*` — один раз на проход: это чтение служит шагу 4 и теневому отчёту (шаг 6). На шаге 3a назначения не прочитаны — назначений этого прохода нет.

4. Ref, который дают два члена и больше, кроме ref, все члены которого — исполнители его назначения шага 3a (N1.4 executors), → contested, единицы этого ref из units снять. На шаге 4 ref, который дают два члена и больше и все члены которого — исполнители его назначения шага 3a (N1.4 executors), не contested: его единицы остаются в units.

5. complete — N1.4b: круг закрыт, все разделы полны (член ok, contested пуст).

6. Теневой отчёт по N1.6: назначения шага 3a; заявки; виды; clean_streak и may_write. На шаге 6 назначения не прочитаны — отчёт этого прохода не строится (N1.6 unread).

7. Записать domain/view (put объекта); отчёт — в память прохода и в объект domain/shadow тем же проходом. На шаге 7 отчёт не построен — domain/shadow и память отчёта прежние.

**Гонки.** Копии членов читаются в разные моменты: вид — наблюдение, а не снимок.

Член может поменять метку между шагами 1
и 2: проход берёт поколение прочитанной метки, следующий проход — новое.

Два прохода держателя (держатель один, глава 8.8)
не пересекаются.

После перезапуска держателя члены `unseen` до первой увиденной смены, `clean_streak` — 0.

Ошибка записи
`domain/view` не меняет прежний объект; дверь отдаёт прежний вид с его `as_of`.

Обрыв между записью вида и теневого
отчёта — вид нового прохода, отчёт прежнего: следующий проход пишет оба; расхождение одного прохода допустимо.

Сбой чтения или записи части прохода
прерывает этот проход: записанное остаётся, остальное делает следующий.

При сбое части прохода сверка людей ([глава 8.4](08.4-domain.norms.md) N3: `domain/disabled`, метки удаления, срок, новые виды, роль `admin`, у каждой своё условие) и резервная копия — свои работы, они идут.

## Решает реализация

Реализация обязана назвать в своём описании:

1. **команду `view`** для приёмки — шаблон с `{input}`; её вызов и вывод — дверь `view` словаря «Стенда домена», формы — N5;
2. **как проход держателя хранит память теневого отчёта** (начало отсчёта SHADOW_STALL по паре, время появления назначения или пропажи последней действующей заявки, `clean_streak`) между проходами; после перезапуска она пуста;
3. **порядок полей JSON** вида — свободен; порядок элементов массивов — N1.4 и N0.
