### N1.5 The token at the worker and the check at the recipient

<!-- req: P/03.7-R009 -->

The local policy selector is [`token-cache.machine.yaml`](../forms/token-cache.machine.yaml) and [effect boundary](../forms/README.md#worker-policy-machines). Capture, IO and cryptography still follow the ordinary procedures below.

<!-- req: P/03.7-R050 -->

A worker's token is a domain token ([domain token contract](../../common/contracts/domain-token.md) «The token», owner P/08.2) with `kind` of a kind of the manifest. The holder's signing key is not handed to the worker, nor is the member's key: the token is requested by the worker that needs it, through the agent of its own cluster.

<!-- req: P/03.7-R052 -->

Except for `keep: true` (P/03.7-R053), the token lives only in the worker's memory: not in a row, not in a book, not in a report, not in the log, not in a
copy.

<!-- req: P/03.7-R053 -->

There is one exception — a kind with `keep: true` of the manifest: the worker also holds the token as the file `<worker state dir>/tokens/<kind>-<sha16(ref)>`, mode 0600, in an envelope of the sealing contract with the context of this path. The owner of the token file for `keep: true` is the kind, not the camera.

<!-- req: P/03.7-R055 -->

At start the worker reads its retained token file for `keep: true`, to work while the domain is silent.

<!-- req: P/03.7-R056 -->

For a retained token with `keep: true`, the term is judged by the receiver, not by the box clock: an expired file is not thrown away but is replaced after the refusal `expired`.

<!-- req: P/03.7-R057 -->

If the retained token-file envelope does not open, the worker treats it as if there were no token file.

<!-- req: P/03.7-R058 -->

A new token with `keep: true` replaces the retained token file only after the first request accepted with it; until then both old and new tokens are in memory.

<!-- req: P/03.7-R059 -->

For a kind with `keep: true`, while the worker holds a token with `current`, it does not request another token.

<!-- req: P/03.7-R060 -->

For a kind with `keep: true`, on `unknown_key` for a token with `current`, the worker waits rather than requests another token.

<!-- req: P/03.7-R061 -->

A token with `keep: true` does not go into a row, a book, a report or the log either. The limit of retaining a token with `keep: true`: theft of the box gives that token until revocation.

<!-- req: P/03.7-R063 -->

The worker requests a token by the local door of the agent: [local token door contract](../../common/contracts/local-token-door.md) (owner
chapter 9.1; socket `<AGENT_TOKEN_DIR>/<W2C_ROLE>.sock`).

<!-- req: P/03.7-R010 -->

The recipient is the worker or the door of the member to which the token is addressed.

<!-- req: P/03.7-R064 -->

The check is the function `token` of the [domain token contract](../../common/contracts/domain-token.md) «The check» with `expect`: `kind` — the kind it expects, `cluster` — its own cluster (the key is required, not `null`: `null` — only with `kind: person`), `audience_claim` — from the declaration of the kind. A token in whose audience there is no recipient cluster is `wrong_audience`. A token of a kind other than the recipient expects is `wrong_kind`.

<!-- req: P/03.7-R067 -->

Then the recipient checks its own claims (`ref_claim` — its own unit, for `scenario` — `acts`). The meaning of the recipient's own claims (`ref_claim`, `acts`) is the subsystem's.

### Data families (built from the standard files)

The form of the rows and objects that the chapter owns by the [catalog](../../common/data/catalog.tsv) is the JSON Schema 2020-12 of the family. An instance of a row is `{key, row}`, of an object `{key, object}`; the key is the grammar of the column `key` of the catalog. The fields of `row` are the values of `items` after the [codec](../../common/data/codec.tsv): the writer checks the schema and its `$defs.writer`, the reader the schema (layer 3 — the words `x-*` of the schema). Unreadable — the row did not decode or did not pass the schema in the reader's mode; the outcome is by the table of outcomes of the family: the path is a prefix of the path of the refusal (empty — the whole row); with several paths of refusal the outcome of the least priority applies.
