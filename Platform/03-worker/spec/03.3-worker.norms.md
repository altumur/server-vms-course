### N1.2 Loop timings

<!-- req: P/03.3-R005 -->

Settings are [runtime-constants.tsv](../forms/runtime-constants.tsv).

<!-- req: P/03.3-R013 -->

WAKE_GAP_MS / 1000 gives seconds without rounding.

<!-- req: P/03.3-R014 -->

LEASE_TTL, LEASE_MARGIN, LEASE_EVERY, again — the lease timings, chapter 3.2 N1.2

<!-- req: P/03.3-R015 -->

HEARTBEAT_EVERY, PASS_SHARE, RETRY_MIN, RETRY_MAX: runtime-constants.tsv

<!-- req: P/03.3-R016 -->

**`POLL`.** The implementation chooses an idle pause or long polling and any rhythm within WAKE_GAP and PASS_SHARE. The exact rhythm is not judged; the heartbeat rhythm of chapter 3.4 and the reaction of the loop within the bounds of the scenario steps remain mandatory.

<!-- req: P/03.3-R017 -->

**`WAKE_GAP`.** WAKE_GAP_MS / 1000. **`WAKE_GAP`.** The conversion gives exact seconds without rounding. **`WAKE_GAP`.** an event pass is no earlier than this gap

<!-- req: P/03.3-R020 -->

An event pass is no more often than PASS_SHARE pass durations for long polling

<!-- req: P/03.3-R021 -->

**`watchdog.notify`.** from the loop, not from the stand-in. **`watchdog.notify`.** WatchdogSec of the unit is the contract of the environment file «Constants and units»

<!-- req: P/03.3-R024 -->

**`retry`.** the backoff of repeating a failed start of a unit. **`retry.rule`.** The delay after failure n is min(Max, Base·2^(n−1)) × a uniform sample from [1−Jitter, 1+Jitter], with n starting at 1, Base = RETRY_MIN and Max = RETRY_MAX. The cap applies before jitter; the final delay need not remain inside RETRY_MIN..RETRY_MAX. The jitter parameter Jitter is in (0, 1], default 0.5; zero is refused. The formula and mandatory jitter are normative; only the exact sampled pauses are not judged. Counting, reset and stalled follow the rules below.

<!-- req: P/03.3-R025 -->

**`retry.rule`.** only failures of the start and of the work of a unit count — a move, fencing and a new name do not change the count. **`retry.rule`.** the count is reset on any of three: after RETRY_MAX of continuous stable work, by the word of the subsystem (its answer «stable»), when the unit is confirmed absent from the desired (the assignment) — an unconfirmed read of the assignment is not absence. **`retry.rule`.** a move does not count as a failure; a unit that has left the worker resets the count when it is confirmed absent from the assignment.

<!-- req: P/03.3-R028 -->

**`retry.stalled`.** the exponential base before jitter has reached RETRY_MAX — status[].stalled: true in the heartbeat (chapter 3.4 N1.1) until the count is reset. **`retry.stalled`.** the subsystem asks with the library word stalled(id) (chapter 3.1 N2)

<!-- req: P/03.3-R006 -->

The stand-in timings (`stand_in`) and the memory budget (`memory`) are [chapter 3.4](03.4-worker.norms.md) N1.2.

<!-- req: P/03.3-R030 -->

The rival's mark
(`contend`) and places (`places`) — [chapter 3.2](03.2-worker.norms.md) N1.2.

## N3 Procedures

### loop() — one turn

<!-- req: P/03.3-R008 -->

```
1. if nobody or not writing_allowed: «rejoin()» (chapter 3.2 N3 «nobody and getting the name back»);
   no name obtained → only the search/the rival's mark and waiting; do not run steps 2–5
```

<!-- req: P/03.3-R031 -->

```
2. the reconciliation pass: read the assignment; an assigned unit without a row or with a tombstone is not started until the next
   pass (the placement row is the controller's business); for each assigned unit that is absent: open the secrets
   (chapter 3.5 N3 «open»: not opened — Sealed, do not take the epoch) → «take_unit_epoch» →
   check the gate and may_act again immediately before start_unit; a refusal → do not start;
```

<!-- req: P/03.3-R032 -->

```
   a led unit absent from the assignment → cancel its unfinished starts, stop_unit;
```

<!-- req: P/03.3-R033 -->

```
   revision grew → with the gate open and may_act, accept the restart attempt: stop_unit (the subsystem learns it by the word restarting(id), chapter 3.1 N2) and start
   under the same epoch/lease through the local transition of chapter 3.2 N3 «take_unit_epoch», without a new issue and without resetting last;
```

<!-- req: P/03.3-R034 -->

```
revision grew and (the gate is closed or may_act is false) → the change of revision waits;
the former unit runs only while may_write allows;
```

<!-- req: P/03.3-R035 -->

```
   born changed (the row was deleted and created anew — a new life, the row check contract, born) → stop_unit, release
   the epoch and take it anew — a new issue, new bindings `of`, as for a deleted and created one (sc. 06); the state
   of the unit the new life writes with its own born and revision (chapter 3.6 N1.7);
```

<!-- req: P/03.3-R036 -->

```
   a crashed process of a unit (an answer of the subsystem) → a raise under the same epoch (chapter 3.2 N3 «take_unit_epoch(unit)», raise)
   after the retry pause of N1.2;
```

<!-- req: P/03.3-R037 -->

```
the row of an own unit does not read by its type (the row check contract «Unit row») → a started unit runs with the last read row,
   `why` of the heartbeat element — «row unreadable: <reason>»;
```

<!-- req: P/03.3-R054 -->

```
the row of an assigned unit is unreadable by its type, and this worker has never successfully read it by that type
→ the unit is not started, the epoch is not taken;
the heartbeat element is {id, phase: "unreadable", why: "row unreadable: <reason>", revision?},
without epoch or observed_revision; revision is the row revision if that revision is readable, otherwise revision is absent (chapter 3.4 N1.1);
```

<!-- req: P/03.3-R055 -->

```
each read of an own unit row that is unreadable by its type → `garbled_rows` of the heartbeat + 1 (chapter 3.4 N1.1);
```

<!-- req: P/03.3-R056 -->

```
a read of the assignment or of rows broken off by an error —
   `pass_failures` + 1;
```

<!-- req: P/03.3-R038 -->

```
in the reconciliation pass, each unit is handled in its own attempt;
a unit with a lost lease is stopped by «lease_step»;
```

<!-- req: P/03.3-R039 -->

```
3. the pump: events (`append`, the contract of the object store client `ops`), requests (chapter 3.6 N3 «holder's look»), commands (the marks
   `objects/<sub>/commands/<rid>`, P/06.4 N1.5 `mark`)
```

<!-- req: P/03.3-R040 -->

```
4. if clock − start_of_previous_lease_step ≥ LEASE_EVERY or again: «lease_step()» (chapter 3.2 N3)
```

<!-- req: P/03.3-R041 -->

```
5. if clock − previous_heartbeat ≥ HEARTBEAT_EVERY: the heartbeat (chapter 3.4 N1.1)
```

<!-- req: P/03.3-R042 -->

```
6. watchdog notify; a pause until POLL or until an event (long polling)
```

<!-- req: P/03.3-R043 -->

```
each step in its own attempt and under the marker guarded(step name) for the stand-in (chapter 3.4 N3 «stand_in()»)
```

<!-- req: P/03.3-R009 -->

**Races.** One loop thread, but the stand-in can lose the name/fence the worker while the epoch issue or start_unit has not returned. A start and fencing agree through the local transition ([chapter 3.2](03.2-worker.norms.md) N3 «take_unit_epoch»). The CAS of the store does not protect the state of the process.

<!-- req: P/03.3-R046 -->

The stand-in writes the heartbeat, the slot, the leases and the place under the same `cas`.

## Implementation decides

The implementation is to name in its description:

1. **long polling or a pause** between passes, the command pump and its period; the stand sees them only within N1.2 `POLL`;
3. **the jitter parameter** of the exponential backoff in N1.2 `retry`; the formula min(Max, Base·2^(n−1)) × uniform [1−Jitter, 1+Jitter], its base cap and the mandatory jitter remain normative. Only the exact sampled pauses are not judged; the stand sees the count, its reset and `stalled` of the heartbeat (P/03.3-R025, P/03.3-R028);
2. ~~**how the worker learns `names_given` and the hang limit**~~ — a norm, not a choice of the implementation: the pass report (P/04; the form —
   the catalogue and the codec, N1) — [chapter 3.2](03.2-worker.norms.md) «Implementation decides» item 3.
