### Н1.2 Terms of the lease, the contender and the places

The rows of М10/5 Н1.2 that the procedures of this chapter carry out. The terms of the loop and of the heartbeat (`HEARTBEAT_EVERY`, `POLL`, `WAKE_GAP`,
`PASS_SHARE`) and the watchdog (`watchdog`) — [chapter 3.3](../03.3-worker.norms.md) Н1.2; the stand-in (`stand_in`) and the memory budget
(`memory`) — [chapter 3.4](../03.4-worker.norms.md) Н1.2.

```yaml
loop:
  LEASE_TTL: 30; LEASE_MARGIN: 5                    # a window of 25 s (Н1.6)
  LEASE_EVERY:  (TTL − MARGIN) / 3 ≈ 8.3            # the lease step, counted from the START of the previous step
  again:        the slot renewal got no answer or at least one lease became silent (Н1.6) — the next step at once
contend:
  CONTEND_EVERY: 10                                 # s; how often a writer rewrites its contender mark
  CONTENDER_FRESH: the observation contract «Свежесть метки соперника» # the value and the freshness at the reader — there (C06-CONTENDER-FRESH-33-01)
places:
  HOLD_SKEW: the observation contract «Удержание места» # the value and the effective hold — there (C06-WHERE-PLACE-HOLD-33-01);
                                                    # a foreign place is free once it has stood unchanged for 45 + HOLD_SKEW
  WRITE_WINDOW: 45 − 5 = 40                         # s; a strict place is written while it is confirmed for no longer than this
  CLOSE_BY:     45 + 5 = 50                         # s; by this moment the writer of the place is closed
```

### Н1.4 The slot row

```yaml
slot:                                     # a manifest section (P/02.1 Н1.2); closed: two keys
  prefix:   <1–8 lowercase Latin letters> # default w; the slot name is <prefix>-<suffix>
  name_env: <VARIABLE_NAME>               # ^[A-Z][A-Z0-9_]*$; the environment variable from which the worker takes the preferred name when it was not given as an argument (Н3 «start()», step 3); no key — the name is not taken from the environment
<sub>/slots/<имя>:                        # name: <prefix>-<suffix>, suffix ^[a-z0-9]+(-[a-z0-9]+)*$: a numeric <n> — the names that
                                          # a capture without a given name invents; <server>-<n> — a name from the unit (P/02.4 Н1.1: the instance
                                          # %i = <prefix>-<server>-<n> as an argument, P/02.4 Н1.2; ADR-0043), <server> = SERVER_NAME (P/02.4 Н1.2);
                                          # n is a decimal integer without leading zeros: 1 — the base process of the role on the server, 2…99 —
                                          # ordered by the controller (P/04 Н3 «заказать()»; ADR-0084); a choice by number (the reduction of
                                          # P/04, the workers script of P/02.4 Н1.5) compares n as an integer, not by the slot order below
  holder:    <instance> | ""              # instance — the instance contract grammar (common/contracts/instance.md; layout audit «А-06», the Architect's decision 2026-10-25)
  until:     <time (P/01.1 Н0 «Time in a row»)>   # the writer's clock + 45; display/divergence, not freshness
  released:  "true" | "false" | "taking"     # taking — the first write of a capture (Н3 «capture» step 3; added by the Quint pilot, F2)
  gen:       <decimal integer ≥ 0>         # the initial generation of an absent row is 0 (Н3 «capture»); +1 on every capture; never decreases
  server:    <server of the holder> | ""   # written on every capture and renewal; "" — the server is unknown (chapter 3.4 Н1.1 server: "", ADR-0029);
                                           # "" is a tolerance of the reader (ADR-0029): a worker of this platform with SERVER_NAME by P/02.4 Н1.2 does not write it — an empty SERVER_NAME fails the grammar, a start refusal with code 2 before the presence lock (guess of stage C W03-G01, the Architect's decision 2026-10-23)
states:    held, lapsed, released, taking, torn — the slot contract «Состояния» (moved there without change; layout audit «А-04», the Architect's decision 2026-10-25)
constants:
  SLOT_TERM, TORN_STILL: the slot contract «Сроки» (common/contracts/slot.md; moved there without change; layout audit «А-04», the Architect's decision 2026-10-25)
  RENEW_EVERY: ~8.3      # (30 − 5) / 3 — the lease step (Н1.2 LEASE_EVERY)
```

**The order of names and the next number** — the [slot name contract](../../../common/contracts/slot-name.md) (moved there without a change of
behaviour, POOL-ORDER-51-01; the name of a role process `<prefix>-<s>-<N>` and its number are there too). The name is checked by the grammar above and by the prefix of its own manifest.
«By name», the slot order (a numeric suffix — by number without overflow, then the others by name) and the next number
`<prefix>-<max + 1>` — in the contract.

The age of an observed version is the time on the monotonic clock of a particular judge since the moment it
first successfully read the current version of the row. A first look, a new version or changed bytes
give age 0; a repeated read of the same state and a non-answer of the store do not reset it.
The memory of observation is each judge's own; after a restart the first look is fresh again (ADR-0049).
Therefore held/lapsed are states relative to the observer, not a comparison of until with its clock.
Judges with different histories can diverge for a while. A write by someone else's clock gives no right to capture:
that right is released/a free name or names_given with the exact version, plus the exceptions of Н3.

The holder itself, to admit its own writes, remembers the monotonic moment of sending the last
confirmed capture (the final write released:false) or slot renewal.
Its own term ends SLOT_TERM after this moment; the time the answer is received and a re-read
do not extend it. A late answer that arrived past this limit does not allow writing without a new
confirmed renewal. This is the local term of its own request, separate from the memory of a judge.
For a replay of one write with the same id, the moment of its first send is kept; the answer again
does not start a new term. A new renewal is a new write, not a replay of the former confirmation.

An absent row has the initial generation 0. For an existing row, an absent or inadmissible
`gen` is not replaced by zero: the former lower bound of the generation cannot be restored from it. Such a candidate
is not rewritten automatically, even after `TORN_STILL` or the controller's permission; the outcome is a refusal
to capture this name with the reason «поколение слота не читается» (the slot generation does not read). The row is kept for recovery.
A damage of other fields with a readable `gen` admits a capture after `TORN_STILL` with the former `gen + 1`.
If there is no preferred name, the refusal of one candidate does not prevent checking the next ones.

### Н1.4а The contender mark

The object `<sub>/contenders/<имя>/<коробка>`: `{name, state: refused | nameless | waiting, box, hostname, server, instance, holder, holder_box, since, at}`; `refused` — NameOnAnotherBox by the capture table of Н3 «capture», including an occupied unreleased lapsed row of another box; `nameless` — its own former capture is gone, the worker waits; `waiting` — it has had no capture of its own yet, and there is no candidate without NameOnAnotherBox. The priority of refused is above the other two. On a decommissioned server (Н3 «start()» step 3) there is no mark: the worker is nobody without a name search and is not a contender. In a search without a given name `name` is `-` and `holder` is `""`; with a given name — the sought name and its current holder. It is rewritten every `CONTEND_EVERY`; the freshness at the reader is the [observation contract](../../../common/contracts/observation.md) «Свежесть метки соперника» (`CONTENDER_FRESH`; C06-CONTENDER-FRESH-33-01, the Architect's decision 2026-10-25): a mark older than `CONTENDER_FRESH` is not counted; an unreadable mark (not in form) is, for a worker reader, as one older than `CONTENDER_FRESH` (review of stage B 3–5, № 5), for the console a fresh unreadable one is a conflict with a flag (the outcomes by reader — [`contenders.outcomes.tsv`](../../data/contenders.outcomes.tsv); C03-CONTENDER-UNREADABLE-01); `since` is kept within one state.

### Н1.5 The epoch row

```yaml
<sub>/epoch/<id>:
  epoch:   <decimal integer ≥ 1>           # MUST; grows by 1 on every taking of the unit by a worker (a new holder or a return after
                                          # a loss); a restart of the same unit by the same holder on a revision change does not change the epoch; the row is not deleted
                                          # at most 2^53 − 1: an issue beyond it is a refusal before the write (Н3 «take_epoch(id)»; review of stage B 3–5, № 8)
platform/epoch_floor:
  floor:          <decimal integer ≥ 0>    # the lower bound of the issue after a recovery (P/01.3 Н3 «recover the store»)
  generation_at:  <time (P/01.1 Н0 «Time in a row»)>  # the moment the floor was raised (the Architect's decision 2026-10-18)
```

### Н1.6 The lease

```yaml
lease:
  TTL: 30; MARGIN: 5                       # the window of action: 25 s from the send of the last confirmed request (monotonic clock)
  states:
    confirmed:    the issue of my epoch is confirmed or a read carries my number → last — the greatest send moment of the confirmed requests
    fenced:       the row has another number, the row does not read or the worker is fenced → forever for this epoch
    silent:       the store did not answer while the window was open → unconfirmed is counted from the end of the window
    lost:         the window ended without a request (overslept), or the initial issue/launch was late, or the epoch is below floor — not silent
  may_act:    not fenced and not lost and now − last < 25 and the own slot term of Н1.4 has not expired
              # lost and the slot term — added by the Quint pilot (F3): with lost writes and live reads the old holder
              # stops acting before the move — its own term is 45 s from the send of the renewal, the move not earlier than 90 s
  may_write:  may_act or (silent and unconfirmed < unconfirmed_max)      # unconfirmed_max: off = 0, forever = ∞
  unconfirmed_max: from manifest.lease (P/02.1): forever | off | <integer ≥ 1 s>; default off
```

The moment of a request is before the first send of the logical call. Network retries inside it,
including a replay of a write with the same id/the answer again, do not move this moment. A new
confirmation request has its own t0; last from requests already confirmed does not decrease. On the first
issue of an epoch, last is set by the confirmed write, then Н3 «confirm» applies.

## Н3 Procedures

### Full keys and store refusal

The worker branches of Н3 «Полные ключи и отказ хранилища» (moved from М10/3) — the choice of a slot, the capture after it has started, the renewal, the write under
the slot guard, the issue and confirmation of an epoch; the branch of the units door (`400 badkey`) — [chapter P/06.1](../../../06-console/spec/06.1-console.norms.md) Н3 «Full keys and store refusal», the branches
of the place hold — Н3 «place: take, hold, let go» (review of stage A 3–5, № 11).

In all operations below, the key rules of P/01.1 Н1 apply after the full path of P/06.1 Н1.1 is assembled,
including the prefix, the family and the separators; the guard key is checked the same way. The grammar of UnitId,
WorkerName and the 200-byte limit of a component of Idempotency-Key are kept. The schema of a component
does not promise the capacity of the full key. Keys are not shortened and not hashed on a refusal.

A definite `badkey` on a read or a write is a refusal of that operation, not the absence of the row,
not a CAS conflict and not a non-answer. The applicable key rules can be checked before calling the store;
a refusal by a smaller declared limit of a file-based implementation is handled the same way.

- In the choice of a slot, badkey means a refusal of the candidate before the first write: a given name leaves
  the process nobody, in a search the next one is checked; a refusal of a new computed name ends
  the search as nobody. After the capture has started, a refusal of an operation aborts the attempt without handing out a live slot;
  writes already confirmed are not rolled back. On a renewal the name is lost; on a write under the guard
  the write is refused, and the error of the target key by itself does not prove the loss of the slot.
- On the issue of an epoch badkey forbids the launch, on a confirmation — fenced without extending the window.
  In no branch is a refusal replaced by a success, an empty read or an endless retry.

### capture(name?) → slot | nobody

A call at the first start of an instance differs from a name search after a loss: the exception for its own
box below is available only to the first call from Н3 «start()». A repeated search, a rejoin
and continuing after fencing do not restore this right; the way to keep the flag is chosen by the implementation.
A first call none of whose candidate reads confirmed the row or its absence (the store did not answer)
does not spend the right: the right passes on to the next search (Н3 «nobody and getting the name back», rejoin()) until such a read happens
(added by the Quint pilot).

**The capture transition table.** These are local states of the attempt, not new fields of the row.
The rows of the table apply from top to bottom: a general refusal has priority over a permission below.
The checks refer to the re-read version; the order of candidates and the writes are performed by the pseudo-code after the table.
There is one kind of worker: an additional role process on a server is the same unit with its own name, the capture is the ordinary one (ADR-0084).

| State of the attempt | State of the row and condition | Action | Next state / result |
|---|---|---|---|
| Search | The read confirmed neither the row nor its absence | Do not write on an unknown state | The candidate is not captured |
| Candidate admission | The name is not by the slot grammar or is without `slot.prefix` | Do not write the slot and do not declare it live; a given name — a start refusal, code 2 (Н3 «start()» step 2a) | The candidate is not captured |
| Search | An existing row with an unreadable `gen` | Keep the row for recovery | A refusal of the candidate by Н1.4 |
| Search | The absence of the chosen name is confirmed | The first write of step 3 with `cas: ""`, initial gen = 0 | On success — the cleanup |
| Search | A torn row with a readable gen, the same version observed for less than TORN_STILL | Do not write | The candidate is not captured |
| Search | The same torn row observed for not less than TORN_STILL | The first write of step 3 by this version | On success — the cleanup |
| Search | A readable row: released = true or taking, or there is no field released, or holder is empty or absent (review of stage B 3–5, № 6) | The first write of step 3 | On success — the cleanup |
| Search | A readable occupied row: its version is exactly equal to names_given for the name | The first write of step 3 | On success — the cleanup |
| First start | A given name, a readable occupied row, the former holder of the same box | The first write of step 3 | On success — the cleanup |
| Search | The other occupied rows, including lapsed without a permission | Do not write; for a given name with a holder of another box — NameOnAnotherBox | The candidate is not captured |
| First write | CAS refused | Do not start the cleanup | The candidate is not captured |
| Write/delete | The outcome of the operation is not confirmed | Do not pass to the next step; a retry by the rules of the store and P/03.4-07 with the same id | The current step waits for a definite outcome; no live slot is handed out |
| Cleanup of the new holder | The deletes under the guard are complete; the CAS of the final write is confirmed | Step 4 | The slot is live, return the slot |
| Cleanup of the new holder | A guard/CAS refusal | Do not declare the slot live and do not write under it | Return nobody; a new acquisition — through a fresh capture |

A candidate is not captured — pass to the next one; with a given name or an exhausted list return nobody.
The table does not allow passing to another name for a named process.

```
1. read the slot rows and the field names_given of the object <sub>/controller/pass (P/04 Н1.2; bound to the version of the slot row);
   do not count a non-answer as an empty list or as the absence of a row → nobody
2. keep only the admissible names of the own manifest and the candidates by the table;
   the order of candidates (skip a repeated name):
   a. the name from the environment, if given, is the only candidate (ADR-0043); do not pass to b–e
   b. the names released by the controller, in the order of names of Н1.4
   c. free readable rows — in the slot order of Н1.4
   d. torn rows with a readable gen that stood unchanged for TORN_STILL — in the slot order
   e. only a process without a given name: a new <prefix>-<max + 1> by Н1.4
3. for a candidate: re-read the row and apply the table again;
   the ground of the chosen branch must persist: the version of names_given is exact, the free row stayed free,
   the torn row did not change, the new name is still absent; otherwise the next candidate;
   for a given name check the conditions of the table anew, including holder and the first-start flag;
   write {holder: me, until: now + 45, released: "taking", gen: gen + 1, server} with cas of the read version; conflict → the next candidate. The slot is captured but not live: the controller and
   the agents do not read it as live, the controller does not take it for a release (Н1.4 taking;
   added by the Quint pilot, F2), writing under it is not allowed (P/03.2-03); from this write on, the guard of the predecessor is invalid —
   its late contribution write gets 412
4. list the contributions of the predecessor under this name (the rows that are collected — М11) — already after step 3, so
   the list is complete; delete each by a write under the guard {key: slot, index: the version of the write of step 3}; then write
   released: "false", until: the writer's clock + 45 with cas by that version → the slot is live; the version of this write = the guard from then on (ADR-0074 C2: no row
   of the predecessor is visible under the live slot of the new holder). No contributions — the second write is made anyway
→ slot; all candidates failed → nobody
```

**Races.** Two processes on one name: `cas` lets one pass, the second goes to the next candidate or becomes nobody.
B at its start took the name from A on the same box; A after fencing repeats the search → A no longer has the start
exception, the live name of B stays with B. A damage of `gen` between the choice of a candidate and the re-read → a refusal
of the candidate without a write; a change after the re-read is cut off by `cas`. The cleanup against a new-new owner: the guard by the slot version — the one whose slot was rewritten gets `412 guard` and does not erase someone else's. The controller releases a name (P/04 Н3 «fate», `names_given`) between my read and my write: `names_given` is bound to the version of the row, my write with `cas` by the same version passes; by a new one — a conflict and a re-read.

### renew() → still mine | lost

```
every RENEW_EVERY:
  read the slot; holder/gen not mine, released or the slot does not read   → lost: become nobody (Н3 «nobody and getting the name back», give_up_name())
  write {…row, until: now + 45, server} with cas; conflict                 → re-read and check all the conditions again
  the store did not answer                                                 → still mine (the lease of the units decides)
```

**Races.** A renewal against a permitted capture by another instance: `cas` by the read version lets one pass; the loser sees a foreign `holder`/`gen` — lost. The silence of the store does not extend its own term: until a new renewal is confirmed, writes under the slot are allowed only within the remaining local window of Н1.4 and by the conditions of the lease of the unit. An unconfirmed request does not change the start of this window.

### release() — only on an orderly stop

```
write {…row, released: "true", until: now} with cas; conflict — do not repeat
```

**Races.** A release against a capture: `cas`; a capture by another before the release — there is nothing to release (a foreign `holder`), nothing is written. A release against the stand-in (chapter 3.4 Н3 «stand_in()»): the stand-in re-reads the slot before renewing and sees `released`.
A release against letting go of a place: the release comes after the place is let go (chapter 3.4 Н3 «stop by SIGTERM», step 4); under
a released slot the place can no longer be let go (review of stage B 3–5, № 4).

### write_under_slot(key, items) → index | refusal

```
re-read the slot; holder is mine, gen is mine, not released, readable, its own confirmed term of Н1.4 has not yet expired,
writing is allowed (writing_allowed, Н3 «start()», step 5) → otherwise do not write
write(key, items, guard: {key: slot, index: the version of the re-read slot})
412 guard → the write is not made; re-read the slot and check ownership and the conditions anew
  the same holder and gen, the slot is live, writing is allowed → the name is kept; a new attempt with a new check is admissible
  a foreign holder/gen, a released or unreadable slot → lost: become nobody
  the store did not answer or its own confirmed term expired → do not write; do not declare success or loss on one 412
```

**Races.** A write under the guard against a change of the slot: 412 `guard`, the write is not made, the re-read
shows the new holder — the former one becomes nobody. Its own renewal v1 → v2 keeps
holder and gen: the write with v1 gets 412, but the re-read confirms ownership; a new attempt checks
all the conditions and uses v2. There is no blind retry with the old guard. Two writes of one row under
one guard — the `cas` of the row decides, the guard lets both pass. The place hold row (Н3 «place») is written by this same path —
under the slot guard and with the `cas` of the place row: the taking, the renewal and the letting go alike; therefore on an orderly stop
the place is let go before the slot is released (chapter 3.4 Н3 «stop by SIGTERM», step 4; review of stage B 3–5, № 4).

### take_epoch(id) → epoch | refusal

```
conditions: I am somebody (the slot is mine); the unit is in the assignment that answered last; not lost since then
read <sub>/epoch/<id>: absent → 0; not a number → refusal EpochUnreadable (not 0)
read platform/epoch_floor: floor (absent → 0; does not read → a refusal of the issue, the floor is not replaced by 0)
max(current, floor) = 2^53 − 1 → a refusal of the issue before the write: the epoch row does not change, do not launch the unit, the log
  names the unit and the epoch (like rev of P/02.3 Н1.5 at the same bound; review of stage B 3–5, № 8)
t0 = now (monotonic, immediately before sending the write)
write {epoch: max(current, floor) + 1} with cas of the read version;
  conflict → re-read the epoch row and the floor and repeat with a new t0 for the new write (the floor — added by the Quint pilot, F1)
  outcome not confirmed → a retry with the same id by P/03.4-07, t0 — the first send (Н1.6); not confirmed even then — a refusal,
                          do not hand out a new lease
  confirmed → last = t0; now − last ≥ 25 → lost, a refusal of the launch, not silent
before start_unit — a successful «confirm» (below) with t0 after the confirmed issue write (the order is causal: the read
  is sent after the answer of the write; equal readings of the monotonic clock within one tick are admissible; C03-POST-GRANT-SAME-TICK-01): an epoch below floor → lost,
  do not launch; another one or unreadable → fenced; the store did not answer — do not launch, silent does not allow
  the first launch (added by the Quint pilot, F1)
→ epoch; lease = a new one with last = t0, only within the remaining window
```

**Races.** Two workers on one unit (a reassignment): both raise the epoch, `cas` lets one pass first; the second re-reads and takes the next one — each has its own, the elder is fenced on confirmation. The floor rose between the read and the write: `cas` on the epoch row does not see it, and reading the floor before the write does not protect from it — the row did not exist (`cas ""`) or the copy kept its version, and the write with the old floor passes; a re-read of the epoch row alone on conflict takes the old floor. What protects is the check after the write: the floor is re-read on conflict, and before start_unit a successful «confirm» sees the floor after the write — an epoch below the floor is `lost`, the unit is not launched (added by the Quint pilot, F1). A recovery that raised the floor (P/01.3 Н3 «recover the store») does not restart processes: the floor is read at every lease step (Н3 «lease_step()», step 2), and a unit with an epoch below the floor loses its lease (`lost`) — its writer stops by itself.

A delayed answer of the issue does not start a new window: a send at 0, a successful answer at 30 — the epoch may
have been written, but the start is already forbidden. The number is not rolled back and not deleted; a late answer gives
neither silent nor a right by unconfirmed_max, not even with forever. The next attempt requires a new successful
read of the assignment and passes the gates of Н3 «take_epoch(unit)» again. Right before start_unit the gates and may_act
are checked once more: a pause between the return of the issue and the launch does not extend the window.

### confirm(id) — a lease step

```
t0 = now (monotonic); read <sub>/epoch/<id> and platform/epoch_floor
  the floor does not read      → fenced, as a refusal of the confirmation: the floor is not replaced by 0
  my epoch is below floor      → lost (Н1.6; the Races of the issue)
  carries my epoch             → the window ended without a request (t0 − last ≥ 25 and not silent — overslept) → lost, do not revive: Н3 «lease_step()»,
                                 step 4 stops the unit (stop_unit); otherwise last = max(last, t0), also after silent:
                                 a successful read of its own epoch returns the lease to confirmed
  another one or unreadable    → fenced: stop the unit, remember the loss of the epoch (Н3 «lease_step()», step 4; the epoch row does not change)
  the store did not answer     → the lease was not silent and the window is still open (t0 − last < 25) → silent from the moment the window ends;
                                 already silent → stays silent (unconfirmed grows up to the ceiling); the window missed without a request → lost
may_act / may_write — by Н1.6
```

**Races.** A confirmation and a change of the epoch by another worker: the read sees either mine or the new one —
in the first case the window is extended by 25 s from t0, in the second the worker is fenced at once. The term of the move is set by
the fate of the slot, not by this read alone (P/03.2-08). With silent, actions stop by the end of the window;
data — by unconfirmed_max: with off also by the end of the window, with a finite ceiling — when it is reached,
with forever no finite stop term for data follows from the silence. The data of different attempts are told apart by epochs.

### take_epoch(unit) — the gates before a launch

```
in order:
  I am nobody (the slot is lost / I seek a name)                       → refusal NoSlot
  the own slot term of Н1.4 has expired (a new renewal is not confirmed) → refusal NoSlot «own slot term ended»: the write of the epoch
                                                                         issue is the very write by which a holder with an expired term
                                                                         would fence the new one (C03-EPOCH-OWN-TERM-01)
  fenced                                                               → refusal Fenced (the reason — fence(why))
  the step lasts longer than FOR (it outlived the stand-in)            → refusal NoSlot «until the loop has looked again»
  the unit was released after the last read of the assignment          → refusal NotReadThisPass
  the assignment did not answer                                        → refusal NotReadThisPass
  the unit is not in the last answered assignment                      → refusal NotReadThisPass
before asking for an epoch: register an unfinished launch attempt for this unit
  and for the current ownership of the name; a loss of the name, fencing or a cancellation of the unit irreversibly cancel the attempt
→ the epoch and a new lease = issue by Н3 «take_epoch(id)»; last — the send time of the confirmed write,
  not the return time; a late answer or the expiry of the window before start_unit → lost, do not launch,
  mark «released until the next successful read of the assignment»
after the issue — a successful Н3 «confirm» with t0 after the confirmed issue write: an epoch below the floor → lost, do not
  launch, «its epoch is below the floor» (added by the Quint pilot, F1);
after the issue and immediately before start_unit check again all the gates above, may_act,
  that the attempt is not cancelled and belongs to the same ownership of the name;
a non-answer of the issue creates no new lease; unconfirmed_max does not allow this first launch
any refusal ends/cancels this attempt; a late completion of a request cannot revive it
a worker that has never read the assignment holds on to no list
```

**Races.** Н3 «take_epoch(id)»: `cas` on the epoch row; the floor read before the write does not protect from its rise — the confirmation after the write before start_unit protects; the second worker of the same unit takes the next epoch, the elder is fenced on confirmation.

A successful answer of a write sent at 0 is received at 30: the number may already have grown, but start_unit
is not called and the number is not rolled back. The same with an answer at 24 and a pause before the launch until 26 without a new
confirmation. If during the issue the slot is lost or the gates change, their repeated check
forbids the launch even with lease time remaining.

The last check and the acceptance of the launch are one local transition, coordinated with fencing,
the giving up of the name and the cancellation of the unit. Fencing before this transition forbids start_unit; after it,
fencing also sees a launch already accepted but not yet completed and cancels/stops it. A late
completion of a cancelled start_unit does not publish the led unit anew. The return of the name and a new
read of the assignment do not revive an old attempt: a new call of the gates is needed. Store requests and
a long start_unit do not hold a lock that would forbid the stand-in to close the admission.
The internal synchronization mechanism is a choice of the implementation; the observable order is mandatory.
This applies to all calls of start_unit, including a restart by revision. For such a restart
the same gates and may_act are checked, but there is no epoch issue, and the state of the former lease is not replaced by
a new one. Silence while data are still allowed postpones the change of revision until a confirmation;
the wait for the restart by itself does not turn an effective silent lease into lost.

**Bringing up under the same epoch** (ADR-0091 item 6; М10B/03:259, М10B/04:615). Bringing up a fallen process of a unit is a local transition,
like a restart by revision, without a new epoch issue, and it is allowed only when all of these hold at once: the launch was accepted earlier in this
instance; the same `observed_revision` and its row body; `may_write`; the unit is in the last read assignment of this
worker and not released (the gates above as a whole); the lease is neither lost nor fenced; the place of the unit, if there is one, is still within the write window
(Н3 «place»); with `NotReadThisPass` — the same predicate. The silence of the store does not forbid bringing up while all the conditions hold;
device actions get no permission through `may_write` (chapter 3.6 «Действие устройства»). An epoch taken for an action
is inherited by the launch without a new issue ([chapter 3.3](../03.3-worker.norms.md) Н3 step 2).
