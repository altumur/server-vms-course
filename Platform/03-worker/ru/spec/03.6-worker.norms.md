### N1.2 Событие: писатель и подавление

Воркер — участник `append` журнала событий: строку события, её `id`, бакет по `t`, класс и дерево тревог, `fsync` тревоги и
журнала, блокировку файла журнала он соблюдает по файловому договору урока 5 —
[договору журнала событий](../../../common/ru/contracts/event-journal.md) (`line`, `bucket`, `class`, `journal`, `writer`) и его
разделу «Запись строки».

Подавление повторов событий — шаг 3 прохода записи в журнал по P/03.6-R007; правила окна подавления и сравнения заданы в P/03.6-R058, P/03.6-R059, P/03.6-R062, P/03.6-R064, P/03.6-R070, P/03.6-R009.

**Подавление событий: `kinds`.** `events.kinds.<kind>: {severity}` (форма — P/02.1) — важность вида для описания вида backend VMS **Подавление событий: `kinds`.** Платформа не судит важность из `events.kinds.<kind>` и не пишет эту важность в строку события.

**Подавление событий: `suppress`.** `events.suppress.<kind>: {window, by}`  (форма — P/02.1)

**Подавление событий: `window`.** секунды > 0


**Подавление событий: `by`.** непустой список строковых имён полей строки или синтетического unit **Подавление событий: `by`.** без by — все поля строки кроме t/id/repeats/since/until **Подавление событий: `by`.** Любое имя из `t`, `id`, `repeats`, `since`, `until` в `by` или пустой `by` даёт отказ загрузки.

**Подавление событий: `rule`.** первая строка окна — как есть **Подавление событий: `rule`.** повторы считаются


**Подавление событий: `rule`.** по закрытии окна или на проходе — одна строка {…поля первой, id: новый, repeats, since, until}: repeats — проглоченные без первой **Подавление событий: `rule`.** В строке итога подавления `since` — `t` первой строки события этого окна. **Подавление событий: `rule`.** В строке итога подавления `until` — `t` последнего проглоченного повтора. **Подавление событий: `rule`.** В строке итога подавления `t` — момент записи итога. **Подавление событий: `rule`.** окно без повторов строки не даёт **Подавление событий: `rule`.** итог прежнего окна пишется раньше первой строки нового

**Подавление событий: `stop`.** при остановке писателя каждое открытое окно с проглоченными повторами закрывается той же строкой итога, until — момент остановки, под may_write и до последнего пульса **Подавление событий: `stop`.** окно без повторов строки не даёт


Подавление всегда раздельно для (дерево, единица пути, эпоха, kind, class), независимо от by. Имя unit в by — единица из аргументов писателя/пути бакета, не одноимённое пользовательское поле строки. Остальные имена by — верхние поля записанной строки; неизвестное/отсутствующее поле даёт отдельное значение «отсутствует», отличное от null. Сравнение структурное JSON: объект без учёта порядка ключей, массив с учётом порядка, bool не число. Отсутствие выбранного поля в конкретном событии не является ошибкой манифеста. t/id и поля итога не участвуют; при отсутствии by остальные поля, включая occurred/of, участвуют.

Форма `events.suppress` в манифесте и отказы её загрузки — [P/02.1](../../../02-installer/ru/spec/02.1-installer.norms.md) N1.2, N4.

Воркер в этой форме: подаёт строку по
`worker.requests` другого манифеста — поля `filed` (свой экземпляр) и `digest` (считает сам при записи, вид `worker`), `rid` по
шаблону `requests.key` цели, иначе по ключу подателя `<своя подсистема>.<ключ>` (ключ — детерминированно из своих данных,
например `<сценарий>-<id события>-<i>`) или случайный без точки — только у просьбы, повтор которой не нужен (договор просьбы
`rid`).

Повтор подачи тем же `rid` проверяется порядком двери
(P/06.4 N3 «подать просьбу»: сначала метка, затем строка и окно `kept`; у цели с `requests.outcome: fetched` шага метки нет) и сверяет `unit` строки и `digest` вида `worker`: тот
же `rid`, та же `unit`, тот же `digest` — `again`; иное — `refused`; как держатель пишет метку — `begun` до вызова, `answer` начавшего, `no_begun` с `ended_by: holder`,
уборка после `kept`.

Пределы держателя — константы времени исполнения по P/03.6-R012; `CLEAR_EVERY`, `SWEEP_EVERY` и `REAP_AFTER` принадлежат жнецу P/06.4 N1.5, не держателю.

Уставки держателя — [runtime-constants.tsv](../../forms/runtime-constants.tsv). PERFORM_GRACE и REQUESTS_HOLD выражены в секундах точным /1000; новых настроек нет.

```yaml
# PERFORM_TIMEOUT, COMMANDS_PER_LOOK: runtime-constants.tsv
PERFORM_GRACE: PERFORM_GRACE_MS / 1000
REQUESTS_HOLD: REQUESTS_HOLD_MS / 1000
```

Подача просьбы воркером следует штампам манифеста цели, проверке тела и правилам публикации по P/03.6-R079, P/03.6-R080, P/03.6-R082 и P/03.6-R083; нечитаемые существующие просьбы и неверные идентификаторы отклоняются по P/03.6-R084 и P/03.6-R085.

Штампы строки по `requests.stamp` цели — как у двери (договор просьбы «Просьба»):
`by` — `<sub>/<unit>` подателя (своя подсистема и единица, от имени которой подаёт); `at` — его часы; `group` — по
`placement.group_by` единицы-адресата ([договор группы по хосту](../../../common/ru/contracts/group-of.md)); поле `about` — значение единицы-адресата (договор просьбы `stamp`).

Тело проверяется по `requests.schema` цели (каталог манифестов, P/02.1 N3) до подачи: не по схеме — не подаётся, исход `refused`. `maxLength` поля тела меряется по записанному тексту поля (строка — как есть, иное значение — канонический JSON) при любом типе значения — как у двери (P/06.4 N2 `too_long`, правило таблицы [`requests-body`](../../../06-console/ru/vectors/requests-body/README.md)); прочие слова схемы — над JSON-значением.

После записи строки просьбы — строка журнала, как аудит двери (P/06.4 N3 «подать просьбу» шаг 6: вид `requests.journal`
цели, дерево `audit` роли воркера): отказ журнала исхода `filed` не меняет, строка лога; `again` журнала не пишет.

Счёт подачи — пульс подателя `filings.<outcome>` (`filed`, `again` — та же просьба
подана снова, `refused`; [P/03.4](03.4-worker.norms.md) N1.1).

Строку под этим `rid`, при любом шаблоне `rid`, воркер, встретив её при подаче, а она есть, но не читается своей формой, — не подаёт и не трогает: исход `refused`, строка лога без значения.


`rid` не по грамматике ([договор просьбы и её метки](../../../common/ru/contracts/request-mark.md)), при любом шаблоне, — то же: не подаётся, `refused`, подающий на нём не стоит.

### N1.6 Заказ строки другой подсистемы: сторона заказчика

Заказчик — подсистема C с `worker.creates: [{sub: A, rows, key}]` (форма и проверки каталога — [P/02.1](../../../02-installer/ru/spec/02.1-installer.norms.md) N1.2a, N3) — заводит и продлевает строки единиц адресата A сам, из библиотеки воркера, под своей эпохой. Когда, о чём и с какими полями заказывать — логика подсистемы C (её урок); здесь — что библиотека делает с каждым заказом (N3 «заказать»).

**Заказ строки: `order`.** событие E, которое исполняет единица U заказчика под своей эпохой (держатель U, P/03.2): время события t_E — секунды Unix по часам писателя события **Заказ строки: `order`.** поля F строки A — без поля-источника id A, без *_secret и blob

**Заказ строки: `id`.** `<C>-<key(F)>` префикс не выбирается

**`key` заказа.** Шаблон `worker.creates[].key` использует подстановки `{field}` через «-»: `{field}` — значение `F[field]` записью `values_by_type` договора проверки строки. Для `string` и `url` вход побайтового кодирования ниже — значение как есть. **`key` заказа.** В записи `values_by_type` договора проверки строки `int` — десятичная запись; полученная запись поля затем кодируется побайтно, как указано ниже. **`key` заказа.** В записи `values_by_type` договора проверки строки `float` следует его правилу выбора; полученная запись поля затем кодируется побайтно, как указано ниже. **`key` заказа.** В записи `values_by_type` договора проверки строки `bool` — `true | false`; полученная запись поля затем кодируется побайтно, как указано ниже. Для каждого типа поля выше каждый байт UTF-8 записи поля вне `A–Z a–z 0–9 _ . ~` кодируется как `%XX`, hex-цифры верхним регистром (`-` → `%2D`, `%` → `%25`). Побайтовое кодирование выполняется до соединения подстановок ниже. **`key` заказа.** Побайтно закодированные выше подстановки `worker.creates[].key` соединяются литералом «-» между ними. **`key` заказа.** Разные значения полей дают разные id, поэтому id задаёт эти значения: вернувшееся имя — тот же предмет.

Векторы creates-key проверяют запись поля по P/03.6-R089, побайтовое кодирование по P/03.6-R089, соединение по P/03.6-R089 и идентичность по P/03.6-R089.

**Заказ строки: `born`.** новое случайное значение при создании (договор проверки строки, born)

**Заказ строки: `made, ORDER_HORIZON, not_after, tombstone`.** договор проверки строки «Customer row: made» — `made` (keep), `ORDER_HORIZON`, `not_after` записи заказа, окно над надгробием договора проверки строки, Строка заказчика: made


**Заказ строки: `fields`.** строка создаётся по договор проверки строки «Подготовка полей», как у двери: непереданное — default или пустая форма типа **Заказ строки: `fields`.** поле-источник id — готовым id **Заказ строки: `fields`.** *_secret не пишутся никогда — остаются пустыми, секрет ставит оператор дверью **Заказ строки: `fields`.** blob пусты (P/06.1 N1.5)


**Заказ строки: `until`.** поле срока адресата — placement.ends.field манифеста A (P/04 N1.3), если ends объявлен **Заказ строки: `until`.** Если манифест A объявляет `placement.ends`, поле срока `placement.ends.field` продлевается как max(прежнего, нового). **Заказ строки: `until`.** Если манифест A объявляет `placement.ends` и прежний срок — `never` (без срока), это значение не меняется.

**Заказ строки: `ends_past`.** строка, чей срок по полю ends в F уже прошёл (≠ never и ≤ now по часам держателя), не заводится

**Заказ строки: `deletes`.** воркер адресата удаляет строку с made по worker.deletes (библиотека) — по правилу договора проверки строки «Customer row: made» `delete` **Заказ строки: `deletes`.** При удалении через `worker.deletes` строки без `made` воркер адресата использует CAS прочитанной версии, как и прежде.

**Заказ строки: `guard`.** каждая запись — CAS своей строки и guard {key: C/epoch/U, index: версия строки эпохи, подтверждённая при взятии эпохи} одной операцией (P/01.1 guard: index — версия строки, не номер эпохи), и только пока may_write (P/03.2 N1.6). **`guard` заказа.** После восстановления хранилища версия стража может совпасть — аренда сверяет пол.


**Заказ строки: `writers`.** строка заказа двухписательная (P/06.1 N1.1): оператор — дверью, любые поля, кроме полей key (P/06.1 N1.3 made_key)

**Заказ строки: `writers`.** заказчик — только строки своего made (made.by = C) **Заказ строки: `writers`.** строку своего made продлевать вправе любая единица C **Заказ строки: `writers`.** строка без своего made — занята: C её не пишет

**Заказ строки: `check`.** общая проверка строки — договор проверки строки (P1–P5, R1–R3), та же, что у двери **Заказ строки: `check`.** Чтения общей проверки строки выводятся из объявления (права — P/02.5 N1.4).


**Заказ строки: `outcomes`.** created | extended | unchanged | taken | gone | expired | refused счёт — пульс C, P/03.4 N1.1 creates

Исходы: `created` — строка заведена

`extended` — строка своего `made` продлена записью

`unchanged` — значения строки
своего `made` не меняются, записи нет

`taken` — строка занята (нет своего `made`)

`gone` — на месте строки надгробие,
записи нет

`refused` — адресата нет в
каталоге, id не по грамматике или не помещается, общая проверка строки отказала или предел повторов исчерпан. Отсечение

## N3 Проход

### взгляд держателя (воркер, на проходе; ≤ REQUESTS_HOLD, ≤ COMMANDS_PER_LOOK)


Предел удержания одного взгляда держателя — `≤ REQUESTS_HOLD`; точное преобразование — `REQUESTS_HOLD = REQUESTS_HOLD_MS / 1000` секунд. Один взгляд держателя обрабатывает `≤ COMMANDS_PER_LOOK` команд.

Этот проход через begun/метку — только обычный профиль.

Дозапись выполняет свой проверяющий данные обработчик и сообщает fetched без метки; elsewhere — его владелец. В профиле дозаписи (`requests.outcome: fetched`) тело с `action` из `elsewhere` — тоже дозапись: держатель сверяет данные и сообщает fetched; `elsewhere` выводит строку из прохода меток и из жнеца только в обычном профиле.

Порядок в группе (`placement.group_by`, «Device action» ниже): строки одной группы идут по `at` штампа, равные — по `rid` байтами, строка без `at` или с нечитаемым — после штампованных, по `rid`; вызов в группу занят — ждут и все младшие: `rid` двери случаен, по имени стоп, поданный вслед движению, исполнился бы раньше. Предел: `at` — часы подателя, две консоли с разбежкой часов порядка не держат, а у `at` одной секунды порядок даёт `rid`; строки разных групп не упорядочены.


Для каждой строки семьи с `unit` моей единицы (просьбы ресурса — строки без `unit` с `{free, volume, server}` — не рассматриваются; имя
`free-*` само по себе ничего не значит; `elsewhere` — не мои действия; строка `free-<server>-<volume>` не по форме
ресурса — не просьба: пропустить её, причина в журнал без значения):

**Шаг 1.** Если строка просьбы или её метка не читается своей формой (исходы — `requests.outcomes.tsv`, `commands.outcomes.tsv` P/06.4),
остановить операцию над этой строкой: без записи, удаления и вызова действия; строка лога, `garbled_rows` пульса + 1
(глава 3.4 N1.1).

**Шаг 2.** Если у метки есть исход, пропустить её (чужая или моя прежняя).

**Шаг 3.** Если это своя `begun` без исхода, не вызывать снова; ждать уже начатое действие.

**Шаг 4.** Если срок дальше `most_valid`, отказать до вызова (метка `refused` и событие — ниже); это раньше закрытия чужой `begun` и раньше срока.


**Шаг 5.** Если это чужая `begun` без исхода: если её `at` + `PERFORM_TIMEOUT` + `PERFORM_GRACE` позади, записать `{outcome: unknown, ended_by: holder,
error: "begun by <instance> and never answered"}` по прочитанному индексу (закрывающий пишет по индексу; при `conflict` —
перечитать, и если исход появился, не трогать); иначе (исполняется) пропустить; `begun` — не `expired` и после срока.

**Шаг 6.** Если срок вышел, создать метку `expired` однажды; дальше. **Шаг 6.** Порядок проверок: метка с исходом, `most_valid`, чужая `begun`, затем срок.


**Шаг 7.** Если штамп `group` просьбы непуст и не равен группе единицы по `placement.group_by` её прочитанной строки (договор группы по хосту; нет `group_by` — группа пуста),
группа переехала: отказать до вызова, `error: "unit <id> was moved to another group after this request was given: it was not performed — give it again if it is still wanted"`;
если штампа нет или он пуст, он не сверяется.

**Шаг 8.** При отказе до вызова (срок дальше `most_valid` — выше; группа переехала, эпоха чужая) создать метку `refused` однажды `{…, error: the reason}`; и записать событие `command.failed {outcome: refused, action?, by, error}` в бакет единицы под эпохой держателя, как при отказе после вызова, без `reply`; если эпохи единицы у держателя нет (не взята), события нет, отказ виден меткой и рядом метрик. **Шаг 8.** Держатель проверяет до вызова срок (`valid_until` в прошлом → `expired`; дальше `most_valid` → `refused`), штамп `group` и свою эпоху единицы — берёт только строки единиц, которые ведёт под своей арендой.

**Шаг 9.** Создать метку `begun` = `put_new {instance, slot, unit, of?, at, digest, valid_until?}`; при `conflict` перечитать;
при отказе или неизвестном исходе — без вызова; только подтверждённый успех разрешает действие.

**Шаг 10.** Вызвать действие с таймаутом `PERFORM_TIMEOUT` (+ `PERFORM_GRACE`).


**Шаг 10.1.** При ответе прочитать метку и записать исход по её индексу; при `conflict` перечитать и повторить только запись, perform не повторяется (у двери хранилища нет «преобразовать» — так запись атомарна относительно прочитанного, а слово держателя по-прежнему побеждает слово жнеца: жнец и второй держатель пишут по индексу однажды); `late: true` ставится по той прочитанной метке, по чьему индексу запись прошла. **Шаг 10.1.** Исход — `{outcome: performed | refused, action?, reply?, ended_at}`; `reply` — ответ perform, то же, что в событии ниже ([договор просьбы](../../../common/ru/contracts/request-mark.md) «Mark»); `action` — значение поля `action` тела просьбы, не имя обработчика; у тела без `action` такого поля нет ([договор просьбы](../../../common/ru/contracts/request-mark.md) «Mark»); `error` ДОЛЖЕН быть при `refused` и отсутствует при `performed`; если исход пришёл после `unknown` (жнеца или другого держателя) — `late: true`.


**Шаг 10.2.** Затем база воркера пишет в бакет единицы под эпохой держателя (N1.2, договор журнала событий) событие kind
`command` при `performed`, `command.failed` при `refused`: `{outcome, action?, by, late?, error?, reply}` — `action` и `by`
тела просьбы (`by` — штамп подателя), `late` и `error` — как в метке, `reply` — ответ perform; отказ до вызова — тоже
`command.failed`, без `reply` (выше); при `unknown` и `expired` события нет (видны по метке и рядам метрик); слова модуля P/07 N1.5 — по этим полям.

**Шаг 10.3.** Без ответа записать полный исход с сохранёнными полями `begun`, `ended_at`, `outcome: unknown`, `error: "no answer in <PERFORM_TIMEOUT> s"`; поздний фактический ответ ещё может заменить `unknown` на `late`. **Шаг 10.3.** Это протокол одной эпохи процесса-держателя: истечение timeout плюс grace не устанавливает завершения старого вызова или междержательный запрет перекрытия (P/03.6-R163, P/03.6-R165).

**Шаг 11.** Пульс: `fetched += SaidID(rid)` (форма — глава 3.4 N1.1 `fetched`; `said_id` — договор отметки просьбы «fetched»; консоль снимет строку).

**Гонки.** Против жнеца и второго держателя — [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md) «Гонки меток» (метки `put_new`, исход начавшего — по индексу прочитанной метки с повтором записи); против `clear` консоли — метка переживает строку: исход читается по метке.

Вызовы действия устройства соблюдают предел одного незавершённого вызова на группу единицы в одной эпохе процесса-держателя (P/03.6-R162) и ожидание после смены держателя по P/03.6-R163; это не обещает междержательного запрета перекрытия (P/03.6-R165).

В пределах одного держателя (одной эпохи процесса) — не больше одного незавершённого вызова действия на группу
единицы (`placement.group_by`, [договор группы по хосту](../../../common/ru/contracts/group-of.md); цель вызова — группа, поэтому цели размещаются вместе), в том числе после
`unknown`: пока вызов в группу не вернулся, второго в неё нет.

Память о вызове у процесса, поэтому новый держатель группы первый вызов в неё делает не раньше `PERFORM_TIMEOUT` + `PERFORM_GRACE` от взятия эпохи первой её единицы, если эта эпоха не первая: вызов прежнего держателя мог ещё идти; просьба ждёт, срок её идёт.


«Устройство не открыто» — ответ подсистемы «не готово»
(`refused` с причиной), а не задержанный вызов.

Фиксированное ожидание не доказывает физического завершения вызова прежнего держателя: после смены держателя вызовы двух держателей могут перекрываться, в том числе после unknown. Риск перекрытия вызовов последовательных держателей назван явно; междержательный запрет перекрытия не обещан.

Подсистеме SHOULD иметь ограждение по эпохе.

Если получатель действия принимает эпоху, он MUST отвергать вызов с эпохой меньше последней виденной.


Потеря эпохи запрещает прежнему держателю новые допуски и записи под guard, но не доказывает отмены или завершения уже посланного вызова.

Двухдержательный шов с поздним возвратом отмечает overlap_possible_marked без выдуманной IO-гарантии или гарантии отмены.

Вызовы идут вне потока цикла; аренды держатся при всех зависших целях.

Для единицы назначения без эпохи — сначала взять эпоху ([P/03.2](03.2-worker.norms.md) N3 «взять_эпоху(единица)»);
запуск единицы наследует эту эпоху без новой выдачи ([P/03.3](03.3-worker.norms.md) N3 шаг 2).

### заказать(E, U) — библиотека заказчика (N1.6)

Держатель U заказчика C под своей эпохой, пока `may_write`; `t_E` — время события, F — поля строки, A/rows — из `worker.creates`.

**Шаг 1.** Если манифеста A нет в каталоге манифестов, исход — `refused`.

**Шаг 2.** Если now − `t_E` > `ORDER_HORIZON`, или поле ends A в F ≠ never и ≤ now, исход — `expired` (записи нет).

**Шаг 3.** Пусть id := C + "-" + key(F) (N1.6 key); если id не по договору проверки строки «Идентификатор и ограничения полей» или ключ A/rows/id не по P/01.1 N1, исход — `refused`.

**Шаг 4.** Прочитать A/rows/id и применить ветви состояния строки P/03.6-R176, P/03.6-R177, P/03.6-R178, P/03.6-R179 и P/03.6-R180 в этом порядке; неизменность, проверка и продление своей строки — P/03.6-R181, P/03.6-R182 и P/03.6-R183, исходы хранилища — P/03.6-R184, P/03.6-R185, P/03.6-R186 и P/03.6-R187.


**Шаг 4.1.** Если строки нет: собрать строку `{id, revision: 1, born: new, made: {by: C, at: t_E, keep: t_E + ORDER_HORIZON + 120}, …}` с
полями по N1.6 fields; если общая проверка строки (договор проверки строки, создание P1–P5) отказывает, исход — `refused`;
записать с `cas ""`, стражем N1.6 и `not_after` для этого t_E по договору проверки строки, Строка заказчика: made, not_after, исход — `created`.

**Шаг 4.2.** Если это надгробие своего made с `made.gone` и t_E допущен условием tombstone договора проверки строки: строка как выше, revision надгробия + 1, новый born;
если общая проверка (создание над надгробием: те же fixed) отказывает, исход — `refused`;
записать с `cas` версии надгробия, стражем и `not_after`, исход — `created`.

**Шаг 4.3.** Если это иное надгробие (своё без gone или событие не допущено тем условием tombstone), исход — `gone` (записи нет).

**Шаг 4.4.** Если made нет или made.by ≠ C (живая строка или надгробие), исход — `taken` (записи нет).

**Шаг 4.5.** Если строка своя, новые значения: поле ends A — max(прежнее, из F), прежнее = never не трогать; made.at — max(прежний, t_E);
made.keep — max(прежний, made.at + ORDER_HORIZON + 120).

**Шаг 4.5.1.** Если значения (в том числе made.at, made.keep) не меняются, исход — `unchanged` (записи нет).

**Шаг 4.5.2.** Если общая проверка строки (договор проверки строки, правка R1–R3 изменённых полей) отказывает, исход — `refused`.

**Шаг 4.5.3.** Записать `{…row, …new, revision + 1}` с `cas` прочитанной версии, стражем и `not_after`, исход — `extended`.

**Шаг 4.6.** При `conflict` (cas) перечитать с шага 4; если предел повторов исчерпан, исход — `refused`.

**Шаг 4.7.** При `409 expired` (время приёма позже not_after) исход — `expired`; той же записью не повторять.


**Шаг 4.8.** При `412 guard` эпоха U потеряна: записи нет, исхода заказа нет; U — P/03.2 N3 «отсечь».

**Шаг 4.9.** При `unavailable` / `ambiguous` повторить той же записью с тем же id записи (P/01.1 N4; P/03.4-07).

**Шаг 5.** Исход считается в пульсе C `creates.<outcome>` (P/03.4 N1.1).

**Гонки.** Две единицы C заказывают одно событие: `cas ""` пропускает одну, вторая перечитывает и находит строку своего
`made` — `unchanged` или `extended`.

Правка оператора между чтением и записью — conflict, перечитать.


Удаление строки
(контроллер, воркер адресата, оператор) между чтением и записью — conflict; перечитанное надгробие — `gone`; строки нет
(физически удалена) — шаг 4 заводит её снова, только если запись принята не позже `not_after`: физическое удаление
строки с `made` принимается не раньше её `not_before` этой удалённой жизни по владельцу, не меньше `not_after` любого исполнимого повтора
(P/04 N3 шаг 8), а время приёма хранилища не убывает — поздний повтор получает `expired`, как бы ни шли стенные часы.

Отсечение эпохи U и запись в любом
порядке: запись сделана до смены строки эпохи или отказана `412 guard` (P/01.1 «Гонки»).

### записать состояние(U, имя, value) — держатель (N1.7)

**Шаг 1.** Если value не по схеме `unit.state.<имя>`, это ошибка подсистемы, записи нет.

**Шаг 2.** Построить key/items/guard конструктором state из [row-write-bindings.tsv](../../forms/row-write-bindings.tsv).

**Шаг 2.** Прочитать строку этого key; записать построенные items с CAS прочитанной версии (пустая строка — строки нет) и построенным guard в одной операции, пока may_write; cursor — не чаще STATE_EVERY.


**Шаг 3.** При `conflict` перечитать и повторить; при `412 guard` эпоха потеряна, записи нет (P/03.2 N3 «отсечь»).

### Исполнение и уборка метки

Таблица состояний подачи, держателя и жнеца — [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md) «Состояния исполняемой просьбы и её метки»; её строки «holder …», «another holder …», «the holder that began …» и «holder, mark cleanup» — сторона этой
главы.

Держатель применяет договор состояний метки по P/03.6-R030 через допуск вызова P/03.6-R031, запрет повторного вызова P/03.6-R197, правило позднего итога P/03.6-R198 и уборку P/03.6-R199.

При недоступном хранилище, неизвестном исходе put_new или невозможности подтвердить метку
действие не вызывается.

Обрыв после begun и до вызова может оставить unknown без исполнения:
это цена «не больше одного раза».

Ошибка публикации исхода не разрешает повторный вызов.

Поздний итог начавшего держателя снимает ended_by закрывавшего и сохраняет instance/slot/unit/
at/digest; error обязателен у refused/unknown (≤ 200 кодовых точек, длиннее — усечение с «…»: [договор метки](../../../common/ru/contracts/request-mark.md) «Mark»), у performed отсутствует.

Метки удаляет только держатель после исчезновения строки и kept; консоль метки не удаляет. Гарантия повторов ограничена временем сохранения метки: после её законной уборки клиент не переиспользует rid/Idempotency-Key и не выдаёт новую подачу за подтверждённый повтор.


Неизвестный исход требует решения человека, а не автоматического исполнения ещё раз.

### Дозапись: сторона держателя

Снятие строки после `fetched` и `settle` и освобождение `asked` делает
консоль (P/06.4 N3 «жнец» `clear`).

Дозапись идемпотентна по данным: держатель сообщает fetched, метки begun/исхода нет; тело с `action` из `elsewhere` — та же дозапись (держатель сообщает fetched). Повтор после снятия допускается и снова сверяется с данными; гарантия «один вызов через метку» к нему не относится.


Отказ дозаписи, который со временем
может стать неверным (диапазон в будущем), не окончателен и меткой не закрывается.

Метка жнеца у дозаписи (`gone`, `expired`) — сторона консоли ([P/06.4](../../../06-console/ru/spec/06.4-console.norms.md) N3 «жнец»):
держатель её не пишет; поздний `fetched` после неё безвреден (договор просьбы «States…»).

Признак дозаписи — `requests.outcome: fetched`; учебный потребитель — просьбы `testsub2`
(форма — README приёмки главы, обработчик — N5).

Учебный писатель вкладов `testsub2` — тоже обязанность стенда реализации (воркер `testsub2`), не платформы; его вклады читают приёмки [P/08.5](../../../08-domain/ru/spec/08.5-domain.norms.md) (книги домена) и глав, что идут на том же стенде: под своим слотом, под стражем слота, для каждого счёта, который ведёт, — элемент `<name>` в `testsub2/notes/<слот>` `{ref: <name>, to: <to>}` и в `testsub2/rolls/<слот>` `{ref: <name>, to: <to>, note_secret: <note_secret>}` (поле без значения — нет; поля `n` нет; `note_secret` счёта воркер открывает кольцом своего кластера и запечатывает заново к строке `rolls` с AAD [главы 3.7](03.7-worker.norms.md) N1.2 `entry` — конверт единицы привязан к ключу строки единицы; кольца нет — поля нет), объект `testsub2/counts/<слот>` `{tallies: <число счетов>}` — обязателен; пишет строку или объект, только когда изменилось открытое содержимое, а не каждым проходом (иначе версия строки растёт впустую).
