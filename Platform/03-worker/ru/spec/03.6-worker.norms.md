## N0 Словарь слов

Нормативные слова — по [канону курса](../../../common/ru/NORMATIVE-TERMS.md). Правила модуля — [P/01.1 N0](../../../01-store/ru/spec/01.1-store.norms.md#n0-словарь-слов).

## N1 Форма

**Время.** Поля времени, которые пишет воркер этой главы, — время по [канону N0 P/01.1](../../../01-store/ru/spec/01.1-store.norms.md#время-в-строке)
(P/06.4 N1 «Time»): строка события — `t`; метка `objects/<sub>/commands/<rid>` — `begun.at`, `begun.valid_until`, `ended_at`;
строка просьбы `<sub>/requests/<rid>`, которую воркер подаёт, — `valid_until`, `at` (штамп); строка заказа — `made.at`
(договор проверки строки «Строка единицы») и поле срока `placement.ends.field` адресата (N1.6); событие заказа — `t_E`.

**Данные** ([каталог](../../../common/data/catalog.tsv)):
- владеет: `<sub>/state/<name>/<id>`;
- пишет: `<sub>/<manifest:unit.rows>/<id>` (guard), `<sub>/state/<name>/<id>` (guard), `objects/<sub>/commands/<rid>` (mark), `<sub>/requests/<rid>` (create), `<events root>/<sub>/<unit>/e<epoch>/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<events root>/<sub>.alarms/<unit>/e<epoch>/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<events root>/audit/<role>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `<events root>/audit.alarms/<role>/e1/<YYYYMMDDTHHMMSSZ>.events.jsonl` (append), `objects/<sub>/<manifest:objects.rows>/*` (cas), `<events or objects root>/<path>/%h<sha256>.name` (create);
- читает: `<sub>/requests/<rid>`, `platform/manifest/<sub>`, `<sub>/requests/free-<server>-<volume>`.

Взгляд держателя читает каждую строку семьи просьб своего манифеста и строки ресурса `free-*` пропускает (N3 «взгляд
держателя»); учебный обработчик дозаписи пишет строку-объект семьи `objects.rows` `marks/*` по прочитанному индексу
(`put_at`, N5 «Учебный обработчик дозаписи»; [P/05](../../../05-resource/ru/spec/05-resource.norms.md) N1.1 `row_object`); файл
`%h<sha256>.name` кладёт рядом с длинным компонентом пути в корне событий или объектов по [договору журнала
событий](../../../common/ru/contracts/event-journal.md) «File names».

Метку держатель создаёт однажды до вызова (`begun`, `no_begun`), пишет исход начавшего по индексу прочитанной метки (conflict — перечитать и повторить только запись), закрывает чужую
`begun` по индексу и убирает после `kept` (операции метки — каталог); просьбу другого манифеста подаёт по `worker.requests`
(`cas ""`, `filed`); читает строки своих единиц своего манифеста и просьбы, которые подал, и `events.suppress`, `requests` манифеста.

Владельцы этих строк и файлов — урок P/05 (журнал событий) и глава P/06.4 (просьбы, метки); их форма для воркера — [договор журнала событий](../../../common/ru/contracts/event-journal.md)
и [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md). Строку единицы
другой подсистемы воркер-заказчик заводит и продлевает по своему `worker.creates` (N1.6; владелец строки — глава
[P/06.1](../../../06-console/ru/spec/06.1-console.norms.md)); своя семья главы — состояние единицы `<sub>/state/<name>/<id>`
(N1.7).

### N1.2 Событие: писатель и подавление

Воркер — участник `append` журнала событий: строку события, её `id`, бакет по `t`, класс и дерево тревог, `fsync` тревоги и
журнала, блокировку файла журнала он соблюдает по файловому договору урока 5 —
[договору журнала событий](../../../common/ru/contracts/event-journal.md) (`line`, `bucket`, `class`, `journal`, `writer`) и его
разделу «Запись строки». Подавление повторов — шаг 3 этого прохода:

```yaml
kinds:                                       # events.kinds.<kind>: {severity} (форма — P/02.1) — важность вида
                                             # для описания вида backend VMS; платформа её не судит и в строку события не пишет
suppress:                                    # events.suppress.<kind>: {window, by}  (форма — P/02.1)
  window:   секунды > 0
  by:       непустой список строковых имён полей строки или синтетического unit; без by — все поля строки кроме t/id/repeats/since/until; эти пять имён и пустой by — отказ загрузки
  rule:     первая строка окна — как есть; повторы считаются; по закрытии окна или на проходе — одна строка
            {…поля первой, id: новый, repeats, since, until}: repeats — проглоченные без первой; since — t первой; until — t последней
            проглоченной; t — момент записи итога; окно без повторов строки не даёт; итог прежнего окна пишется раньше первой строки
            нового
  stop:     при остановке писателя каждое открытое окно с проглоченными повторами закрывается той же строкой итога, until — момент
            остановки, под may_write и до последнего пульса; окно без повторов строки не даёт
```

Подавление всегда раздельно для (дерево, единица пути, эпоха, kind, class), независимо
от by. Имя unit в by — единица из аргументов писателя/пути бакета, не одноимённое
пользовательское поле строки. Остальные имена by — верхние поля записанной строки;
неизвестное/отсутствующее поле даёт отдельное значение «отсутствует», отличное от null.
Сравнение структурное JSON: объект без учёта порядка ключей, массив с учётом порядка,
bool не число. Отсутствие выбранного поля в конкретном событии не является ошибкой манифеста. t/id и поля
итога не участвуют; при отсутствии by остальные поля, включая occurred/of, участвуют.

Форма `events.suppress` в манифесте и отказы её загрузки — [P/02.1](../../../02-installer/ru/spec/02.1-installer.norms.md) N1.2, N4.

### N1.5 Просьба: сторона воркера

Форма строки `<sub>/requests/<rid>`, ключи манифеста `requests` и метка `objects/<sub>/commands/<rid>` — [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md);
учёт `asked` — [глава P/06.4](../../../06-console/ru/spec/06.4-console.norms.md) N1.5. Воркер в этой форме: подаёт строку по
`worker.requests` другого манифеста — поля `filed` (свой экземпляр) и `digest` (считает сам при записи, вид `worker`), `rid` по
шаблону `requests.key` цели, иначе по ключу подателя `<своя подсистема>.<ключ>` (ключ — детерминированно из своих данных,
например `<сценарий>-<id события>-<i>`) или случайный без точки — только у просьбы, повтор которой не нужен (договор просьбы
`rid`). Повтор подачи тем же `rid` проверяется порядком двери
(P/06.4 N3 «подать просьбу»: сначала метка, затем строка и окно `kept`; у цели с `requests.outcome: fetched` шага метки нет) и сверяет `unit` строки и `digest` вида `worker`: тот
же `rid`, та же `unit`, тот же `digest` — `again`; иное — `refused`; как держатель пишет метку — `begun` до вызова, `answer` начавшего, `no_begun` с `ended_by: holder`,
уборка после `kept`. Пределы держателя (строка констант N1.5; `CLEAR_EVERY`, `SWEEP_EVERY`, `REAP_AFTER` — жнец, P/06.4 N1.5):

Уставки держателя — [runtime-constants.tsv](../../forms/runtime-constants.tsv). PERFORM_GRACE и REQUESTS_HOLD выражены в секундах точным /1000; новых настроек нет.

```yaml
# PERFORM_TIMEOUT, COMMANDS_PER_LOOK: runtime-constants.tsv
PERFORM_GRACE: PERFORM_GRACE_MS / 1000
REQUESTS_HOLD: REQUESTS_HOLD_MS / 1000
```

**Подача воркером**. Штампы строки по `requests.stamp` цели — как у двери (договор просьбы «Просьба»):
`by` — `<sub>/<unit>` подателя (своя подсистема и единица, от имени которой подаёт); `at` — его часы; `group` — по
`placement.group_by` единицы-адресата ([договор группы по хосту](../../../common/ru/contracts/group-of.md)); поле `about` — значение единицы-адресата (договор просьбы `stamp`). Тело
проверяется по `requests.schema` цели (каталог манифестов, P/02.1 N3) до подачи: не по схеме — не подаётся, исход
`refused`. `maxLength` поля тела меряется по записанному тексту поля (строка — как есть, иное значение — канонический JSON) при
любом типе значения — как у двери (P/06.4 N2 `too_long`, правило таблицы [`requests-body`](../../../06-console/ru/vectors/requests-body/README.md));
прочие слова схемы — над JSON-значением. После записи строки просьбы — строка журнала, как аудит двери (P/06.4 N3 «подать просьбу» шаг 6: вид `requests.journal`
цели, дерево `audit` роли воркера): отказ журнала исхода `filed` не меняет, строка лога; `again` журнала не пишет. Счёт подачи — пульс подателя `filings.<outcome>` (`filed`, `again` — та же просьба
подана снова, `refused`; [P/03.4](03.4-worker.norms.md) N1.1). Строку под этим `rid`, при любом шаблоне `rid`, воркер, встретив её при подаче, а она есть, но не читается своей формой, — не подаёт и не трогает: исход `refused`, строка лога без значения. `rid` не по грамматике ([договор просьбы и её метки](../../../common/ru/contracts/request-mark.md)), при любом шаблоне, — то же: не подаётся, `refused`, подающий на нём не стоит.

### N1.6 Заказ строки другой подсистемы: сторона заказчика

Заказчик — подсистема C с `worker.creates: [{sub: A, rows, key}]`
(форма и проверки каталога — [P/02.1](../../../02-installer/ru/spec/02.1-installer.norms.md) N1.2a, N3) — заводит и продлевает
строки единиц адресата A сам, из библиотеки воркера, под своей эпохой. Когда, о чём и с какими полями заказывать — логика
подсистемы C (её урок); здесь — что библиотека делает с каждым заказом (N3 «заказать»).

```yaml
order:       событие E, которое исполняет единица U заказчика под своей эпохой (держатель U, P/03.2): время события t_E —
             секунды Unix по часам писателя события; поля F строки A — без поля-источника id A, без *_secret и blob
id:          <C>-<key(F)>                    # префикс не выбирается
key:         шаблон worker.creates[].key — подстановки {поле} через «-»: {поле} — значение F[поле] записью values_by_type
             (договор проверки строки: string, url — как есть; int — десятичная; float — его правило выбора; bool — true | false),
             затем каждый байт UTF-8 этой записи вне A–Z a–z 0–9 _ . ~ — %XX, hex-цифры верхним регистром (`-` → %2D,
             `%` → %25); между подстановками — литерал «-»; разные значения полей дают разные id, поэтому id задаёт эти
             значения: вернувшееся имя — тот же предмет; векторы creates-key
born:        новое случайное значение при создании (договор проверки строки, born)
made, ORDER_HORIZON, not_after, tombstone: договор проверки строки «Customer row: made» — `made` (keep), `ORDER_HORIZON`,
             `not_after` записи заказа, окно над надгробием договора проверки строки, Строка заказчика: made
fields:      строка создаётся по договор проверки строки «Подготовка полей», как у двери: непереданное — default или пустая форма типа; поле-источник id —
             готовым id; *_secret не пишутся никогда — остаются пустыми, секрет ставит оператор дверью;
             blob пусты (P/06.1 N1.5)
until:       поле срока адресата — placement.ends.field манифеста A (P/04 N1.3), если ends объявлен; продление — max(прежнего,
             нового); прежнее = never (без срока) не трогается
ends_past:   строка, чей срок по полю ends в F уже прошёл (≠ never и ≤ now по часам держателя), не заводится
deletes:     воркер адресата удаляет строку с made по worker.deletes (библиотека) — по правилу договора проверки строки
             «Customer row: made» `delete`; строку без made — как прежде (cas прочитанной версии)
guard:       каждая запись — CAS своей строки и guard {key: C/epoch/U, index: версия строки эпохи, подтверждённая при взятии
             эпохи} одной операцией (P/01.1 guard: index — версия строки, не номер эпохи), и только пока may_write
             (P/03.2 N1.6; после восстановления хранилища версия стража может совпасть — аренда сверяет пол)
writers:     строка заказа двухписательная (P/06.1 N1.1): оператор — дверью, любые поля, кроме полей key (P/06.1 N1.3
             made_key); заказчик — только строки своего made (made.by = C); строку своего made продлевать вправе любая
             единица C; строка без своего made — занята: C её не пишет
check:       общая проверка строки — договор проверки строки (P1–P5, R1–R3), та же, что у двери; её чтения выводятся из
             объявления (права — P/02.5 N1.4)
outcomes:    created | extended | unchanged | taken | gone | expired | refused   # счёт — пульс C, P/03.4 N1.1 creates
```

Исходы: `created` — строка заведена; `extended` — строка своего `made` продлена записью; `unchanged` — значения строки
своего `made` не меняются, записи нет; `taken` — строка занята (нет своего `made`); `gone` — на месте строки надгробие,
записи нет; `expired` — событие старше `ORDER_HORIZON`, срок строки уже прошёл или хранилище отказало `409 expired`, записи нет; `refused` — адресата нет в
каталоге, id не по грамматике или не помещается, общая проверка строки отказала или предел повторов исчерпан. Отсечение
эпохи (`412 guard`) исходом заказа не считается: единицу останавливает P/03.2 N3 «отсечь».

### N1.7 Состояние единицы

Конструктор key/items/guard задаёт [row-write-bindings.tsv](../../forms/row-write-bindings.tsv) по [грамматике формы](../forms/row-write-bindings.md). Снимок start неизменяем: born/revision/epoch и версия guard происходят из принятого старта, не из нового чтения. Чтение CAS-версии состояния и IO остаются процедуре R029.

Итог и курсор единицы — не поля её строки и не пульс, а строка хранилища кластера под стражем эпохи,
привязанная к жизни строки единицы (`born`). Объявление — `unit.state: {<имя>: <схема>}` (P/02.1 N1.2a); `cursor` — курсор
единицы.

```yaml
row:         конструктор state из forms/row-write-bindings.tsv; семейство state.schema.json
writer:      только держатель единицы: CAS прочитанной версии строки состояния ("" — её нет) и guard {key: <sub>/epoch/<unit>,
             index: версия строки эпохи, подтверждённая при взятии} одной операцией, пока may_write (P/03.2 N1.6);
             born и revision — запуска, не перечитанной строки единицы: отсечённый держатель, в том числе поздним повтором,
             состояние новой эпохи не перезапишет
acts:        договор проверки строки «Состояние единицы» `acts`
cursor:      unit.state.cursor действует по born (revision не сверяется: правка строки курсор не сбрасывает); монотонен —
             смысл значения задаёт подсистема; пишется не чаще STATE_EVERY; переживает переезд
STATE_EVERY: runtime-constants.tsv # период записи состояния
unreadable:  договор проверки строки «Состояние единицы» `unreadable`
delete:      держатель состояние не удаляет; удаляет контроллер — после подтверждённого удаления строки единицы и уборкой
             осиротевшего (P/04 N3); читают консоль (P/06.1 N2 «State in the answer») и контроллер (P/04 N1.3, N1.3a)
```

### Семьи данных (построены из стандартных файлов)

Форма строк и объектов, которыми глава владеет по [каталогу](../../../common/data/catalog.tsv), — JSON Schema 2020-12 семьи (ADR-0092). Экземпляр строки — `{key, row}`, объекта — `{key, object}`; ключ — грамматика колонки `key` каталога. Поля `row` — значения `items` после [кодека](../../../common/data/codec.tsv): писатель проверяет схему и её `$defs.writer`, читатель — схему (слой 3 — слова `x-*` схемы). Нечитаемо — строка не раскодировалась или не прошла схему в режиме читателя; исход — по таблице исходов семьи: путь — префикс пути отказа (пустой — строка целиком), при нескольких путях отказа действует исход с наименьшим приоритетом.

#### `<sub>/state/<name>/<id>` — строка

Схема — [`state.schema.json`](../../data/state.schema.json), исходы — [`state.outcomes.tsv`](../../data/state.outcomes.tsv); версия формы 1; норма — P/03.6 N1.7.

| Ключ | Тип и границы | Обязательность | Урок | Смысл |
|---|---|---|---|---|
| `born` | строка; целиком `[0-9a-f]{32}` | обязателен |  | The 32 lowercase hex born of the current unit row accepted at the start of the holder (row-check contract, born); absent or empty born is unreadable. |
| `revision` | целое; ≥ 1; ≤ 9007199254740991; целый знак и у читателя (x-whole) | обязателен |  | revision of the unit row at the start of the holder; a decimal integer ≥ 1 |
| `epoch` | целое; ≥ 1; ≤ 9007199254740991; целый знак и у читателя (x-whole) | обязателен |  | the holder's epoch under which it was written (P/03.2 N1.5); not checked on reading |

## N3 Проход

### взгляд держателя (воркер, на проходе; ≤ REQUESTS_HOLD, ≤ COMMANDS_PER_LOOK)

Этот проход через begun/метку — только обычный профиль. Дозапись выполняет свой
проверяющий данные обработчик и сообщает fetched без метки; elsewhere — его владелец. В профиле дозаписи
(`requests.outcome: fetched`) тело с `action` из `elsewhere` — тоже дозапись: держатель сверяет данные и сообщает fetched;
`elsewhere` выводит строку из прохода меток и из жнеца только в обычном профиле.

Порядок в группе (`placement.group_by`, «Device action» ниже): строки одной группы идут по `at` штампа, равные — по `rid` байтами, строка без `at` или с нечитаемым — после штампованных, по `rid`; вызов в группу занят — ждут и все младшие: `rid` двери случаен, по имени стоп, поданный вслед движению, исполнился бы раньше. Предел: `at` — часы подателя, две консоли с разбежкой часов порядка не держат, а у `at` одной секунды порядок даёт `rid`; строки разных групп не упорядочены.

Для каждой строки семьи с `unit` моей единицы (просьбы ресурса — строки без `unit` с `{free, volume, server}` — не рассматриваются; имя
`free-*` само по себе ничего не значит; `elsewhere` — не мои действия; строка `free-<server>-<volume>` не по форме
ресурса — не просьба: пропустить её, причина в журнал без значения):

1. Если строка просьбы или её метка не читается своей формой (исходы — `requests.outcomes.tsv`, `commands.outcomes.tsv` P/06.4),
   остановить операцию над этой строкой: без записи, удаления и вызова действия; строка лога, `garbled_rows` пульса + 1
   (глава 3.4 N1.1).
2. Если у метки есть исход, пропустить её (чужая или моя прежняя).
3. Если это своя `begun` без исхода, не вызывать снова; ждать уже начатое действие.
4. Если срок дальше `most_valid`, отказать до вызова (метка `refused` и событие — ниже); это раньше закрытия чужой `begun` и раньше срока.
5. Если это чужая `begun` без исхода: если её `at` + `PERFORM_TIMEOUT` + `PERFORM_GRACE` позади, записать `{outcome: unknown, ended_by: holder,
   error: "begun by <instance> and never answered"}` по прочитанному индексу (закрывающий пишет по индексу; при `conflict` —
   перечитать, и если исход появился, не трогать); иначе (исполняется) пропустить; `begun` — не `expired` и после срока.
6. Если срок вышел, создать метку `expired` однажды; дальше.
   Порядок проверок: метка с исходом, `most_valid`, чужая `begun`, затем срок.
7. Если штамп `group` просьбы непуст и не равен группе единицы по `placement.group_by` её прочитанной строки (договор группы по хосту; нет `group_by` — группа пуста),
   группа переехала: отказать до вызова, `error: "unit <id> was moved to another group after this request was given: it was not performed — give it again if it is still wanted"`;
   если штампа нет или он пуст, он не сверяется.
8. При отказе до вызова (срок дальше `most_valid` — выше; группа переехала, эпоха чужая) создать метку `refused` однажды `{…, error: the reason}`;
   и записать событие `command.failed {outcome: refused, action?, by, error}` в бакет единицы под эпохой держателя, как при
   отказе после вызова, без `reply`; если эпохи единицы у держателя нет (не взята), события нет, отказ виден меткой и рядом метрик.
   Держатель проверяет до вызова срок (`valid_until` в прошлом → `expired`; дальше `most_valid` → `refused`), штамп `group` и свою эпоху
   единицы — берёт только строки единиц, которые ведёт под своей арендой.
9. Создать метку `begun` = `put_new {instance, slot, unit, of?, at, digest, valid_until?}`; при `conflict` перечитать;
   при отказе или неизвестном исходе — без вызова; только подтверждённый успех разрешает действие.
10. Вызвать действие с таймаутом `PERFORM_TIMEOUT` (+ `PERFORM_GRACE`).
    1. При ответе прочитать метку и записать исход по её индексу; при `conflict` перечитать и повторить только запись, perform
       не повторяется (у двери хранилища нет «преобразовать» — так запись атомарна относительно прочитанного, а слово
       держателя по-прежнему побеждает слово жнеца: жнец и второй держатель пишут по индексу однажды); `late: true` ставится по той прочитанной метке,
       по чьему индексу запись прошла.
       Исход — `{outcome: performed | refused, action?, reply?, ended_at}`; `reply` — ответ perform, то же, что в событии ниже ([договор просьбы](../../../common/ru/contracts/request-mark.md) «Mark»); `action` — значение поля `action` тела просьбы, не имя обработчика; у тела
       без `action` такого поля нет ([договор просьбы](../../../common/ru/contracts/request-mark.md) «Mark»);
       `error` ДОЛЖЕН быть при `refused` и отсутствует при `performed`; если исход пришёл после `unknown` (жнеца или другого держателя) — `late: true`.
    2. Затем база воркера пишет в бакет единицы под эпохой держателя (N1.2, договор журнала событий) событие kind
       `command` при `performed`, `command.failed` при `refused`: `{outcome, action?, by, late?, error?, reply}` — `action` и `by`
       тела просьбы (`by` — штамп подателя), `late` и `error` — как в метке, `reply` — ответ perform; отказ до вызова — тоже
       `command.failed`, без `reply` (выше); при `unknown` и `expired` события нет (видны по метке и рядам метрик); слова модуля P/07 N1.5 — по этим полям.
    3. Без ответа записать полный исход с сохранёнными полями `begun`, `ended_at`, `outcome: unknown`,
       `error: "no answer in <PERFORM_TIMEOUT> s"`; поздний фактический ответ ещё может заменить `unknown` на `late`.
       Это протокол одной эпохи процесса-держателя: истечение timeout плюс grace не устанавливает завершения старого вызова или междержательный запрет перекрытия (R025).
11. Пульс: `fetched += SaidID(rid)` (форма — глава 3.4 N1.1 `fetched`; `said_id` — договор отметки просьбы «fetched»; консоль снимет строку).


**Гонки.** Против жнеца и второго держателя — [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md) «Гонки меток» (метки `put_new`, исход начавшего — по индексу прочитанной метки с повтором записи); против `clear` консоли — метка переживает строку: исход читается по метке.

Действие устройства. В пределах одного держателя (одной эпохи процесса) — не больше одного незавершённого вызова действия на группу
единицы (`placement.group_by`, [договор группы по хосту](../../../common/ru/contracts/group-of.md); цель вызова — группа, поэтому цели размещаются вместе), в том числе после
`unknown`: пока вызов в группу не вернулся, второго в неё нет. Память о вызове у процесса, поэтому новый держатель группы первый вызов в неё делает не раньше `PERFORM_TIMEOUT` + `PERFORM_GRACE` от взятия эпохи первой её единицы, если эта эпоха не первая: вызов прежнего держателя мог ещё идти; просьба ждёт, срок её идёт. «Устройство не открыто» — ответ подсистемы «не готово»
(`refused` с причиной), а не задержанный вызов. Фиксированное ожидание не доказывает физического завершения вызова прежнего держателя: после смены держателя вызовы двух держателей могут перекрываться, в том числе после unknown. Риск назван явно; междержательный запрет перекрытия не обещан. Подсистеме SHOULD иметь ограждение по эпохе. Если получатель действия принимает эпоху, он MUST отвергать вызов с эпохой меньше последней виденной. Потеря эпохи запрещает прежнему держателю новые допуски и записи под guard, но не доказывает отмены или завершения уже посланного вызова. Двухдержательный шов с поздним возвратом отмечает overlap_possible_marked без выдуманной IO-гарантии или гарантии отмены. Вызовы идут вне потока цикла; аренды держатся при всех зависших целях.
Для единицы назначения без эпохи — сначала взять эпоху ([P/03.2](03.2-worker.norms.md) N3 «взять_эпоху(единица)»);
запуск единицы наследует эту эпоху без новой выдачи ([P/03.3](03.3-worker.norms.md) N3 шаг 2).

### заказать(E, U) — библиотека заказчика (N1.6)

Держатель U заказчика C под своей эпохой, пока `may_write`; `t_E` — время события, F — поля строки, A/rows — из `worker.creates`.

1. Если манифеста A нет в каталоге манифестов, исход — `refused`.
2. Если now − `t_E` > `ORDER_HORIZON`, или поле ends A в F ≠ never и ≤ now, исход — `expired` (записи нет).
3. Пусть id := C + "-" + key(F) (N1.6 key); если id не по договору проверки строки «Идентификатор и ограничения полей» или ключ A/rows/id не по P/01.1 N1, исход — `refused`.
4. Прочитать A/rows/id:
   1. Если строки нет: собрать строку `{id, revision: 1, born: new, made: {by: C, at: t_E, keep: t_E + ORDER_HORIZON + 120}, …}` с
      полями по N1.6 fields; если общая проверка строки (договор проверки строки, создание P1–P5) отказывает, исход — `refused`;
      записать с `cas ""`, стражем N1.6 и `not_after` для этого t_E по договору проверки строки, Строка заказчика: made, not_after, исход — `created`.
   2. Если это надгробие своего made с `made.gone` и t_E допущен условием tombstone договора проверки строки: строка как выше, revision надгробия + 1, новый born;
      если общая проверка (создание над надгробием: те же fixed) отказывает, исход — `refused`;
      записать с `cas` версии надгробия, стражем и `not_after`, исход — `created`.
   3. Если это иное надгробие (своё без gone или событие не допущено тем условием tombstone), исход — `gone` (записи нет).
   4. Если made нет или made.by ≠ C (живая строка или надгробие), исход — `taken` (записи нет).
   5. Если строка своя, новые значения: поле ends A — max(прежнее, из F), прежнее = never не трогать; made.at — max(прежний, t_E);
      made.keep — max(прежний, made.at + ORDER_HORIZON + 120).
      1. Если значения (в том числе made.at, made.keep) не меняются, исход — `unchanged` (записи нет).
      2. Если общая проверка строки (договор проверки строки, правка R1–R3 изменённых полей) отказывает, исход — `refused`.
      3. Записать `{…row, …new, revision + 1}` с `cas` прочитанной версии, стражем и `not_after`, исход — `extended`.
   6. При `conflict` (cas) перечитать с шага 4; если предел повторов исчерпан, исход — `refused`.
   7. При `409 expired` (время приёма позже not_after) исход — `expired`; той же записью не повторять.
   8. При `412 guard` эпоха U потеряна: записи нет, исхода заказа нет; U — P/03.2 N3 «отсечь».
   9. При `unavailable` / `ambiguous` повторить той же записью с тем же id записи (P/01.1 N4; P/03.4-07).
5. Исход считается в пульсе C `creates.<outcome>` (P/03.4 N1.1).

**Гонки.** Две единицы C заказывают одно событие: `cas ""` пропускает одну, вторая перечитывает и находит строку своего
`made` — `unchanged` или `extended`. Правка оператора между чтением и записью — conflict, перечитать. Удаление строки
(контроллер, воркер адресата, оператор) между чтением и записью — conflict; перечитанное надгробие — `gone`; строки нет
(физически удалена) — шаг 4 заводит её снова, только если запись принята не позже `not_after`: физическое удаление
строки с `made` принимается не раньше её `not_before` этой удалённой жизни по владельцу, не меньше `not_after` любого исполнимого повтора
(P/04 N3 шаг 8), а время приёма хранилища не убывает — поздний повтор получает `expired`, как бы ни шли стенные часы. Отсечение эпохи U и запись в любом
порядке: запись сделана до смены строки эпохи или отказана `412 guard` (P/01.1 «Гонки»).

### записать состояние(U, имя, value) — держатель (N1.7)

1. Если value не по схеме `unit.state.<имя>`, это ошибка подсистемы, записи нет.
2. Построить key/items/guard конструктором state из [row-write-bindings.tsv](../../forms/row-write-bindings.tsv). Прочитать строку этого key; записать построенные items с CAS прочитанной версии (пустая строка — строки нет) и построенным guard в одной операции, пока may_write; cursor — не чаще STATE_EVERY.
3. При `conflict` перечитать и повторить; при `412 guard` эпоха потеряна, записи нет (P/03.2 N3 «отсечь»).

### Исполнение и уборка метки

Таблица состояний подачи, держателя и жнеца — [договор просьбы и её метки](../../../common/ru/contracts/request-mark.md) «Состояния исполняемой просьбы и её метки»; её строки «holder …», «another holder …», «the holder that began …» и «holder, mark cleanup» — сторона этой
главы. Из того же раздела:

При недоступном хранилище, неизвестном исходе put_new или невозможности подтвердить метку
действие не вызывается. Обрыв после begun и до вызова может оставить unknown без исполнения:
это цена «не больше одного раза». Ошибка публикации исхода не разрешает повторный вызов.
Поздний итог начавшего держателя снимает ended_by закрывавшего и сохраняет instance/slot/unit/
at/digest; error обязателен у refused/unknown (≤ 200 кодовых точек, длиннее — усечение с «…»: [договор метки](../../../common/ru/contracts/request-mark.md) «Mark»), у performed отсутствует.
Метки удаляет только держатель после исчезновения строки и kept; консоль метки не удаляет.
Гарантия повторов ограничена временем сохранения метки: после её законной уборки
клиент не переиспользует rid/Idempotency-Key и не выдаёт новую подачу за подтверждённый повтор.
Неизвестный исход требует решения человека, а не автоматического исполнения ещё раз.

### Дозапись: сторона держателя

Снятие строки после `fetched` и `settle` и освобождение `asked` делает
консоль (P/06.4 N3 «жнец» `clear`). Дозапись идемпотентна по данным: держатель сообщает fetched, метки begun/исхода
нет; тело с `action` из `elsewhere` — та же дозапись (держатель сообщает fetched). Повтор после снятия допускается и снова сверяется с данными; гарантия
«один вызов через метку» к нему не относится. Отказ дозаписи, который со временем
может стать неверным (диапазон в будущем), не окончателен и меткой не закрывается.
Метка жнеца у дозаписи (`gone`, `expired`) — сторона консоли ([P/06.4](../../../06-console/ru/spec/06.4-console.norms.md) N3 «жнец»):
держатель её не пишет; поздний `fetched` после неё безвреден (договор просьбы «States…»).
Признак дозаписи — `requests.outcome: fetched`; учебный потребитель — просьбы `testsub2`
(форма — README приёмки главы, обработчик — N5).

Учебный заказчик `testsub` и учебный держатель состояния `testsub2` — обязанность стенда реализации, не платформы
(сценарий 08):

```yaml
tally_order:   держатель счётчика testsub со start ≥ 1000 при запуске единицы — событие E с t_E = время запуска по своим часам —
               заказывает строку testsub2/tallies (worker.creates testsub) с F = {of: <id счётчика>, until: t_E + 600};
               id — testsub-<of>; повторный запуск (новое событие) продлевает until; счётчики со start < 1000 не заказывают
tally_result:  держатель счёта testsub2 при запуске пишет состояние result {state: "open"}, если действующего result нет
```

Учебный обработчик дозаписи `testsub2` — обязанность стенда реализации (воркер `testsub2`), не платформы:

```yaml
tally_marks:   objects/testsub2/marks/<unit> {count, ranges}   # строка-объект семьи objects.rows [marks/*] манифеста testsub2
  count:       целое ≥ 0 десятичной строкой — сколько целых счёт уже покрыл
  ranges:      покрытые отрезки «<a>-<b>» через запятую, по возрастанию, без пересечений и стыков; пусто — ""
handle:        строка просьбы {unit, from, to} своей единицы (взгляд держателя, профиль дозаписи):
               1. прочитать tally_marks по индексу (нет — {count: "0", ranges: ""})
               2. новые = целые [from, to] вне ranges; from > to — новых нет; число и слияние — арифметикой отрезков,
                  без перебора целых: предела длины диапазона нет
               3. есть новые → count += их число, ranges ∪= [from, to] (слить), записать по прочитанному индексу;
                  conflict → ничего не сообщать, повторить следующим взглядом
               4. данные записаны или новых нет → fetched += rid; метки не писать
```

Учебный писатель вкладов `testsub2` — тоже обязанность стенда реализации (воркер `testsub2`), не платформы; его вклады
читают приёмки [P/08.5](../../../08-domain/ru/spec/08.5-domain.norms.md) (книги домена) и глав, что идут на том же стенде:
под своим слотом, под стражем слота, для каждого
счёта, который ведёт, — элемент `<name>` в `testsub2/notes/<слот>` `{ref: <name>, to: <to>}` и в `testsub2/rolls/<слот>`
`{ref: <name>, to: <to>, note_secret: <note_secret>}` (поле без значения — нет; поля `n` нет; `note_secret` счёта воркер
открывает кольцом своего кластера и запечатывает заново к строке `rolls` с AAD [главы 3.7](03.7-worker.norms.md) N1.2 `entry` —
конверт единицы привязан к ключу строки единицы; кольца нет — поля нет), объект `testsub2/counts/<слот>`
`{tallies: <число счетов>}` — обязателен; пишет строку или объект, только когда изменилось открытое содержимое, а не
каждым проходом (иначе версия строки растёт впустую). Строки `notes`, `rolls` — под стражем
слота; объект `counts` — без CAS (у объектов стражи нет, как у пульса), его пишет только держатель подтверждённого слота,
потерявший слот не пишет.

Пульс несёт `fetched` по форме [главы 3.4](03.4-worker.norms.md) N1.1 (`said_id`); сценарий 07 наблюдает его следствие — снятие строки жнецом, у
дозаписи единственное основание снятия, — и для rid до 40 символов, и для длинного rid, который пульс называет хэшем.

Проверяются чтением: подавление (раздельность, `by`, отсутствующее поле, структурное сравнение, итог окна) — в приёмке P/02.1
нет случаев `suppress`, стенд не пишет повторов одного вида; конкурирующие держатели, потерянный ответ `put_new`, поздний ответ
после `unknown`, ошибка публикации метки и уборка метки после `kept` — свидетельства вне TSV [README приёмки](../acceptance/6/README.md) (только для судьи: README приёмки главы).
