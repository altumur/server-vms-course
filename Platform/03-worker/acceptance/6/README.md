## Подготовка каждого сценария

Два сценария независимы. Перед каждым остановить и дождаться всех процессов прошлого
сценария, создать изолированные каталоги/порты и пустое хранилище: строки, объекты,
память id хранилища, заявки POST консоли, учёт asked и метки commands отсутствуют.
Очистить дерево событий, зеркала и кэш индекса, переменные и ключи повторов раннера.
Установить актуальную testsub из общих testdata с её служебной меткой административными
правами. Единиц и пользовательских строк ещё нет. Подготовка — не перенос состояния
предыдущего сценария и не проверка установщика.

Запустить хранилище, новую консоль testsub и ресурс srv-a по разделу «Стенд» общего README приёмки. Их двери должны быть готовы;
ресурс зарегистрирован и доступен консоли до первого шага. Все процессы этой коробки
используют одну BOX_ID и server=srv-a; каждый новый процесс получает новый instance.
Контроллера и воркеров первоначально нет: сценарии запускают их директивами @start.
platform/mirror и platform/space не заданы; запросы освобождения и копии не готовятся.

console — дверь консоли testsub с петли, доступ к операциям и единицам разрешён;
resource — дверь ресурса srv-a с допустимой личностью; store — дверь хранилища с чтением
testsub/ и objects/testsub/. Если развёртывание использует TLS, выдать соответствующие
сертификаты и роли по P/02.4 Н1.6 (`w2c-ca.sh issue <server> <роль>`, комплект `kit`) и правилу адреса P/02.4 Н1.6;
проверку отказов TLS эти сценарии не заменяют.
Сроки и параметры testsub не ускорять: valid_for=30, most_valid=600; ожидаются обычные
такты держателя и жнеца, settle=60 по умолчанию.

**Сценарий 07** (дозапись) ставит каталог `testsub` и `testsub2` (порядок — «Стенд» общего README приёмки) и запускает контроллеры и
воркеры обеих директивами; `store` читает также `testsub2/` и `objects/testsub2/`. Полки `sh1`
(шаг 6) и `sh2` (шаг 19) кладутся строкой хранилища ролью `console` (`@as console store`), а не дверью таблиц P/06.1 (Н1.6):
приёмка главы от двери таблиц не зависит (журнал cammeta-go, урок 8 № 1). `@as` действует на шаг и следующие
`store`-шаги (словарь общего README приёмки), поэтому ближайшие следующие `store`-шаги 8 и 21 возвращают роль сценария —
`testsub2worker`: она читает `testsub2/`, `objects/testsub2/commands/*` и строки-объекты `objects/testsub2/marks/*`
(журнал cammeta-python, урок 8 № 34). Сроки `testsub2` не ускорять:
settle=30. Воркер `testsub2` несёт учебный обработчик дозаписи (нормы главы Н5): счёт — строка-объект
`objects/testsub2/marks/<единица>` `{count, ranges}`. `fetched` пульса (глава 3.4 Н1.1, имена `SaidID`) сценарий видит через
снятие строки жнецом — единственное основание снятия дозаписи; шаги 19–24 — своя полка `sh2` в зоне `z2` (`spread_by: zone` не ставит две единицы одной зоны на один сервер) и единица с именем длиннее 40 символов: её rid
пульс называет хэшем `#<20 hex>`, строка всё равно снимается (имя единицы с запятой грамматика P/06.1 Н1.3 не пускает). Пределы тела/памяти не должны мешать приведённым малым запросам.

## scenarios.tsv

Формат — словарь директив и дверей «Стенда» общего README приёмки: двери `console`, `console2`, `resource`, `store`,
директивы `@start`, `@until`, `@as`, `@key`, `@sleep`, `@sigterm`. Всего 48 шагов: 40 HTTP (с @until, @as и @key), шесть
@start, @sleep и @sigterm; 2 сценария / 48 шагов. Шаги 05/7–8 — строка стоит через 20 с после `performed`
(нижняя граница settle с запасом); 05/11–13 — пульс через дверь объектов: обязательные поля и последний пульс при SIGTERM
с пустым `status` (мутационная проверка 7cecaf2 № 24, 26, 37).

Шаги сверка python и go М10/6–11 (2026-10-18):
- **05/12–13** — пульс ресурса несёт `units` (`c5` на `w-1`), `waits`, `restore`, `mirror`; `W-1` при `w-1` — 404; прежние
  шаги 12–13 стали 14–15 (E2, E39).
- **07/25–30** — штамп `about` (`of: c1`) и `by` в строке просьбы; журнал `tally.asked` с `sub`, `target`, `addr`;
  `from: -0` — rid `t1-0-0`, счёт `0-3,7-7`; `valid_until` у спеки без `most_valid` — 400 (E53, E54, E56, E57). Квота
  `per_person: 3` не мешает: прежние rid к шагу 25 сняты.

`Idempotency-Key` и `@key(N)` — по словарю. Тело повтора 05/10 совпадает с первоначальным.

Сценарий 05 после performed допускает 90 с (settle 60 плюс такт/запас);
раннер не должен завершать весь сценарий раньше суммарного бюджета его шагов. После
последнего шага дождаться остановки всех созданных процессов, затем удалить состояние.

## Сравнение

Формы ожидания — по словарю. Ожидание одного кода не требует пустого тела.

Повтор переменной внутри expect сравнивает её временное значение.
В 05 перед отправкой шага 5 раннер связывает $rid = r- + первые 16 строчных hex SHA-256
точных UTF-8 байтов выданного этому шагу Idempotency-Key (у testsub нет requests.key).
Шаг 05/5 принимает только 200 Answered либо 202 Queued по полному контракту: у 202
queued равен заранее вычисленному $rid; у 200 answered относится к c5 и digest поданного
тела. Другой 2xx контрактом не разрешён. Так быстрый ответ не меняет переменные следующих шагов. Директивы не отправляются
серверу как HTTP. Полный ответ дополнительно проверяется по контракту его владельца:
хранилище — P/01.1, единицы — P/06.1, двери ресурса — P/05 Н2, остальные двери — [глава P/06.4](../../../06-console/spec/06.4-console.norms.md) Н2. В частности, answered
с @any в TSV всё равно обязан быть полной меткой одной из трёх форм AnsweredMark.

## Свидетельства вне TSV

Это задания реализации/стенда, а не уже выполненные проверки:

| Область | Контрпример и требуемое наблюдение |
|---|---|
| Подавление | suppress выдаёт первую и итог (из строки «События» прежнего README) |
| Просьбы | Два претендента на begun: не более одного вызова; потерянный ответ put_new: ноль вызовов по предположению. Чужое unit/digest не перезаписано; unknown не запускает повтор |
| Исход и уборка | Старый CAS жнеца не затирает performed. Поздний ответ заменяет unknown с late. Ошибка публикации метки оставляет строку; консоль метку не удаляет |

Дополнительные пробы Kimi 33: Исход refused после вызова всегда имеет error, performed никогда; проверить и проход, и форму метки. Это задания проверки норм/стенда, не утверждение об исполнении реализации.

Дополнительная проверка класса ошибок прогона 36 (Kimi), чтением: suppress всегда разделён по дереву/единице/эпохе/kind/class; by — непустой список строк, t/id/repeats/since/until запрещены. unit берётся из пути, отсутствующее выбранное поле отличается от null; без by исключаются только пять служебных полей. Сверить структурные JSON-значения, две разные единицы и эпохи. Срок kept без valid_until начинается только от подтверждённого ended_at.

Дополнительный случай R38-03/04/05:

- Дозапись, P/03.6-04 (держатель) и P/06.4-07 (консоль) (сценарий 07 — путь просьба → данные → снятие → повтор; остальное ниже — чтением; загрузку ключа
  проверяют случаи P/02.1 `requests_outcome_*`, долг продукта — в ХОД-Спецификация.md): допустимая единица testsub2/tallies/t1, просьба {unit:"t1",from:1,to:2}, rid=t1-1-2, резерв asked. Держатель сверяет данные и сообщает fetched; objects/testsub2/commands/t1-1-2 отсутствует до/после. После местного settle консоль снимает прочитанную версию строки CAS и освобождает rid в asked CAS, сохраняя конкурентно добавленный rid. Конфликт CAS/неизвестный fetched не разрешает считать снятие выполненным. Повтор после снятия снова сверяет данные без begun и не повторяет уже лежащий диапазон. Без fetched метка expired/unknown не создаётся и один возраст не освобождает резерв. Elsewhere record и free_ask не попадают в эту ветвь. Это отдельный случай границы ADR-0054, не выполненный прогон rec и не обещание единственного вызова для дозаписи.

Форма потребителя дозаписи в `testsub2` (в байтах спеки с 2026-10-17, ADR-0054 доп. 2026-10-17; поле `action` —
разбор ревью стадии A 6–7, № 14):

```yaml
requests:                     # профиль дозаписи ADR-0054: ключ из данных, итог — fetched держателя, метки нет
  free: true
  schema: {type: object, required: [unit, from, to], additionalProperties: false,
           properties: {unit: {type: string}, from: {type: integer}, to: {type: integer}, action: {type: string}}}
  key: "{unit}-{from:int}-{to:int}"
  outcome: fetched
  per_person: 3
  settle: 30
  ttl: 3600
  stamp: [by, at, about]
  journal: tally.asked
  elsewhere: [recount]
# держатель единицы tallies прибавляет к её счёту число целых из [from, to], которых счёт ещё не покрыл
# (покрытые диапазоны — в строке-объекте objects/testsub2/marks/<единица>, нормы главы Н5), и называет rid в fetched пульса; повтор по данным
# ничего не прибавляет
```

Это предмет ручной проверки спецификации и будущей проверки реализации. Подготовленные запросы, чтение и конечные модели автора не являются выполненным стендовым испытанием.
