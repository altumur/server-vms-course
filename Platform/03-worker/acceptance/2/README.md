# Приёмка P/03.2 — слот, эпоха, аренда, никто, место (стенд)

Стенд, словарь директив и дверей — [общий README приёмки](../../../common/acceptance/README.md#словарь-директив-и-дверей).
Норма главы — [`03.2-worker.norms.md`](../../spec/03.2-worker.norms.md) Н5. Сценарии перенесены из приёмки
М10/05 (стадия B, ADR-0083 доп. (1): без изменения
поведения); номера сценариев и шагов — прежние, кроме сц. 04 и 08: первый шаг — `@start resource`, прежние сдвинуты на один (P03-OBJECTS-DEFAULT-1FD; решение «Архитектора» 2026-10-27). Сц. 02, 06 — приёмка главы 3.3, сц. 03 — главы 3.4, остальные — [P/04](../../../04-controller/acceptance/README.md).

Сценарии на стенде из процессов `testsub` реализации: хранилище, консоль `testsub`, контроллер `testsub` и воркеры
`testsub` (учебный воркер счётчиков), которыми управляет раннер. Каталог стенда — два манифеста, `testsub` и `testsub2`, в порядке
раздела «Стенд» общего README приёмки (сверка python и go М10/3–5, п. 24): воркер одного манифеста при захвате и чистке не трогает
строк другой. Учебный воркер `testsub` докладывает запущенный счётчик элементом `status` с `phase: running` (глава 3.4 Н1.1
`phase`) и одним словом подсистемы `n` — значением счётчика (глава 3.4 Н1.1 `status`; второй пилот, Н-7). Наблюдение — строки
через дверь хранилища P/01.1 и единицы через дверь консоли P/06.1; пульс (объект) здесь не читается. Контроллер стенда —
сосед по контракту (каталог данных, жизненный цикл P/04), не нормы главы (план переноса урока 3, В2).

## Границы сценариев

Между сценариями раннер останавливает все процессы, которые запустил, сбрасывает хранилище (строки и объекты) и переменные `$имя`: каждый сценарий начинается с пустого хранилища, слота `w-1` нет, консоль перезапущена.

## Точная подготовка и завершение

Каждый сценарий получает новое изолированное хранилище, новую консоль, пустую память id хранилища
и пустые заявки POST, а также очищенные объекты пульсов/контроллера/соперников и переменные раннера.
Перед началом установлен каталог `testsub` и `testsub2` из общих testdata и служебные метки манифестов.
Нет чужих контроллеров, ресурсов, запасных процессов и таймеров запуска. Дверь консоли открыта с петли;
роль чтения хранилища имеет доступ к testsub/ и testsub2/. Подготовка использует отдельные административные права.

Все воркеры сценария имеют постоянную BOX_ID стенда и server = srv-a, кроме `@start worker … on <сервер>` (словарь общего README приёмки; разбор ревью стадии B 3–5, № 33) и окружения `<ИМЯ>=<значение>` сц. 22; каждая копия получает новый
instance. Имя передаётся подстановкой `{name}` директивы (общий README приёмки, «Стенд»; разбор ревью стадии B 3–5, № 33). Убывающий бюджет памяти не провоцируется: выбранные
CAPACITY/WORKER_MEMORY_MB должны удовлетворять Н1.2 главы 3.4. Обычная конфигурация testsub использует
safe-умолчания; параметры подмены и сроков не ускоряются ради теста.

@start подтверждает запуск процесса, готовность слота проверяют следующие @until.
В 05-sigkill шаг 3 ждёт также released="false": промежуточная запись захвата с released="true"
ещё не готова к SIGKILL. Только после завершённого захвата посылается сигнал.
@sigkill посылает сигнал нужному процессу и **ждёт подтверждённого завершения**;
таймаут/неверный процесс — отказ раннера, а не ok. В 05-sigkill контрольный until читается после
этого подтверждения, затем сравнивается через 20 с: чтение до сигнала допускало гонку с продлением.
После сценария раннер завершает и дожидается всех созданных процессов, включая первую копию w-1,
лишь затем удаляет состояние. Параллельный сценарий использует другие порты и каталоги.

## Точное сравнение и границы

Заголовок TSV и комментарии пропускаются. Номера шагов непрерывны внутри сценария.
@until повторяет только вложенный запрос и сравнение до предела; исчерпанный предел — FAIL.
Директива ASSERT сравнивает связанные значения: $имя связывается при первом появлении, далее сравнивается.
Новые связи переменных каждой попытки сравнения сначала временные: они становятся общими только
после совпадения кода и всего expect. Повтор переменной внутри expect сравнивается с её временным
значением. Неуспех любого поля, типа, элемента массива или кода отбрасывает все новые связи этой
попытки; уже общие связи не меняются. Порядок обхода полей результата не меняет.
Это относится и к обычному HTTP-шагу, и к каждой попытке @until, и к ASSERT.
Контроль для 04-two-copies, шаг 8: старый holder с gen="1" не связывает $h2; следующий ответ
с новым holder и gen="2" успешно связывает $h2 с новым. Связанный прежде $h1 сохраняется.
@any требует наличия поля; @absent — отсутствия; ~текст — строкового вхождения.
JSON-типы точны, true не равно 1; объекты сравниваются по указанным полям рекурсивно,
массивы — по числу, порядку и значениям элементов, кроме массивов без нормированного порядка (`configured`) — словарь общего README приёмки. Ожидание одного кода не требует пустого тела.
Полный HTTP-ответ дополнительно соответствует контракту хранилища (P/01.1) или единиц (P/06, глава 6.1).

Сценарии наблюдают строки и HTTP-ответы, не содержимое объектов пульса и не фактические внешние записи
единицы. Смена эпохи/назначения сама по себе не доказывает, что старый процесс прекратил работу.
05-sigkill доказывает неизменность строки на протяжении наблюдаемых 20 с после краха,
не общую границу 90 с: контроллер может раньше получить достоверное gone. Остальные свидетельства —
Н5 норм, включая другую коробку и закрытие писателя места.

## Проверки вне TSV после прогона 25

Для unknown server оставить известные BOX_ID/instance и взятое имя, но не задавать сервер;
в отдельном манифесте включить places.server_field и places.lease: strict. Прочитать пульс по двери объектов или проверить
формирование объекта чтением: server присутствует и равен "", server_unsaid содержит текст
ADR-0029, все места строгие. Отдельный вариант с известным сервером даёт непустой server и не
содержит server_unsaid. Подстановка BOX_ID вместо сервера не проходит. Обычный TSV задаёт srv-a
и эту ветвь не наблюдает.

Сравнение @until проверить на двух последовательных ответах: holder=old/gen="1", затем
holder=new/gen="2", при expect holder=$h2/gen="2". Первая попытка не сохраняет $h2; вторая
проходит и связывает его с new. Проверить оба порядка полей и повтор переменной в одном expect.
Общие переменные прежних успешных шагов остаются неизменными после любой неудачной попытки.

## Поздний ответ выдачи эпохи

Отдельно от TSV проверить первый запуск на управляемых часах по
[случаям «Первое окно аренды»](#первое-окно-аренды-проверка-после-прогона-26) ниже (из приёмки М10/03):
отправка в 0, ответы в 24/25/30; пауза между ответом и start_unit; новая CAS-попытка с новым
временем отправки; потеря слота или writing_allowed за время запроса. Записывать вызовы
start_unit, а не только номер epoch. Поздний успех не запускает единицу и не становится silent
даже при forever; номер не откатывается. Следующая попытка требует нового успешного чтения
назначения. Шаги TSV эту задержку не задают.

Гонку с подменой проверить по обе стороны локального принятия запуска: отсечение до него
не даёт start_unit; отсечение после него видит также незавершённый запуск и отменяет/останавливает
его, аренда fenced, поздний результат не публикует ведомую единицу заново. Дополнительный
порядок: запрос эпохи → потеря имени → возврат имени → старый ответ; старый ответ не запускает
единицу даже при вновь открытых воротах. Только новая попытка после нового чтения назначения
может запуститься. Во время задержки запроса/start_unit подмена способна закрыть допуск;
удержание блокировки через весь внешний вызов, мешающее отсечению, не проходит проверку.
Повторить гонку для перезапуска по revision: новый номер не выдаётся, last не сбрасывается,
отсечение отменяет и этот запуск. При silent и may_write=true прежняя единица может продолжать
данные, а изменение revision ждёт подтверждения; после него перезапуск сохраняет эпоху/аренду.

### Сроки слота (прогон 25)

Для слота нужны чтение реализации или управляемая модель: одна история версий, первый взгляд
судьи в t=0, until писателя со сдвигами -30/0/+300 с. На t=20 живость одинакова; при gone

### Первое окно аренды: проверка после прогона 26

Отдельное управляемое время/чтение реализации владельцем, не основной TSV: слот и назначение
получены, все ворота открыты, запрос записи новой эпохи отправлен в t=0. Успех с ответом в 24

было нового подтверждения. Повторить для off, конечного unconfirmed_max и forever: поздняя
первая выдача не является silent. Для CAS-conflict следующая попытка имеет собственный t0:
conflict в 30, новая отправка в 31 и успех в 34 дают окно от 31, а не от первого вызова или 34.

потерять слот/writing_allowed во время запроса с быстрым ответом: повторные ворота запрещают
start_unit, хотя окно ещё открыто. Нужен журнал реальных вызовов start_unit и времени запросов;
одна строка epoch этих исходов не доказывает (P/03.2-06, 07 и P/03.2-10).
