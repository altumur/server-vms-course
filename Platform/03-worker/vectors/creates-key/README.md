# Векторы: id строки заказа (`worker.creates[].key`)

Владелец — глава P/03.6 ([нормы](../../spec/03.6-worker.norms.md) Н1.6 `id`, `key`; ADR-0091 п. 1). Участник —
`<s>worker` заказчика (библиотека воркера). Запись значений по типам — [P/06.1](../../../06-console/spec/06.1-console.norms.md)
Н1.2 `values_by_type` (векторы [`values-by-type`](../../../common/vectors/values-by-type/README.md)). Байты пишет «Спецификация».

## `cases.tsv`

UTF-8, LF, поля через TAB; строки с `#` и пустые пропускаются; первая непропущенная — заголовок `case<TAB>input<TAB>expect<TAB>note`.

| Поле | Значение |
|---|---|
| `case` | имя строки |
| `input` | JSON-объект: `customer` — имя подсистемы-заказчика; `key` — шаблон `worker.creates[].key`; `fields` — поле → `{type, value}`: тип поля адресата (`string`, `url`, `int`, `float`, `bool`) и значение JSON, как его даёт логика заказчика |
| `expect` | id строки заказа — байт в байт |
| `note` | правило |

## Прогон

Сторона строит id своим кодом библиотеки, без хранилища: каждое `{поле}` шаблона — запись значения по `values_by_type`
(P/06.1 Н1.2; `float` — правило выбора Н1.2), затем каждый байт UTF-8 вне `A–Z a–z 0–9 _ . ~` — `%XX` с hex-цифрами
верхним регистром; между подстановками — `-` шаблона; впереди — `<customer>-`. Результат сравнивается с `expect`.
Пары строк с одним `pair` в `note` проверяют, что разные значения дают разные id.

## Команда стенда

`creates-key` — ключ `stand` профиля `03-worker` (раздел «Раскладка по процессам» [общего README приёмки](../../../common/acceptance/README.md)):
шаблон с `{input}` — путь файла, в который раннер пишет ячейку `input` строки байт в байт; stdout — UTF-8 байты id ровно
как `expect`, без перевода строки в конце и без JSON-обёртки; код 0. Вход не по форме этого README — код 2 (`@exit 2`).
Иной код или лишние байты — FAIL строки.
