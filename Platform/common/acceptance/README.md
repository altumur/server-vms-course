## Stand — common to the acceptance of the lessons of the module «Platform», M10 and M11

The acceptance runner of any lesson of M10 starts an implementation only through the interface that the implementation names
in its description (the norms of P/01.1, «Implementation decides» item 10); the runner does not know its internal API.

### Dictionary of directives and doors

One definition per module. A lesson README references this dictionary and writes only its own: the preparation, the roles and
the special comparison rules. The column «Lesson» is the lesson that introduced the directive: a number — the former lesson M10/N,
`P/NN` — a lesson of the module, `M11/N` — a lesson of M11, `-` — a form without a lesson; a lesson introducing a new one
adds a row here. A directive or a door that only one lesson uses is defined in the acceptance README of that lesson; its row here names the lesson and links the definition.

**A row of `scenarios.tsv`** (judge-only: the scenario tables of the lessons are not in M) — exactly the four cells `scenario`, `step`, `request`, `expect` separated by tabs. A cell contains neither a TAB nor a LF and has no escaping; a table with a `# cell-json:` declaration wraps the named cells by the [source-cell form](../contracts/source-cells.md), decoded once. Empty lines, lines of whitespace and lines beginning with `#` are notes and are skipped; a line whose first cell is exactly `scenario` is the header and is skipped too, so a table may also write its header as a `#` note. `expect` is empty only on an `ASSERT` step (which may also write `ok`). The steps of a scenario are numbered from 1 consecutively (1). A row outside this form or outside the forms of this dictionary is a data error of the table, found before the stand starts, not an outcome of the implementation.

**Doors** — the prefix of `request`. Without a prefix the request goes to the door of the lesson: the store in P/01 (chapters 1.1, 1.2) and P/02.5, the console in the chapters P/06 6.1, 6.3, 6.5, 6.6.

Related rules: [P/AC-R006](spec/acceptance.norms.md#n13-target-registry) and [P/AC-R020, P/AC-R024](spec/acceptance.norms.md); argument-bearing doors are defined by the [domain stand](domain-stand.md#domain-stand) and the [pass stand](pass/README.md). Store-specific addresses: [role-header substitution](../../01-store/acceptance/2/README.md#checks-outside-the-scenario-file) (P/01.2-R017), [list name order](../../01-store/acceptance/1/README.md#scenariostsv) (P/01.1-R065), [closed TLS outcomes](tls/README.md#outcome-of-a-probe--the-closed-form) (P/01.3-R059), and [full response contracts](#full-form-by-door) (P/01.3-R211).

| Form | Meaning | Lesson |

| `<code> <JSON>` | by the mode of the column `body` of the routing row of the target ([`forms/targets.routing.tsv`](forms/targets.routing.tsv); judge-only: the routing of the judge); a lesson or a chapter name sets no mode. `whole` — JSON whole (the order of the object fields does not matter): a field that the expectation does not name is a mismatch, except a field that the column `free` of the routing row admits (judge-only: the routing of the judge; the closed words `error` and `size`, each admitted only in the root object of the body, are defined in the notes of the column); a lesson or a chapter README admits no field; the markers of a `whole` expectation are only `$name` (a string) and `!contains text`: `@any`, `@absent`, `@not(…)`, `@time` and `~text` in an expectation of a `whole` target are a data error of the row, the class `data`. `subset` — a **subset**: the named fields are present and equal, the others are admissible; `{}` in an expectation at any level is exactly an empty object; any object is `@any`; no field is `@absent`; an array whose order the norm does not set (the list is here: `configured` of the answer `GET /<rows>`, P/06.1 N2) — without order: the lengths are equal and there is a one-to-one matching under which each element of the expectation matches its actual one by subset; the other arrays — by length, order and elements; JSON types are exact: in both modes, `whole` included, a JSON number is compared by value (`50` = `50.0`, `1e2` = `100`), a string, `true`/`false` and `null` are not equal to a number | 1, 3 |

| `@spoil($name)` in `request` | the bound string with a character changed in the middle of its last segment after «.» (for a string without «.» — in the middle of the string): the position ⌊n/2⌋ of a segment of length n, `A` → `B`, any other character → `A`; the form (length, base64url alphabet, canonicity) is the same — in a signature a character with full 6 bits is changed, not the last one (in a 64-byte signature it carries 2 bits, and the replacement would give a non-canonical tail — `not_a_token` instead of `bad_signature`); the signature of the token or the document no longer verifies — this is how a bound token is forged (`$ta`, `$tok`) | M11 |
| `@any` / `@absent` | the field is present with any value / there is no field | 3 |
