# Стенд приёмки модуля «Платформа», М10 и М11

## Стенд — общий для приёмки уроков модуля «Платформа», М10 и М11

Раннер приёмки любого урока М10 запускает реализацию только через интерфейс, который реализация называет
в описании (нормы P/01.1, «Решает реализация» п. 10); её внутреннего API раннер не знает.

- **Команда запуска** — шаблон с подстановками: `{data}` — новый пустой каталог данных экземпляра; `{socket}` —
  путь сокета двери хранилища (P/01.1); `{port}` — порт HTTP консоли на петле (уроки 3, 4, 9, 10); `{spec}` — каталог
  спек стенда для процессов, которым он нужен (`SPEC_DIR`, P/02.3); команда хранилища его не получает и спек не кладёт; `{body_limit}` и `{row_ceiling}` — предел тела и потолок строки (Н5 P/01.1);
  `{rights}` — путь файла прав, который раннер кладёт до запуска хранилища (P/01.2 Н1.2): в P/01.1 — файл ниже
  («Сокеты ролей»), в главах P/01.2 и P/01.3 — готовый вход [`01-store/acceptance/2/inputs/rights.json`](../../01-store/acceptance/2/inputs/rights.json), в уроках 4–11 — вывод прав из спек стенда командой вывода прав ниже (`{specs}` — каталог спек
  стенда, `{deployment}` = `dep`); команда хранилища получает `{rights}`, а не `{spec}` (журнал cammeta-python, урок 11
  № 29). Реализация называет, какие подстановки нужны каждому её процессу.
- **Команда установки спеки** `spec-put` (P/02.3 Н3 «Смена спеки») — шаблон с `{socket}` и `{file}`: кладёт одну спеку
  через `admin.sock` хранилища (`{socket}`); код 0 — положена, иной — отказ. Раннер ставит ею спеки стенда по одной
  в порядке «Спеки» ниже, после готовности хранилища и до первого `@start` (пилот хранилища, А6).
- **Команда вывода прав** (P/02.5 Н2) — шаблон с `{specs}` (каталог спек), `{deployment}` и `{file}`: пишет файл прав по
  P/02.5 Н1.4; код 0 — файл записан, иной — отказ генерации. Реализация называет её в описании (P/02.5 «Решает
  реализация» п. 1). Варианты приёмки P/02.5 (`5/variants/`) зовут её с `{deployment}` = `dep` (сверка python и go
  М10/6–11).
- **Команда кольца** — шаблон `ring {file}`: создаёт кольцо ключей урока 7 Н1.2 (`w2cctl secrets new` реализации) в файле
  `{file}`; раннер зовёт её до первого процесса с `{file}` = `{data}/etc/secrets/platform.key` (решение «Архитектора»,
  второй пилот); код 0 — кольцо создано.
- **Команды копии** (P/01.3 Н1.3 `copy`, `admin_ops`): `backup` — шаблон с `{socket}` и `{file}`: копия хранилища через
  `admin.sock` в файл, код 0 — копия снята; `import` — шаблон с `{data}`, `{file}` и `{index_base}`: перенос копии в
  свежий каталог остановленного хранилища (P/01.3 Н1.3 `box`), код 0 — перенесено, иной — отказ. Реализация называет
  обе (P/01.3 «Решает реализация» п. 4, 11; пилот хранилища).
- **Команда загрузки одного файла спеки** (P/02.1) — шаблон с `{file}`; код выхода 0 — спека, иной — отказ, текст
  отказа называет файл (нормы P/02.1, «Решает реализация» п. 3).
- **Процессы нескольких ролей** (урок 5 и далее): реализация называет команду запуска каждой роли — хранилище,
  консоль, контроллер, воркер, позже ресурс; команда воркера получает имя подстановкой `{name}` (аргумент), окружение —
  `BOX_ID` (постоянная коробка стенда) и `SERVER_NAME` (P/02.4 Н1.2); из окружения имя воркер берёт только по `slot.name_env` своей спеки
  (P/02.1 Н1.2а), и раннер ставит эту переменную, если спека её объявила (`testsub2` — `TALLY_NAME`; у `testsub` её нет). До урока 6 раннер читает хранилище ролью с полными правами на префикс подсистемы.
- **Ресурс** (урок 8): команда запуска ресурса сервера с подстановкой `{rport}` — порт его двери; раннер ждёт порт
  и строку `platform/doors/<сервер>` до первого шага.
- **Сокеты ролей** (урок 6): и на коробке хранилище открывает сокет на роль (`<роль>.sock`, `admin.sock`) по файлу
  прав; раннер звонит сокетом роли сценария. `{socket}` — путь `admin.sock`; сокеты ролей лежат рядом, в том же каталоге, плоско (P/01.3 Н1.3 `sockets`).
  `{socket}` — дверь с полными правами (подготовка). Урок 1 прогоняет сценарии ролью `acc` — права read и write только на
  `acc/*`, сокет `acc.sock` рядом с `{socket}`. Раннер кладёт в `{rights}` ровно этот файл (форма — P/01.2 Н1.2):
  `{"roles": {"acc": {"group": "acc", "read": ["acc/*"], "write": ["acc/*"], "delete": ["acc/*"]}}}`.
  Удаление — отдельное действие (P/01.2 Н1.3 `allowed`), в файле оно названо явно.
- **Один каталог данных** `{data}` на экземпляр — это `PLATFORM_DIR` (P/02.4 Н1.2 «Канал настройки и раскладка»;
  второй пилот, Н-4). Стенд переводит подстановки в окружение P/02.4 Н1.2: `PLATFORM_DIR={data}`,
  `PLATFORM_STORE=configstore://<сокет роли>`, `CONSOLE_PORT={port}`, `RESOURCE_PORT={rport}`, `BOX_ID`, `SERVER_NAME`,
  `SECRETS_KEY={data}/etc/secrets/platform.key` — кольцо по раскладке P/02.4 Н1.1, его создаёт раннер командой кольца до первого процесса; имя воркера — аргументом `{name}`. Раскладка — по P/02.4 Н1.2: хранилище
  `{data}/configstore`, объекты `{data}/objects`, события `{data}/events`, замки присутствия `{data}/events/.workers`.
  Корень событий сервера выводится однозначно — `{data}/events` его `PLATFORM_DIR` (стенд не задаёт `RESOURCE_ROOT` и
  `EVENTS`), поэтому отдельного ключа корня событий у «Стенда» нет.
  Файл настроек сервера — `W2C_ENV={data}/etc/w2c/w2c.env` (P/02.4 Н1.2: каталог `roles/` — рядом с `w2c.env`,
  другого места нет), файлы ролей — `{data}/etc/w2c/roles/<роль>.env`; у сервера `on <сервер>` — тот же путь в его
  `PLATFORM_DIR` `{data}/servers/<сервер>` (выбор владельца раннеров, cammeta-acceptance e3ec5c3).
- **Спеки** ставятся командой `spec-put` в порядке зависимостей: `testsub`, затем `testsub2` (она ссылается на `testsub`: `about`,
  `near`, `worker.requests`); загрузка каталога (P/02.1 Н3) видит обе.
- **Корень консоли** (`CONSOLE_ROOT`) называет README урока: урок 7 — `testsub2` (короткие пути `/tallies`),
  остальные — `testsub`, вторая подсистема смонтирована под `/testsub2`.
- **Команда печати отчёта прохода** контроллера `<sub>/controller/pass` (урок 4) — шаблон с `{data}` и `{sub}`;
  печатает текущий объект отчёта или ничего, если его нет; по ней раннер ждёт смены отчёта (нормы урока 4,
  «Решает реализация» п. 10).
- **Команды векторов платформы** `order`, `shrink-victim`, `workers-script` (стадия A, A6; ADR-0084) — шаблоны с
  `{input}` — путь файла входа; вывод — JSON в stdout; код 0 — вычислено, 2 — вход не по форме. Пакеты —
  `Platform/04-controller/vectors/order/`, `…/shrink-victim/` (урок 4 Н3 «нехватка(), заказать()», «сократить()»),
  `Platform/02-installer/vectors/workers-script/` (P/02.4 Н1.5): раннер читает `cases.tsv` пакета (UTF-8, TAB, строки
  с `#` и пустые пропускаются, первая непропущенная — заголовок), на каждую строку пишет ячейку `input` байт в байт во
  временный файл, зовёт команду пакета с `{input}` и сравнивает stdout с ячейкой `expect` как JSON по значению,
  целиком (порядок ключей объекта не важен; массив — по длине, порядку и элементам); код ≠ 0 или не JSON — FAIL
  строки; итог пакета — строки по `case`. Реализация называет шаблоны в описании, как прочие команды «Стенда».
- **Долговечность.** Команда хранилища МОЖЕТ нести флаг реализации, выключающий барьеры долговечности ради скорости
  стенда; реализация называет его в описании (P/01.1 «Решает реализация» п. 3). Переменной окружения для этого нет
  (P/01.3 Н1.3 `durability`).
- **Экземпляр** — на сценарий (P/01.1) или на полный прогон, как велит README урока; раннер ждёт сокет или порт,
  затем сверяет параметры поведением по Н5 P/01.1. Готовая дверь вместо запуска — прогон не изолирован и не зелёный.
- **Проверки README сверх TSV** в каждом уроке — сценарий или пункт «проверяется чтением» с предметом: управляемых
  часов, двух консолей на одном хранилище и учений урока 11 на настоящем кластере (`@manual`, М10/11 Н5) этот интерфейс не даёт.

### Словарь директив и дверей

Одно определение на модуль. README урока ссылается на этот словарь и пишет только своё: подготовку, роли и
особые правила сравнения. В скобках — урок, который ввёл директиву; урок, вводящий новую, добавляет строку сюда.

**Строка `scenarios.tsv`** — `scenario`, `step`, `request`, `expect` через табуляцию. Строки с `#` — заметки, строка
заголовка пропускается. Шаги сценария нумеруются с 1 подряд (1).

**Двери** — префикс `request`. Без префикса запрос идёт в дверь урока: хранилище в уроках 1 и 6, консоль в 3, 4, 9.

| Дверь | Куда | Урок |
|---|---|---|
| `store` | дверь хранилища P/01.1 сокетом роли сценария; роль называет README урока, `@as` её меняет | 5 |
| `admin` | дверь хранилища через `admin.sock` | 11 |
| `restored` | дверь через `admin.sock` экземпляра хранилища, который поднял последний `@import store` сценария | 11 (пилот хранилища) |
| `console` | консоль на `{port}`, корневая подсистема `testsub` | 5 |
| `console2` | та же консоль, префикс `/testsub2` смонтированной подсистемы | 10 |
| `resource` | дверь ресурса сервера на `{rport}` с допустимой личностью | 8 |

**Запрос.**

| Форма | Смысл | Урок |
|---|---|---|
| `<МЕТОД> <путь с query> [<тело>]` | путь и query уходят байт в байт, без перекодирования; тело — байты после подстановок, неверный JSON допустим | 1 |
| `@big(N)` | подстановка в любой части запроса: строка из N байт `x`; внутри JSON-строки — до сериализации | 1 |
| `@raw <текст>` | тело — текст байтами UTF-8, `application/octet-stream`; `Content-Length` — по байтам | 10 |
| `@key(<слово>)` / `@nokey` | `Idempotency-Key` у `POST` — по умолчанию `<запуск>-<scenario>-<step>`, свежий на запуск; `@key(<слово>)` ставит `<запуск>-<scenario>-<слово>`, то есть `@key(N)` повторяет точные байты ключа шага N своего сценария; `@nokey` — без заголовка | 3 |
| `@as <роль>` | шаг и следующие `store`-шаги сценария — от этой роли, сокетом `<роль>.sock` (раздел «Стенд» выше) | 6 |
| `@header <Имя>: <значение>` перед методом | добавить заголовок к одному запросу; `@header Idempotency-Key: …` заменяет ключ раннера по умолчанию (`@key`) | 6; ключ — 3 |
| `ASSERT $a != $b [$c …]` | названные значения попарно различны; HTTP не отправляется | 1 |
| `ASSERT <терм> <оп> <терм>` | сравнение связанных значений; HTTP не отправляется. `<терм>` — `$имя`, число JSON или разность `$a - $b`; `<оп>` — `==`, `!=`, `<`, `<=`, `>`, `>=`. Порядок и разность — только у чисел; у строк — `==` и `!=`; разные типы — несовпадение (`ASSERT $t2 - $t1 < 2`, `ASSERT $a <= $b`) | М11 (мутационная проверка 2026-10-18) |

**Директивы стенда** — не HTTP; ответ `ok` или отказ раннера.

| Форма | Смысл | Урок |
|---|---|---|
| `@start controller [<sub>] [shrink_after=<с>]` / `@start worker [<sub>] <имя> [on <сервер>]` / `@start resource [on <сервер>]` | запустить процесс роли командой «Стенда»; `shrink_after=<с>` — контроллеру окружение `W2C_SHRINK_AFTER=<с>` (только стенд, урок 4 Н1.4 `SHRINK_AFTER`; ADR-0084); `<sub>` — подсистема каталога стенда, без него — `testsub`; воркер получает имя подстановкой `{name}` в команде «Стенда» и, если спека объявила `slot.name_env`, ещё в этой переменной (`testsub2` — `TALLY_NAME`), та же коробка, `server=srv-a`; `on <сервер>` (ADR-0084) — процесс сервера `<сервер>`: `SERVER_NAME=<сервер>`, `BOX_ID` — `<коробка стенда>-<сервер>`; у сервера, отличного от `srv-a`, — свой `PLATFORM_DIR` `{data}/servers/<сервер>` (свой корень событий и замки присутствия), то же хранилище (`PLATFORM_STORE`) и то же кольцо (`SECRETS_KEY`), у ресурса — свой `{rport}`; ресурсу каждого сервера раннер кладёт файл роли `roles/<sub>worker.env` каждой спеки с `grows: true` (`HOST_MEMORY_MB=4096`, `WORKER_MEMORY_MB=256`, каталог `roles/` — рядом с `W2C_ENV` его `PLATFORM_DIR`: `<PLATFORM_DIR>/etc/w2c/roles/`, P/02.4 Н1.2), чтобы ресурс писал `room.<sub>` (М10/8); повтор того же имени — вторая копия; готовность проверяют следующие `@until`; команды контроллера и воркера «Стенда» получают подстановку `{sub}` (без `<sub>` — `testsub`), команда ресурса — `{server}` (`srv-a`; у стенда М11 — `srv-<кластер>`) | 5; ресурс и `<sub>` — 8; `on <сервер>` — ADR-0084 |
| `@grow <сервер>…` | до конца сценария раннер раз в 5 с читает `/<sub>/metrics` консоли каждой спеки с `grows: true` и для названных серверов приводит число воркеров `<prefix>-<сервер>-<n>`, `n` ≥ 2, к ряду `<sub>_workers_wanted{server="<сервер>"}` минус 1 (базовый `-1` запускает сценарий сам): недостаёт — `@start worker <sub> <prefix>-<сервер>-<n> on <сервер>` с наименьшим свободным `n`; лишний — `@sigterm` с наибольшим `n` (номер — целым); ряда нет, не читается или консоль молчит — ничего; серверы не названы — заказ на них не исполняется («не поднял»); исполняет скрипт сервера P/02.4 Н1.5 без polkit (его проверяет тест юнита и политики) | ADR-0084 |
| `@sigterm <имя>[#n]` / `@sigkill <имя>[#n]` | остановить процесс; `<имя>` — имя воркера или роль процесса `controller` (контроллер `testsub`), `resource`; по умолчанию последнюю копию с этим именем, `#1` — первую | 5; `#n` у `@sigterm` — М11/12 |
| `@put object <ключ> <файл>` | положить объект хранилища объектов стенда с байтами файла (путь — от каталога приёмки урока) командой записи объекта реализации (урок 11 «Решает реализация» п. 10), мимо писателя и его проверок | М11/11 (мутационная проверка) |
| `@spoil object <ключ>` | испортить объект хранилища объектов стенда командой порчи реализации (урок 11 «Решает реализация» п. 10): после неё чтение объекта — нечитаемо (урок 8 Н1.1); процесс-писатель объекта до этого остановлен | 11 (сверка python и go) |
| `@restart store` | SIGTERM хранилищу, дождаться выхода, запустить той же командой с тем же `{data}`, ждать сокет | 11 |
| `@restart console` | SIGTERM консоли, дождаться выхода, запустить той же командой «Стенда» с тем же `{data}` и `{port}`, ждать порт; не дождался порта за 20 с — отказ раннера | 7 (сверка python и go М10/6–11, S8) |
| `@append event <дерево>/<unit>/e<эпоха> <текст>` | дописать текст строкой (байты UTF-8 и LF) в бакет текущего окна `<корень событий srv-a>/<дерево>/<unit>/e<эпоха>/<start>Z.events.jsonl` (урок 8 Н3 «записать событие», шаг 4; корень — `{data}/events`, «Стенд») мимо писателя; нет файла — создать; `{now}` в тексте — стенные секунды раннера в момент записи (время по Н0 P/01.1); компоненты пути — по кодированию имён урока 8 Н1.1 | 8 (сверка python и go М10/6–11, E19) |
| `@backup store <имя>` | снять копию хранилища стенда командой `backup` «Стенда» в файл раннера `<имя>` (живёт до конца сценария); `ok` — код 0 и файл по форме P/01.3 Н1.3 `copy` (заголовок, строки Row, ключи по возрастанию байтов); иначе отказ раннера | 11 (пилот хранилища) |
| `@backup store <имя> in-data` | команда `backup` «Стенда» с `{file}` = `{data}/configstore/<имя>` — внутри каталога данных хранилища стенда (`-dir`); ожидание `refused` — код ≠ 0 и файла `{data}/configstore/<имя>` нет | 11 (сверка python и go М10/6–11, B8) |
| `@import store <файл>` / `@import store backup <имя>` | вход — файл от каталога приёмки урока или копия `@backup store <имя>` этого сценария; раннер берёт новый пустой `{data}`, зовёт команду `import` «Стенда» с `{index_base}` — `index` заголовка входа (заголовок не читается — `0`), затем запускает на этом `{data}` второй экземпляр хранилища командой «Стенда» со своим `{socket}` и ждёт сокет — его дверь `restored`. Ожидание `ok` — код `import` 0; `refused` — код ≠ 0 (что каталог остался без строк, видят следующие шаги `restored`). Хранилище стенда не трогается | 11 (пилот хранилища) |
| `@foreign store nolabel` / `@foreign store otherlabel` | второй экземпляр хранилища той же командой с новым каталогом `{data}` и своим `{socket}`; раннер до запуска кладёт в каталог хранилища `{data}/configstore`: `nolabel` — файл `rows` с байтами `x` и без `FORMAT`; `otherlabel` — `FORMAT` с байтами `{"format":"w2c-acceptance-foreign","version":1,"impl":"runner"}`. `ok` — процесс вышел с кодом 2 не позже 10 с и дерево каталога (имена, байты) то же, что до запуска; иначе отказ раннера. Хранилище стенда не трогается (P/01.3 Н1.3 `format`) | 11 (пилот хранилища) |
| `@sleep <секунды>` | подождать | 5 |
| `@until <секунды> <request>` | повторять запрос до совпадения с `expect`, не дольше срока; срок вышел — FAIL с последним ответом; повторяется чтение, не мутация | 5 |
| `@manual <текст>` | шаг учения: раннер печатает текст, не исполняет; в итог не входит (не зелёный и не красный), `expect` — `manual` | 11 |

Дополнительная проверка полного ключа (R29-01, P/01.1-16,22): на отдельном экземпляре
с правами на acc/ проверить ключи этого префикса полной длиной 200, 201, 213, 1024 и 1025
UTF-8-байт, включая кириллицу и четырёхбайтные символы. Первые четыре проходят правило двери,
1025 даёт 400 badkey без записи; тот же набор проверить в непустом guard.key. У существующего
стража использовать его фактическую версию, у отсутствующего — index="", чтобы не попасть
в отказ сравнения версии. Для файловой реализации отдельно проверить её объявленный предел:
допустим более ранний badkey, но порог 200 сам по себе не является нормой платформы.
Это отдельная оснастка сверх сценарного TSV; тестировать полное UTF-8-представление, не число символов.

Сценарии прогоняются через дверь хранилища (урок, Н2) любой реализации; путь к двери (unix-сокет роли или стенд с той же дверью) — параметр стенда. Роль прогона — `acc` («Стенд» выше): полные права на префикс `acc/` и ни на что больше. Для **каждого сценария, в том числе при повторном прогоне**, раннер создаёт новый изолированный экземпляр
хранилища с пустыми прикладными строками и пустой памятью идентификаторов записи `id`. В частности,
пусты оба тестовых префикса — `acc/` и `other/`. Очистка строк `acc/<сценарий>/` в прежнем экземпляре
недостаточна: она не снимает память повторов. Версии не обязаны начинаться с заданного числа.

Подготовку экземпляра, его каталога данных и прав делает раннер до начала сценария; проверяемые запросы
идут только от указанной роли с правами на `acc/`. Сценарий 21 не получает дополнительных прав на `other/`: до его первого шага раннер в подготовке (не проверяемый запрос)
записывает строку `other/21-rights/c9` `{n: "1"}` через `admin.sock` экземпляра (`{socket}` «Стенда»); шаг 6 видит её имя
и версию без значения, хотя права чтения на `other/` у роли нет (Н3 «перечислить»). В сц. 24 шаг 7 — query у `POST` не
читается, шаг 8 — тело у `GET` не читается; в сц. 26 шаги 9–10 — `Infinity` и BOM в теле (Н2.1).
Параллельные сценарии используют разные экземпляры и не разделяют ни строки, ни память `id`.

Параметры каждого экземпляра (Н5 урока): потолок строки **524288 байт**, предел чтения HTTP-тела
**1048576 байт**. Раннер сверяет оба значения до сценариев поведением на пробном экземпляре, полученном тем же
способом: тело ровно 1048576 байт доходит до разбора JSON (ответ не `413`), 1048577 байт — `413 toolarge`
с `limit` 1048576; вес `items` ровно 524288 байт записывается, 524289 — `413 toolarge` с `limit` 524288.
Изолированный экземпляр раннер получает способом, который реализация назвала в описании (нормы,
«Решает реализация» п. 10). Если параметры нельзя обеспечить или сверка не сошлась, прогон не выполнен;
нельзя подменять ожидаемые байты под имеющиеся настройки.

Сценарий 15 после раскрытия `@big` посылает тела 524348 и 524344 байта: оба меньше предела тела,
но вес `items` равен 524292 и 524288 байтам. Так проверяется именно потолок строки.
Сценарий 22 посылает тело 4194364 байта, больше 1048576: отказ возникает до разбора JSON и проверки веса.
Раннер передаёт байты тела из `request` после подстановок, без повторной сериализации или иных добавлений.
