# Стенд передачи второго вида

Сценарии `door.pass` второго вида: билет, обратный вызов, поток, лист роли (ADR-0094 B1, Confirmation; нормы — [договор сторожевой и передачи](../../contracts/gate-and-pass.md) «Передача второго вида», [P/06.3](../../../06-console/spec/06.3-console.norms.md) Н1.9, [P/06.5](../../../06-console/spec/06.5-console.norms.md) Н1.8, [договор сертификата роли](../../contracts/role-certificate.md) «Лист обратного вызова», [P/02.5](../../../02-installer/spec/02.5-installer.norms.md) Н1.5). Что проверяется без живого воркера, идёт в главах: сц. 46 [приёмки 6.1](../../../06-console/acceptance/1/README.md), сц. 32 [приёмки 6.5](../../../06-console/acceptance/5/README.md).

8 сценариев / 97 шагов. Воркера играет раннер: сценарию нужно держать запрос открытым, видеть, что дошло до воркера, и звать консоль обратно с билетом и листом, а тестовый воркер реализации этого не даёт и проверял бы сам себя. Манифест — [`probe-p`](probe-p.subsystem.yaml), комплекты сц. 08 — [`stand.json`](stand.json) в форме [TLS-стенда](../tls/README.md), с одним новым полем: `server` листа в `negative` — лист с иным именем сервера.

| № | Сценарий | Нормы |
|---|---|---|
| 01 | билет живёт с запросом: удостоверения не уходят, дверь перечня работает, запись по билету; вне перечня, запись `/session`, чужая подсистема, без билета, по TCP, с сокета чужой роли — 401; ответ отдан — билет мёртв; ряд и журнал `pass.called` | `ticket`, `journal`, `counter`, P/06.3 Н1.9 |
| 02 | заголовки к воркеру и клиенту; 412 `problem+json`, 204, тип вне перечня — 502; `nosniff`, `sandbox`; предел `wait` — 504 | `to_worker`, `to_client`, `types`, `timeout` |
| 03 | свежий `may` — 403; два токена, отозван один: билет первого 401, второго работает; выключенный человек — 401 | `ticket` шаг 5 |
| 04 | консоль открыта: билет есть, обратного вызова вид сессии не даёт | `ticket` шаг 3 |
| 05 | поток: чтения и `/changes`, запись — 401, `Last-Event-ID`, ответ по мере прихода; поток закрывается с запросом и при отзыве токена | `stream`, `close`, `ticket` шаг 4 |
| 06 | таблица `service: true` по билету: человек без прав читает и пишет своё, строка в пакете; строка вне перечня — 401 всего пакета; без билета дверь закрыта | `service`, P/06.3 Н1.9 «Строки пакета», P/06.1 Н1.6 |
| 07 | общая полоса занята передачами, их обратные вызовы проходят | P/06.5 Н2, договор `order` шаг 1 |
| 08 | лист: своя роль и сервер — да; чужая роль, другой сервер, без листа — 401; серверный лист не роли адресата — передачи нет, тело не ушло | `callback_transport`, `transport`, «Лист обратного вызова» |

Чтением, с причиной: break-glass и отладочная личность — тот же шаг 3 порядка `ticket`, что сц. 04; запрос по куке стенд не ведёт. Маршрут двери подсистемы ([P/06.3](../../../06-console/spec/06.3-console.norms.md) Н1.9) — подставной воркер держателем не служит. `X-W2C-Loopback` без петли и `PASS_STREAMS_MAX` — все клиенты стенда на петле, 256 потоков TSV не откроет. `PASS_TICKET_CHECK` — только верхней границей шага 13 сц. 05. Дверь воркера с листом `console` и клиент SDK — P/03.4-15, тест реализации: подставной воркер их не проверяет.

## Исполнимость

Все сценарии **пока не исполнимы**: у раннера нет директив `@pass-worker`, `@pass-open`, `@pass-answer`, `@pass-result`, `@pass-chunk`, `@pass-abort`, `@pass-closed`, `@pass-fill`, `@pass-seen`, `@pass-call` и двери `socket` ([словарь директив](../README.md#словарь-директив-и-дверей)), поля `server` в `negative` и установки третьего манифеста на стенде домена, и сухого прогона реализацией не было. Правило то же, что у [системной приёмки](../system/README.md): в выпуск раннера сценарий идёт только после прогона против реализации, каждый красный шаг разбирается вопросом «норма или данные», а новые сценарии входят в пин линий только выпуском раннера.
