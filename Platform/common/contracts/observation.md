# Договор наблюдения: свежесть, состояние ресурса, чтение решения

Общий договор модуля «Платформа» (ADR-0083 доп. (5): контракт, который читают несколько процессов, лежит в
`Platform/common/`; решение «Архитектора» по разбору ревью стадии A 6–7, № 1, № 2). Читают: контроллер — пул, судья
слота, вывод сервера ([P/04](../../04-controller/spec/04-controller.norms.md) Н1.4, Н3), консоль — выдачи наблюдений
(глава [P/06.5](../../06-console/spec/06.5-console.norms.md): `/servers`, `/resources`, `/where`, `/unplaceable`,
`/metrics`), двери управления (глава [P/06.6](../../06-console/spec/06.6-console.norms.md): вывод сервера, `/schema`,
подъём схемы, дренаж, прогнозы меток) и живые ресурсы слияния `/events` (глава
[P/06.4](../../06-console/spec/06.4-console.norms.md)). Перенесено из P/04 Н1.4 (`resource_state`) и Н1.5 (сторона
читателя решения) без изменения поведения, кроме одного: граница свежести — одно отношение `≤` у всех наблюдателей
(«Свежесть» ниже; разбор ревью стадии A 6–7, № 1). Что наблюдатель делает с состоянием (судьба слота, пул, отказ вывода,
`live` процесса в `/schema`, `state` воркера в выдаче) — в нормах читающих уроков; форма наблюдаемых строк и объектов — у
их владельцев ([каталог](../data/catalog.tsv)).

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md).

## Наблюдение версии

```yaml
observer:  процесс-читатель со своей памятью наблюдения и своими монотонными часами; память не общая между
           наблюдателями и после перезапуска начинается заново (ADR-0049)
changed:   «менялся» — смена версии строки или объекта на глазах наблюдателя (индекс строки P/01.1 Н1, версия объекта
           P/05 Н1.1), а не значение поля времени в нём (`ts`, `at`, `until`): часы писателя свежесть не доказывают
age:       возраст наблюдаемой версии — время по часам наблюдателя с момента, когда он впервые успешно прочёл текущую
           версию ([P/03.2 Н1.4](../../03-worker/spec/03.2-worker.norms.md) «возраст наблюдаемой версии»); первый
           взгляд, новая версия или изменённые байты — возраст 0; повторное чтение того же состояния и неответ хранилища
           возраст не обнуляют
first:     первое наблюдение — свежее: впервые увиденное «только что изменилось» (возраст 0); поэтому новый наблюдатель
           первые LOST_AFTER никого не считает молчащим (P/04 Н1.4а `fresh_controller`)
```

## Свежесть: `LOST_AFTER`

```yaml
LOST_AFTER:  45    # с
fresh:       источник свеж (слышен) — его версия менялась в последние LOST_AFTER: возраст наблюдаемой версии ≤ LOST_AFTER;
             возраст > LOST_AFTER — не свеж (молчит, устарел). Одно отношение у всех наблюдателей и выдач
             (разбор ревью стадии A 6–7, № 1)
```

Отношение одно для всех мест, где норма говорит «менялся в последние LOST_AFTER», «слышен», «живой» по пульсу, «свежий»
или «устаревший» пульс: `resource_state` ниже; живой воркер в выдаче консоли (`worker_state` строки `GET /{rows}`,
`WorkerRow.state` `/servers`); живые процессы `/schema` и подъёма схемы, «слышны» вывода сервера, свежесть пульса
дренажа (глава 6.6); ряд `w2c_resources_live` (глава 6.5); живые ресурсы слияния `/events` (глава 6.4). Прежние записи
«`< 45 с`», «`< LOST_AFTER`» у дверей консоли читаются по этому договору; где выдача давала `<`, это правка поведения на
одном шаге — возраст ровно LOST_AFTER: свеж (после сверки свидетелей).

## Состояние ресурса (`resource_state`)

Ресурс сервера — одно определение для всех наблюдателей (контроллер, консоль), по их монотонным часам; «менялся» — смена
версии на глазах наблюдателя (раздел «Наблюдение версии»), первый взгляд — свежий; правила — по порядку, первое
совпавшее (сверка python и go 2026-10-18).

```yaml
resource_state:
  live:         пульс ресурса platform/resources/<s>/heartbeat читается и менялся в последние LOST_AFTER; нечитаемый
                пульс жизни не подтверждает, и его смена — тоже
  unreachable:  пульс не live (в том числе нечитаемый), строка двери platform/doors/<s> менялась в последние LOST_AFTER —
                ресурс есть, пульсов нет
  unknown:      наблюдатель не видел ни читаемого пульса, ни строки двери ни разу: нечитаемый пульс увиденным не
                считается (сверка python и go М10/6–11, C13)
  silent:       иначе; исключает и двигает только silent
```

Нечитаемый пульс — по форме его писателя ([P/05 Н1.4](../../05-resource/spec/05-resource.norms.md)); строку двери
наблюдатель судит по смене её версии, не по полям (семья `doors` P/05). Что значит каждое состояние для судьбы слота и
пула — [P/04 Н3](../../04-controller/spec/04-controller.norms.md) «судьба», «выбрать»; для выдачи `ServerRow.resource` —
глава 6.5; для отказа вывода сервера — глава 6.6.

## Чтение решения: intent → placement → intent

Эффективное размещение единицы читается по строкам контроллера `<sub>/controller/placement_intent` и `<sub>/placement/<id>`
(форма — [P/04](../../04-controller/spec/04-controller.norms.md) Н1.1, Н1.5; семьи `placement-intent`, `placement`).
Правило одно для всех читателей: контроллера, `/where`, `/unplaceable`, прогнозов меток, дренажа.

```
прочитать intent → нужные placement → снова intent; версия intent изменилась → повторить чтение;
только одинаковые версии intent дают результат
active intent и id в members → решают target/reason/at/spec_rev intent; отсутствие placement не отменяет target активного
  intent; иначе — worker/reason строки placement
обязательное чтение не подтверждено → результата нет (у дверей консоли — 503 unavailable); неподтверждённое чтение не
  означает idle
строка intent не по форме (state не active/idle; у active нет members, target, reason, at или они не по форме) —
  нечитаемая: читатели — 503 unavailable, не idle; контроллер — отказ с failures (P/04 Н1.5, Н4)
```

Одним HTTP-чтением не обещан атомарный снимок всей подсистемы: эффективное размещение и пульс держателя читаются
отдельно, ответ называет наблюдённого держателя. Idle сохраняется писателем, чтобы версия intent не возвращалась к версии
отсутствия между двумя чтениями (сторона писателя — P/04 Н1.5).

## Соответствие прежним урокам

Из P/04 Н1.4 (перенос урока 6, разбор ревью стадии A 6–7, № 2): блок `resource_state` (здесь «Состояние ресурса») и
смысл свежести `LOST_AFTER` (здесь «Свежесть»; константа и её роль в сроках судьи — P/04 Н1.4); из P/04 Н1.5 — правило
читателя решения (абзацы «Active intent — принятое общее решение…», «Нечитаемая строка turn/intent…» в части читателей);
из М10/9 Н3 «`/where/<id>`» — выбор target/reason при активном intent
(глава 6.5); из P/03.2 Н1.4 — определение возраста наблюдаемой версии (ссылкой). Части норм по `note`
[id-map](../id-map.tsv): P/04-04 (жизнь по изменению пульса, первый взгляд), P/04-10 (`resource_state`), P/04-01 (двойное
чтение intent), P/06.5-04 (`ServerRow.resource`, `WorkerRow.state`), P/06.5-05 (`/where`), P/06.6-02 (вывод сервера),
P/06.6-04 (живые процессы `/schema`). Векторов нет: состояние и свежесть — по истории наблюдения на часах наблюдателя,
шаги приёмки P/04, P/06.5, P/06.6 и чтение.
