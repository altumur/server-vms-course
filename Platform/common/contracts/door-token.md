# Договор токена двери: байты `door1`, claims в JCS, подпись Ed25519, ключи `door/keys`, проверка у держателя

Общий договор модуля «Платформа» (ADR-0083 доп. (5) и доп. (11): контракт, который пишет один процесс и читают другие,
лежит в `Platform/common/`; разбор ревью стадии B 3–5, В1). Владелец — урок [P/06](../../06-console/spec/06.5-console.norms.md)
(глава 6.5): консоль выдаёт токен в ответе `/where/<id>` и `/where/<table>/<place>` (P/06.5 Н3), держит подписанта
`door/signer` и пишет открытые ключи `door/keys`. Читают: держатель двери — воркер, который проверяет токен на своей двери
(глава [P/03.4](../../03-worker/spec/03.4-worker.norms.md) Н3 «токен двери у держателя», P/03.4-08); агент домена читает
`door/keys` ([каталог](../data/catalog.tsv)). Перенесено из P/06.5 Н3 «`/where/<id>`» (блок «Токен двери — байты»: `token`
и строка `door/keys`) и P/03.4 Н3 «токен двери у держателя» (строка `door/keys` о проверяющем и фраза «Гонок») без
изменения поведения; после переноса проверка изменена — правки поведения: решения «Архитектора» 2026-10-20 (ADR-0083
доп. (12): строгий base64url, закрытые состав и типы claims, сегмент `routes` по `name`, целый знак `expires`, единый
отказ `forbidden`) и разбор ревью стадии B 6–7 (№ 10 — целое `expires`, № 12 — строгая проверка Ed25519); реализации
сверяются по векторам `door-token` (разбор ревью стадии B 6–7, № 11). Когда и кому консоль выдаёт токен (по `view` на единицу, TTL 120 с, журнал `door.issued`, поле `door`
ответа), подписант `door/signer` и его конверт — в нормах владельца (P/06.5 Н3, семья
[`door-signer`](../../06-console/data/door-signer.form.yaml)); форма строки ключей — семья владельца
[`door-keys`](../../06-console/data/door-keys.form.yaml) с таблицей исходов рядом. JCS — RFC 8785 (ADR-0072; векторы
[`jcs`](../../01-store/vectors/jcs/README.md) урока P/01).

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md).

## Форма

Файлы, по которым работает договор (аудит раскладки, В-15–В-17; решение «Архитектора» 2026-10-25):

- подписант `door/signer` — семья `door-signer`: `Platform/06-console/data/door-signer.form.yaml`,
  `Platform/06-console/data/door-signer.outcomes.tsv`;
- строка ключей `door/keys` — семья `door-keys`: `Platform/06-console/data/door-keys.form.yaml`,
  `Platform/06-console/data/door-keys.outcomes.tsv`;
- пульс держателя (`instance` для `claims.holder`) — семья `heartbeats`: `Platform/03-worker/data/heartbeats.form.yaml`,
  `Platform/03-worker/data/heartbeats.outcomes.tsv`;

## Токен

Из P/06.5 Н3 «`/where/<id>`», «Токен двери — байты» (журнал cammeta-go, урок 9 № 3):

```yaml
token:      door1.<kid>.<claims>.<sig> — ровно четыре части через «.», ASCII
  kid:      имя ключа подписи, 1–32 знака [a-z0-9-]; по нему проверяющий берёт открытый ключ из door/keys
  claims:   base64url без «=» байтов JCS (RFC 8785) объекта {user, unit, holder, routes, expires}: user — доказанное имя
            ([договор сторожевой и передачи](gate-and-pass.md) «Сторожевая» identity), unit — "<sub>/<id>", holder — экземпляр держателя из его пульса (instance, P/03.4 Н1.1), routes — массив
            маршрутов door.routes манифеста с допуском token (элементы-имена и {name} без role и domain; маршруты с role или
            domain в токен не входят — их допуск — сертификат роли, класс mixed договора сертификата роли, или токен домена,
            P/03.4 Н1.7; ADR-0091 доп. (8) п. 3, доп. (14) п. 1), expires — целые стенные секунды выдачи + 120 (разбор ревью стадии B 6–7, № 10): floor(now) + 120, now — стенные часы
            выпускающего в секундах, дробь отбрасывается, не округляется (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7)
  sig:      base64url без «=» 64 байт подписи Ed25519 (RFC 8032) над байтами ASCII «door1.<kid>.<claims>»; проверка — строго
            по RFC 8032 §5.1.7: S вне 0 ≤ S < L, R или открытый ключ не раскодированы — отказ (разбор ревью стадии B 6–7,
            № 12; вектор sig_s_not_reduced); уравнение — без кофактора: [S]B = R + [k]A (как Go crypto/ed25519 и OpenSSL),
            не [8][S]B = [8]R + [8][k]A; A или R малого порядка ([8]P — нейтральная точка) — отказ, хотя уравнение
            выполняется (векторы key_small_order, sig_r_small_order) (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7)
```

Части `claims` и `sig` — строгий base64url без «=» (алфавит `A–Z a–z 0–9 - _`, без «=» и иных знаков; неиспользуемые хвостовые биты последнего знака — нули); часть не
по этой грамматике — отказ проверки (решение «Архитектора» 2026-10-20, векторы door-token). Ненулевой хвостовой бит — тоже отказ, хотя нестрогий
декодер дал бы те же байты (решение «Архитектора» 2026-10-20, векторы door-token). Выпускающий обязан писать claims байтами JCS;
проверяющий канон JCS не проверяет: подпись покрывает байты части claims, а повторный канон у проверяющего дал бы
второй источник расхождений (решение «Архитектора» 2026-10-20, векторы door-token).

## Ключи `door/keys`

Из P/06.5 Н3 «`/where/<id>`» (сторона писателя) и P/03.4 Н3 «токен двери у держателя» (сторона проверяющего):

```yaml
door/keys:  {<kid>: <64 строчных hex открытого ключа>} — несекретная строка; консоль добавляет свой kid при создании
            door/signer, при старте и при выдаче, если его нет (P/06.5 Н3; разбор ревью стадии B 6–7, № 3); иное значение под
            своим kid консоль не перезаписывает: токен не выдаётся, тревога door.keys_conflict (P/06.5 Н3, Н4; (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7)); проверяющий: четыре части, door1, kid в door/keys, подпись, claims ровно {user, unit, holder,
            routes, expires} с типами по договору, now < expires, unit и holder — свои, первый сегмент пути URL запроса к двери
            держателя (без query) — элемент routes байт в байт, сырым — иначе отказ двери держателя: 403 {"error": "forbidden"} без причины
```

Состав claims закрыт: лишнее поле или нет любого из пяти, в том числе `user`, — отказ (решение «Архитектора» 2026-10-20, векторы door-token).
Типы claims закрыты: `user`, `unit`, `holder` — строки JSON; `routes` — массив строк JSON, элементы — сегменты по
грамматике `door.routes` (P/02.1, `strList`), без повторов; `expires` — целое JSON, секунды, не больше 2^53−1. Иной тип,
дробное или большее `expires`, повтор в `routes` — отказ 403 `{"error": "forbidden"}`, даже при верной подписи (решение «Архитектора» 2026-10-20, Kimi SB67-01).
Элемент `routes` — сегмент по грамматике `name` `[a-z][a-z0-9_-]{0,31}`, без «/» ([P/02.1](../../02-installer/spec/02.1-installer.norms.md)
Н1 «Форма», `door.routes`); `read/x` или `Read` — отказ (решение «Архитектора» 2026-10-20). Целое JSON — только запись без точки
и порядка, как целый знак писателя в [диалекте](../DIALECT.md) (`whole: true`): `1792454520.0` и `1.79245452E9` в байтах
claims — отказ, хотя значение целое (решение «Архитектора» 2026-10-20).
Текст claims проверяющий читает по I-JSON (RFC 7493): байты — строгий UTF-8 (неверная последовательность — отказ, не
замена на U+FFFD); имя поля дважды — отказ, не «последнее значение»; имена сравниваются байт в байт (`User` — не `user`:
поля `user` нет — отказ) (разбор ревью стадии B 6–7, № 8; ADR-0083 доп. (12)); в строках и именах нет суррогатов (одиночный
суррогат записью `\uD800` — отказ, хотя байты — верный UTF-8) и некодов (U+FDD0–U+FDEF, U+xFFFE, U+xFFFF — отказ) (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7).
**Место токена и путь** (разбор ревью стадии B 6–7, № 9; ADR-0083 доп. (12)). Держатель берёт токен из заголовка
`Authorization: Bearer <token>`, а если такого заголовка нет — из параметра `t` query (`?t=<token>`: элемент `<video>`
заголовков не ставит, лекция М10B/24). Заголовок `Authorization` с иной схемой — как отсутствующий (дальше `?t=`);
параметр `t` дважды и больше — отказ; ни Bearer, ни `?t=` — отказ; при Bearer query не читается (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7). «Путь запроса» — путь URL без query: «?» и всё после него в путь не входят, у
`/play?t=…` сегмент — `play`. Детали HTTP (догадка стадии C DT-G01, решение «Архитектора» 2026-10-23): схема `Bearer` — без учёта регистра ASCII,
между схемой и токеном — SP или HTAB; заголовок `Authorization` со схемой `Bearer` есть, даже пустой, — query не
читается; query URL-декодируется; повреждённый query (`%` без двух hex-цифр), повтор `t`, несколько заголовков
`Authorization` — 403 `{"error": "forbidden"}`. Query — форма `application/x-www-form-urlencoded` строго (DT-G02): поля
через `&`, имя и значение — по первому `=`, `+` — пробел, `%XX` и UTF-8 — строго (неверное — 403 `forbidden`), поле без
`=` — пустое значение, `;` — обычный знак. Векторы — строки `verify.tsv` с query, DT-G01 и DT-G02.

**Токен места** (ADR-0091 доп. (7) п. 2, доп. (8) п. 9). Дверь места (`/where/<table>/<place>`, P/06.5 Н3): `unit` токена —
единица, чьи данные лежат в месте держателя, не обязательно им держимая; правило «`unit` и `holder` — свои» для двери места
читается так: `holder` — свой, данные `unit` лежат в его месте, иначе 403 `{"error": "forbidden"}`. Векторы — `place.tsv`.
Путь запроса сравнивается первым сегментом: у `/read/x` сегмент `read`; `/reader`, `/x/read` и `/` элементу `read` не
равны (решение «Архитектора» 2026-10-20, векторы door-token). Сегмент сравнивается сырым, без раскодирования `%XX`:
`/re%61d/x` элементу `read` не равен; любое расхождение — отказ, не обход (решение «Архитектора» 2026-10-20, векторы door-token). Отказ — один исход для всех причин: дверь держателя отвечает 403 с телом
`{"error": "forbidden"}` без причины (решение «Архитектора» 2026-10-20, векторы door-token) ([P/03.4](../../03-worker/spec/03.4-worker.norms.md) Н4), порядок проверок не нормирован. Так
клиент не узнаёт, какая проверка не прошла, а реализации не расходятся в порядке проверок (решение «Архитектора» 2026-10-20, векторы door-token).

Нечитаемая строка `door/keys` — исход семьи владельца ([`door-keys.outcomes.tsv`](../../06-console/data/door-keys.outcomes.tsv)):
у держателя — `kid` токена не найден, отказ двери (403 `forbidden`). Единица нечитаемости — строка целиком: запись другого
`kid` не по форме (ключ не 64 строчных hex) делает нечитаемой всю строку, и токен со своим, верным `kid` тоже получает
отказ — проверяющий не читает строку по записям (разбор ревью стадии B 6–7, № 8).

**Гонки.** Ответ называет наблюдённого держателя; переезд может завершиться до использования двери, и ответ не продлевает
аренду. Действительность операции повторно проверяет держатель по эпохе/аренде: изменившийся держатель после ответа
отсекается проверкой эпохи/аренды у двери (из P/06.5 Н3 «`/where/<id>`», «`/where/<table>/<place>`» «Гонки» без изменения;
аудит раскладки Б-21, решение «Архитектора» 2026-10-25).

## Векторы

Пакет [`door-token`](../vectors/door-token/README.md) (решение «Архитектора» 2026-10-20, разбор ревью стадии B 3–5):
выпуск (`issue.tsv`: зерно `door/signer`, `kid`, claims → байты JCS и `token`) и проверка у держателя (`verify.tsv`: строка
`door/keys`, `token`, `now`, свои `unit` и `holder`, путь запроса → `ok` или `forbidden` по списку проверки выше). Реализация
проходит их своей функцией, без стенда; на стенде проверка держателем остаётся чтением (P/06.5-05, P/03.4-08: у стенда нет
двери держателя, которая проверяет токен).

Канонический JSON (RFC 8785, ADR-0072), на который опирается договор, — пакет [`jcs`](../../01-store/vectors/jcs/README.md)
урока P/01 (`canonical_json.tsv`: вход → форма RFC 8785 → sha256; ADR-0083 доп. (33) п. 2).

## Соответствие прежним урокам

Из P/06.5 (разбор ревью стадии B 3–5, В1; прежде М10/9 Н3 «`/where/<id>`»): блок «Токен двери — байты» — строка `token`
(здесь «Токен») и строка `door/keys` о писателе; строка `door/signer` остаётся в P/06.5 Н3. Из P/03.4 Н3 «токен двери у
держателя» (прежде часть М10/9-09): строка `door/keys` о проверяющем и фраза «Гонок» (здесь «Ключи `door/keys`»; обе
половины строки `door/keys` слиты в одну, как в источнике М10/9). Части норм по `note` [id-map](../id-map.tsv): P/06.5-05
(байты токена, `door/keys`), P/03.4-08 (проверка у держателя).
