# Договор проверки строки: форма строки единицы и общая проверка

Общий договор модуля «Платформа» (ADR-0083 доп. (5), доп. (13): общий алгоритм нескольких процессов — договор, а не копии
в главах; догадка стадии C W03-E07, решение «Архитектора» 2026-10-23). Владелец — глава
[P/06.1](../../06-console/spec/06.1-console.norms.md) консоли (Н1.2 «Строка единицы», Н1.3 «Идентификатор», Н3 «Общая
проверка строки»). Участники: дверь единиц и таблиц консоли (P/06.1 Н3 «создать», «править», «таблица — записать
строку») и библиотека заказчика воркера ([P/03.6](../../03-worker/spec/03.6-worker.norms.md) Н1.6, Н3 «заказать»;
ADR-0091 п. 1) — одна проверка над одной формой строки. Перенесено из P/06.1 Н1.2, Н1.3 (named, tombstone, unique,
canonical_url, ref_and_must_match), Н3 «Общая проверка строки» и шагов 4–7 «создать», 2, 4–5 «править» без изменения
поведения; что делает дверь вокруг проверки (заявка, номер, запись, коды HTTP, `made_prefix`, `made_key`, секреты) —
P/06.1 и [P/06.2](../../06-console/spec/06.2-console.norms.md), что делает библиотека — P/03.6.

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). «Н1.2», «Н1.3», «Н3», «Н4» в перенесённом тексте — адреса
глав P/06.1, если не сказано иное; «шаг N» «создать»/«править» — шаги прохода двери P/06.1 Н3, их проверки — разделы
«Порядок проверок» ниже.

## Форма

Строка единицы — по манифесту каталога (`unit.fields`; форма манифеста — `Platform/02-installer/spec/02.1-installer.schema.json`,
[форма](../../02-installer/spec/02.1-installer.schema.json)) и разделу «Строка единицы» ниже. Строка состояния единицы
`<sub>/state/<имя>/<id>` (раздел «Состояние единицы») — форма `Platform/03-worker/data/state.schema.json`, исходы
`Platform/03-worker/data/state.outcomes.tsv` ([форма](../../03-worker/data/state.schema.json),
[исходы](../../03-worker/data/state.outcomes.tsv); C149-STATE-SUPPORT-01, решение «Архитектора» 2026-10-26).

## Строка единицы

```yaml
<sub>/<rows>/<id>:
  id:        <id как строка>                       # ДОЛЖЕН
  revision:  <десятичное целое ≥ 1>                # ДОЛЖЕН; 1 при создании, +1 на каждую правку, удаление не меняет
  born:      <32 строчные hex-цифры>               # жизнь строки (ADR-0091 п. 3): ставит создатель — дверь (Н3 «создать» шаг 8)
                                                   # или библиотека заказчика (P/03.6 Н1.6) — новым случайным значением при
                                                   # каждом создании, и над надгробием; правка, пометка удаления и
                                                   # перезапечатывание его сохраняют; строка без born создана до этой нормы — её жизнь ""
  made:      <канонический JSON {by, at, keep, gone?}>  # только у строки заказчика (P/03.6 Н1.6; ADR-0091 п. 1): by — подсистема-заказчик;
                                                   # at — время события, keep — до какого времени строку никто не удаляет
                                                   # физически (время — Platform/common/data/codec.tsv строка time, P/01.1 Н0; числа JSON) — ставит только
                                                   # библиотека заказчика; gone — время удаления строки дверью, ставит дверь
                                                   # по своим часам (Н3 «удалить»)
  deleted:   "true"                                # только у надгробия; иначе элемента нет
  <поле>:    <значение по типу>                    # каждое поле манифеста, кроме отсутствующих (ниже)
values_by_type:
  string, url: как есть
  int:        десятичная запись
  float:      десятичная запись без экспоненты: из записей, которые при чтении в binary64 дают это число, — с наименьшим
              числом значащих цифр; из них — ближайшая к точному значению числа; из двух равно близких — с чётной
              последней цифрой; -0 → 0 (правило выбора — ADR-0091 п. 1; запись — та же: 5e-7 → 0.0000005, 1e21 →
              1000000000000000000000)
  bool:       "true" | "false"
  list:       элементы через запятую; если есть пустой элемент, элемент содержит запятую или текст начинается с `[` — массив JSON;
              [] хранится как ""; [""] — как JSON-текст '[""]'. При чтении "" → [], ведущий '[' → JSON-массив,
              иначе разделить по запятым; непереданное при правке поле сохраняется в этой форме;
              поле меток размещения (`placement.constraint: labels-subset`) — только слова по [азбуке меток](labels.md) (1–64 ASCII: первая буква или цифра, далее буква, цифра, `_`, `.`, `:`, `-`)
  json:       канонический JSON (ADR-0072); значение null — элемента нет
  blob:       "sha256-<hex>"; байты — объект <sub>/blobs/sha256-<hex> (Н1.5); в строку дайджест попадает
              только дверью байтов PUT /{rows}/{id}/{blob_field} (Н2 «Двери тел и таблиц»):
              правка полей принимает лишь прежний дайджест строки или "" (снять); при создании — только ""
  *_secret:   конверт enc:v2:… (договор запечатывания); клиент никогда не получает значения: в ответе — маска "***" (глава 6.2 Н1.1)
absent:
  - поле с inherit, если не задано: элемента нет (не "" и не "null")
  - json-поле со значением null
platform_fields:   [id, revision, deleted, worker, placement, epoch, phase, observed_revision, born, made]   # строки единицы
table_platform_fields: [by, at, made_at, held_by, garbled]   # строки таблицы — свой список (P/02.1 tables.<имя>.fields «не из»;
  # P/06.1 Н3 «таблица — записать строку» шаг 1): поле таблицы, объявленное с именем из platform_fields единицы (worker,
  # epoch, …), — обычное поле; незнакомое — отказ, как прежде (догадка стадии C C06-ROWCHECK-TABLE-FIELDS-707-01, решение
  # «Архитектора» 2026-10-25)
  # unit.fields не объявляет (отказ загрузки P/02.1), клиент не задаёт; в живой строке только id, revision, born и
  # made (у строки заказчика), deleted — только у надгробия; born и made дверь не выдаёт клиенту на запись: тело с ними —
  # 400 «a client may not set …» (Н3 шаг 4), правка их сохраняет (ADR-0091 пп. 1, 3); made — в ответе (Н2);
  # state — не элемент строки: действующее состояние единицы — в ответе GET (Н2; P/03.6 Н1.7); worker/placement — строка <sub>/placement/<id> (P/04 Н1.1, добавлено М10/4);
  # epoch — строка эпохи; phase, observed_revision — status[].phase, status[].observed_revision
  # объекта <sub>/heartbeats/<имя> (P/03.4 Н1.1, добавлено М10/5)
```

Текстовые формы значений по типам — векторы [`values-by-type`](../vectors/values-by-type/README.md) (разбор ревью стадии A
6–7, № 33).

## Строка заказчика: `made`

Перенесено из [P/03.6](../../03-worker/spec/03.6-worker.norms.md) Н1.6 (`made`, `ORDER_HORIZON`, `not_after`, `tombstone`,
`deletes`) без изменения поведения: правило читают библиотека заказчика (P/03.6), контроллер (P/04 Н3 шаг 8) и дверь единиц
консоли (P/06.1 Н3 «удалить») (аудит раскладки А-11, решение «Архитектора» 2026-10-25).

```yaml
made:        {by: C, at, keep} («Строка единицы» made выше): at — время события, при продлении — max(прежний at, t_E); keep не убывает:
             max(прежний keep, at + ORDER_HORIZON + 120); gone ставит дверь при удалении (P/06.1 Н3 «удалить»)
ORDER_HORIZON: 600                           # с; постоянная платформы, не объявление манифеста: событие старше по часам
                                             # заказчика (now − t_E > ORDER_HORIZON) не исполняется; порог свежести меньше —
                                             # логика заказчика, платформа его не знает (ADR-0091 п. 1, решение владельца 2026-10-22)
not_after:   каждая запись заказа несёт условие хранилища not_after = t_E + ORDER_HORIZON + 60 (P/01.1 Н1, Н3 «Время
             приёма»): запись применяется, только если её время приёма не позже; иначе 409 expired — исход expired, той же
             записью не повторяется. Принятая запись повтора стоит в журнале раньше удаления строки и проваливается на
             CAS, позднейшая — expired: not_after повтора = t_E + 660 ≤ keep − 60 = not_before удалённой жизни (P/04 Н3 шаг 8)
tombstone:   над надгробием строки своего made — только для события позже made.gone + 60: создание с cas версии
             надгробия и теми же fixed («Идентификатор и ограничения полей» tombstone ниже), revision надгробия + 1, новый born; событие в минуте после
             удаления считается прежним — удалённое оператором повтор прежнего события не возрождает (сознательное сужение)
delete:      строку с made удаляют (воркер адресата по worker.deletes — P/03.6 Н1.6, контроллер — P/04 Н3 шаг 8) только когда часы
             удаляющего строго позже made.keep, с условием хранилища not_before = max(0, made.keep − 60) (P/01.1 Н1: время ≥ 0; C04-KEEP-01): 409 early — не удалено, повтор новой записью на
             следующем проходе
```

## Состояние единицы

Перенесено из [P/03.6](../../03-worker/spec/03.6-worker.norms.md) Н1.7 (`acts`, `unreadable`) без изменения поведения:
правило «состояние действует» читают держатель единицы (P/03.6), контроллер (P/04 Н1.3 `retire_when`, Н1.3а `state`) и консоль
(P/06.1 Н2 «Состояние в ответе») (аудит раскладки А-05, решение «Архитектора» 2026-10-25). Форма строки состояния — `Platform/03-worker/data/state.schema.json`, исходы — `Platform/03-worker/data/state.outcomes.tsv`
(P/03.6 Н1.7; C149-STATE-SUPPORT-01, решение «Архитектора» 2026-10-26).

```yaml
acts:        состояние действует, когда строка единицы живая (не надгробие), её born и revision равны born и revision
             состояния, а value читается по схеме; эпоха при чтении не сверяется — итог переживает переезд: новый держатель
             читает действующее состояние, и подсистема законченную задачу не исполняет снова; у курсора (unit.state.cursor)
             сверяется только born — revision не сверяется: правка строки курсор не сбрасывает (P/03.6 Н1.7 cursor;
             C170-STATE-CURSOR-01, решение «Архитектора» 2026-10-27)
unreadable:  строка не по форме семьи или value не по схеме — не действует, как отсутствующая; читатель, собирающий
             многие строки, считает её (P/04 Н1.2 snapshot_state_garbled; P/01.1 Н0 «Устойчивость выдачи»)
```

## Подготовка полей

При создании состав клиентских полей определяется для каждого поля манифеста (до записи строки):

1. Поле передано — взять именно переданное значение, включая `0`, `false`, `[]` и `null` (кроме `null` у поля с
   `inherit` — шаг 2); умолчание его не заменяет. Допустимость значения проверяется по разделам «Порядок проверок» и «Отказы».
2. Поле не передано или передано `null` и имеет `inherit` — не создавать элемент; значение `inherit` является концом
   цепи чтения, а не значением для записи в новую строку.
3. Поле не передано и имеет `default` — взять значение `default` из загруженного манифеста; у поля `string` при
   `unit.id: numeric` каждое `{id}` в нём заменяется десятичной записью id, выданного этому созданию (Н3 «создать»
   шаг 3), — один раз: правка значение не пересчитывает (P/02.1 Н1.3; запрос VMS № 1, решение «Архитектора» 2026-10-23).
4. Иначе взять пустую форму типа из таблицы ниже. `default` и `inherit` вместе запрещены P/02.1.

| Тип | Пустое значение JSON | Элемент строки (раздел «Строка единицы») |
|---|---|---|
| string, url, blob | `""` | `""` |
| int, float | `0` | `"0"` |
| bool | `false` | `"false"` |
| list | `[]` | `""` |
| json | `null` | отсутствует |

Проверки типа и ограничений применяются к полученным значениям в порядке раздела «Порядок проверок»; умолчание не обходит
`fixed`, `enum`, ссылки и остальные ограничения. Непереданное required-поле по-прежнему даёт отказ
П4: подготовка пустой формы или default не считается его передачей клиентом.
После проверки `json: null` не сохраняется. Секрет хранится по границе кольца (ниже) и выдаётся маской `"***"` (глава 6.2 Н1.1), а blob при создании
пуст: default/inherit для blob запрещены P/02.1. При правке непереданные поля сохраняются из строки,
умолчания заново не применяются. Создание над надгробием применяет те же правила подготовки;
проверка fixed сравнивает подготовленное значение с надгробием.

**Строка таблицы** (P/06.1 Н2 «Двери тел и таблиц» `TableRow`, Н3 «таблица — записать строку» — ссылкой; догадка стадии C
C06-ROWCHECK-TABLE-33-01, решение «Архитектора» 2026-10-23). Подготовка — шаги 1 и 3 выше; шаг 4 у таблиц не применяется:
поле, не переданное в `POST` и без `default`, в строке отсутствует — пустая форма типа не добавляется. `POST` таблицы — полная
замена строки по манифесту, не правка: поле прежней строки с тем же именем, не переданное клиентом, в новую строку не
переносится, кроме секретов и штампов — они сохраняются по своим правилам: секрет верхнего уровня пустой, `null` или не
переданный — прежний,
смена `bound_to` без нового секрета — 400 «must be given anew» (глава 6.2 Н3 шаг 3); штампы `by`, `at`, `made_at` ставит
консоль, `made_at` строки с тем же именем — прежний (P/06.1 Н3 «таблица — записать строку» шаг 2), штамп в теле — 400
`unknown field` (там же, шаг 1).

**Граница кольца** (P/06.2 Н1.2 `no_key`, Н4 — ссылкой; догадка стадии C C06-ROWCHECK-DEV-01, решение «Архитектора»
2026-10-23). Состояние кольца проверка получает от вызывающего (опция API библиотеки; читать P/06.2 ей не нужно):

| Кольцо | Секрет в подготовленной строке |
|---|---|
| `SECRETS_KEY` не задан (режим разработки, P/06.2 `no_key.unset`) | правка (`PUT`) с непустым `*_secret` — значение пишется открытым, как есть; создание (`POST`) единицы с непустым `*_secret` на любой глубине — 400 до заявки (там же). Строка таблицы — то же правило (одно для дверей единиц и таблиц, P/06.2 Н3 «создать/править» шаг 3): строки с этим именем нет — `POST` таблицы — создание, непустой `*_secret` на любой глубине — 400 до записи; строка есть — `POST` поверх неё — правка, непустой секрет пишется открытым; пустой, `null` или не переданный секрет верхнего уровня — прежнее значение (догадка стадии C C06-ROWCHECK-TABLE-RING-33-01, решение «Архитектора» 2026-10-23) |
| задано и открывается | конверт `enc:v2` по [договору запечатывания](sealing.md) |
| задано, но не читается или не открывается (в том числе `SECRETS_KEY=""`, P/06.2 `no_key.unreadable`) | 503 `unavailable` до проверки строки (до П1), ничего не пишется |

Список имеет только строковые элементы; иной JSON-элемент — отказ типа поля (раздел «Отказы»).
Значение `int` на входе двери — JSON-число без дробной части и экспоненты в пределах ±(2^53 − 1): `1.0`, `1e2` и
`9007199254740992` у `int` — `not_number` (такое число читает клиент JSON любого языка). Число `-0` хранится как `0`
(JCS, ADR-0072).
Значение json-поля — любое значение JSON; его `schema` — JSON Schema 2020-12 по определению `jsonSchemaLite`
`Platform/02-installer/spec/02.1-installer.schema.json` ([форма манифеста](../../02-installer/spec/02.1-installer.schema.json); перечень ключевых слов и глубина — там; аудит раскладки, Б-06; разбор ревью стадии A 6–7,
№ 11); схема с иным ключевым словом — отказ загрузки `refused:value` (P/02.1), поэтому все реализации проверяют одно и то же.
Пустой элемент допустим у обычного list, но не у меток размещения по [азбуке меток](labels.md).

## Идентификатор и ограничения полей

```yaml
id:
  named:                                    # unit.id: <поле>
    rule:    значение несекретного поля type string, включая умолчание типа; источник с суффиксом _secret запрещён загрузчиком P/02.1; одна строка; ДОЛЖЕН быть непустым
    update:  поле-источник id неизменяемо даже без fixed в манифесте; PUT может не передавать его или передать тот же id;
             другое значение — 400 «<поле> is fixed» без записи; переименование этой дверью не выполняется
    refused: пустое; "." и ".."; содержит `/`, `\`, `|`, `"`, `,`; управляющие знаки (Cc), разделители строк и
             абзацев (Zl, Zp); цифры вне 0–9 (Nd не ASCII); категории — по таблицам Unicode 15.0.0 (UnicodeData), как NFKC
             главы 6.2; знак, не назначенный в этой версии, ни к одной из них не относится (добавлено ревью стадии A 2)
  tombstone:                                # возврат имени после удаления
    rule:    создание над надгробием проходит только с теми же значениями fixed-полей; revision = надгробия + 1,
             записью с cas по версии надгробия; иначе 400 с именем поля
  unique:    true | canonical            # предварительная проверка нового значения по живым единицам;
                                         # пустое ("") и отсутствующее значение не участвуют: две живые единицы с
                                         # пустым unique-полем — не конфликт (догадка стадии C RC-17, решение
                                         # «Архитектора» 2026-10-23)
                                         # canonical — URL в каноническом написании (ниже); конфликт — 409 unique;
                                         # атомарной уникальности между строками нет (Н3 «Гонки» правки)
  canonical_url:                         # синтаксический канон RFC 3986 §6.2.2 (ADR-0057)
    - схема и хост — нижним регистром; шестнадцатеричные цифры процент-кодирования — верхним
    - процент-кодированный незарезервированный знак (буква, цифра, - . _ ~) декодируется
    - точечные сегменты пути удаляются (RFC 3986 §5.2.4); пустой порт («host:») снимается
    - порт по умолчанию не снимается, query не сортируется, пустой путь не заменяется на «/»: «тот же поток» — смысл
      подсистемы, не платформы (ADR-0057)
ref_and_must_match:                      # поле единицы или таблицы (P/02.1 Н1.3)
  ref:        <подсистема>/<семья>       # цель значения v — строка <ref>/<v>
  must_match: {<поле цели>: <поле этой строки>}   # при живой цели значения равны; иначе 409 conflict, fault must_match;
                                                  # отсутствующий элемент цели не равен ничему, и "" тоже
  rules:
    - цели нет — не отказ: ref без must_match не требует существования цели (ADR-0057)
    - цель не читается — 409 conflict, fault garbled
    - в обе стороны (как у таблиц, Н3 «таблица — записать строку», шаг 2): создание или правка единицы, которая
      сама — цель, проверяет живые единицы и строки таблиц каталога, чьё поле с ref на её семью и must_match называет её:
      их значения равны новым значениям цели, иначе 409 conflict, fault must_match; ссылающаяся строка не читается — fault garbled
```

## Значение url

Поле `type: url` читается так: не по RFC 3986 (`%zz`, управляющие знаки, `\`), нет схемы или хоста (место хоста и значения
«хоста нет» — `schemes.<s>.host`/`none` [договора адреса](url-credentials.md) «Схемы»; при `host: path` пути нет — места хоста нет: `mirror://local`), с
учётными данными (`@` в авторитете; пароль или логин в адресе по правилу поля — [договор адреса](url-credentials.md)),
с `#` (кроме схемы с `fragment: none`), схема не из `schemes`, нечисловой порт — отказ `bad_url` (договор адреса «Схемы»).

## Порядок проверок

Проверка — функция подготовленных полей, манифеста таблицы, каталога манифестов и прочитанных строк. Внутри каждой
проверки поля — порядок объявления `unit.fields`; первый отказ — первого по манифесту поля.

```
создание (подготовленные поля строки; у библиотеки — поля F заказа, id и born/made она ставит сама, P/03.6 Н1.6):
П1. поля тела: платформенное поле → незнакомое поле. Платформенные — platform_fields у строки единицы, table_platform_fields
    у строки таблицы; из платформенных отказ называет первое по порядку своего списка;
    незнакомые — все их имена по возрастанию байтов UTF-8 в одном «unknown field(s) …» (RC-10)
П2. подготовка (раздел «Подготовка полей»), сохранив сведения, что передал клиент; затем проверки значений:
    blob (не дайджест; при создании не "") → json (not_json, too_long 4000 байт канонического текста — другой
    границы, в том числе вложенности, нет: RC-13; схема) → enum →
    типы значений (not_number) → вес: присутствующее значение поля placement.weight.field ≥ 1 (P/04 Н1.3; после
    заполнения default) → url (раздел «Значение url») → группа → метки ([азбука меток](labels.md))
    группа: отказа нет — значения нет, оно пусто или хост не читается — единица не в группе; bad_url источника — шаг
    url с именем поля; группу проверка строки не вычисляет (пояснение — P/04 Н1.3 group_by; RC-12)
П3. named: поле-источник id передано или получено умолчанием непустым → по разделу «Идентификатор»; пустой или
    непереданный id П3 пропускает: отказ даст П4 («needs a <поле>»), а у не-required поля — bad id «is empty» после П4;
    создание над надгробием: иные fixed → «<поле> is fixed» (tombstone)
П4. обязательные: каждое required-поле передано клиентом и не ""
П5. ссылки по порядку: прямые ref / must_match самой строки → обратные must_match (строки, которые ссылаются на неё) →
    unique по живым строкам; внутри каждой — порядок unit.fields (RC-11). Обратные must_match, первый отказ: ссылающиеся
    подсистемы по возрастанию байтов имени; в подсистеме — строки единиц, затем таблицы по возрастанию байтов имени;
    внутри — порядок полей манифеста; строки — по возрастанию байтов ключа (RC-15). Цель ref/must_match — ключ самой
    проверяемой строки: цель — она сама в новом подготовленном состоянии, обе стороны сравниваются по новым значениям
    (согласованная правка пары проходит, несогласованная — must_match); так же при создании (RC-16)

правка (только переданные поля, без заполнения умолчаний):
Р1. П1 и проверки значений П2 над переданными полями, кроме blob-подслучая «не прежний дайджест строки» — он в Р2
Р2. по прочитанной строке: fixed-поле меняется или переданное поле-источник именованного id не равно id → «<поле> is
    fixed»; blob-поле: значение не прежний дайджест строки и не ""
Р3. ссылки по новым значениям, порядок П5
```

Порядок отказов П1, П2 «группа», П5 и Р3 — догадки стадии C RC-10–RC-12, RC-15, RC-16, решение «Архитектора» 2026-10-23.

Значение поля-списка в `fixed` (П3 надгробие, Р2) и в сравнениях ссылок сравнивается по значению JSON — список строк,
порядок и повторы сохраняются, — не по тексту элемента строки: `["a", ""]` и `'["a",""]'` — одно значение; `unique` у
списка запрещён загрузчиком (P/02.1, корпус `c3_unique_list`) (догадка стадии C RC-14, решение «Архитектора» 2026-10-23).

Чтения проверки — цели `ref` и `must_match` самой строки и строки каталога, чьё поле с `ref` на эту таблицу и `must_match`
её называют (раздел «Идентификатор» `ref_and_must_match`); удаление ссылок не проверяет. Поле `blob` при создании пусто.

Проверки `ref`/`must_match`/`unique` создания и правки выполняются до записи и не атомарны
с изменением других строк. Две правки разных единиц, обе проверившие прежние значения,
могут успешно записать одинаковое unique-значение. Аналогично результат проверки связи
может устареть из-за правки или удаления связанной строки. Последующий проход контроллера
размещения не проверяет эти ограничения; гарантии автоматического обнаружения, записи
диагностики или исправления такого расхождения нет. Проверка при следующем POST/PUT
выполняется по тем же правилам, а не служит фоновым аудитом. `ref` сам по себе не вводит
требование существования цели (ADR-0057): условия отказа остаются условиями соответствующего поля. У библиотеки так же.

## Отказы

Слова отказа — `error` (текст для человека, тест его не сравнивает) и `fault` из закрытого словаря
[`../vectors/fault/`](../vectors/fault/README.md). У двери — код и тело по P/06.1 Н4 «Дверь единиц» (столбец «дверь»); у
библиотеки — исход заказа `refused` и счёт `creates.refused` пульса (P/03.6 Н1.6, P/03.4 Н1.1).

| Причина | Шаг | Слово | Дверь |
|---|---|---|---|
| задано платформенное поле | П1, Р1 | `error` «a client may not set …» | 400 |
| незнакомое поле | П1, Р1 | `error` «unknown field(s) …» | 400 |
| `blob` не дайджест; при создании не `""`; при правке не прежний дайджест и не `""` | П2, Р2 | `error` | 400 |
| json-поле больше 4000 байт канонического текста / не по схеме | П2 | `fault: too_long` / `error` | 400 |
| `enum` не из списка | П2 | `error` | 400 |
| значение не по типу поля: не число у `int`/`float`, не булево, не список строк, не строка | П2 | `fault: not_number` для чисел; `error` с именем поля | 400 |
| целое значение поля placement.weight.field < 1 | П2 | `{detail, error: "<поле> must be at least 1"}`, без fault | 400 |
| `url` не читается, с учётными данными, с `#`, схема не из `schemes` | П2 | `fault: bad_url`; `error` без значения, с именами полей `credentials` ([договор адреса](url-credentials.md) А15) | 400 |
| метки не по азбуке меток | П2 | `error` | 400 |
| id не по разделу «Идентификатор» | П3 | `error` с именем и причиной (bad id) | 400 |
| `fixed`-поле меняется (правка или возврат над надгробием); меняется поле-источник id | П3, Р2 | `error` «<поле> is fixed …» | 400 |
| `required`-поле не задано или `""` | П4 | `error` — `a <sub> unit needs a <поле>` | 400 |
| `unique`/`ref`/`must_match` нарушены; ссылочная строка не читается | П5, Р3 | `error: conflict`, `fault: unique \| must_match \| garbled` | 409 |
