# Договор замка присутствия: файл, кто держит, кто читает, счёт `room`

Общий договор модуля «Платформа» (ADR-0083 доп. (5); разбор ревью стадии A 3–5, № 9). Владелец — ресурс
[P/05](../../05-resource/spec/05-resource.norms.md): он читает замки своей коробки, выводит из них присутствие процессов
воркеров (P/05 Н1.4 `workers`, `running`, `unknown`, `presence`) и счёт `room.<sub>` строки двери (P/05 Н1.4
`door_row`). Держит замок воркер — сторона воркера: глава [P/03.2](../../03-worker/spec/03.2-worker.norms.md) Н3
«старт()», шаг 2б; число `room.<sub>` читает контроллер ([P/04](../../04-controller/spec/04-controller.norms.md) Н3
«заказать()»); раскладка корня событий — [P/02.4 Н1.2](../../02-installer/spec/02.4-installer.norms.md) «Канал настройки
и раскладка `PLATFORM_DIR`». Перенесено из М10/8 Н1.4 (`presence_lock`, `room`) и М10/11 Н1.4 (`presence`) без изменения
поведения; вывод слов присутствия из полей пульса ресурса — P/05 Н1.4 `presence`.

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md).

## Форма

Содержимое замка — семья `presence-lock`: `Platform/05-resource/data/presence-lock.schema.json`,
`Platform/05-resource/data/presence-lock.outcomes.tsv`; элементы `room.<sub>`, `live.<sub>` пишутся в строку двери
`platform/doors/<сервер>` — `Platform/05-resource/data/doors.schema.json`, `Platform/05-resource/data/doors.outcomes.tsv`
(аудит раскладки, В-45; решение «Архитектора» 2026-10-25).

## Замок

```yaml
presence_lock:  <корень событий>/.workers/<sub>/<экземпляр>.lock   # компоненты — по кодированию имён договора журнала событий
             # («Имена файлов в общих деревьях», event-journal.md); решение «Архитектора», второй пилот, Н-1
             содержимое: JSON {instance, sub, worker, server, pid} — экземпляр, подсистема, имя слота, сервер, pid процесса;
             форма — семья presence-lock P/05 (схема ../../05-resource/data/presence-lock.schema.json, исходы
             presence-lock.outcomes.tsv рядом): worker — имя слота или "" до захвата имени и пока воркер ищет без имени,
             pid — целое ≥ 1, набор полей закрыт (разбор ревью стадии B 3–5, № 23; ADR-0083 доп. (11))
             воркер: при старте, до захвата имени (глава P/03.2 Н3 «старт()»): open(O_CREAT) → исключающий блокирующий flock
             (ждёт, пока ресурс отпустит замок своей проверки; без LOCK_NB) → сверка fstat(fd) и stat(путь) (то же
             устройство и inode; stat отказал ENOENT — файл удалён — несовпадение; разбор ревью стадии B 3–5, № 19); не совпало — закрыть и
             повторить с начала; совпало — записать
             содержимое заново (не дописывает) под замком, worker — ""; после каждого захвата имени — переписать содержимое
             заново под тем же замком, worker — имя слота (разбор ревью стадии B 3–5, № 23); при потере имени (отдать_имя) — переписать
             содержимое заново под тем же замком, worker — "" (решение «Архитектора» 2026-10-20 по № 23); держит flock всё время жизни процесса; замок отпускает только
             выход процесса (ADR-0083 доп. (10))
  modes:     по фактическим читателям (догадка стадии C PL-G02, решение «Архитектора» 2026-10-23): путь к замкам — корень
             событий и .workers — 2771, группа w2c-events: прочим проход без чтения (догадка стадии C PL-G03, решение «Архитектора» 2026-10-23); .workers/<sub> — 2775,
             группа w2c-events (файлы создают воркеры разных подсистем, удаляет ресурс — группа пишет; скрипт воркеров
             w2c-workers без групп, P/02.4 Н1.5, — перечень и чтение как прочий); каталоги бакетов — 2770/2750, договор
             журнала событий bucket modes; файл замка — 0644,
             владелец — пользователь воркера, группа w2c-events (ресурс открывает для flock и читает группой, скрипт
             воркеров — как прочий); режим ставит писатель явно при создании, не umask (у процессов umask 0007, P/02.4
             Н1.1 common); существующий путь к замку (корень событий, .workers, .workers/<sub>) или файл замка с иными
             правами или группой — отказ старта воркера до записи, строка лога; существующие объекты воркер сам не
             меняет (chmod/chown — дело установки, P/02.4), новые каталоги и файл создаёт с точными правами и группой
             нормы, создание каталога сериализуется flock родителя — то же правило, что у журнала событий bucket modes
             (догадка стадии C PL-EXT-02, решение «Архитектора» 2026-10-23); содержимое без fsync — правда о присутствии в самом flock, содержимое справочное; ошибка
             fstat/stat (не ENOENT) или записи после flock — отказ старта или обновления, замок держится до выхода процесса
             ресурс: «известные» воркеры — только по файлам замков, ключ <sub>/<worker> из содержимого; на каждый файл —
             flock без ожидания: взял — сверка fstat(fd) и stat(путь) (ENOENT у stat — несовпадение, разбор ревью стадии B 3–5, № 19); не
             совпало — файл уже заменён или удалён, не трогать; совпало —
             процесс мёртв, gone (замок отпустить; файл, который ресурс удаляет, — удалить, держа замок, и лишь затем отпустить,
             ADR-0083 доп. (10); разбор ревью стадии B 6–7, № 35); занят и содержимое по форме с непустым
             worker — runs; занят, а содержимое пусто, не по форме или worker = "" — живой процесс без номера: входит в
             room.<sub>, не входит в workers, running, live.<sub>; unknown — только файл, который не читается (ошибка
             open или read), не его содержимое (разбор ревью стадии B 3–5, № 23), и замок, проверку которого нельзя
             завершить: ошибка flock, кроме «занят» (EWOULDBLOCK), или ошибка fstat/stat, кроме ENOENT у stat (то —
             несовпадение), — тоже unknown, как нечитаемый файл; файл не трогать (решение «Архитектора» 2026-10-20, разбор ревью стадии B 6–7); у одного <sub>/<worker> несколько файлов — runs, если хоть один занят;
             файл gone ресурс МОЖЕТ удалить, держа его flock и после совпавшей сверки; иного источника присутствия (pid-файлы, kill(pid, 0)) нет
presence:   ресурс говорит о процессах своей коробки полями пульса P/05 Н1.4 (`workers`, `running`, `unknown`; слова и их
            вывод — там же, судьба — P/04); как узнаёт — замок присутствия выше
            (<корень событий>/.workers/<sub>/<экземпляр>.lock, flock; второй пилот, Н-1); нечитаемое → unknown (слово
            закрытого перечня P/04: контроллер ждёт его), никогда «ушёл»
```

Форма содержимого — семья `presence-lock` P/05: [схема](../../05-resource/data/presence-lock.schema.json),
[исходы](../../05-resource/data/presence-lock.outcomes.tsv); экземпляр — `{key, file}`, текст файла с `x-encoding: json` у корня
([слои В7](../LAYERS.md) § 6); колонка `schema` строки каталога называет семью, раздел семей — в нормах P/05 (разбор ревью стадии B 6–7, № 44).

Гонка «воркер между open и flock, ресурс удаляет файл»: воркер открыл файл, ресурс берёт flock без ожидания, сверка
совпала — gone, ресурс удаляет файл и отпускает замок; блокирующий flock воркера получает замок на удалённом файле,
его stat(путь) — ENOENT, это несовпадение: воркер закрывает и повторяет с начала, новый файл. Свидетельство —
чтением: тест с остановкой воркера между open и flock (разбор ревью стадии B 3–5, № 19).

## Счёт `room`

```yaml
room:      элемент room.<sub> каждой подсистемы каталога, чей файл роли roles/<sub>worker.env (договор файла окружения «Переменные окружения») есть на
           коробке, пишется каждой отметкой двери — сколько ещё процессов роли поднимет этот сервер (ADR-0084 п. 2):
           десятичное min(floor(HOST_MEMORY_MB / WORKER_MEMORY_MB) − живые, 98 − живые с номером n ≥ 2), не меньше 0;
           живые — файлы замков присутствия <sub> (presence_lock выше) с занятым flock, по файлам экземпляров, не по
           агрегату running, в том числе с пустым или не по форме содержимым (разбор ревью стадии B 3–5, № 23); номер — n имени <prefix>-<сервер>-<n> из содержимого замка (договор имени слота «Имя процесса роли и его номер»; n 2…99 — заказанные; Б-25);
           файла роли нет — элемента нет; файл роли не разбирается, замок роли unknown (файл не читается, разбор ревью стадии B 3–5, № 23) или перечень каталога замков роли не получен (C05-PRESENCE-SCAN-UNKNOWN-01) — "unknown"; контроллер
           сервер без числа в room.<sub> не выбирает (P/04 Н3 «заказать()») и сам вычитает резервы своих заказов
           (свободно(s), P/04 Н3 «нехватка()»);
           предел схемы: room у каждой роли считается от всей памяти сервера, общий потолок по ролям не делится
           (ADR-0084 доп. (1) Р12)
number:    n имени <prefix>-<сервер>-<n> — каноническая десятичная запись ASCII без ведущих нулей; область — как у экземпляров
           юнита воркера P/02.4 Н1.1: 1 — базовый, 2…99 — по заказу; n > 99 (и запись не каноническая) — не слот этой
           установки: замок как без номера — в живые входит, в «живые с номером» и live — нет, строка лога (векторы
           common/vectors/presence-room; догадка стадии C PL-EXT-01, решение «Архитектора» 2026-10-23)
live:      рядом с каждым room.<sub> — элемент live.<sub>: номера n ≥ 2 живых замков роли, по которым посчитан room.<sub>,
           десятичные через запятую по возрастанию, без повторов, из того же снимка замков; замок без номера (имя не
           <prefix>-<сервер>-<n>, worker = "", содержимое пусто или не по форме — разбор ревью стадии B 3–5, № 23) входит в room, не в список; пустой список — ""; room.<sub> "unknown" — live.<sub> нет;
           контроллер без live.<sub> сервер не выбирает (P/04 Н3 «свободно(s)»; ADR-0084 доп. (3) Р14′; разбор ревью
           стадии A 3–5, № 3, 19)
```

## Векторы

Пакет [`presence-room`](../vectors/presence-room/README.md) (счёт `room`); режимы каталогов и файлов замков — строки `modes.tsv` пакета [`journal`](../vectors/journal/README.md) (вместе с журналом событий). (ADR-0083 доп. (32) п. 2)

## Соответствие прежним урокам

Из М10/8 Н1.4 (стадия B, разбор ревью стадии A 3–5, № 9): `presence_lock` целиком и `room` (у P/05 Н1.4 `room` —
ссылка сюда); из М10/11 Н1.4 — `presence`. Часть нормы М10/8-10 (замок и счёт `room`; P/05-07) — по `note`
[id-map](../id-map.tsv); сторона воркера (шаг 2б «старт()» М10/5) — глава P/03.2, часть М10/5 по id-map урока 3.
