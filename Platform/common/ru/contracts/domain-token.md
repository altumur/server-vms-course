## Форма

Функция `token` читает `domain/keys` и `domain/revoked`: `Platform/08-domain/data/keys.schema.json`, `Platform/08-domain/data/keys.outcomes.tsv`; `Platform/08-domain/data/revoked.schema.json`, `Platform/08-domain/data/revoked.outcomes.tsv`; объявление вида и `audience_claim` — `Platform/02-installer/spec/02.1-installer.schema.json` (аудит раскладки, V-14, B-32; решение «Архитектора» 2026-10-25).

## Токен

Из M11/2 N1.6:

```yaml
token:         <b64url(header)>.<b64url(payload)>.<b64url(sig)>       # ровно три части
  header:      JSON-объект; обязательные alg — строка "EdDSA", kid — строка; прочие поля пропускаются (не отказ);
               выпускающий пишет ровно {alg, kid} в JCS
  payload:     JSON-объект; обязательные: iat, exp — конечные числа, стенные секунды; jti — строка 1–64 [A-Za-z0-9_-];
               kind — непустая строка: person у людей (урок 9), вид манифеста у воркеров (урок 7); прочие поля этим уроком
               пропускаются, кроме поля аудитории вида (P/02.1 N1.2b audience_claim; разбор ревью стадии B 6–7, № 24) при проверке получателем; выпускающий пишет
               JCS и jti — 16 знаков hex из случайных 8 байт, кроме видов keep при живой строке domain/issued (P/08.2 N1.6a)
  sig:         Ed25519 ключа kid набора над ASCII «<header>.<payload>» как пришли
TOKEN_SKEW:    60          # с, допуск часов в обе стороны; часы — стенные часы проверяющего
person:        токен человека: выпускающий (процесс domain при входе, P/08.4 N1.2) пишет ровно {iss: <домен>, sub: <имя
               человека>, kind: "person", iat, exp, jti}, без aud; exp = iat + TOKEN_LIFETIME; проверяющий прочие поля
               пропускает (п. payload), sub проверяет по форме имени — [договор имени человека](person-name.md) `name` (1–64 знака без
               пробельных, управляющих и : | ( ) " /, не break-glass; аудит раскладки A-20) — иначе 401 у сторожевой
               (догадка стадии C GP-L01, решение «Архитектора» 2026-10-23)
```

Проверка токена — функция `token` (раздел «Проверка» ниже) у каждой двери, которая принимает токены домена; каждая
такая дверь ДОЛЖНА передавать `expect` ниже, кроме названной без него (решение «Архитектора» 2026-10-20, ADR-0083 доп. (14) п. 7; разбор ревью стадии A 8–10):

| Проверяющий | Где | `expect` |
|---|---|---|
| сторожевая консоли кластера | [договор сторожевой и передачи](gate-and-pass.md) «Сторожевая» `identity` п. 3; [P/06.3](../../../06-console/ru/spec/06.3-console.norms.md) N1.3, [P/06.7](../../../06-console/ru/spec/06.7-console.norms.md) N1.9 `cluster` | `{kind: person, cluster: null}` |
| сторожевая консоли домена (P/10 N1.5; право — строка `domain` P/08.4 N1.5) | тот же договор, `identity` п. 3 | `{kind: person, cluster: null}` |
| процесс `domain`, двери людей | [P/08.4](../../../08-domain/ru/spec/08.4-domain.norms.md) N3 «дверь людей» шаг 2 | `{kind: person, cluster: null}` |
| получатель токена вида — воркер или дверь члена | [P/03.7](../../../03-worker/ru/spec/03.7-worker.norms.md) N1.5, N3 «проверить у получателя» | `{kind: <вид>, cluster: <свой кластер>, audience_claim: <из объявления вида>, keep: <виды keep: true каталога>}` |
| воркер, дверь `door.pass` первого вида: проверяет учётные данные, переданные консолью кластера | [договор сторожевой и передачи](gate-and-pass.md) «Передача `door.pass`» `rule` | `{kind: person, cluster: null}` |
| процесс `domain`, `POST /domain/revoke` | P/08.4 N1.2 `revoke` | `expect {kind: person, cluster: null}`: токен в теле — удостоверение самого себя, токены видов с `keep` отзывает `DELETE /domain/issued`, вид без `keep` живёт до `exp`: предел (ADR-0110 доп. (16) п. 1) |
| дверь процесса подсистемы, маршрут с `domain` | [P/03.4](../../../03-worker/ru/spec/03.4-worker.norms.md) N1.7 `door_admission` `domain`, `role_domain` | `{kind: [<виды маршрута>], cluster: <свой кластер>, audience_claim: {<вид>: <поле из объявления вида>}, keep: [<виды keep по манифесту, объявившему вид>]}` (ADR-0091 доп. (17) п. 9, доп. (18) п. 1, доп. (19) п. 1) |

Дверь токенов воркера (урок 7) токены выдаёт, а не проверяет. Воркер подсистемы на домене токен человека пришедшего
`door.pass` не проверяет: людей проверяет сторожевая консоли домена, источник запроса воркер принимает по роли
`domainconsole` клиента TLS ([P/03.7](../../../03-worker/ru/spec/03.7-worker.norms.md) N1.6 `door_client`; решение «Архитектора» 2026-10-20 по сверке 3.7). Вид токена и `aud` — урок 7: токен другого кластера или вида
отказывается у получателя, шагами 9–10 этого договора.

## Проверка: `token(keys, revoked, now, token) → ok payload | refused <слово>`

Из M11/2 N3; `keys` — принятый набор ([договор набора ключей домена](keys.md) «Набор»), `revoked` — строка
`domain/revoked` как прочитана (форма — [договор набора ключей домена](keys.md) «Отзывы»), `now` — стенные секунды
проверяющего:

```
1. revoked есть и не по форме N1.6 (не {jtis: строка}; запись не «<jti>:<число>»; число — конечное, по грамматике
   JSON без пробелов: `0123`, `1e400`, `+1` — не по форме; добавлено сверкой M11, T2, T3) → refused no_revocations
2. token не строка; не три части; часть не base64url; header или payload не JSON-объект или с повтором ключа;
   header.alg ≠ "EdDSA"; header.kid не строка                                     → refused not_a_token
3. kid ∉ keys.keys                                                               → refused unknown_key
4. подпись не проверяется keys.keys[kid] над ASCII «<header>.<payload>»           → refused bad_signature
5. iat или exp не конечное число, jti не строка по грамматике N1.6, kind не непустая строка → refused bad_claims
5a. kid ∈ until, now > until[kid] и не (kind ∈ expect.keep и now ≤ keep_until[kid]) → refused unknown_key   # после подписи: kind подписан, судить его раньше нельзя; чужая подпись на истёкшем ключе — bad_signature (ADR-0110 доп. (10) п. 3)
6. now > exp + TOKEN_SKEW                                                         → refused expired
7. now < iat − TOKEN_SKEW                                                         → refused future
8. jti в revoked                                                                  → refused revoked
9. expect есть и kind ≠ expect.kind (строка) или kind не из expect.kind (список)   → refused wrong_kind
10. expect есть, expect.cluster не null и поле аудитории (expect.audience_claim; у списка видов — значение
    отображения для вида, совпавшего на шаге 9; нет записи или нет audience_claim — aud) не список строк или без
    expect.cluster                                                                → refused wrong_audience
11. иначе                                                                         → ok payload
# expect — что ждёт проверяющий (таблица «Токен» выше): вид и свой кластер; у токенов людей кластер — null
# (person без аудитории, урок 9): аудитория не проверяется
```

«N1.6» в шагах 1 и 5 — M11/2 N1.6 (теперь P/08.2 N1.6): форма `domain/revoked` (шаг 1; теперь — [договор набора ключей домена](keys.md) «Отзывы») и грамматика `jti` (раздел «Токен» выше, шаг 5). Форма
`expect` — вход команды `token` ([P/08.2](../../../08-domain/ru/spec/08.2-domain.norms.md) N5): `expect?: {kind: <row> | [<row>…], cluster: <member> | null, audience_claim?: <field
name — a non-empty string, default aud> | {<kind>: <field name>}, keep?: [<kind>…]}`; `keep` — виды с `keep: true` манифеста, нет поля — пусто. `kind` строкой — один вид, `audience_claim` при нём — строка;
`kind` списком — непустой, без повторов, без `person`, `audience_claim` при нём — отображение, ключи — виды из списка (вид без
записи — `aud`); иное сочетание, `person` в списке, ключ отображения не из списка — не по форме, код 2 (ADR-0091 доп. (18)
п. 1, доп. (19) п. 1). Ключ `cluster` обязателен; `null` допустим только при `kind: person` строкой. `expect`
без ключа `cluster` или с `cluster: null` при ином `kind` — не по форме: это ошибка вызывающего, а не слово отказа
(команда `token` — код 2, P/08.2 N5). `expect` — закрытая форма `{kind, cluster, audience_claim?, keep?}`: незнакомый ключ — тоже
не по форме, код 2 (опечатка `audience_clam` иначе молча вернула бы проверку к `aud`; догадка стадии C DT-G03, решение «Архитектора» 2026-10-23). Умолчания «без `cluster` — аудитория не проверяется» нет: оно ослабляло бы
отсечение по аудитории (решение «Архитектора» 2026-10-20, ADR-0083 доп. (14) п. 7; разбор ревью стадии A 8–10).

Равенство на границе принимает: `now = exp + 60` — ещё `ok`. `revoked` отсутствует (строки нет) — отзывов нет. Дверь,
у которой `domain/revoked` есть, но не читается хранилищем, отвечает как при `no_revocations`: проверить нечем (503 `{error: "unavailable"}` у
сторожевой — правило «Нечитаемая строка» договора сторожевой и передачи, [P/06.3](../../../06-console/ru/spec/06.3-console.norms.md) N1.3; решение «Архитектора» 2026-10-28 по сверке ddc9bee1e), а не «токен годен».

## Слова отказа

Из M11/2 N4 (строки о токене):

| Причина | Исход | Кто и как видит | Что делает вызывающий |
|---|---|---|---|
| токен: `no_revocations` | 503 `{error: "unavailable"}` у сторожевой и у дверей процесса `domain` ([P/08.4](../../../08-domain/ru/spec/08.4-domain.norms.md) N1.5; правило «Нечитаемая строка» договора сторожевой и передачи) и при самопроверке выданного токена у двери токенов | вызывающий | ждать читаемой строки |
| токен: `not_a_token`, `unknown_key`, `bad_signature`, `bad_claims`, `expired`, `future`, `revoked`, `wrong_kind`, `wrong_audience` | 401 у сторожевой ([P/06.3](../../../06-console/ru/spec/06.3-console.norms.md)); самопроверка выданного токена у двери токенов — 503 `unavailable` (урок 7) | вызывающий | войти заново / получить новый токен; `future` — проверить часы |

У получателя токена вида (P/03.7 N4) — `wrong_kind`, `wrong_audience` (шаги 9–10). У двери процесса подсистемы, маршрут с
`domain` (P/03.4 N1.7, N4): слова шагов 1–8 — 401 (`no_revocations` — 503), нет токена — 401 `not_a_token`; `wrong_kind`,
`wrong_audience` — 403; тело `{error, detail}` (ADR-0091 доп. (14) п. 2, доп. (17) пп. 3, 8).

## Векторы
