## Поколение, метка, пределы

Копия P/08.3 N1.3 (`generation` … `BODY_LIMIT`) и N1.3a (`ROAD_QUIET`) байт в байт: урок — источник копии (решение
«Архитектора» 2026-11-04); `every` и `REPORT_EVERY` подробно — раздел «Ответ `carry`: `every`»:

```yaml
generation:     domain/members/<член>/reports/<rev>   # объект держателя (P/05 N1.1): целое поколение, JCS
  whole:        {sent_at, objects, key, keys_rev?, pinned?, outcomes?}   # objects — все объекты члена после применения
                изменения; outcomes — P/09.1 N1.5: смена исходов — новое поколение, агент шлёт поле исходов правок, ещё названных держателем (OUTCOME_HOLD), в каждой
                публикации, пока строка domain/outcomes не пуста; нет поля — исходов нет
delta:          domain/members/<член>/reports/<rev>.delta     # байты тела публикации как получены — то, что подписал агент
reported:       domain/members/<член>/reported               # объект-метка; единственная граница принятого
                # две части (решение «Архитектора» по R41-05 прогона 41): поля поколения пишет только generation (договор
                # приёма отчёта, шаг 7); поля последнего принятого запроса — каждый приём с записью метки (шаги 6, 7)
  # поля поколения
  rev:          целое ≥ 1 — номер поколения; выдаёт держатель: +1 на принятое изменение
  sha256:       hex sha256 байтов generation — sha256 от JCS целого whole
  base:         rev, против которого пришло изменение; 0 — пришло целое
  delta_sha256: hex sha256 байтов delta (при base 0 — тела целого, как пришло)
  signature?:   заголовок X-Agent-Signature прямого отчёта, создавшего поколение, как пришёл (N1.4); через ретранслятор
                поля нет (N1.3a); via — поле последнего запроса, поэтому метка без signature и без via законна:
                поколение пришло через ретранслятор, затем прямой heard (решение «Архитектора» по сверке M11, A14)
  key, keys_rev?, pinned?: из публикации — по ним консоль домена принимает члена и показывает закрепление
  # поля последнего принятого запроса
  sent_at:      sent_at публикации; received_at — стенные секунды держателя приёма
  request_sha256: hex sha256 байтов тела этого запроса, как пришло; повтор узнаётся по (sent_at, request_sha256)
  via?:         ретранслятор — N1.3a
  stale:        из публикации при каждом приёме, включая «слышал» (договор приёма отчёта, шаг 6); нет в публикации — []
  sign_failures?: из публикации при каждом приёме с записью метки, как stale; поколения не создаёт и метку само не
                освежает; нет в публикации — поля нет (N1.6a; P/09.1 N1.12; решение «Архитектора» по сверке M11, A7, W1)
  every?:       с — период, сказанный члену последним ответом с записью метки (N1.5; договор приёма отчёта «Ответ `carry`: `every`»); нет — REPORT_EVERY
keep:           два последних поколения и их delta; старшие и те, что выше метки, убираются при следующей ограниченной возобновимой попытке уборки
REPORT_EVERY:   5           # с — проход агента; ответ держателя может назначить every (N1.5), 1 … 3600
MARK_REFRESH:   22.5        # с = LOST_AFTER/2 (глава 8.1 N1.3) по монотонным часам держателя
BODY_LIMIT:     16 MiB      # предел тела двери держателя и ретранслятора: больше — 413, тело не читается дальше; он же —
                            # предел JCS целого шага 4a договора приёма отчёта и целого, которое агент не шлёт (P/09.1 N1.2 body)
ROAD_QUIET:    15         # с, монотонные часы держателя: три прохода агента (REPORT_EVERY 5); дольше — прежняя дорога молчит;
                           # у class camera — road_quiet = max(15, 3 × mark.every) (P/08.3 N1.1a)
```

Метка — граница принятого: объект с номером не выше `reported.rev` неизменяем; объект выше — ничей: не читается, не
переносится, не держит номер, следующий приём пишет поверх. Читатели берут `reported.rev` и читают только объект этого
поколения; метка без объекта или объект не с её `sha256` требует ограниченной перечитки метки ниже перед `silent`; никогда не смесь (читатели — P/08.1, P/08.5,
P/08.8).

## Публикация члена

Из P/09.1 N1.2 (`publication`, `out_of_delta`, `member_objects`, `ready`) и P/08.3 N1.6 `form` без изменения поведения
(разбор ревью стадии B 8–10, № 4; Claude S-6): тело `POST /api/member/<член>`, которое агент шлёт (P/09.1), а держатель и
ретранслятор принимают функцией «принять». Как агент собирает объекты (`change`, `fresh`, вклады в книги, предел тела
агента) — P/09.1 N1.2; формы `tls_ca`, `tls_ca_certs` у члена — [договор сертификата роли](role-certificate.md); их
приём держателем (`on_accept`) — P/08.3 N1.6; `members_rev` — раздел «Список членов отставшему»; `sign_failures` — P/09.1 N1.12.

```yaml

  sent_at:      конечное число — стенные секунды агента в момент отправки
  objects:      {<ключ объекта>: <JSON-значение объекта>} — что изменилось против base (целое при base = 0)
  base?:        целое ≥ 0 — rev поколения у держателя, против которого изменения; нет или 0 — тело целое
  deleted?:     [<ключ объекта>…] — ключи, которых больше нет против base; только при base > 0
  key:          hex ключа члена — тот, что в domain/member-key
  keys_rev?:    rev набора domain/keys, который член держит (нет — набора нет)
  stale?:       [<ключ пульса>…] — пульсы <sub>/heartbeats/<воркер> копии, которые не менялись дольше LOST_AFTER (45 с)
                по монотонным часам агента; по возрастанию; нет — пусто. Вне дельты: не входит в whole и не порождает
                поколения
  pinned?:      отпечаток domain/root члена (нет — не закреплён)
  outcomes?:    {<id>: <исход>} — исходы правок домена, P/09.1 N1.5 (ключ ≠ id внутри исхода — исход не засчитывается,
                P/08.6 N1.6 settle);   tls_ca?, tls_ca_certs? — договор сертификата роли;
                sign_failures?: {domain?: n, console?: n}, n — целое платформы 1 … 9007199254740991 (потолок целого P/08.10),
                целым числом JSON; составное или неизвестное имя, иное n — не по форме (догадки стадии C ACC-FORM-31-01,
                ACC-G01-COUNTER-31-01, решение «Архитектора» 2026-10-23) (запросы, которые агент с запуска не отправил, не
                смог подписать: domain — держателю или ретранслятору, console — правка своей консоли; нет ни одного — поля нет;
                P/09.1 N1.12; догадка стадии C ACC-G01, решение «Архитектора» 2026-10-23);
                members_rev? — раздел «Список членов отставшему» ({term, rev} списка, который член держит; вне дельты);
                book_parts?: {<sub>/<книга>: {<раздел>: {term, rev} | null}} — разделы книг to: "*", которые член держит, null — просьба без копии; не больше BOOK_PARTS_SHOWN 64 окном по кругу (P/08.5 N1.4), вне дельты;
                gathered?: {term, rev} | null — поле gathered своей строки раздела (P/08.8 N1.8a), вне дельты; сверяется с источником, строку просит send_row;
                row?: {doc} — своя строка раздела по слову send_row (P/08.8 N1.8a, P/09.1 N1.2a), вне дельты;
                class?: server | camera, batch?: {name, sig} — раздел «Стук партии»; вне дельты; агент шлёт их, пока своего имени
                нет в своей строке domain/member-list/<раздел> (P/09.1 N1.1 join); нет class — server
out_of_delta:   поле вне дельты — закрытый перечень формы публикации: stale, tls_ca, tls_ca_certs, sign_failures, members_rev, class, batch, row, book_parts, gathered;
                поля, которого нет в публикации P/09.1 N1.2, — тело не по форме, 400 not_a_publication (ответ «Архитектора» 2026-10-25 (аудит раскладки, вопрос T5a)); поле вне дельты не по форме
                своей нормы — поле не взято, журнал держателя, отчёт принимается, как tls_ca ниже; stale — ключи
                без повторов, повтор — поле не взято
tls_ca_form:    в форме публикации tls_ca и tls_ca_certs — списки строк любой длины; не список строк — поле не взято
                (out_of_delta); всё прочее — длина, повтор, не 64 строчных hex, не PEM, не CA:true, не сходится — проверка
                держателя on_accept (P/08.3 N1.6): ничего не меняется, журнал domain.member.ca.refused, отчёт принимается
member_objects:                               # что агент несёт и что держатель хранит; прочее держатель отбрасывает молча;
                                              # ключ сравнивается с перечнем точно, не по началу и не подстрокой
  <sub>/heartbeats/<воркер>:  пульс P/03.4 N1.1 каждого манифеста каталога с domain.ref
  <sub>/snapshot/<шард>:      шард снимка P/04 N1.3a каждого такого манифеста
  <sub>/snapshot-tables/<таблица>:  снимок таблицы P/04 N1.3b: <таблица> — ключ domain.view_tables манифеста каталога, domain.ref не нужен;
                              ready по нему не судится; сумму держит агент (P/09.1 N1.2 tables_budget)
  прочие семьи (догадка стадии C ACC-G01, решение «Архитектора» 2026-10-23; P/09.1 — откуда перенесено):
    reports:                  domain.reports: [<семья>/…] манифеста (элемент — префикс семьи с конечной «/») — объекты
                              <sub>/<семья><имя> (<имя> — один компонент по грамматике <имя>; глубину задаёт элемент объявления;
                              C09-REPORTS-NAME-01) члена как есть; книга их не читает (P/09.1 N1.2)
    вклады:                   objects["<sub>/<строка>[/<слот>]"] = {<item>: <объект входа>} — строки вкладов книг domain.books

                              liveness, in_report; держатель хранит как есть, решает сборка (P/08.5 N1.3)
```

## Проверка члена и ключа

Перенесено из [P/08.3](../../../08-domain/ru/spec/08.3-domain.norms.md) N2, строка `POST /api/member/<член>`, без изменения поведения
(аудит раскладки, решение «Архитектора» 2026-10-25, B-12); подпись — [договор подписи агента](agent-signature.md). Дверь ретранслятора принимает члена тем же
порядком над своей памятью (P/09.2 N2); пакет ретранслятора у держателя — P/08.3 N2 `POST /api/relay` (C08-G06).

```yaml
order:          по порядку: 503 `standby` до чтения тела (P/08.10 N1.7); 413 больше BODY_LIMIT; 400 не публикация P/09.1 N1.2 (в том числе вложенность JSON глубже
                JSON_DEPTH P/01.1 N1 — 128; сверка M11, A12); имя — свой держатель, записи нет или она не `how: "holder"`: подпись ключом из тела неверна — 401, верна — шаг 1 прохода «держатель в списке» (P/08.3 N3), исчерпание или сбой — 503 `unavailable`, агент повторит; не член — подпись ключом из тела (`key`): неверна — 401,
                верна — стук (разделы «Стук», «Стук партии») и 404 «no member called <член>», у class camera с retry_in (раздел «Занято»); идёт сбор «из ничего» — ещё send_row и слияние row (P/08.8 N1.8a), подпись на 403 ключа тоже судится ключом из тела; член — держатель, чья Entry ещё без key
                (P/08.3 N3 «держатель в списке» шаг 1): подпись ключом из тела (`key`) — верна → шаг 2 того прохода, он сверяет ключ с `domain/member-key`,
                иначе 401; запись без key с `revoked_keys` (P/08.3 N3 «принять члена» шаг 1) — как не член: стук; прочий член — 403 ключа нет в записи или он не тот, 403 отозван (`revoked_keys`,
                `revoked_members` набора); 401 подпись ключом записи (P/08.3 N1.4; договор подписи агента); 409
                `deposed` (P/08.8 N1.6) или 503 `standby` потерянной очереди; 429 `busy` (раздел «Занято»), записи нет; затем шаги «принять» ниже в их порядке: 409 `same_sent_at`
```

## Функция «принять»

Из M11/3 N3 «принять(mark, stored, body, via, heard_ago) — держатель, на POST /api/member/<член> после подписи»:

`via` — дорога: нет — прямо, иначе имя ретранслятора (урок 4 N1.3); `heard_ago` — монотонные секунды с последнего
приёма этого члена по любой дороге (нет — не слышал); приём — исходы `generation`, `heard` (с записью метки или без) и
`same`; `ignored` и отказы приёмом не считаются.

```
0. приём одного члена — один за раз в процессе domain (мьютекс); подпись, член и ключ уже проверены (раздел «Проверка члена и ключа»)
1. body — не JSON-объект по форме N1.2                                             → 400 not_a_publication
2. mark есть и body.sent_at = mark.sent_at (одни часы члена на всех дорогах, урок 4 N1.3): sha256(body) ≠
   mark.request_sha256 → 409 same_sent_at; mark.via = via → same (ничего не писать, метку не освежать); иначе → heard
   (повтор другой дорогой: поколения нет, метка — по правилу освежения шага 6; добавлено M11/4)
2a. mark есть, mark.via ≠ via, body.sent_at < mark.sent_at и heard_ago < road_quiet (урок 4 N1.3; у class server это ROAD_QUIET) → ignored
   (ничего не писать: прежняя дорога жива, а это тело старше по часам члена)
3. base > 0 и (mark нет, или mark.via ≠ via, или base ≠ mark.rev, или stored не читается или не с mark.sha256) → 409 rebase
4. objects' = (base > 0 ? объекты stored : {}) ∪ body.objects − body.deleted; объекты вне member_objects отбросить
4a. JCS(whole') больше BODY_LIMIT → 413 {error: "whole too large", detail}; ничего не писать (P/08.10 N1.5; добавлено M11/12)
5. нет шарда снимка какого-то манифеста каталога с domain.ref                           → 409 not_ready
6. mark есть, stored читается и с mark.sha256, и whole' без sent_at = whole stored без sent_at (JCS) → heard
   (stored не читается или не с mark.sha256 — шаг 7: испорченное поколение заменяется новым; добавлено сверкой M11, A1):
   метку этот процесс не писал, или писал не меньше MARK_REFRESH назад (монотонные), или body.stale ≠ mark.stale
   (сравниваются отсортированные списки ключей; сверка M11, A8), или входное every есть и ≠ mark.every →
   переписать метку: поля поколения прежние; поля последнего запроса — sent_at, received_at, request_sha256, via, stale,
   sign_failures, every — этого запроса; иначе ничего не писать
7. иначе → generation: rev = (mark ? mark.rev : 0) + 1; mark.rev = 2^53 − 1 → 503 {error: "refused", reason: "rev_exhausted",
   detail: "<член>'s generations reached 2^53 − 1: the mark cannot grow"}, ничего не меняется (добавлено сверкой M11, A18); записать reports/<rev> = JCS(whole'), затем reports/<rev>.delta = body,
   затем метку {rev, sha256, base, delta_sha256, signature?, key, keys_rev?, pinned?, sent_at, received_at,
   request_sha256 (= delta_sha256), via?, stale, sign_failures?, every?};
   убрать ВСЕ reports/<g> и их .delta при g < rev−1 и объекты выше rev; продолжить прерванную уборку при следующих попытках
```

`sent_at` ниже `mark.sent_at` на той же дороге принимается: порядок на одной дороге задаёт дорога, часы члена, шагнувшие
назад, берутся сразу; между двумя дорогами — шаг 2a (урок 4). Ответ на шаги 2 (same, heard), 2a, 6, 7 — carry (N1.5); его `rev` —
`rev` метки, если `mark.via` = дорога ответа, иначе 0 (другая дорога шлёт целое). Сбой между шагами 7: объект выше метки ничей (N1.3), следующий приём пишет поверх.

## Пакет ретранслятора: пределы

Перенесено из [P/09.2](../../../09-agent/ru/spec/09.2-agent.norms.md) N1.4 (`BATCH_LIMIT`, `KNOCKS`) без изменения; пределы
читают ретранслятор (пишет пакет, P/09.2 N3) и держатель (принимает, [P/08.3](../../../08-domain/ru/spec/08.3-domain.norms.md)
N3 «держатель на POST /api/relay/<ретранслятор>», N4) — у них ссылки сюда (C08-G05, решение «Архитектора» 2026-10-25).

`BATCH_LIMIT` и `KNOCKS` имеют единственный числовой источник — одноимённые строки [формы P/08](../../../08-domain/forms/runtime-constants.tsv). В следующем блоке имена обозначают значения этих строк; `KNOCKS + 1` — следующий незнакомец после заполнения памяти. Формула `BATCH_LIMIT = 4 × BODY_LIMIT` сохраняется; новых настроек или полей провода нет.

```yaml
BATCH_LIMIT:   значение формы P/08     # = 4 × BODY_LIMIT (раздел «Поколение, метка, пределы»); тело POST /api/relay/<ретранслятор>
                          # больше — 413 до разбора; пакеты — в порядке имён членов; член больше BODY_LIMIT — не шлётся (журнал)
KNOCKS:        значение формы P/08; тело стука не больше 256 KiB, с полем row — 768 KiB: строка раздела до 512 KiB; у ретранслятора — KNOCKS незнакомцев в памяти, последний от имени
               заменяет прежний; незнакомец KNOCKS + 1 вытесняет самый старый стук (по времени приёма); вытесненный узнаёт это
               только по knocking держателя (раздел «Стук») — нового отказа нет
holder:        у держателя стуков в пакете больше KNOCKS — сверх первых KNOCKS по имени пропускаются без записи; стук с телом
               больше 256 KiB, с полем row — больше 768 KiB — пропуск без записи (как стук не по форме, P/08.3 N3 шаг 3); пакет живёт; 413 — только
               целый пакет больше BATCH_LIMIT
answer:        ответ держателя клиенту агента и ретранслятора (carry на POST и GET /api/carry, RelayAnswer на
               POST /api/relay) клиент читает не больше BATCH_LIMIT; больше — как «нет ответа» (P/09.1 N3 шаг 5:
               следующий проход, база прежняя), строка журнала без значения тела; нового числа нет
               (C09-ANSWER-LIMIT-01, решение «Архитектора»)
```

## Эксплуатационные обязанности

ADR-0130 Addendum (10), MB2: уборка удаляет ВСЕ поколения отчётов старше двух последних зафиксированных поколений, с дельтами, и незафиксированные объекты выше текущей метки по действующему правилу идентичности. Она возобновима: авария или прерванный ограниченный проход оставляет пригодные поколения следующей попытке, включая поколения старше `rev−2`. Порядок публикации сохраняется: целое, дельта, метка; уборка не удаляет текущее и предыдущее зафиксированные поколения. Конечный положительный объявленный реализацией бюджет работы и уборки ограничивает попытку и завершение при квалифицированной нагрузке.

MB3: перед объявлением `silent` из-за отсутствующего поколения или несовпадения хеша метка перечитывается ровно один раз, затем читается названное ею поколение. При стабильной метке и по-прежнему отсутствующем или несовпадающем объекте сохраняется действующий исход `silent`. Если перечитанная метка изменилась, а названное ею новое поколение не удаётся прочитать точно, наблюдение остаётся временно не подтверждено: публикация производного снимка откладывается; дверь, требующая подтверждённого чтения, использует существующий исход `503 unavailable`. Гонка не публикует `silent`, поколения не смешиваются, новое состояние члена и бесконечный цикл не вводятся.
