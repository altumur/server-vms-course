# Векторы токена двери

Текст производный от `vectors/door-token/README.md`, руками не правится: источник — английский [`vectors/door-token/README.md`](../../../vectors/door-token/README.md), правка идёт в него, русский пересобирается переводом.

[Договор токена двери](../../contracts/door-token.md) задаёт выдачу `door1.<kid>.<claims>.<sig>` (claims в JCS, подпись Ed25519) и проверку у держателя по `door/keys`. Выдача принадлежит консоли в [P/06.5](../../../../06-console/ru/spec/06.5-console.norms.md), N3 `/where/<id>`; проверка — держателю двери в [P/03.4](../../../../03-worker/ru/spec/03.4-worker.norms.md), N3 и N1.7 `door_admission` `token`.

## Прогон

Кто исполняет: консоль (`06-console`) пропускает входы выдачи через свою функцию; воркер (`03-worker`) пропускает входы проверки и токена места через свою проверяющую функцию. Консоль выдаёт в `/where/<id>` и `/where/<table>/<place>`; сама не проверяет. Воркер проверяет и не выдаёт. Агент домена не читает `door/keys`; читатели каталога — консоль и `<s>worker`. Время — вход `now` в секундах настенных часов, а не часы процесса.

Выдача принимает `seed_hex`, `kid`, `claims` и выдаёт `claims_jcs` и `token` байт в байт. Ed25519 (RFC 8032) детерминирован: одинаковые seed и строка байтов дают одинаковую подпись. Проверка принимает `keys`, `authorization`, `now`, `unit`, `holder`, `path` и возвращает `ok` с прочитанными claims либо `forbidden`. Claims сравниваются по значению JSON, а не текстом.

## Команда стенда `door-token-issue`

Ключ `stand` профиля `06-console` ([общая раскладка профиля](../../acceptance/README.md), глава 6.5 N3) — шаблон с `{input}`, путём файла ровно с `{seed_hex, kid, now, claims}`. `seed_hex` и `kid` — строки, `now` — число, `claims` — входная лексема JSON без изменений: порядок полей, порядок `routes` и числовые лексемы не порождаются заново. Числовая форма проверяющей стороны выдачу не ограничивает. Seed, kid и время берутся из входа, а не из часов или собственных секретов стенда.

Ответ — ровно `{"claims_jcs": <текст>, "token": <текст>}`. Договор задаёт claims `{user, unit, holder, routes, expires}`, их форму JCS и кодирование токена: `door1.<kid>.<base64url without «=» of claims_jcs>.<base64url without «=» of the signature over ASCII «door1.<kid>.<claims>»>`. Неправильный вход — не объект, пропущенное, лишнее или повторное поле, неправильный тип либо `seed_hex`, `kid` или `claims` вне договора выдачи. Отказа выдачи с кодом 0 нет. Stdout — ровно один объект JSON и LF: первый байт `{`, затем объект, LF и конец. Лишние поля или байты, CRLF и внешние пробелы проваливают строку; форматирование внутри JSON допустимо; служебный вывод идёт в stderr. Код 0 означает вычисление; неправильный вход даёт код 2 и пустой stdout. Оболочки `result` нет.

## Команда стенда `door-token-verify`

Ключ `stand` профиля `03-worker` ([общая раскладка профиля](../../acceptance/README.md), P/03.4 N5) — шаблон с `{input}`, путём файла со входным объектом проверки `{keys, authorization, now, unit, holder, path}`. `keys` — значение JSON строки `door/keys`; `authorization` — полный заголовок Authorization, пустая строка означает отсутствие заголовка; `now` — число. `unit` (`<sub>/<id>`) и `holder` (instance его heartbeat) — собственные значения держателя. `path` — цель URL запроса, возможно с query; первый сегмент пути без query проверяется по `routes`.

Вызов токена места вместо этого подаёт `{keys, authorization, now, holder, path, place_units}`. Подсистема строит `place_units` из единиц, чьи данные лежат в месте держателя; единицы, чьи данные ещё не легли, нет, если норма двери её не назвала. Смысл задаёт раздел договора «Токен места».

Stdout — ровно один объект JSON в UTF-8 и LF: `{"result":"ok","claims":{…}}` с действительно прочитанными claims либо `{"result":"forbidden"}`; код 0. Неправильный вход даёт код 2. Другой код или result, лишние поля или байты проваливают строку.

## Ключи входа и отказ

Seed — `seed_secret` строки `door/signer` (64 строчные hex); соответствующий открытый ключ — под тем же kid в `door/keys`. Реализация берёт переданные байты seed и открытого ключа и заново их не порождает.

Отказ проверки — одно слово `forbidden`; дверь держателя возвращает 403 и `{"error": "forbidden"}` без причины ([P/03.4](../../../../03-worker/ru/spec/03.4-worker.norms.md), N4). Векторы не задают порядка проверок, потому что ответ не раскрывает причину. При расхождении прав договор, вектор правит «Спецификация».

## Провод векторов

Публичный селектор `table` — `issue.tsv` у выдачи, `verify.tsv` у проверки и `place.tsv` у проверки токена места (judge-only: `issue.tsv`, `verify.tsv`, `place.tsv`).

Строки `common/door-token` [единой формы](../../../vectors/wire.tsv) (judge-only: `wire.tsv`) связывают заголовки, выбранные входы, фикстуры, кадр нативного ответа и сравнение; [грамматика провода](../wire.md) задаёт кадр. Layout — исключение из вызовов функции, а не доказательство отдельной приёмки.

Фиксированные ключи, конкретные случаи выдачи и проверки, соответствия проверки случаям и ожидаемые ответы — в [случаях и покрытии](README.cases.md) (judge-only: `README.cases.md`).
