# Векторы: общая проверка строки

Текст производный от `vectors/row-check/README.md`, руками не правится: источник — английский [`vectors/row-check/README.md`](../../../vectors/row-check/README.md), правка идёт в него, русский пересобирается переводом.

Главе P/06.1 консоли принадлежит [договор проверки строки](../../contracts/row-check.md). Его потребители — дверь единиц консоли ([P/06.1](../../../../06-console/ru/spec/06.1-console.norms.md), N3 создать и править) и библиотека заказчика воркера ([P/03.6](../../../../03-worker/ru/spec/03.6-worker.norms.md), N1.6 и N3 заказать). Обе стороны исполняют свою общую проверку строки.

## Прогон

Функция готовит поля и проверяет P1–P5 у `create` или R1–R3 у `edit` над входными ячейками:

| Ячейка | Значение |
|---|---|
| `unit` | `<подсистема>/<rows>` для таблицы единиц манифеста или `<подсистема>/<таблица>` для таблицы манифеста; строки таблицы используют `table_platform_fields` и подготовку строки таблицы из договора |
| `op` | `create` или `edit` |
| `body` | переданные поля объектом JSON; числовые лексемы сохраняются |
| `stored` | у правки — прочитанная строка; у создания — надгробие, над которым создают; пусто означает отсутствие строки; элементы строки — строки |
| `rows` | прочие строки хранилища, которые читает проверка, объект JSON `{key: row}`; `"@garbled"` означает строку, нечитаемую своей формой |

Команда `vectors` получает манифесты вместе в `files` под именами `testsub.subsystem.yaml` и `testsub2.subsystem.yaml`; это байты файлов выгрузки. Библиотека подаёт поля заказа: поле-источник id — готовым id; `born` и `made` ставит сама и проверке не передаёт.

## Нативный выход проверки строки

Код 0 и один объект JSON: успех — `{"result": "ok", "row": {…}}`, где `row` — подготовленная строка `{element: text}`, у отсутствующего элемента нет ключа. Отказ — `{"result": "refused", "word": "<fault или класс>", "field": "<поле>"}`; у отсутствующего поля нет ключа `field`. Слова отказов и порядок полей задаёт договор; `fault` берётся из [словаря fault](../fault/README.md), иначе класс — `platform_field`, `unknown_field`, `blob`, `enum`, `type`, `labels`, `bad_id`, `fixed` или `required`.

У двери класс читается из `error` по P/06.1 N2; `unknown_field` — `unknown field`, а у строки таблицы `platform_field` — тоже `unknown field`. Поле — `field` без начального `/`; для неизвестных имён функция называет все по возрастанию байтов через запятую, дверь — первое. Текст `detail` не сравнивается. У библиотеки наблюдение — `refused` вместе с причиной, которую она пишет в лог.

Судья сравнивает `result`, `word`, `field` и выбранные элементы `row`: `@absent` означает отсутствие ключа; текст списка массивом JSON сравнивается по значению. Пометка шага договора — для человека, она не сравнивается. Колонки ожиданий не попадают в вызов.

## `state.tsv`

Раздел договора «Состояние единицы» задаёт `acts` и `unreadable`. Форма строки — [state.schema.json](../../../../03-worker/data/state.schema.json), с [исходами семьи](../../../../03-worker/data/state.outcomes.tsv). Входные ячейки — `name` (строка JSON с именем записи `unit.state` манифеста), `unit` (прочитанная строка или `"@absent"`) и `state` (прочитанная строка состояния или `"@absent"`); `files` даёт `testsub2.subsystem.yaml` со схемами `unit.state`. Элементы строки единицы включают `born`, `revision` и надгробие `deleted: "true"`; элементы состояния — `born`, `revision`, `epoch` и `value` текстом JSON.

Нативный результат — код 0 и `{acts, unreadable}`, у действующего состояния также разобранное `value`; JSON сравнивается по значению. Семья читается по тексту строки; JCS проверяет только писатель. Схема манифеста проверяет `value`. `born` нынешнего состояния обязателен и содержит 32 строчные hex; читатель не подставляет пустую жизнь.

## Кто исполняет и проверки вне функции

Дверь единиц консоли (`06-console`) исполняет все проверки строк. Библиотека заказчика воркера (`03-worker`) исполняет проверки таблицы, которую объявляет `worker.creates` её манифеста, у создания и правки; иных таблиц она не пишет. Воркер, контроллер и консоль проверяют состояние, когда их нормы судят, действует ли оно: P/03.6 N1.7, P/04 N1.3 и N1.3a, P/06.1 N2 соответственно. Роль исполняет функцию, которую вызывает её норма.

Функция не покрывает заявку, номер, запись, коды HTTP, `made_prefix`, `made_key` и секреты двери. Пороги веса, обратный `must_match` (включая порядок первого отказа), ссылки на себя, полная замена таблицы, секреты таблицы, граница кольца и поля таблицы с именами платформенных полей единицы также требуют чтения договора или отдельных проверок приёмки. Конкретное покрытие и пропуски записаны со случаями.

Конкретные строки, соответствия случая отказу, ожидаемые ответы и покрытие — в [случаях и покрытии](README.cases.md) (judge-only: `README.cases.md`).
