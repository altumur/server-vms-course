# Таблицы команд

Этот русский текст — производный от `acceptance/command-tables.md`, руками не правится.

Тема [общего README приёмки](README.md): директивы и двери — его [словарь](README.md#словарь-директив-и-дверей).

В таблице команд строка — вызов команды или адаптера профиля, а не HTTP-шаг. Форму называет слово маршрута цели: `verdicts`, `puts` или `variants` ([`forms/targets.routing.tsv`](../../acceptance/forms/targets.routing.tsv); только для судьи: маршруты судьи). Таблицы — из первого каталога строки маршрута. Интерфейс каждого вызова берётся из публичной строки цели ([реестр целей](forms/targets.README.md)). Судья читает каждую таблицу цели целиком до старта стенда. Пустые строки и строки, начинающиеся с `#`, — заметки, кроме объявлений, которые называет форма. Строка вне своей формы — ошибка данных класса `data`, найденная до старта стенда; это не исход реализации. Опись цели (N1.4 [норм](spec/acceptance.norms.md); только для судьи: нормы судьи) называет каждую строку её файлом и номером её физической строки.

## Детерминированные сбои системных вызовов

Две директивы ниже — общие операции стенда. Они наблюдают выбранный процесс хранилища снаружи; они не добавляют рабочую дверь, обработчик сигнала, расписание checkpoint или имя на диске. [Нормы судьи](spec/acceptance.norms.md#n32-жизненный-цикл-стенда) задают планирование, доказательства и классы отказов.

| Форма | Значение |
|---|---|
| `@crash <process> <calls> <K> <trigger>` | перебрать достижимые номера системных вызовов от 1 до K после начала триггера; на выходе выбранного успешного вызова остановить все наблюдаемые потоки до возврата в пользовательский код, послать SIGKILL выбранной группе процессов и подтвердить выход; ожидание `ok` требует независимого наблюдения убийства на этом номере |
| `@io-error <process> <calls> <K> <errno> <trigger>` | перебрать те же номера; на входе выбранного вызова подавить его исполнение и вернуть вызывающему выбранную ошибку без эффекта этого вызова; ошибка однократная, до следующих шагов её снять; ожидание `ok` требует независимого наблюдения подавления и возврата ошибки, а также исхода триггера ниже |

**Аргументы.** `<process>` — `store` или `store@<id>`, существующее имя хранилища стенда. `<calls>` — непустой набор через запятую без повторов и пробелов: `rename`, `fsync`, `write` для `@crash`, `fsync`, `write` для `@io-error`. `<K>` соответствует `^[1-9][0-9]*$`. `<errno>` — ровно `EIO` или `ENOSPC`. `<trigger>` — один строгий объект JSON, ровно одной из форм:

- `{"request":"<request>","expect":"<expect>"}`: исполнить существующий запрос словаря с его обычным ожиданием. Он обращается к выбранному хранилищу или запускает локальную операторскую команду для этого остановленного хранилища. Вложенный перебор, другое хранилище, пустые request/expect или изменение под `@until` — ошибка данных. request и expect — непустые строки без NUL, TAB, CR и LF; повторные поля и нечисла JSON запрещены. Объект JSON занимает остаток ячейки request; пробелы внутри его строк — обычное содержимое.
- `{"checkpoint":{"request":"<request>","expect":"<expect>"}}`: для выбранного работающего хранилища вызвать обязательную команду профиля `stand.checkpoint`. При её значении строка `none` вместо неё исполнить вложенный обычный запрос записи с его ожиданием. Запрос замены и ожидание проверяются и при наличии команды; они пишут через дверь выбранного хранилища. Реализация не выбирает фазу или имя файла.

**Привязка checkpoint.** `stand.checkpoint` — непустая команда оболочки, которая принудительно сохраняет текущее состояние, ждёт завершения и выходит с кодом 0 только после успешных барьеров долговечности; либо ровно строка `none`, если у реализации нет checkpoint.

Команда получает `{data}`, `{dir}`, `{socket}`, `{id}`, `{tls}` выбранного экземпляра; dir — каталог хранилища, data — каталог платформы. Без TLS значение tls пустое. Рабочий каталог профиля и окружение стенда обычные. `none` — объявление, его не исполняют как команду.

Отсутствующая команда — неполный профиль: выбранная цель `blocked` до исполнения, даже при флаге реестра `optional`. При отсутствующей команде нет перехода в `MissingBinding` или `not_executed`. Объявление ОБЯЗАНО описывать настоящую реализацию; `none` не отключает наблюдение и не пропускает записи её журнала.

**Счёт.** Установить наблюдатель до запуска триггера; обнулить счётчик на этой границе, после завершения префикса сценария. Считать только операции над обычными файлами и каталогами внутри каталога выбранного хранилища по разрешённым путям и дескрипторам, включая файлы, которые затем переименованы или удалены. Записи в сокеты, stdout, stderr и посторонние файлы не считать.

Наблюдать все потоки и потомков команды хранилища; для локального операторского триггера — операторскую команду с exec, а не остановленный демон. Помощник checkpoint тоже наблюдается, но его записи в сокет не считаются.

Упорядочить остановки на системных вызовах и записать единый порядок всех потоков. Привести `rename`, `renameat`, `renameat2` к `rename`; `fsync`, `fdatasync` — к `fsync`; `write`, `writev`, `pwrite64`, `pwritev`, `pwritev2` — к `write`.

Номер общий для объединения названных семейств. Для аварии считать успешные выходы; для ошибки — входы вызовов к выбранному объекту хранения. Наблюдатель записывает исходный вызов и семейство. Фаза не выводится из пути кандидата, исходного кода, сообщения журнала или счётчика.

**Перебор и изоляция.** Сценарий — конечное семейство испытаний, а не последовательная порча одного каталога. Для каждого перебора сначала найти достижимые номера без его сбоя, но с уже выбранными предыдущими сбоями. Исполнить этот префикс и триггер на новом стенде с новыми привязками; потребовать обычного ожидания триггера, для команды checkpoint — код 0. Записать трассу, взять номера `1..min(K,C)`, где C — наблюдавшееся число вызовов; если C больше K, записать непроверенный остаток. Ни одного подходящего вызова — отказ `stand`, а не пустой GREEN. Номер больше C отсутствует, это не успешное внедрение.

Затем для каждого выбранного номера повторить сценарий с начала на новом стенде, внедрить сбой и исполнить суффикс. При нескольких переборах исполнить произведение достижимых номеров; каждый последующий перебор исследовать при каждом предыдущем префиксе со сбоем. Между испытаниями не переносятся счётчики, связанные версии, каталоги и процессы; копирование живого каталога не является сбросом. Выбранный номер не достигнут в своём испытании — `stand`.

В отчёте каждого испытания остаются шаг, строка источника и кортеж номеров. Исходный шаг совпал только при совпадении во всех испытаниях, где он исполнялся; отказ подготовки прерывает зависимые шаги этого испытания. Успех сценария требует успешного исследования и всех необходимых испытаний, а не только последнего.

**Исход триггера.** При исследовании триггер должен совпасть со своим обычным ожиданием. При аварийном испытании ожидаемый SIGKILL заменяет только обычный исход прерванного триггера; код отказа, закрытый сокет и тайм-аут не доказывают убийства. Суффикс начинается после выхода всей выбранной группы команды.

При испытании с ошибкой запрос, включая замену при `none`, должен совпасть с заданным ожиданием по обычным правилам ответа; настоящая команда checkpoint после доказанного сбоя может штатно выйти с ненулевым кодом. Авария, тайм-аут, сломанный ответ или неожиданный выход обслуживающего хранилища остаются отказом реализации. До последующих шагов сценария ошибка снимается, наблюдатель отключается. Операции моделируют отказ процесса или ошибку системного вызова; они не доказывают потерю грязных страниц ядра или долговечность при физическом отключении питания.

**Независимые доказательства и контроли.** До оценки проверить наблюдатель и внедрение на собственных временных файлах/процессах судьи: верный и чужой процесс/объект, нулевой и единичный эффект, приведение исходных вызовов, края номеров, все потоки, успешные и неуспешные вызовы, оба номера ошибки, подавленная запись с неизменными байтами, авария с доказанным статусом wait. Включить неактивный/пустой контроль и устаревший номер; внедрение ошибки должно оставить побочные эффекты выбранного вызова отсутствующими.

Невозможность наблюдать, внедрить, подтвердить или убрать — `stand`; неверный селектор или триггер — `data`. Нет возможности наблюдать вызовы — отказ стенда, а не отказ кандидата или успешный неисполненный случай.

Сохранить имена процесса/группы и объекта хранения, монотонные границы, исходный вызов, номер, результат/ошибку и доказательства kill/wait, скрыв секреты. ACK профиля, выход помощника, строка EIO и настроенный хук сами по себе ничего не доказывают.

Разделение привязки и независимо наблюдаемого эффекта такое же, как у [привязок доказательств стенда](seams.md#тестовые-привязки-доказательств-d7); эти директивы не требуют дескриптора D7. Бюджеты конечны по общим правилам стенда; превышение не даёт GREEN.

## Удержание соединений

| Форма | Определение | Пользователи |
|---|---|---|
| `@hold <дверь> <N>` | открыть N соединений с дверью и ничего в них не писать; судья держит свои сокеты открытыми до конца сценария, затем закрывает. Ожидание `ok` — независимое наблюдение Linux сопоставило каждому клиентскому сокету живой принятый серверный сокет в открытом дескрипторе группы процесса, которому принадлежит дверь; все N живы одновременно в пределах срока готовности. Соединения в очереди не учитываются | P/01, P/03 |

Для `@hold` раннер записывает идентичности своих N клиентских сокетов и наблюдает их серверные пары по метаданным сокетов Linux и открытым дескрипторам группы процесса — владельца двери: хранилища для дверей хранилища, именованного воркера для `worker <имя>`. У Unix-сокета раннер получает inode клиента, находит inode его пары через диагностику Unix-сокетов и подтверждает открытый дескриптор этой пары в группе процесса. У TCP-сокета он сопоставляет локальный и удалённый адреса и порты и подтверждает открытый дескриптор принятого серверного сокета в той же группе. Сокет в очереди слушателя не имеет такого принятого дескриптора. Успешный `connect` или сон не доказывает приём. Наблюдение не требует внутреннего счётчика соединений или новой двери реализации.

Срок готовности — строка `@hold` [сроков стенда](README.md#словарь-директив-и-дверей). Это один монотонный интервал от первой попытки открыть клиентское соединение до подтверждения всех N одновременно живых серверных сокетов, не позже границы срока. Открытие или повтор другой попытки не сбрасывает интервал; отдельного срока на соединение нет.

Раннер записывает закрытия, перепроверяет удерживаемый набор перед каждым зависимым шагом и наблюдает его до конца шага. Если удерживаемый сокет закрылся либо независимое наблюдение стало недоступно или ошиблось, пока команда владельца двери жива, результат — `stand`: доказательство предусловия потеряно. Это действует до и во время зависимого шага, включая закрытие по объявленному сроку простоя; код ответа или тайм-аут уже выполняемого HTTP-шага при потерянном предусловии не становится ошибкой `implementation`. Текущий шаг получает `stand`, сценарий заканчивается, последующие шаги не выполняются по общему правилу прерывания сценария. Закрытия от явной директивы остановки — её эффект и не отменяют ранее успешную подготовку. Независимо доказанный неожиданный выход или сигнал команды владельца двери остаётся ошибкой `implementation` по правилу отказа команды.

Объявленные реализацией сроки простоя действуют. `@hold` их не проверяет, не задаёт нижнюю границу, не отключает таймер, не пишет в удерживаемые сокеты и не открывает закрытые сокеты заново для поддержания жизни. Недоступное или ошибочное независимое наблюдение даёт `stand`. Только когда наблюдение работает, ни один удерживаемый сокет не закрылся и ошибок наблюдения нет, отсутствие подтверждения всех N живых принятых сокетов к сроку готовности даёт `implementation`. Потеря удерживаемого сокета или наблюдения имеет приоритет над истечением срока готовности.

## Вердикты загрузчика

Опись строк, включая диагностические подсказки: [P/AC-R008](spec/acceptance.norms.md#n14-вердикт-цели); классы отказов: [P/AC-R024](spec/acceptance.norms.md#n4-отказы).

Слово `verdicts` исполняет `verdicts.tsv` первого каталога вместе с лежащими рядом `classes.tsv` и `diagnostics.tsv`. Правила, по которым ставится вердикт, — нормы владельца цели (P/02.1 N1, N4); эта форма говорит только, как исполняется строка и что наблюдает судья.

- **`verdicts.tsv`.** Строка — `case<TAB>verdict`. Вход — файл `cases/<case>.subsystem.yaml`, загружаемый один, без каталога других манифестов. `verdict` — `ok` (манифест загружается) или `refused` (отказ загрузки). Набор файлов `cases/` равен набору строк; лишний файл или лишняя строка — ошибка данных.
- **Вызов.** Судья загружает каждый файл через интерфейс цели. У команды `stand.load` подстановка `{file}` — путь файла. Код выхода 0 — манифест. Выход с другим кодом, не по сигналу, у которого stdout или stderr содержит имя файла `<case>.subsystem.yaml`, — отказ. У адаптера `load` ([загрузчик манифеста](PROFILE.md#загрузчик-манифеста)) ответ `verdict` — `ok` или `refused`; отказ — `refused`, чей `text` содержит имя файла. Всё прочее — несовпадение строки: смерть по сигналу, отказ, не называющий файл, сломанный ответ адаптера.
- **Вердикт.** Он строгий: `ok` совпадает только с манифестом, `refused` — только с отказом.
- **`classes.tsv`.** Строка — `case<TAB>class`, где `class` — `text`, `form`, `relations` или `catalogue`. Её `case` имеет `refused` в `verdicts.tsv`. Текст отказа содержит слово `refused:<class>` класса случая и ни одного другого слова `refused:<word>`; иначе строка случая — несовпадение.
- **`diagnostics.tsv`.** Строка — `case<TAB>paths<TAB>lines`. Её `case` встречается один раз и имеет `refused` в `verdicts.tsv`. `paths` — JSON-массив путей, каждый — массив имён ключей и индексов списков; `lines` — JSON-массив номеров строк с 1. Строка — подсказка, а не проверка. Судья ищет каждый путь в тексте отказа в форме `keys.path_style` профиля: `json` — текст JSON-массива, `dotted` — имена через `.`, индекс как `[N]`. Каждый номер строки он ищет десятичным словом. Ненайденное он пишет в отчёт, без отказа. Лишние пути в тексте не наблюдаются.

Прогон этих файлов через `manifest put` в это слово не входит; такая выборка пишется строками [последовательностей установок](#последовательности-установок).

## Последовательности установок

Слово `puts` исполняет `puts.tsv` первого каталога и файлы столбца `tables` строки маршрута, все по этой форме. Строка — последовательность установок манифестов в одно свежее хранилище.

**Форма таблицы.** UTF-8, строки разделены LF, ячейки — TAB. Первая строка, не являющаяся заметкой, — заголовок. Он выбирает столбцы: `case<TAB>puts<TAB>expect`, `case<TAB>puts<TAB>expect<TAB>canonical` или `case<TAB>puts<TAB>expect<TAB>canonical<TAB>ceiling`. Затем по строке на случай ровно с ячейками заголовка.

- `case` — имя случая, `[a-z0-9_]+`, уникальное в файле.
- `puts` — слова через один пробел, по порядку: имена файлов и директивы ниже. Имя файла `<file>` — файл `puts/<file>.subsystem.yaml` первого каталога. Файл идёт первым и последним.
- `expect` — `<code> <rev>`, затем по желанию `@stderr`. `<code>` — код возврата **последней** установки, `0` или `2`. `<rev>` — десятичный `rev` строки `platform/manifest/<name>` после неё, где `<name>` — `name` последнего файла; `-` — строки нет.
- `canonical` — имя случая пакета векторов объявления `# canonical:`. Байты его файла `expect/<canonical>.json` — ожидаемое поле `manifest` строки вида; `-` — строки вида нет.
- `ceiling` — потолок строки хранилища этой строки, его `{row_ceiling}`.

**Объявления.** Две строки-заметки — объявления таблицы:

- `# canonical: <directory>` — пакет векторов, чьи файлы `expect/<case>.json` дают байты столбца `canonical`. Таблица со столбцом `canonical` без этого объявления — ошибка данных.
- `# beside: <directory>` — всё содержимое каталога лежит, под теми же путями, рядом с рабочими копиями каждой установки каждой строки.

Путь объявления — от корня спецификации. Он называет каталог строки маршрута цели; другой каталог — ошибка данных.

**Имена.** `<name>` файла — значение его ключа верхнего уровня `name`, прочитанного как YAML. Директива берёт `<name>` файла перед ней.

**Исполнение.** Строки независимы; их порядок не важен. Для каждой строки судья берёт новое пустое хранилище и новый рабочий каталог. Хранилище запускается командой хранилища цели, без файла прав; `{row_ceiling}` — ячейка `ceiling`, а без этого столбца — потолок строки [параметров каждого экземпляра](../../../01-store/ru/acceptance/1/README.md) P/01.1, 524288 байт. Затем судья исполняет `puts` по порядку. Файл копируется в рабочий каталог под своим именем и ставится отдельным вызовом команды `manifest-put` цели, с `{socket}` и `{file}` — рабочей копией. Директива исполняется по своей строке ниже. Каждая установка, кроме последней, MUST вернуть `0`, и каждая директива MUST пройти; иначе случай — несовпадение (подготовка не удалась).

**Сравнение.** После последней установки судья сравнивает:

1. код возврата с `<code>`;
2. при коде, отличном от `0`: stderr содержит имя файла последней установки и каждую подстроку `@stderr`;
3. `rev` строки `platform/manifest/<name>` с `<rev>`: строка читается `GET /v1/get?key=platform/manifest/<name>` через `{socket}`, поле `rev` в `items`; `-` — `items: null`.

Со столбцом `canonical` судья ещё сравнивает:

4. метку `platform/manifest/<name>/rev`. При коде `0` её `rev` — `<rev>`, а её `sha256` — `sha256` строки; при `-` метки нет. При другом коде метка байт в байт та, что была до последней установки: отказанная установка её не трогает;
5. строку вида `platform/manifest/<name>/canonical/1`, её `items` по кодеку [семьи `canonical-row`](../../../02-installer/data/canonical-row.schema.json): `form` — `"1"`, `rev` — `<rev>`, `sha256` — `sha256` строки, `manifest` — байт в байт байты `expect/<canonical>.json`. Прочие поля не сравниваются. При `canonical` = `-` строки вида нет.

Без столбца `canonical` метка и вид не сравниваются. Порядок записей во времени и повтор вида после конфликта `cas` не сравниваются; они проверяются чтением.

**Строка с `ceiling`.** До случая судья подтверждает потолок нового хранилища. `GET /v1/status` даёт `max_value` = `ceiling`. `put` через `{socket}` строки `acceptance/ceiling` с `items` веса ровно `ceiling` проходит; на байт больше — `413 toolarge` с `limit` = `ceiling`. Затем судья удаляет строку. Вес — по P/01.1 N1. Если судья не может подтвердить потолок, строка — `not_executed` с причиной `installer_ceiling_unproven`.

**Слова `puts` и `expect`.** Директивы пишут через `admin.sock` экземпляра, то есть `{socket}`, операциями P/01.1. Директива, которая не прошла, проваливает подготовку своей строки.

## Варианты прав

Слово `variants` исполняет каждый каталог `variants/<variant>/` первого каталога. Вариант выводит права по смыслу на каталоге манифестов вне стенда. В его каталоге — файлы `*.subsystem.yaml` (каталог манифестов варианта) и ровно одно из: `expect.tsv`, `refused` или `check.tsv` с каталогом `check/` (только для судьи: каталоги вариантов — данные приёмки судьи). Каталог без них или с несколькими — ошибка данных. Опись — физические строки `expect.tsv` и `check.tsv` и единственная строка `refused` (только для судьи: файлы вариантов).

**`expect.tsv`** (только для судьи: файл вариантов). UTF-8, LF, ячейки разделены TAB, строки с `#` пропускаются. Заголовок — `role<TAB>action<TAB>key<TAB>expect`; затем по строке на пробу: роль файла прав (P/01.2 N1.1), действие `read`, `write` или `delete`, ключ строки и `allow` или `deny`. Для варианта судья:

1. вызывает команду вывода прав цели, `stand.rights`, с `{manifests}` — каталогом варианта, `{deployment}` = `dep` и `{file}`. Код, отличный от `0`, — несовпадение каждой пробы варианта;
2. запускает свежий экземпляр хранилища с этим файлом как `{rights}`;
3. для каждой строки вызывает через сокет роли: `read` — `GET /v1/get?key=<key>`, `write` — `put` с `items: {"p": "1"}`, `delete` — `delete`, без `cas` и без охраны. `allow` — только подтверждённый успех: для чтения 200 формы `Row` (для отсутствующей строки `{items: null, index: ""}`, P/01.1 N2), для записи и удаления 200 `Written`. `deny` — 403 `forbidden`. Роль без сокета — то же, что 403 (роли нет в файле, P/01.2 N1.3). 5xx, ошибка транспорта или иной ответ — неопределённый исход: проба ни `allow`, ни `deny` и не совпадает.

Порядок строк не важен. Так проверяется смысл файла прав (P/01.2 N1.3 и `never`), а не его байты: порядок шаблонов, `comment`, лишние равносильные шаблоны и группы не сравниваются.

**`refused`.** UTF-8, LF, строки с `#` пропускаются; ровно одна другая строка — `name` манифеста варианта, чьё объявление отвергается. Судья вызывает `stand.rights`, как в п. 1. Код MUST быть `2`, файла по пути `{file}` нет, и stderr называет этот манифест — его `name` или его файл. Остальной текст не сравнивается. Хранилище не запускается, проб нет.

**`check.tsv`.** UTF-8, LF, ячейки разделены TAB, строки с `#` пропускаются. Заголовок — `case<TAB>file<TAB>code`; затем по строке на случай: `case` — `[a-z0-9_]+`, уникальное; `file` — `check/<case>.rights`, файл прав; `code` — `0` (файл по смыслу равен выведенному) или `!0` (любой код, кроме `0`). Для каждой строки судья вызывает команду сверки прав цели, `stand.rights-check`, с `{manifests}` — каталогом варианта, `{deployment}` = `dep` и `{file}` — `check/<case>.rights` и сравнивает её код с `code`. Профиль без `stand.rights-check` оставляет каждую строку `not_executed` с причиной `installer_rights_check_missing`.
