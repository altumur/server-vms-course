13 сценариев / 201 шаг. Воркера играет раннер: сценарию нужно держать запрос открытым, видеть, что дошло до воркера, и звать консоль обратно с билетом и листом, а тестовый воркер реализации этого не даёт и проверял бы сам себя. Манифесты — [`probe-p`](../../../acceptance/pass/probe-p.subsystem.yaml) и дверь первого вида [`probe-f`](../../../acceptance/pass/probe-f.subsystem.yaml) (сц. 10; только для судьи: манифесты стенда), комплекты сц. 08 — [`stand.json`](../../../acceptance/pass/stand.json) (только для судьи: описание комплектов) в форме [TLS-стенда](../tls/README.md), с одним новым полем: `server` листа в `negative` — лист с иным именем сервера. Обратный вызов с листом идёт на отдельный слушатель консоли, подстановка `{cport}` ([подставной воркер](#подставной-воркер-передачи-второго-вида)).

Чтением, с причиной: сокет чужой роли — стенд ставит одну подсистему с `door.pass.calls`, сокета другой роли нет (лист чужой роли — сц. 08); break-glass и отладочная личность — тот же шаг 3 порядка `ticket`, что сц. 04; запрос по куке стенд не ведёт. Маршрут двери подсистемы ([P/06.3](../../../../06-console/ru/spec/06.3-console.norms.md) N1.9) — подставной воркер держателем не служит. `X-W2C-Loopback` без петли и `PASS_STREAMS_MAX` — все клиенты стенда на петле, 256 потоков TSV не откроет. `PASS_TICKET_CHECK` — только верхней границей шага 16 сц. 05. Дверь воркера с листом `console` и клиент SDK — P/03.4-15, тест реализации: подставной воркер их не проверяет.

## Исполнимость

У раннера есть директивы словаря, дверь `socket`, подстановка `{cport}`, ключ `keys.pass_stand`. Правило то же, что у [системной приёмки](../system/README.md): в выпуск раннера сценарий идёт только после прогона против реализации, каждый красный шаг разбирается вопросом «норма или данные», а новые сценарии входят в пин линий только выпуском раннера.

## Сроки

`probe-p` объявляет `wait: {api/x: 300}`: запрос сценария держит билет живым, предел не маскирует проверки отзыва и выключения (`PASS_WAIT` 5 с снял бы билет сам). Поток переживает `PASS_WAIT`, у потока предела нет.

## Подставной воркер передачи второго вида

Директивы этого стенда. Раннер их исполняет (раздел [Исполнимость](#исполнимость)). Воркера играет раннер: так сценарий держит запрос открытым и видит, что дошло до воркера. У директив `<кластер>` стоит на стенде домена, на стенде консоли его нет.

| Форма | Смысл | Урок |
|---|---|---|
| `@pass-worker [<кластер>] <sub> <имя> [kit=<лист>]` | раннер слушает дверь на петле (без `kit` — `url` равен `http://127.0.0.1:<порт>`; с `kit` — https с серверным листом `<лист>` комплектов `@tls-setup`: хост `url` — имя сервера комплекта, цепь — лист и `ca.pem` кластера листа; кластер вместо имени листа — лист `<кластер>-<sub>worker`); при замене воркера того же имени раннер ждёт, пока проба `GET /<sub>/api/x` через консоль придёт на новый слушатель: `url` выдачи не называют, пишет и освежает объект `<sub>/heartbeats/<name>` с `worker`, `url` этой двери, как живой воркер с дверью; принятый запрос держит открытым; ожидание `ok` — консоль видит его живым. Прежний воркер `<имя>` останавливается | P/06 |
| `@pass-open <метка> <дверь> <запрос>` | запрос к консоли фоном, под меткой; `POST` без `Idempotency-Key` получает ключ по правилу `@key`; ждёт, пока подставной воркер его примет. Ожидание `ok <JSON>` — принятое подмножеством: `{method, path, query, body, ticket, headers}`, `ticket` — значение `X-W2C-Pass-Ticket`, отсутствие заголовка — `@absent`; не дошло — ответ клиента, форма `<код> <JSON>` | P/06 |
| `@pass-answer <метка> <код> <Content-Type\|-> [<тело>]` | воркер отвечает на запрос метки: статус `<код>`, `Connection: close`, `Content-Length` кроме 204, `Content-Type`, если не `-`; ожидание — ответ клиенту, формы словаря | P/06 |
| `@pass-chunk <метка> <текст>` | воркер шлёт часть потока: статус 200, `Content-Type: text/event-stream`, кодировка chunked, каждая часть — текст и пустая строка; ожидание `<код> ~<текст>` — клиент уже получил её, ответ ещё открыт | P/06 |
| `@pass-result <метка>` | ответ клиенту без действия воркера: сторона воркера молчит; ожидание — формы словаря | P/06 |
| `@pass-abort <метка>` | клиент рвёт соединение; ожидание `ok` — воркер увидел закрытие | P/06 |
| `@pass-closed <метка>` | консоль закрыла соединение клиента не позже `PASS_TICKET_CHECK` + 30 с; ожидание `ok` | P/06 |
| `@pass-fill <кластер> <sub>` | открывать запросы `GET /<sub>/api/x` к маршруту, пока консоль не ответит 503 `busy`; они живут до конца сценария; ожидание `ok` | P/06 |
| `@pass-seen <имя>` | сколько запросов принял подставной воркер, без проб замены воркера; ожидание `ok {"requests": N}` | P/06 |
| `@pass-call <клиент> <запрос>` | одна проба двери `callback <кластер>`: слушатель обратного вызова, адрес — `X-W2C-Pass-Console` последнего `@pass-open`, порт — `{cport}`; клиент — лист `stand.json` (только для судьи: описание комплектов) или `null`, исход — закрытая форма `@tls`, с подстановками `$name` | P/06 |
| `@pass-step <метка> [<имя>]` | ждать вызов шага операции на подставном воркере (маршрут `door.pass.operations.step`, [P/06.9](../../../../06-console/ru/spec/06.9-console.norms.md) N2; вызов узнаётся по пути: без начальных и конечных `/` путь равен маршруту, запрос не учитывается) и держать его: не дольше 40 с (`OPS_STEP_WAIT` + 2 × `OPS_TICK`). Ожидание `ok <JSON>` — принятое подмножеством `{method, path, ticket, headers, id, index, body, secret, expected, opcount}`, `secret` без значения — `@absent`. `@pass-open` вызовы шага не берёт, `@pass-seen` считает всё принятое | P/06 |
| `@pass-step-answer <метка> <код> <Content-Type\|-> [<тело>]` | ответить на вызов шага; ожидание `ok`. Тело ответа консоль не читает | P/06 |
| `@pass-step-none <имя> <с>` | за срок вызова шага не пришло; срок считается сном: README урока называет причину; ожидание `ok` | P/06 |
| `@pass-step-drop <метка>` | оборвать вызов шага без ответа: потерянный ответ, `OPS_STEP_TRIES`; ожидание `ok` | P/06 |

**Сроки подставного воркера.**

| Что | Срок |
|---|---|
| `@pass-open`: подставной воркер принимает запрос | 30 с |
| `@pass-worker`: консоль видит воркер живым | 30 с |
| пульс подставного воркера | каждые 5 с |
| `@pass-answer`, `@pass-result`: ответ клиенту | читается в пределах 120 с, судится в пределах 180 с |
| `@pass-chunk`, `@pass-abort`, ответ на запрос `@pass-fill` | 30 с |
| `@pass-fill` | не больше 4096 запросов; предел, достигнутый без `503` `busy`, — сбой стенда, не исход реализации |

Подстановка `{cport}` — порт слушателя обратного вызова консоли: стенд ставит `CONSOLE_CALL_PORT={cport}` у консоли с комплектом (договор файла окружения). Профиль консоли объявляет `keys.pass_stand: 1`; без него проверки этого стенда не исполнены (не GREEN). Без комплекта подстановки нет: слушатель не открывается.

Дверь `socket [<кластер>[#<n>]] <роль>` — запрос на сокет роли воркера к консоли `<PLATFORM_DIR>/run/console/<роль>.sock`, по той же форме запроса ([P/02.5](../../../../02-installer/ru/spec/02.5-installer.norms.md) N1.5); `#<n>` — копия консоли `console#<n>`, без номера — первая.
