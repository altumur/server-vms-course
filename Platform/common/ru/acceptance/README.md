# Стенд приёмки модуля «Платформа», M10 и M11

Текст производный от `acceptance/README.md`, руками не правится: источник — английский [`acceptance/README.md`](../../acceptance/README.md), правка идёт в него, русский пересобирается переводом (ADR-0121; ADR-0124 доп. (1) п. 4).

## Стенд — общий для приёмки уроков модуля «Платформа», M10 и M11

Раннер приёмки любого урока M10 запускает реализацию только через интерфейс, который реализация называет
в описании (нормы P/01.1, «Решает реализация» п. 10); её внутреннего API раннер не знает.

### Пример состава

Следующий `assembly.yaml` — схематический полный состав Platform, не поставленные профили или код реализации. Значения `example/…/acceptance.yaml` — условные пути относительно состава; замени их настоящими местами профилей. `modules` — карта канонических идентичностей модулей (имён каталогов уроков) в пути файлов профилей, а не список записей модулей.

```yaml
format: 1
modules:
  01-store: example/01-store/acceptance.yaml
  02-installer: example/02-installer/acceptance.yaml
  03-worker: example/03-worker/acceptance.yaml
  04-controller: example/04-controller/acceptance.yaml
  05-resource: example/05-resource/acceptance.yaml
  06-console: example/06-console/acceptance.yaml
  07-console-module: example/07-console-module/acceptance.yaml
  08-domain: example/08-domain/acceptance.yaml
  09-agent: example/09-agent/acceptance.yaml
  10-domain-console: example/10-domain-console/acceptance.yaml
```

Состав использует `format: 1`; каждый выбранный `acceptance.yaml` — `format: 2` профиля. В [форме состава](PROFILE.md#состав-и-идентичность-входов) только `format` и `modules`, без корневых сборки, команд, ключей или наследуемых умолчаний. Частичная карта допустима для подготовки, но цель с отсутствующим обязательным модулем блокируется до исполнения. Эти пути не объявляют поставленный backend, provider или успешный прогон.

### Раскладка по процессам (стадия C)

Реализация использует один микромодуль на процесс. Полные общие формы `acceptance.yaml` (версия профиля 2),
`assembly.yaml` (версия состава 1), подстановок, исполняемых адаптеров и конверта векторов определены один раз в
[«Профили приёмки и состав»](PROFILE.md). Следующие разделы назначают интерфейсы стенда для уроков.
Профиль описывает эти интерфейсы; сценарии и ожидания этим не меняются.

- **Профиль на микромодуль.** `acceptance.yaml` лежит в каталоге модуля; `module` — каталог урока из
  [`Platform/lessons.tsv`](../../../lessons.tsv) (`01-store` … `10-domain-console`); у профиля своя сборка (`build`),
  необязательные свои регрессии (`unit`), свои команды и адреса стенда (`stand`), ключи (`keys`), адаптеры (`adapters`) и
  публичные результаты сборки (`artifacts`). Профиль называет только свои команды — команды соседнего процесса в нём нет.
  Шаблоны команд ниже («Команда запуска», «Команда установки манифеста», команды векторов и директив) — ключи `stand`
  профиля процесса-владельца.
- **Состав стенда.** Корневой `assembly.yaml` (`format: 1`, `modules`) — только карта «модуль → файл профиля», без
  корневых команд и общей сборки. Стенд берёт соседей из этого состава; замена части (`--part`) переносит её профиль
  целиком — каталог, ключи, команды. Нужной части нет в составе — ошибка состава до запуска, не подмена соседом.
- **Рабочие каталоги и фазы.** Каждая команда исполняется из каталога своего профиля. Сборка — отдельная фаза до
  фиксации входов; во время приёмки пересборки нет. Профили, исходники и артефакты частей стенд фиксирует в паспорте
  прогона. Совпадающие имена алгоритмов у разных потребителей (`said-id`, `fresh-age`) — команды каждого потребителя,
  не одна общая.
- **Словарь стенда прежний.** Подстановки (`{data}`, `{socket}`, `{rights}`, `{port}`, `{rport}`, `{manifest}`,
  `{manifests}`, `{name}`, `{agent_tokens}` и прочие ниже), окружение процессов (`PLATFORM_DIR`, сокеты ролей, кольцо,
  `MANIFEST_DIR`, общий каталог местных дверей токенов) и директивы задаёт стенд по этому README и lifecycle уроков.
  Поля профиля не становятся переменными окружения процессов, HTTP-дверями или иным способом связи модулей.
- **Библиотеки.** P/03 — свой SDK воркера и тестовый воркер профиля 03 (команда `worker`); P/07 — упаковка опубликованных
  `console.*` сборкой профиля 07, без своего процесса и своей TSV-приёмки: сборки 06 и 10 берут эти байты до фиксации
  входов, процесс консоли каталог выгрузки во время работы не читает (lifecycle P/06); ретранслятор P/09.2 — режим
  агента того же модуля 09 (`RELAY=1`), не отдельный профиль.
- **Векторы.** Команда пакета векторов — исполняемая обёртка своей функции процесса-владельца по README пакета; формы
  входа и выхода задаёт README пакета (у `creates-key` и `near-of` — сырой id в stdout, их README «Команда стенда»).
  `expect`, который README пакета сравнивает подмножеством полей вывода, читает `{}` как строка `<код> <JSON>` словаря
  ниже: `{}` на любом уровне — ровно пустой объект; любой объект — `@any`; поля нет — `@absent`; у пакетов, которые
  сравнивают вывод целиком, `{}` и так ровно пустой (ACC-EMPTY-OBJECT-02, решение «Архитектора» 2026-10-26).
  Пакет без отдельного договора команды (раздел README пакета «Команда стенда» или строка команды ниже): вычисленный
  исход функции — нативный код 0 и одно значение JSON; маркеры отказа `@refuse`, `@bad`, `@skip` — строки JSON того же
  написания; положительное значение не JSON (hex ключа, имя, слово) — строка JSON; опубликованный `@exit 2` — нативный
  код 2, вывод не судится. Явные команды `stand` и сырые id (`creates-key`, `near-of`) — без изменений (ACC-VECTORS-CONNECT-04,
  решение «Архитектора» 2026-10-26; строка «Нативный исход» в README пакетов с маркерами).
  Таблица, у которой README пакета не называет нативной формы: одна колонка ожидания (`expect` или иное имя) — значение
  этой колонки по правилу выше; две и больше — нативный код 0 и объект JSON, ключи — имена колонок ожидания таблицы,
  значения — по колонкам, как в TSV (`@absent` — ключа нет); какие колонки — ожидание, называет README пакета (решение «Архитектора» 2026-10-27).
- **Единая команда векторов.** Необязательная карта профиля `vectors` и полный провод входа/выхода определены в
  [«Профили приёмки и состав»](PROFILE.md#единая-команда-векторов). README пакета назначает потребителя, таблицы,
  входные колонки, фикстуры и направления; реализация вычисляет собственный нативный исход. Нет назначенной записи —
  `blocked`, не PASS. Покрытие использует полный SHA выгрузки и SHA таблицы; строка — адрес только внутри этого пина.

- **Команда запуска** — шаблон с подстановками: `{data}` — новый пустой каталог данных экземпляра; `{socket}` —
  путь сокета двери хранилища (P/01.1); `{port}` — порт HTTP консоли на петле (урок P/06 и приёмки со стендом консоли); `{manifest}` — каталог
  манифестов стенда для процессов, которым он нужен (`MANIFEST_DIR`, P/02.3); команда хранилища его не получает и манифестов не кладёт; `{body_limit}` и `{row_ceiling}` — предел тела и потолок строки (N5 P/01.1);
  `{rights}` — путь файла прав, который раннер кладёт до запуска хранилища (P/01.2 N1.2): в P/01.1 — файл ниже
  («Сокеты ролей»), в главах P/01.2 и P/01.3 — готовый вход [`01-store/acceptance/2/inputs/rights.json`](../../../01-store/acceptance/2/inputs/rights.json), в приёмках, перенесённых из M10/4–11, — вывод прав из манифестов стенда командой вывода прав ниже (`{manifests}` — каталог манифестов
  стенда, `{deployment}` = `dep`); команда хранилища получает `{rights}`, а не `{manifest}` (журнал cammeta-python, урок 11
  № 29). Реализация называет, какие подстановки нужны каждому её процессу.
- **Команда установки манифеста** `manifest-put` (P/02.3 N3 «Смена манифеста») — шаблон с `{socket}` и `{file}`: кладёт один манифест
  через `admin.sock` хранилища (`{socket}`); код 0 — положена, иной — отказ. Раннер ставит ею манифесты стенда по одной
  в порядке «Манифесты» ниже, после готовности хранилища и до первого `@start` (пилот хранилища, A6).
- **Команда вывода прав** (P/02.5 N2) — шаблон с `{manifests}` (каталог манифестов), `{deployment}` и `{file}`: пишет файл прав по
  P/02.5 N1.4; код 0 — файл записан, иной — отказ генерации. Реализация называет её в описании (P/02.5 «Решает
  реализация» п. 1). Варианты приёмки P/02.5 (`5/variants/`) зовут её с `{deployment}` = `dep` (сверка python и go
  M10/6–11).
- **Команда сверки прав** (P/02.5 N2 `--check`, N3 «установить») — ключ `stand.rights-check` профиля `02-installer`, шаблон с
  теми же подстановками, что у команды вывода прав (`stand.rights`): `{manifests}` — каталог манифестов, `{deployment}`, `{file}` —
  файл прав, который сверяется (не пишется); исход — код: 0 — файл по смыслу равен выводу прав из манифестов, иной — расходится.
  Варианты приёмки P/02.5 с `check.tsv` зовут её на каждый случай с каталогом манифестов варианта, `{deployment}` = `dep` и
  `{file}` = `check/<case>.rights`; код сравнивается с колонкой `code` (`0` | `!0`). Нет ключа в профиле — случаи `check.tsv`
  не исполнены (не GREEN и не исход реализации). Подстановки `{specs}` в словаре стенда нет (решение «Архитектора» 2026-10-30,
  вопросы норм аудита Gemini, P/02 п. 3; C02-RIGHTS-CHECK-STAND-01).
- **Команда кольца** — шаблон `ring {file}`: создаёт кольцо ключей по [договору запечатывания](../contracts/sealing.md) (`w2cctl secrets new` реализации, P/02.4 N1.9) в файле
  `{file}`; раннер зовёт её до первого процесса с `{file}` = `{data}/etc/secrets/platform.key` (решение «Архитектора»,
  второй пилот); код 0 — кольцо создано. Владелец и режим файла кольца на стенде — раздел «Стенд без root» ниже
  (I02-RING-FIXTURE).
- **Команды копии** (P/01.3 N1.3 `copy`, `admin_ops`): `backup` — шаблон с `{socket}` и `{file}`: копия хранилища через
  `admin.sock` в файл, код 0 — копия снята; `import` — шаблон с `{data}`, `{file}` и `{index_base}`: перенос копии в
  свежий каталог остановленного хранилища (P/01.3 N1.3 `box`), код 0 — перенесено, иной — отказ. Реализация называет
  обе (P/01.3 «Решает реализация» п. 4, 11; пилот хранилища).
- **Команда загрузки одного файла манифеста** (P/02.1) — шаблон с `{file}`; код выхода 0 — манифест, иной — отказ, текст
  отказа называет файл (нормы P/02.1, «Решает реализация» п. 3).
- **Процессы нескольких ролей** (урок P/03 и далее): реализация называет команду запуска каждой роли — хранилище,
  консоль, контроллер, воркер, позже ресурс; команда воркера получает имя подстановкой `{name}` (аргумент), окружение —
  `BOX_ID` (постоянная коробка стенда, `stand-box`) и `SERVER_NAME` (`srv-a` на стенде одного сервера; P/02.4 N1.2); из окружения имя воркер берёт только по `slot.name_env` своего манифеста
  (P/02.1 N1.2a), и раннер ставит эту переменную, если манифест её объявил (`testsub2` — `TALLY_NAME`; у `testsub` её нет). В приёмках, перенесённых из уроков до M10/6 (права — ныне P/01.2), раннер читает хранилище ролью с полными правами на префикс подсистемы.
- **Ресурс** ([P/05](../../../05-resource/ru/spec/05-resource.norms.md)): команда запуска ресурса сервера с подстановкой `{rport}` — порт его двери; раннер ждёт порт
  и строку `platform/doors/<host>` до первого шага. Сценарию, которому нужны пульсы других серверов, ресурс — на сервере
  контроллера: объекты кластера процесс читает через ресурс своего сервера (P/04 N3 «проход()» шаг 0; ADR-0084 доп. (2) R17).
- **Сокеты ролей** (P/01.2, P/01.3 N1.3 `sockets`): и на коробке хранилище открывает сокет на роль (`<роль>.sock`, `admin.sock`) по файлу
  прав; раннер звонит сокетом роли сценария. `{socket}` — путь `admin.sock`; сокеты ролей лежат рядом, в том же каталоге, плоско (P/01.3 N1.3 `sockets`).
  `{socket}` — дверь с полными правами (подготовка). Урок 1 прогоняет сценарии ролью `acc` — права read и write только на
  `acc/*`, сокет `acc.sock` рядом с `{socket}`. Раннер кладёт в `{rights}` ровно этот файл (форма — P/01.2 N1.2):
  `{"roles": {"acc": {"group": "acc", "read": ["acc/*"], "write": ["acc/*"], "delete": ["acc/*"]}}}`.
  Удаление — отдельное действие (P/01.2 N1.3 `allowed`), в файле оно названо явно.
  Хранилище готово, когда `admin.sock` и сокет `<роль>.sock` каждой роли его файла прав принимают соединение, в пределах срока из «Сроки стенда» (по умолчанию 15 с от старта; `@store-start` и `@server-start` — исключения, их строки называют свои сроки); без файла прав ждётся только `admin.sock`. Экземпляр, завершившийся раньше или не готовый к этому сроку, — неудавшийся старт; файл прав, который нельзя прочитать или в котором нет объекта `roles`, — сбой стенда.
  Стенд P/01.2 — это хранилище с готовым входом прав выше: установщика нет, манифест не кладётся.
- **Один каталог данных** `{data}` на экземпляр — это `PLATFORM_DIR` (P/02.4 N1.2 «Канал настройки и раскладка»;
  второй пилот, N-4). Стенд переводит подстановки в окружение P/02.4 N1.2: `PLATFORM_DIR={data}`,
  `PLATFORM_STORE=configstore://<сокет роли>`, `CONSOLE_PORT={port}`, `RESOURCE_PORT={rport}`, `BOX_ID`, `SERVER_NAME`,
  `SECRETS_KEY={data}/etc/secrets/platform.key` — кольцо по раскладке P/02.4 N1.1, его создаёт раннер командой кольца до первого процесса; имя воркера — аргументом `{name}`. Раскладка — по P/02.4 N1.2: хранилище
  `{data}/configstore`, объекты `{data}/objects`, события `{data}/events`, замки присутствия `{data}/events/.workers`.
  В составном стенде, где хранилище работает вместе с другими частями, команда запуска хранилища получает `-dir {data}/configstore`: в самом `{data}` лежат также кольцо и настройки, поэтому он не каталог хранилища. До первого старта хранилища стенд создаёт пустой каталог `{data}/configstore` с правами `0700`, как установщик на коробке ([P/02.4 N1.1](../../../02-installer/ru/spec/02.4-installer.norms.md#n11-процессы-и-юниты)), на стенде одного хранилища, на [стенде группы хранилища](#стенд-группы-хранилища) у каждого члена и на стенде трёх серверов; отсутствующий `-dir` демон не создаёт (решение «Архитектора» по P01.89.4).
  Корень событий сервера выводится однозначно — `{data}/events` его `PLATFORM_DIR` (стенд не задаёт `RESOURCE_ROOT` и
  `EVENTS`), поэтому отдельного ключа корня событий у «Стенда» нет.
  Файл настроек сервера — `W2C_ENV={data}/etc/w2c/w2c.env` (P/02.4 N1.2: каталог `roles/` — рядом с `w2c.env`,
  другого места нет), файлы ролей — `{data}/etc/w2c/roles/<роль>.env`; у сервера `on <сервер>` — тот же путь в его
  `PLATFORM_DIR` `{data}/servers/<сервер>` (выбор владельца раннеров, cammeta-acceptance e3ec5c3).
- **Манифесты** — файлы [`Platform/common/data/testsub/`](../data/testsub/README.md); стенд ставит их командой `manifest-put` в порядке зависимостей: `testsub`, затем `testsub2` (она ссылается на `testsub`: `about`,
  `near`, `worker.requests`); загрузка каталога (P/02.1 N3) видит обе.
  Манифест `testsub2` объявляет `console.shell` и `console.files`: установка читает эти файлы рядом с файлом манифеста (P/02.3 N3
  «Смена манифеста»), поэтому стенд кладёт рядом с копией манифеста всё содержимое
  [`06-console/acceptance/5/inputs/testsub2/`](../../../06-console/acceptance/5/inputs/testsub2) под теми же путями — на каждом стенде, где
  ставится `testsub2`, не только в приёмке 6.5 (ADR-0094 B7).
- **Корень консоли** (`CONSOLE_ROOT`) называет README урока: глава 6.2 — `testsub2` (короткие пути `/tallies`),
  остальные — `testsub`, вторая подсистема смонтирована под `/testsub2`.
- **Команда печати отчёта прохода** контроллера `<sub>/controller/pass` ([P/04](../../../04-controller/ru/spec/04-controller.norms.md)) — шаблон с `{data}` и `{sub}`;
  печатает текущий объект отчёта или ничего, если его нет; по ней раннер ждёт смены отчёта (нормы P/04,
  «Решает реализация» п. 9).
- **Команды векторов платформы** `order`, `shrink-victim`, `shrink-allowed`, `workers-script` (стадия A, A6; ADR-0084;
  `shrink-allowed` — решение «Архитектора» 2026-10-20, № 12 разбора ревью стадии B 3–5) — шаблоны с
  `{input}` — путь файла входа; вывод — JSON в stdout; код 0 — вычислено, 2 — вход не по форме. Пакеты —
  `Platform/04-controller/vectors/order/`, `…/shrink-victim/`, `…/shrink-allowed/` (P/04 N3 «нехватка(), заказать()», «сократить()»),
  `Platform/02-installer/vectors/workers-script/` (P/02.4 N1.5): раннер читает `cases.tsv` пакета (UTF-8, TAB, строки

### Стенд процессов testsub

Стенд ролевых процессов на одном сервере над манифестами стенда `testsub` и `testsub2`: одно хранилище, одна консоль и контроллеры, воркеры и ресурсы, которые запускают шаги. README урока, который пользуется этим стендом, ссылается на этот раздел и пишет только свою подготовку, роли и исключения. Раздел не вводит норм продукта.

- **Каждый сценарий на свежем стенде.** Перед первым шагом сценария судья останавливает все процессы предыдущего сценария и ждёт завершения каждого, в том числе прежней копии имени и процесса, который остановили и запустили снова; только после этого удаляет их состояние. Сценарий получает новый каталог данных `{data}` и новые порты, поэтому строк, объектов, событий, замков присутствия и кэшей предыдущего сценария не остаётся: новое хранилище с пустой памятью id, новая консоль без заявок POST, нет связанных имён `$name` и ключей повтора судьи. Судья запускает хранилище, ставит манифесты стенда с их служебными метками командой `manifest-put` в порядке «Манифесты» выше, затем запускает консоль; их двери готовы до первого шага. Подготовка не переносит состояние предыдущего сценария и не проверяет установщик. README урока, который сохраняет хранилище между сценариями одной таблицы, говорит об этом в своих границах (P/06.2).
- **Нет чужих процессов.** Нет контроллеров, воркеров, ресурсов, запасных процессов и таймеров старта, которых не запускают шаги сценария; роль, запущенную до первого шага, называет README урока (ресурс P/03.6).
- **Одна коробка.** У каждого процесса коробка стенда `BOX_ID` и `SERVER_NAME=srv-a`, кроме слов `on <сервер>` и `<ИМЯ>=<значение>` у `@start`; каждый запуск — новый экземпляр. Параметры и сроки манифестов стенда — значения манифестов: судья не ускоряет их ради теста.
- **Остановка.** `@sigterm` и `@sigkill` посылают сигнал группе процессов названного живого процесса сценария и совпадают с `ok` только после выхода всей группы, по N3.2 [норм](spec/acceptance.norms.md) (R017). Остановка с истёкшим сроком или имя, не называющее живого процесса сценария, — несовпадение шага, а не `ok`.
- **Время сценария.** README урока не задаёт бюджета сценария: бюджет — сумма ожиданий его шагов плюс запас судьи (N3.3, R036), и судья не заканчивает сценарий, пока ожидания его шагов не истекли.
- **Параллельные сценарии.** Сценарии, идущие одновременно, берут каждый свои каталоги данных и порты.

### Шапка таблицы и столбцы по имени

Правило действует для каждой TSV-таблицы, форма которой называет свои столбцы. Это реестры `forms/` урока и `common/acceptance/forms/` (среди них [реестр целей](forms/targets.README.md) и [`targets.routing.tsv`](../../acceptance/forms/targets.routing.tsv)), [`runner-targets.tsv`](../../acceptance/runner-targets.tsv), реестры векторов [`wire.tsv`](../../vectors/wire.tsv) и [`consumers.tsv`](../../vectors/consumers.tsv) и [таблицы команд](#таблицы-команд) `puts.tsv`, `expect.tsv` и `check.tsv`. Форма урока, которая называет свои столбцы, тоже следует правилу.

1. Таблица в UTF-8, строки разделены LF, ячейки — TAB. Пустые строки и строки, начинающиеся с `#`, — заметки, кроме объявлений, которые называет форма (`# cell-json:`, `# canonical:`, `# beside:`).
2. Первая строка, не являющаяся заметкой, — шапка. Каждая её ячейка — имя столбца, имя встречается один раз.
3. Читатель находит каждый столбец по его имени в шапке, никогда по позиции. Ячейка значит то, что значит имя её столбца в форме. Ни порядок столбцов, ни добавленный столбец не меняют смысла ячейки, потому что форма растёт столбцами (столбец `body` таблицы маршрутов), а читатель по позиции после такой правки прочёл бы чужую ячейку. Столбец, которого форма не называет, не читается и ошибкой не считается, если форма не закрывает свой список столбцов.
4. Каждая другая строка имеет ровно столько ячеек, сколько шапка.
5. Таблица вне этой формы — ошибка данных класса `data` (N4 [норм](spec/acceptance.norms.md), P/AC-R024) у каждой цели, которая её читает; она находится до запуска стенда. Вне формы: таблица без шапки, повторённое имя столбца, отсутствующий столбец, который форма требует (столбец её списка, если форма не делает его необязательным), и строка с другим числом ячеек. Такая таблица не считается ни сбоем судьи, ни исходом реализации.

**Позиционные формы.** Три формы задают ячейки позицией и остаются вне этого правила, потому что имена ячеек дают их собственные формы, а многие таблицы уроков записаны без строки шапки:

- форма сценариев: `scenarios.tsv`, `seams.tsv` и `forms/*.scenarios.tsv` — ровно четыре ячейки `scenario`, `step`, `request`, `expect` (строка `scenarios.tsv` в [словаре](#словарь-директив-и-дверей)); шапка может быть заметкой;
- [вердикты загрузчика](#вердикты-загрузчика) P/02.1: `verdicts.tsv`, `classes.tsv` и `diagnostics.tsv` с ячейками этой формы и без шапки;
- таблица случаев векторов, у которой ячейка `header` в `wire.tsv` начинается с `-`: строки шапки у неё нет, а имена после `-` называют её ячейки по позиции ([форма провода векторов](../vectors/wire.md)).

### Реестр целей и списки выгрузки, собранные из уроков

Реестр целей и оба фильтра выгрузки собираются каждый из общей части и частей уроков (ADR-0135 доп. (14)). Урок — каталог `Platform/NN-<процесс>/`. Выгрузка, `check_spec`, цикл и движок читают только собранный реестр и собранные фильтры, никогда — один общий файл или один файл урока.

1. **Реестр.** Общие файлы [`forms/targets.tsv`](../../acceptance/forms/targets.tsv) и [`forms/targets.routing.tsv`](../../acceptance/forms/targets.routing.tsv) содержат шапку каждой таблицы и, в заметках, смысл её столбцов ([реестр целей](forms/targets.README.md)); строк в них нет. Строки целей урока — в `forms/targets.tsv` и `forms/targets.routing.tsv` этого урока, ровно с шапкой общего файла; заметки допустимы ([шапка таблицы и столбцы по имени](#шапка-таблицы-и-столбцы-по-имени)). Собранная таблица — эта шапка, за ней строки уроков в порядке имён их каталогов, строки каждого файла в их порядке. `id` встречается в собранной таблице один раз, строка урока имеет `owner` этого урока, строка маршрута цели — в том же уроке, что и строка цели.
2. **Списки файлов урока.** Фильтр модели `Platform/common/export-model-filter.json` (M) и фильтр входа судьи [`judge-input-filter.json`](../../acceptance/judge-input-filter.json) (J) дают каждому файлу выгрузки одну запись: `path`, `disposition` и `basis`, по порядку `path`. Записи файлов урока — в его форме `forms/export.json`: JSON-объект ровно с полями `version` (целое `1`), `model` (записи M) и `judge` (записи J), каждый массив упорядочен по `path` как байтам UTF-8. Список называет каждый файл каталога своего урока, среди них `ru/` и `journal/`, один раз в `model` и один раз в `judge`, и никакого другого файла. Общий фильтр хранит записи файлов вне каталогов уроков и файлов урока без `forms/export.json`; у пути одна запись в одном месте.
3. **Общие правила списков.** В каждом уроке `forms/targets.tsv` — `model_and_judge` в M и `include` в J, как общая открытая таблица; `forms/targets.routing.tsv` — `judge_only` в M и `include` в J, как общая таблица маршрутов; `forms/export.json` — `judge_only` в M и `exclude` в J, как общие фильтры.
4. **Собранный фильтр.** Собранный фильтр M — общий фильтр M, у которого `files` — его собственные записи и записи `model` списков всех уроков, по порядку `path` как байтов UTF-8; остальные поля — как в общем файле. Собранный фильтр J — то же с общим фильтром J и `judge`. Собранный фильтр записывается как JSON с отступом в два пробела, символы вне ASCII как есть, концы строк LF и завершающий LF; это его байты везде, где связывается blob фильтра.

### Словарь директив и дверей

Одно определение на модуль. README урока ссылается на этот словарь и пишет только своё: подготовку, роли и
особые правила сравнения. Колонка «Урок» — урок, который ввёл директиву: число — прежний урок M10/N (до переноса),
`P/NN` — урок модуля, `M11/N` — урок M11, `ADR-NNNN` — решение без урока (как `@grow`, ADR-0084); урок, вводящий новую,
добавляет строку сюда (разбор ревью стадии B 3–5, № 33).

**Строка `scenarios.tsv`** — ровно четыре ячейки `scenario`, `step`, `request`, `expect` через табуляцию. Ячейка не содержит ни TAB, ни LF и не знает экранирования; таблица с объявлением `# cell-json:` оборачивает названные ячейки по [форме исходных ячеек](../contracts/source-cells.md), которая декодируется один раз. Пустые строки, строки из пробелов и строки, начинающиеся с `#`, — заметки, они пропускаются; строка, первая ячейка которой ровно `scenario`, — заголовок и тоже пропускается, поэтому таблица может записать заголовок и заметкой `#`. `expect` пуст только у шага `ASSERT` (он может написать и `ok`). Шаги сценария нумеруются с 1 подряд (1). Строка вне этой формы или вне форм этого словаря — ошибка данных таблицы, она находится до запуска стенда и не считается исходом реализации.

**Запрос.**

| Форма | Смысл | Урок |
|---|---|---|
| `<МЕТОД> <путь с query> [<тело>]` | путь и query уходят байт в байт, без перекодирования; тело — байты после подстановок, неверный JSON допустим; без текста тела `POST` и `PUT` шлют `Content-Length: 0`, прочие методы — без тела, на любой двери | 1 |
| `@big(N)` | подстановка в любой части запроса: строка из N байт `x`; внутри JSON-строки — до сериализации; подстановки запроса идут по порядку: `@spoil($name)`, затем `$name`, затем `@profile(<имя>)` и `@profile+1(<имя>)`, затем `@rep(N,<текст>)`, затем `@big(N)` | 1 |
| `@raw <текст>` | тело — текст байтами UTF-8, `application/octet-stream`; `Content-Length` — по байтам; `@raw` — только на месте тела, первым словом после пути (`<дверь> <МЕТОД> <путь> @raw <текст>`), у любой двери; «@raw» внутри JSON-тела или иного слова — обычный текст тела, не директива (ревью Codex серии раннера 4faf728) | 10 |
| `@wire <текст>` | сырой HTTP: на месте метода (`<дверь> @wire <текст>`) шаг открывает новое соединение со своей дверью и пишет ровно байты текста, ничего не добавляя: ни заголовка, ни `Content-Length`; экраны `\r`, `\n`, `\t`, `\\` и `\xHH` (две шестнадцатеричные цифры) дают по одному байту и читаются после подстановок, иной `\` — ошибка данных таблицы; ответ читается как HTTP/1.1 на том же соединении | P/01.1 (P01.142) |
| `@halfclose` | последнее слово запроса `@wire`, через один пробел, не входит в его байты: после байтов судья закрывает запись соединения и продолжает чтение | P/01.1 (P01.142) |
| `@rep(N,<текст>)` | подстановка в любой части запроса: текст, повторённый N раз; текст идёт до первой `)` и её не содержит | P/01.1 (P01.142) |
| `@profile(<имя>)` / `@profile+1(<имя>)` | подстановка в любой части запроса, также на месте N у `@big(N)` и `@rep(N,<текст>)`: значение целого ключа `<имя>` поля профиля `keys` (`forms/profile-keys.tsv`) или это значение плюс 1, десятичной записью; иной арифметики нет; отсутствующий ключ оставляет шаг `not_executed` с его именем как причиной | P/01.1 (P01.142) |
| `@pause(<секунды>)` | внутри байтов запроса `@wire`: судья перестаёт писать на столько секунд, десятичным числом, затем пишет остальное; тем временем читает соединение | P/01 (P01.149) |
| `@key(<слово>)` / `@nokey` | `Idempotency-Key` у `POST` — по умолчанию `<запуск>-<scenario>-<step>`, свежий на запуск; `@key(<слово>)` ставит `<запуск>-<scenario>-<слово>`, то есть `@key(N)` повторяет точные байты ключа шага N своего сценария; `@nokey` — без заголовка | 3 |
| `@rid $<имя>` перед методом | приставка запроса, как `@header`; имя после неё связывается, а не подставляется. Судья связывает `$<имя>` до отправки шага: строка `r-` и за ней первые 16 строчных шестнадцатеричных цифр SHA-256 точных байтов `Idempotency-Key`, который он шлёт в этом шаге, — rid двери консоли для подсистемы без `requests.key` ([договор просьбы](../contracts/request-mark.md#просьба), `rid`). Связывание не ждёт ответа, поэтому каждая ветвь `@oneof` этого шага сравнивает один и тот же rid (`202 {"queued": "$rid"}` или `200 answered`, P/06.4 N3 «подать просьбу» шаг 5). Только на `POST /<sub>/requests` двери `console` или `console2`; имя, уже связанное в сценарии, или шаг с `@nokey` — ошибка данных таблицы | P/03.6 (P03.25) |
| `@as <роль>` | шаг и следующие `store`-шаги сценария — от этой роли, сокетом `<роль>.sock` (раздел «Стенд» выше) | 6 |
| `@header <Имя>: <значение>` перед методом | добавить заголовок к одному запросу; `@header Idempotency-Key: …` заменяет ключ раннера по умолчанию (`@key`) | 6; ключ — 3 |
| `ASSERT $a != $b [$c …]` | названные значения попарно различны; HTTP не отправляется | 1 |
| `ASSERT <терм> <оп> <терм>` | сравнение связанных значений; HTTP не отправляется. `<терм>` — `$name`, число JSON или разность `$a - $b`; `<оп>` — `==`, `!=`, `<`, `<=`, `>`, `>=`. Порядок и разность — только у чисел; у строк — `==` и `!=`; разные типы — несовпадение (`ASSERT $t2 - $t1 < 2`, `ASSERT $a <= $b`) | M11 (мутационная проверка 2026-10-18) |

| `@foreign store nolabel` / `@foreign store otherlabel` | второй экземпляр хранилища той же командой с новым каталогом `{data}` и своим `{socket}`; раннер до запуска кладёт в каталог хранилища `{data}/configstore`: `nolabel` — файл `rows` с байтами `x` и без `FORMAT`; `otherlabel` — `FORMAT` с байтами `{"format":"w2c-acceptance-foreign","version":1,"impl":"runner"}`. `ok` — процесс вышел с кодом 2 не позже 10 с и дерево каталога (имена, байты) то же, что до запуска; иначе отказ раннера. Хранилище стенда не трогается (P/01.3 N1.3 `format`) | 11 (пилот хранилища) |
| `@sleep <секунды>` | подождать. Только проверка отсутствия (за срок ничего не случилось) или время, которое норма требует перед действием; ожидание события — `@until` по наблюдаемому признаку. Длина — наименьшая, при которой нарушение успело бы проявиться; каждый сон конкретного случая с причиной назван в инструкциях случаев приёмки урока, принадлежащих судье (ADR-0080 доп. (17) п. 4) | 5 |
| `@together <запрос> \|\| <запрос>` | два запроса одновременно: раннер открывает оба соединения и шлёт оба запроса, не дожидаясь ответа первого (последний байт второго уходит раньше, чем приходит ответ первого); ожидание `ok {"codes": [<код>, <код>]}` — коды обоих ответов по возрастанию, тела не судятся; так приёмка видит гонку допуска, которую последовательные шаги не покажут | ADR-0119 доп. (18) |
| `@until <секунды> <request>` | повторять запрос, не реже раза в секунду, до совпадения с `expect`, не дольше срока; срок вышел — FAIL с последним ответом; повторяется чтение, не мутация | 5 |
| `@hold <дверь> <N>` | открыть N соединений с дверью и ничего в них не писать; они остаются открытыми до конца сценария, затем судья их закрывает; ожидание `ok` — все N приняты | P/01 (P01.149) |
| `@io store $<имя>` | связать имя с числом байт, которые процессы хранилища отдали на запись в хранилище данных: поле `write_bytes` из `/proc/<pid>/io`, сумма по группе процессов хранилища; ожидание `ok`. Когда судья не может прочесть этот счётчик, например под другой учётной записью, шаг и каждый шаг, сравнивающий имя, — `not_executed` с причиной `io_counter_unreadable`, не красные | P/01 (P01.149) |
| `@manual <текст>` | шаг учения: раннер печатает текст, не исполняет; в итог не входит (не зелёный и не красный), `expect` — `manual` | 11 |

Подмножество в `expect` не отменяет полной формы ответа по контракту владельца двери. Код ответа, который контракт его двери не описывает, — пробел контракта, класс `data` на строке контракта, а не тихий пропуск.

| Дверь | Договор полной формы |
|---|---|
| `store`, `admin`, `restored`, `store@<id>`, `admin@<id>` | P/01 |
| `console`, `console2`, `member <кластер> console`, `member <кластер> console2`: пути `/api/…` и `/domain…`; на стенде, кроме стенда домена, — любой путь | P/06 |
| `console` на пересланном пути `/domain/at/<кластер>/…` успешного ответа | P/06 пересланного пути |
| `resource`, `resource#<имя>` | P/05 |
| `holder`, `holder@<кластер>` | P/10, затем P/08: первый договор, называющий операцию |

На стенде без комплекта `no_role`, `wrong_role` или `bad_chain` от `holder` по простому HTTP — несовпадение (P/10 `no_kit`). Полная форма не судится для двери `socket`, для пути консоли стенда домена, кроме `/api/…` и `/domain…`, и для тела не в JSON, если строка его двери этого не требует.

Тело ответа, сравниваемое как JSON, разбирается строго: повтор имени объекта на любом уровне или не-JSON константа числа (`NaN`, `Infinity`) — несовпадение шага.

### Таблицы команд

В таблице команд строка — вызов команды или адаптера профиля, а не HTTP-шаг. Форму называет слово маршрута цели: `verdicts`, `puts` или `variants` ([`forms/targets.routing.tsv`](../../acceptance/forms/targets.routing.tsv)). Таблицы — из первого каталога строки маршрута. Интерфейс каждого вызова берётся из публичной строки цели ([реестр целей](forms/targets.README.md)). Судья читает каждую таблицу цели целиком до старта стенда. Пустые строки и строки, начинающиеся с `#`, — заметки, кроме объявлений, которые называет форма. Строка вне своей формы — ошибка данных класса `data`, найденная до старта стенда; это не исход реализации. Опись цели (N1.4 [норм](spec/acceptance.norms.md)) называет каждую строку её файлом и номером её физической строки.

#### Вердикты загрузчика

Слово `verdicts` исполняет `verdicts.tsv` первого каталога вместе с лежащими рядом `classes.tsv` и `diagnostics.tsv`. Правила, по которым ставится вердикт, — нормы владельца цели (P/02.1 N1, N4); эта форма говорит только, как исполняется строка и что наблюдает судья.

- **`verdicts.tsv`.** Строка — `case<TAB>verdict`. Вход — файл `cases/<case>.subsystem.yaml`, загружаемый один, без каталога других манифестов. `verdict` — `ok` (манифест загружается) или `refused` (отказ загрузки). Набор файлов `cases/` равен набору строк; лишний файл или лишняя строка — ошибка данных.
- **Вызов.** Судья загружает каждый файл через интерфейс цели. У команды `stand.load` подстановка `{file}` — путь файла. Код выхода 0 — манифест. Выход с другим кодом, не по сигналу, у которого stdout или stderr содержит имя файла `<case>.subsystem.yaml`, — отказ. У адаптера `load` ([загрузчик манифеста](PROFILE.md#загрузчик-манифеста)) ответ `verdict` — `ok` или `refused`; отказ — `refused`, чей `text` содержит имя файла. Всё прочее — несовпадение строки: смерть по сигналу, отказ, не называющий файл, сломанный ответ адаптера.
- **Вердикт.** Он строгий: `ok` совпадает только с манифестом, `refused` — только с отказом.
- **`classes.tsv`.** Строка — `case<TAB>class`, где `class` — `text`, `form`, `relations` или `catalogue`. Её `case` имеет `refused` в `verdicts.tsv`. Текст отказа содержит слово `refused:<class>` класса случая и ни одного другого слова `refused:<word>`; иначе строка случая — несовпадение.
- **`diagnostics.tsv`.** Строка — `case<TAB>paths<TAB>lines`. Её `case` встречается один раз и имеет `refused` в `verdicts.tsv`. `paths` — JSON-массив путей, каждый — массив имён ключей и индексов списков; `lines` — JSON-массив номеров строк с 1. Строка — подсказка, а не проверка. Судья ищет каждый путь в тексте отказа в форме `keys.path_style` профиля: `json` — текст JSON-массива, `dotted` — имена через `.`, индекс как `[N]`. Каждый номер строки он ищет десятичным словом. Ненайденное он пишет в отчёт, без отказа. Лишние пути в тексте не наблюдаются.

Прогон этих файлов через `manifest put` в это слово не входит; такая выборка пишется строками [последовательностей установок](#последовательности-установок).

#### Последовательности установок

Слово `puts` исполняет `puts.tsv` первого каталога и файлы столбца `tables` строки маршрута, все по этой форме. Строка — последовательность установок манифестов в одно свежее хранилище.

**Форма таблицы.** UTF-8, строки разделены LF, ячейки — TAB. Первая строка, не являющаяся заметкой, — заголовок. Он выбирает столбцы: `case<TAB>puts<TAB>expect`, `case<TAB>puts<TAB>expect<TAB>canonical` или `case<TAB>puts<TAB>expect<TAB>canonical<TAB>ceiling`. Затем по строке на случай ровно с ячейками заголовка.

- `case` — имя случая, `[a-z0-9_]+`, уникальное в файле.
- `puts` — слова через один пробел, по порядку: имена файлов и директивы ниже. Имя файла `<file>` — файл `puts/<file>.subsystem.yaml` первого каталога. Файл идёт первым и последним.
- `expect` — `<code> <rev>`, затем по желанию `@stderr`. `<code>` — код возврата **последней** установки, `0` или `2`. `<rev>` — десятичный `rev` строки `platform/manifest/<name>` после неё, где `<name>` — `name` последнего файла; `-` — строки нет.
- `canonical` — имя случая пакета векторов объявления `# canonical:`. Байты его файла `expect/<canonical>.json` — ожидаемое поле `manifest` строки вида; `-` — строки вида нет.
- `ceiling` — потолок строки хранилища этой строки, его `{row_ceiling}`.

**Объявления.** Две строки-заметки — объявления таблицы:

- `# canonical: <directory>` — пакет векторов, чьи файлы `expect/<case>.json` дают байты столбца `canonical`. Таблица со столбцом `canonical` без этого объявления — ошибка данных.
- `# beside: <directory>` — всё содержимое каталога лежит, под теми же путями, рядом с рабочими копиями каждой установки каждой строки.

Путь объявления — от корня спецификации. Он называет каталог строки маршрута цели; другой каталог — ошибка данных.

**Имена.** `<name>` файла — значение его ключа верхнего уровня `name`, прочитанного как YAML. Директива берёт `<name>` файла перед ней.

**Исполнение.** Строки независимы; их порядок не важен. Для каждой строки судья берёт новое пустое хранилище и новый рабочий каталог. Хранилище запускается командой хранилища цели, без файла прав; `{row_ceiling}` — ячейка `ceiling`, а без этого столбца — потолок строки [параметров каждого экземпляра](../../../01-store/ru/acceptance/1/README.md) P/01.1, 524288 байт. Затем судья исполняет `puts` по порядку. Файл копируется в рабочий каталог под своим именем и ставится отдельным вызовом команды `manifest-put` цели, с `{socket}` и `{file}` — рабочей копией. Директива исполняется по своей строке ниже. Каждая установка, кроме последней, MUST вернуть `0`, и каждая директива MUST пройти; иначе случай — несовпадение (подготовка не удалась).

**Сравнение.** После последней установки судья сравнивает:

1. код возврата с `<code>`;
2. при коде, отличном от `0`: stderr содержит имя файла последней установки и каждую подстроку `@stderr`;
3. `rev` строки `platform/manifest/<name>` с `<rev>`: строка читается `GET /v1/get?key=platform/manifest/<name>` через `{socket}`, поле `rev` в `items`; `-` — `items: null`.

Со столбцом `canonical` судья ещё сравнивает:

4. метку `platform/manifest/<name>/rev`. При коде `0` её `rev` — `<rev>`, а её `sha256` — `sha256` строки; при `-` метки нет. При другом коде метка байт в байт та, что была до последней установки: отказанная установка её не трогает;
5. строку вида `platform/manifest/<name>/canonical/1`, её `items` по кодеку [семьи `canonical-row`](../../../02-installer/data/canonical-row.schema.json): `form` — `"1"`, `rev` — `<rev>`, `sha256` — `sha256` строки, `manifest` — байт в байт байты `expect/<canonical>.json`. Прочие поля не сравниваются. При `canonical` = `-` строки вида нет.

Без столбца `canonical` метка и вид не сравниваются. Порядок записей во времени и повтор вида после конфликта `cas` не сравниваются; они проверяются чтением. Прежнее правило P/02.2 «при коде `2` stderr называет ключ вида, после `@rev-spoil` — ключ метки» теперь пишется в таблице словом `@stderr`.

**Строка с `ceiling`.** До случая судья подтверждает потолок нового хранилища. `GET /v1/status` даёт `max_value` = `ceiling`. `put` через `{socket}` строки `acceptance/ceiling` с `items` веса ровно `ceiling` проходит; на байт больше — `413 toolarge` с `limit` = `ceiling`. Затем судья удаляет строку. Вес — по P/01.1 N1. Если судья не может подтвердить потолок, строка — `not_executed` с причиной `installer_ceiling_unproven`.

**Слова `puts` и `expect`.** Директивы пишут через `admin.sock` экземпляра, то есть `{socket}`, операциями P/01.1. Директива, которая не прошла, проваливает подготовку своей строки.

#### Варианты прав

Слово `variants` исполняет каждый каталог `variants/<variant>/` первого каталога. Вариант выводит права по смыслу на каталоге манифестов вне стенда. В его каталоге — файлы `*.subsystem.yaml` (каталог манифестов варианта) и ровно одно из: `expect.tsv`, `refused` или `check.tsv` с каталогом `check/`. Каталог без них или с несколькими — ошибка данных. Опись — физические строки `expect.tsv` и `check.tsv` и единственная строка `refused`.

**`expect.tsv`.** UTF-8, LF, ячейки разделены TAB, строки с `#` пропускаются. Заголовок — `role<TAB>action<TAB>key<TAB>expect`; затем по строке на пробу: роль файла прав (P/01.2 N1.1), действие `read`, `write` или `delete`, ключ строки и `allow` или `deny`. Для варианта судья:

1. вызывает команду вывода прав цели, `stand.rights`, с `{manifests}` — каталогом варианта, `{deployment}` = `dep` и `{file}`. Код, отличный от `0`, — несовпадение каждой пробы варианта;
2. запускает свежий экземпляр хранилища с этим файлом как `{rights}`;
3. для каждой строки вызывает через сокет роли: `read` — `GET /v1/get?key=<key>`, `write` — `put` с `items: {"p": "1"}`, `delete` — `delete`, без `cas` и без охраны. `allow` — только подтверждённый успех: для чтения 200 формы `Row` (для отсутствующей строки `{items: null, index: ""}`, P/01.1 N2), для записи и удаления 200 `Written`. `deny` — 403 `forbidden`. Роль без сокета — то же, что 403 (роли нет в файле, P/01.2 N1.3). 5xx, ошибка транспорта или иной ответ — неопределённый исход: проба ни `allow`, ни `deny` и не совпадает.

Порядок строк не важен. Так проверяется смысл файла прав (P/01.2 N1.3 и `never`), а не его байты: порядок шаблонов, `comment`, лишние равносильные шаблоны и группы не сравниваются.

**`refused`.** UTF-8, LF, строки с `#` пропускаются; ровно одна другая строка — `name` манифеста варианта, чьё объявление отвергается. Судья вызывает `stand.rights`, как в п. 1. Код MUST быть `2`, файла по пути `{file}` нет, и stderr называет этот манифест — его `name` или его файл. Остальной текст не сравнивается. Хранилище не запускается, проб нет.

**`check.tsv`.** UTF-8, LF, ячейки разделены TAB, строки с `#` пропускаются. Заголовок — `case<TAB>file<TAB>code`; затем по строке на случай: `case` — `[a-z0-9_]+`, уникальное; `file` — `check/<case>.rights`, файл прав; `code` — `0` (файл по смыслу равен выведенному) или `!0` (любой код, кроме `0`). Для каждой строки судья вызывает команду сверки прав цели, `stand.rights-check`, с `{manifests}` — каталогом варианта, `{deployment}` = `dep` и `{file}` — `check/<case>.rights` и сравнивает её код с `code`. Профиль без `stand.rights-check` оставляет каждую строку `not_executed` с причиной `installer_rights_check_missing`.

### Протокол адаптера швов

Это общая нормализация приёмки для `seams.tsv` урока, не API продукта, новая дверь процесса или сгенерированный пакет. [Грамматика швов P/02](../../../02-installer/ru/forms/README.md#точная-грамматика-швов-без-http) задаёт четыре разделённые TAB колонки `scenario`, `step`, `request`, `expect` и шаги подряд с 1. Сохраняй заданную формой владельца длительность жизни нового адаптера и временных корней, относится ли она к сценарию или к случаю; протокол не переносит изменяемое состояние фикстуры через эту границу. Шов наблюдает настоящий вызов и его эффекты; он не заменяет обычный процессный сценарий, native-вектор, соседний стенд или проверку чтением, которые не исполнил.

Таблицу выбирает слово движка строки маршрута цели ([`forms/targets.routing.tsv`](../../acceptance/forms/targets.routing.tsv)). `run` исполняет `seams.tsv` первого каталога по этому протоколу, только когда в этом каталоге нет `scenarios.tsv`. `seams` исполняет `seams.tsv` первого каталога по этому протоколу и тогда, когда в каталоге есть `scenarios.tsv`; этот `scenarios.tsv` оно не исполняет, он принадлежит другой цели реестра. Колонка `scenarios` строки маршрута относится к исполняемому `seams.tsv`. Оба файла остаются в одном каталоге: ворота `seams:<chapter>` этапа называют `seams.tsv` каталога приёмки своей главы.

Вход модели содержит нормы, формы, схемы, договоры и протоколы. Векторы и сценарии остаются только у судьи. Каждый нужный адаптеру интерфейс, форма payload, точная обязательная кодировка, порядок полей или словарь отказов должны быть определены в этом нормативном входе, не только таблицей тестов или фикстурой. Судья передаёт настоящие входные значения без ожидаемого результата; необходимое определение только в векторе/сценарии — пробел нормы, не право адаптера читать ожидания.

#### Владение процедурами и peer

Поверхность `call` в каталоге отказов означает процедуру; `peer` — проверку, принадлежащую другому уроку ([каталог P/02](../../../02-installer/ru/forms/README.md#каталог-отказов), [каталог P/04](../../../04-controller/ru/forms/README.md#входы-и-отказы)). Ни одна поверхность не создаёт новую местную HTTP-операцию. Сохраняй исходное условие и владельца выбранной строки: её точные код, слово, обязательные поля, заголовки и форма ответа действуют только там, где их задаёт владелец. Отсутствующая числовая проекция `-` не получает выдуманный статус или код выхода. Поверхность `peer` отличается от команды-вектора домена `peer` в [командах-векторах домена](#команды-векторы-домена) и от выбора внутренних имён функций реализацией.

#### Вход и наблюдение CALL

`CALL <name> <JSON>` поглощает одно значение JSON после имени `[a-z][a-z0-9-]*`; порт и его нормализованные вход/выход принадлежат README форм урока. Порты приспосабливают обычные функции, команды или HTTP-пути реализации, а не требуют предоставить такое частное API. [Нормализации CALL P/02](../../../02-installer/ru/forms/README.md#нормализация-call) и разделы швов [P/03](../../../03-worker/ru/forms/README.md#швы), [P/04](../../../04-controller/ru/forms/README.md#швы), [P/05](../../../05-resource/ru/forms/README.md#швы), [P/06](../../../06-console/ru/forms/README.md#швы-и-этапы), [P/08](../../../08-domain/ru/forms/README.md#швы-и-этапы), [P/09](../../../09-agent/ru/forms/README.md#швы-и-этапы), [P/10](../../../10-domain-console/ru/forms/README.md#швы-и-этапы) задают вмешательство фикстуры и наблюдения. Применяй только нормализацию названного владельца; не переноси умолчания другого порта, не переименовывай исходы и не вводи неназначенную оболочку результата.

Вызывай настоящую реализацию и получай наблюдения из её результата, строк, байтов или записанного I/O. Не передавай реализации ожидание и не возвращай его готовым ответом. Допустимо только объявленное источником дополнение фикстуры: явные raw-строки и текст family-read — полные входы, которые не исправляют. Паника, постороннее исключение, ошибка транспорта или неисполненный вызов не являются обычным отказом предметной операции. В частности, P/02 `command` наблюдает нуль против ненуля только там, где владелец не задал точный код; неожиданное падение его не удовлетворяет.

Ожидания CALL JSON используют действующие правила ожиданий этого словаря: рекурсивное подмножество объекта, точные пустые объекты, точные массивы кроме явно названного неупорядоченного случая, сравнение чисел по числовому значению при отличии булевых значений, строк и null от чисел и фиксацию привязок только после совпадения всего шага. Ожидание-подмножество не отменяет полную форму результата владельца. RUN, управление файлами/часами/параллельностью и сравнения названных потоков сохраняют грамматику P/02; грамматика запроса шва shell не исполняет.

#### Нормализация швов P/01

В P/01.1 `seams.tsv` нет строк `CALL`. Его шаги — запросы HTTP и директивы `@clock`, `@reopen` и `@parallel`. Над [мостом](#явный-тестовый-мост-швов) каждый шаг HTTP или директива становится `method: call` с одним из трёх публичных токенов. Новых полей и методов моста нет (решение Архитектора 2026-11-08, ADR-0126 доп. (11) п. 4).

| `name` | Шаг | `input` | Наблюдение |
|---|---|---|---|
| `store-http` | `GET` или `POST` | закрытый объект: обязательные `method` и `target` (путь с запросом, как записан в шаге), необязательный `body` (текст тела шага одной строкой, нет — если у шага тела нет) | `{kind: "value", value: {"status": <integer>, "body": <string>}}`: код и всё тело ответа |
| `clock` | `@clock +N` или `@clock -N` | закрытый объект `{"shift": <string>}`: сдвиг в том же синтаксисе, что в шаге | `{kind: "value", value: {}}` |
| `reopen` | `@reopen` | `{}` | `{kind: "value", value: {}}` |

`store-http` входит в обычную обработку запроса хранилища и не является новой дверью. `clock` сдвигает управляемые часы хранилища на N секунд, нарастающим итогом; часы начинаются с 2000000000, способ управления выбирает реализация. `reopen` закрывает хранилище и открывает его снова на том же каталоге данных с теми же часами. Шаг HTTP `<code> <JSON body>` сравнивается как в приёмке главы 1.1, `ok` директивы соответствует пустому объекту. `@parallel K` следует грамматике P/02 и исключению в мосте ниже. Порты `CALL` главы P/01.3 — в её [README приёмки](../../../01-store/ru/acceptance/3/README.md).

#### Явный тестовый мост швов

Этот вновь выбранный мост — отдельный договор стороны тестов. Это не существующий ключ `stand.call` или `adapters.call`, не конверт native-векторов и не обязательное API продукта. Отдельный дескриптор называется `SEAM_BRIDGE.json`; судья явно передаёт его путь для выбранного случая, без поиска в рабочем каталоге или профиле. Не вводятся угаданная команда, поле формата 2 профиля, поле формата 1 состава, маршрут платформы или рабочий флаг. Настоящие идентичность receiver и вызов входят в доказательства прогона. У нынешнего раннера без такого receiver — `MissingBinding`/`NOTEXEC`; публикация формата его не реализует и не активирует.

Дескриптор — замкнутый объект JSON с ровно обязательными `format` (целое `1`), `source_pin` (полный SHA Source, выбранный для случая), `scope` (непустая точная строка: id цели реестра, при необходимости с `#` и именем одного её сценария или случая) и `bridge`. `bridge` замкнут и содержит обязательные `identity` и `invoke` точных форм идентичностей файлов и вектора аргументов D7 ниже. Эта тестовая идентичность Source не является алиасом `spec_version` профиля, сохраняющего опубликованный смысл Git-SHA выгрузки; настоящая связь Source/выгрузки записывается без новой проверки равенства/неравенства двух строк. Общего объекта roots нет: подготовка, пути и границы новых процесса/состояния остаются по действующему владельцу Source.

Каждый последовательный UTF-8 JSONL запрос — замкнутый объект с ровно обязательными полями:

| Поле | Обязательное значение |
|---|---|
| `format` | Целое `1`, не булево значение. |
| `scope` | Точный scope дескриптора. |
| `request` | Непустой идентификатор, уникальный внутри процесса моста. |
| `method` | `call` или `peer`, только по выбранной публичной привязке Source. |
| `name` | Точный публичный токен нормализованного порта/проверки, выбранный этой привязкой. |
| `input` | Однократно декодированный вход JSON владельца Source, не ожидаемый результат или ответ судьи. Объявленные Source управляемые ответы зависимостей остаются входами; не изготавливай их из ожидания. |

Судье принадлежит полный контекст нормализации запроса: полный пин Source, таблица относительно Source и её raw SHA256, канонический владелец, настоящие исходные ячейки id и scenario/step, физическая строка источника, точная нормализованная привязка порта/peer и её точная публичная ссылка normalizer. Он фиксирует контекст из неизменяемого Source до dispatch и связывает со scope/request. Контекст не выводится из ответа provider, короткого имени порта или написания scope. Метаданные Source/таблицы/строки/selector/normalizer/evidence/expectation provider не передаются. Шестипольный запрос таких полей не получает. [Обёртка source-cell](../contracts/source-cells.md), где объявлена, декодируется ровно один раз перед действующей грамматикой шва; вложенный вход Source не исправляется и не переписывается численно.

Судья должен машинно закрыть процессам адаптеров чтение файлов векторов/сценариев с ожиданиями; одно отсутствие полей ожидания в кадре ещё не такая изоляция. Ему принадлежит отрицательный контроль каждой выбранной цели тем же адаптером над намеренно сломанным продуктом; зелёный результат над сломанным предметом означает провал средства проверки, не квалификацию продукта. Настоящие изоляция и контроли должны быть показаны; их исполнение нынешним receiver не предполагается. Код адаптера независимо читается до вывода, что генерация доказана. Отчёт модели раскрывает только имя случая, якорь нормы и класс расхождения, никогда ожидаемый ответ. Полные raw-доказательства случая и сравнение ожиданий остаются в частной записи судьи; адаптер во время работы получает только свой объявленный входной кадр, не эту запись.

`CALL <name> <JSON>` выбирает `call`, точный публичный токен и однократно декодированный вход JSON. Строки `call` и `peer` каталога исполняются только при настоящих входе, цели и именованной привязке в Source. `peer` вызывает существующие публичные проверку/дверь другого владельца; не создаёт местные HTTP API, peer-порт или форму ответа. Native-вектор домена `peer` остаётся отдельным. Неизвестные имена и отсутствующие peer-вход/цель/публичный normalizer остаются точными `MissingBinding`/`NOTEXEC`, не угаданным вызовом или готовым ответом.

Мост возвращает одну сброшенную JSONL запись на запрос. Она замкнута и содержит ровно обязательные `format`, `scope`, `request`, `observation`: целое `format: 1`, точно совпавшие scope/request и ровно одну из замкнутых форм наблюдения. В ответе шва нет поля последовательности.

| Форма | Смысл и ограничение |
|---|---|
| `{kind: "value", value: <JSON>}` | Настоящий нормализованный строгий JSON результат Source, включая явный null. Числа сравниваются по числовому значению; булевы значения не числовые алиасы. Строка/маркер Source остаётся значением, если владелец явно не назначил другой исход. |
| `{kind: "absence"}` | Отсутствие/пропуск только там, где выбранный владелец Source явно их назначает. Не преобразуй null, пустое значение, неподтверждённое чтение или строковый маркер в отсутствие. |
| `{kind: "native", exit_code: <integer>, stdout_b64: <string>, stderr_b64: <string>}` | Настоящий нормальный native-выход процесса, назначенный владельцем, в `0..255` и точные raw-потоки в каноническом стандартном RFC 4648 Base64; пустые байты — пустая строка. Форма допустима только при назначенной Source поверхности native-выхода/raw-потоков. Это диапазон native-процесса транспорта, не ресурсный/QoS потолок или новый отказ платформы. |

Теги — метаданные транспорта, не Fault продукта и не новые слова предметного исхода. Нормальный native-выход находится внутри наблюдения только по назначению Source. Ранний EOF, ненулевой выход, сигнал, падение или расхождение протокола самого моста — ошибка инструмента, никогда не отказ платформы. Общие статус, тело, Fault kind или широкий отказ не выдумываются. К настоящему наблюдению применяются действующие нормализация статуса/слова/поля/заголовка/результата выбранного владельца и общее сравнение; сохраняются точные пустые объекты, длина/порядок массивов кроме явно назначенного Source неупорядоченного сравнения, сравнение чисел по значению с отличием от булевых значений/строк/null и привязки только после совпадения всего шага.

Одновременно ожидается один уникальный запрос и одно соответствующее наблюдение; нет приветствия, незапрошенных кадров, pipelining и лишней записи. Одно исключение, для `@parallel K` уроков P/01 и P/02: судья шлёт K кадров подряд без ожидания, адаптер исполняет их одновременно над тем же экземпляром и отвечает K записями в любом порядке, сопоставление по существующему полю `request`; новых полей нет, следующий шаг начинается только после всех K ответов. Вне `@parallel` правило выше сохраняется (решение Архитектора 2026-11-08, ADR-0126 доп. (11) п. 4). Обе стороны — строгий UTF-8 JSONL, один физический LF на запись и сброс после ответа; диагностика идёт в stderr. Целочисленные поля кадров/дескрипторов моста и D7 используют целочисленные токены JSON, не булевы значения, дробную или экспоненциальную запись. Это касается только кадров транспорта; вложенный JSON Source сохраняет собственные числовые правила. Внешние кадры отвергают повторные поля, BOM и не-JSON числа. Внешняя запись не по форме означает ошибку инструмента, не отказ платформы. Процесс/состояние новые на объявленной Source границе сценария/случая; подготовка и допустимые прежние шаги внутри границы сохраняют смысл владельца. Не поставленный на деле выбранный dispatch RUN, `@file`, `@read`, `@parallel` или `@clock` остаётся отсутствующим/неисполненным, не PASS для исключённого хвоста.

На завершённой границе вызывающая сторона закрывает stdin, мост нормально выходит с нулём и не оставляет фоновый сервис с тестовым состоянием. Записывай настоящие выход, сигнал, тайм-аут и уборку. Намеренный сигнал проверяемой цели — наблюдение только по назначению Source; сигнал, убивший мост, его не заменяет. Общего тайм-аута, размера строки или ресурсного потолка здесь нет. Совместимость parser/транспорта не является квалификацией кандидата/native или физическими доказательствами, которым нужен D7.

#### Тестовые привязки доказательств D7

Это вновь выбранный договор стороны тестов для часов, носителя, хода и управляемых сбоев. Он не задаёт маршрут или рабочий флаг платформы и не добавляет поле в формат 2 профиля или формат 1 состава. Дескриптор и ответ provider не являются квалификацией. [Владелец эксплуатационной приёмки](../../../01-store/ru/spec/production-acceptance.md#доказательства-и-исходы) по-прежнему различает отсутствующие привязки, ошибки инструмента и измеренные нормативные исходы. Нынешний receiver раннера и настоящие квалифицированные provider должны быть указаны отдельно; публикация договора их не поставляет и не исполняет.

Дескриптор — отдельный тестовый вход. Его замкнутые верхние поля обязательны: `format` (целое `1`), `source_pin` (полный 40-hex коммит Source, выбранный для случая), `scope` (непустая точная строка изолированного случая: id цели реестра, при необходимости с `#` и именем одного её сценария или случая) и `providers` (карта только с ключами `clock`, `storage`, `progress`, `fault`). Поле `spec_version` профиля сохраняет свой опубликованный смысл; записывай настоящую связь Source/выгрузки случая, не выводя их равенство или различие лишь из имён полей. Записи нужны только для возможностей, обязательных выбранному случаю; отсутствие нужной записи оставляет зависимую проверку `MissingBinding`/`NOTEXEC`.

Каждая запись provider — замкнутый объект с обязательными полями:

| Поле | Тип и привязка |
|---|---|
| `identity` | Замкнутый объект с обязательными `id` (непустая строка), `executable` и `artifacts`; необязательный `provenance_ref` — строка точной опубликованной ссылки. `executable` — замкнутый объект с абсолютным `path` и 64-lowercase-hex `sha256` байтов файла. `artifacts` — массив объектов того же вида `path`/`sha256`; пустой массив допустим. Назови все скрипты, интерпретаторы, конфигурации и результаты сборки, существенные для идентифицированного поведения provider. |
| `invoke` | Замкнутый объект с обязательными `argv` (непустой массив строк) и `cwd` (абсолютный путь каталога). `argv[0]` абсолютен и равен `identity.executable.path`. Судья запускает этот вектор аргументов без вставки shell, поиска PATH, globbing или подстановок. Явно названный интерпретатор входит в измеренный вызов. |
| `observer_ref` | Непустой непрозрачный идентификатор только из защищённого реестра наблюдателей судьи. Provider не может назначить заменяющий код наблюдателя. |
| `qualification_ref` | Непустой непрозрачный идентификатор только из защищённого реестра независимой квалификации судьи. Произвольный путь файла, булево значение provider или собственная квитанция не являются квалификацией. |

Судья измеряет запущенные executable/artifacts и записывает настоящую идентичность процесса/runtime-executable и scope. Он проверяет доверенную квитанцию квалификации относительно этой идентичности, Source, возможности, scope, наблюдателя и объявленного свойства, включая настоящие отрицательные контроли. Отсутствие вызова, прав, наблюдателя, квитанции или публичного договора payload случая — отсутствующая привязка. Известная неверная/устаревшая идентичность или противоречивый активный инструмент — ошибка инструмента. Объявление не даёт права записи ни в один защищённый реестр.

Процесс provider принадлежит одной объявленной возможности и изолированному случаю/scope. Он получает последовательные UTF-8 JSONL запросы в stdin и выдаёт одну сброшенную UTF-8 JSONL запись в stdout на запрос; stderr — текст диагностики. Нет приветствия, незапрошенных записей и pipelining. Во внешнем JSON нет повторных полей, не-JSON чисел и BOM. Каждую запись завершает один физический LF. Настоящие выход, сигнал и внешний тайм-аут процесса остаются доказательствами, не нормализованным отказом платформы. Объявленный конечный бюджет вызова/наблюдения случая остаётся отдельным; этот протокол не назначает общего тайм-аута или потолка размера.

| Поле запроса | Обязательный тип |
|---|---|
| `format` | Целое `1`. |
| `scope` | Точная непустая строка scope дескриптора. |
| `request` | Непустой идентификатор, уникальный внутри процесса provider. |
| `capability` | Объявленная процессу `clock`, `storage`, `progress` или `fault`; сменить возможность нельзя. |
| `operation` | `describe`, `activate`, `sample` или `deactivate`. |
| `payload` | Значение JSON по выбранной видимой модели норме, форме, схеме, договору или протоколу этой возможности; судья задаёт значения случая без ожидаемых ответов. Один тестовый вектор/сценарий не является определением payload. |

Объект запроса замкнут. Ответ тоже замкнут и содержит ровно `format`, `scope`, `request`, `seq`, `event`, `payload`. `format` — целое `1`; `scope` и `request` точно совпадают с запросом. `seq` — неотрицательное целое, начиная с `0` в первой записи и увеличиваясь ровно на 1 в каждой следующей, без сброса, пропуска и повтора. `event` равен `identity` для `describe`, `activation` для `activate`, `observation` для `sample` и `deactivation` для `deactivate`. `payload` имеет выбранную видимую модели нормативную форму возможности, не форму, определённую только частным случаем или вектором/сценарием. Payload `identity` ответа `describe` равен объекту identity дескриптора; судья всё равно независимо сверяет настоящую идентичность. Записи несут наблюдения, не вердикт квалификации или PASS; допустимое слово результата Source внутри наблюдения само не становится вердиктом.

Первый запрос — `describe`. После него provider неактивен: `activate` допустим только в неактивном состоянии; `sample` и `deactivate` — только в активном. Деактивация возвращает неактивное состояние; следующий цикл активации использует новые идентификаторы запросов и продолжает последовательность. Scope и идентичность provider не меняются во время процесса. Нормальное завершение — EOF stdin в неактивном состоянии, затем нормальный выход с нулём. Отсутствующие или лишние записи, ранний EOF, падение, сигнал, ненулевой выход и запись не по форме не удовлетворяют ожидаемый предметный отказ.

Порядок транспорта не доказывает эффект. Для каждой из четырёх возможностей независимый наблюдатель должен связать запрос активации, настоящую активацию на выбранной границе, настоящую целевую операцию/эффект/наблюдение и настоящую деактивацию. Он отвергает устаревшие, чужие scope/операцию, неверную фазу и обратный порядок. Настроенный hook, `Config.Now`, `@clock`, ACK/счётчик provider, текст EIO, manager kill, Raft Barrier или Shutdown сами не доказывают заявленную физическую область.

| Возможность | Публичная привязка случая и независимая квалификация | Обязательные отрицательные контроли |
|---|---|---|
| `clock` | Назови наблюдаемый или управляемый домен/единицу часов, настоящую потребляющую границу, независимую монотонную базу и калибровку. Сохраняй различие Source между стенными метками и монотонными сроками. | Должны выявляться только самоотчёт или неактивированный контроль, неверный домен, устаревший scope и обратное время. Выдуманного допуска перекоса нет. |
| `storage` | Назови настоящую идентичность файла/объекта, носитель/режим durability и наблюдаемые фазы эффекта/публикации/барьера, состояние до/после/квалифицированного открытия. Перезапуск процесса или возврат библиотеки не доказывает физическую durability. | Должны выявляться no-op барьер/сбой, неверный объект или фаза, ложные счётчики и устаревшие данные после открытия. |
| `progress` | Назови настоящие операцию, pin/output/sink/latch/cancel/release или другую границу Source, независимые наблюдения хода/ресурсов для объявленной нагрузки/бюджета. Активируй latch до оценки блокировки; задержка старта не остановка sink. | Должны выявляться frozen/no-op/чужая операция, неактивированный latch и ненаблюдаемые или отсутствующие release/progress. |
| `fault` | Назови точные опубликованные фазу Source, цель и поддерживаемую модель сбоя; независимо наблюдай активацию, эффект и порядок. Сохраняй доказанный no-effect против неизвестного или целиком опубликованного восстанавливаемого исхода. | Должны выявляться неактивная/no-op/неверная фаза/устаревшая активация и заявленный эффект без независимого свидетеля. Нет нового класса Fault или обещания общего rollback. |

Payload четырёх возможностей — форма [`forms/d7-payload.schema.json`](../../acceptance/forms/d7-payload.schema.json). Запрос `activate` несёт один объект своей возможности. Его постоянная часть — привязка случая: у `clock` — режим `observe` или `control` и потребляющие домены стенных часов, названные по `-id`; у `storage` — объект, носитель, наблюдаемые фазы и состояния; у `progress` — операция, её границы Source, ресурсы и latch; у `fault` — фаза и модель сбоя. Судья задаёт `targets` (член, каталог хранилища и процесс) и в режиме `control` сдвиг каждого домена при каждой активации. Запросы `describe`, `sample` и `deactivate` несут пустой объект. Записи `activation` и `deactivation` несут члены, у которых граница действительно сменилась, и монотонное показание provider; запись `observation` — наблюдение своей возможности. Активация действует до своей деактивации: `fault` внедряется при каждом проходе своей фазы, пока активен, а `clock` в режиме `observe` ничего не сдвигает. Слова формы закрыты; payload вне её — неверно оформленные запрос или запись. Его поля — наблюдения provider и ничего не квалифицируют: наблюдатель привязки проверяет их независимо. Числовых значений форма не задаёт.

Для привязок цели `P/01/production` слова payload значат следующее. Граница `admission_time` — стенные часы процесса демона, которые P/01.1 N3 «Admission time» читает при допуске: provider наблюдает этот домен часов процесса, а время допуска, которое хранит демон, судится публичными исходами случая, не provider. Ресурс `heap` — резидентная анонимная память процесса (`RssAnon` из `/proc/<pid>/status`), а `memory` — его резидентный набор (`VmRSS`); показатель кучи среды исполнения языка ресурсом формы не является. При latch `sink` provider — читатель вывода, а `cancel` — его деактивация: provider закрывает sink на `deactivate`, `monotonic_ns` записи деактивации — этот момент, и ни одно наблюдение `cancel` не несёт. Фаза `recover_mark` не называет файла: метка — первый изменяющий шаг `recover` в `-dir` (P/01.3 R021), а точка сбоя — первое изменение `-dir` после первой записи верхнего уровня, которую `recover` завершил; поэтому ни payload, ни вызов имени метки не несут. Фаза `copy_after_headers` — конец потока, как его получает клиент после полного блока заголовков ответа `200`, сделанный между демоном и клиентом: она даёт ту половину `RUN-H03`, которую судит CLI. Половина демона после `200` — только неполное закрытие и никакого второго отказа — судится на его собственном потоке при отмене, застое sink и остановке, которые делает судья; у сбоя внутри демона привязки нет.

Настоящие активированные положительные и отрицательные контроли квалифицируют только объявленное свойство наблюдателя/provider; неисполненный список контролей ничего не квалифицирует. Дескриптор и общий кадр не выдумывают отсутствующий настоящий provider. Если у выбранной возможности нет привязки случая по форме payload или отсутствуют настоящий вызов/квалификация, сохраняй `MissingBinding`/`NOTEXEC`. Сохраняй нынешние утверждённые бюджеты владельца и неизвестные входы; нового числового потолка здесь нет.

### Подставной воркер передачи второго вида

Директивы [стенда передачи второго вида](pass/README.md) (ADR-0094 B1). Раннер их исполняет (README стенда pass, раздел «Исполнимость»). Воркера играет раннер: так сценарий держит запрос открытым и видит, что дошло до воркера. У директив `<кластер>` стоит на стенде домена, на стенде консоли его нет.

| Форма | Смысл | Урок |
|---|---|---|
| `@pass-worker [<кластер>] <sub> <имя> [kit=<лист>]` | раннер слушает дверь на петле (без `kit` — `url` равен `http://127.0.0.1:<порт>`; с `kit` — https с серверным листом `<лист>` комплектов `@tls-setup`: хост `url` — имя сервера комплекта, цепь — лист и `ca.pem` кластера листа; кластер вместо имени листа — лист `<кластер>-<sub>worker`); при замене воркера того же имени раннер ждёт, пока проба `GET /<sub>/api/x` через консоль придёт на новый слушатель: `url` выдачи не называют, пишет и освежает объект `<sub>/heartbeats/<name>` с `worker`, `url` этой двери, как живой воркер с дверью; принятый запрос держит открытым; ожидание `ok` — консоль видит его живым. Прежний воркер `<имя>` останавливается | B1 |
| `@pass-open <метка> <дверь> <запрос>` | запрос к консоли фоном, под меткой; `POST` без `Idempotency-Key` получает ключ по правилу `@key`; ждёт, пока подставной воркер его примет. Ожидание `ok <JSON>` — принятое подмножеством: `{method, path, query, body, ticket, headers}`, `ticket` — значение `X-W2C-Pass-Ticket`, отсутствие заголовка — `@absent`; не дошло — ответ клиента, форма `<код> <JSON>` | B1 |
| `@pass-answer <метка> <код> <Content-Type\|-> [<тело>]` | воркер отвечает на запрос метки: статус `<код>`, `Connection: close`, `Content-Length` кроме 204, `Content-Type`, если не `-`; ожидание — ответ клиенту, формы словаря | B1 |
| `@pass-chunk <метка> <текст>` | воркер шлёт часть потока: статус 200, `Content-Type: text/event-stream`, кодировка chunked, каждая часть — текст и пустая строка; ожидание `<код> ~<текст>` — клиент уже получил её, ответ ещё открыт | B1 |

| `@pass-abort <метка>` | клиент рвёт соединение; ожидание `ok` — воркер увидел закрытие | B1 |
| `@pass-closed <метка>` | консоль закрыла соединение клиента не позже `PASS_TICKET_CHECK` + 30 с; ожидание `ok` | B1 |
| `@pass-fill <кластер> <sub>` | открывать запросы `GET /<sub>/api/x` к маршруту, пока консоль не ответит 503 `busy`; они живут до конца сценария; ожидание `ok` | B1 |
| `@pass-seen <имя>` | сколько запросов принял подставной воркер, без проб замены воркера; ожидание `ok {"requests": N}` | B1 |
| `@pass-call <клиент> <запрос>` | одна проба двери `callback <кластер>`: слушатель обратного вызова, адрес — `X-W2C-Pass-Console` последнего `@pass-open`, порт — `{cport}`; клиент — лист `stand.json` или `null`, исход — закрытая форма `@tls`, с подстановками `$name` | B1 |
| `@pass-step <метка> [<имя>]` | ждать вызов шага операции на подставном воркере (маршрут `door.pass.operations.step`, [P/06.9](../../../06-console/ru/spec/06.9-console.norms.md) N2; вызов узнаётся по пути: без начальных и конечных `/` путь равен маршруту, запрос не учитывается) и держать его: не дольше 40 с (`OPS_STEP_WAIT` + 2 × `OPS_TICK`). Ожидание `ok <JSON>` — принятое подмножеством `{method, path, ticket, headers, id, index, body, secret, expected, opcount}`, `secret` без значения — `@absent`. `@pass-open` вызовы шага не берёт, `@pass-seen` считает всё принятое | ADR-0095 |

| `@stream-wait <метка> <с>` | судится первое новое сообщение: подмножество JSON из `data:`, не совпало — FAIL шага: иначе шаг не отличил бы пропуск сообщения; строка `id:` без `data:` — не сообщение, пропускается; сообщения — блоки, разделённые пустой строкой (CRLF читается как LF), строки `data:` блока склеиваются через LF, после двоеточия снимается один пробел, блок без завершающей пустой строки ещё не сообщение, текст `data:` не в JSON не совпадает; `$name` связывается, как в словаре. Ожидание `ok <JSON>`. Срок вышел или поток закрыт раньше сообщения — FAIL шага | V/11 |
| `@stream-none <метка> <с> ~<текст>` | за срок сообщения с этим текстом не было (увиденные за срок сообщения считаются прочитанными: следующий `@stream-wait` судит только более поздние); поток закрыт — несовпадение: молчание закрытого потока ничего не доказывает; срок считается сном: README урока называет причину; ожидание `ok` | V/11 |

| Что | Срок |

Подстановка `{cport}` — порт слушателя обратного вызова консоли: стенд ставит `CONSOLE_CALL_PORT={cport}` у консоли с комплектом (договор файла окружения). Профиль консоли объявляет `keys.pass_stand: 1`; без него проверки этого стенда не исполнены (не GREEN). Без комплекта подстановки нет: слушатель не открывается.

### Стенд группы хранилища

Группа raft из нескольких демонов хранилища на одной машине стенда — приёмка [главы 1.3](../../../01-store/ru/acceptance/3/README.md)
(сц. 07, 17, 18, 25–29, 31). Свойства группы — состав, выборы, перезапуск, дверь без голоса, `recover`, `import` в группу — стенд
видит снаружи; учения на настоящем кластере ([системная приёмка](system/README.md)) этого больше не заменяют
(ПРАВИЛА-РАБОТЫ.md § 4; план `automatic group scenarios plan (2026-10-30, for people)`, принят «Архитектором»
2026-10-30). Нормы — P/01.3 N1.3 (`group`, `door`, `floor`, `import`, `leader_wait`, `repeat`), N1.6, N3 «восстановить
хранилище»; новых норм раздел не вводит.

- **Члены** — по имени `<id>`: голосующие `s1`…`s5`, двери без голоса `d1`, `d2`. Имя сервера листа члена — его `<id>`
  (лист `configstore.<id>` у голосующего, `configstore-door.<id>` у двери; договор сертификата роли `cert`); адреса — петля
  `127.0.0.1`, порты раздаёт раннер (свободные на петле; в описании комплектов адресов нет): `{raft@<id>}`, `{api@<id>}` —
  подстановки в флагах, запросах и пробах. Партнёров член узнаёт как в норме: вступающий — флагом `-join {api@<id>}`
  (P/01.3 N1.3 `join`), дверь — `-voters`, перезапуск — из своего `member.json`; списка пиров раннер не передаёт. Имя пира
  демон сверяет с `<id>` участника, не с хостом адреса (адрес — петля у всех).
- **Комплекты** — описание `inputs/group.json` приёмки главы 1.3: один центр группы, лист на каждого члена; раскладка — договор
  `kit` (`ca.pem`, `<роль>/server.pem`, `<роль>/server.key`), `revoked` пуст, `ca.next.pem` нет.
- **Сборка хранилища — признак профиля реализации `keys.store_build`**: `raft` — сборка с группой, сценарии стенда
  исполняются; `box` — хранилище коробки без raft, законное по P/01.3 N1.3 `box` (один голосующий; `-group-size 3`/`5`,
  `-join`, `-door` — отказ старта, код 2): сценарии стенда группы — not_applicable, в итог не входят и не красные, зачёт
  урока — без них; признака нет или иное значение — сценарии не исполнены (not_executed, как без `keys.tls_stand`; не
  GREEN). Отказы сборки `box` проверяет сц. 04/16 хранилища стенда и чтением (P/01.3-01); стенд группы её не судит
  (решение «Архитектора» 2026-10-30).
- **Запуск члена** — команда хранилища «Стенда» (та же, что у хранилища стенда, с флагом скорости стенда, если он есть), с окружением `BOX_ID=<id>`, `SERVER_NAME=<id>`, `PLATFORM_DIR={data}/<id>` (на стенде трёх серверов — `PLATFORM_DIR` его сервера), и
  подстановки члена: `{data}` — его `PLATFORM_DIR`, `{rundir}` — `{data}/run`, `{socket}` — `admin.sock` там же, и `{rights}`. Шаблон несёт их в своих флагах `-dir {data}/configstore`, `-sockets {rundir}`, `-rights {rights}`, `-max-body {body_limit}`, `-max-value {row_ceiling}` ([подстановки](PROFILE.md#подстановки)), поэтому каталог хранилища члена — `{data}/configstore` его `PLATFORM_DIR`. Раннер дописывает только эти флаги: `-id <id>`, `-tls <каталог комплекта>`,
  `-api {api@<id>}`, `-tuning lan`; голосующему ещё `-raft {raft@<id>}` (адрес посредника раннера,
  который член называет партнёрам) и `-raft-bind <свой порт>` (где он слушает; P/01.3 N1.3 «Флаги демона»). Прочие флаги — из строки
  директивы как написаны (`-bootstrap`, `-join`, `-group-size`, `-force`, `-door`, `-voters`). Шаблон не содержит ни одного дописываемого флага, и флаг скорости стенда — не один из них: повтор флага — отказ старта (P/01.3 N1.3; ответ «Архитектора» по P01.86).
- **Двери члена**: `store@<id> <запрос>` — дверь P/01.1 сокетом роли сценария члена (роль называет README главы, `@as`
  меняет); `admin@<id> <запрос>` — через его `admin.sock` (не пересылается: запись — у лидера).
- **Границы**: между сценариями раннер останавливает всех членов и удаляет их каталоги; комплекты — на сценарий.

| Форма | Смысл | Урок |

### Стенд кластера из трёх серверов

Три сервера платформы на одной машине стенда — сц. 05 [системной приёмки](system/README.md). Отказ сервера, перенос единиц и
возврат стенд видит снаружи, поэтому учение на настоящем кластере их больше не заменяет (ПРАВИЛА-РАБОТЫ.md § 4; этап 2 плана
`automatic group scenarios plan (2026-10-30, for people)`). Нормы — P/04 N1.4a, N3 «вырвать питание», P/05 N1.4, P/01.3 N1.3, P/02.4 N3
«старт сервера»; новых норм раздел не вводит. Раздел продолжает «Стенд группы хранилища» и форму `on <сервер>` словаря.

- **Серверы** — `srv-a`, `srv-b`, `srv-c`. У каждого свой `SERVER_NAME`, `BOX_ID` и `PLATFORM_DIR` — как у `on <сервер>`
  словаря (`{data}` у `srv-a`, `{data}/servers/<сервер>` у прочих); этот каталог — том сервера: его объекты, корень событий и
  замки присутствия. У каждого свой ресурс со своим `{rport}`. Кольцо ключей одно (`SECRETS_KEY`).
- **Хранилище** — группа из трёх голосующих по «Стенду группы хранилища»; `<id>` члена — имя сервера. Комплекты — описание
  [`system/inputs/cluster.json`](../../acceptance/system/inputs/cluster.json) (`@group-setup`); `-dir` члена — `<PLATFORM_DIR>/configstore`,
  `-sockets` — `<PLATFORM_DIR>/run`; файл `{rights}` раннер выводит из манифестов стенда командой вывода прав. Каждый процесс
  говорит с членом своего сервера: `{socket}` и `PLATFORM_STORE` — сокеты этого члена. Поэтому выключенный сервер уносит один
  голос, а не хранилище у соседей.
- **Контроллеры и консоль** — по одному контроллеру на манифест и одна консоль, все на `srv-a`; двери `console`, `console2`.
  Сценарий `srv-a` не выключает: новый контроллер первые `LOST_AFTER` никого не судит (P/04 N1.4a `fresh_controller`), а
  учение проверяет контроллер с заранее наблюдёнными пульсами.
- **Воркеры** — `@start worker … on <сервер>` словаря, чтобы сценарий сам называл имена и порядок запуска.
- **Сборка хранилища — признак профиля `keys.store_build`** профиля `01-store`, как у стенда группы: `raft` — сценарий
  исполняется; `box` — not_applicable, в итог не входит и не красный, потому что группы у такой сборки нет; признака нет или
  иное значение — not_executed, не GREEN. Сценарий начинается с `@group-setup`, раннер планирует его тем же правилом.
- **Что нужно от профилей.** Новых команд и ключей нет. Прежние команды «Стенда» (`store`, `manifest-put`, вывод прав, `resource`,
  `worker`, `controller`, `console`) не вписывают сами порт, каталог, сокет и имя сервера: раннер подставляет `{data}`, `{socket}`,
  `{rport}`, `{server}` и окружение на каждый сервер. Нет нужной части в составе — ошибка состава до запуска.
- **Границы**: между сценариями раннер останавливает все процессы всех серверов, снимает посредников и удаляет каталоги.

| Форма | Смысл | Урок |
|---|---|---|
| `@server-start <имя>` | поднять сервер: член хранилища, затем ресурс. | `@power-pull <имя>` | выдернуть питание: посредник раннера на raft-адресе члена рвёт живые соединения и не принимает новых (как `@cut store@<id>`), затем раннер сразу шлёт SIGKILL всем процессам сервера — члену, ресурсу, воркерам; каталоги не трогает. | `@restart resource#<имя>` | SIGTERM ресурсу сервера, дождаться выхода, запустить той же командой с тем же `{rport}` и каталогом; ожидание `ok` — порт слушает и строка двери есть не позже 20 с. | дверь `admin@<имя> <запрос>` | дверь члена по «Стенду группы хранилища»; сц. 05 читает и пишет ею, потому что ему нужны строки всех семей | P/01.3 (2026-10-30) |

#### Стенд нескольких кластеров

**Кластеры** (M11/3). Кластеры `hold` (держатель), `m1`, `m2` — каждый со своим хранилищем, `{data}`,

**Ретранслятор** (P/09.2): четвёртый кластер стенда `relay`; его агент всегда открывает дверь ретранслятора
(`RELAY=1`, `RELAY_HOST=127.0.0.1`, `RELAY_PORT` — порт `{relay_port}` копии), посредник раннера стоит и перед ней. Копии ретранслятора стартуют раньше членов за ним: `@start agent <кластер> via relay` до копий ретранслятора — ошибка данных, вторая копия ретранслятора при живом члене `via relay` — сбой стенда. `@cut relay` рвёт дорогу ретранслятора
к держателю; двери членов к ретранслятору — свои посредники (`@cut <член>` рвёт дорогу члена, какой бы она ни была).

**Окружение пересылки** (M11/8; `@env` — [P/06.7](../../../06-console/ru/spec/06.7-console.norms.md) «Решает реализация» п. 2): консоль каждого кластера получает `CLUSTERS` — адреса консолей всех кластеров стенда
(`hold=<url>,m1=<url>,m2=<url>[,relay=<url>]`, без посредников; на стенде с комплектом TLS или у сценария с `@cut-route` значения — адреса посредников дорог раннера); процесс `domain` — `DOMAIN_CONSOLE_URL`, адрес двери
консоли домена; `SIGNER_URL` — только консоли `hold`. Комплекта TLS у стенда нет: двери на петле по `http://`
(P/02.4 N1.6). `Idempotency-Key` у `POST`, `PUT`, `DELETE` пути `/domain/…` двери `member <кластер> console` раннер
ставит, как у двери `holder`.

**Ожидания** стенда домена — формы словаря выше: `<код> <JSON>` подмножеством, `$name`, `@spoil($name)`, `@any`/`@absent`,
`@not`, `@time`, `~text` (например `~enc:v2:` — конверт кольца члена), `!contains`, `@exit`; у команд-векторов и `@carry` —
`ok <JSON>`, у `@join` — `ok` или `refused`, у `@move` — `<код> <JSON>` ответа двери. Сны (`@sleep`) с причинами — в README
приёмки главы.
