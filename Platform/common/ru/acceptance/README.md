# Стенд приёмки модуля «Платформа», M10 и M11

Текст производный от `acceptance/README.md`, руками не правится: источник — английский [`acceptance/README.md`](../../acceptance/README.md), правка идёт в него, русский пересобирается переводом (ADR-0121; ADR-0124 доп. (1) п. 4).

## Стенд — общий для приёмки уроков модуля «Платформа», M10 и M11

Раннер приёмки любого урока M10 запускает реализацию только через интерфейс, который реализация называет
в описании (нормы P/01.1, «Решает реализация» п. 10); её внутреннего API раннер не знает.

### Пример состава

Следующий `assembly.yaml` — схематический полный состав Platform, не поставленные профили или код реализации. Значения `example/…/acceptance.yaml` — условные пути относительно состава; замени их настоящими местами профилей. `modules` — карта канонических идентичностей модулей (имён каталогов уроков) в пути файлов профилей, а не список записей модулей.

```yaml
format: 1
modules:
  01-store: example/01-store/acceptance.yaml
  02-installer: example/02-installer/acceptance.yaml
  03-worker: example/03-worker/acceptance.yaml
  04-controller: example/04-controller/acceptance.yaml
  05-resource: example/05-resource/acceptance.yaml
  06-console: example/06-console/acceptance.yaml
  07-console-module: example/07-console-module/acceptance.yaml
  08-domain: example/08-domain/acceptance.yaml
  09-agent: example/09-agent/acceptance.yaml
  10-domain-console: example/10-domain-console/acceptance.yaml
```

Состав использует `format: 1`; каждый выбранный `acceptance.yaml` — `format: 2` профиля. В [форме состава](PROFILE.md#состав-и-идентичность-входов) только `format` и `modules`, без корневых сборки, команд, ключей или наследуемых умолчаний. Частичная карта допустима для подготовки, но цель с отсутствующим обязательным модулем блокируется до исполнения. Эти пути не объявляют поставленный backend, provider или успешный прогон.

### Раскладка по процессам (стадия C)

Реализация использует один микромодуль на процесс. Полные общие формы `acceptance.yaml` (версия профиля 2),
`assembly.yaml` (версия состава 1), подстановок, исполняемых адаптеров и конверта векторов определены один раз в
[«Профили приёмки и состав»](PROFILE.md). Следующие разделы назначают интерфейсы стенда для уроков.
Профиль описывает эти интерфейсы; сценарии и ожидания этим не меняются.

- **Профиль на микромодуль.** `acceptance.yaml` лежит в каталоге модуля; `module` — каталог урока из
  [`Platform/lessons.tsv`](../../../lessons.tsv) (`01-store` … `10-domain-console`); у профиля своя сборка (`build`),
  необязательные свои регрессии (`unit`), свои команды и адреса стенда (`stand`), ключи (`keys`), адаптеры (`adapters`) и
  публичные результаты сборки (`artifacts`). Профиль называет только свои команды — команды соседнего процесса в нём нет.
  Шаблоны команд ниже («Команда запуска», «Команда установки манифеста», команды векторов и директив) — ключи `stand`
  профиля процесса-владельца.
- **Состав стенда.** Корневой `assembly.yaml` (`format: 1`, `modules`) — только карта «модуль → файл профиля», без
  корневых команд и общей сборки. Стенд берёт соседей из этого состава; замена части (`--part`) переносит её профиль
  целиком — каталог, ключи, команды. Нужной части нет в составе — ошибка состава до запуска, не подмена соседом.
- **Рабочие каталоги и фазы.** Каждая команда исполняется из каталога своего профиля. Сборка — отдельная фаза до
  фиксации входов; во время приёмки пересборки нет. Профили, исходники и артефакты частей стенд фиксирует в паспорте
  прогона. Совпадающие имена алгоритмов у разных потребителей (`said-id`, `fresh-age`) — команды каждого потребителя,
  не одна общая.
- **Словарь стенда прежний.** Подстановки (`{data}`, `{socket}`, `{rights}`, `{port}`, `{rport}`, `{manifest}`,
  `{manifests}`, `{name}`, `{agent_tokens}` и прочие ниже), окружение процессов (`PLATFORM_DIR`, сокеты ролей, кольцо,
  `MANIFEST_DIR`, общий каталог местных дверей токенов) и директивы задаёт стенд по этому README и lifecycle уроков.
  Поля профиля не становятся переменными окружения процессов, HTTP-дверями или иным способом связи модулей.
- **Библиотеки.** P/03 — свой SDK воркера и тестовый воркер профиля 03 (команда `worker`); P/07 — упаковка опубликованных
  `console.*` сборкой профиля 07, без своего процесса и своей TSV-приёмки: сборки 06 и 10 берут эти байты до фиксации
  входов, процесс консоли каталог выгрузки во время работы не читает (lifecycle P/06); ретранслятор P/09.2 — режим
  агента того же модуля 09 (`RELAY=1`), не отдельный профиль.
- **Векторы.** Команда пакета векторов — исполняемая обёртка своей функции процесса-владельца по README пакета; формы
  входа и выхода задаёт README пакета (у `creates-key` и `near-of` — сырой id в stdout, их README «Команда стенда»).
  `expect`, который README пакета сравнивает подмножеством полей вывода, читает `{}` как строка `<код> <JSON>` словаря
  ниже: `{}` на любом уровне — ровно пустой объект; любой объект — `@any`; поля нет — `@absent`; у пакетов, которые
  сравнивают вывод целиком, `{}` и так ровно пустой (ACC-EMPTY-OBJECT-02, решение «Архитектора» 2026-10-26).
  Пакет без отдельного договора команды (раздел README пакета «Команда стенда» или строка команды ниже): вычисленный
  исход функции — нативный код 0 и одно значение JSON; маркеры отказа `@refuse`, `@bad`, `@skip` — строки JSON того же
  написания; положительное значение не JSON (hex ключа, имя, слово) — строка JSON; опубликованный `@exit 2` — нативный
  код 2, вывод не судится. Явные команды `stand` и сырые id (`creates-key`, `near-of`) — без изменений (ACC-VECTORS-CONNECT-04,
  решение «Архитектора» 2026-10-26; строка «Нативный исход» в README пакетов с маркерами).
  Таблица, у которой README пакета не называет нативной формы: одна колонка ожидания (`expect` или иное имя) — значение
  этой колонки по правилу выше; две и больше — нативный код 0 и объект JSON, ключи — имена колонок ожидания таблицы,
  значения — по колонкам, как в TSV (`@absent` — ключа нет); какие колонки — ожидание, называет README пакета (решение «Архитектора» 2026-10-27).
- **Единая команда векторов.** Необязательная карта профиля `vectors` и полный провод входа/выхода определены в
  [«Профили приёмки и состав»](PROFILE.md#единая-команда-векторов). README пакета назначает потребителя, таблицы,
  входные колонки, фикстуры и направления; реализация вычисляет собственный нативный исход. Нет назначенной записи —
  `blocked`, не PASS. Покрытие использует полный SHA выгрузки и SHA таблицы; строка — адрес только внутри этого пина.

- **Команда запуска** — шаблон с подстановками: `{data}` — новый пустой каталог данных экземпляра; `{socket}` —
  путь сокета двери хранилища (P/01.1); `{port}` — порт HTTP консоли на петле (урок P/06 и приёмки со стендом консоли); `{manifest}` — каталог
  манифестов стенда для процессов, которым он нужен (`MANIFEST_DIR`, P/02.3); команда хранилища его не получает и манифестов не кладёт; `{body_limit}` и `{row_ceiling}` — предел тела и потолок строки (N5 P/01.1);
  `{rights}` — путь файла прав, который раннер кладёт до запуска хранилища (P/01.2 N1.2): в P/01.1 — файл ниже
  («Сокеты ролей»), в главах P/01.2 и P/01.3 — готовый вход [`01-store/acceptance/2/inputs/rights.json`](../../../01-store/acceptance/2/inputs/rights.json), в приёмках, перенесённых из M10/4–11, — вывод прав из манифестов стенда командой вывода прав ниже (`{manifests}` — каталог манифестов
  стенда, `{deployment}` = `dep`); команда хранилища получает `{rights}`, а не `{manifest}` (журнал cammeta-python, урок 11
  № 29). Реализация называет, какие подстановки нужны каждому её процессу.
- **Команда установки манифеста** `manifest-put` (P/02.3 N3 «Смена манифеста») — шаблон с `{socket}` и `{file}`: кладёт один манифест
  через `admin.sock` хранилища (`{socket}`); код 0 — положена, иной — отказ. Раннер ставит ею манифесты стенда по одной
  в порядке «Манифесты» ниже, после готовности хранилища и до первого `@start` (пилот хранилища, A6).
- **Команда вывода прав** (P/02.5 N2) — шаблон с `{manifests}` (каталог манифестов), `{deployment}` и `{file}`: пишет файл прав по
  P/02.5 N1.4; код 0 — файл записан, иной — отказ генерации. Реализация называет её в описании (P/02.5 «Решает
  реализация» п. 1). Варианты приёмки P/02.5 (`5/variants/`) зовут её с `{deployment}` = `dep` (сверка python и go
  M10/6–11).
- **Команда сверки прав** (P/02.5 N2 `--check`, N3 «установить») — ключ `stand.rights-check` профиля `02-installer`, шаблон с
  теми же подстановками, что у команды вывода прав (`stand.rights`): `{manifests}` — каталог манифестов, `{deployment}`, `{file}` —
  файл прав, который сверяется (не пишется); исход — код: 0 — файл по смыслу равен выводу прав из манифестов, иной — расходится.
  Варианты приёмки P/02.5 с `check.tsv` зовут её на каждый случай с каталогом манифестов варианта, `{deployment}` = `dep` и
  `{file}` = `check/<case>.rights`; код сравнивается с колонкой `code` (`0` | `!0`). Нет ключа в профиле — случаи `check.tsv`
  не исполнены (не GREEN и не исход реализации). Подстановки `{specs}` в словаре стенда нет (решение «Архитектора» 2026-10-30,
  вопросы норм аудита Gemini, P/02 п. 3; C02-RIGHTS-CHECK-STAND-01).
- **Команда кольца** — шаблон `ring {file}`: создаёт кольцо ключей по [договору запечатывания](../contracts/sealing.md) (`w2cctl secrets new` реализации, P/02.4 N1.9) в файле
  `{file}`; раннер зовёт её до первого процесса с `{file}` = `{data}/etc/secrets/platform.key` (решение «Архитектора»,
  второй пилот); код 0 — кольцо создано. Владелец и режим файла кольца на стенде — раздел «Стенд без root» ниже
  (I02-RING-FIXTURE).
- **Команды копии** (P/01.3 N1.3 `copy`, `admin_ops`): `backup` — шаблон с `{socket}` и `{file}`: копия хранилища через
  `admin.sock` в файл, код 0 — копия снята; `import` — шаблон с `{data}`, `{file}` и `{index_base}`: перенос копии в
  свежий каталог остановленного хранилища (P/01.3 N1.3 `box`), код 0 — перенесено, иной — отказ. Реализация называет
  обе (P/01.3 «Решает реализация» п. 4, 11; пилот хранилища).
- **Команда загрузки одного файла манифеста** (P/02.1) — шаблон с `{file}`; код выхода 0 — манифест, иной — отказ, текст
  отказа называет файл (нормы P/02.1, «Решает реализация» п. 3).
- **Процессы нескольких ролей** (урок P/03 и далее): реализация называет команду запуска каждой роли — хранилище,
  консоль, контроллер, воркер, позже ресурс; команда воркера получает имя подстановкой `{name}` (аргумент), окружение —
  `BOX_ID` (постоянная коробка стенда) и `SERVER_NAME` (P/02.4 N1.2); из окружения имя воркер берёт только по `slot.name_env` своего манифеста
  (P/02.1 N1.2a), и раннер ставит эту переменную, если манифест её объявил (`testsub2` — `TALLY_NAME`; у `testsub` её нет). В приёмках, перенесённых из уроков до M10/6 (права — ныне P/01.2), раннер читает хранилище ролью с полными правами на префикс подсистемы.
- **Ресурс** ([P/05](../../../05-resource/ru/spec/05-resource.norms.md)): команда запуска ресурса сервера с подстановкой `{rport}` — порт его двери; раннер ждёт порт
  и строку `platform/doors/<host>` до первого шага. Сценарию, которому нужны пульсы других серверов, ресурс — на сервере
  контроллера: объекты кластера процесс читает через ресурс своего сервера (P/04 N3 «проход()» шаг 0; ADR-0084 доп. (2) R17).
- **Сокеты ролей** (P/01.2, P/01.3 N1.3 `sockets`): и на коробке хранилище открывает сокет на роль (`<роль>.sock`, `admin.sock`) по файлу
  прав; раннер звонит сокетом роли сценария. `{socket}` — путь `admin.sock`; сокеты ролей лежат рядом, в том же каталоге, плоско (P/01.3 N1.3 `sockets`).
  `{socket}` — дверь с полными правами (подготовка). Урок 1 прогоняет сценарии ролью `acc` — права read и write только на
  `acc/*`, сокет `acc.sock` рядом с `{socket}`. Раннер кладёт в `{rights}` ровно этот файл (форма — P/01.2 N1.2):
  `{"roles": {"acc": {"group": "acc", "read": ["acc/*"], "write": ["acc/*"], "delete": ["acc/*"]}}}`.
  Удаление — отдельное действие (P/01.2 N1.3 `allowed`), в файле оно названо явно.
- **Один каталог данных** `{data}` на экземпляр — это `PLATFORM_DIR` (P/02.4 N1.2 «Канал настройки и раскладка»;
  второй пилот, N-4). Стенд переводит подстановки в окружение P/02.4 N1.2: `PLATFORM_DIR={data}`,
  `PLATFORM_STORE=configstore://<сокет роли>`, `CONSOLE_PORT={port}`, `RESOURCE_PORT={rport}`, `BOX_ID`, `SERVER_NAME`,
  `SECRETS_KEY={data}/etc/secrets/platform.key` — кольцо по раскладке P/02.4 N1.1, его создаёт раннер командой кольца до первого процесса; имя воркера — аргументом `{name}`. Раскладка — по P/02.4 N1.2: хранилище
  `{data}/configstore`, объекты `{data}/objects`, события `{data}/events`, замки присутствия `{data}/events/.workers`.
  Корень событий сервера выводится однозначно — `{data}/events` его `PLATFORM_DIR` (стенд не задаёт `RESOURCE_ROOT` и
  `EVENTS`), поэтому отдельного ключа корня событий у «Стенда» нет.
  Файл настроек сервера — `W2C_ENV={data}/etc/w2c/w2c.env` (P/02.4 N1.2: каталог `roles/` — рядом с `w2c.env`,
  другого места нет), файлы ролей — `{data}/etc/w2c/roles/<роль>.env`; у сервера `on <сервер>` — тот же путь в его
  `PLATFORM_DIR` `{data}/servers/<сервер>` (выбор владельца раннеров, cammeta-acceptance e3ec5c3).
- **Манифесты** ставятся командой `manifest-put` в порядке зависимостей: `testsub`, затем `testsub2` (она ссылается на `testsub`: `about`,
  `near`, `worker.requests`); загрузка каталога (P/02.1 N3) видит обе.
  Манифест `testsub2` объявляет `console.shell` и `console.files`: установка читает эти файлы рядом с файлом манифеста (P/02.3 N3
  «Смена манифеста»), поэтому стенд кладёт рядом с копией манифеста всё содержимое
  [`06-console/acceptance/5/inputs/testsub2/`](../../../06-console/acceptance/5/inputs/testsub2) под теми же путями — на каждом стенде, где
  ставится `testsub2`, не только в приёмке 6.5 (ADR-0094 B7).
- **Корень консоли** (`CONSOLE_ROOT`) называет README урока: глава 6.2 — `testsub2` (короткие пути `/tallies`),
  остальные — `testsub`, вторая подсистема смонтирована под `/testsub2`.
- **Команда печати отчёта прохода** контроллера `<sub>/controller/pass` ([P/04](../../../04-controller/ru/spec/04-controller.norms.md)) — шаблон с `{data}` и `{sub}`;
  печатает текущий объект отчёта или ничего, если его нет; по ней раннер ждёт смены отчёта (нормы P/04,
  «Решает реализация» п. 9).
- **Команды векторов платформы** `order`, `shrink-victim`, `shrink-allowed`, `workers-script` (стадия A, A6; ADR-0084;
  `shrink-allowed` — решение «Архитектора» 2026-10-20, № 12 разбора ревью стадии B 3–5) — шаблоны с
  `{input}` — путь файла входа; вывод — JSON в stdout; код 0 — вычислено, 2 — вход не по форме. Пакеты —
  `Platform/04-controller/vectors/order/`, `…/shrink-victim/`, `…/shrink-allowed/` (P/04 N3 «нехватка(), заказать()», «сократить()»),
  `Platform/02-installer/vectors/workers-script/` (P/02.4 N1.5): раннер читает `cases.tsv` пакета (UTF-8, TAB, строки
  с `#` и пустые пропускаются, первая непропущенная — заголовок), на каждую строку пишет ячейку `input` байт в байт во
  временный файл, зовёт команду пакета с `{input}` и сравнивает stdout с ячейкой `expect` как JSON по значению,
  целиком (порядок ключей объекта не важен; массив — по длине, порядку и элементам); код ≠ 0 или не JSON — FAIL
  строки; итог пакета — строки по `case`. Реализация называет шаблоны в описании, как прочие команды «Стенда».
  Команды `exec` и `install-order` профиля `02-installer` и `door-token-verify` профиля `03-worker` отвечают конвертом
  `{"result": …}` — протокол в README их пакетов (`Platform/02-installer/vectors/exec/`, `…/install-order/`,
  `Platform/common/vectors/door-token/`; догадка стадии C I02-STAND, решение «Архитектора» 2026-10-23).
  Команды `group-of` (профили `03-worker`, `04-controller`: адрес → `{group, fault}`) и `fresh-age` (профили `04-controller`,
  `06-console`: возраст → `true`/`false`) — без конверта, по README их пакетов `Platform/common/vectors/group-of/`,
  `…/fresh-age/` (догадка стадии C C04-VECTOR-01, решение «Архитектора» 2026-10-23).
  Команды `rid` и `request-digest` профиля `06-console` — без конверта: `{"status": …}` и `{"canonical", "sha256"}`; вход —
  в README пакетов `Platform/06-console/vectors/rid/`, `…/request-digest/` (догадка стадии C C06-F2-IO-01, решение
  «Архитектора» 2026-10-23).

### Стенд без root

Стенд запускается непривилегированным пользователем; продукт строг, стенд — нет (догадки стадии C I02-RING-FIXTURE,
C04-STAND-GID-01, решение «Архитектора» 2026-10-23):

- **группы платформы** (`w2c-events`, `w2c-secrets`, `w2c-store` и прочие P/02.4 N1.1) на стенде — текущая (основная) группа процесса,
  одна у всех ролей, на любой ОС и есть ли такая группа на машине или нет (деревья событий — договор журнала событий
  `modes`; ACC-EJ-STAND-GROUP-01, решение «Архитектора» 2026-10-28); продукт требует системные группы без запасного пути;
- **корни** `{data}/config` — 2770, `{data}/objects` — 2770, `{data}/events` — 2771 (режимы P/02.4 N1.1 `dirs`; иных корней
  нет; каталоги внутри `objects` — 0775 по P/05 `disk`, это не корни) создаёт команда запуска роли профиля до старта
  процесса, если их нет, — этими режимами, текущими uid/gid (группа на стенде — текущая); существующие права и владельцев не меняет; процесс
  роли корней не создаёт (P/02.4 N1.1 `dirs`); `PLATFORM_DIR` — абсолютный путь (STAND-ROOTS-CLEAR-01, решение «Архитектора» 2026-10-27);
- **кольцо ключей** — команда кольца выше создаёт новый файл (байты — по договору запечатывания) с владельцем — текущими
  uid/gid и режимом 0640; существующий файл не заменяет — ненулевой код; владелец `root:w2c-secrets` продукта (P/02.4 N1.9)
  стендом не проверяется;
- **точка входа процесса на стенде** — команда профиля (например, `controller-stand <sub>`): процесс подключается к хранилищу
  своей ролью (`PLATFORM_STORE` роли), не `admin`.

Дополнительная проверка полного ключа (R29-01, P/01.1-16,22): на отдельном экземпляре
с правами на acc/ проверить ключи этого префикса полной длиной 200, 201, 213, 1024 и 1025
UTF-8-байт, включая кириллицу и четырёхбайтные символы. Первые четыре проходят правило двери,
1025 даёт 400 badkey без записи; тот же набор проверить в непустом guard.key. У существующего
стража использовать его фактическую версию, у отсутствующего — index="", чтобы не попасть
в отказ сравнения версии. Для файловой реализации отдельно проверить её объявленный предел:
допустим более ранний badkey, но порог 200 сам по себе не является нормой платформы.
Это отдельная оснастка сверх сценарного TSV; тестировать полное UTF-8-представление, не число символов.

Сценарии прогоняются через дверь хранилища (урок, N2) любой реализации; путь к двери (unix-сокет роли или стенд с той же дверью) — параметр стенда. Роль прогона — `acc` («Стенд» выше): полные права на префикс `acc/` и ни на что больше. Для **каждого сценария, в том числе при повторном прогоне**, раннер создаёт новый изолированный экземпляр
хранилища с пустыми прикладными строками и пустой памятью идентификаторов записи `id`. В частности,
пусты оба тестовых префикса — `acc/` и `other/`. Очистка строк `acc/<сценарий>/` в прежнем экземпляре
недостаточна: она не снимает память повторов. Версии не обязаны начинаться с заданного числа.

Подготовку экземпляра, его каталога данных и прав делает раннер до начала сценария; проверяемые запросы
идут только от указанной роли с правами на `acc/`. Сценарий 21 не получает дополнительных прав на `other/`: до его первого шага раннер в подготовке (не проверяемый запрос)
записывает строку `other/21-rights/c9` `{n: "1"}` через `admin.sock` экземпляра (`{socket}` «Стенда»); шаг 6 видит её имя
и версию без значения, хотя права чтения на `other/` у роли нет (N3 «перечислить»). В сц. 24 шаг 7 — query у `POST` не
читается, шаг 8 — тело у `GET` не читается; в сц. 26 шаги 9–10 — `Infinity` и BOM в теле (N2.1).
Параллельные сценарии используют разные экземпляры и не разделяют ни строки, ни память `id`.

Параметры каждого экземпляра (N5 урока): потолок строки **524288 байт**, предел чтения HTTP-тела
**1048576 байт**. Раннер сверяет оба значения до сценариев поведением на пробном экземпляре, полученном тем же
способом: тело ровно 1048576 байт доходит до разбора JSON (ответ не `413`), 1048577 байт — `413 toolarge`
с `limit` 1048576; вес `items` ровно 524288 байт записывается, 524289 — `413 toolarge` с `limit` 524288.
Изолированный экземпляр раннер получает способом, который реализация назвала в описании (нормы,
«Решает реализация» п. 10). Если параметры нельзя обеспечить или сверка не сошлась, прогон не выполнен;
нельзя подменять ожидаемые байты под имеющиеся настройки.

Сценарий 15 после раскрытия `@big` посылает тела 524348 и 524344 байта: оба меньше предела тела,
но вес `items` равен 524292 и 524288 байтам. Так проверяется именно потолок строки.
Сценарий 22 посылает тело 4194364 байта, больше 1048576: отказ возникает до разбора JSON и проверки веса.
Раннер передаёт байты тела из `request` после подстановок, без повторной сериализации или иных добавлений.

### Протокол адаптера швов

Это общая нормализация приёмки для `seams.tsv` урока, не API продукта, новая дверь процесса или сгенерированный пакет. [Грамматика швов P/02](../../../02-installer/ru/forms/README.md#точная-грамматика-швов-без-http) задаёт четыре разделённые TAB колонки `scenario`, `step`, `request`, `expect` и шаги подряд с 1. Сохраняй заданную формой владельца длительность жизни нового адаптера и временных корней, относится ли она к сценарию или к случаю; протокол не переносит изменяемое состояние фикстуры через эту границу. Шов наблюдает настоящий вызов и его эффекты; он не заменяет обычный процессный сценарий, native-вектор, соседний стенд или проверку чтением, которые не исполнил.

Вход модели содержит нормы, формы, схемы, договоры и протоколы. Векторы и сценарии остаются только у судьи. Каждый нужный адаптеру интерфейс, форма payload, точная обязательная кодировка, порядок полей или словарь отказов должны быть определены в этом нормативном входе, не только таблицей тестов или фикстурой. Судья передаёт настоящие входные значения без ожидаемого результата; необходимое определение только в векторе/сценарии — пробел нормы, не право адаптера читать ожидания.

#### Владение процедурами и peer

Поверхность `call` в каталоге отказов означает процедуру; `peer` — проверку, принадлежащую другому уроку ([каталог P/02](../../../02-installer/ru/forms/README.md#каталог-отказов), [каталог P/04](../../../04-controller/ru/forms/README.md#входы-и-отказы)). Ни одна поверхность не создаёт новую местную HTTP-операцию. Сохраняй исходное условие и владельца выбранной строки: её точные код, слово, обязательные поля, заголовки и форма ответа действуют только там, где их задаёт владелец. Отсутствующая числовая проекция `-` не получает выдуманный статус или код выхода. Поверхность `peer` отличается от команды-вектора домена `peer` в [командах-векторах домена](#команды-векторы-домена) и от выбора внутренних имён функций реализацией.

#### Вход и наблюдение CALL

`CALL <name> <JSON>` поглощает одно значение JSON после имени `[a-z][a-z0-9-]*`; порт и его нормализованные вход/выход принадлежат README форм урока. Порты приспосабливают обычные функции, команды или HTTP-пути реализации, а не требуют предоставить такое частное API. [Нормализации CALL P/02](../../../02-installer/ru/forms/README.md#нормализация-call) и разделы швов [P/03](../../../03-worker/ru/forms/README.md#швы), [P/04](../../../04-controller/ru/forms/README.md#швы), [P/05](../../../05-resource/ru/forms/README.md#швы), [P/06](../../../06-console/ru/forms/README.md#швы-и-этапы), [P/08](../../../08-domain/ru/forms/README.md#швы-и-этапы), [P/09](../../../09-agent/ru/forms/README.md#швы-и-этапы), [P/10](../../../10-domain-console/ru/forms/README.md#швы-и-этапы) задают вмешательство фикстуры и наблюдения. Применяй только нормализацию названного владельца; не переноси умолчания другого порта, не переименовывай исходы и не вводи неназначенную оболочку результата.

Вызывай настоящую реализацию и получай наблюдения из её результата, строк, байтов или записанного I/O. Не передавай реализации ожидание и не возвращай его готовым ответом. Допустимо только объявленное источником дополнение фикстуры: явные raw-строки и текст family-read — полные входы, которые не исправляют. Паника, постороннее исключение, ошибка транспорта или неисполненный вызов не являются обычным отказом предметной операции. В частности, P/02 `command` наблюдает нуль против ненуля только там, где владелец не задал точный код; неожиданное падение его не удовлетворяет.

Ожидания CALL JSON используют действующие правила ожиданий этого словаря: рекурсивное подмножество объекта, точные пустые объекты, точные массивы кроме явно названного неупорядоченного случая, сравнение чисел по числовому значению при отличии булевых значений, строк и null от чисел и фиксацию привязок только после совпадения всего шага. Ожидание-подмножество не отменяет полную форму результата владельца. RUN, управление файлами/часами/параллельностью и сравнения названных потоков сохраняют грамматику P/02; грамматика запроса шва shell не исполняет.

#### Явный тестовый мост швов

Этот вновь выбранный мост — отдельный договор стороны тестов. Это не существующий ключ `stand.call` или `adapters.call`, не конверт native-векторов и не обязательное API продукта. Отдельный дескриптор называется `SEAM_BRIDGE.json`; судья явно передаёт его путь для выбранного случая, без поиска в рабочем каталоге или профиле. Не вводятся угаданная команда, поле формата 2 профиля, поле формата 1 состава, маршрут платформы или рабочий флаг. Настоящие идентичность receiver и вызов входят в доказательства прогона. У нынешнего раннера без такого receiver — `MissingBinding`/`NOTEXEC`; публикация формата его не реализует и не активирует.

Дескриптор — замкнутый объект JSON с ровно обязательными `format` (целое `1`), `source_pin` (полный SHA Source, выбранный для случая), `scope` (непустая точная строка) и `bridge`. `bridge` замкнут и содержит обязательные `identity` и `invoke` точных форм идентичностей файлов и вектора аргументов D7 ниже. Эта тестовая идентичность Source не является алиасом `spec_version` профиля, сохраняющего опубликованный смысл Git-SHA выгрузки; настоящая связь Source/выгрузки записывается без новой проверки равенства/неравенства двух строк. Общего объекта roots нет: подготовка, пути и границы новых процесса/состояния остаются по действующему владельцу Source.

Каждый последовательный UTF-8 JSONL запрос — замкнутый объект с ровно обязательными полями:

| Поле | Обязательное значение |
|---|---|
| `format` | Целое `1`, не булево значение. |
| `scope` | Точный scope дескриптора. |
| `request` | Непустой идентификатор, уникальный внутри процесса моста. |
| `method` | `call` или `peer`, только по выбранной публичной привязке Source. |
| `name` | Точный публичный токен нормализованного порта/проверки, выбранный этой привязкой. |
| `input` | Однократно декодированный вход JSON владельца Source, не ожидаемый результат или ответ судьи. Объявленные Source управляемые ответы зависимостей остаются входами; не изготавливай их из ожидания. |

Судье принадлежит полный контекст нормализации запроса: полный пин Source, таблица относительно Source и её raw SHA256, канонический владелец, настоящие исходные ячейки id и scenario/step, физическая строка источника, точная нормализованная привязка порта/peer и её точная публичная ссылка normalizer. Он фиксирует контекст из неизменяемого Source до dispatch и связывает со scope/request. Контекст не выводится из ответа provider, короткого имени порта или написания scope. Метаданные Source/таблицы/строки/selector/normalizer/evidence/expectation provider не передаются. Шестипольный запрос таких полей не получает. [Обёртка source-cell](../contracts/source-cells.md), где объявлена, декодируется ровно один раз перед действующей грамматикой шва; вложенный вход Source не исправляется и не переписывается численно.

Судья должен машинно закрыть процессам адаптеров чтение файлов векторов/сценариев с ожиданиями; одно отсутствие полей ожидания в кадре ещё не такая изоляция. Ему принадлежит отрицательный контроль каждой выбранной цели тем же адаптером над намеренно сломанным продуктом; зелёный результат над сломанным предметом означает провал средства проверки, не квалификацию продукта. Настоящие изоляция и контроли должны быть показаны; их исполнение нынешним receiver не предполагается. Код адаптера независимо читается до вывода, что генерация доказана. Отчёт модели раскрывает только имя случая, якорь нормы и класс расхождения, никогда ожидаемый ответ. Полные raw-доказательства случая и сравнение ожиданий остаются в частной записи судьи; адаптер во время работы получает только свой объявленный входной кадр, не эту запись.

`CALL <name> <JSON>` выбирает `call`, точный публичный токен и однократно декодированный вход JSON. Строки `call` и `peer` каталога исполняются только при настоящих входе, цели и именованной привязке в Source. `peer` вызывает существующие публичные проверку/дверь другого владельца; не создаёт местные HTTP API, peer-порт или форму ответа. Native-вектор домена `peer` остаётся отдельным. Неизвестные имена и отсутствующие peer-вход/цель/публичный normalizer остаются точными `MissingBinding`/`NOTEXEC`, не угаданным вызовом или готовым ответом.

Мост возвращает одну сброшенную JSONL запись на запрос. Она замкнута и содержит ровно обязательные `format`, `scope`, `request`, `observation`: целое `format: 1`, точно совпавшие scope/request и ровно одну из замкнутых форм наблюдения. В ответе шва нет поля последовательности.

| Форма | Смысл и ограничение |
|---|---|
| `{kind: "value", value: <JSON>}` | Настоящий нормализованный строгий JSON результат Source, включая явный null. Числа сравниваются по числовому значению; булевы значения не числовые алиасы. Строка/маркер Source остаётся значением, если владелец явно не назначил другой исход. |
| `{kind: "absence"}` | Отсутствие/пропуск только там, где выбранный владелец Source явно их назначает. Не преобразуй null, пустое значение, неподтверждённое чтение или строковый маркер в отсутствие. |
| `{kind: "native", exit_code: <integer>, stdout_b64: <string>, stderr_b64: <string>}` | Настоящий нормальный native-выход процесса, назначенный владельцем, в `0..255` и точные raw-потоки в каноническом стандартном RFC 4648 Base64; пустые байты — пустая строка. Форма допустима только при назначенной Source поверхности native-выхода/raw-потоков. Это диапазон native-процесса транспорта, не ресурсный/QoS потолок или новый отказ платформы. |

Теги — метаданные транспорта, не Fault продукта и не новые слова предметного исхода. Нормальный native-выход находится внутри наблюдения только по назначению Source. Ранний EOF, ненулевой выход, сигнал, падение или расхождение протокола самого моста — ошибка инструмента, никогда не отказ платформы. Общие статус, тело, Fault kind или широкий отказ не выдумываются. К настоящему наблюдению применяются действующие нормализация статуса/слова/поля/заголовка/результата выбранного владельца и общее сравнение; сохраняются точные пустые объекты, длина/порядок массивов кроме явно назначенного Source неупорядоченного сравнения, сравнение чисел по значению с отличием от булевых значений/строк/null и привязки только после совпадения всего шага.

Одновременно ожидается один уникальный запрос и одно соответствующее наблюдение; нет приветствия, незапрошенных кадров, pipelining и лишней записи. Обе стороны — строгий UTF-8 JSONL, один физический LF на запись и сброс после ответа; диагностика идёт в stderr. Целочисленные поля кадров/дескрипторов моста и D7 используют целочисленные токены JSON, не булевы значения, дробную или экспоненциальную запись. Это касается только кадров транспорта; вложенный JSON Source сохраняет собственные числовые правила. Внешние кадры отвергают повторные поля, BOM и не-JSON числа. Внешняя запись не по форме означает ошибку инструмента, не отказ платформы. Процесс/состояние новые на объявленной Source границе сценария/случая; подготовка и допустимые прежние шаги внутри границы сохраняют смысл владельца. Не поставленный на деле выбранный dispatch RUN, `@file`, `@read`, `@parallel` или `@clock` остаётся отсутствующим/неисполненным, не PASS для исключённого хвоста.

На завершённой границе вызывающая сторона закрывает stdin, мост нормально выходит с нулём и не оставляет фоновый сервис с тестовым состоянием. Записывай настоящие выход, сигнал, тайм-аут и уборку. Намеренный сигнал проверяемой цели — наблюдение только по назначению Source; сигнал, убивший мост, его не заменяет. Общего тайм-аута, размера строки или ресурсного потолка здесь нет. Совместимость parser/транспорта не является квалификацией кандидата/native или физическими доказательствами, которым нужен D7.

#### Тестовые привязки доказательств D7

Это вновь выбранный договор стороны тестов для часов, носителя, хода и управляемых сбоев. Он не задаёт маршрут или рабочий флаг платформы и не добавляет поле в формат 2 профиля или формат 1 состава. Дескриптор и ответ provider не являются квалификацией. [Владелец эксплуатационной приёмки](../../../01-store/ru/spec/production-acceptance.md#доказательства-и-исходы) по-прежнему различает отсутствующие привязки, ошибки инструмента и измеренные нормативные исходы. Нынешний receiver раннера и настоящие квалифицированные provider должны быть указаны отдельно; публикация договора их не поставляет и не исполняет.

Дескриптор — отдельный тестовый вход. Его замкнутые верхние поля обязательны: `format` (целое `1`), `source_pin` (полный 40-hex коммит Source, выбранный для случая), `scope` (непустая точная строка изолированного случая) и `providers` (карта только с ключами `clock`, `storage`, `progress`, `fault`). Поле `spec_version` профиля сохраняет свой опубликованный смысл; записывай настоящую связь Source/выгрузки случая, не выводя их равенство или различие лишь из имён полей. Записи нужны только для возможностей, обязательных выбранному случаю; отсутствие нужной записи оставляет зависимую проверку `MissingBinding`/`NOTEXEC`.

Каждая запись provider — замкнутый объект с обязательными полями:

| Поле | Тип и привязка |
|---|---|
| `identity` | Замкнутый объект с обязательными `id` (непустая строка), `executable` и `artifacts`; необязательный `provenance_ref` — строка точной опубликованной ссылки. `executable` — замкнутый объект с абсолютным `path` и 64-lowercase-hex `sha256` байтов файла. `artifacts` — массив объектов того же вида `path`/`sha256`; пустой массив допустим. Назови все скрипты, интерпретаторы, конфигурации и результаты сборки, существенные для идентифицированного поведения provider. |
| `invoke` | Замкнутый объект с обязательными `argv` (непустой массив строк) и `cwd` (абсолютный путь каталога). `argv[0]` абсолютен и равен `identity.executable.path`. Судья запускает этот вектор аргументов без вставки shell, поиска PATH, globbing или подстановок. Явно названный интерпретатор входит в измеренный вызов. |
| `observer_ref` | Непустой непрозрачный идентификатор только из защищённого реестра наблюдателей судьи. Provider не может назначить заменяющий код наблюдателя. |
| `qualification_ref` | Непустой непрозрачный идентификатор только из защищённого реестра независимой квалификации судьи. Произвольный путь файла, булево значение provider или собственная квитанция не являются квалификацией. |

Судья измеряет запущенные executable/artifacts и записывает настоящую идентичность процесса/runtime-executable и scope. Он проверяет доверенную квитанцию квалификации относительно этой идентичности, Source, возможности, scope, наблюдателя и объявленного свойства, включая настоящие отрицательные контроли. Отсутствие вызова, прав, наблюдателя, квитанции или публичного договора payload случая — отсутствующая привязка. Известная неверная/устаревшая идентичность или противоречивый активный инструмент — ошибка инструмента. Объявление не даёт права записи ни в один защищённый реестр.

Процесс provider принадлежит одной объявленной возможности и изолированному случаю/scope. Он получает последовательные UTF-8 JSONL запросы в stdin и выдаёт одну сброшенную UTF-8 JSONL запись в stdout на запрос; stderr — текст диагностики. Нет приветствия, незапрошенных записей и pipelining. Во внешнем JSON нет повторных полей, не-JSON чисел и BOM. Каждую запись завершает один физический LF. Настоящие выход, сигнал и внешний тайм-аут процесса остаются доказательствами, не нормализованным отказом платформы. Объявленный конечный бюджет вызова/наблюдения случая остаётся отдельным; этот протокол не назначает общего тайм-аута или потолка размера.

| Поле запроса | Обязательный тип |
|---|---|
| `format` | Целое `1`. |
| `scope` | Точная непустая строка scope дескриптора. |
| `request` | Непустой идентификатор, уникальный внутри процесса provider. |
| `capability` | Объявленная процессу `clock`, `storage`, `progress` или `fault`; сменить возможность нельзя. |
| `operation` | `describe`, `activate`, `sample` или `deactivate`. |
| `payload` | Значение JSON по выбранной видимой модели норме, форме, схеме, договору или протоколу этой возможности; судья задаёт значения случая без ожидаемых ответов. Один тестовый вектор/сценарий не является определением payload. |

Объект запроса замкнут. Ответ тоже замкнут и содержит ровно `format`, `scope`, `request`, `seq`, `event`, `payload`. `format` — целое `1`; `scope` и `request` точно совпадают с запросом. `seq` — неотрицательное целое, начиная с `0` в первой записи и увеличиваясь ровно на 1 в каждой следующей, без сброса, пропуска и повтора. `event` равен `identity` для `describe`, `activation` для `activate`, `observation` для `sample` и `deactivation` для `deactivate`. `payload` имеет выбранную видимую модели нормативную форму возможности, не форму, определённую только частным случаем или вектором/сценарием. Payload `identity` ответа `describe` равен объекту identity дескриптора; судья всё равно независимо сверяет настоящую идентичность. Записи несут наблюдения, не вердикт квалификации или PASS; допустимое слово результата Source внутри наблюдения само не становится вердиктом.

Первый запрос — `describe`. После него provider неактивен: `activate` допустим только в неактивном состоянии; `sample` и `deactivate` — только в активном. Деактивация возвращает неактивное состояние; следующий цикл активации использует новые идентификаторы запросов и продолжает последовательность. Scope и идентичность provider не меняются во время процесса. Нормальное завершение — EOF stdin в неактивном состоянии, затем нормальный выход с нулём. Отсутствующие или лишние записи, ранний EOF, падение, сигнал, ненулевой выход и запись не по форме не удовлетворяют ожидаемый предметный отказ.

Порядок транспорта не доказывает эффект. Для каждой из четырёх возможностей независимый наблюдатель должен связать запрос активации, настоящую активацию на выбранной границе, настоящую целевую операцию/эффект/наблюдение и настоящую деактивацию. Он отвергает устаревшие, чужие scope/операцию, неверную фазу и обратный порядок. Настроенный hook, `Config.Now`, `@clock`, ACK/счётчик provider, текст EIO, manager kill, Raft Barrier или Shutdown сами не доказывают заявленную физическую область.

| Возможность | Публичная привязка случая и независимая квалификация | Обязательные отрицательные контроли |
|---|---|---|
| `clock` | Назови наблюдаемый или управляемый домен/единицу часов, настоящую потребляющую границу, независимую монотонную базу и калибровку. Сохраняй различие Source между стенными метками и монотонными сроками. | Должны выявляться только самоотчёт или неактивированный контроль, неверный домен, устаревший scope и обратное время. Выдуманного допуска перекоса нет. |
| `storage` | Назови настоящую идентичность файла/объекта, носитель/режим durability и наблюдаемые фазы эффекта/публикации/барьера, состояние до/после/квалифицированного открытия. Перезапуск процесса или возврат библиотеки не доказывает физическую durability. | Должны выявляться no-op барьер/сбой, неверный объект или фаза, ложные счётчики и устаревшие данные после открытия. |
| `progress` | Назови настоящие операцию, pin/output/sink/latch/cancel/release или другую границу Source, независимые наблюдения хода/ресурсов для объявленной нагрузки/бюджета. Активируй latch до оценки блокировки; задержка старта не остановка sink. | Должны выявляться frozen/no-op/чужая операция, неактивированный latch и ненаблюдаемые или отсутствующие release/progress. |
| `fault` | Назови точные опубликованные фазу Source, цель и поддерживаемую модель сбоя; независимо наблюдай активацию, эффект и порядок. Сохраняй доказанный no-effect против неизвестного или целиком опубликованного восстанавливаемого исхода. | Должны выявляться неактивная/no-op/неверная фаза/устаревшая активация и заявленный эффект без независимого свидетеля. Нет нового класса Fault или обещания общего rollback. |

Настоящие активированные положительные и отрицательные контроли квалифицируют только объявленное свойство наблюдателя/provider; неисполненный список контролей ничего не квалифицирует. Дескриптор и общий кадр не выдумывают схему payload возможности или отсутствующий настоящий provider. Если у выбранной возможности нет видимого модели нормативного определения payload или отсутствуют настоящий вызов/квалификация, сохраняй `MissingBinding`/`NOTEXEC`. Сохраняй нынешние утверждённые бюджеты владельца и неизвестные входы; нового числового потолка здесь нет.

### Подставной воркер передачи второго вида

Директивы [стенда передачи второго вида](pass/README.md) (ADR-0094 B1). Раннер их исполняет (README стенда pass, раздел «Исполнимость»). Воркера играет раннер: так сценарий держит запрос открытым и видит, что дошло до воркера. У директив `<кластер>` стоит на стенде домена, на стенде консоли его нет.

### Стенд группы хранилища

Группа raft из нескольких демонов хранилища на одной машине стенда — приёмка [главы 1.3](../../../01-store/ru/acceptance/3/README.md)
(сц. 07, 17, 18, 25–29, 31). Свойства группы — состав, выборы, перезапуск, дверь без голоса, `recover`, `import` в группу — стенд
видит снаружи; учения на настоящем кластере ([системная приёмка](system/README.md)) этого больше не заменяют
(ПРАВИЛА-РАБОТЫ.md § 4; план `automatic group scenarios plan (2026-10-30, for people)`, принят «Архитектором»
2026-10-30). Нормы — P/01.3 N1.3 (`group`, `door`, `floor`, `import`, `leader_wait`, `repeat`), N1.6, N3 «восстановить
хранилище»; новых норм раздел не вводит.

- **Члены** — по имени `<id>`: голосующие `s1`…`s5`, двери без голоса `d1`, `d2`. Имя сервера листа члена — его `<id>`
  (лист `configstore.<id>` у голосующего, `configstore-door.<id>` у двери; договор сертификата роли `cert`); адреса — петля
  `127.0.0.1`, порты раздаёт раннер (свободные на петле; в описании комплектов адресов нет): `{raft@<id>}`, `{api@<id>}` —
  подстановки в флагах, запросах и пробах. Партнёров член узнаёт как в норме: вступающий — флагом `-join {api@<id>}`
  (P/01.3 N1.3 `join`), дверь — `-voters`, перезапуск — из своего `member.json`; списка пиров раннер не передаёт. Имя пира
  демон сверяет с `<id>` участника, не с хостом адреса (адрес — петля у всех).
- **Комплекты** — описание `inputs/group.json` приёмки главы 1.3: один центр группы, лист на каждого члена; раскладка — договор
  `kit` (`ca.pem`, `<роль>/server.pem`, `<роль>/server.key`), `revoked` пуст, `ca.next.pem` нет.
- **Сборка хранилища — признак профиля реализации `keys.store_build`**: `raft` — сборка с группой, сценарии стенда
  исполняются; `box` — хранилище коробки без raft, законное по P/01.3 N1.3 `box` (один голосующий; `-group-size 3`/`5`,
  `-join`, `-door` — отказ старта, код 2): сценарии стенда группы — not_applicable, в итог не входят и не красные, зачёт
  урока — без них; признака нет или иное значение — сценарии не исполнены (not_executed, как без `keys.tls_stand`; не
  GREEN). Отказы сборки `box` проверяет сц. 04/16 хранилища стенда и чтением (P/01.3-01); стенд группы её не судит
  (решение «Архитектора» 2026-10-30).
- **Запуск члена** — команда хранилища «Стенда» (та же, что у хранилища стенда, с флагом скорости стенда, если он есть) и
  флаги, которые раннер ставит сам: `-dir {data}/<id>`, `-sockets {data}/<id>/run`, `-id <id>`, `-tls <каталог комплекта>`,
  `-rights {rights}`, `-api {api@<id>}`, `-tuning lan`; голосующему ещё `-raft {raft@<id>}` (адрес посредника раннера,
  который член называет партнёрам) и `-raft-bind <свой порт>` (где он слушает; P/01.3 N1.3 «Флаги демона»). Прочие флаги — из строки
  директивы как написаны (`-bootstrap`, `-join`, `-group-size`, `-force`, `-door`, `-voters`).
- **Двери члена**: `store@<id> <запрос>` — дверь P/01.1 сокетом роли сценария члена (роль называет README главы, `@as`
  меняет); `admin@<id> <запрос>` — через его `admin.sock` (не пересылается: запись — у лидера).
- **Границы**: между сценариями раннер останавливает всех членов и удаляет их каталоги; комплекты — на сценарий.

| Форма | Смысл | Урок |
|---|---|---|
| `@group-setup <путь описания>` | первым шагом сценария: раннер выпускает комплекты по описанию (путь — от каталога приёмки урока) по своим часам; ожидание `ok`; сценарий с этим шагом раннер планирует по `keys.store_build` (выше): `raft` — исполняет, `box` — not_applicable, иначе — not_executed | P/01.3 (2026-10-30) |

### Стенд кластера из трёх серверов

Три сервера платформы на одной машине стенда — сц. 05 [системной приёмки](system/README.md). Отказ сервера, перенос единиц и
возврат стенд видит снаружи, поэтому учение на настоящем кластере их больше не заменяет (ПРАВИЛА-РАБОТЫ.md § 4; этап 2 плана
`automatic group scenarios plan (2026-10-30, for people)`). Нормы — P/04 N1.4a, N3 «вырвать питание», P/05 N1.4, P/01.3 N1.3, P/02.4 N3
«старт сервера»; новых норм раздел не вводит. Раздел продолжает «Стенд группы хранилища» и форму `on <сервер>` словаря.

- **Серверы** — `srv-a`, `srv-b`, `srv-c`. У каждого свой `SERVER_NAME`, `BOX_ID` и `PLATFORM_DIR` — как у `on <сервер>`
  словаря (`{data}` у `srv-a`, `{data}/servers/<сервер>` у прочих); этот каталог — том сервера: его объекты, корень событий и
  замки присутствия. У каждого свой ресурс со своим `{rport}`. Кольцо ключей одно (`SECRETS_KEY`).
- **Хранилище** — группа из трёх голосующих по «Стенду группы хранилища»; `<id>` члена — имя сервера. Комплекты — описание
  [`system/inputs/cluster.json`](../../acceptance/system/inputs/cluster.json) (`@group-setup`); `-dir` члена — `<PLATFORM_DIR>/configstore`,
  `-sockets` — `<PLATFORM_DIR>/run`; файл `{rights}` раннер выводит из манифестов стенда командой вывода прав. Каждый процесс
  говорит с членом своего сервера: `{socket}` и `PLATFORM_STORE` — сокеты этого члена. Поэтому выключенный сервер уносит один
  голос, а не хранилище у соседей.
- **Контроллеры и консоль** — по одному контроллеру на манифест и одна консоль, все на `srv-a`; двери `console`, `console2`.
  Сценарий `srv-a` не выключает: новый контроллер первые `LOST_AFTER` никого не судит (P/04 N1.4a `fresh_controller`), а
  учение проверяет контроллер с заранее наблюдёнными пульсами.
- **Воркеры** — `@start worker … on <сервер>` словаря, чтобы сценарий сам называл имена и порядок запуска.
- **Сборка хранилища — признак профиля `keys.store_build`** профиля `01-store`, как у стенда группы: `raft` — сценарий
  исполняется; `box` — not_applicable, в итог не входит и не красный, потому что группы у такой сборки нет; признака нет или
  иное значение — not_executed, не GREEN. Сценарий начинается с `@group-setup`, раннер планирует его тем же правилом.
- **Что нужно от профилей.** Новых команд и ключей нет. Прежние команды «Стенда» (`store`, `manifest-put`, вывод прав, `resource`,
  `worker`, `controller`, `console`) не вписывают сами порт, каталог, сокет и имя сервера: раннер подставляет `{data}`, `{socket}`,
  `{rport}`, `{server}` и окружение на каждый сервер. Нет нужной части в составе — ошибка состава до запуска.
- **Границы**: между сценариями раннер останавливает все процессы всех серверов, снимает посредников и удаляет каталоги.

| Форма | Смысл | Урок |
|---|---|---|
| `@server-start <имя>` | поднять сервер: член хранилища, затем ресурс. Флаги члена — как у `@store-start`, вступление раннер выбирает по порядку директив в сценарии: первый — `-bootstrap -group-size 3`, второй — `-join {api@<первый>} -group-size 3 -force`, третий — `-join {api@<первый>} -group-size 3` (сборка 1→2→3, C01-GROUP-BOOTSTRAP-EVEN-01). У первого сервера раннер после готовности члена ставит манифесты (`manifest-put`, порядок — «Манифесты» выше) через его `admin.sock` и запускает консоль, потом ресурс. Файлы ролей ресурса — как у `@start resource on <сервер>`. Ожидание `ok` — `admin@<имя> GET /v1/status` отвечает 200, порт ресурса слушает и строка `platform/doors/<имя>` есть, всё не позже 20 с | система (2026-10-31) |
| `@power-pull <имя>` | выдернуть питание: посредник раннера на raft-адресе члена рвёт живые соединения и не принимает новых (как `@cut store@<id>`), затем раннер сразу шлёт SIGKILL всем процессам сервера — члену, ресурсу, воркерам; каталоги не трогает. Посредника на двери ресурса нет, потому что адрес двери ресурс называет сам: после SIGKILL её порт закрыт. Ожидание `ok` — все процессы вышли; этот момент — `t = 0` учения. `<имя>` — поднятый сервер, не сервер консоли и контроллеров; иначе ошибка данных при исполнении шага | система (2026-10-31) |
| `@power-back <имя>` | вернуть питание: те же каталоги, порты, комплект. Посредник снова пропускает; член запускается прежней командой и прежними флагами без `-bootstrap`, `-join`, `-force`: партнёров он берёт из `member.json` (P/01.3 N1.3 `join`; P/02.4 N3 «старт сервера» шаг 1), и только так шаги ниже доказывают рестарт без вступления. Затем ресурс — той же командой, с тем же `{rport}`. Воркеров директива не запускает, их возвращают шаги `@start worker … on <имя>`. Ожидание — как у `@server-start` | система (2026-10-31) |
| `@restart resource#<имя>` | SIGTERM ресурсу сервера, дождаться выхода, запустить той же командой с тем же `{rport}` и каталогом; ожидание `ok` — порт слушает и строка двери есть не позже 20 с. Первый проход идёт при старте (P/05 N1.4 `pass`), поэтому сценарий получает проход зеркала без ожидания 600 с | система (2026-10-31) |
| `@append event on <имя> <дерево>/<unit>/e<эпоха> <текст>` | как `@append event` словаря, но в корень событий сервера `<имя>` (`<PLATFORM_DIR>/events`) | система (2026-10-31) |
| `@append event-closed on <имя> <дерево>/<unit>/e<эпоха> <текст>` | как строка выше, но в бакет предыдущего окна: `start = floor(now / 600) × 600 − 600`; такой бакет уже закрыт (договор журнала событий `span`: закрыт, когда end ≤ now). `{now}` в тексте — `start + 300`, потому что `t` строки выбирает бакет. После `ok` раннер связывает `$closed` — путь бакета `<дерево>/<unit>/e<эпоха>/<начало>Z.events.jsonl`. Настоящее закрытие ждать нельзя: до 600 с на окно и ещё до 600 с на проход зеркала | система (2026-10-31) |
| дверь `resource#<имя> <запрос>` | дверь ресурса сервера `<имя>` на его `{rport}` с допустимой личностью; `#` здесь — имя сервера, а не номер копии, как у `@sigkill resource#1` | система (2026-10-31) |
| дверь `admin@<имя> <запрос>` | дверь члена по «Стенду группы хранилища»; сц. 05 читает и пишет ею, потому что ему нужны строки всех семей | P/01.3 (2026-10-30) |

**Коды выхода команд-векторов M11** (решение «Архитектора» по сверке M11, H14). Код 2 — нарушена форма того, что вызывающий берёт из своего

#### Стенд нескольких кластеров

**Кластеры** (M11/3). Кластеры `hold` (держатель), `m1`, `m2` — каждый со своим хранилищем, `{data}`,
сокетами ролей, портами и кольцом (README приёмки [главы 8.3](../../../08-domain/ru/acceptance/3/README.md), «Подготовка каждого

агентом каждого кластера и дверью держателя раннер держит свой TCP-посредник: `DOMAIN_URL` агента указывает на него.

Подстановки команд стенда домена (их шаблоны называет описание реализации, [P/08.3](../../../08-domain/ru/spec/08.3-domain.norms.md) и [P/09.1](../../../09-agent/ru/spec/09.1-agent.norms.md) «Решает реализация»; разбор ревью стадии B 8–10, № 22: M-1): у команд процессов
кластера — `{data}` и `{socket}` своего кластера, `{port}` — порт двери этого процесса; у установки и `join` — `{domain}` и

**Ретранслятор** (P/09.2): четвёртый кластер стенда `relay`; его агент всегда открывает дверь ретранслятора
(`RELAY=1`, порт `{relay_port}` экземпляра), посредник раннера стоит и перед ней. `@cut relay` рвёт дорогу ретранслятора
к держателю; двери членов к ретранслятору — свои посредники (`@cut <член>` рвёт дорогу члена, какой бы она ни была).

**Окружение пересылки** (M11/8; `@env` — [P/06.7](../../../06-console/ru/spec/06.7-console.norms.md) «Решает реализация» п. 2): консоль каждого кластера получает `CLUSTERS` — адреса консолей всех кластеров стенда
(`hold=<url>,m1=<url>,m2=<url>[,relay=<url>]`, без посредников); процесс `domain` — `DOMAIN_CONSOLE_URL`, адрес двери
консоли домена; `SIGNER_URL` — только консоли `hold`. Комплекта TLS у стенда нет: двери на петле по `http://`
(P/02.4 N1.6). `Idempotency-Key` у `POST`, `PUT`, `DELETE` пути `/domain/…` двери `member <кластер> console` раннер
ставит, как у двери `holder`.

**Ожидания** стенда домена — формы словаря выше: `<код> <JSON>` подмножеством, `$name`, `@spoil($name)`, `@any`/`@absent`,
`@not`, `@time`, `~text` (например `~enc:v2:` — конверт кольца члена), `!contains`, `@exit`; у команд-векторов и `@carry` —
`ok <JSON>`, у `@join` — `ok` или `refused`, у `@move` — `<код> <JSON>` ответа двери. Сны (`@sleep`) с причинами — в README
приёмки главы.
