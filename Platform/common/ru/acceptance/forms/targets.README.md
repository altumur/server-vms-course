## Форма таблицы

UTF-8, строки по физическим LF, ячейки разделены TAB. Первая строка, не являющаяся заметкой (`#`), — заголовок, столбцы читаются по его именам ([шапка таблицы и столбцы по имени](../tables.md#шапка-таблицы-и-столбцы-по-имени)):

```text
id\towner\tstand_commands\tstand_addresses\tkeys\trequirements\tnorm_anchors\tflags
```

`id` и `owner` — строки; все остальные ячейки — компактные значения JSON. `id` уникален.

| Столбец | Смысл |
|---|---|
| `id` | Имя цели: область договора, а не выбор реализации или входов. |
| `owner` | Модуль, отвечающий за цель. |
| `stand_commands`, `stand_addresses`, `keys`, `requirements`, `norm_anchors` | Те же формы и смысл ячеек, что у одноимённых столбцов в [требованиях к целям](../runner-targets.README.md). |
| `flags` | JSON-массив слов-флагов из закрытого списка ниже; пустой, если флагов нет. |

| Флаг | Смысл |
|---|---|
| `optional` | Профиль, не объявивший интерфейс цели, оставляет цель неисполненной. Без этого флага отсутствующий интерфейс блокирует цель. Ключ профиля из столбца `keys` — не интерфейс: без него цель не исполняется с именем ключа, с флагом и без него (P/AC-R030; только для судьи: нормы судьи). У `P/01/production` флаг относится только к функциональному вердикту (N6.1 норм судьи). |

Эти столбцы не добавляют поля профиля, команды, подстановки, адреса или параметра.

## Исполнение маршрута

Таблица маршрутов `targets.routing.tsv`, предназначенная только судье, имеет обязательные столбцы `id`, `engine`, `acceptance`, `scenarios`, `tables`, `parts`, `body`, `role`, `free`, `rights` и необязательный столбец `execution`. Урок может не включать `execution`; сборка подставляет в этот столбец компактный JSON-объект `{}`. Столбцы маршрутов читаются по имени в любом порядке; неизвестные столбцы игнорируются. Повторённый столбец, отсутствующий обязательный столбец или строка другой ширины — ошибка данных. Формы остальных ячеек маршрута задаёт их общая шапка.

`execution` — компактный JSON-объект по [его схеме](../../../acceptance/forms/targets.execution.schema.json) (только для судьи: схема исполнения маршрута). Закрытый набор полей — `stand`, `exclude` и `between`. Отсутствующее поле не переопределяет действующее правило семейства движка: `{}` не меняет ни выборку, ни жизненный цикл. Имя цели, суффикс вроде `shared`, флаг или имя урока не задают эти поля. Присутствующая ячейка обязана быть объектом; пустая ячейка, `null`, повторённые ключи JSON и неконечные JSON-числа — ошибки данных.

Непустой `execution` относится только к `scenarios.tsv` первого каталога `acceptance` у слов движка `run`, `l06`, `l11`, `store_group` и `power_stand`. Эта таблица обязана существовать. Дополнительные файлы `tables` сохраняют собственные исполнение и жизненный цикл; они не входят в эту группу. Поля не меняют запросы и ожидания шагов, не запускают дополнительные роли и не добавляют интерфейс профиля.

### Выбор сценариев

Раннер сначала применяет `scenarios` с его прежним смыслом: `all`, `none`, `first-step:<directive>`, `not-first-step:<directive>` или включающий границы `range:<first>-<last>` по числовому префиксу. Выбор по первому шагу сравнивает декодированный первый запрос со словом директивы, отдельно либо перед пробелом; отрицательный выбор берёт дополнение. Диапазон берёт десятичный префикс цифр id сценария; id без такого префикса вне диапазона. Нижняя граница не должна превышать верхнюю.

`exclude` — массив уникальных непустых строк: точных id сценариев, а не чисел, префиксов, диапазонов или шаблонов. По умолчанию `[]`. Каждый id обязан входить в множество, выбранное `scenarios` до исключений. Раннер убирает эти сценарии и сохраняет порядок оставшихся в таблице, не меняя порядок шагов каждого сценария. Неизвестное либо уже невыбранное исключение — ошибка данных. Исключение сценария не исполняет его на другом стенде: если он нужен отдельно, его должна выбрать другая строка маршрута. Пустая итоговая выборка не запускает стенд и не даёт успешного сценария.

### Время жизни стенда

`stand: "shared"` создаёт один свежий стенд на всю итоговую выборку этой строки маршрута, готовит его один раз перед первым выбранным сценарием и исполняет выбранные сценарии последовательно на нём. Процессы, сохранённые строки и объекты, заявки повтора и память процессов сохраняются между ними; локальные переменные сценария, текущую роль и привязки ключей запросов раннер сбрасывает на каждой границе сценария по их обычным правилам. `stand: "scenario"` создаёт и готовит отдельный свежий стенд для каждого выбранного сценария. Свежий означает новые экземпляры процессов и отдельное пустое состояние строк/объектов и памяти повтора, затем подготовку манифестов/настроек стенда; удаления только прикладных строк недостаточно.

Раннер изолирует каталоги, порты и группы процессов от других целей и повторных либо параллельных вызовов. Он не делит экземпляр между строками маршрута. Общий стенд он разбирает после последнего выбранного сценария либо при обрыве, стенд на сценарий — на каждой границе сценария. При каждой разборке действуют обычные остановка всей группы и порядок уборки. Отказы остановки и уборки сохраняют свои существующие классы; неясная уборка останавливает прогон по обычному правилу уборки, неубранный экземпляр повторно не используется.

Обычное несовпадение сохраняет правило продолжения словаря сценариев. Если сценарий оборван из-за отказа подготовки или адаптера либо директива не исполнилась, общий стенд нельзя продолжить со следующего сценария или молча пересоздать: оставшиеся выбранные сценарии получают `not_executed` со сценарием/шагом либо существующей причиной, вызвавшей обрыв. Уже наблюдавшиеся исходы остаются в отчёте. Разборка исполняется на каждом пути выхода.

### Подготовка между сценариями

`between` по умолчанию `[]`. Это массив подготовок в порядке итоговой выборки сценариев; он допустим только при явном `stand: "shared"`. Каждый объект имеет ровно `id`, `after`, `before`, `action`, `command`, `sub`, `timeout_s`. Его `id` — слово по `[a-z][a-z0-9-]*`, уникальное в строке маршрута. `after` и `before` — точные id выбранных сценариев, соседних после исключений, причём `after` идёт первым. Граница встречается в массиве один раз. Повторённые id или границы, обратные либо несоседние границы и границы с исключёнными либо отсутствующими сценариями — ошибки данных до запуска стенда.

Сухой план называет область стенда, итоговую упорядоченную выборку и каждую подготовку на её границе. Идентичность подготовки — `<target>#between/<id>`, отдельно от описи шагов сценариев: это не сценарий и не дополнительный случай проверки кандидата. Отчёт прогона сохраняет её идентичность, границу, начало/дедлайн, наблюдения и исход. Он не должен выдумывать исходный шаг или менять число шагов исходного сценария. Проваленная подготовка предотвращает `before` и каждый последующий сценарий этого общего экземпляра; их причина — `precondition:<target>#between/<id>`. Сам отказ сохраняет свой класс, цель не может быть GREEN. Все завершённые шаги сохраняют свои исходы, разборка всё равно исполняется.

Закрытое слово действия — `controller-pass`. `command` — точный `{owner, section: "stand", key}` команды печати отчёта прохода, уже присутствующей в `stand_commands` этой цели. Команда получает `{data}` действующего экземпляра и `{sub}` = `sub`; печатает текущий JSON-объект отчёта контроллера либо ничего, когда отчёта нет. Команда осмотра читает тот же опубликованный отчёт, не создаёт проход и не определяет другую форму отчёта. Объявление не добавляет команду, HTTP-дверь, ключ профиля или подстановку. Отсутствующий обязательный интерфейс подчиняется обычным правилам интерфейса/флага цели до запуска процессов.

После завершения последнего шага `after` раннер начинает один монотонный бюджет положительного JSON-токена целого `timeout_s`, в секундах, и читает свежую базу этой командой. Затем он опрашивает ту же команду до допустимого объекта отчёта, отличного от базы по значению JSON; игнорируется только порядок членов объекта. За отсутствующей базой может следовать первый допустимый объект; отсутствие или неизменный объект никогда не доказывают завершение. Чтение базы, все вызовы команды и ожидания делят один дедлайн; ни один опрос не начинает бюджет заново, ни одна команда не может выйти за его пределы. Отчёт, снятый до границы, не является базой, сон или отсутствие размещения не доказывают проход.

Истечение срока без изменившегося отчёта — отказ подготовки класса `stand`; недоступное или сломанное наблюдение судьи имеет тот же класс. Отказ команды печати реализации, включая неверный непустой кадр отчёта, сохраняет обычный класс команды профиля. Раннер записывает базу и подтверждающий отчёт со скрытыми секретами; один выход команды не является подтверждением. Операция доказывает новый завершённый проход после границы, а не результат размещения кандидата.
