# P/01 — инструкция для реализации

Этот файл — для агента (или человека), который пишет код по уроку. Объяснение «зачем» — [`../01-store.md`](../01-store.md).

## Задача

Реализовать процесс хранилища урока P/01 на языке `<LANG>` так, чтобы он прошёл приёмку Н5 трёх глав через дверь (HTTP на
unix-сокете): словарь операций (глава 1.1), файл прав и оценщик (глава 1.2), демон хранилища (глава 1.3). Получить одинаковый
ответ оценщика прав в файловом хранилище, памяти и кластере; показывать загруженный файл прав только admin.

## Что создать

Обязательное поведение задают нормы глав. Внутренние интерфейсы, представление отказов и устройство кода выбирает реализация (Н5, P/01.1-20); примеры ниже не добавляют к канону требований.

1. **Хранилище с четырьмя операциями Н3** (прочитать, перечислить, записать, удалить). Его внутренний API может возвращать типизированные отказы или представлять их иначе; на двери коды и поля ответа должны соответствовать Н4. Например, типизированное значение с полями `kind`, `key`, `index`, `size`, `limit` удобно переводить в HTTP-ответ.

   Сериализация выбирает форму именно своего исхода Н2: у `conflict` обязателен `index`, у `guard` — ещё
   `key`, у отказа веса — `key`, `size`, `limit`, у отказа тела — `limit` и только допустимый `size`.
   Не сериализовать все поля внутреннего типа с нулевыми значениями. Проверять полное тело по схеме
   ответа конкретной операции и кода; один общий `Fault` не подтверждает правильный вид отказа.
2. **Хранилище данных выбранного вида**: в памяти, на файлах или с реплицированным журналом (группа и демон `configstore` — глава 1.3 Н1.3). Реализация описывает свой выбор и гарантии по разделу «Решает реализация»; наличие сразу нескольких видов не требуется.
3. **HTTP-сервер на unix-сокете** по [`01-store.api.openapi.yaml`](01-store.api.openapi.yaml), который переводит отказы ядра в коды Н4. Предел чтения тела задаётся отдельно от потолка строки; его превышение отказывается по Н2 до разбора JSON и вызова операции.
4. **Проверка прав по Н3 и Н4**. Разрешения на чтение, запись и удаление дают `allowed(роль, действие, ключ)` главы 1.2 Н1.3; внутренний API проверки выбирает реализация. Личность вызывающего определяет сокет роли (глава 1.2 Н1.1 `identity`). Файл прав — глава 1.2 Н1.2: загрузка файла целиком, единый оценщик, привязка личности к сокету или писателю и проверка доверенной пересылки; две HTTP-формы Н2 главы 1.2. Внутренние классы, функции, структура индекса образцов и способ интеграции оценщика остаются реализации; роль приёмки имеет полные права на префикс `acc/` и ни на что больше, перечисление имён не требует права read, но выполняется после проверки личности главы 1.2 (Н3).
5. **Описание реализации** (ARCHITECTURE) — ответ на каждый пункт раздела «Решает реализация». Пункт без ответа — реализация не готова.
6. **Демон хранилища** (глава 1.3): флаги, `FORMAT`, группа и дверь без голоса, сокеты, долговечность, служебные двери, пол, копия и `import`/`restore`/`recover`.
7. **Прогон приёмки** через дверь; реализации с API в процессе СЛЕДУЕТ гонять те же сценарии и через него (Н5, P/01.1-20).

## Порядок работы

Ниже один возможный порядок. Разбиение на функции, внутренние интерфейсы и выбранные виды хранилища можно устроить иначе, сохранив поведение канона.

1. Прочитать нормы глав целиком. Выписать в описание реализации черновые ответы на «Решает реализация».
2. Модель данных Н1: проверки `key`, `items`, `cas`, `guard`, `id` — отдельными чистыми функциями. Это первые тесты.
3. Выбранное хранилище (например, в памяти): проходы Н3 строго по шагам, с тем же порядком проверок (страж раньше CAS).
4. HTTP-слой и отображение отказов Н4.
5. Подготовить экземпляры по README приёмки главы 1.1: потолок строки 524288 байт, предел тела 1048576 байт. Прогнать сценарии главы 1.1. Каждое падение — сверить с нормами глав, исправить **код**.
6. Если выбрано хранилище на файлах: проверить неделимость, версии, барьеры долговечности, повреждённую строку (`Row.unreadable`). Прогнать сценарии снова.
7. Пройти чеклист главы 1.1 (P/01.1-01…23); у пунктов «проверяется чтением» указать в описании реализации, где в коде это обеспечено.

### Глава 1.2 — файл прав и оценщик

1. Загрузить форму Н1.2 целиком. Различать отсутствие delete и явный пустой список.
   В файле нет внутренних ролей, комментариев синтаксиса JSON и неизвестных полей.
   Необязательный строковый comment — метаданные; изменение его текста не меняет права
   и не сравнивается --check (сравнение по смыслу — P/02.5 Н3 «установить»); /v1/rights его возвращает.
2. Реализовать приоритет проверки из Н3: личность, особая операция list, never,
   разрешение admin/внутренних ролей, оценщик обычной роли, право чтения стража.
   Проверить отрицание при совпавшем разрешении и запреты на каждом действии отдельно,
   включая write/delete epoch_floor. Доверенный пересланный admin без файла разрешён
   после never; с файлом — отказ. Подменённая личность отказывается в обоих режимах.
3. Выполнить все шаги приёмки главы, в том числе сценарий заголовка на одной коробке: и там хранилище открывает сокет на роль,
   заголовок роли на нём — 403 (Н1.1 `box`).
   У отказа личности проверять роль сокета и причину, у отказа операции — также действие/ключ.
4. Дополнить HTTP-сценарии чтением загрузчика/генератора и проверкой полных ответов Н2.
   Прогнать положительные и отрицательные примеры форм файла и Listing; параметры
   prefix не ограничивать грамматикой ключа. При незагруженном файле rights даёт 404.

### Глава 1.3 — демон хранилища

Ссылки «Н…» — нормы главы 1.3; права — глава 1.2.

1. Описать устойчивый/переходный состав группы, последовательные join/leave и дверь без голоса. Для status сохранить точные uint64; `leader` — адрес `-api`, `leader_id` — id. Не пересылать admin.sock; права взять у главы 1.2. Флаги демона — только таблица «Флаги демона» Н1.3; сокеты плоско, унаследованные — по `FileDescriptorName` (Н1.3 `sockets`).

   Метку `FORMAT` писать первой в пустой каталог и проверять до любой записи: чужой или безметочный непустой каталог — код 2 без изменений. Копию `backup` писать и `import`/`restore` читать только в форме Н1.3 `copy`, свой формат на диске в копию не выносить.

2. На отдельной модели проверить все фазы restore/import/recover: изоляция, достоверный upper, границы uint64, одно повышение пола, частичный перенос и продолжение той же попытки. Force не разрешает понижение или двух операторов (Н3).

3. Выполнить автоматические 04, 08, 10–12, 14, 15 (шаги 1–8), 16 на свежем стенде со схемой 1 (08 — с долговечным хранилищем); 07, 17, 18 — на стенде группы хранилища (общий README приёмки, «Стенд группы хранилища»; сборке коробки `keys.store_build: box` — not_applicable).

## Ловушки, которые зависят от языка

Места, где идиоматичный код на многих языках нарушает норму:

| Норма | Ловушка | Как правильно |
|---|---|---|
| порядок ключей перечисления — по байтам (Н3) | Java, C#, JS, Kotlin сортируют строки по UTF-16; `localeCompare` — по локали | сравнивать байты UTF-8 |
| вес и длина ключа — в байтах UTF-8 (Н1) | `len()` / `.length` считают символы или UTF-16 units | длина кодировки UTF-8 |
| версия непрозрачна (Н1) | разбор в число и сравнение `>` | хранить и сравнивать как строку; внутри хранилища счётчик МОЖЕТ быть числом |
| items — копия (Н3) | возврат ссылки на внутренний словарь | независимая копия на входе и выходе; проверка чтением по Н5 и P/01.1-03: HTTP-сценарий 03 не наблюдает совместную память |
| неделимость (Н3) | проверка и запись под разными блокировками; async-разрывы между шагами | шаги после «далее одной операцией» — в одной критической секции |
| страж раньше CAS (Н3) | проверка в порядке полей запроса | строго: страж, потом CAS |
| отказ не цитирует присланное (Н4) | сообщения вида `invalid value "<тело>"` из JSON-библиотек | своё сообщение, без присланных данных, кроме ключа |
| написание ключа — `Key`, длина — в байтах (Н1, Н2) | общий отказ валидатора превращает любой неверный ключ в `badrequest` | отсутствующий или нестроковый ключ (команды, стража, чтения) и пустой ключ стража — `badrequest`; строка ключа не по правилам Н1 — `badkey`, в том числе у непустого ключа стража |
| тело сверх предела → 413 (Н2, Н4) | фреймворк отвечает своим 413/400 или подставляет потолок строки в `limit` | ограничить чтение до разбора JSON, вернуть `Fault` с пределом тела в `limit`; необязательный `size` — полный размер тела |
| неизвестный маршрут → 404 badrequest (Н2) | стандартная 404-страница фреймворка | свой обработчик с `Fault` |
| разбор query (Н2.1) | `+` прочитан буквально; при повторе параметра молча взят первый или последний | `application/x-www-form-urlencoded`: `+` — пробел, `%2B` — плюс; повтор `key`/`prefix` — `badrequest`; `key` не UTF-8 — `badkey` |
| разбор JSON (Н2.1) | библиотека берёт последнее из повторённых имён, принимает `NaN`, заменяет одиночный суррогат | повтор имени на любом уровне — `badrequest`; суррогат в ключе — `badkey`, в `items` — `badrequest` |
| неизвестный метод и неразбираемый HTTP (Н2.1) | сервер по умолчанию отвечает 405, 501, 414 или 431 HTML-страницей | `404` либо `400` с `Fault` `{kind: badrequest}` |
| изолированный экземпляр (Н5) | раннер чистит строки прежнего экземпляра | способ получить новый экземпляр с параметрами — в описании реализации («Решает реализация» п. 10) |
| `cas: null` ≡ поля нет (Н1) | JSON-библиотека различает null и отсутствие или путает `""` с null | три состояния: нет/null, `""`, версия |
| неизвестные поля Cmd и items у delete не читаются (Н2) | строгий разбор тела отвергает лишнее поле или включает его в отпечаток id | лишние поля верхнего уровня put/delete игнорировать и не включать в отпечаток; guard остаётся закрытым |
| долговечность («Решает реализация» п. 3) | запись без барьера долговечности; rename без сохранения каталога | обеспечить названные в описании реализации барьеры; для файлов это, например, fsync файла и каталога до успешного ответа |

## При расхождении кода и норм

| Ситуация | Что править |
|---|---|
| сценарий красный, нормы глав однозначны | код |
| нормы глав неполны или противоречивы | не обходить в коде; вопрос в `QUESTIONS.md`; правку делает автор норм, затем код |
| сценарий противоречит нормам глав | дефект приёмки; вопрос автору; код — по нормам глав |
| ИИ ошибся и был исправлен человеком | строка в `corrections.tsv` рядом со сценариями (ADR-0080 доп. 1) |

Дополнительная проверка после прогона 33: Служебные POST: unknown field/не объект/лишний JSON/framing — 400; 1 МиБ + 1 — 413; нет пути/метод — 404/405. Сверить каждую причину с Н2, Н4 и полным Fault, не только номер кода.
