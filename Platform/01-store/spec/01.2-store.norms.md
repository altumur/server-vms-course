### N1.1 Roles

<!-- req: P/01.2-R006 -->
```yaml
roles:
  per_manifest:
    <sub>controller:     the controller of the manifest
    <sub>worker:         the worker of the manifest
  platform:              [resource, console, domain, domainconsole, domainagent]
  store_internal:        [admin, configstore, configstore-door]
  reader_word_only:      [domainworker]
name:        ^[a-z][a-z0-9_-]{0,63}$
group:
  platform role:         w2c-<role>
  subsystem role:        <deployment>-<role>
deployment:  ^[a-z][a-z0-9]*$
identity:
  cluster:
    <role>.sock:         {path: /run/configstore/<role>.sock, mode: "0660", group: the group of the role}
    admin.sock:          {mode: "0600", owner: root}
  box:                   the writer's name
  doors:                 the role certificate
```

<!-- req: P/01.2-R032 -->
The roles `<sub>controller` and `<sub>worker` come from each manifest of the catalogue.

<!-- req: P/01.2-R033 -->
`console` is one per cluster. `console` writes the operator rows of all manifests.

<!-- req: P/01.2-R034 -->
`domain`, `domainconsole` and `domainagent` are the roles of the domain (M11). `domain` is the signer with keys, `domainconsole` has no keys (P/08.2 N1.3).

<!-- req: P/01.2-R035 -->
The roles of `store_internal` are not named in the rights file. `configstore` is the role of a peer, another daemon of the group. `configstore-door` is the door without a vote (added by P/01.3 N1.3).

<!-- req: P/01.2-R037 -->
`domainworker` (P/03.7 N1.6: a worker of a subsystem on the domain) is a platform word in `secrets.readers` (P/02.5 N1.3): it gives no role in the rights file. `domainworker` maps to the role `<sub>domain` of a manifest that has `domain.kept` or a portable book (P/03.7 N1.6: a platform capability, not the removed process `domainpart`). `domainworker` does not enter the comparison «declared = able to read».

<!-- req: P/01.2-R040 -->
A role name matches `name`. `<sub>` of a role name follows the grammar of the manifest name (P/02.1).

<!-- req: P/01.2-R041 -->
The group of a platform role — `console`, `resource`, `domain*` (M11) and every `<sub>controller` — is `w2c-<role>`.

<!-- req: P/01.2-R042 -->
The group `<deployment>-<role>` of a subsystem role belongs only to `<sub>worker`: the controller is the platform role `w2c-<sub>controller`. The deployment name matches `deployment`.

<!-- req: P/01.2-R043 -->
On a cluster the identity is the socket of `identity.cluster`. The group of `<role>.sock` is `SocketGroup=` of the socket unit (P/02.4 N1.1).

<!-- req: P/01.2-R045 -->
On a box the identity is the writer's name at a store of files/memory. On a box the writer's name has the same list of rights. The box door also opens a socket per role. On a box there are no trusted forwarding senders: if a role header comes on any socket, `admin.sock` included, then the store MUST refuse with `403` naming the role of the socket.

<!-- req: P/01.2-R046 -->
At the doors the identity is the role certificate — P/02.4 N1.6 `doors`; its form is the role certificate contract (`Platform/common/contracts/role-certificate.md`).

### N1.2 Rights file

<!-- req: P/01.2-R007 -->
The file is a JSON object with the required field `roles`. The full static form is `RightsFile` in N2. The optional field `comment` of the file is a string. `comment` is the generator's mark; it takes no part in granting rights. The mark necessarily names that the file is generated, the deployment, the source manifests and «do not edit by hand». For the same inputs the text of the mark is the same (P/02.5-01). Each role has the required `group` (a non-empty string), `read` and `write` (arrays of strings). `delete` of a role is an optional array of strings. Unknown fields are rejected. Role names are checked whole, including the end of the string. The internal roles of the store are not in the file: the file does not name `admin`, `configstore`, `configstore-door`.

<!-- req: P/01.2-R008 -->
```yaml
configstore-rights.json:
  comment:  <generator mark>
  roles:
    <role>:
      group:  <socket group>
      read:   [<pattern>…]
      write:  [<pattern>…]
      delete: [<pattern>…]
pattern:
  exact:    "testsub/next_id"
  prefix:   "testsub/counters/*"
  deny:     "!domain/signer*"
  literal:  ["", "!", "!*", "p/!x", "a*b"]
```

The generator always writes `delete` for every role: it equals `write`, unless the manifest separated them by `delete:`.

<!-- req: P/01.2-R054 -->
For the evaluator an absent `delete` is an empty list: no deletes (minimum of rights).

<!-- req: P/01.2-R055 -->
The pattern `exact` matches the key equal to it. A `*` as the last character makes the pattern a prefix (`prefix`). A `*` not last is a literal character. A `!` only as the first character makes the pattern a negation (`deny`). A negation wins everywhere in the list. The patterns of `literal` are admissible in the file. The patterns of `literal` match by the rules above: `""` — only the empty key, `"!"` — the negation of the empty key, `"!*"` — the negation of everything (vector Platform/01-store/vectors/rights-evaluator). A `!` not first is a literal character (a `*` not last —).

<!-- req: P/01.2-R059 -->
If the file is out of form, then the whole file is refused.

<!-- req: P/01.2-R060 -->
The file is generated from the catalogue of manifests (`MANIFEST_DIR`) and the deployment name. The file is not edited by hand.

<!-- req: P/01.2-R061 -->
The daemon loads the file at its start (`-rights`); the flag-absent branch is P/01.2-R030. There is no live reload of the file. Without the file only `admin.sock` opens.

<!-- req: P/01.2-R063 -->
The installer refuses to install a file not equal in meaning to the generated one (`--check`, P/02.5 N3 «install»).

<!-- req: P/01.2-R064 -->
The door shows the file only to admin.

<!-- req: P/01.2-R009 -->
The names of derived roles fit N1.1: the manifest name is limited to 32 characters (P/02.1 N1.2), the suffix controller adds 10, worker — 6. The name of a derived role is not truncated.

<!-- req: P/01.2-R065 -->
The chapter sets no limit on the deployment name: the group `<dep>-<s>worker` may be longer than 32 characters, the generator neither truncates it nor refuses; whether the OS creates it is up to the installer, P/02.4 «Implementation decides» item 1.

<!-- req: P/01.2-R066 -->
The comparison `--check` refers to one unchanging catalogue; publishing manifests during generation and installation is excluded in this chapter by the conditions of service, not detected automatically.

### N1.3 Evaluator

<!-- req: P/01.2-R010 -->
```yaml
allowed(role, action, key):
  action ∈ {read, write, delete}
  role not in the file                                   → no
  any !pattern of the role for action matched            → no
  any pattern of the role for action matched             → yes
  otherwise                                              → no
never:
  - {action: delete, key: "<x>/epoch/<y>"}
  - {action: delete, prefix: domain/, role: not domain_role}
  - {action: [write, delete], key: platform/epoch_floor}
domain_role: [domain, domainagent, <sub>domain]
```

never holds for admin too.

<!-- req: P/01.2-R122 -->
The epoch row of never is `<x>/epoch/<y>`: `x` is exactly one nonempty key segment other than `platform` and contains no slash; `y` is exactly one segment and may be empty. This is the same grammar used by upper (P/01.3-R123). An empty segment `<y>` is included in the epoch row of never (`t/epoch/`). In the epoch row of never x ≠ platform.

<!-- req: P/01.2-R124 -->
A domain role is the name `domain`, `domainagent` or `<sub>domain` (`<sub>` — the grammar of the subsystem name of P/02.1, `[a-z][a-z0-9_-]{0,31}`). Domain roles delete under `domain/` in their own families by the rights derivation contract of P/02.5 N1.4, N1.4a. never checks under `domain/` only the domain role. «Their own families» of the domain roles are set by the delete patterns of the rights file derived by the generator (P/02.5, the `--check` comparison); the store does not re-check them against the catalogue.

<!-- req: P/01.2-R071 -->
`platform/epoch_floor` is written and deleted only by the restore operation (P/01.3).

<!-- req: P/01.2-R072 -->
A listing gives the names and versions under a prefix to any role. A listing gives no values.

<!-- req: P/01.2-R073 -->
A write with a guard requires the read right to the guard row. A guard does not extend rights.

<!-- req: P/01.2-R127 -->
A batch (P/01.1 N3 «write batch») is judged per row: write or delete of every row of writes. In a batch the read of every guard is judged. In a batch never is judged per row, for admin too. A refusal of one row of a batch is a refusal of the whole batch.

<!-- req: P/01.2-R077 -->
admin may do everything except never.

<!-- req: P/01.2-R078 -->
A peer (another daemon) has nothing of its own.

<!-- req: P/01.2-R079 -->
`configstore-door` has only its own `platform/configstore-doors/<id>` (P/01.3 N1.3; not `platform/doors/*` of resources).

## N2 Doors

<!-- req: P/01.2-R012 -->
The rights doors are the store doors of chapter 1.1, behind the role socket. Request parsing at the rights doors is chapter 1.1 N2.1. For `GET /v1/rights` the query is not read. The HTTP contract: [01-store.api.openapi.yaml](01-store.api.openapi.yaml).

<!-- req: P/01.2-R014 -->
`GET /v1/rights` returns the loaded object `RightsFile` whole, without an envelope; if it has a comment, the field is returned too. While no file is loaded, the route `/v1/rights` answers `404 badrequest`; an empty object `roles` does not stand in for the absence of the file. The `404` of `/v1/rights` without a file MUST come after the identity: the row `rc-rights_absent` of [`rights-checks.tsv`](../forms/rights-checks.tsv) stands after `rc-rights_not_admin`, so an identity that is not admin gets `403` and only admin learns that the file is absent. Access to `/v1/rights` is checked by the identity admin, before the file is given out: the row `rc-rights_not_admin` of [`rights-checks.tsv`](../forms/rights-checks.tsv).

<!-- req: P/01.2-R130 -->
A successful `GET /v1/list` uses the `Listing` of chapter 1.1: without the values of rows, with versions and the order of names by UTF-8 bytes. The presence of the path is checked for list too. The trust of the identity is checked for list too. The absence of the read right does not prevent listing.

<!-- req: P/01.2-R015 -->
The forms of all answers of the two routes are set in OpenAPI. The refusals `400` (`/v1/list` out of the form of chapter 1.1 N2.1), `403`, `404`, `503` are exactly `{kind, error}` as strings; no `detail`/`fault` of the console. The `kind` of the refusals `400`, `403`, `404`, `503` of the two routes is respectively `badrequest`, `forbidden`, `badrequest`, `unavailable`.

<!-- req: P/01.2-R085 -->
A body larger than the limit, whatever the method, is `413 toolarge` (`BodyTooLargeFault`, `body_limit` of chapter 1.1) by the frame of chapter 1.1 R034, before the identity and before the table [`rights-checks.tsv`](../forms/rights-checks.tsv).

<!-- req: P/01.2-R086 -->
For a refusal of an operation on a row, `error` names the role, the action and the key.

For a refusal of the identity itself or of `/v1/rights`, `error` names the role and the cause/route.

With a role header on a role socket, `error` names the role of the socket, not the role imposed by the header; parsing the key of the operation for diagnostics is not required.

## N3 Procedures

### check(role, action, key) — in every store before an action

<!-- req: P/01.2-R088 -->
The order of the checks of the identity and the rights of a request is the table [`rights-checks.tsv`](../forms/rights-checks.tsv): the rows in order, the first violated row gives the code, the kind and the fields of the refusal; none — the request goes on to its operation. The table reads the request object `{method, path, query, size, role_header, rights}` (`rights` — a rights file is loaded, a setting of the daemon) and the role of the socket or of the transport; the steps below name the rows of the table and keep as prose what the table does not read.

<!-- req: P/01.2-R017 -->
1. Let role be the role from the socket (a cluster) or from the writer's name (a box).

In the four check forms, `sock` is the caller role at the point being checked: before role forwarding is verified (`read-checks.tsv`, `rights-checks.tsv`, `service-checks.tsv`), it is `<role>` from `<role>.sock`, `admin` from `admin.sock`, the writer's name on a box, or `peer:<role>` from the verified peer certificate on `-api`. In `write-checks.tsv`, put, delete and batch use the effective role after the identity and forwarding checks: the verified forwarded role when present, otherwise the local role or the peer certificate role without `peer:`. For floor, `sock` keeps the transport role: a forwarded admin never becomes the local `admin` of `admin.sock` (P/01.3-R215).

A role header on a role socket is the row `rc-role_header`:
after the frame (chapter 1.1 P/01.1-R034), before the body is parsed (a body out of form with such a header is also `403`).

<!-- req: P/01.2-R018 -->
2. If the role is forwarded, first check the trust in the group daemon (the row `rc-forwarding_untrusted`), before the other rows of the rights.

If the role is forwarded, the ban on a forwarded admin (P/01.2-R090) is checked before the other rows of the rights.

<!-- req: P/01.2-R019 -->
3. If the operation is list, after the identity check return the names and versions without checking the read right: the table has no row of the read right for `/v1/list`.

<!-- req: P/01.2-R020 -->
4. If never (N1.3) holds, return `403 forbidden`.

<!-- req: P/01.2-R021 -->
5. If the role is admin, after never allow the operation.

<!-- req: P/01.2-R136 -->
The internal roles are allowed only by the exceptions of N1.3.

<!-- req: P/01.2-R022 -->
6. For the other roles: if not `allowed(role, action, key)` by N1.3, return `403 forbidden`, before the record to the log.

Steps 4–6 together are the function `allowed` of the tables; the read of `/v1/get` is the row `rc-read_forbidden`;
a write and a delete are the rows `wc-rights` and `wc-write_rights` of [`write-checks.tsv`](../forms/write-checks.tsv).

<!-- req: P/01.2-R023 -->
7. The read right to a guard of a write is the rows `wc-guard_rights` and `wc-guard_elem_rights` of `write-checks.tsv`.

<!-- req: P/01.2-R024 -->
8. For a batch: the rights run per row in the order of writes, then the guards (the groups `write_rights` and `guard_rights` of `write-checks.tsv`).

If one right of a batch is refused, return `403` for the whole batch, before the record to the log.

<!-- req: P/01.2-R139 -->
admin reads a guard of a batch by its own permission of N1.3.

<!-- req: P/01.2-R025 -->
9. In a group: the receiving daemon checks.

<!-- req: P/01.2-R140 -->
In a group the leader checks once more, under the forwarded role.

<!-- req: P/01.2-R089 -->
A forwarding is trusted only from a daemon of the group — a voting one or the door without a vote `configstore-door` (P/01.3 N1.3), by the role in the SAN of the certificate: the row `rc-forwarding_untrusted`.

<!-- req: P/01.2-R090 -->
If a forwarded role is admin while a rights file is loaded, then the daemon MUST refuse with `403 forbidden` (`forwarding_untrusted`) before the operation: the row `rc-forwarded_admin`, after the row `rc-forwarding_untrusted`, before the rows `rc-rights_not_admin` and `rc-read_forbidden` and before the body of a write.

<!-- req: P/01.2-R026 -->
The forwarding conditions apply to list and to /v1/rights too, before data are given out.

<!-- req: P/01.2-R091 -->
A local admin from admin.sock reaches the special rules of N1.3.

<!-- req: P/01.2-R141 -->
A trusted forwarded admin without a file reaches the special rules of N1.3.

<!-- req: P/01.2-R092 -->
The absence of the file does not turn off never. The absence of the file does not turn off the check of trust in the sender.

<!-- req: P/01.2-R027 -->
**Races.** None: rights do not change on the fly — a new file = a restart of the daemon.

## N4 Refusals

<!-- req: P/01.2-R029 -->
The catalogue of these refusals — [`forms/refusals.tsv`](../forms/refusals.tsv): the form is the sole source of code, kind, fields, headers and log projection. The OpenAPI fault schemas and the orders of checks (`forms/write-checks.tsv`, `forms/read-checks.tsv`, `forms/rights-checks.tsv`) stay their owning forms; the causes, priority and caller actions below refer to stable refusal names, without duplicating the outcome cells.
- `list_form`: `/v1/list` out of the form of chapter 1.1 N2.1 (a repeated `prefix`). Caller action: fix the request.
- `rights_no_route`, `rights_store_unavailable`: no route; the store is unavailable (`/v1/list`, `/v1/rights`). Caller action: —.
- `read_forbidden`: a read without the right. Caller action: a deployment error or a foreign process.
- `write_forbidden`: a write/delete without the right. Caller action: the same.
- `guard_read_forbidden`: a guard on a row without the read right. Caller action: the same.
- `never`: a delete of an epoch row; a delete under `domain/` by a role that is not a domain role; a write and a delete of `platform/epoch_floor`. Caller action: never.
- `role_header`: a role header on a role socket. Caller action: a client error.
- `forwarding_untrusted`: a forwarding not from a daemon of the group (a voting one or the door without a vote); a forwarded `admin` with a loaded rights file. Caller action: —.
- `rights_not_admin`: `/v1/rights`: the identity is not admin after the check of admissibility of the forwarding. Caller action: —.
- `rights_not_loaded`: `/v1/rights`: the file is not loaded. Caller action: set up the file and restart.
- `rights_file_form`: the rights file is out of form; it names `admin`/`configstore`/`configstore-door`; a role not by the grammar. Caller action: regenerate.

<!-- req: P/01.2-R030 -->
Not a refusal: a daemon without `-rights` opens only `admin.sock` — give it the file (the flag `-rights`, P/01.3 N1.3).
