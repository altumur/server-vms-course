## Задача

Реализовать процесс хранилища урока P/01 на языке `<LANG>` так, чтобы он прошёл приёмку N5 трёх глав через дверь (HTTP на
unix-сокете): словарь операций (глава 1.1), файл прав и оценщик (глава 1.2), демон хранилища (глава 1.3). Получить одинаковый
ответ оценщика прав в файловом хранилище, памяти и кластере; показывать загруженный файл прав только admin.

## Что создать

Обязательное поведение задают нормы глав. Внутренние интерфейсы, представление отказов и устройство кода выбирает реализация (N5, P/01.1-20); примеры ниже не добавляют к канону требований.

1. **Хранилище с пятью операциями N3** (прочитать, перечислить, записать, удалить, записать пакет). Его внутренний API может возвращать типизированные отказы или представлять их иначе; на двери коды и поля ответа должны соответствовать N4. Например, типизированное значение с полями `kind`, `key`, `index`, `size`, `limit` удобно переводить в HTTP-ответ.

   Сериализация выбирает форму именно своего исхода N2: у `conflict` обязателен `index`, у `guard` — ещё
   `key`, у отказа веса — `key`, `size`, `limit`, у отказа тела — `limit` и только допустимый `size`.
   Не сериализовать все поля внутреннего типа с нулевыми значениями. Проверять полное тело по схеме
   ответа конкретной операции и кода; один общий `Fault` не подтверждает правильный вид отказа.
2. **Хранилище данных выбранного вида**: в памяти, на файлах или с реплицированным журналом (группа и демон `configstore` — глава 1.3 N1.3). Реализация описывает свой выбор и гарантии по разделу «Решает реализация»; наличие сразу нескольких видов не требуется.
3. **HTTP-сервер на unix-сокете** по [`01-store.api.openapi.yaml`](../../spec/01-store.api.openapi.yaml), который переводит отказы ядра в коды N4. Предел чтения тела задаётся отдельно от потолка строки; его превышение отказывается по N2 до разбора JSON и вызова операции.
4. **Проверка прав по N3 и N4**. Разрешения на чтение, запись и удаление дают `allowed(role, action, key)` главы 1.2 N1.3; внутренний API проверки выбирает реализация. Личность вызывающего определяет сокет роли (глава 1.2 N1.1 `identity`). Файл прав — глава 1.2 N1.2: загрузка файла целиком, единый оценщик, привязка личности к сокету или писателю и проверка доверенной пересылки; две HTTP-формы N2 главы 1.2. Внутренние классы, функции, структура индекса образцов и способ интеграции оценщика остаются реализации; роль приёмки имеет полные права на префикс `acc/` и ни на что больше, перечисление имён не требует права read, но выполняется после проверки личности главы 1.2 (N3).
5. **Описание реализации** (ARCHITECTURE) — ответ на каждый пункт раздела «Решает реализация». Пункт без ответа — реализация не готова.
6. **Демон хранилища** (глава 1.3): флаги, `FORMAT`, группа и дверь без голоса, сокеты, долговечность, служебные двери, пол, копия и `import`/`restore`/`recover`.
7. **Прогон приёмки** через дверь; реализации с API в процессе СЛЕДУЕТ гонять те же сценарии и через него (N5, P/01.1-20).

1. Загрузить форму N1.2 целиком. Различать отсутствие delete и явный пустой список.

## Ловушки, которые зависят от языка

Места, где идиоматичный код на многих языках нарушает норму:

| Норма | Ловушка | Как правильно |
|---|---|---|
| порядок ключей перечисления — по байтам (N3) | Java, C#, JS, Kotlin сортируют строки по UTF-16; `localeCompare` — по локали | сравнивать байты UTF-8 |
| вес и длина ключа — в байтах UTF-8 (N1) | `len()` / `.length` считают символы или UTF-16 units | длина кодировки UTF-8 |
| версия непрозрачна (N1) | разбор в число и сравнение `>` | хранить и сравнивать как строку; внутри хранилища счётчик МОЖЕТ быть числом |
| items — копия (N3) | возврат ссылки на внутренний словарь | независимая копия на входе и выходе; проверка чтением по N5 и P/01.1-03: HTTP-сценарий 03 не наблюдает совместную память |
| неделимость (N3) | проверка и запись под разными блокировками; async-разрывы между шагами | шаги после «далее одной операцией» — в одной критической секции |
| страж раньше CAS (N3) | проверка в порядке полей запроса | строго: страж, потом CAS |
| пакет целиком (N3 «записать пакет») | запись строк по одной под замком: питание пропало между файлами — половина пакета | способ п. 3 «Решает реализация»: журнал намерения с барьером до публикации строк; одна запись журнала raft |
| одна версия пакета (N1 `index`) | счётчик версии растёт на каждую строку | версия выдаётся на операцию, все строки пакета получают её |
| отказ не цитирует присланное (N4) | сообщения вида `invalid value "<тело>"` из JSON-библиотек | своё сообщение, без присланных данных, кроме ключа |
| написание ключа — схема `Key` OpenAPI, длина — в байтах (N1, N2) | общий отказ валидатора превращает любой неверный ключ в `badrequest` | отсутствующий или нестроковый ключ (команды, стража, чтения) и пустой ключ стража — `badrequest`; строка ключа не по правилам N1 — `badkey`, в том числе у непустого ключа стража |
| тело сверх предела → 413 (N2, N4) | фреймворк отвечает своим 413/400 или подставляет потолок строки в `limit` | ограничить чтение до разбора JSON, вернуть `Fault` с пределом тела в `limit`; необязательный `size` — полный размер тела |
| неизвестный маршрут → 404 badrequest (N2) | стандартная 404-страница фреймворка | свой обработчик с `Fault` |
| разбор query (N2.1) | `+` прочитан буквально; при повторе параметра молча взят первый или последний | `application/x-www-form-urlencoded`: `+` — пробел, `%2B` — плюс; повтор `key`/`prefix` — `badrequest`; `key` не UTF-8 — `badkey` |
| разбор JSON (N2.1) | библиотека берёт последнее из повторённых имён, принимает `NaN`, заменяет одиночный суррогат | повтор имени на любом уровне — `badrequest`; суррогат в ключе — `badkey`, в `items` — `badrequest` |
| неизвестный метод и неразбираемый HTTP (N2.1) | сервер по умолчанию отвечает 405, 501, 414 или 431 HTML-страницей | `404` либо `400` с `Fault` `{kind: badrequest}` |
| изолированный экземпляр (N5) | раннер чистит строки прежнего экземпляра | способ получить новый экземпляр с параметрами — в описании реализации («Решает реализация» п. 10) |
| `cas: null` ≡ поля нет (N1) | JSON-библиотека различает null и отсутствие или путает `""` с null | три состояния: нет/null, `""`, версия |
| неизвестные поля Cmd и items у delete не читаются (N2) | строгий разбор тела отвергает лишнее поле или включает его в отпечаток id | лишние поля верхнего уровня put/delete игнорировать и не включать в отпечаток; guard остаётся закрытым |
| долговечность («Решает реализация» п. 3) | запись без барьера долговечности; rename без сохранения каталога | обеспечить названные в описании реализации барьеры; для файлов это, например, fsync файла и каталога до успешного ответа |

## При расхождении кода и норм

| Ситуация | Что править |
|---|---|
| сценарий красный, нормы глав однозначны | код |
| нормы глав неполны или противоречивы | не обходить в коде; вопрос в `QUESTIONS.md`; правку делает автор норм, затем код |
| сценарий противоречит нормам глав | дефект приёмки; вопрос автору; код — по нормам глав |
| ИИ ошибся и был исправлен человеком | строка в `corrections-<K>.tsv` (historical correction record) главы (ADR-0080 доп. 1) |

Дополнительная проверка после прогона 33: Служебные POST: unknown field/не объект/лишний JSON/framing — 400; байт сверх действующего `-max-body` — 413; нет пути/метод — 404/405. Сверить каждую причину с N2, N4 и полным Fault, не только номер кода.
