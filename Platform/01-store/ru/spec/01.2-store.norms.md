## N1 Форма

**Данные** ([каталог](../../../common/data/catalog.tsv)):
- владеет: `/etc/w2c/configstore-rights.json` (форма — N1.2; пишет вывод прав [P/02.5](../../../02-installer/ru/spec/02.5-installer.norms.md) N3 «сгенерировать_права»);
- пишет: строк нет;
- читает: строк нет — оценщик отвечает о любых строках по образцам файла прав.

### N1.1 Роли

```yaml
roles:
  per_manifest:
    <sub>controller:     контроллер манифеста
    <sub>worker:         воркер манифеста
  platform:              [resource, console, domain, domainconsole, domainagent]
  store_internal:        [admin, configstore, configstore-door]
  reader_word_only:      [domainworker]
name:        ^[a-z][a-z0-9_-]{0,63}$
group:
  platform role:         w2c-<role>
  subsystem role:        <deployment>-<role>
deployment:  ^[a-z][a-z0-9]*$
identity:
  cluster:
    <role>.sock:         {path: /run/configstore/<role>.sock, mode: "0660", group: группа роли}
    admin.sock:          {mode: "0600", owner: root}
  box:                   имя писателя
  doors:                 сертификат роли
```

Роли `<sub>controller` и `<sub>worker` берутся из каждого манифеста каталога.

`console` одна на кластер. `console` пишет строки оператора всех манифестов.

`domain`, `domainconsole` и `domainagent` — роли домена (M11). `domain` — подписант с ключами, `domainconsole` без ключей (P/08.2 N1.3).

Роли `store_internal` в файле прав не называются. `configstore` — роль равного, другого демона группы. `configstore-door` — дверь без голоса (добавлено P/01.3 N1.3).

`domainworker` (P/03.7 N1.6: воркер подсистемы на домене) — слово платформы в `secrets.readers` (P/02.5 N1.3): роли в файле прав не даёт. `domainworker` отображается в роль `<sub>domain` манифеста, где есть `domain.kept` или переносимая книга (P/03.7 N1.6: платформенная способность, не снятый процесс `domainpart`). `domainworker` в сравнение «объявленные = способные прочесть» не входит.

Имя роли соответствует `name`. `<sub>` имени роли — по грамматике имени манифеста (P/02.1).

Группа платформенной роли — `console`, `resource`, `domain*` (M11) и каждого `<sub>controller` — `w2c-<role>`.

Группа `<deployment>-<role>` роли подсистемы — только у `<sub>worker`: контроллер — платформенная роль `w2c-<sub>controller`. Имя развёртывания соответствует `deployment`.

На кластере личность — сокет `identity.cluster`. Группа `<role>.sock` — `SocketGroup=` юнита сокета (P/02.4 N1.1).

На коробке личность — имя писателя у хранилища файлов/памяти. На коробке у имени писателя тот же список прав. Дверь коробки тоже открывает сокет на роль. На коробке доверенных отправителей пересылки нет: если заголовок роли пришёл на любой сокет, включая `admin.sock`, то хранилище MUST отказать `403` с ролью сокета.

У дверей личность — сертификат роли — P/02.4 N1.6 `doors`; его форма — договор сертификата роли (`Platform/common/contracts/role-certificate.md`).

### N1.2 Файл прав

Файл — объект JSON с обязательным полем `roles`. Полная статическая форма — `RightsFile` в N2. Необязательное поле `comment` файла — строка. `comment` — пометка генератора; она не участвует в выдаче прав. Пометка обязательно называет, что файл сгенерирован, развёртывание, исходные манифесты и «не править вручную». Для одних входов текст пометки один и тот же (P/02.5-01). У каждой роли обязательны `group` (непустая строка), `read` и `write` (массивы строк). `delete` роли — необязательный массив строк. Неизвестные поля отвергаются. Имена ролей проверяются целиком, включая конец строки. Внутренние роли хранилища в файл не входят: файл не называет `admin`, `configstore`, `configstore-door`. Файл разбирается по строгим правилам JSON двери через [общий договор json](../../../common/ru/contracts/json.md): повтор имени члена в любом объекте, BOM, нечисла JSON (`NaN`, `Infinity`), байты не UTF-8 или глубина сверх `JSON_DEPTH` дают отказ старта `rights_file_form`, код 2.

```yaml
configstore-rights.json:
  comment:  <пометка генератора>
  roles:
    <role>:
      group:  <группа сокета>
      read:   [<образец>…]
      write:  [<образец>…]
      delete: [<образец>…]
```

Образцы — по [общему договору оценщика прав](../../../common/ru/contracts/rights-evaluator.md#образцы).

Генератор пишет `delete` у каждой роли всегда: оно равно `write`, если манифест не разнёс их через `delete:`.

Оценщик толкует отсутствующий `delete` по [общему договору оценщика прав](../../../common/ru/contracts/rights-evaluator.md).

Совпадение образцов и приоритет отрицания — по [общему договору оценщика прав](../../../common/ru/contracts/rights-evaluator.md#образцы).

Если файл не по форме, он отказан целиком.

Файл генерируется из каталога манифестов (`MANIFEST_DIR`) и имени развёртывания. Файл руками не правится.

Демон загружает файл при старте (`-rights`); ветвь без флага — P/01.2-R030. Живой перезагрузки файла нет. Без файла открывается только `admin.sock`.

Установщик отказывается ставить файл, по смыслу не равный сгенерированному (`--check`, P/02.5 N3 «установить»).

Дверь показывает файл только admin.

Имена производных ролей помещаются в N1.1: имя манифеста ограничено 32 знаками (P/02.1 N1.2), суффикс controller добавляет 10, worker — 6. Имя производной роли не усекается.

Предела имени развёртывания глава не ставит: группа `<dep>-<s>worker` бывает длиннее 32 знаков, генератор её не усекает и не отказывает; создаёт ли её ОС — установщик, P/02.4 «Решает реализация» п. 1.

Сравнение `--check` относится к одному неизменному каталогу; публикация манифестов во время генерации и установки в этой главе исключена условиями обслуживания, а не обнаруживается автоматически.

### N1.3 Оценщик

`allowed(role, action, key)` — по [общему договору оценщика прав](../../../common/ru/contracts/rights-evaluator.md#вычисление). Хранилище применяет следующие запреты до разрешений ролей:

```yaml
never:
  - {action: delete, key: "<x>/epoch/<y>"}
  - {action: delete, prefix: domain/, role: not domain_role}
  - {action: [write, delete], key: platform/epoch_floor}
domain_role: [domain, domainagent, <sub>domain]
```

never действует и для admin.

Строка эпохи never — `<x>/epoch/<y>`: `x` — ровно один непустой сегмент ключа, кроме `platform`, без косой черты; `y` — ровно один сегмент, может быть пустым. Это та же грамматика, что у upper (P/01.3-R123). Пустой сегмент `<y>` входит в строку эпохи never (`t/epoch/`). В строке эпохи never x ≠ platform.

Роль домена — имя `domain`, `domainagent` или `<sub>domain` (`<sub>` — грамматика имени подсистемы P/02.1, `[a-z][a-z0-9_-]{0,31}`). Роли домена удаляют под `domain/` в своих семьях по договору вывода прав P/02.5 N1.4, N1.4a. never под `domain/` проверяет только роль домена. «Свои семьи» ролей домена задают образцы delete файла прав, выведенного генератором (P/02.5, сверка `--check`); хранилище их не перепроверяет по каталогу.

`platform/epoch_floor` пишет и удаляет только операция восстановления (P/01.3).

Перечисление выдаёт имена и версии под префиксом любой роли. Перечисление значений не выдаёт.

Запись со стражем требует права read на строку-страж. Страж права не расширяет.

Пакет (P/01.1 N3 «записать пакет») судится по каждой строке: write или delete каждой строки writes. В пакете судится read каждого стража. В пакете never судится по каждой строке, и у admin. Отказ одной строки пакета — отказ всего пакета.

admin может всё, кроме never.

Равный (другой демон) ничего своего не имеет.

`configstore-door` имеет только свою `platform/configstore-doors/<id>` (P/01.3 N1.3; не `platform/doors/*` ресурсов).

## N2 Двери

Двери прав — двери хранилища главы 1.1, за сокетом роли. Разбор запроса у дверей прав — глава 1.1 N2.1. У `GET /v1/rights` query не читается. HTTP-контракт: [01-store.api.openapi.yaml](../../spec/01-store.api.openapi.yaml).

`GET /v1/rights` возвращает загруженный объект `RightsFile` целиком, без оболочки; если в нём есть comment, поле также возвращается. При отсутствии загруженного файла маршрут `/v1/rights` отвечает `404 badrequest`; пустой объект `roles` не подменяет отсутствие файла. `404` у `/v1/rights` без файла ДОЛЖЕН идти после личности: строка `rc-rights_absent` таблицы [`rights-checks.tsv`](../../forms/rights-checks.tsv) стоит после `rc-rights_not_admin`, поэтому личность не admin получает `403`, и об отсутствии файла узнаёт только admin. Доступ к `/v1/rights` проверяется по личности admin, до выдачи файла: строка `rc-rights_not_admin` таблицы [`rights-checks.tsv`](../../forms/rights-checks.tsv).

Успешный `GET /v1/list` использует `Listing` главы 1.1: без значений строк, с версиями и порядком имён по UTF-8-байтам. Наличие пути проверяется также для list. Доверие личности проверяется также для list. Отсутствие права read не препятствует перечислению.

Формы всех ответов двух маршрутов заданы в OpenAPI. Отказы `400` (`/v1/list` не по форме главы 1.1 N2.1), `403`, `404`, `503` — ровно `{kind, error}` строками; никаких `detail`/`fault` консоли. `kind` отказов `400`, `403`, `404`, `503` двух маршрутов — соответственно `badrequest`, `forbidden`, `badrequest`, `unavailable`.

Тело больше предела при любом методе — `413 toolarge` (`BodyTooLargeFault`, `body_limit` главы 1.1) по рамке главы 1.1 R034, до личности и до таблицы [`rights-checks.tsv`](../../forms/rights-checks.tsv).

Для отказа операции над строкой `error` называет роль, действие и ключ.

Для отказа самой личности или `/v1/rights` `error` называет роль и причину/маршрут.

При заголовке роли на ролевом сокете `error` называет роль сокета, а не навязываемую заголовком роль; разбирать ключ операции ради диагностики не требуется.

## N3 Проход

### проверить(роль, действие, ключ) — в каждом хранилище перед действием

Порядок проверок личности и прав запроса — таблица [`rights-checks.tsv`](../../forms/rights-checks.tsv): строки по порядку, первая нарушенная строка даёт код, вид и поля отказа; нет такой — запрос идёт к своей операции. Таблица читает объект запроса `{method, path, query, size, role_header, rights}` (`rights` — файл прав загружен, настройка демона) и роль сокета или транспорта; шаги ниже называют строки таблицы и оставляют прозой то, чего таблица не читает.

1. Пусть роль — роль из сокета (кластер) или из имени писателя (коробка).

В четырёх формах проверок `sock` — роль вызывающего в проверяемой точке: до проверки пересылки роли (`read-checks.tsv`, `rights-checks.tsv`, `service-checks.tsv`) это `<role>` из `<role>.sock`, `admin` из `admin.sock`, имя писателя на коробке либо `peer:<role>` из проверенного сертификата участника на `-api`. В `write-checks.tsv` put, delete и batch используют действующую роль после проверки личности и пересылки: проверенную пересланную роль, если она есть, иначе локальную роль или роль сертификата участника без `peer:`. Для floor `sock` сохраняет роль транспорта: пересланный admin не становится локальным `admin` из `admin.sock` (P/01.3-R215).

Заголовок роли на сокете роли — строка `rc-role_header`:
после рамки (глава 1.1 P/01.1-R034), до разбора тела (тело не по форме с таким заголовком — тоже `403`).

2. Если роль пересланная, сначала проверить доверие демону группы (строка `rc-forwarding_untrusted`), раньше остальных строк прав.

Если роль пересланная, запрет пересланного admin (P/01.2-R090) проверяется раньше остальных строк прав.

3. Если операция — list, после проверки личности вернуть имена и версии без проверки права read: строки права read для `/v1/list` в таблице нет.

4. Если выполняется never (N1.3), вернуть `403 forbidden`.

5. Если роль — admin, после never разрешить операцию.

Внутренние роли разрешены только по исключениям N1.3.

6. Для остальных ролей: если не `allowed(role, action, key)` по N1.3, вернуть `403 forbidden`, до записи в журнал.

Шаги 4–6 вместе — функция `allowed` таблиц; чтение `/v1/get` — строка `rc-read_forbidden`;
запись и удаление — строки `wc-rights` и `wc-write_rights` таблицы [`write-checks.tsv`](../../forms/write-checks.tsv).

7. Право read на страж записи — строки `wc-guard_rights` и `wc-guard_elem_rights` таблицы `write-checks.tsv`.

8. Для пакета: права идут по каждой строке в порядке writes, затем стражи (группы `write_rights` и `guard_rights` таблицы `write-checks.tsv`).

Если одно право пакета отказано, вернуть `403` на весь пакет, до записи в журнал.

admin читает страж пакета по своему разрешению N1.3.

9. В группе: проверяет принявший демон.

В группе ещё раз проверяет лидер, под пересланной ролью.

Пересылке верят только от демона группы — голосующего или двери без голоса `configstore-door` (P/01.3 N1.3), по роли в SAN сертификата: строка `rc-forwarding_untrusted`.

Если пересланная роль — admin при загруженном файле прав, то демон ДОЛЖЕН отказать `403 forbidden` (`forwarding_untrusted`) раньше операции: строка `rc-forwarded_admin`, после строки `rc-forwarding_untrusted`, раньше строк `rc-rights_not_admin` и `rc-read_forbidden` и раньше тела записи.

Условия пересылки применяются и к list, и к /v1/rights до выдачи данных.

Локальный admin из admin.sock доходит до особых правил N1.3.

Доверенный пересланный admin без файла доходит до особых правил N1.3.

Отсутствие файла не отключает never. Отсутствие файла не отключает проверку доверия отправителю.

**Гонки.** Нет: права не меняются на ходу — новый файл = перезапуск демона.

## N4 Отказы

Каталог этих отказов — [`forms/refusals.tsv`](../../forms/refusals.tsv): форма — единственный источник кода, kind, полей, заголовков и проекции журнала. Схемы отказов OpenAPI и порядки проверок (`forms/write-checks.tsv`, `forms/read-checks.tsv`, `forms/rights-checks.tsv`) сохраняют свои формы; причины, приоритет и действия ниже ссылаются на устойчивые имена отказов, не повторяя ячейки исходов.
- `list_form`: `/v1/list` не по форме главы 1.1 N2.1 (повтор `prefix`). Действие вызывающего: исправить запрос.
- `rights_no_route`, `rights_store_unavailable`: нет маршрута; хранилище недоступно (`/v1/list`, `/v1/rights`). Действие вызывающего: —.
- `read_forbidden`: чтение без права. Действие вызывающего: ошибка развёртывания или чужой процесс.
- `write_forbidden`: запись/удаление без права. Действие вызывающего: то же.
- `guard_read_forbidden`: страж на строку без права чтения. Действие вызывающего: то же.
- `never`: удаление строки эпохи; удаление под `domain/` не ролью домена; запись и удаление `platform/epoch_floor`. Действие вызывающего: никогда.
- `role_header`: заголовок роли на сокете роли. Действие вызывающего: ошибка клиента.
- `forwarding_untrusted`: пересылка не от демона группы (голосующего или двери без голоса); пересланный `admin` при загруженном файле прав. Действие вызывающего: —.
- `rights_not_admin`: `/v1/rights`: личность не admin после проверки допустимости пересылки. Действие вызывающего: —.
- `rights_not_loaded`: `/v1/rights`: файл не загружен. Действие вызывающего: настроить файл и перезапустить.
- `rights_file_form`: файл прав не по форме; называет `admin`/`configstore`/`configstore-door`; роль не по грамматике. Действие вызывающего: перегенерировать.


Не отказ: демон без `-rights` открывает только `admin.sock` — дать ему файл (флаг `-rights`, P/01.3 N1.3).

## Решает реализация

Реализация обязана назвать в своём описании:

1. **как раннер и тесты звонят ролью на одной коробке** (имя писателя, тестовый сокет);
2. **точный текст** `error` сверх «<роль> may not <действие> <ключ>» (имя файла, демона);
3. **пересылка роли внутри группы демонов** (заголовок, проверка голосующего). Имя заголовка решает реализация, оно не судится; `keys.role_header` связывает это имя, согласованная привязка сохраняет логический исход.
