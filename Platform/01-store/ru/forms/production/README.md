# Данные стенда цели P/01/production

Текст производный от `forms/production/README.md`, руками не правится: источник — английский [`forms/production/README.md`](../../../forms/production/README.md), правка идёт в него, русский пересобирается переводом (ADR-0121).

Это данные стенда для [боевой квалификации P/01](../../../../common/ru/acceptance/spec/acceptance.norms.md#n6-боевая-квалификация-p01): только для судьи, не вход реализации. Исходов, маршрутов и флагов они не добавляют. Длительность долгого случайного прогона ниже — значение процедуры квалификации.

## Привязки

[`bindings.tsv`](../../../forms/production/bindings.tsv) даёт для каждой записи [`production.tsv`](../../../forms/production.tsv) активации её привязок D7 по [форме payload](../../../../common/acceptance/forms/d7-payload.schema.json). У дескриптора записи по [`d7.schema.json`](../../../../common/acceptance/forms/d7.schema.json) scope `P/01/production#<id>` и по одному provider на каждую возможность её строк. Его `identity`, `invoke`, `observer_ref`, `qualification_ref` и `source_pin` стенд пишет по provider, который он собирает и квалифицирует, и по прогону. У записи без квалифицированного provider для возможности её строк дескриптора для неё нет, и запись `not_executed` с этой возможностью как причиной (N6.5).

- `RUN-W03` и `prod-id-age`: `clock` в режиме `observe`, реальное ожидание с независимым наблюдателем часов; стенд часов не сдвигает.
- `prod-clock-group`: `clock` в режиме `control` над раздельными доменами стенных часов голосующих `s1`, `s2`, `s3`. Стенд, члены которого делят одни стенные часы, дать его не может, и тогда проба `not_executed` с причиной `clock`.
- `storage` называет носитель `ext4` — оболочку [первых утверждённых бюджетов](../../qualification/README.md#первые-утверждённые-бюджеты); tmpfs этим носителем не является.

## Вход N6.2

[`input.json`](../../../forms/production/input.json) — вход N6.2 по [`production-input.schema.json`](../../../forms/production-input.schema.json) без `source_pin`. Стенд добавляет `source_pin`, коммит Source прогона, прежде чем назвать файл в вызове. Поле, которого среда ещё не дала, отсутствует, и записи, которым оно нужно, `not_executed` с его именем как причиной (N6.5); значений не выдумываем.

- `budgets` нет, пока владелец не утвердит пороги.
- `manager` нет: срок остановки настоящего менеджера известен (systemd стенда), запас разборки ещё не измерен; стенд добавит объект, когда у него будут оба.
- `volume` нет: каталог ограниченного размера на объявленной файловой системе даёт только том хоста.

## Долгий случайный прогон со сбоями

[`soak.json`](../../../forms/production/soak.json), проверяемый по [`soak.schema.json`](../../../forms/production/soak.schema.json), — запись Q `RUN-SOAK`: длительность 2 ч, списки сбоев для `group` и `box`, наблюдаемые свойства, отрицательные контроли, исполнитель и среда. Процедура — [«Долгий случайный прогон со сбоями»](../../qualification/stand-procedures.md#долгий-случайный-прогон-со-сбоями). Запись отделена от описи `production.tsv` и входа прогона `input.json` N6.2; директивы функционального судьи и поля входа N6.2 она не добавляет.

`sigkill_*` означает `kill -9`; `sigstop` — SIGSTOP с последующим возобновлением; `sigterm` — SIGTERM. `checkpoint_sigkill` использует перечисленные точки checkpoint, а `unsynced_loss` отбрасывает данные, которые не дошли до барьера долговечности, по независимо наблюдаемой модели сбоя носителя. Одно убийство процесса такой потери не доказывает. `unique_applied_versions` различает логические применения: повтор сохраняет первую версию.

`barrier_noop_power_loss` подавляет барьеры файлов с ложным успехом до квалифицированной потери несинхронизированных данных. `directory_barrier_noop_power_loss` делает то же только с барьерами родительского каталога после успешного rename, сохраняя честными барьеры файлов. `isolated_read_stale_response` использует двустороннюю изоляцию от партнёров и устаревший публичный ответ фикстуры стенда после завершения новой записи. [Процедура](../../qualification/stand-procedures.md#история-свойства-и-контроли) определяет включение, верные фикстуры, свидетелей истории и исходы отсутствующей привязки. Они квалифицируют стенд и проверку истории без мутантов кода кандидата; перечень без активации ничего не квалифицирует.

Поля исполнителя записи `scope: load_and_faults` и `stand_controls: requires_qualified_binding` ограничивают историческую ссылку на исполнителя его нагрузкой и сбоями. Закреплённая ревизия не доказывает реализации новых стендовых контролей. Прогон явно привязывает и независимо квалифицирует их настоящего исполнителя; до этого зависимые контроли остаются неисполненными с отсутствующей возможностью по N6.5. Неквалифицированный результат исторического исполнителя их не закрывает.

До готовности квалификатора часть записи о нагрузке/сбоях исполняет `court-tools` на `6fd588df`, каталог `soak/`; затем он служит эталоном сверки в этом охвате. Тяжёлые прогоны используют ВМ; пока её нет — CT 103 при действующем [шлюзе нагрузки](../../../../common/ru/acceptance/spec/acceptance.norms.md#n33-объявленная-среда). Случаи только для ВМ остаются `not_executed` с причиной до появления ВМ; сам долгий прогон остаётся воротами продвижения. Нагрузку, зерно случайности, расписание сбоев и фактическое время записывает прогон. Запись `recovery_checks` повторяет цели `BUDGET_REOPEN` и `BUDGET_MEMBER_RETURN` M для RUN-W03 и RUN-SOAK и называет наблюдения и отрицательные контроли; [проверки бюджетов восстановления](../../qualification/README.md#проверки-бюджетов-восстановления) задают процедуру. Она не добавляет настройки реализации или частоты, интервала сбоев, числа повторов. Прежний исполнитель не доказывает новые наблюдения: их наблюдателю и контролям нужно квалифицированное исполнение.
