## Интерфейс профиля

Профиль — `01-store` по [общему договору профиля и состава](../../../../common/ru/acceptance/PROFILE.md). `stand.store1` запускает свежий экземпляр хранилища главы: получает назначенные каталог данных, административный сокет, подготовленный файл прав и параметры проб тела/строки через подстановки общего стенда. Обычная сторона обслуживает опубликованную роль `acc`. `keys.request_line_limit` называет границу строки запроса реализации, `keys.role_header` — заголовок пересылки роли для нужных проб. Необязательный `adapters.door` предоставляет те же обычные/административные операции постоянным транспортом общего договора; сырые HTTP-проверки он не заменяет. Пакет JCS использует запись `vectors`, назначенную [формой провода](../../../../common/vectors/wire.tsv), а не угаданную команду `stand.jcs`. Реализация выбирает свои имена программ и флаги и связывает эти обязанности в профиле.

- **Долговечность.** Команда хранилища держит барьеры долговечности включёнными (P/01.3-R111); стенд их не выключает.

## `scenarios.tsv`

Глава проверяет требования своего чеклиста готовности. Формат сценариев следует общему словарю директив и дверей с такими правилами главы:

- `expect` — `<код> <JSON-тело>`, JSON сравнивается целиком: у целей этой главы режим `whole` словаря общего README приёмки (`<код> <JSON>`); `error` сравнивается только если назван: его текст не нормируется. Неназванный `error` допустим только в корне тела; лишнее поле в другом месте — расхождение. Цели главы допускают только неназванные поля корня `error` и `size` по этим двум правилам.
- У ответа `200` на `GET /v1/list` проверяется также **порядок имён внутри `keys`**: последовательность имён, декодированных из JSON в порядке получения, ДОЛЖНА совпасть с последовательностью в `expect`, заданной по байтам UTF-8. Раннер сохраняет этот порядок при разборе ответа и не сортирует полученное перед сравнением. Для пустого `keys` последовательность пуста. Пробелы и способ экранирования JSON несущественны; порядок прочих объектов, в том числе `items`, по-прежнему не проверяется.
- `$name` связывает только строку JSON (N1: версия — строка на проводе); число или иной тип — несовпадение шага.
- Неназванный `size` допустим только в корне тела отказа тела (строка `body_limit` в `forms/refusals.tsv`: `413` с видом `toolarge` и пределом тела в `limit`): проверяется, что это целое JSON-число, равное известному полному размеру тела сущности в байтах, не строка и не булево, затем он исключается из сравнения с `expect`. Корректный представимый `Content-Length` определяет этот полный размер и при раннем ответе, когда отправлен лишь префикс тела. При `Transfer-Encoding: chunked` поле `Content-Length` игнорируется: полный размер завершённого chunked-тела — сумма байтов декодированных данных чанков, без обрамления чанков и трейлеров; у незавершённого chunked-тела полный размер неизвестен и `size` отсутствует. Отказ из-за непредставимой длины обрамления не содержит `size`. Отсутствие `size` остаётся допустимым и при известном полном размере; другие неназванные поля, включая `key`, не допускаются. Отказ веса называет `key` и `size` в `expect`, и они сравниваются как названные поля.

**Запрос.**

| Форма | Смысл |
|---|---|
| `@wire <текст>` | сырой HTTP: на месте метода (`<дверь> @wire <текст>`) шаг открывает новое соединение со своей дверью и пишет ровно байты текста, ничего не добавляя: ни заголовка, ни `Content-Length`; экраны `\r`, `\n`, `\t`, `\\` и `\xHH` (две шестнадцатеричные цифры) дают по одному байту и читаются после подстановок, иной `\` — ошибка данных таблицы; ответ читается как HTTP/1.1 на том же соединении |
| `@halfclose` | последнее слово запроса `@wire`, через один пробел, не входит в его байты: после байтов судья закрывает запись соединения и продолжает чтение |
| `@rep(N,<текст>)` | подстановка в любой части запроса: текст, повторённый N раз; текст идёт до первой `)` и её не содержит |
| `@profile(<имя>)` / `@profile+1(<имя>)` | подстановка в любой части запроса, также на месте N у `@big(N)` и `@rep(N,<текст>)`: значение целого ключа `<имя>` поля профиля `keys` (`Platform/common/acceptance/forms/profile-keys.tsv`) или это значение плюс 1, десятичной записью; иной арифметики нет; отсутствующий ключ оставляет шаг `not_executed` с его именем как причиной |
| `@pause(<секунды>)` | внутри байтов запроса `@wire`: судья перестаёт писать на столько секунд, десятичным числом, затем пишет остальное; тем временем читает соединение |

**Директивы стенда** — не HTTP; ответ `ok` или отказ раннера.

| Форма | Смысл |
|---|---|
| `@rights store <file\|none>` | SIGTERM хранилищу стенда, дождаться выхода, запустить той же командой с тем же `{data}` и файлом прав `<файл>` (путь от каталога приёмки урока; раннер кладёт его в `{rights}`) или без `-rights` (`none`: раннер в шаблоне команды «Стенда» снимает вхождение `-rights {rights}` или `-rights={rights}` — флаг с подстановкой `{rights}`, а не любое слово `-rights`: в составной команде оно может принадлежать не хранилищу — и больше ничего не меняет; `<файл>` — тот же `{rights}` указывает на него; такого вхождения в шаблоне нет или их больше одного — сценарий not_executed с причиной); ожидание: `ok` — хранилище готово по правилу «Сокеты ролей» (`none` — без файла прав); запроса для этого раннер не шлёт (`/v1/status` главы 1.3 на этапе `rights` может быть ещё заглушкой); `@exit 2` — процесс вышел с кодом 2 не позже 10 с (файл не по форме P/01.2 N1.2, N4); файл прежней строки на следующие сценарии не переходит |
| `@hold <дверь> <N>` | открыть N соединений с дверью и ничего в них не писать; судья держит свои сокеты открытыми до конца сценария, затем закрывает их; ожидание `ok` — независимое наблюдение Linux сопоставляет каждый клиентский сокет с живым дескриптором принятого серверного сокета у группы процессов хранилища, все N одновременно живы не позже срока готовности; соединения в очереди не считаются. Применяются правила наблюдения и отказа ниже |
| `@io store $<имя>` | связать имя с числом байт, которые процессы хранилища отдали на запись в хранилище данных: поле `write_bytes` из `/proc/<pid>/io`, сумма по группе процессов хранилища; ожидание `ok`. Когда судья не может прочесть этот счётчик, например под другой учётной записью, шаг и каждый шаг, сравнивающий имя, — `not_executed` с причиной `io_counter_unreadable`, не красные |

Для `@hold` раннер записывает идентичности своих N клиентских сокетов и наблюдает их серверных партнёров через метаданные сокетов Linux и открытые дескрипторы сокетов группы процессов хранилища. У Unix-сокета он получает inode клиента, находит inode его партнёра через диагностику Unix-сокетов и подтверждает, что этот inode партнёра принадлежит открытому дескриптору сокета в той группе процессов. У сокета, который ещё стоит в очереди слушателя, такого принятого дескриптора нет; наблюдение его не засчитывает. Одного успешного `connect` или сна недостаточно для подтверждения принятия. Это наблюдение принятых сокетов; оно не предписывает ни внутреннего счётчика соединений, ни новой двери реализации.

Срок готовности — строка `@hold` в [«Сроках стенда»](../../../../common/ru/acceptance/README.md#словарь-директив-и-дверей). Это один монотонный интервал от первой попытки открыть клиентское соединение до подтверждения, что все N сопоставленных серверных сокетов одновременно живы, не позже границы срока включительно. Открытие или повторная попытка другого соединения не сбрасывает интервал; отдельного срока на каждое соединение нет.

Раннер записывает закрытия и перепроверяет удерживаемый состав перед каждым зависимым шагом, затем наблюдает его до завершения того шага. Если удерживаемый сокет закрывается либо его независимое наблюдение становится недоступным или ломается при живой команде хранилища, результат — `stand`: потеряно доказательство предусловия стенда. Это действует до и во время зависимого шага, включая закрытие, разрешённое объявленным idle-сроком; код ответа или таймаут уже идущего зависимого HTTP-шага при потерянном предусловии не становится несовпадением `implementation`. Текущий шаг получает `stand`, сценарий обрывается, более поздние шаги остаются неисполненными по общему правилу обрыва сценария. Закрытия из-за явной директивы остановки в сценарии — эффекты той директивы; они не отменяют прежнюю успешную подготовку. Независимо доказанный неожиданный выход или сигнал команды хранилища остаётся отказом `implementation` по правилу отказа команды.

Объявленные реализацией idle-сроки остаются в силе. `@hold` не судит эти сроки, не вводит минимума, не отключает таймер, не пишет данные в удерживаемые сокеты и не открывает закрытые сокеты заново ради удержания. Если независимое наблюдение недоступно или сломалось, результат — `stand`. Только когда наблюдение работает, ни один удерживаемый сокет не закрылся и сбоя наблюдения не было, отсутствие подтверждения всех N живых принятых сокетов к сроку готовности даёт `implementation`. Потеря удерживаемого сокета или сбой наблюдения имеет приоритет над этим таймаутом готовности.

**Ожидание.**

| Форма | Смысл |
|---|---|
| `<код> @close …` | `@close` сразу после кода: после своего ответа реализация закрывает соединение в пределах срока `@noreply`; остаток ячейки судится как ожидание без `@close` |
| `@noreply` | всё ожидание: ни байта ответа не приходит, пока реализация не закроет соединение или не кончится срок `@noreply` в «Сроках стенда»; ответ — расхождение |
| `… @by(<секунды>)` | последнее слово ожидания: ответ, закрытие `@close` или `@noreply` либо выход после `@sigterm store` приходит не позже стольких секунд вместо срока `@noreply`; для запроса интервал начинается с первого байта запроса, записанного судьёй, а если судья не пишет ни байта запроса — с установления соединения; для `@sigterm store` — с отправки сигнала судьёй. При `@noreply` реализация ещё и закрывает соединение в этот интервал. Это верхняя граница: судья записывает разрешение своих часов и планировщика отдельно и границу не расширяет |

## Экземпляр главы

Дополнительная проверка полного ключа (P/01.1-16,22) идёт сверх сценарного TSV на отдельном экземпляре
с правами на acc/: ключи этого префикса на граничных длинах в байтах UTF-8, включая кириллицу и четырёхбайтные символы,
и тот же набор в непустом guard.key. У существующего стража использовать его фактическую версию, у отсутствующего —
index="", чтобы не попасть в отказ сравнения версии. Любая реализация принимает полный ключ до
KEY_BYTES; на байт больше — badkey.
Тестировать полное UTF-8-представление, не число символов.

Сценарии прогоняются через дверь хранилища (урок, N2) любой реализации; путь к двери (unix-сокет роли или стенд с той же дверью) — параметр стенда. Роль прогона — `acc` («Стенд» общей README): полные права на префикс `acc/` и ни на что больше. Для **каждого сценария, в том числе при повторном прогоне**, раннер создаёт новый изолированный экземпляр
хранилища с пустыми прикладными строками и пустой памятью идентификаторов записи `id`. В частности,
пусты оба тестовых префикса — `acc/` и `other/`. Очистка строк `acc/<сценарий>/` в прежнем экземпляре
недостаточна: она не снимает память повторов. Версии не обязаны начинаться с заданного числа.

Подготовку экземпляра, его каталога данных и прав делает раннер до начала сценария; проверяемые запросы
идут от указанной роли с правами на `acc/`, кроме шагов через дверь `admin` словаря. Строку вне этих прав пишет такой шаг через `admin.sock` экземпляра (`{socket}` «Стенда» общей README); перечисление видит её имя
и версию без значения, хотя права чтения там у роли нет (N3 «перечислить»). Query у `POST /v1/write` и тело у `GET` не читаются; `Infinity` и BOM в теле — N2.1.
Параллельные сценарии используют разные экземпляры и не разделяют ни строки, ни память `id`.

Параметры каждого экземпляра (N5 урока): потолок строки **524288 байт**, предел чтения HTTP-тела
**1048576 байт**. Раннер сверяет оба значения до сценариев поведением на пробном экземпляре, полученном тем же способом.
Изолированный экземпляр раннер получает способом, который реализация назвала в описании (нормы,
«Решает реализация» п. 10). Если параметры нельзя обеспечить или сверка не сошлась, прогон не выполнен;
нельзя подменять ожидаемые байты под имеющиеся настройки.

Раннер передаёт байты тела из `request` после подстановок, без повторной сериализации или иных добавлений.

## `seams.tsv` — сценарии над швами процесса (ADR-0125 доп. (4) п. 7)

Швы процесса проверяют свойства ядра, которые чеклист проверяет «чтением»: память
`id` не забывает по одному времени (P/01.1-11), равенство и обе стороны дробных границ времени приёма для put, delete и batch
(P/01.1-25), дробная часть времени приёма сохраняется при ходе часов назад и после перезапуска (P/01.1-26), одновременный CAS одной строки (P/01.1-15), пакет целиком после перезапуска
(P/01.1-31). Раннер исполняет их через адаптер швов, по [нормализации ниже](#нормализация-швов) (директивы `@clock`, `@reopen`, `@parallel` заданы там и в шапке файла). Этапы — `store_core` (`@clock`, `@parallel`) и `durable` (`@reopen`) из `forms/stages.tsv`, по `seams:1.1:<scenarios>` в их `gate`.

### Нормализация швов

У швов проверки P/01.1 нет строк `CALL`. Его шаги — запросы HTTP и директивы `@clock`, `@reopen` и `@parallel`. Над [мостом](../../../../common/ru/acceptance/seams.md#явный-тестовый-мост-швов) общей README приёмки каждый шаг HTTP или директива становится `method: call` с одним из трёх публичных токенов. Новых полей и методов моста нет.

| `name` | Шаг | `input` | Наблюдение |
|---|---|---|---|
| `store-http` | `GET` или `POST` | закрытый объект: обязательные `method` и `target` (путь с запросом, как записан в шаге), необязательный `body` (текст тела шага одной строкой, нет — если у шага тела нет) | `{kind: "value", value: {"status": <integer>, "body": <string>}}`: код и всё тело ответа |
| `clock` | `@clock +N` или `@clock -N` | закрытый объект `{"shift": <string>}`: сдвиг в том же синтаксисе, что в шаге | `{kind: "value", value: {}}` |
| `reopen` | `@reopen` | `{}` | `{kind: "value", value: {}}` |

`store-http` входит в обычную обработку запроса хранилища и не является новой дверью. `clock` сдвигает управляемые часы хранилища на N секунд, нарастающим итогом; часы начинаются с 2000000000, способ управления выбирает реализация. `reopen` закрывает хранилище и открывает его снова на том же каталоге данных с теми же часами. Шаг HTTP `<code> <JSON body>` сравнивается как в приёмке главы 1.1, `ok` директивы соответствует пустому объекту. `@parallel K` следует грамматике P/02 и исключению в этом мосте. Порты `CALL` главы P/01.3 — в её [README приёмки](../3/README.md).

## Дополнительная проверка класса ошибок

Повтор delete с тем же id и разными items (нет/null/число/объект/массив) сопоставляется по op/key/cas/guard. Смена key, cas, guard, not_after или not_before даёт другой отпечаток (P/01.1-R105). Версии сравниваются только на равенство: уникальность не означает числового порядка. Проверки POST также передают произвольные байты или отсутствие тела по общей грамматике, проверяя P/01.1-R048 и P/01.1-R144 (`body_form`).

Это предмет ручной проверки спецификации и будущей проверки реализации. Подготовленные запросы, чтение и конечные модели автора не являются выполненным стендовым испытанием.

Роль `console` предела числа строк не знает — глава 1.2. Перезапуск и группа — глава 1.3. Отказ тела сверх предела — общий отказ до разбора JSON.

## Лишние поля команды

Put/delete и их повторы принимают разные неизвестные поля верхнего уровня без изменения данных и отпечатка (P/01.1-R040, P/01.1-R090). Вложенный объект zzz не становится guard или новой командой. Настоящий guard остаётся закрытым по P/01.1-R032; put проверяет форму `items` по P/01.1-R019; delete игнорирует `items` по P/01.1-R099. Предел полного тела сохраняется, включая игнорируемые поля, до разбора (P/01.1-R034). Подготовленный сценарий не является выполненным HTTP-прогоном реализации.

Вне TSV проверить корректный GET /v1/list на ролевом сокете с заголовком пересылки роли: 403 forbidden до перечисления. Недоверенная пересылка и запрещённый пересланный admin также отказываются по P/01.2 N3 «проверить». Та же допустимая личность без прав read получает 200 с именами и версиями без значений. Отказы личности требуют профиля сокетов/доверия, в том числе заголовка чужой роли на ролевом сокете, по P/01.1-R066 и P/01.1-R144 (`identity`).

## Ключ, которого нет или который не строка

Проверки различают форму и правила ключа (P/01.1-R030, P/01.1-R031): отсутствующий или нестроковый key команды, guard.key или параметр key чтения даёт `400 badrequest`; строка, нарушающая N1, — `badkey` по P/01.1-R031 и P/01.1-R032. Итоговое чтение подтверждает отсутствие записи.

## Условия времени приёма (P/01.1-25; ADR-0091 п. 1)

Проверки времени приёма охватывают только края времени приёма (P/01.1-R079, P/01.1-R088,
P/01.1-R090): `not_after`, который уже прошёл, `not_after` и `not_before`, которые
ещё не настали при любых часах стенда. `expired` и `early` ничего не пишут;
порядок — «условия времени → страж → CAS»; `not_after` входит в отпечаток повтора (численно равное написание — то же значение, иное число и отсутствие — `400`);
отказ `expired` `id` не занимает; формы
(строка, отрицательное, `null`, `bool` — `badrequest`; форма стража раньше `not_after` — `badkey`). Граница равенства и
неубывание времени приёма — чтением (N5 норм).

## Разбор запроса (N2.1, P/01.1-23)

На ролевом сокете `op: floor` — `403 forbidden` раньше разбора ключа. Форма стража раньше правил ключа:
`guard: null` — `badrequest`. Query: `+` — пробел, `%2B` — плюс, `+` в `prefix`
тоже пробел, повтор параметра — `badrequest`, байты не UTF-8 — `badkey`, `%` без цифр остаётся
буквой ключа и строку не находит. Строгий JSON тела: повтор имени поля на верхнем уровне
и в `items`, `NaN` в лишнем поле, одиночный суррогат в ключе и в `items`; ничего не записано,
суррогат в лишнем поле не читается. Неизвестный метод и известный путь
не своим методом: `404` с `Fault`, а не 405 или 501; путь `/v1/%67et`, `/v1/get/` и `//v1/get` не декодируется и не
нормализуется — тоже `404`. Порядок проверок query: пустые пары пропускаются, `?key` — пустой
ключ (`badkey`), повтор раньше UTF-8 (`badrequest`).

Проба вне TSV — сырые байты в сокет двери, каждый ответ `400` с телом `Fault` `{kind: badrequest}`, а не страница
сервера и не 414, 431, 501 или 505: `GET /v1/list\r\n\r\n` (нет версии HTTP); строка запроса длиной в предел,
названный в описании реализации (п. 9 «Решает реализация»), плюс 1 байт — раннер чужого предела не знает и берёт его
оттуда; заголовок без двоеточия; заголовок с пробелом перед двоеточием и продолжение заголовка obs-fold (RFC 9112 §5.1–5.2).
Отдельно: цель в абсолютной форме `GET http://localhost/v1/get?key=acc/x HTTP/1.1` — `404 badrequest` (путь не
декодируется и не нормализуется, N2.1); тело с `Content-Length` и `Transfer-Encoding: chunked` вместе читается
как chunked (§6.3), после ответа соединение закрывается (RFC 9112 §6.1). Для корректного HTTP/1.1 это не автоматический `400`: ответ определяется своей операцией. Запрос HTTP/1.0 с `Transfer-Encoding` имеет ошибочную рамку: `400 badrequest` и закрытие (R054; RFC 9112 §6.1). Ранний отказ (N2.1): `POST /v1/write` с `Content-Length` больше предела тела и телом,
которое ещё идёт, — клиент получает `413 toolarge` с `Connection: close`, а не сброс соединения.

Пробы рамки и строки запроса (N2.1), каждая на сырых байтах:
- одиночный LF и одиночный CR в конце строки заголовка — `400`; пустая строка перед строкой запроса — `400`;
- сырой `\x00`, `\x01`, TAB, `\x7f` и `#` в цели запроса — `400` (`%00` — три допустимых байта, N2.1);
- заголовки суммой ровно 65536 байт строк полей без CRLF — разбираются (ответ по маршруту), 65537 — `400`; 2000
  коротких строк заголовков в пределе — разбираются;
- тело с JSON глубиной 128 в лишнем поле — записано, 129 — `400`;
- `Content-Length: +5` — `400`; два `Content-Length` с разными значениями — `400` и закрытие; `Content-Length` из 23
  девяток — `413 toolarge` без `size`; размер куска `0x5` — `400`; `Transfer-Encoding: gzip, chunked` и две строки TE —
  `400`; после каждой ошибки рамки соединение закрыто;
- оборванное тело: `Content-Length: 50`, 20 байт и полузакрытие записи; chunked без последнего куска — ответа нет; затем
  `GET` по новому соединению видит прежнее значение строки;
- без `Host`, два `Host`, `Host: a b/c` — как с обычным `Host`; `HEAD /v1/get?key=acc/x` — `404` без тела.

## Свидетели уточнения ядра ADR-0129

Шесть сценариев швов (только для судьи: `s7-admitted-single-refusals` — `s12-zero-version-not-absence` файла `seams.tsv`) используют только прежнюю грамматику HTTP, @clock и @reopen; они проверяют P/01.1-R088, P/01.1-R132, P/01.1-R070, P/01.1-R090, P/01.1-R355. Четыре принятых отказа expired, early, guard и conflict у одиночных записей и пакетов не дают бизнес-эффектов, и это совместимо с сохранёнными метаданными приёма; тот же отказанный id можно использовать с исправленным условием. То же различие сохраняется через обычный Close/Open; это graceful restart, не отключение питания или свидетель консенсуса.

Границы времени приёма сравниваются как значения binary64: у границы, равной часам в binary64, not_after допускает равенство, not_before отказывает, для put/delete/batch. В повторах применённых put/delete/batch написания границ, округляющиеся в одно binary64, дают один отпечаток, а значения, различные в binary64, дают другой отпечаток и badrequest. Байты запроса нельзя нормализовать до разбора настоящим хранилищем. Точное сравнение чисел движком CALL не подменяет отпечаток хранилища. Непустая строковая версия отлична от маркера отсутствия "" у одиночных/пакетных CAS и guards.

Проверки guard и CAS выбирают первый отказ при обоих порядках исходного списка (P/01.1-R125). Перестановка guards успешного повтора не меняет его отпечатка (P/01.1-R134). Успешное удаление отсутствующей строки оставляет index "" и допускает последующее создание (R116); delete отсутствующей строки в пакете следует P/01.1-R128 и P/01.1-R133. Дубликаты этих свидетелей не нужны.

Непрозрачные версии не показывают счётчик выдачи. Новые HTTP-пробы наблюдают неизменные строки/list и возможность использовать отказанный id; они не выводят ноль выданных версий вычитанием или порядком строк index. Обязанность R089/R132 не выдавать версию остаётся прежней проверкой чтением. Форма snapshot/effects, новый порт, native команда, реализация или ручное ядро не поставляются. Это исходные свидетели для обычного адаптера реализации, не исполненные результаты SUT.

## Повтор и последние метаданные приёма

Успешный повтор put/delete/batch с прежним id сохраняет первые ответы и версии; удалённая строка не получает видимой версии. Новые последние метаданные приёма повтора сохраняются через обычный reopen (N3 «Время приёма»). Эти случаи проверяют P/01.1-R070, P/01.1-R078, P/01.1-R105, P/01.1-R122; они входят в durable, поскольку содержат @reopen. Это проверка источника, не зачёт SUT.

## Принятые несовпадения и числовой домен приёма (ADR-0129 доп. (10), п. 3)

put/delete/batch с уже применённым идентификатором и иным содержимым — принятое несовпадение: badrequest с прочными последними метаданными приёма. Исходные строки/видимое отсутствие и первый ответ id сохраняются; повтор исходной команды по-прежнему возвращает этот ответ с again. Несовпадение не заменяет и не освобождает исходную запись памяти применённого id. Это принятые отказы, отдельно от формы/прав/framing до приёма; не всякий badrequest принят.

Назначенное дробное значение binary64 времени приёма переживает обычное открытие. Нельзя обрезать его до целых секунд/миллисекунд или записью времени строки в три знака. Свидетель не задаёт кодирования метаданных или точности физических часов.

Все четыре случая проверяют P/01.1-R078, P/01.1-R105, P/01.1-R122, P/01.1-R070; они используют только существующие HTTP, signed-decimal @clock и @reopen и выбраны прежним gate durable. Нового порта, внутреннего API, грамматики CALL, обещания snapshot или потери питания нет. 56 новых исходных шагов — не исполненная приёмка реализации. Именами констант владеет forms/runtime-constants.tsv; конкретные числа входов стенда/проб остаются тестовыми данными.
