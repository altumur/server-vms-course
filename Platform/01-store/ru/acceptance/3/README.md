## Интерфейс профиля

Используется [формат профиля](../../../../common/ru/acceptance/PROFILE.md) `01-store`. `stand.store` запускает долговечный демон. Подстановки стенда он несёт в своих флагах, каждый по одному разу, и не содержит флагов, которые дописывает стенд группы ([подстановки](../../../../common/ru/acceptance/PROFILE.md#подстановки)); флаги члена дописывает стенд группы ([стенд группы хранилища](#стенд-группы-хранилища)). `stand.backup` делает копию через `{socket}` в `{file}`; `stand.import` переносит `{file}` в остановленный свежий `{data}` с `{index_base}`. Операторские вызовы группы используют `stand.store-op` с `{socket}`, `{dir}`, `{id}`, `{tls}` и подготовленными `{args}`; пробы порчи строки используют `stand.spoil-row` с `{data}`, `{key}`, `{what}` по существующему договору стенда. `keys.store_build` объявляет `raft` или `box` с применимостью ниже; отсутствие и другое значение не выбирают один из вариантов молча. Имя заголовка роли — `keys.role_header`. Программы и обёртки выбирает реализация; смысл операций и флаги, добавляемые стендом группы, остаются по ссылочным нормам и общему стенду.

## Стенд

Хранилище стенда: схема 1, строки манифестов `testsub` и `testsub2` раннер пишет сам через `admin.sock`, без установщика
(ADR-0083 доп. (98)): `put` с `cas: ""` и ровно полями писателя P/02.3 N1.5 — `yaml` (байты файла), `sha256`
этих байтов, `rev` `"1"`; файл прав `{rights}` — подготовленный файл прав по P/01.2-R007, раннер кладёт его до запуска хранилища. Шагам главы из него нужны только сокет роли
`console` без прав `admin` (`@as console`: сц. 08 шаг 8, сц. 15 шаги 1–2) и строки манифестов `testsub`, `testsub2` (сц. 11
шаги 9–10: копия `backup` несёт строки манифестов). Ресурс, контроллер, консоль и воркеры главе не нужны. Хранилище стенда главы —
одиночный участник коробки без `-api` (N1.3 `-api`: флаг не обязателен; партнёров у коробки нет): сц. 16 на этом стоит.

- **Команды копии** (P/01.3 N1.3 `copy`, `admin_ops`): `backup` — шаблон с `{socket}` и `{file}`: копия хранилища через
  `admin.sock` в файл, код 0 — копия снята; `import` — шаблон с `{data}`, `{file}` и `{index_base}`: перенос копии в
  свежий каталог остановленного хранилища (P/01.3 N1.3 `box`), код 0 — перенесено, иной — отказ. Реализация называет
  обе (P/01.3 «Решает реализация» п. 4, 11).

## Пакет и перезапуск (сц. 30)

Пакет `op: batch` на хранилище стенда (P/01.1 N3 «записать пакет», ADR-0094 B9): строки и память `id` переживают `@restart store`, повтор отвечает
`again` с прежней версией; следующий пакет правит одну строку и снимает другую. Обрыв питания посреди пакета стенд не воспроизводит — чтением
(P/01.1-31).

## Чужой каталог (сц. 10)

Метка формата хранилища (глава 1.3 N1.3 `format`): второй экземпляр хранилища на непустом каталоге без
`FORMAT` и на каталоге с чужой меткой не стартует (код 2) и ничего в каталоге не меняет. Хранилище стенда сценарий не
трогает. Первая запись метки в пустой каталог и старт на своём — каждый запуск стенда и `@restart store` сц. 08.

Отдельная исполняемая проба `05-data-ownership` использует исправное завершённое состояние каталога, а не чужую/отсутствующую метку `FORMAT` сценария 10. Проверяются причины `start_data_dir_owned` и `local_data_dir_owned`: отказ второго демона до готовности/любой записи, неизменность первого владельца, данных и владения; отказ локальных import/restore на коробке и recover. Отдельная гонка одновременных стартов, в том числе на пустом каталоге, даёт ровно одного владельца; проверка владения предшествует другим зависящим от каталога причинам. После штатного выхода и `SIGKILL` на исправном завершённом состоянии проверяется законный старт без ручной уборки. Это не отменяет `start_format` или отказ на незавершённом `import`/`restore`: незавершённая передача проверяется отдельным отрицательным случаем после смерти владельца. Используются только собственные изолированные процессы и каталог. Нужны независимое подтверждение живого владельца, порядка проверок и атрибуция изменений; законная фоновая работа первого демона не приписывается второй попытке. Нет native-привязки — `NotExecuted`, не успешный отказ.

## Копия (сц. 11, 12)

**Копия повреждённых строк.** Существующая строка с повреждённым телом и целой версией сохраняется в backup как `{key, items: null, index, unreadable: true}`, где `index` — её точная непустая версия; прежние порядок ключей и согласованный заголовок копии сохраняются. Это отдельно от отказа import/restore на нечитаемом входе по N4. Если версия потеряна, по P/01.1 R028 нужна запись в журнал, CLI backup завершается ненулевым кодом и не заменяет прежний опубликованный файл. HTTP-копия может дать `503 UnavailableFault` до `200` либо неполное закрытие после `200`; завершённая копия с пропуском строки или выдуманным `index` недопустима. Отказ импорта на нечитаемом входе не разрешает убрать повреждённую строку из backup. Привязка `spoil-row` использует `what=body` или `what=index`; без неё зависимое наблюдение остаётся `NotExecuted`.

Копия хранилища (глава 1.3 N1.3 `copy`). Вход (`--from`) — JSON Lines; читатель порядка строк не требует;
копия не толкует строки манифестов (`platform/manifest/*`): `import` переносит строку любой семьи (глава 1.3 N1.3
`import`). При отказе `copy`
не перенесено ничего.

Отказ `copy`: неверные `format` или `version` заголовка, лишнее поле заголовка или строки, первая строка — не заголовок, у строки нет `index`, строка не JSON, значение `items` — не строка, ключ дважды, `index` строки выше `index` заголовка, строка `unreadable`, строка эпохи или пола с недесятичным значением (upper не достоверен), ключ строки — не ключ главы 1.1 N1, `generation_at` пола — не время; верная копия, у пола которой `generation_at` позже часов стенда, — отказ без `-force`.

Пол входа используется только для проверок upper и generation_at и не переносится; `import` поднимает новый пол выше
upper входа перед переносом остальных строк (N1.3 `floor`); число зависит от часов. Копия `backup` хранилища стенда, перенесённая в свежий каталог, несёт строки манифестов.
Сторона писателя правила «время в строке» (N0 главы 1.1): пол после `import`, `generation_at`
(`@time`).

## Фактический потолок тела в status (ADR-0127 P/06 C2)

Ответ Status стандартного стенда несёт обязательный `max_body: 1048576` и неизменный `max_value: 524288`. Повторить обычный status GET на новом store, настроенном существующими `-max-body 2097152` и `-max-value 524288`: max_body равен2097152, max_value остаётся524288. Это обязанность настоящего демона/HTTP; проверка источника/схемы этот повтор не выполняет. Не добавлять ключи acceptance.yaml и не угадывать лимиты по умолчанию.

Независимые проверки схемы содержат полные ответы Status: положительные потолки тела1/1048576/2097152 и отрицательные отсутствие/ноль/отрицательное/нецелое/bool/string/null. Применять существующую схему Status ко всему ответу. max_body считает байты сущности, включая фактический LF; HTTP request/header/chunk framing не входит. Статическая проверка профиля P06 использует значение этого ответа, не новый флаг и не замену max_value.

## Стенд группы хранилища

Группа raft из нескольких демонов хранилища на одной машине стенда — приёмка этой главы
. Свойства группы — состав, выборы, перезапуск, дверь без голоса, `recover`, `import` в группу — стенд
видит снаружи; учения на настоящем кластере ([системная приёмка](../../../../common/ru/acceptance/system/README.md)) этого больше не заменяют.
Нормы — P/01.3 N1.3 (`group`, `door`, `floor`, `import`, `leader_wait`, `repeat`), N1.6, N3 «восстановить
хранилище»; новых норм раздел не вводит.

- **Члены** — по имени `<id>`: голосующие `s1`…`s5`, двери без голоса `d1`, `d2`. В группе приёмки три голосующих; между участниками используется mTLS. Имя сервера листа члена — его `<id>`
  (лист `configstore.<id>` у голосующего, `configstore-door.<id>` у двери; [договор сертификата роли](../../../../common/ru/contracts/role-certificate.md), `cert`); адреса — петля
  `127.0.0.1`, порты раздаёт раннер (свободные на петле; в описании комплектов адресов нет): `{raft@<id>}`, `{api@<id>}` —
  подстановки в флагах, запросах и пробах; оба — адреса посредников раннера, которые член называет партнёрам (ниже). Партнёров член узнаёт как в норме: вступающий — флагом `-join {api@<id>}`
  (P/01.3 N1.3 `join`), дверь — `-voters`, перезапуск — из своего `member.json`; списка пиров раннер не передаёт. Имя пира
  демон сверяет с `<id>` участника, не с хостом адреса (адрес — петля у всех).
- **Комплекты** — комплекты приёмки главы 1.3: один центр группы, лист на каждого члена; раскладка — [договор сертификата роли](../../../../common/ru/contracts/role-certificate.md),
  `kit` (`ca.pem`, `<роль>/server.pem`, `<роль>/server.key`), `revoked` пуст, `ca.next.pem` нет. Раннер создаёт тестовый комплект в своём изолированном каталоге стенда и запускает демон от учётной записи вызывающего пользователя. Каталоги комплекта принадлежат той учётной записи и имеют режим 0750; ключ использует ветвь 0600 договора и принадлежит той же учётной записи демона. Демон может проходить по каталогам и читать свой комплект без привилегированной подготовки.
- **Сборка хранилища — признак профиля реализации `keys.store_build`**: `raft` — сборка с группой, сценарии стенда
  исполняются; `box` — хранилище коробки без raft, законное по P/01.3 N1.3 `box` (один голосующий; `-raft`, `-bootstrap`, `-group-size 3`/`5`,
  `-join`, `-door` — отказ старта, код 2): сценарии стенда группы — not_applicable, в итог не входят и не красные, зачёт
  урока — без них; признака нет или иное значение — сценарии не исполнены (not_executed, как без `keys.tls_stand`; не
  GREEN). Отказы сборки `box` проверяет сц. 04/16 хранилища стенда и чтением (P/01.3-01); стенд группы её не судит.
- **Запуск члена** — команда хранилища «Стенда» (та же, что у хранилища стенда), с окружением `BOX_ID=<id>`, `SERVER_NAME=<id>`, `PLATFORM_DIR={data}/<id>` (на стенде трёх серверов — `PLATFORM_DIR` его сервера), и
  подстановки члена: `{data}` — его `PLATFORM_DIR`, `{rundir}` — `{data}/run`, `{socket}` — `admin.sock` там же, и `{rights}`. Шаблон несёт их в своих флагах `-dir {data}/configstore`, `-sockets {rundir}`, `-rights {rights}`, `-max-body {body_limit}`, `-max-value {row_ceiling}` ([подстановки](../../../../common/ru/acceptance/PROFILE.md#подстановки)), поэтому каталог хранилища члена — `{data}/configstore` его `PLATFORM_DIR`. Раннер дописывает только эти флаги: `-id <id>`, `-tls <каталог комплекта>`,
  `-api {api@<id>}` (адрес посредника API раннера, который член называет партнёрам: `members`, `leader`, своё присоединение) и `-api-bind <свой порт>` (где он слушает служебные двери; P/01.3-R007), `-tuning lan`; голосующему ещё `-raft {raft@<id>}` (адрес посредника раннера,
  который член называет партнёрам) и `-raft-bind <свой порт>` (где он слушает; P/01.3 N1.3 «Флаги демона»). Прочие флаги — из строки
  директивы как написаны (`-bootstrap`, `-join`, `-group-size`, `-force`, `-door`, `-voters`). Шаблон не содержит ни одного дописываемого флага: повтор флага — отказ старта (P/01.3 N1.3).
- **Посредник API** — на `{api@<id>}` каждого члена: mTLS с обеих сторон. Вызывающему посредник предъявляет лист `<id>` и проверяет лист вызывающего по CA группы; к своему порту члена он подключается с листом того же вызывающего из комплектов, поэтому член видит того же пира и его роль в SAN (P/01.2 N3). По умолчанию он пропускает любой поток байтов приложения без изменений в обе стороны, без разбора HTTP и отказа не-HTTP кадрам. HTTP разбирается только при активном `@cut store@<id> answer`. Канал внутренних кадров участников выбирает реализация.
- **Двери члена**: `store@<id> <запрос>` — дверь P/01.1 сокетом роли сценария члена (роль называет README главы, `@as`
  меняет); `admin@<id> <запрос>` — через его `admin.sock` (не пересылается: запись — у лидера).
- **Границы**: между сценариями раннер останавливает всех членов и удаляет их каталоги; комплекты — на сценарий.

| Форма | Смысл | Урок |
|---|---|---|

### Наблюдение старта

Для первого голосующего с `-bootstrap` или двери `ok` означает, что `admin@<id> GET /v1/status` отвечает 200 за интервал старта. Первый голосующий не ждёт объявленного размера группы: остальных голосующих запускают следующие шаги.

Для голосующего, который стартует на пустом каталоге с `-join`, раннер сначала читает `GET /v1/status` через сокет admin живого голосующего, названного в `-join`. Ожидаемые `voters` — идентификаторы голосующих этого статуса с добавленным вступающим `<id>`. Ожидаемая карта `members` содержит ровно эти идентификаторы голосующих, каждый со своим назначенным `{api@<id>}`. Дверь не добавляется в `voters`. После восстановления этот снимок снимается заново; прежние отсечённые члены обратно не добавляются.

После запуска вступающего голосующего раннер опрашивает `admin@<id> GET /v1/status` вступающего и каждого уже работающего голосующего ожидаемого состава. Барьер нового вступления успешен, когда один проход опроса получает 200 от каждого, каждый `id` называет опрошенного голосующего, каждые `voters` равны ожидаемому множеству (порядок не важен), каждые `members` равны ожидаемой карте, у всех один непустой `leader_id` из этого множества. Все наблюдения укладываются в тот же интервал 20 с от запуска вступающего процесса; одного ответа 200 для завершения шага вступления недостаточно. Неуспешный барьер проваливает этот шаг и оставляет зависимые шаги неисполненными по общему правилу обрыва сценария.

Раннер не запускает следующего вступающего голосующего до успеха барьера. Он опрашивает статус, не отправляя повторный join и не добавляя `-force`. Ожидание отказа старта `@exit 2`, запуск первого голосующего с `-bootstrap`, запуск двери и `@restart` этот барьер нового вступления не применяют.

## Группа хранилища (сц. 07, 17, 18, 25–29, 31)

Стенд группы — раздел [«Стенд группы хранилища»](#стенд-группы-хранилища): члены `s1`…`s5`, `d1`, `d2` на петле, стенд передаёт комплекты по P/01.3-R009 (один центр, имя сервера листа — `<id>` члена), роль сценария у дверей `store@<id>` — `console`
(файл прав стенда). Хранилище стенда главы этим сценариям не нужно. Сборка 1→2→3: второй член вступает с `-force` (группа из двух — переходная чётность, P/01.3 N1.3 `join`), третий — без него, после барьера нового вступления второго из [наблюдения старта](#наблюдение-старта). В группе стенда три голосующих; между участниками используется mTLS. Сборка хранилища коробки
(`keys.store_build: box`, P/01.3 N1.3 `box`) группы не имеет: сц. 07, 17, 18, 25–29, 31–34 для неё — not_applicable, не красные; без
признака — не исполнены («Стенд группы хранилища» выше).

- **Пакет в группе (ADR-0094 B9).** Дверь пересылает пакет целиком: ведомые читают обе строки с одной версией; повтор по `id` идёт через голосующего и через дверь; устаревший `cas` строки — остальные не записаны. Своя строка двери пакетом — 403 (N1.3 `door`). После `@sigkill` лидера новый лидер отдаёт обе строки.
- **Размер и дверь без голоса.** Вступление сверх объявленного размера — 409 `refused` и без `force`, и с `force` (сверх объявленного размера `-force` не берёт; N1.3 `join`). Дверь (`-door -voters`): `state` `Door`, запись через неё — тем же файлом прав (пересылка лидеру, видна у ведомого), строка `platform/configstore-doors/<id>` со свежим `seen_at`, ряд `configstore_doors` у лидера. Дверь, у которой `-id` не сервер своего листа, — отказ старта. Лист двери пишет у лидера чужую строку семьи `platform/configstore-doors/` — 403, свою — 200 (N1.3 `door` «своя»); заголовок пересылки роли в пробе — обозначение, имя — из описания реализации.
- **Состав, перезапуск, смена лидера, кворум.** Размер вне `sizes` N1.3 — отказ старта; `leave` остановленного члена, его `join` до `admit` — 403, `admit` повторяем (код 0), после него `join` тем же адресом — 200, иным адресом Raft — 409, `leave` неизвестного — 409 (N1.3 `leave`, `repeat`); перезапущенный член снова ведомый. После перезапуска ведомого и всей группы версии одинаковы у всех, и запись с `cas` этой версии проходит (журнал не применяется повторно). После смены лидера чтение у оставшихся сразу после выборов видит версию записи, вернувшийся член — тоже (чтение линеаризуемо, P/01.1 N3). Без кворума запись через дверь и через голосующего — 503 `unavailable` после действующего интервала `-leader-wait`: дверь в кворум не входит.
- **`import` в группу и `recover`.** `import` копии в свежую группу на лидере; повтор завершённого — отказ (N1.3 `admin_ops`). Перенесённые строки сохраняют версии копии, и `cas` по ним проходит (P/01.3 N1.3 `import`, N3 «копия переигрывается ровно в те строки и версии»): реализация, что переписывает перенос обычными `put` с новыми малыми версиями, здесь падает. Что новые версии после переноса выше `-index-base`, сценарий числами не судит (строки сравниваются только `==`/`!=`) — чтением. При потере большинства `recover` без `-isolated` и с `-upper` ниже вычисленного — отказ до изменений; с `-isolated` — пол по upper строк эпох, строки и эпохи сохранены (upper — из всех строк эпох). Прежние члены со старыми каталогами не возвращаются (N3 шаг 0); новые члены вступают из пустых каталогов (`-force` при переходной чётности); пол виден у нового ведомого.
- **Лист двери на `-raft`**: лист двери на raft-порту члена — `handshake: alert` (P/01.3 N1.6 `raft`).
- **Пересылка, метрики и отрезанный raft-порт**: лист голосующего с заголовком пересылки роли `admin` у лидера при загруженном файле прав — 403 (P/01.2 N3); ряды `/metrics` лидера и ведомого (имена N1.3 `metrics`, состояние строчными по ADR-0070); посредник на raft-порту члена рвёт входящие соединения (исходящие члена идут прямо): после записи чтение у отрезанного члена — новая версия или 503, не прежняя, после `@mend` — новая (кто лидер — шаги не предполагают).
- **Статус и строки двери, края import и recover**: `/v1/status` двери целиком по N2: `Door`, `role` `door`, `term`, `commit`, `applied` — 0; лист двери у лидера: своя строка с `cas: ""`, с лишним элементом и её удаление — 403, своя по форме — 200 (N1.3 `door`: только `put` без `cas` и `guard`, единственный `seen_at`); живая дверь написала свою строку: `import` копии с `-index-base` ниже версий копии — отказ, строк нет; с `-index-base` не ниже них — перенесено, версия копии сохранена (строка двери свежести не отменяет); при потере большинства `recover -peers` без своего члена, без адреса `api`, с повтором члена — отказ; `-upper` выше вычисленного поднимает пол; `import` копии с будущим `generation_at` пола без `-force` — отказ, ничего не перенесено, с `-force` — перенесено, пол поднят (N1.3 `floor` `when`, «Флаги демона» `-force`).
- **Потерянный ответ пересланной записи**: `@cut store@s1 answer` у лидера `s1`, затем запись. Лидер выполняет и фиксирует её, его ответ до вызывающего не доходит. Дверь с `id`, ведомый с `id` и дверь без `id` отвечают 503 `ambiguous`, не `unavailable`: запись ушла лидеру без ответа. Дверь с `id` может повторить у других голосующих; они пересылают лидеру через тот же посредник, их ответ тоже `ambiguous`, поэтому исход двери за её попытки остаётся `ambiguous`. Фиксация через другого члена после смены лидера этот исход тоже не меняет: посредник держит ответ, а не фиксацию. До `@mend` чтение у лидера уже даёт версию записи; после `@mend` повтор с тем же `id` через дверь и через голосующего даёт `again` с этой версией; та же запись `cas: ""` без `id` даёт 409 `conflict` с этой версией, а не вторую запись. Что дверь не повторяет запись без `id`, остаётся чтением: повтор записи с `cas` не оставляет второго наблюдаемого следа.
- **Чтением остаются**: полный разрыв члена в обе стороны (исходящие соединения члена на одной машине не режутся);
  что дверь не повторяет запись без `id` (сц. 34 выше); писатели во время `import` (окно между полом и «Готово»); лист двери
  на `-raft` теперь не чтением: сц. 07, последний шаг, выше; нечитаемая строка двери вне `configstore_doors` (N1.3
  `door`) — запрос TSV не несёт текущего времени для свежего `seen_at`, а строку с давним `seen_at` реализация вправе
  не считать видимой дверью по сроку (дверь пишет её каждые 30 с): шаг не отличил бы нечитаемую строку от несвежей; `recover` при часах раньше
  `generation_at` пола — стенд не ставит пол с будущим `generation_at` в группу (`op: floor` пишет часы лидера).

## Хранилище стенда: перезапуск, копия с эпохой, порча строки, память повторов, служебные двери (сц. 12, 19–24)

- `import` входа со строкой эпохи или пола с недесятичным значением — upper не достоверен, отказ всего входа, ничего не перенесено (N1.3 `import`).
- Версия после перезапуска демона на том же каталоге — прежняя строка с прежней версией, новые версии
  отличны от неё (P/01.1 N1 `index`); недолговечное учебное хранилище эту проверку не исполняет.
- `@spoil row` / `@spoil row-index` (общий README) — порча мимо двери командой профиля `spoil-row`
  при остановленном хранилище, затем запуск: тело нечитаемо — `items: null`, версия цела, `cas` по ней заменяет строку;
  версия потеряна — 503 у чтения и задетого перечисления (P/01.1 N2). Без команды профиля —
  not_executed.
- Память повторов `id` (P/01.1 N3) держится не меньше двух минут; право забыть после 2 мин и 50 000 записей — чтением.
- Ключ строки с `..`, `generation_at` пола не время, часы стенда раньше `generation_at` пола входа (без `-force` директивы `@import store`) — отказ всего входа (N1.3 `import`, `floor`; исходы семьи `epoch_floor`). Повреждённая строка существует для стража и удаления (P/01.1 N2): страж `""` — 412 с её версией, по версии — держит; удаление с `cas: ""` — 409, с `cas` по версии — строки нет; без команды профиля `spoil-row` — not_executed. Служебные двери (N2): лишнее поле в `join`, `leave` и `op: floor` и неверный `id` участника — 400; отказанный пол не записан. 405 у `POST /metrics`, `GET /v1/join`, `GET /v1/leave` (N4).

## Границы сценариев

Между сценариями раннер останавливает процессы, сбрасывает хранилище и переменные; члены группы и их каталоги — тоже.

## Полная форма и воспроизводимость

До каждого автоматического сценария остановить процессы предыдущего, создать отдельные пустые строковое/объектное хранилища и очистить переменные/память повторов. Загрузить неизменённые testsub и testsub2; root — testsub, второй доступен под /testsub2; домена нет, обращения с петли. Фоновые controller/resource/worker до @start не работают. Сборка — схема 1; отсутствие platform/schema подтверждено чтением. Для каждого POST создания единицы раннер выдаёт свежий Idempotency-Key, сохраняемый только для повторов того же шага. POST таблицы не получает этим обещания памяти повторов.

Подмножество expect не заменяет проверку полной HTTP-формы OpenAPI урока: проверить обязательные поля, типы, Content-Type, специальные заголовки и отсутствие тела у HEAD/204. В строках ожиданий `$name` впервые связывается только после успешного совпадения всего ответа; следующие употребления сравнивают, запросы используют только уже связанные значения. Неудачная попытка @until не меняет переменные. @until повторяет чтение до указанного местного срока, не мутацию; после истечения — FAIL с последним ответом. @any допускает любое значение присутствующего поля, @absent требует отсутствия; они не подменяют типы полной схемы. JSON-объект сравнивается по подмножеству (`{}` на любом уровне — ровно пустой объект: словарь общего README), массив — по длине и порядку. Сырой HTML/текст сравнивается как байты UTF-8 с заданной подстрокой, не разбирается как JSON.

Всего 27 сценариев / 328 шагов, все автоматические (только для судьи: `acceptance/3/scenarios.tsv`). Пол только вверх, только admin. Память повторов `op: floor` — в хранилище
(глава 1.3 N2): повтор тем же `id` после перезапуска — тот же `index` и `again`, иной `floor` с этим `id` — 400; реализация,
которая держит её в памяти процесса, после перезапуска отвечает 409 «только вверх» и сценарий не проходит.

## Дополнительная проверка чтением

Чтением: 503 unavailable после действующего интервала -leader-wait без лидера, ambiguous после неизвестного исхода (потерянный ответ пересланной записи — сц. 32–34) и unavailable с Retry-After при пределе соединений — разные ветви. Сц. 05 [системной приёмки](../../../../common/ru/acceptance/system/README.md) с одним выпавшим сервером сохраняет кворум и не проверяет все 503. Повтор id с другим floor — 400 badrequest. Для /v1/write и /v1/rights неизвестный метод — 404 владельцев, 405 только у status/join/leave/metrics. Метрика сц.04 — configstore_raft_voters_expected. Значения запускающего следуют P/02.4, умолчания демона принадлежат только forms/daemon-flags.tsv; переопределение профиля объявляют до приёмки.

Это предмет ручной проверки спецификации и будущей проверки реализации. Подготовленные запросы, чтение и конечные модели автора не являются выполненным стендовым испытанием.

## Швы ревью

Швы комплектов для проверки P/01.3-R006 и P/01.3-R026 используют CALL/JSON [P/02](../../../../02-installer/ru/forms/README.md). Эти четыре шва помогают существующим приёмке и чтению, новых публичных целей раннера нет. Прежний шов s2 главы 1.1 повторяет **тот же id** после early и продвижения часов (только для судьи: шов s2 `acceptance/1/seams.tsv`).

`store-start-flags` вызывает обычные разбор командной строки демона и допуск конфигурации старта (до проверки Raft-возможностей сборки), не отдельный тестовый валидатор. Даны валидные временные dir/sockets, id и нейтральные входы. loopback/non_loopback выбирают валидные адреса по существующему loopback, нового синтаксиса адреса нет. Без TLS отказ до сети, наблюдаются реальные вызовы и код. Здесь проверяется допуск конфигурации, не полный процесс/группа.

`store-copy-floor` использует настоящие прочные backup/import/продолжение. Восстановить валидный исходный вход, снять настоящую backup-копию уже восстановленного хранилища с его floor и хотя бы двумя прочими строками, импортировать неизменную копию в свежий каталог. Прервать I/O после прочного переноса одной строки кроме пола; закрыть и продолжить ту же попытку с тем же входом. Снять первую новую строку F1, включая items/index/generation_at, сравнить её после продолжения. Наблюдать реальный порядок записей, все прочие строки/версии, полноту и отсутствие переноса старого пола. Часы управляемые; готовые результаты backup/import и вымышленные наблюдения не допускаются. Паника, посторонняя ошибка и неисполненный путь проваливают шов.

Каждый порт получает ровно описанный ниже JSON-объект и возвращает свой объект результата как value прежнего протокола CALL/моста. Входы и результаты — закрытые объекты: каждое названное поле обязательно, кроме условных полей ниже; прочих полей нет. Это наблюдения обычной реализации со стороны проверки, а не тела продуктовых команд.

| Порт CALL | Объект входа | Объект результата |
|---|---|---|
| `store-start-flags` | `api`, `raft`, `join`: каждое — строка из `absent`, `loopback`, `non_loopback`; `tls`: boolean | `config_accepted`: boolean. Если true, это единственное поле. Если false, также `exit`: целый код выхода CLI, и `network_setup_calls`: неотрицательное целое число реальных вызовов настройки сети до отказа. |
| `store-copy-floor` | `input`: строка `backup_of_restored_store`; `interrupt_after_target_rows`: целое `1` | Шесть boolean: `first_write_is_new_floor`, `new_floor_greater_than_input`, `old_floor_transferred`, `same_floor_row_after_resume`, `other_rows_and_versions_equal`, `complete`. |

Для старта `absent` убирает флаг, а каждый класс адреса выбирает корректный адрес этого класса; `tls` выбирает валидный комплект или его отсутствие. Адаптер готовит свежие корректные dir/sockets и явный id, прочие нейтральные флаги оставляет с корректными значениями. `config_accepted` наблюдает допуск после обычных проверок флагов/конфигурации, до проверки возможностей сборки Raft; работающий процесс этим не доказывается. При отказе адаптер сообщает реальные код выхода и число вызовов настройки сети. Проверочный валидатор не заменяет запуск.

Для порта копии входной токен выбирает описанную выше процедуру исходного входа/backup/import/продолжения. Управляемые настенные часы делают исходный вход допустимым и не меняются при переносе и продолжении. `first_write_is_new_floor` сравнивает первую запись строки назначения с новой строкой пола; `new_floor_greater_than_input` сравнивает числовой floor с полом backup; `old_floor_transferred` отмечает, переносилась ли когда-либо входная строка пола как строка назначения.

`same_floor_row_after_resume` сравнивает точные items, index и generation_at F1 до и после продолжения. `other_rows_and_versions_equal` сравнивает каждую строку кроме пола с неизменной backup-копией; `complete` наблюдает успешное завершение с ровно этими строками и F1. Прерывание происходит после барьера прочности первой строки назначения кроме пола и до следующей строки назначения, поэтому попытка остаётся незавершённой. Значения получены из реального I/O и сохранённого состояния; паника или посторонний отказ проваливает вызов, а не даёт объект результата.

## Нестандартный предел тела служебной двери

Использовать прежний параметр свежего стенда body_limit (флаг -max-body), например2097152 из свидетеля status выше (только для судьи: `acceptance/3/inputs/status-body-limits.json`). Пусть B — этот фактический предел в max_body. Послать POST /metrics с одним JSON-объектом, дополненным JSON whitespace ровно до B байтов сущности: рамка проходит, прежний исход метода405. При B+1 байтах ответ413 идёт до исхода метода, с BodyTooLargeFault.limit равным B, а не потолку строки или умолчанию флага. Повторить лишнее тело у служебного POST-маршрута: отказ до JSON/body или работы с составом. Сравнить состав до/после: он неизменен. Сохранить обычную проверку полного Fault/заголовков и независимого max_value. Нового ключа профиля, записи команды или грамматики запроса не нужно. Это обязанности сырой HTTP-пробы настоящего демона, не результат исполнения источника/схемы.

## Покрытие боевой квалификации

[Договор производственной приёмки](../../qualification/README.md) (только для судьи: процедуры квалификации) отдельно от этих функциональных сценариев назначает группы нагрузки, сроков фаз, копии/остановки, стадий сбоя и HTTP-копии. Боевой результат требует объявленных бюджетов, независимой активации и полных наблюдений. Прежние TSV-входы/ожидания и применимость обычного/group стенда сохранены; нет привязки или бюджета — blocked/NotExecuted, не PASS.

Для привязок цели `P/01/production` слова payload значат следующее. Граница `admission_time` — стенные часы процесса демона, которые P/01.1 N3 «Admission time» читает при допуске: provider наблюдает этот домен часов процесса, а время допуска, которое хранит демон, судится публичными исходами случая, не provider. Ресурс `heap` — резидентная анонимная память процесса (`RssAnon` из `/proc/<pid>/status`), а `memory` — его резидентный набор (`VmRSS`); показатель кучи среды исполнения языка ресурсом формы не является. При latch `sink` provider — читатель вывода, а `cancel` — его деактивация: provider закрывает sink на `deactivate`, `monotonic_ns` записи деактивации — этот момент, и ни одно наблюдение `cancel` не несёт. Фаза `recover_mark` не называет файла: метка — первый изменяющий шаг `recover` в `-dir` (P/01.3 R021), а точка сбоя — первое изменение `-dir` после первой записи верхнего уровня, которую `recover` завершил; поэтому ни payload, ни вызов имени метки не несут. Фаза `copy_after_headers` — конец потока, как его получает клиент после полного блока заголовков ответа `200`, сделанный между демоном и клиентом: она даёт ту половину `RUN-H03`, которую судит CLI. Половина демона после `200` — только неполное закрытие и никакого второго отказа — судится на его собственном потоке при отмене, застое sink и остановке, которые делает судья; у сбоя внутри демона привязки нет.
