# Урок P/01 — Хранилище

*Модуль «Платформа», урок P/01 — процесс хранилища. Это лекция: она объясняет, зачем и почему, и ничего не нормирует. Точные правила — главы [`spec/01.1-store.norms.md`](spec/01.1-store.norms.md) (словарь операций), [`spec/01.2-store.norms.md`](spec/01.2-store.norms.md) (файл прав и оценщик) и [`spec/01.3-store.norms.md`](spec/01.3-store.norms.md) (демон хранилища); контракт дверей — [`spec/01-store.api.openapi.yaml`](spec/01-store.api.openapi.yaml), инструкция тому, кто пишет реализацию, — [`spec/01-store.README.md`](spec/01-store.README.md). Форма урока — ADR-0080; модуль — ADR-0083.*

**Время:** ~60 минут чтения.

## Зачем этот урок

Всё, что платформа знает о себе, лежит строками в одном хранилище «ключ → значение»: единицы работы подсистем, слоты воркеров, эпохи, назначения, ключи идемпотентности, данные домена (какие именно строки — следующие уроки модуля; перечень — [каталог данных](../common/data/catalog.tsv)).

Хранилище умеет немного. Но на этом немногом стоит вся платформа: выдача номеров без координатора ([урок P/03](../03-worker/03-worker.md)), доказательство права писать (урок P/03), контроллер, который не ломается при двух запущенных экземплярах ([урок P/04](../04-controller/04-controller.md)), и повтор записи, который не применяется дважды (этот урок). Если хранилище держит свои гарантии — платформа работает. Если нет — она ломается так, что причину не найти.

Поэтому словарь операций определяется один раз и здесь. Каждый следующий урок описывает свои проходы (семантику операций по шагам) только этими словами и ссылается сюда; свои примитивы, «атомарно» и «одновременно» без операции словаря в уроках не допускаются.

## Цели и не-цели

После урока вы будете понимать:

- как два процесса правят одну строку без блокировок в прикладном коде;
- почему версию нельзя сравнивать на «больше / меньше»;
- как хранилище отсекает процесс, который уже потерял право писать;
- почему у записи три исхода, а не два, и что делать с третьим.

Границы урока: словарь и наблюдаемые гарантии. Алгоритм консенсуса, права процессов и операции платформы остаются следующим урокам.

## Что нужно знать заранее

Достаточно знать, что такое HTTP-запрос с JSON-телом и unix-сокет. Из курса — ничего: это первый урок модуля.

## Модель данных

В хранилище одна сущность — **строка** (row; запись хранилища, не строка текста):

| Поле | Что это | Пример |
|---|---|---|
| `key` | имя, путь через `/` | `testsub/counters/c1` |
| `items` | содержимое: словарь «строка → строка» | `{"name": "c1", "value": "7"}` |
| `index` | версия, которую выдало хранилище | `"42"` |

Отсутствующая строка читается как `items = null`, `index = ""`. Это не ошибка.

Сквозной пример модуля — учебная подсистема `testsub` (`Source/tests/testdata/testsub.subsystem.yaml`, та же у продукта): её единицы — именованные счётчики `testsub/counters/<имя>`. Остальные строки этой подсистемы вводятся в следующих уроках.

## Шесть слов словаря

Четыре операции — **прочитать**, **перечислить**, **записать**, **удалить** — и два условия записи — **`cas`** (условие на версию той же строки) и **`guard`** (страж: условие на версию *другой* строки). Это и есть «шесть слов», которыми написаны все проходы курса.

## Три гарантии

1. **Запись с условием на версию (`cas`).** Запись проходит, только если версия строки не изменилась с момента чтения.
2. **Версии не повторяются.** Хранилище никогда не выдаёт одну версию дважды — ни после перезапуска, ни после смены лидера, ни после удаления строки.
3. **Условие на другую строку (`guard`, страж).** Запись может потребовать, чтобы *другая* строка всё ещё была на той версии, которую писатель видел.

Разберём каждую.

## Гарантия 1. CAS: одна строка правится по очереди

Два процесса читают один счётчик и оба хотят его увеличить:

```
A: прочитать testsub/counters/c1                  → {"value": "7"}, index "41"
B: прочитать testsub/counters/c1                  → {"value": "7"}, index "41"
A: записать  testsub/counters/c1 {8} cas="41"     → index "42"        успех
B: записать  testsub/counters/c1 {8} cas="41"     → 409 conflict      B опоздал
```

B не затёр изменение A молча. Он получил отказ, перечитал (`"8"`, index `"42"`) и повторил. Никаких блокировок в прикладном коде.

Поле `cas` бывает трёх видов: не задано — запись проходит всегда, поверх того, что есть; `""` — только если строки ещё нет (создание; побеждает первый); версия — только если версия строки ровно эта.

## Гарантия 2. Версия непрозрачна

Версия — строка байт, которую выдало хранилище. Вызывающий возвращает её как есть и сравнивает **только на равенство**.

Соблазн велик: у реплицированного хранилища версия — номер в журнале, выглядит как число. Но это не обещание клиенту, а форма провода двери. Одна строчка `if v > old` в коде — и хранилища, где версия просто строка (как `resourceVersion` в Kubernetes), больше не подходят без правки всего, что выше этого урока.

**Почему версия не повторяется даже после удаления.** Пусть удаление не тратило бы версию:

```
A: прочитать k              → index "5"
B: удалить   k              → сделано
C: записать  k cas=""       → index "5"    ← та же версия у новой строки
A: записать  k cas="5"      → успех        ← A затёр строку, которую никогда не видел
```

Поэтому удаление тоже выдаёт новую версию, и после него `cas="5"` уже не пройдёт.

## Гарантия 3. Страж: запись зависит от другой строки

Представим приложение с двумя строками: `example/permit` называет процесс, которому приложение разрешает менять счётчик `example/counter`. Процесс A прочитал разрешение на версии `"70"`, но задержался. За это время разрешение перешло к B:

```
A: прочитать example/permit                 → {"writer": "A"}, index "70"
B: записать example/permit {"writer": "B"} cas="70" → index "71"
A: продолжить работу со старым разрешением
```

Если A проверит разрешение отдельным чтением перед записью счётчика, между этими двумя операциями оно всё равно может измениться. Страж (guard) проверяет версию строки разрешения **внутри той же операции**, что и запись:

```
A: записать example/counter {"value": "8"} guard={key: "example/permit", index: "70"}
   → 412 guard {key: "example/permit", index: "71"}
```

Хранилище не знает смысла поля `writer`. Оно сравнило версии и отказало: основание, на котором A собирался писать, уже изменилось. Приложение использует это условие, чтобы остановить прежнего писателя. Как платформа применяет его к воркерам и срокам владения, разберём в [уроке P/03](../03-worker/03-worker.md).

**Страж проверяется раньше CAS.** Если нарушены оба условия, ответ — `412 guard`, а не `409 conflict`. Смысл разный: `409` значит «перечитай изменяемую строку и повтори», `412` — «остановись и заново проверь основание для записи». Повторять со старым разрешением не нужно. Страж с `index: ""` означает «пока этой строки нет».

**Условия времени.** Ещё два условия записи смотрят не на строку, а на время: `not_after` — «примени, только если не
позже», `not_before` — «примени, только если строго позже». Время берёт не писатель, а хранилище: лидер ставит каждой
записи журнала **время приёма** — наибольшее из своих часов и времени предыдущей записи, — и условия проверяются по нему
при применении. Так время приёма по журналу не убывает, даже если все часы кластера разом ушли назад, и удаление с
`not_before` = T отсекает всякую позднюю запись с `not_after` = T: она получит `409 expired`. Ранняя попытка удаления —
`409 early`, её повторяют следующим шагом. Кто ставит эти условия и зачем — заказ строки другой подсистемы
(урок P/03, глава 3.6; ADR-0091). В «шесть слов» они не входят: это поля той же операции записи.

## Ключ пишется одним способом

Для человека `testsub/a/../b` и `testsub/b` — одно место. Для хранилища — две разные строки с разными версиями. Два процесса, уверенных, что правят одну строку, оба выиграют свой CAS. Взаимное исключение не сработает — и не из-за гонки, а из-за написания.

Поэтому ключ, который можно записать двумя способами, хранилище отвергает (`400 badkey`), а не нормализует. Точная грамматика ключа и порядок его проверки находятся в [нормах этого урока](spec/01.1-store.norms.md), Н1 и Н3. Префикс перечисления — не ключ: это просто байты, с которых должно начинаться имя, и к нему правила ключа не применяются.

## Три исхода записи

Для вызывающего у записи три исхода: сделана, точно не сделана и неизвестно. Последний возможен и на одной коробке (одном сервере без группы): ответ мог потеряться, или строка уже опубликована, а подтверждение сохранения на носителе не удалось. В группе серверов ещё один пример — запись дошла до лидера, а он упал, не ответив. Он мог успеть её применить, а мог не успеть.

| Ответ | Что случилось | Что делать |
|---|---|---|
| `200` | запись применена | ничего |
| `503 unavailable` | лидер не найден за срок ожидания или у двери занят предел соединений; запись **точно не дошла** | повторить как есть на следующем шаге (при `Retry-After` — не раньше срока) |
| `503 ambiguous` | надёжный результат записи **неизвестен**: например, отказал барьер долговечности или пропал лидер после приёма записи | повторить **с тем же `id`** |

**Почему при `ambiguous` нельзя угадать.** Решили «не применилась» и повторили с тем же `cas` — если первая прошла, придёт `409 conflict`, и клиент решит, что строку изменил кто-то другой, хотя это была его собственная запись. Решили «применилась» — если первая не дошла, запись потеряна. Прочитать и посмотреть тоже не поможет: свою запись не отличить от чужой с тем же содержимым.

**Решение — идентификатор записи `id`.** Клиент ставит на каждую запись случайный `id` (32 шестнадцатеричных знака). Повтор с тем же `id` вернёт ответ первой попытки с пометкой `again: true`, если она применилась, и выполнится как первая, если нет. Клиенту не нужно различать эти случаи.

Хранилище помнит `id` не меньше двух минут после первого применения, **пока** после него применено меньше 50 000 записей с идентификатором (Н3, P/01.1-11). Только когда выполнены оба условия — прошло больше двух минут **и** после первого применения применено не меньше 50 000 записей с идентификатором, — канон разрешает забыть `id`. Тогда повтор выполнится как новая запись. Поэтому у каждой важной записи должен быть `cas`: он подстрахует там, где память `id` кончилась.

И главное: ни `unavailable`, ни `ambiguous` — не `conflict`. Конфликт значит «строку изменил кто-то другой». Если отвечать конфликтом при смене лидера, клиенты будут ошибаться при каждых выборах. К чему это приводит на деле — живой воркер останавливается из-за ложного конфликта при продлении слота — разберём в [уроке P/03](../03-worker/03-worker.md) (глава 3.2).

## Операции одним взглядом

Это пояснение; нормативные проходы по шагам — `spec/01.1-store.norms.md`, раздел Н3.

| Операция | Вход | Результат |
|---|---|---|
| прочитать | key | `items` и `index`; отсутствующая строка — `null`, `""` |
| перечислить | prefix | все ключи с этим префиксом и их версии, по порядку байтов; содержимого не отдаёт и прав на него не требует |
| записать | key, items, `cas`?, `guard`?, `not_after`?, `not_before`?, `id`? | новая версия |
| удалить | key, `cas`?, `guard`?, `not_after`?, `not_before`?, `id`? | новая версия; удалить отсутствующую строку — не ошибка |

Каждая операция неделима: между её шагами никто не вклинится. На одной коробке это обеспечивает блокировка, в группе — одна запись журнала консенсуса, которую каждый сервер применяет одинаково. Чтение линеаризуемо: оно видит все записи, о которых уже узнал хоть один клиент; в группе это значит, что чтение идёт через лидера.

Процессы говорят с хранилищем по HTTP с JSON через unix-сокет своего сервера — эту дверь (HTTP API) и описывает `spec/01-store.api.openapi.yaml`. Именно поэтому реализацию можно написать на любом языке: приёмка идёт снаружи, по HTTP, одними и теми же сценариями.

## Отказы

Список отказов закрыт: код, `kind` и поля нормированы в `spec/01.1-store.norms.md`, раздел Н4, новых видов не бывает без правки норм. Для чтения лекции достаточно трёх групп: ошибки кода и развёртывания (`badkey`, `badrequest`, `forbidden`, `toolarge`) — не повторять, чинить; `conflict` — перечитать и повторить; `guard` — не повторять, проверить владение слотом; `expired` — не повторять: срок записи прошёл; `early` — повторить новой записью следующим шагом; `unavailable` и `ambiguous` — повторить, второй только с тем же `id`. Если ответ оборвался или не пришёл, клиент считает его `unavailable` для чтения и `ambiguous` для записи — и не роняет свой цикл исключением.

У размера есть две разные границы. Хранилище считает вес имён и значений `items`, а дверь ограничивает
всё HTTP-тело: вместе с JSON-обрамлением и остальными полями команды. Поэтому строка ровно на своём
потолке может помещаться, хотя запрос чуть больше неё. В отказе `toolarge` поле `limit` называет ту границу,
которая сработала; точные правила — Н2 и Н4, параметры проверочного стенда — Н5.

## Что оставлено реализации

Урок нарочно не говорит, *как* это сделать. Каждая реализация сама выбирает и описывает в своём описании (ARCHITECTURE): чем обеспечена неделимость, откуда берутся версии, как данные лежат на диске и когда они гарантированно на носителе, сколько помнит `id` сверх минимума, как дверь отличает «не добавлено в журнал» от «неизвестно». Полный список — `spec/01.1-store.norms.md`, «Решает реализация».

## Как проверяется

Набор сценариев приёмки гоняется через дверь против любой реализации — на файлах, в памяти, в группе. Сценарии одинаковые для всех языков, путь к двери — параметр раннера. Часть свойств сценарием не проверить детерминированно: линеаризуемость чтения, `ambiguous` при падении лидера, неповторяемость версий после перезапуска. Их проверяют чтением описания реализации и учениями на настоящем кластере (глава 1.3, [системная приёмка](../common/acceptance/system/README.md)).

## Файл прав и один оценщик (глава 1.2)

### Отказ, а не молчание

Воркер пишет `testsub/placement/c1`. Хранилище отвечает `403 {kind: forbidden, error: "testsubworker may not write testsub/placement/c1"}` — до того, как запись дошла до журнала. Не «проигнорировано», не «записано с предупреждением»: отказ, из которого видно, кто и куда. Чтение без права — тот же `403`. Перечисление — иначе: имена строк под префиксом получает любая роль, вместе с версиями, но без значений (ADR-0021): имя строки не секрет, и воркеру, чтобы ждать свободного места, не нужно читать чужие строки — достаточно видеть, что они есть.

Отрицание сильнее разрешения, где бы оно ни стояло: `["domain/*", "!domain/signer*"]` — всё под `domain/`, кроме подписанта. Образец — точный ключ или префикс со звёздочкой в конце; звёздочка в середине — буквальный знак: `a*b` совпадает только с ключом `a*b`. Роль, которой нет в файле, не может ничего; пустой список у известной роли запрещает всё. Три вещи не может никто, включая `admin`: удалить строку эпохи (урок P/03, глава 3.2 — номер нельзя выдать второй раз), удалить под `domain/` не ролью домена, записать или удалить `platform/epoch_floor` иначе как операцией восстановления (глава 1.3).

### Личность — это сокет

В кластере у хранилища по сокету на роль: `/run/configstore/testsubworker.sock`, режим `0660`, группа роли; `admin.sock` — `0600`, только root. Юнит воркера состоит в группе роли и ходит в хранилище через свой сокет: кто открыл сокет — тот и звонит, и заголовок с другой ролью в запросе — отказ. Группа платформенной роли — `w2c-<роль>` (`w2c-console`, `w2c-testsubcontroller`, ADR-0030); группа воркера подсистемы — `<развёртывание>-<роль>` (`vms-camworker`, ADR-0023). Сам демон хранилища в группах подсистем не состоит: ролевые сокеты лежат плоско в одном каталоге, группу каждого задаёт юнит его сокета (`SocketGroup=`, P/02.4 Н1.1; ADR-0030).

На одной коробке хранилище тоже открывает сокет на роль, а у хранилища файлов или памяти внутри процесса ту же работу делает имя писателя: хранилище файлов или памяти открывается «как `testsubcontroller` с таким-то списком», и оценщик — тот же. Поэтому глава 1.1 требовала прогонять приёмку и через дверь, и через API: права у них одни.

### Отказы и пределы

Неизвестная обычная роль не получает разрешений на строки. У admin есть особое разрешение,
но запреты `never` действуют и для него. Перечисление имён доступно без read, однако
подмена личности и недоверенная пересылка остаются отказами. Полные формы ответов — Н2 главы 1.2,
действия вызывающего при отказе — Н4 главы 1.2.

## Демон хранилища (глава 1.3)

### Хранилище без оркестратора

На каждом сервере — демон хранилища, голос группы raft. Устойчивый состав группы — один, три или пять; два и четыре допускаются лишь как переходный состав при последовательной пересборке, и демон отказывает вступлению, которое делает группу чётной (без `-force` — он нужен для переходной чётности при пересборке) или больше объявленной (всегда: размер меняют флагом `-group-size` на всех демонах, не вступлением) (растить 1 → 3 через 2 можно только так). Процессы ходят только к демону своего сервера, через сокет своей роли; между серверами ходят демоны — по mTLS с сертификатами центра кластера. Нет лидера пять секунд — дверь отвечает `503 unavailable`, и воркеры живут на последнем назначении по аренде (урок P/03). Потеря большинства требует оператора: сначала отсечь всю прежнюю группу и сохранить исходные данные, затем выполнить один `recover` на остановленном демоне. Новый пол должен быть выше достоверной границы всех ранее выданных эпох. Если потерянный хвост не позволяет установить эту границу, урок не обещает безопасное восстановление; `force` это условие не снимает.

Дверь без голоса — демон на сервере без права голоса: тот же файл прав, те же сокеты, пересылает к лидеру; живёт на серверах, где есть процессы, но нет места в группе (четвёртый сервер при группе из трёх).

## Словарь курса

В уроках встречаются короткие слова курса. Вот что они значат на стандартном языке:

| В уроках | Стандартный термин |
|---|---|
| строка (хранилища) | row, запись хранилища |
| дверь | HTTP API процесса (здесь — хранилища на unix-сокете) |
| коробка | один сервер без группы |
| группа | кластер серверов с реплицированным журналом |
| страж | guard, fencing token |
| проход | семантика операции по шагам |
| вес / потолок | размер строки / лимит размера |
| отказ | ошибка, ответ не-200 |
| идентификатор записи | ключ идемпотентности `id` |
| образец | точный ключ или префикс со звёздочкой, с которым сравнивается ключ операции (глава 1.2) |
| отрицание | запрет с `!`, сильнее разрешения того же действия |
| оценщик | один механизм ответа «разрешено ли действие над ключом» |
