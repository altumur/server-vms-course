## `cases.tsv`

UTF-8, LF, поля через TAB; строки с `#` и пустые пропускаются, первая непропущенная — заголовок. Ячейка читается байт в
байт, ничего не раскрывается. Четыре поля: `case`, `input` и `expect` — текст JSON, `note` — зачем строка.

**Вход** — один набор меток; все серверы и воркеры входа ему подходят (метки, `requires` и ресурс — не предмет вектора;
`servers: distinct` — только полями `place_by` набора и `placeless` сервера ниже):
- `default` — `placement.capacity.default` манифеста (целое ≥ 0);
- `workers` — подходящие живые воркеры: `capacity` (целое или `null` — ёмкость не названа) и `free` (свободно);
- `waiting` — точная неотрицательная целая сумма весов ждущих, `groups` — групп, которым нигде нет места;
- `servers` — `{<сервер>: {want, live, room, base?, numbers?, door?, placeless?, drained?, quiet?}}`: `want` — строка заказа, `live` — живые(s)
  по пульсам (с базовым и жертвой), `room` — `room.<sub>`, `base` — базовый `-1` жив (нет поля — `true`), `drained` —
  дренаж или вывод, `quiet` — «failed to raise» в окне `RAISE_QUIET`. `numbers` — номера живых процессов роли по пульсам
  (базовый `1`, если жив; их `live` штук); нет поля — подряд: `1…live` при `base: true`, иначе `2…live + 1`. `in_flight(s)` =
  `|{2…want} ∖ numbers|` — номерами, не счётом; при номерах подряд —
  `max(0, (want − 1) − ordered)`. `door` — список `live.<sub>` строки двери: номера n ≥ 2 живых замков; нет поля —
  номера n ≥ 2 из `numbers` (дверь совпадает с пульсами), `null` — у двери нет `live.<sub>`: сервер не кандидат; `free(s)` = `room −
  |{2…want} ∖ door|`, один раз за проход, минус каждая доля;
- `place_by` набора и `placeless` сервера — только при `servers: distinct` и месте из пульса: `place_by` — имя поля места,
  `placeless` — число подходящих живых процессов без места на этом сервере (нет поля — 0; их свободное в `workers` не
  входит: там только хранители); кандидат — сервер с `placeless` 0 и без пробы в пути (`in_flight(s)` 0); прирост набора — не
  больше одного пробного процесса за проход; остаток — `withheld` с `why: "no free <place_by>"`.
  Оговорка: ёмкость процесса без места в `per` входит (N3 `per` — по всем подходящим живым), а в `workers` вектора её нет;
  строки с `placeless` берут её не меньше `per` хранителей (равной `default`). Случай, где ёмкость воркера без места меньше
  ёмкостей хранителей и потому задаёт `per`, вектор не выражает — чтением.

**Выход** — `{per, processes, in_flight, need, orders, withheld}`: `in_flight` — Σ `in_flight(s)`, `need` — нужно,
`orders` — новый `want` серверов, которым досталась доля, `withheld` — остаток без кандидата, число процессов (как ряд
`workers_withheld{labels}` P/06.5). `in_flight` — сколько в пути набор взял: `min(Σ in_flight, processes)`. Ёмкость
воркера без названной — `default`; `per` — наименьшая положительная по всем `workers`, названная или `default`; названный 0
не заменяется на `default`. Без вычислимого `per` — элемент тех же полей: `{per: null, processes: 0, in_flight: 0,
need: 0, orders: {}, withheld: 0, why: "no positive capacity estimate"}` (`why` — слова `short.withheld` отчёта, N1.2).

**Несколько наборов** — вход с `sets: [{labels, waiting, groups}]` вместо `waiting` и `groups`; все серверы и воркеры
входа подходят каждому набору. Набор меток — множество: каноническая запись — уникальные метки по возрастанию через
запятую, повтор схлопывается. Наборы идут в порядке байт UTF-8 канонической записи (пустой — первым); набор берёт свободное, `in_flight` и `room` только до своей потребности, остаток — следующему (N3 «set order»). Выход — `{sets: {<каноническая запись>: {per, processes, in_flight, need,
withheld}}, orders, withheld}`: `in_flight` набора — сколько ёмкости в пути он взял, `orders` — итоговый `want` серверов,
`withheld` — сумма по наборам.

**Сравнение** — JSON по значению; `orders` — объект, порядок ключей не важен.

## Вход не по форме

Исполнитель вектора отвечает кодом 2 (ячейка `expect` — `@exit 2`) ровно на вход из перечня: не JSON-объект; поле не того
типа (числа — целые ≥ 0, `capacity` — целое ≥ 0 или `null`, `base`, `drained`, `quiet` — булевы, метки — строки по [азбуке
меток](../../../../common/ru/contracts/labels.md)); `want` вне 1…99; `live` вне 0…99; `door` — не список или `null`, в нём номер вне 2…99 или повтор;
имя сервера не по грамматике сервера (P/02.4 N1.2); два набора с одной канонической записью; `placeless` у сервера без `place_by` набора;
`numbers` — не список целых 1…99, с повтором или не `live` штук. Вход по форме с недопустимой метрикой — не отказ: ёмкость пульса не числом (P/04 N1.3) — воркер не
принимает единиц и в `workers` не входит; нечитаемая строка двери — `door: null`. Для полей кроме агрегата waiting/sets[].waiting целое — по точному десятичному значению записи, как `x-integer` (LAYERS §3): `1.0`, `1e0` — 1; `1.5`, булево, строка, число вне binary64 — не целое; номер `n` в имени воркера — лексема строки, без ведущего нуля. Остальное — вне вектора.

## Кто исполняет

Кто исполняет — контроллер (`04-controller`: нехватка, `in_flight`, `free(s)`, кандидаты и доли, P/04 N3 «shortage(), order()») — все строки. Только читают готовое: ресурс (`05-resource`, пишет `room`/`live` строки двери, P/05 N1.4 `door_row`), скрипт сервера (`02-installer`, P/02.4 N1.5) и консоль (`06-console`, ряды `workers_wanted`/`workers_withheld`, P/06.5 N3 «/metrics — текст») (строку исполняет роль, чья норма вызывает её функцию).

## Чего вектор не покрывает

Снятие по сроку,
номер выше want и сокращение — по времени, шаги приёмки.

Агрегат waiting/sets[].waiting сохраняет записи целого по значению, но не имеет потолка common.uint53 и не преобразуется через binary64/int64. Суммы и округление деления вверх точны; отдельные вес/ёмкость и области всех прочих входов прежние.
