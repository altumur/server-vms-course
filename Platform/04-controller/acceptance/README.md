## Стенд

Сценарии на стенде из процессов `testsub` реализации: хранилище, консоль `testsub`, контроллер `testsub` и воркеры `testsub`
(учебный воркер счётчиков), которыми управляет раннер; сц. 11, 14–17 — контроллер и воркеры `testsub2` (разбор ревью стадии B 3–5, № 17). Каталог стенда — две
спеки, `testsub` и `testsub2`, в порядке раздела «Стенд» общего README приёмки (сверка python и go М10/3–5, п. 24): воркер
одной спеки при захвате и чистке не трогает строк другой. Учебный воркер `testsub` докладывает запущенный счётчик элементом
`status` с `phase: running` (P/03.4 Н1.1 `phase`) и одним словом подсистемы `n` — значением счётчика (P/03.4 Н1.1 `status`;
второй пилот, Н-7). Наблюдение — строки через дверь хранилища P/01.1, единицы и размещение через дверь консоли (`/where`,
`/unplaceable`, `/servers`, `/metrics`), отчёт прохода `<sub>/controller/pass` — дверью объектов ресурса (сц. 12, 15);
пульс (объект) здесь не читается. Ресурс P/05 нужен сц. 12, 14–17 (ресурс на сервере контроллера; сц. 15 — два ресурса; разбор ревью стадии B 3–5, № 17):
реализация без ресурса их не проходит.

## Границы сценариев

Между сценариями раннер останавливает все процессы, которые запустил, сбрасывает хранилище (строки и объекты) и
переменные `$имя`: каждый сценарий начинается с пустого хранилища, слота `w-1` нет, консоль перезапущена.

## Точная подготовка и завершение

Каждый сценарий получает новое изолированное хранилище, новую консоль, пустую память id хранилища
и пустые заявки POST, а также очищенные объекты пульсов/контроллера/соперников и переменные раннера.
Перед началом установлен каталог `testsub` и `testsub2` из общих testdata и служебные метки спек.
Нет чужих контроллеров, ресурсов, запасных процессов и таймеров запуска. Дверь консоли открыта с петли;
роль чтения хранилища имеет доступ к testsub/ и testsub2/. Подготовка использует отдельные административные права.

Все воркеры сценария имеют постоянную BOX_ID стенда и server = srv-a, кроме `@start worker … on <сервер>` (словарь общего README приёмки; разбор ревью стадии B 3–5, № 33);
каждая копия получает новый instance. Имя передаётся подстановкой `{name}` директивы (общий README приёмки, «Стенд»; разбор ревью стадии B 3–5, № 33).
Убывающий бюджет памяти не провоцируется: выбранные CAPACITY/WORKER_MEMORY_MB должны удовлетворять P/03.4 (бюджет).
Обычная конфигурация testsub использует safe-умолчания; параметры подмены и сроков не ускоряются ради теста.

@start подтверждает запуск процесса, готовность слота проверяют следующие @until.
@sigterm и @sigkill посылают сигнал нужному процессу и **ждут подтверждённого завершения**;
таймаут/неверный процесс — отказ раннера, а не ok. После сценария раннер завершает и дожидается всех созданных
процессов, лишь затем удаляет состояние. Параллельный сценарий использует другие порты и каталоги.

## Точное сравнение и границы

Заголовок TSV и комментарии пропускаются. Номера шагов непрерывны внутри сценария.
@until повторяет только вложенный запрос и сравнение до предела; исчерпанный предел — FAIL.
Директива ASSERT сравнивает связанные значения: $имя связывается при первом появлении, далее сравнивается.
Новые связи переменных каждой попытки сравнения сначала временные: они становятся общими только
после совпадения кода и всего expect. Повтор переменной внутри expect сравнивается с её временным
значением. Неуспех любого поля, типа, элемента массива или кода отбрасывает все новые связи этой
попытки; уже общие связи не меняются. Порядок обхода полей результата не меняет.
Это относится и к обычному HTTP-шагу, и к каждой попытке @until, и к ASSERT.
@any требует наличия поля; @absent — отсутствия; ~текст — строкового вхождения.
JSON-типы точны, true не равно 1; объекты сравниваются по указанным полям рекурсивно,
массивы — по числу, порядку и значениям элементов. Ожидание одного кода не требует пустого тела.
Полный HTTP-ответ дополнительно соответствует контракту хранилища (P/01.1) или единиц ([P/06](../../06-console/spec/06-console.api.openapi.yaml), глава 6.1).

Сценарии наблюдают строки и HTTP-ответы, не содержимое объектов пульса и не фактические внешние записи
единицы. Смена эпохи/назначения сама по себе не доказывает, что старый процесс прекратил работу.
Остальные свидетельства — Н5 норм урока («Свидетельства вне TSV»).

## Снимок вне TSV (из README приёмки М10/10)

Публикация шарда: max_bytes=0, меньше, равен и больше 64 МиБ; полный размер ровно L/+1; при отказе сохраняются прежний
объект и время. Сценарий 03 не доказывает эти границы. Вне TSV сверить весь список служебных семей и размер полного
snapshot-шарда по min(max_bytes при >0, 64 МиБ). max_bytes=0 не снимает потолок двери; отказ сохраняет прежний шард и его
время. `@until` снимка читает локальный ресурс; ошибка публикации не становится пустым снимком.

## Проверки чтением из приёмки М10/04

Двери консоли М10/04 перенесены в [приёмку P/06.6](../../06-console/acceptance/6/README.md); проверки контроллера из её
README — здесь. TSV на пустом пуле не доказывает свойства ниже. Для каждого указать место реализации, наблюдение
управляемого стенда или абстрактную модель на операциях P/01.1 (прогон 25).

- Два контроллера, разные единицы веса 1, один воркер capacity 1: второе решение видит резерв
  первого; суммарная допущенная нагрузка не становится 2.
- Две единицы с одинаковым spread_by: второе решение не занимает тот же сервер, в том числе
  через другого воркера этого сервера.
- Два члена группы с разными home, два контроллера: один intent содержит всех и общую цель.
  Проверить остановку после active, после каждого снятия/placement и перед idle. Следующий
  держатель сначала завершает intent; до добавления группы сняты все её старые назначения.
- Поздний старый контроллер после смены turn получает 412 на добавление и снятие. При неизвестном
  исходе сначала подтверждается барьер turn; старая команда не может примениться после перечитки.
  При потере самого барьера изменения не продолжаются.
- Чтение intent → placement → intent при смене версии повторяется ([договор наблюдения](../../common/contracts/observation.md)
  «Чтение решения»). Idle не удаляется. Группа сверх потолка intent/назначения отказывается целиком до изменения размещений.
- При одинаковой истории версий слота сдвиги часов писателя -30/0/+300 не меняют судьбу.
  Первый взгляд начинает 45 с, затем запас до 90 с; разные истории судей не обязаны совпадать.
- Grows (ADR-0084): пустой пул и capacity.default=4 дают per=4; воркеры capacity=0 и default=4 также
  используют 4; нет положительных ёмкостей и default=0 — withheld «no positive capacity estimate»,
  без заказа и деления на ноль. Нехватка веса и групп остаётся видимой.

Операции над именами (R28-01/02): проверки P/04-09, 10, 11 выполняются отдельно от HTTP-шагов TSV — нужны чтение
реализации владельцем или управляемый пул. Все прочие фильтры размещения пропускают кандидатов, нужные ресурсы живы,
ёмкость достаточна. У каждого случая своё начальное состояние, порядок обхода карты меняется.

| Подготовка и действие | Ожидаемый исход |
|---|---|
| distinct, одно место, живые w-a/w-b, равные нагрузки 0 и ёмкости 1; разместить единицу веса 1 | Хранитель w-a по слотовому порядку P/03.2 Н1.4 |
| Повторить с w-2/w-10; с w-01/w-1; с w-2/w-a; с w-srv-a-10/w-srv-a-2 | Хранители соответственно w-2, w-01, w-2, w-srv-a-10. Последнее число составного имени не извлекается |
| Нагрузка w-b выше w-a, обе положительны; отдельно shared и одинаковая свободная ёмкость w-2/w-10 | distinct оставляет w-b: нагрузка имеет приоритет. При shared равную ёмкость разрешает сравнение по полному имени, первым w-10 |
| Слот отдаётся контроллером; отдельно until порван, gen читается | holder/until/gen/server сохранены при обоих вариантах записи |

Дополнительная проверка чтением R36-04: A под turn v1 посылает удаление по delete_after с CAS U; запрос задержан. B
получает v2 и размещает ту же версию U. У A guard v1 даёт 412 и сохраняет единицу. Проверить также конфликт версии
единицы, неподтверждённое чтение intent/placement, барьер после неответа и повтор без подстановки нового guard в старый
план. Операции в полёте не моделируются текущей HTTP-TSV.

Дополнительная проверка класса ошибок прогона 36 (Kimi): чтением проверить приоритет ветвей судьбы: после ранних ветвей
слот без назначенных и ведущихся единиц получает release; неизвестный gen сохраняет запрет записи. Для hung/unsure/wait
начало HUNG_MOVE_AFTER — первое наблюдение неизменной версии слота, не until или fate.since. Новый судья начинает с нуля.
Возврат домой разрешён только в объявленном проходе с HOME_BUDGET.
