## P2 — ранний HTTP-ответ по-прежнему теряется при ошибке незаконченной записи

`runner/m11stand.py:167–184`, `Proxy._pump_unix`: recv/send/shutdown находятся под одним общим `except (OSError, ValueError)`, после него `_finish_pair` закрывает обе стороны и теряет оба pending. Ошибка дальнейшей записи запроса не означает, что ответа уже нет или его можно отбросить.

Норма: общий README приёмки `@cut role` / `@mend role` — вне разреза посредник пересылает поток, не меняя личность и смысл запросов; HTTP/1.1 двери роли — договор `common/contracts/store-client.md`. Ранний отказ по размеру допустим до чтения тела (P/01.1 Н2.1/Н4); сам `harness.HttpDoor.request` специально пишет тело отдельным потоком с комментарием «дверь вправе ответить 413, не дочитав его».

Нативный контроль: клиент посылает POST с Content-Length 1048577; собственная Unix-дверь читает заголовки (в одном recv 4096 байт), отправляет полный HTTP 413 с JSON Fault и Content-Length, закрывает соединение, не дочитывая отказанное тело. Это обычное поведение раннего отказа. Реальный `harness.HttpDoor.request`:

- напрямую — **5/5**, получены статус 413 и все байты тела;
- через старый Proxy — **0/5**;

Ошибки транспорта у одного направления и полученный ответ другого нельзя свести к немедленному уничтожению всей пары. Нужна обработка завершения/ошибки направлений, сохраняющая ранний ответ и накопленные байты, с прежними пределами и cut/mend. Добавить контроль раннего отказа до окончания отправки тела; повторить неизменные исходную и новую пробы на двух снимках.
