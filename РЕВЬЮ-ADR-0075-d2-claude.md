## Существенные

### С-1. Порог «адрес — петля» не закрыт: имя в URL, разрешённое в петлю, подменяется своим `SERVER_NAME`

- **Место.** Доп. 2026-10-26 (2) п. 3: «Клиент двери своего кластера, чей адрес — петля (`127.0.0.0/8`, `::1`), соединяется с этим адресом, а имя сервера … берёт из `SERVER_NAME`».
- **Контрпример.** «Адрес» можно прочесть двояко: как запись хоста в URL или как адрес после разрешения имени.
  - Пусть на стенде или у оператора в `/etc/hosts` стоит `127.0.0.1 srv-b`, а клиент на `srv-a` зовёт `https://srv-b:8080`.
    - Если порог считается после разрешения, клиент подставит `srv-a` и примет дверь своей коробки, хотя звал `srv-b`. Отказа нет.
    - Если порог считается по записи URL, клиент проверит `srv-b`, у листа `srv-a`, и получит `wrong_name` — верный отказ.
  - `https://localhost:8080`: по разрешению — имя `SERVER_NAME`, проходит; по записи — имя `localhost`, `wrong_name`.
  - `[::ffff:127.0.0.1]`: стеки расходятся. `netip` в Go снимает отображение и считает адрес петлёй. `ipaddress` в Python до 3.13 петлёй его не считает.
  - Петля ли `127.1` и `[::1%lo0]`, тоже не сказано. По договору `peer` (шаг 1, `:54–55`) `127.1` — имя, а не IP.
  - При `CONSOLE_HOST=0.0.0.0` не сказано, куда соединяется клиент своей коробки. `https://0.0.0.0:8080` не входит в `127.0.0.0/8`, значит имя берётся из адреса.
  - Откуда агент берёт адрес своей консоли, не названо: в lifecycle P/09 строки `CONSOLE_*` нет, и правки Н1.5, `/events` Н1.10 идут «к своей консоли».
- **Источник.** Договор `peer` шаг 1, шаг 8; доп. (2) п. 3.
- **Последствие.**
  - При чтении «по разрешению» имя в URL перестаёт защищать: клиент, позвавший чужой сервер, молча принимает дверь своей коробки.
  - Порог по-разному понимают реализации на разных стеках (отображённый v6, `localhost`).
- **Предложение.**
  - Порог считать по записи хоста URL, до разрешения: IP-литерал по шагу 1 `peer` из `127.0.0.0/8` или ровно `::1`, без зоны и без отображения. Любое имя, в том числе `localhost`, проверяется как имя.
  - Добавить: привязка `0.0.0.0` → клиент своей коробки соединяется с `127.0.0.1`, привязка `::` → с `::1`.
  - Назвать источник адреса своей консоли у агента и у скрипта воркеров — `CONSOLE_HOST`/`CONSOLE_PORT` из `w2c.env` по правилу выше.
  - Строки вектора:

    | URL | Итог |
    |---|---|
    | `127.0.0.1` | `SERVER_NAME` |
    | `127.0.0.2` | `SERVER_NAME` |
    | `[::1]` | `SERVER_NAME` |
    | `localhost` | имя из URL |
    | `127.1` | имя из URL |
    | `[::ffff:127.0.0.1]` | имя из URL |
    | `[::1%25lo0]` | имя из URL |
    | `10.0.0.1` | имя из URL (шаг 1 → `ip_address`) |
    | `srv-b` при своём `srv-a` | `srv-b` |

### С-2. Подмена имени не связана с функцией `peer`: шаг 1 отвечает `ip_address` раньше шага 8

- **Место.** П. 3 и его хвост: «Нормы и векторы (п. 3 — строка клиента своего кластера в договоре сертификата роли и вектор «петля, имя по `SERVER_NAME`»)».
- **Контрпример.**
  - Переход 2 (консоль кластера держателя → консоль домена своей коробки по `view.url` = `DOMAIN_CONSOLE_URL`, P/06.7 Н1.4 `:121–123`) проверяет сервер функцией `peer`: договор пересылки `tls` `:87–89` — «с проверкой сервера peer … консоль домена своей коробки — своя CA».
  - Аргумент `host` функции — имя из адреса. При `DOMAIN_CONSOLE_URL=https://127.0.0.1:8444` шаг 1 отвечает `ip_address` раньше шага 8.
  - П. 3 говорит о «проверке SAN DNS», но не о том, что `host` функции `peer` — `SERVER_NAME`. Одна реализация подставит имя до вызова `peer` и пройдёт. Другая вызовет `peer` с адресом и получит `ip_address`.
  - Пакет `peer` (`{chain, fingerprints, role, host, now}`) получает `host` на входе. Вектор «петля, имя по `SERVER_NAME`» в этом пакете подмену не проверит: её нужно проверять на шаге до `peer`.
  - Договор `peer` в таблице «Кто / Кому» говорит о клиентах другого кластера. Переход 2 и пересылка подписанту своей коробки (P/06.7 Н1.8 `:187`) в ней не названы, хотя пользуются `peer`.
  - «Своего кластера» шире, чем нужно. Подмена верна, только когда дверь на своей коробке и её лист выпущен на `SERVER_NAME` того же `w2c.env`. Дверь своего кластера на другом сервере, до которой дошли через туннель на петле, даст `wrong_name`. Отказ закрытый и верный, но в норме его нет. Ещё нужно условие: на стенде процессы одной коробки получают один `SERVER_NAME`.
- **Источник.** Договор `peer` шаги 1 и 8; договор пересылки `tls`; P/06.7 Н1.4, Н1.8.
- **Последствие.** Переход 2 и пересылка подписанту на петлевом адресе дают у двух реализаций разный итог (`ip_address` или `ok`). Вектор из хвоста п. 3 этого не ловит.
- **Предложение.**
  - В договоре `peer` строку `client` (или новую строку таблицы «клиент своей коробки») сформулировать так: «адрес по порогу С-1 — `host` функции `peer` = `SERVER_NAME`, соединение — к адресу». Ту же фразу дать ссылкой в договоре пересылки `tls` для перехода 2 и пересылки подписанту.
  - Вектор вынести в отдельную форму `{url, SERVER_NAME}` → `{connect, host}`, строки — из С-1.
  - Слова «двери своего кластера» заменить на «двери своей коробки» и добавить: «туннель к другой коробке — `wrong_name`».

### С-3. Браузер к консоли с комплектом при умолчании `127.0.0.1:8080` не доходит по `https://<SERVER_NAME>`

- **Место.** П. 3: «браузер к консоли с комплектом — `https://<SERVER_NAME>` с доверенным центром кластера»; «`CONSOLE_ORIGINS` при комплекте — со схемой `https`».
- **Контрпример.**
  - Умолчание консоли — `127.0.0.1:8080` (P/06 lifecycle `:42`, P/02.4 `:62`).
  - Установщик предупреждает, если `SERVER_NAME` не разрешается в адрес привязки дверей процессов (P/02.4 `install.warn` `:313`). Значит, в штатной установке `srv-a` разрешается не в петлю.
  - Браузер на `https://srv-a:8080` придёт на внешний адрес, где консоль не слушает. Через туннель `https://localhost:8080` получит несовпадение имени (лист — только `SAN DNS srv-a`).
  - Раньше путь «туннель + `http://127.0.0.1:8080`» работал. Теперь в норме рабочего пути браузера при умолчании нет.
  - `https://<SERVER_NAME>` без порта: при сравнении `CONSOLE_ORIGINS` байт в байт (договор файла окружения `:71`) `https://srv-a` ≠ `https://srv-a:8080`.
  - Консоль домена — класс `role`: без листа клиента 401 `no_role`. Браузеру она не дверь, а «к консоли» в п. 3 читается как «к обеим».
  - Двери процессов подсистем с комплектом слушают адреса `SERVER_NAME`, а «петля + https нет» (P/03.4 Н1.7 `door_address` `:200–205`). У консоли теперь правило обратное. Причина разницы не названа.
- **Источник.** P/02.4 `install.warn`; P/03.4 Н1.7 `door_address`; договор файла окружения `CONSOLE_ORIGINS`; класс `role`.
- **Последствие.**
  - Оператор при умолчании либо не открывает консоль, либо принимает предупреждение об имени.
  - V/09.2 (строки площадки `CONSOLE_ORIGINS`) получает источник без порта, и страница не доходит до дверей подсистем (CORS).
- **Предложение.**
  - В P/06 lifecycle и V/09.2 записать путь оператора:
    1. туннель на `127.0.0.1:<CONSOLE_PORT>`;
    2. на машине оператора `SERVER_NAME` → `127.0.0.1`;
    3. страница — `https://<SERVER_NAME>:<CONSOLE_PORT>`, этот же источник — в `CONSOLE_ORIGINS`.
  - В п. 3 «браузер к консоли» заменить на «к консоли кластера».
  - **Вопрос «Архитектору»:** другой путь — консоль с комплектом слушает по правилу `door_address` `kit` (адреса `SERVER_NAME`) и не держит TLS на петле. Тогда браузер и клиенты ходят по имени, подмена п. 3 консоли не нужна, а правило одно у всех дверей с комплектом. Но консоль людей выходит из петли по умолчанию. Это решение владельца, поэтому вопросом. Рекомендую оставить петлю и записать путь оператора выше.

## Мелкие

### М-1. «Только по явному адресу» при умолчании `0.0.0.0` у подписанта и ретранслятора

- **Место.** П. 1: «без комплекта МОГУТ слушать вне петли только по явному адресу».
- **Суть.**
  - У процесса `domain` умолчание `SIGNER_HOST` — `0.0.0.0` (P/08 lifecycle `:28`). У ретранслятора умолчание `RELAY_HOST` — тоже `0.0.0.0` (P/09 lifecycle `:41`).
  - Не сказано, явный ли это адрес, когда переменной в окружении нет. Норма допускает и слушать, и отказать («отказ старта тоже соответствует», `:292`), так что соответствие не страдает. Но установка по умолчанию без комплекта у двух реализаций ведёт себя по-разному.
  - Доп. 2026-10-12 (2) `:130` писал «отказ старта без `-tls` приходит к каждому с его окном». П. 1 делает исключение постоянным, а эту фразу историей не называет.
- **Предложение.**
  - Добавить: «явный — задан в окружении процесса; умолчание без комплекта — по петле» (или наоборот, по выбору «Архитектора»).
  - Добавить: «срок «с его окном» доп. (2) — история».

### М-2. «Центр, роль и отзыв — без изменений»: для клиентов своей коробки, кроме скрипта воркеров, они нигде не записаны

- **Место.** П. 3: «центр, роль и отзыв — без изменений».
- **Суть.**
  - Набор проверки сервера своего кластера записан только у скрипта воркеров: Н1.6 `roles` `:271–272` — «центр ca.pem, роль console в SAN, имя, отзыв».
  - У агента к своей консоли, у консоли кластера к консоли домена и подписанту своей коробки, у консоли домена к `SIGNER_URL` нет строки «ожидаемая роль сервера» (`console`, `domainconsole`, `domain`).
  - Не сказано, что отзыв на этой стороне — `revoked | crl.pem`. Строка `revoke` договора `peer` говорит обратное: «отзыв … чужого кластера звонящему не виден».
  - Сравнивать «без изменений» не с чем.
- **Предложение.** Строка клиента своей коробки — таблицей:

  | Клиент | Сервер | Роль сервера |
  |---|---|---|
  | агент, скрипт воркеров | консоль кластера | `console` |
  | консоль кластера | консоль домена | `domainconsole` |
  | консоль кластера, консоль домена | подписант | `domain` |

  Общая колонка для всех строк: центр — `ca.pem`, `ca.next.pem`; отзыв — `revoked | crl.pem` по договору сертификата роли `revoke`; имя — по С-1 и С-2.

### М-3. П. 4: `kit_absent` — термин класса `mixed`; консоль домена без комплекта

- **Место.** П. 4: «без комплекта (`kit_absent`)»; «умолчание `0.0.0.0:8444` — только с комплектом».
- **Суть.**
  - `kit_absent` записан внутри класса `mixed` (договор сертификата роли `:211–213`), а Н1.6 `process` относится ко всем дверям процессов.
  - Без пояснения не ясно, относится ли «частичный комплект — код 2» к консоли, подписанту, ретранслятору и ресурсу.
  - Для консоли домена без комплекта умолчание `0.0.0.0` даёт код 2. Чтобы она стартовала, нужно явно задать `127.0.0.1`. Тогда переход 2 от консолей других серверов кластера держателя до неё не дойдёт, и это последствие не названо.
- **Предложение.**
  - `kit_absent` вынести в раздел «Комплект кластера…» договора сертификата роли как общий для дверей процессов, а у `mixed` оставить ссылку.
  - В пометке lifecycle P/10 дописать: «без комплекта — только `127.0.0.1`, переход 2 — только с этой коробки».

### М-4. HTTPS-адреса дверей своего кластера с IP-литералом

- **Место.** П. 3: «не из адреса соединения» — подмена только на петле. Вне петли имя берётся из адреса.
- **Суть.**
  - `RESOURCE_URL` оператор задаёт свободно (P/05 lifecycle `:37`). Векторы `common/vectors/object-client/address.tsv` (строки `cluster-bare`, `cluster-resource-overrides` и др.) держат `https://10.0.0.2:8446`.
  - По п. 3 клиент своего кластера к такому адресу проверяет имя `10.0.0.2`. У листа только `SAN DNS <сервер>`, так что итог — `wrong_name` или `ip_address`.
  - Двери подсистем такой адрес исключают: они публикуют `https://SERVER_NAME:<порт>` (P/03.4 Н1.7 `kit`). У ресурса правила нет.
- **Предложение.**
  - `RESOURCE_URL` на `https://` — хост только имя сервера. IP-литерал — код 2 при старте ресурса с `door.mode` `mtls`/`tls`.
  - В векторах `object-client` адреса `https://` записать именем сервера.
