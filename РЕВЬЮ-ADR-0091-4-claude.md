**Два блокера:**

**Одна существенная:** состояние единицы, удалённой дверью, по правилу действия остаётся действующим, и уборка его никогда не снимает (Ч-3).

## Блокеры

**Ч-1 (блокер).** У надгробия строки единицы нет `written`: правило «только событием позже надгробия» не исполнимо.
- ADR:61–63: «над надгробием библиотека пишет только для события позже надгробия (`written`) — с CAS его версии и теми же `fixed` (P/06.1:182): удалённое оператором повтор прежнего события не возрождает».
- Нормы:
  - P/06.1:92–95: строка единицы — `id`, `revision`, `deleted: "true"` (только у надгробия), поля манифеста;
  - P/06.1:591: удаление дверью — «записать {…строка, deleted: "true"} с cas прочитанной версии; revision не меняется»;
  - P/06.1:33: «надгробие `.gone/<ключ>` — `written` (P/05 Н1.1 «Надгробия»). **У строки единицы**, счётчика `next_id` и заявки `idem` **полей времени-строки нет**».
- `written` — поле надгробия тела у ресурса (P/05:114, `.gone/<ключ>` `{written, peers, acked}`), а не строки единицы.
- Контрпример:
  - Оператор удалил `rec/recordings/auto-7` дверью. Надгробие — копия строки с `deleted: "true"`, времени удаления в нём нет.
  - После переезда воркера `auto` переигрывается событие `t` моложе `valid_for`. Библиотеке не с чем сравнить `t`.
  - Реализация А не пишет над надгробием никогда: новое событие запись не заводит, против ADR:62–63. Реализация Б берёт `made.at` надгробия: событие между последним продлением и удалением возрождает запись. Реализация В заводит своё поле времени. Поведение расходится на допустимом входе.
- Последствие: защита «удалённое оператором не возрождается» не задана, приёмка Confirmation («повтор… над надгробием — без нового эффекта», ADR:160–161) не проверяет одно поведение.
- Предложение — назвать одно:
  - дверь пишет в надгробие время удаления по своим часам — новое поле платформы (P/06.1 `platform_fields`, «Время» :33). Сравнение с временем события — в том же допуске 60 с, что `keep` (ADR:48–49). Рекомендую: это прямо та семантика, что названа в ADR;
  - либо сравнение с `made.at` надгробия (оно копируется удалением, P/06.1:591), без нового поля. Тогда в ADR записать, что событие до удаления, но после последнего продления, запись возрождает.

**Ч-2 (блокер; вопрос «Архитектору»).** Физическое удаление строк заказа противоречит ADR-0067 доп. 2026-10-10.
- ADR:59–60: «строку с `made` контроллер физически не удаляет (`delete_after`, `ends`) раньше `made.keep`».
- ADR:103–104: «Срок удаления законченной — существующий `delete_after` по часам контроллера; у строки с `made` — не раньше `made.keep`».
- ADR:73–75 (п. 2, на него опирается п. 1): `ends` — удалить строку «физически, без надгробия… (как `delete_after`)».
- Нормы:
  - P/02.1:262: `placement.unplaced.delete_after` — «только с named id, без fixed-полей кроме id, `about` — только по id (ADR-0067)»; правила загрузчика 46–47 (P/02.1:805–806);
  - ADR-0067 доп. 2026-10-10: «Контроллер… делает `delete` — строки нет, имя свободно, и бакеты, метки и гранты старой единицы читались бы как история новой. Контроллер строку единицы не пишет никогда (`DeleteOnly`), поэтому надгробие ему не дать».
- Контрпример 1 — `detjob`:
  - `cam` и `rec` — `fixed` (`detjob.subsystem.yaml:27`, `:34`), `about: {sub: cam, field: cam}` (`:21`);
  - манифест с `placement.unplaced.delete_after` — `refused:value` по правилам 46 и 47;
  - без ключа заказанные задачи (`auto-…` на каждое событие, `rec-…` на каждый приход) не удаляются никогда — таблица растёт без предела, `made.keep` охранять нечего.
- Контрпример 2 — `rec`:
  - `auto-7` (`cam: 7`, `fixed`, `rec.subsystem.yaml:60`, `:66`) удалена по `ends` после `keep` физически;
  - оператор создаёт `POST rec/recordings {name: auto-7, cam: 8}`: надгробия нет, проверке `fixed` (P/06.1:182) сравнивать не с чем — 201;
  - бакеты и гранты `rec/auto-7` камеры 7 читаются как история записи камеры 8 — ровно то, что запрещает ADR-0067;
  - следующее событие камеры 7 даёт тот же id `auto-7` — строка без своего `made`, «занята» (ADR:51): камеру 7 автоматика больше не пишет.
  - То же у `det` (`cam` — `fixed`, `about` по `cam`, `det.subsystem.yaml:12`, `:18`) с `auto-<cam>-<kind>`.
- Последствие: принятый ADR и норма загрузчика против нового текста; Т-правка упрётся в отказ загрузки `detjob`.
- Предложение — выбор «Архитектора», рекомендую первый:
  - дверь отвергает создание строки с id `<заказчик>-…` объявленного заказчика: под префиксом живут только строки своего `made`. Библиотека выводит `fixed`-поля строки заказа из id детерминированно: id несёт камеру. Тогда возвращённое имя — тот же предмет. Физическое удаление по `delete_after`/`ends` — только строк с `made`; ручные строки удаляет оператор, как сейчас. Поправка ADR-0067 и правил 46–47 называется в ADR-0091;
  - либо контроллер удаляет надгробием (право записи `deleted: "true"` с `cas`). Тогда защиту повтора несёт правило над надгробием (Ч-1), а `keep` не нужен, но надгробия задач копятся без предела.

## Существенные

**Ч-3 (существенная).** Состояние единицы, удалённой дверью, остаётся действующим: уборка его не снимет.
- ADR:87–88: «**действует** состояние, чей `born` = `born` строки и `revision` = `revision` строки».
- ADR:100–102: «**уборка** осиротевшего состояния (строки нет или её `born` другой)… действующее состояние уборка не трогает».
- Нормы:
  - P/06.1:591: удаление дверью — `{…строка, deleted: "true"}`, revision не меняется: `born` и `revision` надгробия те же, что у живой строки;
  - P/06.1:95: надгробие — та же строка с `deleted`.
- Контрпример:
  - Ручная задача `detjob/7-lpr-3` закончена, состояние `result` = done с `born` B, `revision` 4.
  - Оператор удаляет её дверью: надгробие с `born` B, `revision` 4.
  - Уборка: строка есть (надгробие), `born` тот же. Состояние по правилу ADR:87 действующее — «уборка не трогает».
  - Состояние живёт, пока имя не займут снова. У задач с уникальными именами это никогда. Реализация, читающая надгробие как «строки нет», уберёт. Поведение расходится.
- Последствие: утечка строк `<sub>/state/*` на каждую удалённую дверью единицу с состоянием, и расхождение реализаций.
- Предложение: «строки нет, она надгробие или её `born` другой»; действует только состояние живой строки; `guard.index` при надгробии — его версия.

## Мелкие

1. **Уборка без исполнителя.** Третья редакция называла контроллер. ADR:98–102 говорит «снимает уборка», «одной операцией» — без исполнителя и без прохода. Назвать контроллер (шаг прохода P/04), чтение `<sub>/state/*` и право `delete:<s>/state/*` в P/02.5:88 при объявленном `unit.state`.
2. **Тело по `mask_from` снимает уборка тел.** Окно уборки держит только отмеченные дайджесты со ссылками: «doomed = отмеченные без ссылок» (P/06.1:618). Ссылка — поле `blob` строки, а `mask_from` — строка (ADR:66). После перерисовки маски и окна уборки `det` ждущая или переехавшая задача — `failed` (ADR:67). Назвать это исходом в уроке 05 или засчитать `mask_from` ссылкой в уборке тел. Право чтения тела — объекта `det/blobs/…` — записать образцом `worker.reads` явно.
3. **Повтор того же события при продлении.** `max` прежнего и нового (ADR:57) на повторе даёт те же `until` и `made.at`. Если библиотека всё равно пишет, `revision` + 1. Это перезапуск единицы (ADR:81) и снятие действия состояния (ADR:87). Записать: «значения не меняются — записи нет».
4. **Снимок с вложенным `state`.** Форма шарда P/04:503 — `.<имя>[].<имя>`, плоское поле `snapshot` манифеста. Вложенный `state.<имя>` (ADR:90–92) меняет форму шарда. Не сказано, что с единицей, чья строка состояния не читается своим типом: вне шарда (`snapshot_rows_garbled`, P/04:157) или без `state`.

Прежние мелкие (Г-7, Г-8, Г-9, С-4, С-5) разбор отложил до Т-правки — не повторяю.
