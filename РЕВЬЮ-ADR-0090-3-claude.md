## Доп. (3): имя «vms»

**В-1. Запрет противоречит нормам платформы, которые сам ADR отдаёт P/02.4.**

  именем «vms» в спецификации нет».

  `:93-94` — «<пользователь подсистемы> — <dep>-<sub>», «<dep>-<роль> (воркеры)». P/01.2:37 — «subsystem role:

## Доп. (3): снятие `vmsjobs`

Права `vmsjobs`: роль `console` с грантом консоли на `vms`, `rec`, `det`, `detjob`, `survey` (`vmsjobs.container:11-17`).
Это единственная роль, которой можно писать строки единиц:
- воркер — «собственные таблицы, не `unit.rows`» (P/02.1:342);
- контроллер — только размещение и удаление по `delete_after` (P/02.5:88).

| № | Обязанность (источник) | Механизм платформы | Покрыто | Кому |
|---|---|---|---|---|
| J1 | просьба `record` → строка `rec/recordings/<cam>-auto {until}`, продление; метка `ended_by: jobs` (М10B/25:436-512) | `elsewhere` «закрывает её владелец» (`request-mark.md:64`), а владельца-процесса нет; `ended_by: reaper \| holder` (`:85`) | нет | платформа (запрос А) + `auto` |
| J2 | прошёл `until` → удалить строку `rec`/`det` (`rec.subsystem.yaml:76-80`, `det.subsystem.yaml:37-41`) | `retire_when: {field, in}` (P/04:141) — только принадлежность списку; `worker.deletes` (P/04:143) — только своей единицы | частично | `rec`, `det` + запрос Б |
| J3 | `detect`/`scan` → `det/units/<cam>-<kind>-auto`, `detjob/jobs` (`det.subsystem.yaml:64-81`) | как J1 | нет | А + `det`/`auto` |
| J4 | `status.phase` пульса → `state`, `ended` строки задачи (М10B/21:151-190) | `retire_when` читает только поле строки | нет | запрос В |
| J5 | удалить законченную задачу через N дней после `ended` | `unplaced.delete_after` — по часам контроллера и для любой неразмещённой (в том числе `queued` без GPU) | частично | `detjob` + В |
| J6 | фаза `fetching` → `rec/requests` (М10B/21:263-296) | `worker.requests` (P/02.1:344; P/03.6 Н1.5) | да | `detjob` |
| J7 | `closed` пульса `rec` → сканы `detjob` (М10B/22:42-101) | `rec` подаёт `det/requests` сам; дальше J3 | частично (через А) | `rec`, `det` |
| J8 | `hits` обхода → `rec/requests` (М10B/23:209-214) | `worker.requests` | да | `detedge` |
| J9 | снять отвеченные просьбы | жнец P/06.4 Н3 | да (уже не `vmsjobs`) | платформа |
| J10 | метрики `requests_expired`/`unknown` на `JOBS_PORT` | метрики жнеца консоли | частично | платформа (А) |
| J11 | в продукте: `FileLostSpans`, `SealKeeps`, `WatchGarbledKeeps` (`ОБРАТНАЯ-СВЯЗЬ-ИЗ-ПРОДУКТА.md`) | `worker.writes` своей таблицы | частично | `rec` |

### Существенные

**J-1. «Что уже покрывают `retire_when` … и просьбы с жнецом» (`:167`) переоценивает покрытие.**
- Полностью покрыты только J6, J8, J9, и те — через `worker.requests` (P/02.1:344), которого ADR не называет.
- `retire_when` закрывает чтение итога, а не его запись.
- Устойчивое `state` строки записать некому:
  - воркеру нельзя — P/02.1:342; с оператором было бы два писателя одной строки (ADR-0013);
  - контроллеру нельзя — P/02.5:88;
  - консоль проходов подсистем не крутит (ADR-0002);
  - пульс не годится: «факт нельзя хранить в канале, который сам этим фактом закрывается» (М10B/21:220).

**J-2. Нужны три запроса к платформе.** Предлагаю формулировки по форме доп. (1). Вопрос «Архитектору».
- **А. `<дата>-запрос-vms-просьба-строкой.md`.**
  - Блокирует урок: да (`07-auto`, `04-det`, `05-detjob`, `02-rec`).
  - Мешает: `request-mark.md:64` и `:124-126` («`elsewhere` … закрывает её владелец»), владельца в каноне нет (роли
    закрыты, P/02.5:36); у `performed` запрещён `ended_by` (P/06.4:174), а урок 25 пишет `ended_by: jobs`.
  - Рекомендация: декларация в `requests:` спеки-адресата, например `materialize: {action, rows, id: "<шаблон>",
    fields, extend: {max: [until]}}`. Жнец консоли исполняет `elsewhere`-действие записью строки единицы той же дверью,
    что `PUT`: `must_match`, `fixed`, `ref`, права `by`. Метка — `ended_by: console`.
  - Пример: `{sub: rec, action: record, cam: 7, minutes: 10}` → `rec/recordings/7-auto {until: now+600}`; повтор
    продлевает.
  - Обход: старый процесс с долгом.
- **Б. `…-запрос-vms-единица-со-сроком.md`.**
  - Блокирует урок: да (`02-rec`, `04-det`).
  - Мешает: `retire_when` знает только `{field, in}` (P/04:141).
  - Рекомендация: `placement.ends: {field: until, zero: never}` — контроллер не размещает просроченную единицу, снимает её
    и удаляет строку. Право `delete:<s>/<rows>/*` — как при `delete_after` (P/02.5:94).
- **В. `…-запрос-vms-итог-единицы.md`.**
  - Блокирует урок: да (`05-detjob`).
  - Мешает: P/02.1:342, P/02.5:88-89; `retire_when.field` — только поле строки (P/02.1:792).
  - Рекомендация на выбор:
    - (а) `retire_when: {table, field, in, revision: match}` — итог в таблице воркера (`worker.writes`) под слотом,
      действует, пока `revision` итога равна `revision` строки (повторный запуск оператором снимает итог);
    - (б) консоль переносит `status.phase` в поле строки по декларации `unit.mirror` — только от воркера размещения и
      только при `observed_revision == revision`.
  - Плюс давность итога для `delete_after` (J5).

**J-3. Получатели работы названы не все.**
- `:168`: «(`detjob`, `auto`, `rec`)».
- Пропущены `det` (`detect_on_request`, истечение — `det.subsystem.yaml:41`, `:108`) и `detedge` (`keep_what_fired`,
  М10B/23:212).
- Работа продукта J11 не названа.

**J-4. Канон уже противоречит пути `record`.**
- P/03.6:103-105: «В профиле дозаписи (`requests.outcome: fetched`) тело с `action` из `elsewhere` — тоже дозапись:
  держатель сверяет данные и сообщает fetched». ADR-0054:116 даёт `rec` `outcome: fetched`.
- Контрпример: после перевода `rec` регистратор возьмёт `{action: record}` как дозапись. А схема просьбы `rec`
  (`rec.subsystem.yaml:241-247`, `required: [unit, from, to]`, `additionalProperties: false`) тело `record` из
  `auto.subsystem.yaml:84-90` не примет.
- Запрос А должен вынести `record` в свою семью или поправить P/03.6.

**J-5. «До решения запросов процесс остаётся в старом коде» (`:168`) не даёт пути новым реализациям.**
- Старый `Source/` заморожен (ADR-0080 доп. 16) и исполнителем для `cammeta-*` быть не может.
- Уроки `07-auto` и `05-detjob` в `VMS/` нельзя нормировать ни через `vmsjobs` (доп. (3): процессов «vms» нет), ни ссылкой
  на механизм, которого нет.
- Продукт: `vms-jobs.service` живёт без строки долга «Сборке», хотя для прочих имён `:172` её требует.
- Связано с П-1: запросы должны быть до старта.

### Мелкие

**J-6. Описание обязанностей и тексты манифестов.**
- `:164-165`: «закрыть законченную работу по биению воркера — … отвеченная просьба, истёкшая запись». Отвеченные просьбы
  снимает жнец консоли (`vmsjobs.container:12`), а запись истекает по часам (`until`), не по биению.
- Манифесты называют исполнителем консоль: `detjob.subsystem.yaml:68` «The console's reaper moves `state`»,
  `det.subsystem.yaml:40` и `rec.subsystem.yaml:77` «The console's loop deletes the row». Это против ADR-0002 и
  М10B/21:151; опись должна это снять.

## Доп. (4): правила раскладки

### Существенные

**П-1. Запросы «до старта» требуют описи, которая делается «после старта».**
- Преамбула `:175-176`: «точное разнесение по шагам делает опись «Спецификации VMS» (первая задача после старта)».
- П. 1 `:179-180`: «Чего из них нет в `Platform/` …, — список запросов «Архитектора» к платформе до старта комплекта
  VMS».
- Доп. (3) `:168` о `vmsjobs`: «Решает опись «Спецификации VMS»».
- Обязанности J1–J7 — это ровно платформенные половины ГРАНИЦЫ `:125` («21 шаги 3-5, 7, 8; 25 шаг 3 и шаг 8; … курсор и
  окно-подтверждение в 22 и 23»).
- Контрпример: опись начинается после старта, поэтому запросы А–В до старта не появятся. `05-detjob` на старте нечем
  нормировать: строку задачи некому закрыть, и `retire_when` не сработает никогда.
- Нужно: список платформенных половин (п. 1) и запросы по `vmsjobs` — работой «Архитектора» до старта, по перечню
  ГРАНИЦЫ §2.8. Опись после старта — только для VMS-частей.

**П-2. П. 7: «срез прежнего манифеста» у старого кода не существует.**
- П. 7 `:195`: «старый код — замороженный свидетель со срезом прежнего манифеста (ADR-0080 доп. 16)».
