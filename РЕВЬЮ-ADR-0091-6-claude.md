## Блокер

**Е-1 (блокер).** Имя заказанной задачи `detjob` не может нести событие: второй скан той же камеры, записи и модели теряется как повтор.
- ADR:70: «id — из личности события и параметров».
- ADR:39–41: «подстановка кодирует `%` и `-`…, между подстановками — литерал `-`, `:int` — только к целым полям; разные значения полей дают разные id».
- Нормы:
  - P/02.1:176–179: `{имя}` — «только строка без преобразования»; иной тип — 400;
  - P/06.1:98–100: типы `int` и `float` различны;
  - `detjob.subsystem.yaml:38–39`: `from`, `to` — `{type: float}`;
  - остальные поля задачи, которые могли бы различить события, — `params` (непрозрачная строка), `labels`, `mask_from` — события не называют.
- Свидетель: М10B/22:124–126 «Идемпотентность из имени» — `jid = f"{unit}-{d['kind']}-{int(t0)}-{int(t1)}"`: интервал входит в имя.
- Контрпример:
  - `auto` по событию камеры 7 в 10:00 заводит скан `lpr` интервала 09:55–10:05. Строка `auto-7-<rec>-lpr` (больше полей подставить нечем).
  - В 10:30 новое событие той же камеры — скан 10:25–10:35, тот же id.
  - CAS `""` проваливается, строка своего `made`. По ADR:72 и :77 это повтор, «без нового эффекта». Второй интервал не сканируется, а `creates{outcome}` его не отличит от честного повтора.
  - То же у `rec` (`scan_what_arrived`): каждая следующая порция записи камеры.
- Последствие: правило противоречит ADR:70, сценарии `scan` и `scan_what_arrived` теряют работу молча, пока первая задача не удалена по `retire_when.delete_after`.
- Предложение — одно из двух, рекомендую первое:
  - `{поле}` подставляет **каноническую запись** значения по `values_by_type` (P/06.1:98–100: `int` — десятичная, `float` — кратчайшая, восстанавливающая число), затем кодирует `%` и `-`. Запись однозначна для каждого типа, и однозначность построением сохраняется;
  - либо однозначность требуется только по `fixed`-полям и полю `about` (то, что держит ADR-0067), а прочие поля `key` вправе усекать `:int`, как свидетель. Повтор внутри секунды — сознательное сужение.

## Мелкие

1. **Кодирование — только `%` и `-`, а грамматика id отвергает больше.** P/06.1:178–180 отвергает в named id `/`, `\`, `|`, `"`, `,`, Cc, Zl, Zp и цифры вне 0–9. Строковое поле `key` с таким знаком (например, `kind` из настроек сценария) даёт id, который общая проверка строки отвергнет — `creates{refused}` вместо задачи. Кодировать `%XX` все знаки, которые грамматика id отвергает, а не только `%` и `-`.
2. **«Любые поля дверью» против неизменяемых полей `key`.**
   - ADR:65: «оператор — любые поля дверью».
   - ADR:41–42: «Поля `key` у строки с `made` неизменяемы и для двери».
   - Записать в :65 «кроме полей `key` строк с `made`» и назвать отказ двери: 400 «<поле> is fixed», как у `fixed`.
3. **Ручные `rec` и `det` со сроком больше не удаляются.** ADR:84–86 сохраняет ручные строки адресата с `fixed` после срока. У `rec` (`until`, `rec.subsystem.yaml:84`) и `det` (`until`, `det.subsystem.yaml:42`) свидетель удалял их по сроку (`jobs.expire`, `det.subsystem.yaml:40–41`). Отличие названо только для `detjob` (урок 05). Назвать его и в уроках 02 и 04, вместе с `expired_kept`.
4. **Отсчёт `retire_when.delete_after` после рестарта контроллера.** ADR:117–118 говорит «через N с после снятия по часам контроллера», но не говорит, откуда счёт после рестарта или смены очереди. У `unplaced` правило есть (ADR-0067 «Форма ключа»: «после рестарта отсчёт начинается заново (позже, не раньше)»). Сказать то же, иначе реализации разойдутся во времени удаления.

Прежние отложенные мелкие (Г-7, Г-8, Г-9, С-4, С-5) — при Т-правке, не повторяю.
