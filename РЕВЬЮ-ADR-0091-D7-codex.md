## Находки

### R91-D7-01 — блокер: HTTPS на петле публикуется как IP при сертификате только с DNS-именем

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:372–377`, доп. (7), п. 3. Связь: `Platform/common/contracts/role-certificate.md:18–19`; `Platform/02-installer/spec/02.4-installer.norms.md:318–331`.

**Точная цитата ADR:** «хост в адресе — `127.0.0.1` на петле, иначе `SERVER_NAME`; схема — `https` с комплектом». Там же, строка 377: «сертификат роли — по имени (SAN DNS), адреса IP в адресе двери нет».

**Допустимый контрпример.** Сервер `s1`, установленный и доверенный клиентом комплект роли `testsubworker`: SAN DNS `s1`, SAN URI `urn:w2c:role:testsubworker`; IP SAN нет. Дверь привязана к значению по умолчанию `127.0.0.1`, фактический порт 8444. Новый п. 3 требует опубликовать `https://127.0.0.1:8444`. Браузер на этой же коробке получает этот адрес; разрешение DNS исправно, дверь доступна по TCP, токен действителен. Проверка имени сервера всё равно не проходит: IP `127.0.0.1` не совпадает с DNS SAN `s1`. Браузеру нельзя отдельно передать имя проверки `s1`, сохранив URL с IP. Наличие доверенного центра эту ошибку не исправляет.

**Нарушенное основание и последствие.** Форму листа задают договор сертификата роли и P/02.4 Н1.6. Проверка HTTPS строит ожидаемый идентификатор из хоста URL; для IP нужен соответствующий IP SAN: [RFC 9110 §4.3.4–4.3.5](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.3.4). Правило п. 3 одновременно разрешает комплект с привязкой на петле и требует URL, которому комплект не соответствует. Обещанная дверь страницы не работает на разрешённой конфигурации. Кроме того, фраза об отсутствии IP в адресе буквально расходится с предписанным `127.0.0.1`.

**Проба.** `address-and-preflight-model.py`, результат `address-preflight-model.json`: изолированная проверка идентификатора через стандартный `ssl.match_hostname` даёт `match` для `s1`, `mismatch` для `127.0.0.1` на одинаковом SAN. Это не TLS-сеанс и не проверка всей цепочки.

**Вопрос «Архитектору», рекомендация.** Согласовать разрешённые сочетания привязки, публикуемого имени и SAN. Минимальное сужение без изменения формы сертификата: TLS-адрес всегда содержит проверяемое DNS-имя, которое у разрешённых клиентов ведёт к фактическому слушателю; конфигурацию, где этого нет, не объявлять рабочей. Отдельно назвать исход для сочетания TLS с привязкой на петле. Отключение проверки имени не является исправлением.

**Происхождение.** Контрпример был до доп. (7): в `VMS/01-cam/spec/01.5-cam.norms.md:45–49` той же выгрузки уже сочетаются TLS с комплектом и адрес на петле. Этот файл совпадает до и после коммита решения (`fe91c11eb5a36299c5d0747ab66789e80f426cb0` → `8a106017b159a7640b4de53f9705bd0185a9cbd6`). Доп. (7) переносит ошибку в общее правило. Более ранний коммит-причина не устанавливался.

### R91-D7-02 — существенная: preflight не отделён от проверки сертификата/токена маршрута

**Место:** тот же ADR, строки 367–369 и 381–385, пп. 1, 5–6. Связь: `Platform/03-worker/spec/03.4-worker.norms.md:350–356`; `Platform/common/contracts/door-token.md:69–80`.

**Точные цитаты:** п. 1 — «`token` — токен двери (договор `door-token`), иначе 403 `forbidden`; маршрут без допуска — отказ загрузчика»; п. 5 — «методы `GET`, `HEAD`, preflight `OPTIONS`; заголовок `Authorization`».

**Допустимый контрпример.** Страница разрешённой консоли вызывает объявленный читающий маршрут `GET /read/unit-a` иной origin, с верным `Authorization: Bearer …`; сертификата клиента у страницы нет. Для этого GET браузер сначала отправляет отдельный запрос:

```http
OPTIONS /read/unit-a HTTP/1.1
Origin: https://console.s1:8443
Access-Control-Request-Method: GET
Access-Control-Request-Headers: authorization
```

В preflight нет самого Bearer и нет `?t=`: будущий GET передаёт токен заголовком. Общая проверка допуска `token` даёт 403. Добавление заголовков CORS к этому 403 не помогает: браузер не отправит последующий GET. Объявление OPTIONS отдельным маршрутом не решает проблему без специального правила: п. 1 требует допуск у каждого маршрута, а ни роль, ни токен в этом preflight не представлены.

**Основание и последствие.** П. 5 обещает CORS с `Authorization`, но не говорит, что служебный preflight проходит до проверки допуска к данным. Старый договор требует отказ при отсутствии токена. [Fetch §4.8](https://fetch.spec.whatwg.org/#cors-preflight-fetch) строит новый OPTIONS с именами будущих заголовков, а не их значениями; успех требует статуса 2xx. Получается неописанная ветвь: буквальное применение общей проверки из п. 1 закрывает разрешённое чтение страницы. Это существенный пробел конвейера допуска, а не требование анонимного доступа к данным.

**Проба.** В `address-preflight-model.json` запросы сохранены полностью: общий token-gate отвечает preflight кодом 403; модель условия Fetch не допускает последующий GET. При отдельном ответе 204 только на preflight фактический GET без токена по-прежнему получает 403. Модель не запускала браузер и не имитировала криптографию токена.

**Вопрос «Архитектору», рекомендация.** Явно задать исключение: после необходимых транспортных/ресурсных проверок корректный CORS-preflight к объявленному маршруту обрабатывается до role/token, без чтения данных; для разрешённого Origin/метода/заголовков — выбранный 2xx с CORS-заголовками. Реальный GET/HEAD обязательно проходит свой допуск. Приёмка должна проверять OPTIONS без Bearer, затем GET с токеном и GET без него.

**Происхождение.** Доп. (7) коммитом `8a106017b159a7640b4de53f9705bd0185a9cbd6` добавляет совместно новую общую проверку маршрутов и обещание CORS-preflight; исключение между ними не добавлено. Дефект доказан в новом решении. Наличие аналогичной ошибки в более ранних частных реализациях/правилах не исследовалось.

### R91-D7-03 — существенная: HTTP-схема распространена на адреса не-HTTP дверей в пульсе

**Место:** тот же ADR, строки 372–374, п. 3; `VMS/01-cam/spec/01.2-cam.norms.md:64–73,143`. Исходный запрос `2026-10-23-запрос-vms-адрес-двери-процесса.md:18–24` прямо включает RTSP-раздачу.

**Точная цитата ADR:** «`url` и адреса подсистемы в пульсе»; далее — «схема — `https` с комплектом, `http` только на петле».

**Допустимый контрпример.** Работающая камера `c1`, настроенная RTSP-раздача `RTSP_HOST=127.0.0.1`, фактический `RTSP_PORT=8554`, комплекта нет. Подписчик находится на том же сервере. V/01.2 Н1.3 требует `live_url=rtsp://127.0.0.1:8554/c1`; дверь этого урока явно не HTTP (строка 143). При буквальном применении нового общего п. 3 к «адресам подсистемы в пульсе» получается `http://127.0.0.1:8554/c1`. Это другой протокол, не альтернативное написание того же адреса. Выдача `rtsp://…` нарушит общее правило, выдача `http://…` — контракт подписчика и RTSP-раздачи.

**Основание и последствие.** Требование RTSP и его URL остаётся в действующей норме V/01.2; запрос просит определить привязку и имя сервера, не заменить RTSP на HTTP. В новом решении нет отдельного перехода протокола или снятия RTSP. Схема URL оказывается неоднозначной между общей и предметной нормами; исполнитель общего правила ломает опубликованный адрес. Это не требование ввести RTSPS либо новый транспорт.

**Проба.** `rtsp-address-model.py`, результат `rtsp-model.json`: на одном входе конструкции владельца и общего правила имеют схемы `rtsp` и `http`. Реальный RTSP/HTTP-клиент не запускался.

**Вопрос «Архитектору», рекомендация.** Разделить охват п. 3: правило выбора `http/https` относится к HTTP-дверям. Общие требования к привязке и имени можно применять к сетевым дверям иных протоколов отдельно, сохранив схему, которую задаёт урок-владелец. Назвать RTSP явным примером границы. Аналогично не превращать `live_shm` в HTTP-адрес лишь потому, что поле публикуется в пульсе.

**Происхождение.** Новое общее правило добавлено коммитом `8a106017b159a7640b4de53f9705bd0185a9cbd6`; прежняя норма RTSP сохранена. Изменённый этим коммитом файл — только ADR. До него общего предписания `http/https` для всех таких адресов здесь не было (`decision-delta.json`, `origin-check.json`).

## Остальные части решения

- **Один слушатель mixed:** выбор решает исходную потребность процессов и страницы. Необязательный сертификат совместим с браузером без сертификата; отказ TLS при предъявленном неверном сертификате — явная граница решения. Не требую второго слушателя или допуска иностранного центра.
- **Маршруты и форма:** при исполнении понадобятся согласованные новая форма `door.routes`, выпуск/выдача списка читающих маршрутов и договор токена. В выгрузке `02.1-installer.form.yaml:179` это ещё массив сегментов. Само отсутствие будущей формы на срезе рассмотрения ADR не засчитано дефектом.
- **Токен места:** п. 2 устраняет исходную неопределённость «держит единицу» против «хранит её данные в своём месте». Выдача по `view` на единицу и подтверждение держателя места остаются требованиями P/06.5 Н3 (`06.5-console.norms.md:373–389`). Исправность реализации этих проверок не утверждается.
- **Журнал:** адрес `audit/<роль>/e1` согласуется с общим договором. Несколько процессов роли на одном сервере уже предусмотрены: целая строка под исключительной блокировкой, уникальный экземпляр в id (`event-journal.md:65–73,79–87`); требование одного отдельного файла на каждый воркер не нужно. Вид и дополнительные поля определяет владелец двери.
- **DNS и wildcard-привязка:** явный отказ `0.0.0.0`/`::` и предпосылка разрешения имён приняты как ограничения профиля, а не самостоятельные дефекты. Они не устраняют R91-D7-01: там клиент и сервер на одной коробке, DNS исправен.
