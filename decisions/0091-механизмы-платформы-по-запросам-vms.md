# Механизмы платформы по запросам VMS: заказчик заводит строку сам, состояние единицы, срок, диск, доли, рантайм

## Context and Problem Statement
Класс системы: платформенная система. До старта комплекта VMS (ADR-0090) платформенные половины уроков М10B и работа
снимаемого `vmsjobs` должны стать нормами `Platform/` или получить отказ с обходом (ADR-0090 доп. (4)–(7)). Пакет из 11
запросов (`inbox/2026-10-22-запросы-vms-пакет.md`) и первая редакция этого ADR прошли ревью трёх. Первая редакция
отдавала заказ единицы контроллеру адресата; ревью показало корень: часть логики нужна **до** создания строки (ссылка
задачи на запись, `labels` размещения, срок `now + minutes`, подавление дубля), а контроллер платформы логики подсистемы
не исполняет (ADR-0002), и держатель созданной единицы приходит слишком поздно. Итог под одной ревизией не отличал новую
жизнь ключа и поздний ответ отсечённого держателя.

## Decision Drivers
* у строки — один писатель или явно названные два с порядком (P/06.1 Н1.1; исключение — решением этого ADR);
* без хуков: логика подсистемы — в процессе подсистемы, платформа — объявления и общие правила (ADR-0002);
* ограждение эпохой P/03.2 не ослабляется;
* требование — семантикой; имена функций — «Решает реализация»; где у свидетеля есть имя — норма берёт его.

## Considered Options
* **№ 1:** (А) воркер адресата пишет дверью консоли; (Б) воркер адресата пишет в хранилище правом `worker.makes`;
  (В) заказ декларацией `requests.orders`, исполняет контроллер адресата (первая редакция); (Г) **заказчик заводит и
  продлевает строку адресата сам — по объявленному узкому праву, с общей проверкой строки и под своей эпохой**.
* **№ 3, 10:** (А) таблица исполнителя с `revision`; (Б) консоль переносит фазу пульса в строку; (В) **состояние единицы:
  строка хранилища под стражем эпохи, привязанная к жизни строки (`born`)**.
* **Прочее** — по одному варианту с поправками ревью.

## Decision Outcome
1. **Заказчик заводит строку сам (№ 1), вариант (Г), решение владельца.** Манифест заказчика объявляет
   `worker.creates: [{sub: <адресат>, rows: <таблица единиц>, key: <шаблон>}]` (P/02.1). Id создаваемой
   строки — **`<заказчик>-<key>`**: префикс не выбирается, `key` — шаблон P/02.1 Н1.4 по полям строки, называющий
   все `fixed`-поля адресата и поле его `about`, кроме поля-источника id (`unit.id`): его библиотека заполняет готовым
   id, шаблон, ссылающийся на него, — отказ загрузчика. Однозначность — построением: поля `key` — только обязательные
   (`required`) типов `string`, `url`, `int`, `float`, `bool`, у которых запись по `values_by_type` (P/06.1 Н1.2)
   единственна (`float` — правило этой нормы, по образцу JCS RFC 8785, без отсылки к чужому тексту: цифры —
   кратчайшие, восстанавливающие число, из них ближайшие к точному значению, при двух равно близких — с чётной
   последней цифрой; записываются развёрнуто, без экспоненты, как
   требует `values_by_type`, — сама Н1.2 не меняется, получает правило выбора; `-0` → `0`; векторы: два равно близких
   кратчайших (выбор чётной), равные по длине кратчайшие, `5e-7`, `1e21`); `list`, `json`, `blob`, `*_secret` — отказ загрузчика. `{поле}`
   подставляет эту запись, затем кодирует процентами каждый знак вне `A–Z a–z 0–9 _ . ~` (в том числе `%`, `-` и всё,
   что отвергает грамматика id P/06.1 Н1.3), цифры hex — верхним регистром (`%2D`); между подстановками — литерал `-`; `:int` в `key` не допускается (усечение склеивает значения: `from`, `to` задачи — дробные); разные
   значения полей дают разные id, поэтому id задаёт эти значения: вернувшееся имя — тот же предмет (ADR-0067). Поля `key` у строки с `made`
   неизменяемы и для двери (как `fixed`). Права P/02.5 — префиксный образец P/01.2 `<адресат>/<rows>/<заказчик>-*` на создание и правку
   (удаления у заказчика нет). Загрузчик отвергает адресата с `unit.id: numeric` (резерв `next_id` заказчику не даётся)
   и двух заказчиков одной таблицы, чьи префиксы вложены (`rec-` и `rec-x-`); дверь консоли создание id с префиксом
   объявленного заказчика отвергает (400) — под префиксом живут только строки своего `made`; это сужение имён
   оператора (запись `auto-backup` у `rec`) называется в уроках 02, 04 и словами двери; строки с префиксом, созданные
   до объявления заказчика, остаются и заняты. Чтения общей проверки
   строки выводятся из объявления: при создании и правке — цели `ref` и `must_match` самой строки и строки семей
   каталога, чьё поле с `ref` на таблицу адресата и `must_match` (обратная проверка, P/06.1:200–202); удаление ссылок не
   проверяет. Запись идёт **из библиотеки воркера** (P/03.6) и:
   - проверяется **общим правилом строки платформы** — тем же, что у двери консоли (P/06.1: схема, `must_match`, `fixed`,
     `ref`, надгробие); поля-blob при создании не пишутся (P/06.1);
   - идёт **под стражем эпохи единицы заказчика**: CAS своей строки + `guard {key: <заказчик>/epoch/<unit>, index:
     <версия строки эпохи, подтверждённая при взятии эпохи>}` (P/01.1: `index` — версия строки, не номер эпохи);
   - несёт условие хранилища **`not_after`** = `at` + `ORDER_HORIZON` + 60 — новое общее условие записи P/01.1: запись
     журнала применяется, только если её **время приёма** не позже `not_after`, иначе отказ `expired` (группа
     `conflict`: той же записью не повторяется; исход заказчика `creates{expired}`); память id операции проверяется
     раньше `not_after`, и `not_after` входит в отпечаток операции (P/01.1 Н3) — повтор применённой записи получает
     её ответ. Порядок проверок записи — при **применении** записи журнала, по времени приёма, хранимому в ней: память
     id, затем `not_after` / `not_before`, затем `guard`, затем `cas`; при нескольких нарушениях ответ по первому. Так
     повтор, пришедший после `not_after`, пока первая копия ещё не применена, получает ответ первой, а не `expired`. Время приёма **не убывает по журналу**: `max(часы лидера, время приёма предыдущей записи журнала)`,
     хранится в записи журнала, новый лидер и перезапуск продолжают от последнего; хранилище без журнала хранит своё
     последнее время приёма так же прочно, как строки; время приёма входит и в состояние, и в снимок хранилища (P/01.3
     `last_snapshot`). Часы лидера, ушедшие вперёд, поднимают время приёма, и заказы получают `expired`, пока часы не
     догонят: признак `admission_ahead` в `/v1/status` хранилища. Значения строки хранилище не толкует;
   - **удаление** строки с `made` (контроллер, `worker.deletes`) несёт условие хранилища **`not_before`** =
     `not_after` этой жизни, вычисленное из строки: `made.keep` − 60 (контроллер адресата манифест заказчика не
     читает) — новое общее условие P/01.1: запись применяется, только
     если её время приёма строго позже `not_before`, иначе отказ `early` (той же записью не повторяется; удаляющий
     пробует на следующем проходе);
   - несёт хранимое поле платформы `made: {by: <подсистема-заказчик>, at, keep, gone?}` (P/06.1 `platform_fields`):
     `at` — время события (при продлении — наибольшее), `keep` = `at` + `ORDER_HORIZON` + 120 (с `at` не убывает); `gone` — время удаления,
     его ставит дверь консоли по своим часам, удаляя строку с `made`. `made` ставит только библиотека, дверь консоли
     запись `made` отвергает и при правке оператором сохраняет; строку своего `made` продлевать вправе любая единица
     заказчика (два сценария продлевают одну запись); строка без своего `made` — **занята**, заказчик её не пишет.
   Строка **двухписательная** (решение этого ADR): оператор — любые поля дверью, кроме полей `key` строки с `made`
   (400 «is fixed»); заказчик — только строки своего `made`,
   с `If-Match` (P/06.1). Просьб и меток для заказа нет. **Повтор безвреден детерминизмом** (замена прежней защиты
   метки) — правилом библиотеки, не только логики заказчика. Часы писателей кластера (лидер хранилища, контроллер,
   дверь, воркеры, писатель события) расходятся не больше чем на 60 с — новая предпосылка кластера в P/01.1 «Время»
   (как P/08.2:109 у держателей домена):
   - id — из личности события и параметров; срок — **от времени события**: `until = <время события> + minutes × 60`
     (отличие от свидетеля, где отсчёт шёл от исполнения, — записывается в урок 07); продление — `max` прежнего и
     нового, `until: 0` (без срока) не трогается; значения (в том числе `made.at`, `made.keep`) не меняются — записи нет;
   - **горизонт повтора — постоянная платформы `ORDER_HORIZON` = 600 с** (P/03.6), не объявление манифеста: событие
     старше `ORDER_HORIZON` по часам заказчика библиотека не исполняет; `not_after`, `keep`, `not_before` считаются
     только от неё. Порог свежести — логика заказчика, любое значение не больше `ORDER_HORIZON`: он лишь реже исполняет
     события и безопасности не касается, платформа его не знает. Изменяемого горизонта нет — истории смен, `seen`,
     правил новой жизни заказчика не нужно (решение владельца 2026-10-22, разбор ред. 12). Принятая хранилищем
     запись повтора стоит в журнале раньше удаления и проваливается на CAS `""`, позднейшая — `expired`: `not_after`
     повтора = `at` + 660 ≤ `keep` − 60 = `not_before` удалённой жизни; строка, чей срок `ends` по часам заказчика уже прошёл, не заводится;
   - строку с `made` никто не удаляет физически, пока его часы не **строго позже** `made.keep` — ни контроллер
     (`delete_after`, `ends`), ни воркер адресата (`worker.deletes`, проверка библиотеки) — `keep` лишь избавляет от
     заведомо ранних попыток. Порядок держит хранилище: удаление принято при времени приёма > `not_after` (`not_before`),
     время приёма по журналу не убывает — всякая запись после удаления `expired`, как бы ни шли стенные часы до приёма
     удаления и после; запись повтора, принятая раньше удаления, проваливается на CAS `""`;
   - над надгробием библиотека пишет только для события позже `made.gone` + 60 — с CAS его версии и теми же `fixed`
     (P/06.1:182): удалённое оператором повтор прежнего события не возрождает (`scan` из окна — тоже); событие в
     минуте после удаления считается прежним — сознательное сужение; позднейшее событие запись заводит;
   - физически удаляются (`delete_after`, `ends`) у адресата с `fixed`-полями или `about` не по id только строки с
     `made` — поправка ADR-0067 доп. 2026-10-10 и правил 46–47 P/02.1: имя таких строк держит шаблон `key`. Ручные
     строки этого адресата физически не удаляются, и срок к ним не применяется молча нигде: `ends` снимает с
     размещения и не размещает, `delete_after` не удаляет, строка остаётся до удаления оператором дверью; контроллер
     считает такие строки в отчёте прохода (`expired_kept`). Ручные задачи `detjob` удаляет оператор — отличие от
     свидетеля (`jobs.forget_finished`) в уроке 05, ручные `rec` и `det` со сроком — отличие от `jobs.expire` в уроках
     02, 04;
   - срок законченной единицы — от её снятия по `retire_when`: ключ `retire_when.delete_after` (заменяет
     `forget_finished` урока 05); после перезапуска контроллера отсчёт идёт заново, как у `unplaced.delete_after`.
     `unplaced.delete_after` считает время без держателя и задачу, ждущую ёмкости, удалил бы не начатой.
   **Логика — у заказчика**: основа — настройки детектора оператора на той же камере и модели, `params` поверх,
   `labels` наследуются **при создании** (размещение их видит); маска — строковой ссылкой
   `mask_from: <sub>/<id>@sha256-<hex>` в строке задачи, только у строки с `made`: держатель при старте читает тело по
   дайджесту (право — образец `worker.reads` на `<sub>/blobs/*`); ссылкой для уборки тел `mask_from` не служит
   (P/06.1:618) — тела нет, задача `failed` словами в пульсе, скана без маски нет (урок 05); второй детектор на камеру,
   которую уже смотрит ручной без конца, не заводится; скан камеры, которую никто не пишет, не заводится. Заказчики VMS:
   `auto` (`record` → `rec`, `detect` → `det`, `scan` → `detjob`), `rec` (`scan_what_arrived` → `detjob`); `detedge` —
   существующей просьбой дозаписи. Имена создаваемых строк меняются на префиксные (`7-auto` → `auto-7`,
   `<cam>-<kind>-auto` → `auto-<cam>-<kind>`, задачи — `auto-…`, `rec-…`) — правка уроков и долг продукта. Метрика
   заказчика — `creates{outcome}` в пульсе; остаток своих строк с `made` у адресата — `made_rows` там же.
2. **Срок единицы (№ 2).** `placement.ends: {field, never: 0}`: контроллер не размещает и снимает единицу с `<поле>` ≠ 0
   и ≤ своих часов, затем удаляет строку **физически, без надгробия**, с CAS прочитанной ревизии и стражем
   `placement_turn` (как `delete_after`, P/04:561–563) — продление между чтением и удалением отменяет удаление.
3. **Состояние единицы (№ 3, № 10), вариант (В).** Манифест объявляет `unit.state: {<имя>: <схема>}`. Состояние —
   **строка хранилища** `<sub>/state/<имя>/<unit>` (кластерная, как все строки) `{born, revision, epoch, …}`:
   - `born` — значение жизни строки единицы: хранимое поле платформы, его ставит создатель строки (дверь или
     библиотека заказчика) уникальным значением и никто не меняет (P/06.1 `platform_fields`); новая строка с тем же id —
     новый `born`;
   - смена `revision` при том же `born` — перезапуск под прежней эпохой (P/03.3 шаг 2, P/03.2 Н1.5); смена `born` —
     **новая жизнь**: держатель останавливает единицу и берёт эпоху заново, с новыми привязками `of` (ADR-0013), как у
     удалённой и созданной (P/03.3 Н5); состояние пишется с `born` и `revision` запуска, не перечитанной строки;
   - пишет **только держатель** под стражем эпохи (CAS + `guard {key: <sub>/epoch/<unit>, index: <версия строки эпохи,
     подтверждённая при взятии>}`) — отсечённый держатель, в том числе поздним повтором, не перезапишет состояние новой
     эпохи;
   - **действует** состояние живой строки (не надгробия), чей `born` = `born` строки и `revision` = `revision` строки; эпоха при чтении не
     сверяется — итог **переживает переезд**: новый держатель читает состояние и законченную задачу не переисполняет;
   - `retire_when: {state: <имя>, field, in, delete_after?}` (P/04 Н1.3) — по действующему состоянию; `delete_after` —
     физическое удаление через N с после снятия по часам контроллера (п. 1);
   - **видимость**: действующее состояние — вложенным объектом `state: {<имя>: <поля состояния без born, revision,
     epoch>}` в представлении единицы у консоли (только чтение, P/06.1) и в снимке контроллера (P/04 Н1.3а), одним
     правилом действия; в `snapshot` манифеста — `state.<имя>`, без ключа — все состояния, кроме курсора; строка
     состояния не читается своим типом — единица в шарде без этого состояния, счёт `snapshot_state_garbled` в отчёте
     прохода; поле единицы
     с именем `state` при объявленном `unit.state` — отказ загрузки (P/02.1); у `detjob` поля `state` и `ended` уходят
     в состояние `result`, `snapshot: [name, cam, kind, state.result]` — правка манифеста урока 05;
   - курсор — `unit.state.cursor`: монотонный, правкой строки не сбрасывается (действует по `born`), переживает переезд —
     отличие от свидетеля (М10B/25:301) записывается в уроки 06, 07; пишется не чаще `STATE_EVERY`;
   - **удаление единицы** (`delete_after`, `ends`): снять с размещения, удалить строку (CAS прочитанной ревизии, страж
     `placement_turn`) и только после подтверждённого удаления — состояние. Отменённое удаление строки (правка,
     продление) состояние не трогает; обрыв после удаления строки оставляет осиротевшее состояние — его снимает уборка;
   - **уборка** осиротевшего состояния (строки нет, она надгробие или её `born` другой) — шаг прохода контроллера
     (P/04 Н3; чтение `<sub>/state/*`, право `delete:<sub>/state/*` по P/02.5 при объявленном `unit.state`), одной
     операцией: CAS версии состояния и `guard {key: <строка единицы>, index: <прочитанная версия, у надгробия — его;
     "" — строки нет>}` (P/01.1) — строка, созданная или изменённая после чтения, уборку отменяет; действующее
     состояние уборка не трогает.
   Срок удаления законченной — `retire_when.delete_after` от снятия по часам контроллера; у строки с `made` — только
   когда часы строго позже `made.keep` (п. 1).
4. **Диск (№ 4).** P/02.4 Н1.1 `dirs`, `users_groups`, Н1.7 `install`: состояние подсистемы —
   `/data/platform/subsystems/<sub>` `0751 <dep>-<sub>:<dep>-<sub>`; часть — `…/<sub>/<часть>` своего пользователя;
   `/etc/<sub>` → `/data/platform/etc/subsystems/<sub>`; тома архива — точки монтирования
   `/data/platform/subsystems/<sub>/<часть>/volumes/<n>` владельца-писателя, объявлены в манифесте, установщик не
   монтирует, при старте проверяет владельца; группа `<dep>-<sub>` — в `users_groups`.
5. **Доли и части (№ 5).** Владелец: `shares: {<имя>: {kind: socket | dir}}`; потребитель: `worker.uses: [<sub>.<имя>]`
   → группа доли в `SupplementaryGroups`. Каталог доли `2750 <владелец>:<группа доли>`, сокет `0660` (или сокет-юнит с
   `SocketGroup=`); читатель подменить сокет не может. Доля части — группа пользователя части (как у свидетеля), отдельной
   группы нет. Часть со службой — `parts: {<имя>: {exec}}`, юнит `<dep>-<sub>-<часть>.service` по P/02.4 Н1.1. Загрузчик
   каталога строит **все** получившиеся имена ОС и путей (пользователи, группы, юниты, каталоги долей и частей всех
   подсистем) и отвергает любое совпадение и имена длиннее 32.
6. **Рантайм воркера (№ 6).** P/03.3: отступ — экспонента с обязательным дрожанием, пределы, сброс после `max`
   устойчивой работы, по слову подсистемы и когда единицы нет в желаемом, признак `stalled` в пульсе. P/03.2: подъём
   упавшего процесса единицы **под той же эпохой** — локальный переход, как перезапуск по `revision` (P/03.2:548–552):
   ранее принятый запуск в этом экземпляре; та же `observed_revision` и её тело; пока `may_write`; единица в последнем
   прочитанном назначении этого воркера, не отпущена (ворота P/03.2:514–519 целиком); не lost, не fenced; **место
   единицы, если есть, ещё в окне записи** (P/03.2:601–603); при `NotReadThisPass` — тот же предикат; новой выдачи нет,
   действия устройств разрешения через `may_write` не получают. Эпоху, взятую ради действия (ниже), запуск наследует
   без новой выдачи (P/03.3 шаг 2). P/03.6: не больше одного незавершённого вызова действия на группу единицы
   (`group_by`; цель вызова — группа, поэтому цели размещаются вместе, ADR-0011), в том числе после `unknown`;
   «устройство не открыто» — ответ подсистемы «не готово»; вызовы вне потока цикла, аренды держатся при всех зависших
   целях (ADR-0037); правило одного вызова — новая норма из М10B/04:223. Вызов действия для единицы назначения без
   эпохи — сначала взять эпоху (М10B/04:257). Пульс P/03.4: `command_counts.<outcome>`, `commands_in_flight`,
   `commands_reanswered`, гистограммы `command_road.<by>`, `command_request.<by>`, `command_wait` — имена свидетеля.
7. **Просьба от воркера (№ 7).** `about` — по договору (значение единицы-адресата, `request-mark.md:62`); `by` —
   `<sub>/<unit>` подателя; строка журнала — как аудит двери (P/06.4 Н3 шаг 6); тело проверяется по схеме цели до
   подачи; счёт подачи в пульсе подателя — `filings.<outcome>` (имя свидетеля).
8. **Удержание «про» (№ 8).** P/06.4 Н1.5: `holds.unit` называет единицу подсистемы `about.sub`; удержание держит
   единицы и бакеты других подсистем, чьё поле `about` называет удержанную, включая удалённые по полям надгробия; бакет
   без строки держится, пока его единица неизвестна; право ресурса — P/02.5:90.
9. **Места (№ 9) — отказ с обходом:** смысл уже норма (P/03.2:592, 601–605; P/04:132); имена вызовов — «Решает
   реализация» (P/03.1 п. 1); том не открылся — `place_by: ""` в пульсе, единицы уходят по P/04. Одна фраза в P/03.2 Н3.
10. **`near` (№ 11).** P/04 Н1.3: моё значение — поле `by`, иначе мой id; значение соседа — поле `of`, иначе id
    соседа; `prefer` — И по полям, ИЛИ по списку (как `affinity.strict`), путь — шаг по полю-ссылке соседа; среди
    нескольких совпавших соседей — по имени соседней единицы UTF-8 (как свидетель, М10B/26:295, 309); потребители —

11. **Блокирует уроки** (до норм и выгрузки): № 1 — `02-rec`, `04-det`, `05-detjob`, `07-auto`; № 3 — `05-detjob`,
    `06-detedge`, `07-auto`; прочие — как в пакете.

### Consequences
* Good, because логика заказа целиком у подсистемы-заказчика, до создания строки; платформа даёт право, общую проверку
  строки и стражу — без хуков и без языка правил в манифесте.
* Good, because состояние единицы не подделает ни отсечённый держатель (страж эпохи), ни прежняя жизнь ключа (`born`), и
  оно переживает переезд.
* Bad, because впервые одна подсистема пишет строки единиц другой — исключение из «подсистемы говорят просьбами и
  чтением»; строка заказа двухписательная.
* Bad, because отличия от свидетеля: курсор переживает переезд; заказы `vmsjobs` исполняет заказчик, а не общий процесс;
  срок заказа — от времени события; имена создаваемых строк — префиксные (`auto-7`), правка уроков и долг продукта.
* Bad, because горизонт повтора — постоянная `ORDER_HORIZON` = 600 с (у свидетеля — 60 с): строка заказа живёт не
  меньше 12 мин после последнего события, событие старше 10 мин заказа не создаёт; постоянная не повышается.
* Bad, because хранилище получает новые общие условия записи `not_after`, `not_before` и неубывающее время приёма; ADR-0067 доп. 2026-10-10 поправлен для строк
  с `made`.
* Bad, because правок норм много (P/01.1, P/02.1, P/02.4, P/02.5, P/03.2, P/03.3, P/03.4, P/03.6, P/04, P/06.1, P/06.4,
  `request-mark.md`) — одна выгрузка до старта VMS.

### Confirmation
Нормы и приёмка пп. 1–10 на testsub/testsub2 — у обеих реализаций до старта VMS, с отрицательными сценариями: ручная
строка под шаблоном — занята; отсечённый держатель не пишет состояние; обрыв после удаления строки → тот же id — старый
итог не действует; отменённое удаление строки — итог действует; уборка состояния при строке, созданной после чтения, —
отменена; смена `born` — новая эпоха; адресат `numeric` и вложенные префиксы — отказ загрузчика; повтор заказа того же
события — без нового эффекта, в том числе после уборки по сроку, при удалении воркером адресата, запоздавшей записью
(`not_after` — `expired`), на равенстве границ (часы удаляющего = `keep` — не удаляет), при общем ходе стенных часов
назад до приёма удаления (`not_before` — `early`) и после него (время приёма не убывает — `expired`) и над надгробием (событие в
минуте после `made.gone` — прежнее); событие старше `ORDER_HORIZON` — не исполняется; дверь — отказ id с префиксом заказчика и правки поля `key` у строки с `made`;
`key` по (`7`, `1-x`) и (`7-1`, `x`) и по двум интервалам одной камеры — разные id; `:int`, поле `list`, `json`, `*_secret` и необязательное в `key` — отказ загрузчика; кодирование — `%2D`, не `%2d`; шаблон по полю-источнику id — отказ загрузчика; задача, ждущая
ёмкости, не удаляется; ручная строка с прошедшим сроком — снята, не удалена, `expired_kept`; состояние надгробия — осиротевшее; подъём под эпохой вне окна места —
нет; совпадение имени доли с подсистемой — отказ загрузчика; действующее состояние — в выдаче консоли и в снимке.
Запросы во входящих закрыты разделом «Решение».

## Pros and Cons of the Options

### № 1 (А) воркер адресата дверью консоли
* Bad, because у несозданной единицы нет держателя просьбы; у воркера нет личности у сторожевой.

### № 1 (Б) воркер адресата в хранилище
* Bad, because держателя просьбы к несозданной единице всё равно нет.

### № 1 (В) заказ контроллером адресата
* Good, because держатель и личность есть.
* Bad, because логика до создания строки (ссылка, `labels`, срок, подавление) — у подсистемы; контроллеру её не дать без
  языка правил в манифесте; держатель созданной единицы приходит поздно.

### № 1 (Г) заказчик пишет сам
* Good, because логика там, где решение (сценарий, регистратор), — до создания строки.
* Bad, because межподсистемная запись строк — новое исключение границы подсистем.

### № 3 (Б) консоль переносит фазу пульса
* Bad, because второй писатель строки и пульс как хранилище факта (М10B/21:220).

## Дополнение (2), 2026-10-23 — запросы VMS после старта: остановка, окружение и доля части
Решение «Архитектора» по запросам «Спецификации VMS» (`inbox/2026-10-23-запрос-vms-остановка-и-окружение-части.md`,

1. **Срок остановки.** `worker.stop_timeout` (целое ≥ 20, умолчание 20) → `TimeoutStopSec` юнита воркера — это и есть

   Меньше нижней границы — отказ загрузчика.
2. **Порядок юнитов.** Юнит воркера подсистемы с `parts` — `After=` каждого юнита своей части, без `Wants`/`Requires`:

3. **Файл подсистемы.** Юнит воркера и юнит части ставят `W2C_SUB_ENV=/etc/<sub>/<sub>.env`

   воркера и части, старт без файла; своя доля с `part` — `SupplementaryGroups`, `part` не из `parts` — отказ,

## Дополнение (3), 2026-10-23 — ревью доп. (2): запуск части, запись в долю, сроки, права
Решение «Архитектора» (разбор `inbox/2026-10-23-ревью-ADR-0091-доп-2-разбор.md`). Уточняет доп. (2).
1. **Часть запускается сама.** Установщик включает юнит каждой части вместе с воркерами (P/02.4 Н1.7 `enable`), старт
   сервера поднимает части до воркеров; связь воркера с частью — только `After=` (доп. (2) п. 2). Приёмка — холодный

5. **Права.** Каталог состояния части — `0700` пользователя части: группа части, которую потребители доли получают в

## Дополнение (4), 2026-10-23 — программа воркера: `worker.exec`
Решение «Архитектора» по догадке `cammeta-c-python` I02-DOMAINWORKER-EXEC (журнал `inbox/2026-10-23-догадки-стадии-C.md`)
и пробелу описи VMS № 15. P/02.4 Н1.1 говорит «команда воркера получает имя слота аргументом», Н1.12 — `w2c-run.sh
domainworker <sub>`, но откуда берётся команда воркера, нормы не называют (у части она есть — `parts.<часть>.exec`).
1. **`worker.exec`** — ключ манифеста (P/02.1): командная строка программы воркера подсистемы, та же форма, что у
   `parts.<часть>.exec` (абсолютный путь и аргументы, без оболочки). Обязателен у манифеста с единицами (`unit`).
2. **Воркер кластера** — юнит `<dep>-<sub>worker@` исполняет `worker.exec` и последним аргументом имя слота `%i` (P/02.4
   Н1.1, как сейчас «команда воркера получает его аргументом»), `W2C_ROLE=<sub>worker`.
3. **Воркер на домене** — `w2c-run.sh domainworker <sub>` исполняет тот же `worker.exec` без аргумента слота,
   `W2C_ROLE=<sub>domain`; роль процесса программа узнаёт по `W2C_ROLE` (одна программа на обе роли, P/03.7). Отдельной
   программы и пути вида `Source/<sub>domain` нет.

## Дополнение (5), 2026-10-23 — ревью доп. (4): раннер воркера, грамматика `exec`, источник, обязательность
Решение «Архитектора» (разбор `inbox/2026-10-23-ревью-ADR-0091-доп-4-разбор.md`). Уточняет доп. (4).
1. **Воркер кластера — через раннер.** Юнит `<dep>-<sub>worker@` запускает `w2c-run.sh worker <sub> <слот>` (закрытый

   установки (`admin`), и запуск программы из манифеста — того же доверия, что установка.
4. **Обязателен у каждого манифеста** (`unit` обязателен у всех, P/02.1), в том числе с `domain.kept`. Переход:

   отказа «нет `worker.exec`» и его место в порядке Н3, пересчитывает канонические ожидания; манифесты `VMS/` — правкой
   «Спецификации VMS»; продукт — строкой долга «Сборке».
5. P/03.2 Н3 «старт()» — для роли `<sub>worker`; воркер на домене — по P/03.7.
6. Приёмка: смена `worker.exec` v1 → v2 через `manifest put` — после перезапуска исполняется v2 (кластер и домен);

## Дополнение (7), 2026-10-23 — дверь процесса подсистемы: класс «смешанный», адрес, журнал, CORS
Решение «Архитектора» по запросам «Спецификации VMS» (`inbox/2026-10-23-запрос-vms-дверь-для-процессов-и-страницы.md`,
`…-адрес-двери-процесса.md`, `…-журнал-и-cors-двери.md`; выгрузка `1070531`). Дверь процесса подсистемы служит и
процессам других подсистем, и странице в браузере, у которой сертификата клиента нет.
1. **Класс `mixed`** договора сертификата роли: один слушатель; с комплектом — TLS сервера роли процесса, сертификат
   клиента запрашивается **необязательно** и, если предъявлен, проверяется в рукопожатии, как у класса `signed` (центры,
   срок, EKU; `sig`, `revoked`, роль — после). Каждый маршрут двери объявлен в манифесте (`door.routes`) с допуском:
   `role: [<роли>]` — нужен предъявленный сертификат одной из ролей, иначе 403 `no_role`; `token` — токен двери
   (договор `door-token`), иначе 403 `forbidden`; маршрут без допуска — отказ загрузчика. Два слушателя не нужны.
2. **Токен двери места** (`/where`, P/06.5 Н3): `unit` токена — единица, чьи данные лежат в месте держателя (не
   обязательно им держимая); держатель сверяет, что данные единицы лежат в его месте, иначе 403.
3. **Адрес двери процесса** (P/03.4 Н1.1 `url` и адреса подсистемы в пульсе): привязка `<ДВЕРЬ>_HOST`, умолчание
   `127.0.0.1`; `0.0.0.0`/`::` — отказ старта, код 2; хост в адресе — `127.0.0.1` на петле, иначе `SERVER_NAME`; схема —
   `https` с комплектом, `http` только на петле; порт — фактический. Имена серверов кластера друг у друга разрешаются —
   предпосылка развёртывания (DNS или файл хостов оператора), не механизм платформы; установщик на предварительной
   проверке сверяет, что `SERVER_NAME` каждого сервера `platform/servers` разрешается, иначе предупреждение
   (P/02.4); сертификат роли — по имени (SAN DNS), адреса IP в адресе двери нет.
4. **Журнал двери процесса.** Дверь пишет строки своих видов в `audit/<роль>/e1` своим писателем журнала (договор
   журнала событий): общие поля — кто (`user` или роль), что (`target`, `of`), сколько (`bytes`), исход (`status`),
   откуда (`addr`); виды и их поля сверх общих называет урок-владелец двери (`archive.read` — V/02).
5. **CORS** двери процесса (P/03.4 Н1.7): разрешённые источники — консоль кластера и консоль домена своей установки;
   методы `GET`, `HEAD`, preflight `OPTIONS`; заголовок `Authorization`; без куки (`Access-Control-Allow-Credentials` нет);
   иной источник — без заголовков CORS.
6. Приёмка: дверь `mixed` — процесс с ролью и без, страница с токеном и без; токен места для чужой единицы на своём
   месте; отказ старта на `0.0.0.0`; строка `archive.read`; preflight с разрешённым и чужим источником.

## Дополнение (8), 2026-10-23 — ревью доп. (7): адрес и TLS, preflight, допуск маршрутов, CORS, рабочие места
Решение «Архитектора» (разбор `inbox/2026-10-23-ревью-ADR-0091-доп-7-разбор.md`). Уточняет доп. (7).
1. **Адрес и TLS** (заменяет доп. (7) п. 3 в части хоста и схемы): с комплектом дверь слушает адрес сервера (не петлю) и
   публикует `https://SERVER_NAME:<порт>` — сертификат роли по имени сходится; без комплекта — только петля и
   `http://127.0.0.1:<порт>` (P/02.4 Н1.6). Сочетания «петля + https» нет. `0.0.0.0`/`::` — отказ старта, как было.
   Установщик на предварительной проверке сверяет, что `SERVER_NAME` разрешается в адрес привязки двери.
2. **Не только HTTP.** Правило хоста (`SERVER_NAME` вне петли, `127.0.0.1` на петле) и привязки — для любой двери
   процесса в пульсе; схему не-HTTP двери (`rtsp`/`rtsps` и т. п.) называет урок-владелец двери.
3. **Допуск маршрутов** (заменяет доп. (7) п. 1 в части формы): `door.routes` — список, элемент — имя маршрута (допуск
   `token`, как сегодня: маршруты токена двери — это они, договор `door-token`) или `{name, role: [<роли>]}` (допуск по
   сертификату роли). Умолчание — `token`, поэтому нынешние манифесты (`testsub2` `[read, play]`) и корпус переходят без
   правки. Слова отказов — как P/10 Н1.4: листа нет — 401 `no_role`, роль не та — 403 `wrong_role`, цепочка — `bad_chain`;
   токена нет или неверен — 403 `forbidden`.
4. **Роль без комплекта.** Дверь с маршрутом `role` без комплекта не стартует (код 2, имя двери): доказать роль нечем.
   Коробка без комплекта (окно ADR-0075) такие маршруты не обслуживает — ограничение называется в уроке-владельце.
5. **Класс `mixed` «как `signed`» целиком:** без возобновления сессий, TLS ≥ 1.2 (класс `signer`); `CertificateRequest`
   несёт `certificate_authorities` — центры кластера, чтобы браузер без таких листов не спрашивал человека.
6. **Preflight** `OPTIONS` отвечается до проверки допуска маршрута (у preflight нет ни листа, ни токена) — только для
   разрешённого источника.
7. **CORS:** разрешённые источники — список `CONSOLE_ORIGINS` в `w2c.env` (точные `схема://хост[:порт]`, сравнение байт в
   байт; у двери нет иного знания о публичном адресе консоли); методы `GET`, `HEAD`; заголовки запроса `Authorization`,
   `Range`; `Access-Control-Expose-Headers: Content-Range, Accept-Ranges, Content-Length`; `Vary: Origin`; без куки.
8. **Рабочие места.** Предпосылка развёртывания называется и для браузера оператора: рабочее место разрешает имена
   серверов кластера и доверяет центру кластера (`ca.pem`) — иначе страничные маршруты двери недоступны; ход к двери
   через консоль — не в этом решении.
9. **Токен места** (доп. (7) п. 2): договор `door-token` «`unit` и `holder` — свои» уточняется для двери места + вектор.
   Общие поля журнала двери — ещё `sub` (подсистема двери).
10. Приёмка п. 6 доп. (7) — на стенде с комплектом (TLS); где стенд не позволяет (браузер, рабочее место) — чтением.

## Дополнение (12), 2026-10-23 — запись в каталоге домена: исполнители назначения в виде
Решение «Архитектора» по запросу «Спецификации VMS» `inbox/2026-10-23-запрос-vms-запись-в-домене.md` (перевод V/02.9).
Подсистема, чья единица живёт в нескольких кластерах по назначению (основная запись и её резервы), объявляет
`domain.ref`; вид домена не должен считать законное размещение по назначению спором.
1. **Вид: исполнители назначения — не спор** (P/08.1 Н3 шаг 4). `ref`, который дают два члена и больше, — `contested`,
   кроме случая, когда все они — исполнители назначения этого `ref` (`cluster` и `copies`, P/08.6 Н1.1): тогда единицы
   всех исполнителей остаются в `units`, вид полон. Правило одно с `conflict` теневого отчёта (P/08.1 Н1.6) — вид и
   теневой отчёт одного прохода не расходятся.
2. **Строка без значения поля `domain.ref`** (поля нет или `""`) — не единица домена (P/08.1 Н1.2): в `units` её нет,
   полноты вида она не отнимает, спора не даёт; в отчёт члена пульс такой единицы идёт как прежде.
3. **Каталог `domain/reached`** — читатели дополняются воркером `<s>worker`, объявившим его в `worker.reads` (как копии
   книг, P/02.5 Н1.4): воркеру нужна свежесть копии книги назначения для решений на карте.
4. Приёмка: вид с основной и резервной записью одного `ref` в двух кластерах по назначению — `complete: true`, обе в
   `units`; та же пара вне назначения — `contested`; строка без `ref` — вне `units`; воркер с `domain/reached` в
   `worker.reads` читает каталог, без объявления — 403. Сценарии P/08.1, P/08.6 — где стенд домена позволяет, иначе
   векторы вида и чтением.

## Дополнение (14), 2026-10-23 — допуск по токену домена у маршрута двери процесса
Решение «Архитектора» по запросу «Спецификации VMS» `inbox/2026-10-23-запрос-vms-приёмник-на-двери-процесса.md`
(V/02.9 Н1.3, V/03.2). Приёмник регистратора принимает процессы своего кластера (лист роли) и обращающихся из других
кластеров домена (камера-кластер, ретранслятор, толкатель) — у последних есть только токен домена. У процесса один
слушатель двери (доп. (7)); второй слушатель ради допуска — обход, не норма.
1. **Форма** (P/02.1 `door.routes[]`): элемент — `{name, role?, domain?: [<вид>…]}`; строка — сокращение `{name}` (доп. (9)
   п. 3). `domain` — непустой список видов без повторов; каждый вид объявлен в `domain.tokens` какой-либо подсистемы каталога,
   иначе отказ каталога. `role` и `domain` вместе — маршрут допускает любое из двух.
2. **Допуск** (P/03.4 Н1.7 `door_admission`): `domain` — токен домена в `Authorization: Bearer`; проверка — функция `token`
   договора токена домена с `expect {kind: <вид из списка>, cluster: <свой кластер>}` (аудитория — как у вида, P/02.1 Н1.2б
   `audience_claim`); вид токена не из списка — как `wrong_kind`. Отказы — слова договора токена домена: нет токена — 401,
   токен не проходит — 401 со словом отказа, не тот вид или кластер — 403. Утверждения прочитанного токена (`ref` и прочие)
   платформа передаёт обработчику подсистемы, их смысл сверяет подсистема.
3. **Без комплекта** маршрут `domain` работает на петле, как `token` (доп. (9) п. 1); с комплектом — на адресе двери.
4. **Транспорт не-HTTP** (SRT и т. п.) — выбор реализации на отдельном слушателе подсистемы; допуск — тем же правилом пп. 2–3
   (функции платформы `token` и проверка листа роли).
5. Приёмка: маршрут `domain` — токен своего вида и кластера — 200; чужой кластер — 403; вид не из списка — 403; без
   токена — 401; лист роли при `{role, domain}` — 200; отказ каталога на виде, которого нет в `domain.tokens`. Сценарий
   P/03.4 — когда учебная подсистема получит такой маршрут, иначе — чтением и векторами `domain-token`.
