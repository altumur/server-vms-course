# Механизмы платформы по запросам VMS: заказ единицы, состояние единицы, срок, диск, доли, рантайм

## Context and Problem Statement
Класс системы: платформенная система. До старта комплекта VMS (ADR-0090) платформенные половины уроков М10B и работа
снимаемого `vmsjobs` должны стать нормами `Platform/` или получить отказ с обходом (ADR-0090 доп. (4)–(7)). Пакет из 11
запросов (`inbox/2026-10-22-запросы-vms-пакет.md`) прошёл ревью трёх: 2 блокера и 31 существенная находка. Главное:
исполнитель «воркер через дверь консоли» неисполним — у ещё не созданной единицы нет держателя просьбы (P/06.4:284 —
404; P/03.6:108, 118), а у воркера нет личности у сторожевой (P/06.3:56, 81–87); итог по одной ревизии не отличает
новую строку после физического удаления и прежнего держателя от текущего.

## Decision Drivers
* один писатель строки или явно названные два с порядком (ADR-0013); без хуков, только декларации (ADR-0002);
* ограждение эпохой P/03.2 не ослабляется;
* требование — семантикой; имена функций и классы — «Решает реализация»;
* одно имя на обеих сторонах: где у свидетеля есть имя, норма берёт его.

## Considered Options
* **№ 1, исполнитель заказа:** (А) воркер адресата пишет дверью консоли; (Б) воркер адресата пишет в хранилище правом
  `worker.makes`, правила строк — библиотекой; (В) **заказ единицы декларацией, исполняет контроллер адресата**.
* **№ 3, 10, итог и курсор:** (А) таблица исполнителя с `revision`; (Б) консоль переносит фазу пульса в строку;
  (В) **состояние единицы под эпохой**.
* **Прочее** — по одному варианту с поправками ревью (ниже).

## Decision Outcome
1. **Заказ единицы (№ 1), вариант (В).** Манифест адресата объявляет
   `requests.orders: {<action>: {id: "<шаблон из полей тела>", fields: {<поле строки>: <поле тела | константа>},
   extend: [<поле>], revive: true | false}}` (P/02.1). Дверь просьб принимает просьбу с действием заказа к единице,
   которой нет (исключение из P/06.4 «подать просьбу» шаг 1: `unit` = id по шаблону). Исполняет **контроллер адресата**
   (P/04): нет строки — создаёт (CAS `""`, проверки строки двери: схема, `must_match`, `fixed`, `ref` — общим правилом
   платформы, P/06.1); строка есть и создана заказом — продлевает поля `extend` только вперёд (`If-Match`); строка есть и
   заказом не создана — `refused` `taken`; надгробие: `revive: false` — `refused` `deleted`, `true` — создаёт заново.
   Строка заказа несёт `order: {rid, at}` — пишет только контроллер; дверь консоли запись `order` отвергает. Строка
   **двухписательная**: оператор — любые поля дверью, контроллер — только `extend` с `If-Match`. Метка — `performed`
   или `refused` с `ended_by: controller` (новое значение закрытого списка `request-mark.md`; `instance`, `slot` нет);
   жнец снимает отвеченную строку как обычную — действия заказа не `elsewhere`. Права контроллера на `unit.rows`
   выводятся из объявления (P/02.5). Правила над чужими строками — **у держателя созданной единицы** (код подсистемы
   при старте единицы): основа — настройки детектора оператора, `params` заказа поверх, `mask`/`labels` наследуются;
   подавление второго детектора; скан камеры, которую никто не пишет, — итог единицы `failed` (а не `refused` просьбы —
   отличие от свидетеля, записывается в урок). `scan_what_arrived` — `rec` подаёт заказ `scan` на привезённый диапазон
   (`worker.requests: [detjob]`, абсолютный диапазон в схеме) — правка только VMS. Схема просьбы `rec` для `record` —
   `oneOf` по `action` — работа урока `02-rec`; правка P/03.6:103–105 не нужна. Метрика контроллера —
   `requests_orders{outcome}`.
2. **Срок единицы (№ 2).** `placement.ends: {field, never: 0}`: контроллер не размещает и снимает единицу с
   `<поле>` ≠ 0 и ≤ своих часов, затем удаляет строку **физически, без надгробия** (как `delete_after`) условно по
   ревизии прочитанной строки — продление между чтением и удалением отменяет удаление. Контроллер, а не
   `worker.deletes`: неразмещённая единица и одни часы.
3. **Состояние единицы (№ 3, № 10), вариант (В).** Манифест объявляет `unit.state: {<имя>: <схема>}`; объект
   `<sub>/state/<имя>/<unit>` `{epoch, …}` пишет **только держатель единицы под своей эпохой** (`may_write`, CAS;
   `epoch` — текущая эпоха `<sub>/epoch/<unit>`, P/03.2). `retire_when: {state: <имя>, field, in}` действует, только
   если `epoch` состояния = текущей эпохе единицы и ревизия строки та же, что у держателя при записи (`revision`
   в объекте). Курсор — то же: `unit.state.cursor`, монотонный, правкой строки не сбрасывается, переживает переезд
   (новый держатель читает) — новое поведение против свидетеля (М10B/25:301), записывается; пишется не чаще
   `STATE_EVERY` (константа нормы). Состояние удаляется вместе со строкой единицы (кто удаляет единицу — удаляет и
   его). Срок удаления законченной — существующий `delete_after` по часам контроллера; «от `ended`» снято.
4. **Диск (№ 4).** P/02.4 Н1.1 `dirs`, `users_groups`, Н1.7 `install`: состояние подсистемы —
   `/data/platform/subsystems/<sub>` `0751 <dep>-<sub>:<dep>-<sub>`; часть — `…/<sub>/<часть>` своего пользователя;
   `/etc/<sub>` → `/data/platform/etc/subsystems/<sub>`; тома архива — точки монтирования
   `/data/platform/subsystems/<sub>/<часть>/volumes/<n>` владельца-писателя, объявлены в манифесте, установщик не
   монтирует, при старте проверяет владельца; группа `<dep>-<sub>` — в `users_groups`. `/srv/<sub>` — нет.
5. **Доли и части (№ 5).** Владелец: `shares: {<имя>: {kind: socket | dir}}`, каталог `/run/<dep>-<sub>-<имя>`
   `2750 <владелец>:<dep>-<sub>-<имя>`, файл сокета `0660` (или сокет-юнит с `SocketGroup=`); читатель подменить
   сокет не может. Потребитель: `worker.uses: [<sub>.<имя>]` → группа в `SupplementaryGroups`. Часть со своей службой —
   `parts: {<имя>: {exec}}`, юнит `<dep>-<sub>-<часть>.service` по P/02.4 Н1.1. Загрузчик каталога отвергает
   столкновение `<sub>-<часть>` с именем другой подсистемы и имена ОС длиннее 32.
6. **Рантайм воркера (№ 6) и пропуск П-1.** P/03.3: отступ — экспонента с обязательным дрожанием, пределы, сброс после
   `max` устойчивой работы, по слову подсистемы и когда единицы нет в желаемом, признак `stalled` в пульсе. P/03.2:
   подъём упавшего процесса единицы **под той же эпохой** — локальный переход, как перезапуск по `revision`
   (P/03.2:548–552), только пока `may_write`, эпоха та же, единица в последнем прочитанном назначении этого воркера,
   `revision` не изменилась, ограждение не сработало; при `NotReadThisPass` — тот же предикат; новой выдачи нет.
   P/03.6: не больше одного незавершённого вызова действия на группу единицы (`group_by`), в том числе после `unknown`;
   «устройство не открыто» — ответ подсистемы «не готово»; вызовы вне потока цикла, аренды держатся при всех зависших
   целях (ADR-0037); правило одного вызова — новая норма из М10B/04:223, не перенос ADR-0037. Вызов действия для
   единицы назначения без эпохи — сначала взять эпоху (М10B/04:257). Пульс P/03.4: `command_counts.<outcome>`,
   `commands_in_flight`, `commands_reanswered`, гистограммы `command_road.<by>`, `command_request.<by>`,
   `command_wait` — имена свидетеля.
7. **Просьба от воркера (№ 7).** `about` — по договору (значение единицы-адресата, `request-mark.md:62`); `by` —
   `<sub>/<unit>` подателя; строка журнала — как аудит двери (P/06.4 Н3 шаг 6); тело проверяется по схеме цели до
   подачи, отказ — счётчик `requests_unfiled` в пульсе подателя.
8. **Удержание «про» (№ 8).** P/06.4 Н1.5: `holds.unit` называет единицу подсистемы `about.sub`; удержание держит
   единицы и бакеты других подсистем, чьё поле `about` называет удержанную, включая удалённые по полям надгробия; бакет
   без строки держится, пока его единица неизвестна; право ресурса — P/02.5:90.
9. **Места (№ 9) — отказ с обходом:** смысл уже норма (P/03.2:592, 601–605; P/04:132); имена вызовов — «Решает
   реализация» (P/03.1 п. 1); том не открылся — `place_by: ""` в пульсе, единицы уходят по P/04. Одна фраза в P/03.2 Н3.
10. **`near` (№ 11).** P/04 Н1.3: моё значение — поле `by`, иначе мой id; значение соседа — поле `of`, иначе id соседа;
    `prefer` — И по полям, ИЛИ по списку (как `affinity.strict`), путь — шаг по полю-ссылке соседа; потребители — `01-cam`,
    `04-det`, `06-detedge`; приёмка — оба положительных примера.
11. **Блокирует уроки** (до норм и выгрузки): № 1 — `02-rec`, `04-det`, `05-detjob`, `07-auto`; № 3 — `05-detjob`, `06-detedge`, `07-auto` (курсор урока 25); прочие — как в пакете.

### Consequences
* Good, because у заказа есть держатель (контроллер), личность (права хранилища контроллера) и одна точка проверки
  строки; подсистемная логика остаётся у держателя единицы, хуков нет.
* Good, because итог и курсор — одна форма под эпохой: отсечённый держатель и прежняя строка их не подделают.
* Bad, because контроллер впервые пишет строки единиц (по объявлению) — новая обязанность платформы и правка P/02.5.
* Bad, because строка заказа двухписательная, а отказ скана без записи становится итогом единицы — отличие от
  свидетеля в двух местах.
* Bad, because правок норм много (P/02.1, P/02.4, P/02.5, P/03.2, P/03.3, P/03.4, P/03.6, P/04, P/06.1, P/06.4,
  `request-mark.md`) — одна выгрузка до старта VMS.

### Confirmation
Нормы и приёмка по пп. 1–10 на testsub/testsub2 (заказ, срок, состояние, доли, `near`) — у обеих реализаций до старта
VMS; запросы во входящих закрыты разделом «Решение» со ссылкой на этот ADR.

## Pros and Cons of the Options

### № 1 (А) воркер дверью консоли
* Bad, because у несозданной единицы нет держателя просьбы; у воркера нет личности у сторожевой (блокеры ревью).

### № 1 (Б) воркер в хранилище правом `worker.makes`
* Good, because так делал свидетель (М10B/22:107).
* Bad, because держателя просьбы к несозданной единице всё равно нет; правила строки дублируются в библиотеке воркера.

### № 1 (В) заказ декларацией, контроллер
* Good, because держатель и личность есть; проверки строки — общим правилом.
* Bad, because декларация шаблона ограничена: логика выбора — у держателя созданной единицы, а не у исполнителя заказа.

### № 3 (Б) консоль переносит фазу пульса
* Bad, because второй писатель строки и пульс как хранилище факта (М10B/21:220).
