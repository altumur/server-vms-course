# Метка просьбы: итог у каждой просьбы, кто его пишет, чей побеждает

## Context and Problem Statement
У просьбы (семейство `requests`, ADR-0012, ADR-0014) есть метка `<sub>/commands/<id>`. Держатель пишет её только для
create-only, перед вызовом цели, а после ответа дописывает итог. Агент «Сборки» нашёл в окне 3 три дыры.
- Просьбу, которую снял жнец консоли (`expired`, `unknown`), метка не видит вовсе. Тот, кто просил (pusher камеры),
  отвечает «filed» по своему сроку.
- В метке отказа есть только слово исхода, причины нет.
- Позднюю просьбу, которую начал другой экземпляр и не оставил исхода, держатель называет `expired`, как в курсе. Но
  она могла быть исполнена.

ADR-0012 и ADR-0033 этого не покрывают.

## Decision Drivers
* Тот, кто просил, читает итог в одном месте, в метке, и ничего не угадывает по своему сроку.
* Правда о том, что сделано с устройством, сильнее слова того, кто только видел конец.
* Create-only метка остаётся гарантией «не больше одного раза» (ADR-0013).

## Considered Options
* Итог только у держателя, жнец молчит, как было.
* Жнец переписывает метку своим итогом.
* У каждой просьбы итог в метке. Пишут держатель и жнец, жнец только create-only или в метку без итога, итог
  держателя побеждает.

## Decision Outcome
Выбран третий вариант.
- **Итог есть у каждой просьбы:** `performed`, `refused`, `unknown` или `expired`. У отказа и `unknown` рядом
  причина `error`, не длиннее 200 символов. Поздний ответ получает `late: true`.
- **Держатель пишет:**
  - begun create-only перед вызовом, после ответа — итог в свою метку;
  - отказ до вызова (срок, группа, эпоха) — create-only;
  - `expired` для просьбы, которую никто не начинал, create-only;
  - `unknown` для метки другого экземпляра без итога: дописывает итог в ту метку, начавший в ней остаётся.
- **Жнец консоли пишет:**
  - `expired` для просьбы, которую никто не начинал, create-only, с пометкой `ended_by: reaper`;
  - `unknown` в метку без итога, если её держатель ушёл.
  Метку, у которой уже есть итог, жнец не трогает никогда.
- **Побеждает держатель.** Его итог пишется поверх слова жнеца или другого экземпляра. Если держатель исполнил поздно,
  его итог с `late: true` побеждает и `expired`, и `unknown`: это правда о том, что сделано с устройством (решение о
  позднем ответе).
- **Закрывающий пишет по прочитанному индексу, ответ держателя — безусловно.** Тот, кто дописывает `unknown` (жнец,
  держатель в `notKnown`), пишет метку по индексу, который прочёл (`IndexPutter`: `GetAt`/`PutAt`; метки — строки
  хранилища, `RowObjects`, у файлового хранилища — сравнение под замком его каталога). Конфликт значит, что метку
  переписали: перечитать; итог появился — остановиться (ответ начавшего стоит, это и есть правда); итога нет — писать
  снова по новому индексу. Ответ держателя (`confirm`, `confirmLate`) остаётся безусловным `Put`: он единственный знает,
  что сделано с устройством. Хранилища без такой записи не бывает, записи «без индекса» нет («Архитектор» 2026-10-06:
  иначе нарушалось правило хранилища — «every write that matters passes the Index it read»).
- **Начатое не просрочено.** Метка другого экземпляра без итога даёт `unknown` и после срока. `expired` — только
  просьба, которую никто не начинал.

### Consequences
* Good, because у каждой просьбы есть итог там, где его ищут, и pusher не говорит «filed» за «просрочено».
* Good, because «не больше одного раза» держится: метку с итогом не перекрывает никто, кроме держателя.
* Bad, because каждый отказ теперь стоит записи в хранилище объектов. Проход держателя ограничен временем, так что
  длинная очередь отказов растягивается на несколько проходов.

### Confirmation
Тесты продукта: итог в метке при отказе до вызова (с причиной), при `expired`, при `unknown` после срока (начавший
сохранён), при отказе цели (причина); жнец пишет `expired` create-only с `ended_by: reaper`, дописывает `unknown` в
метку ушедшего держателя, не трогает метку с итогом; причина не длиннее 200 символов. Курс делает то же.
