# Снимки «как построено»: факты устройства из кода и прогона, сверка со спецификацией

## Context and Problem Statement

Спецификация говорит, как должно быть. Что построено на самом деле, архитектор узнаёт, только читая код реализаций или ответы прогонов. Нужен слой фактов, который строится сам, хранится в git и сверяется со спецификацией: какие ключи пишет процесс, какие флаги и пределы у него есть, какие отказы он выдаёт, какие маршруты отвечают, где в коде живёт норма.

## Decision Drivers

* Только генерация: руками снимок не правится, вывод детерминированный и сравнимый в diff.
* Факт двумя путями: из кода (что умеет) и из прогона (что делает). Расхождение двух путей — тоже находка.
* У каждого снимка есть пара в спецификации и автоматическая сверка.
* Один формат на все реализации — снимки двух реализаций сравнимы между собой без чтения кода.

## Considered Options

* Ручные записки об устройстве — устаревают с первой правки.
* Только статический разбор кода — не видит поведения.
* Статический и динамический снимок со сверкой — выбран.

## Decision Outcome

1. **Снимки** — `asbuilt/<реализация>/<модуль>/<снимок>.yaml` в репозитории реализации или в выгрузке прогона. В каждом шапка: реализация, commit, источник (`static`, `run`), версия экстрактора, пин спецификации.

| Снимок | Что | Источник | Сверка с |
|---|---|---|---|
| `keys` | префиксы ключей хранилища, которые процесс читает и пишет; операции; роль | журнал хранилища за прогон | манифесты (`writes_via`), файлы прав, граница платформы |
| `params` | флаги, переменные окружения, константы-пределы, умолчания, единицы | код и `--help` | «Флаги демона», параметры уроков, `#lim` форм |
| `refusals` | код, вид, слово отказа; где выдаётся; выдан ли в прогоне | литералы кода и ответы прогона | Н4 уроков, таблицы отказов VMS, формы проверок |
| `interface` | маршруты, методы, коды, формы тел, реально увиденные | запись раннера | OpenAPI урока |
| `topology` | процессы, сокеты, порты, юниты, связи | снимок стенда во время прогона | ARCHITECTURE, граница платформы |
| `rows` | выведенная схема строк хранилища | строки после прогона | схемы семей (ADR-0092), канон |
| `observability` | метрики, метки, события журнала и поля | `/metrics` и журналы прогона | `observability.mdc`, нормы журнала |
| `trace-map` | номер нормы → шаги приёмки → функции кода, что работали | покрытие кода по шагам | матрица прослеживания |
| `deps` | граф импортов, общие библиотеки | код | «модуль не импортирует соседа», `test_boundary` |
| `guesses` | сводка `GUESSES.md` реализаций по местам нормы | файлы реализаций | очередь неясностей норм |

2. **Сверка.** Отчёт «спецификация против построенного» по модулю: совпало, лишнее (есть в построенном, нет в спецификации), недостающее, разошлось между реализациями. Отчёт — машинный (TSV) и короткий человеческий.
3. **Доли.**
   - Статические экстракторы и сверка — «Архитектор», `tools/asbuilt/`.
   - Динамические снимки (`keys`, `interface`, `topology`, `rows`, `observability`, `refusals` из прогона, `trace-map`) — раннер, сборщиком в паспорт прогона, после серии boundary.
   - Читают «Архитектор» и ревьюеры. Модели-генераторы снимков соседей не получают, пока не будет отдельного решения: правило «линии не читают чужие реализации» в силе.
4. **Первый шаг.** `params`, `refusals` (статический) и `deps` по свидетелю c-go P/01 (`cammeta-c-go/01-store`) со сверкой против P/01 (английский источник, ADR-0121). Затем `keys` — динамический, первым из прогонов, когда раннер даст сборщик.
5. **Продукт.** `vmssubsystem` (Go, C++) — те же снимки. Их сверка с курсом даёт паритет по фактам. Порядок — после свидетелей курса.

### Consequences

* Хорошо: архитектор видит устройство без чтения кода, расхождения со спецификацией находятся сами, две реализации сравниваются по фактам.
* Плохо: экстракторы на каждый язык, сборщик в раннере, снимки надо держать свежими — каждая сборка или прогон их перестраивает.
* Предел: статический снимок не видит ветвей, которые код строит на лету. Динамический видит только пройденное прогоном. Поэтому снимков два, и их расхождение показывается.

## Дополнение (1), 2026-11-04 — ревью: review-claude (`РЕВЬЮ-ADR-0123-Claude.md`, ffce5639f; Б 0 С 5 М 3), Codex (`РЕВЬЮ-ADR-0123-Codex.md`, 5bc9dd731; Б 0 С 3 М 0); решения «Архитектора»

1. **Исходы сверки и область (С1 обоих).** Пять исходов:
   - `match`;
   - `extra` — есть в построенном, нет в спецификации;
   - `absent` — статический снимок: в коде нет;
   - `unobserved` — снимок прогона: не встретилось;
   - `differs` — значение иное.

   `unobserved` честен, только если прогон исполнил шаг, который проверяет эту норму: паспорт прогона называет исполненные цели и шаги. Иначе исход — `out_of_scope`.
   - `params` сверяется только по именам спецификации. Флаг вне спецификации — `extra`.
   - У `topology`, `observability`, `deps`, `trace-map` машинной пары пока нет: их пары в спецификации — проза или их нет. Эти снимки — справочные, без сверки, пока пара не появится (`deps` — с `test_boundary`, `trace-map` — с матрицей прослеживания, когда она будет).
2. **Паспорт и детерминизм (С2 обоих).**
   - Шапка каждого снимка: SHA реализации, версия экстрактора, пин выгрузки, а у снимков прогона — пин раннера, профиль стенда, исполненные цели.
   - На каждый вид снимка есть схема (`tools/asbuilt/schemas/`) и правила нормализации. Множества сортируются. Порты заменяются ролями. Время и PID снимаются. `rows` несёт типы полей, а не значения. Миги `topology` — по фазам, не по часам.
   - Проверка: два прогона одного входа дают одни байты.
   - Статический и снимок прогона сравниваются только при одном SHA реализации.
3. **Пин сверки (С3 Claude).** Снимок сверяется с выгрузкой на пине самой реализации, а не с текущим источником. У c-go это 56fc448, русская выгрузка. Снимки двух реализаций сравниваются между собой только при одном пине.
4. **Утечка (С4 Claude).**
   - Снимки и сверка лежат в курсе, в `asbuilt/` и в `tools/asbuilt/out/`. Выгрузка их не несёт, деревья линий и цикл MiniMax — тоже.
   - Значения окружения (`W2C_TOKEN` и прочие) и пути хоста маскируются, поиск утечек — как у выгрузки.
   - Норма не пишется «как у c-go»: снимок даёт вопрос к норме, а не её текст.
5. **Состав (С5 Claude).**
   - Добавлены `forms` (исходы реализации на пробах таблиц и трассах автоматов — мера ADR-0120 доп. (5) п. 2 (б)), `cli` (команды, подкоманды, коды выхода) и `files` (раскладка каталога данных, `FORMAT`, файлы на диске после прогона).
   - `guesses` — не снимок, а исходный файл реализации. Он уходит из перечня в реестр неясностей «Архитектора».
6. **`keys` и `writes_via` (С3 Codex).** Журнал хранилища даёт роль сокета, операцию, префикс ключа и исход, но не подсистему билета. `keys` сверяется с файлами прав. С `writes_via` он сверяется, только если журнал несёт личность билета, иначе — пометка «writes_via журналом не устанавливается». Писать ли билет в журнал хранилища — вопрос к норме P/01, его решит ревью норм урока.
7. **М Claude.**
   - (1) Отчёты сверки разбирает «Архитектор»: вопрос к норме — «Спецификации», дефект — линии. Продукт — после свидетелей.
   - (2) Пары сверки — по номерам английского источника, когда урок их получит (ADR-0121, ADR-0122 доп. (1) п. 1).
   - (3) Снимок устарел, если SHA реализации в шапке не равен её вершине; отчёт сверки это показывает.
