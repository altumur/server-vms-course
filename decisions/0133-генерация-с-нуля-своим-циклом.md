# ADR-0133. Генерация с нуля своим циклом: этапы, адаптеры для судьи, профили по видам кода, судьи — наши

## Context and Problem Statement

Класс системы: платформенная система (процесс генерации реализаций по спецификации курса).

Слово владельца 2026-11-08: «эксперимент состоит в том, чтобы доказать или опровергнуть возможность полной генерации всего с нуля по текущим спекам через свой цикл и минимакс»; «Б — пусть модель пишет всё сама»; «возможно стоит подумать о своём цикле для каждого вида кода»; «да, начни со стенда и генераторов»; «давай это утвердим».

До этого пробы MiniMax (З-15, пробы 41–45b) шли с пакетом `tools/normgen` (каркас и тесты из генераторов) и с частными привязками автора задания. «Нуль» определён как вариант Б — без пакета, вход только выгрузка (ADR-0083 доп. (155)); пробелы выгрузки для Б разобраны в доп. (156).

Что показали пробы и пилоты 2026-11-08:
* Проба 44 (P/02) встала на цели `rights`: модель не реализовала одну команду стенда (`stand.ring`), а цикл не показал причину — раннер скрыл вывод, отчёт утопил сигнал в шуме. Общая диагностика цикла (`549a037`) называет нереализованную команду без знания ответа.
* Пилот генератора 46c встал на 1 из 7: эталон нёс постоянную прозу, невыводимую из описания; 46d с примером на каждый вид прошёл 7/7, но воспроизводил наш генератор по его выводу — это не «с нуля». Проза из кода убрана (ADR-0125 доп. (10)).
* Подсказка с ответом пробе 44 была отменена владельцем: она превращает пробу в воспроизведение.

Вопрос: как устроить процесс, чтобы его итог честно доказывал или опровергал генерацию с нуля.

## Decision Drivers

* Итог должен быть доказательным: ни подсказок с ответом, ни вывода существующих генераторов и реализаций на входе.
* Вердикт даёт судья, независимый от модели: модель не сдаёт экзамен, который сама составила.
* Без адаптеров судья ничего не проверит — их порядок задаёт порядок этапов.
* Разные виды кода судятся по-разному; один движок цикла дешевле нескольких.
* Пробел спеки, который модель не может вывести, — находка эксперимента, а не повод для подсказки.

## Considered Options

* **А. Один движок цикла, профили по видам кода, поэтапный процесс; судьи наши, адаптеры пишет модель.**
* Б. Отдельный цикл на каждый вид кода.
* В. Прежний цикл с пакетом и подсказками по месту.

## Decision Outcome

Выбран вариант «А», потому что он даёт доказательный вердикт (судья независим, вход только спека) при одном движке цикла, а виды кода различаются только профилем: чем судить, что дать на вход, как делить этапы.

1. **Вход** — только выгрузка спеки по пину: нормы, формы, векторы, сценарии, описание стенда, `Platform/common` (включая `versions/go.mod`). Не даются: пакет `tools/normgen`, вывод наших генераторов, реализации (`Source/`, прежние линии), частные привязки автора задания (ADR-0083 доп. (155)). Зависимости — только stdlib и модули из `Platform/common/versions/go.mod`; кэш модулей по `go.sum` даёт стенд как среду (доп. (156) п. 3).
2. **Судьи — наши:** раннер приёмки `cammeta-acceptance`, его сценарии, нагрузка, бюджеты и среда замера; корпус вердиктов спеки. Тесты, которые модель пишет сама, — только самопроверка; вердикт ими не даётся.
3. **Модель пишет всё остальное:** продукт и **адаптеры для судьи** — драйвер стенда (`stand.*`), команду векторов (`bin/vectors`), адаптер швов (по протоколу доп. (156) п. 1), тестовые привязки боевых проверок (ADR-0130 D7).
4. **Этапы:**
   0. Подготовка (цикл, без модели): выгрузка по пину, опись обязательного из форм (команды стенда, флаги, отказы, двери, этапы), план, бюджет.
   1. Адаптеры для судьи: стенд, векторы, швы.
   2. Форма → код: флаги, отказы, двери по OpenAPI, статус и метрики, семьи; модель сама решает — код напрямую или свой генератор; судья — сборка, векторы форм, опись.
   3. Поведение по `stages.tsv` урока (у P/07 формы нет — этапы из целей раннера): выжимка нормы этапа, векторы, сценарии; судья — раннер по этапу и метки регрессий.
   4. Урок целиком и боевые свойства (ADR-0130, веха 2.4б): тестовые привязки D7, затем боевая приёмка раннером.
   5. Следующий урок — поверх своего же кода прошлых уроков.
5. **Цикл — один движок с профилями** (стенд, форма → код, поведение, боевые; затем тесты через мутации, судьи через корпус, сборка и развёртывание, интерфейс). Описание — `PROFILES.md` в репозитории цикла (`/srv/minimax-loop`, ветка `en-generic`).
6. **Разрешено циклу:** общие улучшения без знания ответа — видимость ошибок (секреты затёрты), опись «объявлено — реализовано», предполётные проверки, детектор застоя и свежий взгляд второго агента той же модели, деление этапов, бюджеты. **Запрещено:** подсказки, знающие ответ; примеры из готового кода и генераторов; правка кода модели руками.
7. **Пробел спеки** (модель не может вывести ответ) — запись в журнал пробелов пробы и строка Архитектору; чинится в норме, следующая проба идёт на исправленной выгрузке.
8. **Точка сравнения:** пробы 44 (P/02) и 45b (P/01) с пакетом (вариант А доп. (155)) доводятся до конца на общих правках цикла и общем бюджете, без подсказок.
9. **Кто что делает:** задание варианта Б — coord103-src из выгрузки (доп. (155)); пин, запуск, цикл и профили — представитель владельца; судьи, сценарии, нормы и пробелы — раннер, spec103, Архитектор по их ролям.

### Consequences

* Good, because вердикт доказателен: вход — только спека, судья — независимый.
* Good, because каждый провал раскладывается на «модель», «цикл» или «пробел спеки», и пробелы чинятся в норме для всех будущих генераций.
* Good, because один движок с профилями проще поддерживать, чем несколько циклов.
* Bad, because без пакета модель пишет заметно больше (каркас, адаптеры, тесты) — дольше и дороже, чем пробы 41–45b.
* Bad, because часть провалов будет пробелами спеки; до их починки проба стоит.
* Bad, because критерий «доказано/опровергнуто» требует бюджета, который ещё не задан (ниже — `[TODO]`).

### Confirmation

* Задание варианта Б не содержит пакета, вывода генераторов и частных привязок — проверка задания перед запуском (список из `PROFILES.md` раздел 1).
* Журнал пробы: на каждый ход — какие правки цикла действовали; ни одной подсказки с ответом.
* Журнал пробелов спеки по пробе и их судьба (норма, коммит).
* Итог по уроку: пройдены ли этапы 1–4 раннером; токены и время по этапам; сравнение с 44/45b.
* Критерий итога эксперимента: **доказано**, если P/01 (затем P/01–P/10) проходит этапы 1–4 включая боевую приёмку только по выгрузке в пределах бюджета `[TODO: бюджет на урок — токены и время, задаёт владелец]`; **опровергнуто**, если после починки найденных пробелов спеки и общих правок цикла этап не проходит в пределах того же бюджета `[TODO: число попыток/ходов на этап до вывода «опровергнуто»]`.

## Pros and Cons of the Options

### А. Один движок, профили, этапы

* Good, because доказательно и экономно.
* Bad, because профили надо доделать по видам кода постепенно.

### Б. Отдельный цикл на каждый вид кода

* Good, because каждый цикл проще сам по себе.
* Bad, because общая механика (судья, детектор застоя, учёт, видимость ошибок) копируется и расходится.

### В. Прежний цикл с пакетом и подсказками

* Good, because быстрее доходит до зелёного.
* Bad, because ничего не доказывает о генерации с нуля — это воспроизведение.
