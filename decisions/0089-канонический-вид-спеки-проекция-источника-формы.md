# Канонический вид спеки — проекция принятой спеки по правилам источника формы; его схема строится из источника

## Context and Problem Statement
Класс системы: платформенная система — установщик (урок 2) и читатели спеки (уроки 3–6, 8, 9). Стадия A, пункт A7.

ADR-0083 п. 4 решил: установщик рядом с исходным YAML пишет скомпилированный канонический вид — JCS JSON со своей
схемой и версией; остальные микромодули читают только его, строгий загрузчик YAML нужен одному установщику. Доп. (2)
п. 4: упорядоченное (поля единицы, поля таблиц) — массивами, потому что JCS сортирует ключи; на окно перехода один
наблюдаемый идентификатор версии; форма утверждается до переноса урока 2. `module-design.md` 2.2: установщик пишет его
с переноса урока 2, читатели переходят отдельной правкой, потолок строки назвать.

Формы канонического вида нет. ADR-0087 сделал источником формы спеки `*.form.yaml` урока 2. Если канонический вид
описать своей схемой руками, у спеки снова две формы, которые держат порознь.

## Decision Drivers
* читателю не нужен строгий загрузчик, слой текста и знание умолчаний (самодостаточность урока, ADR-0083 доп. (5));
* форма канонического вида не расходится с формой спеки;
* обе реализации пишут канонический вид байт в байт одинаково;
* перенос урока 2 не меняет поведения читателей.

## Considered Options
* своя схема канонического вида, написанная руками;
* канонический вид — проекция принятой спеки по правилам, заданным в источнике формы; схема строится из источника;
* канонический вид — JCS дерева загрузчика как есть;
* без канонического вида: каждый процесс прогоняет загрузчик (как сейчас).

## Decision Outcome
Выбран вариант «проекция по правилам источника»: форма записана один раз, а читатель получает полное значение без
умолчаний и порядка, которые знает только урок 2.

1. **Канонический вид** — результат построенного загрузчика на принятой спеке, после четырёх правил:
   * **умолчания подставлены**: каждый ключ с `default` в источнике есть явно;
   * **порядок — массивом**: отображение с пометкой `ordered: true` в источнике (поля единицы, поля таблиц; перечень —
     перенос урока 2) становится массивом объектов `{"name": <ключ>, …значение}`; построитель отказывает, если
     значение под `ordered` не объект или в нём есть ключ `name`;
   * **скаляры — значениями JSON по типу узла** (`integer` — число, `string` — строка) и записываются JCS (ADR-0072);
   * **пояснений нет**: комментарии и исходный текст в канонический вид не входят.
2. **Обёртка** несёт номер формы канонического вида, ревизию спеки `rev` — единственный наблюдаемый идентификатор
   версии на окно перехода — и дайджест исходных байтов. Имена полей обёртки — перенос урока 2.
3. **Схема канонического вида строится из источника формы** тем же построителем: закрыта там же, где форма; ключи с
   умолчанием обязательны; `ordered` — массив с уникальным `name`. Руками не пишется.
4. **Слово диалекта `ordered`** — решение владельца (словарь заморожен, ADR-0087 п. 2).
5. **Где.** Установщик пишет канонический вид рядом с исходным текстом спеки; строка или отдельный ключ, потолок
   размера и строка каталога — перенос урока 2 (сейчас установщик отказывает до метки, если документ не помещается —
   правило сохраняется для суммы обоих видов).
6. **Векторы `canonical`** урока 2: байты спеки → байты канонического вида; входы — принятые случаи корпуса и все спеки
   курса; обе реализации — байт в байт.
7. **Когда.** Стадия A — это решение. Перенос урока 2 (стадия B): источник с `ordered`, построенная схема, векторы;
   установщик пишет канонический вид. Читатели (уроки 3–6, 8, 9) переходят на него отдельной правкой поведения после
   переноса урока 2, каждая со своим перечнем шагов; до неё каждый процесс по-прежнему прогоняет загрузчик (М10/2 Н1.5,
   Н3). Смена формы канонического вида — новой версией с окном (ADR-0083 п. 3).

### Consequences
* Good, because читателю нужен разбор JSON, а не загрузчик YAML, слой текста и знание умолчаний.
* Good, because форма канонического вида и форма спеки — один источник; правка формы меняет обе.
* Good, because векторы держат обе реализации на одних байтах.
* Bad, because новое слово диалекта `ordered` — работа в каждом построителе.
* Bad, because строка спеки растёт: исходный текст и канонический вид вместе; потолок придётся назвать заново.
* Bad, because смена умолчания в источнике меняет канонический вид каждой спеки при следующей установке; читатели
  видят новое значение без своей правки.
* Bad, because переход читателей — шесть правок поведения после урока 2.

### Confirmation
* Векторы `canonical` проходят обе реализации байт в байт.
* `check_spec`: канонический вид каждого принятого случая корпуса и каждой спеки курса проходит построенную схему;
  мутация `default` или `ordered` в источнике меняет векторы.
* После правки читателей ни один процесс, кроме установщика, не зависит от загрузчика YAML (проверка зависимостей).

## Pros and Cons of the Options

### своя схема руками
* Good, because не зависит от построителя.
* Bad, because вторая форма спеки, которую держат порознь (довод ADR-0087).

### проекция по правилам источника
* см. Consequences.

### JCS дерева загрузчика как есть
* Good, because правил нет.
* Bad, because JCS сортирует ключи, порядок полей теряется (ADR-0083 доп. (2) п. 4).
* Bad, because читатель должен знать умолчания урока 2 — урок не самодостаточен.

### без канонического вида
* Good, because ничего не меняется.
* Bad, because каждому микромодулю нужен строгий загрузчик и слой текста — против ADR-0083 п. 4.
