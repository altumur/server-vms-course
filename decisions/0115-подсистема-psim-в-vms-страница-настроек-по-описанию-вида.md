# Подсистема psim в VMS: страница настроек строится по описанию вида

## Context and Problem Statement

Класс системы: платформенная система (подсистемы VMS на платформе) с консолью — форком consolem.

Слово владельца 2026-11-03 (через «Консоль»): «разработать новую ADR по новой подсистеме psim в рамках VMS с учетом предложений по переработке openapi — чтобы страница настроек плагинов генерировалась автоматически. Пусть заодно тоже проанализирует предложение и оценит объем переделок. отдельный вопрос — почему придется что-то менять за рамками backend?»

ADR-0071 сделал плагин psim подсистемой платформы через воркер-адаптер: `plugin.json` → манифест `psim-<plugin_id>.subsystem.yaml`, `SendCommand` — строкой `requests`, страница плагина — маршрут двери держателя. Он писался под консоль платформы, которая рисует карточку единицы по манифесту. С ADR-0112 консоль VMS — форк consolem: манифест он не читает, каждая форма в нём написана под свой вид, байты закреплены. Урока psim в VMS нет. Значит, сегодня новый плагин — это ручной экран в форке и ручные строки `mapping.tsv` под каждый вид.

Что даёт psim (`psim-sdk` `c3d9ebb`, схема не менялась с `3c61ddc`): у `object_types[]` и у плагина — `parameters` одной формы: `type`, `default`, `pattern`, `min`, `max`, `enum_values` с ключами перевода, `source` (значения из объектов другого типа), `readonly` (меняет плагин), `hidden`, `secret`, `name_key`, `description_key`; подписи — `langs/<язык>.json`. Своя страница — `provides[]` с `role: setup_ui`, одна на перечисленные виды, различает их по `?type=&id=&lang=`; сейчас страницы только показывают значения. Эмулятор psim по умолчанию рисует общий редактор по манифесту, страницу плагина — по флажку в iframe.

Команда consolem предложила «универсальную модель объектов»: `GET /kinds` с JSON Schema вида, единые `/units`, профили `implements`, раздельные «задано» и «наблюдается» (`status`), ошибки с JSON Pointer к полю, подписи с сервера, `setupUi`, переход этапами.

## Decision Drivers

* Требование владельца: страница настроек объекта плагина строится сама — без ручного экрана под плагин и без правки консоли на каждый плагин.
* Своя страница плагина — необязательная добавка, не замена общей формы.
* ADR-0071: всё, чего манифест не выражает, — новый ключ манифеста, а не обход в адаптере.
* ADR-0112: форк consolem — единственная консоль VMS; его контракт закреплён, форк меняем через команду или свой форк.
* Слово владельца «всё до первой генерации» (ADR-0103 доп. (2)): psim входит в границу первой генерации, этап «после» не планируется.
* Плагин — чужой код: его страница не получает прав консоли.

## Considered Options

1. **Только `backend`.** Каждый вид плагина отображается на существующий `Device(type=…)` форка и `UnitOption.properties` (`{key, options, default: integer}`); новые виды — строками `mapping.tsv` и экранами форка вручную.
2. **Описание вида в контракте, общая форма в форке (выбрано).** Цепочка `plugin.json` → манифест подсистемы → описание вида в контракте (`GET /kinds`, JSON Schema) → форк строит форму по схеме. Новый плагин — без правки форка и без строк `mapping.tsv`.
3. **Вся модель consolem сразу.** Все виды VMS и все ~35 операций переводятся на `/units` и профили в одном шаге.

## Decision Outcome

Выбран вариант 2, с моделью consolem частично и этапами.

### 1. Подсистема

1. Плагин psim — подсистема VMS `psim-<plugin_id>` через воркер-адаптер, как ADR-0071; новый урок `VMS/12-psim` (вписывается в перечни ADR-0090 доп. (2), (3), (5) этим ADR). Генератор `plugin.json` + `langs/` → манифест подсистемы с проверкой по `plugin.schema.json` — часть урока.
2. **Вид = `object_type` плагина**; подсистема = плагин. Каждый `object_type` — свой манифест подсистемы со ссылкой `about` на главный, как сейчас делают «второй манифест» (P/02.1); нового ключа «несколько видов в одном манифесте» нет. Параметры плагина целиком (`Configure`) — единица вида `<plugin>` с одним экземпляром.
3. Вид VMS из нескольких подсистем (камера = `cam` + `rec` + `det`) остаётся видом `backend`: описание вида строит `backend`, а не подсистема.

### 2. Манифест подсистемы: чего не хватает

Поле `unit.fields.<имя>` уже несёт `type`, `default`, `enum`, `schema` (JSON Schema lite: пределы, `pattern`), `ref`. Добавляются ключи манифеста (доля «Спецификации», P/02.1, загрузчик и векторы):

1. **`label`, `help` с ключом перевода** — `{key, text}` вместо одноязычной строки; переводы — таблица `langs/<язык>` манифеста, генератор кладёт туда `langs/*.json` плагина.
2. **`hidden`** — поле не показывается формой.
3. **`written_by: worker`** — поле пишет воркер подсистемы (`readonly` psim, обновление через `ChangeUnit`), форма показывает его только для чтения; консоль его не пишет.
4. **`secret`** — секретное поле платформы, как секретные поля `cam` под кольцом `SECRETS_KEY`; генератор кладёт `secret` psim туда. Если у поля `unit.fields` такого признака нет — ключ манифеста, как п. 1–3.
5. **`source`** psim — `ref` на семью вида другой подсистемы (`ref psim-camera/<семья>`), значения перечня форма берёт чтением этой семьи.
6. **`events`** с важностью — каталог `[{id, severity, label}]` в манифесте; сейчас у событий только `{suppress, older_epochs}`.

### 3. Контракт: что берём из предложения consolem

Берём ядро, которое и делает страницу автоматической:

1. **`GET /kinds`, `GET /kinds/{kind}`** с `ETag`: `UnitKind {kind, origin, label, parents, schema, actions, events, setupUi?}`; `schema` — JSON Schema 2020-12 подмножества манифеста с `x-label {key, text, lang}`, `x-hidden`, `x-readonly`, `x-secret`, `x-ref`, `x-source`. Описание строит `backend` из манифестов; смена манифеста — перезапуск (P/02.3), поэтому события `kinds.changed` нет: клиент перечитывает по `ETag` при переподключении.
2. **Ошибка с путём к полю**: `Problem.field` — JSON Pointer в теле, `errors[]`, `VALIDATION_FAILED` с `params.keyword`; на старых путях — имя поля, как сейчас (черновик «Консоли» Р-3 Б).
3. **Подписи с сервера**: `{key, text, lang}` по `Accept-Language`; словарь интерфейса форка главнее (Р-2 В).
4. **`/units` — только для видов `origin: plugin`** на первом этапе: `GET` с отбором, `POST`, `PATCH` (Merge Patch + `If-Match`), `DELETE`, `actions/{a}` (команды плагина — строкой `requests`), `validate`. Виды VMS (`Device(type=…)` и прочие) остаются на своих путях.
5. **`status`** — раздельно «задано» (`properties`) и «наблюдается» (`status.observed`, `conditions`) — для видов плагина сразу; для видов VMS — этапом перехода.

С поправками или позже:

6. **Профили `implements`** — понятие принимаем, на первом этапе только объявление в `UnitKind` (например, плагин камеры объявляет `vms.camera/1`); ручные экраны по профилю — этапом перехода.
7. **Перевод всех видов VMS на `/units`** (вариант 3) — не в первом шаге: этапы черновика «Консоли» Р-4 Б, один закреплённый контракт на этап. Риск переделать ~35 операций разом без выигрыша для требования владельца.

### 4. Своя страница плагина (`setup_ui`)

1. Общая форма по схеме — всегда; страница плагина — добавка, объявленная в `UnitKind.setupUi {url, kinds, mode}`.
2. **Первый этап — `mode: tab`**: форма показывает ссылку «Страница плагина», она открывается в новой вкладке. Адрес — маршрут двери держателя плагина через прокси `backend` (`/api/plugin-ui/<plugin>/…`), вход — короткий токен страницы в `#` адреса, его даёт `backend` по праву просмотра вида. Права консоли страница не получает.
3. **Второй этап — `mode: iframe`**: встраивание с `sandbox="allow-scripts allow-forms"` без `allow-same-origin`, параметры `?uid=&kind=&lang=`, `postMessage` только `ready`, `height`, `dirty`, `saved` (предложение consolem); CSP оболочки получает `frame-src` только на путь прокси. Запись страница делает своим сервером плагина, не API консоли.

### 5. Почему меняется не только `backend`

Ответ владельцу прямо: `backend` один не может сделать страницу автоматической, потому что форму рисует форк, а описание вида, по которому её рисовать, сегодня негде ни хранить, ни передать.

1. **Форк consolem.** Форма в нём написана под каждый вид (сотни сравнений вида в коде, `LB_RU`, `WIZ`, `tabsFor`), байты закреплены. Общей формы по схеме в форке нет. Без неё любой новый вид — правка форка. Построитель формы по схеме пишется **один раз**, дальше новые плагины его не трогают.
2. **Контракт форка.** `DeviceType` и `TreeNode.kind` — закрытые перечисления, путей `/kinds` нет, `Problem.field` без указателя. Новый вид в закрытое перечисление не войдёт; описание вида контракт не передаёт. Меняются `api/openapi.json`, тестовый сервер, тесты.
3. **Манифест подсистемы и загрузчик (платформа).** Нет перевода подписей, `hidden`, поля «пишет воркер», каталога событий. Без этих ключей генератор кодировал бы их в адаптере — ADR-0071 это запрещает, и описание вида было бы неполным.
4. **Адаптер psim** — его ещё нет совсем: это новый урок.

**Можно ли только `backend`.** Да — вариант 1, ценой: типы и перечни сжимаются в `integer` `UnitOption`, подписи и подсказки теряются, `source`, `hidden`, `readonly` не выражаются, и на каждый плагин — ручные строки `mapping.tsv` и ручной экран форка. Это ровно то, от чего владелец хочет уйти, поэтому вариант 1 отклонён.

### 6. Оценка объёма переделок

| Слой | Что | Объём |
|---|---|---|
| Манифест и загрузчик (P/02.1, «Спецификация») | 5 ключей п. 2, схема, векторы, исходы загрузчика | средний: ~1 раздел норм, ~20 векторов |
| Адаптер psim (`VMS/12-psim`, «Спецификация VMS») | новый урок: генератор, воркер (`ListObjects`, `ChangeUnit`, `SendCommand`, `Configure`), приёмка на `security_controller` + эмулятор | большой: урок целиком |
| `backend` (V/11, `mapping.tsv`) | открытые виды по правилу вместо строк, `GET /kinds` из манифестов, `/units` для `origin: plugin`, прокси страницы, `Problem.field` указателем | средний–большой: 2–3 раздела V/11, правило в `mapping.tsv` вместо строк на вид |
| Форк consolem и модуль консоли | построитель формы по JSON Schema, список видов, ошибки у поля, ссылка «Страница плагина»; модуль платформы — без правок | средний: один компонент форка, его тесты; правка у команды или в нашем форке |
| Контракт форка (`api/openapi.json`, тестовый сервер, тесты) | `/kinds`, `/units` (виды плагина), `Problem.field`, `label`, `setupUi`; новое закрепление контракта | средний: ~10 операций, наборы тестового сервера |
| Нормы и приёмка | V/11.2 судьбы новых операций, профиль тестов, сценарии приёмки psim, CSP оболочки (этап 2) | средний |

Порядок: манифест (п. 2) → урок `VMS/12-psim` → `backend` и контракт этапа 1 → форк этапа 1 → приёмка; встраивание страницы и перевод видов VMS — следующими закреплениями контракта, до первой генерации.

### Consequences

* Хорошо, потому что новый плагин psim получает страницу настроек без правки форка и без строк `mapping.tsv`: достаточно `plugin.json` и `langs/`.
* Хорошо, потому что общая форма по схеме пригодится и видам VMS при переходе на `/units`.
* Плохо, потому что правка затрагивает четыре слоя, а не один; форк и контракт меняются у команды consolem или в нашем форке, это дольше.
* Плохо, потому что граница первой генерации растёт на урок psim и этап 1 контракта.
* Нейтрально: решения Р-1…Р-6 черновика «Консоли» ждут владельца; этот ADR опирается на рекомендации Р-1 А, Р-2 В, Р-3 Б, Р-4 Б, Р-6 А и решает Р-5 (п. 4). Если владелец выберет иначе — дополнение.

### Confirmation

* Приёмка урока `VMS/12-psim`: `security_controller` и `camera` psim-sdk без правок плагинов; форма CONTROLLER и SENSOR строится из `GET /kinds` — перечень `mode`, мультиселект `enum_tags`, перечень `cameras` из вида `CAM` другого плагина, `readonly` только для чтения, `hidden` не виден.
* Тест форка: новый вид с неизвестным форку `kind` получает форму без правки кода форка.
* Ошибка `VALIDATION_FAILED` с указателем ложится под своё поле формы.
* Страница плагина этапа 1 открывается во вкладке и не получает токена консоли.

## Дополнение (1), 2026-11-03 — ревью, review-claude (`decisions/inbox/ревью/РЕВЬЮ-ADR-0115-Claude.md`; решения «Архитектора»)

1. **Б1.** Страница плагина — **другое происхождение**, не путь консоли: адрес двери держателя плагина (ADR-0071), а не прокси `/api/plugin-ui/` под происхождением форка. Иначе скрипт плагина ходил бы в `/api/*` с куки `session` форка правами смотрящего. `UnitKind.setupUi.url` — абсолютный адрес двери, его даёт `backend`; вход — короткий токен страницы в `#` адреса, право — просмотр вида. Прокси и новой связи `backend` (V/11.1 Н1.2а) нет — М1 снят этим. Ответ двери на страницу несёт CSP `sandbox allow-scripts allow-forms`.
2. **С1.** Один манифест на плагин, как ADR-0071: корневой `object_type` — `unit` подсистемы, прочие — таблицы той же подсистемы; один процесс адаптера на плагин. Описание вида `backend` строит одинаково из `unit` и из таблиц. Пп. 1.2 ADR «свой манифест на `object_type`» заменяется этим.
3. **С2.** Установка плагина меняет `/kinds` без перезапуска `backend`: `ETag` — ревизия каталога манифестов, событие `kinds.changed` в потоке событий форка; клиент перечитывает `/kinds` по нему и при переподключении. П. 3.1 «события `kinds.changed` нет» заменяется этим.
4. **С3.** Параметры страницы — свои у psim: `?type=&id=&lang=` (psim-sdk), не `?uid=&kind=`.
5. **С4.** Подписи — существующими `display.fields`, `field_help` с формой `{key, text}` вместо одноязычной строки, без новых ключей `label`, `help`; переводы — таблица `langs/<язык>` манифеста. `secret` — ключ поля `secret: true` в `unit.fields` и полях таблиц (P/02.1); если признак уже есть — это он.
6. **М.** Ключей манифеста шесть: форма подписей, `langs`, `hidden`, `written_by: worker`, `secret`, каталог `events`. `source` — право чтения чужой семьи: форма показывает перечень, только если у смотрящего есть просмотр вида-источника; иначе поле — id без подписи.

## Дополнение (2), 2026-11-03 — второе ревью (0), «Спецификация» (`decisions/inbox/ревью/РЕВЬЮ-ADR-0115-Спецификация.md`), и ревью доп. (1), review-claude (`decisions/inbox/ревью/РЕВЬЮ-ADR-0115-доп-1-Claude.md`); решения «Архитектора»

Цель — меньше правки платформы: всё, что манифест уже выражает, берётся как есть.

1. **Б1 (Спецификация).** `readonly` psim — `unit.state.<имя>` (P/03.6 Н1.7): воркер строк своих единиц не пишет (P/02.5 Н1.4), а `state` уже идёт в ответе консоли. Ключа `written_by: worker` нет; форма показывает `state` только для чтения.
2. **Б2.** Один манифест на плагин (доп. (1) п. 2). Имя подсистемы — `psim-<plugin_id>` в нижнем регистре по грамматике `[a-z][a-z0-9_-]{0,31}`; не влезает — отказ генератора. Прочие `object_type` — таблицы этой подсистемы, родитель — `ref` на семью родителя, не `about`. Слов «второй манифест» в ADR нет.
3. **С1.** Подписи — существующие `display.fields`, `field_help`, `options`, `kinds`, `unit(s)` со значением `строка | {key, text}`. Переводы — новый ключ `display.langs: {<язык>: {<key>: <text>}}`; генератор кладёт туда `langs/*.json`.
4. **С2.** Секрет — существующее правило имени `*_secret`: генератор переименует `x` → `x_secret`; секрет не строкой — отказ генератора, предел. Ключа `secret: true` нет (доп. (1) п. 5 в этой части заменяется).
5. **С3.** Мультивыбор с `source` — список ссылок: `items.ref` у поля-списка; новый ключ P/02.1, загрузчик судит `ref` у каждого элемента.

## Дополнение (16), 2026-11-03 — ревью норм VMS/12-psim, review-claude (`РЕВЬЮ-ADR-0115-нормы-VMS-Claude.md`); решения «Архитектора»

1. **Б1. Заголовки на двери страницы.** Дверь адаптера перед пересылкой плагину снимает `Cookie` и `Authorization` запроса: иначе кука консоли `w2c_token` (токен домена человека, `Path=/`, хост без порта) ушла бы чужому коду. Своя кука страницы — `psim_<plugin_id>`, `Path=/<маршрут плагина>/`; куки другого плагина дверь не пересылает.
2. **С3. Право на страницу.** Страница пишет настройки сервером плагина, поэтому токен страницы — по праву `edit` вида, не `view`. Человек с одним `view` ссылки «Страница плагина» не получает — предел. Доп. (1) п. 1 «право — просмотр вида» заменяется этим.
3. **С1, С2 и М** — правки норм урока без решения: владелец типа — только включённый плагин (или явный `--owner` установки); установка ждёт новую ревизию через `/manifest/<sub>/source` после `put` манифеста и после сборки `backend`, прежде чем писать строку `plugin`.
