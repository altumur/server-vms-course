# Вопросы М11/7 «Токены воркеров через агента»

Свидетели — курс (заморожен) и продукт. Взято без вопроса (ADR-0074 доп. (5), C4, C6, C6b): путь воркер → местная дверь
агента → `POST /api/tokens/<член>/<sub>/<вид>` подписью агента (урок 3 Н1.4) → ответ, запечатанный члену; роль
удостоверяет агент по личности процесса, не по телу; очереди ответов нет; токен — только в памяти воркера; `sub` токена —
член-заявитель, `aud` — список кластеров; утверждения формирует подписант из записи назначения (урок 6), топологии
(урок 4) и общего документа (урок 11); через ретранслятор — байт в байт, ретранслятор не автор (урок 4); формат токена и
проверка — урок 2 Н1.6, Н3 `token`. Ниже — развилки.

## 1. Местная дверь агента

Курс: unix-сокет роли `$TOKEN_REQUESTS_DIR/<роль>/tokens.sock`, маршрут `/tokens/<вид>` (подсистему ищет по виду, виды
уникальны в домене). Продукт: TCP с mTLS по сертификату роли (`AGENT_TOKENS`), маршрут `/tokens/<sub>/<вид>`. ADR
допускает оба способа удостоверить роль (ADR-0031, ADR-0075).

**Рекомендация:** маршрут `POST /tokens/<sub>/<вид>` (продукт: подсистема в пути, не в догадке); роль — личность
соединения одним из двух способов М10/11 (сокет роли на коробке, сертификат роли по ADR-0075 в кластере) — как у других
дверей процессов; виды всё равно уникальны в домене (курс: отказ загрузки каталога), потому что `kind` — утверждение,
которое читает получатель. Тело `{request_id, ref, by?}`.

## 2. Ответ держателя и запечатывание

Курс запечатывает только поле `token` конвертом `x25519:v1` к ключу печати члена с AAD пути, `request_id`, `exp`.
Продукт: `{sealed: "m1.<hex>.<b64>"}`, внутри `{request_id, token, exp}`, запрос в AAD не входит.

**Рекомендация:** `{sealed: <m1 урока 3 Н1.5>}`, внутри `{request_id, token, exp}`; агент проверяет `request_id` и
`exp > now` (курс) и отдаёт исходному соединению `{request_id, token, exp}`. Привязка к запросу — через `request_id`
внутри конверта.

## 3. Порядок и строгость проверок подписанта

Курс строже (решение C6b это принимает): нечитаемое назначение — 403 (продукт падает в `unit` или 404, ошибка
хранилища — 500), пустая или непринятая аудитория — 403, `by` вне `scenario` — 400, все члены ссылок — приняты,
единица заявлена ровно одним членом.

**Рекомендация — курс по строгости**, порядок проверок нормой: подпись и член (урок 3) → форма тела → вид есть и роль в
`grant` → `by` только у `scenario` → область (placement → unit, scenario) → аудитория непуста и из принятых членов.
Слова отказов — закрытым списком, как в уроках 2 и 5.

## 4. Пределы

Тело — 16 KiB у курса, 4 KiB у продукта; `request_id` ≤ 64 — только у продукта.

**Рекомендация:** 4 KiB; `request_id` 1–64 знака `[A-Za-z0-9_-]`.

## 5. Форма `domain.tokens`

Расходятся: повтор имени в `claims` (продукт — отказ), `scenario.items` — путь (курс) или одно имя (продукт), регистр путей
полей (продукт — только строчные), проверка `domain.ref` у `unit`/`scenario` (только курс).

**Рекомендация:** повтор в `claims` — отказ; `items` — одно имя; пути полей `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`;
`domain.ref` для `unit`/`scenario` обязателен (курс). Случаи загрузки — в корпус урока 2 (`m57_tokens_*`), как книги урока 5.
Слова `target_fields`/`caller`: `cluster`, `origin`, `copies` — поля записи назначения, `centre`, `star_centre`,
`poll_home` — вычисляются по топологии (урок 4 Н1.2 `home`), полями единиц не бывают (долг «дыры потребителя» записки
закрывается этим определением).

## 6. Вид у токенов людей

Курс пишет людям `kind: "person"`, продукт — без `kind`; проверка видов у получателя опирается на `kind`.

**Рекомендация:** `kind` есть у каждого токена домена: `person` у людей (урок 9), вид спеки у воркеров; токен без `kind` —
`bad_claims` (урок 2 Н3 шаг 5 получает это поле). Продукт — долг.

## 7. Кто проверяет на стенде

Ни у курса, ни у продукта двери платформы, проверяющей виды `testsub*`, нет; токены проверяет код VMS.

**Рекомендация:** приёмка урока 7 — две части. (а) Чистая функция `issue` (вход: вид спеки, роль, член, `ref`, `by`,
назначения, топология, единицы членов, общий документ, `now` → утверждения или слово отказа) — вся логика областей.
(б) Стенд: дверь `token <кластер> <роль> <запрос>` — раннер обращается к местной двери агента с личностью роли и
получает `{request_id, token, exp}` или отказ; токен затем проверяет команда `token` урока 2 по набору кластера-получателя
(`aud`). Учебной двери-получателя в `testsub*` не вводить.

## 8. Строки реестра

```text
М11_Domain/07	acceptance-entry	inputs	входы команды issue (вид спеки, назначения, топология, единицы членов, общий документ); проверяется по README приёмки
М11_Domain/07	scenarios-format	own	стенд нескольких кластеров с местной дверью агента (дверь token <кластер> <роль>) и векторы issue; проверяется по README приёмки
```

Если п. 1–8 — «да», пишу урок по ним.

## Решение
2026-10-17, «Архитектор». П. 1–8 — да, как рекомендовано. Одно дополнение — `aud` у получателя (обещано уроком 2):
урок 7 нормирует, что получатель отказывает токену, в `aud` которого нет его кластера (слово отказа из закрытого списка
урока 2); команда `token` урока 2 получает во входе кластер-получатель, и стенд п. 7(б) проверяет обе стороны —
токен принят кластером из `aud` и отвергнут кластером вне `aud`. Строки реестра — в навыке.
