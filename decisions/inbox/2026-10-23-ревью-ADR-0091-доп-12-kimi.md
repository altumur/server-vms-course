# Ревью ADR-0091 доп. (12) — запись в каталоге домена: исполнители назначения в виде

Срез: `2e1a98a6a`. Дата: 2026-10-23. Охват: `decisions/0091-механизмы-платформы-по-запросам-vms.md` доп. (12)
пп. 1–4; запрос `decisions/inbox/2026-10-23-запрос-vms-запись-в-домене.md`; сверка с `Platform/08-domain/spec/
08.1-domain.norms.md` (Н1.2, Н1.4, Н1.6, Н3 шаги 4–6, Н4), `08.6-domain.norms.md` (Н1.1, Н1.3 find), `Platform/
02-installer/spec/02.5-installer.norms.md` (Н1.3, Н1.4, Н3 шаг 3), `Platform/05-resource/spec/05-resource.norms.md`
(Н1.1 door, Н2 «Допуск к дверям ресурса», Н4), `Platform/common/data/catalog.tsv:84`.

## Вывод

С правками: три существенные находки (теневой отчёт при п. 2, поиск `ref` при двух исполнителях после п. 1,
механизм прав п. 3) и три мелкие. Обхода спора через самоназначение п. 1 не открывает — исполнители берутся из
назначения, которое пишет только процесс `domain` по двери оператора.

## Проверено без находок

1. **П. 1 — обход спора («член объявил себя исполнителем») не открывается.** Исполнители `ref` — `cluster` и
   `copies` назначения `domain/placement/<sub>/<ref>` (P/08.6 Н1.1 `executors`, `08.6-domain.norms.md:62`); писатель
   назначения — только процесс `domain` по двери Н2 консоли домена, агенту запрещено (`08.6-domain.norms.md:59`,
   `02.5-installer.norms.md` Н1.4а). Член не может сделать себя исполнителем: без назначения два заявителя `ref` —
   `contested` как прежде (приёмка п. 4 «та же пара вне назначения — contested» этот случай и фиксирует).
2. **П. 1 — формулировка сходится с теневым отчётом в основном случае.** «Кроме случая, когда все они — исполнители
   назначения этого `ref`» — то же условие, что `conflict` Н1.6 («действующие заявки `ref` у двух членов, не все из
   которых — исполнители назначения `ref`», `08.1-domain.norms.md:180–181`); правка Н3 шага 4 (`:427`) по этому
   правилу снимает расхождение из запроса. `complete` (Н1.4: все члены `ok` ∧ `contested` пуст) при законном
   размещении `cluster` + `copies` становится `true` — то, что просит запрос.
3. **П. 2 — сторона вида закрыта без потерь для остальных.** Строка без значения `domain.ref` (нет поля или `""`)
   не попадает в `units` — согласовано с формой `units.<имя>[].ref` «обязателен, не из `\"\"`» (`:266`) и не ломает
   существующее `no_ref` Н1.4 (`:143`: элемент пульса без строки шарда не входит и не заявляет). «В отчёт члена
   пульс такой единицы идёт как прежде» — согласовано с P/09.1 Н1.2 (`member_objects` не зависит от `domain.ref`).
   Молчаливая невидимость такой единицы в домене — запрошенное поведение (запрос: «запись `7` кластера `site` без
   `ref` в виде отсутствует и вид не портит»), принимается как решение владельца.

## Находки

### Существенные

1. **П. 2 не закрывает теневой отчёт: заявка с пустым `ref` — `unmanaged` навсегда.** ADR-0091 доп. (12) п. 2
   говорит только о виде. Теневой отчёт строит заявку так: «`ref` — по `id` единицы из шарда снимка этого члена;
   элемент без `ref` (нет строки в шарде) — заявки нет» (Н1.6 `claim`, `08.1-domain.norms.md:167–169`). Строка в
   шарде **есть**, значения поля `domain.ref` нет — родительское «нет строки» этот случай не покрывает, по букве
   нормы заявка получает `ref` = `""` (или не определён). Назначения для `""` не бывает (грамматика `ref` — `named`,
   P/08.6 Н1.1:65), значит это `unmanaged` («действующая заявка `ref` без назначения», `:179`), а `exit`: `may_write`
   ⟺ `unmanaged == 0` ∧ … (`:200`) — домен никогда не поднимет `may_write`, пока у подсистемы есть хоть одна запись
   без `ref` — то есть всегда, раз VMS держит такие записи штатно («запись без `ref` — только своего кластера»).
   Вид при этом `complete: true` — вид и отчёт расходятся ровно там, где доп. (12) их мирит. **Рекомендация:**
   дополнить п. 2 стороной отчёта: элемент пульса, чья строка шарда без значения `domain.ref`, заявки не даёт (как
   элемент без строки), либо назвать отдельный вид находки.
2. **П. 1 делает законным два члена с одним `ref` в `units` — поиск дверей правки не определён.** P/08.6 Н1.3
   `find`: «`ref` → член и id по виду домена (глава 8.1 Н1.4); `?cluster=` — только этот член»
   (`08.6-domain.norms.md:105`); отказы знают `contested` → 503 и «не найден» → 503/404 (`:108–111`), но не случай
   «`ref` найден у двух членов» — раньше он был невозможен (такой `ref` уходил в `contested` и из `units`). После
   п. 1 основная и резервная записи одного `ref` у `cluster` и `copies` обе в `units`: `PUT/DELETE
   /domain/<sub>/<rows>/<ref>` без `?cluster=` находит две единицы, и норма не выбирает члена. Приёмка п. 4 случай
   правки двойной записи не покрывает. **Рекомендация:** нормировать выбор — при двух исполнителях требовать
   `?cluster=` (иначе отказ 409/503 с именами членов) или брать `cluster` назначения — и строку в Н4 P/08.1/P/08.6.
3. **П. 3 называет механизм строк для объекта: «без объявления — 403» не исполнить действующими нормами.**
   `domain/reached` — **объект** (`catalog.tsv:84`, kind=object). `worker.reads` (P/02.5 Н1.4) выводится в образцы
   файла прав **строк** (`02.5-installer.norms.md:33`, Н3 шаг 3 `:133`); объекты файлом прав не покрыты — «объект
   `domain/view` … — дверью объектов P/05, не строкой прав» (`:87`). Дверь объектов допускает к чтению
   `/v1/objects` «любая роль с комплектом (P/02.4 Н1.6)» (`05-resource.norms.md:720`) и даёт 403 только ключу вне
   семей двери (`:806`); семья `domain/*` целиком в `PLATFORM_DOOR` (`:57–58`). То есть воркер (и любая роль) читает
   `domain/reached` уже сегодня без всякого объявления, а 403 «без объявления» взять неоткуда — ни дверь, ни SDK по
   нормам объявление `worker.reads` при чтении объекта не проверяют. Аналогия «как копии книг» не переносится:
   копии книг (`domain/placed/<sub>/`, `catalog.tsv:97`) — строки, там `worker.reads` работает. **Рекомендация:**
   назвать механизм (проверка читателей объекта у двери ресурса по каталогу, либо перенос `domain/reached` в
   строку) или поправить приёмку п. 4 — убрать «без объявления — 403».

### Мелкие

4. **П. 1: «вид и теневой отчёт одного прохода не расходятся» — слишком сильно.** Входы разные: вид считает по
   `units` (пульсы **и шарды**, включая `configured`, Н1.3), отчёт — по действующим заявкам (`live`, Н1.6 `claim`).
   Контрпример: член вне исполнителей держит `configured`-единицу с этим `ref` (строка шарда без живого пульса) —
   вид: три члена дают `ref`, не все исполнители → `contested`, `complete: false`; отчёт: действующей заявки нет →
   находки нет. Расхождение было и до п. 1, но фраза доп. (12) его отрицает. **Рекомендация:** смягчить до
   «одно правило для действующих заявок» или явно принять расхождение на не-живых единицах.
5. **Вектор `10-*` P/08.1 фиксирует прежнее поведение вида.** `08.1-domain.norms.md:486`: «назначение с `copies`:
   заявки исполнителей из `cluster` и `copies` — не `conflict` (вид — `contested`, глава вида не меняет)». После
   правки норм по п. 1 приписка про вид устаревает. **Рекомендация:** при правке норм обновить вектор и приписку.
6. **Шаг 4 Н3 теперь нуждается в назначениях, которые читаются на шаге 6.** Сейчас назначения читает только
   теневой отчёт (Н3 шаг 6, `08.1-domain.norms.md:429`); правило п. 1 на шаге 4 требует их раньше.
   **Рекомендация:** при правке норм явно перенести чтение назначений до шага 4 или в шаг 3.

## Счёт по серьёзности

Блокеров: 0. Существенных: 3 (№ 1–3). Мелких: 3 (№ 4–6).

## Самые важные

1. № 1 — без поправки к `claim` теневого отчёта штатные записи VMS без `ref` навсегда держат `may_write: false`.
2. № 2 — правка единицы с резервом в другом кластере через домен не определена: два члена с одним `ref` в `units`.
3. № 3 — права п. 3 не работают как написано: объявление `worker.reads` объекту ничего не даёт, а обещанный 403
   без объявления противоречит допуску двери объектов P/05.
