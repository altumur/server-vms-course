## R91-D24-01 — существенная: incomplete не определяет epoch_is уже полученного события при сбое чтения эпохи

**Место и точная цитата.** `decisions/0091-механизмы-платформы-по-запросам-vms.md:726`–729:
«подсистема, чьих строк эпох нет в `worker.reads`, — `epoch_is: unknown`, … `complete` не меняется;
объявленную эпоху не удалось прочесть — `incomplete` (как неответ ресурса)».
Следующая строка требует свежего чтения для доказательства, кэш разрешён только для отбора.

**Первичное основание.** Новое решение разделяет необъявленную и объявленную, но непрочитанную эпоху;
в поручении это прямо названо «unknown только для необъявленной эпохи». Прежний п. 3 доп. (23),
разрешавший unknown также при непрочитанном, **заменён**, а не дополнен ещё одним флагом.
При этом сохраняемый договор слияния требует разметить строки ответа:

- `Platform/06-console/spec/06.4-console.norms.md:252`–256 — сравнение с `current_epochs`, разметка,
  возврат строк прежней эпохи с fenced вместо их отбрасывания; пропускается строка не по форме;
- `Platform/06-console/spec/06-console.api.openapi.yaml:6342`–6350 — у **каждой** ConsoleEventRow обязательны
  `epoch_is` и `fenced`; `complete=false` этой обязательности не отменяет;
- `Platform/05-resource/spec/05-resource.norms.md:151` и 195 — current / fenced / earlier-run и соответствие
  fenced; доп. (24) добавляет unknown, но относит его к другой ветви;
- incomplete сейчас имеет адрес **сервера** и причины его неответа (`05-resource.norms.md:155`,
  `06-console.api.openapi.yaml:6382`–6386). Отдельный неответ чтения строки эпохи не назван таким адресом.

**Минимальный допустимый контрпример.** Воркер объявил `testsub/epoch/` в `worker.reads`, начал первый проход,
кэша эпох ещё нет. Живой ресурс `s1` успешно вернул одну корректную строку события для `testsub/c1`, эпоха события **7**.
Все запрошенные ресурсы ответили; чтение `testsub/epoch/c1` из хранилища завершилось ошибкой/таймаутом.
Это ровно разрешённая новая ветвь п. 4, не запрещённый вход и не отсутствие объявления права.

Те же наблюдённые входы возможны, когда настоящая эпоха равна **7**, и когда она уже **8**. В первом случае
разметка по норме — current, во втором при политике fenced — fenced. Выбрать одну из них без чтения нельзя;
earlier-run тоже требует результата сравнения. Ветвь unknown в новой формулировке дана только необъявленной эпохе.
Итог `complete=false` необходим, но не отвечает, **что делать с полученной строкой**:

1. вернуть её с unknown — распространить unknown на случай, для которого это разрешение снято;
2. вернуть без epoch_is — нарушить обязательную форму строки;
3. назначить current/fenced — угадать результат неудавшегося чтения;
4. не вернуть событие или весь ответ `s1` — добавить не названное решение об отборе; ресурс-то ответил,
   его строка правильная, а связь неответа эпохи с причиной/ключом incomplete не установлена.

Не требуется выбирать правильную эпоху без чтения. Требуется **определить отказ/неполный результат**, когда прочесть её
не удалось. Даже если под «как неответ ресурса» подразумевалось отбрасывание зависимых событий, нужно назвать именно
такой исход и его область: одна unit, вся подсистема или весь ответ ресурса. Иначе при двух подсистемах в одном ответе
один автор отбросит только зависимые строки, другой — также события с успешно прочитанными эпохами.

**Последствие и серьёзность.** Автору общего договора придётся самостоятельно выбирать видимые строки и разметку
неполного ответа либо расширить правило unknown вопреки названной границе. Это незаданный исход слияния при
неподтверждённом чтении, **существенная** находка. Одну причину не разделяю на отдельные пункты о строке и ключе incomplete.
Пункты чеклиста о различении неизвестного и определённом исходе частичной операции — строки 45–55 и 85–91.

**Рекомендация — вопрос «Архитектору».** Явно задать пару «исход события + причина неполноты».
Наименьшее расширение — unknown также для объявленной, но непрочитанной эпохи, **с `complete=false`** и адресованной
причиной чтения; unknown без неполноты остаётся случаем необъявленной эпохи. Доказательством ни тот, ни другой не служит.
Если владелец сохраняет unknown исключительно для необъявленной эпохи, вместо этого явно задать исключение зависимых
строк и область причины incomplete. Не подменять неответ хранилища неответом исправного `s1` по умолчанию.
Векторы: ресурс ответил, объявленная эпоха не прочитана, кэша нет; затем тот же случай со старым кэшем и двумя
подсистемами в одном ответе.

**Происхождение.** Наведено заменой ветви в доп. (24), коммит
`261f5fa1f9cce10c8cf981a8c0a1e1197ae65441`. До него доп. (23) п. 3 прямо давало unknown и для «не прочёл»;
после замены определён incomplete, но исход строки этой ветви не указан. До/после сохранены
в `changed-epoch-rule-provenance.json`. Это не переоткрытие своей находки о префиксе или Promise.

## Остальные уточнения

**Карточки оболочки.** П. 2 теперь прямо включает `streamaccounts:local`, что соответствует ref оболочки и
`addCard(prefix, render)` P/07 Н1.5. Ограничение прежнего текста «карточка единицы» больше не исключает нужный VMS
случай. Смена выбора/закрытие/смена страницы по доп. (22) сохраняются. Новые событие и опция select ещё не реализованы
в опубликованных байтах; это не отрицательный результат их jsdom-приёмки. Имя вкладки нужно перенести как id
регистрации `addTab`, где отдельно существуют `id` и `label`; «имя как его даёт addTab» так прочитано, не как новая
переводимая подпись. П. 6 назначает проверку `shell.may_not` тесту страницы, а не HTTP-TSV.

**Digest.** П. 3 теперь явно закрепляет worker-форму **в строке и в метке** у цели с `requests.key`, для обоих писателей;
у двери без такого ключа остаётся client. Тем самым больше не нужно угадывать, каким digest сверять повтор после settle.
Метка по-прежнему копирует digest строки, как в `request-mark.md:84`–98; формулировка не прочитана как назначение
двери нового права начинать исполнение или писать исход вместо держателя.
В новой конечной модели два писателя одного тела получили одинаковый digest, а после удаления строки он сохранился
в метке; иная unit либо иное тело отвергнуты. Внесение третьего правила в README названо пп. 3, 6.

**Чтение для доказательства.** Разделение «кэш — отбор; новое чтение — доказательство» снимает использование старого
current как достаточного основания для действия. Успешное новое чтение неизменной строки эпохи не требует, чтобы
она пульсировала каждые LOST_AFTER: возраст **версии** по observation не обнуляется повторным чтением, а эпоха растёт
при взятии единицы, не по таймеру (P/03.2 Н1.5). Ни атомарного снимка событий и эпох, ни неизменности эпохи после
чтения это решение не обещает. Указанный выше незаданный исход — именно **неуспешного** чтения.
