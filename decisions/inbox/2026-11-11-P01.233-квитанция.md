## Попытка 2 (после отказа judge `17f5fd748`)

Отказ: Б1 пересмотрен Архитектором (note 2026-11-11T22:12:38Z) — форма над байтами raft не гарантирует исхода (сжатие

API. По вопросу run о пути посредника — решение 2026-11-11T22:18:32Z, вариант (а): флаг `-api-bind`. F2 — склейки в
истории. Что сделано:

1. **Флаг `-api-bind`** (как `-raft-bind`): строка `forms/daemon-flags.tsv` (`addr`, default `=-api`, `daemon`, без `bad`),
   назначение в N1.3 «Flag purposes», новое требование **P/01.3-R409** — демон слушает служебные двери на `-api-bind`,
   `-api` остаётся адресом для партнёров (`members`, `leader`, присоединение).
2. **Стенд группы** (A3 «Store group stand», en+ru): `{api@<id>}` — адрес посредника API раннера; запуск члена —
   `-api {api@<id>}` и `-api-bind <свой порт>`; новый пункт «API proxy» (mTLS с обеих сторон: вызывающему — лист `<id>`,
   члену — лист того же вызывающего из комплектов; по умолчанию пропускает всё); `@tls … api@<id>` — к своему порту
   (`-api-bind`), не к посреднику.
3. **Директива `@cut store@<id> answer`** вместо `… answers after <N>` — в A3 и в строке словаря
   `Platform/common/acceptance/README.md:98` (+ru). Действует с шага до `@mend store@<id>`: каждый `POST /v1/write`
   проходит к члену, посредник дожидается полного ответа, не отдаёт его и закрывает соединение; прочие запросы проходят.
   Почему «до `@mend`», а не один запрос: решение 22:12:38Z называет исход двери «503 ambiguous» и `@mend`; дверь с `id`
   повторяет у других голосующих (R251, R252), и при разовом удержании повтор получил бы ответ `again` (200) — исход
   двери не был бы определён. При удержании до `@mend` все пути к лидеру идут через его посредник (`leader`, `members`
   — `{api@s1}`), исход 503 `ambiguous` определён.
   Архитектор подтвердил эту семантику уточнением 2026-11-11T22:27:23Z (note задачи): разовое удержание с `@oneof` не нужно;
   для P01.201 — удержание каждого `POST /v1/write` до `@mend`.
4. **Сц. 32–34 переписаны**: `@cut store@s1 answer` у лидера, запись `{"n":"1"}`; 503 `ambiguous`; до `@mend` чтение у s1 —
   версия записи; после `@mend` повтор по `id` — `again` (32: d1, s2; 33: s2, s3); 34 — повтор без `id` с `cas: ""` — 409

## Долги и открытое

1. Раннер: посредник API на `{api@<id>}` с mTLS и директива `@cut store@<id> answer`; член стенда — с `-api-bind`. Пока их нет,
   сц. 32–34 не исполнены (`not_executed`), а не зелёные.
2. Указатель (P01.200): новые R399–R408 (01.3), R401 (01.1), R143 (01.2) — в строки тем `sockets`, `check_order`, `format`,
   `metrics`, `floor`, `leader_wait`, `group_stand` и «See also».
3. Запрет повтора записи без `id` дверью (R252, R328) снаружи не наблюдаем: повтор записи с `cas` второго следа не
   оставляет. Остаётся чтением.
4. Режим каталога (Б3): у стенда нет директивы, которая запускает каталог одного режима в другом, поэтому это чтение.
5. Заголовок раздела A3 «The store group (sc. 07, 17, 18, 25–29, 31)» не тронут: его якорь адресуют 20 строк
   `history-3.tsv`. Сц. 31–34 названы в тексте раздела.
6. Frictionless-схема `rights-checks.tsv.schema.json`: описание `id` «rc-<check>» не учитывает вторую строку проверки
   `forwarding_untrusted`. Шапка формы это оговаривает, схема — правка Архитектора/P01.228.
7. Класс «адрес прослушивания вне loopback без `-tls`»: ни `-raft-bind`, ни `-api-bind` (по образцу) не имеют `bad` при
   адресе вне loopback без `-tls` — правило loopback (`-api`, `-raft`) проверяет только объявленный адрес. Было у
   `-raft-bind` раньше; новое поведение не выбирал — вопрос Архитектору при желании закрыть.
