# Обвязки P01.299

Рабочие каталоги принадлежат P01.299. Скрипты не выбирают пин, не доставляют входы и не запускают модель или кандидата. Операторы в `evidence/operator/` побайтно скопированы из принятой P01.277; изменялись только обвязки.

Фактический выпуск: `/home/pilot/P01.299-evidence/r2`, C `30310352523e30aa7e7879d901e44d80e01b118d`. Скрипты вызываются `/home/pilot/venv-spec/bin/python -B`. Новый выпуск требует нового каталога доказательств; существующие хранилища и фикстуры не перетираются.

1. `prepare_source.py <новые доказательства> <своё дерево> <C>` проверяет принятие P01.323 и её предшествование C, создаёт собственный bare `source.git` без hardlinks, точный `git archive C`, неизменённые операторы и снимки задачи/квитанций. Затем запускает `check_spec --scope platform` на архиве; принимает только код 0. `preflight.py` выполняет проверки штатного оператора без выпуска. `filter_delta.py <C8> <C> <source.git>` сравнивает семантические классификации M и J-входа.
2. `snapshot_reviews.py <доказательства> <своё дерево>` сохраняет факты ревью: P01.294 — принятый отчёт Claude; P01.323 — квитанция приёма и совпадение её window с handle приёмщика Claude. Из реестра сессий берутся только name/handle/model. `bind_reviews.py <доказательства>` проверяет точный набор трёх новых классификаций, принятые коммиты-предки C и фактические сведения о провайдерах. Унаследованные классификации — из принятой P01.277. В фактическом r2 снимки созданы теми же действиями до появления этих обвязок; `snapshot_reviews.py` повторно сверяет их байты.
3. `release_pair.py <доказательства>` после PASS и связанной матрицы ревью вызывает неизменённый оператор пары. Затем текущий `m_form.pair_m` точного C выбирает узкий M; обязательный маркер доставки добавляется отдельно. Создаются новый независимый bare M, паспорт M и J-вход штатным оператором. Сохраняются команда/stdout/stderr/exit каждого оператора, широкая исходная M и окончательные идентичности. Нормы и операторы не переписываются.
4. `passport_controls.py <доказательства>` выполняет девять независимых контролей на своих копиях. `verify_exports.py <доказательства> <своё дерево>` сверяет все ростеры, режимы/blob, фильтры, `pair_m`, объекты, изоляцию, паспорта, `fsck` и результат неизменённого `verify_ji_raw.py`. Грубые эвристические исключения сканера ограничены точными принятыми путями P01.254. Все asserts должны пройти; итог — `VERIFY-ALL.json`. Проверку готовых артефактов можно повторить.
5. `delta_pair.py <доказательства> <каталог отчёта>` импортирует только шесть выгрузок в собственный `delta.git` и сверяет полную дельту M/J/J-входа против P01.277. Сохраняет пути, режимы, blob, размеры и `git diff --no-renames --numstat`. Из этого результата не выводится поведение реализации.
6. `audit_changed_norms.py <своё дерево> <C> <output.json>` сравнивает абзацы P/01.1 и P/01.3 между C8 и C, требует точного покрытия изменённых R-id строками `CHANGED-NORMS.md` и подтверждения каждого абзаца добавленными строками истории. Содержание снятых текстов и столбец происхождения в журнал модели не копируются. Проверка устанавливает полноту id и связь с историей; краткие формулировки и изменения внешних зависимостей проверяются чтением.
