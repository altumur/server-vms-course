## А. Правки без нового поведения

**К1. Класс команды кандидата при таймауте или сигнале.**
- PR «Unified vector command»: «Signals, timeouts, inability to start and cleanup failures are stand failures».
- AC-R038: команда профиля реализации, которая не стартовала (126/127), умерла от сигнала или вышла по сроку, имеет класс `implementation`; `stand` — только команда самого стенда или прокси судьи.
- N4 `stand` говорит о «term of *its own* command», то есть команды стенда.

Норма решает: R038 закрыт и прямо исключает `stand` для команд профиля. Правка PR: сигнал, истёкший срок и невозможность старта — сбой команды, а не подставленный нативный исход, класс `implementation` по P/AC-R038. Сбой уборки процессов остаётся `stand` (N4). Тот же класс просмотрю у адаптеров `door`, `load` и `tables7` (PR «Executable adapters»: premature EOF, nonzero exit, process failure). Это G12, и правка будет одна на всё.

**К3. Обязательные ключи профиля в трёх местах.**
- K: `absent: owner | not_executed`.
- T, столбец `keys`: «Required existing profile parameters».
- AC-R030: отсутствующий или неприемлемый для цели обязательный ключ даёт `not_executed` с именем ключа.
- AC-R007/R015 и флаг `optional` в T: отсутствующий обязательный *интерфейс* без `optional` даёт `blocked`, с `optional` — `not_executed`.

Норма решает. По R014 интерфейсы — это команды, адреса, адаптеры, векторная команда и швы; ключи `keys` к ним не относятся, R030 называет их отдельно. Запись:
- ключ из столбца `keys` строки цели — обязательный ключ этой цели. Если его нет, цель `not_executed` с именем ключа (R030), а не `blocked`. Это верно и при `absent: owner` в K: строкой реестра хозяин урока и объявляет ключ обязательным для цели. `owner` в K отныне значит «присутствие для остальных проверок решает приёмка урока»;
- значение вне типа — `outside` из K (`format_error` отказывает всему прогону);
- значение в типе, при котором цель не имеет смысла (`store_build: box` у группы), — `not_applicable` (R007). Иное неприемлемое значение — `not_executed` (R030);
- отсутствующий интерфейс: без `optional` — `blocked` (R007, R015); с `optional` — `not_executed` с именем интерфейса (R030). В R030 оговорю «of a target with the flag `optional`» у интерфейса.

Правки: шапка K, T «Flag», одна фраза в R030 и PR «Parameters in `keys`». Если Архитектор считает, что отсутствующий обязательный ключ должен давать `blocked`, как интерфейс, — это меняет R030, и пункт уходит в Б.

**К5. `run` — `scenarios.tsv` или `seams.tsv`.** RT уже решает:

**К7. К чему относится `Idempotency-Key` на `POST`.**
- D `@key`: «`Idempotency-Key` on `POST` — by default …», без сужения по двери.
- AC-R020: строка словаря действует на всех стендах, если сама себя не сужает.

Правка D `@key`: «on every door; the rows of `holder` and `member … console` add `PUT` and `DELETE`».

## Б. Нужен выбор

**Б1 (К2). Сбой сборки кандидата.**
- N4 `stand`: «its build failed».
- R038 говорит только о старте, сигнале и сроке, о ненулевом выходе в нём ничего нет.
- PR: «A nonzero build result stops the stand before acceptance».

У стенда своей сборки в M нет: прочие упоминания `build` касаются только сборки профиля. Значит, «its build» читается двояко. Рекомендую:
- (а) **основной вариант.** Ненулевой выход, сигнал, срок или невозможность старта команды `build` профиля дают класс `implementation`, как `unit` в той же строке N4. Сборка, как и сейчас, останавливает стенд до приёмки: каждая выбранная цель, чей состав требует модуля, красная `implementation`, и её первым шагом названа сборка модуля `<module>`. В N4 `stand` вместо «its build failed» — «the build of the judge's own auxiliary program failed»;
- (б) **запасной вариант.** Сбой сборки остаётся `stand`. Тогда в R038 нужно исключение для `build`. Минус варианта: красная цель без вывода о кандидате при ошибке, которая целиком в его коде.

**Б2 (К4). `@manual` — «ни зелёный, ни красный».**
- D: шаг печатается и не исполняется, «does not enter the result», ожидание `manual`.
- AC-R009: сценарий зелёный, когда у него есть автоматические шаги и все совпали.
- AC-R007: GREEN — «every inventoried row or step was executed and matched».
- AC-R008: ручные шаги входят в инвентарь.

Буквально цель с ручным шагом никогда не GREEN, и слова результата для такого шага нет. Сейчас ручные шаги стоят только в сц. 07–09 `system/`, а их не выбирает ни одна цель (у `system/05-power-pull` `range:5-5`). Рекомендую:
- шаг `@manual` входит в инвентарь (R008), в отчёте получает закрытое слово `manual` и не входит ни в GREEN, ни в red;
- в R007 GREEN — «every inventoried automatic row or step», как в R009;
- цель, в выборке которой нет ни одного автоматического шага, — `not_executed` с новой причиной R030 `manual_only`: R008 уже требует хотя бы одного исполненного шага.

Новые слова — `manual` (результат шага в отчёте) и `manual_only` (причина R030).

**Б3 (К6). `$name` и `@any` в режиме `whole`.**
- D `$name`: «in the mode `whole` only a string, another type is a mismatch». Значит, `$name` в `whole` действует; это решено.
- D `@oneof`: «`whole` — JSON whole, without `@any`».
- Строка `<code> <JSON>` перечисляет маркеры (`@any`, `@absent`, `@not`, `@time`, `~`) только для `subset`.

Что значит такой маркер в ожидании `whole`, не сказано: литерал или ошибка формы. Сейчас ни одна цель `whole` (P/01.1/door, P/01.1/extra, P/01.1/inproc) этих маркеров не несёт; `$name` в их ожиданиях встречается. Рекомендую:
