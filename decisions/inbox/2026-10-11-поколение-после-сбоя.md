# Как освободить незавершённое поколение при нумерации держателем

## Контекст

Решение 71527727 и уточнение 95ac7710 прочитаны. При подключении runtime обнаружена коллизия: метка указывает на
`rev=1`, тело `reports/2` записано, процесс падает до переключения метки. Следующий отчёт имеет новый `sent_at`, но
по правилу «+1 на принятую публикацию» получает тот же `rev=2`. Неизменяемый объект уже содержит другие байты.
Пропуск номера нарушает «+1», перезапись без сериализации может заменить тело конкурентной публикации. Счётчик члена
эту проблему не решаем: он отклонён. Нужен порядок восстановления незавершённой записи.

## Рекомендация

Сохранить `rev` и неизменяемость принятых поколений. Сериализовать приём отчётов одного члена и уборку на уровне
хранилища, между процессами, на весь участок «прочитать метку → проверить повтор → записать тело → переключить метку».
Под этой же блокировкой удалить незавершённый `reports/<reported.rev+1>`, если его байты отличаются от нового тела,
и записать новое. Поколения с номером не выше метки никогда не перезаписывать. Повтор с тем же `sent_at` и SHA-256
возвращает прежнюю метку без освежения; равное время с другим SHA-256 рекомендую отказать как конфликт публикаций.

Для файлового хранилища использовать существующий механизм `.lock.tmp` в каталоге
`domain/members/<член>/` (этот файл уже создаёт запись метки): сделать захват повторно входимым для одного потока,
чтобы вложенная запись `reported` не блокировала сама себя. Интерфейс хранилища — контекст атомарного изменения
нескольких объектов; без реализации этого контекста приём запрещён, запасного неатомарного пути нет. Новой строки
члена, номера на проводе или объекта подписи не добавлять. Держатель переносит только принятые поколения,
снимок метки и тел берёт под той же блокировкой.

Альтернатива — разрешить пропуски `rev` и выбирать следующий свободный номер. Проще по блокировкам, но меняет
явное «+1 на принятую публикацию» и оставляет уборку сирот; не рекомендую без изменения ADR.

## Проба

На ветке `codex/course-book-merge`, после включения main (`dd3e4863`), выполнена проба над настоящим
`FsObjectStore` и `reports.accept`: принято тело 1; `put_at` метки для тела 2 прерван `OSError`; хранилище
открыто заново; под тем же номером 2 передано тело с новым `sent_at`. Результат:

```text
ValueError: report seq already names different bytes
PASS: committed pointer remains 1; orphan 2 blocks the next body at holder revision 2
```

Это проба существующего механизма неизменяемого объекта: модуль ещё использует `seq` и не подключён к runtime.
Выбор номера 2 моделирует предписанное `reported.rev + 1`; она не выдаётся за тест уже реализованного runtime `rev`.
Исходный отчёт остаётся целым, но агент, собирающий каждый раз новое тело, сам восстановиться не сможет.

## Приёмка

Сбой после записи тела и до метки, рестарт, новый отчёт: приём восстанавливается без ручной уборки и без изменения
принятого тела. Два процесса конкурируют за один номер: метка никогда не указывает на чужие байты.
Сбой во время уборки сироты не портит принятое поколение. Повтор не меняет `received_at`; равное время с другим
телом отказано. Переезд переносит согласованные метку и тела; незавершённое тело не становится принятым.
