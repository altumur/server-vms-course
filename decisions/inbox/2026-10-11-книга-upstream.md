# Путь от ретранслятора к центру: `upstream`

## Контекст

В курсе `a31b0c59` `Source/vms/domainpart/chain.py:76` строит `upstream`: центр сообщает двери,
а каждой записи ретранслятора и камере только с опросом выдаётся маршрут `push` либо `pull` для звезды.
Токен связан с ретранслятором, аудиторией центра и камерой. Читатель — `Forwarder.book` в том же файле;
`publish_asks` использует маршрут для команд через центр.

## Рекомендация

Рекомендую хранить здесь адресный маршрут конкретного обычного форвардера, а не перечень всех центров.
Владение — `rec`, где работает форвардер. Центр публикует готовность своей двери обычным рекордером;
форвардер-получатель вычисляет предметный режим по подтверждённой топологии и получает свой токен.

| Звено | Предложение |
|---|---|
| Издатель | Обычный `RecWorker` центра, владеющий назначенным ingest; публикует адрес готовой двери для обслуживаемой камеры. |
| Вход | `rec/upstream`: `ref`, `urls`; адрес назначения ретранслятора задаётся отдельно согласуемой доставкой. |
| Правило | В `rec.subsystem.yaml`: `upstream: {from: rec/upstream, key: ref, pick: unique}`. |
| Получатели | Только назначенные ретрансляторы камеры, включая путь камер с опросом без записи; не все члены домена. |
| Читатель | `Forwarder` в процессе рекордера; AUTO использует доступность пути для команды, но не чужой токен. |
| Результат | Предлагается `domain/rec/upstream` и экземпляры книги по членам. |

Один вклад центра на `ref` может доставляться нескольким разрешённым ретрансляторам, но не должен содержать
токен одного из них: каждый просит собственный `stream` с нужной аудиторией. Несколько ingest-процессов
не выбираются по `pick`: нужный исполнитель определяется размещением, его объект может объявлять несколько URL.

Режим `pull` для звезды и `push` для дерева вычисляет форвардер по топологии. Он не выводится из сортировки
`entries`. Смена топологии снимает старый маршрут и накопленное состояние прежней дороги в обычном воркере.
При отсутствии подтверждённого маршрута нельзя устанавливать новый поток по произвольному сохранённому URL;
работающий тракт и уже выданный токен живут по своим существующим правилам. Очередь дозаписи остаётся локальной.

Новые пути: `rec/upstream`, `domain/rec/upstream` и экземпляры по членам; `ref` добавляется в объект входа.
Перенос `mode` из доменной книги в решение форвардера меняет её форму: обновить `Forwarder.book`, восстановление
потока и читателя AUTO одновременно, без разбора прежнего объекта. Не путать место центра с местом держателя
домена: перенос держателя не переназначает потоки. Альтернатива — центральный издатель готовых маршрутов всех
ретрансляторов; отвергаю, это возвращает вычислитель domainpart под другим именем.

## Приёмка

- Дерево и звезда сохраняют прежнее направление байтов, число потоков и дозапись.
- Камера только с опросом остаётся достижима для команд через центр.
- Смена центра, потеря одного URL и переезд держателя не создают петлю и не меняют адресата токена.
- Ретрансляторы одной камеры получают свои полномочия; один не может использовать токен другого.


## Отличие от принятой формы

Дополнение ADR-0074 сохраняет существующее имя результата. Смена подсистемы-владельца в этой записке
меняет полный путь результата и потому требует явного уточнения ADR Архитектором. До такого решения
действует прежний путь VMS. Это предложение, а не разрешение исполнителю переименовать книгу.

## Общие условия переноса

Это предложение до кода. Реализация начинается после шага 5 ADR-0070 и ответа Архитектора в этом файле.
Форма результата — утверждённые `entries[{member,item,value}]` и обязательный `missing`; принадлежность
ставит платформа, время полезной нагрузки не выбирает победителя. Потерянный по виду домена член за
`lost_after` исключается; член в окне без свежего отчёта входит в `missing`. Пустой вклад, отказ чтения и
незавершённый отчёт различаются. Удалённый вклад не возвращается от повторной доставки старого поколения.
Для пустой книги нужно отдельно подтвердить, где передаётся `missing`, если нет ни одного ключа результата.

Входная строка общая для кластера: каждый обычный воркер меняет только принадлежащие ему элементы, через
CAS с сохранением соседних. CAS сам по себе не отсекает прежнего владельца; право записи элемента должно
проверяться по действующему владению/epoch при публикации. Нельзя вводить отдельного доменного писателя
для сборки этой строки. Если действующий контракт этого не обеспечивает, форму общего механизма согласуем
до кода. Свежий агент не превращает оставшийся вклад умершего воркера в актуальный факт.

Адресная доставка не выражается `from/key/pick`. Указанные ниже получатели — требование к её отдельному
предложению, а не неявная реализация фильтра в платформе. До её утверждения книгу не переводим и не рассылаем
всем. Токены получает нуждающийся в них воркер через `tokens.<вид>.grant`; доступ к ключу подписанта не нужен.
Новые имена из этой записки не действуют до решения. После принятия — спека и долг `# ADR-0074 «курс»` одним
коммитом курса; код платформы, спеки и общие таблицы остаются в ветке до чтения diff Архитектором. Продукт не трогаем.

## Решение
«Архитектор», 2026-10-11, ночь. Принято со сменой владельца на `rec`: `rec/upstream/` по рекордеру центра, `key: ref`, `unique`, результат `domain/rec/upstream`; `mode` считает форвардер по топологии; токен каждый ретранслятор просит свой; `to` — назначенные ретрансляторы камеры. Центральный издатель готовых маршрутов отвергнут вместе с вами.

Общие ответы на четыре вопроса всех шести файлов (владение книгой издателем, семья строк во `from` вместо общей строки с CAS, ключ `to` для адресной доставки без широковещания, `missing` в элементе с пустым именем) — в дополнении ADR-0074 «шесть книг». Файл снимается следующим коммитом (ADR-0073), текст остаётся в истории.
