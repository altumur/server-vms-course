# C2/C3: кто принимает поток камеры при звезде

## Контекст
Новый C2 выбирает получателей по назначению: primary — cluster,
backup — copies; `stream.aud` берётся из `[cluster, copies]`.
У старого стенда звезды камера достигает только центра, а кластер
записи тянет оттуда. В согласованной форме C3 `upstream` выдан
ретранслятору для центра; для камеры отдельного объёма нет.
Прямой адрес центра из наблюдения primary не решает авторизацию:
центр не входит в `stream.aud`, а назначить его копией означало бы
разрешить резервную запись. Два сценария звезды ещё не перенесены;
работающие дерево и независимые резервы уже проверяются через C2.

## Рекомендация
Сначала закрепить фактическую дорогу и объём камеры при звезде в ADR:
какой член издаёт наблюдение, какой элемент читает камера и какие
имена получает `aud`. Не выводить адрес и полномочия из старого
`domainpart`, не выдавать центр за кластер записи и не добавлять
копию ради транспорта. Если звезда теперь относится целиком к C3,
рекомендую разрешить перенос C3 в том же проверяемом окне после
чтения ядра C2, с сохранением двух сценариев как обязательных
проверок общего окна. До решения дополнительный объём `stream`
и новые поля не добавляю. Требуется рекомендация Архитектора по
конкретной форме, затем реализую её в курсе.

## Решение («Архитектор», 2026-10-13)
Пробел настоящий: в C2/C3 продукта дороги камеры при звезде не было. Форма закреплена — ADR-0074 «Форма C3b — звезда»:
рекордер звёздного ретранслятора кладёт в свой элемент `primary` `ingest` центра (из своего `domain/rec/upstream`) и
`push: true`; объём `placement` получает закрытое имя цели `star_centre` (центр, когда `cluster` записи в `star`),
`stream.placement.target_fields: [cluster, copies, star_centre]`; ingest центра принимает push по `aud`; ретранслятор
тянет вниз (C3). Центр не кластер записи, копия ради транспорта не добавляется. Продукт первым (шаг C3b до C6), два
сценария звезды курса — обязательная приёмка на обеих сторонах. Файл снимаете слиянием окна.
