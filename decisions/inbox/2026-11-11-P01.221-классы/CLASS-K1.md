# K1 — сокеты готовы раньше обслуживания первого запроса

**Случаев:** door acceptance/1/scenarios.tsv:3 и rights
acceptance/2/scenarios.tsv:3,7,9 — 4 red. Связанная ранняя
последовательность daemon посчитана только в [K3](CLASS-K3.md).

## Норма и вход

M [01.1-store.norms.md](../../../Platform/01-store/spec/01.1-store.norms.md),
P/01.1-R026, закреплённая строка 241: отсутствующая строка —
200 {"items":null,"index":""}. J acceptance/1/scenarios.tsv:3
спрашивает новый acc/01-absent/c1.

M [01.2-store.norms.md](../../../Platform/01-store/spec/01.2-store.norms.md),
P/01.2-R010, строки 106–119: запрет never для epoch касается delete;
разрешённые read/write определяет файл прав. В J
acceptance/2/inputs/rights.json testsubworker вправе читать/писать
testsub/epoch/c5. Строка 3 записывает epoch="3"; 7 и 9 проверяют
сохранение после запрещённых удалений. Ошибки формулировки never здесь нет.

M [01.3-store.norms.md](../../../Platform/01-store/spec/01.3-store.norms.md),
N1.3 leader_wait, строка 52: отказ по отсутствию лидера относится к
эффективному интервалу ожидания. J общий
[README](../../../Platform/common/acceptance/README.md) «Role sockets»,
строка 126, считает стор готовым, когда admin.sock и все ролевые сокеты
принимают соединение. Норма не требует дополнительного ожидания
IsLeader от судьи.

## Код кандидата

Все пути — от Kfinal/01-store в выкладке P01.222.

1. internal/group/group.go:275–286 запускает bootstrap/watch и возвращает
   группу без ожидания лидерства. internal/daemon/daemon.go:111–133
   после старта группы открывает сокеты.
2. group.go:736–748 при ещё не избранном лидере сразу идёт в forward;
   :958–960 при пустом LeaderAPI отказывает без ожидания. Первый put
   может не записать epoch.
3. Read, :524–535, до лидерства идёт в leaderDoor, :603–614.
   awaitLeader, :1011–1028, может дождаться собственной победы.
   Затем leaderDoor всё равно требует адрес API, а не возвращается
   к локальному чтению. publishSelf, :465–467, при пустом APIAddr
   ничего не публикует.
4. acceptance.yaml:22,24 запускает одноузловой стор без -api.
   Поэтому ранний GET может получить отказ даже после собственной победы;
   следующий запрос при уже установленном лидерстве идёт локально.

## Код движка и предел вывода

run_stand.go:569–582 ждёт соединяемые сокеты; scenario_verdict.go:147–163
затем отправляет запрос и сравнивает ответ. Это соответствует опубликованной
готовности. Перестановки тела или запрета epoch из кода движка для этих
четырёх шагов не найдено.

**Исход — кандидат:** найден конкретный механизм раннего отказа,
а отсутствие записи объясняет зависимые чтения rights. Однако
engine.json содержит только red implementation expectation.
Статус 503, содержание первого ответа и момент выборов не сохранены.
Они здесь — вывод по ветви кода, а не наблюдение суда. Иных возможных
причин конкретного исполнения эта запись не исключает.

## Причина и происхождение

Причина — **модель (без обратной связи)**; вторая — **обвязка/задание**:
поведение при доступных сокетах и ещё не завершённых выборах никто
во время генерации не проверял. Четыре поля и подтверждённое чтение M —
[model-view.md](model-view.md).

daemon_test.go:94–117 перед запросами явно ждёт IsLeader;
TestDaemonRightsFile:291–312 использует этот помощник. Тесты проверяют
права после выборов, поэтому дефект старта пропускают. Они не пустые,
намеренный обход проверки не установлен.

В K150 файл group.go отличается от Kfinal; причинность относительно
поправок между снимками не установлена. Коммита внесения нет.
Рекомендуется проверить в будущем контроль старта по публичному условию
готовности и повторную проверку локального лидерства после ожидания.
