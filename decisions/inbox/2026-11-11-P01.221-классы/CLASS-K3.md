# K3 — ранняя последовательность floor: старт, отпечаток и перевод отказа

**Случаев:** daemon acceptance/3/scenarios.tsv:23,25,26,27,28,29,
сценарий 08-floor-replay, шаги 1,3–7 — 6 red.
Пакет сохраняет последовательность, поскольку без ответов нельзя
однозначно разделить её между пересекающимися механизмами.

## Норма и последовательность

M [01.3-store.norms.md](../../../Platform/01-store/spec/01.3-store.norms.md),
P/01.3-R016, строка 306: первый floor — Written; тот же id и payload —
сохранённый ответ; другой payload того же id — 400 badrequest;
новый id с floor ≤ текущего — 409 refused.
Память общая с записью по id, сохраняется вместе с durable floor.

J на строках 23–29 требует:

| Строка | Действие | Ожидание |
|---|---|---|
| 23 | floor 4294967296, id f1 | 200, index $f |
| 24 | restart | ok; это общее red движка, здесь не считается |
| 25 | тот же floor/f1 | 200, тот же index, again |
| 26 | floor 8589934592 с занятым f1 | 400 badrequest |
| 27 | чтение floor | floor 4294967296 |
| 28 | floor 4294967296 с новым f2 | 409 refused |
| 29 | floor 1000 с новым f3 | 409 refused |

## Три механизма кандидата

1. **Ранний запрос.** Пути старта/Apply/Read из [K1](CLASS-K1.md)
   действуют и на первую операцию daemon. Первый floor может не примениться
   до выборов; последующие шаги уже не имеют заявленной предпосылки.
   Первый GET может дождаться собственной победы и всё же отказать
   из-за пустого APIAddr. Поэтому разность строк 23,25–28 нельзя считать
   пятью независимыми ошибками процедуры floor.
2. **Пустой отпечаток floor.** storecore/fingerprint.go:27–31 использует
   uint64, а jcs.go:40–59 его не сериализует; ошибка превращается
   в "" (fingerprint.go:14–18). Если первый floor применён,
   другой floor с тем же id ошибочно становится повтором и получает 200.
   Это ветвь общего правила [K2](CLASS-K2.md). Из red строки 26
   без трассы не следует, что именно эта ветвь сработала в P01.163.
3. **Вид отказа теряется между группой и дверью.**
   daemon/backend.go:37–38 возвращает group.RaiseFloor напрямую.
   group/group.go:789–790 отдаёт *group.Refusal, например
   floor_not_higher_id из storecore/apply.go:89–90.
   door/answers.go:161–173 распознаёт только *door.Fault;
   прочая ошибка превращается в no_leader_wait, 503.
   backend.go:43–53 содержит нужное преобразование faultOf, и Read
   его вызывает; RaiseFloor — нет. Поэтому при выполненной предпосылке
   нормативный 409 строк 28/29 становится 503. Отказ несовпадения id
   тоже теряет нормативный 400.

## Что относится к движку

@restart на строке 24 движок не исполняет: это
[P01.189 E4](../2026-11-11-P01.189-проверка/independent.md).
Он продолжает следующие шаги на том же процессе.
Поэтому red строки 25 **не доказывает потерю durable памяти при рестарте**.
Строка 24 общая; в собственные шесть не включена.

Найденные механизмы кандидата существуют независимо от этой ошибки движка.
Точное распределение причин для строк 23–29, статусы и тела ответов
не сохранены. Ни статус 503 каждого red, ни отсутствие первоначальной
записи в этом конкретном запуске наблюдением не объявляются.

## Причина, тесты и происхождение

**Исход — кандидат**, с указанным ограничением причинности отдельных шагов.
Причина механизмов — **модель (без обратной связи)**; вторая — обвязка/задание.
Общее неисполнение restart остаётся отдельным дефектом инструмента суда.
Четыре поля и видимый модели текст — [model-view.md](model-view.md).

group_test.go:481–530, TestGroupTransferHoldsTheWriters, ждёт лидерство,
поднимает floor 100 с id t1 и повторяет тот же payload. Он не проверяет
другой floor занятого id или HTTP-код отказа.
door_test.go:325–343, TestDoorReplay, меняет payload только обычного put.
Его fakeBackend переводит отказ floor в *door.Fault (:52–65),
поэтому также не воспроизводит пропуск реального memberBackend.
Догадки об этих местах в GUESSES нет.

Ошибки fingerprint и daemon/backend.go уже есть в K150;
соответствующие файлы побайтно равны Kfinal. Причинность изменения
пути старта между снимками и коммиты возникновения не установлены.
Для следующей проверки нужны ранний запрос, отличный payload того же id
и проверка HTTP-исхода отказа через реальный backend.
