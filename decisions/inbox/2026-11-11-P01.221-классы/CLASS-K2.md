# K2 — ошибка сериализации превращает отпечаток любого batch в пустую строку

**Случаев:** door acceptance/1/scenarios.tsv:266–270,281,282,
сценарий 36-batch-repeat, шаги 5–9,20,21 — 7 red.

## Норма

M [01.1-store.norms.md](../../../Platform/01-store/spec/01.1-store.norms.md),
P/01.1-R122, строки 657–660: другой payload занятого id даёт
400 badrequest, исходная запись и ответ сохраняются.
P/01.1-R134, строки 704–710: отпечаток учитывает порядок writes,
op/key/cas/items, множество guards и временные условия.

В J шаги меняют соответственно порядок writes, items, набор guards,
отсутствие guards, not_after, cas удаления и op. Все семь ожидают 400.
Предыдущие шаги 1–4 создали id и проверили допустимые повторы.

## Код кандидата

В Kfinal/01-store/internal/storecore/fingerprint.go:73–87
guardsValue возвращает **[]string**, в том числе для пустого guards.
batchValue:49–69 помещает этот тип в значение поля guards.
internal/jcs/jcs.go:40–59 сериализует массивы только типа **[]any**;
[]string попадает в ошибку «has no canonical form».
Fingerprint, fingerprint.go:14–18, скрывает ошибку, возвращая "".

Поэтому все batch имеют один пустой отпечаток. storecore/apply.go:126–137
считает разные batch с тем же id одинаковыми и возвращает первый index
с again=true. Это даёт 200 вместо 400 на перечисленных шагах.
Непустые отпечатки обычного put/delete объясняют, почему пересечение
put↔batch рядом на строках 271 и 273 всё же красного не дало.

Это статическое следствие конкретных типов и ветвей, не запуск кандидата.
Фактические тела семи ответов P01.163 не сохранил.
Код движка scenario_verdict.go:517–553 сравнивает статус прежде тела:
ожидание 400 нельзя согласовать с такой ветвью 200.
Основания менять ожидания или норму не найдено.

## Весь класс и тесты

Проверены обе составные ветви fingerprintValue: batch и floor.
Для floor тот же дефект имеет другую форму: fingerprint.go:27–31
передаёт **uint64**, которого нет в switch сериализатора; результат тоже
"". Это дополнительный механизм [K3](CLASS-K3.md), а не ещё один
доказанный красный шаг сверх 19.

storecore_test.go:215–240 проверяет равенство двух batch с переставленными
guards, но не проверяет непустой результат и различие изменённых batch.
Две ошибки "" == "" проходят этот тест. Проверка различия put с разным
cas полезна, но другой тип не покрывает. TestJournalStepProperty
повторяет тот же batch, а TestBatchIsOneOperation не проверяет
другой payload занятого id. Эти тесты не пустые; метки «обход» нет.

## Причина и происхождение

**Исход — кандидат. Причина — модель (без обратной связи)**; вторая —
обвязка/задание, которая не проверяла этот класс поведения.
В NOTES модель верно описала отказ другого содержимого с тем же id.
Догадки на этом месте нет; подтверждённое чтение нормы и четыре поля —
[model-view.md](model-view.md).

fingerprint.go и jcs.go в K150 и Kfinal побайтно равны:
ошибка **была раньше**, на снимке K150. Коммит возникновения и связь
с прежними исправлениями не установлены.

Рекомендация будущей проверке: различать допустимые эквивалентности и
изменение каждого поля отпечатка; отдельно выявлять отказ сериализатора.
Норму о выбранном внутреннем представлении Go-значений добавлять не нужно.
