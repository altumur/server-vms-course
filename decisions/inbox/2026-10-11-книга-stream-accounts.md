# Учётки шлюза: `stream-accounts`

## Контекст

В курсе `a31b0c59` `domainpart/streamclients.py:publish_accounts` строит отдельный набор
`accounts_secret` для каждого кластера из `domain/vms/stream-clients/` и его грантов. Читатель —
`vms/streamclients.py:stream_accounts`, вызываемый `vms/rtspdoor.py:122`. CRUD сейчас обслуживает дверь
процесса domainpart. Дополнение ADR-0074 запрещает `domain/<sub>/…` во `from`, поэтому исходный пункт о локальном
`domain/vms/stream-accounts` требует уточнения входа, а не реализации буквально.

## Рекомендация

Рекомендую передать учётки обычному шлюзу `liveworker`, включая операции создания, отключения и смены пароля,
а вход и книгу — подсистеме `live`. Нельзя поручить каждому шлюзу независимо создавать одинаковую учётку:
нужна одна назначенная единица-владелец учётки, обслуживаемая существующим воркером, а не процессом у держателя.

| Звено | Предложение |
|---|---|
| Издатель | Обычный шлюз, владеющий назначенной учёткой; другие шлюзы только принимают разрешённый набор. |
| Вход | `live/stream-accounts`, элемент учётки с `name`, `disabled`, запечатанным `password_secret`; версия смены определяется учётом хранения, не часами издателя. |
| Правило | В `live.subsystem.yaml`: `stream-accounts: {from: live/stream-accounts, key: name, pick: unique}`. |
| Получатели | Только принятые кластеры, чьи действующие гранты разрешают эту учётку; `disabled` и отсутствие гранта снимают пароль у получателя. |
| Читатель | RTSP-дверь обычного шлюза; дополнительно проверяет грант и область доступа к конкретной раздаче. |
| Результат | Предлагается `domain/live/stream-accounts`, с запечатыванием для адресата; публичного `show` нет. |

Путь `live/stream-accounts` разрешает противоречие входа и результата без нового сегмента `books/`.
Смена владельца книги и хранение учётки — отдельное решение этого файла; не объявляю их уже утверждёнными.
Нынешний `liveworker` владеет раздачами, а не учётками: до кода требуется форма их назначения в обычном runtime.
Рекомендую моделировать учётку как отдельную управляемую единицу того же шлюза, без фиксированного «главного
шлюза домена». Если обычный runtime этого не выражает, форму единиц надо согласовать, не добавлять скрытую роль.

Доставка по гранту не означает право редактирования. Создание/смена пароля — авторизованный request к владельцу;
страница не получает прямую запись секретной строки. Запрет совпадения с именем человека и потолок `view`
остаются платформенными декларациями `domain.names`, не проверкой только в шлюзе. Перенос записей учёток
из `domain/vms/stream-clients/` требует обновить эти декларации, все читатели и права одной согласованной
пачкой, без двойного чтения. Точный путь постоянной конфигурации учётки — отдельная форма после выбора её владельца.

При `missing`, конфликте `name`, неоткрываемом секрете или неподтверждённом гранте новые сессии не допускаются.
Срок/отзыв уже открытой сессии сохраняется и проверяется отдельно; не обещаем немедленный отзыв из удаления
строки в отключённом кластере. Ротация при разрыве связи не должна вернуть старый пароль после переподключения.

Вложенный `password_secret` внутри `value` должен остаться секретом на всём пути: общий сборщик не пишет
открытый пароль в логи/публичный вид, доставка заново запечатывает для получателя. Возможность этого для новой
оболочки нужно подтвердить тестом; старый верхнеуровневый `accounts_secret` нельзя считать доказательством.

Новые пути: `live/stream-accounts`, `domain/live/stream-accounts` и экземпляры по членам. Альтернатива — шлюз
пишет VMS-строку по особому праву; не рекомендую. Широковещательный перенос всех паролей с локальной фильтрацией
отвергаю: неуполномоченный кластер уже получил бы секрет. Адресная доставка по грантам — отдельная форма до кода.

## Приёмка

- Совпадение имени с человеком и грант шире `view` отвергаются в обе стороны, не только при создании шлюзом.
- Пароль виден оператору один раз; в книге/backup/логах запечатан, чужой кластер его не получает.
- Отключение, удаление гранта, ротация и разделение сети не восстанавливают старый доступ повторным отчётом.
- Переезд владельца учётки и держателя домена не дают двух издателей; holder-only чтение подписанта удалено.


## Отличие от принятой формы

Дополнение ADR-0074 сохраняет существующее имя результата. Смена подсистемы-владельца в этой записке
меняет полный путь результата и потому требует явного уточнения ADR Архитектором. До такого решения
действует прежний путь VMS. Это предложение, а не разрешение исполнителю переименовать книгу.

## Общие условия переноса

Это предложение до кода. Реализация начинается после шага 5 ADR-0070 и ответа Архитектора в этом файле.
Форма результата — утверждённые `entries[{member,item,value}]` и обязательный `missing`; принадлежность
ставит платформа, время полезной нагрузки не выбирает победителя. Потерянный по виду домена член за
`lost_after` исключается; член в окне без свежего отчёта входит в `missing`. Пустой вклад, отказ чтения и
незавершённый отчёт различаются. Удалённый вклад не возвращается от повторной доставки старого поколения.
Для пустой книги нужно отдельно подтвердить, где передаётся `missing`, если нет ни одного ключа результата.

Входная строка общая для кластера: каждый обычный воркер меняет только принадлежащие ему элементы, через
CAS с сохранением соседних. CAS сам по себе не отсекает прежнего владельца; право записи элемента должно
проверяться по действующему владению/epoch при публикации. Нельзя вводить отдельного доменного писателя
для сборки этой строки. Если действующий контракт этого не обеспечивает, форму общего механизма согласуем
до кода. Свежий агент не превращает оставшийся вклад умершего воркера в актуальный факт.

Адресная доставка не выражается `from/key/pick`. Указанные ниже получатели — требование к её отдельному
предложению, а не неявная реализация фильтра в платформе. До её утверждения книгу не переводим и не рассылаем
всем. Токены получает нуждающийся в них воркер через `tokens.<вид>.grant`; доступ к ключу подписанта не нужен.
Новые имена из этой записки не действуют до решения. После принятия — спека и долг `# ADR-0074 «курс»` одним
коммитом курса; код платформы, спеки и общие таблицы остаются в ветке до чтения diff Архитектором. Продукт не трогаем.

## Решение
«Архитектор», 2026-10-11, ночь. Принято со сменой владельца на `live`. Учётку владеет кластер её создания; пишет любой шлюз этого кластера своей строкой `live/stream-accounts/<шлюз>` (создание, отключение, смена пароля — дверью шлюза); отдельной единицы «учётка» и главного шлюза нет. `key: name`, `unique`; конфликт имён между кластерами — 409 при создании по собранной книге. `to` — кластеры с грантом, издатель считает по `domain/grants/*`, платформа сверяет по `names.<семья>.grant`; секрет перезапечатывается получателю, подтверждается тестом до переноса. Записи `domain/vms/stream-clients/` переезжают одной пачкой.

Общие ответы на четыре вопроса всех шести файлов (владение книгой издателем, семья строк во `from` вместо общей строки с CAS, ключ `to` для адресной доставки без широковещания, `missing` в элементе с пустым именем) — в дополнении ADR-0074 «шесть книг». Файл снимается следующим коммитом (ADR-0073), текст остаётся в истории.
