## Проверка новых уточнений

**Один вызов `token`, в том числе при нескольких видах.** В доп. (18) шаги разделены однозначно: сначала общие проверки, затем вид из разрешённого набора, затем аудитория. Разрешённый вид указывает одно объявление каталога по сохранённому доп. (17) п. 5 (`ADR-0091:581`–582); поле аудитории берётся из этого объявления. Проверка нестандартного `audience_claim` не должна молча возвращаться к `aud`: это уже следует из строки 601 и договора `domain-token.md:19`, 81–82. В конечной модели проверены два разрешённых вида с разными именами поля аудитории, чужой вид вместе с чужой аудиторией, истечение/подпись раньше вида и прежний строковый `expect.kind`. Модель показывает согласованность порядка, не доказывает устройство будущей общей библиотеки. При внесении решения таблица проверяющих и форма команды должны выражать тот же список из п. 1, а не прежний внешний перебор вариантов.

**Межкластерный TLS.** Строки 602–608 заменяют серверное послабление доп. (17), а не распространяют его на все двери. Клиент другого кластера намеренно не предъявляет лист; сервер `mixed` продолжает отвергать предъявленный чужой лист. Поэтому для этой схемы не требуется превращать недоверенный лист в доверенную роль или подавлять ошибку его проверки. В собственной пробе `ssl.MemoryBIO` с `CERT_OPTIONAL` обе версии TLS 1.2 и 1.3 принимают клиента без листа и отказывают клиенту с предъявленным листом чужого центра. Клиент в пробе доверяет центру сервера; это лишь проверка выполнимости двух TLS-ветвей. Выбор члена и полная проверка `peer` проверены чтением договора, не живым межкластерным запросом.

**`{role, domain}`.** При сохранённых проверках сертификата достаточно одной из двух ветвей допуска: подходящая проверенная роль даёт допуск; чужая роль с Bearer идёт в `token`, без Bearer — `wrong_role`; без листа и Bearer — `no_role`. Валидный лист подходящей роли не требует ещё и токена домена: это соответствует исходному «любое из двух» доп. (14), строка 522. При отсутствии комплекта сохраняется отдельная петлевая граница доп. (14) п. 3, а частичный комплект не становится отсутствующим (`role-certificate.md:152`–156). Полная проверка сертификата после рукопожатия остаётся обязательной, как отмечено в таблице закрытий.

**`no_handler`.** Строка 612 устраняет отсутствие устойчивого слова 503: теперь `{error: no_handler, detail}`. Сохранённое доп. (17) п. 8 требует постоянный `detail`. Это не обещание 503 вместо ошибки самого удостоверения: допуск по-прежнему выполняется своим договором.

**CORS.** Строки 613–614 устраняют потерю читаемого отказа разрешённой страницей и задают `Access-Control-Max-Age: 600`. Сохраняются точные разрешённые источники, preflight до допуска и отсутствие `Access-Control-Allow-Credentials`; методы из CORS не создают обработчики и не отменяют 405. Нового противоречия в этих уточнениях не найдено. Отдельная старая ошибка обоснования остаётся ниже.

**Приёмка доп. (12)–(18).** Строки 615–621 задают проверяемые исходы и разводят векторы, каталог, сценарии домена и TLS. Направления достаточны для переноса решения в соответствующие комплекты: список видов и порядок отказов; уникальность имени вида; два исполнителя без выбора; ранний повтор после подъёма резерва; конфликт с посторонним членом и неполнота при `silent`; preflight/отказ/no_handler; отсутствие и предъявление чужого листа. Случай `cluster` + `origin` вне `copies` читается вместе с сохранённым доп. (15) п. 1: это два различных члена, один из которых вне `{cluster} ∪ copies`; равенство `origin == cluster` этим тестом не превращается в спор. Для раннего повтора доп. (17) п. 1 также сохраняет особый исход при двух найденных памятях. Новая строка приёмки не отменяет эти условия.

Перечень в ADR — задание на будущие проверки, не результат их выполнения. Нынешний README TLS-стенда и P/03.4 Н5 по-прежнему ограничивают проверку двери процесса; разрешённое чтение/тест сервера не следует называть успешно выполненным TLS-сценарием. Наличие в решении такого разделения само по себе не дефект.

## Остаточная находка

### R91-D16-01 — мелкая, прежняя: заголовок `Authorization` не обязателен для всех способов допуска

**Место и точная цитата.** `decisions/0091-механизмы-платформы-по-запросам-vms.md:562`: «запрос со страницы без `Authorization` допуска не получает». Доп. (18) п. 5 эту фразу не заменяет.

**Основание и воспроизводимый контрпример.** Договор `Platform/common/contracts/door-token.md:70`–73 прямо требует брать токен из `?t=`, если Bearer отсутствует. Готовый разрешённый вход — `Platform/common/vectors/door-token/verify.tsv:75`, случай `ok_query_one_segment`: пустой `authorization`, путь `/play?t=<токен из этой строки>`, время `1792454400`, единица `testsub/u1`, держатель `w1-7f3c2a`, ожидаемый исход **`ok`**. Claims этого вектора: `expires: 1792454520`, маршруты `[read, play]`, остальные поля и ключ заданы в той же строке. Добавление разрешённого `Origin` не отменяет этот допуск. Это конкретный вход договора, а не предположение о новом маршруте продукта. Вектор в этом ревью прочитан как данные, его реализация не запускалась.

**Последствие.** Неверно обоснование безопасности. Обязательные правила проверки токена остаются правильными; из примера не следует эксплуатация CSRF, поскольку в нём предъявлен действующий токен. Поэтому серьёзность остаётся мелкой. Подходящий сертификат роли также не требует Bearer, но для опровержения общего утверждения достаточно приведённого вектора.

**Рекомендация — вопрос «Архитектору».** Удалить условие об обязательности `Authorization` и обосновать CORS через действительные способы допуска и точный список источников. Менять маршруты, запрещать `?t=` или добавлять механизм защиты ради исправления этой фразы не требуется.

**Происхождение.** Была до доп. (18), не наведена им. Проверены содержимое до/после коммита `be376a33d3e2beb972429f273481bcbdc40e5b28` и срезы `8683a38e3ea866b664887b5bf1a0eeb6f3b03ee0`, `7bdc92f6fd7b17c49b8ae0fb6e024f5a5cda5ff8`: фраза впервые внесена доп. (16) и сохранена без изменения (`inherited-minor-proof.json`).
