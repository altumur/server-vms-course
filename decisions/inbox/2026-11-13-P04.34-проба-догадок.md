### 5. cleanup, зависит от 4

Обязательства: pass deletion, state sweep, decommission; row-check; P/04-15,24,25,29. Таймер unplaced/retire начинается на первом подтверждённом наблюдении, очищается при отмене условия и restart. До физического delete под turn перечитать row и effective decision; assignment/active intent/unknown запрещают delete. Row удаляется первой, с её CAS и turn guard; состояния — только после подтверждения. Для made строго now>keep, not_before=max(0,keep−60); 409 early не требует barrier или журнала. Manual fixed/about exception остаётся expired_kept.

Для state sweep orphan определяется absent/tombstone/другим born, а не одним несовпадением revision. Delete state несёт его CAS и guard свежего unit index, включая "" для отсутствия. На 412 оставить до следующего прохода; state_swept_total увеличивать только после подтверждённого удаления. Вызывать Unit state общего row-check, не создавать свою реализацию этого договора.

Decommission проходит prepared → cleaning → finalizing. Сначала resume pending и проверить семантические инварианты, request_index и frozen own from prefixes; схема сама их не доказывает. До acceptance полностью прочитать источники и проверить максимальный progress/final, keys, body/row weights. Acceptance атомарно создаёт pending и удаляет want с turn/request guards. Release сохраняет original CAS, slots плюс progress занимают до 64 writes; cleanup сохраняет точный общий release index, даже после переписи progress, не перечитывает новый slot для authority. Обновление cursors, отказ batch, отмена request и lost final answer идут по своим правилам. Final mark и delete pending — последний атомарный шаг, valid final не даёт новых cleanup.

Проверки: s22–s25,s39–s50,s56; common/journal и row-check (назначена именно state.tsv); code:* с C20–C23/C34. ## G01: фиксируемые метаданные decommission

Адреса: нормы:131,147,672,674,1398,1474; pending schema properties units/holds (строки158,169). M задаёт список имён, форму wire и фиксацию до принятия плана. В прочитанных договорах не найдено правила, из каких именно assignment/effective placement/hold наблюдений получить эти метаданные при читаемом рассинхроне. Точная связь units с уже перенесёнными или только подлежащими переносу единицами тоже не проговорена.

Контрпример для обсуждения: manifest/current rows читаемы, intent idle; placement c1 указывает w-srv-a-1, а его workers.units пуст. Рассинхрон внесён внешней CAS-записью через store door после завершённого решения; это класс читаемого повреждённого назначения, для которого M требует sync (1158 и checklist01/sc29). Сервер больше не слышен, есть действующий запрос decommission и исходный slot с server=srv-a; controller получил turn. Шаг2 принимающего прохода выполняется до шага4 sync. По assignments список units пуст; по эффективному решению либо объединению он содержит c1.

Это **не** утверждение, будто штатный crash active intent может оставить такой idle-state до шага2: active recovery предписан раньше. Вмешательство, создающее читаемый рассинхрон, — явная часть контрпримера. Если область допустимых входов исключает такой state либо другое место M уже определяет derivation, гипотезу надо снять по этому месту. Искать ответ в J/старой реализации/истории запрещено.

Для продолжения мысленного плана выбрано уникальное объединение assignment ids и effective-decision ids исходных slots. Holds берутся из читаемых текущих hold rows, относящихся к этим slots, и фиксируются тогда же. Это условный вариант для пробы, чтобы не терять видимые имена при рассинхроне; владелец его не принимал. Наблюдатель различит pending/final metadata и выдачу этих списков читателями.

Проверка гипотезы без выполнения: сравнить обе derivation на этом входе и на нормальном согласованном состоянии, а отдельно — holds при несовпадении heartbeat place и hold row. Любой вариант обязан сохранить frozen request/slot indices, guarded chunk cleanup, no new holder cleanup, final-last atomic и запрет удаления по одним историческим именам. G01 не разрешает менять эти обязательства или подавать списки как authority.
