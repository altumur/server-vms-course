# File: повтор id после ошибки барьера уже опубликованной строки

## Контекст и воспроизведение

Принятое решение о File/Mem `write(cmd) → receipt{index,again}` исполняется в
3569935c. Replay живёт только с процессом, новых записей на диске нет.
Дополнительная проба `windows/m10-1-storage/fsync-replay-probe.log` этого SHA:
File volatile=False, один искусственный OSError из `_durable_dirs` после rename
строки; сама проба меняет только метод временного собственного handle.

Первый `write({op:put,key:acc/row,items:{v:one},id:e1})` выбрасывает OSError,
но get уже видит index1001. Повтор того же id в том же процессе менее чем
через секунду возвращает index1002, again=false. Причина: receipt попадает
в process-memory только после возврата `_apply_write`; после rename, но до
завершения барьеров, ряд уже опубликован, а receipt ещё не зарегистрирован.
Это не перезапуск и не принятый случай забывания id за сроком памяти.

## Рекомендация

Считать rename/unlink границей применения: внутри той же блокировки записывать
в память процесса исходный receipt для заданного id при публикации строки,
до оставшихся directory barriers. Пока барьеры не подтвердились, receipt
остаётся внутренне незавершённым; первый вызов сообщает неизвестный исход
(существующий ambiguous, без новой wire-формы).

Повтор того же id с тем же содержимым повторяет только недостающие барьеры,
не CAS/guard и не изменение строки/выдачу версии. После успешных барьеров
возвращает исходный index, again=true. Если барьеры снова отказывают — снова
неизвестный исход, не успешный ответ. Нельзя просто кэшировать успешный ответ
до fsync и выдавать его на повторе без подтверждения долговечности.

Никакого replay на диске и надгробий: незавершённость — только внутреннее
состояние process-memory. Перезапуск теряет его по уже принятому решению.
Проверки прав вызывающего сохраняются перед обращением к памяти повторов.

Проверки до интеграции: put/delete с одноразовым отказом после rename/unlink;
повтор при повторном отказе барьеров; ошибка до публикации не создаёт ложного
receipt; успешный повтор после смены guard/CAS возвращает исходную версию.

Просим подтвердить эту реализацию существующего Н3 либо явно определить
иную гарантию для уже видимого ряда после ошибки барьера. До решения этот
участок не меняем; полные проверки 3569935c продолжаются на frozen Source.

## Решение («Архитектор», 2026-10-14)

Подтверждаю как исполнение Н3 и М10/1-07. Опубликованная строка, у которой отказал барьер, — исход «неизвестно» и на одной коробке: дверь отвечает `ambiguous`, строку назад не снимает (читатель мог её видеть). Receipt для `id` регистрируется в памяти процесса под той же блокировкой в момент публикации (rename/unlink), до оставшихся барьеров, как незавершённый; повтор с тем же `id` и тем же содержимым довершает только барьеры — без CAS/guard, без изменения строки и без новой версии — и отвечает исходным `index` с `again: true`; барьер отказал снова — снова `ambiguous`; иное содержимое под тем же `id` — 400 (Н4); права вызывающего проверяются до памяти повторов. На диске ничего нового, перезапуск теряет память по принятому решению. Это добавлено строкой в таблицу отказов Н4 урока М10/1 (этим коммитом); проверяется чтением, не TSV. Четыре названные проверки — да, в тестах File и Mem.
