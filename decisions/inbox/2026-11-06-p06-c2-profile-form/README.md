# P06 C2: early typed finite profile and installation binding

This is the early source-form submission requested by coord103 after the Architect accepted variant 3 of proposal391ef. It is not an activated manifest extension, a new flag, a completed installer binding or an English freeze. The accepted static refusal is unchanged: a sufficient bound above B refuses the profile as `refused:form` before installation writes. No deletion-time admission or new DELETE refusal is proposed.

`profile.schema.json` describes an internal typed record passed to the existing installer, not YAML keys added to a subsystem manifest. All quantities are integer byte counts or finite multiplicities. No quantity has a guessed default. Integer arithmetic is exact. Every actual mandatory request is covered separately; the installer needs the whole implementation-specific packet roster, including pending acquisition/intent save, target, saved answer, claim cleanup and every alternative or auxiliary request actually emitted. Replays reuse the same packet bytes. The record cannot omit a packet, use a smaller multiplicity than the procedure permits or declare an unbounded value finite.

## Metadata and byte bound

The serializer is compact JSON, UTF-8, no BOM, comma/colon separators, required JSON escaping, plus exactly the number of final LF bytes the implementation emits (0 or 1). HTTP headers, Content-Length and chunk framing are excluded. The exact packet encoder is the one used to send the request, not a parse/reserialize estimate. Optional command metadata is counted whenever it can be emitted; undeclared extra metadata is forbidden by this internal profile.

The existing store wire bounds are sufficient for metadata: each full write/guard key is at most1024 UTF-8 bytes (not the200-byte unit identifier); CAS and guard index are an empty string or at most20 decimal digits; id, when emitted, is1–64 lowercase hex. A string of K UTF-8 bytes occupies at most6K+2 JSON bytes, including quotes. A timestamp uses the P01 writer notation with at most3 fractional digits; a nonnegative finite binary64 has at most309 integer decimal digits, so313 bytes conservatively cover a serialized timestamp without exponent. There is no change to the caller's opaque treatment of an index. Metadata includes every op, key, cas, index, id, deadline, array/object delimiter, comma, colon and field name.

For each distinct packet shape, build its worst permitted full metadata skeleton with every put's items replaced by `{}`. Let H be the upper bound on its encoded size minus2 for each such put; the separate LF is not in H. A put belongs to exactly one category: ordinary unit/tombstone (`n_unit`, weight<=V), internal claim (`n_claim`, weight<=V), a three-field folder row (`n_folder`, weight<=F), or an empty map (`n_empty`). Delete writes have no items; their full metadata and all guards stay in H. If another nonempty row family is actually written, it needs an explicit weight/category proof before this profile is complete: it cannot disappear from the bound.

`bound = H + (n_unit+n_claim)*(12*V+7) + n_folder*(6*F+19) + 2*n_empty + LF`.

V is the actual effective store row ceiling, not an independent ceiling of the installer; F is the existing `FOLDER_ROW_MAX`. The `12V+7` bound allows all fields permitted by a row's total UTF-8 weight and worst escaping. The tighter folder bound uses exactly its existing three stored fields. An implementation with extra folder fields cannot claim that tighter bound. Each packet must have bound<=B, inclusively. `n_folder<=FOLDERS_PER_UNIT_MAX*n_unit` is available only for the unit-deletion expansion; it is not a bound for arbitrary caller-supplied folder replacements. Mixed console batches must include their independently permitted writes/guards and all consequences. The public64-row limit is not a cap on auxiliary internal rows.

Multiplicity values are computed at installation from the complete confirmed catalogue and the implementation's finite procedure descriptors, using the existing batch, folder and rights rules; they are not taken from the current live row count or a favorable current folder list. The typed record carries provenance for each bound and the complete covered packet roster. A missing proof is not a successful installation. This submission deliberately does not invent an executable loader form for that descriptor: its exact linkage needs the related P02 scope below.
