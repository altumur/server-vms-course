# Ревью ADR-0126 (Claude)

Это ревью — исключение из паузы ADR-0120 доп. (2): владелец согласился на ADR с ревью, слово передал «Архитектор» 2026-11-04.

Что читалось:
- курс, main dbb15b2eb: `decisions/0126-…`; README реализации P/01 `spec/en/01-store.README.en.md`, «Order of work» и «Language-dependent pitfalls»; ADR-0083 доп. (89), (90); ADR-0125 доп. (1); ADR-0120 (форма «таблица»);
- обвес `minimax-loop` 4f527ab: `loop.py` (вехи — `milestone_note`, закрытие вехи по `measure.passed`), `tasks/p01-go.ct102.json` (`milestones`, `targets`, `judges`), `kits/p01-1-en/assembly.yaml`;
- `cammeta-acceptance` `runner/` — названия целей.

Кода не правил.

**Счёт: Б 0, С 5, М 3.**

Решение верное. Порядок работы — свойство урока, а не задания. У каждого этапа есть машинный конец. «Прочитать нормы целиком» уходит из этапов — это и есть беда попыток 7, 13–15 (доп. (90): 102 чтения за 80 ходов).

Но пять мест решение пока не держит:
- `own_tests` в нынешнем виде проходит без единого теста, а «тесты этого этапа» ничем не привязаны к этапу (С1).
- Имена целей и числа `N` в `accept` — из описи раннера, а не из урока. `check_spec` их не проверит, и числа плывут с перепином раннера (С2).
- «Форма-таблица, README её не повторяет» по ADR-0125 доп. (1) п. 5 делает порядок нормой. А README говорит «one possible order». И в «Order of work» есть смысл сверх порядка, его некуда деть (С3).
- `budget` в ходах цикла — настройка обвеса и модели в форме курса. Её правка требует новой выгрузки (С4).
- Одни этапы на всех не учитывают пакет Б: часть этапов в варианте Б отдана пакету. Нет места для языковых подробностей, которые несли вехи пятнадцатой (С5).

## С

### С1. Вид `own_tests` не проверяем и проходит пустым

П. 1: «`own_tests` — свои тесты реализации проходят, и среди них есть тесты этого этапа».
- Цикл гоняет свои тесты судьёй «свои тесты» с командой `go test ./...` из задания. В Go эта команда проходит и без единого теста (`no test files`).
- Что тест относится к этапу, не видно ни из формы, ни из вывода: привязки нет.
- Этап с `own_tests` закроет один пустой файл.
- Свои тесты пишет тот же исполнитель, что и код. Это машинный конец, но не независимый.

Предложение:
- (а) Привязка по имени. Тест этапа несёт имя этапа: `TestStage<stage>_…` в Go, маркер `stage_<stage>` в Python. Вид — `own_tests:<stage>>=<K>`. Цикл гоняет тесты с фильтром (`go test -run '^TestStage<stage>_' -json`) и считает прошедшие. Команда с фильтром — в профиле языка (`assembly.yaml` или задание), форма называет только этап и `K`.
- (б) Независимый вид для этапов до демона — `vectors:<пакет>`. Векторы урока гонятся через адаптер реализации, как их уже гоняет раннер (`c_jcs_vectors` и родственные): `vectors/jcs`, `vectors/rights-evaluator`, пробы `forms/write-checks.probes.tsv`. Тогда ранние этапы судит курс, а не сама реализация. Это ближе к driver «проверка конца, которую видит машина».

### С2. Цели и `N` в `accept` — из раннера, `check_spec` их не видит

- П. 5: «цели приёмки — из описи урока». Но в курсе описи целей нет. Имена `P/01.1 door`, `P/01.1 extra` и числа — из описи раннера (`targets_source`: «опись раннера c612be3 на выгрузке 25812ab8 … door 345 шагов, extra 84 пробы»).
- `check_spec` судит курс и раннер не читает. Проверить имя цели и разумность `N` ему не по чему.
- Числа плывут:
  - перепин раннера после перераскладки (ADR-0124 доп. (1) п. 1) строит опись заново;
  - каждая правка сценариев меняет число шагов.

  `accept:door>=200` сегодня и через неделю — разные вехи.
- Счёт — не по этапу. 100 шагов наберутся и лёгкими шагами чужих этапов. В пятнадцатой веха 1 стояла на `min_passed: 1`: один шаг закрывается и ответом заглушки 404 на неизвестный маршрут.
- Цикл проверяет только текущую веху (`passed >= ms["min_passed"]` по последнему раунду). Если поздний этап сломает ранний, цикл этого не заметит.

Предложение:
- основной вид — `accept:<цель>:<сценарии>`. Номера сценариев есть в `acceptance/*/scenarios.tsv` курса, и `check_spec` их проверит. `>=N` — только для последнего этапа («вся приёмка») или долей (`>=50%`);
- имена целей — курса: глава приёмки (`1`, `1/extra`), а раннер ставит соответствие. Иначе нужна копия описи в курсе, и `check_spec` сверяет с ней;
- этап закрыт, когда держатся его проверка и проверки всех прежних этапов. Цикл должен разбирать итог по сценариям: сейчас `measure.per` — только по целям.

### С3. Граница этапов и норм

- **Форма называет себя нормой, а README говорит «один из порядков».**
  - П. 1: «Форма ADR-0120 „таблица“». П. 2: README «ссылается на таблицу и её не повторяет (как у таблицы проверок …)». А ADR-0125 доп. (1) п. 5 говорит: «таблица — норма».
  - README реализации P/01: «Below is one possible order … may be arranged otherwise».
  - Не сказано, норма ли порядок. Реализация другим порядком — дефект или нет? Считает ли `adr-norms.tsv` строки этапов нормами?
  - Предложение: записать, что `stages.tsv` — форма плана работ, а не норма. Приёмка порядка не судит. Столбец `norms` только ссылается, а `goal` норм не вводит.
- **«Order of work» несёт не только порядок.** Там есть советы по существу, и в одну строку `goal` они не лягут:
  - глава 1.2: «Distinguish the absence of delete from an explicit empty list», порядок приоритета проверки;
  - глава 1.3: «Write the mark `FORMAT` first into an empty directory», «for status keep the exact uint64; `leader` is the `-api` address», какие сценарии на каком стенде.

  Если README «не повторяет таблицу», этим советам нужно место. Например, «Language-dependent pitfalls» или отдельный раздел README со ссылкой из строки этапа по `stage`. Иначе они пропадут при переносе.
- **«Чтение норм — общее правило исполнителя».** Не сказано, где оно записано. Предлагаю «Inputs and their priority» README и голову задания цикла: одна строка, а не этап.

### С4. `budget` — настройка обвеса в форме курса

- **Единица — «ходы цикла»**, то есть ходы одной модели на одном обвесе. MiniMax читает 80–100 ходов перед кодом (доп. (90)). Другой модели нужно другое число, а человеку оно ничего не говорит.
- **Перемен становится две.** Правка `budget` — коммит «Спецификации» в урок, затем новая выгрузка, новый `SPEC_VERSION` и, по ADR-0124 доп. (1) п. 1, перепин раннера. Подстройка обвеса между попытками станет переменой спецификации, и «одна перемена за раз» (ADR-0083 доп. (86) п. 1) ломается.
- **Чьё число действует.** Задание тоже несёт пределы (`max_turns` 600, веха 1 — 120 ходов по доп. (90) п. 2, `read_budget` 15). П. 4: «Задание называет … пределы». Не сказано, что действует при расхождении задания с `budget`.
- **Выгрузка.** Числа уйдут в выгрузку и попадут в голову моделям всех линий как цель.

Предложение. Форма держит порядок и проверки, а `budget` — в задание по имени `stage`. Если ориентир нужен людям, в форме оставить относительный вес (`1`–`5`), не ходы. Задание переводит вес в ходы и всегда старше.

### С5. Пакет Б, языки и линии

- **Варианты.** Этапы P/01 сегодня написаны под вариант А. Шаг 2 «Order of work» — «the checks of … as separate pure functions. These are the first tests». В варианте Б эти проверки дал пакет (`writecheck`, `jsonstrict`, `checks`). По ADR-0125 пакет даст ещё дверь, флаги и отказы, а модели останется «ручная часть» (ADR-0125 доп. (1) п. 2). Одна таблица на всех исполнителей должна знать, какой этап покрыт пакетом. Например, столбец `kit` с частью пакета: цикл не ставит такой этап моделью, но его проверку судит.
- **Язык.** `goal` — одна строка по-английски, без языка. Цели вех пятнадцатой и шестнадцатой несли подробности Go:
  - «Напиши `work/01-store/cmd/configstore/main.go` (package main)»;
  - перечень флагов профиля;
  - «Остальные маршруты — заглушками 404».

  Именно их цикл и подавал модели. Нужно решить, где им жить: дополнение профиля языка по имени `stage`, которое не меняет ни порядка, ни проверок. Иначе либо вехи слабеют, либо подробности снова уходят в задание, а это беда п. «Context».
- **Люди и линии Codex.**
  - Виды `build` и `accept:` требуют раннера и профиля. Линиям Codex это подходит: они идут через раннер. Человеку без раннера остаётся только `own_tests`.
  - `budget` в ходах человеку не нужен (С4).
  - В остальном форма людям годится, если С3 даст место советам.

## М

### М1. `norms` — ссылки на якоря, а `check_spec` якорей не судит

П. 5: «ссылки `norms` ведут на существующие якоря». Сегодня `check_spec` проверяет только, что цель существует (моё С1 ревью пилота перераскладки P/01). Нужна проверка якорей, она же нужна и там.

И синтаксис ячейки не задан: «номера и якоря». Предлагаю id норм (`P/01.1-Н2.1` или `Н…` по `id-map.tsv`) — их `check_spec` уже знает (`norm_ids`) — либо путь с якорем английского источника.

### М2. `n` и `depends`

Цикл идёт по `n`. Тогда `depends` нужен только людям и параллельным линиям, и в нём только прежние номера (п. 5) — циклов быть не может. Стоит сказать прямо, что цикл берёт порядок `n`, а `depends` ему справочен. Иначе генератор вех может решить, что этапы без общей зависимости идут параллельно.

### М3. Грамматика `gate` в TSV

Имена целей раннера содержат пробел (`P/01.1 door`). `accept:P/01.1 door>=1` в ячейке читается неоднозначно, а `:` служит и разделителем перечня сценариев. Нужна закрытая грамматика:
- цель — без пробелов (С2: глава приёмки);
- сценарии — через `,`;
- `check_spec` судит ячейку образцом.

Тогда и проверка п. 3 «первый этап урока с демоном — `accept:…>=1`» судится механически: этап с демоном нужно пометить или найти по цели.
