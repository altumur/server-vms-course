## Согласованность решения

| Предмет | Основание и результат |
|---|---|
| Необязательность условия | P/06.1:493–496: «If-Match … необязателен … Нет — как прежде». Новый четвёртый аргумент api тоже необязателен. Старый вызов с тремя аргументами не получает условия автоматически; форма самой консоли переводится отдельно (доп. (28) п. 3). |
| Область методов | Доп. (28):791–793: заголовок только у PUT/DELETE, у прочих методов «отказ вызова до запроса». Это не превращает POST в условную запись и не меняет его Idempotency-Key или память повторов. |
| Revision на проводе | Доп. (28) ссылается на revision P/06.1 Н3. Значение сериализуется в десятичное целое ≥1 без знака/ведущих нулей по P/06.1:493–494; это не произвольный текст HTTP-заголовка. Нового поля revision в теле нет. |
| 412 | P/06.1:495: `412 {error: "revision moved", revision: <нынешняя>}`, ничего не записано. Доп. (28):793–795 сохраняет этот исход и добавляет только поведение клиента: `throw … retry: false`. Он не повторяет запись с новой revision и не прячет конфликт в успешном ответе. |
| Неизвестный исход | P/07:72–77 разрешает автоматический повтор только у дверей с памятью повторов, при неизвестном исходе PUT требует чтения. Доп. (28):794–795 оставляет правила прежними и явно называет PUT/DELETE без памяти. Это существенно: If-Match не превращает их в двери с памятью id. |
| Совместимость | Доп. (25):737–740 сохраняет version 1 и `?v=1`, добавленное обнаруживается по features. Доп. (28):790,796–797 следует тому же правилу: новая строка `api.if-match`; нет строки — страница не делает условную запись. Нельзя молча вызвать старый модуль с проигнорированным четвёртым аргументом и считать запись защищённой CAS. |
| Граница opts | Доп. (28):792–793 прямо закрывает объект: «иных полей у opts нет, произвольных заголовков модуль не шлёт». `opts` не является HeadersInit/объектом параметров fetch. Через него нельзя выбирать Authorization, Cookie, X-Operator, Idempotency-Key или адрес запроса. Лазейки в тексте решения нет. |
| Владение и исполнение | Доп. (28):798–801 назначает контракт, канонические байты и jsdom-тест «Спецификации»; урок 07 реализации по-прежнему отдаёт байты как есть. Изменение поведения HTTP-двери P/06.1 и её OpenAPI не требуется. |

Проверочная трасса неизвестного исхода: PUT с If-Match 7 записан, ответ потерян, строка стала revision 8. Автоповтор не выполняется; страница читает строку и определяет исход. Если повторить тот же PUT вручную с 7, дверь даст 412, а не прежний успех. Новое дополнение этого не скрывает и не разрешает подставить 8 автоматически. У DELETE повтор может дать 404: надгробие уже поставлено; поэтому чтение нужно и для него. Это трассы по нормам, не запуск реализации.

## Что держать тестами при исполнении

Не новые находки, а границы положительного вывода:

1. Старый вызов без opts и `opts={}` не добавляет If-Match; POST с ifMatch отказывает **до отправки**. Проверить и DELETE, а не только PUT.
2. Передаётся только If-Match; попытка `opts.headers`/иного поля не создаёт HTTP-заголовков. При записи нормы явно сохранить закрытость opts, не раскладывать его целиком в параметры fetch.
3. 412 сохраняет тело владельца, имеет retry:false и не порождает второй запрос. Сеть/таймаут/5xx у PUT/DELETE также не запускают автоматический повтор; следующий шаг страницы — чтение.
4. Feature присутствует только вместе с реализованной возможностью; при её отсутствии assist не отправляет PUT без условия. Version и загрузка `?v=1` остаются прежними.
5. Сериализация revision — по P/06.1, без звёздочки, списка ETag и произвольной строки. Заголовок не дублируется.
