## Находки: кандидат A

### A-01 · Б · Новый член не входит в группу по `-join`
- **Где:** `group/transport.go:127-133`; `group/tls.go:149-175,195-197`; `daemon/group_runtime.go:359-369`; `daemon/group_start.go:130,187-190`.
- **Норма:** P/01.3-01; P/01.3 N1.3 `join` (1.3:47: «the daemon starts first, then joins: ask /v1/status … POST /v1/join»). Стенд группы: адреса `127.0.0.1`, у листа SAN DNS `<id>`, «the daemon checks the name of a peer against the `<id>` … not against the host of the address» (`common/acceptance/README.md` «Store group stand»).
- **Что не так.** Две причины, каждой достаточно.
  1. Слушатель `-api` проверяет `trusted` прямо в рукопожатии TLS: `verifyPeer` → `trustedPeer` (`tls.go:195`). Для роли `configstore` это требует, чтобы id уже был в конфигурации Raft. Входящий член ещё не в ней, поэтому его `GET /v1/status` и `POST /v1/join` рвутся на рукопожатии. Исключение для `/v1/join` в `ResolvePeer` (`group_runtime.go:342`) стоит после рукопожатия и недостижимо.
  2. `joinOnce` строит клиент с `ClientTLSConfig("", …)` (`group_start.go:188`). При пустом `ServerName` `http.Transport` проверяет хост URL `127.0.0.1`, а у листа стенда нет IP SAN.
- **Сценарий.** `s2 -join {api@s1}`: `performJoin` крутится `-leader-wait` и даёт отказ старта с кодом 2 (`group_start.go:158-162`). Группа не растёт дальше первого члена. Сценарии 07, 17, 18, 25–29, 31 главы 1.3 красные по построению.
- **Тест:** `group/node_test.go:25` идёт через `InmemTransport` и прямой `Node.Join`, минуя TLS и HTTP. Пустышка для входа.

### A-02 · Б · Пир mTLS на `-api` без заголовка роли получает `admin`; доверяется любой лист двери
- **Где:** `daemon/group_runtime.go:338-348,359-363`; `door/authorization.go:133`; `door/service_operations.go:242-246`.
- **Норма:** P/01.2-08; P/01.2 N1.3 (`01.2-store.norms.md:123`: «configstore-door — only its own platform/configstore-doors/<id>»); N3 п. 9 (`:188`: «a forwarded admin while a rights file is present — refusal»); P/01.3-R033 (1.3:316: «a role header or network forwarding grants no administrative access»).
- **Что не так.** При отсутствии заголовка `ResolvePeer` возвращает `Identity{Role: "admin", Trusted: true}` без `Forwarded`, поэтому запрет пересланного admin не срабатывает. `trustedPeer` для `configstore-door` всегда `true` и не сверяет id с дверями группы. Любой лист двери того же УЦ или любой голосующий получает по сети без заголовка:
  - `GET /v1/copy`, то есть весь дамп;
  - `POST /v1/leave`;
  - `op: floor`;
  - запись любых строк;
  - `GET /v1/rights`.

  Ограничение «только своя строка двери» (`validateDoorCommand`, `:122-126`) обходится простым отсутствием заголовка.
- **Тест:** `door/rights_test.go:220` с подставным `fixedIdentityResolver` — пустышка для группы.

## Три главных риска

**A:**
1. Группа не собирается дальше одного члена (A-01). Все сценарии стенда группы красные, и тесты этого не видят: группа через TLS и `-api` в тестах не поднимается.
2. Безопасность и исходы на пересылке: пир без заголовка — `admin` по сети (A-02); отказ лидера читается как «строки нет» (A-03); `expired`, `early` и `ambiguous` теряются, дверь дублирует запись без `id` (A-04).
3. Данные при переносе и восстановлении: время в RFC 3339 ломает импорт любой копии по норме (A-07); `recover` удаляет эпохи и не видит снимок (A-08, A-09); импорт стирает группу (A-10).

**B:**
1. Исходы при сбоях: дверь отвечает «не добавлено» на возможно добавленную запись (B-02); лидер застревает неготовым после неудачного барьера (B-10); `replay_limit` нет (B-03).
2. Живучесть под нагрузкой: после EMFILE слушатель мёртв до рестарта (B-04); сборка памяти повторов O(Q) на запись, сама память целиком в RAM (B-05, B-11); остановка большого ящика выходит за срок менеджера (B-06).
3. Членство: `join -force` из CLI не работает и отвечает 0 (B-07); лидер, ушедший сам, принимается обратно без `admit` (B-08).
