## Находки

### С-01 · С · Дефолт `-id=$SERVER_NAME` недостижим, когда `-id` required (-join/-door/-group-size 3|5): required проверяется по явно данных флагам, игнорируя дефолты
- Где: `01-store/internal/flags/flags.go:189-208` (walk: `p.Given[sp.name]`, `celFlags()` только по Given — `flags.go:250-269`), дефолт применяется позже в `01-store/internal/flags/types.go:128-145` (Str: `$SERVER_NAME`), ветка `start_config` недостижима: `01-store/internal/daemon/run.go:99-101`.
- Норма: forms/daemon-flags.tsv (строка `-id`: default `$SERVER_NAME`, required `"-join" in f || "-door" in f || …`); P/01.3-R031 («The default of -id and the absence of a default MUST be defined only by its row and header»); P/01.3-R194 (unmet required → start_flags — required должен считаться по **значению** флага, иначе дефолт строки бессмысленен именно при required).
- Что не так: запуск `configstore -join h:9 …` без `-id` при `SERVER_NAME=s1` отказывает `start_flags` на строке `-id`, хотя значение флага есть (дефолт строки) и старт с id `s1` — ожидаемое поведение. Следствие: ветка автора в `configure()` «no -id and no SERVER_NAME → start_config (code 2)» — ровно его GUESS 7 — недостижима и для `-join` (флаги отказывают раньше). Дефолт строки формы объявлен, но в единственном режиме, где он нужен, не работает.
- Сценарий: стенд не страдает (раннер всегда дописывает `-id <id>` — acceptance/3/README «The runner appends only these flags: -id …»), сценарные ворота зелёные; дефект нормативный, боевой запуск по SERVER_NAME в группе сломан.
- Тест: нет (flags_test.go покрывает форму/типы, случай «required закрыт дефолтом» не покрыт).

### М-01 · М · Продолжение прерванного import/restore на ящике переносит все строки с нуля
- Где: `01-store/internal/copycore/step.go:139-148` (resume начинает с `Cursor = 0`), запуск нового процесса CLI — `01-store/internal/cli/transfer.go:90-109`; идемпотентность записи — `01-store/internal/core/importx.go:85-96`.
- Норма: P/01.3-R151 (продолжение той же попытки; F1 точен — выполняется), P/01.1-R371 (**Scope: production** — «без повторной перезаписи уже обработанного префикса»).
- Что не так: после прерывания и повторного запуска `import` на ящике уже перенесённые строки пишутся в журнал повторно (версии те же, состояние идемпотентно — корректность не ломается, F1 не поднимается вторично). Функционально допустимо; предмет производственной стоимости (RUN-W02), не ворот.
- Тест: частичный — `internal/daemon/transfer_test.go:48-84` покрывает отказ повторного import после Done и bad-input, прерывание+продолжение на ящике не моделируется (в `copycore/copycore_test.go:105` continuation проверен на машине).

### М-02 · М · Ошибка устаревшего prevIndex конфигурации сводится к ambiguous
- Где: `01-store/internal/group/member.go:176-184` (configOutcome: любая ошибка AddVoter/RemoveServer, кроме NotLeader/EnqueueTimeout, → `leader_lost`).
- Норма: P/01.1-R144/R320 (ambiguous — только исход «послано, результат неизвестен»; определённый отказ членства — 409).
- Что не так: `raft.ErrPreconditionFailed` (несовпадение prevIndex) — определённый отказ, а отдаётся `leader_lost` (503 ambiguous). На практике недостижимо: изменения членства сериализованы `memberMu` на одном лидере, recover идёт офлайн. Записываю класс, чтобы правило не расползалось.
- Тест: нет.

### М-03 · М · member.json при -join не помнит партнёров
- Где: `01-store/internal/group/member.go:79` (`writeMemberFile("join", map[string]Member{})` — пустой список партнёров; адрес `-join` не сохраняется).
- Норма: P/01.3-R054 («The daemon MUST remember the partners and how it joined in member.json»).
- Что не так: how=join записан, partners пуст. Оперативное свойство нормы (restart is not a joining — членство восстанавливается из raft-лога/FSM) выполняется, буква «partners» — нет; для узла, стартовавшего с `-join`, единственный известный партнёр теряется до восстановления членства.
- Тест: нет прямого (косвенно — перезапуск s1 в group_test.go идёт через сохранённое raft-состояние).

### М-04 · М · `-max-conns` — один общий пул на все ролевые сокеты
- Где: `01-store/internal/daemon/startbox.go:78` (`roleSlots = newSlots(-max-conns, 0)`, тот же объект всем ролевым сокетам — `startbox.go:88`), admin.sock отдельно (16) — `startbox.go:90`, `-api` свои счётчики с per-address.
- Норма: forms/daemon-flags.tsv (строка `-max-conns`; в M c4a17f05 семантика «на сокет/общий» текстом строки не фиксирована); P/01.3-R008/R321 (ответ 503+Retry-After — выполняется).
- Что не так: если читаемая норма — лимит каждого сокета (так читали ревью попытки 6), общий пул недодаёт: две роли исчерпают 64 суммарно. Если — суммарный по ролевым сокетам, всё верно. Формулировку закрыть у автора нормы; просьба 01-connections (один дверной наблюдатель) обе семантики не различает.
- Тест: `internal/daemon/box_test.go:159-181` — один сокет, admin вне лимита ✓.

### М-05 · М · `-group-size` при рестарте не сверяется с member.json
- Где: `01-store/internal/daemon/startgroup.go:42-51` (размер берётся из флага; в member.json `group_size` пишется — `internal/group/member.go:24` — но не читается).
- Норма: P/01.3-R053 (declared size MUST be the same on all servers).
- Что не так: согласованность размера enforced только на join (размером лидера в `joinAtLeader`, `member.go:139-142`); рестартовавший член с иным `-group-size` не отказывается. Минимальный риск (лидер держит семантику), класс — сверка флага с каталогом.
- Тест: нет.

## Группа Raft по свойствам модели

- **Гонки.** Две записи с одним cas — одна запись лога, порядок лидера; guard/cas в одной записи (apply.go). Два replay одного id — порядок лога, второй получает again (apply.go:71-74). Replay и первое применение вместе — первый в порядке лога (R095/R138 ✓). Чтение на границе смены лидера: fence — commit-index, подтверждённый лидером текущего срока (VerifyLeader у лидера, фрейм read-fence у последователя), затем дожидание FSM до последней команды/конфигурации ≤ index (fsmTarget, backend.go:173-185); член с обрезанным raft-портом отвечает новой версией или 503, не раньше (согласно acceptance/3 README «The store group stand»). Удержание писателей при переносе — состояние Import в FSM/журнале, рестарт его сохраняет (snapshot несёт Import — fsm.go:203-213, metaLine+core.Encode).
- **Повторы.** id-память долговечна везде: журнал ящика, записи/снимок raft; условия R141 строгие (`> ID_REPLAY_MIN_AGE`, `≥ ID_REPLAY_MIN_RECORDS`, часы — admission; forget только при обоих — apply.go:190-205). Повтор floor возвращает сохранённый исход с again; отказанный до применения floor id не занимает (remember только при успехе — apply.go:80-83) — R216 ✓; чужая нагрузка с id floor → 400 (RefIDMismatch→body_form ✓ R218). Продолжение import той же попыткой: точный F1 без повторного подъёма (importx.go:53-70, step.go:139-148); иной вход при Active → import_other_input ✓ R151. Повтор после Done → import_repeated ✓ R122. Повторный join своего id с тем же raft-адресом обновляет api (member.go:126-131) ✓ R178; admit повторен — 0 (тест).
- **Разрывы.** Потеря лидера после отправки записи → `ambiguous_leader` по CommitWait (10 с) или ошибке future (backend.go:59-77) ✓ R326/R320; до лога (NotLeader/EnqueueTimeout) → unavailable ✓ R144. Дверь: попытки DOOR_REQUEST_TIMEOUT по избирателям в сумме ≥ leader-wait+margin, ретрай только чтений и записей с id, «послано без ответа» записи → ambiguousLeader, без id — не ретраится и остаётся ambiguous (door.go:175-232) ✓ R252; все избиратели недостижимы → 503 unavailable ✓ R086. leader_wait считается от потери (lostAt в watch) ✓ R063 — регрессии C-09 попытки 6 нет. Чтение без подтверждения лидером в пределах ожидания → no_leader_wait, не устаревшие данные ✓ R062. Потеря кворума — bounded 503 (тест, <10 с при -leader-wait 2 с).
- **Аварийные окна.** **recover**: все проверки до метки (peers/isolated/upper только вверх/часы/переполнение — recover.go:63-139), метка RECOVER первой изменяющей записью с барьером (R265), дамем сохраняется в raft.orig до успеха (R266), повтор при стоящей метке начинает с исходного дампа (R267), метка снимается последней (R398), отмена незавершённого import с публикацией F2 и удержанием писателей до нового полного import (R268/R269 — CancelImport + held()), членство/пол/отмена — одна запись на сроке выше всех сроков дампа (GUESS 26) — плюс запись member.json how=recover. Окно «снимок между F1 и Done»: FSM snapshot несёт Import целиком — окно закрыто (регрессии C-17 попытки 6 нет). **checkpoint**: ящик — новый журнал, tmp+fsync+rename+dir-fsync, старые журналы удаляются после барьера; порог max(64 MiB, размер последнего чекпоинта) — амортизация; raft — FileSnapshotStore, порог 65536/2 мин в конфиге. Отказ барьера чекпоинта — в лог, не в ответ записи. **backup**: снимок под замком ящика / fence+Clone в группе (backend.go:256-270), ответ вне замка, поток чанками с побайтовым бюджетом записи; CLI: проверка целевого пути вне -dir (R121), leftover tmp удаляется, грамматика целиком, tmp 0600, rename после успеха, прежний файл переживает сбой (R229/R245). Метрики бэкапа не заявлены (probe debt — честно).
