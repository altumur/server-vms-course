## Находки

### Блокирующие

**1. Дыра, ждущая перечня устройства, не входит ни в одно условие итога: по букве нормы итог
`done` пишется сразу, по смыслу — задача ждёт без срока.**

- Место: `VMS/05-detjob/spec/05.3-detjob.norms.md:86` (Н1.5, первая строка таблицы итогов):
  «остатка нет, `missing` пуст, не `following` и не `fetching` (глава 4); постоянные дыры итог не
  держат | `{end: done, covered, asked, events}`…»; `VMS/05-detjob/spec/05.4-detjob.norms.md:87–89`
  (Н1.4): «Элемент камеры в пульсе держателя не читается (`index_url`, `coverage` не по форме,
  V/01.2 Н1.4) — не прочитан, а не отсутствует: дыра этого куска ждёт (`waiting`, `reason`
  «`cam heartbeat unreadable: <поле>`»), «у устройства нет» не ставится; следующий пульс — снова».
- Что не так: дыра «после „видно с“», для которой перечень устройства недоступен (элемент пульса
  держателя не читается — или свежего пульса держателя нет вовсе, этот вход Н1.4 не называет), —
  не остаток (отрезка плана нет), не `missing` (это тома, глава 2 Н1.1), не постоянная дыра (ещё
  не суджена), не `following` и не `fetching`. Условия итога `done` её не держат: по букве Н1.5
  держатель пишет `{end: done, covered < asked}` немедленно — тогда ветвь «дыра ждёт» и вопрос
  устройству мертвы (устройство не спрашивается никогда). По смыслу (раз норма ввела фазу
  `waiting` для неё) задача ждёт — но срока у этой ветви нет: это не «никто не ответил» (там
  срока нет по решению), а «пульс держателя не читается» может длиться вечно.
- Контрпример: вход — задача `[1000, 1060)`, двери архива ответили спанами `[1000, 1030)`, дыра
  `[1030, 1060)` после «видно с», элемент камеры в пульсе держателя постоянно не по форме. Исход
  по одной реализации: немедленный итог `{end: done, covered: 30, asked: 60}` — минуты, которые
  могли быть у устройства, не запрошены. Исход по другой: `waiting` с `reason` «cam heartbeat
  unreadable: index_url» без срока — задача держит ёмкость вечно (ровно то, что закрывал вопрос 1
  разбора: «без срока — только „никто не ответил“»).
- Нарушенный источник: внутренняя согласованность V/05.3 Н1.5 и V/05.4 Н1.1/Н1.4/Н3; класс
  разбора V/05 (вопрос 1): «у единицы, которая кончается, каждая ветвь ожидания ведёт к итогу или
  имеет срок» (решение унаследовано нормой с этим пропуском: перечень судеб дыры в решении 1(а)
  не содержит входа «перечень недоступен»).
- Последствие: две реализации, следующие канону, расходятся в наблюдаемом поведении на допустимом
  входе (итог задачи и её снятие).
- Предложение: в Н1.4 назвать исход для «перечня нет/не читается» со сроком — например, дыра
  ждёт по `waited` (тому же `WAIT_MAX`), затем `partial` (вид — по решению: `<том>@<сервер>` здесь
  нет, возможен третий вид элемента или `device:` на весь кусок); в Н1.5 главы 3 добавить в
  условие `done` «нет дыр, ждущих вердикта устройства». Вход «свежего пульса держателя нет»
  присоединить к той же ветви явно.

**2. Накопление и сброс `waited` определены только для «пропущено»: по букве Н1.2 фаза
`unsupported` не достигает `WAIT_MAX`, итог `failed` «no model» недостижим.**

- Место: `VMS/05-detjob/spec/05.4-detjob.norms.md:54–57` (Н1.2): «**Срок — накопленная
  длительность** в курсоре: поле `waited` (секунды, ≥ 0). Держатель прибавляет к нему приращение
  своих монотонных часов между записями курсора, пока что-то пропущено; … Поле обнуляется, когда
  пропущенного не стало. Срок вышел — `waited` ≥ `WAIT_MAX` = 3600 с»; там же `:44` (Н1.1, фаза):
  «`unsupported` | вида модели нет у воркера (V/04.2): ждёт `WAIT_MAX` по `waited` (Н1.2), затем
  итог `failed` «`no model <kind> on this worker`» (V/05.3 Н1.5)…».
- Что не так: «пропущено» — определённый термин Н1.2 («`missing` — тома `silent`, `garbled`,
  `unread`, глава 2 Н1.1»); `unsupported` к нему не относится. Для задачи с неизвестным видом и
  без пропущенных томов условие накопления ложно (не растёт), а условие сброса истинно
  («пропущенного не стало» — обнуляется): `waited` остаётся 0 навсегда, `WAIT_MAX` не наступает,
  строка итога Н1.5 «модели вида нет, `WAIT_MAX` вышел» мертва. Комментарий канона
  (`detjob.subsystem.yaml:73`: «seconds something has been missing (or the model unsupported)»)
  фазу покрывает, но он не норма, и сброс при появлении модели не определён нигде: `waited` = 3000
  при `unsupported`, модель поставили, позже том умолк — до `partial` 600 с или 3600 с, норма
  молчит.
- Контрпример: вход — заказ `rec-…` с `kind`, которого нет в реестре воркера (штатный случай:
  модель не доехала). Исход по букве Н1.2: задача в `unsupported` вечно, ёмкость занята. Исход по
  Н1.1/Н1.5: через час накопленного ожидания итог `{end: failed, why: "no model <kind> on this
  worker"}`. Две реализации расходятся.
- Нарушенный источник: внутренняя согласованность V/05.4 Н1.1 ↔ Н1.2 ↔ V/05.3 Н1.5; решение
  разбора V/05 вопрос 1(г) («`unsupported` ждёт `WAIT_MAX` … потом пишется итог `failed`») нормой
  не исполнено — дефект унаследован из формулировки решения 2 («обнуляется, когда пропущенного
  не стало»).
- Предложение: в Н1.2 условия записать исчерпывающе: «прибавляет … пока что-то пропущено или
  модель `unsupported`; обнуляется, когда ни того ни другого нет».

- Нарушенный источник: договор проверки строки `ref_and_must_match` + вектор `ref_no_target`

**4. `unread`: «последняя строка пульса» без критерия «последней» при нескольких строках.**

- Место: `VMS/05-detjob/spec/05.2-detjob.norms.md:41`: «| включённый том `rec/volumes/*` без
  живого держателя, у которого есть строка пульса `rec/heartbeats/*` (последняя, пока она есть,
  даже несвежая) с `volume` — этот том и элементом записи `<rec>` в `status[]` | `unread` | …».
- Что не так: каждый воркер `rec` пишет свою строку `rec/heartbeats/<имя>`; строк, называющих
  том, может стать две (воркер переименован при переустановке — обе строки остаются, обе
  несвежие). «Последняя» — по какому порядку (возраст версии объекта? `ts`?) — не названо. Чтения:
  (а) существительное — `unread`, если **хотя бы одна** строка называет том и `<rec>`;
  (б) строгое — только последняя. При расходящихся `status[]` исходы разные: `unread` (том ждут
  час, затем `partial`) против «не `unread`» (том не ждут вовсе).
- Контрпример: вход — том `v1` включён, держателя нет; строка пульса старого имени воркера
  (`volume: v1`, в `status[]` есть `<rec>`, версия старше), строка нового имени (`volume: v1`, в
  `status[]` записи `<rec>` уже нет, версия новее). Исход по (а): том `unread` — в `missing`; по
  (б): не `unread` — дыра вечная или итог `done` раньше срока.
- Нарушенный источник: внутренняя определённость V/05.2 Н1.1 (норма читается двояко там, где
  реализации нужно решение); решение разбора V/05 (вопрос 4) слово «последняя» ввело, критерий —
  нет.
- Серьёзность: существенная (узкий вход; по последствию — разные `missing`/`partial`).
- Предложение: заменить на существительное («у которого есть строка пульса … с `volume` — этот
  том и элементом записи `<rec>` в `status[]`; таких строк нет — не `unread`») либо назвать

## Вопросы «Архитектору»

1. **`scan.partial` только у срока пропущенных томов.** Н1.2 главы 4 при выходе `WAIT_MAX` по
   `waited` велит строку события `scan.partial` до итога; Н1.4 при выходе `fetch_waited` — только
   итог `done` с `partial` (`device:<from:int>-<to:int>`), строки события нет, и схема семьи
   (`data/detjob-events.schema.json`) поля для кусков дозаписи не имеет. Строка заказа удаляется
   через трое суток (`retire_when.delete_after`), журнал живёт годами: след недошедшей дозаписи
   исчезает, а пропущенного тома — нет. Нужна ли строка события (и поле в семье) для
   `device:`-кусков, или асимметрия намеренна?

   ответил» («no recorder's archive door answered») и для нечитаемого пульса держателя
   («cam heartbeat unreadable: <поле>»); для «что-то пропущено, пришедшее прочитано» — нет
   (Н1.1 `:41`). Закрепить слово сейчас или оставить семье пульса при генерации (находка 11
   разбора)?
