# Ревью ADR-VMS-0001 и ADR-VMS-0002

**Б 0 / С 4 / М 2.** Отдельный поток VMS на маке соответствует слову владельца и ADR-0083 (146). Вариант «явное API без кода реализации» поддерживаю. До его исполнения нужно дополнить поверхности, ограничить обещание совместимости и определить, что именно проверяется на пине. Само отсутствие ещё не написанного списка/проверщика не считаю находкой: это предусмотренные шаги proposed ADR; ниже — недостающие условия этих шагов.

Независимое чтение точного `origin/owner/adr-vms-0001 = 6fe89fce7`, родитель `4928fbabb`. Чужие отчёты по этим черновикам не открывались. Нормы, код, реестры и основной worktree не менялись. Новых моделей, стендов и полных проверок не запускал.

## С2. Приёмка платформы не задаёт общего ABI, поэтому «любая реализация» пока не обеспечена

**Место:** ADR-VMS-0002, Decision Drivers п. 1, Consequences п. 2, строка 76; ADR-VMS-0001, Decision Outcome п. 3.

**Цитата:** «реализация VMS должна работать поверх любой реализации платформы, прошедшей её приёмку»; «может стоять на любой реализации платформы, прошедшей приёмку».

P/03.1-R004 прямо оставляет форму шести вызовов языку/реализации: “whose form is a matter of the language (the implementation decides)”. R006/R007 так же оставляют форму stalled/restarting. Это семантический договор, не закреплённые package names, структуры, calling convention или межпроцессный протокол. P/03.1 N5 дополнительно говорит, что стенд не наблюдает сами вызовы подсистемы; testsub не переопределяет stop calls. Две реализации могут пройти платформенные сценарии и иметь несовместимые способы подключения VMS. Из прохождения приёмки не следует переносимость готового worker binary или неизменённого binding.

У wire и in-process профилей тоже разная граница: `Platform/common/contracts/store-client.md`, Address, различает `configstore:///` — HTTP/Unix role socket — и `file://`, `memory://` внутри той же реализации. P/01.3 «Implementation decides», пп. 1, 7, не поддерживает смешение реализаций/языков через внутренний file:// формат. Список смысловых норм не превращает его в общий API.

**Предложение:** явно разделить: (1) wire-совместимость по выбранному профилю; (2) семантический SDK contract плюс публикуемое описание binding конкретной реализации; (3) пересборку/адаптер VMS при смене SDK binding. До выбора отдельного стабильного ABI обещать переносимость требований VMS, не произвольного готового бинаря. Добавить как минимум критерий реализации выбранного binding и интеграционную проверку вызовов обычного VMS-воркера; один PASS платформенного testsub этого не заменяет. API можно описать без чтения кода платформы — сам код для решения не нужен.

Это также недостающий `Bad, because`: при смене реализации платформы может понадобиться новый binding и пересборка VMS даже при неизменном семантическом контракте.

## С3. Проверка прямых ссылок и req-diff не охватывает источники значений и зависимости API

**Место:** ADR-VMS-0002, Decision Outcome пп. 4, 7; «Как держится граница», строки 68–71; Confirmation, строки 84–85.

**Цитата:** «урок, глава, якорь нормы или путь, с какого пина»; «каждая ссылка из VMS/ на платформу попадает в список»; «разница API между пинами (по req-якорям и дельтам ADR-0122)».

Разрешённый адрес не равен полному обещанию. Например:

- P/01.1 задаёт KEY_BYTES/BATCH_* ссылкой на `Platform/01-store/forms/runtime-constants.tsv`, а configured row/body defaults — через `daemon-flags.tsv` (R019). Значение меняется в форме при неизменном тексте/якоре читаемой нормы.
- P/06.8 N1.3 отсылает FOLDERS_* к форме `Platform/06-console/forms/runtime-constants.tsv`. VMS опирается на дверь папок, но не обязана повторять прямую ссылку на каждую её константу.
- P/02.1 ссылается на собственную схему; семьи, которыми пользуются воркеры и консоль, лежат в `Platform/NN-*/data/`, а не только в `Platform/common/data`. Например, P/03.4 указывает `../data/heartbeats.schema.json` и outcomes. Common contracts, OpenAPI, schema/codec/формы не обязаны иметь req-якоря.

Изменение такой зависимости может изменить допустимое тело или исход, не добавив ни одной новой ссылки VMS и не поменяв выбранный req-блок. Если ADR помечает API-изменение только по непосредственно перечисленным файлам, скрытый вход выпадет и из журнала. Ссылка на будущие дельты не определяет замыкание этих зависимостей.

**Предложение:** manifest должен включать явные нормативные зависимости каждого элемента: первичные формы значений, OpenAPI/schema/$ref, codec/layers, семантические ссылки на другие нормы. У каждой зависимости — стабильный selector и digest либо digest файла, когда устойчивого selector нет. Обязательная разница — также добавленные/удалённые элементы и изменения неякорных входов; дельты ADR объясняют изменение, но не заменяют сравнение байтов источников. Неразрешимый адрес/якорь и неподдержанный вид ссылки — ошибка или точная строка начального долга, не молчаливое отсутствие API.

Не требуется включить всю платформу транзитивно по любым ссылкам подряд: пояснительная/историческая ссылка и нормативная зависимость должны различаться явно. Для будущей проверки нужны как минимум независимые случаи: изменён только включённый constant/schema; удалён нужный req; появилась внешняя $ref; добавлена ссылка только в истории. Первые три должны попасть в аудит API, последняя не должна автоматически создавать новое продуктовое обещание.

## С4. Пин VMS и текущий main используются как будто это одна проверяемая платформа

**Место:** ADR-VMS-0001, Decision Outcome пп. 2–3, строки 52–53, Confirmation строка 71; ADR-VMS-0002, «Как держится граница», строки 68–70.

**Цитата:** «полная проверка check_spec без новых ошибок против main» одновременно с «API … на закреплённом пине выгрузки».

Нынешний `check_spec` принимает один `--root` — “complete course source root” (`skills/lesson-spec/scripts/check_spec.py:28–35`). Относительные ссылки VMS разрешаются в Platform этого дерева. Между тем ADR-0090 доп. (1), «Версия платформы», требует проверять их против COURSE_COMMIT выбранной выгрузки; текущие главы VMS ещё называют export `7a875c75`. Main платформы продолжает меняться независимо от выбора нового пина владельцем.

Новая VMS-норма может сослаться на API, которое есть в текущем main, но отсутствует на её выбранном export: полная проверка общего дерева зелена, реальная целевая платформа этого API не имеет. Возможен и обратный случай: удаление/перемещение файла в новом main краснит VMS, хотя её закреплённый API не менялся. Само изменение ветки VMS поверх свежего main не должно считаться неявной сменой платформенного пина.

**Предложение:** закрепить начальную идентичность `{full export SHA, COURSE_COMMIT, API-manifest digest, compatibility profile}` и способ её хранения/чтения. Развести две проверки: регрессия интегрируемого курса против main и совместимость текущего VMS source с **неизменяемым Platform root выбранного export**. При недоступной/несовпадающей идентичности вторая не выполнена; fallback на Platform текущего worktree запрещён. Отдельно уточнить, чем новый порядок заменяет старое требование ADR-0090 ставить всё VMS-дерево на COURSE_COMMIT выгрузки: в одном репозитории новые VMS-коммиты и независимый platform pin иначе смешиваются.

Это условие проверяемости разделения, а не просьба сейчас выбирать новый пин или запускать выгрузку. В этом ревью export `7a875c75` заново не аттестован.

## Полнота, лишнее и риски: что занести в первый список

Статический разбор Markdown targets и YAML `$ref` вне ru нашёл **451 ссылку на 54 различных существующих пути Platform**, ни одного отсутствующего целевого файла в этом срезе. Это отдельная мера, не сумма 1726 bare P-адресов; JSON `$ref` и неоформленные ссылки она не объявляет полностью покрытыми. Список нужно строить по обоим видам адресов, а не только по Markdown: P/03.1 и P/06.6 используются главным образом bare-текстом. Диапазоны глав и многострочные ссылки также требуют определённого правила.

| Поверхность | Предложение по границе |
|---|---|

У каждого элемента полезно иметь назначение `product / verification / build / history`, точный нормативный адрес, обязательные зависимости и профиль совместимости. Это не новое разрешение читать код: можно описать всё перечисленное файлами норм/контрактов. Строки истории и тестовых управляющих команд нужны для воспроизводимости, но не все являются обещанием установленной платформы приложению VMS.

Дополнительные риски для Consequences/плана, вне отдельного счёта:

- Включение внутреннего места в список не определяет политику совместимости: нужно различить изменение в новом пине, обязанность сохранять старый профиль и право владельца принять breaking change. Текущий pin защищает чтение старой спецификации, но сам по себе не гарантирует версию установленного runtime.
- Уменьшаемый долг должен идентифицировать точную ссылку/обязательство и причину, а не только число: нельзя погасить одну старую строку добавлением другой при том же счётчике.
- Для новой серии нужно до учёта исполнения выбрать однозначный ключ `VMS-0001`, адрес файла и писателей стадий в общих adr-pipeline/adr-norms либо отдельный совместимый реестр. Использовать голое `0001` нельзя: оно уже номер платформенного ADR. Проверку не следует «чинить» расширением прав spec-vms на Platform; запрос на платформенную часть проверщика идёт обычным маршрутом.
- Отсутствие своей машины/серверного раннера уже названо минусом 0001 корректно. Форма/API-list/review не должны закрывать первую приёмку VMS, её load/fault свойства или ADR-0130. Нужен отдельный исполнимый профиль и результат позже; запусков этим ревью не назначаю.
