## 3. Дефекты

### 3.1 Пилот

**П-1 (критический). После рестарта журнал raft применяется повторно к долговечному хранилищу; реплики расходятся.**
`fsm.go:81–96`: FSM пишет прямо в долговечный `d.store` из `-dir`. Индекса применённой записи
у FSM нет, и до `NewRaft` хранилище ничем не сбрасывается. Снимки raft делаются только после 8 192
записей (`group.go:203–204`). Пока снимка нет, hashicorp/raft после рестарта переигрывает журнал с
индекса 1 поверх уже применённого состояния. Каждый `put` без условия и каждое `delete` применяются
второй раз и тратят новые версии.
Проба (приложение А): группа из одного участника, три `put` без условия → версия `3`; рестарт →
версия той же строки `6`. В группе из трёх перезапущенный ведомый получает версии, которых у
лидера нет. Ломается CAS между репликами после смены лидера и стражи по версиям. Утверждение
README «в группе версию выдаёт применение записи лидером, и она одинакова у всех участников»
неверно. `TestGroupOfThree` перезапускает `two`, но версий реплик не сверяет. Основная линия эту
ловушку обошла: `raft_cluster.go:101–134` (`initial.json`, «refusing to replay over a later mirror»).

**П-2 (высокий). Чтение в группе не линеаризуемо.** `service.go:351–373`: в режиме группы сокетам
ролей назначен только `Write`, у `Get`/`List` перехватчика нет — читается локальное хранилище
участника. То же на `-api` (`api.go:54–56`). Ведомый, отрезанный от группы, и низложенный лидер
отдают старые версии. Норма P/01.1 Н3 называет ровно этот случай: «ведомый, отрезанный от группы,
не должен подтверждать эпоху, которую остальные уже сдвинули». Дверь без голоса шлёт чтение
«любому голосующему» (`doorless.go` `targets`), то есть и ведомому. Механизм линеаризуемости
(P/01.1-15 «механизм назван в описании») в README пилота тоже не назван.

**П-3 (высокий, безопасность). Поток raft пускает сертификат двери без голоса.** `group.go:330`:
`peerServerConfig(…, []string{RoleConfigstore, RoleConfigstoreDoor})` на слушателе `-raft`.
Транспорт raft других проверок не делает. Владелец листа `configstore-door` может послать
`AppendEntries`/`InstallSnapshot` со старшим сроком и переписать журнал группы. Норма: дверь
«без raft» (P/01.3-02). Привязки id участника к адресу тоже нет. У основной линии и то и другое
есть: `raft_wire.go:148`, `peerTLSClient(expectedID)`.

**П-4 (высокий). Строка двери не привязана к двери.** `group.go:1162–1184` `doorRowAllowed`
проверяет только префикс `platform/configstore-doors/`. Дверь A пишет `seen_at` двери B (или
ключ `platform/configstore-doors/x/y` вне шаблона `<id>`), и мёртвая дверь B считается в
`configstore_doors` живой. Норма: «только свою `platform/configstore-doors/<id>`» (P/01.2 Н1.3,
P/01.3 Н1.3 `door`). Основная берёт `<id>` из CN пира (`raft_cluster.go:533`).

**П-5 (высокий). Перенос копии в группу не держит гарантий `import`.** `import.go:61–150`:
- строки идут обычными `put` (`import.go:143`): версии копии не сохраняются, `-index-base` в
  выдаче не участвует (догадка А8). Свежая группа выдаёт версии с малых чисел. CAS, сохранённый
  клиентом в прежней группе, может совпасть с новой версией той же строки — именно от этого
  защищает база (P/01.1-07, Н1.3 `import`);
- обычных писателей во время переноса ничто не останавливает (Н1.3: «Обычные писатели до
  завершения не допускаются»);
- повтор завершённого переноса не отказывается (B12): все строки пишутся заново с новыми
  версиями;
- проверка «свежести» (`import.go:106`) спотыкается о строку двери, которую живая дверь пишет
  каждые 30 с.

**П-6 (средне-высокий). Upper в `recover` недостоверен.** `recover.go:270–310` `computedUpper`:
строка эпохи с нечитаемым или недесятичным `epoch` пропускается молча (`continue`); нечитаемая
строка пола (`row.Items == nil`) не учитывается вовсе. Upper выходит ниже настоящего, и выдача
эпох после восстановления может повторить номер. Норма Н3 «Проверка»: нет достоверного upper —
восстановление не выполняется; для `import` то же прямо в Н1.3 (В7 п. 3, строка 13). Основная
проверяет весь дамп через `ParseCopy` над теневым переигрыванием.

**П-7 (средний). `leader_wait` считается не от потери лидера.** `group.go:547–559`: лидер
неизвестен или его `-api` ещё не в применённом составе — запись сразу получает 503. Норма:
5 с от потери лидера. Флейк Р4-1 (`PILOT.md`) — ровно этот случай: перезапущенный ведомый знает
`leader_id`, но адреса ещё не знает. Его поправили в тесте (`waitFor` ждёт `leader≠""`), а код
остался прежним: после рестарта ведомый отказывает писателям, пока не переиграет состав.

**П-8 (средний). Сбой носителя при применении записи журнала не останавливает реплику.**
`fsm.go:92–95`: ошибка `ApplyAt` возвращается как ответ, raft идёт дальше, зеркало реплики
отстаёт молча. Основная в таком случае гасит FSM и raft (`failFSM`) и отвечает `ambiguous`
(`TestCommittedRaftIOFailureStaysAmbiguous`).

**П-9 (средний, производительность). Журнал raft переписывается целиком на каждую запись.**
`raftstore.go:134–174`: `StoreLogs` переписывает весь `log.jsonl` с fsync; `GetLog` ищет
линейно; замена — O(N·M) плюс сортировка. `TrailingLogs` не задан, то есть по умолчанию 10 240,
и порог снимка 8 192: на каждую запись переписывается до ~18 тыс. записей, каждая — до 1 МиБ
тела в base64. У основной тот же приём «переписать файл» (`raft_disk.go:47`), но журнал ограничен
(`TrailingLogs 128`, порог 256) и выбор записан в комментарии.

**П-10 (средний). admin.sock двери без голоса пишет в отдельное хранилище.** `service.go:363`:
у двери admin-сокету не даны `Write`/`Get`/`List`, и он обслуживает собственный каталог двери
(`DoorStoreFormat`). Запись оператора туда получает 200, но в группу не попадает. Норма:
«admin.sock дверь не трогает и его запросов не пересылает». Основная отвечает 403 «admin.sock is
local only» (`raft_relay.go:218`).

**П-11 (низкий). Группа на петле без `-tls`.** `group.go:126–165` и `plainStream` (`:328`).
Н1.6: «демоны — всегда с `-tls`». Нужно только тестам; в эксплуатации стоило бы отказывать.

**П-12 (низкий).** Повтор `X-Configstore-Role` на сокете роли — 400 вместо 403 (`door.go:241–247`).

**П-13 (низкий).** Предел тела служебных дверей — `-max-body` (`api.go:64`, `daemon.go:328`).
По Н2 у служебных POST предел — фиксированный 1 МиБ.

**П-14 (низкий).** `peekLine` (`daemon.go:523–534`) зовёт `Peek(n)` для n = 1…65 536 и каждый
раз ищет `\n` заново — квадратичная работа на первой строке. Соединение учитывается в
`-max-conns` только после первой строки: молчащие соединения предела не занимают.

**П-15 (низкий).** Состав меняется не атомарно: в `join` сначала `AddVoter`, потом
`publishMembers`; в `leave` сначала `publishMembers`, потом `RemoveServer`. Сбой между шагами
расходит конфигурацию raft и `members`.

**П-16 (низкий).** У лидера любая ошибка `raft.Apply` отвечает `ambiguous` (`group.go:503–507`).
`ErrNotLeader` и `ErrEnqueueTimeout` доказывают, что запись в журнал не попала, — это
`unavailable`.

**П-17 (косметика).** Мёртвый код: `hostOf` (`peer.go:264`), `WaitSignal` (`daemon.go:734`),
поле `NoFsync` — флаг читается и только пишется в журнал; честно описано в README.

**П-18 (спорно).** `recover` на коробке отвечает своими словами, а не «this build has no raft»
(А6; код 2 совпадает). `recover` снимает все строки дверей (А12) — толкование нормы, не дефект
кода.

### 3.2 Основная линия

Ошибок корректности уровня П-1…П-6 не нашёл. Замечания:

**М-1 (средний, документ).** В `01-store` на `c-v7-46` нет описания реализации, хотя его требуют
«Решает реализация» П/01.1 (пп. 1–11), П/01.2 (пп. 1–3) и П/01.3 (пп. 1–7), а чек-лист
проверяет его «чтением описания»: механизм линеаризуемости (P/01.1-15), срок памяти повторов
(P/01.1-11), профиль снимков, секрет транспорта, согласованность `backup`, взаимное исключение
`recover`. `IMPLEMENTATION.md` удалён в `084a3ee9`; `REPORT.md` — журнал переходов пинов;
`contracts/store-file.md` покрывает только п. 7 главы 1.3. Если описание лежит вне дерева урока —
пункт снять.

**М-2 (низкий).** `forwardWrite` (`raft_cluster.go:594–611`): любая ошибка транспорта — `ambiguous`,
даже отказ соединения до отправки. Это безопасно, но неточно (п. 7). У двери без голоса то же
различение сделано через `httptrace` (`raft_relay.go`); у пересылки с ведомого — нет.

**М-3 (низкий).** `main.go:236`: каталог сокетов, если его создаёт сам демон, получает режим 0700.
Группа роли не войдёт в каталог, и сокет 0660 «с группой процесса» ей недоступен. Если каталог
заранее создал юнит, вреда нет.

**М-4 (низкий, у обеих).** Любой отказ — код 2 (`main.go:39–45`), в том числе сбой слушателя на
ходу и неудача вступления за 20 с. Код 2 означает `RestartPreventExitStatus`: временную беду
systemd не перезапустит. У пилота то же для `joinGroup` (5 с).

**М-5 (низкий).** У двери без голоса `configstore_doors 1` записано в коде (`raft_relay.go:249`),
а `voters_expected` берётся из `-group-size` двери (по умолчанию 1). Пилот такой же дефект
(Р2) у себя исправил.

**М-6 (низкий, повторное использование).** Свой разбор query (`handler.go:27–71`) вместо
`httpwire.ParseQuery`; поведение совпадает (сц. 25 зелёный). Пилот это исправил на ревью (Р1).

**М-7 (производительность, выбор).** Каждая запись лидера проходит три круга: `VerifyLeader`,
`Barrier` и `Apply`. Записи идут строго по одной (`proposal`). Каждое чтение на ведомом — новое
TLS-соединение к лидеру и ограда. Журнал переписывается целиком, но ограничен. Норм это не
нарушает, но пропускная способность низкая.

**Общее у обеих.** Три тревоги Н1.3 `metrics` (состав ≠ объявленному, ведомый отстал > 1000,
выборов > 3 за 10 мин) не реализованы, и теста метрик на них нет (P/01.3-05). Выборы считаются
опросом состояния (каждые 25 мс у основной, 200 мс у пилота) — короткий срок кандидата можно
пропустить.

## 5. Итог

**Где сильнее основная линия.** Всё, где решает модель консенсуса: линеаризуемое чтение,
корректный рестарт (сброс зеркала до переигрывания), `leader_wait` от потери лидера,
`unavailable`/`ambiguous` у лидера, остановка FSM при сбое носителя, перенос в группу с базой
версий и оградой писателей, recover через `raft.RecoverCluster` в теневой копии с проверкой
всего дампа, роль `configstore` только на `-raft`, привязка id к CN, строка двери по CN, admin.sock
двери закрыт. Тесты основной бьют по отказам: смена лидера, кворум, снимок, сбой носителя.

**Где сильнее пилот.** Структура пакетов, читаемость, описание реализации по пунктам «Решает
реализация» (у основной его в дереве нет), честный учёт догадок, общий `ParseQuery`,
`configstore_doors` по строкам семьи, различение «ушло или нет» у пересылки с ведомого. Скорость:
урок с группой raft и TLS-пиром — за сутки и пять вызовов исполнителя.

**Дефекты.** У пилота шесть существенных (П-1 — повтор журнала после рестарта, подтверждён
пробой; П-2 — нелинеаризуемое чтение; П-3 — дверь в raft; П-4 — чужая строка двери; П-5 — перенос
в группу без базы версий; П-6 — недостоверный upper в recover) и около десятка мелких. У
основной — ни одного уровня корректности; главное замечание — нет описания реализации (М-1).

**Оценка генерации Kimi+MiniMax против Codex(+MiniMax).** На коробке, то есть там, где
работает общий движок и где идут автоматические сценарии приёмки, пилот почти не уступает:
порядок проверок, формы, права, копия, метка формата, `sd_listen_fds`, TLS-пир сделаны верно, и
внутренние проверки CT 103 у него зелёные. Разрыв открывается в режиме группы. Здесь нормы задают
свойства (линеаризуемость, неубывание, неповторение версий между репликами, недостоверный upper —
отказ), а не поведение двери, и TSV их не видит. Пилот прошёл свои тесты и две ревизии, но
сделал классические ошибки встраивания raft: долговечный FSM без индекса применения, чтение
мимо лидера, слабое отсечение по роли на транспорте. Ревью ведущей Kimi ловило отступления от
слов нормы (Р1–Р5, Р3-1, Р3-2), но не ловило свойства модели консенсуса.

Генерация пилота — хорошая для двери и коробки и **непригодная для группы без доработки** П-1…П-6.

**Оговорки.**
- Пины разные. Новые нормы основной (§0) пилоту не засчитаны. Все дефекты П-1…П-6 — против норм,
  которые есть и на `774fa704` (P/01.1 Н3 «Чтение линеаризуемо», «Время приёма»; P/01.1-07;
  P/01.2 Н1.3 `configstore-door`; P/01.3 Н1.3 `door`, `import`, Н3 «Проверка»).
- У основной на порядок больше раундов (64 коммита урока, цепочка приёмок и ревью) против одного
  дня пилота. Расширять объём до группы пилоту пришлось посреди работы (раунд 3), не с начала.
  Часть дефектов основной, видимо, тоже когда-то была и снята этими раундами

## Приложение А. Проба П-1

Файл `01-store/internal/daemon/zz_review_replay_test.go` лежал в копии дерева пилота в
scratchpad, не в ветке. Запуск:
`go test -mod=vendor -ldflags=-linkmode=external -count=1 -run TestReviewReplayAfterRestart -v ./01-store/internal/daemon/`.

```go
func TestReviewReplayAfterRestart(t *testing.T) {
	kit := newTestKit(t)
	kit.leaf("configstore", "localhost")
	kit.leaf("configstore-door", "localhost")
	one := startParticipant(t, kit.dir, "one", groupOptions{bootstrap: true, groupSize: 1})
	waitFor(t, "leader", func() bool { s, _ := one.status()["state"].(string); return s == "Leader" })
	read := func() string { /* GET /v1/get?key=acc/k на admin.sock → index */ }
	for i := 0; i < 3; i++ { /* POST /v1/write {"op":"put","key":"acc/k","items":{"n":"1"}} */ }
	before := read()
	one.restart(kit.dir)
	waitFor(t, "leader again", …)
	waitFor(t, "applied", func() bool { /* commit > 0 && applied >= commit */ })
	if after := read(); before != after { t.Fatalf("REPLAY: %s -> %s", before, after) }
}
```

write -> {"index":"2"}
write -> {"index":"3"}
