## Находки к кандидату

### Б01 — Повтор recover может уничтожить единственный полный дамп

**Место:** `C/internal/group/recover.go:35`, `:53`; `C/internal/group/dircopy.go:28`, `:32`. **Норма:** N13:635, :642, :645, :648 — P/01.3-R021/R398/R266/R267: сохранить строки и исходный вход до завершения, при метке повторить с того же входа.

После успешного построения результата `Recover` рекурсивно удаляет `raft.orig`, пока `RECOVER` ещё существует. Сценарий: остановка процесса посередине удаления `raft.orig` → остаются полный результат в `raft`, неполный original и метка → повтор сначала удаляет весь `raft`, затем копирует неполный original. Прежний полный вход и полный результат потеряны. Если original уже удалён целиком, ветка `dircopy.go:29` считает, что дамп не менялся, хотя это уже результат предыдущего recover; повтор вычисляет новую генерацию по другому входу.

Нужны устойчиво различимые состояния завершения и уборки, при которых повтор никогда не заменяет полный дамп частично удалённой копией. Штатный `TestGroupImportRecover` этого окна не проверяет (`C/internal/daemon/transfer_test.go:109`).

### Б02 — Ошибка checkpoint оставляет подтверждённые записи в журнале, который restart удалит

**Место:** `C/internal/boxstore/checkpoint.go:200`, `:203`; `C/internal/boxstore/journal.go:230`, `:234`, `:240`, `:66`; `C/internal/local/engine.go:107`. **Норма:** N11:733 — «Implementation decides», п. 3, сохранность подтверждённой записи/пакета; N13:197 — R107, одинаковая сохранность строк и admission.

Сценарий: checkpoint с номером следующего журнала `q+1` уже переименован в `checkpoint`; завершающий fsync каталога даёт EIO. `Checkpoint` возвращается, оставив активным журнал `q`. Ошибка только логируется. Следующая малая запись в `q` и fsync самого файла успешны; повтор checkpoint отказывает уже на первом fsync каталога, до обновления снимка. Клиент получает успех. После restart загружается старый checkpoint с номером `q+1`, а `Open` удаляет журнал `q` как уже покрытый снимком. Подтверждённая следующая запись, её id и admission исчезают.

Это один продолжающийся отказ fsync каталога при работающем fsync файла, а не предположение, что любая ошибка checkpoint сразу теряет данные. После неоднозначной публикации checkpoint требуется безопасно завершить смену журнала либо прекратить подтверждать новые записи в старом.

### Б03 — Повреждение внутри последнего сегмента принимается за оборванный хвост

**Уже объявлено автором:** `GUESSES.md:125`–127, G27. **Место:** `C/internal/group/logstore.go:108`, `:116`, `:120`; аналогично `C/internal/boxstore/journal.go:112`, `:123`. **Норма:** N11:267–270 — R028/R212, повреждение не становится отсутствием; N11:733 — долговечность и целость пакета.

Сценарий: до снимка подтверждены несколько записей односерверной Raft-группы; портится CRC полностью записанной записи посередине последнего сегмента, после неё есть другие полные подтверждённые записи. Загрузчик не отличает это от незавершённого последнего append и обрезает весь остаток сегмента. Строки и id исчезают, счётчик версий может откатиться. В box происходит такое же отсечение остатка последнего файла. Нужен отказ открытия при повреждении сохранённой середины, а допустимое восстановление оборванного append должно быть ограничено доказанным хвостом. Эта заявленная уступка не соответствует M.

### С01 — Членство Raft и запрет возврата после leave фиксируются двумя разными переходами

**Место:** `C/internal/group/member.go:143`, `:146`, `:209`, `:212`, проверка `:115`. **Норма:** N13:107 — R058, ушедшего нельзя принять до admit; N13:688 — R272, устойчивые результаты членства.

Сценарий: `RemoveServer` уже подтверждён → лидер теряется до отдельной записи `meta("left")` → новый лидер видит удалённого участника без отметки left и разрешает ему join без admit. При выходе самого лидера отдельная последующая запись ещё уязвимее. Для join симметричное окно оставляет нового voter без его API-метаданных. `memberMu` исключает конкурирующий вызов в одном процессе, но не разрыв между двумя записями. Нужен сохраняемый переход членства с завершением после смены лидера. Тест штатного leave другого участника этого не доказывает.

### С02 — Одновременные импорты одного файла считаются продолжением

**Уже объявлено автором:** `GUESSES.md:116`–119, G25. **Место:** `C/internal/core/importx.go:54`, `:59`; `C/internal/group/frames.go:64`. **Норма:** N13:700 — R415: конкурентный import/restore/recover отказывает без изменений; N13:284 — R151 разрешает продолжение после прерывания.

Два живых CLI с одинаковым digest принимаются в одну активную попытку. Второй может выполнять Transfer одновременно с первым; отсутствие другого бизнес-результата из-за одинаковых байтов не выполняет запрет менять что-либо второй конкурентной операцией. Возможный поздний отказ одного CLI после Done первого не отменяет уже исполненные шаги второго. Нужен владелец живой попытки, отличающий конкуренцию от продолжения после разрыва. Это отклонение кандидата, а не недостающая норма.

### С03 — Restore допустимой большой версии переполняет счётчик

**Место:** `C/internal/copycore/step.go:177`; `C/internal/core/importx.go:74`, `:98`; `C/internal/core/state.go:134`. **Норма:** N11:120 — форма версии из 1–20 цифр; N13:272, :278 — R141/R149, F1 и новые версии строго выше base.

Вход — две корректно завершённые LF строки:

```json
{"format":"w2c-configstore-copy","version":1,"index":"18446744073709551615"}
{"key":"acc/a","items":{},"index":"18446744073709551615"}
```

В пустой цели `base+1` переполняется в 0, затем сравнение с пустым `MaxVersion=0` поднимает Next до 1. F1 получает 1, ниже base. После переноса строки с maxUint64, Done снова переполняет оба повышения и оставляет Next=0; следующие записи получают 0 и 1, повторяя уже выданную F1-версию. Даже копия только с таким header уже нарушает требование F1 выше base. Переполнение нужно обнаружить до Begin и первой записи, отказав без изменения цели.

### С04 — Два равных Unicode-имени поля обходят запрет повторов JSON

**Место:** `C/internal/jsonx/parse.go:196`, `:237`, `:330`; `C/internal/jsonx/value.go:101`; вызов JCS — `C/internal/jcs/jcs.go:24`. **Норма:** N11:323 — R048, повтор имени в любом объекте даёт 400.

Сценарий: разрешённый put с `items` вида `{"😀":"a","\ud83d\ude00":"b"}`. `rawIdentity` сохраняет literal как одну кодовую точку 128512, а escape как две единицы 55357/56832, поэтому `seen` не видит повтор. Обычный `str()` декодирует оба в одинаковое имя; преобразование в map молча оставляет одно значение. Вместо 400 запрос может записаться. JCS через тот же parser также пропускает повтор имени. Для корректной пары суррогатов идентичность должна совпадать с literal; различать следует только действительно одиночные суррогаты. В `parse_test.go:12` есть простые повторы, этой пары представлений нет.

### С05 — Stop не сериализован с фактическим допуском запроса

**Место:** `C/internal/api/server.go:70`; `C/internal/api/write.go:55`, `:63`; `C/internal/local/engine.go:69`; `C/internal/api/service.go:43`; `C/internal/daemon/serve.go:194`. **Норма:** N13:719 — R277: прочитанный, но ещё не допущенный запрос при stop получает 503 без допуска.

Сценарий: HTTP-write прошёл `stopping.Load`, ждёт блокировку Engine → начинается stop → блокировка освобождается → `Engine.Write` допускает и журналирует запрос без повторной проверки остановки. Проверка до ожидания не закрывает эту гонку. Служебные join/leave вообще не проверяют `stopping` перед изменением членства. Нужна общая граница stop/admission под тем же механизмом, который допускает работу, включая служебные пути. Установка read deadline всем соединениям не отменяет уже разобранный запрос в обработчике.

### С06 — Poll двери выходит за общий срок запроса

**Место:** `C/internal/group/door.go:175`, `:201`, `:120`, `:123`. **Норма:** N13:601 — R252: все попытки должны помещаться в end-to-end deadline вызывающего.

После прохода попыток `send` делает sleep, затем без новой проверки срока вызывает `poll`. Для каждого voter `poll` создаёт отдельный timeout от `context.Background()`, а не от ctx запроса. Сценарий: ctx истёк у конца прохода, адреса принимают соединение, но не отвечают → запрос ещё ждёт последовательные полные poll-таймауты. Внешняя граница цикла этого не предотвращает. Передавать остаток срока и отмену в poll; фоновое обновление членства отделить от критического ожидания запроса.

### С07 — Неправильная строка chunk-size принимается и может исполнить запись

**Место:** `C/internal/httpx/conn.go:192`–202. **Норма:** N11:356, :359 — R054/R244, chunk-size состоит из HEXDIG, нарушение framing даёт 400 и закрытие до исполнения.

Сценарий: корректный разрешённый put передан одним chunk, но после шестнадцатеричного размера перед CRLF стоит пробел или табуляция без extension. `chunkSize` удаляет их и принимает размер. Тело доходит до записи вместо отказа framing. Содержимое после `;` также вообще не проверяется на форму extension. Следует разбирать всю строку по нормативной грамматике, сохранив поддержку допустимых extensions и существующий предел строки.

### С08 — Переполненный duration молча становится нулевым ожиданием

**Место:** `C/internal/flags/types.go:50`, `:157`; `C/internal/daemon/startbox.go:152`; `C/internal/local/engine.go:53`. **Норма:** N13:386 — R031, положительный duration; N13:601 — эффективный leader-wait.

`-leader-wait 999999999999999999999s` проходит regex типа. Ошибка `time.ParseDuration` отброшена, возвращается 0. На занято́м Engine запрос может немедленно получить lock_wait вместо заданного ожидания; для группы меняется поиск лидера. Нужна проверка представимости/положительности при разборе с явным отказом, а не подмена интервала нулём.

### С09 — Не объявлен обязательный конечный дисковый бюджет

**Место:** `C/ARCHITECTURE.md:109`–113. **Норма:** N13:607 — R036, finite disk and descriptor budgets; `M/Platform/common/contracts/production-obligations.md:9`–11.

Описание перечисляет сроки, connections, processing и поведение full disk, но не конечный дисковый бюджет. Сценарий квалификации длительной записи: по поставке невозможно установить согласованный предел журнала/снимков и область, в которой обещаны восстановление и продолжение после освобождения места. Обработка ENOSPC не заменяет объявление бюджета. Требование R036 не помечено Scope: production и проверяется чтением; отдельные неизмеренные производственные показатели ниже остаются NotExecuted.

### С10 — Backup возвращает отказ уже после замены прежнего опубликованного файла

**Место:** `C/internal/cli/cmds.go:80`, `:84`. **Норма:** N13:550 — R229, при отказе или отмене прежняя опубликованная копия сохраняется; N13:589 — R245, публикация backup по R229.

Сценарий: существует прежняя копия A → новая B полностью получена и записана с fsync во временный файл → rename на целевой путь успешен → fsync каталога возвращает ошибку. CLI возвращает ошибку, но target уже содержит B, а A заменена. Проверка HTTP/JSON до rename это окно не закрывает. Требуется сохранить прежнюю копию до устойчивого завершения публикации и определить безопасное завершение/восстановление при отказе последнего барьера. Это отдельное нарушение обещания backup, помимо Б02 с журналом хранилища.

## Профиль, assembly, формы и тесты

`assembly.yaml:1` (корень кандидата) содержит одну часть `01-store`; `C/acceptance.yaml:1` — format 2 с точным M SHA. Все 16 code mappings, 8 vector bindings, store/store1, backup/import/store-op/spoil-row и door adapter присутствуют. Обязательные placeholders store/store1 заданы по одному; `store` не навязывает групповые флаги. Структурного дефекта профиля/assembly не установлено. Пробел review-seam — С11.

Встроенные write-checks, daemon-flags, refusals, runtime-constants сравнены с M: байты совпадают. Формы исполняются через CEL/табличные загрузчики, а не только хранятся рядом. Pure cores отделены от I/O; Step-сигнатуры есть. Имеются property wrappers для WriteCheck, Canonical, AdmissionStep, JournalStep и Decide. Это подтверждает устройство кода; мутации строк формы не выполнялись и не объявляются пройденными. Самопроверка сложности не считает default CaseClause (`coderules/coderules_test.go:112`), но функции, уже нарушающей лимит именно по этой причине, не установлено; отдельной находки нет.

В копии **26 файлов `_test.go`, 94 функции Test…, 0 Fuzz…**. Машинных меток норм в тестах не обнаружено; M разрешает комментарии, но не требует конкретной маркировки (`spec/01-store.README.md:31`). Поэтому счёт «тесты с меткой / честные / пустышки» здесь: **0 / 0 / 0 по меткам**, а не утверждение, что остальные тесты пустые.

Содержательные тесты проверяют HTTP-фазы, права, TLS/CRL/rotation, replay, batch, version loss, reopen, copy/import и группу. Ограничения:

- `C/acceptance.yaml:6` запускает `go test -short ./...`; основные TestGroup, TestGroupImportRecover и doorpeer-тесты пропускаются через `testing.Short()` (`daemon/group_test.go:126`, `transfer_test.go:86`, `doorpeer_test.go:41`, `:82`). Данная владельцем квитанция полного race-прогона шире этого unit-профиля, но здесь не повторялась.
- `daemon/group_test.go:157` обрезает beyond-size запросы до 46/56 байт и проверяет только `!=200`. Он может пройти по 400 body_form, не доказав join_parity. Это слабое доказательство конкретного отказа, не самостоятельное утверждение, что вся проверка членства отсутствует.
- `TestGroupImportRecover` поднимает один s1 (`transfer_test.go:90`) и штатно останавливает его перед recover; это не потеря большинства трёх серверов и не прерывание RECOVER.
- Не найдены проверки конкретных окон Б01/Б02, разрыва конфигурация→meta членства, одновременных одинаковых импортов и Unicode-пары С04. Положительные тесты повтора и restart эти сценарии не охватывают.
