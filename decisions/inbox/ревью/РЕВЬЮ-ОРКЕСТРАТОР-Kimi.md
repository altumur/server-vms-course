## Находки

### Блокеры

**Б1. Авторизация всех CLI опирается на само-утверждённый `--from` — обход ролей одной строкой.**
Файлы: `cammeta-send:134`, `cammeta-accept:29`, `cammeta-done:28`, `cammeta-task:32,39,43`, `tasks.py:866-869`.
Цитата: `sender = … os.environ.get('CAMMETA_FROM', '') or 'unknown'`; в `tasks.py:868` проверяется только формат: `if not SESSION_RE.fullmatch(sender or ''): raise Refused('--from is not a session name')`.
Сценарий: все сессии и оркестратор работают под одним пользователем ОС (pilot), технической привязки вызывающего к имени нет. Сессия запускает `cammeta-accept --from coord103-src <task> --commit <hex> --receipt x` — и фиксирует чужую задачу «сделано» (обход приёмa и «свою работу не принимать»); `--from architect` создаёт корневую задачу и отвечает на вопросы; `--from architect`/`dispatcher103` закрывает чужие строки очереди (`queues.py:355-356` DONE_CLOSERS); подделанный `created_by: architect` в файле задачи проходит `_rule_problem` (`tasks.py:396-416`). Последствие: при доверии только к cooperative-агентам это не эксплуатируется, но тогда любое правило «только architect/accept-роль» — конвенция, а не свойство; при компрометации одной сессии — ложное «сделано», подмена плана, закрытие чужих строк.
Исправление: либо зафиксировать в ADR-0134 как принятое свойство («идентичность самоутверждена, сессии доверенные»), либо ввести привязку (отдельный Unix-пользователь/токен на сессию, проверяемый перед записью).

### Существенные

**С1. Правила создания обходятся прямой записью файла задачи без `created_by`.**
Файл: `tasks.py:396-400`.
Цитата: `creator = fields.get('created_by'); if not creator: return ''`.
Сценарий: правила (корень только от architect и с `adr NNNN#step`/`req З-N`, субтаск только ролью родителя, id с префиксом родителя) проверяются только для файлов с полем `created_by`. Файл, записанный в `tasks/` напрямую (все сессии — тот же пользователь ОС; каталог в синхронизируемом дереве `SESSIONS/tasks`), без `created_by` проходит все проверки создания: корень не от architect и без adr/req — валиден и может быть выдан, если `role` в ALLOWED. Тест `test_files_without_created_by_stay_valid` (test_tasks.py:991) закрепляет grandfather-правило намеренно, но ничто не отличает «наследие импорта» от нового файла. Отличается от Б1 механизмом (обход через ФС, а не CLI).
Последствие: правила создания из ADR-0134(1)–(3) не являются свойством системы, а только свойством инструмента; молчаливая потеря проверок при ручной правке/копировании файла.
Исправление: либо требовать `created_by` для новых корней (с исключением для списка импортированных id), либо явно записать границу «вне cammeta-task правила не гарантированы» в ADR.

### Мелкие

**М1. Строка, отправляемая в окно, не ограничена по длине.**
`queues.py:604`: `line = 'из очереди q:%s: %s' % task` — без TEXT_CAP (TEXT_CAP=300 применён только к хранимым `text`/`end_line`, `queues.py:171,494`). Сценарий: задача с многокилобайтным `goal` (парсер длину не ограничивает) → строка целиком уходит в терминал сессии и в `entry['line']` ledger. Последствие: зависание ввода терминала, раздувание ledger. Исправление: обрезать `line` до разумного предела с пометкой «…».

**М2. Строка TSV с id, совпадающим с id задачи, тратит id и связывает с задачей чужой ход.**
`queues.py:291` (`pending = [task for task in tasks if task[0] not in entries]`), `queues.py:596` (`tasks = tasks + [… extra]`), `tasks.py:243-254` (`line_task` не проверяет наличие link). Сценарий: в файле `queues/<сессия>.tsv` появляется строка с id, равным id готовой задачи (правится тем же пользователем ОС; `parse` отклоняет дубликаты только внутри файла). Free-text строка выдаётся, id оседает в ledger — задача больше никогда не выдаётся, а её состояние («идёт»/«на приёме») выводится из чужого хода; предупреждения нет. Исправление: при слиянии источников отклонять/журналировать id, присутствующие и в TSV, и в источнике задач.

**М3. `cammeta-send --unread/--since` читает журнал любой сессии.**
`cammeta-send:117-125,156-159` — имя сессии из argv, проверки читателя нет. Сценарий: любой, кто может запустить CLI, читает входящие строки, тексты поручений и пометки другой сессии. Последствие: разглашение внутри доверенного хоста; вероятно, допущено для отладки, но не зафиксировано. Исправление: разрешить чтение только своей сессии либо записать допуск в ADR.

**М4. `accept()` читает файлы задач вне блокировки каталога — TOCTOU между проверкой и записью.**
`tasks.py:814-822` (загрузка задач и проверка `sender != task['accept']`) до `tasks.py:833` (`with file_lock(str(directory / '.lock'), 10)` — блокировка каталога accepted, а не tasks). Сценарий: параллельная правка файла задачи (правка возможна вне flock tasks/.lock, т.к. `accept` его не берёт) между чтением и записью записи приёмки → запись о приёмке для уже изменённого `accept`/файла. Окно малое, последствие — рассинхрон записи и файла. Исправление: читать файлы задач под flock tasks/.lock (или перечитывать внутри блокировки accepted и сверять).

**М5. Фильтр управляющих символов покрывает только Cc; bidi-override и таб в `cammeta-send` проходят.**
`tasks.py:60-61` (`unicodedata.category(c) == 'Cc'`), `queues.py:74`, `cammeta-send:56` (вырезаны только `\r\n`/`\n`/`\r`). Сценарий: `title`/`goal`/`note` с U+202E (категория Cf) доходят до страницы и терминала — спуф отображения текста состояния; текст `cammeta-send` с табом уходит в окно как есть. Последствие: косметическое подделка отображения, возможны артефакты ввода. Исправление: расширить `_control` до `Cc|Cf` и фильтровать `\t` в send_line.

**М6. Гонка паузы в `cammeta-send`: строка уходит после установки паузы.**
`cammeta-send:60-66`: `is_paused` проверяется до append/send; пауза, поставленная между проверкой и отправкой, не отрабатывает (для collector-пути held-доставка паузу перепроверяет). Последствие: одна строка в обход «приостановленной копится». Исправление: перечитывать паузу непосредственно перед send либо принять однострочный допуск.

**М7. `open_count` на странице считает `cleared`-записи открытыми.**
`queues.py:563`: `sum('issued_epoch' in e and not closed(name, i) …)` — без исключения `status == 'cleared'`. Сценарий: оператор снимает запись (cleared — «id spent, запись снята», модульный докстринг), done-записи нет → строка висит в счётчике открытых неопределённо. Исправление: исключать `cleared` из `open_count` (как `newest()`).
