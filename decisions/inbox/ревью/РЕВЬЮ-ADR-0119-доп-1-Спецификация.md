# Второе ревью ADR-0119 доп. (1) (main acb1d8717) вместе с (0) («Спецификация»)

Сверено с:
- договором права («Функция `may`», вход `unit`, «Суд по цели»);
- P/06.3 Н1.9 (билет: «судится человек билета», «консоль кластера пересылает с токеном человека»);
- P/06.7 Н1.3, Н1.4 (пересылка дверей домена);
- договором сторожевой «Предел попыток»;
- P/08.4 Н1.2.

**Счёт: Б 1, С 2, М 2.**

Чисто:
- п. 1 — дверь у процесса домена, путь `/domain/verify`;
- п. 2 — ключ (автор, имя), 5 за 900 с и общий потолок; вход проверяемого не запирается;
- ответы и тело как у входа, `200 {user}`, `supervised_by` — имя.

## Б

**Б1. Право по камерам процесс домена не рассудит: у него нет единиц кластера (п. 3).**
Места: договор права, `input.unit` — `{sub, id, labels, about?, chains?}`; `"any"` — «суд домена по кластеру цели: хоть одна строка нужного ранга, область не судится» («Суд по цели»).

Чтобы рассудить `admin` на `exp/<id>` по области гранта, нужны:
- метки единицы (`labels:`);
- её `about` (камера);
- цепочки папок (`chains`, `memberof`).

Это строки хранилища кластера, их судит сторожевая консоли кластера по копии грантов `domain/grants` (P/09.1 Н1.4, P/06.7 Н1.9). У процесса домена есть гранты, но нет единиц: он может сказать только «хоть одна строка `admin` на `exp` у кластера» (`any`), а не «по каждой камере заказа». Грант супервизора на одну папку камер прошёл бы на любую камеру кластера.

Предлагаю разделить:
- **Процесс домена** сверяет пароль (`POST /api/verify` → `200 {user}`), право не судит.
- **Консоль кластера**, получив 200, судит `may(user, need = cap, unit)` проверенного человека по каждой единице `need.units`. Это та же функция и те же входы, что у сторожевой, только `user` — проверенный, а не человек билета. Ответ билету — `200 {user, need: [{unit, may}]}`, или `200 {user}` и `403 denied` с первой единицей без права.
- `domain.verify` пишет процесс домена (пароль). Суд права пишет консоль кластера в свой `audit` (например, `access.verify.need {by_sub, by_user, user, cap, units, outcome}`).

Доля норм тогда — P/06.7 (суд права у консоли кластера), договор права (`user` ≠ человек сеанса — новый вход), P/08.4 (сверка).

## С

**С1. «Только по `calls`» у процесса домена невидимо.** Консоль кластера пересылает двери домена с токеном человека (P/06.3 Н1.9: `GET domain/relays`, `domain/shared` и другие). Консоль домена и процесс видят запрос человека, а не билет. Тогда человек, у которого есть сеанс, позвал бы `POST /domain/verify` из своего браузера через свою консоль и подбирал бы чужой пароль мимо `backend`.

Нужно два правила:
- строка P/06.7 Н1.3 `POST /domain/verify` — только по билету: консоль кластера отказывает 403 сеансу человека, по куке и по токену;
- консоль кластера ставит при пересылке признак билета, например `X-W2C-Ticket: <подсистема>`. Процесс домена верит ему только от консоли домена, а консоль домена — только от соединения с сертификатом роли `console` (как «Адрес клиента» договора пересылки). Без признака — 403.

**С2. Автор — человек билета, пересланный токеном.** Ключ предела и `by_user` журнала — `user` токена, который консоль кладёт в пересылку (P/06.3 Н1.9). Билет без человека (воркер сам по себе) — 403. Нужно сказать прямо: автор = `user` токена пересылки, а не адрес.

## М

**М1. `need` в теле.** Если суд права у консоли (Б1), `need` до процесса домена не идёт. Тело `/api/verify` — ровно `{user, password}`, как у входа, остальное — 400. Ключ тела — `user`, как у входа, не `login` (п. 1 основного текста).

**М2. Аудит.** `domain.verify {by_sub, by_user, user, outcome}`, `domain.verify.limited {by_user, user}` — без пароля, в журнале `audit` процесса домена (договор журнала событий). Отказ формы (400, 413) — без строки, как у входа.
