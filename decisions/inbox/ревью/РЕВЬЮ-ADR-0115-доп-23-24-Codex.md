## С1. Барьер `rollout` не исполним на сервере с дверью хранилища без голоса

**Место:** (24), пп. 1–2, строки 296–297; унаследованный порядок обхода всех серверов из (21)–(23).

**Цитата решения:** «его `applied` ≥ `commit` лидера»; «`w2cctl rollout …` на каждом сервере по очереди … перезапуск члена, барьер п. 1».

**Норма для сверки:** P/01.3 Н1.3 `door`: «без голоса; те же сокеты и права»; в метриках — «дверь без голоса реплики строк не держит». P/01.3 Н2, `GET /v1/status`: «Door требует role=door и term/commit/applied=0».

**Проблема:** допустимы три голосующих сервера и сервер D с `configstore-door`, консолью и воркерами. D тоже нужны новые локальные права и каталог консоли. После установки файлов и перезапуска D его `/v1/rights` уже совпадает с требуемым, но `applied` навсегда равен 0; у работающего лидера `commit` уже больше 0. Барьер не завершится, последний этап включения новой подсистемы не наступит. Исключить D из обхода тоже нельзя: тогда его роли останутся со старыми правами. Дверь нельзя учитывать как дополнительного живого голосующего для условия «кворум + 1».

**Предложение:** разделить шаг сервера по режиму хранилища. Для голосующего — барьер догонки и правило сохранения большинства; для `Door` — сверка загруженных локальных прав и подтверждение работоспособности пересылки к действующей группе, без сравнения `applied` с журналом лидера. Сверку консоли выполнять в обоих случаях. Явно считать кворум только по голосующим. Добавить сценарий «3 голосующих + сервер с дверью без голоса»: права двери обновлены, консоль служит нужным манифестом, обход завершается.

## М1. `served` нельзя сравнивать с SHA-256

**Место:** (24), п. 1, строка 296.

**Цитата решения:** «отдаёт `served` и `sha256`, равные хешам обхода».

**Норма для сверки:** P/06.5 Н2, `/manifest/<sub>/source`: «`served = rev` — ревизия, которой консоль служит». P/02.3 Н1.5: `rev` — целое 1…9007199254740991, `sha256` — строка `[0-9a-f]{64}`. Команда `rollout` получает только пары `<sub>=<sha256>`.

**Проблема:** буквальная проверка обоих полей на равенство переданному хешу всегда неуспешна. Смысл сверки понятен, но формула смешивает номер ревизии и дайджест и будет перенесена в условие завершения команды.

**Предложение:** записать отдельно: `source.sha256 == ожидаемый хеш` и `source.served == source.rev` для ответа из каталога запуска, как требует действующий P/06.5. Если нужно сравнение именно с сохранённой ревизией `put`, её следует отдельно сохранить вместе с хешем и сравнивать `served` с ней. Проверять ответ для каждого манифеста обхода и именно у консоли текущего сервера.

Колонки конвейера и другие репозитории не изменялись. Требуется разбор С1; М1 достаточно уточнить при переносе в нормы.
