## С1. Нет исполнимой границы между «ответил в начале» и «поднялся до первого запроса»

**Место:** доп. (28) п. 1 (а)–(в), строки 329–331 ADR; перенос в P/02.4 Н1.9 `pre` и `leader`.

**Цитаты решения:** «каждый опрос … читает `commit` лидера заново, в своём начале»; «голосующий, который в начале опроса ответил, сверяется с этим `commit`»; «который в начале не ответил … при его первом ответе».

**Связанная норма:** P/02.4 Н1.9 `pre`: «сначала commit лидера … затем applied каждого голосующего». P/01.3 Н2 даёт отдельный `GET /v1/status` каждого члена — локальное наблюдение; общего снимка доступности членов в момент чтения лидера нет.

Пункт не задаёт последовательность запросов, позволяющую выбрать между (б) и (в). Первый обход статусов после чтения лидера вправе считаться ответами «в начале опроса». Тогда остаётся такой ход перед перезапуском `b`:

| Шаг | Наблюдение/событие |
|---|---|
| 1 | Три голосующих `a`, `b`, `c`; лидер `a`. `c` лежит, его `applied=100`. `pre` читает у лидера `commit=100`. |
| 2 | `a`, `b` принимают запись 101; `c` её пропускает. |
| 3 | `c` поднимается с `applied=100` **до первого запроса к нему**. Первый запрос сразу получает `Follower`, `leader_id=a`, `applied=100`; ни одного неответа команда не наблюдала. |
| 4 | По (б) `c` сравнивается с начальным 100 и считается догнавшим. Живых три, то есть кворум + 1. После перезапуска `b` запись 101 есть только у `a`; запись в кластер стоит до догонки `c`. |

В отличие от разобранного случая, команда не получила начального неответа, который включил бы (в). Слова «на каждого голосующего» в заголовке и «при первом ответе» только в ветке (в) не запрещают этот порядок. Уточнение про отдельный второй `pre` его тоже не устраняет.

Уже выполненный FIX_C0 не снимает неоднозначность сетевого порядка: в `ro.qnt:106` `snap` при FIX_C0 атомарно отбирает `st == "ok"` в момент начала опроса (`start:178`, второй `pre:289`); восстановившийся с пропущенной записью член не добавляется в `c0` (`recover:408`). У исполнителя указанного набора HTTP-чтений такого знания о состоянии `c` в момент чтения `commit` нет. Это чтение границы абстракции, не новый вычисленный контрпример модели и не повтор прежнего С1 без проверки решения.

**Предложение:** задать единый исполнимый порядок для каждого голосующего в каждом новом опросе: дождаться первого ответа его статуса → прочитать и зафиксировать для него `commit` лидера → последующими ответами этого голосующего дождаться `applied ≥` зафиксированного значения. Сохранить проверку `state`/`leader_id`, предел `ROLLOUT_WAIT`, новый target во втором `pre` и `-last`. Target больше не двигать при непрерывной записи. Тогда не требуется различать недоступные общие моменты «ответил в начале» и «не ответил в начале»; в приведённом ходе target для `c` будет не ниже 101. Иной протокол допустим, но его порядок чтений должен быть назван столь же явно.
