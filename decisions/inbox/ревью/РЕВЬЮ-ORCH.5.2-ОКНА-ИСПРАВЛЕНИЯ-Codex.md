## Новые причины ремонта

### Н-Б1. Отложенный close/send применяется к новому владельцу повторно использованного слота

Код: `taskwindows.py:344,377–378,895–918,919–925`. Основание: ADR0134 Add21.1,25,29.3; окно закрывается по завершению именно своей задачи; сохранение единственного писателя.

1. P планирует close для принятой и влитой A в run-1/h-A.
2. Q закрывает A, фиксирует retired и очередным законным проходом создаёт B в освободившемся run-1/h-B. Создание B уже сериализовано и соблюдает лимит.
3. P продолжает _execute старого action(task=A,name=run-1). Строка 896 перечитывает текущую B только по имени run-1; строка 906 проверяет готовность B, а не принадлежность A.
4. P закрывает h-B и _retire удаляет B; результат всё ещё сообщает task=A и outcome=closed.

Последствие: Незавершённое окно B закрыто; его writer/slot освобождён по чужому основанию. Аналогичный stale send может послать A-текст в B; мутация после внешнего close также может retire уже следующую запись.

Доказательство: UNIT_AST_EXACT D01; positive N01 + STATIC finite schedule. Все handles, task IDs, процессы и ответы здесь synthetic; настоящего Orca-вызова не было. Нормальный предшествующий случай проверен до неблагоприятного.

Новизна/разделение причин: Новая привязка _execute к свежему ledger[name] в ремонте. Старый Б1 о нерезервированном create не пересчитан как новая находка: N08 теперь проходит.

Рекомендация: Резервировать close/send с op_id/task/handle/incarnation конкретной записи, перепроверять тот же токен при взятии действия и фиксации результата; не исполнять устаревший action после смены записи. Длинный внешний вызов не помещать под общий lock.

### Н-С1. Удалённая сверка и Git-проверка выполняются под общим ledger lock

Код: `taskwindows.py:248–255,834–835,840–849,746–759,551–554,564–574; tasks.py:1221–1226`. Основание: Цель ORCH.5.2: short reservation, callbacks/timeouts/lock scope; ADR Add22/25 и команда background из ORCH.5 требуют сохранять управляемость уже открытых окон.

1. После неизвестного create есть законная запись CREATE_UNKNOWN.
2. Проход входит в locked(timeout=10), затем внутри него reconcile вызывает adapter.find → terminal list с допустимым timeout=20.
3. При штатной задержке list больше 10 секунд параллельные background/другой pass не могут взять ledger lock и завершаются TimeoutError. Несколько записей удлиняют удержание последовательно.
4. Второй участок под тем же lock вызывает plan→default_merged→Git fetch(timeout=20) для принятой работы, то есть проблема не ограничена create.

Последствие: Восстановление одного окна блокирует управление всеми слотами/команду фона на время внешних операций; отказ нового прохода возможен раньше штатного timeout callback. Это не требование нового численного бюджета и не вечный deadlock.

Доказательство: UNIT_AST_EXACT D06, actual owned flock; positive N08 outside-lock launch + STATIC timeout schedule. Все handles, task IDs, процессы и ответы здесь synthetic; настоящего Orca-вызова не было. Нормальный предшествующий случай проверен до неблагоприятного.

Новизна/разделение причин: Общий locked и reconciliation появились в ремонте; до него этого нового общего lock не было. Не дублирует Н-Б1: даже неизменная запись одного окна воспроизводит задержку.

Рекомендация: Снять снимок/зафиксировать токены под lock, выполнить list/Git/source I/O вне него, затем применить результат под lock только к прежней операции. Не держать общий lock при model_source, если его внешние зависимости не ограничены как локальное чтение.

### Н-С2. Цикл review_of обрывает весь проход RecursionError

Код: `tasks.py:1587–1599; taskwindows.py:528–541,458–459,849; cammeta-task:46,102`. Основание: ORCH6: до review известны предмет/автор/точная редакция; неизвестное/непригодное назначение удерживается, а не срывает выдачу независимых задач; явное требование invalid-input fail-closed в ORCH.5.2.

1. Architect через разрешённый add создаёт root SELF, role=judge, accept=architect, adr=0134#5, review_of=SELF. Все обычные поля проходят актуальные render/parse; self-ref не проверяется.
2. Готовый standalone review передаётся в default_author. Он находит ту же запись и рекурсивно вызывает себя без visited/глубины.
3. RecursionError выходит из plan/run_pass, не превращается в hold только SELF; cammeta-windows ловит LedgerError/OSError/TimeoutError, но не эту ошибку. Два взаимно ссылающихся review дают ту же причину.

Последствие: Одна допустимая для нового CLI метадата прекращает обработку других готовых окон до действий. Это отказ обработки данных, не исполнение вложенной команды.

Доказательство: UNIT_AST_EXACT D12 using actual add_task/render/parse; STATIC whole-pass propagation. Все handles, task IDs, процессы и ответы здесь synthetic; настоящего Orca-вызова не было. Нормальный предшествующий случай проверен до неблагоприятного.

Новизна/разделение причин: Рекурсивное review_of и его CLI-проводка добавлены именно baf68a2; в before default_author не рекурсивен.

Рекомендация: Проверять существование/тип/цикл review_of при разрешении ссылки, с canonical task-id visited; дать точный hold/error проблемной задаче, продолжить независимые. Не добавлять новый публичный DSL.
