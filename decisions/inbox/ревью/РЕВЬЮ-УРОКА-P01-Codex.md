## С1. Обещание повторять тот же отказ противоречит процедурам early, guard и CAS

**Место:** P/01.1-R088, `spec/01.1-store.norms.md:538–542`; R078–R086, R131–R132. Русская пара — `ru/spec/01.1-store.norms.md:367–371`.

**Цитата нормы:** «the same write with the same `id` will get the same refusal (the admission time does not decrease)»; перед этим `expired`, `early`, `conflict`, `guard` не занимают id.

Для `early` монотонность даёт другой результат: команда с `id=a`, `not_before=1` при admitted=1 получает early; при admitted=2 та же команда проходит, поскольку id не занят и условие теперь выполнено. Guard/CAS тоже могут измениться между попытками. Только уже наступивший expired неизбежно остаётся expired при том же deadline и неубывающем admission. Рекомендация клиенту не повторять прежнюю команду не меняет алгоритм двери и не делает такую команду невозможной.

**Проверка:** буквальный судья `claimStableRefusal` нарушен двухшаговой трассой Quint; алгоритмический судья early на той же базе чист. См. модель ниже.

**Предложение:** ограничить обещание неизменного отказа случаем expired; для прочих незапомненных отказов явно указать повторную проверку по актуальному admission/состоянию. Сохранить клиентское правило перечитать условие и принять новое решение. Добавить в seams повтор с тем же id после early и продвижения часов; текущий s2 повторяет запрос без id и этого противоречия не фиксирует.

## С2. Форма флагов допускает запуск без TLS, который две нормы прозы запрещают

**Место:** P/01.3-R006 `group.identity`, `spec/01.3-store.norms.md:49–50`; R011, строка 232; `forms/daemon-flags.tsv:23–28`; ADR-0125 (2) п. 4.

**Цитаты нормы:** «-api and -join only with -tls»; «daemons — always with -tls». В форме -tls необязателен, `bad` у -api/-raft запрещает отсутствие TLS только вне loopback; у -join такого условия нет вообще.

Например, `-dir /tmp/store -id a -api 127.0.0.1:9000` без -tls проходит названные условия формы, но не group.identity. При -join расхождение ещё шире. Одновременно refuse_start, таблица флагов и Н4 говорят об отказе именно для адреса вне loopback без TLS. Получаются разные правила запуска внутри одного источника; грамматическая сверка форм не выбирает одно из них.

**Предложение:** явно разделить режимы, если локальный HTTP box отличается от TLS-пересылки группы, и согласовать group.identity, Н1.6, refuse_start/Н4 и CEL `required`/`bad`. Зафиксировать ожидаемые исходы для loopback -api, loopback -join и адреса вне loopback без TLS. Вопрос касается условия запуска, а не проверки содержимого сертификата, которая обоснованно осталась вне формы флагов.

## С3. Для старой floor-строки копии нет исполнимого правила переноса после New floor

**Место:** P/01.3-R006, `spec/01.3-store.norms.md:83`, `floor/import:111–149`, `box:168`; R026, строки 344–346.

**Цитаты нормы:** «platform/epoch_floor is an ordinary row»; «transferred rows keep the versions of the copy»; «the floor as the first write, then the rows»; «it only grows».

Входная копия может содержать floor F0. Фаза New floor поднимает его до F1>upper≥F0. Затем Transfer велит переносить строки копии, не исключая старую floor-строку. Буквальный перенос её items/index возвращает F0 и нарушает рост. Отказ от этой строки или замена её содержимого сохраняет безопасность, но такой шаг и его влияние на обещание сохранить версии/проверить полноту не заданы.

Это неполнота алгоритма, **не допустимый всей нормой unsafe-ход**: глобальное «it only grows» уже запрещает понижение. В модели выбрано безопасное предположение о новом floor; оно не закрывает пробел текста. Нового Б за разрешённое понижение не выставляется.

**Предложение:** назвать старую floor-строку входом вычисления upper/generation_at и явно определить её исключение либо преобразование при Transfer. Задать итоговые items, index, generation_at и критерий полноты; повтор после частичного переноса сохраняет тот же F1. Проба — backup уже восстановленного хранилища с существующим floor, затем import и продолжение прерванного import: финальный floor выше входного и не заменяется старой строкой, остальные строки/версии сохранены.

## М1. Комментарий формы исключает код 2 из exit !0, хотя проза требует любой ненулевой

**Место:** `forms/refusals.tsv:5`, строки recover_isolated/recover_upper/recover_peers; P/01.3 Н3 шаг 0 и Н4; ADR-0125 (2) п. 6.

**Цитата нормы:** «exit !0 — a non-zero code other than 2». В Н3/Н4 — «code ≠ 0», без исключения 2. Кроме того, отсутствие обязательного флага может дать именно 2 по правилам формы flags.

**Предложение:** убрать «other than 2»: exit !0 означает любой ненулевой, exit 2 — строго 2. Если нужен иной смысл, это надо согласованно изменить в прозе и словаре формы; сейчас такое дополнительное ограничение не задано решением ADR-0125.
