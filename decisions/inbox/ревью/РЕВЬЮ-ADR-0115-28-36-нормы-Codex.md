Прежний С1 обоих ревьюверов из (34), (35) закрыт: `target` прямо говорит «чтение commit, начатое до разрыва, цели не даёт». Предыдущие находки и явно принятые пределы модели повторно не считаются. Новая находка относится к добавленному в норме времени фиксации состава голосующих.

## С1. Состав из mode остаётся основой кворума и во втором pre после смены состава группы

**Место:** P/02.4 Н1.9 `poll`, строка 492; `pre`, строки 479–483; `limit`, строки 543–544.

**Цитаты:** «Голосующие — voters статуса своего члена **при mode**, их адреса — members того же ответа»; `pre` выполняется «перед действиями и ещё раз перед перезапуском члена», порог — «кворум — ⌊voters / 2⌋ + 1». Названный предел параллелизма запрещает оператору два одновременных `rollout`, но не изменение состава хранилища. P/01.3 Н1.3 `group.join` разрешает вступление до объявленного размера, переходную чётность — с `-force`; операции `join`/`leave` существуют на работающей группе.

В каждой партии читается свежий статус своего члена, но его новый `voters`/`members` правило использовать или хотя бы сравнивать с исходным снимком не велит. Новый опрос получает новые цели, сохраняя прежний набор участников и прежний знаменатель кворума.

Ход без двух параллельных `rollout`:

1. Объявленный размер группы — 5, фактические голосующие пока `a`, `b`, `c`; все живы. Число ниже объявленного даёт тревогу P/01.3, но отказ `rollout` по этому условию не задан. Команда на `b` делает `mode`, сохраняет троих, проходит первый `pre`, исполняет get/install.
2. Вступают `d`, `e` (переход через четверых — с `-force`); теперь фактических голосующих пять. Затем `d`, `e` недоступны. Группа ещё работает: `a`, `b`, `c` — её кворум из трёх.
3. Перед перезапуском `b` второй `pre` опрашивает только старых `a`, `b`, `c`, считает по прежнему размеру 3: кворум 2, порог 3. Все трое догнали цель — проход. Свежий статус `b` уже содержит пятерых, но это поле по `poll` не пересматривается.
4. Перезапуск `b` оставляет двух из пяти. Теперь нет кворума 3: обход сам останавливает запись, хотя новый `pre` как раз должен был этого не допустить.

Это не отказ после последней проверки, не прежний случай пропущенного падения и не незамеченный секундный разрыв. Актуальный состав уже виден команде до перезапуска; норма предписала использовать старый снимок. Запрет параллельной установки/правки MANIFEST_DIR из P/02.5 не запрещает административный `join`/`leave`.

**Предложение:** явно задать неизменность состава голосующих как предусловие обхода и запретить оператору менять его до окончания команды; либо при обнаружении изменения `voters` в свежем статусе прекращать текущую команду до перезапуска/начинать новый опрос с новым составом и новыми целями. Как минимум второй `pre` не должен успешно считать кворум по снимку `mode`, когда уже наблюдается иной состав. Отдельно назвать поведение при изменении адресов `members`. Полной защиты от внешней смены состава после последнего чтения это не обещает: такой предел следует назвать, как уже названы остальные пределы опроса.

Ход проверен чтением договоров и арифметикой кворума; он не выдаётся за трассу Quint. Готовность всей модели диапазона и реализации не заявляется.
