## Ответ 1. hashicorp/raft используется по-настоящему?

**Внутри пакета `internal/group` — да (ок).** Прямые вызовы API библиотеки: `raft.NewRaft` (node.go:167), `DefaultConfig`+`ValidateConfig` (136–158), `BootstrapCluster` (193), `AddVoter`/`RemoveServer`/`GetConfiguration` (436, 472, 506), `Apply` (369), `HasExistingState` (160), `NewFileSnapshotStoreWithLogger` (95–101), `NewTCPTransportWithLogger` (233) и собственный mTLS stream layer через `NewNetworkTransportWithLogger` (tls.go:252). FSM реализует `raft.FSM` (`Apply`/`Snapshot`/`Restore`, fsm.go:261–273). Самописного ядра консенсуса нет: выборы/термы читаются только через `raft.State()`/`CurrentTerm()`; пакет по существу является набором адаптеров (fsm.go:1–2). Пустых импортов `_ "..."` нет; в `go.mod` нет `replace`/`exclude`/`retract`; `vendor/` нет; `go.sum` содержит корректные суммы `github.com/hashicorp/raft v1.7.3` (единственная версия, как у канона).

**Но в собранном бинарии raft никогда не стартует (находка 1).** `runRaftDaemon` (internal/daemon/group.go:504) никто не вызывает; единственный вход `daemon.Run` (internal/daemon/daemon.go:26) безусловно поднимает one-box store (`OpenFileStoreWithReporter`, daemon.go:97). Флаги `-bootstrap`/`-join`/`-raft`/`-api`/`-group-size` парсятся (flags.go), но `Run` их игнорирует. `internal/group` импортирует только сам `internal/daemon/group.go`. Сам кандидат описывает группу как будущую стадию («the later group implementation», «the group stage will», «the group/door stage will declare its own», ARCHITECTURE.md:156, 202–204, 296, 438–439). То есть это не обёртка-пустышка над raft, а написанный, но не подключённый код группы.

## Ответ 2. Адаптеры по common/versions/README.md

1. **Долговечные LogStore и StableStore — ок (с оговоркой находки 6).** `durableStore` реализует оба интерфейса (asserts file_store.go:291–292): лог — один JSON-файл на запись (`logs/log-%020d.json`), stable — файлы с base64url-именами ключей. Запись атомарная: tmp + chmod 0600 + `Sync` + rename + sync каталога (writeAtomicFile 246–277), выключателей durability нет (норма N1.3 `durability`); `GetLog` → `raft.ErrLogNotFound` (109); диапазон first/last пересобирается при открытии и держится при Store/DeleteRange; переоткрытие покрыто тестом (file_store_test.go:10–40).
2. **Идентичность mTLS — частично (пробелы 7–8).** `LoadTLSKit` (tls.go:34–81) грузит `ca.pem` и `ca.next.pem` (ротация CA) и листовую пару `<dir>/<role>/server.pem|key`; сверяет, что сертификат принадлежит ожидаемым роли и id (77–79). `CertificateIdentity` (86–120): роль из URI SAN `urn:w2c:role:*` или префикса CN; id из DNS SAN (все DNS SAN обязаны совпадать) и CN вида `<role>.<id>`. `verifyPeer` (122–139): роль из закрытого allowed-списка + `certificate.Verify` по roots. На `-raft` допускается только роль `configstore` (NewTLSTransport 233–254), на `-api` — `configstore` и `configstore-door` (internal/daemon/group.go:564): это соответствует N1.6 (`C01-RAFT-DOOR-LEAF-01`). Чего нет: проверки отзыва (revoked/crl.pem демон не читает вообще) и сверки алгоритмов подписи цепочки.
3. **Атомарное применение FSM — ок.** Каждая запись проходит через FSM (fsm.apply 76–156): проверка формата/версии команды, запрет хвостовых данных, admission-время из реплицированной записи (одинаково на всех репликах — `ApplyConsensusWrite/Batch/Floor`, mutation.go:276, 409). Отказ проверки (`OpError`) возвращается как ответ рекорда, а не как сбой FSM (fsm.go:147–154). Граница атомарности: батч — один лог-рекорд, один кандидат-state, одна версия (норма N1.3 `batch`). Долговечная фиксация (`commitCandidateLocked`, mutation.go:571–598) выполняется **до** публикации `state.Store` под мьютексом мутации; ошибка/таймаут 30 с коммиттера → 503 и state не публикуется — откат не требуется. Команды членства персистят до публикации карт (fsm.go:135–143); при сбое персиста состояние сходится реплеем лога после рестарта. Порядок локов единый (fsm.mu → store.mu) — контракт библиотеки о конкурентности FSM соблюдён.
4. **Снимки и восстановление — ок.** `NewFileSnapshotStoreWithLogger` keep=2 (node.go:95–101), порог 8192 / интервал 30 с (139–140); `FSMSnapshot.Persist` с `Cancel` при ошибке записи (fsm.go:181–189); `Restore` проверяет формат/версию и хвост (211–239). Старт: STATE грузится до `raft.NewRaft` (117–134), `HasExistingState` различает bootstrap и перезапуск (160–190). Admission-время хранится в STATE и в снимке FSM (`LastAdmission`) — восстановленный узел продолжает монотонность (норма N1.3 `admission`).
5. **Исходы ошибок — ок.** `applyPayload` (node.go:365–397): `ErrNotLeader`/`ErrEnqueueTimeout`/`ErrRaftShutdown` → 503 `unavailable` («no leader»); прочие сбои коммита, отмена ctx и истечение commitWait → 503 `ambiguous`; ответ-ошибка FSM → 503 `unavailable`; отказ проверки → `OpError` из рекорда. Членства: 400 `badrequest` (форма), 409 `refused` (другой raft-адрес, больше объявленного, чётность без `-force`, последний voter, неизвестный), 403 `forbidden` (join_left, до admit), 503 `unavailable` (коммит членства/конфигурация). Слова N4 (`join_parity`, `join_left`, `no_leader`, `leader_lost`→ambiguous) соблюдены.

## Итог

1. Как код пакета `internal/group` библиотека hashicorp/raft v1.7.3 используется по-настоящему: настоящие вызовы API, FSM, транспорты, членства, снимки; своего ядра консенсуса, пустых импортов и подмены модуля нет — вопрос 1 закрыт «ок» на уровне пакета.
2. Кандидат как групповая сборка несоответствует: группа не подключена к входу демона (1), отказ `box_no_raft` отсутствует (2), `recover` отсутствует (3) — три находки уровня Б; это не может компенсировать прогон стенда P01.66.
3. Адаптеры в основном по норме (долговечность, атомарность FSM, снимки/восстановление, исходы ошибок), но с пробелами: revocation и sigalg в mTLS, фиктивные `elections_total`, полная перезапись STATE на запись против RUN-W01, молчащее `admission_ahead`.
4. Условие соответствия: подключить `runRaftDaemon` к `daemon.Run` с отказом `box_no_raft` для box-сборки, реализовать `recover`, закрыть mTLS-пробелы; после этого код группы выглядит рабочей основой. До этого зачёт по группе (P/01.3 N1.3 group/lifecycle) давать нельзя.
