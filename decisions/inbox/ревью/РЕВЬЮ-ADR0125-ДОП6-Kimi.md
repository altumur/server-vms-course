## Ответы на вопросы задания

### 1. Достаточно ли п. 1, чтобы проверить, что заголовок воспроизводит генератор?

Да, при связке с п. 4. П. 1 задаёт свойство (описание содержит: колонки входа, поля выхода,
правила преобразования, выбор варианта — генератор воспроизводится по описанию), а механизм
проверки назван в п. 4: повтор пилота 46c, эталон — настоящие пакеты уроков. Одного п. 1 без
п. 4 недостаточно: критерий не говорит, чем сверяется описание.

Фактическая сверка действующего `gen_refusals` с критерием п. 1 (исходная точка доп. (6)):
колонки входа описаны в коде явно (`PLAIN_COLUMNS`/`RESPONSE_COLUMNS`, комментарий
«P/05 has ResourceError text bodies…», строки 230–236); выбор варианта описан НЕ — он
закодирован ветками `L.key` (строки 251, 285, 328, 351). Это ровно пробел, который доп. (6)
устраняет; после исполнения пп. 2–4 описание должно покрывать выбор варианта. Следствие для
исполнения: «заголовок» следует понимать как описание у генератора (docstring/комментарии
к вариантам + раздел выбора), иначе проверяющий 46c не найдёт носителя описания; это
оформление, не смысл.

### 2. Набор колонок как единственный признак варианта: где он не различает выход, который должен различаться?

Перечень веток по `L.key` в `tools/normgen/gen_*.py` среза 0db5dfb0, с классификацией по
критерию «набор колонок входа различает выход?»:

1. **`gen_refusals.py:251,285` — P/05 vs P/06 (RESPONSE-вариант).** Набор колонок одинаков:
   оба урока имеют `… word response_schema cause …` (15 колонок, проверено по заголовкам
   `Platform/05-resource|06-console/forms/refusals.tsv`; код: `RESPONSE_COLUMNS`, строка 247
   `self.response = head == RESPONSE_COLUMNS`). Выход различается: полные определения схем,
   сверка required/optional-ролей со схемой и допуск `?`-полей подключены только для
   `L.key == "06-console"` (строки 251, 285–301); P/05 получает только проверку имён схем
   (строка 252). Набор колонок не различает. Развилка по п. 4 доп. (6): либо унификация
   варианта (P/05 получит сверку ролей — его выход/проверки изменятся), либо вопрос
   «Архитектору».
2. **`gen_families.py:32` — P/01 vs P/02+ (`DOC_MODE`).** Вход — общие таблицы
   (`Platform/common/data/catalog.tsv`, `layers.tsv`, `outcomes.tsv`, `key-placeholders.tsv`,
   `outcome-units.tsv`), набор колонок одинаков для всех уроков; выход различается:
   `RUNTIME_FLAT` (P/01, «byte for byte») против `RUNTIME_DOC` (P/02+). Набор колонок не
   различает; причина различия — историческая, формой входа не выражается → кандидат
   на вопрос «Архитектору» (п. 4) или на отдельный форменный признак.
3. **`gen_door.py:1206` — та же граница P/01/P/02+** (P/01 остаётся на старом `gen_door`,
   остальные → `gen_door_lesson.py`); вход P/01 — не door-таблицы (в `Platform/01-store/forms/`
   их нет), сопоставление колонок здесь неприменимо, класс тот же, что в п. 2 перечня.
4. **`gen_door_lesson.py` (строки 735, 1076, 1123, 1189, 1371, 1390) — P/06 vs остальные
   уроки с дверями.** Вход — OpenAPI-спецификация урока плюс `door-roles.tsv` с фиксированными
   колонками `method path roles norm` (строка 1273), одинаковыми для всех уроков. Выход P/06
   различается: привязка каталога (`p06CatalogueBinding`, mounted/subs-варианты), стабильная
   идентичность операций (old140 + шесть опубликованных HEAD), приоритетная поверхность в KIT.
   Набор колонок не различает; форменный признак — наличие монтирования/каталога в spec
   (не «набор колонок»), либо вопрос «Архитектору».
5. **`gen_cmdtests.py:433,1514,1521,1552` — P/03 (`workerpolicy`).** К выходу P/03 добавляется
   пакет policy-machines из собственных форм урока; признак — наличие policy-форм у урока
   (не набор колонок cmdtests). Переносимая ветка: новый урок с теми же policy-формами по
   п. 2 должен получить тот же вариант.
6. **`gen_refusals.py:328,351` — P/02.** Набор колонок у P/02/P/03/P/04 одинаков
   (проверено), выход сейчас различается по имени; по п. 3 доп. (6) различие снимается
   унификацией — это не случай «должен различаться», а назначенный к удалению долг.

Не примеры: `gen_manifest.py:191` и `gen_row_writes.py:40` — одноурочные генераторы
(`raise`/отключение для прочих уроков, варианта выбора нет); `gen_vectors.py` — ветки P/02/P/06
опираются на wire-объявления (`consumers.tsv`/`stages.tsv`), различие по форме входа частично
уже выражено, остаток — в перечень п. 4.

### 3. Верны ли пп. 3–5 для `gen_refusals` и пакетов на `ce8d6db6`?

- **П. 3 — верен по фактам.** Колонки P/02, P/03, P/04 одинаковы (14 колонок, заголовки
  совпадают). P/02 сейчас отличается по имени урока: `L.key != "02-installer"` в строках
  328, 351 (обработка `word`-токенов и `word_any`). Необязательные поля P/06 определяются
  записью `?` в `fields`: код строк 281–290, в P/06 такие записи есть (например,
  `detail,error,supervision?`). Следствие, значимое для проверки делом: переход P/02 на
  общий вариант меняет его выход в двух местах — появятся `Named`/`WordCell` (`word_any`)
  и 8 `word`-ячеек P/02 без backticks (`busy`, `refused:catalogue`, …) по правилу строк
  328–334 станут `-`; в P/03+ такие же без-backtick ячейки уже сейчас дают `-`
  (свидетель: `generation_exhausted`). Если норма P/02 требует этих слов в выходе, правка
  формы P/02 (backticks) — отдельный шаг spec103; это предмет повтора 46c, не противоречие
  доп. (6).
- **П. 4 — исполним.** Правка `gen_refusals` локальна (ветки 328, 351; выбор варианта уже
  по набору колонок, строка 247). Перечень веток для coord103-tools — в ответе на вопрос 2.
- **П. 5 — верен и согласован.** `ce8d6db6` — закреплённая выгрузка (З-18/З-19; ADR-0083
  доп. (140) п. 2: tools разрешает её до полного SHA; в git курса её нет — выгрузка хранится
  вне main, это нормально). Непересборка согласована с ADR-0129 доп. (26) п. 4 и доп. (28)
  п. 6 (пробы владельца на пине не меняются). Эталон для 46c — настоящие пакеты: выход P/02
  меняется (п. 3), поэтому сверку P/02 с пакетами, собранными до правки, следует читать с
  этим следствием (эталон общего варианта — выход уроков той же формы P/03/P/04 либо
  пересобранный пакет на выгрузке позже `ce8d6db6`).
