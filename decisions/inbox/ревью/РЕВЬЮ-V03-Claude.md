## Существенные

**С-1. Оффер первого зрителя сверяется с «кодеком раздачи», которого ещё нет; README решает обратное**
- **Место.**
  - `03.3-live.norms.md:55`: шаг 5 — «оффер без секции `m=video` или без кодека раздачи (глава 4) — 400 `bad offer`».
  - `03.4-live.norms.md:41`: «кодека раздачи в оффере нет — 400 `bad offer`».
  - Но источник открывается «при **первом зрителе**» (`03.4:25`, `03.2:61`), а параметры потока шлюз смотрит «после
    каждого ответа» (`03.4:53`), «параметров ещё нет — …» (`:62`).
  - README решение 3 (`README.md:51-52`): «кодек, которого нет в оффере, — ответ с запиской `codec` в пульсе, не отказ».
- **Контрпример:** первый зритель H.265-камеры, оффер браузера только с H.264. На шаге 5 кодек раздачи не известен:
  - A сверяет по `codec` пульса держателя (такого поля в V/01.2 Н1.4 нет);
  - B открывает источник до ответа;
  - C пропускает проверку и шлёт ответ без видео.
  - Исходы разные; по README — записка, не 400.
- **Предложение:** назвать, откуда кодек известен на шаге 5 (например, открыть источник и ждать первого ключевого кадра
  в пределах `ICE_WAIT`). README — по норме.

**С-2. Метки раздачи ставит первый зритель, второй с другой сетью получает 409 и шлюз, до которого не дотянуться**
- **Место.**
  - `03.1-live.norms.md:36`: `labels` — «где зрители: метки сети зрителей (`public-address` — вне локальной сети)».
  - `:50-51`: «второй зритель той же камеры, любого её потока, — 409 `exists` …; его `labels` строку не меняют».
- **Контрпример.**
  - Оператор в LAN открыл камеру 7 (`labels: []`), раздачу взял шлюз без публичного адреса.
  - Зритель снаружи шлёт `POST /live/streams {cam: 7, labels: [public-address]}` → 409, `/live/where/7` даёт адрес
    внутреннего шлюза. Смотреть он не может до конца `grace` после ухода первого.
  - Норма не говорит, что делать странице или консоли: правка `labels` — `PUT` с `view` → 403 (`:52`).
- **Предложение:** назвать исход — объединение меток (кто вправе), раздача на набор меток или «смотрит только сеть
  первого» как принятое ограничение в Н1.2 и лекции.

**С-3. `grace` без границ**
- **Место:** `03.1-live.norms.md:37`, манифест `:27`: `grace: {type: int, default: 30}`, без `minimum`/`maximum`.
- **Контрпример:**
  - `grace: 0` — подписка снимается в том же проходе, первый зритель на `not yet` ждёт вечно (спрос снят до заведения);
  - `grace: -5` — арифметика отсчёта (`03.5:31-33`) не определена;
  - `grace: 10^9` — строка живёт годы.
  - Дверь всё это принимает.
- **Предложение:** `schema: {minimum: …, maximum: …}` в каноне манифеста и строка Н4.

**С-4. CORS двери шлюза: перечень урока уже платформы и без `Authorization`** (класс V/02 С-10)
- **Место:** `03.3-live.norms.md:81-82`: «CORS — P/03.4 Н1.7 `cors` (…; методы `POST`, `DELETE`, заголовок
  `Content-Type`, `Expose-Headers: Location`…): странице хватает нормы».
- **Источник:** договор сертификата роли, `mixed` `cors.allow`: методы `GET, HEAD, POST, PUT, DELETE`; заголовки
  `Authorization, Range, Content-Type`.
- **Контрпример:** токен двери страница несёт в `Authorization: Bearer` (`:35`). Реализация по перечню урока не
  разрешает `Authorization` в preflight, и браузер не шлёт оффер. Остаётся `?t=`, но норма его выбор не обязывает.
- **Предложение:** ссылка на `cors` договора без своего перечня.

**С-5. Удаление учётки: где и с каким правом снимаются гранты; исход неудачи не назван**
- **Место:** `03.6-live.norms.md:73-74`: «`DELETE` снимает гранты на имя через свою консоль: `GET /domain/grants`, `PUT
  /domain/grants/<кластер>` без строк этого `subject`».
- **Источник:** P/08.4 Н2 — `PUT /domain/grants/<кластер>` требует `admin` (Н1.5). У человека на `/live/accounts`
  проверен `admin` кластера (`03.6:48`).
- **Контрпример.**
  - Учётка `wall` доставлена книгой в m2, гранты на неё есть в строке `domain/grants/m2`. Какой `<кластер>` правит
    шлюз m1 — свой или все? Права на строку m2 у человека нет.
  - A удаляет строку учётки и отвечает 200, гранты в m2 живут. Человек, позже заведённый с именем `wall` (имя
    освободилось), получает `view` на камеры m2.
  - B отвечает 403 и строку не удаляет.
- **Предложение:**
  - порядок: сначала гранты во всех строках, где есть `subject`, затем строка учётки;
  - нет права или отказ — учётка не удаляется, 403/503 со словами;
  - либо пометка имени, как `domain/deleting/<имя>` у людей (P/08.4).

**С-6. Создание учётки в кластере без домена: проверка имени не определена**
- **Место:** `03.6-live.norms.md:67-68`: «Перед созданием шлюз спрашивает `GET /domain/users` **через свою консоль** как
  этот человек … человек с таким именем — 409». Книга (`:80`): «только в установленном домене».
- **Контрпример:** кластер без домена, у консоли нет `/domain/users` (404 или 503).
  - A отказывает в создании (503 «консоль не отвечает», `:62`).
  - B создаёт: людей домена нет.
- **Предложение:** «домена нет (`domain/keys` нет) — проверка только по своей таблице».

**С-7. OpenAPI: маршруты консоли `/live/accounts…` лежат на сервере двери шлюза**
- **Место:** `03-live.api.openapi.yaml:11-15`, `:72-163` — один `servers` (`http://127.0.0.1:{port}`, дверь шлюза) и пути
  `/live/accounts…`.
- **Источник:**
  - чеклист «Двери и маршруты»: каждый полный URL — `servers` своего владельца;
  - договор `gate-and-pass`, «Передача»: консоль передаёт «метод, путь, query», и путь консоли зависит от корня (`/accounts`
    при `CONSOLE_ROOT=live`, `/live/accounts` у смонтированной).
- **Контрпример:** шлюз A ждёт `/live/accounts`, шлюз B — `/accounts`. Консоль с корнем `live` передаёт `/accounts`, и
  A отвечает 404.
  - У путей учёток нет `403` сторожевой и `401`, которые получает клиент консоли.
- **Предложение:** разнести на два сервера (консоль — `/live/accounts`, дверь шлюза — путь, который приходит
  передачей). Если путь передачи — забота платформы, сослаться на её правило.

**С-8. Чеклист обещает «`PUT` с одним `view` — 403», приёмка этого не проверяет**

**С-9. Клиенты RTSP: ёмкость, `viewers`, удаление строки — не определены**
- **Место.**
  - `03.6-live.norms.md:92-93`: «Клиент RTSP — зритель: сессия, ёмкость (`headroom`), ветвь (глава 4)».
  - Подписка точки — «подписка раздачи этого шлюза на тот же (камера, поток) — её, иначе своя, … закрывается через
    `LINGER` = 10 с после последнего».
  - Против этого глава 5: `headroom = max(0, capacity − sessions − answering)`, `sessions` — «сессий сейчас»
    (`03.5:66-67`); удаление строки — «ни у одной подписки нет зрителей» (`:32`); `viewers` — «сессий раздачи по всем
    подпискам» (`:75`).
- **Контрпример:** клиент RTSP смотрит поток через подписку раздачи `7`, браузеров нет.
  - Строка `7` удаляется через `grace` (зритель RTSP — «зритель»?), и подписка закрывается под ним? Или RTSP держит
    строку вечно?

  - A и B расходятся в ёмкости и в журнале `live.view.ended`.
- **Предложение:** в главе 5 — сессии RTSP в `sessions` и `viewers`. Подписку, которую держит клиент RTSP, строка не
  держит и не снимает (или наоборот), сказать явно.

**С-10. Отбой: порядок «сессии нет — 404» и «нет токена — 403»**

- **Предложение:** Н1.3 по порядку: допуск токена (403) → сессия (404) → раздача и владелец (403).
