# Ревью ADR-0119 доп. (9) — «Спецификация»

Второй ревьювер. main 7a5f0e917. Сверено с:
- P/06.1 (Н1.6 `service`, Н2 «Пакетная дверь», Н3 «создать», «править», «удалить», «пакет»);
- P/06.7 Н1.15;
- договор сторожевой «Надзор»;
- V/08.6 Н1.5;
- `exp.subsystem.yaml`;
- ревью review-claude `РЕВЬЮ-ADR-0119-0112-23-нормы-VMS-Claude.md` Б1 и его предложения 1–3.

**Счёт: Б 1, С 2, М 3.**

## Б

**Б1. Дверь, судящая надзор по ролям, оставляет подделку `supervised_by` и расширяет `*` до остановки всех записей.**

Доп. (9) закрывает сеанс только при `required(u, s)`. Отсюда два следствия, которых в тексте нет.

1. **Подделка у автора без надзора.** Пусть ни одна роль автора не несёт `supervision.exp`, тогда `required` — `false`. Сеанс автора с `edit` на `exp` пишет `POST /exp/parts` сам и вписывает `supervised_by: <любое имя>`.
   - Платформа поля не знает: имён VMS в платформе нет, доп. (5) п. 1.
   - `fixed` судит только неизменность.
   - Держатель надзор не судит (V/08.6 Н1.5).
   - `export.made` назовёт подтвердившим человека, который ничего не подтверждал.

   Значит, фраза «Поле `supervised_by` пишет только этот путь» не держится. Путь закрыт лишь тем, чьи роли требуют надзора, а журналу камеры верят все.

2. **`*` у двери строк.** В договоре «Надзор» строка `limit` говорит: одна испорченная строка роли даёт `*` всем людям всех кластеров. До (9) это останавливало только действия с надзором, то есть экспорт (доп. (7) п. 4). У двери строк `required(u, s) = true` для любой `s`. Значит, пока строку роли не починят, сеансом нельзя записать ни одной строки ни одной подсистемы: ни камеры, ни правила, ни папки единицы. Консоль у людей встаёт на запись по всему домену. Это новый масштаб отказа, и его стоит назвать решением, а не выводить из `*`.

**Предложение** (рекомендую 1):
1. **Слово манифеста «только по билету» вместо суда по ролям** — это вариант 2 review-claude в общем виде. Единица или объявленная таблица несёт `writes_via: [<sub>…]`. Запись её строк человеком (одиночная, строкой пакета, тело) идёт только по билету названной подсистемы; сеанс и билет иной подсистемы получают `403 {"error": "via ticket"}`. Чтение не меняется.
   - Это расширение `service` (P/06.1 Н1.6). `service` закрывает и чтение и пускает только свою подсистему, а здесь закрыта только запись, и подсистемы названы.
   - `exp` объявляет `unit.writes_via: [backend]`. Тогда:
     - подделка закрыта для всех авторов, а не только для тех, у кого требуется надзор;
     - `*` и копия ролей у двери строк не участвуют, и расширения отказа нет;
     - заодно закрыты прежние пределы V/11.4 «части мимо `backend`» (маска, `EXPORT_TOTAL_MAX`).
   - Надзор по-прежнему судит только `backend` по заголовку и `/domain/verify`.
   - Цена — новое слово в P/02.1 (загрузчик, связь «подсистема из `writes_via` — в каталоге») и строка у дверей P/06.1. Оба в моей доле.
2. Если остаётся суд по ролям (доп. (9) как есть), надо дописать две вещи:
   - (а) При `*` у двери строк закрыты записи всех подсистем. Это отдельная строка в `limit` и решение. Сигнал — тот же `domain.roles.unreadable`.
   - (б) Подделка `supervised_by` при `required: false` — предел, его надо назвать. Держатель в V/08.6 его не закроет: он видит строку, но не путь, которым её записали.

## С

**С1. «Билет подсистемы, который прошёл проверку».** Консоль не знает, звал ли билет `/domain/verify` перед записью: запись строк и проверка — разные запросы, и связи между ними у неё нет. Норма поэтому может сказать только «по билету». Чей билет — тоже открыто. Запись строк `s` по билету открыта любой подсистеме с записью `calls` на строки `s`. Если её воркер надзор не судит, это тот же обход.
- При варианте Б1-1 вопрос снимается: подсистемы перечислены в `writes_via`.
- При варианте Б1-2 нужна строка: «по билету — любой подсистемы с `calls` на строки `s`, судит адресат по заголовку `X-W2C-Supervision`; подсистема, которая надзор не судит, его обходит — предел».

**С2. Охват двери.** «Запись строк подсистемы» не перечисляет двери. Для варианта Б1-2 предлагаю перечень и решу его сама, если нет возражений:
- создать, править, удалить единицу `s`;
- двери тел и байтов единицы `s`;
- `POST` и `DELETE` объявленной таблицы `s`;
- строки пакета с ключом `s/…` (отказ одной строки — 403 всего пакета, как у шага 3 «пакет»);
- запуск операции `s` (P/06.9).

Строки папок и членства (`platform/*`) и просьбы P/06.4 в охват не входят. Проверка надзора — после `may` (шаг прав). Тогда «копия не дошла» сперва даёт `503` у `may`, а не `403`.

Для варианта Б1-1 охват тот же, без операций: операция пишет своё, а не строки единиц.

## М

**М1. Слово отказа.** `403 supervision required` (или `via ticket`) — новое слово у P/06.1 «Отказ: `error` и `field`», без `field`. В журнале — `access.denied` с причиной. С `SUPERVISOR_REQUIRED` у `backend` (V/11) это слово не спутать: у них разный адресат.

**М2. Доля P/06.7.** Что меняется в P/06.7, из (9) не видно. Н1.15 уже даёт `required` той же функцией. Предлагаю: правка в P/06.1 и в договоре «Надзор» (строка `door`), а в P/06.7 — только ссылка.

**М3. Временная строка V/11.8.** «До правки P/06.1, P/06.7 — `NOT_SUPPORTED`» — это зависимость двух долей. Предлагаю записать её в `adr-norms.tsv` (моя строка — «доля платформы: … — снимает `NOT_SUPPORTED` V/11.8»), чтобы «Спецификация VMS» сняла `NOT_SUPPORTED` после вливания платформы, а не по памяти.
