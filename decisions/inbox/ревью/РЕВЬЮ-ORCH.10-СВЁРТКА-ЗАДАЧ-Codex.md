## Нормальный путь и сохранённые границы

`cammeta-task:91–95,123–125` разбирает group и передаёт список в `tasks.set_group`. Команда требует architect; это принятое заявленное имя, не новая аутентификация. Под общим tasks/.lock сначала читаются и проверяются все затронутые файлы, строится trial, затем каждый файл заменяется через atomic_write. Невалидный последний ID не приводит к записи первых. Конкурентные note/group используют один flock; в собственном контроле обе правки сохранились.

`Model.__init__:389–399` хранит groups отдельно от children. `_compute`, `_rollup`, effective_after, `_cycle_members` графа исполнения, definition_hash, add_task, `_accept_locked` и `_hand_in_locked` не получили зависимости от group. Зафиксированы raw/AST hashes неизменённых методов и конкатенаций в PROTECTED-BLOCKS. Hash по-прежнему состоит из goal/role/accept. Это подтверждено обычной группировкой и clear без потери комментария/note/ID и без изменения состояний. Приёмные и handed-файлы команда group не пишет.

`_groups` сообщает об invalid reference через errors и не меняет состояние самой работы. Missing target, self, target с собственной group, попытка сделать существующую свёртку членом другой, прямой parent-descendant конфликт проверяются. Нового правила «group id обязан иметь префикс» здесь не нужно: префикс относится к parent. Реальные дети сохраняют primary parent на странице.

`group_members` включает явных членов и их parent-потомков с set-защитой от дублей. `group_summaries` считает фактические state через Model, не превращает root в DONE. В выбранном спектре accepted/cancelled исключены из open; event wait, rejected-to-next-attempt и broken child остаются учтены. Root может оставаться самостоятельно принятой задачей при открытых group members: это допустимая сводка показа, а не скрытая преграда приёму.

## С1. Смешанный цикл parent/group принимается без ошибки

**Координаты:** `tasks.py:403–421` (`group_problem`), `1906–1919` (`set_group` trial); потребитель — `report.tpl.html:986–1001` (`taskForest`). **Основание:** назначенные проверки циклов/конфликтов и цель «показываются под ней». **Доказательство:** G08, U05, STATIC. Это новый root cause group-validator, не прежний dependency cycle исполнения.

Положительный случай A/B→R принимается. Для контрпримера все четыре задачи создаются настоящим AST-точным add_task в собственном каталоге, с допустимым происхождением и префиксами:

1. Корни G.1 и G.2; G.1.1 — parent G.1, G.2.1 — parent G.2. Подзадачи ставит роль соответствующего родителя.
2. `set_group('G.1', architect, rollup='G.2.1')` допустим.
3. `set_group('G.2', architect, rollup='G.1.1')` тоже проходит. Оба group поля остаются действующими, errors о цикле нет.
4. Отношение «под кем рисовать» стало G.1→G.2.1→G.2→G.1.1→G.1. В нём нет корня.

Каждая проверка идёт от target только по parent. Она не видит предыдущую group на другом участке кольца. Отдельная проверка «target не имеет своей group» не исключает чередование двух parent и двух group.

UI не зацикливается бесконечно: seen/drawn ограничивают обход. Но fallback произвольно добавляет G.1 в roots, несмотря на её group, и рисует разорванное дерево. U05 получил roots=[G.1] и циклический kids. Сводки двух roots взаимно захватывают чужие части. **Не утверждаю**, что строки исчезли или изменилось исполнение: обнаружено принятие непредставимой иерархии, которое должен отсечь validator.

**Рекомендация:** проверять весь effective parent-путь для пробного display graph (действующий parent, иначе допустимая group) после всех изменений batch. Цикл метаданных сообщать как invalid group, не превращая его автоматически в dependency error исполнения. Проверять и связанные старые group, а не только прямую цепь target.parent.

## М1. Новые display children создают ложное ожидание after на Ганте

**Координаты:** `report.tpl.html:990–1001` — расширенный kids передан в `taskTreeSpans`; `1007–1023` — start(after) использует end зависимой строки, а end обходит этот kids. **Основание:** group не меняет правила/связи задачи; подпись дерева `1118` обещает порядок очереди по after. **Доказательство:** U04, exact before/after Node VM. Это только ошибка показа, не доказательство блокировки реальной очереди.

Легальная конечная ситуация: R самостоятельно принята (`сделано`), A открыта и получает `group:R`, B открыта с `after:[R]`. У R нет настоящих parent-детей. По модели B уже может идти: R завершена, незавершённая A не становится новой зависимостью B.

На exact before функциях B имеет span=[0,0]. На exact subject тех же строк B получает [1,1]. Новая связь A.group→R добавляет A в kids[R], end(R) вместо−1 становится0 и start(B) прибавляет1. Отдельного rule/gate в backend не появилось — только диаграмма стала изображать несуществующую преграду.

**Рекомендация:** разделить дерево показа и граф зависимостей/настоящих parent. Можно растягивать визуальную свёртку на members, но вычисление удовлетворения after должно использовать исходную семантику завершённой задачи. Не лечить это добавлением искусственных after или изменением состояния R.
