## Ответы на шесть вопросов ревью

1. **Какие запреты пропущены, без которых окно нанесёт вред?** — Пропущены четыре. (а) Служебное состояние оркестратора: «Файлы задач руками не правят» (ВЗАИМОДЕЙСТВИЕ-СЕССИЙ.md §1a) — в промпте нет, окно может править `tasks/**`, `queues/**`, `handed/`, `accepted/`. (б) Push: «остальные пушат только свои коммиты и только если перед ними нет чужих незапушенных» (СЕССИИ.md §1.4) — промпт не разделяет «своя ветка» и «main». (в) Уборка: своё дерево нельзя удалять до приёма, «дерево, на которое указывает квитанция, остаётся до переноса доказательств» (доп. (13)). (г) Запрет «новых окон» без исключения «большая задача — фоновым агентом внутри» (СЕССИИ.md §1.22) вынуждает нарушать или стоять.
2. **Что в общей части лишнее или двусмысленно?** — «Правила проекта: CLAUDE.md» лишняя: файл и так загружается автоматически при старте внутри репозитория (подтверждено этой пробой: содержимое AGENTS.md/CLAUDE.md пришло в системный промпт сессии Kimi само), а принцип 3 черновика велит общие документы открывать по необходимости. «Другие каталоги только читать» двусмысленна: не закрепляет базис (задачи ревью сидят на срезе: P01.16.1 «база bc7e3912…», ORCH.6.2 «main не ниже f76fd7bb0») и не называет зеркала/чужие worktree (СЕССИИ.md §1.4: «Общие папки … — зеркала origin/main: в них не коммитят и не держат веток»).
3. **Хватит ли окну файла задачи? Три примера?** — P01.16.1 вытянет: цель самодостаточна (пути, запреты, формат находок, место отчёта). P01.67 вытянет: решение в том же файле — «answered: 2026-11-09T18:11:14Z architect: Да по всем, с двумя уточнениями…», плюс note перекрывает часть цели. P01.62.5 — на пределе: «Как P01.46.2» и «после зелёного P01.62.4» требуют чужих квитанций (зелень P01.62.4, фильтр blob 5ce37700…), а маршрута к ним в промпте нет — см. Б2. Общий вывод: ревью-задачи и писатель вытянут файл; задачи-продолжения зависящих цепочек — только с путём к квитанциям.
4. **Как окно узнает о решениях владельца после создания задачи?** — Частично покрыто: ответы приходят в поле `answered:` файла задачи (пример P01.67), отказы — «вставляются новому окну в промпт» (таблица черновика). Не покрыто: ADR-дополнения, принятые после создания окна, — дерево создано на базисе старта, промпт fetch не велит; окно дополнений середины задачи не увидит. Правка в С2.
5. **Где окно может сломать чужую работу?** — (а) `main` и зеркала: лишний пуш в main ломает общее зеркало и сигнал «красный main» (доп. (18) п. 3). (б) `/home/pilot/cammeta-sessions` (задачи, очереди, handed/accepted) — одно неверное ручное исправление портит учёт всех окон. (в) Чужие worktree/клоны, включая `/home/pilot/server-vms-course` (зеркало). (г) Преждевременное удаление своего дерева: квитанция ссылается на его файлы (доп. (13)). (д) Замороженные байты `Source/vms/*` (AGENTS.md) — не в запретах промпта, хотя писатель их и не должен трогать.
6. **Как проверять окно до сдачи, кроме приёмщика?** — Действующие слои: (а) само окно по чек-листу (ветка, базис, чистота diff, тесты/check_spec — доп. (18) п. 3); (б) родитель читает отчёт до своей сдачи — квитанция P01.16.1: «Родитель полностью прочитал отчёт и лично сверил все 16 корневых причин»; (в) оркестратор проверяет протокол (definition hash, attempts, window mark — tasks.py `hand_in`); (г) красный main и check_spec на точном коммите как внешний сигнал. В пробу: сверить фактические чтения/команды окна с границами промпта и замерить стартовый расход.

## Находки

### Б

**Б1. Нет запрета править служебное состояние оркестратора.**
В §1a: «Файлы задач руками не правят» (доп. (9), разбор задач P/01). Промпт молчит — окно с полным доступом pilot может править `tasks/*.yaml`, `queues/*.tsv`, `handed/`, `accepted/` и ломать учёт всех окон. Сценарий: окно «исправляет» свою задачу в yaml вместо `cammeta-task ask`, оркестратор выдаёт двойную работу.
Правка — в строку «Запреты:» общей части после «чужие сессии не тревожить…»:
```
файлы задач и служебные каталоги /home/pilot/cammeta-sessions (tasks/, queues/, handed/, accepted/) не править — только команды cammeta-task;
```

**Б2. Не назван путь к квитанциям зависимостей.**
Таблица «Что ещё даётся» обещает «родитель и зависимости — их квитанции, по ссылке», но промпт не говорит, где квитанции лежат. По факту: сдача — `/home/pilot/cammeta-sessions/tasks/handed/<id>.json`, приём — `accepted/<id>.json` (проверено: оба файла по P01.62.5 существуют, содержат commit, receipt, from, utc). Без этого окно P01.62.5 не найдёт квитанцию «зелёной» P01.62.4 иначе как перебором диска — а перебор диска противоречит экономии и запретам.
Правка — в общую часть после строки про файл задачи:
```
Квитанции сдачи и приёма любой задачи: /home/pilot/cammeta-sessions/tasks/handed/<id>.json и accepted/<id>.json, читать по имени задачи.
```

**Б3. Push не разделён: своя ветка против main.**
Добавка писателя: «опубликовать в main», но общие запреты не велят остальным не пушить main. СЕССИИ.md §1.4: «остальные пушат только свои коммиты и только если перед ними нет чужих незапушенных»; доп. (12): «автор публикует, приём проверяет». Сценарий: окно-рецензент решает «подправить опечатку» и пушит main — зеркало и сигнал приёма ломаются для всех.
Правка — в строку «Запреты:»:
```
push — только ветку своей задачи; в main пушит только писатель по своей добавке, остальные main и чужие ветки не пушат;
```

### С

**С1. Запрет новых окон без исключения про фонового агента.**
СЕССИИ.md §1.22: «Большие задачи — фоновым агентом… у Codex и Kimi — фоновый агент своего CLI». Задача-окно длиннее ~20 минут либо нарушит запрет, либо встанет и сожрёт слот лимита окон.
Правка — в строку «Запреты:»:
```
новых окон и сессий не заводить; задачу дольше ~20 минут или на много файлов веди фоновым агентом внутри своего окна;
```

**С2. Решения владельца после создания задачи: промпт молчит (вопрос 4).**
Дерево стоит на базисе старта; дополнения ADR в середине задачи окно не увидит без fetch. Правка — в общую часть перед строкой «Конец:»:
```
Перед сдачей: git fetch origin; если с твоего базиса вышли дополнения к ADR из задачи — учти их или спроси заново.
```
(Допустим и вариант перекладывания на оркестратора: свежий базис отвечает приёмщик, а не окно; тогда вместо строки — строка в таблицу «Что ещё даётся». Предпочитаю вариант выше: он закрывает оба примера P01.67 и ORCH.6.2.)

**С3. Строка про рабочий каталог двусмысленна (вопрос 2).**
Не закрепляет базис, не называет зеркала и чужие деревья. Сценарий: окно ревью переключает ветку на origin/main «посвежее» и рецензирует не тот срез (задача ORCH.6.2 сама требует «main не ниже f76fd7bb0» — у промпта нет слов, запрещающих уйти выше).
Правка — заменить строку:
```
Рабочий каталог: {worktree}; базис указан в задаче — ветку не переключать и не обновлять. Зеркала (/home/pilot/server-vms-course) и чужие деревья не трогать: не коммитить, не держать веток.
```

**С4. Бюджет старта 1–2 КБ не сходится с текстом промпта.**
Опрос: «Объём старта 1–2 КБ сверх CLAUDE.md». Измерено на черновике: общая часть 1743 байта, добавка роли 400–508 байт, файл задачи 0,3–1,6 КБ (P01.13.1.3 — 1,6 КБ) — суммарно 2,5–3,9 КБ сверх CLAUDE.md (7,5 КБ). Либо ужимать общую часть (кандидаты на сокращение: «Правила проекта: CLAUDE.md.», см. С5), либо честно поднять бюджет до «≈4 КБ сверх CLAUDE.md для цепочек» и проверить на пробе.
Правка — в раздел «Что показал опрос» п. 3:
```
3. **Объём старта 1–2 КБ** сверх `CLAUDE.md` для задач-листьев (ревью без зависимостей); до ≈4 КБ для задач с `note`/`answered` и цепочками. Промпт ужать: убрать дубли автозагрузки (С5), бан «CLAUDE.md».
```

**С5. «Правила проекта: CLAUDE.md» — дубль и противоречие принципу 3.**
CLAUDE.md (симлинк на AGENTS.md, 7539 байт) при старте внутри репозитория загружается средой сам; строка велит читать то, что прочитано, и расходует бюджет. Эта проба подтверждает: Kimi получил AGENTS.md в системный промпт автоматически (по путям ворктри и cammeta-sessions).
Правка — заменить строку:
```
Правила проекта уже в контексте (CLAUDE.md/AGENTS.md загружены средой). Чего не хватает для задачи — спроси, не додумывай.
```

### М

**М1. Добавка рецензента не требует сценарий находки.**
Квитанция-пример P01.16.1: «Находки с файлом и строкой, уровнем Б/С/М и сценарием»; в добавке «счёт Б/С/М с файлом и строкой» — сценария нет, без него находка непроверяема (правило самого черновика: «Находка без сценария не считается находкой» — но только в общей форме не написано; в добавке рецензента нет).
Правка — в добавку рецензента:
```
Отчёт: файл из цели, ветка `<провайдер>/<задача>`, коммит только отчёта, счёт Б/С/М; каждая находка — с файлом, строкой и сценарием.
```

**М2. Писатель: в main — только свои файлы.**
§1.4: «если файл уже грязный чужой правкой, коммитить только свои ханки». В добавке писателя этого нет.
Правка — в добавку писателя:
```
В main — только свои файлы и свой коммит: чужих правок и чужих веток в публикацию не брать.
```

**М3. Таблица «Что ещё даётся» фиксирует базис неверно.**
Строка «рабочий каталог | создаётся оркестратором от origin/main» противоречит задачам с закреплённым срезом (P01.16.1: «база bc7e3912…»; ORCH.6.2: «main не ниже f76fd7bb0» — обе взяты из целей задач).
Правка — строку таблицы:
```
| рабочий каталог | создаётся оркестратором; базис — из задачи, по умолчанию origin/main, ветка по задаче |
```
