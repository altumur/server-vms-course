## 1. [Блокер] Один `sub` запроса против двух разных `sub` обязательных проверок

**Место:** `decisions/0097-гранты-по-подсистемам-и-папкам.md:85`, §2; там же `:110`, `:113`, §5. Связанные: ADR-0094 доп. (9) п. 2 (`decisions/0094-…:351`), ADR-0095 §3/§5, ADR-0096 §4.

> Все проверки одного запроса — с одним `sub` действия

Но §5 задаёт для записи папки `admin`, `sub: platform`, а для добавляемого члена — ещё:

> **`edit` на `U` в её подсистеме**

**Контрпример.** У человека ровно две строки:

```yaml
- {cap: admin, sub: platform, scope: 'folder:F'}
- {cap: edit,  sub: cam,      scope: 'unit:cam/7'}
```

Один PUT состава добавляет `cam/cameras/7` в F. По §5 он разрешён: есть оба права, цель уже доступна по прямому гранту. По §2 с `sub=platform` отфильтруется строка edit/cam; с `sub=cam` — admin/platform. Одного допустимого `sub` нет. `null` не решение: таблица §2 назначает записи папок platform, а null намеренно отключает отсечение по подсистеме.

Тот же конфликт у смешанного пакета B9. При `admin sub:cam unit:cam/7`, без прав rec, пакет пишет cam/7 и её часть rec. Если весь пакет проверять с sub=cam, строка rec тоже проходит через about=cam/7. Если проверять с sub каждой строки, пакет отказывается. ADR-0094 требует права по каждой строке; §2 ADR-0097 не называет исключения и даёт противоположную единицу проверки. У шагов ADR-0095 есть ещё строки итога/счётчиков и смешанная запись folderIds.

**Последствие.** Буквальное выполнение §2 либо запрещает разрешённые §5 действия с узкими грантами, либо позволяет записать часть другой подсистемы без её права. Разные реализации получают разные исходы. Противоречие внутри нового ADR, а не претензия к выбранному дополнительному полю.

**Предложение.** `sub` должен принадлежать отдельному проверяемому действию/записываемой строке, а не всему HTTP-запросу. Внутри одного действия ссылки unit_of/reach/names проверяются с его sub — это полезное правило сохраняется. Явно задать состав требований смешанного запроса: для папки admin/platform, для члена edit/его sub, для строк B9 — sub каждой записи; служебные следствия — по уже принятому частному правилу. В Confirmation добавить положительный случай ровно с двумя строками выше и отказ пакета cam+rec без права rec.

## 2. [Существенная] Подсистема события берётся из поля, которого у обычных событий и marks нет

**Место:** `decisions/0097-…:83`, таблица §2; `:74` — null принимает все строки гранта.

> события и метки (`/events`, `/marks`) — поле `sub` записи журнала

**Источник.** `Platform/common/contracts/event-journal.md:20`: общая строка события имеет t/kind/id/of/class, а остальные поля — слова подсистемы. Обязательного `sub` у неё нет. `sub`/target действительно есть у **audit** (`:80`), но это не универсальная форма события. У отметки (`Platform/06-console/spec/06.4-console.norms.md:67`) дерево console, адресат — of, индекс subsystem=console; POST /marks принимает unit/note (`:248`), лишние поля в событие не попадают. Происхождение unit-события хранится в дереве/индексе, адресат about — отдельно в of.

**Контрпример.** У человека только `view, sub:rec, scope:unit:cam/7`. Ресурс отдаёт корректное событие det о cam/7 без поля sub. Если отсутствие sub попадает во вход may как null, rec-грант его разрешает: действие перестаёт быть ограниченным подсистемой. Если читатель определяет sub=det по происхождению, строка скрыта. Если отсутствие поля считать отказом, пропадают обычные события и отметки даже у надлежащих узких грантов. Само поле `<поля>.sub` также может быть прикладным значением и не должно произвольно задавать область доверия.

Для POST /marks решение требуется **до** записи журнала: в запросе есть unit, а не готовая строка журнала. Правило пока не называет, как выполнить body_unit с новым sub и затем прочитать такую отметку.

**Последствие.** Новая ось прав у одного из основных чтений VMS имеет неоднозначный или недостоверный вход. При null возможен доступ через грант другой подсистемы; при отказе ломается обычная видимость.

**Предложение.** Задать отдельную матрицу для unit-событий, audit и marks: достоверный источник подсистемы действия, её отличие от of/about и индексного дерева console/audit; для POST /marks — вывод из адресата unit до проверки edit. Не сводить отсутствие/нечитаемость этого признака к специальному null «все подсистемы». Проверить событие det о cam/7 без sub, отметку о cam/7 и audit-запись, а также произвольное прикладное поле sub. Выбор точной политики — «Архитектору»; текущее утверждение о едином поле неверно по связанному договору.

## 3. [Существенная] Доступ через папки меняется без предусмотренного reset ленты B2

**Место:** `decisions/0097-…:98`, §4; `:152`, перечень изменений норм; `:162`:

> перенос единицы гранты не трогает

**Источник.** ADR-0094 B2 (`decisions/0094-…:115`) требует reset при смене грантов или меток в view подписчика. ADR-0096 §5 включает в ленту строки папок; его §3 делает всех потомков удалённой папки недостижимыми сразу, до жнеца. ADR-0097 добавляет другую зависимость view — memberof и доступность цепочки папок, — но изменения B2/его reset в решении и порядке нет.

**Контрпример.** Подписчик с `view sub:cam folder:F` прочитал список и cam/7, затем подписался на /changes. Другой администратор снимает cam/7 из F: меняются строка F и memberof, но не гранты, labels или сама строка cam/7. Новый may уже отказывает, однако предусмотренного reset нет и уведомления об изменении cam/7 тоже нет. Состояние клиента, который обновляет перечень по reset, не сводится к новой области видимости. При обратном переносе новая доступная, но не изменённая единица не появляется в его списке. Удаление предка даёт то же для целого поддерева без изменений членства потомков до прохода жнеца.

Уведомление об изменении самой папки не равно предусмотренной B2 пересинхронизации всех затронутых единиц: клиент не обязан из него вычислять разность прав через about и все подпапки. Это именно причина уже существующего reset при смене меток.

**Предложение.** Расширить основание reset изменениями подтверждённого членства и достижимости предков, меняющими view подписчика, либо явно задать эквивалентную полную синхронизацию с теми же гарантиями. Перечень зависимостей должен включать about-членство. Внести B2 в порядок §8 и сценарии: добавление/снятие члена, удаление предка, права при неизменных грантах и labels, клиент со старым курсором. Не ждать жнеца ради отзыва доступа.

## Что в модели согласуется

- Поле sub — независимый от cap/scope фильтр; грант без поля сохраняет прежнее покрытие, в том числе about и labels. Null явно отдельный режим чтений, а не значение нового поля строки. Platform уже запрещено как имя манифеста P/02.1: коллизии с подсистемой нет.
- Выдача кластерных грантов остаётся дверью **процесса domain** с admin по `domain/grants/domain` (P/08.4 Н3 «гранты», шаг 1). Admin только в rec или platform у члена не получает права писать документ грантов. Поле sub в доменном документе отвергнуто; last_admin не ослаблен.
- Членство хранится отдельно от меток размещения, объединение с about явно задано. Полная цепочка до корня и запрет повторения id наследуются от ADR-0096: удалённую ветку нельзя оживить новой папкой того же id. Ошибка чтения исключает только соответствующее покрытие, не отменяет независимый прямой/звёздный грант.
- Видимость id всех членов папки обладателю любой строки — уже принятое решение владельца В6 ADR-0096; новой утечкой его не считаю. Роли, группы/LDAP, именованные действия, условия и автоматическое view cam прямо отложены §7; отсутствие этих возможностей не находка.
- Перевод Access в §6 информативен. Закрытый контракт V/11 сейчас оставляет GET /access и POST /access/apply NO_ROUTE; собственную модель прав backend не вводит. Объявление Access целиком до готовности ролей/групп было бы отдельным решением, его ADR-0097 не требует.

## Вопросы «Архитектору» — не включены в число находок

1. **Власть администратора членства между подсистемами.** Алиса имеет admin/platform/folder:F, edit/cam/unit:cam/7 и admin/rec/folder:F; cam/7 пока вне F. По §5 она вправе добавить камеру в F. После этого ей впервые доступны admin-действия rec о cam/7, хотя до переноса права rec на неё не было. То же позволяет делегировать доступ другому человеку с грантом на F. Это прямое следствие динамической области, а не ошибка вычисления may; подтвердить ли такую власть записи членства как политику продукта? Если нет — какой дополнительный допуск нужен на изменение области? В тесте зафиксировать принятое решение, не скрывать его общим утверждением «нельзя перетащить чужую единицу».
2. **Момент проверки и конкурентный отзыв.** ADR-0096 ставит стражи предков при записях папок. Теперь обычная запись единицы может разрешаться по отдельно прочитанным memberof/предкам. Должны ли их индексы стать стражами пакета этой записи, или уже проверенный запрос вправе завершиться после изменения членства/удаления предка? Нужен явный исход для порядка «may прочитал → членство изменилось → пакет единицы». Членство добавляемого U для §5 следует проверять в исходном подтверждённом состоянии, до помещения в разрешающую папку.
3. **Цена подготовки may.** При N единицах, F=`FOLDERS_PER_UNIT_MAX`, D=`FOLDERS_DEPTH_MAX` без повторного использования снимка получается порядка `2N·(1+F·(D+1))` чтений папок/членства с учётом about, до обхода строк грантов. У /events уже возможен предел ресурса 10000 (P/06.4). Формулировка §Decision Outcome «как метки — одним чтением» не отражает эту цену; сам §Consequences цепочку признаёт. Нужны общий бюджет запроса, однократная подготовка/дедупликация общих предков и поведение при его исчерпании, без устаревшего разрешающего кэша. Числа — `[TODO: уточнить в норме]`; существующие F/D ограничивают глубину, но не устраняют умножение на число объектов/проверок.
4. Доставка книг и индекс имён при sub=null уже названы открытым вопросом §3. Его не считаю новой находкой; при последующих ролях/группах нужен тот же фильтр действующих строк, без второго компилятора прав у backend. Правки `<sub>/policy` стоит явно отличить от общих настроек platform в таблице §2.
