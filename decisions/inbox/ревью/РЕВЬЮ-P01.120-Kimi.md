## Проверка 1. Соответствие словарю и формату

Закрытое множество видов держится: `KIND_ARGS` (code_checks.py:32) — ровно 7 видов словаря; вид словаря вне `KIND_ARGS` — `CodeCheckError` (отказ, не молчание), вид строки урока вне словаря — отказ, недостающий вид словаря — отказ; анализатор на неизвестный вид даёт красную строку («unknown kind»). Заголовки обеих форм и число колонок проверяются, `args` — ровно ключи вида, JSON-объект. Формат строки урока `id kind name args stage norm` парсится по нему.

Находки:

- **Б-1. Колонка `name` словаря не принимается интерпретатором.** Словарь main (строки 18, 20, 23) значит `function` (step_form, property_tests) и `package or function` (complexity); `SUBJECTS` (code_checks.py:29) — `("package", "func", "type", "package|func")`. Прогон на реальных данных main: `common/acceptance/forms/code-rules.tsv:18: name function is not one of package, func, type, package|func`. Любая попытка P/01 падает на prep. Сценарий: prep любой generation_only-задачи P/01. (Править интерпретатор под словарь или словарь под интерпретатор — решение владельца; тесты цикла держат игрушечный словарь с `func`/`package|func`, поэтому зелень тестов расхождение не ловит.)
- **Б-2. `step_form` отказывает в args, которые словарь и строки урока требуют.** Словарь: `{} or {"core": <name>}`; строки C10/C20/C22 несут `{"core": "store_core"|"copy_core"}`. `KIND_ARGS["step_form"] = ()` (code_checks.py:34) и проверка «extra/lack → CodeCheckError» (code_checks.py:137) дают на реальных строках: `args of step_form are []; unknown ['core']`. P/01 не стартует даже после починки Б-1.
- **С-1. Оговорка `core` вида step_form не реализована в анализаторе.** Словарь: «With core: the package of the function is the package that the field code maps core to, and core is the name of a pure_core row of the same lesson». `derive` не имеет ветки step_form (code_checks.py:170), анализатор `stepForm(pkg, name)` (main.go:306) не получает и не проверяет core. Сейчас недостижимо (Б-2 глушит prep раньше), но если Б-2 чинить приёмом `core` без исполнения оговорки, получится ситуация проверки 2: строка засчитывается зелёной без исполнения оговорки вида (Step из любого пакета, не только ядра). Чинить вместе.
- **М-1. `requires_module.from` не сверяется с форматом «путь go.mod».** Формат словаря: `<path of a go.mod>`; `derive` (code_checks.py:207) принимает любой файл M с строкой версии рядом с именем модуля. Слабее формата, ложного зелёного у модели не даёт.
- **М-2. `property_tests` не требует сигнатуру `TestXxx(t *testing.T)`.** Словарь требует; анализатор (main.go:433 и далее) проверяет только префикс `Test`. Проверка слабее словаря.
- **М-3. `exhaustive` не проверяет базовый тип.** Словарь: underlying — integer или string basic type; анализатор (main.go:567) только находит тип и считает константы. На практике недостижимо (константы иного типа невозможны), но формальное условие вида не исполняется.
- **М-4. Лишние ключи поля `code` не отказываются.** PROFILE.md («Code-check names»): цикл отказывает ключ, не имя строки урока; `request`/`resolve` (code_checks.py:253,229) лишние ключи молча игнорируют.
- **М-5. Не проверяется «two name types for one name».** Словарь объявляет это data error (prep_failed); интерпретатор согласованность субъектов строк с одним `name` не сверяет.

## Проверка 2. Ложный зелёный

Находок нет. Каждая due-строка даёт вердикт: `result` (code_checks.py:307) — строка без отображения красная с причиной («no mapping»), `ans is None` → все проанализированные строки красные «not checked (the loop's code checker gave no answer)» плюс дефект цикла `code_checker_no_answer` в паспорт (loop.py:2481,2516; дефект раунда — judge-defect по доп. (41), не модели), отсутствие id в ответе → красная «no answer for this row», красная строка анализатора несёт `why`. Сбой сборки анализатора → `CODECHECK_BUILD_FAILED` → тот же путь дефекта. Неисполненное не бывает зелёным: `code_view` (loop.py:2527) считает `ok = green == total` по due-строкам; закрытие этапа — только при `ok` всех проверок (loop.py:3944). Отказ данных в prep: `code:*` без строк урока, строка после последнего `code:*`, вид вне словаря, args не вида, этап вне stages.tsv. Прогоны на копии: пустая code-карта и `ans=None` красят все 24 строки красным. Тесты: `test_no_answer_is_a_defect_not_the_models`, `test_no_mapping_in_profile`, ломающие варианты «красна ровно своя строка» по каждому виду. Замечание (не находка): исключения из `model_code` в `code_gate` не ловятся — как у соседнего `mech_gate`, поведение цикла в целом, к интерпретатору не относится.

## Проверка 3. Покрытие строки воротами этапа

Находок нет. `stage` строки валидируется против forms/stages.tsv (`load`), строке даётся `from_n`; ворота только грамматики формы: `code:*` в ячейке этапа (loop.py:1497), проверка добавляется только этапу, держащему `code:*` (loop.py:2353); prep отказывает строку, у которой ни её этап, ни later не держат `code:*` (`gate_violations`, code_checks.py:265). Прогон на реальных данных main: `code:*` на этапах 1,2,3,4,5,6,9,10,11; `gate_violations` = []; due-покрытие 4,5,8,12,15,18,21,23,24 — каждая из 24 строк due хотя бы одним воротом, на последнем этапе (group, 11) due все 24. Этапы 7 (rights) и 8 (daemon_doors) `code:*` не держат и закрываются без проверки строк, due к тому моменту, — это семантика самой грамматики (C2 ревью P01.103: ворота — только ячейка формы; строки остаются due следующего `code:*` и ловятся там). Одно исполнение анализа на раунд, вид на каждый этап (кэш раунда — loop.py:3929). Строка между этапами не теряется.
