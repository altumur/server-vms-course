## Ответы на вопросы задания

### 1. Сохраняет ли запись `word` P/02 в обратных кавычках смысл токенов и работу судьи?

Да, сходятся и факт, и числа. У P/02 ровно 9 непустых `word`-ячеек (подсчёт по форме):
`busy`, `refused`, `refused:catalogue`, дважды `refused:form`, `refused:relations`, `refused:text`,
`unknown-row-form`, `unreadable`. Это в точности «потеря 9 `Word`» из факта разбора доп. (6) — простой
перевод P/02 на общий вариант без правки ячеек обнулил бы все девять проекций (правило строк 328–334:
ячейка без обратных кавычек — «prose cell», `word` становится `-`). Все 9 ячеек однотокенные, без запятых
и пробелов: запись «`tok`» по правилу строк 329–332 даёт тот же `word_cell` (один токен, без `word_any`),
что и сейчас для P/02 (сохранение ячейки), а `Named`/`WordCell` при включённом `word_any` — те же строки
каталога. Смысл токенов (фиксированные слова отказов/диагностики по README P/02, строка «`word` is a fixed
refusal/diagnostic token») не меняется; Word-ожидания судьи остаются достижимыми. Условие исполнения:
запись строго однотокенная «`t`»; многословные ячейки через запятую дали бы список `word_any` — у P/02
таких нет. Правка судьи и `test_gen_refusals_plain.py` в той же доле (п. 3) — контроль «Архитектора».

### 2. Верно ли включать сверку ролей для всех таблиц с `response_schema`?

Да. Это устраняет молчаливое послабление, найденное при ревью доп. (6): `gen_refusals` строка 252 даёт
P/05 только проверку имён схем, а сверку required/optional-ролей со схемой (строки 291–301) включает
только для `06-console`. Таблицы с колонкой `response_schema` — P/05, P/06, P/09, P/10 (заголовки
`refusals.tsv` подтверждены); набор колонок у них одинаков, по доп. (6) п. 2 это один вариант — со
сверкой для всех. Развилка расхождений названа честно: `relay_01_413` (P/09, `fields=error,detail`,
`response_schema=RelayRefusal`) и `c10_007_502` (P/10, `fields=error`, `response_schema=ForwardingRefusal`)
исправляются в формах, при несогласии формы — вопрос «Архитектору», а не ослабление сверки. Запись `?`
как определение необязательного поля подтверждена кодом (строки 281–290; пример в P/06 — `supervision?`).

### 3. Достаточен ли признак формы по п. 2?

Для `gen_refusals` — да. Действующий код уже выбирает вариант по набору колонок (строка 247:
`self.response = head == RESPONSE_COLUMNS`): варианта два (PLAIN / RESPONSE), различитель — набор колонок,
что и есть ядро признака п. 2. Дополнения п. 2 (наличие файла формы, вид объекта схемы, записи значений
в ячейке) покрывают другие генераторы и будущие варианты. Важное разграничение: записи `?` и
backticks-`word` — правила внутри варианта (п. 4 и п. 3 доп. (7)), а не различители вариантов refusals,
поэтому требование «объявлена в `forms/README`» к ним как к признаку сейчас не применяется — на момент
среза ни одна `forms/README` слова «backtick» не содержит (grep по всем `Platform/*/forms/README.md` пуст),
описание `?` в README P/06 читается косвенно (строка 52 про required/optional через схему). Это условие
на будущее: если запись станет различителем варианта, п. 2 требует её README-объявления; для пп. 2–4
не ошибка. Случаи вне покрытия признака (историческая ветка P/01/P/02+ в `gen_families`/`gen_door`)
по доп. (6) п. 4 идут вопросом «Архитектору», п. 2 их покрывать не обещал.
