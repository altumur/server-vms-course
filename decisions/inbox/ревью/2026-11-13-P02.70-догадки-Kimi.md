## 2. План реализации урока P/02 по этапам `forms/stages.tsv` (без кода)

Сквозные решения плана (общие модули — по `common/modules.md`; договоры P/01 — только как договоры):

- Языковая основа: Go 1.22 (`common/versions/go.mod`), потому что код-чеки урока (`forms/code-rules.tsv` C02–C04, C23–C26) требуют Go-модулей с пинами `go.yaml.in/yaml/v3 v3.0.5`, `santhosh-tekuri/jsonschema/v6 v6.0.2`, `cel-go v0.26.1` и общих модулей `servervms.local/common/{json,store-client,log-mask}` (пины уже стоят в go.mod). Парсинг/кодирование JSON только через общий `json` (C26 запрещает `encoding/json` в main module).
- Архитектура: чистое ядро (loader, projection/canonical, rights derivation, install-order, rollout poll) в пакетах без импортов `os/net/time/sync/io/fs/syscall/os/exec` (C05, C08, C11, C18, C22 `pure_core`) + shell (команды `w2cctl`/`w2c-run.sh`/`w2c-workers.sh`/`w2c-ca.sh`, store-клиент, systemd-артефакты). Стандартные файлы форм исполняются как данные (LAYERS.md §1): схема 2.1, relations CEL, layers.tsv, scalars.tsv — встраиваются байт-в-байт (`table_driven` C13–C17).
- Договоры P/01 как договоры: store door `/v1/get|list|write` через `admin.sock`/роль по `store-client`; потолок/тело — фактические `max_value`/`max_body` из `GET /v1/status` (status-fields.tsv); права — файл P/01.2 N1.2, evaluator и `never` — P/01.2 N1.3. Внутренний код P/01 не входит в модель.

Этап 1 `manifest-load` (gate `verdicts:2.1:*; vectors:common/yaml-suite; vectors:exec; seams:2.1:s1–s4; code:*`):
1) Слой 1 текста: байтовый препаспорт (UTF-8/BOM/C0/CR, один документ, корень — блок-маппинг) + парсер yaml/v3 пиновой версии + тонкая проверка N1.1 (правила `bytes…parser` из норм 02.1:101–161), обходы дефектов D13/D16 (LAYERS.md §4). Скаляры классифицируются своей таблицей `scalars.tsv` по стилю ноды, не по типам библиотеки.
2) Слой 2 формы: исполнение `02.1-installer.schema.json` (JSON Schema 2020-12) + слов `x-integer-place`, `x-opaque`, `x-complement-of` (layers.tsv) с местами отказа по LAYERS.md §6 и полным совпадением выражений (§3).
3) Слой 7 relations: CEL по `02.1-installer.relations.json` (функции `depth/template/text`, расширения `strings`, `two-var-comprehensions`; ошибка исполнения — отказ, не «строчка сошла»).
4) Шаг 4 N3: статические дефолты (без ослабляющих для `lease.unconfirmed_max`, `unplaced.delete_after`, `places.server_field`). Порядок text → form → relations нормативен.
5) `load_catalogue`: межманифестные проверки N3 (requests, near-отложка, creates 1–5, uses, виды токенов, OS-имена ≤32, A=B пересечения, calls) на дереве уже загруженных манифестов, без store.

Этап 2 `canonical`: проекция N1.1 гл. 2.2 (sugar ×3 → дефолты → P1–P5 → ordered → скаляры по типу → JCS без финального LF). Ядро `canonical` pure (C05, C07). Внешняя проверка — векторы `canonical` байт-в-байт; мутационная проба `check_spec` (удаление default/x-ordered/шага меняет вектор).

Этап 3 `manifest-put`: команда `w2cctl manifest put` — процедура 2.3 N3 целиком: load → shell `on…=` → файлы/потолки `FILE_MAX`/`FILES_TOTAL_MAX` → полный подтверждённый каталог → `/v1/status` → внутренний конечный профиль удаления (6a, `finite-profile.schema.json`) → части файлов (FILE_PART, до строки) → чтение строки/вида/метки → «unchanged» (строка равна по значению И вид равен проекции) → шаг 14a (вес вида с финальным rev) → запись частей → строка (cas) → вид (cas) → метка (только вверх) → удаление чужих частей. Store-доступ — общий `store-client`, лог — `log-mask`. Шов `s1-put-invalid-source`, gate `puts:2.3:*`.

Этап 4 `canonical-put`: поведение вида при put (`puts:2.2:*`, в т.ч. граница потолка и `ceiling_rev_10`), «окно формы» (`canonical/<form+1>`) — по чтению.

Этап 5 `rights`: генератор `w2cctl rights -deployment <name>` — таблица N1.4/N1.4a, общие правила (read включает write, negation-вычитание, idem/asked только console, secrets — читатели, отказы генерации до файла), байт-стабильный вывод с сортировкой, `--check` по смыслу; роли/группы по P/01.2 N1.1. Gate `accept:2.5:*` (8 сценариев/70 шагов от имени ролей через store door).

Этап 6 `install-order`: чистое ядро топологического порядка (requests и виды токенов задают порядок; near/creates/uses — нет; цикл — отказ до изменений, код 2; нативный вывод `{"result":"ok","order":[…]}`/`{"result":"refused"}`; ввод вне формы — exit 2, пустой stdout). Векторы `install-order` (9 строк).

Этап 7 `runner-workers`: юниты N1.1 (рендер всех unit/socket-файлов, пользователи/группы, каталоги/права, tmpfiles.d), раннер `w2c-run.sh` (порядок env-файлов по env-file contract, `W2C_ROLE`, чтение строки+метки+вида, `W2C_MANIFEST_REV`, запуск `worker.exec` без shell со слотом последним аргументом), структурные тесты юнитов, скрипт `w2c-workers.sh` (правила 1–6 как чистая функция от входа JSON — векторы `workers-script`), сертификаты `w2c-ca.sh` (центр, листья 825 суток, CRL/revoked, kits, адресное правило N1.6). Gates: vectors + seams `s14` + `build`.

Этап 8 `operator-files`: команды N1.9 (`manifest get` с quarantine `.old` и хэшем оператора; `secrets new|seal|rotate|status` с Walk-выборкой и кодами 0/1; `mirror|space|retention`; `tls status`; разбор опций по `daemon-flags.tsv` — `command_options` до любого эффекта), семейства retention/mirror/space/alarms_retention по схемам, отложенный слой — установка домена по `domain-founding`. Gates: seams s2–s4, s12–s13, s15–s20; build.

Этап 9 `rollout-poll`: чистая машина опроса по `rollout-poll.machine.yaml` (Step/Event-форма, C18–C21), константы из формы (BATCH 1, READ 1, ROLLOUT_WAIT 300), обвязка команды `w2cctl rollout` (mode/done/pre/leader/steps/barrier). Швы s5–s11.

Сквозное после этапов: описание реализации (24 пункта «Implementation decides» 2.1–2.5), закрытие readiness-checklists (test/reading/stand), системные пункты — по чтению и стендам (system/tls/pass), `build` — только сборка.

Опасные догадки (выбор меняет вердикты/байты приёмки, а канон даёт слабую опору):

1. **G-09** — бюджет повторов cas/re-read не нормирован: риск либо бесконечного цикла при конфликтах, либо преждевременного отказа; пример rev 9→10 требует пересчёта веса при КАЖДОМ повторе. Нужна строка бюджета в описании реализации.
2. **G-10** — «полный подтверждённый каталог»: подтверждение чтения (list+get) при частичной недоступности store определяет отказ до записи; производительность при большом каталоге не нормирована — риск таймаутов стенда (команды стенда — 120 с).
3. **G-07 + G-06** — собственная классификация скаляров и точное место workaround-ов: ошибка даст системные расхождения вердиктов по всему корпусу 951 файла (set B, profile_*, c5–c9) — самый массовый источник красного.
4. **G-17** — сортировка паттернов прав: ошибка порядка ломает байт-стабильность генерации (две генерации сравниваются), при смысловом `--check` останется незамеченной до отдельной проверки.
5. **G-11** — вес view row с финальным rev: граничные строки `puts-ceiling.tsv` (`ceiling_rev_10`) чувствительны к одному байту; формула не вынесена в норму отдельным числом — вывод через P/01.1 N1 обязателен.
6. **G-16** — семантика одновременных событий машины опроса (порядок «read_expired; tick; wait_expired; внешние»): ошибка в диспетчеризации меняет исходы швов s5–s11; формальная опора — только env-раздел машины.

Не догадки, а прямые разрывы, требующие вопроса автору норм при генерации (по правилу «On a gap or a contradiction in the norms»): нет — противоречий в прочитанном не найдено; разрывы G-18/G-19 — следствие условия пробы (читать только M), а не дефекта норм.
