## Нормальная ветвь — статический положительный разбор

1. Новый валидный лист T без holds/question/cancelled, роль S и отдельный acceptor, неизменные goal/role/accept=H1: модель READY, issuable передаёт T/attempt1/H1. Collision-фильтр отсекает конфликтующие TSV, глобальная резервация и durable inbox предшествуют sender.
2. Только input_accepted даёт состояние «начало не подтверждено». Настоящий start записывает mark; последующее чтение даёт WORKING. Наблюдённый STOP после хода даёт «ход закончен, не сдано», не REVIEW/DONE.
3. Done с C1/R1 пишет hand-in текущей попытки; модель REVIEW. Pending notice адресуется отдельному acceptor. Его accept C1/R1 без открытого вопроса записывает H1; совпадение определения даёт DONE, затем after может отпустить следующий шаг.
4. Закрытые дети ставят родителя на его отдельный приём. Все отменённые дети дают CANCELLED. Отказанный родитель ждёт новой подзадачи. Reject листа увеличивает work-attempt; редоставка не делает этого.

Это чтение ветвей, не выполненный контроль. NORMAL-FLOW.md записан отдельно до оформления отрицательных случаев. Ниже приведены границы, которые эта нормальная ветвь не доказывает.

## Оставшиеся и новые дефекты

Б — нарушает допустимый порядок работы/привязку результата. С — теряет доставку, контроль либо обязательную информацию ожидания. Все расписания ниже **NOT_EXECUTED**; это пути через замороженный исходник и разрешённые определения/команды, без инъекции production-объектов или частных тестовых оракулов.

### Б-1. Версия реально взятой задачи замораживается не на всех путях

**Код:** `tasks.py:621–622, 1037–1064, 1251–1261; queues.py:540–553`. **Основание:** ADR §2 «Определение под идущей работой», Add4.3.

**Статический вход/порядок:** Роль S создаёт себе T.1 в пределах своей задачи; приёмщик наследуется от родителя. issuable намеренно не отправляет такую подзадачу. S законно делает start T.1 и работает по G1. После допустимой правки goal на G2 новый done C/R и независимый accept находят отсутствие queue-записи, берут current H2 и делают DONE для G2 по результату G1.

**Следствие:** Новая отметка start содержит лишь id/from/utc, hand-in не содержит H; _issued_definition ищет только queue ledger и падает обратно к current. Это новый приём с H2, а не разрешённое старое принятие без hash. Соседний случай очереди: role S1 меняется на S2 во время попытки; start/done проверяют S2 из текущего файла, поэтому законный S1 уже не может подтвердить/сдать старую попытку, хотя правка должна действовать со следующей.

**Минимальная правка:** Замораживать выбранные goal/role/accept для каждой реально взятой попытки, включая self-assigned/manual start; start, done и accept должны смотреть один сохранённый вариант. Не расширять набор хэшируемых полей.

### Б-2. Явный старый attempt в done заменяется текущим

**Код:** `tasks.py:1218–1247; queues.py:887–893`. **Основание:** Прямой протокол start/done; ADR §2 попытки/версия; Add2.7.

**Статический вход/порядок:** Попытка T.r2 выдана и начата S; C2/R2 сдан и отклонён, счётчик rejected теперь 2. Перед третьей попыткой goal законно изменён с G2 на G3, и T.r3 выдана по G3. После этого приходит поздний done от той же роли с явным T.r2 и отличающимся улучшенным C2b/R2b, всё ещё по G2. line_task возвращает attempt=2, но hand_in его игнорирует и записывает attempts=2 — то есть сдачу рабочей попытки 3.

**Следствие:** effective_handed считает эту сдачу текущей; задача сразу REVIEW и может быть принята по H3 из новой выдачи, хотя C2b относится к G2. Если T.r3 ещё не выдана, эта сдача сама подавляет её выдачу. Guard одинакового ранее отклонённого commit не помогает: C2b отличается от C2. Это не подмена --from и не повторная транспортная доставка того же work-attempt. В штатной инструкции done также печатается базовый task id, поэтому привязки к выданной попытке нет.

**Минимальная правка:** Проверять явную попытку и связывать сдачу с подтверждённым start/определением именно этой попытки. Устаревший ACK не превращать в текущий.

### Б-3. Start/done допускаются из состояния с невыполненными условиями

**Код:** `queues.py:540–562; tasks.py:535–561, 1209–1248`. **Основание:** ADR §2 старт после DONE зависимости; Add4.2; прямое правило обязательного start.

**Статический вход/порядок:** Новый T имеет after:[D], D отменена, собственной question у T нет. Модель правильно даёт DECISION. Законная роль S вызывает start T: проверяется только «не CLOSED», поэтому пишется mark. Без queue-entry последующее чтение отдаёт WORKING по mark раньше проверки cancelled. done того же T тоже допускается из DECISION; handed поднимает REVIEW раньше dependency gate.

**Следствие:** Сданный результат затем может принять настоящий acceptor: accept не проверяет эти зависимости. Аналогично новый done без единого start сразу создаёт REVIEW. Это обход переходов через новые штатные команды, а не новая трактовка старой принятой отмены. Сохранённый question всё ещё блокирует accept и этой находкой не считается снятым.

**Минимальная правка:** Применить существующие ограничения готовности/решения/отмены при подтверждении взятия и сдачи; для нового протокольного листа требовать соответствующий start. Сериализовать проверку и запись, сохранив выбранные исключения для старого состояния.

### С-1. Поздний start не отменяет уже спланированную редоставку

**Код:** `queues.py:922–927, 728–733; automation.py:405–419; tasks.py:1251–1261`. **Основание:** Прямой протокол: повтор только без start; Add2.7.

**Статический вход/порядок:** t0: plan читает marks без T и ставит queue_resend после 15 мин остановки. t1: S успешно пишет start T, получает подтверждение и начинает работу. t2: run проверяет реестр, паузу, окно и отсутствие T в composer, но не перечитывает marks; reserve(queue_resend) и sender всё равно отправляют текст T.

**Следствие:** started/.lock не согласован с резервацией повторной доставки; свежий check_window не проверяет busy и не заменяет task ACK. Из-за старой строки data.rows повтор может попасть уже работающей сессии. Доказана лишняя отправка после start, не утверждается фактическое повторное исполнение модели. Это не принятое окно гонки паузы.

**Минимальная правка:** Согласовать публикацию start с условной резервацией редоставки по одной попытке; новый ACK должен отменять ещё не отправленный повтор.

### С-2. Повтор done с другой квитанцией ошибочно считается точным повтором

**Код:** `tasks.py:1238–1242; cammeta-task:72–74`. **Основание:** Прямой протокол done с exact commit/receipt.

**Статический вход/порядок:** S сдала T с C и R1. Затем для того же C передаёт другую корректную строку R2, например исправленный путь квитанции. Ветка previous.commit==commit и attempts==current возвращает False без сравнения receipt. CLI печатает already handed in с exit0.

**Следствие:** В durable записи и автоматически отправляемой приёмщику команде остаётся R1. Запрошенная пара C/R2 не записана и не отвергнута как конфликт. Это отличается от поздней попытки: обе команды относятся к одной текущей попытке.

**Минимальная правка:** Идемпотентным считать точный повтор зафиксированной пары и её попытки; другую квитанцию явно отклонить как конфликт либо явно записать разрешённое изменение.

### С-3. Отсутствие STOP снимает held-watch как доказанный старт

**Код:** `queues.py:243–250, 265–267; collector.py:156–175`. **Основание:** Add2.1: наблюдаемая работа или изменившаяся строка STOP.

**Статический вход/порядок:** Held отправлено с input_accepted, line_at_send содержит исходную STOP-строку. Следующий свежий нескролленный снимок имеет state=СТОИТ и пустую status_line: парсер не нашёл STOP, занятость тоже не подтверждена. update_held_watch видит отличие пустой строки и удаляет запись.

**Следствие:** Ни работа, ни новая STOP-строка не наблюдались. Через 15 мин held_not_started уже не возникнет; сообщение остаётся без контроля. Прямая доставка caller-sees-result, принятая разбором, здесь не предъявляется.

**Минимальная правка:** Удалять watch только по названному доказательству старта/завершившегося хода; потеря или неизвестность STOP не является положительным доказательством.

### С-4. Crash между sent и held-watch теряет наблюдение навсегда

**Код:** `queues.py:710–714, 779–788; inbox.py:51–59; automation.py:435–458`. **Основание:** Add2.1–2, сохранность состояния после crash.

**Статический вход/порядок:** Резервируется held, сообщение отправлено и принято только во ввод. settle сначала fsync-ит inbox status=sent. Процесс падает сразу после этого, до создания/сохранения held_watch. После рестарта held_jobs больше не выбирает sent; watch отсутствует.

**Следствие:** Контроль старта и его сигнал потеряны навсегда. Окно есть и после фактической отправки до всего settle, когда inbox ещё sending: оно тоже не выбирается. Повтор текста не предлагается как лечение неизвестного исхода.

**Минимальная правка:** Записывать durable намерение контроля до отправки/терминального статуса и восстанавливать незавершённый контроль при старте; не превращать неизвестный исход в успешный старт.

### С-5. Резервация уведомления приёмщику навсегда тратит его ключ без отправки

**Код:** `queues.py:726–727, 958–960, 799–802; automation.py:435–442`. **Основание:** Прямое требование уведомления acceptor; Add2.2.

**Статический вход/порядок:** Текущая сдача T/C/R создаёт handin job. reserve сохраняет handin_notices[T:C]=reserved. Затем inbox.opened отказывает, и новый правильный no-send guard делает continue. До sender код не дошёл. На следующем такте pending_notices существует, но key in sent навсегда исключает job.

**Следствие:** То же подавление остаётся после crash между резервированием и отправкой или после failed. Адресное уведомление приёмщику больше не выставляется; отдельного разбора этих записей нет. Общая получасовая сводка Архитектору не является доставкой именно этому acceptor.

**Минимальная правка:** Хранить не завершённое уведомление, а его этап/исход: подтверждённо неотправленное оставлять для доставки, неопределённое удерживать с одним адресным сигналом ответственному. Не слать неизвестно доставленный текст вслепую.

### С-6. Путь квитанции попадает в рекомендуемую shell-команду без цитирования

**Код:** `tasks.py:423–425, 1215; queues.py:959–960`. **Основание:** Прямой протокол exact commit/receipt; передача роли через inbox.

**Статический вход/порядок:** Обычный допустимый путь квитанции R=/tmp/it's-ready.json проходит _one_line. pending_notices формирует --receipt '/tmp/it's-ready.json'. В полученной рекомендуемой команде незакрытая shell-кавычка.

**Следствие:** Приёмщик не может исполнить напечатанную команду с исходным аргументом. Управляющие shell-символы разрешённого имени также выходят из цитирования. Не утверждается RCE: агент/шелл не запускались, злоумышленник с иной учётной записью не предполагается.

**Минимальная правка:** Формировать аргументы независимо от строкового шаблона: корректное shell-цитирование каждого значения или однозначная структурированная команда. Сам send уже передаёт текст списком argv и этой ошибки не имеет.

### С-7. Медленные отказы первых окон навсегда занимают бюджет перед здоровым inbox

**Код:** `automation.py:358–404; queues.py:958–984; watchcfg.py:42`. **Основание:** Add2.2–3, закрытие Codex С-5.

**Статический вход/порядок:** Допустимый набор: 14 текущих handin notices разным зарегистрированным acceptor перед здоровым held. Все первые окна отвечают отказом чтения по настроенному READ_TIMEOUT=3 с; их роли не paused. На каждом такте первые 14 проверок исчерпывают JOB_BUDGET_SECONDS=40, не резервируя ни одного notice.

**Следствие:** Их ключи остаются pending, порядок не меняется; здоровый held в хвосте никогда не достигается. Это разрешённое статическое расписание тайм-аутов, не замер существующих окон и не претензия к скорости. Буквальный прежний случай восьми paused alerts исправлен; общая бесконечная задержка из-за плохого префикса осталась.

**Минимальная правка:** Сохранить лимиты, но обеспечить продвижение между тактами: справедливый курсор/разделение бюджета или удержание повторяющихся отказов, чтобы один плохой префикс не занимал каждый такт.

### С-8. Ожидающий приёма вложенный родитель исчезает из причины ожидания

**Код:** `tasks.py:740–783, 632–643`. **Основание:** Add4.1 (отдельный приём родителя), Add2.5 (ожидание из состояния).

**Статический вход/порядок:** Три законно созданных уровня: T -> T.1 -> T.1.1. Последний лист принят. T.1 теперь REVIEW у своего acceptor S, T ещё ждёт этот обязательный приём. plan_hold(T) вызывает _open_leaves: у T.1 есть дети, поэтому рекурсивно проходит в уже DONE лист и возвращает пустой набор.

**Следствие:** В колонке «Что держит» T получается «—», приёмщик и шаг T.1 исчезают. Сам accept(T) правильно отказывает при открытом T.1; это потеря обязательного шага в проекции ожидания, не ложный DONE. Model._lesson_leaves/_expand уже учитывают ожидающего приёма родителя, но _open_leaves этого не делает.

**Минимальная правка:** Считать ожидающего собственного приёма вложенного родителя открытым шагом при вычислении holds, до его отдельного приёма.

### С-9. Старый done может затереть уже подтверждённую сдачу новой попытки

**Код:** `tasks.py:1218–1247, 984–992, 1022–1048`. **Основание:** Протокол done; ADR §2 сохранность попыток/состояния и независимый accept.

**Статический порядок:** t0: в попытке 2 роль S начинает законный done T.r2 с улучшенным C2b/R2b; файл и счётчик attempts=1 прочитаны, до handed/.lock процесс задержан. t1: отдельный настоящий acceptor отклоняет ранее сданный C2, attempts становится 2. t2: попытка 3 нормально выдана/начата/сдана как C3/R3, handed/T.json содержит attempts=2. t3: старый done продолжает работу, берёт handed/.lock, видит другой commit C3 и записывает C2b с ранее прочитанным attempts=1 поверх текущего файла.

**Следствие:** Текущая подтверждённая сдача C3 уходит в history, а effective_handed теперь возвращает None, поскольку верхний attempts=1 не совпадает с текущим 2. Старый CLI возвращает handed in с успехом, но актуальный результат откатывается в несданное состояние. Даже предварительная правильная проверка явного attempt из Б-2 не закрывает это окно: в t0 он был текущим. Никакой подмены роли или правки state-файла вручную не требуется.

**Минимальная правка:** Сериализовать чтение определения/счётчика, проверку разрешённого attempt и запись hand-in с изменением attempt при reject; перед заменой не допускать отката версии сдачи. Согласовать порядок блокировок с accept.

### С-10. Ошибка чтения подтверждённого start считается отсутствием start

**Код:** `tasks.py:220–234; queues.py:199–216, 922–927`. **Основание:** ADR §2: непрочитанное состояние не считается пустым; прямой протокол — повтор только без start.

**Статический вход/порядок:** S успешно выполнила start T; started/T.json уже durable, и работа этой попытки взята. На следующем такте чтение именно этого файла даёт обычный OSError, например EIO. read_marks молча continue и возвращает словарь без T. Сессия имеет свежую STOP-строку достаточно давно; работа может продолжаться фоном внутри той же роли.

**Следствие:** with_mark не видит started_mark, unstarted считает T невзятой, redelivery_jobs разрешает ещё одну отправку. Непрочитанное подтверждение трактуется как доказанное отсутствие подтверждения; ошибка чтения даже не добавляется в errors. Позднее возможен ложный not_taken. Это не ручная подмена JSON/--from и не принятая гонка паузы, а явный путь обработчика проверочной ошибки.

**Минимальная правка:** Различать отсутствие start и невозможность проверить его. При ошибке чтения соответствующее подтверждение/состав держать в UNKNOWN с диагностикой; не разрешать редоставку на основании этой ошибки.
