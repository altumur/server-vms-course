# Ревью ADR-0100 — Codex

Срез `8aa4a15b34c0fece8bd137ca2276642b790e2c35`, ADR-0100 `proposed`. **Один блокер, три существенные находки, мелких нет.** Выбор встроенной роли admin и отдельного права на пользователей не оспариваю. Нужны уточнения проверки отрицательного права, сериализации, начального состояния и прохода сроков.

Класс — платформенная система: права и состояние домена, без исключения для пути захвата. Метод — `skills/platform-review/SKILL.md`, форма — `skills/lesson-spec/references/review-checklist.md`; правила `architecture`, `consensus-and-leadership`, `resilience`, безопасные умолчания ADR-0012. Прочитаны ADR-0097/0098/0099 с разборами, договор may, относящиеся к вопросу нормы P/08/P/10 и контракт consolem. Нормы и код не изменялись, коммит без push.

## 1. Блокер — неизвестное назначение admin нельзя считать отсутствующим для admin only

**Место:** ADR-0100 §1 строки 63–65, §3 строки 87–99; ADR-0098 §4 строки 148–149.

> «менять … человека с действующим назначением admin» — только admin;
> «нечитаемая роль в таблицу не идёт, нечитаемая группа ролей своим людям не даёт (сужение)».

Пропуск неизвестного безопасно сужал положительное разрешение роли. Теперь то же назначение используется как **запрет управляющему менять другого человека**. Пропуск снимает защиту. ADR-0100 не задаёт исход «не удалось доказать, что цель обычная» и не меняет прежнее правило пропуска.

**Контрпример.** У `a` — admin через группу G; `b` — отдельный читаемый прямой бессрочный администратор, чтобы last_admin не мешал; `m` — управляющий пользователями через исправную обычную роль. Строка G или admin становится нечитаемой. Право `m` по его роли остаётся. В отфильтрованной таблице действующего admin у `a` нет: буквальная проверка §3 разрешает `m` сменить пароль `a`. Затем `b` восстанавливает читаемое назначение/состав с прежним `a`. Полные права получает учётная запись с паролем, известным `m`. Смена пароля не входит в перечисленные §2 изменения last_admin, а `b` всё время существует.

Модель даёт два неразличимых для проверяющего состояния: в неизвестной группе `a` состоит либо нет. Разрешить смену в обоих нельзя: в первом это запрещённая власть над администратором. Это дефект определения будущего алгоритма, не утверждение о ещё не написанном коде.

**Источник:** предел §3 «управляющий … не делает себя администратором», ADR-0012; общее «нечитаемое не расширяет» ADR-0099 §2. Нужна отдельная проверка цели по исходным данным, а не по отфильтрованной положительной таблице.

**Предложение.** Три исхода: доказан admin — 403 admin only; доказан обычный — разрешить в пределах роли; статус нельзя установить — 503 unavailable без записи. Назвать источники отрицательного доказательства: admin.assigned, нужные группы, прямые строки домена, их читаемость. При записи сторожить версии этого решения, включая подтверждённое отсутствие. Контроли: испорченная роль, испорченная группа, исправная посторонняя группа, смена пароля/выключение/удаление, затем восстановление читаемости.

## 2. Существенная — last_admin не защищён общим условием двух независимых правок

**Место:** ADR-0100 §2 строки 76–80; механизм ADR-0098 §5 строки 214–217 и §6 строки 254–260.

> «после каждой правки … Нет ни одного — 409 last admin, ничего не записано»;
> «одна запись B9 по CAS всех затронутых строк».

Проверка итогового состояния **одного** пакета не обеспечивает глобальный инвариант при независимых строках. Имеющиеся стражи ссылок защищают строки, на которые ссылается записываемое members/assigned; отдельного условия на прочитанные источники последнего администратора нет. Единственный активный процесс domain и signer-turn ограждают другого писателя, но не два параллельных запроса того же процесса с одной версией очереди.

**Контрпример.** Роль admin бессрочно назначена G1 и G2; G1.members=[a], G2.members=[b]. Оба человека бессрочные, включены. Запрос 1 готовит `G1.members=[]`, видит оставшегося b; запрос 2 готовит `G2.members=[]`, видит a. Каждый проходит last_admin своего итогового снимка. CAS разных строк проходят, новые списки пусты — стражей ссылок на участников нет, signer-turn прежний. После двух успешных записей администраторов ноль. Удаление групп имеет тот же риск. Даже полностью атомарный B9 каждого запроса его не устраняет.

Конечная модель перебрала все шесть порядков «прочитать/подготовить → записать» двух запросов: **четыре нарушения из шести**. При стражах обеих прочитанных строк нарушений нет. Последовательный положительный контроль отклоняет последнее снятие.

**Источник:** инвариант владельца и §2; линеаризуемое изменение состояния платформы, `architecture.mdc`, `consensus-and-leadership.mdc`; чеклист «CAS одной единицы не объявлен общим допуском».

**Предложение.** Явно зафиксировать общую точку сериализации для всех путей §2: общую версию политики с CAS либо полный набор стражей прочитанного доказательства в B9, с повтором всех проверок после конфликта. Если выбран локальный сериализатор единственного активного domain, назвать его область — двери, проход, восстановление — и ограждение сменой писателя. Та же защита нужна проверке admin only при одновременном назначении admin цели чужой правки. Добавить конкурентный контроль двух разных групп, не только двух запросов к admin.assigned.

## 3. Существенная — новый шаг 4а недостижим при отсутствующем документе грантов

**Место:** ADR-0100 §1 строки 59–68; договор may, шаги 3–4.

> «действующее назначение admin … разрешено всё»;
> «Новый шаг 4а после шага 4 (stale)»;
> прежний шаг 3: `grants = null → deny no_grant`.

**Контрпример.** Читаемый включённый бессрочный человек, действующее назначение admin, `roles` доступны у держателя, `as_of=null`, но `domain/grants/domain` отсутствует. Такое отсутствие — допустимый вход may; новая установка прямую строку домена больше не пишет. До 4а вычисление не доходит: отказ no_grant на все двери управления. У члена отсутствующий документ дополнительно не даёт пары grants/roles по механизму ADR-0098 §4. Одного обещания нести admin всем кластерам недостаточно.

Это не утверждение, что любая реализация first-admin обязательно так сделает: она могла бы создать пустой doc. Но ни §1, ни bootstrap не устанавливают такого предусловия, тогда как порядок may определён явно. Подтверждённый admin и grants=null имеют противоречивые ответы двух пунктов ADR.

**Источник:** обещание allow §1 и полная область входа договора may. Конечная модель буквального порядка 1–4а воспроизводит no_grant; с пустым `{lines:[]}` — allow.

**Предложение.** Определить эту ветвь: либо отделить доказанное назначение admin от наличия грантов с сохранением disabled, свежести и неизвестности таблицы, либо обязать first-admin/сверку и доставку создавать связанный пустой документ там, где достаточно назначения admin. Назвать восстановимый порядок bootstrap; нечитаемый документ не приравнивать к отсутствующему. Векторы: отсутствие, пустой doc, нечитаемость, свежая/старая таблица admin, first-admin без единой обычной строки грантов.

## 4. Существенная — прежний expiry_kept перестаёт выключать обычных людей новой установки

**Место:** перечень замен в начале ADR-0100 и §2; сохранённый ADR-0098 §3 строки 123–127.

> «Проход не пишет имя в domain/disabled по сроку, если после этого не останется ни одного человека со строкой {cap: admin, scope: *, until: 0} в domain/grants/domain».

ADR-0100 заменяет §5 last_admin, но не эту отдельную проверку прохода §3. В новой установке прямых строк домена нет по §1, даже когда есть исправный бессрочный встроенный администратор. Следовательно старое условие «не останется ни одного со строкой» истинно при истечении **любого обычного человека**. Проход оставляет его включённым и пишет expiry_kept. Вход и may не читают expires непосредственно (ADR-0098 §3 строки 119–122), поэтому ограничение срока не действует.

**Источник:** значение expires в ADR-0098 §3 и требование сохранить бессрочного администратора в ADR-0100 §2. Изменить только подсчёт двери недостаточно: это самостоятельный переход прохода, включая путь после восстановления.

**Предложение.** Явно заменить предикат fallback в ADR-0098 §3 тем же доказательством администратора, что §2 ADR-0100, и указать поведение при неизвестном доказательстве/восстановлении. Контроль: постоянный admin только через встроенную роль, прямых строк нет, у обычного u наступает expires — u выключен; второй контроль — аномальное состояние без доказанного администратора и определённый защитный исход. Не снимать защиту срока молча со всех людей.

## Остальная проверка и вопросы

- Прямое назначение admin, группа и legacy-строка считаются раздельно; одно конечное until/expires не заменяет постоянного администратора. Политика «проверить итог пакета» верна для замены администратора внутри одного пакета; проблема №2 — между пакетами.
- Без нечитаемости/гонки очевидная самоэскалация управляющего закрыта: admin.assigned, защищённые люди и группы, domain/grants/domain и break-glass запрещены. Выдача себе всех **кластерных** прав разрешена владельцем и не названа находкой.
- Исключения ADR-0099 внутри другой роли не отменяют доказанного встроенного admin. Старые прямые администраторы сохраняют только прежние права домена, не становятся глобальными автоматически — это указанная совместимость.
- Аварийный вход кластера не превращается в токен человека процесса domain: его двери требуют kind:person, cluster:null. Отсутствие такой эскалации — не находка. Правило glass раньше чтения грантов у консоли кластера сохраняется.
- Роли/группы уже включены ADR-0098 §5 в state копии и заморозку передачи. Повторять прежнюю находку об их потере при переносе оснований нет.

**Вопрос 1.** Какой точный исход восстановления, если после открытия секретов и применения state не осталось ни одного доказанного администратора (P/08.8 Н1.8 шаг 7 допускает Sealed и продолжает перенос)? Двери групп/людей этого пути не видят. Нужна явно названная аварийная ветвь, а не предположение, что обычный last_admin уже защитил любую резервную копию.

**Вопрос 2.** Как встроенный admin без строк представляется в `/session.grants` и подсказке P/07? ADR-0098 §4 считает подсказку по элементам строк, а у admin их нет. Предлагаю назвать синтетический элемент/признак только для ответа и добавить P/06.7/P/07 в порядок работ; он не должен становиться запрещённой сохранённой строкой role:admin. Отдельно контракт consolem `/access/apply` обещает SELF_LOCKOUT текущему администратору даже при наличии второго: это остаётся проверкой V/11 сверх доменного last_admin или намеренно не поддерживается?
