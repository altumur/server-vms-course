## С-01. Перечень содержания заголовка не задаёт воспроизводимую независимую проверку

Место: `decisions/0125-генераторы-по-спецификации-пилот-p01.md:192,195`,
пп. 1 и 4.

П. 1 требует описать «колонки входа, поля выхода, правила преобразования,
выбор варианта, так, чтобы генератор воспроизводился по описанию» и называет
это проверкой Т3. П. 4 задаёт пилот с эталоном настоящих пакетов. Это ясная
цель описания, но ещё не полный проверочный договор: не названы разрешённые
входы воспроизводящего автора, единица сравнения и проверка переноса правила
на иной допустимый вход той же формы.

Минимальный контрпример проверки только нынешних снимков: воспроизводящий
код содержит готовые выходы для известных пакетов и не использует строки
таблицы. На этих пакетах он совпадает с эталоном. На копии той же таблицы
с новым допустимым `name` строка/объявление не меняются. Это не генератор,
воспроизведённый из правила, и не обещанное п. 2 поведение нового входа.
Например, у нынешнего gen_refusals имя должно определять соответствующий Spec
и индекс ByName; описанный hardcode этого не делает.

Кроме того, одинаковые API и значения метаданных при разных комментариях/
оформлении Go дают разный результат при побайтном и семантическом сравнении.
Какое равенство требуется пилотом, из пп. 1/4 не следует. Не навязываю один
из этих способов как новое решение владельца — требуется явно выбрать его.

Предложение для исполнения:

1. Закрепить header SHA, Source/input roster и разрешённые зависимости.
   Воспроизводящий автор получает описание и объявленные входы, а не тело
   исходного продюсера, его скрытые шаблоны или ожидаемые ответы.
2. Явно назвать сравниваемое: файлы/API/структуры и значения либо точные байты
   с объявленным форматированием. Генератор, копируемые runtime-файлы и YOURS
   не смешиваются в одно неописанное обещание воспроизводимости.
3. Помимо настоящего пакета проверить допустимое изменение данных при прежних
   колонках и отсутствие зависимости от имени урока. Для отказов достаточно
   независимого изменения строки/имени/значения и проверки соответствующего
   Spec; не нужен новый публичный язык.
4. Проверить сохранение строгого отказа на повреждённом входе. Сборка,
   неполный ответ и недоступный вход — ошибки проверки, не свидетельство
   успешного воспроизведения и не смысловой kill.

Требование закрытой грамматики и её предметного проверщика Т3 не исчезает
от совпадения двух выходов: два кода могут одинаково неверно принять вход.
Нужны независимые ожидания из объявленного входа/нормы, а не только сравнение
с render автора. Это уточнение процедуры проверки принятого решения,
не предложение заменить заголовок документацией в другом месте.

Серьёзность — существенная: без проверочного договора можно принять
непереносимую копию снимков либо отвергнуть корректное воспроизведение по
необъявленному критерию. Причинность — новая проверка пп. 1/4 пока описана
только целью. Ни один пилот или реконструктор здесь не исполнялся.

## С-02. Новый эталон 46c нужно отделить от неизменяемого старого P/02

Место того же файла: `:194–196`, пп. 3–5.

П. 3 прямо меняет выход P/02 на общий вариант. П. 4 требует эталон из
настоящих пакетов уроков, но не называет их версию. П. 5 правильно запрещает
пересборку закреплённых пакетов ce8 ради нового правила.

Разрешённая текстом ошибочная последовательность: реализован новый общий
вариант P/02, а для 46c взят прежний настоящий пакет со старым P/02. Правильный
новый выход закономерно не совпадёт с ним. Если вместо этого подогнать
воспроизводящий код под старый пакет, он сохранит отменённое различие.

Это не утверждение, что конкретный старый пакет уже выбран неправильно:
фактические пакеты/пины пилота в данном задании не представлены и не открывались.
Но версия эталона — необходимый вход до запуска, особенно при намеренном
изменении результата.

Предложение: назвать последовательность «новый заголовок и prod/common P02 →
новый отдельно опубликованный пакет на разрешённой выбранной выгрузке →
эталон 46c». В передаче пилоту закрепить Source/export pin, Code/header pin,
package/artifact identity, состав уроков и критерий сравнения из С-01.
Старый ce8 не лечить, не перезапечатывать, не подменять новым CodeRoot под
прежним именем. Его можно сохранить историческим свидетельством различия,
а не эталоном изменённого варианта. Пилот запускает владелец; это ревью
его не назначает и не снимает отдельные удержания P/02.

Серьёзность — существенная: смешение двух редакций даёт ложный отказ либо
ложное подтверждение нового правила. Причинность — новый выход п. 3 и
неуказанная редакция эталона п. 4 при правильной защите п. 5.

## Набор колонок: факты о gen_refusals

Статически прочитаны текущие заголовки реальных форм:

| Вход | Фактическая форма на целевом pin |
|---|---|
| P02/P03/P04 | Одинаковые 15 колонок `chapter,row,name,surface,code,kind,fields,headers,log,norm,word,cause,outcome,diagnostic,caller` |
| P05/P06/P08/P09/P10 | Те же колонки с `response_schema` после `word` |
| P01 в коде Table | 10-колоночная форма без последующих текстовых колонок |

П. 3 верно называет P02/P03/P04 одной формой. Нынешний код действительно
различает их по имени:

- `tools/normgen/gen_refusals.py:328–351`: P02 оставляет word как есть;
  P03+ сохраняет WordCell и строит индекс Word/Named по quoted tokens;
- `:421–424`: исключение для текста Chapter у P02;
- `:438–441`: Named/WordCell включаются по `table.word_any`, полученному
  из имени урока;
- `:489–492`: выбор Table/PlainTable уже опирается на колонки.

Общий вариант не означает одинаковые значения на разных строках. Он означает
одно описанное правило преобразования для одной формы. Данные таблицы
по-прежнему определяют строки, значения и допустимые условные части выхода.

Есть важное следствие перехода: P02 `load_text` имеет word `refused:text`
(`Platform/02-installer/forms/refusals.tsv:11`), а P03 первая строка содержит
backticks (`.../03-worker/forms/refusals.tsv:8`). Механически перенести старый
P03-проектор и потерять смысл буквального слова P02 нельзя. Общий контракт
должен явно сохранять исходную ячейку/её смысл и описать индекс; необходимы
проверки потребителей изменяемого API. Само изменение представления P02
разрешено владельцем, новая семантика отказа — нет.

У P03 есть peer fields/headers, хотя у нынешних P02/P04 таких строк нет
(`03-worker/forms/refusals.tsv:44,53`). Нельзя спутать различие данных с
правом сохранить скрытый selector по имени.

### Необязательные поля P06

`Platform/06-console/forms/refusals.tsv:249`, c67_027_503_1, действительно
содержит `detail,error,supervision?`. В `gen_refusals.py:281–290` suffix уже
читается, но его допуск закрыт на `L.key == "06-console"`; полный разбор
schema definitions для ролей также только у P06 (`:251,291–301`).

Для принятого правила урок с той же response-формой не должен получать иной
смысл `?` по имени. Заголовок должен описать общий суффикс, условие http/
response_schema и связь required/optional с полным OpenAPI. Сам suffix не
отменяет условную обязанность supervision у соответствующего тела. Входные
required-проекции не превращать в требование перечислить все optional
properties; оригинальное supervision? при его наличии не терять.

Это необходимые последствия реализации п. 3 и общности варианта, не новые
находки сверх С-01/С-02 и не CODE-поручение от рецензента.

gen_core, gen_flags, gen_launch, gen_policy_machines, gen_stagetests.
Это не доказательство отсутствия всех возможных скрытых веток по любому
алиасу; op/rows/defaults и другие ветви не проверялись целиком.
