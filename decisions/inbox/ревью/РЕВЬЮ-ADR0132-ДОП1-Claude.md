# Независимое ревью ADR-0132 доп. (1) — review103-claude

**Вывод: с правками; удаление не включать, пока не исправлены Б1 и Б2.** Счёт: Б 2 / С 5 / М 3.

Решение владельца не оспаривается: деревья и ветки убираются таймером. Но условия пп. 1–2 в нынешней записи допускают необратимую потерю, и это видно на сегодняшнем состоянии CT 103 и GitHub:

- **Б1.** Ветку можно удалить без метки, если «содержимое в `origin/main`». У 35 живых веток так и есть, а конец в `main` не входит. В 27 из них лежат коммиты, на которые ссылаются ADR.

## Находки

**Б1. Ветка удаляется без метки, если содержимое в `main`.**
- Место: `:66` «содержимое в `origin/main` или конец сохранён меткой `archive/<ветка>`; метка ставится до удаления, чтобы ссылки ADR на коммиты отчётов не повисли».
- Случай: отчёт ревью попадает в `main` переносом файла, а не слиянием. Пример: `claude103/review-adr0129-text-56643214`, коммит `c4df2594a`, ADR-0129 `:449`; файл отчёта в `main` есть, коммит предком `main` не является. Условие «содержимое в `origin/main`» истинно, метка необязательна, ветка удаляется, SHA из ADR больше ни на что не указывает.
- Масштаб: 35 веток, 27 с процитированными коммитами.
- Источник: сам `:66` (цель метки); ADR-0114 (разбор ссылается на SHA отчётов).
- Последствие: ссылка повисает; GitHub может убрать объект, восстановить коммит нельзя.
- Предложение: без метки удалять только ветку, конец которой — предок `origin/main`. Иначе — метка всегда. «По содержимому» из условия удаления ветки убрать.

**Б2. «Ветка удалена» и «конец ветки» не определены для дерева.**
- Место: `:65` «если ветка в `origin/main` по содержимому или удалена … Конец ветки должен быть достижим из `origin/main` или метки».
- Случай: дерево на отсоединённом HEAD. Ветки нет: условие «удалена» можно счесть выполненным, а «конца ветки» нет. Сейчас таких 10, из них 3 чистых дерева с HEAD, не входящим ни в `origin/main`, ни в метку, ни в одну локальную ветку, и без строки `hold`:

| Дерево | HEAD | Сверх `origin/main` |
|---|---|---|
| `/home/pilot/wt-spec103-p08-forward-gate` | `3cf73bba1a74` | 14 |
| `/home/pilot/wt-spec103-p08-review-source-gate` | `e0f7927b7a88` | 20 |
| `/home/pilot/wt-spec103-p09-forward-gate` | `1eac8d337467` | 23 |

  HEAD дерева — единственная ссылка на эти коммиты: после `git worktree remove` они недостижимы и уйдут при очистке.
  Вариант той же ошибки: локальная ветка впереди удалённой, или push шёл по URL без `origin/<ветка>` (так делает эта сессия): «удалена» по удалённым ссылкам ложно.
- Последствие: необратимая потеря коммитов.
- Предложение: условие задать через HEAD дерева: `HEAD` — предок `origin/main` или метки, ссылка свежая (`git fetch` / `ls-remote` в том же проходе). «Ветка удалена» убрать. Иначе дерево остаётся и идёт в список.

**С1. Доп. (1) не согласовано с основным текстом.**
- Место: `:65`, `:66`; `:31` «только то, на что есть строка `release`»; `:42` «Никогда без слова владельца: … рабочие деревья»; `:40` «нет открытых файлов, cwd и отображений в памяти … Непосредственно перед удалением тождество каталога и `hold` проверяются заново».
- Случай: исполнитель не может решить, нужна ли строка `release` (`:68` оставляет её как вариант). Если не нужна — дерево с чистым состоянием удаляется при открытой задаче. Проверка только cwd пропустит процесс с cwd вне дерева, читающий файлы дерева: сборку или тест, запущенные с абсолютными путями.
- Предложение: прямо сказать, какие пункты заменены и какие общие условия (`:40`) действуют; перепроверка `hold` и условий непосредственно перед удалением обязательна. По `release` решение за Архитектором; рекомендую требовать.

**С2. Метка и удаление не атомарны, имя метки может быть занято.**
- Место: `:66`, `:67`.
- Случай: (а) список составлен в 04:00, автор отправил новый коммит, таймер удаляет ветку по имени: новый конец потерян. (б) `archive/<ветка>` уже есть от прежней ветки с тем же именем: проверка «метка существует» проходит, а новый конец не сохранён.
- Предложение: одна атомарная операция: `git push --atomic`, создание метки и удаление с `--force-with-lease=<ветка>:<OID>`. Метка должна указывать ровно на этот OID, при занятом имени — пропуск и строка в отчёте.

**С3. «Старше суток» не определено.**
- Место: `:66`.
- Случай: у Git нет времени создания ссылки. По дате коммита новая ветка, поставленная на старый коммит (срез, пин), окажется «старой» сразу.
- Предложение: считать по наблюдению таймера: тот же OID виден не менее суток.

**С4. «Живое дерево» видно не везде; у ветки нет `hold`.**
- Место: `:66`; `disk-policy.tsv` (колонка `path`).
- Случай: ветка в дереве другого клона (на CT 103 их минимум 7: `review103-kimi`, `review103-claude`, `spec103-claude` и другие) или на маке. Проход по одному репозитории её не увидит. Защитить ветку нельзя: `hold` принимает только путь, а условия `:66` его не называют.
- Предложение: объединённый список деревьев по всем клонам; форма `hold` для ветки; для мака — решение, как он участвует.

**С5. Не задан охват: какие репозитории и какие ветки защищены.**
- Место: `:65`, `:66`.
- Случай: (а) деревья есть в репозиториях с другим `origin`: `cammeta-acceptance`, `cammeta-specs` (рабочая ветка `exports`), `assist-pilot`. «В `origin/main`» там значит другое. (б) На GitHub 7 веток про VMS (`vms/*` — 4, `owner/adr-vms-0001`, `Claude/`, `Codex/review-adr-vms-0001`) старше суток могут быть сняты, хотя ADR-0083 доп. (146) п. 3 «Из репозитория ничего не удаляется». Закрытого списка защищённых имён нет.
- Предложение: назвать репозитории и ветку по умолчанию для каждого; закрытый список защищённых имён; по VMS — вопрос Архитектору.

### Мелкие

**М1. Порог сработает сразу.** `:69`: 60 деревьев, сейчас 170 только в основном репозитории. Предложение: задать порог после первой уборки или в зависимости от состояния.

**М2. Часть ссылок проверить нельзя.** 149 коротких хешей в строках об отчётах и коммитах не находятся; часть — других репозиториев. В ADR-0129 есть ссылки короче 7 знаков (`3bc5`, `180f`, `8c92`). 132 метки `archive/*` на заявленные 198 удалённых веток (`:63`): разницу стоит объяснить (достижимые из `main` метки не требуют). Предложение: разовая опись до включения.

**М3. Состояния дерева сверх статуса.** `git status` не покажет правки файлов с флагами `S`/`h` (`git ls-files -v`) и не отразит незавершённый rebase/merge, stash и блокировку `locked`. Сейчас таких файлов на диске не найдено. Предложение: добавить эти проверки в список; `--force` не использовать.

## Что проверить перед первым включением

1. Прогнать режим списка на трёх деревьях Б2 и на 35 ветках Б1: все должны быть «оставить» или «поставить метку», ни одно — «удалить без метки».
2. Контрольные случаи: отсоединённый HEAD; локальная ветка впереди; push между списком и удалением; занятое имя метки; ветка в другом клоне; `hold` родителя и потомка; процесс с открытым файлом без cwd внутри.
3. Опись ADR: каждый полный или 7+ знаков SHA отчёта разрешается в объект, достижимый из `main` или метки, до и после прогона.
4. Репетиция восстановления: из метки вернуть ветку, из метки или `main` — дерево; записать время.
5. Закрытый список защищённых имён и репозиториев принят Архитектором.
6. Журнал: путь или ветка, OID до удаления, метка, правило, время. Без OID восстановление не опереть.
7. Ночной проход не пересекается с работой: блокировка от двух одновременных проходов.
