# Ревью ADR-0126 — Codex

Основа: `origin/main` **dbb15b2eb**. Прочитаны ADR-0126, README реализации P/01 и английский источник его «Order of work», ADR-0083 доп. (89), (90). Для уточнения существующего договора просмотрены обработка вех в `minimax-loop/loop.py` и текущее задание P/01.1; код не запускался. Итог: **Б 0, С 3, М 1**.

Это ревью решения: отсутствие пока не написанных `stages.tsv`, её судьи или нового генератора вех само по себе находкой не считается.

## С1. `own_tests` не позволяет машине установить наличие тестов именно текущего этапа

**Место:** Decision Drivers, второй пункт; Decision Outcome п. 1, `gate: own_tests`; п. 5.

**Цитата нормы:** «У каждого этапа — проверка конца, которую видит машина»; «`own_tests` — свои тесты реализации проходят, и среди них есть тесты этого этапа».

Таблица не несёт идентификатора набора тестов, связи теста с `stage`/`norms` или договора отчёта об исполненных тестах. Успех общего `go test ./...` не отличает тесты проверок Н1 от тестов хранилища Н3; тем более он не доказывает, что нужные тесты вообще были исполнены, а не пропущены. В текущем задании судья своих тестов — именно такая общая команда. По одному её exit code следующий этап может получить тот же зелёный результат без нового теста и без реализации своей цели.

Существование якорей в `norms` этого не исправляет: оно проверяет адрес нормы, а не связь результата тестирования с этапом. Для человека и разных языков нельзя молча зашить такую связь через имена Go-пакетов.

**Предложение:** задать переносимый договор `own_tests`: стабильные идентификаторы проверок/наборов этапа и адаптер реализации, который сообщает реально исполненные идентификаторы и исходы. Нужный набор должен быть непустым; skipped, отсутствие набора или недоступность адаптера не закрывают этап. Принадлежность и содержательность собственных тестов подтверждаются ревью, машина проверяет идентификаторы и выполнение. Не обещать, что машинная проверка наличия набора сама доказывает покрытие всех норм этапа.

## С2. Общая таблица урока не определяет выбор этапов для попытки на часть его целей

**Место:** Decision Outcome п. 1 (`norms`, `depends`), п. 3 и п. 4.

**Цитата нормы:** «Задание называет только урок, цели приёмки и пределы»; «Цикл MiniMax берёт вехи из `forms/stages.tsv` урока, а не из задания».

P/01 — уже конкретный случай несовпадения областей. README задаёт работу по всем трём главам, включая группу, копии и восстановление. Попытки (89), (90) реализуют только P/01.1; текущее задание называет цели `P/01.1 door`, `P/01.1 extra` и явно оставляет за пределами raft, import, floor и recover. При этом запуск и часть прав из **P/01.3 и P/01.2** обязательны для этой попытки.

В `stages.tsv` нет области применимости этапа к целям/профилям, а правило выбора отсутствует. Взять всю таблицу — расширить попытку до полного урока. Отобрать этапы по ссылкам `norms` на главу 1.1 — потерять запуск из 1.3 и права из 1.2. Отобрать только строки с подходящим `accept:` — потерять ранние строки `own_tests` и `build`. `depends` задаёт зависимости уже выбранных строк, но не определяет исходный выбор, особенно если одна строка объединяет разные области.

**Предложение:** определить применимость этапа к целям и профилям и алгоритм отбора: выбранные терминальные этапы → замыкание `depends` → порядок по `n`. Для P/01.1 явно включить минимальный запуск и права, не включая весь демон 1.3. Смешанный этап, который нельзя отобрать целиком, разделять. Неизвестная цель или отсутствие полного пути к её завершению — ошибка подготовки попытки. Человек и линия Codex выбирают область работы по тому же правилу; вся таблица остаётся порядком полного урока.

## С3. Не определено, сохраняется ли жёсткий предел вехи при чтении `budget`

**Место:** Decision Outcome п. 1 (`budget`), п. 4; Consequences, «Предел».

**Цитата нормы:** «`budget` — ориентир усилия в ходах цикла»; «`budget` — только ориентир». ADR-0083 (89) п. 3: «Предел ходов вехи истёк — остановка `milestone_stalled`». Доп. (90) п. 2 устанавливает первой вехе **120 ходов**.

Действующий цикл использует `max_turns` каждой вехи как жёсткую границу, а новый текст предлагает брать вехи из формы с рекомендательным числом. Две реализации одинаково правдоподобны: превратить `budget` в `max_turns` и остановить модель либо считать его подсказкой и продолжать до общего предела задания. У попыток будут разные исходы и цена при одной таблице. П. 4 оставляет заданию «пределы», но не задаёт их связь с бюджетом этапа.

**Предложение:** выбрать явно: либо `budget` — рекомендация всем исполнителям, а жёсткий предел этапа задаётся отдельной политикой цикла в задании; либо это предел для MiniMax и справочный ориентир для людей/Codex. Во втором случае поправить слово «только». Определить приоритет общего предела, счёт ходов, начало/возобновление этапа и запись применённого предела в паспорт. Указать, заменяются ли 120 ходов из (90), и сохранить бюджет чтений (90) как отдельный счётчик, а не ещё одно толкование `budget`.

## М1. Для селекторов сценариев и порогов недостаточно проверить только имя цели

**Место:** Decision Outcome п. 1, два вида `accept:`; п. 5.

**Цитата нормы:** «цели приёмки — из описи урока»; «`accept:<цель>:<сценарии>` — названные сценарии проходят целиком».

В перечне проверки не названы существование и применимость самих сценариев, непустота их выбора и достижимость N. При существующей цели строка с неизвестным сценарием или порогом выше числа её проверок проходит перечисленные условия, но исполнить gate невозможно. Для цели вроде `extra` проверки также могут не иметь идентификаторов TSV-сценариев. Числа целей зависят от закреплённых версии раннера и профиля: в (89) 429 — сумма door и extra, а не автоматически число одной цели.

**Предложение:** описать синтаксис списка/диапазона сценариев и разрешать его только у целей с такой адресацией. Судить существование каждого селектора, непустоту реально применимого набора; skipped/not_applicable/неисполненное не считать прохождением сценария. Порог — положительный и достижимый по описи выбранного профиля. `check_spec` проверяет статическую часть формы, подготовка попытки — соответствие закреплённой описи раннера; расхождение должно останавливать подготовку, а не расходовать budget модели.

## Граница формы и норм

Отказ от второго текста «Order of work» и сохранение английских ссылок полезны: таблицу смогут читать люди и разные линии. README сейчас прямо разрешает иной внутренний API и разбиение на функции; форма этапов не должна отменять эту свободу или добавлять поведение сверх норм. Для ранних этапов `own_tests`, сборки и адресуемых сценариев достаточно как проверок рабочего прогресса после уточнений выше. Порог N также годится как веха прогресса, но не доказывает выполнения конкретной нормы: в P/01.1 даже проверки неизвестных маршрутов дают пройденные шаги.

Отдельно сохранить завершение полного урока: чеклист и пункты «checked by reading»/«Implementation decides» из README не заменяются зелёным счётчиком приёмки. Этапы и их gate — порядок работы; готовность реализации остаётся по канону и полной приёмке применимой области.

В этом проходе проверены текст и связи договоров, без запуска MiniMax, раннера, реализаций и серверных проб. Общая пауза ADR-0120 не снималась.
