# Ревью ADR-0117, дополнение (4), Codex

Проверена версия `origin/main` **4ef090082**, вместе с действующим текстом ADR-0117. Прочитаны прежние отчёты Codex и Claude о (2), (3). Сверены P/02.1, P/02.5 Н1.4, P/04 Н1.3 и Н3 шаг 8, договор сторожевой и передачи (`need`), V/05.1 Н1.3, V/11.8. Код клонов и тесты реализации не запускались.

**Счёт по (4): Б 0, С 2, М 0.**

Б1 закрыт: единицы только в `exp/parts`, заказ — таблица; агрегация не требует второго вида размещаемых строк. Прежний С1 о запрещённой очистке поля воркером снят выбранным пределом хранения секрета до удаления части. Утрата файлов при переезде и расход `capacity` готовыми частями названы пределами, повторно не выставляются. Однако автоматическое удаление строки и отмена с объявленным рангом пока не обеспечены нормами.

## С1. `retire_when.delete_after` не удалит созданную backend строку части с fixed-полями

**Место:** доп. (4) пп. 1–3.

**Цитаты решения:** части имеют `cam`, `rec` с `fixed`, `about: cam`; backend создаёт заказ и части одним пакетом; пароль «уходит вместе со строкой при её снятии по сроку файлов — предел: до 24 ч».

**Норма:** P/04 Н1.3, `unplaced`, и Н3 шаг 8: при fixed-полях или `about` не по id физически удаляется только строка с `made`; «ручная строка не удаляется — `expired_kept + 1`». То же действует для `retire_when.delete_after` и `ends`. Образец V/05.1 Н1.3 прямо различает удаляемые заказы с `made` и ручные строки. `made` — метка заказа другого воркера по `worker.creates`, не обычного пакетного создания backend по билету.

**Проблема:** `exp/parts` создаётся обычным пакетом консоли, с fixed-полями камеры и записи. В тексте нет создания по механизму `made`. Истечение снимет часть с размещения, но контроллер оставит строку с `password_secret`. Поэтому новый предел хранения не выполняется даже при работающем контроллере: секрет может остаться после удаления файлов бессрочно.

**Предложение:** назвать отдельный разрешённый механизм физической очистки. Например, `worker.deletes: [parts]` и удаление всей строки держателем с CAS до потери возможности исполнить уборку, плюс явное правило для уже снятой/перенесённой части; либо нормированная уборка под admin. Не считать слово «снятие» эквивалентом удаления. Приёмка — часть, созданная именно `/exports` через пакет backend без `made`: после срока файлов строки и секрета нет, в `expired_kept` она не остаётся.

## С2. Ранг `edit` позволяет создать экспорт, но не выполнить отмену записью строки части

**Место:** доп. (4) пп. 1 и 4; основной текст §2 «Отмена — своего задания».

**Цитаты решения:** «отмену [backend] пишет в каждую часть»; «`EXPORT` — `edit` на `exp` по камере»; `admin` обозначает уже исключения из обязательных пароля и маски.

**Норма:** договор сторожевой и передачи, `need`: для строк единиц `PUT/DELETE` требуют `admin`; «`rights.routes` их не понижает — у строк единиц понижается только создание». V/05 (`detjob`) использует `edit` именно для создания задачи, сохраняя admin для правки и удаления её строки. Backend работает по билету автора и собственных прав записи не имеет (V/11.1 Н1.3).

**Проблема:** автор с `EXPORT`, но без функций обхода защиты, получает `edit` на `exp`. Он создаст части через пониженное право создания, но `POST /exports/{id}/cancel`, реализованный записью каждой строки части, получит отказ проверки прав. Проверка `by` не повышает ранг билета. Повышение такого автора до `admin` по новой схеме одновременно разрешило бы ему немаскированный экспорт без пароля, то есть изменило бы политику ради отмены.

**Предложение:** отмену передавать разрешённой автору просьбой/маршрутом, а результат записывать держателем в `state`, либо явно принять отдельный механизм доступа. Если удаление задания также должно быть доступно автору с `edit`, определить аналогичный путь. Приёмка — автор только с `EXPORT` создаёт защищённый экспорт и отменяет его, не приобретая права на экспорт без маски и пароля.
