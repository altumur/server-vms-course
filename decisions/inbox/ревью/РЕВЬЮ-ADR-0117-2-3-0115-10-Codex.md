# Ревью ADR-0117, дополнение (2), Codex

Проверена версия `origin/main` **ef52742b2**, основной текст с дополнениями (1)–(3). Прочитаны прежние отчёты Codex и Claude. Сверены P/02.1 (один `unit`, таблицы), P/04 Н1.3 (размещение), P/02.5 Н1.4, P/06.3, V/03.3, V/11.8 и требования `cammeta-console/ТРЕБОВАНИЯ-ЭКСПОРТ.md`. Код клонов и тесты реализации не запускались.

**Счёт по (2): Б 1, С 0, М 0.**

Прежний Б1 о двери готового файла закрыт выбранным удержанием задания до истечения файлов; потеря сервера названа пределом. Прежние С2–С4 закрыты: выбран маршрут кадра по роли, отказ при недоступной обязательной защите и выдача байтов только автору. Проверка всего набора камер в п. 2 закрывает прежний пробел проверки доступа. Но новая раскладка заказа и частей пока не выражается манифестом одной подсистемы.

## Б1. `exp/jobs` и `exp/parts` описаны как два независимо размещаемых семейства единиц одной подсистемы

**Место:** доп. (2) пп. 1–2, доп. (3) п. 4.

**Цитаты решения:** «Задание — строка заказа `exp/jobs/<id>` и строки частей `exp/parts/<id>` … у каждой свои `cam`, `rec`, `about: cam`, `near: rec`»; «Координатор — держатель заказа»; готовые задания также продолжают держаться, а сборка читает двери частей.

**Норма:** P/02.1 определяет единственный `unit: {rows, id, fields?, state?}` подсистемы; `about` и `placement` — разделы этого манифеста. У `tables.<имя>` закрытый набор `{key, fields, schema, service, stamp, journal, delete_after}`: нет собственного `about`, `near`, размещения, состояния или держателя. P/04 Н1.3 размещает единицы `unit.rows`, а не строки каждой таблицы.

**Проблема:** при `unit.rows: jobs` строки `parts` — таблица и не получают обещанных независимых держателей рядом с записями. При `unit.rows: parts` заказ в `jobs` — таблица и не получает своего держателя-координатора и двери файлов. Описать два `unit` в одном манифесте нельзя. Пакетное создание строк эту разницу не устраняет. Поэтому прежний вопрос «как части работают на разных серверах» ещё не имеет исполнимого ответа по выбранной раскладке.

**Предложение:** выбрать явную модель без неявного расширения платформы: отдельные подсистемы для заказов и частей; либо одно семейство единиц с различителем заказа/части и едиными правилами размещения; либо только камерные единицы, из которых backend собирает заказ, с явно выбранным координатором. Назвать для каждой роли `unit.rows`, держателя, состояние и дверь. Приёмка — две части разных записей на разных серверах, отдельная агрегация и скачивание после `done`.

# Ревью ADR-0117, дополнение (3), Codex

**Счёт по (3): Б 0, С 1, М 0.** Правки хранения функций и `depth`, владелец отметок P/06.4, использование токена `where`, поле автора и перенос тел в нормы названы. Осталось противоречие новому способу очистки пароля.

## С1. Воркер не имеет права очистить `password_secret` в строке заказа

**Место:** доп. (3) п. 3.

**Цитата решения:** «Пароль до воркера идёт полем `password_secret` строки заказа; воркер снимает его сразу после упаковки последнего файла».

**Норма:** P/02.5 Н1.4: «Строки единиц остаются за консолью … исключение таблицы воркера не даёт ему прав на `unit.rows`». `worker.writes` не может называть `unit.rows`. P/02.1 также отвергает `worker.writes` для объявленной таблицы с полем `*_secret`; `worker.deletes` разрешает удалить единицу целиком, а не очистить одно её поле.

**Проблема:** заказ создаёт backend через консоль, а держатель затем пишет ход и итог в `unit.state`. Чтение секрета не даёт ему права переписать строку заказа. Для хранилища удаление поля — новая запись всей строки, а не разрешённое удаление ключа единицы. Значит, обещанная очистка не произойдёт с существующими правами. Перенос заказа в обычную объявленную таблицу воркера с тем же секретным полем также не является готовым обходом ограничения.

**Предложение:** выбрать предусмотренного писателя и механизм очистки: отдельное хранилище/службу доставки секретного материала с собственным жизненным циклом либо явно нормированное действие консоли. Если меняются права платформы, назвать это отдельной долей работ; если принимается иной срок хранения, изменить обещание и требования явно. Приёмка — упаковка при уже закрытом запросе и без открытого окна пользователя, затем проверка отсутствия секрета в строке без удаления самого задания.

## С1. Алгоритм для каждого `source` не отделяет ссылку на собственный тип от межплагинной зависимости

**Место:** доп. (10) п. 1.

**Цитаты решения:** «Для каждого `object_type` из `source` сборщик … находит плагина-владельца среди установленных»; «Генератор добавляет зависимому манифесту … `worker.requests` к нему».

**Норма:** `source.object_type` в схеме psim называет тип объектов `ListObjects`, без требования, чтобы это был другой плагин. P/02.1: `worker.requests` — «другие подсистемы (своя — отказ)»; связь № 88 требует `. != @name`.

**Проблема:** допустим, параметр SENSOR выбирает CONTROLLER того же плагина. Сборщик найдёт владельцем этот же плагин и по буквальному алгоритму добавит `worker.requests` на собственную подсистему. Полученный манифест загрузчик отвергнет. Заголовок о межплагинных вызовах не задаёт исключения внутри правила «для каждого `source`».

**Предложение:** явно разделить случаи: свой тип обслуживается локальным каталогом/адаптером без `worker.requests` и внешней зависимости; для чужого типа добавляются межподсистемные декларации. Предел вызовов вне `source` также формулировать именно для чужих типов. Приёмка — собственный `source` внутри одного плагина и внешний `CAM` у `security_controller`; оба манифеста проходят загрузчик, самоссылки в `worker.requests` нет. Это пример по схеме, код не запускался.
