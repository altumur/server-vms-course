## С1 — исходный `harness.Instance` остался без подготовки каталога

**Где:** `runner/harness.py:305–321`, `Bench.open:376–379`; достижимые вызовы — `runner/extra.py:158–175`, `runner/run.py:167–190`. В изменённом `runner/c_store.py:67–89` подготовлена другая реализация Instance, и лишь мост на строках 452–453 подменяет ею `harness.Instance`. Сам общий низкоуровневый носитель не исправлен.

**Нормальное ожидание:** Source `6379b876…`, README:133, требует подготовленный пустой `configstore 0700` для одиночного стенда. Обычная команда запуска демона с `-dir {data}/configstore` может полагаться на это и не обязана добавлять скрытый mkdir в wrapper.

**Конкретный путь:** прямой вызов существующего `extra.py --start '<обычный шаблон демона>' --cwd <каталог>` создаёт `Bench`; первый probe вызывает `bench.open()`. Тот вызывает исходный глобальный `harness.Instance`, поскольку этот процесс не прошёл через `c_store._configured`. Конструктор создаёт workdir, `run` и rights, но не создаёт ни `{data}`, ни его `configstore`; затем сразу вызывает Popen с подставленным путём. У `run.py` тот же Bench, при наличии требуемого этим CLI `--request-line-limit`. Движки по-прежнему принимают эти аргументы; отказа «прямой режим не поддерживается» до Popen нет.

**Следствие:** демон, исполняющий новое правило и не создающий отсутствующий `-dir`, на этом одиночном стенде не запустится. Фикс c_store не достигает такого пути. Дополнительные wrapper-действия реализации могли бы скрыть проблему, но не выполняют обязанность самого общего носителя. Это ограниченный дефект прямых low-level входов, а не подтверждённый сбой официального format2/C запуска и не вердикт реального кандидата.

**Доказательство:** статическая цепочка выше плюс `test_unwrapped_legacy_inventory_observation_only`: точный исходный AST-конструктор с подменённым Popen получил `data/configstore` отсутствующим. Положительный контроль в том же новом запуске подтвердил существование, пустоту и mode каталога для исправленного `c_store.instance_class`. Никакой CLI и демон для воспроизведения не запускались. Наблюдательный тест проходит, когда обнаруживает отсутствие каталога; его PASS нельзя считать выполнением нормы.

**Корневая причина:** новая общая обязанность разнесена по четырём вариантам, но базовый носитель прямого стенда оставлен прежним. Его байты не изменились в коммите; замечание — о неполноте реализации нового решения, а не о новой поломке внутри его старого тела. Один root cause, без отдельного счёта для run/extra/cached aliases.

**Короткое исправление:** использовать общую подготовку также в исходном Instance. Текущий README раннера:480–482 ещё предлагает прямой запуск этих команд. Самовольно снимать такую поддержку или считать успешным пропуск проверки нельзя; иное решение о границе требует отдельного слова владельца. Исправление подготовки не требует новой формы профиля. ## Foreign, import, backup и restart

**Foreign.** `_second` теперь уже создаёт cdir. Поэтому старое `os.makedirs(cdir)` в `foreign` удалено; повторный mkdir не мешает контролю. Снимок exact `Stand.tree` сделан после этих seed-записей и до подменённого старта. При exit2 без изменения дерева обе ветви прошли; при дополнительном изменении bytes метод вернул mismatch. Это проверка самого наблюдателя, не отказ настоящего демона.

**Import.** Команда `import` получает прежний `{data}`, а не cdir вместо PLATFORM_DIR. Проверка с собственной callback-командой увидела готовый пустой `configstore 0700` ещё до импорта, отдельный файл входа и index_base из заголовка. В положительной ветви callback наполнил cdir своим маркером; `_start_second` затем увидел тот же результат без очистки. В refused-ветви другой second остался пустым и тоже существовал до следующего запуска. Начальный пустой каталог создаётся до операции, а не заново поверх результата импорта перед restored: это соответствует совмещённому чтению README:133 и 277. Семантика действительного переноса, проверка full copy и реальные двери NOTEXEC.

**Backup in-data.** Exact `Stand.backup:607–633` по-прежнему задаёт `{file}=self.data/configstore/<name>`. На собственном существующем FORMAT/rows snapshot подменённый CLI возвратил ненулевой код без файла; метод принял refusal, а дерево осталось побайтно тем же. Подготовка не добавляла mkdir или записи в data после исходного снимка. Полный успешный backup/durability не проверялся; это граница аргумента, отсутствующего файла и отсутствия дополнительных записей раннера.

**Restart / power-back.** `Stand.restart_store` и `restart` идут в существующий `start_store` без нового `store_directory`. `Group.restart` повторяет сохранённый command. Повторный `Group.start` и `Members.directory` пропускают создание при наличии каталога. Собственные FORMAT/rows и выбранный mode существующего каталога сохранены при этих путях. Power-back не очищает данные и не добавляет join/bootstrap/force; проверена функция на fake process state, без реального падения питания или живых процессов.

Прямой helper на существующем непустом каталоге даёт FileExistsError без очистки; его обычные вызовы находятся только на новых data-root. Подмена ошибки chmod подтвердила её распространение до запуска; это CheckingError подготовки, не отказ реализации. Общую политику filesystem aliases, конкурентных чужих создателей или миграции прежних mode это ревью не вводит.
