## Блокеры

### Б-1. Умолчание у самого определения не видят ни построитель раздела, ни проба мутантов

**Место.**
- `v7/section.py`:
  - `Section.walk` — столбец «Обязательность» берётся из `need(parent, k, s)` по самому месту;
  - `defs_body` — у строки `<определение>` столбец «Обязательность» всегда пуст: `rows = [("<%s>" % k, self.kind(d), "", …)]`.
- `v7/vectors.py:mutants` — фильтр `k != "default" or (len(path) >= 2 and path[-2] == "properties")`.

**Факт.**
- В схеме 02.1 умолчание типа поля стоит у определения: `$defs/fieldType` — `{"default": "string", "enum": [...]}`.
- В разделе диалекта строки `unit.fields.<имя>.type` и `tables.<имя>.fields.<имя>.type` говорили «необязателен; умолчание `string`».
- В разделе В7 — «необязателен», а строка `<fieldType>` — с пустой обязательностью.
- Строка «умолчание `string`» в нормах 02.1 после перехода встречается 0 раз (было 2). То же в 02.2: `<fieldType>` без умолчания.
- Проба мутантов: у диалекта 62 мутанта, у В7 — 61. Потерян ровно `default defs.fieldType`: фильтр пропускает `default` у корня определения (`path[-2] == "$defs"`).
- Добавил этот мутант руками: векторы его убивают (62 из 62). Сейчас правило держится. Но если векторы перестанут его держать, проба этого не увидит.

**Почему блокер.** Это норма формы, и проекция П4 её использует: в каноническом виде `type` есть всегда. После перехода её нет в тексте норм. `check_spec` требует, чтобы раздел совпадал с построенным байт в байт, поэтому вписать её руками «Спецификация» не может.

**Класс.** Аннотация места (`default`, `description`, `x-owner`), стоящая у определения, а не у места ссылки. Её применения:
- раздел (Б-2);
- мутанты;
- `x-default-text` — проверить так же.

**Предложение.**
- В разделе: у определения, показанного отдельным блоком, — его `default` и `x-default-text` в строке `<определение>`.
- У места, ссылающегося на такое определение, — «умолчание — по определению `X`».
- В `mutants`: снимать `default` везде, кроме значения внутри карты `properties` (то есть кроме `path[-1] == "properties"`), а не только под `properties`.

## Д. Добавка: UDR7 — висячая запятая в потоке

**Верно ли, что YAML 1.2.2 так читает — да.**
- Грамматика 1.2.2: `ns-s-flow-seq-entries(n,c) ::= ns-flow-seq-entry(n,c) s-separate(n,c)? ( c-collect-entry s-separate(n,c)? ns-s-flow-seq-entries(n,c)? )?`. После запятой продолжение необязательно, поэтому одна запятая перед `]` допустима. Две подряд недопустимы: после запятой обязана идти запись или `]`.
- `ns-s-flow-map-entries` устроено так же, поэтому то же верно для `{…}`.
- Набор `data-2022-01-17`:
  - принимает UDR7 (Пример 5.4 `[ one, two, ]`), 5KJE (Пример 7.13 `[ one, two, ]`) и 5C5M (Пример 7.15 `{ one : two , three: four , }`);
  - отвергает CTN5 `[ a, b, c, , ]` и 9MAG `[ , a, b, c ]`.
- 5KJE и 5C5M у В7 уже в `yts-refusals.tsv`, но по правилу корня (`root`), а не по запятой.

**Прогон слоя 1** (`a: <форма>\n`; В7 Python — `textv7`, В7 Go — `v7check`, эталон диалекта):

| Форма | В7 Python | В7 Go | Диалект |
|---|---|---|---|
| `[x, y, ]`, `[x,]`, `[x, y, ]  `, `[x, ] #c` | ok | ok | `empty flow` |
| `{b: 1, }`, `{b: 1,}` | **ok** | **ok** | `empty flow` |
| `[[x, ], y]`, `{b: [x, ], }` | ok | ok | `empty flow` |
| `[x,,y]`, `[x, , y]`, `[, x]`, `[ , ]`, `[,]`, `[x, y, , ]` | parser (text) | parser (text) | parser |
| `{, b: 1}`, `{b: 1,, }`, `{ , }` | parser (text) | parser (text) | parser |
| `[b: 1, ]` | ok `[{"b":1}]` | ok | `pair k: v` |
| `[x, ]#c` | lexis (`comment-tight`, 9JBA) | lexis | `#` right |
| `{b: 1, c: , }` | flow (п. 4 `{k:}`) | flow | `empty flow` |
| `[\n  x,\n  ]` | rare (многострочный поток) | rare | flow |

**Выводы.**
1. **Решение открывает и `{a: 1, }`.** Стек В7 обоих языков его уже принимает, YAML 1.2.2 тоже. Решение «Архитектора» и правка Н1.1 названы только по списку. Их нужно записать на обе формы: «одна висячая запятая в потоковом списке и отображении допустима». Иначе Н1.1 молчит о форме, которую принимает норма-стек.
2. **Иных висячих форм решение не открывает.** `[a,,b]`, `[,a]`, `[a, , ]`, `{,}`, `{a: 1,, }` — ошибки YAML 1.2.2, оба парсера отказывают одинаково (`text`). Тонкое правило не нужно, тут согласен.
   - В Н1.1 стр. 61 фраза «пустой элемент потока (`[a,,b]`, `[a,]`)» объединяет обе формы. Правка должна её разделить, а не снять целиком: `[a,,b]` остаётся отказом `text`, уже как ошибка разбора YAML.
   - Пара в потоковом списке с висячей запятой (`[b: 1, ]`) ведёт себя как без неё: форма отказывает там, где нужна строка (`c2_flow_seq_pair`).
   - `{k: , }` по-прежнему отказ п. 4.
   - Многострочный поток — по-прежнему тонкое правило.
3. **Корпус.** Ни один из 680 случаев корпуса P/02.1 (после пакета) не содержит запятую перед `]` или `}`. Отказ `[a,]` диалекта корпусом не держался. Предлагаю случаи:
   - `[x, ]` — ok;
   - `{b: 1, }` — ok;
   - `[x,,y]` — refused `text`;
   - `[, x]` — refused `text`;
   - `{b: 1,, }` — refused `text`.

   Для принятых — векторы `canonical`: вид тот же, что без запятой.
4. **Диагностика.** У ошибок разбора Go даёт строку 0, Python — 1. Это подсказка по п. 7.2, на вердикт не влияет.
