# Ревью ADR-0125 — Codex

Основа: `origin/main` **d829cdaef**. Проверены основной текст ADR-0125, ADR-0120 с дополнениями, ADR-0083 доп. (86), исходники генератора, его сверки и сборщика пакета в `tools/normgen`, формы и нормы P/01. Итог: **Б 0, С 4, М 0**.

Это ревью решения и его исполнимости, а не приёмка ещё не написанных генераторов. Код реализаций и серверные прогоны не запускались. Утверждение о 12 000 входов повторно не проверялось.

## С1. Для новых генераторов не задана проверка исполняемого результата независимым судьёй

**Место:** Decision Drivers; Decision Outcome п. 1, графа «Сверка» строк 2–6; п. 4.

**Цитата нормы:** «Код выходит из формы механически и сверяется с независимым эталоном»; для флагов — «против таблицы прозы (`check_spec`): закрытый набор, умолчания, код 2»; для тестов — «тесты сами сверяются с векторами».

Проверить согласованность двух источников недостаточно, чтобы проверить скомпилированный код. Например, машинная таблица и проза совпадают, `check_spec` проходит, но генератор флагов теряет проверку неизвестного флага или выдаёт неверное умолчание. Для каталога отказов совпадение слов тоже не доказывает правильность полей и их присутствия. Замер числа проверок **P/01.1** не закрывает флаги демона из **P/01.3**.

У генератора тестов отдельный риск: потеря отрицательных векторов или неверное сравнение ожидаемого результата может оставить зелёный прогон. Фраза «тесты сами сверяются с векторами» не определяет внешнего наблюдателя, который обнаружит эту ошибку. Последующая сверка двери этими же тестами даст зависимые подтверждения. Оговорка «не замена приёмки» полезна, но проверку самого генератора тестов не задаёт.

Для генератора № 1 способ уже конкретен: `test_gen_checks.py` исполняет полученные Go/Python проверки и сравнивает их с CEL-эталоном `check_tables`, включая синтетические выражения и случайные входы. Это положительный пример, а не замечание к его независимости. Для остальных строк сопоставимого договора нет.

**Предложение:** для каждого генератора назвать исполняемый артефакт, отдельный источник ожидаемых результатов и условие допуска в пакет Б. Для флагов — запуск полученного парсера на допустимых и ошибочных аргументах с проверкой значений и exit code; для отказов — точные тела/статусы и обязательные поля; для семей — вызов полученного читателя на векторах. Для тестов — учёт всех входных случаев и мутации реализации, которые они обязаны отвергнуть. Проверку формы через `check_spec` оставить отдельным условием. Приёмочные ожидания не строить тем же генератором, который проверяется.

## С2. «Модели остаётся ядро Н3» не согласовано с исключённой из генерации рамкой HTTP

**Место:** Context, второй абзац; Decision Outcome п. 1 строка 2, п. 3 первая очередь, п. 5; Consequences, «Предел».

**Цитата нормы:** «Сначала 2 и 6 — формы готовы»; «Модели остаётся ядро Н3»; одновременно «рамка HTTP формы не имеет и генерации не подлежит».

Кто предоставляет эту часть в следующих попытках, не определено. Пакет Б по ADR-0083 (86) содержит строгий JSON-разборщик и проверки команды, но не всю HTTP-дверь. Это явно отражено в `kit/go/writecheck/writecheck.go`: `Check` принимает тело, у которого «рамка HTTP и предел тела уже пройдены», и требует внешнюю функцию проверки прав.

OpenAPI тоже оставляет исполняемые требования описаниями: у `/v1/list` `prefix` имеет `type: string`, а допустимость произвольных байтов задана `description`; у `Listing` прямо сказано, что JSON Schema не проверяет порядок имён. Коды и формы отказов не определяют очередность проверок и ранний отказ HTTP. Генерация типов и маршрутов сама по себе эти обязанности не исполняет. При нынешнем тексте либо модель продолжает писать часть Н2, либо пакет получает неучтённую ручную реализацию двери.

**Предложение:** назвать результат генератора № 2 точно: маршрутизация, типы, сериализация и точки вызова ручных примитивов. Перечислить не генерируемую часть двери и назначить её модели либо ручной части пакета Б. Для второго варианта задать API, отдельную сверку и учёт строк по ADR-0120 (5) п. 2 (а), ADR-0083 (86) п. 3. Обещание «только Н3» применять после покрытия этих обязанностей, а не сразу после появления генератора OpenAPI.

## С3. Табличная запись исходов семей пока не является формой для генерации поведения

**Место:** Decision Drivers; Decision Outcome п. 1 строка 5.

**Цитата нормы:** «Генератор не толкует прозу: где формы нет, генерации нет»; источник генератора семей — «`configstore-doors`, `epoch_floor` (`schema.json`, `layers.tsv`, `outcomes.tsv`)».

Не определено, что именно генерируется из каждого слоя. В `epoch_floor.outcomes.tsv` поле `outcome` — предложение, а не код действия. Для `/floor` одна строка содержит разные действия: «epoch issue: the issue is refused ...; lease confirmation: fenced; import, restore: the whole input is refused, nothing changes». При этом `reader` равен `*`. Строка `/generation_at` также различает чтение поля разными операциями словами. Генератор не может механически получить эти ветви из закрытого набора значений: его пока нет.

Сгенерировать валидатор формы записи можно без реализации всех этих исходов. Но тогда поведение при нечитаемости, включая отказ всего импорта до изменений, остаётся за вызывающим кодом. Нынешняя строка не позволяет ни определить объём генератора, ни выбрать, что должны доказать векторы его сверки.

**Предложение:** ограничить первый генератор семей проверкой структуры/слоёв и типизированным результатом нечитаемости, а действия читателя оставить явно названным ручным обработчикам. Либо сначала ввести формальные идентификаторы операций, исходов и область атомарного отказа с закрытой семантикой. До этого `outcomes.tsv` считать источником документации и требований к обработчикам, а не исполняемых действий; запретить молчаливое игнорирование неподдерживаемого слоя/исхода.

## С4. Для временных копий таблиц не установлен источник, решающий расхождение

**Место:** Decision Outcome п. 2 и п. 4 последний пункт; Consequences.

**Цитата нормы:** «машинная копия»; «`check_spec` сверяет их с таблицами прозы, пока проза их повторяет»; «Каждое такое место — неясность нормы, вопрос “Спецификации”».

ADR-0120 п. 2 (а) устанавливает другую конструкцию для проверок записи: «Норма ссылается на таблицу, а не повторяет её прозой». Здесь две таблицы временно разрешены, но не сказано, какая из них источник и блокирует ли их расхождение выпуск кода/пакета. Вопрос «Спецификации» не задаёт этого барьера. Например, при изменённом умолчании `-max-body` генерация из машинной копии и ручное ядро/описание из прозы могут получить разные пределы на одном пине.

Сверка также нуждается в определённой проекции: таблицы Н4 содержат переводимые пояснения и условия, таблица флагов — сочетания флагов и процедурные ссылки. Сравнение только набора флагов, кодов и умолчаний не обнаружит потери условия вроде несовместимости `-bootstrap` с `-join`; буквальное сравнение всей прозы не превращает его в формальное условие.

**Предложение:** объявить `forms/*.tsv` единственным источником формализованных полей, в прозе оставить ссылку или производный блок. Для перехода перечислить сравниваемые поля и отдельно оставшиеся прозаические ограничения с их исполнителем. Любое расхождение нормативных значений должно блокировать выпуск генерации/пакета до решения «Спецификации». Сохранить общий пин форм и ручной части в паспорте.

## Пакет Б и линии

Разрешение использования кода в MiniMax опирается на ADR-0083 (86); отдельное решение владельца для варианта Б линий Codex в п. 5 сохранено. Требования паспорта и раздельного учёта происхождения кода уже есть в ADR-0120 (5) и ADR-0083 (86); повторно отсутствие их полного текста в ADR-0125 находкой не считаю. Отложенное ревью генераторов соответствует названной паузе. Настоящее ревью не снимает её и не разрешает другие прогоны.
