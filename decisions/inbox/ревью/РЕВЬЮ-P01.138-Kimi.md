## 1. Срочный раздел: ворота D1–D4 (P01.125)

Фактические формулировки ворот (найдены в коде, не предполагались):

- **env (D1)** — `judge_line.py:2041–2067` (`check_env`): цель с instance красная, если запись «env» какого-либо старта экземпляра несёт `missing`/`wrong`; список переменных механически выводится из предложения README «The stand translates the substitutions into the environment» (`stand_env`, `judge_line.py:583–600`, якорь `:290`). Заглушка сама проверяет своё окружение (`judge_stub.py:772–791`, запись `:840–842`): отсутствие/пустота — missing; равенство значению подстановки — только для `NAME={subst}` без плейсхолдеров `<…>`; переменная, чья подстановка команде не дана, пропускается (`:780–781`).
- **answers (D2–D4)** — `judge_line.py:2070–2132` (`check_answers`): заглушка отвечает шаг двери «по ожиданию», если ожидание разбирается формами словаря (`parse_expect`, `judge_stub.py:620–644`: литерал, `$name`, `!contains`, `@any`, `@absent`, `@time`, `@not(…)`, `~text`; синтез ответа `_synth`, `:686–727`; отбор шагов `stub_plan`, `judge_line.py:1148–1155`); пока все ранние шаги сценария — такие и GREEN, такой шаг обязан быть GREEN; отдельно — `ASSERT` со `!=` over именами, которые связала заглушка (значения различны), — обязан быть GREEN. Недошедший запрос в `notg` не попадает (`how≠expected` молча обрывает счёт сценария).
- **directives (D2)** — `judge_line.py:1819–1839`: директива без HTTP (ASSERT) исполнена — результат `GREEN`/`red`, но не `not_executed` вне прерванного сценария.
- **steps (дополнение к D4)** — `judge_line.py:1427–1490`: шаг, отчитанный как исполненный, чей запрос к двери не дошёл до заглушки в порядке очереди, красит цель («reported as executed, but its … request to a door did not reach the stub»).

Контроль (`control-oldJ/gate-lines.txt`, 19:51Z): `env: 0 of 6` — все шесть целей с instance, у каждой «started without BOX_ID, PLATFORM_DIR, PLATFORM_STORE, SECRETS_KEY, SERVER_NAME»; `answers: 2 of 5` — у door «5 steps answered … are not GREEN: 15-too-large:73, 18-no-echo:86, 21-rights:108, 22-body-edge:110, 39-batch-weight:339» плюс ровно 5 ASSERT (те же 5 у inproc) и «1 steps … 18-no-echo:86» у inproc; `directives` флагают те же 10 ASSERT. Прогон `control/` (новый J `f11bf34d`): движок падает на `targets.routing.tsv:9: unexpected header` — новый J обратно несовместим, доказательная сила по D1–D4 — только у `control-oldJ`.

**D1 — ПОДТВЕРЖДАЮ.** Правило ловит класс: 281 случай у движка d9066b16 — прямое следствие `limitedEnvironment` (в окружении старта нет ни одной переменной стенда; в `control-oldJ` те же 6 целей красные по env). Не наказывает верный движок по построению: проверяется собственное окружение процесса заглушки; буквальные `srv-a`/`stand-box` не требуются (bare-переменные — только наличие), значение сверяется лишь там, где норма его фиксирует подстановкой (`SECRETS_KEY={data}/etc/secrets/platform.key`, README J:131), а `PLATFORM_STORE=configstore://<role socket>` с плейсхолдером — только присутствие. Список переменных совпадает с README J:129–131 + 203.

**D2 — ПОДТВЕРЖДАЮ.** Ловит: `answers` флагает ровно 10 шагов класса (5 door + 5 inproc), `directives` — те же. Не наказывает верный движок: заглушка связывает значения `b1, b2, …` — попарно различны, нормально исполненный `ASSERT $a != $b $c` даёт GREEN; проверка включается только когда все имена связаны заглушкой и предыдущие шаги чисты (консервативно, ложных срабатываний от этой конструкции нет). Предел: движок, исполняющий ASSERT «всегда GREEN» без сравнения, воротом не отличается — механический предел любых ворот, не находка.

**D3 — ПОДТВЕРЖДАЮ.** Ловит: `18-no-echo:86` (`!contains` в значении поля JSON) флагается у door и inproc; форма `$name` покрыта тем же механизмом — в контрольном прогоне заглушка ответила `21-rights:107` «по ожиданию» со связью `v`, движок дал GREEN (а соседний `21-rights:108` с литеральным `size` — пойман, счёт сценария до 107 вёлся). Не наказывает верный движок: ответ заглушки построен по форме ожидания (для `!contains` — символ вне подстроки, для `$name` — связанное/новое значение `bN`), нормально сравнивающий движок даёт GREEN на обеих ветвях. Включённые формы — все формы значений словаря, которые заглушка умеет отвечать (`parse_expect`), включать дополнительно нечего.

**D4 — ПОДТВЕРЖДАЮ.** Два режима отказа покрыты вместе: (1) запрос дошёл, ответ не засчитан — `answers` флагает `22-body-edge:110` (в контроле заглушка ответила 413 по ожиданию, движок дал red — строка есть в `gate-lines.txt`); (2) запрос не дошёл (режим d9066b16 `red stand transport`) — ловит `steps` («reported as executed, but its POST request to a door did not reach the stub»). Не наказывает верный движок: транспорт адаптера в заглушке — строки stdin без потолка (`judge_stub.py:530–532`), отказ 413 — обычный ответ (PROFILE.md J:106), корректный движок доставляет 4 МиБ и получает GREEN (у inproc в контроле `22-body-edge:110` GREEN). Норма по вопросу 1 представителя: потолка кадра протокол не допускает — исход «норма» для D4 отпадает, класс — «движок».

Находка по воротам — М1 (см. раздел 3): режим «запрос не дошёл» в `answers` без диагностики (компенсируется `steps`, но строки ворот нет).

## 2. Классы D1–D6 и LOGMASK

### D1 — стенд без окружения (281 + 78) — исход: **движок**

Норма (сверено с J): README J:129–131 («The stand translates the substitutions into the environment of P/02.4 N1.2: `PLATFORM_DIR={data}`, `PLATFORM_STORE=configstore://<role socket>`, `CONSOLE_PORT={port}`, `RESOURCE_PORT={rport}`, `BOX_ID`, `SERVER_NAME`, `SECRETS_KEY={data}/etc/secrets/platform.key`»), J:203 («Every process, platform | `PLATFORM_DIR`, `PLATFORM_STORE`, `BOX_ID`, `SERVER_NAME`, …»), J:519 (группа: «with the environment `BOX_ID=<id>`, `SERVER_NAME=<id>`, `PLATFORM_DIR={data}/<id>`»), J:115 (`SERVER_NAME` (`srv-a` on a single-server stand)). Цитаты представителя точны. Проба запуска кандидата (`probe-start.sh`, тот же бинарник): без `SERVER_NAME`/`PLATFORM_DIR` старт отказан (`member id or SERVER_NAME is required`), с ними — сокеты открыты; поведенчески подтверждено и воротами (раздел 1).

Механическое правило (уже ворота env): процесс экземпляра заглушки фиксирует своё окружение; цель красная при любом `missing`/`wrong` против списка из предложения README.

Причина: **модель** (норма однозначна, движок не выставляет окружение — в `run_stand.go` окружение урезано, класс пакета D1, коду движка недоступен, но ворота это показывают поведенчески); вторая — **цикл** (заглушки P01.107/P01.114 окружение не требовали; gate env в P01.125 закрывает).

Ответы представителю: 1) да, J:128–131 + 203 достаточно — предложение общее для стенда, не только «composite stand» (ограничения «In a composite stand…» в J:132 касаются только `-dir {data}/configstore`, не окружения); 2) буквальные `srv-a`/`stand-box` обязательны для эталонного стенда курса, для стенда судьи — любые непустые (кандидату нужно наличие, ворота проверяют только наличие); 3) да, ловит и не наказывает (раздел 1).

### D2 — `ASSERT $a != $b $c` (10) — исход: **движок**

Норма: README J:255 («`ASSERT $a != $b [$c …]` | the named values are pairwise distinct; no HTTP is sent») — «the named values» включает `$a`; J:256 (форма сравнения), J:309 (`$name` binds/compares). Цитаты точны.

Механическое правило (ворота answers+directives, раздел 1): ASSERT вне прерванного сценария не бывает `not_executed`; над связанными заглушкой различными значениями — GREEN.

Причина: **модель** (ветка кода сравнивает только `fields[2:]`, класс пакета D1 по коду движка; недоступен для сверки, но ворота воспроизводят симптом на сохранённых прогонах); вторая — **цикл** (ворота P01.107 принимали `not_executed` с закрытой причиной).

Ответы: 1) да, `$a` входит («the named values» — все именованные); 2) исход ASSERT при несвязанном имени норма не называет — пробел (находка С2); ворота его обходят (проверка только при полностью связанных именах); 3) правило подходит, демонстрировано контролем.

### D3 — формы ожидания `!contains` и `$name` (4) — исход: **движок**

Норма: README J:315 («`!contains text` | a string value does not contain the substring») — форма значения поля; формы тела — отдельные строки J:316–317 (`<code> ~text`, `<code> !contains text`); J:309 (`$name`: «the first occurrence binds, the following ones compare»); J:308 (P/01.1 — JSON whole). Цитаты точны. Ответ на вопрос 1: подтверждаю — 315 относится к значению строкового поля внутри JSON-ожидания; раннер прав.

Механическое правило (ворота answers): шаг, чьё ожидание заглушка может воспроизвести формой, при чистых предшественниках — GREEN; иначе красный.

Причина: **модель** (значения полей форм сравниваются буквально, класс пакета по коду движка); вторая — **цикл** (ворота compare по доп. (9) — только буквальные `expect`).

Ответы: 2) формы уже включены все (`parse_expect`); см. раздел 1.

### D4 — `@big(4194304)` через адаптер двери (1) — исход: **движок**

Норма: README J:250 («`@big(N)` | a substitution in any part of the request: a string of N bytes `x`…»); PROFILE.md J:94–106 («Store door»: «The transport adds no per-request timeout or line-size ceiling», «An operation refusal is a normal response, not an adapter exit or an outer error frame»); урок P/01.1 README J:44–48 (предел тела 1048576 проверяется поведением) и J:118–119 (ранний отказ `413 toolarge`). Цитаты представителя точны (в пакете строка 250 указана как 250 — верно; у меня в разделе сверки встречается 249 только как следствие иной нумерации вывода, фактический номер по `grep -n` — 250).

Ответ на вопрос 1: протокол адаптера потолка кадра не допускает — исход «норма» отпадает; `stand transport` на 4 МиБ — отказ движка, не норма.

Механическое правило (ворота answers+steps, раздел 1): тело `@big(N)` при N больше предела доставляется к заглушке целиком и ответ по ожиданию засчитывается; недоставленный запрос исполненного шага — красный.

Причина: **модель**; вторая — **цикл** (заглушка не гоняла `@big` через адаптер).

### D5 — пробы extra (3 у раннера + 15 у движка) — исход: **норма** (главное) **+ движок** (причина)

Норма (сверено с J): `forms/extra.tsv` — «The README is the source of each probe; this table lists them and adds no expectation»; колонки `probe`/`expect` — проза со ссылками на разделы README урока (в J `Platform/01-store/acceptance/1/README.md` присутствует, разделы «The instance of the chapter» и «Request parsing» содержат точные числа, но машинной формы запроса/ожидания в табличном виде нет). README J:190: подпрогон сценариев «does not carry the chapter-wide probes… its result names the subset, and a target is green only by its full run». P/AC-R030 (norms J:59–61): закрытый список причин `not_executed` — `installer_ceiling_unproven`, `installer_rights_check_missing`, `store_rights_template`, `store_spoil_row_missing`, `stage_package_not_exported`, причины N6.5, имена отсутствующих интерфейсов/ключей, причина оборванного сценария; слова «проба описана без машинной формы» в списке нет. `fault` — слово привязок D7 (таблица у norms J:291: «a required D7 binding is absent | `not_executed`, the reason is `clock`, `storage`, `progress` or `fault`»), к пробам extra не относится. P/AC-R002 (norms J:13–15): «A step of a lesson that the dictionary does not express is a gap of the specification, not a reason for lesson-specific code». Цитаты представителя точны.

Вывод: пробы extra не выражены словарём/таблицей — по R002 это «gap of the specification»; исполнить их механически, не вводя lesson-specific код, нельзя — главный исход **норма**. Одновременно норма противоречит себя: README:190 вменяет полному прогону chapter-wide probes, a R002 запрещает для них lesson-specific код; и R030 не даёт закрытой причины для честной отметки. Не хватает фраз (находка Б1): в R030 — причины вида «the probe is described without a machine form» (например `no_machine_form`) и в README к extra.tsv — фразы, что цель-опись без машинной формы судится перечислением всех строк с этой причиной и что машинная форма проб — долг спецификации. Вторичный исход **движок**: причина `fault` вне её нормативного места (D7) — слово вне закрытого списка R030; движок должен был использовать (после правки нормы) закрытое слово, а не `fault`.

Причина по схеме: **спека** (главная), как и предполагала догадка №5 представителя.

Ответы: 1) закрытого слова нет — пробел нормы (Б1); 2) README:190 вменяет ношение проб полным прогоном, но исполнение прозы требует lesson-specific кода (запрещён R002) — противоречие; до правки нормы честный максимум движка — перечень всех 15 строк с закрытой причиной (после её введения); цель всё равно не GREEN по R031 («Every `not_executed` row or scenario of a target takes GREEN from it», norms J:65) — что согласуется с калибровкой (оба судьи «не GREEN» по существу, цвет совпадает); 3) 3 своих группы проб раннер исполняет собственным кодом — это знание урока в судье, прямо запрещённое P/AC-R002; раннер выведен (ADR-0135 доп. (8), (10)) — записывается как предел раннера, правки не будет.

### D6 — шаг после красного шага (1) — исход: **кандидат** (гипотеза; доказательство закрыто пробелом нормы)

Норма: norms J:135 — «A failed step ends its scenario only when it is a directive of preparation… The other steps go on and are judged.» — оба судьи сценарий после красного шага 3 (`40-batch-rights:343`) продолжили правильно; цитата представителя точна. Сценарий (J, scenarios.tsv:341–349): шаги 1–6 — batch-записи, каждый трогает `other/40-batch-rights/x` и ждёт `403`; шаг 7 — `GET acc/40-batch-rights/a` ждёт `{"items":null}`; шаг 8 — запись в `acc/` ждёт 200; шаг 9 — `GET list?prefix=other/40-batch-rights/` ждёт `{"keys":{}}`. Ничто в сценарии `other/` не пишет законно.

Наблюдения, доступные мне: `summary.json` второй точки — группа `both_not_green|red|implementation|red` (14 случаев, inproc) включает `40-batch-rights` 342, 343 и **347**; то есть шаг 7 (ожидание `items:null` при отсутствующем ключе) красный у обоих судей — кандидат оставил запись `acc/40-batch-rights/a`, несмотря на отказ 403: частичное применение запрещённых batch-записей подтверждено обоими судьями. Расхождение только в шаге 9: у раннера под `other/` есть ключи (тело 187 Б), у движка — нет (GREEN). При согласованных шагах 1–8 (один TSV, одни бинарники, изолированный экземпляр на сценарий по README урока) различие состояния к шагу 9 — это какие именно запрещённые записи просочились в каждом прогоне; раз у обоих судей шаги 1–7 красные по существу, а набор просочившегося различается между прогонами, наиболее экономное объяснение — недетерминированное частичное применение запрещённых batch-записей кандидатом; оба судьи свои наблюдения засудили согласованно (раннер red по факту ключей, движок GREEN по факту их отсутствия).

Механическое правило: для класса «кандидат» правило ворот не строится; фиксируется запись предела (как у класса «раннер») — здесь: запись о недетерминизме кандидата для суда над продуктом.

Причина: **модель** (недетерминизм поведения кандидата, ADR-0133 доп. (42)).

Оговорка и находка С1: вывод — гипотеза; тела ответов движок не пишет, тела раннера лежат в `/srv` (нет доступа), поэтому вариант «один из судей иначе исполнил шаги 4–8» по доступным данным не снят. Ответ на вопрос 2: норма об отчёте есть — N1.5 (norms J:79–87): отчёт «does not give out response bodies…: it gives at most the length, the digest and the content type of such a value» — дайджест разрешён, но не обязан; не хватает фразы, обязывающей красный шаг нести длину и дайджест фактического ответа. Ответ на вопрос 1: установить по доступным мне сырым выходам нельзя (см. ограничение доступа); раннер несёт sha256 тел (`99542851…`, `d20e317e…` по пакету), движок — ничего.

### LOGMASK — 11 строк log-mask, красных у обоих — исход: **кандидат**

Норма (сверено): шапка `cases.tsv` J:1–6 («The norm — M10/7 N1.4 `log` with N1.1a (pairs, addresses)»); контракты курса (в J-вход P/01 не входят, цепочка норм по срезу): `contracts/log-mask.md` — header: Basic/Bearer маскируется, «another scheme (Digest) stays as it is», credential «run to the first white-space character», «space» = white_space из `contracts/person-name.md` «White space» (U+0009–U+000D, U+00A0, U+3000…, person-name.md:26–28); pairs — `contracts/url-credentials.md`: `common_words` (строка 30) включает `password` и не включает `user`; A5/A6 (строки 139–155): имя из common_words — секрет, логин показывается как написан; в `vectors/secret-in/fields.yaml` поле `cam.source` объявляет `user` логином (`param/login: [user, …]`) — для векторов каталог подаётся входом (log-mask.md:23–28). Цитаты строк 29, 32, 53 из пакета совпали с `cases.tsv` буквально.

Ответы представителю: 1) да, однозначно: строка 29 (RTSP-адрес, `user=admin&password=hunter2xyz`) — `password` есть в common_words → маскируется; `user` — логин по fields.yaml → «shown as written»; `&` — разделитель пар, не трогается; кандидат, замаскировавший и `user`, маскирует лишнее («masking too much is safe» — относится к прилипшим символам credential заголовка, не к логинам пар: логин показывается, log-mask.md:57–58 и A6). Строка 53 (`Authorization: Bearer abc<U+00A0>x`) — credential кончается первым white-space (U+00A0 ∈ white_space), хвост `<U+00A0>x` сохраняется; кандидат, потерявший хвост, неверен. 2) среди 11 строк (20, 29, 31, 32, 33, 43, 53–57) спорных ожиданий не нашёл: каждая имеет точный якорь (A7/A9 для 20 и 43; Digest для 31; userinfo A10 для 32; JSON-скаляр для 33; white_space для 53–57). Исход «кандидат» (модель по ADR-0133 доп. (42)) подтверждаю; судьи сравнивают верно и согласны — правил для судей не нужно.

Замечание М2: описания строк у самого представителя расходятся между RESULT-P01.110.md и LOGMASK.md (строки 29, 31, 32, 33: «Digest-ответ», «JSON-скаляр», «имя &pwd») — по байтам `cases.tsv` верен LOGMASK.md.
