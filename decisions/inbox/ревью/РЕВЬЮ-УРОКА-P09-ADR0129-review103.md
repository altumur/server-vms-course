## Находки источника

### С1 / P09-S01. OpenAPI relay не содержит шесть GET-пересылок из собственной нормы

**Место:** `Platform/09-agent/spec/09.2-agent.norms.md:122`, `:133`; `Platform/09-agent/spec/09-agent.api.openapi.yaml:5`, `:39`. Требование `P/09.2-R007`.

В N2 перечислены GET `/api/members/{member}/{part}`, `/api/anywhere/{member}`, `/api/topology/{member}`, `/api/backup-part/{member}/{part}`, `/api/book/{member}/{sub}/{book}` и `/api/book/{member}/{sub}/{book}/{part}`. Это входы relay, со своей проверкой подписи/членства, памятью rows и отказом 502 при недоступности держателя. Но контракт заявляет четыре операции и не содержит ни одной из этих шести. Наличие тех же адресов у держателя P08 задаёт исходную форму, но не объявляет их обслуживание relay.

**Минимальный контрпример:** реализация/клиент, ограниченные перечисленными операциями P09, не имеют входа GET topology через relay, хотя N2 требует его. Собственное структурное чтение всех paths: шесть отсутствуют в P09 и шесть присутствуют у держателя; четыре нынешние операции P09 найдены как положительный контроль. Это расхождение источников, не наблюдение HTTP 404 у реализации.

**Предложение:** перечислить эти шесть relay-привязок с формами по существующим ссылкам P08 и собственными условиями relay; не копировать формы и не создавать новые двери. Доказательство — E/`probe-source-forms.json`, раздел `forwarded_routes`.

### С2 / P09-S02. Форма RelayRefusal допускает отсутствие обязательных detail и контекстного reason

**Место:** `Platform/09-agent/spec/09-agent.api.openapi.yaml:160`, `:172`, `:279`; `Platform/09-agent/spec/09.2-agent.norms.md:136`; `Platform/09-agent/forms/refusals.tsv:17`, `:20`, `:27`. Требования `P/09.2-R007`, `P/09.2-R009`.

Норма задаёт `{error: "refused", detail, reason?, send_row?}`; причина обязательна в соответствующем исходе accept. Форма отказов отдельно требует `error,detail,reason` для 409 rebase, а для первого 503 — `error,detail`. Общая схема имеет только `required: [error]`. POST member использует её и для 409, и для 503.

**Минимальные контрпримеры:** стандартная JSON Schema принимает `503 {"error":"refused"}` и `409 {"error":"refused","detail":"send whole"}`. Первый теряет заданное описание отсутствия ответа, второй — машинное слово rebase, от которого зависит действие вызывающего. Корректные 503 с detail, 409 с reason=rebase и 413 без reason проходят. Лишнее поле, bool вместо reason/detail и отсутствие error отвергаются. Для GET carry отдельный RelayNothingBody уже отвергает отсутствие detail.

**Предложение:** сделать detail обязательным; контекстные обязательность/слова reason выразить для соответствующих ответов, сохранив законное отсутствие reason у 413 по размеру тела, 403 и 405. Не делать reason обязательным для всех отказов. Это собственная форма P09, не повтор входящих замечаний к ответам P08. Доказательство — E/`probe-source-forms.json`, `relay_post_refusals`; работа HTTP-обработчика не проверялась.
