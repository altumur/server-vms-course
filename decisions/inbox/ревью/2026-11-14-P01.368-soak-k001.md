## Независимая проверка

Минимальный свидетель с явным источником A состоит из четырёх выделенных операций.
Вся история ключа содержит **ровно одну запись A — 92414**, с одной HTTP-попыткой.
Её ответ задержан до 589.464437, однако чтение 92421 уже увидело A к 580.070328.
Поэтому линейная последовательность обязана удовлетворять:

```text
put A (92414) → read A (92421) → put B (92445) → read A (92447)
```

Первая стрелка следует из единственного источника прочитанного A. Две следующие — из
неперекрывающихся интервалов; последние put и read принадлежат одному последовательному клиенту c5.
После B вернуть A нельзя: ни одна другая запись во всей истории не пишет A.
В частности, неизвестный CAS 92430 пишет `lc82.c2.11550`, а не A; его применение или отсутствие
эффекта не меняет противоречия. Другие put/delete также могут только удалить A из состояния.
Поэтому включение остальных операций не спасает свидетель.

[verify.py](2026-11-14-P01.368-soak-k001/verify.py) перебрал все **24** порядка четырёх операций.
Только **4** сохраняют порядок неперекрывающихся интервалов; **0** отвечают модели регистра.
Контроли с удалением каждого из трёх наблюдений/перезаписи после источника A допускают исполнение.
Замена последнего ответа на B также допускает исполнение.

Отдельный поиск проверил все **13** операций окна от подтверждённого состояния 92397.

## Атрибуция и место в коде

**Наблюдаемый дефект — устаревшее чтение при возврате прежнего лидера.** Потеря подтверждённой
записи, двойная запись, нарушение порядка CAS или дисковое восстановление для этого вывода
не требуются. Их наличие за пределами свидетеля этим разбором не устанавливается.

Прибор не объясняет нарушение:

- `load.go`: значение формируется из run/client/seq; у четырёх операций по одной попытке,
  итоги `ok`, HTTP 200. Отложенный ответ 92414 не принят за отложенный эффект после первого чтения A.
- `stand/http.go`: каждый запрос использует новое Unix-соединение, тело ответа принадлежит этому
  обмену. Чтение берёт `items.v` и `index` из собственного JSON-ответа, не из клиентского кэша.
- `Runner.now()` использует `time.Since(r.start).Nanoseconds()` в одном процессе.
  Порядок не зависит от часов кандидата и их синхронизации; порядок 92445 → 92447 дополнительно
  задан последовательным клиентом c5.
- В свидетеле нет CAS и неизвестного исхода. Возможные общие ограничения модели CAS и отсечения
  `info` в исходном checker не могут создать этот контрпример. Поиск окна независимо оставляет info.
- Пауза лидера — зарегистрированный сбой прибора; для доказательства не требуется авария вне модели.
  Отдельного события потери хоста, повреждения файлов или перевода часов в этом окне нет.

Путь чтения снимка 8.2:

1. `01-store/internal/group/backend.go:216`: `Node.Read` вызывает `fence`, затем читает локальную
   FSM (машину применённого состояния) через `fsm.With`.
2. `backend.go:149`: `fence` получает границу через `leaderIndex`, ждёт `AppliedIndex` и
   `WaitApplied(fsmTarget(idx))`. Ожидание уже применённой старой границы не доказывает её актуальность.
3. `backend.go:187–198`: локальная ветвь `leaderIndex` сохраняет `CommitIndex()` **до**
   `VerifyLeader().Error()` и возвращает сохранённый индекс. Она не связывает эту границу с проверенным
   term и не проверяет актуальность заново при выходе. `ready()` в `node.go:207` сравнивает только
   локальные state/term с `readyTerm`.
4. `01-store/internal/group/frames.go:108–117`: `readFence` для другого участника использует тот же
   порядок `CommitIndex` → `VerifyLeader` → ответ со старым сохранённым индексом.

Подтверждённая локализация — путь подтверждения чтения и последующий локальный снимок.
В нём есть окно между сохранением границы, подтверждением лидерства и чтением состояния.
В используемой зависимости `hashicorp/raft v1.7.3` подтверждение будущих `VerifyLeader` получает
ответы через `followerReplication.notifyAll` (`replication.go:98`, `raft.go:965`); время отправки
конкретного RPC не записано в данном прогоне. Поэтому нельзя доказать, какой внутренний порядок
сработал у 92447: задержанный ответ прежнего term или переход между проверками. Также нельзя
объявить перестановку двух вызовов достаточным исправлением. Для исправления нужно обеспечить
само свойство R062 на всём пути, включая ответ на запрос к другому участнику.

## Находка для круга 8.3 — только обязательство M

**Б, кандидат. P/01.1-R062, подтверждение чтения после паузы лидера.**
После успешного put B клиент выполняет get того же ключа и получает более ранние A/39481,
хотя B уже подтверждено версией 39488. Другой get наблюдал A ещё до put B; повторной записи A нет.
Read 92447 через возвращающийся s1 в `[581150721898; 589464323664]` не имеет допустимой точки
линеаризации. M требует чтения не старше последней завершённой записи через лидера текущего term;
без подтверждения в срок требуется существующий `no_leader_wait`.
Место: `group.Node.Read` → `fence` → `leaderIndex` в `backend.go`, парный `readFence` в `frames.go`.
Исправление должно сохранять это свойство при смене лидера и задержанных сообщениях; допустимый
отказ остаётся существующим отказом M. Норма R062 сверена с точным источником M8″ и совпадает
с R062 рабочего дерева. Ответы суда и процедуры испытания не являются частью этой формулировки.
