## Б1. Граница закрыта у файловых инструментов, но не у исполняемого кода модели

**Место:** `loop.py:95–117`, `judged`/`judges`; `cammeta-machines/server/minimax/minimax-judge`, bind-mount всего `cammeta-acceptance`, checkout specs и work с последующим `setpriv`.

**Норма:** (61) п. 1 — «Граница — у исполняемого кода, не у инструментов», код кандидата читает только work, выгрузку на пине и правила. (81) п. 3: «README раннера целиком модели не даётся»; пп. 4, 5: `.git` work и выгрузки модели закрыты.

`Roots.deny` действительно запрещает прямые обращения к корневой `.git` через `read_file`, `list_dir`, `grep`. Но Go-тест/программа не пользуется `Roots`: её выполняет `minimax-judge`, внутри чьего вида ФС читаем весь раннер, а теперь и git-копия выгрузки. Достаточно `os.ReadFile` в собственном Go-тесте; его содержимое можно вернуть через ошибку/вывод судьи. Чистка путей не распознаёт произвольный текст судьи, историю git или их кодированное представление.

**Подтверждение CT 102 — сообщение «Машин» в этой сессии.** От пользователя minimax вызвана фактическая `sudo -n /usr/local/sbin/minimax-judge` на отдельном `runs/probe-b1`, cwd — его work. Три `test -r` дали по порядку **OK OK OK**, код 0:

1. `/srv/minimax-loop/cammeta-acceptance/README.md`;
2. `/srv/minimax-loop/cammeta-acceptance/runner/all.py`;
3. `/srv/minimax-loop/specs-8d67ccd/.git/HEAD`.

Проверялись права чтения, содержимое не читалось, ключ не трогался; probe-b1 убран, девятая и приёмка не затронуты. Это подтверждение доступности запрещённых файлов, **не свидетельство фактической отправки их содержимого в API девятой попыткой**.

**Что старое, что новое.** Весь `cammeta-acceptance` монтировался судье уже в попытках 1–7: этот путь к README и коду раннера не внесён diff db81977..df07bd1. Новое в (81) — `.git` выгрузки и создаваемая судьёй `.git` work. Обёртка монтирует work целиком с правами rw для того же пользователя: Python-запрет не защищает и эту метаинформацию от Go-кода. Это один дефект границы исполнения, а не отдельный Б за каждый читаемый файл.

### Предложение и цена разделения

**Сборка, vet, свои тесты, run.** Отдельный профиль исполнения кандидата: только его work **без `.git`**, опубликованные файлы пина **без `.git`**, правила и инструментальная цепочка; раннер и acc туда не монтировать. Одного RO для `.git` недостаточно — чтение запрещено тоже. Цена ограниченная: режим/вторая обёртка, маршрутизация этих судей в `judged`, проверка маскирования метаданных и канарейки. Нужны права на запись результатов сборки, но не на git. Это полезная первая правка, однако **она не закрывает Б1 приёмки**.

**Приёмка.** Технически соседство кода модели с раннером в одном виде ФС не неизбежно. Доверенный процесс приёмки может видеть раннер, git work и git пина, а собственные build/unit/stand/adapter/vector-команды запускать через отдельную границу кандидата. Сейчас `prepare.run`, `c_store` и другие исполнители создают дочерние процессы с тем же uid/видом ФС; очистка их окружения эту границу не создаёт. Нужен общий путь запуска либо охват всех таких мест, отдельный вид ФС/PID и желательно отдельный uid для кода кандидата; только необходимые артефакты, сокеты и временные данные стенда передаются явно. Сам git init/commit остаётся у доверенной стороны.

Цена полного варианта существенно выше первой правки: изменение точек запуска раннера, сохранение cwd/подстановок/сокетов, уборки групп и тайм-аутов, новые проверки всех классов запуска. Приёмочный минимум после правки — канарейки чтения README/кода/git из каждого типа команды, проба git init/commit под доверенным судьёй и прогон всех 11 целей P/01 с ложным стендом; затем обычный прогон реализации. Это оценка объёма работ, не измеренные часы или токены. Перед очередной попыткой отдельно зафиксировать новый pin обвеса/обёртки, старые попытки сохранить свидетелями.

**Предел с канарейкой** — только по явному изменению правила владельцем. Если в приёмке оставить кандидат тому же uid и дать читать раннер/git, проба канарейкой покажет этот доступ, но не запретит его и не докажет отсутствие чтений на следующем ходе. Такой вариант меняет границу (61), (81), а не исполняет её. У уже идущей девятой нельзя приписывать отсутствие реальной утечки только потому, что файловые инструменты не показывают `.git`; её дальнейшую судьбу решает Архитектор/владелец.

## С1. Приёмка не запускает build профиля, вопреки новому заданию

**Место:** `tasks/p01-go.ct102.json:44,50`; контекст раннера `format2_cli.py:99,136`, `prepare.py:336–338`.

**Цитата задания:** «он собирает модуль по build». Но командная строка — `runner/all.py --impl … --only P/01 --out …` — не содержит `--build`. Флаг раннера `store_true`, по умолчанию false; команда профиля исполняется только при `if build`. Отдельное `go build ./...` не обязано создавать `bin/store` и артефакт части 02 по их собственным профилям.

Проба «Машин» этого не ловит: её `build: true`, а `01-store/bin/store` и `02-installer/bin/installer` уже лежат в заготовке. Она доказывает доход до целей при готовых артефактах и работоспособность git-пути, но не обещанную сборку из чистого work. Модель с корректными build-командами и ещё отсутствующими bin-файлами снова может получать отказ подготовки, хотя следует заданию. Вызов без --build был и раньше; новая формулировка задания не устраняет этот остаток причины неисполнения приёмки.

**Предложение:** добавить `--build` в доверенный вызов приёмки либо явно исполнять все build выбранных частей перед ней. Проба должна начинаться без артефактов; build создаёт проверяемый файл/метку, и отсутствие этого эффекта проваливает пробу. Профиль build и код модели запускать с границей из Б1, а не расширять доверенный доступ ради сборки.

## С2. Исчезнувший stop-заголовок открывает весь хвост README

**Место:** `loop.py:649–658` (`runner_format`), `tests/dry_run.py` — фикстура выдержки.

**Норма:** (81) п. 3 — только выбранные разделы; весь README с историей серий и чужих линий модели не даётся.

Если `runner_stop[title]` задан, но такой заголовок отсутствует/переименован, цикл не применяет обычную границу уровня заголовка и доходит до EOF. Затем весь остаток записывается в rules и может войти в голову. Начальный заголовок проверяется с отказом, завершающий — нет. Чистая функциональная проба с `## Allowed`, отсутствующим `### OldStop` и последующим `PRIVATE_HISTORY_MARKER` воспроизвела включение маркера. У текущего локального README оба настроенных stop-заголовка присутствуют — это **не утверждение о текущей ошибочной выдержке**, а дефект защиты при изменении README.

**Предложение:** при заданной, но не найденной завершающей границе отказывать до старта/API; ограничить допустимый диапазон заголовков и добавить отрицательную фикстуру. Существующая проба проверяет только случай с найденным stop и потому остаётся зелёной при этом дефекте.

## М1. Доля токенного потолка седьмой попытки посчитана не по действующему бюджету

**Место:** (81), абзац итога и причина (г): «prompt — 47,9 млн, это 95,9 % потолка 50 млн», «попытка сожгла потолок токенов до max_turns».

По (77) п. 4 и коду предел 50 млн относится к **входу вне кэша плюс выходу**, а кэш имеет отдельный предел 200 млн. В result/usage седьмой: prompt **47 938 415**, cached **45 633 259**, completion **775 717**. Для первого потолка использовано **3 080 873**, то есть **6,16 %**; кэш — **22,82 %** своего потолка. Остановка действительно `max_turns`, 400 ходов; 13 раундов в passport действительно auto. Денежной цене долгого простоя это не противоречит, но 95,9 % не является долей действующего токенного потолка.

**Предложение:** оставить полный prompt как статистику, исправить его сравнение с потолком и слова об исчерпании бюджета; отдельно называть вход вне кэша, выход и кэш.
