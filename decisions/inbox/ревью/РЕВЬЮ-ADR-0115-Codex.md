## Б1. Установка нового плагина не открывает его таблицы backend по билету

**Место:** основной текст §3 п. 4, §6; доп. (1) п. 3; заключение доп. (3).

**Цитаты решения:** «`/units` — только для видов `origin: plugin`»; «Установка плагина меняет `/kinds` без перезапуска `backend`»; «Консоль платформы, проверка строки, права — без правок».

**Норма:** V/11.1 Н1.3: «Обратный вызов — только по билету и только на двери **закрытого перечня**, который объявляет манифест». P/06.3 Н1.9: «дверь вне `calls` на запросе — 401». Параметры `<s>/<t>` в таблице нормы обозначают конкретные имена в записи `calls`, а не разрешение обращаться к любой будущей таблице. Действующий `backend.subsystem.yaml` перечисляет конкретные таблицы `cam`, `rec`, `auto` и других подсистем.

**Проблема:** после установки `psim-security_controller` backend может узнать описание вида, но чтение и запись `psim-security_controller/controller`, чтение `controller_seen`, подача `requests` и получение `where` не становятся разрешёнными обратными вызовами. Ни новая операция `/units`, ни правило в `mapping.tsv` не расширяют `door.pass.calls`. Прямая работа воркера с хранилищем противоречит V/11.1. Автоматическое добавление строк в манифест backend возможно, но это ещё один необходимый шаг установки; он меняет его ревизию и требует согласовать обещание работы без перезапуска. Альтернатива с динамическими разрешениями меняет консоль платформы, вопреки доп. (3).

**Предложение:** выбрать и описать механизм. При сохранении платформы — установщик собирает конкретный `calls` backend из каталога плагинов, публикует новую ревизию его манифеста и выполняет предусмотренный P/02.3 перезапуск; исправить доп. (1) п. 3 и учесть переподключение потока. Если нужен backend без перезапуска — отдельно принять и нормировать расширение проверки обратного вызова. Приёмка: установить ранее неизвестный плагин на работающем стенде и через общую форму прочитать, создать и изменить объект, выполнить команду и открыть страницу; проверить именно вызовы по билету.

## С1. `source` теряет поле значения и поле подписи

**Место:** основной текст §2 п. 5, §3 п. 1; доп. (3) п. 5.

**Цитаты решения:** «`source` psim — `ref` на семью вида другой подсистемы»; «`items.ref` … Только подсказка формы: перечень значений для мультивыбора».

**Норма источника:** `plugin.schema.json`, `definitions.parameter.properties.source`: `value_field` — «Поле Unit, кладущееся в значение параметра. По умолчанию object.id»; `display_field` — «Ключ параметра из Unit.params для подписи в UI … Fallback — id». P/02.1 задаёт `ref` только как `<подсистема>/<семья>`.

**Проблема:** ссылка на семью не сохраняет ни один из этих двух выборов. В реальном `security_controller` у `cameras`, `primary_camera`, `secondary_camera` указан `display_field: name`. Общая форма не может восстановить это из одного `ref`; наличие `x-source` в выходном контракте не помогает, если его данные потеряны на шаге `plugin.json` → манифест. Схема psim также допускает явный `value_field`, отличный от `id`: тогда подстановка id незаметно меняет сохраняемое значение, а обычный `ref` начинает указывать на другой ключ строки.

**Предложение:** назвать декларативное место хранения обоих полей и правило переноса в `x-source`. Если на первом этапе поддерживается только `value_field: id`, закрепить явный отказ генератора для остальных значений; `display_field` всё равно сохранить. Приёмка: два ссылочных поля к одному виду с разными `display_field` показывают разные подписи; выбор отправляет исходное значение psim. Эта находка не повторяет прежний вопрос проверки `items.ref`: здесь теряются данные самого описания формы.

## С2. Локальные идентификаторы событий разных видов сливаются в один каталог

**Место:** доп. (3) пп. 1, 4, 6; основной текст §3 п. 1.

**Цитаты решения:** «Каждый `object_type` — таблица подсистемы»; «Событие строки таблицы — бакет единицы-плагина с полем `object` (id строки)»; «`events.kinds: {<id>: {severity}}`, подпись — `display.kinds`».

**Норма источника:** в `plugin.schema.json` массив `events` объявлен внутри каждого `object_types[]`; у его элемента собственные `id`, `name_key`, `description_key`, `severity`. Глобального ограничения уникальности `events[].id` между разными `object_type` схема не задаёт. По решению `/kinds/{kind}` должен вернуть события именно этого вида.

**Проблема:** допустимы CONTROLLER и SENSOR с событием `OFFLINE`, но с разными подписями и важностью. В единственном `events.kinds.OFFLINE` и `display.kinds.OFFLINE` две записи не помещаются. Даже при разных id плоский каталог не указывает, как backend разложит события обратно по `UnitKind.events`. Поле `object` в журнале хранит экземпляр, а не принадлежность описателя события виду; оно не решает потерю на этапе генерации. После принятой раскладки «все виды — таблицы» отдельных манифестов, которые обеспечивали бы пространство имён, больше нет.

**Предложение:** определить обратимое пространство имён, например `<таблица>.<event_id>`, в `events.kinds`, `display.kinds` и журнале, а также перевод исходного id в адаптере и правило отбора каталога для `/kinds/{kind}`. Либо хранить явную принадлежность виду в описателе. Приёмка: два вида с одинаковым исходным id и разной важностью получают разные описания и правильно подписанные события. Это отдельная проблема от уже рассмотренных формы ключа `events`, класса события и права на его бакет.

## С3. Единственный экземпляр плагина объявлен, но его создание и ограничение числа не определены

**Место:** доп. (3) п. 1; основной текст §3 п. 4 и порядок §6.

**Цитаты решения:** «Единица подсистемы … — сам плагин … один экземпляр»; для видов плагина объявлены `POST` и `DELETE /units`; порядок начинается с манифеста и урока psim.

**Норма:** P/02.3 Н1.5 описывает установку строки `platform/manifest/<sub>` и её ревизии, не создание строки единицы плагина. P/03.1-02: `start_unit(id, row, epoch)` — «запуск единицы под эпохой». В самом V/11.1 Н1.1 отдельно названо, кто создаёт строку `backend/instances`, и прямо сказано: «Строк нет или ни одну не держит живой воркер — WebUI не работает».

**Проблема:** загрузка сгенерированного манифеста сама по себе не задаёт строку, которую должен держать адаптер, её id, порядок заполнения параметров `Configure` и право на создание. Слово «один» также не ограничивает общий `POST /units`: два экземпляра означают две размещаемые единицы и потенциально два запуска одного плагина над общими таблицами объектов. Для плагина без собственных `parameters` не сказано даже, какое действие оператора запускает его после установки. Удаление экземпляра оставляет без описанного исхода таблицы его объектов и `_seen`.

**Предложение:** задать фиксированный id экземпляра и единственный путь его создания (установщик либо явный мастер), момент запуска после задания обязательных параметров, отказ второго создания и судьбу объектов при удалении/повторном создании экземпляра. Обозначить применимость `POST`/`DELETE` отдельно к виду плагина и к видам объектов. Приёмка: чистая установка плагина без параметров запускает ровно один экземпляр; повтор установки и попытка второго `POST` не создают второго держателя.
