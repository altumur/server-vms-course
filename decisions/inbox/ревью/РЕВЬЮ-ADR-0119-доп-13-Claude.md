# Ревью ADR-0119 доп. (13) (Claude)

main 4f25d9ce5 (текст доп. (13)). Сверено с доп. (1) п. 2 (ключ (автор, имя), блокировки по имени нет — № 26), доп. (5) п. 4 (общий потолок — заменяется), P/08.4 Н1.10 (`verify`).

**Счёт: Б 0, С 1, М 1.**

П. 1 верен по сути: свой потолок снимает отказ в обслуживании входа через `backend`, а 20/900 с на автора не даёт одному автору перебирать имена.

**С1. «Бюджет подбора на одно имя не растёт» — верно только при одном авторе.**
- Ключ (автор, имя) — 5 неудач за 900 с на пару. Общего потолка теперь нет. На одно имя (например, супервизора с `admin`) бюджет — 5 × число авторов за 900 с: десять учёток с `EXPORT` дают 50 попыток за 15 минут на один пароль.
- Прежний общий потолок с входом это ограничивал; доп. (13) его снимает и в п. 1 говорит обратное.

Вход сам не лучше: ключ (адрес, имя) при многих адресах растёт так же. Но адресов у вызывающего через `backend` нет вовсе, а учётки авторов — внутренние люди.

Предложение — одно из двух:
- (а) третий ключ — по проверяемому имени, общий для авторов: например, `VERIFY_NAME_FAIL_MAX` 10/900 с. Сверх — `429` только проверке этого имени: вход не задет, страдает лишь подтверждение этим супервизором. Это та же цена, что ключ (автор, имя), но для всех авторов вместе;
- (б) назвать пределом честно: «на одно имя — 5 × авторов за 900 с».

Рекомендую (а): цена — только отказ проверки одному супервизору, а не вход.

**М1. Какой из ключей сработал.** Оба потолка отвечают одним `429` и одной строкой `domain.verify.limited`. Назвать поле ключа в аудите (`key: author | pair`) и `Retry-After` до конца окна. Без этого оператор не отличит перебор имён от перебора одного пароля.
