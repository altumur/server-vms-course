## С

**С1. `PSIM_TIMEOUT` = 300 с меньше того, что норма разрешает верной реализации.** Комментарий: «PSIM_MANIFEST_WAIT (120 s) for each manifest it puts, plus the build». Но число манифестов на один `install` по V/12.4 переменное:
- Н1.2 шаг 5 — свой манифест (≤ 120 с);
- Н1.3 шаг 2 — каждый изменившийся плагин (≤ 120 с каждый);
- Н1.3 шаг 4 — `backend` (≤ 120 с), шаг 5 — повтор при сдвиге ревизий.

В `02-dependent` шаг 2 (`install camera` после `security_controller`) это три манифеста: `psim-camera`, перестроенный `psim-security_controller` (кольцо и чтение) и `backend`. До 360 с без сборки, и реализация, верная по каждому пределу, получит `SIGKILL` и красное. Срок — функция числа манифестов. Предлагаю `PSIM_MANIFEST_WAIT × (плагинов на стенде + 2)` + запас на сборку; на этом стенде (≤ 2 плагина) — 600 с. Тот же срок — в `budgets` плана.

**С2. Стенд главы 12.4 не запускает `backend`, а README подготовки говорит «`backend` запущен».** `CANON_ONLY` и `CHAPTERS['12.4']`: канон ставится, процесса нет («starts no process of it, so no V11-backend profile is required»). А `VMS/12-psim/acceptance/4/README.md`, «Подготовка»: «установлен канон `VMS/11-backend/backend.subsystem.yaml`, `backend` запущен». Это важно по V/12.4 Н1.3 шаг 4: сборка кончается только после «пульс каждого экземпляра `backend/instances` с новым instance… или ETag `/kinds` с новой rev — что раньше; не дольше `PSIM_MANIFEST_WAIT`».
- Без процесса реализация, читающая «каждого» по пустому множеству, пройдёт сразу.
- Реализация, которая ждёт хоть одного пульса или ETag `/kinds` (дверь самого `backend`), простоит 120 с и кончит отказом: каждый `@psim install` — красный.

`SUT 0` прогона этого не показал. Решить не раннеру одному: либо стенд поднимает `backend` (нужен профиль `V11-backend`), либо «Спецификация VMS» правит README и V/12.4 Н1.3 шаг 4 («`backend/instances` пуст — ждать нечего»). До решения — спросить её. Сам стенд README не противоречить не может.

## М

**М1. Группа `psim` после обычного выхода и при исключении.** `killpg` — только по сроку. Если команда урока оставила потомков (сборщик, ожидание) и вышла, или раннер прерван (`KeyboardInterrupt`, ошибка в `communicate`), группа живёт дальше и держит лог и порты. `try/finally` с `killpg(SIGKILL)` после `communicate` (ошибку `ProcessLookupError` — молча).

**М2. «Ничего не записал» видит только `platform/manifest/` и `psim-`.** Отказ шага 3 должен оставить хранилище целым, а сломанная реализация может записать и мимо этих префиксов: другие строки `platform/` установщика, `backend/…` сборки. Сверять весь перечень ключей с ревизиями (на стенде он мал), исключая известный шум: пульсы, `*/heartbeats/`. И проверить, что `/v1/list` отдаёт всё, а не первую страницу.

**М3. `t` вне диапазона дат.** `event_bucket` берёт любое конечное `t`. `time.gmtime` при `t` ~ 1e20 бросает `OverflowError`, и раннер падает, а не даёт шагу отказ. При `t` ~ 1e13 имя файла выйдет с годом из шести цифр, не по грамматике журнала. В выгрузке таких `t` нет (все `{now}` или 1700000000…1700090000), но `@append event` нарочно кладёт строки «мимо писателя». `t` вне `[0, 253402300799]` — текущее окно, как у строки без `t`.
