## Находки

### С1. Граница HTTP для копии не определена относительно разрешённого внутреннего frame

**Тип:** неоднозначность нового смысла/границы нормы, решение Архитектора. **Место:** `decisions/0130-боевая-пригодность-сгенерированного-кода.md:33`, связь с `:14`, `:25` и `:47`. Контекст того же pin: `Platform/01-store/spec/01.3-store.norms.md:295` — таблица HTTP-дверей P/01.3-R016; `:306`–`:307` — CLI backup, P/01.3-R018; `:435`–`:438` — Implementation decides, внутренний формат admin.sock, без новых HTTP routes.

Пункт 5 требует «копию через объявленный HTTP-договор». Но в прочитанной таблице дверей нет отдельного HTTP-маршрута копии. Нынешняя норма задаёт CLI backup, единый JSON Lines файл и согласованность снимка, а frame admin.sock для read-fence/admit/import прямо оставляет внутренним форматом реализации. Без указания конкретной существующей HTTP-операции или явного нового изменения читатель не отличит исправление HTTP на уже объявленной двери от требования ввести новую дверь копии/запретить разрешённый внутренний frame.

**Минимальный контрпример, только текст.** Реализация обслуживает все опубликованные HTTP-двери по их договору. CLI backup получает согласованный срез через именованный/версионированный внутренний read-fence frame admin.sock и публикует требуемый файл tmp+rename. По указанным фрагментам P/01 такой выбор механизма допустим. Если пункт 5 буквально требует HTTP-передачу самой копии, этот вариант уже недостаточен, хотя новый маршрут/форма не названы. Обратная трактовка пункта 5 — проверять HTTP только у существующих HTTP-дверей — не вводит такого требования. Это две разные области будущей приёмки.

**Минимальное предложение.** Рекомендую сохранить имеющуюся границу: потребовать настоящий HTTP framing там, где уже объявлена HTTP-дверь; отдельно назвать, какая именно операция/сокет копии нарушает этот договор. Сохранить внутренний формат admin.sock и CLI backup до явного решения об их изменении. Если владелец намерен стандартизировать передачу копии по HTTP, включить новый маршрут/форму и снятие прежнего выбора в отдельный явный пункт согласованного Source-пакета. До этого не превращать строку 33 в скрытое требование новой двери или в отказ допустимому внутреннему read-fence.

Я не утверждаю, что частный протокол конкретной41 соответствует нынешней норме: её код/ревью не читал. Находка относится к области нового требования в ADR, а не оправдывает сообщённый владельцем дефект.

### М1. Offline-контроль должен различать использование vendor и просто успешную сборку без загрузки

**Тип:** уточнение Confirmation, не новая норма алгоритма. **Место:** `decisions/0131-raft-закреплённой-библиотекой.md:26`–`:27`, `:41` и `:49`.

Текст правильно требует полный runtime vendor и сборку именно из него. Перечисленные три переменные запрещают загрузку через proxy/sumdb и смену toolchain, но сами по себе не описывают выбор источника пакетов. Для воспроизводимого доказательства стоит явно исключить альтернативный module/workspace/cache путь и сравнить фактически выбранную идентичность с закреплённой, а не только записать её.

**Минимальный мысленный отрицательный контроль, не выполнялся.** Runtime-файл отсутствует в vendor; окружение выбирает module mode, а требуемые модули уже находятся в локальном cache. Успешный import/build с указанными переменными доказывает возможность offline-сборки, но не полноту или использование переданного vendor. Аналогично успешная сборка через локальную замену не доказывает применение выбранного upstream. Это не соответствует требованию «из vendor», хотя один exit0 и список переменных могут выглядеть как его подтверждение.

**Минимальное предложение.** В плане проверки явно закрепить выбор vendor и отсутствие workspace/replace/cache обхода; записать фактические module/version/source identities и сравнить их с Source pin/vendor roster. Добавить отрицательный контроль: повреждение/изъятие нужного vendor payload даёт ошибку проверки без подхвата cache/сети или пересоздания. Конкретную команду/среду выбирает tools; новых числовых бюджетов или режима платформы это не требует. Фактическое качество уже готового пакета здесь не оценивалось.
