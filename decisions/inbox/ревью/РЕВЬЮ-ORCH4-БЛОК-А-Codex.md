## Находки

Б — нарушение контроля выдачи или обязательной проверки приёма. С — потеря возобновления/наблюдаемости или некорректная обработка отказа. М — малое замечание; таких не заявлено. Несколько воспроизведений одной причины считаются одной находкой.

### Б1. Второй просмотр разрешает выдачу в уже занятое поле ввода

**Новый код:** [automation.py:290–305, `check_turn`](/home/pilot/review103/orch4-block-a-6dc3939/inputs/after/automation.py:290), вызов `run:440–449`. **Неизменённый контекст:** `windows.py:99–108`, `find_line` и `one:148–159` на том же endpoint. Основание — доп. (18) пп. 1–2, доп. (2) п. 1; поручение отдельно требует проверить попадание в набранный текст.

Нормальное пустое поле под прежней строкой СТОП допускается. Контрпример отличается только непустым вводом:

```text
status: running
СТОП: готово | ЖДУ: файл задачи
──────────────────────────────
❯ harmless already typed draft
```

1. Первый сбор строк допускает получателя и готовый шаг A.
2. К моменту второго просмотра пользователь уже набрал текст, ещё не нажав Enter. Busy-сигнала нет.
3. `find_line` прекращает анализ после горизонтальной границы (`windows.py:101–102`), прежде чем проверит prompt ниже неё. Возвращается прежний СТОП. `one` не возвращает отдельного признака занятого composer.
4. `check_turn` сравнивает только ok/noscreen/scrolled/busy/confirm и текст СТОП. Возвращает пустую причину, то есть разрешение.
5. `run` резервирует A и вызывает sender с текстом и Enter. В тесте sender подставной: зарегистрирована одна отправка, ledger=`issued`, хотя ожидалось ноль. Реальный терминал не трогался.

**Причина:** новый call site использует результат общего поиска СТОП как доказательство свободного ввода. Поиск СТОП такого свойства не доказывает. Это не новая находка против старого парсера сама по себе: недостаточен именно новый барьер выдачи на его результате, при снятом пороге тишины.

**Эффект:** строка задачи может попасть в чужой незавершённый ввод; при Enter возможна отправка объединённого/заменённого текста. Как именно конкретный CLI объединит ввод, не исполнялось и не утверждается. Уже разрешение выдачи при непустом поле нарушает требуемую защиту.

**Доказательство:** `typed_composer_is_not_a_free_turn` использует настоящие `windows.one`/`find_line` с подставленным `read_screen`; `typed_composer_full_dispatch` дополнительно проходит настоящие `run → reserve → settle`, sender фальшивый. Оба дали расхождение. Форма синтетического экрана явно указана; это не запись реального окна.

**Краткая правка:** перед резервированием отдельно доказать пустоту актуального composer/последнего prompt и отсутствие нового хода; неопределённый результат запрещает выдачу. Не считать неизменившийся СТОП достаточным. Связать доказательство с той же актуальной инкарнацией окна.

### Б2. hold/cancel завершаются до резервирования, но старый план всё равно отправляет шаг

**Новые команды:** [tasks.py:1540–1580, `cancel`, `hold`](/home/pilot/review103/orch4-block-a-6dc3939/inputs/after/tasks.py:1540). **Путь выдачи:** `automation.run:397–464`, `queues.plan:1071–1103`, `Plan.reserve:828–883`. Последние методы частично существовали раньше; новые команды впервые обещают выполнить эту смену состояния штатным API в рассматриваемом блоке. Основание — доп. (18) п. 4 и документированный смысл удержания/отмены.

Положительный полный проход без конкурентной команды отправляет A ровно один раз. Минимальный порядок для hold:

1. Collector под своим writer lock строит `Plan`: A=`готова`, его job уже включён в jobs.
2. Архитектор вызывает `hold A`. Команда под `tasks/.lock` атомарно пишет `owner: true` и `answered`, fsync завершается, команда успешно возвращается.
3. Свежее чтение задачи даёт `ждёт владельца`. Резервирования A ещё не было.
4. Collector делает предусмотренный второй просмотр окна: прежний реальный СТОП, поле пусто, busy нет.
5. `Plan.reserve` проверяет лишь отсутствие уже зарезервированной попытки. Ни текущие поля A, ни owner/cancelled/after повторно не читаются. Старый READY job записывается и отправляется.

Вариант с `cancel A` имеет тот же порядок: свежее состояние `отменено`, но sender вызывается. Обе команды исполняются легально от architect, без подмены актёра. Команда завершается **до** reserve, поэтому это не вопрос, обязана ли отмена отзывать уже переданную агенту работу.

**Доказательство:** `hold_between_plan_and_reserve`, `cancel_between_plan_and_reserve`: реальные temp-файлы команд, `plan`, `run`, reserve/settle. Управляющая команда выполняется в подставном callback чтения окна между plan и reserve. Получено по одному queue action; замороженная модель=`готова`, свежая — соответственно `ждёт владельца`/`отменено`. Потоки не нужны, поскольку полностью выписан допустимый конечный порядок двух актёров.

**Причина:** отдельные замки защищают собственные записи, но отсутствует общий момент проверки текущей допустимости шага и его резервирования. Перечитывается окно, не задача.

**Краткая правка:** определить и реализовать один порядок/момент линеаризации команды управления и reserve. Если hold/cancel уже завершилась перед reserve, новый reserve должен перечитать состояние под согласованным замком и отказать. Сохранить durable reserve до send и защиту от двойной попытки. Не держать task lock на 400-секундной проверке или произвольном внешнем процессе.

### С1. release не возобновляет ранее выданный и снятый шаг

**Новый код:** [tasks.py:1583–1591, `release`](/home/pilot/review103/orch4-block-a-6dc3939/inputs/after/tasks.py:1583). Контекст: `queues.close_withdrawn:701–714`, `Plan.closures/settled:926–960`, `tasks.Model._compute:607–614`. Основание — доп. (18) п. 4, docstring `release`: «Take a held step back to issue».

Для ещё не выданного шага hold/release работает. Проблема — допустимый жизненный цикл уже доставленного, но не взятого шага:

1. A выдана, ledger содержит attempt 1, статус `issued`; start отсутствует.
2. Архитектор удерживает A через hold.
3. Следующий plan вызывает существующий `close_withdrawn`: A закрывается в `QUEUE_DONE/A.json` как снятая с выдачи. Это не acceptance задачи.
4. Архитектор вызывает release. Удаляется только `owner:`, история `answered` остаётся.
5. Следующий проход, даже через час, не имеет queue/resend job для A. Старый ledger-row оставляет задачу `выдано`, поэтому `Model.issuable()` не возвращает её. `closures()` видит постоянную done-запись и запрещает resend.

**Эффект:** успешная release не возвращает шаг в автоматическую доставку, хотя работы/приёма не было. Сам файл цели не уничтожен; вручную его ещё можно взять/переоформить. Не утверждается физическая потеря байтов. Отдельного READY-сигнала этот путь также не создаёт, поскольку состояние осталось `выдано`.

**Доказательство:** `released_issued_step_must_resume_delivery`, с реальными временными task/ledger/done файлами. После release: jobs=[], issuable=[], state=`выдано`; done-запись содержит причину удержания. Новый counterexample, а не повтор старых проверок answer --hold.

**Краткая правка:** release должна согласованно возобновлять допустимую доставку ранее снятого шага, сохраняя историю выданных идентификаторов и не обходя защиту двойной выдачи. Не лечить это удалением ledger-записи. Конкретный способ продолжения/новой попытки должен оставаться согласован с действующим учётом попыток.

### С2. Будильник снимается по закрытому подмножеству настоящего ожидания

**Код:** [tasks.py:1406–1434, `named_tasks`, `wait_checker`](/home/pilot/review103/orch4-block-a-6dc3939/inputs/after/tasks.py:1406), `automation.wakeup_candidates:175–182`, production wiring `collector.py:413`. Основание — доп. (18) п. 5 и доп. (2) п. 5: ожидаемое должно действительно произойти; свободный текст СТОП не является источником истины.

Положительные границы работают: ожидание только принятой A снимается; A плюс известная открытая B не снимается; исключение при построении модели сохраняет будильник.

Контрпример 1:

1. A принята. В файле B есть ошибка формы (нет обязательных полей); B попала в `model.broken`, не в `model.tasks`.
2. Получатель ждёт «приёмки A и B от Архитектора». Состояние B не доказано закрытым.
3. `named_tasks` ищет только в `model.tasks` и silently отбрасывает токен B. Возвращается [A].
4. `all(state in CLOSED)` истинно для A, и `wakeup_candidates` удаляет направленный будильник с причиной `CLOSED: the wait names only closed tasks`.

Общая ошибка файла B может позднее дать отдельный сигнал Архитектору; это не сохранение будильника по исходному ожиданию. Не утверждаю, что все механизмы наблюдаемости молчат.

Контрпример 2 не требует сломанного файла: «приёмки A **и отдельного ответа Архитектора о разрешении продолжить**». A закрыта, отдельного ответа ещё нет. Распознаётся только A и всё составное ожидание объявляется состоявшимся. В такой модели ошибок файлов нет. Простое упоминание закрытой задачи не доказывает независимое событие, даже если оно относится к этой задаче.

**Причина:** проекция текста на известные task IDs затем используется как доказательство полноты всего ожидания. Проверка исключения из `_quick_model` не спасает нормальное возвращение неполной модели. Это одна причина, не две находки.

**Доказательство:** `broken_named_dependency_must_keep_alarm` прошёл реальную цепь чтения файлов → wait_checker → wakeup_candidates и получил отсутствие target; `owner_answer_after_closed_task_must_keep_alarm` получил True для незавершённого составного условия. Все данные синтетические и принадлежат проверке.

**Краткая правка:** неизвестный/сломанный явно названный шаг, а также недоказанная дополнительная часть ожидания должны сохранять UNKNOWN/будильник. ### С3. Ошибка worktree remove и частичное add не оставляют корректного учёта уборки

**Код:** [tasks.py:1139–1172, `run_check_spec`](/home/pilot/review103/orch4-block-a-6dc3939/inputs/after/tasks.py:1139). Оба caller — `_check_spec_gate` и `cammeta-main-check:54`. Основание — требование задания проверить остатки worktree и собственный контракт временного worktree.

Нормальный add → checker → remove проходит. Ветка отказа после удачного add:

1. Worktree зарегистрирован. Checker завершился, например с кодом 0.
2. `git worktree remove --force` вернул ненулевой код. `_course_git` возвращает CompletedProcess; код возврата здесь не проверяется. Исключение также подавляется.
3. `shutil.rmtree(base, ignore_errors=True)` удаляет физическое дерево, но не Git-регистрацию в основном репозитории.
4. Результат остаётся `ok: true, error: ''`; никаких сведений о неудавшейся уборке в нём нет.

Второе окно той же причины: add успел создать регистрацию, но завершился таймаутом/частичным отказом до `added=True`. Finally вообще не вызывает remove; затем удаляется base. Частичный add как физическое поведение Git в этой работе не исполнялся. Это явно указанный порядок отказа, который код не компенсирует, если он случился.

**Доказательство:** изолированная модель транспорта `failed_worktree_remove_must_not_leave_registration` / `partial_worktree_add_timeout_must_cleanup_registration`: подставной Git удерживает регистрацию, Python выполняет настоящее удаление только собственного temp base; в результате регистрация остаётся, физического пути уже нет. Это **не наблюдение настоящей Git-регистрации**, не доказательство частоты таймаутов и не настоящий запуск checker. Для первого окна статически достаточно факта, что неуспешный remove не проверяется; второй контроль подтверждает условие `added`.

**Эффект:** накапливаются висячие регистрации и теряется диагностика уборки. Зелёность собственно завершившегося checker не опровергается ошибкой remove; результат уборки нужно учитывать отдельно, не превращать ошибку инфраструктуры в семантический результат задачи.

**Краткая правка:** учитывать начатое add и его частичные следы; проверять результат удаления; сохранять точный собственный путь/идентичность для безопасной последующей уборки и явный cleanup error. Не подавлять его без записи и не объявлять ресурс убранным только потому, что rmtree не поднял исключение. Чужие worktree не затрагивать.
