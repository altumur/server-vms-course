## P2 — исключение опознавателей применяется и к полям чужого ответа

`runner/diagnostic_secrets.py:47–57`: `identities = field in self.IDENTITY_FIELDS`; далее чувствительность ключа отключается через `not identities`. Здесь не различаются карта опознавателей **отчёта** и обычное поле **ответа** с тем же именем. `learn_received` и `body` вызывают этот же `learn` для чужих значений; JSON-строка тела также разбирается им.

Контрпример, не содержащий имени сценария с token:

```json
{"scenarios":{"safe-case":[{"step":"4","line":6,"ok":true,"why":[],"got":{"cases":{"token":"own-issued-cases-credential-042"}}}]}}
```

До finalize зарегистрированный лог процесса содержит точное `native echo: own-issued-cases-credential-042`. После `learn_received` и двух проходов finalize у старого снимка токен есть в `values`, лог содержит `<redacted>`. У нового токен не узнан ни до, ни после finalize, его точное вхождение осталось в логе. Для `scenarios`, `cases`, `variants`, `probes` внутри got результат одинаков; также для сериализованного JSON-тела. **Восемь old GREEN → new RED.** Это одна причина, не восемь находок.

Источник — заявленная неизменность границы А/Б и правило самой серии: token внутри ответа остаётся секретом; process logs получают точную замену известных значений. Новый код перестал узнавать значение непосредственно из token-поля. Это не требование разбирать кодировки process logs: проба содержит только точное вхождение, прежнее поведение. Собственные файлы А в этой пробе остаются opaque; утечку raw тела в А не заявляю.

Нужно ограничить исключение доказанными картами идентичностей отчёта. При входе в got/response/body и при разборе строкового тела переключаться на обычное обучение чувствительным полям, без исключения по случайному имени `cases` и т. п. Возможен отдельный обход отчёта и `learn_response`; важна граница происхождения, а не белый список имён на любой глубине. Сохранить отсутствие ограничения длины и обучение коротких секретов.
