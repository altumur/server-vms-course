## P2 — EOF закрывает Unix-посредник до отправки накопленных байтов

`runner/m11stand.py:161–174`, `Proxy._pump_unix`; подключение посредника — `runner/stand.py:166–171,226–228`. Норма: общий README приёмки на `13a30dc`, словарь `@cut role` / `@mend role` (строка 224); провод клиента хранилища — HTTP/1.1 через Unix-сокет роли (`common/contracts/store-client.md`, «Адрес»).

После `recv` прочитанные байты помещаются в `pending` и будут записаны только на следующем обороте `select`. Если источник уже закрыл запись, тот же следующий оборот возвращает EOF читаемого источника и готовность назначения к записи. Читаемые сокеты обрабатываются первыми: `if not raw: return` вызывает `_finish_pair`, который закрывает обе стороны. Запись `pending` не исполняется. Это происходит без `@cut`, при обычной пересылке.

Воспроизведение на настоящих Unix-сокетах:

- HTTP-сервер отдаёт целиком ответ `200` с `Content-Length: 1024` и `Connection: close`, затем закрывается. Прямой `harness.HttpDoor.request` получает всё тело — 3/3; через `Proxy(unix=…)` — 0/3, `connection closed without a response`. Сервер получил полный запрос и отправил все 1124 байта ответа.
- При теле 200000 байт прямой обмен — 3/3; посредник — 0/3, `truncated response body`, хотя сервер отправил все 200102 байта. Потеря последнего буфера воспроизводится и после передачи нескольких полных буферов.
- Клиент отправляет полный HTTP-запрос и делает `shutdown(SHUT_WR)`, продолжая читать ответ. Прямой обмен — 3/3; посредник — 0/3, сервер получает 0 байт запроса: симметрично теряется ещё не переданный буфер запроса.

Следствие: допустимое закрытие HTTP-соединения превращается в `no_reply`. Посредник устанавливается до запуска процессов любого сценария с названной ролью, поэтому нормальная реализация может не пройти даже подготовку до разреза, а после `@mend` снова получать искусственные отказы. Тест с echo, держащим соединение открытым, этот дефект не обнаруживает. Содержимое HTTP в пробе — собственные публичные байты; исходы сравниваются настоящим транспортным читателем, код реализации не используется.

Нужно учитывать EOF отдельно по направлениям: передать накопленные байты, затем закрыть запись соответствующего назначения; обратное направление оставить до его EOF/завершения. Переходы должны сохранять правила cut/mend и предел буфера. Одной перестановки циклов read/write недостаточно: EOF клиента не должен лишать его ещё ожидаемого ответа. Повторить неизменную пробу на `50ce0b0` и исправленной вершине, включая оба размера ответа и half-close клиента.
