## Нормальный предусмотренный путь и то, что уже соблюдено

Вызов `cammeta-windows --plan` только строит план. `--pass` отказывается без точного `ORCH5_ENABLED=1`; реальный `--pass` в ревью **не вызывался**. Новый код читает `tasks.Model`, ledger окон и наблюдения, распределяет отдельно N run и N judge, готовит worktree/prompt и выполняет действия через Orca adapter. Start/done/accept продолжают использовать существующие факты задач. Turn/delivery не делают задачу DONE: это по-прежнему acceptance record.

Статически и выбранными UNIT подтверждены следующие положительные границы:

- N одно для двух отдельных видов, а не один общий pool. `counts` считается по kind; уменьшение N не порождает close существующих окон. Run-reserve один внутри N, без нового выдуманного общего лимита. Равные declared area блокируют второго run writer в одном плане; область не освобождается просто после hand-in.
- Приём идёт раньше самостоятельного review. У **приёма** выбирается другой provider известного автора; неизвестный автор или отсутствие другого provider даёт hold. Это не распространяется автоматически на standalone review — С5.
- Окно с открытым вопросом остаётся в ledger и занимает место. Подтверждённый ответ планируется в тот же handle. Нет автоматического нового окна вместо живого вопрошающего.
- Run после hand-in остаётся открыт. После принятия ему посылается просьба влить; close предлагается только при `merged` и idle. Отказ в живое окно сохраняет его контекст и cwd: это соответствует актуальному ORCH6-промпту:56 и ожиданию приёма по Add25–26, при отдельном указании задания о новом окне после отказа. При действительно exited working window замена сохраняет worktree и причину.
- Неизвестный UI dialog в выбранном нормальном случае не нажимается. Явная ошибка `adapter.close` не удаляет запись и writer reservation. Это проверено отдельно, не объявлено дефектом.
- Путь и prompt filename shell-quoted при формировании launch command; task IDs ограничивает существующий reader. Здесь не обнаружена отдельная shell-инъекция через repo/cwd в launch: проблема Б3 относится к **передаче текста в уже неподходящий терминал**, а не к отсутствию shlex.quote.

Эти положительные результаты не доказывают работу actual Orca/CLI/модели. В частности, synthetic «checker green» проверяет только вызов заглушки gate, не реальный check_spec.

## Подтверждённые находки

### Б1. Create не имеет атомарной резервации и восстановления

**Код:** `taskwindows.py:559–572`, `511–555`, особенно529–535; `cammeta-windows:39`. **Основание:** Add20.3,21.1,25 — пределы и единственность писателя; ранняя §2:91 описывает требуемый смысл восстановления, здесь это также явная граница задания. **Доказательство:** UNIT `B08_two_pass_reservation_race`, `B09_partial_create_retry` + статическая трасса.

Положительный последовательный путь держит уже записанное окно в `held`. Но два обычных прохода могут прочитать один пустой ledger: P планирует open run-1/A.1; Q до записи P планирует то же; P создаёт h1 и сохраняет; Q создаёт h2, перезаписывает тот же ключ run-1. В fake-backend получилось **два create, в последнем ledger только h2**. Это конечная последовательность двух snapshots, не вероятностное утверждение о race и не две настоящие сессии.

Ни CLI, ни run_pass не берут writer/reservation lock. В отличие от старого queue-пути они не работают внутри collector writer lock: collector не вызывает новый run_pass, а новый CLI вызывает его непосредственно. `save_ledger` использует общий `.tmp`, но atomic replace отдельного файла не сериализует read→decide→create. Один task/area и численный лимит больше не гарантированы.

Есть и одиночное окно сбоя: create успел, но ответ backend потерян/timeout. До получения handle записи ещё нет (532→533). Исключение лишь записывает error outcome; следующий проход снова выдаёт open. Вторая fake-сцена дала два возможно созданных окна, **ноль сохранённых handles**. Аналогично crash между create и persist оставляет orphan. Это один корень — отсутствие транзакции/reservation и reconciliation внешнего create, не отдельная находка на каждый сбой.

**Минимальная правка:** резервировать task/kind/area и operation identity под коротким общим lock, проверить свежую задачу и лимит, затем отпустить lock до длительного backend; хранить неизвестный исход create и сверять его до повтора. Не держать tasks/.lock через launch/confirm и не считать отсутствие ответа доказательством отсутствия окна.

### Б2. Новая роль run обходит обязательный check_spec

**Код:** `tasks.py:1153–1156,1293–1306`; новая ветка `_check_published:1165–1169`, spec-подсказка `taskwindows.py:79`. **Норма:** Add18.3,29.2. **Доказательство:** нормальный `N08_legacy_gate_positive` и контрпример `B03_run_gate_missing`.

В before существующая проверка обслуживала publishing roles spec103/spec103-claude. Новый runtime назначает писателю курса `role: run`, отдельно проверяет публикацию в task branch, но `_check_spec_gate` оставлен зависимым от `needs_main(fields)`. Для обычного `role: run` без publish override эта функция false. Поэтому даже для меняющего Platform коммита gate возвращает None; `run_check_spec` не вызывается. У старой роли в том же UNIT-fixture вызов был, у новой — **0**.

Это не повтор старого спора о доверии checker-коду. Неподключён **новый путь писателя** к уже принятому обязательному gate. Human judge может следовать prompt и запускать проверку сам, однако `cammeta-accept` разрешает acceptance без машинной проверки и без записанного explicit bypass. Положительная подсказка в prompt такого отсечения не заменяет.

**Правка:** отделить «нужна проверка спецификации» от «должен уже быть в main»; для course run проверять точный сдаваемый branch commit до acceptance и сохранять результат. Внешний code repo не надо ошибочно проверять как course Platform.

### Б3. Follow-up и Kimi prompt идут в занятое/непроверенное поле ввода

**Код:** `taskwindows.py:223–225,489–492,498–501,539–545`; неизменённые `automation.py:245–263,265–316` — контекст нового вызова. **Основание:** прямое задание о небезопасном вводе и ORCH6:23,28,84–88, материалы не команды. **UNIT:** `B05_busy_followup_injection`, `B06_startup_typed_injection` после положительных N09/N10.

`plan` вычисляет idle, но не использует его для send ответа, rejection, resubmission или merge-сообщения. `Orca.send` вызывает низкоуровневый `automation.send` с Enter напрямую, без check_window/check_turn/composer. В UNIT при `busy=True,idle=False` строка ответа всё равно поступила fake sender. Последний безопасный снимок также не перепроверяется перед действием.

При первом Kimi prompt достаточно совпадения ready marker; `confirm` не требует `seen.idle` и игнорирует typed/unknown input. В fixture с ready marker и уже набранным текстом ушли текст и Enter, затем busy был принят за started. Новая строка может склеиться с draft или вмешаться в ход.

Более опасная статическая ветвь того же корня: агент уже вышел к shell, но terminal ещё running. Низкоуровневый send не проверяет, что текст примет агент. Обычный ответ с процитированным `; ...` может стать shell-вводом. Это не предположение о злоумышленнике с чужими правами: такой stop/shell boundary уже учитывает сохранённый `automation.check_window`, но новый caller его обходит. На shell ничего не посылалось и исполнение команды не доказывалось.

**Правка:** перед каждым текстом/Enter требовать свежую доказанную готовность того же agent incarnation, пустой composer и отсутствие хода/системного диалога; unknown оставлять в ожидании. Стартовый ready marker сам по себе этого не доказывает.

### Б4. Startup selector превращает процитированные данные в UI-действие

**Код:** `taskwindows.py:59–64,449–455,477–484`. **Норма:** ORCH6:10,23,84–88 и разрешение только конкретных стартовых метаопераций. **UNIT:** `B16_startup_selector_reads_quoted_data` и `B07_busy_startup_text_injection`; N13/N11 показывают обычный busy и отказ на unknown dialog.

`observe` ищет `Update available` по всему screen text. Достаточно, чтобы рабочий агент вывел цитату исходника `Update available / 2. Skip` и свой Working marker. Actual exact parser возвращает одновременно **busy=true и startup=codex update**. `confirm` ставит startup раньше busy и посылает цифру2. В fake runner это записано; никакого реального нажатия не было. То же возможно для оставшегося текста старого диалога.

Ошибка независима от границы пустого composer: даже пустой composer не делает цитату системным меню. DIALOG/STARTUP regex не привязаны к достоверному активному диалогу запуска и выбранному provider; строка внутри данных получает управляющую силу. `keys` returncode при этом не проверяется до следующего шага выбора.

**Правка:** отвечать только доказанному актуальному startup UI конкретного launcher, не истории/цитате/draft; busy/unknown исключают нажатие. Если такой UI нельзя отличить безопасно, оставить unproven и сообщить, не нажимать. Право на `Yes, proceed` у directory-trust отдельно нельзя выводить из того, что эта фраза попала в allowlist исходника; в ревью это действие не выполнялось.

### С1. Приёмщик не может исполнить выданный ему start/ask/done

**Код:** `taskwindows.py:66–82,289–293`; существующие `queues.py:739–758`, `tasks.py:1598–1613,1884–1889`. **Норма:** Add22,23.2,27 и ORCH6:24–27,40. **UNIT:** N07, B01, B02.

Для сданной A.1 с `role: run,accept: judge` создаётся accept window с role judge. Общий prompt велит `cammeta-task start --from judge A.1` и при смысловом вопросе `ask --from judge A.1`. Но start и ask допускают только **роль работы**, run. Точная permission-проверка вернула `only the role ... (run) may start/ask`. Start run в том же fixture проходит. Общая команда done для judge тоже не подходит `_hand_in_locked`, а после acceptance задача уже CLOSED.

Приёмщик физически может вызвать cammeta-accept без своего start, но это обход обещанного ему протокола. Главное, он не может записать допустимый вопрос по принимаемой работе и получить ответ по предусмотренному пути. Проверки старой роли не были дефектом до появления этого нового caller.

**Правка:** согласовать протокол accept-фазы с правами start/ask/завершения, сохранив отдельную авторскую start-mark и право сдачи работы. Нельзя просто разрешить judge отмечать работу run как собственную. Аутентификацию `--from` здесь не пересматриваю: Owner уже принял заявленное имя.

### С2. Unknown delivery расходует сообщение навсегда

**Код:** `taskwindows.py:223–225,539–544`. **Норма:** Add22 и ORCH6:49. **UNIT:** N09 и B04.

После подтверждённого answer следующий план правильно не дублирует его. Но при возврате `unknown` код так же записывает key в rec.sent и для новой сдачи ещё сдвигает handed. Следующий план не создаёт send, поскольку проверяет лишь наличие ключа, а не delivery. В finite fixture fake transport не доставил ответ, вернул unknown; второй план дал **0 sends**. Окно остаётся открытым, но ответ так и не получает.

Это не требование слепо повторять неизвестную доставку: unknown действительно может означать «дошло, но квитанция потеряна». Нужен отдельный pending/unknown outcome с reconciliation request/receipt и устойчивым сигналом ошибки, а не окончательное consuming dedup. В следующем public window projection результат конкретного pending message вообще не виден.

### С3. Потеря входа освобождает либо забывает окна

**Код:** `taskwindows.py:130–139,227–230`. **Норма:** принятые предел/один writer и закрытие после acceptance (Add21,25,26); требование не выдавать неизвестное за завершённое. **UNIT:** B10, B11.

Повреждённый ledger catch-ится как `{windows:{},closed:[]}`. Существующие физические окна после этого не инвентаризируются, план открывает A.1 заново с нулевым счётчиком. Это другой корень, чем Б1: даже строго один проход после исправления lock прочитает corrupt ledger как пустой.

Вторая ветвь той же ошибки tri-state: если task исчез из view, idle window закрывается с причиной «файла задачи нет». Файл мог временно отсутствовать/быть недоступен; отсутствие не есть acceptance или явный cancel. В UNIT такой close действительно появился. Для malformed файла Model сохраняет broken row — это правильная соседняя граница; физически отсутствующий источник так не защищён.

**Правка:** отсутствующий впервые ledger отделить от ошибки чтения существующего; corruption/error блокирует выдачу и вызывает сигнал. Task missing/unknown сохраняет окно/area до сверки, не завершает работу. Это не предложение сохранять cancelled окно вечно: явный cancel и проверенный idle — другой, предусмотренный путь.

### С4. Reuse не проверяет cwd/base принимаемой редакции

**Код:** `taskwindows.py:412–426`, выбор accept cwd/base289–292. **Норма:** Add29.2, ORCH6:22,47–48. **UNIT:** B12, где существующий собственный fixture directory с содержимым старой редакции получил reused без единого fake Git-запроса.

Конечный статический сценарий: judge проверял C1; после отказа и новой сдачи C2 его окно завершилось; новый accept action объявляет base=C2, но использует тот же `wt-judge-A.1`. `prepare_worktree` видит каталог и возвращает reused, не сверяет ни репозиторий, ни HEAD. Первоначально созданный detached worktree всё ещё C1. Prompt описывает другой базис. Сообщение о будущей пересдаче это не исправляет: при новом открытии handed уже устанавливается в timestamp C2, поэтому отдельного «пересдано» с checkout не будет.

UNIT не изображает настоящий Git worktree и не доказывает checkout C1 на диске: он показывает безусловный reuse любой существующей директории. Сценарий с корректным старым worktree следует из этой же ветви. Для run recovery сохранение незакоммиченных правок намеренно и не объявляется дефектом.

**Правка:** отдельно проверять принадлежность и actual base/cwd; для judge подготовить объявленный commit либо остановиться с точным несовпадением, не сбрасывая чужие/сохранённые правки. Для run сохранить его разрешённый незавершённый контекст.

### С5. Provider independence реализована только для accept

**Код:** `taskwindows.py:315–334,179–194`. **Норма:** Add20.3,26.2, ORCH6:38,48. **UNIT:** B13.

Нормальный accept выбирает choices без provider автора. В отдельной ветви reviews берётся raw.provider либо первый judge_provider, а author_of вообще не вызывается и author metadata в prompt не добавляется. Review задачи с известным автором Claude и raw.provider=claude выдаётся Claude. В UNIT явно переданный author resolver не изменил это поведение. Если автор неизвестен, отдельного hold тоже нет — в отличие от accept.

Owner может выбрать provider в файле задачи, но это не даёт коду разрешение нарушить общую независимость. Human reviewer может заметить конфликт и спросить; ресурс и неправильное назначение уже выданы. Нужны точные автор/редакция/provider для review и такой же фильтр/hold до открытия. Нельзя угадывать provider из имени логической роли.

### С6. Отсутствующий repo даёт true вместо неизвестного доказательства
