## 4. Новые причины

### Н-С1. Новый matcher допускает ответ без полной Source-формы

**Код:** `scenario_verdict.go:393–422,437–475`, вызов `:118–135`. **Норма:** P01 acceptance1 README:16–23, общий README:308–309,323,340. JSON chapter1 сравнивается целиком; unnamed error разрешён только в корне, дополнительный non-error field не разрешён. P01.1 binding — только строка; generic binding также не допускает boolean.

Нормальный полностью разобранный ответ на actual Source `01-absent` — `200 {"items":null,"index":""}`. Он проходит. Если добавить `"unassigned":true`, matcher тоже возвращает match. Он всегда передаёт `subset=true` и рекурсивно не проверяет неназванные поля. В другом положительном контроле `index:"v1"` связывается нормально; замена index на boolean true тоже принимается как `$a`. Публичная форма такого ответа не выполнена, однако шаг получает GREEN. Это **ISOLATED REPRO**: Test…01/02; не результат реального кандидата или полного target.

Корневая проблема этой группы — новый matcher считает частичное pattern-match достаточным, не установив полную Source-форму и типы. Тот же код не обеспечивает exact-empty-object. Отдельно остаётся прежняя неполнота whole-step bindings Б1: provisional bound map применяется до проверки matched (`:123–126`), так что неудачная попытка может менять контекст; этот STATIC остаток не добавлен отдельным новым count. Рекомендация: полный Source-owned form/type guard и правильный whole/subset режим перед оценкой, exact empty objects, допустимые binding types и commit только целиком совпавшего шага. Никакого literal `if lesson==…` или выдуманного нового DSL из этого не следует; если выбранный вход не даёт необходимой проекции, это точный unexecuted gap, не permissive match.

### Н-С2. ASSERT оценивается из колонки expect вместо request

**Код:** `scenario_verdict.go:93–100`, helper `:483–535`. **Норма:** общий README:232,255–256; actual J `Platform/01-store/acceptance/1/scenarios.tsv:17` содержит ASSERT request и пустой expect. Норма допускает в expect пусто либо ok; выражение находится в request.

После нормального трёхшагового Source precursor новое valid-grammar `ASSERT $a == $a` с пустым expect должно совпасть. Диспетчер передаёт helper именно item.expect, получает not_executed/assertion и не выполняет законное утверждение. Actual Source ASSERT с пустым/ok expect попадает в ту же ветвь. **ISOLATED REPRO:** Test…04; метод00 перед ним подтвердил весь нормальный precursor и три записи.

Есть смежная латентная ошибка helper: в pairwise `$a != $b` seen заполняется только правыми операндами (`:488–502`), а левый пропущен. Отдельный helper control сначала принял разные строки, затем ошибочно принял равные. Сейчас валидный Source не доходит до этой проверки из-за wrong-cell dispatch; поэтому этот результат не назван отдельным достижимым false-GREEN incident и не удваивает count. Рекомендация: разбирать выражение request и при исправлении сохранить все named terms/разность/типы и включить lhs в pairwise distinctness.

### Н-С3. Новый JSON-value comparator теряет различие чисел

**Код:** `run_vectors.go:543–559`, используется также matcher сценарием через vectorJSONEqual. **Норма:** wire.md:71 требует сравнение JSON по значению с сохранением типов; общий README:308,360, а P01 acceptance1 README:138 отдельно отличает exact-number comparison judge от binary64 fingerprint хранилища.

Положительные контроли:1 равно1.0; boolean true не равен числу1. Затем строгие JSON integer values9007199254740992 и9007199254740993 признаются равными: ParseFloat округляет оба к одному binary64. **ISOLATED REPRO:** Test…09. Это синтетическая граница опубликованного value grammar, не утверждение о таком конкретном actual J case или результате кандидата. Она не переносит judge arithmetic в business fingerprint и не добавляет ресурсного потолка.

Следствие — изменённое numeric значение может дать match. Рекомендация: сравнивать числовые JSON значения без потери точности при промежуточном binary64; отдельные owner-defined binary64 правила остаются у алгоритма владельца.
