## Что подтвердилось на нормальном пути

Положительный полный dispatch R42.P01 проходит реальный `plan → check_turn → reserve/admission → settle` с подставным sender. Sender смог взять тот же `tasks/.lock` с timeout=0: замок к этому моменту освобождён. R42.P09 и R42.P11 проверяют это же требование внутри sender при обычном resend и resend после release. Долгих реальных отправок не было, но динамическая попытка взять файл-замок подтверждает его границу в этих путях. Статически `with admission` заканчивается до возврата reserve, `automation.run` вызывает sender позже.

Пустые поддержанные боксы допускают выдачу; непустые Claude/Kimi/Codex, непустой `draft` и неизвестный composer запрещают её. Неизвестный composer не тратит ID. Обычный resend с пустым вводом проходит; другой набранный текст запрещает resend без добавления sends. После hold → снятие → release та же очередь возобновляется с сохранёнными sends и reopen_history; непустой ввод по-прежнему запрещает resend. Это новые исполнения на новых байтах, не переприсвоение прежних 31 результатов.

В проверенном сценарии первой выдачи новый admission действительно обнаруживает hold/cancel, закончившиеся после построения плана. Он сверяет task/attempt/definition и роль. Оставшаяся Б2 ниже относится к другой ветви kind, а не к неработающему замку первого reserve.

В cleanup helper результат успешного checker остаётся зелёным при отдельной ошибке уборки — это правильно: CheckingError не семантический отказ. Успешное удаление сверяется повторным `worktree list`; частичный add также доходит до очистки. На новом пути не вызывается глобальный prune. Fake Git был задан независимым жизненным циклом: множество регистраций, add/remove/list, отдельные returncode/timeout; это не настоящий Git fault experiment.

Изменённый main-check при failed fetch теперь не вызывает checker для якобы текущего head: сохраняет `last_fetch_error`, возвращает ошибку; `queues.main_check_events` порождает `main_check_stale`. R42.P22 подтвердил это с fake Git и пустым списком вызовов checker. Новая метка `report.tpl.html:1274` проходит в renderer через textContent. Для успеха/неуспеха cleanup main-check сохраняет поле в состоянии (`cammeta-main-check:66–75`); реальный timer не запускался.

Новая проверка `--no-check` разрешает override только заявленному architect (`tasks.py:1245–1246`); `checker_changed` — отдельная информационная отметка. Эти ветви прочитаны статически; отдельного runtime PASS для них не заявляю. Гипотеза о настоящем export-фильтре не возобновлялась. В1 о будущем происхождении checker не превращён в дефект.

## Что осталось от прежних причин

### Б2 — проверка состояния обходит повторную доставку

**Адрес:** [queues.py:903–908, Plan.reserve queue_resend](/home/pilot/review103/orch4-repeat-9befd52b/inputs/after/queues.py:903). Первое резервирование и его admission — строки 920–953. Caller — `automation.run:449–473`.

1. A уже один раз доставлена, но start отсутствует; прошёл интервал resend. Сессия остановилась, composer пуст.
2. Collector строит job `queue_resend` из готового к повторной доставке состояния.
3. Разрешённый architect выполняет `hold A` либо `cancel A`; команда атомарно заканчивается **до** резервирования повторной отправки.
4. `may_resend` перепроверяет mark и наличие своей строки во вводе; `check_turn` подтверждает пустой ввод. Текущее owner/cancelled не перечитывается.
5. Ветвь reserve для queue_resend сразу добавляет sends; admission с task lock находится только в другой ветви. Подставной sender получает строку.

Новые R42.F01/F02 дали `actual=1` вместо ожидаемых 0; свежее состояние — `ждёт владельца`/`отменено`. Это прежняя причина «управляющая команда до reserve не учитывается», сохранившаяся в resend; **новая Б за неё не посчитана**. Первая выдача, проверенная P13/P14, исправлена.

**Рекомендация:** линеаризовать и резервирование resend с командами управления. Перечитывать применимые ограничения уже выданной попытки, не копировать буквально READY-предикат первой выдачи, который запретил бы все resends. Замок освобождать до чтения внешнего терминала и send. Не обнулять историю для обхода проверки.

### С1 — старый снимок удержания закрывает доставку после release

**Адрес:** [queues.py:1157–1166, plan](/home/pilot/review103/orch4-repeat-9befd52b/inputs/after/queues.py:1157), `close_withdrawn:744–757`; `tasks.release:1662–1677`.

Нормальный последовательный сценарий теперь работает. Незакрытый порядок двух разрешённых актёров:

1. Доставленная A удержана; done-запись содержит системное снятие.
2. Новый collector plan получил из `task_source` модель, в которой owner=true, и ещё не вызвал close_withdrawn.
3. `release` под task lock убрала системное закрытие в reopen_history, затем owner из task-файла; команда вернулась.
4. Collector продолжает со старой моделью и вызывает close_withdrawn. Та снова пишет системное закрытие в closed, не сверяя текущий task под тем же lock.
5. На следующем проходе apply_reopened видит историю и обновляет бюджет, но новая closed-запись остаётся. Первая выдача ID уже потрачена, resend закрыт: jobs=[] несмотря на снятое удержание.

R42.F03 исполнил именно этот порядок через callback возврата task_source, без потоков и без live state. Свежий quick-model без ledger показывает READY; это **не** утверждение, что полная queue-модель готова: она сохраняет старую выданную попытку. Конкретный факт — нет ни queue, ни queue_resend job и снова присутствует закрытие после успешной release.

Это продолжение прежнего С1, а не новый счёт. **Рекомендация:** системное close_withdrawn и release должны иметь согласованный момент проверки/записи. Нельзя закрывать по уже устаревшему owner snapshot; re-read и изменение done должны быть согласованы с tasks/.lock. Не держать его на send.

### С3 — error/refusal gate не переносит cleanup_error вызывающему

**Адрес:** [tasks.py:1230–1235, _check_spec_gate](/home/pilot/review103/orch4-repeat-9befd52b/inputs/after/tasks.py:1230); CLI `cammeta-accept:47–50`.

1. Checker для Platform-правки завершился красным, код 2.
2. Remove не удался. Новый run_check_spec корректно возвратил `cleanup_error` с точным собственным путём и причиной; helper-часть исправлена.
3. `_check_spec_gate` в зелёной ветви переносит cleanup_error в acceptance. В красной и error ветвях строит Refused лишь из commit/error/code/log. Поле cleanup_error игнорируется.
4. Acceptance при отказе не записывается. CLI печатает текст Refused. В log попал stdout/stderr checker, а cleanup helper туда эту ошибку не писал. Таким образом, сведения об остатке теряются в штатном внешнем пути приёма.

В R42.R04b actual-message не содержит `synthetic remove failure`, хотя реальный новый helper с fake Git вернул её в result. Acceptance отсутствует — красный не принят, и такого нарушения не заявляется. Проблема — наблюдаемость/учёт остатка, не семантическая краснота. Это продолжение С3; main-check для того же поля имеет отдельную правильную запись в state.

**Рекомендация:** переносить cleanup_error также в отказ/ошибку и устойчивую квитанцию/log пути приёма. Не менять семантический verdict checker из-за уборки и не скрывать cleanup потому, что основной результат уже red/error.

## Новый дефект Н1 — С: свободная заметка отменяет собственный done

**Изменённый адрес:** [tasks.py:1653, _reopen_withdrawn](/home/pilot/review103/orch4-repeat-9befd52b/inputs/after/tasks.py:1653). Неизменённая публичная достижимость: `cammeta-done:26–40` → `queues.close_line:680–720`. Это чтение exact Git, не вызов установленного CLI.

Нормальная собственная closure с заметкой `normal explicit done` сохраняется после hold/release (R42.P23). Отличие нового контрпримера — только допустимый свободный текст заметки:

```text
снято с выдачи: закончил эту доставку сам
```

1. A выдана review103. Исполнитель законно закрывает **свою очередь** через close_line с этой однострочной заметкой. Это закрытие доставки, не фиктивный acceptance задачи; task может отдельно оставаться открытым.
2. Запись содержит `from: review103`, а не системный actor architect. Ни правила CLI, ни parse не запрещают такой текст заметки.
3. Architect удерживает и затем освобождает открытый task. Код обещает переоткрыть только системно снятые доставки, сохранив own done.
4. `_reopen_withdrawn` определяет системное снятие только по `note.startswith(WITHDRAWN_NOTE)`. `from` и фактическое происхождение closure не проверяются.
5. Собственное закрытие review103 удаляется из closed и переносится в reopen_history. Следующий plan создаёт queue_resend для уже явно закрытой доставки.

R42.F05 получил `closed={}` и job=`queue_resend` вместо сохранённой собственной closure. Все функции и записи относятся к временной копии 9bef. Прочитанный после независимого контроля авторский `test_tasks.py:408–417` подтверждает намерение сохранять own done, но проверяет только другую заметку и не исполнялся здесь.

**Причина:** свободная диагностическая заметка стала признаком происхождения управляющего события. Это новая регрессия функции reopen: старый release вообще не удалял closure. Она отличается от продолжающегося С1, где правильное системное снятие закрывается повторно из stale snapshot. Не требуется недоверенный пользователь или подмена --from; используются легальные actor и текст.

**Рекомендация:** использовать доказанный признак системного снятия, а не префикс свободной заметки. Как минимум собственная closure от исполнителя не должна превращаться в системную из-за note. Сохранить историю и существующий запрет самоприёма; публичную новую грамматику задач отчёт не предлагает.
