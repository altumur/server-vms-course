# Ревью ADR-0083 доп. (40) и (41) — Claude

Предмет: `origin/main` — `f79a54cde` (доп. (40)), `fd6e13733` (доп. (41)). Сверено с доп. (37)–(39) ADR-0083,
ADR-0087 доп. (7), ADR-0092, README `cammeta-acceptance` (поиск по словам) и моим ревью доп. (39) (`c3b739989`).
Код реализаций не читал. Статическая работа шла в окне P/03. После CLOSED сделаны два лёгких наблюдения машины:
- опыт `taskpolicy -b` с дочерними процессами — секунды;
- один `ps`.

## Вывод

**(40)** упраздняет линию MiniMax-Go без противоречия по существу. Но:
- три места в других ADR по-прежнему её называют, а ADR-0087 доп. (7) п. 5 ставит на неё условие перехода к В7 (Е-3);
- «раннер теперь пишет Claude» расходится с доп. (39) п. 1 и 3(б): там объём раннера пишет MiniMax (Е-2);
- дыра в независимости чтения стала шире, чем в (39). Python, Go и раннер теперь делает один и тот же конвейер
  «ведущий Claude + исполнители MiniMax», нормы и векторы пишет тоже Claude. Единственный читатель другой модели — Kimi,
  и только для серий раннера, не для прочтения норм реализациями (Е-1).

**(41).** `taskpolicy -b` для CPU годится: наследование дочерними проверено. Но правило:
- не связывает исполнителей MiniMax — их `claude -p` с инструментами идут на этой машине с обычным приоритетом;
- «один процесс» не определено: на линию или на машину, и считаются ли процессы исполнителей (Е-4);
- не ограничивает то, что `taskpolicy` не трогает: память, диск и кэш, порты и сокеты тестов, `GOMAXPROCS` (Е-5).

Откат по классу «нагрузка/время» не измерим. Классов «нагрузка» и «время» в README раннера нет, журнала фоновой
работы генераторов нет, класс ставит раннер — код одной из линий под ведущим Claude (Е-6).

Блокирующих — 2 (Е-1, Е-4), существенных — 4 (Е-2, Е-3, Е-5, Е-6), мелких — 3 (Е-7…Е-9).

## Доп. (40)

### Е-1. Блокирует. Независимость прочтения нормы: обе реализации и раннер — один конвейер

**Где.** Доп. (40) пп. 2, 3; доп. (38), абзац причин («вторая модель делает прочтение нормы независимым»); доп. (39) п. 3(в)
(«для сравнения меняем одну переменную»).

После (40):

| звено | кто |
|---|---|
| нормы, векторы | «Спецификация» — Claude |
| Python | ведущий Claude, объём — MiniMax |
| Go | ведущий Claude, объём — MiniMax |
| раннер | ведущий Claude (доп. (39) п. 3(б)), объём — MiniMax (или Claude, Е-2) |
| чтение серий | «Спецификация» (Claude) + Kimi |

Совпадение Python × Go на сценариях и в смешанной матрице больше не свидетельство независимого прочтения: обе
реализации раскладывает одна модель, пишет одна модель. Довод доп. (38) и довод доп. (39) п. 3(в) («меняем одну
переменную») сняты, но (40) этого не говорит. Kimi читает протоколы серий, то есть проверяет, что раннер верно оценил
прогон. Как реализация прочла норму, Kimi не проверяет. Моя находка Д-1 к доп. (39) этим усиливается: тогда хотя бы Go
был другой организацией работы, теперь и её нет.

**Предложение** — одно из трёх:
- (а) у одной из линий исполнители другой модели (Kimi; Codex после 2026-11-02);
- (б) независимый читатель другой модели делает раннюю проверку точного пакета по пунктам договора (доп. (37) п. 5) для
  каждого места «чтением» обеих линий;
- (в) записать это **принятым риском** решением владельца и убрать из доп. (38) довод о независимом прочтении.

### Е-2. Существенно. «Раннер теперь пишет Claude» против доп. (39) п. 1, п. 3(б)

**Где.** Доп. (40) п. 3.

По доп. (39) п. 1 ведущий «код пишет только малыми правками при слиянии — объём пишут исполнители», п. 3(б) — раннер
«так же». Тогда объём раннера пишет MiniMax, и «раннер пишет Claude» неверно. От этого зависит, кто «не автор раннера» по
модели. Если автор — MiniMax, то «Спецификация» (Claude) — другая модель, но та же, что ведущий раннера.

Ещё два пробела:
- «Два CLEAN» из двух названных читателей — это единогласие; бывшие читатели (ведущий Python, генератор Go) из правила
  выпали молча. Нужно сказать: они читают и их не-CLEAN — вето, или не читают вовсе.
- Само правило серий так и не записано: что такое серия, что такое CLEAN, срок чтения. Это Д-2 к доп. (39); (41) п. 1
  говорит, что правила окна «жили в README раннера», но слова CLEAN в README `cammeta-acceptance` нет.
- Нет порядка на случай недоступности Kimi или лимита Claude у «Спецификации».

**Предложение.** «Раннер — ведущий Claude, объём — MiniMax (доп. (39) п. 1); чтение серии — два CLEAN: „Спецификация“
и Kimi, оба обязательны; ведущие линий не читают свои серии. Нет CLEAN одного из двух — серия не засчитана». И записать
правило серий целиком: в README раннера или решением.

### Е-3. Существенно. Линию MiniMax-Go по-прежнему называют три места

**Где.**
- ADR-0087 доп. (7) п. 5 и его правка (строки 177, 187–189): «линия MiniMax-Go проходит уроки 01–06 целиком сама»,
  «условие п. 3 для Go — уроки 01–06 одной реализации (Codex-Go, пока она есть, или MiniMax-Go)»;
- ADR-0092 `informed` — «MiniMax-Go»;
- ADR-0083 доп. (39) п. 4 — читатель «генератор Go (MiniMax-Go или Codex-Go)».

(40) п. 1 отменяет доп. (38) п. 1, 3 и уточнение п. 3, а ADR-0087 доп. (7) п. 5 не трогает. Условие перехода к В7 «для
Go — уроки 01–06 одной реализации» стоит на несуществующей линии.

**Предложение.** В (40) добавить: «ADR-0087 доп. (7) п. 5: Go — линия `cammeta-c-go` (ведущий Claude), уроки 01–06 одной
реализации — этого репозитория (доп. (39) п. 3(а))». В ADR-0092 `informed` — «c-go, c-python».

### Е-7. Мелко. Передача Codex-Go → ведущий в `cammeta-c-go` не описана

Для Python доп. (39) п. 3(а) задаёт передачу: коммит состояния, `GUESSES.md`, записка передачи, Codex новых задач не
берёт. Для Go (40) п. 2 говорит только «окно перезапущено». Доп. (38) п. 2 («Codex-Go доводит урок 03 и опоры 02, 05, 06»)
формально не отменён. Кто доводит урок 03 после окна P/03 по `e6b4d40`: Codex-Go или ведущий? Предложение: «передача
Go — как доп. (39) п. 3(а); доп. (38) п. 2 отменяется с момента записки передачи».

## Доп. (41)

### Е-4. Блокирует. Правило не связывает исполнителей, «один процесс» не определён

**Где.** Доп. (41) пп. 2, 3 («генерация исполнителями MiniMax… облако, машину не грузят»; ACK генератора).

Модель MiniMax — облако, но исполнитель — локальный процесс Claude Code с инструментами. На этой машине после CLOSED
`ps` показывает:
```
12384  pri 31  claude -p --dangerously-skip-permissions Ты исполнитель. Прочитай и выполни задачу из файла .exec/TASK.md …
12198  pri 31  /bin/sh /Users/murat/w2c/cammeta-c-go-exec/c03-logmask-json/.exec/run.sh
```
Обычный приоритет, права без подтверждения. Его `go test`, `go build`, `pytest` идут здесь, и `taskpolicy -b` их не
касается, если обёртка `run.sh` не запущена через него. ACK даёт ведущий, но команды исполнителей он не исполняет.

Сколько это процессов: две линии × (ведущий + до двух исполнителей) = до шести сборок одновременно. «Одним процессом» —
на линию, на машину или на сессию?

**Предложение.**
- «Один процесс сборки или тестов **на машину**» — общий замок-файл, который берут все генераторы и исполнители;
- в OPEN исполнители стартуют только через `taskpolicy -b` (обёртка `run.sh` линии);
- ACK ведущего покрывает исполнителей его линии;
- при OPEN ведущий ставит исполнителей на паузу или проверяет, что их обёртка фоновая.

### Е-5. Существенно. `taskpolicy -b` отдаёт E-ядра, но не память, диск, порты и потоки

**Где.** Доп. (41) п. 2 («фоновый класс… уступает приёмке»).

Что проверено. Фоновый класс наследуется: `taskpolicy -b sh -c 'sleep 30 & sh -c "sleep 31" & wait'` — у родителя и обоих
детей `pri 4`, без `taskpolicy` — `pri 31`. Так что `go test` с дочерними бинарниками и компиляторами целиком в фоновом
классе. Для времени CPU этого достаточно: SUT в обычном классе на P-ядрах фоновую работу вытесняет.

Чего фоновый класс не ограничивает:
- **Память.** `go build` и тесты занимают гигабайты. Нехватка памяти — сжатие и подкачка у SUT — даёт задержки ровно
  там, где мерят `LOST_AFTER` и `@until`.
- **Диск и кэш.** Вывод сборки вытесняет страничный кэш. Записи будят `fseventsd`, `mds_stores` (Spotlight) в обычном
  классе — это уже не фон.
- **Порты, сокеты, пути `/tmp`.** Модульные тесты, которые слушают порт или создают сокет и lock-файл, могут столкнуться
  со стендом. Такой провал — ни «нагрузка», ни «время», и откат п. 4 его не ловит.
- **Потоки внутри процесса.** `go test -p 1` ограничивает число пакетов, но бинарник теста берёт `GOMAXPROCS` = все ядра
  (`t.Parallel`, горутины). «Один процесс» — не «одно ядро».
- **Тепло и общее питание SoC** при долгой нагрузке.
- **load1.** Фоновые потоки входят в load average. Шлюз п. 1 (load1 < 12, 180 с) действует только при открытии, а в окне
  load1 уже не мерило «чистоты» стенда.

**Предложение.**
- `GOMAXPROCS=2`;
- в OPEN не запускать тесты с сетью и сокетами (тег или пометка; Python — маркер);
- `TMPDIR` генераторов — свой каталог, не общий `/tmp` стенда;
- предел памяти через `ulimit -v`, если реализуемо, или правило «тесты с большой памятью — после CLOSED»;
- каталоги сборки — вне индекса Spotlight.

Для временных сценариев: раннер пишет в итог прогона фактическую задержку будильника или шага (насколько `@until`
сработал позже срока). Это мерило искажения, а не догадка.

### Е-6. Существенно. Откат п. 4 не измерим: классов нет, журнала нет, класс ставит раннер

**Где.** Доп. (41) п. 4.

1. **Классы.** В README `cammeta-acceptance` нет классов провала «нагрузка» и «время» (поиск по словам): «нагрузка»
   встречается только в «нагрузка и gate — по назначению Архитектора». Значит, классификатор ещё не определён.
2. **Основание.** Чтобы отнести провал к нагрузке, нужно знать, что в это время делали генераторы. Журнала их фоновой
   работы (кто, когда, чем) правило не требует. Без него «нагрузка» — догадка в обе стороны:
   - настоящий дефект аренды (`LOST_AFTER`) спишут на фон и повтором замажут;
   - провал от фона отправят генератору как «реализация».
3. **Кто ставит.** Раннер — линия под ведущим Claude (доп. (39) п. 3(б)), а генераторы, чья фоновая работа под
   подозрением, — тоже линии под ведущим Claude. Класс до GREEN ставится причинным разбором, не повтором (доп. (37)
   п. 3), а здесь «прогон повторяется» — повтор может стать основанием класса.

**Предложение.**
- Классы «нагрузка» и «время» записать в README раннера с признаками: задержка шага сверх допуска, load1 и давление
  памяти в момент провала по журналу выборок раннера.
- Общий журнал окна: каждая сборка или тест генераторов и исполнителей — строка «кто, команда, начало, конец» (через ту
  же обёртку, Е-4).
- Класс ставит раннер по правилу, утверждает «Архитектор» разбором. Повтор — отдельный прогон; исходный отчёт и его класс
  сохраняются (доп. (37) п. 3).
- Откат срабатывает при классе «нагрузка», утверждённом разбором, а не при любом провале по времени.

### Е-8. Мелко. Сирота SUT от прошлой приёмки

На машине работает процесс SUT P/02.1, запущенный 2026-10-21 14:51 (`ps`: шесть суток, родитель — `launchd`):
```
99701  ppid 1  /bin/sh -c cd /Users/murat/w2c/cammeta-diff/acceptance-b30c83e/impl-go-c91d7bc && ./bin/cammeta store --data /tmp/ca-g4c0hw7w/P-02.1/… --socket …/admin.sock …
```
Раннер после прогона не гасит дерево процессов. Сирота держит сокет и данные в `/tmp` и сам по себе — фон в каждом окне.
Предложение: к правилу окна — «CLOSED объявляется после проверки, что процессов стенда не осталось» (группа процессов
или каталог прогона). Самого процесса не трогал.

### Е-9. Мелко. Оформление

- (41) п. 2: «энергоэффективным ядрам» — верно для Apple Silicon; машина приёмки не названа.
- (41) п. 5: «отдельная машина или пользователь macOS» — пользователь macOS не разделяет ни память, ни диск, ни ядра.
  От Е-5 спасает только отдельная машина; это стоит сказать владельцу.
- (40) п. 4: «остальное доп. (39) — до разбора его ревью» — разбор ещё не записан. (40) уже меняет п. 4 доп. (39)
  (читатели), до разбора — тоже назвать.
