## Findings

### С1 — фильтр как артефакт не определён (missing definition, среднее)

- Где: доп. (3) п. 1, п. 2, п. 4.
- Цитаты: «Паспорт записывает C, M, J и **идентичность фильтра**» (п. 1); «J раннер принимает только для объявленной пары и проверяет её: **тот же фильтр над J даёт дерево M**, оба из C» (п. 2); «В M нет … **перечня фильтра**» (п. 4).
- Суть: проверка пары опирается на фильтр, но в тексте доп. (3) фильтр нигде не определён: какие пути он убирает (векторы/сценарии по доп. (1) — а также висячие ссылки на удалённое, маркеры, что-то ещё?), где он хранится, в чём его неизменность между выбором пары и проверкой, и по какому объекту считается записываемая в паспорт «идентичность фильтра». Делегирование п. 5 («Имена флагов и форму объявления пары выбирает раннер») покрывает способ объявления пары, но не состав и идентичность самого фильтра — а «тот же фильтр» без определённой идентичности невоспроизводимо. Это вход, без которого центральная проверка п. 2 не имеет точного смысла. Исправление не предлагается (конкретный флаг/поле/формат не выдумываю).

### С2 — равенство «фильтр над J = дерево M» без соглашения о маркере `SPEC_VERSION` (missing definition, среднее)

- Где: доп. (3) п. 2 и вводный абзац.
- Цитаты: «тот же фильтр над J даёт **дерево M**, оба из C» (п. 2); «Это **разные коммиты**, даже из одного коммита курса C» (вводный абзац).
- Контекст неизменных правил: `SPEC_VERSION` — корневой файл репозитория со значением пина: «The implementation repository has a root `SPEC_VERSION`» (`PROFILE.md`); в курсовых текстах маркер материализуется содержимым пина (`tools/normgen/launch_judge.py`: запись корневого `SPEC_VERSION` значением `spec`; `СЕССИИ.md`: «`cammeta-specs` на коммите `8c9b221` (`SPEC_VERSION`)»); `spec_version` профиля — «String of exactly 40 hexadecimal digits naming the specification export commit».
- Суть: если маркер входит в сравниваемые деревья, два разных коммита M и J не могут дать байтово равные деревья (маркер каждого называет свой коммит), и равенство п. 2 достижимо только с явным соглашением — маркер исключён из сравнения или переписывается фильтром. Доп. (3) такого соглашения не содержит. Точный механизм маркера в дереве выгрузки из курсовых текстов однозначно не выводится (раннер внешний — предел ревью), поэтому это зафиксировано как незакрытый пункт определения, а не как доказанный дефект.

### М1 — «оба из C»: механизм проверки принадлежности C не назван (missing input, мелочь)

- Где: доп. (3) п. 2 («…оба из C») и п. 1 («Две неизменяемые выгрузки **из одного C**»).
- Суть: паспорт записывает C, и проверка пары называет принадлежность C частью проверки, но способ машинной сверки не указан. В проекте есть подходящий механизм — маркеры доставки: «The profile and repository pin name the export's Git commit, not the source-course commit recorded in delivery `COURSE_COMMIT` markers» (`PROFILE.md`), — однако доп. (3) на него не ссылается. Без этого ссылочного закрепления заявленное в вводном абзаце «подставить C нельзя» опирается на незаписанную деталь: J' из иного курсового коммита C' с совпадающим невекторным содержимым формально удовлетворял бы «фильтр(J') = дерево M».

### М2 — «В M нет объектов J» при M ⊂ J (wording, мелочь)

- Где: доп. (3) п. 4.
- Цитата: «В M нет **объектов J**, ссылок на него, перечня фильтра и хэшей случаев судьи».
- Суть: по собственному п. 2 M — проекция J («фильтр над J даёт дерево M»), то есть каждый объект M встречается и в J; буквальное чтение «нет объектов J» неверно. Смысл читается из контекста — «нет объектов, уникальных для J» (векторы, сценарии, сырые отчёты, хэши случаев), — но для нормативного текста граница изоляции стоит формулировать точнее.
