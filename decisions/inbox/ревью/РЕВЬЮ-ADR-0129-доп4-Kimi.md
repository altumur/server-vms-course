## Свои находки

### С1. П. 4 противоречит Ф6 на названном же прецеденте sealing.go

Ф6: «Не из запрещённого списка Т5». Список Т5 (основной текст, п. 2):
«алгоритм по ожидаемым ответам, **криптография по векторам**, распределённая
корректность по локальной машине». П. 4: «Прежние функции `slotname.go`,
`sealing.go` удовлетворяют условиям и остаются».

`sealing.go` — криптография: конверт `enc:v2`, AES-256-GCM, nonce, AAD
(`common/contracts/sealing.md`), и судится она векторами
(`common/vectors/sealing/open.tsv`; сам контракт ссылается на кейс
`open.tsv noncanonical_ct`). Это буквально пункт запрещённого списка. При
прямом чтении Ф6 утверждение п. 4 «удовлетворяют условиям» неверно.

По смыслу запрет Т5 писался против **генерации** криптографии из векторов
(модель подгоняет выход под ожидаемые ответы, не понимая примитива). К ручной
общей функции этот риск не относится — криптография как раз должна быть
единой, написанной один раз и судимой независимо. Но поправка этого различия
не делает: Ф6 переносит список генераторов на функции без пересмотра
мотивировки.

Правка: в Ф6 записать, какие пункты Т5 переносятся на ручные функции
(«алгоритм по ожидаемым ответам» и «распределённая корректность по локальной
машине» — да; «криптография по векторам» — нет, с обоснованием), либо в п. 4
назвать sealing сознательным исключением. Иначе первый же новый кандидат-
криптография (или пересмотр sealing) даст двум читателям противоположные
решения по одному тексту.

### М1. Ф2 «нужна двум урокам и больше» не проверяемо в момент решения

Первая ветка Ф2 — предсказание: второй урок ещё не запускался, когда функцию
кладут для первого. Прецеденты (slotname — P/03 и P/04; sealing — P/02.4,
P/03.5, P/06.2, M11) подтвердили нужность постфактум. Для нового кандидата
при первом уроке первая ветка недоступна, остаётся только «точка срыва»;
не сказано, кладётся ли функция по прогнозу читающих уроков или ждёт
фактического второго потребителя.

Правка фразой: «два урока» засчитываются, когда договор функции в норме
называет читающие уроки (как уже делает sealing.md разделом Readers) — тогда
условие проверяется статически, до запуска второго урока.

### М2. Не названа синхронизация функции с уточнением нормы

П. 3: «Норма этого места всё равно уточняется (п. 1)». Уточнение по журналам
линии без пакета может менять договор, по которому функция написана (Ф1).
Кто правит функцию вслед за нормой, по какому сигналу и как это видно линиям
(версия пакета, SHA выгрузки в паспорте функции) — поправка молчит. Паспорт
функции из предложения Claude (С1) с SHA прочитанного закрыл бы и это;
без него — дыра.

## Ответы на особые вопросы поручения

### Достаточно ли Ф1–Ф6, чтобы функция не стала посевом готового кода

Нет, и это показано дважды независимо (Codex С1, Claude С1): условия не
задают границу объёма и закрытости — функция может покрыть все обязанности
этапа, и для линии это неотличимо от посева. Ф3/Ф4 — свойства происхождения,
а не того, что получает линия. Моя С1 добавляет симптом: условия не отлажены
даже на двух собственных прецедентах п. 4. Поддерживаю оба предложения:
явная граница обязанностей (Codex) и Ф7 «закрытость, не этап, паспорт»
(Claude).

### Честен ли п. 3 (мера догадок по месту — у линии без пакета)

По замыслу честен, по тексту — с оговорками Codex С3 и Claude С3: «место»
шире функции (интеграция остаётся модели и продолжает давать догадки),
линии без пакета сейчас нет, «модель эту часть нормы не читает» слишком
широко — договор функции модель читает обязательно.

Моё дополнение — эмпирическое. Прецедент sealing уже показывает нужный разрез:
его контракт сам ссылается на догадки линий о **договоре** общей функции
(«guess of stage C S-001» — канонический base64url, «S-002» — форма ошибок,
«S-006» — U+FEFF в kid). Эти записи были и пошли в уточнение нормы. По
буквальному п. 3 место sealing «выпало бы из меры» вместе с этими догадками.
Значит, исключаться должно тело алгоритма, а догадки об интерфейсе и об
оставшейся интеграции — оставаться в мере. Формулировка Codex С3 («исключать
конкретные переданные обязанности, не всю норму») подтверждается историей.

### Годится ли ядро хранилища P/01.1 под Ф1–Ф6

Поддерживаю Claude С5 и таблицу Codex: **целиком — нет, частью — не сейчас.**

- Ядро целиком: Ф2 держится на одном срыве слабой модели (MiniMax не мера,
  ADR-0129 Consequences); durability и консенсус — Т5 и «Implementation
  decides» (выбор, который функция сделала бы за все линии — Claude С4).
- Чистая функция применения над снимком: Ф1 сейчас не выполнено — §4 разбора
  сам называет типы «эскизом, не публичным ABI», а §6 прямо: «внутренний тип
  плана не предписывает публичную сигнатуру». Оценка судьи 1180–1980 строк
  против выхода 245–465 (разбор §7.4) — отношение 2,5–8×; даже по правилу
  доп. (2) п. 2 (судья вдвое больше выхода → решение «Архитектора») это
  прошло бы только отдельным решением, и Claude С6 верно замечает, что
  правила цены для функции пока нет вовсе.
- Сам разбор требует четырёх решений до любых forms/code (§9) — его автор
  не считает работу достаточной для кладки. П. 5 доп. (4) правильно
  откладывает решение.

Порядок, который следует из всех трёх ревью: сначала уточнение нормы P/01.1
(п. 5 основного текста, доп. (2) пп. 6–9, spec103), затем прогон линии без
пакета на уточнённой норме, и только если срыв на ядре останется — возврат
к вопросу с конкретным договором чистой функции в норме.

## Что сходится (проверено самостоятельно)

- Прецеденты п. 4 по Ф1/Ф2: slotname — договор `common/contracts/slot-name.md`
  с читающими уроками P/03, P/04; sealing — `sealing.md` с Readers P/02.4,
  P/03.5, P/06.2, M11. (По Ф6 — см. С1.)
- ADR-0083 доп. (86) действительно уже допускает ручной код пакета (строгий
  JSON-разборщик «руками один раз на язык»), так что доп. (4) оформляет
  существующую практику, а не вводит новую.
- Разбор ядра методологически аккуратен: L/B/C/K-метод §7.1 воспроизводим,
  остаток модели не измерялся, оценки §7.4 честно помечены уверенностью.
