# Ревью норм платформы ADR-0119 (0)–(8), второй ревьювер («Спецификация VMS»)

main 9aa823051. Доля платформы — 68b06cd69 и правки ревью a6f229f84 (`spec/0119`, `spec/0119-fix`). Прочитаны по тексту main:
- P/06.7 Н1.15 «Проверка без входа `POST /domain/verify`» и строка таблицы дверей;
- P/08.4 Н1.2а, Н1.3а (`supervision` роли), Н1.3б (таблица ролей члена, `limit`);
- договор сторожевой и передачи: «Надзор», «Предел попыток», перечни заголовков `door.pass`;
- договор пересылки: «Билет на пересылке», строка `X-W2C-Ticket`;
- P/09.1 `member_roles`;
- OpenAPI консоли: `/domain/verify`, `VerifyInput`, `VerifyAnswer`.

С ADR сверены доп. (0)–(8) по пунктам. Доп. (9)–(12) (`writes_via`) — вне этого ревью, у них свой отчёт.

**Счёт: Б 0, С 2, М 2.**

Исполнено верно:
- дверь только по билету с записью `domain/verify` в `calls`; сеанс и билет без человека — `403`; автор — человек токена пересылки;
- домену — ровно `{user, password}`, `X-W2C-Ticket` ставит только консоль кластера, верят ему только на соединениях `console` и
  `domainconsole`, извне он снимается;
- ответ домена без токена и `Set-Cookie`; неизвестному и выключенному — тот же `401 refused` по фиктивному хешу, как у входа;
- `need {cap, sub, units}` — без имён VMS, `VERIFY_UNITS_MAX` = 256, отказ формы до пересылки и не в счёт предела;
- `may` проверенного — копии сторожевой, `glass: false`, `disabled: []`, `iat` — момент ответа домена;
- `unavailable` хоть одной единицы — `503` целиком, частичного ответа нет;
- надзор: `required` и `ok` одной функцией, в пользу надзора при нечитаемом, `ok = false` при нечитаемой копии;
- `X-W2C-Supervision` на каждый пересланный запрос, `-` и `*`, у второго вида — по человеку билета;
- роли с надзором всегда в таблице члена, отметка `unreadable` у держателя и в копии P/09.1; `409 roles table too large`;
- своя роль супервизоров допустима, `400 unknown role`, `409 role referenced`.

## С

**С1. Общий потолок `ceiling` даёт отказ в обслуживании входа всего домена через `backend`, а пределом это не названо.**
Договор сторожевой, «Предел попыток» `verify`: «отказы идут и в `ceiling` процесса `domain` вместе с входом — потолок общий».
`ceiling`: «20 отказов всех ключей за последние 900 с → каждому ключу не чаще одной попытки в 60 с».
- Ключ проверки — (автор, имя), адрес не судится. Автор с правом создать выгрузку перебирает имена супервизоров. 5 отказов на
  ключ — `429` по ключу, но 20 отказов по четырём именам за 15 минут включают `ceiling`.
- После этого каждый человек домена входит не чаще раза в минуту, пока окно не очистится. Это и вход администратора.
- Доп. (5) п. 4 выбрал общий потолок, чтобы проверка не удваивала бюджет подбора. Цена — что один оператор торможением запирает
  вход всем. В нормах она не названа ни пределом, ни сигналом.

**Предложение.** Одно из двух.
(а) Назвать предел в договоре рядом с `verify`: «проверка через `backend` расходует потолок входа всего домена; 20 неудачных
проверок за 900 с замедляют вход каждому». Плюс строка аудита `domain.verify.limited` с причиной `ceiling` — оператор видит, кто
выжег потолок.
(б) Свой потолок проверки, по автору: например, 20 отказов автора за 900 с — `429` только ему; общий `ceiling` проверку
не считает. Подбор при этом не удваивается: ключ (автор, имя) по-прежнему 5/900 с, а у автора свой предел сверху.
Рекомендую (б): автор проверки всегда известен, а вход через консоль домена от него не зависит.

**С2. OpenAPI `/domain/verify` не объявляет ответов процесса домена, которые P/08.4 Н1.2а и доп. (1) п. 3 называют.**
Доп. (1) п. 3: «ответы — как у входа целиком (`disabled`, `429`, `503`, `409 deposed`, `413`)». P/08.4 Н1.2а: «смещённый держатель
— `409 deposed`; тело больше `LOGIN_BODY` — `413 too large`». P/06.7 Н1.15: «ответ процесса не 200 — как пришёл».
- В OpenAPI консоли у `POST /domain/verify` есть только `200`, `400`, `401`, `403`, `429`, `503`. Ни `409`, ни `413` нет.
- Реализация `backend` пишется по контракту: `409 deposed` на проверке супервизора она не ждёт. При смене держателя домена
  выгрузка с надзором получит необъявленный ответ — это не «недоступно», а неопределённость.

**Предложение.** Добавить `409` (`deposed`, ссылка на `Refusal` урока P/08) и `413` (`too large`). У `backend` (V/11, при контракте
`/exports`) `409 deposed` переведу в `503`: держатель сменился, повторить позже.

## М

**М1. `scope` и `count` предела попыток не согласованы с `verify`.**
- `scope`: «свой счёт у каждой двери». `verify` ниже: потолок общий с входом. Строку `scope` стоит уточнить: «ключи — свои у каждой
  двери; `ceiling` процесса `domain` — общий у `/api/login` и `/api/verify`».
- `count` перечисляет только неверную пару входа и шаг аварийного входа. Отказ проверки (`401` по паролю) тоже считается — в
  `count` его нет, он назван только в `verify`.

**М2. `VerifyInput.need.units` — без шаблона.** Норма: `units` — `<sub>/<id>`. В схеме — строка `minLength: 3`. Строку без `/`
схема пропустит, отказ придёт уже из `may` (`deny`: «строки единицы нет»), а не `400` формы до пересылки. Шаблон вида
`^(?:[a-z][a-z0-9_-]{0,31}/[^/]+)$` закрепит то, что норма называет формой.

## Вне ревью

Доля VMS ADR-0119 — у меня: V/08.6 (`supervised_by`), V/11.8 (`Role.supervision`), V/08.8. Перевод `/exports` с супервизором — при
закреплении контракта форка. Ответ на С2 (`409 deposed` → `503`) внесу туда же.
