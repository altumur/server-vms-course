# Черновик: новые директивы стенда для приёмки P/02 (установщик)

Черновик к словарю директив и дверей общего README приёмки (`Platform/common/acceptance/README.md`, раздел
«Словарь директив и дверей», таблица `| Форма | Смысл | Урок |`) и к формату `puts.tsv` главы 2.3
(`Platform/02-installer/acceptance/3/README.md`, раздел «puts.tsv», «Форма файла»). Ничего в курсе не правится: это
предложение «Спецификации» — две директивы, которых в словаре нет, а норма требует проверяемого свойства.

Новые строки (в форме словаря: `форма | смысл`; колонка «Урок» — как в общем README):

| Форма | Смысл | Урок |
|---|---|---|
| `@rev-max <sub> [<форма>]` | поднять `rev` строки манифеста `platform/manifest/<sub>` (и её метки `/rev`, и её вида `canonical/<форма>`) до 9007199254740991 — записью через `admin.sock` экземпляра, прочие поля байт в байт прежние | P/02.3 (2026-10-30) |
| `@shell-put <sub> <файл>` | заменить байты файла оболочки `<sub>.shell.html` (рядом с файлом манифеста) байтами файла `<файл>` — в рабочей копии каталога установок | P/02.3 (2026-10-30) |

Подробности — по каждой директиве ниже.

---

## 1. `@rev-max <sub> [<форма>]`

**Зачем (место в норме).** P/02.3 Н3 «Смена манифеста» — «строка есть, прежняя rev = 2^53 − 1 (не «без изменений») → отказ
до любой записи: код 2, stderr называет ключ строки и rev»; Н4 — «`manifest put`: новая ревизия при `rev` строки =
2^53 − 1 … (тот же манифест — «без изменений», код 0)»: код возврата 2, отказ ДО любой записи — строка, вид и метка прежние;
Н5 — «Граница `rev` проверяется чтением: при `rev` строки 2^53 − 1 тот же манифест — «без изменений», код 0, новая ревизия —
отказ до любой записи, код 2 … `puts.tsv` ставит установки в свежее хранилище и `rev` до границы не доводит». Иными словами:
граница `rev` проверена быть не может — стенд её не доводит, а «проверяется чтением» означает, что исполненной проверки нет.

**Форма.**

```
@rev-max <sub> [<форма>]
```

`<sub>` — имя манифеста (`name`), чью строку поднять; `[<форма>]` — форма вида (по умолчанию `1`, текущая форма по
П/02.2 Н1.2). Директива пишет через `admin.sock` экземпляра (дверь `admin` общего README приёмки; операции P/01.1):

1. читает строку `platform/manifest/<sub>`; если её нет — директива не исполняется (отказ раннера: подготовка не удалась);
2. читает метку `platform/manifest/<sub>/rev` и вид `platform/manifest/<sub>/canonical/<форма>` (если вида нет — вид не
   трогаем; метки нет — метку не создаём: директива не пишет то, чего не было);
3. в каждой прочитанной строке меняет ТОЛЬКО поле `rev` на 9007199254740991 (2^53 − 1), прочие поля (yaml, shell, sha256,
   form, manifest) — байт в байт прежние; записывает с `cas` по прочитанной версии.

**Ожидание.** `ok` — директива исполнена (это действие раннера, ответа хранилища в словаре нет). Дальше строки случая
исполняются как обычно, и норм-ожидания наступают сами:

| состояние после `@rev-max` | следующая установка того же манифеста | следующая установка ИЗМЕНЁННОГО манифеста |
|---|---|---|
| строка, метка и вид с `rev` = 9007199254740991 | «без изменений» (те же yaml и shell; вид текущей формы есть, читается и равен проекции) → код 0, `rev` не растёт | отказ до любой записи: код 2, строка, вид и метка прежние; stderr называет ключ строки и `rev` |

**Что требуется от реализации/раннера.** От реализации — ничего: это штатная запись через `admin.sock` (P/01.1, дверь
`admin`). Раннер: умеет читать и писать строку по `admin.sock` с `cas`; подставляет `<форма>` вида; различает «вид есть» и
«вида нет». Оговорка для владельца: поднимать ли `rev` и у метки, и у вида. Предложение черновика — поднимать у всех
трёх (тогда состояние ровно такое, какое было бы после честной установки с ревизией 2^53 − 1, и ветка «без изменений»
срабатывает по существу). Альтернатива — поднимать только `rev` строки: тогда вид и метка отстают (допустимое состояние:
«метка ниже строки — не смена»), но реализация, сверяющая `rev` вида с `rev` строки, уйдёт в другую ветвь Н3 — выбор
владельца.

**Кто проверяет.** Черновик B02 (`черновики/P02/B02-rev-max.tsv`): строка `rev_max_same` — та же установка при
`rev` = 2^53 − 1 → код 0, `rev` 9007199254740991; строка `rev_max_changed` — изменённый файл → код 2, `rev` прежний.

## 2. `@shell-put <sub> <файл>`

**Зачем (место в норме).** P/02.3 Н3 «Смена манифеста» — второй шаг: «shell (файл `<sub>.shell.html`) с атрибутом `on…=` в
любом теге → отказ: код возврата 2, stderr называет файл и атрибут; до чтения каталога (P/06.5 Н1.1 page)»; Н1.5 — «Одинаковые
yaml и shell — «без изменений», rev не растёт; shell сравниваются по байтам, отсутствие равно пустому», и форма строки:
поле `shell` — «источник — файл `<sub>.shell.html` рядом с файлом манифеста, файла нет — поле не пишется»; Н4 — строка
«`manifest put`: оболочка `<sub>.shell.html` с атрибутом `on…=`»: код возврата 2, stderr называет файл и атрибут; П/02.3-01 —
«тот же файл снова — «без изменений» (rev 1), дальнейшее изменение поднимает `rev` на один». В корпусе приёмки глав
2.1–2.5 нет НИ ОДНОГО файла `.shell.html` — все три свойства оболочки не проверяются ничем.

**Форма.**

```
@shell-put <sub> <файл>
```

`<sub>` — имя манифеста, чью оболочку меняем (по Н1.5 имя файла оболочки — `<sub>.shell.html`, то есть по ИМЕНИ манифеста,
а не по имени файла манифеста); `<файл>` — файл с новыми байтами оболочки (из каталога установок, как файлы установки).
Директива заменяет байты файла `<sub>.shell.html` в рабочей копии каталога установок байтами файла `<файл>`.

**Ожидание.** `ok` — файл заменён (действие раннера). Следующая установка того же манифеста берёт новую оболочку: если она
отличается по байтам от прежней, установка не «без изменений» — новая ревизия (`rev` + 1), вид переписывается, метка
догоняется; если в новой оболочке есть атрибут `on…=` — отказ установки (код 2), файл и атрибут в stderr.

**Что требуется от реализации/раннера.** От реализации — ничего: установщик сам читает файл оболочки рядом с файлом
манифеста. Раннер: (1) у него должна быть РАБОЧАЯ КОПИЯ каталога установок на каждый случай — иначе подмена оболочки
из одной строки таблицы изменит её для других строк (в главе 2.3 каждая строка и так получает новое хранилище — копия
каталога установок логична туда же); (2) он обязан класть рядом с файлом манифеста файл `<sub>.shell.html` — иначе
установщик оболочку не найдёт, и случай станет «установкой без оболочки» (в норме это допустимо, но не то, что проверяется).

**Кто проверяет.** Черновик B03 (`черновики/P02/B03-shell.tsv`): `shell_onclick` — оболочка с `onmouseover=` → код 2,
строки нет; `shell_same_twice` — та же оболочка при повторной установке → код 0, `rev` 1; `shell_changed` — подмена
оболочки → код 0, `rev` 2.

## Сводка: что требуется от владельца словаря

1. Внести две строки в словарь директив (формы выше). Куда именно: по общему README «Одно определение на модуль…
   урок, вводящий новую, добавляет строку сюда» — в общий словарь с уроком `P/02.3`; но `@view-delete` и `@view-spoil`
   живут не в общем словаре, а в README приёмки главы 2.2 («Директивы»). Выбор — за владельцем; черновик предлагает
   общий словарь (директивы модульные, а не главные), с указанием в README главы 2.3.
2. Формат `puts.tsv` главы 2.3 директив не знает: «Форма файла» главы 2.3 говорит «имена файлов `puts/<имя>.subsystem.yaml`
   через один пробел, по порядку установки». Нужна правка: в поле `puts` допускаются и директивы, между файлами; первый и
   последний — файл (как в главе 2.2). Также нужна оговорка про изоляцию: рабочая копия каталога `puts/` — на каждый случай
   своя (иначе `@shell-put` и `@rev-max` влияют на соседние строки).
3. Решить по `@rev-max`: поднимать ли `rev` у метки и у вида (предложение — да, у всех трёх) и как поступать, если вида или
   метки нет (предложение — не создавать).
4. Согласовать форму `@shell-put`: имя оболочки — по ИМЕНИ манифеста (`<sub>.shell.html`), а не по имени файла манифеста;
   это следует из Н1.5 главы 2.3 и должно быть сказано в README главы 2.3 (куда класть файл оболочки при установке).
