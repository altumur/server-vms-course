# Черновик B07 — обратные чтения `must_match`: выведенные чтения общей проверки строки (вариант манифестов).

# Что проверяет: чтение, которое заказчик (`vb`, объявивший `worker.creates` на строки `va/items`) получает не из своих
#   объявлений, а из ВЫВОДА прав по общей проверке строки, — а именно чтение семьи каталога `vc/links`, чьё поле `of`
#   имеет `ref` на таблицу адресата (`va/items`) и `must_match`. Это та ветвь, которой в учебных манифестах нет и которая
#   в приёмке не покрыта.
# Место нормы:
#   - Platform/02-installer/spec/02.5-installer.norms.md Н1.4, строка `<s>worker`, графа «read сверх своих write»:
#     «чтения общей проверки строки по `worker.creates` — выводятся из объявления (P/06.1 Н3 «Общая проверка строки»):
#     цели `ref` и `must_match` полей адресата `<ref>/*` и семьи каталога, чьё поле с `ref` на таблицу адресата и
#     `must_match`, — `<их sub>/<семья>/*`»;
#   - чеклист П/02.5-05 главы 2.5: «…выведенные чтения общей проверки строки…; обратные чтения `must_match` — чтением
#     (в учебных манифестах такой ссылки нет)»;
#   - договор проверки строки (Platform/common/contracts/row-check.md), раздел «Идентификатор» `ref_and_must_match`:
#     «в обе стороны… создание или правка единицы, которая сама — цель, проверяет живые единицы и строки таблиц каталога,
#     чьё поле с `ref` на её семью и `must_match` называет её»; раздел «Чтения проверки»: «Чтения проверки — цели `ref` и
#     `must_match` самой строки и строки каталога, чьё поле с `ref` на эту таблицу и `must_match` её называют»; порядок
#     проверок П5: «прямые ref / must_match самой строки → обратные must_match (строки, которые ссылаются на неё)»;
#   - кто выполняет проверку: дверь единиц и таблиц консоли (P/06.1 Н3) и библиотека заказчика воркера (P/03.6 Н1.6) —
#     одна и та же проверка над одной формой строки (договор, вступление).
# Место приёмки: Platform/02-installer/acceptance/5, раздел «Варианты манифестов» — каталог `variants/<вариант>/` с
#   файлами `*.subsystem.yaml` (каталог манифестов варианта) и `expect.tsv`; формат `expect.tsv`: UTF-8, LF, поля через
#   TAB, строки с `#` пропускаются, заголовок `role<TAB>action<TAB>key<TAB>expect`, дальше по строке на пробу:
#   роль файла прав, действие `read|write|delete`, ключ строки, `allow|deny`. Исполнение: инструмент вывода прав
#   реализации (Н2) на каталоге варианта с развёртыванием `dep`, затем свежий экземпляр хранилища с этим файлом прав,
#   затем пробы сокетом роли: `read` — `GET /v1/get?key=…`, `write` — `put` с `items: {"p":"1"}`, `delete` — `delete`;
#   `allow` — только подтверждённый успех (у чтения 200 формы `Row`, у записи и удаления 200 `Written`), `deny` — 403
#   `forbidden`; сокета роли нет — то же, что 403; каждая проба — на своём свежем экземпляре.
# Существующие директивы: не требуются — вариант манифестов исполняется не сценарным файлом, а таблицей проб.
# Новых директив не требуется.

## Оборудование варианта (`черновики/P02/variants/v7-must-match/`)

| Файл | Что объявляет |
|---|---|
| `va.subsystem.yaml` | адресат: `unit.rows: items`, `unit.id: name`; поля `name`, `code` (обязательное — подстановка ключа заказа), `zone`, `shelf` (`ref: va/shelves`, `must_match: {zone: zone}`); таблица `shelves` (`key: name`, поля `name`, `zone`) — цель прямой ссылки |
| `vb.subsystem.yaml` | заказчик: поля `name`, `code` (своё `code` — значение подстановки `{code}` в создаваемой строке); `worker.creates: [{sub: va, rows: items, key: "{code}"}]` — префиксный образец `va/items/vb-*` (создание и правка строк своего заказа), только write, без delete |
| `vc.subsystem.yaml` | третий манифест: таблица `links` (`key: name`), поле `of` — `ref: va/items`, `must_match: {zone: zone}`, и поле `zone` — обратная ссылка на таблицу адресата |

Проверки формы манифестов, которые входы обязаны выдержать (загрузчик главы 2.1): `must_match` без `ref` — нельзя (у обоих
`ref` есть); ключ `must_match` — поле той же формы (строка 5 таблицы связей — `unit.fields.$f.must_match.*` → `. in
keys(unit.fields)`; строка 19 — `tables.$t.fields.$f.must_match.*` → `. in keys(tables.$t.fields)`): у `va` есть поле `zone`,
у `vc.links` есть поле `zone`; правила `worker.creates` (П/02.1 Н3): `sub`/`rows` — `va/items`, `unit.id` адресата не
`numeric`, подстановка `{code}` — обязательное строковое поле адресата, не поле-источник id, у адресата нет обязательного
`*_secret`, `fixed`-полей и `about` у адресата нет.

## Таблица ожиданий (`expect.tsv`)

```
role	action	key	expect
vbworker	read	va/shelves/u1	allow
vbworker	read	vc/links/x	allow
vbworker	read	va/items/vb-1	allow
vbworker	write	va/items/vb-1	allow
vbworker	write	va/items/x	deny
vbworker	delete	va/items/vb-1	deny
vbworker	read	va/items/other-1	deny
vbworker	read	vc/notes/x	deny
vacontroller	read	vc/links/x	deny
console	read	vc/links/x	allow
```

Какая строка доказывает ИМЕННО ветвь `must_match`, а не обычный `ref`:

- **`vbworker read vc/links/x allow`** — обратная ветвь. В манифесте заказчика `vb` нет НИ ОДНОГО объявления, ведущего к
  `vc/links`: нет `worker.reads`, нет `secrets.reads`, нет `ref` на `vc`, нет `worker.creates` в `vc`. Единственный возможный
  источник этого чтения — выведенное правило Н1.4 главы 2.5 («семьи каталога, чьё поле с `ref` на таблицу адресата и
  `must_match`, — `<их sub>/<семья>/*`»): семей `vc/links`, поле `of` — `ref: va/items` + `must_match`. Убери из `vc` поле
  `must_match` — и чтение должно исчезнуть (это стоит проверить отдельной строкой в том же варианте: без `must_match` у
  поля `of` обратной ветви нет, и `vbworker read vc/links/x` должен стать `deny`).
- `vbworker read va/shelves/u1 allow` — прямая ветвь (цель `ref` поля `shelf` адресата). Её покрывает сценарий 13 главы 2.5
  («`testsubworker` … читает `testsub2/shelves/*` (цель `ref` поля `shelf` адресата — выведенное чтение)») — здесь она
  нужна как сосед, чтобы различать две ветви.
- `vbworker write va/items/vb-1 allow` / `vbworker write va/items/x deny` / `vbworker delete va/items/vb-1 deny` — образец
  заказа `va/items/vb-*`: только write, без delete (П/02.5 Н1.4, «только write, без delete»; сценарий 13 главы 2.5).
- `vbworker read va/items/other-1 deny` — образец заказа не даёт чужих строк.
- `vbworker read vc/notes/x deny` — единицы третьей подсистемы заказчику не выдаются (выведенные чтения — только семья
  `links`, а не все строки `vc`).
- `vacontroller read vc/links/x deny` — обратную ветвь получает заказчик (тот, кто выполняет проверку при заказе строки),
  а не контроллер адресата: общую проверку строки выполняют дверь консоли и библиотека заказчика (договор проверки
  строки, вступление; П/06.1 Н3, П/03.6 Н1.6). Это строка, которая держится на буквальном чтении Н1.4.
- `console read vc/links/x allow` — дверь выполняет ту же проверку и читает всё (`<s>/*` всех манифестов, П/02.5 Н1.4,
  строка `console`).

## Оговорки

- Вариант — новый (`v7-must-match`); в приёмке главы 2.5 сейчас `v1`–`v6`. Номер и имя — на усмотрение владельца
  (приборы главы 2.5 перенесены из М10/6, имена `v1`–`v6` заняты).
- Права выводятся инструментом реализации по каталогу варианта (Н2); если инструмент не выводит выведенные чтения, строка
  `vbworker read vc/links/x allow` будет `deny` — это и есть предмет проверки (не «ошибка прибора»).
- Пробы идут на свежем экземпляре каждая (`allow` — подтверждённый успех; у отсутствующей строки чтение даёт 200 с
  `items: null`, поэтому ключи проб могут не существовать — это нормально).
- Сценарий 13 главы 2.5 покрывает прямую ветвь на учебных манифестах (`testsub`/`testsub2`); обратной ветви там нет —
  учебные манифесты такой ссылки не содержат (чек-лист П/02.5-05).
