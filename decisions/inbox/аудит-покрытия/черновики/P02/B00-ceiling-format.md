# Черновик B00 — формат для потолка хранилища не по умолчанию (экземпляр с `{row_ceiling}` ≠ 524288).

# Что проверяет: установщик обязан брать потолок строки у хранилища (`max_value` из `GET /v1/status`), а не считать
#   524288 константой установщика. Проверяется это на экземпляре с потолком НЕ по умолчанию: вид манифеста, вес которого
#   ровно на байт выше потолка, должен быть отвергнут, а на байт ниже — принят.
# Место нормы:
#   - Platform/02-installer/spec/02.2-installer.norms.md Н1.2 — потолок вида = `max_value` (`ceiling`);
#   - Platform/02-installer/spec/02.3-installer.norms.md Н3 «Смена манифеста» — «прочитать потолок строки хранилища:
#     GET /v1/status → max_value (P/01.3 Н2; 524288 — умолчание -max-value, не константа установщика)» и ветвь «построить
#     вид … → toolarge вида: отказ установки целиком, ничего не записано, код 2; stderr называет файл, ключ вида, вес и
#     потолок (окно 2.2, п. 8)»; Н4 — строки «потолок строки хранилища не прочитан» и «канонический вид выше потолка
#     строки хранилища для ключа вида»;
#   - Platform/01-store/spec/01.1-store.norms.md Н1 — вес `items` (сумма байтов имён и значений) и потолок;
#   - Platform/common/acceptance/README.md — «Параметры каждого экземпляра» (потолок строки 524288, предел тела 1048576;
#     раннер сверяет параметры ПОВЕДЕНИЕМ на пробном экземпляре: вес `items` ровно 524288 записывается, 524289 → 413
#     `toolarge` с `limit` 524288) и «Команда запуска» (подстановка `{row_ceiling}`).
# Место приёмки: Platform/02-installer/acceptance/2 — таблица `puts.tsv` (формат главы 2.2: `case<TAB>puts<TAB>expect<TAB>canonical`,
#   ровно четыре поля) и её раздел «Кандидат: потолок хранилища не по умолчанию», где пара случаев ждёт: «Строка войдёт в
#   `puts.tsv`, когда стенд и формат выразят потолок экземпляра на случай; до того — чтением». Этот черновик — предложение
#   такого выражения: формат и две строки.
# Существующие директивы: `@view-delete`, `@view-spoil` (глава 2.2) — пишут строку вида через `admin.sock` экземпляра.
# Новых директив не требуется: потолок — ПАРАМЕТР ЭКЗЕМПЛЯРА, а не действие между установками.

## Почему не директива, а колонка

Потолок строки задаётся при старте хранилища (флаг `-max-value`, подстановка `{row_ceiling}` в «Команде запуска»), и
изменить его у живого хранилища нельзя. Директива в поле `puts` исполняется МЕЖДУ установками, когда хранилище уже поднято,
поэтому `@ceiling <N>` в этой форме невозможен. Значит, потолок — свойство строки случая: раннер поднимает для этой строки
свой экземпляр с нужным потолком и кладёт его в поле строки.

## Предлагаемая форма

Пятая колонка `ceiling` в `puts.tsv` главы 2.2:

```
case<TAB>puts<TAB>expect<TAB>canonical<TAB>ceiling
```

- `ceiling` — десятичное число: потолок строки экземпляра этой строки случая (подстановка `{row_ceiling}` команды запуска);
  `-` — умолчание стенда 524288 (тогда поведение прежнее, все нынешние строки сохраняются, а форма требует колонку у всех).
- Альтернатива, если владелец не хочет менять форму действующей таблицы: отдельный файл `puts-ceiling.tsv` в приёмке главы 2.2
  того же формата (пять полей) — тогда `puts.tsv` остаётся четырёхполевым. Выбор — решение владельца.
- Правка README приёмки главы 2.2: раздел «Форма файла» («ровно четыре поля») → пять полей, плюс абзац «Потолок экземпляра».

## Исполнение (что требуется от раннера)

1. Для каждой строки с числом в колонке `ceiling` раннер поднимает НОВЫЙ экземпляр хранилища (пустой каталог данных, свой
   сокет) командой запуска с `{row_ceiling}` = это число; строки с `-` — обычный путь (умолчание).
2. Параметр проверяется ДО случая: `GET /v1/status` → `max_value` = запрошенному числу (П/01.3 Н2; установщик читает
   ровно это поле). Дополнительно — поведенческая сверка по общему README: запись `items` весом ровно `ceiling` проходит,
   на байт больше — `413 toolarge` с `limit` = `ceiling`; не сошлось — прогон не выполнен (параметры подменять нельзя).
3. Дальше строка исполняется как обычно: файлы ставятся по порядку в одно хранилище, после последней установки
   сравниваются код, `rev` строки, метка и вид (`canonical`) — по правилам README главы 2.2.

## Две строки (кандидат главы 2.2)

```
case	puts	expect	canonical	ceiling
ceiling_976	probe	2 -	-	976
ceiling_977	probe	0 1	example-sections	977
```

Почему такие ожидания (арифметика от файла `puts/probe.subsystem.yaml` главы 2.2, 187 байт):

| величина | расчёт | байт |
|---|---|---|
| строка манифеста | 187 (yaml) + 78 (ключи `yaml`+`sha256`+`rev` = 13; значения 187 + 64 + 1 = 252) | 265 |
| метка `platform/manifest/probe/rev` | 9 (ключи `rev`+`sha256`) + 65 (значения 1 + 64) | 74 |
| строка вида `platform/manifest/probe/canonical/1` | 87 (ключи `form`+`rev`+`sha256`+`manifest` = 21; значения 1 + 1 + 64) + 890 (байты вида) | 977 |

- Потолок 976: строка манифеста (265) и метка (74) помещаются, ВИД (977) — нет, на байт. Вид строится ДО любой записи
  (окно 2.2, п. 8), поэтому отказ установки ЦЕЛИКОМ: код 2, не записано НИЧЕГО — строки манифеста, вида и метки нет
  (`expect` = `2 -`, `canonical` = `-`); stderr называет файл и ключ вида `platform/manifest/probe/canonical/1`.
- Потолок 977: вид помещается ровно (вес `items`, равный потолку, записывается — «Параметры каждого экземпляра»), установка
  проходит: код 0, `rev` 1, вид — вектор `example-sections`, метка записана.

## Оговорки

- Вектор `example-sections` — из `Platform/02-installer/vectors/canonical` (уже применён в существующей строке
  `view_over_ceiling` главы 2.2); вес вида 890 — из этой же приёмки, число приведено здесь для проверки арифметики.
- Проверка «установщик берёт потолок у хранилища, а не константу» — именно эти две строки; при потолке 976 реализация с
  константой 524288 приняла бы установку, и строка стала бы красной.
- Потолок экземпляра меняет и вес обычных строк: при 976 любая строка `items` тяжелее 976 не пишется — в этих двух случаях
  строки манифеста (265) и метки (74) укладываются, иначе отказ был бы по другой причине.
- Обе строки требуют, чтобы раннер умел поднимать экземпляр с нестандартным `{row_ceiling}` — это уже есть в «Команде
  запуска» общего README (подстановка), но не описано как «параметр строки случая»; правка README главы 2.2 — условие
  исполнения этих строк.
