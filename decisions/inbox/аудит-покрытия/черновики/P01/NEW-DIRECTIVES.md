# Черновик: новые директивы стенда для приёмки P/01

Черновик к словарю директив и дверей общего README приёмки (`Platform/common/acceptance/README.md`, раздел
«Словарь директив и дверей», таблица `| Форма | Смысл | Урок |`). Ничего в курсе не правится: это предложение
«Спецификации» — четыре директивы и одна проба, которых в словаре нет, а норма требует проверяемого свойства.

Новые строки словаря (в форме словаря: `форма | смысл`; колонка «Урок» — как в общем README):

| Форма | Смысл | Урок |
|---|---|---|
| `@spoil row <ключ>` | испортить тело строки хранилища, мимо двери: байты тела строки становятся нечитаемыми, версия строки цела | P/01.1 (2026-10-30) |
| `@spoil row-index <ключ>` | испортить сохранённую версию строки хранилища, мимо двери: тело цело, версия строки не читается | P/01.1 (2026-10-30) |
| `@rights store <файл\|none>` | перезапустить хранилище стенда с файлом прав (путь от каталога приёмки урока) или без файла (`none`) | P/01.2 (2026-10-30) |
| `@cut store@<id>` / `@mend store@<id>` | перерезать и восстановить связь члена группы с группой: посредник раннера на портах `-raft` и `-api` члена рвёт соединения и не принимает новых / пропускает снова | P/01.3 (2026-10-30) |
| `@tls <путь пробы>` с дверью `raft@<id>` | проба к порту `-raft` члена группы: клиент предъявляет лист роли `configstore-door`; рукопожатие отвергается | P/01.3 (2026-10-30) |

Подробности — по каждой директиве ниже.

---

## 1. `@spoil row <ключ>` и `@spoil row-index <ключ>`

**Зачем (место в норме).** P/01.1 Н2 — форма `Row` главы 1.1: строка, тело которой не читается, отдаётся с
`items: null` и `unreadable: true`, версия строки при этом сохраняется; потеря самой версии — порча хранилища,
не строки: чтение этого ключа и перечисление, которое его касается, отвечают `503 unavailable`
(Platform/01-store/spec/01.1-store.norms.md, Н2 и абзац про потерю версии; C01-ROW-INDEX-LOST-01, решение
«Архитектора» 2026-10-29). То же — «Решает реализация» п. 5 главы 1.1: реализация обязана назвать в описании,
как хранилище обнаруживает порчу, что пишет в лог и как хранит версию строки, чтобы порча тела её не теряла.
Сейчас это свойство проверяется только чтением описания реализации (чек-лист P/01.1-17 и п. 5) — сценарием не
проверяется.

**Форма.**

```
@spoil row <ключ>
@spoil row-index <ключ>
```

Ключ — полный ключ строки (как в других директивах словаря: `@put object <ключ> <файл>`). Действие — испортить
строку ВНУТРИ хранилища, мимо двери и мимо писателя: прямое вмешательство в данные на носителе.

- `@spoil row <ключ>` — портятся **байты тела** строки (значения `items`): тело больше не раскодируется своей
  семьёй, строка нечитаема; **сохранённая версия строки цела** и выдаётся вместе с признаком нечитаемости.
- `@spoil row-index <ключ>` — портится **сохранённая версия** строки: тело цело и читается, но версия не
  восстанавливается (потеря версии — 503).

**Ожидание.** `ok` — порча сделана (команда вышла с кодом 0). Дальнейшие шаги сценария читают строку дверью
(`GET /v1/get`, `GET /v1/list`) и получают по Н2/N4 главы 1.1:

| после | `GET /v1/get?key=<ключ>` | `GET /v1/list?prefix=<префикс>` (касается строки) |
|---|---|---|
| `@spoil row` | `200 {"items": null, "index": "<версия>", "unreadable": true}` | `200`, имя строки и её версия в `keys` |
| `@spoil row-index` | `503 {"kind": "unavailable"}` | `503 {"kind": "unavailable"}` |

**Что требуется от реализации/раннера.** Команда порчи строки — по образцу `@spoil object` (P/05 «Решает
реализация» п. 8): реализация называет в описании команду порчи и её семантику (какая часть строки портится,
что остаётся целым); «Решает реализация» п. 5 главы 1.1 дополняется указанием на эти команды. Команда
применима к реализациям с файловым носителем (в хранилище в процессе, открытом в памяти, строки на диске нет —
портить нечего; для таких сборок директива не исполняется, сценарий помечается неисполнимым, а не красным).
Раннер: у `@spoil object` порча идёт при остановленном писателе, потому что писатель — другой процесс; здесь
писатель — само хранилище, и порча выполняется под ЖИВЫМ демоном: проверяется обнаружение порчи при чтении.
Оговорка для владельца словаря: реализация, отвечающая из кэша памяти, порчу под живым демоном может не увидеть —
для неё сценарий вставляет `@restart store` между порчей и чтениями (обнаружение свежим процессом); выбор
варианта — решение «Спецификации» при переносе, оба проверяют одну норму.

**Кто проверяет.** Сценарий A05 (`черновики/P01/A05-spoil-row.tsv`): (а) `@spoil row` → чтение `200` с
`unreadable`, перечисление отдаёт имя и версию, запись поверх этой версии `cas` проходит (испорченная строка
заменяется), чтение — новое значение; (б) `@spoil row-index` → `503 unavailable` и на чтение, и на
перечисление.

## 2. `@rights store <файл|none>`

**Зачем (место в норме).** P/01.2 Н1.2 (Platform/01-store/spec/01.2-store.norms.md) — «загружается при старте
демона (`-rights`); без файла открывается только `admin.sock`; живой перезагрузки нет»; Н4: «`/v1/rights`: файл
не загружен → 404 `badrequest`» и «файл прав не по форме; называет `admin`/`configstore`/`configstore-door`;
роль не по грамматике → демон не стартует, лог». Сейчас оба свойства проверяются только чтением (README
приёмки главы 1.2, раздел «Проверки вне сценарного файла») — сценарием не проверяются, потому что стенд всегда
класт файл прав.

**Форма.**

```
@rights store <файл|none>
```

`<файл>` — путь к файлу прав от каталога приёмки урока (как `@put object`: «путь — от каталога приёмки урока»).
`none` — запуск без файла прав вообще. Директива перезапускает хранилище стенда: SIGTERM, ожидание выхода,
запуск той же командой «Стенда» с теми же `{data}` и `{socket}`, но с флагом `-rights <файл>` (или без него) —
как у `@restart store`, только с другим файлом прав.

**Ожидание.**

- `@rights store none` → `ok` (хранилище поднялось; открыт только `admin.sock`); следующий шаг:
  `admin GET /v1/rights` → `404 {"kind": "badrequest"}` (Н4: файл не загружен).
- `@rights store <файл с нарушением формы>` → `@exit 2` — процесс вышел с кодом 2 не позже 10 с (как у
  `@store-start`: отказ старта, P/01.3 Н1.3 `refuse_start`). Нарушения формы: неизвестное поле в объекте роли;
  внутренняя роль (`admin`, `configstore`, `configstore-door`) в `roles`; имя роли не по грамматике
  `^[a-z][a-z0-9_-]{0,63}$` (Н1.1, Н1.2).

**Что требуется от реализации/раннера.** Ничего нового от реализации не требуется: это штатные флаги `-rights` и
проверка формы файла (Н1.2). Раннер: кладёт файл в `{data}/etc/w2c/configstore-rights.json` (путь владельца по
Н1 главы 1.2) до старта, после перезапуска ждёт сокет `admin.sock` (или выход с кодом 2). Файлы нарушений формы —
в каталоге `inputs/` приёмки главы 1.2 (например `inputs/rights-bad-field.json`,
`inputs/rights-internal-role.json`, `inputs/rights-bad-name.json`).

**Кто проверяет.** Сценарий: `@rights store none` → `admin GET /v1/rights` → 404; `@rights store
inputs/rights-bad-field.json` → `@exit 2`. Плюс контрольный шаг: `@rights store inputs/rights.json` → `ok`,
`admin GET /v1/rights` → `200` (файл виден) — проверка, что перезапуск со сменой файла не оставляет хранилище
в прежнем режиме.

## 3. `@cut store@<id>` / `@mend store@<id>`

**Зачем (место в норме).** P/01.1 Н3 («Проход», линеаризуемость чтения в группе): «ведомый, отрезанный от группы,
не должен подтверждать эпоху, которую остальные уже сдвинули» — иначе читатель, у которого отозвали аренду,
продолжит читать и подтверждать своё. P/01.3 Н1.3 `leader_wait`: 5 с от потери лидера → `503 unavailable`.
План `decisions/inbox/2026-10-30-план-сценарии-группы-автоматом.md`, этап 1: «`@cut store#<n>` / `@mend store#<n>`
— посредник раннера на raft-порту члена» — в словарь директив не внесено (в плане имя члена ещё было `store#<n>`,
в словаре принято `store@<id>`).

**Форма.**

```
@cut store@<id>
@mend store@<id>
```

Член `<id>` — голосующий (`s1`…`s5`) или дверь без голоса (`d1`, `d2`), как у `@sigterm store@<id>` и
`@restart store@<id>` (словарь, раздел «Стенд группы хранилища»).

- `@cut store@<id>` — посредник раннера на портах `-raft` и `-api` члена **рвёт живые соединения и не принимает
  новых**: пакеты в обе стороны не доходят, соединения закрываются.
- `@mend store@<id>` — посредник снова пропускает трафик в обе стороны.

**Ожидание.** `ok` — посредник переключился (это не наблюдение хранилища, а действие раннера; ответа демона нет).
Дальнейшие шаги сценария — по наблюдаемым признакам: `@until <с> <запрос>` до ответа `503 {"kind": "unavailable"}`
(линейно не читается) либо после срока `leader_wait` 5 с — отказ `503 unavailable` на запись через отрезанного
ведомого; при `@mend` — `@until <с> <запрос>` снова `200` с прежней версией строки.

**Что требуется от реализации/раннера.** От реализации — ничего: порты члена уже свои (`-raft`, `-api`; порты
раздаёт раннер, см. словарь). Раннер: на портах члена (а не на портах самого демона) ставится посредник, который
по `@cut` закрывает соединения и перестаёт пересылать, по `@mend` — возобновляет; у члена в это время процесс
жив (в отличие от `@sigkill`, которым проверяется отказ по потере лидера). Требуется решение владельца словаря:
сейчас разрыв связи между членами на одной машине не проверяется («Чтением остаются: ведомый, отрезанный от
группы сетью…», README приёмки главы 1.3) — директива снимает этот пункт.

**Кто проверяет.** Сценарий группы: запись лидером → `@cut store@s3` → чтение у `s3` не подтверждает новое
(либо `503 unavailable`, либо старая версия — но подтверждать эпоху нельзя: по Н3 читатель без аренды должен
прекратить чтение); `@mend store@s3` → `@until` снова `200` с той же версией.

## 4. Проба `@tls` к двери `raft@<id>`

**Зачем (место в норме).** P/01.3 Н1.3 `door`: дверь без голоса — «те же сокеты и права; к лидеру или любому
голосующему (попытка 2 с, запас 1 с)»; в группу (raft) дверь не входит — «дверь в кворум не входит»
(Platform/01-store/acceptance/3/README.md, сценарий 17, П-3). P/01.3 Н1.6: «демон хранилища проверяет TLS-пира на
`-raft` и `-api`; …роли демона: `configstore`, `configstore-door`» — по одному этому перечню лист двери на
`-raft` проходит, хотя говорить raft дверь не должна. Сравнение линий (decisions/inbox/ревью/РЕВЬЮ-СРАВНЕНИЕ-P01-Claude.md,
П-3): «поток raft пускает сертификат двери без голоса… норма: дверь “без raft” (P/01.3-02)». Сейчас это
проверяется только чтением («сертификат двери на `-raft` (П-3, рукопожатие потока raft не HTTP — пробы `@tls`
нет)», README приёмки главы 1.3) — то есть проверки нет вовсе.

**Форма.** Расширение уже есть в словаре: `@tls <путь пробы>` — «вход `{door: "api@<id>", client: "<id2>",
request}`; клиент предъявляет лист члена `<id2>` описания `group.json`, проверяет сервер по центру группы и
`<id>`». Новая форма — та же директива с дверью `raft@<id>`: вход

```json
{"door": "raft@s1", "client": "d1", "request": "GET /v1/status"}
```

где `client` — **дверь без голоса** (`d1`), предъявляющая свой лист (`CN configstore-door.d1`). `request` на порту
`-raft` не читается (это не HTTP — протокол raft), поэтому поле `request` в этой пробе не участвует в сравнении;
проба судит только рукопожатие.

**Ожидание.** `ok {"handshake": "alert", "http": null}` — сервер отказал рукопожатием (закрытая форма исхода
пробы — Platform/common/acceptance/tls/README.md: при `handshake: alert` — `http: null`, `version` — выбранная
версия или `null`, `reused: false`, `session_available: false`). Исход `alert` означает: лист роли `configstore-door`
на порту `-raft` голосующего не принимается — дверь без голоса в потоке raft не участвует.

**Что требуется от реализации/раннера.** От реализации: на слушателе `-raft` принимаются только пиры роли
`configstore` (голосующие); лист роли `configstore-door` на этом порту — отказ рукопожатия. Раннер: проба
подключается к порту `-raft` члена (порт члена известен — `{raft@<id>}`), предъявляя лист `d1` из комплекта
`inputs/group.json`; отдельная форма входа — «door: raft@<id>» в словаре `@tls` дополняется (сейчас там только
`api@<id>` и `kit`).

**Кто проверяет.** Сценарий группы: подняты `s1`, `s2`, `s3` и дверь `d1`; проба `@tls` к `raft@s1` клиентом
`d1` → `alert`. Смысл: дверь, которая пишет свою строку `platform/configstore-doors/d1` и ходит к лидеру по
`-api`, не может быть участником потока raft и не должна выглядеть участником для членов группы.

## Сводка: что требуется от владельца словаря

1. Внести четыре строки в словарь директив общего README приёмки (формы выше) и дополнить строку `@tls` формой
   двери `raft@<id>`.
2. Решить по `@rights store`: имя `none` для «без файла прав» — согласовать с уже принятыми `none` в описаниях
   (в README приёмки главы 1.2 `none` — роль в файле прав; в словаре директив такого слова ещё нет).
3. Подтвердить, что `@cut`/`@mend` режут **оба** порта члена (`-raft` и `-api`) — по норме «отрезанный от группы»
   означает отрезанный от группы, а не только от лидера.
4. Согласовать имя `<файл>` для `@rights store` (путь от каталога приёмки урока — как у `@put object`) и требование
   к именам файлов нарушений формы в `inputs/`.
