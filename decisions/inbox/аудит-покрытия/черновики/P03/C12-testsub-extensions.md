# Черновик C12 — ЗАДАНИЕ на расширение учебного воркера testsub: медленное действие, падающая единица, маркеры вызовов остановки.

Это не сценарий, а задание: перечислить, что должно появиться в учебном воркере (и в манифесте), чтобы три ветви
нормы, которые корпус приёмки проверяет только чтением, стали выражаться существующими директивами. После расширения
черновики сценариев пишутся обычным делом (`черновики/P03/C08…C10` — образец формы).

## Что проверяет (после расширения)

1. **Взгляд держателя при вызове, который не ответил вовремя** — П/03.6-03: `unknown` по таймауту действия и поздний
   ответ, заменяющий `unknown` на `late: true`; П/03.6-08: не больше одного незавершённого вызова действия на группу.
2. **Отступ повтора запуска единицы** — П/03.3-02: пауза растёт экспонентой от `RETRY_MIN` до `RETRY_MAX` с
   обязательным дрожанием, счёт считает только неудачи, обнуляется по трём условиям, а при паузе в `RETRY_MAX` в пульсе
   `status[].stalled: true`.
3. **Вызовы остановки** — П/03.1-03: `before_stop_all` до `stop_unit` всех единиц, `after_stop` после отдачи слота и
   места, только при SIGTERM, при крахе их нет; ошибка — строка журнала, остановка продолжается, код выхода не меняется.

## Место нормы

- П/03.6 Н3 «взгляд держателя» (Platform/03-worker/spec/03.6-worker.norms.md): «вызвать действие с таймаутом
  PERFORM_TIMEOUT (+ PERFORM_GRACE)»; «нет ответа → полный исход с сохранёнными begun-полями, ended_at, outcome: unknown,
  error: "no answer in <PERFORM_TIMEOUT> s"; поздний фактический ответ ещё может заменить unknown с late: true»;
  «ответ → прочитать метку и записать исход по её индексу; conflict → перечитать и повторить только запись, perform не
  повторяется»; «Действие устройства … Не больше одного незавершённого вызова действия на группу единицы
  (`placement.group_by`) … в том числе после `unknown`: пока вызов в группу не вернулся, второго в неё нет».
  Константы — Н1.5: `PERFORM_TIMEOUT: 10; PERFORM_GRACE: 0.2; REQUESTS_HOLD: 0.5; COMMANDS_PER_LOOK: 200`.
  Чек-лист: **П/03.6-03**, **П/03.6-08**.
- П/03.3 Н1.2 `retry` (Platform/03-worker/spec/03.3-worker.norms.md): `RETRY_MIN: 1` (первая пауза после неудачи),
  `RETRY_MAX: 60` (предел паузы), «пауза растёт экспонентой от RETRY_MIN до RETRY_MAX с обязательным дрожанием (форма
  экспоненты и дрожания — «Решает реализация» п. 3)», «считаются только неудачи запуска и работы единицы», «счёт
  обнуляется при любом из трёх», `stalled: пауза дошла до RETRY_MAX — status[].stalled: true в пульсе (глава 3.4 Н1.1),
  пока счёт не обнулён». Форма пульса — Platform/03-worker/data/heartbeats.schema.json: `status[].stalled` — bool, одно
  из `true`. Чек-лист: **П/03.3-02** (в норме — «проверяется чтением: учебные подсистемы не падают по заказу стенда»).
- П/03.1 Н2 (Platform/03-worker/spec/03.1-worker.norms.md): шесть вызовов подсистемы, из них
  `before_stop_all() — упорядоченная остановка, до stop_unit всех единиц … ошибка — строка журнала, остановка
  продолжается`, `after_stop() — после отдачи слота и места: подсистема закрывает своих писателей; по умолчанию ничего;
  ошибка — строка журнала, код выхода остановки по SIGTERM не меняется`; «Оба вызова остановки зовутся только при
  упорядоченной остановке (SIGTERM, глава 3.4 Н3); при крахе их нет». Чек-лист: **П/03.1-03** (тоже «проверяется
  чтением (Н5)»).
- П/03.4 Н3 «остановка по SIGTERM» (Platform/03-worker/spec/03.4-worker.norms.md): порядок — 1 подмена стоп; 2
  `before_stop_all()`, остановить все единицы, закрыть писателей мест; 3 пульс последний раз; 4 отпустить место, затем
  отдать слот; 5 `after_stop()`. Чек-лист: П/03.4-05 (часть про вызовы остановки — П/03.1-03).
- Договор просьбы и её метки (Platform/common/contracts/request-mark.md): метка `objects/<sub>/commands/<rid>`, поля
  `instance, slot, unit, of?, at, digest, valid_until?` (begun) и `{outcome, action?, ended_at, error, late?}`; исходы
  `performed | refused | unknown | expired | gone`.
- Договор журнала событий (Platform/common/contracts/event-journal.md): «Решает реализация» п. 1 — строки журнала с
  неназванными видами выбирает реализация, и приёмка их не судит. Отсюда: имя вида для проверяемой строки должен
  назвать владелец.

## Существующие директивы

Всё, что нужно для проверки после расширения, уже есть: `@start worker <имя>`, `@start resource`, `@sleep <с>`,
`@until <с> <запрос>`, `@sigterm <имя>`, двери `console` (`POST /counters`, `POST /testsub/requests`),
`store` (чтение строк и меток), `resource` (чтение пульса), `console` (`GET /events` — чтение журнала).

## Новых директив не требуется

Расширение учебного воркера — работа по реализации, а не по словарю директив. Одна оговорка: код выхода процесса,
остановленного по SIGTERM, наблюдается ожиданием `@exit <код>` на шаге `@sigterm` — это предложение раздела 2
черновика `черновики/P03/NEW-DIRECTIVES.md` (тот же идиом, что у `@kit-start` и `@store-start` общего README приёмки).
Без него наблюдаемо только «процесс вышел» (`ok`), но не «код выхода не изменился».

## Расширение 1 — медленное действие (просьба, на которую вовремя нет ответа)

**Что нужно.** Учебный обработчик testsub умеет только прибавить `add` к счётчику (свидетельство:
`/Users/murat/w2c/vmssubsystem/vmsworker/w2cplatform/testsub/cmd/testsubworker/main.go` — обработчик платформенной
библиотеки; в курсе — `Source/tests/conftest.py`, `CounterWorker.perform`). Научить его выполнять действие дольше
`PERFORM_TIMEOUT` (10 с).

**Как (предложение).** Поле строки единицы — например `slow` (число секунд; 0 — обычное действие) — в
`unit.fields` манифеста `testsub` (правка каталога манифестов — работа «Спецификации», П/02.1 Н3; сейчас поля
`name, start, labels, step, marks`). Учебный воркер в действии над единицей спит `slow` секунд. Почему поле единицы,
а не поле тела просьбы: тело проверяется по `requests.schema` манифеста (`additionalProperties: false`), и без правки
манифеста дверь такую просьбу откажет; а поле единицы правится в одном месте — и строкой единицы, и её формой.

**Что должно быть видно после расширения (и это то, что сценарий проверяет).**

- Метка `objects/testsub/commands/<rid>`: сначала `begun` (`instance`, `slot`, `unit`, `at`, `digest`), затем — через
  ~10 с — исход `unknown`: `{"outcome": "unknown", "error": "no answer in 10 s", "ended_at": …}`, затем, когда вызов
  вернулся, исход поверх него: `{"outcome": "performed", "late": true, "ended_at": …}`.
- В пульсе держателя: `commands_in_flight` (есть, пока вызов не вернулся) и `command_counts.unknown` — ненулевой.
- Второй вызов в ту же группу, пока первый не вернулся, НЕ начинается: второй просьбы метки нет (держатель пишет
  `begun` прямо перед вызовом). Когда первый вернулся — второй выполняется, и его метка появляется с исходом
  `performed`.

**Что требуется от реализации.** Таймаут и поздний ответ — уже есть в платформенной библиотеке (свидетельство
`Source/w2cplatform/worker.py`: `_timed_out` пишет `unknown` в свою же метку по прочитанному индексу, `_confirm`
пишет поверх неё с `late: true`; вызов идёт вне потока цикла, «пока вызов в группу не вернулся, второго в неё нет» —
проверка цели в `_performing`). То есть платформенная часть готова; работа — в учебном обработчике (уметь висеть) и в
манифесте (поле `slow`).

**Расхождения нормы и свидетельства — вопрос владельцу (в сценарии проверять метку, а не эти поля).**

1. Текст ошибки: норма требует `error: "no answer in <PERFORM_TIMEOUT> s"` (то есть «no answer in 10 s»), а свидетельство
   пишет «target did not answer» (`_timed_out`). Пока текст не сходится, ожидание в сценарии — `~no answer` либо
   проверка только `outcome`.
2. `commands_reanswered`: форма пульса (Platform/03-worker/data/heartbeats.schema.json) говорит «исходов, записанных
   снова (late)», а свидетельство считает в этот счётчик другое — «исход, записанный снова другим держателем»
   (`_answered_before`), и поздний ответ в него не попадает.

## Расширение 2 — падающая единица (отступ повтора и `stalled`)

**Что нужно.** Учебная единица должна уметь не запуститься «по заказу стенда», и платформа — вести отступ повтора.

**Как (предложение).** Поле строки единицы — например `fails` (bool; по умолчанию false) — в `unit.fields` манифеста
`testsub`; учебный воркер в `start_unit` (или в своей работе единицы) отказывается запускать единицу, у которой это
поле истинно, и говорит почему (поле `status[].why` формы пульса — «причина платформы, когда единица не идёт»).

**Главное: пауза — дело платформы, а не подсистемы.** Норма (П/03.3 Н1.2 `retry`) требует, чтобы отступ повтора
неудачного запуска держала платформа: пауза растёт экспонентой от `RETRY_MIN` (1 с) до `RETRY_MAX` (60 с) с
обязательным дрожанием, счёт считает только неудачи запуска и работы единицы, обнуляется при любом из трёх условий, а
при паузе в `RETRY_MAX` пульс несёт `status[].stalled: true`. Ни в одном свидетеле этого нет: в
`Source/w2cplatform/worker.py` нет ни `RETRY_MIN`, ни `RETRY_MAX`, ни `stalled`; в `vmsworker/w2cplatform` (Go) — тоже
(grep по `RETRY_MIN`/`stalled` пуст, `RETRY` встречается только в ресурсе — `RESTORE_RETRY`). Значит, это долг
платформенной библиотеки, и учебное расширение — только его половина (научить единицу падать).

**Что должно быть видно после расширения.** Элемент `status[]` единицы в пульсе несёт `stalled: true`, пока счёт не
обнулён; единица при этом не `running`. Число пауз и их форма — не норма (форма экспоненты и дрожания — «Решает
реализация»), поэтому сценарий ждёт ФЛАГ, а не времени: до паузы в 60 с накопленного ожидания ≈ 63 с
(1 + 2 + 4 + 8 + 16 + 32) плюс время до первой попытки — но это оценка для порядка, не ожидание.

**Что выражается, а что остаётся чтением.**

- Выражается: появление `stalled: true`; исчезновение флага при обнулении счёта.
- Обнуление по третьему условию («ушедшая с воркера единица обнуляет счёт») выражается, если снять единицу с
  назначения; как это делается на стенде — вопрос прав консоли над строками единиц (П/06.1 Н1.6), не этого черновика.
- Остаётся чтением: обнуление после устойчивой работы (`RETRY_MAX` непрерывной устойчивой работы) и обнуление по
  слову подсистемы («устойчива») — для них нужна работающая единица, которая проработает `RETRY_MAX` (60 с) без сбоев,
  а слово «устойчива» — слово подсистемы, и его форма в пульсе нормой не названа (в пульсе нет поля для такого слова;
  `status[]` по форме несёт только `id, phase, epoch?, revision?, observed_revision?, why?, stalled?, lease?,
  unconfirmed_s?` и «прочие имена автора»). Если владелец хочет, чтобы это выражалось, нужно назвать поле и слово.

## Расширение 3 — маркеры вызовов остановки (`before_stop_all` / `after_stop`)

**Что нужно.** Учебный воркер должен переопределить оба вызова и дать их увидеть.

**Как (предложение).**

1. Учебный воркер переопределяет `before_stop_all` (сбросить буферы, закончить начатое) и `after_stop` (закрыть своих
   писателей) — сейчас он не переопределяет ни одного (свидетельство `main.go`: по SIGTERM освобождает единицы, пишет
   последний пульс, отдаёт слот, выходит с кодом 0; вызовов остановки нет). Норма требует, чтобы они звались только
   при SIGTERM и в указанном порядке (П/03.4 Н3: `before_stop_all` — шаг 2, до `stop_unit` всех единиц; `after_stop` —
   шаг 5, после отдачи места и слота).
2. Маркер: **либо** строка журнала, **либо** поле пульса. Форму надо назвать владельцу — иначе приёмка её не судит
   (договор журнала, «Решает реализация» п. 1: виды без названия выбирает реализация и приёмка их не судит).
   - Предложение A (журнал): вид `worker.stop_calls`, поле `call` — «before_stop_all» или «after_stop»; при ошибке
     вызова — та же строка с полем `why` (ошибка — строка журнала; остановка продолжается; код выхода не меняется).
     Проверка: `console GET /events?unit=audit/testsubworker&kind=worker.stop_calls` → `200 {"events": [{"kind":
     "worker.stop_calls"}]}`.
   - Предложение B (пульс): поле `stop_calls` в пульсе — список имён вызовов, выполненных при остановке. Тогда
     проверка — в пульсе держателя после SIGTERM: `{"stop_calls": ["before_stop_all", "after_stop"]}`. Требует правки
     формы пульса (Platform/03-worker/data/heartbeats.schema.json) — работа «Спецификации».
   - Порядок виден только по тому, что строки журнала идут по времени (журнал — по времени), а по полю пульса порядок
     не виден вовсе; поэтому предложение A сильнее.

**Что должно быть видно после расширения.**

- При `@sigterm <имя>` — обе строки журнала в порядке `before_stop_all` → `after_stop`, а единицы остановлены, место и
  слот отданы (последний пульс написан), код выхода тот же (0).
- При падении (SIGKILL) — строк нет: вызовы остановки зовутся только при упорядоченной остановке.
- При ошибке в `before_stop_all` — строка журнала с причиной, остановка продолжается (единицы остановлены, слот отдан),
  код выхода не меняется. Для этого учебному воркеру нужно уметь упасть в `before_stop_all` «по заказу стенда» —
  например, тем же полем строки единицы (`fails`), если владелец так решит.

## Эскизы сценариев (пишутся после расширения; здесь — только форма и ожидания)

Общая подготовка: `@start resource`, `@start controller`, `@start worker w-1`; счётчик создаётся дверью консоли
(`console POST /counters {"name": "c5", "start": 1}`), просьба — `console POST /testsub/requests {"unit": "c5", "add": 5}`
(форма приёмки главы 3.6, сценарий 05).

```
сценарий 01-slow-action-unknown-late
  @start worker w-1                                                  ok
  console POST /counters {"name": "c5", "start": 1, "slow": 12}       201 {"id": "c5", "revision": 1}
  console POST /testsub/requests {"unit": "c5", "add": 5}             @oneof 202 {"queued": "$rid"} | 200 {"answered": "@any"}
  store GET /v1/get?key=objects/testsub/commands/$rid                 200 {"items": {"outcome": "unknown", "unit": "c5"}}   # ~10 с: таймаут
  @until 40 store GET /v1/get?key=objects/testsub/commands/$rid       200 {"items": {"outcome": "performed", "late": true}}

сценарий 02-one-call-per-group
  # та же единица c5 (медленная); вторая просьба подана, пока первый вызов не вернулся
  console POST /testsub/requests {"unit": "c5", "add": 7}             @oneof 202 {"queued": "$rid2"} | 200 {"answered": "@any"}
  store GET /v1/get?key=objects/testsub/commands/$rid2                200 {"index": "", "items": null}   # второго вызова нет
  @until 60 store GET /v1/get?key=objects/testsub/commands/$rid2      200 {"items": {"outcome": "performed"}}

сценарий 03-failing-unit-stalled
  console POST /counters {"name": "c6", "start": 1, "fails": true}     201 {"id": "c6", "revision": 1}
  @until 170 resource GET /v1/objects/testsub/heartbeats/w-1?scope=local
                                                                     200 {"status": [{"id": "c6", "stalled": true}]}

сценарий 04-stop-calls
  @sigterm w-1                                                       ok        # (предложение: @exit 0)
  console GET /events?unit=audit/testsubworker&kind=worker.stop_calls 200 {"events": [{"kind": "worker.stop_calls"}]}
```

Замечания к эскизам (не часть черновика сценария):

- В сценарии 03 элемент `status` сравнивается как массив «без порядка» (порядок элементов норма не задаёт) — длина
  должна совпасть, поэтому у воркера должен быть ровно один элемент `status` (одна единица).
- `phase` у падающей единицы — слово подсистемы; в ожидании его лучше не называть (норма требует только `stalled`).
- В сценарии 01 ожидание `unknown` нужно выдержать на середине: таймаут наступает через `PERFORM_TIMEOUT` (10 с) от
  начала вызова, а поздний ответ — через `slow` секунд (12) плюс время до начала вызова; зазор между ними мал, поэтому
  шаг читает метку в `@until`-режиме с двумя разными ожиданиями по очереди, а не «спит и смотрит один раз».
- В сценарии 02 «второй вызов в группу» для testsub совпадает со «вторым вызовом в ту же единицу»: у testsub нет
  `placement.group_by`, группа — сама единица. Общая группа (две единицы с одним `feed`) проверяется на testsub2, но у
  него просьбы `free` с исходом `fetched`, и меток они не пишут — поэтому на нём этот чек не выражается.

## Оговорки

- Три расширения — работа по реализации (учебный воркер и, для 2, платформенная библиотека), а не по словарю
  директив; в курсе в этой части ничего не правится.
- Названия новых полей (`slow`, `fails`) и вид строки журнала (`worker.stop_calls`) — предложения; владелец называет их
  окончательно. Поля строки единицы меняют форму `unit.fields` манифеста — это правка каталога манифестов («Спецификация»),
  а не курса.
- `placement.group_by` у testsub не объявлен, поэтому «один вызов на группу» проверяется как «один вызов на единицу».
- Если платформа не получит отступ повтора (расширение 2), `stalled` не появится никогда, и П/03.3-02 остаётся
  проверкой чтением — это долг платформы, а не стенда.
