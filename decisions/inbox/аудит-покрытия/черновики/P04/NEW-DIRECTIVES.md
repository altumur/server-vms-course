# Черновик: новые директивы стенда для приёмки P/04

Черновик к словарю директив и дверей общего README приёмки (`Platform/common/acceptance/README.md`, раздел
«Словарь директив и дверей», таблица «Директивы стенда»). Ничего в курсе не правится: это предложение
«Спецификации» владельцу словаря. Свои новые директивы черновиков P/03 уже предложены там — здесь только
указатели на них (раздел 3), чтобы владелец видел полный список одним местом.

Новые строки словаря (в форме словаря: `форма | смысл`; колонка «Урок» — как в общем README):

| Форма | Смысл | Урок |
|---|---|---|
| `@install <sub> <файл>` | установить манифест подсистемы `<sub>` из файла `<файл>` — командой установки манифеста «Стенда» (`manifest-put {socket} {file}`) | P/04 (предложение 2026-10-30) — **ОТКЛОНЕНО** при разборе P/04, 2026-10-30 (см. раздел 4) |
| `@exit <код>` как ожидание `@start controller [<sub>]` | процесс контроллера вышел с кодом `<код>` не позже 10 с (вывод не сравнивается) | P/04 (предложение 2026-10-30) — **ПРИНЯТО** при разборе P/04, 2026-10-30 (общий README приёмки) |

Подробности — по обеим директивам ниже; вердикты разбора — в разделе 4.

## 1. `@install <sub> <файл>`

**Вердикт разбора P/04 (2026-10-30): ОТКЛОНЕНО** — см. раздел 4. Раздел остаётся как запись оснований; черновик
`черновики/P04/D09-manifest-swap.md` остаётся эскизом чтением.

**Зачем (место в норме).** П/04 Н3 «Гонки» («смену `rev` контроллер видит проверкой метки (P/02.3) и
останавливается с кодом 0; новый экземпляр с новой `rev` перечитывает всё»), Н3 «проход()» шаг 1 («прочесть
каталог манифестов (platform/manifest/*) — каждым проходом: манифест near.sub появился — сродство действует с
этого прохода; нет его — сродства нет, near_waiting»), Н1.3 `near` («Манифеста `sub` нет в каталоге — сродство не
действует…; сродство включается с прохода, на котором манифест `sub` появился в каталоге»), Н3 «manifest_rev —
страж правила», П/02.3 Н3 «Смена манифеста» (процедура `manifest put`; работающий процесс читает метку и
останавливается с кодом 0). Чек-лист П/04-16 («`manifest_rev` на строке, страж правила, `manifest_behind`, штамп
старых строк (ADR-0068) — проверяется чтением») и П/04-27 («… манифеста `near.sub` нет в каталоге — сродства
нет, `near_waiting` в отчёте прохода, включение с прохода, на котором он появился … — чтением: стенд ставит
каталог `testsub` + `testsub2` до старта, директивы установки манифеста посреди сценария в словаре «Стенда» нет»).

Свойства «манифест сменился на ходу» и «манифест соседа появился в каталоге» в корпусе приёмки не выражены: в
словаре нет директивы установки манифеста, а команда установки манифеста «Стенда» (`manifest-put {socket}
{file}`) раньше вызывается только при подготовке стенда — по одному манифесту, до первого `@start`. Из-за этого
оба пункта чек-листа (П/04-16 и часть П/04-27) помечены «проверяется чтением».

**Форма.**

```
@install <sub> <файл>
```

- `<sub>` — имя подсистемы (манифеста). Имя манифеста внутри файла должно быть равно `<sub>`; иначе — отказ
  раннера (установщик кладёт манифест по его `name`, П/02.3 Н3 «Смена манифеста»: «подставить кандидат по его
  name»).
- `<файл>` — путь к файлу манифеста: относительный — от каталога приёмки урока (как у `@store-op`: «путь
  `inputs/…` — от каталога приёмки урока»), абсолютный — как есть. Файл — целиком, байты как есть.
- Действие: команда установки манифеста «Стенда» (`manifest-put {socket} {file}`) с `{socket}` — `admin.sock`
  хранилища стенда. Раннер не пишет в хранилище ничего сам: пишет установщик (П/02.3 Н1.5: «Писатель строки и
  метки — только установщик … правом admin»).

**Ожидание.** `ok` — команда вернула код 0 (манифест положен; «без изменений» — тоже код 0, П/02.3 Н4). Иной
код — отказ раннера (не `ok`): П/02.3 Н4 — «`manifest put` отказанного файла → не положено → код возврата 2,
отказ на stderr». Сравнивать вывод команды не нужно.

**Что требуется от реализации/раннера.** Только раннер: у него уже есть команда установки манифеста «Стенда» —
нужно вызвать её посреди сценария с файлом сценария. От реализации ничего не требуется: манифест, его канонический
вид и метку пишет установщик сам.

Оговорки для владельца словаря:

- **Ревизия.** П/02.3 Н1.5: «Одинаковые yaml и shell — “без изменений”, rev не растёт». Значит повторная
  установка того же файла ревизии не поднимает и смены манифеста не вызывает: для проверки смены нужен файл,
  отличающийся от установленного. Каким считается «тот же yaml» — байтами или канонической формой — вопрос к
  «Спецификации»: от ответа зависит, годится ли фикстура, отличающаяся только комментарием YAML.
- **Установка нового имени.** Директива позволяет установить манифест, которого в каталоге не было (новое имя
  подсистемы): это нужно для «сродство включается с прохода, на котором манифест появился». Форма имени —
  по П/02.1 (имя манифеста; `[a-z][a-z0-9_-]{0,31}`, как у значения `near_waiting` в отчёте прохода, Н1.2).
- **Права.** Установка идёт через `admin.sock` (полные права) — в отличие от строк сценарной роли, у которой
  права только на `testsub/` и `testsub2/` (README приёмки P/04). Сама директива прав не требует: права нужны
  команде установки, а не сценарной роли.
- **Кто следит за меткой.** Метку читает контроллер (`platform/manifest/<sub>/rev` в его списке чтения, П/04
  Н1). Воркер метку не читает (П/03.2 Н1: список чтения её не содержит) и на смену манифеста не останавливается —
  поэтому смена манифеста останавливает только контроллер, и перезапускать надо лишь его.

**Кто проверяет.** Черновик `черновики/P04/D09-manifest-swap.md`: эскиз (а) — смена манифеста на ходу
(контроллер останавливается с кодом 0, отчёт прохода замирает, новый экземпляр читает новую ревизию, строка
размещения штампуется; страж правила — строка с ревизией больше ревизии контроллера не трогается,
`manifest_behind` растёт); эскиз (б) — `near_waiting` и включение сродства с прохода появления манифеста соседа.
Фикстуры эскизов — `черновики/P04/inputs/`.

## 2. `@exit <код>` у `@start controller` и ожидание кода выхода работающего процесса

**Вердикт разбора P/04 (2026-10-30): `@exit <код>` у `@start controller` — ПРИНЯТО** (внесено в общий README
приёмки); `@wait-exit` (код выхода уже работающего процесса) — ОТКЛОНЕНО. См. раздел 4.

**Зачем (место в норме).** Platform/common/contracts/schema.md «Граница»: «достоверно испорченная/слишком новая
схема — отказ старта с кодом 2»; Platform/06-console/data/schema.outcomes.tsv (читатель `<s>controller`: «старт
контроллера — не стартовать, выход с кодом 2 и строкой журнала, как `version > SCHEMA`… повтор — перезапуском
юнита»); П/02.3 Н3 «Смена манифеста»: работающий процесс при смене метки «останавливается с кодом 0».
Чек-лист П/04-23 («проверка схемы при старте контроллера … не число или выше SCHEMA — не стартовать, код 2 до
чтения манифеста … — проверяется чтением»).

**Форма.** Ожидание `@exit <код>` у `@start controller [<sub>]` — как у `@kit-start` и `@store-start` в словаре
общего README приёмки: процесс вышел с кодом `<код>` не позже 10 с, вывод не сравнивается. Иначе — `ok` (процесс
жив). Форма `@exit <код>` у `@start worker` и у `@sigterm` уже предложена в `черновики/P03/NEW-DIRECTIVES.md` §2
— здесь она распространяется на `@start controller`.

**Что требуется от реализации/раннера.** Только раннер: уметь сравнить код выхода процесса контроллера (умеет
уже для `@kit-start`).

**Отдельная нужда — код выхода УЖЕ работающего процесса.** Смена манифеста останавливает работающий контроллер
с кодом 0, и этот код — часть нормы (П/02.3 Н3 «Смена манифеста»), а не диагностика. Словарь сегодня не умеет
ждать код выхода процесса, который раннер запустил раньше: `@exit` — ожидание старта. В черновике D09 это место
заменено наблюдением замершего отчёта прохода («после смены манифеста отчёт не обновляется» — прямое следствие
того, что проход, в котором контроллер увидел новую метку, не доходит до конца, а отчёт пишется в конце
прохода). Возможная форма для словаря: `@wait-exit <роль>[#n] <код>` — дождаться выхода уже работающего процесса
с кодом `<код>` (не позже срока; иначе — отказ раннера). Решение — за владельцем словаря; без него соответствующая
часть П/02.3-03 остаётся проверкой чтением.

## 4. Вердикты разбора P/04 по предложениям этого файла

Разбор P/04 («Спецификация», 2026-10-30, внесено dc93ebc74) — по предложениям самого файла:

| Предложение | Раздел | Вердикт | Следствие |
|---|---|---|---|
| `@exit <код>` как ожидание `@start controller [<sub>]` | §2 | **принято** | внесено в общий README приёмки: у `@start controller` ожидание `@exit <код>` — процесс вышел с кодом `<код>` не позже 10 с от запуска, вывод не сравнивается (рядом с `@exit` у `@start worker`) |
| `@install <sub> <файл>` | §1 | **отклонено** — не определено: какие процессы останавливаются (только контроллер, у которого процесс читает метку, или ещё и воркеры), права нового манифеста (у сценарной роли прав на запись нет — запись идёт через `admin.sock`, и это отдельное решение), что считать «тем же yaml» (байты или каноническая форма) | `черновики/P04/D09-manifest-swap.md` остаётся эскизом чтением: смена манифеста на ходу и появление соседнего манифеста в каталоге (`near_waiting`) в корпусе приёмки проверяются чтением (П/04-16, П/04-27) |
| `@wait-exit <роль>[#n] <код>` — код выхода УЖЕ работающего процесса | §2 (отдельная нужда) | **отклонено** | код выхода работающего контроллера после смены манифеста в корпусе приёмки остаётся проверкой чтением (П/02.3-03); наблюдение замершего отчёта прохода в черновике D09 остаётся записью замысла |
