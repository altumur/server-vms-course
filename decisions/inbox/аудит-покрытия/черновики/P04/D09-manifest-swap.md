# Черновик D09 — смена манифеста на ходу и `near_waiting`: два эскиза.
#
# @install отклонён при разборе P/04 — эскиз остаётся чтением.
#
# Файл — `.md`, а не `.tsv`: обе проверки требуют того, чего на стенде нет. (1) Смены манифеста посреди сценария:
#   в словаре «Стенда» нет директивы установки манифеста — это прямо отмечено в чек-листе П/04-27 («директивы
#   установки манифеста посреди сценария в словаре «Стенда» нет»); команда установки есть («Команда установки
#   манифеста» `manifest-put {socket} {file}` общего README приёмки), но раньнер ею ставит манифесты стенда по
#   одному до первого `@start`. (2) Манифеста, у которого `near.sub` нет в каталоге: каталог стенда состоит из
#   двух манифестов (`testsub`, `testsub2`) и посреди сценария не меняется, а `near` есть только у `testsub2`, и
#   его `near.sub` — `testsub`, который в каталоге есть.
#   Ниже — эскизы двух сценарных TSV (готовые к переносу в `.tsv`), перечень фикстур и список спорных мест,
#   которые надо решить владельцу приёмки, прежде чем черновик станет сценарным файлом.
#
# Что проверяет:
#   (а) Смена манифеста на ходу: работающий контроллер видит новую метку и останавливается с кодом 0 — отчёт
#       прохода замирает (последний `at` не меняется); новый экземпляр контроллера читает новую ревизию
#       (в отчёте — другая `manifest_rev`) и штампует строку размещения своей ревизией. Сверх того — страж
#       правила: строка размещения, помеченная ревизией БОЛЬШЕ ревизии контроллера, не трогается, а счётчик
#       `manifest_behind` растёт.
#   (б) `near` без манифеста соседа: манифест, у которого `near.sub` нет в каталоге, — сродства нет, единица
#       размещается без него, а подсистема стоит в `near_waiting` отчёта прохода; после установки манифеста
#       соседа сродство включается с прохода, на котором манифест появился в каталоге (поле `near_waiting`
#       исчезает).
#
# Место нормы:
#   — Platform/02-installer/spec/02.3-installer.norms.md Н1.5 (строка `platform/manifest/<sub>` и метка
#     `platform/manifest/<sub>/rev`; «rev строго растёт»; «Одинаковые yaml и shell — “без изменений”, rev не
#     растёт»), Н3 «Смена манифеста» (процедура `manifest put`: новая rev := прежняя + 1, запись строки с `cas`,
#     запись вида, доведение метки; «работающий процесс, на каждом проходе и не реже чем раз в 30 с: прочитать
#     метку; rev метки ≥ запомненной и не равен ей, или метки нет → как смена: остановиться с кодом 0;
#     супервизор запускает заново»), Н3 «Старт процесса» (шаг 4 «запомнить rev строки; служить»; программа
#     воркера сверяет `W2C_MANIFEST_REV` с rev прочитанной строки), Н4 («`manifest put` отказанного файла —
#     код возврата 2, отказ на stderr»). Чек-лист P/02.3-01 (первая установка — `rev: 1`, изменение поднимает
#     `rev` на один), P/02.3-03 (смена метки: процесс останавливается с кодом 0 и перезапускается супервизором).
#   — Platform/04-controller/spec/04-controller.norms.md Н1.1 (строка `<sub>/placement/<id>`: поля `worker`,
#     `reason`, `at`, `rev`, `manifest_rev`; `manifest_rev` — необязателен, «строки без него штампует проход»),
#     Н1.2 (отчёт прохода: `manifest_rev` — «ревизия манифеста контроллера», `manifest_behind` — «строк, решённых
#     более новым манифестом», `unplaced`, `near_waiting`), Н1.3 (`near`: «Манифеста `sub` нет в каталоге —
#     сродство не действует, единица размещается без него, строки `sub` контроллеру не нужны; подсистема — в
#     `near_waiting` отчёта прохода (Н1.2); сродство включается с прохода, на котором манифест `sub` появился в
#     каталоге»), Н3 «проход()» шаг 1 («ревизия: прочесть ревизию манифеста; строки размещения без
#     manifest_rev — проштамповать своей (один раз); прочесть каталог манифестов (platform/manifest/*) — каждым
#     проходом: манифест near.sub появился — сродство действует с этого прохода; нет его — сродства нет,
#     near_waiting»), абзац «Штамп manifest_rev без изменения цели — отдельная запись с cas и guard turn, intent
#     ему не нужен», раздел «manifest_rev — страж правила» («перед каждой записью строки размещения (разместить,
#     переехать, снять): row.manifest_rev > моя ревизия → не трогать; manifest_behind + 1»), Н3 «Гонки» («Смена
#     манифеста во время прохода: `rev` читается раз на проход, решения пишутся с этим `manifest_rev`; смену `rev`
#     контроллер видит проверкой метки (P/02.3) и останавливается с кодом 0; новый экземпляр с новой `rev`
#     перечитывает всё; строка с прежним `manifest_rev` — снимок решения, не правило»), Н3 «выбрать» («размещена
#     (worker ≠ "") → как есть; не пересматривать»), Н4 (таблица причин: «строка размещения решена более новым
#     манифестом → не трогать; `manifest_behind`; перезапуск контроллера с новым манифестом»). Чек-лист П/04-16
#     («`manifest_rev` на строке, страж правила, `manifest_behind`, штамп старых строк (ADR-0068) — проверяется
#     чтением»), П/04-27 («`near` … манифеста `near.sub` нет в каталоге — сродства нет, `near_waiting` в отчёте
#     прохода, включение с прохода, на котором он появился … — чтением: стенд ставит каталог `testsub` +
#     `testsub2` до старта, директивы установки манифеста посреди сценария в словаре «Стенда» нет»).
#   — Решение ADR-0068 (спека в ключе хранилища, ревизия правила на решении): «rev не тот, с которым стартовал, —
#     … выход кодом 0»; контроллер пишет в отчёт прохода ревизию и счётчик отставания.
#   — Договор азбуки меток, П/06.6 Н2.1 — здесь не участвует; П/01.1 Н1 — «запись без `cas` — поверх»,
#     «два создания с `cas: ""` — проходит ровно одно» (эскиз (а), сценарий 02: строка размещения пишется с
#     `cas: ""`, то есть как создание).
#
# Подготовка (стенд и фикстуры):
#   — Стенд testsub: ресурс, контроллер, воркер `w-1`, счётчик `c1` (дверь консоли `POST /counters`). Стенд
#     testsub2: ресурс, контроллер, воркер `t-1`, полка `s-1` (дверь `console2`: `POST /shelves`,
#     `POST /tallies`), — как в черновиках D05/D06.
#   — Фикстуры (три файла, каждый отличается от манифеста стенда ровно одной строкой). Пути в эскизах — от каталога
#     приёмки урока (как у `@store-op`: «путь `inputs/…` — от каталога приёмки урока»), то есть в приёмке урока их
#     место — `Platform/04-controller/acceptance/inputs/`; в этом черновике те же файлы лежат рядом с ним, в
#     `черновики/P04/inputs/`:
#       `inputs/testsub-swap.subsystem.yaml` — манифест `testsub` с `capacity: {from: capacity, default: 5}`
#         вместо `default: 4`. Смена должна быть настоящей сменой манифеста (Н1.5: «Одинаковые yaml и shell —
#         “без изменений”, rev не растёт»), поэтому файл должен отличаться от установленного; ёмкость 4 → 5
#         ничего не меняет для сценария (единица одна, места хватает).
#       `inputs/testsub2-near-testsub3.subsystem.yaml` — манифест `testsub2` с `near: {sub: testsub3, …}`
#         вместо `near: {sub: testsub, …}`; остальное — байт в байт.
#       `inputs/testsub3.subsystem.yaml` — манифест с именем `testsub3` (копия манифеста `testsub` с одной
#         заменой `name: testsub` → `name: testsub3`). Он нужен, чтобы «сродство включилось» было чем-то
#         вызвано: до его установки `testsub3` в каталоге нет.
#   — Оговорка о фикстуре `testsub3`: её примет ли установщик (P/02.1 Н3 «загрузить_каталог») — вопрос к
#     владельцу приёмки и к «Спецификации»: копия манифеста `testsub` под другим именем ссылается на роли и
#     семьи, которых у `testsub3` нет. Если её приём отвергнут, нужен иной третий манифест — минимальный, с
#     формой по P/02.1; в этом черновике он не приведён, потому что его форма — не мой выбор.
#
# Существующие директивы: `@start resource`, `@start controller [<sub>]`, `@start worker [<sub>] <имя>`,
#   `@sleep <с>`, `@until <с> <запрос>`, `@as <роль>`; двери `console` (`POST /counters`), `console2`
#   (`POST /shelves`, `POST /tallies`), `store` (строки размещения, слоты, удержания), `admin` (чтение строки
#   манифеста), `resource` (отчёт прохода).
# Новых директив: `@install <sub> <файл>` — установка манифеста посреди сценария (предложение владельцу
#   словаря, см. `черновики/P04/NEW-DIRECTIVES.md` §1). Без неё оба эскиза не выразимы: смена манифеста и
#   появление манифеста соседа в каталоге — это и есть предмет проверки. Дополнительно в эскизе (а) помечено
#   место, где не хватает директивы «дождаться кода выхода работающего процесса» (§2 NEW-DIRECTIVES.md).
#
# Сроки и допуски:
#   — проход раз в 5 с (П/04 Н1.4 `PASS_EVERY`); отчёт пишется в конце прохода.
#   — смена манифеста видна процессу, который читает метку «на каждом проходе и не реже чем раз в 30 с»
#     (P/02.3 Н3 «Смена манифеста»): контроллер читает метку каждым проходом (П/04 Н1 «читает:
#     `platform/manifest/<sub>/rev`»), поэтому сон 12 с после установки — с запасом два прохода.
#   — «отчёт замерз» проверяется двумя чтениями подряд (после установки и ещё через 12 с): так не мешает
#     возможной последней записи отчёта тем проходом, в котором контроллер увидел смену.
#   — потолок сценария — 3 минуты; эскиз (а) сценарий 01 ≈ 80 с, сценарий 02 ≈ 60 с; эскиз (б) ≈ 90 с. Потолок
#     не превышен.
#
# Почему ожидание именно такое:
#   — «контроллер остановился» наблюдается замершим отчётом, а не кодом выхода: код остановки по смене манифеста
#     — 0 (P/02.3 Н3 «Смена манифеста»), но TSV не умеет ждать код выхода уже работающего процесса (в словаре
#     есть `@exit` только как ожидание старта — предложение §2). Замерший `at` — прямое следствие нормы: проход,
#     в котором контроллер увидел новую метку, не доходит до конца (шаг 1), а отчёт пишется в конце прохода.
#   — `manifest_rev` в отчёте — «ревизия манифеста контроллера» (Н1.2); после перезапуска она другая, потому что
#     новый экземпляр читает новую строку манифеста (P/02.3 Н3 «Старт процесса», шаг 4). Проверяется не число, а
#     отличие от прежней (`@not($r1)`) — номер ревизии задаёт установщик, а сценарий не должен зависеть от того,
#     сколько раз до него ставили манифест.
#   — строка размещения после перезапуска: «размещена (worker ≠ "") → как есть; не пересматривать» (Н3
#     «выбрать») — воркер прежний, а `manifest_rev` строки — либо прежний («строка с прежним manifest_rev —
#     снимок решения, не правило»), либо новый (П/04-16 «штамп старых строк», Н3 «проход()» шаг 1 и абзац о
#     штампе). Эти два прочтения расходятся — см. «Спорные места» № 1; в эскизе принят второй (штамп), и это
#     единственное место, где ожидание зависит от нерешённого вопроса.
#   — страж правила (`manifest_behind`) в эскизе (а) сценарий 02 проверяется не гонкой двух контроллеров, а
#     строкой, помеченной ревизией 999: она «решена более новым манифестом», поэтому контроллер её не трогает
#     (Н3 «manifest_rev — страж правила») и ведёт счётчик `manifest_behind` (Н4: «строка размещения решена более
#     новым манифестом → не трогать; `manifest_behind`»). Единица при этом остаётся неразмещённой: её строка
#     размещения не переписана.
#   — `near_waiting` появляется ровно тогда, когда манифеста `near.sub` нет в каталоге (Н1.3 `near`, Н1.2
#     `near_waiting`); исчезновение поля — это и есть наблюдаемое «сродство включилось с прохода, на котором
#     манифест появился в каталоге». Проверять само предпочтение (предпочтителен воркер, держащий соседа) не
#     нужно: по чек-листу П/04-27 это «чтением» (README векторов `near-of`: «Вектор проверяет только выбор
#     соседа; что предпочтителен воркер, держащий его, … — Н3 «выбрать», чтением»), а соседа у `testsub3` на
#     стенде нет — держать его нечем.
#   — единица в эскизе (б) размещается без сродства: по Н1.3 «Манифеста `sub` нет в каталоге — сродство не
#     действует, единица размещается без него». Проверяется сама строка размещения (воркер есть) и поле
#     `near_waiting` отчёта.
#
# Спорные места (вопросы владельцу приёмки; до их решения черновик не переносится в `.tsv`):
#   1. Штамп старых строк: после смены манифеста строка размещения, помеченная прежней ревизией, — сохраняет
#      прежний `manifest_rev` («строка с прежним manifest_rev — снимок решения, не правило») или получает новый
#      (П/04-16 «штамп старых строк»; Н3 «проход()» шаг 1 говорит о строках «без manifest_rev», а абзац о
#      штампе — о записи с guard turn без изменения цели)? В эскизе принят штамп; при втором прочтении шаг с
#      `manifest_rev` меняется на прежнее значение.
#   2. Природа счётчика `manifest_behind`: «строк, решённых более новым манифестом» (Н1.2) — это сколько строк
#      (счётчик строк) или сколько встреч со стражем (накопительный)? В эскизе проверяется только «не ноль»
#      (`@not(0)`) — оба прочтения удовлетворяют; если владелец хочет точное число, это надо уточнить.
#   3. Гонка за `manifest_behind` с двумя контроллерами (П/04-16 «два контроллера … более новая manifest_rev»,
#      строка 1122 норм) на стенде неустойчива: контроллер, увидевший новую метку, останавливается в том же
#      проходе, а счётчик не нулевой только в том проходе, который совпал с записью более нового контроллера.
#      Поэтому в эскизе страж проверяется строкой с ревизией 999, а не гонкой; гонка остаётся чтением.
#   4. Фикстура `testsub3` (третий манифест): её форму и приёмку установщиком должен подтвердить владелец
#      приёмки вместе со «Спецификацией»; от неё зависит эскиз (б).
#   5. Наблюдение кода выхода работающего контроллера (остановка с кодом 0) — нужна директива; в эскизе заменено
#      замершим отчётом (§2 NEW-DIRECTIVES.md).
#
# Оговорка: эскизы не проверены прогоном — стенд требует доработки (директива `@install`, фикстуры). Все ожидания
#   выведены из норм и общих таблиц исходов; ни одно слово причины, код и имя поля не выдуманы: слово причины не
#   проверяется вовсе (грамматика Н3 «Причина» для этого случая не задана).

## Эскиз (б) — `near` без манифеста соседа

