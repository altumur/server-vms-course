## Стандарт и выбранная граница

OpenAPI 3.1.0 запрещает разные имена одного шаблона той же иерархии. Компоненты сами по себе не активируют операции; параметр пути не обозначает неэкранированный остаток со слэшами. В действующем Paths имя path-параметра соответствует оставшемуся шаблону; если operationId назван, он уникален. [OpenAPI 3.1.0: шаблоны](https://spec.openapis.org/oas/v3.1.0.html#path-templating), [компоненты](https://spec.openapis.org/oas/v3.1.0.html#components-object), [параметры](https://spec.openapis.org/oas/v3.1.0.html#parameter-object), [операции](https://spec.openapis.org/oas/v3.1.0.html#operation-object).

Стандарт описывает конечные пути/операции; допуск и передача произвольного хвоста остаются в уже существующей норме P/06.3 и P/06.7-R008. Это сознательная граница представления, а не новая дверь. Одна лишь валидация OAS не доказывает полноту этого семейства. Нового языка описания, x-поля, универсального интерпретатора или отдельного генератора не требуется.

## Связывание шести блоков

| Компонент | Нынешний владелец пути | Остаток после подстановки |
|---|---|---|
| UnitsCollection | unit.rows выбранной подсистемы | список/создание |
| UnitItem | тот же unit.rows | прежний UnitId |
| TableCollection | имя таблицы выбранной подсистемы | список/запись |
| TableItem | та же таблица | прежнее имя строки |
| PassRoot | объявленный door.pass | прежний нормативный хвост |
| ConsoleFile | точное console.files | ничего, всё имя конкретно |

Подстановка выполняется в существующем потребителе API с тем же принятым каталогом. Это разрешение на поддержку стандартного конструкта существующим классом, не создание новой формы настройки. Таблица выше фиксирует нынешние шесть вариантов; описание/summary не парсится как язык. Выбор ветви не угадывается по одному названию параметра. Например, forwarding-route из door.routes не становится unit.rows только потому, что старый шаблон назвал сегмент rows.

Для каждого связывания обязательны:

1. Разрешить `$ref` исходного PathItem и получить собственный действующий блок. Вставить конкретные каталожные сегменты в путь, сохранив нынешние короткий корень, явно названный корень и монтирование там, где они допущены нормой. Каталог проверяется прежними правилами допуска; неизвестное имя не получает новую ветвь.
2. Убрать только те path-параметры, значения которых уже стали конкретной частью пути, на уровне PathItem и операции. Не менять оставшиеся id/name, их типы, порядок декодирования и прежний badkey. Полное имя file вставляется всеми объявленными сегментами, без glob и перекодирования slash.
3. Согласовать серверный префикс с уже подставленным путём: выбранный sub нельзя добавить второй раз. В конкретном примере ниже путь уже содержит /testsub2, поэтому сервер содержит только прежний origin. Origin остаётся контекстом адреса, не новой настройкой сервера.
4. Не совмещать ветви широким anyOf и необязательными общими заголовками. Обязательность ключа, версии, query/body, media, ответы/отказы и права сохраняются у своей операции. Подстановка не смешивает произвольное тело pass с ClientFields или TableInput.
5. Сохранить существующий приоритет конкретных адресов, каталожных вариантов и параметров, выбор метода после пути и отсутствие запасной маршрутизации. Пересечения конкретного каталога проверяются отдельно; недопустимая/неоднозначная ветвь не разрешается молча. Не менять прежние 404/405.
6. Сохранить исходную идентичность операции/адаптера и происхождение: исходный pointer + method, компонент, каталожная запись и полученный путь. При необходимости уникального operationId в конечном документе показать детерминированное соответствие старой идентичности; не менять Op по случайному новому порядку обхода. Новых публичных operationId без необходимости не вводить.

Нельзя объявить шесть перенесённых неиспользуемых компонентов полным API. Действующий конкретизированный документ может содержать развёрнутые блоки либо ссылки на уже специализированные блоки; неизменённый `$ref` с оставшимся rows-параметром не годится для конкретного пути. Все шесть исходных блоков должны быть реально потреблены и отражены в происхождении. Старый неразрешённый шаблонный файл сам по себе не становится полным конкретным контрактом.

## Решение по хвосту

- ConsoleFile конкретизируется точным конечным списком файлов. Многосегментное имя уже известно, отдельного tail-параметра нет.
- PassRoot описывает допускающий префикс. Его уже разрешённый остаток и query передаются прежней процедурой без изменения исходного пути, числа сегментов или прав.
- Две domain-at-tail операции связываются с прежним владельцем P/06.7-R008 и door.routes. Нулевой, один и несколько сегментов проверяются отдельно. Нельзя потерять две старые ветви только потому, что в стандартном описании префикса они объединены: карта покрытия сохраняет обе исходные обязанности.

Пустая, одно- и многосегментная формы не превращаются в новые aliases. Не перекодировать slash в %2F ради соответствия OAS. Открытый переменная адреса сервера не заменяет admission каталога и этим решением не вводится. Полное чисто-OAS перечисление всех длин хвоста не требуется как способ исполнения этого решения: его полнота доказывается совместно со старой нормативной процедурой. Новый суженный одно-сегментный {tail} не принимается.

Архитектор подготовил внешний пример из прежнего API и канонического testsub2: `/testsub2/tallies`, `/testsub2/tallies/{id}`, `/testsub2/shelves`, `/testsub2/shelves/{name}`, `/testsub2/entries`, `/testsub2/deep/er/Name_1-2.v3.js`. Пример не охватывает весь каталог, остальные 121 операции, дополнительные нормативные HEAD, domain-at и неограниченный хвост; их приёмка не присваивается. ## Исполнение и приёмка

spec103 уточняет API-план и источник по выбранному способу: конкретизация параметров/servers, карта достижимости и старых идентичностей, полный каталог и хвостовые примеры. Повторного выбора рамки у Архитектора не требуется. Снятие прежней блокировки S08 касается выбранного представления; конкретные исходные блоки и кодовые доли всё равно активирует coord103 после проверки их точной области. Верхняя граница обычного источника 71 путь сама по себе не расширяется. coord103 может активировать исходник только в проверенной точной области общего плана; это решение не меняет её автоматически.

Доли кода потребителей и судей назначаются отдельно по прежним владельцам: Генераторы — существующие потребители, производители и doorrt2, review103 — существующие проверки. До кода нужны точные файлы, блоки и ожидания и независимая карта всех 19+121 старых операций, двух domain-at-tail ветвей и шести уже нормативных HEAD. Правка одного YAML, один положительный каталог или прохождение схемы не закрывают зависимость.

Проверить полный допущенный каталог, сохранность закрытой формы семейства/обязательных заголовков и тела, корень, явный префикс корня и монтирования, метод/404/405, точный file, хвост с нулём, одним и несколькими сегментами и query, отрицательные чужие имена и семейства. Судья не должен разделять с производителем один ошибочный выбор ветви. Ошибка/неполный ответ не обнаружение мутанта.

При совместной работе S08 не возвращает обычные ответы/схемы к старому 9d7. Блоки для переноса берутся из согласованного составного кандидата с явной картой прежних и новых обязанностей. ResourceRow P/05, DoorState, WorkerRow, четыре нейтральных фона /door, P/03 общие 15 и P/04 агрегаты сохраняются. Иные принятые исправления P/06 активируются coord103 независимо в своей точной области. Поддержка ms не возобновляется. Полное независимое P/09 на 7f6 имеет немедленный приоритет. Новая форма/язык/URI/право вне этой рамки возвращается Архитектору до кода.
