# P/07: тип и сборка существующего unread частей

7 ноября 2026, Архитектор. Уточнение текущего reader-поля для ADR-0129 (18), после закрытых worker-aa06 и refresh-ceb решений. Запрос `b0b2c057247960af89f72c90c94be43e6f6414f71ab8759fdd304b061568910a`, источник `16996d715fb74e1bbd6144b11a53518534c76b11`. Проверены семь точных мест по SHA/UTF-8/символьным координатам и исходная строка view-rows.outcomes. Schema, JS, тесты и программы авторов не исполнялись.

P/10-R004 уже называет `unread` списком непрочитанных частей. P/08.1 и исходы `domain/view-rows/<part>` требуют пропустить нечитаемую часть и выразить неполноту полем ответа. У ServedView пока нет именованной типовой привязки этого поля. Это пробел представления существующего reader-результата, не разрешение нового wire-поля и не экспериментальный вывод о том, что нынешний валидатор принимает или отклоняет образец. `May.unread` о ролях — другой вход и здесь не используется.

Выбран тип **optional Part[]**. Каноническое имя части остаётся Schema Object существующего параметра Part. Владелец привязки — P/08 API ServedView; P/10 GET /domain 200 уже ссылается на него. Точный новый именованный узел после отдельной исходной декларации:

```yaml
# /components/schemas/ServedView/allOf/1/properties/unread
unread:
  type: array
  items:
    $ref: '#/components/parameters/Part/schema'
```

Поле не добавляется в required. Не копируются регулярное выражение или вторая схема P/10; не вводятся minItems/maxItems/uniqueItems, alias, новый порт, статус, событие или формат. Stored View, его writer и другие поля с именем unread этим не меняются. Типовая привязка не расширяет видимость: ограничения wide/non-wide и прочие существующие правила P/10 сохраняются. Отсутствие поля из-за видимости не доказывает полноту чтения.

Для одной обычной последовательности пагинации в том же контексте применяется следующий сборщик:

1. Если поле отсутствовало на всех прочитанных страницах, в собранном ответе его также нет. Нельзя синтезировать `unread: []` из отсутствия.
2. Если поле присутствовало хотя бы на одной странице, в собранном ответе оно присутствует. Значение — объединение встреченных литеральных Part-строк без повторов в порядке первого появления, включая порядок элементов внутри каждой страницы. Итог может быть `[]`.
3. Сравниваются исходные строки, без parseInt, trim, дополнения нулями, сортировки или нормализации. Позднее отсутствие поля или пустой список не стирает ранее наблюдённые части. Это не добавляет uniqueItems-ограничение к отдельному HTTP-ответу: сборщик убирает повторы только в своём итоговом объединении.
4. `unread` — наблюдение чтения частей, а не неизменяемое поле записанного head. Этот явно выбранный сборщик не переписывает первый head: as_of/holder/complete и остальные глобальные поля остаются по принятому правилу. Нельзя выполнять AND/patch complete, выводить его из пустого unread или добавлять клиентский флаг. Межстраничного снимка нет.

Примеры наличия: absent + absent → absent; [] + absent → []; ["0003", "0001"] + ["0001", "0002"] → ["0003", "0001", "0002"]. Это примеры сборки допустимых Part-значений, не новые имена частей или границы формы.

Валидный ответ 200 с `unread`, включая непустой список, — обычное наблюдение неполноты. Он не становится domain:null или транспортной ошибкой. То же относится к штатным complete:false/unread-состояниям поздней страницы: сохраняются первый head и объявленная неполнота, а не фиктивный полный префикс или новый error. Настоящая ошибка HTTP/сети/разбора продолжения сохраняет прежний carrier domain:null по решению ceb; последнее полное значение может оставаться отдельно как private last-known. Существующее исключение cluster-refresh при неуспешном root /servers также остаётся прежним.
