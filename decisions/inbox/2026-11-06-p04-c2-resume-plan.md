# P/04 review C2: resumable server decommission

This is the concrete source design for the Architect decision under ADR-0127 (P/04 C2), before the lesson freeze. It adds no native command, kit part or public HTTP refusal. The new progress row is `<sub>/decommission-pending/<host>`, distinct from the exact final mark `<sub>/decommissioned/<host>`. The Architect chose this sibling prefix so prefix readers cannot mistake progress for a final mark. Architect follow-ups explicitly authorize exactly this P/02 controller write prefix with its ordinary read/delete projection, plus reservation of decommission-pending in rowsName/tableName of schemas 02.1 and 02.2. No other family/role right changes. Workers/console keep reading the unchanged final key.

The progress row fixes the request's opaque index, its asked_at, manifest revision, the complete ordered list of candidate slot names and their observed indices, the owned book from prefixes, and final-mark metadata. It records remaining candidates, released/skipped names, a current release chunk and its cleanup cursor. The complete input/row/key reads and representable progress/final objects are checked before acceptance; a preflight failure changes no slot or order. A row/body ceiling remains a real refusal, not permission to publish a partial final mark.

Accept progress and delete want under CAS plus placement-turn and exact-request guards. A pending server is outside the placement pool and receives no new order row. Every modifying batch counts the progress/service writes as well as slot writes/deletes, and counts all distinct guards against BATCH_WRITES/BATCH_GUARDS and the body ceiling. No guard duplicates a written key; its CAS protects that key. Lost turn or an ambiguous response uses the existing barrier, never a blind new plan.

A release chunk contains at most BATCH_WRITES-1 slots plus the progress write. CAS is against the original planned versions; a changed candidate is skipped, never adopted at a newer version. In one atomic batch, set released=true while keeping readable holder/gen/server/until and write progress state=cleaning/current. The P/01 batch index is shared by every slot and progress row. Therefore after a lost answer or a controller restart the index of the cleaning progress row is the exact release index for those slots, without a slot re-read.

During cleanup, process one current slot at a time and split its ordered from keys. Deletes and progress update share one batch, guarded by placement_turn, the fixed request and that slot's exact release index. Before the first progress rewrite preserve the release index as cleanup_index; a later progress-row index must never replace it. 409/412 discards the remaining removals for that slot without re-reading or retrying them with a new version. The adapter must demonstrate that a new holder and its contribution survive. After cleanup, advance to the next current slot, then the next planned release chunk. With no from families, the release batch may advance directly to the next prepared chunk/finalizing.

Only when every planned candidate has been released or proven obsolete and every eligible contribution removal has completed or been discarded under the conservative conflict rule may finalization atomically write the final mark and delete progress (plus a remaining want row if necessary). The fixed request/turn guards still apply. The final mark is never written at acceptance or after merely the first release chunk. A withdrawn/replaced request cancels its old progress under CAS and current request/turn evidence; it does not undo already confirmed releases/deletes. A new request begins with a new plan. The ordinary rule for already existing final marks and guarded legacy contribution remainders remains, without rewriting their slots.

Required witnesses use the existing controller-pass port and actual recorded IO: 62 and 63 slots with no books; more than 63 contributions of one slot; a break/restart after a release chunk before cleanup; capture of an old slot by another server before resumed cleanup; atomic final-marker failure/ambiguous response. Every witness derives batch sizes, CAS/guard indices and marker ordering from actual requests/answers, not expected constants. They are lesson-kit obligations, not a claim of executed SUT acceptance.
