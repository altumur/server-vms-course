# Задел VMS: камера с профилями потоков; `io` — своей подсистемой

**Не делается сейчас.** VMS на паузе до первой полной генерации платформы (ADR-0090); работа — с её стартом.

## Как сейчас (V/01)
Единица `cam` — канал устройства с одним адресом `source`; основной и дополнительный поток одной камеры — две единицы
`cam` (два адреса, например `subtype=0` и `subtype=1`); все каналы одного хоста — у одного держателя (`group_by:
{field: source, cut_at: host}`), устройство — строка `cam/devices/<хост>`. `rec`, `live`, `det` указывают камеру полем
`about: {sub: cam, field: cam}`: запись — на канал основного потока, живое видео и детекция — на канал дополнительного.
Связи «два потока одной камеры» модель не знает: метки, права, `ref`, события — у каждого канала свои; живое видео
профиль по зрителю не выбирает. Устройство без картинки — `kind: io` в той же `cam`.

## 1. Камера с профилями потоков
- Единица `cam` — **место**, которое видит канал (не устройство: регистратор на 16 каналов — 16 мест; права, метки,
  `ref`, тревоги и запись привязаны к месту). Имя `cam` не меняется (переименование в `dev` отклонено: единица «устройство»
  хуже, переименование трогает все уроки VMS, манифесты, `rid`, ключи, книги домена, словарь границы).
- Профили внутри камеры: `streams: {main: <адрес>, sub: <адрес>, …}` (учётные данные — как у `source` сейчас).
- `rec`, `live`, `det` указывают камеру **и имя профиля**; живое видео может выбирать профиль по зрителю (сетка — `sub`,
  полный экран — `main`).
- Держатель открывает каждый нужный профиль одним соединением; устройство — группа и таблица, как сейчас.
- Затрагивает: манифест `cam`, V/01.1–01.5 (двери, держатель, раздача), `rec`, `live`, `det`, страницу (V/08).

## 2. `io` — своей подсистемой
Пока неканальных устройств мало (вход и реле камеры, отдельный модуль) — `kind: io` в `cam` остаётся. Когда их станет
много (СКУД, датчики, контроллеры дверей) — отдельная подсистема `io` со своими единицами и событиями; `cam` — только
видео.

## Триггеры
- старт VMS после первой полной генерации платформы (п. 1 — в план уроков VMS);
- рост класса неканальных устройств (п. 2) — решение владельца.

## Решение владельца 2026-10-26: число профилей не ограничивать; после стадии C
«Лучше не ограничивать кол-во потоков. Дождёмся тогда завершения генерации». Вариант с постоянным набором полей
(`source`, `source_sub`), который уложился бы в нынешние механизмы платформы, отклонён. Профили — произвольный набор
`streams: {<имя>: <адрес>, …}`; для этого платформе нужны механизмы над значениями внутри отображения: `unique:
canonical`, `credentials`/`bound_to`/`secret_in` у каждого адреса, `group_by` с `cut_at: host` по адресам (все профили
камеры — у одного держателя). Это правки уроков P/02 (форма манифеста, загрузчик), P/06.1–06.2 (проверка строки,
секреты), P/04 (группа) и общих договоров `row-check`, `url-credentials`, `group-of` — **после завершения стадии C**
(первая полная генерация платформы), запросом VMS к платформе (ADR-0091) вместе со стартом VMS.

## Вопрос к модели профилей: откуда потребитель берёт поток (владелец, 2026-10-26)
Владелец: «если мы настроили 3 разных потока для rec, live и det, то логично сразу их забирать напрямую каждому своё».
Сейчас (V/01, V/03 гл. 2, V/04 гл. 2) `live` и `det` берут поток только у держателя камеры: на его сервере — общая память
или RTSP петли, на другом — через приёмник кластера записи; прямого RTSP к устройству нет. Держатель `cam` тянется к
регистратору (`home: near`), `live` размещается по своим меткам, `det` — по меткам (`gpu` по умолчанию) с пожеланием
`near: cam`.

Когда у каждого потребителя свой профиль, выигрыш «одно соединение на всех подписчиков» пропадает, остаётся сетевой
переход. Сравнить при проектировании профилей:
- **(A) прямой забор**: каждый потребитель сам открывает свой профиль. Минусы: логика устройства (подключение, отступ,
  `silent`, кодек, отказы) — в трёх подсистемах и с разными суждениями; пароль камеры раздаётся трём подсистемам; предел
  сессий устройства никто не учитывает (вместе с командами и событиями `cam`); профиль с несколькими потребителями всё
  равно требует раздачи; толкающие камеры (сотовые, камера-кластер) недостижимы снаружи.
- **(Б) держатель на профиль, рядом с потребителем** — склонность «Архитектора»: логика устройства и пароль остаются в
  `cam`; каждый профиль открывает воркер `cam` на сервере своего потребителя (`main` — у записи, `sub` — у шлюза,
  профиль детекции — на GPU-сервере); перехода нет, суждение о камере одно, предел сессий считается по всем профилям.
  Цена: у единицы `cam` несколько держателей (по профилю) — для платформы новое; возможно, профиль — своя единица
  (`cam-stream`) с размещением `near` своего потребителя.
Решение — вместе с профилями, после стадии C.

## Подумать: камера w2c — кластер из одного, толкает потоки потребителям (владелец, 2026-10-26)
Владелец: «подумать про вариант с камерой w2c — кластер из одного: если камера будет отправлять поток на детекцию и на
шлюз». Сейчас (V/01.6) камера-кластер из одного толкает поток только в приёмник кластера записи (долгий опрос, толкает,
пока поток кому-то нужен); шлюз и детектор другого сервера получают его через приёмник. Вопрос для модели профилей:
- камера сама — держатель своих профилей (она и есть `cam` на своём кластере из одного): толкает профиль прямо
  потребителю — `main` в приёмник записи, `sub` в шлюз живого видео, профиль детекции — в детектор; приёмник кластера —
  посредник только там, где потребитель камере недоступен;
- что это значит для варианта (Б) «держатель на профиль рядом с потребителем»: у камеры-кластера держатель уже на камере,
  переход сокращается толканием, а не размещением;
- что нужно: адрес и допуск потребителя для толкания (токен `stream` домена — сейчас только для приёмника), желание
  потока от шлюза/детектора (подписка как желание — V/03 гл. 2), учёт сессий и полосы на камере, отказ и возврат к
  приёмнику.
Решение — вместе с профилями, после стадии C.
