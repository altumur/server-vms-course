# Задел VMS: несколько потоков камеры — поток = единица, камера = единица `main`; `io` — своей подсистемой

**Не делается сейчас.** VMS на паузе до первой полной генерации платформы (ADR-0090); работа — с её стартом. Платформу
этот задел не меняет (кроме проверки п. 1.4) — генерацию стадии C не задевает.

## Как сейчас (V/01)
Единица `cam` — канал устройства с одним адресом `source`; основной и дополнительный поток одной камеры — две единицы
`cam` (два адреса, например `subtype=0` и `subtype=1`); все каналы одного хоста — у одного держателя (`group_by:
{field: source, cut_at: host}`), устройство — строка `cam/devices/<хост>`. `rec`, `live`, `det` указывают камеру полем
`about: {sub: cam, field: cam}`. Связи «потоки одной камеры» модель не знает: метки, права, `ref`, события — у каждого
канала свои; живое видео поток по зрителю не выбирает. Устройство без картинки — `kind: io` в той же `cam`.

## 1. Потоки камеры (решение владельца 2026-10-26: «да, перепиши задел»)
1. **Поток = единица `cam`**, как сейчас: потоков сколько угодно (решение владельца «не ограничивать кол-во потоков»
   выполняется без новых механизмов платформы).
2. **Камера = единица потока `main`.** Всё общее для камеры пишется **только в `main`**: имя места («Вход, 1 этаж»),
   метки, права (`ref`), команды устройства (PTZ, выходы), события устройства (движение, вход), тревоги. Правка общего —
   одна запись, атомарно. Учётные данные — один раз, в строке устройства `cam/devices/<хост>` (как сейчас).
3. **Прочий поток** несёт только своё: адрес `source`, имя потока (`profile`, любое) и ссылку на камеру `main: <id>`.
   Общих полей у него нет — расходиться нечему.
4. **Права и метки прочих потоков — через `main`:** поток объявляет `about: {sub: cam, field: main}`; грант `labels:L`
   по договору `may` судит метки `about`, если он есть, — метки камеры покрывают все её потоки; `unit:cam/<main>`
   покрывает и потоки (их `about`). **Проверить при старте VMS:** допускает ли манифест `about` на единицу своей же
   подсистемы и как его видит консоль; если нет — это одна правка платформы запросом VMS (ADR-0091).
5. **Какой поток куда — решает пользователь.** `rec` и `det` указывают поток (поле `cam`, как сейчас) — выбор
   пользователя в форме из потоков этой камеры; у `live` — поток сетки и поток полного экрана, оба выбирает
   пользователь. Платформа и VMS только подсказывают (самый крупный — запись, самый мелкий — сетка), не решают.
6. **Дерево консоли** группирует потоки по камере в оболочке VMS (`vms.shell.html`, её право); модуль платформы рисует
   единицы как есть.
7. **Держатель потока** — по варианту (Б) ниже: каждый поток — своя единица и может размещаться у своего потребителя;
   для этого ослабить «все каналы хоста — у одного держателя», предел сессий устройства считать по всем держателям его
   потоков.
8. Затрагивает: манифест `cam` (поля `main`, `profile`, `about`), V/01.1–01.5, `rec`, `live`, `det` (выбор потока),
   страницу (V/08).

**Отклонено:** профили-отображение внутри одной единицы (`streams: {<имя>: <адрес>}`) — требовали от платформы механизмов
над значениями внутри отображения (`unique`, `credentials`/`secret_in` по каждому адресу, `group_by` по адресам: P/02,
P/04, P/06 и три общих договора) и перегенерации этих уроков; переименование `cam` → `dev` — отклонено раньше.

## 2. `io` — своей подсистемой
Пока неканальных устройств мало (вход и реле камеры, отдельный модуль) — `kind: io` в `cam` остаётся. Когда их станет
много (СКУД, датчики, контроллеры дверей) — отдельная подсистема `io` со своими единицами и событиями; `cam` — только
видео.

## 3. Откуда потребитель берёт поток (владелец, 2026-10-26)
Владелец: «если мы настроили 3 разных потока для rec, live и det, то логично сразу их забирать напрямую каждому своё».
Сейчас (V/01, V/03 гл. 2, V/04 гл. 2) `live` и `det` берут поток только у держателя камеры; прямого RTSP к устройству нет.
- **(A) прямой забор** каждым потребителем: логика устройства и пароль — в трёх подсистемах, предел сессий никто не
  учитывает, толкающие камеры недостижимы — отклонить.
- **(Б) держатель потока рядом с потребителем** — склонность «Архитектора», с моделью п. 1 естественна: поток — своя
  единица `cam` с размещением `near` своего потребителя (`main` — у записи, поток сетки — у шлюза, поток детекции — на
  GPU-сервере); логика устройства и пароль — в `cam`, перехода нет. Цена — п. 1.7.

## 4. Камера w2c — кластер из одного, толкает потоки потребителям (владелец, 2026-10-26)
Сейчас (V/01.6) камера-кластер из одного толкает поток только в приёмник кластера записи. Подумать: камера сама —
держатель своих потоков, толкает каждый прямо потребителю (запись — в приёмник, сетка — в шлюз, детекция — в детектор);
приёмник — посредник там, где потребитель камере недоступен. Нужно: адрес и допуск потребителя для толкания (токен
`stream` домена — сейчас только для приёмника), желание потока от шлюза и детектора (подписка как желание — V/03 гл. 2),
учёт сессий и полосы на камере, отказ и возврат к приёмнику.
