# C2: долговечность повторного ключа после исхода правки

## Контекст
Форма Edit/Outcome и подпись согласованы. ADR требует 422 при повторном ключе
с другим методом, путём или телом. Если после Outcome удалять Edit, исход
не содержит исходного метода/пути/тела: после рестарта держателя проверка
невозможна. Нового имени на диске не нужно. Подключение подписанной консоли
и страницы продолжается независимо; слияние платформы ждёт чтения diff.

## Рекомендация
Сохранить исходную Edit в domain/pending/<член> после Outcome как свидетельство
использования ключа; в состоянии waiting показывать только Edit без Outcome.
Агент хранит исход и не применяет завершённую Edit повторно. Новый ключ — новая
операция. Так повтор переживает рестарт без дополнительного формата/памяти
процесса. Если продукт уже хранит отдельный журнал идемпотентности, прошу
указать закреплённую форму для зеркала, без чтения продуктового кода.
Уточнить оставшиеся типы существующих полей: рекомендую what = отсортированный
список имён полей, body = JSON-объект, status = целый HTTP-код. В ADR типы
what/body/status явно не зафиксированы; новых полей не предлагаю.

## Решение («Архитектор», 2026-10-13)
По факту продукта, закреплено поправкой к форме C2 в ADR-0074: `pending` держит только ожидающие правки, после исхода
правка снимается; 422 на тот же ключ с иным содержимым — пока правка в ожидании; повтор ключа после исхода домен не
отвергает — его гасит консоль члена своими ключами идемпотентности в хранилище кластера (`<sub>/idem/<ключ>`, срок
сутки), ответ как в первый раз. Хранить правку после исхода как свидетельство — отвергнуто (второе место). Типы:
`what` строка (имена полей через запятую, отсортированы), `body` JSON-объект, `status` целое (0 — консоль не
спрошена), `at` число секунд. Файл снимаете слиянием окна.
