# Запрос: форма ожидания «одно из» в словаре общего README приёмки

**Какая норма мешает.** P/06.4 Н3 «подать просьбу», шаг 5: если после записи строки держатель уже сообщил исход,
консоль отвечает `200 {answered: <метка>}`, иначе — `202 {queued: <rid>}`. Оба ответа верны, какой из них придёт,
решает гонка держателя и консоли. Словарь ожиданий общего README приёмки (`Platform/common/acceptance/README.md`,
таблица форм `expect`) знает точный код с телом-подмножеством и класс кода `2xx` без тела. Формы «один из двух ответов,
каждый со своим телом и своими связываниями» в нём нет.

**Место.** `VMS/01-cam/acceptance/4/scenarios.tsv`, `01-no-device` шаги 4–5: подача команды камере-файлу и чтение
метки `cam/commands/$rid`. Прежнее ожидание `202 {"queued": "$rid"}` отвергало верный `200 answered`.

**Контрпример.** Держатель запущен, его `running` подтверждён, отказ камере без устройства — немедленный. Консоль
записала строку, держатель увидел её и записал `refused`, консоль на шаге 5 перечитала метку и вернула `200 answered`.
Ожидание `202` даёт RED верной реализации. Ожидание `2xx` проходит, но связать `$rid` нельзя: `200 answered` rid не
несёт. Шаг чтения метки по rid после любого из двух исходов этим словарём не записать.

**Обход до ответа.** Сценарий подаёт просьбу до запуска держателя: метки писать некому, шаг 5 даёт `202 queued`
детерминированно, `$rid` связан; затем `@start worker`, держатель берёт камеру и исполняет просьбу — метка `refused` по
`$rid` и событие `command.failed`. Подачу при живом держателе (гонка 200/202) приёмка так не проверяет — это и даёт форма.
Класс кода `2xx` словаря не годится: rid не связать, а `check_spec` навыка для сценариев VMS класса кода не принимает
(ожидание — код `[1-5][0-9]{2}` и JSON) — это вторая часть запроса, к навыку: форма словаря должна проходить и `check_spec`.

**Рекомендация.** Форма в таблице `expect` общего словаря:

```
@oneof <код> <JSON> | <код> <JSON>
```

Шаг проходит, если ответ совпал с одной из ветвей по правилам своей формы (код точный, тело — подмножество,
`@any`/`@absent`/`~`). Связывания `$имя` фиксирует только совпавшая ветвь; имя, связанное лишь в другой ветви, в
следующих шагах не связано, и шаг, который его использует, проваливается как «не связано» (как сейчас у упавшего
связывателя). Ветви проверяются по порядку, первая совпавшая выигрывает. Для подачи просьбы:
`@oneof 202 {"queued": "$rid"} | 200 {"answered": {"outcome": "refused"}}`. Тогда чтение метки по `$rid` — отдельным
сценарием, где подача заведомо не может получить немедленный исход, или ASSERT-формой словаря, если она есть.
