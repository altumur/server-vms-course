# Отсечение запоздавшей записи вклада после смены владельца слота

Ответ Архитектора уже записан в дополнении 3 ADR-0074 (`9abd26c8`). Ниже исходная находка и проба;
повторное согласование не требуется.

## Контекст

После закрытия шага 5 ADR-0070 начал ядро слияния в ветке `codex/course-book-merge` от `e0c83de4`.
Дополнение 2 ADR-0074 рассчитывает на существующее отсечение слота для строки `<sub>/<семья>/<воркер>`.
Проба использует имя слота `w-1` как id строки. `Worker.renew_slot` обнаруживает смену владельца, но обычный `Variables.put`
не проверяет слот. Новый владелец уже записал вклад, а задержавшийся старый перезаписал его успешным CAS.
Пока не подключал запись вкладов к runtime, спеки подсистем не менял.

## Рекомендация

Перед подключением издателей утвердить условную запись Variables: сравнение версии строки слота и запись
вклада в одной операции хранилища. Рекомендую форму `put(path, items, cas=…, guard={key: <slot>, index: <index>})`;
`guard` здесь только предложение нового поля протокола, не реализованный ключ.

Общий метод Worker перед отправкой убеждается, что прочитанный слот принадлежит его экземпляру, и передаёт
его индекс в `guard`. Хранилище атомарно проверяет этот индекс вместе с CAS самой строки вклада. Изменился слот —
запись отказана, даже если запрос начат раньше. Повтор сначала проверяет владение заново; `unconfirmed_max`
не разрешает публиковать управляющее состояние при неподтверждённом владении. Все реализации Variables,
включая FileVariables и configstore, должны иметь одинаковую семантику, без неатомарного запасного пути.

Это общий механизм платформы, без знания имени книги или подсистемы и без callback в хранилище.
Права на целевую строку и чтение guard проверяются отдельно; guard не расширяет ACL. Цена — дополнительное
условие операции и возможный повтор при очередном обновлении слота, даже если владелец тот же.
Форму ошибки и перенос guard через дверь без голоса нужно согласовать вместе с операцией до кода.

Альтернатива — неизменяемые поколения вкладов и проверяемый указатель на поколение действующего владельца.
Не рекомендую её для первого шага: меняет уже согласованную семью строк и добавляет сборку мусора.
Если под id писателя имеется в виду уникальный `instance`, а не имя слота, нужно явно закрепить это
и проверку соответствия instance текущему слоту при чтении; одного разнесения путей для отсечения недостаточно.
Одно `renew_slot()` перед отдельным `put()` не закрывает промежуток между этими операциями.

## Воспроизведение

Из `Source/`, Python окружения курса. Используется настоящий Worker и FileVariables, без замены их методов:

```python
import json
from tests.conftest import Box, testsub
from tests.test_worker_life import _bare

box, spec = Box("book-fence-probe-"), testsub()
old = _bare(box, spec, "w-1")
assert old.renew_slot()
new = _bare(box, spec, "w-1")
path = "testsub/counts/w-1"
new.vars.put(path, {"i": json.dumps({"ref": "r", "to": "b", "n": 2})})
_, index = old.vars.get(path)
old.vars.put(path, {"i": json.dumps({"ref": "r", "to": "b", "n": 1})}, cas=index)
assert box.vars.get(spec.sub.slot_key("w-1"))[0]["holder"] == new.instance
assert json.loads(box.vars.get(path)[0]["i"])["n"] == 1
assert old.renew_slot() is False
```

Проба выполнена на `e0c83de4` с рабочими изменениями только загрузчика и чистого сборщика книг;
Worker и хранилище не менялись. Это воспроизведение недостатка, а не зелёный тест требуемой защиты.
Места: `Source/w2cplatform/worker.py:536` (`renew_slot`), `variables.py:459` (`put`),
`configstorevars.py:257` (тело `put` содержит только op/key/items/cas, без условия слота).

## Приёмка

Задержать публикацию старого владельца после проверки слота; передать слот новому, записать его вклад;
разрешить старый запрос. Хранилище должно отказать старому, строка нового не меняется. Проверить это на
FileVariables, raft/configstore и через дверь без голоса, включая потерю ответа, повтор и отказ кворума.
Сборщик не должен выдавать старый вклад за свежий только потому, что агент продолжает присылать отчёты.
