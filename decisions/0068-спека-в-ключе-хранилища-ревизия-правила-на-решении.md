# Спека подсистемы лежит в ключе хранилища кластера, решение размещения помнит ревизию правила; etcd не берётся

## Context and Problem Statement
Класс системы: платформенная система.

Правила размещения уже данные: спека `<sub>.subsystem.yaml` (ADR-0001, ADR-0012). Но каждый процесс читает свою копию из
`SPEC_DIR` при старте, а контроллеров в кластере из N серверов N на спеку (ADR-0030: один шаблон, экземпляр на спеку,
на каждом сервере, лидера нет, сходятся CAS-ом). Пока новая спека раздаётся по серверам, контроллер со старой считает
размещение по новой нарушением и переставляет единицу обратно; CAS на строке размещения этого не ловит — он
сравнивает ревизию строки, а не правила. Между двумя версиями спеки единицы дёргаются, а переезд рвёт запись
(ADR-0027, ADR-0044). Это «гонка правил» из внешнего разбора; остальные его посылки к нам не относятся: правила не
часть артефакта, ёмкость — слово воркера в биении (ADR-0030 п. 6), неподвижность камеры после создания — замысел.

Разбор предлагает etcd как хранилище с транзакциями и снимками. У нас своё хранилище на raft с ролевыми сокетами и
правами из спеки (ADR-0014, ADR-0021), на нём построен М11 курса.

## Decision Drivers
* в одном кластере в каждый момент одно правило; раскатка правила по частям внутри кластера невозможна по построению
* решение, принятое по новому правилу, не отменяется процессом со старым
* платформа знает только спеку (ADR-0001); источник спеки один на кластер
* права хранилища по-прежнему из спеки (ADR-0014), без курицы и яйца при установке
* одна форма у курса и продукта (ADR-0019)
* своё хранилище и курс М11 остаются (ADR-0021)

## Considered Options
* Спека в ключе `platform/spec/<sub>` с ревизией; строка размещения несёт `spec_rev`; контроллер со спекой старше не трогает её; etcd не берётся.
* Перейти на etcd: транзакция «сравнить ревизию спеки и записать размещение», чтение состояния на одной ревизии, watch.
* Оставить файлы в `SPEC_DIR` и дисциплину «везде или нигде» при раздаче.

## Decision Outcome
Выбран первый вариант.

1. Спека каждой подсистемы кластера лежит в ключе хранилища `platform/spec/<sub>` (байты YAML как есть, ревизия —
   ревизия ключа). Кладёт её `w2cctl spec put <файл>` при установке и при каждой правке; файл в `SPEC_DIR` остаётся
   источником для установщика и для генерации прав (`w2cctl rights`, ADR-0030 доп.), иначе права на чтение ключа
   нечем вывести. Загрузчик платформы читает спеку из ключа; процесс без ключа не стартует (строгий загрузчик,
   ADR-0012). Консоль отдаёт `/spec` из того же ключа.
2. Контроллер берёт снимок спеки в начале каждого прохода. Строка размещения, которую он пишет, несёт `spec_rev` —
   ревизию ключа спеки, под которой принято решение. Контроллер, чья спека старше `spec_rev` строки, не трогает её
   (ни переезда, ни снятия) и пишет это в биение одной строкой; после перезапуска он читает новую спеку и догоняет.
   Так старое правило уступает новому монотонно, и внутри кластера в каждый момент действует одно правило.
3. Смена спеки это смена ключа: процессы, прочитавшие другую ревизию, завершаются и перезапускаются systemd/launchd
   (ADR-0046); живой перечитки спеки нет — какие ключи безопасно менять на ходу, система не знает, и не притворяется.
4. Разные правила на разных площадках — разные кластеры со своими хранилищами, как сейчас; постепенная раскатка одного
   правила внутри кластера не нужна и невозможна.
5. etcd не берётся: транзакция по двум ключам закрывается п. 2 без транзакции; ролевые сокеты, права из спеки, объекты
   файлами и курс М11 стоят своего хранилища. Если понадобится сравнение двух ключей в одном `put`, оно добавляется в
   configstore — это дешевле смены хранилища. Пересмотр — когда кластер выйдет за десятки серверов.

### Consequences
* Good, because гонка правил закрыта по построению; одна спека на кластер; откат правила — возврат ревизии ключа.
* Good, because своё хранилище и курс остаются; изменение в загрузчике, контроллере и `w2cctl`, не в архитектуре.
* Bad, because смена спеки перезапускает процессы кластера; это и сегодня так, но теперь явно.
* Bad, because файл и ключ существуют оба (файл для установки и прав, ключ для процессов); расхождение ловит тест
  `w2cctl spec status` и ночной прогон.

### Confirmation
* Продукт: тест контроллера — два контроллера одной спеки с разными ревизиями; размещение под новой ревизией старый не
  трогает и говорит об этом в биении; после перезапуска догоняет. Тест загрузчика: процесс без ключа спеки не стартует.
* Стенд: `w2cctl spec put` новой спеки, перезапуск, строки размещения несут новую `spec_rev`, дёрганья нет.
* Курс: та же форма в `w2cplatform` (`spec_rev`, ключ `platform/spec/<sub>`), `spec_parity_debt.txt` без строк.

## Pros and Cons of the Options

### Спека в ключе, `spec_rev` на решении
* Good, because одно правило на кластер и монотонная уступка без транзакций.
* Bad, because два носителя спеки (файл и ключ) и перезапуск при смене.

### etcd
* Good, because транзакции, MVCC-снимки, watch, аренды из коробки.
* Bad, because чужой демон на каждом сервере, права из спеки пришлось бы отображать на RBAC, объекты в лог или рядом,
  переписывание М11 и всех процессов; цена несоразмерна одной гонке.

### Файлы и дисциплина раздачи
* Bad, because на десятках серверов «везде или нигде» это проект, а не операция; гонка остаётся.
