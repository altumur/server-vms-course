# Кластер без оркестратора: ключи в `configstore` на raft, объекты файлами, процессы под systemd

## Context and Problem Statement
Класс системы: платформенная система — консоль и контроллер распоряжаются воркерами для подсистем.

М11 строил кластер на Nomad: raft Nomad'а держал Variables, планировщик раскладывал процессы, ACL-токены разграничивали пишущих, объекты лежали в Variables под `objects/` с потолком 64 КиБ. Владельца беспокоили два следствия. Переход коробки в кластер требовал переноса ключей в чужую систему со своими ACL и супервизором. И камере без серверов Nomad не по карману, а одна схема для камеры, офиса и серверной ценнее двух.

От Nomad платформе на деле нужно хранилище с CAS, а не планировщик: камеры по воркерам раскладывает свой контроллер, слоты воркеры берут сами по CAS, консоль и ресурс стоят по одному на сервер.

## Decision Drivers
* слоты, эпохи и размещение требуют линеаризуемой записи с CAS, переживающей смерть одного сервера из трёх;
* аренды воркеров продлеваются постоянно, поэтому хранилище с одним держателем — единая точка отказа записи всех камер;
* камере и одиночной коробке не нужен ни оркестратор, ни кворум;
* хранилище называется по тому, что хранит: это компонент платформы, а не VMS.

## Considered Options
* Nomad Variables под Nomad, файлы на коробке, утилита слияния при переходе;
* своё хранилище с держателем, как у домена (один сборщик);
* своё реплицируемое хранилище на встроенном raft (`hashicorp/raft`), процессы под systemd, объекты — файлами на своих серверах.

## Decision Outcome
Выбран третий вариант. Ключи держит `configstore` — демон на каждом сервере на `hashicorp/raft` с семантикой `FileVariables` (версия ключа — индекс raft, `put` с `cas`), процессы ходят к нему через сокет своей роли. Объекты (heartbeat'ы, отчёт прохода, срезы снапшота) — файлы на сервере своего писателя, чужие читаются через ресурс; blob'ы копируются соседям с проверкой хеша. Процессы — фиксированный набор юнитов systemd (launchd на macOS) на каждом сервере; запасные поднимает скрипт по таймеру по числу из консоли. Вывод сервера — `platform/drain`, раскатка — пакет по серверам. Nomad и Kubernetes остаются только формой поставки: у заказчика уже есть оркестратор, узлы появляются сами, десятки разнородных узлов, жёсткая изоляция. Хранилище называется `configstore` — компонент платформы.

### Consequences
* Good, because коробка, камера и кластер живут без оркестратора, а `vms/` не замечает смены хранилища (шов `OpenVars`).
* Good, because потолка 64 КиБ у объектов нет, и снапшот не надо резать ради него.
* Bad, because эксплуатация консенсуса — наша: снапшоты, усечение журнала, резервная копия, восстановление при потере большинства, смена состава группы.
* Bad, because аутентификация между процессами по сети (mTLS) становится условием мультисерверного хранилища, а не задачей на потом.
* Bad, because два сервера по-прежнему не решаются: raft из двух голосов хуже одного сервера, офис из двух серверов остаётся двумя кластерами из одного.

### Confirmation
Замер продукта (ветка `r20-store`): один узел → три под нагрузкой продлений → убить лидера; худшая пауза записи 2,8 с по умолчанию и 1,5 с с настройками для локальной сети при запасе аренды 16,7 с, ни одной потерянной аренды и подтверждённой записи. Общий набор тестов контракта `Variables` проходит на одном и трёх узлах. В курсе — стенд М11 из трёх серверов на `configstore` (`М11_ClusterVMS/clustervms/tests/stand.py`, трассы `М11_ClusterVMS/traces/`).

## Pros and Cons of the Options

### Nomad Variables под Nomad
* Good, because кворум, ACL и workload identity уже есть.
* Bad, because переход коробки в кластер — перенос ключей в чужую систему; камере Nomad не по карману; объекты упираются в 64 КиБ.

### Держатель хранилища, как у домена
* Good, because просто и тот же код, что у домена.
* Bad, because смерть держателя останавливает продление аренд, и запись камер встаёт на всех серверах ровно в момент отказа; автоматическая смена держателя без раскола требует голосования большинства.

### `configstore` на raft
* Good, because одна схема от камеры до серверной, хранилище не зависит от оркестратора.
* Bad, because консенсус и его эксплуатация — наша работа.
