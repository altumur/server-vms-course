# Контроллер заказывает воркеры по серверам, скрипт сервера исполняет заказ; запасных воркеров нет

## Context and Problem Statement
Класс системы: платформенная система — контроллер кластера размещает единицы подсистем по воркерам, а процессы
поднимает systemd на каждом сервере.

Когда единицам не хватает места, нужен ещё один процесс роли. Сейчас (ADR-0021, ADR-0046; М10/3, 4, 5, 11) контроллер
пишет предложения — пустые строки слота `w-<N>` с `offer=<набор меток>`, — а скрипт `w2c-spares.sh` на каждом сервере
раз в минуту читает «нужен воркер где-то» и поднимает безымянного запасного. Запасной берёт предложение по CAS.

Записка «Запасные воркеры: как было и как предлагается» (2026-10-19) показала цену. Где появится ёмкость, решает
случай: чей таймер раньше, чей CAS первый. Правила размещения контроллера на это не влияют. Проигравший запасной висит
без имени, выигравший остаётся и после нужды. Особый процесс тянет особую инфраструктуру: поля `offer`, `offered_at`,
`taken_at`, исключение в захвате слота, `OFFER_GRACE`, отдельный шаблон юнита и тест сверки с юнитом роли,
`SPARE_FOR` и файл `/run/w2c-spares/<юнит>.env`, отдельные отказы старта. В нормах М10 слова «запасн», `spare`, `offer`
встречаются 92 раза.

## Decision Drivers
* **требование владельца:** все единицы роли на сервере в одном процессе не держим;
* **требование владельца:** число процессов роли на сервере заранее не задаём — оно растёт по нужде;
* размещение решает одно место — контроллер (М10/4), с причиной в отчёте прохода;
* у контроллера нет права запускать процессы (ADR-0021): запуск остаётся у сервера;
* лишние процессы не остаются навсегда;
* у дополнительного процесса те же учётные данные, что у роли (цель ADR-0046), без второго описания роли.

## Considered Options
* запасные как есть (предложения, безымянный процесс, скрипт решает сам);
* контроллер заказывает число воркеров роли на конкретном сервере, скрипт сервера приводит к нему число процессов;
* один воркер на роль на сервере с ёмкостью по серверу;
* фиксированное число воркеров роли на сервере;
* воркер сам запускает дочерние процессы;
* оркестратор (Kubernetes, Nomad).

## Decision Outcome
Выбран вариант «контроллер заказывает воркеры по серверам», потому что он возвращает контроллеру единственное решение
размещения, которое от него ушло, и убирает всё, что было нужно только ради соревнования серверов.

1. **Заказ.** Контроллер считает нехватку, как сейчас, выбирает сервер по правилам размещения (метки, не дренируется
   и не выведен, ресурс отвечает, `servers: distinct`, есть место по `room`, менее загружен) и пишет строку
   `<sub>/want/<сервер>` — число воркеров роли на этом сервере — под `placement_turn`, в intent прохода (смена
   контроллера не даёт второго заказа). Причина выбора — в отчёте прохода. Не больше одного заказа на кусок нехватки
   за проход.
2. **Место.** Ресурс сервера пишет в строке двери `platform/doors/<сервер>` поле `room: {<роль>: <сколько ещё
   процессов>}` = `floor(HOST_MEMORY_MB / WORKER_MEMORY_MB)` − работающие процессы роли; работающие считает по замкам
   присутствия (`<events>/.workers/<sub>/*.lock`, М10/8 Н1.4). Скрипт перед запуском перепроверяет память сам.
3. **Исполнение.** Скрипт сервера раз в минуту читает свой ряд `<sub>_workers_wanted{server}` из `/metrics` консоли
   и приводит число процессов к нему: запускает или останавливает `<dep>-<sub>worker@<prefix>-<сервер>-<n>`, n от 2. Ряды
   других серверов не читает. polkit: `start` и `stop` юнита своей роли с именем своего сервера и номером 2–99.
4. **Дополнительный воркер — обычный воркер** из того же юнита, что `<prefix>-<сервер>-1`, со своим именем; захват слота
   обычный.
5. **Сервер не поднял заказ** за срок (прежний `OFFER_GRACE`, 90 с): контроллер снимает заказ, на время помечает
   сервер «не поднял», заказывает на следующем подходящем; отказ — в отчёте и тревоге.
6. **Сокращение** — новое основание переноса. Нехватки нет дольше выдержки и остальным хватает места: контроллер
   выводит воркер с наибольшим номером из пула, переносит его единицы не быстрее бюджета за проход (как `HOME_BUDGET`),
   и только при пустом назначении уменьшает `want`. `want` не опускается ниже 1.
7. **Страховка остановки.** Воркер, получивший SIGTERM при непустом назначении, отдаёт слот штатно (М10/5
   «остановка»): рассинхрон скрипта и контроллера стоит переезда, а не потери единиц.
8. **Запасных нет.** Уходят: поля `offer`, `offered_at`, `taken_at`; исключение захвата и фильтр набора; режим
   запасного у воркера; `SPARE_FOR`, `W2C_SPARE_FILE`, `/run/w2c-spares`; шаблон `<dep>-<sub>worker-spare@` и тест
   сверки; ряд `<sub>_spare_offers`.

### Consequences
* Good, because ёмкость появляется там, где решил контроллер по правилам размещения, а причина видна в отчёте.
* Good, because на одну нехватку поднимается один процесс; лишние снимаются сокращением, память возвращается.
* Good, because один вид воркера и один юнит: расхождение с юнитом роли невозможно по устройству, тест сверки не нужен,
  новая роль растёт без своего шаблона.
* Good, because меньше поверхность атаки: нет файла, задающего окружение процессу с ключами кластера; скрипт ничего
  не решает.
* Bad, because новая строка `<sub>/want/<сервер>`, новое поле `room` и новая работа ресурса (считать процессы ролей).
* Bad, because новый шаг прохода контроллера (выбор сервера, снятие заказа по сроку) и новое основание переноса
  «сокращение» с выдержкой и бюджетом.
* Bad, because у скрипта появляется `stop` — право шире прежнего, хоть и ограничено своей ролью, своим сервером и
  номером от 2.
* Bad, because скорость не растёт: таймер раз в минуту, и скрипт по-прежнему зависит от консоли.
* Bad, because правка широкая: М10/3, 4, 5, 6, 8, 9, 11, спеки (`offers`), приёмка 03, 04, 09, обе реализации и продукт.

### Confirmation
* Нормы: в М10 нет `offer`, `offered_at`, `taken_at`, `SPARE_FOR`, шаблона запасного (`check_spec` и поиск по словам);
  у каждой новой строки и поля — строка каталога данных (`<sub>/want/<сервер>`, `room`).
* Приёмка: директива «Стенда», которая исполняет ряд `workers_wanted` вместо скрипта; шаги — заказ одному серверу при
  нехватке, сервер не поднял — заказ на другом, сокращение после выдержки, SIGTERM при непустом назначении — переезд.
* Quint: модель слота М10 (пилот) дополняется заказом, сокращением и сменой контроллера; инварианты — не больше
  одного заказа на кусок нехватки, не остановлен воркер с единицами, нет бесконечной раскачки.
* Обе реализации зелёные на новой приёмке; сверка затронутых уроков.
* Продукт (проверено «Архитектором» 2026-10-19 по `vmssubsystem` `ea1be7d0`): имён `SpareWorkers` и `ScaleHint` там
  больше нет; `vmsworker/vms/volumefront.go` только показывает странице `rec_workers_needed` — при переходе показывать
  `<sub>_workers_wanted{server}`. Запасные в продукте — `vmsworker/w2cplatform/spares.go` и его тесты. Работа над
  продуктом на паузе (решение владельца), правка — когда «Сборка» вернётся к продукту.

## Pros and Cons of the Options

### запасные как есть
* Good, because уже нормировано и исполнено обеими реализациями.
* Bad, because где появится ёмкость, решает случай; висящие и вечные процессы; особая инфраструктура (раздел Context).

### контроллер заказывает воркеры по серверам
* Good, because см. Consequences.
* Bad, because см. Consequences.

### один воркер на роль на сервере
* Bad, because все единицы роли на сервере в одном процессе — против требования владельца.

### фиксированное число воркеров роли на сервере
* Bad, because число процессов задаётся заранее — против требования владельца.

### воркер сам запускает дочерние процессы
* Bad, because у одного имени несколько процессов, платформа их не видит; меняет модель воркера.

### оркестратор
* Bad, because отвергнут ADR-0021.

* строка заказа у установленной роли есть всегда, `want` 1…99, сокращение пишет `want = 1`; нет ряда — скрипт ничего
  не делает (Р1, Р9);
* `want` — абсолютная цель; заказанные и ещё не поднявшиеся процессы — ёмкость в пути: нехватка их вычитает, `room`
  их резервирует; восстановление доводит цель, а не прибавляет; обещание — «один действующий логический заказ на кусок
  нехватки», поздний старт снимается сокращением (Р2);
* сокращаемый воркер записан в строке заказа (`retiring`), исключён из пула, сокращение — отдельный шаг с бюджетом,
  первая неделимая группа может его превысить, гистерезис по запасу ёмкости; жертва — по числовому номеру (Р3, Р4);
* сроки — по ADR-0049: местные монотонные часы от первого наблюдения версии заказа (Р5); «не поднял» не считает
  базовый процесс (Р6); дренаж и вывод снимают заказы (Р7); `distinct` — по месту `place_by` (Р8);
* Confirmation: плановая остановка против внешнего SIGTERM, сходимость — временное свойство при названных
  предпосылках (Р10); polkit — полные имена `<dep>-<sub>worker@<prefix>-<SERVER_NAME>-<n>`, `n` 2–99 (Р11).

**Дополнение (2), 2026-10-19 — по сверке Python и Go М10/3–5** (разбор `inbox/2026-10-19-сверка-м10-3-5-adr84-разбор.md`,
решения Р13–Р24; решение «Архитектора», класс структурных вопросов ADR-0081 п. 3). Уточняют п. 1, 2, 6 и доп. (1):
* в пути не включает базовый: `max(0, (want − 1) − живые заказанные n ≥ 2)` — одно определение для нехватки, кандидата и
  сокращения; мёртвый базовый — `no_base`, сокращение роли на других серверах не держит (Р13);
* дверь несёт рядом с `room.<sub>` число замков `live.<sub>`, по которому он посчитан; кандидат — `room − max(0, want −
  live_door) > 0`, обе части на один момент; `@grow` стенда — с потолком памяти (Р14);
* пустое место `""` — места нет; общего места не бывает; при `distinct` живые без места — свободная ёмкость, нехватка мест
  — причина в `/unplaceable`, не повод заказывать (Р15, Р16);
* объекты кластера — через ресурс своего сервера (Р17);
* векторы: `in_flight` — взятое набором, ёмкость без названной — `default`, форма набора без `per`, набор меток —
  множество, перечень «не по форме» в README пакета, формы `short`, ряда withheld и `why` (Р18–Р24).
