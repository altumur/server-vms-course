# Исключения прав: ранг `none`, внутри роли решает самая точная область, между ролями — наибольшее

Заменяет ADR-0098 п. 3 («понижения — `NOT_SUPPORTED`»), ADR-0097 §7 «Понижение не переводится», ADR-0097 §8.4
(«запреты строкой») и ADR-0097 §6 «Снять `U` из `G` — … без права на `U`: снятие только сужает права» (§4 здесь).
Уточняет ADR-0098 §5 (кто считается `unr`, §7 здесь).

## Context and Problem Statement
Класс системы: платформенная система (`may`, гранты домена). Первый потребитель — `backend` (права consolem).

**Как сейчас.** Строки грантов только складываются: шаг 7 `may` — «хоть одна строка с рангом не ниже и покрывающей
областью». Поэтому не переводится роль consolem, которая даёт папке больше, чем камере в ней (`folderAccess` `FULL`,
`objectAccess` камеры 7 `FORBID` или `ONLY_ARCHIVE`), или подпапке меньше, чем родителю. Буквальный перевод молча дал бы
камере права папки. ADR-0097 §7 и ADR-0098 п. 3 отвечают такой роли `NOT_SUPPORTED`.

**Что решил владелец.** Исключения делать (2026-10-30). Смысл — «внутри своей роли» (2026-10-30, после разбора), как в
consolem `index.html` `9849d28` (`accRoleLevel`, `accEffIn`, «Итоговый доступ»):
- внутри роли действует исключение объекта. Если его нет — значение ближайшей папки объекта, где оно задано (сама папка,
  иначе выше, вплоть до корня домена). Объект в нескольких папках получает наибольшее из них. Нет и папок — умолчание
  роли. «Неограниченный доступ» обходит всё;
- между ролями — наибольшее. Запрет в одной роли не отнимает того, что дала другая.

Прототип 11 consolem (`6bffe89`, `index_11_isklyuchenie-vazhnee.html`) считает иначе: исключение объекта из любой роли
сильнее папок и умолчаний всех ролей. Владелец выбрал «внутри своей роли». Расхождение — в Consequences и «Запрос
продукту» п. 4.

## Decision Drivers
* Смысл совпадает с consolem `9849d28`: роль переводится в строки без потерь и без расширения.
* Старые строки и их смысл не меняются (ADR-0003): прямые строки человека складываются, как сегодня.
* Ни один читатель не читает строки шире, чем записано: кто не знает исключений, не исполняет и строк ролей.
* Нечитаемое не расширяет (безопасные умолчания ADR-0012). Пропуск строки или неизвестный вход не открывают более общую
  область той же роли.
* Одна строка гранта — одна проверка. Раскладки прав в строки на каждую единицу нет.
* Право на запись, принятое по составу папок, не расходится с составом (стражи членства, ADR-0097 §5).
  Запись состава не поднимает права без права на единицу.

## Considered Options
* **(а) Внутри роли решает самая точная область; между ролями — наибольшее** (consolem `9849d28`).
* (а') Исключение объекта из любой роли сильнее папок и умолчаний всех ролей; между ролями — наибольшее (прототип 11).
* (б) Запрещающая строка перекрывает всё: любая строка «нельзя» у человека или его роли — отказ.
* (в) Исключений нет, понижения — `NOT_SUPPORTED` (ADR-0097 §7, ADR-0098 п. 3).

## Decision Outcome
Выбран «(а)» (владелец, 2026-10-30): исключение остаётся в своей роли, поэтому добавить роль никогда не сужает права.

### 1. Ранг `none` и формы строк ролей
```yaml
cap:   none | view | edit | admin       # none < view < edit < admin
none:  «в этой подсистеме и в этой области — ничего»; разрешения не даёт никогда; действует, когда его ярус —
       первый непустой ярус своей группы (§2)
```
- `none` бывает только в строках ролей (`subject: role:<имя>`, ADR-0098 §2). Строка человека или ключа индекса с `none` —
  400 bad line. Причина: прямые строки складываются, как сегодня, и понижать в них нечего.
- Строка роли с областью `labels:` — 400 bad line (решение «Архитектора» А2). Перевод consolem меток не пишет, а ярус
  меток дал бы два пути к расширению: нечитаемые метки и снятие метки с about-единицы. Запрет снимается новым ADR, когда
  появится потребитель.
- В `domain/grants/domain` ролей нет (ADR-0098 §2), поэтому нет и `none`.
- Старый читатель сочтёт `none` не по форме и пропустит строку. Поэтому §8: исключения и роли вводятся одним приращением.

### 2. `may`: группы строк и ярусы области
Шаг 5 (ADR-0097 §2, ADR-0098 §4) отбирает действующие строки по субъекту, сроку и `sub`. Дальше:

- **Группы.** Прямые строки человека (и ключа индекса) — одна группа. Строки каждой действующей роли человека — своя
  группа на роль.
- **Прямая группа** — как сегодня: шаги 6–7 над её строками, строки только складываются.
- **Группа роли.** По каждой проверке `(cap, unit, sub)` она берёт **первый ярус**, где у неё есть строка, покрывающая
  единицу. Уровень группы — наибольший `cap` строк этого яруса. `none` и положительная строка одного яруса, в том числе
  одной области, дают положительную: у consolem в одной точке одно значение, а между папками одного яруса он сам берёт
  наибольшее. Ярусы, от точного к общему:

| ярус | строки |
|---|---|
| 1 | `unit:` — сама единица |
| 2 | `unit:` — её about-единица |
| 3 | `folder:` — ближайшие папки (ниже) |
| 4 | `*` |

- **Ближайшая папка.** Вход `may` у `unit` и `about` получает цепочки вместо набора `folders` (ADR-0097 §5):
  `chains: [[F, родитель F, …]…]`, по одной на каждое членство единицы и её about-единицы, только живые (правило «только
  живая цепочка» ADR-0097 §5 без изменения). В каждой цепочке берётся первая папка, на которую у группы есть строка
  `folder:` из отбора шага 5; ранг при выборе не смотрится, папка только с истёкшими строками пропускается. Ярус 3 —
  строки этих папок по всем цепочкам, уровень — наибольший (consolem: «из нескольких папок — наибольшее»). Цепочка без
  такой папки в ярус 3 ничего не даёт.
- **Нечитаемое не расширяет** (решение «Архитектора» 2). Группа роли не опускается к менее точному ярусу, если более
  точный нельзя вычислить. Тогда группа даёт **«нечитаемо»**, а не уровень общего яруса. Входы, которые могут быть
  неизвестны:
  - строка этой роли не по форме. Разбор в две ступени: субъект прочёлся как `role:R` — «нечитаема» группа `R` (если
    прочёлся и `sub` — только в этой `sub`); субъект не прочёлся — «нечитаемы» все группы ролей документа. Прямая
    группа по-прежнему пропускает такую строку (P/08.4 Н1.3): пропуск в ней только сужает. Признак неполноты доходит до
    `may`, вызывающий не теряет его при фильтрации;
  - `about` единицы (ярус 2), если его нужно читать из строки единицы;
  - членство, звено цепочки и его живость (ярус 3).

  Вход `may` различает «нет» и «неизвестно»: `about` нет или неизвестен, `chains: []` или неизвестны.
- **Итог.** Разрешено, если прямая группа разрешает или хоть одна группа роли даёт уровень не ниже `cap`. Иначе 503
  `unavailable`, если есть «нечитаемая» группа, которая могла бы разрешить: в ярусах, которые она смотрела бы, есть её
  строка с рангом не ниже `cap`. Иначе 403. В списках — `withheld`, как метки в P/06.4. Это правило «Нечитаемая строка»
  договора сторожевой и ADR-0098 §4 (нечитаемая таблица ролей): 403 только когда проверено, что нельзя.
- **Отсечка.** Членство не читается, если результат от него не зависит. Все строки `folder:` группы в этой `sub` с рангом
  не ниже `cap`, и ярус 4 разрешает — разрешено без чтения. Все ниже `cap`, и ярус 4 не разрешает — отказ без чтения.
- Шаг 6 («`unit = null`, `cap = view`: хоть одна строка») — хоть одна строка с `cap ≠ none`.
- `unit = "*"` (создание — `admin` на `*`) и `unit = null` покрывает только ярус 4. Папка как объект записи (ADR-0097 §5)
  — ярусы 3 и 4 по её цепочке `[F, предки F]`.
- Срок строки: истёкшая строка в ярусе не участвует. Истёк `none` на камеру — действует ярус папки.

Пример: роль «Оператор» — `view sub: live folder:Склад`, `none sub: live unit:cam/7`; роль «Охрана» — `view sub: live
unit:cam/7`. Проверка — `unit = {sub: cam, id: 7}`, `sub: live`. Человек с одной ролью «Оператор» живого видео камеры 7
не видит (ярус 1 — `none`), остальные камеры склада видит. С обеими ролями — видит камеру 7 (`view` «Охраны»).

### 3. Цена и стражи
- Ярус 1 — без чтений. Ярусу 2 нужна строка единицы, если `about` не пришёл в запросе (как ADR-0097 §5). Ярус 3
  читается, только если у группы есть строка `folder:` в этой `sub`, ярусы 1–2 пусты и отсечка (§2) не решила. Порядок
  чтений на запрос — как ADR-0097 §5.
- Быстрый путь P/06.4 («`view *` без `sub` — видит всё») — у прямой группы как сегодня. У группы роли — только если у
  неё нет строк точнее `*` ни в одной подсистеме и нет строк `none`: запрос событий охватывает все подсистемы сразу.
- **Стражи членства** (ADR-0097 §5). Решение о записи зависело от членства, если разрешил ярус 3 или разрешил ярус 4 при
  прочитанном членстве. Тогда консоль кладёт стражей строк членства единицы и её about, в том числе стража отсутствующей
  строки при подтверждённом отсутствии. Иначе одновременное добавление в папку с `none` и запись по праву `*` разошлись
  бы.
- Лента `/changes` (ADR-0097 §3): `reset` при смене членства — подписчикам со строками `folder:` в прямых строках
  **или** в ролях. Смена таблицы ролей (ADR-0098 §4) — как смена грантов.

### 4. Запись состава папок (заменяет ADR-0097 §6 «снятие только сужает»)
С `none` в ролях снятие единицы из папки может поднять права: ярус 3 пустеет, и действует `*` той же роли. Поэтому
(решение «Архитектора» А1):
- снять `U` из `G` и перенести `U` из `G` — ещё `admin` на `U` в её подсистеме, по составу **до** записи, как при
  добавлении (ADR-0097 §6);
- удалить папку `G`, на которую или на потомка которой в копии грантов есть строка роли `folder:`, — ещё `admin` на `*`
  в каждой `sub` таких строк. Удаление поддерева атомарно (ADR-0096 §3), а обход его членов дорог; `admin` на `*` в
  `sub` покрывает любого члена. Без строк ролей на поддереве — как сегодня.

Иначе администратор папки (`admin sub: platform folder:G`) снимал бы запреты ролей на её членов в других подсистемах —
то самое «право в одной подсистеме → `admin` во всех», от которого ADR-0097 §6 закрыл добавление. В переводе consolem
ведение папок до ответа продукта есть только у `unr` (ADR-0097 §7), поэтому на пути `backend` правило ничего не стоит.

### 5. События с `of` (решение «Архитектора» А3)
P/06.4: строка события — единицы её `unit` и единицы `of`. Прямая группа — как сегодня: строку показывает грант `view` на
любую из двух. У группы роли решает `of`, если он есть, как P/06.4 уже делает для меток. Пример: роль `view sub: auto *`
+ `none sub: auto unit:cam/7` событие сценария `auto/s1` с `of cam/7` не показывает. Причина: исключение объекта у
consolem прячет объект целиком, с его событиями. Между группами — по-прежнему «или», поэтому монотонность сохраняется.

### 6. Выдача
- `GET /session`: `grants: [{cap, sub?, scope, role?}]` — с `none`. Подсказка модуля консоли (P/07) считает по тем же
  группам и ярусам. Ей нужны цепочки, а не набор `folders`, и та же неизвестность входов, а не пустые массивы. Сервер
  проверяет всегда.
- Доставка ключей книги и индекс имён (P/08.5 Н1.3, Н1.7) не меняются: строк ролей, а значит и `none`, они не читают
  (ADR-0098 §4).
- `grant too wide` — по рангу, `none` ниже всех.

### 7. Перевод consolem (информативно; норма — V/11; заменяет ADR-0097 §7 «Понижение не переводится»)
- Роль → группа строк `role:<id>` (ADR-0098). **Неограниченная роль** (`unr`) → только `admin *` без `sub`. Роль
  считается неограниченной, только если это её единственная действующая строка. Роль, где рядом с `admin *` написаны
  руками и другие строки, — не `unr`. Это уточняет инвариант `unr` у `backend` (ADR-0098 §5). *Заменено ADR-0100 §4:
  `unr` — назначения встроенной роли `admin`, строк у неё нет.*
- **Точки роли.** Каждая точка — одно место consolem с одним значением поля:
  - **`*`** — одна точка. По каждому полю вида её значение — значение корня домена (`folderAccess[<id домена>]`), если
    оно задано, иначе умолчание роли (`dCam`, …). Две строки одного яруса от корня и от умолчания не пишутся: ярус 4
    взял бы из них наибольшее, и понижение корнем пропало бы;
  - **`folder:F`** — каждая папка с заданным значением;
  - **корень в цепочках.** У consolem корень — звено каждой цепочки (`accGroups`, `accChain`), его значение участвует в
    «наибольшем из папок». У платформы корня-папки нет (ADR-0096). Поэтому, если у корня задано значение поля, каждая
    папка первого уровня без своего значения получает строки корня. Иначе камера в папках `F` (без значения) и `G`
    (`FORBID`) при корне `ARCHIVE` получила бы отказ вместо `ARCHIVE`. Папку первого уровня, созданную потом не через
    `backend`, перевод не знает: её единицы до следующего перевода сужаются, но не расширяются;
  - **`unit:`** — каждый объект с исключением.
- В каждой точке `backend` считает уровень consolem по каждому полю вида и пишет **строку на каждую подсистему вида**:
  ранг, что уровень и функции дают этой подсистеме, или `none`. Подсистемы, которых уровень не даёт, получают `none`
  явно: иначе ярус оказался бы пустым и сработал бы более общий. Пример: `folderAccess` «Склад» `cam: FULL`,
  `objectAccess` камеры 7 `cam: ONLY_ARCHIVE` → `folder:Склад`: `edit cam`, `view live`, `edit rec`; `unit:cam/7`:
  `view cam`, `none live`, `view rec`.
- **Экономия строк.** Строка точки `F` для `sub` не пишется, если она равна строке ближайшей папки-предка с заданным
  значением. Относительно `*` строка не опускается: цепочка без строки `folder:` в ярус 3 ничего не даёт, и наибольшее по
  цепочкам изменилось бы.
- **Уровни камеры и максимум** (решение «Архитектора» 3). Перевод ADR-0097 §7 по `(cam, live, rec)`: `FORBID` (0,0,0),
  `ONLY_ARCHIVE` (1,0,1), `MON` (1,1,0), `ARCHIVE` (1,1,1), `ARCH_MANAGE` (1,1,2), `FULL` (2,1,2). Для всех пар, кроме
  {`MON`, `ONLY_ARCHIVE`}, наибольшее по подсистемам равно переводу наибольшего уровня (модель Codex, 36 пар). Для этой
  пары consolem даёт `MON` (без архива), а платформа — архив тоже. Поэтому `backend` проверяет итоговое состояние пакета
  `/access/apply` (роли, назначения, группы) до записи, как инвариант `unr`, и отвечает `NOT_SUPPORTED`, если
  наибольшее может встретить `MON` и `ONLY_ARCHIVE` одного поля на одной единице:
  - внутри роли — две папки с `MON` и `ONLY_ARCHIVE` (любые две: состав папок меняется позже);
  - между действующими ролями одного человека (прямо или через группы) — одна роль даёт `MON`, другая `ONLY_ARCHIVE` в
    любой точке. Исключение — две разные точки `unit:`: они одну единицу не покрывают.

  Поле порядка у строк роли («в ярусе побеждает точка с наибольшим уровнем») чинит пару только внутри роли, между ролями
  максимум по каждой `sub` остаётся. Поэтому его нет. Ответ продукта «объединение» («Запрос продукту» п. 2) снимет этот
  отказ.
- **`MON_PROT`** («Просмотр на охране») переводом ADR-0097 §7 не объявлен — `NOT_SUPPORTED` до ответа продукта («Запрос
  продукту» п. 3). Если его переведут как `MON`, пара с `ONLY_ARCHIVE` входит в тот же отказ.
- **Хранилище** (решение «Архитектора» А4). У тома `rec/volumes` единицы нет: в манифесте `rec` `rights.unit_of` есть только
  у `keeps`. Проверка тома идёт с `unit = null`, её покрывает только `*`. Поэтому `objectAccess` хранилища в `unit:` не
  переводится. Поле `arch` (`dArch`, корень) и записи камер (поле `cam`) пишут в одну `sub: rec`. Поэтому `arch`
  переводится, только если в `rec` на `*` даёт не больше, чем уровень `cam` в точке `*`; иначе — `NOT_SUPPORTED` у
  `/access/apply`. Что даёт `arch: FULL` в `rec`, задаёт V/11. Иначе `dArch: FULL` при `dCam: MON` открыл бы записи всех
  камер.
- Записи камеры (`rec/recordings`, `about: cam`) наследуют папки камеры через about. Это совпадает с consolem: архив
  камеры у него даёт уровень `cam`, посчитанный по папкам камеры. Хранилище у consolem в папках не лежит
  (`ACC_NOFOLDER`), у платформы у тома нет единицы — расхождения нет.
- Других пар полей в одной подсистеме нет: `mic` и прочие устройства, кроме камер, не переводятся (V/11.3).
- Функции роли (`DEVICES_SETUP` → `admin cam` …, ADR-0097 §7) тоже пишутся в точки. Как функция сочетается с уровнем
  объекта — «Запрос продукту» п. 1. До ответа `backend` считает, что функция действует только там, где уровень объекта
  даёт хоть что-то в этой подсистеме. Это сужение: `DEVICES_SETUP` при `dCam = FORBID` не создаёт камеру вне папок.
- Подпапка ниже родителя — строки `folder:` подпапки: ярус 3 берёт ближайшую.
- Чего нет в строках (`tel`, `depth`, `restr`, расписания, …), по-прежнему не объявляется (ADR-0097 §7).

### 8. Порядок
1. ADR-0097, ADR-0098 и это решение вводятся **одним приращением** норм и кода (после зачёта B). Читатель, который знает
   строки ролей, знает и ярусы. Строки ролей без ярусов и `none` без ролей не исполняет никто.
2. «Спецификация домена»: P/08.4 Н1.3 (`cap: none`; 400 на `none` у прямых строк и на `labels:` у строк ролей; разбор
   строки в две ступени), договор `may` (группы, ярусы, ничья, вход `chains` и «неизвестно», «нечитаемо» и 503, отсечка,
   шаг 6), векторы `may` и `covers.tsv`.
3. «Спецификация»: договор сторожевой (стражи §3, страж отсутствующей строки, цепочки во входе), P/06.4 (быстрый путь,
   события с `of`), правила записи папок (§4), P/06.7 (`/session`), лента B2, P/07 (подсказка).
4. «Спецификация VMS»: V/11 — перевод §7 (точка `*`, корень в папках первого уровня, `NOT_SUPPORTED` пар уровней,
   `MON_PROT`, хранилище, определение `unr`).
5. Пометки «заменяется ADR-0099» — в ADR-0097 §6, §7, §8.4, ADR-0098 п. 3; «уточняется ADR-0099 §7» — ADR-0098 §5
   («Архитектор»).

### Consequences
* Good, because любая роль consolem с исключениями переводится без потерь: `NOT_SUPPORTED` по понижениям больше нет.
* Good, because смысл совпадает с consolem `9849d28` и его «Итоговым доступом»: интерфейс показывает то, что решит
  сервер.
* Good, because прямые строки и их смысл не меняются; `none` в них запрещён.
* Good, because запрет в одной роли не отнимает права другой — добавить роль никогда не сужает права.
* Good, because нечитаемое внутри роли не открывает её более общую область: исход — 503, а не право `*`.
* Bad, because прототип 11 consolem считает иначе: исключение объекта из одной роли там отнимает у человека папки и
  умолчания других ролей. Если consolem выпустит прототип 11, его «Итоговый доступ» покажет отказ там, где сервер
  разрешит («Запрос продукту» п. 4).
* Bad, because `may` сложнее: группы, четыре яруса, цепочки папок вместо набора, «нечитаемо» как третий исход группы.
* Bad, because у роли с `folder:` и `*` членство читается и тогда, когда разрешил `*` (если отсечка не решила).
* Bad, because 503 бывает чаще: сбой чтения членства или строки единицы у роли с исключением — 503, а не 403.
* Bad, because перевод пишет строку на каждую подсистему вида в каждой точке, в том числе `none`, и строки корня в
  папках первого уровня: строк у роли больше.
* Bad, because стражи членства ставятся чаще — и при разрешении по `*`.
* Bad, because роли с сочетанием `MON` и `ONLY_ARCHIVE` (в двух папках роли или в двух ролях человека), `MON_PROT` и
  `arch` выше `cam` — `NOT_SUPPORTED` до ответа продукта и V/11.
* Bad, because снять единицу из папки теперь нельзя без права на неё, а удалить папку со строками ролей на поддереве —
  без `admin` на `*` в их подсистемах.
* Neutral, because истёкшая строка-исключение поднимает права до уровня папки; у consolem сроков у исключений нет.
* Neutral, because `labels:` в строках ролей запрещён, пока нет потребителя; прямые строки `labels:` не меняются.

### Confirmation
* Векторы `may`:
  - роль `edit folder:F` + `none unit:cam/7` — камера 7 deny, другая камера в `F` allow;
  - та же роль и другая роль с `view unit:cam/7` — allow; прямая строка `admin *` + роль с `none unit:cam/7` — allow;
  - подпапка `none` под `edit` родителя — deny; две папки объекта с `view` и `edit` — `edit`; `none folder:F` и
    `view folder:G` у объекта в обеих — `view`;
  - `none` и `view` одной `(sub, scope)` в одной роли — allow;
  - `unit = "*"` и `unit = null` — только ярус 4; истёкший `none` — ярус папки;
  - нечитаемое: роль `admin *` + `none unit:cam/7` с испорченным `until` второй строки — 503; `edit *` + `none
    unit:cam/7`, проверка `det/5` (about `cam/7`) при нечитаемой строке `det/5` — 503; `none folder:F` + `admin *` при
    нечитаемом членстве или предке в цепочке — 503; та же нечитаемость рядом с прямой строкой `admin *` — allow; у роли

    `sub: live`).
* `covers.tsv`: ярусы 1–4 и выбор первого непустого.
* Приёмка P/08.4: `none` у прямой строки — 400 bad line; `labels:` у строки роли — 400 bad line.
* Приёмка P/06:
  - запись по `*` роли с `none folder:F` при одновременном добавлении единицы в `F` — 412 стража;

## Pros and Cons of the Options
### (а') Исключение объекта сильнее всех ролей (прототип 11)
* Good, because совпадает с прототипом 11 consolem.
* Good, because у роли с исключением решение принимается без членства: чтений и стражей меньше.
* Bad, because добавить роль может сузить права: монотонность между ролями теряется.
* Bad, because нечитаемая строка или назначение любой роли делает нечитаемым итог всех ролей: исключение пропавшей роли
  снялось бы со всех остальных.
* Bad, because не совпадает с consolem `9849d28`, по которому переводится V/11 (отклонено владельцем 2026-10-30).

### (б) Запрет перекрывает всё
* Good, because правило проще: любое «нельзя» — отказ.
* Bad, because не совпадает с consolem: роль с исключением отнимала бы права, которые дают другие роли и прямые строки;
  добавление роли сужало бы права.

### (в) Без исключений
* Good, because `may` не меняется.
* Bad, because обычные роли consolem («вся папка, кроме этой камеры») не переводятся (отклонено владельцем).

## Запрос продукту (через «Консоль», с «пушь» владельца)
1. Как функции роли сочетаются с уровнем объекта. Настраивает ли `DEVICES_SETUP` камеру, на которую в этой же роли
   `FORBID` или `MON`? Создаёт ли `DEVICES_SETUP` камеру, если умолчание роли `dCam = FORBID`? Ставит ли
   `ARCHIVES_SETUP` хранение камеры с `ONLY_ARCHIVE`? До ответа — «функция только там, где уровень объекта даёт хоть
   что-то в подсистеме» (§7).
2. `MON` ∨ `ONLY_ARCHIVE` = `MON`: у consolem камера в двух папках роли (`MON` и `ONLY_ARCHIVE`) или человек с двумя такими
   ролями получает `MON` без архива — добавление роли с живым видео убирает архив. Это замысел или следствие линейного
   списка уровней? Если ответ «объединение» (`ARCHIVE`), такие роли переводятся; до ответа — `NOT_SUPPORTED` (§7).
3. `MON_PROT` («Просмотр на охране»): что он даёт — живое видео, архив, что-то сверх `MON`? До ответа — `NOT_SUPPORTED`.
4. Прототип 11 (`6bffe89`): исключение объекта из любой роли сильнее папок и умолчаний всех ролей. Владелец выбрал
   «внутри своей роли», как `index.html` `9849d28`. Просим consolem считать «Итоговый доступ» так же. Иначе интерфейс
   покажет отказ там, где сервер разрешит.

**Правка 2026-10-31.** §4: право судится в подсистеме единицы, поэтому строка `none` чужой `sub` снимается этим же правом; это политика (`decisions/inbox/2026-10-31-решения-норм-приращение-прав.md`).
