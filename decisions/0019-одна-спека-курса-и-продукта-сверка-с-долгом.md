# Спеки курса и продукта — один YAML; расхождения проверяются тестами с убывающим долгом

## Context and Problem Statement
Класс системы: платформенная система. Курс и продукт описывают одни подсистемы (`vms`, `rec`, `live`, `auto`) своими спеками; ключи сводились по письмам, и файлы расходились: у курса ключи шагов 6–7, у продукта свои (`heartbeat.strings`, `secrets`, `objects.door`, слова консоли).

## Considered Options
* сводить ключи по договорённости, без проверки;
* проверять тестом на обеих сторонах, расхождения записывать долгом, который может только убывать.

## Decision Outcome
Выбрано второе. В продукте `vms/spec_parity_test.go` сверяет пути ключей общих спек с `Source/vms/*.subsystem.yaml` курса, а `vms/spec_load_test.go` грузит спеки курса строгим загрузчиком продукта; у курса зеркальные тесты. Данные (слова `display`, JSON Schema полей, строки `secret_in`) и подсистемы одной стороны не сравниваются. Долг каждого теста — файл с именами путей; новая разница — красный, устаревшая строка долга — красный. Без соседнего checkout другой стороны тест пропускается: каждая сторона собирается одна.

### Consequences
* Good, because расхождение видно в момент, когда его вносят, и закрывается явно: одна сторона реализует ключ, другая убирает, или обе переименовывают.
* Bad, because каждое изменение спеки на одной стороне требует хода на другой или строки долга.

### Confirmation
Тесты сверки и загрузки зелёные на обеих сторонах при соседних checkout; долг сверки продукта и курса совпадает байт в байт.
