## 1. О чём эта система

Платформа — это общий каркас, на котором живут **подсистемы**: видеонаблюдение (VMS) с его камерами и архивами, учебная подсистема счётчиков `testsub`, любая другая. Платформа не знает, что такое камера. Она умеет одно и то же для всех: хранить состояние, узнавать устройство подсистемы из декларативного описания, запускать и размещать рабочие процессы, раздавать права, держать секреты, собирать события и показывать всё это человеку в консоли.

Сквозной пример модуля — учебная подсистема `testsub`, чьи единицы — именованные счётчики. Она нарочно простая, чтобы на ней было видно механизм, а не предметную область. Всё, что рассказано про счётчики, буквально то же самое делается для камер: вместо «счётчик c1» читайте «камера 7».

Два принципа, на которых стоит всё остальное:

- **Всё состояние — строки в одном хранилище «ключ → значение»**. Нет ни отдельной базы для расписаний, ни службы координации, ни оркестратора. Хранилище умеет нарочито мало — и на этом немногом построены выдача номеров без координатора, доказательство права писать, контроллер, который не ломается при двух запущенных экземплярах, и повтор записи, который не применяется дважды.
- **Платформа исполняет манифест, а не код подсистемы**. Устройство подсистемы описано одним YAML-файлом — манифестом. Платформа читает знакомые ключи и ведёт себя соответственно; произвольный код из файла она не получает.

И ещё одно следствие, которое определило форму самого курса: процессы говорят друг с другом по HTTP поверх unix-сокетов и TLS, а приёмка идёт снаружи, через эти двери, одними и теми же сценариями для любой реализации. Поэтому реализацию можно написать на любом языке — правила не привязаны ни к Python, ни к Go.

Урок модуля — не тема, а процесс или библиотека со своим контрактом и приёмкой. Разделы 2–12 рассказывают один кластер: хранилище (урок P/01), манифест и установщик (P/02), воркер (P/03), контроллер (P/04), ресурс (P/05), консоль (P/06), модуль консоли (P/07). Разделы 13–19 — домен, который соединяет независимые кластеры: процесс `domain` держателя (P/08), агент члена и ретранслятор (P/09), консоль домена (P/10).

Несколько коротких слов курса, которые встречаются сразу: **строка** — запись хранилища (row, не строка текста); **дверь** — HTTP API процесса; **коробка** — один сервер без группы; **группа** — кластер серверов с реплицированным журналом; **отказ** — ответ не-200; **проход** — семантика операции по шагам.

## 2. Хранилище: шесть слов и три гарантии

### 2.1. Модель данных

В хранилище одна сущность — **строка**:

| Поле | Что это | Пример |
|---|---|---|
| `key` | имя, путь через `/` | `testsub/counters/c1` |
| `items` | содержимое: словарь «строка → строка» | `{"name": "c1", "value": "7"}` |
| `index` | версия, которую выдало хранилище | `"42"` |

Отсутствующая строка читается как `items = null`, `index = ""` — это не ошибка. Все значения в `items` — строки байт; типы восстанавливаются по манифесту на стороне читателя (раздел 3).

### 2.2. Шесть слов

Четыре операции — **прочитать**, **перечислить**, **записать**, **удалить** — и два условия записи:

- **`cas`** — условие на версию той же строки;
- **`guard`** (страж) — условие на версию *другой* строки.

Этими шестью словами написаны все проходы платформы. Свои примитивы, «атомарно» и «одновременно» без операции словаря нигде больше не допускаются.

| Операция | Вход | Результат |
|---|---|---|
| прочитать | key | `items` и `index`; отсутствующая — `null`, `""` |
| перечислить | prefix | все ключи с префиксом и их версии, по порядку байтов; содержимого не отдаёт и прав на него не требует |
| записать | key, items, `cas`?, `guard`?, `id`? | новая версия |
| удалить | key, `cas`?, `guard`?, `id`? | новая версия; удалить отсутствующее — не ошибка |

Каждая операция неделима: между её шагами никто не вклинится. На коробке это блокировка, в группе — одна запись журнала консенсуса. Чтение линеаризуемо: оно видит все записи, о которых уже узнал хоть один клиент (в группе чтение идёт через лидера).

### 2.3. Гарантия 1: CAS — одна строка правится по очереди

Два процесса читают один счётчик и оба хотят его увеличить:

```
A: прочитать testsub/counters/c1                  → {"value": "7"}, index "41"
B: прочитать testsub/counters/c1                  → {"value": "7"}, index "41"
A: записать  testsub/counters/c1 {8} cas="41"     → index "42"        успех
B: записать  testsub/counters/c1 {8} cas="41"     → 409 conflict      B опоздал
```

B не затёр изменение A молча: он получил отказ, перечитал и повторил. Никаких блокировок в прикладном коде. Поле `cas` бывает трёх видов: не задано — запись всегда, поверх; `""` — только если строки ещё нет (создание, побеждает первый); версия — только если версия ровно эта.

### 2.4. Гарантия 2: версии не повторяются и непрозрачны

Версия — строка байт, которую выдало хранилище. Её возвращают как есть и сравнивают **только на равенство**. У реплицированного хранилища версия выглядит как номер в журнале, и соблазнительно написать `if v > old` — но это форма провода, а не обещание. Одна такая строчка — и хранилища, где версия просто строка (как `resourceVersion` в Kubernetes), больше не подходят.

Хранилище никогда не выдаёт одну версию дважды — ни после перезапуска, ни после смены лидера, ни после удаления строки. Удаление тоже тратит версию: иначе строка, созданная на месте удалённой, получила бы старую версию, и процесс с `cas` по ней затёр бы строку, которую никогда не видел.

### 2.5. Гарантия 3: страж — запись зависит от другой строки

Пусть `example/permit` называет процесс, которому разрешено менять `example/counter`. A прочитал разрешение на версии `"70"` и задержался; разрешение перешло к B. Проверка отдельным чтением не помогает — между чтением и записью разрешение снова может измениться. Страж проверяет версию основания **внутри той же операции**:

```
A: записать example/counter {"value": "8"} guard={key: "example/permit", index: "70"}
   → 412 guard {key: "example/permit", index: "71"}
```

Хранилище не знает смысла полей — оно сравнило версии и отказало: основание, на котором A собирался писать, уже изменилось. На этом построено всё владение в платформе (разделы 4–6). Страж проверяется **раньше** cas: при нарушении обоих ответ — `412 guard`. Смысл разный: `409` значит «перечитай изменяемую строку и повтори», `412` — «остановись и заново проверь основание». Страж с `index: ""` означает «пока этой строки нет».

### 2.6. Ключ пишется одним способом

Для человека `testsub/a/../b` и `testsub/b` — одно место; для хранилища — две разные строки с разными версиями, и взаимное исключение между ними не сработает не из-за гонки, а из-за написания. Поэтому ключ, который можно записать двумя способами, отвергается (`400 badkey`), а не нормализуется. Префикс перечисления — не ключ: это просто байты, с которых начинается имя, и правила ключа к нему не применяются.

### 2.7. Три исхода записи

У записи не два исхода, а три: **сделана**, **точно не сделана**, **неизвестно**. Третий возможен и на одной коробке (ответ потерялся; строка опубликована, а подтверждение сохранения на носителе не удалось), а в группе — тем более: запись дошла до лидера, и он упал, не ответив.

| Ответ | Что случилось | Что делать |
|---|---|---|
| `200` | запись применена | ничего |
| `503 unavailable` | лидер не найден за срок или занят предел соединений; запись **точно не дошла** | повторить как есть на следующем шаге (при `Retry-After` — не раньше срока) |
| `503 ambiguous` | надёжный результат **неизвестен**: отказал барьер долговечности или пропал лидер после приёма | повторить **с тем же `id`** |

Угадать исход при `ambiguous` нельзя. Решили «не применилась» и повторили с тем же `cas` — если первая прошла, придёт `409 conflict`, и клиент решит, что строку изменил чужой, хотя это была его собственная запись. Решили «применилась» — если она не дошла, запись потеряна. Прочитать и посмотреть не помогает: свою запись не отличить от чужой с тем же содержимым.

Решение — **идентификатор записи `id`**: клиент ставит на каждую запись случайный `id` (32 шестнадцатеричных знака). Повтор с тем же `id` вернёт ответ первой попытки с пометкой `again: true`, если она применилась, и выполнится как первая, если нет. Клиенту не нужно различать эти случаи. Хранилище помнит `id` не меньше двух минут после первого применения и пока после него применено меньше 50 000 записей с идентификатором; только когда оба условия выполнены, `id` может быть забыт — поэтому у каждой важной записи есть ещё и `cas`: он подстраховывает там, где память `id` кончилась.

И главное: ни `unavailable`, ни `ambiguous` — не `conflict`. Конфликт значит «строку изменил кто-то другой». Если бы смена лидера отвечала конфликтом, клиенты ошибались бы при каждых выборах — живой воркер останавливался бы от ложного конфликта на продлении слота (раздел 6).

### 2.8. Отказы и пределы размера

Список отказов закрыт: код, `kind` и поля нормированы, новых видов не бывает без правки норм. Для понимания достаточно четырёх групп: ошибки кода и развёртывания (`badkey`, `badrequest`, `forbidden`, `toolarge`) — не повторять, чинить; `conflict` — перечитать и повторить; `guard` — не повторять, проверить основание; `unavailable`/`ambiguous` — повторить, второй только с тем же `id`. Оборвавшийся или непришедший ответ клиент считает `unavailable` для чтения и `ambiguous` для записи — и не роняет свой цикл исключением.

У размера две разные границы: хранилище считает вес имён и значений `items`, а дверь ограничивает всё HTTP-тело с JSON-обрамлением. Поэтому строка ровно на своём потолке может помещаться, хотя запрос чуть больше неё. В отказе `toolarge` поле `limit` называет сработавшую границу.

Процессы говорят с хранилищем по HTTP с JSON через unix-сокет своего сервера. Что реализация выбирает сама: чем обеспечена неделимость, откуда берутся версии, как данные лежат на диске, сколько помнит `id` сверх минимума.

## 3. Манифест подсистемы и строгий загрузчик

### 3.1. Один файл описывает подсистему

Платформа узнаёт устройство подсистемы из манифеста — одного файла YAML:

```yaml
name: testsub
unit:
  rows: counters
  id: name
  fields:
    name:  {type: string, required: true}
    start: {type: int, default: 0}
placement:
  capacity: {from: capacity, default: 4}
```

`name` — имя подсистемы; в `unit.fields` автор называет поля счётчика. Слово `start` принадлежит автору, а слова `type`, `required`, `default` — грамматике платформы. Платформе не нужно знать, что такое счётчик: ей достаточно общего описания полей. У поля есть тип и дополнительные свойства (`default`, `inherit`, `required`, `fixed`, `unique`, …); одновременно `default` и `inherit` задавать нельзя.

### 3.2. Незнакомый ключ — отказ, не предупреждение

Опечатка в манифесте опаснее опечатки в подписи кнопки: автор думает, что включил проверку, а программа молча пропустит незнакомый ключ `fallbak`. Строгий загрузчик останавливает такую ошибку до начала работы: он либо принимает документ целиком, либо объясняет, почему тот не является манифестом.

Закрытый набор действует на каждом уровне, но уровни устроены по-разному. В `unit.fields` ключи — имена автора; в описании каждого поля ключи снова принадлежат платформе; есть и явно обозначенные непрозрачные места (тело JSON Schema), где загрузчик проверяет только внешнюю форму. Порядок проверки фиксирован: сначала текст и имя подсистемы, затем незнакомые ключи (все — в один отказ), и только потом значения и ссылки. Половина принятого манифеста не возвращается: иначе процессы начали бы работать по описанию, которого автор не писал.

### 3.3. Почему недостаточно просто прочитать YAML

Разные библиотеки понимают один текст по-разному: `Off` — как логическое значение или слово, `010` — как восьмеричное или десятичное, повторный ключ незаметно заменяется последним значением. Поэтому у манифеста своё подмножество YAML 1.2: `Off` — слово, `010` — десять, число в кавычках остаётся строкой; повторные ключи, якоря и теги отвергаются. Проверяется сам текст, а не только объект из библиотеки — так одинаковый смысл документа сохраняется на разных языках. Загрузчик не превращает `"90"` в `90` по догадке.

### 3.4. Отсутствие и пустое значение — разные вещи

У большинства ключей есть умолчания; отсутствие необязательного раздела включает правило его владельца. Но отсутствие ключа само по себе не включает удаление данных и не ослабляет проверку права писать: `placement.unplaced.delete_after` разрешает удаление по сроку только потому, что автор явно его выбрал. Пустое `lease:` (ключ есть, значения нет) — отказ, а не умолчание. Обязательные вещи — имя подсистемы, `unit` с явными `rows`/`id`, `placement.capacity.default`: загрузчик не выбирает за автора.

### 3.5. Один манифест для всех процессов

Если каждый процесс читает свой файл, во время обновления они получат разные правила. Поэтому источник манифеста кластера — строка `platform/manifest/<sub>` в хранилище. Установщик проверяет исходный файл, затем записывает его байты (включая комментарии), дайджест SHA-256 и ревизию `rev` (первая установка — `1`; ревизия манифеста не то же самое, что непрозрачная версия строки хранилища). Даже правильный документ может не поместиться в строку — тогда установщик сообщает о превышении потолка и заканчивает работу до публикации метки.

Работающие процессы следят за маленькой строкой-меткой `platform/manifest/<sub>/rev`, которую установщик пишет после основной строки. Гонки разобраны явно: процесс, стартовавший между двумя записями, ждёт, когда метка догонит его ревизию, а не возвращается к старым правилам; запись с `cas` не даёт отставшему установщику понизить метку; остановка установщика между записями оставляет старую метку до следующего `manifest put`, и какое-то время старые процессы работают по старому манифесту, а новые — по новому.

Процесс с отсутствующей или неверным манифестом не начинает работу. Обнаружив новую ревизию, работающий процесс останавливается, и супервизор запускает его снова: живой перечитки нет, новый запуск проверяет описание целиком.

### 3.6. Что получает консоль

Процедура загрузки получает байты и имя источника и возвращает манифест либо объяснение отказа — это вход реализации, не HTTP. Через него проходят файл, строка хранилища и встроенное описание. У консоли отдельная дверь `GET /manifest`: она отдаёт форму уже загруженной подсистемы для страницы (`ManifestView`) — поля и слова интерфейса, не исходный YAML. Ревизия в этот ответ не входит: консоль, обнаружившая её смену, завершает работу и запускается заново.

Приёмка загрузчика — таблица вердиктов: каждому файлу соответствует `ok` или `refused`, файлы подаются по одному через штатный путь. Авария загрузчика не считается правильным отказом: нужен ответ словами, называющий файл; для выбранных случаев ожидаются ещё и пути ключей с номерами строк.

## 4. Единицы, слоты, эпохи, аренда

P/01 и P/02 дали строки и манифест. Теперь нужно связать желание оператора с процессом, который выполняет работу, и отличать правку счётчика от смены процесса. Для этого пять понятий: **единица** — то, что оператор создал по манифесту (счётчик `c1`); **воркер** — процесс, который ведёт единицы; **слот** — строка, подтверждающая, что процесс владеет именем воркера; **эпоха** — номер попытки вести единицу; **аренда** — ограниченное время, в течение которого процесс вправе действовать по последнему подтверждению.

### 4.1. Одна единица, четыре числа

Оператор создаёт счётчик через консоль: `POST /counters` с телом `{"name": "c1", "start": 5}` и заголовком `Idempotency-Key: create-c1`. Консоль создаёт строку `testsub/counters/c1` с элементами-строками: `id: "c1"`, `revision: "1"`, `name: "c1"`, `start: "5"`, `labels: ""`. В JSON-ответе `start` и `revision` уже числа, а `labels` — список: консоль восстанавливает типы по манифесту; ответ на создание содержит и `worker: null`.

Когда воркер начинает вести счётчик, появляются ещё две строки: `testsub/slots/w-1` (какой экземпляр носит имя `w-1`) и `testsub/epoch/c1` (какая по счёту попытка ведёт `c1`). Числа отвечают на разные вопросы:

| Значение | Что меняется |
|---|---|
| версия строки хранилища | результат записи, с которым сравнивает `cas` |
| `revision` единицы | каждое успешное редактирование оператором (повторная правка `start: 5` тоже увеличит) |
| `gen` слота | каждый захват имени |
| `epoch` единицы | каждое новое взятие единицы воркером |

Поле, из которого получен именованный id (`name`), переименовать через PUT нельзя: новое значение получает 400. Перезапуск работы тем же держателем сохраняет эпоху; потеря единицы и новое взятие требуют новой. Проверка `unique` выполняется перед записью, и две одновременные правки разных строк могут обе её пройти — cas каждой строки не связывает эти проверки в одну операцию.

**Отсутствующее поле имеет смысл.** При создании непереданный `start` берётся из `default` манифеста; у `labels` нет ни default, ни inherit — его пустая форма `[]`, в строке пустой текст. Приоритет: переданное значение → правило отсутствия inherit → default → пустая форма типа. При правке непереданное поле сохраняет прежнее значение. Обязательное поле всё равно должно быть передано — default его не подменяет. Наследуемое поле `step`, не заданное оператором, в строке отсутствует вовсе: запись пустой строки уничтожила бы различие «не задано» и «задано пустым». Списки с запятыми или пустыми элементами хранятся формой массива JSON — иначе `["a,b","c"]` неотличим от трёх элементов, а `[]` от `[""]`.

### 4.2. Повтор создания и память заявки

Ответ на создание может потеряться после успешной записи; простой повтор получил бы `409 exists`. Поэтому POST несёт `Idempotency-Key`, который становится сегментом ключа хранилища (поэтому `..` в нём отвергается до записи). Консоль сохраняет заявку под `testsub/idem/<ключ>`: завершённая заявка с тем же отпечатком возвращает прежний ответ; другой запрос под тем же ключом — `422 key reused`; пока другая консоль работает с заявкой — `409 in flight`. Отпечаток учитывает вызывающего, метод, путь и тело.

Заявка, числовой счётчик и строка единицы записываются отдельно. Если процесс остановился между записями, продолжение зависит от того, что сохранилось; номер, поднятый в счётчике, но не записанный в заявку, сгорает. После 30 секунд зависшую заявку может продолжить консоль с тем же отпечатком — но прежний процесс мог ожить, поэтому перехват меняет версию заявки, а записи счётчика и единицы проверяют её стражем: поздняя консоль не создаст вторую единицу. Память заявок — часть состояния: удаление строк единиц не делает повторный прогон чистым, поэтому приёмка задаёт начальное состояние и для данных, и для заявок.

### 4.3. Удаление оставляет надгробие

Удаление записывает в строку `deleted: "true"` — это **надгробие**. Правка и повторное удаление отвечают `404`; физическая строка нужна другим участникам, чтобы заметить удаление. Само удаление не увеличивает `revision`; новое создание над надгробием продолжает номер (удалённый на ревизии 3 → новый получает 4). Вернуть имя можно только с прежними значениями `fixed`-полей: смена неизменяемого свойства — другая единица под другим именем. Числовые id берутся из отдельного счётчика с учётом надгробий (а при восстановлении повреждённого счётчика — и живых заявок): очистка строк не считается безопасным способом начать нумерацию заново.

### 4.4. Слот доказывает владение именем

Процесс запущен с желанием называться `w-1`. Чтобы получить имя, он записывает свой экземпляр в `testsub/slots/w-1` с `cas` по прочитанной версии: два процесса могут прочитать одну свободную строку, записать по ней — один.

Имя и экземпляр различаются: после перезапуска имя остаётся `w-1`, а `holder` другой. Счётчик `gen` растёт при захвате; `until` — срок на часах писателя, а читатель судит живость по возрасту наблюдаемой версии на своих монотонных часах, поэтому сдвиг часов писателя не меняет судьбу. Пустой holder ещё не значит «доступно любому»: контроллер может предложить имя запасному для определённого набора меток. Имя, заданное при запуске, разрешено забрать у прежнего экземпляра своей коробки только при первом старте; отсечённый процесс это право заново не получает и ждёт освобождения имени. Повреждённый срок при читаемом поколении восстанавливается захватом после установленного ожидания; нечитаемое `gen` не восстанавливается подстановкой нуля — автоматический захват отказывается, сохраняя строку.

При смене держателя новый владелец сначала записывает слот с `released: true`, затем удаляет служебные вклады предшественника под стражем этой версии слота и только потом — `released: false`: старые вклады не показываются под живым именем нового владельца.

Страж из раздела 2 защищает каждую запись под именем: `guard: {key: "testsub/slots/w-1", index: "<версия слота>"}`. Причиной `412` бывает и собственное продление (holder и gen прежние, версия изменилась) — поэтому после 412 воркер перечитывает владение: своё продление сохраняет имя, чужой захват лишает его. Страж защищает конкретную версию владения; течение времени за процессом он не проверяет.

### 4.5. Эпоха разделяет результаты попыток

Старый процесс может зависнуть, а потом продолжить, не узнав о смене владельца. При новом взятии единицы воркер увеличивает строку эпохи с `cas`, и номер входит в имена данных: старая попытка пишет под `…/c1/e2/…`, новая — под `…/c1/e3/…`. Эпоха сама старый процесс не останавливает — она позволяет читателю отличить текущие данные от отсечённых. Отсутствующая строка эпохи и нечитаемая дают разные исходы: в первом случае счёт начинается, во втором запуск отказывается — нельзя выдать новый номер, притворившись, что истории нет. При выдаче учитывается нижняя граница `platform/epoch_floor` (зачем — раздел 12).

### 4.6. Аренда ограничивает время действия

Аренда даёт окно 25 секунд (срок 30 с с запасом 5). Воркер подтверждает свою эпоху чтением, а начало окна считает от момента **запроса** по монотонным часам: если ответ шёл долго, задержка не добавляет времени. Первое окно при выдаче эпохи — то же правило: ответ через 30 секунд уже опоздал, единица не запускается, номер не возвращается.

Последнее подтверждение в момент 0; до момента 25 воркер может действовать. Дальше:

- чужая или нечитаемая эпоха — `fenced`: попытка отсечена;
- хранилище не ответило на запрос, начатый внутри окна — `silent`;
- процесс пропустил окно без запроса — `lost`; поздний ответ проспанную аренду не оживляет.

Действия (команда устройству) разрешены только в подтверждённом окне. Для записи данных манифест может задать `lease.unconfirmed_max` — сколько продолжать при молчании (умолчание `off` — нисколько); продолжение относится к `silent`, не к проспавшему процессу, и данные продолжают нести свою эпоху. При `forever` молчание само по себе не задаёт конечного срока остановки данных: фраза «к 25 секундам всё остановилось» применима к действиям, а данные ограничены потолком и отсечением по эпохе.

## 5. Контроллер и размещение

Контроллер подсистемы — процесс, который на каждом проходе читает мир, ведёт локальную историю наблюдения и сохраняет решения в хранилище: где какой единице быть, чей слот отдать, сколько запасных позвать. Экземпляры на разных серверах читают общее состояние; лидера нет.

### 5.1. Строка — решение, назначения его исполняют

Завершённое решение «`c1` — воркеру `w-2`» хранится в `testsub/placement/c1`; список `testsub/workers/w-2` его исполняет. Во время изменения есть две служебные строки: `placement_turn` допускает одного контроллера к записи, `placement_intent` хранит состав и цель операции. Пока intent активен, он определяет размещение своих единиц: остановка процесса не теряет ни решение, ни резерв места.

Переезд: записать intent → снять группу из всех назначений → довести строки placement → одной записью добавить группу на выбранного воркера → отметить intent завершённым. Каждая запись защищена `cas` целевой строки и `guard` версии turn. Новый контроллер сначала завершает оставленный intent; поздние записи прежнего получают 412. Из источников снимают всех прежде добавления в цель. Действия прежних процессов ограничены их арендой (25 с), данные при `silent` могут продолжаться по `unconfirmed_max` и различимы эпохой.

Чего контроллер **не делает**: не запускает процессов (публикует числа и предложения; запускает хозяйство сервера), не переставляет размещённое без объявленного основания (добавить более свободного воркера ничего не двигает; объявленный `home` может вернуть единицу в пределах `HOME_BUDGET`), не лечит молчащих (молчание — факт, который он записывает), не слушает консоль (консоль, умеющая размещать, — второй контроллер с браузером перед ним).

### 5.2. Картина мира без срока давности

Три факта о воркере контроллер берёт из его пульса без срока давности: ёмкость, сервер, метки узла. Ёмкость — слово воркера, не мнение контроллера: смешанный парк серверов невозможен иначе. Срок давности есть у одного — у факта жизни: воркер жив, если его пульс **менялся** в последние 45 с по часам контроллера. Не «ts в пульсе свежий» — часы воркера могут убежать вперёд, — а «я видел, как он изменился». Поэтому только что запустившийся контроллер первые 45 с никого не считает мёртвым: всё впервые увиденное для него «только что изменилось».

Метки сервера — отдельная строка `platform/servers/<s> {labels}`, которую правит администратор из консоли; пока строки нет, метки берутся из узла через пульс. Строка побеждает, даже пустая: пустая значит «сервер не достаёт ни до одной сети». Нечитаемая строка оставляет последние прочитанные метки и запрещает судить о достижимости с этого сервера.

### 5.3. Пул, ограничение, предпочтение

Выбор воркера — три слоя, их нельзя путать:

- **Пул** — кто вообще может нести: живые воркеры минус отданные слоты, минус воркеры дренируемого и выведенного сервера, минус (при `requires: resource`) те, чей ресурс молчит, минус (при `servers: distinct`) все, кроме одного на место.
- **Ограничение сужает пул** для данной единицы: `labels-subset` (метки единицы ⊆ меток воркера), `spread_by` (не на сервер, где уже есть единица с тем же значением), `affinity` (только место, которое её принимает), группа (только воркер, который уже держит группу).
- **Предпочтение упорядочивает** оставшихся: дом (`home`), сосед (`near`), потом «больше всего свободной ёмкости». Предпочтение никогда не нарушает ограничение и не двигает размещённое, кроме объявленного возврата домой.

Свободная ёмкость для нового допуска — `ёмкость − нагрузка с резервами`: учитываются уникальные единицы в назначении и уже принятых решениях, включая весь активный intent. Фактическая нагрузка считается по назначению: камера 4K тяжелее камеры 720p вдевятеро, и манифест говорит, каким полем строки это выражено. Побеждает наибольшая свободная ёмкость, строго больше; при равенстве — первый в порядке имён. Единица тяжелее ёмкости любого воркера попадает в `unplaceable` со словами.

Группа (`group_by`, например все каналы одного устройства) получает одно решение с местом на всех: разные предпочтения членов не превращаются в независимые решения; если вся группа не помещается, нельзя разместить только удобную часть.

### 5.4. Судьба слота

Версия слота `w-1` не менялась 45 с на часах этого контроллера, пульса нет. Что делать с единицами — зависит от того, что можно узнать:

- **процесс мёртв, ресурс сервера жив и говорит это** — единицы уезжают сразу по истечении срока (`move`);
- **ресурс сервера молчит** — сервер умер или отрезан: срок плюс запас, 90 с наблюдения неизменной версии (`move`);
- **процесс жив, но не продлевает и не пишет пульс** — завис: единицы остаются до `hung_move_after` (15 мин) от первого наблюдения неизменной версии этим судьёй, с тревогой; потом `hung_moved`;
- **про процесс нельзя сказать** — ресурс отвечает, но пульсов нет или присутствие не названо: `unsure`, тот же предел, `unsure_moved`;
- **ресурс жив, но о воркере не сказал** — старый ресурс или незарегистрированный воркер: `wait`, единицы не переезжают без предела, имя отдаётся после `hung_move_after`;
- **сервер неизвестен вовсе** — два молчания: `move` по сроку с запасу;
- **воркер ни в одном назначении** — слот отдаётся (`release`).

Имя отдаётся только исходами `move`, `hung_moved`, `unsure_moved`, `release` и `wait` за пределом — и **привязанным к версии строки слота**: новый процесс берёт имя записью с `cas` по этой версии и не возьмёт, если строка с тех пор менялась. Так зависший, продливший слот в последнюю секунду, не теряет имени под собой. При крахе воркера контроллер **не пишет ничего**: отпущенный слот — утверждение держателя, истёкший — лишь отсутствие.

### 5.5. Ревизия правила

Контроллер читает манифест при старте и пишет `manifest_rev` в каждую строку размещения, которую решил. Контроллер, чей манифест старше `manifest_rev` строки, эту строку не трогает и считает в отчёте (`manifest_behind`); после перезапуска он прочтёт новый манифест и догонит. Так в кластере, где новый манифест раздаётся по серверам, старое правило уступает новому монотонно, а не дёргает единицы туда-сюда.

## 6. Воркер: цикл под слотом

Подсистема пишет только то, что делает её единица: открыть поток камеры, писать архив. Всё, что делает единицу **единицей кластера** — имя, слот, эпоха, аренда, пульс, назначение, остановка по сигналу, — живёт в базовом воркере платформы и одинаково у камеры, рекордера и сценария. Подсистема получает четыре рабочих вызова (запустить единицу, остановить, доложить состояние, сделать шаг сверки) и два вызова упорядоченной остановки; всё остальное она получает готовым и не может забыть.

### 6.1. Три правила цикла

1. **Слот проверяется первым**, до любой эпохи: отказ продления слота значит «ты больше не этот воркер», и дальше смотреть нечего.
2. **Потерянная аренда — дело одной единицы**: единица остановлена, остальные идут.
3. **Молчание хранилища — не потеря**: пока хранилище не ответило, слот ещё мой, аренда не подтверждена, но не отсечена, и манифест решает, писать ли данные дальше.

Кто перепутает первое со вторым — остановит сорок камер из-за одного переезда; кто третье со вторым — остановит все при каждой смене лидера.

### 6.2. Три правила на примерах

**Молчание.** Хранилище переизбирает лидера и пять секунд не отвечает. Шаг аренды `w-1` (ведёт `c1`, `c2`, `c3`): продление слота — ошибка, «всё ещё я»; подтверждения аренд — ошибки, «не подтверждены», все три ещё в окне; данные пишутся, действия разрешены в оставшейся части окна. Если молчание продлится до конца окна (25 с от отправки последнего подтверждённого запроса), действия прекращаются; данные — только по `unconfirmed_max`.

**Переезд.** Контроллер перевёз `c2` на `w-2`, тот взял эпоху 4. Шаг аренды `w-1`: слот мой; `c1`, `c3` подтверждены; у `c2` в строке эпоха 4, моя 3 — отсечена. Назначение прочитано: `c2` там нет — это переезд: `c2` остановлена, эпоха отпущена, остальные идут.

**Две копии.** Администратор по ошибке запустил второй `w-1` на той же коробке; новый взял слот (`gen` 2 — захват у живого на своей коробке разрешён при первом старте). Шаг аренды старого: продление отказано, в строке другой `holder` — состояние **«никто»**: отдать имя, остановить все единицы, отпустить эпохи, тревога `worker.name_taken`. Старый не берёт другое имя: ему дали `w-1`, он ждёт его освобождения.

### 6.3. Что воркер помнит

Эпохи и аренды своих единиц, свой слот и экземпляр, удержание места, имя, которое ему дали при старте (`given`), имя, которое он ищет, потеряв (`seeking`), момент старта, потолок `unconfirmed_max`. **Решений по старому назначению он не принимает**: список перечитывается каждый шаг аренды; последний отвеченный список при неответе хранится с пометкой «не отвечено» и не разрешает вновь взять эпоху; отвеченный список без единицы означает, что она больше не назначена. Экземпляр — `<коробка>:<pid>:<6 hex случайности>`: pid переиспользуются, случайный хвост делает экземпляр уникальным и позволяет узнать «это мой прежний я» при перезапуске.

Ворота перед запуском единицы: начатая выдача эпохи ещё не разрешает запуск; первое окно считается от отправки записи; за время запроса подмена могла отсечь воркера, поэтому возврат ответа вновь проходит ворота; отменённая попытка не оживает даже после возврата имени.

### 6.4. «Не сделано» против «неизвестно» — на продлении слота

Воркер продлевает слот записью с `cas: 5`; запись ушла лидеру, лидер умер, ответа нет. Угадать «не сделано» и повторить с `cas: 5` — если первая применилась, повтор получает `conflict`, и приняв его за чужое владение, получим ложное отсечение: сорок камер остановлены собственным продлением. Угадать «сделано» — если первая не применилась, контроллер по истечении срока отдаст имя, и два воркера будут вести одни единицы: эпоха не даст смешать данные, но команды устройству уйдут дважды. Поэтому дверь отвечает `ambiguous`, а воркер повторяет продление **тем же `id`**: применилась — ответ прежний с `again: true`, нет — применяется сейчас. Так же — захват, отдача, эпоха: всякая запись воркера со значением несёт `id`. А «не сделано» (`unavailable`) повторяют как есть на следующем шаге: аренда ещё идёт.

| Наблюдение | Что прекращается | Что позволяет продолжить |
|---|---|---|
| слот уже принадлежит другому | вся работа прежнего имени | новое получение имени, затем свежее назначение |
| у c2 новая эпоха, слот мой | работа c2 | следующий список и новое взятие эпохи, если назначена |
| хранилище молчит | действия ограничены окном; данные — потолком манифеста | ответ с подтверждением владения |
| длительный шаг пережил подмену | новое взятие эпохи запрещено | цикл снова прочитал назначение |
| своё продление изменило версию слота | запись со старым стражем не проходит | перечитка holder/gen и новая проверка |

Пульс, строка слота и работа подсистемы — три разных наблюдения: строка эпохи, оставшаяся после остановки, не доказывает, что процесс работает. Собственной HTTP-двери у воркера нет: стенд пользуется дверями хранилища и единиц.

## 7. Права: кто звонит и что ему можно

P/06, P/04, P/03 и P/01 раз за разом говорят «писатель строки один». Это обещание ничего не стоит, пока его держит дисциплина кода. Права делают его механизмом: хранилище знает, **кто** звонит, и у каждого «кто» — закрытый список того, что ему можно, выведенный не руками, а из манифестов кластера.

Три опоры:

- **Личность — это сокет** (в кластере) или имя писателя (на одной коробке), а не поле в запросе: что процесс о себе говорит, не читается.
- **Один оценщик** правил для файлового хранилища, памяти и кластера: одинаковый ответ на один вопрос везде, и тест на коробке проверяет права кластера.
- **Права — из манифеста**: файл прав генерируется из каталога манифестов, установщик отказывается ставить устаревший. Слово в манифесте `worker.writes: [shelves]` и есть право; код платформы о камерах ничего не знает.

### 7.1. Четыре роли одного манифеста

Манифест `testsub` рождает роли `testsubcontroller` и `testsubworker`; `console` (одна на все манифесты) и `resource` — роли платформы. Каждая получает ровно те семьи, которые её урок назвал её писателем:

```
console            testsub/counters/*  testsub/next_id  testsub/idem/*  testsub/policy  testsub/sweep  testsub/requests/*
                   platform/servers/*  platform/drain  platform/decommission/*  platform/schema  door/signer  door/keys
testsubcontroller  testsub/workers/*  testsub/placement/*  testsub/slots/*  testsub/decommissioned/*
                   testsub/controller/placement_turn  testsub/controller/placement_intent  (только write, без delete)
                   delete:testsub/counters/*            ← только удаление, и только потому что в манифесте unplaced.delete_after
testsubworker      testsub/epoch/*  testsub/slots/*  testsub/holds/*  + worker.writes + <другая>/requests/* из worker.requests
resource           platform/doors/*  <sub>/requests/free-* (requests.free)
```

Пересечения намеренные: `slots/*` пишут и держатель (захват, продление, отдача), и контроллер (отдать чужой истёкший, предложить имя). Право удаления проверяется отдельно от записи: контроллер может удалять строку единицы по `delete_after`, сохраняя запрет на её запись.

### 7.2. Отказ, а не молчание

Воркер пишет `testsub/placement/c1` → `403 {kind: forbidden, error: "testsubworker may not write testsub/placement/c1"}` — до того, как запись дошла до журнала. Чтение без права — тот же 403. Перечисление — иначе: имена строк под префиксом получает любая роль вместе с версиями, но без значений: имя строки не секрет, и воркеру, чтобы ждать свободного места, не нужно читать чужие строки.

Отрицание сильнее разрешения, где бы оно ни стояло: `["domain/*", "!domain/signer*"]` — всё под `domain/`, кроме подписанта. Образец — точный ключ или префикс со звёздочкой в конце; звёздочка в середине не совпадает ни с чем. Роль, которой нет в файле, не может ничего; пустой список у известной роли запрещает всё. Три вещи не может никто, включая `admin`: удалить строку эпохи (номер нельзя выдать второй раз), удалить под `domain/` не ролью домена, записать или удалить `platform/epoch_floor` иначе как операцией восстановления.

### 7.3. Сокет роли и сертификат роли

В кластере у хранилища по сокету на роль: `/run/configstore/testsubworker.sock`, режим `0660`, группа роли; `admin.sock` — `0600`, только root. Юнит воркера состоит в группе роли и ходит через свой сокет: кто открыл сокет — тот и звонит; заголовок с другой ролью — отказ. Группа платформенной роли — `w2c-<роль>` (`w2c-console`), группа воркера подсистемы — `<развёртывание>-<роль>` (`vms-camworker`). Демон хранилища в группах подсистем не состоит: сокеты он создаёт в setgid-каталогах, владелец каталогов — `w2c`. На коробке у хранилища файлов или памяти внутри процесса ту же работу делает имя писателя — оценщик тот же.

Для дверей между процессами личность — сертификат роли от удостоверяющего центра кластера: SAN URI `urn:w2c:role:<роль>`, CN `<роль>.<сервер>`.

### 7.4. Файл прав

Генератор получает каталог манифестов и имя развёртывания и строит имена ролей, группы и списки прав (имя подсистемы ограничено 32 знаками — `controller`/`worker` помещаются в предел имени роли без усечения). Оператор удерживает каталог неизменным на время генерации, проверки и установки; работающий демон использует уже загруженные права до перезапуска; `--check` отвечает «совпадает ли файл с результатом генерации», не обещая мгновенной смены прав всех демонов.

## 8. Секреты и запечатывание

Пароль камеры нужен воркеру в момент открытия потока. По дороге значение может попасть в ответ консоли, копию ответа для повтора, снимок домена, журнал, аргументы процесса, копию хранилища. Поэтому секрет — не «поле, которое стараются не показывать», а тип данных с четырьмя свойствами:

1. **Узнаётся по имени** (`*_secret`), без реестра.
2. **Показывается маской** (`***`) и никогда значением, на любой глубине ответа.
3. **Лежит запечатанным** в хранилище: консоль запечатывает по пути строки, воркер открывает в последний момент; у контроллера, ресурса и резервной копии ключа нет.
4. **Не живёт в адресе**: `rtsp://admin:hunter2@cam/` — отказ с указанием, в какое поле положить пароль, потому что адрес — вещь публичная.

### 8.1. Один пароль, пять мест

Оператор создаёт камеру: `{source: "rtsp://10.0.0.5/live", cred_username: "admin", cred_secret: "hunter2"}`. Дальше с `hunter2`:

```
дверь консоли      → отказы формы; значение не попало в журнал («поля: source, cred_username, cred_secret»)
запечатать         → cred_secret = enc:v2:k1:<nonce>:<шифртекст>, связано с «cam/cameras/7» и «cred_secret»
строка хранилища   → только конверт; читатели строки видят конверт, не значение
ответ 201          → cred_secret: "***"; копия ответа для повтора ключа — тоже с маской
снимок для домена  → поля без *_secret; адрес — с маской, если в нём был логин
воркер камеры      → open_row в start_unit: конверт → hunter2 → драйверу; в памяти и в пульсе остаётся конверт
```

Конверт нельзя переставить: шифртекст из `cam/cameras/7` не откроется в `cam/cameras/8` и не откроется в поле `access_secret` — он связан с путём строки и именем поля (AAD). Поэтому «скопировать запечатанное в другую строку» — гарантированный отказ, и оператор не может прислать конверт сам: «a sealed value is not taken from outside — give the password itself».

### 8.2. Пароль в адресе

Каждый `url` читается правилом поля: `credentials` называет, куда положить логин и пароль; `secret_in` говорит, в каких параметрах и формах прячутся учётные данные (`?pwd=`, `/user=admin_password=…`, `#~login:pin=…`), сверх общего словаря (`password`, `pwd`, `token`, `key`, `apikey`, `=auth`, `=pin`…). Распознанное отказывается на входе со словами «положите логин в `cred_username`, пароль в `cred_secret`», а в показе маскируется где стоит: `rtsp://admin:***@h/`, `?usr=admin&pwd=***`. Логин показывается, пароль — никогда; отказ значение не повторяет. Распознавание — не эвристика, а таблицы: `secret_in.tsv` (сотни адресов, что показать и что отказать) и `log_mask.tsv` (то же для строк лога и ошибок) — одни на все реализации.

### 8.3. Привязка и пустое значение

Пустое или отсутствующее `*_secret` в PUT значит «оставь прежний» — оператор меняет имя камеры, не перепечатывая пароль. Но если в той же правке сменился адрес, к которому пароль привязан (`bound_to: [source]`), прежний пароль к новому адресу не переносится: это был пароль **той** камеры. Отказ: «source changed: cred_secret must be given anew». Присланная обратно маска `***` — тоже отказ: отсутствие поля и его маска — разные вещи.

### 8.4. Смена ключа

Кольцо хранит текущий и прежние ключи; конверт называет свой `kid`. Новый файл кольца сначала доставляют держателям, прежние ключи сохраняют; после перезапуска держателей консоль и `seal` перезапечатывают строки с CAS — прикладная `revision` не растёт. Прежние ключи нужны и отпечаткам живых заявок: повтор проверяется тем ключом, которым подписан сохранённый отпечаток; ноль конвертов в `status` не разрешает удалить ключ. Обслуживание ограничено: один оператор, обычные записи секретов остановлены на время ротации; `rotate` обслуживает последовательность имён `kN`, другие допустимые kid читаются, но автоматическая ротация их отвергается.

### 8.5. Отказы и пределы

Незаданный ключ и нечитаемый файл — разные состояния. Первый режим явно разрешён для разработки (громкое сообщение при старте, пустая память заявок): POST с непустым секретом отказывается до создания заявки, обычное чтение и правка сохраняются. Маска у разных секретов одинакова, поэтому маскированное тело не может различать повторы: POST с секретом требует кольцо и HMAC исходного запроса. Нечитаемый файл (включая пустой или неверный) даёт 503 любому POST/PUT единицы — кольцо нужно и для HMAC памяти повторов, — и не разрешает сохранить открытое значение. Воркер без нужного ключа не запускает единицу и сообщает причину без пароля. Ошибка ключа не вводит собственный алгоритм памяти повторов: действуют владение заявкой и правила 5xx из раздела 4.

## 9. Объекты, события, ресурс, просьбы

### 9.1. Две половины хранения

Строки маленькие и дорогие: каждая — запись в реплицированный журнал с версией. Пульс раз в десять секунд от каждого воркера, события камер, снимки, тела изображений — это **объекты**: большое или частое, что пишет один и никто не ищет по ключу, появляется целиком или никак. Объекты лежат файлами на сервере писателя; у каждого каталога писатель один; читают их через дверь ресурса этого сервера.

Правило границы: если следующий писатель объекта может оказаться на другом сервере, объект — строка хранилища `objects/<ключ>`, создаваемая один раз; иначе — файл. Метка просьбы начинается держателем и может быть закончена жнецом с другого сервера — она строка. Пульс пишет только его воркер — файл.

```
строки                                       объекты
маленькие, с версией, ищут по ключу          большие или частые, целиком или никак, по имени писателя
реплицированы на все серверы                 файл на сервере писателя; копия — только у зеркала
testsub/counters/c1                          testsub/heartbeats/w-1   пульс
testsub/placement/c1                         testsub/snapshot/w-1     снимок (раздел 11)
objects/testsub/commands/<rid>  ← строка!    testsub/blobs/sha256-…   тело (раздел 11)
                                             events/testsub/c1/e3/20261014T100000Z.events.jsonl
```

### 9.2. Событие катится по часам

Воркер камеры замечает потерю потока: `observe(kind: "stream.lost", …)`. Платформа дописывает строку JSON в файл `events/cam/7/e3/20261014T100000Z.events.jsonl`. В `id` строковые компоненты кодируются hex UTF-8, а номер выделяется экземпляром один раз: дефисы в именах не создают ложных дублей. Три решения в пути:

- **Эпоха в пути** (`e3`): данные старой попытки не смешаются с новыми; читатель узнает их по `epoch_is: fenced`.
- **Файл по `t`**, десятиминутными корзинами (бакетами): бакет закрывается, когда прошло его время, а не когда подсистема что-то сделала — поэтому ресурс знает, какие файлы можно зеркалировать и убирать.
- **`of` ставит платформа**: единица, про которую строка, берётся из `about` манифеста; подсистема своё `of` сказать не может — только два дерева платформы, отметки консоли и журнал, пишут про единицы сами.

Класс строки — тревога или наблюдение — объявляется писателем: тревога идёт в отдельное дерево `cam.alarms/…`, с `fsync` до корня, живёт три года; наблюдение — год, без `fsync`. Повторы одного вида гасятся подавлением из манифеста: первая строка окна пишется как есть, остальные считаются, по закрытии окна — одна строка с `repeats`, `since`, `until`. Журнал — дерево `audit`.

### 9.3. Индекс ничего не хранит

Отдельной базы событий нет: индекс — кэш над деревом файлов, и правильность ответа от кэша не зависит. Запрос «события камеры 7 за час» приходит в консоль; у консоли индекса нет — она спрашивает каждый живой ресурс, тот читает своё дерево и копии зеркала, отвечает строками с `epoch_is`, консоль сливает ответы, убирает дубли копий по `id` и говорит, кто не ответил (`incomplete`). Кандидатные файлы считаются по именам из окна времени, читаются с места, где закончили прошлый раз, и живут в ограниченном кэше, который можно выбросить в любой момент без потери правильности. Состояние индекса всегда `live`: нечего догонять.

`GET /events/wait` ускоряет следующий проход (какие потоки могли измениться), но не приносит события и не гарантирует доставку подсказок — клиент всё равно перечитывает данные. `complete` не означает, что `limit` ничего не отсёк (`truncated`) или что в открытом файле не было порванного хвоста (`partial`); консоль тоже обрезает объединённый список до limit, и её `truncated` складывает локальные пропуски и пропуски общей обрезки — точного числа потерянных событий этот счётчик не обещает.

### 9.4. Ресурс просит освободить место

Диск заполнен выше 85 %. Ресурс не удаляет чужие данные — он **просит**: пишет каждому манифесту с `requests: {free: true}` строку `<sub>/requests/free-<сервер>-<том> {free, volume, server, at}`, где `free` — байты до нижней отметки. (Имя тома в этом профиле — ASCII-буквы, цифры и `_`, длина 1–64, без дефиса: разделение пары по последнему дефису однозначно.) Ресурс меняет и снимает только строку со своими `server`/`volume` и прочитанной версией. Подсистема, которая умеет освобождать (рекордер — кольцо архива), говорит в пульсе `freeing: {<том>: байты}`, и ресурс вычитает из нужды ещё не отражённое в измерении; уже освободившиеся и измеренные байты второй раз не вычитаются. Единственное, что ресурс убирает сам, — бакеты событий старше срока подсистемы (`<sub>/retention`, год по умолчанию; тревоги — три) и отметки консоли не раньше самого долгого дерева. Срок — на подсистему, не на единицу.

### 9.5. Просьба и её метка

Просьбы — единственный способ попросить единицу сделать что-то сверх её строки. Оператор просит счётчик `c1` прибавить пять. Консоль пишет строку `testsub/requests/<rid>` созданием-однажды, с `valid_until` через 30 с. Держатель `c1` на своём взгляде видит строку, **сначала** создаёт метку `objects/testsub/commands/<rid>` созданием-однажды — «начал я, экземпляр такой-то, слот такой-то» — и только потом зовёт действие. Ответ пишется в метку: `performed`, `refused` с причиной, или `unknown`, если за десять секунд ответа нет. Второй держатель той же единицы метку создать не сможет — просьба не исполнится дважды. «Не больше одного раза» без транзакций — это метка, созданная один раз до вызова, и человек, решающий, что «возможно, ни разу» лучше, чем «возможно, дважды».

Строку снимает консоль, подтвердив метку, после задержки `settle` от первого наблюдения исхода; `fetched` подсказывает перечитать метку, но его исчезновение из пульса исход не отменяет. Строку, которую никто не начал до срока плюс минута, закрывает жнец консоли: метка `expired` созданием-однажды, после `settle` строка удаляется. Из четырёх исходов `unknown` должен быть нулём на здоровом кластере, и он не превращается в повтор: решает человек. Метка может остаться после обрыва между её созданием и вызовом: действие не произошло, но автоматический повтор всё равно запрещён. Начавший держатель может заменить `unknown` своим поздним ответом; жнец такой ответ не затирает — он закрывает чужую метку только по прочитанному индексу. После законной уборки метки по `kept` память о старом rid исчезает, и клиент не переиспользует его.

У дозаписи архива — исключение: детерминированный ключ и результат по данным, `fetched` без метки; правило единственного вызова к ней не применяется.

## 10. Консоль

Консоль — единственное место, где платформа и подсистема встречаются перед человеком, и единственное, где легче всего нарушить границу («добавим в консоль вкладку с архивом»). Поэтому она собрана из трёх частей с разными хозяевами:

- **Процесс консоли** — платформа: читает каталог манифестов и отвечает дверями, одинаковыми для счётчиков и камер; слова для человека берёт из `display` манифеста, не читая их смысла.
- **Модуль консоли** — платформа, один файл `console.js` у всех реализаций байт в байт: знает только слова манифеста и платформенные двери; у него закрытый список того, что он может позвать.
- **Оболочка** — подсистема: страница `<sub>.shell.html`, которая монтирует модуль и добавляет свои вкладки и карточки вызовами библиотеки, не хуками; за байтами потока и архива идёт к держателю единицы по двери из `/where`, мимо консоли.

### 10.1. Три строки страницы

```html
<link rel="stylesheet" href="/platform/console.css?v=1">
<div id="app"></div>
<script src="/platform/console.js?v=1"></script>
<script>PlatformConsole.mount(document.getElementById("app"), {lang: "ru"})</script>
```

Это вся платформенная страница и начало любой оболочки. Дальше модуль делает всё сам: спрашивает `/session`, `/manifest`, `/mounts`, строки единиц, `/servers`, `/unplaceable`, `/drain`, `/schema`, домен, `/metrics`; рисует рейку разделов, дерево, карточку, окно входа; опрашивает каждые пять секунд. Оболочка `cam.shell.html` добавляет после `mount` вкладку «Поток» (`addTab`), узлы дерева (`addTreeNodes`), редактор поля (`addFieldEditor`); для байтов зовёт `C.where(ref)`, получает `door: {url, token, expires, routes}` и идёт к держателю. Версия модуля — число в `?v=`; старая версия не отдаётся (`404 no such version`): совместимости назад нет, оболочка и модуль одной версии ставятся вместе.

### 10.2. Сторожевая спрашивает в порядке

Консоль не выдаёт личности: человека удостоверяет домен, консоль получает токен (`Authorization: Bearer` или кука `w2c_token`), спрашивает у домена, кто это и что ему дано, и перед **каждой** дверью решает, достаточно ли гранта — на единицу, на метки или на весь кластер. Порядок «сначала путь, потом тело» не случаен: что дверь требует, известно до чтения тела, и тело лишнего не читается. Пример: `PUT /cameras/7` — путь говорит «строка единицы 7», дверь требует `admin` (или ниже, если `rights.routes` манифеста понизила); домен отвечает «Иванов, edit на unit:cam/7, view на *»; `admin` на cam/7 нет — `403 {detail: "Иванов may not admin cam/7"}`, журнал `access.denied`, тело не читалось. Если гранта хватило — тело, и ещё раз по телу: `rights.unit_of`, `reach`, `names` могут добавить единицы, на которые тоже нужен грант.

Пока достоверно нет ни ключей, ни следов домена, консоль **открыта** — но только для своей машины: вне петли — 403 «this cluster is in no domain … loopback». `X-User` в запросе не читается никогда: сторожевая стирает его и вписывает доказанное имя. Ключи были, а проверить нечем — консоль закрыта (503), не открыта: потеря доверия не отпирает дверь.

### 10.3. Слова, а не логика

`display` манифеста — слова и один флаг: `unit: камера`, `units: камеры`, `fields: {source: Адрес}`, `options: {mode: {plain: Обычный}}`, `form: […]`, `kinds: {stream.lost: Поток потерян}`, `tree: {group_by: host, group_title: Устройства}`. Загрузчик проверяет, что названные поля — поля строки; модуль подставляет слова в свои пустые места; платформа смысла слов не читает. Что не названо — показывается именем поля и сырым видом; чего модулю не хватает для любой подсистемы — чинится в модуле, а не словом в манифесте. `servers.show` — какие строки таблицы показать в карточке сервера; `servers.status` — какие значения из пульса воркера положить в строку сервера как есть; `console.running` — какой ряд метрик считать «работает».

### 10.4. Что означает прочитанная картина

`/servers` соединяет пульсы, слоты и результат контроллера — они могли измениться между чтениями. `live` означает, что консоль недавно видела изменение пульса, — не обещание, что процесс жив в момент следующего запроса. `/where` при переезде может устареть; операцию разрешает держатель после проверки своей эпохи и аренды. Ошибка чтения не означает пустой кластер. Модуль получает гранты через `/session` и использует `may` для доступности кнопок, но сервер повторяет проверку независимо от кнопок; в закрытой сессии неизвестные гранты не дают разрешения. Два одинаковых на вид нажатия могут означать два действия — у каждого свой ключ идемпотентности; повтор потерянного POST сохраняет прежний ключ и тело только там, где дверь хранит результат, а PUT без такой памяти сначала требует выяснить исход чтением.

## 11. Схема, дренаж, снимки, пределы, тела

Четыре темы объединяет одно: они про **форму, а не про механизм**. Потолки в платформе не растут под задачу; задача меняет форму.

### 11.1. Номер схемы поднимают последним

Новая сборка понимает раскладку хранилища №2, старая — №1. Платформа не хранит двух толкований одной строки. Порядок: новые процессы стартуют на старой раскладке (новая сборка читает старую — всегда можно); оператор смотрит `GET /schema`: `understood`, `builds`, `can_raise_to` — минимум схемы самой консоли и наблюдённых живых процессов. Этого недостаточно для молчащей старой машины: оператор закрывает старты старых сборок на время обслуживания и подтверждает остановку их писателей. Затем совместимая консоль выполняет `PUT /schema?version=2`. С этого момента процессы старой сборки не стартуют: «store is at schema 2; this build understands 1» — крах при старте, видимый в журнале супервизора, а не тихая порча. Назад номер не идёт; поднимать с живым старым процессом нельзя: «still running: w-3 — at schema 1».

### 11.2. Дренаж показывает наблюдённый остаток

`safe` требует отсутствия единиц и несброшенных записей (`pending_writes`); неизвестный или старый пульс делает состояние небезопасным; `would_strand` называет единицы, которым некуда уехать. Перед выключением оператор прекращает новые назначения и ждёт начатые операции: отдельные чтения не блокируют новые записи. Дренаж не выключает сервер и не создаёт воркеров — двери лишь записывают желание, которое контроллер прочтёт на проходе.

### 11.3. Снимок — по шарду на воркера

Снимок большого кластера одним объектом рос к потолку объекта — и правильной мыслью было не поднять потолок, а спросить, почему один объект описывает весь кластер, когда меняется он по одному воркеру. Контроллер после каждого прохода пишет объекты `testsub/snapshot/w-1`, `…/w-2`, `…/unplaced`: в каждом — строки единиц этого воркера, только поля из `snapshot:` манифеста плюс `id`, `revision`, `worker`, `server`, адреса с маской. Секретов и тел в снимке нет по построению: они исключены по умолчанию, а манифест, который называет их в `snapshot:`, не грузится. Шард воркера, которого больше нет, переписывается пустым — не удаляется; кластер без единиц пишет пустой `unplaced`: «опубликовано, что никого нет» отличимо от «не публиковали». Читатель (консоль на `/metrics`) берёт возраст самого старого наблюдённого шарда по своим монотонным часам; неудачное чтение шард свежим не делает. Шарды обновляются отдельно: это конфигурация для наблюдения, а не резервная копия одного момента; для действия потребитель сверяет `revision`. Перед публикацией проверяется размер шарда: он должен помещаться и в хранилище, и в 64 МиБ двери чтения; при отказе прежний шард остаётся — увеличение хранилища не снимает предел двери.

### 11.4. Тело — дайджест в строке

Поле `type: blob` держит в строке `sha256-<hex>` и ничего больше; байты кладут отдельной дверью `PUT /<rows>/<id>/<поле>`: объект пишется **первым** и прочно, строка с дайджестом — второй. Дайджест в имени объекта — проверка при чтении: подменённые байты не пройдут. Тела зеркалируются соседям всегда, независимо от ручки зеркала событий. Уборка — дело консоли: её фоновая часть отмечает неиспользуемые дайджесты и выдерживает 300 секунд, а удаление выполняется в окне обслуживания (писатели и копирование остановлены, начатые операции завершены, ссылки перечитаны) — повторная загрузка тех же байтов может сохранить индекс объекта, поэтому один CAS списка и проверка возраста от новой ссылки после обхода не защищают; окно делает эту гонку недопустимой без ещё одного протокола блокировок. Удаление оставляет надгробие: его хранят не меньше семи дней и до подтверждения всех известных соседей; отключённый сосед подтвердившим не считается; после частичного сбоя удалений окно остаётся закрытым до восстановления надгробий.

## 12. Платформа на железе: коробка и кластер

### 12.1. Один набор юнитов на каждом сервере

Группа без оркестратора значит: на каждом сервере стоит один и тот же набор юнитов, а всё остальное решают строки.

```
configstore.service           хранилище, голос группы             user configstore   без групп воркеров; сокеты в setgid-каталогах ролей
w2c-resource.service          ресурс сервера                      user w2c           w2c-store w2c-events
w2c-controller@<sub>.service  контроллер подсистемы, по одному    user w2c           w2c-store w2c-events (+ роль)
                              на манифест
w2c-console.service           консоль                             user w2c           w2c-store w2c-events w2c-secrets
w2c-domain.service            процесс domain (у держателя)        user w2c
w2c-domainagent.service       агент члена, один на кластер        user w2c
w2c-domainconsole.service     консоль домена (у держателя)        user w2c
<dep>-<sub>worker.service     воркер подсистемы                   user подсистемы    роль, w2c-store, w2c-events, w2c-secrets
<dep>-<sub>worker-spare@N     запасной: тот же юнит без имени     user подсистемы    то же
w2c-spares.timer/.service     скрипт запасных, раз в минуту       user w2c-spares    без групп
```

Контроллеров — по одному на манифест на **каждом** сервере, лидера нет. Воркеров — по одному на роль на сервер плюс запасные. Юнит даёт процессу имя (`WORKER_NAME=w-%l-1`), сокет роли (`PLATFORM_STORE=configstore:///run/configstore/<роль>.sock`) и группу этого сокета; настройки сервера (`SERVER_NAME`, `LABELS`) — из файла окружения, и строка файла задаёт имя, только если юнит его не задал; `SPARE_FOR` из файла окружения не берётся никогда — это слово скрипта запасных. «Платформа от `w2c`»: процесс платформы никогда не в группах подсистемы. Имя от юнита: процесс просит только своё имя.

### 12.2. Хранилище без оркестратора

На каждом сервере — демон хранилища, голос группы raft. Устойчивый состав — один, три или пять; два и четыре допускаются лишь как переходный состав при последовательной пересборке: демон отказывает вступлению, которое делает группу чётной (без `-force`, нужного для переходной чётности) или больше объявленной (всегда: размер меняют флагом `-group-size` на всех демонах, не вступлением; растить 1 → 3 можно только через 2 таким образом). Процессы ходят только к демону своего сервера через сокет своей роли; между серверами ходят демоны — по mTLS с сертификатами центра кластера.

Нет лидера пять секунд — дверь отвечает `503 unavailable`, и воркеры живут на последнем назначении по аренде. **Дверь без голоса** — демон на сервере без права голоса: тот же файл прав, те же сокеты, пересылает к лидеру; живёт на серверах, где есть процессы, но нет места в группе (четвёртый сервер при группе из трёх).

Потеря большинства требует оператора: сначала отсечь всю прежнюю группу и сохранить исходные данные, затем выполнить один `recover` на остановленном демоне с **полом эпох** — новый пол выше достоверной границы всех ранее выданных эпох, чтобы номер, уже бывший в данных, не вышел второй раз. Если потерянный хвост не позволяет установить границу, безопасное восстановление не обещано; `force` это условие не снимает.

### 12.3. Порядок запуска и готовность

`After=configstore.service` — порядок запуска systemd, но хранилище в этот момент ещё может искать лидера: ресурс, контроллер, консоль и воркер ждут достоверных данных до своих первых действий. Неверный манифест останавливает процесс с кодом 2; временная недоступность не превращается в пустую установку. Возвращающийся демон читает `member.json` и продолжает членство, а не вступает заново.

Установщик заранее проверяет доступные входы, но ошибка диска на позднем шаге может оставить часть новых файлов: исход фиксируется с фазой и путём, новые службы не запускаются, повтор продолжает после исправления причины. Атомарная замена каталога кода не делает всю установку одной транзакцией.

Запасные запускает один выбранный механизм: он проверяет числа бюджета до деления и учитывает ещё не подтвердившиеся старты, чтобы два прохода не потратили одну и ту же память; консоль с устаревшим результатом не даёт основания запускать новые процессы.

### 12.4. Отказ сервера

Сервер выдернули из розетки. Единицы уехали по двум молчаниям (раздел 5.4); у соседей доступны подтверждённые зеркальные копии; открытый бакет и ещё не скопированные закрытые могут быть потеряны; данные подсистемы на томе сервера недоступны, пока сервер не вернётся, и не перестраиваются; хранилище потеряло один голос из трёх. Сервер вернулся — его ресурс тянет свои бакеты назад, его воркеры берут свободные имена, но без объявленного `home` единицы сами обратно не едут: контроллер не перебалансирует по своей воле. Единственное, что требует человека, — потеря большинства хранилища (`recover` с полом эпох).

## 13. Домен: уровень выше кластера

Разделы 2–12 закончились там, где всё работает. Контроллер кластера — единственный писатель строк размещения, воркеры переживают смерть сервера, кластер знает, где каждая его единица, — в одном raft своего хранилища, строго согласованно. Как только кластеров два, ровно три вещи перестают быть известными:

- **Где единица.** Спросите кластер о единице, которой у него нет, — он скажет «нет». И это неверное слово: он не может отличить «не у меня» от «нигде».
- **В какой кластер ставить новую.** Ни один кластер не знает, до чего дотягиваются другие.
- **Полон ли ответ.** Сказать, что ответ частичный, может только тот, кто знает, сколько кластеров существует.

Домен добавляет уровень выше и не повторяет уровень ниже. Кластеры-**члены** полностью независимы: у каждого своё хранилище со своим raft, свои объекты, свои процессы, и между ними ничего не реплицируется. Службы домена работают на одном члене — **держателе**; это роль, а не вид кластера: держателем бывает серверная, облачный регион или камера на стене. Процесс `domain` держателя — единственный писатель строк держателя: другой писатель был бы вторым мнением о домене.

### 13.1. Домен читает членов, но к ним не ходит

Держатель не опрашивает кластеры: **агент** каждого члена сам оставляет у держателя отчёт — копию того, что кластер публикует (пульсы воркеров и шарды снимка каждой подсистемы из раздела 11.3), и уносит домой ответ: набор ключей, гранты, правки, топологию. Камера на LTE не должна отсылать весь кластер каждые пять секунд, поэтому по проводу идёт изменение против названной держателем базы, а у держателя копия лежит целой (раздел 15). Молчащий член не стоит держателю ничего: у домена нет соединения, которого надо дождаться, — есть метка, которая стареет.

### 13.2. Вид домена: сводка, которая знает, чего не знает

Держатель раз в три секунды сводит копии членов в **вид домена**: для каждой подсистемы с `domain.ref` — единицы с членом, воркером, фазой и свежестью. Единица ищется по имени домена — значению поля `domain.ref` (у `testsub` это `name`): номер единицы принадлежит кластеру, и «счётчик 1» есть в каждом члене, а вот `c1` — один на домен.

Главное в виде — не список, а то, чем он помечен. Два члена, у каждого счётчик: `c1` в `m1`, `c2` в `m2` — вид полный, `complete: true`. Пусть `m2` замолчал: его метка у держателя не менялась дольше 45 секунд. Тогда `m2` — `silent`, его единицы остаются в виде со словом `silent`, а `complete` — `false`. «`c2` не найден» при таком виде — факт о сети, а не о домене: короткий список, показанный как полный, — то, как расследование пропавшей камеры закрывается с неверным ответом. Если один и тот же `ref` заявляют два члена, вид не выбирает победителя: оба названы в `contested`, ни одна их единица не попадает в список. Свежесть считается по монотонным часам держателя — «менялось на глазах держателя», как пульсы в разделе 5.2; после перезапуска держателя член сначала `unseen`, и это тоже неполнота, а не смерть.

Эпохе домен не нужен: эпоха (раздел 4.5) должна быть монотонной только для одной единицы, а единица всю жизнь живёт в одном кластере — воркер не пересекает его границу. Граница эпохи — кластер, и это правильная граница.

### 13.3. Теневой режим: домен, который сначала только смотрит

Домен, который в первый же день пишет в три кластера по модели, которую никто не сверил с реальностью, — это то, как появляются единицы, которые никто не размещал. Поэтому первый режим домена — теневой: держатель сравнивает назначения домена (раздел 16.3) с тем, что воркеры членов сообщают в пульсах, и печатает разницу шести видов: `lagging` (воркер отстаёт, но движется — норма), `stalled` (отстаёт и стоит дольше 60 с — отказ), `orphaned` (назначена, а никто не ведёт — отказ), `unmanaged` (кластер ведёт то, чего домен не назначал — измерение), `conflict` (единицу ведут двое — отказ), `stale_epoch` (заявка под старой эпохой — отказ). Заявляет единицу только живой пульс: последний пульс умершего воркера устаревает и перестаёт заявлять сам, иначе зомби вечно держал бы конфликт. Число, ради которого режим существует, — `unmanaged == 0`: всё, что работает и не описано моделью, — дыра в модели. Критерий выхода записан в норме: ни одной `unmanaged`, ни одного отказа, три чистых прохода подряд.

## 14. Доверие без связи: корень, набор, отзыв

Прежде чем член принесёт первую копию, у домена должно быть то, чему член верит без связи: кто подписывает токены, какие ключи отозваны, к какому ключу запечатывать секреты. Над доменом никого нет: корень самоподписан, и перевыпустить его сверху некому.

### 14.1. Корень лежит у оператора

Корень — пара Ed25519, одна на всю жизнь домена. Его закрытая половина лежит в файле восстановления у оператора и больше нигде: ни на держателе, ни в резервной копии, ни у консоли. Корень подписывает одну вещь — набор ключей `domain/keys`; всё, что держатель подписывает каждую минуту (токены, записи срока), подписывают ключи держателя, названные в наборе. Почему не держать корень на держателе? Держателем бывает камера, а камеру можно унести: если корень уходит вместе с ней, вор становится доменом; если корня на камере нет, вор уносит только ключи держателя — их отзывает новый набор, а подписать его вор не может. Цена — корень нужен руками: при установке, плановой смене ключа токенов, смене ключа приёма книг и переносе после кражи. Это редкие события, и каждое и так требует оператора.

### 14.2. Набор: то, чему член верит без связи

Набор — подписанный корнем документ: ключи токенов держателя (`keys`, текущий `current`, у прежних — срок `until`), ключи выпускающего (`issuing`, отозванные — `revoked_issuing`), отозванные ключи членов и открытый ключ приёма книг `book_seal`. Член держит ровно один набор и принимает новый, только если набор подписан корнем, **закреплённым заранее** (при установке на держателе или при приёме члена оператором), содержит `book_seal` и его `rev` больше того, что член держит. Первого набора «на доверии» нет: если корень закрепляет тот, кто первым ответил агенту, первым может ответить и чужой. Равный `rev` — «держу», а не «перепишу»: иначе повтор старого ответа переписывал бы набор.

Ревизия набора — `max(прежняя + 1, стенные секунды подписанта)`. Плюс единица не дала бы ревизии расти правильно: член, выключенный неделю назад, мог взять набор, которого не видел никто из достижимых сейчас, и номер «наибольший из видимых плюс один» он отверг бы как старый. Секунды смены больше любого номера, подписанного раньше.

### 14.3. Отзыв — задача сроков, и окно у него названо

Член проверяет токен сам, по своему набору, своей копии `domain/revoked` и своим стенным часам; держатель в проверке не участвует. Поэтому отзыв доходит не мгновенно, и честная норма называет окно числом:

- **отозванный токен** принимается, пока его `jti` не дошёл до проверяющего, и не дольше `exp + 60` секунд по часам проверяющего; без связи это весь срок жизни токена плюс минута (самый долгий вид — 600 с, значит окно — 660 с);
- **прежний ключ токенов** после плановой смены годен ещё час (`until`): токены, выданные до смены, доживают;
- **украденный текущий ключ** не ограничен сроком: вор выпускает новые токены, и член без связи принимает их, пока не возьмёт набор без этого ключа. Это предел, и норма говорит о нём прямо, а не обещает меньше.

Список отзыва сам себя чистит: запись `jti:exp` не нужна после `exp + 60`, и писатель снимает её — список не длиннее числа живых токенов.

### 14.4. Ключ приёма книг и конверт `x25519:v1`

Секреты во вкладах членов в книги (раздел 16.2) едут к держателю по чужим дорогам — через ретранслятор, в отчёте, в копии, — и кольцо кластера им не подходит: кольцо держателя никуда не едет. Поэтому у домена свой ключ приёма книг X25519: зерно лежит у держателя (`domain/book-seal`), открытая половина — в наборе. Член запечатывает секрет к открытой половине до подписи отчёта; открыть конверт может только держатель и только при сборке книги. Конверт связан с местом, откуда пришёл секрет: его AAD — тройка «член, строка-источник, элемент» и путь секрета внутри элемента, как у кольца кластера (раздел 8.1); переставленный в другой вклад, строку или поле секрет не откроется, а подмену не отличить от чужого ключа — AEAD говорит только «не открылось».

### 14.5. Смена после кражи и член, который её проспал

Держатель украден. Оператор достаёт файл восстановления, и корень подписывает новый набор: ключи держателя — только новые, без перекрытия; прежние выпускающие и ключ члена украденного держателя отозваны; ключ приёма книг — новый. Порядок важен: сначала строка нового ключа приёма книг, потом набор — иначе держатель получил бы конверт к ключу, которым не может открыть. Член, который был без связи, ничего этого не знает: пока он держит прежний набор, он принимает токены вора и запечатывает вклады к прежнему ключу. Вернувшись, он берёт новый набор — его ревизия больше любой прежней, пока часы держателей расходятся не больше чем на 60 с (это предпосылка нормы), — и с этой минуты токены прежних ключей для него «ключ не из набора», а его вклады `missing`, пока он не пришлёт отчёт, запечатанный к новому ключу.

Холодный старт идёт в строгом порядке: хранилище каждого кластера поднимается само → установка на держателе (файл восстановления, ключи держателя, ключ приёма книг, набор rev 1, закреплённый корень) → старт процесса `domain` → оператор принимает членов, и агенты уносят набор. Пока набор не дошёл, каждый кластер работает сам: в этом весь проект. Процесс `domain` домена не основывает: домен основывает установка, один раз.

## 15. Отчёты: как держатель получает копию каждого члена

### 15.1. Приём — с двух сторон

Принять кластер — значит, чтобы каждая сторона знала ключ другой, и знала не со слов первого, кто ответил. Приём — две команды оператора в любом порядке: `join` на члене закрепляет корень (оператор вводит открытый ключ, который напечатала установка, и сверяет отпечаток), `POST /domain/members` на держателе вносит ключ члена (консоль показывает стучащегося с отпечатком его ключа, и человек сверяет его с тем, что напечатал агент). Агент отчитывается и до приёма — иначе держателю нечего показать в списке стучащихся, — но набор ключей не берёт, пока корень не закреплён. Член, принятый с одной стороны, — ещё не член.

### 15.2. Поколения: держатель никогда не читает половину

Принятая копия члена хранится целым объектом поколения `domain/members/<член>/reports/<rev>`; рядом — байты отчёта, как они пришли, и метка `reported`. Номер `rev` выдаёт держатель, а не член. Порядок записи — главное в уроке: сначала объект поколения, затем байты отчёта, затем одной записью метка. Метка — граница принятого: если держатель упал между объектом и меткой, объект выше метки — ничей, его никто не читает, а следующий приём пишет поверх. Читатель берёт номер из метки и читает только этот объект, сверив `sha256`. Чтение между любыми двумя записями даёт целое старое, целое новое или «не знаю» — и никогда смесь.

### 15.3. По проводу — изменение, у держателя — целое

Агент шлёт изменение против поколения, которое держатель назвал в прошлом ответе (`base`): изменённые объекты и исчезнувшие ключи. Держатель применяет его к своему целому и пишет новое целое каноном JCS. Если не изменилось ничего, кроме `ts` пульсов, агент шлёт пустое изменение: держатель ничего не пишет, а метку освежает не чаще раза в 22,5 секунды — ровно эту «смену метки» и видит вид (раздел 13.2). Не знает держатель базы — отвечает 409 `rebase`, и агент сразу шлёт целое, один раз; других поводов слать целое нет, иначе каждый член писал бы объект раз в полминуты без единого изменения. Тот же `sent_at` с теми же байтами — повтор: держатель ничего не пишет и отвечает тем, что знает сейчас; тот же `sent_at` с другими байтами — 409: у одного момента члена одно тело. Часы члена, шагнувшие назад, на той же дороге принимаются сразу: порядок задаёт дорога.

Каждый запрос агента подписан ключом члена: метод, путь, миллисекунды и хэш тела; окно — 300 секунд в обе стороны по часам проверяющего. Кэша повторов нет, и норма говорит это прямо: те же байты в окне примутся снова — безвредно, потому что повтор отчёта держатель узнаёт по `sent_at` и хэшу. Ответ на отчёт — то, что агент уносит домой: набор ключей, список отзыва, список членов и всё, что другим частям домена нужно донести до члена (запись срока, назначения, правки, топология, резервная копия, общий документ); секретное запечатано члену конвертом `m1` к тому же ключу члена, переведённому в X25519, — отдельного ключа запечатывания нет.

Список членов в ответе — только отставшему: член называет номер списка, который держит, и держатель кладёт список, только когда номер другой. На трёхстах членах иначе это были бы 90 КБ в каждом ответе — больше пяти мегабайт в секунду того, что член уже держит.

### 15.4. Ретранслятор, топология, две дороги

Член за NAT или в закрытой сети ходит к держателю через **ретранслятор** — другого члена, который несёт его отчёты пакетом (его сторона — раздел 17). Держатель проверяет подпись ретранслятора и спрашивает **топологию** — запись оператора `via`: какой член ходит через какой ретранслятор. Её отказы — правила сети: член не ходит через себя; ретранслятор не ходит через другой — между членом и держателем не больше одного; держатель ничей не ретранслятор и сам ни через кого не ходит. Топология не выбирает дорогу агенту (агент идёт туда, куда смотрит его окружение) — она говорит держателю и ретранслятору, кого через кого принимать: пришедший не через тот ретранслятор получает отказ. Подпись самого члена через ретранслятор не переносится: держатель верит ретранслятору, и норма называет это пределом — принятый ретранслятор мог бы подменить отчёт члена за ним; перенос подписи — отложенное решение.

Член за ретранслятором может однажды дотянуться и прямо, и тогда его отчёты придут двумя дорогами в любом порядке. На одной дороге порядок задаёт сама дорога: последнее принятое — новее. Между двумя дорогами сравнивают `sent_at`: часы у члена одни на обе дороги. Тело с другой дороги, которое старше метки, держатель не берёт, пока член слышен; если прежняя дорога молчит 15 секунд и дольше — берёт и его. У каждой дороги своя база дельт: ответ называет `rev` метки только той дороге, которой метка пришла.

### 15.5. Отпечатки центра в записи члена

У каждого кластера свой удостоверяющий центр (раздел 7.3), и кластеру надо знать, каким центрам верить у соседей. Член публикует отпечатки своего центра (`tls_ca`) в подписанном отчёте, держатель пишет их в запись члена (`ca`) — так отпечаток привязан к ключу члена подписью. Отпечатков не больше двух: нынешний и следующий на время смены центра. Публикация без отпечатков запись не чистит — умолчание не ослабляет; снять отпечатки может только администратор. Клиент, который звонит чужому кластеру, проверяет сервер по этим отпечаткам (раздел 17.3).

## 16. Люди, книги, правки, токены

### 16.1. Люди и гранты: делегировать власть, не раздавая секрет

Человек входит у держателя — у процесса `domain`, где лежит хеш его пароля, — и получает короткий подписанный токен вида `person`: имя и срок, и больше ничего — ни ролей, ни прав, ни кластеров. Кластер проверяет подпись открытым ключом у себя, без сети: N кластеров с открытым ключом — ноль мест, откуда украсть пароль. Отказ входа один на всё — нет человека, он выключен, пароль неверный: 401 одними словами, а сверка идёт и с фиктивным хешем той же стоимости, чтобы время не выдало, есть ли имя. Неудачи считаются по адресу: после пяти за 15 минут — 429; блокировать имя нельзя — тогда любой выключил бы администратора, просто ошибаясь его паролем.

Что человеку можно в кластере, написано в строке грантов этого кластера: «кто, что, на что, до какого времени». Строку пишет процесс `domain` по правке через консоль домена, агент уносит её домой в ответе держателя, проверка — локальное чтение: отрезанный кластер продолжает пускать своих операторов, пока жив их токен. Отзыв асимметричен — устаревшая выдача видна сразу (человек жалуется), устаревший отзыв молчит, — поэтому у копии грантов есть срок: сутки от приёма; кластер, до которого отзыв не дошёл, сам перестаёт верить копии. Пределов два, и оба названы заранее: выданный токен живёт 15 минут плюс минута допуска часов; снятый грант у отрезанного кластера — до суток. Выключенный человек не теряет строк: держатель просто не возит их членам, и включение возвращает всё как было.

Сторожевая (раздел 10.2) спрашивает функцию `may`: можно ли этому человеку это действие с этой единицей. Порядок: аварийная сессия — да; выключен — нет; копия грантов старше суток — нет; `view` без единицы — любая действующая строка; иначе — строка с правом не ниже нужного и областью, которая покрывает единицу. Область — `*`, одна единица или метки; метки берутся с той единицы, о которой речь: право на камеры первого этажа покрывает их записи, а собственные метки записи говорят, где ей работать, а не кто её смотрит. Одна и та же функция стоит у процесса `domain`, у сторожевой консоли кластера и у консоли домена. У двери домена свои права — `domain/grants/domain`, а не гранты кластера держателя: администраторы домена — не администраторы этого кластера; последнего администратора снять нельзя.

**Аварийная учётка** — на случай «канал лежит, токен истёк, а оператор на площадке»: одна учётка на кластер, пароль ставит администратор домена, хеш едет с ответом агенту; проверяет консоль кластера и открывает сессию в своей памяти на 15 минут; каждая попытка — тревога в журнале, каждое действие сильнее чтения — тоже. **Удаление человека** трогает несколько строк (он сам и его гранты во всех кластерах), поэтому процесс сначала ставит метку `domain/deleting/<имя>`, потом снимает строки: обрыв посередине доводит сверка следующего прохода по метке — полуудалённый человек не остаётся.

### 16.2. Книги и индекс имён

Кластеру иногда нужно знать то, что знают другие: кто записывает камеру, которую видит этот, где её резерв. **Книга** собирается из строк, которые обычные воркеры членов пишут у себя под своими слотами; держатель только сводит их и раздаёт. Манифест объявляет, откуда книга берёт входы (`from`), какое поле их ключ (`key`), сколько вкладов на ключ (`pick: unique` — ровно один в домене, `all` — все) и кому вход адресован (`to`); код подсистемы правила выбора не пишет — оно объявлено, и платформа исполняет его одинаково для всех. Секрет во входе едет к держателю конвертом к ключу приёма книг (раздел 14.4), держатель открывает его только при сборке и запечатывает каждому получателю заново: ретранслятор и копия держат шифр.

Правило главы одной фразой: **чего нет из-за члена — тот в `missing`**. Член молчит — его записей нет, и он в `missing` со словом `silent`. Член ещё не подтвердился после перезапуска держателя — его записи есть, но и он в `missing`: ответ неполон, пока смена не увидена. Вход члена испорчен или секрет не открылся — весь его вклад снят, а он в `missing` с причиной. Слова причин — закрытый список, его сравнивает приёмка; читатель книги сам решает, годится ли ему неполная.

Запись видит только тот, кто назван в её `to` и принят в домен; получатель вне списка членов не получает ничего ни в каком виде — держатель называет его только в своём виде (`undelivered`), чтобы оператор нашёл опечатку. Конфликт `unique` — ключа в книге нет, и держатель называет его в `conflicts`. Подсистема может держать книгу, чьи элементы — тоже субъекты грантов (учётки шлюза); манифест объявляет это `domain.names`, и держатель ведёт **индекс имён**: какой член заявил какое имя. По индексу: человека не заводят под именем элемента; элементу не дают гранта шире объявленного; элемент с именем человека не доставляется никому. Если индекс неизвестен (кто-то молчит), создание человека и новый грант не для человека ждут (503), а удаление, отзыв и строки людей домена не ждут никогда.

### 16.3. Назначение и правка, которая ждёт выключенного члена

До сих пор домен только смотрел; теперь два действия. Запись `domain/placement/<sub>/<ref>` говорит, какой член исполняет единицу (`cluster`), кто ещё исполняет её копии (`copies`) и чей она источник (`origin`). Пишет её только оператор: назначение может опередить единицу — теневой отчёт через минуту назовёт её `orphaned`. Члену запись доходит в ответе держателя, но только если называет его: член не узнаёт, где живут чужие единицы, и ответ не растёт как члены × записи.

**Правка** единицы идёт через домен, но домен не пишет в члены: правка хранится у держателя и ждёт, пока агент члена заберёт её с ответом, — поэтому ответ 202, а не 200: «принято» — не «сделано». Тот же ключ — та же правка; тот же ключ с другим телом — 422; ждущих правок у члена не больше пятидесяти. Правка помнит ревизию единицы, которую домен видел в копии члена, когда её принял, и агент применяет её с `If-Match` этой ревизии: если единицу на члене тем временем поменяли руками, дверь члена отвечает 412, правка не применяется, а держателю уходит исход `conflict` — домен не затирает молча то, чего не видел, решает оператор. Две правки одной единицы не спорят: вторая ждёт ревизию после первой. Найти единицу — значит найти её в виде домена, поэтому отказы правки — отказы вида (раздел 13.2): нет в полном виде — 404; не нашли, пока кто-то молчит или `ref` спорный, — 503 с именами. Поле `*_secret` в правке домена — 400: пароль задают в собственном кластере единицы.

### 16.4. Токены воркеров: что написано в токене, решает домен

Воркеру одного кластера иногда нужно, чтобы его принял воркер другого: рекордер, который тянет поток камеры соседа; сценарий, который просит действия у камеры в другом здании. Получатель должен знать, что просьба законна, а спросить домен он не может — связи с держателем у него может не быть. Поэтому законность едет с просьбой — токеном, подписанным доменом. Ключей у воркера нет: он просит токен у местной двери агента своего кластера (раздел 17.2), агент подписывает просьбу ключом члена и несёт держателю; держатель выдаёт токен и запечатывает ответ члену конвертом `m1`.

Воркер даёт только `ref` — о какой единице речь; всё остальное подписант берёт из того, что знает домен. Область `placement` берёт запись назначения: заявитель должен стоять в её поле `caller`, а аудитория — исполнители из `target_fields`. Область `unit` берёт, кто владеет единицей и какая у владельца ближайшая дверь к домену. Область `scenario` берёт общий документ (раздел 18.3): включённые элементы с этой целью и этим триггером дают `acts`, а дорога по топологии даёт аудиторию. Чего домен не может подтвердить, того в токене нет: нечитаемое назначение — отказ, а не переход к другой области; пустая аудитория — отказ, а не токен «для всех». Каждый отказ выдачи — слово из закрытого списка: `not_granted`, `outside_scope`, `no_assignment`, `no_centre` и другие.

## 17. Агент и ретранслятор

Держа держателя (P/08), домену нужна вторая сторона — процесс `domainagent`, один на каждый кластер-член, в том числе у держателя: держатель — тоже член. Агент несёт отчёты держателю и ответ домой; строк держателя он не пишет — у своего члена он пишет копии того, что принёс, и исходы правок.

### 17.1. Агент члена

**Ключ члена** — зерно Ed25519 в `domain/member-key`; агент создаёт его при первом старте, печатает отпечаток и подписывает им каждый свой запрос (раздел 15.3). По проводу — изменение против `base`; на 409 `rebase` агент сразу шлёт целое, один раз.

**Дома агент пишет только при отличии**: ответ без новостей не стоит ни одной записи. Одно исключение — метки свежести (время копии грантов, время, когда член последний раз дотянулся до домена): их агент освежает не чаще раза в минуту и только ответом, который держатель собрал заново, — ответ из памяти ретранслятора их не двигает.

**Вклад в книгу живёт ровно со слотом**: воркер пишет вход под своим слотом и его стражем, агент несёт строку в отчёт, только пока слот держат, и перечитывает слот после строки — вход умершего воркера не переживает его и не попадает в книгу как факт. **Правку** агент применяет с `If-Match` той ревизии, которую видел домен (раздел 16.3), а исход — `performed`, `conflict`, `refused` — уносит держателю.

**Тревога не ждёт прохода**: член кладёт в отчёт страницу своих тревог — новейшие за сутки, не больше сотни; раз в секунду агент читает одну строку индекса, и появление новой тревоги собирает внеочередной отчёт, но не чаще раза в секунду. Член, у которого тревог больше страницы, так и говорит: шторм одной камеры не прячет единственный взлом у соседней.

**Агент в процессе.** На камере платформа — один процесс, и агент живёт в нём, без комплекта TLS своей роли: держателю агент доказывает себя подписью, а не сертификатом, а сервер держателя проверяет по отпечатку центра; местная дверь токенов в процессе становится вызовом с теми же телом, ответом и отказами. Права остаются по ролям: один процесс — не одна роль.

**Строка `domain/agent`** — то, что член говорит о себе дома, когда отчитаться не может: целое поколение больше 16 MiB — член не отчитывается и пишет об этом сюда; ключ члена не читается — сюда же число неподписанных запросов. Держатель увидит такого члена молчащим, а строка дома объяснит почему.

### 17.2. Местная дверь токенов: ключей у воркера нет

Ключ подписи — у подписанта держателя, ключ члена — у агента; воркер не получает ни того, ни другого. Он просит токен у агента своего кластера местной дверью, и агент знает, кто спрашивает, по личности соединения — сокету роли или сертификату роли; имени роли в теле запроса не верят. Агент подписывает просьбу ключом члена, несёт держателю и отдаёт полученный токен только тому соединению, которое спросило. Очереди ответов нет: не дождался — спроси снова. Токен живёт в памяти воркера и больше нигде.

### 17.3. Дороги, `domain/reached` и клиент, который знает, кому звонит

Дорога агента — его окружение: дверь держателя или дверь ретранслятора. Член за ретранслятором записывает, когда домен последний раз отвечал (`domain/reached`); ретранслятор добавляет к ответу возраст своего последнего разговора с держателем, и член вычитает его — так камера знает, насколько свеж её последний ответ.

Клиент, который звонит чужому кластеру по `https://`, знает, кому звонит. Он берёт отпечатки из записи этого члена (раздел 15.5) и проверяет сервер: в цепочке есть центр с таким отпечатком; лист подписан по пути к нему; сроки действуют; роль в SAN URI — роль двери, имя — хост адреса. IP вместо имени — отказ; отпечатка нет — отказ `foreign_ca`. Доверия «при первой встрече» нет: первый адрес держателя оператор даёт вместе с отпечатком. Этим же правилом — договором `peer` — звонят консоль кластера и процесс `domain`: одно место для всех.

### 17.4. Члены следуют за большим сроком

Никто не сообщает членам о переносе домена. Агент каждого члена на каждом проходе спрашивает консоли кластеров, у кого домен, проверяет каждую запись срока своим набором и идёт за наибольшим сроком. Назад он не идёт никогда: агент, всё ещё несущий через дверь старого держателя, не отменит перенос. Общий документ член берёт по тому же правилу «никогда назад»: сравнение `(term, rev)` идёт раньше любой загрузки, и `term` старше `rev` (раздел 18.3).

### 17.5. Ретранслятор — член, а не посредник

Ретранслятор — обычный член домена: его приняли, у него свой ключ и свой отчёт. Его агент открывает ещё одну дверь — для членов за ним (`RELAY=1`, порт 8446). Член за ретранслятором отчитывается в эту дверь так же, как отчитался бы держателю — той же публикацией, той же подписью; ретранслятор проверяет подпись ключом, который держатель сам ему назвал, и складывает отчёты членов в **пакет**. Ответы держателя для них он держит в памяти и отдаёт при следующем обращении члена; секретное в ответе запечатано члену, и ретранслятор его не откроет. Просьбу токена воркера он несёт держателю байт в байт и так же возвращает ответ. Если держатель не отвечает ретранслятору, тот не теряет отчётов: публикации возвращаются в память, если с тех пор не пришло новее; его собственный отчёт может не пройти, а ретрансляция продолжится. Отказы: член не через этот ретранслятор — 403; ответа для члена ещё нет — 503; пакет больше 64 MiB — 413, поэтому ретранслятор дробит пакеты.

## 18. Срок, перенос, общий документ, цена

Держатель — один кластер, иногда одна камера на стене: он умирает, его меняют, его уносят. Домен переживает смену держателя без единого сообщения членам.

### 18.1. Срок — эпоха уровнем выше

Воркер держит эпоху единицы, держатель держит **срок** домена. Голосовать нечем: ни один raft не охватывает кластеры, поэтому срок растёт только по слову оператора — переносом или передачей; аренды и автоматической смены держателя нет. Запись срока («держатель срока N — этот кластер, его дверь — здесь») подписывает выпускающий ключ держателя: его serial стоит в наборе, набор подписан корнем, и член проверяет запись своим набором — подделать её без ключа нельзя, а запись отозванного выпускающего не значит ничего. Члены следуют за большим сроком сами (раздел 17.4).

### 18.2. Резервная копия и хранители

Ключи, отзывы и права каждого кластера уже лежат на каждом члене. Не лежат правка для выключенного члена, список членов, топология, назначения, люди, гранты — то, что домен **решил** и чего больше нет ни у кого. Держатель публикует это одним подписанным документом — резервной копией — и даёт двум **хранителям** указатель на неё; агент хранителя несёт её домой, как несёт ключи. Секреты в копии запечатаны её ключом, а не кольцом держателя (у нового держателя кольца старого нет): ключ выведен из корня, поэтому новый держатель откроет копию файлом восстановления — и по той же причине украденный файл восстановления открывает все резервные копии: файл восстановления — всё. Новая ревизия копии появляется, только когда содержимое изменилось: тихий домен не пишет на флеш хранителя ничего.

**Аварийный перенос.** Держатель умер. Оператор приносит файл восстановления на новый кластер и говорит «перенеси сюда». Новый подписант спрашивает соседей, у кого какая запись и какая резервная копия, и берёт наибольшую проверенную; новый срок — на единицу больше наибольшего, что он увидел, поэтому второй перенос в том же месяце не сравняется с первым. Если сосед объявил копию новее, но не отдал её, перенос отказывает: восстановиться из старой значило бы молча откатить домен; оператор может назвать её сам (`copy` с `why`) — и это будет строка журнала.

**Старый держатель возвращается.** Его агент приносит запись большего срока, процесс читает её в своём хранилище и уступает: дальше он отказывает каждой правке словами «правки — туда» (409 `deposed`) и забывает ключи. То, что он успел изменить после последней резервной копии (**брошенное**), он перечисляет для человека: отбросить молча нельзя, применить самому — значит дать заменённому писать в замену.

**Плановая передача.** Держатель жив, и домен надо перенести на новую серверную — аварийный путь потерял бы всё после последней копии. Держатель замораживает правки на секунды передачи (503 `frozen`), отдаёт последнюю копию самой цели и ждёт, пока её агент скажет, что взял, затем передаёт цели свои ключи, запечатанными к ключу, который цель приготовила. Цель восстанавливается из этой копии и пишет запись следующего срока теми же ключами — набор менять не надо, корень не нужен. Предел назван прямо: ключи копируются, и что прежний держатель их забыл — обещание, а не доказательство; если прежнему нельзя доверять, путь один — аварийный перенос со сменой ключей (`stolen`).

**Камера-держатель.** У камеры кроме «умерла» есть второй отказ: её уносят — а с ней ключи домена, запечатанные кольцом, которое лежит на той же камере. Перенос по резервной копии вора не останавливает: он по-прежнему подписывает токены и записи срока. Спасает смена ключей при переносе; корень вне держателя делает кражу обычным переносом (раздел 14). Ставить держателя на камеру стоит, только если ничего другого нет — и тогда в помещении, на PoE с бесперебойным питанием, с хранителями на другом коммутаторе и другом питании; один из хранителей — преемник: оператор заранее знает, где нажимать «перенести домен сюда».

### 18.3. Общий документ и история тревог

Две вещи нужны каждому домену, и ни одна не требует базы данных. Первая — настройки «для всех» (шаг счёта, общие метки, сценарии между камерами), которые каждый кластер знает и тогда, когда домен недоступен. Что общее, говорит манифест: `domain.shared` перечисляет поля единицы, которые наследуют (значение домена у счётчика, у которого нет своего), и документы целиком. Секрет общим быть не может: документ подписан, а не запечатан; не наследующее поле — тоже: значению домена некуда было бы лечь (исключение — поле, по которому страница группирует дерево: его значение домена — сами группы). Документ — объект, а строка `domain/shared` — указатель на него с контрольной суммой: правка пишет сначала объект, потом указатель по CAS, и два редактора не затрут друг друга. Подписывает процесс `domain` выпускающим ключом; член проверяет подпись своим набором, никогда — тем, что пришло вместе с документом: копия, которая проходит проверку, хороша, откуда бы ни пришла; которая не проходит — ничто. Домен, восстановленный из вчерашней копии, указывает на вчерашнюю ревизию, и член с сегодняшней её не берёт — поэтому после переноса новый держатель переподписывает документ следующей ревизией своего срока. «Принято» — не «доставлено»: рядом с документом держатель показывает, кто держит текущую ревизию, кто старую, кто отказался и почему, кто молчит; выключенный член назван по имени, а не округлён.

Вторая — один список тревог по всем членам. Страница тревог члена — это сутки (раздел 17.1); неделю истории хранит держатель: он и так читает каждую страницу. Сам список отдаёт консоль домена (раздел 19).

### 18.4. Цена и очередь

Площадка из камер, каждая из которых сама себе кластер, даёт триста членов в первый же день, и вечером тридцать из них выключены. Код домена от этого не меняется — член отчитывается сам, — меняется цена, и глава её называет. Каждый член отчитывается раз в пять секунд: у держателя 60 приёмов в секунду. Спокойная площадка поколений не пишет вовсе (меняется только время в пульсе, а время изменением не считается) — пишется только метка, раз в 22,5 секунды на член: около 13 записей в секунду на всю площадку. Изменение члена стоит трёх объектов и двух удалений. Молчащий член не стоит ничего.

Потолки названы заранее: строка хранилища — полмегабайта, список членов — одна строка, запись члена в худшем случае 820 байт — поэтому членов не больше пятисот, с запасом; из прежних ключей держатся четыре последних; отчёт и целое поколение — не больше 16 MiB.

У держателя из трёх серверов юниты `w2c-domain` стоят на каждом, и три процесса вели бы проход втроём — три писателя каждой строки. Поэтому процессы `domain` одного кластера берут **очередь** `domain/signer-turn` — ту же механику, что у контроллера (раздел 5.1): активен тот, кто держит очередь, каждая его запись идёт со стражем очереди, а остальные — ждущие: прохода не ведут и на каждую дверь отвечают 503 `standby`, что агент читает как «держатель недоступен на этот проход». «Держатель на одном узле» значит «одна очередь», а не «один сервер»: смена узла внутри кластера — не перенос, срок не меняется.

## 19. Консоль домена

Двери людей домена — вид, список членов, топология, назначения, правки — живут у **консоли домена** (процесс `domainconsole`) на коробке держателя, а оператор сидит у консоли своего кластера: консоль кластера пересылает ему эти двери (поздний слой урока P/06), консоль домена их принимает. Строк она не пишет: что можно прочитать — вид, члены, топологию (из строки, не из вида: правка видна следующему чтению сразу), назначения, гранты, общий документ — отдаёт сама из строк держателя; правки, двери людей и вход передаёт процессу `domain` как пришли — метод, путь, тело, `Authorization`, ключ повтора, — и отдаёт его ответ как пришёл. Процесс проверяет личность и грант сам: двери людей с паролями он не доверяет никому другому. Дверь вида отвечает 404, пока держатель не построил вид. Три отказа процесса никто по дороге не пересчитывает: `deposed`, `frozen`, `standby` доходят до человека как пришли.

Пересланный вход несёт `X-Operator: console`, и признать этот заголовок можно только у соединения, чья роль `console` доказана сертификатом; прав он не даёт — права решает сторожевая по токену (та же функция `may`, право — по `domain/grants/domain`). Консоль домена доверяет в рукопожатии только центрам принятых членов и своему: чужой центр не доходит даже до HTTP. Маршруты подсистемы (`door.pass`) консоль домена передаёт воркеру на домене. Страницу держателя отдаёт тот же модуль консоли (раздел 10.1) с разделом `domain`: `/manifest` без корня, `/mounts` по каталогу держателя, `/session`.

Список тревог домена сливает страницы членов, и каждая строка называет своего члена. Погасший член — тоже строка тревоги, со временем, когда его отчёт стал старым; его тревоги из последнего отчёта остаются в списке: выбросить их значило бы потерять самое важное. Молчание бывает двух видов — «члена нет» (посылают охрану) и «член жив, но не отчитывается» (посылают того, кто чинит), — и отличает их **свидетель**: независимый процесс, который слышит единицу члена (`domain.witness` в манифесте); слышал позже последнего отчёта — `not_reporting`.

## 20. Как всё сходится: одна история от начала до конца

**Установка.** Оператор ставит пакет на три сервера. На каждом поднимаются одни и те же юниты: демон хранилища, ресурс, контроллер каждого манифеста, консоль, агент, воркеры подсистем, таймер запасных. Демоны образуют группу из трёх по mTLS; центр кластера выпускает сертификаты ролей. Установщик кладёт манифест `testsub` в строку `platform/manifest/testsub` с дайджестом и ревизией 1, затем публикует метку. Генератор строит файл прав из каталога манифестов; демон загружает его при старте.

**Создание единицы.** Оператор в браузере: модуль консоли спросил `/session`, `/manifest`, нарисовал форму по `display` манифеста. `POST /counters {name: c1, start: 5}` с ключом идемпотентности. Сторожевая до чтения тела проверила путь и грант; консоль записала заявку `testsub/idem/create-c1`, подняла номер в счётчике, создала строку `testsub/counters/c1` (все значения — строки байт; `step` отсутствует — он наследуемый), запечатав `cred_secret` конвертом кольца, и ответила 201 с маской.

**Размещение.** Контроллер на проходе видит неразмещённую `c1`. Пул: живые воркеры (пульс менялся за 45 с) минус дренируемые; ограничений нет; предпочтение — больше свободной ёмкости с учётом резервов активного intent. Он пишет `testsub/placement/c1` с `manifest_rev` и добавляет `c1` в `testsub/workers/w-1` под `cas` и стражем turn.

**Запуск.** Воркер `w-1` на шаге аренды: слот мой (продление с `id`, `until` +45 с), аренды подтверждены, назначение перечитано — появилась `c1`. Ворота: взять эпоху записью с `cas` (строки не было — счёт начинается, `epoch: 1` с учётом пола), окно считается от отправки; ответ вовремя — запуск единицы: вызов `start_unit` подсистеме, конверт раскрыт в последний момент, драйвер получил пароль, в памяти и пульсе — конверт. Пульс пишется файлом каждые десять секунд.

**Жизнь.** События единицы ложатся строками в бакеты `events/testsub/c1/e1/…`; тревоги — в своё дерево с `fsync`. Просьба «прибавь пять» — строка `requests/<rid>`; воркер создал метку `objects/…` созданием-однажды, выполнил, записал `performed`; консоль после `settle` сняла строку. Контроллер после прохода переписал шард снимка `testsub/snapshot/w-1`.

**Сбой.** Хранилище переизбрало лидера — пять секунд `unavailable`/`ambiguous`: воркер повторяет продление тем же `id`, действия разрешены до конца окна. Хуже: сервер `w-1` выдернули из розетки. Пульс перестал меняться; версия слота неизменна; ресурс молчит — через 90 с наблюдения контроллер отдаёт имя, привязав отдачу к версии строки, и перевозит `c1` через intent на `w-2`; тот берёт эпоху 2 и запускает единицу; старые данные остаются под `e1` и помечены `fenced`. Сервер вернулся — ресурс тянет бакеты из зеркала, воркер берёт свободное имя; `c1` назад сама не едет, пока не объявлен `home`.

**Обновление.** Новая сборка понимает схему 2. Процессы перезапущены на старой раскладке; `GET /schema` показывает `can_raise_to: 2`; оператор закрывает старты старых сборок, поднимает номер; старый процесс, попытавшийся стартовать, падает видимо и сразу.

**Домен.** Три кластера — центр и две площадки — соединяются в домен. Установка на держателе породила корень в файл восстановления, ключи держателя, ключ приёма книг и набор rev 1. Оператор принимает членов с двух сторон: на каждом `join` закрепляет корень, на держателе вносит ключ члена. Агент площадки подписывает отчёт ключом члена и несёт держателю изменение против названной базы; держатель пишет поколение, байты, метку — и отвечает набором, грантами и ждущими правками, секретное — конвертом `m1`. Площадка за NAT отчитывается через ретранслятора пакетом. Вид домена сводит копии каждые три секунды; молчащий член — `silent`, и вид неполон. Оператор домена правит единицу выключенного члена: правка хранится у держателя (202), агент забирает её с ответом и применяет с `If-Match` той ревизии, которую видел домен. Воркер рекордера просит у местной двери агента токен на поток камеры соседа; домен решает, что в токене написано, получатель проверяет его своим набором, без сети.

**Перенос.** Держатель умер. Оператор приносит файл восстановления на новый кластер; тот спрашивает соседей, берёт наибольшую проверенную резервную копию — правки для выключенных, список членов, топология, назначения, люди, гранты — и пишет запись нового срока. Агенты членов сами находят её и идут за большим сроком; никто никому ничего не сообщил. Старый держатель вернулся — прочитал запись большего срока, уступил (`deposed`), забыл ключи и перечислил человеку то, что успел изменить после последней копии.

|---|---|
| строка (хранилища) | row, запись хранилища |
| дверь | HTTP API процесса (на unix-сокете или TLS) |
| коробка | один сервер без группы |
| группа | кластер серверов с реплицированным журналом (raft) |
| страж | guard, fencing token — условие записи на версию другой строки |
| проход | семантика операции по шагам |
| вес / потолок | размер строки / лимит размера |
| отказ | ошибка, ответ не-200 |
| идентификатор записи | ключ идемпотентности `id` |
| единица | то, что оператор создал по манифесту (счётчик, камера) |
| воркер | процесс, ведущий единицы |
| слот | строка, подтверждающая владение именем воркера |
| эпоха | номер попытки вести единицу |
| аренда | ограниченное время действия по последнему подтверждению |
| надгробие | строка с `deleted: "true"`, оставшаяся после удаления |
| заявка | запись памяти идемпотентности `idem/<ключ>` |
| манифест | декларативное описание подсистемы в одном YAML |
| конверт | строковое представление запечатанного значения с `kid` |
| кольцо | текущий и прежние ключи запечатывания |
| AAD | данные привязки шифртекста к строке и полю |
| маска | значение для показа (`***`), которое нельзя прислать как новый секрет |
| объект | большое/частое данное, файл на сервере писателя |
| бакет | файл событий, закрываемый по времени |
| метка | строка `objects/<ключ>`, созданная один раз до вызова просьбы |
| жнец | проход консоли, закрывающий неначатые просьбы |
| роль | установленная личность процесса с набором разрешений |
| образец | точный ключ или префикс для сравнения в правах |
| отрицание | запрет с `!`, сильнее разрешения |
| оценщик | общий механизм ответа «разрешено ли действие над ключом» |
| сторожевая | проверка личности и грантов перед каждой дверью консоли |
| модуль консоли | один `console.js` у всех реализаций, байт в байт |
| оболочка | страница подсистемы, монтирующая модуль и добавляющая своё |
| схема | версия раскладки хранилища |
| шард снимка | объект-описание единиц одного воркера |
| тело (blob) | байты по дайджесту: дайджест в строке, байты в объекте |
| запасной | юнит воркера без имени, ждущий предложения |
| дверь без голоса | демон хранилища-пересыльщик на сервере вне группы |
| пол эпох | нижняя граница выдаваемых номеров после восстановления |
| член | кластер, принятый в домен |
| держатель | член, на котором работают службы домена; роль, не вид кластера |
| корень | пара Ed25519 домена; закрытая половина только в файле восстановления |
| закрепление | `domain/root` члена: корень, которому член верит; пишется при установке или приёме |
| набор | `domain/keys`, подписанный корнем: ключи держателя, отзывы, ключ приёма книг |
| ключ приёма книг | X25519 домена; зерно у держателя, открытая половина в наборе |
| окно отзыва | сколько отозванное ещё принимается без связи; называется числом и часами проверяющего |
| стук | отчёт кластера, которого нет в списке, с верной подписью своим ключом |
| копия члена | то, что держатель принял от члена последним; не путать с резервной копией домена |
| поколение | целая копия члена у держателя под номером `rev` |
| метка `reported` | граница принятого: читатель берёт номер поколения из неё |
| дельта | изменение отчёта против поколения `base` |
| дорога | прямо или через ретранслятор; её называет держатель |
| топология | запись оператора `via`: кто через кого ходит |
| ретранслятор | член, через агента которого отчитываются члены без своей дороги к держателю |
| пакет | отчёты членов за ретранслятором одним запросом |
| отпечаток центра | sha256 сертификата центра кластера; запись члена несёт до двух |
| вид домена | сводка копий для людей и консоли, с пометками неполноты |
| теневой режим | первый режим домена: только смотрит и печатает разницу шести видов |
| токен человека | подписанный доменом токен вида `person`: имя и срок |
| строка грантов | права людей в одном кластере (или у двери домена) |
| копия грантов | строка, которую агент принёс домой; годна сутки от приёма |
| аварийный вход | одна учётка кластера на случай без связи; сессия в памяти консоли кластера |
| книга | сводка входов членов по правилу манифеста (`from`, `key`, `pick`, `to`) |
| вклад | строки одного члена для одной книги; живёт ровно со слотом |
| `missing` | кого не хватает в книге, с закрытым словом причины |
| индекс имён | какие члены заявили какие имена книги с `domain.names` |
| назначение | запись оператора `domain/placement/<sub>/<ref>`: исполнитель единицы и её копий |
| хранимая правка | правка единицы члена, ждущая его агента у держателя |
| исход | что сделала консоль члена с правкой: `performed`, `conflict`, `refused` |
| вид токена | объявление манифеста: кому выдаётся, что в нём, из какой области |
| область | откуда подписант берёт утверждения: назначение, единица или общий документ |
| аудитория | кластеры, которым токен адресован |
| срок | номер держателя; растёт только переносом или передачей |
| запись срока | подписанное выпускающим «держатель срока N — этот кластер, его дверь — здесь» |
| резервная копия | подписанный документ того, что решил домен; хранители несут её домой |
| хранитель | член, выбранный держать резервную копию |
| брошенное | то, что старый держатель изменил после копии, из которой восстановлен новый срок |
| общий документ | подписанные значения и документы, объявленные `domain.shared` |
| указатель | строка `domain/shared`: ревизия и сумма объекта |
| страница тревог | новейшие тревоги члена в его отчёте: сутки, не больше сотни |
| свидетель | независимый процесс, слышащий единицу члена; отличает «нет члена» от «не отчитывается» |
| очередь процесса `domain` | строка `domain/signer-turn`: активен её держатель |
| ждущий (`standby`) | процесс `domain` без очереди: прохода не ведёт, отвечает 503 `standby` |
| местная дверь токенов | дверь агента, у которой воркер просит токен, не получая ключей |
