# Файл `<имя>.subsystem.yaml` — манифест подсистемы; переименование — одним переходом в стадии B

## Context and Problem Statement
Класс системы: платформенная система — декларативный файл подсистемы, который платформа читает и проверяет строгим
загрузчиком (М10/2), и имена, которыми его называют курс, реализации и продукт.

Слово «спека» у нас означает и файл `<имя>.subsystem.yaml`, и нормы уроков (`spec/*.norms.md` с API и приёмкой), и
выгрузку `cammeta-specs`, и сессию «Спецификация». Фраза «правка спеки» читается двояко. Предложение
«Манифест подсистемы вместо спеки подсистемы» (2026-10-19): файл называть манифестом, как принято (манифест Kubernetes,
где `spec` — раздел внутри манифеста; `AndroidManifest.xml`; манифест расширения и плагина). Затронуты около 2700
вхождений в прозе (часть — про нормы, слепая замена не годится), имена файлов урока 2, имена на проводе
(`platform/spec/<sub>`, `spec_rev` решения размещения), код обеих реализаций и продукт.

## Decision Drivers
* одно слово — одно понятие; после переименования «spec» значит только нормы;
* «одно имя на обеих сторонах» и «переименование без следов» (СЕССИИ.md §1): нельзя жить в полупереименованном
  состоянии, где проза говорит «манифест», а ключ — `platform/spec`;
* цена правки кода и провода у двух реализаций и продукта.

## Considered Options
* переименовать сейчас, по частям;
* переименовать одним переходом в стадии B ADR-0083;
* не переименовывать.

## Decision Outcome
Выбран вариант «одним переходом в стадии B»: уроки и так переезжают в `Platform/` с новыми именами файлов и
переписанной прозой, а в стадии C обе реализации генерируются заново — имена кода и провода идут за спецификацией без
отдельной правки.

1. Имя: **манифест подсистемы** — файл `<имя>.subsystem.yaml` (суффикс не меняется). Урок — «Манифест подсистемы и
   строгий загрузчик» (`Platform/02-installer/`).
2. Провод: ключ `platform/manifest/<sub>`, поле `manifest_rev` решения размещения и прочие имена на проводе и в
   строках — в том же переходе.
3. ADR-0071: «манифест плагина» (`plugin.json`, имя PSIM) и «манифест подсистемы»; уточнение обязательно везде.
4. Тексты принятых ADR не переписываются — это запись решённого тогда; меняются действующие документы, глоссарий
   (новая статья «Манифест подсистемы») и, по желанию, заголовки индекса.
5. До стадии B ничего не меняем.
6. Продукт — вместе с «Сборкой», когда работа над продуктом возобновится; до того старые имена продукта — долг паритета.

### Consequences
* Good, because «спека», «спецификация», `spec/` остаются только за нормами; двусмысленность уходит.
* Good, because имя совпадает с общепринятым, читателю не нужно учить наше.
* Good, because в стадии C код реализаций получает новые имена бесплатно, вместе с регенерацией.
* Bad, because около 2700 мест прозы решаются по смыслу, вручную.
* Bad, because смена имён на проводе — правка формы на обеих сторонах и в продукте; до возобновления продукта — долг
  паритета.
* Bad, because до стадии B старое имя живёт, а решение о новом уже принято.

### Confirmation
* После стадии B в выгрузке нет «спек…» в значении файла подсистемы (поиск по смыслу, список исключений — нормы);
  ключи `platform/manifest/<sub>` и `manifest_rev` в нормах, каталоге данных и OpenAPI.
* Обе реализации стадии C зелёные на приёмке с новыми именами.
* Глоссарий: статья «Манифест подсистемы»; ADR-0071 и действующие документы — «манифест плагина».

## Pros and Cons of the Options

### переименовать сейчас, по частям
* Good, because двусмысленность уходит раньше.
* Bad, because полупереименованное состояние (проза против провода) и отдельная правка кода двух реализаций, которые
  в стадии C всё равно генерируются заново.

### одним переходом в стадии B
* см. Consequences.

### не переименовывать
* Good, because нет работы.
* Bad, because «правка спеки» остаётся двусмысленной навсегда.
