# Подсистема `backend`: REST API consolem для WebUI — отдельная подсистема VMS; платформа даёт делегирование, ленту изменений, версии и память повторов

## Context and Problem Statement
Класс системы: прикладной сервис (подсистема VMS) поверх платформенной системы; часть решения — изменение платформы.

Продуктовая команда утвердила интерфейс конфигуратора consolem (`github.com/ndm234234/consolem`): WebUI и его контракт с
сервером — `api/openapi.json` (60 операций и 3 служебные), приёмка — их тесты API против стенда. Сессия «Консоль» сравнила
его с нашей консолью (СВОДКА-КОНСОЛИ.md §5): принципы совпадают (сервер — правда, без оптимистичных обновлений, CAS по
версии, ключ идемпотентности), но платформа сейчас не держит того, что нужно этому API:
- браузер узнаёт о переменах опросом (модуль — около 8 + 2N запросов каждые 5 с);
- `If-Match` есть только у строки единицы и необязателен;
- память повторов `Idempotency-Key` — только у `POST /<rows>`;
- отказ — английское слово без указания поля;
- воркер не может действовать от имени человека.

Решения владельца 2026-10-29 (через «Консоль», АДАПТЕР-CONSOLEM.md §8):
1. Адаптер к API consolem пишем мы.
2. Адаптер — отдельная подсистема VMS `backend`, целиком наша; отдаёт WebUI REST API consolem; размещается рядом с `live`
   (те же метки серверов, отдельный процесс).
3. Пока у каждого кластера свой `backend`; общий для домена — следующим шагом.
4. От имени человека `backend` ходит в консоль **делегированием токеном двери**.
5. Единица `backend` — вход на набор меток, как у `live`.
6. Контракт ведёт продукт: закрепляем коммит `openapi.json` consolem, сверяемся при каждой их правке; свои отличия — только
   объявлением возможностей, контракт не правим.

## Decision Drivers
* WebUI consolem утверждён продуктом — его API нужно отдать без правки контракта.
* Права и правду решает консоль платформы; второй источник прав недопустим (ADR-0093 доп. (1): учётных данных админа
  воркер не получает).
* Модулю консоли самому нужны те же механизмы (СВОДКА-КОНСОЛИ.md §4 пп. 1–5): тихое затирание правок без `If-Match`,
  опрос вместо подсказки о переменах.
* Текущая цель — Go GREEN 01–10 и генерация VMS (ADR-0090 доп. (14)); изменение платформы не должно её сорвать.

## Considered Options
* **А. Подсистема VMS `backend` поверх платформы с доработками платформы (B1–B6 ниже).**
* Б. Адаптер внутри консоли платформы (новые двери консоли в форме consolem).
* В. Адаптер вне платформы со своим входом и своими правами (сервисная учётная запись).
* Г. Править WebUI consolem под нашу консоль.

## Decision Outcome
Выбран вариант «А», потому что он отдаёт API consolem без правки их контракта, не заводит второго источника прав
(действует человек, права — его гранты), а механизмы платформы, которые для него нужны, нужны и нашему модулю консоли.
Б смешивает чужой контракт с платформенным и тянет его в каждую реализацию платформы; В — второй источник прав (против
ADR-0093 доп. (1)); Г — против решения владельца (контракт ведёт продукт).

### A. Подсистема `backend` (урок `VMS/11-backend`, «Спецификация VMS»)
1. Контракт двери — `openapi.json` consolem на закреплённом коммите (сейчас `9dc1688`), без своих правок. Чего у нас
   нет — `404 NO_ROUTE` и объявление возможностей (запрос продукту — владелец).
2. Единица — `backend/endpoints/<name>`, вход на набор меток; размещение как у `live`: `labels-subset`, `grows: true`,
   ёмкость — сессии. Процесс отдельный.
3. Воркер без своего состояния; пишет только свой префикс (память группового `idempotencyKey`, пока нет B3). Статику
   WebUI раздаёт своей дверью.
4. Своего входа нет: при 401 — на вход консоли.
5. Сопоставление «вид consolem ↔ подсистема VMS» — таблица данными урока (камера = `cam` + `rec` + `det`, правило =
   `auto`, хранилище = `rec/volumes`, домен consolem = наш кластер).

### B. Платформа (уроки P/06, P/07, P/10; «Спецификация», «Спецификация домена»)
1. **Делегирование токеном двери.** Консоль принимает свой токен двери подсистемы `backend` (P/06.5 `/where`, договор
   токена двери) как личность `claims.user` — только от процесса роли `backend` (сертификат роли), только на дверях
   людей, только до `expires`; права — гранты этого человека. Токен у браузера человека есть и без того; учётных данных
   админа воркер не получает (ADR-0093 доп. (1) не нарушен).
2. **Лента изменений** `GET /changes` (SSE или длинный опрос): сообщения «строка X — ревизия R / удалена»; строится
   сравнением перечислений префиксов хранилища; номера — в пределах экземпляра консоли, чужой номер → `reset`; фильтр по
   `view` человека, как у `/events`; подсказка, а не канал (ADR-0038). Модуль консоли переходит на неё вместо опроса.
3. **Память повторов `Idempotency-Key`** на `PUT`, `DELETE` и записях таблиц, а не только на `POST /<rows>`.
4. **Версия на всех записях людей:** `revision` у строк таблиц и снимков настроек; `ETag`; `If-Match` на всех дверях
   записи; 412 с текущей строкой в теле. `If-Match` у двери остаётся необязательным, форма модуля шлёт его всегда
   (закрывает ADR-0091 доп. (28) п. 3).
5. **Коды отказов:** закрытый перечень `error` по дверям и `field` (путь поля) у 400, 409, 412.
6. **`/session`** отдаёт `server_time` и `timezone`.

### C. Вторая очередь — отдельными ADR, когда до неё дойдёт урок `backend`
Папки (группы) как записи; групповые операции в консоли (шаги с ожидаемыми ревизиями, ход в ленту, пауза, отмена,
повтор, откат); роли, группы людей и каталоги LDAP в домене; просьбы с ходом и `GET` состояния; телеметрия сервера в
пульсе ресурса.

### Порядок
1. B — следующим приращением платформы **после** зачётного Go GREEN 01–10 (рубеж генерации VMS, ADR-0090 доп. (14)): до
   него нормы 01–10 не расширяются этим ADR. Нормы B пишут «Спецификация» (P/06, P/07) и «Спецификация домена» (P/10),
   каждая по разбору ревью этого ADR; линии Go и Python догоняют пином.
2. A — урок `VMS/11-backend` «Спецификация VMS» пишет текстом сейчас, параллельно; генерация — с остальной VMS после B.
3. Запрос продукту (объявление возможностей, профиль тестов на нашем стенде, версия сборной камеры) — отправляет
   владелец; черновик — `/Users/murat/w2c/cammeta-console/ЗАПРОС-ПРОДУКТУ-CONSOLEM.md`.

### Consequences
* Good, because адаптер без состояния и без своих прав; права и правду решает консоль; лента и версии нужны и нашему
  модулю консоли; приёмка `backend` — тесты продукта.
* Bad, because новая личность у консоли — делегирование; ему нужен отдельный разбор ревью и модель угроз.
* Bad, because лента добавляет консоли работу: перечисление префиксов на каждый такт.
* Bad, because контракт ведёт чужая команда — идём за их правками.
* Neutral, because риск: тесты продукта без объявления возможностей и профиля под наш стенд не пройдут; версия сборной
  камеры у consolem — целое, у нас камера — несколько строк (вопрос продукту).

### Confirmation
* `backend`: тесты API consolem против стенда в профиле возможностей; `?selftest` их интерфейса на стенде.
* Платформа: приёмка P/06 — новые сценарии ленты, `If-Match` и 412 на таблицах, память повторов `PUT`/`DELETE`,
  делегирование (свой токен от роли `backend` — принят, от иной роли и после `expires` — отказ); jsdom модуля — форма с
  `ifMatch` и экран 412.
* Ревью этого ADR — Kimi и Claude (Codex — после сброса лимита), разбор — «Архитектор»; нормы — после разбора.
