# Плагины PSIM работают у нас как подсистема через воркер-адаптер; платформа не меняется

## Context and Problem Statement
Класс системы: расширяемая система поверх платформенной.

Репозиторий `psim-sdk` (`src.axxonsoft.dev/bitbucket/scm/~v.bratishchev/psim-sdk.git`, коммит `3c61ddc`, 05.10.2026)
описывает плагинную систему PSIM: плагин — исполняемый файл с gRPC-сервером `Plugin` (`Configure`, `ChangeUnit`,
`PullEvents`, `SendCommand`, `CanCreateChild`, `Shutdown`), платформа — сервер `Platform` (`Authenticate`, `Register`,
`PullEvents`, `SendCommand`, `RegisterResource`, каталог объектов); манифест `plugin.json` объявляет типы объектов с
родителем, параметры, события, команды, `provides` (веб-интерфейс, прокси, ссылки) и `requires` (PostgreSQL, BL API,
HTTP API); бутстрап — два кадра в stdin, логи — JSON-строки в stdout; учётные данные `client_id`/`client_secret`,
короткий JWT, сессия; перезапуск с backoff. Вопрос владельца: могут ли такие плагины работать на нашей платформе.

Платформа знает только спеки подсистем (ADR-0001), хуков нет (ADR-0002), плагин — отдельный процесс с бюджетами и не
в критическом пути (`plugins-extensibility.mdc`).

## Decision Drivers
* плагины не меняются: бинарь и `plugin.json` как есть, их эмулятор и примеры — приёмка
* платформа ничего не узнаёт о PSIM: граница держится
* всё объявленное плагином становится декларацией спеки, не хуком
* чужие управляемые ресурсы (СУБД) мы не заводим

## Considered Options
* Подсистема через адаптер: генератор манифеста в спеку, воркер-адаптер хостит процесс плагина и играет для него
  роль `Platform`; платформа не меняется.
* Реализовать сервис `Platform` в самой платформе (консоль, контроллер) и считать объекты плагинов единицами
  напрямую.
* Переписывать плагины под наш контракт воркера.

## Decision Outcome
Выбран первый вариант. Соответствие:

| У PSIM | У нас |
|---|---|
| `plugin.json`: типы объектов, родитель, параметры, события, команды, `provides`, `requires` | спека `psim-<plugin_id>.subsystem.yaml`: единицы с полями, дети — таблица со ссылкой на единицу (или вторая спека с `about`, если детей размещают отдельно), `events:`, семейство `requests:` с меткой итога (ADR-0054), `door.routes`, `display` |
| плагин — процесс, платформа толкает `ChangeUnit` | воркер-адаптер держит единицы по размещению и аренде, читает свои строки и толкает их плагину (`INITIAL`/`NEW`/`UPDATE`/`DELETE`) |
| `PullEvents` с номером возобновления | журнал событий единицы, `of: <sub>/<id>` |
| `SendCommand` к объекту | строка `requests` → `SendCommand`, итог в метку |
| `Authenticate`, JWT, сессия | адаптер — «платформа» для плагина: учётка процесса в секретных строках спеки, токен выдаёт адаптер |
| `provides` | маршруты двери держателя; страница ходит на дверь сама, адрес из `/where` |
| каталог пишет плагин | записи строк по `worker.writes`, форма через загрузчик |
| падение, backoff, здоровье | `Reconciler`/`Backoff` базового воркера, метрики с именем и версией плагина |

Что строится, всё на стороне подсистемы: (1) генератор `plugin.json` → спека с проверкой по `schema/plugin.schema.json`
PSIM; (2) воркер-адаптер на базовом воркере платформы: процесс плагина по правилу расширяемости (отдельный процесс,
бюджеты памяти и времени вызова, перезапуск с backoff, stdin как канал жизни, stdout в журнал), сервер `Platform`
для него, перевод в обе стороны; (3) выдача учётных данных и токена из секретных строк. Решения по пробелам:
`requires: postgresql | bl_api | http_api` в первой версии — отказ загрузчика (управляемых СУБД у нас нет; внешняя
база оператором как секретная строка — отдельным решением по первому реальному плагину); плагин с одним
соединением к внешней системе размещается целиком, как группа (ADR-0053); всё, чего спека не выражает, — новый
ключ спеки через «Архитектора», не обходной путь в адаптере.

Порядок: прототип на `security_controller` и `camera` из `psim-sdk` сначала в курсе как урок («Лекции»), затем в
продукте («Сборка»), после шагов 1 и 3 ADR-0070. Приёмка: оба примерных плагина и эмулятор работают под нашим
адаптером на стенде без единой правки в плагинах.

### Consequences
* Good, because чужие плагины работают без переписывания, а граница платформы не трогается.
* Good, because манифест становится спекой: права, события, команды и страницы проходят через загрузчик и правила.
* Bad, because плагины с управляемой СУБД и ресурсами NGP в первой версии не работают.
* Bad, because плагин, рассчитанный на все свои объекты в одном процессе, при размещении по серверам нужно держать
  группой.

### Confirmation
Генератор принимает оба примерных манифеста и отказывает манифесту вне схемы; эмулятор PSIM и два плагина проходят их
сценарии под адаптером на стенде; тест границы зелёный (слов PSIM в платформе нет); метрики адаптера несут
`plugin_id` и `plugin_version`.
