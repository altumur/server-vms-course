# Групповые операции consolem: запись консоли, ведёт консоль под очередью и поколением, шаг переводит и пишет `backend` по билету шага; на `exp` — пауза; откат не объявляется

## Context and Problem Statement
Класс системы: платформенная система (консоль кластера). Потребители — подсистема VMS `backend` (ADR-0094 A) и модуль
консоли платформы.

Ссылки вида `openapi:N` — строка N файла `VMS/11-backend/consolem.openapi.json` (закреплённый коммит consolem
`ef7175b`, V/11.2 Н1.1). «Разбор» — `decisions/inbox/2026-10-30-ревью-ADR-0095-0096-разбор.md`.

Контракт consolem описывает групповую операцию так:
- `POST /operations` (`openapi:1886`): «Шаги выполняются по одному; ход приходит в поток (operation.progress,
  operation.finished). Объект, над которым идёт другая операция, — 409 BUSY» (`openapi:1893`). Ответ — 202 с записью
  операции (`openapi:1905`); отказы 404, 409, 412, 422, 428 (`openapi:1915`–`1927`).
- Тело `OperationRequest` (`openapi:8261`): `idempotencyKey` — «запрос с тем же ключом в течение 10 минут вернёт ту же
  операцию и ничего не выполнит снова» (`openapi:8273`); `expectedVersions` — «Не совпала хоть одна — 412, ничего не
  выполняется» (`openapi:8289`).
- Шаг `OperationItemRequest` (`openapi:8216`) — над одним объектом `targetId`, ровно одно из трёх: `set` (правка полей
  устройства, сервера, домена, хранилища или тома), `folderIds` (папки устройства целиком), `create` (дочернее
  устройство) (`openapi:8222`).
- Запись `Operation` (`openapi:8344`): `state` — `running | paused | done`, `createdAt`, `finishedAt`, `revertOf`,
  `retryOf`, счётчики `total`, `done`, `ok`, `failed`, `cancelled`, шаги `items`; «Частичный успех — норма: каждый шаг
  завершается сам по себе» (`openapi:8423`). Шаг `OperationItem` (`openapi:8294`): `state` — `wait | run | ok | fail |
  cancel`, `code`, `version` после шага, `createdId`.
- `GET /operations/{id}` (`openapi:1939`) — ход и итог. Двери перечня операций (`GET /operations`) в контракте нет.
- `pause` (`openapi:1980`): «Текущий шаг доигрывает, следующие ждут» (`openapi:2022`); `resume` (`openapi:2025`);
  `cancel` (`openapi:2069`): «Выполненное остаётся, невыполненные шаги — cancel» (`openapi:2111`).
- `retry-failed` (`openapi:2114`) — «Повторить неудачные шаги новой операцией»; ответы — 202, 404, 409, 401
  (`openapi:2133`–`2149`), **412 среди них нет**.
- `revert` (`openapi:2158`): «Сервер помнит, какими объекты были до каждого выполненного шага. Если объект с тех пор
  изменился, его шаг отката — fail VERSION_MISMATCH» (`openapi:2165`).
- Поток: `operation.progress` — «kind=operation, entityId — операция, payload — шаг (OperationItem) и счётчики»,
  `operation.finished` — «payload — итог (state, ok, failed, cancelled)» (`openapi:7406`–`7407`).
- Объявление возможностей: необъявленная операция отвечает 404 `NO_ROUTE`; «Объявленное обязано работать по контракту
  целиком» (`openapi:7355`–`7362`).

Сейчас все семь операций — 404 `NO_ROUTE` (V/11.2 Н1.2, № 38–44, `VMS/11-backend/spec/11.2-backend.norms.md:87`–`93`;
профиль `VMS/11-backend/data/profile.tsv:45`–`51`), двери `/operations` нет в перечне обратного вызова `backend`
(ADR-0094 B1, `decisions/0094-…:104`; V/11.1 Н1.5, `VMS/11-backend/spec/11.1-backend.norms.md:179`), поток сообщений
`operation.*` не шлёт (V/11.5, `VMS/11-backend/spec/11.5-backend.norms.md:85`). ADR-0094 «C» (`decisions/0094-…:129`–`132`)
отложил групповые операции отдельным ADR.

Что у `backend` уже есть рядом. Групповые записи `POST /devices`, `POST /devices/update`, `POST /objects/delete`
синхронны: элементы по порядку, у каждого свой пакет B9 и сверка версии элемента, ответ `{done, failed}` в том же
запросе (V/11.4 Н1.5, `VMS/11-backend/spec/11.4-backend.norms.md:185`); память группового ключа — своя таблица
`backend/repeats/<h>`, итог шага ложится в пакете шага (V/11.4 Н1.4, `…/11.4-backend.norms.md:139`–`172`; ADR-0094 доп.
(3) п. 4, доп. (9) п. 3). Операция отличается тем, что живёт дольше запроса: 202 сразу, шаги потом, пауза и отмена —
другими запросами, ход — в поток.

Главное ограничение: у `backend` нет удостоверения человека вне открытого запроса. Билет B1 мёртв, как только ответ
человеку закрыт (ADR-0094 B1, `decisions/0094-…:96`), а долгоживущее делегирование снято ревью как блокер (там же,
`:29`–`32`). Обратный вызов по билету проходит ту же проверку, что токен двери: отзыв `jti`, срок, ключ (ADR-0094 доп.
(3) п. 1, `decisions/0094-…:218`–`221`). Значит, после ответа 202 `backend` сам писать строки `cam`, `rec`, `det` от
имени человека не может.

## Decision Drivers
* Права решает консоль: каждый шаг идёт правами человека, проверенными заново на этом шаге (ADR-0094 Decision Drivers).
* У воркера нет удостоверения человека, которое живёт дольше одного вызова (ADR-0094 B1, блокер Б-1/Б-2), а билет
  проверяет отзыв, срок и ключ токена без исключений (ADR-0094 доп. (3) п. 1).
* Перевод вида consolem в строки подсистем — знание VMS, его место — `backend` (ADR-0094 A6, `mapping.tsv`); консоль
  платформы его не знает.
* Операция переживает закрытие браузера и перезапуск экземпляра консоли; шаг не исполняется дважды, устаревший ведущий
  ничего не пишет.
* Чужая правка не затирается: шаг пишет с ожидаемой версией (B4), пакетом всё или ничего (B9).
* Пароль устройства не лежит в хранилище открытым и не живёт дольше, чем нужен.
* Нагрузка ограничена: пределы шагов, одновременных операций, срок и число попыток вызова шага.
* Не делать того, чего контракт не требует: объявление возможностей позволяет отдать часть операций.

## Considered Options
* А. Консоль исполняет шаги сама: `backend` в запросе `POST /operations` переводит весь план в готовые пакеты B9, консоль
  хранит их и пишет по одному.
* **Б. Консоль ведёт операцию (запись, очередь, поколение, пауза, отмена, ход), шаг переводит и пишет `backend` по
  билету шага, который консоль выдаёт на один вызов шага.**
* В. `backend` ведёт и исполняет операцию сам: своя таблица операций, своя очередь между экземплярами, свой доступ к
  строкам подсистем.
* Г. Операцию ведёт браузер (WebUI или модуль консоли), как модуль сейчас ведёт групповое переименование
  (`КОНСОЛЬ-МОДУЛЬ-ПЛАТФОРМЫ.md:188`).

## Decision Outcome
Выбран вариант «Б», потому что он единственный держит три вещи вместе: права — у консоли и свежие на каждом шаге,
перевод вида — у `backend`, состояние и жизнь операции — в хранилище платформы под очередью консоли. Удостоверение
человека у воркера живёт ровно один вызов шага, как билет B1 живёт один запрос. Все три ревьюера выбор подтвердили
(разбор, вступление).

А отпадает, потому что индексы хранилища после шага неизвестны при плане: второй шаг над той же камерой (детектор,
затем камера — обычный план карточки) заранее не построить, его `cas` и стражи зависят от итога первого. В требует
удостоверения человека у воркера на всё время операции — это вариант А ADR-0094, снятый блокером; со своей учётной
записью — второй источник прав (В′ ADR-0094). Г не переживает закрытия вкладки, а `GET /operations/{id}` из другого
клиента не видит хода.

### 1. Строки операции
Семья принадлежит подсистеме, объявившей операции (у нас `backend`), пишет её консоль — как строки просьб
`<sub>/requests/*` (P/06.1 Н1.1). Рабочие имена (точные — норма P/06):

| Строка | Что в ней | Кто пишет |
|---|---|---|
| `<sub>/operations/<id>` | `{by, jti, kid, exp, created_at, finished_at, state, paused, expired, cancel, total, retry_of}` | консоль |
| `<sub>/opsteps/<id>/<i>` | тело шага без секретов, корень цели, `password_secret` | консоль (при приёме; снятие секрета — ведущий) |
| `<sub>/opdone/<id>/<i>` | итог шага `{state: ok \| fail \| cancel, code?, field?, version?, created_id?, versions}` | `backend` пакетом шага; консоль — `cancel` и сбой вызова |
| `<sub>/opcount/<id>` | счётчики `done`, `ok`, `failed`, `cancelled` | тот же пакет, что итог |
| `<sub>/opbusy/<корень>` | id операции, которая держит корень цели | консоль |
| `<sub>/operations-turn` | очередь ведущего (договор `turn.md`) | консоль |
| `<sub>/operations-epoch` | поколение ведущего | консоль, новый держатель очереди |

- `by` — автор, `jti`, `kid`, `exp` — токен, к которому операция сейчас привязана (п. 5).
- **Тело шага без секретов** (разбор, решение 1; блокер Kimi 0095-Б1). Договор запечатывания шифрует только поля
  `*_secret` (`Platform/common/contracts/sealing.md`), «тело целиком» в нём не выражается. Поэтому `backend` при приёме
  выносит пароль из `set.password` (и всякое поле секрета по таблице секретов V/11.3) в отдельное значение; консоль
  кладёт его в поле `password_secret` строки шага (запечатано договором, путь AAD `/password_secret`), тело хранит без
  него и подставляет пароль только в вызов шага. Консоль по-прежнему не знает вида шага.
- Строки тел шагов входят в обход перезапечатывания консоли (P/06.2 Н3, «перезапечатать при старте»): иначе после смены
  кольца и вывода прежнего `kid` тело незавершённой операции не откроется.
- После итога `ok` ведущий снимает `password_secret` шага: `retry-failed` нужны только тела шагов `fail`.
- **Корень цели** (разбор, А2). Разные `targetId` делят строки хранилища: версия камеры склеена из индексов `cam`, `rec`,
  `det` (V/11.4 Н1.1), `Archive` и `Volume` — одна строка тома. Поэтому `backend` при приёме называет корень каждой цели
  (камера — для себя и своих детекторов; строка тома — для `Archive` и `Volume`), а консоль хранит его непрозрачной
  строкой, как тело. Занятость и цепочка ожидаемых версий идут по корню.
- **Счётчики — своя строка** (разбор, решение 3). Её пишет пакет шага с `cas`, в том числе при отказе без записи (тогда
  пакет — две строки: итог и счётчики); итоги `cancel` консоль пишет вместе со счётчиками. Шаги одной операции идут строго
  по одному, поэтому `cas` счётчиков сам с собой не спорит. `operation.progress` читает её, а не все итоги.
- `state: run` консоль выводит при чтении: первый шаг без итога у незавершённой операции не на паузе. Шаг без итога у
  завершённой операции — `cancel` (итог `cancel` записан при завершении, п. 4).

### 2. Приём операции (`POST /operations` через `backend`)
1. **Память — первой** (V/11.4 Н1.4): строка `backend/repeats/<h>` с `op: createOperation` создаётся «начато» `cas ""`.
   Строка есть с итогом — ответ — та же операция (`openapi:8273`), даже после её первого шага или завершения; сверка
   `expectedVersions` при повторе не идёт. Наш срок памяти дольше 10 минут контракта — это строже и контракту не
   противоречит.
2. `backend` читает цели снимком и сверяет `expectedVersions`; расхождение хоть одной — 412, ничего не создано
   (`openapi:8289`). У шага `set` или `folderIds` нет версии цели в `expectedVersions` — 428 (наше чтение; «Запрос
   продукту», п. 1).
3. `backend` зовёт дверь консоли «создать операцию» по билету запроса (перечень B1 пополняется ею): тела шагов без
   секретов, значения секретов, корни целей и строку `backend/repeats/<h>` с итогом (id операции).
4. Консоль пишет тела шагов, затем **одним пакетом**: запись операции, строку счётчиков, строку
   `<sub>/opbusy/<корень>` `cas ""` на каждый корень и строку `backend/repeats/<h>` с `cas` прочитанной строки «начато»
   (разбор, Г3: память ложится вместе с операцией, как строка `repeats` в пакете шага). Корень занят незавершённой
   операцией (в том числе на паузе) — `cas ""` строки занятости не проходит, 409 `BUSY` (`openapi:1893`), ничего не
   записано. Приёмы без общих корней не спорят: строки разные.
5. Ответ — 202 с записью операции, все шаги `wait`.

Пакет приёма — **внутренняя запись консоли**: его ограничивает вес (предел тела хранилища `-max-body`, умолчание 1 МиБ,
`Platform/01-store/spec/01.3-store.norms.md:169`), а не число строк. Предел строк пакета B9 («Спецификация» предлагает
64, `decisions/inbox/2026-10-29-план-ADR-0094-B-платформа.md:96`) — у двери пакетной записи для вызывающих (разбор, А1).
Число корней операции ограничивает `OPS_STEPS_MAX` нормы так, чтобы `N + 3` строк уложились в вес. Правка P/01.1 и нормы
B9 — **[B]**, если норма B9 ещё не написана, иначе в приращении C.

`BUSY` проверяют только приём операции и `retry-failed`. Одиночные правки и групповые записи объекта в операции не
отказывают 409: их охраняет `If-Match`, а шаг операции после чужой правки получит `VERSION_MISMATCH`.

**Ограничение** (разбор, Г12 М-6; рядом с ADR-0094 доп. (3) п. 5): между сверкой `expectedVersions` (шаг 2) и пакетом
приёма (шаг 4) есть окно. Цель изменилась в нём — 202 всё равно, а шаг потом `fail VERSION_MISMATCH`.

### 3. Исполнение шага
- **Ведущий.** Ведёт одна консоль кластера на подсистему: очередь писателя по договору `Platform/common/contracts/turn.md`
  (`<sub>/operations-turn`, `TURN_TERM` 45 с, `turn.md:28`). Записи ведущего — под стражем очереди (шаг 5 договора).
- **Поколение ведущего** (разбор, А3 (б)). Новый держатель очереди сразу после взятия переписывает строку
  `<sub>/operations-epoch` (`cas`, под стражем очереди) — это и есть барьер договора `turn`. Билет шага помнит её индекс,
  консоль добавляет **страж поколения** в пакет шага. Продление очереди поколения не меняет, поэтому параллельные шаги и
  продления не спорят (договор запрещает продление параллельно целевой записи, `turn.md:77`–`83`). Отказ по стражу
  поколения консоль отдаёт отдельным словом; `backend` тогда не пишет итог `fail VERSION_MISMATCH`, а заканчивает вызов.
  Операция завершается, только когда её вызов шага закончен или билет мёртв; итоги `cancel` консоль пишет `cas ""`, и
  поздний пакет прежнего ведущего упирается в них.
- **Шаг.** Ведущий читает строку итога; итог есть — шаг окончен. Иначе — вызов шага к экземпляру `backend` по
  транспорту B1 с **билетом шага**, телом шага и подставленным паролем.
- **Лист сервера** (разбор, Г10). Консоль в вызове шага проверяет серверный лист `backend`: роль `backend` и экземпляр —
  адресат билета. Чужой лист — вызов не идёт, тело и пароль не уходят. Та же проверка нужна передаче B1 второго вида, где
  тело `PATCH /devices` несёт пароль, — дополнением к ADR-0094 доп. (6) **[B]**, «Спецификации» в план B (P/06.3,
  `gate-and-pass`).
- **Билет шага** — второй вид билета B1: консоль помнит `{user: by, jti, kid, exp, операция, шаг, экземпляр-адресат,
  индекс поколения}`; билет живёт, пока открыт вызов шага. Обратные вызовы по нему — все проверки B1 и доп. (3) п. 1:
  лист роли, перечень дверей, свежий `may`, отзыв `jti`, **срок `exp`** и **ключ** (`kid` — в принятом наборе
  `domain/keys`, его `until` не прошёл); вместо «открыт внешний запрос человека» — «открыт вызов шага». Билет шага даёт
  запись ровно одной строки итога и строки счётчиков своей операции.
- **Как `backend` исполняет шаг.** Так же, как элемент `POST /devices/update` (V/11.4 Н1.3, Н1.5): снимок частей, сверка
  версии корня с ожидаемой, один пакет B9 с `cas` из снимка, стражами частей и стражем поколения. **В том же пакете** —
  строка итога `cas ""` (с версиями объектов корня после шага) и строка счётчиков с `cas`. Итог и запись ложатся вместе
  или не ложатся — тем же приёмом, что строка `backend/repeats` у групповых записей (V/11.4 Н1.4 шаг 3).
- **Итог пишет `backend`** (разбор, Г11): пакетом шага при записи; при отказе без записи (версия не та,
  `NOT_SUPPORTED`, `PERMISSION_DENIED`, `DEVICE_OFFLINE`) — пакетом из двух строк, итог `fail` с кодом `ProblemCode` и
  счётчики. Консоль пишет только итоги `cancel` и итог сбоя вызова (ниже).
- Пакет шага ответил 412 по стражу частей — `backend` перечитывает строку итога: итог есть (его записал другой
  исполнитель) — шаг окончен; нет — итог `fail` `VERSION_MISMATCH`.
- Ключ `Idempotency-Key` пакета шага — hex SHA-256 от id операции и номера шага: потерянный ответ на тот же пакет
  получает сохранённый ответ памяти B3, а не ложный 412.
- **Ожидаемая версия шага** (разбор, Г5, А2): из `expectedVersions`, пока ни один прежний шаг операции не писал строк
  этого корня; иначе — подтверждённая версия из итога последнего **успешного** шага над корнем. После отказа без записи
  ожидаемая версия не меняется. Чужую новую версию ведущий не перечитывает как согласие человека. `version` у шага
  `create` — версия цели (камеры) после шага, id созданного — `created_id`.
- **Срок и попытки вызова** (разбор, Г7). `OPS_STEP_WAIT` — срок вызова шага; по истечении билет мёртв, повтор — тем же
  ключом пакета. `OPS_STEP_TRIES` — подряд неудачных вызовов без итога. Исчерпаны — консоль пишет итог `fail` с кодом
  сбоя («Запрос продукту», п. 4), операция идёт дальше: ядовитый шаг не держит корни до `OPS_RUN_MAX`. Ряды
  `<sub>_op_step_retries_total`, `<sub>_op_step_poisoned_total`.
- **Пароль не открылся** — итог `fail` с тем же кодом сбоя, операция идёт дальше.
- Шаг `set` с `ServerPatch` или `DomainPatch` — итог `fail` `NOT_SUPPORTED`: эти правки у нас `NO_ROUTE` (V/11.2 № 6,
  13), а код «в групповых — по объекту» (`openapi:8487`). Шаг `folderIds` до норм ADR-0096 — `fail` `NOT_SUPPORTED`,
  `field: folderIds`; после — пакет со строками папок и обратного членства по ADR-0096.
- Шаги одной операции идут строго по одному (`openapi:1893`). Разные операции ведущий ведёт одновременно, не больше
  `OPS_PARALLEL`.

### 4. Пауза, продолжение, отмена, повтор
- `pause`, `resume`, `cancel` — двери консоли, `backend` зовёт их по билету запроса (перечень B1 пополняется ими). Консоль
  правит запись с `cas`: `paused: true | false`, `cancel: true`. У завершённой операции — 409 (контракт даёт 409 у всех
  трёх, `openapi:1980`–`2111`). Текущий шаг доигрывает: флаг читается перед следующим шагом.
- `cancel` отменяет и ожидание паузы: ведущий завершает операцию одним пакетом — `state: done`, итоги `cancel`
  оставшихся шагов `cas ""` со счётчиками, снятие строк `opbusy` её корней.
- `retry-failed` — новая операция с `retry_of`; автор — тот, кто повторяет; шаги — копии тел и секретов шагов `fail`
  прежней. Каждый повторённый шаг берёт ту ожидаемую версию, которую имел в прежней операции в момент своего исполнения:
  версию после последнего успешного шага над тем же корнем, иначе из `expectedVersions` (разбор, Г5; наше чтение —
  «Запрос продукту», п. 2). 412 у повтора в контракте нет (`openapi:2133`–`2149`), поэтому сверка идёт шагом: корень
  изменился — шаг снова `fail` `VERSION_MISMATCH`, человек строит новый план. Корень занят — 409 `BUSY`;
  `retry-failed` у незавершённой операции — 409.
- **`revert` не объявляется** (404 `NO_ROUTE`, `revertOf` всегда `null`; решение владельца В2). «До» шага с паролем
  требует либо открытого пароля в хранилище, либо записи запечатанного значения мимо двери (консоль запечатывает при
  записи сама, P/06.2); откат шага `create` оставляет надгробия иными, чем «до». Вынос пароля в `password_secret` этого не
  меняет. Итог хранит версии после шага, поэтому откат можно добавить позже без смены формы.

### 5. Права и срок токена
- **Шаги — правом автора.** Каждый обратный вызов шага проверяет свежий `may` автора `by` на каждой строке пакета (B9,
  `decisions/0094-…:351`).
- **Видимость — `view`, управление — `edit`** (решение владельца В3; разбор, решение 4). Операцию видит тот, у кого
  `view` на таблицу операций подсистемы (грант), как прочие строки; лента B2 не меняется. `pause`, `resume`, `cancel`,
  `retry-failed` — по `edit` на ту же таблицу. Без `view` — 404 `NOT_FOUND` («не видна текущему администратору»).
- **Срок `exp` — пауза** (решение владельца В1, вариант (б)). Билет шага проверяет срок, как велит ADR-0094 доп. (3) п. 1,
  исключения нет. Ведущий перед шагом видит, что `exp` привязанного токена прошёл, и пишет в запись `expired: true`;
  контракт видит `state: paused`. Любой запрос **автора** к операции по его билету (чтение, поток хода, `pause`,
  `resume`, `cancel`) перепривязывает её к нынешнему токену: `jti`, `kid`, `exp` в записи заменяются, `expired`
  снимается. Человеческая пауза (`paused`) от перепривязки не снимается. Пока вкладка автора открыта, операция идёт;
  закрыта — идёт до срока последнего токена и ждёт автора.
- **Отзыв, выключение, ключ — событием** (разбор, решение 6). Ведущий каждый такт обходит незавершённые операции, в том
  числе на паузе, и пишет `cancel: true`, если отозван их `jti`, выключен автор, `kid` вне принятого набора или истёк
  `OPS_RUN_MAX`. Так отмена записана в строку и не пропадает после `prune` записи отзыва (`exp + 60`,
  `Platform/common/contracts/keys.md:134`–`136`). Отзыв, пришедший, пока консоль недоступна дольше `exp + 60`, не
  теряет силы: операция к этому времени уже на паузе по `exp` и продолжится только запросом автора с новым токеном.
- **Код шага при выключении** (разбор, Г11): шаг, чей `may` уже отказал, — `fail PERMISSION_DENIED`; оставшиеся —
  `cancel`.
- Журнал консоли: на каждый шаг — `user: by`, `via: backend/<экземпляр>`, `op: <id>/<i>` (как журнал B1); перепривязка —
  своим видом с прежним и новым `jti`.

### 6. Ход в поток
- Строки операции — строки консоли; лента `/changes` (B2) охватывает их с обычным фильтром `view`.
- `backend` в `GET /stream` переводит сообщение о строке итога в `operation.progress` (шаг и счётчики из строки
  `opcount`), запись с `state: done` — в `operation.finished` (`openapi:7406`–`7407`). Значение он читает обычной
  дверью, как всё в B2.
- Порядок шагов в потоке не обещан сверх B2: клиент берёт истину из `GET /operations/{id}`.

### 7. Срок, перезапуск, нагрузка
- **Перезапуск.** Ведущий упал — очередь берёт другой экземпляр через `TURN_TERM` и переписывает поколение. Шаг в работе
  он не повторяет вслепую: есть строка итога — шаг окончен; нет — вызов шага тем же ключом пакета. Поздний пакет прежнего
  ведущего отсекает страж поколения. Упал экземпляр `backend` — вызов уходит другому тем же ключом.
- **Жнец** — новая работа жнеца консоли P/06.4 Н3 с периодом в норме (не `sweep` P/06.1 Н1.5: тот снимает только в окне
  обслуживания). Он снимает завершённую операцию со всеми строками через `OPS_KEEP` после `finished_at`; тела шагов без
  записи операции; строку `opbusy`, чья операция завершена или отсутствует.
- **Незавершённая операция** живёт не дольше `OPS_RUN_MAX`; дальше — отмена событием (п. 5). Без этого операция на
  паузе держала бы корни занятыми вечно.
- **Пределы:** шагов в операции — `OPS_STEPS_MAX` (и вес пакета приёма, п. 2); незавершённых операций на подсистему —
  `OPS_ACTIVE_MAX`, на человека — `OPS_PER_PERSON_MAX`; одновременно ведомых — `OPS_PARALLEL`. Сверх предела — отказ
  приёма 422 `VALIDATION_FAILED`, `field: items`.

### 8. Манифест и граница
- Подсистема объявляет операции в манифесте: маршрут вызова шага (не входит в маршруты `door.pass`, браузеру
  недоступен), пределы в пределах потолков нормы. Грамматика — P/02.1 («Спецификация»).
- Новые семьи `operations`, `opsteps`, `opdone`, `opcount`, `opbusy`, `operations-turn`, `operations-epoch` — в
  запрещённые имена `unit.rows` и таблиц (P/02.1 Н1.2а) и в образцы роли `console` (P/02.5 Н1.4); очередь операций —
  столбцом в «Различия очередей» договора `turn` (форма `holder`, что под стражем, когда отдаётся).
- Перечень обратного вызова B1 пополняется дверями: «создать операцию», чтение записи, итогов и счётчиков (для
  `GET /operations/{id}`), `pause`, `resume`, `cancel`, `retry-failed`.
- Консоль не знает, что такое шаг: она хранит тело и корень непрозрачными, ведёт очередь, выдаёт билет. Поэтому механизм
  годится и другим подсистемам, а модуль консоли сможет вести через него свои групповые правки, когда это решат
  отдельно (`КОНСОЛЬ-МОДУЛЬ-ПЛАТФОРМЫ.md:188` — сейчас групповое переименование ведёт браузер).

### 9. Порядок
1. Нормы и код — отдельным приращением **после зачёта приращения B** (ADR-0094 B1–B9), не раньше: решение стоит на B1
   (билет), B2 (лента), B3 (память), B4 (версии), B9 (пакет), а B — на Go GREEN 01–10 (ADR-0094 «Порядок» п. 1).
2. В план B — «Спецификации» сейчас (**[B]**): лист сервера в передаче B1 второго вида (дополнение к ADR-0094 доп. (6));
   предел пакета B9 строками только у двери, у внутренних пакетов консоли — вес (если норма B9 ещё не написана).
3. Платформа — «Спецификация»: P/06 (семьи, двери, ведущий, поколение, билет шага, жнец, пределы, перезапечатывание
   строк шагов), P/02.1 (ключ манифеста, запрещённые имена), P/02.5 (образцы `console`), договоры `turn`,
   `gate-and-pass`, перечень обратного вызова `backend`.
4. Урок V/11 — «Спецификация VMS»: V/11.2 (№ 38–43 — «переводится», № 44 — `NO_ROUTE`), V/11.3 (вынос секретов шага),
   V/11.4 (шаг операции, корень цели, версии корня в итоге), V/11.5 (сообщения `operation.*`), `profile.tsv` (строки
   файла 45–50 — `in`), объявление `capabilities.operations`.
5. Шаг `folderIds` — после норм ADR-0096.
6. Запрос продукту — одним письмом через «Консоль», отправляет владелец (разбор, «Порядок» п. 4).

### Consequences
* Good, because права остаются у консоли и проверяются заново на каждом шаге, а удостоверение человека у воркера живёт
  один вызов шага; срок, ключ и отзыв токена проверяются без исключений из ADR-0094 доп. (3) п. 1.
* Good, because шаг операции у `backend` — та же процедура, что элемент `/devices/update`: снимок, сверка, пакет B9,
  итог в пакете; второго способа писать устройство нет.
* Good, because шаг не исполняется дважды и устаревший ведущий ничего не пишет: строка итога в пакете шага, ключ пакета
  из id операции и страж поколения переживают перезапуск и консоли, и `backend`.
* Good, because пароль не лежит открытым нигде, а запечатанный живёт только до итога `ok`.
* Good, because механизм общий: консоль не знает вида consolem, подсистема объявляет шаг манифестом.
* Good, because второй админ видит, какая операция держит корень при 409 `BUSY`.
* Bad, because у консоли много нового: семьи операций, ведущий под очередью и поколением, второй вид билета, вызов
  воркера по инициативе консоли, перепривязка, новая работа жнеца.
* Bad, because долгая операция при закрытой вкладке автора встаёт на паузу на `exp` и ждёт автора.
* Bad, because каждый шаг — вызов консоли к `backend` и обратные вызовы к консоли, а пакет шага несёт ещё строки итога и
  счётчиков: на тысячу шагов это тысячи проходов транспорта B1 и тысячи записей счётчиков.
* Bad, because откат (`revert`) не объявлен: WebUI спрячет кнопку «Отменить выполненное», тесты отката вне профиля.
* Bad, because id корней и коды шагов видны обладателю `view` на таблицу операций, даже для единиц вне его `view`.
* Neutral, because `retry-failed` не помогает шагам `VERSION_MISMATCH` — так и задумано: чужая правка не затирается.
* Neutral, because окно между сверкой `expectedVersions` и пакетом приёма даёт 202 с шагом `fail VERSION_MISMATCH`.

### Confirmation
* Приёмка P/06 (новые сценарии, «Спецификация»):
  - приём: потерянный 202, повтор на другом экземпляре `backend` — та же операция, шаги не исполнены дважды; два
    одновременных исполнителя одного ключа; повтор ключа после завершения операции — та же операция;
  - занятость: корень в незавершённой операции (в том числе на паузе) — 409 `BUSY`, ничего не записано; два приёма без
    общих корней проходят оба; два шага одной операции над камерой и её детектором — один корень;
  - версии: `fail → set`, `ok → fail → set` над одним корнем, те же случаи в `retry-failed`, чужая правка между шагами;
  - пауза посреди шага — шаг доигрывает, следующий не начат; продолжение; отмена — оставшиеся `cancel`, выполненные
    остались; отмена на паузе; 409 у завершённой и `retry-failed` у незавершённой;
  - перезапуск ведущего во время шага — новый держатель переписал поколение; итог есть — шаг не исполнен снова; итога
    нет — доведён тем же ключом; потерянный ответ пакета — сохранённый ответ B3, а не 412; ведущий на паузе процесса,
    другой взял очередь, `cancel` — поздний пакет прежнего отказан по стражу поколения, итог остаётся `cancel`;
  - срок токена: на `exp` операция встаёт на паузу; запрос автора с новым токеном перепривязывает её и снимает
    `expired`; запрос не автора не перепривязывает; отзыв во время паузы — отмена; `resume` после `exp + 60` у отменённой —
    409;
  - права: человек выключен посреди операции — шаг, чей `may` отказал, `fail PERMISSION_DENIED`, оставшиеся `cancel`;
    `kid` выведен — отмена; без `view` — 404; без `edit` — `pause` отказан; обратный вызов по билету шага после конца
    вызова — 401; билет шага на итог чужого шага — 403;
  - ядовитый шаг: `OPS_STEP_TRIES` неудачных вызовов — итог `fail`, операция идёт дальше; ряды
    `<sub>_op_step_retries_total`, `<sub>_op_step_poisoned_total`;
  - секреты: сырое чтение хранилища — открытого пароля нет нигде, после `ok` нет и запечатанного; после смены кольца
    тело незавершённой операции открывается; пароль не открылся — итог `fail`;
  - лист сервера: на стенде с TLS лист другого экземпляра `backend` — вызов шага не идёт;
  - пределы шагов и операций, вес пакета приёма; жнец снимает завершённую операцию после `OPS_KEEP`, тела без записи и
    висячие строки `opbusy`.
* Приёмка V/11: тесты API consolem тега `operations` на закреплённом коммите в профиле (строки файла 45–50 `profile.tsv`
  — `in`, строка 51 `revert` — `out`); имена файлов тестов — [TODO: уточнить по коммиту `ef7175b`].
* Векторы: ключ пакета шага (id операции, номер → hex SHA-256); ожидаемая версия шага по цепочке корня.
* Ревью — Codex, Claude, Kimi; разбор — `decisions/inbox/2026-10-30-ревью-ADR-0095-0096-разбор.md`.

## Pros and Cons of the Options

### А. Консоль исполняет заранее переведённые пакеты
* Good, because консоль ведёт и пишет сама, вызова воркера по инициативе консоли нет.
* Good, because шаг — обычный пакет B9 с `cas`; при совпавших версиях заранее переведённый пакет равен пакету,
  переведённому в момент шага.
* Bad, because индексы хранилища после шага неизвестны при плане: второй шаг над тем же корнем заранее не построить.
* Bad, because перевод тысячи шагов — внутри одного запроса `POST /operations`, а хранить приходится строки целиком на
  всё время операции.
* Bad, because отказ шага консоль видит словом платформы; перевести его в `ProblemCode` может только `backend` при чтении.

### Б. Консоль ведёт, `backend` переводит и пишет шаг по билету шага
* Good, because перевод — в момент шага по свежему снимку, тем же кодом, что групповые записи.
* Good, because права свежие на каждом шаге, удостоверение у воркера — на один вызов, проверки токена — без исключений.
* Good, because консоль не знает вида consolem; механизм годится другим подсистемам.
* Bad, because нужны второй вид билета, вызов воркера по инициативе консоли, поколение ведущего и перепривязка.
* Bad, because `backend` должен быть жив, чтобы операция шла (без него шаги ждут, затем `fail` по `OPS_STEP_TRIES`).

### В. `backend` ведёт и исполняет сам
* Good, because платформа почти не меняется: своя таблица и своя очередь у `backend`.
* Bad, because воркеру нужно удостоверение человека на минуты — снято ревью ADR-0094 как блокер; своя учётная запись —
  второй источник прав (В′ ADR-0094).
* Bad, because «воркер без состояния вне хранилища» (ADR-0094 доп. (3) п. 4) становится воркером с ведущим и очередью.

### Г. Операцию ведёт браузер
* Good, because ничего нового на сервере: так модуль уже ведёт групповое переименование.
* Bad, because закрытая вкладка останавливает операцию, а `GET /operations/{id}` из другого клиента не видит хода.
* Bad, because контракт требует 202 и ход в поток — это сервер, не клиент.
