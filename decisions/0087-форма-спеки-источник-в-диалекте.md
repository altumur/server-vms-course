# Форма спеки — источник в узком диалекте; загрузчики и раздел урока строятся из него; заменяет ADR-0085

## Context and Problem Statement
Класс системы: платформенная система — строгий загрузчик спеки подсистемы (манифеста, ADR-0086), урок М10/2 (в стадии
B — `Platform/02-installer/`).

Форму спеки (М10/2 Н1.2, Н1.2а, Н1.3, Н1.4 и таблица скаляров Н1.1) сейчас описывает проза, и каждая реализация
переводит её в код сама: сверка уроков 1–2 — 62 расхождения при зелёной приёмке, чистая комната — 31 догадка, ревью
урока 2 — 25 находок о форме. ADR-0085 поставил рядом схему JSON Schema как проверку в `check_spec`; ревью ADR-0085 и
записка «Схема — источник формы» показали, что так проверяется схема против корпуса, а не проза: третье описание формы,
которое держат руками и которое ничего не даёт реализациям.

Два пилота (`/Users/murat/w2c/cammeta-schema-pilot/`):
* вариант B — схема под чужими валидатором и парсером (`REPORT.md`): библиотеки расходятся с нормой и между собой;
* вариант C — источник в узком диалекте, код строится из него (`source/REPORT.md`, `a7b06e8`): корпус 466/466,
  формы Python и Go на одном дереве 831/831 вместе с путями, особых веток ноль, у построенных загрузчиков в зависимостях
  только стандартная библиотека; оставшиеся расхождения — `yaml.v3` в слое текста.

## Decision Drivers
* форма записывается один раз и не расходится ни с уроком, ни с кодом;
* в загрузчике нет чужого кода, решающего вердикт (выводы пилота B);
* класс и путь отказа задаёт наша запись, а не дерево ошибок библиотеки;
* правка формы — одна правка, а не перевод в двух языках.

## Considered Options
* проза — источник, схема — проверка рядом (ADR-0085);
* схема — норма, исполняют чужие валидатор и парсер (вариант B);
* источник в узком диалекте, загрузчики и раздел урока строятся из него (вариант C);
* без схемы, проза и корпус.

## Decision Outcome
Выбран вариант C — по пилоту он единственный даёт одну запись формы без чужого кода в загрузчике.

1. **Источник формы** — три файла урока-владельца: `*.form.yaml` (форма Н1.2–Н1.3 в диалекте), `*.references.tsv`
   (ссылки Н1.4 и отношения класса value), `*.scalars.tsv` (таблица скаляров Н1.1). Смысл ключей — `description` со
   ссылкой на урок. Байты — «Спецификация» (ADR-0080 доп. 16). Источник входит в выгрузку: это норма.
2. **Диалект** — `DIALECT.md` урока: закрытый перечень слов узла и правил, язык отношений, правило чисел (целое —
   только целый знак), `pattern` — подмножество ASCII без просмотра вперёд, порядок слоёв, класс отказа как свойство
   правила (`x-class`), путь отказа. **Словарь заморожен**: новое слово — решением владельца.
3. **Урок 2** включает раздел формы, построенный из источника, целиком; связующий текст урока пишется руками.
   `check_spec` строит раздел и сверяет его с уроком байт в байт, прогоняет корпус через построенный загрузчик и все
   спеки курса.
4. **Слой текста** (подмножество YAML Н1.1) — свой код каждой реализации, без стандартных парсеров YAML; его держат
   корпус (`c2_*`…`c6_*`) и сверки.
5. **Реализации** строят загрузчик формы из источника (построитель или интерпретатор диалекта на стандартной
   библиотеке).
6. **Когда.** Стадия B ADR-0083 (урок 2 переписывается и переезжает, вместе с переходом ADR-0086 — последним коммитом
   B); стадия C — генераторы строят загрузчики из источника. До того нормы урока 2 — проза, а `check_spec` со схемой
   ADR-0085 работает как сейчас.
7. **Схемы строк хранилища** — тот же диалект и принцип «источник»; решение — отдельным ADR после перевода формы спеки
   (пилот строк: `data/REPORT-data.md`).

### Consequences
* Good, because форма записана один раз: урок и оба загрузчика строятся из неё и не расходятся.
* Good, because в загрузчике нет валидатора JSON Schema и парсера YAML; дефект построенного кода чинится у нас.
* Good, because класс и путь отказа заданы записью: переводчика дерева ошибок нет.
* Good, because новый язык получает построитель и корпус, а не 258 строк прозы для угадывания.
* Bad, because источник формы длиннее прозы (около 900 строк против 258), построенный раздел урока вдвое длиннее.
* Bad, because генераторам нужен построитель или интерпретатор диалекта (600–900 строк на язык) и свой слой текста.
* Bad, because язык отношений — главный риск: разбор выражений около 260 строк; каждое новое слово — работа в каждом
  построителе.
* Bad, because корпус держит 73 из 111 отношений — до перехода нужны недостающие случаи.
* Bad, because «Спецификация» начинает правку формы с источника, а не с прозы; продукт переходит, когда возобновится
  (долг продукта).

### Confirmation
* Загрузчики Python и Go, построенные из источника, проходят весь корпус урока 2 и совпадают на всех вариантах сверки
  (831) вместе с путями.
* В зависимостях построенных загрузчиков нет валидатора JSON Schema и стандартного парсера YAML.
* `check_spec` строит раздел формы и находит его в уроке байт в байт; корпус и все спеки курса проходят через построенный
  загрузчик.
* Корпус держит каждую строку `references.tsv` хотя бы одним случаем.
* Следующие прогоны ревью урока 2 не находят расхождений прозы формы с источником.

## Pros and Cons of the Options

### проза — источник, схема — проверка (ADR-0085)
* Good, because реализации не трогаются.
* Bad, because прозу не проверяет; третье описание формы держат руками; реализациям ничего не даёт.

### схема — норма под чужими библиотеками (B)
* Bad, because по пилоту ни одно условие перехода не выполнено: библиотеки расходятся с нормой и между собой.

### вариант C
* см. Consequences.

### без схемы
* Good, because нет новой работы.
* Bad, because каждая реализация продолжает переводить прозу; расхождения находятся только после ошибки.
