# Этапы реализации урока — форма `forms/stages.tsv`

## Context and Problem Statement

README реализации урока (`spec/*.README.md`) содержит раздел «Order of work» — порядок работы для исполнителя. В P/01 это 7 шагов. Цикл MiniMax в попытках 15–16 вёл модель по вехам, которые «Архитектор» сам придумал в задании, а с этим порядком не сверил. Сверка показала три беды:
- шаг 1 — «Read the norms of the chapters in full». Модель исполняет его буквально и 80–100 ходов читает, хотя нормы уже лежат у неё в голове;
- у шагов нет проверяемого конца;
- демон, без которого не идёт приёмка 1.1, по README появляется только в главе 1.3.

## Decision Drivers

* Одни этапы для всех исполнителей: человека, линий Codex и цикла MiniMax.
* У каждого этапа — проверка конца, которую видит машина.
* Ранние этапы проверяются своими тестами, а не приёмкой: приёмке нужен готовый стенд.

## Considered Options

* Вехи в задании цикла — расходятся с уроком (попытки 15, 16).
* Проза «Order of work» — у шагов нет проверяемого конца.
* Таблица этапов урока, которую читает цикл, — выбран.

## Decision Outcome

1. **Форма** `forms/stages.tsv` урока (раскладка ADR-0124), рядом с README реализации. Форма ADR-0120 «таблица». Столбцы:
   - `n` — номер этапа по порядку;
   - `stage` — имя (латиница);
   - `goal` — цель одной строкой, по-английски;
   - `norms` — ссылки на разделы норм (номера и якоря английского источника);
   - `gate` — проверка конца закрытого вида:
     - `own_tests` — свои тесты реализации проходят, и среди них есть тесты этого этапа;
     - `build` — сборка профиля проходит;
     - `accept:<цель>>=<N>` — приёмка цели урока даёт не меньше N проверок;
     - `accept:<цель>:<сценарии>` — названные сценарии проходят целиком;
   - `budget` — ориентир усилия в ходах цикла (для людей — справочно);
   - `depends` — номера этапов, без которых этот не начинается.
2. **README «Order of work»** ссылается на таблицу и её не повторяет (как у таблицы проверок, ADR-0120 доп. (5) п. 5, ADR-0125 доп. (1) п. 5). Шаг «прочитать нормы целиком» уходит из этапов: чтение норм — общее правило исполнителя, а не этап.
3. **Первым этапом урока с демоном** идёт запуск: процесс стартует по профилю и отвечает на один маршрут (`accept:…>=1`). Раньше него — только этапы с `own_tests`.
4. **Цикл MiniMax** берёт вехи из `forms/stages.tsv` урока, а не из задания. Задание называет только урок, цели приёмки и пределы. Генератор вех — `loop.py`.
5. **Сверка.** `check_spec` судит форму: номера подряд, закрытый вид `gate`, цели приёмки — из описи урока, ссылки `norms` ведут на существующие якоря, `depends` — только на прежние этапы.
6. **Порядок и доли.**
   - P/01 — первым, после вливания перераскладки (ADR-0124), «Спецификация».
   - Затем уроки платформы по мере попыток.
   - VMS — «Спецификация VMS», когда до VMS дойдут попытки.
   - Цикл и сверка в `check_spec` — «Архитектор».
   - Ревью формы — review-claude и Codex.

### Consequences

* Хорошо: один порядок работы у всех исполнителей. Вехи цикла выводятся из урока. У каждого этапа есть машинный конец.
* Плохо: ещё одна форма на урок и её сверка.
* Предел: таблица не учит писать код. Она задаёт порядок и проверку, а `budget` — только ориентир.

## Дополнение (1), 2026-11-04 — ревью: review-claude (`РЕВЬЮ-ADR-0126-Claude.md`, 3554c715d; Б 0 С 5 М 3), Codex (`РЕВЬЮ-ADR-0126-Codex.md`, 46add96d9; Б 0 С 3 М 1); вопросы «Спецификации» (`cammeta-status/ADR-0126-этапы-P01-предложение.md`); решения «Архитектора»

1. **Свои тесты этапа (С1 обоих).** Вид `own_tests` заменяется двумя.
   - `tests:<stage>` — свои тесты реализации с именем этапа. Имя по соглашению языка: у Go — `Test<Stage>_…`. Судья запускает только их (у Go — `go test -run '^Test<Stage>_' -json`) и требует хотя бы один исполненный и пройденный тест без падений. Команда — в профиле языка цикла (в задании), не в курсе.
   - `vectors:<пакет>` — векторы урока (`jcs`, `rights-evaluator`, пробы `write-checks`) через команду векторов реализации. Это независимый судья для этапов до демона.
2. **Проверка конца — по сценариям курса (С2 Claude, М1 Codex).**
   - Основной вид — `accept:<глава>:<сценарии>`: глава — каталог приёмки урока (`1.1`, `1.2`, `1.3`), сценарии — имена из `scenarios.tsv` этой главы через запятую или `*` (все применимые).
   - Порог `accept:<глава>>=N` убран: N зависел от описи раннера, которой нет в курсе.
   - `check_spec` проверяет: сценарии существуют, выбор не пуст, каждый применим к профилю.
   - Этап закрыт, когда держатся его проверка и проверки всех прежних этапов.
3. **Форма — план, а не норма (С3 Claude).** `stages.tsv` — один из возможных порядков, как и README («one possible order»). Нормой он не служит. Советы README («FORMAT первым», `delete` против пустого списка, `uint64` в status, стенды 1.3) остаются прозой в разделе советов README. Правило «нормы читаются целиком» — общее правило исполнителя в разделе «Inputs», а не этап.
4. **Усилие (С4 Claude, С3 Codex).** Колонки `budget` в форме нет. Вместо неё `weight` — относительный вес этапа, целое 1–5: людям для плана, циклу как подсказка. Предел ходов вехи — жёсткий (ADR-0083 доп. (89) п. 3). Его задаёт задание цикла по `weight`, и при расхождении задание старше. Правка предела — правка обвеса, а не курса.
5. **Попытка на часть урока (С2 Codex).** Задание называет этапы попытки списком имён из формы. Цикл проверяет, что их `depends` входят в список или уже закрыты пакетом. Этапы вне списка не ставятся.
6. **Пакет Б (С5 Claude).** Колонка `kit` — какая часть пакета закрывает этап или его часть (например, `writecheck`). В попытке с пакетом этап, закрытый пакетом, проверяется, но не поручается. Подробности языка (путь `cmd/configstore`, имя модуля) — в профиле языка задания, не в курсе. Людям без раннера годятся `tests:` и `vectors:`.
7. **Ответы «Спецификации».**
   - (1) Цели — главы `1.1`, `1.2`, `1.3` (п. 2).
   - (2) `norms` — ссылки курса (`P/01.1 Н3`). `check_spec` разрешает их в якоря английского источника и судит, что якорь существует (М1 Claude).
   - (3) Полный этап главы — `accept:1.1:*`, а не число.
   - (4) Неприменимый этап — колонка `when`: условие CEL над ключами профиля (`keys.store_build != 'box'`). Пусто — этап применим всегда.
   - (5) Этап «чеклист и описание реализации» в форму не входит: машинного конца у него нет. Он остаётся в README «Done when».
8. **Грамматика (М2, М3 Claude).** `gate` — `<вид>:<аргумент>[:<аргумент>]` без пробелов. Имена сценариев — через запятую. `depends` ссылается только на `n` прежних строк. `check_spec` судит грамматику.

## Дополнение (2), 2026-11-04 — `kit` и `when` формы P/01 (вопросы 10, 11 «Спецификации», `cammeta-status/ADR-0125-P01-вопросы.md`); решения «Архитектора»

1. **Имена частей пакета (в. 10).** `kit` — список частей через запятую, имена — генераторов ADR-0125: `writecheck` (проверки, 1), `door` (дверь из OpenAPI, 2), `flags` (разбор флагов из `daemon-flags.tsv`, 3), `refusals` (тела и слова отказов из `refusals.tsv`, 4), `tests` (тесты из векторов, 6). P/01: `model` — `writecheck`; `launch` — `flags`; `http` — `door,refusals`; остальные — `-`, пока генераторы не написаны (`check_spec` судит имя по этому перечню).
2. **`durable` (в. 11).** Ключа профиля нет и не нужно: долговечность обязательна (P/01.3 Н1.3 `durability`: выключающего её флага нет), отключение — только флагом команды «Стенд» для скорости. `when` у этапа `durable` пуст — этап применим всегда.

## Дополнение (3), 2026-11-04 — цикл кодогенерации читает `stages.tsv` (слово владельца: «утвердим форму плана разработки, которую читает цикл»); решения владельца и «Архитектора»

До сих пор вехи цикла (`minimax-loop`) были зашиты в задании и мерились числом пройденных шагов приёмки (1 → 100 → 200 → 300 → 429). Они не совпадали с порядком работы урока и не говорили, какая часть кода готова. Теперь вехи цикла — этапы формы урока.

1. **Источник вех — `forms/stages.tsv` урока из выгрузки.** Веха = этап, порядок — `n`. Задание вех не перечисляет: оно называет этапы попытки списком имён (доп. (1) п. 5), основу предела ходов и профиль языка — команды сборки, своих тестов и векторов. Подробности языка в форму не входят.
2. **Проверка этапа — `gate`**, цикл исполняет её сам:
   - `vectors:<пакет>` — команда векторов профиля на пакете урока, все векторы пройдены;
   - `tests:<этап>` — свои тесты реализации с именем этапа (у Go — `go test -run '^Test<Этап>_' -json`, имя этапа в CamelCase); хотя бы один пройден, ни одного упавшего;
   - `build` — сборка профиля;
   - `accept:<глава>:<сценарии|*>` — раннер на названных сценариях главы, все применимые шаги зелёные.

   Этап закрыт, когда держится его проверка и проверки всех прежних этапов попытки. Регресс прежнего этапа возвращает веху на него.
3. **Предел ходов этапа = 40 × `weight`** (решение владельца): `jcs` — 40, `store_core` — 120, `http` — 160, `group` — 200. Основу 40 задание может поменять; при расхождении задание старше (доп. (1) п. 4). Прежние «120 на первую, 80 на прочие» доп. (90) заменяются этим.
4. **Застревание — один сброс, потом стоп** (решение владельца). Этап не закрылся в свой предел:
   - в первый раз цикл даёт модели сводку состояния (что проверено, что красное), сжимает историю и открывает ещё один предел того же этапа;
   - во второй раз — стоп `milestone_stalled` с отчётом об этапе.
5. **Что видит модель** (решение владельца): в заметке вехи — `goal`, `norms` (ссылки курса, разрешённые в разделы английского источника) и `gate` словами («сценарии 1.1 целиком», «векторы jcs»). Вес и предел ходов модели не показываются.
6. **`kit`.** Этап, закрытый частью пакета этой попытки, цикл проверяет первым ходом, но не поручает. Если проверка такого этапа красная, это дефект пакета, а не модели: стоп с отчётом.
7. **`depends` и `when`.** Цикл ставит этап, только когда закрыты этапы из `depends`. Этап, чьё условие `when` ложно на профиле задания, выпадает из попытки, как неприменимый сценарий.
8. **Мера для отчёта** — по-прежнему шаги и пробы приёмки (`acceptance_measure`): её видят люди в паспорте попытки. Решает о вехе только `gate`.
9. **Что меняется:**
   - обвес `minimax-loop` (чтение формы, судьи по видам `gate`, сброс) — «Архитектор»;
   - `check_spec` судит форму: виды `gate`, имена сценариев, `depends`, `kit` по перечню доп. (2) п. 1, `when` компилируется (доп. (1) п. 8);
   - выгрузка несёт `forms/` урока (ADR-0124).

   Семнадцатая попытка (P/01.2, P/01.3 на CT 103, доп. (92) ADR-0083) — первая на этой форме.

## Дополнение (4), 2026-11-04 — ревью доп. (3): Codex (`РЕВЬЮ-ADR-0126-доп-3-Codex.md`, 7266acfce; Б 0 С 3 М 1), review-claude (`РЕВЬЮ-ADR-0126-доп-3-Claude.md`, 882690bd4; Б 2 С 7 М 3); выбор «Архитектора» (слово владельца: «пусть оспаривают… а ты выберешь окончательно»)

Пп. 3–5 доп. (3) ревьюеры могли оспаривать. Число 40 × `weight` и один сброс оставлены начальной политикой пилота (оба ревью); уточнены условия сброса, учёт и заметка модели.

1. **Посев — третий способ закрыть `depends`** (Б1 Claude). Задание может назвать посев: код прошлой попытки на sha. Перед первым ходом все этапы до этапов попытки судятся своим `gate`, как этапы пакета.
   - Зелёный этап посева закрыт и модели не поручается.
   - Красный этап посева — первая веха попытки с обычным пределом. Это не дефект пакета и не регресс.
   - `tests:<этап>` на посеве без тестов с этим именем — красный: модель пишет их первой вехой. Разбор шестнадцатой показал, что своих тестов у неё почти нет, так что это по делу.
   Семнадцатая — посев шестнадцатой (`p01-1-go-ct102-16-green`), этапы 1–10.
2. **Исполнимость `gate` проверяется до первого хода** (Б2 Claude, С1 обоих). Сухая проба цикла сопоставляет каждый `gate` попытки с целью раннера и её статусом `ready | blocked | not_executed`. Не `ready` — ошибка подготовки, попытка не стартует.
   - До семнадцатой раннер на CT 103 проверяет цель `P/01.3/daemon` (`stand.backup`, `stand.import`, `stand.manifest-put`) и сценарии группы (`@group-setup`, `store_build`).
   - Источник `manifest-put` (часть установщика P/02) задание называет явно.
3. **Порядок этапов P/01** (Б2 Claude). Копия (`backup`, `import`, `restore`) нужна проверке `durable`, поэтому `daemon_box` идёт раньше `durable`. «Спецификация» меняет порядок и `depends` в форме.
4. **Соответствие `gate` раннеру** (С1 Claude).
   - Глава формы `1.1` — каталог `acceptance/1` и все цели главы: `door`, `extra` и прочие. `accept:1.1:*` включает пробы `extra`.
   - Названные сценарии цикл берёт из отчёта движка по сценариям (`report.scenarios`), а не из общего `green` цели.
   - Таблица «глава → цели» — в обвесе.
   - `vectors:<пакет>` исполняется только целью раннера с адаптером профиля, как `P/01/vectors-jcs`. Драйверы для `rights-evaluator` и проб `write-checks` пишет раннер. Протокол адаптера векторов — в профиле языка задания: его видит модель (п. 9).
5. **Остановки попытки — от этапов** (С2 обоих).
   - `stalled`, `build_stalled`, `judges_exhausted` старого режима в режиме этапов сняты. Мера приёмки только пишется в паспорт.
   - Зелёный `gate` закрывает этап, а не попытку. Кандидат замораживается, когда закрыт последний этап попытки.
   - Исходы различаются: «этапы попытки закрыты» и «полный набор судей зелёный».
   - `max_turns` и `max_hours` задания — потолок попытки, старше суммы пределов этапов (С4 Claude).
6. **Пакет: полное и частичное покрытие** (С1 Codex, С3 Claude).
   - Колонка `kit` — только для этапа, который пакет закрывает целиком. Такой этап проверяется первым ходом; красный — дефект пакета, стоп.
   - Новая колонка `parts` — части пакета, которыми этап пользуется. Этап поручается модели как обычно, части названы в заметке вехи.
   - P/01: `model` — `kit writecheck`; `launch` — `parts flags`; `http` — `parts door,refusals`.
   - `kit.manifest.json` несёт `parts: [...]` именами доп. (2) п. 1, `check_spec` пакета их сверяет.
7. **Предел и вход** (С4 Claude). Первому этапу попытки — запас входа +40 ходов (чтение и план). Остальное — 40 × `weight`.
8. **Сброс** (С3 Codex, С5 Claude).
   - Последний ход предела — обязательный раунд `gate`, и только по нему решается: закрыт, сброс или стоп.
   - Сброс даётся, только если с начала этапа в его `gate` прибавилось зелёного или в `work/` есть новая запись. Иначе сразу стоп.
   - Сброс — чистый разговор (`milestone_reset`) со сводкой «что зелёно, что красно, оглавление `work/`», а не сжатие.
   - Один сброс на этап. Счёт по имени этапа хранится в состоянии и переживает обрыв и обычное `--resume`.
   - После окончательного `milestone_stalled` продолжение — новая попытка со своим паспортом. Доп. (91) п. 2 ADR-0083 в режиме этапов этим заменяется.
9. **Регресс не переносит веху** (С6 Claude). Красная проверка прежнего этапа — часть проверки текущего («держатся прежние»). Её расхождения идут в отчёт текущей вехи первыми, ходы считаются текущему этапу. Последняя фраза доп. (3) п. 2 заменяется этим.
10. **Заметка модели** (С7 Claude). `goal`, `norms`, `gate` словами плюс строка профиля языка этапа:
    - точное имя тестов (`go test -run '^TestStoreCore_'`);
    - команда или адаптер векторов;
    - путь и пакет для этапов с демоном.
    Вес и предел по-прежнему не показываются.
11. **`when`** (М1 обоих). Все `when` вычисляются до первого хода на профиле задания.
    - Допустим только boolean. Отсутствующий ключ или ошибка CEL — ошибка подготовки, а не неприменимость.
    - Профиль P/01 обязан нести `store_build`.
    - После отбора по `when` цикл заново проверяет замкнутость `depends`: этап, чья зависимость исключена, — ошибка задания.
12. **Паспорт по этапам** (оба). По каждому этапу пишутся ходы, сбросы, причины переходов, исходы `gate` и цена — по ним правится основа 40.
13. **Кто что делает:**
    - «Спецификация» — колонка `parts`, порядок `daemon_box` → `durable`, сверка `kit`/`parts` в `check_forms`;
    - раннер — драйверы векторов `rights-evaluator` и проб `write-checks`, отбор сценариев по отчёту, проверка цели `P/01.3/daemon` и группы на CT 103;
    - «Архитектор» — обвес по пп. 1, 2, 4–12;
    - генераторы пакета пишут `parts` в манифест.

## Дополнение (5), 2026-11-04 — команда векторов в пакете (Б ревью Codex исправлений обвеса, 460a42a); решение «Архитектора»

Проверка `vectors:write-checks` звала подкоманду реализации `configstore vectors {input}`. У посева (код шестнадцатой) её нет, поэтому этап `model` (`kit writecheck`) упал бы первым раундом как `kit_defect` — ещё до модели.

1. **Пакет несёт бинарь векторов `cmd/vectors`** (часть `tests`, генератор № 6): `main` из одной строки — `vectorcmd.Main`.
   - `write-checks` — через проверки пакета (`checks`);
   - `jcs`, `rights-evaluator` — через адаптер `internal/vectoradapter`, который пишет модель (заглушка пакета до неё отвечает «not implemented»).
2. **Команда векторов профиля** — `bin/vectors {input}`, а не подкоманда демона; `bin/vectors` собирает сборка профиля (артефакт `vectors`): сборка внутри команды писала бы в опечатанное дерево стенда (находка «Генераторов», 20261104T174152Z). Часть `door` пакета — каталог `internal/apidoor`: реализация может держать свой `internal/door` (у шестнадцатой — рамка HTTP). Этап, закрытый пакетом, судится без кода модели. Этапы `jcs` и `rights_eval` судятся тем же бинарём, но уже через адаптер модели.
3. Заметка вехи (доп. (4) п. 10) называет адаптер и его две функции. Подкоманда `vectors` у демона не нужна.

## Дополнение (6), 2026-11-04 — тесты этапов в форме и в цикле (слово владельца: «добавь тесты в ADR-0126»; основание — ADR-0125 доп. (3), (4))

Тесты этапа больше не пишет модель: их генерирует пакет из сценариев курса (ADR-0125 доп. (3), (4)). Здесь — что это значит для формы `stages.tsv` и для цикла.

1. **Вид проверки `tests:` с выбором сценариев.**
   - Полная форма — `tests:<этап>:<глава>:<сценарии|*>` по грамматике `accept:` (доп. (1) п. 8).
   - Короткая `tests:<этап>` остаётся для урока без части `tests` в пакете: тогда действует прежнее правило — свои тесты модели `Test<Этап>_`, ≥ 1 пройден, 0 упавших (доп. (1) п. 1).
   - Если в пакете есть часть `tests`, а сценарии не названы, это ошибка формы (`check_spec` и подготовка цикла).
2. **Чем `tests:` отличается от `accept:`.** По одним сценариям:
   - `accept:` — раннер на демоне: сокеты, стенд, сырой HTTP, все шаги;
   - `tests:` — тесты пакета в процессе через адаптер: префикс сценария до первого неисполнимого шага (ADR-0125 доп. (4) п. 2).

   `tests:` судит раньше демона — с этапа `store_core`, до `launch` и `http`. Позже тот же сценарий целиком судит `accept:`.
3. **P/01.**
   - `store_core` — `tests:store_core:1.1:<сценарии Н3>`; список даёт «Спецификация» дельтой формы.
   - Сценарии швов процесса (`@clock`, `@reopen`, `@parallel`, ADR-0125 доп. (4) п. 7) входят в `tests:` своих этапов: часы и параллельность — `store_core`, повторное открытие — `durable`.
   - Гонки — тем же судьёй с `-race -count=N` (N — в профиле языка задания).
4. **Цикл:**
   - судья `tests:` запускает только каталог тестов пакета (`internal/stagetests` или имя из манифеста пакета), не `./...`;
   - опись ожидаемых тестов — из манифеста пакета, неизменна. Свои тесты модели с тем же префиксом её не закрывают, пропущенный тест красный;
   - каталог тестов пакета и `cmd/vectors` закрыты для записи модели. Адаптер (`Open`, `Handler` поверх `apidoor.Dispatch`) — её;
   - мера `tests:` в паспорте — шаги проекции: зелёные / переведённые / исключённые. Прибавление зелёных шагов — движение для сброса (доп. (4) п. 8);
   - заметка вехи (доп. (4) п. 10) называет адаптер, его функции и команду судьи (`go test ./internal/stagetests -run '^TestStoreCore_'`).
5. **Свои тесты модели** допустимы и полезны, на этап не влияют. Обязательства модели вне сценариев — только через сценарии швов (п. 3). Отдельного этапа «напиши тесты» в форме нет.
6. **Порядок.**
   - «Генераторы» — тесты из сценариев и опись в манифесте пакета (ветка `tools/normgen-scenario-tests`).
   - «Спецификация» — дельта формы P/01 (п. 3) и сценарии швов.
   - «Архитектор» — судья `tests:` в обвесе по описи пакета и `check_spec` для полной формы `tests:`.
   - Семнадцатая идёт без этого (прежнее правило п. 1), восемнадцатая — на этом.

## Дополнение (7), 2026-11-04 — ревью доп. (6): Codex (`РЕВЬЮ-ADR-0126-доп-6-Codex.md`, 62e9ee9a8; Б 0 С 3 М 0), review-claude (`РЕВЬЮ-ADR-0126-доп-6-Claude.md`, ededfd341; Б 1 С 6 М 3); предложение швов «Спецификации» (`cammeta-status/ADR-0125-швы-P01-предложение.md`); выбор «Архитектора»

1. **Швы — в своём файле** (Б1 review-claude, С3 Codex). Сценарии над швами процесса лежат в `acceptance/<глава>/seams.tsv`: колонки как у `scenarios.tsv`, раннер файл не читает. Так `accept:*` и опись раннера не меняются, а `@clock` раннера (часы стенда) и `@clock` шва не смешиваются.
   - Грамматика директив закрыта: `@clock ±N` (`Config.Now`), `@reopen` (Close + Open на тех же данных, `Config.DataDir`), `@parallel K` (следующий шаг K раз; исходы `expect each …` | `one …; rest …`).
   - Исполнитель задан файлом: `scenarios.tsv` — раннер и тесты пакета (префикс), `seams.tsv` — только тесты пакета.
2. **Грамматика `tests:` — как у `accept:`, без имени этапа** (С review-claude). Вид `tests:<глава>:<сценарии|*>[:seams]`: имя этапа даёт строка формы, `:seams` выбирает файл швов. Полная форма — всегда; короткой формы нет.
3. **Несколько проверок у этапа — списком** (С2 Codex, С review-claude). `gate` — список через `;`. Этап закрыт, когда держатся все. Мера — по каждой отдельно.
   - P/01: `store_core` — `tests:1.1:<сценарии Н3>; tests:1.1:<швы часов и параллельности>:seams`;
   - `durable` — `tests:1.1:<швы reopen>:seams; accept:1.3:<прежние сценарии>`.

   Отдельных этапов `store_seams` и `durable_seams` нет.
4. **Новый судья включает опись этапа, а не строка `parts: tests`** (С1 Codex). Манифест пакета различает части `vectors` (тесты и команда векторов, генератор № 6 прежний) и `stagetests` (тесты этапов из сценариев). `tests:` судит опись `stagetests` этапа. Если её нет, а форма требует `tests:`, это ошибка подготовки.
   - Семнадцатая — на прежнем пакете с частью `vectors` и прежней формой P/01 из выгрузки 4ff91870: её `tests:store_core` — прежнее правило (доп. (1) п. 1). Это прямо разрешено.
5. **Договор адаптера** (С review-claude):
   - пакет даёт `Handle` (Route → Dispatch → Encode из `apidoor`) и судью;
   - модель пишет `Open(Config) (Core, error)`, `Context(call Call, header map[string]string) C`, `Close()` и методы `apidoor.Handler[C]` ядра;
   - `Config`: пределы стенда, файл прав, `Now func() time.Time`, `DataDir` и обязанность выдерживать параллельные вызовы `Handle`.

   Для `store_core` пакет несёт части `door`, `refusals` и `stagetests`. Пять методов `Handler[C]` главы 1.3 приходят заглушками пакета «not in this stage».
6. **Мелкое** (М review-claude):
   - `-race` — только на тестах с `@parallel`, и судье нужен cgo/gcc в песочнице (профиль языка; раннер ставит пакет);
   - непустую проекцию этапа судит `check_spec`;
   - префикс сценария кончается и на отказе позднего этапа (403 по файлу прав в сц. 21, 40), а `floor` на сокете (17/5, 32/5) исполним через `writecheck`.
7. **Порядок.**
   - «Спецификация» — `seams.tsv` P/01 по своему предложению (классы приняты) и дельта формы P/01 по пп. 2, 3;
   - «Генераторы» — части `vectors` / `stagetests`, адаптер п. 5, директивы швов;
   - «Архитектор» — обвес: `gate` списком, судья `tests:` по описи `stagetests`, `check_spec` для пп. 2, 3, 6.
   - Семнадцатая — без этого (п. 4).
