# ADR-0135. Урок судьи и общий движок приёмки

## Context and Problem Statement

Класс системы: платформенная система; судья — внутренний инструмент проверки курса.

Судья (программа, которая проверяет сгенерированный продукт) сейчас один — раннер. Владелец хочет получить второго, независимого, написанного MiniMax с нуля. Второй судья нужен, потому что вердикт одного судьи не отличает ошибку продукта от ошибки судьи.

Владелец прочитал P/01-часть раннера на пине `bcb22c07` (`runner/c_store.py`, `runner/c_targets.py`). Код «под урок» там — таблица и проводка, а логика лежит в общих движках. При этом часть правил есть только в коде и нет в общих протоколах приёмки. Модель не может написать судью по спецификации, в которой этих правил нет.

## Decision Drivers

* Судья нового образца должен следовать из спецификации, а не из чтения кода раннера.
* Одна строка кода под урок означает пробел спецификации и повторяется на десяти уроках.
* Проверить правильность судьи во время генерации нечем: кандидатов для этого владелец не использует.
* Проба варианта Б (ADR-0133) не должна ждать этой работы.
* Писатель общей части `spec103` сейчас держит первый блокер пути к выгрузке (`P01.10.5`).

## Considered Options

* А. `Platform/common/acceptance` становится уроком судьи, MiniMax пишет один общий движок.
* Б. MiniMax пишет отдельного судью на каждый урок.
* В. Отдельная спецификация судьи вне общей приёмки.
* Г. Оставить одного судью — раннера.

## Decision Outcome

Выбран вариант А. Общая приёмка уже описывает словарь стенда и протоколы, поэтому её дешевле довести до нормы, чем писать вторую спецификацию. Один движок переносит проверку на все уроки сразу.

1. **Урок судьи.** `Platform/common/acceptance` получает нормы, формы и якоря, как обычный урок. Состав: форматы таблиц (`scenarios.tsv`, `cases.tsv` векторов, `wire.tsv`); словарь шагов сценариев: что делает шаг и какой исход ожидается; жизненный цикл стенда: запуск ролей, готовность, остановка, сбои, каталоги; протоколы адаптеров: `stand.*`, команда векторов, швы; реестр целей; форма вердикта и отчёта; гигиена секретов.
2. **Реестр целей в спецификации таблицей.** Расширяет ADR-0083 доп. (156) п. 2: цель, владелец, движок или семейство сценариев, требуемые `stand.*` и keys, каталог приёмки, диапазон сценариев, части других уроков в стенде главы, флаги.
3. **Первый шаг — опись скрытых норм движков раннера на пине** (`harness`, `stand`, `l03`–`l11`, `m11stand`, `store_group`, `power_stand`, `pass_stand`, `c_targets`, `c_store`): всё, что есть только в коде и нет в общих протоколах.
4. **Известные скрытые нормы `c_store.py`** переходят в общую README приёмки и `PROFILE.md`: `BOX_ID`, `SERVER_NAME`, форма файла прав стендового экземпляра, правило готовности (оба сокета, 15 с), стенд P/01.2 без установщика, белый список окружения ролей формой. Наследственные `rundir` из сокета и `manifests→specs` решает Архитектор.
5. **Судья — один общий движок.** Урок — только данные. Общие движки следуют словарю, а не уроку. MiniMax пишет движок только после того, как нормы урока судьи готовы.
6. **Код под урок — пробел спецификации.** Понадобилась строка под урок — писатель исправляет спецификацию, а не судью.
7. **Обратная связь генератору только механическая,** без знания правильного вердикта: сборка; полнота: сухой режим перечисляет все цели, сценарии и строки векторов, цикл сверяет с описью J; разбор всех таблиц J; соблюдение протокола стенда и форм вызова. Годные кандидаты, мутанты и экзамен не используются.
8. **Правильность проверяется потом:** код-ревью судьи рецензентом другого провайдера, затем сверка вердиктов с нынешним раннером на кандидатах. Расхождение — ошибка судьи или пробел спецификации.
9. **Вход генератора судьи** — J без кода продуктов, корпуса вердиктов и мутантов.

### Consequences

* Good, because скрытые правила раннера становятся нормами и видны всем читателям.
* Good, because новый урок не требует нового кода судьи.
* Bad, because опись пишется по коду раннера, поэтому второй судья наследует его допущения; независимость неполная.
* Bad, because продукт и судью пишет один провайдер: независимость держится разными контекстами и отсутствием доступа к коду друг друга. Для зачёта «доказано» это ограничение (ADR-0133 доп. (13)); снимет его второй провайдер.
* Bad, because до код-ревью и сверки правильность судьи ничем не подтверждена.
* Bad, because нормы добавляют работы `spec103` и меняют общую README, которую читают фильтр выгрузки и `check_spec`.

### Confirmation

* Движок исполняет все цели P/01 без единой строки под урок; это проверяет код-ревью.
* Сухой режим перечисляет цели, сценарии и строки векторов без пропусков и лишних по описи J.
* Вердикты совпадают с раннером на кандидатах; каждое расхождение классифицировано.

## Pros and Cons of the Options

### А. Урок судьи и один движок

* Good, because работа над нормами полезна и нынешнему раннеру.
* Bad, because движок надо писать сразу широко, а проверяем его сначала только на P/01.

### Б. Судья на каждый урок

* Good, because быстрее первый результат.
* Bad, because десять судей дублируют логику, а код под урок скрывает пробелы спецификации.

### В. Отдельная спецификация судьи

* Good, because не трогает общую приёмку.
* Bad, because возникает вторая правда о тех же протоколах.

### Г. Только раннер

* Good, because не требует работы.
* Bad, because ошибку судьи не от чего отличить.

## Дополнение (2), 2026-11-09 — разбор ревью текста (решение Архитектора)

Разбор: `decisions/inbox/ревью/2026-11-09-ADR-0135-разбор.md`. Там, где расходится с основным текстом, действует это дополнение. C, M, J — срез спецификации и две его выгрузки (ADR-0133 доп. (3)): M — правила для модели продукта, J — полная для судьи.

1. **Изоляция линии судьи.** Запрет читать J (ADR-0133 доп. (3) п. 4, доп. (4) п. 7) относится к линии продукта. Линия судьи — отдельная учётная запись, ей доступен только **J-вход**: неизменяемое дерево, полученное вторым фильтром над J; идентичность — коммит и blob фильтра в паспорте генерации. В J-вход не входят код продуктов, код раннера, опись `P01.28`, корпус вердиктов и мутанты. Учётная запись линии продукта не видит J-вход, код движка и журнал линии судьи; это проверяется канарейкой по образцу ADR-0133 доп. (6) п. 7. Цикл линии судьи строит опись по J-входу, и полнота сухого режима считается по ней же.
2. **M и J внутри урока судьи.** Фильтр режет только целые файлы, поэтому реестр — два файла: `targets.tsv` (M: цель, владелец, `stand.*`, keys, абзац нормы, флаги для модели) и `targets.routing.tsv` (J: движок, каталог, диапазон, части других уроков). Ключ — id цели, столбец принадлежит одному файлу. Словарь шагов — правило толкования, идёт в M; перечни шагов конкретных сценариев остаются в `scenarios.tsv`.
3. **Механическая проверка протокола.** Цикл даёт заглушку протокола: она записывает вызовы и отвечает только формой, без вердикта; пишет её не генератор движка. Каждая цель обязана реально вызвать протокол на заглушке, иначе движок-перечислитель пройдёт проверку. Застой — 3 хода без роста числа зелёных механических проверок. Бюджет: 150 млн токенов, 24 активных часа. Генерация окончена, когда зелёны все механические проверки.
4. **Сверка (шаг 8).** Оба судьи работают на одном C и одном пине раннера, поэтому устаревший кандидат краснеет у обоих и расхождением не считается. Кандидаты называются поимённо. Единица сравнения — случай. Обязательный красный набор: пустая сборка, «отказ на всё», мутанты; мутанты здесь разрешены, запрет доп. (15) относится к генерации. Классы расхождения: ошибка нового судьи, ошибка раннера, пробел спецификации, сбой среды. Шаг закрывает Архитектор, когда каждое расхождение классифицировано.
5. **Роль второго судьи.** До итогов шага 8 движок только сравнивается и в вердикт продукту не входит. Вхождение и условие ADR-0133 доп. (13) п. 5 — отдельным словом владельца.
6. **Опись** охватывает все модули, достижимые от целей `c_targets` на пине. Исключения поимённо с причиной: `vms_*`, тесты.
7. **«Код под урок» определён машинно:** в коде движка нет литералов идентификаторов уроков, целей и пакетов; ветка выбирается только по значениям закрытого словаря из норм. Пробел признаёт Архитектор, круги — по образцу ADR-0133 доп. (2) п. 3.
8. **Классификация описи.** Каждая строка получает отметку: норма, случайность реализации или ошибка раннера. Предлагает `spec103`, спорное решает Архитектор. Норма пишется через наблюдаемое поведение; правило готовности записывается единым.
9. **Порядок.** Нормы урока судьи — после `P01.10.5`. Разведка и зачётная проба шаг 4 не ждут: зачётную пробу судит нынешний раннер. Норма, меняющая вердикт и решённая до выгрузки, войдёт в неё сама.
10. **Первая волна движка:** цели P/01 со стендом, сценариями и векторами. Вне её: боевые цели D7, нагрузка, суд семей, консольные и многокластерные стенды, VMS. Следствие «новый урок не требует нового кода» считается подтверждённым только на втором уроке.
11. **Мелкое.** Принимает опись Архитектор. Рецензента шага 7 назначает Архитектор, провайдер не MiniMax. Скрыто значение `BOX_ID="stand-box"`, имена уже в README. Риск двух разборщиков одних таблиц в сухом режиме принят: его закрывают код-ревью и сверка. Основание переноса — ADR-0133 доп. (18).

## Дополнение (4), 2026-11-09 — боевая квалификация в спецификации раннера (слово владельца)

2. Вердикт движка по-прежнему только сравнивается (доп. (2) п. 5).
3. Генерация `P01.25` ждёт `P01.67` и конца генерации попытки 3 (ADR-0133 доп. (33) Г).

## Дополнение (5), 2026-11-10 — усиленные ворота и продолжение генерации движка (слово владельца)

Слово владельца: «да, усиливай ворота и продолжай генерацию движка». Основание — ревью `P01.79`: движок проходил механику (52 из 52), но не судил: сценарий исполнялся одним запросом, у векторов проверялась только обёртка, итога цели не было (Б1–Б5).

1. **Ворота строятся из данных J-входа,** цикл урока не знает (ADR-0133 доп. (36)):
   - заглушка ждёт все шаги каждого выбранного сценария в их порядке, а движок отчитывается по каждому шагу;
   - по каждому случаю таблицы векторов движок даёт исход из закрытого списка; заглушка, кроме верных, отвечает и заведомо неверными по форме ответа, и такой ответ не может получить GREEN;
   - у каждой цели итог из закрытого списка исходов нормы, со сводкой классов;
   - числа в ответах заглушки — настоящие JSON-числа;
   - сухой перечень боевой цели называет записи N6 по таблице норм.
2. **Модели ревью не даётся:** обратная связь по-прежнему только механическая (доп. (2) п. 3). Модель видит сообщения новых ворот, а не отчёт рецензента.
3. **Продолжение** в той же работе, остаток бюджета (около 135 млн токенов из 150). Перед стартом — обход.
4. **Затем** повторное ревью другим провайдером и сверка с раннером (шаги 7, 8).

## Дополнение (7), 2026-11-10 — второй круг доработки движка и суд попытки 4 обоими судьями (слово владельца)

Слово владельца: «да, доработка движка и суд обоими судьями». Основание — калибровка `P01.80`: из 1086 расхождений 1012 у движка, 984 из них — две причины.

1. **Ворота второго круга** из данных J-входа, без знания урока: без приёмника моста не исполняются только строки швов, а не вся цель; сокет роли выбирается по профилю; сборка `box` даёт not_applicable групповой цели; директивы словаря (`@big`, `ASSERT`) исполняются или отмечаются по закрытому списку; векторы сравниваются по всем таблицам протокола; боевая цель без входа даёт MissingBinding.
2. **Продолжение генерации** в той же работе, на J-входе новой пары `P01.88`; модели ревью и калибровка не даются, обратная связь только механическая.
3. **Суд попытки 4** проводят оба судьи на одних бинарниках: раннер — последний раз по доп. (6), движок — после второго круга. Это вторая точка сравнения; вердикт продукту по-прежнему даёт раннер (доп. (2) п. 5).

## Дополнение (9), 2026-11-10 — заглушка отвечает и верным значением (решение Архитектора)
