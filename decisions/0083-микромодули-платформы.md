# Микромодули платформы: граница процесса — граница модуля, контракты трёх видов, один модуль уроков «Платформа»

## Context and Problem Statement
Класс системы: платформенная система.

Спецификация платформы — это уроки М10 «Платформа» (11) и М11 «Домен» (12), нарезанные по темам: хранилище, спека,
права, секреты, отчёты, книги и т. д. По ним независимо сгенерированы две реализации: `cammeta-python` (М10 и М11) и
`cammeta-go` (М10). Обе проходят всю приёмку.

Сверки двух реализаций (`cammeta-diff/REPORT-m10-01-02.md`, `REPORT-m10-03-05.md`) нашли 134 расхождения на зелёной
приёмке. Почти все они — места, где связь между частями платформы держится не на двери, а на неявном:
- общие строки хранилища, которые один процесс пишет, а другой читает;
- общий строгий загрузчик спеки, который прогоняет каждый процесс;
- общие алгоритмы (JCS, подписи, конверты, оценщик прав).

Владелец хочет, чтобы части платформы выпускались независимо, на своих языках, и знали друг о друге только контракт.
Нарезка уроков по темам этому не помогает: одна тема (права, секреты) распадается по нескольким процессам, а один
процесс (консоль, процесс `domain`) собирается из многих уроков.

## Decision Drivers
* Независимый релизный цикл и свой язык у каждой части платформы.
* Связь между частями — только явным контрактом, проверяемым приёмкой; неявная связь через общие данные запрещена.
* Две независимые реализации уже показали, где контракт неполон: решение должно сделать эти места контрактом, а не
  договорённостью.
* Кластеры домена и так обновляются в разное время: агент версии N говорит с держателем версии N±1. Совместимость
  версий нужна уже сейчас, но нигде не названа.
* Цена: каждая новая сетевая граница — это задержка и ещё один отказ. Дробить мельче процесса нельзя.

## Considered Options
* **А. Микромодуль = процесс.** Контракты трёх видов, один модуль уроков «Платформа» по микромодулям.
* **Б. Оставить нарезку по темам** (М10, М11) и дописать к ней каталог контрактов.
* **В. Мельче процесса:** общие алгоритмы (загрузчик, оценщик прав, конверты) — отдельные сервисы.

## Decision Outcome
Выбран вариант **А**: граница модуля совпадает с границей процесса, а нормативные контракты задаются только между
процессами.

### 1. Микромодули
Одиннадцать микромодулей, у каждого — свой процесс (или библиотека), свой контракт, своя приёмка, свой релиз и
допустимо свой язык:
1. хранилище;
2. спека и установщик;
3. воркер (SDK);
4. контроллер;
5. ресурс;
6. консоль кластера;
7. модуль консоли (JS);
8. процесс `domain`;
9. агент;
10. ретранслятор;
11. консоль домена.

Состав, порядок и перенос норм М10 и М11 — записка модуля `Platform/module-design.md`.

### 2. Три вида контракта
Других связей между микромодулями нет.
1. **Двери** — HTTP и unix-сокеты. Контракт — OpenAPI микромодуля-владельца двери.
2. **Данные** — строки и объекты хранилища, которые пишет один микромодуль, а читает другой. Контракт — **каталог
   контрактов данных**: на каждую семью ключей схема (JSON Schema), единственный писатель, читатели, версия формы.
   Читать чужую строку без записи в каталоге запрещено.
3. **Общие алгоритмы** — JCS, подпись агента, `record`, конверты `enc:v2` и `x25519:v1`, оценщик прав, вывод прав из
   спеки, разбор адреса урока 7. Контракт — пакет **векторов** (вход → выход). Каждый микромодуль реализует алгоритм
   сам и проходит векторы. Формат принадлежит микромодулю, который его вводит по порядку уроков.

### 3. Совместимость версий
* Отправитель шлёт только объявленные поля: закрытые формы ответов и строк остаются нормой для писателя.
* Получатель игнорирует незнакомые поля в ответах, строках и объектах. Это общее правило, а не правило отдельной
  двери. Входы дверей (запросы) остаются строгими, как сейчас.
* Несовместимое изменение двери или формы — только новой версией (путь двери или поле `v` формы) с окном, когда
  работают обе версии. Окно называет ADR изменения.
* Каждый микромодуль публикует, какие версии контрактов он пишет и читает.

### 4. Канонический вид спеки
Установщик (микромодуль 2) рядом с исходным YAML пишет скомпилированный канонический вид — JCS JSON со своей схемой и
версией. Остальные микромодули читают только его. Строгий загрузчик YAML нужен одному установщику. Это меняет
М10/2 Н1.5 и Н3: «каждый процесс при старте прогоняет загрузчик» больше не норма.

### 5. Приёмка
* У каждого микромодуля своя приёмка по его контрактам. Соседи на стенде — любой реализации.
* Добавляется **матрица совместимости**: прогоны смешанных сборок (микромодуль одной реализации среди соседей другой).
* Сверка двух реализаций на одинаковых входах — постоянный шаг после каждой крупной выгрузки, наравне с проверкой
  мутациями.

### 6. Уроки
М10 и М11 сводятся в **один модуль уроков «Платформа»** из 11 уроков: урок = микромодуль. Новый модуль живёт в
отдельном каталоге `/Users/murat/w2c/Platform`. `М10_Platform/` и `М11_Domain/` курса остаются, пока всё не перенесено:
урок снимается в том коммите, где его нормы перенесены (ADR-0003). Модули подсистем (М12A, М12B), М13 и М14 решение
не меняет.

### 7. Пилот
Первый микромодуль — **хранилище**. Подтверждение — Python-реализация остальных процессов М10 поверх Go-хранилища
проходит ту же приёмку, что и целиком Python. Неявные связи, которые пилот найдёт, становятся контрактами (п. 2).

### Consequences
* Good, because каждый микромодуль можно выпускать и переписывать независимо, а связь проверяется приёмкой контракта,
  а не совпадением реализаций.
* Good, because самая тяжёлая общая зависимость — строгий загрузчик YAML (439 случаев корпуса) — остаётся в одном
  микромодуле.
* Good, because совместимость версий домена, нужная уже сейчас, получает правило.
* Good, because урок читается как спецификация одного процесса: всё, что делает консоль, — в одном уроке.
* Bad, because уроки по темам (права, секреты) распадаются по нескольким урокам. Сквозную тему придётся читать в
  нескольких местах, и записке нужны указатели.
* Bad, because каталог контрактов данных — новый артефакт, который надо вести. Сотни семей ключей М10 и М11 придётся
  выписать из норм.
* Bad, because перенос двух модулей (23 урока, около 1500 шагов приёмки) — долгий период, когда живы и старые, и новые
  уроки. Генераторы и выгрузка `cammeta-specs` переключаются только в его конце.
* Bad, because процесс `domain` — самый крупный микромодуль (части шести уроков М11), и его урок будет большим. Ему
  нужны главы (п. «Форма урока» записки).

### Confirmation
* **Пилот на хранилище:** смешанная сборка Python + Go-хранилище проходит приёмку М10 уроков 3–11. Отчёт —
  `/Users/murat/w2c/cammeta-interop/REPORT.md`.
* **`check_spec` для модуля «Платформа»** проверяет, что у каждой семьи ключей, которую читает урок, есть запись в
  каталоге данных с этим читателем. Чтение без записи — ошибка.
* **Матрица совместимости в общей приёмке** (`cammeta-acceptance`) зелёная хотя бы для пар Python/Go по каждому
  микромодулю, у которого есть обе реализации.
* **Перенос завершён**, когда `М10_Platform/` и `М11_Domain/` сняты, а `cammeta-specs` выгружается из `Platform/`.

## Pros and Cons of the Options

### А. Микромодуль = процесс
* Good, because граница проверяема: процесс либо говорит по контракту, либо нет.
* Good, because совпадает с тем, как платформа разворачивается: юниты М10/11 — это и есть процессы.
* Bad, because требует переноса уроков и нового каталога контрактов.

### Б. Нарезка по темам плюс каталог контрактов
* Good, because уроки не переносятся.
* Bad, because урок по-прежнему не соответствует единице релиза: чтобы выпустить консоль, надо собрать её из девяти
  уроков.
* Bad, because темы, общие для процессов, продолжают держать неявные связи внутри одного урока.

### В. Мельче процесса
* Good, because общий алгоритм реализован один раз.
* Bad, because загрузчик и оценщик прав в критическом пути каждого запроса превращаются в сетевой вызов: задержка и
  новый отказ.
* Bad, because противоречит п. «Цена» драйверов: выгоды нет, связи становятся сетевыми.

## Дополнение 2026-10-18 (1): писатель — по образцу ключа и операции; перенос без изменения поведения
Решение «Архитектора» по замечаниям «Спецификации» к записке (`decisions/inbox/2026-10-18-записка-платформы-замечания.md`).
- **Каталог данных (п. 2).** «Единственный писатель» — на образец ключа и операцию (`create`, `put`, `mark`, `delete`),
  а не на семью. Пример: у `<sub>/requests/<rid>` создаёт консоль или воркер, отмечают ресурс и держатель, закрывает
  жнец. `check_spec` сверяет писателей и читателей каталога с правами, выведенными из спеки (М10/6 Н1.4).
- **Порядок введения.** Новое поведение вводится отдельными правками после переноса урока-владельца, каждая — с
  перечнем изменённых шагов приёмки и проходом по классу. Это касается трёх правил:
  - читатель игнорирует незнакомые поля (п. 3);
  - канонический вид спеки (п. 4);
  - порядок массивов во всём модуле.

  Перенос урока само поведение не меняет.
- **Канонический вид спеки.** Форма решается до переноса урока 3: её читают уроки 3–6, 8 и 9.
- **Приёмка (п. 5).** Сквозные сценарии нескольких микромодулей — `acceptance/system/`. `id-map.tsv` ведёт нормы,
  сценарии и векторы.

   `append`) перечислены **участники** с условиями. Пример: слот продлевает воркер, а отдаёт контроллер; просьбу

3. **Подписанное — до терпимости** (уточняет п. 3). Подписанный документ хранится, пересылается и проверяется байт в
   байт. Незнакомые поля отбрасываются только после проверки подписи и целостности.
4. **Канонический вид спеки** (уточняет п. 4):

   - на окно перехода у спеки один наблюдаемый идентификатор версии;
   - форма утверждается **до переноса урока 2**.

   - 9.1 — агент члена;
   - 9.2 — режим ретранслятора: своя часть OpenAPI агента и свой подкаталог приёмки.

   Микромодулей **десять**, консоль домена — урок 10. Выделение ретранслятора в отдельный процесс со своей ролью — отдельное решение с изменением поведения, не часть переноса; тогда же делится и урок.
6. **Порядок чтения.**

     порядке.
   - Направление: права выводятся из каталога данных, чтобы у факта «кто пишет и кто читает» был один источник.
7. **Где живёт модуль** (меняет п. 6, ответы на вопросы записки).

1. **Чтение ограничено.** Генератор микромодуля читает только свой урок (`Platform/NN-<процесс>/`) и общие контракты
   соседей: OpenAPI, строки каталога данных, векторы, файлы жизненного цикла, договоры библиотек, `common/`. Нормы других
   процессов он не читает.
2. **Порядок.** Сначала один язык, затем второй. Нынешние `cammeta-python` и `cammeta-go` остаются свидетелями для сверки
   с новой генерацией.
3. **Код ложится по процессам:** свой пакет, своя сборка и свой `acceptance.yaml` у каждого микромодуля.

**Зачем.**
- Это самая честная проверка переноса: нынешний код несёт знания сверок, которых может не быть в тексте.
- Это прямое доказательство ADR-0083: модули знают друг о друге только контракт.
- Это мера зрелости спецификации по числу догадок.

**Confirmation:** части, сгенерированные порознь, проходят приёмку каждого урока, сквозные сценарии и матрицу
совместимости. Догадки — находки к спецификации.

Раннеры приёмки переделываются под раскладку по процессам и сборку из частей до стадии C.

## Дополнение 2026-10-20 (10): замок присутствия — сверка inode после захвата
Решение «Архитектора» по ревью стадии B 3–5 (Codex RB35-01; проба двумя процессами). Договор
`Platform/common/contracts/presence-lock.md` (владелец P/05) допускал гонку: воркер открыл и записал файл, но ещё не взял
`flock`; ресурс взял свободный замок, объявил `gone` и удалил файл; воркер затем взял замок на удалённом inode — живой
процесс исчезает из `room` и `live`. Перестановка «замок до записи» окна между `open` и `flock` не закрывает. Решение:
- **воркер:** `open(O_CREAT)` → исключающий `flock` → сверка `fstat(fd)` и `stat(путь)` (то же устройство и inode); не
  совпало — закрыть и повторить с начала; совпало — записать содержимое заново под замком;
- **ресурс:** неблокирующий `flock` взят → та же сверка inode; не совпало — файл уже заменён, не трогать; совпало — читать,
  объявлять `gone` и удалять, держа замок.
Свидетельство протокола — именно это чередование (воркер остановлен между `open` и `flock`); было до переноса (М10/8 Н1.4),
поэтому — правка поведения со строкой долга реализациям и продукту.
