# Микромодули платформы: граница процесса — граница модуля, контракты трёх видов, один модуль уроков «Платформа»

## Context and Problem Statement
Класс системы: платформенная система.

Спецификация платформы — это уроки М10 «Платформа» (11) и М11 «Домен» (12), нарезанные по темам: хранилище, спека,
права, секреты, отчёты, книги и т. д. По ним независимо сгенерированы две реализации: `cammeta-python` (М10 и М11) и
`cammeta-go` (М10). Обе проходят всю приёмку.

Сверки двух реализаций (`cammeta-diff/REPORT-m10-01-02.md`, `REPORT-m10-03-05.md`) нашли 134 расхождения на зелёной
приёмке. Почти все они — места, где связь между частями платформы держится не на двери, а на неявном:
- общие строки хранилища, которые один процесс пишет, а другой читает;
- общий строгий загрузчик спеки, который прогоняет каждый процесс;
- общие алгоритмы (JCS, подписи, конверты, оценщик прав).

Владелец хочет, чтобы части платформы выпускались независимо, на своих языках, и знали друг о друге только контракт.
Нарезка уроков по темам этому не помогает: одна тема (права, секреты) распадается по нескольким процессам, а один
процесс (консоль, процесс `domain`) собирается из многих уроков.

## Decision Drivers
* Независимый релизный цикл и свой язык у каждой части платформы.
* Связь между частями — только явным контрактом, проверяемым приёмкой; неявная связь через общие данные запрещена.
* Две независимые реализации уже показали, где контракт неполон: решение должно сделать эти места контрактом, а не
  договорённостью.
* Кластеры домена и так обновляются в разное время: агент версии N говорит с держателем версии N±1. Совместимость
  версий нужна уже сейчас, но нигде не названа.
* Цена: каждая новая сетевая граница — это задержка и ещё один отказ. Дробить мельче процесса нельзя.

## Considered Options
* **А. Микромодуль = процесс.** Контракты трёх видов, один модуль уроков «Платформа» по микромодулям.
* **Б. Оставить нарезку по темам** (М10, М11) и дописать к ней каталог контрактов.
* **В. Мельче процесса:** общие алгоритмы (загрузчик, оценщик прав, конверты) — отдельные сервисы.

## Decision Outcome
Выбран вариант **А**: граница модуля совпадает с границей процесса, а нормативные контракты задаются только между
процессами.

### 1. Микромодули
Одиннадцать микромодулей, у каждого — свой процесс (или библиотека), свой контракт, своя приёмка, свой релиз и
допустимо свой язык:
1. хранилище;
2. спека и установщик;
3. воркер (SDK);
4. контроллер;
5. ресурс;
6. консоль кластера;
7. модуль консоли (JS);
8. процесс `domain`;
9. агент;
10. ретранслятор;
11. консоль домена.

Состав, порядок и перенос норм М10 и М11 — записка модуля `Platform/module-design.md`.

### 2. Три вида контракта
Других связей между микромодулями нет.
1. **Двери** — HTTP и unix-сокеты. Контракт — OpenAPI микромодуля-владельца двери.
2. **Данные** — строки и объекты хранилища, которые пишет один микромодуль, а читает другой. Контракт — **каталог
   контрактов данных**: на каждую семью ключей схема (JSON Schema), единственный писатель, читатели, версия формы.
   Читать чужую строку без записи в каталоге запрещено.
3. **Общие алгоритмы** — JCS, подпись агента, `record`, конверты `enc:v2` и `x25519:v1`, оценщик прав, вывод прав из
   спеки, разбор адреса урока 7. Контракт — пакет **векторов** (вход → выход). Каждый микромодуль реализует алгоритм
   сам и проходит векторы. Формат принадлежит микромодулю, который его вводит по порядку уроков.

### 3. Совместимость версий
* Отправитель шлёт только объявленные поля: закрытые формы ответов и строк остаются нормой для писателя.
* Получатель игнорирует незнакомые поля в ответах, строках и объектах. Это общее правило, а не правило отдельной
  двери. Входы дверей (запросы) остаются строгими, как сейчас.
* Несовместимое изменение двери или формы — только новой версией (путь двери или поле `v` формы) с окном, когда
  работают обе версии. Окно называет ADR изменения.
* Каждый микромодуль публикует, какие версии контрактов он пишет и читает.

### 4. Канонический вид спеки
Установщик (микромодуль 2) рядом с исходным YAML пишет скомпилированный канонический вид — JCS JSON со своей схемой и
версией. Остальные микромодули читают только его. Строгий загрузчик YAML нужен одному установщику. Это меняет
М10/2 Н1.5 и Н3: «каждый процесс при старте прогоняет загрузчик» больше не норма.

### 5. Приёмка
* У каждого микромодуля своя приёмка по его контрактам. Соседи на стенде — любой реализации.
* Добавляется **матрица совместимости**: прогоны смешанных сборок (микромодуль одной реализации среди соседей другой).
* Сверка двух реализаций на одинаковых входах — постоянный шаг после каждой крупной выгрузки, наравне с проверкой
  мутациями.

### 6. Уроки
М10 и М11 сводятся в **один модуль уроков «Платформа»** из 11 уроков: урок = микромодуль. Новый модуль живёт в
отдельном каталоге `/Users/murat/w2c/Platform`. `М10_Platform/` и `М11_Domain/` курса остаются, пока всё не перенесено:
урок снимается в том коммите, где его нормы перенесены (ADR-0003). Модули подсистем (М12A, М12B), М13 и М14 решение
не меняет.

### 7. Пилот
Первый микромодуль — **хранилище**. Подтверждение — Python-реализация остальных процессов М10 поверх Go-хранилища
проходит ту же приёмку, что и целиком Python. Неявные связи, которые пилот найдёт, становятся контрактами (п. 2).

### Consequences
* Good, because каждый микромодуль можно выпускать и переписывать независимо, а связь проверяется приёмкой контракта,
  а не совпадением реализаций.
* Good, because самая тяжёлая общая зависимость — строгий загрузчик YAML (439 случаев корпуса) — остаётся в одном
  микромодуле.
* Good, because совместимость версий домена, нужная уже сейчас, получает правило.
* Good, because урок читается как спецификация одного процесса: всё, что делает консоль, — в одном уроке.
* Bad, because уроки по темам (права, секреты) распадаются по нескольким урокам. Сквозную тему придётся читать в
  нескольких местах, и записке нужны указатели.
* Bad, because каталог контрактов данных — новый артефакт, который надо вести. Сотни семей ключей М10 и М11 придётся
  выписать из норм.
* Bad, because перенос двух модулей (23 урока, около 1500 шагов приёмки) — долгий период, когда живы и старые, и новые
  уроки. Генераторы и выгрузка `cammeta-specs` переключаются только в его конце.
* Bad, because процесс `domain` — самый крупный микромодуль (части шести уроков М11), и его урок будет большим. Ему
  нужны главы (п. «Форма урока» записки).

### Confirmation
* **Пилот на хранилище:** смешанная сборка Python + Go-хранилище проходит приёмку М10 уроков 3–11. Отчёт —
  `/Users/murat/w2c/cammeta-interop/REPORT.md`.
* **`check_spec` для модуля «Платформа»** проверяет, что у каждой семьи ключей, которую читает урок, есть запись в
  каталоге данных с этим читателем. Чтение без записи — ошибка.
* **Матрица совместимости в общей приёмке** (`cammeta-acceptance`) зелёная хотя бы для пар Python/Go по каждому
  микромодулю, у которого есть обе реализации.
* **Перенос завершён**, когда `М10_Platform/` и `М11_Domain/` сняты, а `cammeta-specs` выгружается из `Platform/`.

## Pros and Cons of the Options

### А. Микромодуль = процесс
* Good, because граница проверяема: процесс либо говорит по контракту, либо нет.
* Good, because совпадает с тем, как платформа разворачивается: юниты М10/11 — это и есть процессы.
* Bad, because требует переноса уроков и нового каталога контрактов.

### Б. Нарезка по темам плюс каталог контрактов
* Good, because уроки не переносятся.
* Bad, because урок по-прежнему не соответствует единице релиза: чтобы выпустить консоль, надо собрать её из девяти
  уроков.
* Bad, because темы, общие для процессов, продолжают держать неявные связи внутри одного урока.

### В. Мельче процесса
* Good, because общий алгоритм реализован один раз.
* Bad, because загрузчик и оценщик прав в критическом пути каждого запроса превращаются в сетевой вызов: задержка и
  новый отказ.
* Bad, because противоречит п. «Цена» драйверов: выгоды нет, связи становятся сетевыми.

## Дополнение 2026-10-18 (1): писатель — по образцу ключа и операции; перенос без изменения поведения
Решение «Архитектора» по замечаниям «Спецификации» к записке (`decisions/inbox/2026-10-18-записка-платформы-замечания.md`).
- **Каталог данных (п. 2).** «Единственный писатель» — на образец ключа и операцию (`create`, `put`, `mark`, `delete`),
  а не на семью. Пример: у `<sub>/requests/<rid>` создаёт консоль или воркер, отмечают ресурс и держатель, закрывает
  жнец. `check_spec` сверяет писателей и читателей каталога с правами, выведенными из спеки (М10/6 Н1.4).
- **Порядок введения.** Новое поведение вводится отдельными правками после переноса урока-владельца, каждая — с
  перечнем изменённых шагов приёмки и проходом по классу. Это касается трёх правил:
  - читатель игнорирует незнакомые поля (п. 3);
  - канонический вид спеки (п. 4);
  - порядок массивов во всём модуле.

  Перенос урока само поведение не меняет.
- **Канонический вид спеки.** Форма решается до переноса урока 3: её читают уроки 3–6, 8 и 9.
- **Приёмка (п. 5).** Сквозные сценарии нескольких микромодулей — `acceptance/system/`. `id-map.tsv` ведёт нормы,
  сценарии и векторы.

   Микромодулей **десять**, консоль домена — урок 10. Выделение ретранслятора в отдельный процесс со своей ролью — отдельное решение с изменением поведения, не часть переноса; тогда же делится и урок.

     порядке.

1. **Чтение ограничено.** Генератор микромодуля читает только свой урок (`Platform/NN-<процесс>/`) и общие контракты

## Дополнение 2026-10-20 (10): замок присутствия — сверка inode после захвата
Решение «Архитектора» по ревью стадии B 3–5 (Codex RB35-01; проба двумя процессами). Договор
`Platform/common/contracts/presence-lock.md` (владелец P/05) допускал гонку: воркер открыл и записал файл, но ещё не взял
`flock`; ресурс взял свободный замок, объявил `gone` и удалил файл; воркер затем взял замок на удалённом inode — живой
процесс исчезает из `room` и `live`. Перестановка «замок до записи» окна между `open` и `flock` не закрывает. Решение:
- **воркер:** `open(O_CREAT)` → исключающий `flock` → сверка `fstat(fd)` и `stat(путь)` (то же устройство и inode); не
  совпало — закрыть и повторить с начала; совпало — записать содержимое заново под замком;
- **ресурс:** неблокирующий `flock` взят → та же сверка inode; не совпало — файл уже заменён, не трогать; совпало — читать,
  объявлять `gone` и удалять, держа замок.
Свидетельство протокола — именно это чередование (воркер остановлен между `open` и `flock`); было до переноса (М10/8 Н1.4),
поэтому — правка поведения со строкой долга реализациям и продукту.

## Дополнение 2026-10-21 (17): стадия C — вторая генерация того же языка ради счёта догадок
Решение владельца. В стадии C, кроме основной генерации языка (доп. (5) п. 2), тот же язык МОЖЕТ сгенерировать другой
агент по той же выгрузке и с тем же ограниченным чтением (доп. (5) п. 1). Её цель — только сведения о догадках: где
спецификация не определила поведение и агенту пришлось выбирать.
- Каждый генератор ведёт журнал догадок: норма или договор, чего в тексте нет, что выбрано.
- Вторая генерация проходит приёмку уроков своим прогоном раннера. В матрицу совместимости она не входит, смесей с
  ней нет; зелёной на последующих выгрузках её не держат, свидетелем сверки она не служит.
- Итог — сравнение двух журналов и расхождений поведения, которые приёмка не различила. Каждая догадка — находка к
  спецификации обычным порядком (ADR, норма, выгрузка); после итога вторую генерацию снимают.

**Зачем.** На одном языке расхождение не объясняется языком: две реализации расходятся, только если норма допускает два
прочтения или одна от неё отступила. Это прямая мера доп. (5) «зрелость спецификации по числу догадок», без цены
матрицы, которая растёт квадратично с числом реализаций.

  пропускает запрос или нет — сторожевая по `Authorization` (урок P/06.3, P/08.4);
- `X-Operator: console` на этом переходе не признаётся — роль не доказана — и снимается до сторожевой (договор пересылки
  `x_operator`, «Принять консолью» п. 2); признаёт его только дверь роли консоли домена (P/10 Н1.4 `server.role`). Способ
  Go не переносится на Python: у консоли кластера, не держащей домен, есть отпечатки центров, но не сами сертификаты, а
  `ssl` Python 3.12 проверяет сертификат клиента в рукопожатии по загруженным центрам (то же основание — P/10 Н1.4
  «Слова foreign_ca нет»);
- снятие центра члена (`POST /domain/members/<член>/ca`) снимает доверие TLS к нему, а не членство: пересылка члена с
  действующим токеном идёт по-прежнему; отказ рукопожатием видит прямое соединение консоли члена с дверью роли держателя.
  Приёмка TLS № 14: строки 2–3 («502 у пересылающей», журнал со `status: 502`) переходят на прямую пробу
  `m2-console` → дверь роли держателя (`{"handshake": "alert", "http": null}`), строка пересылки после снятия — `200`
  (Т-правка «Спецификации»).
Поведение Python не меняется; Go перестаёт признавать `X-Operator: console` на переходе 1 (правка поведения отдельным
коммитом со строкой долга cammeta-go). Свидетель — `cammeta-go/runs/tls-er-d288d0b-1356e0a/TLS/TLS/stand.json`.

## Дополнение 2026-10-22 (20): дверь процесса domain — предъявленный сертификат клиента проверяется в рукопожатии
Решение «Архитектора», согласовано владельцем 2026-10-22 (TLS-приёмка выгрузки 8638b9e, п. 2, строка `signer` |
`foreign-console`; Python 3/4, Go 4/4; итог «cammeta-acceptance» — класс «ждёт решения владельца»). Про одну дверь —
процесс `domain` держателя (`SIGNER_URL`) — сказано две вещи. Договор сертификата роли «Серверная сторона: класс
`signed`»: сертификата клиента не требуют, предъявленный не проверяют. P/02.4 Н1.6 `client_cert`: дверь запрашивает
сертификат клиента необязательно и доверяет только своим `ca.pem`, `ca.next.pem` — роль `domainconsole` открывает
`X-W2C-Client` (P/08.4 Н1.10 `address`). Стек, который сертификат запрашивает и центрам доверяет, предъявленный проверяет
в рукопожатии: `ssl` Python 3.12 с `CERT_OPTIONAL`, OpenSSL с `SSL_VERIFY_PEER` без `FAIL_IF_NO_PEER_CERT`, nginx
`ssl_verify_client optional`; чужой центр — alert. Принять предъявленный без проверки и проверить после рукопожатия
стандартная библиотека Python не умеет (обратного вызова проверки у `ssl` нет), Go умеет (`RequestClientCert`) —
реализации разошлись: Go `ok`, Python `alert`. Решение:
- **Класс `signed` в части клиента делится по запросу.** Дверь, которая сертификата клиента не запрашивает (дверь и пакет
  ретранслятора P/09.2 Н1.6, консоль кластера для входящих из других кластеров P/06.7 Н1.7 `server`), предъявленный не
  проверяет — без изменений. Дверь процесса `domain` запрашивает его необязательно и **предъявленный проверяет в
  рукопожатии** по своим `ca.pem`, `ca.next.pem` средствами стека — цепочка до центра, срок, EKU `clientAuth`; не прошёл —
  alert, HTTP нет. Без сертификата — как было: рукопожатие `ok`, личность — подпись. Лист своего центра без роли
  `domainconsole` — `ok`, прав не даёт (`X-W2C-Client` не читается).
- Остальное в классе `signed` не меняется: личность — подпись, сертификат клиента не требуется; единственное, что он
  даёт, — чтение `X-W2C-Client` ролью `domainconsole`.
- **Нормы** (Т-правка «Спецификации» после разбора ревью): договор сертификата роли «Серверная сторона: класс `signed`» —
  оговорка о двери процесса `domain`; P/02.4 Н1.6 `client_cert` — «предъявленный проверяется в рукопожатии, не прошёл —
  alert»; P/08.0-02 — то же словами; приёмка TLS п. 2, строка `signer` | `foreign-console` →
  `{"handshake": "alert", "http": null}` с нормой `client_cert`. Правило «предъявленный не проверяется» остаётся
  проверенным строкой № 14 (`member m1 console`, клиент `foreign-console` → `{"handshake": "ok"}`).
- **Поведение.** Python не меняется. Go: дверь процесса `domain` проверяет предъявленный сертификат в рукопожатии
  (`VerifyClientCertIfGiven`, `ClientCAs` из `ca.pem`, `ca.next.pem`) — правка поведения отдельным коммитом со строкой
  долга cammeta-go; после выгрузки — повтор TLS у обоих. Сведение «Сборке» (ADR-0005): продукт сверяет свою дверь
  держателя при переводе.
- **Цена.** Консоль домена с листом снятого центра получает alert, а не ответ HTTP — причина видна хуже (журнал стека,
  не журнал двери). Ротация не задета: на двери загружены оба центра (P/02.4 Н1.6 `rotation`). Агенты и ретрансляторы
  сертификата не шлют (P/02.4 Н1.6 `client_cert`, P/09.1 Н1.11 `holder`) — для них ничего не меняется.
- **Отвергнуто.** Норма как есть (`ok` для чужого центра): требует от реализации того, чего нет в стандартной библиотеке
  одного из языков генерации — Python понадобился бы pyOpenSSL с обратным вызовом проверки; спецификация пишется для
  многих языков. Отдельный адрес для роли `domainconsole`: новый адрес и норма P/02.4 ради расхождения в одной строке
  приёмки.
- Нормы — после разбора ревью трёх (`СЕССИИ.md` §1 п. 17; ср. доп. (19) п. 2, последний пункт).

Confirmation: TLS п. 2 у обеих реализаций 4/4 на выгрузке с правкой; строка `signer` | `foreign-console` — `alert`.

## Дополнение 2026-10-22 (21): ревью доп. (20) — дверь процесса domain, уточнения
Решение владельца 2026-10-22 — вариант «2 уточнённый» (разбор `inbox/2026-10-22-ревью-ADR-0083-доп-20-разбор.md`).
Доп. (20) остаётся: дверь процесса `domain` предъявленный лист проверяет в рукопожатии. Уточняется:
1. **Довод.** Отказ рукопожатием даёт `ssl` Python 3.12 (`CERT_OPTIONAL`) и OpenSSL со стандартной проверкой (без своего
   обратного вызова, сохраняющего соединение); nginx — неверный пример (проверку читает после рукопожатия, ответ HTTP
   400), снят. Прочие стеки ДОЛЖНЫ отказать рукопожатием тоже (Go — `VerifyClientCertIfGiven`).
2. **Класс `signed` делится по слушателю, не по маршруту.** Слушатель `SIGNER_URL` — все его маршруты (агенты, пакет
   ретранслятора, `prepare`/`take`/`move`, двери людей) — сертификат клиента запрашивает необязательно и предъявленный
   проверяет. Дверь ретранслятора и слушатель консоли кластера для входящих из других кластеров — **сертификата клиента не
   запрашивают** (эти слова заменяют «предъявленный не проверяют»: без запроса клиент листа не шлёт). Личность — по норме
   маршрута (подпись, токен, пароль), не «подпись» вообще.
3. **Проверка в рукопожатии — закрытый набор**: лист сходится к своим `ca.pem` или `ca.next.pem`, срок действует, нет
   extendedKeyUsage без `clientAuth` (слова P/10 Н1.4 `server.role`); иначе — alert, HTTP нет. Лист вне договора `cert`
   (keyUsage, размер ключа, строгие расширения) рукопожатие МОЖЕТ отказать; приёмка таких листов не берёт.
4. **После рукопожатия**: `X-W2C-Client` читается, только если роль из SAN — `domainconsole`, подписи листа и центра — в
   списке `sig`, серийник не в `revoked`; иначе — адрес TCP-пира (договор пересылки «Адрес клиента»). Отказа HTTP здесь
   нет: дверь обслуживает и другие маршруты.
5. **Как у двери роли P/10 Н1.4**: смену `ca.pem`, `ca.next.pem`, `revoked` видят новые соединения без перезапуска;
   сессий дверь не возобновляет (билеты и PSK выключены) — иначе возобновлённая сессия пропустит лист снятого центра.
   Хвост P/10 Н1.4 «двери класса signed это не затрагивает» — про двери без запроса.
6. **Клиенты из других кластеров** — агент члена, ретранслятор — свой лист двери `SIGNER_URL` держателя **не
   предъявляют** (требование: P/09.1 Н1.7, P/09.2, договор сертификата роли `peer_role`); иначе лист своего центра — alert,
   член молчит. Лист предъявляют клиенты своего кластера (консоль домена — `domainconsole`; консоль кластера при пересылке
   подписанту своей коробки).
7. **Дверь воркера на домене** (P/03.7 Н1.6 `door_client`) — та же форма: иной центр, срок, EKU — alert; нет сертификата,
   иная роль, подпись вне `sig`, отозванный — 403 `forbidden`.
8. **Цена — условно**: отказ — при фактическом предъявлении листа. Консоль домена с листом снятого центра, предъявив его,
   получает alert и отвечает 502 на все передаваемые двери и `/api/login`; клиент, не предъявивший лист (Go с выбором по
   списку центров запроса), идёт без `X-W2C-Client`.
9. **Приёмка** (данные «Спецификации»): клиент пробы предъявляет указанный лист на любой запрос сертификата, независимо
   от списка центров запроса; без запроса — не шлёт. Строки двери `signer` п. 2: `null` → `ok`; `hold-domainconsole` →
   `ok`; лист следующего центра `hold` (`ca.next.pem`) → `ok`; свои листы `domainconsole` центра `hold` — просроченный и
   без `clientAuth` → alert; `foreign-console` → alert; `m2-domainagent` → alert; свой с подписью вне `sig` → `ok`
   (`X-W2C-Client` стенд не наблюдает). Чего стенд не умеет (лист следующего центра у `signer`) — строкой долга стенда.
   Строки № 14 не меняются.
10. **Отвергнуто**: «оба исхода допустимы» (alert или `ok` без `X-W2C-Client`) — `X-W2C-Client` стенд не наблюдает, и
    отрицательные строки ничего бы не различали; проверка двери стала бы только чтением.
11. **Нормы** (Т-правка «Спецификации»): договор сертификата роли (вводная, `peer_role`, «Серверная сторона: класс
    `signed`»), P/02.4 Н1.6 `client_cert`, P/08.0 Н1.6 (тело), Н5, P/08.0-02, P/08.3 Н2, договор пересылки «Адрес
    клиента», P/03.7 Н1.6 `door_client`, P/09.1 Н1.7, P/09.2 (клиент ретранслятора), P/10 Н1.4 (хвост), README и лекция
    P/08, `stage-a-after-m11.md`, `id-map.tsv`, TLS README (шапка, клиент пробы, п. 2), `stand.json`. Ссылка доп. (20)
    «P/02.4 Н1.6 `rotation`» — договор сертификата роли `rotation`; «P/09.1 Н1.11 `holder`» — `peer_role`.
12. **Поведение** (правки отдельными коммитами со строкой долга): обе реализации — п. 4–6 там, где их ещё нет; Go — ещё
    `VerifyClientCertIfGiven` с `ClientCAs` из `ca.pem`, `ca.next.pem`. Раннер — клиент пробы по п. 9
    («cammeta-acceptance»). Сведение «Сборке» (ADR-0005) — вся линия: запрос, проверка, `X-W2C-Client`, клиенты агента
    (дверь подписанта продукта сертификата не запрашивает вовсе, ADR-0075).

Confirmation: все строки двери `signer` п. 2 у обеих реализаций по п. 9; строки № 14 без изменений.

## Дополнение 2026-10-23 (25): Python и Go — параллельно; устройство генерации стадии C
Решение владельца 2026-10-23 (п. 1) и «Архитектора» (пп. 2–6).
1. **Языки параллельно.** Доп. (5) п. 2 «сначала один язык, затем второй» снят: `cammeta-c-python` и `cammeta-c-go`
   генерируются одновременно по выгрузке `8c9b221` — `7122377` (доп. (24) п. 1) и нормы двери ретранслятора P/09.2
   (справка `inbox/2026-10-23-справка-свидетелей-дверь-ретранслятора.md`), выгружены до открытия сессий генерации. «Первая генерация» доп. (23) п. 3 — та из двух,
   что раньше станет зелёной на приёмке всех уроков `Platform/`.
2. **Сессия языка — ведущая, микромодуль — отдельный агент.** Ограниченное чтение доп. (5) п. 1 в одном контексте не
   соблюсти, поэтому сессия языка не пишет код микромодулей сама: на каждый микромодуль она заводит агента с новым
   контекстом и списком разрешённого чтения, принимает его код, собирает и ведёт журнал. Сама она читает только
   `Platform/README.md`, `lessons.tsv`, `common/` и п. 3 соседей.
3. **Разрешённое чтение агента микромодуля `NN-<процесс>`:** свой урок `Platform/NN-<процесс>/` целиком; у соседей —
   только контракты: `spec/*.openapi.yaml`, `vectors/`, `data/`, `lifecycle.md`; `Platform/common/` целиком (договоры
   библиотек, каталог данных, диалект, векторы); `НОРМАТИВНЫЕ-СЛОВА.md`; данные `Source/tests/testdata/`; для 06 и
   07 — `Source/w2cplatform/console.*` и `КОНСОЛЬ-МОДУЛЬ-ПЛАТФОРМЫ.md`. Нормы (`*.norms.md`), лекции и README соседей —
   нет; курс, ADR, свидетели, прежние генерации, продукт — нет (доп. (23) п. 2).
4. **Раскладка репозитория** (п. 7 «Генераторы»): один репозиторий на язык, каталог на микромодуль со своей сборкой и
   своим `acceptance.yaml`; общий код только как библиотека с договором из `common/contracts/`. `SPEC_VERSION` —
   коммит `cammeta-specs`.
5. **Журнал догадок** — `GUESSES.md` в корне репозитория по форме ADR-0080 доп. 15: место нормы или договора, чего в
   тексте нет, что выбрано, какой микромодуль. Каждая догадка — строкой «Архитектору»; решение идёт нормой и
   выгрузкой, генератор переходит на неё сменой `SPEC_VERSION`.
6. **Порядок микромодулей** — по зависимостям: 01 хранилище, 02 установщик, 03 воркер (библиотека), 04 контроллер, 05
   ресурс, 06 консоль кластера, 07 модуль консоли (байты как есть), 08 domain, 09 агент, 10 консоль домена. Приёмка
   микромодуля — по готовности раннеров cammeta-acceptance под раскладку по процессам; до того — собственные
   регрессии генерации. Вторые генерации доп. (17) — по отдельному слову владельца.
