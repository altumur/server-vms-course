# Ревью ADR-0083 доп. (20) — Claude

Срез `main` 9ac51bc60. Предмет — `decisions/0083-микромодули-платформы.md:468-505`: дверь процесса `domain`
(`SIGNER_URL`) проверяет предъявленный сертификат клиента в рукопожатии. Форма —
`skills/lesson-spec/references/review-checklist.md` «Отчёт ревьювера». Код реализаций не читался; поведение стеков
(Python `ssl`, OpenSSL, Go `crypto/tls`, nginx) — по их документации и исходному поведению, без запуска.

## Вывод

**С правками.** Блокеров нет. Решение выбрано верно: дверь с необязательным запросом проверяет предъявленный
сертификат — это общее подмножество стеков; у двери роли P/10 Н1.4 это уже так. Но в доводе и в перечне правок есть пробелы:

- довод о стеках верен для стандартной библиотеки Python, а не для «стека, который запрашивает» вообще: nginx и Go —
  контрпримеры (С-1). Слова «средствами стека» оставляют набор проверок открытым (С-2). Список подписей `sig` и отзыв
  решение не называет (С-3). Список центров в запросе сертификата (Go его шлёт, Python — нет) делает исход «Цены»
  и строки приёмки зависимыми от стека клиента (С-4);
- перечень правок норм неполон. Дверь воркера на домене (P/03.7 Н1.6 `door_client`) — третья дверь того же рода, и
  у неё норма «иной центр — 403», которую Python не исполнит (П-1). Двери агентов держателя стоят на том же слушателе
  (П-2). «Агенты не шлют» нигде не записано как требование, а ссылка на него неверна (П-3). Не названы
  договор пересылки «Адрес клиента», тело P/08.0 Н1.6 и Н5, P/08.3 Н2 (П-4);
- проверка правила `signed` строкой № 14 не теряется, но формулировка «предъявленный не проверяется» после решения
  пуста (А-1). Confirmation одной строкой не проверяет ни положительный случай, ни срок, ни EKU у двери `signer` (А-2).

Итог: 19 находок — 12 существенных, 7 мелких.

## 1. Довод о стеках

### С-1 (существенная). Обобщение о стеках неверно: оно держится только на `ssl` Python

`decisions/0083-микромодули-платформы.md:474-476`: «Стек, который сертификат запрашивает и центрам доверяет,
предъявленный проверяет в рукопожатии: `ssl` Python 3.12 с `CERT_OPTIONAL`, OpenSSL с `SSL_VERIFY_PEER` без
`FAIL_IF_NO_PEER_CERT`, nginx `ssl_verify_client optional`; чужой центр — alert».

Контрпримеры:
- **nginx.** Обратный вызов проверки у nginx (`ngx_ssl_verify_callback`) всегда возвращает 1, поэтому рукопожатие
  с листом чужого центра завершается. Итог проверки nginx читает уже в фазе HTTP: при `ssl_verify_client optional`
  (и `on`) клиент получает HTTP 400 «The SSL certificate error» (внутренний код 495), а не TLS alert.
  Так что nginx — пример противоположного поведения: стек на OpenSSL принимает предъявленный лист и проверяет его
  после рукопожатия.
- **OpenSSL.** Alert получается только без своего обратного вызова `SSL_CTX_set_verify(..., cb)`; с ним стек ведёт
  себя как nginx. Это касается продукта: у него Go и C++.
- **Go.** Запрос с доверием центрам (`ClientAuth: RequestClientCert` при заданном `ClientCAs`) центры в запросе
  называет, но предъявленный лист не проверяет. Это «запрашивает и доверяет» без проверки.

Верная часть довода — `0083:476-477`: стандартная библиотека Python не умеет принять лист без проверки, потому что
обратного вызова проверки у `ssl` нет. Так же довод сформулирован в P/10 Н1.4 `server.role`
(`Platform/10-domain-console/spec/10-domain-console.norms.md:215-216`: «ssl Python 3.12 проверяет сертификат клиента в
рукопожатии без обратного вызова»).

**Последствие.** Довод, записанный как общее свойство стеков, вводит в заблуждение генератор на C++ или на nginx перед
бэкендом. Такой генератор решит, что alert даст стек сам, и получит 400.

**Предложение.** Записать довод как в P/10: «общее подмножество — `ssl` Python 3.12 проверяет предъявленный в
рукопожатии; прочие стеки ДОЛЖНЫ отказать рукопожатием тоже (Go — `VerifyClientCertIfGiven`; OpenSSL — без своего
обратного вызова или с отказом из него; nginx перед дверью — недопустим или `optional_no_ca` с проверкой в двери —
не подходит)».

### С-2 (существенная). «Средствами стека» — открытый набор проверок; стеки расходятся на листе своего центра

`0083:481-482`: «предъявленный проверяет в рукопожатии по своим `ca.pem`, `ca.next.pem` средствами стека — цепочка до
центра, срок, EKU `clientAuth`».

Стек проверяет не только эти три пункта, и наборы проверок у стеков разные. Контрпримеры — все на листе **своего**
центра с ролью `domainconsole`:
- **keyUsage без `digitalSignature`** (например, только `keyEncipherment`). Назначение `ssl_client` в OpenSSL
  отвергает такой лист, и Python отвечает alert. Go keyUsage листа не проверяет — `ok`.
- **RSA 1024 бит.** Python 3.10+ ставит уровень безопасности 2 и отвечает alert. Go принимает ключ от 1024 бит — `ok`.
- **Python 3.13.** `ssl.create_default_context()` включает `VERIFY_X509_STRICT`: лист без `authorityKeyIdentifier`
  или центр без критичного `basicConstraints` получают alert. В 3.12 и в Go — `ok`.
  `stand.json` (`defaults.leaf`) этих расширений не задаёт.

Ни один из этих листов не соответствует договору `cert` (`role-certificate.md:16-17`) и списку `sig` (`:18-20`) в
полной мере. Но решение не говорит, какой исход для них верен. Две реализации по канону расходятся на этих листах так
же, как расходились на строке, ради которой решение принято.

**Предложение.** Закрыть набор:
- лист по договору `cert` и `sig` проходит, если сходится к `ca.pem` или `ca.next.pem`, срок действует и EKU
  допускает `clientAuth`;
- лист вне договора `cert` или `sig` — рукопожатие МОЖЕТ быть отказано, а если не отказано, `X-W2C-Client` не читается.

Приёмка берёт только листы, на которых стеки совпадают. Это тот же приём, что у P/02.4 Н1.6 `cert`
(`02.4-installer.norms.md:266-267`: «иначе отказ рукопожатия или 403»).

### С-3 (существенная). Список подписей `sig` и отзыв `revoked` решение не называет

Решение перечисляет проверки: «цепочка до центра, срок, EKU `clientAuth`; не прошёл — alert» (`0083:482-483`).

Контрпримеры, где оба стека дают `ok`:
- **Лист вне списка `sig`.** Лист `domainconsole` своего центра с подписью ECDSA-SHA512 (вне закрытого списка
  `role-certificate.md:18-20`) рукопожатие проходит и в Python, и в Go. На стенде такой лист есть — `m2-sig-sha512`.
  У двери роли для этого случая есть ответ после рукопожатия — 403 `bad_chain`
  (`10-domain-console.norms.md:210-212`). У двери `domain` ответа нет: читать ли `X-W2C-Client`, не сказано.
- **Отозванный лист.** Отозванный лист `domainconsole` (серийник в `revoked`) ни один стек не отвергнет. Файл
  `revoked` — список серийников, а `crl.pem` Go в рукопожатии не читает вовсе. Строка `revoke`
  (`role-certificate.md:23`: «процессы перечитывают по содержимому») — общая для всех проверяющих. Отозванный лист
  консоли домена сейчас открывает `X-W2C-Client`.

**Предложение.** Записать в P/02.4 Н1.6 `client_cert` (и в «Адрес клиента»): «после рукопожатия: подпись вне `sig`
или серийник в `revoked` — `X-W2C-Client` не читается (адрес TCP-пира)».

### С-4 (существенная). Список центров в запросе сертификата делает исход зависимым от пары стеков

`0083:493` предписывает Go `VerifyClientCertIfGiven`, `ClientCAs` из `ca.pem`, `ca.next.pem`.

Go-сервер с заданным `ClientCAs` шлёт в запросе сертификата список центров (`certificate_authorities`). Python-сервер
список не шлёт: `ssl` не умеет `SSL_CTX_set_client_CA_list`. Go-клиент с `tls.Config.Certificates` (без
`GetClientCertificate`) предъявляет лист, только если издатель листа есть в этом списке; иначе шлёт пустой
сертификат. Python-клиент с `load_cert_chain` шлёт лист всегда.

Контрпримеры:
- **«Цена»** (`0083:496`: «Консоль домена с листом снятого центра получает alert»). Это верно для Python-двери или
  Python-консоли. Для Go-двери с Go-консолью домена лист не предъявляется: рукопожатие `ok`, `X-W2C-Client` не
  читается, предел входа считает пару (адрес консоли, имя). Это прежняя деградация, не alert.
- **Строка приёмки** `signer` | `foreign-console` → `alert`. Если клиент стенда фильтрует лист по списку центров,
  как Go с `Certificates`, верная Go-дверь получит `ok`, и строка покраснеет у верной реализации. README TLS
  (`Platform/common/acceptance/tls/README.md:56-58`) про это молчит: «Клиент — имя листа … `null` — без сертификата
  клиента».

**Предложение.**
- в README TLS: «клиент пробы предъявляет лист на любой запрос сертификата, независимо от списка центров запроса»;
- в «Цене»: исход для консоли с листом снятого центра — alert или `ok` без `X-W2C-Client`, по паре стеков;
- либо нормой клиента консоли домена: «лист предъявляет всегда».

Тот же класс касается строк `holder` (P/10 Н1.4): там исход зависит от того, шлёт ли Go-дверь роли список центров.

### С-5 (существенная). Не рассмотрен вариант «оба исхода допустимы»

`0083:499-502` отвергает два варианта: «норма как есть» и «отдельный адрес».

Третий вариант курс уже применяет:
- P/02.4 Н1.6 `cert` (`02.4-installer.norms.md:266-267`): «отказ рукопожатия или 403 с ролью и маршрутом»;
- TLS README п. 8 (`:110-111`): «проходят оба исхода».

Для чужого центра у двери `domain` это значит: `alert` или `ok` без `X-W2C-Client`. Права в обоих исходах одинаковы
(лист чужого центра прав не даёт ни там, ни там). Этот вариант не требует правки поведения Go и продукта, а строка
приёмки принимает оба исхода.

Против варианта говорит С-4: исход зависит от пары стеков. За него — то же С-4: alert всё равно не гарантирован
клиентом.

**Вопрос «Архитектору»:** записать причину отказа от этого варианта в «Отвергнуто» или принять его.

### С-6 (существенная). «Ротация не задета» — при условии, которого нормы не задают

`0083:497`: «Ротация не задета: на двери загружены оба центра (P/02.4 Н1.6 `rotation`)».

Договор называет только файл: `rotation: ca.next.pem рядом — следующий центр, которому уже верят`
(`role-certificate.md:24`). Без перезапуска перечитывается только `revoked` (`:23`). Когда процесс берёт
`ca.next.pem`, нормы двери `domain` не говорят.

**Контрпример.** Порядок смены центра:
1. `ca.next.pem` положен;
2. лист `domainconsole` перевыпущен новым центром, консоль домена перезапущена;
3. процесс `domain` не перезапускался.

До решения: рукопожатие `ok`, `X-W2C-Client` не читается — деградация предела входа. После решения: alert на каждом
соединении, консоль домена отвечает 502 на все передаваемые двери и `/api/login` (P/10 Н1.3 `pass`: «502 при обрыве
и молчании»).

**Предложение.** Записать в `client_cert` или `rotation`: «дверь видит появление и смену `ca.pem`, `ca.next.pem` без
перезапуска (новые соединения)», как у двери роли (`10-domain-console.norms.md:206-207`). Либо назвать порядок смены
центра: процесс `domain` перезапускается до перевыпуска листа консоли домена.

Ссылка «P/02.4 Н1.6 `rotation`» ведёт в P/02.4, где строки `rotation` нет. P/02.4 отсылает к договору
(`02.4-installer.norms.md:222-224`), так что ссылаться надо на договор сертификата роли `rotation`.

### С-7 (мелкая). «EKU `clientAuth`» уже, чем формулировка P/10

`0083:482`: «EKU `clientAuth`». У P/10 Н1.4 (`10-domain-console.norms.md:208-209`) сказано точнее: «отказано листу
клиента, у которого есть extendedKeyUsage без clientAuth».

Лист без расширения EKU оба стека принимают. По формулировке решения его можно прочитать как отказ.

**Предложение.** Взять слова P/10.

### С-8 (мелкая). Билеты сессий у двери `domain`

P/10 Н1.4 (`10-domain-console.norms.md:217-220`): «билеты сессий и PSK выключены … двери класса signed это не
затрагивает».

Теперь дверь `domain` проверяет лист в рукопожатии, а возобновлённая сессия несёт лист, проверенный прежним набором
центров. После снятия центра (С-6) билет TLS 1.3 сохраняет `X-W2C-Client` консоли с листом прежнего центра до конца
срока билета.

**Предложение.** Либо назвать срок как допустимый, либо выключить билеты у двери `domain`, как у двери роли. Хвост
`:220` — поправить.

## 2. Полнота перечня правок норм

### П-1 (существенная). Дверь воркера на домене — та же дверь, той же нормы; в перечне её нет

`Platform/03-worker/spec/03.7-worker.norms.md:97-100`, `door_client`: «дверь воркера на домене под TLS принимает
door.pass только от клиента роли domainconsole: сертификат клиента, выпущенный ca.pem или ca.next.pem кластера, роль
из SAN — domainconsole …; нет сертификата, иной центр или иная роль — 403 {"error": "forbidden"}».

Это третья дверь, которая запрашивает сертификат и доверяет своим центрам. Её норма требует того самого, что решение
признало невыполнимым для Python (`0083:476-477`): принять лист чужого центра в рукопожатии и ответить 403. По доводу
решения Python ответит здесь alert, Go — 403 (если не запрашивает с проверкой). Расхождение не видно, потому что
дверь «проверяется чтением» (`:101-102`).

**Предложение.** Внести P/03.7 Н1.6 `door_client` в перечень:
- «иной центр, срок, EKU — отказ рукопожатия (alert)»;
- «нет сертификата, иная роль — 403 `forbidden`».

Слова `не проверяется`/`проверяется` у двери P/03.7 согласовать с `client_cert`.

### П-2 (существенная). Двери агентов держателя стоят на том же слушателе — проверка рукопожатия и у них

Решение делит класс `signed` «по запросу» (`0083:479-481`) и пишет: «Остальное в классе `signed` не меняется … сертификат
клиента не требуется» (`:485`).

Но у процесса `domain` одна дверь `SIGNER_URL`. Рукопожатие идёт до маршрута, поэтому на этом слушателе проверка
действует для всех маршрутов. Сводная таблица P/08.0 Н2 (`08.0-domain.norms.md:83-96`) показывает на нём:
- `POST /api/member`, `GET /api/carry` — агенты;
- `POST /api/relay/<ретранслятор>` — пакет ретранслятора;
- `POST /api/tokens` — агенты;
- `/api/prepare`, `/api/take`, `/domain/move` — консоль кластера;
- двери людей.

Договор сертификата роли (`role-certificate.md:73-76`) называет эти маршруты классом `signed` с правилом «предъявленный
не проверяют»: «POST /api/member/<член>, GET /api/carry/<член> держателя (P/08.3), дверь и пакет ретранслятора (…; приём
пакета держателем — P/08.3); процесс domain держателя … предъявленный не проверяют». P/08.3 Н2
(`08.3-domain.norms.md:491-494`) говорит о тех же дверях: «сертификат клиента не требуется и прав не даёт».

**Последствие.** После правки по перечню решения договор останется противоречивым. Строки 73-76 говорят «не проверяют»
о маршрутах, которые проверяют.

**Предложение.** В договоре разделить класс `signed` по слушателю, не по маршруту:
- «слушатель `SIGNER_URL` — все маршруты: запрашивает необязательно, предъявленный проверяет»;
- «дверь ретранслятора, слушатель консоли кластера — не запрашивают».

P/08.3 Н2 `:491-494` внести в перечень.

### П-3 (существенная). «Агенты и ретрансляторы сертификата не шлют» — описание, не требование; ссылка неверна

`0083:497-498`: «Агенты и ретрансляторы сертификата не шлют (P/02.4 Н1.6 `client_cert`, P/09.1 Н1.11 `holder`) — для
них ничего не меняется».

**Где это записано:**
- P/09.1 Н1.11 — агент **в процессе без комплекта** (`09.1-agent.norms.md:470-479`). Строка `holder` — о сервере:
  «двери держателя для агентов сертификата клиента не требуют ни у кого».
- Агент с комплектом `domainagent` — P/09.1 Н1.7 (`:389-392`), и там тоже только сторона сервера: «свой комплект роли
  `domainagent` …; двери держателя класса `signed` сертификата клиента не требуют».
- «Не шлют» есть лишь пояснением в скобках: P/02.4 `:233-235` и договор пересылки `:100-101`. Ещё одно место —
  `peer_role` (`role-certificate.md:41-42`): «свой лист клиент двери signed не предъявляет».

**Контрпример.** Агент члена `m2` использует «клиент роли `domainagent`», как консоль — «клиент роли console» по
договору пересылки `tls` (`forwarding.md:74`); в продукте так устроен `roletls.HTTPClient`, ADR-0075 доп. (7),
`0075:274`. Python-клиент шлёт лист центра `m2` на любой запрос сертификата. Дверь держателя по решению отвечает
alert. Член не отчитывается, токенов не получает, держатель видит его `silent`.

До решения так было только у Python-держателя. После правки Go так будет у любого держателя с Python-агентом (С-4).
Ретранслятор как клиент держателя (`POST /api/relay`) — то же.

**Предложение.**
- в P/09.1 Н1.7, P/09.2 (клиент ретранслятора) и `peer_role`: «клиент двери держателя и ретранслятора НЕ ДОЛЖЕН
  предъявлять свой лист»;
- в «Цене»: «агент, предъявивший лист своего центра, держателю чужого кластера — alert»;
- строка TLS п. 2: `signer` | `m2-domainagent` → `{"handshake": "alert", "http": null}`;
- ссылку `P/09.1 Н1.11 holder` заменить на `peer_role`.

### П-6 (мелкая). «Личность — подпись» неверно для половины маршрутов двери

## 3. Приёмка

### А-1 (существенная). У двери без запроса лист не предъявляется: правило «предъявленный не проверяется» пусто

`0083:490-491`: «Правило «предъявленный не проверяется» остаётся проверенным строкой № 14 (`member m1 console`, клиент
`foreign-console` → `{"handshake": "ok"}`)».

В TLS 1.2 и 1.3 клиент шлёт сертификат только в ответ на запрос сервера (CertificateRequest). Консоль кластера
сертификата не запрашивает (`role-certificate.md:80`, P/06.7 Н1.7 `server`, TLS README `:173-174`). Значит, клиент
`foreign-console` у неё ничего не предъявляет, и строка № 14 по исходу совпадает со строкой `null` (`:179`).

Что строка проверяет на деле: консоль «не запрашивает с проверкой». Для консоли этого достаточно, проверка не
теряется. Но после решения в платформе не остаётся двери, которая запрашивает и не проверяет. Правило «предъявленный
не проверяют» (`role-certificate.md:76`) теряет предмет, а `:80` («в рукопожатии по центру не отказывает») говорит то
же иными словами. У двери ретранслятора строки стенда нет вовсе (P/09.2-07, `09.2-agent.norms.md:231`: «когда назовёт
дверь ретранслятора»).

**Предложение.**
- в договоре: «двери без запроса — сертификата клиента не запрашивают» вместо «предъявленный не проверяют»;
- в ADR: «правило „не запрашивает“ проверяет строка № 14 у консоли; у двери ретранслятора — долг стенда».

### А-2 (существенная). Confirmation одной строкой не проверяет ни положительный случай, ни срок и EKU у `signer`

Сейчас у двери `signer` две строки (`Platform/common/acceptance/tls/README.md:102-103`), после решения —
`null` → `ok` и `foreign-console` → `alert`. Все отрицательные листы стенда выпущены центром `m2`
(`stand.json`, `negative`: `issuer: "m2"`). У двери `signer` они отказаны уже по центру, так что срок, EKU и `sig` у
неё проверить нечем.

Контрпримеры неверных реализаций, которые пройдут Confirmation:
- **Python.** `CERT_OPTIONAL` без `load_verify_locations` центров кластера — alert на любой предъявленный лист, в том
  числе на лист своей консоли домена. `X-W2C-Client` не читается никогда.
- **Go.** `VerifyClientCertIfGiven` при `ClientCAs == nil` проверяет по системным корням — лист своего центра получает
  alert. Тот же итог.

Обе реализации выходят зелёными по строкам `null` → `ok` и `foreign-console` → `alert`.

**Предложение (данные «Спецификации»):**
- строка `signer` | `hold-domainconsole` → `{"handshake": "ok"}` — лист есть в `stand.json`, `clusters.hold`;
- отрицательные листы с `issuer: "hold"`, `role: "domainconsole"`: `hold-expired`, `hold-server-only`,
  `hold-sig-sha512`; строки `signer` → `alert`, `alert`, `ok` (последняя — С-3: рукопожатие проходит, прав нет);
- строка `signer` | `m2-domainagent` → `alert` (П-3).

Чтение `X-W2C-Client` стенд не наблюдает (`08.0-domain.norms.md:126-127`), поэтому положительная строка проверяет
только рукопожатие. Этого хватает, чтобы поймать оба контрпримера.

### А-3 (мелкая). «4/4» не называет строк

`0083:470`: «Python 3/4, Go 4/4»; `:505`: «TLS п. 2 у обеих реализаций 4/4».

В п. 2 одиннадцать строк: девять `holder` и две `signer` (`README.md:93-103`). Что значит «4», из текста не видно.
С добавлением строк А-2 счёт изменится.

**Предложение.** Confirmation — «все строки `signer` п. 2 у обеих реализаций; строки № 14 без изменений».

## 4. Последствия

### Д-1 (мелкая). Цена для консоли домена — 502 на всех передаваемых дверях, не только «причина видна хуже»

`0083:496`: «Консоль домена с листом снятого центра получает alert, а не ответ HTTP — причина видна хуже (журнал стека, не
журнал двери)».

Видимый итог — консоль домена отвечает 502 на каждую передаваемую дверь и на `POST /api/login` (P/10 Н1.3 `pass`,
`10-domain-console.norms.md:163-164`: «502 при обрыве и молчании»). Это касается и `door.pass` воркеру на домене
(П-1). Вход в домен и правки людей останавливаются целиком. Прежде было `ok` без `X-W2C-Client`: предел входа по паре
(адрес консоли, имя), правки шли.

Тот же лист снятого центра у сервера консоли домена уже ломает переход 2: консоль кластера проверяет консоль домена
своей коробки «своей CA» (`forwarding.md:74-76`). Так что коробка в таком состоянии неисправна и без решения;
новое — что ломается и переход 3.

**Предложение.** В «Цене» назвать 502 у консоли домена. В P/10 Н1.3 или журнале консоли домена — причину отказа
рукопожатия на переходе 3 (`detail`), чтобы её было видно не только в журнале стека.

### Д-2 (мелкая). Дверь подписанта продукта сертификата не запрашивает — сведение «Сборке» уже, чем нужно

`0083:494-495`: «продукт сверяет свою дверь держателя при переводе».

По ADR-0075 уточнение 3 окна 4 (`decisions/0075-…:231-240`) у продукта «`SIGNER_TLS=1` (дверь подписанта, роль
`domain`) … TLS только сервера, звонящий доказывает себя как сейчас». Дверь подписанта продукта сертификата клиента не
запрашивает вовсе. Значит, у продукта нет ни необязательного запроса, ни доверия `X-W2C-Client` по роли
`domainconsole`.

**Предложение.** В сведении назвать всю линию: запрос, проверка, `X-W2C-Client`, а также требование П-3 к клиентам
агента (`roletls.Kit.ClientForeign`, `0075:195`), а не одну дверь.

## Проверено без находок

- Правки поведения Python решение не требует. Python-дверь с `CERT_OPTIONAL` уже даёт alert на чужой центр (`0083:478`).
- Go `VerifyClientCertIfGiven` проверяет цепочку до `ClientCAs`, срок и EKU `ClientAuth` (опции проверки клиента в
  `crypto/tls`) — совпадает с перечнем решения.
- Агент в процессе без комплекта (P/09.1 Н1.11) сертификата не имеет — решение его не задевает.
- Пересылка подписанту (P/06.7 Н1.8) идёт к `SIGNER_URL` своей коробки. Лист консоли кластера выпущен своим центром
  и проходит; переход по `@tls-kit hold console foreign` (№ 14) пересылку подписанту не вызывает.
- Дверь ретранслятора и слушатель консоли кластера сертификата не запрашивают — для них решение ничего не меняет.
- Формат: решение, цена, отвергнутое, Confirmation есть; нормы отложены до разбора — по `СЕССИИ.md` §1 п. 17.
