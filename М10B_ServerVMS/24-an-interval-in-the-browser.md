# Урок 24 — Интервал архива в браузере

**Модуль:** М10B — ServerVMS (часть вторая)
**Вы напишете:** `vms/fmp4.py` — разбор Annex-B, перевод кадра в сэмпл MP4, `avcC` из параметров потока, писатель фрагментированного MP4 с `tfdt` и флагами синхронизации, и `from_samples`, который собирает файл из кадров тома; `tests/test_fmp4.py`, который читает написанные коробки обратно; и на странице VMS `vms/vms.shell.html` — игру интервала кусками у двери держателя (`PIECE`, `piecesFrom`, `segmentURL`, `playNext`, `seek`).
**Время:** ~90 минут.

## Зачем этот урок

Таймлайн есть с урока 8, плеер на странице — с урока 12. Но между ними долго стояло допущение, которого больше нет: что видео лежит файлами и браузеру можно отдать файл по пути.

Видео лежит в томе ObjectStorage (урок 6). В томе нет файлов — есть потоки сэмплов. Сэмпл — это один кадр H.264 в той форме, в какой его отдала камера, со своими временами начала и конца и флагом «ключевой». Браузер такого не играет. Он играет MP4.

Значит, интервал приходится **собирать**: взять кадры из тома и обернуть их в MP4 — не декодируя ни одного кадра. Перекодирование здесь так же недопустимо, как в уроке 13: это решение о размещении, метка GPU и видимая стоимость, а не побочный эффект нажатия «смотреть».

Отсюда предмет урока: **как из того, что лежит в томе, получить то, что играет браузер, и как страница играет интервал, который длиннее одного ответа.**

> **Проверка без железа.** Почти всё. Муксер проверяется на байтах: на входе access unit'ы, на выходе MP4, и тесты **разбирают его обратно** — дерево коробок, `tfdt`, смещения, флаги. Муксер, который никто не разбирает, неверен так, что скажет об этом только браузер: молча, чёрным экраном. Кусок идёт против живого `obsd`: дверь архива над настоящим томом (`store`, `footage`, `door` из `tests/vmsconftest.py`), кадры — `fake_samples` с настоящими SPS и PPS. Чего тесты не делают — не открывают браузер: игру кусками на странице не проверяет ни один тест.

## Шаг 1 — Почему фрагментированный MP4

Обычный MP4 хранит **индекс** — таблицы `stts`, `stsz`, `stco` — в одной коробке (`moov`), и в индексе лежат абсолютные смещения всех сэмплов в файле. Индекс нельзя написать, пока не написаны все данные: он их и адресует. Поэтому файл либо пишут дважды, либо держат целиком, чтобы потом подставить индекс в начало.

Фрагментированный MP4 устроен наоборот. Заголовок — `ftyp` и `moov` без единого сэмпла. За ним — последовательность самодостаточных кусков, и каждый описывает сам себя. Ничего не переписывается после записи. Плеер может начать с любого куска.

Вот как это объясняет сам модуль:

```python
"""…Why FRAGMENTED MP4 and not a plain one. A plain MP4 keeps its index at one
end, so the whole file has to exist before its first byte can be written — and
an interval of an archive is read as it is answered. A fragmented file is a
header and then a run of self-describing pieces: nothing is ever rewritten,
and a player can start at any fragment.
"""
```

Для архива из кадров это вдвойне удобно. Кадры приходят группами — от ключевого до ключевого, — и группа ложится во фрагмент как есть. Индекса на весь интервал не нужно вовсе.

## Шаг 2 — Две формы одних и тех же байтов

```python
def nals(au: bytes) -> list[bytes]:
    """One Annex-B access unit split into NAL units, start codes removed.

    Both `00 00 01` and `00 00 00 01` are scanned for: a camera may use either
    and is not obliged to be consistent. Zero bytes just before a start code
    belong to it, not to the payload.
    """
```

Камера отдаёт **Annex-B**: NAL-юниты, разделённые стартовыми кодами `00 00 01` или `00 00 00 01`. Формат потоковый: его можно начать читать с любого места, найдя стартовый код. Регистратор кладёт в том именно это — тело сэмпла и есть access unit в Annex-B, как его выдал `h264parse` с `stream-format=byte-stream,alignment=au` (урок 9).

MP4 хранит **AVCC**: тот же NAL, но без стартового кода и с длиной в четырёх байтах перед ним. Формат файловый: длина известна заранее, искать ничего не надо.

Две детали, на которых спотыкаются.

**Стартовые коды обеих длин, вперемешку.** Камера вправе использовать любой и не обязана быть последовательной внутри одного access unit'а. Поэтому ищутся оба.

**Нули перед стартовым кодом принадлежат ему, а не полезной нагрузке.** `00 00 00 01` — это трёхбайтовый код с ведущим нулём. Если этот ноль оставить в конце предыдущего NAL, получится NAL, который не разбирается. В коде это две строки:

```python
        while end > begin and au[end - 1] == 0:
            end -= 1
```

Тест — `test_start_codes_of_both_lengths_and_the_zeroes_before_them`.

## Шаг 3 — Параметры кодека переезжают

Регистратор пишет в том кадры, у которых SPS и PPS лежат **в каждом ключевом кадре**:

```python
# The recorder's sink is not a file: every access unit leaves the pipeline through `appsink` and goes into the
# volume's writer as one sample (`RecSink`, `vms/recworker.py`) — byte-stream, one access unit per buffer, the
# parameter sets on every key frame (`config-interval=-1`), so a sequence the engine opens on a key frame can be
# played on its own.
REC_SINK = ("h264parse config-interval=-1 ! video/x-h264,stream-format=byte-stream,alignment=au ! "
            "watchdog timeout={watchdog} ! {ring}appsink name=sink emit-signals=true sync=false max-buffers=200")
```

Для тома это правильно: последовательность открывается ключевым кадром (урок 7), и любая последовательность, с которой начали читать, сама несёт всё, что нужно декодеру.

Для MP4 — неправильно. В MP4 параметры лежат **один раз**, в описании дорожки, в коробке `avcC`:

```python
    def _avcc(self) -> bytes:
        sps = self.sps[0].ljust(4, b"\x00")
        b = bytes([1, sps[1], sps[2], sps[3], 0xFF, 0xE0 | len(self.sps)])
```

Три байта из SPS — это `profile_idc`, `constraint_flags` и `level_idc`, то самое `profile-level-id`, которое браузер называет в SDP (урок 13). Байт `0xFF` говорит главное: **длины NAL-юнитов четырёхбайтовые**, то есть именно та форма, которую пишет `to_avcc`.

Поэтому из сэмплов параметры выбрасываются:

```python
        if nal[0] & 0x1F in (NAL_SPS, NAL_PPS, NAL_AUD, NAL_FILLER):
            continue
```

SPS и PPS уже в `avcC`. AUD (access unit delimiter) говорит, где начинается access unit, а в MP4 это говорит граница сэмпла. Повторять их в каждом кадре — байты, которые браузер обязан пропустить. Тесты — `test_a_sample_is_length_prefixed_and_carries_no_parameter_sets` и `test_the_parameter_sets_come_out_of_the_stream_and_go_into_avcc`.

**И отсюда же — отказ, а не тихий файл:**

```python
        if not sps or not pps:
            raise ValueError("an MP4 sample entry needs the parameter sets: no SPS/PPS in this interval")
```

Интервал, в котором не нашлось параметров, собрать нельзя: файл получится валидным и не покажет ничего. Лучше сказать это там, где интервал собирают (`test_an_interval_without_parameter_sets_is_refused_rather_than_written`).

## Шаг 4 — Фрагмент, который понятен в одиночку

Каждый фрагмент — это `moof` (что дальше лежит) и `mdat` (байты). В `moof` три вещи, и каждая отвечает на свой вопрос плеера.

**`tfhd` с флагом `default-base-is-moof`.** Смещения внутри фрагмента считаются от начала **этого** `moof`, а не от начала файла. Без этого фрагмент нельзя понять отдельно от предыдущих.

**`tfdt` — где фрагмент стоит на шкале:**

```python
        tfdt = _box("tfdt", _full(1, 0) + _U64(self.decode_time))
```

Это ответ на «куда перематывать»: плеер узнаёт позицию фрагмента, **не прочитав предыдущие**. Версия 1 — 64 бита. Шкала — миллисекунды (`TIMESCALE = 1000`), как у архива, поэтому ничего по дороге не округляется. Тест — `test_every_fragment_says_where_it_belongs_without_the_ones_before_it`.

**`trun` — таблица сэмплов фрагмента**, и в ней смещение данных:

```python
        # The trun's data offset counts from the first byte of the moof, so the moof has to be MEASURED
        # before it can be written. Built twice with the same argument: the size does not depend on the
        # offset's value.
        moof = self._moof(samples, 0)
        moof = self._moof(samples, len(moof) + 8)
```

Смещение считается от первого байта `moof`, поэтому `moof` надо **измерить** прежде, чем записать. Он строится дважды: размер не зависит от значения смещения, а значение — зависит от размера. Ошибка на восемь байт (забыли заголовок `mdat`) даёт файл, который не играет вообще, без единого сообщения. Тест — `test_the_data_offset_points_at_the_first_byte_of_the_mdat`.

## Шаг 5 — Флаги сэмпла: куда можно перемотать

```python
def sample_flags(key: bool) -> int:
    """Whether a player may start here. A key sample depends on nothing and is a
    sync sample; anything else depends on what came before and is not one. A seek
    that lands on a non-sync sample shows nothing until the next key frame."""
    return 2 << 24 if key else (1 << 24) | (1 << 16)
```

Два бита, и оба про перемотку. Ключевой сэмпл **ни от чего не зависит** и **является** точкой синхронизации. Остальные зависят от предыдущих и точками не являются.

Отсюда правило сборки: **фрагмент начинается с ключевого кадра.** Тогда любая граница фрагмента — законная точка старта, и длинный интервал перематывается без индекса вообще. Тест — `test_a_key_frame_is_one_a_player_may_start_at`.

Флаг «ключевой» муксер берёт у сэмпла тома, а не угадывает по NAL. Движок сам открывает последовательность только на ключевом (урок 7), так что флаг тома — то же знание, уже проверенное при записи.

## Шаг 6 — Проверка чтением

Муксер нельзя проверить «зелёным тестом на запись»: он всегда что-нибудь запишет. Поэтому тесты **разбирают вывод обратно**:

```python
    kinds = [k for k, _, _ in boxes(buf)]
    assert kinds == ["ftyp", "moov", "moof", "mdat", "moof", "mdat"]
    ...
    assert tfdts == [90_000, 90_080], "the second fragment must begin where the first one's samples ended"
```

И одна ловушка, на которой спотыкается любой первый парсер MP4, включая наш тестовый: **не все коробки содержат сразу вложенные.** У `stsd` перед детьми лежат версия с флагами и счётчик записей, у `avc1` — семьдесят восемь байт полей визуальной записи. Читатель, который этого не знает, «не находит» `avcC` в файле, где он есть:

```python
SKIP = {"stsd": 8, "avc1": 78}
```

Семь тестов `test_fmp4.py` проверяют: стартовые коды обеих длин, отсутствие параметров в сэмплах, флаги ключевого кадра, `avcC` с профилем из SPS, рост `tfdt` между фрагментами, смещение данных, указывающее ровно на первый байт `mdat`, и отказ при интервале без параметров.

## Шаг 7 — Из кадров тома в файл: `from_samples`

Всё, что выше, — инструменты. Собирает их одна функция:

```python
# The archive's frames, as a browser plays them: a run of samples out of a volume (`vms/archive.py`, each an
# Annex-B access unit with its own times) → one fragmented MP4, a fragment per group of pictures. The parameter
# sets come from the first key frame; the size from its coded header. Nothing is decoded on the way.
def from_samples(samples) -> bytes:
    import io
    first = next((s for s in samples if s.key), None)
    if first is None:
        raise ValueError("no key frame in this interval: nothing a player can start from")
    sps, pps = param_sets(first.body)
    width, height = struct.unpack("<II", first.sub[:8]) if len(first.sub) >= 8 else (0, 0)
    out = io.BytesIO()
    w = Writer(out, sps, pps, width, height)
    w.start_at(0)
    frag: list[Sample] = []
    for s in samples[samples.index(first):]:
        if s.key and frag:
            w.write_fragment(frag)
            frag = []
        frag.append(Sample(to_avcc(s.body), max(1, int(s.end - s.begin)), s.key))
    w.write_fragment(frag)
    w.close()
    return out.getvalue()
```

Пять решений, и каждое — про то, что браузер сделает с файлом.

**Начало — первый ключевой кадр.** Всё до него выбрасывается: декодировать это не с чего. Нет ключевого вовсе — отказ с объяснением, а не пустой файл.

**Параметры — из первого ключевого кадра.** `config-interval=-1` гарантирует, что они там есть (шаг 3).

**Размер картинки — из закодированного заголовка сэмпла** (`sub`: ширина и высота, два little-endian u32, как их пишет `obsd.video`). Разбирать ради этого SPS не нужно: регистратор уже сказал.

**Фрагмент — группа кадров.** Новый фрагмент начинается на каждом ключевом. Это и есть правило шага 5, выполненное по построению.

**Длительность — из времён тома.** `end - begin` в миллисекундах архива, но не меньше одной: при нулевой длительности следующий кадр встал бы в ту же точку шкалы. Шкала начинается с нуля (`start_at(0)`): где этот кусок стоит в сутках, знает страница, а не файл (шаг 9).

Чего здесь нет — `Range` и частичной отдачи. Функция возвращает весь файл байтами: это сборка целиком, для того, кому файл нужен в памяти. Дверь куска её не зовёт — она пишет тот же файл потоком тем же `Writer` (шаг 8), — и в коде курса `from_samples` сейчас не вызывает никто, даже тест (упражнение 4).

## Шаг 8 — Что дверь обещает муксеру

Кусок интервала браузер берёт не у консоли: байты идут мимо неё (ADR 0015). Консоль только говорит, где дверь держателя записи, и даёт к ней токен — `GET /rec/where/<запись>` → `door: {url, token, expires, routes}` ([М10A, урок 15](../М10A_Platform/15-SpecConsole.md), шаг 12), — а маршруты двери объявляет спека `rec`: `door: {routes: [timeline, segment]}`. Сам маршрут куска — у регистратора, в `vms/footage.py`:

```
GET /segment/<recording>/e<epoch>/<fromMs>-<toMs>.mp4      one piece of it as a fragmented MP4; `.backfill.mp4` the
                                                           backfilled stream, `.device.mp4` (epoch 0) what the camera
                                                           holds itself
```

Кусок — это поток **одной** эпохи: живой (`.mp4`) или её дозапись (`.backfill.mp4`); границы — в пути, в миллисекундах. `.device.mp4` — то, что держит сама камера (урок 15): его дверь передаёт от держателя камеры как есть, мимо муксера. Потолок — `EXPORT_MAX`, час на один ответ. Дверь спрашивает таймлайны всех дверей регистраторов (запись могла жить в нескольких томах), оставляет спаны эпохи куска и прогоняет над ними `authoritative` — каждый момент от эпохи, которая им владеет, у двери, которая её держит. Дверь, которая не ответила до первого байта, называется в заголовке `X-Unreachable`; отказавшая после него обрывает ответ без последнего куска (шестое ревью); `archive.read` с sha256 пишется после отправки — только у целого файла. Здесь важна одна часть — та, что готовит кадры для муксера. Дверь не собирает файл целиком через `from_samples`, а пишет его потоком тем же `Writer`, и кадры отбираются по одному, по мере того как приходят:

```python
            for smp in heapq.merge(stream(), key=lambda s: s.begin):
                ...
                if end is not None and smp.begin < end:
                    continue                             # this moment came from another door already
                if writer is None:
                    if not smp.key:
                        continue
                    ...
                if smp.key and frag:
                    writer.write_fragment(frag)
                    frag = []
                frag.append(fmp4.Sample(fmp4.to_avcc(smp.body), max(1, int(smp.end - smp.begin)), smp.key))
                end = smp.end
```

**Каждый момент — один раз.** Чьи кадры за какую минуту, дверь уже решила `authoritative` над спанами всех дверей. Но соседние отрезки всё равно касаются краями: дверь тома начинает каждый отрезок с ключевого кадра на его первом моменте или раньше, и подводка следующего ложится на конец предыдущего. Два кадра на один момент муксер записал бы подряд, и время в файле пошло бы медленнее, чем в жизни. Поэтому кадр, начавшийся раньше конца уже взятого, пропускается.

**Начало — ключевой кадр.** Та же мысль, что в `from_samples`: пока писателя нет, кадры до первого ключевого пропускаются, и писатель создаётся на нём.

Сама дверь тома отдаёт кадры тоже с ключевого — с того, что стоит на первом моменте отрезка **или раньше** (`Archive.samples` за `/samples/<запись>`, урок 8). Поэтому кусок, попрошенный с 10:05, начинается не ровно в 10:05, а на ключевом кадре в 10:05 или за секунду-другую до него. Начать со следующего ключевого значило бы потерять начало куска.

Тесты на дверь — `test_slot_and_read.py::test_archive_read_says_what_left_and_the_digest_of_what_left` (ответ `video/mp4`, файл начинается с `ftyp`, один и тот же интервал даёт один и тот же файл — тот же sha256), `test_slot_and_read.py::test_a_door_that_stops_answering_after_the_first_byte_breaks_the_export_and_the_journal_says_so` (дверь встала после двух минут из пяти: `IncompleteRead` у клиента, `broken` без суммы в журнале), `test_slot_and_read.py::test_a_segment_is_one_epochs_stream_from_whichever_door_holds_it` (поток выжившего и поток зомби в двух томах: кусок эпохи выжившего читается из его тома, хотя дверь зомби стоит в списке первой и покрывает те же минуты), `test_slot_and_read.py::test_an_answer_with_neither_chunks_nor_a_length_is_not_taken_for_a_whole_one` (дверь, ответившая без кусков и без длины, — не целый отрезок, а дверь, которая не ответила: седьмое ревью) и `test_lesson6_controller.py::test_the_console_over_http` (дверь записи отдаёт таймлайн сырым списком в миллисекундах и кусок `/segment/1/e1/<from>-<to>.mp4` — MP4, а кусок, где ничего не записано, — 404). Что консоль байтовых маршрутов не держит вовсе, проверяет `test_where_volume.py::test_the_console_has_no_byte_routes_of_its_own`; что кусок начинается с ключевого кадра до своего начала — `test_review_remainder.py::test_a_read_starts_on_the_key_frame_before_the_moment_asked_for`.

## Шаг 9 — Страница играет кусками

Страница — `vms/vms.shell.html`, страница VMS над модулем консоли платформы ([урок 12](12-the-vms-console.md)). Таймлайн она строит сама, по дверям: у каждой записи камеры — дверь её регистратора (`/rec/where/<запись>`), у каждого тома, где запись могла лежать, — дверь его держателя (`/rec/where/<таблица>/<место>?unit=rec/<запись>`, урок 28). Каждый спан помнит, от какой двери пришёл (`where`), и куски просит у неё же.

Спан на таймлайне бывает длиной в сутки, а дверь отвечает не больше чем на час. Страница поэтому не просит спан целиком. Она режет его на куски по минуте, как режет консоль продукта:

```javascript
// A span is played in pieces the page cuts (60 s, as the product's console cuts): /segment/<recording>/e<epoch>/
// <fromMs>-<toMs>[.<source>].mp4 at the door the span came from, the token as ?t= — a media element sets no header.
// Every moment once (М10B, lesson 24): the spans overlap — two epochs over the same minutes, two volumes, a keep's copy
// — so a fenced span (an epoch another took over) is played only when it is the one clicked, and `until` remembers the
// end of what is queued: the next span is queued from there, not from its start. From a moment `t`, the pieces that end
// after it, the first entered at `t` (`off`: its scale starts at zero).
const PIECE=60;
function piecesFrom(i,t){
  const out=[];let until=-Infinity;
  V.spans.forEach((s,j)=>{
    if(j<i||!s.media||(s.fenced&&j!==i))return;
    for(let a=Math.max(s.start,until);a<s.end;a+=PIECE){
      const p={i:j,start:a,end:Math.min(s.end,a+PIECE),off:0};
      if(t&&p.end<=t)continue;
      if(t&&!out.length&&t>p.start)p.off=t-p.start;
      out.push(p);
    }
    until=Math.max(until,s.end);
  });
  return out;
}
```

```javascript
async function segmentURL(s,p){
  const d=await doorOf(s.where);if(!d)return"";
  return `${d.url}/segment/${encodeURIComponent(s.recording)}/e${s.epoch}/${Math.round(p.start*1000)}-${Math.round(p.end*1000)}${s.source?"."+s.source:""}.mp4?t=${encodeURIComponent(d.token)}`;
}
```

**Почему куски.** Дверь отдаёт кусок потоком, без `Content-Length`: браузеру (HTTP/1.1) — кусками chunked, и последний кусок приходит только у целого файла, так что оборванный кусок — ошибка загрузки, а не короткое видео (пятое ревью). Минута — это файл, который дверь отдаст быстро и браузер начнёт играть почти сразу; длину выбрал продукт, курс её повторяет. Час — потолок для человека, который скачивает интервал; страница так много за раз не просит.

**Токен — в адресе.** Элемент `<video>` заголовков не ставит, поэтому токен двери едет параметром `?t=`; `doorOf` спрашивает `/where` заново за двадцать секунд до срока токена, а `doorFetch` — один раз сразу на 401. Суффикс `.<source>` — из спана: `backfill` для дозаписанного потока, `device` для того, что держит камера.

**Каждый момент — один раз.** Спаны таймлайна перекрываются: две эпохи над одними минутами, два тома, копия метки `e0` поверх живой записи. Очередь, собранная по всем спанам подряд, сыграла бы такие минуты дважды, а то и трижды. Поэтому два правила. Отсечённый спан (`fenced` — эпоха, у которой запись уже перехватила следующая) играется, только если щёлкнули именно по нему: оператор хочет посмотреть минуты зомби — пусть смотрит, но сам по себе плеер на них не заходит. И `until` помнит конец уже поставленного: следующий спан ставится с того места, где кончился предыдущий, а не со своего начала. Чьи кадры за эти минуты придут внутри куска, решает уже не страница, а дверь: она берёт каждый момент от эпохи-владельца (шаг 8).

**Страница не знает, как устроен том.** Путь куска — маршрут, который объявила спека (`door.routes`), и в нём только запись, эпоха и границы. Ни файлов, ни путей тома страница не видит.

`playNext` берёт следующий кусок из очереди, подписывает его и ставит в плеер; следующий кусок пойдёт по `ended` плеера:

```javascript
async function playNext(){
  if(!V.queue.length)return;
  stopLive(true);
  const p=V.queue.shift(),s=V.spans[p.i];
  [...$("#timeline").children].forEach((el,j)=>el.classList.toggle("playing",j===p.i));
  const cap=$("#playing");
  if(cap)cap.textContent=`${fmtT(p.start)} – ${fmtT(p.end)} · эпоха ${s.epoch}`+(s.server?" · с "+s.server:"")+
    (s.backupOnly?" · из резервного архива":"")+(s.source==="backfill"?" · дозаписано из резервного":"");
  const v=$("#player");v.srcObject=null;v.crossOrigin="anonymous";
  v.src=await segmentURL(s,p);
  if(p.off)v.addEventListener("loadedmetadata",()=>{v.currentTime=p.off},{once:true});
  v.play().catch(()=>{});
}
```

Подпись — «<с> – <по> · эпоха N», и для записи на резервном томе — «из резервного архива», для дозаписанного — «дозаписано из резервного». `playNext`, `segmentURL`, `doorOf` и `loadTimeline` — ядро страницы, копия продуктового со сверкой (`test_shell_core.py`); `piecesFrom` со своим правилом «каждый момент один раз» — курса.

**Перемотка — в кусок, а потом внутри него.** Щелчок по событию на таймлайне зовёт `seek(t)`:

```javascript
function seek(t){
  const i=V.spans.findIndex(s=>s.media&&s.start<=t&&t<s.end);
  if(i<0){setCap(`${fmtT(t)} · в этот момент не записывалось`);return}
  V.queue=piecesFrom(i,t);playNext();
}
```

`piecesFrom(i, t)` ставит в очередь только куски, которые кончаются после `t`; первым идёт тот, в котором лежит момент, и у него `off = t − start`. Плеер встаёт внутрь куска на `off` по `loadedmetadata`. Шкала куска начинается с нуля (`start_at(0)`, шаг 7), поэтому смещение считает страница. Момент, на который нет записи, — подпись «в этот момент не записывалось», а не чёрный экран.

**Чего здесь нет — непрерывности.** Каждый кусок — новая загрузка и новый первый кадр, поэтому раз в минуту плеер запинается. Склеивать куски без швов (MSE) страница не берётся: она играет то, что отдаёт дверь.

## Что может пойти не так

- **Смещение данных считали от начала файла.** Фрагмент перестаёт быть самодостаточным. Считать от `moof` — это флаг `default-base-is-moof`.
- **Забыли `mvex`.** Плеер читает `moov`, не находит в нём сэмплов и честно сообщает, что файл пуст. Фрагменты он при этом даже не смотрит.
- **`tfdt` не растёт.** Все фрагменты встают в одну точку шкалы; перемотка ведёт в начало, а длительность куска равна длительности последнего фрагмента.
- **Фрагмент начинается не с ключевого кадра.** Формально файл верен, перемотка на его границу показывает чёрный экран до следующего ключевого.
- **Файл начинается не с ключевого кадра.** Первые секунды куска чёрные. Экспорт пропускает всё до первого ключевого, и `from_samples` — тоже.
- **Оставили SPS/PPS в сэмплах.** Браузер пропустит, но это байты в каждом ключевом кадре — на длинном интервале заметная доля.
- **Взяли `profile_idc` из строки камеры, а не из SPS.** В паспорте написано одно, поток бывает другой; в `avcC` должно стоять то, что в потоке (та же мысль, что в уроке 13).
- **Два кадра на один момент.** Кадры соседних отрезков не прорежены по времени, и время в файле идёт медленнее, чем в жизни.
- **Брать кадры у первой двери, которая их отдала.** Минуты, которые две эпохи держат в двух томах, придут от зомби.
- **Ставить в очередь все спаны подряд.** Минуты двух томов, копии метки и отсечённой эпохи играются по два-три раза.
- **Попросили спан целиком.** Сутки в одном куске — 400 от двери; без потолка — слот двери, занятый на час.
- **Перемотка промахивается на секунду-другую.** Кусок начинается на ключевом кадре в `from` или раньше, а страница считает смещение от `from`.
- **Сэмпл нулевой длительности.** Два кадра встают в одну точку шкалы. Отсюда `max(1, …)`.

## Итог

- Том хранит кадры в Annex-B, браузер хочет AVCC внутри MP4: те же байты, другая разметка, и ни одного декодированного кадра между ними.
- Параметры кодека переезжают из каждого ключевого кадра в `avcC` — одна запись на дорожку.
- Обычный MP4 не годится не потому, что «не поддерживается», а потому что его индекс нельзя написать раньше данных.
- Фрагмент самодостаточен: `default-base-is-moof`, `tfdt`, `trun` со смещением от `moof`.
- Флаги сэмпла — это про перемотку, и поэтому фрагмент начинается с ключевого кадра.
- Муксер проверяется разбором собственного вывода: зелёный тест на запись не значит ничего.
- `from_samples` собирает файл из кадров тома: с первого ключевого, фрагмент на группу, параметры и размер — из первого ключевого.
- Дверь куска даёт муксеру каждый момент один раз, от эпохи-владельца через все двери, и с ключевого кадра.
- Страница играет интервал кусками по минуте у двери, с которой пришёл спан, каждый момент один раз: отсечённый спан — только по щелчку, общие минуты — с первого спана. Подпись называет эпоху, а у резервного и дозаписанного — откуда кусок. Перематывает в кусок, а потом внутри него. Без швов — не здесь.

## Упражнения

1. Соберите интервал из двух групп с разными SPS (камера сменила разрешение). Что покажет браузер и где это надо было заметить? Подсказка: `from_samples` берёт параметры только из первого ключевого кадра.
2. Уберите `mvex` и разберите получившийся файл своим же `boxes()`. Что именно скажет плеер и почему не «файл битый»?
3. Сделайте `tfdt` версии 0 (32 бита). Посчитайте, сколько часов в миллисекундах влезет в него. Мешает ли это кускам, у которых шкала начинается с нуля?
4. Напишите тест на `from_samples`, который разбирает его вывод: число фрагментов равно числу групп кадров, первый сэмпл каждого фрагмента — ключевой, `avcC` несёт профиль из SPS первого ключевого.
5. Уберите прореживание по времени в двери куска (`_export` в `vms/footage.py`) и положите одну запись в два тома. Сколько будет длиться минутный кусок в плеере?
6. Поменяйте `PIECE` на 3600. Что изменится во времени до первой картинки и в том, как долго кусок держит слот двери (`EXPORTS_AT_ONCE`)? Почему потолок `EXPORT_MAX` при этом не мешает?
7. Сделайте так, чтобы перемотка не промахивалась: страница должна знать, на каком моменте начался кусок. Где взять это знание — в файле, в заголовке ответа или в отдельном запросе?
