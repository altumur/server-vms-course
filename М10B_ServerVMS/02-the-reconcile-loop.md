# Урок 2 — Цикл сверки

**Модуль:** М10B — ServerVMS (часть вторая)
**Вы напишете:** `w2cplatform/reconcile.py` — помощник сверки платформы (ADR 0033): `Backoff`, `Want`, `Pass`, `Position` и `Reconciler` с `once`, `running`, `forget`, `drop`, `clear`, `reset_backoff`, `status`. Это цикл М9, ставший общим для подсистем, — и семь тестов М9 против него (`tests/test_lesson4_worker.py`), а рядом тесты помощника на `testsub` и `testsub2` (`tests/test_reconcile.py`).
**Время:** ~70 минут.

## Зачем этот урок

Этот урок почти не пишет нового. Он **переносит** — и в этом весь смысл.

В М9 вы написали цикл сверки для коробки: одна машина, локальный Postgres, список камер в нём. Сейчас машин может быть много, хранилище стало распределённым, появились эпохи, аренды и слоты. Естественное ожидание: цикл придётся переписать.

Контракт не меняется. И это не удача, а **проверка того, что М9 была разложена правильно**: цикл сверки не знал, откуда берётся желаемое состояние, и потому ему безразлично, что теперь оно берётся из назначения в распределённом хранилище. Он не знал, что делает запуск, и потому ему безразлично, что теперь запуск — это ворота с эпохой и арендой.

Меняется адрес. Цикл с откатом и джиттером нужен не одной VMS: им крутят камеры держатель и записи регистратор, им же сверяют свои единицы воркеры `testsub` и `testsub2`. Механизм, нужный двум подсистемам, по правилу границы — платформенный (ADR 0002), и откат с джиттером — инвариант, который платформа обязана дать любому воркеру с набором конвейеров: единицы, отказавшие вместе, не повторяют попытку вместе (ADR 0033). Поэтому цикл лежит в `w2cplatform/reconcile.py`, а VMS его берёт.

Доказательство переноса — тоже из М9: **семь его тестов прогоняются против помощника платформы, не поменяв смысла.** Если бы хоть один потребовал другого смысла, значит, контракт изменился, и значит, где-то в платформу просочилось знание, которому там не место.

Формула, вокруг которой всё построено, — одна строка докстроки:

> *Desired state is persisted. Actual state is derived.*

Желаемое лежит в хранилище и переживает всё. Действительное — в памяти процесса и не переживает даже перезапуск. Урок объясняет, почему второе не ошибка, а требование.

> **Проверка без железа.** Весь урок. У цикла нет ни сети, ни файлов: часы и случайность — поля, которые тест подменяет своими, запуск — поддельный актуатор, желаемое — словарь.

## Что нужно знать заранее

- **М9, урок 6** — тот самый цикл: если помните его, урок будет чтением с комментариями.
- **Урок 1** — поля `id`, `enabled`, `revision`: цикл смотрит только на ревизию, а включённость решает воркер.
- **М10A, урок 8** — `Worker` и его `reconcile_once` (шаг 8): место, откуда цикл зовут.

## Чему вы научитесь

1. Писать цикл сверки, не знающий ни хранилища, ни того, что значит «запустить».
2. Объяснять, почему сравнение ревизий — `>=`, а не `==` или `!=`.
3. Останавливать по тому, что работает, а не по тому, что настроено, и говорить, что ловит только этот порядок.
4. Разносить откаты двухсот камер джиттером и считать, во что обходится его отсутствие.
5. Различать четыре выхода из «работает» и три положения единицы — и держать положения выводимыми.

## Шаг 1 — Пять имён и ни одной зависимости

```python
CONVERGED, LAGGING, STALLED = "converged", "lagging", "stalled"

@dataclass(frozen=True)
class Want:
    rev: int
    body: Any = None

@dataclass
class Pass:
    started: list = field(default_factory=list)
    stopped: list = field(default_factory=list)
    restarted: list = field(default_factory=list)
    waiting: list = field(default_factory=list)
    failed: list = field(default_factory=list)
```

Весь словарь модуля, кроме отката (шаг 5) и положения (шаг 7). `Want` — желаемое одного ключа: ревизия, которую цикл сравнивает, и `body`, который он не читает вовсе — это строка, из которой воркер соберёт конвейер. `Pass` — что сделал один проход, ключ за ключом, в том порядке, в каком сделал. Пишет его в пульс воркер, если хочет; сам помощник не пишет ничего.

Импорты — `random`, `time`, `dataclasses`, `types`, `typing`. Ни одного из `w2cplatform`, ни одного из `vms`, хотя файл лежит в платформе. **Цикл не знает, что такое камера, воркер, эпоха, аренда и хранилище.** Отсюда и переносимость: в уроке 10 этот же класс будет крутить записи — регистратор наследует воркер VMS вместе с его циклом.

Помощник — не шаг жизненного цикла и не крючок (ADR 0002): воркер зовёт его, а он не зовёт у воркера ничего, кроме двух функций, с которыми построен. База воркера по-прежнему объявляет проход, `reconcile_once`, и не реализует его (М10A, урок 8, шаг 8): что значит «работает», знает только воркер. Воркер `testsub` в тесте границы пишет проход десятком строк без всякого помощника, детектор VMS (урок 14) — своим проходом. Помощник **необязателен**; он для тех, у кого единицы — набор долгоживущих конвейеров.

## Шаг 2 — Состояние, которого нет на диске

```python
class Reconciler:
    def __init__(self, start: Callable[[Hashable, Want], bool], stop: Callable[[Hashable], Any],
                 backoff: Backoff | None = None, restart: Callable[[Hashable, Want], bool] | None = None):
        self._start, self._stop, self._restart = start, stop, restart
        self._backoff = backoff if backoff is not None else Backoff()
        self.now: Callable[[], float] = time.monotonic
        self.rand: Callable[[], float] = random.random
        self.stall_failures = 3
        self._running: dict = {}
        self._up_since: dict = {}
        self._failures: dict = {}
        self._wanted: dict = {}
```

Два обязательных аргумента — две функции: `start(key, want) -> bool` (`False` — запуск не удался) и `stop(key)`. Третья необязательна, `restart(key, want) -> bool`, о ней шаг 3. Глаголов, хранилища, протокола «магазина» нет: желаемое приходит в каждый проход аргументом.

Комментарий над классом написан капслоком, и он заслужен: **`_running` — IN MEMORY ONLY: a persisted one is a cache that lies.**

Соблазн его сохранить огромен. Процесс перезапустился — он «знает», что камера 7 работала на ревизии 3, и не трогает её. Экономия целого прохода.

И это ложь ровно в момент перезапуска. Процесс умер — умерли его конвейеры. Сохранённое `_running` утверждало бы, что камера работает, когда её никто не держит, и камера не поднялась бы **никогда**: цикл на каждом проходе видел бы ревизию не ниже желаемой и пропускал её.

Правило, которое из этого следует и которое стоит держать шире цикла сверки: **кэш, переживающий процесс, чьё состояние он описывает, — это кэш, который врёт.** Свежий экземпляр начинает с пустого `_running` и заново поднимает всё, что должно работать. Один лишний проход в обмен на невозможность соврать.

Поля — `now` (часы задержек, секунды, монотонные), `rand` (равномерное в `[0, 1)`) и `stall_failures` (после скольких неудач подряд единица объявляется застрявшей). Часы и случайность — поля, а не вызовы внутри цикла, и от этого зависит вся проверяемость: тест джиттера (двести камер, откаты в интервале) подставляет свои часы и выполняется мгновенно и детерминированно. Воркер VMS ставит в `now` свои часы (урок 3). А `start`, `stop` и откат — не поля: откат проверяется один раз, конструктором, и ничто не подменяет его мимо этой проверки.

## Шаг 3 — Проход: сначала стоп, потом перезапуски, потом старты

```python
    def once(self, desired: dict) -> Pass:
        now, p = self.now(), Pass()
        self._wanted = {k: w.rev for k, w in desired.items()}
        self._settle(now)
        for key in [k for k in self._failures if k not in desired]:
            del self._failures[key]                   # nobody wants it now: its next start is a first one (ADR 0033)
        for key in list(self._running):
            if key not in desired:
                self._stop(key)
                …
                p.stopped.append(key)
        behind = [k for k, w in desired.items() if k in self._running and self._running[k] < w.rev]
        fresh = [k for k in desired if k not in self._running]
```

`desired` — словарь `{ключ: Want}`. Что в него войдёт, решает воркер: у держателя камер это включённые строки назначения, `{r["id"]: Want(r["revision"], r) for r in self.desired() if r["enabled"]}` (урок 3). Выключенные вообще не попадают в желаемое. Не «попадают и останавливаются»: их там нет, и остановит их цикл остановки, ровно тем же путём, что и удалённые. Одна дорога для «выключили» и «удалили» — меньше кода и меньше случаев.

И главная строка урока — то, что оставляет работающий ключ в покое:

```python
        behind = [k for k, w in desired.items() if k in self._running and self._running[k] < w.rev]
```

Перезапускается ключ, чья работающая ревизия **меньше** желаемой; ключ на желаемой ревизии или дальше не трогается. Это `>=`, а не `==`. Разберём, почему каждая альтернатива хуже.

`==` сломается, когда действительная ревизия окажется *больше* желаемой. Кажется невозможным — но возможно: контроллер откатил правку, вернув старое значение, а воркер уже запустил новую. При `==` цикл увидит несовпадение и перезапустит конвейер, который и так делает нужное.

`!=` — то же самое другими словами.

`>=` читается как утверждение о достаточности: *у меня работает не хуже, чем просят.* Это и есть контракт сверки. Не «состояние совпало», а «желаемое достигнуто».

```python
        for key, done in [(k, p.restarted) for k in behind] + [(k, p.started) for k in fresh]:
            failed = self._failures.get(key)
            if failed is not None and now < failed[1]:
                p.waiting.append(key)
                continue
            if done is p.restarted and self._restart is None:
                self._stop(key)                       # no restart of its own: a restart is a stop, then a start
                …
            call = self._restart if done is p.restarted and self._restart is not None else self._start
            if call(key, desired[key]):
                self._running[key] = desired[key].rev
                self._up_since[key] = now
                done.append(key)
            else:
                self._fail(key, now)
                p.failed.append(key)
        return p
```

Порядок прохода — **стопы, затем перезапуски, затем старты**, ключи в порядке `desired`. То, что остановлено, свободно раньше, чем что-то запустится: ёмкость, которую держала ушедшая камера, достаётся пришедшей в том же проходе (`test_a_pass_stops_first_then_restarts_then_starts`).

Проверка отката — **после** проверки ревизии. Порядок важен: единица, которая уже сошлась, не должна ждать отката от старой неудачи. Ключ, чья задержка не прошла, попадает в `waiting` без попытки.

**Перезапуск — одним вызовом, если воркер его дал.** Без `restart` перезапуск — это стоп, затем старт. С ним ключ на меньшей ревизии перезапускается одним вызовом — и для держателя камеры в этом вся разница: стоп отпускает аренду, старт берёт новую эпоху, то есть новый писатель на каждую правку строки, разрыв потока `<id>/e<эпоха>` и отказ, если хранилище молчит. Воркер VMS даёт все три функции (урок 3): правка камеры сохраняет эпоху и аренду. Цикл об эпохах не знает и знать не должен — он знает только, что вызовов может быть один или два. Неудачный перезапуск через `restart` оставляет ключ работающим на старой ревизии: следующая попытка — снова перезапуск, после задержки.

Возврат — `Pass`, а не `None`. Тесты читают его, воркер логирует и кладёт в пульс, и это дешевле, чем разбирать журнал.

## Шаг 4 — Цикл остановки

```python
        for key in list(self._running):
            if key not in desired:
                self._stop(key)
                self._running.pop(key, None)
                self._up_since.pop(key, None)
                p.stopped.append(key)
```

Пять строк, и в них — вторая по важности мысль урока после `>=`. Комментарий над `once` говорит её словами: *the stop loop walks what is RUNNING.*

**Цикл остановки идёт по тому, что работает, а не по желаемому.** Разница видна на вопросе: как остановить камеру, которой больше нет в конфигурации?

Если идти по желаемому, её там нет — и остановить её нечем. Конвейер продолжит работать, соединение с камерой останется, файлы будут писаться, и единственным способом это заметить будет ручной осмотр процесса.

Идя по тому, что *работает*, цикл спрашивает иначе: «вот что я держу — нужно ли оно ещё?» И отвечает на оба случая сразу: строку удалили, строку выключили. Обе выпали из `desired`, обе останавливаются.

`list(self._running)` — копия ключей, потому что словарь меняется внутри цикла.

Ещё одно следствие, менее очевидное: **цикл остановки останавливает только то, что запускал он сам**. Конвейер, поднятый предыдущим экземпляром процесса и переживший его, в `_running` не попадёт. Это не дыра — это ровно та ситуация, ради которой существует эпоха (урок 6 М10A): предыдущий экземпляр умер вместе со своими конвейерами, а если не умер, его отсечёт эпоха, а не цикл.

## Шаг 5 — Откат с джиттером

```python
@dataclass(frozen=True)
class Backoff:
    base: float = 1.0
    max: float = 60.0
    jitter: float = 0.5

    def __post_init__(self):
        if not self.base > 0:
            raise ValueError(f"backoff base must be positive, not {self.base!r}")
        if not self.max >= self.base:
            raise ValueError(f"backoff max ({self.max!r}) is under its base ({self.base!r})")
        if not 0 < self.jitter <= 1:
            raise ValueError(f"backoff jitter must be in (0, 1], not {self.jitter!r}: without it, units that failed "
                             f"together retry together")

    def delay(self, n: int, rand: float) -> float:
        return min(self.max, self.base * 2 ** (n - 1)) * (1 - self.jitter + 2 * self.jitter * rand)
```

Две строки арифметики и три проверки, за которыми — авария, которую они предотвращают.

`min(max, base·2^(n−1))`: первая неудача — секунда, вторая — две, третья — четыре, и на седьмой база упирается в минуту. Обычная экспонента с потолком.

`1 − jitter + 2·jitter·rand` — множитель, равномерный в **`[1 − jitter, 1 + jitter]`**, при умолчании — от половины до полутора. Задержка разбросана вокруг базы в обе стороны. Это и есть джиттер.

Зачем он. Представьте двести камер на одном воркере и упавший коммутатор. Все двести отказывают в одном проходе. Без джиттера все двести получат `retry_at = now + 1` — и через секунду воркер попытается поднять двести конвейеров одновременно. Коммутатор всё ещё лежит, все двести снова отказывают, все получают `now + 2`. Система превращается в синхронный молот, бьющий по сети всё реже, но всё сильнее.

С джиттером те же двести откатов **размазаны по интервалу от 0,5 до 1,5 секунды**, и попытки идут ровным потоком. Тест М9 это и проверяет: двести камер, отказавших в `now=0`, имеют `retry_at` в `[0,5; 1,5]` с разбросом больше полусекунды; в `0,49` все двести ждут, к `1,5` пробуются все.

Поэтому джиттер **нельзя выключить**: `jitter = 0` — отказ конструктора, как и всё больше единицы, при котором задержка стала бы отрицательной. Откат без разброса — это одна и та же задержка у всех единиц, отказавших в одно мгновение, то есть ровно тот молот, от которого откат строили. Ошибка не в коде цикла, а в настройке, и ловить её надо там, где настройка рождается. Там же ловятся ещё две (четырнадцатое ревью, minor 22; так же проверяет продуктовый `Backoff.Check`): база не больше нуля даёт нулевую задержку каждой неудаче — отказавшая единица пробуется на каждом проходе, то есть отката нет вовсе, — а потолок меньше базы делает первую же задержку потолком, и удваивать нечего. Проверки написаны как `not self.base > 0`, а не `self.base <= 0`: так `NaN`, для которого ложно любое сравнение, тоже отказ.

Потолок — потолок **базы**. Самая долгая задержка — `(1 + jitter)·max`, при умолчаниях 90 секунд, и это число известное и конечное: тест держит `max(waits) <= 90`. Разброс в обе стороны держит среднюю задержку равной базе: экспонента остаётся экспонентой, а не сдвигается вниз или вверх от того, что её размазали.

```python
    def _settle(self, now: float) -> None:
        for key in [k for k in self._failures if k in self._up_since and k in self._wanted
                    and self._running[k] >= self._wanted[k] and now - self._up_since[k] >= self._backoff.max]:
            del self._failures[key]
```

**Успех стирает неудачи не сразу.** Счёт ключа обнуляется, только когда единица продержалась `backoff.max` после своего запуска. Иначе конвейер, умирающий через секунду после каждого старта, вечно перезапускался бы с первой, самой короткой задержкой. С этим правилом он ждёт всё дольше — 1, 2, 4, 8, 8 при потолке 8, — а продержавшись `max`, зарабатывает счёт обратно (`test_a_unit_that_dies_after_every_start_waits_longer_and_one_that_stays_up_earns_its_count_back`).

**И продержаться значит продержаться на желаемой ревизии.** Первая версия условия смотрела только на `_up_since`. Камера пишет час, оператор правит строку, перезапуск на месте отказывает — а ключ всё ещё работает на старой ревизии, и его `_up_since` часовой давности. Такой `_settle` в начале каждого прохода стирал счёт: перезапуск повторялся на каждом проходе без растущей задержки, `/metrics` показывали `lagging, failures 0`, и `stalled` не наступал никогда (четырнадцатое ревью, major 7, проба `base/b1`). Час, который ключ продержался, заработал обратно неудачи **до** него, а не неудачи перезапуска, который отказывает сейчас: отставший ключ не держит ничего из того, что просят. Поэтому `_settle` зовётся после того, как `_wanted` стал желаемым этого прохода, и стирает счёт только у ключа, работающего на нём или дальше, — как продуктовый `reconcile.go`, где отставший ключ уходит в `stale` раньше, чем дойдёт до стирания. Тест: `test_a_unit_that_held_past_max_and_then_fails_its_restart_counts_waits_longer_and_stalls` — 1, 2, 4 секунды и `stalled` на третьей неудаче.

**Счёт живёт, пока ключ желаем.** Вторая строка шага 3, сразу за `_settle`, стирает неудачи каждого ключа, которого нет в `desired` этого прохода, — раньше, чем что-то остановлено или запущено. Без неё счёт переживал бы ключ: камера, дважды отказавшая и уехавшая к другому воркеру, вернувшись раньше своего мгновения, ждала бы его, а вернувшись хоть через неделю, первой же неудачей новой жизни получала бы третью по счёту — задержку 4 вместо 1 и `stalled` на экране, хотя в этой жизни отказала один раз. Вернувшийся ключ — **новая жизнь**: пробуется сразу, и первая его неудача ждёт базу. Ключ, желаемый всё время, свой счёт держит, пока его не сотрёт `_settle` или `reset_backoff`. Стирается только счёт: работающий нежеланный ключ — забота цикла остановки (шаг 4). Так и продуктовый `Once` (`w2cplatform/reconcile.go`): *nobody wants it now: its next start is a first one*, одно правило (ADR 0033). Тест: `test_a_unit_nobody_wants_loses_its_count_and_comes_back_a_new_life_while_one_still_wanted_keeps_its_count` — после двух неудач (1, 2) ключ выпадает на один проход и возвращается с задержкой 1, а не 4; соседний ключ, желаемый всё время, ждёт свои 2 и падает в третий раз с задержкой 4.

## Шаг 6 — Четыре выхода из «работает»

```python
    def forget(self, key) -> None:
        self._running.pop(key, None)
        self._up_since.pop(key, None)
        self._fail(key, self.now())

    def drop(self, key) -> None:
        self._running.pop(key, None)
        self._up_since.pop(key, None)

    def clear(self) -> None:
        self._running.clear()
        self._up_since.clear()

    def reset_backoff(self, *keys) -> None:
        if not keys:
            self._failures.clear()
        for key in keys:
            self._failures.pop(key, None)
```

Помимо `once`, ключ уходит из работающих четырьмя путями, и различаются они тем, **почему**.

**`forget` — умер сам или потерял аренду, оставаясь своим.** Конвейер умер под циклом — не по команде, а сам. Актуатор скажет об этом, когда воркер вычерпает его шину, и воркер позовёт `forget` (урок 4, `drain_bus`). Тем же путём уходит камера, чья аренда потеряна, когда назначение всё ещё отдаёт её этому воркеру (урок 4, `stop_unit`; ADR 0033 с дополнениями, четырнадцатое ревью, minor 22). Два действия, и второе неочевидно: убрать из работающих — понятно, следующий проход поднимет заново. Но зачем **считать неудачу**? Затем, что камера, чей конвейер падает сам по себе, — это камера с проблемой, и мгновенный перезапуск превращает её в цикл «поднялся — упал — поднялся» с частотой прохода. Засчитанная неудача даёт откат, откат даёт паузу, а после трёх падений единица становится `stalled`, и это видно на экране.

**`drop` — остановил воркер, мимо цикла.** Камера уехала к другому воркеру — её аренда потеряна, и в назначении её больше нет, — место записи перестало подходить: воркер остановил конвейер сам (`stop_unit`, урок 4). Камера ни в чём не виновата — неудачи нет. Старые неудачи `drop` не трогает: у камеры, которая всё ещё желаема, они остаются, а у уехавшей уйдут на ближайшем `once`, где её нет в `desired` (шаг 5). А потеря аренды на камере, которая всё ещё своя, — это `forget`: кто-то раз за разом берёт её эпоху (зомби) или хранилище раз за разом не подтверждает аренду, и три такие потери за `max` должны дать `stalled` на экране, а не камеру, перезапускаемую сразу и вечно. Так решает и продукт (`Forget` в `vms/worker.go`).

**`clear` — отсечён процесс.** Экземпляр огорожен — строка его слота называет другой экземпляр (М10A, урок 8, шаг 9), — всё остановлено, и цикл должен забыть, что что-то держал, **не трогая запуск и стоп**: стоп уже вызван снаружи. Зовёт `clear` воркер VMS из двух своих ответов рантайму платформы: `fence_units` (сначала `actuator.stop_all()`, потом `clear`) и `forget_units` (когда огороженный возвращается под другим именем, урок 4). Неудачи остаются: `clear` не засчитывает новых, потому что камеры ни при чём, и штрафовать их откатом было бы наказанием за чужую вину, — но и не стирает старых.

**`reset_backoff` — вернулось то, чего ждали.** Открылся том, на котором записи отказывали; слот взят под новым именем, и то, что отказывало под старым, здесь ничего не ждёт. Неудачи названных ключей уходят, а без имён — все. `forget_units` у воркера VMS зовёт его без имён сразу после `clear`.

Разница в одной строке на каждый случай: `forget` — про одну единицу, и виновата единица; `drop` — про одну, и не виноват никто; `clear` — про все, и виноват процесс; `reset_backoff` — не про работающих вовсе, а про то, сколько ждать.

## Шаг 7 — Три положения

```python
@dataclass(frozen=True)
class Position:
    state: str
    lag: int
    failures: int = 0
    retry_at: float = 0.0

class Reconciler:
    …
    def status(self) -> dict:
        self._settle(self.now())
        out = {}
        for key, rev in self._wanted.items():
            lag = max(rev - self._running.get(key, 0), 0)
            n, retry_at = self._failures.get(key, (0, 0.0))
            state = (CONVERGED if key in self._running and lag == 0
                     else STALLED if n >= self.stall_failures else LAGGING)
            out[key] = Position(state, lag, n, retry_at)
        return out
```

Статус **вычисляется**, а не хранится. Нет поля «состояние», которое кто-то обновляет; есть функция от желаемого последнего прохода, работающего и неудач. Это то же решение, что `_running` в памяти, применённое к отчётности: то, что можно вывести, не хранят, потому что хранимое расходится.

Три положения и отставание числом:

| Положение | Когда | Что означает для оператора |
|---|---|---|
| `converged` | работает, отставание 0 | правда соответствует желаемому |
| `lagging` | отставание есть, неудач меньше `stall_failures` | идёт работа, подождите |
| `stalled` | отставание есть, неудач `stall_failures` и больше | не получается, смотрите |

`max(…, 0)` — та же защита, что и `>=` в проходе: действительная ревизия может обогнать желаемую, и отрицательное отставание бессмысленно. У неработающего ключа отставание — вся его ревизия. И потому `converged` спрашивает ещё и «работает ли»: строка без `revision` желаема на ревизии 0, и ключ, чей старт отказал пять раз, имел бы отставание 0 и назывался бы «сошлось» (четырнадцатое ревью, minor 21). Ключ, который ничего не держит, не `converged` никогда.

Отставание отдаётся числом, а не флагом, потому что «отстаёт на 1» и «отстаёт на 7» — разные новости: во втором случае правок накопилось семь, и ни одна не доехала. Рядом — сколько неудач подряд и когда следующая попытка: `retry_at` на тех же часах, что `now`.

## Результат

```python
rows = [cam(1)]
r = Reconciler(lambda k, w: act("start", w.body), lambda k: act("stop", {"id": k}),
               restart=lambda k, w: act("restart", w.body))

r.once(_wants(rows)).started      # [1]
r.once(_wants(rows))              # Pass()           — сошлось, ничего не делается
rows[0]["revision"] = 2
r.once(_wants(rows)).restarted    # [1]
rows[0]["enabled"] = False
r.once(_wants(rows)).stopped      # [1]

Reconciler(…).running()           # {}               — свежий экземпляр начинает заново
```

`_wants(rows)` — то, что воркер просит у цикла: `{c["id"]: Want(c["revision"], c) for c in rows if c["enabled"]}`.

Семь тестов М9 против помощника платформы — зелёные, без правки смысла (`tests/test_lesson4_worker.py`, `test_1_converge_then_idle` … `test_7_lagging_vs_stalled`):

1. сходится и замолкает;
2. изменение ревизии перезапускает;
3. выключение и удаление останавливают;
4. свежий экземпляр выводит всё заново;
5. сохранённое `_running` врёт (тест написан как демонстрация);
6. двести отказов размазаны джиттером;
7. три неудачи — `stalled`, `forget` возвращает в `lagging`.

А `tests/test_reconcile.py` проверяет то, чего у М9 не было, на воркерах `testsub` и `testsub2`, без единого слова о камерах: удвоение до потолка, разброс внутри `[1 − J, 1 + J]`, отказ `jitter = 0`, два ключа с одной историей неудач, которые не ждут одинаково, счёт, обнуляемый только после `max` на желаемой ревизии, счёт, уходящий вместе с ключом из желаемого, отказ базы не больше нуля и потолка меньше базы, неработающий ключ, который не `converged`, порядок «стопы, перезапуски, старты», перезапуск одним вызовом против стопа со стартом, и `drop`, `clear`, `reset_backoff`, `status`.

## Что может пойти не так

- **Сохранить `_running` на диск.** Камеры не поднимутся после перезапуска — никогда, без единой ошибки в журнале.
- **`==` вместо `>=`.** Откат правки вызовет перезапуск конвейера, который и так делает нужное.
- **Цикл остановки по желаемому.** Удалённая камера останется висеть соединением, и заметят это по счёту лицензий на камере, которой нет в списке.
- **Откат без джиттера.** Двести камер будут бить по упавшей сети синхронным залпом; через час это заметят на сетевом оборудовании, а не в VMS. Поэтому `jitter = 0` не проходит конструктор.
- **Успех, стирающий неудачи сразу.** Конвейер, умирающий через секунду после старта, перезапускается раз в секунду вечно.
- **Перезапуск правки стопом и стартом у держателя.** Новая эпоха на каждую правку имени: новый писатель, разрыв потока, отказ при молчащем хранилище.
- **`drop` вместо `forget` при потерянной аренде своей камеры.** Зомби, раз за разом берущий её эпоху, или хранилище, раз за разом не подтверждающее аренду, дают камеру, перезапускаемую сразу и вечно, без `stalled`. А `forget` для камеры, которая уехала, — штраф за переезд.
- **Счёт, стираемый у отставшего ключа.** Перезапуск правки, отказывающий каждый раз, идёт на каждом проходе без задержки и никогда не становится `stalled`.
- **Счёт, переживающий ключ.** Камера, вернувшаяся после переезда, ждёт откат прошлой жизни, а первая её неудача считается к старым: долгая задержка и `stalled` раньше времени.
- **`time.monotonic()` внутри цикла вместо поля `now`.** Тест джиттера станет невоспроизводимым, и его выкинут первым.
- **`status`, хранимый в поле.** Рано или поздно поле и правда разойдутся, и верить перестанут обоим.

## Итог

- Цикл сверки — помощник платформы (ADR 0033): нужен двум подсистемам, и откат с джиттером — инвариант, который платформа обязана дать. Шаг `reconcile_once` остаётся у воркера, помощник необязателен.
- Цикл не знает ни хранилища, ни того, что значит «запустить»: две функции, необязательная третья, ни одного импорта из проекта.
- Желаемое персистентно, действительное выводится: кэш, переживающий процесс, чьё состояние он описывает, врёт.
- `>=` означает «не хуже, чем просят», и переживает откат правки.
- Проход: стопы, перезапуски, старты; цикл остановки идёт по тому, что работает, и потому ловит и выключенное, и удалённое одним путём.
- Джиттер разбрасывает откат в `[1 − J, 1 + J]` вокруг базы и не выключается; счёт неудач стирается, только когда единица продержалась `max` на желаемой ревизии, — или вместе с ключом, выпавшим из желаемого: вернувшийся начинает с базы (ADR 0033).
- `forget` — про единицу и со штрафом; `drop` — про единицу и без штрафа; `clear` — про процесс, неудачи остаются; `reset_backoff` — неудачи уходят.
- Статус вычисляется из желаемого, работающего и неудач; отставание — число, не флаг.
