## Находки

### Урок 6

**K31-01 — существенная. Н4 не содержит отказ удаления `platform/epoch_floor` из never Н1.3.**
Место: `М10_Platform/spec/06-rights.norms.md:214` (строка Н4 «удаление строки эпохи; удаление под `domain/` не ролью домена; запись `epoch_floor`») против `:78` (Н1.3 never: «write и delete platform/epoch_floor (только операция восстановления, урок 11)»).
Что не так: Н4 — закрытая таблица отказов урока; случай `delete platform/epoch_floor` нормой Н1.3 определён (отказ и для admin), но в таблице названа только запись. Читатель, реализующий отказы по Н4, удаление пола эпохи не покрывает. Лекция (`06-rights.md:47`, «написать … иначе как операцией восстановления») повторяет то же сужение.
Контрпример: `DELETE platform/epoch_floor` от admin — по Н1.3 отказ `403 forbidden` (never), в Н4 причина отсутствует.
Правило: ADR-0080 (Н4 — закрытый список; каждый отказ Н1–Н3 представлен в Н4).
Рекомендация: расширить причину строки Н4 до «запись и удаление `platform/epoch_floor`».

**K31-02 — существенная. Правило раннера «error содержит роль и ключ» для голого 403 противоречит Н2 на сценарии 08.**
Место: `Source/tests/testdata/acceptance/М10_Platform/06/README.md:15` («expect без тела у кода 403 — … с ролью и ключом в error; раннер проверяет kind и что error содержит роль и ключ») + `scenarios.tsv:39` (сц. 08, заголовок роли на сокете роли, expect — голый `403`) против `М10_Platform/spec/06-rights.norms.md:141–142` (Н2: «для отказа самой личности … — роль и причину/маршрут») и `:177` (Н3: отказ на этапе личности, до разбора операции).
Что не так: сц. 08 — отказ личности (заголовок на сокете роли); канон требует в error роль и причину, ключ не требуется и на этом этапе тело запроса может быть ещё не разобрано. Раннер по README обязан найти в error и ключ (`testsub/counters/c8`). Дополнительно не определено, чья роль названа — сокета (`testsubworker`) или заголовка (`console`).
Контрпример: реализация отвечает `{kind: forbidden, error: "testsubworker: role header on a role socket"}` — соответствует Н2/Н3/Н4, но заваливает сц. 08.
Правило: ADR-0080 (приёмка исполнима по README и не требует сверх норм урока).
Рекомендация: в README ограничить проверку «роль и ключ» отказами операций над строкой; для сц. 08 требовать роль (назвать чью) и причину по Н2.

**K31-03 — существенная. Закоммиченный файл прав содержит пометку генерации полем внутри JSON — против закрытой формы Н1.2.**
Место: `Source/deploy/cluster/configstore-rights.json:2` (`"comment": "generated by … — do not edit, regenerate"`) против `М10_Platform/spec/06-rights.norms.md:36–38` (Н1.2: «единственное поле `roles`… Неизвестные поля отвергаются», «неверная форма — файл отказан целиком»), `:166–167` (Н3 шаг 5: «generated — do not edit» — «не комментарий и не добавочное поле внутри JSON»), `spec/06-rights.api.openapi.yaml:166–177` (`RightsFile`: `additionalProperties: false`).
Что не так: ADR-0082 доп. 14 (MODIFIED М10/6-02) закрепил «пометка о генерации находится вне JSON», но закоммиченный артефакт — предмет сверки Н5 («равенство закоммиченного сгенерированному», `06-rights.norms.md:244`) — держит пометку полем `comment` внутри JSON. Демон по Н1.2 обязан отказать такой файл целиком и не стартовать.
Контрпример: загрузка закоммиченного файла хранилищем, исполняющим Н1.2, → отказ формы; моя проба схемой `RightsFile` отвергает ровно эту форму (`{"roles": …, "comment": …}`). Ожидаемо: артефакт проходит собственную сверку; фактически: он невалиден по канону этого же урока.
Рекомендация: перегенерировать файл без поля `comment` внутри JSON (пометку — вне JSON) и привести `configstore-rights.json.md` в соответствие.

**K31-05 — мелкая. Н1.1 помещает `console` в блок `per_spec`, хотя роль одна на кластер.**
Место: `М10_Platform/spec/06-rights.norms.md:16–20` (`per_spec:` → `console: одна на кластер; …`).
Что не так: заголовок блока читается «из каждой спеки каталога», а первая его строка — исключение; врезка спасает только комментарием. Лекция (`06-rights.md:25`) верна.
Рекомендация: вынести `console` из `per_spec` (отдельной строкой уровня `platform`), чтобы структура не предлагала роль на спеку.

### Урок 7

**K31-04 — мелкая. Неясно, буквальна ли «k» в сообщении о чужом kid.**
Место: `М10_Platform/spec/07-secrets-and-sealing.norms.md:57–58` (Н1.2 `open_without`: «sealed with key k, which this process does not hold»).
Что не так: рядом стоящее сообщение («sealed and this process has no key») — буквальная строка; здесь `k` читается то ли как буквальное «k» (бесполезная диагностика без номера ключа), то ли как неоформленный `<kid>`.
Рекомендация: записать «sealed with key `<kid>`, …» или явно пометить буквальность.

## Проверенные зависимые участки М10/3 (без находок)

- `SealingUnavailable` (`03-….api.openapi.yaml:293–299`): `error: unavailable`, фиксированный `detail: "the sealing key is set and does not read"`, без `fault` — совпадает с М10/7 Н2 (`07-….norms.md:136`) и Н4 (`:233`) и строкой М10/3 Н4 (`03-….norms.md:571`).
- Привязка к операциям: `WriteUnavailable` (oneOf `Unavailable|SealingUnavailable`) назначен только POST `/{rows}` и PUT `/{rows}/{id}`; GET и DELETE сохраняют `Unavailable` — как требует ADR-0082 доп. 14 и README приёмки 07 («GET/DELETE не получают эту новую причину»). Пробами подтверждено: тела кольца и `busy` различимы ровно одной ветвью oneOf; «error: unavailable» с иным detail отвергается обеими.
- Память повторов/заявки: М10/7 Н2 (:136), Н4 (:233), инструкция (п. 5) и corrections07 сходятся на «5xx не done; судьба pending и запрет снимать чужую заявку — М10/3 Н3»; отпечаток идемпотентности (`07` Н1.2 `print`, HMAC под производным ключом кольца / отпечаток маскированного тела без ключа) согласован со сц. 01.2 (повтор ключа возвращает сохранённый ответ с маской).
