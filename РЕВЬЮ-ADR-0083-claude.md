# Ревью ADR-0083 доп. (34): скорость генерации

Срез — `origin/main` `dd740a9bd`.

Прочитано:
- `decisions/0083-микромодули-платформы.md`, доп. (34) (строки 773–792), доп. (25)–(33) (строки 591–772);
- разделы «Векторы» договоров `Platform/common/contracts/*.md`;
- P/06.4 Н5 (что проверяется чтением).

Код генераций (`cammeta-c-*`), их внутренние записки и чужие отчёты не читались. Поэтому «независимую публичную
проверку» сужу по словам ADR — в курсе она не определена (М-1).

## Вывод: с правками

Найдено 2 существенных и 3 мелких, блокеров нет.

- **П. 2** исполним и с доп. (25)–(33) согласен: переход по-прежнему сменой `SPEC_VERSION` скриптом (доп. (29) п. 4),
  выгрузок просто меньше.
- **П. 4** исполним. Риски — переделка кода, уже написанного по старой раскладке, и одна большая дельта перехода
  (М-2).
- **П. 1** снимает раннюю независимость там, где её больше ничто не даёт: у договоров без векторов и у поведения,
  которого приёмка не видит (С-1).
- **П. 3** в нынешнем виде открывает угадывание без записи. Он расходится с доп. (29) п. 5: ответ на догадку — без
  пересказа, сменой `SPEC_VERSION` (С-2).

## Что ловит приёмка и что теряется без ранней независимой проверки SDK

Пакет SDK после п. 1 до кандидата проверяет только сессия `common`, тестами, которые написала она же из того же
текста договора. Независимая проверка приходит у кандидата.

| Что | Кто ловит до кандидата после п. 1 | Ловит ли приёмка у кандидата |
|---|---|---|
| поведение, названное векторами договора | `common` (все векторы через API и CLI) | да, если сценарий уроков идёт через этот путь |
| договор без векторов: `forwarding`, `gate-and-pass`, `holds`, `local-token-door`, `secret-files` (5 из 36) | только свои тесты `common` по тексту договора (доп. (32) п. 2) — та же голова, что писала код | частично: только то, что видно на дверях сценариев |
| поведение внутри процесса — порядок вызовов SDK воркера, повторы клиента хранилища, замок присутствия, гонки | никто | нет, если нет сценария. Таймеры, fsync, потоки и сбои — «проверяются чтением», 27 файлов норм это говорят (P/06.4 Н5 `:407`: «ни одно не заменяет исполнение … на стенде») |
| сила тестов SDK (мутанты) | никто | нет: приёмка проверяет поведение, а не тесты |
| воспроизводимость сборки, точность архива (пересборка, точные архивы) | никто | нет |
| два урока закрепили разные версии одного пакета | проверки потребителя каждого урока порознь | только в сборке кандидата |

Итог: до кандидата слабое место SDK (договор без векторов или путь вне сценариев) расходится по всем потребителям.
Видно оно станет только у кандидата, а переделывать тогда — в каждом уроке.

## Существенные

### С-1. П. 1: независимость снимается там, где её больше ничто не даёт

- **Место.** `decisions/0083-микромодули-платформы.md:778–782`: «Промежуточный выпуск … сессия `common` проверяет
  обычными проверками … независимая публичная проверка … — **один раз**, при объявлении кандидата».
- **Контрпример.**
  - Договор `local-token-door` — «векторов нет». Библиотеку и её тесты пишет одна сессия `common` по одному тексту.
  - Сессия неверно прочла порядок проверок, и тест подтвердил то же прочтение. Уроки 09 и 03 (агент, который отвечает этой дверью, и воркер, который через неё
    просит токен) закрепили этот пакет и построили на нём своё.
  - До кандидата этого никто не увидит. Мутанты, которые показали бы, что тест не различает порядок, не
    запускаются. У кандидата приёмка поймает расхождение, только если сценарий проходит этот порядок. Если поймает —
    переделка в обоих уроках и новый кандидат.
- **Источник.** Доп. (32) п. 2 (договор без векторов — свои тесты по тексту); доп. (29) п. 1 (сессия `common` —
  одна); таблица выше.
- **Последствие.** Выигрыш во времени — ожидание независимой проверки на каждом патче. Плата — позднее обнаружение
  с умножением на число потребителей. Для договоров без векторов это не обмен скорости на риск, а потеря
  единственной внешней проверки до кандидата.
- **Предложение.**
  - **а)** Независимая проверка промежуточного выпуска — фоном, не задерживая потребителей: выпуск доступен сразу,
    отказ проверки — находка `common` и пометка «у пакета X находка» потребителям. Скорость та же, обнаружение ранее.
  - **б)** Если фон невозможен — оставить раннюю независимую проверку пакетам договоров без векторов и пакетам с
    двумя и более потребителями. Прочим — у кандидата.
  - У кандидата — только пакеты, изменённые после последней проверки. Тогда «один раз» значит «один раз на версию
    пакета».

### С-2. П. 3: «решение строкой журнала» не доходит до сессии урока без пересказа и открывает догадки без записи

- **Место.** `:785–787`: «решение строкой журнала — основание делать до выгрузки»; «(подтверждает доп. (25) п. 5)».
- **Контрпример.**
  - Доп. (25) п. 5: «решение идёт нормой и выгрузкой, генератор переходит на неё сменой `SPEC_VERSION`». Работы до
    выгрузки он не разрешает, так что «подтверждает» неточно.
  - Доп. (29) п. 5: «ответ на догадку — сменой `SPEC_VERSION` и id строки журнала, без пересказа». Сессия урока
    читает только своё рабочее место (доп. (27) п. 1).
  - Решение «Архитектора» — его строка во входящих курса. Сессии урока её не видно. Чтобы работать по решению, ведущая
    должна передать текст, то есть пересказ, которого доп. (29) п. 5 не допускает.
  - Пусть даже текст дошёл: строка решения — «выбрано: 409 `exists`, тело TextError». Слова `detail`, порядок
    проверки относительно схемы и запись журнала сессия добирает сама. Это догадки, но строк `GUESSES.md` у них нет:
    они сделаны «по решению».
  - Когда придёт норма, `TRANSITION-<spec>.md` ставит место в коде «каждому изменённому id нормы» (доп. (31) п. 6).
    Код, написанный по решению, — уже место. Запись «не затрагивает» скроет, что код писан не по этой норме. Python и
    Go доберут детали по-разному.
- **Источник.** Доп. (25) п. 5; доп. (27) п. 1; доп. (29) п. 5; доп. (31) п. 6; доп. (22) п. 2 (мера догадок — пробелы
  текста).
- **Последствие.** Угадывание возвращается мимо счёта догадок, а ограниченное чтение — мимо устройства, ради
  которого оно сделано «устройством, а не просьбой» (доп. (27)).
- **Предложение.**
  - **Канал:** решение приходит в `NN-*/GUESSES.md` той же строки — отметкой ведущей по шаблону «решено `<id>`:
    выбор догадки подтверждён». Либо «иное: `<поле>` = `<значение>`» — только наблюдаемые байты (код, поле, слово
    отказа), без доводов и ссылок на нормы. Это шаблон доп. (29) п. 5, расширенный полем значения. Фильтр — как у
    `CONTRACT.md` (доп. (33) п. 4).
  - **Предел:** до выгрузки работают только решения, которые подтверждают выбранное или задают его байтами целиком.
    Всё, чего в отметке нет, — новая строка `GUESSES.md`.
  - **Сверка:** запись перехода на выгрузку с нормой ставит каждой отметке «решено» id нормы и «совпало / исправлено».
    Расхождение решения и нормы — находка «Архитектору».
  - Слова «подтверждает доп. (25) п. 5» заменить на «дополняет доп. (25) п. 5, доп. (29) п. 5».

## Мелкие

### М-1. Состав «независимой проверки» и «обычных проверок» в курсе не определён

- **Место.** `:779–782`: «проверки потребителя, закреплённые версии у потребителя … независимая публичная проверка
  точных архивов, режимы, мутанты, пересборка … Не ослабляются: прогон всех векторов договора, закрепление версий,
  запрет копий общего алгоритма в уроках (доп. (28)–(33))».
- **Суть.**
  - В доп. (28)–(33) нет ни «закрепления версий», ни «запрета копий» этими словами. Ближайшее — доп. (25) п. 4 (общий
    код только библиотекой), доп. (26) п. 3 (нет импортов между микромодулями), доп. (31) п. 3 («у генерации одна
    реализация формата»).
  - «Режимы», «мутанты», «точные архивы» в курсе нигде не названы (`grep` по `decisions/`). Что именно сдвигается к
    кандидату, ревьювер ADR проверить не может.
  - «Один раз» — на кандидата или на генерацию? После отказанного кандидата — заново по всем пакетам или по
    изменённым?
- **Предложение.** Перечень в одной фразе со ссылкой на место, где он описан (README генерации или раннеров). Ссылки
  «не ослабляются» — на доп. (25) п. 4, (26) п. 3, (31) п. 3. «Один раз» — «на каждую версию пакета, вошедшую в
  кандидата» (С-1).

### М-2. П. 4: генерация не стоит — код по старой раскладке переделывается; одна большая дельта перехода

- **Место.** `:788–792`: «Итог — список во входящих … нормы — одной выгрузкой. Генерация во время аудита не стоит».
- **Суть.**
  - Строки аудита первого вида («алгоритмы и константы, нужные нескольким процессам, но записанные в главе одного
    урока») переносят текст в `common/contracts/`. Код, который уроки за время аудита напишут по главе соседа или по
    своей главе, станет копией общего алгоритма. По доп. (31) п. 3 он заменяется библиотекой.
  - Одна выгрузка всех норм аудита — большая дельта у каждой сессии. Если файл уходит из списка чтения урока
    (алгоритм вынесен из его главы, а глава остаётся в выгрузке), это «сужение»: сессия заменяется новой (доп. (29)
    п. 4, доп. (31) п. 6).
  - Почему 03–10, а не 01–02, не сказано.
- **Предложение.**
  - Строки аудита, которые переносят алгоритм в общий договор, — сразу пометкой ведущей сессиям-потребителям: «этот
    алгоритм — не писать до договора». Это `pending` по п. 2 только этого куска.
  - В итоге аудита — столбец «сужает чтение урока NN: да/нет», чтобы замены сессий были известны заранее.
  - Одной фразой — почему 01–02 вне аудита (уже пройдены или устоялись).

### М-3. П. 2 и п. 3 вместе: окно расхождения решения и нормы — до 2–3 часов работы

- **Место.** `:783–787`.
- **Суть.** С пачками решение и его норма расходятся во времени до 2–3 часов. Всё это время сессии пишут по решению
  (п. 3). Если «Спецификация», записывая норму, уточнит решение (так бывает: доп. (21)–(25) ADR-0091 — сплошь
  уточнения после ревью), переделка — у обоих языков.
- **Предложение.** В п. 2: «норма решения, по которому уже работают (п. 3), — в ближайшей пачке. Уточнение решения
  при записи нормы — отметкой в той же строке журнала до выгрузки, чтобы сессии остановились». Вместе с С-2 это
  закрывает окно.
