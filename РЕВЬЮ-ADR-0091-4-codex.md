Дата: 2026-10-22. Срез: **`8c6b0b96fbad8ae60efa1d42130deee944133b5d`**.
Ветка: `codex/review-adr-0091-4`.

**Вывод: с правками — 2 блокера, 1 существенная, 0 мелких; 3 причины.**

Блокеры остаются в гарантии удержания личности исполненного заказа: `made.keep` ограничивает только

## П. 1 — горизонт повтора

### R91.4-01 — блокер. keep не ограничивает физическое удаление воркером адресата

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:59`–60:

> «строку с `made` контроллер физически не удаляет (`delete_after`, `ends`) раньше `made.keep` по своим часам:
> пока повтор события возможен, его id занят».

Отсутствие удаления у **заказчика** (строка 38) правильно, но это не отсутствие удаления у **адресата**.

**Разрешённый профиль:** адресат `sink` с именованной `unit.rows: jobs`, id — поле `name`,
`worker.deletes: [jobs]`. Заказчик `source` объявляет создание в sink/jobs с `valid_for: 600`.
Новая задача `source-e` имеет `made: {by: source, at: 1000, keep: 1660}`. Можно взять конечную задачу
с состоянием result из п. 3; fixed-полей кроме id и `about` в примере нет.
Это допустимый общий профиль нового механизма, а не утверждение, что нынешний detjob уже объявляет deletes.

1. Задача исполнена. В t=1010 воркер **sink** физически удаляет свою строку с CAS прочитанной версии
   по существующему праву `worker.deletes`. Контроллер в этой операции не участвует.
2. Заказчик после обрыва до записи курсора повторно рассматривает то же событие в t=1301.
   Оно ещё моложе 600 с. Целевой id тот же, guard текущей эпохи заказчика правилен.
3. Строки нет; новая логическая попытка создания с CAS `""` успешна, born новый. Прежний итог относится
   к старому born и не удерживает новый запуск. Если состояние тоже уже убрано, результата вовсе нет.

Для разных логических вызовов допустимы разные id операций хранилища. Это не замена id у сетевого
повтора после ambiguous: такой повтор обязан сохранить свой id. Детерминированный id **единицы** один и тот же.

**Первичное основание:** `Platform/02-installer/spec/02.1-installer.norms.md:345`, 844 разрешает
`worker.deletes` для своей unit.rows; `Platform/02-installer/spec/02.5-installer.norms.md:94` выдаёт удаление
с CAS, без права записи. `Platform/04-controller/spec/04-controller.norms.md:143` прямо называет и этот
путь физического удаления. Новый отказ загрузчика или обязательная проверка made.keep для него не введены.
P/01.1 Н1, строки 87–90: CAS отсутствия проверяет отсутствие сейчас, а не историю ключа.
Обещание ADR:59–60 и Confirmation:160–161 требует отсутствия нового эффекта того же события.

**Последствие:** ограничение времени контроллера не обеспечивает заявленную занятость id на всём горизонте
повтора. Заказчик соблюдает префикс, valid_for, CAS и эпоху, но создаёт уже исполненную работу заново.

**Вопрос «Архитектору» / рекомендация:** распространить удержание made на каждый разрешённый путь
физического удаления, включая worker.deletes, либо явно отвергать сочетание адресата worker.creates
с таким удалением. Обычный операторский DELETE с надгробием — другой путь, сохраняющий занятость имени;
его запрещать ради этого примера не нужно.

**Происхождение:** сохранившийся случай класса R91.3-04. В `9b46188e4` гарантии удержания не было вообще;
`8c6b0b96f` вводит её только для контроллера. Нормы worker.deletes в Platform/ между срезами не менялись.
Это не новый разрешённый способ удаления, наведённый четвёртой редакцией, а неполное закрытие класса.

**Проба:** `recipient-worker-delete-bypasses-keep` в `probes-v2.py`: удаление раньше 1660 и повторный `ok`
с born=B. Проверены операции декодированных строк, не реальный воркер или загрузка полного манифеста.

### R91.4-02 — блокер. Достигнутый keep не отменяет уже подготовленную запись того же события

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:48`, 58–60:

> «`keep` = `at` + `valid_for` + 60»;
> «событие старше `valid_for` не исполняется»;
> «пока повтор события возможен, его id занят».

Последний вывод требует ограничить не только момент допуска события, но и момент применения уже
допущенной записи. Страж, заданный в ADR:45–46, проверяет эпоху **заказчика**, а не закрытие окна события.

**Контрпример без обхода ограничения удаления:** событие имеет время 1000, valid_for=600, keep=1660.
Часы контроллера опережают часы заказчиков на разрешённые 60 с. Адресат — именная конечная задача без ends,
без иных fixed-полей, с `delete_after: 1`, состоянием result и retire_when по done.
Предел delete_after ≥1 и ограничения формы — P/02.1:262, 804–806.

| Шаг | Часы заказчика | Часы контроллера | Состояние |
|---|---:|---:|---|
| Два логических вызова той же подсистемы обрабатывают тот же вход события и параметры; оба до записи читают отсутствие id и готовят создание | 1598.8 | 1658.8 | событию 598.8 с, обе попытки допустимы |
| Запись A с CAS `""` успешна; запись B ещё в пути | 1598.8 | 1658.8 | строка A с made.keep=1660 |
| Задача A быстро заканчивается и снята | 1598.82 | 1658.82 | результат done сохранён |
| Прошли delete_after и keep; контроллер законно удаляет строку первой, затем состояние | 1600 | 1660 | строки и результата нет |
| Запись B, отправленная раньше, применяется с прежним действующим guard своей эпохи и CAS `""` | 1600.1 | 1660.1 | CAS успешен: задача появилась снова |

Два вызова имеют собственные id операций `aa` и `bb`; каждый использует свой id при сетевых повторах.
Случай не требует нарушить P/03.4-07 заменой id после ambiguous. Made.by допускает работу нескольких единиц
одной подсистемы с одной строкой; правило ADR не запрещает конкурентные вызовы с одинаковой личностью
события/заказа. Детерминированность целевого id здесь соблюдена. Эпохи обоих заказчиков и права остаются
действующими. Задержка B — 1.3 с, поэтому потеря аренды или большое молчание не требуются.

**Первичное основание:** P/01.1 Н3 `записать`,
`Platform/01-store/spec/01.1-store.norms.md:255`–266 проверяет в момент применения только память id,
текущие guard и CAS. Запись не несёт проверяемого хранилищем срока действия; хранилище не толкует made.
P/03.2 Н1.5–Н1.6, строки 145–175, не меняет индекс эпохи просто по истечении valid_for чужого заказа.
Проверка времени в библиотеке до отправки не может отозвать уже отправленную запись.

Модель дополнительно рассмотрела и **тот же id операции**, а не два вызова: исходная запись применена
в t=1000; её повторная отправка уже в пути с t=1001; контроллер удалил строку после keep в t=1661;
отложенная копия применяется в t=1700. При 50 000 последующих записей P/01.1:311 разрешает забыть квитанцию,
после чего неизменные CAS/guard опять проходят. Это отдельное подтверждение предела фиксированного срока,
а не необходимость для основной трассы. Задержка и истечение памяти здесь — условия модели; сеть и 50 000
настоящих записей не выполнялись.

**Последствие:** даже идеально соблюдённый keep у всех удаляющих процессов не даёт обещанной безвредности
повторов. Первая задача уже выполнена, удержание закончено, а ранее допущенная запись создаёт новую жизнь.
Это отличается от R91.4-01: запрещение worker.deletes не исправляет эту трассу.

**Вопрос «Архитектору» / рекомендация:** выбрать границу, после которой ни один ранее допущенный вызов
не может создать этот id: проверяемое при применении закрытие допуска, долговечный исход либо объявленный
профиль с доказанным пределом доставки/применения и удержанием, учитывающим этот предел вместе с часами.
Просто ещё одна проверка now перед put или увеличение произвольной константы без предела доставки не
доказывает гарантию. Конкретный внутренний API не требуется.

**Происхождение:** сохранившийся случай класса R91.3-04, проявляющийся на новой границе keep.
До `8c6b0b96f` этот запаздывающий вызов также ничем не отсекался; новая правка откладывает удаление,
но не вводит барьер для уже допущенных записей. Это не утверждение, что именно правка впервые создала
возможность задержанной доставки.

**Пробы:** `late-prepared-create-after-keep` и `late-inflight-copy-after-keep`, `changed-clause-models-v2.json`.
События/время заданы конечной трассой; это не сетевой тест и не доказательство поведения конкретной реализации.

## П. 1 — возврат над надгробием

### R91.4-03 — существенная. Допуск часов позволяет старому событию выглядеть новее удаления оператора

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:61`–63:

> «над надгробием библиотека пишет только для события позже надгробия (`written`) … удалённое оператором
> повтор прежнего события не возрождает … новое событие запись заводит».

**Контрпример с разрешённым разбросом часов:** часы писателя события на 60 с впереди консоли.
По общему времени событие e произошло в 1000, получило stamp=1060 и уже завело запись `auto-7`.
Оператор удалил эту запись в 1020; written надгробия=1020. При повторном рассмотрении того же e в 1030
заказчик видит возраст всего 30 с по своим часам. Формальное сравнение `1060 > 1020` разрешает запись
с CAS надгробия и прежними fixed-полями, хотя это именно событие, исполненное **до** удаления.
Срок until=1060+10×60 ещё впереди; правило ends повтор не отклоняет.

**Первичное основание:** новый ADR сам допускает 60 с между часами писателей, строка 48, и ссылается на
`Platform/08-domain/spec/08.2-domain.norms.md:109`–111, где это предел **расхождения**, а не равенство часов.
Тот же ADR:62 и Confirmation:160–161 сохраняет намерение оператора — повтор прежнего события не возрождает
удалённое. Одно сравнение необработанных стенных времён этого не обеспечивает. Более общий запрет возрождения
старого события остаётся ясным, но описанная проверка времён не является его достаточным исполнением.

Контрпример предполагает, что Т-правка действительно добавит время удаления written к надгробию единицы:
сейчас P/06.1:33 и Н3:591 времени у него не задают (written тела `.gone/…` — другой объект).
Недостающая пока Т-правка сама по себе здесь не считается ещё одной находкой. Даже после добавления поля
сравнение часов без допуска остаётся неверным.

**Последствие:** библиотека может отменить ручное удаление при вполне допустимых часах.

**Вопрос «Архитектору» / рекомендация:** выбрать причинное правило возврата либо консервативное сравнение
с учётом допуска, например `event_at > written + 60`, и явно назвать исход для неопределённой полосы.
Второй вариант намеренно не признаёт заведомо новым событие в этой полосе; это сужение следует записать,
а не выдавать за точную хронологию. Проверка только equality/id последней операции не заменяет такого решения
для всех повторно читаемых событий.

**Происхождение:** наведено `8c6b0b96f`: в третьей редакции правило CAS `""` и занятое надгробием имя
не разрешало эту запись вообще; четвёртая редакция добавляет возврат по сравнению с written. Трасса после
правки даёт разрешение, которого до неё не было. Смена поведения для действительно нового события принята;
находка касается пропуска **старого**, а не требования сохранить запрет любого возврата.

**Проба:** `old-event-looks-newer-than-tombstone`: реальная последовательность event<delete, сравнение
stamp>written истинно; при добавлении 60 к written — ложно. Это арифметическая модель, не проверка NTP или часов ОС.

консенсуса, загрузчика, криптографии или blob. Проверка проекции показывает согласованное прочтение нового
решения, а не тест будущей выдачи. Значение 50 000 в дополнительной трассе — допустимое условие истечения
памяти по норме; нагрузочный запуск не выполнялся.

check_spec.py, его тесты, HTTP-стенд и реализации не запускались. Новая форма worker.creates/unit.state ещё
