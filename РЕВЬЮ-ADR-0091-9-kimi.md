## Проверено без находок

- **Блокер Codex R91.8-01 (две кратчайшие записи равной длины) — закрыт.** ECMAScript Number::toString — единственная детерминированная запись binary64 («из кратчайших — ближайшая к точному значению»), тот же канон, что JCS (RFC 8785), уже действующий в курсе для json-полей (ADR-0072) и `-0` → `0` (P/06.1 Н1.2 хранит `-0` как `0` — согласовано). Векторы с равными по длине кратчайшими записями объявлены — приёмка зафиксирует выбор.
- **`not_before` из строки (Claude мелкое 1) — верно.** `not_before` = `made.keep` − 60 читается из самой строки; «контроллер адресата манифест заказчика не читает» — самодостаточность адресата сохранена (ADR-0083 доп. (5) по духу). Подъём `valid_for` не возвращает удалённые жизни: события старше старта под новым манифестом исполняются по меньшему из прежнего и нового `valid_for`, прежнее значение — в курсоре заказчика (`unit.state.cursor` — монотонный, переживает переезд, п. 3); арифметика `not_after`/`keep` старых жизней не затрагивается, т.к. вычисляется из хранимого `made` строки.
- **Порядок проверок (Kimi 1 ред. 8) — закрыт в точности:** память id → `not_after`/`not_before` → `guard` → `cas`, при нескольких нарушениях ответ по первому. Память id первой сохраняет «повтор применённой записи получает её ответ» даже после прохода `not_after`; временные условия перед `guard`/`cas` — как условие самой возможности приёма; относительный порядок `guard` раньше `cas` сохранён (P/01.1).
- **Claude мелкие 2–3** отложены в Т-правку осознанно (шаг 8 P/04, код и группа `early`, `not_before` в отпечатке, форма `admission_ahead`) — перечень правок P/01.1/P/04 их покрывает.

## Находки

### 1. Мелкая — п. 1: «float — ECMAScript Number::toString» против «без экспоненты» в действующей Н1.2

- **Место:** decisions/0091-….md, п. 1 (скобка про `float`); Platform/06-console/spec/06.1-console.norms.md:100.
- **Что не так:** действующая норма `values_by_type` для `float` — «десятичная запись без экспоненты, кратчайшая» (P/06.1 Н1.2). Number::toString даёт экспоненту при |x| ≥ 1e21 и 0 < |x| < 1e-6 (`1e+21`, `1e-7`). ADR вводит ECMAScript-запись в скобке про `key`, не называя, меняется ли сама Н1.2 (тогда меняется хранимая форма всех float-полей единиц и таблиц — читаемо терпимо, но писательская строгость сдвигается) или только подстановка в `key`. При Т-правке строка «без экспоненты» в Н1.2 останется противоречием.
- **Контрпример:** float-поле `key` со значением 1e-7: по ECMAScript id получает `1e-7`; по действующей Н1.2 хранимая запись поля — `0.0000001`; если реализация подставит хранимую запись, id двух реализаций разойдутся.
- **Источник:** P/06.1 Н1.2 :100; ADR-0072 (JCS); RFC 8785 §3.2.2.3.
- **Рекомендация:** одна фраза: «запись float в Н1.2 меняется на ECMAScript Number::toString» (и «без экспоненты» снимается) — или явно «только для подстановки в `key`».
