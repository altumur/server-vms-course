# М10/1 — инструкция для реализации

Этот файл — для агента (или человека), который пишет код по уроку. Объяснение «зачем» — [`../01-storage.md`](../01-storage.md).

## Задача

Реализовать хранилище строк урока М10/1 на языке `<LANG>` так, чтобы оно прошло приёмку Н5 [`01-storage.norms.md`](01-storage.norms.md) через дверь (HTTP на unix-сокете).

## Входы и их приоритет

| Файл | Роль | Приоритет |
|---|---|---|
| [`01-storage.norms.md`](01-storage.norms.md) | нормы: что ДОЛЖНО быть | 1 — канон |
| [`01-storage.api.openapi.yaml`](01-storage.api.openapi.yaml) | форма HTTP-запросов и ответов | 2 — при расхождении с `01-storage.norms.md` прав `01-storage.norms.md` |
| `Source/tests/testdata/acceptance/М10_Platform/01/` (`scenarios.tsv`, `README.md`) | приёмка | 3 — проверяет `01-storage.norms.md`, не дополняет его |
| [`../01-storage.md`](../01-storage.md) | контекст, мотивация | не норма; требований из неё не выводить |

Правила:

- Не добавлять поведения, которого нет в `01-storage.norms.md`. Не «улучшать» семантику: нормализация ключей, сравнение версий на больше/меньше, повтор при `guard`, новые коды и виды отказов — запрещены.
- Если `01-storage.norms.md` молчит или противоречит себе — не угадывать. Записать вопрос в `QUESTIONS.md` реализации со ссылкой на раздел и выбрать самое консервативное поведение (отказ, а не допущение). Открытых вопросов у урока на 2026-10-15 нет: все известные закрыты в нормах.
- Для удобства проверки можно ссылаться на нормы в комментариях: `// М10/1 Н3 записать, шаг 7` или `// М10/1-10` у места, которое исполняет норму.

## Что создать

Обязательное поведение задаёт `01-storage.norms.md`. Внутренние интерфейсы, представление отказов и устройство кода выбирает реализация (Н5, М10/1-21); примеры ниже не добавляют к канону требований.

1. **Хранилище с четырьмя операциями Н3** (прочитать, перечислить, записать, удалить). Его внутренний API может возвращать типизированные отказы или представлять их иначе; на двери коды и поля ответа должны соответствовать Н4. Например, типизированное значение с полями `kind`, `key`, `index`, `size`, `limit` удобно переводить в HTTP-ответ.

   Сериализация выбирает форму именно своего исхода Н2: у `conflict` обязателен `index`, у `guard` — ещё
   `key`, у отказа веса — `key`, `size`, `limit`, у отказа тела — `limit` и только допустимый `size`.
   Не сериализовать все поля внутреннего типа с нулевыми значениями. Проверять полное тело по схеме
   ответа конкретной операции и кода; один общий `Fault` не подтверждает правильный вид отказа.
2. **Хранилище данных выбранного вида**: в памяти, на файлах или с реплицированным журналом (устройство группы — урок 11). Реализация описывает свой выбор и гарантии по разделу «Решает реализация»; наличие сразу нескольких видов не требуется.
3. **HTTP-сервер на unix-сокете** по [`01-storage.api.openapi.yaml`](01-storage.api.openapi.yaml), который переводит отказы ядра в коды Н4. Предел чтения тела задаётся отдельно от потолка строки; его превышение отказывается по Н2 до разбора JSON и вызова операции.
4. **Проверка прав по Н3 и Н4**. Разрешения на чтение, запись и удаление различаются по уроку 6; внутренний API проверки выбирает реализация. Личность вызывающего определяет сокет (урок 6). Политика — урок 6; роль приёмки имеет полные права на префикс `acc/` и ни на что больше, перечисление имён не требует права read, но выполняется после проверки личности М10/6 (Н3).
5. **Описание реализации** (ARCHITECTURE) — ответ на каждый пункт раздела «Решает реализация». Пункт без ответа — реализация не готова.
6. **Прогон приёмки** через дверь; реализации с API в процессе СЛЕДУЕТ гонять те же сценарии и через него (Н5, М10/1-21).

## Порядок работы

Ниже один возможный порядок. Разбиение на функции, внутренние интерфейсы и выбранные виды хранилища можно устроить иначе, сохранив поведение канона.

1. Прочитать `01-storage.norms.md` целиком. Выписать в описание реализации черновые ответы на «Решает реализация».
2. Модель данных Н1: проверки `key`, `items`, `cas`, `guard`, `id` — отдельными чистыми функциями. Это первые тесты.
3. Выбранное хранилище (например, в памяти): проходы Н3 строго по шагам, с тем же порядком проверок (страж раньше CAS).
4. HTTP-слой и отображение отказов Н4.
5. Подготовить экземпляры по README приёмки: потолок строки 524288 байт, предел тела 1048576 байт. Прогнать все сценарии текущего scenarios.tsv (01–23). Каждое падение — сверить с `01-storage.norms.md`, исправить **код**.
6. Если выбрано хранилище на файлах: проверить неделимость, версии, барьеры долговечности, повреждённую строку (`Row.unreadable`). Прогнать сценарии снова.
7. Пройти чеклист М10/1-01…23; у пунктов «проверяется чтением» указать в описании реализации, где в коде это обеспечено.

## Ловушки, которые зависят от языка

Места, где идиоматичный код на многих языках нарушает норму:

| Норма | Ловушка | Как правильно |
|---|---|---|
| порядок ключей перечисления — по байтам (Н3) | Java, C#, JS, Kotlin сортируют строки по UTF-16; `localeCompare` — по локали | сравнивать байты UTF-8 |
| вес и длина ключа — в байтах UTF-8 (Н1) | `len()` / `.length` считают символы или UTF-16 units | длина кодировки UTF-8 |
| версия непрозрачна (Н1) | разбор в число и сравнение `>` | хранить и сравнивать как строку; внутри хранилища счётчик МОЖЕТ быть числом |
| items — копия (Н3) | возврат ссылки на внутренний словарь | независимая копия на входе и выходе; проверка чтением по Н5 и М10/1-03: HTTP-сценарий 03 не наблюдает совместную память |
| неделимость (Н3) | проверка и запись под разными блокировками; async-разрывы между шагами | шаги после «далее одной операцией» — в одной критической секции |
| страж раньше CAS (Н3) | проверка в порядке полей запроса | строго: страж, потом CAS |
| отказ не цитирует присланное (Н4) | сообщения вида `invalid value "<тело>"` из JSON-библиотек | своё сообщение, без присланных данных, кроме ключа |
| написание ключа — `Key`, длина — в байтах (Н1, Н2) | общий отказ валидатора превращает любой неверный ключ в `badrequest` | целевой неверный ключ — `badkey`; пустой ключ стража — `badrequest`, прочие неверные ключи стража — `badkey` |
| тело сверх предела → 413 (Н2, Н4) | фреймворк отвечает своим 413/400 или подставляет потолок строки в `limit` | ограничить чтение до разбора JSON, вернуть `Fault` с пределом тела в `limit`; необязательный `size` — полный размер тела |
| неизвестный маршрут → 404 badrequest (Н2) | стандартная 404-страница фреймворка | свой обработчик с `Fault` |
| `cas: null` ≡ поля нет (Н1) | JSON-библиотека различает null и отсутствие или путает `""` с null | три состояния: нет/null, `""`, версия |
| неизвестные поля Cmd и items у delete не читаются (Н2) | строгий разбор тела отвергает лишнее поле или включает его в отпечаток id | лишние поля верхнего уровня put/delete игнорировать и не включать в отпечаток; guard остаётся закрытым |
| долговечность («Решает реализация» п. 3) | запись без барьера долговечности; rename без сохранения каталога | обеспечить названные в описании реализации барьеры; для файлов это, например, fsync файла и каталога до успешного ответа |

## Готово, когда

- [ ] все сценарии текущего scenarios.tsv (01–23) зелёные через дверь, включая порядок имён в `keys` по README приёмки;
- [ ] (СЛЕДУЕТ) те же сценарии зелёные через API в процессе у каждого хранилища данных;
- [ ] описание реализации отвечает на все пункты раздела «Решает реализация»;
- [ ] каждый пункт чеклиста М10/1-01…23 либо закрыт сценарием, либо в описании указано место в коде;
- [ ] `QUESTIONS.md` пуст или каждый вопрос передан автору норм.

## При расхождении кода и норм

| Ситуация | Что править |
|---|---|
| сценарий красный, `01-storage.norms.md` однозначен | код |
| `01-storage.norms.md` неполон или противоречив | не обходить в коде; вопрос в `QUESTIONS.md`; правку делает автор норм, затем код |
| сценарий противоречит `01-storage.norms.md` | дефект приёмки; вопрос автору; код — по `01-storage.norms.md` |
| ИИ ошибся и был исправлен человеком | строка в `corrections.tsv` рядом со сценариями (ADR-0080 доп. 1) |
