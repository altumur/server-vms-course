# М10/3 — инструкция для реализации

## Задача

Реализовать строку единицы и операции над ней, владение именем через слот, выдачу эпохи и состояние аренды.
HTTP-входы здесь — дверь единиц консоли. Слот, эпоха и аренда работают через операции хранилища P/01.1;
отдельных HTTP-маршрутов для них этот урок не вводит.

## Входы и их приоритет

- Канон — [нормы](03-units-slots-epochs-lease.norms.md), включая Н0, порядок Н3 и отказы Н4.
- [OpenAPI](03-units-slots-epochs-lease.api.openapi.yaml) выражает HTTP-формы канона.
- [Приёмка](../../Source/tests/testdata/acceptance/М10_Platform/03/README.md) проверяет нормы.
- [Лекция](../03-units-slots-epochs-lease.md) объясняет механизм и примеры.

Для полей единицы нужна загруженная спека по [P/02.1](../../Platform/02-installer/spec/02.1-installer.norms.md).
Статическая схема HTTP не знает произвольного набора `unit.fields`: проверку имён, типов, обязательности,
ссылок и ограничений поля выполнить по спеке и Н3. Соответствие только общей схеме не означает допустимый запрос.

Противоречие записать с местом и контрпримером и передать по правилам проекта. Произвольный отказ не заменяет
пропущенную норму. Внутренние интерфейсы, типы, классы ошибок и разбиение на компоненты выбирает реализация.

## Что создать

1. Преобразование типизированных полей спеки в элементы строки и обратно по Н1.2. Отдельно сохранить
   отсутствие `inherit`/`json: null`, маску секрета и ограничения записи дайджеста `blob`.
2. Создание, правку и удаление единиц по Н3: числовые и именованные id, заявки повторов, `revision`, надгробия.
   HTTP-ответы формируются по Н2; строка хранилища и объект ответа имеют разные типы значений.
3. Захват, продление и отдачу слота, чистку вкладов предшественника и запись под стражем по Н1.4 и Н3.
4. Выдачу эпохи и состояние аренды по Н1.5–Н1.6 и Н3. Процедуры сообщают потерю владельцу цикла;
   цикл — урок 5 Н3 «цикл()»; остановка единицы и чтение `platform/epoch_floor` на шаге аренды —
   урок 5 Н3 «шаг_аренды()», шаги 2 и 4.
5. Описание всех выборов раздела «Решает реализация» и средство выполнения приёмки.

## Порядок работы

Это предлагаемый порядок, а не обязательное устройство кода.

1. Выписать семьи ключей, их писателей и формы строк из Н1. Проверить, какие поля берутся из спеки,
   а какие принадлежат платформе. Не переносить поля размещения и пульса в строку единицы.
   Считать UTF-8-байты полного ключа вместе с префиксом и разделителями; предел компонента
   не заменяет предел хранилища. Определённый badkey обрабатывать по Н3, включая страж,
   состояние pending и выдачу/подтверждение эпохи; источник формы holds — М10/5 Н1.3.
2. Реализовать преобразования значений. Проверять тип до преобразования: булево не становится целым,
   число в кавычках — числом, список — строкой. При создании подготовить каждое поле по Н1.2:
   переданное значение, отсутствие inherit (не передано или `null`), default, пустая форма типа. Required проверять по исходному телу.
   При правке незаданные поля сохраняются, default заново не применяется. Поле-источник именованного id
   неизменяемо независимо от fixed в спеке: переданное новое имя получает 400 на шаге 4 после чтения строки.
3. Выполнить проходы создания, правки и удаления в порядке Н3. Для создания проследить отдельно заявку,
   счётчик и строку: это разные записи. Разобрать обрыв после каждой из них, повтор с тем же и другим отпечатком,
   `pending` до и после 30 секунд и отказ после резерва номера. Перехват должен отсечь позднего исполнителя
   атомарными guard/cas на каждой записи; чтение заявки перед записью этого не доказывает. Проверить 5xx:
   при записанной единице или неизвестном исходе pending сохраняется, чужую заявку снимать нельзя.
   Проверки unique/ref/must_match предварительные: раздельные CAS единиц не делают их атомарными.
   Контроллер размещения не обещает фоновое обнаружение нарушения; гонку проверять с этой границей Н3.
4. Подготовить отдельный экземпляр по README приёмки: загружена `testsub`, пусты её данные и память заявок,
   фоновые писатели остановлены, вызывающий имеет нужные права. Выполнить 14 сценариев / 85 шагов в порядке файла.
   Сценарии связаны: сценарии 04 и 11 используют `c3`, созданную сценарием 03. Сбрасывать стенд между ними нельзя.
5. Проверить Н2 отдельно от частичных ожиданий TSV: обязательные поля и типы полных ответов, маски,
   `worker: null` при создании, тот же полный ответ при повторе POST, форму удаления и отказов.
   Недопустимые при любом unit.id значения `a/b` и `..` отвергаются схемой; выбранный вид id проверяется отдельно.
   GET/DELETE не возвращают fault проверки полей записи: их 400 содержит только detail и error.
   Ошибки, которые таблица проверяет только кодом, не освобождают от проверки тела по контракту.
   Тело ниже HTTP-предела может превысить потолок строки: 413 row too large сохраняется как ответ POST,
   единица не создаётся; правка сохраняет прежнюю строку/revision. До создания проверить также будущую
   done-заявку с полным ответом: успех единицы не должен сделать повтор нехранимым.
6. Разобрать захват и чистку: сначала новый страж и `released: true`, затем удаления под этим стражем,
   затем `released: false`. Проверить смену владельца между любыми двумя действиями; чужой вклад не удаляется.
   Таблица Н3 задаёт переходы, псевдокод — порядок чтений и записей; вид воркера один (ADR-0084): каждую ветвь
   проверить с заданным именем, без имени и через names_given.
   Слотовый порядок и «по имени» различаются по Н1.4; проверяются также нечисловые суффиксы,
   равные номера разных имён и следующий номер после длинного цифрового суффикса.
   После 412 перечитать владение: собственное продление сохраняет имя, чужой holder/gen отсекает.
   Отъём на своей коробке доступен только первому старту; NameOnAnotherBox оставляет процесс никем
   с меткой `refused` в объекте `<sub>/contenders/<имя>/<коробка>` (урок 5 Н1.4) и тревогой `worker.name_taken`
   (урок 5 Н3 «никто и возврат имени») по Н4, без смены имени. При порванном gen кандидат не переписывается;
   при порванном until и читаемом gen после TORN_STILL поколение увеличивается.
7. Проверить эпоху и аренду на границах окна: подтверждение от момента запроса, другой номер,
   нечитаемая строка, молчание до истечения окна, пропущенный запрос и достижение `unconfirmed_max`.
   Первое окно тоже считается от отправки подтверждённой записи: ответы на 24/25/30-й секунде,
   пауза между ответом и start_unit, CAS-conflict с новой попыткой. Поздний успех не разрешает
   запуск, номер не откатывается; следующий запуск требует нового успешного чтения назначения.
   Проверить off, конечный потолок и forever: граница 25 секунд относится к действиям, а не ко всем данным.
   Различить монотонное время аренды и стенные секунды слота; разность сроков не доказывает общую точку отсчёта. Выдача эпохи использует пол;
   проверка поднявшегося пола во время работы относится к уроку 5 Н3 «шаг_аренды()», шаг 2: чтение
   `platform/epoch_floor` раз за шаг; эпоха ниже пола — потеря аренды.
8. Заполнить все пункты канонического чеклиста М10/3. Для частей вне TSV приложить свидетельство чтения по таблице предметов Н5
   (для каждого предмета там назван сценарий или учение урока-владельца) или результат соответствующего стенда уроков 4, 5, 8, 9, 11 и М11. Ссылка на будущий стенд сама по себе не является проверкой.

## Ловушки языка и библиотеки

| Норма | Возможная ошибка | Как сохранить поведение |
|---|---|---|
| Н1.2, Н3: типы значений | `true` принимается за 1; `"7"` приводится к числу | различать JSON-типы до числовой проверки; сц. 08 |
| Н3: `required` | проверка истинности отказывает `0`, `false` или `[]` | проверять наличие и именно пустую строку; не обобщать это на все пустые значения |
| Н1.2: `inherit`, `json: null` | сериализатор записывает отсутствующее поле как `""` или `"null"` | сохранять отсутствие элемента; сц. 10 и чтение преобразования JSON |
| Н1.2: список | разделение по запятой портит `"a,b"` или начальный `[` | использовать JSON также при пустом элементе; [] и [""] должны различаться после перезапуска/правки; метки размещения проверять отдельно; сц. 09 |
| Н1.3: имя | ASCII-регулярное выражение пропускает запрещённые категории Unicode | дополнительно проверить Cc, Zl, Zp и Nd вне ASCII; не запрещать допустимое `a.b` |
| Н3: ключ повторов | предел 200 считают символами, сравнивают только тело или очищают только строки единиц | отвергать .. до записи заявки; считать UTF-8-байты; отпечаток включает вызывающего, метод, путь и тело; приёмка начинает с пустых заявок |
| Н3: запись с `cas` | повторяют запись со старой версией или старым результатом проверки | перечитать с указанного шага; в правке заново проверить `fixed` и прежний дайджест `blob` |
| Н3: захват слота | слот объявлен живым до удаления вкладов | сохранять две записи слота и страж на удалениях; даже без вкладов завершающая запись нужна |
| Н3: перехват pending | поздняя консоль продолжает после чужого CAS | guard заявки на счётчике и единице, CAS на самой заявке; при потере версии — исходы Н3, не присвоение чужой версии |
| Н3: 412 слота | собственное продление принято за смену владельца | перечитать holder/gen и released; проверить свой подтверждённый срок, а не until чужих часов; повтор только после проверки условий |
| Н1.4: gen | нечитаемое поколение заменено нулём после TORN_STILL | существующий слот не захватывается; отсутствие строки и порча её gen различаются |
| Н1.4–Н1.6: время | сравнивают стенные часы с монотонными; подтверждают аренду от получения ответа | `until` — только стенные секунды писателя для показа; возраст версии у судьи и свой срок подтверждённого запроса — монотонные; задержка ответа не расширяет окно |
| Н3: эпоха | нечитаемое значение трактуется как отсутствующее и заменяется нулём | ноль только при отсутствии; нечитаемая строка — `EpochUnreadable` |
| Н1.6: молчание | проспавший процесс получает право писать по `unconfirmed_max` | `lost` отличается от `silent`; потолок молчания не оживляет пропущенное окно |

## Готово, когда

Описаны все восемь выборов реализации, выполнены все нормы канонического чеклиста М10/3 и зафиксированы способы проверки.
HTTP-приёмка прошла с указанной подготовкой, а полные тела ответов сверены с Н2 и загруженной спекой.
В RunningUnit поле worker имеет форму имени слота Н1.4: пустота, верхний регистр, разделители
пути и конечный перевод строки отвергаются. Совпадение с slot.prefix спеки проверяется отдельно;
worker:null при создании остаётся отдельной формой CreatedUnit.
Чтение покрывает оставшиеся предметы Н5; заявка, слот, эпоха и аренда проверены с названными вмешательствами.
Отступления от СЛЕДУЕТ объяснены по Н0.

Успех TSV подтверждает только наблюдаемые им ветви. Он не доказывает поведение двух консолей,
захват слота, чистку вкладов, пол эпох и сроки остановки писателя. Проверка OpenAPI не запускает реализацию
и не проверяет ограничения, зависящие от спеки, состояния, прав или UTF-8-размера.

## При расхождении

Назвать id нормы, вход, начальное состояние, ожидаемый и полученный исход. Если ошибочна реализация — исправить
её и повторить относящиеся проверки. Если расходятся норма, контракт или ожидание — согласовать источник
по правилам проекта и исправить связанные места. Изменение приёмки или повторяющуюся ошибку её толкования
записать в `corrections.tsv`; новое правило не оставлять только в инструкции.

## Проверки границ прогона 25

По отдельной оснастке README приёмки проверить веса -1/0/1: нижняя граница действует после
материализации POST и для переданного PUT, отказ не меняет строку. Нечисло остаётся обычным
not_number, а целое меньше 1 даёт текстовый отказ без fault.

Для слота различать три времени: показ until на часах писателя, возраст версии на часах судьи
и срок собственного подтверждённого запроса. Сдвиг первых часов не меняет held/lapsed или судьбу.
Проверить новый первый взгляд, свой поздний ответ и окно записи после собственного продления.


## Полный URL подсистемы (G37-03)

Для путей подсистемы контракт задаёт два стандартных servers: origin консоли и
origin/{sub}. К первому или второму прибавляется путь paths; origin не имеет
завершающего слеша. localhost/testsub — подставляемые примеры, не настройки запуска.
Короткий путь выбирает CONSOLE_ROOT, префиксный — названную загруженную спеку.
Сверить оба URL, методы, коды и тела с Н2 и М10/9 Н2 («Полные формы и границы Н2»: origin без завершающего `/` либо origin/{sub}). Общие двери и дверь ресурса
не получают префикс из соседнего path item. Прочитать существующие сценарии root
и testsub2 как контроль маршрутизации; структурная валидность не исполняет HTTP.
