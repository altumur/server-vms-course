## Н1 Форма

### Н1.1 Раскладка ключей подсистемы

`unit`, `unit.rows` и `unit.id` обязательны без умолчаний (P/02.1 Н1.2). `unit.rows` — имя по грамматике и не из перечня запрещённых имён сводной таблицы P/02.1 Н1.2а (служебные семьи
этой раскладки, первые сегменты платформенных дверей, семьи объектов, а также cluster, worker, ts из оболочки
снимка М10/10). Непредставимое имя — отказ загрузки, не недостижимая дверь.

Все ключи подсистемы начинаются с её имени (P/02.1). У каждой строки один писатель; у семьи их может быть несколько, когда урок-владелец делит её по форме строки (просьбы — строка `<sub>/requests/<rid>` урока 8 Н1.5, писатели по `worker.requests`; таблицы — `worker.writes` урока 10 Н1.6); права — роли и образцы P/02.5 Н1.4 (`console`, `<s>controller`, `<s>worker`).

```yaml
rows:                                  # строки хранилища (P/01.1)
  <sub>/<rows>/<id>:        {писатель: консоль; контроллер — только удаление по placement.unplaced.delete_after}
  <sub>/next_id:            {писатель: консоль; items: {n}}
  <sub>/idem/<key>:         {писатель: консоль; форма — решает реализация (п. 3); только консоль читает}
  <sub>/policy:             {писатель: консоль; items: {servers: shared | distinct}}        # урок 4
  <sub>/slots/<имя>:        {писатель: держатель; контроллер — отдать (P/04 Н3 «судьба», release); форма P/03.2 Н1.4}
  <sub>/holds/<место>:      {писатель: держатель; форма слота без server, плюс by — P/03.2 Н1.3}
  <sub>/epoch/<id>:         {писатель: воркер; items: {epoch}; никогда не удаляется}
  <sub>/placement/<id>:     {писатель: контроллер; items: {worker, reason, at, rev, spec_rev} — P/04 Н1.1}
  <sub>/workers/<имя>:      {писатель: контроллер; items: {units, rev} — P/04 Н1.1}
  <sub>/controller/placement_turn, <sub>/controller/placement_intent: {писатель: контроллер; строки допуска P/04 Н1.5; не удаляются}
  <sub>/requests/*:         {писатели: консоль (дверь); воркер по worker.requests; ресурс — free_ask своей формы — P/05 Н1.4}
  <sub>/asked/*:            {писатель: консоль; items: {rids, by, at} — учёт человека, урок 8 Н1.5 ledger}
  <sub>/<таблица>/*:        {писатель: консоль; таблица из worker.writes — её воркер, консоль только читает — урок 10}
  <sub>/sweep:              {писатель: консоль; items: {at, digests} — урок 10 Н1.5 sweep}
  <sub>/decommissioned/<сервер>: {писатель: контроллер — P/04 Н1.1, Н3 «вывести_сервер»}
platform rows:
  platform/epoch_floor:     {items: {floor, generation_at}; писатель — операция «восстановить хранилище» P/01.3 Н3 (поднимает пол на поколение); право — только у неё (P/01.2 Н1.3 never)}
objects:                               # объекты, не строки; дверь объектов — P/05 Н1.1
  # heartbeats — P/03.4 Н1.1; contenders — P/03.2 Н1.4а; snapshot — P/04 Н1.3а; controller/pass — P/04 Н1.2;
  # blobs — урок 10 Н1.5; метка просьбы — строка-объект objects/<sub>/commands/<rid> урока 8 Н1.5 mark (ключ
  # хранилища строк, не дверь объектов; каталог данных)
  <sub>/heartbeats/<имя>, <sub>/contenders/<имя>/<коробка>, <sub>/snapshot/*, <sub>/controller/pass,
  <sub>/blobs/<дайджест>
reserved_table_names:   <rows> и перечень запрещённых имён таблиц P/02.1 Н1.2а
```

`controller` не может быть именем unit.rows или таблицы подсистемы: этот префикс содержит
служебные строки допуска [P/04 Н1.5](../../Platform/04-controller/spec/04-controller.norms.md) (`placement_turn`, `placement_intent`). Загрузчик отказывает таким значениям (перечень P/02.1 Н1.2а).

### Н1.2 Строка единицы

```yaml
<sub>/<rows>/<id>:
  id:        <id как строка>                       # ДОЛЖЕН
  revision:  <десятичное целое ≥ 1>                # ДОЛЖЕН; 1 при создании, +1 на каждую правку, удаление не меняет
  deleted:   "true"                                # только у надгробия; иначе элемента нет
  <поле>:    <значение по типу>                    # каждое поле спеки, кроме отсутствующих (ниже)
values_by_type:
  string, url: как есть
  int:        десятичная запись
  float:      десятичная запись без экспоненты, кратчайшая, восстанавливающая число
  bool:       "true" | "false"
  list:       элементы через запятую; если есть пустой элемент, элемент содержит запятую или текст начинается с `[` — массив JSON;
              [] хранится как ""; [""] — как JSON-текст '[""]'. При чтении "" → [], ведущий '[' → JSON-массив,
              иначе разделить по запятым; непереданное при правке поле сохраняется в этой форме;
              поле меток размещения (`placement.constraint: labels-subset`) — только слова по азбуке меток урока 4 Н2.1 (1–64 ASCII: первая буква или цифра, далее буква, цифра, `_`, `.`, `:`, `-`)
  json:       канонический JSON (ADR-0072); значение null — элемента нет
  blob:       "sha256-<hex>"; байты — объект <sub>/blobs/sha256-<hex> (урок 10 Н1.5); в строку дайджест попадает
              только дверью байтов PUT /{rows}/{id}/{blob_field} (урок 10 Н2):
              правка полей принимает лишь прежний дайджест строки или "" (снять); при создании — только ""
  *_secret:   конверт enc:v2:… (договор запечатывания); клиент никогда не получает значения: в ответе — маска "***" (урок 7 Н1.1)
absent:
  - поле с inherit, если не задано: элемента нет (не "" и не "null")
  - json-поле со значением null
platform_fields:   [id, revision, deleted, worker, placement, epoch, phase, observed_revision]
  # unit.fields не объявляет (отказ загрузки P/02.1), клиент не задаёт; в живой строке только id и revision,
  # deleted — только у надгробия; worker/placement — строка <sub>/placement/<id> (P/04 Н1.1, добавлено М10/4);
  # epoch — строка эпохи; phase, observed_revision — status[].phase, status[].observed_revision
  # объекта <sub>/heartbeats/<имя> (P/03.4 Н1.1, добавлено М10/5)
```

Поле bytes остаётся обычным полем единицы только в спеках без blob: сочетание с любым
blob-полем отвергается загрузчиком по P/02.1, чтобы счётчик `bytes` в ответе двери байтов `PUT /{rows}/{id}/{blob_field}` (М10/10 Н2) не затирал поле.

При создании состав клиентских полей определяется для каждого поля спеки (до записи строки):

1. Поле передано — взять именно переданное значение, включая `0`, `false`, `[]` и `null` (кроме `null` у поля с
   `inherit` — шаг 2); умолчание его не заменяет. Допустимость значения проверяется по Н3/Н4.
2. Поле не передано или передано `null` и имеет `inherit` — не создавать элемент; значение `inherit` является концом
   цепи чтения, а не значением для записи в новую строку.
3. Поле не передано и имеет `default` — взять значение `default` из загруженной спеки.
4. Иначе взять пустую форму типа из таблицы ниже. `default` и `inherit` вместе запрещены P/02.1.

| Тип | Пустое значение JSON | Элемент строки Н1.2 |
|---|---|---|
| string, url, blob | `""` | `""` |
| int, float | `0` | `"0"` |
| bool | `false` | `"false"` |
| list | `[]` | `""` |
| json | `null` | отсутствует |

Проверки типа и ограничений применяются к полученным значениям в порядке Н3; умолчание не обходит
`fixed`, `enum`, ссылки и остальные ограничения. Непереданное required-поле по-прежнему даёт отказ
Н3 шага 6: подготовка пустой формы или default не считается его передачей клиентом.
После проверки `json: null` не сохраняется. Секрет хранится конвертом (договор запечатывания) и выдаётся маской `"***"` (урок 7 Н1.1), а blob при создании
пуст: default/inherit для blob запрещены P/02.1. При правке непереданные поля сохраняются из строки,
умолчания заново не применяются. Создание над надгробием применяет те же правила подготовки;
проверка fixed сравнивает подготовленное значение с надгробием.

Список имеет только строковые элементы; иной JSON-элемент — отказ типа поля (Н4).
Значение `int` на входе двери — JSON-число без дробной части и экспоненты в пределах ±(2^53 − 1): `1.0`, `1e2` и
`9007199254740992` у `int` — `not_number` (такое число читает клиент JSON любого языка). Число `-0` хранится как `0`
(JCS, ADR-0072).
Значение json-поля — любое значение JSON; его `schema` — JSON Schema 2020-12 из ключевых слов `type`, `enum`, `const`,
`properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`,
`maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `pattern`, `if`/`then`/`else`, `allOf`, `anyOf`, `oneOf`, `not`;
схема с иным ключевым словом — отказ загрузки `refused:value` (P/02.1), поэтому все реализации проверяют одно и то же.
Пустой элемент допустим у обычного list, но не у меток размещения по азбуке урока 4 Н2.1.

### Н1.3 Идентификатор

```yaml
id:
  numeric:                                  # unit.id: numeric
    rule:    десятичное целое ≥ 1 из счётчика <sub>/next_id; первый — 1; номер не используется повторно никогда,
             в пути — десятичная запись без знака, пробелов и ведущих нулей (`01`, `+1` — 400 bad id);
             надгробия считаются; номер, выданный отказанной попытке, не возвращается
    recover: только при полном подтверждённом перечне строк/надгробий и живых заявок; утрата истории или ошибка чтения не считается пустотой и не разрешает автоматическое восстановление. Счётчик не читается → наибольший номер среди строк <rows>/ (с надгробиями) и номеров в живых заявках + 1, счётчик
             переписан целиком; номера отказанных попыток следов не оставляют и после восстановления МОГУТ выйти снова —
             единственное исключение из «никогда», журнал `next_id.recovered {from, to}`
  named:                                    # unit.id: <поле>
    rule:    значение несекретного поля type string, включая умолчание типа; источник с суффиксом _secret запрещён загрузчиком P/02.1; одна строка; ДОЛЖЕН быть непустым
    update:  поле-источник id неизменяемо даже без fixed в спеке; PUT может не передавать его или передать тот же id;
             другое значение — 400 «<поле> is fixed» без записи; переименование этой дверью не выполняется
    refused: пустое; "." и ".."; содержит `/`, `\`, `|`, `"`, `,`; управляющие знаки (Cc), разделители строк и
             абзацев (Zl, Zp); цифры вне 0–9 (Nd не ASCII); категории — по таблицам Unicode 15.0.0 (UnicodeData), как NFKC
             урока 7; знак, не назначенный в этой версии, ни к одной из них не относится (добавлено ревью стадии A 2)
  tombstone:                                # возврат имени после удаления
    rule:    создание над надгробием проходит только с теми же значениями fixed-полей; revision = надгробия + 1,
             записью с cas по версии надгробия; иначе 400 с именем поля
  unique:    true | canonical            # предварительная проверка нового значения по живым единицам;
                                         # canonical — URL в каноническом написании (ниже); конфликт — 409 unique;
                                         # атомарной уникальности между строками нет (Н3 «Гонки» правки)
  canonical_url:                         # синтаксический канон RFC 3986 §6.2.2 (ADR-0057)
    - схема и хост — нижним регистром; шестнадцатеричные цифры процент-кодирования — верхним
    - процент-кодированный незарезервированный знак (буква, цифра, - . _ ~) декодируется
    - точечные сегменты пути удаляются (RFC 3986 §5.2.4); пустой порт («host:») снимается
    - порт по умолчанию не снимается, query не сортируется, пустой путь не заменяется на «/»: «тот же поток» — смысл
      подсистемы, не платформы (ADR-0057)
ref_and_must_match:                      # поле единицы или таблицы (P/02.1 Н1.3)
  ref:        <подсистема>/<семья>       # цель значения v — строка <ref>/<v>
  must_match: {<поле цели>: <поле этой строки>}   # при живой цели значения равны; иначе 409 conflict, fault must_match;
                                                  # отсутствующий элемент цели не равен ничему, и "" тоже
  rules:
    - цели нет — не отказ: ref без must_match не требует существования цели (ADR-0057)
    - цель не читается — 409 conflict, fault garbled
    - в обе стороны (как у таблиц, урок 10 Н3 «таблица — записать строку», шаг 2): создание или правка единицы, которая
      сама — цель, проверяет живые единицы и строки таблиц каталога, чьё поле с ref на её семью и must_match называет её:
      их значения равны новым значениям цели, иначе 409 conflict, fault must_match; ссылающаяся строка не читается — fault garbled
```

Профиль восстановления numeric не совместим с физической уборкой: unit.id: numeric вместе с placement.unplaced.delete_after — отказ загрузки P/02.1. Успешные номера представлены сохранёнными строками/надгробиями; очистка done-заявок это не отменяет. Произвольная утрата этих строк не покрыта формулой recover.

Любое имя, которое разрешают грамматика id и слота и предел полного ключа P/01.1, хранит любая реализация: имена файлов
(каталоги бакетов — договор журнала событий «Имена файлов в общих деревьях») реализация кодирует сама, более узкого файлового профиля нет — иначе части разных
реализаций над одними данными несовместимы (сверка python и go М10/3–5, U20).

## Н2 Двери

Пути единиц относятся к CONSOLE_ROOT без префикса или к явно названной подсистеме
под /{sub}, включая root. Полный URL в OpenAPI задают стандартные servers + paths
по М10/9 Н2; префикс не является частью id.

Дверь единиц — консоль подсистемы (урок 9 описывает страницу; здесь — строки). Все тела — JSON-объекты; ответ-отказ — `{detail, error, fault?}`.
Разбор запроса — урок 9 Н2 «Разбор запроса консоли» (P/01.1 Н2.1 с отступлениями консоли); своих отступлений у двери единиц нет.

[Контракт двери единиц](03-units-slots-epochs-lease.api.openapi.yaml) — OpenAPI 3.1.

Значения строки хранилища из Н1.2 и JSON-ответа различаются: в ответе числа и булевы имеют свои JSON-типы,
списки — массивы, `json` — значение JSON, строковые поля — строки; непустой секрет заменён `"***"`,
пустой остаётся пустым (урок 7). `id` выдаётся строкой, `revision` — целым числом от 1.
Отсутствующие `inherit` и `json: null` не добавляются в ответ. У поля с `inherit` значение `null` в теле создания или
правки значит «не задано»: элемента в строке нет, значение снова наследуется (`PUT {"step": null}` возвращает `step` к
наследуемому); у прочих полей, кроме json, `null` — 400 по типу. Путь сравнивается байт в байт (урок 9 Н3 шаг 5):
`/counters/` — не маршрут, 404. Сегмент id процент-декодируется после выбора маршрута (RFC 3986 §2.1): `/counters/a%20b` —
единица `a b`, `%31` у numeric — `1`; результат не UTF-8 или не по грамматике id Н1.3 — 400 `bad id`. Заголовки, которые
читает дверь (`Idempotency-Key`, `If-Match`): значение без OWS по краям (RFC 9112 §5.5); заголовок дважды — 400, как
повтор параметра; пустой `If-Match` — 400 «If-Match is a unit revision». Остальные имена полей определяет спека;
открытый набор свойств общей схемы не разрешает неизвестные поля.

| Операция | Успешное тело | Норма-владелец |
|---|---|---|
| POST | типизированная строка с `id`, `revision` и `worker: null`; при повторе — сохранённый ответ целиком | Н1.2, Н3 создать; М10/3-02, 03, 07 |
| PUT | типизированная строка после правки с `id` и новой `revision` | Н1.2, Н3 править; М10/3-02, 03 |
| DELETE | ровно `{deleted: <id как строка>}` | Н3 удалить; М10/3-10 |
| GET | ровно `{rows: [...], configured: [...]}`; `rows` — единицы пульса с `worker`, `server`, `age`, `worker_state` (правило ниже; пульсов нет — `[]`), `configured` — типизированные живые строки с масками (надгробий нет; порядок не нормирован); двери `GET /<rows>/<id>` нет | собственный контракт М10/3 Н2 (UnitList/RunningUnit); фильтрация по `view` — М10/9 Н1.3 `need` (GET/HEAD → view на единицу); форма пульса — [P/03.4 Н1.1](../../Platform/03-worker/spec/03.4-worker.norms.md) |

Ключ повторов POST — непустой сегмент без `/`, не равный `..`, не больше 200 UTF-8-байт. `maxLength` в схеме — только верхняя
граница числа символов; проверка байтов отдельная. POST и PUT требуют JSON-объект; набор `unit.fields`,
обязательность и типы проверяются по загруженной спеке в порядке Н3. Схема не заменяет проверок состояния,
ссылок, прав и размера. При отказе выдаются ровно `detail`, `error` и, только для причин Н4, `fault`.
У `409 conflict` поле `fault` обязательно; `exists`, `in flight` и `key reused` его не добавляют.


`HEAD /{rows}` — как `GET` без тела (урок 9 Н2); иной метод у `/{rows}` и `/{rows}/{id}` — `405`, путь длиннее `/{rows}/{id}` — `404` (Н4), кроме двери байтов `/{rows}/{id}/{blob_field}` урока 10 Н2: на ней иной метод, чем `PUT`, — `405`; общие коды консоли (401, 403, 408, 413, 429, 503 busy) — урок 9 Н4. Отдельной двери `GET /{rows}/{id}` нет: единицу читают в составе `GET /{rows}` (этот Н2; фильтрация по `view` — урок 9 Н1.3 `need`).

Двери слота, эпохи и аренды перенесены в [P/03.2 Н2](../../Platform/03-worker/spec/03.2-worker.norms.md) (стадия B).

**`rows` в `GET /{rows}`.** Каждый элемент `status` последнего пульса каждого воркера подсистемы, любого возраста
([P/03.4 Н1.1](../../Platform/03-worker/spec/03.4-worker.norms.md)), дополненный полями: `worker` — имя слота воркера; `server` — поле `server` пульса, а если его нет — `?`;
`age` — секунды, сколько эта консоль видит версию пульса неизменной, по её монотонным часам (первый взгляд — 0),
с одним знаком после точки; `worker_state` — `live` при `age` ≤ 45 с (LOST_AFTER [P/04 Н1.4](../../Platform/04-controller/spec/04-controller.norms.md)), иначе `stale`. Элемент
без `id`, с `id` не по грамматике Н1.3 или с нецелыми `epoch`/`revision` пропускается; `worker` — имя слота из ключа
пульса `<sub>/heartbeats/<слот>`, а не поле пульса. Список упорядочен по id единицы (байты UTF-8), при равных — по имени слота воркера (байты UTF-8). Фильтр `view` — урок 9 Н1.3 `need`.

## Н3 Проход

### Полные ключи и отказ хранилища

Во всех операциях ниже правила ключа P/01.1 Н1 применяются после сборки полного пути Н1.1,
включая префикс, семейство и разделители; ключ стража проверяется так же. Грамматика UnitId,
WorkerName и 200-байтный предел компонента Idempotency-Key сохраняются. Схема компонента
не обещает вместимость полного ключа. Ключи не сокращаются и не хешируются при отказе.

Определённый `badkey` при чтении или записи — отказ этой операции, не отсутствие строки,
не CAS-conflict и не неответ. Применимые правила ключа можно проверить до вызова хранилища;
отказ меньшего объявленного предела файловой реализации обрабатывается тем же способом.

- Дверь единиц отвечает `400 {detail, error: "badkey"}`, без fault; detail называет семейство
  ключа и причину без содержимого секретов. У PUT/DELETE строка и revision не меняются.
  POST до получения своей pending отвечает без сохранения; после получения — завершает
  отказ шагом 9. Прежний резерв номера не возвращается. Отказ сохранения самого ответа
  на шаге 9 по-прежнему даёт 503, а не неподтверждённый 400. Правила утраты заявки/guard
  имеют прежний приоритет; чужую заявку не меняют.
- Ветви воркера (выбор слота, захват, продление, запись под стражем, выдача и подтверждение эпохи) перенесены в
  [P/03.2 Н3 «Полные ключи и отказ хранилища»](../../Platform/03-worker/spec/03.2-worker.norms.md) (стадия B; разбор ревью стадии A 3–5, № 11).

### создать(тело, ключ) → 201 строка | отказ

```
1. ключ идемпотентности: есть, один сегмент без '/', не '..', ≤ 200 байт                    → иначе 400
   тело — JSON-объект                                                      → иначе 400 (fault по Н4); одиночный суррогат
   (`\ud800` без пары) и число вне double (`1e400`) — 400 not_json здесь, до заявки
   профиль М10/7: кольцо не задано и передан непустой *_secret на любой глубине → 400 sealing key required,
   без fault и без создания/изменения заявки (Н1.2/Н4 М10/7); маска не используется как отпечаток
   заданное нечитаемое кольцо → 503 SealingUnavailable для любого POST до HMAC/заявки (М10/7 Н3)
2. заявка <sub>/idem/<ключ>: записать cas "" (в заявке — отпечаток запроса, время, pending)
   отпечаток: кто, метод, путь /<rows> (короткий и с префиксом подсистемы — один путь) и тело как значение
   JSON (порядок полей и экранирование значения не имеют, как P/01.1 Н3)
   есть, done, тот же отпечаток                                            → прежний ответ как есть
   есть, done, иной отпечаток                                              → 422 key reused
   заявка не по форме заявки                                               → 503 store unavailable, заявку не трогать
   есть, pending, стоит < 30 с по монотонным часам этой консоли от её первого наблюдения
   текущей версии заявки (после перезапуска отсчёт заново), любой отпечаток → 409 in flight
   есть, pending, стоит ≥ 30 с, тот же отпечаток                           → забрать записью с cas; дальше как своя
   есть, pending, стоит ≥ 30 с, иной отпечаток                              → 422 key reused (заявку не трогать)
   версия успешной записи pending = моя версия заявки; после перехвата сохранить уже записанный номер
3. numeric: номер уже в заявке → использовать его; иначе next_id записью с cas и guard моей версии заявки
   (при conflict счётчика повторить под тем же guard; предел повторов исчерпан → 503 store unavailable по шагу 9: 5xx в
   done не запоминается, своя pending снимается — единица не записана; журнал cammeta-go, урок 3 № 2);
   номер записать в заявку с cas моей версии,
   полученная версия заявки становится моей; не создавать единицу до успешного сохранения номера
4. отказы формы по порядку (внутри каждой проверки поля — в порядке объявления unit.fields; первый отказ — первого по
   спеке поля): платформенные поля → незнакомые;
   создание: дополнить непереданные поля по Н1.2, сохранив сведения, что передал клиент;
   правка: только переданные поля, без заполнения умолчаний; затем проверки значений:
   blob (не дайджест; при создании не ""; при правке не прежний дайджест строки и не "" — новый дайджест только дверью байтов `PUT /{rows}/{id}/{blob_field}`, урок 10 Н2) → json (not_json, too_long 4000 байт
   канонического текста, схема) → enum → типы значений (Н4 not_number) → вес: присутствующее значение поля placement.weight.field ≥ 1 (P/04 Н1.3)
   (при создании также после заполнения default; при правке — если поле передано) → url → группа (P/04 Н1.3) → метки (азбука урока 4 Н2.1, добавлено М10/4)
   у *_secret значение-конверт enc: и значение-маска — 400 (добавлено М10/7 Н3 «создать/править», шаг 2; М10/7 Н4)
5. named: поле-источник id передано или получено умолчанием непустым → по Н1.3; пустой или непереданный id шаг 5
   пропускает: отказ даст шаг 6 («needs a <поле>»), а у не-required поля — 400 bad id «is empty» после шага 6;
   строка есть и не надгробие → 409 exists — кроме продолжения заявки (Гонки): строка с revision 1
   записана этой заявкой (ответа в заявке нет) → шаг 9 с этой строкой; надгробие с иными fixed → 400
6. обязательные: каждое required-поле передано клиентом и не ""                        → иначе 400 «needs a <поле>»
7. ссылки: ref / must_match (в обе стороны, Н1.3) / unique по живым строкам → 409 conflict с fault
8. подготовить строку {id, revision: 1 | надгробие + 1, поля} и полную строку done-заявки с успешным ответом в форме реализации (п. 3 выбора);
   проверить вес обеих против потолка хранилища → иначе 413 row too large, единицу не писать, к шагу 9;
   записать строку единицы с cas "" | cas надгробия
   и guard: {key: <sub>/idem/<ключ>, index: моя версия заявки}
   toolarge: достоверно ничего не записано → 413 row too large, к шагу 9;
   conflict: numeric с зарезервированным id и строка уже есть → это тот же create → 201 та же строка;
             named → 409 exists
9. запомнить ответ < 500, в том числе отказ формы 400, в заявке с cas моей версии; успех записи → вернуть ответ (201: {строка, worker: null})
   если запись результата не подтверждена (в том числе toolarge самой заявки) → 503 store unavailable;
   5xx как done не запоминать; снять свою pending с cas только если строка единицы достоверно не записана;
   если строка записана или результат её записи неизвестен — сохранить pending для продолжения
```

**Владение заявкой.** Версия строки заявки — условие каждого изменения: записи/снятия самой заявки
идут с `cas` моей версии, резерв счётчика и создание единицы — со стражем этой версии вместе с `cas`
целевой строки. Проверить заявку отдельным чтением перед безусловной записью недостаточно.
После успешного изменения заявки исполнитель запоминает новую версию; перехват всегда меняет её.
После `412 guard` или конфликта `cas` заявки прежний исполнитель прекращает изменения и перечитывает
заявку, не присваивая себе её новую версию: тот же отпечаток и `done` → сохранённый ответ целиком;
тот же отпечаток и `pending` → `409 in flight`; иной отпечаток → `422 key reused`;
нет заявки или хранилище не ответило → `503 store unavailable`, клиент повторяет с тем же ключом.
Он не сохраняет этот отказ и не снимает чужую заявку. После неизвестного исхода записи он также
не продолжает со старым предположением об успехе: до выяснения сохраняется pending, клиент получает 503.

Отсутствующее после материализации поле веса (например, ненаданное inherit) не подменяет отказ
значения: для расчёта веса такой строки используется placement.weight.default. Присутствующие
0, отрицательное или нечисловое значение не заменяются этим default. Пустая форма int равна 0,
поэтому спека с полем веса без подходящего default может требовать явного положительного значения
при POST; правила материализации Н1.2 остаются общими.

**Гонки.** Две консоли с одним ключом: заявка с `cas ""` пропускает одну; вторая видит `pending` и отвечает `409 in flight`, потом — прежний ответ. Две консоли с разными ключами и одним именем: запись строки с `cas ""` пропускает одну; вторая получает `409 exists`. Консоль умерла после резерва номера: заявка через 30 с достаётся другой консоли, и та продолжает с шага 4 — проверки формы, обязательных полей и ссылок повторяются — и пишет на шаге 8 номером из заявки (numeric): строка с ним уже есть → тот же create, 201 та же строка; нет → записать её этим номером. Named: строка с этим именем есть, `revision: 1`, а ответа в заявке нет → записана этой заявкой, 201 (одноимённое чужое создание в то же окно 30 с неразличимо и принимается). Консоль умерла между резервом номера (cas счётчика) и записью номера в заявку: заявка без номера — резервировать заново с шага 3, прежний номер сгорел (две строки, две операции — неделимости между ними нет). Номер, записанный в заявку до смерти, не сгорает; сгорает номер отказанной попытки (шаги 5–7 вернули отказ).

Прежняя консоль A может ожить после перехвата консолью B. Если A зарезервировала 1, но не сохранила
его в заявке, её поздний `cas` заявки отказывается; A не доходит до записи единицы 1. B резервирует 2
и создаёт только её. Если номер 1 уже сохранён, B сохраняет его при перехвате: поздняя запись A
под старым стражем отказывается, а B продолжает с номером 1. Если A записала единицу до перехвата,
B находит эту же строку и сохраняет ответ; поздний `cas` ответа A не заменяет результат B.
Та же защита действует на отказ и снятие pending: A не удаляет заявку B. Потеря ответа о создании
не даёт права снять pending — сохранённый номер нужен продолжению. Эти исходы опираются на атомарные
`cas`/`guard` P/01.1, а не на предположение, что прежний исполнитель умер.

Превышение потолка служебной записи до шага 8 также даёт 413 row too large. Если pending ещё
не создана, сохранять ответ негде; если заявка своя — отказ завершается через шаг 9. Зарезервированный
номер не возвращается. Отказ сохранения результата на шаге 9 — 503: если единица уже записана или
исход неизвестен, pending остаётся для восстановления; чужую заявку не изменяют.

### править(id, тело) → 200 строка | отказ

`Idempotency-Key` у PUT не читается: правка сходится по `cas` прочитанной строки, а повтор PUT — новая правка,
которая снова поднимает `revision`.

**Условие `If-Match`** (М11/6: правка домена применяется агентом от ревизии, которую видел домен). Заголовок
`If-Match: <revision>` у `PUT` и `DELETE` необязателен, для любого вызывающего: значение — десятичное целое ≥ 1 без
знака и ведущих нулей, иначе 400 `{error: "If-Match is a unit revision"}` до чтения строки. Есть и не равно `revision`
прочитанной строки → 412 `{error: "revision moved", revision: <нынешняя>}`, ничего не записано; сравнение — на каждом
перечитывании прохода (после конфликта `cas` — с шага 3 снова). Нет — как прежде.

```
1. id по Н1.3; путь — ровно один id                                        → иначе 400 / 404
   тело — JSON-объект; заданное нечитаемое кольцо → 503 SealingUnavailable до правки/проверок полей (М10/7 Н3)
2. отказы формы (шаг 4 выше), кроме blob-подслучая «не прежний дайджест строки» — он после чтения; секрет пустой или null — сохранить прежний (урок 7 Н3 «создать/править», шаг 3; смена поля из bound_to при пустом секрете — 400 «must be given anew»)
3. прочитать строку; нет или deleted                                       → 404 no such unit
   (нет строки и свежий дайджест в теле — 404: строки нет, сравнивать не с чем)
3а. If-Match есть и не равен revision строки                                 → 412 revision moved {revision}
4. fixed-поле меняется или переданное поле-источник именованного id не равно id пути → 400 «<поле> is fixed»;
   blob-поле: значение не прежний дайджест строки и не ""                  → 400 (новый дайджест — только дверью байтов `PUT /{rows}/{id}/{blob_field}`, урок 10 Н2)
5. ссылки по новым значениям, must_match в обе стороны (Н1.3)               → 409 conflict с fault
6. записать {…прежние, …новые, revision: прежний + 1} с cas прочитанной версии;
   toolarge → 413 row too large, прежняя строка/revision сохранены; conflict → перечитать с шага 3;
   предел повторов при conflict исчерпан → 503 store unavailable, строка и revision прежние (журнал cammeta-go, урок 3 № 2)
```

**Гонки.** Две правки одной строки: `cas` пропускает одну, вторая перечитывает и накладывает свои поля поверх (шаг 6 → 3) — обе отвечают 200, у второй `revision` на два выше — кроме blob-поля: проверка «прежний дайджест строки» идёт на шаге 4 по **перечитанной** строке, и повтор, заставший `mask` снятым (`""`), с тем же дайджестом в теле получает 400, а не восстанавливает ссылку на тело, которое уборка могла уже снять; клиент версий не присылает, 409 — только `exists`/`conflict` ссылок. Правка против удаления: перечитав надгробие — 404.

Проверки `ref`/`must_match`/`unique` создания и правки выполняются до записи и не атомарны
с изменением других строк. Две правки разных единиц, обе проверившие прежние значения,
могут успешно записать одинаковое unique-значение. Аналогично результат проверки связи
может устареть из-за правки или удаления связанной строки. Последующий проход контроллера
размещения не проверяет эти ограничения; гарантии автоматического обнаружения, записи
диагностики или исправления такого расхождения нет. Проверка при следующем POST/PUT
выполняется по тем же правилам, а не служит фоновым аудитом. `ref` сам по себе не вводит
требование существования цели (ADR-0057): условия отказа остаются условиями соответствующего поля.

### удалить(id) → 200 | 404

```
0. If-Match не по форме                                                     → 400
1. прочитать строку; нет или deleted                                       → 404
1а. If-Match есть и не равен revision строки                                → 412 revision moved {revision}
2. записать {…строка, deleted: "true"} с cas прочитанной версии; revision не меняется; conflict → с шага 1
3. второй шаг — контроллер (P/04 Н3 «проход()», шаг 4 «снять удалённые (reason deleted)»): снять с назначения, строка размещения {worker: "", reason: deleted, rev + 1}
```

**Гонки.** Удаление против правки: `cas` — проигравший перечитывает и повторяет (удаление — поверх правки, правка — 404 на надгробии); удаление против удаления — второе 404 (надгробие уже стоит); удаление при живом назначении — контроллер снимает единицу следующим проходом ([P/04 Н3 «проход()»](../../Platform/04-controller/spec/04-controller.norms.md), шаг 4), воркер — при чтении назначения ([P/03.3 Н3 «цикл()»](../../Platform/03-worker/spec/03.3-worker.norms.md), шаг 2: ведомой нет в назначении → stop_unit).

## Решает реализация

Реализация обязана назвать в своём описании:

1. **разбивку семей** на строки и объекты сверх Н1.1, если она иная, и где лежат объекты;

6. **периоды**: предел повторов при `conflict` на `next_id`, правке (исход исчерпания — норма Н3: 503 store unavailable у двери);
   шаг продления и повторы захвата и эпохи — [P/03.2](../../Platform/03-worker/spec/03.2-worker.norms.md) «Решает реализация» п. 2 (стадия B);

## Чеклист готовности

Реализация соответствует уроку, когда выполнена каждая норма; id нормы `М10/3-NN` — то, на что ссылаются дельты решений, находки и записи окон (ADR-0080 доп. 6):

- [ ] **М10/3-01** раскладка ключей Н1.1: семьи, зарезервированные имена таблиц; у строки один писатель, семья делится по форме строки только по правилу урока-владельца (просьбы — урок 8 Н1.5, таблицы — урок 10 Н1.6) — проверяется чтением (права — P/02.5 Н1.4); представимость обязательного файлового пути до публикации/захвата — чтением Н1.3 и README приёмки
