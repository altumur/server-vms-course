# V/04.3 — Detector events: norms

This English text is the source; the Russian [`04.3-det.norms.md`](../04.3-det.norms.md) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 3 of lesson V/04 «Живая детекция» (ADR-0080; the VMS module — ADR-0090). [Lecture](../../04-det.md),
[instructions](../04-det.README.md), manifest [`det.subsystem.yaml`](../../det.subsystem.yaml). The platform is the export
`cammeta-specs` `7a875c75`.

The output of the detector is not video but event rows in the resource log of its own server. Events are not a subsystem: an event has no
unit of work, its place is decided by the writer, reading and merging are the platform. The chapter sets norms for what the detector writes, of which
class a row is, what is suppressed and how a detection mark reaches the screen. The mechanism of the log is [the event log contract](../../../../Platform/common/contracts/event-journal.md),
the worker's writer is [P/03.6 Н1.2](../../../../Platform/03-worker/spec/03.6-worker.norms.md).

Norm ids are `V/04.3-MM`; the map to former lessons is [`id-map.tsv`](../../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../../Platform/01-store/spec/01.1-store.norms.md#н0-vocabulary).

## Н1 Form

**Time.** The `t` of a row is the seconds of the writer's clock at the moment of writing (the event log contract `line`); the moment of the model's
observation, if it is different, is `occurred`.

**Data** (the shared families of the [platform catalogue](../../../../Platform/common/data/catalog.tsv)): writes — the resource log files
of its own server `<корень событий>/det/<name>/e<эпоха>/…events.jsonl` and `<корень событий>/det.alarms/<name>/e<эпоха>/…`
([P/05](../../../../Platform/05-resource/spec/05-resource.norms.md) Н1.2); `requires: resource` (V/04.1 Н1.4) places the detector
on a server with a resource.

### Н1.1 Writing

Each event of the model `(kind, поля)` (chapter 2 Н1.2) MUST be one log row written by the worker's writer (P/03.6 Н1.2): the tree `det`,
the unit — the detector's name, the epoch — its epoch (chapter 2 Н1.3); `of: cam/<cam>` — from `about` (V/04.1 Н1.1): the detector's events are
the camera's events, they are found by a query about the camera. The subsystem, the unit and the epoch are not repeated in the row — the path tells them.

- Before **each** write the worker MUST check the right to write under the lease ([P/03.2 Н1.6](../../../../Platform/03-worker/spec/03.2-worker.norms.md)
  `may_write`; `unconfirmed_max` — default `off`): if the lease is not confirmed, the row MUST NOT be written; the model is not stopped until
  the runtime decides.
- The model's fields are the top-level fields of the row next to the log fields (`t`, `id`, `kind`, `class`, `of`, `v`); the model MUST NOT give fields with
  these names nor with the names of the suppression summary `repeats`, `since`, `until`; its own `occurred` MUST be only a finite number (the event log contract «line», «Отказы писателя»). The model MAY omit the field `cam`: the link to the camera is `of`.
- If a row was not written — a write error or the lease is not confirmed (`may_write` is false): the row is lost, it is counted in `events_refused`
  of the heartbeat (chapter 4 Н1.1 — the same definition); the model goes on. A repeat while `may_write` is false does not enter the suppression window and
  is counted in the same way.

### Н1.2 Row class

The class is decided by the writer (the event log contract «class»): a row is `alarm` if its `kind` is in the field `alarms` of the detector
row (V/04.1 Н1.1; default `["linecross", "lpr"]`), otherwise `observation`. An alarm is written with `fsync` into its own tree
`det.alarms/…`, lives for the alarm retention and, when the window overflows, goes ahead of observations ([the event merge contract](../../../../Platform/common/contracts/events-merge.md) `cut`). The class is a fact about what
the operator set the model up for; the platform fixes only the two words.

### Н1.3 Suppression

`events.suppress.motion: {window: 30, by: [cam]}` (P/03.6 Н1.2): the first row of a window is written as it is; repeats in the window
are counted; the summary of the window is by P/03.6 Н1.2 `rule`; the flush is on each pass.
Suppression, even without `by`, is separate per (tree, unit, epoch, `kind`, class); `by: [cam]` means «any motion of this detector in the
window» (the field `cam` of the model; an absent one is one value «absent»): the model's fields (the score, the box, the counter) drift between two
looks at one scene and do not multiply observations. 30 s is a VMS number: a tree in the wind — one row per window, two people a
minute apart — two. `linecross` and `lpr` are not suppressed: a second car across the line is a second car. `motion` is suppressed even with `alarms: [motion]`:
suppression is by `kind`, the class only gives a separate window (P/03.6 Н1.2). The window lives in the writer, not in the model: `stop_unit` does
not close it, a restart under the same epoch continues it; once the epoch is released, `may_write` is false and the summary is not written on closing (Н1.1).

### Н1.4 The path of a detection mark to the screen

The detector notifies no one: the row is written into the resource's file — and that is all. The resource index reads the files at the moment of the query
(P/05 Н1.3); the page asks the console's `/events?unit=cam/<cam>`, the console merges the answers of the resources of all servers and marks
the rows of former epochs `fenced` ([P/06.4 Н1.3](../../../../Platform/06-console/spec/06.4-console.norms.md)); the detector's mark is on the
camera's timeline (V/11). Five steps, four processes, not a single call from the writer to the reader.

## Н3 Pass

```
for each running detector: the model's events → for each: may_write? → class by alarms → suppression (motion) → row
on each pass: flush of the closed suppression windows (summary row)
```

**Races.** Substitution: a new worker took the detector with a higher epoch, the former one still writes until it loses the lease — the reader marks the rows of the former epoch
`fenced` (P/06.4 Н1.3); there are no duplicates in one tree: the epoch is in the path.

---

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| the lease is not confirmed | the row is not written, `events_refused` | heartbeat | the runtime decides the fate of the unit (P/03.2) |
| the write failed | the row is lost, `events_refused` | heartbeat | the resource, the disk |
| there is no resource on the server | the detector is not placed (`requires: resource`) | the pass report | install a resource |

## Н5 Acceptance

mechanism (acceptance P/03.6, P/06.4), by reading.
