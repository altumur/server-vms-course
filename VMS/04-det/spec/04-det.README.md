# V/04 Живая детекция — инструкция для реализации

Что реализация подсистемы `det` делает и как проверить результат. Канон — нормы глав `04.K-det.norms.md`; эта
инструкция их не дополняет. Платформа — выгрузка `cammeta-specs` `d3f8e05` (пин VMS).

## Входы и их приоритет

- Канон — нормы глав `04.K-det.norms.md` (Н1–Н5 каждой главы; адреса `V/04.K Н…`).
- Канон манифеста — [`det.subsystem.yaml`](../det.subsystem.yaml): байты как есть.
- Приёмка — [глава 1](../acceptance/1/README.md), [глава 4](../acceptance/4/README.md); стенд и словарь — [общий README приёмки VMS](../../common/acceptance/README.md); новых требований приёмка не вводит.
- Векторы — [`mask`](../../04-det/vectors/mask/README.md) (команда пакета).
- [Лекция](../04-det.md) объясняет причины; платформа — нормы выгрузки пина VMS по адресам `P/…` (их правит не VMS).

Противоречие записать с местом и контрпримером (раздел «При расхождении»); произвольный отказ не заменяет
отсутствующую норму. Устройство кода остаётся реализации в рамках канона.

## Что создать — результат по главам

| Глава | Что есть у реализации | Проверка |
|---|---|---|
| V/04.1 | манифест `VMS/04-det/det.subsystem.yaml` грузится строгим загрузчиком без правок (вместе с `auto` — заказчиком строк `det`); дверь единиц консоли исполняет объявления детектора | [приёмка 1](../acceptance/1/README.md) |
| V/04.2 | источник по пульсам (доля `cam.shm`, RTSP петли, приёмник своего кластера листом `detworker`), сверка; реестр моделей и учебная `tick`; фазы с `reason`; перезапуск по ревизии | чтением; приёмка 4 (глава 4) |
| V/04.3 | события модели — строки журнала писателем платформы (`of` камеры, `may_write` перед каждой), класс по `alarms`, подавление `motion` | чтением; приёмка 4 (глава 4) |
| V/04.4 | пульс (`events_written`, `events_refused`, элемент `phase`/`reason`/`events`/`via`), ряд `units_running`, остановка; команда запуска воркера для «Стенда» — в описании реализации | [приёмка 4](../acceptance/4/README.md) |

Манифест — данные спецификации: реализация читает его байты как есть (ADR-0090 доп. (6) п. 8).

## Порядок

Сначала платформа (генерация стадии C, прошедшая приёмку платформы), затем `cam` (V/01), `rec` (V/02), затем `det` —
приёмка VMS идёт только на такой платформе (ADR-0090 доп. (8), (9)).

## Ловушки

| Норма | Возможная ошибка | Как сохранить поведение |
|---|---|---|
| V/04.1 Н1.1 | брать маску детектора, когда у заказа свой непустой `mask` | свой `mask` — первым, иначе маска строки `mask_of` на момент запуска; детектора нет — отказ запуска |
| V/04.4 Н1.1 | называть свой счётчик пульса `events` | верхний счётчик — `events_written`: имя `events` занято платформой |
| V/04.4 Н1.3 | терять проглоченные повторы при остановке | каждое окно подавления с повторами закрывается строкой итога до последнего пульса |
| V/04.1 Н1.1 | считать `params` малым полем со своим пределом | `params` — строка, предел — общий предел строки |

## Готово, когда

Манифест грузится строгим загрузчиком без правок; приёмка глав 1, 4 проходит на платформе, прошедшей свою приёмку; векторы урока проходят командой пакета;
пункты чеклистов, отмеченные «чтением», подтверждены описанием реализации (раздел «Решает реализация» каждой главы).
Проверка схемы, загрузчика и стенда друг друга не подменяют.

## При расхождении

Порядок источников: нормы главы → OpenAPI → приёмка и векторы → лекция; платформа — нормы выгрузки пина VMS.
Норма молчит или противоречит себе — вопрос «Спецификации VMS» с местом, контрпримером и предложением; норма
платформы — через «Архитектора». Дефект приёмки (ожидание против нормы) — тот же маршрут; закрытое решение
вносится в канон, а не остаётся в этой инструкции.
