# V/10.2 — The model door: norms

This English text is the source; the Russian translation `ru/spec/10.2-assist.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 2 of lesson V/10 «Ассистент» (ADR-0080; the VMS module — ADR-0090; the subsystem — ADR-0093, addendum (1) items 1, 2).
Lecture (`ru/10-assist.md`, for people, not in the export), [instructions](10-assist.README.md), [OpenAPI](10-assist.api.openapi.yaml), manifest
[`assist.subsystem.yaml`](../assist.subsystem.yaml). The platform is the export `cammeta-specs` `7a875c75`.

A door client with `view` on the model row asks the console for the address of the holder's door and a token (`GET /assist/where/<name>`) and
calls the door itself, as a viewer calls the gateway (V/03.3); `backend` calls it by a console route by ticket, the console sets the token
(V/11.7 Н1.2, ADR-0093 addendum (7)). The admin's credentials do not go to the holder: the door token is narrow, for 120 s, and is not good for the console. A model step takes 10–50 s, therefore the door is **asynchronous**:
submit a step, ask its state or answer, cancel it. A step belongs to the person whose name is in the token; for anyone else it does not exist.
The chapter sets norms for the route `chat`, the step and its life, the step owner, the queue, limits, the log and the model stub for acceptance.
What the client sends in a step (messages, tool descriptions) and what it does with the answer — V/11.9–V/11.11.

Norm ids are `V/10.2-MM`; the map to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../NORMATIVE-TERMS.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#n0-vocabulary).

## Н1 Form

**Time.** `expires` of the token is Unix seconds (the door token contract); the door's timeouts are the process's monotonic clock, in seconds.

**Data** (the shared families of the [platform catalogue](../../../Platform/common/data/catalog.tsv)): reads — `door/keys` (token
verification); writes — the door log `audit/assistworker/e1` (the event log contract «Журнал двери процесса»), the heartbeat (`queued`,
`active`, `steps`, chapter 1 Н1.4). Steps live only in the holder's memory: their texts go neither to disk, nor to the store, nor to the log.

### Н1.1 Address and token

- `door: {routes: [chat]}` — the route is a name: admittance is the console door token ([P/03.4 Н1.7](../../../Platform/03-worker/spec/03.4-worker.norms.md)
  `door_admission` `token`; [the door token contract](../../../Platform/common/contracts/door-token.md)). The address is the rule
  `door_address` of P/03.4 Н1.7 (with a kit of the role `assistworker` — `https://<SERVER_NAME>:<порт>`, without one — loopback), the port is
  `CHAT_PORT` of the subsystem file `/etc/assist/assist.env` (not set or 0 — an OS port); the address is the field `url` of the heartbeat.
- The address and the token are issued by the console: `GET /assist/where/<name>` with the right `view` on the model row → `door: {url, token,
  expires, routes}` ([P/06.5](../../../Platform/06-console/spec/06.5-console.norms.md) Н3 «`/where/<id>`»; TTL 120 s;
  the console log `door.issued`). The door exists at the holder of the row:
  while nobody holds the row, `where` gives no door.
- The token is by the contract, the client sends `Authorization: Bearer` (P/03.4 Н3 «токен двери у держателя»); the holder MUST verify it by the contract: `unit` is
  `assist/<name>` of the request path and a row that this instance holds, `holder` is its own instance, `routes` contains `chat`, it has not expired. Any token refusal is 403
  `{"error": "forbidden"}` without a reason. The token is needed on every request; it has expired — the client takes a new `where` (V/11.9).
- **The step owner** is `user` of the verified token with which the step was submitted (ADR-0093 addendum (1) item 2). State, answer and
  cancellation — only by a request with a token of the same `user`; for another `user` there is no step — 404, as for an unknown one. A new token of the same
  `user` at the same holder continues the step: the step is bound to the person, not to the token. In an open cluster (`open: true`)
  everyone has one `user` — and their steps are shared; this is intended: there are no different rights there either.

### Н1.2 Submitting a step

`POST /chat/<name>/steps`, the body is JSON (`Content-Type: application/json`), the OpenAI chat form without streaming output:

```yaml
messages:          an array of 1…512 messages {role: system | user | tool, content?: string, tool_call_id?: string} or
                   {role: assistant, content?: string | null, tool_calls?: [{id, type: function, function: {name,
                   arguments: string}}], reasoning_content?: string} — a model message from the answer (Н1.3) returns
                   to the history as is; extra keys of tool_calls are skipped; whether to return the reasoning is decided by the client (V/11.9)
tools:             an array of 0…64 {type: function, function: {name, description?, parameters: a JSON Schema object}}, extra keys are skipped; optional
tool_choice:       auto | required | none; optional, the default is auto
reasoning_effort:  low | medium | high; optional, the default is medium
max_tokens:        an integer 1…context of the model row; optional
turn:              the client's turn to which the step belongs: 32 lowercase hex (128 random bits, V/11.9); optional —
                   without it the step shares the data cache with no other step (Н1.4)
```

1. `Content-Length` greater than `BODY` = 1 MiB — 413 before reading the body and before admittance (`door_limits` P/03.4 Н1.7);
2. token (Н1.1) → otherwise 403; not JSON or not in the form above — 400 `{"error": "bad step", "detail": <первое нарушение>}`;
3. the phase of the model row (chapter 1 Н1.4): `loading` — 503 `{"error": "loading", "retry_after": 5}`; `failed`, `stopped` — 503
   `{"error": "model unavailable", "detail": <reason>}`;
4. the owner already has `PER_USER` = 2 unfinished steps at this model — 429 `{"error": "too many steps"}`;
5. the queue already holds `QUEUE` = 4 steps — 503 `{"error": "busy", "retry_after": 1}`;
6. **202** `{step, state: "queued"}`, `Location: /chat/<name>/steps/<step>` (the segment `step` is percent-encoded); the step enters the queue (Н1.4).

`step` is `<instance>.<32 строчных hex>`: the holder's instance (`instance` of the heartbeat, P/03.4 Н1.1; it may contain a dot —
[the instance contract](../../../Platform/common/contracts/instance.md)) and 128 random bits. It is parsed by the **last**
dot: on the right — 32 hex, on the left — the instance; there is no dot or on the left is not its own instance — 410 `gone`; its own on the left, there is no step — 404. A repeat
of `POST` is a new step: the door has no memory of repeats, the client does not repeat an unknown outcome by itself (V/11.9).

### Н1.3 State and answer

`GET /chat/<name>/steps/<step>[?wait=<секунды>]`, `wait` is an integer 0…20, default 0;
anything else (a repeat, empty, not an integer, outside 0…20) — 400 `bad step` (Н1.6 «Input parsing»).

1. token → otherwise 403;
1a. `wait` is parsed (Н1.6 «Input parsing») → otherwise 400 `bad step`: query parsing finishes before the checks of the instance and
   the owner (two errors at once — 400; an addition by Kimi to the analysis of the V/10 review, С2);
2. the instance in `step` is not its own — 410 `{"error": "gone"}`: the step was at another holder or before a restart of this one; the client
   starts the turn anew (ADR-0093 addendum (1) item 2);
3. there is no step or its owner is not `user` of the token — 404 `{"error": "no such step"}`;
4. the step is not finished and `wait` > 0 — the answer waits for the step to finish, but no longer than `wait` seconds;
5. **200** — the state:

```yaml
step:           the step id
state:          queued | running | done | failed | cancelled
ahead:          steps ahead in the queue — when queued
message:        when done — the model message: {role: assistant, content (string | null), tool_calls?, reasoning_content?};
                content is a string; the model answer has none — null is given (the contract: content is mandatory; an addition by Kimi to the analysis of the V/10 review, С1);
                other fields of the model server answer the holder does not give — the message is fit for the history of the next step (Н1.2)
finish_reason:  when done — stop | tool_calls | length
usage:          when done — exactly {prompt_tokens, completion_tokens}; other fields of the model server the holder does not give
seconds:        when done, failed — the model's seconds on the step; a step that did not reach the model — 0
reason:         when failed, cancelled — the words of the table below
```

| Outcome | `state` | `reason` |
|---|---|---|
| the model answered 200 | `done` | — |
| the model answered not 200 or 200 not in the form `step` (chapter 1 Н1.3; `finish_reason` not from the list above, `arguments` not a string), or the model process crashed | `failed` | `model failed` |
| the step is in work longer than `STEP_MAX` = 180 s | `failed` | `too long` — the request to the model is broken off |
| the step is in the queue longer than `QUEUE_MAX` = 120 s | `failed` | `queue too long` |
| the step messages are longer than the window (`context`) | `failed` | `context exceeded` |
| an edit of the model row; the queue steps at a process restart (chapter 1 Н1.3) | `failed` | `model restarted` |
| `enabled: false` (chapter 1 Н1.3) | `cancelled` | `disabled` |
| cancellation by the owner (Н1.5) | `cancelled` (the log row; the cancellation answer is 200 `cancelled`) | `cancelled`; then the step is forgotten, 404 (an addition by Kimi to the analysis of the V/10 review, С3) |
| the owner has not asked about the unfinished step for longer than `ABANDON` = 30 s — from the end of the last answer to a `GET` of this step (from `202` if there was no `GET`); while a long poll is in progress, the step is not abandoned | `cancelled` | `abandoned` — the request to the model is broken off |

**How long a finished step lives.** After the first issuance of the finished state — another `KEEP` = 60 s (a repeat of `GET` after
a break reads the same answer); one not issued — `KEEP_UNREAD` = 120 s after finishing. Then the step is forgotten — 404.

### Н1.4 The queue and isolation of steps

- **One model step at a time.** The holder sends the model process one step (chapter 1 Н1.3), the others wait in the queue in
  the order of submission. The limits are `QUEUE` and `PER_USER` (Н1.2).
- **A step is only what is in it.** The model sees the messages of its own step and nothing more: the holder keeps no history between steps
  and does not carry messages of one step into another. The history of the turn is carried by the client (V/11.9).
- **The model cache.** The context (prefix) cache of the model process is divided into two parts (ADR-0093 addendum (1) item 2, a clarification
  by «Архитектор» 2026-10-28):
  - **the data-free prefix** — tool descriptions (`tools`) and the leading `system` messages of the step — is shared by all: it holds
    only the system text of the lesson, without rows, requests, rights and results. This is a requirement on the client: the `system` messages
    of a step are only the lesson text; the overview, rights and rows go as `user` and `tool` messages (the norm V/11.9 with the harness package);
    the holder does not check the content of `system`;
  - **everything after it** — the request text, tool results, model answers — is reused only by a step of the same
    `user` and the same `turn` (Н1.2). Between turns of one person the data cache is not carried over: grants may
    narrow between turns, and a new turn MUST NOT see what the person saw before. A step without `turn` starts after the shared prefix with
    an empty cache.
  How the holder separates the shared prefix and drops the rest is named by the implementation.
- **Change of holder.** Another worker took the row, or this one was restarted — the steps of the former one are lost: 410 `gone` (Н1.3 step 2).
  There is no transfer of steps.

### Н1.5 Cancellation

`DELETE /chat/<name>/steps/<step>`: token — otherwise 403; the instance is not its own — 410 `gone`; there is no step or it is someone else's — 404
`no such step`; otherwise — **200** `{step, state: "cancelled"}`: a step in the queue is removed, for one in work the request to the model is broken off
(chapter 1 Н1.3 `step`), the step is forgotten; an already finished step is forgotten, `state` is its outcome (`done`, `failed`, `cancelled`).
The client cancels a step when the turn is cancelled or the client leaves (V/11.9); if it did not manage to, `ABANDON` removes the step (Н1.3). Another method
on the route — 405, another path — 404.

### Н1.6 Limits, log, CORS

- **Limits** — `door_limits` of P/03.4 Н1.7 (connections 32, per address 8, headers within 5 s, body 1 MiB, pace). The pace
  (`PACE_FLOOR` after `PACE_AFTER` = 30 s) is measured from the start of the connection, and a chain of long polls over one
  keep-alive connection would pass 30 s almost without bytes and would be broken off, and the client puts into its pool and hands to a poll any
  connection whose answer came without `Connection: close`. Therefore the door gives **all answers of the route `chat`** — `202`, `200` with any
  `wait`, the cancellation answer, the refusals 400, 403, 404, 405, 410, 429, 503 — with `Connection: close`: each request is its own
  connection, a poll lasts no longer than 20 s. Residual risk: the answers that the process door itself gives before the route (preflight
  `OPTIONS`, 413 and `busy` from `door_limits`, P/03.4 Н1.7) are not normed by the lesson; preflight is cached for 600 s, and its
  connection is taken at once by the real request. The door `chat` does not
  offer HTTP/2 (ALPN — only `http/1.1`): an HTTP/2 stream does not close the connection. `Connection: close`, `QUEUE`, `PER_USER`,
  `STEP_MAX`, `QUEUE_MAX`, `ABANDON`, `KEEP`, `KEEP_UNREAD` are lesson constants (`door_limits.other`).
- **Log** — the shared fields of the process door log (the event log contract) and, beyond them, one row per step:
  `assist.step` — `of` (`assist/<name>`), `step`, `user`, `state`, `reason`, `seconds`, `prompt_tokens`,
  `completion_tokens`; at completion, and for a step forgotten unfinished — at forgetting: `state` is the last one (`queued`, `running`),
  there is no `reason`. The row is written outside a request: `sub` is `assist`, `target` is `<name>`, `user` is the owner; `status`, `bytes`,
  `addr` and fields without a value are not written. A log refusal does not change the step outcome and does not hold the queue; the log row is without texts.
  There are no texts of messages, tool descriptions and model answers in the log.
- **CORS** — `cors` of the role certificate contract via P/03.4 Н1.7, without a list of its own. The door writes the retry timeout into the body —
  `retry_after` (Н1.2): an application response header is not visible to a client in a browser from another origin (a class shared by the VMS lessons); except
  `busy` of the process door: there is no timeout in the body, the client waits 5 s (V/11.9 Н1.3).
- **Input parsing** — the shared parsing of [P/01.1 Н2.1](../../../Platform/01-store/spec/01.1-store.norms.md) via P/03.4 Н1.7
  `door_limits` (body framing, `chunked`, early refusal) with deviations: the segment `step` is percent-decoded once,
  a bad `%` — 404 `no such step`; the rest of the path — byte for byte (a trailing slash, an empty segment,
  `%`-encoding — another path, 404); a method outside the route — 405; query — only `wait` at a `GET` of a step (Н1.3): the value
  is decoded (P/01.1 Н2.1), then `^(0|[1-9][0-9]?)$` and the limit 0…20: `%35` is accepted; a repeat, an empty value, `05`, `+5`,
  `5.0`, `-0` — 400 `{"error": "bad step"}`; other parameters, except `t` of the door token contract, are not read; the `POST` body is one JSON object,
  strictly (UTF-8, a repeated key, a non-finite number — 400 `bad step`). Order: path → method → token → query and body;
  parsing of query and body finishes before the checks of the instance and the owner (Н1.2, Н1.3).

## Н3 Pass

```
submit:  Content-Length → token → body → phase → PER_USER → QUEUE → step (instance.random), queue, 202
every answer of the route chat — Connection: close
queue:   first in the queue and the model is free → running → POST /v1/chat/completions to the model process (chapter 1 Н1.3)
         → answer 200 → done | not 200, crashed, STEP_MAX → failed | cancellation, ABANDON → break off the request, cancelled or forgotten
         → log assist.step → the next in the queue
ask:     token → wait parsed? → own instance (by the last dot)? → own owner? → wait ≤ wait → state
cancel:  token → own instance? → own owner? → remove or break off → forget
```

**Races.** Cancellation and a model answer at one moment: whichever finished first under the steps lock is the outcome; after cancellation
the step is forgotten, a late model answer is discarded. The step is forgotten while a poll is pending — the answer is at once 404 `no such step`; a break of the poll
is the end of an answer for `ABANDON`. Two `POST`s of one owner beyond `PER_USER`: the count is under the same
lock, the second gets 429. The row was released while a step is in work: the model process goes out (chapter 1 Н1.3), the steps are
forgotten, at the new holder — 410. The token expired in the middle of a long poll: the answer of this poll is given (the token was verified at the
admission of the request), the next request asks for a new `where`.

## Н4 Refusals

A closed list — [`data/refusal-words.tsv`](../data/refusal-words.tsv), the door `chat`.

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| no token, the wrong one, expired | 403 `forbidden` | the client | `where` again, once |
| the body is larger than 1 MiB | 413 | the client | — |
| the body is not in the step form | 400 `bad step`, `detail` | the client | — (a client error) |
| `wait` not in form, a path with a trailing slash or `%`-encoded, except the segment `step` | 400 `bad step` / 404 | the client | — (a client error) |
| the model is loading | 503 `loading`, `retry_after` | the client | repeat after `retry_after` |
| the model is `failed` or `stopped` | 503 `model unavailable`, `detail` | the client | the words to the admin |
| the owner already has 2 steps | 429 `too many steps` | the client | wait or cancel one's own step |
| the queue is full | 503 `busy`, `retry_after` | the client | repeat after `retry_after` |
| the step is at another holder or from before a restart | 410 `gone` | the client | the turn anew |
| no step, someone else's or forgotten | 404 `no such step` | the client | the turn anew |
| connections beyond the limit | 503 `busy`, `Retry-After: 1` | the client | repeat |

## Н5 Acceptance

[Acceptance 2](../acceptance/2/README.md) — a stand with a model holder and a **model stub** instead of the model server
(ADR-0093 addendum (1) item 11). Scenarios hold transient states by **barriers** of the stub, not by the speed of the stand: `loading` —
by the barrier `load hang`, `queued` of the second step — after the observed `running` of the first (it is held by the barrier `hang`). It observes: the phases `loading` → `running`,
the step `202` → `done`, the long poll, `bad step`, 403 without a token, 410 `gone`; its own id with a `%`-encoded segment `step` — 404 `no such step`, the step owner (someone else's — 404; a domain stand, two
people), `PER_USER`, the queue, cancellation, `abandoned`, `failed`, `stopped`. By reading: `too long`, `queue too long`, the division
of the cache, the log without texts, `Connection: close`, 410 after a change of holder.

**The model stub** is the runner program `model-stub`, which the stand names in `MODEL_COMMAND` (chapter 1 Н1.3) instead of the
model server. No field of the model row switches it on: the stub is a property of the stand, not a setting. The stub protocol:

```yaml
start:   model-stub <answers file>; the environment is as for the model process (chapter 1 Н1.3); listens on ASSIST_MODEL_SOCKET
script:  the answers file — UTF-8, LF, fields separated by TAB, lines with # are comments; the first line is load <seconds> or
         load hang (barrier: the model never loads); then a line for each request POST /v1/chat/completions in
         order: <after> <status> <JSON response body>; <after> is seconds or hang (barrier: no answer until the holder
         breaks off the connection)
busy:    an optional second line busy — during a step GET /health answers 503, as a server with one busy slot
health:  GET /health — 503 for the first load seconds from the start (with load hang — always), then 200; during a step — 200, and with
         busy — 503
step:    request n gets line n: after <after> — the status and the body; not enough lines — 500
seen:    the stub writes to its stderr a line per request: n, the number of messages, a break (aborted) — without texts
```
