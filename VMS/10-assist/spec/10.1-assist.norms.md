# V/10.1 — The model — the unit and the worker: norms

This English text is the source; the Russian translation `ru/spec/10.1-assist.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 1 of lesson V/10 «Ассистент» (ADR-0080; the VMS module — ADR-0090; the subsystem — ADR-0093, addendum (1)).
Lecture (`ru/10-assist.md`, for people, not in the export), [instructions](10-assist.README.md), manifest [`assist.subsystem.yaml`](../assist.subsystem.yaml).
The platform is the export `cammeta-specs` `7a875c75`.

The unit `assist` is an instance of the model on a server with memory for it: «the model floor-3 stands on the server srv-gpu». Its holder is
a platform worker (P/03: capture, epoch, lease, heartbeat, door) with the model server as a child process. The worker has no rights
of its own: it does not read rows of other subsystems, it does not receive people's credentials; everything a model step needs is brought by the door's client
(chapter 2). The chapter sets norms for the fields and rights of the model row, placement, the model process and the heartbeat. The door — chapter 2.

Norm ids are `V/10.1-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#n0-vocabulary).

## Н1 Form

**Time.** The deadlines and timeouts of the chapter are seconds of the monotonic clock of the process.

**Data** (the shared families of the [platform catalogue](../../../Platform/common/data/catalog.tsv)): the row `assist/models/<name>`
(P/06.1), the heartbeat `assist/heartbeats/<воркер>`, the snapshot `assist/snapshot/*` (P/04 Н1.3а); the chapter has no families of its own beyond them.
The worker does not read rows of other subsystems (`worker` of the manifest without `reads`, `writes`, `requests`, `creates`).

### Н1.1 Fields and rights

`unit: {rows: models, id: name}` — the row `assist/models/<name>`, the name is given by the operator. The row has no `about`: the model is about nothing.

| Field | Form | Meaning | Who reads |
|---|---|---|---|
| `name` | `string`, required | the name of the model for people and for `where` | — |
| `enabled` | `bool`, default `true` | `false` — the holder shuts down the model process, the row stays, steps are a refusal (`stopped`, Н1.4) | holder |
| `model` | `string`, default `gpt-oss-20b`, `enum: [gpt-oss-20b]` | which model | holder (Н1.3) |
| `quant` | `string`, default `q8_0`, `enum: [q8_0]` | which weights of the model | holder (Н1.3) |
| `context` | `int`, default `16384`, `4096…65536` | the model window in tokens: the messages of the step and the answer together | holder (Н1.3), door (chapter 2) |
| `labels` | `list`, required, not empty | the label of **one** server with memory for the model (Н1.2) | placement (`labels-subset`) |

- The pair `model`, `quant` is one for now: that pair was measured by the pilot (ADR-0093 item 2). A new pair is an edit of the manifest and of the delivery
  of the weights (V/09), not an operator field. The weights lie in the package; the holder does not go outside.
- Empty `labels` would mean «any server», and for a model of twelve gigabytes that is a mistake. Therefore the schema requires at least
  one label: an empty list — 400 at the door ([the row check contract](../../../Platform/common/contracts/row-check.md)).
- **Rights.** The model row is created, edited and deleted by `admin` (the default rule of the units door;
  [the gate and pass contract](../../../Platform/common/contracts/gate-and-pass.md)). **Talking to the model** is
  the right `view` on the model row: by it the console issues the door token (P/06.5 Н3, chapter 2 Н1.1). The holder's door has no
  manifest key: `rights.routes` is about rows, tables and `door.pass` of the console, not about a route with a token (ADR-0093 addendum (2)
  item 4). The grant on the model is exactly «who may use the assistant». This grant does not allow writing anything: the model only answers. The model door is open to any client with
  `view`, not only `backend`; but a step belongs to its owner (chapter 2 Н1.1), and the worker has no rights.

The row check, `fixed` and the defaults — [the row check contract](../../../Platform/common/contracts/row-check.md).

### Н1.2 Placement: one model per server

`placement: {capacity: {from: capacity, default: 1}, constraint: labels-subset, tie_break: most-free-capacity}`, without
`grows`, without `unit_mb` ([P/04](../../../Platform/04-controller/spec/04-controller.norms.md) Н1.3).

- **Where.** The labels of the model row ⊆ the labels of the holder's server. The operator puts a label on a server that has memory for the model
  and its window (the numbers — the deployment lesson V/09, by the measurements of the harness handover package, ADR-0093 item 8), and names it in
  `labels` of the model row. The label is the operator's promise about memory; the worker's memory rule (P/03.4 Н1.2 `memory`) does not
  count the model: `unit_mb` is not set.
- **Why without `unit_mb`.** The base worker `m-<SERVER>-1` is installed on every server where the subsystem is installed
  ([P/02.4](../../../Platform/02-installer/spec/02.4-installer.norms.md) Н1.1), and `CAPACITY > 0` (Н1.5). With the model's budget
  in `unit_mb` the base worker would not start on a server without such memory. Without `unit_mb` it stands everywhere as a light one, and the model
  comes up only at the holder of the row (Н1.3).
- **One model per server.** The worker's capacity is 1 (the heartbeat `capacity`, Н1.4), and the controller does not order a second worker per server
  (there is no `grows`). `CAPACITY` of the role file `assistworker` (P/02.4 Н1.5) is exactly 1: not set — 1, the manifest default;
  set and not equal to 1 — the worker does not start, exit code 2, the log line `CAPACITY must be 1 for assist` (V/09 puts `CAPACITY=1`). So a server holds no more than one model row. Two rows with one label — one
  is held, the second is not placed (`unplaced`) until another server with the same label is found. Each model server gets
  its own label (`assist-<сервер>`), if the operator wants to know which model is where.
- **Not placed.** A row that nobody holds is not deleted by the controller (there is no `unplaced.delete_after`): it was created by the
  operator, and it waits for a server with the label.
- **Snapshot** — `[labels]` (P/04 Н1.3а).

### Н1.3 Model process

The model server is a **child process of the holder**, not a part of the subsystem: a part (`parts`) is a service on every server of the
installation (P/02.4 Н1.1), while the model lives only at the holder of the row (ADR-0093 addendum (1) item 3).

**The subsystem file** `/etc/assist/assist.env` is read by the holder by the environment file contract (no file — the defaults; it is not
readable or a value is not by the grammar — a start refusal, code 2; the port `CHAT_PORT` is taken — the same):

| Key | Read by | Grammar | Default | Norm |
|---|---|---|---|---|
| `MODEL_COMMAND` | holder | `execLine` (the first word is an absolute path) | `/usr/lib/assist/model-server` | «Command» below |
| `CHAT_PORT` | holder | an integer 0…65535 | an OS port (`0` — the same) | [chapter 2](10.2-assist.norms.md) Н1.1 |

**Command.** `MODEL_COMMAND` of the subsystem file `/etc/assist/assist.env` ([the environment file contract](../../../Platform/common/contracts/env-file.md));
not set — `/usr/lib/assist/model-server` from the package (V/09). The command is an `execLine` string (the first word is an absolute path,
without a shell). The holder starts it with the environment:

```yaml
ASSIST_MODEL_SOCKET:   the path of a unix socket in the worker's directory; the directory — mode 0700, the owner — the worker's user
ASSIST_MODEL_WEIGHTS:  the path of the weights file of the pair (model, quant) in the package (V/09)
ASSIST_MODEL_CONTEXT:  context of the row
ASSIST_MODEL_NAME:     model of the row
```

**The model process protocol** is HTTP/1.1 on this socket, and only on it: the model process has no TCP port.

```yaml
health:  GET /health → 200 — the model is loaded, including while it computes a step; 503 — loading or (at a server with one
         slot) busy with a step; anything else or no answer — not ready
step:    POST /v1/chat/completions, the body — the OpenAI chat form without streaming output: {messages, tools?, tool_choice?,
         reasoning_effort?, max_tokens?} → 200 {choices: [{message, finish_reason}], usage: {prompt_tokens,
         completion_tokens}}; message — {role: assistant, content?, tool_calls?, reasoning_content?}
         not 200 — the step failed (chapter 2 Н1.3); the holder breaking the connection — a cancellation of the step: the model process stops
         computing it; cache fields beyond the form are named by the implementation (chapter 2 Н1.4), the stub does not read them
one:     the holder sends the model process one step at a time (the queue — chapter 2 Н1.4)
```

The answer to `/health` is awaited for no longer than the polling period (1 s in `loading`, 10 s in `running`); if it has not come — there is no answer.

**The life of the process:**

| Holder state | Event | Action | Phase (Н1.4) |
|---|---|---|---|
| took the row, `enabled` | — | start the command; `GET /health` once per 1 s | `loading` |
| took the row, not `enabled` | — | do not start the process | `stopped`, `disabled` |
| `loading` | `/health` 200 | steps are accepted (chapter 2) | `running` |
| `loading` | no 200 within `LOAD_WITHIN` = 300 s from the start of the command, the command did not start or the process exited | shut down the process; do not start until an edit of the row or a restart of the worker | `failed`, `model did not load` |
| `running` | the process exited; or **outside a step** `/health` not 200 three times in a row (once per 10 s) | the running step — `failed` `model failed`, the queue — `failed` `model restarted` (chapter 2); shut down, start again after 5 s | `loading`, `reason` — `model restarted` |
| any | the third failure of a `running` row within a sliding 10 minutes | do not perform the third start; do not start until an edit of the row or a restart of the worker | `failed`, `model keeps failing` |
| any except `stopped` | an edit of the row (growth of `revision`), except `enabled` | steps — `failed` `model restarted`; shut down, start with the new ones | `loading` |
| any | `enabled` became `false` | steps — `cancelled`; shut down | `stopped`, `disabled` |
| `stopped` | `enabled` became `true` | start with the current ones | `loading` |
| any | released the row, the holding is lost (`fenced`), the end of the lease, a stop of the worker | steps are forgotten; **shut down before giving up the slot** | the row is not in the heartbeat |

- **An edit of the row** is any growth of `revision`: the platform calls `stop_unit` and `start_unit` under the same epoch (P/03.3 Н3 step 2).
  The holder tells a restart by `revision` from a release by the question `restarting(id)` from `stop_unit` (P/03.1 Н2); the outcome of the steps is decided by the row
  that `start_unit` brings. An edit while `stopped` is only remembered. An edit of the row and a new taking reset the failure count.
- **Health during a step.** While the model process computes a step, the holder does not count a `/health` refusal: 200 and 503 mean alive
  (at a server with one slot a busy slot answers 503). The count of three refusals runs only outside a step; the life of a step is guarded by
  `STEP_MAX` (chapter 2 Н1.3), an exit of the process is always a refusal.
- **Shut down** — `SIGTERM`, wait for the exit up to `STOP_WITHIN` = 10 s, then `SIGKILL`. The holder gives up the slot and writes the heartbeat without
  the row only after the model process has exited. Otherwise, when the row moves to the same server, there would be two
  models in memory.
- **A failure of the holder.** The model process does not outlive it: it is in the process group of the worker's unit (P/02.4 Н1.1), and
  a stop of the unit shuts it down together with the worker. How the process learns of the parent's death without a unit (a stand) is named by the
  implementation (the section «Implementation decides»).
- **The process output.** stdout and stderr of the model process go to the worker's log line by line, through the log mask
  ([the log mask contract](../../../Platform/common/contracts/log-mask.md)). The model process is started in a mode in which
  it does not print the texts of steps; the package command sets this mode.
- **Memory.** The holder's budget is its process tree (the worker and the model process), measured as the PSS of the tree. The numbers — V/09 by the
  measurements of the handover package; lesson V/10 does not write them.

### Н1.4 Heartbeat and series

The worker's heartbeat `assist/heartbeats/<воркер>` (P/03.4 Н1.1) beyond the platform fields:

- top: `capacity` — 1 (Н1.2); `steps` — `{done, failed, cancelled, abandoned}`, cumulative since the start of the worker: `done`,
  `failed` — by the `state` of the step; `cancelled` — a cancellation by the owner and `disabled`; `abandoned` — `reason` `abandoned`
  (Kimi's addition to the analysis of the review of V/10, С3; chapter 2 Н1.3); `step_seconds` — the model's seconds over steps, cumulative: all the model's time, including that of broken-off steps;
- the element `status[]` of the model row (the epoch is always taken; `why` is a platform field, the subsystem's words are `reason`):
  - `phase` — `loading` | `running` | `failed` | `stopped`; `reason` — the words of the table of Н1.3 or empty;
  - `queued`, `active` — steps in the queue and in work (chapter 2 Н1.4).

The series of the manifest: `assist_models_running` (the phase `running`, `console.running`), `assist_steps_total{outcome}`,
`assist_step_seconds_total`. There are no texts of steps, names of people or their requests either in the heartbeat or in the series.

## Н3 Pass

```
take the row → enabled? no — stopped; yes — start the model process (loading) → /health 200 → running → steps (chapter 2)
an edit of the row, except enabled → steps failed → shut down → start (loading)
enabled false → steps cancelled → shut down (stopped); enabled true → start (loading)
release, fenced, the end of the lease, a stop → steps forgotten → shut down → wait for the exit → give up the slot, the heartbeat without the row
```

**Races.** The row is released while the model process is still loading — it is shut down the same way, the loading is interrupted. The row has returned
to the same server while the former process is shutting down — the new one is started only after the former one has exited (the slot is given up after
the exit, Н1.3). Two rows with one label — one holds (capacity 1), without a race for memory.

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| `labels` are empty or absent | 400 at the units door | operator | name the label of the model server |
| `model`, `quant` not from the list; `context` outside the bounds | 400 at the units door | operator | — |
| no server with the labels of the row | the row is not placed, there is no heartbeat | console (`unplaced`) | put a label on a server with memory |
| the model process did not load within 300 s | `failed`, `model did not load` | heartbeat, the worker's log | check the memory and the weights; edit the row |
| the model process keeps falling | `loading`, `model restarted`; the third time within 10 minutes — `failed`, `model keeps failing` | heartbeat | the same |
| `enabled: false` | `stopped`, `disabled` | heartbeat | — |
| `CAPACITY` of the role is not 1 | the worker does not start, code 2, a log line | the unit's log | `CAPACITY=1` in `roles/assistworker.env` |

## Implementation decides

The implementation MUST name in its description:
- **the package command `/usr/lib/assist/model-server`**: which model server, how it listens on the unix socket, how it does not print
  the texts of steps, how a cancellation (a broken connection) reaches the model;
- **the path of the weights of the pair in the package**; the holder does not check the file: no weights — `model did not load` from the model server;
- **how the model server reports an overflow of the window** and how the holder tells it from any other non-200; not told apart — `model failed`;
- **how the model process shuts down with the death of the holder** outside a unit (a stand);
- the command to start the worker for «Стенд».
