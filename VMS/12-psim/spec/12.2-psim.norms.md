# V/12.2 — The generator: norms

This English text is the source; the Russian translation `ru/spec/12.2-psim.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 2 of lesson V/12 psim plugins (ADR-0071; ADR-0115 addendum (5) item 1, addendum (6) item 1, addendum (7) item 1, addendum (10) item 1).
Lecture (`ru/12-psim.md`, for people, not in the export), [instructions](12-psim.README.md). The platform is the export `cammeta-specs` `7a875c75`.

The generator is a pure function: from the plugin directory and the list of installed plugins it builds the subsystem manifest by
the layout of chapter 1 and the fragment `calls` for the manifest of `backend`. It installs nothing itself: it is called by the install step
(chapter 4), and only there does the result get into the store. The chapter sets norms for the input, the check, the output and the refusals.

Norm ids are `V/12.2-MM`.

## N0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../Platform/common/NORMATIVE-TERMS.md). The words of the lesson are chapter 1 N0.

- **Plugin directory** — the executable `process_name` (default `plugin`), with `plugin.json` and `langs/*.json` next to it
  (this is how the plugin itself looks for them: the reading of the manifest and translations in psim-sdk).
- **Installed list** — for each installed plugin, its `type`, the `source` types of its parameters, and `enabled` and `owners` of
  the row `plugin`: `{plugin_id → {types, sources, enabled, owners}}`; it is given by the assembler (chapter 4 N1.3). By the `sources` of foreign plugins the generator
  creates the ring `<t>_events` of its own kind (chapter 1 N1.2; addendum (14)).

## N1 Form

**Data.** The chapter has no families of its own. The input and the output are files; the vectors are [`vectors/generate`](../vectors/generate/README.md).

### N1.1 Input and check

- **Input:** `plugin.json`, all `langs/<language>.json`, the installed list. There are no other inputs: the time, the environment, the
  machine name do not affect the output. The same input — the same output.
- **The psim schema.** `plugin.json` is checked against `schema/plugin.schema.json` of psim-sdk `c3d9ebb` (JSON Schema draft-07, extra
  keys are forbidden). If it does not pass — the refusal `plugin.json is not a psim manifest: <path>: <keyword>`. A plugin with another
  schema is a new pin of psim-sdk, not an edit of the generator.
- **Translations.** Each `langs/<language>.json` is an object key → value. Non-string values are discarded, as by the psim host
  (psim-sdk); a file that is not a JSON object — a refusal.
- **Layout** — by chapter 1; its refusals — chapter 1 N4.

### N1.2 Output

1. **The subsystem manifest** `psim-<id>.subsystem.yaml` by chapter 1. The strict loader of P/02.1 loads it without edits: a loader
   refusal on the generator output is a generator error, not a plugin error.
2. **The fragment `calls`** for the manifest of `backend` (addendum (5) item 1, addendum (7) item 1) — the list of callback doors of P/06.3 N1.9:

   ```yaml
   plugin:   psim-<id>
   enabled:  [psim-<id>/units, GET psim-<id>/where, GET manifest/psim-<id>/source]   # the instance kind, the page, the kind description — always
   objects:  [psim-<id>/<t>…, GET psim-<id>/<t>_seen…, psim-<id>/requests]  # the object kinds — only of an enabled plugin
   ```

   `psim-<id>/units` — reading and writing the plugin parameters `/units` by ticket (addendum (7) item 1); `GET psim-<id>/where` — the address and
   the token of the page door (chapter 3 N1.6); `GET manifest/psim-<id>/source` — the full form of the manifest for the kind description (V/11.14 N1.1); `<t>` — objects, `<t>_seen` — read only, `requests` — commands. The division into
   `enabled` and `objects` is for disabling: the assembler takes `objects` only from a plugin with `enabled: true` (addendum (8) item 2).
3. **Owners of `source`** (addendum (10) item 1, addendum (16) item 3). A type from a `source` is resolved by `owners` of its own row, otherwise among the
   **enabled** plugins of the list: found in one — that one is the owner (chapter 1 N1.3, N1.6); in two or more without `owners` — the refusal
   `object type <T> has two owners: <a>, <b>`; `owners` names a plugin that does not have the type — a refusal; `owners` named by a disabled
   plugin is not judged, and `owners` naming a disabled plugin means «no owner» (ADR-0115 addendum (20) item 2; M2 of the norms review
   of the merge): a second enabled owner is not taken silently; in none — the field is without `ref`,
   `items.ref`, `ref_label` and without reads and requests to the owner. If the type appears later, the assembler rebuilds the manifest by the same
   pass (chapter 4 N1.3).

### N1.3 Refusal

A refusal is one line `psim: <plugin_id>: <reason>` and nothing is built: neither the manifest nor the fragment. The causes are N1.1, N1.2 item 3
and chapter 1 N4. The first refusal in the order of the layout (chapter 1 N3) is the only one.

## N3 Pass

```
input (N1.1) → psim schema → translations → layout (chapter 1) with the owners of source (N1.2 item 3)
  → subsystem manifest and fragment calls (N1.2) | refusal (N1.3)
```

**Races.** None: the generator is a function of the input.

---

## N4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| `plugin.json` outside the psim schema | refusal, the path and the keyword | the installing operator | — |
| a `langs/` file is not a JSON object | refusal, the file | operator | — |
| a layout refusal (chapter 1 N4) | refusal, the cause | operator | — |
| a `source` type in two installed plugins | refusal, the type and the owners | operator | remove one of the owners |
