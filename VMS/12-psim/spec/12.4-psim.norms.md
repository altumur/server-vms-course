# V/12.4 — Установка и сборщик манифеста `backend`: нормы

Канон главы 4 урока V/12 «Плагины psim» (ADR-0115 доп. (5) пп. 1, 4, доп. (6) п. 1, доп. (7) пп. 2–4, доп. (8), доп. (9),
доп. (10) пп. 1, 3; М ревью Claude доп. (8)). [Лекция](../12-psim.md), [инструкция](12-psim.README.md). Платформа — выгрузка
`cammeta-specs` `7a875c75`.

Новый плагин — это новая подсистема и новые двери для `backend`. Обратный вызов `backend` — закрытый перечень его манифеста
(V/11.1 Н1.3), поэтому установка плагина ставит две ревизии: манифест плагина и манифест `backend`, собранный заново из
канона и фрагментов всех плагинов. Глава нормирует шаг установки, начальные значения, включение и выключение, сборщик и
пересборку зависимых плагинов.

Id норм — `V/12.4-MM`; соответствие прежним урокам — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Слова урока — глава 1 Н0, глава 2 Н0.

- **Шаг установки** — команда урока `psim` под администратором кластера: `install <каталог> [--values <файл>]`, `enable <id>`,
  `disable <id>`, `sync`. Пишет она установщиком P/02.3 (`manifest put`) и дверью консоли (P/06.1).
- **Канон `backend`** — `VMS/11-backend/backend.subsystem.yaml` выгрузки VMS (V/11.1).

## Н1 Форма

**Данные.** Строки `platform/manifest/psim-*` (P/02.3 Н1.5), `platform/manifest/backend`, строки `psim-*/units/plugin`
(глава 1 Н1.1). Своих семей у шага нет: состояния между запусками он не держит.

### Н1.1 Каталог плагина на серверах

Каталог плагина (глава 2 Н0) лежит на каждом сервере кластера в `/usr/lib/psim-<id>/`, его ставит пакет плагина, как
пакет подсистемы (V/09). Адаптер — один исполняемый файл `/usr/lib/psim/adapter` пакета урока на все плагины, каталог — его
аргумент (глава 1 Н1.6). Пакет плагина несёт код, не манифест: манифест `psim-<id>` строит шаг установки (Н1.2), на прочие
серверы его файл кладёт обход — `w2cctl manifest get --sha256` в `rollout` (P/02.4 Н1.9; ADR-0115 доп. (21) п. 3). Сервер без каталога — адаптер на нём не поднимает плагин: `unfit` `plugin directory missing`, предел
(размещение каталога не знает).

### Н1.2 Установка

Новая подсистема приходит на работающий кластер только порядком платформы `add` (P/02.4 Н1.7; ADR-0115 доп. (21)–(23)):
права хранилища и каталог консоли берутся на старте процесса, поэтому по серверам — перезапуск члена хранилища и консоли.
Шаг установки этот обход не исполняет — его ведёт оператор установщиком по серверам; шаг стоит до и после него
(решение «Спецификации VMS»: шаг идёт с одной машины, а обход — на каждом сервере):

```
psim install <каталог> [--values <файл>] [--owner <T>=<plugin_id>…]:             до обхода (доп. (23) п. 3 (а))
  1. прочитать каталог: строки platform/manifest/psim-* и строки psim-*/units/plugin       → список установленных (глава 2 Н0)
  2. генератор (глава 2) по каталогу, списку и owners этого шага                         → отказ: ничего не записано
  3. начальные значения (Н1.4) — только проверка: строки plugin до обхода нет            → отказ: ничего не записано
  4. manifest put psim-<id> (P/02.3) и сборка (Н1.3) с новым плагином как включённым: зависимые, владельцы,
     backend — manifest put каждого изменённого (P/02.4 Н1.7 add шаг 0); ждать served = rev работающих — их консоль
     подхватывает по метке; served psim-<id> — только в finish (доп. (25) п. 4 (а))       → отказ установщика: стоп
  5. вывод — набор обхода: слова «<sub>=<sha256>» на каждый manifest put шага 4, по имени подсистемы — аргументы rollout; код 0

обход — оператор, P/02.4 Н1.7 add шаги 1, 2 по набору обхода (доп. (22)–(25)):
  w2cctl rollout <sub>=<sha256>… [-allow-downtime] [-last] (P/02.4 Н1.9) на каждом сервере по очереди, сервер лидера —
  последним с -last; код 0 — сервер сделан, иначе обход стоит; затем install без W2C_HOLD на каждом сервере — юниты
  psim-<id> включены (доп. (23) п. 3 (б), (г)). Сервер с дверью хранилища rollout судит по её режиму (доп. (25) п. 1).
  Файлы изменённых манифестов набора — backend, зависимых, владельцев — rollout заменяет на каждом сервере, и на машине
  шага: прежние из пакета там есть (manifest get, доп. (26))

psim finish <каталог> [--values <файл>] [--owner <T>=<plugin_id>…]:              после обхода (доп. (23) п. 3 (в), (д))
  1. генератор по каталогу, списку и owners → sha256 манифеста psim-<id> равен строке; иначе отказ
     «manifest changed since install (catalogue or --owner)», ничего не записано: install заново
  2. начальные значения (Н1.4) заново — значения и секрет между шагами не хранятся  → отказ: ничего не записано
  3. ждать served = rev строки у GET /manifest/<sub>/source каждой подсистемы набора, не дольше PSIM_MANIFEST_WAIT → отказ: стоп
  4. строка psim-<id>/units/plugin: нет — PUT с начальными значениями, enabled: true, version, owners;
     есть — PATCH с If-Match только новыми параметрами, version и owners, прочие поля не трогаются
  5. подъём backend (Н1.3 шаг 4) и сборка по ревизии строки plugin: те же байты — manifest put нет, второго обхода нет
```

- **Почему так** (доп. (23) п. 3). Сборка шага 4 уже считает плагин включённым, поэтому строка `plugin` с `enabled: true`
  в `finish` манифестов не меняет. Строку раньше обхода не записать: консоль не знает `psim-<id>` до своего перезапуска.
  Значения и секрет `finish` получает заново: шаг между вызовами ничего не хранит, секрет на диске не лежит.
- **Обход прерван** — кластер работает, юниты `psim-<id>` не включены, строки `plugin` нет: подсистема стоит выключенной.
  Повтор обхода — те же команды с тем же набором с первого сервера: на пройденном `rollout` находит барьер выполненным и
  выходит 0 без перезапусков (P/02.4 Н1.7 add `resume`; доп. (22) п. 4, (24) п. 1). `finish` до конца обхода — отказ шага 3 по сроку.
- **Пределы** (доп. (21) п. 2, (22) п. 2, (23) п. 4 (а)). Каждый сервер на время обхода теряет консоль, его воркеры дольше
  `LOST_AFTER` переразмещаются; на ещё не пройденных серверах зависимые, владельцы и `backend` живут со старыми правами и
  кольцом — переходные отказы новых чтений; `backend` с `calls` нового плагина раньше, чем консоли ему служат, — переходные
  `404` и `401` (доп. (25) п. 4 (б)). Кластер из одного члена — обход только с согласием оператора на простой: `rollout -allow-downtime` (P/02.4; доп. (23) п. 1,
  (24) п. 2).
- Обновление плагина — тот же `install` нового каталога, обход и `finish`: строка `plugin` остаётся, её значения не трогаются
  (шаг 4 — `PATCH` только новыми полями, М1 ревью норм); новые параметры без `default` спрашиваются по Н1.4.
- **Ожидание ревизии** (доп. (16) п. 3, (21) п. 2). Источник — поле `served` ответа `GET /manifest/<sub>/source` (P/06.5; ADR-0116
  доп. (6), ADR-0115 доп. (20) п. 1). После обхода консоль уже перезапущена, `served` приходит сразу; `PSIM_MANIFEST_WAIT` =
  120 с — запас на перезапуск консоли машины шага (решение «Спецификации VMS»).
- **`--owner <T>=<id>`** — выбор владельца типа, когда включённых владельцев двое: пишется в `owners` строки зависимого
  (шаг 4 `finish`) и действует во всех следующих сборках (доп. (16) п. 3). `finish` с иными `--owner`, чем у `install`, —
  отказ шага 1 (ADR-0115 доп. (27) п. 4 (г)): шаг между вызовами ничего не хранит, поэтому иной выбор он видит по байтам —
  owners решают, чьи таблицы читает манифест `psim-<id>` (глава 2 Н1.2 п. 3), и его `sha256` расходится со строкой.
  `--owner`, называющий единственного включённого владельца типа, выбора не меняет и байтов тоже: иным он не считается,
  в `owners` пишется то, что дал `finish` (решение «Спецификации VMS»).
- **Снятия нет** (доп. (7) п. 4): плагин выключают (Н1.5). Таблицы объектов и `<т>_seen` остаются, повторное включение видит
  прежние объекты; полного удаления нет, предел.

### Н1.3 Сборка

```
сборка:
  1. прочитать каталог и строки plugin (как Н1.2 шаг 1), запомнить их ревизии
  2. генератор по каждому установленному плагину и новому списку; манифест изменился → manifest put, в набор обхода
     (зависимые: доп. (10) п. 1)
  3. манифест backend = канон ∪ фрагменты (глава 2 Н1.2 п. 2) всех плагинов по имени подсистемы:
       часть enabled — у каждого; часть objects — у плагина со строкой enabled: true
  4. изменился против platform/manifest/backend → manifest put, в набор обхода; ждать served = новой rev у
     GET /manifest/backend/source (консоль подхватывает backend по метке, доп. (25) п. 4 (а)), затем подъёма самого backend: пульс каждого экземпляра
     backend/instances с новым instance позже put или ETag /kinds с новой rev — что раньше; всё не дольше PSIM_MANIFEST_WAIT;
     шаг кончается только после этого (М2 ревью норм слияния: у backend свой перезапуск по метке);
     строк backend/instances нет — подъёма ждать не у кого: шаг кончается после served (стенд приёмки 4 — так)
  5. прочитать каталог и строки plugin снова: ревизии не те, что в шаге 1 → повторить с шага 1
```

- **Источник фрагментов** — строки каталога, не файлы генератора (доп. (7) п. 3): фрагмент каждого плагина строится заново из
  его строки `platform/manifest/psim-<id>`. Вторая установка первую не затирает, обновление VMS плагинов не отрезает
  (доп. (6) п. 1).
- **Обновление VMS** — новый канон `backend` и `psim sync`: та же сборка. **Сборка с изменением** — набор обхода: `psim sync` выводит
  его, оператор проходит обход (Н1.2). Член перезапускается, только если файл прав обхода не равен загруженному: `rollout`
  сверяет `/v1/rights` сам, равно — перезапусков нет (доп. (25) п. 3); так кончается сборка без новых префиксов прав.
- **Каталог при пересборке** (М2 ревью норм). Генератор шага 2 берёт каталог плагина машины шага `/usr/lib/psim-<id>/`; его
  `metadata.plugin_version` не равен `version` строки `plugin` — отказ сборки `plugin <id> here is <v>, installed <w>`,
  ничего не записано: сначала обновить пакет плагина на машине шага.
- **Владельцы `source`.** Установлен владелец типа — зависимый плагин получает чтение и просьбы шагом 2 той же сборки.
  Установлен зависимый — владелец получает кольцо `<т>_events` у типа, на который тот ссылается, тем же шагом 2 (доп. (14));
  список установленных несёт и такие ссылки (глава 2 Н0).
  Два включённых владельца одного типа без `owners` — отказ шага 2 (глава 2 Н1.2 п. 3), ничего не записано; выбор — выключить
  одного или `install --owner`.
- **Пределы.** Каждая сборка с изменением — перезапуск `backend` (доп. (7) п. 3). Новый зависимый даёт владельцу кольцо
  `<т>_events` — новую ревизию манифеста владельца, его адаптер и процесс плагина перезапускаются (М3 ревью норм). Две сборки одновременно сходятся шагом 5.
  `enabled`, записанное дверью администратора мимо шага, адаптер слушается сразу (глава 3 Н1.1), а `calls` `backend` оно
  меняет только при следующем шаге установки или пересборке: сборка видит его по ревизии строки `plugin` в шагах 1 и 5
  (доп. (10) п. 3, доп. (14)), предел.

### Н1.4 Начальные значения

- **Что спрашивается** — параметр плагина без `default`, не `readonly`, у которого пустая форма типа (`""`, `0`, `false`, `[]`;
  договор проверки строки «Подготовка полей», шаг 4) не проходит `schema` или `enum` поля (М2 ревью доп. (8); доп. (9)). Иные
  параметры без `default` строка получает пустой формой. `readonly` не спрашиваются: их задаёт плагин (доп. (9)).
- **Откуда** — `--values <файл>` (JSON-объект имя psim → значение) или ввод оператора. Значение `*_secret` — только ввод: оно
  проходит один раз дверью консоли; секрет в файле — отказ шага с именем поля (М3 ревью доп. (8)).
- **Отказ** — нужное значение не дано или не проходит схему поля: отказ с именами полей, ничего не записано (доп. (8) п. 1).
  Черновика строки нет.

### Н1.5 Включение и выключение

- `psim disable <id>` — `enabled: false` строки `plugin` (`PUT` с `If-Match`), затем сборка и набор обхода, обход (Н1.3). Включение
  и выключение меняет у `backend` только `door.pass.calls`, не файл прав: обход обычно кончается без перезапусков (доп. (25)
  п. 3, заменил (23) п. 5). Часть `objects` уходит из
  `calls`, `/kinds` вид объектов не показывает, вид экземпляра остаётся — плагин виден выключенным (доп. (8) п. 2). Адаптер
  останавливает процесс (глава 3 Н1.1); единица держится, адаптер поднят.
- `psim enable <id>` — `enabled: true`, сборка, обход; виды объектов снова видны.
- **`enabled` в форме** — только для чтения: `PATCH /units` с ним — 400 (М1 ревью доп. (8)); норма V/11 — веткой V/11 при закреплении
  контракта этапа 1 (V/11.14 Н1.3), до неё — нет. Запись мимо шага — Н1.3
  «Пределы».

## Н3 Проход

```
install: каталог → список → генератор → начальные значения → manifest put плагина → строка plugin → сборка
enable/disable: строка plugin → сборка
sync: сборка
сборка: каталог и строки → зависимые манифесты → backend = канон ∪ фрагменты → manifest put → перечитать, сошлось?
```

**Гонки.** Две сборки одновременно — каждая перечитывает каталог после своей записи (Н1.3 шаг 5): последняя видит обе
установки. Правка `enabled` во время сборки — тот же шаг 5.

## Н4 Отказы

| Причина | Исход | Кто и как видит | Что делает вызывающий |
|---|---|---|---|
| отказ генератора | ничего не записано, строка генератора | оператор | — |
| нужного начального значения нет или оно не по схеме | ничего не записано, имена полей | оператор | дать значение |
| `*_secret` в файле значений | ничего не записано, имя поля | оператор | ввести вручную |
| тип `source` у двух включённых плагинов без `owners` | ничего не записано | оператор | выключить одного или `--owner` |
| консоль не отдала новую ревизию за `PSIM_MANIFEST_WAIT` | стоп; манифест записан, строки нет | оператор | `psim sync` |
| версия каталога машины шага не равна `version` строки | ничего не записано | оператор | обновить пакет плагина |
| `finish`: манифест `psim-<id>` по каталогу и `--owner` не равен строке — иной каталог или иной выбор владельца, чем у `install` | ничего не записано | оператор | `install` заново |
| отказ установщика `manifest put` | стоп на этом шаге; прежние шаги записаны | оператор, код 2 | `psim sync` после исправления |
| нет каталога плагина на сервере | `unfit` `plugin directory missing` | форма, фаза | поставить пакет плагина |

## Н5 Приёмка

[Приёмка 4](../acceptance/4/README.md): установить `camera`, затем `security_controller` на работающем стенде; через `/units` по
билету прочитать, создать, изменить объект, выполнить команду, прочитать и изменить параметр плагина, открыть страницу
(доп. (5) п. 1, доп. (7) п. 1); выключить `camera` и увидеть его выключенным; включить; `psim sync` после нового канона
`backend` — плагины не отрезаны (доп. (6) п. 1, доп. (8) п. 2); обратный порядок установки — `security_controller` получает
чтение `psim-camera` сборкой.

## Соответствие прежним урокам

Прежних шагов у главы нет. Строки `id-map.tsv` — `ADR-0115` → `V/12.4-01` … `V/12.4-05`.
