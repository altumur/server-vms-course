# V/12.4 — Installation and the `backend` manifest assembler: norms

This English text is the source; the Russian translation `ru/spec/12.4-psim.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 4 of lesson V/12 «Плагины psim» (ADR-0115 addendum (5) items 1, 4, addendum (6) item 1, addendum (7) items 2–4,
addendum (8), addendum (9), addendum (10) items 1, 3; «М» of the Claude review of addendum (8)). Lecture (`ru/12-psim.md`, for people, not in the export),
[instructions](12-psim.README.md). The platform is the export `cammeta-specs` `7a875c75`.

A new plugin is a new subsystem and new doors for `backend`. The callback of `backend` is a closed listing of its manifest
(V/11.1 Н1.3), therefore installing a plugin puts two revisions: the plugin's manifest and the `backend` manifest, assembled anew
from the canon and the fragments of all plugins. The chapter norms the install step, the initial values, enabling and disabling,
the assembler and the reassembly of dependent plugins.

Norm ids are `V/12.4-MM`; the map to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md).
The words of the lesson — chapter 1 Н0, chapter 2 Н0.

- **Install step** — the lesson's command `psim` run as the cluster administrator: `install <каталог> [--values <файл>]`, `enable <id>`,
  `disable <id>`, `sync`. It writes through the installer of P/02.3 (`manifest put`) and through the console door (P/06.1).
- **The `backend` canon** — `VMS/11-backend/backend.subsystem.yaml` of the VMS export (V/11.1).

## Н1 Form

**Data.** The rows `platform/manifest/psim-*` (P/02.3 Н1.5), `platform/manifest/backend`, the rows `psim-*/units/plugin`
(chapter 1 Н1.1). The step has no families of its own: it keeps no state between runs.

### Н1.1 The plugin directory on the servers

The plugin directory (chapter 2 Н0) lies on every server of the cluster in `/usr/lib/psim-<id>/`; it is installed by the plugin's
package, like the package of a subsystem (V/09). The adapter is one executable file `/usr/lib/psim/adapter` of the lesson's package
for all plugins; the directory is its argument (chapter 1 Н1.6). The plugin's package carries code, not a manifest: the manifest
`psim-<id>` is built by the install step (Н1.2); on the other servers its file is put in place by the traversal —
`w2cctl manifest get --sha256` in `rollout` (P/02.4 Н1.9; ADR-0115 addendum (21) item 3). On a server without the directory the adapter
does not bring the plugin up: `unfit` `plugin directory missing`, a limit (placement does not know the directory).

### Н1.2 Installation

A new subsystem comes to a running cluster only by the platform procedure `add` (P/02.4 Н1.7; ADR-0115 addenda (21)–(23)):
the store rights and the console catalogue are taken at process start, therefore, server by server, the store member and the console
are restarted. The install step does not execute this traversal — the operator conducts it with the installer server by server; the
step stands before and after it (a decision of «Спецификация VMS»: the step runs from one machine, while the traversal runs on every
server):

```
psim install <каталог> [--values <файл>] [--owner <T>=<plugin_id>…]:             before the traversal (addendum (23) item 3 (a))
  1. read the catalogue: the rows platform/manifest/psim-* and the rows psim-*/units/plugin  → the list of installed ones (chapter 2 Н0)
  2. the generator (chapter 2) by the directory, the list and the owners of this step       → refusal: nothing written
  3. initial values (Н1.4) — a check only: there is no plugin row before the traversal        → refusal: nothing written
  4. manifest put psim-<id> (P/02.3) and the assembly (Н1.3) with the new plugin counted as enabled: the dependent ones, the owners,
     backend — manifest put of each changed one (P/02.4 Н1.7 add step 0); wait for served = rev of the running ones — the console
     picks them up by label; served of psim-<id> — only in finish (addendum (25) item 4 (a))      → installer refusal: stop
  5. output — the traversal set: the words «<sub>=<sha256>», one per manifest put of step 4, by subsystem name — the arguments of rollout; code 0

traversal — the operator, P/02.4 Н1.7 add steps 1, 2 by the traversal set (addenda (22)–(25)):
  w2cctl rollout <sub>=<sha256>… [-allow-downtime] [-last] (P/02.4 Н1.9) on every server in turn, the leader's server —
  last, with -last; code 0 — the server is done, otherwise the traversal stands; then install without W2C_HOLD on every server — the units
  psim-<id> are enabled (addendum (23) item 3 (b), (d)). On a server with the store door, rollout judges by the door's mode (addendum (25) item 1).
  The files of the changed manifests of the set — backend, the dependent ones, the owners — rollout replaces on every server, including the
  step's machine: the former ones from the package are there (manifest get, addendum (26))

psim finish <каталог> [--values <файл>] [--owner <T>=<plugin_id>…]:              after the traversal (addendum (23) item 3 (c), (e))
  1. the generator by the directory, the list and the owners → sha256 of the manifest psim-<id> equals the row's; otherwise the refusal
     «manifest changed since install (catalogue or --owner)», nothing written: install again
  2. initial values (Н1.4) anew — the values and the secret are not stored between the steps  → refusal: nothing written
  3. wait for served = rev of the row at GET /manifest/<sub>/source of each subsystem of the set, no longer than PSIM_MANIFEST_WAIT → refusal: stop
  4. the row psim-<id>/units/plugin: absent — PUT with the initial values, enabled: true, version, owners;
     present — PATCH with If-Match with only the new parameters, version and owners; the other fields are not touched
  5. backend coming up (Н1.3 step 4) and the assembly by the revision of the plugin row: the same bytes — no manifest put, no second traversal
```

- **Why so** (addendum (23) item 3). The assembly of step 4 already counts the plugin as enabled, therefore the row `plugin` with
  `enabled: true` in `finish` does not change the manifests. The row cannot be written before the traversal: the console does not know
  `psim-<id>` until its restart. `finish` obtains the values and the secret anew: the step keeps nothing between calls, the secret does
  not lie on disk.
- **Traversal interrupted** — the cluster works, the units `psim-<id>` are not enabled, there is no row `plugin`: the subsystem stands
  disabled. Repeating the traversal means the same commands with the same set from the first server: on a server already passed,
  `rollout` finds the barrier done and exits 0 without restarts (P/02.4 Н1.7 add `resume`; addendum (22) item 4, (24) item 1).
  `finish` before the end of the traversal — the refusal of step 3 on timeout.
- **Limits** (addendum (21) item 2, (22) item 2, (23) item 4 (a)). Every server loses its console for the time of the traversal; its
  workers are re-placed after longer than `LOST_AFTER`; on servers not yet passed, the dependent ones, the owners and `backend` live with
  the old rights and ring — transient refusals of new reads; `backend` with the `calls` of the new plugin before the consoles serve it —
  transient `404` and `401` (addendum (25) item 4 (b)). A cluster of one member — the traversal only with the operator's consent to
  downtime: `rollout -allow-downtime` (P/02.4; addendum (23) item 1, (24) item 2).
- Updating a plugin is the same `install` of the new directory, the traversal and `finish`: the row `plugin` remains, its values are not
  touched (step 4 — `PATCH` with only the new fields, М1 of the norms review); new parameters without `default` are asked for by Н1.4.
- **Waiting for the revision** (addendum (16) item 3, (21) item 2). The source is the field `served` of the response
  `GET /manifest/<sub>/source` (P/06.5; ADR-0116 addendum (6), ADR-0115 addendum (20) item 1). After the traversal the console has
  already been restarted, `served` comes at once; `PSIM_MANIFEST_WAIT` = 120 s — a margin for the restart of the console of the step's
  machine (a decision of «Спецификация VMS»).
- **`--owner <T>=<id>`** — the choice of the owner of a type when there are two enabled owners: it is written into `owners` of the
  dependent's row (step 4 of `finish`) and acts in all subsequent assemblies (addendum (16) item 3). `finish` with a `--owner` other than
  that of `install` — the refusal of step 1 (ADR-0115 addendum (27) item 4 (d)): the step keeps nothing between calls, therefore it sees
  a different choice by the bytes — the owners decide whose tables the manifest `psim-<id>` reads (chapter 2 Н1.2 item 3), and its
  `sha256` diverges from the row. A `--owner` that names the only enabled owner of a type changes neither the choice nor the bytes: it
  is not counted as different; into `owners` is written what `finish` was given (a decision of «Спецификация VMS»).
- **There is no removal** (addendum (7) item 4): a plugin is disabled instead (Н1.5). The object tables and `<т>_seen` remain; enabling
  again sees the former objects; there is no full deletion, a limit.

### Н1.3 Assembly

```
assembly:
  1. read the catalogue and the plugin rows (as Н1.2 step 1), remember their revisions
  2. the generator for each installed plugin and the new list; the manifest changed → manifest put, into the traversal set
     (the dependent ones: addendum (10) item 1)
  3. the manifest backend = canon ∪ fragments (chapter 2 Н1.2 item 2) of all plugins by subsystem name:
       the part enabled — of every plugin; the part objects — of a plugin whose row has enabled: true
  4. changed against platform/manifest/backend → manifest put, into the traversal set; wait for served = the new rev at
     GET /manifest/backend/source (the console picks up backend by label, addendum (25) item 4 (a)), then for backend itself to come up: the heartbeat of every instance
     in backend/instances with a new instance later than the put, or the ETag of /kinds with the new rev — whichever is earlier; all of it no longer than PSIM_MANIFEST_WAIT;
     the step ends only after this (М2 of the merge norms review: backend has its own restart by label);
     there are no rows backend/instances — there is nobody to wait for to come up: the step ends after served (the stand of acceptance 4 is so)
  5. read the catalogue and the plugin rows again: the revisions are not those of step 1 → repeat from step 1
```

- **Source of the fragments** — the catalogue rows, not the generator's files (addendum (7) item 3): the fragment of each plugin is
  built anew from its row `platform/manifest/psim-<id>`. A second installation does not overwrite the first, an update of VMS does
  not cut the plugins off (addendum (6) item 1).
- **VMS update** — a new `backend` canon and `psim sync`: the same assembly. **An assembly with a change** gives a traversal set:
  `psim sync` outputs it, the operator goes through the traversal (Н1.2). A member is restarted only if the rights file of the
  traversal is not equal to the loaded one: `rollout` compares `/v1/rights` itself, equal — no restarts (addendum (25) item 3); this is
  how an assembly without new rights prefixes ends.
- **The directory at reassembly** (М2 of the norms review). The generator of step 2 takes the plugin directory of the step's machine
  `/usr/lib/psim-<id>/`; its `metadata.plugin_version` is not equal to `version` of the row `plugin` — the assembly refusal
  `plugin <id> here is <v>, installed <w>`, nothing written: first update the plugin's package on the step's machine.
- **Owners of `source`.** The owner of a type is installed — the dependent plugin gets reading and requests by step 2 of the same
  assembly. A dependent is installed — the owner gets the ring `<т>_events` for the type the dependent refers to, by the same step 2
  (addendum (14)); the list of installed ones carries such references too (chapter 2 Н0).
  Two enabled owners of one type without `owners` — the refusal of step 2 (chapter 2 Н1.2 item 3), nothing written; the choice is to
  disable one of them or `install --owner`.
- **Limits.** Every assembly with a change is a restart of `backend` (addendum (7) item 3). A new dependent gives the owner the ring
  `<т>_events` — a new revision of the owner's manifest; its adapter and the plugin process are restarted (М3 of the norms review). Two
  simultaneous assemblies converge by step 5. `enabled` written by the administrator door bypassing the step is obeyed by the adapter at
  once (chapter 3 Н1.1), but it changes the `calls` of `backend` only at the next install step or reassembly: the assembly sees it by
  the revision of the row `plugin` in steps 1 and 5 (addendum (10) item 3, addendum (14)), a limit.

### Н1.4 Initial values

- **What is asked for** — a plugin parameter without `default`, not `readonly`, whose empty form of the type (`""`, `0`, `false`, `[]`;
  the row check contract «Подготовка полей», step 4) does not pass the `schema` or `enum` of the field (М2 of the review of addendum (8);
  addendum (9)). The other parameters without `default` the row gets with the empty form. `readonly` ones are not asked for: the plugin
  sets them (addendum (9)).
- **From where** — `--values <файл>` (a JSON object psim name → value) or operator input. A value of `*_secret` — input only: it passes
  once through the console door; a secret in the file — a refusal of the step with the field name (М3 of the review of addendum (8)).
- **Refusal** — a needed value is not given or does not pass the field schema: a refusal with the field names, nothing written
  (addendum (8) item 1). There is no draft of the row.

### Н1.5 Enabling and disabling

- `psim disable <id>` — `enabled: false` in the row `plugin` (`PUT` with `If-Match`), then the assembly and the traversal set, the
  traversal (Н1.3). Enabling and disabling change at `backend` only `door.pass.calls`, not the rights file: the traversal usually ends
  without restarts (addendum (25) item 3, which replaced (23) item 5). The part `objects` leaves
  `calls`, `/kinds` does not show the kind of the objects, the instance kind remains — the plugin is seen disabled (addendum (8) item 2).
  The adapter stops the process (chapter 3 Н1.1); the unit is held, the adapter is up.
- `psim enable <id>` — `enabled: true`, the assembly, the traversal; the object kinds are visible again.
- **`enabled` in the form** is read-only: `PATCH /units` with it — 400 (М1 of the review of addendum (8)); the V/11 norm comes by the
  V/11 branch of the core (the contract 0.2.0, V/11.14 Н1.3), until then there is none. A write bypassing the step — Н1.3
  «Limits».

## Н3 Pass

```
install: directory → list → generator → initial values → manifest put of the plugin → plugin row → assembly
enable/disable: plugin row → assembly
sync: assembly
assembly: catalogue and rows → dependent manifests → backend = canon ∪ fragments → manifest put → reread, converged?
```

**Races.** Two simultaneous assemblies — each rereads the catalogue after its own write (Н1.3 step 5): the last one sees both
installations. An edit of `enabled` during an assembly — the same step 5.

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| a generator refusal | nothing written, the generator's line | the operator | — |
| a needed initial value is absent or not by the schema | nothing written, the field names | the operator | give the value |
| `*_secret` in the values file | nothing written, the field name | the operator | enter it by hand |
| the type `source` at two enabled plugins without `owners` | nothing written | the operator | disable one or `--owner` |
| the console did not serve the new revision within `PSIM_MANIFEST_WAIT` | stop; the manifest is written, the row is not | the operator | `psim sync` |
| the directory version of the step's machine is not equal to `version` of the row | nothing written | the operator | update the plugin's package |
| `finish`: the manifest `psim-<id>` by the directory and `--owner` is not equal to the row — a different directory or a different owner choice than at `install` | nothing written | the operator | `install` again |
| an installer refusal of `manifest put` | stop at this step; the previous steps are written | the operator, code 2 | `psim sync` after the fix |
| no plugin directory on the server | `unfit` `plugin directory missing` | the form, the phase | install the plugin's package |
