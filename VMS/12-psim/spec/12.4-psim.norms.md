# V/12.4 — Установка и сборщик манифеста `backend`: нормы

Канон главы 4 урока V/12 «Плагины psim» (ADR-0115 доп. (5) пп. 1, 4, доп. (6) п. 1, доп. (7) пп. 2–4, доп. (8), доп. (9),
доп. (10) пп. 1, 3; М ревью Claude доп. (8)). [Лекция](../12-psim.md), [инструкция](12-psim.README.md). Платформа — выгрузка
`cammeta-specs` `7a875c75`.

Новый плагин — это новая подсистема и новые двери для `backend`. Обратный вызов `backend` — закрытый перечень его манифеста
(V/11.1 Н1.3), поэтому установка плагина ставит две ревизии: манифест плагина и манифест `backend`, собранный заново из
канона и фрагментов всех плагинов. Глава нормирует шаг установки, начальные значения, включение и выключение, сборщик и
пересборку зависимых плагинов.

Id норм — `V/12.4-MM`; соответствие прежним урокам — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Слова урока — глава 1 Н0, глава 2 Н0.

- **Шаг установки** — команда урока `psim` под администратором кластера: `install <каталог> [--values <файл>]`, `enable <id>`,
  `disable <id>`, `sync`. Пишет она установщиком P/02.3 (`manifest put`) и дверью консоли (P/06.1).
- **Канон `backend`** — `VMS/11-backend/backend.subsystem.yaml` выгрузки VMS (V/11.1).

## Н1 Форма

**Данные.** Строки `platform/manifest/psim-*` (P/02.3 Н1.5), `platform/manifest/backend`, строки `psim-*/units/plugin`
(глава 1 Н1.1). Своих семей у шага нет: состояния между запусками он не держит.

### Н1.1 Каталог плагина на серверах

Каталог плагина (глава 2 Н0) лежит на каждом сервере кластера в `/usr/lib/psim-<id>/`, его ставит пакет плагина, как
пакет подсистемы (V/09). Адаптер — один исполняемый файл `/usr/lib/psim/adapter` пакета урока на все плагины, каталог — его
аргумент (глава 1 Н1.6). Сервер без каталога — адаптер на нём не поднимает плагин: `unfit` `plugin directory missing`, предел
(размещение каталога не знает).

### Н1.2 Установка

```
psim install <каталог> [--values <файл>] [--owner <T>=<plugin_id>…]:
  1. прочитать каталог: строки platform/manifest/psim-* и строки psim-*/units/plugin       → список установленных (глава 2 Н0)
  2. генератор (глава 2) по каталогу, списку и owners этого шага                         → отказ: ничего не записано
  3. начальные значения (Н1.4)                                                            → отказ: ничего не записано
  4. manifest put psim-<id>.subsystem.yaml (P/02.3 «Смена манифеста»)                     → отказ установщика: стоп
  5. ждать ревизию: GET /manifest/psim-<id>/source отдаёт rev шага 4, не дольше PSIM_MANIFEST_WAIT → отказ: стоп, psim sync
  6. строка psim-<id>/units/plugin: нет — PUT с начальными значениями, enabled: true, version, owners;
     есть — PATCH с If-Match только новыми параметрами, version и owners, прочие поля не трогаются
  7. сборка (Н1.3)
```

- Обновление плагина — тот же `install` нового каталога: строка `plugin` остаётся, её значения не трогаются (шаг 6 —
  `PATCH` только новыми полями, М1 ревью норм); новые параметры без `default` спрашиваются по Н1.4.
- **Ожидание ревизии** (доп. (16) п. 3): консоль служит прежним каталогом, пока не увидит метку (P/02.3), — строка новой
  подсистемы раньше дала бы 404, новые поля — 400. `PSIM_MANIFEST_WAIT` = 120 с: 30 с проверки метки и подъём консоли
  (решение «Спецификации VMS»). Источник ревизии — `GET /manifest/<sub>/source` (ADR-0116 доп. (6)).
- **`--owner <T>=<id>`** — выбор владельца типа, когда включённых владельцев двое: пишется в `owners` строки зависимого
  (шаг 6) и действует во всех следующих сборках (доп. (16) п. 3).
- **Снятия нет** (доп. (7) п. 4): плагин выключают (Н1.5). Таблицы объектов и `<т>_seen` остаются, повторное включение видит
  прежние объекты; полного удаления нет, предел.

### Н1.3 Сборка

```
сборка:
  1. прочитать каталог и строки plugin (как Н1.2 шаг 1), запомнить их ревизии
  2. генератор по каждому установленному плагину и новому списку; манифест изменился → manifest put и ожидание ревизии,
     как Н1.2 шаг 5 (зависимые: доп. (10) п. 1)
  3. манифест backend = канон ∪ фрагменты (глава 2 Н1.2 п. 2) всех плагинов по имени подсистемы:
       часть enabled — у каждого; часть objects — у плагина со строкой enabled: true
  4. изменился против platform/manifest/backend → manifest put; backend перезапускается (P/02.3, не позже 30 с);
     ждать ревизию GET /manifest/backend/source, не дольше PSIM_MANIFEST_WAIT; шаг кончается только после неё
  5. прочитать каталог и строки plugin снова: ревизии не те, что в шаге 1 → повторить с шага 1
```

- **Источник фрагментов** — строки каталога, не файлы генератора (доп. (7) п. 3): фрагмент каждого плагина строится заново из
  его строки `platform/manifest/psim-<id>`. Вторая установка первую не затирает, обновление VMS плагинов не отрезает
  (доп. (6) п. 1).
- **Обновление VMS** — новый канон `backend` и `psim sync`: та же сборка.
- **Каталог при пересборке** (М2 ревью норм). Генератор шага 2 берёт каталог плагина машины шага `/usr/lib/psim-<id>/`; его
  `metadata.plugin_version` не равен `version` строки `plugin` — отказ сборки `plugin <id> here is <v>, installed <w>`,
  ничего не записано: сначала обновить пакет плагина на машине шага.
- **Владельцы `source`.** Установлен владелец типа — зависимый плагин получает чтение и просьбы шагом 2 той же сборки.
  Установлен зависимый — владелец получает кольцо `<т>_events` у типа, на который тот ссылается, тем же шагом 2 (доп. (14));
  список установленных несёт и такие ссылки (глава 2 Н0).
  Два включённых владельца одного типа без `owners` — отказ шага 2 (глава 2 Н1.2 п. 3), ничего не записано; выбор — выключить
  одного или `install --owner`.
- **Пределы.** Каждая сборка с изменением — перезапуск `backend` (доп. (7) п. 3). Новый зависимый даёт владельцу кольцо
  `<т>_events` — новую ревизию манифеста владельца, его адаптер и процесс плагина перезапускаются (М3 ревью норм). Две сборки одновременно сходятся шагом 5.
  `enabled`, записанное дверью администратора мимо шага, адаптер слушается сразу (глава 3 Н1.1), а `calls` `backend` оно
  меняет только при следующем шаге установки или пересборке: сборка видит его по ревизии строки `plugin` в шагах 1 и 5
  (доп. (10) п. 3, доп. (14)), предел.

### Н1.4 Начальные значения

- **Что спрашивается** — параметр плагина без `default`, не `readonly`, у которого пустая форма типа (`""`, `0`, `false`, `[]`;
  договор проверки строки «Подготовка полей», шаг 4) не проходит `schema` или `enum` поля (М2 ревью доп. (8); доп. (9)). Иные
  параметры без `default` строка получает пустой формой. `readonly` не спрашиваются: их задаёт плагин (доп. (9)).
- **Откуда** — `--values <файл>` (JSON-объект имя psim → значение) или ввод оператора. Значение `*_secret` — только ввод: оно
  проходит один раз дверью консоли; секрет в файле — отказ шага с именем поля (М3 ревью доп. (8)).
- **Отказ** — нужное значение не дано или не проходит схему поля: отказ с именами полей, ничего не записано (доп. (8) п. 1).
  Черновика строки нет.

### Н1.5 Включение и выключение

- `psim disable <id>` — `enabled: false` строки `plugin` (`PUT` с `If-Match`), затем сборка: часть `objects` уходит из
  `calls`, `/kinds` вид объектов не показывает, вид экземпляра остаётся — плагин виден выключенным (доп. (8) п. 2). Адаптер
  останавливает процесс (глава 3 Н1.1); единица держится, адаптер поднят.
- `psim enable <id>` — `enabled: true`, сборка, виды объектов снова видны.
- **`enabled` в форме** — только для чтения: `PATCH /units` с ним — 400 (М1 ревью доп. (8)); норма V/11 — веткой V/11 при закреплении
  контракта этапа 1 (V/11.14 Н1.3), до неё — нет. Запись мимо шага — Н1.3
  «Пределы».

## Н3 Проход

```
install: каталог → список → генератор → начальные значения → manifest put плагина → строка plugin → сборка
enable/disable: строка plugin → сборка
sync: сборка
сборка: каталог и строки → зависимые манифесты → backend = канон ∪ фрагменты → manifest put → перечитать, сошлось?
```

**Гонки.** Две сборки одновременно — каждая перечитывает каталог после своей записи (Н1.3 шаг 5): последняя видит обе
установки. Правка `enabled` во время сборки — тот же шаг 5.

## Н4 Отказы

| Причина | Исход | Кто и как видит | Что делает вызывающий |
|---|---|---|---|
| отказ генератора | ничего не записано, строка генератора | оператор | — |
| нужного начального значения нет или оно не по схеме | ничего не записано, имена полей | оператор | дать значение |
| `*_secret` в файле значений | ничего не записано, имя поля | оператор | ввести вручную |
| тип `source` у двух включённых плагинов без `owners` | ничего не записано | оператор | выключить одного или `--owner` |
| консоль не отдала новую ревизию за `PSIM_MANIFEST_WAIT` | стоп; манифест записан, строки нет | оператор | `psim sync` |
| версия каталога машины шага не равна `version` строки | ничего не записано | оператор | обновить пакет плагина |
| отказ установщика `manifest put` | стоп на этом шаге; прежние шаги записаны | оператор, код 2 | `psim sync` после исправления |
| нет каталога плагина на сервере | `unfit` `plugin directory missing` | форма, фаза | поставить пакет плагина |

## Н5 Приёмка

Стенд урока (ветка приёмки урока): установить `camera`, затем `security_controller` на работающем стенде; через `/units` по
билету прочитать, создать, изменить объект, выполнить команду, прочитать и изменить параметр плагина, открыть страницу
(доп. (5) п. 1, доп. (7) п. 1); выключить `camera` и увидеть его выключенным; включить; `psim sync` после нового канона
`backend` — плагины не отрезаны (доп. (6) п. 1, доп. (8) п. 2); обратный порядок установки — `security_controller` получает
чтение `psim-camera` сборкой.
