# V/11.4 — Перевод чтений и записей: нормы

Канон главы 4 урока V/11 «Бэкенд конфигуратора» (ADR-0094 A3, A6; доп. (2) пп. 3, 4). [Лекция](../11-backend.md),
[инструкция](11-backend.README.md), таблица [`data/mapping.tsv`](../data/mapping.tsv), контракт
[`consolem.openapi.json`](../consolem.openapi.json). Платформа — выгрузка `cammeta-specs` `9f851112` (пин VMS; приращение прав поверх норм B, ADR-0090 доп. (17); пометка «норма платформы B» — где глава на них опирается).

Глава 3 говорит, какой вид consolem какой подсистеме отвечает. Эта глава — как `backend` собирает запись вида из строк
подсистем, как разбирает правку обратно по строкам, как сверяет версию, что помнит о повторах и как переводит отказ
консоли в отказ контракта. Всё — обратными вызовами по билету запроса на двери перечня (V/11.1 Н1.5).

Id норм — `V/11.4-MM`; соответствие — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Правила модуля «Платформа» — [P/01.1
Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-словарь-слов).

- **Часть** — строка подсистемы, из которой собрана запись вида: у камеры — строка камеры `cam/cameras/<id>` (пустой
  `main`) и её потоки (`cam/cameras` с `main` = id), её записи `rec/recordings` и детекторы `det/units` (глава 3 Н1.2).
- **Индекс хранилища** — версия строки хранилища (P/01.1): не повторяется (рост доп. (4) не обещает); у надгробия строки
  — свой индекс (P/06.1; ADR-0094 доп. (2) п. 4 (в), доп. (3) п. 9; не надгробие тела `.gone/` ресурса).
- **Групповая запись** — `POST /devices` (создание), `POST /devices/update` и `POST /objects/delete` контракта:
  несколько объектов одним запросом с `idempotencyKey` в теле; **шаг** — один элемент `items`.
- **Пакет** — пакетная запись хранилища B9 дверью консоли (ADR-0094 доп. (9); норма платформы B):
  у каждой записываемой строки свой `cas`, у прочитанных незаписываемых — стражи; всё или ничего.
- **Скрытый член** — член папки, которого нет в `deviceIds`: поток камеры, вторая строка `type: ipsrv` хоста, член вне перечня читателя (Н1.7).
- **Корень цели** — строка операции, по которой консоль судит занятость (P/06.9 Н1.3): Н1.8.
- **Кластер входа**, **своё**, **чужое** — глава 3 Н1.2а. **Связка** — одна хранимая правка из нескольких строк, `POST /domain/edits` (P/08.6 Н1.3б): Н1.13.

## Н1 Форма

**Время.** Срок памяти повторов — `delete_after` таблицы `repeats`: его считает консоль от первого наблюдения версии
строки, не время хранилища, и строку снимает жнец платформы (Н1.4); стенных часов `backend` память не судит (разбор ревью V/11, Codex № 7, вопрос 3).

**Данные.** Части читаются и пишутся дверями консоли по билету (V/11.1 Н1.3). Своя семья главы — память повторов
группового ключа: таблица манифеста `backend/repeats/<h>` (Н1.4; форма — поля таблицы `repeats`
[манифеста](../backend.subsystem.yaml): семья таблиц платформы — со схемой `manifest`, P/06.1 Н1.6), дверью таблиц
и пакетной дверью консоли по билету (V/11.1 Н1.5).

### Н1.1 Сборка записи (чтение)

- Камера (`Device`, `type: camera`) — строка камеры `cam/cameras/<id>` (пустой `main`, `type: camera`), её потоки (строки `cam/cameras`
  с `main` = id), записи `rec/recordings` про эту камеру (`cam` записи — её id, V/02.1) и детекторы `det/units` про неё
  (`cam`, V/04.1), всё — дверями единиц консоли (`GET /<sub>/<rows>`), слова пульса — `GET /<sub>/<rows>` (`rows`, P/06.1
  Н2). Поля — строками таблицы главы 3; `recordMode` — из записей `<cam>`, `<cam>-<том>` (глава 3 Н1.3). Строка
  `cam/cameras` с непустым `main` — поток своей камеры, отдельным устройством не отдаётся.
- Детектор, том — одна строка своей подсистемы (глава 3 Н1.2); хранилище — строка тома и записи на нём (`retentionDays`);
  правило и библиотека — Н1.10, Н1.11. Строка записи камеры и `cam/rule_state/<id>` читаются тем же снимком (глава 3 Н1.3).
- Дерево устройства (глава 3 Н1.3 «Дерево») читается тем же снимком: таблицы `cam/devices`, `cam/children`, `cam/child_settings`, `cam/device_units` — дверями таблиц (`GET /cam/devices`, P/06.1 Н1.6), строки с индексом. Строки `cam/devices/<хост>` нет — `channels`, `videos` не сказаны: `ipsrv` есть только по строке `type: ipsrv`, `videoChannel` нет. Строка нечитаема (`garbled`) — поля не прочитаны, а не отсутствуют: записи этого хоста (`ipsrv`, каналы, камеры) в `GET /devices` не отдаются, чтение одной — 503, как нечитаемая папка (Н1.7). Значение `type` вне перечня не отдаётся: слово не прочитано (V/01.1 Н1.1б). 403 двери таблицы — часть не видна, отказа нет, как у надгробий (ниже): `ipsrv` и `parentId` выводятся по строке и адресу (глава 3 Н1.3), молчат `channels`, `subtype`, `videoChannel`, каналов нет, часть `h` пуста.
- Id записи вида — Н1.6.
- Чужая запись — те же сборки из вида домена, без двойного чтения: глава 3 Н1.2а.
- **Чужая запись** собирается теми же правилами из вида домена (глава 3 Н1.2а). Версия — та же склейка с `revision` строки вместо индекса: индекса и надгробий в виде нет, поэтому часть снятой строки пуста, и версия чужой записи может вернуться к прежней. Двойного чтения нет. Одна запись через разные входы имеет две версии: `If-Match` сверяется с версией того входа, что её выдал; после смены входа — 412 и перечитывание.
- **Версия** записи — непрозрачная строка контракта, сравнивается только на равенство (ADR-0094 доп. (4) п. 1). У
  детектора, тома, `channel`, `storage`, единицы — индекс хранилища строки; у строки `eventsrc`, `acfa` — индекс этой строки. У камеры — склейка индексов частей в постоянном порядке: `c<индексы
  cam>.r<индексы rec>.d<индексы det>.h<индекс cam/devices>.i<индекс строки ipsrv>.s<индекс cam/rule_state>.a<индекс строки записи>`: после буквы части — индексы её строк через `-` (у `c` — строка камеры, затем её
  потоки; у прочих — в порядке ключа строки, байты UTF-8), у удалённой строки `rec`, `det` — индекс её надгробия, у
  части без строк — пусто (`c17.r.d.h.i.s.a`, `c17-18.r21-30.d44.h9.i31.s52.a60`). Строка заказа (`made`) частью не бывает: её ведёт вычислитель (глава 3 Н1.3). Строки `cam/devices` хоста, `ipsrv` и `cam/rule_state` входят в версию (от них зависят `parentId`, `videoChannel`, `armed`), но не в стражи пакета: их полей правка не пишет, а предел стражей занят частями (Н1.2). Это предел: их смена между снимком и пакетом правку не отменяет, запись `events`, `videos` соседа меняет версию камеры без видимой правки, а снятие строки `ipsrv` возвращает пустую часть, и версия может вернуться к прежней при той же видимой записи. У `ipsrv` — `h<индекс cam/devices>.c<индекс строки>`, у ребёнка — `k<индекс cam/children>.s<индекс cam/child_settings>`; части нет — пусто. Дети — свои записи, в версию камеры не входят; `subtype` от детей зависит, но в версию их не берёт: смена описания пишет и строку `cam/devices`. У хранилища — `v<индекс тома>.r<индексы записей с home =
  том>` (от записей зависит `retentionDays`; разбор ревью V/11, Codex № 13). Индекс — провод P/01.1 Н2 (десятичные
  цифры), поэтому буквы, точка и `-` склейку не путают. Строки `rec` и `det` части — строки этой подсистемы про камеру
  (`cam` строки — id камеры) и надгробия таких строк; надгробия частей не убираются, пока камера жива (доп. (4) п. 1
  (в)). Потоки и записи хранилища входят живыми строками: надгробие потока не находится (у строки `cam` нет `about`),
  надгробие записи — по камере, не по тому. Поэтому версия камеры или хранилища может вернуться к прежней, если поток
  или запись тома завели и сняли мимо `backend`; видимая запись при этом та же — её поля — функция тех же строк тех же
  индексов (открытый пункт README: строгое «не возвращается» продукта).
- Индексы: индекс строки — в элементе списка `GET /<rows>` и таблиц (норма платформы B4; разбор
  ревью V/11, вопрос 6); надгробия частей камеры — `GET /<rows>?deleted=1&about=<cam>` → `{deleted: [{id, index, revision}]}`
  (надгробие хранит значение `about`; B4, доп. (5) п. 1); 403 этой двери — часть не видна: надгробий этой подсистемы в
  склейке нет, отказа нет; индекс надгробия своей записи — `ETag` ответа `DELETE` и
  сообщение ленты. Двери одной строки у консоли нет: «404 с `ETag` надгробия» (доп. (3) п. 9) заменено этим чтением. До
  B4 двери консоли индекса не отдают, и версии записи `backend` выдать не может: глава действует после приращения
  платформы (вместе с B1, без которого передачи `backend` нет, V/11.1 Н1.3).
- Поля не из строк частей (пульсы, сервер держателя) в версию не входят (глава 3 Н1.3; разбор ревью V/11,
  Claude С-1).
- **Версия зависит от смотрящего** (ADR-0094 доп. (12) п. 12). Строки части, которых человек не видит, в склейку не входят:
  перечень отдаёт только разрешённые. Два человека с разными правами получают разные версии одной камеры, и `If-Match` сверяется с
  версией того, кто пишет. Часть без `view` страж не стережёт; строка, которой он не видит, в пакете отказывает тем же словом,
  что отсутствующая: наружу это 412.
- **Чтение двойное** (там же): строк частей две двери, поэтому снимок читается дважды подряд, пока индексы двух чтений не совпадут; не
  совпали за три попытки — 503: снимка, годного для версии, нет. У `GET /devices` снимок — весь список, попытка — пара полных чтений, 503 — ответу целиком.
- Ответ — `ETag` записи вида — её версия строкой в кавычках (`"c17.r21-30.d44.h9.i.s.a"`); `If-Match` сверяется равенством
  строки целиком.

### Н1.2 Разборка правки (запись)

Своя запись. Чужая — те же строки связкой: Н1.13.

- **Постоянные ключи частей** (разбор ревью V/11, вопрос 1 (а)): записи и детекторы, которые создаёт `backend`, — с
  ключами от камеры: основная запись — `rec/recordings/<cam>`, резервная на томе `<том>` — `rec/recordings/<cam>-<том>`,
  детектор — `det/units/<cam>-<kind>` (образец V/04), второй того же вида — `det/units/<cam>-<kind>-<n>`: `n` — наибольший номер живых строк и надгробий этой пары из снимка + 1, не меньше 2. Одновременное создание одной части сходится на одном `cas ""`:
  второй пакет — отказ, ничего не записано.
- **Замок устройства — строка камеры** (вопрос 1 (б)). Каждый пакет части камеры **пишет** строку `cam/cameras/<id>` —
  `cas` её индекса из снимка, значение прежнее или новое: правка камеры, её записи или детектора, создание и удаление
  детектора, удаление камеры. Две записи одного устройства упорядочены строкой камеры: вторая — 412. Удаление камеры
  и запись её части не проходят обе.
- **Запись устройства — один пакет** (ADR-0094 доп. (9) п. 3). Правка камеры (`PATCH /devices/{id}`): строка камеры
  (замок), записываемые части — каждая с `cas` своего индекса **из того же снимка**, по которому сверена версия (Н1.3),
  не перечитанным; прочие части устройства из снимка — потоки, строки `rec` и `det` камеры — **стражами** с их
  индексами. Пакет проходит целиком или не проходит: изменилась хоть одна строка снимка — 412 консоли, не записано
  ничего. Часть, которой ещё нет, пишется в пакете поверх её надгробия с `cas` его индекса, если надгробие было в снимке,
  иначе — созданием (`cas ""`). Правка детектора (`Device`, `type: det`) — пакет из строки `det` и строки его камеры
  (замок); `zone` с фигурой — ещё дверь тела маски (глава 3 Н1.3 «`zone`»). Строки про камеру, созданные мимо `backend` (прямые двери консоли) после снимка, пакет не стережёт: их видит
  следующее чтение — новая `version`.
- **`recordMode`** — переход по записям `<cam>`, `<cam>-<том>` (глава 3 Н1.3; разбор ревью V/11, вопрос 2), в одном пакете
  с прочей правкой:
  - `always` — основная `<cam>` `enabled: true`, `replica_from` пуст; её нет — создание на томе `archiveId` тела, а без него — 422
    `VALIDATION_FAILED`, `field: archiveId`;
  - `replica` — основная `<cam>` `enabled: true`, `replica_from`: `device`, непустое не меняется (глава 3 Н1.3); её нет — так же создание;
  - `none` — все записи `<cam>`, `<cam>-<том>` — `enabled: false`;
  - `motion` (ADR-0111 п. 4) — основная `<cam>` `enabled: false`, её нет — создание на томе `archiveId` тела, а без него — 422 `VALIDATION_FAILED`, `field: archiveId`; строка записи камеры (глава 3 Н1.3) в том же пакете: нет — создание с `auto/next_id`, как у камеры, есть — запись с `cas` снимка; `recordDetectorIds` тела — её цель и `enabled`, поля нет — цель прежняя;
  - `sched` — 422 `NOT_SUPPORTED`, `field: recordMode`: ждёт контракта.
  Уход из `motion` снимает строку записи в том же пакете. `archiveId` при `motion` пишется и в `archive` её действия. Пакет с `auto/scenarios` судится правом сценария на весь кластер (`cluster_rows`, V/07): без него — 403 всего пакета, режим не меняется, это предел.
  `archiveId` — `home` основной `<cam>` (`null` — снять основную, `DELETE` в пакете; том `backup`, `edge`, `incidents` — 422 `VALIDATION_FAILED`, `field: archiveId`, глава 3 Н1.3); `extraArchives` — набор дополнительных:
  элемент — строка `<cam>-<том>`, элемент тома `edge` (глава 3 Н1.3) эхом пропускается без записи (`recordMode` элемента `null`, `always` — `enabled: true`, `replica_from` пуст, у новой строки на томе `backup` ещё `when: offline`; `replica` — `enabled: true`, `replica_from`: `device`, непустое не меняется (глава 3 Н1.3); `none` — `enabled: false`; иное — 422
  `NOT_SUPPORTED`; `stream` — `stream` записи; `when` нынешней строки не меняется), строки вне набора снимаются; `stream` — `stream` основной; основной нет
  и тело её не создаёт (в том числе `archiveId: null` в том же `set`) — 422 `VALIDATION_FAILED`, `field: stream` (разбор
  ревью V/11, дополнение Kimi, № 8). Новая запись — со сроком хранилища своего тома (глава 3 Н1.3). Основная, созданная
  `archiveId` без `recordMode` в том же `set`, — `enabled: false`: режим не меняется.
- **Создание строки устройства** (`POST /devices`, элемент `type: camera`, `ipsrv`, `eventsrc`, `acfa` с `parentId: null`) — один пакет; `type` тела — поле строки, адрес — глава 3 Н1.3 «Адрес устройства»: счётчик `cam/next_id` (`cas` прочитанного,
  значение `n + 1`; значение и индекс — `GET /cam/next_id`, P/06.1 Н2 «Дверь счётчика»), строка `cam/cameras/<n + 1>` (`cas ""`), записи `<n + 1>`, `<n + 1>-<том>` и детекторы
  `<n + 1>-<kind>` из `children` и полей записи — записи и детекторы только у `camera` (ADR-0111 п. 3: строка `camera` и все её записи получают `ref` = `<CLUSTER>-<n + 1>`, запись, заведённая позже, — `ref` строки камеры; основная в домене одна: V/02.9 Н1.6; норма платформы B9, `POST /console/batch`, P/06.1 Н2 «Пакетная дверь»:
  номер называет вызывающий, счётчик идёт в том же пакете; разбор ревью V/11, вопрос 9). `n` —
  значение счётчика, прочитанное до пакета: последний выданный номер, новой камере — следующий (P/06.1 Н1.3). Счётчик
  сдвинули — 412 `row moved` с `key: cam/next_id`, пакет строится заново с новым чтением (Н1.4). **`identifier` создания** — проверка, а не ключ: строка `cam/cameras/<identifier>` жива и не выдана этой группой (`steps` строки `<h>`) — отказ элемента 409 `IDENTIFIER_TAKEN`, `field: identifier`, до прочих проверок элемента: мастер нумерует строки сам, а счётчик может быть впереди его дерева, номера своей группы значения не занимают; иначе значение пропускается: номер выдаёт счётчик, ответ несёт выданный. Мастер шлёт номер при каждом импорте CSV, считая его по своему дереву, поэтому свободный номер — не отказ. Создание детектора — пакет из строки ключа выше (`cas ""`, надгробие в снимке — `cas` его индекса) и строки камеры (замок); `kind` — `detectorKind`, его нет — 422 `VALIDATION_FAILED`, `field: detectorKind`; `name` тела — поле `title` (глава 3 Н1.3). Создание хранилища
  (`POST /archives`) — строка `rec/volumes/<name>` (`cas ""`) из полей хранилища и `firstVolume` (том = то же
  хранилище: `disk`, `sizeBytes`, адрес — строки таблицы `Volume`).
- **`configMode`** (ADR-0107 доп. (1)) — поле запроса создания камеры, не поле строки; связи с источником нет. `current` — ничего. `default` — в `resolution`, `fps` новой строки значения модели из `device-catalog.json`; поля `res`, `fps` тела важнее. Это меняет настройку камеры: держатель передаст их драйверу обычным путём (V/01.2 Н1.2а). Модели нет (`rtspUrl`) или её нет в файле — 422 `VALIDATION_FAILED`, `field: configMode`. `template` — тем же пакетом разовая копия с камеры `templateId` той же модели, видимой читателю: `resolution`, `fps`, `firmware`, строки её прочих потоков с `profile`, `source` — как «Потоки за камерой» (глава 3 Н1.3), поток на ином хосте не копируется, у каждого свой номер счётчика; поля тела важнее. Адрес, логин, пароль, имя, записи, папки, детекторы, `norm` детей не копируются. Источника нет или `vendor`, `model` разные — 422 `VALIDATION_FAILED`, `field: templateId`. Поток сверх `DEVICE_PARTS_MAX` — как у прочих частей.
- **Встроенный детектор** (`Device`, `type: det`, `builtin: true`; глава 3 Н1.3). Создание — `parentId` основная камера с адресом `ipint://`; её `vendor`, `model` нет в `device-catalog.json` — 422 `NOT_SUPPORTED`, `field: builtin`. `template` тела — детектор модели, вне `detectorOptions` — 422 `VALIDATION_FAILED`, `field: template`. Не назван — детекторы модели, чей вид по `detector-kinds.tsv` равен `detectorKind`: нет — 422 `NOT_SUPPORTED`, `field: detectorKind`; один — он; несколько — 422 `VALIDATION_FAILED`, `field: template`. Номер и пакет — как у единицы, ниже; `title` — `name`, `folderId` не `null` — 422 (Н1.7): строка не единица прав. **Правка** — `name`, `enabled`, `sensitivity`, строка целиком с `cas` снимка, строка камеры — страж; `detectorKind`, `model` — 422 `NOT_SUPPORTED`, `field`. **Снятие** — как у единицы. Право — `admin` на строку камеры (`rights.unit_of`, V/01.1 Н1.5). `children` камеры с `builtin: true` — те же шаги в пакете создания камеры.
- **Удаление камеры** (`DELETE /devices/{id}`) — один пакет: снятие строки камеры, её потоков, записей, детекторов
  и строки записи (контракт: «вместе с дочерними»), каждой с `cas` её индекса из снимка. **Удаление детектора** — пакет: снятие строки
  `det`, запись строки камеры (замок) и строки записи этой камеры без него, если он в цели. Прочие правила — каскад Н1.10.
- **Включение камеры, выключенной правилом** (глава 3 Н1.3; V/01.4 Н1.4д): `PATCH enabled: true`, шаг `set`, элемент `POST /devices/update`, пока выключение действует, — просьба `cam` `disable` со сроком в прошлом; строка камеры с `enabled: true` поля не получает, строка с `enabled: false` получает его пакетом. Прочие поля тела — обычный пакет, раньше просьбы; только `enabled` — пакета нет, версия сверяется снимком (Н1.3). `POST /cam/requests` по билету (P/06.3 Н1.9): `{unit: <cam>, action: disable, disabled_by_rule: <значение строки>, disabled_until: 0}`, `Idempotency-Key` — hex SHA-256 от `enable`, нулевого байта, `<cam>`, нулевого байта и индекса строки `cam/rule_state`: повтор той же правки — та же просьба. Подача повторяется тем же ключом, пока не придёт 200 с меткой, в пределах срока маршрута `api/devices`. `performed` — запись читается заново. Метки нет к сроку, `expired`, `gone`, `unknown` — 409 `DEVICE_OFFLINE`, `field: enabled`; `refused`, отказ двери — по Н4, `field: enabled`; у групповых дверей — элемент `failed`, у шага — итог `fail`, прочие поля при этом записаны. Шаг операции подаёт просьбу до пакета итога, ключ тот же. В стопку отката просьба не ложится: строки записи нет. **Предел:** выключение вернётся только новой сработкой, откат и `retry` его не дают.
- **`ipsrv`** (ADR-0102 доп. (5) п. 5, доп. (6) пп. 6, 7, 10). Строка `type: ipsrv` есть — `PATCH`, `POST /devices/update`, шаг `set` пишут её одним пакетом, `cas` индекса снимка: `name`, `enabled`, `short`, `lat`, `lon`, `azimuth`, `mac`, `login`, `password`, поля адреса; `DELETE` снимает её, камеры хоста остаются и теряют только родителя, если `channels` не больше 1. Смена хоста — отказ (глава 3 Н1.3). Строки нет (`derived: true`) — `PATCH` и `DELETE` — 422 `NOT_SUPPORTED`, `field` первого поля тела, у `DELETE` — `field: type`.
- **`eventsrc`, `acfa` строкой** — одна строка: `PATCH`, `POST /devices/update`, шаг `set` пишут её с `cas` индекса снимка, `DELETE` снимает её и строки `cam/device_units` на ней одним пакетом, из папок снимает консоль тем же пакетом. Камера и `ipsrv` с единицами — так же. Строка `cam/unit_next` остаётся: id строки не повторяется.
- **Единицы** (`acfa_sensor`, `acfa_lock`, `acfa_fence`, `relay` единицы, `acfa` с родителем; V/01.1 Н1.2б). Создание — по `parentId`; `acfa` с родителем — строка `type: controller`, адреса `ip`, `vendor` нет, адрес единицы — `path`: запись основной строки `cam/cameras` (корень) или единица, её `camera` — `camera` новой; у записи `ipsrv` — строка `type: ipsrv` её хоста, из двух наименьший id числом. Иной родитель, в том числе `ipsrv` без строки, — `PARENT_MISMATCH`, `field: parentId` (Н1.5). **Шаблон** — по [`unit-templates.tsv`](../../01-cam/data/unit-templates.tsv): строки с `vendor` адреса строки `camera`, `parent` — шаблон родителя (`-` у корня), `type` тела, у `acfa` — `controller`; адрес не `ipint://` — строк нет. Нет строк — 422 `NOT_SUPPORTED`, `field: type`. Одна — она. Несколько — выбирает `model`; не назван или вне них — 422 `VALIDATION_FAILED`, `field: model`. Промежуточные узлы заводятся по одному, сверху вниз: цепочку `backend` сам не строит, узлу может быть нужен свой адрес; два узла одного шаблона различает их id.
  **Номер.** Прочитать снимком `cam/unit_next/<строка>` и строки `cam/device_units` этой строки: `n` — большее из значения счётчика и наибольшего номера живых строк, счётчика нет — 0, живых строк нет — 0: строку могли завести дверью таблиц мимо счётчика. Счётчик не читается — 503: снятый номер мог бы вернуться. Пакет: `cam/unit_next` со значением `n + 1` и `cas` снимка (`""`, если строки нет), `cam/device_units/<строка>-<n + 1>` с `cas ""`, стражи основной строки и единицы-родителя. В группе — номера подряд. 412 по любой из этих строк — пакет строится заново с новым чтением (Н1.4).
  **Правка** — строка целиком с `cas` снимка: `name`, `enabled`, `path`; `model`, `parentId` — 422 `NOT_SUPPORTED`, `field`. **Снятие** (`DELETE`, элемент `/objects/delete`) — единица и все вложенные одним пакетом, каждая с `cas`; не вмещается в пакет — 422 `NOT_SUPPORTED`, `field: type`. Право — `admin` на основную строку (`rights.unit_of`, V/01.1 Н1.5), `folderId` — 422 (Н1.7).
- **`channel`, `storage`** правки и `DELETE` не имеют: 422 `NOT_SUPPORTED`, `field: type`.
- **Дети** (`sensor`, `relay`, `mic`, `spk`). Создания и удаления нет: `POST /devices`, шаг `create` — 422 `NOT_SUPPORTED`, `field: type`, `DELETE`, элемент `/objects/delete` — так же. `PATCH` правит `name`, `enabled`, `norm`; прочие поля — по `way` главы 3. `POST` таблицы — полная замена строки, поэтому `PATCH` сливает: читает строку `cam/child_settings/<id>` снимком, берёт её `title`, `enabled`, `norm`, поверх — поля тела, пишет строку целиком с `camera`, `type`, `number` из ключа, `cas` индекса снимка или `""`, в одном пакете со стражем строки `cam/children/<id>`. Право — `edit` на хозяина (`rights.routes`, V/01.1 Н1.5). Ребёнок `gone` или с мёртвым хозяином — 404 `NOT_FOUND`.
- **Каскады хранилища** (разбор ревью V/11, Codex № 14, Claude С-16) — один пакет на объект:
  - `DELETE /archives/{id}` — «камеры не удаляются»: у камеры, чья основная `<cam>` на этом томе, основной становится
    первая дополнительная `<cam>-<Y>` по имени тома, кроме томов `backup` (основная `<cam>` получает `home: Y` и поля той записи; `replica_from`, называвший `<cam>`, снимается: иначе источник — она сама; `<cam>-<Y>`
    снимается), такой нет — основная снимается (`recordMode: none`), записи на `backup` остаются; дополнительные `<cam>-<том>` на этом томе
    снимаются; записи с иными именами на томе снимаются; строки затронутых камер пишутся (замок); затем снятие строки
    тома;
  - пакет больше предела B9 — отказ консоли, ничего не записано (Н4).
- **Предел частей.** `DEVICE_PARTS_MAX` = 56: потоков, записей и детекторов устройства (ADR-0094 доп. (12) п. 4). Он не выше предела
  стражей: стражи — части, цепочка папки до 7 и страж поколения дают 56 + 7 + 1 = 64 (`BATCH_GUARDS`); записи — камера, части,
  счётчик, строка `<h>`, папка, членство, итог и счётчики шага дают 1 + 56 + 6 = 63 ≤ 64 (`BATCH_WRITES`), строка `backend/undo` — 64. Строка записи камеры и `auto/next_id` считаются двумя частями. `backend`
  держит его при создании части: запись `POST /devices`, `PATCH /devices` сверх предела — 422 `VALIDATION_FAILED`, `field:
  extraArchives` или `parentId`. Части, созданные мимо `backend`, предел обходят: такой пакет — 413 консоли, строка Н4.
- **Папки при удалении.** Камеру и детектор из папок снимает консоль тем же пакетом (P/06.8 Н3 «удаление единицы дверью»); `backend`
  этих строк не называет. Вес держит Н1.7 `DEVICE_FOLDERS_MAX`.
- **Отказ пакета** — любой строки: `cas` или страж (412), права, проверка строки, предел пакета — отказ всего пакета без
  записи (доп. (9) п. 2); ответ — отказ контракта (Н4), при 412 — с текущей записью вида. Записанного наполовину
  устройства не бывает.

### Н1.3 Сверка версии

- Запись без `If-Match` — 428 `PRECONDITION_REQUIRED` (контракт). Порядок проверок и 412 у чужой записи те же, снимок — вид домена (Н1.13).
- После 428 тело сверяется со схемой контракта: неизвестное поле, тип, `enum` — 422 `VALIDATION_FAILED`, `field`. Затем
  цель: нет — 404 `NOT_FOUND`; затем версия (ниже); затем поля по `way` (глава 3 Н1.1).
- `backend` читает части записи одним снимком и считает её версию (Н1.1); не совпала с `If-Match` — 412
  `VERSION_MISMATCH`, `current` — текущая запись вида (контракт). `If-Match` камеры — версия всего устройства. Совпала —
  пакет (Н1.2): строка камеры пишется, записываемые части с `cas`, прочие стражами, индексы — из того же снимка (ADR-0094
  доп. (9) п. 3). Правка **любой** строки снимка, кроме `cam/devices` и строки `ipsrv` хоста (Н1.1), между сверкой и записью — 412 консоли по пакету, ничего не записано;
  ответ — 412 `VERSION_MISMATCH` с текущей записью вида. Перекоса по частям нет: прежнее ограничение (доп. (3) п. 5)
  снято доп. (9) — `412` значит «ничего не изменилось», связанные поля строк `rec` (`recordMode`, `archiveId`,
  `extraArchives`) при одновременных правках не расходятся. **Предел:** `412` говорит только об этом запросе. У одиночной
  правки ключа нет (Н1.4 — группы и шаги), запрос без ключа автоматически не повторяется (P/06.1 Н2 «Двери тел и таблиц»): ответ консоли потерян —
  502–504, исход неизвестен, и повтор клиента с прежним `If-Match` на свою же легшую правку получает 412 (`DELETE` — 404,
  `POST /archives` — занятое имя). Исход после неответа — чтением.

### Н1.4 Память повторов группового ключа — своя таблица, всегда

- Групповая запись несёт `idempotencyKey` в теле (контракт). `backend` помнит её **всегда** (не «до B3») и общей для
  экземпляров памятью — своей таблицей манифеста `backend/repeats/<h>` (разбор ревью V/11, вопрос 3; Codex № 2, 3, 5–7,
  Claude Б-2, С-6–С-9). `h` — SHA-256 (hex строчными) от байтов `user`, нулевого байта и внешнего `idempotencyKey`
  (`user` — человек билета). Служебная семья `<sub>/idem/` консоли — не её. Чтение — дверь таблиц консоли по билету
  (V/11.1 Н1.5), запись с `cas`, в том числе `cas ""`, — строка таблицы в `POST /console/batch`: таблица `service: true` (P/06.1 Н1.6, ADR-0094 доп. (15) п. 3) читается и пишется только по живому
  билету от листа роли `backend`, правом следствий, `may` человека не проверяется — людям строк на `sub: backend`
  перевод прав не даёт. Строка — `{h, user, idem_key, op, body, state, steps}`: `op` — `operationId` группы (`createDevices`, `updateDevices`, `deleteObjects`, `createOperation`, `updateRules`, `assignServers`), `body` — SHA-256
  (hex) байтов тела запроса, `state` — `started` | `done`, `steps` — итоги шагов `[{index, outcome: done | failed, id?,
  code?, field?}]` текстом JSON: поле `json` кончается на 4000 байтах (P/06.1 Н1.4), группа длиннее. Форма — поля таблицы `repeats` манифеста со схемами полей (семья таблиц платформы — со схемой
  `manifest`, P/06.1 Н1.6); исход нечитаемой строки — ниже.
- **Порядок.** Первым — память, потом версия:
  1. Строка `<h>` создаётся `cas ""` — `{state: started, steps: []}` — **до** снимка и до первого шага.
  2. Создать не вышло (строка есть) — её читают. `user` и `idem_key` строки не те, что у запроса, — 422
     `VALIDATION_FAILED`, `field: idempotencyKey` (совпадение `h` разных ключей); `op` или `body` не те — то же 422
     (ключ занят иным телом; кода «ключ занят» в контракте нет); `state: done` — ответ из `steps` (ниже) без обращений к
     частям; `state: started` — ответ по завершении: повтор продолжает ту же группу (ниже), его ответ — из `steps`,
     когда строка `done`.
  3. Шаг: снимок и сверка версии элемента (Н1.3), затем пакет устройства (Н1.2), и в **том же пакете** — строка `<h>` с
     итогом шага в `steps` (`cas` её индекса): итог и запись шага ложатся вместе или не ложатся (норма платформы B9: пакет
     несёт строку таблицы `backend/repeats`). Отказ шага (ничего не записано) — итог `failed` пишется отдельно, `cas`
     строки `<h>`.
  4. После последнего шага — `state: done`, `cas` строки.
- **Повтор при `state: started`** — первый запрос ещё идёт или оборвался (жив ли он, `backend` не видит): повтор идёт
  по той же группе. Шаги с итогом в `steps` не исполняются снова и не сверяют версию; прочие — по порядку (шаг 3).
  Исполнителей может быть два, и их упорядочивает строка `<h>`: каждый пакет шага несёт её `cas`. Шаг создания (версии у элемента нет)
  ответил 412 по строке с прочитанным индексом — `cam/next_id`, `cam/unit_next`, строка папки и её цепочка (Н1.7), строка камеры детектора, основная строка и единица-родитель единицы, строка `cam/device_units`, `det/units` с `cas ""` — это не итог: строку сдвинул другой запрос,
  шаг строится заново с новым чтением этих строк и строки `<h>` (Н1.2, «Ключи шагов»), отказ даёт уже новое чтение: папки нет — `NOT_FOUND`. Иной 412 — строку `<h>` перечитать: итог шага в ней есть (его записал другой исполнитель) — шаг окончен, иначе — итог
  `failed` с кодом по Н4. `409 in flight` и `422 key reused` — строку `<h>` перечитать, итог есть — шаг окончен. Итога нет: при `422 key reused` прежний пакет под этим ключом отказан и не записан — итог `failed` `VERSION_MISMATCH`; при `409 in flight` другой исполнитель занял ключ — ответ 503 (Н4), `<h>` остаётся `started`. Сделанный шаг не отвечает 412 на свою же запись: его итог лёг с ним в одном пакете.
  Оборванная группа так доходит до конца повтором.
- **Ответ из памяти:** `id` шага — корневая запись; элемент `done` — запись вида, прочитанная сейчас, у `POST /devices`
  `devices` — она и дочерние; запись снята или скрыта — элемент опускается; у `/objects/delete` — её id; элемент `failed` —
  сохранённые `code` и `field`; форма — `{done, failed}` операции.
- **Нечитаемая строка** `<h>` — элемент `garbled` или значение не по полям таблицы манифеста (обязательные, `enum`,
  `pattern`), судит `backend` — неизвестный исход: 503 (код — глава 2 Н1.3), не повтор и не исполнение заново; строка не
  переписывается.
- **Срок** — `delete_after` таблицы `repeats`, 86400 с, как память повторов консоли (P/06.1 Н3): считает консоль от
  первого наблюдения версии строки, не время хранилища, поэтому срок может только удлиниться; строку снимает жнец
  (глава 6.4 Н3 `tables`; ADR-0094 шаг 3б). Строки нет — запрос первый. У приёма операции `OPS_KEEP` (P/06.9 Н1.6) не меньше этого
  срока, но часы разные, поэтому Н1.8 «Память и операция» называет, что бывает на стыке.
- **Ключи шагов.** `Idempotency-Key` обратного вызова шага — hex SHA-256 от `h`, нулевого байта и десятичной записи номера шага; у шага создания дальше — нулевой байт и десятичная запись прочитанного `n`, если пакет берёт номер, и за нулевым байтом индекс каждой прочитанной строки пакета вне `<h>` и счётчика, в порядке пакета (`cas ""` индекса не несёт) —
  64 знака, один сегмент, в пределах ключа консоли (200 байт, P/06.1; разбор ревью V/11, Claude С-9). Ключ считается от прочитанного, а не от числа попыток: `cas` строк в отпечаток не входит, отказ двери лежит в памяти консоли, снимает заявку только `412 row moved` (P/06.1 Н3 «память повторов», «пакет» шаг 5), поэтому шаг, построенный заново, и повтор после смерти исполнителя со сдвинутой строкой идут новым ключом. Повтор после
  потери ответа на тот же пакет приходит с тем же ключом, и консоль отвечает сохранённым ответом (B3, B9).
- «Без своего состояния» воркера (ADR-0094 A3) читается так: без состояния вне хранилища платформы. Процесс воркера
  своей памяти между запросами не держит, кроме кэша снимков таблиц домена (глава 3 Н1.2а): он только ускоряет, пропал — полное чтение, исход запроса от него не зависит.

### Н1.5 Групповая запись — по элементу

- `POST /devices` (разбор ревью V/11, Codex № 5, Claude С-6): элемент `items` `{device, domainId, parentId, folderId}` —
  создание устройства с дочерними одним пакетом (Н1.2), в кластере Н1.13 «Кластер новой записи»; `domainId` — `Domain.id` (Н1.6; иной — `NOT_FOUND`), `parentId` камеры
  — `null` или id `ipsrv` её хоста, детектора — id камеры, единицы — основная строка или единица (Н1.2), `acfa` — `null` или то же, прочих — `null`; иное — `failed` `PARENT_MISMATCH`, `field: parentId`; `folderId` не `null` — папка по Н1.7, в домене — отдельным шагом после устройства; `candidateId` — находка уходит из итога (Н1.9); вид вне
  `deviceTypes` — `failed` `NOT_SUPPORTED`, `field: type`; занятый `identifier` — `failed` `IDENTIFIER_TAKEN`, `field: identifier` (Н1.2). Итог — `{done: [{index, devices, folders}], failed:
  [{index, code, field?}]}`: `folders` — папка `folderId` после записи, иначе `[]`.
- `POST /devices/update`: каждый элемент `{deviceId, version, set}` — отдельная правка записи, свой пакет на устройство
  (Н1.2, Н1.3 с `version` элемента вместо `If-Match`; доп. (9) п. 3); итог — `{done: [Device…], failed: [{deviceId,
  code, field?}…]}`.
- `POST /objects/delete`: каждый элемент `{id, version}` — удаление записи своего вида со сверкой версии; вид — по имени
  UUID (Н1.6: `Archive` и `Volume` одной строки различаются id), правило — Н1.10, каскад — как у одиночного `DELETE` (Н1.2), пакет на
  объект; папка — дверью снятия папки с `If-Match` (Н1.7) и ключом шага (Н1.4), итог хранится в `steps` отдельной записью, `cas` строки `<h>`, как `failed`: обрыв между ними — повтор получает сохранённый 200, итог `done`; id `Volume` — `failed` `NOT_SUPPORTED`: том отдельно не снимается (глава 2 № 36); детектор камеры, снятой раньше в том же теле, — `done`. Итог — `{done: [id…], failed: [{id, code}…]}`. Серверы и домены так не удаляются (контракт).
- Элементы исполняются по порядку тела; отказ элемента не останавливает следующие; частичный успех — по элементам,
  элемент в `failed` не записан ничем, кроме чужого с `kept` (Н1.13). Память — Н1.4.
- Неответ шага (502–504, обрыв) — не итог: `failed` не пишется, группа останавливается, ответ — Н4, `<h>` остаётся
  `started`; повтор идёт тем же ключом шага (Н1.4).

### Н1.6 Id записи вида

- Id записей контракта — UUID. `backend` выводит UUID детерминированно — UUID версии 5 (RFC 9562, SHA-1) над
  пространством имён урока; имя — байты UTF-8 строки `<вид>:<кластер>/<место>` (разбор ревью V/11, вопрос 10; ADR-0110 доп. (5) п. 4): одна запись через
  любой `backend` получает один id, поэтому кластер стоит в имени и своих записей. `<кластер>` — `CLUSTER` члена, чья строка: у своей — свой, у чужой —
  поле `cluster` вида домена. У записи из строки хранилища `<место>` — ключ строки `<sub>/<rows>/<id>` или `<sub>/<таблица>/<имя>` как он записан, без нормализации
  (регистр, Unicode, `/` — как есть; ADR-0094 доп. (3) п. 10 (7)); `<вид>` — `device`, `archive`, `volume`, `candidate`, `rule`, `ruleVersion`; у записей
  без строки хранилища — перечень главы 3 Н1.2 (`server:`, `event:`, `ruleFire:`). `Archive` и `Volume` одной
  строки `rec/volumes/<name>` получают разные id.
- Записи домена одни на домен, кластера в имени нет (перечень главы 3 Н1.2): `folder:`, `user:`, ключи ролей и групп; так же постоянные `schedule:`, `mode:`.
- **`Domain`.** Имя — `domain:<root>`, `root` поля `domain` ответа `GET /session`: постоянный знак домена, id не зависит от входа, вида и связи. Поля нет — кластер вне домена, своя запись, `domain:<CLUSTER>`. `null` — домен не прочитан: `Domain` не выводится, 503 (глава 3 Н1.2а). 404 `no domain here` у `GET /domain` при поле `domain` — вид ещё не готов, только своё, id прежний. При входе кластера в домен `Domain.id` и `domainId` всех записей меняются один раз.
- Обратный путь — по перечню строк вида: свои — дверями кластера (у удалённой — по надгробиям камеры), чужие — по виду домена. Кластер вне домена — чужая запись не находится; связи нет — 503 (глава 3 Н1.2а).
- Ссылки (`parentId`, `archiveId`, `serverId`, `domainId`) — тем же правилом: кластер ссылки — кластер строки, на которую она указывает; поле строки называет ключ в кластере
  самой строки, если вид не говорит иного. Пространство имён — константа урока `BACKEND_NS` = `4ffc0b08-e8bd-4a4e-b7fb-d4ecc8a83ecb`.

### Н1.7 Папки

Папка — строка домена, у члена копия только для чтения (ADR-0110 доп. (5) п. 3; P/08.5 Н1.8, P/06.8 Н1.2а). Вне домена (в `GET /session` нет поля `domain`, Н1.6) она запись консоли кластера. Членство — забота платформы: `backend` переводит форму и хранит только правило скрытых членов (ADR-0096 §7).

- **Чтение вне домена.** `Folder` — элемент `GET /folders`, `GET /folders/<id>`: `id` — UUID v5 `folder:platform/folders/<id>`, `domainId` — `Domain.id`
  (Н1.6), `parentId` — id родителя или `null` при `parent: ""`, `version` — `index` строки, `deviceIds` — видимые члены по порядку.
  Обратный путь — по перечню `GET /folders`. Элемент `{id, garbled: true}` не отдаётся, а при чтении этой папки — 503.
  Id `deviceIds` вне перечня вида — 422 `VALIDATION_FAILED`, `field: deviceIds`, без обращения к двери.
- **Чтение в домене.** Дерево — `GET /domain/folders`, состав — копия `GET /folders`; поля — как выше, `parent` и `name` из дерева. Копия несёт только единицы этого кластера, поэтому `deviceIds` — только они, чужие единицы папки в ответе этого входа не видны: предел (P/06.8 Н1.2а). 403 двери `/folders` — своего нет, папки нет в копии — тоже: `deviceIds` пуст. `version` — hex SHA-256 индекса строки копии (строки нет — пустых байтов), точка, `index` дерева. Копия отстаёт на проход агента: новый состав виден со следующим ответом агенту, `version` меняется с ним.
- **Чтение без связи** — двери домена не отвечают (502–504, обрыв): дерево и состав из копии, `index` дерева в `version` пуст. Смена `version` при обрыве и возврате связи — ограничение.
- **Видимый член** — `cam/cameras/<id>` с пустым `main`, `det/units/<id>` из перечня единиц читателя; строка `type: ipsrv` видна как `ipsrv` своего хоста, из двух на хосте — наименьший id. Дети, строки `cam/device_units`, `channel`, `storage`, `ipsrv` без строки — не единицы, членами не бывают (P/06.8 Н1.1): такая запись в `deviceIds`, цель шага `folderIds`, `folderId` её создания — 422 `NOT_SUPPORTED`, `field` этого поля. `ipsrv` виден, если видна его строка, камера его хоста или ребёнок на его строке (ADR-0102 доп. (6) п. 6); канал виден вместе с ним. Члена вне перечня перевод считает скрытым: права нет или он
  удалён мимо двери, по отфильтрованному перечню их не отличить, а контракт велит не раскрывать невидимое (ADR-0096 доп. (1)). Дверь папки отдаёт члены как есть, чтение платформой
  не меняется.
- **Создание** — `POST /folders`, в домене `POST /domain/folders`, `{name, parent}`: `domainId` иной — 404 `NOT_FOUND`; `name`, пустое после снятия крайних пробелов, — 422 `NAME_REQUIRED`. Ответ в домене — чтением дерева.
- **Правка** (`PATCH`, `If-Match` — 428 без него) вне домена — `PUT /folders/<id>` с `If-Match: "<version>"`, поля `name`, `members`; `412 folder moved` — 412
  `VERSION_MISMATCH`, `current` из `row` ответа.
- **Правка в домене.** `If-Match` судится частью после первой точки против `index` дерева: копия о версии записи не судит; не равно — 412 `VERSION_MISMATCH`, `current` — чтение. `name` — `PUT /domain/folders/<id>` `{name}` с `If-Match: "<index>"`; `412 revision moved` — как `folder moved`. Состав — разница `deviceIds` с видимыми членами: на каждую единицу, по порядку тела, `PUT /domain/memberof/<кластер>/<ссылка>` `{folders}`, `If-Match: "<index>"`, `folders` и `index` — `GET /domain/memberof/<кластер>/<ссылка>`, плюс или минус эта папка; кластер — записи единицы, чужой тоже (Н1.6). Пары «папка + членство» нет (P/08.5 Н1.8): запись не одна, отказ останавливает, записанное остаётся, ответ — отказ Н4. Скрытых разница не трогает. Порядка в домене нет: перестановка записи не даёт. Ответ — чтение дерева, `deviceIds` — прочитанные с разницей: копия ещё не дошла.
- **Удаление в домене** — `DELETE /domain/folders/<id>` с `If-Match` по правилу правки; устройства остаются.
- **Дерево правит администратор домена** (P/08.5 Н1.8 `rights`, строка гранта кластера его не даёт): создание, `name`, удаление администратору кластера — 403 `PERMISSION_DENIED`, `params: {scope: "domain"}`. Состав он правит: правом на единицу и папку в своём кластере. Показ на чтении — глава 8 Н1.10.
- **Без связи** папку и членство не правят (ADR-0110 доп. (5) п. 3): двери домена не отвечают (502–504, обрыв) — 409 `SERVER_OFFLINE`, ничего не записано.
- **Скрытые члены** вне домена сохраняются: `members` — видимые в порядке `deviceIds`, а каждый скрытый член встаёт сразу за ближайшим видимым
  **перед ним** в прежнем списке, который остался, в прежнем порядке скрытых; такого нет — в начало списка. Состав читается из той же
  версии, что `If-Match`, поэтому член, добавленный мимо `backend`, не теряется: запись отвечает 412. Смена `version` папки от правки
  скрытого члена — ограничение: новая версия без видимого изменения.
- **Отказ цепочки** — 404 `NOT_FOUND` (ADR-0096 §7): предка нет, надгробие, 412 стража цепочки. В контракте `POST /folders` нет 409 и 412.
- **`folderId` создания в домене** (ADR-0111 п. 13) — два шага: до записи папка ищется в дереве, затем пакет устройства без строк папок (`400 badkey`, P/06.8 Н1.2а), затем `PUT /domain/memberof/<кластер>/<ссылка>` `{folders: [<папка>]}`, кластер — записи устройства. Двери домена не отвечают до записи — `failed` `VALIDATION_FAILED`, `field: folderId`, устройства нет; папки нет — `failed` `NOT_FOUND`, `field: folderId`. Отказ членства после пакета — устройство создано, `done` с `folders: []`, причина — в журнал воркера.
- **Шаг `folderIds` в домене** — `PUT /domain/memberof/<кластер цели>/<ссылка>` `{folders}`, список тела целиком, чтения прежнего не нужно, поэтому и у чужой цели; `Idempotency-Key` — `step_key(id, i)`, затем пакет итога (Н1.8). Цель судит страж держателя (P/08.5 Н1.8 `member`). Двери домена не отвечают — итог `fail` `SERVER_OFFLINE`.
- **`folderId` создания и шаг `folderIds` вне домена** — пакет B9 со строками папок и членства (P/06.8 Н2 «Строки папок в пакетной двери»): новый член
  в конец; `cas` — индекс строки папки, строка членства из `GET /folders?member=` (`member.index`), стражи — цепочка предков каждой добавленной
  папки и строка единицы, если её нет в `writes`. Строку папки или цепочку сдвинули — шаг создания строится заново (Н1.4). Порядок папок устройства не хранится (ADR-0096, «Запрос продукту» п. 1).
- **Вес каскада.** `DEVICE_FOLDERS_MAX` = 15: различных папок у камеры и её детекторов вместе (решения норм прав, п. 18). Удаление устройства
  пишет строку каждой такой папки; `FOLDER_ROW_MAX` × 15 с ключами частей входит в тело пакета `-max-body` 1 МиБ (P/06.8 Н1.3).
  `backend` держит предел при `folderId`, шаге `folderIds` и `PATCH /folders` по перечню `GET /folders`: сверх него — 422 `VALIDATION_FAILED`,
  `field: folderId`, `folderIds` или `deviceIds`. Две одновременные записи и записи мимо `backend` предел обходят: удаление такого
  устройства — 413, строка Н4, ничего не записано; снять его из папок и повторить.

### Н1.8 Групповая операция

Операцию ведёт консоль (P/06.9), шаг переводит и пишет `backend`. Таблица операций `service: true`: двери — только по билету, людям строк
`sub: backend` перевод не даёт, чужая операция — 404 `NOT_FOUND` (решения норм прав, пп. 21, 22).

- **Id.** `id` операции — 128 случайных бит, называет `backend`; в контракте — те же биты в форме UUID 8-4-4-4-12. Обратный путь —
  снятие дефисов.
- **Приём** `POST /operations`, по порядку (ADR-0095 §2):
  1. Память первой: строка `<h>` с `op: createOperation` создаётся «начато» `cas ""`, как Н1.4. Строка есть: чужие `user`, ключ, `op`, `body` —
     422 `VALIDATION_FAILED`, `field: idempotencyKey`; `state: done` — 202 с той же операцией (`operation` строки); `state: started` — приём
     идёт заново по той же строке, спор решает `cas` памяти в пакете приёма.
  2. Цели читаются снимком (Н1.3) и сверяются с `expectedVersions`: расхождение хоть одной — 412 `VERSION_MISMATCH`, ничего не создано. Шаг
     `set` или `folderIds` без версии цели в `expectedVersions` — 428 `PRECONDITION_REQUIRED` (чтение ADR-0095 §2; «Запрос продукту» п. 1).
     До снимка целей: шаг не ровно с одним из `set`, `folderIds`, `create`, пустой `items` — 422 `VALIDATION_FAILED`, `field: items`.
  3. `POST /backend/operations` `{id, items, memory}`: `items[]` — `{body, root, expected, secret?}`; `body` — элемент запроса без секрета;
     `root` — корень; `expected` — `{"versions": {<id объекта корня>: <версия>}}` по целям этого корня; `memory` — `{key: backend/repeats/<h>, fields:
     <строка с state: done и operation>, cas}`. Ответ — 202 `Operation`, итогов нет: `state` шагов — по P/06.9 Н2 (первый `run`, прочие `wait`).
  4. `409 root busy` — 409 `BUSY`, `412 row moved` с `field: /memory/cas` — другой исполнитель принял: перечитать строку и ответить, как `state: done`.
  Цель не найдена — 404 `NOT_FOUND`, ничего не создано: корень без неё не вычислить.
- **Корень** (ADR-0095 §1): `<cam>` — камера и строка `eventsrc`, `acfa`, у камеры и её детекторов один; `v-<name>` — строка тома, у `Archive` и `Volume` одной строки один;
  `ipsrv-<хост>` — `ipsrv`, `channel` и `storage`, `child-<id>` — ребёнок, единица — `<cam>` своей строки; у шага над сервером и доменом — `<вид>-<id>`. Строки корня: у `<cam>` — части камеры, у строки `eventsrc`, `acfa` — она; у `ipsrv-<хост>` — строка `type: ipsrv` хоста, её нет — карта пуста; у `child-<id>` — `cam/children/<id>` и `cam/child_settings/<id>`. Занятость и цепочка версий идут по корню.
- **Чужая цель** — Н1.13 «Шаг операции». Память, операция и стопка отката — у `backend` входа.
- **Занятые объекты** (ADR-0111 п. 20, заменяет в этой части ADR-0095 «`BUSY` проверяют только приём»). Пока операция не завершена, её объекты не меняют и другие запросы. Дверь консоли этого не судит (P/06.9 Н1.3), судит `backend`: пакет `PATCH`, `DELETE` устройства, хранилища, тома, потока (Н1.15), элемента `POST /devices/update`, `POST /objects/delete` идёт пакетной дверью и несёт на каждый задетый корень стража `{key: backend/opbusy/<корень>, index: ""}`, у каскада — корни всех снимаемых строк, у `DELETE` хранилища — ещё корни камер с записями на нём, у `DELETE` детектора — корни камер, что пишут по нему. `412 row moved` с ключом строки занятости — 409 `BUSY`, `params: {targetId}` — объект этого корня, у пакетных дверей — элемент `failed` с кодом `BUSY`, прочие элементы идут. Пакет шага этого стража не несёт: шаг идёт по своему корню. **Предел:** двери папок (P/06.8) стража не берут, поэтому состав и удаление папки под операцией не отказывают.
- **Шаг.** Консоль зовёт `POST /opstep` `{id, index, body, secret?, expected, opcount}` с `X-W2C-Pass-Ticket` по маршруту объявления (P/06.9 Н2 «Вызов шага»);
  тело ответа консоль не читает, поэтому ответ — 204 при любом исходе: исход — строка итога.
  1. **Сверка.** `expected` бывает двух форм. `{"versions": …}` — первый шаг над корнем: версии контракта, сверка как Н1.3. `{"rows": {<ключ строки>: <revision>}}` —
     цепочка корня: шаг после успешного шага; карта всех живых строк корня должна быть равна карте снимка. Версию контракта в цепочку положить нельзя: индекс
     пакета при его сборке неизвестен (P/06.1 «пакет»), а `revision` записанной строки предсказуем (файл решений, разбор ревью V/11, п. 1).
  2. `set` — как элемент `POST /devices/update` (Н1.5): снимок, пакет B9 с `cas` снимка и стражами частей; `create` — как элемент `POST /devices`, родитель —
     `targetId`; `folderIds` — Н1.7: состав папок цели становится списком тела, запись камеры не меняется; вне домена стражем идёт строка самой цели (P/06.8 Н3 шаг 7);
     пакету `folderIds` стражей частей нет места (P/06.8 Н1.3).
  3. В том же пакете — строка `backend/opdone/<id>/<i>` `cas ""` и `backend/opcount/<id>` с `cas` — значение `opcount` тела вызова шага (P/06.9 Н2). `versions` итога — карта `{"rows": …}`
     строк корня после шага: у записанной `revision` + 1, у новой 1, поверх надгробия — `revision` надгробия + 1 (`?deleted=1`), снятой нет, прочие из снимка. `version` итога — отпечаток этой карты: SHA-256 hex канонического JSON её значения (индекс пакета при сборке неизвестен, п. 1), наружу он не идёт; `created_id` — id созданного.
     `Idempotency-Key` — `step_key(id, i)` (P/06.9 Н2). `revision` снятой и созданной заново строки таблицы может вернуться (P/06.1 Н2 «Версии»): чужое снятие и создание
     той же строки внутри цепочки сверка не ловит, это ограничение.
  4. Отказ без записи (версия не та, `NOT_SUPPORTED`, `PERMISSION_DENIED`) — пакет из итога `fail` с кодом контракта и `field` и счётчиков, **без** ключа: `step_key` занят ответом
     пакета записи, а двойной итог отсекает `cas ""` (файл решений, разбор ревью V/11, п. 2).
  5. `412 row moved` — перечитать итог: есть — шаг окончен, нет — итог `fail`, код по Н4 (P/06.9 Н2). Заново шаг не строится: предел — у `create` версии нет, и `VERSION_MISMATCH` здесь значит «строка сдвинулась, повторить» (`retry-failed`). `412 leader moved` — закончить вызов, итога не писать: в память `step_key`
     этот ответ не ложится, это не исход шага (там же). Пакет лёг, а у нового вызова другой `opcount`: `cas` вне отпечатка пакета (P/06.1 Н3 «память повторов»), поэтому те же значения строк дают сохранённый ответ, шаг лёг; иные значения `opcount` — `422 key reused`: закончить вызов, итога не писать, итог читает консоль (P/06.9 Н3 «Гонки»), второго счёта нет. 5xx, обрыв, 401, `409 in flight` — закончить вызов, итога не писать (P/06.9 Н3 «шаг» п. 8); прочие 4xx — п. 4, код по Н4.
  6. `set` с `DomainPatch` — итог `fail` `NOT_SUPPORTED`: эта правка у нас `NO_ROUTE` (глава 2 № 6). `set` с `ServerPatch` — Н1.19, итог отдельной записью, в стопку не ложится; поле, кроме `labels`, — итог `fail` `NOT_SUPPORTED`.
- **Чтение** `GET /operations/{id}`: `GET /backend/operations/<id>`; `createdAt`, `finishedAt` — секунды в RFC 3339 UTC; `retryOf` — `retry_of` в форме UUID;
  `revertOf`, `redoOf`, `single`, `revertible`, `redoable` — Н1.12; `items[i]` — `{index: i, targetId, state, code, version?, createdId?, params?}`, `targetId` — из `items[i].body` ответа (P/06.9 Н2, при
  `service: true`), `code` — `code` итога или `null`. `version` — только у завершённой операции и только у последнего шага `ok` своего корня: `backend` читает цель снимком (Н1.1) и считает отпечаток карты строк корня; равен `version` итога — нынешняя версия цели, иначе поля нет: цель менялась после шага, а версия контракта на момент шага нигде не записана. `not_run` — `UPSTREAM_UNAVAILABLE` (глава 2 Н1.3). `params` — только у `BUSY` несовместимого детектора: итог шага полей подробностей не несёт (P/06.9 Н1.2), поэтому `field` итога — `incompatible:<id детектора>`, чтение даёт `params: {reason: incompatible, with}`, `field` наружу не идёт.
- **Управление:** `cancel`, `retry-failed` — двери консоли, `pause`, `resume` не переводятся (глава 2 № 40, 41), `revert`, `redo` — Н1.12, `409 operation done`, `409 operation running`, `409 nothing to retry` — 409 `BUSY`;
  у `retry-failed` `backend` называет новый `id`, памяти ключа нет: ключа в контракте нет (исключение стенда — глава 6 Н1.3). `cancel` исполняет ведущий на такте, а контракт отдаёт завершённую запись: после двери `backend` перечитывает операцию, пока не `state: done`, в пределах срока маршрута `api/operations`; срок вышел — ответ с прочитанным `state`.
- **Память и операция.** Числа равны, 86400 с, часы разные: `OPS_KEEP` считается от `finished_at`, срок строки `<h>` — от первого
  наблюдения её версии (Н1.4). Память может пережить операцию только на задержку наблюдения и период жнецов, если операция кончилась
  сразу: повтор ключа тогда получает 404 `NOT_FOUND` от чтения операции, спустя сутки при обещании контракта 10 минут. Операция может пережить память, она идёт до
  `OPS_RUN_MAX` и ещё `OPS_KEEP`: повтор ключа после срока памяти идёт как новый приём и получает 409 `BUSY` или 412 по версиям. Шаг, меняющий
  версию, дважды не исполняется ни там, ни там; операция только из `folderIds` версий не меняет: такой повтор — новая операция с тем же итогом.

### Н1.9 Поиск устройств и вопрос о модели

Поиск и вопрос исполняет базовый воркер `cam` на каждом сервере кластера входа ([V/01.8](../../01-cam/spec/01.8-cam.norms.md)): `backend` просит и сводит итог. Домен пути — `Domain.id` (Н1.6),
иной `domainId` — 404 `NOT_FOUND`. Запрос сервера не называет: поиск идёт на всех серверах кластера входа и видит их подсети; устройство сети другого кластера находится входом через него (ADR-0111 п. 9). Один поиск на вход. Права — двери таблиц (P/06.1 Н1.6): чтение `view`, запись `admin`, отказ — 403 `PERMISSION_DENIED`.

- **`GET`.** Читаются строка `cam/searches/<CLUSTER>` и таблица `cam/found`:

| Строка поиска | `state` | `progress` | `startedAt` | `finishedAt` |
|---|---|---|---|---|
| нет | `idle` | 0 | `null` | `null` |
| есть `stopped_at` | `stopped` | доля на `stopped_at` | `started_at` | `stopped_at` |
| сейчас ≥ `until` | `done` | 100 | `started_at` | `until` |
| иначе | `searching` | доля сейчас | `started_at` | `null` |

  Доля — целая часть 100 · (t − `started_at`) / (`until` − `started_at`), не меньше 0 и не больше 99.
- **Строка поиска не читается** — на всех трёх дверях 503 `UPSTREAM_UNAVAILABLE` (глава 2 Н1.3): это не `idle` и не свободный поиск.
- **`candidates`** — строки `cam/found` с `search` строки поиска, порядок — `found_at`, затем `h`. Не отдаётся: строка, которая не читается (строка лога); находка, чей `ip`
  равен `ip` камеры или `ipsrv` в `GET /devices` читателя: устройство заведено, новым не считается.
- **Кандидат.** `id` — UUID v5 `candidate:<кластер>/cam/found/<h>` (Н1.6): от поиска к поиску тот же, пока адрес и MAC те же. `type` — `camera`: вида драйвер не говорит. `name` — `<vendor> <model>`: имени
  драйвер не говорит. `mac` — поле строки, нет его — пустая строка. `vendor`, `model`, `ip`, `port`, `support` — поля строки (V/01.8 Н1.2). `login`, `password` не отдаются: поиск их не подбирает, пароль вводит оператор, `support: ok` значит «драйвер есть», а не «вошли».
- **`POST`.** Строка говорит `searching` — 409 `BUSY`. Иначе — одна строка таблицы в `POST /console/batch`, `cas` прочитанной, строки нет — `cas ""`: новый `search` (32 hex, случайно),
  `started_at` — сейчас, `until` — плюс `SEARCH_TIME` (V/01.8 Н1.1). 412 `row moved` — другой поиск начат раньше: 409 `BUSY`. Ответ — 202 `Discovery`: `searching`, `progress` 0, `candidates`
  пуст; прежний итог заменён, находки приходят потоком после ответа (глава 5 Н1.2).
- **`DELETE`.** Строка говорит `searching` — та же запись с `stopped_at` = сейчас, 412 — перечитать и судить заново. Иначе — без записи. Ответ — 200 `Discovery`; найденное остаётся.
- **`candidateId`** в `POST /devices`: устройство создаётся обычным пакетом (Н1.5), с `serverId` другого кластера — связкой, кандидат остаётся своим. После пакета строка `cam/found` этого `id` снимается `DELETE` с `cas`; строки нет или отказ — итог
  создания тот же, строка лога. В пакет снятие не входит: таблица воркера в пакете — 403 (P/06.1 Н2).
- **`POST /devices/probe`.** Тело по схеме контракта, иначе 422 `VALIDATION_FAILED`, `field`. `POST /cam/probes`: новый `id`, поля тела, `until` — сейчас + `PERFORM_TIMEOUT` (V/01.8 Н1.3). Затем опрос `GET /cam/probe_replies`:
  строка этого вопроса с `model` — `{model}`; ответили без `model` все серверы `GET /servers` на связи или вышел `until` — `{model: null}`. Строка, которая не читается, ответом не считается. Логина и пароля в запросе нет (предел V/01.8 Н1.3). Повтор — новый вопрос.

### Н1.10 Правила

Правило — строка единицы `auto/scenarios/<id>` и её отметки `auto/rule_marks/<id>` (`mute`, `order`), номер выдаёт счётчик `auto/next_id` (ADR-0105 п. 1). Сверка версии — Н1.3: версия — склейка двух индексов (глава 3 Н1.3), `If-Match` обязателен, 412 — с текущей записью. Пакет, пишущий одну из строк, стережёт другую. `backend` проверяет правило при записи; вычислитель судит то же проходом (V/07.3), этот суд не заменяется. Запись идёт пакетом B9 по билету: право — двери строк и таблиц.

**Предел:** при загрузке форма зовёт ещё `/rules/{id}/fires`, `/versions` на каждое правило: N запросов подряд, отказ журнала на непустой установке роняет старт. **Чтение на старте.** `GET /rules`, `/schedules`, `/day-groups`, `/modes`, `/modes/current`, `/maintenance-windows` объявлены, и WebUI зовёт их при загрузке, отказ роняет старт, поэтому пустая установка на них отвечает обычным 200: строк нет — пустой список и постоянные записи главы 3 Н1.3, живой вычислитель им не нужен. Отказ `403` двери таблицы — то же: часть не видна, отказа нет (Н1.1). `404` двери `auto` — подсистема не установлена — тоже. Прочий отказ — как чтение всякой части.

- **Список** — строки без `hidden` и выразимые в `Rule` (глава 3 Н1.3), порядок — `order` отметки, затем id числом. `garbled` не отдаётся, чтение такой строки — 503, как нечитаемая папка (Н1.7).
- **Проверка** (`RULE_INVALID`). `name`, пустое после снятия крайних пробелов, — 422 `NAME_REQUIRED`, `field: name`, при любом `enabled`. Выключенное правило хранится незаконченным, необъявленный шаг в нём — данные. У включённого — первая ошибка по порядку ниже: 422 `RULE_INVALID`, `params.issue` — `{code, params}`:

| Проверка | `issue.code`, `params` |
|---|---|
| `start: event`: нет триггеров; больше одного и `windowSec` 0; один и `windowSec` не 0 | `rule.noTrigger`, `rule.noWindow`, `rule.extraWindow` |
| `start: event`: триггер без цели; цель-область без устройства вида; `fromEvent` у триггера, у события `waitEvent` | `trigger.noTarget`, `trigger.areaEmpty`, `{kind}`, `trigger.fromEvent`, `control.fromEvent` |
| `start: schedule`: нет `runAt`, дней, времени | `rule.noRunAt` |
| условие `mode` без режимов; у правила чужого кластера: режимы — кластера входа; `output` с `pulse` без `pulseMs` | `cond.noMode`; `cond.modeOther`; `action.noPulse` |
| условие `time`: расписания нет; расписание пусто | `cond.scheduleGone`; `cond.scheduleEmpty`, `{scheduleId}` |
| условие с устройством: нет цели; область пуста | `cond.noTarget`, `cond.areaEmpty`, `{kind}` |
| ни одного действия во всём дереве | `rule.noAction` |
| глубина ветвления больше 2 | `rule.tooDeep` |
| шаг или действие вне справочников (глава 2 Н1.5) | `control.notDeclared`, `{control}`; `action.notDeclared`, `{action}` |
| `wait`, `waitEvent`: `sec` вне 1…3600; у `waitEvent` нет цели, область пуста | `control.sec`; `control.noTarget`, `control.areaEmpty`, `{control}` |
| номер входа, выхода расходится с записью цели (глава 3 Н1.3) | `trigger.portMismatch`, `action.portMismatch` |
| действие: нет цели; не задано поле; область пуста; `fromEvent` без устройства в событиях | `action.noTarget`, `action.field`, `action.areaEmpty`, `action.noEventDevice`, `{action, field?}` |
| `record`, `duration: event`: конца события в журнале нет (V/07.3) | `action.notDeclared`, `{action}` |
| `runrule`: сам себя; правила нет; `allowChain: false` | `chain.self`, `chain.ruleGone`, `chain.forbidden`, `{ruleId}` |
| шаблон `text`: неизвестная подстановка | `action.unknownVar`, `{action, name}` |
| цель с `gone` или с `id` без живой записи | `rule.targetGone` |

  Коды — те же, что подсказка WebUI; `*.notDeclared` — наши: у контракта нет системы, где шага нет, запрос об этом у «Консоли». `windowSec` больше 3600 — 422 `VALIDATION_FAILED`, `field: windowSec`: граница `within` (V/07.1). Сверх 4000 байт в поле `json` строки — 400 двери, 422 `VALIDATION_FAILED`, `field` по главе 3.
- **Кластер правила** (ADR-0111 пп. 8, 10). Правило живёт в кластере своих целей: чужой кластер — Н1.13. `serverId` выбирает кластер, цели другого кластера — 422 `VALIDATION_FAILED`, `field: serverId`; цели из нескольких кластеров — 422 `NOT_SUPPORTED`, `field: triggers`: такой сценарий — документ V/07.5, `Rule` его не выражает. Цель-папка цели не называет: кластер — `serverId`, поля нет — кластер входа.
- **`POST /rules`** — пакет: `auto/next_id` (как камера, Н1.2), строка `cas ""`, `auto/versions/<n>-1` с `note: {code: created, params: {}}`. строка отметки `cas ""`. `created_*`, `changed_*` — человек билета и момент, `mute: null`, `order` — наибольший `order` + 1: два одновременных создания могут получить один, порядок между ними — id. `412 row moved` по счётчику — пакет заново.
- **`PUT /rules/{id}`** — пакет: строка с `cas` снимка, поля вне содержимого — из снимка, `changed_*` новые; строка версии `number` — наибольший + 1, `note` — `historyNote`, без `params` — `{}`, нет — `null`. `historyNote.code: undo` с `params.number`, равным последней версии: её строка снимается в том же пакете, `changed_*`, `log_only_since` — из её `was`; версия записи всё равно новая.
- **`GET /rules/{id}/versions`** — строки `auto/versions` сценария по `number`. Строки живут, пока живо правило: срока нет. Чужое правило — глава 3 Н1.2а «Сверх вида».
- **`GET /rules/{id}/fires`** — `GET /events?subsystem=auto&unit=auto/<id>`, новые первыми (глава 3 Н1.3). Чужое правило — там же.
- **`POST /rules/update`** — групповая запись (Н1.4, Н1.5): элемент `{ruleId, version, set, historyNote?}`, пакет на правило. Нет — `NOT_FOUND`, версия — `VERSION_MISMATCH`, включение с ошибкой — `RULE_INVALID` без `params`: у элемента их нет. `log_only_since` — сегодня по `TIMEZONE`, когда правило входит в «только журнал», `null` — когда выходит. `mute` — `{since: сейчас, until, by, reason}` в строке отметки, `null` снимает; строка сценария при этом не пишется. Смена слова состояния (`off`, `watch`, `on`) и `historyNote` — строка версии, `note: {code: state, params: {mode}}`; приглушение версии не пишет. `changed_*` меняет только состояние.
- **`POST /rules/reorder`** — один пакет: только строки `auto/rule_marks` с `cas` снимка, строки сценариев — стражи; правило со своим `order` не пишется, версия остальных меняется. Нет — 404; версия не та, 412 пакета — 412 `VERSION_MISMATCH`, `current`, `params.ruleId`, ничего не записано. Больше `BATCH_WRITES` изменённых строк или `BATCH_GUARDS` стражей — 422 `VALIDATION_FAILED`, `field: items`: всё или ничего сильнее полноты.
- **`POST /rules/{id}/run`, `/fires/{fireId}/retry`** (ADR-0105 п. 10) — просьбы `run`, `retry` вычислителю сценария (V/07.4 Н1.12), `POST /auto/requests` по билету: только подача, право — `need` двери просьб, судится человек билета (P/06.3 Н1.9). Строки нет, `hidden`, не выражается в `Rule` — 404 `NOT_FOUND`; `fireId` нет среди сработок журнала этого правила — 404 `NOT_FOUND`; `enabled: false` — 409 `NOT_RUNNABLE`, `params.reason: {code: off}`, просьба не подаётся: держать выключенное вычислитель не обязан. Тело — `{unit, action: run}`, `{unit, action: retry, fire}`, `fire` — `firing`; `Idempotency-Key` — `idempotencyKey` тела. Дверь отвечает 202, пока исхода нет: подача повторяется тем же ключом до 200 с меткой, в пределах срока маршрута `api/rules`. Исход метки: `performed` — `reply.firing`, журнал читается до строки `fired` этой сработки, ответ 201 `RuleFire`; `refused`, `expired`, `gone` — 409 `NOT_RUNNABLE`, `params.reason.code` — `error` метки (`off`, `logOnly`, `refused`, `nothing`, `unread`), без него — слово исхода. `unknown`, срок вышел без метки или без строки журнала — 503 `UPSTREAM_UNAVAILABLE`: запуск мог пойти, на широкой цели `PERFORM_TIMEOUT` выходит раньше конца, исход неизвестен, повтор тем же ключом — тот же запуск. `409 exists`, `409 spent` — ключ занят иным телом: 422 `VALIDATION_FAILED`, `field: idempotencyKey`.
- **Ответ оператора** (V/07.6 Н1.9; ждёт контракта). Путь вне 106 операций: `POST /rules/{id}/fires/{fireId}/answer`, тело `{step, answer}`, `answer` — `yes`, `no`, `ack:<уровень>`. Перевод: `backend` читает сработку из журнала; нет — 404 `NOT_FOUND`; запуск не ждёт — 409 `NOT_RUNNABLE`, `params.reason.code: over`; иначе строка `auto/answers/<scenario>-<fire>-<step>-<user>`, номер сценария и имя сработки — обратным путём id, в `POST /console/batch`, `cas ""`, `user` — человек билета, судится он же. Он уже отвечал — 409 `BUSY`, `params.reason: answered`. Ответ — 202 без тела: роль судит вычислитель, исход виден в сработке. Роль человека `backend` не судит: у него один источник — строка `by`. До контракта форма пути не зовёт, приёмка `in` его не судит.
- **`POST /rules/test`** — `POST /auto/test/<id>` по билету (ADR-0105 п. 7): `ruleId` не `null` — его номер, нет строки — 404 `NOT_FOUND`; `null` — наименьший номер перечня `GET /auto/scenarios`, чью строку держит живой воркер (V/07.4). Тело — `{scenario, rule, events, at, branches, log}`, `rule` — черновик полями строки, проверки Н1.10 не идут; `log` без `ruleId` — 422 `VALIDATION_FAILED`, `field: log`. `RuleFire.id` — от `firing` ответа двери (есть при `log: true`), иначе случайный UUID, `ruleId` — как в теле. Держателя нет или строк нет — 503 `UPSTREAM_UNAVAILABLE`: пробовать некому. Право — `view` на строку (P/06.3 Н1.9).
- **Удаление** — элемент `POST /objects/delete`: снятие строки, отметки, её строк `auto/versions` и своих расписаний (`owner.kind: rule`), если они больше нигде не используются (Н1.11), одним пакетом; не вмещается — версии своими пакетами, строка последней. Журнал запусков остаётся.

**Каскад устройства** (ADR-0105, контракт). После пакета снятия устройства с дочерними, в том числе элементом `/objects/delete`, `backend` читает `GET /auto/scenarios`: элемент `include` `device` снятой записи уходит в `gone` её именем, такой же `exclude` снимается, строка пишется с `cas`, новая версия записи, строка истории не добавляется. Строки `auto/versions` этого правила правятся так же, в том же пакете, не вместились — следующими. У строки записи другой камеры детектор просто уходит из цели. `412` — перечитать и повторить, не больше трёх попыток. **Предел:** каскад идёт после снятия, не одним пакетом: правил может быть больше предела пакета. Отказ, обрыв или `403` права сценария (`cluster_rows`) исход снятия не меняют: строка лога, цель остаётся с мёртвым `id`, вычислитель судит её `target.deviceGone`, запись такого включённого правила — `rule.targetGone`.

### Н1.11 Расписания, группы дней, режимы, окна

Таблицы `auto` читает вычислитель, момент считает он один (ADR-0105 п. 2): `backend` не вычисляет, действует ли расписание. Запись — таблицы в пакете B9 с `cas`, версия — индекс строки, Н1.3. Таблицы эти — кластера входа: хранимой правкой не идут, чужая запись библиотеки — 422 `NOT_SUPPORTED`, `field: type`, вход через её кластер.

- **Встроенные** «Всегда», «Никогда» — `Schedule` с `kind` `always`, `never`, `builtin: true`, id — глава 3 Н1.2, версия `"1"`. `GET` отдаёт их и без строк. Запись, ссылающаяся на встроенное, несёт его строку `cas ""`, если её нет: вычислитель читает таблицу. `PUT`, `DELETE` — после сверки версии 409 `BUILTIN`.
- **`POST`, `PUT /schedules`.** `name` пустое — 422 `NAME_REQUIRED`, `field: name`; `owner` на нет правила или окна — 422 `VALIDATION_FAILED`, `field: owner`. `POST` — новый UUID, `builtin: false`, 201.
- **Где используется расписание** — режим, условие `time`, окно.
- **`POST`, `PUT /day-groups`** — то же без `owner`. **`DELETE /day-groups/{id}`**: группа уходит из `overrides` всех расписаний.
- **`GET /modes`** — глава 3 Н1.3. **`PUT /modes`** — `If-Match`, строки нет — `cas ""` при версии `"0"`. Пропал системный режим — 409 `BUILTIN`, `params.modeId`; `otherwise` не из `items` — 422 `VALIDATION_FAILED`, `field: otherwise`; пустое имя — 422 `NAME_REQUIRED`, `field: items`. Снятый режим уходит из условий `mode` правил (новая версия записи, версия истории не пишется), его ручное включение снимается.
- **`GET /modes/current`** — `manual`: строка `auto/mode_current/now`, её режим есть в списке, `until` нет или позже сейчас: `{until}`, иначе `null`. `modeId`: `manual` не `null` — режим строки; строки `modes` нет — `otherwise`; иначе — слово `object_mode` услышанного вычислителя с наименьшим слотом, из `GET /servers`; живого вычислителя нет или он поля не несёт (`unknown`) — `otherwise`: его слова нет, а форме нужен ответ при загрузке; момент считает только он, это предел. `GET /servers` не ответил, строка не читается — 503. Версии нет (контракт).
- **`POST /modes/current`** — `modeId` не из списка — 404 `NOT_FOUND`; значение — строка `now` с `cas`, `null` — снятие. Ответ — как `GET`.
- **`POST /maintenance-windows`** — один пакет: окно и расписание с `owner` — это окно. Ответ — 201 `{window, schedule}`. **`PUT`:** расписания нет — 422 `VALIDATION_FAILED`, `field: scheduleId`.
- **Удаление окна** — и его расписание, если больше нигде не используется.
- **Удаление расписания:** режимы — `schedule: null`, условия `time` и окна — встроенное «Никогда»; у правил новая версия записи, истории — нет.
- **Каскад — один пакет.** Не вмещается в `BATCH_WRITES` — зависимые строки своими пакетами, снятие или строка `modes` последней: обрыв оставляет объект живым, повтор доводит. **Предел:** между пакетами вычислитель видит часть правок. Правка задетой строки в окне — 412 — перечитать, не больше трёх попыток, иначе 412 `VERSION_MISMATCH`.

### Н1.12 Откат

Откат — только последняя неоткаченная операция автора, как кнопка undo: предыдущая откатывается только после неё (ADR-0106 с доп. (1)–(4); ADR-0111 пп. 18, 19). Платформа и запись не меняются; всё — своя таблица `backend/undo/<id>` (манифест). Пользователи, роли, гранты, папки, пароли, правила и таблицы `auto` вне отката, кроме строки `hidden: record`.

- **Что ложится в стопку.** Шаг операции, элемент `POST /devices`, `/devices/update`, `/objects/delete`, а также одиночные `PATCH`, `DELETE /devices/{id}`, `POST`, `PATCH`, `DELETE /archives`, `PATCH /volumes/{id}`, `POST`, `PATCH`, `DELETE /devices/{id}/streams…`, в том же пакете, что запись. Пресет и команда не ложатся: положения и исхода устройства назад не прочитать. `id` — операции; групповая запись — первые 32 знака `<h>`; одиночная — 128 случайных бит: операция из одного шага. Первая запись — `cas ""`, прочие — `cas` строки. Всё, кроме `POST /operations`, несёт `single: true`.
- **Строка.** Операция отката — строка с `revert_of` и пустыми `steps`, только для `revertOf` чтения, откатить её нельзя. Операция повтора — строка с `redo_of` и обычными `steps`, откатывается как всякая. Шаг: `index`, `target`, `root` (Н1.8), `rows` — на строку настроек оборудования `{key, op, born?, before, after}`: `cam/cameras`, `cam/child_settings`, `cam/device_units`, `rec/recordings`, `rec/volumes`, `det/units` и строка `hidden: record` смены `recordMode`; счётчики, замок, `backend/*`, строки операции не входят; `op` — `set`, `create` или `recreate`, `before`, `after` — изменённые поля без `*_secret`, у `create` `after` — все поля и `born`, у `recreate` (снятая строка `hidden: record`) `before` — все поля строки без `revision`, `after` нет. Только шаги с записью.
- **Слово `refuse` шага** ставится при записи и даёт `fail` отката: `volume` — у `rec/volumes` менялись `url`, его части, `quota_bytes`, `shrink_confirmed`: откат не должен стереть архив; `deleted` — строка снята: номер не повторяется; строка `hidden: record` слова не получает, у неё `recreate`; `bound_to` — менялось поле `bound_to`: пароль задаётся заново; `secret` — менялся `*_secret`; `folderIds` — папки вне отката; `view` — чужой шаг, поле вне вида (Н1.13).
- **Пределы стопки.** `UNDO_DAYS` = 7 суток — `delete_after`; `UNDO_KEEP` = 50: глубина отката, операции отката в стопку не входят. Новая строка — `GET /backend/undo`: сверх 50 строк без `revert_of` и сверх 100 строк всего старшие по `at` снимаются `DELETE` с `cas`, отказ — строка лога. Строка не вмещается в потолок хранилища (`413 row too large`) — `overflow: true`, `steps` пусты, откатить её нельзя: шаг важнее следа.
- **`POST /operations/{id}/revert`**, по порядку; всякий отказ — 409 `NOT_REVERTIBLE`, `params.reason`, кроме названных:
  1. Строки нет, срок вышел — `expired`; чужой `user` — 404 `NOT_FOUND`; не читается — 503.
  2. Строка с `revert_of` — `isRevert`; все ряды откачены — `reverted`; `reverted_by` называет незавершённую операцию отката — `running`; `overflow`, пустые `steps` — `empty`; есть младшая строка этого `user` без `revert_of` с открытым рядом — `notLast`. Операция отката завершена, а открытые ряды остались — откат можно повторить: неудачная попытка операцию не закрывает.
  3. Запись операции у консоли есть и `state` не `done` — `running`. Отменённая законченная годится: возвращаются выполненные шаги. Записи нет — операция одиночная или старше `OPS_KEEP`: законченная.
  4. `POST /backend/operations`: шаги — в обратном порядке, `body` — `{targetId, revert: {of, index}}`, `targetId` — цель шага, `root` — шага, `expected` — `{}`; `memory` — строка `<id>` с `reverted_by` — id этой операции отката, `cas` прочитанной: двойной клик не откатывает дважды, откаченным ряд делает только его шаг. `409 root busy` — 409 `BUSY`, `params.targetId`; `412 row moved` с `field: /memory/cas` — `reverted`. Ответ — 202 `Operation`, `revertOf` — `id`. Новая строка `backend/undo` ложится пакетом первого шага, `revert_of` — `id`.
- **Шаг отката** (`/opstep`, Н1.8, строка цели из снимка, `expected` не читается): `refuse` — итог `fail` `NOT_SUPPORTED`, слово — `field`. Проверка по значениям: строка `key` есть, каждое поле `after` равно текущему, у `create` ещё `born`; иначе `fail` `VERSION_MISMATCH`: правка мимо `backend` не затирается. Ряд с итогом `ok` получает `reverted: true` пакетом шага, ряд с `fail` остаётся открытым. Правка другого поля той же строки откату не мешает. `recreate` судится иначе: у камеры есть живая строка `hidden: record` — `fail` `VERSION_MISMATCH`: двух строк записи быть не должно; иначе пакет заведения Н1.2: `auto/next_id` с `cas` прочитанного, строка `auto/scenarios/<n + 1>` `cas ""` из `before`, первая строка `auto/versions`, номер наружу не выходит. Запись — `before` поверх снимка, `create` — снятие; пакет, замок, итог, счётчики — как шаг `set`.
- **Очередь повтора** этого `user` (ADR-0106 доп. (4)) — как redo редактора, по строкам `backend/undo` от младшей по `(at, id)`: строка с `redo_of` помечает цель повторённой; строка с `revert_of` называет цель; строка без обоих полей кончает обход: новая правка, попавшая в стопку, очищает повтор целиком, своей записи не нужно. Правка сервера в стопку не входит и повтор не очищает. **Верх очереди** — первая названная цель, не помеченная, с откаченным рядом.
- **`POST /operations/{id}/redo`**, по порядку; всякий отказ — 409 `NOT_REVERTIBLE`, `params.reason`, кроме названных:
  1. Строки нет, срок вышел — `stale`; чужой `user` — 404 `NOT_FOUND`; не читается — 503.
  2. `reverted_by` называет незавершённую операцию отката, цель очереди ниже верха — `notLast`; не верх и не в очереди (не откатывалась, очищена, уже повторена) — `stale`.
  3. `POST /backend/operations`: шаги с откаченными рядами в прямом порядке, `body` — `{targetId, redo: {of, index}}`, `root` — шага, `expected` — `{}`; `memory` — строка `<id>` с `redone_by` — id этой операции, `cas` прочитанной: двойной клик не повторяет дважды. `409 root busy` — 409 `BUSY`, `params.targetId`; `412 row moved` с `field: /memory/cas` — `stale`. Ответ — 202 `Operation`, `redoOf` — `id`. Новая строка `backend/undo` ложится пакетом первого шага с записью, `redo_of` — `id`.
- **Шаг повтора** (`/opstep`, строка цели из снимка, `expected` не читается). `set`: каждое поле `before` равно текущему, иначе `fail` `VERSION_MISMATCH`: чужое не затирается; запись — `after` поверх снимка. `create`: `fail` `NOT_SUPPORTED`, `field: created`: снятое не возвращается, номер новый; строка `hidden: record` заводится заново, как `recreate`, иначе `recordMode` разошёлся бы с записями. `recreate`: нынешняя строка записи снимается, если её поля равны `before`, иначе `fail` `VERSION_MISMATCH`. Новая строка несёт те же `before`, `after`; пакет, замок, итог, счётчики — как шаг `set`.
- **Чтение.** `GET /operations/{id}` записи консоли нет, строка `backend/undo` есть — `Operation` из неё: `state: done`, `createdAt`, `finishedAt` — `at`, шаги `ok`. Поля строки: `revertOf`, `redoOf` — `revert_of`, `redo_of` в форме UUID, нет строки — `null`, у операции без записанного шага `redoOf` — `redo.of` тела шага; `single` — поле строки, нет строки — `false`; `revertible` — `revert` прошёл бы шаги 1–3; `redoable` — строка — верх очереди и отката не идёт.
- **`GET /operations`** — перечень этого `user`, новые сверху: строки `GET /backend/undo` и строки `backend/repeats` с `op: createOperation`, чьего `operation` в `backend/undo` нет, запись каждой — как `GET /operations/{id}`; порядок — `at`, у строки памяти — `created_at` записи консоли; `limit` — 1…50, умолчание 50. Запись не читается — не отдаётся, строка лога. **Предел:** `retry-failed` без записанного шага в перечень не входит: строк у него нет. Откат и повтор идут строками перечня.
- **Чужой шаг** — Н1.13 «Откат».

### Н1.13 Запись чужого кластера

Своё пишется дверями Н1.2–Н1.12. У чужого двери нет: запись идёт хранимой правкой домена ([P/08.6](../../../Platform/08-domain/spec/08.6-domain.norms.md) Н1.3б, Н1.4; ADR-0110 доп. (4) п. 1), применяет её агент члена, точно судит консоль члена, по тому же человеку (договор права «Суд по цели» `write`). Перевод тела, проверки по `way` и слова отказа — те же, что у своей записи.

**Состояние — у входа** (ADR-0110 доп. (5) п. 5). `backend/repeats`, `backend/undo`, операции живут в кластере входа: consolem подключён к одному `backend`, другой — только при потере входа. На другом входе прежних операций нет, а тот же `idempotencyKey` исполнится заново: после 5xx и смены входа запись перечитывается.

**Вход.** `need` входа — грант в любом кластере домена (ADR-0110 доп. (5) п. 5): строка `domain/anywhere` договора права. Вошедшему по `anywhere` без прав на своём кластере своего нет (глава 3 Н1.2а): новая запись без `serverId` идёт в кластер входа и получает 403 его двери.

- **Кластер новой записи** (ADR-0111 п. 8). `POST /devices`, `POST /archives`, `POST /rules`: кластер — член сервера `serverId` по обратному пути Н1.6, поля нет — кластер входа; сервера нет в перечне вида — `NOT_FOUND`, как у `POST /archives`. `parentId` — запись другого кластера: кластер родителя, `serverId` другого кластера при этом — `PARENT_MISMATCH`, `field: parentId`. После создания у `camera`, `ipsrv`, `acfa`, `det` `serverId` — наблюдение (глава 3 Н1.1). `serverId` камеры без назначения — поля нет.
- **Строки.** Запись устройства — одна правка: `POST /domain/edits {cluster, writes}`, `cluster` — член цели, `writes` — те же строки, что пакет Н1.2 (ADR-0111 п. 16). `cas`, стражей, замка `cas`, `backend/opbusy`, строк `<h>` и `backend/undo` в связке нет: `base` и применение всего или ничего держит платформа. Строка единицы — `{op, sub, rows, id, fields}`, `id` — `key` строки снимка таблицы вида: без `ref` строку адресует пара (`cluster`, `id`), поиска нет, `siblings` не мешают, а `domain.ref` не нужен, поэтому так же правятся детектор, правило, `ipsrv`, `eventsrc`, `acfa`, поток. `put` единицы без `create`, `new` — только по живой строке, иначе исход `refused`: части, которой в снимке нет или которая снята, — `create: true`, у `unit.id: numeric` — `new`. Строка таблицы — `{op, sub, rows, name, fields}`, `fields` — строка целиком: поля снимка, поверх — тело. Новая строка таблицы — тот же `put`: `create`, `new` — слова единицы. Часть с `about` идёт со строкой камеры: не меняется — `fields: {}`. В `fields` единицы — только изменённые поля.
- **Что шлёт связка.** Единицы: `cam/cameras` (камера, `ipsrv`, `eventsrc`, `acfa`, поток), `rec/recordings` — по `domain.ref`; `det/units`, `auto/scenarios` — по `domain.edit`, снятие — по `domain.edit_delete` манифеста. Таблицы `domain.edit_tables`: `cam/child_settings`, `cam/device_units`, `cam/unit_next`, `rec/volumes`, `auto/versions`, `auto/rule_marks`. Поля — списки этих слов. Иных строк нет: чего в них нет, чужой правкой не пишется.
- **`base`.** Правка по id берёт `revision` строки шарда копии, иначе снимка таблиц (P/08.6 Н1.3б). Все строки выше — в `domain.view_tables`, кроме `auto/versions`: новая строка `base` не несёт, а снятая при `historyNote` и удалении правила затирает локальную правку, это предел. Так же у таблицы со снимком `refused`.
- **Создание.** Строка камеры — `{new: true, op: put, sub: cam, rows: cameras, id: "$id", fields}`, `ref` — `<кластер>-$id` (ADR-0111 п. 3), записи — `{create: true, id: "$id"}`, `{create: true, id: "$id-<том>"}`, поле `cam` — `$id`. Номер выдаёт агент, исход несёт его полем `made`: из него `backend` строит id записи. Прочие вида с `unit.id: numeric` — так же, детектор — `{create: true, id: "$id-<kind>"}`, второй вида — с номером, правило — `{new: true, sub: auto, rows: scenarios}`, `auto/rule_marks/$id` и `auto/versions/$id-1` той же связкой. `new` в связке один: создание камеры с `recordMode: motion` — две правки, строка записи после `made`; копия `template` с потоками — 422 `NOT_SUPPORTED`, `field: templateId`. `identifier` судится по снимку. Том — связкой: новая строка таблицы `rec/volumes`, `put` по `name` (P/08.6 Н1.3б); единица — `cam/unit_next` с `n + 1` по снимку и `cam/device_units/<строка>-<n + 1>`, одной связкой; счётчик сдвинули — исход `conflict`.
- **Ключ.** `Idempotency-Key` одиночной правки — hex SHA-256 от `edit`, нулевого байта, `user`, нулевого байта, id записи, нулевого байта, `If-Match` и нулевого байта с SHA-256 тела без полей `edit_secrets`: ключ лежит открыто в `domain/pending` и `carry`, производного от секрета в нём быть не должно. Повтор той же правки находит прежнюю (P/08.6 Н1.4 `repeat`). Секрет в теле — ещё 128 случайных бит: повтор с секретом — вторая правка с тем же значением, безвредно. У элемента групповой записи — ключ шага Н1.4 без прочитанного, у шага операции — `step_key` (P/06.9 Н2).
- **Секрет.** `password`, `secret` тела уходят открытым значением только в теле двери, полем `edit_secrets` манифеста (`cred_secret`, `access_secret`): запечатывает ключом члена процесс `domain` (P/08.6 Н1.3а). В `backend/repeats` и `backend/undo` его нет. Адрес с учётными данными дверь отказывает: логин идёт полем.
- **Отказы двери** до приёма — строки Н4, ничего не хранится. `409 kept_full` — 409 `BUSY`, `params.reason: kept_full`: член не успевает.
- **Ответ.** Чтение и сверка — как Н1.3. Член цели в виде не `ok` — 409 `SERVER_OFFLINE`, `params.targetId`, правка не подаётся: принятую правку не отменить, а молчащая коробка применит её неизвестно когда. У групповых — `failed`, у шага — итог `fail`. Иначе подача, `202 {kept}` — ожидание исхода в пределах срока маршрута: опрос `GET domain`, элемент `outcomes.<член>` с `id` = `kept`, затем чтение заново.

| Исход | Ответ |
|---|---|
| `performed` | 200 записи вида, новая версия; вид отстаёт — чтение повторяется в том же сроке |
| `conflict` | 412 `VERSION_MISMATCH`, `current`: запись на члене поменяли после приёма |
| `refused`, `status` 403 | 403 `PERMISSION_DENIED` |
| `refused`, `status` 404 | 404 `NOT_FOUND` |
| `refused`, прочее, в том числе `status` 0 | 422 `VALIDATION_FAILED` без `field`: `error` исхода — фраза, код из неё не выводится (Н4) |
| срок вышел | 409 `SERVER_OFFLINE`, `params: {targetId, kept}`: правка хранится и применится, не применена она только сейчас. Повтор той же правки новую не заводит и ждёт её исход; новая версия даст 412 |

  Хранимая правка не отменяется (ADR-0111 п. 16): откат — новая правка. Групповая запись подаёт элементы по порядку, ждёт одним сроком на всю группу; элемент без исхода — `failed` `SERVER_OFFLINE`, итога в `steps` нет, `<h>` остаётся `started`: повтор ключа доводит его (Н1.4, отказ `SERVER_OFFLINE` до подачи — обычный итог).
- **Шаг операции.** Подача в шаге, ожидание в пределах `OPS_STEP_WAIT`, исход — итог: `performed` — `ok`, `versions` — карта `{"rows": …}` `revision` строк вида, прочие — `fail` по таблице выше. `expected.rows` чужого шага не сверяется: порядок держит `base` и `same_path` (P/09.1 Н1.5), вид отстаёт. Срок вышел — кончить вызов, итога нет (Н1.8 шаг 5), консоль вызовет шаг снова, тем же ключом. **Предел:** после `OPS_STEP_TRIES` итог `fail not_run`, а правка всё равно применится. Секрет шага — как выше.
- **Откат.** Строка `backend/undo` чужого шага ложится после исхода `performed` отдельной записью: пакета с записью нет, обрыв между ними оставляет шаг вне стопки. `rows` — поля снимка таблицы вида до и после; поле вне `domain.view_tables` — слово `refuse` `view`. Шаг отката — новая связка `before` поверх снимка, шаг повтора — `after`, проверка по значениям — по виду, с его задержкой.
- **Занятость.** Строки `backend/opbusy` другого кластера страж не видит, связка стражей не несёт: чужая операция над той же записью судится только `base`, исход `conflict`. Удаление камеры снимает потоки, записи, детекторы и строку записи той же связкой. Каскады Н1.2, Н1.10 — так же, не вмещается — 422 `VALIDATION_FAILED` без `field`; правила другого кластера каскад снятия не правит: цель с мёртвым `id` судит вычислитель (Н1.10).
- **Только через свой кластер.** Включение камеры, выключенной правилом (Н1.2), — просьба `cam`: чужой дверью не идёт, `enabled` — 422 `NOT_SUPPORTED`, `field: enabled`. Таблицы Н1.11 — так же. Поле `server` единицы дверь отказывает как платформенное: чужое правило его не хранит, `serverId` только выбирает кластер. Строка `auto/versions` идёт связкой и члену за NAT: номер — `revision` строки сценария в снимке + 1, он больше прежних номеров, историю читать не надо, снимок отстал — `conflict` всей связки; номера идут с пропусками. Чтение истории — глава 3 Н1.2а. `run`, `retry` чужого правила — просьбы: 409 `NOT_RUNNABLE`, `params.reason.code: otherCluster`. `apply` — групповая операция по кластерам (ADR-0111 п. 12): V/11.8.
- **Живое, пресеты, поворот, команда** (ADR-0111 п. 11). Запись другого кластера отвечает 422 `NOT_SUPPORTED`, `field: type`, ссылкой на вход через её кластер, `params.url` — `members[].url` вида: только https без учётных данных, незрителю домена только у кластеров с его строкой. Поля нет — ссылки нет: член за NAT, или кластер не его. Камера w2c за NAT: живое — из шлюза кластера приёмника, движение арендой недоступно, пресет идёт просьбой `cam`, а не строкой: дверью правки не проходит.

### Н1.14 Приём в домен и приёмник

- **Приём** (ADR-0110 доп. (6)). Элемент `POST /servers/assign` `allocated: true` — стучащийся из `knocking` (глава 3 Н1.3 «`Server`»): `POST /domain/members {name, fingerprint}`, `version` элемента равна `fingerprint`, иначе `failed` `VERSION_MISMATCH`. Отказ держателя 409: потолок серверов, нет хранителей, строка раздела полна — `failed` `NOT_SUPPORTED`, `message` — слова держателя; 429 `busy` — `failed` `BUSY`. Сервер в кластер заводит установщик, `join` с закреплением корня — подготовка коробки.
- **Исключение** (ADR-0111 п. 17). `allocated: false` — член сервера находится по виду (глава 3 Н1.2а), `version` элемента сверяется с записью `Server`, иначе `failed` `VERSION_MISMATCH`; затем `GET /domain/members/<член>` и `DELETE /domain/members/<член>` с `If-Match` — `ETag` этого чтения: член целиком (P/08.3 Н2, P/10 Н1.2б). Сервер члена с несколькими серверами — `failed` `NOT_SUPPORTED`. 400 держателя — `failed` `NOT_SUPPORTED`, 404 — `NOT_FOUND`, 412 и 409 `the list of members kept changing` — `VERSION_MISMATCH`, неответ — Н4. `done` — запись сервера с `allocated: false`.
- Обе двери судит `admin` домена, а не грант кластера: 403 — `failed` `PERMISSION_DENIED`, хотя права на кластер есть. Память — Н1.4, `op` — `assignServers`. Операция не объявляется, пока контракт не несёт отпечаток и подтверждение сверки (глава 3 Н1.3 «`Server`»): отпечаток, взятый `backend` из вида, сверкой человека не служит, а без неё в домен входит чужая коробка.
- **Приёмник** (ADR-0111 п. 5). Операции в закреплённом контракте нет (`Device.recordingTarget` — черновик). Перевод: `PUT /domain/placement/rec/<ref> {cluster, origin, copies}`, `If-Match` — `rev` записи, `origin` — кластер камеры, `cluster`, `copies` — кластеры серверов приёмника; вместе с назначением — строка `rec/recordings/<cam>` в кластере приёмника связкой (Н1.13): строки назначение не создаёт (V/02.9 Н1.1).

### Н1.15 Потоки камеры и живое видео

Поток — строка `cam/cameras` (глава 3 Н1.3 «Потоки»). Цель не `camera` — 422 `NOT_SUPPORTED`, `field: type`; потока нет — 404 `NOT_FOUND`. `If-Match` у этих операций нет (контракт): снимок читается, версия не сверяется, дальше — пакет правки камеры (Н1.2): замок, `cas` снимка, стражи частей, страж занятости (Н1.8), строка `backend/undo` (Н1.12). 412 пакета — снимок заново, не больше трёх попыток, иначе 409 `BUSY`: у операции нет 412. Ответ — камера целиком, `ETag`.

- **`POST`.** `name` пустое — 422 `NAME_REQUIRED`, `field: name`. Строка: номер — счётчик `cam/next_id`, как новая камера, `main` — id камеры, `profile` — `name`, `resolution`, `fps` — тело. Адрес — `source` камеры с параметром `stream=<k>`, `k` — наименьшее целое ≥ 1, не занятое потоками камеры; адрес камеры не `ipint://` — 422 `NOT_SUPPORTED`, `field: type`: второго адреса `backend` не выводит. Адрес занят (`unique`) — следующий `k`. Сверх `DEVICE_PARTS_MAX` — 422 `VALIDATION_FAILED`, `field: name`. Ответ 201.
- **`PATCH`.** `name` — `profile`, `res`, `fps` — как поля камеры (глава 3 Н1.3). Основной поток — та же запись, что `PATCH` камеры без `If-Match`.
- **`DELETE`.** Основной — 422 `NOT_SUPPORTED`, `field: streamId`. Строка `rec/recordings` или `det/units` этой камеры с `stream` = id потока — 422 `VALIDATION_FAILED`, `field: stream`. В стопке — слово `deleted`.
- **Чужая камера** — связкой Н1.13, поток — строка с `new`; занятость — только `base`.
- **`POST /devices/{id}/live`** (ADR-0112 доп. (1)). Цель не `camera` — 422 `NOT_SUPPORTED`, `field: type`; нет связи — 409 `DEVICE_OFFLINE`. `GET /live/where/<cam>` по билету, право — `view` на камеру: `door: {url, token, expires, routes}` (V/03.3 Н1.1). Ответ: `whepUrl` — `<url>/whep/<cam>?width=<ш>&height=<в>`, поток по размеру выбирает шлюз (V/03.3 Н1.2); `token`, `expiresAt` — `expires` в RFC 3339. Токен идёт через `backend` один раз: в журнал и строки не попадает. Ответ `/where` без `door` — 409 `DEVICE_OFFLINE`. Раздачи нет, двери шлюза нет (404, 503 двери) — 409 `DEVICE_OFFLINE`. Чужая камера — Н1.13.

### Н1.16 Поворот и пресеты

Предмет — камера с `ptz` (V/01.4 Н1.4г). Перед записью: цель не `camera` — 422 `NOT_SUPPORTED`, `field: type`; дальше, кроме имени пресета и `DELETE` пресета: `ptz` ложь — 422 `NOT_SUPPORTED`, `field: ptz`; нет связи, `can` не сказан — 409 `DEVICE_OFFLINE`. Право — `edit` на камеру, отказ — 403 `PERMISSION_DENIED`. Камера выключена правилом: просьба — отказ держателя, ниже; поворот — успех записи, строка `ptz_moves` лежит, камера стоит, слово в `ptz_reason` пульса.

- **`PUT /devices/{id}/ptz`** — строка таблицы `cam/ptz_moves/<camera>-<person>`: `POST` двери таблиц без `cas`, полная замена, `camera`, `person` — человек билета, `seq` — миллисекунды часов воркера: растёт с каждым продлением, `pan`, `tilt`, `zoom`, `focus` — значение контракта × 100, до целого, нет поля — 0. Имя человека не годится ключу таблицы (V/01.4 Н1.4г) — 422 `NOT_SUPPORTED`, `field: ptz`. Ответ — `{expiresAt}`: сейчас + `ttlSec`. Срок держателя один, `PTZ_LEASE` = 5 с: `ttlSec` меньше него камеру раньше не останавливает, это предел. `DELETE` снимает строку, 404 двери — тоже 204. Двое на камере — V/01.4 Н1.4г.
- **Просьба устройству** — `POST /cam/requests` по билету (P/06.3 Н1.9), `Idempotency-Key` — 128 случайных бит запроса, подача повторяется тем же ключом до 200 с меткой, в пределах срока маршрута `api/devices`. Исход: `performed` — успех; `refused` со словом `no such operation` или `unit needs n and an operation` — 409 `DEVICE_REFUSED`, `params.reason: noOperation`; прочий `refused` — 409 `DEVICE_REFUSED`, `params.reason: refused`; метки нет к сроку, `expired`, `gone`, `unknown` — 409 `DEVICE_OFFLINE`.
- **`PUT /devices/{id}/presets/{n}`.** `PUT {}` — просьба `{unit: <cam>, action: preset_save, n}`; после `performed` строки `cam/preset_labels/<cam>-<n>` нет — создаётся с пустым `label`, отказ устройства строки не оставляет. `PUT {name}`, пустое тоже, положения не трогает никогда: строки нет — создаётся, `name` ложится в `label`; есть — `label` заменяется, пустое снимает подпись, строка остаётся. Запись имени не идёт устройству: связь и `ptz` её не судят; пакет с `cas`, у чужой камеры связкой Н1.15. Строку снимает только **`DELETE`**, всегда и первой; затем `preset_clear` при `ptz`, связи и своей камере. Иначе просьбы нет, 200, положение в камере остаётся: это предел. Просьба отказана — 409 `DEVICE_REFUSED`, строка уже снята. Номер с именем драйвера остаётся в `presets`, пока драйвер его называет. Граница `n` судится только при сказанном `can`: `n` больше `can.presets` — 404 `NOT_FOUND` у обоих; станет `presetMax`, когда поле придёт в форк. Ответ — камера целиком, `ETag`; строки таблицы в `presets` свежие, имена драйвера идут из пульса и отстают на его период, это предел.

### Н1.17 Команда единицы

`POST /devices/{id}/operations/{operation}` — просьба устройству (Н1.16) `{unit: <camera строки>, action: unit, n: <n строки>, operation}`. Цель — запись `cam/device_units` не `type: det`, иная — 422 `NOT_SUPPORTED`, `field: type`. Нет связи — 409 `DEVICE_OFFLINE`, до просьбы. Ответ — `{done: true}`. `Device.operations` — подсказка, судит держатель: `operation` вне неё всё равно подаётся.

### Н1.18 Учётки потоков

Дверь шлюза `/live/accounts` (V/03.6 Н1.2) по билету, судится человек билета: `need` двери, `view` на что-либо — чтение, `admin` на `*` — запись (ADR-0112 доп. (1)).

- `GET` — `GET /live/accounts`, элемент — `{name, disabled, at, by}`, `at` — RFC 3339. `POST` — `{name}`, 201 `StreamAccountSecret`. `PATCH` — `PUT /live/accounts/<имя> {disabled}`. `DELETE` — 204. `POST …/password` — `StreamAccountSecret`: `name` — `account.name`, `password`. Тело `StreamAccountSecret` не логируется и не держится дольше ответа, ответ несёт `Cache-Control: no-store`. **Предел:** `POST …/password` не идемпотентен: сбой ответа теряет пароль, новый уже действует.
- **Пароль** идёт через `backend` один раз: только в ответ; в журнал, строку, `backend/*` и лог не попадает.
- **Отказы:** имя пустое после снятия крайних пробелов — 422 `NAME_REQUIRED`, `field: name`; `400 bad name` — 422 `VALIDATION_FAILED`, `field: name`; `409 name taken` — 409 `NAME_TAKEN`; `404 no such account` — 404 `NOT_FOUND`; 401, 403 шлюза — 403 `PERMISSION_DENIED`; подсистемы нет, шлюза не слышно, 502, 503 — 503 `UPSTREAM_UNAVAILABLE`.
- Сообщение потока `streamAccounts` не шлётся: таблица в ленту не идёт (глава 5 Н1.2). Учётки — кластера входа.

### Н1.19 Метки сервера

`PATCH /servers/{id}` (ADR-0112 доп. (1)): `If-Match`, 428, 412 — Н1.3, версия — глава 3 Н1.3 `Server.version`. Пишется только `labels`: `PUT /servers/<имя>/labels {labels}` (P/06.6), `null` — `DELETE`: снова действуют метки узла. Прочее поле тела — 422 `NOT_SUPPORTED`, `field` этого поля, раньше записи; `name` и `ip` — так же. Метка не по азбуке, повтор — 422 `VALIDATION_FAILED`, `field: labels`. Сервер другого кластера, стучащийся — 422 `NOT_SUPPORTED`, `field: type`: дверь у консоли его кластера. Метка `server:*` — слово `serverId` (глава 3 Н1.3): запись её сохраняет. Ответ — запись `Server`, `ETag`. В стопку не ложится и повтор не очищает (Н1.12). Смена меток двигает размещение следующим проходом: ответ `will_move` наружу не идёт.

## Н5 Приёмка

Тесты API consolem (`tests/api-hardware.js`, `api-devices.js`, `api-domains.js`, `api-bulk.js` на закреплённом коммите) против
стенда в профиле возможностей (глава 6); до приращения платформы — чтением.

Чего они не видят, проверяет [`acceptance/4/`](../acceptance/4/README.md) (ADR-0094 доп. (17), (18)): отказ обычному человеку, скрытое, память `backend/repeats` и перезапуск воркера,
операции профиля без теста `in` (глава 6 Н1.2), дерево устройства (`11-devices`), поиск и вопрос о модели на двойнике (`14-discovery`, `15-probe`), правила (`17-rules`), библиотека (`18-schedules`), откат (`19-revert`), запись по детектору (`20-motion`), чужая запись (`22-foreign`), потоки (`24-streams`), поворот и пресеты (`25-ptz`), команда (`26-unit-op`), журнал (`27-journal`), повтор и перечень операций (`28-redo`), живое и учётки (`30-live-accounts`), метки сервера (`31-server-labels`).
