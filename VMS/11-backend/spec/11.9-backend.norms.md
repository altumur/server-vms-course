# V/11.9 — The turn loop: norms

This English text is the source; the Russian translation `ru/spec/11.9-backend.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 9 of lesson V/11 «Configurator backend», the assistant (ADR-0080; the VMS module — ADR-0090; the subsystem — ADR-0093 items 3, 5, 8, addendum (1)
items 2, 4, addendum (3) items 1, 3, 6, addendum (4) items 1, 2, 6, 7). Lecture (`ru/11-backend.md`, for people, not in the export), [instructions](11-backend.README.md). The platform is pinned by [`VMS/PLATFORM_PIN`](../../PLATFORM_PIN) (ADR-VMS-0002).

`backend` leads the turn, not the model and not the console: the loop is only here (ADR-0093 addendum (8) item 2), the page panel is removed. `backend` sends steps to the model door (V/10.2) and gives out the result by the stream (chapter 7). In the working branches it executes the model's read calls through console doors by ticket (chapter 10) and checks a proposed plan (chapter 11). The separate `learn` branch selects a delivered chapter without working reads or a working plan (N1.7). The model answers only with a call from the chosen branch's closed set. The working harness — the system text, the tool descriptions, the loop policy — was handed over by the pilot (ADR-0093 item 8, addendum (3)): its basis is the tools v4.0 and `tool_choice: required` (56 of 60 requests of the pilot's suite, not a single parse failure at the model server). The chapter sets norms for the turn, the step messages, the parsing of the model answer, the turn outcomes and the life of the turn.

Norm ids are `V/11.9-MM`.

## N0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../Platform/common/NORMATIVE-TERMS.md). The rules of the module «Platform» are [P/01.1 N0](../../../Platform/01-store/spec/01.1-store.norms.md#n0-vocabulary).

- **Turn** — from the admin's text (the request) to the outcome of its type (chapter 7): the working outcomes of N1.5, the learning result of N1.7, «turn not completed» or a cancellation.
  A question of the model (`ask_admin`) does not end the turn; it ends the HTTP request: the stream is closed with the event `question`, the admin's answer is a new HTTP request with the `context` of the question (chapter 7 N1.2; ADR-0093 addendum (6) item 2).
- **Texts of the turn** — the request and the admin's answers to `ask_admin` of this turn, as the person entered them: `backend` records the text from
  the person's input, not from the model's output (ADR-0093 addendum (3) item 1); chapter 11 reconciles «named» against them for a working plan. The words of `backend` (the overview, the message about secrets, the loop hints) and the words of the model are not part of
  the texts of the turn.
- **Model call** — one step of the model door that has reached the model's answer (`done`, V/10.2 N1.3).

## N1 Form

**Data.** The chapter has no families of its own. The turn lives in the memory of `backend` for the duration of the HTTP request, between HTTP requests — in `context` at the client: the texts of the turn, the message history and the model's answers
go neither into the console store nor into logs. The working harness below is lesson data, not code of `backend`. It is not the learning prompt or learning tool set (N1.7):

| File | What | How `backend` takes it |
|---|---|---|
| [`harness/system.md`](../harness/system.md) | the system text (in English, as in the pilot's measurement) | the bytes as is — the content of the only `system` message of the step |
| [`harness/tools.json`](../harness/tools.json) | the tools: name, description, argument schema (chapter 10 N1.1) | `tools` of the step — N1.2 |
| [`harness/words.json`](../harness/words.json) | the locale data of the check and of the loop (chapter 10 N1.4, chapter 11 N1.2) | chapter 11 |

`backend` carries the harness as the bytes of these files; the harness is edited by editing the files.

The differences of this working harness from the handover package (the measurement is of the pilot's package; ADR-0093 addendum (3) item 6, addendum (4) item 7) are the **post-measurement edits**,
the listing is from the lesson README:

1. The cluster overview is the first `user` message, not in `system`.
2. The secret label is `{"secret": N}` and the message «Secret N is entered» instead of a text slot; `system.md` and the note of
   `get_manifest` are about the label.
3. The admin's answer is the result of `ask_admin`, the turn does not end with it; the description of `ask_admin` and `system.md` say the same.
4. Tool names are without the pilot's prefix; `system.md` — «Use only the tools you are given».
5. The description of `list_table` has an example of the table `rec`; `tools.json` ends with a newline.
6. A call written as text is not executed; a hint without a call counts toward 25 (addendum (4) item 6).
7. The reconciliation «named» is strengthened (addendum (4) items 3, 5): the names `named` and rows — «name in the text», a word shorter than 4 letters — whole
   or with an ending from `endings` (the Architect's decision on the measurement), `stop`, the polarity of `bool` and of removals; the error words «ask the
   admin so that the answer itself names…».
8. The data of `words.json`: Russian strings; `rights`, `not_found`, `all` — with boundaries and forms; `polarity`, `endings`, `stop`;
   the words of the VMS operators (`fields`, `options`, `units`).
9. A right is the capability of the write door (`need`), not `edit` (addendum (4) item 4).
10. An accepted `ask_admin` stops the calls of the answer, the unexecuted ones get `not executed`; the window does not
    shorten the results of `ask_admin`; restarts on 410/404 — no more than 2.
11. The overview is without the name and the grants of the session (`/session` is not read for the overview);
    the model sees rights by `can_edit` of units; the scope is the subsystems of `backend` (ADR-0093 addendum (5)).
12. `refuse` with `other_kind` and the line of `system.md` about a request of another type (ADR-0093 addendum (13), V/11.7 N1.6); it was not in the measurement.

### N1.1 Panel

Removed (ADR-0093 addendum (8) item 2). Input, questions, display and choice are led by the consolem form, the turn is the operation `POST /assist/turns` (chapter 7 N1.1); the model of the turn is the default of chapter 7 N1.2. The address of the norm is kept.

### N1.2 Step messages

The working message form of a step of the model door (V/10.2 N1.2) is below; the type-specific working harnesses are defined in chapters 7, 13 and 20. `learn` uses N1.7 instead of this overview, working harness, secrets message and working history. The window and runtime constants below remain common to all types.

```yaml
messages:           [system, user-overview, user-request, (user-secrets)?, …turn history]
  system:           {role: system, content: the bytes of harness/system.md} — the only system message of the step (V/10.2 N1.4:
                    a common prefix without data)
  user-overview:    {role: user, content: "## Cluster overview\nA snapshot of the console doors (list_subsystems,
                    get_manifest of every subsystem, the admin's rights):\n```json\n<overview>\n```\n"}
  overview:         JSON without spaces {subsystems, manifests, session}: subsystems — the result of list_subsystems (chapter 10),
                    manifests — {<sub>: the result of get_manifest} of every subsystem from subsystems, session — {note: "the
                    admin's rights are per unit: find_units shows can_edit: false where the admin has no right; such units
                    are left out of the plan"} — without the name and the grants: /session is not read for the overview (was P/06.5
                    N1.1), the right is can_edit of units (chapter 10 N1.2); built once at the start of the turn
  user-request:     {role: user, content: the request as the admin entered it}
  user-secrets:     present if a secret was entered in the turn (V/11.12 N1.3): {role: user, content: "Secret N is entered." — one
                    line per number, ascending}; a new secret after the start of the turn — the same message at the end of the history;
                    the secrets live with the plan (V/11.12 N1.3) — the message about them is in every step of the turn, also on a restart on 410/404
  history:          the model's messages as is (V/10.2 N1.3 message) without reasoning_content; tool results
                    {role: tool, tool_call_id, content}; the admin's answers — as the result of ask_admin (N1.4); loop hints
                    {role: user} (N1.4)
tools:              harness/tools.json in the OpenAI form: [{type: function, function: {name, description, parameters:
                    inputSchema}}] — in the order of the file
tool_choice:        "required"
reasoning_effort:   "medium"
max_tokens:         none
turn:               the turn id — 32 lowercase hex (128 random bits), one per turn (V/10.2 N1.2, N1.4)
```

- **The overview is a `user` message**, not in `system`: it holds the manifests the person sees, and the person's rights; the common prefix of the model's
  cache is only the system text and the tools (V/10.2 N1.4; ADR-0093 addendum (3) item 6). The overview is built by the same functions
  as the tools of chapter 10, and by the same console read.
- **Window, all types.** The window is `context` of the model row of the turn (V/10.1 N1.1). Before a step `backend` estimates the prompt: `prompt_tokens`
  of the previous call plus the growth of messages since then, `CHARS_PER_TOKEN` characters of JSON per token (without a previous call — all
  messages the same way). If the estimate is larger than `context − RESERVE`, then the content of the oldest tool results is replaced by the
  string `[result elided: context window; call the tool again if needed]`, one at a time, until the estimate fits or
  only the `KEEP_TOOL_RESULTS` last results remain. `system`, the overview, the texts of the turn (and the results of `ask_admin` — these are the
  admin's answers) and the model's messages are not shortened. For `learn`, `system` includes the catalogue and learning instructions; there is no overview or secrets message, and only learning history is considered (N1.7).

```yaml
CHARS_PER_TOKEN:    3
RESERVE:            4096 tokens — the window reserve for the model's answer
KEEP_TOOL_RESULTS:  4
TURN_CALLS:         25 — model calls between the admin's texts: after the request and after each answer (ADR-0093 addendum (4) item 2)
STEP_TRIES:         3 — attempts of a step on failed `model failed` and `model restarted` (N1.3)
RESTARTS:           2 — restarts of the turn on 410/404 per turn (ADR-0093 addendum (4) item 2)
ENQUEUE_WAIT:       300 — s of the accumulated wait for submitting a step: 503 `loading`, 429, 503 `busy` (N1.3)
```

### N1.3 Step

`backend` calls the model door by the route `/assist/chat/<name>/…` by ticket (chapter 7 N1.2; ADR-0093 addendum (7)): it has no door token, it does not read `where`. Admittance (`view` on the model row) is judged by the console: on a refusal the turn does not start. One step of the turn at a time. `learn` uses the same admission, shared queue, protocol and window; a different prompt and tool set do not create another model door or queue.

| Door answer | What `backend` does |
|---|---|
| `POST` 202 | `GET …/steps/<step>?wait=3` repeatedly, shorter than the route limit `PASS_WAIT`, until `state` is `done`, `failed`, `cancelled`; the status line — by `queued` (`ahead`) and `running` |
| `done` | the model call is credited; the answer — N1.4 |
| `failed` `model failed`, `model restarted` | the same step again, up to `STEP_TRIES` attempts; not credited; the last one failed — the outcome «turn not completed», the reason is `reason` |
| `failed` `too long`, `queue too long` | the outcome «turn not completed», the reason is `reason` |
| `failed` `context exceeded` | the outcome «turn not completed»: «did not fit into the model context window» |
| `cancelled` (not by a cancellation of `backend`) | the outcome «turn not completed», the reason is `reason` |
| 503 `loading`, 429, 503 `busy` on `POST` | wait `retry_after` of the body (otherwise 5 s) and submit again; the status line — «model loading» or «model busy». The wait accumulates over all three refusals in a row and is reset by the acceptance of the step (202); longer than `ENQUEUE_WAIT` — the outcome «turn not completed»: «model busy» |
| 503 `model unavailable`, no route, or the network | the outcome «turn not completed»: «model unavailable», the reason is `reason` of the body, if there is one |
| 403 on a step of a started turn | the outcome «turn not completed»: «step failed» |
| 410 `gone`, 404 `no such step` | the step is lost (the holder changed, V/10.2 N1.3): the turn starts anew — a new `turn`, the call count from zero; working tool results are read again, while `learn` rebuilds only its learning messages by N1.7; the texts of the turn — in one `user` message separated by an empty line, as in a rebuild (N1.5); up to `RESTARTS` times per turn, then the outcome «turn not completed» |
| 400, 413 | the outcome «turn not completed», the reason is the words of the door (an error of `backend`, not of the model) |
| the network, no answer, 503 `busy` on `GET` | `POST` is not repeated by itself (V/10.2 N1.2: there is no memory of repeats) — the outcome «turn not completed»; `GET` — up to 3 times per step every 2 s, then the outcome «turn not completed»; the step is removed by `ABANDON` (V/10.2 N1.5) |

### N1.4 Model answer

From `message` of the answer (`done`) `backend` takes the calls. Items 2–6 below describe the working policy. `learn` uses N1.7: it shares call ordering, JSON argument parsing and the limit, but not the working hint, name recovery by arguments, data-first read or plan execution.

1. **Calls.** `tool_calls` in order. A call written as text in `content` is not executed (ADR-0093 addendum (4) item 6;
   ADR-0093 item 3: the turn ends with a call, not with parsing of text).
2. **No call.** Into the history go the model's message and the hint `{role: user, content: "Use a tool call: answer the admin
   only with a tool call: a plan — propose_plan, a question — ask_admin, a refusal or \"there are no such units\" —
   refuse with the reason."}`, then the next model call; the call counts toward `TURN_CALLS` (N1.4 item 7). With `tool_choice:
   "required"` an answer without a call is not expected.
3. **Arguments and name.** Arguments: a string is JSON, an empty one is `{}`; a ready object is accepted; anything else gives the result `error: the
   arguments are not JSON: <first 300 characters>`. A name not from the set of chapter 10 means the tool to which the arguments fit
   (the keys are from its properties, the required ones are all there), if there is exactly one such; otherwise the result `no tool <name>`.
4. **Data first.** If the first `ask_admin` or `refuse` of the turn comes when before it in the turn there was not a single `find_units`,
   `field_values`, `list_table`, then it is not executed; the result is the error (chapter 10 N1.3) `error: an answer not checked
   against the data. First find_units or field_values for the request's words (rights — can_edit of the units found,
   label codes — field_values); then a plan, a question or a refusal. If the request names neither a unit nor a value,
   call ask_admin again.` Once per turn.
5. **Execute** — by chapter 10 (reading) and chapter 11 (`propose_plan`, the check of `refuse`). The result is the message
   `{role: tool, tool_call_id, content}`; a tool error is also a result, the turn goes on (chapter 10 N1.3).
6. **End and question.** An accepted `propose_plan` with `valid: true`, an accepted `refuse` and an accepted `ask_admin` stop
   the execution of the calls of this answer: every following call of the same answer is not executed and gets the result
   `not executed: <reason>` — `the turn is over` after a plan and a refusal, `waiting for the admin's answer` after a question
   (the call–result pairs in the history stay intact). A plan and a refusal end the turn. A question ends the HTTP request: `backend` gives out
   the question with the event `question`; the admin's answer comes as a new HTTP request with `context` and becomes the result of this `ask_admin` (`content` is the text as the person entered it; ADR-0093
   addendum (3) item 1); it joins the texts of the turn, the model call count starts from zero, the next model call follows. The answer field has
   the hint: «answer in words — name the field and value; “yes” names nothing».
7. **Limit.** There are at most `TURN_CALLS` model calls after the last admin text; when there can be no next one — the outcome
   «turn not completed» with the last check reason (chapter 11 N1.6) or «turn limit», not `refuse` (ADR-0093 addendum (4) item 2).

### N1.5 Turn outcomes

The plan and refusal forms below are for the working branch; the other working types retain their results from chapter 7. The learning result is N1.7 and V/11.7 N1.10, without a new event. Step failures, the turn limit and cancellation remain common.

| Outcome | When | What the admin sees |
|---|---|---|
| plan | `propose_plan` with `valid: true` | the selection block and the diff (chapter 11 N1.7), `summary` — «the model's words», «Apply» (V/11.12) |
| refusal | an accepted `refuse` | `reason` — «the model's words» |
| «turn not completed» | N1.3, N1.4 item 7, the working overview is not built (N1.2) | the words of `backend` by the kind of reason («turn limit», «model unavailable», «step failed», «the console could not be read», «the plan did not pass the check: &lt;rule&gt;»); the original text of the reason (a check error, `reason` of the door) — collapsed under them; the admin may rewrite the request |
| cancelled | «Cancel the turn», «New turn», a break of the stream before the end event, logging out, a change of session | — |

- **The words of «turn not completed».** The turn limit after rejected plan versions is «the plan did not pass the check: &lt;rule&gt;», where
  the rule is the kind of the first error of the last version (chapter 11 N1.6) in the words of `backend`:

```yaml
secret: «secret marker in the wrong place»        rights: «no write right on the unit»     empty: «empty edit»
twice: «field edited twice»              missing: «selected units are missing»    extra: «extra units in the plan»
condition: «selection condition is not from the request»  named: «unit not named in the request»     selection: «selection disagrees with the edits»
value: «value not named in the request»     list: «list edit without a verb»          field: «field not named in the request»
form: «edit violates the field form»            other: «check rule»
```

  The kind is by the error words of chapter 11 (N1.3, N1.4): «secret label», «is a secret» — `secret`; «has no right to edit» —
  `rights`; «empty edit» — `empty`; «is edited twice» — `twice`; «selected but missing» — `missing`; «not selected (» —
  `extra`; «selection.where: condition» — `condition`; «selection.named:» — `named`; any other «selection» — `selection`;
  «value … is not named» — `value`; «does not say to add, remove or replace» — `list`; «field … is not named»,
  «selection.fields» — `field`; the form errors of N1.3 — `form`; anything else — `other`. A limit without plan versions — «turn limit»;
  a step `cancelled` at the door — «step removed at the model door»; an unknown reason — «step failed».
- An outcome ends the turn. A new text without `context` is a new request, a new turn, a new `turn`; the texts of the previous turn are not
  carried into the new one. A new text with the `context` of an outcome is a **clarification**: `plan` and `refused` carry `context`, the form sends it with the words «Clarify», the previous plan is removed. The same `turn`, the text is appended to the texts of the turn as a `user` message: the new plan replaces the previous one whole, therefore the words of the previous texts remain in the reconciliation «named»; the call count starts from zero.
- **Working rebuild** after applying (V/11.12 N1.4 «Result») is a new turn: the request is the texts of the previous turn, as the admin entered them,
  in one `user` message separated by an empty line; the rows for the rebuild `backend` names in a separate `user` message
  of its own words (unit names and outcomes, without secret values), it is not part of the texts of the turn.
- **The model's answer is not executed by itself**: neither a plan nor a refusal writes anything; only «Apply» writes (V/11.12).

### N1.6 Life of the turn

The HTTP request lives from `POST` to the end event (chapter 7 N0, N1.1). A break of the stream before the end event is a cancellation; the cancellation of the step is done by `ABANDON` of the door (V/10.2 N1.3). The event `question` is not a break: the turn waits for a new HTTP request from the client. `backend` has no state of its own, the conversation is at the client (ADR-0094 A3); the model's answer and the texts of the turn go neither into the store nor into logs. A working secret label lives only inside its working turn (V/11.12 N1.3); it is never added to a learning turn. Learning questions use the same HTTP lifetime and `context` exchange, with only their own learning transcript (N1.7).

### N1.7 Learning branch

`learn` is the sixth internal type selected by V/11.7 N1.6, N1.10 (ADR-VMS-0004 through addenda (1), (2)). It has its own system prompt and exactly the tools of V/11.10 N1.7: `open_chapter`, `no_chapter`, `ask_admin`, with `tool_choice: required`. The catalogue from the single delivered source is the first part of that prompt, before the learning instructions, so unchanged catalogue bytes can reuse the model's prefix cache. The catalogue's stable topic and chapter IDs, version or digest, language, title, goal, training dataset and build availability are the selection data; no second editable copy or invented catalogue values are used.

- **Messages and isolation.** The model receives the catalogue, the learning instructions, the person's learning request and only this learning turn's own transcript, including its questions and answers. A previous working `context`, working transcript, object snapshot, draft, plan or secret is not input to this branch. There is no cluster or camera overview before the learning step, on a question continuation or on a restart; no working read is fetched to prepare it. The branch has no working search, schema, plan or apply tool. Working plan checks in V/11.11–11.13 remain unchanged and are not applied to a learning reference.
- **Calls.** Calls are processed in order. Text is not a call. A missing call retains the learning message, adds a reminder to use only the three learning tools, and requests the next call; it counts toward `TURN_CALLS`. Names must be own keys of this closed learning set; a different name gives `no tool <name>`, with no recovery to a working tool by its arguments. JSON arguments are parsed as in N1.4 item 3, then checked against the learning tool's schema. Neither the working no-call hint nor the data-first rule of N1.4 item 4 is used: no working read is permitted.
- **Question.** `ask_admin` reuses V/11.10 N1.6 and N1.4 item 6: the accepted question ends this HTTP request with `question`, the person's new request with its `context` supplies the tool result, and the call count starts from zero. The continuation stays in `learn`, with its own transcript only; it does not route through the working overview or ask the person to name a working field and value.
- **Checked result.** `open_chapter` supplies only a chapter ID from the catalogue enum. Code checks that ID and the version or digest of the catalogue used for the prompt against the current delivered catalogue, including chapter availability. Model-side grammar filtering is an implementation property, not this guarantee. An accepted choice ends the learning turn with the checked logical reference described as future `answer.learn` in V/11.7 N1.10; it never launches the show by itself. `no_chapter` ends it without claiming that a suitable lesson exists and offers the manual catalogue or search when available. After either terminal choice, later calls of the same answer are `not executed` as after a working terminal result. An unknown ID, a foreign catalogue version or an unavailable chapter offers no launch: use the manual catalogue when available. The interface rechecks the current ID and version before offering or launching a chapter, and truthfully names its language; current tours are Russian even in an English interface.
- **Lifetime and fallback.** Admission on the model row, the shared queue, window, `TURN_CALLS`, `STEP_TRIES`, `RESTARTS`, `ENQUEUE_WAIT` and cancellation are N1.2–N1.6. On a lost step, only this turn's learning texts are rebuilt; no working history or reads are restored. If the model is unavailable, the manual catalogue and ordinary search remain available when the build contains them. A build without training does not promise a lesson. No quality or latency threshold follows from a pilot measurement.
- **Contract dependency.** `answer.learn` is the agreed logical typed reference for a future supported contract, not a field of the current closed cb728a4 API. The Console fork change and contract agreement, then an authorised repin, are required before this reference can be carried. This text adds no request type field, SSE event, result JSON schema or runtime switch; the current `--without-learn` bundle remains unchanged. The show and its isolation are V/11.1 and V/11.12.

## N3 Pass

The type is selected before preparing its input. The following pass is the working loop; the learning pass is N1.7 with the same model-step lifecycle and limits, its own prompt and closed tools, and no overview or data-first read.

```
admin text → (no turn: a new turn, turn, the overview — chapter 10) → texts of the turn += text; count = 0
loop:
  count = TURN_CALLS → outcome «turn not completed» (the last reason)
  window (N1.2) → step (N1.3): 202 → poll → done | failed (repeat up to STEP_TRIES) | 410/404 → the turn anew
    503 loading, 429, 503 busy → wait retry_after, again; accumulated longer than ENQUEUE_WAIT → «turn not completed»
  count += 1; calls (N1.4 items 1, 3); no call → the hint "use a tool call" (counted)
  each call in order:
    ask_admin/refuse without a search in the turn → the error "data first" (once per turn)
    otherwise execute (chapter 10, chapter 11) → the result into the history
    propose_plan valid → outcome "plan"; refuse accepted → outcome "refusal"; ask_admin accepted → event question, the HTTP request is over; a new HTTP request with context → admin text
    after an accepted one — the other calls of the answer: not executed
```

**Races, all types.** The stream is broken while a step is running: the step is removed by `ABANDON`, a late model answer is not executed. While the calls of one answer are being executed, no new step is submitted. In a working turn, the admin's rights narrowed in the middle of a turn:
the next console read and the plan check see the new ones (chapter 10 N1.2, chapter 11); the overview of the turn is from the start of the turn, the plan
is checked by a fresh read.

## N4 Refusals

| Reason | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| `TURN_CALLS` calls without an outcome | «turn not completed», the last check reason | the admin | rewrite the request |
| a step `failed` after `STEP_TRIES`, `too long`, `queue too long`, `context exceeded`, `cancelled` | «turn not completed», `reason` | the admin | later or shorter |
| the model is unavailable (no route, 503 `model unavailable`) | «turn not completed», the reason | the admin | the operator — the model row (V/10.1) |
| the step is not submitted within `ENQUEUE_WAIT` (503 `loading`, 429, 503 `busy`) | «turn not completed»: «model busy» | the admin | later |
| 400, 413 of the model door | «turn not completed», the words of the door | the admin | — (an error of `backend`) |
| the working overview is not built (the console read) | «turn not completed»: «the console could not be read» | the admin | later |
| the step is lost (410, 404) | the turn anew, after `RESTARTS` — «turn not completed» | the admin | later |
