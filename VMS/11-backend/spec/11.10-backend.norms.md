# V/11.10 — Tools: norms

This English text is the source; the Russian translation `ru/spec/11.10-backend.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 10 of lesson V/11 «Бэкенд конфигуратора», the assistant (ADR-0080; the VMS module — ADR-0090; the subsystem — ADR-0093 items 3, 8, addendum (1) item 9,
addendum (2) item 2, addendum (3), addendum (4) items 4, 5, addendum (5)). Lecture (`ru/11-backend.md`, for people, not in the export), [instructions](11-backend.README.md). The platform is the export
`cammeta-specs` `7a875c75` (P/06.1 Н2 — the units door; P/06.5 — `/manifest`).

The model reads nothing by itself: `backend` executes each of its calls through the console doors by the person's ticket (chapter 7 Н1.2)
and returns the result as text. Therefore the model sees exactly what the admin sees — and no more: secret masks, the rights `view`,
the console's selection by grant act as they do for the form. The set is closed: nine tools of the handover package (ADR-0093 item 8) —
six for reading and three answers to the admin. The console doors have no filters: `backend` reads a list whole and selects by itself
(ADR-0093 addendum (2) item 2). The chapter sets norms for the set, the console reading, each read tool and `ask_admin`; `propose_plan`
and the `refuse` check are chapter 11.

Norm ids are `V/11.10-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#n0-vocabulary).

- **Subsystem** — `cam`, `rec`, `det`: the assistant's **scope**, a constant (chapter 7 Н1.2; ADR-0093 addendum (5), (6)). The overview, the tools and the plan go only by it. For the type `explain` the scope also includes `auto`, read only (V/11.7 Н1.7; ADR-0093 addendum (16)).
- **Subsystem rows** — the elements `configured` of the answer to `GET` of its rows (P/06.1 Н2): for the root `/<rows>`, for any other
  `/<sub>/<rows>`; `rows` is `rows` of the manifest. The row id is the field `id`; the name field is `id` of the manifest (`id_field`).
- **Related subsystem** — by `about` of the manifest (`about: {sub, field}`): a row refers to a unit of that subsystem by the
  field `field`. `about.<поле>` is a field of the related unit.
- **Manifest** of a subsystem — `GET /manifest` filtered by the scope (chapter 7 Н1.2): a projection of the manifest with the keys `name`, `rows`, `id`, `fields`, `about`, `display`, `servers`, `places` and others. **Root** — `cam`: its rows are `/<rows>`.

## Н1 Form

**Data.** No families of its own. It reads the console doors (Н1.2); it writes nothing.

### Н1.1 The set

The tools of the type `config` are exactly [`harness/tools.json`](../harness/tools.json), the set of the type `rules` is chapter 13 Н1.2: `list_subsystems`, `get_manifest`, `get_schema`,
`find_units`, `field_values`, `list_table` (reading), `propose_plan`, `ask_admin`, `refuse` (answer to the admin). The name, the description and
the argument schema are the bytes of the file; the model sees them in `tools` of the step (chapter 9 Н1.2). There is no other call: for a name not from the set
the result is `no tool <имя>` (chapter 9 Н1.4); membership in the set is an own key of a closed registry, not a property
inherited from the prototype (`constructor`, `toString`, `__proto__` — `no tool`); likewise the names of fields, tables and words
that the model writes are looked up only among own keys. The assistant cannot create or delete a unit, or write tables, servers, policy, the domain
— to such a request the model answers `refuse`.

### Н1.2 Console reading

- **Only by ticket**: the console doors of the person (chapter 7 Н1.2). The paths are a closed list:

```yaml
reads:   /schema, /manifest, /<rows>, /<sub>/<rows>, /<table>, /<sub>/<table>
         # <table> — a table from tables of the subsystem (list_subsystems): servers.show[].table and places.table of the manifest;
         # for the root — /<rows>, /<table>, for any other — /<sub>/<rows>, /<sub>/<table> (P/06.1 Н2)
never:   /mounts; writing (only «Применить» does it, chapter 12); holder doors; /events; /domain/*
```

- **Freshness.** Every tool call reads anew; the turn overview (chapter 9 Н1.2) is read once at the start of the turn. Within
  one call one door is read once.
- **Read error** — an answer other than 200 or a break: the call ends with the tool error
  `GET <путь>: <статус> <detail>`; there is no empty or truncated result instead of an error (ADR-0093 addendum (1) item 9). 403
  is «нет доступа» ("no access"): the person may not read this door, the same form `GET <путь>: 403 <detail>` (chapter 7 Н1.2), there is no separate
  rights check before reading. 401 — the ticket is dead: the stream is closed (chapter 7 Н4).
- **List limit.** More subsystem rows than `LIST_MAX` — the tool error `<sub>: more than <LIST_MAX> units — too
  many to check here; refuse and say so`; likewise for a table (ADR-0093 addendum (2) item 2: a limit and `refuse`, not a truncated
  selection).

```yaml
LIST_MAX:   5000 rows of one door
ROW_LIMIT:  50 — units and table rows in a tool result; the number is complete (count)
```

- **The right** of a unit (`can_edit`) is the capability that the write door of this row requires (`PUT /<rows>/<id>`), by
  `need` of the [gate and pass contract](../../../Platform/common/contracts/gate-and-pass.md): `admin` on the unit —
  `rights.routes` of unit rows lowers only creation (the table «Права по телу» of the contract). The check is only the
  rule `can_edit` of chapter 7 Н1.2 (the grants of the ticket's person, `sub` — the subsystem of the write door, the gate and pass contract «Подсистема проверки»; the area — including by the `about` unit),
  without its own read of `grants`: an emergency session (break-glass) and the open mode are judged as at the server. One rule serves the overview, `find_units`, the plan
  check, completeness and the `refuse` check (ADR-0093 addendum (4) item 4). This is a preliminary check: there is no key `rights` in
  `ManifestView`, therefore `rights.cluster_rows` (for `auto` a write requires a grant on the cluster) and what an edit
  touches beyond the row (`rights.reach`, `names`) `backend` does not see in advance — the server always checks them at writing
  (ADR-0093 addendum (1) item 9; a refusal is the outcome `refused`, V/11.12 Н1.4).
- **Unreadable subsystem** — reading its rows ended with an error or `LIST_MAX`. Where a tool or a check
  iterates over all subsystems (the hints of `find_units`, the `refuse` check of chapter 11 Н1.5, the unit names for the numbers of the text of chapter
  5 Н1.2), such a subsystem is skipped:
  there is nothing to refute with it; the `find_units` hint names it: `subsystem <s> could not be read: <причина>`.

### Н1.3 Result and error

- The result of a call is `content` of the message `tool` (chapter 9 Н1.2): JSON without spaces, keys in the order of the forms below.
- **Tool error** — `content` is `error: <слова>`; the turn goes on, the model corrects the call. The error words are in the
  forms below, in English, as in the pilot's measurement.
- `null` of a row field and the absence of the field are one and the same: «не задано» ("not set").

### Н1.4 Field words

The field view for the model (`get_manifest`, the overview) and the words for the check (chapter 11 Н1.2) are taken from `display` of the manifest and
[`harness/words.json`](../harness/words.json) — lesson data, not model settings:

```yaml
field:      {name, type, required?, fixed?, enum?, default?, inherit?, bound_to?, label?, label_from?, help?, enum_labels?,
             words?, enum_words?, secret?} — keys in this order; a key without a value (absent, false) is not written
  type:     the field type of fields of the manifest (string, int, float, bool, list, json, url, blob)
  label:    display.fields[name]; absent — words.json labels[sub][name] and label_from: "lesson"; absent too and the type is list — null;
            absent for another type — no key
  help:     display.field_help[name]
  enum_labels: display.options[name]
  words:    words.json fields[sub][name] — the operators' words beyond the label
  enum_words: words.json options[sub][name]
  secret:   true — the name ends with _secret (P/02.1 Н1.3а)
```

### Н1.5 Read tools

**`list_subsystems`** `{}` → `{subsystems: [элемент]}` in the order of subsystems; `элемент` is the element:

```yaml
element:  {sub, rows, id_field, unit_word, units_word, section, words?, unit_word_from?, about?, tables?}
  unit_word, units_word, section: display.unit, display.units, display.section (absent — null)
  words:  words.json units[sub]
  unit_word_from: there is no display.unit, and a subsystem that refers to this one by about gave a hint of the link field
          (display.field_help[about.field]) — unit_word = that hint, unit_word_from: "no label in display; the word comes
          from the help of field <другая>.<поле>"
  about:  "each unit (\"<unit_word or sub>\") belongs to a unit of <about.sub> (\"<its unit_word or sub>\") via field
          <about.field>; that unit's fields in find_units are about.<field>"
  tables: the names of the tables servers.show[].table and places.table, by name; none — no key
```

**`get_manifest`** `{sub}` → `{sub, rows, id_field, about?, fields, word_unit?, word_units?, word_section?, word_general?,
form?, status_words?, notes}`:

- no such subsystem — `error: no subsystem "<sub>"; there are: <подсистемы через ", ">`; the subsystem is mounted but outside
  the scope (Н0) — `error: subsystem <sub> is outside the assistant's scope (this page: <подсистемы через ", ">) — refuse:
  not in scope, not a lack of rights` (ADR-0093 addendum (5) item 1); likewise for every tool and every plan edit with this
  subsystem;
- `about` — `{sub, field, note, about_list_fields}`: `note` — `a unit belongs to a unit of <about.sub> whose name is in
  field <about.field>. That unit's fields are filters about.<field>: <about.<поле> связанной через ", ">. A unit's labels
  are the labels of the related unit: about.labels; its own list fields (<свои поля list через ", " или none>) are not
  labels`; `about_list_fields` — `about.<поле>` of the `list` fields of the related unit;
- `fields` — the view of every field of `fields` of the manifest (Н1.4) in order; `word_*` — `display.unit`, `units`, `section`,
  `general`; `form` — `[{title, fields}]` from `display.form`; `status_words` — `display.options` by the names that are not
  among the fields;
- `notes` — four lines:
  1. `look up field values (labels, zones, shelves) with field_values — the admin's words are stored as values (e.g.
     "northern" → north, "quiet" → plain)`;
  2. `a field with secret: true is hidden from you (the console shows ***); a new secret value is never written into a
     plan — only the secret label {"secret": N} the admin entered`;
  3. `a fixed field cannot be changed; the id_field is the unit's name, it is not changed`;
  4. `a field with inherit and no own value: find_units shows null, and inherited says what applies; from is null or
     the effective value`.

**`get_schema`** `{}` → the answer of `GET /schema` as is.

**`find_units`** `{sub, where?, fields?}` → `{sub, count, shown, units, can_edit_note?, query, hints?}`:

- **Conditions** `where` — a list of `{field, op, value}`, all joined by AND. Short forms: an object `{<поле>: <значение>, …}` — equalities;
  `{field, <op>: <значение>}` with one key from `op` — this `op`. `op` not given — `eq`. Errors: another key — `condition
  <условие>: extra keys <ключи>; the form is {"field": …, "op": "eq", "value": …}`; no `value` with an `op` other than
  `exists`/`missing` — `condition <условие>: no value; …`; not an object or without `field` — `a condition is {field, op,
  value}`; `op` not from `eq ne in not_in contains not_contains gt gte lt lte exists missing` — `op "<op>": one of <список>`;
  a field not among the row fields, `id`, `revision` — `no field "<поле>" in <sub>; fields: <по имени>`; `about.<поле>` without `about`
  — `<sub> has no about`; `about.<поле>` not among the fields of the related subsystem and `id` — `no field "<поле>" in the related subsystem <s>;
  its fields: <about.поле…> — filter about.<field>`.
- **The value** of a condition for a row is its field; `about.<поле>` is the field of the unit of the related subsystem whose id equals the link field of the
  row (there is no such unit — not set).
- **Comparison** `same(a, b)` — equality of JSON values, but `true`/`false` are not equal to numbers. `eq` — `same`; `ne` — not `same`;
  `in`/`not_in` — `same` with an element of the value list (a value that is not a list — as a list of one); `contains` — the list field contains the value (a list value — all its
  elements); `not_contains` — the negation of `contains`; `exists`/`missing` — set / not set; `gt gte lt lte` — numbers (not
  `bool`) on both sides, otherwise it does not match.
- **Empty list.** For a `list` field: `eq`/`ne` with `""`, `[]`, `null` and `exists`/`missing` judge «пусто или не задано» ("empty or not set");
  a not-set field with `inherit` has the value of `inherit`. `eq`, `missing` — empty; `ne`, `exists` — not empty.
- **Units** — the matching rows ordered by id, ids by UTF-8 bytes (Kimi's addition to the analysis of the V/10 review, С5); in `units` —
  the first `ROW_LIMIT`: `{unit: "<sub>/<id>", …вид}`. The view is the row fields (only from `fields`, if given) without `id`,
  `revision`, `index`, the name field, without an empty string (if the field was not requested), without `null` (if not requested); `[]` and `""` of a requested
  field are visible. A not-set field with `inherit` (among the requested ones) is `null`, and `inherited: {<поле>: <значение inherit>}`. With
  `about`: `about.labels` — the labels of the related unit, if non-empty; `about.<поле>` from `fields` — the value of the field of the related
  unit (not set and the field of that subsystem has `inherit` — the value of `inherit` and an entry in `inherited`), and in that case also
  the link field of the row. No right (Н1.2) — `can_edit: false`.
- `count` is the number of matching units, `shown` the number in `units`. With `can_edit: false` there is `can_edit_note`: `can_edit: false — the
  admin has no edit right on this unit: leave it out of the plan, tell the admin in summary`. `query` is `{sub, where}`
  after the short forms.
- **Found during the turn.** Every shown unit goes into the turn's ledger `unit → право` (for the `refuse` check, chapter 11 Н1.5).
- **Hints** `hints` — at zero findings and non-empty conditions, in order, all that fired; none fired — `["no matches
  anywhere; check the field's values with field_values"]`:
  1. one field twice via `eq` — `field <поле> twice with eq — conditions are AND, one unit cannot equal two values;
     for "or" use {"field": "<поле>", "op": "in", "value": <значения>}`;
  2. a condition value (not `contains`/`not_contains`) is an element of a list field of some row of the subsystem —
     `<значение> is an element of list field <поле> — a list needs op contains: {"field": "<поле>", "op": "contains",
     "value": …}` (one per condition);
  3. there is `about`, and a string condition value is a value or an element of a field of the related subsystem (`labels`, then the keys of the first row in reading order, `id` among them) —
     `"<значение>" is in field <поле> of the related subsystem <s> — filter about.<поле>` (one per value);
  4. a string condition value is the id of a unit of another subsystem — `"<значение>" is the name of a unit of subsystem <s>`;
  5. another subsystem cannot be read (Н1.2) — `subsystem <s> could not be read: <причина>`.

**`field_values`** `{sub, field}` → `{sub, field, values, empty_units?, empty_note?}`: `values` — `[{value, units}]`
of the field's values (for a list — of its elements; for `about.<поле>` — at the related units; objects, lists and not-set values are not counted)
by descending `units`, at equality — by ascending value as JSON: first the type in the order string, number, `bool`,
within a type — numbers by value, strings by UTF-8 bytes, `false` < `true` (Kimi's addition to the analysis of the V/10 review, С5). For a
`list` field the empty or not-set units (with `inherit` — by it) give `empty_units` and `empty_note`: `empty or not set: {"field":
"<поле>", "op": "eq", "value": []}`. No such field — `no field "<поле>" in <sub>`; `about.<поле>` — as with `find_units`.

**`list_table`** `{sub, table}` → `{sub, table, rows, read_only: true}`: `rows` — the first `ROW_LIMIT` rows of the table without the fields
`by`, `at`, `made_at`, `held_by`, `revision`, `index`. The table is not among `tables` of the subsystem or not in the answer — `no table "<table>" in <sub>`.

### Н1.6 The answer to the admin

- **`ask_admin`** `{question}`: empty — the error `question is one short question to the admin`. Otherwise it is accepted: `backend`
  gives out the question as the event `question` and ends the request (chapter 9 Н1.4 item 6); the result is the text of the admin's answer from the new request.
- **`refuse`** `{reason, other_kind?}`: empty — the error `reason is why the request cannot be done (or that there are no such units)`;
  the refusal check is chapter 11 Н1.5; accepted — the outcome «отказ» ("refusal") (chapter 9 Н1.5). `other_kind: true` — a request of another type: there is no check, `backend` chooses the type anew (V/11.7 Н1.6).
- **`propose_plan`** — chapter 11.

## Н3 Pass

```
call → is the name from the set? otherwise no tool
arguments → short forms → check of fields and op → tool error | further
manifest — GET /manifest by the scope; reading of rows (and of the related subsystem) — by ticket; not 200 → error; > LIST_MAX → error
selection in `backend` → view, can_edit, ledger of the found, hints → result JSON
```

**Races.** Rows changed between calls — every call reads anew; the plan is checked against its own read (chapter 11), and
applying goes by the `revision` of that read (V/11.12). Rights narrowed in the middle of a turn — the next call sees less.

## Н4 Refusals

| Reason | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| a name not from the set | `no tool <имя>` | model | another call |
| a condition not in the form, no such field, no such subsystem, no such table | a tool error with the words of Н1.5 | model | correct the call |
| a console read is not 200 | `GET <путь>: <статус> <detail>` | model | `refuse` or a repeat later |
| more rows than `LIST_MAX` | the error «too many to check here» | model | `refuse` |
| console 401, the ticket is dead | the stream is closed (chapter 7 Н4) | WebUI | repeat the request |

## Н5 Acceptance

By the `backend` driver (chapter 7 Н5): the vectors of the read tools — a console read (rows,
manifests, session) and a call → a result or an error: short forms of conditions, each `op`, the empty list and `inherit`,
`about.<поле>`, `can_edit` by the capability of the write door (and the emergency session, the open mode), hints 1–5 and an unreadable subsystem, `field_values`, `list_table`, a read error. The vectors are
[`vectors/plan-check/`](../vectors/plan-check/README.md) (the cases `tools-*` and the replay of the pilot base; `LIST_MAX` —
5000 is read, 5001 is an error, the field `bulk`).
