# V/11.12 — Applying the plan and secrets: norms

This English text is the source; the Russian translation `ru/spec/11.12-backend.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 12 of lesson V/11 «Бэкенд конфигуратора», the assistant (ADR-0080; the VMS module — ADR-0090; the subsystem — ADR-0093, addendum (1) items 6, 7, 10;
addendum (2) item 5, addendum (4) item 1). Lecture (`ru/11-backend.md`, for people, not in the export), [instructions](11-backend.README.md). The platform is the export `cammeta-specs`
`7a875c75`.

A plan that has passed the check (chapter 11) is seen and applied by the admin personally: the form shows the plan in the words of the translation, «Применить» ("Apply") is a write by the client (chapter 7 Н1.3). A secret — a password that the admin enters in a separate field — is never seen by the model: in the plan it is only a label, and `backend` substitutes the value itself. The chapter sets norms for the changes to apply, the display and the secret label; the panel write is removed (ADR-0093 addendum (8) item 2).

Norm ids are `V/11.12-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н1 Form

**Data.** The chapter has no families of its own. The targets of the plan are fields of the unit rows of subsystems with a manifest (chapter 11) and the places of `UnitPatch` of the records (chapter 7 Н1.3).

### Н1.1 Changes to apply

From the checked plan (the plan form — chapter 11) applying reads only the **row changes**:

```yaml
rows:       [{unit, revision, changes}] — one per unit, in plan order
unit:       "<sub>/<id>" — the unit row of a subsystem with a manifest
revision:   revision of the row in the read GET /<sub>/<rows> by which the plan was built (the element configured)
changes:    [{field, from, to}] — the row field, the value in the read, the new value; field is not id, not fixed, not blob (chapter 11)
```

- **A row is one write.** All changes of one row go as one write element with one version — the one in the read
  (chapter 7 Н1.3; ADR-0093 addendum (1) item 6). Otherwise the first write would raise `revision`, and the second would get 412 without anyone else's edit.
- **Refusal of the plan before display** (the check of chapter 11 rejects it; applying does not start if it sees it): a field twice in one row
  — with the same `to` too; two different `revision` for one row; `from` = `to` — an empty edit (ADR-0093 addendum (2) item 3);
  a secret label not by Н1.3.
- The plan format promises neither idempotency nor a check without a write (ADR-0093 addendum (2) item 5): a repeat of «Применить» is a new
  attempt with the same `revision`, and a row already applied gets 412 (chapter 7 Н1.3).

### Н1.2 Display

Before «Применить» the form shows the plan whole, in the words of the translation (chapter 7 Н1.3), not in the text of the model:

- for every row — the name of the unit and of its subsystem (`display.unit`), for every change — the field label (`display.fields`,
  otherwise the field name), `from → to` (the options of an `enum` — by the labels `display.options`), the `why` of the edit;
- selection — by chapter 11 Н1.7: the selection condition in words and the number of units in a separate block above the diff (ADR-0093 addendum (3) item 2);
- a secret label — in the words «секрет № N» ("secret No. N") (Н1.3); the secret value is shown nowhere, and in `from` of a secret field is
  what the console gave (`***` or empty).

The assistant has no applying without a version: `items` carry `version` (chapter 7 Н1.3).

### Н1.3 The secret label

- **Input.** The admin enters a secret in a separate field of the form (`secrets` of the turn HTTP request, chapter 7 Н1.1), not in the request text (ADR-0093 addendum (1) item 7).
  Every entered value gets a turn number `N` — an integer ≥ 1, in the order of entry within this turn. The client
  holds the values until the end of the conversation and sends them as a whole array in every HTTP request (the contract `AssistTurnRequest.secrets`): `N` is continuous, the position in the array, a question and the display of the plan do not erase them (ADR-0093 addendum (4) item 1). The end of the conversation is applying the plan, cancelling the turn, the outcome «отказ» ("refusal") or «ход не завершён» ("turn not completed") without a clarification, a new request, a rebuild, logging out, a change of person, a break of the stream. At `backend`
  they exist only for the time of the HTTP request, there is no state after it (chapter 9), they are not put into `context`. They go neither into the model steps nor into the log.
- **What the model knows.** Only «секрет № N введён» ("secret No. N entered") goes into the step text — the number, without the value.
- **The plan value type.** The secret label is the object `{"secret": N}`, a separate value type, not a string. It is allowed only
  **whole** as `to` of a field whose name ends with `_secret` (the name rule — [P/02.1](../../../Platform/02-installer/spec/02.1-installer.norms.md)
  Н1.3а; P/06.2 Н1.1), and only with an `N`
  entered in this turn. One label — one field name in the whole plan: one value may be set to several rows into one
  and the same field (`cred_secret` of three cameras), but not into different fields.
- **A plan refusal that the admin's answer does not lift:** a label in a field that is not `*_secret`; a label inside a string or an array; a label in
  `from`, in a selection, in `why`, in `summary`; a number that the turn does not have; one label in two different fields; the pilot's text label
  (`secret:N` in double curly braces) anywhere in the plan as a string. The refusal words — chapter 11.
- **`to` of a secret field** is only a label: a string, `***` or empty in `to` of a field `*_secret` is a plan refusal (the mask on input is
  400 at the door, P/06.2 Н3; empty means «сохранить прежний» ("keep the previous one"), an empty edit).
- **Substitution.** `backend` puts the secret value in place of the label into `/properties/password` of `patch` of the plan element (chapter 7 Н1.3), only after
  the check. The value is absent in the display, in the outcomes, in the refusal words, in the model steps.
- **Address and password.** The field from `bound_to` of a secret changes without a new secret — the door answers 400 «must be given anew»
  (P/06.2 Н3), a refusal of the client's write (chapter 7 Н1.3).

### Н1.4 Write and outcomes

Removed together with the panel. The write is the client's: `PATCH /units/{uid}` with `If-Match` per element or the steps `{uid, patch}` of `POST /operations` with `expectedVersions`; a record changed after the plan — 412 (chapter 7 Н1.3). The address of the norm is kept.

## Н3 Pass

```
plan accepted → translation (chapter 7 Н1.3) → event plan → «Применить» of the client: PATCH /units/{uid} | POST /operations
```

**Races.** Someone else's edit of a row between the read and «Применить» is 412 of the client's write (chapter 7 Н1.3): it is not overwritten. Two admins apply plans on one row — the second gets 412.

## Н4 Refusals

| Reason | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| a field twice in a row, two `revision` for a row, an empty edit, a secret label not by Н1.3 | refusal of the plan before display (chapter 11) | the model — the words of the reason, the admin — the result of the turn | — |
| the row was changed after the read | 412 of the client's write: of the `PATCH` of that record, of the whole `POST /operations` (chapter 7 Н1.3) | the admin — the form | rebuild |
| the door rejected the edit (form, rights, references, size, «must be given anew») | a refusal of the write (the answer of `PATCH`, the step `failed` of the operation), the words of the door | the admin — the form | rebuild or fix manually |
