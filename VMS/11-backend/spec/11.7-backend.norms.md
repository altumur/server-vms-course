# V/11.7 — Ассистент конфигурирования в `backend`: нормы

Канон главы 7 урока V/11 «Бэкенд конфигуратора» (ADR-0093 доп. (6); ADR-0094 доп. (10)). [Лекция](../11-backend.md),
[инструкция](11-backend.README.md), контракт [`consolem.openapi.json`](../consolem.openapi.json); ассистент — урок
[V/10](../../10-assist/README.md). Платформа — выгрузка `cammeta-specs` `7a875c75` (пин VMS; приращение прав поверх норм B, ADR-0090 доп. (17); пометка «норма платформы B» — где глава на них опирается).

Ассистент конфигурирования (ADR-0093) — администратор пишет просьбу словами, модель внутри кластера предлагает план,
код проверяет план, записывает только человек. У нашей страницы ход идёт в браузере (V/11.9). Для WebUI consolem ход
идёт в `backend` (решение владельца, ADR-0093 доп. (6)): у `backend` нет своих прав, обращения в консоль — правами
человека по билету, пока открыт его запрос (ADR-0094 B1). Одна норма, две реализации: инструменты, проверка плана и
векторы — главы 9–13: цикл только в `backend` (ADR-0093 доп. (8) п. 2), панель страницы снята. Глава нормирует операцию хода,
цикл хода в `backend`, перевод плана в слова consolem и предел хода.

Id норм — `V/11.7-MM`; соответствие — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Правила модуля «Платформа» — [P/01.1
Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-словарь-слов).

- **Ход** — V/11.9 Н0: от просьбы до исхода; вопрос ход не кончает.
- **Запрос** — один `POST /assist/turns` от открытия до события конца: `question`, `plan`, `refused`, `error`.
- **Переписка** — тексты хода и сообщения шагов модели, которые держит клиент и возвращает с каждым запросом:
  своего состояния у `backend` нет (ADR-0094 A3).
- **План consolem** — проверенный план (V/11.11 Н1.1), переведённый в `items` формы `DevicesUpdateRequest` контракта.

## Н1 Форма

**Время.** Сроки главы — секунды монотонных часов процесса.

### Н1.1 Операция хода

- Операция хода — потоковая операция контракта `POST /assist/turns` (`assistTurn`, глава 2 № 90), возможность `assist`, тело `AssistTurnRequest` `{text, context?,
  secrets?}` (`text` — что написал человек; `context` — непрозрачная строка из прошлого ответа разговора, клиент
  возвращает её как есть; `secrets` — массив строк, секрет № N — место N с 1 (V/11.12 Н1.3):
  модели идёт только «секрет № N введён», значение подставляет код `backend` в `password` плана, Н1.3; в `context`
  секреты не кладутся; дополнение Kimi к разбору ревью V/11, замечание «Консоли»), ответ — поток SSE `text/event-stream`: на сообщение строка `data:` (`AssistEvent`), без `event:` и `id:` (ADR-0094 доп. (10) п. 2).
- `text` пустой — 422 `VALIDATION_FAILED`, `field: text`, ответ `application/problem+json`, потока нет. Типа хода в запросе нет: его выбирает `backend`, Н1.6; поле `kind` контракт b09cdf8 не знает — 422 `VALIDATION_FAILED`, `field: kind`, как всякое лишнее. Поле `world` — только демо-страница контракта: V/11 его не принимает, 422 `VALIDATION_FAILED`, `field: world`.
- Маршрут передачи — `api/assist/turns`, **потоковый** (V/11.1 Н1.5; норма платформы B1): без предела 5 с и буфера
  4 МиБ; билет потока годится только на чтения и маршрут двери подсистемы — инструментам и проверке плана этого хватает
  (V/11.10, V/11.11 только читают), а модель зовётся маршрутом. Предел ожидания маршрута — `ASSIST_TURN_MAX` (Н1.5).
- Обрыв потока до события конца — отмена хода: билет погас вместе с запросом, поэтому `backend` отбой `DELETE` шага послать не может и
  больше ничего не шлёт; незавершённый шаг дверь модели снимает по `ABANDON` (V/10.2 Н1.3).
  Оборванный поток не продолжается: клиент повторяет запрос с тем же `context`.

### Н1.2 Цикл хода в `backend`

Цикл — V/11.9 Н1.2–Н1.5 (сообщения шага, окно, шаг, разбор ответа модели, исходы). Здесь — чем он связан с запросом контракта:

- **Модель** — дверь модели V/10.2 через консоль: `backend` зовёт маршрут `/assist/chat/<имя>/…` по билету (обратный
  вызов из перечня, V/11.1 Н1.5; P/06.3 Н1.9 «Маршрут двери»), консоль передаёт его держателю с токеном двери (право
  `view` на строку модели — человека билета; ADR-0094 доп. (12) п. 7, ADR-0093 доп. (7)). Адреса и токена двери `backend`
  не видит: `/assist/where` он не читает. Шаг ставится и опрашивается по V/10.2 Н1.2, Н1.3; у маршрута предел `PASS_WAIT`,
  поэтому `wait` опроса — 3 с (V/11.9 Н1.3). Модель хода — строка модели, которую называет `context`, без него
  — первая видимая человеку строка `assist/models` по имени с фазой `running`; список
  — `GET /assist/models` по билету (обратный вызов из перечня, V/11.1 Н1.5; дополнение Kimi к разбору ревью V/11, № 1).
  Ключей и адреса модели клиент не видит.
- **Переписка** — в `context`: base64url без `=` UTF-8 JSON `{v: 1, model, turn, texts, messages}` — модель хода, `turn`
  хода (V/11.9 Н1.2), тексты хода и сообщения шагов, которые идут в историю (V/11.9 Н1.2); `type` — тип хода при открытом вопросе (Н1.6), иначе поля нет. Каждый запрос с `context` — новый `text`
  добавляется к `texts`, ответ на вопрос и уточнение (V/11.9 Н1.5); `context` не читается или `v` не `1` — ход заново без истории (новый `turn`). Секретов в
  `context` нет: метки секретов живут только внутри одного хода (V/11.12 Н1.3), и новый ход их не наследует.
- **`context` — ввод клиента без доверия** (дополнение Kimi к разбору ревью V/11, вопрос 3): подписи (MAC) нет — у
  `backend` нет ни состояния, ни своих ключей. Его сообщения — не доказательство ни прав, ни данных: модель видит их как
  историю, а вред ограничен правами человека по билету (каждое чтение — его правом), проверкой плана кодом над свежим
  чтением (V/11.11) и тем, что маршрут двери модели проходит только по праву `view` человека.
- **Вопрос** `ask_admin` кончает запрос (V/11.9 Н1.4 п. 6): поток кончается событием `question`, ответ
  человека — новый запрос с `context` вопроса (ADR-0093 доп. (6) п. 2).
- **Тип `rules`** (V/11.13): харнес, инструменты, план и слои — той главы, ход и окно — эти. Тип выбирает `backend`, Н1.6. План — событие `plan` с `rules`, `AssistRuleEdit`: тело переводчика нейтрального плана, `id` — UUID, `@<ref>` как есть, `logOnly: true` у нового правила (V/11.13 Н1.4). Запись правил — по «Применить» контрактными дверями `POST /rules`, `PUT /rules/{ruleId}` сессией человека (V/11.13 Н1.7), не операция хода.
- **Инструменты** типа `config` — закрытый набор V/11.10: те же имена, аргументы, результаты, ошибки и слова; чтения — двери консоли из
  перечня V/11.10 Н1.2 по билету потока. **Охват** — константа урока: `cam`, `rec`, `det` (ADR-0093
  доп. (5), (6)); `list_subsystems` и `get_manifest` — по `GET /manifest`, отфильтрованному по охвату; `/mounts` не
  читается (дополнение Kimi к разбору ревью V/11, вопрос 4). **`can_edit`** — то же правило `may("admin",
  "unit:<sub>/<id>", "<sub>")` модуля (P/07 Н1.5: гранты сессии и область P/06.3 Н1.3) над `GET /session` человека билета. Каждая
  дверь, которую читают инструменты, — в перечне обратного вызова (V/11.1 Н1.5). Отказ двери 403 — ошибка инструмента
  V/11.10 Н1.2 «нет доступа» (`GET <путь>: 403 <detail>`), ход идёт дальше; 401 — билет мёртв: поток закрыт (Н4).
- **Проверка плана** — V/11.11 целиком (форма и права, сверка слов, отбор, вопрос и отказ), над свежим чтением консоли
  по билету; затем — перевод в план consolem (Н1.3). Модель план не проверяет: проверяет код.
- **Счёт вызовов** — `TURN_CALLS` = 25 на ход (V/11.9 Н1.2), `STEP_TRIES`, `RESTARTS`, `ENQUEUE_WAIT` — по главе 9
  (V/11.9 Н1.3); исход за пределом — тот же: «ход не завершён».

### Н1.3 Перевод плана в слова consolem

- **Охват** (ADR-0093 доп. (6) п. 4). Проверка плана в `backend` пропускает только правки, у которых есть место в
  `DevicePatch` (V/11.3, таблица `mapping.tsv`): правка иного поля или иной единицы — отказ проверки с именем поля
  (`field`) и словами «сделайте это вручную»; правка единицы `auto` — отказ `not in scope` (Н1.7). Частичного плана нет: одна такая правка — отказ всего плана.
- **Правки с местом** — по единицам устройства (V/11.3 Н1.2):

| Правка плана (`unit`, `field`) | Поле `DevicePatch` устройства |
|---|---|
| `cam/<id>` (камера, пустой `main`): `name`, `enabled`, `cred_username` | камера: `name`, `enabled`, `login` |
| `cam/<id>`: `source`, меняются только хост и порт | камера: `ip`, `port` |
| `rec/<cam>`: `enabled` | камера: `recordMode` — при `true` `always`, с непустым `replica_from` — `replica`; при `false` — `none` (V/11.3 Н1.3) |
| `rec/<cam>`: `home`, `stream` | камера: `archiveId`, `stream` |
| `rec/<cam>-<том>`: `enabled` | камера: `extraArchives`, элемент тома — `recordMode` `always` \| `replica` \| `none` |
| `det/<cam>-<kind>`, `det/<cam>-<kind>-<n>`: `enabled` | детектор: `enabled` |
| `det/<cam>-<kind>`, `det/<cam>-<kind>-<n>`: `params`, меняется только ключ `sensitivity` | детектор: `sensitivity` (кодек V/11.3 Н1.3) |
| `cam/<id>`: `cred_secret`, `to` — метка `{"secret": N}` (V/11.12 Н1.3) | камера: `password` = `secrets[N − 1]` запроса хода (`DevicePatch.password` контракта: «новый пароль; в ответах его нет»); метки без такого места в `secrets` — отказ проверки |

  Иное — отказ проверки (выше): секрет тома (`access_secret`), тома, записи с иными именами, потоки,
  поля без строки в таблице, `source` с иным путём, `params` с иными ключами.
- **План consolem** — `items` формы `DevicesUpdateRequest.items` (`deviceId`, `version`, `set`) и к каждому устройству
  пояснение: `name` и `changes` — правки `AssistChange` `{field, before?, after, why}` в полях consolem; у секрета `before` нет, `after` — только номер: «новый (секрет № N)». Правки строки камеры и её записей сходятся в
  элемент камеры, правки детектора — в свой элемент (детектор — своё устройство); `version` —
  версия устройства (V/11.4 Н1.1) по тому же чтению, по которому прошла проверка плана; `deviceId` — V/11.4 Н1.6.
  Порядок элементов — по `deviceId` байтами. Итог: `{summary, context, items}`.
- **«Применить»** — не операция хода: клиент шлёт `POST /devices/update` с `items` как есть и новым `idempotencyKey`
  (глава 4 Н1.5); устройство изменилось после плана — его элемент `failed` с 412, в нём ничего не записано (пакет,
  ADR-0094 доп. (9)).

### Н1.4 События потока

| `type` сообщения `AssistEvent` | Когда | Поля |
|---|---|---|
| `progress` | шаг цикла начат: где модель, шаг модели, инструмент, проверка плана — сколько угодно раз | `{text}` — строка хода работы (V/11.9 Н1.1 «строка состояния»: «модель загружается», «модель занята», «читаю `<sub>`», «проверяю план») |
| `question` | принят `ask_admin` | `{text, context}` |
| `plan` | план прошёл проверку и перевод | `{summary, context, items}` (Н1.3) |
| `refused` | принят `refuse`; правка вне охвата; «ход не завершён» (V/11.9 Н1.5) | `{text, context, field?}` — слова причины |
| `answer` | принят `answer` типа `explain` (Н1.7) | `{text, context}` — ничего не пишет |
| `found` | принят `found`, отбор посчитан (Н1.8) | `{text, context, conditions, ids \| filter, total?, truncated?}` |
| `error` | отказ двери консоли, который ходом не исправить | `{code, message}` — `code` из `ProblemCode` (глава 2 Н1.3) |

- Поток кончается ровно одним из `question`, `plan`, `refused`, `answer`, `found`, `error`; затем `backend` закрывает поток.
- Каждое сообщение несёт `at` — момент, когда `backend` его произвёл, RFC 3339 UTC (глава 5 Н1.2). Поток без завершающего сообщения форма считает обрывом: `UPSTREAM_UNAVAILABLE`.
- `id:` событий хода нет: ход не возобновляется по `Last-Event-ID` (оборванный — повтор запроса, Н1.1).

### Н1.5 Предел хода

- `ASSIST_TURN_MAX` = 7500 с — потолок запроса: `TURN_CALLS` (25) × предел вызова модели (`QUEUE_MAX` 120 с +
  `STEP_MAX` 180 с, V/10.2 Н1.3) (ADR-0094 доп. (10) п. 2). Это предел ожидания маршрута `api/assist/turns` у консоли
  (число — здесь, потолок `PASS_WAIT_MAX` — норма платформы B1) и предел хода у `backend`: ход, не кончившийся за него от начала
  запроса, кончается `refused` «ход не завершён: дольше предела хода»; повторы `STEP_TRIES`, `RESTARTS` и ожидание
  `ENQUEUE_WAIT` идут внутри него.
- Предел: билет потока кончается с `exp` токена запроса (договор сторожевой и передачи, `close`), а `TOKEN_LIFETIME` = 900 с
  ([P/08.4 Н1.3](../../../Platform/08-domain/spec/08.4-domain.norms.md)) меньше `ASSIST_TURN_MAX`. Запрос, не кончившийся к `exp`, — обрыв потока (Н1.1): события-исхода нет,
  повтор идёт с прежнего `context`. Запрос дольше остатка токена не завершается, потолок при таком токене не достигается.

### Н1.6 Тип реплики

ADR-0093 доп. (13), (15) п. 1; контракт форка b09cdf8: у `AssistTurnRequest` поля `kind` нет, у `AssistEvent` тоже.

- Тип выбирает `backend` по каждой реплике, вызывающий его не называет: в одном разговоре бывают правка, правило, вопрос о системе и список. Выбранный тип наружу не отдаётся, форма его не показывает (ADR-0093 доп. (12), (13)).
- **Типы:** `config` — главы 9–12; `rules` — V/11.13; `explain` — Н1.7; `found` — отбор, Н1.8.
- **Ответ на вопрос** не классифицируется заново: `context` вопроса несёт тип полем `type` переписки (Н1.2), ответ идёт тем же харнесом. Тип выводится у реплики без открытого вопроса: первой, после плана, отказа, ответа и списка.
- **Шаг `route`** — один шаг двери модели до цикла: `system` — байты [`harness/route/system.md`](../harness/route/system.md), `tools` — [`harness/route/tools.json`](../harness/route/tools.json), `tool_choice: required`, сообщение `user` — тексты хода через пустую строку. Вызов `route {kind}`: `config`, `rules`, `explain`, `found` — тип; `ask` — событие `question` с `question` вызова, `context` без типа: ответ выбирается заново. Нет вызова или иное значение — шаг повторяется один раз, затем `question` на языке реплики (решила: кириллица в текстах хода — русский, иначе английский): «Уточните, что нужно: изменить настройку, правило, вопрос о системе или список.», «Please say what you need: a settings change, a rule, a question about the system or a list.». Шаг `route` в `TURN_CALLS` не входит, его сбой — исходы V/11.9 Н1.3, как у шага цикла.
- **Отказ типа:** `refuse` любого из четырёх харнесов несёт поле `other_kind`; `true` — просьба другого типа (правка у `explain`, вопрос у `config`, правило у `found`), правило ставить его — в каждом `system.md`. Только по нему `backend` один раз повторяет `route` с `reason` отказа в сообщении `user` и идёт выбранным типом, проверки отказа V/11.11 Н1.5 у такого `refuse` нет: он не показывается; второй такой отказ или выбран тот же тип — `refused` с `reason`. `refuse` без `other_kind` — обычный исход «отказ».
- Харнес `route` — опыта `plan-neutral` (`assist-pilot` `REPORT-neutral.md`, 9dc2afc), текст тега `bridge-public-24` пилота. **Цена:** шаг около 2 с на реплику. **Предел:** на спорных просьбах выбор ошибается примерно в трети (3,5 % набора, ошибка в них 33 %), человек этого не видит: план виден до «Применить», ответ `explain` подписан, отбор показывает условие словами; ошибочный выбор кончается планом, ответом или списком не того типа, записи без «Применить» нет. Замер на нормах V/11 не делался.

### Н1.7 Ответ на вопрос о системе

ADR-0093 доп. (10) п. 1, (13), (16): тип `explain` — только чтение.

- Харнес — [`harness/explain/system.md`](../harness/explain/system.md), [`harness/explain/tools.json`](../harness/explain/tools.json): инструменты чтения V/11.10 (`list_subsystems`, `get_manifest`, `find_units`, `field_values`, `list_table`, их чтения, ошибки и слова), `rule_state {rule}`, `rule_fires {rule}`, `answer {text}`, `ask_admin`, `refuse`. Инструмента записи нет, проверки плана нет. **Охват** `explain` — `cam`, `rec`, `det`, `auto` (ADR-0093 доп. (16)): у `auto` строки `scenarios` (`find_units`) и таблицы `schedules`, `day_groups`, `modes`, `mode_current`, `windows`, `rule_marks` (`list_table`) — то, что нужно ответу «почему правило не сработает»; читаются дверями консоли по билету из перечня V/11.1 Н1.5, право — `view`; `list_subsystems`, `get_manifest` отдают `auto` только этому типу. Охват `config` не меняется: правка плана со строкой `auto` — отказ проверки `<unit>: not in scope: a rule is changed by a rule request or in the console form` (Н1.3, ADR-0093 доп. (18)).
- **Состояние правила** (ADR-0093 доп. (17)): `rule_state` — элемент `status[]` строки `GET /auto/scenarios/<id>`: фаза, `reason`, `unfit`, `unchecked`, `state.runs` (V/07.3, V/07.4 Н1.11; пульс `GET auto/heartbeats` — слова `servers.status`); `rule_fires` — `GET /events?subsystem=auto&unit=auto/<id>&from=<сейчас − 86400>&limit=50`, новые первыми, как `GET /rules/{id}/fires` V/11.4 Н1.10. **Решила:** окно — сутки, `limit` 50, `late` — умолчание 3600: сработка пишется в бакет своего `t`, `t` близко к `occurred`; `truncated` журнала — словом в результате. Чужое правило — те же двери через `/domain/at/<член>/…`. Правило по имени: два с одним именем — ошибка `several rules are named <имя>`, нет — `no rule <имя>`. Строка `hidden: record` — запись камеры, правилом не называется.
- **Права:** билет, как прочее чтение. Нет права `view` на `auto` (`GET /session` человека: ни одного гранта `view`, область которого покрывает `auto`) — ошибка инструмента `no rights to read rules`, а не пустой список: «правила нет» сказать нельзя. **Предел:** с частью грантов правила вне них не видны, ответ — о видимых.
- Цикл — V/11.9 Н1.2–Н1.5: принятый `answer` кончает ход, остальные вызовы ответа — `not executed`. Событие — `answer {text, context}`: конечное, ничего не пишет; разговор продолжается новым запросом с этим `context`.
- **Обзор полей** — с подписями и вариантами из манифеста: «запись выключена» — режим записи, не `enabled` камеры (`assist-pilot` `REPORT-rules.md`, X13; тег `bridge-public-19`).
- **Предел:** эталон замера проверял названные факты, а не весь ответ: 0 ложных успехов на 30 значит «нужные факты названы»; сработки старше суток `rule_fires` не видит.

### Н1.8 Отбор

ADR-0093 доп. (14), (15); контракт 39ba6a3: `AssistEvent` `found`, `AssistFoundFilter`, `Device.detectorKinds`, фильтр `noDetector`.

- Харнес — [`harness/found/system.md`](../harness/found/system.md), [`harness/found/tools.json`](../harness/found/tools.json): `device_values {field, type?}` — значения поля `Device` в охвате со счётом; охват больше `LIST_MAX` — ошибка `<sub>: more than <LIST_MAX> units — too many to check here`, как у `field_values` V/11.10 Н1.2, `found {text, type?, where}`, `ask_admin`, `refuse`. Модель составляет условие `where` словами контракта: поля `Device`, операторы и пустой список — как условия `find_units` V/11.10 Н1.5, но над полями `Device` (V/11.3), не строк. Поле не из `Device` — ошибка инструмента `<поле>: Device has no such field`, ход идёт. **Обзор полей** — поля `Device` с подписями и вариантами, «запись выключена» — `recordMode` `none`, не `enabled` `false` (X13, `REPORT-rules.md`; вопроса на эти слова нет, ADR-0093 доп. (15) п. 5).
- **Исполняет `backend`, не модель:** `ids` считает код по полям `Device`, выведенным по V/11.3, иначе они выдуманы. Найдено 0 — тоже `found`.
- **Две формы, ровно одна.** Охват — строки, которые надо прочесть, чтобы вывести поля условия: по строкам вида, у камер домена — страницы вида (V/11.3 Н1.2а, ADR-0113 доп. (8)).
  - Охват не больше `LIST_MAX` = 5000 строк на подсистему (V/11.10 Н1.2): `backend` проходит его целиком и отдаёт `ids` по имени, без повторов (контракт), `total` — всех совпавших. Совпавших больше 500 (`selectMax`) и все условия — поля `AssistFoundFilter` — форма `filter` ниже; не выражается им — первые 500 `ids` и `truncated: true`.
  - Охват больше `LIST_MAX`: все условия — поля `AssistFoundFilter`: `q`, `type`, `status`, `domainId`, `noFolder`, `noRecord`, `noDetector` — `filter`: форма листает его тем же ограниченным проходом, что обычный фильтр (V/11.3 «Фильтры `GET /devices` по цене»), `total` нет, `truncated: true`: полного прохода не было. `serverId`, `archiveId`, `folderId` в `AssistFoundFilter` нет: условие на них идёт формой `ids` или отказом. Не выражается — `refused` «больше 5000 устройств: такое условие здесь не проверить, сузьте отбор папкой, сервером или типом» (ADR-0093 доп. (15) п. 4).
- Событие — `found {text, context, conditions, ids | filter, total?, truncated?}`: `text` — слова модели, `conditions` — по строке на условие `where`, переводит `backend`, не модель (**решила**): «<подпись поля>: <вариант>» по подписям и вариантам обзора полей, оператор словом: `eq` — «:», `ne` — «: не», `in` — «: одно из», `not_in` — «: ни одно из», `contains` — «: есть», `not_contains` — «: нет», `exists` — «задано», `missing` — «не задано»; форма показывает их над деревом.
- **Детекторы.** Поле камеры `detectorKinds` (V/11.3, `mapping.tsv`): виды всех её детекторов, выключенных тоже — строки `det/units` с её `cam` и встроенные по `detector-kinds.tsv`, вне таблицы `other`; фильтр `noDetector=<вид>` — тот же вывод. «Камера без детектора движения» — без строки вида вообще. **Предел:** выключенный детектор считается настроенным.
- **Цена:** чтение охвата, до 5000 строк на подсистему, на каждую реплику отбора; условие вне фильтров — чтение записи на камеру. **Предел:** надёжно одно-два условия на полях самой камеры (ADR-0093 доп. (14) п. 2); замер отбора на нормах V/11 не делался.

## Н2 Двери

Своей двери у главы нет: операция хода — контракт за передачей консоли (V/11.1 Н1.5), двери чтения — обратные вызовы
из перечня, дверь модели — V/10.2.

## Н3 Проход

```
POST /assist/turns (поток, билет потока)
  context → переписка (не читается — новый ход); text → тексты хода
  открытый вопрос → тип из context; иначе шаг route (Н1.6): config | rules | explain | found | ask → question
  цикл V/11.9: шаг модели маршрутом /assist/chat/<имя>/… по билету → разбор → инструменты V/11.10 по билету → progress …
    ask_admin → question; refuse → refused; answer → answer (explain)
    found → отбор кодом (Н1.8): ≤ LIST_MAX — ids | filter, > LIST_MAX — filter | refused
    propose_plan → проверка V/11.11: ошибки → valid: false, ход дальше → охват DevicePatch → перевод → plan | refused (field)
  TURN_CALLS, ASSIST_TURN_MAX → refused «ход не завершён»
  поток оборван клиентом до события конца → билет погас, конец; шаг снимает ABANDON двери модели
```

## Н4 Отказы

| Причина | Исход | Кто видит | Что делает вызывающий |

| поле `world` | 422 `VALIDATION_FAILED`, `field: world` | WebUI | — |

## Н5 Приёмка

Векторы ассистента:

[`turn`](../vectors/turn/README.md) (цикл хода; вопрос кончает запрос) исполняет драйвер `backend` над
