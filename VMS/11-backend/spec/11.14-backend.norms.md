# V/11.14 — The kind description and the move to the core: norms

This English text is the source; the Russian translation `ru/spec/11.14-backend.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 14 of lesson V/11 «Бэкенд конфигуратора» (ADR-0080; the VMS module — ADR-0090; the transition of the fork contract — ADR-0116;
the core for plugin kinds — ADR-0115; the fork is the only console — ADR-0112). Lecture (`ru/11-backend.md`, for people, not in the export),
[instructions](11-backend.README.md). The platform is the export `cammeta-specs` `7a875c75`.

Today the fork contract is typed. Kinds are closed enumerations (`DeviceType`, `TreeNode.kind`), the form of each kind is written in
the fork by hand, the translation is the table `mapping.tsv` (chapter 3). The transition leads the contract to the consolem model: kind descriptions
`GET /kinds`, uniform `/units`, profiles `implements`. It goes in stages 0–5, and at each stage one contract is pinned.
The chapter sets norms for the w2c kind model, the sources of the stage 0 agreements, the order of stages with the condition of moving to the next one, and
the chapters that each stage changes. The translation of a manifest into a kind description (Н1.5) is set by norms when the contract of
stage 1 is pinned.

Norm ids are `V/11.14-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-vocabulary).

- **Kind** — `kind` of the contract: a row of the kind table of `backend`. It is not a subsystem: one kind may be assembled from several
  subsystems, one subsystem may have several kinds.
- **Composite kind** — a kind made of parts of several subsystems or tables: a camera is `cam` + `rec` + `det` (chapter 3 Н1.2).
- **Core paths** — the operations of the model: `/kinds…`, `/units…` and the steps of `/operations` by `uid`. **Legacy paths** — the typed
  operations of the contract at the commit of chapter 2 Н1.1.
- **Stage** — one pinned fork contract (chapter 2 Н1.1) and the norms that translate it.

## Н1 Form

**Data.** The chapter has no families of its own. The kind table is lesson data (Н1.1), like `mapping.tsv` (chapter 3 Н1.1).

### Н1.1 The kind model

- **The kind table** is lesson data `data/kinds.tsv`, not norms and not code (ADR-0116 §1 item 1). One row per kind: `kind`; `from` —
  what the kind is assembled from (a subsystem unit — `<sub>` with `unit`; a table row — `<sub>/<таблица>`; an assembly — a listing of parts);
  `write` — how the kind is written (below, "What is published"); `implements` — profiles; `actions`; `events`. The rows of units and tables
  `backend` builds from the subsystem manifests by the translation rule (Н1.5). The assembly row and the `write` of tables with a cascade are written by the lesson.
- **File and paths.** The kind table appears with the stage 1 contract and from then on judges the core paths. The closed kind table
  of chapter 3 Н1.2 and `mapping.tsv` judge the legacy paths until stage 5 removes them (Н1.3).
- **A composite kind — by a profile** (§1 item 2). The VMS camera is the kind `vms.cam` with `implements: [vms.camera/1]`. The camera kinds of plugins are
  their own `kind` with the same profile (addendum (2) item 6): a profile is a common interface, not a kind name. Writing a composite kind by a
  core path is the same translation as by the legacy path: one batch B9, `cas` on the written parts, guards on the others; on a refusal nothing
  is written (chapter 4 Н1.2). There is no second assembly next to the former one: the core path and the legacy path of the camera call one translation,
  therefore their rows are the same. This is the condition of stage 3, Н1.3.
- **Another cluster.** An edit of a record of another cluster by a core path gives the same outcomes as the legacy path (chapter 4 Н1.13;
  addendum (2) item 5). For a camera of another cluster and for a member without a connection this is `409 SERVER_OFFLINE` with `params.targetId`, for a camera also with
  `kept`, and the accepted edit is held.
- **A table row is a kind with its own version** (§1 item 3): `revision` of the row and `If-Match`. A table is not a "document": there is no write of the whole
  table in one body.
- **`uid`** is unique in the domain and stable (addendum (2) item 2). For an object with a legacy id the `uid` is that same id: for a composite kind it is
  `Device.id`, for other records — the UUID v5 of chapter 3 Н1.2. Therefore there is no translation of references between the legacy paths and the core.
  Equal table keys in different clusters give different `uid` and do not merge. For a table row without a legacy id the `uid` is a
  UUID v5 by the rule of the kind record id (chapter 4 Н1.6) from the name `<kind>:<кластер>/<sub>/<таблица>/<ключ>` (addendum (3) item 2): the contract
  holds `uid` as `format: uuid`. There is no stored reverse translation table — it would not know a row written past `backend`: the reverse
  path goes by listings, as for the kind record id (chapter 4 Н1.6), with the memory of `backend` from the listings and the change
  feed; on a miss — the listing of the cluster's kinds, with a limit (addendum (4) item 2).
- **What is published** (addendum (2) item 3; the rule applies before stage 1). Service tables (`service: true`: `backend/undo`,
  `backend/repeats` and the like) are not kinds. Tables that a worker writes (`worker.writes`, P/06.1 Н1.6) are `write: none`:
  only reading and `status`; the table `<т>_seen` of a plugin is not a kind but the `status` of the kind `<т>` (addendum (3) item 3). Temporary subject data (search, jobs, rows with `delete_after`) do not become kinds and
  stay on their own paths. Tables with a cascade or a part of an assembly (`rec/volumes` and the like) are `write: assembly`: they are written
  only by the translation of `backend` (chapter 4), they have no independent write. Other tables are `write: row`. The server judges the write capability
  from stage 2, without waiting for `kindAccess` of stage 4. A refusal is in the form of the stage 2 contract, nothing is written.
- **Subsystem manifests** `backend` reads in the form `GET /manifest/<sub>/source` (P/06.5; addendum (4) item 1, (6) item 1): `{name, rev,
  served, sha256, manifest, secret_defaults}`, the canonical view of the revision the console serves. For it `backend` needs the entry
  `GET manifest/<sub>/source` in `calls` of its manifest — per subsystem whose kinds it builds (with the stage 1 contract; for plugins —
  the fragment V/12.2 Н1.2); the door refuses all others, since the full view carries `domain.books`, `tokens`, `witness` (addendum (7)). `default`
  of the fields `*_secret` is `null` there, the names of such fields are `secret_defaults`; a secret default does not get into the kind description, the form
  sees only "set" (addendum (5)). It rereads them on every `/kinds`.
- **`ETag` of `/kinds`** — the set of `served` revisions of the manifests that `backend` reads, its own included, in canonical order by
  subsystem name, and the answer language (`Vary: Accept-Language`) (addendum (4) items 1, 3): the body and the `ETag` come from one source
  (ADR-0115 addendum (20)). Its own manifest is included because a plugin disabled in its `calls` hides kinds. There are no events `kinds.changed`:
  a manifest change restarts the cluster console and breaks the stream, the client gets `stream.reset` and rereads `/kinds`
  (addendum (3) item 1). `backend` restarts only when its own manifest changes: a new table in the callback listing,
  a new subsystem, a plugin (ADR-0115 addendum (5) item 1).
- **The camera assembly stays the meaning of `backend`.** `recordMode` ↔ rows of `rec`, cascades and the lock in one batch with `cas`
  cannot be expressed by a kind description. Chapters 3 and 4 set norms for them, as now. Only new fields, tables and subsystems
  get by without a hand-made screen and without `mapping.tsv` rows (ADR-0116 Consequences).

### Н1.2 The stage 0 agreements at w2c

The form of the fields is set by the stage 0 contract. This section says only where `backend` takes the values from (§2):

| Agreement | Source at w2c |
|---|---|
| `Problem.field` | On core paths — a JSON Pointer into the request body (P/06.1 «Формат `field`»): `backend` translates the pointer to a field of the door row into a pointer of the kind schema by the translation rule (Н1.5). On legacy paths — the field name, as now (chapter 2 Н1.3, chapter 4), until stage 5 removes them (decision «Р-3 Б»). `errors[]`, `VALIDATION_FAILED` with `params.keyword` — by the stage 0 contract |
| `label {key, text, lang}` | `text` — from `display` of the manifest (`display.fields`, `display.unit`, `display.options`), `lang` — the language of this text. Without a translation in `display.langs` (ADR-0115) and at an `Accept-Language` without a match the text of the manifest goes with its own `lang`, there is no substitution of the language. `key` is built from the names of the kind and the field, not from the text: an edit of a label does not change the key. The interface dictionary takes precedence over `text` (decision «Р-2 В») |
| `version` | An opaque string for `If-Match`, as now: for a kind of one row — the store index of the row, for a composite kind — a concatenation of the indexes of the parts (chapter 4 Н1.1). There is no new version |
| `status` | "Set" (`properties`) — the row fields that the console door writes. "Observed" (`status.observed`) — the heartbeat words and `state` of the subsystem worker. `conditions` and `observedVersion` — by the translation rule (Н1.5) |
| `TreeNode.kind`, `StreamMessage.kind` | Open strings — a rule of the client. `backend` sends only the values of its kind table (Н1.1) and of the message table (chapter 5) |

### Н1.3 Stages

| Stage | What | Condition of moving to the next |
|---|---|---|
| 0 | the agreements of Н1.2 | the API tests in the profile of the stage 0 contract are green; new fields do not break the legacy paths |
| 1 | the core read-only: `GET /kinds`, `/kinds/{kind}`, `GET /units`, `/units/{uid}`, `/units/{uid}/schema`; an unknown kind is shown | all kinds of the table Н1.1 are visible through `/units`, the schemas — by the translation rule (Н1.5) |
| 2 | writing kinds without a profile: `POST`, `PATCH` (Merge Patch with `If-Match`), `DELETE /units`, `actions/{a}`, `validate`, the steps of `/operations` by `uid`; w2c table rows; the plugin kinds of ADR-0115 | the suite `test.unknown` and w2c table rows are written through the core |
| 3 | the profiles of known kinds from the table Н1.1; the hand-made screens of the fork move to profiles; the legacy paths are alive | `PATCH /units/{uid}` of a camera and the legacy path give the same rows `cam`, `rec`, `det` (Н1.1) |
| 4 | rights and rules for the administrator (addendum (8) item 1): `Me` is an administrator with rights to everything, `accessLevels` of a kind, `objectAccess` and `kindAccess` answer "everything is allowed", the server judges rights; events and actions of rules — from kind descriptions | no ADR is needed before the stage: the current rights by subsystems suffice (addendum (8) item 2) |
| 5 | removal of the typed CRUD: `Device`, `DeviceType` and other "create, modify, delete" forms, the `Role`/`RoleGlobal` codes | the tests of stages 1–4 are green; every operation of chapter 2 Н1.2 has a fate; end-to-end acceptance of viewing, PTZ, archive, rights and rules |

- **One stage — one pinned contract** (§3): the fork commit, the copy, SHA-256, the table of operations of chapter 2 Н1.2 and the reconciliation
  by «Спецификация VMS» (ADR-0094 A7). There are six pinnings, one per stage 0–5 (addendum (2) item 6). There is no new pinning for
  every fork commit.
- **Subject operations stay** (addendum (2) item 4). Viewing, PTZ, archive, export and the like are not removed by stage 5. From stage 3
  they accept `uid`; for records with a legacy id it is that same id (Н1.1). A CRUD operation is removed only after a checked replacement of
  each of its scenarios. Its former test coverage is moved into a core profile or into its own suite `acceptance/`, not
  excluded (chapter 6 Н1.2 «Перенос строки»).
- **The norms of a stage are written when its contract is pinned.** The translation is judged by the pinned bytes (chapter 2 Н1.1), and a norm
  written before the contract would describe bytes that do not exist yet. Until the stage is pinned, chapters 2–13 apply over the
  legacy paths.
- **Order.** The next stage is pinned after the condition of the previous one is met on the stand: the API tests in the profile of
  its contract are green (chapter 6 Н1.2), and the condition from the column of the table is met. The stages are the work order of the first generation,
  not a postponement (ADR-0103 addendum (2)).
- **The legacy paths are alive until stage 5.** A client without translation works at stages 0–4. The norms of chapters 2–4 and `mapping.tsv` for the legacy
  paths are not removed at these stages.

administrator, and the operator in the fork contract (ADR-0117 item 9) is a separate decision of the owner after the administrator screens
(addendum (8) items 2, 3).

### Н1.5 Translation of a manifest into a kind description

The rule is set by norms when the stage 1 contract is pinned (Н1.3). The kind description is built by `backend` from the subsystem manifests
(ADR-0115 §1 item 3), not by the subsystem. The table «манифест → `UnitKind`» of the draft of «Консоли»
(`ОТВЕТ-КОМАНДЕ-УНИВЕРСАЛЬНАЯ-МОДЕЛЬ.md`, question 1) is a reference, not canon.

## Н3 Pass

```
stage N: fork contract → pinning (chapter 2 Н1.1) → stage norms (Н1.4) → stand: test profile (chapter 6) and condition Н1.3 → stage N+1
```

**Races.** There are never two pinned contracts at once: `backend` translates one, the last pinned (chapter 2 Н1.1).

## Н4 Refusals

| Reason | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| a core operation earlier than the stage that pinned it | `404 NO_ROUTE` (chapter 2 Н1.2) | client | — |
| writing a kind `write: none` or `assembly` bypassing the translation (Н1.1) | a refusal in the form of the stage 2 contract, nothing is written | client — an error | write through the assembly or do not write |
| an edit of another cluster: a camera or a member without a connection (Н1.1) | `409 SERVER_OFFLINE` (chapter 4 Н1.13) | client | for a camera the edit is held (`kept`); otherwise wait for the connection |
| the stage condition is not met | the next stage is not pinned | «Спецификация VMS», «Консоль» | fix `backend` or the stage norm |

## Н5 Acceptance

At every stage — the consolem API tests in the profile of its contract (chapter 6 Н1.2) and the condition of Н1.3. Stage 3 checks the camera assembly
with its own suite: the core path and the legacy path give the same rows. The checks appear with the stage contract.

The design of chapter 4: one assembly translation for both paths, the order of reading the manifests.
