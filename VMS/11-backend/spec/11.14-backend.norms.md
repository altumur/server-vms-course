# V/11.14 — The kind description and the move to the core: norms

This English text is the source; the Russian translation `ru/spec/11.14-backend.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 14 of lesson V/11 «Бэкенд конфигуратора» (ADR-0080; the VMS module — ADR-0090; the transition of the fork contract — ADR-0116;
the core for plugin kinds — ADR-0115; the fork is the only console — ADR-0112). Lecture (`ru/11-backend.md`, for people, not in the export),
[instructions](11-backend.README.md). The platform is the export `cammeta-specs` `7a875c75`.

The fork contract is the consolem model 0.2.0 as a whole (ADR-0116 addendum (9)): kind descriptions `GET /kinds`, uniform `/units` with the
address `uid`, profiles `implements`; there are no typed paths. The stages 0–5 of the hybrid are removed (addendum (9) item 1): the transition is made
at once. The chapter sets norms for the w2c kind model, where `backend` takes the values of the core agreements from, the contract without stages,
the chapters that the core changes, and the translation of a manifest into a kind description (Н1.5).

Norm ids are `V/11.14-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-vocabulary).

- **Kind** — `kind` of the contract: a row of the kind table of `backend`. It is not a subsystem: one kind may be assembled from several
  subsystems, one subsystem may have several kinds.
- **Composite kind** — a kind made of parts of several subsystems or tables: a camera is `cam` + `rec` + `det` (chapter 3 Н1.2).
- **Core paths** — the operations of the model: `/kinds…`, `/units…` and the steps of `/operations` by `uid`. **Legacy paths** — the typed
  operations of the former contracts (`/devices`, `/servers`, `/folders`, `/archives`, `/volumes`, `/domains/{id}` and the like): the contract 0.2.0
  has none of them (chapter 2 Н1.2).

## Н1 Form

**Data.** The chapter has no families of its own. The kind table is lesson data (Н1.1), like `mapping.tsv` (chapter 3 Н1.1).

### Н1.1 The kind model

- **The kind table** is lesson data [`data/kinds.json`](../data/kinds.json), not norms and not code (ADR-0116 §1 item 1). Per kind of the
  lesson: `from` — what the kind is assembled from (the places of the row `—` of `mapping.tsv`: a table, a console door, an assembly of several
  parts); `write` — how the kind is written (below, "What is published"); `description` — the `UnitKind` that `GET /kinds` gives out:
  `label`, `parents`, `createParents`, `children`, `implements`, `capabilities`, `access`, `schema`, `actions`, `events`, `x-archive`,
  `x-ui-category`. **Decided:** the table is built from the reference set `fixtures/demo.json` of the pinned commit (the source of the profile
  tables of the fork's `api/BACKEND.md`), narrowed to the translation: the properties of `schema` are the rows `properties.<имя>` of
  `mapping.tsv` (`readOnly` for `way` `read` and `const`, `writeOnly` for `write`), the capabilities, parents, children, actions and events —
  what `backend` translates (chapter 2 Н1.2). The kinds of plugins and of table rows without a lesson row `backend` builds from the manifests
  by the translation rule (Н1.5). **Decided:** `profiles` of the table — the `Profile` entries of the reference set for the profiles its kinds
  implement; `GET /kinds` gives them as `profiles`.
- **File and paths.** The kind table judges the core paths, which are the only paths of the contract (Н1.3). `mapping.tsv` (chapter 3 Н1.1)
  maps the properties of a kind onto the places of the subsystems.
- **A composite kind — by a profile** (§1 item 2). The VMS camera is the kind `camera` with `implements: [vms.camera/1, vms.live/1, vms.ptz/1, vms.timeline/1]`.
  **Decided:** the kind codes of w2c are the codes of the contract and of its sets — `domain`, `server`, `folder`, `camera`, `det`,
  `ipsrv`, `channel`, `sensor`, `relay`, `mic`, `spk`, `storage`, `eventsrc`, `acfa`, `acfa_sensor`, `acfa_lock`, `acfa_fence`, `stream`,
  `volume`, `archive.local`, `archive.network`, `archive.backup`, `archive.edge`, `archive.incidents`: the API tests of the set `one-domain`
  name the kinds by these codes (`/units?kind=camera`). The camera kinds of plugins are
  their own `kind` with the same profile (addendum (2) item 6): a profile is a common interface, not a kind name. Writing a composite kind by a
  core path is the same translation as by the legacy path: one batch B9, `cas` on the written parts, guards on the others; on a refusal nothing
  is written (chapter 4 Н1.2). The camera assembly of chapter 4 is that translation: the core path writes the same rows as the former
  legacy path did.
- **Another cluster.** An edit of a record of another cluster by a core path gives the same outcomes as the legacy path (chapter 4 Н1.13;
  addendum (2) item 5). For a camera of another cluster and for a member without a connection this is `409 SERVER_OFFLINE` with `params.targetId`, for a camera also with
  `kept`, and the accepted edit is held.
- **A table row is a kind with its own version** (§1 item 3): `revision` of the row and `If-Match`. A table is not a "document": there is no write of the whole
  table in one body.
- **`uid`** is unique in the domain and stable (addendum (2) item 2). For an object with a legacy id the `uid` is that same id: for a composite kind it is
  the device id of the former contracts, for other records — the UUID v5 of chapter 3 Н1.2. Therefore there is no translation of references between the legacy paths and the core.
  Equal table keys in different clusters give different `uid` and do not merge. For a table row without a legacy id the `uid` is a
  UUID v5 by the rule of the kind record id (chapter 4 Н1.6) from the name `<kind>:<кластер>/<sub>/<таблица>/<ключ>` (addendum (3) item 2): the contract
  holds `uid` as `format: uuid`. There is no stored reverse translation table — it would not know a row written past `backend`: the reverse
  path goes by listings, as for the kind record id (chapter 4 Н1.6), with the memory of `backend` from the listings and the change
  feed; on a miss — the listing of the cluster's kinds, with a limit (addendum (4) item 2).
- **What is published** (addendum (2) item 3). Service tables (`service: true`: `backend/undo`,
  `backend/repeats` and the like) are not kinds. Tables that a worker writes (`worker.writes`, P/06.1 Н1.6) are `write: none`:
  only reading and `status`; the table `<т>_seen` of a plugin is not a kind but the `status` of the kind `<т>` (addendum (3) item 3). Temporary subject data (search, jobs, rows with `delete_after`) do not become kinds and
  stay on their own paths. Tables with a cascade or a part of an assembly (`rec/volumes` and the like) are `write: assembly`: they are written
  only by the translation of `backend` (chapter 4), they have no independent write. Other tables are `write: row`. The server judges the write capability
  by the kind table, not by `kindAccess` (chapter 8). A refusal is in the form of the contract, nothing is written.
- **Subsystem manifests** `backend` reads in the form `GET /manifest/<sub>/source` (P/06.5; addendum (4) item 1, (6) item 1): `{name, rev,
  served, sha256, manifest, secret_defaults}`, the canonical view of the revision the console serves. For it `backend` needs the entry
  `GET manifest/<sub>/source` in `calls` of its manifest — per subsystem whose kinds it builds (for plugins —
  the fragment V/12.2 Н1.2); the door refuses all others, since the full view carries `domain.books`, `tokens`, `witness` (addendum (7)). `default`
  of the fields `*_secret` is `null` there, the names of such fields are `secret_defaults`; a secret default does not get into the kind description, the form
  sees only "set" (addendum (5)). It rereads them on every `/kinds`.
- **`ETag` of `/kinds`** — the set of `served` revisions of the manifests that `backend` reads, its own included, in canonical order by
  subsystem name, the SHA-256 of `kinds.json` of the instance, and the answer language (`Vary: Accept-Language`) (addendum (4) items 1, 3): the body and the `ETag` come from one source
  (ADR-0115 addendum (20)). Its own manifest is included because a plugin disabled in its `calls` hides kinds. There are no events `kinds.changed`:
  a manifest change restarts the cluster console and breaks the stream, the client gets `stream.reset` and rereads `/kinds`
  (addendum (3) item 1). `backend` restarts only when its own manifest changes: a new table in the callback listing,
  a new subsystem, a plugin (ADR-0115 addendum (5) item 1).
- **The camera assembly stays the meaning of `backend`.** `recordMode` ↔ rows of `rec`, cascades and the lock in one batch with `cas`
  cannot be expressed by a kind description. Chapters 3 and 4 set norms for them, as now. Only new fields, tables and subsystems
  get by without a hand-made screen and without `mapping.tsv` rows (ADR-0116 Consequences).

### Н1.2 The core agreements at w2c

The form of the fields is set by the contract. This section says only where `backend` takes the values from (§2):

| Agreement | Source at w2c |
|---|---|
| `Problem.field` | On core paths — a JSON Pointer into the request body (P/06.1 «Формат `field`»): `backend` translates the pointer to a field of the door row into a pointer of the kind schema by the translation rule (Н1.5). The operations outside the core keep the field names of their schemas, as the contract says (chapter 2 Н1.3, chapter 4; decision «Р-3 Б»). `errors[]`, `VALIDATION_FAILED` with `params.keyword` — by the contract |
| `label {key, text, lang}` | A kind of the lesson — the texts of `kinds.json` (Н1.1). Otherwise `text` — from `display` of the manifest (`display.fields`, `display.unit`, `display.options`), `lang` — the language of this text. Without a translation in `display.langs` (ADR-0115) and at an `Accept-Language` without a match the text of the manifest goes with its own `lang`, there is no substitution of the language. `key` is built from the names of the kind and the field, not from the text: an edit of a label does not change the key. The interface dictionary takes precedence over `text` (decision «Р-2 В») |
| `version` | An opaque string for `If-Match`, as now: for a kind of one row — the store index of the row, for a composite kind — a concatenation of the indexes of the parts (chapter 4 Н1.1). There is no new version |
| `status` | "Set" (`properties`) — the row fields that the console door writes. "Observed" (`status.observed`) — the heartbeat words and `state` of the subsystem worker. `conditions` and `observedVersion` — by the translation rule (Н1.5) |
| `TreeNode.kind`, `StreamMessage.kind` | Open strings — a rule of the client. `backend` sends only the values of its kind table (Н1.1) and of the message table (chapter 5) |

### Н1.3 One contract without stages

- **The contract 0.2.0 as a whole** (addendum (9) items 1, 2): one pinned contract (chapter 2 Н1.1), the core paths only. The stages 0–5
  of the hybrid, their six pinnings and the conditions of moving are removed; there is no stage contract and no legacy path to keep alive.
- **What the model does not remove** (addendum (9) item 1): a kind ≠ a subsystem (Н1.1), the camera assembly and the cascades are the meaning of
  `backend` (chapter 4), the rights — the screens only for the administrator (addendum (8); chapter 8).
- **Subject operations** — viewing, PTZ, archive, export and the like (addendum (2) item 4) — are the paths `/units/{uid}/…` and their own
  paths of the contract (chapter 2 Н1.2); for a record with a legacy id the `uid` is that same id (Н1.1). The former test coverage of a removed
  typed operation is moved into the profile of the contract or into its own suite `acceptance/`, not excluded (chapter 6 Н1.2 «Перенос строки»).
- **The norms are written by the pinned bytes** (chapter 2 Н1.1): what the contract does not have does not get a norm ahead of it.
- **Order** — the first generation (ADR-0103 addendum (2)): the chapters of Н1.4 move onto the core together with the pinning.

### Н1.5 Translation of a manifest into a kind description

The description `UnitKind` is built by `backend` (ADR-0115 §1 item 3), not by the subsystem; the keywords of `schema` are those of the contract
schema `JsonSchema` (`readOnly`, `writeOnly`, `x-label`, `x-ref`, `x-immutable` and the like). The table «манифест → `UnitKind`» of the draft of
«Консоли» (`ОТВЕТ-КОМАНДЕ-УНИВЕРСАЛЬНАЯ-МОДЕЛЬ.md`, question 1) is a reference, not canon.

1. **A kind of the lesson** — a kind of [`kinds.json`](../data/kinds.json): `description` as is (Н1.1). A record narrows it by `Unit.writable` and
   `Unit.capabilities` (chapter 3); `schemaPerUnit` is not set, and `GET /units/{uid}/schema` gives the schema of the record's kind.
2. **A kind of a table** — the table `<т>` of the manifest of a plugin `psim-<id>` (V/12.1; ADR-0115 §1 item 2) and a table of a subsystem
   `write: row` that `kinds.json` does not describe ("What is published" above):
   - `kind` — `<plugin_id>/<т>` for a plugin, `<sub>/<таблица>` otherwise (**decided**: as the contract example
     `security_controller/CONTROLLER`); `origin` — `{system: "w2c", subsystem: <sub>}`, for a plugin also `plugin`;
   - `label` — `display.tables.<т>` (V/12.1 Н1.4), none — the table name; `parents` — `[null]`; `access` — none: the kind gets
     `view < edit < admin` and the class equal to its code (the contract);
   - `capabilities` — `create` and `delete` when the console writes the table (not `worker.writes`), `rename` when the table has the field `name`;
   - `schema` — `type: object`, `additionalProperties: false`, a property per field of the table: `type`, `enum`, `default` and the keys of
     `schema` of the field (limits, `pattern`) as is; `required` — the fields with `required: true`; `x-label` — `display.fields.<т>.<поле>`
     (Н1.2); `readOnly` — a field of `worker.writes`; `writeOnly` — a secret field `*_secret`, its `default` is not given out (Н1.1);
     `x-ref {kinds}` — a field with `ref` to the family of another kind; a `hidden` field is not in the schema, and a write keeps its value;
   - `actions` — the commands of the kind (V/12.1 Н1.5): `{id: <команда>, label, execution: "instant", params}`; `events` — the events
     `<т>.<событие>` of `events.kinds` with the labels `display.kinds`;
   - the table `<т>_seen` is the `status.observed` of the kind `<т>` (Н1.1), not a kind.
3. **Who changes what.** A kind of the lesson changes with `kinds.json` of the release; a kind of a table — with the manifest (`ETag`, Н1.1).

## Н4 Refusals

| Reason | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| an operation outside the pinned contract | `404 NO_ROUTE` (chapter 2 Н1.2) | client | — |
| writing a kind `write: none` or `assembly` bypassing the translation (Н1.1) | a refusal in the form of the contract, nothing is written | client — an error | write through the assembly or do not write |
| an edit of another cluster: a camera or a member without a connection (Н1.1) | `409 SERVER_OFFLINE` (chapter 4 Н1.13) | client | for a camera the edit is held (`kept`); otherwise wait for the connection |
