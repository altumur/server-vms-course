## Подготовка

Стенд домена VMS (общий README приёмки VMS, «Стенд домена VMS»): `@domain m1`, на `m1` установлены манифесты `VMS/01-cam/cam.subsystem.yaml`, `VMS/02-rec/rec.subsystem.yaml`,
`VMS/04-det/det.subsystem.yaml`, `VMS/05-detjob/detjob.subsystem.yaml`, `VMS/06-detedge/detedge.subsystem.yaml`, `VMS/07-auto/auto.subsystem.yaml`, `VMS/11-backend/backend.subsystem.yaml`, контроллеры всех семи. Консоль — `CONSOLE_ROOT=cam` (`member m1 console`), `backend` смонтирован:
`member m1 console2` — префикс `/backend`, поэтому API контракта — `member m1 console2 … /api/…`. Воркер `b-srv-a-1` запускает сценарий, держателей `cam`, `rec`, `det` и вычислителя `auto` на стенде нет: сценариям
нужны строки, а не камеры; строки держателя `cam/devices`, `cam/children` в `11-devices`, `cam/found` в `14-discovery` и `cam/rule_state` в `20-motion` кладёт дверь `member m1 store`, как память в `05-resume`: это двойник держателя. Без комплектов TLS: обратный вызов — сокетом роли на петле (ADR-0094 доп. (6) п. 4). Файл подсистемы `backend` не задан: `/test/*` наборам не нужны.
Манифесты на `hold` — те же: `PUT /domain/shared` судит поле по манифесту держателя (P/08.9 Н1.3), `auto` там обязателен для `40-domain-parts`. Текущий человек после `@domain` — `root`, пароль `w2c test root password`; `@person -` — без токена. Каждый сценарий — на чистом экземпляре.

Id записей выводит V/11.4 Н1.6, поэтому сценарии пишут их значениями, кластер в именах — `m1`, у `device:` первые 12 бит — раздел `m1`, `ca0`; домен — `$dom`: `root` стенда случаен, id берётся из `GET /api/domains`; камеры `1`, `2`, `3` — `ca08e8ba-11ab-5128-97e6-d03888680c2e`, `ca07be2d-dfe2-5601-b0b3-f4eba44b12f8`, `ca0ca265-e670-5862-92f2-bfae90f7da31`, человек `root` — `6ad9a883-cad5-5ab8-802f-0889506a2358`, роль `admin` — `cd290440-e663-50ed-bef1-7b3cdbab3c03`.

Камеры сценариев — с разными `ip`: у `source` стоит `unique: canonical`. Сценарий `05-resume` кладёт строку `backend/repeats/<h>` дверью `member m1 store`: пакет шага и его итог ложатся вместе (V/11.4 Н1.4), поэтому такая строка и есть состояние
воркера, убитого между шагами, а сигнал в нужный миг дал бы гонку. `h` и `body` — SHA-256 по V/11.4 Н1.4 от байтов запроса следующего шага; поля строки — столбцы таблицы `repeats`
манифеста, `steps` — текст JSON (форма, как у `@as console store` приёмки P/06.2). В `04-repeats` нечитаемая строка положена той же дверью: `@spoil row` на стенде домена нет.

Ожидание — `@until` по наблюдаемому признаку. Сны — `09-stream`, `14-discovery`, `@stream-none s1 10` — верхняя граница с запасом: сообщение о правке доходит до потока за такт ленты консоли (1 с) и опрос `backend`.
Правка раньше начала подписки потоку не видна (V/11.5 Н1.2), а заголовки ответа начала не доказывают. Поэтому у `s1` видимая правка идёт после `@stream-none`, а у `s3` начало подтверждено `stream.reset`: `Last-Event-ID` иной формы отвечает им до первой правки.

**Чтением** (состояние не наблюдается): обрыв живого потока при падении воркера — `s3` закрыт раньше, директивы «поток закрылся» нет; строка «начато» до
снимка и итог шага в одном пакете с шагом — внутреннее; срок памяти и строк поиска `delete_after` — 86400 с стенду не дождаться; обрыв обратного вызова посреди записи — нет сбоя между воркером и консолью.
