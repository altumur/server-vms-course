`member m1 console2` — the prefix `/backend`, so the contract API is `member m1 console2 … /api/…`. The worker `b-srv-a-1` is started by the scenario; there are no holders of `cam`, `rec`, `det` nor the `auto` evaluator on the stand: the scenarios

The ids of the records are derived by V/11.4 Н1.6, so the scenarios write them as values; the cluster in the names is `m1`, the first 12 bits of `device:` are the section of `m1`, `ca0`; the domain is `$dom`: the `root` of the stand is random, the id is taken from `GET /api/domains`; the cameras `1`, `2`, `3` are `ca08e8ba-11ab-5128-97e6-d03888680c2e`, `ca07be2d-dfe2-5601-b0b3-f4eba44b12f8`, `ca0ca265-e670-5862-92f2-bfae90f7da31`, the person `root` is `6ad9a883-cad5-5ab8-802f-0889506a2358`, the role `admin` is `cd290440-e663-50ed-bef1-7b3cdbab3c03`.

The scenario cameras have different `ip`: `source` has `unique: canonical`. The scenario `05-resume` puts the row `backend/repeats/<h>` by the door `member m1 store`: the package of a step and its result land together (V/11.4 Н1.4), so such a row is exactly the state
of a worker killed between steps, while a signal at the right moment would give a race. `h` and `body` are SHA-256 by V/11.4 Н1.4 of the bytes of the request of the next step; the fields of the row are the columns of the table `repeats`
of the manifest, `steps` is JSON text (the form is as in `@as console store` of acceptance P/06.2). In `04-repeats` the unreadable row is put by the same door: there is no `@spoil row` on the domain stand.

The wait is `@until` by an observable sign. Sleeps — `09-stream`, `14-discovery`, `@stream-none s1 10` — an upper bound with a margin: a message about an edit reaches the stream within a tick of the console feed (1 s) and a `backend` poll.
An edit made before the start of the subscription is not seen by the stream (V/11.5 Н1.2), and the answer headers do not prove the start. Therefore for `s1` the visible edit goes after `@stream-none`, and for `s3` the start is confirmed by `stream.reset`: a `Last-Event-ID` of another form answers them before the first edit.

**By reading** (the state is not observed): the break of a live stream when the worker falls — `s3` is closed earlier, there is no directive «поток закрылся» ("the stream closed"); the row «начато» ("started") before
the snapshot and the step result in one package with the step — internal; the expiry of the memory and of the search rows `delete_after` — 86400 s, the stand cannot wait that long; a break of the callback in the middle of a write — there is no failure between the worker and the console.
