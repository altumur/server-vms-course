# V/11.4 — Перевод чтений и записей: нормы

Канон главы 4 урока V/11 «Бэкенд конфигуратора» (ADR-0094 A3, A6; доп. (2) пп. 3, 4). Лекция (`ru/11-backend.md`, для человека, в выгрузку не входит),
[инструкция](11-backend.README.md), таблица [`data/mapping.tsv`](../../data/mapping.tsv), контракт
[`consolem.openapi.json`](../../consolem.openapi.json). Платформа — выгрузка `cammeta-specs` `7a875c75` (пин VMS; приращение прав поверх норм B, ADR-0090 доп. (17); пометка «норма платформы B» — где глава на них опирается).

Текст производный от `spec/11.4-backend.norms.md`, руками не правится: источник — английский [`spec/11.4-backend.norms.md`](../../spec/11.4-backend.norms.md), правка идёт в него, русский пересобирается переводом (ADR-0121).

Глава 3 говорит, какой вид consolem какой подсистеме отвечает. Эта глава — как `backend` собирает запись вида из строк
подсистем, как разбирает правку обратно по строкам, как сверяет версию, что помнит о повторах и как переводит отказ
консоли в отказ контракта. Всё — обратными вызовами по билету запроса на двери перечня (V/11.1 Н1.5).

Id норм — `V/11.4-MM`; соответствие — [`id-map.tsv`](../../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../../Platform/common/ru/NORMATIVE-TERMS.md). Правила модуля «Платформа» — [P/01.1
Н0](../../../../Platform/01-store/ru/spec/01.1-store.norms.md#n0-словарь-слов).

- **Часть** — строка подсистемы, из которой собрана запись вида: у камеры — строка камеры `cam/cameras/<id>` (пустой
  `main`) и её потоки (`cam/cameras` с `main` = id), её записи `rec/recordings` и детекторы `det/units` (глава 3 Н1.2).
- **Индекс хранилища** — версия строки хранилища (P/01.1): не повторяется (рост доп. (4) не обещает); у надгробия строки
  — свой индекс (P/06.1; ADR-0094 доп. (2) п. 4 (в), доп. (3) п. 9; не надгробие тела `.gone/` ресурса).
- **Групповая запись** — `POST /units` (создание), `POST /objects/delete`, `POST /rules/update` и приём `POST /operations` контракта:
  несколько объектов одним запросом с `idempotencyKey` в теле; **шаг** — один элемент `items`.
- **Запись**, **`uid`** — запись `Unit` вида из `GET /kinds` и её адрес (глава 14 Н1.1, глава 3 Н1.2); коды видов и пути
  свойств — по [`data/kinds.json`](../../data/kinds.json) и [`data/mapping.tsv`](../../data/mapping.tsv).
- **Пакет** — пакетная запись хранилища B9 дверью консоли (ADR-0094 доп. (9); норма платформы B):
  у каждой записываемой строки свой `cas`, у прочитанных незаписываемых — стражи; всё или ничего.
- **Скрытый член** — член папки, которого нет в составе, что видит форма: поток камеры, вторая строка `type: ipsrv` хоста, член вне перечня читателя (Н1.7).
- **Корень цели** — строка операции, по которой консоль судит занятость (P/06.9 Н1.3): Н1.8.
- **Кластер входа**, **своё**, **чужое** — глава 3 Н1.2а. **Связка** — одна хранимая правка из нескольких строк, `POST /domain/edits` (P/08.6 Н1.3б): Н1.13.

## Н1 Форма

**Время.** Срок памяти повторов — `delete_after` таблицы `repeats`: его считает консоль от первого наблюдения версии
строки, не время хранилища, и строку снимает жнец платформы (Н1.4); стенных часов `backend` память не судит (разбор ревью V/11, Codex № 7, вопрос 3).

**Данные.** Части читаются и пишутся дверями консоли по билету (V/11.1 Н1.3). Своя семья главы — память повторов
группового ключа: таблица манифеста `backend/repeats/<h>` (Н1.4; форма — поля таблицы `repeats`
[манифеста](../../backend.subsystem.yaml): семья таблиц платформы — со схемой `manifest`, P/06.1 Н1.6), дверью таблиц
и пакетной дверью консоли по билету (V/11.1 Н1.5).

### Н1.1 Сборка записи (чтение)

- Камера (вид `camera`, `GET /units/{uid}`, элемент `GET /units?kind=camera`) — строка камеры `cam/cameras/<id>` (пустой `main`, `type: camera`), её потоки (строки `cam/cameras`
  с `main` = id), записи `rec/recordings` про эту камеру (`cam` записи — её id, V/02.1) и детекторы `det/units` про неё
  (`cam`, V/04.1), всё — дверями единиц консоли (`GET /<sub>/<rows>`), слова пульса — `GET /<sub>/<rows>` (`rows`, P/06.1
  Н2). Поля — строками `mapping.tsv` (глава 3); `properties.recordMode` — из записей `<cam>`, `<cam>-<том>` (глава 3 Н1.3). Строка
  `cam/cameras` с непустым `main` — поток своей камеры: отдаётся записью вида `stream` под камерой (Н1.15), не камерой.
- Детектор, том — одна строка своей подсистемы (глава 3 Н1.2); хранилище — строка тома и записи на нём (`retentionDays`);
  правило и библиотека — Н1.10, Н1.11. Строка записи камеры и `cam/rule_state/<id>` читаются тем же снимком (глава 3 Н1.3).
- Дерево устройства (глава 3 Н1.3 «Дерево») читается тем же снимком: таблицы `cam/devices`, `cam/children`, `cam/child_settings`, `cam/device_units` — дверями таблиц (`GET /cam/devices`, P/06.1 Н1.6), строки с индексом. Строки `cam/devices/<хост>` нет — `channels`, `videos` не сказаны: `ipsrv` есть только по строке `type: ipsrv`, `videoChannel` нет. Строка нечитаема (`garbled`) — поля не прочитаны, а не отсутствуют: записи этого хоста (`ipsrv`, каналы, камеры) в `GET /units` не отдаются, чтение одной — 503, как нечитаемая папка (Н1.7). Значение `type` вне перечня не отдаётся: слово не прочитано (V/01.1 Н1.1б). 403 двери таблицы — часть не видна, отказа нет, как у надгробий (ниже): `ipsrv` и `parentId` выводятся по строке и адресу (глава 3 Н1.3), молчат `channels`, `properties.subtype`, `properties.videoChannel`, каналов нет, часть `h` пуста.
- Id записи вида — Н1.6.
- Чужая запись — те же сборки из вида домена, без двойного чтения: глава 3 Н1.2а.
- **Чужая запись** собирается теми же правилами из вида домена (глава 3 Н1.2а). Версия — та же склейка с `revision` строки вместо индекса: индекса и надгробий в виде нет, поэтому часть снятой строки пуста, и версия чужой записи может вернуться к прежней. Двойного чтения нет. Одна запись через разные входы имеет две версии: `If-Match` сверяется с версией того входа, что её выдал; после смены входа — 412 и перечитывание.
- **Версия** записи (`Unit.version`) — непрозрачная строка контракта, сравнивается только на равенство (ADR-0094 доп. (4) п. 1); контракт 0.2.0 её не меняет (глава 14 Н1.2). У
  детектора, тома, `channel`, `storage`, потока, единицы — индекс хранилища строки; у строки `eventsrc`, `acfa` — индекс этой строки. У камеры — склейка индексов частей в постоянном порядке: `c<индексы
  cam>.r<индексы rec>.d<индексы det>.h<индекс cam/devices>.i<индекс строки ipsrv>.s<индекс cam/rule_state>.a<индекс строки записи>`: после буквы части — индексы её строк через `-` (у `c` — строка камеры, затем её
  потоки; у прочих — в порядке ключа строки, байты UTF-8), у удалённой строки `rec`, `det` — индекс её надгробия, у
  части без строк — пусто (`c17.r.d.h.i.s.a`, `c17-18.r21-30.d44.h9.i31.s52.a60`). Строка заказа (`made`) частью не бывает: её ведёт вычислитель (глава 3 Н1.3). Строки `cam/devices` хоста, `ipsrv` и `cam/rule_state` входят в версию (от них зависят `parentId`, `properties.videoChannel`, `status.observed.armed`), но не в стражи пакета: их полей правка не пишет, а предел стражей занят частями (Н1.2). Это предел: их смена между снимком и пакетом правку не отменяет, запись `events`, `videos` соседа меняет версию камеры без видимой правки, а снятие строки `ipsrv` возвращает пустую часть, и версия может вернуться к прежней при той же видимой записи. У `ipsrv` — `h<индекс cam/devices>.c<индекс строки>`, у ребёнка — `k<индекс cam/children>.s<индекс cam/child_settings>`; части нет — пусто. Дети — свои записи, в версию камеры не входят; `properties.subtype` у `ipsrv` от детей зависит, но в версию их не берёт: смена описания пишет и строку `cam/devices`. У хранилища — `v<индекс тома>.r<индексы записей с home =
  том>` (от записей зависит `properties.retentionDays`; разбор ревью V/11, Codex № 13). Индекс — провод P/01.1 Н2 (десятичные
  цифры), поэтому буквы, точка и `-` склейку не путают. Строки `rec` и `det` части — строки этой подсистемы про камеру
  (`cam` строки — id камеры) и надгробия таких строк; надгробия частей не убираются, пока камера жива (доп. (4) п. 1
  (в)). Потоки и записи хранилища входят живыми строками: надгробие потока не находится (у строки `cam` нет `about`),
  надгробие записи — по камере, не по тому. Поэтому версия камеры или хранилища может вернуться к прежней, если поток
  или запись тома завели и сняли мимо `backend`; видимая запись при этом та же — её поля — функция тех же строк тех же
  индексов (открытый пункт README: строгое «не возвращается» продукта).
- Индексы: индекс строки — в элементе списка `GET /<rows>` и таблиц (норма платформы B4; разбор
  ревью V/11, вопрос 6); надгробия частей камеры — `GET /<rows>?deleted=1&about=<cam>` → `{deleted: [{id, index, revision}]}`
  (надгробие хранит значение `about`; B4, доп. (5) п. 1); 403 этой двери — часть не видна: надгробий этой подсистемы в
  склейке нет, отказа нет; индекс надгробия своей записи — `ETag` ответа `DELETE` и
  сообщение ленты. Двери одной строки у консоли нет: «404 с `ETag` надгробия» (доп. (3) п. 9) заменено этим чтением. До
  B4 двери консоли индекса не отдают, и версии записи `backend` выдать не может: глава действует после приращения
  платформы (вместе с B1, без которого передачи `backend` нет, V/11.1 Н1.3).
- Поля не из строк частей (пульсы, сервер держателя) в версию не входят (глава 3 Н1.3; разбор ревью V/11,
  Claude С-1).
- **Версия зависит от смотрящего** (ADR-0094 доп. (12) п. 12). Строки части, которых человек не видит, в склейку не входят:
  перечень отдаёт только разрешённые. Два человека с разными правами получают разные версии одной камеры, и `If-Match` сверяется с
  версией того, кто пишет. Часть без `view` страж не стережёт; строка, которой он не видит, в пакете отказывает тем же словом,
  что отсутствующая: наружу это 412.
- **Чтение двойное** (там же): строк частей две двери, поэтому снимок читается дважды подряд, пока индексы двух чтений не совпадут; не
  совпали за три попытки — 503: снимка, годного для версии, нет. У `GET /units` снимок — вся страница, попытка — пара полных чтений, 503 — ответу целиком.
- Ответ — `ETag` записи вида — её версия строкой в кавычках (`"c17.r21-30.d44.h9.i.s.a"`); `If-Match` сверяется равенством
  строки целиком.

### Н1.2 Разборка правки (запись)

Своя запись. Чужая — те же строки связкой: Н1.13.

- **Тела** (глава 3 Н1.1). `PATCH /units/{uid}` — JSON Merge Patch `UnitPatch {name, folders, properties}` (RFC 7396): `properties`
  сливаются с записью, `null` снимает свойство по правилу «`null` у `both`» главы 3 Н1.1, массив заменяется целиком; `folders` — Н1.7; родителя
  меняет только `POST /units/{uid}/move` (Н1.14). `POST /units` принимает строки `UnitCreate` с `children` (Н1.5). Шаг `patch` операции — то же
  тело, что `PATCH`, шаг `createUnit` — как строка (Н1.8). `field` отказа — JSON Pointer в тело (`/name`, `/properties/<p>`,
  `/children/<i>/…`; глава 14 Н1.2).
- **`POST /units/validate`** — проверки Н1.3 и этого раздела без пакета и без памяти ключа: элемент `{uid, patch}` — как
  `PATCH /units/{uid}` без сверки версии (`If-Match` у запроса нет), `{create}` — как строка `POST /units`. Ответ — `{items: [{index,
  ok, errors?}]}`, `errors` — отказы в форме `ProblemError` (`code`, `field`, `params`), всё, что показывает один снимок; `identifier` и
  пределы — по тому же снимку (контракт: «по возможности системы»). **Решено:** `uid` без записи — `errors: [{code: NOT_FOUND, field:
  /uid}]`: другого места для этого в контракте нет.

- **Постоянные ключи частей** (разбор ревью V/11, вопрос 1 (а)): записи и детекторы, которые создаёт `backend`, — с
  ключами от камеры: основная запись — `rec/recordings/<cam>`, резервная на томе `<том>` — `rec/recordings/<cam>-<том>`,
  детектор — `det/units/<cam>-<kind>` (образец V/04), второй того же вида — `det/units/<cam>-<kind>-<n>`: `n` — наибольший номер живых строк и надгробий этой пары из снимка + 1, не меньше 2. Одновременное создание одной части сходится на одном `cas ""`:
  второй пакет — отказ, ничего не записано.
- **Замок устройства — строка камеры** (вопрос 1 (б)). Каждый пакет части камеры **пишет** строку `cam/cameras/<id>` —
  `cas` её индекса из снимка, значение прежнее или новое: правка камеры, её записи или детектора, создание и удаление
  детектора, удаление камеры. Две записи одного устройства упорядочены строкой камеры: вторая — 412. Удаление камеры
  и запись её части не проходят обе.
- **Запись устройства — один пакет** (ADR-0094 доп. (9) п. 3). Правка камеры (`PATCH /units/{uid}`): строка камеры
  (замок), записываемые части — каждая с `cas` своего индекса **из того же снимка**, по которому сверена версия (Н1.3),
  не перечитанным; прочие части устройства из снимка — потоки, строки `rec` и `det` камеры — **стражами** с их
  индексами. Пакет проходит целиком или не проходит: изменилась хоть одна строка снимка — 412 консоли, не записано
  ничего. Часть, которой ещё нет, пишется в пакете поверх её надгробия с `cas` его индекса, если надгробие было в снимке,
  иначе — созданием (`cas ""`). Правка детектора (вид `det`) — пакет из строки `det` и строки его камеры
  (замок); `zone` с фигурой — ещё дверь тела маски (глава 3 Н1.3 «`zone`»). Строки про камеру, созданные мимо `backend` (прямые двери консоли) после снимка, пакет не стережёт: их видит
  следующее чтение — новая `version`.
- **`recordMode`** — переход по записям `<cam>`, `<cam>-<том>` (глава 3 Н1.3; разбор ревью V/11, вопрос 2), в одном пакете
  с прочей правкой:
  - `always` — основная `<cam>` `enabled: true`, `replica_from` пуст; её нет — создание на томе `archiveId` тела, а без него — 422
    `VALIDATION_FAILED`, `field: /properties/archiveId`;
  - `replica` — основная `<cam>` `enabled: true`, `replica_from` по `replicaFrom`, без поля — `device`, непустое не меняется (глава 3 Н1.3); её нет — так же создание;
  - `none` — все записи `<cam>`, `<cam>-<том>` — `enabled: false`;
  - `motion` (ADR-0111 п. 4) — основная `<cam>` `enabled: false`, её нет — создание на томе `archiveId` тела, а без него — 422 `VALIDATION_FAILED`, `field: /properties/archiveId`; строка записи камеры (глава 3 Н1.3) в том же пакете: нет — создание с `auto/next_id`, как у камеры, есть — запись с `cas` снимка; `recordDetectorIds` тела — её цель и `enabled`, поля нет — цель прежняя;
  - `backup` — 422 `NOT_SUPPORTED`, `field: /properties/recordMode`: только элемент `extraArchives` (глава 3 Н1.3);
  - `sched` (глава 3 Н1.3) — как `motion`, у строки записи `when` пуст, `conditions: [{kind: time, schedule}]`; `recordScheduleId` нет или расписания нет — 422 `VALIDATION_FAILED`, `field: /properties/recordScheduleId`, значение, равное нынешнему, не судится: камеру со снятым расписанием править можно; `recordScheduleId` без `sched` пропускается; встроенное — запись несёт его строку `cas ""`, если её нет (Н1.11).
  Уход из `motion`, `sched` снимает строку записи в том же пакете; переход между ними переписывает `when`, `conditions`, `enabled` и `minutes` строки. `archiveId` при `motion`, `sched` пишется и в `archive` её действия. Пакет с `auto/scenarios` судится правом сценария на весь кластер (`cluster_rows`, V/07): без него — 403 всего пакета, режим не меняется, это предел.
  `archiveId` — `home` основной `<cam>` (`null` — снять основную, `DELETE` в пакете; том `backup`, `edge` — 422 `NOT_SUPPORTED`, том с `admits: false` — 422 `VALIDATION_FAILED`, `field: /properties/archiveId`, глава 3 Н1.3); `extraArchives` — набор дополнительных:
  элемент — строка `<cam>-<том>`, элемент тома `edge` (глава 3 Н1.3) эхом пропускается без записи (`recordMode` элемента `null`, `always` — `enabled: true`, `replica_from` пуст, у новой строки на томе `backup` ещё `when: offline`; `replica` — `enabled: true`, `replica_from`: `device`, непустое не меняется (глава 3 Н1.3); `none` — `enabled: false`; иное — 422
  `NOT_SUPPORTED`; `stream` — `stream` записи; `when` нынешней строки не меняется), строки вне набора снимаются; `stream` — `stream` основной; основной нет
  и тело её не создаёт (в том числе `archiveId: null` в том же теле) — 422 `VALIDATION_FAILED`, `field: /properties/stream` (разбор
  ревью V/11, дополнение Kimi, № 8). Новая запись — со сроком хранилища своего тома (глава 3 Н1.3). Основная, созданная
  `archiveId` без `recordMode` в том же теле, — `enabled: false`: режим не меняется.
- **Создание строки устройства** (`POST /units`, строка вида `camera`, `ipsrv`, `eventsrc`, `acfa` с `parentId: null`) — один пакет; `kind` строки — поле `type` строки хранилища, адрес — глава 3 Н1.3 «Адрес устройства»: счётчик `cam/next_id` (`cas` прочитанного,
  значение `n + 1`; значение и индекс — `GET /cam/next_id`, P/06.1 Н2 «Дверь счётчика»), строка `cam/cameras/<n + 1>` (`cas ""`), записи `<n + 1>`, `<n + 1>-<том>` и детекторы
  `<n + 1>-<kind>` из `children` (строки вида `det`) и полей записи — записи и детекторы только у `camera` (ADR-0111 п. 3: строка `camera` и все её записи получают `ref` = `<CLUSTER>-<n + 1>`, запись, заведённая позже, — `ref` строки камеры; основная в домене одна: V/02.9 Н1.6; норма платформы B9, `POST /console/batch`, P/06.1 Н2 «Пакетная дверь»:
  номер называет вызывающий, счётчик идёт в том же пакете; разбор ревью V/11, вопрос 9). `n` —
  значение счётчика, прочитанное до пакета: последний выданный номер, новой камере — следующий (P/06.1 Н1.3). Счётчик
  сдвинули — 412 `row moved` с `key: cam/next_id`, пакет строится заново с новым чтением (Н1.4). **`identifier` создания** — проверка, а не ключ: строка `cam/cameras/<identifier>` жива и не выдана этой группой (`steps` строки `<h>`) — отказ строки 409 `IDENTIFIER_TAKEN`, `field: /properties/identifier`, до прочих проверок элемента: мастер нумерует строки сам, а счётчик может быть впереди его дерева, номера своей группы значения не занимают; иначе значение пропускается: номер выдаёт счётчик, ответ несёт выданный. Мастер шлёт номер при каждом импорте CSV, считая его по своему дереву, поэтому свободный номер — не отказ. Создание детектора (строка вида `det`, `parentId` — камера, или дочерняя строки камеры) — пакет из строки ключа выше (`cas ""`, надгробие в снимке — `cas` его индекса) и строки камеры (замок); `kind` строки хранилища — `properties.detectorKind`, его нет — 422 `VALIDATION_FAILED`, `field: /properties/detectorKind`; `name` строки — поле `title` (глава 3 Н1.3). Создание хранилища
  (`POST /units`, строка вида `archive.*` с первым томом в `children[0]`, вид `volume`) — строка `rec/volumes/<name>` (`cas ""`) из свойств хранилища и тома (том = то же
  хранилище: `disk`, `sizeBytes`, адрес — строки `volume` из `mapping.tsv`); второй элемент `children` — 422 `NOT_SUPPORTED`, `field: /children/1`: у вида `volume` нет `create` (`kinds.json`), том — само хранилище.
- **`configMode`** (ADR-0107 доп. (1)) — поле запроса создания камеры, не поле строки; связи с источником нет. `current` — ничего. `default` — в `resolution`, `fps` новой строки значения модели из `device-catalog.json`; свойства `res`, `fps` тела важнее. Это меняет настройку камеры: держатель передаст их драйверу обычным путём (V/01.2 Н1.2а). Модели нет (`rtspUrl`) или её нет в файле — 422 `VALIDATION_FAILED`, `field: /properties/configMode`. `template` — тем же пакетом разовая копия с камеры `templateId` той же модели, видимой читателю: `resolution`, `fps`, `firmware`, строки её прочих потоков с `profile`, `source` — как «Потоки за камерой» (глава 3 Н1.3), поток на ином хосте не копируется, у каждого свой номер счётчика; поля тела важнее. Адрес, логин, пароль, имя, записи, папки, детекторы, `norm` детей не копируются. Источника нет или `vendor`, `model` разные — 422 `VALIDATION_FAILED`, `field: /properties/templateId`. Поток сверх `DEVICE_PARTS_MAX` — как у прочих частей.
- **Встроенный детектор** (вид `det`, `properties.builtin: true`; глава 3 Н1.3). Создание — `parentId` основная камера с адресом `ipint://`; её `vendor`, `model` нет в `device-catalog.json` — 422 `NOT_SUPPORTED`, `field: /properties/builtin`. `properties.template` тела — детектор модели, вне `detectorOptions` — 422 `VALIDATION_FAILED`, `field: /properties/template`. Не назван — детекторы модели, чей вид по `detector-kinds.tsv` равен `detectorKind`: нет — 422 `NOT_SUPPORTED`, `field: /properties/detectorKind`; один — он; несколько — 422 `VALIDATION_FAILED`, `field: /properties/template`. Номер и пакет — как у единицы, ниже; `title` — `name`, `folders` не пуст — 422 `NOT_SUPPORTED`, `field: /folders` (Н1.7): строка не единица прав. **Правка** — `name`, `properties.enabled`, `properties.sensitivity`, строка целиком с `cas` снимка, строка камеры — страж; `detectorKind`, `model` — 422 `NOT_SUPPORTED`, `field` — указатель свойства. **Снятие** — как у единицы. Право — `admin` на строку камеры (`rights.unit_of`, V/01.1 Н1.5). `children` камеры с `builtin: true` — те же шаги в пакете создания камеры.
- **Удаление камеры** (`DELETE /units/{uid}`, с `If-Match` — Н1.3) — один пакет: снятие строки камеры, её потоков, записей, детекторов
  и строки записи (контракт: «вместе с дочерними»), каждой с `cas` её индекса из снимка. **Удаление детектора** — пакет: снятие строки
  `det`, запись строки камеры (замок) и строки записи этой камеры без него, если он в цели. Прочие правила — каскад Н1.10.
- **Включение камеры, выключенной правилом** (глава 3 Н1.3; V/01.4 Н1.4д): `PATCH /units/{uid}` `properties.enabled: true`, шаг `patch` (Н1.8), пока выключение действует, — просьба `cam` `disable` со сроком в прошлом; строка камеры с `enabled: true` поля не получает, строка с `enabled: false` получает его пакетом. Прочие поля тела — обычный пакет, раньше просьбы; только `enabled` — пакета нет, версия сверяется снимком (Н1.3). `POST /cam/requests` по билету (P/06.3 Н1.9): `{unit: <cam>, action: disable, disabled_by_rule: <значение строки>, disabled_until: 0}`, `Idempotency-Key` — hex SHA-256 от `enable`, нулевого байта, `<cam>`, нулевого байта и индекса строки `cam/rule_state`: повтор той же правки — та же просьба. Подача повторяется тем же ключом, пока не придёт 200 с меткой, в пределах срока маршрута `api/units`. `performed` — запись читается заново. Метки нет к сроку, `expired`, `gone`, `unknown` — 409 `DEVICE_OFFLINE`, `field: /properties/enabled`; `refused`, отказ двери — по Н4, `field: /properties/enabled`; у шага — итог `fail`, `params.field: /properties/enabled` (Н1.8), прочие поля при этом записаны. Шаг операции подаёт просьбу до пакета итога, ключ тот же. В стопку отката просьба не ложится: строки записи нет. **Предел:** выключение вернётся только новой сработкой, откат и `retry` его не дают.
- **`ipsrv`** (ADR-0102 доп. (5) п. 5, доп. (6) пп. 6, 7, 10). Строка `type: ipsrv` есть — `PATCH`, шаг `patch` пишут её одним пакетом, `cas` индекса снимка: `name`, свойства `enabled`, `short`, `lat`, `lon`, `azimuth`, `mac`, `login`, `password`, свойства адреса; `DELETE` снимает её, камеры хоста остаются и теряют только родителя, если `channels` не больше 1. Смена хоста — отказ (глава 3 Н1.3). Строки нет (`status.observed.derived: true`) — `PATCH` и `DELETE` — 422 `NOT_SUPPORTED`, `field` — указатель первого поля тела, у `DELETE` — `field: /kind`, `params.capability: delete` (глава 2 Н1.2).
- **`eventsrc`, `acfa` строкой** — одна строка: `PATCH`, шаг `patch` пишут её с `cas` индекса снимка, `DELETE` снимает её и строки `cam/device_units` на ней одним пакетом, из папок снимает консоль тем же пакетом. Камера и `ipsrv` с единицами — так же. Строка `cam/unit_next` остаётся: id строки не повторяется.
- **Единицы** (`acfa_sensor`, `acfa_lock`, `acfa_fence`, `relay` единицы, `acfa` с родителем; V/01.1 Н1.2б). Создание — по `parentId`; `acfa` с родителем — строка `type: controller`, адреса `ip`, `vendor` нет, адрес единицы — `path`: запись основной строки `cam/cameras` (корень) или единица, её `camera` — `camera` новой; у записи `ipsrv` — строка `type: ipsrv` её хоста, из двух наименьший id числом. Иной родитель, в том числе `ipsrv` без строки, — `PARENT_MISMATCH`, `field: /parentId` (Н1.5). **Шаблон** — по [`unit-templates.tsv`](../../../01-cam/data/unit-templates.tsv): строки с `vendor` адреса строки `camera`, `parent` — шаблон родителя (`-` у корня), `type` — `kind` строки, у `acfa` — `controller`; адрес не `ipint://` — строк нет. Нет строк — 422 `NOT_SUPPORTED`, `field: /kind`. Одна — она. Несколько — выбирает `properties.model`; не назван или вне них — 422 `VALIDATION_FAILED`, `field: /properties/model`. Промежуточные узлы заводятся по одному, сверху вниз: цепочку `backend` сам не строит, узлу может быть нужен свой адрес; два узла одного шаблона различает их id. Единица в `children` строки — 422 `NOT_SUPPORTED`, `field: /children/<i>/kind`: единицы заводятся своими строками с `parentId`.
  **Номер.** Прочитать снимком `cam/unit_next/<строка>` и строки `cam/device_units` этой строки: `n` — большее из значения счётчика и наибольшего номера живых строк, счётчика нет — 0, живых строк нет — 0: строку могли завести дверью таблиц мимо счётчика. Счётчик не читается — 503: снятый номер мог бы вернуться. Пакет: `cam/unit_next` со значением `n + 1` и `cas` снимка (`""`, если строки нет), `cam/device_units/<строка>-<n + 1>` с `cas ""`, стражи основной строки и единицы-родителя. В группе — номера подряд. 412 по любой из этих строк — пакет строится заново с новым чтением (Н1.4).
  **Правка** — строка целиком с `cas` снимка: `name`, `properties.enabled`, `properties.path`; `properties.model` — 422 `NOT_SUPPORTED`, `field: /properties/model`; родитель не переносится (`move` не возможность вида). **Снятие** (`DELETE`, элемент `/objects/delete`) — единица и все вложенные одним пакетом, каждая с `cas`; не вмещается в пакет — 422 `NOT_SUPPORTED`, `field: /kind`. Право — `admin` на основную строку (`rights.unit_of`, V/01.1 Н1.5), `folders` — 422 `NOT_SUPPORTED`, `field: /folders` (Н1.7).
- **`channel`, `storage`** правки и `DELETE` не имеют (`write: none`, возможности в `kinds.json` пусты): свойство — 422 `NOT_SUPPORTED`, `field: /properties/<p>` (вне `Unit.writable`), `DELETE` — 422 `NOT_SUPPORTED`, `field: /kind`, `params.capability: delete`; карта камеры w2c — глава 3 Н1.3 «`storage` камеры w2c».
- **Дети** (`sensor`, `relay`, `mic`, `spk`). Создания и удаления нет (нет `create`, `delete` в `kinds.json`; реле единицы — выше): строка `POST /units`, шаг `createUnit` — 422 `NOT_SUPPORTED`, `field: /kind`, `params.capability: create`, `DELETE`, элемент `/objects/delete` — так же с `delete`. `PATCH` правит `name`, `properties.enabled`, `properties.norm`; прочие поля — по `way` главы 3. `POST` таблицы — полная замена строки, поэтому `PATCH` сливает: читает строку `cam/child_settings/<id>` снимком, берёт её `title`, `enabled`, `norm`, поверх — поля тела, пишет строку целиком с `camera`, `type`, `number` из ключа, `cas` индекса снимка или `""`, в одном пакете со стражем строки `cam/children/<id>`. Право — `edit` на хозяина (`rights.routes`, V/01.1 Н1.5). Ребёнок `gone` или с мёртвым хозяином — 404 `NOT_FOUND`.
- **Каскады хранилища** (разбор ревью V/11, Codex № 14, Claude С-16) — один пакет на объект:
  - `DELETE /units/{uid}` записи `archive.*` — «камеры не удаляются»: у камеры, чья основная `<cam>` на этом томе, основной становится
    первая дополнительная `<cam>-<Y>` по имени тома, кроме томов `backup` (основная `<cam>` получает `home: Y` и поля той записи; `replica_from`, называвший `<cam>`, снимается: иначе источник — она сама; `<cam>-<Y>`
    снимается), такой нет — основная снимается (`recordMode: none`), записи на `backup` остаются; дополнительные `<cam>-<том>` на этом томе
    снимаются; записи с иными именами на томе снимаются; строки затронутых камер пишутся (замок); затем снятие строки
    тома;
  - пакет больше предела B9 — отказ консоли, ничего не записано (Н4).
- **Предел частей.** `DEVICE_PARTS_MAX` = 56: потоков, записей и детекторов устройства (ADR-0094 доп. (12) п. 4). Он не выше предела
  стражей: стражи — части, цепочка папки до 7 и страж поколения дают 56 + 7 + 1 = 64 (`BATCH_GUARDS`); записи — камера, части,
  счётчик, строка `<h>`, папка, членство, итог и счётчики шага дают 1 + 56 + 6 = 63 ≤ 64 (`BATCH_WRITES`), строка `backend/undo` — 64. Строка записи камеры и `auto/next_id` считаются двумя частями. `backend`
  держит его при создании части: запись `POST /units`, `PATCH /units/{uid}` сверх предела — 422 `VALIDATION_FAILED`, `field:
  /properties/extraArchives` или `/parentId`. Части, созданные мимо `backend`, предел обходят: такой пакет — 413 консоли, строка Н4.
- **Папки при удалении.** Камеру и детектор из папок снимает консоль тем же пакетом (P/06.8 Н3 «удаление единицы дверью»); `backend`
  этих строк не называет. Вес держит Н1.7 `DEVICE_FOLDERS_MAX`.
- **Отказ пакета** — любой строки: `cas` или страж (412), права, проверка строки, предел пакета — отказ всего пакета без
  записи (доп. (9) п. 2); ответ — отказ контракта (Н4), при 412 — с текущей записью вида. Записанного наполовину
  устройства не бывает.

### Н1.3 Сверка версии

- Запись без `If-Match` — 428 `PRECONDITION_REQUIRED` (контракт). Порядок проверок и 412 у чужой записи те же, снимок — вид домена (Н1.13).
- После 428 тело сверяется со схемой контракта (`UnitPatch`): неизвестное поле, тип, `enum` — 422 `VALIDATION_FAILED`, `field`,
  `params.keyword`. Затем цель: нет — 404 `NOT_FOUND`. **Решено:** затем `properties` по схеме вида цели (`kinds.json`;
  `additionalProperties`, `readOnly`, тип, `enum` — 422 `VALIDATION_FAILED`, `field: /properties/<p>`, `params.keyword`) и `Unit.writable`
  записи (422 `NOT_SUPPORTED`, `field` — указатель; глава 3 Н1.1): схема вида известна только с целью, а сверка тела
  остаётся раньше версии, как прежде; затем версия (ниже); затем поля по `way` (глава 3 Н1.1). `DELETE /units/{uid}` идёт тем же
  порядком без тела; `POST /units/{uid}/move` — Н1.14.
- `backend` читает части записи одним снимком и считает её версию (Н1.1); не совпала с `If-Match` — 412
  `VERSION_MISMATCH`, `current` — текущая запись вида (контракт). `If-Match` камеры — версия всего устройства. Совпала —
  пакет (Н1.2): строка камеры пишется, записываемые части с `cas`, прочие стражами, индексы — из того же снимка (ADR-0094
  доп. (9) п. 3). Правка **любой** строки снимка, кроме `cam/devices` и строки `ipsrv` хоста (Н1.1), между сверкой и записью — 412 консоли по пакету, ничего не записано;
  ответ — 412 `VERSION_MISMATCH` с текущей записью вида. Перекоса по частям нет: прежнее ограничение (доп. (3) п. 5)
  снято доп. (9) — `412` значит «ничего не изменилось», связанные поля строк `rec` (`recordMode`, `archiveId`,
  `extraArchives`) при одновременных правках не расходятся. **Предел:** `412` говорит только об этом запросе. У одиночной
  правки ключа нет (Н1.4 — группы и шаги), запрос без ключа автоматически не повторяется (P/06.1 Н2 «Двери тел и таблиц»): ответ консоли потерян —
  502–504, исход неизвестен, и повтор клиента с прежним `If-Match` на свою же легшую правку получает 412 (`DELETE` — 404,
  создание хранилища — занятое имя). Исход после неответа — чтением.

### Н1.4 Память повторов группового ключа — своя таблица, всегда

- Групповая запись несёт `idempotencyKey` в теле (контракт). `backend` помнит её **всегда** (не «до B3») и общей для
  экземпляров памятью — своей таблицей манифеста `backend/repeats/<h>` (разбор ревью V/11, вопрос 3; Codex № 2, 3, 5–7,
  Claude Б-2, С-6–С-9). `h` — SHA-256 (hex строчными) от байтов `user`, нулевого байта и внешнего `idempotencyKey`
  (`user` — человек билета). Служебная семья `<sub>/idem/` консоли — не её. Чтение — дверь таблиц консоли по билету
  (V/11.1 Н1.5), запись с `cas`, в том числе `cas ""`, — строка таблицы в `POST /console/batch`: таблица `service: true` (P/06.1 Н1.6, ADR-0094 доп. (15) п. 3) читается и пишется только по живому
  билету от листа роли `backend`, правом следствий, `may` человека не проверяется — людям строк на `sub: backend`
  перевод прав не даёт. Строка — `{h, user, idem_key, op, body, state, steps}`: `op` — `operationId` группы (`createUnits`, `deleteObjects`, `createOperation`, `updateRules`, `createExport`), `body` — SHA-256
  (hex) байтов тела запроса, `state` — `started` | `done`, `steps` — итоги шагов `[{index, outcome: done | failed, id?,
  code?, field?}]` текстом JSON: поле `json` кончается на 4000 байтах (P/06.1 Н1.4), группа длиннее. Форма — поля таблицы `repeats` манифеста со схемами полей (семья таблиц платформы — со схемой
  `manifest`, P/06.1 Н1.6); исход нечитаемой строки — ниже.
- **Какие операции** (контракт 0.2.0: тела с `idempotencyKey`). Память — эта таблица у `createUnits` (`POST /units`, Н1.5),
  `deleteObjects` (`POST /objects/delete`, Н1.5), `createOperation` (приём `POST /operations`, Н1.8), `updateRules` (`POST /rules/update`,
  Н1.10) и `createExport` (`POST /exports`, глава 20 Н1.2). Ключ у `createUnits` необязателен: **Решено:** без него строки `<h>` нет, строки
  исполняются как в первый раз, повтор заводит заново, пакеты строк идут без ключа, как одиночная правка (Н1.3 «Предел»). Вне этой таблицы:
  `runRule`, `retryRuleFire` — ключ — `Idempotency-Key` просьбы вычислителю, память — консоли (Н1.10); `runUnitAction` — ключ, если он есть, —
  `Idempotency-Key` просьбы устройству (Н1.17); `runKindAction` — вопрос модели ничего долгого не пишет, повтор — новый вопрос (Н1.9);
  `checkExport` ничего не пишет (глава 20 Н1.2). У одиночных `PATCH`, `DELETE /units/{uid}` и `POST /units/{uid}/move` ключа нет (Н1.3
  «Предел»): приём сервера `move` — одиночная правка, память операции покрывает только её шаг `move` (Н1.14).
- **Порядок.** Первым — память, потом версия:
  1. Строка `<h>` создаётся `cas ""` — `{state: started, steps: []}` — **до** снимка и до первого шага.
  2. Создать не вышло (строка есть) — её читают. `user` и `idem_key` строки не те, что у запроса, — 422
     `VALIDATION_FAILED`, `field: idempotencyKey` (`/idempotencyKey` у `POST /units` и `POST /operations`; совпадение `h` разных ключей); `op` или `body` не те — то же 422
     (ключ занят иным телом; кода «ключ занят» в контракте нет); `state: done` — ответ из `steps` (ниже) без обращений к
     частям; `state: started` — ответ по завершении: повтор продолжает ту же группу (ниже), его ответ — из `steps`,
     когда строка `done`.
  3. Шаг: снимок и сверка версии элемента (Н1.3), затем пакет устройства (Н1.2), и в **том же пакете** — строка `<h>` с
     итогом шага в `steps` (`cas` её индекса): итог и запись шага ложатся вместе или не ложатся (норма платформы B9: пакет
     несёт строку таблицы `backend/repeats`). Отказ шага (ничего не записано) — итог `failed` пишется отдельно, `cas`
     строки `<h>`.
  4. После последнего шага — `state: done`, `cas` строки.
- **Повтор при `state: started`** — первый запрос ещё идёт или оборвался (жив ли он, `backend` не видит): повтор идёт
  по той же группе. Шаги с итогом в `steps` не исполняются снова и не сверяют версию; прочие — по порядку (шаг 3).
  Исполнителей может быть два, и их упорядочивает строка `<h>`: каждый пакет шага несёт её `cas`. Шаг создания (версии у элемента нет)
  ответил 412 по строке с прочитанным индексом — `cam/next_id`, `cam/unit_next`, строка папки и её цепочка (Н1.7), строка камеры детектора, основная строка и единица-родитель единицы, строка `cam/device_units`, `det/units` с `cas ""` — это не итог: строку сдвинул другой запрос,
  шаг строится заново с новым чтением этих строк и строки `<h>` (Н1.2, «Ключи шагов»), отказ даёт уже новое чтение: папки нет — `NOT_FOUND`. Иной 412 — строку `<h>` перечитать: итог шага в ней есть (его записал другой исполнитель) — шаг окончен, иначе — итог
  `failed` с кодом по Н4. `409 in flight` и `422 key reused` — строку `<h>` перечитать, итог есть — шаг окончен. Итога нет: при `422 key reused` прежний пакет под этим ключом отказан и не записан — итог `failed` `VERSION_MISMATCH`; при `409 in flight` другой исполнитель занял ключ — ответ 503 (Н4), `<h>` остаётся `started`. Сделанный шаг не отвечает 412 на свою же запись: его итог лёг с ним в одном пакете.
  Оборванная группа так доходит до конца повтором.
- **Ответ из памяти:** `id` шага — корневая запись; элемент `done` — запись вида, прочитанная сейчас, у `POST /units`
  `units` — она и дочерние; запись снята или скрыта — элемент опускается; у `/objects/delete` — её `uid` или id правила; элемент `failed` —
  сохранённые `code` и `field`; форма — `{done, failed}` группы; у `createOperation` — операция (Н1.8), у `createExport` — глава 20 Н1.2.
- **Нечитаемая строка** `<h>` — элемент `garbled` или значение не по полям таблицы манифеста (обязательные, `enum`,
  `pattern`), судит `backend` — неизвестный исход: 503 (код — глава 2 Н1.3), не повтор и не исполнение заново; строка не
  переписывается.
- **Срок** — `delete_after` таблицы `repeats`, 86400 с, как память повторов консоли (P/06.1 Н3): считает консоль от
  первого наблюдения версии строки, не время хранилища, поэтому срок может только удлиниться; строку снимает жнец
  (глава 6.4 Н3 `tables`; ADR-0094 шаг 3б). Строки нет — запрос первый. У приёма операции `OPS_KEEP` (P/06.9 Н1.6) не меньше этого
  срока, но часы разные, поэтому Н1.8 «Память и операция» называет, что бывает на стыке.
- **Ключи шагов.** `Idempotency-Key` обратного вызова шага — hex SHA-256 от `h`, нулевого байта и десятичной записи номера шага; у шага создания дальше — нулевой байт и десятичная запись прочитанного `n`, если пакет берёт номер, и за нулевым байтом индекс каждой прочитанной строки пакета вне `<h>` и счётчика, в порядке пакета (`cas ""` индекса не несёт) —
  64 знака, один сегмент, в пределах ключа консоли (200 байт, P/06.1; разбор ревью V/11, Claude С-9). Ключ считается от прочитанного, а не от числа попыток: `cas` строк в отпечаток не входит, отказ двери лежит в памяти консоли, снимает заявку только `412 row moved` (P/06.1 Н3 «память повторов», «пакет» шаг 5), поэтому шаг, построенный заново, и повтор после смерти исполнителя со сдвинутой строкой идут новым ключом. Повтор после
  потери ответа на тот же пакет приходит с тем же ключом, и консоль отвечает сохранённым ответом (B3, B9).
- «Без своего состояния» воркера (ADR-0094 A3) читается так: без состояния вне хранилища платформы. Процесс воркера
  своей памяти между запросами не держит, кроме кэша снимков таблиц домена (глава 3 Н1.2а): он только ускоряет, пропал — полное чтение, исход запроса от него не зависит.

### Н1.5 Групповая запись — по элементу

- `POST /units` (`createUnits`; разбор ревью V/11, Codex № 5, Claude С-6): строка `items` — `UnitCreate {kind, parentId, name, domainId,
  folders, properties, candidateId, children}` — создание записи с дочерними одним пакетом (Н1.2), в кластере Н1.13 «Кластер новой записи»;
  `domainId` — `Domain.id` (Н1.6). **Решено:** цель `x-ref`, которой нет, — неизвестный `domainId` или `parentId` или цель свойства с `x-ref` в `kinds.json` (`properties.serverId` камеры…) — `failed` `VALIDATION_FAILED`, `field: /domainId` | `/parentId` | `/properties/<p>`, `params.keyword: x-ref` (контракт); в `PATCH` и шагах — тот же отказ 422. Вид без `create` в `kinds.json` или вне `GET /kinds` —
  `failed` `NOT_SUPPORTED`, `field: /kind`, `params.capability: create` (глава 2 Н1.2, глава 14 Н1.1). `parentId` — по `createParents` вида и по Н1.2:
  у камеры — `null` или `uid` `ipsrv` её хоста, у детектора и потока — камера, у единицы — основная строка или единица (Н1.2), у `acfa` —
  `null` или то же, у хранилища `archive.*` — сервер (кластер хранилища, Н1.13), у папки — `null` или папка (Н1.7), у прочих —
  `null`; иная существующая запись — `failed` `PARENT_MISMATCH`, `field: /parentId`. `folders` не пуст — папки по Н1.7, в домене — отдельным шагом после
  записи; `candidateId` — находка уходит из итога (Н1.9); занятый `identifier` — `failed` `IDENTIFIER_TAKEN`, `field:
  /properties/identifier` (Н1.2). `children` — строки видов из `children` вида родителя с `create`, в том же пакете: у камеры — детекторы
  (Н1.2) и, **Решено:** потоки (Н1.15 «`POST`»: контракт «Дочерние объекты, создаются вместе», `stream` — в `children` у `camera` с
  `createParents: [camera]`), у хранилища — его единственный том (Н1.2); иной вид — `failed` `NOT_SUPPORTED`, `field: /children/<i>/kind`. Итог —
  `{done: [{index, units}], failed: [{index, code, field?, params?}]}`: `units` — созданная запись и её дочерние, прочитанные после записи, с `folders`.
- **Групповая правка записей** — шаги `patch` в `POST /operations`, для быстрой записи с `wait: true` (Н1.8; ADR-0113 доп. (10) п. 1: сверх
  500 — несколькими операциями): каждый шаг — отдельная правка записи, свой пакет на запись (Н1.2, Н1.3 с `expectedVersions` вместо
  `If-Match`; доп. (9) п. 3); исход — `OperationItem` по шагу.
- `POST /objects/delete`: элементов до `selectMax`, больше — 422 `VALIDATION_FAILED`, `field: items`. Каждый элемент `{id, version}` — удаление записи своего вида со сверкой версии: `id` — `uid` записи или id правила; версия — `Unit.version` или `r<revision>` записи камеры-кластера из перечня (глава 3 Н1.2б), обе формы; `r<revision>` сверяется с `revision` строки вида и только у камеры-кластера, у прочих — `failed` `VERSION_MISMATCH`, снятие — Н1.13; вид — по
  `uid` (Н1.6: `archive.*` и `volume` одной строки различаются `uid`), правило — Н1.10, каскад — как у одиночного `DELETE /units/{uid}` (Н1.2), пакет на
  объект; папка — дверью снятия папки с `If-Match` (Н1.7) и ключом шага (Н1.4), итог хранится в `steps` отдельной записью, `cas` строки `<h>`, как `failed`: обрыв между ними — повтор получает сохранённый 200, итог `done`; запись вида без `delete` в `kinds.json` (`volume`: том отдельно не снимается; `server`, `domain`, `channel`, `storage`, дети) — `failed` `NOT_SUPPORTED` (глава 2 Н1.2); детектор камеры, снятой раньше в том же теле, — `done`. Итог — `{done: [id…], failed: [{id, code}…]}`.
- Элементы исполняются по порядку тела; отказ элемента не останавливает следующие; частичный успех — по элементам,
  элемент в `failed` не записан ничем, кроме чужого с `kept` (Н1.13). Память — Н1.4.
- Неответ шага (502–504, обрыв) — не итог: `failed` не пишется, группа останавливается, ответ — Н4, `<h>` остаётся
  `started`; повтор идёт тем же ключом шага (Н1.4).

### Н1.6 Id записи вида

- **Id с контрактом 0.2.0 не меняются**: `uid` записи — её прежний id по этому разделу (глава 14 Н1.1, глава 3 Н1.2); ссылка
  на запись — `parentId`, `folders`, `properties.archiveId`, `RuleTarget.include[].uid`, `expectedVersions` — несёт тот же `uid`.
- Id записей контракта — UUID. `backend` выводит UUID детерминированно — UUID версии 5 (RFC 9562, SHA-1) над
  пространством имён урока; имя — байты UTF-8 строки `<вид>:<кластер>/<место>` (разбор ревью V/11, вопрос 10; ADR-0110 доп. (5) п. 4): одна запись через
  любой `backend` получает один id, поэтому кластер стоит в имени и своих записей. `<кластер>` — `CLUSTER` члена, чья строка: у своей — свой, у чужой —
  поле `cluster` вида домена. У записи из строки хранилища `<место>` — ключ строки `<sub>/<rows>/<id>` или `<sub>/<таблица>/<имя>` как он записан, без нормализации
  (регистр, Unicode, `/` — как есть; ADR-0094 доп. (3) п. 10 (7)); `<вид>` — `device`, `archive`, `volume`, `candidate`, `rule`, `ruleVersion`; у записей
  без строки хранилища — перечень главы 3 Н1.2 (`server:`, `event:`, `ruleFire:`). Записи `archive.*` и `volume` одной
  строки `rec/volumes/<name>` получают разные id. `<вид>` — слово имени, а не код вида: всякий вид устройства, в том числе `stream`, — `device`.
- Записи домена одни на домен, кластера в имени нет (перечень главы 3 Н1.2): `folder:`, `user:`, ключи ролей и групп; так же постоянные `schedule:`, `mode:`.
- **`domain`.** Имя — `domain:<root>`, `root` поля `domain` ответа `GET /session`: постоянный знак домена, id не зависит от входа, вида и связи. Поля нет — кластер вне домена, своя запись, `domain:<CLUSTER>`. `null` — домен не прочитан: запись `domain` не выводится, 503 (глава 3 Н1.2а). 404 `no domain here` у `GET /domain` при поле `domain` — вид ещё не готов, только своё, id прежний. При входе кластера в домен `Domain.id` и `domainId` всех записей меняются один раз.
- **Раздел в id** (ADR-0113 доп. (22)): всякая запись `device:` всякого члена, `class: camera`, `class: server` и свой кластер, дети камеры — биты её члена. Id — UUID v5 по правилу выше, затем первые 12 бит заменены первыми 12 битами SHA-256 от байтов UTF-8 имени члена: раздел члена (P/08.3 Н1.1). Форма UUID та же, версия и вариант на месте, контракт не меняется. Записи прочих видов — без замены.
- Обратный путь. `device:`: биты — раздел своего кластера, запись своя — дверями кластера (у удалённой — по надгробиям камеры); иначе одна строка раздела и таблицы только этого члена (глава 3 Н1.2б «Запись по id»), не проход серверов. Прочие виды — по перечню строк вида: свои — дверями кластера, чужие — по виду домена. Кластер вне домена — чужая запись не находится; связи нет — 503 (глава 3 Н1.2а).
- Ссылки (`parentId`, `properties.archiveId`, `properties.serverId`, `domainId`) — тем же правилом: кластер ссылки — кластер строки, на которую она указывает; поле строки называет ключ в кластере
  самой строки, если вид не говорит иного. Пространство имён — константа урока `BACKEND_NS` = `4ffc0b08-e8bd-4a4e-b7fb-d4ecc8a83ecb`.

### Н1.7 Папки

Папка — строка домена, у члена копия только для чтения (ADR-0110 доп. (5) п. 3; P/08.5 Н1.8, P/06.8 Н1.2а). Вне домена (в `GET /session` нет поля `domain`, Н1.6) она запись консоли кластера. В контракте — запись вида `folder` (`kinds.json`: `parents` — `null` или папка, возможности `create`, `rename`, `delete`), членство — `Unit.folders` записи члена (глава 3 Н1.2). Членство — забота платформы: `backend` переводит форму и хранит только правило скрытых членов (ADR-0096 §7).

- **Чтение вне домена.** Запись `folder` — элемент `GET /folders`, `GET /folders/<id>`: `uid` — UUID v5 `folder:platform/folders/<id>`, `domainId` — `Domain.id`
  (Н1.6), `parentId` — `uid` родителя или `null` при `parent: ""`, `version` — `index` строки. Состава в записи нет: `GET /units?folderId=` (глава 3 Н1.2б).
  Обратный путь — по перечню `GET /folders`. Элемент `{id, garbled: true}` не отдаётся, а при чтении этой папки — 503.
- **Чтение в домене.** Дерево — `GET /domain/folders`; поля — как выше, `parent` и `name` из дерева, `version` — `index` дерева.
- **Чтение без связи** — двери домена не отвечают (502–504, обрыв): дерево и состав из копии, `index` дерева в `version` пуст. Смена `version` при обрыве и возврате связи — ограничение.
- **`Unit.folders`** члена — только в `GET /units/{uid}` (глава 3 Н1.2б): в домене — `folders` из `GET /domain/memberof/<кластер>/<ссылка>`, вне домена — строка членства `GET /folders?member=`; `uid` папок — по Н1.6.
- **Видимый член** — `cam/cameras/<id>` с пустым `main`, `det/units/<id>` из перечня единиц читателя; строка `type: ipsrv` видна как `ipsrv` своего хоста, из двух на хосте — наименьший id. Дети, строки `cam/device_units`, `channel`, `storage`, поток, `ipsrv` без строки — не единицы, членами не бывают (P/06.8 Н1.1; виды без возможности `folders` в `kinds.json`): такая запись с `folders` в `PATCH`, в шаге `folders`, в строке её создания — 422 `NOT_SUPPORTED`, `field: /folders`. `ipsrv` виден, если видна его строка, камера его хоста или ребёнок на его строке (ADR-0102 доп. (6) п. 6); канал виден вместе с ним. Члена вне перечня перевод считает скрытым: права нет или он
  удалён мимо двери, по отфильтрованному перечню их не отличить, а контракт велит не раскрывать невидимое (ADR-0096 доп. (1)). Дверь папки отдаёт члены как есть, чтение платформой
  не меняется.
- **Создание** — строка вида `folder` в `POST /units` `{name, parentId, domainId}`: в домене `POST /domain/folders {name, parent}`, вне домена `POST /folders`; `domainId` неизвестный — `failed` `VALIDATION_FAILED`, `field: /domainId`, `params.keyword: x-ref` (Н1.5); `name`, пустое после снятия крайних пробелов, — `failed` `NAME_REQUIRED`, `field: /name`; `folders`, непустые `properties`, `children` — `failed` `NOT_SUPPORTED`, `field` — указатель этого поля: папка заводится одним вызовом двери, у двери домена пакета нет. Итог в домене — чтением дерева.
- **Правка** (`PATCH /units/{uid}` папки, только `name`; `If-Match` — 428 без него; `folders`, `properties` — 422 `NOT_SUPPORTED`, `field` — указатель) вне домена — `PUT /folders/<id>` с `If-Match: "<version>"`, поля `name`, `members` прочитанные; `412 folder moved` — 412
  `VERSION_MISMATCH`, `current` из `row` ответа.
- **Правка в домене.** `name` — `PUT /domain/folders/<id>` `{name}` с `If-Match: "<version>"`; `412 revision moved` — как `folder moved`.
- **Папка не переносится:** `POST /units/{uid}/move` папки — 422 `NOT_SUPPORTED`, `field: /kind`, `params.capability: move`: у вида нет `move` (`kinds.json`), а двери `PUT /domain/folders/<id>`, `PUT /folders/<id>` не принимают `parent` (P/08.5 Н2, P/06.8 Н2).
- **Состав — `Unit.folders`** (ADR-0112 доп. (10) п. 4): `PATCH /units/{uid}` `{folders}` записи члена и шаг `folders` в `POST /operations` (Н1.8) — весь список папок записи: Merge Patch заменяет массив целиком (Н1.2). Проверки до записи, а у шагов `folders` и `patch` с `folders` — до запуска операции (контракт `createOperation`): больше `selectMax` папок, `uid` не папки домена или невидимый читателю — 422 `VALIDATION_FAILED`, `field: /folders`, `params.keyword: x-ref` у `uid`, без обращения к двери (в операции — указатель контракта `/items/<i>/folders/<j>`, `/items/<i>/patch/folders/<j>`, `params.targetId` — объект шага); запись не член — 422 `NOT_SUPPORTED`, `field: /folders` (выше); больше `DEVICE_FOLDERS_MAX` — ниже. Затем версия записи (`If-Match`, Н1.3; в операции — `expectedVersions`); запись под групповой операцией — 409 `BUSY`, `params.targetId` (Н1.8). Право на запись и на папку и связь с доменом судятся при записи (в операции — по шагу). Вне домена — пакет B9 со строками папок и членства (P/06.8 Н2 «Строки папок в пакетной двери»): в каждую добавленную папку член в конец `members`, из каждой снятой он вынимается, прочие члены — на своих местах, скрытые тоже (ниже); `cas` — индекс строки папки, строка членства из `GET /folders?member=` (`member.index`), стражи — цепочка предков каждой добавленной
  папки и строка единицы, если её нет в `writes`; `412 folder moved` — чтение и повтор, второй раз — 409 `BUSY`: версия записи строк папок не несёт. В домене — `PUT /domain/memberof/<кластер>/<ссылка>` `{folders}`, список тела целиком: чтения прежнего не нужно, поэтому и у чужой цели; кластер — записи (Н1.6). Цель судит страж держателя (P/08.5 Н1.8 `member`). Пары «папка + членство» нет (P/08.5 Н1.8): `PATCH` с `folders` и прочими полями — две записи по порядку: поля (Н1.2), затем членство; отказ членства — отказ Н4, поля остаются записанными, это предел. Список, уже стоящий как просили, записи не даёт, поэтому повтор безопасен. Ответ — запись `Unit`, прочитанная заново. В стопку отката не ложится (Н1.12).
- **Удаление в домене** — `DELETE /units/{uid}` папки, элемент `/objects/delete`: `DELETE /domain/folders/<id>` с `If-Match` по правилу правки; члены остаются.
- **Дерево правит администратор домена** (P/08.5 Н1.8 `rights`, строка гранта кластера его не даёт): создание, `name`, удаление администратору кластера — 403 `PERMISSION_DENIED`, `params: {scope: "domain"}`. Состав он правит: правом на единицу и папку в своём кластере. Показ на чтении — глава 8 Н1.10.
- **Без связи** папку и членство не правят (ADR-0110 доп. (5) п. 3): двери домена не отвечают (502–504, обрыв) — 409 `SERVER_OFFLINE`, ничего не записано; в операции — итог `fail` `SERVER_OFFLINE`.
- **Скрытые члены** вне домена сохраняются: запись строки папки (членство выше, правка `name`) меняет только тех членов, кого называет, а дверь папки хранит
  прочих как есть — скрытых на прежних местах; запись всего `members` ставит каждого скрытого члена сразу за ближайшим видимым
  **перед ним** в прежнем списке, который остался, в прежнем порядке скрытых; такого нет — в начало списка. Состав читается из той же
  версии, что строка папки в пакете, поэтому член, добавленный мимо `backend`, не теряется: запись отвечает 412. Смена `version` папки от правки
  скрытого члена — ограничение: новая версия без видимого изменения.
- **Отказ цепочки** — 404 `NOT_FOUND` (ADR-0096 §7): предка нет, надгробие, 412 стража цепочки. У дверей папок при создании нет 409 и 412.
- **`folders` создания в домене** (ADR-0111 п. 13) — два шага: до записи папки ищутся в дереве, затем пакет записи без строк папок (`400 badkey`, P/06.8 Н1.2а), затем `PUT /domain/memberof/<кластер>/<ссылка>` `{folders}`, кластер — записи. Двери домена не отвечают до записи — `failed` `VALIDATION_FAILED`, `field: /folders`, записи нет; папки нет — `failed` `NOT_FOUND`, `field: /folders`. Отказ членства после пакета — запись создана, `done` с `folders: []`, причина — в журнал воркера.
- **Шаг `folders` в домене** — дверь состава выше, `Idempotency-Key` — `step_key(id, i)`, затем пакет итога (Н1.8). Двери домена не отвечают — итог `fail` `SERVER_OFFLINE`.
- **`folders` создания и шаг `folders` вне домена** — пакет B9 состава выше, новый член
  в конец; строку папки или цепочку сдвинули — шаг создания строится заново (Н1.4). Порядок папок записи не хранится (ADR-0096, «Запрос продукту» п. 1).
- **Вес каскада.** `DEVICE_FOLDERS_MAX` = 15: различных папок у камеры и её детекторов вместе (решения норм прав, п. 18). Удаление устройства
  пишет строку каждой такой папки; `FOLDER_ROW_MAX` × 15 с ключами частей входит в тело пакета `-max-body` 1 МиБ (P/06.8 Н1.3).
  `backend` держит предел при `folders` создания, `PATCH` и шага `folders` по перечню `GET /folders`: сверх него — 422 `VALIDATION_FAILED`,
  `field: /folders`. Две одновременные записи и записи мимо `backend` предел обходят: удаление такого
  устройства — 413, строка Н4, ничего не записано; снять его из папок и повторить.

### Н1.8 Групповая операция

Операцию ведёт консоль (P/06.9), шаг переводит и пишет `backend`. Таблица операций `service: true`: двери — только по билету, людям строк
`sub: backend` перевод не даёт, чужая операция — 404 `NOT_FOUND` (решения норм прав, пп. 21, 22).

- **Id.** `id` операции — 128 случайных бит, называет `backend`; в контракте — те же биты в форме UUID 8-4-4-4-12. Обратный путь —
  снятие дефисов.
- **Шаги** (`OperationItemRequest`): `uid` объекта и ровно одно из `patch` (как `PATCH /units/{uid}`, Н1.2), `folders` (Н1.7), `createUnit`
  (дочерняя строка, Н1.5), `move` с `params` (как `POST /units/{uid}/move`, Н1.14), `action` с `params` (как `POST /units/{uid}/actions/{action}`,
  Н1.17), `delete: true` (как `DELETE /units/{uid}`, Н1.2, Н1.7). `params` идёт только с `move` и `action`.
- **Приём** `POST /operations`, по порядку (ADR-0095 §2; контракт `createOperation`):
  1. Память первой: строка `<h>` с `op: createOperation` создаётся «начато» `cas ""`, как Н1.4. Строка есть: чужие `user`, ключ, `op`, `body` —
     422 `VALIDATION_FAILED`, `field: /idempotencyKey`; `state: done` — та же операция (`operation` строки), прочитанная сейчас, при `wait: true` и `state: done` — 200, иначе 202; `state: started` — приём
     идёт заново по той же строке, спор решает `cas` памяти в пакете приёма.
  2. До снимка целей: шаг не ровно с одним из шести, `params` без `move` или `action`, пустой `items` — 422 `VALIDATION_FAILED`, `field: /items/<i>` (`/items`).
     Объекта шага нет — 422 `VALIDATION_FAILED` на всю операцию, `field: /items/<i>/uid`, `params.keyword: x-ref`, `params.targetId` — этот `uid` (контракт), ничего не создано.
     Шаг `patch`, `delete`, `folders` или `move` без версии своего объекта в `expectedVersions` — 428 `PRECONDITION_REQUIRED` (контракт; чтение ADR-0095 §2); `createUnit` и `action` её не требуют.
  3. Цели читаются снимком (Н1.3) и сверяются с `expectedVersions`: расхождение хоть одной — 412 `VERSION_MISMATCH`, ничего не создано.
  4. Шаги `patch`, `folders`, `createUnit` проверяются до запуска (контракт): проверки Н1.3 без версии (схема вида, `Unit.writable`), Н1.5 у `createUnit` (вид, `parents`, `children`, `identifier`), Н1.7 у папок. Непрошедший отклоняет всю операцию своим отказом, ничего не создано: `field` — указатель в теле запроса (`/items/<i>/patch/properties/<p>`, `/items/<i>/folders/<j>`, `/items/<i>/createUnit/…`), `params.targetId` — объект шага. **Решено:** родитель `createUnit` — объект шага: `createUnit.parentId` нет или равен `uid`, иначе 422 `PARENT_MISMATCH`, `field: /items/<i>/createUnit/parentId` — контракт «создать дочерний». `move`, `delete`, `action`, права и связь с доменом папки судятся при исполнении, по шагу.
  5. `POST /backend/operations` `{id, items, memory}`: `items[]` — `{body, root, expected, secret?}`; `body` — шаг запроса без секрета;
     `root` — корень; `expected` — `{"versions": {<uid объекта корня>: <версия>}}` по целям этого корня; `memory` — `{key: backend/repeats/<h>, fields:
     <строка с state: done и operation>, cas}`. Ответ — 202 `Operation`, итогов нет: `state` шагов — по P/06.9 Н2 (первый `run`, прочие `wait`).
  6. **`wait: true`** и все шаги — `patch`, `folders` или `move` (контракт: «все шаги мгновенные»): **Решено:** после двери `backend` перечитывает `GET /backend/operations/<id>`, пока не `state: done`, в пределах срока маршрута `api/operations`, как у `cancel` (ниже), и отвечает 200 законченной операцией; **предел:** срок вышел — 202 с прочитанным `state`. Прочие шаги с `wait` — 202, как без него.
  7. `409 root busy` — 409 `BUSY`, `params.targetId`; `412 row moved` с `field: /memory/cas` — другой исполнитель принял: перечитать строку и ответить, как `state: done`.
- **Корень** (ADR-0095 §1): `<cam>` — камера и строка `eventsrc`, `acfa`, у камеры и её детекторов один; `v-<name>` — строка тома, у `archive.*` и `volume` одной строки один; поток — `<cam>` своей камеры;
  `ipsrv-<хост>` — `ipsrv`, `channel` и `storage`, `child-<id>` — ребёнок, единица — `<cam>` своей строки; у шага над сервером, папкой и доменом — `<вид>-<id>`. Строки корня: у `<cam>` — части камеры, у строки `eventsrc`, `acfa` — она; у `ipsrv-<хост>` — строка `type: ipsrv` хоста, её нет — карта пуста; у `child-<id>` — `cam/children/<id>` и `cam/child_settings/<id>`. Занятость и цепочка версий идут по корню.
- **Чужая цель** — Н1.13 «Шаг операции». Память, операция и стопка отката — у `backend` входа.
- **Занятые объекты** (ADR-0111 п. 20, заменяет в этой части ADR-0095 «`BUSY` проверяют только приём»). Пока операция не завершена, её объекты не меняют и другие запросы. Дверь консоли этого не судит (P/06.9 Н1.3), судит `backend`: пакет `PATCH /units/{uid}`, `DELETE /units/{uid}` устройства, хранилища, тома, потока (Н1.15), элемента `POST /objects/delete` идёт пакетной дверью и несёт на каждый задетый корень стража `{key: backend/opbusy/<корень>, index: ""}`, у каскада — корни всех снимаемых строк, у `DELETE` хранилища — ещё корни камер с записями на нём, у `DELETE` детектора — корни камер, что пишут по нему. `412 row moved` с ключом строки занятости — 409 `BUSY`, `params: {targetId}` — объект этого корня, у пакетных дверей — элемент `failed` с кодом `BUSY`, прочие элементы идут. Пакет шага этого стража не несёт: шаг идёт по своему корню. **Предел:** двери папок (P/06.8) стража не берут, поэтому состав и удаление папки под операцией не отказывают.
- **Шаг.** Консоль зовёт `POST /opstep` `{id, index, body, secret?, expected, opcount}` с `X-W2C-Pass-Ticket` по маршруту объявления (P/06.9 Н2 «Вызов шага»);
  тело ответа консоль не читает, поэтому ответ — 204 при любом исходе: исход — строка итога.
  1. **Сверка.** `expected` бывает двух форм. `{"versions": …}` — первый шаг над корнем: версии контракта, сверка как Н1.3. `{"rows": {<ключ строки>: <revision>}}` —
     цепочка корня: шаг после успешного шага; карта всех живых строк корня должна быть равна карте снимка. Версию контракта в цепочку положить нельзя: индекс
     пакета при его сборке неизвестен (P/06.1 «пакет»), а `revision` записанной строки предсказуем (файл решений, разбор ревью V/11, п. 1).
  2. `patch` — как `PATCH /units/{uid}` (Н1.2): снимок, пакет B9 с `cas` снимка и стражами частей, `folders` правки — затем членство (Н1.7); `createUnit` — как строка `POST /units` (Н1.5), родитель —
     `uid` шага; `folders` — Н1.7: состав папок записи становится списком тела, запись не меняется; вне домена стражем идёт строка самой цели (P/06.8 Н3 шаг 7);
     пакету `folders` стражей частей нет места (P/06.8 Н1.3); `delete` — как `DELETE /units/{uid}` (Н1.2; папка — Н1.7); `move` — Н1.14 своими дверями домена, затем пакет итога,
     `created_id` — запись, которой стал сервер (стук `class: camera`, принятый камерой; контракт `OperationItem.createdId`); `action` — просьба Н1.17, затем пакет итога:
     описание команды без `group: true` (`kinds.json`) — итог `fail` `NOT_SUPPORTED`, `field: /action` (контракт `ActionDescriptor.group`).
  3. В том же пакете — строка `backend/opdone/<id>/<i>` `cas ""` и `backend/opcount/<id>` с `cas` — значение `opcount` тела вызова шага (P/06.9 Н2). `versions` итога — карта `{"rows": …}`
     строк корня после шага: у записанной `revision` + 1, у новой 1, поверх надгробия — `revision` надгробия + 1 (`?deleted=1`), снятой нет, прочие из снимка. `version` итога — отпечаток этой карты: SHA-256 hex канонического JSON её значения (индекс пакета при сборке неизвестен, п. 1), наружу он не идёт; `created_id` — id созданного.
     `Idempotency-Key` — `step_key(id, i)` (P/06.9 Н2). `revision` снятой и созданной заново строки таблицы может вернуться (P/06.1 Н2 «Версии»): чужое снятие и создание
     той же строки внутри цепочки сверка не ловит, это ограничение.
  4. Отказ без записи (версия не та, `NOT_SUPPORTED`, `PERMISSION_DENIED`) — пакет из итога `fail` с кодом контракта и `field` и счётчиков, **без** ключа: `step_key` занят ответом
     пакета записи, а двойной итог отсекает `cas ""` (файл решений, разбор ревью V/11, п. 2).
  5. `412 row moved` — перечитать итог: есть — шаг окончен, нет — итог `fail`, код по Н4 (P/06.9 Н2). Заново шаг не строится: предел — у `create` версии нет, и `VERSION_MISMATCH` здесь значит «строка сдвинулась, повторить» (`retry-failed`). `412 leader moved` — закончить вызов, итога не писать: в память `step_key`
     этот ответ не ложится, это не исход шага (там же). Пакет лёг, а у нового вызова другой `opcount`: `cas` вне отпечатка пакета (P/06.1 Н3 «память повторов»), поэтому те же значения строк дают сохранённый ответ, шаг лёг; иные значения `opcount` — `422 key reused`: закончить вызов, итога не писать, итог читает консоль (P/06.9 Н3 «Гонки»), второго счёта нет. 5xx, обрыв, 401, `409 in flight` — закончить вызов, итога не писать (P/06.9 Н3 «шаг» п. 8); прочие 4xx — п. 4, код по Н4.
  6. `patch` записи `domain` — отказ до запуска: у вида нет правимого свойства (`kinds.json`), 422 `NOT_SUPPORTED`, `field: /items/<i>/patch/…`. `patch` записи `server` — Н1.19, итог отдельной записью, в стопку не ложится; поле, кроме `properties.labels`, — отказ до запуска, 422 `NOT_SUPPORTED`.
- **Чтение** `GET /operations/{id}`: `GET /backend/operations/<id>`; `createdAt`, `finishedAt` — секунды в RFC 3339 UTC; `retryOf` — `retry_of` в форме UUID;
  `revertOf`, `redoOf`, `single`, `revertible`, `redoable` — Н1.12; `items[i]` — `{index: i, targetId, state, code, version?, createdId?, params?}`, `targetId` — `uid` из `items[i].body` ответа (P/06.9 Н2, при
  `service: true`), `code` — `code` итога или `null`, `createdId` — `created_id` итога. `version` — только у завершённой операции и только у последнего шага `ok` своего корня: `backend` читает цель снимком (Н1.1) и считает отпечаток карты строк корня; равен `version` итога — нынешняя версия цели, иначе поля нет: цель менялась после шага, а версия контракта на момент шага нигде не записана. `not_run` — `UPSTREAM_UNAVAILABLE` (глава 2 Н1.3). `params` — итог шага полей подробностей не несёт (P/06.9 Н1.2), всё идёт в `field` итога: JSON Pointer относительно тела шага (`/properties/ip`, `/folders/0`, `/params/preset`) — `params.field`; **Решено:** у `VALIDATION_FAILED` за указателем через пробел — слово схемы — `params.keyword` (контракт `OperationItem.params.keyword`; у итога другого места для него нет); `incompatible:<id детектора>` у `BUSY` несовместимого детектора — `params: {reason: incompatible, with}`; `folders` отката папок (Н1.12) — `{reason: folders}`, без `params.field`.
- **Управление:** `cancel`, `retry-failed` — двери консоли, `pause`, `resume` не переводятся (глава 2 № 7, 8), `revert`, `redo` — Н1.12, `409 operation done`, `409 operation running`, `409 nothing to retry` — 409 `BUSY`;
  у `retry-failed` `backend` называет новый `id`, памяти ключа нет: ключа в контракте нет (исключение стенда — глава 6 Н1.3). `cancel` исполняет ведущий на такте, а контракт отдаёт завершённую запись: после двери `backend` перечитывает операцию, пока не `state: done`, в пределах срока маршрута `api/operations`; срок вышел — ответ с прочитанным `state`.
- **Память и операция.** Числа равны, 86400 с, часы разные: `OPS_KEEP` считается от `finished_at`, срок строки `<h>` — от первого
  наблюдения её версии (Н1.4). Память может пережить операцию только на задержку наблюдения и период жнецов, если операция кончилась
  сразу: повтор ключа тогда получает 404 `NOT_FOUND` от чтения операции, спустя сутки при обещании контракта 10 минут. Операция может пережить память, она идёт до
  `OPS_RUN_MAX` и ещё `OPS_KEEP`: повтор ключа после срока памяти идёт как новый приём и получает 409 `BUSY` или 412 по версиям. Шаг, меняющий
  версию, дважды не исполняется ни там, ни там; операция только из `folders` версий не меняет: такой повтор — новая операция с тем же итогом.

### Н1.9 Поиск устройств и вопрос о модели

Поиск и вопрос исполняет базовый воркер `cam` на каждом сервере кластера входа ([V/01.8](../../../01-cam/ru/spec/01.8-cam.norms.md)): `backend` просит и сводит итог. Домен пути — `Domain.id` (Н1.6),
иной `domainId` — 404 `NOT_FOUND`. Запрос сервера не называет: поиск идёт на всех серверах кластера входа и видит их подсети; устройство сети другого кластера находится входом через него (ADR-0111 п. 9). Один поиск на вход. Права — двери таблиц (P/06.1 Н1.6): чтение `view`, запись `admin`, отказ — 403 `PERMISSION_DENIED`.

- **`GET`.** Читаются строка `cam/searches/<CLUSTER>` и таблица `cam/found`:

| Строка поиска | `state` | `progress` | `startedAt` | `finishedAt` |
|---|---|---|---|---|
| нет | `idle` | 0 | `null` | `null` |
| есть `stopped_at` | `stopped` | доля на `stopped_at` | `started_at` | `stopped_at` |
| сейчас ≥ `until` | `done` | 100 | `started_at` | `until` |
| иначе | `searching` | доля сейчас | `started_at` | `null` |

  Доля — целая часть 100 · (t − `started_at`) / (`until` − `started_at`), не меньше 0 и не больше 99.
- **Строка поиска не читается** — на всех трёх дверях 503 `UPSTREAM_UNAVAILABLE` (глава 2 Н1.3): это не `idle` и не свободный поиск.
- **`candidates`** — строки `cam/found` с `search` строки поиска, порядок — `found_at`, затем `h`. Не отдаётся: строка, которая не читается (строка лога); находка, чей `ip`
  равен `properties.ip` камеры или `ipsrv` в `GET /units` читателя: устройство заведено, новым не считается.
- **Кандидат.** `id` — UUID v5 `candidate:<кластер>/cam/found/<h>` (Н1.6): от поиска к поиску тот же, пока адрес и MAC те же. `type` — `camera`: вида драйвер не говорит. `name` — `<vendor> <model>`: имени
  драйвер не говорит. `mac` — поле строки, нет его — пустая строка. `vendor`, `model`, `ip`, `port`, `support` — поля строки (V/01.8 Н1.2). `login`, `password` не отдаются: поиск их не подбирает, пароль вводит оператор, `support: ok` значит «драйвер есть», а не «вошли».
- **`POST`.** Строка говорит `searching` — 409 `BUSY`. Иначе — одна строка таблицы в `POST /console/batch`, `cas` прочитанной, строки нет — `cas ""`: новый `search` (32 hex, случайно),
  `started_at` — сейчас, `until` — плюс `SEARCH_TIME` (V/01.8 Н1.1). 412 `row moved` — другой поиск начат раньше: 409 `BUSY`. Ответ — 202 `Discovery`: `searching`, `progress` 0, `candidates`
  пуст; прежний итог заменён, находки приходят потоком после ответа (глава 5 Н1.2).
- **`DELETE`.** Строка говорит `searching` — та же запись с `stopped_at` = сейчас, 412 — перечитать и судить заново. Иначе — без записи. Ответ — 200 `Discovery`; найденное остаётся.
- **`candidateId`** строки `POST /units`: устройство создаётся обычным пакетом (Н1.5), с `properties.serverId` другого кластера — связкой, кандидат остаётся своим. После пакета строка `cam/found` этого `id` снимается `DELETE` с `cas`; строки нет или отказ — итог
  создания тот же, строка лога. В пакет снятие не входит: таблица воркера в пакете — 403 (P/06.1 Н2).
- **Вопрос о модели** — команда вида `POST /kinds/camera/actions/probe` (`scope: [kind]` в `kinds.json`; строки `camera(probe)` в `mapping.tsv`): `params` по схеме команды, иначе 422 `VALIDATION_FAILED`, `field: /params/<p>`; иная команда или вид — 404 `NOT_FOUND` (контракт). `POST /cam/probes`: новый `id`, `ip`, `port`, `vendor` из `params`, `until` — сейчас + `PERFORM_TIMEOUT` (V/01.8 Н1.3). Затем опрос `GET /cam/probe_replies`:
  строка этого вопроса с `model` — `{result: {model}}`; ответили без `model` все серверы `GET /servers` на связи или вышел `until` — `{result: {model: null}}`. Строка, которая не читается, ответом не считается. `params.login`, `params.password` принимаются и дальше тела не идут: строка `cam/probes` общая, а учётных данных поиск не хранит (V/01.8). Драйвер получает пустые, ответ бывает `model: null`, контракт это разрешает. **Предел** V/01.8 Н1.3. Повтор — новый вопрос, `idempotencyKey` тела не запоминается (Н1.4).

### Н1.10 Правила

Правило — строка единицы `auto/scenarios/<id>` и её отметки `auto/rule_marks/<id>` (`mute`, `order`), номер выдаёт счётчик `auto/next_id` (ADR-0105 п. 1). Сверка версии — Н1.3: версия — склейка двух индексов (глава 3 Н1.3), `If-Match` обязателен, 412 — с текущей записью. Пакет, пишущий одну из строк, стережёт другую. `backend` проверяет правило при записи; вычислитель судит то же проходом (V/07.3), этот суд не заменяется. Запись идёт пакетом B9 по билету: право — двери строк и таблиц, `names` манифеста судит всё, что правило называет (V/07.1 Н1.4); отказ — 403 `PERMISSION_DENIED`, `params.target` `{kind, id}` — единица из `detail` двери, id — глава 3 Н1.2, ничего не записано.

**Предел:** при загрузке форма зовёт ещё `/rules/{id}/fires`, `/versions` на каждое правило: N запросов подряд, отказ журнала на непустой установке роняет старт. **Чтение на старте.** `GET /rules`, `/schedules`, `/day-groups`, `/modes`, `/modes/current`, `/maintenance-windows` объявлены, и WebUI зовёт их при загрузке, отказ роняет старт, поэтому пустая установка на них отвечает обычным 200: строк нет — пустой список и постоянные записи главы 3 Н1.3, живой вычислитель им не нужен. Отказ `403` двери таблицы — то же: часть не видна, отказа нет (Н1.1). `404` двери `auto` — подсистема не установлена — тоже. Прочий отказ — как чтение всякой части.

- **Триггеры, действия и цели 0.2.0** (контракт `RuleTrigger`, `RuleAction`, `RuleTarget`, `RuleFire`; V/11.13). Перевод на строку — главы 3 Н1.3 «Правило»; форма контракта ложится на его прежние поля так, вычислитель `auto` не меняется:
  - **Триггер** `{source: unit, kinds | implements, event, target, match}`: `event` — прежний `kind`, id из `UnitKind.events` в `kinds.json` (`motion`, `linecross`, `lpr`, `abandoned`, `disappeared`, `crowd`, `silent`, `segment.lost` у `camera`, `io.input` у `sensor`, `acfa_sensor`, `text` у `eventsrc`, `unit` у единиц); прежний `source` (`sub` строки) следует из события по каталогу триггеров (`rule-catalog.json`: `vms` — `io.input`, `text`, `unit`, `silent`; `det` — события детекторов; `rec` — `segment.lost`) и наружу не идёт: `source` — постоянное `unit`. Событие, которого нет ни у одного вида `kinds.json`, у включённого правила — 422 `NOT_SUPPORTED`, `field: triggers`, `params.issue.code: trigger.notDeclared` (каталог ниже). `kinds`, `implements` называют виды, чьё это событие: вид без этого события среди них — тот же отказ; иначе они только проверка, в строку не пишутся, и чтение поля не даёт — **предел**: сужение по виду внутри цели-области не хранится. `match` — поля `EventDescriptor.params`: `match.value` у `io.input`, `match.word` у `text` и `unit` (прежний `match.word`), `match.port` — как глава 3 Н1.3; `match.template` — не поле ни одного события, отказ главы 3 Н1.3 («`match.template`»).
  - **Действие объекта** `{type: unitAction, action, target, params}`: `action` — id из `UnitKind.actions` с `ruleAction` видов цели (`arm`, `disarm`, `preset`, `record`, `disable`, `detect`, `scan`, `alarm` у `camera`; `output` у `relay`; `unit` у единиц), `params` — прежние поля действия по схеме `params` команды (`preset`, `duration`, `minutes`, `afterSec`, `archive`, `detectorKind`, `beforeSec`, `params`, `priority`, `text`, `operation`, `state`, `pulseMs`, `port`); прежний `source` следует из действия по каталогу действий (`vms` — `arm`, `disarm`, `preset`, `disable`, `output`, `unit`; `rec` — `record`; `alarm` — `alarm`; `det` — `detect`, `scan`). Действие вне этих, у включённого правила — 422 `NOT_SUPPORTED`, `field: steps`, `params.issue.code: action.notDeclared`; поле `params` вне схемы — `action.fieldNotDeclared`; тип не по схеме — 422 `VALIDATION_FAILED`, `field: steps` (контракт `RuleAction`). **Действие системы** `{source, action, …}` (`client`, `ntf`, `net`, `rule`) — как прежде, по каталогу `ruleActions`.
  - **Цель** `RuleTarget.include[]`: `{uid}` без `area` — объект (прежний `{kind: device, id}`), `{area: folder | server | domain, uid}` — область (прежние `folder`, `server`, `domain` с `id`), `uid` — по Н1.6; `exclude` — `uid` объектов; `gone`, `fromEvent` — как прежде. Путь на строку — глава 3 Н1.3 «Перевод цели».
  - **`RuleFire.events[]`**, события `RuleTestRequest` — `{source: unit, event, match, deviceId}`: `event` ↔ `kind` строки журнала или двери `auto/test`, `deviceId` — `uid` объекта события; `sub` тела двери — по правилу триггера выше.
  - **Решено:** 403 двери консоли или домена на шаге правила — 403 `PERMISSION_DENIED` без `params.right`: судится право двери; `ActionDescriptor.right`, `ruleRight`, `EventDescriptor.right` из `kinds.json` суда не добавляют (V/11.8 Н1 «Классы»).
- **Список** — строки без `hidden` и выразимые в `Rule` (глава 3 Н1.3), порядок — `order` отметки, затем id числом. `garbled` не отдаётся, чтение такой строки — 503, как нечитаемая папка (Н1.7).
- **Проверка** (`RULE_INVALID`). `name`, пустое после снятия крайних пробелов, — 422 `NAME_REQUIRED`, `field: name`, при любом `enabled`. Выключенное правило хранится незаконченным, необъявленный шаг в нём — данные. У включённого — первая ошибка по порядку ниже: 422 `RULE_INVALID`, `params.issue` — `{code, params}`:

  Коды — те же, что подсказка WebUI. **Каталог** (глава 2 Н1.5): включённое вне него — 422 `NOT_SUPPORTED`, `field` — раздел `start`, `triggers`, `conditions`, `steps`, `params.issue` — `rule.startNotDeclared`, `trigger.notDeclared`, `cond.notDeclared`, `control.notDeclared`, `action.notDeclared`, `action.fieldNotDeclared`, `target.notDeclared`; в `/rules/update` — элемент `failed` с этим кодом; запуск такого правила — 409 `NOT_RUNNABLE`, `params.reason.code` — код. `runAsRoleId` не роль домена — 422 `VALIDATION_FAILED`, `field: runAsRoleId`; шаг, которому роль не дала права, — `fail`, `role.denied` (V/07.4 Н1.9). `windowSec` больше 3600 — 422 `VALIDATION_FAILED`, `field: windowSec`: граница `within` (V/07.1). Сверх 4000 байт в поле `json` строки — 400 двери, 422 `VALIDATION_FAILED`, `field` по главе 3.
- **Кластер правила** (ADR-0111 пп. 8, 10). Правило живёт в кластере своих целей: чужой кластер — Н1.13. `serverId` выбирает кластер, цели другого кластера — 422 `VALIDATION_FAILED`, `field: serverId`; цели из нескольких кластеров — 422 `NOT_SUPPORTED`, `field: steps`, `params.issue.code: rule.crossDomain`: `ruleCrossDomainActions` пуст, такой сценарий — документ V/07.5, `Rule` его не выражает. Цель-папка цели не называет: кластер — `serverId`, поля нет — кластер входа.
- **`POST /rules`** — пакет: `auto/next_id` (как камера, Н1.2), строка `cas ""`, `auto/versions/<n>-1` с `note: {code: created, params: {}}`. строка отметки `cas ""`. `created_*`, `changed_*` — человек билета и момент, `mute: null`, `order` — наибольший `order` + 1: два одновременных создания могут получить один, порядок между ними — id. `412 row moved` по счётчику — пакет заново.
- **`PUT /rules/{id}`** — пакет: строка с `cas` снимка, поля вне содержимого — из снимка, `changed_*` новые; строка версии `number` — наибольший + 1, `note` — `historyNote`, без `params` — `{}`, нет — `null`. `historyNote.code: undo` с `params.number`, равным последней версии: её строка снимается в том же пакете, `changed_*`, `log_only_since` — из её `was`; версия записи всё равно новая.
- **`GET /rules/{id}/versions`** — строки `auto/versions` сценария по `number`. Строки живут, пока живо правило: срока нет. Чужое правило — глава 3 Н1.2а «Сверх вида».
- **`GET /rules/{id}/fires`** — `GET /events?subsystem=auto&unit=auto/<id>`, новые первыми (глава 3 Н1.3). Чужое правило — там же.
- **`POST /rules/update`** — групповая запись (Н1.4, Н1.5): элемент `{ruleId, version, set, historyNote?}`, пакет на правило. Нет — `NOT_FOUND`, версия — `VERSION_MISMATCH`, включение с ошибкой — `RULE_INVALID` без `params`: у элемента их нет. `log_only_since` — сегодня по `TIMEZONE`, когда правило входит в «только журнал», `null` — когда выходит. `mute` — `{since: сейчас, until, by, reason}` в строке отметки, `null` снимает; строка сценария при этом не пишется. Смена слова состояния (`off`, `watch`, `on`) и `historyNote` — строка версии, `note: {code: state, params: {mode}}`; приглушение версии не пишет. `changed_*` меняет только состояние. Значение, какое уже есть, в запись не идёт; записывать нечего — строки нет, `revision` та же, запуск не снят.
- **`POST /rules/reorder`** — один пакет: только строки `auto/rule_marks` с `cas` снимка, строки сценариев — стражи; правило со своим `order` не пишется, версия остальных меняется. Нет — 404; версия не та, 412 пакета — 412 `VERSION_MISMATCH`, `current`, `params.ruleId`, ничего не записано. Больше `BATCH_WRITES` изменённых строк или `BATCH_GUARDS` стражей — 422 `VALIDATION_FAILED`, `field: items`: всё или ничего сильнее полноты.
- **`POST /rules/{id}/run`, `/fires/{fireId}/retry`** (ADR-0105 п. 10) — просьбы `run`, `retry` вычислителю сценария (V/07.4 Н1.12), `POST /auto/requests` по билету: только подача, право — `need` двери просьб, судится человек билета (P/06.3 Н1.9). Строки нет, `hidden`, не выражается в `Rule` — 404 `NOT_FOUND`; `fireId` нет среди сработок журнала этого правила — 404 `NOT_FOUND`; `enabled: false` — 409 `NOT_RUNNABLE`, `params.reason: {code: off}`, просьба не подаётся: держать выключенное вычислитель не обязан. Тело — `{unit, action: run}`, `{unit, action: retry, fire}`, `fire` — `firing`; `Idempotency-Key` — `idempotencyKey` тела. Дверь отвечает 202, пока исхода нет: подача повторяется тем же ключом до 200 с меткой, в пределах срока маршрута `api/rules`. Исход метки: `performed` — `reply.firing`, журнал читается до строки `fired` этой сработки, ответ 201 `RuleFire`; `refused`, `expired`, `gone` — 409 `NOT_RUNNABLE`, `params.reason.code` — `error` метки (`off`, `logOnly`, `refused`, `nothing`, `unread`), без него — слово исхода. `unknown`, срок вышел без метки или без строки журнала — 503 `UPSTREAM_UNAVAILABLE`: запуск мог пойти, на широкой цели `PERFORM_TIMEOUT` выходит раньше конца, исход неизвестен, повтор тем же ключом — тот же запуск. `409 exists`, `409 spent` — ключ занят иным телом: 422 `VALIDATION_FAILED`, `field: idempotencyKey`.
- **Ответ оператора** (V/07.6 Н1.9). `GET /rule-prompts` — глава 3 Н1.3 «`RulePrompt`», чтение `GET /auto/scenarios`, `GET /session`. `POST /rule-prompts/{promptId}/answer` по порядку: вопрос среди открытых; нет — среди шагов запусков `runs` и имён `done` сценария: id односторонний, сработку называет только этот обход. Нашёлся: журнал этой сработки несёт конец шага ответом, `note` `ask.answer` или `label` `esc.ack` (V/07.4 Н1.6), — 409 `BUSY`, `params.reason: answered`; не несёт — 409 `NOT_RUNNABLE`, `params.reason.code: over`; журнал не ответил — 503 `UPSTREAM_UNAVAILABLE`. Не нашёлся — 404 `NOT_FOUND`, журнал не ищется: `done` живёт вопросом назад, позже кончившийся вопрос — 404, предел. Запуск снят новой `revision`, выключением, удалением — тоже 404, предел: `state` снят, `runs`, `done` не действуют; снятый `restart` лежит в `done` — 409. **Предел:** строка конца ложится после записи шага (V/07.4 Н1.11), ответ журнала бывает обрезан (`truncated`): там отвеченный вопрос даёт `over`. У открытого: роли нет (`canAnswer`) — 403 `PERMISSION_DENIED`, это дверь, последним судит вычислитель; ответ не того вида — 422 `VALIDATION_FAILED`, `field: answer`; `until` вышел — 409 `NOT_RUNNABLE`, `over`. Запись — строка `auto/answers/<scenario>-<fire>-<step>-<user>` в `POST /console/batch`, `cas ""`, `user` — человек билета, судится он же: `answer` — `yes`, `no`, `ack` ↔ `ack:<level вопроса>`. Строка занята — 409 `BUSY`, `params.reason: answered`, в том числе своя отвергнутая: человек отвечает один раз (V/07.6 Н1.9). Ответ — 202 без тела: засчитанный ответ решает вычислитель проходом, исход виден в сработке (V/07.6 Н1.9).
- **`POST /rules/test`** — `POST /auto/test/<id>` по билету (ADR-0105 п. 7): `ruleId` не `null` — его номер, нет строки — 404 `NOT_FOUND`; `null` — наименьший номер перечня `GET /auto/scenarios`, чью строку держит живой воркер (V/07.4). Тело — `{scenario, rule, events, at, branches, log}`, `rule` — черновик полями строки, `events` — по правилу `RuleFire.events[]` выше, проверки Н1.10 не идут; `log` без `ruleId` — 422 `VALIDATION_FAILED`, `field: log`; `bad_branches` двери — 422 `VALIDATION_FAILED`, `field: branches`. `RuleFire.id` — от `firing` ответа двери (есть при `log: true`), иначе случайный UUID, `ruleId` — как в теле. Держателя нет или строк нет — 503 `UPSTREAM_UNAVAILABLE`: пробовать некому. Право — `view` на строку (P/06.3 Н1.9).
- **Удаление** — элемент `POST /objects/delete`: снятие строки, отметки, её строк `auto/versions` и своих расписаний (`owner.kind: rule`), если они больше нигде не используются (Н1.11), одним пакетом; не вмещается — версии своими пакетами, строка последней. Журнал запусков остаётся.

**Каскад устройства** (ADR-0105, контракт). После пакета снятия устройства с дочерними, в том числе элементом `/objects/delete`, `backend` читает `GET /auto/scenarios`: элемент `include` `{uid}` без `area` снятой записи уходит в `gone` её именем, такой же `uid` в `exclude` снимается, строка пишется с `cas`, новая версия записи, строка истории не добавляется. Строки `auto/versions` этого правила правятся так же, в том же пакете, не вместились — следующими. У строки записи другой камеры детектор просто уходит из цели. `412` — перечитать и повторить, не больше трёх попыток. **Предел:** каскад идёт после снятия, не одним пакетом: правил может быть больше предела пакета. Отказ, обрыв или `403` права сценария (`cluster_rows`) исход снятия не меняют: строка лога, цель остаётся с мёртвым `id`, вычислитель судит её `target.deviceGone`, запись такого включённого правила — `rule.targetGone`.

### Н1.11 Расписания, группы дней, режимы, окна

Таблицы `auto` читает вычислитель, момент считает он один (ADR-0105 п. 2): `backend` не вычисляет, действует ли расписание. Запись — таблицы в пакете B9 с `cas`, версия — индекс строки, Н1.3. Таблицы эти — кластера входа: хранимой правкой не идут, чужая запись библиотеки — 422 `NOT_SUPPORTED`, `field: type`, вход через её кластер.

- **Встроенные** «Всегда», «Никогда» — `Schedule` с `kind` `always`, `never`, `builtin: true`, id — глава 3 Н1.2, версия `"1"`. `GET` отдаёт их и без строк. Запись, ссылающаяся на встроенное, несёт его строку `cas ""`, если её нет: вычислитель читает таблицу. `PUT`, `DELETE` — после сверки версии 409 `BUILTIN`.
- **`POST`, `PUT /schedules`.** `name` пустое — 422 `NAME_REQUIRED`, `field: name`; `owner` на нет правила или окна — 422 `VALIDATION_FAILED`, `field: owner`. `POST` — новый UUID, `builtin: false`, 201.
- **Где используется расписание** — режим, условие `time`, окно.
- **`POST`, `PUT /day-groups`** — то же без `owner`. **`DELETE /day-groups/{id}`**: группа уходит из `overrides` всех расписаний.
- **`GET /modes`** — глава 3 Н1.3. **`PUT /modes`** — `If-Match`, строки нет — `cas ""` при версии `"0"`. Пропал системный режим — 409 `BUILTIN`, `params.modeId`; `otherwise` не из `items` — 422 `VALIDATION_FAILED`, `field: otherwise`; пустое имя — 422 `NAME_REQUIRED`, `field: items`. Снятый режим уходит из условий `mode` правил (новая версия записи, версия истории не пишется), его ручное включение снимается.
- **`GET /modes/current`** — `manual`: строка `auto/mode_current/now`, её режим есть в списке, `until` нет или позже сейчас: `{until}`, иначе `null`. `modeId`: `manual` не `null` — режим строки; строки `modes` нет — `otherwise`; иначе — слово `object_mode` услышанного вычислителя с наименьшим слотом, из `GET /servers`; живого вычислителя нет или он поля не несёт (`unknown`) — `otherwise`: его слова нет, а форме нужен ответ при загрузке; момент считает только он, это предел. `GET /servers` не ответил, строка не читается — 503. Версии нет (контракт).
- **`POST /modes/current`** — `modeId` не из списка — 404 `NOT_FOUND`; значение — строка `now` с `cas`, `null` — снятие. Ответ — как `GET`.
- **`POST /maintenance-windows`** — один пакет: окно и расписание с `owner` — это окно. Ответ — 201 `{window, schedule}`. **`PUT`:** расписания нет — 422 `VALIDATION_FAILED`, `field: scheduleId`.
- **Удаление окна** — и его расписание, если больше нигде не используется.
- **Удаление расписания:** режимы — `schedule: null`, условия `time` и окна — встроенное «Никогда», кроме строки `hidden: record`: она остаётся, `time` ложно (V/07.4 Н1.8), слово `schedule is gone`; у правил новая версия записи, истории — нет.
- **Каскад — один пакет.** Не вмещается в `BATCH_WRITES` — зависимые строки своими пакетами, снятие или строка `modes` последней: обрыв оставляет объект живым, повтор доводит. **Предел:** между пакетами вычислитель видит часть правок. Правка задетой строки в окне — 412 — перечитать, не больше трёх попыток, иначе 412 `VERSION_MISMATCH`.

### Н1.12 Откат

Откат — только последняя неоткаченная операция автора, как кнопка undo: предыдущая откатывается только после неё (ADR-0106 с доп. (1)–(4); ADR-0111 пп. 18, 19). Платформа и запись не меняются; всё — своя таблица `backend/undo/<id>` (манифест). Пользователи, роли, гранты, папки, пароли, правила и таблицы `auto` вне отката, кроме строки `hidden: record`.

- **Что ложится в стопку.** Шаг операции, строка `POST /units`, элемент `/objects/delete`, а также одиночные `PATCH /units/{uid}`, `DELETE /units/{uid}` записи настроек оборудования (виды строк ниже: устройство, его детектор, единица, ребёнок, поток, `archive.*`, `volume`), хранилище — в стопке с `createdId` созданного хранилища, в том же пакете, что запись. Пресет, команда и шаг `action` не ложатся: положения и исхода устройства назад не прочитать. **Предел:** `POST /units/{uid}/move` сервера и шаг `move` в стопку не ложатся, хотя контракт (`UnitMoveRequest`) кладёт туда перенос сервера: приём и исключение — двери домена, а не строки настроек оборудования (Н1.14). `id` — операции; групповая запись — первые 32 знака `<h>`; одиночная — 128 случайных бит: операция из одного шага. Первая запись — `cas ""`, прочие — `cas` строки. Всё, кроме `POST /operations`, несёт `single: true`.
- **Строка.** Операция отката — строка с `revert_of` и пустыми `steps`, только для `revertOf` чтения, откатить её нельзя. Операция повтора — строка с `redo_of` и обычными `steps`, откатывается как всякая. Шаг: `index`, `target`, `root` (Н1.8), `rows` — на строку настроек оборудования `{key, op, born?, before, after}`: `cam/cameras`, `cam/child_settings`, `cam/device_units`, `rec/recordings`, `rec/volumes`, `det/units` и строка `hidden: record` смены `recordMode`; счётчики, замок, `backend/*`, строки операции не входят; `op` — `set`, `create` или `recreate`, `before`, `after` — изменённые поля без `*_secret`, у `create` `after` — все поля и `born`, у `recreate` (снятая строка `hidden: record`) `before` — все поля строки без `revision`, `after` нет. Только шаги с записью.
- **Слово `refuse` шага** ставится при записи и даёт `fail` отката: `volume` — у `rec/volumes` менялись `url`, его части, `quota_bytes`, `shrink_confirmed`: откат не должен стереть архив; `deleted` — строка снята: номер не повторяется; строка `hidden: record` слова не получает, у неё `recreate`; `bound_to` — менялось поле `bound_to`: пароль задаётся заново; `secret` — менялся `*_secret`; `folderIds` — шаг `folders` или `patch` с `folders`: папки вне отката, итог шага `fail` `NOT_SUPPORTED`, `field` итога `folders`, у формы `OperationItem.params: {reason: folders}`; `view` — чужой шаг, поле вне вида (Н1.13).
- **Пределы стопки.** `UNDO_DAYS` = 7 суток — `delete_after`; `UNDO_KEEP` = 50: глубина отката, операции отката в стопку не входят. Новая строка — `GET /backend/undo`: сверх 50 строк без `revert_of` и сверх 100 строк всего старшие по `at` снимаются `DELETE` с `cas`, отказ — строка лога. Строка не вмещается в потолок хранилища (`413 row too large`) — `overflow: true`, `steps` пусты, откатить её нельзя: шаг важнее следа.
- **`POST /operations/{id}/revert`**, по порядку; всякий отказ — 409 `NOT_REVERTIBLE`, `params.reason`, кроме названных:
  1. Строки нет, срок вышел — `expired`; чужой `user` — 404 `NOT_FOUND`; не читается — 503.
  2. Строка с `revert_of` — `isRevert`; все ряды откачены — `reverted`; `reverted_by` называет незавершённую операцию отката — `running`; `overflow`, пустые `steps` — `empty`; есть младшая строка этого `user` без `revert_of` с открытым рядом — `notLast`. Операция отката завершена, а открытые ряды остались — откат можно повторить: неудачная попытка операцию не закрывает.
  3. Запись операции у консоли есть и `state` не `done` — `running`. Отменённая законченная годится: возвращаются выполненные шаги. Записи нет — операция одиночная или старше `OPS_KEEP`: законченная.
  4. `POST /backend/operations`: шаги — в обратном порядке, `body` — `{uid, revert: {of, index}}`, `uid` — цель шага, `root` — шага, `expected` — `{}`; `memory` — строка `<id>` с `reverted_by` — id этой операции отката, `cas` прочитанной: двойной клик не откатывает дважды, откаченным ряд делает только его шаг. `409 root busy` — 409 `BUSY`, `params.targetId`; `412 row moved` с `field: /memory/cas` — `reverted`. Ответ — 202 `Operation`, `revertOf` — `id`. Новая строка `backend/undo` ложится пакетом первого шага, `revert_of` — `id`.
- **Шаг отката** (`/opstep`, Н1.8, строка цели из снимка, `expected` не читается): `refuse` — итог `fail` `NOT_SUPPORTED`, слово — `field`. Поле, которого нет, в `before`, `after` идёт значением `null`: проверка судит его как поле, запись снимает его, так `Archive.recordMode` `null` откатывается и повторяется. Проверка по значениям: строка `key` есть, каждое поле `after` равно текущему, у `create` ещё `born`; иначе `fail` `VERSION_MISMATCH`: правка мимо `backend` не затирается. Снятие созданного, которое уже меняли, — `revision` строки больше той, что записала операция, или том, на котором есть запись, — `fail` `NOT_SUPPORTED`: значения совпали, а строка уже не та. Ряд с итогом `ok` получает `reverted: true` пакетом шага, ряд с `fail` остаётся открытым. Правка другого поля той же строки откату не мешает. `recreate` судится иначе: у камеры есть живая строка `hidden: record` — `fail` `VERSION_MISMATCH`: двух строк записи быть не должно; иначе пакет заведения Н1.2: `auto/next_id` с `cas` прочитанного, строка `auto/scenarios/<n + 1>` `cas ""` из `before`, первая строка `auto/versions`, номер наружу не выходит. Запись — `before` поверх снимка, `create` — снятие; пакет, замок, итог, счётчики — как шаг `set`.
- **Очередь повтора** этого `user` (ADR-0106 доп. (4)) — как redo редактора, по строкам `backend/undo` от младшей по `(at, id)`: строка с `redo_of` помечает цель повторённой; строка с `revert_of` называет цель; строка без обоих полей кончает обход: новая правка, попавшая в стопку, очищает повтор целиком, своей записи не нужно. Правка сервера в стопку не входит и повтор не очищает. **Верх очереди** — первая названная цель, не помеченная, с откаченным рядом.
- **`POST /operations/{id}/redo`**, по порядку; всякий отказ — 409 `NOT_REVERTIBLE`, `params.reason`, кроме названных:
  1. Строки нет, срок вышел — `stale`; чужой `user` — 404 `NOT_FOUND`; не читается — 503.
  2. `reverted_by` называет незавершённую операцию отката, цель очереди ниже верха — `notLast`; не верх и не в очереди (не откатывалась, очищена, уже повторена) — `stale`.
  3. `POST /backend/operations`: шаги с откаченными рядами в прямом порядке, `body` — `{uid, redo: {of, index}}`, `root` — шага, `expected` — `{}`; `memory` — строка `<id>` с `redone_by` — id этой операции, `cas` прочитанной: двойной клик не повторяет дважды. `409 root busy` — 409 `BUSY`, `params.targetId`; `412 row moved` с `field: /memory/cas` — `stale`. Ответ — 202 `Operation`, `redoOf` — `id`. Новая строка `backend/undo` ложится пакетом первого шага с записью, `redo_of` — `id`.
- **Шаг повтора** (`/opstep`, строка цели из снимка, `expected` не читается). `set`: каждое поле `before` равно текущему, иначе `fail` `VERSION_MISMATCH`: чужое не затирается; запись — `after` поверх снимка. `create`: `fail` `NOT_SUPPORTED`, `field: created`: снятое не возвращается, номер новый; строка `hidden: record` заводится заново, как `recreate`, иначе `recordMode` разошёлся бы с записями. `recreate`: нынешняя строка записи снимается, если её поля равны `before`, иначе `fail` `VERSION_MISMATCH`. Новая строка несёт те же `before`, `after`; пакет, замок, итог, счётчики — как шаг `set`.
- **Чтение.** `GET /operations/{id}` записи консоли нет, строка `backend/undo` есть — `Operation` из неё: `state: done`, `createdAt`, `finishedAt` — `at`, шаги `ok`. Поля строки: `revertOf`, `redoOf` — `revert_of`, `redo_of` в форме UUID, нет строки — `null`, у операции без записанного шага `redoOf` — `redo.of` тела шага; `single` — поле строки, нет строки — `false`; `revertible` — `revert` прошёл бы шаги 1–3; `redoable` — строка — верх очереди и отката не идёт.
- **`GET /operations`** — перечень этого `user`, новые сверху: строки `GET /backend/undo` и строки `backend/repeats` с `op: createOperation`, чьего `operation` в `backend/undo` нет, запись каждой — как `GET /operations/{id}`; порядок — `at`, при равном — больший индекс строки, у строки памяти — `created_at` записи консоли; `limit` — 1…50, умолчание 50. Запись не читается — не отдаётся, строка лога. **Предел:** `retry-failed` без записанного шага в перечень не входит: строк у него нет. Откат и повтор идут строками перечня.
- **Чужой шаг** — Н1.13 «Откат».

### Н1.13 Запись чужого кластера

Своё пишется дверями Н1.2–Н1.12. У чужого двери нет: запись идёт хранимой правкой домена ([P/08.6](../../../../Platform/08-domain/ru/spec/08.6-domain.norms.md) Н1.3б, Н1.4; ADR-0110 доп. (4) п. 1), применяет её агент члена, точно судит консоль члена, по тому же человеку (договор права «Суд по цели» `write`). Перевод тела, проверки по `way` и слова отказа — те же, что у своей записи.

**Состояние — у входа** (ADR-0110 доп. (5) п. 5). `backend/repeats`, `backend/undo`, операции живут в кластере входа: consolem подключён к одному `backend`, другой — только при потере входа. На другом входе прежних операций нет, а тот же `idempotencyKey` исполнится заново: после 5xx и смены входа запись перечитывается.

**Вход.** `need` входа — грант в любом кластере домена (ADR-0110 доп. (5) п. 5): строка `domain/anywhere` договора права. Вошедшему по `anywhere` без прав на своём кластере своего нет (глава 3 Н1.2а): новая запись без `serverId` идёт в кластер входа и получает 403 его двери.

- **Кластер новой записи** (ADR-0111 п. 8). Строка `POST /units` — кластер — член сервера `properties.serverId`, у `archive.*` — сервера `parentId`, `POST /rules` — сервера `serverId`, по обратному пути Н1.6, поля нет — кластер входа; сервера нет в перечне вида — 422 `VALIDATION_FAILED`, `field: /properties/serverId` (у `archive.*` — `/parentId`), `params.keyword: x-ref` (Н1.5). `parentId` — запись другого кластера: кластер родителя, `properties.serverId` другого кластера при этом — `PARENT_MISMATCH`, `field: /parentId`. После создания у `camera`, `ipsrv`, `acfa`, `det` `properties.serverId` — наблюдение (глава 3 Н1.1). `serverId` камеры без назначения — поля нет.
- **Строки.** Запись устройства — одна правка: `POST /domain/edits {cluster, writes}`, `cluster` — член цели, `writes` — те же строки, что пакет Н1.2 (ADR-0111 п. 16). `cas`, стражей, замка `cas`, `backend/opbusy`, строк `<h>` и `backend/undo` в связке нет: `base` и применение всего или ничего держит платформа. Строка единицы — `{op, sub, rows, id, fields}`, `id` — `key` строки снимка таблицы вида: без `ref` строку адресует пара (`cluster`, `id`), поиска нет, `siblings` не мешают, а `domain.ref` не нужен, поэтому так же правятся детектор, правило, `ipsrv`, `eventsrc`, `acfa`, поток. `put` единицы без `create`, `new` — только по живой строке, иначе исход `refused`: части, которой в снимке нет или которая снята, — `create: true`, у `unit.id: numeric` — `new`. Строка таблицы — `{op, sub, rows, name, fields}`, `fields` — строка целиком: поля снимка, поверх — тело. Новая строка таблицы — тот же `put`: `create`, `new` — слова единицы. Часть с `about` идёт со строкой камеры: не меняется — `fields: {}`. В `fields` единицы — только изменённые поля.
- **Что шлёт связка.** Единицы: `cam/cameras` (камера, `ipsrv`, `eventsrc`, `acfa`, поток), `rec/recordings` — по `domain.ref`; `det/units`, `auto/scenarios` — по `domain.edit`, снятие — по `domain.edit_delete` манифеста. Таблицы `domain.edit_tables`: `cam/child_settings`, `cam/device_units`, `cam/unit_next`, `cam/preset_labels`, `rec/volumes`, `auto/versions`, `auto/rule_marks`. Поля — списки этих слов. Иных строк нет: чего в них нет, чужой правкой не пишется.
- **`base`.** Правка по id берёт `revision` строки шарда копии, иначе снимка таблиц (P/08.6 Н1.3б). Все строки выше — в `domain.view_tables`, кроме `auto/versions`: новая строка `base` не несёт, а снятая при `historyNote` и удалении правила затирает локальную правку, это предел. Так же у таблицы со снимком `refused`.
- **Создание.** Строка камеры — `{new: true, op: put, sub: cam, rows: cameras, id: "$id", fields}`, `ref` — `<кластер>-$id` (ADR-0111 п. 3), записи — `{create: true, id: "$id"}`, `{create: true, id: "$id-<том>"}`, поле `cam` — `$id`. Номер выдаёт агент, исход несёт его полем `made`: из него `backend` строит id записи. Прочие вида с `unit.id: numeric` — так же, детектор — `{create: true, id: "$id-<kind>"}`, второй вида — с номером, правило — `{new: true, sub: auto, rows: scenarios}`, `auto/rule_marks/$id` и `auto/versions/$id-1` той же связкой. `new` в связке один: создание камеры с `recordMode: motion` — две правки, строка записи после `made`; копия `template` с потоками, потоки в `children` — 422 `NOT_SUPPORTED`, `field: /properties/templateId`, `/children/<i>/kind`. `identifier` судится по снимку. Том — связкой: новая строка таблицы `rec/volumes`, `put` по `name` (P/08.6 Н1.3б); единица — `cam/unit_next` с `n + 1` по снимку и `cam/device_units/<строка>-<n + 1>`, одной связкой; счётчик сдвинули — исход `conflict`.
- **Ключ.** `Idempotency-Key` одиночной правки — hex SHA-256 от `edit`, нулевого байта, `user`, нулевого байта, id записи, нулевого байта, `If-Match` и нулевого байта с SHA-256 тела без полей `edit_secrets`: ключ лежит открыто в `domain/pending` и `carry`, производного от секрета в нём быть не должно. Повтор той же правки находит прежнюю (P/08.6 Н1.4 `repeat`). Секрет в теле — ещё 128 случайных бит: повтор с секретом — вторая правка с тем же значением, безвредно. У элемента групповой записи — ключ шага Н1.4 без прочитанного, у шага операции — `step_key` (P/06.9 Н2).
- **Секрет.** `password`, `secret` тела уходят открытым значением только в теле двери, полем `edit_secrets` манифеста (`cred_secret`, `access_secret`): запечатывает ключом члена процесс `domain` (P/08.6 Н1.3а). В `backend/repeats` и `backend/undo` его нет. Адрес с учётными данными дверь отказывает: логин идёт полем.
- **Отказы двери** до приёма — строки Н4, ничего не хранится. `409 kept_full` — 409 `BUSY`, `params.reason: kept_full`: член не успевает.
- **Ответ.** Чтение и сверка — как Н1.3. Член цели в виде не `ok` — 409 `SERVER_OFFLINE`, `params.targetId`, правка не подаётся: принятую правку не отменить, а молчащая коробка применит её неизвестно когда. У строки `POST /units` — `failed`, у шага — итог `fail`. Цель — камера-кластер, `class: camera` (ADR-0113 доп. (1) п. 3): ожидания нет, правка доходит с периодом камеры, поэтому сразу 409 `SERVER_OFFLINE`, `params: {targetId, kept}`, как срок вышел. Это каждая правка камеры из другого кластера, подпись пресета тоже; контракт называет `SERVER_OFFLINE` с `params: {targetId, kept}` не отказом: правка принята и применится (глава 14 Н1.1), у строки `POST /units` элемент `failed` несёт те же `params` (`UnitsCreateResult.failed[].params`). Вторая правка этой камеры до применения первой — 412 `VERSION_MISMATCH`: чтение отдаёт прежнюю версию; повтор той же правки новую не заводит. Иначе подача, `202 {kept}` — ожидание исхода в пределах срока маршрута: опрос `GET domain`, элемент `outcomes.<член>` с `id` = `kept`, затем чтение заново.

| Исход | Ответ |
|---|---|
| `performed` | 200 записи вида, новая версия; вид отстаёт — чтение повторяется в том же сроке |
| `conflict` | 412 `VERSION_MISMATCH`, `current`: запись на члене поменяли после приёма |
| `refused`, `status` 403 | 403 `PERMISSION_DENIED` |
| `refused`, `status` 404 | 404 `NOT_FOUND` |
| `refused`, прочее, в том числе `status` 0 | 422 `VALIDATION_FAILED` без `field`: `error` исхода — фраза, код из неё не выводится (Н4) |

  Хранимая правка не отменяется (ADR-0111 п. 16): откат — новая правка. Групповая запись подаёт элементы по порядку, ждёт одним сроком на всю группу; элемент без исхода — `failed` `SERVER_OFFLINE`, итога в `steps` нет, `<h>` остаётся `started`: повтор ключа доводит его (Н1.4, отказ `SERVER_OFFLINE` до подачи — обычный итог).
- **Шаг операции.** Подача в шаге, ожидание в пределах `OPS_STEP_WAIT`, исход — итог: `performed` — `ok`, `versions` — карта `{"rows": …}` `revision` строк вида, прочие — `fail` по таблице выше. `expected.rows` чужого шага не сверяется: порядок держит `base` и `same_path` (P/09.1 Н1.5), вид отстаёт. Срок вышел — кончить вызов, итога нет (Н1.8 шаг 5), консоль вызовет шаг снова, тем же ключом. **Предел:** после `OPS_STEP_TRIES` итог `fail not_run`, а правка всё равно применится. Секрет шага — как выше.
- **Откат.** Строка `backend/undo` чужого шага ложится после исхода `performed` отдельной записью: пакета с записью нет, обрыв между ними оставляет шаг вне стопки. `rows` — поля снимка таблицы вида до и после; поле вне `domain.view_tables` — слово `refuse` `view`. Шаг отката — новая связка `before` поверх снимка, шаг повтора — `after`, проверка по значениям — по виду, с его задержкой.
- **Занятость.** Строки `backend/opbusy` другого кластера страж не видит, связка стражей не несёт: чужая операция над той же записью судится только `base`, исход `conflict`. Удаление камеры снимает потоки, записи, детекторы и строку записи той же связкой. Каскады Н1.2, Н1.10 — так же, не вмещается — 422 `VALIDATION_FAILED` без `field`; правила другого кластера каскад снятия не правит: цель с мёртвым `id` судит вычислитель (Н1.10).
- **Только через свой кластер.** Включение камеры, выключенной правилом (Н1.2), — просьба `cam`: чужой дверью не идёт, `properties.enabled` — 422 `NOT_SUPPORTED`, `field: /properties/enabled`. Таблицы Н1.11 — так же. Поле `server` единицы дверь отказывает как платформенное: чужое правило его не хранит, `serverId` правила только выбирает кластер. Строка `auto/versions` идёт связкой и члену за NAT: номер — `revision` строки сценария в снимке + 1, он больше прежних номеров, историю читать не надо, снимок отстал — `conflict` всей связки; номера идут с пропусками. Чтение истории — глава 3 Н1.2а. `run`, `retry` чужого правила — просьбы: 409 `NOT_RUNNABLE`, `params.reason.code: otherCluster`. `apply` — групповая операция по кластерам (ADR-0111 п. 12): V/11.8.
- **Живое, пресеты, поворот, команда** (ADR-0111 п. 11). Запись другого кластера, кроме подписи пресета `PUT {name}` (ADR-0111 доп. Поля нет — ссылки нет: член за NAT, или кластер не его. У камеры за NAT `status.observed.direct: false` (глава 3 Н1.3). Камера w2c за NAT: живое — из шлюза кластера приёмника, движение арендой недоступно, положение пресета идёт просьбой `cam`, а не строкой: дверью правки не проходит, предел Н1.16; подпись пресета работает. Так и говорит `status.observed.direct` профиля `vms.camera/1`.

### Н1.14 Приём в домен и приёмник

`POST /units/{uid}/move` записи `server` и шаг `move` в `POST /operations` (Н1.8): у вида `server` есть возможность `move` (`kinds.json`), профиль `vms.server/1` сам судит родителя и `params` (контракт `UnitMoveRequest`): `parentId` — домен приёма, `null` — исключение. Запись иного вида без `move` — 422 `NOT_SUPPORTED`, `field: /kind`, `params.capability: move` (глава 2 Н1.2). `If-Match` — 428 без него, 412 `VERSION_MISMATCH` с `current` при иной версии (Н1.3); тело по схеме, иначе 422 `VALIDATION_FAILED`, `field`. **Решено:** стучащаяся запись с `parentId: null` и распределённая с `parentId` не `null` — 422 `PARENT_MISMATCH`, `field: /parentId`: профиль принимает только стучащийся сервер и исключает только распределённый (контракт `UnitMoveRequest`); `parentId` не `Domain.id` — то же.

- **Приём** (ADR-0110 доп. (6)). `parentId` — `Domain.id`, запись — стучащийся сервер из `knocking` (`server(knocking)`, глава 3 Н1.3 «`server`»; такого нет — 404 `NOT_FOUND`): `POST /domain/members {name, fingerprint}`. `params.fingerprint` — подтверждение сверки человеком: нет его или не равно `status.observed.fingerprint` стука — 409 `FINGERPRINT_MISMATCH` (контракт `UnitMoveRequest`), ничего не записано; `If-Match` — версия стучащейся записи, её `fingerprint` (глава 3 Н1.3). Камера w2c после приёма — запись камеры (глава 5 Н1.2). Отказ держателя 409: потолок серверов, нет хранителей, строка раздела полна — 422 `NOT_SUPPORTED`, `message` — слова держателя; 429 `busy` — 409 `BUSY`. Сервер в кластер заводит установщик, `join` с закреплением корня — подготовка коробки.
- **Исключение** (ADR-0111 п. 17). `parentId: null` — член сервера находится по виду (глава 3 Н1.2а), `If-Match` сверяется с версией записи `server`; затем `GET /domain/members/<член>` и `DELETE /domain/members/<член>` с `If-Match` — `ETag` этого чтения: член целиком (P/08.3 Н2, P/10 Н1.2б). Сервер члена с несколькими серверами — 422 `NOT_SUPPORTED`, `field: /parentId`. 400 держателя — 422 `NOT_SUPPORTED`, 404 — 404 `NOT_FOUND`, 412 и 409 `the list of members kept changing` — 412 `VERSION_MISMATCH`, неответ — Н4. **Решено:** `params.domainId`, отличный от `Domain.id`, — 404 `NOT_FOUND` (контракт: «домена нет»): у вида `domain` нет `create`, другого домена нет.
- **Ответ.** **Решено:** запись, которой стал сервер, прочитанная заново, с `ETag` (контракт отвечает `Unit` и у шага называет её: `OperationItem.createdId`): после приёма `class: server` — запись `server` с `properties.allocated: true`, `class: camera` — запись камеры этого члена (глава 5 Н1.2); после исключения — запись `server` с `properties.allocated: false`. Вид отстаёт — чтение повторяется в пределах срока маршрута, как при `performed` (Н1.13); к сроку запись не видна — 503 `UPSTREAM_UNAVAILABLE`: перенос состоялся, его исход — чтением.
- Обе двери судит `admin` домена, а не грант кластера: 403 — 403 `PERMISSION_DENIED`, хотя права на кластер есть; у шага — итог `fail`. У одиночного `move` памяти ключа нет: `UnitMoveRequest` не несёт `idempotencyKey`; у шага — память операции (Н1.4, `op: createOperation`). Объект под групповой операцией — 409 `BUSY`, `params.targetId`. Перенос в стопку отката не ложится (Н1.12 «Предел»).
- **Приёмник** (ADR-0111 п. 5) — `PUT /units/{uid}/recording-target {serverId, copies}`, тело по схеме, иначе 422 `VALIDATION_FAILED`, `field` — указатель; запись не реализует `vms.camera/1` — 422 `NOT_SUPPORTED`, `field: /kind`; камера своего кластера, не камера w2c — 422 `NOT_SUPPORTED`, `field: /serverId`: её пишет свой кластер; сервера нет — 422 `VALIDATION_FAILED`, `field: /serverId`. `copies` — список `serverId` дополнительных приёмников, порядок значим, пусто — копий нет; копия — кластер: повтор, сервер, которого нет, два сервера одного кластера, сервер кластера основного — 422 `VALIDATION_FAILED`, `field: /copies`, склеивать молча нельзя: человек выбрал два и получил бы один. `serverId: null` при непустом `copies` — то же. Перевод: `PUT /domain/placement/rec/<ref> {cluster, origin, copies}`, `If-Match` — `rev` записи, `origin` — кластер камеры, `cluster` — кластер `serverId`, `copies` — кластеры серверов `copies` по порядку, плюс `origin`, если у него есть том `edge` (V/02.6 Н1.7; читается `GET /domain/at/<origin>/rec/volumes`, не прочиталось — ставится): иначе запись на карту камеры w2c встанет `assigned to another cluster` и при обрыве связи кадры не лягут нигде (V/02.9 Н1.1); добавленный `origin` наружу не отдаётся: на чтении `copies` без него; вместе с назначением — строка `rec/recordings/<cam>` в кластере приёмника связкой (Н1.13): строки назначение не создаёт (V/02.9 Н1.1). `serverId: null` — `DELETE /domain/placement/rec/<ref>`; строка записи остаётся: снимает её правка записи. 412 — 409 `BUSY`, без связи — 409 `SERVER_OFFLINE`. Ответ — `GET /units/{uid}`.

### Н1.15 Потоки камеры и живое видео

Поток — строка `cam/cameras` и запись вида `stream` под своей камерой (глава 3 Н1.3 «Потоки»; `kinds.json`: `parents: [camera]`, возможности `create`, `rename`, `delete`): `POST /units` с `parentId` — камерой, `PATCH /units/{uid}`, `DELETE /units/{uid}` потока. `parentId` не камера — 422 `PARENT_MISMATCH`, `field: /parentId`; потока нет — 404 `NOT_FOUND`. ### Н1.16 Поворот и пресеты

Предмет — камера с `ptz` (V/01.4 Н1.4г). Перед записью: запись не реализует `vms.ptz/1` — 422 `NOT_SUPPORTED`, `field: /kind` (контракт); дальше, кроме имени пресета и `DELETE` пресета: `properties.ptz` ложь — 422 `NOT_SUPPORTED`, `field: /properties/ptz`; нет связи, `can` не сказан — 409 `DEVICE_OFFLINE`. Право — `edit` на камеру, отказ — 403 `PERMISSION_DENIED`. Камера выключена правилом: просьба — отказ держателя, ниже; поворот — успех записи, строка `ptz_moves` лежит, камера стоит, слово в `ptz_reason` пульса.

- **`PUT /units/{uid}/ptz`** — строка таблицы `cam/ptz_moves/<camera>-<person>`: `POST` двери таблиц без `cas`, полная замена, `camera`, `person` — человек билета, `seq` — миллисекунды часов воркера: растёт с каждым продлением, `pan`, `tilt`, `zoom`, `focus` — значение контракта × 100, до целого, нет поля — 0. Имя человека не годится ключу таблицы (V/01.4 Н1.4г) — 422 `NOT_SUPPORTED`, `field: /properties/ptz`. Ответ — `PtzLease {expiresAt}`: сейчас + `ttlSec`. Срок держателя один, `PTZ_LEASE` = 5 с: `ttlSec` меньше него камеру раньше не останавливает, это предел. `DELETE` снимает строку, 404 двери — тоже 204. Двое на камере — V/01.4 Н1.4г.
- **Просьба устройству** — `POST /cam/requests` по билету (P/06.3 Н1.9), `Idempotency-Key` — 128 случайных бит запроса, у команды с `idempotencyKey` — Н1.17; подача повторяется тем же ключом до 200 с меткой, в пределах срока маршрута `api/units`. Исход: `performed` — успех; `refused` со словом `no such operation` или `unit needs n and an operation` — 409 `DEVICE_REFUSED`, `params.reason: noOperation`; прочий `refused` — 409 `DEVICE_REFUSED`, `params.reason: refused`; метки нет к сроку, `expired`, `gone`, `unknown` — 409 `DEVICE_OFFLINE`.
- **`PUT /units/{uid}/presets/{n}`.** **Предел** (ADR-0111 доп. (1)): сохранение положения на камере за NAT — 409 `OTHER_CLUSTER`, ссылки нет: положение пишет устройство в момент просьбы, хранимая правка исполнилась бы через период отчёта, на случайном положении. Подпись пресета идёт правкой, у камеры за NAT тоже. `PUT {}` — просьба `{unit: <cam>, action: preset_save, n}`; после `performed` строки `cam/preset_labels/<cam>-<n>` нет — создаётся с пустым `label`, отказ устройства строки не оставляет. `PUT {name}`, пустое тоже, положения не трогает никогда: строки нет — создаётся, `name` ложится в `label`; есть — `label` заменяется, пустое снимает подпись, строка остаётся. Запись имени не идёт устройству: связь и `ptz` её не судят; пакет с `cas`, у чужой камеры связкой Н1.13. Строку снимает только **`DELETE`**, всегда и первой; затем `preset_clear` при `ptz`, связи и своей камере. Иначе просьбы нет, 200, положение в камере остаётся: это предел. Просьба отказана — 409 `DEVICE_REFUSED`, строка уже снята. Номер с именем драйвера остаётся в `properties.presets`, пока драйвер его называет. Граница `n` судится только при сказанном `can`: `n` больше `properties.presetMax` — 404 `NOT_FOUND` у обоих. Ответ `PUT` и `DELETE` — запись камеры, `ETag` (контракт); строки таблицы в `properties.presets` свежие, имена драйвера идут из пульса и отстают на его период, это предел.

### Н1.17 Команда единицы

`POST /units/{uid}/actions/{action}` (`runUnitAction`) — команда из `UnitKind.actions` вида записи (`kinds.json`): команды, которой у вида нет, команда со `scope: [kind]` или с `ruleOnly: true` (действия камеры для правил, `unit`) — 404 `NOT_FOUND` (контракт `ActionDescriptor`); `params` по схеме команды, иначе 422 `VALIDATION_FAILED`, `field: /params/<p>`. Команда единицы — `open`, `close`, `block` у `acfa_lock`, `arm`, `disarm` у `acfa_fence` — просьба устройству (Н1.16) `{unit: <camera строки>, action: unit, n: <n строки>, operation: <action>}`: цель — запись `cam/device_units` не `type: det`. Нет связи — 409 `DEVICE_OFFLINE`, до просьбы. Ответ — `UnitActionResult {result: {done: true}}`. `properties.operations` — подсказка, слово судит держатель. `idempotencyKey` тела — **Решено:** он — `Idempotency-Key` просьбы вместо случайного, как у `run`, `retry` правила (Н1.10; ключ даёт контракт, память — консоли), `409 exists`, `409 spent` — 422 `VALIDATION_FAILED`, `field: /idempotencyKey`; без него — 128 случайных бит (Н1.16). **Решено:** 403 двери консоли или домена — 403 `PERMISSION_DENIED` без `params.right`: судится право двери, `ActionDescriptor.right` суда не добавляет (V/11.8 Н1 «Классы»).

**Реле** (ADR-0112 доп. (13)). Команда `output` у `relay` — просьба `{unit: <хозяин>, action: output, port: <number>, state[, pulse_ms]}`: `params {state, pulseMs?, port?}`, `state` нет — 422 `VALIDATION_FAILED`, `field: /params/state`; **Решено:** `port`, отличный от `properties.channel`, — 422 `VALIDATION_FAILED`, `field: /params/port` (схема команды: «если поле есть, значит то же самое»); `true` — `closed`, `false` — `open`; `true` с `pulseMs` — `state: pulse`, `pulse_ms`. **Предел:** `false` с `pulseMs` — `open`, возврата нет: у держателя импульс только замыкает. Ответ `{result: {done: true}}`. Право — `edit` на хозяина. Нет связи, ответ — как у единицы.

### Н1.21 Документ сценариев

Один документ на домен: `settings.shared.auto.scenarios`, сценарии между камерами V/07.5 Н1.1. Не `Rule`, вне отката, истории нет (ADR-0112 доп. (10)). Вне домена: `GET` — `{version: "0", items: []}`, `PUT` — 409 `SERVER_OFFLINE`. Двери — записи `GET domain/shared/auto`, `domain/shared`, `GET domain/at/auto/heartbeats` (ADR-0112 доп. (12) пп. 1, 3).

- **`GET /domains/{id}/scenarios`** — `GET /domain/shared/auto`: `items` — `fields.scenarios.value`, нет — `[]`; `version` — `r<rev>`, документа нет — `r0`.
- **Строка документа ↔ `Scenario`.** `name`, `kind`, `action`, `n`, `port` как есть; `validForSec` ↔ `valid_for`; `ratePerMinute` ↔ `rate_per_minute`; `enabled` как есть, чужие поля не добавляются. `deviceId` ↔ `(member, camera)`: `camera` — `ref`, id записи считается от `id` строки (Н1.6), поэтому `GET` читает на различный `member` одну строку `GET domain/cam/cameras?cluster=<member>`, запись — обратный путь Н1.6 по строке раздела. **Срок** — как у `status`: новый вызов не позже 10 с от начала запроса; не успел — 503 `UPSTREAM_UNAVAILABLE`, ничего не записано: документ не отдаётся частями, запись его потеряла бы сценарии. Чтение строки без `member` — член, владеющий этим `ref`, не один или нет — `deviceId` своего кластера, форма покажет неизвестную цель. Запись пишет `member` всегда, и в `when`, и в `then`: `ref` уникален только в кластере (ADR-0112 доп. (10) п. 2).
- **`PUT /domains/{id}/scenarios`** (`If-Match` — 428 без него): право — `admin` домена, иначе 403 `PERMISSION_DENIED`. Форма по порядку: больше `scenariosMax` — 422 `VALIDATION_FAILED`, `field: items`; повтор `name` — 409 `NAME_TAKEN`, `field: items[i].name`; `n` и `port` вместе, `n` при `output`, `port` при `preset`, `validForSec` вне 10…600, `ratePerMinute` вне 0…600, `kind` вне `scenarioKinds` — 422 `VALIDATION_FAILED`, `field: items[i].…`; цель не камера — 422, `field: items[i].then.deviceId`, триггер — `items[i].when.deviceId`. Что умеет цель, форма не судит: это отказ цели, он виден в состоянии (V/07.5 Н1.6). Запись — `PUT /domain/shared {base_rev, shared: {auto: {scenarios}}}`, `base_rev` — число из `If-Match` контракта `"r<rev>"`, первая запись — 0; не такая форма — 412 `VERSION_MISMATCH`, без обращения. Заголовка `If-Match` к двери нет: рядом с `base_rev` ей годится только индекс, а версия контракта — `rev` (P/08.0 Н1.9). Чужая правка, `409 the shared settings are at` — 412 `VERSION_MISMATCH`, `current` — чтение; 403 — 403; двери домена не отвечают — 409 `SERVER_OFFLINE`, ничего не записано. Ответ — записанное, `version` — `rev` ответа двери: копия кластера отстаёт. Поток — `entity.changed` `kind: scenarios` (глава 5 Н1.2). **Предел:** чтение — копия, она отстаёт на проход агента: запись по старой версии — 412, пока копия не дойдёт. **Предел:** документ пишется целиком, правки разных сценариев конфликтуют на 412 (ADR-0112 доп. (10) п. 3).
- **`GET /domains/{id}/scenarios/status`** — только чтение, версию не двигает: документ общий на домен, состояние видно целиком (ADR-0112 доп. (12) п. 3). Кластеры — различные `when.member` документа; нет поля — кластер владельца `ref`, не найден — сценарий пропущен. Свой кластер — `GET /auto/heartbeats`, чужой — `GET /domain/at/<кластер>/auto/heartbeats`: обе двери → `{rows: [{worker, server, ts, age, worker_state, fields}]}`, в `fields` только `shared`, манифест `heartbeat: {door: [shared]}` (V/07.5 Н1.6, P/06.7 Н1.6 `pulse`; поля `status` там нет, он и не нужен). Поля: `phase`, `reason`, `since`, `asked`, `outcomes`, `holding`, `decidedWithout` ↔ `decided_without`, элемент на имя; сценарий у двух серверов — с большей `since`. Кластеры — по порядку имён, свой первым. Новый вызов не начинается позже 10 с от начала запроса: `wait` маршрута 15 с минус `FORWARD_WAIT` 5 с. Кластер не ответил или не успел — его элементов нет, ответ идёт. **Цена:** вызов на кластер документа, не больше `scenariosMax`, срок сверху. **Предел:** сценарий, ещё не взятый вычислителем, и сценарий члена без ответа в ответ не идут.

### Н1.22 Шкала и куски

ADR-0112 доп. (13) п. 5. Порядок — V/11.16 Н1.2, V/11.17 Н1.1; здесь — что делает `backend`. Двери регистратора зовёт он сам, адрес и токен — `where` по билету человека (V/11.1 Н1.2а); байты кусков идут мимо него.

- **`GET /units/{uid}/timeline?from&to&limit&cursor`.** Запись не реализует `vms.timeline/1` — 422 `NOT_SUPPORTED`, `field: /kind` (контракт). Нет `from`, `to` — всё: 0 и сейчас.
  1. Записи: своя камера — `GET /rec/recordings` с её `cam`; чужая — таблица члена `GET /domain/rec/tables/recordings` (глава 3 Н1.2а). Записи других кластеров — раздел книги по `ref`: `GET /domain/rec/books/primaries/*/<раздел>`, раздел — 12 бит SHA-256 `ref` (V/02.9 Н1.6), отвечает держатель, просьбы не нужно, зритель не ждёт копии; элементы `ref` камеры с ролью `primary`, `backup` и `running`. Цена — одно чтение строки раздела, с числом камер домена не растёт. 404 `empty_part` — записей других кластеров нет, молчание. 503 — голова срока ещё не вышла, у `primaries` до 20 мин после переноса: `unavailable` `what: cluster`, `id` — свой кластер, запись других кластеров названа недоступной; прочий отказ двери — то же.
  2. На запись: `GET /rec/where/<запись>`, `GET <door>/timeline/<запись>?from&to`.
  3. На запись и место таблицы мест `rec`: `GET /rec/where/<таблица>/<место>?unit=<запись>` и `/timeline` там. Запись другого кластера — через консоль цели, полная шкала: `GET /domain/at/<член>/rec/timeline/<запись>?from&to`, на каждое его место ещё `?place=<таблица>/<место>`, места — `GET /domain/rec/tables/volumes` члена; `where` не нужен, ответ как у двери (ADR-0112 доп. (13) п. 10, P/06.7 Н1.6). Ответ больше 1 МиБ — 502 `answer too large`: окно делится пополам, половины спрашиваются заново, не больше `TIMELINE_SPLITS` = 8 вызовов на каждый исходный вызов — «запись» и каждый «запись, место» отдельно: у каждого свой ответ и свои 1 МиБ, это 4–5 частей окна, значение на замер (ADR-0112 доп. (14) п. 1; решила «Спецификация VMS» по ревью норм (14)–(17) М1). Прочий 502 — член не слышен, окно не делится. Сверх него или не ответила — `unavailable` `what: cluster`: непрочитанный остаток окна назван, «целиком» значит в этих пределах.
  4. Слияние, уступка, недоступное — V/11.16 Н1.2.
- **Цена:** 2 + R × (1 + 2P) вызовов на **страницу**, R — записей, P — мест: около 125 на 3 записи и 20 мест, у чужой записи 1 + P без `where`, деление окна — до `TIMELINE_SPLITS` вызовов вместо каждого исходного: у чужой записи всего до 8 × (1 + P), 168 при 20 местах; состояния у `backend` нет, поэтому каждая страница собирает шкалу заново. Каждый `where` — строка журнала `door.issued`: R × (1 + P) строк. Принято: цена на зрителя, а не на домен (ADR-0112 доп. (13) п. 5). `TIMELINE_PARALLEL` = 8 вызовов разом, ответ двери — 5 с (V/02.5 Н1.5), `TIMELINE_BUDGET` = 20 с на чтение: значения без опоры, на замер. Что не успело, — в `unavailable`, ошибки нет.
- **Спан:** `start`, `end` — `start_ms`, `end_ms`; `archiveId` — хранилище тома: дом записи или место двери, у тома `edge` свёрнутого члена — id его `storage`; `recordingId` — id записи; `epoch` — эпоха, `0` поля не даёт (копия удержания, архив устройства); `source` — нет поля — `live`, `backfill`, `device`; `backupOnly` — остаток «только в резервном» V/11.16; `fenced`. Порядок — `(start, spanId)`, `cursor` — кодированный `(start, spanId)` последней строки, чужой — 422 `INVALID_CURSOR`.
- **`spanId`** — base64url без `=` UTF-8 JSON `{m, r, e, s, a, b, p?}`: член, запись, эпоха, источник, границы в мс, место двери. Ввод клиента без доверия: подписи нет, право судит `where` по билету, запись не этой камеры — 404 `NOT_FOUND`.
- **`unavailable`:** `what: server` — `unreachable`, не ответивший `where` записи; `volume` — `unavailable`, место 404 с `X-Unreachable`, `id` — `<том>@<сервер>`; `cluster` — дверь члена, `id` — член. `reason` — слова V/11.16. Место 404 без `X-Unreachable` — молчание. 403 двери — `where` заново один раз.
- **`GET /units/{uid}/playback?at&spanId`.** Со `spanId` — один `where`: записи, у `p` — места `?unit=`, у чужого члена — через `/domain/at`: адрес двери чужого кластера клиенту, сквозь консоль байты не идут, предел `FORWARD_MAX` (ADR-0112 доп. (13) п. 11). Член `m` без `members[].url`: адреса нет, `/domain/at` 404 `no console known`, шкала — `unavailable` `what: cluster`, спанов нет, `playback` без `spanId` — 404, `spanId` с таким `m` — 409 `OTHER_CLUSTER` без `params.url` (Н1.13). Судит член записи, не камера: запись камеры w2c за NAT на сервере с `url` доступна. **Предел:** `members[].url` — адрес консоли, `door` — адрес регистратора, лист от корня чужого кластера: член с `url` за проброшенным портом даёт 200 с адресом, которого браузер не откроет, форма покажет сбой куска, `backend` этого не видит. Кусок — сетка 60 с от `a`: `from` = `a` + ⌊(`at` − `a`) / 60 с⌋ × 60 с, `to` = min(`from` + 60 с, `b`). `url` — `<door>/segment/<запись>/e<эпоха>/<fromMs>-<toMs>[.backfill | .device].mp4?t=<токен>`, `expiresAt` — `expires`: токен 120 с, адрес годится на кусок и начало следующего. Без `spanId` — переход по моменту: окно шкалы `[at − 60 с, at + 1 с)`, цена шкалы, спан по V/11.17 Н1.1: неотсечённый над моментом, нет такого — отсечённый. Спана нет, момент вне его, в том числе вне `[a, b)` данного `spanId`, — 404 `NOT_FOUND`. `at` не по форме — 422 `VALIDATION_FAILED`, `field: /at` (параметр запроса, контракт).

### Н1.23 Удержания

`Hold` — строка `rec/keeps/{cam}-{from:int}-{to:int}` (V/02.7 Н1.1, V/11.18 Н1.2). `id` — сам ключ: `StreamMessage.entityId` у него не UUID. `deviceId` — `uid` камеры `cam`, `by` — `stamp.by`, `at` — `made_at`, `releasedAt` — `released_at`, `recordingIds` — `recordings`, `note`.

- **`GET /units/{uid}/holds`.** `GET /rec/keeps` и отбор по `cam`: у таблицы отбора по полю нет, **цена** — вся таблица кластера на чтение карточки. `states` — поле `keeps` дверью пульса `GET /rec/heartbeats`: `{archiveId — хранилище volume пульса, state, why?}`, не названо — не сказано. Страницы — общее правило, порядок — по ключу. Чужая камера — те же двери через `/domain/at/<член>`, `id` — `<ключ>@<член>`: номер камеры уникален только в кластере, голый ключ совпал бы со своей меткой того же окна.
- **`POST /units/{uid}/holds`** `{from, to, note?, recordingIds?}`. Секунды — вниз у `from`, вверх у `to`; `to` не позже `from` — 422 `VALIDATION_FAILED`, `field: /to`; запись не этой камеры — 422, `field: /recordingIds`; `recordingIds` нет или пуст — все записи камеры сейчас. Запись не реализует `vms.timeline/1` — 422 `NOT_SUPPORTED`, `field: /kind`; чужая камера — 409 `OTHER_CLUSTER`: запись удержаний туда не идёт. Ключа нет — строка `cas ""`, 201. Есть — поля прочитанной строки, `recordings` объединяются, заметка и `released_at` не стираются, новая `note` — только у пустой, `cas` чтения, 200. 412 — заново, не больше трёх раз, иначе 409 `BUSY`. Право — `edit` на камеру, 403 — `PERMISSION_DENIED`. Срок метки — `longest` манифеста, 604800 с: длиннее держать платформа не станет (V/02.7).
- **`DELETE /holds/{id}`.** `id` с `@<член>` — 409 `OTHER_CLUSTER`: снятие только в кластере камеры. Иначе `DELETE /rec/keeps/<id>`; 404 — `NOT_FOUND`. **Предел:** строка нечитаема — право `*`, договор сторожевой и передачи `unresolved`, иначе 403. `released_at` контракт не пишет: метку, которую удаление не берёт, снимают дверью таблицы, мимо формы.
- **`POST /holds/{id}/verify`.** `id` с `@<член>` — 409 `OTHER_CLUSTER`. **Предел** (ADR-0112 доп. (16), (17) п. 2): `verify` метки другого кластера проверяет кластер записи у себя, через консоль цели маршрута нет. На запись метки, пусто — на записи камеры: `where` места первого включённого тома `incidents` с держателем, `POST <door>/keeps/<id>/verify?recording=<запись>` (V/11.18 Н1.2), `result` строкой. Маршрута `keeps` у двери нет — 409 `DEVICE_REFUSED`. Другой том не сверяется: предел. **Цена:** два вызова на запись.
- **`status.observed.heldBy`** записи `volume` — `held_by`, `null` — нет или не подтверждён.
- **`status.observed.incidentsLost`, `incidentsAtRisk`** записи `volume` — только у тома хранилища `archive.incidents`: `incidents_lost {метка: секунды}` и `incidents_at_risk [метка]` пульса держателя тома (V/02.7 Н1.5), элемент пульса регистратора `held_by` тома, `GET /rec/heartbeats`; у чужого тома — `GET /domain/at/<член>/rec/heartbeats`, член за NAT — 404, полей нет, не прочитано. Метка — ключ `rec/keeps`, `Hold.id`. Пусто или не прочитано — поля нет. Наблюдение, в версию тома не входит. **Цена:** чтение пульса на карточку тома, как `properties.state` тома.

### Н1.24 Отметки

`Bookmark` — строка журнала `kind: mark` (P/06.4 Н1.2). Правки и удаления нет, срок — срок журнала: отметка уходит с ним, защитить нечем (ADR-0112 доп. (13) п. 3). Отметка — момент или отрезок (ADR-0117 доп. (1) п. 2): `type: span` — у строки есть `to`, конец отметки оператора-отрезка `[occurred, to]` (P/06.4 Н1.2 `marks`), `type: moment` — нет. Метка `rec` конца не получает: ADR-0117 доп. (3) п. 2 заменил эту правку V/02.7 концом `to` отметки, поэтому отрезок архив не удерживает — удержание своей строкой (Н1.23). Выгрузку из отметки строит окно: отрезок — его границы, момент — ± `limits.bookmarkPadSec` из `Reference.export` (глава 20 Н1.8).

- **`GET /units/{uid}/bookmarks?from&to`.** `GET /events?from&to&unit=cam/<id>&kind=mark&by=occurred&late=<с>`: отметка о прошлом лежит в бакете своего `t`, а строка позже `to + late` запросу не видна, поэтому `late` — возраст конца окна, `now − to`, целое вверх, не меньше умолчания 3600, как V/11.16 Н1.3; нет `to` — сейчас, нет `from` — от начала журнала. **Цена:** чтение старого окна проходит бакеты от него до сейчас. `limit` идёт в журнал, страница одна, `nextCursor` нет: курсора у журнала нет, усечённое `truncated` — предел. `id` — UUID `event:`, `occurred` — поле строки, нет — `t`; `at` — `t`; `by` — `user`; `type` — `span`, если у строки есть `to`, иначе `moment`; `to` — поле `to` строки. Отрезок выбирается по своему `occurred`, как момент: отрезок, начатый до `from`, в окно не попадает — предел. Новые сверху.
- **`POST /units/{uid}/bookmarks`** `{note, occurred?, type?, to?}`. `note` пуста после снятия крайних пробелов — 422 `VALIDATION_FAILED`, `field: /note`. Нет `type` — `moment`; `moment` с `to`, `span` без `to` или с `to` не позже `occurred` — 422 `VALIDATION_FAILED`, `field: /to` (контракт `BookmarkCreate`). Отрезок без `occurred` — `occurred` — момент запроса по часам `backend`, переданный в теле: дверь берёт `to` только вместе с `occurred` (P/06.4 Н1.2). `POST /marks {unit: cam/<id>, note[, occurred][, to]}`, 201. Право — `edit` на единицу тела (P/06.3 Н1.9 `marks`), 403 — `PERMISSION_DENIED`; `global.bm` — вывод из него, V/11.8 Н1.2. Чужая камера — 409 `OTHER_CLUSTER`.

### Н1.25 Закрепить

`POST /units/{uid}/archive-fetch {archiveId, from, to}` — «Закрепить» V/11.16 Н1.2, просьбы V/02.8 Н1.4. `to` не позже `from` — 422, `field: /to`; чужая камера — 409 `OTHER_CLUSTER`. Основная — запись своего кластера этой камеры на томе `archiveId`, с домом не на резервном томе и без `replica_from`; нет — 409 `NO_PRIMARY`.

Отрезок делится по суткам, на сутки — `POST /rec/requests {unit: <основная>, from, to}`. `accepted` — сколько подано. `refused` — только о подаче: `per_person` — предел 7 на человека, остаток отрезка той же причиной, прочий отказ двери — её словом. Отказ регистратора приходит поздно, в журнале `archive.backfill.refused` (V/02.8 Н1.4): `GET /journal` камеры его показывает, глава 3 Н1.3. Склейку минут делает форма по спанам `backupOnly`, `source: device`: `backend` просит что сказано. **Цена:** запись на сутки отрезка.
