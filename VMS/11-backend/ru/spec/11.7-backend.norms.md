# V/11.7 — Ассистент конфигурирования в `backend`: нормы

Канон главы 7 урока V/11 «Бэкенд конфигуратора» (ADR-0093 доп. (6); ADR-0094 доп. (10)). Лекция (`ru/11-backend.md`, для человека, в выгрузку не входит),
[инструкция](11-backend.README.md), контракт [`consolem.openapi.json`](../../consolem.openapi.json); ассистент — урок
[V/10](../../../10-assist/ru/README.md). Платформа — по [`VMS/PLATFORM_PIN`](../../../PLATFORM_PIN) (ADR-VMS-0002) (пин VMS; приращение прав поверх норм B, ADR-0090 доп. (17); пометка «норма платформы B» — где глава на них опирается).

Текст производный от `spec/11.7-backend.norms.md`, руками не правится: источник — английский [`spec/11.7-backend.norms.md`](../../spec/11.7-backend.norms.md), правка идёт в него, русский пересобирается переводом (ADR-0121).

Ассистент конфигурирования (ADR-0093) — администратор пишет просьбу словами, модель внутри кластера предлагает план,
код проверяет план, записывает только человек. У нашей страницы ход идёт в браузере (V/11.9). Для WebUI consolem ход
идёт в `backend` (решение владельца, ADR-0093 доп. (6)): у `backend` нет своих прав, обращения в консоль — правами
человека по билету, пока открыт его запрос (ADR-0094 B1). Одна норма, две реализации: инструменты, проверка плана и
векторы — главы 9–13: цикл только в `backend` (ADR-0093 доп. (8) п. 2), панель страницы снята. Глава нормирует операцию хода,
цикл хода в `backend`, перевод плана в слова consolem и предел хода.

Id норм — `V/11.7-MM`.

## N0 Словарь слов

Нормативные слова — по [канону курса](../../../../Platform/common/ru/NORMATIVE-TERMS.md). Правила модуля «Платформа» — [P/01.1
N0](../../../../Platform/01-store/ru/spec/01.1-store.norms.md#n0-словарь-слов).

- **Ход** — V/11.9 N0: от просьбы до исхода; вопрос ход не кончает.
- **Запрос** — один `POST /assist/turns` от открытия до прежнего события конца: `question`, `plan`, `refused`, `answer`, `found`, `error`.
- **Переписка** — тексты хода и сообщения шагов модели, которые держит клиент и возвращает с каждым запросом:
  своего состояния у `backend` нет (ADR-0094 A3).
- **План consolem** — проверенный план (V/11.11 N1.1), переведённый в `items` `AssistPlanItem` контракта: `PATCH /units/{uid}` или шаги `patch` `POST /operations`.

## N1 Форма

**Время.** Сроки главы — секунды монотонных часов процесса.

### N1.1 Операция хода

- Операция хода — потоковая операция контракта `POST /assist/turns` (`assistTurn`, глава 2 № 51), возможность `assist`, тело `AssistTurnRequest` `{text, context?,
  secrets?}` (`text` — что написал человек; `context` — непрозрачная строка из прошлого ответа разговора, клиент
  возвращает её как есть; `secrets` — массив строк, секрет № N — место N с 1 (V/11.12 N1.3):
  модели идёт только «секрет № N введён», значение подставляет код `backend` в `/properties/password` плана, N1.3; в `context`
  секреты не кладутся; дополнение Kimi к разбору ревью V/11, замечание «Консоли»), ответ — поток SSE `text/event-stream`: на сообщение строка `data:` (`AssistEvent`), без `event:` и `id:` (ADR-0094 доп. (10) п. 2).
- `text` пустой — 422 `VALIDATION_FAILED`, `field: text`, ответ `application/problem+json`, потока нет. Типа хода в запросе нет: его выбирает `backend`, N1.6; поле `kind` контракт (b09cdf8, 0.2.0) не знает — 422 `VALIDATION_FAILED`, `field: kind`, как всякое лишнее. Поле `world` — только демо-страница контракта: V/11 его не принимает, 422 `VALIDATION_FAILED`, `field: world`.
- Маршрут передачи — `api/assist/turns`, **потоковый** (V/11.1 N1.5; норма платформы B1): без предела 5 с и буфера
  4 МиБ; билет потока годится только на чтения и маршрут двери подсистемы — инструментам и проверке плана этого хватает
  (V/11.10, V/11.11 только читают), а модель зовётся маршрутом. Предел ожидания маршрута — `ASSIST_TURN_MAX` (N1.5).
- Обрыв потока до события конца — отмена хода: билет погас вместе с запросом, поэтому `backend` отбой `DELETE` шага послать не может и
  больше ничего не шлёт; незавершённый шаг дверь модели снимает по `ABANDON` (V/10.2 N1.3).
  Оборванный поток не продолжается: клиент повторяет запрос с тем же `context`.

### N1.2 Цикл хода в `backend`

Цикл — V/11.9 N1.2–N1.5 (сообщения шага, окно, шаг, разбор ответа модели, исходы). Здесь — чем он связан с запросом контракта:

- **Модель** — дверь модели V/10.2 через консоль: `backend` зовёт маршрут `/assist/chat/<name>/…` по билету (обратный
  вызов из перечня, V/11.1 N1.5; P/06.3 N1.9 «Маршрут двери»), консоль передаёт его держателю с токеном двери (право
  `view` на строку модели — человека билета; ADR-0094 доп. (12) п. 7, ADR-0093 доп. (7)). Адреса и токена двери `backend`
  не видит: `/assist/where` он не читает. Шаг ставится и опрашивается по V/10.2 N1.2, N1.3; у маршрута предел `PASS_WAIT`,
  поэтому `wait` опроса — 3 с (V/11.9 N1.3). Модель хода — строка модели, которую называет `context`, без него
  — первая видимая человеку строка `assist/models` по имени с фазой `running`; список
  — `GET /assist/models` по билету (обратный вызов из перечня, V/11.1 N1.5; дополнение Kimi к разбору ревью V/11, № 1).
  Ключей и адреса модели клиент не видит.
- **Переписка** — в `context`: base64url без `=` UTF-8 JSON `{v: 1, model, turn, texts, messages}` — модель хода, `turn`
  хода (V/11.9 N1.2), тексты хода и сообщения шагов, которые идут в историю (V/11.9 N1.2); `type` — тип хода при открытом вопросе (N1.6), иначе поля нет. Каждый запрос с `context` — новый `text`
  добавляется к `texts`, ответ на вопрос и уточнение (V/11.9 N1.5); `context` не читается или `v` не `1` — ход заново без истории (новый `turn`). Секретов в
  `context` нет: метки секретов живут только внутри одного хода (V/11.12 N1.3), и новый ход их не наследует.
- **`context` — ввод клиента без доверия** (дополнение Kimi к разбору ревью V/11, вопрос 3): подписи (MAC) нет — у
  `backend` нет ни состояния, ни своих ключей. Его сообщения — не доказательство ни прав, ни данных: модель видит их как
  историю, а вред ограничен правами человека по билету (каждое чтение — его правом), проверкой плана кодом над свежим
  чтением (V/11.11) и тем, что маршрут двери модели проходит только по праву `view` человека.
- **Вопрос** `ask_admin` кончает запрос (V/11.9 N1.4 п. 6): поток кончается событием `question`, ответ
  человека — новый запрос с `context` вопроса (ADR-0093 доп. (6) п. 2).
- **Тип `learn`** — N1.10 и V/11.9 N1.7: отдельная ветвь только по каталогу, без чтений рабочих объектов, рабочего контекста, секретов и инструментов плана. Выбор идёт до построения рабочего обзора. Учебные инструменты — V/11.10 N1.7; допуск к модели и очередь — прежние V/10. Эта ветвь и логическое расширение `answer.learn` закрыты условием N1.10 и не включены в закреплённую поставку.
- **Тип `rules`** (V/11.13): харнес, инструменты, план и слои — той главы, ход и окно — эти. Тип выбирает `backend`, N1.6. План — событие `plan` с `rules`, `AssistRuleEdit`: тело переводчика нейтрального плана, `id` — UUID, `@<ref>` как есть, `logOnly: true` у нового правила (V/11.13 N1.4). Запись правил — по «Применить» контрактными дверями `POST /rules`, `PUT /rules/{ruleId}` сессией человека (V/11.13 N1.7), не операция хода.
- **Тип `export`** (ADR-0093 доп. (47); V/11.20) — N1.9: просьба о выгрузке; модель называет заказ, тело `AssistExport` контракта (`ExportCreate` без `password`, `supervisor`, `idempotencyKey`) собирает код и проверяет по миру. Ход ничего не пишет: план — событие `plan` с `export`; окно проверяет заказ через `POST /exports/check`, пароль и супервизора вводит человек, и «Экспорт» создаёт заказ через `POST /exports` сессией человека (V/11.20 N1.2). Тип по умолчанию выключен, как `config`: ключ `ASSIST_EXPORT` файла подсистемы (`off` \| `on`, по умолчанию `off`; V/09.2).
- **Инструменты** типа `config` — закрытый набор V/11.10: те же имена, аргументы, результаты, ошибки и слова; чтения — двери консоли из
  перечня V/11.10 N1.2 по билету потока. **Охват** — константа урока: `cam`, `rec`, `det` (ADR-0093
  доп. (5), (6)); `list_subsystems` и `get_manifest` — по `GET /manifest`, отфильтрованному по охвату; `/mounts` не
  читается (дополнение Kimi к разбору ревью V/11, вопрос 4). **`can_edit`** — то же правило `may("admin",
  "unit:<sub>/<id>", "<sub>")` модуля (P/07 N1.5: гранты сессии и область P/06.3 N1.3) над `GET /session` человека билета. Каждая
  дверь, которую читают инструменты, — в перечне обратного вызова (V/11.1 N1.5). Отказ двери 403 — ошибка инструмента
  V/11.10 N1.2 «нет доступа» (`GET <path>: 403 <detail>`), ход идёт дальше; 401 — билет мёртв: поток закрыт (N4).
- **Проверка рабочего плана конфигурации** — V/11.11 целиком (форма и права, сверка слов, отбор, вопрос и отказ), над свежим чтением консоли
  по билету; затем — перевод в план consolem (N1.3). Модель план не проверяет: проверяет код.
- **Счёт вызовов** — `TURN_CALLS` = 25 на ход (V/11.9 N1.2), `STEP_TRIES`, `RESTARTS`, `ENQUEUE_WAIT` — по главе 9
  (V/11.9 N1.3); исход за пределом — тот же: «ход не завершён».

### N1.3 Перевод плана в слова consolem

- **Охват** (ADR-0093 доп. (6) п. 4). Проверка плана в `backend` пропускает только правки, у которых есть место в
  `UnitPatch` записи (V/11.3 N1.1, таблица `mapping.tsv`; таблица ниже): правка иного поля или иной единицы — отказ проверки со
  словами «сделайте это вручную» и `field` — указателем свойства записи по `mapping.tsv` (`/properties/<p>`), если у поля строки оно есть, иначе без `field` (**Решено:** контракт: `field` у `refused` — JSON Pointer поля объекта, «нет — отказ не о поле»); правка единицы `auto` — отказ `not in scope` (N1.7). **Решено:** правка с местом, чьё `name` или свойство вне `Unit.writable` записи в том же чтении (V/11.3 N1.1: камера-кластер, чужая запись без связи), — тот же отказ проверки «сделайте это вручную» с `field` — указателем (`/name`, `/properties/<p>`), до «Применить»: запись получила бы 422 `NOT_SUPPORTED`. Частичного плана нет: одна такая правка — отказ всего плана.
- **Правки с местом** — по единицам записи (V/11.3 N1.2):

| Правка плана (`unit`, `field`) | Указатель в `UnitPatch` записи |
|---|---|
| `cam/<id>` (камера, пустой `main`): `name`, `enabled`, `cred_username` | камера: `/name`, `/properties/enabled`, `/properties/login` |
| `cam/<id>`: `source`, меняются только хост и порт | камера: `/properties/ip`, `/properties/port` |
| `rec/<cam>`: `enabled` | камера: `/properties/recordMode` — при `true` `always`, с непустым `replica_from` — `replica`; при `false` — `none` (V/11.3 N1.3) |
| `rec/<cam>`: `home`, `stream` | камера: `/properties/archiveId`, `/properties/stream` |
| `rec/<cam>-<volume>`: `enabled` | камера: `/properties/extraArchives`, элемент тома — `recordMode` `always` \| `replica` \| `none`; список целиком, из того же чтения (**Решено:** `UnitPatch` — JSON Merge Patch, массив заменяется целиком) |
| `det/<cam>-<kind>`, `det/<cam>-<kind>-<n>`: `enabled` | детектор (вид `det`): `/properties/enabled` |
| `det/<cam>-<kind>`, `det/<cam>-<kind>-<n>`: `params`, меняется только ключ `sensitivity` | детектор: `/properties/sensitivity` (кодек V/11.3 N1.3) |
| `cam/<id>`: `cred_secret`, `to` — метка `{"secret": N}` (V/11.12 N1.3) | камера: `/properties/password` = `secrets[N − 1]` запроса хода (`writeOnly` схемы вида, `way: write` `mapping.tsv`: ответы несут только `secrets.password`); метки без такого места в `secrets` — отказ проверки |

  Иное — отказ проверки (выше): секрет тома (`access_secret`), тома, записи с иными именами, потоки,
  поля без строки в таблице, `source` с иным путём, `params` с иными ключами.
- **План consolem** — `items` `AssistPlanItem` (`uid`, `version`, `patch`) и к каждой записи
  пояснение: `name` и `changes` — правки `AssistChange` `{field, before?, after, why}`, `field` — указатель таблицы выше, как `Problem.field` у `PATCH /units/{uid}` (контракт; V/11.14 N1.2); у секрета `before` нет, `after` — только номер: «новый (секрет № N)». Правки строки камеры и её записей сходятся в
  элемент камеры, правки детектора — в свой элемент (детектор — своя запись вида `det`); `patch` — `UnitPatch` только с правлеными `name` и `properties`; `version` —
  `Unit.version` записи (V/11.4 N1.1) по тому же чтению, по которому прошла проверка плана; `uid` — V/11.4 N1.6, V/11.14 N1.1.
  Порядок элементов — по `uid` байтами. Итог: `{summary, context, items}`.
- **«Применить»** — не операция хода: клиент пишет `items` как есть (контракт `AssistPlanItem`) — либо `PATCH /units/{uid}` с `If-Match: version` и телом `patch` на элемент
  (глава 2 № 95; V/11.4 N1.2, N1.3): запись изменилась после плана — 412 `VERSION_MISMATCH` её `PATCH`, в ней ничего не записано (пакет,
  ADR-0094 доп. (9)), прочие элементы записаны; либо один `POST /operations` с шагами `{uid, patch}`, `version` в `expectedVersions` и новым `idempotencyKey` (глава 2 № 5; V/11.4 N1.8): запись изменилась после плана — 412 всей операции, ничего не выполнено. Контракт называет оба пути; выбор — за клиентом.

### N1.4 События потока

| `type` сообщения `AssistEvent` | Когда | Поля |
|---|---|---|
| `progress` | шаг цикла начат: где модель, шаг модели, инструмент, проверка плана — сколько угодно раз | `{text}` — строка хода работы (V/11.9 N1.1 «строка состояния»: «модель загружается», «модель занята», «читаю `<sub>`», «проверяю план») |
| `question` | принят `ask_admin` | `{text, context}` |
| `plan` | план прошёл проверку и перевод | `{summary, context, items}` (N1.3); тип `export` — `{summary, context, export}` (`AssistExport`) |
| `refused` | принят `refuse`; правка вне охвата; «ход не завершён» (V/11.9 N1.5) | `{text, context, field?}` — слова причины |
| `answer` | принят `answer` типа `explain` (N1.7) | `{text, context}` — ничего не пишет |
| `found` | принят `found`, отбор посчитан (N1.8) | `{text, context, conditions, ids \| filter, total?, truncated?}` |
| `error` | отказ двери консоли, который ходом не исправить | `{code, message}` — `code` из `ProblemCode` (глава 2 N1.3) |

Таблица — нынешний закреплённый договор. После условия договора/поставки N1.10 учёба использует прежний конечный исход `answer` с согласованным логическим расширением `answer.learn`; этот текст не добавляет события или нынешнего поля провода.

- Поток кончается ровно одним из `question`, `plan`, `refused`, `answer`, `found`, `error`; затем `backend` закрывает поток.
- `action` у `found` (контракт 0.2.0: команда над отобранным) не отдаётся: у харнеса `found` нет аргумента для неё (N1.8).
- Каждое сообщение несёт `at` — момент, когда `backend` его произвёл, RFC 3339 UTC (глава 5 N1.2). Поток без завершающего сообщения форма считает обрывом: `UPSTREAM_UNAVAILABLE`.
- `id:` событий хода нет: ход не возобновляется по `Last-Event-ID` (оборванный — повтор запроса, N1.1).

### N1.5 Предел хода

- `ASSIST_TURN_MAX` = 7500 с — потолок запроса: `TURN_CALLS` (25) × предел вызова модели (`QUEUE_MAX` 120 с +
  `STEP_MAX` 180 с, V/10.2 N1.3) (ADR-0094 доп. (10) п. 2). Это предел ожидания маршрута `api/assist/turns` у консоли
  (число — здесь, потолок `PASS_WAIT_MAX` — норма платформы B1) и предел хода у `backend`: ход, не кончившийся за него от начала
  запроса, кончается `refused` «ход не завершён: дольше предела хода»; повторы `STEP_TRIES`, `RESTARTS` и ожидание
  `ENQUEUE_WAIT` идут внутри него.
- Предел: билет потока кончается с `exp` токена запроса (договор сторожевой и передачи, `close`), а `TOKEN_LIFETIME` = 900 с
  ([P/08.4 N1.3](../../../../Platform/08-domain/ru/spec/08.4-domain.norms.md)) меньше `ASSIST_TURN_MAX`. Запрос, не кончившийся к `exp`, — обрыв потока (N1.1): события-исхода нет,
  повтор идёт с прежнего `context`. Запрос дольше остатка токена не завершается, потолок при таком токене не достигается.

### N1.6 Тип реплики

ADR-0093 доп. (13), (15) п. 1; контракт форка b09cdf8, а также 0.2.0: у `AssistTurnRequest` поля `kind` нет, у `AssistEvent` тоже.

- Тип выбирает `backend` по каждой реплике, вызывающий его не называет: в одном разговоре бывают правка, правило, вопрос о системе и список. Выбранный тип наружу не отдаётся, форма его не показывает (ADR-0093 доп. (12), (13)).
- **Шесть внутренних типов:** `config` — главы 9–12; `rules` — V/11.13; `explain` — N1.7; `found` — отбор, N1.8; `export` — V/11.20; `learn` — N1.10, после его условия будущего договора. Это внутренний выбор, не новое поле HTTP или событие.
- **Учёба и живое объяснение.** Просьбы научить, со словами «как…», «покажи как…», «научи…», выбирают `learn`. Вопросы о живых объектах со словами «где…», «есть ли…», «какие…» выбирают `explain`, с правами человека как прежде. Правило учебных слов проверяется до построения рабочего обзора; новая учебная просьба классифицируется по этой просьбе, рабочая переписка в её учебный контекст не передаётся. Подходящая глава каталога может дополнить живой ответ проверенной ссылкой `answer.learn` после условия N1.10; урок не заменяет живой ответ. Выбор главы не даёт права на рабочий объект.
- **Ответ на вопрос** не классифицируется заново: `context` вопроса несёт тип полем `type` переписки (N1.2), ответ идёт тем же харнесом. Тип выводится у реплики без открытого вопроса: первой, после плана, отказа, ответа и списка.
- **Шаг `route`** — один шаг двери модели до цикла: `system` — байты [`harness/route/system.md`](../../harness/route/system.md), `tools` — [`harness/route/tools.json`](../../harness/route/tools.json), `tool_choice: required`, сообщение `user` — тексты хода через пустую строку. Для нынешней закреплённой поставки эти файлы роутера описывают прежние рабочие типы. Роутер с обучением ДОЛЖЕН выбирать также `learn` по границе выше; его prompt/tool inputs — следующая поставка, не новые фикстуры здесь. Вызов `route {kind}` выбирает один из шести внутренних типов (`learn` — после N1.10); `ask` — событие `question` с `question` вызова, `context` без типа: ответ выбирается заново. Нет вызова или иное значение — шаг повторяется один раз, затем `question` на языке реплики (решила: кириллица в текстах хода — русский, иначе английский): «Уточните, что нужно: изменить настройку, правило, вопрос о системе или список.», «Please say what you need: a settings change, a rule, a question about the system or a list.». Шаг `route` в `TURN_CALLS` не входит, его сбой — исходы V/11.9 N1.3, как у шага цикла.
- **Отказ типа:** `refuse` рабочего харнеса, в котором оно определено, несёт поле `other_kind`; `true` — просьба другого типа (правка у `explain`, вопрос у `config`, правило у `found`), правило ставить его — в каждом `system.md`. Только по нему `backend` один раз повторяет `route` с `reason` отказа в сообщении `user` и идёт выбранным типом, проверки отказа V/11.11 N1.5 у такого `refuse` нет: он не показывается; второй такой отказ или выбран тот же тип — `refused` с `reason`. `refuse` без `other_kind` — обычный исход «отказ».
- У закрытого учебного набора нет `refuse` и `other_kind`: нужное уточнение — `ask_admin`, подходящей главы нет — `no_chapter` (N1.10).
- Нынешний харнес `route` — опыта `plan-neutral` (`assist-pilot` `REPORT-neutral.md`, 9dc2afc), текст тега `bridge-public-24` пилота. **Цена:** шаг около 2 с на реплику. **Предел:** на спорных просьбах выбор ошибается примерно в трети (3,5 % набора, ошибка в них 33 %), человек этого не видит: план виден до «Применить», ответ `explain` подписан, отбор показывает условие словами; ошибочный выбор кончается планом, ответом или списком не того типа, записи без «Применить» нет. Замер на нормах V/11 не делался.

### N1.7 Ответ на вопрос о системе

ADR-0093 доп. (10) п. 1, (13), (16): тип `explain` — только чтение.

- Харнес — [`harness/explain/system.md`](../../harness/explain/system.md), [`harness/explain/tools.json`](../../harness/explain/tools.json): инструменты чтения V/11.10 (`list_subsystems`, `get_manifest`, `find_units`, `field_values`, `list_table`, их чтения, ошибки и слова), `rule_state {rule}`, `rule_fires {rule}`, `answer {text}`, `ask_admin`, `refuse`. Инструмента записи нет, проверки плана нет. **Охват** `explain` — `cam`, `rec`, `det`, `auto` (ADR-0093 доп. (16)): у `auto` строки `scenarios` (`find_units`) и таблицы `schedules`, `day_groups`, `modes`, `mode_current`, `windows`, `rule_marks` (`list_table`) — то, что нужно ответу «почему правило не сработает»; читаются дверями консоли по билету из перечня V/11.1 N1.5, право — `view`; `list_subsystems`, `get_manifest` отдают `auto` только этому типу. Охват `config` не меняется: правка плана со строкой `auto` — отказ проверки `<unit>: not in scope: a rule is changed by a rule request or in the console form` (N1.3, ADR-0093 доп. (18)).
- **Состояние правила** (ADR-0093 доп. (17)): `rule_state` — элемент `status[]` строки `GET /auto/scenarios/<id>`: фаза, `reason`, `unfit`, `unchecked`, `state.runs` (V/07.3, V/07.4 N1.11; пульс `GET auto/heartbeats` — слова `servers.status`); `rule_fires` — `GET /events?subsystem=auto&unit=auto/<id>&from=<now − 86400>&limit=50`, новые первыми, как `GET /rules/{id}/fires` V/11.4 N1.10. **Решила:** окно — сутки, `limit` 50, `late` — умолчание 3600: сработка пишется в бакет своего `t`, `t` близко к `occurred`; `truncated` журнала — словом в результате. Чужое правило — те же двери через `/domain/at/<member>/…`. Правило по имени: два с одним именем — ошибка `several rules are named <name>`, нет — `no rule <name>`. Строка `hidden: record` — запись камеры, правилом не называется.
- **Права:** билет, как прочее чтение. Нет права `view` на `auto` (`GET /session` человека: ни одного гранта `view`, область которого покрывает `auto`) — ошибка инструмента `no rights to read rules`, а не пустой список: «правила нет» сказать нельзя. **Предел:** с частью грантов правила вне них не видны, ответ — о видимых.
- Цикл — V/11.9 N1.2–N1.5: принятый `answer` кончает ход, остальные вызовы ответа — `not executed`. Событие — `answer {text, context}`: конечное, ничего не пишет; разговор продолжается новым запросом с этим `context`.
- **Необязательная учебная ссылка.** После условия договора N1.10 подходящая глава каталога может идти вместе с живым ответом `explain` как `answer.learn`. V/11 проверяет ID и версию каталога до предложения ссылки; интерфейс проверяет их ещё раз перед запуском. Неверная или недоступная ссылка ничего не запускает, предлагается ручной каталог, если он доступен. Живой ответ и чтения с отбором по правам прежние. Ссылка — не рабочий план.
- **Обзор полей** — с подписями и вариантами из манифеста: «запись выключена» — режим записи, не `enabled` камеры (`assist-pilot` `REPORT-rules.md`, X13; тег `bridge-public-19`).
- **Предел:** эталон замера проверял названные факты, а не весь ответ: 0 ложных успехов на 30 значит «нужные факты названы»; сработки старше суток `rule_fires` не видит.

### N1.8 Отбор

ADR-0093 доп. (14), (15); контракт 39ba6a3: `AssistEvent` `found`, `AssistFoundFilter`, фильтр `noDetector`; на 0.2.0 (ADR-0116 доп. (9)): `ids` — `Unit.uid`, `AssistFoundFilter` `kinds`, `implements`, `fields`, `status` списком, `noDetector` — `true` или вид детектора, виды детекторов камеры — `status.observed.detectorKinds`.

- Харнес — [`harness/found/system.md`](../../harness/found/system.md), [`harness/found/tools.json`](../../harness/found/tools.json): `device_values {field, type?}` — значения поля записей вида `type` в охвате со счётом; охват больше `LIST_MAX` — ошибка `<sub>: more than <LIST_MAX> units — too many to check here`, как у `field_values` V/11.10 N1.2, `found {text, type?, where}`, `ask_admin`, `refuse`. **`type`** — код вида `GET /kinds` (`UnitKind.kind`, глава 14 N1.1); нет — `camera`. Модель составляет условие `where` словами контракта: поля записи `Unit`, операторы и пустой список — как условия `find_units` V/11.10 N1.5, но над полями записи (V/11.3), не строк. **Решено:** поле условия — путь `Unit` по `mapping.tsv`, свойство — без `properties.`, как его называет `fields` у `GET /units`: `name`, `folders`, свойства схемы вида (`recordMode`, `archiveId`, …), `status.link`, `status.observed.<name>`. Поля, которого у вида нет, — ошибка инструмента `<field>: <type> has no such field`, ход идёт. **Обзор полей** — поля вида с подписями и вариантами схемы вида (`x-label`, `x-enum-labels`, `kinds.json`), «запись выключена» — `recordMode` `none`, не `enabled` `false` (X13, `REPORT-rules.md`; вопроса на эти слова нет, ADR-0093 доп. (15) п. 5).
- **Исполняет `backend`, не модель:** `ids` — `Unit.uid` совпавших записей, считает код по полям записи, выведенным по V/11.3, иначе они выдуманы. Найдено 0 — тоже `found`.
- **Две формы, ровно одна.** Охват — строки, которые надо прочесть, чтобы вывести поля условия: по строкам вида, у камер домена — страницы вида (V/11.3 N1.2a, ADR-0113 доп. (8)).
  - Охват не больше `LIST_MAX` = 5000 строк на подсистему (V/11.10 N1.2): `backend` проходит его целиком и отдаёт `ids` по имени, без повторов (контракт), `total` — всех совпавших. Совпавших больше 500 (`selectMax`) и все условия — поля `AssistFoundFilter` — форма `filter` ниже; не выражается им — первые 500 `ids` и `truncated: true`.
  - Охват больше `LIST_MAX`: все условия — поля `AssistFoundFilter`: `q`, `fields`, `kinds`, `implements`, `status`, `domainId`, `noFolder`, `noRecord`, `noDetector` — `filter`, `type` идёт как `kinds: [<type>]`: форма листает его тем же ограниченным проходом, что обычный фильтр (V/11.3 N1.2b «Фильтры `GET /units` по цене»), `total` нет, `truncated: true`: полного прохода не было. `serverId`, `archiveId`, `folderId`, `parentId`, `ref` у `GET /units` в `AssistFoundFilter` нет: условие на них идёт формой `ids` или отказом. Не выражается — `refused` «больше 5000 устройств: такое условие здесь не проверить, сузьте отбор папкой, сервером или типом» (ADR-0093 доп. (15) п. 4).
- Событие — `found {text, context, conditions, ids | filter, total?, truncated?}`: `text` — слова модели, `conditions` — по строке на условие `where`, переводит `backend`, не модель (**решила**): «<подпись поля>: <вариант>» по подписям и вариантам обзора полей, оператор словом: `eq` — «:», `ne` — «: не», `in` — «: одно из», `not_in` — «: ни одно из», `contains` — «: есть», `not_contains` — «: нет», `exists` — «задано», `missing` — «не задано»; форма показывает их над деревом.
- **Детекторы.** Поле камеры `status.observed.detectorKinds` (V/11.3, `mapping.tsv`): виды всех её детекторов, выключенных тоже — строки `det/units` с её `cam` и встроенные по `detector-kinds.tsv`, вне таблицы `other`; фильтр `noDetector: <kind>` — тот же вывод, `noDetector: true` — ни одного детектора. «Камера без детектора движения» — без строки вида вообще. **Предел:** выключенный детектор считается настроенным.
- **Цена:** чтение охвата, до 5000 строк на подсистему, на каждую реплику отбора; условие вне фильтров — чтение записи на камеру. **Предел:** надёжно одно-два условия на полях самой камеры (ADR-0093 доп. (14) п. 2); замер отбора на нормах V/11 не делался.

### N1.9 Тип `export`

ADR-0093 доп. (47) п. 6; контракт 754a52e: `AssistExport`, `AssistEvent.export`; на 0.2.0 — камера по `uid` (`ExportCamera.uid`, ADR-0116 доп. (9)). Содержание — пакет пилота `handover/export` (`assist-pilot`, ветка `export`, 0f40447; модель Gemma 4 26B-A4B IQ4 на CT 103, `tool_choice: required`). Тип заказывает выгрузку по V/11.20 и ничего не пишет (N1.2): исход — тело `AssistExport`, которое человек проверяет и отправляет в окне выгрузки.

- **Выключатель и объявление.** `ASSIST_EXPORT` (V/09.2): `on` — тип достижим; `off` — ход типа `export` (по словам выбора или по `route`) кончается без шага модели событием `refused` «Выгрузку ассистент здесь пока не готовит: закажите её в окне выгрузки.». Нет `Reference.export` (система не объявила `createExport`, V/11.20 N1.8; контракт: «есть, если система объявила createExport») — `refused` без шага модели «В этой системе выгрузки нет: справочник не объявляет её (reference.export).».
- **Мир** — то, что `backend` отдаёт человеку на чтениях контракта, по билету потока (V/11.3): `GET /me` — `serverTime`, `timezone`; `GET /reference` — `export`; камеры — записи `GET /units?implements=vms.camera/1`: `uid`, `name`, `properties.ip`, `properties.archiveId`, `status.link`, `folders`; имена папок — записи вида `folder` (`GET /units?kind=folder`). «Сейчас» — `serverTime`, часы сервера; **решила:** читается один раз в начале запроса.
- **Системное сообщение** — байты [`harness/export/system.md`](../../harness/export/system.md) с подстановками таблицы и после текста блок камер; сообщение `user` — просьба как есть (тексты хода, N1.2).

| Место | Из мира |
|---|---|
| `{now}`, `{weekday}`, `{tz}` | `serverTime` в поясе `timezone` (IANA): «YYYY-MM-DD HH:MM», день недели по-английски, имя пояса |
| `{max_periods}`, `{max_total_h}`, `{max_cameras}`, `{file_max}` | `Reference.export.limits`: `maxPeriods`, `maxTotalSec` / 3600 до 0,1, `maxCameras`, `maxFileMbMax` |
| `{formats}` | `formats`: `<id> (<kind>[, live too])` через «; »; «live too» — `entries` содержит `live` |
| `{compression}` | `compression[].id` через «, », затем «; none — original» |
| `{resolutions}`, `{fps}`, `{titles}` | `resolutions[].id`, `fpsDivisors`, `titleFields` через «, » |
| `{single}` | `id` тех `formats[]`, где `singleFile: tracks`; таких нет — `none` |

- **Блок камер.** Камер не больше 300 — строка `## Cameras (id (marks)); folders — find_cameras` и строка на камеру `<name>[ (no archive[, offline])]`; имя повторяется среди камер — `<name> [<ip or 8 id characters>]`: `properties.ip` камеры, без него — первые 8 знаков `Unit.uid`. Отметки: `no archive` — у камеры нет `properties.archiveId`; `offline` — `status.link` `offline`. Камер больше 300 — строка `## Cameras` и строка `<N> cameras: find them with find_cameras.` Строка камеры начинается её ключом: модель называет камеру им, код переводит ключ в `Unit.uid`. Блок и решает исход: без него (общий `find_units`) замер дал 18 из 35 и 6 сбоев, с ним — 34 из 35 (замер ниже).
- **Инструменты** — [`harness/export/tools.json`](../../harness/export/tools.json):
  - `find_cameras {text}` — чтение. Слова `text` в нижнем регистре (`ё` → `е`), без `камера`, `камеры`, `камер`, `камеру`, `камерой`, `camera`, `cameras`, `the`, `с`, `со`, `из`; слово совпало, если одно из слов имени начинается с него или оно начинается с этого слова; слова длиннее 4 букв сравниваются без двух последних букв («главного» ≈ «главный»); совпасть должно каждое слово. Имя и папка раздельно: результат — `{by_name, folders, in_folder, in_folder_count}` — `by_name` камеры, чьё имя содержит все слова, `folders` папки, чьё имя их содержит (не больше 10), `in_folder` все камеры этих папок; строки как в блоке, каждый список не длиннее 50. «Касса» — не камеры папки «Кассовые зоны», «папка Цех» — не камера «Цех — проход»; просьба о папке берёт все камеры `in_folder` (hold1 H22). Пустой `text` — все камеры.
  - **Точное имя** (H19, R04; решила). Имя, равное всему имени камеры, — эта камера, даже если с него начинаются другие имена: «Рампа» при «Рампа 1», «Рампа 2» в мире — камера «Рампа»: заказ, камера названа в `text`, человек видит её в окне до «Экспорт»; `ask_admin` — только если камеры ровно с таким именем нет, а начинаются с него несколько. Правило — строка [`harness/export/system.md`](../../harness/export/system.md).
  - `export`, `ask_admin {question}`, `refuse {reason}` кончают ход. Текст без вызова — сообщение `user` «Answer only with a tool call.» и следующий вызов (V/11.9 N1.4).
  - Харнес отказывает в том, чего система не умеет: маски, облако, плеер или `exe`, ускорение, предел fps, кодек, шрифты и цвета титров, треки детекторов, отправка почтой или в мессенджер, расписание выгрузок; «когда случится X, выгрузи …» — правило, не этот тип.
- **`export` → `AssistExport`.** Модель называет суть, тело собирает код:

| Аргумент | Поле тела |
|---|---|
| `mode` | `mode` |
| `source` (нет — `archive`) | `source` |
| `format` (нет — `mp4` у `video`, `jpg` у `frame`) | `format` |
| `cameras[].camera` — ключ блока | `cameras[].uid` — `Unit.uid` |
| `cameras[].area` `{x, y, w, h}` | `cameras[].area` |
| `periods[].from`, `.to` — местное «YYYY-MM-DD HH:MM[:SS]» (или ISO с поясом) | `periods[]` — UTC `…Z` |
| `at` — так же | `at` |
| `compression` (не `original`), `resolution` (не `source`), `fpsDivisor` (не 1) | `quality.compression`, `.resolution`, `.fpsDivisor` |
| `titles[]` | `titles.fields`, без повторов |

| `comment` (до 500 знаков) | `comment` |

  Код никогда не ставит `name`, `bookmarkId`, `privacy`, `highlight`, `destination`, `cameras[].archiveId`, `quality.codec`, `quality.maxFps`, `quality.speed`, `special.player` и поля `titles`, кроме `fields`; `password`, `supervisor`, `idempotencyKey` в `AssistExport` нет (контракт: «их вводит человек в окне выгрузки»). Просьба с паролем — заказ без него, и `text` говорит «пароль — в окне выгрузки».
- **Проверки** вызова `export` — пп. 1–5 V/11.20 N1.2 по миру, в этом порядке; отказ — ошибка инструмента со словом проверки модели, ход идёт: модель правит вызов, спрашивает или отказывает.
  1. `mode` — `video` или `frame`; `source` — `archive` или `live`.
  2. `format` есть в `formats`, и его `kind` — `mode`; `source: live` — только `mode: frame` и формат, у которого `entries` содержит `live`.
  3. ### N1.10 Учебная ветвь только по каталогу и условие договора

ADR-VMS-0004 через доп. (1), (2). Раздел задаёт следующий договор с обучением. Нынешняя закреплённая cb728a4 схема `AssistEvent` закрыта и не имеет `answer.learn`; API, оболочка, манифест и поставка `--without-learn` прежние. «Консоль» должна подготовить согласованную правку договора форка, затем нужен разрешённый перепин и условия учебной поставки V/11.1 N1.4a, прежде чем такую ссылку можно выдавать или обещать. Этот текст не добавляет полей провода, события, флага запроса или опции демона; подробную форму ссылки задаёт согласование договора.

- **Вход и инструменты.** Учёба начинается с нынешней учебной просьбы и её собственных уточнений, не с переписки рабочего разговора. Ей не передаются обзор камер/кластера, снимок рабочих объектов, рабочий черновик, секрет или рабочая история. Своя системная подсказка ставит каталог первым ради повторного использования префикса. Закрытый набор — ровно `open_chapter {chapter: enum catalogue ID}`, `no_chapter`, `ask_admin`, с `tool_choice: required` (V/11.9 N1.7; V/11.10 N1.7). Модель выбирает только enum ID главы, не URL, HTML, JavaScript, селектор или последовательность действий интерфейса. Рабочих чтений, инструментов рабочего плана и применения нет. Проверки рабочих планов V/11.11–11.13 прежние; учебная ссылка вместо плана не проходит.
- **Один каталог.** У каталога один источник с поставляемыми турами: устойчивые ID тем и глав, версия или отпечаток, язык, название, цель, учебный набор и доступность в сборке. Тексты во второй редактируемый каталог не копируются. Недостающие ID, версия или тур не выдумываются. Логическая типизированная ссылка называет эту версию каталога, тему и главу; интерфейс строит адрес по своему поставленному каталогу. Точные имена полей и форму объекта задаст согласование договора, здесь они не выводятся.
- **Проверки и исходы.** V/11 проверяет возвращённый ID главы по нынешнему каталогу и его версии, даже если грамматический фильтр модели кажется достаточным: фильтр — свойство реализации. Только правильная доступная глава предлагается как `answer.learn` после условия. Интерфейс вновь проверяет ID/версию/доступность в сборке перед запуском. Неизвестный ID или чужая версия ничего не запускают, предлагается ручной каталог. `no_chapter` не предлагает выдуманного урока; `ask_admin` использует прежнее продолжение вопроса/ответа с контекстом только учёбы. Нового события SSE `learn` нет: будущая ссылка сопровождает прежний исход `answer`, не `plan` и не автоматический запуск.
- **Обход и честность.** Если модель недоступна, человек пользуется ручным каталогом и обычным поиском при наличии учебной поставки. Если обучения нет, интерфейс не обещает урок. Нынешние туры русские; английский интерфейс честно называет язык. Главы об ассистенте используют явно подписанные подготовленные ответы или заглушки: успех урока не замер живой модели и не доказательство проверки рабочего плана. Порог качества или задержки из замеров Пилота не выводится.
- **Показ по решению человека.** Показ запускает человек кнопкой в той же вкладке, не событие SSE. Предупреждение, постоянная полоса «Учебные данные», обычный вход при возврате, исключение параметров и отказ при нарушении изоляции — V/11.1 N1.4a и V/11.12 N1.5. Учебная ссылка никогда не применяет рабочую правку.

```

  открытый вопрос → тип из context; иначе шаг route (N1.6): config | rules | explain | found | export | learn (условие N1.10) | ask → question

    ask_admin → question; refuse → refused; answer → answer (explain)
    found → отбор кодом (N1.8): ≤ LIST_MAX — ids | filter, > LIST_MAX — filter | refused
```
