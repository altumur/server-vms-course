# V/07.2 — Вычислитель — вопрос к журналу: нормы

Канон главы 2 урока V/07 «Сценарии» (ADR-0080; модуль VMS — ADR-0090). [Лекция](../07-auto.md),
[инструкция](07-auto.README.md), манифест [`auto.subsystem.yaml`](../auto.subsystem.yaml). Платформа — выгрузка
`cammeta-specs` `d3f8e05` (пин VMS; глава переведена на договор слияния журнала — `cf4a3ce`).

Вычислитель не держит автомат состояний в памяти: каждый проход он спрашивает журнал событий кластера, что случилось после
курсора, и решает сработку по завершающему событию. Глава нормирует, что вычислитель смотрит, как читает журнал, когда
сценарий срабатывает, курсор и долгий опрос. Соответствие сценария камерам — глава 3; что делается при сработке — глава 4.

Id норм — `V/07.2-MM`; соответствие прежним урокам — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Правила модуля «Платформа» — [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-словарь-слов).

## Н1 Форма

**Время.** `t` строки — когда записана; `occurred` — когда произошло (если писатель сказал; иначе `t`); курсор — по `t`.

**Данные** (общие семьи [каталога платформы](../../../Platform/common/data/catalog.tsv)): читает — журнал событий кластера (Н1.2),
строки ресурсов `platform/doors/*`, строки эпох `<sub>/epoch/*` подсистем VMS (`worker.reads`); пишет — курсор `auto/state/cursor/<scenario>` ([P/03.6 Н1.7](../../../Platform/03-worker/spec/03.6-worker.norms.md)),
эпоху (при взятии единицы, P/03.3). Файл подсистемы `/etc/auto/auto.env` читает вычислитель по договору файла окружения
(нет файла — умолчания; не читается или значение не по грамматике — отказ старта, код 2; сводка — V/09.2):

| Ключ | Читает | Грамматика | Умолчание | Норма |
|---|---|---|---|---|
| `LONG_POLL` | вычислитель | `0` \| `1` | `1` | Н1.2: `0` — без долгого опроса |

### Н1.1 Что смотреть

**Желания** вычислителя — тройки `(sub, kind, unit)` из триггеров его включённых сценариев; триггер без `unit` — любая
единица. Выключенный сценарий ничего не смотрит. `unit` триггера — id единицы подсистемы `sub` (число — своей десятичной
записью); в вопрос к журналу и в сравнение он идёт ссылкой `<sub>/<unit>` (голый id ресурс отвергает, договор
`events-merge` «Запрос и ответ ресурса»).

### Н1.2 Чтение журнала

Вычислитель — участник [договора слияния журнала](../../../Platform/common/contracts/events-merge.md) (владелец P/06.4): сливает
сам `GET /events` живых ресурсов (строки дверей `platform/doors/*`, свежесть `LOST_AFTER`; P/05 Н1.3, допуск `autoworker`) по тем
же правилам, что консоль, — дубли по `id`, порядок `cut`, `truncated`, `incomplete` и `complete`; дверь консоли ему не
открывается. Эпохи — строки `<sub>/epoch/*` подсистем, объявленных в `worker.reads`: `cam`, `rec`, `live`, `det`, `detjob`,
`detedge` (события VMS); строку прежней эпохи вычислитель помечает `epoch_is` по политике `older_epochs` её манифеста (`fenced` |
`earlier-run`); подсистема, чьих эпох он не объявил, — `epoch_is: unknown`, не доказательство (сработки не даёт, Н1.3), `complete` не
меняется; эпохи всех подсистем VMS объявлены, `unknown` — только у чужой: сценарию нужны её события — её эпоха в `worker.reads`;
нужная эпоха не прочитана — `incomplete[<sub>/epoch]`, окно неполно (Н1.4). Строку, которую он считает отсечённой, он сверяет
со свежим чтением эпохи (договор, `epochs_age`). Вопрос — на каждую тройку желаний и каждый класс (`class=alarm`, `class=observation`: внутри класса порядок `cut` — по `t`)
отдельно, окно `[through, max(through, now − JOURNAL_SETTLE))` по `t` (`JOURNAL_SETTLE` = 5 с: до «сейчас» курсор не доходит — поздние строки
ещё дописываются), `keep: oldest`: растущее окно читается с начала, обрезка не теряет ранних строк.

**Полнота.** Окно полное, когда у каждого вопроса прохода `complete` и `truncated` = 0 (`complete` платформы не
переопределяется, договор `events-merge` «Ответ»). Ответ обрезан (`truncated` > 0) — окно этого прохода кончается на `t`
последней выданной строки, не включая это `t`, — по наименьшему из обрезанных вопросов (Н1.4); все выданные строки на одном
`t` — курсор стоит. Одно правило — здесь, в Н1.4 и Н4.

**Партнёры** — отдельный вопрос на тройку каждого **другого** триггера сценария, `by=occurred`, окно
`[occurred(e) − within, occurred(e)]` по кандидатам `e` прохода (параметр `by` договора `events-merge`, «Запрос и ответ
ресурса»); его полнота — по тому же правилу, неполный — курсор стоит. Строка, дописанная позже `JOURNAL_SETTLE` с `t` < `through`,
завершающей уже не становится (окно по `t` её прошло), а партнёром — да: вопрос партнёров идёт по `occurred`.


### Н1.3 Сработка

Сценарий срабатывает на **завершающем** событии `e` (по порядку `t`), если:

1. `e` совпало с одним из триггеров: поле строки `subsystem` = `sub`, `kind` = `kind`, ссылка `<sub>/<unit>` триггера — `unit`
   строки или её `of` (как фильтр `unit` ресурса, P/05 Н3 «запрос (ресурс)» шаг 4: триггер `det` с `unit: "7-linecross"` и
   строка с `of: cam/7` не совпадают — `of` чужой подсистемы), каждое поле `match` равно полю строки строго (`"1"` ≠ `1`;
   форму поля задаёт урок писателя события — `io.input` у `cam`, V/01.2 Н1.5; V/07 только сравнивает);
2. для каждого **другого** триггера в окне `[occurred(e) − within, occurred(e)]` есть совпавшее событие-партнёр, годное по п. 3;
3. `e` — не сводка подавления (строка с `repeats` не срабатывает никогда) и доказательство по эпохе: `epoch_is: current` или
   `earlier-run` (прежний запуск — не ограждение) — да; `fenced`, `unknown` (эпоха не проверена — событие могло быть отсечённым) и
   строка без `epoch_is` (эпоха не прочитана) — нет (договор `events-merge` «Эпохи»; ADR-0091 доп. (23)–(27)).

У сценария с одним триггером окна нет (`within` = 0; иначе — отказ, глава 3). **Сработка** — `<сценарий>-<id события e>`;
одно событие — одна сработка, сколько бы раз её ни вычисляли.

### Н1.4 Курсор

`unit.state.cursor` — `{through, held_from?}`: докуда по `t` журнал прочитан (секунды) и с какого прохода окно неполно.

- **Сначала подать, потом сдвинуть** (глава 4): сработки окна поданы — курсор идёт на конец окна; пишется не чаще
  `STATE_EVERY` = 10 с (P/03.6 Н1.7). После переезда новый держатель начинает с курсора — повтор той же сработки даёт те
  же имена действий (глава 4), он безвреден.
- **Только за полное окно:** окно неполно (`complete: false`: ресурс не ответил, `silent`, `said`, или эпоха не прочитана;
  неполный вопрос партнёров) — курсор стоит, фаза сценария `running` с полем `holding` (секунд с `held_from`); ответ обрезан —
  курсор идёт до `t` последней выданной строки, не включая его (Н1.2 «Полнота»), все строки на одном `t` — стоит.
- **`COLD_START`** = 300 с — потолок отставания: окно неполно дольше 300 с от `held_from` — вычислитель решает по тому, что
  есть, и двигает курсор; поле `decided_without` (ключи `incomplete`: какие ресурсы и эпохи молчали; обрезка на одном `t` —
  ключ `truncated:<sub>/<kind>[/<unit>]`, у `incomplete` такого нет) — один раз за перерыв.
- Первое взятие: курсора нет — `through = now − JOURNAL_SETTLE` (сценарий не срабатывает на прошлом).

### Н1.5 Долгий опрос

При `LONG_POLL` ≠ 0 вычислитель держит `GET /events/wait` на каждом живом ресурсе ([P/05 Н1.6](../../../Platform/05-resource/spec/05-resource.norms.md))
с `want` = `<sub>/<kind>[/<unit>]` по желаниям (Н1.1): ответ `changed` — ранний проход только по тронутым сценариям (`touched`);
сменились сценарии или ресурсы — новый запрос, до него — не дольше 30 с; ошибка ожидания — пауза около 2 с (± 50 %), проход не
будится. Периодический проход рантайма остаётся (P/03.3). Пульс — `waits`, `woken`, `early_passes`, `wait_errors` (глава 4).

## Н3 Проход

```
желания — из включённых сценариев; долгий опрос по желаниям (ранний проход по touched)
для сценария: окно [through, now − 5) → вопрос на тройку и класс, keep oldest → события
  кандидаты e → вопрос партнёров by=occurred [occurred(e) − within, occurred(e)]
  сработки: завершающее событие + партнёры; только current и earlier-run, без сводок → глава 3 (годен?) → глава 4
  окно полное → курсор = конец окна (после подачи); обрезано → курсор до t последней строки (не включая)
  неполное → holding; > 300 с → decided_without, сдвиг
```

**Гонки.** Подмена вычислителя: прежний ещё подаёт до потери аренды (`unconfirmed_max: off` — не подаёт после), новый
читает курсор и вычисляет те же сработки — имена действий те же (глава 4), повтор безвреден. Событие дописано на ресурс
позже своего `t` (поздняя строка) — `JOURNAL_SETTLE` 5 с покрывает обычную задержку; что позже и с `t` < `through` — завершающим
не становится (следующее окно начинается с `through`), а партнёром — да (вопрос партнёров — по `occurred`, Н1.2).

## Н4 Отказы

| Причина | Исход | Кто и как видит | Что делает вызывающий |
|---|---|---|---|
| ресурс молчит | окно неполно, `holding`; через 300 с — `decided_without` | пульс | — |
| ответ обрезан (`truncated`) | курсор — до `t` последней выданной строки (не включая); все строки на одном `t` — стоит, через 300 с — `decided_without` `truncated:<sub>/<kind>[/<unit>]` | пульс | — |
| вопрос партнёров неполон | курсор стоит, `holding` | пульс | — |
| ожидание сорвалось | пауза 2 с, `wait_errors` | пульс, ряд | — |

## Н5 Приёмка

Сработка на стенде (событие учебного детектора → `fired`) — глава 4; функция слияния — векторы
[`events-merge`](../../../Platform/common/vectors/events-merge/README.md) (участник-воркер: объявленная, необъявленная и не
прочитанная эпоха); решение сработки — чтением и тестом реализации (`fires` над событиями; случаи: партнёр A до курсора и завершающее B после;
переезд между ними; поздняя строка партнёра; `unit` триггера `"12"` и `12` против строки единицы `12`; `of` чужой
подсистемы).
