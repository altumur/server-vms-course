# V/07.1 — The scenario — the unit and the language: norms

This English text is the source; the Russian translation `ru/spec/07.1-auto.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 1 of lesson V/07 «Сценарии» (ADR-0080; the VMS module — ADR-0090). Lecture (`ru/07-auto.md`, for people, not in the export),
[instructions](07-auto.README.md), manifest [`auto.subsystem.yaml`](../auto.subsystem.yaml). The platform is the export
`cammeta-specs` `7a875c75`.

A scenario is «when this happened (and that, within a window), under such conditions, do this». The chapter sets norms for the
scenario row, its language — triggers, conditions and steps of a fixed form, rights, placement and the snapshot. What the evaluator does with a
scenario — chapters 2–4; scenarios across cameras of different members — chapter 5; schedules, modes and windows — chapter 6.

Norm ids are `V/07.1-MM`; the correspondence to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-vocabulary).

## Н1 Form

**Time.** `within`, `valid_for` are seconds; `created_at`, `changed_at` are time by the canon P/01.1 Н0.

**Data** (the shared families of the [platform catalogue](../../../Platform/common/data/catalog.tsv)): the row `auto/scenarios/<id>`, the counter `auto/next_id` (P/06.1),
the snapshot `auto/snapshot/*`; the chapter has no families of its own beyond them.

### Н1.1 Fields

`unit: {rows: scenarios, id: numeric}`, the counter `auto/next_id` (P/06.1 Н1.3). The number is permanent: the name is editable, it may be Cyrillic and
contain spaces, so the log, requests and the firing name speak by the number (`auto/<id>`). The scenario is a unit, the evaluator is its
holder: «exactly one evaluator per scenario» is given by the epoch with the lease (P/03.2), not by the care of the code.

| Field | Form | Meaning | Writes | Reads | No field |
|---|---|---|---|---|---|
| `name` | `string`, required | the operator's name, any characters: `Дверь по пропуску` | operator | page, snapshot | — |
| `start` | `event`, `schedule`, `manual`, default `event` | how it is started (chapter 2) | operator | evaluator | default |
| `run_at` | `json`: `{days, time}` or `null`; `days` — 1…7 from Monday, `time` — `ЧЧ:ММ` up to `24:59`: `24:MM` is a minute of the next day (chapter 2 Н1.6) | the run moment of `schedule` (chapter 2 Н1.6) | operator | evaluator | `start: schedule` is not started: a refusal of chapter 3 |
| `run_mode` | `always`, `manual`, default `always` | `manual` — only by a manual run | operator | evaluator | default |
| `operator_menu` | `bool`, default `false` | data: a button of the operator client; there is no client in VMS | operator | `backend` | default |
| `repeat` | `skip`, `restart`, `queue`, default `skip` | a new run while one is running (chapter 4) | operator | evaluator | default |
| `when` | `json`, default `[]`, schema Н1.2 | 0–4 triggers | operator | evaluator | empty |
| `within` | `int`, 0…3600, default `0` | the window between triggers, seconds | operator | evaluator | default |
| `conditions` | `json`, default `[]`, schema Н1.2а | what must hold at the moment of the run | operator | evaluator | there are no conditions |
| `then` | `json`, default `[]`, schema Н1.3 | 0–4 top-level steps | operator | evaluator | empty |
| `rate_per_minute` | `int`, `0` or 1…600, default `6` (the row stores `0`, the evaluator reads it as the default) | the ceiling of the scenario's firings per minute (chapter 4) | operator | evaluator | default |
| `valid_for` | `int`, `0` or 10…600, default `30` (the row stores `0`, the evaluator reads it as the default; the lower bound is `JOURNAL_SETTLE` 5 s plus the road: a row may land that much later than its `t`) | how long a filed action stays valid from the moment of the event (chapter 4) | operator | evaluator | default |
| `enabled` | `bool`, default `true` | | operator | evaluator | default |
| `labels` | `list` | the labels of the evaluator's server | operator | controller | there are no labels |
| `log_only`, `log_only_since` | `bool`, default `false`; a date `ГГГГ-ММ-ДД` or `null` | it runs, files no actions, the log says what it would have done (chapter 4) | operator | evaluator | default; the date is data |
| `owner`, `purpose`, `server` | `string` | page data; the run does not depend on them | operator | `backend` | empty |
| `run_as_role` | `string`, empty — on behalf of the system | the action is judged by the right of this role (chapter 4) | operator | evaluator | empty |
| `allow_chain` | `bool`, default `true` | whether this scenario may be started from another one (chapter 4) | operator | evaluator | default |
| `created_at`, `created_by`, `changed_at`, `changed_by` | `float`, `string` | who and when, data | `backend` | `backend` | empty |
| `hidden` | `""` or `record`, default `""` | a row that `backend` keeps for the camera's `recordMode`; the rule list does not show it | `backend` | `backend` | default |

A field that has not passed the schema of its type does not lie in the row: the door refused. A row written past the door and unreadable — chapter 3
Н1.3. A write through the door accepts empty `when` and `then` for any scenario: the door does not compare fields; an enabled scenario that
has nothing to start by or nothing to do is a refusal of the evaluator (chapter 3 Н1.1).

### Н1.2 Trigger

`when` is an array of up to 4 objects `{sub, kind, unit?, target?, match?}`, with no extra keys; `unit` and `target` together are a refusal: `sub` is the subsystem of the event, `kind` the kind of
the event, `unit` the unit (a non-empty string without `/` or an integer ≥ 0; absent — any; the id of a unit of the subsystem `sub`, a number — by its decimal notation, the comparison — by
the reference `<sub>/<unit>`, chapter 2 Н1.3), `match` an object «event field → value», the comparison is strict (`"1"` ≠ `1`), structural
JSON, as in suppression (P/03.6 Н1.2); the field is not in the row — no match: the form
of an event field is set by the lesson of its writer (`io.input` — `port` a JSON integer from 1, `value` — `open` or `closed`, not the device's word: `closed` is the start of the alarm, `open` its end, V/01.2 Н1.5), the scenario
writes `match` with the same type (`"port": 1`). A fixed language, not expressions: the form is checked at the door for any writer (P/06.1 Н1.2, the schema of the field
`json`), the meaning — by the evaluator (chapter 3).

**The target** `target` — several devices or an area, for a trigger and for a step, the form is one:

```yaml
target:                  # null — not chosen: a disabled scenario stores it unfinished
  include: [{kind: device | child | folder | server | domain, id: <non-empty string>}]
  exclude: [<device id>]     # excluded from the areas of include
  gone:    [<name>]               # removed devices and areas, as the author saw them; at a step — `fail`, `target.gone` (chapter 4 Н1.9), the write of an enabled one is judged by `backend` (V/11.4 Н1.10)
  from_event: <bool>             # the device from the event that started the scenario; only at a step and a condition, at a trigger and at the event of `wait_event` — a refusal of chapter 3
```

`device` is the decimal id of a row `cam/cameras` or the key of a row `cam/children` (V/01.1 Н1.2а), `folder` the id of a folder (P/06.8), `server` the name
of a server, `domain` the whole cluster. An area is expanded by the evaluator at the moment of the step (chapter 4 Н1.9): the door and `backend` do not
expand it, a new device enters by itself.

### Н1.2а Condition

`conditions` is an array of objects `{kind, schedule?, modes?, target?, value?}`, with no extra keys; the schema requires only `kind`;
an unfinished condition of an enabled scenario and a field not of its `kind` are a refusal of chapter 3. `value` — only at `armed`.

| `kind` | Fields | True |
|---|---|---|
| `time` | `schedule` — a row of `schedules` | `in_effect` (chapter 6 Н1.3) |
| `mode` | `modes` — ids of modes | `object_mode` is in `modes` (chapter 6 Н1.5) |
| `armed` | `target`, `value`, absent — `true` | the word `armed` of each target equals `value` (chapter 4 Н1.8) |
| `recording` | `target` | the recording of each target is running (chapter 4 Н1.8) |
| `online` | `target` | each target is online (chapter 4 Н1.8) |

The moment and the limit of the current state — chapter 4 Н1.8.

### Н1.3 Action

`then` is an array of up to 4 steps; a step is an action or a flow step. There are no extra keys, except at a step without a subject (below). The form of an action with
`unit`, `cam` is full: the required keys of the table. The form with `target` instead of them is allowed unfinished: `target` may be
`null`, the other keys are optional, completeness is judged by chapter 3. `unit` or `cam` together with `target` is a refusal.

| `sub`, `action` | Required | Optional | Executes |
|---|---|---|---|
| `cam`, `output` | `unit`, `port` | `state`, `pulse_ms` | the camera holder — a request (V/01.4) |
| `cam`, `preset` | `unit`, `n` | — | the camera holder — a request (V/01.4) |
| `rec`, `record` | `cam`, `minutes` | `archive` (the volume); `duration`, `after_sec` — data: `duration: event` is a refusal of chapter 3 | an order of a recording for a time (chapter 4; V/02.1) |
| `det`, `detect` | `cam`, `kind`, `minutes` | `params` (a string, as the owner's — V/04.1) | an order of a detector for a time (chapter 4; V/04.1) |
| `det`, `scan` | `cam`, `kind` | `before`, `after`, `rec`, `params` (a string — V/05.1) | an order of a job over an interval (chapter 4; V/05.1) |
| `cam`, `unit` | `unit`, `n`, `operation` | — | the camera holder — a request, the form of V/01.4, the unit `<unit>-<n>`; the right — `reach.requests`, the whole group |
| `cam`, `arm`, `disarm` | `unit` | — | the camera holder (V/01.4) |
| `cam`, `disable` | `unit`, `minutes` (an integer 1…1440) | — | the camera holder — a request (V/01.4) |
| `auto`, `alarm` | `target` | `text`, `priority` (`normal`, `high`) | a log row of the class `alarm` (chapter 4) |
| `auto`, `runrule` | — | `rule` — the number of a scenario; an enabled one needs it (chapter 3) | the run of another scenario (chapter 4) |

A flow step is `control` instead of `sub`, `action`; it waits on the run row (chapter 4):

| `control` | Required | Meaning |
|---|---|---|
| `wait` | `sec` | wait `sec` seconds |
| `wait_event` | `event` (the trigger form), `sec`, `yes`, `no` | wait for an event: it came — `yes`, it did not — `no` |
| `ask` | `text`, `role`, `sec`, `default`, `yes`, `no` | ask an operator of the role; no answer within `sec` — as `default` |
| `escalate` | `levels: [{role, via, wait_min}]`, `stop` (`ack`, `reset`) | notify the roles in turn |

`yes`, `no` are arrays of steps of the same form, nesting up to two levels: a second-level step with non-empty `yes`, `no` is a refusal of the door. When a branch has ended, the run goes on with the next step of the list it came out of; when there is none, one level up (chapter 4 Н1.11).
The field schema has no references (P/02.1 `jsonSchemaLite`), so the door judges the form of top-level steps and the depth, and the form of a step
inside a branch is judged by the evaluator with the same schema, a refusal of chapter 3.

A step without a subject — `sub` from `ntf`, `net`, `client`, `alarm`, `action` from `email`, `tg`, `http`, `layout`, `wall`, `alarmclose`, the other
keys any: a disabled scenario stores it as data, for an enabled one it is a refusal of chapter 3. The tree has no size limit of its own: the ceiling
of a `json` field is 4000 bytes (P/06.1 Н1.4), more — `too_long`. The rule sets of consolem (ADR-0105) are checked against these limits by a stand run: there is no implementation, the row `in` judges by itself. **Limit:** `via` of an `escalate` level with the words `tg`, `email`, like the actions `email`, `tg`, has no subject: the level is a row `step`, nobody sends messages.

The forms of action fields are no wider than the schema and the rules of the owner of the row or request: `unit`, `cam` — a string or an integer, they go into the request body
and the order row in decimal notation; `port`, `n`, `pulse_ms` — a JSON integer ≥ 1 for `port`, `n` (numbering from 1, V/01.4 Н1.1), ≥ 0 for
`pulse_ms`; `state` — as at `cam`: `open`, `closed`, `pulse`; `minutes` — `number` 1…1440, `before`, `after` — `number`
0…3600 (no strings). `before` = `after` = 0 is an empty scan window: a link of two fields, a refusal of the evaluator (chapter 3 Н1.1).

The step catalogue = this schema. The catalogue says what a scenario **may ask for**, not what a device can do: what a camera can do is checked by the evaluator (chapter 3)
and by the holder at execution.

### Н1.4 Rights

The manifest's `rights`: `cluster_rows: true`, `routes: {view: [answers], edit: [schedules, day_groups, modes, mode_current, windows, versions, rule_marks]}`, `unit_of: {versions:
scenario, answers: scenario, rule_marks: scenario, chains: target}`, `names` — records of the manifest, the meaning below, «Targets in depth» ([gate and pass contract](../../../Platform/common/contracts/gate-and-pass.md) «Права по телу»): a write
of a scenario is a matter of the whole cluster (labels say where the evaluator works, not whose the scenario is); the units that the scenario
names — of each trigger and action — require rights on them too: a scenario does not command a camera on which the author had no
right at the write. An action from `reach.requests` of the target (`output`, V/01.1 Н1.5) requires `edit` on the whole group of the camera, as the request itself does. The right is judged only at the write of the row: a scenario is a decision of the cluster, the row does not carry the author, the filing stamp is the
scenario itself (chapter 4 Н1.1). The tables of chapter 6 are written with `edit`, the row `versions` — of its own scenario; the row `answers` is written with `view` on the scenario (chapter 6 Н1.9). `run_as_role` judges an action by the right of the role by the copy of `domain/grants`
(`worker.reads`; the rights contract, section «Действие от роли», P/02.5 Н3 step 3): the evaluator does not read the roles of `run_as_role`; the copy of `domain/roles` is read only by the operator's answer (chapter 6 Н1.9).

**Targets in depth.** `names` is read from the trigger, the step and each node of the branches `yes`, `no` (gate and pass contract, `names`: `at`, `walk`, `quiet`): `unit`, `cam`, `rule`, `target.include[]` and `event`, `event.target.include[]` of the step `wait_event`. The write of a step carries `action`: a relay through a target is judged as a relay by `unit`. A device is the unit `cam`, a child — the unit by `rights.unit_of` of the row `children`, unreadable — `*`, a folder — the folder object of the rights contract, a server and a domain — `*`: they have no unit. `exclude` does not change reach: the right is judged on the whole included area. A step without a target — `wait`, `ask`, `escalate`, `alarm` without a target — names nobody.

Limit: revoking a grant, disabling and deleting the author do not stop a running scenario — it is stopped by
`enabled: false` or by the removal of the row.

### Н1.5 Placement, lease, snapshot

| Key | Value | Meaning |
|---|---|---|
| `capacity` | `{from: capacity, default: 50, unit_mb: 1, base_mb: 21}` | scenarios per evaluator (a window and a query to the log for each); memory — the measurement of ADR-0070 |
| `headroom` | `{from: headroom}` | the headroom — the platform's |
| `constraint` | `labels-subset` | |
| `requires` | `resource` | the evaluator reads events, and events live on resources |
| `servers` | `shared` | two evaluators on one server are allowed |
| `tie_break` | `most-free-capacity` | |
| `grows` | `true` | not enough evaluators — an order of one more on a server (ADR-0084) |
| `rebalance` | `{dead_band: 0.10}` | |

There is no `near`: what a scenario watches is said inside `when` (JSON), the placement rule does not read JSON. `lease: {unconfirmed_max:
off}` (P/03.2 Н1.6): an action under an unconfirmed lease is a second opening of the door, not a duplicate. The snapshot is `snapshot: [name,
enabled]` (P/04 Н1.3а): to the domain — that the scenario exists and whether it is enabled, not its triggers, conditions and steps.

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| `when`, `conditions` or `then` not by the schema (more than 4, an extra key, a wrong step form, `unit` together with `target`, depth more than two, `run_at` not by the form) | 400 (the field schema, P/06.1 Н1.2) | the response | — |
| `start`, `run_mode`, `repeat`, `hidden` outside the list | 400 | the response | — |
| `within` outside 0…3600, `rate_per_minute`, `valid_for` outside the bounds (`valid_for` 1…9) | 400 | the response | — |
| `minutes` outside 1…1440 or a string; `before`, `after` outside 0…3600 or a string; `port`, `n` not an integer ≥ 1 | 400 (the field schema) | the response | — |
| `id` in the body | 400 `platform_field` (P/06.1) | the response | the number is issued by the console |
| one `json` field longer than 4000 bytes | 400 `too_long` (P/06.1 Н1.4) | the response | simplify the scenario |
| no right on a unit that the scenario names | 403 | the response | — |
| no grant on the cluster | 403 (`cluster_rows`) | the response | — |
