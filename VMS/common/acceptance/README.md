# Приёмка модуля VMS — общий стенд и директивы

Общее для приёмок уроков VMS (`VMS/NN-<имя>/acceptance/K/`). Основа — [общий README приёмки платформы](../../../Platform/common/acceptance/README.md)
(выгрузка, на которой стоит модуль; словарь директив, дверей, запросов и ожиданий, формат `scenarios.tsv`, раздел «Стенд»):
приёмка VMS пользуется его формами и добавляет только то, что ниже. Прогон — после первой генерации стадии C, прошедшей
приёмку платформы (ADR-0090 доп. (8), (9)); до него сценарии — текст нормы. README урока называет свой стенд ссылкой
сюда и пишет только отличия.

## Стенд VMS

Процессы платформы — по разделу «Стенд» общего README: хранилище, консоль кластера, контроллер каждой установленной
подсистемы, ресурс сервера `srv-a` (и `srv-b`, если README урока его называет). Установлены манифесты VMS, которые
называет README урока, из их канона `VMS/<NN-sub>/<sub>.subsystem.yaml` (ADR-0090 доп. (6) п. 8) — байты как есть.
Консоль — `CONSOLE_ROOT=<sub>` урока; прочие подсистемы смонтированы (P/06.5 Н1.1). Файлы подсистем
`/etc/<sub>/<sub>.env` не заданы, если README урока не говорит иного (умолчания подсистемы). Кольцо ключей задано
(`SECRETS_KEY`): секреты строк запечатываются.

**Стенд домена VMS.** Сценарий, которому нужны люди с грантами (README урока его называет), идёт на «Стенде домена»
общего README платформы (`@domain`, двери `holder`, `member <кластер> …`, `@person`): кластер `m1` — «Стенд VMS» выше
с манифестами урока; `member m1 console` — консоль `m1`, корень — подсистема урока, `member m1 console2` — она же,
смонтированная подсистема, которую называет README урока (префикс `/<sub>`, как `console2` ниже; у платформы
`member … console2` — `/testsub2`). Строку грантов `m1` сценарий пишет целиком (`holder PUT /domain/grants/m1`, со строкой
`root`).

**Медиа стенда.** `MEDIA_DIR` стенда (V/01.3; файл подсистемы `cam` задаёт его каталогом стенда) содержит `door.mp4` — H.264, ≥ 10 с; камера `driverpack://file/door.mp4` —
файл, который ведёт себя как камера (без хоста, без устройства с выходами и архивом).

**Доля кадров на стенде.** Файл подсистемы `cam` задаёт и `SHM_DIR` (V/01.2 Н1.3, Н1.7) — каталог доли кадров своего
экземпляра, абсолютный путь (`{data}/run/cam-shm`), не `/run/vms-cam-shm` машины приёмки; подстановка `{shm}` — этот
каталог. Подписчики (`rec`, `det`) каталог не настраивают: точный адрес берут из пульса держателя. Адрес доли в
ожидании — `shm://{shm}/…`: путь абсолютный, начинается с `/`, и `shm://` + путь даёт три косых (`shm:///…`).

**Движок `obsd` на стенде.** Часть `obsd` (V/02.2) — двоичный файл движка версии V/02.2 Н1.4 (ObjectStorage, дерево
`2bbee4a` с патчами 01–07), собранный заранее на машине приёмки; подстановка `{obsd}` — путь к нему (исходник движка не
выгружается: норма урока — договор `obsd`). Стенд запускает часть командой `parts.obsd.exec` манифеста с `{obsd}` вместо
программы и задаёт в файле подсистемы `rec` (`{data}/etc/rec/rec.env`, `W2C_SUB_ENV` части и регистраторов) `OBSD_SOCKET`
— сокет в каталоге своего экземпляра (`{data}/run/rec-obsd/obsd.sock`, короче `sun_path`), не `/run/vms-rec-obsd/obsd.sock`
машины приёмки: параллельные экземпляры не делят сокет и его замок. Точка тома — `{data}/subsystems/rec/obsd/volumes/<n>`
(ниже); каталог доли `cam` — `{shm}` (выше).

## Директивы и двери VMS

| Форма | Смысл | Уроки |
|---|---|---|
| `@start worker <sub> <имя> on <сервер>` | запустить воркер подсистемы VMS `<sub>` со слотом `<имя>` (`<prefix>-<сервер>-<n>`, P/02.4 Н1.1) на сервере стенда — командой «Стенда» реализации подсистемы (её описание называет команду; раздел «Решает реализация» инструкции урока); ожидание — `ok`, когда процесс захватил слот | V/01 (главы 2, 4), V/04 (глава 4) |
| `@start worker <sub> <имя> on <сервер> labels=<метки>` | то же, с метками сервера: воркеру окружение `LABELS=<метки>` как есть (форма `labels=` общего README платформы) | V/10 (глава 2) |
| `@until <секунды> <запрос>` | как в общем README: повторять чтение до совпадения | V/01 |
| `console <МЕТОД> <путь>` (или путь без двери) | консоль кластера, корень — подсистема урока (`/cameras`, `/devices`, `/requests`) | V/01 |
| `console2 <запрос>` | та же консоль, смонтированная подсистема, которую называет README урока: путь запроса получает её префикс `/<sub>` (`console2 POST /cameras {…}` → `/cam/cameras`) | V/02 (глава 4) |
| `holder <воркер> <МЕТОД> <путь>` | дверь держателя камеры (V/01.5) воркера `<воркер>`: стенд задаёт в `/etc/cam/cam.env` `PLAYBACK_PORT={hport}` (свой порт на воркер), без комплекта — `http://127.0.0.1:{hport}` | V/01 (глава 5) |
| `archive <воркер> <МЕТОД> <путь>` | дверь архива регистратора (V/02.5) воркера `<воркер>`: адрес — поле `url` его пульса; без комплекта — `http://127.0.0.1:<порт>` | V/02 (глава 5) |
| `resource GET /v1/objects/<ключ>` | дверь ресурса сервера `srv-a` (P/05 Н2): объекты подсистемы — метки просьб `<sub>/commands/<rid>`, пульсы `<sub>/heartbeats/<воркер>` | V/01 (глава 4) |
| `@domain <кластер>` | стенд домена VMS («Стенд домена VMS» выше): `@domain` общего README платформы с одним членом | V/03 (глава 1) |
| `@person <имя> <пароль>` | как в общем README платформы; пароль у людей сценариев VMS — без пробелов | V/03 (глава 1) |
| `holder <запрос>` | на стенде домена VMS — консоль домена (дверь `holder` общего README платформы); отличается от двери держателя камеры `holder <воркер> <МЕТОД> <путь>` выше вторым словом: здесь — метод; первый сценарий, которому на стенде домена нужны обе, даёт двери домена своё слово | V/03 (глава 1) |
| `member <кластер> console <запрос>` | консоль кластера-члена, корень — подсистема урока; несёт токен человека `@person` | V/03 (глава 1) |
| `member <кластер> console2 <запрос>` | та же консоль, смонтированная подсистема урока (префикс `/<sub>`) | V/03 (глава 1) |
| `door <единица> <запрос>` | дверь держателя единицы `<единица>` (`<sub>/<id>`) с токеном двери: стенд берёт `GET /where/<id>` консоли (корень — подсистема единицы; иначе `/<sub>/where/<id>`) личностью петли и шлёт запрос (`<МЕТОД> <путь> [тело]`, JSON — `Content-Type: application/json`) на `door.url` с `Authorization: Bearer <door.token>`; токен — свежий на каждый запрос | V/10 (глава 2) |
| `door <единица> bare <запрос>` | та же дверь без `Authorization` (отказ токена) | V/10 (глава 2) |
| `member <кластер> door <единица> <запрос>` | дверь держателя единицы на стенде домена VMS: `where` — консолью кластера-члена с токеном человека `@person`, затем как `door` выше | V/10 (глава 2) |

**Файл подсистемы на стенде.** Ключи файла подсистемы (`/etc/<sub>/<sub>.env`), которые называет README урока (и на
сценарий — тоже), стенд пишет в файл `{data}/etc/<sub>/<sub>.env` своего экземпляра и даёт воркеру подсистемы его путь в
`W2C_SUB_ENV` (P/02.4 Н1.2; [договор файла окружения](../../../Platform/common/contracts/env-file.md)) — до `@start
worker`; файл — свой на сценарий. Подстановки VMS сверх общего README: `{model_stub}` — программа раннера `model-stub`
(заглушка модели, V/10.2 Н5); `{spec}` — корень спецификации (каталог с `Platform/` и `VMS/`); `{hport}` — порт двери
держателя камеры (выше); `{obsd}` — двоичный файл движка `obsd` (выше).
Подстановки стенда действуют и в запросах и ожиданиях `scenarios.tsv` VMS: путь
`/data/platform` норм (`PLATFORM_DIR`, P/02.4 Н1.2) на стенде — `{data}` своего экземпляра, и сценарий пишет `{data}`
(`file://{data}/subsystems/rec/obsd/volumes/1`), не буквальный путь машины приёмки; `{shm}` — каталог доли кадров (выше).

Связывание `$имя` — в пределах сценария (общий README); сценарий, которому нужна камера, создаёт её сам. Каждый
сценарий — на чистом экземпляре, если README урока не говорит иного; повторный и параллельный прогон — свои экземпляры.
Двойника устройства с выходами, пресетами и архивом у стенда пока нет: нормы, которым он нужен, проверяются чтением
(README урока называет их).
