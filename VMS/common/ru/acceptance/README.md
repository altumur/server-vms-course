# Приёмка модуля VMS — общий стенд и директивы

Общее для приёмок уроков VMS (`VMS/NN-<имя>/acceptance/K/`). Основа — [общий README приёмки платформы](../../../../Platform/common/ru/acceptance/README.md)
(выгрузка, на которой стоит модуль; словарь директив, дверей, запросов и ожиданий, формат `scenarios.tsv`, раздел «Стенд»):
приёмка VMS пользуется его формами и добавляет только то, что ниже. Прогон — после первой генерации стадии C, прошедшей
приёмку платформы (ADR-0090 доп. (8), (9)); до него сценарии — текст нормы. README урока называет свой стенд ссылкой
сюда и пишет только отличия.

Текст производный от `acceptance/README.md`, руками не правится: источник — английский [`acceptance/README.md`](../../acceptance/README.md), правка идёт в него, русский пересобирается переводом (ADR-0121).

## Стенд VMS

Процессы платформы — по разделу «Стенд» общего README: хранилище, консоль кластера, контроллер каждой установленной
подсистемы, ресурс сервера `srv-a` (и `srv-b`, если README урока его называет). Установлены манифесты VMS, которые
называет README урока, из их канона `VMS/<NN-sub>/<sub>.subsystem.yaml` (ADR-0090 доп. (6) п. 8) — байты как есть.
Консоль — `CONSOLE_ROOT=<sub>` урока; прочие подсистемы смонтированы (P/06.5 Н1.1). Файлы подсистем
`/etc/<sub>/<sub>.env` не заданы, если README урока не говорит иного (умолчания подсистемы). Кольцо ключей задано
(`SECRETS_KEY`): секреты строк запечатываются.

**Стенд домена VMS.** Сценарий, которому нужны люди с грантами (README урока его называет), идёт на «Стенде домена»
общего README платформы (`@domain`, двери `holder`, `member <кластер> …`, `@person`): кластеры `hold` и `m1` готовятся
одинаково, как у платформы (README приёмки P/08.3 «Подготовка каждого сценария»), — «Стенд VMS» выше с манифестами урока,
процессы — какие называет README урока, сверх них — то, что требует стенд домена платформы (ресурс своего сервера,
домен и консоль домена на `hold`, агенты `hold` и `m1`); `member m1 console` — консоль `m1`, корень — подсистема урока, `member m1 console2` — она же,
смонтированная подсистема, которую называет README урока (префикс `/<sub>`, как `console2` ниже; у платформы
`member … console2` — `/testsub2`). Строку грантов `m1` сценарий пишет целиком (`holder PUT /domain/grants/m1`, со строкой
`root`).

**Медиа стенда.** `MEDIA_DIR` стенда (V/01.3; файл подсистемы `cam` задаёт его каталогом стенда) содержит `door.mp4` — H.264, ≥ 10 с; камера `driverpack://file/door.mp4` —
файл, который ведёт себя как камера (без хоста, без устройства с выходами и архивом).

**Доля кадров на стенде.** Файл подсистемы `cam` задаёт и `SHM_DIR` (V/01.2 Н1.3, Н1.7) — каталог доли кадров своего
экземпляра, абсолютный путь (`{data}/run/cam-shm`), не `/run/vms-cam-shm` машины приёмки; подстановка `{shm}` — этот
каталог. Подписчики (`rec`, `det`) каталог не настраивают: точный адрес берут из пульса держателя. Адрес доли в
ожидании — `shm://{shm}/…`: путь абсолютный, начинается с `/`, и `shm://` + путь даёт три косых (`shm:///…`).

**Плагины psim на стенде** (V/12). Каталоги плагинов `security_controller` и `camera` psim-sdk `c3d9ebb` — исполняемый файл,
собранный из `psim_plugins/cmd/<плагин>` заранее на машине приёмки, `plugin.json` и `langs/` как есть, без правок; подстановка
`{psim}` — каталог, где они лежат (`{psim}/camera`, `{psim}/security_controller`). Стенд кладёт каталог плагина в
`{data}/usr/lib/psim-<id>/` своего экземпляра вместо `/usr/lib/psim-<id>/` (V/12.4 Н1.1) перед каждым `@psim install`; `<id>` —
`metadata.plugin_id` в нижнем регистре, как в имени подсистемы (V/12.1 Н1.1); аргумент шага остаётся `{psim}/<плагин>`. Адаптер —
программа реализации урока V/12. Канон `backend` — `VMS/11-backend/backend.subsystem.yaml` выгрузки; обход P/02.4 `add` после `@psim install`, `@psim disable`, `@psim enable`,
`@psim sync` стенд исполняет шагом `@traverse` своими процессами (файлы манифестов, права, хранилище и консоль при разнице, контроллер `psim-<id>`); набор обхода — stdout команды; воркер-адаптер `psim-<id>` —
шагом сценария `@start worker psim-<id> <имя> on <сервер>`, программа — ключ `stand.worker` профиля `V12-psim`. Строк `backend/instances`
и воркера `backend` на стенде нет (реализации V/11 у стенда нет): сборка ждёт только `served` манифестов, подъёма `backend`
ждать не у кого — «пульс каждого экземпляра» пуст (V/12.4 Н1.3 шаг 4). Секрет вводом (`--secret`) стенд пишет в `stdin`
команды строкой `<поле>=<значение>` и переводом строки, по строке на секрет; `<поле>` — имя параметра psim без суффикса
`_secret`; в аргументы команды `--secret` не идёт (решение «Спецификации VMS»).

**Движок `obsd` на стенде.** Часть `obsd` (V/02.2) — двоичный файл движка версии V/02.2 Н1.4 (ObjectStorage, дерево
`2bbee4a` с патчами 01–07), собранный заранее на машине приёмки; подстановка `{obsd}` — путь к нему (исходник движка не
выгружается: норма урока — договор `obsd`). Стенд запускает часть командой стенда `obsd` профиля реализации `rec` — её
обёрткой части (`parts.obsd.exec`, V/02.2 Н1.1) — с `{obsd}` (путь движка) в шаблоне команды; как обёртка берёт путь движка
из команды — «Решает реализация»; стенд задаёт в файле подсистемы `rec` (`{data}/etc/rec/rec.env`, `W2C_SUB_ENV` части и
регистраторов) `OBSD_SOCKET` — сокет в каталоге своего экземпляра (`{data}/run/rec-obsd/obsd.sock`, короче `sun_path`), не `/run/vms-rec-obsd/obsd.sock`
машины приёмки: параллельные экземпляры не делят сокет и его замок. Точка тома — `{data}/subsystems/rec/obsd/volumes/<n>`
(ниже); каталог доли `cam` — `{shm}` (выше).

**Подстановка `$имя` внутри строки ожидания** (сценарии VMS, поверх строки `$имя` общего README платформы, где связывается и
сравнивается только значение целиком). В строке JSON ожидания, которая не равна `$имя` целиком, каждое вхождение `$` и за ним
`[A-Za-z0-9_]+` — имя до первого знака не из этого класса — заменяется значением связанного имени сценария, затем строка
сравнивается целиком: `"cam-$c1-card"` при `$c1` = `7` — `"cam-7-card"`, `"folder:$fid"` — `"folder:<id папки>"`. Связывания внутри
строки нет: имя должно быть связано раньше шагом с `$имя` целиком; несвязанное имя — несовпадение шага. Формы `@not($имя)`,
`@spoil($имя)` — по словарю платформы, как прежде (решение «Спецификации VMS» по вопросу раннера, V/02.4 `06-edge`, V/11 приёмка 8). Экранирования нет: `$` перед буквой, цифрой или `_` в ожидании VMS — всегда имя; настоящего знака `$` перед ними в
ожиданиях VMS нет (сверено по всем `scenarios.tsv` 2026-11-03). Понадобится — правило `$$` вводится тогда, со словарём раннера.

**Файл подсистемы на стенде.** Ключи файла подсистемы (`/etc/<sub>/<sub>.env`), которые называет README урока (и на
сценарий — тоже), стенд пишет в файл `{data}/etc/<sub>/<sub>.env` своего экземпляра и даёт воркеру подсистемы его путь в
`W2C_SUB_ENV` (P/02.4 Н1.2; [договор файла окружения](../../../../Platform/common/ru/contracts/env-file.md)) — до `@start
worker`; файл — свой на сценарий. Подстановки VMS сверх общего README: `{model_stub}` — программа раннера `model-stub`
(заглушка модели, V/10.2 Н5); `{spec}` — корень спецификации (каталог с `Platform/` и `VMS/`); `{hport}` — порт двери
держателя камеры (выше); `{obsd}` — двоичный файл движка `obsd` (выше).
Подстановки стенда действуют и в запросах и ожиданиях `scenarios.tsv` VMS: путь
`/data/platform` норм (`PLATFORM_DIR`, P/02.4 Н1.2) на стенде — `{data}` своего экземпляра, и сценарий пишет `{data}`
(`file://{data}/subsystems/rec/obsd/volumes/1`), не буквальный путь машины приёмки; `{shm}` — каталог доли кадров (выше).

Связывание `$имя` — в пределах сценария (общий README); сценарий, которому нужна камера, создаёт её сам. Каждый
сценарий — на чистом экземпляре, если README урока не говорит иного; повторный и параллельный прогон — свои экземпляры.
Двойника устройства с выходами, пресетами и архивом у стенда пока нет: нормы, которым он нужен, проверяются чтением
(README урока называет их).
