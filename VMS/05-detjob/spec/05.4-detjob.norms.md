# V/05.4 — Wait, follow, request; heartbeat: norms

This English text is the source; the Russian translation `ru/spec/05.4-detjob.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 4 of lesson V/05 «Задача по интервалу архива» (ADR-0080; the VMS module — ADR-0090). Lecture (`ru/05-detjob.md`, for people, not in the export),
[instructions](05-detjob.README.md), manifest [`detjob.subsystem.yaml`](../detjob.subsystem.yaml). The platform is the export
`cammeta-specs` `7a875c75`.

Not all the video of an interval can be read at once: a door is silent, no one holds a volume, the recording is still going, the minutes are not with us but are
at the camera. The chapter sets norms for when a job waits and for how long, when it follows the recording, when it requests catch-up recording, and what it says in
the heartbeat. Reading is chapter 2; the result is chapter 3 Н1.5; catch-up recording at the recorder is [V/02.8](../../02-rec/spec/02.8-rec.norms.md) Н1.4.

Norm ids are `V/05.4-MM`; the map to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н1 Form

**Time.** The media time of the interval and of the spans; `now` is the worker's clock; waiting timeouts are an accumulated duration in the cursor
(`waited`, `fetch_waited`, seconds; they survive a move, Н1.2).

**Data** (the shared families of the [platform catalogue](../../../Platform/common/data/catalog.tsv)): writes — the requests `rec/requests/<rid>`
(`worker.requests: [rec]`, [P/03.6 Н1.5](../../../Platform/03-worker/spec/03.6-worker.norms.md)), the heartbeat; reads — the heartbeats
of the holders `cam/heartbeats/*` (the address of the device archive listing, V/01.5), the recording row `rec/recordings/<rec>` (retention,
«visible from»). The subsystem file `/etc/detjob/detjob.env` is read by the job's worker by the environment file contract (no file —
the defaults; unreadable or a value not by the grammar — a start refusal, code 2; the summary — V/09.2):

| Key | Read by | Grammar | Default | Norm |
|---|---|---|---|---|
| `VISIBLE_LAG_SECONDS` | the job's worker | an integer ≥ 0 | 600 | Н1.3 «follow» |


### Н1.1 Phases

An element of the job's `status[]` is under the taken epoch (V/05.3 Н1, P/03.3); `reason` is the subsystem's words, `why` — the platform's:

| `phase` | When |
|---|---|
| `queued` | the model is not loaded yet (V/05.3 Н1.1) |
| `running` | segments of the plan are being read |
| `waiting` | everything that arrived has been read, but there is no result yet: no door answered, something is missed (`missing`, Н1.2) or a hole waits for the device listing (Н1.4); `reason` — the table below |
| `following` | the recording is still going towards the end of the interval (Н1.3) |
| `fetching` | the minutes exist at the device, the catch-up recording request has been filed or its filing was refused (`filings.refused`: not by the schema, `rid` not by the grammar, the row under `rid` is unreadable, P/03.6 Н1.5), or the store is silent (Н1.4) |
| `unsupported` | the worker does not have the model's kind (V/04.2): the job asks no doors, there is no `reason`; it waits `WAIT_MAX` by `waited` (Н1.2), then the result `failed` «`no model <kind> on this worker`» (V/05.3 Н1.5); any edit of the row — the job anew (V/05.1 Н1.3) |
| `failed` | the model or the mask does not start (the runtime backoff; V/05.3 Н1.3) |
| `done`, `failed` | a result is valid (V/05.3 Н1.5): the phase is its `end`, between the result and the removal the job is not executed |

The phase of an element is the first one that holds: the result; `unsupported`; `failed`; `queued`; `running` (the remainder is being read); `waiting` when no one
answered; `following`; `waiting`; `fetching`.

**The reason of `waiting`** is the first condition from the top that holds (as V/04.2 «Нет источника»); the words are a contract:

| Condition | `reason` |
|---|---|
| the recording row `rec` is unreadable or the store did not answer (V/05.2 Н1.1) | `recording <rec> unreadable` |
| no archive door answered (Н1.2) | `no recorder's archive door answered` |
| `n` volumes are missed (`missing`, Н1.2) | `<n> volumes missing` |
| the camera element in the holder's heartbeat is unreadable (Н1.4) | `cam heartbeat unreadable: <поле>` |
| there is no fresh heartbeat of the camera holder (Н1.4) | `camera holder not heard` |

### Н1.2 Wait for what is missed

- **No one answered** — there is no plan, `waiting`: «no one» is not «nothing»; the wait accumulates `waited` (below), at `WAIT_MAX` —
  the result `failed` «`no recorder's archive door answered`» (V/05.3 Н1.5) (an amendment from the analysis of the V/05 review, `68c286e45`).
- **Missed** (`missing` — the volumes `silent`, `garbled`, `unread`, chapter 2 Н1.1): what arrived is read, there is no result `done`
  until what is missed has been read.
- **The timeout is an accumulated duration** in the cursor: the field `waited` (seconds, ≥ 0). The holder MUST add to it the increment
  of its monotonic clock between cursor writes while no one answered, **or** something is missed, **or** a segment of the plan
  is not read (chapter 2 Н1.3), **or** the model is `unsupported` (Н1.1), **or** a hole
  waits for the device listing (Н1.4), **or** the recording row is unreadable (V/05.2 Н1.1; at `WAIT_MAX` — the result `failed`
  «`recording <rec> unreadable`», V/05.3 Н1.5); a new holder continues from the value of the cursor.
  Time without a holder (a move, the job is not placed) does not count: one move loses no more than `STATE_EVERY` with
  successful cursor writes. The timeout is per job: a lull does not zero the field, only a new `revision` resets it (V/05.3 Н1.2).
  The timeout has run out — `waited` ≥ `WAIT_MAX` = 3600 s. It is judged on a pass where there is nothing to read: there is no remainder or none of its segments
  was read on the pass, and not over `following`; an unread remainder is named by the volume of its door (`partial`).
- **The timeout has run out** — first one event row `scan.partial` (`partial` — the same elements as in the result; `waited` — the value of
  the counter that ran out, if both ran out — the larger one; `occurred` — `from` of the interval; class `observation`) under `may_write`, then the result by CAS `{end: done, …, partial: […]}` (V/05.3 Н1.5). A write error of the row MUST NOT delay the result
  — the count `events_refused`; a break between the row and the result — the new holder writes the row again (V/05.3
  «Гонки»).
- **`partial`** is only what was not waited for; when any timeout runs out — everything not waited for, of two kinds: `<том>@<сервер>` —
  a volume not read by the deadline, including the volume of the door of an unread segment (here; `<сервер>` — by V/02.5 Н1.5);
  `device:<from:int>-<to:int>` — a piece of a catch-up recording request that did not arrive by the deadline, or a hole for which the device listing
  never came (Н1.4). There are no permanent holes in it. The same row `scan.partial` is written also when the timeout `fetch_waited` runs out
  (Н1.4).

### Н1.3 Follow the recording

`following`: `written_through < to` (chapter 2 Н1.4) and `now < to + FOLLOW_LAGS × VISIBLE_LAG_SECONDS` (`FOLLOW_LAGS` = 2,
`VISIBLE_LAG_SECONDS` = 600 — the worst path of a frame to visibility: the engine block size over the bitrate, V/02.3). The job reads what is visible and
waits for growth; a growing span is not read twice (the remainder by time, V/05.3 Н1.2). An interval entirely in the future is `following`,
not `waiting`. The timeout has run out (the camera went dark) — the minutes beyond `written_through` become a permanent hole, the result is by what is visible:
`covered` < `asked`. The delay of a job is the visibility lag; «look
now» is the detector's business (V/04).

### Н1.4 Request catch-up recording

- **Hole** — the minutes `[from, to)` without a segment of the plan and outside `done` (V/05.3 Н1.2). The job takes «visible from» of the recording row (V/02.5 Н1.2)
  only here. The job decides the fate of a hole when `missing` is empty: the minutes may lie in an unread volume (a volume that
  nothing names does not go into `missing`: the limit of chapter 2 Н1.1). The fate of a hole:
  - before «visible from», without a span in the door's answer — a **permanent hole**: it is not waited for and not requested (the decision of plan 8);
  - after «visible from» and up to `min(to, now, written_through)` — a question to the device (below): `{spans}`, 501 or an error — a request, `fetching` up to
    `WAIT_MAX`; `[]` — a permanent hole;
  - beyond `written_through` — `following` (Н1.3), until its timeout runs out, then a permanent hole.

  Permanent holes do not hold the result (V/05.3 Н1.5): that not everything was viewed is said by `covered` < `asked`.
- **Whether the device has it:** the holder's archive listing `GET <index_url>?from&to` (V/01.5; the leaf of the role `detjobworker`; it does not spend
  a playback session): `{spans: […]}` — request the intersection, the rest is a permanent hole; `[]` — the device does not have it,
  a permanent hole; 501 `no index` or an error — by the summary `coverage` of the holder's heartbeat: the summary does not intersect the piece — a permanent
  hole, otherwise, optimistically, a request for the whole piece of the hole. The camera element is readable, there is no `coverage`, or `cam` is of the form `ref:<ref>` —
  the device does not have it, a permanent hole. **There is no listing** — the camera element in
  the holder's heartbeat is unreadable (`index_url`, `coverage` not by the form, V/01.2 Н1.4) or there is no fresh heartbeat of the holder (the observation
  contract `LOST_AFTER`): not read, rather than absent — the hole of this piece waits (`waiting`, `reason` by the table of Н1.1), «the
  device does not have it» is not set, the next heartbeat — again; the wait accumulates `waited` (Н1.2), at `WAIT_MAX` — `partial` with the element
  `device:<from:int>-<to:int>` for the whole piece of the hole, the row `scan.partial` and the result (V/05.3 Н1.5). No door is `silent` and
  none is `garbled`, at least one answered, the plan is empty, not `following` and not `fetching`, no holes waiting for the device's verdict —
  the result `done` (V/05.3 Н1.5).
- **Request** — filing by the worker: the row `rec/requests/<rid>` with the body `{unit: <rec>, from, to}` in pieces no longer than a day
  from the start of the piece of the hole (as V/06.4 Н1.2); before filing the bounds are rounded to whole seconds (`from` — down, `to` — up): the body
  and the `rid` are built from the same numbers, a piece shorter than a second does not occur. A piece is frozen at the first filing: the holder
  keeps the bounds in memory, `now` and «visible from» do not move them; after a move a new `rid` is allowed. The `rid` is by the key of the requests of `rec`
  (`{unit}-{from:int}-{to:int}`; a repeat — the same row), the stamps `by: detjob/<job>`, `at`, `about` ([P/03.6
  Н1.5](../../../Platform/03-worker/spec/03.6-worker.norms.md)); the execution is the recorder's (V/02.8 Н1.4), what arrived is
  the stream `…/backfill`, the plan takes it without changes (chapter 2). The job does not wait for the outcome: the recorder closes the request
  (`fetched`), and if there is no one to close it — the reaper (V/02.8 Н1.4).
- `fetching` holds while the hole exists, no longer than `WAIT_MAX` = 3600 s of accumulated waiting (the field `fetch_waited`
  of the cursor — by the rule of `waited`, Н1.2); when it has run out — the row `scan.partial` (Н1.2), then the result `done` with `partial` (the pieces that did not arrive,
  `device:<from:int>-<to:int>`). The job MUST NOT read the device archive itself: it has two sessions per device — the operator's and
  the recorder's.

### Н1.5 Heartbeat and series

The form is [P/03.4 Н1.1](../../../Platform/03-worker/spec/03.4-worker.norms.md); the platform puts in the capacity, the reserve, `filings`
(filing of requests, P/03.6 Н1.5). `detjob` adds: at the top — `events_written`, `events_refused` (counters since the start; the name
`events` is taken by a platform field, P/03.4 Н1.1 `platform_strings`); in the job element — `phase`, `reason`, `from`, `to`,
`asked`, `covered`, `done_through` (the largest end of what was read — a progress bar, not a resumption point),
`events`, `missing` (a list of `<том>@<сервер>`, when something is missed). The series are `jobs_running` (`console.running`: the manifest
metric that `console.running` names — by its declaration `from`, `agg`, `equals`, `live`, as any series of
`metrics[]`, P/06.5 Н3, C06-CONSOLE-RUNNING-DEF-01), `filings_total` (the manifest).

## Н3 Pass

```
1. No one answered → waiting; waited += increment; waited ≥ WAIT_MAX → result failed.
2. missing or a segment not read → read what arrived; waited += increment; nothing to read, not following and waited ≥ WAIT_MAX → the row scan.partial, then result done + partial.
3. written_through < to and now < to + 2·lag → following.
4. Holes with missing empty: before «visible from» — permanent; after — the device listing → [] permanent | requests in pieces ≤ a day → fetching.
   4.1. No listing (the holder's heartbeat is unreadable or not heard) → waiting; waited ≥ WAIT_MAX → scan.partial, result done + device:.
   4.2. fetch_waited ≥ WAIT_MAX → the row scan.partial, then result done + partial.
5. unsupported: waited += increment; waited ≥ WAIT_MAX → result failed.
6. No remainder, missing empty, not following, not fetching, no holes waiting for a listing (permanent ones do not hold) → result done (V/05.3 Н1.5).
```

**Races.** Catch-up recording arrived between passes — the next plan takes the stream `…/backfill`, the hole is closed, `fetching` is removed. Two
jobs requested pieces with equal bounds — the `rid` is one, the row is one. A move in the middle of a wait — the timeouts continue what was
accumulated in the cursor, not anew; time without a holder does not count.

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| no door answers | `waiting`; at `WAIT_MAX` — the result `failed` «`no recorder's archive door answered`» | heartbeat, result | bring up the recorders |
| a volume is not read for an hour | the result `done` + `partial`, `scan.partial` | result, events | — |
| the request is not by the schema `rec`, `rid` not by the grammar, the row under `rid` is unreadable | not filed, `filings.refused`; the hole stays, `fetching` up to `WAIT_MAX` | heartbeat | — |
| the recorder refused the request | the hole stays; `fetching` up to `WAIT_MAX` | the recorder's heartbeat (`requests_refused`) | — |
| the recording went dark | the result by what is visible after 2 lags | result | — |
| the device has no minutes (`[]`, no summary or it does not intersect the piece, `cam` of the form `ref:<ref>`), minutes before «visible from» | a permanent hole; the result `done`, `covered` < `asked` | result | — |
| the camera element in the holder's heartbeat is unreadable | the hole waits, `waiting`, `reason` «`cam heartbeat unreadable: <поле>`»; at `WAIT_MAX` — `partial` `device:` | heartbeat, result | — |
| there is no fresh heartbeat of the camera holder | the hole waits, `waiting`, `reason` «`camera holder not heard`»; at `WAIT_MAX` — `partial` `device:` | heartbeat, result | bring up the camera holder |
| a catch-up piece did not arrive within `WAIT_MAX` | the row `scan.partial`, the result `done` + `partial` `device:` | result, events | — |
| there is no model of the kind for an hour | the result `failed` «`no model <kind> on this worker`» | result | a model onto the worker, a new job |

## Н5 Acceptance

The lesson has no acceptance catalogue on the stand yet: a scan needs the TLS VMS stand (the leaves `recworker`, `detjobworker`) and visibility of
the recording — up to `VISIBLE_LAG_SECONDS` (engine blocks), a scenario with the teaching model would take minutes and would depend on the pace at which
blocks are flushed. The chapter and chapters 2, 3 are checked by reading and by a test of the implementation; the scan scenario (`tick` by the recording up to the result `done` and
removal) will appear with the TLS VMS stand.
