# V/09.3 — Пакет: нормы

Канон главы 3 урока V/09 «Развёртывание VMS» (ADR-0080; модуль VMS — ADR-0090). [Лекция](../09-deploy.md),
[инструкция](09-deploy.README.md). Платформа — выгрузка `cammeta-specs` `d3f8e05`.

Глава нормирует, что VMS поставляет: один пакет на все серверы, из чего он собран, как его доставляют и что пакет обязан
сказать о лицензиях того, на чём стоит. Установка и обновление пакета — платформы ([P/02.4](../../../Platform/02-installer/spec/02.4-installer.norms.md)
Н1.7).

Id норм — `V/09.3-MM`; соответствие прежним урокам — [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Словарь слов

Нормативные слова — по [канону курса](../../../НОРМАТИВНЫЕ-СЛОВА.md). Правила модуля «Платформа» — [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-словарь-слов).

## Н1 Форма

### Н1.1 Один пакет

- Один пакет VMS на все серверы всех кластеров — серверный кластер, камера как кластер из одного (P/02.4 Н1.10), держатель
  домена; на архитектуру процессора — своя сборка того же пакета.
- Различие между серверами — **свойство сервера**: метки (`LABELS`), набор включённых юнитов (домен — только у держателя,
  P/02.4 Н1.12; воркеры — по ролям сервера) и несколько строк `w2c.env`; не имя сервера и не форк пакета на кластер.
- Сборка называет себя `BUILD` (P/06.6): пульс каждого воркера несёт `build`, `GET /schema` консоли — `builds`: различные `build`
  своей сборки консоли и всех процессов `processes`, включая `live: false` (P/06.6 Н2.3); отставший живой процесс — по
  `processes.*` с `live: true` и `build`, не равным новой сборке.

### Н1.2 Состав

| Что | Откуда | Норма |
|---|---|---|
| процессы платформы, раннер, установщик | реализация платформы | P/02.4 |
| исполняемые воркеров VMS — пути `worker.exec` | реализация VMS | глава 1 Н1.1 |
| манифесты и страница — байты канона как есть | спецификация | глава 1 Н1.1; V/08.1 |
| `obsd` — движок части `rec`, `/usr/local/bin/obsd`; обёртка части `/usr/lib/rec/obsd-part` | двоичный файл движка версии V/02.2 Н1.4 (ObjectStorage, дерево `2bbee4a`, патчи 01–07), собранный вне генерации VMS (как `{obsd}` стенда); исходник не выгружается; пакет кладёт его как есть; обёртка — исполняемый VMS | V/02.2 Н1.1, Н1.4 |
| медиабиблиотека (тройник, очередь, упаковщик RTP, WebRTC) | системные пакеты ОС | V/03.4 |
| набор WebUI конфигуратора consolem (семь файлов: стили, шрифт, словарь, картинки `png`, `svg`; без `index.html` — входная страница — оболочка `backend.shell.html` урока) — рядом с манифестом `backend`; отдаёт консоль статическими файлами подсистемы (B7) | репозиторий продукта на закреплённом коммите `9dc16881`, сверка SHA-256 каждого файла по списку манифеста; в курс не входит | V/11.1 Н1.4 |
| ключ вендора `/etc/cam/vendor.pem` | вендор | глава 1 Н1.1; V/01.7 |
| примеры файлов подсистем | реализация VMS | глава 2 Н1.1 |
| файлы семи ролей `roles/<роль>.env`, проходящие правило памяти | реализация VMS | глава 2 Н1.3 |

- Зависимости — из пакетов ОС выпуска; сборка не ходит в сеть за пакетами языка; своей базы данных на сервере нет (правда —
  в хранилищах платформы).
- `obsd` без патча 07 (ограда замка тома, `WRITER_ABANDON`) не годится — регистратор отказывает при подключении (V/02.2).

### Н1.3 Доставка

- **Толкание** — сборочная линия ставит пакет на каждый сервер (`install.sh` по P/02.4 Н1.7, сервер за сервером): линия должна
  дотянуться до каждого сервера в момент запуска; упавший запуск не виден на площадке.
- **Вытягивание** — площадка опрашивает хранилище пакетов и ставит новое сама тем же `install.sh`: лежавший канал стоит
  задержки, и только.
- Выбор — площадки; в обоих случаях отставание видно по `builds` (Н1.1), и обновление идёт по P/02.4 Н1.7 `upgrade` — со
  схемой, которую новая сборка понимает, и без отката схемы.

### Н1.4 Лицензии того, на чём стоит пакет

- Пакет несёт уведомление каждой поставленной зависимости и путь к исходному коду той её версии, что поставлена.
- Реализация называет каждую зависимость пакета (движок архива, медиабиблиотека, библиотеки платформы) и одной фразой
  говорит, что её лицензия требует от продукта и что изменило бы ответ (правка файлов библиотеки, статическая сборка,
  поставка в иной форме).

## Н3 Проход

```
сборка (на архитектуру): процессы платформы + исполняемые VMS + манифесты и страница + obsd (патчи 01–07) + ключ вендора
  + примеры файлов подсистем и файлы ролей + уведомления зависимостей → пакет с BUILD
доставка: толкание или вытягивание → install.sh сервер за сервером (P/02.4 Н1.7) → builds видны в /schema
```

---

## Н4 Отказы

| Причина | Исход | Кто и как видит | Что делает вызывающий |
|---|---|---|---|
| `obsd` без патча 07 | регистратор отказывает при подключении | статус записи, журнал | собрать с патчами 01–07 |
| сервер отстал (старая сборка) | живой процесс с `build` ≠ новой (`processes.*`, `live: true`) | `/schema`, `/servers` | доставить пакет |
| старая сборка на новой схеме | не стартует (видимо) | журнал | обновить сервер (P/02.4 Н1.7 `rule`) |

## Решает реализация

Реализация обязана назвать в своём описании: **формат пакета** и его сборку на каждую архитектуру; **зависимости** с
лицензиями и фразой «что требует» (Н1.4); **способ доставки** для своей площадки (Н1.3); **откуда взят двоичный файл движка `obsd`** и его `sha256`.
