# V/09.3 — The package: norms

This English text is the source; the Russian translation `ru/spec/09.3-deploy.norms.md` (for people, not in the export) is derived from it by translation and is not edited by hand (ADR-0121).

The canon of chapter 3 of lesson V/09 «Развёртывание VMS» (ADR-0080; the VMS module — ADR-0090). Lecture (`ru/09-deploy.md`, for people, not in the export),
[instructions](09-deploy.README.md). The platform is the export `cammeta-specs` `7a875c75`.

The chapter sets norms for what VMS ships: one package for all servers, what it is built from, how it is delivered and what the package MUST
say about the licences of what it stands on. Installing and upgrading the package belongs to the platform ([P/02.4](../../../Platform/02-installer/spec/02.4-installer.norms.md)
Н1.7).

Norm ids are `V/09.3-MM`; the map to former lessons is [`id-map.tsv`](../../common/id-map.tsv).

## Н0 Vocabulary

Normative keywords (MUST, MUST NOT, SHOULD, MAY by RFC 2119 and RFC 8174) follow the [course canon](../../../НОРМАТИВНЫЕ-СЛОВА.md). The rules of the module «Платформа» are [P/01.1 Н0](../../../Platform/01-store/spec/01.1-store.norms.md#н0-vocabulary).

## Н1 Form

### Н1.1 One package

- There is one VMS package for all servers of all clusters — a server cluster, a camera as a cluster of one (P/02.4 Н1.10), the domain
  holder; for each processor architecture there is a separate build of the same package, and the word `BUILD` is one for all architectures of one build.
- The difference between servers is a **property of the server**: the labels (`LABELS`), the set of enabled units (the domain only at the holder,
  P/02.4 Н1.12) and a few lines of `w2c.env`; not the server name and not a fork of the package per cluster.
- The build names itself `BUILD` (P/06.6): the heartbeat of each worker carries `build`, `GET /schema` of the console carries `builds`: the distinct `build` values
  of the console's own build and of all processes `processes`, including `live: false` (P/06.6 Н2.3); a live process that lags behind is found by
  `processes.*` with `live: true` and a `build` not equal to the new build; the controller and `obsd` do not write a heartbeat, `/schema`
  does not see their lag.

- Dependencies come from the OS packages of the release; the pinned versions of `Platform/common/versions` come from the build tree; the build does not go to the network
  for language packages; there is no database of its own on the server (the truth is in the stores of the platform).
- The model weights are an optional part of the package: a camera as a cluster of one does not install them, no fork is needed. Without the weights the installation has no assistant: there is no external model in a real installation (ADR-0093 addendum (9) item 2).
- `obsd` without patch 07 (the volume lock fence, `WRITER_ABANDON`) is not fit — the recorder refuses on connection (V/02.2).

### Н1.3 Delivery

- **Push** — the build line installs the package on each server (`install.sh` by P/02.4 Н1.7, server by server): the line MUST
  reach each server at the moment of the run; a failed run is not visible at the site.
- **Pull** — the site polls the package repository and installs what is new by itself with the same `install.sh`: a channel that was down costs
  a delay, and nothing more. The queue is the drain: a server takes `POST /drain`, on 409 it waits for the next poll (P/06.6 Н1.2); raising the schema
  (`upgrade` step 4) is the operator's hand, pull does not do it.
- The choice belongs to the site; in both cases the lag is visible by `builds` (Н1.1), and the upgrade goes by P/02.4 Н1.7 `upgrade` — with the
  schema that the new build understands, and without a schema rollback.

### Н1.4 Licences of what the package stands on

- The package carries the notice of each shipped dependency and the path to the source code of the version of it that is shipped.
- The implementation names each dependency of the package (the archive engine, the media library, the platform libraries) and in one sentence
  says what its licence requires of the product and what would change the answer (editing the library files, a static build,
  shipping in another form).

## Н3 Pass

```
build (per architecture): platform processes + VMS executables + manifests and pages + obsd (patches 01–07)
  + model weights (optional part) + vendor key
  + sample files of the subsystems and role files + notices of the dependencies → package with BUILD
delivery: push or pull → install.sh server by server (P/02.4 Н1.7) → builds visible in /schema
```

## Н4 Refusals

| Cause | Outcome | Who sees it and how | What the caller does |
|---|---|---|---|
| `obsd` without patch 07 | the recorder refuses on connection | the recording status, the log | build with patches 01–07 |
| a server lags behind (an old build) | a live process with a `build` ≠ the new one (`processes.*`, `live: true`) | `/schema`, `/servers` | deliver the package |
| an old build on a new schema | does not start (visibly) | the log | upgrade the server (P/02.4 Н1.7 `rule`) |

## Implementation decides

The implementation MUST name in its description: the **package format** and its build for each architecture; the **dependencies** with
their licences and the sentence «what it requires» (Н1.4); the **delivery method** for its site (Н1.3); **where the binary file of the engine `obsd` is taken from** and its `sha256`; the **path of the weights file** in the package (`ASSIST_MODEL_WEIGHTS`).
