# V/09 Развёртывание VMS — инструкция для реализации

Что реализация установки VMS делает и как проверить результат. Канон — нормы глав `09.K-deploy.norms.md`; эта инструкция их
не дополняет. Платформа — выгрузка `cammeta-specs` `d3f8e05`.

## Входы и их приоритет

- Канон — нормы глав `09.K-deploy.norms.md` (Н1–Н5 каждой главы; адреса `V/09.K Н…`).
- [Лекция](../09-deploy.md) объясняет причины; платформа — нормы выгрузки пина VMS по адресам `P/…` (их правит не VMS).

Противоречие записать с местом и контрпримером (раздел «При расхождении»); произвольный отказ не заменяет
отсутствующую норму. Устройство кода остаётся реализации в рамках канона.

## Что создать — результат по главам

| Глава | Что есть у реализации | Проверка |
|---|---|---|
| V/09.1 | источник: девять манифестов (`backend` — после приращения B), страницы рядом с манифестами, `worker.exec`, часть `obsd`, ключ вендора; `W2C_DEPLOYMENT=vms`; порядок `manifest put` (`requests` и виды токенов; `near` — не ребро, одним проходом); после установки — тома части смонтированы, том сервера объявлен строкой `rec/volumes` | чтением; установка на стенде |
| V/09.2 | пример файла каждой подсистемы с ключами уроков 01–07, 10, 11; строки площадки `SERVER_NAME`, `LABELS`, `CONSOLE_ORIGINS`; файлы девяти ролей в пакете, проходящие правило памяти (`recworker` ≥ 1951 МБ при `CAPACITY=50`), `CAPACITY` по правилу и названному пределу нагрузки | чтением; установка на стенде |
| V/09.3 | один пакет на все виды кластеров (различие — свойство сервера, `BUILD`); состав — исполняемые, байты канона, `obsd` с патчами 01–07, медиабиблиотека из пакетов ОС, файлы ролей; доставка толканием или вытягиванием; уведомления и фраза о лицензии каждой зависимости | чтением; установка на стенде |
| V/09.4 | здоровье — отказ (`/<sub>/unplaceable`, фазы «отказ» владельцев, `workers_live`), ряд `console.running` — диагностика; «архив пополняется» — `recordings_running`, `writer` ok, `volume_error` 0, `archive_failure` нет (`last_frame_age` — подсказка) | чтением; установка на стенде |

Установка — механизм платформы (P/02.4): реализация VMS даёт источник и значения, а не свой установщик.

## Ловушки

| Норма | Возможная ошибка | Как сохранить поведение |
|---|---|---|
| V/09.4 Н1.1 | судить здоровье по разнице счётов | здоровье — отказ (фазы «отказ», `/unplaceable`, `workers_live`); счёты — диагностика |
| V/09.2 Н1.3 | выводить `CAPACITY` из `unit_mb` | `CAPACITY` — предел нагрузки, названный реализацией; файл роли — `default` манифеста |
| V/09.1 Н1.2 | ставить установку под основу имён, отличную от `vms` | `W2C_DEPLOYMENT=vms`: каталоги долей и группа клиентов `obsd` от неё зависят |

## Готово, когда

Примеры файлов подсистем и ролей проходят договор файла окружения и правило памяти; установка на стенде реализации даёт
здоровье главы 4; пункты чеклистов, отмеченные «чтением», подтверждены описанием реализации. Проверка установщика
платформы её не подменяет.

## При расхождении

Порядок источников: нормы главы → OpenAPI → приёмка и векторы → лекция; платформа — нормы выгрузки пина VMS.
Норма молчит или противоречит себе — вопрос «Спецификации VMS» с местом, контрпримером и предложением; норма
платформы — через «Архитектора». Дефект приёмки (ожидание против нормы) — тот же маршрут; закрытое решение
вносится в канон, а не остаётся в этой инструкции.
