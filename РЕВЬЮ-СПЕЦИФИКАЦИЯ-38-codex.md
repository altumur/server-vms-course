## Урок 2

### R38-02 — отсутствие unit разрешено общим правилом, но его умолчания не определены

**Серьёзность: существенная.** Места: `М10_Platform/spec/02-the-spec-and-the-strict-loader.norms.md:47`, `:54`; `02-the-spec-and-the-strict-loader.api.openapi.yaml:38`; зависимость — `03-units-slots-epochs-lease.norms.md:17`, `:113`.

Н1.2 при отсутствии раздела отсылает к умолчанию урока-владельца; без умолчания обязательны name и placement.capacity.default. Для целого отсутствующего `unit` владелец 3 не задаёт ни rows, ни выбор numeric/named, ни отдельную форму «подсистема без единиц». При этом rows обязан удовлетворять непустой грамматике, а GET /spec требует поля rows и id.

**Минимальный вход:**

```yaml
name: probe
placement: {capacity: {default: 1}}
```

Других спек и полевых ссылок здесь нет. Разделы отсутствуют по разрешённому правилу Н1.2, обязательные значения заданы. Однако из канона нельзя получить ни семейство единиц, ни значение id для опубликованного GET /spec. Произвольное rows="units"/id="numeric", отказ из-за unit или особое поведение без единиц были бы дополнительными решениями реализации.

**Последствие:** два генератора получают разные обязательность, представление спеки и поверхность операций из одного допустимого документа. Для этого случая нет однозначного вердикта/нормативного исхода. Проба `unit-absent.subsystem.yaml` подтверждает только структуру примера, не вердикт реального загрузчика.

**Основание:** ADR-0012 о строгой загрузке и безопасных умолчаниях; ADR-0080 о полном языконезависимом каноне; Н1.2/Н2 урока 2 и владелец unit в уроке 3.

**Рекомендация:** явно определить обязательность unit/rows/id либо точные умолчания и форму работы при отсутствии unit, затем закрепить случай приёмкой.

**Происхождение:** была раньше. На `47cc741e845eaa83f33f834cfbf05892a9154c58` то же правило отсутствующего раздела и те же две формы id; минимальный пример оставляет те же вопросы. Первоначальный коммит не устанавливался; `provenance.stdout`.

## Урок 8

### R38-03 — UnitRef не представляет отметку допустимого экземпляра консоли

**Серьёзность: существенная.** Места: `М10_Platform/spec/08-events-resource-requests.norms.md:75`, `:86`, `:92`; `08-events-resource-requests.api.openapi.yaml:853`; зависимость — `11-the-platform-on-a-box-and-a-cluster.norms.md:62`.

Экземпляр — непустая уникальная строка; INSTANCE_ID может заменить стандартное значение. UnitRef прямо включает console/<экземпляр>, но его pattern запрещает запятую во второй части, перенося на экземпляр ограничение идентификатора единицы. Канон такого ограничения INSTANCE_ID не вводит.

**Контрпример:** выбрать ранее не использованный INSTANCE_ID=`node,a` в объявленном файловом профиле, который допускает этот короткий ASCII-компонент и инъективно отображает такие имена. Этот случай не нарушает ограничения представимости ФС. Сделать разрешённый `POST /marks {"unit":"testsub/c1","note":"x"}`. Н1 требует дерево console/node,a, а ответ индекса — `unit: "console/node,a"`. Корректные id события и bucket имеют форму Н1, но EventRow отвергается только по unit. Близкий INSTANCE_ID=`node-a` проходит.

**Проверка и последствие:** полный пример EventRow проверен Draft202012Validator; отдельно нативный ECMAScript RegExp подтвердил `[true,false]` для двух UnitRef. Это проба документа, не HTTP. Стандартный клиент по опубликованной схеме отвергает допустимую отметку; фильтр events по этой же ссылке также не представим схемой.

**Основание:** ADR-0080 о согласованности формы и дверей; ADR-0082 дополнения 17/24/29; собственные Н1.2/Н2 урока 8 и окружение урока 11. Файловое сужение из дополнения 29 само по себе допустимо и данным примером не обходится.

**Рекомендация:** согласовать область экземпляров и ссылок событий; если выбран более узкий профиль INSTANCE_ID, назвать его явно до старта и применять ко всем источникам значения.

**Происхождение:** была раньше: тот же UnitRef, разрешённый экземпляр и результат индекса были на `47cc741e…`; прежняя файловая область также допускала короткое имя с запятой. Первоначальный коммит не устанавливался. Свидетельства: `counterexamples-final.stdout`, `probe-ecma-unitref.json`, `provenance.stdout`.

### R38-04 — settle не участвует в снятии отвеченной строки и расходится с приёмкой

**Серьёзность: блокер.** Места: `М10_Platform/spec/08-events-resource-requests.norms.md:195`, `:497`; `Source/tests/testdata/acceptance/М10_Platform/08/README.md:28`; `08/scenarios.tsv:34` и `:35`.

Н1.5 задаёт settle как секунды до снятия отвеченной строки, умолчание 60. Н3 clear каждые 2 с снимает строку по fetched и подтверждённой метке; ни settle, ни начало его отсчёта в проходе не участвуют. У testsub settle не указан; README требует обычные параметры без ускорения.

**Контрпример:** обычная просьба сценария 05 быстро получает performed и fetched; шаг 6 сразу наблюдает метку. Следующий clear наступает через 2 с. По Н3 строка снимается тогда, по объявленной задержке Н1 — спустя 60 с после ответа. Шаг 7 требует увидеть отсутствие максимум через 40 с после немедленно успешного шага 6: исполнение с задержкой 60 с падает на допустимом быстром расписании.

**Последствие:** реализация, использующая опубликованный параметр задержки, и реализация буквального clear имеют несовместимое поведение; приёмка выбирает второе, не согласовав норму. Если settle должен ограничивать другой объект или означать иной срок, это не следует из текущего определения. Ограниченная временная трасса 0/2/40/60 в `counterexamples-final.stdout` показывает расхождение; реальные таймеры не запускались.

**Основание:** ADR-0080 о согласованном нормативном проходе и приёмке; Н1.5/Н3/Н5 урока 8. Правило asked по ttl/settle — другой объект и не задаёт задержку строки requests.

**Рекомендация:** определить единственный смысл и точку отсчёта settle и согласовать с ними clear, README и ожидание шага 05/7.

**Происхождение:** была раньше: на `47cc741e…` имеются те же settle=60 по умолчанию, clear без этого условия и тот же сценарный срок. Первоначальный коммит не устанавливался; `provenance.stdout` и сохранённое сравнение срезов.

### R38-05 — жнец требует метку у дозаписи, для которой ADR-0054 прямо запрещает её

**Серьёзность: блокер.** Места: `М10_Platform/spec/08-events-resource-requests.norms.md:403`, `:500`, `:508`; первичный канон — `decisions/0054-метка-просьбы-итог-у-каждой-просьбы.md:99`; конкретная допустимая форма — `Source/vms/rec.subsystem.yaml`, раздел requests.

Дополнение ADR-0054 от 2026-10-11 отдельно устанавливает: дозапись rec/<unit>-<from>-<to> заканчивается fetched, строку снимает консоль, метки нет; повтор решается по данным. Н3 урока 8 разрешает clear и освобождение rid из asked только после подтверждённой терминальной метки. Вводная таблицы исключает free без unit и действия elsewhere, но дозапись имеет unit и в rec elsewhere перечислен только record.

**Контрпример:** каталог cam/rec без недопустимого live; есть допустимая запись rec/recordings/7. Подать по схеме rec тело `{"unit":"7","from":1,"to":2}` с новым ключом. Получается rid `7-1-2`, не действие record. Держатель завершает дозапись по ADR, сообщает fetched, метки не создаёт. Все чтения успешны; отсутствие метки достоверно. Н3 clear оставляет строку, а правило asked не освобождает резерв. Создание метки ради этих условий нарушило бы прямо названное исключение ADR.

**Последствие:** допустимая завершённая дозапись не имеет согласованного способа очистки и освобождения per_person; обещание «метка у каждой просьбы» неверно распространяется на исключённый класс. Это противоречие двух текстовых канонов, а не заявление о невнедрённом коде rec. Булева трасса clear с fetched и отсутствующей меткой сохранена в `extra-counterexamples.stdout`.

**Основание:** ADR-0054, дополнение 2026-10-11, строки 99–106; ADR-0082 доп. 17 объявляет таблицу состояний выражением этого ADR; ADR-0080 требует не заменять решение архитектурным предложением ревьювера.

**Рекомендация:** явно отразить исключение дозаписи и её способ завершения/очистки/освобождения учёта в применимости Н1/Н3/чеклиста и отдельном приёмочном случае.

**Происхождение:** была раньше: на `47cc741e…` одновременно присутствуют исключение ADR, общий clear с обязательной меткой и та же форма rec. Первоначальный коммит не устанавливался; `provenance.stdout`.

## Межурочные причины

### R38-06 — один GET /v1/list одновременно запрещает и требует 403 личности

**Серьёзность: блокер.** Места: `М10_Platform/spec/01-storage.norms.md:142`; `01-storage.api.openapi.yaml:18`; `06-rights.norms.md:189`; `06-rights.api.openapi.yaml:53`. Затронуты уроки 1 и 6.

Урок 1 прямо утверждает отсутствие 400/403 у перечисления; его закрытый контракт имеет только 200/404/503. Урок 6 проверяет личность до list, требует 403 при заголовке пересылки на ролевом сокете и включает этот код в контракт того же GET /v1/list.

**Контрпример:** загружен файл прав, клиент подключается к сокету testsubworker и делает `GET /v1/list?prefix=acc/` с заголовком роли, имя которого объявлено в профиле развёртывания. Н3/6 возвращает 403 до перечисления; Н3/1 и его OpenAPI этот исход запрещают. Аналогично действует недоверенная пересылка. Само отсутствие права read здесь не проверяется и не является причиной 403.

**Последствие:** нельзя исполнить оба опубликованных контракта одной двери. Клиент, построенный по владельцу 1, не имеет требуемой ветви отказа; реализация буквального «нет 403» обходила бы проверку личности 6.

**Основание:** ADR-0080 доп. 2026-10-13 о закрытом списке кодов; ADR-0082 доп. 14/18 о личности до list и согласовании копий с владельцем 1; М10/6-05/09. Это не предложение ограничить list правом чтения.

**Рекомендация:** отделить отсутствие проверки read у list от обязательного отказа личности и согласовать владельца 1, Н4 и изложение двери в 6.

## Записка модуля

### R38-07 — карта модуля по-прежнему описывает переезд как три записи

**Серьёзность: мелкая.** Места: `М10_Platform/module-design.md:36`; владелец — `spec/04-the-controller-and-placement.norms.md:287` и `:296`, М10/4-12/22.

**Контрпример:** перенос одной единицы с w-1 на пустой w-2 при уже взятом turn и idle intent. Даже без захвата/продления turn требуются отдельные записи: active intent, снятие с w-1, placement на w-2, назначение w-2, idle intent. Это минимум пять, не три. Составная группа/восстановление могут потребовать больше.

**Последствие:** численная характеристика в карте урока устарела относительно описываемого протокола и скрывает сохраняемую незавершённую фазу. Нормы 4 из-за этого не предлагается переписывать.

**Основание:** ADR-0080 доп. 8 об общем допуске и сохраняемом intent; действующий Н3/4; согласованность module-design с комплектом уроков.

**Рекомендация:** заменить «три записи» описанием порядка через сохраняемый intent либо ссылкой на актуального владельца.

**Происхождение:** была раньше: такая же строка карты и тот же пятифазный протокол есть на `47cc741e…`; первоначальный коммит не устанавливался. Трасса приведена в `extra-counterexamples.stdout`, сравнение — `provenance.stdout`.

## Lesson-spec

### R38-08 — структурный CLI принимает не-ASCII цифру в HTTP-коде ожидания

**Серьёзность: существенная.** Места: `.claude/skills/lesson-spec/scripts/check_spec.py:353`; заявленная проверка формата — `references/validation.md`, строка таблицы scenarios.tsv; контрольный поддерживаемый формат — `scripts/test_check_spec.py:52`.

В Python выражение `[1-5]\d\d` принимает Unicode-цифры в двух последних позициях. Код HTTP состоит из трёх ASCII-цифр, поэтому текст `2٢0` с U+0662 не является допустимым кодом ожидания. Это дефект обещанной механической проверки, не требование поддержать TSV03–11 или проверять семантику запроса.

**Воспроизведение:** в отдельном минимальном комплекте из собственного тестового шаблона навыка заменить только строку scenarios.tsv на:

```text
01-example<TAB>1<TAB>GET /example<TAB>2٢0 {}
```

Настоящий CLI возвращает exit 0 и `PASS structural checks only`. Близкий `200 {}` также даёт exit 0; `600 {}` корректно даёт exit 1 с `expected HTTP status and JSON body`. Эти три запуска действительно выполнены в прогоне 38; точные argv, cwd, exit code и оба потока — `probe-cli-control-ascii.json`, `probe-cli-unicode-digit.json`, `probe-cli-control-invalid.json`; воспроизводящий их генератор — `probes.py`.

**Последствие:** испорченный ожидаемый HTTP-код получает структурный PASS в поддерживаемом формате 01/02. Ограничение «семантика вручную» эту лексическую проверку не исключает.

**Основание:** ADR-0080 доп. 2026-10-15 (3): неподдержанная/неполная проверка не даёт зелёного результата; собственное обещание validation.md проверять HTTP/ASSERT и JSON ожиданий.

**Рекомендация:** использовать ASCII-грамматику кода и добавить отрицательный тест с Unicode-цифрой рядом с положительным ASCII-контролем.

**Происхождение:** была раньше: то же выражение находится на строке 316 версии `47cc741e…`; изменение YAML-резолверов после 37 эту ветвь не меняло. Контрпример применим к прежней ветви без изменения её условий; `provenance.stdout`.
