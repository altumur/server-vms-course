## R91-D9-01 — существенная: нет сервера назначения заказа у нового места без сервера и держателя

**Место:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:436–438`, доп. (9), п. 6. Зависимости: `Platform/04-controller/spec/04-controller.norms.md:138–145,815–881`; `Platform/03-worker/spec/03.2-worker.norms.md:60–65,604–609`.

**Точные цитаты ADR:** «Связывающая строка с пустым `server_field` — строгость по держателю места, без сервера». Следом: «при `grows` по месту без держателя — заказ воркера на сервер места».

**Допустимый контрпример.** Подсистема `testsub2`, таблица мест `shelves`, единица `u` с `home: bk`. Существенные параметры:

```yaml
placement:
  capacity: {default: 1}
  grows: true
  servers: distinct
  place_by: shelf
  places:
    table: shelves
    where: {enabled: true}
    server_field: server
    lease: strict
  affinity:
    field: home
    table: shelves
    server_field: server
    strict: {kind: backup, exclusive: true}
```

Поле `home` объявлено строкой-ссылкой на `shelves`; у таблицы объявлены поля `server` (строка), `kind` (строка), `enabled` (булево). Новая строка `shelves/bk` содержит `{server: "", kind: backup, enabled: true}`. Строки удержания `holds/bk` ещё нет — это первое взятие, не пропавший пульс старого держателя.

На `srv-a` и `srv-b` роль установлена, базовые воркеры живы и держат другие места `p1`, `p2`. Их ёмкость 1 полностью занята. Метки подходят; ресурсы доступны; дренажа, вывода, подавления после отказа подъёма нет. У обоих серверов `want=1`, `room=1`; процессов в пути и живых воркеров без места нет. Обычный порядок P/04 имеет двух допустимых кандидатов для одного нового процесса, первым будет `srv-a` (`04-controller.norms.md:867–875`). Новый процесс мог бы взять переносимое `bk`.

Но у `bk` нет ни собственного сервера, ни держателя, по которому можно вывести сервер. Два новых предложения п. 6 охватывают это состояние, не определяя, что означает «на сервер места». Не названо ни наследование общего порядка кандидатов, ни отказ/ожидание с причиной. Пустой `server_field` здесь не ошибка данных: новая первая фраза прямо вводит этот случай, а P/03.2 допускает место не своей/любой коробки.

**Основание и последствия.** P/04 Н3 заказывает процесс строкой `<sub>/want/<сервер>` на конкретном сервере (строки 817–818); общий набор кандидатов и порядок определены. Новое сужение по серверу места должно иметь ветвь на всей явно допущенной области п. 6. При переносе решения автор вынужден самостоятельно решить, увеличивать ли `want/srv-a` общим порядком либо не заказывать до появления держателя. Во втором варианте первое взятие места может остаться недостижимым, хотя подходящая мощность есть. Это пропущенная ветвь решения; проба не утверждает, что настоящий контроллер уже зависает.

**Проба.** `place-model.py`, результат `place-model.json`: обычные кандидаты — `[srv-a, srv-b]`, общий выбор — `srv-a`, значение «сервер места» отсутствует. Положительный контроль: при `bk.server=srv-b` адресат вычисляется. Это конечная модель входов и адресата, не запуск контроллера или проверка нового манифеста загрузчиком.

**Вопрос «Архитектору», рекомендация.** При непустом сервере места — выбирать этот сервер с сохранением общих условий допуска, room и базового. При пустом сервере и отсутствии держателя — общий порядок кандидатов P/04 либо явно выбранное ограничение профиля и определённое ожидание. Предпочтителен первый вариант: он позволяет впервые взять переносимое место без привязки к коробке. В приёмку включить новый `holds/bk` без истории; существующий держатель не проверяет эту ветвь.

**Происхождение.** Сочетание введено доп. (9) коммитом `59a606a141c27ff6e03ed30b18d0244a77a70aad`: одновременно добавлены строгость при пустом сервере и направленный заказ по месту. Дельта до/после — `decision-delta.json`. Ранее в рассматриваемом ADR этой комбинации новых предписаний не было; прежний общий алгоритм P/04 сам по себе не объявляется новой находкой.

## П. 5 и остальной п. 6

**Открытие секретов места.** Добавленный момент — взятие места — отвечает вопросу запроса. AAD остаётся формулой договора, не буквальным AAD какой-либо единицы: для `testsub2/shelves/bk` и `access_secret` это UTF-8 ключа этой строки + `0x00` + `/access_secret` (`Platform/common/contracts/sealing.md:25,37–41`). Ключ строки `testsub2/tallies/u` дал бы другой контекст. `Sealed` не разрешает взять место; причина относится к месту, не останавливает произвольную единицу как ошибку её секрета. Открытое значение не публикуется в пульсе/журнале. Пульс уже именует удерживаемое место через поле из `place_by` (P/03.4 Н1.1); выражение добавленной диагностики предстоит внести в нормы. Криптографическое открытие и реальное кольцо не проверялись.

**Исключительность.** Фильтр для чужих единиц не отменяет остальные ограничения P/04; пустой итоговый набор означает ожидание, не обход фильтра ради размещения. При переносе метаключ `exclusive` нужно отделить от предиката полей строки: нынешний источник `02.1-installer.form.yaml:479` и ссылка Н1.4 (`02.1-installer.references.tsv:48`) трактуют ключи `strict` как поля таблицы. Их будущая правка следует из нового решения; отсутствие этой правки на срезе ADR отдельно не засчитано дефектом. Заказ на коробке камеры не снимает условия установленной роли, живого базового, room и других условий P/04. Новая причина здесь — R91-D9-01.
