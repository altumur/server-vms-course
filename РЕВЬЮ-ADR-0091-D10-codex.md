## Закрытие собственной находки дополнения (9)

**R91-D9-01 — закрыто явным ограничением.** Предыдущая находка относилась к заказу воркера для связывающего места с пустым полем сервера и без держателя: дополнение (9) разрешало такое место, но предписывало заказать процесс «на сервер места», которого в этом состоянии нет. Соответствие собственной находке подтверждает строка 22 авторского разбора: «Codex (сервер заказа) … п. 3».

Исправление находится в `decisions/0091-механизмы-платформы-по-запросам-vms.md:450–451`:

> «место с пустым `server_field` без держателя заказа воркера не вызывает — сервера нет, место ждёт держателя».

Повторная проверка исходной ветви по тексту: в строке места `bk` поле сервера пусто, держателя нет, связанная единица ждёт; `grows: true`, на двух серверах есть базовые воркеры и свободный `room`. Дополнение (10) теперь однозначно запрещает прирост заказа **из-за этого места**: ни первый, ни второй сервер не выбирается как выдуманный «сервер места». Если держатель появится независимо, применяется оставленное дополнением (9) правило связывания по держателю. Гарантии автоматического появления первого держателя здесь больше нет, и требовать её поверх принятого ограничения нельзя.

Это закрытие неоднозначной ветви выбором ожидания, а не доказательство прогресса во всех конфигурациях. Новая причина под другим ID не создаётся.

## Проверка новых уточнений

| Пункт дополнения (10) | Сверка и результат |
|---|---|
| 1. `affinity.exclusive` | Строки 444–446 сохраняют `strict` предикатом полей таблицы. Это согласуется с P/04 Н1.3, строка 143: «каждое поле `strict` равно значению или входит в список значений». Метаданные исключительности больше не требуют наличия поля `exclusive` в строке места. Отсутствие `strict` получает явный отказ загрузчика. |
| 2. Исключительность воркера | Строки 447–449 ограничивают и взятие других мест, и приём посторонних единиц; отдельно исключают ёмкость из нехватки для этих единиц. Поэтому новый фильтр при размещении не оставлен без соответствующего ограничения расчёта роста P/04 Н3, строки 847–860. Механизм CAS и стража своего слота при взятии места P/03.2:604–610 не отменяется. |
| 3. Заказ под место | Ветка без сервера и держателя определена, см. закрытие выше. Для известного отказа открытия секрета выбран запрет заказа с `withheld`, а не попытки исправить секрет увеличением `want`. Базовые условия кандидата P/04:867–880 этим не заменяются. |
| 4. `place_error` и перечитывание | Строки 453–456 вводят отдельное поле причины, индексированное именем места. `place_by` остаётся именем поля из манифеста; его значение по P/03.4:63–64 — имя удерживаемого места либо пустая строка. Ошибка открытия секрета не подменяет это имя и не записывается как статус посторонней единицы. Изменение строки держимого места требует нового чтения и открытия, а не вечного использования прежнего открытого значения. Действующие правила потери удержания и закрытия писателя P/03.2:610–634 сохраняются. |
| 5. Привязка | Для нескольких адресов `SERVER_NAME` выбран весь набор слушателей; явный HOST вне набора получает код 2; временная ошибка разрешения отделена от неверной конфигурации ожиданием с повтором. Случаи нескольких адресов и временного отказа DNS в дополнении (9) больше не оставлены без указанного исхода. |
| 6. Проверка и перенос `rec` | Пункт не объявляет стенд способным проверить всё: сценарии назначены там, где он позволяет, остальное — векторами и чтением. Место внесения `affinity.exclusive` в `rec` и ответственный названы. Это план проверки и переноса, не уже выполненная приёмка. |

Для проверки секрета не использовался контрпример с несогласованной ротацией колец как с гарантированно рабочим состоянием: P/06.2:264–269 и 379–390 явно задаёт обслуживание одним оператором с остановленными обычными записями и перезапуском держателей до перезапечатывания.

Старые формы P/04 и пульса ещё не содержат всех вводимых ключей. Само это не посчитано новой находкой: предмет — решение, уточняющее предстоящую правку норм; их отсутствие в ещё не исполненном переносе не доказывает противоречия решения.
