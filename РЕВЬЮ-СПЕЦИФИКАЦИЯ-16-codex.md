## Урок 1 — канон, инструкция и контракт

### R16-01 — Инструкция делает внутренний API обязательным, хотя канон оставляет его реализации

**Серьёзность: блокер.** Места: I:26, I:29; N:214, М10/1-21.

В Н5 прямо сказано: «внутренний API — выбор реализации». Инструкция «Что создать» требует языковой интерфейс ядра с типизированными значениями отказов, запрещает строки и общие исключения, а для проверки прав задаёт конкретную точку расширения `authorize(caller, action, key) → allow | deny`. Эти требования не представлены как примеры возможной реализации.

Реализация с той же семантикой и HTTP-ответами Н4, но с другим внутренним представлением отказов или другим интерфейсом проверки прав, соответствует канону и одновременно нарушает инструкцию. Приоритет `norms.md`, объявленный в I:13, позволяет выбрать сторону при споре, но не устраняет противоречие в самом задании агенту. Отдельных id и проверок для этих ограничений внутреннего API в чеклисте нет.

Правило: ADR-0080, дополнение 2026-10-15 — канон находится в `spec/norms.md`, README задаёт инструкцию реализации по нему; Н5 и М10/1-21 сохраняют выбор внутреннего API.

Рекомендация: обозначить конкретные внутренние интерфейсы и представления отказов как примеры, сохранив обязательными требования канона к наблюдаемому поведению.

### R16-02 — Схема запроса не различает правила `items` для `put` и `delete`

**Серьёзность: существенная.** Места: O:60–66; N:173; I:59; М10/1-12; A/scenarios.tsv:74, сценарий `16-items`, шаг 3.

У `Cmd` обязательны только `op` и `key`; свойство `items` имеет одну безусловную схему объекта строк. Поэтому структурно допустим `{"op":"put","key":"acc/example"}` без `items`, хотя Н4 и сценарий 16, шаг 3 требуют `400 badrequest`. Обратный пример — `{"op":"delete","key":"acc/example","items":42}`: схема отвергает его по типу `items`, хотя комментарий к этой же схеме и I:59 говорят, что у удаления поле не читается и его передача не является отказом. Н4 ограничивает проверку объекта строк случаем `put`.

Комментарий описывает различие операций, но загрузчик схемы не получает этого ограничения. Автоматическая проверка или генерация по самостоятельному OpenAPI-файлу расходится с текстом урока. Это схема **запроса**, поэтому находка не относится к отложенному долгу по телам ответов.

Правило: ADR-0080, дополнение 2026-10-15 — отдельный OpenAPI является контрактом двери; Н2, Н4 и М10/1-12 должны задавать согласованную форму запроса.

Рекомендация: выразить в схеме `Cmd` существующее различие правил `items` для двух операций и сверить её на обоих приведённых входах.

### R16-03 — Игнорирование `items` при удалении не проверяется приёмкой

**Серьёзность: существенная.** Места: O:66; I:59; N:139, N:173, М10/1-06 и М10/1-12; A/scenarios.tsv:17–23 (`06-delete`), A/scenarios.tsv:72–76 (`16-items`).

При выделении контракта в отдельный файл явно записано: у `delete` поле `items` не читается; инструкция отдельно предупреждает, что строгий разбор не должен отвергать такое поле. Однако во всей приёмке урока каждый запрос `delete` отправляется без `items`. Сценарий 16 проверяет форму `items` только у `put`.

Реализация, которая отвергает `delete` с любым переданным `items` либо проверяет его как содержимое `put`, проходит имеющиеся сценарии. Указанное свойство удаления не помечено как проверяемое чтением; проверить его можно через уже описанную дверь. Исправление одной схемы из R16-02 не добавит проверку поведения реализации.

Правило: ADR-0080, дополнение 3 п. 4 и дополнение 6 п. 3 — норма покрывается сценарием либо явно отнесена к проверке чтением с причиной.

Рекомендация: добавить удаление с `items`, не соответствующим форме содержимого `put`, и проверку успешного удаления последующим чтением строки.

## Урок 1 — лекция для человека

### R16-04 — Объяснение стража требует ещё не введённых воркеров, слотов и аренды

**Серьёзность: мелкая.** Места: L:5, L:34, L:80–102; `М10_Platform/module-design.md`:24.

В предварительных знаниях сказано, что из курса ничего не требуется. Строка и условия записи введены, но воркер, слот, владение единицей и аренда до примера не объяснены. Вместо объяснения стража на уже знакомых строках раздел начинает историю «воркер A держит слот», затем использует истечение аренды, захват другим воркером и потерю права писать. Упоминание путей `testsub/slots/...` в L:34 не определяет эти понятия.

Это именно развёрнутая история из поздних уроков, которую правило «Что знает читатель» запрещает помещать в первый урок; допустимой короткой отсылкой к последующему уроку она не является. Замечание относится к порядку объяснения, а не к архитектуре стража.

Правило: `module-design.md`, строка «Что знает читатель» — повествование опирается только на уже введённое; ADR-0080, дополнение 2026-10-15 сохраняет лекцию как объяснение для человека.

Рекомендация: объяснить проверку стража через две уже введённые строки, оставив историю о воркере и аренде соответствующему позднему уроку.

### R16-05 — Лекция обещает более сильную память повторов, чем канон

**Серьёзность: мелкая.** Места: L:124; N:162; М10/1-11.

Лекция говорит: «не меньше двух минут и не меньше 50 000 записей». Это читается как два самостоятельных нижних предела: в частности, до истечения двух минут запись ещё помнят независимо от числа последующих записей. В Н3 временная гарантия условна: она действует, **пока** после первого применения было меньше 50 000 записей с идентификатором.

Например, после более чем 50 000 таких записей за десять секунд обязательная область гарантии Н3 уже закончилась, а безусловное обещание лекции ещё действует. Ненормативный статус лекции разрешает выбрать канон, но объяснение поведения клиента остаётся неверным.

Правило: ADR-0080, дополнение 2026-10-15 — лекция объясняет канон `norms.md`; Н3 «Повтор по идентификатору» и М10/1-11 задают предел гарантии.

Рекомендация: передать в лекции условную связь времени и числа последующих записей, сославшись на Н3 и М10/1-11.

### R16-06 — Третий исход записи ошибочно представлен как свойство только группы

**Серьёзность: мелкая.** Места: L:112–118; N:181, N:183; М10/1-14.

Начало объяснения противопоставляет одной коробке с двумя исходами группу с третьим, неизвестным исходом. Но Н4 прямо задаёт `503 ambiguous` и на одной коробке: строка уже опубликована, а барьер долговечности отказал. Кроме того, потерянный или нечитаемый ответ на запись означает для вызывающего `ambiguous` независимо от наличия группы.

Лекция ниже, в L:145, уже правильно описывает обрыв ответа без ограничения группой. Поэтому её собственные объяснения тоже не согласованы. Начальный тезис может привести читателя к неверному выводу, что локальному варианту не нужны правила обработки неопределённого результата записи.

Правило: ADR-0080, дополнение 2026-10-15 — объяснение следует канону; закрытая таблица Н4 и М10/1-14 различают сделанную, несделанную и неизвестную запись для применимых условий, включая одну коробку.

Рекомендация: объяснить неизвестный для вызывающего исход и для одной коробки, используя уже заданные в Н4 случаи.

## Проверки формы и приёмки

Новая раскладка из четырёх файлов присутствует. В каноне сохранены Н0–Н5, «Решает реализация», чеклист и «Соответствие прежним урокам». Все 23 id уникальны и совпадают с прежним однофайловым уроком; у пяти проходов Н3 есть «Гонки». В лекции присутствуют цели, предварительные знания и не-цели; README агенту содержит предусмотренные новой формой разделы.

Самостоятельный OpenAPI-файл успешно загружен как YAML системным Ruby; все 26 локальных `$ref` разрешаются. Списки кодов ответов трёх маршрутов сопоставлены с Н4: самостоятельной дыры в списках кодов не установлено. Проверка формы запроса выявила R16-02. Это не полный прогон линтера OpenAPI или валидатора JSON Schema.

В приёмке 22 сценария и 99 шагов; все сценарии названы в Н5, таблица имеет четыре столбца, номера шагов последовательны. README задаёт изоляцию сценариев, связывание переменных, `ASSERT`, `@big` и сравнение ответа; шаги читаются без обращения к коду. Каталог приёмки не изменился относительно среза прогона 15. Новая явно сформулированная ветвь удаления при этом осталась без сценария — R16-03. Локальные файловые ссылки из трёх Markdown-файлов урока разрешаются.

Структурные проверки и чтение сценариев не означают, что какая-либо реализация прошла приёмку. Найденные расхождения лекции не превращены в новые нормативные требования; поэтому R16-04–06 оценены как мелкие замечания к объяснению.

## Итог

**6 находок: 1 блокер, 2 существенные, 3 мелкие.**

Три самые важные:

1. **R16-01:** агент получает обязательные внутренние интерфейсы вопреки выбору, оставленному каноном.
2. **R16-02:** машинная схема `Cmd` не отражает разные правила `items` для `put` и `delete`.
3. **R16-03:** приёмка не обнаруживает отказ при удалении с игнорируемым полем `items`.
