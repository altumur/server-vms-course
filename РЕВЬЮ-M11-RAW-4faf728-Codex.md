## P2 № 1. `@raw` внутри обычного JSON меняет его байты и тип

**Место:** `runner/m11stand.py:758`, `raw_request`, вызов из `Run._step:1343`.

```python
raw = re.search(r"(?:^| )@raw (.*)$", req, re.S)
```

Поиск идёт по всей строке вместо позиции начала тела. Буквальный ` @raw ` внутри JSON-строки принимается за директиву. Префикс уже содержит начало JSON, поэтому `split_request` возвращает его отдельным словом; `Bench.door` отправляет этот неполный префикс как тело и игнорирует добавленное второе слово.

**Выполненный контрпример без директивы @raw:**

```text
token m2 testsubworker POST /tokens/testsub/tally {"request_id": "j1", "ref": "value @raw tail"}
```

На базе в Unix-сокет уходят исходные **46 байт**, Content-Type `application/json`, Content-Length 46, JSON читается. На новой вершине — **34 байта** `{"request_id": "j1", "ref": "value`, Content-Type `application/octet-stream`, Content-Length 34; JSON повреждён. Это фактическая запись HTTP через `Run.step → Bench.door → HttpDoor`, не только разбор функции. Семантическая допустимость ref не разрешает раннеру менять входные байты проверки.

**Нарушение:** общий README приёмок, строка `@raw` задаёт явный маркер тела; обычное JSON-тело остаётся последним словом целиком. Заявление серии «без @raw обычное деление прежнее» не выполнено. Ожидания формы/смысла тела начинают судить другой запрос.

**Рекомендация:** выделять позицию тела после адреса двери, метода и пути; распознавать `@raw ` только в её начале. JSON-тело не искать и не разбирать ради маркера. Контроль `json_literal_marker` должен сохранить исходные 46 байт и JSON Content-Type.
