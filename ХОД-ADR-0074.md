## Ответ Архитектора

Обе находки разобраны в дополнении 3 ADR-0074 (`9abd26c8`, отметка `d0c3a5a7`):

1. Обычный CAS строки не отсекает запоздавшего владельца слота. Принято атомарное `guard: {key, index}`
   для `put`/`delete`, отдельный HTTP 412, одинаковая семантика всех Variables и двери без голоса;
   общий метод Worker проверяет свой экземпляр и передаёт индекс слота. Неатомарного запасного пути нет.
2. Отчёт на прежних путях позволял читать `[new, old]` при неизменной метке. Принят один неизменяемый объект
   `domain/members/<член>/reports/<seq>` с исходными байтами подписанного тела, затем атомарная метка `reported`;
   читатель фиксирует поколение. Держатель сохраняет два поколения. Запись и чтение прежних `v/<путь>` уходят.

Исходные предложения с пробами сохранены в inbox рабочей ветки; ответы уже в ADR, повторного решения не требуется.
Обратная совместимость не сохраняется (повторное указание владельца 2026-10-11): без алиасов, двойного чтения
и миграционных fallback. Переносимые книги без `from` — самостоятельный режим, прямо сохранённый ADR-0074.

## Дополнение 3: отсечение и снимки отчётов

Работа продолжается в `codex/course-book-merge`, в main курса публикуются только текстовый отчёт
и вопрос о недостающей форме. Платформу в main не вливать без чтения diff Архитектором.

### Готово в ветке

- `Variables.put/delete(..., guard={key, index})`: FileVariables проверяет guard и CAS под одним файловым
  замком; обе реализации памяти — под замком общего состояния; configstore — в одной команде raft.
  Индекс guard сравнивается как непрозрачное значение. Частичная форма, неизвестные поля, bool/null вместо
  индекса отказаны; явный `guard: null` на проводе тоже отказан, а не превращён в незащищённую запись.
- Guard не даёт прав записи; отдельно проверяется право чтения его строки. `GuardFailed` отличается от
  `Conflict`; точное тело HTTP 412 сохраняется и через дверь без голоса. Условие guard входит в отпечаток
  операции, поэтому потеря ответа не позволяет повтору выполнить другую запись под тем же id.
- `Worker.put_under_slot` проверяет собственный экземпляр, освобождение/истечение слота и запрет работы
  отсечённого воркера, затем передаёт индекс в guard. После 412 не повторяет запись; следующий вызов вновь
  проверяет владение. Льгота `unconfirmed_max` не даёт права публиковать управляющее состояние.
- `domain/reports.py`: приём уже аутентифицированных исходных байтов в неизменяемый `reports/<seq>`, затем
  CAS метки `reported`; меньший/повторный номер отказан. Читатель фиксирует метку и проверяет SHA-256 одного
  тела, без чтения частей из прежних путей. Очистка оставляет два поколения; закреплённые байты читателя
  переживают очистку. Гонка с удалением до чтения тела даёт явную неполноту.

### Что ещё не подключено

`reports.py` пока вызывается тестами. `uplink`, агент, ретранслятор и их читатели ещё не переключены: это
не завершённое исполнение дополнения 3. Существующий путь отчётов не является слоем совместимости нового:
новый путь ещё не включён. При переключении старые части и их чтение удаляются в том же изменении.

Архитектор ответил `71527727`, перенёс решение в ADR (`95ac7710`) и снял вопрос (`93f7b8f8`).
Строка счётчика члена и отдельный объект подписи отклонены. Держатель назначает `rev`, метка содержит
`rev, sha256, signature, sent_at, received_at, via`; ретранслятор отправляет `{relayed: {член: публикация}}`.
Существующий автономный модуль снимков с `seq` ещё предстоит заменить по этому решению; по одному SHA-256
он происхождение не утверждает — подпись проверяет приёмник до вызова хранилища.

При подготовке замены воспроизведён сбой: после сохранения тела 2 и падения до метки метка остаётся 1;
следующий отчёт имеет новые байты и по правилу `rev+1` снова претендует на занятый объект 2.
Проба на `FsObjectStore` завершилась exit 0, подтвердив отказ и сохранность старого отчёта. Она моделирует
выбор номера держателем поверх текущего механизма, а не утверждает, что новый runtime уже реализован.
Вопрос с рекомендацией сериализации приёма и уборки сироты —
`decisions/inbox/2026-10-11-поколение-после-сбоя.md`; изменение правила номеров или перезапись объекта
без решения не введены. Проверки ниже относятся к предыдущей реализации, после объединения с main не повторялись.
