Прежде чем вступит первый офис и загрузится первая камера, домен должен появиться. Это делают один раз, на сервере центра `srv`: установщик создаёт корень домена, подписывает им первые ключи и запись о том, кто держит домен, отдаёт корень оператору и уходит. Потом стартуют процессы держателя и делают первые проходы — по домену, в котором ещё никого нет.

Все запросы части — сцена 1 стенда, [`traces/01-founding.txt`](traces/01-founding.txt) (короткая — [`01-founding.brief.txt`](traces/01-founding.brief.txt)). Часы стоят на `1757500000.0` и за всю сцену не двигаются. До сцены в хранилище `srv` лежит одна строка: дверь ресурса `platform/doors/srv` с `index` 1001, её пишет ресурс при подъёме стенда (М11, [урок 6](../../М11_Cluster/06-what-stays-on-the-server.md)). Поэтому первая запись сцены получает 1002.

## 2.1. Почему домен основывают раньше всех

Порядок здесь не дело вкуса. Член домена верит только тому, что подписал корень домена: набору ключей, которым он проверяет токены людей, и записи о держателе. Первый же набор ключей, подписанный корнем, член **закрепляет** у себя — строкой `domain/root` — и дальше принимает только наборы, подписанные этим корнем (`w2cplatform/domain/agent.py:265-287`; М12A, [урок 14](../../М12A_Domain/14-a-domain-holder-on-one-node.md), шаг 9). Значит, к моменту, когда агент офиса первый раз постучит в дверь домена, подписанный корнем набор уже должен лежать у держателя.

Отсюда и разделение сцен: в этой части членов нет вовсе, а агенты офисов и камер стартуют только в части 3.

## 2.2. Корень вне держателя

Установщик на `srv` — у курса это функция `term.install` (`w2cplatform/domain/term.py:359-372`), у продукта — команда `domain install --holder srv --recovery …` (`vmssubsystem/scripts/nightly/stand.sh`, шаг `start`). Она делает четыре вещи:

1. Создаёт **корень домена** (`DomainRoot`, `w2cplatform/trust/signer.py:176`) — ключ Ed25519 и самоподписанный сертификат.
2. Пишет **файл восстановления** и отдаёт его оператору. В файле корень и больше ничего: ни ключей держателя, ни списка членов (`signer.py:217-222`).
3. Подписывает корнем три вещи: сертификат держателя-выпускающего, первый набор ключей и запись держателя срока 1.
4. Уходит. Корня на держателе не остаётся.

Зачем так сложно: корень **решает**, кто такой домен, а держатель только **подписывает** каждую минуту. Вор, укравший сервер центра, получит ключи держателя и сможет выпускать токены до переноса домена. Захватить домен он не сможет: новый срок подписывает только корень, а члены закрепили корень и чужой набор ключей не примут (М12A, урок 14, шаг 9).

### Строка подписывающего

Сначала установщик проверяет, что домена здесь ещё нет, и пишет строку ключей держателя:

```
# installer on srv → /run/configstore/domain.sock
GET /v1/get?key=domain/signer
→ 200 {"items": null, "index": ""}

# installer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/signer", "cas": "", "items": {
  "issuing_key_secret": "«секрет 1»",
  "issuing_cert": "«сертификат 1»",
  "token_key_secret": "«секрет 2»",
  "kid": "8c47b46a",
  "gen": "1",
  "previous": "[]",
  "backup_key_secret": "«секрет 3»",
  "backup_key_rev": "1",
  "issued": "true"
}}
→ 200 {"index": 1002}
```

Разберу по полям (`Signer._persist`, `signer.py:335-345`).

| Поле | Что это |
|---|---|
| `issuing_key_secret`, `issuing_cert` | ключ и сертификат держателя-выпускающего. Сертификат выдан корнем и сам выдавать удостоверяющие центры не может (`path_length=0`, `signer.py:198-206`). Им подписываются LDevID членов и сертификаты служб |
| `token_key_secret`, `kid` | ключ, которым подписываются токены, и его имя `8c47b46a` |
| `gen`, `previous` | поколение ключей и прежние ключи токенов со сроком их снятия; на свежем домене — первое и пусто |
| `backup_key_secret`, `backup_key_rev` | ключ, которым запечатаны секреты резервной копии домена: HMAC корня и ревизии (`backup_key`, `signer.py:241-249`). Хранитель копии корня не имеет и её секретов не прочтёт; новый держатель выведет этот ключ заново из файла восстановления |
| `issued` | `true`: ключи выданы корнем, а не собственные. Такой подписывающий свою копию ключей не отдаёт никогда |

Корня в строке нет. Это и значит «корень вне держателя».

Секреты здесь — `«секрет N»`, то есть **открытые**: у функции установки нет кольца, и `seal_items` без кольца пишет строку как есть, с предупреждением в журнал (`w2cplatform/sealing.py:163-173`). Запечатает их подписывающий при первом старте (раздел 2.4). Между установкой и первым стартом ключи держателя лежат в хранилище открытыми; на стенде это одна и та же секунда.

### Первый набор ключей

```
# installer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/keys", "cas": "", "items": {
  "doc": "{\"issuing\": [\"«серийный номер 1»\"], \"keys\": {\"current\": \"8c47b46a\", \"key:8c47b46a\": \"«ключ 1»\"}, \"kid\": \"root\", \"rev\": 1, \"revoked_ca\": [], \"root\": \"«ключ 2»\", \"sig\": \"«подпись 1»\"}"
}}
→ 200 {"index": 1003}
```

Это документ, который каждый член унесёт домой и по которому будет проверять токены людей (`DomainRoot.key_set`, `signer.py:207-215`):

- `keys` — открытые ключи токенов: текущий `8c47b46a` и сам ключ `«ключ 1»`;
- `root` — открытый ключ корня, `«ключ 2»`; его член закрепит;
- `issuing` — серийные номера сертификатов держателей-выпускающих, которым верят; `revoked_ca` — тем, которым больше не верят;
- `rev` — ревизия; набор ходит только вперёд, член старый набор поверх нового не возьмёт;
- `kid: "root"` и `sig` — подписал корень.

### Запись держателя срока 1

```
# installer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/holder", "cas": "", "items": {
  "doc": "{\"at\": 1757500000.0, \"holder\": \"srv\", \"kid\": \"root\", \"sig\": \"«подпись 2»\", \"term\": 1}"
}}
→ 200 {"index": 1004}
```

Срок — эпоха уровнем выше. Воркер держит эпоху для камеры, держатель — срок для домена. Ни то, ни другое не раздаётся голосованием: ни один raft не охватывает кластеры, голосовать нечем. Перенос домена берёт следующий номер, и номер решает (М12A, урок 14, шаг 1). Эту запись подписал корень, поэтому держатель её никогда не перепишет своей подписью: держатель, у которого есть запись корня, другой подписать не может (`term.py:378-416`).

### Чем установка курса отличается от продукта

У курса установка — функция, а не команда: её зовут тесты урока 15 и этот стенд. У процесса подписывающего курса есть свой путь первого старта — `RECOVERY_FILE` (`signer_service.py:865-875`): по нему корень подписывает сертификат держателя и первый набор ключей. Запись держателя срока 1 этот путь не пишет, а проход держателя без такой записи считает, что домен «никогда не ставили со сроком», и срока не держит (`term_of`, `signer_service.py:945-952`). Поэтому стенд зовёт `term.install`, как тесты. У продукта всё это делает одна команда `domain install`.

## 2.3. Первый человек — тоже установщика

```
# installer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "identity/users/anna", "cas": "", "items": {
  "id": "anna",
  "kind": "local",
  "roles": "",
  "pwhash_secret": "«запечатано кольцом 1»",
  "idp_subject": "",
  "created": "1757500000.0"
}}
→ 200 {"index": 1005}

# installer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/grants/domain", "cas": "", "items": {"anna|admin|": "0.0"}}
→ 200 {"index": 1006}
```

Почему людей заводит установщик, а не консоль: дверь людей — подписывающего (`/api/people/users`), и она спрашивает админа домена. Пока админа нет, через дверь его не завести. У продукта это команды `domain user add` и `domain grant --cluster domain`; у курса — вызовы `IdentityStore.create_local` и `grants.set_domain_grants` (`stand.py:275-288`).

`pwhash_secret` — хеш scrypt пароля Анны, запечатанный кольцом `srv` (М12A, [урок 15](../../М12A_Domain/15-domain-secrets.md), шаг 1). `domain/grants/domain` — права людей **на самом домене**: Анна — админ, `0.0` — бессрочно. Права на кластерах — другие строки, `domain/grants/<кластер>`, и о них часть 3.

Перед каждой из двух записей установщик читает строку, которой пока нет:

```
# installer on srv → /run/configstore/domain.sock
GET /v1/get?key=domain/vms/stream-clients/anna
→ 200 {"items": null, "index": ""}
```

Это проверка имён, которую платформа делает на каждой записи хранилища держателя (`declared.guarded`, `w2cplatform/domain/declared.py:148-200`). VMS объявила, что имена учёток RTSP и имена людей не пересекаются (`stream-clients/: {exclusive_with: domain/users}`, `vms/vms.subsystem.yaml:411-412`). Поэтому человек `anna` не заводится, если есть учётка `anna`, и права выше `view` учётке не даются. Роль `domain` установщика эту строку читать может. Та же проверка в части 3 обрывает дверь консоли домена, у роли которой такого чтения нет (находка F1).

## 2.4. Подписывающий стартует

Юнит `w2c-domain` поднимает подписывающего с `CLUSTERS=srv,relay-a=http://relay-a:8080,relay-b=http://relay-b:8080`. Голое имя `srv` — свой кластер, его подписывающий читает сам. `relay-a=…` — член, которого домен читает **по отчётам**, с адресом его консоли (`deploy/domain/systemd/domain.env.example:17-20`). Камер в строке нет: в домен они войдут по списку членов (часть 3).

Сначала подписывающий осматривается: перечисляет `domain/`, читает права домена, запись держателя, набор ключей и свою строку. Потом **запечатывает** то, что нашёл открытым:

```
# signer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/signer", "cas": 1002, "items": {
  "issuing_key_secret": "«запечатано кольцом 2»",
  "issuing_cert": "«сертификат 1»",
  "token_key_secret": "«запечатано кольцом 3»",
  …
  "backup_key_secret": "«запечатано кольцом 4»",
  …
}}
→ 200 {"index": 1007}
```

Это `w2cctl.seal` (`w2cplatform/w2cctl.py:68-93`), его зовёт `signer_service.main` первым делом (`signer_service.py:859-862`): каждый секрет в открытую он запечатывает, каждый запечатанный старым ключом — перезапечатывает текущим. Кольцо — ключ платформы `SECRETS_KEY`, юнит получает его как учётные данные `systemd` (М12A, урок 15, шаг 2). Строку человека `identity/users/anna` подписывающий только читает: она уже запечатана.

Потом подписывающий **заявляет срок**:

```
# signer on srv → /run/configstore/domain.sock
POST /v1/write {"op": "put", "key": "domain/holder", "cas": 1004, "items": {
  "doc": "{\"at\": 1757500000.0, \"holder\": \"srv\", \"kid\": \"root\", \"sig\": \"«подпись 2»\", \"term\": 1}"
}}
→ 200 {"index": 1008}
```

Документ тот же, байт в байт, а `index` новый. Подписывающий при старте сначала **смотрит**, держит ли он ещё домен, и только потом заявляет: агент мог уже принести сюда больший срок, пока процесс лежал (`DomainHolder.start`, `term.py:418-424`). Запись корня он не переподписывает, а пишет как есть (`term_of`, `signer_service.py:960-967`). Записи «без изменений» здесь не отсеиваются, поэтому одна запись стоит одного номера.

Между этими записями стоит одно чтение не от подписывающего:

```
# resource on srv → /run/configstore/resource.sock
GET /v1/list?prefix=platform/doors/
→ 200 {"keys": {"platform/doors/srv": 1001}}
```

Это ресурс `srv` узнаёт, где ресурсы других серверов **своего** кластера, чтобы ответить на чтение объектов с `scope=cluster` (М11, урок 6). В кластере `srv` сервер один, дверь одна.

Последней подписывающий открывает свою дверь, на стенде `srv:8071`, и сокет токенов (`signer_service.py:895-908`).

## 2.5. Кто ещё стартует на srv

Четыре юнита рядом с подписывающим. Ключей домена нет ни у одного (М12B, [`module-design.md`](../../М12B_DomainVMS/module-design.md), «Процессы у держателя»).

| Процесс | Юнит, роль | Что сделал в сцене |
|---|---|---|
| консоль домена | `w2c-domain-console`, `domainconsole` | ничего не записал: читать ей пока нечего, а решений человека ещё не было |
| воркер VMS на домене | `vms-domainpart`, `vmsdomain` | спросил у сокета токенов, какие виды токенов он может просить |
| агент держателя | `w2c-domainagent`, `domainagent` | сделал ключ члена |
| консоль кластера `srv` | `w2c-console`, `console` | прочла `platform/schema`: сборка старше хранилища не стартует |

Воркер VMS спрашивает сокет токенов:

```
# vmsdomain on srv → the signer's token socket /run/w2c-signer/tokens.sock
GET /kinds
→ 200 {
  "stream": {"lifetime": 86400.0, "claims": ["aud", "ref"]},
  "ask":    {"lifetime": 86400.0, "claims": ["aud", "ref", "by", "acts", "up"]}
}
```

Это ровно то, что объявила спека VMS (`vms.subsystem.yaml:413-415`). Подписывающий выдаёт токены только этих видов и только с этими полями; ключ при этом остаётся у него (`w2cplatform/domain/tokendoor.py:1-15`). Что такое токен потока и зачем ему сутки, — в [справочнике](01-reference.md), раздел «Токены».

Агент держателя делает ключ члена:

```
# domainagent on srv → /run/configstore/domainagent.sock
POST /v1/write {"op": "put", "key": "domain/member-key", "cas": "", "items": {
  "seed_secret": "«запечатано кольцом 5»",
  "pub": "«ключ 3»",
  "seal_pub": "«ключ 4»"
}}
→ 200 {"index": 1009}
```

Из одной затравки выходят два ключа: `pub` (Ed25519) — им член подписывает свои запросы к двери, `seal_pub` (X25519) — ему держатель запечатывает секреты. Затравка запечатана кольцом кластера: копия хранилища — не копия личности (`w2cplatform/trust/memberkey.py:1-28`; М12A, урок 15, шаг 5). Зачем ключ члена держателю, который сам себе дверь: держатель держит домен не вечно. После переноса он станет членом, как остальные, и его ключ едет в каждой резервной копии под подписью (`holder_key`, `term.py:392-396`, `:462`).

## 2.6. Первый проход подписывающего

Подписывающий проходит раз в 5 секунд (`REFRESH_INTERVAL`, `signer_service.py:914`), и у каждого выхода прохода один писатель — он (ADR-0032). Первый проход по пустому домену выглядит так; запросы сгруппированы по смыслу, в трассе они перемешаны:

```
# что за домен и держу ли я его
GET /v1/get?key=domain/keys                      → набор rev 1           ×2
GET /v1/get?key=domain/holder                    → срок 1, srv           ×2

# отчёты членов из CLUSTERS — файлы в объектах держателя, через ресурс srv
GET /v1/objects/domain/members/relay-a/reported?scope=cluster   → 404     ×5
GET /v1/objects/domain/members/relay-b/reported?scope=cluster   → 404     ×5

# свой кластер — как любой другой: heartbeat'ы и срезы снапшота
GET /v1/objects?prefix=vms/heartbeats/&scope=cluster            → пусто
GET /v1/objects?prefix=vms/snapshot/&scope=cluster              → пусто   ×3

# решения человека и сохранённые правки
GET /v1/get?key=domain/members                   → null                  ×4
GET /v1/get?key=domain/topology                  → null                  ×2
GET /v1/get?key=domain/pending/srv               → null   … relay-a и relay-b ×2
GET /v1/get?key=domain/vms/crossings             → null

# резервная копия
GET /v1/list?prefix=domain/backup/               → {}                    ×2

# вид домена — файл на srv
PUT domain/view
```

Итого: 16 чтений и 2 перечисления хранилища, **ни одной записи в хранилище**, 14 запросов объектов к ресурсу и один файл. Посчитано по трассе.

**Отчёты `relay-a` и `relay-b` — `404`.** Офисы ещё не поднялись. Для домена это не ошибка, а ответ: член, который ни разу не отчитался, будет показан как «ни разу не отчитывался», а не пропущен (М12A, [урок 1](../../М12A_Domain/01-what-a-cluster-cannot-know.md)).

**Одну строку читают по нескольку раз.** У контроллера М11 проход запоминает каждую прочитанную строку до конца прохода (`one_pass`). У прохода держателя такой памяти нет: каждый шаг — члены, топология, вид, правки, тревоги, копия — читает своё сам (`Holder.steps`, `signer_service.py:119-142`; М12A, урок 14, шаг 10). Сколько это стоит на сотнях членов, — часть 12.

**Резервной копии нет.** Копию проход пишет не чаще раза в 30 секунд и на двух **живых** членов (`BACKUP_EVERY`, `BACKUP_HOLDERS`, `signer_service.py:77-79`). Живых членов нет — листинг `domain/backup/` пуст, и копировать некуда.

**Вид домена** — `domain/view`, файл на `srv`. Его читает консоль домена: всё, что знает только подписывающий, — его срок, упавшие шаги, строки, которых он не смог прочесть, — она берёт оттуда (`console.py:5-12`).

## 2.7. Первый проход воркера VMS на домене

Сначала воркер берёт **слот** — чтобы проходов по книгам не было два сразу:

```
# vmsdomain on srv → /run/configstore/vmsdomain.sock
GET /v1/get?key=domain/vms/worker
→ 200 {"items": null, "index": ""}

# vmsdomain on srv → /run/configstore/vmsdomain.sock
POST /v1/write {"op": "put", "key": "domain/vms/worker", "cas": "", "items": {
  "instance": "srv:1201:0004b1",
  "at": "1757500000.0"
}}
→ 200 {"index": 1010}
```

Слот берётся по CAS. Второй экземпляр воркера ждёт, пока первый не промолчит `SLOT_LOST = 45` секунд (`vms/domainpart/worker.py:49-60`). Это тот же приём, что слот воркера в кластере М11, только на домене и для одного процесса.

Потом проход по книгам, по шагу (`vms/domainpart/books.py:41-71`): члены, топология, вид, книги источников, основных, опроса, `upstream`, общие настройки, запросы, учётки RTSP. Всё читается пустым: `domain/members`, `domain/topology`, `domain/vms/crossings`, листинги `domain/vms/sources/`, `domain/vms/primaries/`, `domain/vms/asks/`, `domain/shared` — `null` или `{}`. Решений «кто пишет какую камеру» нет, значит, книг тоже нет.

Пишется одно — книга учёток RTSP, по одной на каждый кластер из `CLUSTERS`:

```
# vmsdomain on srv → /run/configstore/vmsdomain.sock
POST /v1/write {"op": "put", "key": "domain/vms/stream-accounts/relay-a", "cas": "", "items": {
  "accounts_secret": "«запечатано кольцом 6»"
}}
→ 200 {"index": 1011}
```

То же для `relay-b` (1012) и `srv` (1013). Внутри — пустой список учёток: перед каждой записью воркер прочёл права кластера `domain/grants/<кластер>` (`null`) и листинг `domain/vms/stream-clients/` (пусто). Книга пишется для каждого кластера, который домен читает, как только у держателя есть набор ключей (`publish_accounts`, `vms/domainpart/streamclients.py:252-274`). Пустой список — тоже ответ: «здесь никто не играет».

Итого по трассе: 17 чтений и 6 перечислений, 4 записи.

## 2.8. Первый проход агента держателя

Агент держателя не ходит в дверь: он стоит на том же сервере и читает хранилище `srv` прямо (`DOMAIN_CONFIG_URL`, `agent.py:631-633`). Но читает он его тем же путём, что дверь: только общие строки и строки своего кластера (`carry.answer`, `w2cplatform/domain/carry.py:127-147`) — `domain/keys`, `domain/revoked`, `domain/holder`, `domain/shared`, `domain/topology`, `domain/members`, затем `domain/grants/srv`, `domain/pending/srv`, `domain/backup/srv`, `domain/ldevid/srv`, `domain/break_glass/srv` и каждую книгу VMS для `srv`.

Пишет он три строки:

```
# domainagent on srv → /run/configstore/domainagent.sock
POST /v1/write {"op": "put", "key": "domain/root", "cas": null, "items": {"pub": "«ключ 2»"}}
→ 200 {"index": 1014}

# domainagent on srv → /run/configstore/domainagent.sock
POST /v1/write {"op": "put", "key": "domain/vms/stream-accounts", "cas": "", "items": {
  "accounts_secret": "«запечатано кольцом 8»"
}}
→ 200 {"index": 1015}

# domainagent on srv → /run/configstore/domainagent.sock
POST /v1/write {"op": "put", "key": "domain/member", "cas": "", "items": {"cluster": "srv"}}
→ 200 {"index": 1016}
```

**`domain/root`** — закреплённый корень. `«ключ 2»` — тот же ключ, что в поле `root` набора ключей: агент проверил, что набор подписан этим корнем, и закрепил его, раз закреплённого ещё не было (`agent.py:265-287`). С этой строки любой набор, подписанный другим корнем, агент отклонит словами «signed by a root this member did not pin».

**`domain/vms/stream-accounts`** — своя книга учёток, унесённая «домой» под именем без хвоста `/srv`. Значение запечатано тем же кольцом, что книга у держателя, `«запечатано кольцом 8»`: агент держателя спрашивает без ключа запечатывания, и строки идут как лежат (`carry.py:127-130`).

**`domain/member`** — «этот кластер — член». По ней консоль кластера отличает «ключи потеряны» от «их не было никогда» (`agent.py:42-47`).

Строк `domain/keys` и `domain/holder` агент не пишет: под теми же именами в том же хранилище они уже лежат. Отчёта он тоже не пишет: держателю некому отчитываться, его объекты и есть объекты держателя.

## 2.9. Что держит только держатель

После этой сцены почти всё, что знает домен, лежит в одном месте — на `srv`. Так будет не всегда: с каждым проходом агентов часть состояния расходится по членам (М12A, урок 14, шаг 2).

| Что | У держателя | Где ещё будет |
|---|---|---|
| ключи держателя `domain/signer` | да, запечатаны кольцом | **нигде**: в резервную копию не идут никогда |
| корень | нет | только файл восстановления у оператора |
| набор ключей, запись держателя | да | у каждого члена, после первого прохода его агента |
| люди `identity/users/*`, аварийные хеши кластеров | да | в резервной копии домена |
| список членов, топология | да | у каждого члена — копия; в резервной копии |
| права на кластере `domain/grants/<кластер>` | да | у этого кластера; в резервной копии |
| сохранённые правки `domain/pending/*` | да | у кластера — когда он включится; в резервной копии |
| решения VMS `domain/vms/crossings`, `roads` | да | только в резервной копии (`domain.kept`) |
| книги VMS | да | у своего члена; в копию не идут — их пересчитает проход |
| неделя тревог | объект держателя | в резервной копии |

Резервная копия — подписанный документ `backup/rev-<n>` в объектах держателя и указатель `domain/backup/<член>` для каждого из двух членов, выбранных её хранить. Агент хранителя уносит её домой как строку `domain/backup-taken` и объект рядом. Секреты в копии запечатаны ключом копии, а не кольцом держателя, — хранитель не прочтёт ни одного (`signer.py:241-249`; М12A, урок 14, шаг 2). Перенос домена берёт новейшую копию, которую хранит хоть кто-то, — часть 10.

В этой сцене копий нет: живых членов нет. Первая копия появится, когда офисы и камеры отчитаются (часть 4). На момент трасс агент офиса, собранный как процесс курса, копию не брал, а агент камеры — брал (находка O5).
