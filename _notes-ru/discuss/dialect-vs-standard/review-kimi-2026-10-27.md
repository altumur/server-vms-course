## П. 2. Форма манифеста → JSON Schema 2020-12

Мой переводчик `form2schema.py` (form.yaml читается моим слоем текста): properties → закрытый набор;
`names` → `propertyNames` + `additionalProperties`; правила с условием на имя — в `patternProperties` по
областям `^(?=(?:P)$)` / `^(?!(?:P)$)` (в т. ч. через `ref`: правила def-цели поднимаются на место `names`);
прочие правила → `if`/`then` (`reject` → `then: false`); `is`/`is_not` — с умолчаниями формы (chase ref →
default) через `anyOf` с `not`/`required`; образцы диалекта (fullmatch, re.S) → `^(?:…)$`, `.` → `[\s\S]`;
`variants` → `anyOf`; `opaque` — без ключей; `ordered` не переводится (судья эталона его тоже не проверяет).

Схема `form.schema.json` — 61756 байт (у автора 65458 — другой переводчик), валидна по метасхеме 2020-12.

**Полный прогон: 545/557; все 12 расхождений — правило «4.0 в месте целого — отказ»**
(`c5_int_capacity_4dot0/4dot/4e0/4bigE0/4eplus0`, `c5_int_lease_1dot0`, `c5_int_lease_1e2`,
`c5_int_field_default_1dot0/1e0`, `c5_int_field_f1_default_1dot0`, `lease_1e308`, `lease_1.0e308`).
**Со слоем «целый знак» (свой TypeChecker: integer — только записанное целое) — 557/557.** Ровно числа и
состав расхождений записки.

По пути был свой баг перевода (правило с `name_not_pattern` у значения-`ref` терялось — находил своими же
случаями `profile_blob_*`); после починки расхождений, кроме «целого знака», нет.

## П. 3. Связи → CEL

Мой переводчик `rel2cel.py` (разбор строк — разбор источника диалекта, не предмет проверки; AST → CEL —
мой): образцы диалекта → `^(?:…)$` и `.` → `[\s\S]` (RE2, `matches` частичный); `@путь` без значения —
умолчание формы статически (цепочки присутствия + подстановка константы); терм без значения: `=` ложно,
`!=` истинно, `in` ложно, `not in` истинно, `~` ложно, `!~` истинно (О6, О7); `keys`/`values` — списки CEL
(у отображений итерация по ключам: `m.map(k, k)`; `.keys()` в CEL нет; `in` по отображению — по ключу);
ключи списка — его строки (О8); `unique` — двумя двуместными `exists`; `prefix_free` —
`endsWith`/`startsWith`; `split` — `ext.Strings`; многозначные обходы для `in`/`not in` — цепочками `exists`
без flatten; `unique` над многозначным множеством — попарными двуместными `exists` (нарушение = две позиции
с равными значениями); обход списков с индексом — `transformList(i, v, …)` (двуместного `map` нет);
`bind`/`each_bind` в наборах — подстановка из окружения строки.

**Переведено 112 строк из 121** — ровно расклад записки (95 чистый CEL + 7 `split` + 10 многозначных);
не переводятся только 9 строк своих функций: `depth` × 6 (строки 12, 25, 26, 79, 93, 119), `template` × 2
(16, 75), `text` × 1 (70).

Исполнение — Go-раннер на cel-go v0.33.0 (`doc` — dyn; числа JSON → int64 при целом значении: в CEL
`int == double` ложно, в диалекте `1 = 1.0`, Ф9; литералы-целые переводятся в int тем же правилом).
Выражение строки даёт вложенные списки путей нарушений (сплющивание в раннере).

**Полный прогон: 270 случаев с чистой формой (ровно число записки), 0 различий с эталоном по множествам пар
(строка, путь); сработали все 112 переведённых строк.**

Различия CEL и диалекта, которые перевод обязан учитывать (подтверждаю список записки своими): `matches`
частичный и `.` без `\n`; `in` по отображению — по ключу; нет `.keys()`; нет двуместного `map`; `x != null`
не компилируется для статических строковых литералов; `string(x)` нет для строк; равенство чисел строго по
типу. Отдельно: celpy 0.5.0 как движок непригоден — нет двуместных макросов и `split`, `1 == 1.0` — ошибка,
`true == 1` → True (против диалекта); п. 3 сделан на cel-go (эталонная реализация CEL, другой язык —
независимость выше).
