## 8.1. Оператор нажал «Сохранить» дважды

Браузер повторил `POST` с **тем же** `Idempotency-Key`, и повтор попал на консоль другого сервера. Вторая консоль пробует занять ключ так же, как первая, — записью «только если ключа нет»:

```
PUT /v1/var/vms/idem/8f4b21e0-…?cas=0

{"Items": {"state": "pending", "at": "1757500000.0", "sub": "operator", "sha256": "54c50059…"}}

→ 409 Conflict                       ← ключ уже занят
```

В заявке теперь два поля, которых раньше не было: `sub` — кто спрашивает, и `sha256` — отпечаток тела запроса. Ключ — это имя **одного** запроса **одного** человека. Если повтор пришёл от другого пользователя или с другим телом, консоль отвечает `422` («этот ключ называет другой запрос») и чужой ответ не отдаёт (`IdempotencyKeys._mismatch` в `w2cplatform/console.py`).

Камеру вторая консоль не создаёт. Она начинает опрашивать ключ — до 40 раз с паузой в 50 миллисекунд:

```
GET /v1/var/vms/idem/8f4b21e0-…
→ {"state": "pending", "at": "1757500000.0", "sub": "operator", "sha256": "54c50059…",
   "id": "1"}                                    ← первая ещё пишет, но номер уже взяла
…
GET /v1/var/vms/idem/8f4b21e0-…
→ {"state": "done", "status": "201", "body": …, "sub": "operator", "sha256": "54c50059…"}

Items.body:
{"id": 1, "name": "Ворота", …, "worker": null}
```

Поле `id` в заявке появилось тоже недавно. Первая консоль вписывает в заявку номер камеры **до** того, как пишет строку камеры (`IdempotencyKeys.reserve`, вызывается из `SpecController.create`). Зачем — ниже.

Вторая консоль отдаёт оператору **чужой ответ**:

```
HTTP/1.1 201 Created

{"id": 1, "name": "Ворота", …, "worker": null}
```

Одна камера, а не две. Если первая консоль так и не ответила за две секунды, вторая честно говорит об этом:

```
HTTP/1.1 409 Conflict

{
  "detail": "the same request is in flight on another console",
  "error": "in flight"
}
```

Что будет, если первая консоль так и не ответит никогда — упала между заявкой и ответом? Раньше такая заявка висела весь срок ключа, сутки, и каждый правильный повтор получал `409`. Теперь заявку, которая простояла неизменной 30 секунд (`PENDING_TTL`), следующий повтор перехватывает условной записью по её версии. Тридцать секунд считаются по монотонным часам **той консоли, которая смотрит**, от момента, когда она впервые увидела эту версию заявки. Отметку `at`, которую чужая консоль написала по своим стенным часам, никто не сравнивает: консоль, отстающая на минуту, иначе принимала бы каждую свежую заявку за брошенную.

Перехватившая консоль создаёт камеру **под номером из заявки**. Если камера с этим номером уже есть — первая успела её записать и упала, не дописав ответ, — она отвечает этой камерой. Так «ответ потерялся» и «запись не случилась» перестают выглядеть одинаково. А если первая консоль не умерла, а только замерла и потом очнулась, её собственная запись в заявку не пройдёт: версия уже чужая, и она получает `409 taken over`, ничего не создав.

И ещё одно отличие от прежнего. Ответ с кодом `5xx` под ключом не запоминается: «хранилище не ответило» — не ответ на запрос. Заявка снимается, и повтор делает работу заново (`IdempotencyKeys.store`).

## 8.2. Два оператора создают камеру одновременно на разных консолях

Обе консоли читают счётчик и получают один и тот же индекс:

```
# консоль А                          # консоль Б
GET /v1/var/vms/next_id              GET /v1/var/vms/next_id
→ {"n": "1"}, ModifyIndex 4405       → {"n": "1"}, ModifyIndex 4405

                                     PUT /v1/var/vms/next_id?cas=4405
                                     {"Items": {"n": "2"}}
                                     → 200, ModifyIndex 4418
PUT /v1/var/vms/next_id?cas=4405
{"Items": {"n": "2"}}
→ 409 Conflict

(случайная пауза)
GET /v1/var/vms/next_id
→ {"n": "2"}, ModifyIndex 4418
PUT /v1/var/vms/next_id?cas=4418
{"Items": {"n": "3"}}
→ 200, ModifyIndex 4426
```

Консоль Б получила номер 2, консоль А повторила цикл с новым индексом и получила номер 3. Номера не пересекаются, ни одна камера не затёрта. Повторов допускается до десяти (`Controller.write`), после чего запрос падает с ошибкой.

Повтор теперь идёт не сразу, а после случайной паузы, которая растёт с каждой попыткой: от долей миллисекунды до потолка в 100 миллисекунд (`cas_pause` в `w2cplatform/variables.py`). Без паузы те же двое встречались бы снова и снова.

Между счётчиком и строкой камеры у каждой консоли появились ещё запросы — по одному на каждую уже существующую камеру:

```
GET /v1/vars?prefix=vms/cameras/
GET /v1/var/vms/cameras/1
GET /v1/var/vms/cameras/2
PUT /v1/var/vms/cameras/3?cas=0
```

Это проверка, что у новой камеры **свой** источник и свой `ref` (`refuse_camera` в `vms/volumes.py`): один канал устройства — одна камера, одно имя для доменного слоя — одна камера. Проверка сверяет только с тем, что уже записано. Два оператора, заводящих один и тот же канал в одно и то же мгновение, могут пройти оба — код говорит об этом прямо.

## 8.3. У камеры метка, которой нет ни на одном сервере

Оператор создал камеру 4 с меткой `vlan:cctv-dmz`, а такой метки нет ни у одного воркера.

Камера создаётся нормально — `201`. Но на проходе контроллера фильтр по меткам вычищает весь пул, размещать не на кого, и контроллер **не пишет ничего**: ни строки размещения, ни назначения.

```
GET /where/4

→ 404
{"worker": null, "reason": null, "directory": null, "scans": 1}
```

Честный ответ на вопрос «почему» даёт отдельный маршрут:

```
GET /unplaceable

→ 200
[{"id": 4, "labels": ["vlan:cctv-dmz"], "workers_live": 3}]
```

«Живых воркеров три, ни один не достаёт до этой метки». `workers_live` здесь — это пул размещения, а не все, кто шлёт heartbeat: из живых уже вычтены отпустившие слот, стоящие на сервере с молчащим ресурсом, на выводимом сервере и простаивающие по политике (`SpecController._pool`). В снапшоте такая камера уезжает в отдельный шард с зарезервированным именем:

```
PUT /v1/var/objects/vms/snapshot/unplaced

Items.data:
{"cluster": "room-a", "worker": null, "ts": …, "cameras": [{"id": 4, …}]}
```

Важно, что сообщение звучит как «система не дотягивается», а не «w-1 переполнен»: причина в достижимости, а не в ёмкости.

У такой камеры есть цена, которую снаружи не видно: каждый проход контроллер снова пробует её разместить и при этом перечитывает строки **всех** камер. Сколько это стоит в запросах — в разделе [10.2](10-limits-and-scale.md).

## 8.4. На `srv-2` замолчал ресурс

Ресурс на `srv-2` перестал писать heartbeat, и его последняя отметка старше 45 секунд. Спецификация VMS требует ресурс (`requires: resource`), поэтому `w-2` выпадает из пула.

Если это случилось **до** размещения, арифметика меняется так:

| Камера | свободно у w-1 | свободно у w-3 | выбран | почему |
|---|---|---|---|---|
| 1 | 50 | 50 | **w-1** | равенство, побеждает первый по алфавиту |
| 2 | 49 | 50 | **w-3** | `50 > 49` |
| 3 | 49 | 49 | **w-1** | снова равенство, снова первый по алфавиту |

Камеры лягут 2 к 1: две на `srv-1`, одна на `srv-3`. Причина в строке размещения назовёт это прямо — вот она у камеры 3, последней из трёх:

```
most free capacity (49) among 2 worker(s) reaching vlan:cctv; on srv-1, whose resource is live
```

Число `2` вместо `3` в этой строке и есть весь след пропавшего ресурса: `w-2` в пул не попал, поэтому и выбирали из двоих.

Если ресурс замолчал **после** размещения, камеру увозит следующий проход контроллера (`redistribute`), и причина будет составной — сначала что случилось, потом куда переехали. Записей три, и порядок у них теперь другой, чем был: сначала решение, потом назначения.

```
# 1. Решение — первым. CAS заодно проверяет, что строка всё ещё называет w-2
PUT /v1/var/vms/placement/2?cas=4449
{
  "Items": {
    "worker": "w-1",
    "reason": "resource on srv-2 silent; most free capacity (49); on srv-1",
    "at": …,
    "rev": "2"
  }
}

# 2. Убрать камеру у прежнего воркера
PUT /v1/var/vms/workers/w-2?cas=…
{"Items": {"units": "", "rev": "2"}}

# 3. Добавить новому
PUT /v1/var/vms/workers/w-1?cas=…
{"Items": {"units": "1,2", "rev": "2"}}
```

Почему так (`SpecController.move` и `move_from`). Строка размещения — это решение, а назначения его исполняют. Если контроллер упадёт между записями, следующий проход начнёт с того, что приведёт назначения в соответствие строкам (`sync_assignments`), и дорежет переезд с любой стороны. А проверка «строка всё ещё называет `w-2`» нужна на время деплоя, когда контроллеров на секунды два: без неё каждый увозил камеру туда, где считал лучше, и камера оказывалась в двух назначениях сразу.

## 8.5. Воркер один, а не три

Тот же сценарий на кластере, где живой воркер только `w-1`:

| Камера | capacity | load до | свободно | выбран |
|---|---|---|---|---|
| 1 | 50 | 0 | 50 | w-1 |
| 2 | 50 | 1 | 49 | w-1 |
| 3 | 50 | 2 | 48 | w-1 |

Все три на одном сервере, причины: `most free capacity (50) among 1 worker(s) …`, потом `(49)`, потом `(48)`.

Это не деградация и не ошибка — это то же самое правило. Раскладка по трём серверам в [части 4](04-placement.md) была следствием того, что серверов было три и все свободны. **Никакого правила «разнести камеры по серверам» в подсистеме VMS нет**, и разъезжаются они только потому, что каждая следующая видит у предыдущего хозяина на единицу меньше свободной ёмкости.

Разводить камеры по разным серверам принудительно платформа умеет — полем `spread_by` в спецификации, — но работает оно не так, как хочется прочитать. `spread_by` называет **поле в строке камеры**, и по разным серверам расходятся те камеры, у которых значение этого поля одинаково. Это жёсткий фильтр, а не предпочтение: сервер, уже занятый камерой с тем же значением, вычёркивается из пула ещё до выбора. Правила «каждая камера на своём сервере» из этого не собрать. Я проверил все семь спецификаций в `vmsserver/vms/*.subsystem.yaml`: `spread_by` не задан ни в одной.

Что будет, когда камер станет больше, чем этот воркер готов взять, — в разделе 8.8.

## 8.6. `w-2` упал после того, как камеру ему назначили

Слот `w-2` протух: `until` в прошлом, `released` по-прежнему `false`. Контроллер такие слоты **не разбирает**, и это осознанно:

```
GET /v1/vars?prefix=vms/slots/
GET /v1/var/vms/slots/w-2

→ 200
{
  "Items": {
    "holder": "srv-2:2044:1c7e9b",
    "until": "1757500050.0",
    "released": "false",
    "gen": "1"
  }
}
```

`released: false` означает «процесс не прощался, он умер». Планировщик поднимет его заново, новый процесс возьмёт тот же слот `w-2` и вместе с именем унаследует назначение — камеру 2. Двигать её никуда не нужно, и контроллер её не двигает.

### Откуда берутся просроченные слоты

Строка слота — это **аренда на имя**, а не запись о нём. В ней четыре поля, и каждое отвечает за свою часть смысла:

| Поле | Что значит |
|---|---|
| `holder` | какой именно процесс держит имя. На кластере это идентификатор аллокации Nomad: задание передаёт его процессу как `INSTANCE_ID=${NOMAD_ALLOC_ID}`. Без него процесс называет себя сам: `хост:pid:шесть-случайных-знаков` — эту форму я оставил в примерах сценария (раздел [2.2](02-before-first-camera.md), здесь и в справочнике). В отрывках из трасс урока и в разделах 8.7 и 8.9 стоит то, что стенд кладёт в `INSTANCE_ID`: `alloc-0099`, `alloc-2` |
| `until` | до какого момента по стенным часам аренда действует |
| `released` | попрощался ли прежний держатель по-хорошему |
| `gen` | сколько раз это имя вообще захватывали |

Аренда берётся на 45 секунд и сама по себе не продлевается.

### Кто продлевает и каким запросом

Продлевает **сам воркер, и только он** — тот процесс, чей `instance` записан в `holder`. Ни контроллер, ни консоль слот не продлевают: у контроллера есть право писать в `vms/slots/*`, но пользуется он им ровно в одном случае — пометить слот отпущенным. Никакого внешнего сторожа, который следит за живостью воркеров, в системе нет: воркер отчитывается о себе сам, а молчание и есть сигнал.

Внутри процесса продлевать теперь могут двое: основной цикл и его **дублёр** — отдельный поток, который подхватывает продление, когда шаг цикла завис. О дублёре — ниже.

Продление — это три вызова: проверка схемы хранилища, чтение строки и условная запись.

```
# 0. Не поднял ли кто-нибудь схему хранилища выше той, что понимает этот процесс
GET /v1/var/platform/schema
→ 404                                ← строки нет: схема 1, всё в порядке

# 1. Прочитать строку — заодно узнать, моё ли ещё имя
GET /v1/var/vms/slots/w-2

→ 200
{
  "Items": {
    "holder": "srv-2:2044:1c7e9b",
    "until": "1757500050.0",
    "released": "false",
    "gen": "1"
  },
  "ModifyIndex": 5120
}

# 2. Переписать с тем же holder и отодвинутым сроком
PUT /v1/var/vms/slots/w-2?cas=5120

{
  "Items": {
    "holder": "srv-2:2044:1c7e9b",
    "until": "1757500095.0",      ← единственное изменение: теперь + 45 с
    "released": "false",
    "gen": "1"
  }
}

→ 200 {"ModifyIndex": 5121}
```

Шаг 0 появился после второго раунда ревью (`Worker._renew_slot` в `w2cplatform/contract.py`). Оператор может поднять версию схемы, пока процесс работает. Хранилище откажет в этом, если среди **живых** процессов есть понимающий меньше. Но процесс, который проверил схему при старте и ещё не прислал heartbeat, для этой проверки не живой. Поэтому проверка повторяется на каждом продлении. Если схема ушла вперёд, воркер отсекает себя так же, как если бы слот взял кто-то другой.

Меняется в строке ровно одно поле — `until`. `holder` воркер вписывает свой же, `gen` не трогает: поколение растёт только при захвате имени, а не при подтверждении.

Обратите внимание, что этот же запрос отвечает и на вопрос «я ли ещё держу имя». Проверок три, и все означают одно:

| Что случилось | Как воркер это видит | Вывод |
|---|---|---|
| в `holder` чужой экземпляр | видно уже на шаге 1 | имя отобрали, я не настоящий |
| в строке `released: true` | видно на шаге 1 | имя списали (`retire`), поздним продлением его не вернуть |
| `PUT` вернул `409` | кто-то переписал строку между шагами | то же самое |

Третий случай трактуется так же строго, как первый: проиграл гонку — считай, что имя не твоё. Здесь выгодно ошибиться в сторону осторожности, потому что цена ложной тревоги — лишний перезапуск, а цена пропуска — два процесса, которые держат одну камеру.

А вот хранилище, которое **не ответило**, ни о чём из этого не говорит. Воркер считает, что он по-прежнему `w-2`, и записывает это в счётчик `store_errors` (`VmsWorker.lease_pass`). Право писать от этого не продлевается: его держат аренды на эпохи, и они истекают сами.

### Когда воркер это делает

Продление живёт в том же шаге цикла, что и продление аренд на эпохи камер, и стоит в нём **первым**: сначала «я ли ещё `w-2`», и только потом «мои ли ещё камеры». Порядок не случайный — зависший экземпляр должен отсеиваться на имени, не дожидаясь разбирательства по каждой камере.

| Что | Как часто |
|---|---|
| основной цикл воркера | каждые 2 секунды |
| между проходами | каждые 0,25 секунды воркер смотрит строки запросов `vms/requests/` и вычерпывает шину пайплайнов (`COMMANDS_BEAT`); продление и heartbeat этот такт не приближает |
| продление слота и аренд | на первом проходе, где с прошлого раза прошло 8,3 секунды, — то есть примерно раз в 10 секунд |
| heartbeat | раз в 10 секунд, отдельной записью в `objects/vms/heartbeats/w-2` |

Число 8,3 не выбрано на глаз: это `(30 − 5) / 3`, треть от срока аренды эпохи за вычетом запаса. Смысл в том, чтобы до истечения оставалось место на три попытки — два подряд неудачных продления ещё ничего не ломают.

Продление и heartbeat стоят каждый в своём `try` (`VmsWorker.run`). Раньше у них был общий, и одна строка, которая не читается, роняла продление, а вместе с ним и heartbeat. Ревью нашло, что так через 45 секунд контроллер терял все рекордеры кластера разом. Теперь продление, которое упало, повторяется на следующем круге, а heartbeat уходит в любом случае.

Heartbeat и продление слота легко спутать, но это две разные записи в два разных ключа. Heartbeat рассказывает контроллеру, что воркер умеет и что у него запущено. Продление слота говорит только одно: имя всё ещё занято мной.

Итого у живого воркера `until` всегда висит на 45 секунд впереди и переписывается за этот срок четыре-пять раз. Запас такой не от щедрости: промах одного продления — сетевой всплеск, перевыборы лидера в raft — не должен стоить воркеру имени.

### Дублёр: когда шаг цикла завис

Продление стоит в цикле, а цикл может застрять на одном шаге: вызов хранилища, который не возвращается, вызов в движок архива. Раньше вместе с шагом вставало и продление, и через срок аренды камеры воркера уезжали к соседу, хотя процесс был жив и вот-вот вернулся бы.

Теперь каждый шаг цикла отмечает своё начало и конец (`Worker.guarded`), а рядом с циклом живёт поток-дублёр (`Worker.start_stand_in`). Раз в две секунды он смотрит на текущий шаг. Если с последнего продления — или с начала шага, что раньше, — прошло больше половины окна аренды (12,5 из 25 секунд), дублёр продлевает за цикл слот и аренды. Запросы те же самые, что выше: схема, слот по CAS, по одному чтению эпохи на камеру. Делает он это так же часто, как цикл, и только пока строка слота называет этот экземпляр.

У дублёра три ограничения:

- **Только на время.** Пять минут (`STAND_IN_FOR`) от последнего продления, которое цикл сделал сам. Шаг, зависший навсегда, не должен держать камеры навсегда: после этого дублёр перестаёт, аренды истекают, и камеры честно уезжают.
- **Никогда не воскрешает.** Слот, который взял другой экземпляр, аренду, которую отсекли, экземпляр, который отсёк сам себя, — ничего из этого дублёр не продлевает и ничего не решает. Что значит потерянный слот, решает цикл, когда вернётся.
- **Не мешает циклу.** Если цикл прямо сейчас продлевает слот сам, дублёр не ждёт и пропускает свой раз.

В heartbeat'е появляется поле `stand_in_renewals` — сколько раз дублёр продлевал за этот процесс. Если оно не ноль, значит, у воркера зависали шаги и кто-то держал за него камеры.

**Просрочка — это просто прекращение продлений.** Никто не «помечает» слот протухшим: строка лежит нетронутой ровно в том виде, в каком её оставило последнее удачное продление, и в какой-то момент стенные часы обгоняют её `until`. Три условия просрочки читаются прямо из полей: имя кем-то взято (`holder` не пуст), прощания не было (`released: false`), срок вышел (`until` в прошлом).

Дойти до этого состояния можно ровно одним способом — процесс перестал писать, — но причин у этого несколько:

| Причина | Что произошло |
|---|---|
| процесс убит | падение, `SIGKILL`, нехватка памяти — писать некому |
| сервер выключился | питание, ядро, перезагрузка мимо штатной остановки |
| процесс жив, но не достаёт до хранилища | сеть разошлась: запись не проходит, аренда всё равно истекает |
| процесс жив, но замер целиком | виртуалка приостановлена, долгая пауза сборщика мусора: дублёр стоит вместе с циклом |

Третья и четвёртая строки — самые интересные: в хранилище всё выглядит как смерть, а процесс при этом работает.

Для четвёртой правило осталось прежним: процесс не имеет права действовать по одной только своей памяти. Аренда на камеру считается по внутренним часам и кончается за пять секунд до того, как кто-то снаружи успеет её перехватить.

С третьей строкой с тех пор появилась оговорка (`Lease.may_record` в `w2cplatform/epoch.py`). Аренда, которая истекла, пока хранилище **молчало**, — это не аренда, которую кто-то забрал: сказать «эпоха кончилась» было некому. Поэтому **данные** — поток камеры и её события — идут дальше под той же эпохой. **Действия** — щёлкнуть реле, повернуть камеру — останавливаются строго через 25 секунд. На кластере данные идут не дольше `UNCONFIRMED_MAX = 90` секунд сверх этих 25 (так задано в `deploy/vmsworker.nomad.hcl`). Подробнее — в разделах [5.2](05-workers-and-epochs.md) и 8.7.

### Когда именно слот становится просроченным

Срок отсчитывается не от смерти, а от **последнего удачного продления**, и всегда ровно 45 секунд:

```
T+0.0    последнее удачное продление: until = T+45
T+3.1    процесс умирает — в хранилище не меняется ничего
T+45.0   until обгоняют часы: слот просрочен
```

Поскольку продления идут примерно раз в 10 секунд, момент смерти отстоит от просрочки на 35–45 секунд. Быстрее узнать нельзя, и это цена того, что хранилище узнаёт о смерти не от умершего, а по молчанию.

### Просроченный и отпущенный — разные вещи

Их легко перепутать, а реакция на них противоположная:

| Состояние слота | Как выглядит строка | Что это значит | Кто и что делает |
|---|---|---|---|
| **держится** | `released: false`, `until` в будущем | процесс жив | никто ничего |
| **просрочен** | `released: false`, `until` в прошлом | умер, не попрощавшись | контроллер не трогает; имя ждёт замену |
| **отпущен** | `released: true` | ушёл по-хорошему | контроллер тут же раздаёт его камеры |

Обычно разницу создаёт сам процесс при остановке. На штатный `SIGTERM` он успевает дописать строку `released: true` — это уменьшение числа экземпляров или вывод сервера. При падении дописывать некому, и молчание остаётся единственным свидетельством.

Но тот же флаг может поднять и контроллер, когда оператор говорит ему, что процесс не вернётся (`Controller.retire`). Это второй и последний способ получить `released: true`, и запросы у него те же самые. Разбор — в справочнике, в разделе «А теперь — как контроллер помечает слот отпущенным» ([01-reference.md](01-reference.md)).

Отсюда и правило: **просроченный слот — работа планировщика, отпущенный — работа контроллера.** Разбирать камеры упавшего воркера незачем, потому что имя ему вернут вместе с назначением: под Nomad замена приходит с тем же номером аллокации и берёт слот этого номера, а безымянная замена сама выбирает просроченный слот первым.

Как это выглядит у замены, видно в трассе урока `М11_ClusterVMS/traces/04-a-crash-releases-nothing.txt`. Номер аллокации для слота — пожелание, которое процесс исполняет условной записью: он берёт свой слот, **даже если срок прежнего держателя ещё не вышел**. Планировщик — авторитет в вопросе, какой процесс сейчас настоящий, а прежний узнает об этом при своём продлении (`Worker.claim_slot(prefer=…)`).

```
GET /v1/var/platform/schema
GET /v1/vars?prefix=vms/slots/
GET /v1/var/vms/slots/w-2
GET /v1/var/vms/slots/w-2
PUT /v1/var/vms/slots/w-2?cas=1006
{"Items": {"holder": "alloc-0099", "until": "1757500105.0", "released": "false", "gen": "2"}}

GET /v1/var/objects/vms/heartbeats/w-2      ← heartbeat прежнего экземпляра: отсюда меряется перерыв
GET /v1/var/vms/workers/w-2                 → {"units": "1", "rev": "1"}
GET /v1/var/vms/cameras/1
```

### Что просроченный слот не отменяет

Строки слотов никто не удаляет. Просроченный `w-2` продолжает лежать в хранилище, попадает в листинг и ждёт того, кто его подберёт.

Подобравший поднимает `gen` на единицу и вписывает себя в `holder`. Этим закрывается случай «мертвец ожил»: если прежний процесс всё-таки вернётся и попробует продлить аренду, он прочитает чужого держателя, поймёт, что имя уже не его, и погасит все свои пайплайны. Что он делает дальше — в разделе 8.7.

И один момент, который стоит держать в голове отдельно: **просрочка слота и устаревание heartbeat'а — разные факты**, хотя порог у обоих 45 секунд. Heartbeat решает, входит ли воркер в пул размещения; слот решает, кому принадлежит имя. Именно поэтому один сигнал не заменяет другой.

И поэтому признать **сервер** потерянным контроллер соглашается только по двум независимым молчаниям сразу (`SpecController.gone_servers`): слот просрочен и остаётся таким ещё 45 секунд, а ресурс на том же сервере тоже не отвечает. Одно молчание — это упавший процесс, и его переселяет планировщик; два — это факт про сервер, и тогда камеры двигает контроллер. Работает это при политике `servers: distinct`; при `shared` дохлый сервер целиком остаётся заботой планировщика.

Если бы процесс останавливали **по-хорошему** (уменьшили число экземпляров, выводят сервер), он успел бы записать `released: true`, и тогда контроллер на ближайшем проходе раздал бы его камеры живым воркерам. Записи те же три, что в разделе 8.4, и в том же порядке — решение первым:

```
# 1. Переписать решение о размещении — только если строка всё ещё называет w-2
PUT /v1/var/vms/placement/2?cas=4449

{
  "Items": {
    "worker": "w-1",
    "reason": "slot w-2 released; most free capacity (49); on srv-1",
    "at": …,
    "rev": "2"
  }
}

# 2. Убрать камеру у прежнего воркера
PUT /v1/var/vms/workers/w-2?cas=…
{"Items": {"units": "", "rev": "2"}}

# 3. Добавить новому
PUT /v1/var/vms/workers/w-1?cas=…
{"Items": {"units": "1,2", "rev": "2"}}
```

Отпустивший слот выпадает и из пула: на него не поставят новую камеру на том же проходе, на котором с него увозят старые (`SpecController._pool`).

**Одно поле `released` отделяет «подожди, он вернётся» от «его больше не будет».**

## 8.7. Две копии `w-2` ожили одновременно

Такое бывает при перезапуске, когда старый процесс не умер, а завис. Nomad поднимает замену с тем же номером аллокации. Она берёт слот `w-2` — условной записью поверх живого ещё держателя, как разобрано в конце раздела 8.6, — читает назначение и поднимает камеру 2, а значит берёт новую эпоху:

```
# новый процесс
PUT /v1/var/vms/slots/w-2?cas=1011
{"Items": {"holder": "alloc-2b", "until": "1757500050.0", "released": "false", "gen": "2"}}

GET /v1/var/vms/workers/w-2     → 200 {"Items": {"units": "2", "rev": "1"}}
GET /v1/var/vms/cameras/2
GET /v1/var/vms/epoch/2         → 200 {"Items": {"epoch": "1"}}
PUT /v1/var/vms/epoch/2?cas=1024    {"Items": {"epoch": "2"}}
                                → 200
```

Старый узнаёт об этом на ближайшем шаге продления — не позже чем через 10 секунд после того, как снова заработал. И узнаёт уже **на слоте**: до эпох дело не доходит.

```
# старый процесс
GET /v1/var/platform/schema     → 404
GET /v1/var/vms/slots/w-2
→ 200 {"Items": {"holder": "alloc-2b", "until": "1757500050.0", "released": "false", "gen": "2"}}
                                                                   ← а держатель был alloc-2
```

Это всё, что он прочитал на этом шаге. Чужой держатель в строке слота значит одно: имя отобрали, и этот экземпляр — лишний. С этой строки он **никто** (`VmsWorker.lease_pass`, затем `Worker.give_up_name`):

- гасит все свои пайплайны, а не только камеру 2 (`fence`);
- ничего не говорит под именем `w-2`. Раньше он слал heartbeat с `fenced: true` поверх законного, пока не перезапустят. Теперь heartbeat под чужим именем не уходит вовсе (`Worker.heartbeat` молчит, пока экземпляр в состоянии `seeking`);
- назначение `w-2` для него пусто, эпоху он взять не может (`take_epoch` бросает `NoSlot`), дублёр за него ничего не продлевает.

Раньше отсечённый экземпляр так и стоял — живой, ничего не продлевающий и ничего не пишущий, — пока кто-нибудь не перезапустит его руками. Супервизор не перезапускает процесс, который не умер. Теперь на следующем проходе он берёт **свободный** слот и начинает с нуля (`VmsWorker.rejoin`):

```
# старый процесс, следующий проход
GET /v1/var/platform/schema
GET /v1/var/platform/schema
GET /v1/vars?prefix=vms/slots/          → w-1, w-2, w-3
GET /v1/var/vms/slots/w-1
GET /v1/var/vms/slots/w-2
GET /v1/var/vms/slots/w-3
GET /v1/var/vms/slots/w-4               → 404
PUT /v1/var/vms/slots/w-4?cas=0
{"Items": {"holder": "alloc-2", "until": "1757500058.0", "released": "false", "gen": "1"}}

GET /v1/var/vms/workers/w-4             → 404     ← назначения нет: начинает пустым
PUT /v1/var/objects/vms/heartbeats/w-4
{"Items": {"data": {"worker": "w-4", "status": [], …, "fenced": false, "conflicts": 0,
                    "was_fenced": "slot w-2 is held by another instance now", …, "headroom": 50, …}}}
```

Порядок кандидатов тот же, что у любого безымянного процесса: сначала просроченные слоты, потом свободные, потом новый номер. Здесь просроченных и свободных нет, поэтому `w-4`. Если взять слот не вышло — хранилище моргнуло, кандидатов разобрали из-под рук, — экземпляр остаётся никем и пробует снова на каждом проходе. Раньше в этом месте он оставался со старым именем: снова читал чужое назначение и слал heartbeat поверх законного. У детекторов ревью так нашло два процесса, по очереди бравших одни и те же детекторы (`Worker.keep_slot`).

Для контроллера `w-4` — четвёртый воркер с пятьюдесятью свободными местами. Поле `was_fenced` в его heartbeat'е и есть след того, что случилось.

Обратите внимание на `conflicts: 0`. Счётчик `vms_epoch_conflicts` в этом случае **не растёт**: старый экземпляр отсечён на слоте и до эпох не дошёл. Растёт он, когда сменилась эпоха, а слот по-прежнему мой. И тогда, начиная с обратной связи BC, останавливается **одна** камера, а не весь воркер:

```
# слот мой, а эпоха камеры 2 сменилась — так выглядит переназначение
GET /v1/var/vms/epoch/1         → 200 {"Items": {"epoch": "1"}}
GET /v1/var/vms/epoch/2         → 200 {"Items": {"epoch": "2"}}   ← а моя была 1
GET /v1/var/vms/epoch/3         → 200 {"Items": {"epoch": "1"}}
```

Пайплайн камеры 2 останавливается, её эпоха отдаётся, камеры 1 и 3 работают дальше. Если камера 2 по-прежнему в моём назначении, воркер поднимет её снова, со своей задержкой и под новой эпохой. Слот продлён строкой выше, значит, второго экземпляра меня нет, и останавливать пятьдесят камер из-за одной незачем (трасса `М11_ClusterVMS/traces/09-a-reassignment-is-not-a-zombie.txt`; разбор обоих исходов — в разделе [5.2](05-workers-and-epochs.md)).

Сколько старый успел сделать под эпохой 1, пока не узнал? Если он работал и связь с хранилищем была, — до своего ближайшего шага продления, то есть до 10 секунд. Если он замер и очнулся, — меньше: на первом же круге после паузы с прошлого продления прошло больше 8,3 секунды, и шаг продления идёт сразу за проходом и вычерпыванием шины.

Если же он жив, но **не достаёт до хранилища**, узнать ему не у кого. Тогда работают два предела:

- **Действия** — команды устройству — он перестаёт выполнять через `30 − 5 = 25` секунд после последнего подтверждения. Их проверяет строгий `may_write`.
- **Данные** — поток и события камеры — идут под эпохой 1 ещё до `UNCONFIRMED_MAX = 90` секунд сверх этих 25, то есть до 115 секунд после последнего подтверждения (`Lease.may_record`, `Lease.unconfirmed`). Условие одно: молчание хранилища должно начаться, пока аренда ещё действовала. Такую цену выбрали в обратной связи BK: остановка стоит дыры в данных, а лишняя запись под старой эпохой — только дубля. Эпоха стоит в пути каждой корзины событий, и то, что писал отсечённый экземпляр, видно и потом.

На кластере третий предел ставит сам Nomad. Клиент, потерявший связь с серверами, через 25 секунд останавливает задачу сам: в задании воркера стоит `stop_on_client_after = "25s"`.

## 8.8. Камер больше, чем ёмкости: кто запускает второй воркер

Разберём вопрос прямо: воркер объявил `capacity: 50`, а камер сто. Откуда возьмётся второй процесс?

Короткий ответ: **сама система его не запустит, и Nomad сам ни о чём не догадается.** Ни контроллер, ни консоль не умеют запускать процессы — контроллер умеет только писать строки. Nomad про камеры не знает вовсе: для него `vmsworker` — это `count = N` одинаковых экземпляров, и `N` меняют ровно двое: человек и автомасштабатор.

### Что происходит, пока никто не поменял `count`

Ничего драматического. Контроллер разложит первые пятьдесят камер, а на пятьдесят первой посчитает свободную ёмкость и получит ноль:

| Камера | capacity | load до | свободно | результат |
|---|---|---|---|---|
| …50 | 50 | 49 | 1 | размещена на `w-1` |
| 51 | 50 | 50 | **0** | **не размещена** — строки размещения не появилось |
| …100 | 50 | 50 | 0 | то же самое |

Лишние камеры просто ждут. Они созданы, их строки лежат в хранилище, `GET /where/51` вернёт `worker: null`. Никакого частичного размещения или переполнения воркера не происходит: контроллер либо кладёт камеру целиком, либо не кладёт вовсе.

Ждут они не бесплатно. Каждый проход контроллер пробует разместить каждую ждущую камеру заново. Камеры VMS группируются по устройству (`group_by: device`), и для каждой такой попытки контроллер перечитывает строки **всех** камер кластера — ищет, не стоит ли уже где-нибудь канал того же устройства (`SpecController.worker_with_group`).

Я прогнал настоящий код контроллера над хранилищем в памяти и посчитал запросы. Сто камер на одном воркере ёмкостью 50 — это 7 384 чтения за проход. Пятьдесят камер на том же воркере, без ждущих, — 834. Каждая ждущая камера добавляет к проходу примерно столько чтений, сколько в кластере камер. Что это значит в масштабе — раздел [10.2](10-limits-and-scale.md).

Важная деталь: в `/unplaceable` такие камеры **не появятся**. Этот маршрут отвечает только на «ни один сервер до неё не дотягивается» — это про метки, а не про ёмкость. Переполнение видно по другим числам:

```
vms_headroom 0                       ← свободной ёмкости в кластере нет
vms_worker_load{worker="w-1"} 1.000  ← назначено ÷ capacity
```

### Как из этих чисел получается второй процесс

Цепочка замкнута не через код системы, а через штатные части Nomad, и в ней четыре звена:

| Звено | Что делает | Откуда число |
|---|---|---|
| консоль | отдаёт `/metrics` | суммирует heartbeat'ы воркеров |
| Prometheus | снимает эти метрики | сервис консоли помечен тегом `metrics` |
| Nomad Autoscaler | считает `avg(vms_worker_load)` и сравнивает с целью `0.9` | запрос к Prometheus |
| Nomad | меняет `count` и размещает новый экземпляр | решение автомасштабатора |

Рамки задаёт джобспек, и это решение человека, а не системы: `min = 1`, `max = 12`, цель загрузки `0.9`, проверка раз в минуту, пауза после изменения — пять минут.

На наших числах: загрузка `1.0` против цели `0.9` даёт новый `count = 2`. Сто камер на два воркера — это снова `1.0`, и следующий шаг поднимет `count` до трёх. Цель `0.9`, а не `1.0`, как раз и оставляет запас, чтобы кластер не жил впритык.

Обратите внимание, чем меряется нагрузка: **назначено ÷ ёмкость**, а не процессор. Так сделано намеренно — воркер с сорока процентами процессора и исчерпанным назначением полон, и никакой график загрузки CPU этого не покажет.

### Сколько это занимает

Минуты, а не секунды: проверка раз в минуту, пауза пять минут после каждого изменения. Пауза сознательно длиннее перезапуска воркера — иначе обычное переселение упавшего экземпляра читалось бы как рост спроса, и кластер раздувался бы от каждой аварии.

### Слабое место: сигнал не умеет сказать «насколько»

Здесь у цепочки есть изъян, и его лучше знать заранее. Метрика `vms_worker_load` — это `назначено ÷ ёмкость`, а контроллер никогда не назначает сверх ёмкости. Значит, выше `1.0` она не поднимается **никогда**: и при одной лишней камере, и при пятистах лишних она показывает ровно единицу. `vms_headroom` — свободная ёмкость — точно так же упирается в `0` и дальше молчит.

Число, которое назвало бы глубину очереди, в консоли теперь есть: `vms_units_unplaced` — сколько камер ни на ком. Но консоль берёт его из отчёта о проходе, который контроллер пишет в хранилище (`SpecController.pass_once`, объект `vms/controller/pass`). Контроллер одиночной коробки так и делает (`vmsserver/vms/__main__.py`). Контроллер кластера — нет: в `М11_ClusterVMS/clustervms/cluster/__main__.py` он гоняет те же четыре шага по отдельности и `pass_once` не вызывает. Отчёта в хранилище нет, и на кластере эта метрика показывает `0`. А политика автомасштабатора её не читает вовсе. Так что на кластере **сколько камер ждёт размещения, по-прежнему не сообщает ни одна метрика, которую кто-то смотрит**.

Автомасштабатор поэтому работает вслепую и растёт долями. Цель `0.9` при загрузке `1.0` даёт ему множитель `1 ÷ 0.9 ≈ 1.11`, то есть примерно плюс девятую часть за шаг — и так шаг за шагом, каждый с пятиминутной паузой:

| Кластер | Шагов до нужного числа воркеров | Сколько ждать |
|---|---|---|
| 100 камер, 1 воркер → нужно 2–3 | 2 | ~10 минут |
| 600 камер, 1 воркер → нужно 12 | ~10 | около часа |

Вывод из этого практический: **на плановый ввод большой партии камер автомасштабатор рассчитывать нельзя.** Он хорош там, где нагрузка ползёт вверх сама, и бесполезен там, где её добавляют разом. Партию заводят вместе с `nomad job scale`, заранее и руками. Тем более что весь этот час каждая ждущая камера стоит контроллеру прочтения всех строк на каждом проходе.

Быстро добавить воркера можно и руками: `nomad job scale vmsworker 3`. Это тот же самый рычаг, просто дёрнутый человеком.

> Ещё одна причина не полагаться на эту цепочку прямо сейчас: в репозитории она не собрана до конца. Джоб автомасштабатора есть, но ACL-политика под его токен не заведена, а Prometheus, у которого он спрашивает метрику, отдельным джобом не развёрнут. То есть на стенде из этого документа `count` меняет только человек.
>
> Рядом с ним в деплое есть джоб `vms-scaler` — та же петля без Prometheus, со своей политикой `scale-job`. Но он масштабирует только рекордеры, по числу объявленных томов архива, которые некому держать. Воркеров VMS он не трогает.

### Что происходит дальше, и почему без единого уведомления

```
Nomad поднял вторую аллокацию
  → процесс берёт слот своего номера: PUT /v1/var/vms/slots/w-2?cas=0
  → пишет heartbeat: capacity 50, headroom 50
  → ближайший проход контроллера (не позже чем через 5 с) видит нового воркера
  → размещает на него ожидающие камеры
```

Никто никого не звал. Контроллер не знает про автомасштабатор, автомасштабатор не знает про камеры, новый воркер не знает, что его позвали из-за нехватки ёмкости.

### Куда встанет второй воркер

Джобспек просит `spread` по узлам, а не `distinct_hosts`: Nomad ставит воркеров на разные серверы, пока может, и удваивает на одном, когда иначе никак. От переуплотнения коробку защищает не VMS, а собственный учёт Nomad — у задачи объявлены `cpu = 2000` и `memory = 2048`, и второй экземпляр не встанет на узел, где столько не свободно.

А вот **повезёт ли второму воркеру на том же сервере получить камеры** — это уже решение администратора, а не планировщика, и живёт оно в строке `vms/policy`:

| Значение `servers` | Что значит |
|---|---|
| `shared` (по умолчанию) | камеры берут все воркеры, в том числе два на одном сервере |
| `distinct` | камеры несёт один воркер на сервер, лишний числится простаивающим по политике |

Отсюда и ответ на исходный вопрос в его буквальной форме: сто камер на одном сервере возможны — как два процесса по пятьдесят при политике `shared`, — но это выбор администратора, который он делает, зная бюджет коробки. Система такое не назначает сама.

## 8.9. Строка в хранилище не читается

Этого отказа в первой версии разбора не было, а ревью находило его семь раундов подряд, каждый раз в новой таблице. Строку в хранилище поправили руками, запись оборвалась на середине, её писала другая сборка — и в поле, где ждут число, оказалось слово. Раньше такую строку читали «как есть», исключение вылетало из цикла по многим строкам, и неприятность одной строки останавливала проход для всех.

Теперь все таблицы читаются через один читатель, `w2cplatform/rows.py`. Строка, которая не разбирается, — это неприятность **только этой строки**. Её пропускают, считают один раз, пока она не починится, и называют в журнале. Что значит «пропустить», решает тот, кто читает. Два примера из нашего сценария.

**Испорчена строка слота `w-2`.** Скажем, кто-то вписал руками `"until": "завтра"`. Сам `w-2` на ближайшем продлении читает её как строку, которую писал сам, и переписывает целиком, условной записью:

```
GET /v1/var/vms/slots/w-2
→ 200 {"Items": {"holder": "alloc-2", "until": "завтра", "released": "false", "gen": "1"}, "ModifyIndex": 1028}

PUT /v1/var/vms/slots/w-2?cas=1028
{"Items": {"holder": "alloc-2", "until": "1757500055.0", "released": "false", "gen": "1"}}
→ 200
```

Безымянный процесс, ищущий себе слот, такую строку кандидатом не считает. А в heartbeat'е `w-2` появляется `"slots_garbled": 1`, и консоль отдаёт его на `/metrics` как `vms_worker_slots_garbled{worker="w-2"}` (`read_slot` и `Worker._own_slot` в `w2cplatform/contract.py`).

**Испорчена строка эпохи камеры 2** — `{"epoch": "два"}`. Хранилище ответило, но не эпохой. Это не молчание, через которое можно писать дальше: кто-то переписал счётчик, и, может быть, отдал камеру. Поэтому аренда камеры 2 отсекается, как если бы номер сменился, и пайплайн останавливается (`Lease.renew`). Новую эпоху из такой строки не выдать, и камера не стартует, пока строку не починят. Но это неприятность одной камеры: камеры 1 и 3 на соседних воркерах ничего не заметили. Причина видна прямо в статусе камеры:

```
GET /v1/var/vms/epoch/2
→ 200 {"Items": {"epoch": "два"}, "ModifyIndex": 1028}

PUT /v1/var/objects/vms/heartbeats/w-2
{… "status": [{"id": 2, …, "phase": "failed", "epoch": 0, …,
               "why": "its epoch could not be taken: invalid literal for int() with base 10: 'два'"}], …}
```

С остальными таблицами так же. Строка камеры, испорченная **после** размещения, не останавливает воркер: он держит камеру по строке, прочитанной в прошлый раз, и пишет в статусе `why: "its row does not parse: …; going on with the row read last"`. Контроллер такую строку пропускает и считает (`SpecController.units`). Назначение со словом в `rev` читается ради списка камер, который в нём записан, с `rev 0` (`read_assignment`).
