## Справка: HTTP API configstore

Всё хранилище системы — это три запроса. Больше их нет, и всё, что в документе дальше, собрано из них.

| Что нужно | Запрос |
|---|---|
| прочитать один ключ | `GET /v1/get?key=<ключ>` |
| перечислить ключи по префиксу | `GET /v1/list?prefix=<префикс>` |
| записать или удалить один ключ | `POST /v1/write {"op": "put" \| "delete", "key", "cas", "items"}` |

Запрос идёт не по сети, а в unix-сокет демона `configstore` на **своём** сервере: `/run/configstore/<роль>.sock`. Демон сам решает, кто в группе лидер, и доносит до него запись. Процесс об этом не знает: он говорит только со своим сервером (`w2cplatform/configstorevars.py`).

Две вещи клиентская ручка добавляет к каждому запросу, а трассы их не печатают. Первая — заголовок `X-Deadline`: сколько ручка готова ждать ответа. Вторая — поле `"id"` в каждой записи, свежий номер операции. По нему демон узнаёт повтор, если запись ушла лидеру, а ответа не пришло: на повтор он отдаёт первый ответ и не применяет запись второй раз (`storemachine.StoreMachine`). Ключ в строке запроса трассы тоже показывают без %-кодирования: `key=vms/cameras/1`, а не `key=vms%2Fcameras%2F1`.

### Чтение одного ключа

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/cameras/2
→ 200 {
  "items": {
    "id": "2",
    "revision": "1",
    "name": "Парковка",
    "source": "driverpack://acme/10.2.0.12",
    "enabled": "true",
    "priority": "100",
    "labels": "vlan:cctv",
    "folders": "",
    "ref": "",
    "cred_username": "",
    "cred_secret": "",
    "live": "always",
    "kind": "video"
  },
  "index": 1010
}
```

В ответе два поля:

| Поле ответа | Что это | Зачем |
|---|---|---|
| `items` | сами данные, плоский набор «ключ → строка» | это и есть значение |
| `index` | версия ключа | чтобы записать обратно с условием «версия та же» |

Больше в ответе ничего нет: ни времени создания, ни времени правки. `index` — номер команды в журнале raft, которая последней записала ключ, плюс база группы. Номера в журнале не повторяются никогда, поэтому версия, запомненная до перезапуска демона или смены лидера, ни с чем новым не совпадёт. На стенде база — 1000, и номер растёт только с записями. На живом демоне чтения тоже идут командами журнала, поэтому номера там растут быстрее. В записках все `index` условные.

**Значения в `items` всегда строки.** Число `100` лежит как `"100"`, признак «включена» — как `"true"`, список меток — как `"vlan:cctv,floor:2"`. Разбор обратно в числа и списки делает читатель.

**Ключа нет — это тоже `200`**, только пустой:

```
# vmsworker w-srv-a-1 on srv-a → /run/configstore/vmsworker.sock
GET /v1/get?key=vms/slots/w-srv-a-1
→ 200 {"items": null, "index": ""}
```

Ручка читает это как «значения нет, версия 0». Отсюда правило, которое встретится в документе десяток раз: **`"cas": ""` означает «записать, только если ключа ещё нет»**.

### Запись одного ключа

Значение кладётся **целиком**. Обновить одно поле нельзя: прочитал всё, подменил поле, записал всё обратно. Так консоль правит камеру 2 в [части 7](07-edit-and-delete.md):

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/cameras/2", "cas": 1010, "items": {
  "id": "2",
  "revision": "2",
  "name": "Парковка",
  "source": "driverpack://acme/10.2.0.12",
  "enabled": "true",
  "events_retention_days": "30",
  "priority": "100",
  "labels": "vlan:cctv",
  "folders": "",
  "ref": "",
  "cred_username": "",
  "cred_secret": "",
  "live": "always",
  "kind": "video"
}}
→ 200 {"index": 1023}
```

`index` в ответе — **новая** версия ключа. Её и надо предъявлять в следующей записи.

`cas` означает «запиши, только если версия сейчас ровно такая». Три случая:

| `cas` в записи | Смысл | Когда так пишут в сценарии |
|---|---|---|
| `""` | записать, только если ключа не существует | создание камеры, взятие слота и эпохи, захват ключа идемпотентности, первое размещение, первый `vms/next_id` |
| `1010` | записать, только если версия сейчас 1010 | любая правка существующей строки |
| `null` | записать безусловно, затерев чужое | `platform/decommission/<сервер>` (консоль) и `vms/decommissioned/<сервер>` (контроллер): у каждой строки один писатель |

Раньше безусловно писали heartbeat'ы и снапшот. Теперь это файлы на сервере писателя (ниже), и в хранилище их нет.

### Что приходит, когда записать не вышло

Отказы означают разное, и тело у каждого — `{"kind", "error", …}`.

**Версия не совпала — кто-то записал раньше:**

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/next_id", "cas": "", "items": {"n": "1"}}
→ 409 {"kind": "conflict", "error": "vms/next_id: cas='' but the version is 1009", "index": 1009}
```

Это не авария, а `409` значит «твоя версия устарела». Текущую версию демон кладёт в тело, но читатель ею не пользуется. Он перечитывает ключ, накладывает свою правку на свежее значение и пробует снова — до десяти раз подряд. Между попытками он выжидает случайную, растущую паузу (`cas_pause` в `w2cplatform/contract.py`): без неё те же двое тут же столкнулись бы снова. Как это выглядит у двух операторов сразу — раздел [8.2](08-failures.md).

**Сокету не разрешён этот ключ** (трасса урока 5 М11):

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/workers/w-srv-a-1", "cas": null, "items": {"units": "7"}}
→ 403 {"kind": "forbidden", "error": "console may not write vms/workers/w-srv-a-1"}
```

Так консоль узнаёт, что размещение не её дело. Отказывает демон её же сервера, до того как переслать запись лидеру. Подробнее — в следующем разделе.

**Ключ, который не ключ.** `400` с `kind` `badkey`: пустой ключ, `..` или слэш в начале, или ключ длиннее 246 байт. Предел длины взят от файлового хранилища коробки: ключ, перенесённый с коробки в кластер и обратно, должен оставаться именем файла.

**Хранилище не ответило.** `503` с `kind` `unavailable` значит: лидера нет, запись **не** сделана. `503` с `kind` `ambiguous` значит: лидер ушёл, не ответив, и запись ещё может примениться. Повторять её можно только с тем же `id`. Ручка превращает оба ответа в ошибку «хранилище не ответило», и никогда — в «нет»: воркер держит то, что держал, и пробует снова.

**Потолка на размер записи больше нет.** На Nomad запись была ограничена 64 КиБ, и консоль заранее отвечала оператору `413`. У демона `configstore` потолка нет (`max_bytes = 0`). Проверка в коде осталась, но срабатывает, только если хранилище само объявит потолок (`w2cplatform/limits.py`).

### Удаление

```
POST /v1/write {"op": "delete", "key": "<ключ>", "cas": <версия>}
→ 200 {"index": N}
```

Удаление — такая же запись: с условием по версии, и оно тоже занимает номер в журнале. Два удаления не делает никто, какие бы права ни были: строку эпохи (эпоха — счётчик, удалённая начнётся снова с 1) и строки `domain/*` (их удаляют только роли самого домена). В нашем сценарии удалений нет: даже `DELETE /cameras/3` в [части 7](07-edit-and-delete.md) не удаляет строку, а ставит в ней пометку `deleted`.

### Перечисление по префиксу

```
# vmscontroller on srv-a → /run/configstore/vmscontroller.sock
GET /v1/list?prefix=vms/cameras/
→ 200 {"keys": {"vms/cameras/1": 1008, "vms/cameras/2": 1010, "vms/cameras/3": 1012}}
```

**Обратите внимание, чего здесь нет: значений.** Листинг отдаёт только ключи и их версии. Чтобы получить данные трёх камер, нужны ещё три `GET`.

Отсюда растёт `N+1` — обход, где на один листинг приходится по чтению на каждый найденный ключ. На трёх камерах это четыре запроса, на шестистах — шестьсот один.

Зато версия в листинге есть у каждого ключа, и по ней можно было бы дочитывать только изменившиеся строки. Сейчас ручка её выбрасывает: `list` отдаёт процессу только отсортированные ключи. Про это подробно в записках [«Куда попадает настройка камеры»](../where-camera-settings-go.md), часть 2.

**Листинг отвечает только то, что роли можно читать.** Ключи, на чтение которых у сокета нет права, демон молча выбрасывает из ответа (`storemachine.answer`). Поэтому листинг не падает, а становится короче, и это надо помнить, когда права узкие.

#### Что вообще считается префиксом

Здесь кроется главное недоразумение, поэтому скажу прямо: **префикс — это просто начало строки ключа, а не каталог.**

Никаких каталогов в хранилище нет. Есть плоский список ключей, где ключ — строка вида `vms/cameras/1`. Слэши в ней ничего не значат для демона: он берёт ваш префикс и оставляет те ключи, что с него начинаются. Ровно как сравнение строк.

Из этого следуют вещи, которые иначе выглядят загадочно:

| Запрос | Что вернёт | Почему |
|---|---|---|
| `prefix=vms/cameras/` | `vms/cameras/1`, `vms/cameras/2`, `vms/cameras/3` | все ключи, начинающиеся с этих 12 символов |
| `prefix=vms/cameras/1` | `vms/cameras/1`, а также `vms/cameras/17` | это по-прежнему сравнение строк, а не «камера номер один» |
| `prefix=vms/camera` | **всё то же самое** | слэш не обязателен, префикс может обрываться посреди слова |
| `prefix=vms/` | все камеры, размещения, назначения, слоты, эпохи, счётчик, ключи повторов | всё, что начинается с `vms/` |
| `prefix=vms` | то же самое | и заодно `vmsfoo/…`, если бы такой ключ завели |
| `prefix=` (пусто) | **всё, что этой роли можно читать** | пустая строка — начало любой строки; остальное отсеют права |

Поэтому во всех запросах документа префикс кончается слэшем: `vms/cameras/`, `vms/slots/`, `platform/doors/`. Слэш здесь — не украшение, а **граница**. Без него `vms/camera` однажды поймает соседний ключ, которого в момент написания кода ещё не существовало.

Один процесс в системе пользуется пустым префиксом — консоль, когда собирает временную шкалу событий. Ей нужны эпохи всех подсистем сразу, поэтому она перечисляет всё хранилище и отбирает ключи, содержащие `/epoch/`. Это единственное такое место, и оно осознанное исключение. Права консоли на чтение — `vms/*`, `rec/*`, `platform/*` и строки домена, поэтому эпохи других подсистем в такой листинг не попадут.

#### Раскладка ключей: что под каким префиксом лежит

Раз префикс — это начало строки, то **раскладка ключей и есть структура хранилища**. Вот вся раскладка нашего сценария:

| Префикс | Что под ним лежит | Кто пишет | Кто его перечисляет |
|---|---|---|---|
| `vms/cameras/` | по строке на камеру | консоль | консоль (список для UI), контроллер (проход) |
| `vms/placement/` | по решению на камеру: где ей работать и почему | контроллер | контроллер |
| `vms/workers/` | по назначению на воркера: что ему запускать | контроллер | контроллер, консоль (`/where`) |
| `vms/slots/` | по строке на имя воркера: кто его держит и до когда; ещё — предложения слотов для запасных | воркер, контроллер | воркер при старте, контроллер |
| `vms/epoch/` | по токену ограждения на камеру: `{epoch: N}` | воркер | консоль (временная шкала) |
| `vms/idem/` | по ключу на каждый POST оператора | консоль | консоль (подчистка) |
| `vms/retention/` | срок хранения событий — только у камер, которым срок задан явно | консоль | ресурс сервера |
| `vms/alarms_retention/` | то же для тревог, у которых свой срок | консоль | ресурс сервера |
| `vms/servers/` | что сервер достигает, словами администратора из консоли: `{labels}` | консоль | контроллер (в сценарии пусто) |
| `vms/decommissioned/` | отметка контроллера, что списание сервера исполнено | контроллер | контроллер, консоль (`/servers`) |
| `vms/holds/` | по занятому месту: какой из объявленных администратором томов взял процесс | воркер | контроллер (в сценарии пусто) |
| `vms/devices/` | по строке на устройство: что оно умеет, со слов воркера, который его держит | воркер | читают по имени (автоматика) |
| `vms/requests/` | по заявке оператора на разовую работу вне обычного прохода | консоль | воркер (каждые 250 мс), консоль (уборка) |
| `objects/vms/commands/` | по отметке «начинаю выполнять заявку» — единственный «объект», который строка (ниже) | воркер | воркер (уборка) |
| `platform/doors/` | по строке на сервер: где отвечает его ресурс, `{url, since}` | ресурс | ресурсы друг друга |
| `platform/decommission/` | по заявке оператора на списание сервера | консоль | контроллеры; воркер читает строку своего сервера при старте |

И одиночные строки, которые **не** префиксы: `vms/next_id` (счётчик), `vms/policy` (настройка администратора), `vms/sweep` (что уборка больших полей пометила к удалению и когда), `platform/drain` (какой сервер выводят, ниже) и `platform/schema` (версия формата хранилища; в нашем кластере её нет). Их читают по имени.

Ещё консоль на каждом запросе оператора читает строки домена — `domain/keys`, `domain/member`, `domain/root`, `domain/grants`, `domain/revoked`, `domain/break_glass` — и по ним решает, спрашивать ли, кто звонит. В нашем кластере их нет. Домен — служба платформы; его строки пишет его агент через свой сокет `domainagent`.

Ключа, которым запечатаны пароли камер, в хранилище больше нет. Раньше это была строка `secrets/vms`, теперь это файл `/etc/w2c/secrets/platform.key` на каждом сервере. Его получают как учётные данные `systemd` (`LoadCredential=`) только три юнита: консоль, воркер и регистратор. Ни одна роль хранилища не читает строк под `secrets/` (`test_the_clusters_key_is_a_credential_of_the_three_units_that_open_a_password_and_no_row`). Как это выглядит в строке камеры — в [части 3](03-creating-a-camera.md).

Видно правило, по которому всё это разложено: **`<подсистема>/<вид записи>/<кого она касается>`**. Подсистема первая, потому что подсистем несколько (`vms`, `rec`, `live`, `det`) и каждая живёт в своём куске хранилища; платформа — `platform/`. Вид записи второй, потому что именно он определяет писателя. Имя камеры, воркера или сервера — последним.

Имя стоит последним не для красоты. Благодаря этому право выражается одной строкой `vms/epoch/*`, а читатель перечисляет один префикс и ничего не отсеивает — под ним не лежит ничего постороннего. **Префикс, который нельзя назвать в файле прав, — это ошибка раскладки, а не нехватка возможностей у прав.**

#### Один и тот же префикс — это сразу три вещи

Последнее, что делает раскладку важнее, чем кажется. Одна и та же строка живёт в трёх разных местах:

| Где | Как выглядит | Что означает |
|---|---|---|
| ключ в хранилище | `vms/cameras/1` | где лежат данные |
| право в файле прав | `"write": ["vms/cameras/*", …]` у роли `console` | кому разрешено туда писать |
| каталог на диске сервера | `<архив>/vms/1/e1/…` | куда воркер кладёт события этой камеры |

Поэтому имя единицы проверяется на входе. У камер это неважно — им номер выдаёт счётчик, — но в подсистемах, где имя единицы придумывает оператор, слэш или `..` сломали бы все три вещи по-разному: ключ раздвоился бы, право совпало бы не с тем префиксом, а каталог уехал бы вверх по дереву. Такое имя консоль отклоняет с `400`, а не пытается починить.

#### Порядок в ответе — лексикографический

Ещё одна мелочь, о которую легко споткнуться. Демон отдаёт ключи как строки, отсортированные посимвольно:

```
vms/cameras/1
vms/cameras/10
vms/cameras/100
vms/cameras/2
```

Числового порядка тут нет и быть не может: в ключе лежит текст. Читатели сортируют по номеру уже после того, как прочитали строки. Для нашего сценария из трёх камер это незаметно, а вот постраничный список в UI на такой сортировке ломается — страницы надо резать по ключам **до** чтения значений.

### Объекты — файлы на своём сервере

Heartbeat'ы воркеров и ресурсов, отчёт прохода контроллера и срезы снапшота в коде называются «объектами». В хранилище их нет: каждый объект — файл на сервере того, кто его пишет, в каталоге объектов этого сервера (`OBJECTS=cluster:///data/platform/objects?…` в `/etc/w2c/w2c.env`). У каждого объекта один писатель, и почти каждый он переписывает на следующем же такте, поэтому согласие трёх серверов ему не нужно (`clustervms/cluster/objectstore.py`).

**Запись — это файл на своём диске.** По сети при этом ничего не идёт. В трассах она выглядит так:

```
# vmsworker w-srv-a-1 on srv-a → its own files on srv-a
PUT vms/heartbeats/w-srv-a-1
```

Содержимое я привожу отдельным блоком после такой строки — как обычный JSON, с размером в байтах.

**Чтение чужого — через ресурс своего сервера.** Процесс спрашивает ресурс на своём сервере с `scope=cluster`, а тот спрашивает ресурсы остальных серверов (их адреса — в `platform/doors/*`) и отдаёт самую свежую копию:

```
# vmscontroller on srv-a → the resource on srv-a, http://srv-a:8090
GET /v1/objects/vms/heartbeats/w-srv-b-1?scope=cluster
→ 200 {"bytes": 484, "X-Written": "1757500000.0", "X-Server": "srv-b"}

# vmscontroller on srv-a → the resource on srv-a, http://srv-a:8090
GET /v1/objects?prefix=vms/heartbeats/&scope=cluster
→ 200 {
  "server": "srv-a",
  "objects": {
    "vms/heartbeats/w-srv-a-1": {"written": 1757500000.0, "server": "srv-a", "size": 484},
    "vms/heartbeats/w-srv-b-1": {"written": 1757500000.0, "server": "srv-b", "size": 484},
    "vms/heartbeats/w-srv-c-1": {"written": 1757500000.0, "server": "srv-c", "size": 484}
  }
}
```

На самом деле ответ на чтение одного объекта — сами байты файла, а время записи и сервер приходят в заголовках `X-Written` и `X-Server`. Трасса пишет вместо байтов их число. Объекта нет ни на одном сервере — `404`. Если какой-то сервер не ответил, его имя приходит в `X-Missing` у чтения и в поле `missing` у листинга: читатель знает, чего он не увидел, и не путает молчание с отсутствием.

Ключи объектов этого сценария:

| Ключ объекта | Чей файл | Кто читает |
|---|---|---|
| `vms/heartbeats/<воркер>` | воркера, на его сервере | контроллер, консоль, сам воркер при старте |
| `platform/resources/<сервер>/heartbeat` | ресурса, на его сервере | контроллер, консоль |
| `vms/controller/pass` | контроллера, на его сервере | консоль (`/metrics`), контроллер в начале прохода |
| `vms/snapshot/<воркер>`, `vms/snapshot/unplaced` | контроллера, на его сервере | домен (М12), контроллер |
| `vms/blobs/<хеш>` | консоли; ресурс копирует их соседям | кто разворачивает большое поле строки |

**Потолка в 64 КиБ у объектов больше нет.** Он был у переменных Nomad и ушёл вместе с ними. Срезы снапшота по воркерам остались: снапшот по-прежнему режется так, на случай хранилища, которое потолок объявит.

Одно исключение. Отметку «начинаю выполнять заявку» воркер должен создать **один раз на весь кластер**: два держателя одного устройства могут стоять на двух серверах, а «создать, если нет» у файла работает только на одном диске. Поэтому такая отметка — строка хранилища `objects/vms/commands/*`, записанная с `"cas": ""`. Это единственный «объект», который лежит в хранилище.

Листинги объектов читатель на кластере помнит секунду (`LIST_FRESH = 1.0`), прежде чем спросить снова. На стенде, с которого сняты трассы, эта память выключена, поэтому запросов объектов в трассах больше, чем будет в жизни.

## Кто звонит: сокет роли

Короткий ответ: **процесс не предъявляет ничего — демон знает, кто звонит, по тому, в какой сокет пришёл запрос**. Токена нет ни в файле, ни в окружении, ни в заголовке.

### Как это устроено

Демон хранилища на каждом сервере открывает по сокету на роль: `/run/configstore/<роль>.sock`, права 0660, группа — группа этой роли (`vms-vmsworker`, `vms-console`, `w2c-resource`…). Юнит процесса входит в группу своей роли и называет сокет этой роли, например юнит воркера:

```ini
SupplementaryGroups=vms-vmsworker
Environment=PLATFORM_STORE=configstore:///run/configstore/vmsworker.sock
```

Процесс, чей юнит в группе `vms-vmsworker`, может открыть сокет воркера и никакой другой. Для демона этот сокет и есть то, кто звонит. Сокет — строка юнита, а не общего файла окружения: строка `PLATFORM_STORE` в `/etc/w2c/w2c.env` отдала бы права одной роли всем процессам сервера. Поэтому скрипт запуска `w2c-run.sh` берёт строки файлов, только если юнит их не задал (М11, урок 3).

Ещё есть `admin.sock`, права 0600: его может открыть только пользователь демона и root. Через него ходят команды администратора, и через него же снят срез хранилища в [части 2](02-before-first-camera.md). Демоны разных серверов друг друга узнают иначе — по сертификатам одной CA (М11, урок 5), но процессы стенда этой двери не касаются.

### Что этот сокет разрешает

Права демон читает из файла `/etc/w2c/configstore-rights.json`. В репозитории это `clustervms/deploy/configstore-rights.json`, и его не пишет никто: его печатает `python3 -m cluster rights` из тех же списков, по которым код решает, что ему писать. `install.sh` устаревший файл не ставит. Права воркера целиком:

```json
"vmsworker": {
  "group": "vms-vmsworker",
  "read":   ["platform/schema", "vms/*", "platform/decommission/*", "domain/keys", "domain/member", "objects/vms/commands/*"],
  "write":  ["vms/epoch/*", "vms/slots/*", "vms/holds/*", "vms/devices/*", "objects/vms/commands/*"],
  "delete": ["vms/epoch/*", "vms/slots/*", "vms/holds/*", "vms/devices/*", "objects/vms/commands/*"]
}
```

Шаблон со звёздочкой в конце — префикс, без звёздочки — один точный ключ. Шаблон с `!` в начале — запрет, и запреты спрашиваются раньше разрешений (`storemachine.Rights.allows`). В файле курса запретов пока нет.

Читается так: воркер **пишет** свои эпохи, свой слот, занятое место, описания устройств, которые держит, и отметки «начинаю выполнять заявку». Удалять он может то же, что пишет, кроме строки эпохи: её не удаляет никто. **Читает** он всю подсистему `vms/`, версию схемы, заявки на списание серверов и ровно две строки домена, которые спрашивает его дверь воспроизведения. Грантов домена и хеша аварийного пароля воркер не читает (`test_the_holder_reads_no_more_of_the_domain_than_its_door_asks`). Занятое место (`vms/holds/*`) — это том архива, который процесс взял из объявленных администратором. Устроено как слот, только имена кандидатов придумывает не воркер. В нашем сценарии томов не объявляли, и эти ключи пусты.

### Четыре сокета этого сценария

У каждого процесса свой сокет и свои права. Именно они, а не договорённость в коде, делят ключи между процессами:

| Сокет (роль) | Пишет | Читает |
|---|---|---|
| **`console.sock`** | `vms/cameras/*`, `vms/next_id`, `vms/idem/*`, `vms/policy`, `vms/sweep`, `vms/requests/*`, `vms/servers/*`, `vms/retention/*`, `vms/alarms_retention/*`, `platform/drain`, `platform/decommission/*`; строки записи под `rec/` | `vms/*`, `rec/*`, `platform/*`, шесть строк домена и `domain/grants/*` |
| **`vmscontroller.sock`** | `vms/workers/*`, `vms/placement/*`, `vms/slots/*`, `vms/decommissioned/*` | `vms/*`, `rec/*`, `platform/*` |
| **`vmsworker.sock`** | `vms/epoch/*`, `vms/slots/*`, `vms/holds/*`, `vms/devices/*`, `objects/vms/commands/*` | `vms/*`, `platform/schema`, `platform/decommission/*`, `domain/keys`, `domain/member`, `objects/vms/commands/*` |
| **`resource.sock`** | `platform/doors/*` | `platform/doors/*`, `platform/mirror`, `platform/space`, `platform/schema`, сроки хранения каждой подсистемы (`<подсистема>/retention`, `…/retention/*`, то же для `alarms_retention`), `rec/recordings/*`, `rec/keeps/*` |

Самая узкая роль — у ресурса. Из подсистем он не пишет ничего, а читает только сроки хранения и строки записи — то, что нужно, чтобы убирать и зеркалить события своего сервера.

Heartbeat'ов, срезов снапшота и отчётов прохода в этой таблице нет. Это файлы на сервере писателя, строк под них в хранилище нет, и права их писать строкой нет ни у кого (`test_nothing_writes_what_it_has_no_business_writing`).

Ключ `vms/slots/*` — единственный общий. Воркер слот **берёт** и **отпускает**, а контроллер делает со слотом только две вещи: пишет **предложение** слота для запасного процесса и **отпускает** слот, под которым больше ничего не работает. Оба пишут в строку с условием по версии, поэтому одновременная запись её не портит. Предложение выглядит так (раздел [8.8](08-failures.md)):

```
# vmscontroller on srv-a → /run/configstore/vmscontroller.sock
POST /v1/write {"op": "put", "key": "vms/slots/w-2", "cas": "", "items": {
  "holder": "",
  "until": "0",
  "released": "false",
  "gen": "0",
  "offer": "vlan:cctv",
  "offered_at": "1757500000.0"
}}
→ 200 {"index": 1024}
```

Строка без держателя, с набором меток, для которого не хватает воркера. Её по CAS забирает запасной, которого поднял `w2c-spares.sh` с `SPARE_FOR=vlan:cctv`.

#### Сначала — чем оператор пользуется обычно: `platform/drain`

Прежде чем разбирать, как контроллер отпускает слот, стоит назвать ту строку, которой оператор действительно распоряжается, иначе следующий раздел повисает в воздухе. Когда машину собираются остановить — обновить, перезагрузить, увезти, — оператор говорит это **консолью**, и его слова ложатся в одну строку на весь кластер. В трассах сценария этой записи нет, запросы ниже собраны по коду (`Controller.drain`):

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=platform/drain
→ 200 {"items": null, "index": ""}           ← никого не выводят

# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "platform/drain", "cas": "", "items": {"server": "srv-b", "at": "1757500050.0"}}
→ 200 {"index": …}
```

Строка одна и не начинается с `vms/`, потому что выводят **машину**, а на ней живут воркеры всех подсистем сразу. Выводить можно только один сервер за раз: попытка объявить второй, пока не закончился первый, отклоняется — обновление идёт по очереди, иначе кластер из трёх серверов разом теряет две трети.

Дальше никого не уведомляют. Контроллер и так читает эту строку на каждом проходе (вы видели её в разделе [4.1](04-placement.md)) и делает из неё два вывода: на воркеров выводимого сервера новые камеры не ставить, а те, что на них есть, увезти к живым — с причиной `server srv-b draining`. Смысл в слове «заранее»: выключи сервер молча, и кластер узнает об этом только по молчанию, и всё это время камеры лежат.

Строку слота вывод сервера при этом **не трогает вовсе**. Машина вернётся, `systemd` поднимет процесс под тем же именем, и тот заберёт своё назначение обратно.

#### А теперь — как контроллер отпускает слот

Это уже другой и куда более редкий случай: процесс под этим именем не вернётся никогда.

Вся власть контроллера над чужим слотом сводится к одному: он может **пометить слот отпущенным** (`Controller.free_slot` в `w2cplatform/contract.py`). Занять слот, переименовать или удалить его контроллер не может. Он читает строку, поднимает в ней один флаг и записывает обратно с условием по версии. Так это выглядит, когда оператор списал сервер `srv-c` (трасса 08-10):

```
# vmscontroller on srv-a → /run/configstore/vmscontroller.sock
POST /v1/write {"op": "put", "key": "vms/slots/w-srv-c-1", "cas": 1006, "items": {
  "holder": "srv-c:4103",      ← не трогает
  "until": "1757500045.0",     ← не трогает
  "released": "true",          ← единственное изменение
  "gen": "1"                   ← не трогает
}}
→ 200 {"index": 1029}
```

Три правила этой операции:

- **Меняется ровно один флаг.** Ни имя держателя, ни срок, ни поколение контроллер не переписывает: он не претендует на слот, а только сообщает о нём факт.
- **Повторный вызов ничего не делает.** Если `released` уже `true` или слот снова продлили, контроллер не пишет вовсе — записи без изменений в этой системе не делаются. Одно исключение: строку слота, которая не разбирается, `free_slot` переписывает целиком — `released: true`, без держателя.
- **По одному молчанию он так не решает.** Молчащий воркер — это упавший процесс, а его `systemd` поднимет под тем же именем, и тот заберёт своё назначение. Что делать со слотом, который перестал продлеваться, контроллер решает одним правилом, `slot_fate`: ждать (`wait`) или увести камеры (`move`). Слот при этом остаётся как был, кроме двух случаев ниже. В развёртке М11 воркер у ресурса не регистрируется (`present()` не вызывается), поэтому при живом сервере ответ — `wait`: камера ждёт, пока systemd поднимет процесс. Уводят её только два молчания сразу — слот истёк **и** ресурс сервера молчит. Разбор — в разделе [8.6](08-failures.md).

Отпускает слот контроллер в двух случаях:

1. **Оператор списал сервер.** Консоль пишет заявку `platform/decommission/<сервер>`, и каждый контроллер на ближайшем проходе отпускает слоты всех воркеров этого сервера (раздел [8.10](08-failures.md)).
2. **Ресурс сервера жив и говорит, что такого воркера у него больше нет.** Слот истёк, воркер молчит, а ресурс его сервера отвечает и в списке своих воркеров его не называет. Значит, процесс с машины убрали, и под этим именем там ничего не поднимется (`release_unlisted`). Ресурс знает своих воркеров, только если те ему представились (`Worker.present`). Юнит воркера курса этого не делает, раздел [8.6](08-failures.md).

Дальше ничего особенного не происходит. В том же проходе контроллер, как и каждые пять секунд, просматривает слоты, видит среди них отпущенный с непустым списком камер и раздаёт эти камеры живым воркерам — с причиной `slot w-srv-c-1 released; …`. Отдельной процедуры «разобрать списанного воркера» в системе нет: пометка просто делает слот заметным для шага, который и так выполняется на каждом проходе.

> **Списание сервера в курсе.** Списать оператор может только **сервер**, а не воркер. Воркер — это слот, и какие слоты существуют, решают юниты и контроллер. Оператор знает другое: машина сгорела или её навсегда вынули из стойки. Маршрут консоли — `POST /servers/<сервер>/decommission {"why": "…"}`, право — `admin` на весь кластер. `DELETE` того же пути возвращает сервер. Трасса 08-10, разбор — в разделе [8.10](08-failures.md):
>
> 1. Пока сервер отвечает хоть по одному из трёх признаков — ресурс слышен, воркер этого сервера слышен, слот воркера продлевается, — консоль отвечает `409` с признаком словами и ничего не пишет: `"srv-c answers: its resource was heard 0 s ago — take the server out of service and switch it off first"`. Сервер, чей ресурс не был слышен никогда, проходит с предупреждением: тут остаётся только слово оператора.
> 2. Когда сервер молчит, консоль пишет заявку `platform/decommission/srv-c` — `{by, at, why}` — и отвечает `202` со списком воркеров, камер и томов, которые на нём были. Строку слота консоль не трогает: права на `vms/slots/*` у её сокета нет. Консоль, которая могла бы писать слоты, была бы вторым контроллером с браузером впереди.
> 3. Каждый контроллер на ближайшем проходе снова проверяет три признака, отпускает слоты воркеров сервера и пишет отметку `vms/decommissioned/srv-c` — `{asked_at, at, slots, units, holds}`, — чтобы заявка исполнилась один раз. Камеры уезжают в том же проходе: камера 3 переехала на `w-srv-a-1`.
> 4. Пока заявка стоит, на сервер ничего не ставят, а процесс на нём слот не получит: воркер читает `platform/decommission/<свой сервер>` при старте.
>
> **Тома списание не освобождает.** Занятое место `vms/holds/*` остаётся за списанным; консоль называет такие тома в ответе и в `/servers`, и объявление тома, сгоревшего вместе с сервером, администратор отзывает сам.
>
> Чем это отличается от простой смерти воркера: камеры мёртвого сервера контроллер уводит и без списания, по двум молчаниям (слот истёк **и** ресурс сервера молчит, раздел [8.6](08-failures.md)). Списание добавляет другое: сервер выходит из размещения насовсем, процесс, вернувшийся под этим именем, слот не получит, а консоль показывает сервер как списанный.

> **В продукте (vmssubsystem)** раньше было списание **слота**: `POST /workers/<w>/retire` и заявка `<подсистема>/retire/<w>`, которую исполнял контроллер. Его убрали: оно смотрело на одно молчание — аренду слота и heartbeat воркера — и разрешало списать воркер, который завис, но ещё пишет. У его камер появлялся второй писатель. Теперь продукт устроен так же, как курс: оператор списывает сервер (`platform/decommission/<сервер>`, отметка `<подсистема>/decommissioned/<сервер>`), а слоты, которые ресурс живого сервера больше не называет, контроллер отпускает сам (`ReleaseUnlisted`; `vmsworker/w2cplatform/decommission.go`). Одно отличие правила: третий признак «сервер отвечает» продукт засчитывает, только пока слот продлевается, а курс ждёт ещё 45 секунд после истечения слота, как и везде, где решает судьбу слота.

Порт контроллеру так и не нужен, а консоль по-прежнему не пишет размещение. Списание остаётся словом человека — система лишь доносит его до процессов, которым позволено его исполнить.

### Почему это важно для сценария

Когда в [части 3](03-creating-a-camera.md) консоль отвечает `worker: null`, это не вежливость и не недоработка. Консоль **физически не может** записать размещение: её сокету такой ключ не разрешён, и демон ответит ей `403`.

Проверить это можно на живом сервере: `deploy/verify-bench.sh` стучится в настоящие сокеты настоящего демона и ожидает `200` на своё и `403` на чужое. Стенд, с которого сняты трассы, делает то же на каждой сцене: каждый процесс ходит через сокет своей роли с правами закоммиченного файла, и запись без права падает `403` прямо на стенде.

**Чтение тоже проверяется, и по тем же правам.** `get` ключа, который роли читать нельзя, — `403`. Листинг отвечает только то, что роли читать можно (`storemachine.answer`). Демон и стенд отвечают одной и той же функцией, поэтому на стенде права на чтение проверялись при каждом запросе этих трасс, и ни одно чтение не получило `403`. Тесты `test_every_row_the_code_reads_is_granted` и `test_the_gate_and_the_schema_are_readable_by_every_process_that_asks_them` сверяют каждое чтение стенда и чтения, которых стенд не касается, с файлом прав.

Раньше здесь стояла пометка `[TODO]` о правах на чтение на живом Nomad. Тогда стендовое хранилище чтение не проверяло, и я сверял политики с трассами глазами. Нашлись два расхождения: в политиках консоли и воркера не было `domain/*` и `platform/schema`, а у контроллера `path "*"` открывал ему ключ паролей. Оба закрыты. Строки домена и `platform/schema` есть в правах всех ролей, которые их читают. Ключа паролей в хранилище больше нет, а контроллер читает только `vms/*`, `rec/*` и `platform/*`. Один пробел остаётся: `verify-bench.sh` на живом сервере проверяет только записи. Чтение на живом демоне проверяет тот же код, что и на стенде, но отдельно его там никто не пробует.
