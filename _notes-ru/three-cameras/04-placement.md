[← карта разбора](README.md) · назад: [03-creating-a-camera.md](03-creating-a-camera.md) · вперёд: [05-workers-and-epochs.md](05-workers-and-epochs.md)


`T+3.4` — контроллер просыпается. Этот проход и есть главное событие сценария.

Контроллер — юнит `vms-vmscontroller.service`, и стоит он на каждом сервере (урок 3 М11). В живом кластере их три, и все три делают один и тот же проход раз в пять секунд. Разбираем проход контроллера на `srv-a`. Как три контроллера при этом не раскладывают одну камеру трижды — в разделе 4.3.

Один проход — это `pass_once(1)` и `publish_snapshot()` внутри одного `one_pass` (`cluster/__main__._placement_pass`). Внутри прохода каждый ключ хранилища и каждый объект спрашиваются один раз и дальше берутся из памяти прохода; после прохода память выбрасывается. Поэтому в трассе почти каждый запрос встречается один раз, хотя код спрашивает одно и то же по многу раз.

Хранилище контроллер спрашивает через сокет своей роли, `/run/configstore/vmscontroller.sock`. Объекты (heartbeat'ы, отчёт прохода, снапшот) — это файлы на серверах, и чужие объекты он читает через ресурс своего сервера, `http://srv-a:8090`, с `scope=cluster`.

## 4.1. Что контроллер читает, прежде чем решить

**Отчёт прошлого прохода.** Самое первое — объект, который прошлый проход записал о себе (`pass_report`): из него берутся счётчики, которые копятся от прохода к проходу (`failures`, `last_success`, `*_total`).

```
GET /v1/objects/vms/controller/pass?scope=cluster
→ 200 {"bytes": 775, "X-Written": "1757500000.0", "X-Server": "srv-a"}
```

Его записал пустой проход по кластеру без камер (раздел [2.5](02-before-first-camera.md)).

**Списания серверов** (`apply_decommissions`). Оператор не списывал ни одного сервера, и контроллер ни одного не списал:

```
GET /v1/list?prefix=platform/decommission/   → 200 {"keys": {}}
GET /v1/list?prefix=vms/decommissioned/      → 200 {"keys": {}}
```

**Слоты и их судьба** (`release_unlisted`, через `fates`). По каждому занятому слоту контроллер решает, что с ним (`slot_fate`, урок 8 М11): жив ли процесс, не умер ли сервер. Для этого он читает строку слота и heartbeat его воркера:

```
GET /v1/list?prefix=vms/slots/
→ 200 {"keys": {"vms/slots/w-srv-a-1": 1004, "vms/slots/w-srv-b-1": 1005, "vms/slots/w-srv-c-1": 1006}}

GET /v1/get?key=vms/slots/w-srv-a-1
→ 200 {"items": {"holder": "srv-a:4101", "until": "1757500045.0", "released": "false", "gen": "1", "server": "srv-a"}, "index": 1004}

GET /v1/objects/vms/heartbeats/w-srv-a-1?scope=cluster
→ 200 {"bytes": 570, "X-Written": "1757500000.0", "X-Server": "srv-a"}

… то же для w-srv-b-1 (heartbeat с "X-Server": "srv-b") и w-srv-c-1 ("X-Server": "srv-c")
```

`X-Server` — сервер, на диске которого лежит файл. Heartbeat `w-srv-b-1` лежит на `srv-b`, и ресурс `srv-a` сходил за ним к ресурсу `srv-b` (урок 6 М11). Все три слота заняты, не отпущены и продлены до `until`; в каждом сказано, на каком сервере держатель (`server`). Отпускать нечего, переносить не с кого. Размеры heartbeat'ов здесь стендовые — 570 байт; в юните они 509 (раздел [2.3](02-before-first-camera.md)).

**Размещения и назначения.** Шаги `unplace_deleted`, `unplace_retired` и сверка `sync_assignments` спрашивают один и тот же листинг `vms/placement/`. В проходе он прочитан один раз:

```
GET /v1/list?prefix=vms/placement/   → 200 {"keys": {}}   ни удалённых, ни завершённых, ни решений
GET /v1/list?prefix=vms/workers/     → 200 {"keys": {}}   назначений ещё нет
```

Сверка `sync_assignments` нужна вот зачем. Каждый проход начинается с того, что строки `vms/workers/*` приводятся к тому, что говорят строки `vms/placement/*`: камера дописывается воркеру, которого назвало решение, и вычёркивается у любого другого. Две записи размещения делаются по очереди (раздел 4.3), и контроллер может упасть между ними.

**Камеры.** Листинг отдаёт ключи вместе с их версиями, но не значения. Значения приходится дочитывать по одному:

```
GET /v1/list?prefix=vms/cameras/
→ 200 {"keys": {"vms/cameras/1": 1008, "vms/cameras/2": 1010, "vms/cameras/3": 1012}}

GET /v1/get?key=vms/cameras/1
→ 200 {
  "items": {
    "id": "1",
    "revision": "1",
    "name": "Ворота",
    "source": "driverpack://acme/10.2.0.11",
    "enabled": "true",
    "priority": "100",
    "labels": "vlan:cctv",
    "folders": "",
    "ref": "",
    "cred_username": "",
    "cred_secret": "",
    "live": "always",
    "kind": "video"
  },
  "index": 1008
}

GET /v1/get?key=vms/cameras/2   → «Парковка», driverpack://acme/10.2.0.12, "index": 1010
GET /v1/get?key=vms/cameras/3   → «Склад», driverpack://acme/10.2.0.13, "index": 1012
```

Версии из листинга контроллер не запоминает до следующего прохода: между проходами он не помнит ничего, чтобы его можно было убить в любом месте. Поэтому строки он перечитывает на каждом проходе.

Теперь камера 1 (`place`). Сначала — нет ли уже решения. Строку камеры `place` тоже спрашивает, но она уже в памяти прохода, запроса нет:

```
GET /v1/get?key=vms/placement/1
→ 200 {"items": null, "index": ""}   решения ещё нет
```

Потом пул кандидатов (`_pool`):

```
# кто вообще живой — heartbeat'ы не старше 45 секунд (сами объекты уже прочитаны выше, при слотах)
GET /v1/objects?prefix=vms/heartbeats/&scope=cluster
→ 200 {"server": "srv-a", "objects": {
    "vms/heartbeats/w-srv-a-1": {"written": 1757500000.0, "server": "srv-a", "size": 570},
    "vms/heartbeats/w-srv-b-1": {"written": 1757500000.0, "server": "srv-b", "size": 570},
    "vms/heartbeats/w-srv-c-1": {"written": 1757500000.0, "server": "srv-c", "size": 570}}}

# у чьего сервера жив ресурс — спецификация VMS требует resource
GET /v1/objects?prefix=platform/resources/&scope=cluster    → три heartbeat'а ресурсов, по 649 байт
GET /v1/objects/platform/resources/srv-a/heartbeat?scope=cluster
GET /v1/objects/platform/resources/srv-b/heartbeat?scope=cluster
GET /v1/objects/platform/resources/srv-c/heartbeat?scope=cluster
→ свежие: live, live, live

# политика размещения: shared или distinct
GET /v1/get?key=vms/policy        → 200 {"items": null, "index": ""}   умолчание: shared

# не выводят ли сервер на обслуживание
GET /v1/get?key=platform/drain    → 200 {"items": null, "index": ""}   никто не выводится
```

Отпущенные слоты и списанные серверы тоже вычёркиваются из пула, но эти строки уже прочитаны в начале прохода.

Пул: `[w-srv-a-1, w-srv-b-1, w-srv-c-1]`.

Дальше — фильтр по меткам, и его стоит разобрать отдельно.

### Что такое `labels` и зачем они

Метка отвечает на один вопрос: **до какой камеры этот сервер физически дотягивается по сети.**

Камеры стоят в разных сегментах: одни в служебной сети видеонаблюдения, другие в демилитаризованной зоне, третьи на удалённой площадке за туннелем. Сервер видит не все сегменты — у него столько сетевых интерфейсов, сколько ему дали. Камера в сегменте `cctv` с сервера без интерфейса в этом сегменте просто не откроется: ни потока, ни записи, ни тревог.

Значит эту физику нужно как-то сообщить контроллеру, иначе он разложит камеры красиво по ёмкости и половина из них не подключится. Метки и есть такое сообщение, и объявляют их **с двух сторон**:

| Сторона | Что объявляет | Откуда берётся | Где лежит |
|---|---|---|---|
| **камера** | из какого сегмента её видно | оператор пишет при создании | поле `labels` строки камеры |
| **сервер** | какие сегменты он достаёт | администратор пишет `LABELS=` в файл платформы `/etc/w2c/w2c.env` на сервере; воркер читает его при старте. Поверх этого администратор может задать метки сервера в консоли | поле `labels` heartbeat'а воркера; строка консоли `vms/servers/<srv>`, если её завели |

Формат один и тот же: список строк вида `имя:значение`, разделённых запятой. Ничего, кроме сравнения строк, система с ними не делает — смысл `vlan:cctv` или `site:msk-hq` знает только человек, который их придумал. Алфавит у меток один и для камеры, и для сервера: буквы, цифры и `_ . : -`, до 64 символов (`LABEL_WORD`).

Метки сервера контроллер читает так (`labels_of`). Если у сервера есть строка `vms/servers/<srv>`, действует она. Если строки нет — метки из heartbeat'а воркера. Строки читаются по ключу для каждого сервера, на котором стоят воркеры (`server_labels`). Листинг их тоже называет, но, если он какую-то строку пропустит, она всё равно будет прочитана по ключу. В нашем сценарии строк нет ни у кого:

```
GET /v1/list?prefix=vms/servers/       → 200 {"keys": {}}
GET /v1/get?key=vms/servers/srv-a      → 200 {"items": null, "index": ""}
GET /v1/get?key=vms/servers/srv-b      → 200 {"items": null, "index": ""}
GET /v1/get?key=vms/servers/srv-c      → 200 {"items": null, "index": ""}
```

значит у всех трёх серверов действует то, что сказал воркер: `"labels": "vlan:cctv"` из `LABELS=vlan:cctv`.

> **В продукте (vmssubsystem) метку сервера правят из консоли — и в курсе теперь тоже:** `PUT /servers/<server>/labels` пишет строку `vms/servers/<server>`, и сервер, потерявший метку, увозит свои камеры на сервер с ней (или снимает их с размещения с причиной) на следующем проходе контроллера, не больше десяти за проход (`ensure_reach`, `REACH_BUDGET = 10`; М10A урок 11). Без такой строки метка сервера живёт в файле на диске узла (`LABELS` в `/etc/w2c/w2c.env`), и, чтобы её поменять, нужно править файл и перезапускать воркеров: `LABELS` воркер читает при старте. Строку пишет консоль, право — `admin` на весь кластер; API — `PUT /servers/<server>/labels {"labels": [...]}`, `DELETE` возвращает метки узла, `GET …/labels?labels=a,b` заранее говорит, какие камеры уедут (`would_move`). Пустой список `[]` означает «не видит ни одной сети», а не «строки нет». Метку сервера, который никто не объявлял, консоль не пишет: опечатка в имени — 400, а не строка, которую никто не читает.
>
> Кто главнее: если строка есть, действует она; если нет — `LABELS` узла, как здесь. Так `LABELS` остаётся первым значением и запасным вариантом. `GET /servers` отдаёт `labels`, `labels_node` и `labels_source` (`console` | `node`), и консоль показывает оба значения, когда они расходятся.
>
> Перезапускать воркеров не нужно. Метки — утверждение о физике сети, и правит их человек в одном месте, рядом с камерами, у которых тот же формат. Отвергнутый вариант — менять метки самого узла из консоли: консоли понадобились бы права на чужую машину, работающий воркер новую метку не увидел бы без перезапуска, и появились бы две правды.

### Правило сравнения: подмножество, а не пересечение

Воркер подходит камере, если **все** метки камеры есть у его сервера. Не «хотя бы одна общая», а именно все. В спецификации VMS это `constraint: labels-subset`.

| Метки камеры | Метки сервера | Подходит? |
|---|---|---|
| `vlan:cctv` | `vlan:cctv` | да, точное совпадение |
| `vlan:cctv` | `vlan:cctv`, `site:msk-hq`, `gpu` | **да** — у сервера больше, чем требуется, и это нормально |
| `vlan:cctv`, `site:msk-hq` | `vlan:cctv` | **нет** — второй метки у сервера нет |
| пусто | `vlan:cctv` | **да** — пустой список требований выполняет кто угодно |
| `vlan:cctv` | пусто | нет |

Четвёртая строка — важный практический случай. Камера без меток размещается **где угодно**, и на площадке с одной плоской сетью это ровно то, что нужно: не заполняйте поле, и фильтр не будет мешать.

Обратное несимметрично: чем больше меток у камеры, тем меньше серверов ей подходит. Метка — это **требование**, а не пожелание.

### Это фильтр, а не предпочтение

Разница принципиальная, и она видна по тому, что происходит, когда подходящих серверов нет.

Ёмкость — это предпочтение: заполненный воркер уступает свободному, но камера всё равно куда-нибудь встанет. Метка так не работает. Если её не может выполнить ни один сервер, камера **не размещается вовсе** и ждёт — потому что поставить её на сервер, который до неё не дотянется, значит получить вечно падающий пайплайн вместо честного «не могу».

Именно так устроен раздел [8.3](08-failures.md): камера с меткой `vlan:cctv-dmz` создаётся нормально, но остаётся без размещения, и консоль отвечает на вопрос «почему» отдельным маршрутом `/unplaceable`.

И формулировка отказа поэтому звучит как «система не дотягивается», а не «воркеры переполнены». Это разные аварии и чинятся они по-разному: первая — сетью или меткой на сервере, вторая — ещё одним воркером.

> **Метка, поменявшаяся после размещения.** И в курсе, и в продукте метка решает не только следующее размещение. В проходе контроллера сразу после размещения есть шаг `ensure_reach` (в продукте — `EnsureReach`): если у уже размещённой камеры или у её сервера метки поменялись так, что сервер её больше не видит, камера переезжает на сервер, который её видит, не больше десяти за проход. Причина начинается словами `srv-a no longer reaches vlan:cctv`. Если не видит никто — камера снимается с размещения с причиной и попадает в `/unplaceable`. Каналы одного прибора переезжают все вместе или ждут. Работает для обеих сторон — и для меток камеры, и для меток сервера. В нашем проходе этот шаг ничего не сдвинул: в отчёте прохода `reach_moves: 0`.

### В нашем сценарии

У всех трёх камер метка `vlan:cctv`, у всех трёх серверов она же. Проверка `{vlan:cctv} ⊆ {vlan:cctv}` проходит у всех троих, пул остаётся полным — и дальше решает уже ёмкость.

Метка попадает и в причину размещения (`reaching vlan:cctv`), и в снапшот, который уезжает на доменный слой. Первое — чтобы человек видел, по какому требованию выбирали; второе — чтобы слой над кластером знал, куда эту камеру вообще можно переселить.

### Второй фильтр: один прибор — один воркер

В спецификации VMS рядом с метками стоит ещё строка `group_by: device`. Она про другую физику: **прибор — это одно соединение**. Шестнадцать каналов одного видеорегистратора — шестнадцать строк камер, и если разложить их по ёмкости на четыре воркера, к прибору откроются четыре сессии, а лицензирован он, скажем, на две. Отказ тогда придёт словами прибора — «слишком много сессий», канал не стартует, — и ничто в нём не укажет на решение о размещении, принятое на другом сервере час назад.

Поэтому правило жёсткое, как и метки: камера, у которой уже есть размещённые соседи по прибору, идёт **только** на их воркер. Места там нет — камера не размещается и ждёт. В ответе `/unplaceable` её при этом не будет: этот маршрут перечисляет камеры, которым не подходит ни один живой воркер (`unplaceable` в `w2cplatform/spec.py`), а здесь подходящий есть, он просто полон. Если же воркер соседей перестал подходить камере (например, его сервер больше не видит её метку), камера в `/unplaceable` попадает, и там написано, у кого держат её прибор. Растекаться по соседям группе не дают, потому что растекание и есть то, от чего правило защищает. Одно исключение: если воркер соседей сам выпал из пула (умер, уходит, сервер выводят), группу он за собой не держит, и она собирается заново там, куда ляжет первая камера. Первую камеру группы контроллер ставит туда, где есть место для всех её неразмещённых каналов, если такой воркер есть (`_room_for_group`).

Поля «прибор» в строке камеры нет. Его вычисляет сама подсистема из источника (`VmsController.group_value` → `device_of` в `vms/config.py`): у `driverpack://<производитель>/<адрес>/ch/<n>` прибор — это `<производитель>/<адрес>`, канал отбрасывается. Платформа схему `driverpack://` не знает и знать не должна, поэтому у неё крючок, а разбор — в коде VMS.

В нашем сценарии фильтр ничего не решает: у трёх камер три разных прибора — `acme/10.2.0.11`, `acme/10.2.0.12`, `acme/10.2.0.13`, у каждого по одному каналу. Группы из одной камеры ничем не ограничены.

### Что эти два фильтра стоят в запросах

Оба фильтра — функция `eligible`. Метки воркера она берёт из строки сервера или из его heartbeat'а, а соседей по прибору ищет среди всех строк камер. И то, и другое уже в памяти прохода: heartbeat'ы прочитаны при слотах, строки камер — в начале, строки серверов — четыре запроса выше. Группы по прибору строятся один раз за проход (`_rows_by`). Своих запросов у фильтров нет.

### Последнее чтение перед решением

Есть ли у камеры запись, рядом с которой ей стоять (раздел 4.2), — один листинг heartbeat'ов подсистемы записи:

```
GET /v1/objects?prefix=rec/heartbeats/&scope=cluster
→ 200 {"server": "srv-a", "objects": {}}   записывающих воркеров нет
```

И сколько камер уже назначено каждому — по строке назначения на воркера. Ёмкость воркера — из его heartbeat'а, он уже прочитан:

```
GET /v1/get?key=vms/workers/w-srv-a-1   → 200 {"items": null, "index": ""}   назначений нет, load = 0
GET /v1/get?key=vms/workers/w-srv-b-1   → 200 {"items": null, "index": ""}   load = 0
GET /v1/get?key=vms/workers/w-srv-c-1   → 200 {"items": null, "index": ""}   load = 0
```

## 4.2. Как он выбирает: одно вычитание

> **Всё, что дальше в этом разделе, — сменная часть.** Правило выбора принадлежит контроллеру и только ему: ни воркер, ни консоль, ни доменный слой не знают и не спрашивают, как он выбирал. Правила берутся по имени из небольшого каталога — в спецификации это ключи `constraint` и `tie_break`, — и подсистема вправе зарегистрировать там своё, кодом под именем (`register_constraint`). Сегодня в каталоге два ограничения (`none`, `labels-subset`) и одно разрешение ничьей, а рядом с ними — два фильтра по полю строки, `group_by` и `spread_by`; завтра их может стать больше, и на остальную систему это не повлияет никак.
>
> Не повлияет потому, что **результат записывается всегда одинаково: одна строка `vms/placement/<камера>` и одна `vms/workers/<воркер>`.** Эти две записи и есть контракт со всей системой, разбор — в разделе 4.3. Причина размещения меняется вместе со стратегией, но она текст для человека: ни один процесс её не разбирает.
>
> Так что арифметику ниже можно пролистать, если вам интересно устройство, а не сегодняшнее правило.

Правило в спецификации VMS записано под ключом `tie_break` и называется `most-free-capacity`. Название стоит прочитать буквально: это **разрешение ничьей**, а не всё правило выбора. Полное правило — «сначала притяжение к записи, а если оно не сработало, то самый свободный», и второй половиной мы и займёмся. Почему в нашем сценарии работает именно она — сразу после таблицы.

Само вычитание умещается в две строки (`_best`):

```
свободно(воркер) = capacity из его heartbeat'а − сколько камер ему уже назначено
выбран           = воркер с наибольшим «свободно», при равенстве — первый по алфавиту
```

Оба числа контроллер только что прочитал: `capacity` — из объекта heartbeat'а (`"capacity": 50`, это `CAPACITY` воркера), число назначенных камер — из строки `vms/workers/<w>`. Своего мнения о ёмкости у контроллера нет: **сколько камер потянет воркер, решает сам воркер**. Число 50 в спецификации (`capacity: {from: capacity, fallback: 50}`) — только запасное значение для воркера, который ничего не сказал.

Сравнение **строгое** (`свободно > лучшего`), и это важно для всего сценария: при равенстве побеждает тот, кого перебрали первым. Перебирает контроллер пул, отсортированный по именам, поэтому «первый» здесь — первый по алфавиту. Сортировка посимвольная: если появятся запасные воркеры с именами по номеру предложения, `w-10` окажется раньше `w-2`.

Начинается перебор с «лучшего», у которого свободно равно нулю, и отсюда ещё одно следствие: воркер, у которого свободно ровно `0`, не побеждает никогда — ноль не больше нуля. А если таких все, победителя нет вовсе, и камера остаётся без размещения. Контроллер в этом случае не говорит «`w-srv-a-1` переполнен» — он не говорит ничего ни про кого конкретно, потому что отказ относится к кластеру целиком. Что при этом видно снаружи и кто поднимает ещё один воркер — в разделе [8.8](08-failures.md).

Для камеры 1:

| Воркер | capacity | load | свободно | больше текущего лучшего? |
|---|---|---|---|---|
| w-srv-a-1 | 50 | 0 | **50** | да (0 → 50), лучший `w-srv-a-1` |
| w-srv-b-1 | 50 | 0 | 50 | нет, `50 > 50` ложно |
| w-srv-c-1 | 50 | 0 | 50 | нет |

Выбран **`w-srv-a-1`**.

### Почему здесь сработала только вторая половина правила

Спецификация VMS объявляет камере ещё две вещи: `near: {sub: rec, of: cam}` — «держись рядом с записью этой камеры» — и `home: near` — «и возвращайся туда, если ушла». Обе про одно: камера ходит за своей записью, а не наоборот. Причина в том, что запись прибита к дискам конкретного сервера, а раздачу потока можно забрать с любого сервера по RTSP: из пары двигается то, что способно двигаться.

Порядок выбора поэтому такой (`_pick`), и вычитание из таблицы выше — это только его последний шаг:

| Шаг | Что делает контроллер | Хвост причины |
|---|---|---|
| 1 | ищет живого воркера записи, который держит **запись** этой камеры | — |
| 2 | нашёл — выбирает `most-free-capacity` **только среди воркеров того сервера** | `, beside <воркер записи> holding it` |
| 3 | не нашёл или там нет места — выбирает `most-free-capacity` по всему пулу | `, away from <воркер записи> on <сервер> (no room there)` — если запись есть |

Ищет он не по строкам записей, а по heartbeat'ам воркеров записи: держателем считается тот, у кого в `status` есть запись **этой камеры** (её поле `cam` равно номеру камеры) в состоянии `running` и чей отчёт свежее 45 секунд. В спецификации это `near: {sub: rec, of: cam}`: запись называет оператор, и совпадение номеров записи и камеры было бы случайностью. Если записей у камеры две, контроллер встаёт рядом с резервной (`rank_near_recording` в `vms/volumes.py`): упадёт сервер основной — воркер камеры переживёт его вместе с резервной записью. Притяжение работает от того, что происходит **сейчас**, а не от того, что кто-то когда-то записал в конфигурацию.

В нашем сценарии подсистема записи не участвует вовсе: записей нет, держать камеру рядом не с чем, и шаг 1 сразу отдаёт «ничего» — это тот самый пустой листинг `rec/heartbeats/` из раздела 4.1. Управление проваливается на шаг 3, и остаётся чистое `most-free-capacity` по всем трём воркерам. Поэтому хвост причины у всех трёх камер пустой — и именно по пустому хвосту это в строке размещения и видно.

Держать это в голове стоит вот зачем: **тот же самый кластер с включённой записью разложил бы три камеры иначе.** Они легли бы туда, где лежат их записи, даже если свободной ёмкости там меньше. Разбор такого кластера — за рамками этого сценария.

## 4.3. Две записи, и порядок между ними не случайный

Причина размещения собирается из кусков в предложение, которое потом читает человек (`place`). Вот из каких и откуда берётся каждый:

| Кусок причины | Откуда значение | В нашем случае |
|---|---|---|
| `most free capacity (50)` | свободная ёмкость победителя | `50` |
| `among 3 worker(s)` | размер пула после всех фильтров | `3` |
| ` reaching vlan:cctv` | метки камеры — только если фильтр по меткам включён и метки у камеры есть | `vlan:cctv` |
| `; on srv-a` | сервер победителя из его heartbeat'а | `srv-a` |
| `, whose resource is live` | состояние ресурса — только если подсистема его требует | `live` |
| хвост про соседство | где лежит запись этой камеры — если запись есть | пусто, записи нет |

Новых чтений ради причины нет: сервер победителя и состояние ресурса уже в памяти прохода.

**Запись первая — решение о размещении.** Пишет её `Controller.write` по CAS. Строка, которую он прочитал, пустая (`"index": ""`), поэтому `cas: ""` — «только создать»:

```
POST /v1/write {"op": "put", "key": "vms/placement/1", "cas": "", "items": {
  "worker": "w-srv-a-1",
  "reason": "most free capacity (50) among 3 worker(s) reaching vlan:cctv; on srv-a, whose resource is live",
  "at": "1757500000.0",
  "rev": "1"
}}
→ 200 {"index": 1013}
```

**Запись вторая — назначение воркеру** (`assign_add`). Строки `vms/workers/w-srv-a-1` нет, она тоже создаётся:

```
POST /v1/write {"op": "put", "key": "vms/workers/w-srv-a-1", "cas": "", "items": {"units": "1", "rev": "1"}}
→ 200 {"index": 1014}
```

Эти два поля — весь список дел воркера, и расшифровать их стоит сразу, потому что дальше они встречаются постоянно:

| Поле | Что значит | Здесь |
|---|---|---|
| `units` | **список камер, которые этот воркер должен запустить**, — их номера через запятую | `"1"` — одна камера, та самая, что оператор создал первой |
| `rev` | счётчик правок самого списка: растёт на единицу при каждом изменении | `"1"` — список записан впервые |

Слово `units` — «единицы работы» — принадлежит платформе, и оно намеренно не говорит «камеры». Платформа не знает, что такое камера: для неё это строки с идентификаторами, которые она раздаёт воркерам. Что за ними стоит, знает только сама подсистема. Та же строка в подсистеме записи перечисляла бы записи, а в подсистеме детекции — детекторы.

Значение всегда одна строка, а не массив. Три камеры на одном воркере выглядели бы как `"units": "1,2,3"`, а пустой список — как `"units": ""`.

Важно, чего в этой строке **нет**: настроек. Воркер получает только номера и дальше идёт читать каждую камеру сам. Поэтому правка настройки не трогает назначение, а переназначение не трогает настройки — это две независимые записи в два разных ключа.

Порядок именно такой: **сначала решение, потом назначение**. Причина — в том, что случится, если контроллер упадёт между ними. Упал после первой записи: размещение говорит `w-srv-a-1`, назначение пустое, и следующий проход в самом начале, на сверке `sync_assignments` (раздел 4.1), допишет камеру в `vms/workers/w-srv-a-1`. Заново размещать её он не стал бы: существующее решение `place` возвращает нетронутым. Без сверки такая камера не была бы размещена повторно, не попала бы в `/unplaceable` и не работала бы нигде. Упал бы в обратном порядке: воркер получил бы камеру, о которой ни одна строка размещения не знает, и найти эту сироту было бы не по чему.

CAS на строке размещения решает ещё и спор контроллеров, а он здесь обычное дело: контроллер стоит на каждом сервере. Если контроллер `srv-b` успел разместить камеру раньше, запись `srv-a` получает `409 {"kind": "conflict", …}`, `write` перечитывает строку, видит, что воркер уже назван, и ничего не пишет: решение соседа принимается. Камера не окажется на двух воркерах сразу. Трасса такой встречи — урок 10 М11, шаг 4 (`traces/10-two-controllers-one-camera.txt`). В нашем стенде проход делал только контроллер `srv-a`, поэтому конфликтов нет.

## 4.4. Камеры 2 и 3: то же самое, но арифметика уже другая

Ещё раз: числа ниже иллюстрируют сегодняшнее правило, а не устройство системы. Устройство — это две записи из раздела 4.3, и они не меняются от того, какое правило стоит в спецификации.

Тот же проход, следующая камера. Единственное, что изменилось, — на `w-srv-a-1` теперь числится одна камера. Свою запись проход забыл (запись выбрасывает из памяти прохода то, чего коснулась), поэтому назначение `w-srv-a-1` он перечитывает, а назначения двух других берёт из памяти:

```
GET /v1/get?key=vms/placement/2       → 200 {"items": null, "index": ""}
GET /v1/get?key=vms/workers/w-srv-a-1 → 200 {"items": {"units": "1", "rev": "1"}, "index": 1014}

| w-srv-c-1 | 50 | 0 | 50 | нет, `50 > 50` ложно |

POST /v1/write {"op": "put", "key": "vms/workers/w-srv-b-1", "cas": "", "items": {"units": "2", "rev": "1"}}

```

Для камеры 3 перечитываются `vms/placement/3` (пусто) и `vms/workers/w-srv-b-1` (`"units": "2"`, `"index": 1016`):

**Вот здесь и стоит остановиться, потому что это ответ на главный вопрос сценария.**

Камеры разъехались по трём серверам **не потому, что кто-то велел их разложить**. Правила «раскладывай по разным серверам» в подсистеме VMS нет: поле `spread_by` в её спецификации не задано, и ни один сервер из-за соседства с другой камерой из пула не вычёркивается. Есть обратное правило — `group_by: device`, «каналы одного прибора вместе», — но приборы у наших камер разные, и оно молчит. Разъехались они как побочный результат `most-free-capacity` со строгим сравнением: каждая размещённая камера уменьшает свободную ёмкость своего воркера на единицу, и следующая уходит к соседу, у которого на единицу больше.

Отсюда следствие, которое лучше знать заранее: **если воркер один, все три камеры лягут на него**, и это не поломка. Проверка в разделе [8.5](08-failures.md).

## 4.5. Конец прохода: остальные шаги и публикация снапшота

После размещения в `pass_once` идут ещё пять шагов, каждый в своём `try`, и в нашем сценарии ни один ничего не меняет:

- **`ensure_reach`** — камеры, которые их сервер больше не видит (врезка в разделе 4.1). Все метки совпадают, переносить нечего.
- **`redistribute`** — камеры с воркеров, которых больше нет в пуле: слот отпущен, ресурс на сервере замолчал, сервер выводят или списали. Таких нет.
- **`ensure_home`** — не больше одной камеры за проход обратно туда, где ей место. Для VMS «место» — сервер, где лежит её запись (`home: near`). Записей нет, значит дома нет.
- **`offer_spares`** — недостача по набору меток и предложения запасным (раздел [8.8](08-failures.md)). Всем трём камерам хватило места: `units_short` и `workers_needed` по нулям, предложений нет.
- **`name_conflicts`** — заявки на чужие имена (`vms/contenders/`, раздел [2.2](02-before-first-camera.md)). Их нет.

Всё, что им нужно, уже в памяти прохода. Заново проход спрашивает только то, что сам записал:

```
GET /v1/get?key=vms/placement/1        → w-srv-a-1, "index": 1013
GET /v1/get?key=vms/placement/2        → w-srv-b-1, "index": 1015
GET /v1/get?key=vms/placement/3        → w-srv-c-1, "index": 1017
GET /v1/list?prefix=vms/placement/     → {"vms/placement/1": 1013, "vms/placement/2": 1015, "vms/placement/3": 1017}
GET /v1/get?key=vms/workers/w-srv-c-1  → {"units": "3", "rev": "1"}, "index": 1018
```

Один объектный запрос в конце новый — шаг `name_conflicts`; хранилище он не читает:

```
GET /v1/objects?prefix=vms/contenders/&scope=cluster   → {"server": "srv-a", "objects": {}}
```

**Отчёт прохода.** Проход записывает о себе объект `vms/controller/pass`. Объект — это файл на сервере писателя, поэтому контроллер `srv-a` пишет его на свой диск, а не в хранилище:

```
PUT vms/controller/pass      (файл на srv-a)
```

Из него консоль берёт числа для `/metrics`: сколько камер не размещено, сколько строк испорчено, сколько переездов было, недостача для запасных. В нашем проходе:

```
{"ts": 1757500000.0, "ok": true, "error": "", "failures": 0, "last_success": 1757500000.0,
 "diverged": 0, "reach_moves": 0, "slots_released": [], "servers_decommissioned": [],
 "workers_hung": [], "hung_move_after": 900.0, "workers_unjudged": [], "units_unjudged": 0,
 "name_conflicts": 0, "reach_budget": 10, "units_left_on_leaving": 0, "servers_labels_unread": 0,
 "units_short": {"": 0, "vlan:cctv": 0}, "workers_needed": {"": 0, "vlan:cctv": 0},
 "spare_offers": {"": 0, "vlan:cctv": 0}, "spares_withheld": {}, "unplaced": 0, "garbled": 0, …}
```

**Публикация снапшота** (`publish_snapshot`) — копия для доменного слоя, по объекту на воркера. Строки, камеры, размещения и серверы воркеров уже в памяти прохода, поэтому снапшот не читает из хранилища ничего. Один запрос он всё-таки делает — какие шарды уже есть:

```
GET /v1/objects?prefix=vms/snapshot/&scope=cluster
→ 200 {"server": "srv-a", "objects": {
    "vms/snapshot/unplaced": {"written": 1757500000.0, "server": "srv-a", "size": 75}}}

PUT vms/snapshot/w-srv-a-1   (файл на srv-a)
PUT vms/snapshot/w-srv-b-1
PUT vms/snapshot/w-srv-c-1
PUT vms/snapshot/unplaced    {"cluster": "cluster-a", "worker": null, "ts": …, "cameras": []}
```

Все четыре файла ложатся на `srv-a` — на сервер контроллера, который их пишет, в том числе шарды воркеров с `srv-b` и `srv-c`. Контроллеров в кластере три, значит и копий снапшота на дисках три, по одной на сервере каждого контроллера; читатель берёт самую свежую по `written` (урок 6 М11).

Шард `unplaced` остался с прохода по пустому кластеру (раздел [2.5](02-before-first-camera.md)): тогда пустой шард был заявлением «камер нет». Теперь неразмещённых камер нет, но публикация свои шарды не удаляет никогда: любой шард, который виден в листинге и который этот проход не заполнил, она переписывает пустым (`publish_snapshot`). Так же будет переписан шард воркера, у которого не осталось камер, — это видно в разделе [7.2](07-edit-and-delete.md).

Содержимое шарда `vms/snapshot/w-srv-a-1` (389 байт):

```
{
  "cluster": "cluster-a",
  "worker": "w-srv-a-1",
  "ts": 1757500000.0,
  "cameras": [
    {
      "id": 1,
      "name": "Ворота",
      "source": "driverpack://acme/10.2.0.11",
      "enabled": true,
      "events_retention_days": null,
      "priority": 100,
      "labels": ["vlan:cctv"],
      "alarms": null,
      "ref": "",
      "live": "always",
      "kind": "video",
      "revision": 1,
      "worker": "w-srv-a-1",
      "server": "srv-a"
    }
  ]
}
```

Шарды `w-srv-b-1` (401 байт, камера 2 «Парковка», `"server": "srv-b"`) и `w-srv-c-1` (383 байта, камера 3 «Склад», `"server": "srv-c"`) устроены так же. `cluster-a` — имя кластера из `$CLUSTER`; на стенде оно не задано, и это умолчание `SpecController`. Юнит контроллера без `CLUSTER` назвал бы кластер `room-a` (раздел [2.5](02-before-first-camera.md)).

Пароля в снапшоте нет, и это решение, а не случайность: снапшот покидает кластер, а `cred_secret` в список полей снапшота (`snapshot:` в спецификации) не входит. Нет в нём и `cred_username`, и папок оператора (`folders`): доменному слою они не нужны. Из адреса источника учётные данные тоже вырезаются (`hide_in_url`). Метки, наоборот, уходят списком — это уже не строка ввода, а данные для того, кто будет решать, куда камеру можно переселить.

`null` у срока хранения событий и у списка тревог — не ошибка, а «не задано». Оба поля в спецификации наследуемые (`inherit`), и пока оператор их не заполнил, в строке камеры их нет вовсе: значение решается там, где его используют, — у камеры своё, иначе общее для подсистемы, иначе умолчание (365 дней для событий). Запиши консоль умолчание в строку при создании, общее значение не смогло бы подействовать никогда: «задано 365» и «не задано» стали бы одной и той же строкой.

Снапшот пишется без всякого CAS: это файл, у каждого файла один писатель — контроллер своего сервера, — потерянной правки быть не может, и последняя версия всегда лучше предыдущей.

## 4.6. Сколько этот проход стоил на самом деле

Выше я перечислял запросы по ходу дела. Вот их сумма по трассе — весь проход, размещение трёх камер, остальные шаги, отчёт и снапшот:

| Что | Сколько |
|---|---|
| чтений хранилища | **31** (8 листингов и 23 чтения по ключу) |
| записей в хранилище | **6** — три `vms/placement/<id>` и три `vms/workers/<w>` |
| запросов объектов к ресурсу `srv-a` | **12** |
| файлов, записанных на `srv-a` | **5** — отчёт прохода и четыре шарда снапшота |

Откуда 31 чтение:

| Что читалось | Чтений |
|---|---|
| списания: `platform/decommission/`, `vms/decommissioned/` | 2 |
| слоты: листинг и три строки | 4 |
| листинги `vms/placement/` и `vms/workers/` | 2 |
| камеры: листинг и три строки | 4 |
| `vms/placement/<id>` каждой камеры перед решением | 3 |
| `vms/policy`, `platform/drain` | 2 |
| метки серверов: листинг `vms/servers/` и три строки | 4 |
| назначения трёх воркеров, и ещё два — перечитанные после своих записей | 5 |
| в конце прохода: листинг и три строки размещения, назначение `w-srv-c-1` | 5 |

И 12 объектных запросов: отчёт прошлого прохода, три heartbeat'а воркеров, листинг heartbeat'ов, листинг ресурсов и три их heartbeat'а, листинг `rec/heartbeats/`, листинг заявок `vms/contenders/` и листинг `vms/snapshot/`. Heartbeat'ы воркеров в листинге не перечитываются: каждый объект тоже спрашивается один раз за проход.

**Каждый ключ читается один раз за проход.** Проход идёт внутри `one_pass` (`w2cplatform/contract.py`): каждый ключ, листинг и объект спрашиваются один раз и помнятся до конца прохода, не дольше. Запись забывает то, чего коснулась, поэтому проход читает обратно своё же написанное, а проигранный CAS спрашивает хранилище заново. Снапшот публикуется в том же проходе и заново ничего не читает. До `one_pass` тот же код на тысяче камер делал 64 159 чтений за проход: каждый шаг заново читал строки и размещения, а снапшот и `ensure_home` перечитывали все heartbeat'ы на каждую камеру (урок 10 М11, шаг 6).

Следующий проход, когда всё уже на местах, не пишет ничего. Пусть N — камеры, W — воркеры, S — серверы, чьи метки он читает. Тогда

```
чтений хранилища за установившийся проход = 2·N + 2·W + S + 9
запросов объектов                          = W + S + 6
```

Два чтения на камеру — её строка и её строка размещения. По два на воркера — слот и назначение. По одному на сервер — строка `vms/servers/<srv>`. Ещё девять — семь листингов (`platform/decommission/`, `vms/decommissioned/`, `vms/slots/`, `vms/placement/`, `vms/workers/`, `vms/cameras/`, `vms/servers/`), политика и `platform/drain`. Для нашего стенда, N = 3, W = 3, S = 3, это 24 чтения; новый процесс контроллера читает ещё `platform/schema`, и стенд намерил 25. На 30 камерах — 79, на 100 — 219: около двух чтений на камеру. Если в кластере есть запись на R рекордерах, к объектам добавляются их heartbeat'ы. Объектных запросов на стенде больше, чем будет в работе: стенд не кэширует объектные листинги (`list_fresh=0`), а в работе ресурс помнит листинг секунду (`LIST_FRESH=1.0`). Таблицы по размерам кластера — в [части 10](10-limits-and-scale.md), раздел 10.2. Потолок числа держит тест `Source/tests/test_read_budget.py::test_an_idle_controller_pass_over_a_thousand_cameras_reads_each_row_once`: тысяча камер — не больше `2·N + 150` чтений на проход. Проход повторяется через пять секунд после окончания предыдущего.

Для понимания сценария это не важно: решение принимается по тем же данным. Тест `Source/tests/test_read_budget.py::test_a_busy_pass_decides_exactly_what_the_pass_that_read_everything_again_decided` гоняет занятый проход дважды, с памятью прохода и без неё, и сверяет размещения, назначения и снапшот. Два чтения на камеру за проход остаются: листинг отдаёт версии ключей, но контроллер между проходами не помнит ничего, и узнать, что в строке, можно только прочитав её. Разбор — в разделе 10.5 [части 10](10-limits-and-scale.md).
