## 4.1. Что контроллер читает, прежде чем решить

Начало прохода — три проверки на то, чего в нашем сценарии нет, но запросы они делают:

```
GET /v1/vars?prefix=vms/placement/   → []   unplace_deleted: удалённых камер нет
GET /v1/vars?prefix=vms/placement/   → []   unplace_retired: завершённых работ нет
GET /v1/vars?prefix=vms/workers/     → []   sync_assignments: назначений ещё нет…
GET /v1/vars?prefix=vms/placement/   → []   …и решений, с которыми их сверять, тоже
```

Третья проверка — сверка назначений с решениями (`sync_assignments`). Каждый проход начинается с того, что строки `vms/workers/*` приводятся к тому, что говорят строки `vms/placement/*`: камера дописывается воркеру, которого назвало решение, и вычёркивается у любого другого. Зачем это нужно, видно в разделе 4.3, где две записи размещения делаются по очереди, и контроллер может упасть между ними.

Дальше он берёт список камер. Это тот самый `N+1`: листинг отдаёт только пути, значения приходится дочитывать по одному.

```
GET /v1/vars?prefix=vms/cameras/

→ 200
[
  {"Path": "vms/cameras/1", "ModifyIndex": 4409, …},
  {"Path": "vms/cameras/2", "ModifyIndex": 4421, …},
  {"Path": "vms/cameras/3", "ModifyIndex": 4433, …}
]

GET /v1/var/vms/cameras/1   → Items камеры 1
GET /v1/var/vms/cameras/2   → Items камеры 2
GET /v1/var/vms/cameras/3   → Items камеры 3
```

Теперь он берётся за камеру 1. Сначала две проверки — не размещена ли она уже и жива ли её строка (`place` читает строку сам, хотя только что прочитал её в списке):

```
GET /v1/var/vms/placement/1              → 404 → решения ещё нет
GET /v1/var/vms/cameras/1                → строка камеры 1, та же
```

Потом он собирает пул кандидатов. Здесь запросов больше всего:

```
# кто вообще живой — heartbeat'ы не старше 45 секунд
GET /v1/vars?prefix=objects/vms/heartbeats/
→ ["objects/vms/heartbeats/w-1", "objects/vms/heartbeats/w-2", "objects/vms/heartbeats/w-3"]
GET /v1/var/objects/vms/heartbeats/w-1   → {"worker": "w-1", "server": "srv-1", "labels": "vlan:cctv", "capacity": 50, …}
GET /v1/var/objects/vms/heartbeats/w-2   → {"worker": "w-2", "server": "srv-2", …}
GET /v1/var/objects/vms/heartbeats/w-3   → {"worker": "w-3", "server": "srv-3", …}

# кто отпустил слот по-хорошему — такие в пул не попадают
GET /v1/vars?prefix=vms/slots/           → 3 пути
GET /v1/var/vms/slots/w-1                → released: false
GET /v1/var/vms/slots/w-2                → released: false
GET /v1/var/vms/slots/w-3                → released: false

# у чьего сервера жив ресурс — спецификация требует resource.
# Для каждого воркера по отдельности: на каком он сервере, и жив ли ресурс там
GET /v1/vars?prefix=objects/vms/heartbeats/              → 3 пути        w-1 — на каком сервере?
GET /v1/var/objects/vms/heartbeats/w-1..w-3              → 3 объекта     → srv-1
GET /v1/vars?prefix=objects/platform/resources/          → 3 пути
GET /v1/var/objects/platform/resources/srv-1..3/heartbeat → ts свежий    → live
… и те же восемь запросов ещё дважды — для w-2 и для w-3

# политика размещения: shared или distinct
GET /v1/var/vms/policy                   → 404 → умолчание "shared"

# не выводят ли сервер на обслуживание
GET /v1/var/platform/drain               → 404 → никто не выводится
```

Пул: `[w-1, w-2, w-3]`.

Дальше — фильтр по меткам, и его стоит разобрать отдельно.

### Что такое `labels` и зачем они

Метка отвечает на один вопрос: **до какой камеры этот сервер физически дотягивается по сети.**

Камеры стоят в разных сегментах: одни в служебной сети видеонаблюдения, другие в демилитаризованной зоне, третьи на удалённой площадке за туннелем. Сервер видит не все сегменты — у него столько сетевых интерфейсов, сколько ему дали. Камера в сегменте `cctv` с сервера без интерфейса в этом сегменте просто не откроется: ни потока, ни записи, ни тревог.

Значит эту физику нужно как-то сообщить контроллеру, иначе он разложит камеры красиво по ёмкости и половина из них не подключится. Метки и есть такое сообщение, и объявляют их **с двух сторон**:

| Сторона | Что объявляет | Откуда берётся | Где лежит |
|---|---|---|---|
| **камера** | из какого сегмента её видно | оператор пишет при создании | поле `labels` строки камеры |
| **сервер** | какие сегменты он достаёт | администратор задаёт в настройке узла | поле `labels` heartbeat'а воркера |

Формат один и тот же: список строк вида `имя:значение`, разделённых запятой. Ничего, кроме сравнения строк, система с ними не делает — смысл `vlan:cctv` или `site:msk-hq` знает только человек, который их придумал.

### Правило сравнения: подмножество, а не пересечение

Воркер подходит камере, если **все** метки камеры есть у его сервера. Не «хотя бы одна общая», а именно все.

| Метки камеры | Метки сервера | Подходит? |
|---|---|---|
| `vlan:cctv` | `vlan:cctv` | да, точное совпадение |
| `vlan:cctv` | `vlan:cctv`, `site:msk-hq`, `gpu` | **да** — у сервера больше, чем требуется, и это нормально |
| `vlan:cctv`, `site:msk-hq` | `vlan:cctv` | **нет** — второй метки у сервера нет |
| пусто | `vlan:cctv` | **да** — пустой список требований выполняет кто угодно |
| `vlan:cctv` | пусто | нет |

Четвёртая строка — важный практический случай. Камера без меток размещается **где угодно**, и на площадке с одной плоской сетью это ровно то, что нужно: не заполняйте поле, и фильтр не будет мешать.

Обратное несимметрично: чем больше меток у камеры, тем меньше серверов ей подходит. Метка — это **требование**, а не пожелание.

### Это фильтр, а не предпочтение

Разница принципиальная, и она видна по тому, что происходит, когда подходящих серверов нет.

Ёмкость — это предпочтение: заполненный воркер уступает свободному, но камера всё равно куда-нибудь встанет. Метка так не работает. Если её не может выполнить ни один сервер, камера **не размещается вовсе** и ждёт — потому что поставить её на сервер, который до неё не дотянется, значит получить вечно падающий пайплайн вместо честного «не могу».

Именно так устроен раздел [8.3](08-failures.md): камера с меткой `vlan:cctv-dmz` создаётся нормально, но остаётся без размещения, и консоль отвечает на вопрос «почему» отдельным маршрутом `/unplaceable`.

И формулировка отказа поэтому звучит как «система не дотягивается», а не «воркеры переполнены». Это разные аварии и чинятся они по-разному: первая — сетью или меткой на сервере, вторая — новым сервером.

### В нашем сценарии

У всех трёх камер метка `vlan:cctv`, у всех трёх серверов она же. Проверка `{vlan:cctv} ⊆ {vlan:cctv}` проходит у всех троих, пул остаётся полным — и дальше решает уже ёмкость.

Метка попадает и в причину размещения (`reaching vlan:cctv`), и в снапшот, который уезжает на доменный слой. Первое — чтобы человек видел, по какому требованию выбирали; второе — чтобы слой над кластером знал, куда эту камеру вообще можно переселить.

### Второй фильтр: один прибор — один воркер

В спецификации VMS рядом с метками стоит ещё строка `group_by: device`. Она про другую физику: **прибор — это одно соединение**. Шестнадцать каналов одного видеорегистратора — шестнадцать строк камер, и если разложить их по ёмкости на четыре воркера, к прибору откроются четыре сессии, а лицензирован он, скажем, на две. Отказ тогда придёт словами прибора — «слишком много сессий», канал не стартует, — и ничто в нём не укажет на решение о размещении, принятое на другом сервере час назад.

Поэтому правило жёсткое, как и метки: камера, у которой уже есть размещённые соседи по прибору, идёт **только** на их воркер. Места там нет — камера не размещается и ждёт. В ответе `/unplaceable` её при этом не будет: этот маршрут перечисляет камеры, которым не подходит ни один живой воркер (`unplaceable` в `w2cplatform/spec.py`), а здесь подходящий есть, он просто полон. Растекаться по соседям группе не дают, потому что растекание и есть то, от чего правило защищает. Одно исключение: если воркер соседей сам выпал из пула (умер, уходит, сервер выводят), группу он за собой не держит, и она собирается заново там, куда ляжет первая камера.

Поля «прибор» в строке камеры нет. Его вычисляет сама подсистема из источника: у `driverpack://<производитель>/<адрес>/ch/<n>` прибор — это `<производитель>/<адрес>`, канал отбрасывается. Платформа схему `driverpack://` не знает и знать не должна, поэтому у неё крючок, а разбор — в коде VMS.

В нашем сценарии фильтр ничего не решает: у трёх камер три разных прибора — `acme/10.2.0.11`, `acme/10.2.0.12`, `acme/10.2.0.13`, у каждого по одному каналу. Группы из одной камеры ничем не ограничены.

### Что эти два фильтра стоят в запросах

Оба фильтра — функция `eligible`, и про хранилище она ничего не помнит. Метки воркера она берёт из его heartbeat'а, сервер — оттуда же, и каждый раз перечитывает все heartbeat'ы. А чтобы найти соседей по прибору, она перечитывает все строки камер:

```
# метки каждого из трёх воркеров: три раза листинг и три объекта
GET /v1/vars?prefix=objects/vms/heartbeats/   → 3 пути     ×3
GET /v1/var/objects/vms/heartbeats/w-1..w-3   → 3 объекта  ×3

# сервер каждого (на случай spread_by — у VMS его нет, но вопрос задаётся): ещё трижды то же
GET /v1/vars?prefix=objects/vms/heartbeats/   → 3 пути     ×3
GET /v1/var/objects/vms/heartbeats/w-1..w-3   → 3 объекта  ×3

# соседи по прибору: все строки камер заново
GET /v1/vars?prefix=vms/cameras/              → 3 пути
GET /v1/var/vms/cameras/1..3                  → 3 строки
```

### Последнее чтение перед решением

Есть ли у камеры запись, рядом с которой ей стоять (раздел 4.2), — один листинг heartbeat'ов подсистемы записи:

```
GET /v1/vars?prefix=objects/rec/heartbeats/   → []   записывающих воркеров нет
```

И сколько камер уже назначено каждому. Перед каждым из этих чтений контроллер ещё раз перечитывает все heartbeat'ы — за ёмкостью воркера:

```
GET /v1/var/vms/workers/w-1   → 404 → назначений нет, load = 0
GET /v1/var/vms/workers/w-2   → 404 → load = 0
GET /v1/var/vms/workers/w-3   → 404 → load = 0
```

## 4.2. Как он выбирает: одно вычитание

> **Всё, что дальше в этом разделе, — сменная часть.** Правило выбора принадлежит контроллеру и только ему: ни воркер, ни консоль, ни доменный слой не знают и не спрашивают, как он выбирал. Правила берутся по имени из небольшого каталога — в спецификации это ключи `constraint` и `tie_break`, — и подсистема вправе зарегистрировать там своё, кодом под именем. Сегодня в каталоге два ограничения и одно разрешение ничьей, а рядом с ними — два фильтра по полю строки, `group_by` и `spread_by`; завтра их может стать больше, и на остальную систему это не повлияет никак.
>
> Не повлияет потому, что **результат записывается всегда одинаково: одна строка `vms/placement/<камера>` и одна `vms/workers/<воркер>`.** Эти две записи и есть контракт со всей системой, разбор — в разделе 4.3. Причина размещения меняется вместе со стратегией, но она текст для человека: ни один процесс её не разбирает.
>
> Так что арифметику ниже можно пролистать, если вам интересно устройство, а не сегодняшнее правило.

Правило в спецификации VMS записано под ключом `tie_break` и называется `most-free-capacity`. Название стоит прочитать буквально: это **разрешение ничьей**, а не всё правило выбора. Полное правило — «сначала притяжение к записи, а если оно не сработало, то самый свободный», и второй половиной мы и займёмся. Почему в нашем сценарии работает именно она — сразу после таблицы.

Само вычитание умещается в две строки:

```
свободно(воркер) = capacity из его heartbeat'а − сколько камер ему уже назначено
выбран           = воркер с наибольшим «свободно», при равенстве — первый по алфавиту
```

Оба числа контроллер только что прочитал: `capacity` — из объекта heartbeat'а, число назначенных камер — из строки `vms/workers/<w>`. Своего мнения о ёмкости у контроллера нет: **сколько камер потянет воркер, решает сам воркер**.

Сравнение **строгое** (`свободно > лучшего`), и это важно для всего сценария: при равенстве побеждает тот, кого перебрали первым. Перебирает контроллер пул, отсортированный по именам, поэтому «первый» здесь — первый по алфавиту. Сортировка посимвольная, как и в листинге: на десяти воркерах `w-10` окажется раньше `w-2`.

Начинается перебор с «лучшего», у которого свободно равно нулю, и отсюда ещё одно следствие: воркер, у которого свободно ровно `0`, не побеждает никогда — ноль не больше нуля. А если таких все, победителя нет вовсе, и камера остаётся без размещения. Контроллер в этом случае не говорит «`w-1` переполнен» — он не говорит ничего ни про кого конкретно, потому что отказ относится к кластеру целиком. Что при этом видно снаружи — в разделе [8.8](08-failures.md).

Для камеры 1:

| Воркер | capacity | load | свободно | больше текущего лучшего? |
|---|---|---|---|---|
| w-1 | 50 | 0 | **50** | да (0 → 50), лучший `w-1` |
| w-2 | 50 | 0 | 50 | нет, `50 > 50` ложно |
| w-3 | 50 | 0 | 50 | нет |

Выбран **`w-1`**.

### Почему здесь сработала только вторая половина правила

Спецификация VMS объявляет камере ещё две вещи: `near: {sub: rec, of: cam}` — «держись рядом с записью этой камеры» — и `home: near` — «и возвращайся туда, если ушла». Обе про одно: камера ходит за своей записью, а не наоборот. Причина в том, что запись прибита к дискам конкретного сервера, а раздачу потока можно забрать с любого сервера по RTSP: из пары двигается то, что способно двигаться.

Порядок выбора поэтому такой, и вычитание из таблицы выше — это только его последний шаг:

| Шаг | Что делает контроллер | Хвост причины |
|---|---|---|
| 1 | ищет живого воркера записи, который держит **запись** этой камеры | — |
| 2 | нашёл — выбирает `most-free-capacity` **только среди воркеров того сервера** | `, beside <воркер записи> holding it` |
| 3 | не нашёл или там нет места — выбирает `most-free-capacity` по всему пулу | `, away from <воркер записи> on srv-N (no room there)` |

Ищет он не по строкам записей, а по heartbeat'ам воркеров записи: держателем считается тот, у кого в `status` есть запись **этой камеры** (её поле `cam` равно номеру камеры) в состоянии `running` и чей отчёт свежее 45 секунд. В спецификации это `near: {sub: rec, of: cam}`: запись теперь называет оператор, и совпадение номеров записи и камеры было бы случайностью. Если записей у камеры две, контроллер встаёт рядом с резервной (`rank_near_recording` в `vms/volumes.py`): упадёт сервер основной — воркер камеры переживёт его вместе с резервной записью. Притяжение работает от того, что происходит **сейчас**, а не от того, что кто-то когда-то записал в конфигурацию.

В нашем сценарии подсистема записи не участвует вовсе: записей нет, держать камеру рядом не с чем, и шаг 1 сразу отдаёт «ничего» — это тот самый пустой листинг `objects/rec/heartbeats/` из раздела 4.1. Управление проваливается на шаг 3, и остаётся чистое `most-free-capacity` по всем трём воркерам. Поэтому хвост причины у всех трёх камер пустой — и именно по пустому хвосту это в строке размещения и видно.

Держать это в голове стоит вот зачем: **тот же самый кластер с включённой записью разложил бы три камеры иначе.** Они легли бы туда, где лежат их записи, даже если свободной ёмкости там меньше. Разбор такого кластера — за рамками этого сценария.

## 4.3. Две записи, и порядок между ними не случайный

Причина размещения собирается из кусков в предложение, которое потом читает человек. Вот из каких и откуда берётся каждый:

| Кусок причины | Откуда значение | В нашем случае |
|---|---|---|
| `most free capacity (50)` | свободная ёмкость победителя | `50` |
| `among 3 worker(s)` | размер пула после всех фильтров | `3` |
| `reaching vlan:cctv` | метки камеры — только если фильтр по меткам включён | `vlan:cctv` |
| `; on srv-1` | сервер победителя из его heartbeat'а | `srv-1` |
| `, whose resource is live` | состояние ресурса — только если подсистема его требует | `live` |
| хвост про соседство | где лежит запись этой камеры — если запись есть | пусто, записи нет |

Собранное вместе и попадает в строку размещения. Ради двух кусков про сервер контроллер, уже выбрав `w-1`, ещё дважды перечитывает все heartbeat'ы воркеров (на каком сервере победитель) и один раз — все heartbeat'ы ресурсов (жив ли ресурс там): двенадцать чтений, прежде чем писать.

**Запись первая — решение о размещении:**

```
GET /v1/var/vms/placement/1
→ 404

PUT /v1/var/vms/placement/1?cas=0

{
  "Items": {
    "worker": "w-1",
    "reason": "most free capacity (50) among 3 worker(s) reaching vlan:cctv; on srv-1, whose resource is live",
    "at": "1757500003.4",
    "rev": "1"
  }
}

→ 200 {"ModifyIndex": 4441}
```

**Запись вторая — назначение воркеру:**

```
GET /v1/var/vms/workers/w-1
→ 404

PUT /v1/var/vms/workers/w-1?cas=0
{"Items": {"units": "1", "rev": "1"}}
→ 200 {"ModifyIndex": 4444}
```

Эти два поля — весь список дел воркера, и расшифровать их стоит сразу, потому что дальше они встречаются постоянно:

| Поле | Что значит | Здесь |
|---|---|---|
| `units` | **список камер, которые этот воркер должен запустить**, — их номера через запятую | `"1"` — одна камера, та самая, что оператор создал первой |
| `rev` | счётчик правок самого списка: растёт на единицу при каждом изменении | `"1"` — список записан впервые |

Слово `units` — «единицы работы» — принадлежит платформе, и оно намеренно не говорит «камеры». Платформа не знает, что такое камера: для неё это строки с идентификаторами, которые она раздаёт воркерам. Что за ними стоит, знает только сама подсистема. Та же строка в подсистеме записи перечисляла бы записи, а в подсистеме детекции — детекторы.

Значение всегда одна строка, а не массив. Три камеры на одном воркере выглядели бы как `"units": "1,2,3"`, а пустой список — как `"units": ""`.

Важно, чего в этой строке **нет**: настроек. Воркер получает только номера и дальше идёт читать каждую камеру сам. Поэтому правка настройки не трогает назначение, а переназначение не трогает настройки — это две независимые записи в два разных ключа.

Порядок именно такой: **сначала решение, потом назначение**. Причина — в том, что случится, если контроллер упадёт между ними. Упал после первой записи: размещение говорит `w-1`, назначение пустое, и следующий проход в самом начале, на сверке `sync_assignments` (раздел 4.1), допишет камеру в `vms/workers/w-1`. Заново размещать её он не стал бы: существующее решение `place` возвращает нетронутым. Без сверки такая камера не была бы размещена повторно, не попала бы в `/unplaceable` и не работала бы нигде. Упал бы в обратном порядке: воркер получил бы камеру, о которой ни одна строка размещения не знает, и найти эту сироту было бы не по чему.

CAS на строке размещения решает ещё и спор двух контроллеров. Если второй экземпляр успел разместить камеру раньше, наша запись не проходит, и мы берём чужое решение — камера не окажется на двух воркерах сразу.

## 4.4. Камеры 2 и 3: то же самое, но арифметика уже другая

Ещё раз: числа ниже иллюстрируют сегодняшнее правило, а не устройство системы. Устройство — это две записи из раздела 4.3, и они не меняются от того, какое правило стоит в спецификации.

Тот же проход, следующая камера. Единственное, что изменилось, — на `w-1` теперь числится одна камера.

Для камеры 2:

| Воркер | capacity | load | свободно | лучший? |
|---|---|---|---|---|
| w-1 | 50 | **1** | 49 | да (0 → 49) |
| w-2 | 50 | 0 | **50** | да, `50 > 49` — лучший становится `w-2` |
| w-3 | 50 | 0 | 50 | нет, `50 > 50` ложно |

```
PUT /v1/var/vms/placement/2?cas=0

{
  "Items": {
    "worker": "w-2",
    "reason": "most free capacity (50) among 3 worker(s) reaching vlan:cctv; on srv-2, whose resource is live",
    "at": "1757500003.5",
    "rev": "1"
  }
}

→ 200 {"ModifyIndex": 4449}

PUT /v1/var/vms/workers/w-2?cas=0
{"Items": {"units": "2", "rev": "1"}}

→ 200 {"ModifyIndex": 4452}
```

Для камеры 3:

| Воркер | capacity | load | свободно | лучший? |
|---|---|---|---|---|
| w-1 | 50 | 1 | 49 | да (0 → 49) |
| w-2 | 50 | 1 | 49 | нет, `49 > 49` ложно |
| w-3 | 50 | 0 | **50** | да — лучший `w-3` |

```
PUT /v1/var/vms/placement/3?cas=0

{
  "Items": {
    "worker": "w-3",
    "reason": "most free capacity (50) among 3 worker(s) reaching vlan:cctv; on srv-3, whose resource is live",
    "at": "1757500003.6",
    "rev": "1"
  }
}

→ 200 {"ModifyIndex": 4457}

PUT /v1/var/vms/workers/w-3?cas=0
{"Items": {"units": "3", "rev": "1"}}

→ 200 {"ModifyIndex": 4460}
```

**Вот здесь и стоит остановиться, потому что это ответ на главный вопрос сценария.**

Камеры разъехались по трём серверам **не потому, что кто-то велел их разложить**. Правила «раскладывай по разным серверам» в подсистеме VMS нет: поле `spread_by` в её спецификации не задано, и ни один сервер из-за соседства с другой камерой из пула не вычёркивается. Есть обратное правило — `group_by: device`, «каналы одного прибора вместе», — но приборы у наших камер разные, и оно молчит. Разъехались они как побочный результат `most-free-capacity` со строгим сравнением: каждая размещённая камера уменьшает свободную ёмкость своего воркера на единицу, и следующая уходит к соседу, у которого на единицу больше.

Отсюда следствие, которое лучше знать заранее: **если воркер один, все три камеры лягут на него**, и это не поломка. Проверка в разделе [8.5](08-failures.md).

## 4.5. Конец прохода: остальные шаги и публикация снапшота

После размещения контроллер делает ещё два шага, и в нашем сценарии оба ничего не меняют.

**Перераздача осиротевших камер** (`redistribute`). Контроллер ищет воркеров, с которых камеры надо снять: слот отпущен по-хорошему, ресурс на сервере замолчал, сервер выводят на обслуживание. Начинает он с того же, с чего начинался проход, — заново перечисляет `vms/placement/` и по каждой из трёх строк перечитывает строку камеры: не удалили ли её за последние доли секунды. Потом читает heartbeat'ы и `vms/slots/` (три занятых слота), для каждого воркера заново выясняет сервер и живость ресурса — те же восемь запросов на воркера, что и в разделе 4.1, — и последними читает `platform/drain` и `vms/policy`. Снимать не с кого, ни одной записи. Сорок одно чтение.

**Возврат камер домой** (`ensure_home`). Контроллер переносит не больше одной камеры за проход туда, где ей место. Для VMS «место» — это сервер, где лежит её запись (`home: near`, `near: {sub: rec, of: cam}`). Записи в нашем сценарии нет, значит дома нет, и возвращать некуда. Но запросы при этом всё равно делаются, и не один: пул собирается заново (те же чтения, что в разделе 4.1), а дом ищется для **каждой** камеры по очереди, и на каждую контроллер листит `objects/rec/heartbeats/` заново — три листинга, три пустых списка. Сорок четыре чтения.

**Публикация снапшота** — единственная безусловная запись прохода. Контроллер собирает копию для доменного слоя, по объекту на воркера:

```
# ещё раз весь список камер
GET /v1/vars?prefix=vms/cameras/            → 3 пути
GET /v1/var/vms/cameras/1..3                → 3 строки

# по каждой камере: где она, и на каком сервере этот воркер
GET /v1/var/vms/placement/1                 → w-1
GET /v1/vars?prefix=objects/vms/heartbeats/ → 3 пути     (сервер w-1 — снова из heartbeat'ов)
GET /v1/var/objects/vms/heartbeats/w-1..w-3 → 3 объекта  → srv-1
… то же для камер 2 и 3

# какие шарды уже есть (чтобы переписать пустыми те, что осиротели)
GET /v1/vars?prefix=objects/vms/snapshot/   → ["objects/vms/snapshot/unplaced"]

# три записи — и пустой `unplaced`, оставшийся с прохода по пустому кластеру
PUT /v1/var/objects/vms/snapshot/w-1
PUT /v1/var/objects/vms/snapshot/w-2
PUT /v1/var/objects/vms/snapshot/w-3
PUT /v1/var/objects/vms/snapshot/unplaced   → {"worker": null, "cameras": []}
```

Шард `unplaced` остался с прохода по пустому кластеру (раздел [2.5](02-before-first-camera.md)): тогда пустой шард был заявлением «камер нет». Теперь неразмещённых камер нет, но публикация свои шарды не удаляет никогда: любой шард, который есть в хранилище и который этот проход не заполнил, она переписывает пустым (`publish_snapshot`). Так же будет переписан шард воркера, у которого не осталось камер, — это видно в разделе [7.2](07-edit-and-delete.md).

Содержимое шарда `w-1`:

```
Items.data:
{
  "cluster": "room-a",
  "worker": "w-1",
  "ts": 1757500003.7,
  "cameras": [
    {
      "id": 1,
      "name": "Ворота",
      "source": "driverpack://acme/10.2.0.11",
      "enabled": true,
      "events_retention_days": null,
      "priority": 100,
      "labels": ["vlan:cctv"],
      "alarms": null,
      "ref": "north-gate",
      "live": "always",
      "kind": "video",
      "revision": 1,
      "worker": "w-1",
      "server": "srv-1"
    }
  ]
}
```

Пароля в снапшоте нет, и это решение, а не случайность: снапшот покидает кластер, а `cred_secret` в список полей снапшота не входит. Нет в нём и `cred_username`, и папок оператора (`folders`): доменному слою они не нужны. Метки, наоборот, уходят списком — это уже не строка ввода, а данные для того, кто будет решать, куда камеру можно переселить.

`null` у срока хранения событий и у списка тревог — не ошибка, а «не задано». Оба поля в спецификации наследуемые (`inherit`), и пока оператор их не заполнил, в строке камеры их нет вовсе: значение решается там, где его используют, — у камеры своё, иначе общее по домену, иначе умолчание (365 дней для событий). Запиши консоль умолчание в строку при создании, общее значение домена не смогло бы подействовать никогда: «задано 365» и «не задано» стали бы одной и той же строкой.

Снапшот пишется **без CAS**: у него один писатель, потерянной правки быть не может, и последняя версия всегда лучше предыдущей.

## 4.6. Сколько этот проход стоил на самом деле

Выше я перечислял запросы по логике: «прочитал heartbeat'ы, прочитал слоты, решил». На самом деле контроллер ничего из прочитанного не запоминает на время прохода, поэтому реальных запросов заметно больше.

Каждый раз, когда ему нужно узнать про воркера хоть что-нибудь — на каком тот сервере, какие у него метки, какую ёмкость он объявил, — контроллер перечитывает **все** heartbeat'ы заново. А нужно ему это по нескольку раз на каждую камеру и на каждого кандидата. Трасса стенда даёт точное число. Весь проход — размещение трёх камер, перераздача, возврат домой и публикация снапшота — это **десять записей и 395 чтений**:

| Шаг | Чтений | Записей |
|---|---|---|
| `ensure_placed` — сверка и размещение трёх камер | 290 | 6 |
| `redistribute` | 41 | 0 |
| `ensure_home` | 44 | 0 |
| `publish_snapshot` | 20 | 4 |
| **весь проход** | **395** | **10** |

Из этих чтений 168 — объекты heartbeat'ов воркеров, каждый прочитан по 56 раз, и ещё 56 листингов их префикса. Heartbeat'ы ресурсов — 54 чтения и 18 листингов.

Следующий проход, когда размещать уже нечего, дешевле: **134 чтения и 4 записи** (только снапшот). Из них 33 — heartbeat'ы воркеров. Я вывел по коду, из чего складывается такой холостой проход, и сверил формулу со стендом на трёх камерах. Пусть N — камеры, W — воркеры, R — серверы с ресурсом, а записи (подсистемы `rec`) в кластере нет. Тогда

```
чтений за холостой проход = 17 + 15·N + N·W + 5·W + 2·W·(W + R + 2)
```

Член `N·W` — это публикация снапшота: сервер каждой камеры она берёт из heartbeat'а, и для этого на каждую камеру перечитывает все heartbeat'ы. Для N = 3, W = 3, R = 3 формула даёт 134, как на стенде. Для проектных шестисот камер на двенадцати воркерах и двенадцати серверах получается около **17 000 чтений за проход**. Это посчитано, а не измерено. Проход повторяется через пять секунд после окончания предыдущего. Будь в кластере запись, к этому добавилось бы ещё по чтению каждого heartbeat'а записывающих воркеров на каждую камеру (поиск дома в `ensure_home`). Как это ложится на кластер целиком, разобрано в [части 10](10-limits-and-scale.md).

Для понимания сценария это не важно: решение принимается по тем же данным. Для эксплуатации важно, и лечится это просто — прочитать heartbeat'ы один раз в начале прохода и дальше пользоваться прочитанным. Разбор — в части 3 записок [«Куда попадает настройка камеры»](../where-camera-settings-go.md).
