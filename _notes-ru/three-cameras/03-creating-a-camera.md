Дальше идёт время. `T+0` — момент, когда оператор нажал «Сохранить».

Все запросы этой части сняты со стенда: настоящая консоль курса (`cluster.console.make_console`) поднята по HTTP поверх хранилища стенда, и оператор `anna` отправляет ей три `POST /cameras` через консоль на `srv-a`. Под каждым HTTP-обменом трасса показывает все запросы консоли к хранилищу, сделанные ради него. Числа `index` и отметки времени условные.

## 3.1. Запрос оператора

```
POST /cameras HTTP/1.1
Host: srv-a:8080
Content-Type: application/json
X-User: anna
Idempotency-Key: k-anna-0001

{"name": "Ворота", "source": "driverpack://acme/10.2.0.11", "labels": ["vlan:cctv"]}
```

Заголовок `Idempotency-Key` обязателен: консоль без него отвечает `400` (`SpecConsole._idem` в `w2cplatform/console.py`). Причина в том, что повтор запроса может попасть на **другую консоль** — на другом сервере кластера, — и она должна узнать о первой попытке, а узнать может только из хранилища. Ключ становится частью имени ключа в хранилище, поэтому он должен быть одним сегментом: без `/` и `..`, не длиннее 200 символов, иначе тоже `400`. Страница консоли шлёт свежий случайный ключ на каждый `POST`; на стенде ключи читаемые и постоянные — `k-anna-0001`, `k-anna-0002`, `k-anna-0003`.

`X-User: anna` — имя, под которым оператор действует. В кластере без домена его никто не проверяет (об этом ниже, в «кто звонит»); без заголовка имя было бы `operator`.

Поле `source` — адрес устройства, и консоль проверяет его как адрес: логин и пароль внутри него (`driverpack://root:hunter2@…`) отклоняются, потому что `source` уходит в снапшот, за пределы кластера (`SubsystemSpec.refuse` в `w2cplatform/spec.py`). Учётные данные устройства идут в отдельные поля `cred_username` и `cred_secret`. В нашем запросе их нет.

Поле `labels` здесь — требование к серверу: «эту камеру видно только из сегмента `vlan:cctv`». Контроллер по нему отсеет серверы, которые до камеры не дотягиваются; у всех трёх наших серверов метка та же (`LABELS=vlan:cctv`), так что отсеивать нечего. Подробно — в разделе [4.1](04-placement.md), где этот фильтр применяется. Прислать метки можно и списком (`["vlan:cctv"]`), и строкой через запятую — хранится всё равно строка, поэтому значение в списке не может содержать `,`.

Полей `worker`, `placement`, `revision`, `observed_revision`, `epoch`, `phase`, `id` в теле нет и быть не может. Это поля платформы (`PLATFORM_FIELDS`), и попытка их прислать даёт `400` с объяснением, чьи они.

## 3.2. Во что этот запрос превращается в хранилище

Консоль ходит в хранилище через сокет своей роли, `/run/configstore/console.sock`: что можно писать и читать этому сокету, решает файл прав демона хранилища ([М11, урок 5](../../М11_ClusterVMS/05-rights-by-who-is-calling.md)). На первую камеру трасса насчитала **18 чтений и 5 записей**. Двенадцать чтений — проверка «кто звонит». Остальное — в жёстком порядке: застолбить запрос, выдать номер и записать его в захват, убедиться, что источник не занят, записать строку, в конце — положить ответ туда, где его найдёт повтор.

> Одно чтение случилось ещё раньше, при старте консоли, и к запросу оператора не относится: `GET /v1/get?key=platform/schema`. Его делает один раз любой процесс, открывший хранилище (`check_schema` в `w2cplatform/contract.py`), — сверяет, понимает ли он его формат. Ключа нет (`{"items": null, "index": ""}`) — значит «формат тот, который знает эта сборка»: установка свежая. Будь хранилище новее сборки, консоль не запустилась бы вовсе. В трассе части 3 этого чтения нет: консоль поднята раньше.

**Сначала — кто звонит.**

До всякой записи консоль спрашивает хранилище, состоит ли кластер в домене (`Gate` в `w2cplatform/access.py`). Признак один — набор ключей домена `domain/keys`, который туда кладёт агент домена (М12). Если набора нет, консоль проверяет ещё пять строк, которые пишет только агент домена (`DOMAIN_MARKS`): по ним видно, что кластер в домене **был** и ключи потерял — удалили или откатили из резервной копии. Тогда консоль не открывается, а закрывается: `503` на всё, пока агент не вернёт ключи.

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/keys
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/member
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/root
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/grants
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/revoked
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=domain/break_glass
→ 200 {"items": null, "index": ""}

… и те же шесть ещё раз
```

`{"items": null, "index": ""}` — так хранилище отвечает на ключ, которого нет: `200`, а не `404`.

Дважды — потому что вопросов два, и каждый перечитывает хранилище заново (`Gate.access` ничего не запоминает: кластер может вступить в домен, пока консоль работает). Первый — «кто звонит» (`Gate.caller`), по одним заголовкам, до того как прочитан хоть байт тела. Второй — «можно ли ему это» (`Gate.admit` с тем, что вернул `SpecConsole.needs`: для `POST /cameras` это право `admin`). Порядок задаёт `SpecConsole.dispatch`. У нас кластер ни в какой домен не входит, все шесть строк отсутствуют, и консоль **открыта**: кого-либо спрашивать она не будет, `admit` возвращает имя из `X-User`, а в журнал консоль один раз пишет, что любой, кто до неё дотянулся, — администратор под любым именем. Двенадцать чтений на запрос оператора — цена этой проверки в открытом кластере. Читать эти шесть ключей сокету консоли разрешает файл прав: в списке чтений роли `console` они перечислены поштучно.

В кластере с доменом этим не кончается: консоль проверяет токен из заголовка `Authorization` (или cookie страницы), и для `POST /cameras` у его владельца должно быть право `admin`, не привязанное к какой-то одной камере — камеры ведь ещё нет. Запросов этого пути со стенда я не снимал.

**Вызов 1. Занять ключ идемпотентности.**

> Сразу оговорка, чтобы дальше не искать этот ключ там, где его нет. `vms/idem/` — **целиком дело консоли и её веб-интерфейса**: браузер шлёт заголовок с каждой попыткой записи, консоль этим заголовком защищается от повторов. Контроллеру, воркерам, ресурсам и домену эти строки не принадлежат: писать их не может ни один чужой сокет, и ни один из этих процессов их не читает, хотя права на чтение `vms/*` у контроллера и воркера есть. На размещение, запуск потока и содержимое камеры они не влияют никак.

Проще всего думать об этом как о номерке в гардеробе.

Оператор пришёл с запросом и принёс с собой номерок — тот самый `Idempotency-Key`, строку, которую придумал его браузер. Консоль первым делом пытается повесить этот номерок на гвоздь, и гвоздь тут один на весь кластер: ключ в хранилище с именем номерка.

Дальше возможны ровно два исхода, и они решают всё:

| Что вернуло хранилище | Что это значит | Что делает консоль |
|---|---|---|
| **200** — номерок повесила я | такого запроса раньше не было | обрабатывает: выдаёт номер камере, пишет строку |
| **409** — гвоздь уже занят | этот же запрос уже принял кто-то | **ничего не создаёт**, идёт смотреть, что ответил первый |

Зачем это нужно: оператор мог нажать «Сохранить» дважды, браузер мог сам повторить запрос при обрыве связи, а балансировщик — увести повтор на консоль другого сервера. Без номерка каждая попытка создала бы отдельную камеру, потому что `POST` всегда создаёт новое. С номерком вторая попытка упирается в занятый гвоздь и возвращает **тот же ответ**, что получила первая.

Сам запрос из трассы:

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/idem/k-anna-0001", "cas": "", "items": {
  "state": "pending",
  "at": "1757500000.0",
  "sub": "anna",
  "sha256": "3ef9cbe88ad6f39f04f5254e2e881d595fa138e4b8e50ed666a321aaa62800c4"
}}
→ 200 {"index": 1007}
```

Роль «гвоздя» играет `"cas": ""` — «создать, только если ключа ещё нет» (в коде это `cas=0`, `IdempotencyKeys.claim`). Именно поэтому двое одновременно повесить номерок не могут: один получит `200`, второй `409 {"kind": "conflict", …}`, и решит это хранилище, а не договорённость между консолями. (Клиент хранилища кладёт в каждую запись ещё поле `id` — номер самой записи, чтобы хранилище ответило на её повтор первым ответом; трасса его не печатает.)

`state: pending` означает «я взялась, ответа пока нет». Ответ придёт последним вызовом, когда камера уже создана. Что видит повтор, пришедший в промежутке, разобрано в разделе [8.1](08-failures.md).

Два поля говорят, **чей это номерок и на что он выдан**. `sub` — кто звонит: имя, которое доказал токен, а в открытом кластере — заголовок `X-User`, здесь `anna`. `sha256` — хеш тела запроса, байт в байт как оно пришло. Повтор с тем же ключом от другого человека или с другим телом получит `422 key reused`, а не чужой ответ: номерок выдан на один запрос одного человека.

Сразу после удачного захвата консоль подчищает старые ключи (`IdempotencyKeys.prune`). Делает она это **только здесь** — отдельного процесса-уборщика нет, уборка едет попутным грузом на успешном захвате. В трассе подчистка — это два чтения сразу за захватом:

```
# console on srv-a → /run/configstore/console.sock
GET /v1/list?prefix=vms/idem/
→ 200 {"keys": {"vms/idem/k-anna-0001": 1007}}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/idem/k-anna-0001
→ 200 {
  "items": {
    "state": "pending",
    "at": "1757500000.0",
    "sub": "anna",
    "sha256": "3ef9cbe88ad6f39f04f5254e2e881d595fa138e4b8e50ed666a321aaa62800c4"
  },
  "index": 1007
}
```

Листинг отдаёт ключи с их версиями; консоль читает каждый и смотрит на его `at`. Ключ здесь один — только что повешенный, ему 0 секунд, он остаётся. Будь среди них ключ старше суток, за чтением последовало бы удаление с условием по версии:

```
POST /v1/write {"op": "delete", "key": "vms/idem/<старый ключ>", "cas": <его index>}
```

Четыре правила, по которым это работает:

| Правило | Значение | Зачем именно так |
|---|---|---|
| срок жизни ключа | **24 часа** с момента записи (`ttl=86400`) | сутки — заведомо больше любого разумного повтора запроса |
| как часто подчищать | **не чаще раза в 60 секунд** на процесс консоли | иначе каждое создание камеры стоило бы полного обхода префикса |
| чем меряется этот минутный интервал | монотонными часами **внутри процесса** | у каждой из трёх консолей свой таймер, и они не договариваются |
| как удаляется | `delete` с условием по версии | если кто-то тронул ключ между чтением и удалением, отказ просто пропускается |

Последняя строка — та же защита, что и везде в этой системе: удаляем ровно то, что прочитали, а не «всё, что подошло под условие минуту назад». Ключ, у которого `at` не число, не удаляется и не останавливает обход: возраст его неизвестен, он остаётся.

Право удалять `vms/idem/*` у консоли — из файла прав, а не из кода. Правило файла простое: роль удаляет то, что пишет (у консоли это строки камер, счётчик, ключи идемпотентности, производные строки сроков, заявки и прочее из её списка записи). Два исключения не может снять никакой файл: строку эпохи не удаляет никто, а `domain/*` — никто, кроме ролей самого домена (`StoreMachine.allows` в `w2cplatform/storemachine.py`). Heartbeat'ов и срезов снапшота в хранилище нет вовсе — это файлы на сервере писателя, и удалять их строкой некому и нечего.

В нашем сценарии кластер запущен только что, ключей старше суток нет, и удалять нечего.

### Зачем эти ключи вообще нужны и как они связаны с остальным

Стоит сказать прямо, потому что механизм выглядит тяжёлым для «просто создать камеру».

**Проблема ровно одна: `POST` не повторяем.** Повторите `PUT /cameras/7` десять раз — камера семь десять раз получит одни и те же настройки, итог тот же. Повторите `POST /cameras` десять раз — счётчик десять раз выдаст новый номер, и в кластере появится десять камер. Разница не в вежливости, а в том, что `POST` **создаёт новую сущность с новым именем**, и повторить его «без последствий» невозможно в принципе.

А повторы будут. Браузер повторяет запрос сам при обрыве соединения. Оператор нажимает «Сохранить» дважды, не дождавшись ответа. Балансировщик уводит повтор на консоль **другого** сервера, потому что первая перестала отвечать.

**Отсюда требование: состояние повторов должно лежать там, где его увидят все три консоли.** Держи консоль список обработанных запросов у себя в памяти — повтор, попавший на соседнюю, создал бы вторую камеру, а перезапуск консоли стёр бы всю защиту. Поэтому ключи живут в общем хранилище кластера — `configstore`, реплицированном raft'ом на три сервера ([М11, урок 2](../../М11_ClusterVMS/02-the-store-becomes-replicated.md)), — рядом со строками камер.

**Ключ придумывает клиент, а не сервер.** Браузер генерирует ключ перед отправкой и повторяет запрос **с тем же** заголовком. Это и делает повтор узнаваемым: сервер узнаёт его по ключу, а хеш тела в захвате только проверяет, что под этим ключом пришёл тот же самый запрос.

Из этого следует граница, которую стоит знать: **ключ узнаёт повтор, но не дубль**. Два запроса с разными ключами — это два создания, и одинаковое тело тут ничего не меняет. Дубль останавливает другая проверка — `source` и `ref` у камеры свои (вызов 5 ниже), и вторая камера на тот же канал устройства получит `400`. А тот же ключ с другим телом — `422`: под одним номерком два разных запроса не проходят.

**Жизнь одного ключа целиком:**

| Состояние | Что в ключе | Что видит повтор |
|---|---|---|
| захвачен | `state: pending`, `at`, `sub`, `sha256` | ждёт до двух секунд (40 опросов по 50 мс), потом получает `409 in flight`; захват, простоявший 30 секунд, повтор забирает себе условной записью и делает работу сам |
| с номером | то же и `id` выданного номера | то же, но забравший создаёт камеру **под этим номером** — или находит её созданной и отвечает ею |
| отработан | `state: done`, код ответа и его тело | **тот же самый ответ**, что получил первый запрос |
| просрочен | ключа больше нет | обрабатывается как новый запрос |

Тридцать секунд (`PENDING_TTL`) меряются часами той консоли, которая ждёт, с момента, когда она впервые увидела эту версию захвата (`IdempotencyKeys.claim`), а не по `at`, которое записала соседняя консоль своими часами: консоль с отстающими часами иначе считала бы чужие свежие захваты брошенными. Без номера в захвате «ответ потерялся» и «камера так и не создана» выглядели бы для повтора одинаково, и он создавал бы вторую.

Последняя строка сознательная: забытый ключ — это новый запрос. Через сутки гарантия просто перестаёт действовать, и это честнее, чем хранить её вечно. Вторую камеру на тот же источник просроченный ключ всё равно не создаст: её остановит проверка источника.

**Связь с остальными механизмами документа.** Их легко перепутать, потому что все четверо отвечают на вопрос «кто победил», но защищают они разное:

| Механизм                             | От чего защищает                          | Где живёт                 |
| ------------------------------------ | ----------------------------------------- | ------------------------- |
| **ключ идемпотентности**             | повтор запроса создаст вторую камеру      | `vms/idem/<ключ>`         |
| **`cas` при записи**                 | две правки одной строки затрут друг друга | поле запроса `/v1/write`  |
| **`revision` и `observed_revision`** | настройка записана, но ещё не применена   | поле строки и heartbeat'а |
| **эпоха**                            | два процесса пишут архив одной камеры     | `vms/epoch/<камера>`      |

Общий у них ровно один приём — **«первый, кто записал, выиграл»**. Захват ключа идемпотентности делается тем же `"cas": ""`, что и создание камеры, и тем же, что и взятие эпохи воркером. Одна и та же операция хранилища закрывает три совершенно разные задачи, и в этом всё удобство: ничего специального под идемпотентность в хранилище добавлять не пришлось.

**Цена вопроса** — три записи на каждое создание (захват, номер в захвате, ответ), плюс обход префикса не чаще раза в минуту. Для `PUT` заголовок необязателен, и там он нужен реже: правка и так повторяема.

**Вызовы 2 и 3. Выдать номер камере.**

Номер выдаёт счётчик — отдельный ключ с единственным полем. Прочитать, прибавить единицу, записать обратно с условием по версии (`SpecController._next_id` через `Controller.write`):

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/next_id
→ 200 {"items": null, "index": ""}            ← счётчика ещё нет

# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/next_id", "cas": "", "items": {"n": "1"}}
→ 200 {"index": 1008}
```

Камера получила номер **1**.

Почему два вызова, а не один: хранилище не умеет прибавлять к полю, оно умеет только «положить, если версия всё ещё та». Пустой `index` прочитанного ключа становится `"cas": ""` — «только создать». Если бы вторая консоль в этот момент выдавала номер своей камере, одна из двух получила бы `409` и повторила цикл, перечитав счётчик, — до десяти попыток, с растущей случайной паузой между ними. Как это выглядит в трассе, когда две консоли сталкиваются, — раздел [8.2](08-failures.md).

**Вызов 4. Записать номер в захват.**

Номер выдан, но строки камеры ещё нет. Прежде чем её писать, консоль кладёт номер в свой захват ключа идемпотентности — условной записью по версии, которую сама записала вызовом 1 (`1007`):

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/idem/k-anna-0001", "cas": 1007, "items": {
  "state": "pending",
  "at": "1757500000.0",
  "sub": "anna",
  "sha256": "3ef9cbe88ad6f39f04f5254e2e881d595fa138e4b8e50ed666a321aaa62800c4",
  "id": "1"
}}
→ 200 {"index": 1009}
```

Зачем — сказано выше, в таблице жизни ключа: если консоль умрёт между этим вызовом и строкой камеры, повтор, забравший захват, создаст камеру под номером 1, а не выдаст второй номер. А `cas` здесь нужен на обратный случай: если захват уже забрала другая консоль, эта получит `409`, ответит `409 taken over` и строку писать не станет (`IdempotencyKeys.reserve`).

**Вызов 5. Не занят ли источник.**

```
# console on srv-a → /run/configstore/console.sock
GET /v1/list?prefix=vms/cameras/
→ 200 {"keys": {}}                            ← камер ещё нет: сравнивать не с чем
```

Один канал устройства — одна камера, и одно имя для слоя выше — одна камера: консоль перебирает все строки камер и сравнивает их `source` и `ref` с присланными (`refuse_camera` в `vms/volumes.py`). Совпадение — `400` с номером той камеры, которая этот источник уже занимает. Для первой камеры это один пустой листинг; для второй — листинг и одно чтение, для N-й — листинг и N−1 чтений.

**Вызов 6. Записать строку камеры.**

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/cameras/1", "cas": "", "items": {
  "id": "1",
  "revision": "1",
  "name": "Ворота",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": "true",
  "priority": "100",
  "labels": "vlan:cctv",
  "folders": "",
  "ref": "",
  "cred_username": "",
  "cred_secret": "",
  "live": "always",
  "kind": "video"
}}
→ 200 {"index": 1010}
```

Четыре вещи стоит заметить.

**Записались не только присланные поля.** Оператор прислал три, в строке тринадцать: `id`, `revision` и умолчания спецификации (`enabled: true`, `priority: 100`, `live: always`, `kind: video`, пустые `folders`, `ref`, `cred_username`, `cred_secret`). Все значения — строки: так хранилище держит `items`, и список меток стал строкой `"vlan:cctv"`. А трёх полей в строке нет вовсе — `events_retention_days`, `alarms_retention_days` и `alarms`. У них не умолчание, а наследование (`inherit` в `vms/vms.subsystem.yaml`): не заданное у камеры значение берётся там, где его читают, — своё, иначе срок подсистемы, иначе 365 дней для событий и 1095 для тревог; список тревожных видов `alarms` не заменяет общий, а складывается с ним. Запиши консоль 365 в строку, общее умолчание уже никогда бы до этой камеры не дошло: «задано 365» и «не задано» стали бы одной строкой.

**`revision: 1`.** Это счётчик правок, и он же — токен сходимости. Воркер сравнит его со своим `observed_revision` и так поймёт, применил он эту версию настроек или ещё нет.

**Пароль в строке был бы запечатан.** У нас `cred_secret` пустой, и печатать нечего. Будь он задан, консоль зашифровала бы его ключом кластера (`w2cplatform/sealing.py`) в `enc:v1:<kid>:<nonce>:<шифротекст>`: AES-256-GCM, а дополнительные данные — имя ключа строки (`vms/cameras/1`) и имя поля, так что запечатанный пароль, вставленный в другое поле или в строку другой камеры, не откроется. Процесс получает ключ файлом: юнит systemd консоли загружает его как учётные данные (`LoadCredential=platform.key:/etc/w2c/secrets/platform.key`, `SECRETS_KEY=%d/platform.key`), и видит этот файл только сам процесс ([М11, урок 3](../../М11_ClusterVMS/03-units-on-every-server.md)). Ключ лежит не в хранилище, а файлом на каждом сервере, поэтому копия хранилища без него — шифротекст. Открывают пароль только воркер и регистратор — в последний момент, для пайплайна; контроллер, ресурс и домен ключа не имеют.

**Снова `"cas": ""`.** Номер 1 только что выдан счётчиком, и всё же запись создающая. Если бы ключ уже существовал, запись провалилась бы вместо того, чтобы затереть чужую камеру.

**Вызовы 7 и 8. Производные строки для ресурса.**

Сроки хранения дублируются в отдельные ключи, потому что у них **другой читатель**: ресурсу сервера нужен срок хранения событий и тревог, а камера целиком ему не нужна.

```
# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/retention/1
→ 200 {"items": null, "index": ""}

# console on srv-a → /run/configstore/console.sock
GET /v1/get?key=vms/alarms_retention/1
→ 200 {"items": null, "index": ""}
```

Только чтения, без записей (`SpecController._derived`). Срок у камеры не задан, производной строке сказать нечего: пустое совпало с пустым, и консоль её не пишет. Ресурс, не найдя строку, пойдёт по своей цепочке — `vms/retention` подсистемы, иначе год для событий и три года для тревог (`retention_days` в `w2cplatform/resource.py`). Пришли оператор `"events_retention_days": 30`, здесь была бы ещё запись `vms/retention/1` с `"cas": ""` и `{"days": "30"}` — так и происходит при правке камеры 2 в [части 7](07-edit-and-delete.md).

**Вызов 9. Положить ответ рядом с ключом идемпотентности.**

```
# console on srv-a → /run/configstore/console.sock
POST /v1/write {"op": "put", "key": "vms/idem/k-anna-0001", "cas": 1009, "items": {
  "state": "done",
  "status": "201",
  "body": "{\"id\": 1, \"name\": \"\\u0412\\u043e\\u0440\\u043e\\u0442\\u0430\", \"source\": \"driverpack://acme/10.2.0.11\", \"enabled\": true, \"events_retention_days\": null, \"alarms_retention_days\": null, \"priority\": 100, \"labels\": [\"vlan:cctv\"], \"folders\": [], \"alarms\": null, \"ref\": \"\", \"cred_username\": \"\", \"cred_secret\": \"\", \"live\": \"always\", \"kind\": \"video\", \"revision\": 1, \"worker\": null}",
  "at": "1757500000.0",
  "sub": "anna",
  "sha256": "3ef9cbe88ad6f39f04f5254e2e881d595fa138e4b8e50ed666a321aaa62800c4"
}}
→ 200 {"index": 1011}
```

`body` — тот самый ответ оператору, сериализованный в JSON (`В…` — это «Ворота»). И здесь условная запись по версии своего захвата (`1009`): если его успела забрать другая консоль, ответ хранить будет она. Ответ с кодом `5xx` под ключом не хранится вовсе — «хранилище недоступно» не ответ на запрос; захват тогда отпускается, и повтор делает работу заново.

Итого на один `POST` оператора в трассе — **18 чтений и 5 записей**, объектов и файлов ноль. Пять записей: захват ключа, счётчик, номер в захвате, строка камеры, ответ. Чтения: двенадцать «кто звонит», два подчистки (листинг `vms/idem/` и чтение каждого ключа под ним), счётчик, листинг камер, две производные строки. К ним добавляется по чтению на каждую уже заведённую камеру, а подчистка бывает не чаще раза в минуту. И одна строка `unit.created` — с именами присланных полей, без значений — в журнал действий (`w2cplatform/journal.py`); это строка журнала событий на диске сервера, под ресурсом, а не запись в хранилище.

## 3.3. Ответ оператору

```
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 1,
  "name": "Ворота",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": true,
  "events_retention_days": null,
  "alarms_retention_days": null,
  "priority": 100,
  "labels": [
    "vlan:cctv"
  ],
  "folders": [],
  "alarms": null,
  "ref": "",
  "cred_username": "",
  "cred_secret": "",
  "live": "always",
  "kind": "video",
  "revision": 1,
  "worker": null
}
```

`null` у `events_retention_days`, `alarms_retention_days` и `alarms` — это «у камеры не задано», а не «ноль»: значения возьмут по цепочке наследования из вызова 6. В ответе значения уже снова своих типов (`true`, `100`, список меток), а не строки, как в хранилище.

Два поля в этом ответе объясняют всю дальнейшую часть документа.

**`cred_secret`.** Здесь он пустой, потому что пароль не присылали. Присланный пароль на выходе был бы `"***"`: поле, чьё имя кончается на `_secret`, наружу не уходит (`mask_secrets` в `w2cplatform/secrets.py`; пустое значение маскировать нечем, оно остаётся пустым). Замаскирован и тот ответ, что консоль кладёт в ключ идемпотентности, — иначе пароль лежал бы вторым экземпляром там, куда никто не догадается заглянуть.

**`worker: null`, и это не ошибка.** Консоль размещение не выбирает и выбрать не может: её сокету запрещено писать `vms/placement/*` и `vms/workers/*`. Попытка вернула бы `403 {"kind": "forbidden", "error": "console may not write vms/workers/w-srv-a-1"}` — такая строка есть в трассе [урока 5 М11](../../М11_ClusterVMS/05-rights-by-who-is-calling.md). Камера создана, но пока нигде не работает — её подберёт контроллер на своём проходе.

Ровно это и делает ответ честным: «настройка записана» и «камера работает» — разные утверждения, и между ними до пяти секунд.

## 3.4. Что теперь в хранилище

К тому, что лежало до оператора ([часть 2](02-before-first-camera.md): `platform/doors/srv-a…c` и слоты `vms/slots/w-srv-a-1…w-srv-c-1`), прибавилось:

| Ключ | index | Значение |
|---|---|---|
| `vms/idem/k-anna-0001` | 1011 | `state: done`, ответ 201 |
| `vms/next_id` | 1008 | `n: 1` |
| `vms/cameras/1` | 1010 | строка, `revision: 1` |
| `vms/retention/1`, `vms/alarms_retention/1` | — | **не существуют**: сроки не заданы |
| `vms/placement/1` | — | **не существует** |
| `vms/workers/w-srv-a-1` | — | **не существует** |

Ни одного объекта и ни одного файла консоль не тронула: heartbeat'ы воркеров и ресурсов остались, какими были.

## 3.5. Камеры два и три

Оператор создаёт ещё две камеры, через секунду и через две. Запросы те же, меняются номера и индексы. Трасса для них печатает только HTTP-обмен и записи, а чтения считает: 17 у камеры 2, 18 у камеры 3. Какие это чтения, видно по коду — ниже они вписаны строками без ответа.

**Камера 2:**

```
POST /cameras
X-User: anna
Idempotency-Key: k-anna-0002

{"name": "Парковка", "source": "driverpack://acme/10.2.0.12", "labels": ["vlan:cctv"]}

→ GET  domain/…  ×12                                    кто звонит: никто не спрашивает
  put  vms/idem/k-anna-0002     cas ""                  → index 1012
  GET  vms/next_id                                       {"n": "1"}, index 1008
  put  vms/next_id              cas 1008, {"n": "2"}    → index 1013
  put  vms/idem/k-anna-0002     cas 1012, id: "2"       → index 1014
  GET  list vms/cameras/                                 [vms/cameras/1]
  GET  vms/cameras/1                                     source …10.2.0.11: не совпадает
  put  vms/cameras/2            cas ""                  → index 1015
  GET  vms/retention/2, vms/alarms_retention/2           нет
  put  vms/idem/k-anna-0002     cas 1014, state: done   → index 1016

→ 201 {"id": 2, "name": "Парковка", …, "revision": 1, "worker": null}
```

Обратите внимание на запись счётчика: теперь он существует, поэтому запись идёт не с `"cas": ""`, а с `"cas": 1008` — «только если с момента моего чтения его никто не трогал». Подчистки ключей идемпотентности здесь нет: с прошлой не прошло и минуты, поэтому чтений на два меньше, зато прибавилось чтение `vms/cameras/1`.

**Камера 3:**

```
POST /cameras
X-User: anna
Idempotency-Key: k-anna-0003

{"name": "Склад", "source": "driverpack://acme/10.2.0.13", "labels": ["vlan:cctv"]}

→ 201 {"id": 3, "name": "Склад", …, "revision": 1, "worker": null}
```

Запросы те же, что у камеры 2, кроме одного места: проверка источника теперь читает две строки, `vms/cameras/1` и `vms/cameras/2` (отсюда 18 чтений). Записи: захват `vms/idem/k-anna-0003` → 1017, счётчик `{"n": "3"}` с `"cas": 1013` → 1018, номер в захвате → 1019, строка `vms/cameras/3` → 1020, ответ → 1021.

Итог: три камеры, все с одинаковой меткой `vlan:cctv`, ни одна нигде не размещена.

| Камера | Имя | Источник | Метки | revision | placement |
|---|---|---|---|---|---|
| 1 | Ворота | `driverpack://acme/10.2.0.11` | `vlan:cctv` | 1 | нет |
| 2 | Парковка | `driverpack://acme/10.2.0.12` | `vlan:cctv` | 1 | нет |
| 3 | Склад | `driverpack://acme/10.2.0.13` | `vlan:cctv` | 1 | нет |
