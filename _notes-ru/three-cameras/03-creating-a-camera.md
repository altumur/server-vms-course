Дальше идёт время. `T+0` — момент, когда оператор нажал «Сохранить».

## 3.1. Запрос оператора

```
POST /cameras HTTP/1.1
Host: srv-1:8080
Content-Type: application/json
Idempotency-Key: 8f4b21e0-5d3c-4a19-9b77-0c2e5a1f3d64

{
  "name": "Ворота",
  "source": "driverpack://acme/10.2.0.11",
  "labels": "vlan:cctv",
  "ref": "north-gate",
  "cred_username": "operator",
  "cred_secret": "hunter2"
}
```

Заголовок `Idempotency-Key` обязателен: консоль без него отвечает `400`. Причина в том, что повтор запроса может попасть на **другую консоль**, и она должна узнать о первой попытке — а узнать может только из хранилища. Ключ становится частью пути в хранилище, поэтому он должен быть одним сегментом: без `/` и `..`, не длиннее 200 символов, иначе тоже `400`.

Поле `source` — адрес устройства, и консоль проверяет его как адрес: логин и пароль внутри него (`driverpack://root:hunter2@…`) отклоняются, потому что `source` уходит в снапшот, за пределы кластера. Учётные данные устройства идут в отдельные поля `cred_username` и `cred_secret`.

Поле `labels` здесь — требование к серверу: «эту камеру видно только из сегмента `vlan:cctv`». Контроллер по нему отсеет серверы, которые до камеры не дотягиваются. Подробно — в разделе [4.1](04-placement.md), где этот фильтр применяется. Прислать метки можно и списком (`["vlan:cctv"]`), и строкой через запятую — хранится всё равно строка.

Полей `worker`, `placement`, `revision`, `observed_revision`, `epoch`, `phase`, `id` в теле нет и быть не может. Это поля платформы, и попытка их прислать даёт `400` с объяснением, чьи они.

## 3.2. Во что этот запрос превращается на стороне Nomad

Консоль делает **девять** вызовов своим токеном — плюс по чтению на каждую уже заведённую камеру и подчистку старых ключей, если подошёл её срок, — а перед ними спрашивает, кто звонит. Порядок у них жёсткий: сначала застолбить запрос, потом выдать номер и записать его в захват, потом убедиться, что источник не занят, потом записать данные, в конце — положить ответ туда, где его найдёт повтор.

Запросы ниже сняты со стенда: настоящая консоль М11 поднята по HTTP поверх хранилища в памяти, и три `POST /cameras` из этой части отправлены ей как есть.

> Одно чтение случилось ещё раньше, при старте консоли, и к запросу оператора не относится: `GET /v1/var/platform/schema` → `404`. Его делает один раз любой процесс, открывший хранилище, — сверяет, понимает ли он его формат. `404` значит «формат тот, который знает эта сборка»: установка свежая. Будь хранилище новее сборки, консоль не запустилась бы вовсе.

**Сначала — кто звонит.**

До всякой записи консоль спрашивает хранилище, состоит ли кластер в домене (`Gate` в `w2cplatform/access.py`). Признак один — набор ключей домена `domain/keys`; а если его нет, она проверяет ещё пять строк, которые пишет только агент домена: по ним видно, что кластер в домене был и ключи потерял.

```
GET /v1/var/domain/keys        → 404
GET /v1/var/domain/member      → 404
GET /v1/var/domain/root        → 404
GET /v1/var/domain/grants      → 404
GET /v1/var/domain/revoked     → 404
GET /v1/var/domain/break_glass → 404

… и те же шесть ещё раз
```

Дважды — потому что вопросов два, и каждый перечитывает хранилище заново: «кто звонит» (`Gate.caller`, по заголовкам, до того как прочитано тело) и «можно ли ему это» (`Gate.admit`). У нас кластер ни в какой домен не входит, все шесть строк отсутствуют, и консоль **открыта**: кого-либо спрашивать она не будет, а в журнал один раз пишет, что любой, кто до неё дотянулся, — администратор под любым именем. Двенадцать чтений на запрос оператора — цена этой проверки в открытом кластере.

В кластере с доменом этим не кончается: консоль проверяет токен из заголовка `Authorization`, и для `POST /cameras` у его владельца должно быть право `admin` (`SpecConsole.needs` в `w2cplatform/console.py`), не привязанное к какой-то одной камере — камеры ведь ещё нет. Запросов этого пути я со стенда не снимал.

**Вызов 1. Занять ключ идемпотентности.**

> Сразу оговорка, чтобы дальше не искать этот ключ там, где его нет. `vms/idem/` — **целиком дело консоли и её веб-интерфейса**: браузер шлёт заголовок с каждой попыткой записи, консоль этим заголовком защищается от повторов. Контроллеру, воркерам, ресурсам и доменному слою эти строки не принадлежат: писать их не может ни один чужой токен, и ни один из этих процессов их не читает, хотя права на чтение `vms/*` у контроллера и воркера есть. На размещение, запуск потока и содержимое камеры они не влияют никак.

Проще всего думать об этом как о номерке в гардеробе.

Оператор пришёл с запросом и принёс с собой номерок — тот самый `Idempotency-Key`, случайную строку, которую придумал его браузер. Консоль первым делом пытается повесить этот номерок на гвоздь, и гвоздь тут один на весь кластер: ключ в хранилище с именем номерка.

Дальше возможны ровно два исхода, и они решают всё:

| Что вернуло хранилище | Что это значит | Что делает консоль |
|---|---|---|
| **200** — номерок повесила я | такого запроса раньше не было | обрабатывает: выдаёт номер камере, пишет строку |
| **409** — гвоздь уже занят | этот же запрос уже принял кто-то | **ничего не создаёт**, идёт смотреть, что ответил первый |

Зачем это нужно: оператор мог нажать «Сохранить» дважды, браузер мог сам повторить запрос при обрыве связи, а балансировщик — увести повтор на другую консоль. Без номерка каждая попытка создала бы отдельную камеру, потому что `POST` всегда создаёт новое. С номерком вторая попытка упирается в занятый гвоздь и возвращает **тот же ответ**, что получила первая.

Сам запрос выглядит так:

```
PUT /v1/var/vms/idem/8f4b21e0-5d3c-4a19-9b77-0c2e5a1f3d64?namespace=default&cas=0

{
  "Items": {
    "state": "pending",
    "at": "1757500000.0",
    "sub": "operator",
    "sha256": "54c500595d60ca8852b2490fd940865bcc4b9d6d7cd4e9a971eb4ee69412c265"
  }
}

→ 200 {"ModifyIndex": 4401}
```

Роль «гвоздя» играет `cas=0` — «создать, только если ключа ещё нет». Именно поэтому двое одновременно повесить номерок не могут: один получит `200`, второй `409`, и решит это хранилище, а не договорённость между консолями.

`state: pending` означает «я взялась, ответа пока нет». Запись ответа придёт последним вызовом, когда камера уже создана. Что видит повтор, пришедший в промежутке, разобрано в разделе [8.1](08-failures.md).

Два поля говорят, **чей это номерок и на что он выдан**. `sub` — кто звонит: имя, которое доказал токен, а в открытом кластере — заголовок `X-User` или, как здесь, `operator` по умолчанию. `sha256` — хеш тела запроса. Повтор с тем же ключом от другого человека или с другим телом получит `422 key reused`, а не чужой ответ: номерок выдан на один запрос одного человека.

Сразу после удачного захвата консоль подчищает старые ключи. Делает она это **только здесь** — отдельного процесса-уборщика в системе нет, уборка едет попутным грузом на успешном создании.

Подчистка устроена так:

```
# 1. Взять все ключи идемпотентности этой подсистемы
GET /v1/vars?prefix=vms/idem/

→ 200
[
  {"Path": "vms/idem/8f4b21e0-…", "ModifyIndex": 4401, …},
  {"Path": "vms/idem/b30d77c4-…", "ModifyIndex": 2110, …}
]

# 2. Прочитать каждый и посмотреть на его отметку времени
GET /v1/var/vms/idem/8f4b21e0-…   → {"state": "pending", "at": "1757500000.0", …}   возраст 0 с → оставить
GET /v1/var/vms/idem/b30d77c4-…   → {"state": "done",    "at": "1757410000.0", …}   возраст 25 ч → удалить

# 3. Удалить просроченные, с условием по версии
DELETE /v1/var/vms/idem/b30d77c4-…?cas=2110
→ 200
```

Четыре правила, по которым это работает:

| Правило | Значение | Зачем именно так |
|---|---|---|
| срок жизни ключа | **24 часа** с момента записи | сутки — заведомо больше любого разумного повтора запроса |
| как часто подчищать | **не чаще раза в 60 секунд** на процесс консоли | иначе каждое создание камеры стоило бы полного обхода префикса |
| чем меряется этот минутный интервал | монотонными часами **внутри процесса** | у каждой из трёх консолей свой таймер, и они не договариваются |
| как удаляется | `DELETE` с условием по версии | если кто-то тронул ключ между чтением и удалением, отказ просто пропускается |

Последняя строка — та же защита, что и везде в этой системе: удаляем ровно то, что прочитали, а не «всё, что подошло под условие минуту назад».

Удаление вообще-то редкая операция. В подсистеме VMS право стирать есть у консоли на четырёх префиксах — ключи идемпотентности, производные строки со сроком хранения событий (`vms/retention/*`), байты больших полей и заявки оператора на разовую работу (`vms/requests/*`) — и у воркера на одном: его отметки «начинаю выполнять заявку» (`objects/vms/commands/*`). В подсистеме записи консоль стирает ещё тома архива и «сохранить этот отрезок» (`rec/volumes/*`, `rec/keeps/*`). Heartbeat'ы и шарды снапшота стереть не может никто — поэтому шард ушедшего воркера контроллер переписывает пустым вместо того, чтобы удалить.

Заметьте, что и это право взялось не из кода, а из токена: в политике у этих путей стоит отдельная возможность `destroy`. У контроллера её нет нигде.

В нашем сценарии кластер запущен только что, ключей старше суток нет, и удалять нечего.

### Зачем эти ключи вообще нужны и как они связаны с остальным

Стоит сказать прямо, потому что механизм выглядит тяжёлым для «просто создать камеру».

**Проблема ровно одна: `POST` не повторяем.** Повторите `PUT /cameras/7` десять раз — камера семь десять раз получит одни и те же настройки, итог тот же. Повторите `POST /cameras` десять раз — счётчик десять раз выдаст новый номер, и в кластере появится десять камер. Разница не в вежливости, а в том, что `POST` **создаёт новую сущность с новым именем**, и повторить его «без последствий» невозможно в принципе.

А повторы будут. Браузер повторяет запрос сам при обрыве соединения. Оператор нажимает «Сохранить» дважды, не дождавшись ответа. Балансировщик уводит повтор на **другую** консоль, потому что первая перестала отвечать.

**Отсюда требование: состояние повторов должно лежать там, где его увидят все три консоли.** Держи консоль список обработанных запросов у себя в памяти — повтор, попавший на соседнюю, создал бы вторую камеру, а падение консоли стёрло бы всю защиту. Поэтому ключи живут в Nomad Variables, рядом со всем остальным.

**Ключ придумывает клиент, а не сервер.** Браузер генерирует UUID перед отправкой и повторяет запрос **с тем же** заголовком. Это и делает повтор узнаваемым: сервер узнаёт его по ключу, а хеш тела в захвате только проверяет, что под этим ключом пришёл тот же самый запрос.

Из этого следует граница, которую стоит знать: **ключ узнаёт повтор, но не дубль**. Два запроса с разными ключами — это два создания, и одинаковое тело тут ничего не меняет. Дубль останавливает другая проверка — `source` и `ref` у камеры свои (вызов 5 ниже), и вторая камера на тот же канал устройства получит `400`. А тот же ключ с другим телом — `422`: под одним номерком два разных запроса не проходят.

**Жизнь одного ключа целиком:**

| Состояние | Что в ключе | Что видит повтор |
|---|---|---|
| захвачен | `state: pending`, `sub`, `sha256` | ждёт до двух секунд, потом получает `409 in flight`; захват, простоявший 30 секунд, повтор забирает себе условной записью и делает работу сам |
| с номером | то же и `id` выданного номера | то же, но забравший создаёт камеру **под этим номером** — или находит её созданной и отвечает ею |
| отработан | `state: done`, код ответа и его тело | **тот же самый ответ**, что получил первый запрос |
| просрочен | ключа больше нет | обрабатывается как новый запрос |

Тридцать секунд меряются часами той консоли, которая ждёт, с момента, когда она впервые увидела эту версию захвата (`IdempotencyKeys.claim`), а не по `at`, которое записала соседняя консоль своими часами: консоль с отстающими часами иначе считала бы чужие свежие захваты брошенными. Без номера в захвате «ответ потерялся» и «камера так и не создана» выглядели бы для повтора одинаково, и он создавал бы вторую.

Последняя строка сознательная: забытый ключ — это новый запрос. Через сутки гарантия просто перестаёт действовать, и это честнее, чем хранить её вечно. Вторую камеру на тот же источник просроченный ключ всё равно не создаст: её остановит проверка источника.

**Связь с остальными механизмами документа.** Их легко перепутать, потому что все четверо отвечают на вопрос «кто победил», но защищают они разное:

| Механизм                             | От чего защищает                          | Где живёт                 |
| ------------------------------------ | ----------------------------------------- | ------------------------- |
| **ключ идемпотентности**             | повтор запроса создаст вторую камеру      | `vms/idem/<ключ>`         |
| **`cas` при записи**                 | две правки одной строки затрут друг друга | параметр запроса          |
| **`revision` и `observed_revision`** | настройка записана, но ещё не применена   | поля строки и heartbeat'а |
| **эпоха**                            | два процесса пишут архив одной камеры     | `vms/epoch/<камера>`      |

Общий у них ровно один приём — **«первый, кто записал, выиграл»**. Захват ключа идемпотентности делается тем же `cas=0`, что и создание камеры, и тем же, что и взятие слота воркером. Одна и та же операция хранилища закрывает три совершенно разные задачи, и в этом всё удобство: ничего специального под идемпотентность в хранилище добавлять не пришлось.

**Цена вопроса** — три записи на каждое создание (захват, номер, ответ), плюс обход префикса не чаще раза в минуту. Для `PUT` заголовок необязателен, и там он нужен реже: правка и так повторяема.

**Вызов 2 и 3. Выдать номер камере.**

Номер выдаёт счётчик — отдельный ключ с единственным полем. Прочитать, прибавить единицу, записать обратно с условием по версии:

```
GET /v1/var/vms/next_id
→ 404                                       ← счётчика ещё нет: (None, 0)

PUT /v1/var/vms/next_id?cas=0
{"Items": {"n": "1"}}
→ 200 {"ModifyIndex": 4405}
```

Камера получила номер **1**.

Почему два вызова, а не один: Nomad не умеет инкрементировать поле. Прочитали, прибавили, записали с условием «индекс всё ещё тот». Если бы вторая консоль в этот момент выдавала номер своей камере, одна из двух получила бы `409` и повторила цикл с новым индексом — до десяти попыток.

**Вызов 4. Записать номер в захват.**

Номер выдан, но строки камеры ещё нет. Прежде чем её писать, консоль кладёт номер в свой захват ключа идемпотентности — условной записью по версии, которую сама записала вызовом 1:

```
PUT /v1/var/vms/idem/8f4b21e0-5d3c-4a19-9b77-0c2e5a1f3d64?cas=4401

{
  "Items": {
    "state": "pending",
    "at": "1757500000.0",
    "sub": "operator",
    "sha256": "54c500595d60ca8852b2490fd940865bcc4b9d6d7cd4e9a971eb4ee69412c265",
    "id": "1"
  }
}

→ 200 {"ModifyIndex": 4407}
```

Зачем — сказано выше, в таблице жизни ключа: если консоль умрёт между этим вызовом и строкой камеры, повтор, забравший захват, создаст камеру под номером 1, а не выдаст второй номер. А `cas` здесь нужен на обратный случай: если захват уже забрала другая консоль, эта получит `409`, ответит `409 taken over` и строку писать не станет (`IdempotencyKeys.reserve`).

**Вызов 5. Не занят ли источник.**

```
GET /v1/vars?prefix=vms/cameras/
→ 200 []                                    ← камер ещё нет: сравнивать не с чем
```

Один канал устройства — одна камера, и одно имя для слоя выше — одна камера: консоль перебирает все строки камер и сравнивает их `source` и `ref` с присланными (`refuse_camera` в `vms/volumes.py`). Совпадение — `400` с номером той камеры, которая этот источник уже занимает. Для первой камеры это один пустой листинг; для второй — листинг и одно чтение, для N-й — листинг и N−1 чтений.

**Вызов 6. Записать строку камеры.**

```
PUT /v1/var/vms/cameras/1?cas=0

{
  "Items": {
    "id": "1",
    "revision": "1",
    "name": "Ворота",
    "source": "driverpack://acme/10.2.0.11",
    "enabled": "true",
    "priority": "100",
    "labels": "vlan:cctv",
    "folders": "",
    "ref": "north-gate",
    "cred_username": "operator",
    "cred_secret": "enc:v1:<kid>:<nonce>:<шифротекст>",
    "live": "always",
    "kind": "video"
  }
}

→ 200 {"ModifyIndex": 4409}
```

Четыре вещи стоит заметить.

**Записались не только присланные поля.** Оператор прислал шесть, в строке тринадцать: `id`, `revision` и умолчания спецификации (`enabled: true`, `priority: 100`, `live: always`, `kind: video`, пустые `folders`). А трёх полей в строке нет вовсе — `events_retention_days`, `alarms_retention_days` и `alarms`. У них не умолчание, а наследование (`inherit` в `vms/vms.subsystem.yaml`): не заданное у камеры значение берётся там, где его читают, — своё, иначе умолчание домена, иначе 365 дней для событий и 1095 для тревог; список тревожных видов `alarms` не заменяет доменный, а складывается с ним. Запиши консоль 365 в строку, общее умолчание домена уже никогда бы до этой камеры не дошло: «задано 365» и «не задано» стали бы одной строкой.

**`revision: 1`.** Это счётчик правок, и он же — токен сходимости. Воркер сравнит его со своим `observed_revision` и так поймёт, применил он эту версию настроек или ещё нет.

**Пароль в строке запечатан.** Консоль шифрует каждое поле `*_secret` ключом кластера (`w2cplatform/sealing.py`): AES-256-GCM, имя поля — дополнительные данные, так что запечатанный пароль, вставленный в другое поле, не откроется. Процесс получает ключ файлом (`SECRETS_KEY`). На отдельном сервере это файл, смонтированный двум юнитам; в кластере джобспек консоли и воркера рендерит его из переменной Nomad `secrets/vms` — то есть ключ лежит в том же raft, только под путём, который читают не все, и копия raft целиком унесёт и его. Открывает пароль только воркер — в последний момент, для пайплайна. Контроллер, ресурс и домен файла ключа не имеют и видят шифротекст; копия строк камер без ключа — тоже шифротекст (что токен контроллера по букве политики может прочесть и саму переменную `secrets/vms`, — пометка в конце [справочника](01-reference.md)). Стенд, с которого сняты эти запросы, шёл без ключа: тогда пароль пишется как есть, и консоль один раз говорит в журнал, что секреты хранятся открытыми.

**Снова `cas=0`.** Номер 1 только что выдан счётчиком, и всё же запись создающая. Если бы ключ уже существовал, запись провалилась бы вместо того, чтобы затереть чужую камеру.

**Вызов 7 и 8. Производные строки для ресурса.**

Сроки хранения дублируются в отдельные ключи, потому что у них **другой читатель**: ресурсу сервера нужен срок хранения событий и тревог, а камера целиком ему не нужна.

```
GET /v1/var/vms/retention/1
→ 404

GET /v1/var/vms/alarms_retention/1
→ 404
```

Только чтения, без записей. Срок у камеры не задан, производной строке сказать нечего, и консоль её не пишет: ресурс, не найдя строку, пойдёт по своей цепочке — срок подсистемы, иначе год для событий и три года для тревог (`retention_days` в `w2cplatform/resource.py`). Пришли оператор `"events_retention_days": 30`, здесь был бы ещё `PUT /v1/var/vms/retention/1?cas=0` с `{"days": "30"}`.

**Вызов 9. Положить ответ рядом с ключом идемпотентности.**

```
PUT /v1/var/vms/idem/8f4b21e0-5d3c-4a19-9b77-0c2e5a1f3d64?cas=4407

{
  "Items": {
    "state": "done",
    "status": "201",
    "body": …,
    "at": "1757500000.0",
    "sub": "operator",
    "sha256": "54c500595d60ca8852b2490fd940865bcc4b9d6d7cd4e9a971eb4ee69412c265"
  }
}

Items.body:
{"id": 1, "name": "Ворота", … "cred_secret": "***", … "worker": null}

→ 200 {"ModifyIndex": 4414}
```

И здесь условная запись по версии своего захвата: если его успела забрать другая консоль, ответ хранить будет она. Ответ с кодом `5xx` под ключом не хранится вовсе — «хранилище недоступно» не ответ на запрос; захват тогда отпускается, и повтор делает работу заново.

Итого на один `POST` оператора — **девять запросов к Nomad**. Пять записей: захват ключа, номер в захвате, счётчик, строка камеры, ответ. Четыре чтения: счётчик, листинг камер, две производные строки. К ним добавляется по чтению на каждую уже заведённую камеру, двенадцать чтений «кто звонит» перед всеми и не чаще раза в минуту — подчистка: обход префикса, чтение каждого ключа и удаление просроченных. И одна строка `unit.created` — с именами присланных полей, без значений — в журнал действий (`w2cplatform/journal.py`); это строка журнала событий на диске сервера, под ресурсом, а не запись в хранилище.

## 3.3. Ответ оператору

```
HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 1,
  "name": "Ворота",
  "source": "driverpack://acme/10.2.0.11",
  "enabled": true,
  "events_retention_days": null,
  "alarms_retention_days": null,
  "priority": 100,
  "labels": ["vlan:cctv"],
  "folders": [],
  "alarms": null,
  "ref": "north-gate",
  "cred_username": "operator",
  "cred_secret": "***",
  "live": "always",
  "kind": "video",
  "revision": 1,
  "worker": null
}
```

`null` у `events_retention_days`, `alarms_retention_days` и `alarms` — это «у камеры не задано», а не «ноль»: значения возьмут по цепочке наследования из вызова 6.

Два поля в этом ответе объясняют всю дальнейшую часть документа.

**`cred_secret: "***"`.** Пароль устройства замаскирован на выходе. Правило одно: поле, чьё имя кончается на `_secret`, наружу не уходит. Замаскирован и тот ответ, что консоль положила в ключ идемпотентности, — иначе пароль лежал бы вторым экземпляром там, куда никто не догадается заглянуть.

**`worker: null`, и это не ошибка.** Консоль размещение не выбирает и выбрать не может: её токену запрещено писать `vms/placement/*` и `vms/workers/*`. Попытка вернула бы `403` от Nomad. Камера создана, но пока нигде не работает — её подберёт контроллер на своём проходе.

Ровно это и делает ответ честным: «настройка записана» и «камера работает» — разные утверждения, и между ними до пяти секунд.

## 3.4. Что теперь в хранилище

| Ключ | ModifyIndex | Значение |
|---|---|---|
| `vms/idem/8f4b21e0-…` | 4414 | `state: done`, ответ 201 |

## 3.5. Камеры два и три

Оператор создаёт ещё две камеры, через секунду и через две. Запросы те же, меняются номера и индексы.

**Камера 2:**

```
POST /cameras
Idempotency-Key: c1a9f742-8e0b-4d55-a3f1-7b6e2c9d8054

{
  "name": "Парковка",
  "source": "driverpack://acme/10.2.0.12",
  "labels": "vlan:cctv",
  "ref": "parking"
}

→ GET /v1/var/domain/…  ×12                → 404     кто звонит: никто не спрашивает
  PUT /v1/var/vms/idem/c1a9f742-…?cas=0      → ModifyIndex 4415
  GET /v1/var/vms/next_id                    → {"n": "1"}, ModifyIndex 4405
  PUT /v1/var/vms/next_id?cas=4405           → {"n": "2"}, ModifyIndex 4418
  PUT /v1/var/vms/idem/c1a9f742-…?cas=4415   → id: "2", ModifyIndex 4419
  GET /v1/vars?prefix=vms/cameras/           → [vms/cameras/1]
  GET /v1/var/vms/cameras/1                  → source …10.2.0.11, ref north-gate: не совпадают
  PUT /v1/var/vms/cameras/2?cas=0            → ModifyIndex 4421
  GET /v1/var/vms/retention/2                → 404
  GET /v1/var/vms/alarms_retention/2         → 404
  PUT /v1/var/vms/idem/c1a9f742-…?cas=4419   → state: done, ModifyIndex 4423

→ 201 {"id": 2, …, "revision": 1, "worker": null}
```

Обратите внимание на запись счётчика: теперь он существует, поэтому запись идёт не с `cas=0`, а с `cas=4405` — «только если с момента моего чтения его никто не трогал». Подчистки ключей идемпотентности здесь нет: с прошлой не прошло и минуты.

**Камера 3:**

```
POST /cameras
Idempotency-Key: 2d7c6b18-3f4a-4e92-88c5-1a0d9e7f6b33

{
  "name": "Склад",
  "source": "driverpack://acme/10.2.0.13",
  "labels": "vlan:cctv",
  "ref": "storage"
}

→ 201 {"id": 3, …, "revision": 1, "worker": null}
```

Запросы те же, что у камеры 2, кроме одного места: проверка источника теперь читает две строки, `vms/cameras/1` и `vms/cameras/2`. Строка камеры 3 ложится с индексом 4433.

Итог: три камеры, все с одинаковой меткой `vlan:cctv`, ни одна нигде не размещена.

| Камера | Имя | Источник | Метки | revision | placement |
|---|---|---|---|---|---|
| 1 | Ворота | `driverpack://acme/10.2.0.11` | `vlan:cctv` | 1 | нет |
| 2 | Парковка | `driverpack://acme/10.2.0.12` | `vlan:cctv` | 1 | нет |
| 3 | Склад | `driverpack://acme/10.2.0.13` | `vlan:cctv` | 1 | нет |
