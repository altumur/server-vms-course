## Блокер

**Д-1 (блокер).** Шаблон `key` для `detjob` нельзя сделать однозначным в грамматике P/02.1 Н1.4.
- ADR:37–39: «`key` — шаблон P/02.1 Н1.4 по полям строки, называющий все `fixed`-поля адресата и поле его `about`. Шаблон однозначен — разные значения его полей дают разные id (правило проверки загрузчиком — Т-правка), поэтому id задаёт эти значения».
- Нормы:
  - P/02.1:176–180: `{имя}` — «только строка без преобразования»; `{имя:int}` — число, «усечение к нулю» (`7.9` → `7`); иной тип — 400;
  - `detjob.subsystem.yaml:27`, `:34`: `cam` и `rec` — `{type: string, fixed: true}`, `about` по `cam` (`:21`);
  - `rec.subsystem.yaml:63`: имя записи — «"7", "7-cloud" — the operator's name», то есть с `-`;
  - P/06.1 Н1.3 named: дефис в id допустим.
- Контрпример:
  - Шаблон задачи `auto` должен назвать `cam` и `rec` (а для разных задач одного события ещё `kind`), то есть не меньше двух строковых полей без преобразования.
  - `{cam}-{rec}` при `cam: "7"`, `rec: "1-x"` и `cam: "7-1"`, `rec: "x"` даёт один id `auto-7-1-x`. Любой разделитель допустим и в значении, так что неоднозначность есть у любого шаблона с двумя такими полями.
  - `{cam:int}` к строковому полю — «иной тип», 400. К `from` (float) `:int` склеивает `10.2` и `10.7`.
  - Значит, загрузчик, честно проверяющий «однозначен», отвергает `worker.creates` к `detjob` у `auto` и `rec`. Загрузчик, пропускающий шаблон, возвращает дефект ADR-0067: имя из физически удалённой строки получает другие `fixed`.
- Последствие: п. 1 для `detjob` невыполним либо небезопасен. Две реализации разойдутся по тому, что считать однозначным.
- Предложение — однозначность построением, а не проверкой:
  - подстановка в `key` кодирует в значении `%` как `%25` и `-` как `%2D` (оба знака допустимы в named id, P/06.1 Н1.3);
  - загрузчик требует только литерал `-` между соседними подстановками;
  - `{поле:int}` в `key` — только к полям `int`, без усечения.
  - Тогда разные значения дают разные id при любых строках, и правило загрузчика проверяемо.

## Существенная

**Д-2 (существенная).** `delete_after` удаляет не законченную, а неразмещённую: заказанный скан, ждущий GPU, исчезает.
- ADR:119–120: «Срок удаления законченной — существующий `delete_after` по часам контроллера; у строки с `made` — не раньше `made.keep`».
- ADR:73–75: физическое удаление по `delete_after` теперь допустимо у `detjob` для строк с `made` (поправка правил 46–47).
- Нормы:
  - P/04:654: «неразмещённые дольше delete_after… Всё ещё неразмещена и срок подтверждён → удалить строку»;
  - ADR-0067 п. 1: «единицу, которую не держит ни один воркер», отсчёт — с первого прохода без держателя (п. 4).
  - Причины «не держит» не различаются: снята `retire_when` (P/04:646) или не нашлось места.
- Контрпример:
  - `detjob` с `capacity: 2` (`detjob.subsystem.yaml:47`), все GPU-воркеры заняты. Событие → `auto` заводит `auto-…-lpr-…`. Строка неразмещена, потому что места нет.
  - Через `max(delete_after, keep − now)` контроллер удаляет её физически. Скан не начинался, итога нет, оператор ничего не видит.
  - С `delete_after` побольше («дни», как у свидетеля `jobs.forget_finished`, `:43`) законченные висят дни. Это приемлемо, но любой скан, ждущий дольше, всё равно пропадает.
- Последствие: у единицы с концом срок удаления не отличает «готово» от «в очереди». Потеря заказанной работы — молча.
- Предложение:
  - у единицы с `retire_when` срок `delete_after` считается от первого прохода, снявшего её по `retire_when` (действующее состояние в `in`), а не от любого прохода без держателя;
  - либо отдельный ключ `retire_when.delete_after`.
  - Записать в уроке 05 как замену `forget_finished`.

## Мелкие

1. **Отказ двери по префиксу сужает имена оператора.**
   - Запись `auto-backup` (`rec`, имя свободное, `rec.subsystem.yaml:63`), детектор с именем `auto-…` теперь — 400. Назвать отказ словами в уроках 02, 04 и в выдаче двери.
   - Строки с таким префиксом, созданные до объявления заказчика, остаются. ADR:58 «строка без своего `made` — занята» и Confirmation (ADR:175–176) «ручная строка под шаблоном — занята» достижимы только для них. Так и сказать.
2. **Поля `key` вне `fixed` правит оператор.**
   - `det` `kind` не `fixed` (`det.subsystem.yaml:19`), а id `auto-<cam>-<kind>` его называет.
   - Оператор правит `kind` у `auto-7-lpr` на `motion`. Следующее событие `lpr` даёт тот же id: строка своего `made`, продление (ADR:57–58) — продлён детектор `motion`, а `lpr` не заведён.
   - Предложение: поля `key` у строки с `made` неизменяемы дверью (как `fixed`), или библиотека сверяет их и при расхождении считает строку занятой.
3. **`not_after` и повтор по `id`.**
   - Повтор с тем же `id` после `ambiguous` отвечает ответом первой записи (P/01.1:256–258, :281).
   - Если лидер проверяет `not_after` до памяти повторов, то повтор после `not_after` получает `expired`, хотя первая применилась.
   - Назвать порядок: память `id` раньше `not_after`, `not_after` входит в отпечаток. На одной коробке без журнала (P/01.1:221) — та же проверка под блокировкой по часам процесса хранилища.
4. **Предпосылка часов.**
   - ADR:61–62 ссылается на P/08.2:109, но там — «стенные часы держателей домена».
   - `not_after`, `keep`, `gone` опираются на часы лидера хранилища, контроллера, двери, воркеров и писателя события. Это новая предпосылка кластера в P/01.1 «Время».
   - Граница: приём при часах лидера = `not_after` и удаление при часах удаляющего = `keep` совпадают ровно на допуске. Одну сторону сделать строгой.
5. **Ручные задачи `detjob` больше не забываются.** ADR:74–75: ручные строки адресата физически не удаляются. Свидетель удалял законченные по `jobs.forget_finished` (`detjob.subsystem.yaml:43`). Назвать отличие в уроке 05: удаляет оператор.
6. **Счёт нечитаемого состояния.** ADR:105–106: «счёт в отчёте прохода» — имя счёта не названо. `snapshot_rows_garbled` (P/04:99) считает строки вне шарда, а здесь единица в шарде. Назвать новый счёт.

Прежние отложенные мелкие (Г-7, Г-8, Г-9, С-4, С-5) — при Т-правке, не повторяю.
