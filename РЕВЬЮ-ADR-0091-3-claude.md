## Существенные

**Т-1 (существенная).** Выводимые чтения названы не те: обратная проверка идёт при создании и правке.
- ADR:39–41: «Чтения, нужные общей проверке строки (цели `ref` и `must_match` адресата, строки, ссылающиеся на удаляемую), выводятся из объявления тоже».
- Нормы:
  - P/06.1:200–202: «создание или правка единицы, которая сама — цель, проверяет живые единицы и строки таблиц каталога, чьё поле с ref на её семью и must_match называет её… ссылающаяся строка не читается — fault garbled»;
  - P/06.1:585–594: удаление ссылок не проверяет.
- Контрпример:
  - `detjob.rec` — `ref: rec/recordings, must_match: {cam: cam}` (`detjob.subsystem.yaml:34`).
  - Продление `rec/recordings/auto-7` воркером `auto` — правка цели, и общая проверка читает `detjob/jobs/*`.
  - По ADR выводится чтение строк, «ссылающихся на удаляемую», а заказчик ничего не удаляет. Чтения `detjob/jobs/*` нет — `409 garbled`, запись не продлевается.
- Предложение: «строки семей каталога, чьё поле с `ref` на таблицу адресата и `must_match` — при создании и правке». Чтения логики заказчика (`det/units/*` для детектора оператора, `rec/recordings/*` для «камеру никто не пишет») — `worker.reads` уроков 02, 04, 05, 07.

**Т-2 (существенная).** «Сначала состояние, затем строка» теряет состояние, когда удаление строки отменено.
- ADR:83–84: «при удалении единицы (`delete_after`, `ends`) — сначала снять с размещения, затем удалить состояние, затем строку; обрыв между шагами безопасен».
- ADR:64–65: «продление между чтением и удалением отменяет удаление».
- P/04:654: удаление по `delete_after` — «под своим turn заново прочитать единицу», запись с `cas`.
- Контрпример:
  - Задача `detjob` закончена, состояние `done` действует, `retire_when` её снял. Срок `delete_after` вышел.
  - Контроллер удаляет состояние (CAS + страж строки — проходит). В это время оператор правит строку задачи, и `cas` удаления строки проваливается: строка живёт.
  - Действующего `done` больше нет, `retire_when` её не держит. Контроллер размещает задачу снова, скан идёт с нуля (часы GPU), курсора нет.
  - То же у единицы с `ends` и состоянием, которую заказчик продлил в момент удаления.
- Последствие: обрыв безопасен, а отмена удаления, которую п. 2 называет нормальной, — нет.
- Предложение — одно из двух:
  - удалять строку первой. Состояние с её `born` после этого уже не действует, его снимет уборка: CAS + страж `""`;
  - удалять состояние только после подтверждённого удаления строки.

**Т-3 (существенная).** `mask` «держателем при старте» не закреплена за задачей и не имеет правила источника.
- ADR:43: «поля-blob при создании не пишутся (P/06.1) — их берёт держатель созданной единицы при старте».
- ADR:57: «`mask` — держателем при старте».
- Свидетель:
  - М10B/22:114: дайджест копируется в строку задачи при создании;
  - М10B/22:119: «Ретро-прогон с другими параметрами — не тот же ответ».
- Контрпример:
  - Скан `detjob/auto-7-lpr-…` на час. `j-1` стартовал с маской детектора оператора `det/units/7-lpr`, дайджест X.
  - Оператор перерисовал маску (Y). `j-1` упал, `j-2` берёт задачу и при старте читает Y. Половина интервала просканирована с одной маской, половина — с другой.
  - Тело X уборка тел `det` может уже снять: его больше не называет ни одна строка (P/06.1:615–618).
  - Ручная задача оператора без маски: из нормы держатель не знает, наследовать ли.
- Последствие: заказанная задача не детерминирована по своей строке — против «повтор безвреден детерминизмом» (ADR:51) и поведения свидетеля.
- Предложение:
  - заказчик пишет в строку несекретную ссылку на источник — строковое поле манифеста, например `mask_from: <sub>/<id>@<дайджест>`;
  - держатель берёт тело по этой ссылке;
  - наследование — только у строки с `made`;
  - нет тела — отказ задачи словами в пульсе, а не скан без маски.

## Мелкие

1. **Префиксы `detjob` и правила загрузчика.**
   - Префиксы `detjob` для `scan` (`auto`) и `scan_what_arrived` (`rec`) не названы (ADR:59–61 называет только `rec` и `det`).
   - Загрузчик должен отвергать два заказчика одной таблицы, чьи префиксы — префикс один другого.
   - Не определено, что такое «узкий образец» (ADR:38–39); пустой префикс, видимо, — отказ.
   - Ручная строка оператора с тем же префиксом попадает под право заказчика.
   - Право на удаление логике заказчика не нужно (ADR:38).
2. **Срок заказа.**
   - Источник `valid_for` не назван: раздел `requests` `det` с `valid_for: 60` (`det.subsystem.yaml:81`) для `detect` и `scan` уходит.
   - Время события `t` — по часам писателя события (P/03.6:29), а `until` сравнивает контроллер по своим (ADR:63–64).
   - Строку с `until` ≤ now заказчику лучше не заводить: контроллер сразу её удалит, а `born` сменится зря.
3. **Повтор того же события после удаления оператором.** `record` и `detect` создаются над надгробием, поэтому переигранное после переезда событие (в пределах `valid_for`) возвращает запись, которую оператор только что снял. У свидетеля метка этого не давала (М10B/25:519). Назвать отличием в уроке 07 или не возрождать по тому же id события.
4. **Перезапуск по `born` — под той же эпохой** (P/03.2:548–549, ADR:70). События двух жизней одного id ложатся в одно дерево `e<эпоха>`. Строка состояния должна нести `born` жизни, с которой стартовал процесс, а не текущей строки. Предложение: смена `born` — новая эпоха.
5. **Видимость — только у консоли.**
   - `detjob.subsystem.yaml:76` `snapshot: [name, cam, kind, state]`: после снятия поля `state` (ADR:78) — либо отказ загрузки, либо домен без итога.
   - Поле `ended` (`:41`) остаётся без писателя.

Прежние мелкие (Г-7, Г-8 `*_secret`, Г-9, С-4, С-5) разбор отложил до Т-правки — не повторяю.
