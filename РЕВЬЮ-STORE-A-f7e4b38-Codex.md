## 1. P2 — rights_command меняет аргументы другой команды оболочки

`runner/store_audit.py:19–57`: `words()` пропускает `;&|<>()`, а `rights_command()` ищет единственный `-rights` / `-rights=...` во всех получившихся словах. Принадлежность слова запускаемой команде хранилища не проверяется.

Контрпример профиля:

```sh
printf '%s\n' -rights '/prelude rights' > setup.log && exec STORE --implicit-rights '/actual rights'
```

У самой команды STORE нет поддержанного флага `-rights`, значит сценарий смены прав должен стать `not_executed`. Сейчас `scenario_reason()` возвращает `None`. Вариант `none` удаляет аргументы `printf`, вариант `file` подставляет новый путь в `printf`; argv STORE в обоих случаях **вообще не меняется**. Такой же результат у подготовительного аргумента `'-rights=/prelude rights'`.

Нативная проба исполнила обе формы и оба преобразования через настоящую оболочку: подготовительный вывод изменился, окончательный argv наблюдателя остался `['--implicit-rights', '/actual rights']`. Наблюдатель только записывает argv, реализации хранилища и модели прав в нём нет.

Последствие: вместо честного сценарного пропуска команда с неподдержанным источником прав считается поддержанной. Сц. 13 проверит прежние права и получит ложный отказ реализации либо ответ иной ветви; обещанная смена файла/снятие флага не произошло. Кроме того, меняются посторонние аргументы команды подготовки.

Источник: общий README «`@rights store <файл|none>`», уточнение Спецификации `af952a0`, строки 228–229: снимается argv-флаг команды хранилища и «больше ничего не меняет»; иной способ задания прав — сценарий `not_executed`. Текст копии уточнения сверен чтением с Git `af952a0`.

Нужно сначала доказать принадлежность флага argv запуска хранилища. Для неподдержанной/неоднозначной конструкции оболочки безопасно вернуть `NotExecuted` до запуска; не считать слово внутри другой команды или данных её флагом. Текущая проверка только числа совпадений этого не обеспечивает.

## 2. P2 — штатный not_executed после экспорта расходится с capability plan

`runner/c_execute.py:80–82` сравнивает весь `not_executed_scenarios` отчёта с планом, включая буквальные строки причин. Новые `l06`/`l11` пишут такие строки в JSON, но обязательный финальный проход `c_store.main → diagnostic_secrets.finalize → clean` превращает значение под ключом сценария в metadata тела. Это штатная рамка А; расширять её произвольными строками не требуется.

Контрпример: ровно семь опубликованных строк `13-rights-file`, профиль `unused --implicit-rights`, без поддержанного argv-флага. Реальный `c_store.main --driver store-rights` не запускает хранилище и выдаёт ожидаемый отказ stand: `green:false`, `total_steps:0`, `passed_steps:0`, все семь `ok:null/not_executed:true`. Но план ожидает:

```json
{"13-rights-file":"store command must name exactly one argv -rights flag"}
```

Экспортированный отчёт содержит вместо строки `{content_type:null,length:53,sha256:"9eda0d6333363e6b7ee22e64cf6f433ec20ed4e56eb0987e63ab38340d3a937c",body_omitted:true}`. `c_execute.coverage()` даёт ложное **`not-executed scenarios differ from the capability plan`** при нулевых ожидаемых и фактически исполненных шагах.

Это не превращает пропуск в GREEN: общий отказ stand сохраняется. Ошибка ломает обещанную сверку корректного паспорта — нормативный пропуск выглядит как расхождение плана и результата, хотя адреса, число и признаки пропуска точны. Авторский контроль передаёт raw-словарь сразу в coverage и не проходит реальный экспорт.

Нужно согласовать структуру плана с окончательным безопасным отчётом: например, стабильный закрытый код причины с проверенными адресами сценариев либо одинаковая нормализация на обеих сторонах. Не разрешать свободные строки реализации ради этого сравнения. Проверка должна проходить настоящий `c_store.main` и его finalize.
