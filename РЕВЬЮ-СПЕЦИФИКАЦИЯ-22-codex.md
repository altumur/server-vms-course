### R22-01 — Неверные JSON Pointer разрешаются по правилам индексации Python

**Серьёзность: существенная.** Места: S/scripts/check_spec.py:151–159,214–216; S/references/validation.md:20,32–36.

Разрешатель выполняет `int(part)` для индекса массива и заменяет `~1`/`~0`, не проверяя грамматику токена. Поэтому отрицательный индекс, ведущий ноль и недопустимая escape-последовательность могут разрешиться в существующий объект и получить итоговый `PASS`.

Контрпример: в OpenAPI временного комплекта заменить `components.schemas` на:

```yaml
components:
  schemas:
    List:
      prefixItems:
        - {type: string}
        - {type: integer}
    Example:
      $ref: '#/components/schemas/List/prefixItems/-1'
```

CLI возвращает **0 / PASS**, `openapi=1`, `local_refs=2`. Замена `-1` на `01` также даёт 0. Отдельный опыт: добавить корневой `x-target~2: {type: object}` и направить `Example.$ref` в `#/x-target~2` — снова 0, хотя `~2` не является допустимым экранированием. Контроли: допустимые индекс `1` и ссылка `#/x-target~02` проходят, отсутствующий индекс `2` даёт 1.

Последствие: контракт с неразрешимой по стандарту ссылкой объявлен проверенным; совместимый разрешатель отвергнет его, тогда как инструмент подставляет другую схему, например последний элемент массива. Это ошибка внутри заявленного поддержанным способа ссылок, а не просьба расширить набор диалектов.

Основание: ADR-0080, дополнение 2026-10-15 (3), строки 263–266; собственное обещание проверки корневых JSON Pointer в validation.md:20. RFC 6901 допускает для массива ноль либо положительные десятичные цифры без ведущего нуля, а в escape-последовательности после `~` — только `0` или `1`; нарушение останавливает разрешение. [RFC 6901, §§3–4, 7](https://www.rfc-editor.org/rfc/rfc6901).

Рекомендация: проверять грамматику JSON Pointer до обращения к объекту/массиву и добавить отрицательные CLI-пробы на неверные индексы и экранирование.

### R22-02 — Исключение HTML-ссылок и изображений разрешает зелёный результат для непроверенного пути

**Серьёзность: существенная.** Места: S/references/validation.md:19; S/scripts/check_spec.py:138–143,185–193,383; `decisions/0080-лекции-как-спецификации.md`:263–266.

Новая граница в validation.md относит HTML и изображения к ручной проверке. Однако скрипт не обозначает обнаруженную неподдержанную локальную ссылку: он извлекает только `link_open`, игнорирует HTML и `image` и возвращает общий структурный `PASS`.

Контрпример — заменить текст лекции временного комплекта на:

```html
# Example
<a href="spec/missing.norms.md">Norms</a>
```

Файла нет, но CLI возвращает **0 / PASS**, без диагностики неподдержанной ссылки. Отдельная замена на `![Diagram](spec/missing.svg)` даёт тот же результат. Контроль с `[Norms](spec/missing.norms.md)` возвращает 1 и `missing link target`.

Последствие: отсутствующая цель реально используемой локальной ссылки исчезает из результата проверки при смене формы записи. Предупреждение в руководстве не отражается в выводе конкретного прогона. Это не смысловая оценка текста или требование проверять произвольные веб-страницы: остаётся непроверенным существование локального файла.

Основание: ADR-0080, дополнение 2026-10-15 (3), прямо требует, чтобы неподдержанная ссылка или формат не давали зелёного результата. Ограничение реализации допустимо, но молчаливый успешный пропуск ему не соответствует. Исходные reference-ссылки R21-03 исправлены; эта находка относится к явно добавленному исключению других форм локальных ссылок.

Рекомендация: проверять локальные цели этих форм либо явно завершать проверку как неполную/неподдержанную вместо `PASS`, закрепив обе формы отрицательными CLI-пробами.
