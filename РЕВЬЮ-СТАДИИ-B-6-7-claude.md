## Правки поведения №13, №14 урока 6

### Н-1. Существенная — №13: строка `/status` объявлена единицей «элемент», но для части читателей роняет весь пульс; остальные читатели не названы
- Место: `Platform/03-worker/data/heartbeats.outcomes.tsv:7` (та же таблица — `03.4-worker.norms.md:179`).
- Цитата: «элемент нечитаем: консоль `GET /{rows}` его пропускает, остальные элементы пульса — в rows … консоль
  `/servers` и `/metrics`, контроллер, дренаж — как пульс целиком нечитаемый (строка ""; нынешнее поведение) … | 0 |
  элемент».
- Что говорит DIALECT (`Platform/common/DIALECT.md:170–171`): «`unit` — единица нечитаемости …: отказ ниже неё не
  делает нечитаемым содержащий узел». Строка этому противоречит.
- Не названы читатели: door.pass (`06.5:146–150`, «исходы семьи пульса P/03.4»), `/where`, `/schema` `processes.live`,
  «слышен» у вывода сервера в 6.6.
- Контрпример: у пульса `w-1` два элемента, у второго `observed_revision: 1.5`.
  - door.pass по DIALECT считает пульс читаемым, и воркер подходит.
  - door.pass по аналогии с `/servers` считает пульс нечитаемым, и выходит 503.
- Ещё одна дыра — приоритеты: при `worker` ≠ ключу вместе с плохим элементом действуют пути `/status` (приоритет 0) и
  `""` (1). По правилу «наименьший» побеждает пропуск элемента, и пульс с чужим `worker` попадает в `rows`.
- Нарушено: DIALECT §9; разбор A 6–7 №13 («пропуск по элементу»).

### Н-2. Существенная — №13: три перечня «элемент не по форме» и два прочтения «целого»

## Токен двери: договор и векторы

### D-1. Блокер (вопрос «Архитектору») — форма числа `expires` в claims не задана
- Место: `Platform/common/contracts/door-token.md:27` — «expires — стенные секунды выдачи + 120». Там же
  `06.5-console.norms.md:34–35`.
- Почему форму никто не задаёт:
  - `Platform/01-store/spec/01.1-store.norms.md:39` выводит поле из канона времени: «Правило не касается чисел во входах
    и ответах дверей (… `expires` двери …): их форму задаёт своя норма». Своя норма (договор) формы не даёт.
  - OpenAPI `06-console.api.openapi.yaml:4196`: `expires: type: number`.
  - Строки `verify.tsv` проверяют `now < expires` только на целых. `issue.tsv:11` (`number_form`) подаёт `1.79245452E9`,
    но тоже целое по значению.
- Контрпример: claims `{"expires":1792454520.25,"holder":"w1-7f3c2a","routes":["read","play"],"unit":"testsub/u1","user":"admin"}`
  в JCS, подпись `c1`, `now=1792454400`, путь `/read/x`.
  - Проверяющий, который читает число JSON, отвечает `ok`.
  - Проверяющий, который читает `expires` в int64 (типизированная структура), отвечает `forbidden`.
  - Выпускающий на `time.time() + 120` пишет именно такие байты. Это законный JCS, и запрет договора его не задевает.
- Нарушено: ADR-0083 доп. (5) (договор — единственный источник для раздельно сгенерированных консоли и воркера); шкала
  блокера: две реализации по канону расходятся на допустимом входе.
- Последствие: при стадии C консоль одной сборки и держатель другой закрывают все двери держателей.
- Что нужно: слово договора («целые секунды» или «число; сравнение `now < expires` как double») и строки векторов:
  дробный `expires` в выпуске и проверке, граница `now = expires` для дробного.

### D-2. Существенная (вопрос «Архитектору») — читатель JSON claims и строки `door/keys` не задан, векторы расходящихся читателей не ловят
- Место:
  - `door-token.md:33–35` — «проверяющий канон JCS не проверяет»;
  - `door-token.md:43`, `:48` — «claims ровно {user, unit, holder, routes, expires}», «Состав claims закрыт»;
  - `verify.tsv:51` (`claims_not_jcs`) — подписанные неканонические claims дают `ok`, то есть это законный вход проверки.
- Контрпримеры (каждые claims подписаны `c1`). Читатель A — обычный JSON, имена с учётом регистра. Читатель B —
  типизированная структура:

  | Вход | A | B |
  |---|---|---|
  | `"User":"admin"` вместо `user` | `forbidden` | `ok` (Go сопоставляет имена без учёта регистра) |
  | байт `0xFF` в `user` | `forbidden` | `ok` (замена на U+FFFD) |
  | `"user":null` | `ok` | `forbidden` |
  | `"expires":1.79245452E9` | `ok` | `forbidden` |

  Дубль `"unit":"testsub/u2","unit":"testsub/u1"` даёт `ok` у обоих, но читатель по I-JSON (RFC 7493) скажет
  `forbidden`. Пять ли это полей «ровно», текст не говорит.
- `door/keys` с одной плохой записью: `{"c1":"865e…a0db","old":"XYZ"}` и токен `ok_basic`.
  - По канону строка нечитаема целиком (`door-keys.outcomes.tsv`, единица «строка»), значит `forbidden`.
  - Читатель по записям даёт `ok`.
  - Строки `keys_upper_hex`, `keys_short_hex`, `keys_not_object` портят запись самого `kid` или строку целиком, так что
    терпимый по записям читатель проходит все 46 строк.
- Последствие: две реализации, прошедшие векторы, расходятся на входах, которые договор сам допускает. Подделки нет, но
  стык разных сборок ломается.
- Что нужно:
  - назвать читателя: строгий UTF-8, без дублей, имена байт в байт, типы полей;
  - добавить строки: регистр имени, дубль, `null`, плохая чужая запись в `door/keys`.

### D-3. Существенная — «путь запроса» не определён относительно query; место токена у держателя не нормировано
- Место: `door-token.md:44` — «первый сегмент пути запроса к двери держателя — элемент routes байт в байт, сырым».
- Контрпример: токен `ok_basic`, путь `/play?t=<токен>`.
  - Реализация, которая берёт сегмент из сырой цели запроса (`BaseHTTPRequestHandler.path` вместе с query), получает
    `play?t=…` и отвечает `forbidden`.
  - Реализация, которая берёт сегмент из пути URL, получает `play` и отвечает `ok`.
- Почему это не редкость: токен в query — штатный путь (`М10B_ServerVMS/24-an-interval-in-the-browser.md:303`: «токен
  двери едет параметром `?t=`», для fetch — Bearer). Договор платформы места токена (заголовок или `?t=`) не называет.
  Строк с query в `verify.tsv` нет.
- Нарушено: однозначность договора для двух реализаций (ADR-0083 доп. (5)).

### D-4. Существенная — `door/keys` может остаться без своего `kid` навсегда
- Место:
  - `Platform/common/data/catalog.tsv` строка `door/keys` — «cas=console(добавить свой kid)»;
  - `door-token.md:42` — «консоль добавляет свой kid при создании door/signer»;
  - `door-keys.outcomes.tsv:4` — «консоль — свой kid не добавляет».
- Контрпример: консоль создала `door/signer` и упала до `cas` в `door/keys`. После перезапуска подписант уже есть,
  создания нет, и `kid` в ключи не попадает. Держатель отвечает 403 `forbidden` на каждый токен.
- Нарушено: P/06.5 Н3 не говорит, когда выполняется «добавить свой kid» (только при создании или при каждом старте или
  выдаче). Одна реализация чинит ключи, другая — никогда.
- Последствие: двери держателей закрыты до ручной правки.

## Общие договоры и самодостаточность глав 6.x

### K-1. Существенная (вопрос «Архитектору») — `kept` при `ttl: 0` или без `ttl`
- Место: `Platform/common/contracts/request-mark.md:82` — «kept: max(60, ttl) от момента, когда держатель увидел, что

- Контрпример: спека с `ttl: 0`, строка просьбы снята.

- Последствие: метки копятся без конца, либо гарантия повтора у двух реализаций разная. Глава 3.6 уже перенесена и сама

### C-1. Существенная (вопрос «Архитектору») — каталог даёт консоли чтение `domain/grants/<кластер>`, вывод прав его не даёт

### C-2. Существенная — консоль читает `door/signer`, только если спека сама объявила это чтение

### C-4. Существенная (вопрос «Архитектору») — не сказано, что хранит `n` в `next_id`

## Правки по разбору стадии B 3–5

### B-1. Существенная (вопрос «Архитектору») — правило «конец» сокращения осталось штучным
- Место: `Platform/04-controller/spec/04-controller.norms.md:877`, `:885–886`, `:889–890`.
- Цитаты:
  - :877 — «жертва: воркер роли с наибольшим номером n ≥ 2»;
  - :885–886 — «назначение жертвы пусто → want := want − 1 … скрипт сервера останавливает процесс с наибольшим n (P/02.4
    Н1.5) — это и есть жертва»;
  - :889–890 — дренаж: «want − 1 при пустом назначении жертвы».
- Контрпример (а): want 2, живы {1, 2, 3}. Номер 3 выше want (Р28): ещё не остановлен, единиц не получает. Нехватки нет
  дольше SHRINK_AFTER, жертва — 3, её назначение пусто, и «конец» сразу даёт want := 1. Скрипт по Р26 останавливает и 3,
  и 2, а у 2 есть единицы: гистерезис считался без него.
- Контрпример (б): идёт сокращение, want 4, жертва 4 с `retiring`. Номер 3 упал и не поднялся за WANT_GRACE. Р27 даёт
  want 3, «конец» потом — want 2: лишний шаг вниз. Что снятие по сроку делает с `retiring`, не сказано.
- Нарушено: ADR-0084 доп. (4) Р26, Р28. Тождество «наибольший n — это и есть жертва» держалось только при счёте штуками.
  Вектор `shrink-victim` want не принимает, поэтому этого не ловит.

### B-2. Существенная — Р27 противоречат строка Н4 P/04 и норма P/02.4
- `04-controller.norms.md:998`: «grows: сервер не поднял заказ за WANT_GRACE | — | want назад до живых». Н3 :859 даёт
  «want(s) := 1 + |живые номера ∩ {2…want(s)}|».
- Контрпример: живы {1, 4}, want 3. «До живых» даёт 2, а Н3 — 1 + |{4} ∩ {2, 3}| = 1.
- `Platform/02-installer/spec/02.4-installer.norms.md:201–202`: «контроллер уменьшает want только после пустого
  назначения сокращаемого воркера». Р27 уменьшает want при непустом назначении. Лекция `04-controller.md:73–74` говорит
  то же, что P/02.4.
- Нарушено: ADR-0084 доп. (4) Р27.
- Последствие: реализация по строке Н4 ставит want 2 вместо 1.

### B-3. Существенная — семья `presence-lock` оформлена по отменённому правилу
