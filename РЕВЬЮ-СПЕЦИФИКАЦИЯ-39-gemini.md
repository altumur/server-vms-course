### G39-01 — блокер. Урок 11 добавляет виды `busy` и `refused` в закрытую дверь урока 1

Противоречат: `11-the-platform-on-a-box-and-a-cluster.norms.md:253` (409 `refused` на `/v1/write`), `:256` (для `write` 503 «либо `{kind: busy, error}` с `Retry-After: 1`»), Н4 `:346` («соединений больше предела — 503 `busy`»); `11-…api.openapi.yaml:237-263` (409 `oneOf M1_ConflictFault | Refused`, 503 `anyOf …| Busy`).

- **Основание:** М10/1 Н2 `:116`; change-map строка «Причина отказа и наблюдаемый результат» (общий набор не заменяет сверку по операции). ADR-разрешения `busy` для двери хранилища нет (`grep busy decisions/*.md`).
- **Последствия:** клиент, построенный по канону М10/1, получает неопределённый вид отказа на основной двери; строгий разбор ответа роняет цикл, повтор не определён.

### G39-03 — существенная. Допустимый id единицы блокирует всё размещение подсистемы через ключ `placement/<id>`
- **Уроки:** М10/3, М10/4 (М10/10 Н1.4).
- **Места:** `03-…norms.md:139` (до создания проверяется только файловый профиль бакета), `:285-306` (полные ключи — для своих операций), приёмка `03/README.md:14` (id из 1007 ASCII при `testsub/counters/` — 1024 байта — проходит); `10-…norms.md:75` (предел имени — только `<sub>/<rows>/<id>`). `04-…norms.md:302` предпроверяет до шага 2 только вес intent/назначения; шаг 4 `:294-295` пишет `<sub>/placement/<id>`; `:344-346` — badkey = ошибка шага, «если ошибка не позволяет довести active intent, новое решение не принимается»; `:280` (шаг 0: сначала довести active intent, новых решений нет), Н4 `:515-516`.
- **Контрпример:** testsub, хранилище с пределом 1024. `POST /counters {"name":"<1007×a>"}` → 201 (ключ `testsub/counters/…` = 17+1007 = 1024). Контроллер при свободной ёмкости пишет active intent (вес в норме), затем `testsub/placement/<id>` = 18+1007 = **1025** байт → определённый `400 badkey`. Intent недоводим; каждый следующий проход (и новый держатель turn, `:304`) сначала доводит его и снова получает badkey → ни одна другая единица testsub больше не размещается. То же при `DELETE` такой единицы (снятие строкой размещения `deleted`).
- **Основание:** checklist `review-checklist.md:33-34` («для составного ключа измеряется результат с префиксами… отказ потребителя прослежен до исхода вызывающего»); change-map «Операция над допустимым значением». ADR-0080 доп. 13 (`0080-…:760-762, 777-779`) решил «не принимает новое решение поверх незавершимого intent» и отказался от гарантий сквозного размещения предельных имён, но не объявил, что одна такая единица останавливает размещение **всех** единиц подсистемы.
- **Последствия:** потеря живости контроллера целой подсистемы от одного допустимого POST.
- **Рекомендация (в рамках существующего шаблона, не новая архитектура):** либо предпроверять представимость `<sub>/placement/<id>` всех members до шага 2 так же, как вес (отказ шага без intent), либо явно объявить это следствие в ADR/Н4 и ограничить id при создании самым длинным производным ключом.
- **Происхождение:** была до исправлений 38 (тексты `04:344`, `04:302`, `03/README:14` есть на `294ca6c5`); по ADR-0080 доп. 13 возникла при исправлении R29 (2026-10-15), что сам ADR называет как известное «Bad» без указания общей блокировки.
