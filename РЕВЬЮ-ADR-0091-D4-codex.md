## Находки

### R91-D4-01 — блокер: строка команды не имеет единственного преобразования в argv

**Места:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:313–318`; отсылка — `Platform/02-installer/spec/02.1-installer.form.yaml:170` и `02.4-installer.norms.md:84–87` (исполнение `parts.exec` раннером).

**Цитата:** «командная строка программы воркера подсистемы, та же форма, что у `parts.<часть>.exec` (абсолютный путь и аргументы, без оболочки)». Но исходник формы части определяет только `exec: {type: string, description: "команда службы части"}`. Отдельных правил разбиения, кавычек и экранирования в проверенных зависимостях нет.

**Допустимый вход проекта:**

```yaml
worker:
  exec: '/opt/a/worker --label "front desk"'
```

Абсолютный путь назван, аргументы разрешены; внутренние кавычки не запрещены. YAML-кавычки снаружи снимает разбор YAML, внутренние остаются в значении. Один исполнитель снимает внутренние кавычки и получает `[/opt/a/worker, --label, "front desk"]`, где последний элемент — одна строка без кавычек. Другой разбивает только по пробелам, считая кавычки обычными знаками: `[/opt/a/worker, --label, '"front', 'desk"']`. Оба могут затем вызвать программу напрямую, без оболочки, и добавить слот ровно последним аргументом. Запрет оболочки сам по себе не выбирает одну из этих грамматик.

**Наблюдаемый результат:** программа с аргументом `--label <одно значение>` получает разную метку или отказывает из-за лишнего аргумента. В кластере разница сохраняется после добавления `%i`; на домене остаётся без него. Значение `W2C_ROLE` этой разницы не устраняет. Собственная проба получила именно два разных массива, не вызывая продукт.

**Первичное основание:** обещание одного `worker.exec` для обеих ролей в пп. 1–3 дополнения, P/02.4 Н1.1 (имя слота передаётся аргументом) и правило раздела «Поля, значения, отказы» чеклиста об определённости операций на всей разрешённой области Н1. Форма существующего `parts.exec` не предоставляет недостающего правила. Отдельный контракт профиля тоже не решает вопрос: `cammeta-acceptance/README.md:435` явно исполняет **свои** команды через `/bin/sh`, тогда как новый ключ манифеста — без оболочки.

**Почему блокер:** разные трактовки разрешённой строки дают разный вход программе; канон не выбирает одну. Это дефект проектируемого контракта, а не утверждение, что две реальные генерации уже разошлись.

**Рекомендация / вопрос «Архитектору»:** определить один разбор для обоих `exec`, либо явно сузить строку до однозначного подмножества. Назвать поведение пробелов, кавычек, обратной косой, пустого аргумента и отказа неполной записи; отделить YAML-разбор от разбора команды. При выпуске юнита сохранять полученные аргументы, не вводя повторно подстановки из содержимого ключа. Проверка должна наблюдать фактические argv и роль в двух режимах, а не только текст ExecStart. Если предпочтителен список аргументов вместо строки — это отдельное решение о форме, не требование этого отчёта.

**Происхождение:** `parts.exec` уже не имел этой грамматики в выгрузке `555ff2b`. Новое доп. (4) коммита `aeb8201c2d66650c436be808747b49bcefe700e8` переносит пробел на `worker.exec`; не утверждается, что оно впервые внесло корень в `parts.exec`.

### R91-D4-02 — существенная: не задано применение изменённого worker.exec к уже установленному юниту

**Места:** `decisions/0091-механизмы-платформы-по-запросам-vms.md:315–320`; зависимые проходы — `Platform/02-installer/spec/02.3-installer.norms.md:124–157`, `02.4-installer.norms.md:346–350`.

**Цитаты:** «юнит … исполняет `worker.exec`»; приёмка — «строка `ExecStart` … из `worker.exec`». При этом P/02.3 Н3 на смену метки предписывает «остановиться с кодом 0; супервизор запускает заново» (`:156–157`). Генерация юнитов находится в другом проходе — повторной установке P/02.4 Н1.7 (`:346–350`).

**Контрпример:** оператор установил допустимую подсистему `a` с `/opt/a/worker-v1`, юнит получил эту программу и аргумент слота. Затем оба исполняемых файла уже существуют, оператор успешно выполняет `manifest put` с единственной правкой `worker.exec=/opt/a/worker-v2`. Ни неизменяемость ключа, ни запрет такой правки не объявлены. P/02.3 публикует новую строку/вид/метку; работающий v1 замечает смену и выходит с кодом 0. Супервизор снова исполняет v1 из старого юнита. Смена манифеста не содержит записи юнитов или перечитывания их команды супервизором.

Обе программы могут корректно реализовывать роль подсистемы, различаясь, например, сообщением сборки. Старый процесс способен загрузить новую строку и продолжить работу — вместо запуска явно выбранной v2. Никакое правило дополнения не называет такое состояние отложенным применением или отказом. У доменного воркера дополнительный раннер может перечитать ключ, что ещё и оставляет разные способы применения одного значения в двух режимах.

**Нарушение и последствие:** новому требованию исполнять программу манифеста не соответствует существующая процедура его изменения. В отличие от проверки холодного ExecStart, здесь требуется правило перехода: успешный `manifest put` и рестарт сами по себе не меняют статическую команду. Возникает незаданный исход между принятой ревизией и программой процесса.

**Рекомендация / вопрос «Архитектору»:** выбрать и описать применение ключа в обеих ролях. Возможны выбор программы из актуального принятого манифеста при каждом запуске либо явный порядок изменения установочного ключа с обновлением юнитов. Во втором случае назвать судьбу отдельного `manifest put`, обнаружившего такую смену: отказ или явно объявленное отложенное применение с условием завершения. Для проверки — смена v1 → v2 с наблюдением реально запущенной программы после предписанного перехода. Конкретный внутренний API не требуется.

**Серьёзность:** существенная — пропущена ветвь применения нового ключа; это не доказательство отказа конкретного установщика. Контрпример воспроизведён на модели буквального статического юнита и прохода публикации/рестарта.

**Происхождение:** для самого нового `worker.exec` вопрос возникает в доп. (4), коммит `aeb8201c2d66650c436be808747b49bcefe700e8`. Первая дата аналогичного пробела у иных установочных ключей не устанавливалась, отдельное ревью их жизненного цикла не выполнялось.
