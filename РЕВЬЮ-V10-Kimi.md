## Находки

### С1. `content` сообщения модели: контракт требует, нормы разрешают отсутствие — существенная

Место: `VMS/10-assist/spec/10-assist.api.openapi.yaml:161` (`required: [role, content]`), :165
(`content: {type: [string, "null"]}`), :225 (ответ `done` — `message: {$ref: ModelMessage}`);
`VMS/10-assist/spec/10.1-assist.norms.md:105`; `VMS/10-assist/spec/10.2-assist.norms.md:52-53`, :92.

Цитаты:
- контракт: `ModelMessage … required: [role, content] … additionalProperties: false`;
- протокол процесса модели (10.1 Н1.3): «message — `{role: assistant, content?, tool_calls?, reasoning_content?}`»;
- форма запроса (10.2 Н1.2): «`{role: assistant, content?: строка | null, …}` — сообщение модели из ответа (Н1.3)
  возвращается в историю как есть»;
- ответ двери (10.2 Н1.3): «message: при done — сообщение модели: `{role: assistant, content (строка | null),
  tool_calls?, reasoning_content?}`; иные поля ответа сервера модели держатель не отдаёт» — без «?» у `content`.

Контрпример: сервер модели отвечает допустимым по 10.1 Н1.3 телом
`{"choices":[{"message":{"role":"assistant","tool_calls":[{"id":"c1","type":"function","function":{"name":"get_schema","arguments":"{}"}}]},"finish_reason":"tool_calls"}],"usage":{"prompt_tokens":10,"completion_tokens":2}}`
— ключа `content` нет. Реализация А отдаёт сообщение в `200 done` как принято (без `content`) — ответ невалиден по
контракту (`required`, `additionalProperties: false`), и общая сверка ответа с контрактом его отвергает.
Реализация Б подставляет `content: null` — валидно. Байты ответа двери на допустимом входе расходятся.

Основание: чеклист «Статическая грамматика выражена схемой: тип, обязательность…» и «Необязательное поле не
игнорируется без проверки». Старшинство разрешает исход однозначно: Н2 главы 2 объявляет дверь — «OpenAPI урока»,
и 10.2 Н1.3 пишет `content` без «?»; но реализация по протоколу 10.1 Н1.3 и форме 10.2 Н1.2 («как есть»,
`content?`) ошибётся. Разбор RV10N-06/Н-2 кругов 1–2 это место правил («принимает как есть»), обязательность в
контракте осталась невыровненной. Приёмка ветку не покрывает: заглушка модели всегда шлёт `content` строкой
(`vectors/model-stub/02-step.tsv:3,6`, `04-owner.tsv:3`); `content: null` встречается только в истории запроса
(`acceptance/2/scenarios.tsv:18`, README `02-step`).

Рекомендация (минимальная): в 10.2 Н1.3 записать «`content` — строка; отсутствующий у ответа модели `content`
отдаётся как `null`» (одна фраза, контракт уже это требует). Альтернатива — снять `content` из `required` в
контракте и допустить отсутствие; тогда фраза «возвращается в историю как есть» остаётся дословно верной.

Происхождение: новая находка этого ревью.

### С2. Совмещённые отказы `GET` шага: разбор query против проверок экземпляра и владельца — существенная

Место: `VMS/10-assist/spec/10.2-assist.norms.md:78-85` (Н1.3), :164 (Н1.6), :183 (Н3).

Цитаты:
- Н1.3: «`wait` — целое 0…20, умолчание 0; иное (повтор, пустое, не целое, вне 0…20) — 400 `bad step` (Н1.6
  «Разбор входа»)» и далее нумерованный список: «1. токен → иначе 403; 2. экземпляр в `step` — не свой — 410…;
  3. шага нет или его владелец — не `user` токена — 404…; 4. шаг не завершён и `wait` > 0 — ответ ждёт…» — шага
  разбора query в списке нет;
- Н1.6: «Порядок: путь → метод → токен → query и тело»;
- Н3: «спросить: токен → свой экземпляр (по последней точке)? → свой владелец? → ждать ≤ wait → состояние» —
  разбора query тоже нет.

Контрпример: `GET /chat/m1/steps/<чужой-экземпляр>.<32 hex>?wait=x` с валидным токеном. Реализация по Н1.6
(разбор query — сразу после токена, до проверок ресурса) отвечает 400 `bad step`; реализация по нумерованному
списку Н1.3 (токен → экземпляр → владелец, `wait` понадобится лишь на шаге 4) отвечает 410 `gone`; при своём
экземпляре и чужом/отсутствующем шаге — 400 против 404 `no such step`.

Основание: чеклист «Совмещённые отказы идут в одном порядке у владельца двери и у использующих её уроков» и
«Порядок отказов: у каждого перечня "по порядку" есть шаги с двумя ошибками сразу — для каждой соседней пары».
Старшинство разрешает: Н1.3 сама делегирует разбор `wait` в Н1.6 (:79), где порядок назван, — верный ответ 400;
но реализация по списку Н1.3 и проходу Н3 ошибётся. Приёмочный класс «две ошибки по порядку» (fa83e4c24) эту пару
не покрывает: 410 проверяется одиночным шагом (`acceptance/2/scenarios.tsv:23`, 02-step шаг 16), битый `wait` в
сценариях не встречается вовсе (grep по `wait=` — только валидные `wait=20`).

Рекомендация (минимальная): в список Н1.3 между пп. 1 и 2 вставить шаг «`wait` разобран (Н1.6) — иначе 400» (и ту
же стрелку в проход Н3 «спросить»), либо в Н1.6 явно сказать «разбор query и тела завершается до проверок Н1.2
пп. 3–5 и Н1.3 пп. 2–4». Плюс шаг приёмки с двумя ошибками (битый `wait` × чужой экземпляр → 400).

Происхождение: новая находка этого ревью.

### С3. Отбой шага владельцем: ни ключа счётчика, ни `state`/`reason` для журнала — существенная

Место: `VMS/10-assist/spec/10.2-assist.norms.md:109` (таблица исходов), :137-139 (Н1.5), :155-157 (Н1.6, журнал);
`VMS/10-assist/spec/10.1-assist.norms.md:143` (Н1.4, пульс), :149 (ряды).

Цитаты:
- таблица исходов Н1.3: «| отбой владельцем (Н1.5) | — | шаг забыт, 404 |» — `state` и `reason` не названы;
- Н1.5: «иначе — **200** `{step, state: "cancelled"}`: шаг в очереди снят, в работе — запрос к модели оборван…,
  шаг забыт»;
- журнал Н1.6: «одна строка на завершённый **или забытый** шаг: `assist.step` — `of`…, `step`, `user`, `state`,
  `reason`, `seconds`, `prompt_tokens`, `completion_tokens`»;
- пульс 10.1 Н1.4: «`steps` — `{done, failed, cancelled, abandoned}`, накопительно с запуска воркера (глава 2
  Н1.3)»; ряды: «`assist_steps_total{outcome}`».

Контрпример: владелец отбивает свой шаг в работе (`DELETE` → 200 `cancelled`, шаг забыт). Реализация А пишет
`steps.cancelled += 1` и строку журнала с `state: "cancelled"`, придуманным `reason` (или пустым); реализация Б
не трогает счётчики и пишет строку без `seconds`/токенов или не пишет вовсе. Пульс (`assist/heartbeats/<воркер>`)
и байты журнала расходятся на допустимом входе. Попутно не названо, как выбирается ключ при `cancelled`: ключи
`cancelled`/`abandoned` — по `state` (тогда куда `abandoned`?) или по `reason` (тогда `disabled` → `cancelled`,
`abandoned` → `abandoned`); обе выкладки совместимы с текстом.

Основание: чеклист «Отсутствие, неверное значение и состояние "неизвестно" имеют разные исходы» и «У каждого
предела/поля названы единицы и состав измеряемого»; пульс и журнал — наблюдаемое поведение (Н1.4 главы 1, договор
журнала событий). Приёмка покрывает только `abandoned`: `acceptance/2/scenarios.tsv:38`
(`{"steps": {"abandoned": 1}}`) и :39 (`state: cancelled, reason: abandoned`); счётчики `done`/`failed`/`cancelled`
и строка журнала отбитого шага не проверяются нигде.

Рекомендация (минимальная): в таблице исходов Н1.3 у строки «отбой владельцем» назвать `state`/`reason` для
журнала (например `cancelled`/`cancelled`), а в 10.1 Н1.4 одной фразой поставить ключи счётчиков в соответствие
исходам: «`done`/`failed` — по `state`; `cancelled` — отбой владельцем и `disabled`; `abandoned` — `abandoned`»

### С5. Порядки сортировки инструментов главы 4 без определённого сравнения — существенная

Место: `VMS/10-assist/spec/10.4-assist.norms.md:173` (`find_units`), :197 (`field_values`), :72 (`ROW_LIMIT`);
`VMS/01-cam/cam.subsystem.yaml:48`.

Цитаты:
- «**Единицы** — подходящие строки по id; в `units` — первые `ROW_LIMIT`» (`ROW_LIMIT` = 50);
- «`values` — `[{value, units}]` … по убыванию `units`, при равенстве — по возрастанию значения как JSON»;
- `cam.subsystem.yaml:48`: «`id: numeric`».

Контрпримеры:
1. `find_units` по `cam` с id 1…12: «по id» байтами UTF-8 (порядок `rows` двери P/06.1 Н2) даёт 1, 10, 11, 12, 2…;
   численное сравнение — 1, 2, …, 12. При числе подходящих строк сверх `ROW_LIMIT` = 50 в `units` попадают разные
   множества — модель строит план по разным единицам. Норма не говорит ни «в порядке ответа двери», ни способа
   сравнения id.
2. `field_values` по bool-полю с ничьей (`true` у 3 строк, `false` у 3): «по возрастанию значения как JSON» не
   определяет порядок `true`/`false` (равно как ничьей числа со строкой, если поле смешанного наполнения через
   `about.<поле>`). Байты результата инструмента расходятся между реализациями.

Основание: чеклист «Каждая операция над значением (сравнение, сортировка…) определена на всей разрешённой области
Н1». Смягчение: панель — единственная канон-реализация ядра, векторы байт-точны и сняты с неё; приёмка порядки не
пинит — в векторах `plan-check` единственная единица `cam/4`, прочие id — слова и один одноразрядный суффикс
(`Gate-1/2`, `Store-1/2`…), ничьи `field_values` — только однотипные строки (`east`/`floor3`/`west` по 2).
Расхождение проявится у перевоплощения ядра или при росте стендовых данных.

Рекомендация (минимальная): у `find_units` записать «в порядке ответа двери единиц (P/06.1 Н2)» или назвать
сравнение id; у `field_values` определить сравнение «как JSON» на всей области значений полей (хотя бы: сначала
тип по фиксированному перечню, внутри типа — числа по значению, строки по байтам UTF-8, `false` < `true`).

Происхождение: новая находка этого ревью.

### М3. `max_tokens` в контракте без верхней границы и без описания — мелкая

Место: `VMS/10-assist/spec/10-assist.api.openapi.yaml:199`; `VMS/10-assist/spec/10.2-assist.norms.md:58`.

Цитаты: контракт — «`max_tokens: {type: integer, minimum: 1}`»; норма — «`max_tokens`: целое 1…`context` строки
модели; необязательно».

Что не так: верхняя граница зависит от строки модели и схемой не выразима, но `description` у параметра нет —
клиент по контракту не узнает, что `max_tokens` сверх `context` — 400 `bad step` («не по форме», Н1.2 п. 2).

Рекомендация: `description: "верхняя граница — context строки модели (V/10.2 Н1.2)"`.

## Что проверено без находок
