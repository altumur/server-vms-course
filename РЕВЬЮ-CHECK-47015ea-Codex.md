## 1. [P2] Успешный `--wait` оставляет разрешённой очистку при оборванном заборе

**Место:** `portable/check.py:264`, `:296`–`319`, `:342`–`343` в `47015ea`.

**Причина:** `cleanup_allowed = True` меняется на `False` только в обработчике исключения от `systemd-run --wait`. Когда этот вызов завершился нормально, весь забор до проверки SHA и манифеста проходит с разрешённой очисткой.

**Контрпример:** unit завершился, создал готовый outbox, `--wait` вернулся успешно. Затем ноутбук засыпает/соединение рвётся при `sha256sum` либо `cat` результата. В пробе реальный машинный `check.py run` создаёт архив, а fake SSH отдаёт первые 32 байта и выбрасывает ошибку транспорта. `forward_one` попадает в общий обработчик и удаляет outbox, рабочую папку и вход. Архивной копии и опубликованного результата ещё нет; локально остаётся лишь неполный файл. Та же потеря получается при обрыве чтения SHA и при коротком скачивании с кодом 0, обнаруженном проверкой SHA.

**Наблюдение CT 103:** `normal_fetch` — события `launch → sha → fetch → clean`; перед `clean`: `outbox=true`, `archived=false`; после: `outbox_retained=false`, `published=null`. `normal_sha` и `normal_short` также RED. Соответствующие сценарии на базе тоже RED: это сохранённое окно исходного дефекта, не новая регрессия. В новой серии путь `recovered_fetch`, где перед скачиванием уже оборвался `--wait`, GREEN: `clean` не вызывается, outbox остаётся.

**Основание:** заявленная раннером граница серии — очистка только после проверенного забора либо подтверждённого конца без outbox; оборванный fetch сохраняет удалённые данные. Различие этих двух путей в доказательстве сохранности результата отсутствует. Это сбой **после запуска, до проверенного забора**, поэтому оговорка README о сохранении прежнего поведения до запуска/после проверки его не покрывает.

**Предложение:** до отправки запуска запретить очистку при неизвестном исходе и сохранить запрет также после успешного `--wait`, пока результат не забран и не проверен. Разрешение возвращать только после проверки результата либо отдельного достоверного доказательства завершения без outbox. Обязательные тесты — три указанные ошибки без предварительного обрыва `--wait`, с проверкой сохранения удалённого архива.

## 2. [P2] `not-found` без outbox не доказывает завершение неизвестного запуска

**Место:** `portable/check.py:236`–`246`, `:302`–`304` в `47015ea`.

**Причина:** после любого неизвестного исхода `systemd-run` наблюдение `LoadState=not-found` (вместе с обычным для отсутствующего unit `ActiveState=inactive`) и отсутствие outbox немедленно превращаются в `FinishedWithoutResult`; обработчик разрешает `clean`. Код не имеет подтверждения, что исходный запуск уже был принят и завершился, либо окончательно не сможет вступить в силу.

**Контрпример:** исходное SSH-соединение оборвалось до подтверждения приёма запуска. Его удалённая команда/запрос ещё не дошла до создания transient unit. Новая проба получает `not-found`. После этого исходный, всё ещё **первый**, запуск вступает в силу; outbox ещё нет, проверка `test -f` отвечает 1. Пересыльщик считает unit закончившимся и стирает вход и рабочую папку уже начавшейся проверки. Повторный `systemd-run` для этого сценария не нужен.

**Наблюдение CT 103:** сценарный контроль `late_launch` моделирует именно этот порядок на границе fake SSH: `launch → status(not-found) → outbox-probe → original-launch-takes-effect → clean`. Перед очисткой в рабочей папке есть маркер выполняющейся проверки (`active=true`), архивной копии нет; после очистки маркер и вход удалены. Это контроль допустимого порядка событий, **не** заявление о воспроизведении задержки настоящего systemd/sshd на CT. Настоящий SSH и системные unit-ы проба не вызывает.

**Основание:** наблюдение нынешнего отсутствия unit не является квитанцией завершения исходного запроса. [Документация systemd-run, `--wait`](https://www.freedesktop.org/software/systemd/man/254/systemd-run.html) разделяет приём/постановку запуска и последующее ожидание деактивации; [systemctl](https://www.freedesktop.org/software/systemd/man/262/systemctl.html) описывает `LOAD`/`ACTIVE` как состояния unit, не историю неизвестного вызова. Возможность позднего вступления исходного запуска в силу — вывод из отсутствия подтверждения и отсечения старой попытки в рассматриваемом протоколе. Обещание серии «неизвестное состояние сохраняет удалённые данные» должно покрывать и этот случай.

**Предложение:** `not-found` с существующим outbox можно использовать для безопасного забора, как в тесте автора. `not-found` без outbox после неизвестного исхода считать неизвестным, сохранять файлы и наблюдать до потолка; сам потолок разрешения очистки не даёт. Для очистки без результата нужно положительное свидетельство завершения именно принятой попытки либо отсечение возможности её позднего запуска. Добавить контроль `not-found → поздний исходный запуск`; один отрицательный `test -f` не заменяет такого свидетельства.
