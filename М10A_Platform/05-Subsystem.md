# Урок 5 — Раскладка ключей

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** `Subsystem` — однострочные методы, которые собирают все ключи системы, — и `Assignment`, строку назначения, в которой список единиц работы лежит одной строкой через запятую. И увидите раскладку целиком, до того как появится первая подсистема.
**Время:** ~75 минут.

## Зачем этот урок

В уроках 2–4 ключи набирались руками: `"vms/cameras/7"`, `"vms/epoch/7"`, `"vms/heartbeats/w-1"`. Это работало, потому что их было три и все они лежали в тестах. В системе их будет полтора десятка семейств на подсистему, семь подсистем в М10B, и ещё префикс платформы — и набранные руками они разойдутся: кто-то напишет `testsub/worker/w-1` вместо `testsub/workers/w-1`, тест пройдёт (он же пишет и читает одно и то же), а контроллер не найдёт назначения.

Поэтому ключ никогда не набирается. Есть один объект, который умеет их составлять, и все обращения к хранилищам идут через него. Три десятка однострочных методов, ни одного алгоритма — и всё же это, пожалуй, самый плотный файл курса по отношению «решений на строку», потому что каждый метод здесь — это утверждение о том, что в системе есть, кто это пишет и как оно называется.

Второе, что делает этот урок: выписывает раскладку **целиком**, на одну страницу. Когда все ключи видны разом, становится видно и то, чего в них нет, — а это в проектировании обычно важнее.

> **Что можно проверить без железа.** Всё. Тест урока 1 проверяет четыре ключа и оба ACL прямой подстановкой; тест `test_controller_and_worker_bases_speak_only_the_contract` гоняет через `Assignment` полный цикл — назначить, прочитать, переназначить, увидеть новую ревизию.

## Что нужно знать заранее

- **Урок 2** — хранилище конфигурации и то, что список разрешённых префиксов есть утверждение об архитектуре.
- **Урок 4** — хранилище объектов и ключ heartbeat'а.

## Чему вы научитесь

1. Собирать ключи в одном месте и объяснять, почему это не «красивая обёртка».
2. Читать раскладку целиком и говорить, кто пишет каждое семейство.
3. Хранить список в хранилище, у которого только строки, — и понимать, чем за это платят.
4. Объяснять, зачем у назначения есть своя ревизия, если у ключа уже есть `ModifyIndex`.
5. Отличать грубый ACL базы от точного ACL спецификации и говорить, почему они разные.

## Шаг 1 — Одно поле, пять методов

```python
class Subsystem:
    name: str

    def config(self, *parts: str) -> str:
        return "/".join((self.name,) + parts)

    def assignment(self, worker: str) -> str:
        return f"{self.name}/workers/{worker}"

    def heartbeat_key(self, worker: str) -> str:
        return f"{self.name}/{HEARTBEATS}/{worker}"

    def epoch_key(self, unit: str) -> str:
        return f"{self.name}/epoch/{unit}"

    def slot_key(self, worker: str) -> str:
        return f"{self.name}/slots/{worker}"
```

Поле одно — имя. `Subsystem("testsub")` в тесте границы, `Subsystem("thing")` в тестах урока 1; в М10B — `vms`, `rec` и ещё пять. Всё остальное выводится из него — и ниже каждый из пяти методов разобран отдельно, потому что у каждого своя причина выглядеть именно так. (`HEARTBEATS = "heartbeats"` — константа рядом, потому что каталог heartbeat'ов читают и по ней.) Остальные методы `Subsystem` — ключи, которые приходят в своих уроках: снимок, блобы, просьбы о работе, метки серверов, списание, захваты мест; все они в таблице шага 3.

### `config(*parts)` — всё, что называет подсистема

```
sub.config("counters", "c1")  ->  testsub/counters/c1   строка оператора
sub.config("next_id")         ->  testsub/next_id       счётчик идентификаторов
sub.config("policy")          ->  testsub/policy        ручка администратора
sub.config("placement", "c1") ->  testsub/placement/c1  решение контроллера, с причиной
```

Общий случай и единственный метод, который ничего не знает о форме ключа: ему передают части, он их склеивает. Через него ходит всё, что не получило отдельного метода, и этим пользуется `SpecController`, который не знает заранее, как подсистема назвала свои строки — `counters` у `testsub` и своё слово в каждой YAML М10B. Лежит в **хранилище конфигурации**, то есть под CAS.

### `assignment(worker)` — что несёт этот воркер

```
sub.assignment("w-1")        ->  testsub/workers/w-1
```

Переменная, у которой **ровно один писатель — контроллер**, и ровно один заинтересованный читатель — воркер с этим именем, перечитывающий её каждый проход. Внутри список единиц и `rev`, который растёт с каждой правкой: воркер сравнивает его со своим и понимает, изменилось ли что-то, не сравнивая списки. Обратите внимание на слово `workers` в середине — ключ называет не воркера, а **его долю работы**, и поэтому переживает замену процесса: новый, захвативший имя `w-1`, читает ту же строку и получает те же единицы.

### `heartbeat_key(worker)` — что воркер знает о себе

```
sub.heartbeat_key("w-1")     ->  testsub/heartbeats/w-1
```

Единственный из пяти, который живёт **не в конфигурации, а в объектном хранилище**: десять килобайт, переписываемых целиком каждые десять секунд, — версии им не нужны, нужна атомарная замена (урок 4). Пишет его воркер и только о себе; читают контроллер, чтобы узнать, кто вообще существует, и консоль, чтобы показать. Имя воркера стоит **последним сегментом**, и это не эстетика — см. врезку ниже.

### `epoch_key(unit)` — кто сейчас пишет эту единицу

```
sub.epoch_key("c1")          ->  testsub/epoch/c1
```

Токен отсечения, и ключевое в нём — что он привязан к **единице, а не к воркеру**. Двое, держащих счётчик `c1` одновременно, — ровно тот случай, ради которого эпоха существует, и в такой раскладке они дерутся за один ключ: номер выдаёт `next_epoch` по CAS, удерживает аренда (урок 6). Была бы эпоха у воркера, два воркера имели бы две разные эпохи и оба считали бы себя вправе писать.

### `slot_key(worker)` — имя, взятое по CAS

```
sub.slot_key("w-1")          ->  testsub/slots/w-1
```

Единственный префикс во всей системе, у которого **два законных писателя**. Воркер слот захватывает и продлевает — кто он такой, процесс решает сам, иначе назначающий оказался бы на пути каждого запуска. Контроллер слот **освобождает**, одним методом `free_slot`, когда под слотом точно ничего не работает: сервер говорит, что такого процесса у него больше нет, или оператор списал сам сервер. Сам воркер такого сказать не может, потому что в этот момент его уже нет (урок 7).

Четыре из пяти — переменные под CAS, пятый — объект. И три из них платформа пишет **сама**: назначение, эпоху и слот. Подсистема на их форму не влияет вовсе; она влияет только на первое слово.

> **Этот порядок был выбран наоборот и переигран.** Сначала здесь стояло `<имя>/w-1/heartbeat` — «пусть объекты одного воркера лежат в одном каталоге, их будет больше одного». Довод был разумный и оказался неверным: имя воркера в **первом** сегменте делает грант невыразимым. Имя берётся в рантайме (`claim_slot` выдаёт `w-1`), а права — статический текст, написанный до запуска (в кластере — файл прав демона, сгенерированный из спецификаций), поэтому «может писать свой heartbeat и больше ничего» записать было нечем: самый узкий выражаемый грант — весь префикс объектов подсистемы, вместе со снимком, который читает М12, и блобами, которым доверяют воркеры. Имя воркера уехало в **последний** сегмент, и грант появился. Разбор — **урок 20**.

## Шаг 2 — Два ACL на базе

```python
    def acl_controller(self) -> list[str]:
        return [f"{self.name}/*"]

    def acl_worker(self) -> list[str]:
        return [f"{self.name}/epoch/*", f"{self.name}/slots/*", f"{self.name}/holds/*"]
```

**ACL** — access control list, список доступа: отображение «имя писателя → префиксы, в которые ему можно писать». В уроке 2 мы написали механизм, который его исполняет, — четыре строки в начале `put`, сверяющие путь со списком и бросающие `Forbidden`, если совпадения нет. Здесь появляется то, что этот механизм проверяет.

Три вещи стоит сказать прямо, потому что дальше они предполагаются известными.

**Это про запись.** На коробке читают все и всё: конфигурация и решения о размещении — не секреты. В кластере у роли есть и список чтения — демон отвечает 403 на чтение чужого префикса, — но выводится он так же, из спецификаций, и ничего не меняет в том, что пишет кто. Секреты в строках в системе есть, и разговор о них отдельный (урок 18).

**Это про токен, а не про человека.** Список говорит, что может писать **процесс** с таким именем, и ничего не говорит о том, кто такой оператор за экраном: аутентификация человека живёт в консоли и приходит только в М12. Здесь речь о другом — что воркер, каким бы кодом он ни был, физически не может изменить строку единицы.

**Это то, ради чего раскладка вообще выписана отдельно.** В М9 конфигурацию писал рекордер — весь процесс целиком, — и поле, которое воркер переписывал «чтобы не терять», оказалось тем же, что правил оператор; искали три дня. Дефект был не в коде, который перезаписал поле, а в том, что этот код **имел право** его перезаписать. Соглашение «воркер сюда не пишет» держится ровно до следующего человека, который добавляет функцию в пятницу; отказ держится всегда.

Отсюда и место этих двух методов — на `Subsystem`, рядом с ключами. Права **выводятся из имени тем же кодом**, что и сами ключи, поэтому список прав и раскладка не могут разойтись: нельзя добавить ключ и забыть про право, если и то и другое собирается из одного слова. В кластере М11 эти же списки становятся ролями в файле прав демона `configstore` — файл генерируется из спецификаций, — и проверяет их демон, а не процесс, — но текст в них тот же.

Те самые списки из урока 2, но выведенные из имени. И здесь есть неточность, которую надо назвать сразу, потому что иначе она обнаружится в уроке 9 как противоречие.

`acl_controller()` отдаёт **весь префикс подсистемы** — `testsub/*`. Это грубо: контроллер получает право писать и строки единиц тоже, хотя писать их будет консоль. Почему так: на этом уровне подсистемы-как-данных ещё нет, и платформа не знает, как называются строки оператора — а значит, не может вырезать их из прав. Точный список появится в уроке 9, когда появится YAML: `SubsystemSpec.acl_controller()` вернёт `["testsub/workers/*", "testsub/placement/*", "testsub/slots/*", "testsub/decommissioned/*"]`, и в нём строк оператора не будет.

Базовая версия остаётся для подсистем, у которых нет спецификации, — то есть для тестов платформы и для гипотетического случая, когда кто-то захочет использовать `Controller` напрямую. Полезное правило: **если у подсистемы есть YAML, права берутся из неё**, а `Subsystem.acl_controller()` — это то, что было до неё.

`acl_worker()` точен с самого начала: воркер пишет свои эпохи, свой слот и место, которое занял, и это не зависит ни от какой спецификации. `test_identity_by_claim_is_a_platform_piece` проверяет строки подстановкой — `sub.acl_worker() == ["thing/epoch/*", "thing/slots/*", "thing/holds/*"]`.

Три префикса — это три ответа воркера о себе: **что я делаю** (эпоха единицы), **кто я** (слот) и **где я** (захват места, урок 7, шаг 11). Конфигурации среди них нет и быть не может: всё, что воркер пишет, — утверждения о нём самом.

**Третьего списка здесь нет вовсе**, и это не потому, что консоль пишется только в уроке 15: `acl_console()` в `Subsystem` нечего было бы вернуть. Права воркера и контроллера собираются из слов платформы — `epoch`, `slots`, `workers`, `placement`, — одинаковых во всех подсистемах. Консоль пишет строки оператора, а как они называются, знает только подсистема: `counters` у `testsub`, своё слово у каждой подсистемы М10B. Вывести `testsub/counters/*` из имени `testsub` нельзя, а зашить в платформу слово подсистемы не даст тест границы урока 1. Поэтому права консоли появляются вместе со спецификацией — `SubsystemSpec.acl_console()` в уроке 9, — и грубость `acl_controller()` выше есть та же дыра с другой стороны: `testsub/*` временно покрывает и то, что принадлежит консоли.

## Шаг 3 — Раскладка целиком

Вот всё, что система когда-либо положит в два хранилища. Каждая подсистема даёт свою копию первого блока; строки `platform/*` — общие.

**Конфигурация** (`variables.py`):

| Ключ | Кто пишет | Что это |
|---|---|---|
| `<sub>/<строки>/<id>` | консоль | строка оператора — единица работы; как называются строки, говорит спецификация |
| `<sub>/next_id` | консоль | счётчик идентификаторов, растёт по CAS |
| `<sub>/idem/<ключ>` | консоль | заявка на идемпотентный POST и сохранённый ответ (урок 15) |
| `<sub>/policy` | консоль | ручка администратора: `servers: shared \| distinct` (урок 11) |
| `<sub>/servers/<сервер>` | консоль | что сервер достаёт — его метки, как их сказал администратор |
| `<sub>/<таблица>/<имя>` | консоль | строка таблицы, объявленной в спецификации: не единица, на ней ничего не размещается (урок 15) |
| `<sub>/requests/<id>` | консоль, ресурс | просьба о конечной работе вне обычного прохода: от оператора; от ресурса — освободить место на диске (урок 14) |
| `<sub>/sweep` | консоль | что уборка блобов пометила и когда (урок 20) |
| `<sub>/retention[/<id>]`, `<sub>/alarms_retention/<id>` | консоль | производные строки, объявленные спецификацией: сколько дней ресурс держит бакеты событий подсистемы или этой единицы (урок 14) |
| `<sub>/workers/<воркер>` | контроллер | назначение: какие единицы несёт этот воркер |
| `<sub>/placement/<id>` | контроллер | решение о размещении, с причиной |
| `<sub>/decommissioned/<сервер>` | контроллер | отметка, что списание сервера исполнено: какие слоты отпущены, какие единицы ушли (урок 17) |
| `<sub>/slots/<воркер>` | воркер (захват), контроллер (освобождение, предложение запасному) | имя, взятое по CAS |
| `<sub>/holds/<место>` | воркер (захват) | место с квотой, взятое по CAS, чтобы писать туда одному (урок 7, шаг 11) |
| `<sub>/epoch/<id>` | воркер | токен отсечения: кто сейчас пишет эту единицу |
| `platform/drain`, `platform/decommission/<сервер>` | консоль (оператор) | «эта машина сейчас остановится» и «этой машины больше нет» — одна строка на все подсистемы (урок 17) |
| `platform/schema` | оператор | версия раскладки, которую поднимают последней (урок 17) |
| `platform/doors/<сервер>` | ресурс | где отвечает ресурс этого сервера (урок 14) |
| `platform/mirror` | инсталлятор | ручка зеркалирования бакетов между ресурсами |
| `platform/space` | инсталлятор | отметки высокой и низкой воды на диске и пол в днях, ниже которого ресурс не просит отдавать ничего (урок 14) |

Две последние строки стоят особняком: `platform/mirror` и `platform/space` — ключи, которых не пишет ни один процесс курса. «Инсталлятор» здесь — человек, который разворачивает систему, с управляющим токеном в руках, а не роль рядом с консолью и контроллером: в файле прав кластера у ресурса на них только `read`, а у консоли их нет вовсе. Так и задумано: обе ручки — свойства железа, а не подсистемы (копировать ли бакеты между серверами; при какой занятости диска начинать освобождать), их ставят один раз при развёртывании, и процесса, которому это полагалось бы по работе, в системе нет. Обе вводятся в [уроке 14](14-Resource.md): `platform/mirror` в первой его половине, `platform/space` во второй.

**Объекты** (`objects.py`):

| Ключ | Кто пишет | Что это |
|---|---|---|
| `<sub>/heartbeats/<воркер>` | воркер | всё, что он про себя знает (урок 4) |
| `<sub>/snapshot/<воркер>` | контроллер | копия строк с возрастом — то, что уезжает из кластера в М12 (уроки 11 и 19) |
| `<sub>/blobs/<дайджест>` | консоль | байты поля `blob`, неизменяемые по построению (урок 19) |
| `<sub>/controller/pass` | контроллер | отчёт о последнем проходе: сколько не хватает воркеров, кому предложены запасные (уроки 11, 19) |
| `<sub>/contenders/<слот>/<коробка>` | воркер | «я хочу это имя, а держит его другой экземпляр» (урок 7) |
| `<sub>/used/<место>` | воркер | место, которое воркеры подсистемы открыли, и где (урок 7) |
| `platform/resources/<сервер>/heartbeat` | ресурс | что лежит на его дисках, сколько занято, где его HTTP |

Это вся система. Теперь то, чего в ней нет. Теперь то, чего в ней нет.

**Нет ключа со списком воркеров.** Кто существует — выводится из `list` heartbeat'ов и из отметок времени в них. Реестр пришлось бы поддерживать в согласии с реальностью, а он бы расходился.

**Нет ключа со статусом.** Статус — в heartbeat'е, то есть у того, кто его наблюдает, а не у того, кто про него спрашивает.

**Нет ключа с блокировкой или лидерством.** Контроллеров может быть два, и они не выбирают лидера: каждая запись идёт по CAS, и второй проигрывает гонку. Ключ лидерства — это ключ, за который надо бороться, и время, в течение которого его никто не держит.

**Нет очереди и нет журнала команд.** Решение записывается в `placement/<id>` и остаётся там; воркер читает своё назначение. «Отправить» команду было бы значит завести получателя, подтверждение и повтор — а так повтором занимается сам цикл сверки.

## Шаг 4 — Назначение

```python
@dataclass
class Assignment:
    worker: str
    units: list[str]                 # what the subsystem calls its units of work; the platform does not know
    rev: int = 0
```

Три поля, и комментарий в середине — это граница модуля, записанная в объявлении структуры. `units` — список строк. Что эти строки значат, платформа не знает: для `testsub` это имена счётчиков, для `thing` в тестах — `"1"`, `"2"`, `"3"`; в М10B у одной подсистемы — номера, у другой — имена вида `7-linecross`.

```python
    def to_items(self, key: str = "") -> dict:
        for u in self.units:
            if LIST_SEPARATOR in str(u):
                UNLISTED.garbled(f"{key or self.worker}#{u}", f"{LIST_SEPARATOR!r} in its name")
        return {"units": LIST_SEPARATOR.join(u for u in self.units if LIST_SEPARATOR not in str(u)), "rev": self.rev}

    @classmethod
    def from_items(cls, worker: str, items: dict | None) -> "Assignment":
        if not items:
            return cls(worker, [])
        return cls(worker, [u for u in items.get("units", "").split(",") if u], int(items.get("rev", 0)))
```

Список склеивается в строку через запятую (`LIST_SEPARATOR`), потому что в хранилище значения — строки (урок 2, шаг 8), и ничего вложенного туда положить нельзя. Разбор — `split(",")` с отбрасыванием пустых: без этого пустое назначение дало бы список из одной пустой строки, и воркер пошёл бы искать единицу с именем `""`.

Отсюда же — ограничение, о котором стоит знать: **идентификатор единицы не может содержать запятую.** `to_items` его и проверяет: единица с запятой в имени не попадает ни в одно назначение — список её бы разрезал, — а считается испорченной (`UNLISTED`: «она не назначена никому; создайте её заново под именем без запятой») и называется в логе один раз. Тихо развалить назначение она не может. Альтернатива — JSON в значении — обменяла бы этот запрет на нечитаемость строки глазами (`configstore backup` печатает строки как есть) и на разбор, который может кинуть исключение. Выбрана запятая.

Отсутствующий ключ даёт пустое назначение, а не `None`. Это та же линия, что `get` → `(None, 0)` и `objects.get` → `None`: **свежий воркер, у которого нет строки назначения, ничего не выдумывает.** Он получает пустой список и не делает ничего — и это буквально утверждение теста `test_a_worker_with_no_assignment_invents_nothing` в М11.

## Шаг 5 — Зачем назначению своя ревизия

У ключа уже есть `ModifyIndex`. Зачем `rev`?

Потому что это разные числа для разных читателей. `ModifyIndex` — механизм хранилища: он растёт при любой записи в любой ключ, и его значение ничего не говорит о том, сколько раз менялось **это** назначение. Он нужен тому, кто пишет, — как `cas`.

`rev` — счётчик изменений назначения, и он нужен тому, кто **читает**. Воркер кладёт его в heartbeat (`assignment_rev`), и консоль показывает: назначение ревизии 4, воркер отчитывается о ревизии 3 — значит, он ещё не дошёл до последнего прохода. Без `rev` это можно было бы получить из `ModifyIndex`, но тогда номер прыгал бы на десятки при каждой чужой записи, и «отстал на одну ревизию» перестало бы что-либо значить.

Та же пара — «версия хранилища для писателя, счётчик изменений для читателя» — повторится в строках единиц: `revision` у строки единицы растёт с каждой правкой оператора, `observed_revision` возвращается воркером, и цикл сверки сравнивает их через `>=` (это М9, урок 6). Одна и та же идея на двух уровнях.

## Шаг 6 — Как это выглядит в работе

Из теста урока 1, теперь целиком понятный:

```python
    sub = Subsystem("thing")
    ctl = Controller(sub, box.vars, box.objects, wall=box.wall)
    w = Worker(sub, "t-1", box.vars, box.objects, clock=box.clock, wall=box.wall)
    ...
    a = ctl.assign("t-1", ["3", "1", "2"])
    assert a.units == ["1", "2", "3"] and a.rev == 1 and w.assignment().units == ["1", "2", "3"]
    assert ctl.assign("t-1", ["1"]).rev == 2
```

Три вещи за четыре строки. Контроллер назначает `["3", "1", "2"]` — и получает обратно `["1", "2", "3"]`: **назначение сортируется при записи**. Это не косметика: строка в хранилище должна зависеть только от множества единиц, а не от порядка, в котором контроллер их перебрал, иначе два прохода с одинаковым результатом дали бы две разные записи и лишнюю ревизию.

Воркер тут же читает своё назначение и видит то же самое — через `sub.assignment("t-1")`, то есть через тот же составитель ключа. Ни одна строка ключа в тесте не набрана.

Второе назначение даёт `rev == 2`. Счётчик увеличивается при каждой записи, даже если состав изменился на противоположный, — он считает **изменения**, а не единицы.

**Результат:** `Subsystem` и `Assignment` в `contract.py`; раскладка целиком, выписанная своими словами; и ответ на вопрос, почему в ней нет ключа со списком воркеров.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Воркер не видит своего назначения | Ключ где-то набран руками (`testsub/worker/` вместо `testsub/workers/`). Единственное лекарство — не набирать: все обращения через `Subsystem`. |
| Пустое назначение даёт единицу с пустым именем | В разборе потерян фильтр `if u`. `"".split(",")` — это `[""]`, а не `[]`. |
| Единица не размещается, хотя воркеры есть | В её имени запятая: `to_items` не кладёт её ни в одно назначение и считает её `unlisted`. Создайте её заново под именем без запятой. Если подсистеме правда нужны такие имена, менять придётся `to_items`/`from_items` — и вместе с ними всех, кто читает строку назначения глазами. |
| `rev` прыгает через несколько | Кто-то подставил `ModifyIndex` вместо счётчика. Это разные числа: первое растёт от чужих записей. |
| Контроллер пишет строку единицы и ему это удаётся | Он взял `Subsystem.acl_controller()` — грубую версию `<имя>/*`. С появлением YAML права должны приходить из `SubsystemSpec.acl_controller()`. |
| Два прохода контроллера с одинаковым исходом дают две ревизии | Назначение записано без сортировки, либо запись происходит без сравнения с текущим значением. |

## Итог

- Ключи не набираются руками нигде: их составляет `Subsystem`, и у него одно поле — имя.
- Свои семейства платформа называет сама — назначение, heartbeat, эпоха, слот, захват места, снимок, просьбы, метки серверов; подсистема называет только свои строки и таблицы, через спецификацию, а `config(*parts)` склеивает их тем же способом.
- Вся система — одна таблица раскладки на страницу. В ней нет реестра воркеров, ключа статуса, лидерства и очереди, и каждое отсутствие — решение.
- Список хранится строкой через запятую, потому что значения в хранилище — строки; цена — запрет на запятую в идентификаторе.
- Отсутствующее назначение — это пустой список, а не ошибка: воркер, которому ничего не назначено, ничего не выдумывает.
- У назначения две версии: `ModifyIndex` для писателя, `rev` для читателя. Та же пара повторится как `revision`/`observed_revision`.
- Назначение сортируется при записи, чтобы строка зависела от множества, а не от порядка обхода.
