# Урок 17 — Обновление без простоя

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** `platform/drain` — одну строку с одним именем; `on_draining` и третью причину в `redistribute`; `would_strand` — сухой прогон; `drain_state` с его `safe`; и вторую половину — `SCHEMA`, `check_schema`, `builds`, `set_schema`.
**Время:** ~70 минут.

## Зачем этот урок

Десять серверов, на каждом запись, и её надо обновить. Выключать всё сразу нельзя; выключать по одному можно — но каждый раз получать полторы минуты без записи на тех камерах, что стояли на этой машине, тоже нельзя, потому что за десять серверов это пятнадцать минут дыр в архиве, которые оператор увидит и не простит.

Причина этих полутора минут — в уроке 11, и она не ошибка. Единицы рекордера уезжают, когда его слот залапсился **и** ресурс его сервера молчит: два независимых молчания, каждое по `lost_after`. Правило верное — одно молчание это упавший процесс, и его возвращает планировщик, — но оно про **аварию**.

Обновление аварией не является. Мы знаем о нём заранее. И весь этот урок — про то, что из этого следует.

Две половины, и они отвечают на разные вопросы:

| | вопрос | ответ |
|---|---|---|
| `platform/drain` | эту машину можно гасить? | по одной за раз, и работа уходит первой |
| `platform/schema` | все машины уже новые? | номер поднимают последним, а не первым |

Обе — строки в хранилище. Ни нового процесса, ни новой подсистемы, ни слова «обновление» ни в одной подсистеме.

> **Проверка без железа.** Полностью. Осушение — это строка, и её действие видно в двух функциях, которые уже проверяются тестами; версии — две строки и один скан объектов. Ни Nomad, ни настоящей перезагрузки для этого не нужно.

## Что нужно знать заранее

- **Урок 7** — слот и `release_slot`: осознанная отдача против просроченной. Осушение — третий вид «меня здесь нет», и первый, о котором говорят заранее.
- **Урок 11** — `_pool`, `eligible`, `home` и `ensure_home`: сюда осушение вставляется, и отсюда работа возвращается; `redistribute`, `without_resource`, `gone_servers`: реакции на молчание, к которым добавится одна реакция на заявление.
- **Урок 14** — ресурс и его heartbeat; в М10B — что видео лежит в томах-кольцах фиксированного размера (урок 27 М10B).

## Чему вы научитесь

1. Отличать плановую остановку от молчания и объяснять, почему у них разная цена.
2. Выражать «эта машина сейчас уйдёт» так, чтобы ни одна подсистема не узнала нового слова.
3. Отвечать на «можно гасить?» условием, а не таймаутом.
4. Спрашивать «что станет неразмещаемым» до перезагрузки, а не после.
5. Ставить проверку версии в ту сторону, в которую надо, и поднимать номер в тот момент, в который надо.

## Шаг 1 — Одна строка, одно имя

```python
DRAIN_KEY = "platform/drain"


def draining(vars_) -> str:
    items, _ = vars_.get(DRAIN_KEY)
    return (items or {}).get("server", "")
```

Строка **платформенная**, а не подсистемы: на машине стоят и воркер, и рекордер, и ресурс, и уходят они вместе.

Строка держит **одно** имя — и это вся взаимная блокировка, которая здесь нужна:

```python
    def drain(self, server: str) -> dict:
        def mutate(items):
            have = (items or {}).get("server", "")
            if have and have != server:
                raise DrainRefused(f"{have} is already draining; one server at a time")
            return {"server": server, "at": str(self.wall())}
        return self.write(DRAIN_KEY, mutate)
```

`write` — это CAS из урока 8. Два оператора одновременно, или скрипт с ошибкой в цикле, не могут осушить две машины сразу не потому, что кто-то догадался проверить, а потому, что запись одна и она под CAS.

И одна деталь про токены: осушение пишет **консоль**, не контроллер. Это заявление оператора, а не решение системы, — `DRAIN_KEY` попал в `acl_console`, и контроллер строку только читает. Та же линия, что в уроке 9: консоль не размещает, контроллер не редактирует.

## Шаг 2 — Два места, где строка действует

```python
    def on_draining(self, workers) -> list[str]:
        server = self.draining()
        return [w for w in workers if server and self.server_of(w) == server] if server else []

    def _pool(self, workers):
        pool = sorted(workers if workers is not None else self.workers_seen())
        leaving = {n for n, s in self.slots().items() if s.released}
        gone = set(self.without_resource(pool)) | set(self.idle_by_policy(pool)) | leaving | set(self.on_draining(pool))
        return [w for w in pool if w not in gone]
```

Третий член в множестве, которое уже было. «Не здесь» теперь бывает четырёх видов: слот отпущен, ресурс молчит, политика велела простаивать — и машина уходит. Ни одна подсистема этого не заметит: они все ходят через `_pool`.

Но исключить из пула мало. Единицы, которые **уже** там стоят, надо увести, и для этого — вторая половина, в `redistribute`:

```python
        for w in self.on_draining(seen):                               # an operator said this machine is about to stop
            if self.assignment(w).units:
                gone_for.setdefault(w, f"server {self.server_of(w)} draining")
```

Рядом в том же методе стоит ещё одна причина увести единицы с живого воркера, и она той же формы: **воркер жив, но нести единицы не может.** Там, где подсистема размещает по месту (`place_by: volume`), воркер без места — запасной. Это нормальное состояние, пока у него нет назначений. Но регистратор, потерявший том — два перезапустились, том взял другой, — остаётся жив, держит слот и не может записать ни байта, а назначенные ему записи стояли на нём, не записываемые никем, сколько он жил (продукт нашёл это на своём ящике; обратная связь, BN). Он сам говорит, что места у него нет (`volume: ""` в heartbeat), и `redistribute` уводит его единицы с причиной «r-1 holds no volume now».

Ровно та же форма, что у `without_resource` строкой выше. Разница одна, и она вся в комментарии: там система **заметила**, здесь оператор **сказал**.

Причина размещения потом читается как обычно: `server srv-a draining; most free capacity (7); on srv-b`. Никакого особого режима, никакого флага «идёт обновление» — обычный переезд с обычной причиной.

## Шаг 3 — Сухой прогон

Пятьдесят камер, уезжающих с машины, должны куда-то приехать. «Куда-то» — это факт про запас и метки, а не надежда:

```python
    def would_strand(self, server: str, workers: list[str] | None = None) -> list[str]:
        pool = [w for w in self._pool(workers) if self.server_of(w) != server]
        out = []
        for row in self.units():
            uid = row["id"]
            pl = self.placement(uid)
            if pl is not None and self.server_of(pl.worker) != server:
                continue                                   # it is not on that server: not its business
            if not self.eligible(row, pool):
                out.append(str(uid))
        return out
```

Тем же `eligible`, который будет отвечать по-настоящему через минуту. Это важно: сухой прогон, считающий по своей формуле, рано или поздно разойдётся с настоящим размещением, и разойдётся молча.

Альтернатива вопросу — прочитать `/unplaceable` **после** перезагрузки, когда камера уже не пишется. Разница между «спросил и не стал» и «сделал и увидел» здесь стоит ровно столько, сколько стоит запись.

## Шаг 4 — Условие вместо `sleep`

Вот к чему всё шло. Скрипт обновления не должен спать и надеяться:

```python
    def drain_state(self, server: str = "") -> dict:
        ...
        units = sum(len(ctl.assignment(w).units) for w in here)
        strand = ctl.would_strand(server)
        # Nothing waits on this machine to be moved somewhere: what a worker wrote is wherever it wrote it — a
        # recorder's footage in its volume, closed when the writer was closed. No units left is the whole answer.
        return {"draining": server, "subsystem": ctl.spec.name, "workers": sorted(here),
                "units": units, "would_strand": strand, "safe": units == 0}
```

`safe` — одно слагаемое: **единиц не осталось**. Работа уехала, и это видно контроллеру (`test_lesson11_edge.py::test_the_upgrade_script_polls_a_condition_instead_of_sleeping`: запись ушла с `r-1` на `r-2` — и `safe` истинно).

Второго слагаемого — про данные — здесь нет, и комментарий говорит почему. На машине нечему ждать переноса. Регистратор пишет кадр в писатель тома в ту минуту, когда кадр пришёл (М10B, урок 10); очереди файлов, которые ещё надо куда-то отвезти, у него нет. Остановленный конвейер закрывает свою последовательность (`RecSink.finish`), а последний сброс писателя делает штатная остановка регистратора: `after_stop` закрывает писателя, пока том ещё его, и только потом отпускает захват (урок 27 М10B).

Маршрут `GET /drain` живёт на `Mount`, а не на подсистеме: машина несёт несколько, и `safe` истинно, только когда так говорит каждая. И за воротами, как любой маршрут: изменить — `admin`, прочитать — `view`; вывод и возврат сервера и подъём схемы — строки журнала (`drain.started`, `drain.ended`, `schema.raised`). Сначала эти маршруты отвечали до ворот — `POST /drain` без токена уводил записи с сервера (третье ревью, блокер 2; М10A, урок 15). Скрипту обновления, который их зовёт, нужен токен администратора; `PUT /schema` к тому же пишет строку платформы, которую токен консоли писать не может, — и отвечает 403 со словами хранилища, а не обрывом.

## Шаг 5 — Сбрасывать нечего

Тут стоит остановиться, потому что это тот случай, когда задуманный механизм оказался не нужен.

Хотелось добавить в осушение команду «сбрось всё, что записано, и только потом скажи `safe`». Пока архив был файлами, у условия и правда было второе слагаемое — очередь закрытых кусков на диске этой машины, — но и тогда команда не понадобилась: очередь опустошала сама остановка конвейеров.

С архивом в ObjectStorage исчезло и само слагаемое. Кадр уходит в том, как только пришёл, и ждать на машине нечего. Последние минуты в томе — следствие порядка штатной остановки регистратора: сначала закрыть писателя, его сброс кладёт хвост в том, потом отпустить захват. На это юниту дано `StopTimeout=40` (`deploy/recworker@.container`), а сброс протокол разрешает растянуть до тридцати секунд.

Правило, которое стоит унести из этого шага: прежде чем добавлять глагол, посмотрите, не является ли нужное вам уже следствием. Команда, дублирующая то, что система делает сама, — это второй путь к тому же состоянию, и расходиться они начнут в первый же нештатный день.

## Шаг 6 — Вторая половина: направление проверки

Обновление по одной машине означает, что старые и новые процессы какое-то время работают над одним хранилищем. Добавить поле — бесплатно. Поменять смысл поля — нет, и это новый номер:

```python
SCHEMA = 1
SCHEMA_KEY = "platform/schema"


def check_schema(vars_) -> int:
    have = schema_version(vars_)
    if have > SCHEMA:
        raise SchemaTooNew(f"store is at schema {have}; this build understands {SCHEMA}")
    return have
```

Проверяется **одно** направление, и это вся суть.

**Новый процесс против старого хранилища — нормально.** Он понимает старую раскладку; в этом и состоит обновление. Если запретить и это, обновляться будет нечем.

**Старый против нового — отказ стартовать.** Громко, в цикле перезапусков, который оператор видит, — а не тихо, теряя незнакомые поля на первом же read-modify-write. Второе страшнее, потому что выглядит как работающая система.

Вызов стоит в конструкторах `Controller`, `Worker` и `Resource` — то есть забыть его нельзя. Отсутствующая строка означает «свежая установка», и проверка проходит.

## Шаг 7 — Номер поднимают последним

```python
    def set_schema(self, version: int) -> dict:
        now = self.wall()
        behind = {n: b for n, b in builds(self.objects, now).items() if b["live"] and b["schema"] < version}
        if behind:
            raise SchemaTooNew(f"still running: {', '.join(sorted(behind))} — at schema "
                               f"{min(b['schema'] for b in behind.values())}")
```

Если бы номер поднимал первый обновлённый процесс, он заблокировал бы все ещё не обновлённые машины — то есть устроил бы ровно тот простой, ради избежания которого затевалось скользящее обновление. Поэтому подъём — отдельный шаг оператора, после того как всё новое.

«Всё новое» — проверяемо, и проверять нечем новым: каждый процесс и так публикует свой номер.

**Битая строка схемы — не новая схема.** Сверка при каждом продлении сделала строку `platform/schema` точкой отказа всего парка: строка, которая не разбирается, останавливала продление аренд и heartbeat у всех (третье ревью). Теперь `check_schema(vars_, last=)`: работающий процесс держит версию, которую прочитал целой последней, и отсекается только версией, которая **разбирается и новее**; процесс, который схему не читал ни разу, с битой строкой не стартует. Тест в `test_lesson1_platform.py`.

**И проверяется не один раз.** Старая сборка сверяла схему при старте и публиковала номер только с первым heartbeat'ом — после прохода. Стартовав в это окно, она проходила проверку `set_schema` (её ещё не видно) и дальше работала со старой схемой поверх новой (ревью платформы, m4). Теперь `renew_slot` сверяет схему перед каждым продлением (`check_schema`): хранилище ушло вперёд — `SchemaTooNew`, воркер отсекается (`lease_pass` → `fence`) и **не возвращается** (`rejoin` сверяет первым делом), пока его не обновят. Цена — одно чтение `platform/schema` на продление; в трассах стенда М11 оно теперь видно. Тест: `test_lesson1_platform.py::test_a_build_the_store_outgrew_while_it_ran_fences_and_does_not_rejoin`.

```python
    def heartbeat(self, status: list[dict], **extra) -> None:
        extra.setdefault("schema", SCHEMA)
        extra.setdefault("build", BUILD)
```

Из базового класса, поэтому ни одна подсистема про это не помнит. А `builds` находит их все одним сканом, потому что ключ heartbeat'а у всех кончается одинаково:

```python
def builds(objects, now: float, lost_after: float = 45.0) -> dict[str, dict]:
    out = {}
    for key in objects.list(""):
        if not key.endswith("/heartbeat"):
            continue
```

Назад номер тоже не идёт. Откат сборки — это откат кода, а не раскладки: данные, написанные новой версией, старая не разучится читать оттого, что ей поменяли число.

## Шаг 8 — Круг целиком, и где он дрейфует

```
POST /drain?server=srv-a
polling GET /drain   →  {"safe": false, "would_strand": {...}}
                     →  {"safe": true}
гасим · обновляем · поднимаем
DELETE /drain
ждём, пока работа вернётся
следующий сервер
PUT /schema?version=2      ← один раз, когда все десять новые
```

Предпоследняя строка — не формальность. `ensure_home` возвращает **одну** единицу за проход: сервер с полусотней записей набирает их назад минут за пять. Это правильно — постепенно, без шторма эпох, — но если скрипт считает признаком готовности «машина загрузилась», а не «работа вернулась», то за десять серверов единицы сдрейфуют: каждое следующее осушение сгоняет их на ещё не обновлённые машины, а вернуться они не успевают.

К концу круга последние две машины несут всё. Тома записи — кольца фиксированного размера (урок 27 М10B): в каждый теперь пишет больше записей, кольцо оборачивается быстрее, и глубина архива тает. Регистратор поднимет `archive.shallow` у записей, которым обещан пол. Формально ничего не сломалось. Практически вы обновили кластер и укоротили архив.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Полторы минуты без записи на каждой машине | Осушения нет: система ждёт двух молчаний вместо того, чтобы прочитать заявление. |
| Единицы не уезжают, хотя строка написана | Есть `_pool`, нет причины в `redistribute`: новых туда не ставят, старые остаются. |
| Осушили две машины разом | Строка держит список вместо одного имени. CAS тут ни при чём — форма данных. |
| Последних минут нет в томе | Сервер выключили, не дав регистратору штатно остановиться. `safe` говорит, что работа ушла, а не что процессы остановлены: писатель закрывается — и сбрасывает хвост — в `after_stop`. |
| Камеры стали `unplaceable` после перезагрузки | Сухой прогон не спросили. Он отвечает тем же `eligible`, что разместит потом. |
| Старая сборка молча портит строки | Проверка схемы поставлена в обратную сторону — или её нет в конструкторе. |
| Половина кластера в цикле перезапусков | Номер подняли до конца обновления. Это и есть тот простой, которого избегали. |
| К концу круга две машины несут всё | Скрипт шёл дальше по «машина загрузилась» вместо «работа вернулась». |

## Итог

- Плановая остановка — не молчание: о ней известно заранее, и работа может уйти первой.
- Одна строка, одно имя: взаимная блокировка — это форма данных плюс CAS, а не отдельная проверка.
- Действует в двух местах: не ставить туда (`_pool`) и увести оттуда (`redistribute`). Первого без второго мало.
- Заявление оператора пишет консоль; контроллер читает. Та же линия, что между размещением и редактированием.
- Сухой прогон отвечает той же машинерией, что ответит по-настоящему, — иначе он однажды разойдётся с ней молча.
- Готовность — условие, а не таймаут: единиц не осталось. Данным ждать на машине нечего — кадр уходит в том, как только пришёл.
- Прежде чем добавлять глагол, проверьте, не следствие ли это. Сброс писателя — следствие штатной остановки регистратора.
- Проверка версии — в одну сторону: новый против старого хранилища работает, старый против нового не стартует.
- Номер поднимают последним, и только когда каждый живой процесс сказал, что понимает его.
- Возврат домой идёт по одной единице за проход. Признак «можно дальше» — вернувшаяся работа, а не загрузившаяся машина.

## Упражнения

1. Уберите `on_draining` из `_pool`, оставив причину в `redistribute`. Осушите сервер и опишите, что будет происходить с единицами следующие три прохода.
2. И наоборот: оставьте `_pool`, уберите причину. Сколько единиц уедет с машины?
3. Сделайте строку списком серверов. Осушите два из трёх и посчитайте, сколько камер станут неразмещаемыми.
4. Добавьте в `safe` второе слагаемое: «писатель тома на этой машине закрыт». Осушите сервер и скажите, когда условие станет истинным — и почему скрипт обновления теперь не дождётся его никогда.
5. Остановите регистратор `kill -9` вместо штатной остановки и прочитайте, что найдёт следующий регистратор того же тома на этом хосте (`reattached`, урок 27 М10B). Что из записанного пропало?
6. Поставьте проверку схемы в обе стороны (новый процесс тоже отказывается против старого хранилища). Опишите, как теперь выглядит обновление.
7. Пусть номер поднимает первый новый процесс. Прогоните обновление десяти серверов на бумаге и скажите, на каком по счёту всё встанет.
8. Напишите скрипт обновления, который идёт дальше по «машина загрузилась». Десять серверов, пятьдесят записей на каждом, `ensure_home(1)` раз в пять секунд: где окажутся записи к концу круга?

## Что дальше

Платформа умеет разместить работу, вернуть её домой, освободить место и пережить обновление — и ничего из этого не знает про камеру. Ни одна из четырёх подсистем М10B не добавит к этому уроку ни строки: осушение видно им через `_pool`, а версию они публикуют из базового класса, не зная об этом.

Остались три долга, и первый тянется с самой первой камеры: у неё есть логин и пароль. [**Урок 18**](18-Secrets.md) — про то, какие две точки касания у секрета законны, и почему всё остальное в системе его видеть не должно.
