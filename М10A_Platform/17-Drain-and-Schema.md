# Урок 17 — Обновление без простоя

**Модуль:** М10A — Платформа (ServerVMS, часть первая)
**Вы напишете:** `platform/drain` — одну строку с одним именем; `on_draining` и причину осушения в `leaving`, по которому идёт `redistribute`; `would_strand` — сухой прогон; `drain_state` с его `safe`; и вторую половину — `SCHEMA`, `check_schema`, `builds`, `set_schema`.
**Время:** ~70 минут.

## Зачем этот урок

Десять серверов, на каждом работают воркеры нескольких подсистем, и всё это надо обновить. Выключать всё сразу нельзя; выключать по одному можно — но каждый раз получать полторы минуты, когда единицы этой машины не обслуживает никто, тоже нельзя: за десять серверов это пятнадцать минут дыр (в М10B — дыр в записи камер), которые оператор увидит и не простит.

Причина этих полутора минут — в уроке 11, и она не ошибка. Единицы воркера уезжают, когда его слот залапсился **и** ресурс его сервера молчит: два независимых молчания, каждое по `lost_after`. Правило верное — одно молчание это упавший процесс, и его возвращает планировщик, — но оно про **аварию**.

Обновление аварией не является. Мы знаем о нём заранее. И весь этот урок — про то, что из этого следует.

Две половины, и они отвечают на разные вопросы:

| | вопрос | ответ |
|---|---|---|
| `platform/drain` | эту машину можно гасить? | по одной за раз, и работа уходит первой |
| `platform/schema` | все машины уже новые? | номер поднимают последним, а не первым |

Обе — строки в хранилище. Ни нового процесса, ни новой подсистемы, ни слова «обновление» ни в одной подсистеме.

> **Проверка без железа.** Полностью. Осушение — это строка, и её действие видно в двух функциях, которые уже проверяются тестами; версии — две строки и один скан объектов. Ни второй машины, ни настоящей перезагрузки для этого не нужно.

## Что нужно знать заранее

- **Урок 7** — слот и `release_slot`: осознанная отдача против просроченной. Осушение — третий вид «меня здесь нет», и первый, о котором говорят заранее.
- **Урок 11** — `_pool`, `eligible`, `home` и `ensure_home`: сюда осушение вставляется, и отсюда работа возвращается; `redistribute`, `without_resource`, `gone_servers`: реакции на молчание, к которым добавится одна реакция на заявление.
- **Урок 14** — ресурс и его heartbeat: второе молчание из двух.

## Чему вы научитесь

1. Отличать плановую остановку от молчания и объяснять, почему у них разная цена.
2. Выражать «эта машина сейчас уйдёт» так, чтобы ни одна подсистема не узнала нового слова.
3. Отвечать на «можно гасить?» условием, а не таймаутом.
4. Спрашивать «что станет неразмещаемым» до перезагрузки, а не после.
5. Ставить проверку версии в ту сторону, в которую надо, и поднимать номер в тот момент, в который надо.

## Шаг 1 — Одна строка, одно имя

```python
DRAIN_KEY = "platform/drain"


def draining(vars_) -> str:
    return DRAINS.read(DRAIN_KEY, lambda: str((vars_.get(DRAIN_KEY)[0] or {}).get("server", "")), "")
```

Строка **платформенная**, а не подсистемы: на машине стоят воркеры нескольких подсистем и ресурс, и уходят они вместе. Её читает каждый проход размещения каждой подсистемы, поэтому это одна маленькая строка, а не каталог: ответ стоит одного `get`. Чтение идёт через таблицу `DRAINS` (урок 8): строка, которую хранилище не может разобрать, читается как «никто не осушается» и считается, а не роняет проход.

Строка держит **одно** имя — и это вся взаимная блокировка, которая здесь нужна:

```python
    def drain(self, server: str) -> dict:
        def mutate(items):
            have = (items or {}).get("server", "")
            if have and have != server:
                raise DrainRefused(f"{have} is already draining; one server at a time")
            return {"server": server, "at": str(self.wall())}
        return self.write(DRAIN_KEY, mutate)
```

`write` — это CAS из урока 8. Два оператора одновременно, или скрипт с ошибкой в цикле, не могут осушить две машины сразу не потому, что кто-то догадался проверить, а потому, что запись одна и она под CAS.

И одна деталь про права в хранилище: осушение пишет **консоль**, не контроллер. Это заявление оператора, а не решение системы, — `DRAIN_KEY` попал в `acl_console`, из которого собраны права роли `console`, а у роли контроллера строка только в чтении. Та же линия, что в уроке 9: консоль не размещает, контроллер не редактирует.

## Шаг 2 — Два места, где строка действует

```python
    def on_draining(self, workers) -> list[str]:
        server = self.draining()
        return [w for w in workers if server and self.server_of(w) == server] if server else []

    def _pool(self, workers):
        pool = sorted(workers if workers is not None else self.workers_seen())
        leaving = {n for n, s in self.slots().items() if s.released}
        gone = set(self.without_resource(pool)) | set(self.idle_by_policy(pool)) | leaving | set(self.on_draining(pool)) \
            | set(self.on_decommissioned(pool))
        return [w for w in pool if w not in gone]
```

Ещё один член в множестве, которое уже было. «Не здесь» бывает пяти видов: слот отпущен, ресурс молчит, политика велела простаивать, машина уходит на время (`on_draining`) — и машина выведена насовсем (`on_decommissioned`, строка `platform/decommission/<server>`, тот же приём для конца сервера). Ни одна подсистема этого не заметит: они все ходят через `_pool`.

Но исключить из пула мало. Единицы, которые **уже** там стоят, надо увести, и для этого — вторая половина. `redistribute` спрашивает `leaving(seen)`, у каких воркеров единицы должны уйти и почему, и причина осушения стоит там:

```python
        for w in self.on_draining(seen):                               # an operator said this machine is about to stop
            if self.assignment(w).units:
                gone_for.setdefault(w, f"server {self.server_of(w)} draining")
```

Рядом в том же методе стоит ещё одна причина увести единицы с живого воркера, и она той же формы: **воркер жив, но нести единицы не может.** Там, где подсистема размещает по месту (`place_by: <поле heartbeat'а>`), воркер, который говорит это поле пустым, — запасной (`placeless`). Это нормальное состояние, пока у него нет назначений. Но воркер, потерявший своё место, остаётся жив, держит слот и не может сделать ни шага работы, а назначенные ему единицы стояли бы на нём, не обслуживаемые никем, сколько он жил (продукт нашёл это на своём ящике; обратная связь, BN; в М10B так теряет том регистратор). Он сам говорит, что места у него нет, и `leaving` уводит его единицы с причиной `"{w} holds no {place_by} now"`.

Ровно та же форма, что у `without_resource` выше в том же методе. Разница одна, и она вся в комментарии: там система **заметила**, здесь оператор **сказал**.

Причина размещения потом читается как обычно: `server srv-a draining; most free capacity (7); on srv-b`. Никакого особого режима, никакого флага «идёт обновление» — обычный переезд с обычной причиной.

## Шаг 3 — Сухой прогон

Пятьдесят единиц, уезжающих с машины, должны куда-то приехать. «Куда-то» — это факт про запас и метки, а не надежда:

```python
    def would_strand(self, server: str, workers: list[str] | None = None) -> list[str]:
        """Unit ids that nothing left could serve if `server` stopped now."""
        with one_pass(self):
            return self._would_strand(server, workers)

    def _would_strand(self, server: str, workers: list[str] | None) -> list[str]:
        pool = [w for w in self._pool(workers) if self.server_of(w) != server]
        out = []
        for row in self.units():
            uid = row["id"]
            pl = self.placement(uid)
            if pl is not None and self.server_of(pl.worker) != server:
                continue                                   # it is not on that server: not its business
            if not self._eligible_or_none(row, pool, "would_strand"):
                out.append(str(uid))                       # …nor one whose filters raise: nobody can say it lands
        return out

    # `eligible`, or `[]` when this unit's filters raise on its row — one unit's trouble, counted once a spell
    # (`UNIT_JUDGED`), not the end of the walk: a field that read and then raised in a comparison or in an `admit` took
    # `/unplaceable` and `/drain` down for every unit (the review's tenth pass).
    def _eligible_or_none(self, row: dict, pool: list[str], walk: str) -> list[str]:
        key = f"{self.row_key(row['id'])}#{walk}"
        return UNIT_JUDGED.read(key, lambda: self.eligible(row, pool), [])
```

Тем же `eligible`, который будет отвечать по-настоящему через минуту. Это важно: сухой прогон, считающий по своей формуле, рано или поздно разойдётся с настоящим размещением, и разойдётся молча. Тест: `test_lesson11_edge.py::test_the_dry_run_answers_before_the_reboot_not_after`.

**Единица, чьи фильтры бросают исключение, стоит только себя.** `eligible` звался голым на каждую единицу. Поле, которое прочиталось, но падает в сравнении фильтра, роняло `/drain` целиком, для всех единиц, хотя шаги контроллера уже переступали через одну единицу (десятое ревью закрыло корни: пульс без имени сервера, `device_of`, — а защиты на единицу у этого обхода не было). Теперь `eligible` идёт через `_eligible_or_none`. Единица, на которой он упал, для сухого прогона — та, которую никто не примет: про неё нельзя сказать, что она приедет, а настоящее размещение её тоже не поставит (`ensure_placed` пропускает её с исключением в логе). Она считается раз за серию на обход (таблица `unit_judged`, на `/metrics` консоли — `<p>_console_rows_garbled{table="unit_judged"}`), и остальные единицы считаются как обычно. Тест: `test_one_bad_element.py::test_a_unit_whose_filters_raise_is_one_nothing_can_serve_and_the_others_are_judged`.

**Сухой прогон — один проход по чтениям.** Для каждой единицы он спрашивает её размещение, сервер её воркера и `eligible` по пулу, а `eligible` — heartbeat'ы и запас каждого воркера; без кэша это было бы по чтению хранилища на каждый вопрос каждой единицы. Поэтому `would_strand` открывает `one_pass` (урок 8, шаг 1): внутри каждый ключ читается один раз, а между вызовами не помнится ничего. Сам расчёт — в `_would_strand`. `drain_state` консоли зовёт `would_strand` на каждый `GET /drain` и получает свежие чтения: проход кончается вместе с вызовом. А позванный изнутри уже открытого прохода, `one_pass` ничего нового не открывает — проход внутри прохода считается внешним.

Альтернатива вопросу — прочитать `/unplaceable` **после** перезагрузки, когда единицу уже не обслуживает никто. Разница между «спросил и не стал» и «сделал и увидел» здесь стоит ровно столько, сколько стоит работа этой единицы.

## Шаг 4 — Условие вместо `sleep`

Вот к чему всё шло. Скрипт обновления не должен спать и надеяться:

```python
    def drain_state(self, server: str = "") -> dict:
        ctl, now = self.ctl, self.wall()
        server = server or ctl.draining()
        if not server:
            return {"draining": "", "subsystem": ctl.spec.name}
        here = [w for w in heartbeats(ctl.objects, ctl.sub.name + "/") if ctl.server_of(w) == server]
        units = sum(len(ctl.assignment(w).units) for w in here)
        strand = ctl.would_strand(server)
        …
        return {"draining": server, "subsystem": ctl.spec.name, "workers": sorted(here),
                "units": units, "would_strand": strand, "safe": units == 0}
```

`safe` — одно слагаемое: **единиц не осталось**. На каждом воркере подсистемы, чей heartbeat говорит этот сервер, назначение пусто. Работа уехала, и это видно контроллеру по его же строкам (`test_lesson11_edge.py::test_the_upgrade_script_polls_a_condition_instead_of_sleeping`: оба воркера на осушаемом сервере отдают свои единицы воркерам на соседнем — и `safe` истинно).

Это ровно то, что `safe` утверждает, и не больше. Оно ничего не говорит о том, что воркер ещё **не дописал**. Платформа знает назначения, а не данные: что воркер держит у себя — открытый файл, буфер в памяти, очередь на диске машины, — в его строках не видно, и `drain_state` об этом не спрашивает. Воркер, у которого на диске осушаемой машины лежит очередь недописанного, получит `safe` в ту минуту, когда у него забрали последнюю единицу, а не когда очередь ушла. Помните это, читая `safe`: «работы здесь больше нет», а не «здесь больше нечего терять».

Маршрут `GET /drain` живёт на `Mount`, а не на подсистеме: машина несёт несколько, и `safe` истинно, только когда так говорит каждая. И за воротами, как любой маршрут: изменить — `admin`, прочитать — `view`; вывод и возврат сервера и подъём схемы — строки журнала (`drain.started`, `drain.ended`, `schema.raised`). Сначала эти маршруты отвечали до ворот — `POST /drain` без токена уводил все единицы с сервера (третье ревью, блокер 2; М10A, урок 15). Скрипту обновления, который их зовёт, нужен токен администратора; `PUT /schema` к тому же пишет строку платформы, которой нет в правах роли `console` в хранилище, — и при отказе хранилища отвечает 403 с его словами (`this console's token does not reach platform/schema`), а не обрывом.

## Шаг 5 — Глагола «сбрось» нет

Тут стоит остановиться, потому что хочется добавить механизм, которого в платформе нет.

Хочется добавить в осушение команду «сбрось всё, что не дописано, и только потом скажи `safe`». Платформа такой команды не даёт, и вот что вместо неё. Машину после `safe` гасят **штатно**: супервизор шлёт каждому юниту SIGTERM и ждёт его `StopTimeout` (у юнитов воркеров на ящике — от 10 до 40 секунд, `deploy/*worker@.container`). По SIGTERM воркер заканчивает своё и последним шагом отпускает слот с пометкой `released` (`release_slot` базового `Worker`, урок 7) — это и отличает штатную остановку от аварии. Что именно «своё», решает воркер: закрыть файл, сбросить буфер, отдать очередь. Платформа здесь знает одно — что процесс остановился штатно.

Команда «сбрось», добавленная в осушение, дублировала бы то, что воркер делает при штатной остановке. Это второй путь к тому же состоянию, и расходиться они начнут в первый же нештатный день. Правило, которое стоит унести из этого шага: прежде чем добавлять глагол, посмотрите, не является ли нужное вам уже следствием.

Граница этого правила — та же, что в шаге 4. Штатная остановка закрывает то, что воркер успевает закрыть за `StopTimeout`. Чего за это время не закрыть — долгой очереди на диске машины, — `safe` сегодня не видит.

## Шаг 6 — Вторая половина: направление проверки

Обновление по одной машине означает, что старые и новые процессы какое-то время работают над одним хранилищем. Добавить поле — бесплатно. Поменять смысл поля — нет, и это новый номер:

```python
SCHEMA = 1
SCHEMA_KEY = "platform/schema"


def check_schema(vars_) -> int:
    have = schema_version(vars_)
    if have > SCHEMA:
        raise SchemaTooNew(f"store is at schema {have}; this build understands {SCHEMA}")
    return have
```

Проверяется **одно** направление, и это вся суть.

**Новый процесс против старого хранилища — нормально.** Он понимает старую раскладку; в этом и состоит обновление. Если запретить и это, обновляться будет нечем.

**Старый против нового — отказ стартовать.** Громко, в цикле перезапусков, который оператор видит, — а не тихо, теряя незнакомые поля на первом же read-modify-write. Второе страшнее, потому что выглядит как работающая система.

Вызов стоит в конструкторах `Controller`, `Worker` и `Resource` — то есть забыть его нельзя. Отсутствующая строка означает «свежая установка», и проверка проходит.

## Шаг 7 — Номер поднимают последним

```python
    def set_schema(self, version: int) -> dict:
        now = self.wall()
        behind = {n: b for n, b in builds(self.objects, now, eyes=self.eyes).items()
                  if b["live"] and (b["schema"] is None or b["schema"] < version)}   # not known: behind any (`builds`)
        if behind:
            known = [b["schema"] for b in behind.values() if b["schema"] is not None]
            raise SchemaTooNew(f"still running: {', '.join(sorted(behind))} — at schema "
                               f"{min(known) if known else 'not known'}")
        …
            if version < have:
                raise SchemaTooNew(f"schema does not go back: {have} -> {version}")
            return {"version": str(version), "at": str(now)}
        return self.write(SCHEMA_KEY, mutate)
```

Процесс, чья схема в heartbeat'е не читается, — «не известно», и он отстаёт от любой версии: иначе процесс, которого `builds` не перечислил, не мешал бы подъёму, а подъём запер бы именно его.

Если бы номер поднимал первый обновлённый процесс, он заблокировал бы все ещё не обновлённые машины — то есть устроил бы ровно тот простой, ради избежания которого затевалось скользящее обновление. Поэтому подъём — отдельный шаг оператора, после того как всё новое.

«Всё новое» — проверяемо, и проверять нечем новым: каждый процесс и так публикует свой номер.

**И при возвращении — тоже последняя прочитанная.** `rejoin` звал `check_schema` без последней известной версии, и воркер, огороженный за слот, на битой строке схемы не возвращался никогда (четвёртое ревью). Теперь `rejoin` передаёт `schema_seen`; а воркер, огороженный именно **из-за** схемы, забывает свою версию — иначе на следующей битой строке он вернулся бы со старой. Тест: `test_a_worker_fenced_for_its_slot_rejoins_over_a_garbled_schema_row_and_one_fenced_for_the_schema_does_not`.

**Имя на хранилище новее сборки не берут — и под отданным молчат.** Свободный слот огороженный воркер берёт одной дорогой, `_seek_slot` (урок 8), и она сверяет схему первой — для всех воркеров, а не только в `rejoin` держателя (шестое ревью). Вторая половина — про heartbeat. Отсечённый за схему держит слот в руках и продолжает говорить `fenced: true` под своим именем; но слот он не продлевает (`renew_slot` бросает `SchemaTooNew` раньше, чем читает строку), строка протухает, имя берёт новая сборка — и старый процесс писал heartbeat поверх неё. Теперь на каждом шаге аренд он читает свою строку (`name_taken`), и с шага, который видит в ней другой экземпляр, под этим именем не пишет ничего. Тесты: `test_slot_fence.py::test_a_holder_fenced_for_the_schema_stops_speaking_when_another_instance_takes_its_name`, `test_a_worker_on_a_store_raised_past_its_build_is_nobody_once_another_instance_takes_its_name`.

**Битая строка схемы — не новая схема.** Сверка при каждом продлении сделала строку `platform/schema` точкой отказа всего парка: строка, которая не разбирается, останавливала продление аренд и heartbeat у всех (третье ревью). Теперь `check_schema(vars_, last=)`: работающий процесс держит версию, которую прочитал целой последней, и отсекается только версией, которая **разбирается и новее**; процесс, который схему не читал ни разу, с битой строкой не стартует. Тест в `test_lesson1_platform.py`.

**И проверяется не один раз.** Старая сборка сверяла схему при старте и публиковала номер только с первым heartbeat'ом — после прохода. Стартовав в это окно, она проходила проверку `set_schema` (её ещё не видно) и дальше работала со старой схемой поверх новой (ревью платформы, m4). Теперь `renew_slot` сверяет схему перед каждым продлением (`check_schema`): хранилище ушло вперёд — `SchemaTooNew`, воркер отсекается (`lease_pass` → `fence`) и **не возвращается** (`rejoin` сверяет первым делом), пока его не обновят. Цена — одно чтение `platform/schema` на продление; в трассах стенда М11 оно теперь видно. Тест: `test_lesson1_platform.py::test_a_build_the_store_outgrew_while_it_ran_fences_and_does_not_rejoin`.

```python
    def heartbeat(self, status: list[dict], **extra) -> None:
        extra.setdefault("schema", SCHEMA)
        extra.setdefault("build", BUILD)
```

Из базового класса, поэтому ни одна подсистема про это не помнит. А `builds` находит их все одним сканом, потому что ключи heartbeat'ов у всех устроены одинаково — `<подсистема>/heartbeats/<воркер>` и `platform/resources/<server>/heartbeat`, и ничего другого под это не подходит:

```python
def builds(objects, now: float, lost_after: float = 45.0, eyes: "Eyes | None" = None) -> dict[str, dict]:
    …
    out = {}
    for key in objects.list(""):
        if not is_heartbeat_key(key):
            continue
```

Назад номер тоже не идёт. Откат сборки — это откат кода, а не раскладки: данные, написанные новой версией, старая не разучится читать оттого, что ей поменяли число.

## Шаг 8 — Круг целиком, и где он дрейфует

```
POST /drain?server=srv-a
polling GET /drain   →  {"safe": false, "would_strand": {...}}
                     →  {"safe": true}
гасим · обновляем · поднимаем
DELETE /drain
ждём, пока работа вернётся
следующий сервер
PUT /schema?version=2      ← один раз, когда все десять новые
```

Предпоследняя строка — не формальность. `ensure_home` возвращает **одну** единицу за проход (`budget: int = 1`): сервер с полусотней единиц набирает их назад минут за пять. Это правильно — постепенно, без шторма эпох, — но если скрипт считает признаком готовности «машина загрузилась», а не «работа вернулась», то за десять серверов единицы сдрейфуют: каждое следующее осушение сгоняет их на ещё не обновлённые машины, а вернуться они не успевают.

К концу круга последние две машины несут всё. Ёмкость их воркеров (`placement.capacity`) на исходе, и следующая единица, которой не хватит места, станет неразмещаемой, хотя восемь машин стоят почти пустыми. Что ещё стоит перегрузка, знает подсистема: в М10B, например, на этих машинах тома записи начнут оборачиваться быстрее (урок 27 М10B). Формально ничего не сломалось. Практически вы обновили кластер и собрали его работу на двух машинах.

## Что может пойти не так

| Симптом | Скорее всего |
|---|---|
| Полторы минуты без работы на каждой машине | Осушения нет: система ждёт двух молчаний вместо того, чтобы прочитать заявление. |
| Единицы не уезжают, хотя строка написана | Есть `_pool`, нет причины в `leaving`: новых туда не ставят, старые остаются. |
| Осушили две машины разом | Строка держит список вместо одного имени. CAS тут ни при чём — форма данных. |
| Воркер не дописал своё | Сервер выключили, не дав воркерам штатно остановиться, — или воркеру не хватило `StopTimeout`. `safe` говорит, что работа ушла, а не что процессы остановлены и всё дописано. |
| Единицы стали `unplaceable` после перезагрузки | Сухой прогон не спросили. Он отвечает тем же `eligible`, что разместит потом. |
| Старая сборка молча портит строки | Проверка схемы поставлена в обратную сторону — или её нет в конструкторе. |
| Половина кластера в цикле перезапусков | Номер подняли до конца обновления. Это и есть тот простой, которого избегали. |
| К концу круга две машины несут всё | Скрипт шёл дальше по «машина загрузилась» вместо «работа вернулась». |

## Итог

- Плановая остановка — не молчание: о ней известно заранее, и работа может уйти первой.
- Одна строка, одно имя: взаимная блокировка — это форма данных плюс CAS, а не отдельная проверка.
- Действует в двух местах: не ставить туда (`_pool`) и увести оттуда (`leaving`, по которому идёт `redistribute`). Первого без второго мало.
- Заявление оператора пишет консоль; контроллер читает. Та же линия, что между размещением и редактированием.
- Сухой прогон отвечает той же машинерией, что ответит по-настоящему, — иначе он однажды разойдётся с ней молча.
- Готовность — условие, а не таймаут: единиц не осталось. Это условие про назначения, не про данные: что воркер ещё не дописал, `safe` не видит.
- Прежде чем добавлять глагол, проверьте, не следствие ли это. Дописать своё воркер успевает при штатной остановке, до `release_slot`.
- Проверка версии — в одну сторону: новый против старого хранилища работает, старый против нового не стартует.
- Номер поднимают последним, и только когда каждый живой процесс сказал, что понимает его.
- Возврат домой идёт по одной единице за проход. Признак «можно дальше» — вернувшаяся работа, а не загрузившаяся машина.

## Упражнения

1. Уберите `on_draining` из `_pool`, оставив причину в `leaving`. Осушите сервер и опишите, что будет происходить с единицами следующие три прохода.
2. И наоборот: оставьте `_pool`, уберите причину. Сколько единиц уедет с машины?
3. Сделайте строку списком серверов. Осушите два из трёх и посчитайте, сколько единиц станут неразмещаемыми.
4. Добавьте в `safe` второе слагаемое: «каждый воркер на этой машине остановился». Осушите сервер и скажите, когда условие станет истинным — и почему скрипт обновления теперь не дождётся его никогда.
5. Остановите воркер `kill -9` вместо штатной остановки, пока `safe` ещё ложно. Каким путём теперь уедут его единицы (урок 11), сколько это займёт и что прочитает контроллер в его слоте? Что из недописанного воркером пропало (в М10B это разбирает урок 27, `reattached`)?
6. Поставьте проверку схемы в обе стороны (новый процесс тоже отказывается против старого хранилища). Опишите, как теперь выглядит обновление.
7. Пусть номер поднимает первый новый процесс. Прогоните обновление десяти серверов на бумаге и скажите, на каком по счёту всё встанет.
8. Напишите скрипт обновления, который идёт дальше по «машина загрузилась». Десять серверов, пятьдесят единиц на каждом, `ensure_home(1)` раз в пять секунд: где окажутся единицы к концу круга?

## Что дальше

Платформа умеет разместить работу, вернуть её домой, освободить место и пережить обновление — и ничего из этого не знает о подсистемах: ни что такое камера, ни что такое запись. Строка осушения — про сервер, `safe` — про назначения, схема — про номер в heartbeat'е. Ни одна подсистема М10B не добавит к этому уроку ни строки и не получит в нём ни одного своего слова: осушение видно им через `_pool` и `leaving`, а версию они публикуют из базового класса, не зная об этом. И обратное тоже правило: причина любого механизма этого урока должна быть общей. Если объяснить его можно только данными одной подсистемы, он принадлежит ей, а не платформе.

Остались три долга, и первый тянется с первой же единицы, которой нужен вход куда-то: у неё есть логин и пароль (в М10B — у камеры). [**Урок 18**](18-Secrets.md) — про то, какие две точки касания у секрета законны, и почему всё остальное в системе его видеть не должно.
